# AI 开发团队：外出远程开发工作台架构

> 目的：回答“人在外出、仅通过聊天工具，是否仍能继续开发”这一目标下，当前架构是否足够，以及还缺哪些关键能力与对象。

---

## 一、核心结论

如果目标是：

- 人在外出
- 主要通过聊天工具参与协作
- 不依赖 IDE 也能继续推进开发
- 由 AI 助手与多个专业 Agent 持续工作
- 人类只在关键节点做确认、纠偏、审批

那么当前架构：

- **作为后台控制面、事实面、编排面，方向是对的**
- **作为“纯聊天式远程开发工作台”的完整产品架构，还不够完整**

更准确地说：

> 当前体系已经具备“AI 开发团队”的后台骨架，但还缺一个正式的“会话协作层 / 远程工作台层”。

也就是说，现在不是要推翻现有 `3+1` 架构，而是要在其上补一个面向聊天、群聊、异步协作、移动端交互的前台工作层。

---

## 二、先明确目标：你真正想做的是什么

我建议把目标从“在聊天工具里集成一个 AI 助手”升级为更准确的表达：

> **一个面向外出、异步、移动场景的 AI 开发团队工作台。**

这个工作台的关键特征应是：

- 聊天是入口
- 群聊是协作空间
- AI 助手和专业 Agent 是执行者
- 正式对象和阶段流程是约束与落点
- 云端资产库是事实底座
- 人类通过卡片、摘要、审批、指令来持续指挥开发推进

这和普通聊天工具 + AI 插件是两回事。

---

## 三、当前架构已经能支撑哪些能力

### 1. 已有正式事实底座

当前已经有：

- `研发协作平台`：项目、需求、任务、缺陷、验收
- `工程执行平台`：代码、接口、测试、制品
- `发布运行平台`：发布、灰度、回滚、事故、监控
- `AI 编排与知识平台`：Agent 模板、策略、上下文快照、权限、审计、工作记录

这意味着：

- 开发过程不只存在聊天消息里
- AI 不只是“说建议”，还可以绑定正式对象
- 每一步推进都能回到 SoR，而不是变成不可追溯的对话

### 2. 已有流程化推进基础

当前已经定义了：

- 阶段 0 到阶段 5 的主流程
- `entry_contract`
- `handoff_package`
- `exit_packet`
- `workflow_completion_record`
- `loop_events`
- `rollback / return / hold` 等正式语义

这意味着系统不是随意聊天，而是可以把开发协作嵌入正式阶段流转中。

### 3. 已有恢复现场能力雏形

当前已经具备：

- `上下文快照库`
- `worklog / 工作记录`
- `会话恢复点`
- `审计轨迹`

这对“人在外出、回来继续接手”非常重要。

---

## 四、为什么说当前还不能完全满足

真正的问题不在于“有没有任务库、发布库”，而在于：

> **是否已经具备了一个聊天驱动、异步持续、移动端友好的协作运行时。**

这部分当前还没有被正式建模成一层独立能力。

---

## 五、当前最关键的缺口

### 1. 缺少会话协作层

当前架构更多解决的是：

- 正式对象怎么建模
- 流程怎么推进
- AI 怎么受控
- 事实怎么回写

但如果你在外面主要通过聊天工具继续开发，还需要系统原生支持：

- 聊天会话
- 群聊
- 线程
- 人类与 AI 混合参与者
- 消息驱动动作
- 异步协作和通知

这层还没有被正式拉出来。

### 2. 缺少“消息 -> 正式动作”转换层

如果你在外面发一句：

- “先让测试 agent 补测试”
- “这个先不要发布”
- “进入阶段 2”
- “给我一个今日进展摘要”
- “灰度继续，但异常就 hold”

系统必须能把这类消息转换成：

- 正式指令
- 动作卡
- 执行任务
- 审批动作
- 工作流状态变化

这意味着要有一层明确的：

- 消息解析
- 指令识别
- 动作生成
- 执行编排
- 结果回写

### 3. 缺少移动端优先的信息组织方式

外出场景下，用户通常：

- 不会看长文档
- 不会看复杂表格
- 不会看太长 diff
- 不会持续在线盯多个界面

所以系统必须优先提供：

- 自动摘要
- 当前状态卡
- 缺失项卡
- 风险卡
- 审批卡
- 下一步建议卡

否则即使后台能力很强，移动端也不可用。

### 4. 缺少异步工作模式

外出时的真实工作模式不是“你一直在线聊天”，而是：

- 你发目标
- AI 在后台持续推进
- 遇到关口再来找你
- 你不在线时先积累结果
- 你回来后看摘要和待决策项

所以必须支持：

- 异步 Agent 执行
- checkpoint
- 待审批等待点
- 通知与提醒
- 日报式摘要

### 5. 缺少“远程模式”权限边界

人在外出时，系统不能默认让 AI 无限制执行所有动作。

至少要区分：

- AI 可自动执行的动作
- 聊天中确认即可执行的动作
- 必须桌面端确认的动作
- 外出模式禁止执行的动作

否则风险会很大。

---

## 六、如果目标是“外出也能继续开发”，更准确的定义是什么

我建议把目标收敛成：

> **外出时，用户不一定亲自编码，但仍能通过聊天持续指挥 AI 开发团队推进开发。**

这比“在手机上像在 IDE 里一样开发”更现实，也更符合系统设计。

### 这个目标包含三层能力

#### 1. 管理式继续开发

用户可以通过聊天：

- 看进度
- 看摘要
- 批动作
- 批风险
- 改方向
- 做审批

#### 2. 编排式继续开发

用户可以让 AI：

- 继续做任务拆解
- 继续补方案
- 继续补测试
- 继续推动阶段流转
- 继续执行低风险工程动作

#### 3. 轻量审阅式继续开发

用户可以：

- 看 PR 摘要
- 看 diff 摘要
- 看改动风险提示
- 选择同意 / 退回 / 让 AI 修改

我不建议把“移动端亲自大规模写代码”作为主目标，那不是这套系统最擅长的方向。

## 八、我建议补出的关键能力

### 1. 聊天驱动动作卡系统

让消息可以被转换成正式动作，例如：

- 创建需求
- 创建任务
- 发起评审
- 进入下一阶段
- 请求补测试
- 发起发布检查
- 暂停 / 恢复 / hold / rollback

### 2. 异步 Agent 持续执行机制

支持：

- 用户一句话发目标
- Agent 后台持续工作
- 到 checkpoint 或风险点时再通知用户
- 用户不在线也不阻塞低风险推进

### 3. 移动端优先卡片系统

至少要有：

- 当前状态卡
- 达标状态卡
- 缺失项卡
- 风险卡
- 审批卡
- 下一步动作卡
- 今日摘要卡

### 4. 会话与流程绑定机制

要明确：

- 一个群聊是否对应一个项目
- 一个线程是否对应一个阶段
- 一条消息如何绑定正式对象
- 一次会话如何绑定 `workflow_session`

### 5. 轻量审阅能力

至少支持：

- PR 摘要
- diff 摘要
- 风险摘要
- 测试摘要
- 发布摘要
- 审批按钮

### 6. 远程模式权限策略

需要引入：

- `auto_allowed`
- `chat_approval_required`
- `desktop_approval_required`
- `remote_forbidden`

这样的动作等级。

## 九、当前架构最适合怎样演进

我不建议推翻现有 `3+1`，而建议补成下面这个结构：

### 1. 前台：AI 开发团队工作台

负责：

- 聊天
- 群聊
- 线程
- 卡片
- 移动端消息交互
- 状态总览
- 摘要与审批

### 2. 中间层：会话协作运行时

负责：

- 消息服务
- 会话状态机
- 参与者与角色路由
- Agent turn 调度
- 动作卡执行
- 通知与提醒
- 会话快照与恢复

### 3. 后台：现有 `3+1`

负责：

- 正式业务与工程事实
- 流程对象
- 发布运行控制
- AI 编排、快照、审计、权限、知识

### 一句话理解

- 工作台负责“怎么聊、怎么批、怎么协作”
- 运行时负责“怎么转成动作、怎么异步跑、怎么恢复现场”
- `3+1` 负责“事实落哪、流程怎么走、AI 怎么受控”

## 十、如果不补这层，会出现什么问题

### 1. 聊天很多，但无法形成正式推进

- 群里讨论很多
- 但没有正式对象落点
- 也没有阶段推进闭环

### 2. 多 Agent 容易失控

- 谁该发言
- 谁该执行
- 谁能做决定
- 谁只能提供建议

这些都可能混乱。

### 3. 外出场景下信息爆炸

- 太多消息
- 太多文档
- 没有摘要和卡片
- 用户无法在手机上快速判断

### 4. 高风险动作缺乏远程约束

- AI 可能推进过头
- 人类不在线时没有明确审批门
- 容易造成“移动端误触发”式风险

## 十二、对“当前是否满足”的最终判断

我的判断是：

- **后台骨架：基本满足**
- **流程与正式对象：基本满足**
- **AI 编排与恢复现场：方向正确**
- **聊天式远程协作运行时：还不满足**
- **移动端外出开发工作台：还需要专门设计**

如果一定给一个成熟度估计，我会这样看：

- 正式对象与流程底座：`80%`
- AI 编排基础：`75%`
- 会话协作运行时：`35%`
- 外出远程工作台：`30% ~ 40%`
- 整体支撑“外出时继续开发”：`60%` 左右

也就是说：

> 当前架构已经足够支撑“AI 开发团队”的后台骨架，但还不足以直接支撑“外出时通过聊天工具持续开发”的完整产品目标。

## 十三、运行节点与展示终端应显式分离

我建议把这套系统进一步抽象成：

> **运行节点负责持续执行，展示终端负责连接、展示、输入与审批。**

这样后面就不会再被“到底该部署在服务器还是本机”这个问题卡住。

### 1. 什么是运行节点

运行节点是系统真正干活的地方，负责：

- 云端库服务
- 会话协作后端
- workflow 编排
- agent runtime
- worklog / snapshot
- Search / Extract / Decision View
- 任务队列
- 审计与权限
- 远程开发工作区

也就是说：

- Agent 在这里运行
- 状态在这里保存
- 任务在这里推进
- 快照在这里恢复

### 2. 什么是展示终端

展示终端不承担主执行职责，主要负责：

- 聊天交互
- 群聊与线程浏览
- 状态卡与风险卡展示
- 审批与确认
- 轻量控制与摘要查看
- 必要时打开更深层详情

我建议把它理解成：

- 手机 App
- Mac 客户端
- Windows 客户端
- Web 工作台

它们都只是连接运行节点的入口，而不是系统主现场。

### 3. 这样抽象后的直接好处

- 退出本地终端，不等于系统停工
- 更容易支持外出场景与多端接入
- 更容易支持群聊型多 Agent 协作
- 更容易统一审计、快照、审批与任务队列
- 更容易支持服务器部署和桌面自托管两种形态

---

## 十四、我建议固定三种部署形态

如果采用“运行节点 + 展示终端”的抽象，我建议直接固定三种部署形态。

### 1. Server Mode

运行节点部署在 Linux 服务器。

特点：

- 最适合持续运行
- 最适合团队协作
- 最适合外出场景
- 多端接入最自然

适合：

- 个人长期运行
- 小团队协作
- 私有服务器 / 云主机部署

### 2. Desktop Self-Hosted Mode

运行节点部署在 Mac / Windows 电脑，本机同时也可以作为展示终端。

特点：

- 没有服务器时也能跑完整系统
- 适合个人版 / 本地自托管版
- 架构上仍和 Server Mode 一致，只是宿主不同

我建议把它理解成：

> **电脑本地不是“临时 App 模式”，而是“本机自托管运行节点模式”。**

### 3. Mobile Client Mode

移动端默认不承载主运行节点，而作为展示终端存在。

特点：

- 适合查看摘要、状态、风险、待审批项
- 适合发指令、看群聊、做轻量决策
- 不适合作为主 agent runtime 宿主

原因主要是：

- 后台保活能力弱
- 长任务不稳定
- 开发工作区能力不足
- 系统权限与文件能力受限

所以我建议固定一个结论：

> **移动端适合做客户端，不适合做主运行节点。**

---

## 十五、这样设计后，服务器与本地就统一了

你现在这个新思路最重要的价值，就是把“远程”和“本地”统一成了同一个概念框架。

### 1. 有服务器时

- 把运行节点部署到 Linux 服务器
- 把后端库服务、会话协作层、agent runtime、工作流编排都跑在服务器
- 手机 / Mac / Windows 都作为展示终端接入

### 2. 没服务器时

- 把同一套运行节点部署在你的电脑上
- 电脑既是宿主节点，也是一个展示终端
- 其他设备仍可作为客户端接入

所以真正变化的不是产品模型，而只是：

- 运行节点宿主是谁
- 是否持续在线
- 网络访问边界如何配置

### 3. 我建议固定的总原则

我建议把这一条钉死：

> **系统默认采用“前端无状态、运行节点可迁移部署”的结构；有服务器时跑服务器，没有服务器时跑本机，但前端交互模型不变。**

这会让后面产品和工程都更清晰。

---

## 十六、对你的目标，我建议的推荐结论

如果结合你当前“AI 开发团队 + 外出继续开发 + 聊天工作台”的目标，我建议最终收敛成下面这版：

### 推荐方向

- 后端统一做成 `运行节点`
- 前端统一做成 `展示终端`
- Agent、workflow、worklog、snapshot、任务队列都归运行节点
- 手机 / Mac / Windows / Web 都只是连接运行节点的客户端
- 服务器部署与桌面自托管只是部署形态差异，不应演变成两套产品

### 一句话版

> **一套后端、多个宿主节点、多个展示终端。**

## 十七、运行节点模块拆分建议

如果继续往实现层推进，我建议把“运行节点”进一步拆成一组清晰模块，不然后面很容易把聊天、编排、执行、审计混成一个大服务。

### 1. 我建议的一级模块

| 模块 | 主要职责 |
|------|----------|
| `conversation_service` | 管理群聊、线程、消息、消息附件、提及路由 |
| `presence_service` | 管理在线状态、谁正在处理、谁在等待审批 |
| `agent_runtime_service` | 承载 Agent 生命周期、任务执行、运行状态 |
| `workflow_orchestrator` | 承载阶段流程、任务编排、checkpoint、resume |
| `action_card_service` | 把聊天意图转成动作卡、审批卡、执行卡 |
| `artifact_binding_service` | 绑定消息、卡片、线程与正式对象 |
| `snapshot_service` | 管理会话快照、运行快照、恢复点 |
| `worklog_service` | 记录关键动作、判断、切换原因与产出引用 |
| `policy_service` | 管理权限、审批、远程模式策略、动作分级 |
| `integration_gateway` | 对接项目库、任务库、测试库、发布库等外部事实源 |
| `search_extract_service` | 提供 Search / Extract / Decision View 能力 |
| `notification_service` | 管理提醒、待决策通知、日报摘要推送 |

### 2. 我建议优先保住的边界

我建议至少先把下面几条边界钉死：

- `conversation_service` 不直接改正式对象，它只管理会话事实
- `workflow_orchestrator` 不自己伪造业务事实，它只编排与聚合
- `agent_runtime_service` 不直接决定审批是否通过，它只执行被允许的任务
- `integration_gateway` 负责访问外部 SoR，不让各模块自己乱调项目库/发布库
- `snapshot_service` 和 `worklog_service` 分开，前者偏恢复，后者偏解释与审计

## 十八、各模块职责再细一层

### 1. `conversation_service`

负责：

- `workspace`
- `channel`
- `group_chat`
- `conversation_thread`
- `message`
- `message_attachment`
- `mention_routing_rule`

它回答的是：

- 谁在聊
- 聊在哪个线程
- 消息和卡片如何组织
- `@Assistant` / `@TechLead` / `@Tester` 如何被路由

### 2. `agent_runtime_service`

负责：

- Agent 启停
- 运行上下文装配
- 任务执行状态
- async run
- 错误状态
- 重试与挂起

它回答的是：

- 哪个 Agent 正在处理
- 当前处理到哪一步
- 是运行中、挂起中、失败还是等待恢复

### 3. `workflow_orchestrator`

负责：

- `workflow_session`
- 阶段切换
- checkpoint
- resume
- loop / return / rollback 路由
- 与正式阶段对象的映射

它回答的是：

- 当前流程在哪个阶段
- 是否允许进入下一步
- 出现回环 / 退回 / rollback 时如何编排

### 4. `action_card_service`

负责：

- 从聊天消息中识别可执行动作
- 生成 `action_card`
- 生成 `approval_card`
- 管理卡片状态流转

它回答的是：

- 这条消息是否应转成正式动作
- 当前需要自动执行、聊天确认还是更高等级审批

### 5. `artifact_binding_service`

负责：

- 消息与正式对象绑定
- 卡片与任务 / 需求 / 发布对象绑定
- 线程与 `workflow_session` 绑定
- 证据引用关系维护

它回答的是：

- 这条聊天内容到底落到了哪个正式对象
- 这次审批、这张卡、这条消息对应哪条事实链

### 6. `snapshot_service` 与 `worklog_service`

我建议这两个显式分开：

- `snapshot_service`：负责恢复现场
- `worklog_service`：负责解释做过什么

也就是：

- `snapshot` 偏“继续执行”
- `worklog` 偏“理解历史”

### 7. `integration_gateway`

负责统一对接：

- 项目库
- 需求库
- 任务库
- 接口库
- 测试库
- 发布库
- 监控/事故库

它非常关键，因为它保证：

- 外部 SoR 接入方式统一
- AI 模块不直接散落调用各业务系统
- 认证、缓存、重试、限流在同一层收敛

## 十九、模块之间的最小事件协作建议

为了避免后面做成同步大泥球，我建议运行节点内部尽量采用事件协作。

### 1. 一条最小链路

```text
message_received
-> mention_routed
-> action_card_created
-> action_card_approved | action_card_rejected
-> agent_run_started
-> workflow_checkpoint_updated
-> artifact_bound
-> worklog_written
-> digest_updated
```

### 2. 我建议优先固定的内部事件

| 事件主题 | 说明 |
|----------|------|
| `conversation.message-received` | 收到新消息 |
| `conversation.mention-routed` | 提及已路由到人或 Agent |
| `action-card.created` | 动作卡已生成 |
| `action-card.approved` | 动作卡已批准 |
| `agent-run.started` | Agent 开始执行 |
| `agent-run.suspended` | Agent 因资源/权限原因挂起 |
| `workflow.checkpoint-updated` | 编排进度已更新 |
| `artifact.binding-created` | 已绑定正式对象 |
| `snapshot.created` | 创建恢复点 |
| `worklog.written` | 关键工作记录已写入 |
| `digest.updated` | 摘要已更新 |

### 3. 我建议避免的耦合

- 不要让 `conversation_service` 直接调 `agent_runtime_service` 的内部方法
- 不要让 `agent_runtime_service` 直接写业务主库
- 不要让 `workflow_orchestrator` 直接改消息状态
- 不要把所有审批逻辑都塞进 `action_card_service`

我建议始终通过：

- 明确 API
- 明确事件
- 明确对象绑定

这三种方式协作，而不是隐式串逻辑。

## 二十、对下一步实现最有价值的收敛建议

如果你准备继续 formalize，我建议下一步最值得做的是下面两个方向：

1. `把运行节点的一级模块继续落成正式对象与 API`
2. `把展示终端的信息架构映射到这些模块产出的对象与事件`

其中我更建议先做第一个，因为：

- 模块清楚了，后端边界就清楚
- 后端边界清楚了，前端页面和卡片才能稳定
- 后面无论是 Server Mode 还是 Desktop Self-Hosted Mode，都会更容易落地

## 二十一、这套体系应做成一套框架还是两套框架

如果继续往“LLM 框架”方向思考，我不建议把它做成两套彼此独立的系统，但也不建议把所有东西揉成一层。

我更推荐的答案是：

> **对外是一套统一框架，对内分成“编排框架 + 实现框架”，必要时再加一层场景实现层。**

### 1. 为什么不建议做成完全独立的两套

如果彻底拆成两套独立框架：

- 编排层不知道实现层真实能力边界
- 实现层对流程对象没有一等支持
- 快照、工作记录、审批、checkpoint 很难统一
- 使用者要同时理解两套抽象，心智成本高
- 最后很容易出现“运行时能做，但流程层接不住”或者“流程定义了，但 runtime 不支持”的断层

也就是说：

- 你会失去统一产品心智
- 也会失去你这套体系最大的差异化：`流程 + Agent + 协作 + 正式对象` 的一体化

### 2. 为什么又不能做成完全不分层的一套

如果把所有能力都揉成一层：

- 阶段流转会绑死具体 runtime
- runtime 很难替换模型、工具、执行器
- Search / Extract / memory / snapshot / card / workflow 会互相污染
- 代码仓库边界会越来越混乱
- 后面想拆 Server Mode、Desktop Self-Hosted Mode 都会更痛苦

也就是说：

- 对外可以是一套
- 对内必须分层

## 二十二、我建议的三层拆法

我建议把整个体系统一成一套框架，但内部至少拆成三层。

### 1. Runtime / Implementation Layer

这层负责“系统到底怎么跑”。

核心内容应包括：

- model adapter
- tool adapter
- `agent_runtime_service`
- session state
- memory / snapshot
- sandbox / executor
- tracing / telemetry
- queue / persistence
- `integration_gateway`

它回答的是：

- 模型怎么接
- 工具怎么调
- Agent 怎么执行
- 状态怎么保存
- 失败后怎么恢复

### 2. Orchestration Layer

这层负责“系统应该怎么走”。

核心内容应包括：

- `workflow_orchestrator`
- stage machine
- handoff / entry / exit
- action card / approval card
- loop / return / rollback
- checkpoint / resume
- conversation-to-workflow binding
- artifact binding

它回答的是：

- 当前流程在哪个阶段
- 是否允许进入下一步
- 哪些动作需要审批
- 回退、hold、rollback 如何编排

### 3. Solution / App Layer

这层负责“面向开发团队场景怎么用起来”。

核心内容应包括：

- AI 开发团队工作台
- 外出远程开发模式
- 群聊 / 线程 / 卡片 / 状态面板
- 项目 / 需求 / 任务 / 测试 / 发布的领域视图
- 移动端、Mac、Windows、Web 终端

它回答的是：

- 用户实际在界面里看到什么
- 不同角色如何协作
- 聊天、审批、摘要、状态如何呈现

---

## 二十三、市面主流 LLM 框架通常怎么做

我建议把主流框架的共同模式理解成：

> **统一品牌/统一入口 + 内部分层模块化。**

它们很少是完全割裂的两套，也很少是一层到底。

### 1. LangChain / LangGraph

我对它们的理解是：

- `LangChain` 更像高层组件、模型/工具集成、常见 agent 抽象
- `LangGraph` 更像低层 orchestration/runtime，强调 stateful、durable execution、interrupts、memory

这说明：

- 主流已经把“组件能力”和“编排/runtime”分开
- 但它们对外仍然属于同一生态，而不是两套彼此无关的产品

### 2. AutoGen

AutoGen 的分层也很清楚：

- `Core`：事件驱动、多 Agent runtime
- `AgentChat`：对话式单/多 Agent 应用编程层
- `Extensions`：外部服务、执行器、MCP、Docker 等扩展
- `Studio`：面向原型验证的 UI 层

这说明：

- 底层 runtime 一层
- 高层协作一层
- 再加可视化与扩展层

### 3. Semantic Kernel

Semantic Kernel 更偏“统一编程模型”，但内部依然是分层抽象：

- plugins
- functions
- memory
- planner / process
- connectors

这说明：

- 也可以对外保持统一心智
- 但内部必须有能力层、连接层、流程层的区分

### 4. CrewAI

CrewAI 更偏：

- agents
- tasks
- crews
- flows

它给人的感觉是“一套框架”，但内部仍然区分：

- Agent 抽象
- 任务抽象
- 协作抽象
- 流程抽象

### 5. OpenAI Agents SDK

OpenAI Agents SDK 也不是单层：

- agents
- tools
- sessions
- handoffs
- human-in-the-loop
- tracing
- sandbox
- run state

这说明主流正在往：

- session
- handoff
- run state
- sandbox

这样的完整系统抽象走，而不是只停留在 prompt + tool call。

## 二十四、对我们当前体系的推荐结论

如果回到你现在这套体系，我建议这样收敛：

### 1. 对外定义

对外我建议仍然称它为：

- 一套统一的 AI 开发团队框架
- 或者一套 Agent Workflow & Collaboration Framework

这样对用户和团队的心智是统一的。

### 2. 对内结构

对内我建议至少拆成：

- `runtime`
- `orchestration`
- `solution` / `apps`

也就是：

- `runtime` 解决“能不能跑”
- `orchestration` 解决“该怎么走”
- `solution` 解决“用户怎么用”

### 3. 代码与仓库层面的启发

如果以后真的写代码，我建议：

- 可以是一个 monorepo
- 但要有明确 package / module 边界
- 不建议一上来拆成两个完全独立 repo
- 也不建议把所有逻辑都塞进一个大包

我会更偏向：

- `packages/runtime`
- `packages/orchestration`
- `packages/solution-workbench`
- `packages/connectors`
- `packages/ui-client`

这样既统一，又可演进。

## 二十五、最小结论

我建议把结论收敛成下面这版：

- 这套体系不适合做成两套彼此独立的框架，也不适合揉成一层
- 最合理的是：**对外一套统一框架，对内拆成 `实现框架(runtime) + 编排框架(orchestration)`，必要时再加 `场景实现层(solution)`**
- 市面主流 LLM 框架基本也都是“统一入口、内部分层”，而不是完全分裂或完全不分层
- 因此下一步最自然的是：**把当前体系的 runtime / orchestration / solution 三层边界正式写成对象、API、模块与仓库结构**

## 一、组织架构(Phase 1 遗留,已过时)

AI 公司与真实公司的根本区别：不存在"招聘"和"固定编制"。创建一个新 Agent 只需要一个角色模板（prompt + 工具 + 权限），可以瞬间实例化，也可以用完释放。因此架构不是"部门 → 固定员工"，而是"模板 → 按需实例化"。

```
公司 (Company)
  ├── 角色模板池（定义每种角色的能力，不是固定的人）
  │     ├── Tech Lead 模板
  │     ├── 前端开发 模板
  │     ├── 后端开发 模板
  │     ├── 移动端开发 模板
  │     ├── 测试工程师 模板
  │     ├── DevOps 模板
  │     ├── UI 设计师 模板
  │     └── ... 用户可自定义新模板
  │
  ├── 持久 Agent 池（核心骨干，跨项目积累经验和记忆）
  │
  └── 项目群组 (Project Group)
        └── 持久 Agent + 按需实例化的临时 Agent
```

### Agent 的两种生命周期

| 类型 | 特点 | 适用场景 |
|------|------|----------|
| **持久 Agent** | 长期存在，跨项目积累记忆和经验，参与越多越"老练" | 公司核心骨干（Tech Lead、资深开发） |
| **临时 Agent** | 为某个项目按需创建，项目结束后可释放 | 并行增援、特定项目的专业角色 |

### 动态扩展机制

当项目所需的能力或人数不足时，系统可自动扩展：

**缺少角色类型**（如需要移动端开发但模板池没有）：

```
Dispatcher/Tech Lead → 用户:
  "当前系统没有移动端开发的角色模板，
   是否允许我创建一个？或者您手动定义这个角色的能力？"
```

用户确认后，系统创建新的角色模板并实例化 Agent 加入项目。

**项目中途发现缺人**（如设计阶段发现需要支付接入专家）：

```
Tech Lead:
  ① 评估：现有角色加个工具能解决，还是需要新角色？
  ② 如果需要 → 从模板池实例化新角色 → 拉入群组
  ③ 向新成员同步当前项目上下文
```

**并行能力不足**（如需要 3 个开发并行但只有 1 个）：

```
Tech Lead: 任务A、B、C可以并行，需要增加开发人手
  → 系统从同一模板实例化 开发工程师-2、开发工程师-3
  → 拉入群组，每个实例有独立 ID 和上下文
  → Tech Lead 分别分配任务
```

## 二、角色系统

每个角色模板定义了一种 Agent 的能力：system prompt、工具集、权限范围。从模板实例化出来的就是具体的 AI 员工。

将产品经理与架构师合并为 **项目负责人 (Tech Lead)**，原因：
- AI 没有精力瓶颈，一个 Agent 可以同时理解需求和做技术设计
- 减少角色间的对话轮次，降低 token 成本和时间消耗
- 小型任务（修 Bug、加功能）不需要臃肿的多层审批流程

### 默认角色模板

| 角色模板 | 类型 | 职责 |
|----------|------|------|
| **Dispatcher（前台调度）** | 系统级常驻 | 接收用户需求、评估规模、自动组建团队 |
| **项目负责人 (Tech Lead)** | 核心 | 需求分析、任务拆解、技术方案设计、工作分配、代码审查 |
| 后端开发工程师 | 核心 | 后端编码实现、API 开发 |
| 前端开发工程师 | 核心 | 前端编码实现、页面开发 |
| 测试工程师 | 核心 | 编写测试用例、执行测试、报告 Bug |
| DevOps | 核心 | CI/CD、部署、环境管理 |
| UI 设计师 | 可选 | 界面布局、交互设计、设计规范 |
| 移动端开发工程师 | 可选 | iOS/Android 开发 |
| ... | 可扩展 | 用户可自定义新角色模板 |

### 角色模板的结构（三层分离，借鉴 OpenClaw）

角色模板不是单个配置文件，而是**分层结构**。daemon 在实例化 Agent 时按层组装 prompt：

```
company/
  ├── shared_rules/                    # 第一层：共享规则（所有角色加载）
  │     ├── communication.md           # 沟通规则（@提及、三种回复类型）
  │     ├── tdd.md                     # TDD 工作方式
  │     ├── debugging.md               # 四步调试规范
  │     ├── verification.md            # 完成前验证规则
  │     └── review.md                  # 代码审查规范
  │
  └── role_templates/
        └── backend-developer/         # 每个角色一个目录
              ├── identity.md           # 第二层：角色定义（身份+约束）
              └── permissions.yaml      # 第三层：角色权限（工具+路径）
```

**第一层：共享规则** `shared_rules/*.md`

所有角色通用的行为规范，改一处全员生效：

| 文件 | 内容 |
|------|------|
| communication.md | @提及触发、三种回复类型、参与度控制 |
| task-card.md | 讨论与执行边界、建卡规则、关闭必填交付物 |
| tdd.md | TDD 红-绿-重构循环 |
| debugging.md | 四步调试规范 |
| verification.md | 无新鲜证据不宣称成功 |
| review.md | 两维度审查、严重级别分类、审查响应规范 |

新增角色自动继承全部共享规则。项目级配置可排除不需要的规则（如某项目关闭 TDD）。

**第二层：角色定义** `identity.md`

身份和约束写在一起（同一个角色定义的两面）：

```markdown
# 后端开发工程师

## 身份
你是一名后端开发工程师，负责服务端编码实现和 API 开发。

## 职责
- 按工单实现后端功能
- 编写单元测试（遵循 TDD）
- 提交代码供 Tech Lead 审查

## 约束
- 不修改 tasks/ 下的任务卡（只能更新自己负责任务的状态字段）
- 不修改其他角色的代码文件
- 不跳过单元测试直接提交
- 不在代码审查未通过时自行合并
```

**第三层：角色权限** `permissions.yaml`

```yaml
tools:
  - code_editor
  - git
  - terminal
  - mcp_database

paths:
  read: ["src/", "docs/", "tasks/", "tests/"]
  write: ["src/backend/", "tests/backend/"]
  forbidden: ["tasks/", "src/frontend/", "deploy/"]

can_be_persistent: true
```

**daemon 组装 prompt 的顺序：**

```
最终 system_prompt =
    shared_rules/*（全部共享规则）
  + identity.md（角色定义）
  + 当前阶段规则（从阶段状态机注入）
  + 当前任务上下文（工单内容，如果在阶段 3）
```

permissions.yaml 不注入 prompt，而是由 daemon 在工具调用时做**运行时权限校验**。

**默认权限矩阵（借鉴 OpenClaw 细粒度权限）：**

| 角色 | 可写 | 禁止写 |
|------|------|--------|
| Tech Lead | tasks/、docs/ | src/（不直接写代码） |
| 后端开发工程师 | src/backend/、tests/backend/ | tasks/（仅可更新自己任务的状态字段）、src/frontend/ |
| 前端开发工程师 | src/frontend/、tests/frontend/ | tasks/（仅可更新自己任务的状态字段）、src/backend/ |
| 测试工程师 | tests/、bug-reports/ | src/、tasks/（仅可创建 BUG 卡） |
| DevOps | deploy/、ci/、.github/ | src/、tasks/ |
| UI 设计师 | design/、src/styles/ | src/logic/、tasks/ |

### 灵活性设计

- Dispatcher 根据需求类型自动决定实例化哪些角色（如有前端界面则实例化 UI 设计师）
- 如果模板池没有匹配的角色，提示用户创建新模板（只需写 identity.md + permissions.yaml）
- 新角色自动继承全部共享规则，无需重复编写 TDD、调试等规范
- 大型项目可手动将 Tech Lead 拆分为独立的 PM + 架构师
- 简单任务甚至只需要 Tech Lead + 开发，两个角色即可
- 同一模板可实例化多个 Agent（如 3 个后端开发并行工作）
- 每个实例有独立 ID，名称可重复但 ID 唯一
- 权限由 daemon 运行时校验，防止 AI 越界操作

## 三、任务管理系统

纯聊天无法追踪进度，需要独立于聊天的结构化任务管理。

### 任务卡即文件（借鉴 OpenClaw）

任务卡存为项目文件空间中的 **Markdown 文件**，不是数据库记录：

```
project_files/<project>/
  └── tasks/
       ├── TASK-001.md
       ├── TASK-002.md
       ├── TASK-003.md
       └── BUG-001.md
```

每个任务卡使用 YAML frontmatter 存储结构化字段，正文为详细描述：

```markdown
---
id: TASK-003
title: 实现文章标签系统
type: dev                    # 任务类型：design/dev/test/fix/doc/ops
status: in_development       # 状态由 daemon 根据任务级状态机更新
assignee: 开发工程师-1
priority: high
tdd: true
dependencies: [TASK-001, TASK-002]
created_by: tech-lead
source: "阶段2设计讨论-接口设计频道"   # 来源：哪个讨论/频道产生了这个任务
verification_command: "cargo test tests::tags"
blocked_reason: ""           # 阻塞时必填，否则留空
---

## 描述
用户可以给文章添加标签，支持多标签。

## 设计引用
- 接口文档 → POST /api/tags, GET /api/articles?tag=xxx
- 表结构 → tags 表、article_tags 关联表

## 涉及文件
- src/models/tag.rs — 新建 Tag 模型
- src/routes/tags.rs — 新建标签相关 API

## 验收标准
- [ ] POST /api/tags 可以创建标签
- [ ] GET /api/articles?tag=rust 返回所有带 rust 标签的文章
- [ ] 一篇文章可以有多个标签

## 交付物（关闭时必填）
- 交付摘要：
- 交付链接：
```

### 讨论与执行的边界（借鉴 OpenClaw）

不是所有事情都要建卡。判断标准：**一旦出现明确动作、负责人、交付物、验收目标中的任意一项 → 必须建卡**。

| 不建卡（讨论） | 必须建卡（执行） |
|---------------|-----------------|
| 需求澄清 | 方案设计 |
| 方案讨论 | 开发实现 |
| 头脑风暴 | 测试验证 |
| 评审意见本身 | Bug 修复 |
| 信息交换 | 部署发布 |

### 任务关闭规则

任务关闭时**必须**补充交付物字段，否则 daemon 拒绝将状态改为已关闭：
- 交付摘要：做了什么
- 交付链接：代码路径、PR 链接、测试报告等

### 好处

- **AI 天然可操作**：Agent 读写文件即可获取/更新任务，不需要额外 API
- **版本可控**：任务卡随项目一起 Git 版本管理
- **简化架构**：不需要独立的任务数据库服务
- **可追溯**：每张卡记录来源讨论，方便回溯决策过程
- 并发安全：每张卡有明确负责人，同一时刻只有一个 Agent 修改同一张卡；状态字段更新由 daemon 加锁

### 看板视图

前端从 `tasks/*.md` 文件的 frontmatter 中解析状态字段，生成看板视图：

```
需求 → 设计 → 开发 → 测试 → 交付
```

- 用户可在看板上查看所有项目的整体进度
- 任务状态变更自动同步到群聊（daemon 发送 `STATUS_UPDATE` 消息）

## 四、工作流/流程定义

### 4.0 项目启动与 Dispatcher（前台调度）

在进入开发流程之前，需要一个**启动机制**——用户如何发起项目、系统如何自动组建团队。

#### Dispatcher 角色定义

Dispatcher（前台调度）是一个**系统级常驻机器人**，不属于任何项目，是用户进入系统后的唯一入口。

| 职责 | 说明 |
|------|------|
| 接收需求 | 用户与 Dispatcher 始终是一对一私聊 |
| 评估规模 | 根据需求内容判断任务规模（Hotfix / 小 / 中 / 大） |
| 组建团队 | 根据规模自动决定拉哪些角色 |
| 创建群组 | 自动创建项目群组，将用户和 AI 成员拉入 |
| 转交需求 | 将用户原始需求转发到群组，交给 Tech Lead |

Dispatcher **不做**的事：不参与项目讨论、不做需求分析、不做技术决策。建完群后退出或保持静默。

#### 启动交互流程

```
用户                    Dispatcher（前台）               项目群组
 │                          │                              │
 │  "我想做一个博客系统"    │                              │
 │ ──────────────────────> │                              │
 │                          │ ① 快速评估需求规模/类型       │
 │                          │ ② 决定需要哪些角色            │
 │                          │ ③ 创建项目群组                │
 │                          │ ④ 拉入 Tech Lead + 团队成员   │
 │                          │ ⑤ 将用户拉入群组              │
 │                          │ ────────────────────────────> │
 │  "已为您创建项目群组，    │                              │
 │   Tech Lead 将为您服务"  │                              │
 │ <─────────────────────  │                              │
 │                                                         │
 │               Tech Lead 在群内接手                        │
 │  "您好，我是本项目负责人，                                │
 │   关于博客系统有几个问题…"                                │
 │ <────────────────────────────────────────────────────── │
```

#### Dispatcher 评估逻辑

```yaml
dispatcher_rules:
  - if: 需求包含"修复""bug""报错"等关键词
    scale: hotfix
    team: [开发工程师, 测试工程师]

  - if: 需求是单个明确功能
    scale: small
    team: [Tech Lead, 开发工程师, 测试工程师]

  - if: 需求涉及多个模块或完整系统
    scale: medium
    team: [Tech Lead, 开发工程师, 测试工程师, DevOps]

  - if: 需求是从零构建产品
    scale: large
    team: [Tech Lead, 开发工程师 x N, 测试工程师, DevOps]
```

#### 两种启动方式共存

- **默认方式（方案 B）**：新手用户直接跟 Dispatcher 说需求，系统自动组队
- **手动方式（方案 A）**：高级用户可自行建群、选角色、精细控制团队构成
- Dispatcher 建好群后，用户仍可手动调整群成员（加人、踢人）

### 4.1 优化后的开发流程（6 阶段）

> 相比初版 7 阶段，本版做了 5 项关键优化：
> 1. **合并设计与任务拆解**（原阶段 2+3 → 新阶段 2），减少一轮审批
> 2. **测试左移**：测试工程师从阶段 1 起就有并行工作，而非等到代码写完
> 3. **任务级流水线**：每个任务独立流转（开发→审查→测试），不等全部开发完再统一测试
> 4. **DevOps 提前介入**：阶段 2 就搭建 CI/CD，而非最后才出场
> 5. **增量验收**：每完成一个功能就让用户预览，而非全部做完再一次性验收

#### 阶段 1：需求理解

- **输入**：用户的原始需求（由 Dispatcher 转发到群组）
- **产出**：需求规格文档（PRD）、会议纪要、专项备忘
- **硬门禁**：用户确认需求文档后才能进入阶段 2（借鉴 superpowers HARD-GATE）

本阶段分四轮推进，核心思路：跟用户的沟通和团队内部的头脑风暴是两件事，分开进行。

Tech Lead 在第一轮结束后需要判断用户需求的清晰度，根据不同情况调整后续轮次的侧重点：

| 用户输入清晰度 | AI 的工作方式 |
|---------------|--------------|
| 清晰完整的需求 | Tech Lead 确认细节即可，团队评估可行性 |
| 有方向但缺细节 | Tech Lead 问几个关键问题，团队补全其余 |
| 只有一句模糊想法 | AI 主动生成完整方案，用户只需说"对/不对" |

**关键原则：用户不知道答案的问题，别问用户。AI 自己想，然后让用户确认。**

---

**第一轮：需求收集（Tech Lead ↔ 用户，superpowers 风格）**

- 参与回复：仅 Tech Lead
- 其他成员：旁听（已读但不回复，降低 token 消耗）
- 用户在此轮只与 Tech Lead 对话，体验清晰有结构

根据需求清晰度，Tech Lead 的提问策略不同：

- **需求清晰时**：逐步问具体细节，分块展示理解结果，每块征求确认
- **需求模糊时**：只问 2-3 个方向性问题（给谁用？参考哪个产品？核心想解决什么问题？），不追问用户答不上来的细节

示例（模糊需求）：
```
Tech Lead: "博客系统主要给谁用？是个人博客还是多人平台？"
用户:      "个人用的"
Tech Lead: "有没有特别想参考的产品？比如 WordPress、Medium 那种？"
用户:      "类似 Medium 吧，简洁一点"
Tech Lead: "明白了，我先让团队讨论一下方案，稍后给您看"
```

---

**第二轮：团队头脑风暴（群聊，全员参与，用户可旁观）**

Tech Lead 将收集到的需求信息抛到群聊，全员从各自角度集思广益：

- **需求清晰时**：团队讨论技术方案、评估可行性、发现风险
- **需求模糊时**：团队**主动补全产品定义**——替用户想功能、想场景、想边界

示例（模糊需求下的头脑风暴）：
```
Tech Lead → 群聊:
  "用户想做一个个人博客，风格参考 Medium，简洁为主。
   目前信息就这些，大家从各自角度补全一下这个产品应该长什么样"

开发工程师: "个人博客核心功能：文章CRUD、Markdown编辑器、
            标签分类、归档。可以考虑加RSS订阅..."
测试工程师: "需要考虑：SEO是否重要？是否需要评论功能？
            如果有评论需要防垃圾评论..."
DevOps:     "简洁的话建议静态生成+CDN部署，成本低速度快。
            如果要评论和后台管理就需要后端服务..."
开发 @DevOps: "可以主体静态生成，评论用独立微服务"
DevOps:     "同意，这样部署最简单"
```

- 所有成员自由发言，允许互相 @讨论和碰撞
- 用户可以旁观团队讨论过程（核心产品体验——"看到机器人的工作流"）
- 用户如果感兴趣，也可以直接在群聊插话参与
- 需要深入讨论某个专项细节时，可创建频道拉相关人单独讨论，结论反馈回群聊

---

**第三轮：方案整理与呈现（Tech Lead → 用户）**

Tech Lead 综合团队讨论结果，向用户呈现方案。呈现方式根据需求清晰度不同：

- **需求清晰时**：展示 2-3 个技术方案 + 权衡分析 + 推荐
- **需求模糊时**：展示"产品轮廓"，将功能分为三档，让用户做选择题

示例（模糊需求下的产品轮廓）：
```
Tech Lead → 用户:

  团队讨论后，建议的产品轮廓如下：

  【核心功能】
  ✅ 文章编写（Markdown 编辑器）
  ✅ 标签分类 + 归档
  ✅ 简洁阅读页面（参考 Medium 风格）
  ✅ RSS 订阅

  【可选功能】
  ❓ 评论系统（要不要？）
  ❓ 暗色模式
  ❓ 文章搜索

  【暂不包含】
  ❌ 多用户注册
  ❌ 付费订阅
  ❌ 社交分享统计

  您看这个方向对吗？可选功能要加哪些？有没有遗漏的？
```

- 用户不需要从零想出功能，AI 已经替用户想好了，用户**只做选择题**
- 如果用户反馈带来新问题，可触发新一轮团队讨论（第二轮 → 第三轮循环）

---

**第四轮：需求评审（群聊，全员参与）**

- Tech Lead 在群聊中发布完整需求文档（文件卡片形式）
- 所有成员从各自专业角度审查并回复：
  - 开发工程师：接口描述是否清晰、技术上有无遗漏
  - 测试工程师：验收标准是否可测试、是否缺少指标
  - DevOps：部署要求是否完整
- Tech Lead 综合反馈修订文档，发布最终版
- Tech Lead 向用户发送 [门禁卡片]，请求最终确认
- **用户确认通过 → 进入阶段 2**

**产出物：**

| 产出 | 生成方式 | 存储位置 |
|------|----------|----------|
| 会议纪要 | 系统从每轮讨论中自动提取关键结论和决策 | 项目文件空间 |
| 需求文档 (PRD) | Tech Lead 编写，写入文件（非仅聊天），经评审修订后定稿 | 项目文件空间，版本管理 |
| 专项备忘 | 从频道讨论中提取，附在需求文档后 | 关联到需求文档 |

**沟通原则：**

- **群聊**用于需要共享的讨论：技术决策、评审、进度同步、跨角色争议
- **频道**用于不需要其他人知道的细节讨论：群聊内对频道无感知，结论反馈到群聊
- 任何成员可以在群聊中 @任何人直接沟通，不必事事经过 Tech Lead
- **Tech Lead 是决策者，不是传话筒**——大家直接沟通，Tech Lead 在讨论僵持时做最终决策，并确保结论记录到文档
- 不是所有消息都触发所有 AI 回复——通过"参与度控制"机制区分：旁听 / 被 @时回复 / 主动发言
- 产出物写入文件空间——不只是在聊天里发文字，而是有结构、有版本、可追溯
- 会议纪要自动化——系统解析结构化消息自动生成，不需要额外角色编写

#### 阶段 2：设计与规划（原阶段 2+3 合并）

Tech Lead 在做架构设计时，自然就知道要拆哪些任务。合并后减少一个阶段，用户一次审批即可。

**主线工作（Tech Lead 主导）：**

| 子阶段 | 角色 | 产出 | 可否并行 |
|--------|------|------|----------|
| 2a: UI/交互设计 | UI 设计师（可选） | UI 设计稿、交互流程图、设计规范 | 可与 2b 并行 |
| 2b: 接口/协议设计 | Tech Lead + 开发工程师（频道） | 接口文档（API、请求/响应、错误码） | 可与 2a 并行 |
| 2c: 架构/数据结构设计 | Tech Lead | 技术方案（架构图、选型、目录、表结构） | 依赖 2b |
| 2d: 任务拆解 | Tech Lead | 任务列表（自包含工单） | 依赖 2c |

**工单模板（零上下文可执行，借鉴 superpowers writing-plans）：**

每个工单必须假设执行者零上下文，拿到工单就能开干：

```yaml
task:
  id: "TASK-003"
  title: "实现文章标签系统"
  description: |
    用户可以给文章添加标签，支持多标签。
    标签用于分类和筛选文章。

  design_refs:                          # 关联的设计文档
    - "接口文档 → POST /api/tags, GET /api/articles?tag=xxx"
    - "表结构 → tags 表、article_tags 关联表"

  files_to_create_or_modify:            # 具体要改哪些文件
    - "src/models/tag.rs — 新建 Tag 模型"
    - "src/routes/tags.rs — 新建标签相关 API"
    - "src/routes/articles.rs — 修改文章查询，支持按标签筛选"

  acceptance_criteria:                  # 怎么算做完了
    - "POST /api/tags 可以创建标签"
    - "GET /api/articles?tag=rust 返回所有带 rust 标签的文章"
    - "一篇文章可以有多个标签"

  verification_command: "cargo test tests::tags"
  tdd: true                             # 默认 true，简单任务可设为 false
  dependencies: ["TASK-001", "TASK-002"]
  assignee: "开发工程师-1"
```

**并行工作（其他角色同步推进，不空等）：**

| 角色 | 在阶段 2 同步做的事 | 产出 |
|------|---------------------|------|
| 测试工程师 | 根据 PRD 提取验收标准，编写测试用例框架 | 测试用例框架（待阶段 3 填充具体断言） |
| DevOps | 初始化 Git 仓库、搭建 CI/CD 流水线、准备开发环境、建立分支策略 | 可用的 CI/CD + 开发环境 + 分支结构 |

**分支策略（借鉴 superpowers using-git-worktrees，适配多 Agent 并行）：**

```
main（主分支，受保护，仅通过合并请求写入）
  └── dev（开发分支，集成用）
       ├── task/TASK-001（开发工程师-1 的工作分支）
       ├── task/TASK-002（开发工程师-2 的工作分支）
       └── task/TASK-003（开发工程师-1 的另一个任务）
```

- 每个任务创建独立的 `task/TASK-xxx` 分支，开发者在自己的分支上工作，互不干扰
- 代码审查通过后，该任务分支合并到 dev
- CI 在每次合并到 dev 时自动跑全量测试，发现冲突或回归立即通知
- 所有任务完成 + 集成测试通过后，dev 合并到 main

**汇总评审（群聊，全员参与）：**

- Tech Lead 发布完整方案：设计文档集 + 任务列表
- 全员从各自角度审查
- **软门禁**：用户审批方案（默认自动通过，用户可配置为需要审批）

#### 阶段 3：迭代开发与测试（任务级流水线）

本阶段是核心优化点——不再是"全部开发完 → 全部测试"，而是**每个任务独立流转**：

**单个任务的流转（含 TDD）：**

```
任务工单 → 写失败测试 → 编码实现 → 测试通过 → 代码审查 → 任务测试 → 完成
              │            │           │          │           │
           开发工程师    开发工程师   开发工程师   Tech Lead   测试工程师
```

**多任务并行流水线：**

```
时间 ──────────────────────────────────────────────────────>

任务A: ██ 开发 ██ → █ 审查 █ → ██ 测试 ██ → ✓
任务B:     ██ 开发 ██ → █ 审查 █ → ██ 测试 ██ → ✓
任务C:          ██ 开发 ██ → █ 审查 █ → ██ 测试 ██ → ✓
                                                      ↓
                                               集成测试 → ✓
                                                      ↓
                                              用户增量预览
```

**开发工程师行为规范 — TDD 工作方式（借鉴 superpowers test-driven-development）：**

默认强制 TDD（工单中 `tdd: false` 时可跳过）。每个任务按以下步骤执行：

```
① 读工单，理解要做什么
② 写一个失败的单元测试（定义"完成"长什么样）
③ 跑测试，确认失败（红色）— 如果没失败，说明测试写得有问题
④ 写最少的代码让测试通过
⑤ 跑测试，确认通过（绿色）
⑥ 重构代码（测试保护下放心改）
⑦ 跑工单中的 verification_command，确认全部通过
⑧ 提交代码 + 测试 → 进入代码审查
```

**各角色在本阶段的工作：**

| 角色 | 工作内容 |
|------|----------|
| 开发工程师 | 按优先级逐个实现任务，TDD 方式：先写测试 → 编码 → 重构 → 自测 |
| Tech Lead | 每个任务做两维度代码审查：① 规格合规（是否符合需求）② 代码质量（风格、可维护性、测试覆盖）。不通过则打回 |
| 测试工程师 | 任务通过审查后立即执行集成/验收测试（不等其他任务），发现 Bug 创建 BUG_REPORT |
| DevOps | CI 自动运行：每次代码提交触发构建和单元测试，失败自动通知开发 |

**Tech Lead 代码审查规范（借鉴 superpowers requesting-code-review）：**

审查输入：Git diff + 关联工单 + 设计文档引用（精简上下文，不塞整段聊天历史）

审查反馈按严重级别分类：

| 级别 | 含义 | 处理方式 |
|------|------|----------|
| `blocker` | 阻断性问题，必须修复 | 打回，开发必须修复后重新提交 |
| `major` | 重要问题，应该修复 | 打回，开发修复后重新提交 |
| `suggestion` | 改进建议，可选 | 通过，开发自行决定是否采纳 |

开发工程师收到审查意见后（借鉴 superpowers receiving-code-review）：
- 先用自己的话复述理解（确保没有误解）
- 对照代码验证意见是否正确（审查者也可能错）
- 逐条实现修改并跑测试
- 禁止空洞附和式回应（如"好的我改"却不验证）

**Bug 修复流程 — 系统化调试（借鉴 superpowers systematic-debugging）：**

测试工程师发 BUG_REPORT 时必须提供结构化信息：

```yaml
bug_report:
  id: "BUG-007"
  title: "登录接口在空密码时返回500"
  severity: blocker          # blocker / major / minor
  related_task: "TASK-003"
  steps_to_reproduce:
    - "调用 POST /api/login"
    - "body: { username: 'test', password: '' }"
  expected: "返回 400 Bad Request，提示密码不能为空"
  actual: "返回 500 Internal Server Error"
  evidence: "curl 命令输出 / 测试日志"
```

开发工程师收到 BUG_REPORT 后，必须按四步走，禁止凭症状盲目打补丁：

| 步骤 | 动作 | 禁止 |
|------|------|------|
| ① 复现 | 按 steps_to_reproduce 复现 Bug | 不复现就动手改 |
| ② 定位根因 | 读代码、加日志、缩小范围 | 凭报错信息猜测打补丁 |
| ③ 写复现测试 | 写一个能稳定触发此 Bug 的测试用例（与 TDD 衔接） | 不写测试就改代码 |
| ④ 修复并验证 | 修复代码 → 跑复现测试确认通过 → 跑全量单元测试确认无回归 | 只修不验 |

如果复现不了，开发工程师返回 `NEEDS_CONTEXT` 状态，请求测试工程师补充信息。反复无法复现则升级到 Tech Lead 介入。

**完成前验证规则（借鉴 superpowers verification-before-completion）：**

核心规则：**无新鲜证据不宣称成功。**"我跑过了"不算证据，必须贴出实际的命令输出。

| 谁声称完成 | 必须提供的证据 |
|-----------|---------------|
| 开发工程师提交代码 | verification_command 的完整运行输出（全部通过） |
| Tech Lead 审查通过 | 审查结论 + 按严重级别分类的问题列表（即使无问题也要声明） |
| 测试工程师测试通过 | 测试报告（通过项 / 失败项 / 覆盖率） |

系统在收到 `DELIVERABLE` 或 `REVIEW_RESULT` 消息时，校验是否附带了证据字段。缺少证据的完成声明不被接受，任务状态不流转。

**增量用户预览（可选）：**

每完成一个功能模块（一组关联任务全部通过测试），Tech Lead 可向用户展示阶段性成果：
- 不是硬门禁，不会阻塞流程
- 用户看到后如果发现方向偏了，可以及早纠正
- 减少最终验收时的返工风险

**集成测试（所有任务完成后）：**

- 测试工程师执行完整的集成测试，验证所有模块组合后的表现
- 出口条件：所有关键测试通过，无阻断性 Bug

#### 阶段 4：用户验收

- **角色**：Tech Lead（代表团队向用户汇报）
- **输入**：集成测试通过的完整产品 + 测试报告
- **动作**：向用户展示最终成果，说明已实现的功能，提供使用说明
- 由于开发过程中已有增量预览，用户对产品已有认知，最终验收更高效
- **门禁**：用户确认满意 / 提出修改意见
- **回退**：修改意见根据性质回退到阶段 3（代码调整）或阶段 1（需求变更）

#### 阶段 4.5：分支收尾（借鉴 superpowers finishing-a-development-branch）

用户验收通过后、部署前，需要完成 Git 分支的合并和清理：

- **角色**：Tech Lead + DevOps
- **流程**：

```
用户验收通过
  → Tech Lead 确认 dev 分支上所有测试通过（附带 CI 输出证据）
  → Tech Lead 发起合并请求（dev → main）
  → DevOps 审查合并请求（检查 CI 状态、无冲突、无遗留 TODO）
  → 合并到 main
  → 清理已完成的 task/* 分支
  → 进入阶段 5 部署
```

- 如果合并有冲突，DevOps 解决冲突后重新跑测试确认无回归
- 合并完成后，dev 分支和所有 task/* 分支应被清理

#### 阶段 5：部署交付

- **角色**：DevOps
- **输入**：main 分支上用户验收通过的代码
- **动作**：构建 → 部署到 staging 环境 → 验证 → 部署到生产环境
- **产出**：可运行的产品 + 部署说明 + 用户手册
- **完成前验证**：部署后必须提供 staging 环境的验证证据（健康检查通过、核心功能可用）
- 注意：由于 CI/CD 在阶段 2 就已搭建，此阶段主要是切换到生产环境

### 4.2 按任务规模裁剪流程

不是所有任务都需要跑完整 6 阶段。Tech Lead 收到任务后的第一个动作是**评估任务规模**，选择对应流程：

| 任务规模 | 示例 | 流程 | 参与角色 |
|----------|------|------|----------|
| **Hotfix** | 修一个已知 Bug | 定位 → 修复 → 测试 → 部署 | 开发 + 测试 |
| **小功能** | 加一个导出按钮 | 简要设计 → 开发测试 → 交付 | Tech Lead + 开发 + 测试 |
| **中型功能** | 用户权限系统 | 完整 6 阶段 | 全员 |
| **大型项目** | 从零做一个产品 | 完整 6 阶段，多轮迭代 | 全员，多个开发并行流水线 |

### 4.3 阶段状态机

**项目级状态机**（由系统控制流转，AI 不能自行跳阶段）：

```
CREATED → REQUIREMENT_ANALYSIS → DESIGN_AND_PLANNING → ITERATIVE_DEV
  → USER_REVIEW → DEPLOYING → DONE
```

其中 DESIGN_AND_PLANNING 内部含子状态（部分可并行）：
```
DESIGN_AND_PLANNING
  ├── UI_DESIGN（可选，可并行）
  ├── API_DESIGN（可并行）
  ├── ARCHITECTURE_DESIGN（依赖 API_DESIGN）
  ├── TASK_BREAKDOWN（依赖 ARCHITECTURE_DESIGN）
  ├── TEST_FRAMEWORK_PREP（测试工程师并行）
  └── CI_CD_SETUP（DevOps 并行）
  → DESIGN_REVIEW（汇总评审）
```

**任务级状态机**（项目进入 ITERATIVE_DEV 后，每个任务独立流转）：
```
TASK_CREATED → WRITE_TESTS → IN_DEVELOPMENT → CODE_REVIEW → TASK_TESTING → TASK_DONE
```
其中 WRITE_TESTS → IN_DEVELOPMENT 是 TDD 循环（红→绿→重构），当 tdd: false 时跳过 WRITE_TESTS。

辅助状态：
```
任何状态 → BLOCKED（必须填写 blocked_reason）→ 阻塞解除后回到原状态
TASK_DONE → CLOSED（必须填写交付物摘要和链接）
```

任务级回退路径：
```
CODE_REVIEW 不通过    → 回退到 IN_DEVELOPMENT（开发修改，测试保护下重构）
TASK_TESTING 发现 Bug → BUG_REPORT（结构化）→ 开发四步调试（复现→定位→写测试→修复）→ CODE_REVIEW → TASK_TESTING
开发无法复现 Bug     → NEEDS_CONTEXT → 测试补充信息 → 重试 / Tech Lead 介入
```

项目级回退路径：
```
USER_REVIEW 小改     → 创建修改任务 → ITERATIVE_DEV
USER_REVIEW 需求变更 → 回退到 REQUIREMENT_ANALYSIS
```

所有任务 TASK_DONE + 集成测试通过 → 项目进入 USER_REVIEW

门禁说明：
- **硬门禁**：REQUIREMENT_ANALYSIS 末尾（必须用户确认）
- **软门禁**：DESIGN_REVIEW（默认自动通过，可配置为需要审批）
- **硬门禁**：USER_REVIEW（必须用户确认）

### 4.5 阶段规则定义

每个阶段需要结构化定义以下内容，作为该阶段角色的 prompt 约束：

```yaml
# 项目级阶段示例
stage: REQUIREMENT_ANALYSIS
  role: tech_lead
  input: 用户原始需求文本
  required_output:
    - 功能列表（结构化格式）
    - 核心用例描述
    - 约束和排除项
  output_format: markdown document
  validation:
    - 功能列表不能为空
    - 每个功能必须有清晰的一句话描述
  next_stage: DESIGN_AND_PLANNING
  gate: user_approval_required

# 任务级阶段示例
stage: IN_DEVELOPMENT
  role: developer
  input: 任务工单 + 关联设计文档
  required_output:
    - 实现代码
    - 单元测试（覆盖核心逻辑）
  validation:
    - 单元测试全部通过
    - 代码符合项目规范
  next_stage: CODE_REVIEW
  gate: none
```

每个 AI 进入某阶段时，prompt 中自动注入：
- 你是谁（角色）
- 你在哪个阶段（项目级 or 任务级）
- 你的输入是什么
- 你必须产出什么格式的结果
- 什么条件下才算完成

### 4.6 沟通协议

#### 消息类型

AI 之间的对话需要结构化消息类型，让系统可解析并自动更新任务状态：

| 消息类型 | 方向 | 用途 |
|----------|------|------|
| `TASK_ASSIGN` | Tech Lead → 开发 | 分配任务，附带工单详情 |
| `QUESTION` | 任意 → 任意 | 请求澄清，需对方回复 |
| `DELIVERABLE` | 开发 → Tech Lead | 提交代码/产出物，请求审查（必须附带验证证据） |
| `REVIEW_RESULT` | Tech Lead → 开发 | 审查反馈，通过或打回（必须附带问题列表） |
| `BUG_REPORT` | 测试 → 开发 | 报告问题，附带结构化复现步骤 |
| `STATUS_UPDATE` | 任意 → 群聊 | 进度同步，系统自动更新看板 |
| `GATE_REQUEST` | Tech Lead → 用户 | 请求用户审批，阻塞直到用户响应 |
| `NEEDS_CONTEXT` | 任意 → 任意 | 缺少信息无法继续，请求对方补充 |

#### 回复类型约束（借鉴 OpenClaw）

所有 AI 的回复**只允许三种类型**，禁止空话：

| 类型 | 含义 | 示例 | 禁止 |
|------|------|------|------|
| **结果** | 我完成了，这是产出 | "代码已提交，测试全部通过，输出如下…" | ~~"收到，我来处理"~~ |
| **阻塞** | 我被卡住了，需要帮助 | "数据库连接配置缺失，无法继续" | ~~"正在进行中"~~ |
| **澄清** | 我需要更多信息 | "接口返回格式是 JSON 还是 XML？" | ~~"好的，我了解了"~~ |

**例外**：阶段 1 第二轮（团队头脑风暴）放宽为自由发言，因为讨论本身就是价值。

此规则写入 `shared_rules/communication.md`，所有角色加载。

#### 门禁规则

- 哪些节点需要用户审批（可配置）
- 审批通过后自动流转到下一阶段
- 审批拒绝后回退到指定阶段，附带拒绝原因
- 超时未审批的处理策略（提醒 / 自动通过 / 持续等待）

## 五、通信模型

系统中有三种沟通空间，层级清晰：

```
私聊（一对一）
 └── 用户 ↔ Dispatcher
 └── 用户 ↔ 任意 AI
 └── AI ↔ AI

群聊（项目级主聊天）
 └── 所有项目成员可见
 └── 需要共享的讨论、评审、进度同步、跨角色争议

频道（群组下的子空间）
 └── 部分成员参与，讨论某个子任务/子话题
 └── 群聊内对频道无感知
 └── 频道结论需反馈到群聊
```

### 沟通规则

| 场景 | 使用方式 |
|------|----------|
| 两人讨论某个具体的实现细节 | 创建频道，不打扰其他人 |
| 讨论结果影响其他人或涉及多人 | 在群聊中 @相关人直接讨论 |
| 评审、进度汇报、门禁审批 | 群聊 |
| 用户发起新项目 | 私聊 Dispatcher |
| 用户想了解某个 AI 的工作状态 | 私聊该 AI 或"登录"查看 |

### @提及触发机制（借鉴 OpenClaw）

@提及是参与度控制的**底层实现**，规则简单明确：

| 条件 | AI 行为 |
|------|---------|
| 未被 @ | **静默**，不回复（旁听，消息进入上下文但不触发回复） |
| 被 @ | **必须回复**，且回复必须是结果/阻塞/澄清之一 |
| 系统自动 @所有人 | 全员回复（评审轮、头脑风暴轮） |
| AI 遇到问题 | 可**主动 @**其他角色求助（如开发 @Tech Lead 求助） |

此规则写入 `shared_rules/communication.md`，所有角色加载。

### 消息格式

| 机制 | 说明 |
|------|------|
| 消息类型 | 文本、代码块、文件、任务卡片、审批卡片 |
| 指令 | 类似 Slack `/command`，快捷触发操作 |

## 六、文件/产物管理

软件开发过程产出的文件需要统一管理：

- 每个项目群组关联一个**文件空间**
- 支持的产物类型：PRD、设计文档、代码仓库、测试报告、部署日志
- 与 Git 仓库集成，代码变更可在聊天中引用和查看
- 产物有版本记录，可追溯历史

---

## 七、Agent 记忆与上下文管理

AI 系统的核心问题，必须解决：

- **持久化记忆**：每个 AI 员工记住自己参与的项目、讨论内容、代码进度
- **摘要与检索**：聊天上下文窗口有限，需要自动摘要 + 语义检索机制
- **上下文隔离**：同一个 AI 在不同项目中的记忆互不干扰
- **共享知识库**：公司级别的知识（技术栈、编码规范等）对所有 AI 可用

---

## 八、用户角色与视角

用户在系统中有三种视角，UI 和权限各不相同：

| 视角 | 能力 |
|------|------|
| 管理者 | 发布需求、审批关键节点、查看整体进度看板 |
| 观察者 | 查看任意 AI 的聊天记录、工作状态（"登录"机器人） |
| 参与者 | 直接在群聊中与 AI 对话、干预讨论方向 |

## 优先级规划

| 优先级 | 模块 | 原因 |
|--------|------|------|
| P0 | 角色系统 + 工作流定义 | AI 需要知道自己是谁、该干什么 |
| P0 | 任务管理系统 | 纯聊天无法追踪项目进度 |
| P1 | 组织架构 | "拉群"需要有逻辑依据 |
| P1 | Agent 记忆管理 | AI 没有记忆就无法持续工作 |
| P2 | 文件/产物管理 | 开发产出需要存储和版本管理 |
| P2 | 通信模型丰富化 | 提升协作效率和体验 |
| P3 | 用户角色明确化 | 影响前端 UI 设计 |

## 一、方案由来(Phase 1 遗留,已过时)

### 1.1 遇到的问题

在讨论"项目级角色团队"设计时，我们发现角色定义的存储位置存在多个选项：

**选项 A：角色定义在 Git 仓库**
- ❌ 角色配置散落在多个仓库，难以统一管理
- ❌ 跨项目复用困难
- ❌ 不符合"配置与代码分离"原则

**选项 B：角色定义在云端配置库**
- ✅ 集中管理，便于维护
- ❌ 但实际运行时，Agent 需要直接加载配置文件

**选项 C：角色定义在 agent-runtime 内部**
- ✅ 随系统发布
- ❌ 无法项目级定制

### 1.2 核心矛盾

根据已有架构设计：

```
数据库（前端展示、查询）
  └── 项目列表、项目状态、任务卡元数据...

文件系统（Agent 工作区）
  ├── 源代码
  ├── 设计文档、PRD
  ├── 测试报告
  ├── Agent 的 project_notes
  └── 共享规则、角色模板 ← Agent 需要直接加载
```

**关键矛盾：**
- Agent 需要从文件系统加载配置
- 但配置不应该在 Git 仓库中
- 需要支持跨机器恢复

### 1.3 解决思路

借鉴现有的"Git 仓库 + 云端服务"混合架构：

- Git 仓库：仅存储代码
- 云端服务：存储配置、快照、文档等
- 本地目录：运行时按需组装

## 二、核心架构

### 2.1 设计原则

```
关键原则：
1. Git 仓库仅存储代码
2. Agent 配置、快照、文档等存储在云端服务
3. 本地项目目录通过工具按需拉取组装
4. 项目配置文件（manifest）驱动整个恢复流程
5. 支持跨机器恢复和同步
```

### 2.2 本地项目目录结构

```
project_files/{project}/
├── agent/        # Agent 配置（从云端配置库拉取）
│   ├── team.yaml
│   ├── roles/
│   │   ├── tech_lead.yaml
│   │   └── seo_specialist.yaml
│   └── permissions.yaml
│
├── snapshot/     # 项目快照（从云端快照库拉取）
│   ├── team.yaml
│   ├── agents/
│   │   ├── tech_lead_notes.yaml
│   │   └── backend_dev_notes.yaml
│   └── project-state.yaml
│
├── docs/         # 文档（从云端文档库拉取）
│   ├── prd/
│   └── design/
│
├── tasks/        # 任务卡（从云端任务库拉取）
│   └── TASK-001.yaml
│
└── git/          # 代码仓库（从 Git 拉取）
    ├── src/
    ├── tests/
    └── README.md
```

**关键点：**
- ✅ 所有内容通过工具按需拉取
- ✅ 不在 Git 仓库中（Git 仅存储代码）
- ✅ 支持跨机器恢复和同步

## 三、项目配置文件（Manifest）

每个项目有一个轻量级配置文件，定义所有数据源：

```yaml
# ~/.projects/blog-project.yaml

project_id: blog-project
project_name: "博客系统"

# 数据源配置
sources:
  # Git 仓库（代码）
  git:
    type: git
    repo: "git@github.com:company/blog-backend.git"
    branch: "develop"
    target_dir: "git/"
    
  # 云端配置库（Agent 配置）
  agent_config:
    type: cloud_config
    service: "config-service"
    namespace: "projects/blog-project/agent"
    target_dir: "agent/"
    
  # 云端快照库（项目快照）
  snapshot:
    type: cloud_snapshot
    service: "snapshot-service"
    namespace: "projects/blog-project/snapshot"
    target_dir: "snapshot/"
    
  # 云端文档库（可选）
  docs:
    type: cloud_doc
    service: "doc-service"
    namespace: "projects/blog-project/docs"
    target_dir: "docs/"
    
  # 任务卡片库
  tasks:
    type: cloud_task
    service: "task-service"
    namespace: "projects/blog-project/tasks"
    target_dir: "tasks/"

# 项目状态
status: active
last_sync: 2026-04-10T10:30:00Z
```

**配置文件作用：**
- 定义项目的所有数据源
- 驱动项目恢复工具的同步行为
- 支持跨机器快速恢复

## 四、项目同步工具

### 4.1 工具定位

**工具名称：** `project-sync`

**技术栈：** Rust（高性能、跨平台）

**核心功能：**
- ✅ 一键恢复整个项目（从各个数据源拉取）
- ✅ 支持部分恢复（指定数据源）
- ✅ 支持推送到云端（同步本地更改）
- ✅ 跨平台支持（Linux、macOS、Windows）

### 4.2 命令行接口

```bash
# 安装工具
cargo install project-sync

# 恢复项目
project-sync restore blog-project

# 恢复到指定目录
project-sync restore blog-project --target /path/to/project

# 仅恢复特定部分
project-sync restore blog-project --only git,agent

# 推送本地更改到云端
project-sync push blog-project --only agent,snapshot

# 查看项目状态
project-sync status blog-project
```

### 4.3 工具架构

```
project-sync/
├── Cargo.toml
├── src/
│   ├── main.rs              # CLI 入口
│   ├── lib.rs               # 库入口
│   ├── manifest.rs          # 配置文件解析
│   ├── sync/
│   │   ├── mod.rs
│   │   ├── git.rs           # Git 同步逻辑
│   │   ├── cloud.rs         # 云端服务同步
│   │   └── snapshot.rs      # 快照同步
│   ├── client/
│   │   ├── mod.rs
│   │   ├── config_client.rs  # 配置服务客户端
│   │   ├── snapshot_client.rs # 快照服务客户端
│   │   └── task_client.rs    # 任务服务客户端
│   └── utils/
│       ├── mod.rs
│       └── fs.rs            # 文件系统工具
└── tests/
    └── integration_tests.rs
```

## 六、完整工作流程

### 6.1 项目启动流程

```
1. 用户向 Assistant 提出需求
   ↓
2. Assistant 协助确认项目申请表
   ↓
3. 创建项目配置文件（manifest）
   ↓
4. 保存到云端配置库
   ↓
5. 保存到用户本地配置目录（~/.projects/）
   ↓
6. 调用 project-sync 工具一键拉取所有内容
   ↓
7. 创建项目群聊，实例化 Agent
   ↓
8. Tech Lead 接手项目
```

### 6.2 项目恢复流程

```
1. 用户选择恢复某个项目
   ↓
2. 从云端拉取项目配置文件（manifest）
   ↓
3. 调用 project-sync 工具一键恢复
   ↓
4. 从各个数据源拉取：
   - Git 仓库 → git/
   - 云端配置 → agent/
   - 云端快照 → snapshot/
   - 云端文档 → docs/
   - 云端任务 → tasks/
   ↓
5. 恢复 Agent 状态
   ↓
6. 重建项目群聊
```

### 6.3 项目同步流程

```
Agent 修改配置 → 自动推送到云端 → 其他机器可拉取

具体：
1. Agent 修改了 agent/roles/ 下的配置
2. daemon 检测到变更
3. 调用 project-sync push 推送到云端
4. 用户在其他机器上执行 project-sync restore 即可同步
```

## 七、关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| Git 仓库内容 | **仅代码** | 符合 Git 最佳实践，避免配置污染代码库 |
| Agent 配置存储 | **云端配置库** | 集中管理，跨机器同步 |
| 项目快照存储 | **云端快照库** | 跨机器恢复，版本管理 |
| 任务卡存储 | **云端任务库** | 实时查询，前端展示 |
| 本地项目目录 | **按需组装** | 不占用本地空间，支持跨机器恢复 |
| 同步工具技术栈 | **Rust** | 高性能、跨平台、可靠性 |

---

## 八、优势总结

✅ **清晰分层**：云端持久化 + 本地运行时  
✅ **按需拉取**：不占用本地空间  
✅ **跨机器同步**：配置文件驱动  
✅ **Git 独立**：代码仓库独立管理  
✅ **版本可控**：云端配置有版本历史  
✅ **高性能**：Rust 实现同步工具

## 九、与现有架构的集成

### 9.1 与 daemon 的集成

```
daemon 职责：
1. 项目启动时调用 project-sync restore
2. 检测本地变更，调用 project-sync push
3. 管理项目配置文件缓存
```

### 9.2 与数据库的集成

```
数据库存储：
- 项目元数据（project_id、name、status）
- 项目配置文件引用（manifest_url）
- 同步状态（last_sync）

文件系统存储：
- 通过 project-sync 按需拉取的完整内容
```

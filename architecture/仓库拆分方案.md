## 一、拆分哲学

### 1.1 三条分仓原则(对照 `架构设计.md` §6)

1. **按稳定依赖方向分仓** — L0 最稳定,被所有层依赖;L5/L6 最不稳定,不被依赖
2. **按聚合一致性边界分仓** — 每个聚合根独占一仓,跨仓只发事件不直接调用
3. **按变化速率分仓** — 变化快的(UI/生态)与变化慢的(协议/契约)分开,避免快速变化拉动稳定层

### 1.2 不分仓的反例

有意识避免的分仓反模式:
- ❌ **按技术层分仓**(前端仓 / 后端仓 / 数据库仓)— 违反聚合一致性
- ❌ **按部署单元分仓**(service-a / service-b)— 违反 DDD 边界
- ❌ **按代码行数分仓**(太大就拆)— 缺乏语义依据
- ❌ **按组织架构分仓**(团队 A 的仓 / 团队 B 的仓)— Conway Law 反向应用

### 1.3 本方案的最小单位

**一个仓 = 一个聚合根 OR 一个可组合能力 OR 一个独立产品**

不按"一个 service"分 —— 部署单元和仓库是正交的,一个仓可能部署成多个 service,多个仓也可能组合成一个部署单元。

## 三、L0 · 共享契约层(3 仓)

### 3.1 `quantalithos-core`

**作用**:所有仓编译期依赖的共享契约。
**语言**:Rust(主) + 通过 buf 生成 Python / TypeScript 代码
**核心内容**:
- `.proto` 文件 — gRPC 接口契约
- CloudEvents schema — 六域事件定义(identity.member.hired / conversation.turn.posted / ...)
- 共享数据模型 — IDs / Timestamps / enums
- 错误码枚举 — 全平台通用 error.proto

**发版节奏**:月度稳定版 + 紧急修订;版本号严格 semver;breaking change 必须走 ADR

### 3.2 `quantalithos-bus`

**作用**:事件总线的抽象接口 + 多后端适配
**语言**:Rust + Python + TypeScript 三语言 client
**核心内容**:
- `EventBus` trait(publish / subscribe / ack / dead-letter)
- NATS JetStream 适配(默认后端,开发/生产)
- Redis Streams 适配(轻量部署)
- Kafka 适配(企业部署)
- In-memory 适配(单元测试)

**依赖**:`core`(消费 event schema)

### 3.3 `quantalithos-sdk`

**作用**:对外的多语言 client,内外都用
**语言**:Python + Rust + TypeScript,独立发布
**核心内容**:
- 六域 API 的高层封装(不是裸 gRPC)
- 认证 / trace 传播 / 重试 / 指数退避
- 配置加载(env + file + remote)
- 类型生成脚本(从 `core` proto 生成 bindings)

**依赖**:`core`(type) + `bus`(订阅事件时)
**发版**:三语言独立发版,但类型从 `core` 同版本派生

## 四、L1 · 领域服务层(7 仓)

**每个域 / 跨域视图一个仓,严格聚合根或视图局部状态边界,跨域以事件和只读查询为主**

### 4.1 `quantalithos-identity`

**聚合根**:GlobalMember / Role / Capability
**语言**:Rust(ADR-0003 锁定)
**职责**:
- 员工档案的 CRUD + 生命周期状态机
- Role 注册(作为 SPEM RoleDefinition 的服务端载体)
- Capability 能力清单管理
- 员工招聘 / 退休事件发布
- semantic_memory_ref 句柄管理(不存向量,存引用)

**不做**:ProjectMember(归 work)、容器编排(归 member-service)、对话(归 conversation)

**发布事件**:MemberHired / MemberActivated / MemberPaused / MemberRetired / MemberCapabilityUpdated / RoleCreated / RoleRetired

### 4.2 `quantalithos-conversation`

**聚合根**:Conversation / Turn
**语言**:Rust(高并发 + 强一致)
**职责**:
- Conversation 的四种形态(group / channel / dm / thread)
- Turn 的消息 / mention / decision / artifact 指针 / gate 指针
- 实时推送(AG-UI 协议 17 种事件对齐)
- 对话历史检索

**发布事件**:TurnPosted / ConversationCreated / MentionTriggered / DecisionMade

### 4.3 `quantalithos-work`

**聚合根**:Project(含 ProjectMember 作为内部实体)/ WorkItem / Iteration
**语言**:Rust
**职责**:
- Project 立项 / 归档 / 复活
- **ProjectMember 管理**(引用 GlobalMember,扩展 tool_scope / policy_overrides / memory_slot)
- Backlog 管理
- WorkItem 状态机(story / task / bug / prototype / spike / review / NFR)
- Iteration / Stage 时段管理
- 依赖图 + 看板视图 API

**发布事件**:ProjectCreated / ProjectMemberAssigned / WorkItemCreated / WorkItemStateChanged / IterationStarted / IterationClosed

### 4.4 `quantalithos-process`

**聚合根**:ProcessTemplate / ProcessProfile / ProcessInstance / Activity
**语言**:Python(BPMN 引擎生态丰富 + Activity 内含轻量 DSL 解析)
**职责**:
- BPMN 2.0 引擎(基于现有开源 + 定制)
- Template → Profile(裁剪)→ Instance 三段式
- 每个 Activity 的**持久化执行**(不只是 checkpoint,对齐 Temporal 模式)
- Gate 触发点的外抛

**发布事件**:ProcessInstantiated / ActivityStarted / ActivityCompleted / GateTriggered / ProcessCompleted

### 4.5 `quantalithos-governance`

**聚合根**:Gate / Policy / Control / Approval / ImpactAssessment / SoADocument
**语言**:Rust
**职责**:
- Gate 一等对象(六段式:trigger / decision_request / candidate_options / evidence_requirement / resolution / audit_trail)
- Policy 下发 + 版本管理
- Control(ISO 42001 Annex A 的 38 个控制项)
- 42001 AIIA / SoA / Conformance Declaration
- Approval 投票 + 超时策略

**发布事件**:GateRaised / GateDecided / PolicyUpdated / ControlViolated / AIIACompleted / NonconformityRaised

### 4.6 `quantalithos-artifact`

**聚合根**:Artifact / ArtifactRelation / Baseline / DatasetArtifact
**语言**:Rust
**职责**:
- Artifact 状态机(initiated → reviewed → approved → baselined → published → archived)
- Artifact kind 枚举:Requirement / Design / Prototype / Code / TestPlan / TestReport / UserDoc / Release / LessonLearned / Dataset
- ArtifactRelation 血缘(derives-from / implements / verifies / validates / replaces)
- Baseline 冻结 + 变更控制
- Quality 标签(对齐 ISO 25010 九特性)

**发布事件**:ArtifactCreated / ArtifactReviewed / ArtifactApproved / ArtifactBaselined / ArtifactPublished / ArtifactArchived

### 4.7 `quantalithos-workspace`

**聚合 / 视图根**:PersonalWorkspace / ProjectWorkspace / InboxItem / ReadCursor / WorkspacePreference

**语言**:Rust

**职责**:
- PersonalWorkspace:GlobalMember 视角的个人首页 / inbox / 项目列表 / 私聊 / 跨项目待办视图
- ProjectWorkspace:ProjectMember / Project 视角的项目首页 / 项目目标 / 项目成员 / 项目群聊 / 任务板 / 当前流程 / 相关产物 / gate 视图
- 统一 read cursor / unread count projection / pinned projects / muted conversations / notification preferences / last opened project / inbox visibility
- 为 Chat / Console / Assistant / AI Member Runtime 提供一致的成员上下文视图
- 订阅 identity / work / conversation / process / artifact / governance 事件,维护可重建的聚合投影

**不做**:GlobalMember 真相(归 identity)、Project / ProjectMember / WorkItem 真相(归 work)、Conversation / Turn 真相(归 conversation)、Process / Activity 真相(归 process)、Artifact 正文(归 artifact)、Gate decision 真相(归 governance)

**发布事件**:WorkspaceProjectionUpdated / InboxItemUpdated / ReadCursorUpdated / WorkspacePreferenceUpdated

## 五、L2 · Member 运行层(5 仓)

**AI 员工的容器内运行形态;详细设计见 `architecture/ai-member设计.md`(待写)**

### 5.1 `quantalithos-member`

**作用**:Member 进程 —— 容器内的社交门面(嘴耳)
**语言**:Rust(ADR-0003 同栈)
**六子模块**(详见 ai-member设计文档):
1. Identity — 持有 member_id / role / profile / launch_token
2. Event Subscriber — 订阅 bus 主题,按 member_id / role / 项目上下文过滤
3. Event Publisher — 把 Runtime 产出的业务事实写成 CloudEvents
4. External RPC Server — :50143,处理 Register / Heartbeat / Shutdown
5. Attention — 入站事件/消息的优先级判定 + Prompt Injection 预过滤
6. IPC Bridge — 容器内 UDS gRPC,面向 Runtime

**不做**:决策、LLM 调用、工具调用、记忆写入

### 5.2 `quantalithos-runtime`

**作用**:Runtime 进程 —— 容器内的大脑
**语言**:Python 3.12+(LLM 生态 + pydantic + async)
**九子模块**:
1. LLM Loop — ReAct 主循环
2. Prompt Composer — Identity / Policy / Goal / Memory / Context 组装
3. Memory Store — working / episodic / semantic 三层
4. Goal / Plan — 当前 Activity 的目标栈
5. Context Manager — 聚合 + 截断
6. Policy Cache — 治理域下发的共享规则缓存
7. Checkpoint Store — 每轮 think-act-observe 后持久化
8. Sub-Agent Spawner — 独立上下文的子 agent
9. Tool Invoker + ToolCallSite — 前置 policy check + schema 校验 + AuditEvent 发布

**不做**:对外网络、容器编排

### 5.3 `quantalithos-tools`

**作用**:Tools monorepo,按 Role 装载的工具集
**语言**:Python(主)+ 少量 Rust 加速模块
**结构**:
```
quantalithos-tools/
├── code/         file_read / file_write / code_search / code_edit
├── git/          git_* 工具族
├── sandbox/      container exec / file system isolation
├── lsp/          lsp-python / lsp-typescript / lsp-rust / lsp-go
├── test/         pytest / vitest / playwright
├── mcp-client/   MCP Client 实现(对接 capability-hub)
├── browse/       web browsing
└── ask-teammate/ 跨 Member 沟通工具
```

**不做**:LLM 调用(那是 Runtime 的职责)

### 5.4 `quantalithos-member-images`

**作用**:Dockerfile + CI 构建脚本仓,按 Role 预构建镜像(ADR-0005)
**内容**:
- `base/Dockerfile` — 底层镜像(ai-member-base)
- `roles/tech-lead/` / `backend-dev/` / `frontend-dev/` / `qa/` / `devops/` / `ux/` / `auditor/` / `assistant/` 各自 Dockerfile
- `ci/` — GitHub Actions / GitLab CI 脚本
- `registry-config/` — 镜像 registry 配置

**不做**:运行时代码(纯构建资产)

### 5.5 `quantalithos-member-service`

**作用**:L2 编排层 —— 管理所有 Member 容器的生命周期
**语言**:Rust
**职责**:
- Identity Store 本地副本(从身份域订阅事件同步)
- Container Orchestrator 抽象(Docker / k8s 两后端)
- Endpoint Registry — member_id → container_endpoint
- Heartbeat Monitor — 心跳 + 重启策略
- Event Subscription Broker — 按 Role/Capability 订阅主题路由给具体 Member

**订阅事件**:ProjectMember 变化(扩容/收缩容器)、GlobalMember 退休(下线容器)、PolicyUpdated(下发到容器)

## 十二、仓级元数据约定

每个仓的 `README.md` 必须包含:

```yaml
repo_id:         quantalithos-<name>
layer:           L0 / L1 / L2 / L3 / L4 / L5 / L6
aggregates:      [...]           # 承载的聚合根(仅 L1)
```

## 十四、设计原则审视(对照 `架构设计.md`)

| 原则 | 本方案体现 |
|---|---|
| 稳定依赖 | L0→L1→L2→L3→L4→L5→L6 严格单向依赖 |
| 按聚合 / 视图状态分仓 | L1 各业务域拥有聚合根,workspace 独立拥有跨域视图局部状态 |
| 推迟不可逆决策 | 分层足够细,任一层内部选型都可独立调整(ADR-0003 只约束 identity) |
| 可演进 | 新增仓、合并仓都有明确判据;L2 五仓可视情况合并(ADR 路径) |
| 可组合 | 10 产品由 27 仓自由组合,不绑死 |
| 最小知识 | 跨仓只通过事件或 SDK,不共享内部 struct |
| 关注点分离 | 6 域分离 + L 层分离 + 横切(观测 / 方法)单独成仓 |

## 十五、标准对齐

- **BPMN 2.0 / SPEM 2.0**:process 仓 + method-library 仓各自承载引擎与内容
- **ISO 29110 Profile**:ProcessProfile 机制在 process + method-library 协作实现
- **ISO 42001 AIMS**:governance 仓承载 38 控制项,observability 承载审计证据,archive 承载 ComplianceDeclaration
- **ISO 24748-2**:method-library 的 ProcessTemplate 家族覆盖 24748-2 的 8 种参考模型
- **ISO 25010**:artifact 仓的 quality_tags 字段对齐 9 特性;L5 NFR 作为 WorkItem
- **三条横切红线**:可审计性(observability)/ 可追溯性(observability + artifact 血缘)/ 可裁剪性(method-library + governance)

## 一、路线图哲学

### 1.1 不采用"Phase 1/2/3"分期

A 方案废弃了 Phase 1/2/3 的分期方式。理由:
- Phase 分期暗示"前一期完成才能后一期",与多仓并行不符
- Phase 语义模糊(什么叫"完成 Phase 1"?),缺乏硬边界
- 六域事件编织的架构允许多仓独立演进,不需要全局同步点

### 1.2 改用"L 层识别路径 + 产品 MVP"双轴

```
纵轴:L0 → L1 → L2 → L3 → L4 → L5 → L6 的自底向上交付
横轴:三个产品 MVP(Minimal / Core / Enterprise)的端到端闭环
```

交付顺序同时看两条轴:底层先就位,上层才能跑;同时任何节点都必须支撑某个产品 MVP 的闭环,不做"底层完美但上不了线"的地基工程。

### 1.3 交付单位

**"可运行的端到端切片"** — 每次节点交付都产出可被 **MVP-M** 使用的能力,而不是"某个仓完成到某个百分比"。

## 二、三个产品 MVP

从小到大三个 MVP,每个对应一个路线图节点:

### MVP-M · Minimal(最小可用)

- 单用户 + 单项目 + 一个 Member(Assistant)+ 一个 Backend Dev
- 完整走通"立项 → 需求对话 → 简单代码产出 → 验收"一个小迭代
- 仅 Chat 前端,无 Console,无 Bridges,无 Marketplace
- 本地部署(单机 Docker Compose)

### MVP-C · Core(核心闭环)

- 单用户 + 3 项目并发 + 4-6 个 Member 的完整团队
- 覆盖六阶段完整流程(含 Gate 审批)
- Chat + Console + Runner + Sync
- 审计事件完备,支持项目归档与恢复
- 可 SaaS 部署

### MVP-E · Enterprise(企业就绪)

- 多用户 + 多组织 + 方法库治理 + 42001 合规证据
- Bridges(Mattermost / Slack)+ Marketplace 基础版
- SDK 三语言发布
- 完整 ISO 42001 Tailored Conformance 能够举证

## 三、节点式路线图

节点按**前置依赖**排序,**不按时间**排序。每个节点可在前置就绪后立刻启动,多节点可并行。

### 节点 N0 · 契约地基(L0)

**Exit Criteria**:
- `core` 第一版 proto 定义(身份 + 工作 + 对话 + 过程 + 治理 + 制品 六域事件类型)
- `bus` 抽象 + NATS JetStream 实现 + in-memory 实现
- `sdk` Python + Rust 最小客户端(能订阅 + 发布)

**产出**:可被所有下游仓引用的契约层
**前置**:无
**并行仓**:core / bus / sdk 三仓可并行(有依赖但边界清晰)

### 节点 N1 · 身份与对话先行(L1 子集)

**Exit Criteria**:
- `identity` 仓:GlobalMember CRUD + Role 注册 + 生命周期状态机 + 事件发布
- `conversation` 仓:Conversation 四形态 + Turn 基本字段 + AG-UI 事件对齐

**产出**:"人"和"说话"两个基础,下游所有域都要引用
**前置**:N0
**并行**:identity 和 conversation 可并行开发

### 节点 N2 · 工作与过程(L1 剩余)

**Exit Criteria**:
- `work` 仓:Project + ProjectMember + WorkItem + Iteration + 基本依赖图
- `process` 仓:BPMN 引擎最小实现 + ProcessTemplate / Profile / Instance 三段式 + 至少 2 种模板(iterative-standard / waterfall-classic)
- `governance` 仓:Gate 六段式对象 + Policy 下发 + Approval 投票
- `artifact` 仓:Artifact 状态机 + Relation 血缘 + Baseline

**产出**:六域全就位,核心业务逻辑可跑
**前置**:N1
**并行**:work / process / governance / artifact 四仓可并行(小心 process ↔ method-library 依赖)

### 节点 N3 · 方法能力层(L3)

**Exit Criteria**:
- `method-library` 仓:SPEM Method Content CRUD + 初始 ProcessTemplate 8 种(24748-2 家族)+ 9 种 Role 定义
- `capability-hub` 仓:MCP Registry + MCP Client 代理 + 2-3 个外部集成适配(GitHub / Figma 优先)

**产出**:"怎么做"和"用什么"两套资产就位
**前置**:N2
**注意**:process 仓的 BPMN 引擎需要 method-library 的内容才能跑起来,这个依赖要提早对齐

### 节点 N4 · Member 运行层(L2)

**Exit Criteria**:
- `member-images` 仓:9 个 Role 的镜像每晚 CI 构建(ADR-0005)
- `member` 仓:6 个子模块 + 容器内进程稳定启动
- `runtime` 仓:ReAct 主循环 + 三层记忆 + Checkpoint + Tool Invoker
- `tools` 仓:code / git / sandbox / lsp-python / test / mcp-client / ask-teammate 最小工具集
- `member-service` 仓:Docker 编排 + Endpoint Registry + Heartbeat + 按 Role 启容器

**产出**:AI 员工能进入项目、收事件、做决策、发 Artifact
**前置**:N3 + L4.sandbox 至少有 dev-mode
**并行**:5 仓可并行,但要有每日集成测试保证容器能起来

### 节点 N5 · 基础设施(L4)

**Exit Criteria**:
- `sandbox` 仓:Docker + gVisor 加固 + 资源限额 + 文件系统快照
- `observability` 仓:OTel Collector 配置 + 审计事件 append-only 存储 + 哈希链 + 追溯查询 API
- `archive` 仓:项目归档打包 + 恢复流程 + 分层存储(hot/warm/cold)

**产出**:合规证据、隔离保障、归档能力齐备
**前置**:N2(归档需要六域数据)+ N4(沙箱需要 Member 来用)
**并行**:3 仓完全可并行,互相独立

### 节点 N6 · MVP-M 首个端到端闭环

**Exit Criteria**:
- `chat` 仓:桌面端 + Web(最小可用)
- 用户能:立项 → Assistant 私聊 → 招 Backend Dev → 需求对话 → 代码产出 → 验收 Gate → 归档
- 本地 Docker Compose 一键部署

**前置**:N0-N5 全部
**这是第一个可演示版本**

### 节点 N7 · MVP-C(Console + Runner + Sync 并行)

**Exit Criteria**:
- `console` 仓:员工管理 + 方法库管理 + 审计视图 + 指标看板
- `runner` 仓:跨平台运行 AI 产出软件
- `sync` 仓:manifest 驱动的工作区同步
- 三项目并发 + 六阶段完整流程 + 42001 控制项基础覆盖

**前置**:N6
**并行**:3 仓可并行

### 节点 N8 · MVP-E(Bridges + SDK 正式版 + Marketplace + 合规)

**Exit Criteria**:
- `bridges` 仓:Mattermost + Slack 适配器
- `sdk` 仓:Python + Rust + TypeScript 稳定发布版
- `marketplace` 仓:资产上传 / 下载 / 审核基础版
- 42001 Tailored Conformance 完整证据链

**前置**:N7
**并行**:bridges / marketplace / sdk-publish 可并行

### 节点 N9 · `website` 营销站

**独立节点**:可在任何时机启动,不阻塞主路径
**前置**:需要有"可以展示的产品"(至少 MVP-M 可演示)
**交付**:营销页 + 文档站 + API 参考

## 六、发布节奏与版本策略

### 6.1 仓级发版

按 semver。L0 的 breaking change 触发全平台同步升级,必须走 ADR。

| 层 | 典型节奏 | Breaking Change 处理 |
|---|---|---|
| L0 | 月度稳定 + 紧急补丁 | 6 周 deprecation 窗口 + ADR |
| L1 | 双周 | 3 周 deprecation |
| L2/L3 | 周度 + 每晚 CI | 保持向后兼容,破坏性变更需升版 |
| L4 | 周度 | 依赖 L0 版本 |
| L5 | 双周 | 用户可见变更走 ChangeLog |
| L6 | 月度 | 外部平台 API 变化跟随 |

### 6.2 组合产品发版

| 产品 | 版本来源 |
|---|---|
| Server(组合) | 所有 L0+L1+L3+L4 仓的最新稳定版组合 |
| AI Members(组合) | L2 四仓的 image 组合,每晚 CI 自动发版 |

## 七、交付里程碑的验证

每个节点 N0-N9 交付时,必须同时产出:

1. **集成测试报告** — 该节点新增能力的端到端测试通过
2. **架构对齐证据** — 对照 `架构设计.md` 原则清单
3. **三红线对齐** — 可审计 / 可追溯 / 可裁剪 的具体落地点
4. **ADR 更新**(如有新决策)
5. **文档同步** — 涉及的 `domain/` / `standards/` 文档更新

## 八、风险与预案

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| L0 contract 频繁变更拉动全局 | 中 | 高 | 设 2 周冻结期 + 强制 ADR |

| 42001 合规证据体量过大 | 低 | 中 | 归档包分层存储,按日聚合 |
| MCP / A2A 生态不成熟 | 中 | 中 | capability-hub 设计时兼容降级(白名单为空也能跑) |

## 九、设计原则审视

| 原则 | 本路线图体现 |
|---|---|
| 先跑通再迭代 | N6 就产出 MVP-M,不追求"先做完美底层再上线" |
| 推迟不可逆决策 | 节点之间的边界允许调整,技术选型在节点内 ADR 决定 |
| 可演进 | L 层分层 + 节点并行 + 无 Phase 捆绑 |
| 最小化风险敞口 | 每节点都有 Exit Criteria,不达标不推进 |
| 可观测 | 每节点都要求集成测试 + 审计证据 |

## 十、与 24748-2 生命周期模型的对齐

本路线图自身是一个**生命周期模型实例**。按 ISO 24748-2 的分类:

- **选用的模型组合**:Incremental(增量)× Iterative(迭代)× Agile(敏捷)
- **裁剪方式**:Reduction(不做完整系统工程过程)+ Extension(新增 Node/MVP 概念)+ Adaptation(把 Sprint 映射为 2-4 周开发周期)
- **Decision Gates**:N0-N9 的每个 Exit Criteria 都是一次 Decision Gate
- **符合性声明**:本项目最终按 Tailored Conformance 声明符合 12207

详见 `methodology/standards-discussion/ISO-IEC-IEEE-24748-2.md`。

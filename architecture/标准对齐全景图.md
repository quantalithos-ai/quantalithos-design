## 二、仓间协作对齐

> 标准的价值不仅在**单仓内部对齐**,更在**跨仓协作的边界上**。本节按"协作类型"组织,列出每种协作涉及的标准。

### 2.1 领域事件流(L1 六域之间)

**场景**:六域通过 bus 发事件通信,不直接 RPC。

| 协作 | 涉及标准 | 参考内容 |
|---|---|---|
| 事件 schema | 【Research】CloudEvents 1.0 | 所有跨域事件统一 CloudEvents 包络 |
| 事件可追溯 | 【Research】W3C Trace Context + OTel GenAI | trace_id 贯穿事件链 |
| 事件次序与一致性 | 【Research】Temporal + 架构设计.md §4 一致性理论 | 最终一致 + Outbox 模式 |
| 事件内容审计 | 【ISO】42001 §9.1 + 9001 Documented Information | 事件=证据,不可篡改 |
| 事件级联防御 | 【Research】错误级联(arxiv 2603.04474) | 后续域不无脑信任前序事件,需要验证 |

**关键六元组事件族**(按 14 标准定义):

```
identity.member.*       ← SPEM RoleDefinition + 42001 AI Actor
conversation.turn.*     ← BPMN MessageFlow + AG-UI
work.project.*          ← 12207 Project / Scrum Product
work.workitem.*         ← 12207 Work Product / Scrum Backlog Item
process.instance.*      ← BPMN Process / SPEM ProcessUse
governance.gate.*       ← 24748-2 Decision Gate + 42001 Control
artifact.*              ← 15288 Work Product / 9001 Documented Information
```

### 2.2 Process ↔ Method-Library 协作(L1 ↔ L3)

**场景**:process 仓执行 Template,Template 的定义在 method-library。

| 协作点 | 涉及标准 | 参考内容 |
|---|---|---|
| Template 定义 | 【ISO】SPEM 2.0 Definition vs Use | TaskDefinition / RoleDefinition 在 method-library 里;TaskUse / ProcessInstance 在 process 里 |
| Template 分发 | 【ISO】29110 Deployment Package | method-library 的资产以 DP 格式对外分发 |
| Template 版本管理 | 【ISO】9001 文档控制 | Template 有版本 + 批准人 + 生效日期 |
| Template 裁剪 | 【ISO】29110 Profile + 24748-2 Tailoring Record | Profile 在 method-library,Tailoring Record 在 process.ProcessProfile |

### 2.3 Governance ↔ Process 协作(L1 内两域)

**场景**:流程里的 Gate 节点触发治理,治理完成回推流程。

| 协作点 | 涉及标准 | 参考内容 |
|---|---|---|
| Gate 触发 | 【ISO】BPMN UserTask / BoundaryEvent + 24748-2 Decision Gate | BPMN 在 process,Gate 一等对象在 governance |
| Gate 决策 | 【Research】自主性 5 级(arxiv 2506.12469) | governance.Gate.autonomy_level 决定 AI/人类权重 |
| Gate 超时 | 【ISO】42001 A.9 Responsible Use | 无响应的默认行为,governance 定义 |
| Gate 审计 | 【ISO】42001 §9.1 + 24748-2 Conformance Claim | Gate 决策留痕,归入 Conformance Claim |

### 2.4 Governance ↔ Artifact 协作(L1 内两域)

**场景**:42001 AIIA / SoA / ConformanceDeclaration 本质是 Artifact,但必须经过 Gate 审批。

| 协作点 | 涉及标准 | 参考内容 |
|---|---|---|
| AIIA 作为 Artifact | 【ISO】42001 §8.2 + 42005 | ImpactAssessment 既是治理活动也是 Artifact.kind |
| SoA 作为 Artifact | 【ISO】42001 §6.1.3 | Statement of Applicability 是可审计制品 |
| Artifact 基线 | 【ISO】24748-2 Baseline + 9001 | governance.Baseline 聚合控制哪些 Artifact 进入基线 |

### 2.5 Member Runtime ↔ 工具/方法 协作(L2 ↔ L3)

**场景**:runtime 执行 ReAct 循环时需要 tool_invoker 调用 tools + 按 Role 加载能力。

| 协作点 | 涉及标准 | 参考内容 |
|---|---|---|
| Tool 调用协议 | 【Research】MCP(Model Context Protocol) | 通过 capability-hub 代理调用 |
| Tool 前置校验 | 【Research】OpenAI Guardrails | runtime 在调用前过 policy cache |
| Tool 后置校验 | 【Research】OpenAI Guardrails | 输出 schema 校验,失败回滚 |

## 三、整体架构对齐

> 单仓和仓间对齐是"微观",本节讲"整体框架"的对齐 —— 哪些标准影响了 A 方案的**根本形态**。

### 3.1 六域模型的标准根据

| A 方案决策 | 对齐的标准 | 对齐方式 |
|---|---|---|
| 六域平权,不设主心骨 | 【方法论】DDD 限界上下文 + 架构设计.md §2.1 | 每个域 = 一个限界上下文 |
| Member 是持久实体 | 【ISO】SPEM 2.0 Role 持久化 + 42001 AI Actor | 员工即 AI Actor,有生涯 |
| Conversation 一等聚合根 | 【ISO】BPMN Collaboration + 【Research】AG-UI | 对话是 BPMN Collaboration 的领域化 |
| Gate 一等对象 | 【ISO】24748-2 Decision Gate + 42001 Control + 9001 Approval | 三标准共同要求的一等对象 |
| 过程三段式(Template/Profile/Instance) | 【ISO】SPEM Definition/Use + 29110 Profile + BPMN 元模型 | 三标准合力 |
| Artifact 带状态机 | 【ISO】15288 SoI + 9001 Documented Information + 24748-2 Baseline + 25010 QualityTag | 四标准合力 |
| 跨域只发事件 | 【Research】CloudEvents + 【方法论】架构设计.md §4.1 聚合间最终一致 | 标准 + 架构理论合力 |

### 3.2 26 仓 × 7 层拆分的标准根据

| 拆分决策 | 对齐的标准 | 对齐方式 |
|---|---|---|
| 按聚合分仓(L1) | 【方法论】DDD 聚合根 + 架构设计.md §3.1 稳定依赖 | 每聚合一仓 |
| L0 契约层独立 | 【Research】CloudEvents + W3C TC + 架构设计.md §6 演进性 | 最稳定层独立,支撑演进 |
| L2 Member 运行层 5 仓 | 【ISO】SPEM RoleDefinition + ADR-0005 镜像预构建 | Role 稳定 → 镜像预构建 → 5 仓分工 |
| L3 Method/Capability 分 | 【ISO】SPEM Method Content vs 【Research】MCP Server Registry | "方法"和"能力"是不同种类的资产 |
| L4 Sandbox/Observability/Archive | 【Research】沙箱逃逸 + 【ISO】42001 §7.5 + 24748-2 Conformance Claim | 三个横切关注点 |
| L5 UI 多仓 | 【ISO】25010 Interaction Capability(不同产品不同优化方向) | UI 按产品形态拆,不混 |
| L6 生态独立 | 【ISO】42001 A.10 + 9001 供应商管理 | 外部接入的治理边界 |

### 3.3 三段式推进的标准根据

| 决策 | 对齐的标准 |
|---|---|
| 段 1 蓝图固化优先 | 【方法论】架构设计.md §7 ADR + §1.1 不可逆决策 |
| 段 2 设计补全 | 【ISO】42001 §6 策划(AIIA 必须前置) |
| 段 3 写代码前准备 | 【ISO】24748-2 七步法(Step 6 执行之前必须走完 1-5) |
| 路线图 N0-N9 节点 | 【ISO】24748-2 增量+迭代+敏捷组合 + 【ISO】Scrum Sprint |

### 3.4 三条横切红线的标准根据

| 红线 | 标准依据 | 具体条款 |
|---|---|---|
| 可审计性 | 【ISO】42001 A.2/A.5/A.6 + 9001 §9 绩效评价 + 27001 审计要求 | 所有写操作 append-only + 哈希链 |
| 可追溯性 | 【ISO】24748-2 §3.4 可追溯 + 12207 配置管理 + 15288 SoI 血缘 | Artifact → Turn → Member → WorkItem → Process 全链路 |
| 可裁剪性 | 【ISO】29110 Profile + 24748-2 Tailoring + SPEM Method Plugin | 不硬编码过程/角色/Gate |

### 3.5 整体架构必守的标准优先级

当多个标准对同一问题有不同要求时,按以下优先级裁决:

1. **42001**(AI 治理)> 其他(对 AI 特化事项)
2. **24748-2**(生命周期与裁剪)> 12207/15288(基础过程)
3. **29110 Profile**(裁剪机制)> 24748-2 Tailoring(理念一致但 29110 更可执行)
4. **BPMN 2.0**(流程表达)> SPEM(过程元模型)(BPMN 是实现,SPEM 是定义,实现优先)
5. **9001 PDCA** > 其他(是跨所有 MS 标准的骨架)
6. **25010**(质量特性)> 其他(作为术语约定)
7. **Research 结论** > ISO 标准(**仅在 AI 特化事项且 ISO 尚未涵盖时**,例如 Prompt Injection 防御)

### 3.6 整体架构刻意不追的标准

| 标准 | 为什么不追 |
|---|---|
| 完整 CMMI ML 5 评估 | 成本过高,只借鉴 PA 清单,不做 ML 评估 |
| 完整 SPICE Assessment | 只借鉴 PRM + PAM 骨架,不跑正式评估 |
| 完整 9001 认证 | 初期 Self-declaration,中期才争取第三方 |
| BPMN Choreography 视角 | 我们用 Collaboration 和 Process 两视角足够 |
| 完整 Automotive SPICE | 不做汽车行业 |
| COBIT | 企业 IT 治理,不是产品本身关注点 |
| ITIL(IT 服务管理) | 产品期暂不涉及,后期 SaaS 运营可能引入 |
| XP 全部工程实践 | 吸收部分(TDD、CI、Pair),不做全盘 |
| SAFe | 过重,适合超大组织 |

## 六、重要观察(本文整理过程中的发现)

### 6.1 14 标准里最"赚"的几份

- **24748-2**:贯穿 `process` / `governance` / `method-library` / `archive` 四仓,是整体架构的方法论基石
- **42001**:定义了 AMI 本体,影响治理 / 身份 / capability-hub 三仓 + 整体合规路径
- **SPEM 2.0**:是 `method-library` + `identity` + `member-images` 的核心;Definition/Use 分离是 A 方案最关键原则之一
- **BPMN 2.0**:`process` 的引擎原语 + `conversation` 的抽象结构

### 6.2 有些标准覆盖度超预期

- **25010**:原以为只在 `chat`,实际在 `artifact` / 几乎所有 L5 / `sandbox` / `console` 都有角色
- **9001**:看似"传统质量",实际是所有 MS 标准(27001/42001)的 HLS 基石
- **Scrum + Kanban**:不止在"敏捷节奏",还深入 `work` / `conversation` / `chat` UI

### 6.3 标准覆盖度不足的领域

- **非功能性测试的标准对齐** → 未来可能需要引入 ISO 29119(测试过程)补齐
- **持续集成/部署的标准对齐** → 未来可能需要引入 IEEE 1012(V&V)补齐
- **需求工程** → 未来可能需要 IEEE 29148(SRS 格式)补齐
- **架构描述** → 未来可能需要 IEEE 42010(架构描述)补齐

这 4 份标准的讨论文档尚未建立(`—(待补)`)。

### 6.4 有些 Research 结论超出任一 ISO 标准覆盖

- **Prompt Injection 组合防御** — 42001 虽有安全要求但无具体方案
- **LLM 路由** — 所有标准都没有这个概念
- **记忆三层架构** — 42001 没到这个细度
- **自主性 5 级** — 42001 A.9 暗示但未显式分级

这些是 AI 特有的,ISO 生态还在追赶。Quantalithos 的价值一部分在于**把 Research 结论制度化**,等 ISO 正式标准补齐时直接对接。

### 6.5 整体架构的"标准化评级"

综合看,A 方案的标准对齐情况:

| 维度 | 评级 | 依据 |
|---|---|---|
| 过程治理对齐 | ⭐⭐⭐⭐⭐ | BPMN/SPEM/12207/15288/24748-2/29110 全覆盖 |
| AI 治理对齐 | ⭐⭐⭐⭐ | 42001 对齐,待原文复核完善 |
| 质量对齐 | ⭐⭐⭐⭐ | 25010 对齐,待原文复核 |
| 评估对齐 | ⭐⭐⭐ | CMMI/SPICE/330xx 借鉴,不做完整评估 |
| 敏捷对齐 | ⭐⭐⭐⭐ | Scrum+Kanban 覆盖执行节奏 |
| QMS 对齐 | ⭐⭐⭐⭐ | 9001 PDCA 骨架 |
| AI 特化 | ⭐⭐⭐⭐⭐ | Research 清单覆盖 ISO 生态的缺口 |
| 标准间优先级 | ⭐⭐⭐⭐ | 见 §3.5,明晰有序 |

**薄弱环节**:测试标准(29119)+ V&V 标准(IEEE 1012)+ 需求标准(29148)+ 架构标准(42010)。这些是段 2 / 段 3 的补齐目标。

## 一、部署拓扑总览

Quantalithos 支持 **三种部署拓扑**,同源代码同 proto,按规模与合规选择:

| 拓扑 | 主要用户 | 规模假设 | 运维成本 |
|---|---|---|---|
| **Single-node(Docker Compose)** | 开发 / 单机 SaaS 试点 / 演示 | 1-10 用户 / 5 项目 / 10 AI Member | 极低 |
| **Cluster(Kubernetes)** | 企业自托管 / 中型 SaaS 部署 | 10-10000 用户 / 数百 项目 / 千级 AI Member | 中 |
| **Managed SaaS(Quantalithos 官方)** | 最终用户无需运维 | 10000+ 用户 / 多租户 | Quantalithos 承担 |

**关键原则**:三种拓扑**完全同源**(同一 Docker 镜像集、同一 Helm Chart、同一 Terraform 模块),**不为不同拓扑维护不同代码分支**。规模差异由配置驱动。

## 二、Single-node 部署

### 2.1 拓扑图

```
┌────────────────────────────────────────────────────┐
│  单台主机(Linux / macOS / Windows WSL2)          │
```

### 2.2 启动命令

```bash
# 一键启动全栈
curl -fsSL https://install.quantalithos.example.com | bash

# 等价于下面步骤:
git clone https://github.com/quantalithos/quantalithos-server-deploy
cd quantalithos-server-deploy/single-node
cp .env.example .env
# 编辑 .env(至少配 JWT_SECRET / DB_PASSWORD / OAUTH_CLIENT_SECRET)
docker compose up -d

# 验证
docker compose ps
curl -s https://localhost/health
```

### 2.3 资源需求

| 指标 | 最低 | 推荐 |
|---|---|---|
| CPU | 4 核 | 8 核 |
| 内存 | 8GB | 16GB |
| 磁盘 | 50GB(不含 AI Member 镜像) | 200GB |
| 网络 | 50Mbps 出网 | 200Mbps |

**AI Member 镜像**:9 个 Role 镜像 × 平均 500MB = 4.5GB 一次性拉取(docker pull 完后本地可共享 layer)。

### 2.4 适用场景与限制

**适用**:
- 开发 / demo / 演示
- 小团队试点(≤ 10 用户)
- Air-gap 环境(见 §五)

**不适用**:
- 生产多租户 SaaS
- 高可用要求(本拓扑是 single point of failure)
- 数据冗余要求

### 3.3 关键部署配置

#### 3.3.1 PG 高可用

```yaml
# values-medium.yaml(节选)
postgres:
  architecture: cluster
  replicaCount: 3
  persistence:
    size: 500Gi
    storageClass: fast-ssd
  backup:
    enabled: true
    schedule: "0 2 * * *"         # 每日凌晨 2 点
    retention: 30d
  monitoring:
    enabled: true
```

**迁移**:identity / conversation / work / process / governance / artifact 各有独立 schema,共享 PG cluster 或独立 cluster(由 values 决定)。

#### 3.3.2 NATS JetStream

```yaml
nats:
  cluster:
    enabled: true
    replicas: 3
  jetstream:
    memStorage: 1Gi
    fileStorage: 100Gi
    maxAge: 90d                   # 业务流保留 90 天
    maxAgeAudit: 2555d            # 审计流保留 7 年
  tls:
    enabled: true
    secretName: nats-tls
  auth:
    enabled: true
```

#### 3.3.3 对象存储(MinIO)

```yaml
minio:
  mode: distributed
  replicas: 4
  persistence:
    size: 2Ti                     # 每节点 2TB
  buckets:
    - name: artifacts
      policy: private
    - name: checkpoints           # ADR-0007 Checkpoint 外部 blob
      policy: private
    - name: memory                # ADR-0006 Memory 向量
      policy: private
    - name: archive-cold
      policy: private
      lifecycle:
        transitionToGlacier: 90d  # (AWS)冷存迁移
```

#### 3.3.4 L1 服务 HPA(水平扩缩)

```yaml
services:
  conversation:                   # 对话写入频率最高
    replicaCount: 3
    autoscaling:
      enabled: true
      minReplicas: 3
      maxReplicas: 20
      targetCPUUtilizationPercentage: 70
      targetMemoryUtilizationPercentage: 80
  governance:                     # 高可用 ≥ 99.95%
    replicaCount: 3
    autoscaling:
      enabled: true
      minReplicas: 3
      maxReplicas: 10
    podDisruptionBudget:
      minAvailable: 2             # 滚动升级时保证可用
  process:                        # Activity 持久执行,有状态
    replicaCount: 3
    # process 可能更适合 StatefulSet,见 §三.4
```

### 3.4 有状态 vs 无状态

| 服务 | 形态 | 原因 |
|---|---|---|
| identity | Deployment | 无状态(PG 在外) |
| conversation | Deployment | 无状态 |
| work | Deployment | 无状态 |
| **process** | **StatefulSet or Deployment + leader** | Checkpoint 写 PG,但引擎内存态复杂;按需测试决定 |
| governance | Deployment | 无状态 |
| artifact | Deployment | 无状态 |
| method-library | Deployment | 无状态(读多) |
| capability-hub | Deployment | 无状态 |
| observability | Deployment | 无状态(TSDB 在外) |
| archive | Deployment | 无状态(对象存储在外) |
| **member-service** | **StatefulSet** | 管理容器池 + leader election |

## 四、Managed SaaS 部署(Quantalithos 官方)

### 4.1 拓扑特点

Managed SaaS 基于 Cluster 拓扑,多加**多租户 + 全球部署 + 计费集成**:

```
┌─────────────────────────────────────────────────────────────────────┐
│  全球边缘(CDN + Anycast)                                           │
│  ├─ quantalithos.ai(Website + 登录)                              │
│  ├─ api.quantalithos.ai(主 API 路由)                             │
│  └─ chat.quantalithos.ai(Chat Web)                               │
└─────────┬───────────────────────────────────────────────────────────┘
          │
┌─────────┴───────────────────────────────────────────────────────────┐
│  区域集群(US-East / EU-West / AP-South,按租户就近)                │
│  ├─ 控制面(identity / billing / tenancy / routing)                │
│  ├─ 业务面(6 × 3 L1 cluster + L3/L4)                            │
│  └─ 数据面(PG / NATS / MinIO,按租户分片或共享)                 │
└─────────────────────────────────────────────────────────────────────┘
          │
┌─────────┴───────────────────────────────────────────────────────────┐
│  Member Runtime 池(每租户独立 Namespace / Node Group)             │
│  └─ member-service + member pods(每 ProjectMember 一个)          │
└─────────────────────────────────────────────────────────────────────┘
```

### 4.2 多租户隔离策略

三级隔离(强度递增):

1. **逻辑隔离(共享集群 + tenant_id 过滤)** — 默认小租户;PG row-level security;NATS subject 带 tenant_id
2. **命名空间隔离(共享节点 + 独立 Namespace)** — 中等租户;Namespace 级 RBAC + NetworkPolicy
3. **物理隔离(独立 Node Group / 甚至独立 Cluster)** — 大企业 / 高合规租户

**默认规则**:
- 新注册:逻辑隔离
- 付费升级:命名空间隔离
- 企业 + 合规需求(HIPAA / FedRAMP 等):物理隔离

### 4.3 边缘 + 区域路由

- **Website**:CDN(Cloudflare / AWS CloudFront)
- **API**:GeoDNS 路由到最近区域 cluster
- **Chat WebSocket**:同区域粘滞(保持 StreamEvents 连接)
- **Bridges**:按外部平台接入区域就近部署

### 4.4 计费与 SLA

(不在本文硬设计,留给 billing 系统产品阶段决策):

- Metering:`capability-hub` 记 LLM token / 对外 API 调用成本
- SLA tier:99.5% / 99.9% / 99.95%(对应三级隔离)
- 成本模型:订阅费 + 按量(Member 活跃 / LLM token)

### 4.5 与 Cluster 部署的主要差异

| 维度 | Cluster(客户自托管) | Managed SaaS |
|---|---|---|
| 多租户 | 单租户或简单多租户 | 三级隔离 |
| 升级 | 客户控制节奏 | Quantalithos 统一排期 |
| 跨区域 | 客户自己做 | 原生多区域 |
| 计费 | 无 | 有完整计费 |
| 合规 | 客户负责 | Quantalithos 有 ISO 42001 认证 |

## 五、Air-Gap 与离线部署

### 5.1 需求场景

企业客户常见需求:

- 政府 / 军工 / 金融监管环境不允许出网
- 无法访问 quantalithos.ai 的注册 / 镜像 / LLM 供应商
- 需要完整产品在内网可用

### 5.2 Air-Gap 部署包

Quantalithos 提供 `air-gap bundle`:

```
quantalithos-air-gap-v1.2.3.tar.zst(约 8-12GB)
├── images/                        所有 26 仓的 Docker 镜像 tar
│   ├── core-*.tar
│   ├── identity-*.tar
│   ├── ...
│   └── ai-member-*.tar            9 个 Role 镜像
├── helm-charts/                   离线 Helm chart 包
├── terraform/                     可选基础设施 terraform(air-gap 版)
├── docs/
│   ├── install-guide.pdf
│   ├── offline-upgrade.pdf
│   └── runbook.pdf
├── signatures/                    cosign 签名验证
└── install.sh                     离线安装脚本
```

### 5.3 离线安装流程

```bash
# 1. 下载 bundle(通过物理介质 / 运维通道)
# 2. 验证签名
cosign verify-blob \
  --signature quantalithos-air-gap-v1.2.3.tar.zst.sig \
  --certificate quantalithos-air-gap-v1.2.3.tar.zst.cert \
  quantalithos-air-gap-v1.2.3.tar.zst

# 3. 解压
tar -I zstd -xf quantalithos-air-gap-v1.2.3.tar.zst

# 4. 导入镜像到内网 registry
for img in images/*.tar; do
  docker load < "$img"
  docker tag "<temp-name>" "registry.internal:5000/<name>"
  docker push "registry.internal:5000/<name>"
done

# 5. 安装
cd helm-charts
helm install quantalithos quantalithos-umbrella.tgz \
  -f values-air-gap.yaml
```

### 5.4 Air-Gap 场景下的限制

| 限制 | 影响 | 解决 |
|---|---|---|
| 无法调 Anthropic / OpenAI API | LLM 不可用 | 用户必须自托管 LLM(例如 vLLM + Llama / Qwen / DeepSeek) |
| 无法用 Quantalithos Marketplace | 资产无法下载 | 提供离线资产包;企业可自建内部 Marketplace |
| 无法自动升级 | 升级需要人工介入 | 定期产出离线升级包 + 人工安装 |
| 无远程 LLM 审计 | 需本地完整审计 | observability 本地审计链足够(air-gap 常见强审计要求) |

### 5.5 自托管 LLM 集成

`capability-hub` 的 Provider Contract 支持:

```yaml
# values-air-gap.yaml(节选)
capabilityHub:
  providers:
    - id: "llama-internal"
      kind: "openai-compatible"
      endpoint: "http://vllm-server.internal:8000/v1"
      models:
        - name: "llama-3.3-70b"
          cost_per_1k_tokens: 0
        - name: "qwen-2.5-coder-32b"
          cost_per_1k_tokens: 0
      routes:
        default: "llama-3.3-70b"
        coding: "qwen-2.5-coder-32b"
```

Runtime C1 LLM Loop 调用时不感知具体 endpoint,只认 capability-hub 的路由。

## 六、网络拓扑与安全

### 6.1 网络分层

```
┌─────────────────────────────────────────────────────┐
│  [外部] 客户端(Chat / Console / Runner / Sync / Bridges)│
└────────────────┬────────────────────────────────────┘
                 │ TLS 1.3 + OAuth2 / mTLS
                 ▼
┌─────────────────────────────────────────────────────┐
│  [边缘] Ingress / WAF / Rate Limit                    │
│  ├─ TLS 终止                                          │
│  ├─ OAuth2 token 验证                                │
│  ├─ 速率限制(tenant 级)                            │
│  └─ WAF(OWASP Top 10 防护)                        │
└────────────────┬────────────────────────────────────┘
                 │ mTLS(内部)
                 ▼
┌─────────────────────────────────────────────────────┐
│  [L5 UI 层 Pod 网络]                                  │
│  ├─ Chat Web Server(如适用)                        │
│  └─ Console Web Server                              │
└────────────────┬────────────────────────────────────┘
                 │ mTLS
                 ▼
┌─────────────────────────────────────────────────────┐
│  [L1-L4 Service Mesh]                               │
│  ├─ 六域服务                                         │
│  ├─ L3 / L4 服务                                    │
│  └─ member-service                                  │
└────────────────┬────────────────────────────────────┘
                 │ mTLS
                 ▼
┌─────────────────────────────────────────────────────┐
│  [L2 Member 容器池]                                   │
│  ├─ 强网络隔离:容器间默认不可通信                    │
│  ├─ 允许流量:容器 ↔ member-service / bus / L1 服务 │
│  └─ 出网默认 deny,白名单 allow(经 capability-hub) │
└─────────────────────────────────────────────────────┘
```

### 6.2 mTLS 细节

- **内部服务 mTLS**:全部启用(子项目清单 R10 + 产品清单 SV3)
- **证书来源**:
  - Cluster:cert-manager + 内部 CA 或 Let's Encrypt
  - Managed SaaS:全球 CA 根证书 + 区域中间 CA
- **证书轮换**:每 90 天自动续签
- **服务身份**:SPIFFE ID 格式 `spiffe://quantalithos.internal/ns/<namespace>/sa/<service>`

### 6.3 NetworkPolicy

典型 Cluster 部署下的 Kubernetes NetworkPolicy:

```yaml
# L2 Member 容器的 NetworkPolicy(严格)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: member-container-restrict
  namespace: quantalithos-member
spec:
  podSelector:
    matchLabels:
      component: ai-member
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: {name: quantalithos-member}
          podSelector:
            matchLabels: {app: member-service}
  egress:
    - to:
        - namespaceSelector:
            matchLabels: {name: quantalithos-data}    # bus
    - to:
        - namespaceSelector:
            matchLabels: {name: quantalithos-core}    # L1 服务
    - to:
        - namespaceSelector:
            matchLabels: {name: quantalithos-system}
          podSelector:
            matchLabels: {app: capability-hub}
    # 不允许任何其他出网!LLM 调用必须经 capability-hub 代理
```

### 6.4 Secret 管理

- **KMS**:AWS KMS / GCP KMS / Vault Transit Engine
- **envelope encryption**:敏感字段(API key / PII / launch_token)走信封加密
- **external-secrets operator**:从 Vault 同步到 Kubernetes Secret(只读挂载)
- **不允许**明文 Secret 写 etcd

### 6.5 审计日志

所有 API 调用发 observability 的审计链(append-only + hash chain)。访问 Console 的操作同样审计(42001 §9.2 内审要求)。

## 七、灾备与恢复

### 7.1 备份策略

| 数据类型 | 备份频率 | 保留 | 存储 |
|---|---|---|---|
| PG(业务数据) | 每日全量 + 持续 WAL | 30 天 hot / 1 年 warm / 7 年 cold | 跨区域对象存储 |
| PG(审计表) | 每日全量 + 持续 WAL | 7 年(合规基线) | 跨区域 + WORM |
| NATS JetStream | 每小时快照 | 7 天 | 同区域 |
| MinIO(artifact / checkpoint) | 对象版本化 + 跨区域复制 | 按 RetentionPolicy | MinIO 版本化 + S3 Glacier |
| Qdrant / pgvector(memory) | 每日快照 | 30 天 | 同区域 |

### 7.2 RPO / RTO 目标

| 场景 | RPO | RTO |
|---|---|---|
| 单 Pod 故障 | 0 | < 30s(k8s 自动重启) |
| 单节点故障 | 0(多副本) | < 2min(调度到其他节点) |
| 单可用区故障 | < 1min | < 10min(流量切换到其他 AZ) |
| 整个区域故障 | < 5min(跨区域复制) | < 30min(切换到备区域) |
| 整体灾难 | < 24h(每日备份) | < 4h(从备份重建) |

### 7.3 演练

Managed SaaS 每季度做一次演练:
- 模拟单 AZ 故障(切断网络)
- 模拟 PG 主故障(手动 kill primary)
- 模拟 NATS 集群脑裂(网络分区)
- 恢复到预期 RPO / RTO

Cluster 自托管提供演练脚本,客户按需执行。

## 八、滚动升级

### 8.1 升级顺序(铁律)

对齐 `产品矩阵.md` §9.3 发布流水线:

```
core.proto 改动
  ↓
Server 核心服务
  ├─ 先滚 identity(最独立,影响面小)
  ├─ 然后 method-library / capability-hub(无状态,被消费多)
  ├─ 然后 governance(高依赖,必须稳)
  ├─ 然后 work / conversation / artifact
  ├─ 然后 process(状态复杂,最后滚)
  └─ 最后 member-service
  ↓
AI Members 镜像(触发员工容器按 Policy 滚动重启)
  ↓
SDK(三语言同步发版)
  ↓
UI 产品(Chat / Console / Runner / Sync,各自按 4 周节奏)
  ↓
Bridges(按需)
```

### 8.2 PodDisruptionBudget

每个服务的 PDB 保证滚动时最小可用:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: governance-pdb
spec:
  minAvailable: 2              # 3 副本时,至少 2 可用
  selector:
    matchLabels: {app: governance}
```

governance 要求 `minAvailable: 2`(3 副本里),其他服务可以 `minAvailable: 1`。

### 8.3 Schema migration 策略

三阶段迁移(避免停机):

```
Phase 1: 扩展(deploy new version 前)
  - 新表 / 新列 / 新索引添加
  - 保持 backward compatible
  - 部署新代码(双读 - 可选)

Phase 2: 切换(deploy new version)
  - 流量切新代码
  - 新代码写双写或写新 schema
  - 老代码仍能读(兼容期)

Phase 3: 收缩(new version 稳定后)
  - 迁移老数据
  - 删老列 / 老表
  - 下个 major 版本一起清理
```

### 8.4 Breaking Change 升级

Schema 的 breaking change(极罕见,需要 ADR):
- 按三阶段迁移
- 整体过渡期 ≥ 2 个 minor
- 提供专用 migration runbook
- Managed SaaS 统一排期 + 客户通知

### 8.5 回滚策略

- Server 主版本:保留上 3 个版本可回滚(deployment rollback 秒级)
- AI Members 镜像:保留上 5 个版本(docker tag retention)
- Schema:**不回滚 schema**(只回滚代码,新 schema 向后兼容老代码)
- 数据:如需恢复,走备份 restore(RTO < 4h)

### 8.6 Canary / Feature Flag

大版本启用 canary:

```yaml
# 10% 流量到 new version
apiVersion: flagger.app/v1beta1
kind: Canary
metadata:
  name: governance
spec:
  analysis:
    interval: 1m
    threshold: 5
    stepWeight: 10
    maxWeight: 50                # 上限 50%,剩余经 Gate 人工审批
  webhooks:
    - name: smoke-test
    - name: regression-check
```

新功能可选 feature flag(governance Policy 驱动):
- 租户级开关
- 用户级开关
- 百分比 rollout

### 9.1 OTel Collector

```
[各服务 pod] → OTel SDK → OTel Collector(sidecar or cluster-wide DaemonSet)
                                         ↓
                                         ├─ Prometheus(metrics)
                                         ├─ Jaeger / Tempo(traces)
                                         └─ Loki(logs)
                                         ↓
                                     quantalithos-observability
                                     ├─ 审计链(append-only + hash)
                                     ├─ 指标聚合(DORA / EBM)
                                     └─ 血缘查询 API
```

### 9.2 仪表板

Grafana 默认仪表板:

1. **整体健康** — 六域服务可用性 + bus 吞吐 + 延迟
2. **DORA 指标** — Lead Time / Deployment Frequency / Change Failure Rate / Recovery Time
3. **EBM 指标** — Current Value / Unrealized Value / Time to Market / Ability to Innovate
4. **AI Member 运行** — 容器数量 / LLM 调用成本 / Tool 调用
5. **Governance** — Gate 挂起时长 / Policy 分发延迟 / Nonconformity 未关闭
6. **Outbox 健康** — 积压 / 发布延迟 / DLQ

### 9.3 告警(PagerDuty / OpsGenie)

见 `architecture/bus-draft/README.md` §八 + 各 domain README §七。关键:

- 后端(PG / NATS / MinIO)不可用 → critical
- 审计链哈希断裂 → critical
- governance 可用性 < 99.95% → major
- 沙箱逃逸检测 → critical
- AIIA 到期未复评 → major

## 十一、开放问题

### Q1. process 服务是 Deployment 还是 StatefulSet

见 §3.4 表。Instance 有状态(Checkpoint + Token + 运行时上下文),StatefulSet 更安全但调度灵活性差。

**推进**:段 3 末压测后决策。

### Q2. Member 容器的 Node Group 策略

**候选**:
- A 与 L1 服务混布(节省资源)
- B 独立 Node Group(隔离 + 可按 Member 用量自动扩缩)
- C GPU 节点单独(若未来 Member 需要 GPU)

**倾向**:B

**推进**:中等规模部署实测后。

### Q3. Namespace 粒度

- 按层分(data / core / member / edge / bridges)
- 还是按租户分(tenant-A / tenant-B)
- 还是混合(系统 Namespace + 租户 Namespace)

**倾向**:按层(当前设计)+ Managed SaaS 叠加租户 Namespace

### Q4. observability 是 push 还是 pull

- OTel Collector 主流是 push(各服务主动发)
- Prometheus 传统是 pull(scrape)
- 本设计默认 push(OTel)+ 关键指标补 pull

### Q5. Air-Gap 升级的频率

- 月度?季度?半年?
- 紧急安全补丁走 fast track

**倾向**:季度大版本 + 紧急补丁

### Q6. 自托管 LLM 的最低基线

Air-Gap 场景下 Runtime 需要 LLM。**最小配置**:
- 单 H100 或 A100 80G 跑 Llama 3.3 70B(推理速度勉强)
- 或 2 × A6000 48G 跑 Qwen 32B
- 或 Llama 8B + 多实例(不推荐,质量不够)

**推进**:自托管场景发布阶段。

#### 四、贯穿全部 11 份文档的共同骨架

**共同骨架 1:Definition vs Use 的分离**
- SPEM:TaskDefinition → TaskUse
- 12207/15288:Process(定义)→ Activity/Task(使用)
- Scrum:Product Goal(长期)→ Sprint Goal(当前承诺)

**共同骨架 2:Purpose → Outcomes → Activities → Tasks → Work Products**
- 12207/15288/29110/15504/330xx 统一五层
- CMMI 变体:Goal → Practice → Implementation → Evidence
- ISO 9001 变体:Policy → Objective → Process → Record → Audit

**共同骨架 3:术语三对要区分**
- Process ≠ Procedure ≠ Method
- Outcome ≠ Work Product ≠ Deliverable
- Verification ≠ Validation
- Conformance ≠ Compliance

**共同骨架 4:裁剪 / 符合性机制**
- 12207/15288:Full/Tailored Conformance + Task-based/Outcome-based claim
- 29110:Profile Group → Profile → Tailoring
- 15504/330xx:Assessment Class + Context + Comparability
- CMMI:Tailoring 到组织标准过程

**共同骨架 5:检视-适应闭环**
- PDCA(ISO 9001 主干)
- Empiricism / Inspect-Adapt(Scrum)
- Feedback Loop with Action(Kanban)
- Monitoring → Audit → Management Review → Nonconformity → Corrective Action(9001)
- Appraisal → Gap → Improvement Action(CMMI / 15504 / 330xx)

#### 一、这些规则能构成"完整的软件开发流程"吗

**能构成完整的"治理 + 过程骨架 + 评估闭环",但不够构成完整的"软件开发流程"。**

覆盖了的 ✓:
- 为什么做(9001 / 12207 协议过程组)
- 谁来做、做到什么(12207 / 15288 / 29110 的过程目的和结果)
- 按什么节奏跑(Scrum / Kanban)
- 画给谁看、给谁执行(BPMN / SPEM)
- 怎么知道做对了(9001 / CMMI / 15504 / 330xx)
- 怎么持续变好(PDCA / Inspect-Adapt / Appraisal-Improve)

没覆盖的 ✗(必须外接):
- 代码怎么写(XP / 编码规范 / 评审 / TDD)
- 系统怎么部署(DevOps / CI/CD / SRE / 可观测性)
- 安全合规(ISO 27001 / 21434 / GDPR / SBOM)
- 产品应该做什么(Product Discovery / 用户研究 / 增长 / 数据分析)
- 架构本身的设计(42010 / DDD / 设计模式)
- 组织文化与变革(9001 只给治理骨架)

所以这套标准组合是**"骨架 + 治理 + 检视"**,不是完整的 SDLC。真正的"怎么做软件"还得靠工程实践和产品方法论填进骨架里。

#### 三、一句话总结

这 11 份标准整合后,回答的是"**一个组织应该如何把软件研发这件事作为一个受控的 · 可改进的 · 可证明的经营活动来组织**" — 覆盖面是**经营治理 + 过程骨架 + 节奏控制 + 证据评估**。

但**"软件到底怎么做出来"是这个骨架之外的事** — 骨架规定你要有 Implementation / Verification 过程并留下 Evidence,但不规定你具体怎么写代码、怎么部署、怎么做用户研究。

对 Quantalithos 来说,这意味着:这套骨架可以直接用作"AI 员工如何在一个受治理的项目里协作"的元模型,但产品内核里还得单独规划**工程实践层**(代码/测试/部署)、**产品层**(要做什么)和**AI 特有的治理层**(Model/Data/Eval)。

```
验证域
  Verification                        对照规格验证
```

```
  10. 产品组装 / 放行           29110 SI.06 · 9001 Release
  11. 转移 / 上线               12207 Transition
  12. 确认                      12207 Validation · CMMI Validation
  13. 运行                      12207 Operation
  14. 维护                      12207 Maintenance · 9001 Change
  15. 处置                      12207 Disposal

  持续贯穿的 6 条横切过程(非阶段,一直在跑):
   A · 项目管理      12207 Planning · 29110 PM · CMMI Managing
   B · 配置管理      12207 CM · CMMI CM
   C · 信息 / 度量   12207 Information & Measurement
   D · QA / 评审     9001 Audit · CMMI QA · 12207 QA
   E · 需求变更      9001 Change · 12207 Req Mgmt
   F · 决策 / 风险   12207 Decision & Risk · CMMI Risk

  组织每一次穿越的节奏框架(非阶段,节拍器):
   瀑布:   1→2→3→...→15 一次走完
   迭代:   2→3→4→5→6→7→8→9→返回 2 多次循环
   Scrum:  每个 Sprint 跑完 "需求→设计→编码→测试→Increment"
   Kanban: 每个 Work Item 自己走完工作流
   DevOps: 10→11→13 高频自动化
```

#### 三、几个值得注意的差异

1. **12207 的 14 个技术过程是最完整的答案**,其它标准要么是它的子集(29110、CMMI),要么是它的变体(ASPICE SWE.1-6)。
2. **29110 Basic 给出"最小必须经历"的 6 步**(SI.01~SI.06),对 ≤25 人团队是官方认可的合法裁剪版。
3. **CMMI 不按顺序讲**,讲的是"你必须具备这些能力",顺序由自己的生命周期模型决定。
4. **Scrum / Kanban 不单独定义"阶段"**,规定的是节奏,把 12207 过程**压缩进每个 Sprint 或每张卡**。
5. **Verification 和 Validation 是两步**:
   - Verification = 对照**规格**("造对了吗")
   - Validation   = 对照**价值**("造了对的吗")
6. **架构(Architecture)和设计(Design)是两步不是一步**(15288 特别强调)。

#### 四、结论

**有明确答案。**

- 想要权威完整清单 → **IEEE 12207 的 14 个技术过程**
- 想要小团队裁剪版 → **29110 Basic 的 PM + SI(6 activity)**
- 想要能力检查单 → **CMMI Doing 的 5 个 PA**

这些清单给的都是"**有哪些过程必须被覆盖**",**不规定"用什么方法 / 什么工具 / 什么节奏"去做** — 这是三份标准共同的立场,也是它们和 Scrum/Kanban/DevOps 互补而不冲突的原因。

| 过程 | 怎么用 prototype |
|---|---|
| Life Cycle Model 选择 | "iterative development 模型由 prototyping/testing/analyzing/refining 循环构成" |

| System Analysis | 方法之一:"engineering models, simulation, visualization, and **prototyping**" |
| Integration | "Firmware 常以 **prototype** 形式制造并装到硬件里" |

| Validation | "用 prototype 做可用性确认" |
| Configuration Management | CM 要覆盖 "software design, **prototype**, integration, test releases" |
| Disposal | 概念/开发阶段的 prototype 需要处置 |

**ISO/IEC/IEEE 15288:2023 原文**

有一处**把 Prototype 列为独立类别**:

> "e) **Prototypes**: Prototypes are either acquired or fabricated. Often, they are used in early stages to..."

在 15288 视角下,**Prototype 本身就是一类 System Element / Work Product** — 不是"过程",而是一类被承认的**对象**。

#### 三、结论

**没有任何一个标准把"原型设计"规定为一个独立的必经流程。** 但:

```
     身份 1:  生命周期模型的实现手段
              ("iterative / prototyping 模型")
                         │
                         ▼
     身份 2:  多个过程的技术手段
              Requirements / Design / System Analysis /
              Integration / Verification / Validation
                         │
                         ▼
     身份 3:  一种 Work Product / System Element
              (15288 把 Prototype 列为一类可获取或制造的对象)
```

要"有原型设计"该套用哪里:

| 想把原型做成什么 | 挂到哪 |
|---|---|
| 用原型**澄清需求** | 12207 Stakeholder Needs/Requirements Definition 的技术手段 |
| 用原型**探索设计** | 12207 Design Definition 的工件,15288 System Analysis 的方法 |
| 用原型**验证可行性** | 12207/15288 Verification 的对象 |
| 用原型**让用户试用** | 12207/15288 Validation 的对象 |
| 采用**原型驱动开发** | 选 iterative Life Cycle Model |
| 把原型当作**可交付资产** | 15288 的 Prototype System Element |

如果在 Quantalithos 的流程里显式放一个"原型设计"阶段,**不违反任何标准** — 因为标准给的是过程和目的,不规定手段,而原型在 12207/15288 被列为**合法且推荐的多用途手段**。

#### 一、先把"最终目的"精确地说出来

从 `基础想法.md`、`user_aris.md` 和反复强调的叙事里,最终目的是:

> **让用户以"管理者"而非"开发者"的身份,通过创建机器人群聊委派任务,由一群有身份、有分工的 AI 员工在可观察的协作过程中自主完成软件项目,关键决策由用户把关,最终产出可运行的交付物。**

这句话埋了六个**不可妥协的定位**:

1. **用户是管理者** — 不写代码、不画图,只给意图和批准决策
2. **员工是有身份的个体** — 名字、职业、能力、过往经验、可被"登录"
3. **协作载体是对话** — 不是工单流,是群聊 + 频道 + 私聊
4. **工作对象是软件项目** — 不是 Q&A、不是单次请求
5. **关键节点强制人类** — 门禁不是断点,是治理的本体
6. **过程可观察** — 任何时候打开 app 都能看见大家在干嘛

#### 二、这六个定位带来的独特建模挑战(标准都没答)

| 缺口 | 传统标准假设 | Quantalithos 真相 |

| 员工身份 | Performer/Role 是抽象槽位 | Member 是有**个体性 + 记忆 + 职业生涯**的实体 |
| 协作媒介 | 沟通是非功能性假设,不建模 | **Conversation 是一等聚合根** |
| 用户位置 | User 是 Actor 或 Customer,触发流程 | User 是**裁决者 + 见证者**,持续在回路里 |
| 工作定义 | Process 是预先建模好的 BPMN 图 | **Process 从对话中涌现 + 选模板 + 被裁剪** |

#### 四、建模的底层原则(从最终目的反推)

**原则 A · 六域分离,不互相入侵**
"谁、说什么、做什么、怎么做、谁说了算、产出什么"这六件事必须分成六个独立域,跨域只通过**领域事件**连接。

**原则 B · Definition vs Use 严格分离**(借自 SPEM)
所有可复用的方法知识和具体项目的使用必须分为两个对象,不是一个。

**原则 C · Conversation 是一等聚合根,不是载体**
对话必须像 Git 仓库一样被独立建模:标识、权限、历史、搜索、事件流。决策、讨论、门禁都以 Conversation Turn 的形式被引用和追溯。

**原则 D · 员工是持久性实体,不是任务执行器**
Member 有自己的生命周期(hire/active/paused/retired),有 Memory、Capability、Availability、Career 维度。分给 Member 的不是"任务",是 **Work Assignment**,完成后写入 Career History。

**原则 E · 门禁(Gate)是一等流程控制对象**
不是 BPMN UserTask 的特化,是自己的一类对象:发起方、决策方、候选选项、证据要求、超时策略、决策后果。

**原则 F · 过程以模板 + 裁剪 + 实例三段式**(借自 29110 Profile + SPEM Method Plugin)
`ProcessTemplate → ProcessProfile(裁剪)→ ProcessInstance(本项目)`。

**原则 G · Artifact 是带状态的资产**(借自 29110 Work Product State)
initiated → reviewed → approved → baselined → published → archived。Prototype、Code、Doc、TestReport 都是 Artifact 的子类型。

**原则 H · 可观察性内置,不是外挂**(借自 OTel GenAI)
所有六个域的每一次状态变化都发出**领域事件**,Conversation 订阅相关事件并实时呈现。

#### 七、项目实际运行时六域如何协同(事件流)

```
 时刻 T0  用户在 chat 说"我想做一个博客系统"
  [对话域]  Conversation(group-1) 增加 Turn(user-message)
  [对话域]  事件:UserIntentReceived
            │
            ▼
 时刻 T1  Assistant Member 响应
  [身份域]  Member(Assistant) 被激活(Available → Working)
  [对话域]  Turn(agent-message) 追加
  [工作域]  事件:ProjectCreationRequested → 新建 Project(draft)
            │
            ▼
 时刻 T2  选择流程模板
  [过程域]  从 MethodLibrary 取 ProcessTemplate("Small Web App")
  [过程域]  创建 ProcessProfile (根据项目特征裁剪)
  [过程域]  实例化 ProcessInstance,Stage=Concept
  [过程域]  发布 StageEntered(Concept)
            │
            ▼
 时刻 T3  组队
  [身份域]  查询符合 Profile 所需 Role 的 Member 池
  [身份域]  为项目分配 RoleAssignment(TL, BE-Dev, QA, UX)
  [对话域]  把被分配的 Member 自动加入 Conversation(group-1)
  [对话域]  每个 Member 发出"自我介绍"Turn
            │
            ▼
 时刻 T4  需求理解
  [工作域]  ProcessInstance 推 Activity="需求收集"
  [工作域]  创建 WorkItem("Gather Requirements")
  [对话域]  Turn 增加(TL 在群聊提问)
  [制品域]  新 Artifact("PRD-draft", state=initiated)
  [治理域]  Gate("用户确认需求")被创建,等待 user Approval
            │
            ▼
 时刻 T4(续)
  [过程域]  ProcessInstance 推进 Stage: Concept → Definition
  [过程域]  下一批 Activity 被派发(Design / Task-Breakdown)
  [工作域]  WorkItem 创建
  [制品域]  新 Artifact 初始化
            │
            ▼
 时刻 T5  开发
  [工作域]  Stage=Development,Backlog 里的 WorkItem 被并行派发
  [身份域]  BE-Dev / FE-Dev / QA / DevOps 多 Member 并行 working
  [对话域]  每个 WorkItem 有独立 Thread + 群聊主干同步状态
  [制品域]  Code / Test / Design 原子级产出,带血缘链接回 PRD
            │
            ▼
 时刻 T6  验收
  [治理域]  "验收门禁"触发 → 用户验收
  [制品域]  Release Artifact baselined
  [过程域]  Stage=Release → Operation
  [评估横切] Metrics: Lead Time/Throughput/Quality 写入度量
  [评估横切] 项目结束 → Retrospective → Improvement Action
```

**核心原则**:没有任何一个域"指挥"其它五个域。每个域只根据自己收到的**领域事件**推进状态,并把自己的状态变化广播出去。

#### 九、推荐的三个方案

| 方案 | 动作 | 代价 | 收益 |
|---|---|---|---|
| **A · 全量采纳** | 推倒重写时按六域建模,flow/platform/chat 重新分拆 | 最大 — 需重新切分子项目 | 和最终目的最贴合,标准对齐最彻底 |

#### 三、关键决策说明

**L0 拆成 3 个而不是 1 个**
- core:编译期 proto + model,稳定
- bus:运行时组件,多后端,迭代更快
- sdk:多语言门面,发布节奏不同

这是 "schema vs runtime vs client" 三层分离。

**六域一域一仓**
每个域有独立的数据模型、事件契约、演进节奏、scale 属性、团队主人。合并会回到当前 platform 作为上帝对象的问题。

**Member 运行层拆 5 个**
- member:网络门面,Rust/Go,稳定
- runtime:Python,迭代频繁
- tools:独立模块 monorepo
- member-images:CI 专用
- member-service:容器编排,Rust

**method-library 单独一仓**
SPEM 核心教诲:方法知识和流程骨架分离。主要内容是结构化数据(YAML/Markdown),更新频率是**产品运营节奏**,非工程节奏。运营团队、方法论专家能单独贡献。

**capability-hub 单独一仓**
MCP Registry、A2A External Agent、第三方集成是**插件池**,必须和核心引擎解耦,才能支持社区贡献 MCP 工具、新增集成不触发核心发布、白名单策略独立演进。

**bridges 是 mono-repo**
四个桥接器逻辑相似(都是消息转发 + 身份映射),都用 Lua/Python 写,共用 bridge-sdk。合 mono-repo 按子目录拆更干净。

**保留 meta 仓**
多仓项目痛点是"新人不知道从哪开始看"。meta 仓:README/愿景/路线图、repo 索引、跨仓脚本、ADR 决策记录。**不放任何代码**。

```

           ├──────────┼──────────┼──────────┼──────────┼──────────┤

           └──────────┴──────────┴──────────┴──────────┴──────────┘

```

**关键发现:**
- **Chat 和 Console 互补不重叠** — Chat 是"协作产品视角",Console 是"管理治理视角"
- **Runner 只消费 artifact 域** — 它只管跑 AI 产出的应用,不管过程
- **Sync 只碰 work 和 artifact** — 它同步工作区文件
- **Bridges 只转 conversation** — 它是 Chat 的"外挂入口"
- **SDK 是所有客户端的统一接入层** — 任何前端都通过 SDK 连 Server

### 四、三条必须强制执行的"横切规范红线"

最后留三条横贯所有子项目、不讨论裁剪的红线:

**红线 1 — 可审计性(来自 ISO 42001 + 27001 + 9001)**
```
任何影响系统状态的写操作必须产生不可变审计事件。
事件包含:actor · action · target · before/after · trace_id · timestamp。
审计日志必须 append-only 并有防篡改哈希链。
```

**红线 2 — 可追溯性(来自 12207 CM + OTel + W3C Trace Context)**
```
任何跨服务调用必须携带 trace-id 和 span-id。
任何 Artifact 变化必须能追溯到:
 · 触发的 Conversation Turn
 · 负责的 Member + Role
 · 执行的 WorkItem
 · 归属的 ProcessInstance
"无法追溯"等同于"事件没发生过"。
```

**红线 3 — 可裁剪性(来自 SPEM Method Plugin + 29110 Profile + 12207 Tailoring)**
```
任何"过程/规则/门禁"的实现都必须能被声明为 Profile 的一部分进行裁剪。
不允许在代码里硬编码"阶段顺序"、"必需角色"、"必需制品"。
这些必须是 method-library 里的可配置资产。
```

这三条不是"加分项",是"符合 A 方案必须上的地基"。任何违反这三条的实现都应该在评审阶段被打回。

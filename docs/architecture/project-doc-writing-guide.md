# 项目文档写作指南

> 基于 teleop-quic-transformer 项目的设计流程总结，适用于新项目的文档编写。

---

## 核心原则：三层设计文档的抽象级别不同

概览、概要设计、详细设计的本质区别是**抽象级别**，而非内容类型。同一个项目特性，在三份文档中的表达方式完全不同。

---

## 一、总览（OVERVIEW）— 写什么、写到什么程度

### 目标读者

初次接触项目的人。

### 核心问题

是什么、怎么用。

### 应有章节

| 章节 | 写什么 |
|------|--------|
| **项目定位** | 一句话定义 + 核心职能 + 核心特性列表 + 适用/不适用场景 |
| **端到端数据流** | 全链路 ASCII 图 + 单会话时序图，让人 30 秒看懂数据怎么流 |
| **技术选型** | 核心依赖表格（名称→用途），不展开对比（那是概要设计的事） |
| **快速开始** | 编译→配置→运行→验证的完整可执行步骤 |
| **目录结构** | 带注释的文件树 + 源码统计 |
| **模块速览** | 每个模块一张表格（文件→职责），列出关键类型名和生命周期 API |
| **配置要点** | 核心配置字段速查表，细节指向 CONFIG.md |
| **读码建议路径** | 按角色/按目标给出阅读顺序（如 1h/4h/8h） |
| **文档导航** | 所有文档的索引表（文档名→内容→适合场景） |

### 不要写的

| 不要写 | 原因 |
|--------|------|
| 结构体字段 | 读者此时只需要知道"有什么模块"，不需要知道内部细节 |
| API 签名 | 概览阶段无法据此修改代码 |
| 设计决策的理由 | 这是概要设计的事 |
| 状态机转换细节 | 概览只需提"有状态机"并链接到概要设计 |
| 配置字段的完整列表 | 只列核心字段，完整列表指向 CONFIG.md |

### 各要素写到什么程度

| 内容 | 写到什么程度 | 示例 |
|------|-------------|------|
| 项目定义 | **一句话 + 3-5 个核心特性** | "用户态 TCP/QUIC 多路径转发器"，列出5个特性 |
| 数据流 | **ASCII 时序图，只画主干** | 只画 TCP→QUIC→TCP 的骨架，不画背压/pending 分支 |
| 模块速览 | **每个模块一句话 + 关键类型名** | "session 层：会话生命周期管理，关键类型 session_t" |
| 目录结构 | **带一行注释的文件树** | 每个文件一行说明 |
| 快速开始 | **可复制粘贴执行的完整步骤** | apt install → cmake → make → run → verify |
| 文档导航 | **索引表** | 文档名 → 一句话内容 → 适合场景 |

### 写法要点

1. **面向"初次接触"的读者**，不假设任何上下文
2. **ASCII 图优先**：数据流图、端口映射图用纯文本，比截图更可维护
3. **模块速览只给表格**，不给内部实现细节，详细内容链接到 ARCHITECTURE.md
4. **重要概念区分要显式声明**：容易混淆的概念，用对比表格明确
5. **快速开始必须可执行**：从依赖安装到验证命令，复制粘贴就能跑

### 完成标准

读完总览，读者能回答"这个项目干什么的、我该不该用、怎么跑起来"。

## 二、概要设计（ARCHITECTURE）— 写什么、写到什么程度

### 目标读者

需要理解整体设计的开发者。

### 核心问题

为什么这样设计、模块间如何协作。

### 应有章节

| 章节 | 写什么 |
|------|--------|
| **设计目标与边界** | 目标 + 非目标 + 系统边界（本项目在整体架构中的位置用 ASCII 框图） |
| **连接模型设计** | 当前模型 + 选择理由 + 备选模型 + 为什么暂不实现 |
| **技术选型与对比** | 与备选方案的逐维度对比表 + 核心依赖选型理由 |
| **分层架构** | 层次图 + 分层约束规则表（谁能调谁、谁不能调谁） |
| **模块依赖关系** | 依赖链 + 依赖方向 + 头文件 include 关系 |
| **线程模型** | 主线程/辅助线程的职责 + 并发边界与数据共享方式 |
| **数据流详解** | 每个端（Client/Server）的完整流程时序 + 特殊机制说明 |
| **流控/背压架构** | 设计目标 + 缓冲区设计 + 触发/恢复机制 + 信号传播路径图 |
| **特殊机制（项目特化）** | 如多路径、网口状态机等，按需展开 |
| **可观测性架构** | 每个子系统的架构图 + 特性表 |
| **资源管理与生命周期** | 阶段模型 + 信号处理 + 内存管理策略表 |
| **错误处理架构** | 错误分类表 + 恢复策略 + 错误码约定 |
| **安全边界** | 加密 + 无回退 + 输入校验 |
| **性能设计考量** | 关键性能选择理由 + 权衡 |
| **关键设计决策记录** | 每个决策用"为什么选 X 而不是 Y"格式 |
| **外部系统接口** | FFI 函数表 + 回调注册表 + 句柄类型使用表 |

### 关于数据结构

**不写结构体的具体字段，但写结构体之间的持有关系和协作方式。**

```
❌ 不要写：
session_t 包含：
  - tcp_to_quic_pending: session_pending_buf_t
  - quic_to_tcp_pending: session_pending_buf_t
  - pause_tcp_read: bool
  - ...

✅ 要写：
session_t 持有 3 个 pending buffer（tcp_to_quic / quic_to_tcp / quic_pre_tcp），
用于背压流控。触发/恢复机制如下...
```

概要设计关注的是**结构体之间的关系和协作方式**，而非字段清单。

### 关于代码

**不写实现代码，但写关键伪代码片段说明选择逻辑。**

```
❌ 不要写：
static int session_pending_append_tcp_to_quic(session_t *s,
    const uint8_t *data, size_t len) {
    if (s->buf.tcp_to_quic.len + len > s->buf.tcp_to_quic.size) {
        size_t new_size = s->buf.tcp_to_quic.size * 2;
        ...
    }
    memcpy(s->buf.tcp_to_quic.data + s->buf.tcp_to_quic.len, data, len);
    ...
}

✅ 要写：
路径选择逻辑：
  1. 优先根据 TQUIC 指定的 src_addr 查找对应路径
  2. 若未找到或路径不可用，fallback 到第一个可用路径
  选择条件：path->active == true && path->tx_enabled == true
```

概要设计的代码片段是为了**说明设计意图和决策**，不是为了可编译。

### 关于状态机

**要写，但要写"为什么"而不只是"是什么"。**

| 写法 | 示例 |
|------|------|
| 状态列表 + 转换关系 ✅ | INIT → STABILIZING → READY → DRAINING |
| 转换条件 ✅ | present && link_up && has_addr && route_ready → STABILIZING |
| 设计动机 ✅ | "为什么需要 settle 窗口：车载 4G/5G 链路抖动，300ms 观测期避免频繁上线" |
| 状态枚举值 ❌ | 不需要写 `NETIF_STATE_READY = 5` 这种具体数值 |

### 关于时序

**要写带时间节点的完整时序，这是概要设计最有价值的部分之一。**

```
✅ 概要设计的时序：
T0:     内核检测到链路 UP
T0+1ms: NETLINK 事件到达
T0+3ms: converger 处理，进入 STABILIZING
T0+306ms: settle 定时器到期，激活路径，创建 UDP socket
T0+310ms: QUIC 路径添加，发起 PATH_CHALLENGE
T0+330ms: 收到 PATH_RESPONSE，路径可用
总延迟: ~330ms

关键：不是写"接口上线后路径可用"，而是写清楚每一步的耗时和触发条件。
```

### 项目特化内容怎么处理

像"quic_pre_tcp 缓冲区"、"settle/drain 窗口"这些是项目特有的机制，处理原则：

1. **总览中**：不提。或者只用一句话带过（"支持背压流控"），链接到概要设计
2. **概要设计中**：**重点写**。这是设计的核心价值——说明为什么需要这个机制、它怎么工作、时间窗口怎么定
3. **详细设计中**：写字段表、API、调用链，让开发者可以正确实现

**核心判断标准**：这个内容是否帮助读者做决策？

### 各要素的深度要求

| 要素 | 深度 | 说明 |
|------|------|------|
| 分层架构 | 层次图 + 分层约束 | 谁能调谁、谁不能调谁 |
| 模块依赖 | 依赖链 + 方向 + 头文件关系 | 画出 include 链 |
| 线程模型 | 每个线程的职责 + 共享数据表 | 哪些数据无锁、哪些需要同步 |
| 数据流 | 完整时序（含时间节点） | 关键路径必须有时间估计 |
| 状态机 | 状态图 + 转换条件 + 设计动机 | 每个窗口参数要说为什么是这个值 |
| 背压/流控 | 触发→传播→恢复的完整路径 | 画出信号传播方向 |
| 设计决策 | 决策 + 理由 + 备选方案 + 为什么不选 | 格式统一 |
| 外部接口 | FFI 函数表 + 回调表 | 接口契约 |
| 错误处理 | 分类表 + 恢复策略 | 哪类错误怎么兜底 |
| 性能考量 | 选择理由 + 权衡 | 如"单线程 vs 多线程"的取舍 |

### 写法要点

1. **每个设计决策必须有理由**，最好同时写出备选方案和为什么不选
2. **分层架构必须有约束规则**：谁可以调谁、谁不能调谁，用表格明确
3. **数据流要用完整时序**：带时间节点，比 UML 时序图更可读
4. **状态机必须画出来**：状态和转换条件
5. **关键窗口参数要解释设计动机**：不说"等 300ms"，而说"为什么是 300ms、如果不等会怎样"
6. **背压机制要画信号传播路径**：从快端到慢端，pause/resume 的传播方向
7. **外部接口用表格罗列**：FFI 函数、回调注册、句柄类型——这些是跨模块/跨库的契约

### 完成标准

读完概要设计，读者能回答"为什么这样设计、模块间怎么协作、关键机制怎么工作"。

## 三、详细设计（DETAILED_DESIGN）— 写什么、写到什么程度

### 目标读者

要改代码的人。

### 核心问题

结构体有哪些字段、API 签名是什么、状态机怎么转、调用链怎么走。

### 组织方式

**按模块组织**，每个模块独立完整。读某个模块的详细设计时，不需要频繁跳转到其他模块。

### 每个模块应包含

| 模块内章节 | 写什么 |
|-----------|--------|
| **源文件/头文件清单** | 该模块对应的所有 .c/.h |
| **总体原则** | 模块边界、命名规范、错误处理约定、内存所有权 |
| **结构体字段表** | 每个结构体的每个字段：字段名→类型→默认值→说明 |
| **API 参考** | 每个公共函数的签名 + 行为描述（不是实现体） |
| **内部回调表** | 回调名→触发时机→行为 |
| **状态机转换表** | 当前状态→事件→下一状态→动作 |
| **内部实现要点** | 关键算法、边界条件、为什么这样实现 |
| **跨模块调用链分析** | 端到端调用链（从入口函数到最终动作） |

### 关于数据结构

**必须写完整字段表，与头文件一一对应。**

```
✅ 详细设计的结构体写法：

#### session_t

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| id | uint64_t | 0 | 会话唯一标识 |
| state | session_state_t | SESSION_STATE_INIT | 当前状态 |
| tcp.handle | uv_tcp_t | - | TCP 连接句柄 |
| tcp.side | tcp_side_t | TCP_SIDE_UNINITIALIZED | TCP 侧状态 |
| buf.tcp_to_quic | session_pending_buf_t | {0} | TCP→QUIC pending |
| buf.quic_to_tcp | session_pending_buf_t | {0} | QUIC→TCP pending |
| buf.quic_pre_tcp | session_pending_buf_t | {0} | Server 侧早期数据缓存 |
| quic.conn | quic_conn_t* | NULL | QUIC 连接句柄 |
| quic.stream_id | uint64_t | 0 | 双向 stream ID |
| bp.tcp_read_paused | bool | false | TCP 读取是否暂停 |
| bp.quic_read_blocked | bool | false | QUIC 读取是否阻塞 |
```

**标准**：拿到这份字段表，可以直接写出头文件定义，不需要再去看代码。

### 关于代码 — 两种写法，用于不同场景

详细设计中的代码分为**两类**，写法和目的完全不同：

#### 类型 1：API 参考 — 写签名 + 行为描述，不写实现体

用于模块的**所有公共函数**，目的是定义接口契约。

```c
✅ API 参考写法：

| 函数 | 返回 | 说明 |
|------|------|------|
| `quic_transport_init(t, loop, role, cert, key, mgr, ctx, opts)` | `int` | 创建 TQUIC endpoint、TLS config |
| `quic_transport_connect(t, addr, len, sni, out)` | `int` | 发起 QUIC 连接（client） |
| `quic_transport_start(t)` | `int` | 启动 poll、timer |
| `quic_transport_stop(t)` | `void` | 停止 poll、timer |
```

```c
✅ 对于行为复杂的函数，写详细的行为描述：

/**
 * session_close - 统一关闭入口
 *
 * 行为：
 *   1. 如果 state >= CLOSING，直接返回（幂等）
 *   2. 状态转换 → SESSION_STATE_CLOSING
 *   3. 如果 TCP 已连接 → uv_read_stop + uv_close(tcp)
 *   4. 如果 QUIC 已连接 → quic_conn_close()
 *   5. 处理未初始化的侧：直接标记 CLOSED
 *
 * 返回：void（幂等，多次调用安全）
 * 线程安全：否（仅主线程调用）
 */
void session_close(session_t *session);
```

#### 类型 2：关键实现 — 贴完整源码 + 源码位置 + 设计理由

用于模块中**最核心、最易出错、最需要说理**的函数。这是详细设计区别于 API 文档的关键所在。

**选哪些函数贴完整源码？** 不是所有函数都贴，只贴满足以下条件之一的：

| 条件 | 示例 |
|------|------|
| 包含非显然的状态转换逻辑 | `session_close`：双侧异步关闭、HALF_CLOSED 中间态 |
| 包含与第三方库的交互契约 | `on_conn_created`：TQUIC 回调中 Client/Server 侧的不同行为 |
| 包含防抖/去抖/滞回等非显然算法 | `session_update_quic_read_backpressure_with_watermarks`：高低水线滞回 |
| 包含时间窗口相关的竞争处理 | `netif_converger_apply_event`：settle/drain 窗口 |
| 隐含约束不写清楚会导致 UAF/死锁 | `session_finalize_if_ready`：必须等双侧 CLOSED 才能 free |
| 路径选择/fallback 逻辑 | `on_packets_send`：按 src_addr 匹配路径 + fallback |
| 需要解释"为什么要这样做" | `on_keepalive_cb`：ping 后还要 wantwrite 的原因 |

```

**关键实现的实际写法示例（来自原项目）：**

示例 1：说理型 — 解释非显然的约束

```c
#### `session_finalize_if_ready` — 双侧 CLOSED 后执行最终销毁

> 源文件：`src/session/session_lifecycle.c:124-140`

---

**为什么必须等 TCP 和 QUIC 双侧都 CLOSED 后才能 destroy session？**

这是由 libuv 和 TQUIC 的异步关闭语义决定的：

约束 1：libuv uv_handle_t 生命周期
- uv_close() 之后不能立即 free，必须等 close callback
- 若提前 free(session)，libuv 访问已释放内存（UAF）

约束 2：TQUIC 连接的异步排空
- quic_conn_close() 后 TQUIC 可能继续触发 on_packets_send 回调
- on_packets_send 中会通过 quic_conn_context(conn) 取回 session 指针
- 若提前 free(session)，野指针访问崩溃

约束 3：半关闭（HALF_CLOSED）的语义
- TCP FIN 表示"不再发送"，但对端可能还有数据
- 必须继续处理 QUIC→TCP 方向，不能直接关闭

双侧关闭条件：
  state == SESSION_STATE_CLOSING
  && tcp.side == TCP_SIDE_CLOSED
  && quic.side == QUIC_SIDE_CLOSED

---

[然后贴完整源码]
```

示例 2：说理型 — 解释算法选择

```c
#### `session_update_quic_read_backpressure_with_watermarks` — 水线背压判定

> 源文件：`src/session/session_backpressure.c:154-183`

---

**为什么使用高/低双水位（滞回 hysteresis），而不是单阈值？**

若只使用单阈值，在弱网下会出现高频振荡：
- pending 从 128001 降到 127999 → 恢复 QUIC 读
- QUIC 读入 1KB → pending 升到 128999 → 阻塞 QUIC 读
- quic_stream_wantread 每毫秒可能调用数十次

高/低双水位解决方案：
- high = pending_limit / 2（128KB）：超过才触发阻塞
- low = high / 2（64KB）：降至才触发恢复
- 区间 [low, high] 为滞回区间，保持当前状态不变

效果：大幅减少开关频率，保证流量平滑性。

### 关于状态机

**写完整转换表，精确到每个转换条件。**

| ESTABLISHED | TCP EOF / QUIC close / error | CLOSING | 停止读写 |

| * | state >= CLOSING | (不变) | 幂等返回 |

### 关于校验行为的写法

**必须区分硬校验与软归一化：**

- **硬校验**：失败返回错误，程序退出（如 `local.port=0`、server 缺 TLS）
- **软归一化**：非法值回退安全默认值并打印 `LOG_WARN`（如 CC algorithm 非法 → 回退 `bbr`）

每个字段都要标注属于哪种。如果是软归一化，要写明回退到什么值。

| `pending_max_kB = 0` | 回退 256 kB |

### 关于常见错误的写法

每类错误必须包含三要素：**错误写法/场景 → 实际日志 → 修复方法**

```markdown
### interfaces 写成 IP 地址

```json
"interfaces": ["10.10.0.2"]
```

错误：`interfaces parse failed, reason: ip literal is not allowed, value: 10.10.0.2`

修复：改为网卡名 `["eth0"]`。


### 写法要点

1. **字段参考按 JSON 层级组织**，不要平铺，保持与配置文件结构一致
2. **每个字段必须写明默认值**，这是读者最常查阅的信息
3. **单位转换规则必须显式声明**：如 `_kB` 表示乘以 1024 转字节
4. **配置示例必须完整可运行**：不是片段，而是可以直接复制使用的完整 JSON
5. **校验行为必须区分硬/软**：硬校验退出，软归一化回退
6. **依赖关系必须穷举**：隐式联动是配置出错的重灾区
7. **对应实现源文件要标注**：在文档开头注明对应的 .c 文件

### 关于每个问题的写法

**每个具体问题必须包含六要素：**

```markdown
### 3.1 QUIC 连接建立失败（-109、TLS、地址解析）

**现象**：`quic_transport_connect()` 失败，日志 `quic_endpoint_connect failed: -109`。

**可能原因**：server 未监听、TLS 配置错误、`remote.addr`/`interfaces` 无效、防火墙阻断 UDP。

**排查步骤**：
① `ss -ulnp | grep 4433` 确认 server 监听
② 检查 `tls.cert`/`tls.key` 路径
③ `tcpdump -i <iface> udp port 4433` 确认 UDP 可达
④ `ip addr show <接口名>` 确认 interfaces 有效

**解决方案**：修正 `remote.addr`、用网卡名配 `interfaces`、放行防火墙。

**相关代码**：`src/transport/transport_io.c`、`src/config/config_validator.c`

**日志示例**：
```
quic_endpoint_connect failed: -109
config validation failed, reason: server mode requires tls.cert and tls.key
```
```

**六要素的价值：**
- **现象**：让运维快速匹配当前问题
- **可能原因**：缩小排查范围
- **排查步骤**：有序执行，不是无头苍蝇
- **解决方案**：最终修复方法
- **相关代码**：需要深入时知道看哪里
- **日志示例**：可以 grep 搜索

### 关于症状归因速查表

这是故障排查最常用的入口，必须覆盖全面：

```markdown
| 症状 | 优先检查 | 常见根因 |
|------|----------|----------|
| 连接失败 -109 | remote、server、TLS | 网络不通、TLS 错误 |
| 空闲断开 | keepalive、idle_timeout | interval 过大或 0 |
| 内存上涨 | pending_max、背压 | 缓冲大、背压未触发 |
```

### 写法要点

1. **诊断流程不超过 5 步**：运维在紧急情况下需要快速指引
2. **每个问题必须有日志示例**：运维通过 grep 定位问题
3. **排查步骤必须有序编号**：①②③④，不是无序列表
4. **解决方案必须具体可执行**：不是"检查配置"，而是"设 `keepalive.interval_s: 20`"
5. **症状归因表必须覆盖所有已知问题**：这是值班时最常用的入口
6. **问题按域分组**：连接/性能/日志/内存/环境/稳定性/多路径/编译

### 完成标准

运维人员在凌晨收到告警，拿到故障排查指南可以独立定位和修复问题，不需要打电话叫醒开发者。

## 八、部署文档（DEPLOY）— 写什么、写到什么程度

### 目标读者

运维人员、部署工程师。

### 核心问题

怎么装、怎么启停、怎么升级、怎么回滚、怎么扩缩容。

### 应有章节

| 章节 | 写什么 |
|------|--------|
| **部署架构** | 集群拓扑 ASCII 图 + 节点角色 + 各角色的资源要求（CPU/内存/磁盘/网络） |
| **环境要求** | 操作系统版本、内核版本、依赖库列表、端口清单、磁盘空间、网络要求 |
| **安装步骤** | 从零部署的完整步骤（包安装/二进制部署/容器部署），每步可复制执行 |
| **配置文件管理** | 配置文件路径 + 配置文件模板 + 多环境差异说明（dev/staging/prod） |
| **启停与运维命令** | 启动/停止/重启/状态查看/健康检查的完整命令 + 参数说明 |
| **升级流程** | 升级前检查 → 升级步骤 → 升级后验证，支持灰度和全量两种模式 |
| **回滚方案** | 回滚触发条件 + 回滚步骤 + 回滚命令 + 回滚后验证 |
| **数据与存储** | 数据目录 + 日志目录 + 数据备份与清理策略 + 磁盘满的应急处理 |
| **监控与告警** | 关键指标列表 + 告警阈值 + 告警通知方式 + 仪表盘配置 |
| **网络与防火墙** | 入站/出站端口表 + 防火墙规则 + 安全组配置 + TLS 证书管理 |
| **扩缩容** | 扩容步骤 + 缩容步骤 + 容量评估参考指标 |
| **常见部署问题** | 安装失败/启动失败/端口冲突/证书错误等常见问题的排查方法 |

### 关于安装步骤的写法

**必须完整可执行，区分不同部署方式：**

```markdown
### 3.1 二进制部署

#### 3.1.1 依赖安装
```bash
sudo apt-get update
sudo apt-get install -y libuv1-dev libssl-dev
```

#### 3.1.2 编译
```bash
git clone <repo_url>
cd <project>
mkdir build && cd build
cmake -DCMAKE_BUILD_TYPE=Release ..
make -j$(nproc)
```

#### 3.1.3 安装
```bash
sudo make install
```

#### 3.1.4 验证
```bash
<binary> --version
<binary> --help
```
```

### 关于升级流程的写法

**分灰度和全量两种模式，每步有验证：**

```markdown
### 6.1 灰度升级

#### 步骤 1：升级前检查
- [ ] 确认新版本二进制已准备
- [ ] 确认配置文件兼容（对照 CONFIG.md 中的变更）
- [ ] 确认回滚二进制已备份

#### 步骤 2：灰度节点升级
```bash
# 停止灰度节点
sudo systemctl stop <service>
# 替换二进制
sudo cp <new_binary> /usr/local/bin/<binary>
# 启动
sudo systemctl start <service>
```

#### 步骤 3：灰度验证（观察 15 分钟）
- [ ] 进程存活：`systemctl status <service>`
- [ ] 连接正常：`ss -tlnp | grep <port>`
- [ ] 日志无异常：`journalctl -u <service> --since "15 min ago" | grep -i error`
- [ ] 业务指标正常（对照监控仪表盘）

#### 步骤 4：全量升级
逐台重复步骤 2-3，每台间隔 5 分钟。
```

### 关于回滚方案的写法

**必须包含触发条件、步骤和验证：**

```markdown
### 7.1 回滚触发条件

| 条件 | 等级 |
|------|------|
| 进程启动失败 | S 级（立即回滚） |
| 核心功能不可用 | S 级（立即回滚） |
| 性能下降 > 30% | A 级（评估后决定） |
| 非核心功能异常 | B 级（可先修复） |

### 7.2 回滚步骤

```bash
# 1. 停止当前版本
sudo systemctl stop <service>

# 2. 恢复旧版本二进制
sudo cp /opt/backup/<binary>.<old_version> /usr/local/bin/<binary>

# 3. 恢复旧版本配置（如需）
sudo cp /opt/backup/<config>.<old_version> /etc/<project>/<config>

# 4. 启动
sudo systemctl start <service>

# 5. 验证
sudo systemctl status <service>
ss -tlnp | grep <port>
```

### 7.3 回滚后验证
- [ ] 进程正常运行
- [ ] 连接恢复正常
- [ ] 业务指标回到基线
```

### 关于监控与告警的写法

**列出关键指标和告警阈值，运维可以直接配置：**

```markdown
| 指标 | 采集方式 | 告警阈值 | 说明 |
|------|----------|----------|------|
| 进程存活 | 进程监控 | 进程不存在 | S 级 |
| 连接数 | 指标接口 / ss | > 80% 最大连接数 | A 级 |
| 内存使用 | /proc/pid/status | > 80% 配置上限 | A 级 |
| CPU 使用 | top / 指标接口 | > 90% 持续 5 分钟 | B 级 |
| 会话断开率 | 日志统计 | > 5%/分钟 | A 级 |
```

### 关于网络与防火墙的写法

**必须列出入站/出站端口，运维可以直接配置防火墙：**

```markdown
| 方向 | 端口 | 协议 | 用途 | 来源/目标 |
|------|------|------|------|-----------|
| 入站 | 40001 | TCP | 本地 TCP 监听 | 127.0.0.1 |
| 入站 | 4433 | UDP | QUIC 监听 | 对端 IP |
| 出站 | 4433 | UDP | QUIC 连接 | 对端 IP |
```

### 写法要点

1. **安装步骤必须可复制粘贴执行**：从依赖到验证，一步不缺
2. **区分部署方式**：二进制/容器/包管理，按项目实际提供
3. **升级必须支持灰度**：先一台验证，再逐步全量
4. **回滚必须可执行**：触发条件 + 回滚命令 + 验证步骤
5. **端口和防火墙必须列表**：运维配置防火墙的直接依据
6. **监控指标必须给阈值**：不是"关注内存"，而是"内存 > 80% 告警"
7. **多环境差异必须显式声明**：dev/staging/prod 的配置差异用表格列出
8. **数据目录必须写清理策略**：日志轮转、临时文件清理、磁盘满的应急

### 完成标准

运维人员拿到部署文档，可以从零安装、正确配置、顺利升级、安全回滚，不需要开发者现场支持。

## 九、文档体系全景图

### 完整文档清单与职责

| 文档 | 核心问题 | 目标读者 | 必要性 |
|------|---------|---------|--------|
| **OVERVIEW.md** | 是什么、怎么用 | 初次接触项目的人 | 必须 |
| **ARCHITECTURE.md** | 为什么这样设计 | 需要理解设计的人 | 必须 |
| **DETAILED_DESIGN.md** | 具体怎么实现 | 要改代码的人 | 必须 |
| **CONFIG.md** | 每个配置项怎么配 | 运维、部署 | 必须 |
| **IMPLEMENTATION_PLAN.md** | 做到哪了、还差什么 | 项目负责人、新加入者 | 必须 |
| **TROUBLESHOOTING.md** | 出了问题怎么查 | 运维、值班开发者 | 必须 |
| **DEPLOY.md** | 怎么装、怎么升级 | 运维、部署工程师 | 必须 |

### 文档间链接关系

```
OVERVIEW ──→ ARCHITECTURE ──→ DETAILED_DESIGN
 (导航)       (设计决策)        (实现细节)
   │              │                  │
   ├── CONFIG     └── 专项文档       └── 调用链分析
   │  (配置参考)     (按需)
   │
   ├── IMPLEMENTATION_PLAN
   │  (进度→计划)
   │
   ├── TROUBLESHOOTING
   │  (故障→排查)
   │
   └── DEPLOY
      (部署→升级→回滚)
```

### 核心原则

每层文档只做自己的事，通过链接引用其他文档，不重复内容：
- **OVERVIEW 不写设计理由**
- **ARCHITECTURE 不写字段细节**
- **DETAILED_DESIGN 不写架构概述**
- **CONFIG 不写实现代码**
- **TROUBLESHOOTING 不写设计动机**
- **DEPLOY 不写设计决策**

### 新增功能/模块时的文档更新清单

- [ ] 在 OVERVIEW.md 中更新导航索引和模块速览
- [ ] 在 ARCHITECTURE.md 中补充模块位置与依赖
- [ ] 在 DETAILED_DESIGN.md 中补充结构体与关键函数
- [ ] 若涉及配置，更新 CONFIG.md

- [ ] 更新 IMPLEMENTATION_PLAN.md 中的功能清单和 TODO

## 十、通用写作要求

### 关于图表

- 优先使用 ASCII 图（数据流、架构层次、时序），可维护性优于截图
- 如果需要复杂图，使用 drawio 格式，导出 PNG 嵌入文档，源文件同目录存放
- 每张图下方注明编辑原图的路径

### 关于命名一致性

- 文档中的结构体名、函数名、枚举值必须与头文件一致
- 日志格式示例必须与代码实际输出一致
- 配置字段名必须与 JSON 配置文件一致

### 关于文档维护

每次代码结构或行为变更后，至少同步更新：

| 文档 | 更新内容 |
|------|----------|
| OVERVIEW.md | 导航、模块索引 |
| ARCHITECTURE.md | 层次关系、模块职责、设计决策 |
| DETAILED_DESIGN.md | 结构体字段、API 签名、调用链 |
| CONFIG.md | 字段、默认值、示例 |
| TROUBLESHOOTING.md | 新增故障场景、症状归因表 |
| DEPLOY.md | 端口、依赖、升级步骤 |
| IMPLEMENTATION_PLAN.md | 功能清单、TODO、验收口径 |

# 开发路线图与优先级

> 基于 AI 驱动研发协作平台的仓库拆分方案，制定开发步骤与优先级规划。

---

## 一、开发原则

1. **先跑通再迭代**：每个阶段都要有可运行的产物
2. **核心路径优先**：先打通用户 → Agent → 产物的主链路
3. **逐步增加复杂度**：从单角色到多角色，从线性流程到动态编排
4. **技术债务可控**：每个阶段结束后进行必要重构

## 三、Phase 1：核心交互原型（MVP）

**目标：** 用户能与 Agent 聊天，Agent 能按工作流模板执行任务，能在群聊中协作

**周期：** 2-3 周

### 优先级排序

| 优先级 | 任务 | 说明 | 仓库 |
|--------|------|------|------|
| P0 | 项目脚手架搭建 | 初始化仓库结构 | quantalithos-infra |
| P0 | 基础聊天界面 | 私聊 + 群聊 UI，消息收发 | quantalithos-chat |
| P0 | Agent 核心抽象 | Agent 基类、生命周期管理 | quantalithos-runtime |
| P0 | LLM 调用封装 | 统一调用 OpenAI/Claude/本地模型 | quantalithos-runtime |
| P0 | 消息存储 | 基础的聊天记录持久化 | quantalithos-infra |
| P0 | TaskProvider 抽象 | 统一接口 + LocalFileProvider 实现 | quantalithos-runtime |
| P1 | Assistant 角色 | 入口助手，加载 Agent 级工作流模板执行启动流程 | quantalithos-runtime |
| P1 | Tech Lead 角色 | 项目负责人，需求讨论 | quantalithos-runtime |
| P1 | Agent 级工作流引擎 | 加载工作流模板，按 step 驱动单 Agent 执行 | quantalithos-runtime |
| P1 | 共享规则加载 | schema + content 分离，三级覆盖 | quantalithos-runtime |
| P1 | 会话上下文管理 | 对话记忆（Phase 1 内存） | quantalithos-runtime |
| P1 | WebSocket 实时通信 | 消息实时推送 | quantalithos-chat |
| P2 | 用户认证（简化版） | 基础登录，暂不复杂化 | quantalithos-infra |

### Phase 1 验收标准

- [ ] 用户可以在私聊中与 Assistant 对话
- [ ] Assistant 能按工作流模板执行启动流程（7 步）
- [ ] Assistant 能创建群聊并拉入 Tech Lead
- [ ] 群聊中用户和 Agent 消息能实时同步
- [ ] Agent 能记住当前对话上下文
- [ ] 共享规则（communication.yaml）的 schema 校验生效
- [ ] TaskProvider 接口可用（LocalFileProvider）

### 技术选型

```
quantalithos-chat:     React + TypeScript + TailwindCSS
quantalithos-runtime:  Python (纯 Python，Phase 1 不引入 Rust)
                       Pydantic + FastAPI + asyncio + structlog
quantalithos-infra:    Docker Compose + PostgreSQL + Redis
```

## 四、Phase 2：流程引擎与多角色

**目标：** Pipeline Template 驱动阶段流转，Workflow Template 驱动 step 推进，多 Agent 协作可见，门禁可控制

**周期：** 4-5 周

### 优先级排序

| 优先级 | 任务 | 说明 | 仓库 |
|--------|------|------|------|
| P0 | Pipeline Template 加载 | 配置驱动的阶段定义，非硬编码枚举 | quantalithos-flow |
| P0 | 阶段状态机 | 阶段推进、回退、暂停（事件驱动） | quantalithos-flow |
| P0 | Workflow Template 加载 | 工作流模板解析、WorkflowInstance 管理 | quantalithos-flow |
| P0 | daemon 事件循环 | 接收 StepEvent，推进 step/阶段 | quantalithos-flow |
| P0 | StepAssignment 下发 | flow → runtime 的正式接口 | quantalithos-flow |
| P0 | 门禁控制器 | hard / soft / none，审批卡片 | quantalithos-flow |
| P0 | 任务状态机 | created → assigned → ... → completed | quantalithos-flow |
| P0 | PlatformAPIProvider | TaskProvider 的平台 API 实现 | quantalithos-runtime |
| P0 | Backend Dev 角色 | 后端开发 Agent | quantalithos-runtime |
| P0 | Tester 角色 | 测试工程师 Agent | quantalithos-runtime |
| P1 | Frontend Dev 角色 | 前端开发 Agent | quantalithos-runtime |
| P1 | 消息路由 | 参与度控制（mention_only / free / muted） | quantalithos-flow |
| P1 | 流程可视化（前端） | 阶段进度条、当前 step 展示 | quantalithos-chat |
| P1 | 门禁确认组件 | 用户点击确认/驳回 | quantalithos-chat |
| P1 | 并行任务调度 | 阶段 3 多任务并行 | quantalithos-flow |
| P2 | DevOps 角色 | 部署运维 Agent | quantalithos-runtime |
| P2 | 动态流程编排 | TL 提议 → flow 编译 | quantalithos-flow |
| P2 | 角色动态加载 | 按需实例化 Agent | quantalithos-runtime |

### Phase 2 验收标准

- [ ] 项目能按 Pipeline Template 定义的阶段推进
- [ ] 每个阶段内按 Workflow Template 驱动 step 执行
- [ ] daemon 能接收 StepEvent 并推进流程
- [ ] 用户门禁需要显式确认（hard gate）
- [ ] 多 Agent 能在群聊中协作讨论
- [ ] 阶段产物（如 PRD）能生成和展示
- [ ] 任务状态随 step 推进自动流转
- [ ] hotfix Pipeline Template 可用（3 阶段流程）

## 五、Phase 3：产物管理、网关与工作区同步

**目标：** 产物可存储、版本化、追溯；工作区可跨机器恢复；系统完整闭环

**周期：** 3-4 周

### 优先级排序

| 优先级 | 任务 | 说明 | 仓库 |
|--------|------|------|------|
| P0 | 产物存储服务 | CRUD + 元数据管理 | quantalithos-platform |
| P0 | 产物类型定义 | PRD、方案、代码、测试报告等 | quantalithos-platform |
| P0 | Git 集成 | 代码版本管理 | quantalithos-platform |
| P0 | API 网关基础 | 统一入口、路由 | quantalithos-gate |
| P0 | 用户认证完善 | SSO/OAuth、JWT | quantalithos-gate |
| P0 | 权限控制 | RBAC、项目级权限 | quantalithos-gate |
| P0 | quantalithos-sync CLI | manifest 解析、restore/push 基础功能 | quantalithos-sync |
| P0 | Git 同步模块 | 代码仓库的克隆、拉取、分支管理 | quantalithos-sync |
| P1 | 云端配置同步 | Agent 配置、角色定义的拉取与推送 | quantalithos-sync |
| P1 | 快照同步 | 项目快照的保存与恢复 | quantalithos-sync |
| P1 | daemon 集成 | 项目启动时 restore，变更时 push | quantalithos-sync |
| P1 | 产物搜索 | 全文搜索、标签过滤 | quantalithos-platform |
| P1 | 产物版本历史 | diff、回滚 | quantalithos-platform |
| P1 | WebSocket 网关 | 实时消息推送 | quantalithos-gate |
| P1 | 审计日志 | 操作记录追溯 | quantalithos-gate |
| P2 | 跨机器恢复 | 完整项目工作区的跨机器重建 | quantalithos-sync |
| P2 | 产物模板 | PRD 模板、方案模板 | quantalithos-platform |

### Phase 3 验收标准

- [ ] 所有阶段产物都能存储和检索
- [ ] 代码能关联 Git 仓库
- [ ] 用户权限正确控制（项目成员、角色权限）
- [ ] `quantalithos-sync restore` 能一键恢复项目工作区
- [ ] `quantalithos-sync push` 能推送本地变更到云端
- [ ] daemon 能在项目启动时自动调用 sync
- [ ] 完整的审计日志
- [ ] 系统完整闭环可用

## 六、Phase 4：扩展能力与企业级特性

**目标：** 知识库、代码沙箱、监控告警等企业级能力

**周期：** 4-6 周

### 优先级排序

| 优先级 | 任务 | 说明 | 仓库 |

| P1 | Agent 工具扩展 | 文件操作、API 调用、数据库查询 | quantalithos-runtime |
| P1 | 动态流程编排 | TL 提议流程 → runtime 编译执行 | quantalithos-flow |
| P1 | 多项目并行 | 支持用户同时参与多个项目 | 全局 |
| P2 | CI/CD 集成 | 自动化构建部署 | quantalithos-infra |
| P2 | 日志分析 | ELK Stack | quantalithos-infra |
| P2 | 多租户隔离 | 企业级租户管理 | quantalithos-gate |
| P2 | API 开放平台 | 外部系统集成 | quantalithos-gate |

### Phase 4 验收标准

- [ ] Agent 能查询公司内部知识库
- [ ] 生成的代码能在沙箱中安全运行
- [ ] 系统运行状态可监控、异常可告警
- [ ] 支持多项目并行
- [ ] 流程可动态编排（TL 提议 → runtime 编译）

## 九、风险与应对

| 风险 | 可能性 | 影响 | 应对策略 |
|------|--------|------|----------|
| LLM 调用成本过高 | 高 | 高 | 缓存、流式输出、模型选择策略 |
| Agent 行为不可控 | 中 | 高 | 严格的角色约束、工具权限控制、daemon 状态机层约束 |
| 流程复杂度爆炸 | 中 | 中 | 先做线性流程，再迭代动态编排 |
| 实时通信稳定性 | 中 | 中 | WebSocket 重连、消息队列 |
| 工作区同步冲突 | 中 | 中 | quantalithos-sync 加锁机制、冲突检测 |
| 知识库质量差 | 低 | 高 | 人工审核、反馈循环 |

## 十、下一步行动

### 立即开始（本周）

1. **初始化项目仓库结构**
   - 创建 `quantalithos-chat` 仓库
   - 创建 `quantalithos-runtime` 仓库
   - 创建 `quantalithos-infra` 仓库（Docker Compose 基础配置）

2. **技术选型确认**
   - 前端框架：React + TypeScript
   - Agent 框架：Python + 自建核心 + 可选 LangChain 底层复用
   - 数据库：PostgreSQL
   - 同步工具：Rust (quantalithos-sync)

3. **搭建开发环境**
   - 本地 Docker 开发环境
   - CI/CD 基础配置
   - 代码规范

### 需要确认的决策

1. 是否使用 monorepo（如 Nx/Turborepo）？
2. 是否需要对接现有的企业系统（SSO、GitLab）？
3. LLM 提供商选择（OpenAI / Claude / 本地模型）？

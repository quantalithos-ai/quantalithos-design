# 实施计划书写规范

> 实施计划回答 **"代码按什么顺序落地"**。
> 它是设计文档到可运行代码的桥梁——定义编码步骤、依赖关系和每步的完成标准。
> 概要设计见 → [概要设计书写规范](概要设计书写规范.md)
> 详细设计见 → [详细设计书写规范](详细设计书写规范.md)

---

## 一、实施计划的目标

实施计划的核心目标是**让开发者拿到详细设计后，不用再做"从哪开始"的决策**。它要解决四个核心问题：

1. **编码顺序**：先写什么、后写什么——避免写到一半发现前面的设计要改
2. **增量可运行**：每一步结束都产出一个可启动、可验证的系统
3. **风险前置**：最不确定的事先验证，不要做到后期才发现方案不可行
4. **完成标准**：每一步做到什么程度算"做完了"，怎么验证

> **实施计划的终极检验标准**：一个开发者严格按照实施计划执行，能否不回头修改已完成阶段的代码，顺利走到最后一步？如果中途需要返工，说明计划阶段划分有误或依赖分析不完整。

---

## 二、实施计划的定位

```
设计文档漏斗：

  需求文档          "要什么"
     │
     ▼
  概要设计          "为什么这样做、做什么"     ← 方向与边界
     │
     ▼
  详细设计          "具体怎么做"              ← 实现细节
     │
     ▼
  实施计划          "按什么顺序落地"          ← 编码路径  ← 你在这里
     │
     ▼
  可运行代码        "跑起来的系统"
```

实施计划**不重复设计内容**，它引用详细设计的模块，定义编码的先后顺序和依赖关系。

## 二-A、前置条件

在编写和执行实施计划之前，**必须**满足以下前置条件。不满足前置条件就动手编码，等同于没有图纸就施工——返工概率极高。

### 前置条件 0：Git 仓库初始化

每个子项目在开始编码前，必须确认 Git 仓库已正确初始化：

**检查步骤：**

1. 确认项目目录下存在 `.git/` 目录，如果不存在则执行 `git init`
2. 创建 `README.md`（至少包含项目名称和一句话描述）
3. 配置项目级 Git 用户信息：

```bash
cd <project-root>
git config user.name "quantalithos-labs"
git config user.email "quantalithos.ai@gmail.com"
```

4. 验证配置：

```bash
git config user.name   # 应输出 quantalithos-labs
git config user.email  # 应输出 quantalithos.ai@gmail.com
```

> **注意**：使用 `git config`（不带 `--global`）确保只影响当前项目，不污染全局配置。

### 前置条件 1：设计文档阅读确认

实施计划的制定者和执行者都必须**完整阅读**以下设计文档，并确认理解：

| 文档 | 阅读目的 | 确认方式 |
|------|---------|----------|
| [架构设计](架构设计.md) | 理解系统整体架构方向、模块边界、关键技术选型依据 | 能回答"为什么选 A 不选 B" |
| 每个项目的 `概要设计.md` | 理解系统上下文、接口边界、数据流概览、横切关注点 | 能回答"核心数据流怎么走" |
| 每个项目的 `详细设计.md` | 理解代码目录结构、结构体定义、接口契约、伪代码、数据 DDL、异常处理 | 能回答"这个函数的完整逻辑是什么" |
| [设计模式使用规范](设计模式使用规范.md) | 理解项目允许使用哪些设计模式、何时使用、如何避免滥用模式 | 能回答"当前场景为什么适合这个模式" |

> **铁律**：如果无法回答上述问题，说明设计文档阅读不充分，**不得进入编码阶段**。此时应回到对应设计文档补充理解，而非边写代码边猜。

### 前置条件 2：编码规范阅读确认

实施计划的执行者必须**完整阅读**对应编程语言的编码规范，并确认遵循：

| 语言 | 编码规范 | 重点确认项 |
|------|---------|------------|
| Rust | [Rust编码规范](Rust编码规范.md) | 命名规范、错误处理范式、trait 设计规范、unsafe 使用规范 |
| C | 项目 C 编码规范（如有） | 命名规范、内存管理规范、错误码规范、头文件组织 |
| Python | 项目 Python 编码规范（如有） | 类型注解规范、dataclass 使用规范、异步编程规范 |
| 其他 | 项目对应语言编码规范 | 命名规范、错误处理范式、依赖管理规范 |

> **原则**：编码规范是团队共识的底线。违反编码规范的代码即使功能正确，也会在 Code Review 时被退回——与其返工，不如一开始就遵循。

### 前置条件 3：语言与提交规范

#### 代码语言要求

- 所有代码文件**全英文**（变量名、函数名、注释、字符串常量）
- **不允许出现任何中文字符**
- 用户面向的文本通过 i18n 机制处理（Phase 2）
- 文档注释使用英文（`///` doc comments）

> **理由**：代码是跨国协作的基础设施，中文注释和字符串会在编码、搜索、国际化等环节引入额外成本。

#### 代码注释要求

- 结构体定义处必须注明**结构体整体作用**
- 结构体的**每个成员变量**都必须注释说明其作用、语义或约束
- 函数声明处必须注释说明**函数作用**、输入输出语义、关键前置条件
- 函数内部的**关键实现**、复杂分支、补偿逻辑、性能敏感路径和**易错处**必须有充分注释

> **理由**：结构体、字段、函数和关键逻辑的注释要求不是为了"写得好看"，而是为了让后来者在不猜测设计意图的前提下安全修改代码。

#### 注释合格与不合格对比

以下对比覆盖四个维度：**结构体作用说明**、**成员变量注释**、**函数声明注释**、**函数内部关键逻辑注释**。左列为不合格写法，右列为合格写法。

**③ 函数内部关键逻辑注释**

```rust
// ✗ 不合格：逻辑复杂但无注释，后续维护者无法判断哪些是刻意设计、哪些是易错点
pub async fn create_order_with_defense(&self, cmd: &CreateOrderCmd) -> Result<String, ServiceError> {
    let fingerprint = compute_fingerprint(cmd);
    let idempotent_key = format!("idempotent:order:{}", fingerprint);
    let setnx_result = self.cache.setnx(&idempotent_key, "", 86400).await?;
    if !setnx_result {
        if let Some(existing_id) = self.cache.get(&idempotent_key).await? {
            return Ok(existing_id);
        }
    }
    let stock_result = self.stock_proxy.batch_deduct(&cmd.items).await?;
    if !stock_result.success {
        self.cache.del(&idempotent_key).await?;
        return Err(ServiceError::StockInsufficient);
    }
    // ...
}

// ✓ 合格：关键步骤、设计意图、易错处都有注释
pub async fn create_order_with_defense(&self, cmd: &CreateOrderCmd) -> Result<String, ServiceError> {
    // STEP 1: Idempotent guard — use request fingerprint to deduplicate.
    // Key design: SETNX with 24h TTL; on duplicate request, return existing order_id.
    // CAUTION: if the process crashes between SETNX and order creation,
    // the idempotent key will block retries until TTL expires (acceptable trade-off).
    let fingerprint = compute_fingerprint(cmd);
    let idempotent_key = format!("idempotent:order:{}", fingerprint);
    let setnx_result = self.cache.setnx(&idempotent_key, "", 86400).await?;
    if !setnx_result {
        // Key already exists — this is a duplicate request.
        // Read the existing order_id from the key value; if empty, the previous
        // request is still in-flight (rare), treat as conflict.
        if let Some(existing_id) = self.cache.get(&idempotent_key).await? {
            return Ok(existing_id);  // Idempotent return: same result as first call
        }
    }

    // STEP 2: Stock pre-deduction — reserves inventory before order creation.
    // CAUTION: this is a distributed call; timeout does NOT mean failure.
    // Phase 4 adds confirm_deduct to handle the timeout ambiguity.
    let stock_result = self.stock_proxy.batch_deduct(&cmd.items).await?;
    if !stock_result.success {
        // Stock deduction failed — MUST clean up idempotent key to allow retry.
        // Without this cleanup, the user would be blocked for 24h on a failed attempt.
        self.cache.del(&idempotent_key).await?;
        return Err(ServiceError::StockInsufficient);
    }

    // ... (order construction & persistence, same as Phase 3) ...

    // STEP 3: Update idempotent key value with the created order_id.
    // This enables duplicate requests to return the correct order_id.
    self.cache.set(&idempotent_key, &order.order_id, 86400).await?;
    Ok(order.order_id)
}
```

> - [ ] 结构体定义处是否有一段话说明它是什么、在哪个上下文中使用？

> - [ ] 函数声明是否说明了作用、前置条件、返回值语义、可能错误和副作用？

#### Commit 规范

每完成一个**大功能**（对应实施计划中的一个阶段或子阶段），提交一次 commit。commit 必须遵循以下格式：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**Type 列表**：

| Type | 含义 |
|------|------|
| feat | 新功能 |
| fix | 修复 Bug |
| refactor | 重构（不改变功能） |
| docs | 文档变更 |
| test | 测试相关 |
| chore | 构建/工具/依赖变更 |
| perf | 性能优化 |
| ci | CI/CD 变更 |
| style | 代码格式（不影响逻辑） |

**Scope 列表**（按项目实际情况调整）：

project | workitem | artifact | agent-config | snapshot | event | api | common | design | integration | knowledge

**Footer 规范**：

| 场景 | footer 内容 |
|------|------------|
| AI 辅助编写 | `Co-Authored-By: Claude <noreply@anthropic.com>` |
| 关联 issue | `Closes #42` 或 `Refs #42` |
| 破坏性变更 | `BREAKING CHANGE: <description>` |

**单功能改动示例**：

```
feat(workitem): implement state machine validation

- state_machine.rs (+95): add TASK/BUG/REQUIREMENT transition tables
- handler.rs (+5): call validate_transition before status update
- state_machine_test.rs (+120): cover all legal and illegal transitions
```

**多功能改动示例（按功能分组，每个功能用一句英文概括，列出文件和改动内容）**：

```
feat(platform): add task scheduling and auto-assign

Scheduling execution lifecycle with start and completion hooks:
- task_scheduler.rs (+180): implement start_execution and on_task_completed
- handler.rs (+45): register start-execution route

Auto-assign workitems based on role-based rules on transition:
- service.rs (+60): implement auto_assign with role-based rules
- handler.rs (+12): call auto_assign in transition handler

Publish lifecycle events for downstream consumers:
- event_bus.rs (+8): add TaskBecameReady and AllTasksCompleted variants

Co-Authored-By: Claude <noreply@anthropic.com>
```

**AI 辅助修复示例**：

```
fix(engine): prevent token advancement when gateway has no matching condition

- state_machine.rs (~3): change silent None return to RuntimeError

Co-Authored-By: Claude <noreply@anthropic.com>
```

> **要点**：
> - **大功能 = 一次 commit**：实施计划中一个阶段完成、或一个可独立验证的子功能完成时提交
> - **文件名只写文件本身**：如 `task_scheduler.rs`，不带目录路径——reviewer 可通过 `git diff` 定位文件
> - **功能分组用一句英文概括**：不用简单的名词标签（如"任务调度"），而是用一句完整的话描述该功能做了什么（如 "Scheduling execution lifecycle with start and completion hooks"）
> - **body 必须列出改动文件和内容**：让 reviewer 不看 diff 就能理解改了什么
> - **全英文 commit message**：与代码语言要求一致
> - **不要攒一堆不相关的改动一次性提交**：每个 commit 只做一件事

## 四、五阶段模型

### 理论基础

代码落地不是"把详细设计翻译成代码"这么简单。编码顺序如果错了，会导致：

- **返工**：先写了前端页面，发现后端接口定义要改
- **阻塞**：数据层没建好，业务逻辑无法验证
- **风险后置**：最不确定的技术选型放到最后才验证，发现不可行时大量代码作废

五阶段模型的核心思想是**增量构建 + 风险前置**——每个阶段都在上一个可运行系统上叠加，任何阶段完成都产出一个可启动、可验证的系统。

```
阶段 0: 技术验证（可选）
   │
   ▼
阶段 1: 骨架可启动
   │
   ▼
阶段 2: 数据层闭环
   │
   ▼
阶段 3: 核心链路贯通
   │
   ▼
阶段 4: 防御性补全
   │
   ▼
阶段 5: 生产化
```

### 阶段 0：技术验证（Spike）

#### 何时需要

不是所有项目都需要 Spike。以下场景**必须先 Spike**：

| 场景 | 判断标准 | 示例 |
|------|---------|------|
| 新框架/新中间件 | 团队首次使用，无最佳实践 | 首次集成 gRPC、首次用 ClickHouse |
| 性能目标存疑 | 非功能需求接近技术天花板 | "单机 10 万 QPS"、"P99 < 1ms" |
| 外部接口未确认 | 依赖的外部 API 还在开发中或文档不完整 | 第三方支付 SDK 沙箱环境验证 |
| 核心算法存疑 | 算法正确性或性能未经实践验证 | 自研分片路由算法、分布式 ID 生成 |

#### Spike 的产出

Spike **不产出可运行的系统代码**，它产出的是一个结论：

| 结论 | 含义 | 后续动作 |
|------|------|---------|
| ✓ 可行 | 技术方案验证通过 | 进入阶段 1，Spike 代码可作为参考 |
| △ 需调整 | 方案可行但需修改设计 | 回到详细设计修改相关模块，再进入阶段 1 |
| ✗ 不可行 | 方案行不通 | 回到概要设计重新选型，不能进入阶段 1 |

> **铁律**：Spike 结论为"不可行"时，**绝不硬着头皮进入阶段 1**。此时应该回到概要设计重新评估备选方案，而不是在不可行的方案上浪费编码时间。

#### Spike 编写要点

- Spike 代码是**一次性验证代码**，不合并到主干
- Spike 必须有**通过标准**：如"能承受 10 万 QPS 无错误"、"API 调用成功返回预期结果"
- Spike 必须有**结论文档**：1 页以内，写明"验证了什么、结论是什么、对设计有什么影响"

### 阶段 2：数据层闭环

#### 目标

数据能存、能取、能校验。这一步完成后再写业务逻辑时，不需要关心数据怎么存取。

#### 输入

| 输入模块 | 用到什么 |
|---------|---------|
| 数据设计 | 完整 DDL、缓存 Key 设计、数据所有权声明 |
| 结构体定义 | 核心结构体字段列表和约束 |
| 接口定义 | Repository 接口签名 |

#### 动作

1. 在开发库执行 DDL（含索引、约束、分区策略）
2. 实现结构体类（字段、默认值、校验注解）
3. 实现 Repository 层（CRUD + 乐观锁更新）
4. 实现缓存层（Key 构建、查询、失效逻辑、击穿防护）
5. 编写 Repository 单元测试：插入、查询、更新冲突、缓存穿透

#### 产出

数据层完全可用。通过 Repository 可以正确地增删改查，缓存逻辑经过验证。

#### 检查点

| 检查项 | 验证方式 |
|--------|---------|
| DDL 执行成功 | 表结构、索引、约束在开发库中存在 |
| CRUD 正常 | 单测：插入 → 查询 → 更新 → 查询，结果一致 |
| 乐观锁生效 | 单测：两个线程并发更新同一行，一个成功一个抛出 `OptimisticLockException` |
| 缓存命中 | 单测：首次查询走 DB，二次查询走缓存 |
| 缓存击穿防护 | 单测：并发查询一个不存在的 Key，DB 只被查询一次 |
| 数据所有权合规 | 确认每个 Repository 只操作自己服务拥有的表 |

#### 深度标尺

| 深度 | 判断标准 | 是否合格 |
|------|---------|---------|
| 不足 | 只实现了部分 CRUD，缓存未做 | ✗ |
| 适中 | 完整 CRUD + 乐观锁 + 缓存 + 击穿防护 + 单测全过 | ✓ |
| 过度 | 在 Repository 里写了业务逻辑（如状态校验） | ✗ 业务逻辑属于阶段 3 |

```c
// === C: 数据层闭环（以 SQLite 为例） ===

// src/repository/order_repo.h — 接口定义
typedef struct {
    char order_id[32];
    char user_id[32];
    int  status;
    long total_amount;
    int  version;        // 乐观锁版本号
} order_t;

typedef struct order_repo order_repo_t;

struct order_repo {
    int  (*save)(order_repo_t *self, const order_t *order);           // INSERT or UPDATE
    int  (*find_by_id)(order_repo_t *self, const char *id, order_t *out);
    int  (*update_with_version)(order_repo_t *self, const order_t *order);  // 乐观锁更新
};

// src/repository/order_repo.c — 实现
#include <sqlite3.h>

static int save(order_repo_t *self, const order_t *order) {
    sqlite3 *db = (sqlite3 *)self->ctx;
    const char *sql = "INSERT INTO t_order (order_id, user_id, status, total_amount, version) "
                      "VALUES (?, ?, ?, ?, 0)";
    sqlite3_stmt *stmt;
    sqlite3_prepare_v2(db, sql, -1, &stmt, NULL);
    sqlite3_bind_text(stmt, 1, order->order_id, -1, SQLITE_STATIC);
    sqlite3_bind_text(stmt, 2, order->user_id, -1, SQLITE_STATIC);
    sqlite3_bind_int(stmt, 3, order->status);
    sqlite3_bind_int64(stmt, 4, order->total_amount);
    int rc = sqlite3_step(stmt);
    sqlite3_finalize(stmt);
    return rc == SQLITE_DONE ? 0 : -1;
}

static int update_with_version(order_repo_t *self, const order_t *order) {
    sqlite3 *db = (sqlite3 *)self->ctx;
    // 乐观锁：WHERE version = 旧版本号，UPDATE version = 旧版本号 + 1
    const char *sql = "UPDATE t_order SET status=?, total_amount=?, version=version+1 "
                      "WHERE order_id=? AND version=?";
    sqlite3_stmt *stmt;
    sqlite3_prepare_v2(db, sql, -1, &stmt, NULL);
    sqlite3_bind_int(stmt, 1, order->status);
    sqlite3_bind_int64(stmt, 2, order->total_amount);
    sqlite3_bind_text(stmt, 3, order->order_id, -1, SQLITE_STATIC);
    sqlite3_bind_int(stmt, 4, order->version);
    int rc = sqlite3_step(stmt);
    sqlite3_finalize(stmt);
    // affected_rows == 0 → 乐观锁冲突
    return sqlite3_changes(db) == 0 ? -2 : 0;  // -2 = version conflict
}
```

```rust
use redis::AsyncCommands;

pub struct OrderCache {
    redis: redis::aio::ConnectionManager,
}

impl OrderCache {
    pub async fn get(&self, order_id: &str) -> Result<Option<Order>> {
        let key = format!("order:{}", order_id);
        let val: Option<String> = self.redis.clone().get(&key).await?;
        match val {
            Some(json) => Ok(Some(serde_json::from_str(&json)?)),
            None => Ok(None),  // 缓存未命中，走 DB
        }
    }

    pub async fn set(&self, order: &Order) -> Result<()> {
        let key = format!("order:{}", order.order_id);
        let val = serde_json::to_string(order)?;
        self.redis.clone().set_ex(&key, &val, 1800).await?;  // TTL = 30min
        Ok(())
    }

    pub async fn invalidate(&self, order_id: &str) -> Result<()> {
        let key = format!("order:{}", order_id);
        self.redis.clone().del(&key).await?;  // Cache-Aside: 写时删缓存
```

```python
# === Python: 数据层闭环（以 SQLAlchemy + Redis 为例） ===

# src/repository/order_repo.py — 接口与实现
from abc import ABC, abstractmethod
from sqlalchemy import text
from redis import Redis

class OrderRepo(ABC):
    @abstractmethod
    def save(self, order: Order) -> None: ...
    @abstractmethod
    def find_by_id(self, order_id: str) -> Order | None: ...
    @abstractmethod
    def update_with_version(self, order: Order) -> None: ...  # 乐观锁

class SqlAlchemyOrderRepo(OrderRepo):
    def __init__(self, session: Session, cache: Redis):
        self._session = session
        self._cache = cache

    def save(self, order: Order) -> None:
        self._session.execute(
            text("""INSERT INTO t_order (order_id, user_id, status, total_amount, version)
                   VALUES (:order_id, :user_id, :status, :total_amount, 0)"""),
            {"order_id": order.order_id, "user_id": order.user_id,
             "status": order.status, "total_amount": order.total_amount}
        )

    def update_with_version(self, order: Order) -> None:
        result = self._session.execute(
            text("""UPDATE t_order SET status = :status, total_amount = :total_amount,
                   version = version + 1 WHERE order_id = :order_id AND version = :version"""),
            {"status": order.status, "total_amount": order.total_amount,
             "order_id": order.order_id, "version": order.version}
        )
        if result.rowcount == 0:
            raise OptimisticLockConflictError(f"Order {order.order_id} version conflict")

    def find_by_id(self, order_id: str) -> Order | None:
        # Cache-Aside: 先查缓存，未命中查 DB
        cache_key = f"order:{order_id}"
        cached = self._cache.get(cache_key)
        if cached:
            return Order.from_json(cached)  # 缓存命中

        # 缓存未命中，查 DB
        row = self._session.execute(
            text("SELECT * FROM t_order WHERE order_id = :order_id"),
            {"order_id": order_id}
        ).fetchone()
        if row is None:
            return None
        order = Order.from_row(row)
        self._cache.setex(cache_key, 1800, order.to_json())  # TTL = 30min
        return order
```

### 阶段 3：核心链路贯通

#### 目标

最重要的业务路径能端到端走通。此时外部依赖用 Mock/Stub 实现。

#### 输入

| 输入模块 | 用到什么 |
|---------|---------|
| 关键函数伪代码 | 核心业务函数的实现逻辑 |
| 核心流程 | 时序图、流程图 |
| 状态机 | 转换矩阵和状态转换函数 |
| 接口定义 | 完整的 API 契约（前置/后置条件） |

#### 动作

1. 按伪代码填充 AppService / DomainService 的核心方法
2. 实现状态机转换函数（严格按照转换矩阵）
3. 外部依赖用 Mock/Stub 实现（返回预定义的合理数据）
4. 编写核心路径集成测试

#### Mock/Stub 的标准

Mock 不是随便返回个值就行。合格的 Mock 必须满足：

| 要求 | 说明 | 示例 |
|------|------|------|
| 返回值合理 | 返回的格式和真实接口一致 | StockProxy.deduct 返回 `{success: true, deducted: [...]}` |
| 模拟延迟 | 可配置延迟，用于验证超时逻辑 | Mock 支持设置 3s 延迟 |
| 模拟失败 | 可配置失败，用于验证异常路径 | Mock 支持设置 `throw TimeoutException` |
| 状态感知 | Mock 的返回值能根据输入变化 | deduct 同一 SKU 第二次返回 `stock insufficient` |

#### 产出

核心业务路径可端到端执行。如"创建订单 → 支付 → 发货"能用 curl 跑通完整链路。

#### 检查点

| 检查项 | 验证方式 |
|--------|---------|
| 主路径走通 | curl 创建订单 → 返回 orderId → 查询订单状态为 CREATED |
| 状态转换正确 | 支付后状态变为 PAID，发货后状态变为 SHIPPED |
| 前置条件生效 | 未支付时发货返回错误，未发货时确认收货返回错误 |
| 后置条件满足 | 创建订单后，订单总金额 = 行项金额之和 |
| 外部调用被 Mock | 日志中无真实 RPC 调用，只有 Mock 返回 |

```c
    DeductRequest request = build_deduct_request(items);
    DeductResponse response;
    grpc_status_t status = impl->stub->Deduct(&ctx, request, &response);

    // 监控埋点
    metrics_histogram_observe("stock_proxy_deduct_duration_ms", elapsed_ms());
    metrics_counter_inc(status.ok ? "stock_proxy_deduct_success" : "stock_proxy_deduct_failure");

    if (!status.ok) {
        log_warn("StockProxy.Deduct failed: code=%d msg=%s", status.code, status.message);
        if (status.code == GRPC_STATUS_DEADLINE_EXCEEDED) {
            return DEDUCT_RESULT_TIMEOUT;
        }
        return DEDUCT_RESULT_FAILURE;
    }

    log_info("StockProxy.Deduct success: order_count=%d", items->count);
    return response.success ? DEDUCT_RESULT_SUCCESS : DEDUCT_RESULT_INSUFFICIENT;
}
```

## 五、阶段依赖拓扑

### 基本依赖

```
Spike(可选) ──→ 阶段1 ──→ 阶段2 ──→ 阶段3 ──→ 阶段4 ──→ 阶段5
```

这是最常见的串行路径。但实际项目中，某些阶段可以部分并行。

### 并行机会

```
阶段1: 骨架可启动
   │
   ├──→ 阶段2a: 核心数据层（主表、核心缓存）  ──┐
   │                                            ├──→ 阶段3: 核心链路贯通
   └──→ 阶段2b: 辅助数据层（日志表、统计表）──┘
```

并行规则：

| 规则 | 说明 |
|------|------|
| 阶段 1 必须先完成 | 没有骨架，后面的代码无处放置 |
| 阶段 3 必须等阶段 2 完成 | 没有数据层，业务逻辑无法运行 |
| 阶段 4 必须等阶段 3 完成 | 没有核心链路，异常处理没有附着点 |
| 阶段 5 必须等阶段 4 完成 | 没有防御性代码，接入真实服务会出事故 |
| 阶段 2 内部可并行 | 不同表/不同缓存可以并行实现 |

> **关键路径**：阶段 1 → 阶段 2a → 阶段 3 → 阶段 4 → 阶段 5。关键路径上的任何延迟都会导致整体延期。

## 六、回退规则

### 核心原则

**如果某个阶段走不通，不是硬着头皮往下写，而是回头改设计。**

走不通通常意味着详细设计不够细或设计有误。以下是每个阶段的回退触发条件：

| 阶段 | 回退触发条件 | 回退到 | 修正动作 |
|------|-------------|--------|---------|
| 阶段 1 | 依赖冲突导致框架无法启动 | 概要设计 | 重新评估技术选型 |
| 阶段 1 | 目录结构无法反映模块边界 | 详细设计 | 重新划分模块和目录 |
| 阶段 2 | DDL 无法满足查询需求（缺索引、缺字段） | 详细设计 | 补充数据设计 |
| 阶段 2 | 乐观锁/缓存策略不可行 | 详细设计 | 重新设计并发方案 |
| 阶段 3 | 伪代码逻辑有遗漏，无法直接翻译 | 详细设计 | 补充伪代码 |
| 阶段 3 | 状态机转换矩阵有遗漏 | 详细设计 | 补充转换矩阵 |
| 阶段 4 | 并发场景有遗漏 | 详细设计 | 补充竞态分析 |
| 阶段 4 | 补偿逻辑导致状态不一致 | 详细设计 | 重新设计补偿流程 |
| 阶段 5 | 真实外部服务行为与文档不一致 | 详细设计 + 外部文档 | 更新接口定义 |

### 回退流程

```
发现走不通
   │
   ▼
记录问题（什么场景、什么现象、为什么设计覆盖不到）
   │
   ▼
判断影响范围（仅影响当前模块 / 影响多个模块 / 影响架构方向）
   │
   ├── 局部影响 → 修改详细设计对应模块 → 更新实施计划 → 继续执行
   │
   ├── 多模块影响 → 修改详细设计多个模块 → 从受影响的最早阶段重新执行
   │
   └── 架构影响 → 回到概要设计重新评估 → 重新制定实施计划
```

## 七、实施计划与详细设计的映射

实施计划的每个阶段都**直接引用详细设计的模块**，不重复设计内容：

| 实施阶段 | 引用详细设计的模块 | 编码行为 |
|---------|-----------------|---------|
| 阶段 0 | 无（独立验证） | 编写一次性验证代码 |
| 阶段 1 | §2 代码目录结构 + §13 框架集成与代码骨架 + §4 接口定义 | 搭建骨架 |
| 阶段 2 | §3 结构体定义 + §6 数据设计 | 实现数据层 |
| 阶段 3 | §5 关键函数伪代码 + §7 核心流程 + §8 状态机 + §4 接口定义 | 实现业务逻辑 |
| 阶段 4 | §9 异常处理与容错 + §10 并发与一致性 | 实现防御性代码 |
| 阶段 5 | §4 接口定义 + §13 框架集成 + §14 部署与运维 | 接入真实依赖 + 可观测 |

> **如果某个阶段引用的详细设计模块内容不完整，应该先补全详细设计，而不是在编码时临时决定。**

## 十、常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 跳过前置条件直接编码 | 不了解架构方向和编码规范，写出风格不一致甚至方向错误的代码 | 先阅读设计文档和编码规范，确认理解后再动手 |
| 跳过 Spike 直接编码 | 做到阶段 4 才发现核心方案不可行，大量代码作废 | 先 Spike 验证最不确定的点 |
| 阶段 1 就写业务逻辑 | 骨架还没稳定就开始写逻辑，后续结构变更导致返工 | 阶段 1 只搭骨架，不写业务 |
| 阶段 3 不写 Mock 标准 | Mock 随便返回数据，核心路径"看似走通"实际隐藏 Bug | Mock 必须符合真实接口格式和行为 |
| 阶段 4 跳过并发测试 | "应该没问题"→ 上线后并发 Bug 频出 | 每个竞态场景必须有对应的并发测试 |
| 检查点不可执行 | "代码写差不多了"→ 其实还差很多 | 每个检查点必须是可运行的命令或断言 |
| 阶段 5 才对接真实服务 | 发现真实接口与文档不一致，大量逻辑要改 | 如果外部接口未确认，应在 Spike 阶段验证 |
| 回退时硬着头皮往下写 | 在错误的基础上继续堆砌，最终返工代价更大 | 发现走不通就停下来，回头改设计 |

# 架构设计理论体系

> 架构的本质不是选择技术组件，而是对系统中的**约束**和**变化方向**进行有意识的组织。
> 好的架构让系统在预期的变化维度上容易修改，在预期的稳定维度上受到保护。

---

## 一、架构的本质

### 1.1 架构的定义

架构没有一个统一定义，但不同流派的定义揭示了架构的不同侧面：

| 定义来源 | 定义 | 侧重点 |
|---------|------|--------|
| IEEE 1471 | "一个系统的基本组织，体现在其组件、组件间关系和指导其设计与演进的原则中" | 结构 + 原则 |
| Ralph Johnson (GoF) | "架构是那些无论如何选择都很难在后期改变的东西" | 不可逆决策 |
| Martin Fowler | "架构是那些需要在早期做出的、一旦做出就难以改变的决策的集合" | 决策的不可逆性 |
| Robert C. Martin | "架构是关于意图的，架构应该尖叫出系统的意图" | 意图表达 |
| Eric Evans | "架构是那些使领域模型得以清晰表达的结构性决策" | 领域表达 |

**核心共识**：架构关注的是**重要的、难以逆转的决策**——这些决策影响系统的组织方式、依赖方向、边界划分和演化能力。

### 1.2 架构的根本矛盾

架构设计始终在两极之间做取舍：

```
        简单性                                    灵活性
          ◄──────────────────────────────────────►
          
     · 容易理解                              · 适应未来变化
     · 开发快                                · 局部修改不影响全局
     · 运维成本低                            · 可独立扩展
     · 但变化来临时修改代价大                  · 但当下理解成本高
     · 容易过早优化                           · 容易过度设计
```

**关键判断**：不是"简单 vs 复杂"，而是"复杂度放在哪里"。

- **推迟复杂度**：当不确定时，先选简单方案，让真实需求驱动复杂度的引入
- **保护性复杂度**：当某些维度的变化可以预见时，提前建立边界和抽象来隔离变化

### 1.3 架构的理论基础

架构决策背后有三大理论支撑：

```
┌─────────────────────────────────────────────────────────────┐
│                    架构决策的理论基础                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ① 认知论：人类理解复杂系统的方式                              │
│     - 分而治之 (Decomposition)                               │
│     - 抽象层次 (Levels of Abstraction)                       │
│     - 信息隐藏 (Information Hiding)                          │
│     → 推导出：模块化、分层、封装                               │
│                                                             │
│  ② 经济论：变化的成本与收益                                    │
│     - 变更成本曲线 (Cost of Change Curve)                     │
│     - 不可逆决策的成本 (Irreversibility Cost)                 │
│     - 机会成本 (Opportunity Cost)                             │
│     → 推导出：依赖倒置、接口隔离、演进式设计                    │
│                                                             │
│  ③ 组织论：人的协作方式如何塑造系统结构                         │
│     - 康威定律 (Conway's Law)                                │
│     - 认知负荷 (Cognitive Load)                               │
│     - 沟通成本与团队边界                                      │
│     → 推导出：限界上下文、服务拆分、团队对齐                    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 二、架构风格理论

### 2.1 架构风格的本质

架构风格（Architectural Style）是一组约束的集合，它限制了组件的类型和交互方式，从而为特定类别的系统带来可预测的属性。

Mary Shaw 和 David Garlan 在 *Software Architecture: Perspectives on an Emerging Discipline* 中定义：

> 架构风格是组件和连接器类型的词汇表，加上一组关于它们如何组合的约束。

**选择架构风格的本质**：选择一组约束，放弃一些自由度，换取特定维度的收益。

### 2.2 主要架构风格及其约束-收益分析

```
┌───────────────────────────────────────────────────────────────────────┐
│                        架构风格的光谱                                   │
│                                                                       │
│  单体 ◄──────── 模块化单体 ◄──────── 微服务 ◄──────── Serverless       │
│                                                                       │
│  约束递增：部署自由度 ↓   运维复杂度 ↑   分布式问题 ↑   供应商绑定 ↑    │
│  收益递增：开发速度 ↑→↓  边界清晰度 ↑   独立扩展 ↑   弹性伸缩 ↑        │
│                     ↑                                                 │
│                  临界点：收益不一定随约束递增                            │
│                  超过业务需要的约束 = 过度设计                           │
└───────────────────────────────────────────────────────────────────────┘
```

#### 分层架构 (Layered Architecture)

**约束**：每一层只能与相邻层通信；上层依赖下层，下层不知道上层。

**收益**：关注点分离；每层可独立替换；容易理解。

**代价**：层数过多导致简单操作穿过多层带来性能和认知开销；层间抽象泄漏时反而更难维护。

**理论基础**：Edsger Dijkstra 的"关注点分离"原则——将系统按照不同关注维度进行纵向切割，每一层只处理一个关注维度。

```
┌─────────────────────┐
│  Presentation Layer  │  ← 用户交互 / API 入口
├─────────────────────┤
│  Business Layer      │  ← 业务规则 / 领域逻辑
├─────────────────────┤
│  Persistence Layer   │  ← 数据存取 / ORM
├─────────────────────┤
│  Database Layer      │  ← 数据库 / 外部存储
└─────────────────────┘

依赖方向：↓（自上而下）
问题：业务层常常被持久化层的细节反向渗透
```

**关键洞察**：分层架构最常见的失败模式是**层泄漏**——业务逻辑散落在表现层或持久化层中，分层变成名义上的而非实质上的。这不只是纪律问题，而是分层架构本身没有提供足够的结构约束来防止泄漏。

#### 六边形架构 (Hexagonal Architecture / Ports & Adapters)

**提出者**：Alistair Cockburn, 2005

**约束**：内部（业务逻辑）不依赖任何外部技术；所有与外部世界的交互都通过端口（Port 接口）和适配器（Adapter 实现）。

**核心洞察**：传统分层架构用"上下"隐喻，暗示"数据库在下，UI 在上"。但 Cockburn 发现：UI 侧和数据库侧的问题**本质相同**——都是业务逻辑与外部实体的纠缠。真正的对称性不是"上下"之分，而是**"内外"之分**。

```
              ┌─────────────┐
              │   Test      │  自动化测试也是一种"驱动者"
              └──────┬──────┘
                     │
  ┌──────────┐      │      ┌──────────┐
  │   REST   │──────┤      │   SQL    │
  │ Adapter  │      │      │ Adapter  │
  └──────────┘      │      └──────────┘
                ┌───┴───┐
                │       │
                │  App  │  ← 内部只知道 Port 接口
                │ Core  │     不知道 HTTP / SQL / 消息队列
                │       │
                └───┬───┘
                    │
  ┌──────────┐      │      ┌──────────┐
  │   GUI    │──────┘      │  Mock DB │
  │ Adapter  │             │ Adapter  │  ← 测试时替换
  └──────────┘             └──────────┘
  
  Port = 内部定义的接口（"我需要什么能力"）
  Adapter = 外部提供的实现（"如何对接具体技术"）
```

**与分层架构的本质区别**：

| 维度 | 分层架构 | 六边形架构 |
|------|---------|-----------|
| 隐喻 | 上下（暗示层级高低） | 内外（暗示核心与边缘） |
| 驱动者数量 | 两个（UI 和 DB） | 任意多个（REST / MQ / Test / Schedule...） |
| 防泄漏机制 | 纪律约束 | 接口强制隔离 |
| 测试方式 | 从上到下穿透测试 | 端口级隔离测试 |

#### 整洁架构 (Clean Architecture)

**提出者**：Robert C. Martin (Uncle Bob), 2012

**约束**：依赖规则必须由外向内——内层（业务规则）不能依赖外层（框架、数据库、UI）。

**与六边形架构的关系**：Clean Architecture 是对 Hexagonal Architecture、Onion Architecture、Screaming Architecture、DCI 等思想的**统一归纳**。它们的共同点是都强调"依赖方向由外向内"。Clean Architecture 的贡献在于给出了更明确的多层模型和跨边界调用规则。

```
┌─────────────────────────────────────────────────┐
│  Frameworks & Drivers（框架与驱动层）             │
│  ┌─────────────────────────────────────────────┐ │
│  │  Interface Adapters（接口适配器层）           │ │
│  │  ┌─────────────────────────────────────────┐ │ │
│  │  │  Application Business Rules（用例层）    │ │ │
│  │  │  ┌─────────────────────────────────────┐ │ │ │
│  │  │  │  Enterprise Business Rules（实体层） │ │ │ │
│  │  │  └─────────────────────────────────────┘ │ │ │
│  │  └─────────────────────────────────────────┘ │ │
│  └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘

依赖方向：外层 → 内层（越往内越稳定、越抽象）
跨边界调用：内层定义接口（DIP），外层提供实现
```

**四层模型的职责划分**：

| 层 | 职责 | 稳定性 | 变化频率 |
|----|------|--------|---------|
| Enterprise Business Rules | 企业级通用业务规则，不随应用场景改变 | 最高 | 最低 |
| Application Business Rules | 应用级业务规则，编排实体完成特定用例 | 高 | 低 |
| Interface Adapters | 数据格式转换，连接用例层与外部世界 | 中 | 中 |
| Frameworks & Drivers | 框架、数据库、UI，是可替换的细节 | 低 | 高 |

**关键原则**：框架是工具而非架构——你不应该被框架绑定。如果你的业务规则依赖于 Spring 或 Hibernate，那不是整洁架构。

#### 领域驱动设计 (Domain-Driven Design)

**提出者**：Eric Evans, 2003

**核心主张**：软件的核心是其解决业务问题的能力。大多数软件项目失败不是因为技术选型错误，而是因为没有正确理解业务领域。

**DDD 不是一种架构风格，而是一种设计方法论**——它提供了一套以业务领域为中心的软件设计方法，可以与六边形架构、整洁架构等结合使用。

**两大设计维度**：

```
┌──────────────────────────────────────────────────────────┐
│                    战略设计（Strategic Design）            │
│  解决"领域边界怎么划"的问题                               │
│                                                          │
│  核心产出：                                               │
│  · 统一语言（Ubiquitous Language）                        │
│    → 团队用一致的业务术语沟通需求、模型和代码               │
│    → 代码中的命名与业务概念一一对应                        │
│    → 如果开会说的词和代码里的词不一样，就没有统一语言       │
│                                                          │
│  · 限界上下文（Bounded Context）                          │
│    → 同一术语在不同上下文中有不同含义，明确边界防止概念混用  │
│    → "Product"在商品上下文是 SKU + 价格，在物流上下文是重量+尺寸│
│                                                          │
│  · 上下文映射（Context Map）                              │
│    → 描述多个限界上下文间的关系模式                        │
│    → 防腐层 / 开放主机服务 / 共享内核 / 各走各路 等        │
│                                                          │
│  · 子域划分                                              │
│    → 核心域：竞争力所在，值得投入最优秀的建模资源            │
│    → 支撑子域：必要但不构成壁垒                            │
│    → 通用子域：可购买/复用现成方案                          │
├──────────────────────────────────────────────────────────┤
│                    战术设计（Tactical Design）            │
│  解决"模型内部怎么落"的问题                               │
│                                                          │
│  核心产出：                                               │
│  · 聚合（Aggregate）                                     │
│    → 事务一致性边界，外部只能通过聚合根访问                 │
│    → 聚合要尽量小，只包含必须保证一致性的对象               │
│                                                          │
│  · 实体 vs 值对象                                        │
│    → 实体：通过身份标识区分，生命周期中有状态变化            │
│    → 值对象：通过属性值区分，不可变，可安全替换              │
│                                                          │
│  · 领域事件（Domain Event）                              │
│    → 表达"领域中已经发生的重要事实"                        │
│    → 实现上下文间的异步解耦                               │
│                                                          │
│  · 仓储（Repository）                                    │
│    → 提供像集合一样的接口访问聚合，屏蔽持久化细节            │
│                                                          │
│  · 领域服务（Domain Service）                             │
│    → 承载不自然归属于某个实体/值对象的领域规则              │
└──────────────────────────────────────────────────────────┘
```

**DDD 成功的关键**：不是技术实现有多精巧，而是团队是否建立了真正有效的统一语言，是否正确识别了核心域和限界上下文。如果开会说的词和代码里的词不一样，DDD 就没有真正落地。

#### CQRS + Event Sourcing

**CQRS** (Command Query Responsibility Segregation)

**提出者**：Greg Young; Martin Fowler 于 2011 年撰文阐述

**核心思想**：使用不同的模型来更新信息（Command）和读取信息（Query），而非传统 CRUD 中读写共用同一模型。

**理论依据**：在复杂领域里，命令和查询的优化方向完全不同——命令需要保证业务规则和一致性，查询需要优化性能和展示。强制两者共用一个模型，结果是模型既满足不了命令侧的语义精确性，也满足不了查询侧的性能需求。

```
         Command Model              Query Model
        ┌─────────────┐           ┌─────────────┐
  Cmd → │  Write Side  │ → Events → │  Read Side   │ → Queries
        │  (Domain)    │           │  (Projections)│
        │  Aggregate   │           │  Denormalized │
        │  Invariants  │           │  View Models  │
        └──────┬───────┘           └──────┬────────┘
               │                          │
        ┌──────┴───────┐           ┌──────┴────────┐
        │  Write DB    │           │  Read DB      │
        │  (Normalized)│           │  (Optimized)  │
        └──────────────┘           └───────────────┘
```

**Martin Fowler 的警告**：CQRS 增加了显著的复杂性，只应在**特定限界上下文**中使用，**不应整个系统使用**。大多数 CRUD 系统用 CQRS 是在解决不存在的问题。

**Event Sourcing** (事件溯源)

**核心思想**：不存储对象的当前状态，而是存储所有改变状态的事件。系统状态是事件日志的投影（projection），任何时候都可以通过重放事件来重建状态。

**类比**：版本控制系统——commit 日志是事件存储，工作目录是系统状态。`git checkout` 是投影，`git rebase -i` 是替代历史。

**关键区分（Martin Fowler 特别强调）**：

| 常见误解 | 正确理解 |
|---------|---------|
| 事件溯源 = 异步 | 事件处理不必须是异步的（如本地 Git 操作就是同步的） |
| 所有组件都直接访问事件日志 | 大多数处理应基于 projection（工作副本），只有真正需要事件日志信息的组件才操作日志 |
| 事件溯源天然解决一致性问题 | 事件回放依赖外部系统交互时反而变得复杂 |

**CQRS + ES 的适用条件**：
- 读写差异确实很大
- 需要强审计能力
- 需要时间旅行（重建历史状态）
- 领域事件本身是业务的核心资产

#### 微服务架构 (Microservices Architecture)

**提出者**：James Lewis & Martin Fowler (ThoughtWorks), 2014

**核心约束**：服务独立部署、独立数据库、通过轻量级协议通信。

**九大特征的理论根源**：

| 特征 | 理论根源 |
|------|---------|
| 通过服务组件化 | 信息隐藏原则——服务边界是最强的信息隐藏 |
| 围绕业务能力组织 | 康威定律——组织结构决定系统结构 |
| 产品而非项目 | 生命周期责任制——降低"公地悲剧"风险 |
| 智能端点与哑管道 | 端到端原则——智能应在端点而非网络 |
| 去中心化治理 | 有限理性——集中决策的信息成本过高 |
| 去中心化数据管理 | 耦合理论——共享数据是最大的耦合源 |
| 基础设施自动化 | 反馈回路——缩短部署周期以降低风险 |
| 为失败而设计 | 故障隔离——分布式系统中故障是常态 |
| 演进式设计 | 复杂适应系统——架构应随环境变化而演化 |

**微服务的代价模型**：

```
┌─────────────────────────────────────────────────────────────┐
│                     微服务的隐含成本                          │
│                                                             │
│  网络延迟    ：进程内调用 → 网络调用，延迟增加 10~100 倍      │
│  数据一致性  ：本地事务 → 分布式事务 / Saga，一致性保障复杂   │
│  运维复杂度  ：1 个进程 → N 个进程 × M 个版本               │
│  调试困难    ：单进程栈跟踪 → 分布式链路追踪                 │
│  团队沟通    ：接口契约 → 版本协商、兼容性管理               │
│  测试复杂度  ：集成测试 → 契约测试 + 混沌工程               │
│                                                             │
│  结论：只有在业务规模和团队规模真正需要时，                   │
│        微服务的收益才能覆盖这些成本                           │
└─────────────────────────────────────────────────────────────┘
```

**Martin Fowler 的建议**："先构建单体，当你确实需要时再拆分。"——这不只是实用建议，而是基于变更成本曲线的理论推导：在不确定性高的早期，推迟不可逆决策是理性的。

#### 事件驱动架构 (Event-Driven Architecture)

**Martin Fowler 的关键贡献**：他于 2017 年指出"事件驱动"不是一个单一模式，而是四种语义完全不同的模式，容易混淆导致设计错误。

| 模式 | 语义 | 耦合程度 | 典型风险 |
|------|------|---------|---------|
| 事件通知 | "某事已发生"（只携带 ID 和链接） | 最低 | 跨事件的业务流程不显式，难以调试；易将命令伪装成事件 |
| 事件携带状态转移 | "某事已发生，这是变更后的数据" | 中等 | 数据冗余；接收方维护状态的复杂性 |
| 事件溯源 | "状态 = 所有事件的投影" | 最高 | 事件 Schema 演化困难；外部系统交互时回放复杂 |
| CQRS | 读写使用不同模型 | 可变 | 增加系统复杂性，容易被误用 |

**关键区分**：
- **事件 ≠ 命令**：事件表达"已发生的事实"（过去时），命令表达"请执行某操作"（祈使语气）。"请创建订单"是命令，"订单已创建"是事件。
- **事件溯源 ≠ 异步**：事件处理可以是同步的（如 Git 本地操作），不要混淆。
- **事件通知 ≠ 事件溯源**：前者是轻量级通知，后者是完整的状态重建机制，复杂度差一个数量级。

#### Serverless 架构

**约束**：开发者不管理服务器；函数由事件触发、按需执行、有执行时长限制。

**适用条件分析**：

```
┌─────────────────────────────────────────────────┐
│  ✅ 适合 Serverless                              │
│  · 负载突发性大，有明显的波峰波谷                 │
│  · 任务短时、无状态、事件触发                     │
│  · 团队运维能力有限                               │
│  · API 后端、数据处理管道、定时任务               │
├─────────────────────────────────────────────────┤
│  ❌ 不适合 Serverless                             │
│  · 长时间运行的任务（如视频转码 30 分钟）         │
│  · 需要保持有状态的服务（如 WebSocket 长连接）    │
│  · 对延迟极度敏感的实时系统                       │
│  · 需要细粒度控制基础设施的场景                   │
└─────────────────────────────────────────────────┘
```

**关键权衡**：冷启动延迟 vs 按需计费；供应商锁定 vs 运维成本降低。

### 2.3 架构风格选择的决策理论

选择架构风格的本质是**选择一组约束来获得特定收益**，而约束本身有成本。决策框架：

```
┌──────────────────────────────────────────────────────────────┐
│                    架构风格决策框架                             │
│                                                              │
│  Step 1: 识别系统的主要变化维度                               │
│    · 哪些部分变化最频繁？                                     │
│    · 哪些部分最需要独立演进？                                  │
│    · 哪些部分最需要独立扩展？                                  │
│                                                              │
│  Step 2: 评估约束的收益-成本                                  │
│    · 这个约束是否解决了 Step 1 中识别的真正问题？              │
│    · 这个约束的成本（运维、理解、沟通）是否可接受？            │
│    · 如果去掉这个约束，最坏情况是什么？                        │
│                                                              │
│  Step 3: 选择约束最少的风格                                   │
│    · 优先选约束少的风格（单体 > 模块化单体 > 微服务）          │
│    · 只有当约束的收益明确大于成本时才增加约束                  │
│    · 约束应该是被问题驱动的，而不是被趋势驱动的                │
│                                                              │
│  Step 4: 预留演进路径                                        │
│    · 当前选择不应关闭未来选择的门                              │
│    · 模块化单体应该能按模块拆成微服务                          │
│    · 分层架构应该能演进为六边形架构                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**核心原则**：**约束必须被问题驱动，而不是被趋势驱动**。"别人也这样拆"不是选择架构风格的理由。

## 三、依赖理论

### 3.1 依赖的方向与稳定性

依赖关系决定了系统的**变化传播方向**：当 A 依赖 B 时，B 的变化可能波及 A。

**稳定性原则**（来自 Robert C. Martin 的稳定依赖原则 SDP）：

> 依赖的方向应该与稳定性的方向一致——稳定的模块被依赖，不稳定的模块依赖稳定的模块。

```
  正确的依赖方向                  错误的依赖方向

  不稳定                            稳定
    │                                │
    ▼                                ▼
  ┌──────┐  依赖  ┌──────┐       ┌──────┐  依赖  ┌──────┐
  │  UI  │───────>│Domain│       │Domain│───────>│  DB  │
  └──────┘        └──────┘       └──────┘        └──────┘
                        ▲                              │
                        │                              │
                   稳定、不变                      稳定、不变
                   被依赖是安全的                   依赖它是有风险的
                   不会引起连锁变化                 DB 变化会波及核心

  问题：Domain 依赖 DB 意味着
  · 换数据库要改核心逻辑
  · 核心逻辑无法独立测试
  · 业务规则被技术细节绑架
```

### 3.2 依赖倒置原则 (DIP)

**原则**：高层模块不应该依赖低层模块，两者都应该依赖抽象。抽象不应该依赖细节，细节应该依赖抽象。

**DIP 是架构层面最重要的原则之一**——它是六边形架构、整洁架构、洋葱架构等所有"依赖由外向内"架构的理论基石。

```
  没有 DIP：                          有 DIP：

  高层 ──依赖──> 低层                  高层 ──依赖──> 抽象 <──依赖── 低层
  (业务逻辑)    (数据库)               (业务逻辑)   (接口)      (数据库实现)

  高层被低层绑架                       高层定义"我需要什么"（Port）
  换低层 = 改高层                      低层实现"怎么提供"（Adapter）
                                      换低层 = 换 Adapter，高层不变
```

**Port 和 Adapter 的语义**：
- **Port**（端口）：内部定义的接口，表达"我需要什么能力"
- **Adapter**（适配器）：外部的实现，表达"如何对接具体技术"

### 3.3 依赖的度量

可以用以下指标评估依赖的健康程度：

| 指标 | 含义 | 健康方向 |
|------|------|---------|
| 传入耦合 (Afferent Coupling) | 被多少其他模块依赖 | 核心模块应该高（被依赖） |
| 传出耦合 (Efferent Coupling) | 依赖了多少其他模块 | 核心模块应该低（不依赖） |
| 不稳定性 (Instability) | 传出 / (传入 + 传出) | 核心模块应该接近 0（最稳定） |
| 抽象度 (Abstractness) | 抽象类/接口的比例 | 稳定模块应该高抽象 |

**主序列**：抽象度和稳定性之间应该保持平衡——高度稳定的模块应该高度抽象，高度不稳定的模块可以是具体实现。

## 四、一致性理论

### 4.1 一致性的层次

```
┌──────────────────────────────────────────────────────────────┐
│                      一致性层次模型                            │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Level 1: 聚合内一致性（强一致）                        │  │
│  │  · 通过事务保证聚合的不变式                              │  │
│  │  · 聚合根是唯一入口，所有修改必须经过聚合根               │  │
│  │  · 本地事务即可满足                                      │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Level 2: 聚合间一致性（最终一致）                      │  │
│  │  · 跨聚合的操作无法在一个事务中原子完成                   │  │
│  │  · 通过领域事件 + 异步通知实现最终一致性                  │  │
│  │  · 需要设计补偿机制处理失败场景                          │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  Level 3: 跨服务一致性（Saga 模式）                    │  │
│  │  · 每个服务有自己的数据库，无法使用跨库事务               │  │
│  │  · 通过编排或协调的 Saga 模式管理长事务                   │  │
│  │  · 每个步骤有对应的补偿操作                              │  │
│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 CAP 定理与一致性选择

CAP 定理指出：分布式系统最多同时满足以下三项中的两项——一致性 (Consistency)、可用性 (Availability)、分区容错 (Partition tolerance)。由于网络分区是不可避免的，实际选择是在 CP 和 AP 之间。

**但 CAP 定理在架构设计中的实际指导意义有限**——它是关于极端网络分区场景的理论结论，而大多数架构决策发生在日常场景中。更有实践意义的是 **一致性-延迟权衡**：

| 方案 | 一致性 | 延迟 | 可用性 | 复杂度 |
|------|--------|------|--------|--------|
| 两阶段提交 (2PC) | 强一致 | 高（同步等待） | 低（任一参与者故障则整体失败） | 中 |
| Saga (编排式) | 最终一致 | 中（异步补偿） | 高（局部失败可补偿） | 中 |
| Saga (协调式) | 最终一致 | 中（中央协调） | 高 | 高 |
| 事件驱动 + Outbox | 最终一致 | 低（异步解耦） | 最高 | 中 |

### 4.3 Saga 模式的两种形态

```
  编排式 Saga (Choreography)               协调式 Saga (Orchestrator)

  服务A ──事件──> 服务B                   ┌──────────┐
    │                │                     │ Saga     │──命令──> 服务A
    │                │                     │ Orchestr.│<──结果──┘
    │<──事件────────┘                     │          │──命令──> 服务B
    │                                      │          │<──结果──┘
    │                                      └──────────┘
    
  优点：简单、去中心化                      优点：流程显式、容易监控
  缺点：流程隐含在事件链中，                缺点：协调器可能成为单点
        难以理解和调试                            需要额外维护状态机
```

**选择依据**：
- 参与者 ≤ 3 且流程简单 → 编排式
- 参与者 > 3 或流程复杂 → 协调式
- 需要集中监控和审计 → 协调式

### 4.4 Transactional Outbox 模式

**问题**：业务数据写入数据库和事件发布到消息队列无法在同一个事务中原子完成（它们是不同的存储系统）。

**解决方案**：将事件和业务数据写入同一个数据库事务，然后异步将事件从 Outbox 表发布到消息队列。

```
  ┌────────────────────────────────────┐
  │  1. BEGIN TX                       │
  │  2. INSERT 业务数据                 │
  │  3. INSERT 事件到 outbox 表         │  ← 同一事务，原子写入
  │  4. COMMIT TX                      │
  └────────────────────────────────────┘
            │
            │  异步（轮询 / CDC 拖尾）
            ▼
  ┌────────────────────────────────────┐
  │  Message Relay                     │
  │  5. 读取 outbox 中未发布的事件      │
  │  6. 发布到消息队列                  │
  │  7. 标记事件为已发布                │
  └────────────────────────────────────┘
```

**Outbox 模式保证了**：业务数据持久化和事件发布要么同时成功，要么同时失败，消除了"数据写了但事件没发"或"事件发了但数据没写"的不一致场景。

## 五、建模理论

### 5.1 架构建模的目的

架构建模不是画图，而是**建立团队对系统的共享认知**。模型的本质是选择性地忽略细节，使重要的结构和关系得以显现。

**模型的三种用途**：

| 用途 | 关注点 | 读者 | 精度要求 |
|------|--------|------|---------|
| 沟通与对齐 | 系统的边界、组件、关系 | 团队成员、利益相关者 | 中 |
| 决策支持 | 依赖方向、数据流、一致性边界 | 架构师、技术负责人 | 高 |
| 交付规范 | 接口契约、部署拓扑、监控链路 | 开发者、运维 | 最高 |

**关键原则**：**每个模型只解决一个问题**。试图用一张图回答所有问题，结果是什么都看不清。

### 5.2 C4 模型

C4 模型由 Simon Brown 提出，核心思想是**分层抽象**——不同的受众需要不同层次的细节。

```
┌──────────────────────────────────────────────────────────────┐
│                       C4 模型四层                             │
│                                                              │
│  Level 1: System Context                                     │
│  · 问题：系统和谁交互？                                      │
│  · 受众：所有人（包括非技术人员）                             │
│  · 元素：系统 + 外部角色 + 外部系统                           │
│  · 不画：内部结构、技术细节                                   │
│                                                              │
│  Level 2: Container                                          │
│  · 问题：系统内部有哪些独立部署单元？怎么通信？               │
│  · 受众：开发者、运维                                        │
│  · 元素：应用 + 数据库 + 消息队列 + 技术栈标注               │
│  · 不画：模块内部结构                                        │
│                                                              │
│  Level 3: Component                                          │
│  · 问题：一个容器内部的模块怎么划分？依赖方向是什么？         │
│  · 受众：开发者                                              │
│  · 元素：模块 + 接口 + 依赖关系                              │
│  · 不画：类级别的细节                                        │
│                                                              │
│  Level 4: Code                                               │
│  · 问题：类/接口级别的设计                                   │
│  · 受众：开发者                                              │
│  · 通常由 IDE 和代码自描述，不需要单独画图                    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**C4 的核心价值**：不是规定了"画什么图"，而是规定了"什么层级应该忽略什么细节"——这是抽象能力的体现。

### 5.3 领域模型图

**目的**：揭示业务概念的边界和关系，而非技术实现。

**需要表达的要素**：

| 要素 | 表达内容 | 标记方式 |
|------|---------|---------|
| 限界上下文 | 概念的适用边界 | 大框 |
| 聚合 | 一致性边界 | 中框 |
| 聚合根 | 聚合的唯一入口 | 中框内高亮 |
| 实体 | 有独立身份的对象 | 实线小框 |
| 值对象 | 通过值区分的不可变对象 | 虚线小框 |
| 上下文间关系 | 防腐层 / 开放主机 / 事件 / API | 箭头 + 标注 |

**上下文映射的关系模式**（来自 Eric Evans 和 Vaughn Vernon）：

| 关系模式 | 语义 | 适用场景 |
|---------|------|---------|
| 防腐层 (ACL) | 下游隔离上游模型，保护自身纯净 | 上游模型不稳定或与下游概念不匹配 |
| 开放主机服务 (OHS) | 上游提供标准化的服务协议 | 上游被多个下游依赖 |
| 已发布语言 (PL) | 用共享协议/格式作为公共语言 | 跨团队需要稳定的集成契约 |
| 共享内核 (SK) | 多个上下文共享一小部分稳定模型 | 概念高度重合且变更极少 |
| 客户-供应商 (C/S) | 上游根据下游需求提供能力 | 下游需求优先级高 |
| 遵奉者 (Conformist) | 下游直接采用上游模型 | 适配成本高于遵从成本 |
| 各走各路 (SW) | 上下文独立，不建立集成 | 集成的收益低于成本 |

### 5.4 数据流图

**目的**：揭示数据的所有权、读写路径和变更传播方式。

**需要回答的问题**：
- 数据从哪来？到哪去？
- 谁拥有数据的写入权？谁只有读取权？
- 数据变更是同步传播还是异步传播？
- 数据变更失败时如何补偿？

**关键原则**：**每份数据有且只有一个写入者**（Single Writer Principle）。多个服务对同一份数据的写入是分布式系统中最危险的耦合。

### 5.5 状态机图

**目的**：揭示业务对象的生命周期，特别是状态间的合法转换和异常路径。

**设计要点**：
- 每个状态是独立节点
- 箭头标注触发条件
- 终态要有明确标记
- **异常/回退路径必须画出**（这些是最容易出 bug 的地方）
- 状态转换的守卫条件要明确

**与 DDD 的关系**：聚合根的核心职责之一就是保证状态转换的合法性——状态机是聚合根不变式的形式化表达。

### 5.6 依赖方向图

**目的**：揭示模块间的耦合关系，判断核心逻辑是否被外部依赖绑架。

**评估标准**：
- 核心业务模块的传出依赖是否为零？
- 依赖方向是否与稳定性方向一致？
- 是否存在循环依赖？
- 是否存在对具体实现的直接依赖（而非对抽象的依赖）？

## 六、演进理论

### 6.1 架构的演进性

演进性 (Evolvability) 不是架构的可选属性，而是**第一优先级**——因为软件系统的本质是持续变化的。

**演进性的两个维度**：

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  维度 1: 当前的可修改性                                     │
│  · 新增一个业务能力需要改多少模块？                          │
│  · 修改一个业务规则的影响范围是否可控？                      │
│  · 是否存在"牵一发动全身"的紧耦合区域？                     │
│                                                             │
│  维度 2: 未来的可迁移性                                     │
│  · 替换数据库 / MQ / 框架时核心业务是否受影响？              │
│  · 团队扩大 2 倍后边界是否仍能支撑协作？                    │
│  · 从单体拆分为微服务是否可行？成本多高？                   │
│                                                             │
│  两个维度都需要通过"边界 + 依赖方向"来保证                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 演进的路径依赖

架构决策具有路径依赖性——早期的决策会限制后期的选择空间。

**关键原则**：**推迟不可逆决策**（Last Responsible Moment）。

```
  决策的不可逆程度：

  ┌──────────────────────────────────────────────────────┐
  │  高可逆 (随时可改)                                    │
  │  · 具体算法实现                                       │
  │  · UI 布局                                           │
  │  · 缓存策略                                          │
  │  · 框架版本                                          │
  ├──────────────────────────────────────────────────────┤
  │  中等可逆 (改造成本中等)                              │
  │  · 数据库选型                                        │
  │  · 消息队列选型                                      │
  │  · 服务间通信协议                                    │
  ├──────────────────────────────────────────────────────┤
  │  低可逆 (改造成本极高)                                │
  │  · 系统边界划分                                      │
  │  · 依赖方向                                          │
  │  · 数据所有权                                        │
  │  · 统一语言                                          │
  └──────────────────────────────────────────────────────┘
  
  策略：
  · 高可逆决策 → 快速决定，边做边调
  · 中等可逆决策 → 通过端口/适配器隔离，降低切换成本
  · 低可逆决策 → 充分思考，尽早确定，用 ADR 记录
```

### 6.3 推荐的演进路线

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  Phase 1: 模块化单体                                         │
│  ─────────────────                                           │
│  · 内部按限界上下文分模块                                    │
│  · 每个模块有自己的 domain / app / infrastructure            │
│  · 模块间通过接口/事件通信                                   │
│  · 逻辑隔离数据库 schema                                     │
│  · 一个部署单元                                              │
│                                                              │
│  Phase 2: 按需拆分                                           │
│  ────────────────                                            │
│  · 当部署冲突频繁时，拆出变化最频繁的模块                     │
│  · 当团队扩大时，按团队边界拆分                              │
│  · 当性能瓶颈明确时，拆出需要独立扩展的模块                   │
│  · 每次只拆一个模块，不要一次性全拆                          │
│                                                              │
│  Phase 3: 持续优化                                           │
│  ────────────────                                            │
│  · 根据实际运行数据调整服务边界                              │
│  · 引入 CQRS / ES 只在真正需要的上下文                       │
│  · 优化部署和运维自动化                                      │
│                                                              │
│  演进触发条件：                                              │
│  · 团队规模 > 15 人                                         │
│  · 部署冲突频率 > 每周 2 次                                  │
│  · 某个模块的 QPS 与整体差距 > 10 倍                        │
│  · 某个模块的发布频率与整体差距 > 5 倍                      │
│                                                              │
│  注意：这些是参考阈值，不是硬性标准。                        │
│  真正的触发条件应该是"当前架构的痛苦程度"而非数字。           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 七、决策理论

### 7.1 架构决策记录 (ADR)

ADR (Architecture Decision Record) 由 Michael Nygard 提出，是记录重要架构决策的标准方法。

**ADR 的核心价值**：
- **减少重复决策**：新团队成员可以理解"当时为什么这样选"
- **减少返工**：避免"遗忘历史而重新论证已否决的方案"
- **建立问责**：决策是可追溯的，而非"一直就是这样"

**ADR 模板**：

```markdown
# ADR-NNN: [决策标题]

## 状态
[提议 | 已接受 | 已废弃 | 已替代]

## 背景
[描述问题、约束和驱动力。不是"描述决策"，而是"描述为什么需要做决策"]

## 决策
[描述做出的决策。简洁明确]

## 备选方案
[列出考虑过的其他方案及各自的优缺点]

## 取舍
- 收益：这个决策带来了什么好处
- 成本：这个决策需要付出什么代价

## 后果
[这个决策带来的正面和负面影响。包括对团队、运维、未来演进的影响]
```

**ADR 的使用原则**：
- 只记录**重要的、难以逆转的**决策，不需要记录日常决策
- 备选方案和取舍是 ADR 最有价值的部分——它记录了"为什么不选那个"
- ADR 一旦写定就不再修改，如果决策被替代，写新的 ADR 并标注替代关系

## 八、反模式理论

### 8.1 反模式的本质

反模式 (Anti-Pattern) 是"看起来合理但实际有害"的模式。理解反模式比学习模式更重要——因为模式告诉你"怎么做对"，而反模式告诉你"为什么会错"。

### 8.2 核心反模式

| 反模式 | 根因 | 正确理解 |
|--------|------|---------|
| **简历驱动架构** | 用技术时髦度而非问题驱动决策 | 先有痛点再选方案，技术选型是手段不是目的 |
| **过早微服务** | 混淆了"最终形态"和"起步形态" | 微服务是演进的结果，不是起点 |
| **分布式单体** | 拆了服务但共享数据库 | 数据耦合是最强的耦合；Database per Service 是微服务的前提 |
| **全局 CQRS** | 没有局部复杂度就全局引入 | CQRS 只应在确实需要时用于特定上下文 |
| **忽视康威定律** | 架构与团队协作方式不匹配 | 架构边界应对齐团队边界 |
| **层泄漏** | 业务逻辑出现在 Controller/DAO | 分层不只是目录结构，而是职责隔离 |
| **万能 common 模块** | 什么都往 common 里塞 | common 应极薄，只放工具类和通用接口定义 |
| **事件伪装命令** | "请创建订单"伪装成事件 | 命令表达意图（祈使语气），事件表达事实（过去时） |
| **过度抽象** | 为假想的未来变化建立抽象 | 抽象应该由当前需求驱动，而非想象中的未来 |
| **技术驱动的边界** | 按技术层（UI/Service/DAO）而非业务划分 | 业务边界比技术边界更稳定 |

### 8.3 反模式的共性

所有反模式的共性可以归结为一个根本原因：**将手段当作目的**。

- 微服务是手段，业务解耦是目的
- DDD 是手段，领域理解是目的
- 事件驱动是手段，降低耦合是目的
- 技术选型是手段，解决问题是目的

**检验方法**：对于每一个架构决策，问自己——"如果去掉这个技术/模式，我解决的那个问题是否还存在？如果不存在，说明这个技术/模式是在解决一个不存在的问题。"

## 九、架构设计原则体系

### 9.1 原则的层次

架构设计原则不是平面的列表，而是有层次的体系：

```
┌──────────────────────────────────────────────────────────────┐
│                    设计原则的层次体系                          │
│                                                              │
│  第一层：元原则（指导其他原则的原则）                         │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  · 关注点分离 (SoC) — 所有其他原则的基础               │  │
│  │  · 最小知识 (LoD) — 减少不必要的耦合                   │  │
│  │  · 高内聚低耦合 — 模块设计的黄金标准                   │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  第二层：结构原则（指导模块间关系的原则）                     │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  · 单一职责 (SRP) — 一个模块只有一个变化原因           │  │
│  │  · 开闭原则 (OCP) — 对扩展开放，对修改关闭             │  │
│  │  · 依赖倒置 (DIP) — 依赖抽象而非实现                   │  │
│  │  · 接口隔离 (ISP) — 不应被迫依赖不需要的接口           │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  第三层：行为原则（指导模块内部设计的原则）                   │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  · 里氏替换 (LSP) — 子类型必须能替换基类型             │  │
│  │  · 命令查询分离 (CQS) — 修改状态和查询状态分离         │  │
│  │  · 不可变性 — 优先使用不可变数据结构                   │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  第四层：经济原则（指导决策的原则）                           │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  · YAGNI — 不做目前不需要的                             │  │
│  │  · KISS — 保持简单                                     │  │
│  │  · DRY — 不重复                                        │  │
│  │  · 推迟不可逆决策 — Last Responsible Moment             │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 9.2 原则之间的张力

原则之间不是总是一致的，它们之间存在张力：

| 张力对 | 冲突点 | 解决思路 |
|--------|--------|---------|
| DRY vs SRP | 两个不同职责的模块有相似的代码 | 如果变化原因不同，重复好于错误的耦合 |
| YAGNI vs OCP | 为未来扩展留接口 vs 不做目前不需要的 | 只为**可预见且成本可控**的扩展留接口 |
| KISS vs DIP | 引入接口增加间接层 vs 保持简单 | 核心边界用 DIP，内部实现用 KISS |
| SRP vs 内聚 | 过度拆分导致模块碎片化 | SRP 的"职责"应理解为"变化原因"而非"功能点" |

**核心洞见**：原则不是规则，而是方向。真正的架构能力体现在**知道何时违背原则**，而不是机械地遵循所有原则。

## 十、架构设计交付物

### 10.1 交付物体系

架构设计完成后，交付的文档不是"写完了事"的形式主义，而是**团队对系统的共享认知载体**。文档的价值在于：让未参与设计的人能理解"为什么这样设计"，让未来的自己能回溯决策上下文。

```
┌──────────────────────────────────────────────────────────────┐
│                    架构设计交付物体系                          │
│                                                              │
│  必选（任何项目都必须产出）                                   │
│  ──────────────────────                                      │
│  ① 架构决策记录 (ADR)                                       │
│  ② 系统上下文图                                              │
│  ③ 容器/部署图                                               │
│  ④ 接口契约文档                                              │
│                                                              │
│  按需（根据项目复杂度选择）                                   │
│  ──────────────────────                                      │
│  ⑤ 领域模型文档                                              │
│  ⑥ 数据流与一致性文档                                        │
│  ⑦ 状态机文档                                                │
│  ⑧ 横切能力设计文档                                          │
│  ⑨ 运维与部署文档                                            │
│  ⑩ 演进路线文档                                              │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 10.2 ① 架构决策记录 (ADR)

**定位**：记录重要的、难以逆转的决策及其推理过程。ADR 是所有交付物中**信息密度最高**的文档。

```
┌──────────────────────────────────────────────────────────────┐
│  ADR 文档结构                                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 编号与标题                                               │
│     · 格式：ADR-NNN: 简明标题                                │
│     · 标题应表达决策内容而非问题                              │
│     · 例：ADR-001 采用模块化单体而非微服务 ✅                 │
│         ADR-001 架构选型 ❌（太模糊）                        │
│                                                              │
│  2. 状态                                                     │
│     · 提议 → 已接受 → 已废弃 / 已替代                       │
│     · 状态变更是文档的一部分，反映决策的生命周期              │
│                                                              │
│  3. 背景                                                     │
│     · 描述问题、约束和驱动力                                 │
│     · 不描述决策本身，而是"为什么需要做这个决策"             │
│     · 包含技术约束、业务约束、团队约束                       │
│                                                              │
│  4. 决策                                                     │
│     · 简洁明确地描述决策内容                                 │
│     · 避免模糊表述，应可被直接执行                           │
│                                                              │
│  5. 备选方案                                                 │
│     · 列出所有认真考虑过的方案                               │
│     · 每个方案的优缺点                                       │
│     · 这是 ADR 最有价值的部分——记录了"为什么不选那个"       │
│                                                              │
│  6. 取舍                                                     │
│     · 收益：这个决策带来了什么好处                           │
│     · 成本：这个决策需要付出什么代价                         │
│                                                              │
│  7. 后果                                                     │
│     · 对团队、运维、未来演进的影响                           │
│     · 正面和负面影响都要写                                   │
│     · 后果是不可撤销的——即使决策被替代，后果已经发生        │
│                                                              │
│  使用规则：                                                  │
│  · 只记录重要的、难以逆转的决策                              │
│  · 写定后不再修改；被替代时写新 ADR 并标注替代关系           │
│  · 放在代码仓库中，与代码一起版本管理                        │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```


## 十一、总结

### 架构设计的本质

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  架构设计的本质是：                                           │
│                                                              │
│  ① 识别约束 — 哪些是不能变的，哪些是可以变的                  │
│  ② 选择边界 — 在哪里划分模块/服务/上下文                     │
│  ③ 控制方向 — 依赖朝哪走，数据归谁管                         │
│  ④ 管理变化 — 哪些维度需要容易修改，哪些需要稳定              │
│  ⑤ 记录决策 — 为什么这样选，不那样选                         │
│                                                              │
│  贯穿始终的核心原则：                                         │
│                                                              │
│  · 约束必须被问题驱动，而非趋势驱动                          │
│  · 推迟不可逆决策，保留演进空间                               │
│  · 简单性是特性，不是缺陷                                    │
│  · 架构应该尖叫出系统的意图                                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

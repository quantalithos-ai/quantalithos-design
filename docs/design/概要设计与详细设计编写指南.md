# 概要设计与详细设计编写指南

> 设计文档的价值不在于"写完了"，而在于"想清楚了"。
> 概要设计回答 **"为什么这样做、做什么"**，详细设计回答 **"具体怎么做"**。
> 两层文档形成漏斗：上层收束方向，下层展开实现。

---

## 一、设计文档的本质与价值

### 1.1 为什么要写设计文档

设计文档不是流程产物，而是工程决策的载体。它的核心价值：

```
┌───────────────────────────────────────────────────────────────┐
│                    设计文档的五大价值                            │
├───────────────────────────────────────────────────────────────┤
│                                                               │
│  ① 提前发现问题 — 编码前修改成本远低于编码后                     │
│                                                               │
│  ② 形成共识 — 让团队对方案和边界有一致理解                       │
│                                                               │
│  ③ 知识传承 — 新人 / 后继者能理解"为什么这样设计"               │
│                                                               │
│  ④ 约束范围 — 防止需求蔓延和实现偏离                            │
│                                                               │
│  ⑤ 可追溯 — 架构决策有据可查，方便回溯与复盘                    │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

### 1.2 概要设计 vs 详细设计的分工

```
                     设计文档层次
          ┌─────────────────────────────┐
          │                             │
          │    概要设计 (High-Level)     │    回答：做什么、为什么这样做
          │    ─────────────────────    │
          │    · 系统边界与上下文        │
          │    · 架构风格与选型          │
          │    · 模块划分与职责          │
          │    · 关键接口与数据流        │
          │    · 备选方案与取舍          │
          │    · 质量目标与约束          │
          │                             │
          ├─────────────────────────────┤
          │                             │
          │    详细设计 (Detailed)       │    回答：具体怎么做（能直接编码）
          │    ─────────────────────    │
          │    · 代码目录结构            │
          │    · 结构体定义与字段说明    │
          │    · 接口契约（入参/出参）    │
          │    · 关键函数伪代码          │
          │    · 数据结构与表设计        │
          │    · 核心流程与时序          │
          │    · 异常处理与容错          │
          │    · 部署与运维细节          │
          │                             │
          └─────────────────────────────┘

    输入 → 需求文档、业务流程     输入 → 概要设计、技术约束
    输出 → 架构图、模块职责       输出 → 接口定义、流程图、表结构
```

### 1.3 什么时候该写 / 不该写

| 场景 | 建议 |
|------|------|
| 新系统或重大重构 | **必写**概要 + 详细 |
| 新模块 / 新服务 | 写概要，详细视复杂度 |
| 小功能迭代（1~2 天） | 可写 1~3 页迷你设计文档 |
| Bug 修复 / 配置变更 | **不需要**设计文档 |
| 探索性原型 | 先原型，后补文档，原型本身是设计验证 |

> **经验法则**：如果方案的实现路径不唯一、涉及跨团队协作、或失败代价较高，就应该写设计文档。

## 二、概要设计

### 2.1 概要设计的目标

概要设计要解决三个核心问题：

1. **系统边界**：这个系统是什么、不是什么、和谁交互
2. **架构方向**：选什么架构风格、怎么拆模块、关键技术选型
3. **取舍依据**：为什么选 A 不选 B，做了哪些权衡

### 2.2 概要设计必须包含的模块

```
┌─────────────────────────────────────────────────────────────┐
│                   概要设计文档结构                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 文档元信息                                               │
│     - 标题 / 作者 / 日期 / 评审人 / 状态                     │
│     - 版本号与变更记录                                       │
│     - 读码导航路径（推荐）                                    │
│                                                             │
│  2. 背景与问题定义                                           │
│     - 业务背景、问题现状、为什么要做                           │
│                                                             │
│  3. 目标与非目标                                             │
│     - 目标：本次要达成什么                                    │
│     - 非目标：明确不在本次范围内的事项                         │
│                                                             │
│  4. 约束条件                                                 │
│     - 技术约束、资源约束、时间约束、合规约束                   │
│     - 容量规划：单实例内存/CPU/连接数上限                      │
│                                                             │
│  5. 系统上下文与边界                                         │
│     - 系统上下文图（谁和谁交互）                              │
│     - 系统边界定义                                           │
│                                                             │
│  6. 总体架构设计                                             │
│     - 架构风格与分层                                         │
│     - 模块划分与职责                                         │
│     - 模块依赖关系                                           │
│     - 层间约束规则（防退化）                                  │
│                                                             │
│  7. 关键技术选型                                             │
│     - 决策四元组：当前选择 + 备选 + 理由 + 演进路径            │
│                                                             │
│  8. 备选方案与取舍                                           │
│     - 至少 2~3 个备选                                        │
│     - 各方案的优劣势与选择理由                                │
│                                                             │
│  9. 关键接口与数据流概览                                     │
│     - 核心接口列表（不写细节，写边界）                        │
│     - 核心数据流向（至少一条路径精确到函数调用链）             │
│                                                             │
│  10. 横切关注点                                             │
│     - 安全 / 性能 / 可用性 / 可观测性 / 成本                  │
│     - 性能预算表（端到端延迟分解）                             │
│                                                             │
│  11. 风险与待确认事项                                        │
│     - 已知风险、缓解策略、待确认问题                          │
│     - 异常场景分「常见」和「边缘」两层                         │
│                                                             │
│  12. 上线策略                                               │
│     - 灰度方案、回滚策略、监控指标                            │
│                                                             │
│  13. 需求追溯矩阵                                           │
│     - 需求 ID ↔ 概要设计章节 ↔ 详细设计章节 ↔ 测试场景       │
│                                                             │
│  14. ADR 索引（可选）                                       │
│     - 关键架构决策的 ADR 链接                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 概要设计的输入与输出

| 维度 | 输入材料 | 输出内容 |
|------|---------|---------|
| 业务 | 需求文档 / PRD / 用户故事 | 目标与非目标、问题定义 |
| 架构 | 现有系统架构文档、技术栈规范 | 系统上下文图、架构图、模块划分 |
| 约束 | 时间线、人力、成本预算 | 约束条件、容量规划、备选方案取舍 |
| 依赖 | 外部系统接口文档、SDK 文档 | 关键接口概览、数据流图 |
| 风险 | 历史事故报告、安全规范 | 风险清单、异常场景、横切关注点、上线策略 |
| 需求 | 非功能需求（含量化指标与来源） | 性能预算表、需求追溯矩阵 |

#### 示例：模块划分与层间约束

```
order-service/
│
├── order-api/          # 对外接口层：REST / 消息消费
├── order-domain/       # 领域层：订单聚合根、领域服务
├── order-infra/        # 基础设施层：DB / MQ / 缓存
└── order-application/  # 应用层：编排、事务协调

层间约束：
  · api 层只做参数校验和响应组装，不含业务逻辑
  · domain 层不直接依赖 infra 层（通过接口倒置）
  · infra 层不调用 application 层
```

#### 示例：关键技术选型（决策四元组）

| 决策点 | 当前选择 | 备选方案 | 选择理由 | 演进路径 |
|--------|---------|---------|---------|----------|
| 下单模式 | 混合模式 | A: 同步 / B: 异步 | 核心链路强一致 + 非核心异步，平衡一致性与吞吐 | — |
| 消息队列 | RocketMQ | Kafka / RabbitMQ | 事务消息原生支持，适合订单场景 | 若需流处理可引入 Kafka |
| 缓存 | Redis Cluster | 本地缓存 / Memcached | 分布式、高可用、丰富数据结构 | 热点数据可加本地缓存 |

#### 示例：备选方案与取舍

| 维度 | 方案 A：同步下单 | 方案 B：异步下单 | 方案 C：混合模式 |
|------|-----------------|-----------------|-----------------|
| 一致性 | 强一致 | 最终一致 | 核心链路强一致 + 非核心异步 |
| 吞吐量 | 低（锁竞争） | 高 | 中 |
| 复杂度 | 低 | 中（需补偿） | 高 |
| 选择 | ✗ | ✗ | **✓** — 平衡一致性与吞吐 |

> 本项目选择方案 C：核心下单链路（库存扣减 + 订单创建）同步保证一致，通知、积分等异步处理。

#### 示例：数据流概览（精确到函数级）

```
1. 创建订单主路径
   OrderController.createOrder()
   └─→ OrderAppService.createOrder()    — 编排：校验 → 锁库存 → 计价 → 持久化
       └─→ StockProxy.deduct()           — 调用库存服务预扣
       └─→ OrderDomain.create()          — 领域逻辑（计算金额、生成订单号）
       └─→ OrderRepo.save()              — 写入 DB
```

#### 示例：性能预算表

| 环节 | 预估延迟 | 依据 |
|------|---------|------|
| 网关路由 → Controller | ~2ms | 内网 RTT + 框架开销 |
| 库存预扣（RPC） | ~5ms | 库存服务 P99 |
| 计价 + 领域逻辑 | ~1ms | 纯内存计算 |
| DB 写入 | ~3ms | MySQL 单行写入 |
| **总延迟（P99）** | **< 15ms** | 非功能需求 ORD-NF01 |

## 三、详细设计

### 3.1 详细设计的目标

详细设计的核心目标是**让开发者能够不看代码就能完成编码**。为此，它要解决五个核心问题：

1. **代码骨架**：目录结构怎么组织、源文件怎么划分
2. **数据结构**：每个结构体怎么定义、每个成员变量做什么
3. **接口契约**：每个模块对外暴露什么、依赖什么
4. **实现逻辑**：关键函数内部怎么走、伪代码怎么写
5. **流程与异常**：正常流程怎么走、异常怎么处理、边界条件

> **详细设计的终极检验标准**：一个没有参与过该项目的开发者，仅凭概要设计 + 详细设计，能否直接编写出与设计意图一致的代码？如果不能，说明详细设计还不够细。

```
注意：详细设计超过 1500 行时，应按模块拆分为子文档，每份独立可读。
```

### 3.3 详细设计的输入与输出

| 维度 | 输入材料 | 输出内容 |
|------|---------|---------|
| 架构 | 概要设计文档 | 代码目录结构、模块内部结构、依赖关系 |
| 数据 | 领域模型、业务规则 | 结构体定义、表结构、缓存结构、数据流 |
| 接口 | 外部系统 API 文档、协议规范 | 接口契约定义（含前置/后置条件） |
| 逻辑 | 业务规则、算法描述 | 关键函数伪代码、核心流程 |
| 流程 | 业务流程图、状态定义 | 时序图、状态机、异常处理 |
| 运维 | 基础设施规范、SLO | 部署图、配置项（含五要素）、监控指标、告警规则 |

```java
// Order.java — 订单聚合根
// ═══════════════════════════════════════════════════

public class Order {
    String      orderId;       // 订单唯一ID，格式: ORD + 时间戳 + 4位随机数
    String      userId;        // 下单用户ID，关联用户服务
    OrderStatus status;        // 订单当前状态，参见 OrderStatus 枚举
    List<OrderItem> items;     // 订单行项列表，1~50 个
    long        totalAmount;   // 订单总金额（分），由领域服务计算
    long        discountAmount;// 优惠金额（分），初始0，使用优惠券后更新
    String      addressId;     // 收货地址ID，关联地址服务
    String      couponId;      // 使用的优惠券ID，可为null
    LocalDateTime createdAt;   // 创建时间，自动填充
    LocalDateTime updatedAt;   // 最后更新时间，状态变更时自动更新
    int         version;       // 乐观锁版本号，每次更新 +1，防并发修改
}

// ═══════════════════════════════════════════════════
// OrderItem.java — 订单行项值对象
// ═══════════════════════════════════════════════════

public class OrderItem {
    String  skuId;       // 商品SKU ID，关联商品服务
    String  skuName;     // 商品名称（冗余，防止商品改名后不可追溯）
    int     quantity;    // 购买数量，>= 1
    long    unitPrice;   // 单价（分），下单时快照，不随商品价格变动
    long    subtotal;    // 小计 = unitPrice × quantity
}

// ═══════════════════════════════════════════════════
// OrderStatus.java — 订单状态枚举
// ═══════════════════════════════════════════════════

public enum OrderStatus {
    CREATED,     // 已创建，等待支付
    PAID,        // 已支付，等待发货
    SHIPPED,     // 已发货，等待确认收货
    COMPLETED,   // 已完成
    CANCELLED,   // 已取消（超时未支付 / 主动取消）
    REFUNDED     // 已退款
}
```

#### 示例：关键函数伪代码

```pseudocode
// ═══════════════════════════════════════════════════
// OrderAppService.createOrder — 创建订单主流程
// ═══════════════════════════════════════════════════

function createOrder(cmd: CreateOrderCmd) -> CreateOrderResult:

    // 1. 幂等检查
    fingerprint = md5(cmd.userId + cmd.items.hash() + cmd.addressId)
    if redis.exists("order_fp:" + fingerprint, TTL=5s):
        return existingOrder(fingerprint)

    // 2. 参数校验
    if cmd.items.isEmpty() or cmd.items.size() > MAX_ITEMS:
        return error(INVALID_PARAM)

    // 3. 商品信息查询与快照
    skus = batchQuerySku(cmd.items.map(i -> i.skuId))   // 批量查商品
    for item in cmd.items:
        if skus[item.skuId].status != ON_SALE:
            return error(ORDER_004, item.skuId)
        item.unitPrice = skus[item.skuId].price          // 价格快照
        item.subtotal = item.unitPrice * item.quantity

    // 4. 库存预扣（关键路径，可能失败）
    deductResult = stockProxy.deduct(cmd.items)           // RPC 调用
    if deductResult.failed:
        return error(ORDER_001)                           // 可恢复：库存不足

    try:
        // 5. 计价
        totalAmount = sum(item.subtotal for item in cmd.items)
        discountAmount = 0
        if cmd.couponId != null:
            coupon = couponProxy.validate(cmd.couponId, totalAmount)
            if coupon.invalid:
                return error(ORDER_002)                   // 可恢复：优惠券不可用
            discountAmount = coupon.discount

        // 6. 创建 Order 聚合根
        order = Order(
            orderId  = generateOrderId(),                 // ORD + timestamp + random
            userId   = cmd.userId,
            status   = CREATED,
            items    = cmd.items,
            totalAmount    = totalAmount,
            discountAmount = discountAmount,
            addressId = cmd.addressId,
            couponId  = cmd.couponId,
            version   = 0
        )

        // 7. 持久化
        orderRepo.save(order)                             // 乐观锁写入

        // 8. 发送领域事件（异步）
        eventPublisher.publish(OrderCreatedEvent(order))

        // 9. 写入幂等键
        redis.set("order_fp:" + fingerprint, order.orderId, TTL=5s)

        return CreateOrderResult(order.orderId, order.totalAmount)

    catch Exception:
        // 补偿：释放预扣库存
        stockProxy.release(cmd.items)
        return error(SYSTEM_ERROR)                        // 不可恢复


// ═══════════════════════════════════════════════════
// Order.transition — 订单状态转换
// ═══════════════════════════════════════════════════

function transition(order: Order, newStatus: OrderStatus, reason: String):
    legalTransitions = {
        CREATED    -> [PAID, CANCELLED],
        PAID       -> [SHIPPED, REFUNDED],
        SHIPPED    -> [COMPLETED, REFUNDED],
        COMPLETED  -> [REFUNDED],
        CANCELLED  -> [],           // 终态
        REFUNDED   -> []            // 终态
    }

    if newStatus not in legalTransitions[order.status]:
        log WARN "非法状态转换: {order.status} -> {newStatus}, orderId={order.orderId}"
        return false                                     // 状态不变，不崩溃

    order.status = newStatus
    order.updatedAt = now()
    order.version += 1
    log INFO "订单状态变更: {order.orderId} -> {newStatus}, 原因={reason}"
    return true
```

> **伪代码写作要点**：
> - 用自然语言 + 代码混合写，不需要严格语法正确，但逻辑必须精确
> - 每个分支都要写清楚走向（包括 return / throw / continue）
> - try-catch 的补偿逻辑必须写出来
> - 标注关键性能路径（如上面的 RPC 调用、批量查询）
> - 状态转换函数应列出完整的合法转换矩阵

#### 示例：异常处理策略

| 异常场景 | 处理策略 | 幂等保障 | 分层 |
|---------|---------|---------|------|
| 库存预扣失败 | 返回 ORDER_001，不创建订单 | 自然幂等 | 常见 |
| 支付超时 | 查询支付状态，未支付则关闭订单释放库存 | 订单号做幂等键 | 常见 |
| 重复提交 | 同一用户 5s 内相同请求返回原订单号 | 请求指纹去重 | 常见 |
| 下游服务不可用 | 快速失败 + 告警，不自动重试 | — | 常见 |
| DB 连接池耗尽 | 拒绝新请求 + 告警 | — | 边缘 |
| 分布式锁超时 | 释放锁 + 回滚 + 告警 | — | 边缘 |

```sql
-- 数据所有权：订单服务（唯写方）
-- 读方：支付服务、通知服务、管理后台
-- ═══════════════════════════════════════════════════

CREATE TABLE t_order (
    order_id        VARCHAR(32)   NOT NULL COMMENT '订单ID，格式 ORD+timestamp+4位随机',
    user_id         VARCHAR(32)   NOT NULL COMMENT '用户ID',
    status          TINYINT       NOT NULL DEFAULT 0 COMMENT '0=CREATED, 1=PAID, 2=SHIPPED, 3=COMPLETED, 4=CANCELLED, 5=REFUNDED',
    total_amount    BIGINT        NOT NULL DEFAULT 0 COMMENT '总金额（分）',
    discount_amount BIGINT        NOT NULL DEFAULT 0 COMMENT '优惠金额（分）',
    pay_amount      BIGINT        NOT NULL DEFAULT 0 COMMENT '实付金额（分）= total - discount',
    address_id      VARCHAR(32)   NOT NULL COMMENT '收货地址ID',
    coupon_id       VARCHAR(32)   NULL     COMMENT '优惠券ID，可为空',
    version         INT           NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    created_at      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at      DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    PRIMARY KEY (order_id),
    INDEX idx_user_created (user_id, created_at),    -- 用户订单列表查询
    INDEX idx_status_created (status, created_at),    -- 按状态扫描（超时关单）
    INDEX idx_created_timeout (created_at)            -- 超时关单定时扫描
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单主表';

-- ═══════════════════════════════════════════════════
-- 订单行项表
-- 数据所有权：订单服务（唯写方）
-- ═══════════════════════════════════════════════════

CREATE TABLE t_order_item (
    id              BIGINT        AUTO_INCREMENT,

    sku_name        VARCHAR(128)  NOT NULL COMMENT '商品名称快照',
    quantity        INT           NOT NULL DEFAULT 1 COMMENT '购买数量 >= 1',
    unit_price      BIGINT        NOT NULL COMMENT '单价快照（分）',

    PRIMARY KEY (id),
```

#### 示例：并发与一致性设计

```
┌──────────────────────────────────────────────────────────────┐
│  并发与一致性分析                                             │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  场景 1：同一用户同时提交两个创建订单请求                     │
│  ──────────────────────────────────────────                  │
│  风险：重复创建订单                                           │
│  方案：幂等指纹去重（Redis SETNX + TTL=5s）                  │
│  实现：createOrder 入口处计算 fingerprint，                  │
│        SETNX 成功才继续，失败返回已有订单号                  │
│                                                              │
│  场景 2：订单支付回调与超时关单并发                           │
│  ──────────────────────────────────────────                  │
│  风险：支付成功但订单已被超时关单                             │
│  方案：                                                      │
│  a. 乐观锁（version 字段）：更新时 WHERE version = ?         │
│  b. 状态前置检查：关单时先查支付状态，                       │
│     支付中则跳过关单                                         │
│  c. 补偿：支付回调发现订单已关闭，触发人工确认流程           │
│                                                              │
│  场景 3：库存预扣与释放的竞态                                │
│  ──────────────────────────────────────────                  │
│  风险：释放库存后，另一个请求预扣了刚释放的库存              │
│  这是正常行为（库存本就该被其他用户抢到）                    │
│  无需额外处理                                                │
│                                                              │
│  场景 4：同一订单的多次状态变更（支付+退款同时到达）         │
│  ──────────────────────────────────────────                  │
│  风险：状态回退（PAID → REFUNDED 和 PAID → SHIPPED 冲突）   │
│  方案：                                                      │
│  a. 乐观锁 + 状态机：transition 函数原子检查合法性           │
│  b. 先到的请求成功，后到的请求因 version 不匹配而失败        │
│  c. 失败的请求记录 WARN 日志，不重试                        │
│                                                              │
│  事务边界：                                                   │
│  ──────────                                                  │
│  · createOrder: 本地事务（写 Order + OrderItem + StatusLog）│
│  · 库存预扣: RPC 调用，不在本地事务内                        │
│  · 预扣失败补偿: 本地事务回滚 + 释放库存（最终一致性）      │
│  · 隔离级别: READ_COMMITTED（避免脏读，允许不可重复读）      │
│                                                              │
│  例外分析（声明模型之外）：                                   │
│  ────────────────────────                                    │
│  Java memory model 下 Order.status 无需 volatile，           │
│  因为所有读写都经过 DB（乐观锁），不依赖内存可见性。          │
│  但如果引入本地缓存，则需考虑缓存一致性。                    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 四、ASCII 架构图与流程图绘制指南

> 图是设计文档的核心载体。一张好图的价值远超千字描述——但前提是图画到了正确的深度。
> 本章不是教"怎么画图"，而是教"画到什么程度"、"该画什么不该画什么"。

### 4.1 系统上下文图（C4 Context 级）

#### 理论定位

系统上下文图回答的是**"这个系统和谁交互"**，它是所有读者——包括非技术人员——理解系统的第一入口。它的核心价值不是展示内部结构，而是**划定边界**：系统是什么、系统不是什么、系统依赖谁、谁依赖系统。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  系统上下文图的深度标尺                                       │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足（缺少关键信息）：                                   │
│  ────────────────────────                                    │
│  ✗ 只画了系统名称和几个外部角色，没有标注交互意图             │
│  ✗ 外部系统只写了名字，没有区分"内部系统"和"第三方系统"     │
│  ✗ 连线上没有标注通信协议或语义                              │
│  ✗ 漏掉了间接依赖（如通过消息队列消费的系统）                │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 每条连线标注交互意图（如"查询库存"、"发送支付请求"）     │
│  ✓ 区分人员角色与外部系统                                    │
│  ✓ 区分内部系统 vs 第三方系统 vs 基础设施                   │
│  ✓ 标注关键交互的协议（HTTPS / MQ / gRPC）                  │
│  ✓ 系统边界用醒目标记（双线框 / ★ 标记）                    │
│  ✓ 配套文字说明系统的职责边界（做什么 / 不做什么）           │
│                                                              │
│  过度深度（不应出现）：                                       │
│  ────────────────────────                                    │
│  ✗ 展开系统内部的模块或组件                                  │
│  ✗ 标注端口号、IP 地址、部署信息                             │
│  ✗ 画出系统内部的数据表或缓存                                │
│  ✗ 每条连线标注具体的 API 路径                               │
│                                                              │
│  原则：一张系统上下文图应在 30 秒内让读者理解                 │

│                                                              │
```

#### 必须包含的要素

| 要素 | 说明 | 示例 |
|------|------|------|
| 待设计系统 | 图的中心，唯一的双线框/高亮框 | ★ 订单服务 ★ |
| 外部人员角色 | 所有人类用户 | 终端用户、运营人员 |
| 外部系统（内部） | 同组织内的其他系统 | 库存系统、用户服务 |
| 外部系统（第三方） | 不受控的外部依赖 | 支付宝、微信支付 |
| 基础设施 | 间接交互的中间件 | 消息队列、对象存储 |
| 交互意图标注 | 每条连线上的动词短语 | "查询库存"、"发送订单事件" |
| 协议标注 | 关键交互的通信方式 | HTTPS / MQ / gRPC |

#### 配套文字说明

系统上下文图**必须**附带文字说明，补充图无法表达的内容：

1. **职责边界**：系统做什么、不做什么（一句话定义）
2. **外部系统可用性约束**：第三方系统的 SLA、限流、维护窗口
3. **关键依赖风险**：哪些外部依赖不可用时系统如何降级
4. **数据归属**：每类数据由谁拥有（写入方），本系统是读还是写

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 漏画间接依赖（如 MQ 的消费方） | 读者无法感知系统变更的影响范围 | 追踪所有数据流出路径 |
| 不区分内部/第三方系统 | 读者误以为第三方系统可控，忽略可用性风险 | 用不同边框或标注区分 |
| 连线上没有意图标注 | 图变成"方框连线游戏"，不传达语义 | 每条线至少一个动词 |
| 画了系统内部结构 | 混淆了上下文图和容器图的职责 | 内部结构移至容器图 |

### 4.2 容器图（C4 Container 级）

#### 理论定位

容器图回答的是**"系统内部有哪些独立部署单元，它们之间怎么通信"**。"容器"不是 Docker 容器，而是**任何独立运行的进程**——一个 Spring Boot 服务、一个前端 SPA、一个数据库实例、一个消息队列，都是一个容器。

容器图的核心价值是让读者理解：**系统的运行时形态**——启动了几个进程、用了什么技术栈、数据存在哪里、通信用什么协议。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  容器图的深度标尺                                             │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只画了服务框，没有标注技术栈                              │
│  ✗ 数据库/缓存只画了一个框，没有区分类型（MySQL/Redis/MQ）   │
│  ✗ 容器间的连线没有标注通信协议                              │
│  ✗ 漏掉了管理后台、定时任务等"不起眼"的容器                 │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 每个容器标注技术栈（Spring Boot / Vue3 / MySQL）          │
│  ✓ 容器间连线标注协议（HTTP / gRPC / MQ / TCP）             │
│  ✓ 数据存储标注类型和归属（谁写谁读）                        │
│  ✓ 区分前端应用、后端服务、数据存储                          │
│  ✓ 标注每个容器的职责（一句话）                              │
│  ✓ 配套文字说明通信方式选择的理由                            │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 展开容器内部的模块/组件                                   │
│  ✗ 标注具体的类名或接口名                                    │
│  ✗ 画出每个容器的内部线程模型                                │
│  ✗ 画出具体的 API 路径或消息 Topic                          │
│                                                              │
│  原则：容器图让读者能回答"部署几个进程？用什么技术？         │
│  怎么通信？数据存哪？"这四个问题即可。                       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 每个独立部署的进程 | 服务、前端应用、定时任务、消费者进程 |
| 每个容器的技术栈 | 如 "Spring Boot 3.x"、"Vue3 SPA" |
| 每个数据存储 | 数据库、缓存、对象存储，标注类型 |
| 容器间通信协议 | HTTP / gRPC / MQ Topic / Redis 协议 |
| 数据归属 | 每个数据存储的写入方（Single Writer 原则） |
| 容器职责 | 每个容器的一句话职责描述 |

#### 配套文字说明

1. **每个容器的职责描述**：做什么、不做什么
2. **通信方式选择的理由**：为什么这里用同步 HTTP 而非异步 MQ
3. **数据存储的归属规则**：谁写谁读，是否允许跨服务直连数据库
4. **部署拓扑**：集群/单机、区域、实例数
5. **非功能性约束**：QPS 上限、延迟要求、容量估算

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 漏掉定时任务/消费者进程 | 部署时遗漏组件 | 列出所有独立运行进程 |
| 不标注数据存储的归属 | 多个服务写同一张表 | 标注 Single Writer |
| 混入组件级细节 | 图变得复杂且难以维护 | 组件细节移至组件图 |
| 只画服务不画前端 | 遗漏部署单元 | 前端 SPA 也是容器 |

#### 示例

```
│  └──────┬───────┘    └──────┬───────┘                   │
│         │                   │                            │
│         ▼                   ▼                            │
│  ┌──────────────────────────────┐                       │
│  │       order-service          │                       │
│  │    (Spring Boot Core)        │                       │
│  └──┬────────┬────────┬────────┘                       │
│     │        │        │                                 │
│     ▼        ▼        ▼                                 │
│  ┌──────┐ ┌──────┐ ┌──────┐                            │
│  │ MySQL│ │ Redis│ │  MQ  │                            │
│  └──────┘ └──────┘ └──────┘                            │
│                                                          │
```

### 4.3 组件图（C4 Component 级）

#### 理论定位

组件图回答的是**"一个容器内部有哪些协作模块，它们的职责和依赖是什么"**。它是概要设计到详细设计的桥梁——概要设计用组件图表达模块划分，详细设计用组件图展开实现细节。

组件图的核心价值是揭示**容器内部的职责边界和依赖方向**，从而暴露两个关键问题：
- 职责是否清晰（有没有一个组件承担了过多职责）
- 依赖是否合理（是否存在循环依赖、是否违反依赖倒置）

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  组件图的深度标尺                                             │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只画了大的分层（Controller / Service / DAO），           │
│    没有展示层内的组件划分                                     │
│  ✗ 组件间只有连线，没有标注交互语义                          │
│  ✗ 没有区分内部组件和外部代理（Proxy / Client）              │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 展示每个容器内的核心组件及其职责                          │
│  ✓ 标注组件间的依赖方向和交互语义                            │
│  ✓ 区分领域组件（Domain）和基础设施适配组件（Proxy/Repo）   │
│  ✓ 标注依赖倒置的接口点（虚线框标注接口）                   │
│  ✓ 配套文字说明层间约束和依赖规则                            │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 展开每个组件内部的类/方法                                 │
│  ✗ 标注具体的函数签名或代码级细节                            │
│  ✗ 画出异常处理分支                                          │
│                                                              │
│  原则：组件图让读者能回答"这个容器内部的职责怎么分的？       │
│  依赖方向是否合理？有没有循环依赖？"即可。                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 核心组件 | 容器内所有关键模块 |
| 组件职责 | 每个组件的一句话职责 |
| 依赖方向 | 组件间的箭头方向，标注语义 |
| 依赖倒置点 | 哪些依赖通过接口解耦（虚线标注） |
| 外部代理 | 调用其他容器/系统的适配组件 |
| 层间约束 | 哪些层可以调用哪些层，哪些不允许 |

#### 配套文字说明

1. **层间约束规则**：如 "domain 层不直接依赖 infra 层"
2. **依赖倒置的实现方式**：接口定义在哪个层、实现在哪个层
3. **外部调用的封装策略**：是否使用防腐层（ACL）

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 没有标注层间约束 | 后续开发"图方便"跨层调用，架构退化 | 在图上或文字中写明约束 |
| 不区分领域组件和适配组件 | 读者无法判断哪些是核心逻辑、哪些是外部依赖 | 用不同颜色/边框区分 |
| 箭头方向混乱 | 依赖方向不清晰，可能存在循环依赖 | 确保依赖方向一致向下 |
| 组件粒度不一致 | 有的粗到一层一个，有的细到一个类一个 | 统一为"一个职责单元"粒度 |

#### 示例

```
┌──────────────────── order-service ──────────────────────┐
│                                                         │
│  ┌─────────────┐                                        │
│  │ OrderControl│──创建订单──►┌──────────────┐           │
│  │   (入口)    │            │ OrderAppServ  │           │
│  └─────────────┘            │  (应用服务)   │           │
│                             └──┬───┬───┬───┘           │
│                                │   │   │                │
│                 ┌──────────────┘   │   └──────┐        │
│                 ▼                  ▼          ▼        │
│          ┌────────────┐   ┌────────────┐ ┌─────────┐  │
│          │ OrderDomain│   │ StockProxy │ │PayProxy │  │
│          │ (领域服务) │   │ (库存适配) │ │(支付适配│  │
│          └─────┬──────┘   └────────────┘ └─────────┘  │
│                │           ┌────────────┐              │
│                └──────────►│ OrderRepo  │              │
│                    接口    │ (持久化)   │              │
│                            └────────────┘              │
│                                                         │
│  层间约束：                                              │
│  · api → application → domain ← infra（依赖倒置）      │
│  · domain 不直接依赖 infra（通过接口倒置）              │
│  · infra 不调用 application                             │
└─────────────────────────────────────────────────────────┘
```

### 4.4 流程图

#### 理论定位

流程图回答的是**"处理步骤的先后顺序和分支逻辑"**。它用于描述**单个角色视角下的处理过程**，关注的是控制流的走向——每一步做什么、条件分支怎么走、异常怎么回退。

流程图和时序图的本质区别：流程图描述**一个角色内部的逻辑步骤**，时序图描述**多个角色之间的交互顺序**。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  流程图的深度标尺                                             │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只有"正向路径"，没有失败/异常分支                         │
│  ✗ 判断条件模糊（如"校验？"不写校验什么）                   │
│  ✗ 并行步骤用串行表示（丢失并行语义）                        │
│  ✗ 没有标注哪些步骤是关键路径                               │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 每个判断节点标注明确的条件（如"库存 > 0？"）             │
│  ✓ 每个分支都有明确的走向（是 / 否 / 成功 / 失败）          │
│  ✓ 异常/失败路径必须画出，标注补偿动作                      │
│  ✓ 关键路径标注（如"★ 关键路径"）                           │
│  ✓ 异步步骤标注（如"（异步）"）                              │
│  ✓ 终止节点标注最终状态（成功 / 失败 / 降级）               │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 每个步骤展开为子流程的子流程                              │
│  ✗ 标注具体的代码行号或函数名                                │
│  ✗ 把所有边界条件都画成独立分支（图变得不可读）              │
│                                                              │
│  原则：流程图让读者能回答"正常怎么走？失败了怎么处理？       │
│  关键路径是哪条？"即可。                                     │
│  边界条件过多的，用表格补充而非全画进图里。                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 流程图的三个层次

| 层次 | 粒度 | 用途 | 示例 |
|------|------|------|------|
| 业务流程 | 跨角色、跨系统 | 概要设计中展示端到端流程 | 用户下单 → 支付 → 发货 |
| 处理流程 | 单服务内部 | 详细设计中展示处理逻辑 | 接收请求 → 校验 → 预扣 → 持久化 |
| 异常流程 | 失败路径 | 详细设计中展示容错逻辑 | 支付超时 → 查询状态 → 关单/放行 |

#### ASCII 绘图约定

```
┌───┐
│   │   方框 = 处理步骤（内写动词短语）
└─┬─┘
  │
  ▼       实线箭头 = 主流程方向
◇         菱形 = 判断/分支（内写条件，分支标注"是/否"）
─╋─       横线 = 并行/汇聚
  │
  ╧         终止符 = 流程结束（标注最终状态）

关键标注：
  ★ = 关键路径步骤
  （异步）= 非阻塞步骤
  ⚠ = 需要补偿的步骤
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 起始节点 | 流程的触发条件 |
| 处理步骤 | 每步做什么（动词短语） |
| 判断节点 | 条件和分支标注 |
| 失败/异常路径 | 每个可能失败的步骤的处理方式 |
| 补偿动作 | 失败后需要回退的操作 |
| 终止节点 | 最终状态（成功/失败/降级） |

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 只画正常路径，不画异常 | 上线后异常路径凭开发者临场发挥 | 每个可能失败的步骤必须画补偿 |
| 判断条件模糊 | 不同开发者理解不同 | 条件写具体（"库存 > 0" 而非 "校验？"） |
| 把跨系统交互画成流程图 | 流程图表达不了时序语义 | 跨系统交互用**时序图** |
| 图太深太细，不可读 | 读者放弃看图 | 超过 15 个节点的流程拆为子流程 |

#### 示例：下单主流程

```
         ┌───────────┐
         │  接收请求  │
         └─────┬─────┘
               │
               ▼
         ┌───────────┐     否
         │ 参数校验？ ├──────────► 返回 400
         └─────┬─────┘
            是 │
               ▼
         ┌───────────┐     否
         │ 库存充足？ ├──────────► 返回 ORDER_001
         └─────┬─────┘
            是 │
               ▼
         ┌───────────┐  ★ 关键路径
         │ 预扣库存   │  ⚠ 需补偿
         └─────┬─────┘
               │
               ▼
         ┌───────────┐
         │ 计算价格   │
         └─────┬─────┘
               │
               ▼
         ┌───────────┐     失败
         │ 创建订单   ├──────────► ⚠ 释放库存 + 返回 500
         └─────┬─────┘
            成功 │
               ▼
         ┌───────────┐
         │ 发送通知   │（异步）
         └─────┬─────┘
               │
               ▼
         ┌───────────┐
         │ 返回订单号 │ ✔ 成功
         └───────────┘
```

### 4.5 时序图

#### 理论定位

时序图回答的是**"谁在什么时候给谁发了什么消息，收到了什么响应"**。它用于描述**多个角色（服务/模块/系统）之间的协作顺序**，关注的是消息的时序和因果关系。

时序图是**分布式系统设计中最重要**的图——因为分布式系统的复杂性不在任何一个节点内部，而在节点间的交互和失败处理。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  时序图的深度标尺                                             │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只有请求没有响应（看不出成功/失败）                       │
│  ✗ 没有标注同步/异步                                         │
│  ✗ 只画正常路径，没有失败和补偿路径                          │
│  ✗ 参与者选错了粒度（太粗：只画"系统"；太细：画到了函数）   │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 每条消息标注语义（动词短语，如"扣减库存"）               │
│  ✓ 请求和响应都有（成功响应 + 失败响应）                     │
│  ✓ 区分同步调用（实线）和异步消息（虚线/斜体）              │
│  ✓ 失败路径用 [条件] 标注，画出补偿步骤                     │
│  ✓ 标注关键的非功能性约束（超时/重试/幂等）                 │
│  ✓ 参与者粒度为服务/模块级别（非函数级别）                  │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 标注每条消息的完整 JSON 字段                              │
│  ✗ 画出内部函数调用链                                        │
│  ✗ 每个条件判断都展开为分支                                  │
│                                                              │
│  原则：时序图让读者能回答"谁先做什么？失败了怎么办？         │
│  补偿顺序是什么？"即可。                                     │
│  字段级别的细节用接口契约文档补充。                           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 时序图的四种模式

| 模式 | 适用场景 | 特点 |
|------|---------|------|
| 请求-响应 | 同步调用链 | 请求向下，响应向上，成对出现 |
| 事件驱动 | 异步解耦 | 生产者发事件后不等待，消费者独立处理 |
| Saga 编排 | 分布式事务 | 每步有补偿，失败时逆序补偿 |
| 超时-重试 | 不可靠依赖 | 标注超时阈值和重试策略 |

#### ASCII 绘图约定

```
参与者    垂直线    同步请求    同步响应    异步消息
  A        │        ────►       ◄────       - - - ►
  B        │

条件分支标注：
  [支付成功]       正常路径
  [支付失败]       补偿路径

关键标注：
  ⏱ = 超时边界
  🔁 = 重试
  ⊘ = 幂等
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 参与者 | 涉及的服务/模块（横轴） |
| 消息时序 | 谁给谁发什么（纵轴从上到下） |
| 同步/异步 | 每条消息的通信方式 |
| 成功路径 | 正常情况下的交互序列 |
| 失败路径 | 失败时的补偿/回退序列 |
| 关键约束 | 超时、重试、幂等标注 |

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 只画正常路径 | 上线后遇到失败不知道怎么补偿 | 必须画失败+补偿路径 |
| 不区分同步/异步 | 读者误解调用方式，设计出不可行的方案 | 标注每条消息的通信方式 |
| 参与者粒度太细（画到函数） | 图变得冗长且难以维护 | 参与者为服务/模块级别 |
| 不标注超时 | 读者不知道调用是否可能在时间维度失败 | 关键同步调用标注超时阈值 |

#### 示例：分布式事务（Saga 模式）

```
  客户端      订单服务      库存服务      支付服务
    │           │             │             │
    │──下单───►│             │             │
    │          │──扣库存───►│             │
    │          │◄──成功─────│             │
    │          │             │             │
    │          │──创建订单──►│             │
    │          │  (本地事务) │             │
    │          │             │             │
    │          │──发起支付──────────────►│
    │          │◄──支付成功──────────────│
    │          │             │             │
    │◄─成功───│             │             │
    │          │             │             │
    │          │  [支付失败]               │
    │          │──补偿：释放库存────────►│
    │          │──补偿：取消订单(本地)    │
    │◄─失败───│             │             │
```

### 4.6 信号传播路径图

#### 理论定位

信号传播路径图回答的是**"当某个条件触发时，信号如何传播、系统如何响应、如何恢复"**。它专门用于描述**流控、背压、限流、降级**等反应式场景，这些场景用流程图或时序图都无法精确表达。

信号传播路径图的核心价值是揭示**级联效应**——一个信号如何从一个节点传播到另一个节点，以及恢复条件的传递路径。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  信号传播路径图的深度标尺                                     │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只写了"触发限流"，没有标注信号传播到上游的方式            │
│  ✗ 没有标注恢复条件                                          │
│  ✗ 没有标注各节点的阈值                                      │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 标注信号的触发条件和传播方向                              │
│  ✓ 标注每个节点的阈值（高水位/低水位、限流 QPS）            │
│  ✓ 标注恢复条件（信号消失的触发条件）                        │
│  ✓ 标注传播延迟（信号从触发到生效的时间）                    │
│  ✓ 标注级联效应（一个信号是否触发另一个信号）               │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 画出具体的实现代码逻辑                                    │
│  ✗ 画出所有可能的信号组合                                    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 触发条件 | 什么条件产生信号 |
| 传播方向 | 信号如何传播到上下游 |
| 各节点阈值 | 高水位/低水位、限流 QPS 等 |
| 恢复条件 | 什么条件下信号消失 |
| 级联效应 | 信号传播是否触发其他信号 |

#### 示例：背压信号传播

```
上游 (快) → 缓冲增长 → 触发高水位 (80%) → 暂停上游读取
                                          ↓
                                 消费缓冲 → 发送
                                          ↓
                                 低于低水位 (30%) → 恢复上游读取

信号传播链：
  缓冲大小 → [高水位] → 上游暂停
  缓冲大小 → [低水位] → 上游恢复
  上游暂停 → 上游感知延迟 → 级联：更上游可能也需暂停
```

### 4.7 数据结构生命周期图

#### 理论定位

数据结构生命周期图回答的是**"一个数据结构从创建到销毁经历了哪些阶段，在异步回调期间谁持有它的引用"**。它专门用于**涉及异步资源的场景**——fd、handle、buffer、连接等，这些资源的生命周期管理是内存泄漏和 UAF（Use After Free）的高发区。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  数据结构生命周期图的深度标尺                                 │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只画了创建和销毁，没有中间状态                            │
│  ✗ 没有标注异步回调期间的引用关系                            │
│  ✗ 没有标注谁负责释放资源                                    │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 画出从创建到销毁的完整状态链                              │
│  ✓ 标注每个状态转换的触发条件                                │
│  ✓ 标注异步回调期间的引用持有者                              │
│  ✓ 标注资源释放的责任方                                      │
│  ✓ 标注危险窗口期（回调未完成但资源已释放）                 │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 画出引用计数的具体数值变化                                │
│  ✗ 画出所有可能的错误码路径                                  │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 完整状态链 | 从创建到销毁的所有状态 |
| 状态转换触发条件 | 什么操作导致状态变更 |
| 引用持有者 | 异步回调期间谁持有引用 |
| 资源释放责任方 | 谁负责释放，释放的时机 |
| 危险窗口期 | 回调未完成但资源已释放的时段 |

#### 示例：异步资源生命周期

```
  create()                    close()
     │                          │
     ▼                          ▼
┌──────────┐  start()   ┌──────────┐  stop()
│ CREATED  │───────────►│ ACTIVE   │───────────►
└──────────┘            └──────────┘
                              │
                              ▼
                        ┌──────────┐
                        │ CLOSING  │ close_cb ──► 释放
                        └─────┬────┘
                              │
                        ⚠ close 回调期间
                           资源仍被引用
```

### 4.8 状态机图

#### 理论定位

状态机图回答的是**"业务对象在什么条件下可以从什么状态变成什么状态"**。它是**业务规则最精确的表达方式**——比文字描述更不容易有歧义，比代码更可读。

状态机图的核心价值不在于画出合法转换（那通常不难想到），而在于：
1. **穷举所有状态**，特别是异常态和暂态
2. **明确定义非法转换的处理策略**——这才是 bug 的高发区
3. **标注每个转换的守卫条件**——防止不满足前置条件时发生转换

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  状态机图的深度标尺                                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只画了正常状态（如 已创建→已支付→已完成），              │
│    没有异常态（已取消/已退款）                                │
│  ✗ 转换上只写了触发动作，没有守卫条件                        │
│  ✗ 没有说明非法转换怎么处理                                  │
│  ✗ 没有标注哪个是初态、哪个是终态                            │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 包含所有状态（正常态 + 异常态 + 暂态）                   │
│  ✓ 每个转换标注：触发条件 [守卫条件] / 产生的副作用          │
│  ✓ 明确定义初态和终态                                        │
│  ✓ 明确定义非法转换的处理策略（记日志？拒绝？异常？）       │
│  ✓ 配套转换矩阵表格（穷举所有 from→to 组合）               │
│  ✓ 标注超时自动转换（如"30 分钟未支付自动取消"）           │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 把每个状态内的子状态全部展开                              │
│  ✗ 把状态机实现细节（锁、CAS）画进图里                      │
│                                                              │
│  原则：状态机图 + 转换矩阵表格 = 完整的状态生命周期描述。    │
│  图用于直觉理解，表格用于穷举验证。                          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 全部状态 | 正常态、异常态、暂态 |
| 初态和终态 | 明确标注 |
| 转换条件 | 触发事件 + 守卫条件 + 副作用 |
| 非法转换策略 | 遇到非法转换时系统的行为 |
| 超时转换 | 自动状态变更（如超时取消） |
| 转换矩阵 | 表格形式穷举所有状态组合 |

#### 转换矩阵（必须附带）

状态机图**必须**附带转换矩阵表格，用于穷举验证——图可能漏画，表格不会：

| 从 \ 到 | CREATED | PAID | SHIPPED | COMPLETED | CANCELLED | REFUNDED |
|---------|---------|------|---------|-----------|-----------|----------|
| CREATED | — | ✅ 支付成功 | ❌ | ❌ | ✅ 超时/主动取消 | ❌ |
| PAID | ❌ | — | ✅ 发货 | ❌ | ❌ | ✅ 退款成功 |
| SHIPPED | ❌ | ❌ | — | ✅ 确认收货 | ❌ | ✅ 退款成功 |
| COMPLETED | ❌ | ❌ | ❌ | — | ❌ | ✅ 退款成功 |
| CANCELLED | ❌ | ❌ | ❌ | ❌ | —（终态） | ❌ |
| REFUNDED | ❌ | ❌ | ❌ | ❌ | ❌ | —（终态） |

> 非法转换处理策略：记录 WARN 日志，状态不变，不抛异常，不崩溃。

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 只画合法转换，不定义非法转换处理 | 非法转换时系统行为不可预期 | 必须写明策略（记日志/拒绝/异常） |
| 没有转换矩阵 | 图可能漏画转换，上线后才发现 | 表格穷举所有 from→to 组合 |
| 忽略超时自动转换 | 资源永久占用（如库存永远被预扣） | 标注超时转换和阈值 |
| 不区分暂态和稳态 | 读者误以为暂态是可停留的状态 | 标注暂态（如"处理中"） |

#### 示例：订单状态机

```
                    ┌───────────┐
         ┌────────►│  CREATED  │  初态
         │         └─────┬─────┘
         │               │ 支付成功
         │               ▼
         │         ┌───────────┐
    超时未支付     │   PAID    │◄───┐
         │         └─────┬─────┘    │
         │               │          │
         │          发货 │          │ 退款成功
         │               ▼          │
         │         ┌───────────┐    │
         │         │ SHIPPED   │    │
         │         └─────┬─────┘    │
         │          确认收货│        │
         │               ▼          │
         │         ┌───────────┐    │
         │         │ COMPLETED │    │
         │         └───────────┘    │
         │                        │
         ▼                        │
   ┌───────────┐          ┌──────┴────┐
   │ CANCELLED │          │  REFUNDED  │
   │  (终态)   │          │  (终态)    │
   └───────────┘          └───────────┘
```

### 4.9 数据流图

#### 理论定位

数据流图回答的是**"数据从哪来、到哪去、经过什么变换、谁写谁读"**。它和时序图的区别在于：时序图关注**控制流**（谁先做什么），数据流图关注**数据流**（数据怎么流转、怎么变换）。

数据流图的核心价值是揭示**数据所有权**问题——每份数据的写入方是谁，读取方是谁，是否存在多方写入的风险。

#### 深度标尺

```
┌──────────────────────────────────────────────────────────────┐
│  数据流图的深度标尺                                           │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  深度不足：                                                   │
│  ──────────                                                  │
│  ✗ 只画了"服务A → 服务B"，没有标注流经的数据是什么          │
│  ✗ 没有标注读/写语义（是写入还是查询）                      │
│  ✗ 没有标注同步/异步                                        │
│                                                              │
│  深度适中（推荐）：                                           │
│  ────────────────────────                                    │
│  ✓ 标注每条数据流的内容（如"订单数据"、"库存变更事件"）     │
│  ✓ 标注读/写语义（写入 / 查询 / 订阅）                      │
│  ✓ 标注同步/异步                                            │
│  ✓ 标注数据存储的归属（谁写入、谁读取）                     │
│  ✓ 配套数据所有权矩阵表格                                   │
│  ✓ 标注数据变换（如"聚合"、"过滤"、"格式转换"）            │
│                                                              │
│  过度深度：                                                   │
│  ──────────                                                  │
│  ✗ 标注每条数据的完整字段列表                                │
│  ✗ 画出内部缓存命中/未命中的分支                            │
│                                                              │
│  原则：数据流图让读者能回答"每份数据归谁管？谁写谁读？       │
│  有没有多方写入的风险？"即可。                               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

#### 必须包含的要素

| 要素 | 说明 |
|------|------|
| 数据流内容 | 流经的是什么数据 |
| 读/写语义 | 每个操作是写入、查询还是订阅 |
| 同步/异步 | 数据的传输方式 |
| 数据存储归属 | 每个数据存储的写入方 |
| 数据变换 | 经过什么变换（聚合/过滤/转换） |

#### 配套数据所有权矩阵

| 数据 | 拥有者（写入方） | 消费者（读取方） | 风险标注 |
|------|----------------|----------------|---------|
| 订单数据 | 订单服务 | 支付服务、通知服务 | — |
| 库存数据 | 库存服务 | 订单服务（查询） | ⚠ 订单服务也写库存（预扣），需区分 |

#### 常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 不标注读写语义 | 读者不知道是读还是写，可能误判数据归属 | 每条流标注写/读/订阅 |
| 不区分同步和异步 | 读者误解数据一致性保证 | 标注通信方式 |
| 不画数据变换 | 读者以为数据原样传递 | 标注变换（聚合/过滤/转换） |

| 21 | 跨模块调用链汇总 | 表格 | 开发 + 测试 |
| 22 | 从设计到编码的实施路线图 | ASCII / 表格 | 开发 |

## 七、写作原则与常见误区

### 7.1 写作原则

| 原则 | 说明 |
|------|------|
| **先问题后方案** | 先讲清楚"为什么要做"，再讲"怎么做" |
| **非目标必写** | 明确不在范围内的事，比写目标更重要 |
| **方案要对比** | 只给一个方案等于没做设计，至少给 2~3 个备选 |
| **写权衡不写事实** | "选 Kafka 因为吞吐高"是事实，"选 Kafka 而非 RabbitMQ 因为我们的场景吞吐优先于路由灵活"是权衡 |
| **图胜于表，表胜于文** | 能用图的不用表，能用表的不用段落 |
| **文档要活** | 实现偏差要更新到文档，否则文档会变成"考古材料" |
| **适度即可** | 大项目 10~20 页，小功能 1~3 页，过度文档化不如不写 |
| **决策有演进** | 每个技术决策不仅写当前选择，还要写备选和演进路径，让未来维护者知道"还可以怎么做" |
| **约束即防线** | 分层约束、接口契约、前置/后置条件——写在文档里的约束就是架构的防线 |
| **可验证即可信** | 验收准则用可执行的命令/指标/断言表达，非功能指标标注来源依据 |
| **详细设计即代码骨架** | 详细设计的目录结构、结构体定义、关键函数伪代码应达到"照着写就能编码"的粒度 |

### 7.2 常见误区

```
┌───────────────────────────────────────────────────────────┐
│                   设计文档的 10 个致命误区                   │
├───────────────────────────────────────────────────────────┤
│                                                           │
│  ❶ 把设计文档写成开发任务说明书                              │
│     → 设计文档讲"为什么这样做"，不是"先建表再写接口"          │
│                                                           │
│  ❷ 只有方案，没有目标和边界                                  │
│     → 读者不知道方案在解决什么问题、边界在哪里               │
│                                                           │
│  ❸ 没有备选方案                                           │
│     → 评审无法做有效决策，方案合理与否无法评估               │
│                                                           │
│  ❹ 只写功能，不写非功能                                     │
│     → 性能、安全、可观测、成本同等重要                      │
│                                                           │
│  ❺ 没有灰度和回滚方案                                      │
│     → 上线后出问题只能"硬扛"                               │
│                                                           │
│  ❻ 没有验收指标                                           │
│     → "做完了"但不知道"是否成功了"                         │
│                                                           │
│  ❼ 上线后不维护                                           │
│     → 文档与实现脱节，后来者只能"考古"                     │
│                                                           │
│  ❽ 架构图只画分层，不写约束                                │
│     → 后续开发"图方便"跨层调用，架构逐渐退化                │
│                                                           │
│  ❾ 状态机只画合法转换，不写非法转换怎么办                    │
│     → 非法转换时崩溃？忽略？记日志？——必须在设计中明确      │
│                                                           │
│  ❿ 非功能指标给数字不给来源                                │
│     → "吞吐 ≥ 500Mbps"——依据是什么？评审无法判断合理性     │
│                                                           │
└───────────────────────────────────────────────────────────┘
```

## 八、评审检查清单

### 8.1 概要设计评审清单

- [ ] 背景和问题定义是否清晰
- [ ] 目标和非目标是否明确
- [ ] 系统边界是否画清楚
- [ ] 架构选型是否使用决策四元组（选择+备选+理由+演进路径）
- [ ] 备选方案是否至少 2~3 个
- [ ] 分层架构是否写入层间约束规则
- [ ] 核心数据流是否至少有一条路径精确到函数调用链
- [ ] 关键路径是否有端到端时序分析
- [ ] 横切关注点（安全/性能/可用性/可观测/成本）是否覆盖
- [ ] 性能章节是否包含端到端延迟预算表
- [ ] 是否包含容量规划（内存/CPU/连接数）
- [ ] 风险是否识别并有缓解策略，异常场景是否区分「常见」和「边缘」
- [ ] 是否有需求追溯矩阵（需求ID ↔ 设计章节 ↔ 测试场景）
- [ ] 非功能需求指标是否标注来源和依据
- [ ] 灰度和回滚方案是否完备
- [ ] 上下游影响是否评估
- [ ] 文档是否包含版本号和变更记录
- [ ] 评审人是否覆盖架构/开发/测试/运维

### 8.2 详细设计评审清单

- [ ] 模块职责是否单一、边界是否清晰
- [ ] 文档是否声明数据来源（如"从头文件提取"）
- [ ] **代码目录结构是否完整，每个文件的职责是否标注**
- [ ] **核心结构体是否定义，每个成员变量的作用是否说明**
- [ ] **结构体字段是否有默认值、有效范围、约束说明**
- [ ] 接口定义是否完整（入参/出参/错误码/三值语义）
- [ ] 关键 API 是否有前置/后置条件
- [ ] **关键函数是否提供伪代码，逻辑分支是否完整**
- [ ] **伪代码是否包含异常处理和补偿逻辑**
- [ ] **仅凭详细设计，能否直接编写出代码？**（终极检验）
- [ ] 数据表结构是否提供完整 DDL（含索引、约束、分区策略）
- [ ] 缓存结构是否包含 Key 设计 / TTL / 击穿防护
- [ ] 每张表是否声明数据所有权（谁写谁读）
- [ ] 涉及异步资源的数据结构是否有生命周期图
- [ ] 核心流程是否有时序图（多模块交互场景必须有）
- [ ] 状态机是否包含非法转换的处理策略 + 转换矩阵表格
- [ ] 流控/背压场景是否有信号传播路径图
- [ ] 异常处理是否覆盖关键场景（含边缘场景）
- [ ] 幂等方案是否设计（幂等键、幂等窗口、实现方式）
- [ ] 并发/竞态场景是否逐一分析（哪些路径会并发读写同一资源）
- [ ] 并发控制策略是否明确（锁/CAS/版本号）
- [ ] 事务边界与隔离级别是否声明
- [ ] 声明模型之外的例外是否分析
- [ ] **是否提供框架集成说明（依赖注入/组件注册/中间件配置）**
- [ ] **是否提供可直接复制粘贴的类骨架模板**
- [ ] **是否包含"从设计到编码"的实施路线图（搭框架的步骤顺序）**
- [ ] 监控指标和告警是否定义
- [ ] 配置项是否包含五要素（类型/默认值/范围/依赖/排查）
- [ ] 测试场景是否覆盖核心路径 + 异常路径 + 状态机路径
- [ ] 测试验收准则是否可执行（可运行 curl / 断言）
- [ ] 是否有跨模块调用链汇总（5~10 个关键场景）
- [ ] 详细设计是否超过 1500 行？如超过，是否已按模块拆分
- [ ] 文档与代码的一致性是否有自动化校验机制

## 九、文档模板速查

### 9.1 概要设计模板

```markdown
# [项目名] 概要设计

> 作者 | 日期 | 评审人 | 状态
> 版本 | 最后更新 | 变更记录

## 读码导航（推荐）

## 1. 背景与问题
## 2. 目标与非目标
## 3. 约束条件（含容量规划）
## 4. 系统上下文与边界（附上下文图）
## 5. 总体架构（附架构图、层间约束规则、模块划分）
## 6. 关键技术选型（附决策四元组表）
## 7. 备选方案与取舍（附对比表）
## 8. 关键接口与数据流概览（附数据流图，至少一条精确到函数级）
## 9. 横切关注点
  - 9.1 安全
  - 9.2 性能（含性能预算表）
  - 9.3 可用性
  - 9.4 可观测性
  - 9.5 成本
## 10. 风险与待确认事项（异常场景分常见/边缘）
## 11. 上线策略（灰度/回滚/监控）
## 12. 需求追溯矩阵
## 13. ADR 索引
```

### 9.2 详细设计模板

```markdown
# [模块名] 详细设计

> 作者 | 日期 | 关联概要设计
> 版本 | 最后更新 | 变更记录

## 数据来源声明

## 1. 模块职责
## 2. 代码目录结构（含文件职责说明）
## 3. 结构体定义
  - 3.1 核心结构体字段列表与成员变量作用
  - 3.2 字段默认值、有效范围、约束
  - 3.3 结构体间引用/组合关系
  - 3.4 数据结构生命周期图（异步资源必须标注）
## 4. 接口定义
  - 4.1 API 签名（含前置/后置条件、三值语义）
  - 4.2 消息协议
  - 4.3 错误码
## 5. 关键函数伪代码
  - 5.1 核心业务函数伪代码
  - 5.2 状态转换函数伪代码
  - 5.3 性能敏感路径标注
## 6. 数据设计
  - 6.1 表结构（完整 DDL，含索引、约束、分区策略）
  - 6.2 缓存结构（Key 设计 / TTL / 击穿防护）
  - 6.3 数据生命周期
  - 6.4 数据所有权声明（每张表谁写谁读）
## 7. 核心流程（附时序图/流程图/信号传播路径图）
## 8. 状态机（含非法转换处理策略 + 转换矩阵表格）
## 9. 异常处理与容错（分常见/边缘场景，含幂等方案）
## 10. 并发与一致性
  - 10.1 竞态场景分析
  - 10.2 并发控制策略（锁/CAS/队列/版本号）
  - 10.3 事务边界与隔离级别
  - 10.4 分布式一致性方案
  - 10.5 声明模型之外的例外分析
## 11. 性能设计
## 12. 测试设计（验收准则可执行）
## 13. 框架集成与代码骨架
  - 13.1 依赖注入/组件注册方式
  - 13.2 中间件/拦截器注册
  - 13.3 配置加载与绑定
  - 13.4 可直接复制粘贴的类骨架模板
## 14. 部署与运维（附部署图、配置项五要素、监控告警）
## 15. 跨模块调用链（5~10 个关键场景）

## 附录：从设计到编码的实施路线图
  - 第 1 步：搭骨架（目录 + 类模板 + 框架注册）
  - 第 2 步：建数据（DDL + Repository + 单测）
  - 第 3 步：串主流程（伪代码 → 代码 + Mock）
  - 第 4 步：补异常（补偿 + 幂等 + 并发控制）
  - 第 5 步：接外部（Mock → 真实 RPC/MQ）
  - 第 6 步：补横切（日志 + 监控 + 配置中心）
```

# BPMN 2.0 业务流程建模标准

> Business Process Model and Notation, Version 2.0
> 标准编号：ISO/IEC 19510:2013（OMG 标准编号：formal/2013-12-09）
> 发布：Object Management Group (OMG)，2011 年发布，2013 年成为 ISO 标准

---

## 一、标准概述

BPMN 2.0 是当前业务流程建模领域的主流国际标准。与 ISO 5807 面向程序逻辑不同，BPMN 面向的是**业务流程和组织协作**。

核心设计目标：
- 提供所有业务利益相关者都能理解的标准化标注
- 从业务分析师的流程设计到技术人员的流程实现，使用同一套语言
- 支持可执行的流程定义（BPMN XML 可以直接被流程引擎执行）

BPMN 2.0 定义了约 50 种图形元素，分为五大类：
1. 流对象（Flow Objects）— 事件、活动、网关
2. 连接对象（Connecting Objects）— 顺序流、消息流、关联
3. 泳道（Swimlanes）— 池、道
4. 数据（Data）— 数据对象、数据存储
5. 制品（Artifacts）— 组、注释

---

## 二、流对象（Flow Objects）

流对象是 BPMN 的核心，定义流程中"发生什么"。

### 2.1 事件（Events）

事件表示流程中"发生的事情"，用圆形表示。按位置分三类，按触发类型再细分。

```
事件的三个位置：

  ○    开始事件（Start Event）     — 流程从这里开始
       单细线圆，只有出口没有入口

  ◎    中间事件（Intermediate Event）— 流程中间发生的事
       双细线圆，有入口也有出口

  ⊕    结束事件（End Event）       — 流程到这里结束
       单粗线圆，只有入口没有出口
```

**开始事件（Start Events）：**

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形    名称                  含义                                │
├──────────────────────────────────────────────────────────────────┤
│  ○      None Start           空白开始，流程手动或自动启动         │
│  ○✉     Message Start        收到消息时启动流程                  │
│  ○⏱     Timer Start          到达指定时间时启动流程              │
│  ○⚡     Signal Start         收到信号时启动流程                  │
│  ○⊕     Conditional Start    满足条件时启动流程                  │
│  ○//    Multiple Start       多种触发方式之一即可启动             │
│  ○//+   Parallel Multiple    所有触发条件都满足时才启动           │
└──────────────────────────────────────────────────────────────────┘
```

**中间事件（Intermediate Events）：**

中间事件分为"捕获"（Catching，等待事件发生）和"抛出"（Throwing，主动触发事件）。

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形    名称                  含义                  捕获/抛出     │
├──────────────────────────────────────────────────────────────────┤
│  ◎      None Intermediate    流程中的标记点         —            │
│  ◎✉↓    Message Catch        等待收到消息           捕获         │
│  ◎✉↑    Message Throw        发送消息               抛出         │
│  ◎⏱     Timer Catch          等待指定时间到达       捕获         │
│  ◎⚡↓    Signal Catch         等待信号               捕获         │
│  ◎⚡↑    Signal Throw         发送信号               抛出         │
│  ◎⊕     Conditional Catch    等待条件满足           捕获         │
│  ◎↗↓    Escalation Catch     捕获升级事件           捕获         │
│  ◎↗↑    Escalation Throw     触发升级               抛出         │
│  ◎✕     Error Catch          捕获错误               捕获         │
│  ◎↩↓    Compensation Catch   捕获补偿请求           捕获         │
│  ◎↩↑    Compensation Throw   触发补偿               抛出         │
│  ◎∥     Link Catch           链接入口（跨页连接）   捕获         │
│  ◎∥     Link Throw           链接出口（跨页连接）   抛出         │
│  ◎✖     Cancel Catch         捕获取消事件           捕获         │
└──────────────────────────────────────────────────────────────────┘
```

**结束事件（End Events）：**

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形    名称                  含义                                │
├──────────────────────────────────────────────────────────────────┤
│  ⊕      None End             正常结束                            │
│  ⊕✉     Message End          发送消息后结束                      │
│  ⊕⚡     Signal End           发送信号后结束                      │
│  ⊕✕     Error End            抛出错误后结束                      │
│  ⊕↗     Escalation End       触发升级后结束                      │
│  ⊕↩     Compensation End     触发补偿后结束                      │
│  ⊕✖     Cancel End           取消事务后结束                      │
│  ⊕✖✖    Terminate End        立即终止整个流程（含所有分支）       │
│  ⊕//    Multiple End         触发多个结果后结束                  │
└──────────────────────────────────────────────────────────────────┘
```

**边界事件（Boundary Events）：**

附着在活动边框上的中间事件，表示活动执行过程中可能发生的异常。

```
  ┌──────────────┐
  │              │
  │   活动       ◎⏱  ← 边界定时事件：活动超时时触发
  │              │
  └──────────────┘
         │
         ▼
    超时处理流程

  ┌──────────────┐
  │              │
  │   活动       ◎✕  ← 边界错误事件：活动出错时触发
  │              │
  └──────────────┘
         │
         ▼
    错误处理流程
```

### 2.2 活动（Activities）

活动表示流程中"要做的工作"，用圆角矩形表示。

**任务（Tasks）— 原子活动，不可再分：**

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形      名称                含义                                │
├──────────────────────────────────────────────────────────────────┤
│ ┌──────┐  Abstract Task      抽象任务，未指定类型                 │
│ └──────┘                                                         │
│ ┌─👤──┐  User Task           需要人类执行的任务                   │
│ └──────┘                     例：审批、填写表单                   │
│ ┌─⚙──┐   Service Task       系统自动执行的任务                   │
│ └──────┘                     例：调用 API、执行计算               │
│ ┌─📜──┐  Script Task         执行脚本的任务                      │
│ └──────┘                     例：运行 Python 脚本                │
│ ┌─✉↑──┐  Send Task           发送消息的任务                      │
│ └──────┘                     例：发送邮件、推送通知               │
│ ┌─✉↓──┐  Receive Task        等待接收消息的任务                  │
│ └──────┘                     例：等待回复、等待回调               │
│ ┌─⊞──┐   Business Rule Task  执行业务规则的任务                  │
│ └──────┘                     例：计算折扣、风险评估               │
│ ┌─🔧──┐  Manual Task         完全由人工执行，无系统辅助           │
│ └──────┘                     例：搬运物品、现场检查               │
└──────────────────────────────────────────────────────────────────┘
```

**子流程（Sub-Processes）— 复合活动，内部包含完整流程：**

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形          名称                含义                            │
├──────────────────────────────────────────────────────────────────┤
│ ┌─ ─ ─ ─┐                                                       │
│ │   +    │    Collapsed          折叠子流程，内部细节隐藏          │
│ └─ ─ ─ ─┘    Sub-Process        点击展开可看到内部流程            │
│                                                                  │
│ ┌─────────────────────────┐                                      │
│ │ ○→ 步骤1 → 步骤2 → ⊕  │  Expanded          展开子流程        │
│ └─────────────────────────┘  Sub-Process        直接显示内部流程  │
│                                                                  │
│ ┌─ ─ ─ ─┐                                                       │
│ │  ⊞ +   │    Transaction       事务子流程                       │
│ └─ ─ ─ ─┘    Sub-Process        要么全部成功，要么全部回滚        │
│              (双线边框)          支持补偿和取消                    │
│                                                                  │
│ ┌─ ─ ─ ─┐                                                       │
│ │  ⚡ +   │    Event             事件子流程                       │
│ └─ ─ ─ ─┘    Sub-Process        由事件触发，不在主流程线上        │
│              (虚线边框)          例：全局错误处理、超时处理        │
│                                                                  │
│ ┌─ ─ ─ ─┐                                                       │
│ │  ~ +   │    Ad-Hoc             临时子流程                      │
│ └─ ─ ─ ─┘    Sub-Process        内部活动没有固定顺序              │
│              (波浪底线)          执行者自行决定顺序和次数          │
└──────────────────────────────────────────────────────────────────┘
```

**活动标记（Activity Markers）：**

```
  ┌──────────────┐
  │              │
  │   活动       │
  │      ↻       │  ← 循环标记：活动重复执行直到条件满足
  └──────────────┘

  ┌──────────────┐
  │              │
  │   活动       │
  │      ≡       │  ← 多实例标记（并行）：同时创建多个实例
  └──────────────┘

  ┌──────────────┐
  │              │
  │   活动       │
  │      |||     │  ← 多实例标记（顺序）：依次创建多个实例
  └──────────────┘
```

### 2.3 网关（Gateways）

网关控制流程的分支和合并，用菱形表示。

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形    名称                  含义                                │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ◇      Exclusive (XOR)      排他网关：只走一条分支              │
│  ╱╲                          分支时：评估条件，走第一个为真的     │
│  ╲╱                          合并时：任一分支到达即通过           │
│                              例：审批通过/不通过                  │
│                                                                  │
│  ◇+     Parallel (AND)       并行网关：所有分支同时执行          │
│  ╱╲                          分支时：同时启动所有出口分支         │
│  ╲╱                          合并时：等待所有分支都到达           │
│                              例：同时通知多个部门                 │
│                                                                  │
│  ◇○     Inclusive (OR)       包含网关：走一条或多条分支          │
│  ╱╲                          分支时：评估所有条件，走所有为真的   │
│  ╲╱                          合并时：等待所有已激活的分支到达     │
│                              例：根据订单金额，可能同时触发       │
│                              审批 + 风控 + 通知                   │
│                                                                  │
│  ◇⚡     Event-based          事件网关：等待事件决定走哪条路      │
│  ╱╲                          分支时：等待，第一个到达的事件       │
│  ╲╱                          决定走哪条分支                       │
│                              例：等待用户回复 或 超时             │
│                                                                  │
│  ◇*     Complex              复杂网关：自定义分支/合并逻辑       │
│  ╱╲                          用于上述网关都无法表达的场景         │
│  ╲╱                          需要自定义表达式                     │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**网关使用示例：**

```
排他网关（XOR）— 审批场景：

                    ◇ XOR
                   ╱ ╲
          approved╱   ╲rejected
                ╱     ╲
               ▼       ▼
          下一步     打回修改


并行网关（AND）— 同时通知多方：

               ◇+ AND (fork)
              ╱  │  ╲
             ╱   │   ╲
            ▼    ▼    ▼
         通知A  通知B  通知C
            ╲    │   ╱
             ╲   │  ╱
              ▼  ▼ ▼
              ◇+ AND (join)
                 │
                 ▼
              继续流程


包含网关（OR）— 根据条件走多条路：

                    ◇○ OR
                   ╱ │ ╲
        金额>1000 ╱  │  ╲ VIP客户
                 ╱   │   ╲
                ▼    │    ▼
             审批    │   VIP通道
                ╲    │   ╱
                 ╲   │  ╱
                  ▼  ▼ ▼
                  ◇○ OR (join)
                     │
                     ▼
                  继续流程

  如果金额>1000 且是 VIP，两条路都走
  如果只满足一个条件，只走一条
```

## 三、连接对象（Connecting Objects）

```
┌──────────────────────────────────────────────────────────────────┐
│ 图形          名称                含义                            │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│ ──────────>   Sequence Flow      顺序流：同一个池内的执行顺序     │
│               (实线箭头)          连接流对象（事件、活动、网关）   │
│                                                                  │
│ ─ ─ ─ ─ ─>   Message Flow       消息流：不同池之间的消息传递     │
│               (虚线空心箭头)      不能连接同一个池内的对象         │
│                                  例：客户 → 供应商 的订单消息     │
│                                                                  │
│ ·········>    Association         关联：将制品/数据连接到流对象    │
│               (点线箭头)          例：将注释连接到活动             │
│                                                                  │
│ ·····<····>   Data Association   数据关联：数据对象与活动的关系    │
│               (点线双向箭头)      表示数据的输入或输出             │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**条件顺序流和默认顺序流：**

```
  ──◇──────>    Conditional        条件顺序流：满足条件才走
                Sequence Flow      起点有小菱形标记
                (实线+菱形)

  ──/──────>    Default            默认顺序流：其他条件都不满足时走
                Sequence Flow      起点有斜线标记
                (实线+斜线)
```

## 七、BPMN 2.0 的分层体系

BPMN 2.0 定义了三个建模层次，从简单到复杂：

```
┌─────────────────────────────────────────────────────────────────┐
│  Level 1：描述性建模（Descriptive）                              │
│                                                                 │
│  面向：业务分析师                                                │
│  使用：基础元素（任务、网关、事件、泳道）                         │
│  目的：沟通和文档化                                              │
│  元素数量：~20 种                                                │
│                                                                 │
│  例：○ → 接单 → ◇审批 → 发货 → ⊕                              │
├─────────────────────────────────────────────────────────────────┤
│  Level 2：分析性建模（Analytical）                               │
│                                                                 │
│  面向：流程分析师                                                │
│  使用：Level 1 + 中间事件、子流程、消息流、数据对象              │
│  目的：详细分析和优化                                            │
│  元素数量：~35 种                                                │
│                                                                 │
│  例：加入超时处理、错误分支、跨部门消息传递                      │
├─────────────────────────────────────────────────────────────────┤
│  Level 3：可执行建模（Executable）                               │
│                                                                 │
│  面向：技术人员                                                  │
│  使用：全部元素 + 执行语义（表达式、数据映射、服务绑定）         │
│  目的：直接由流程引擎执行                                        │
│  元素数量：~50 种                                                │
│                                                                 │
│  例：加入脚本任务、业务规则、补偿处理、事务子流程                │
└─────────────────────────────────────────────────────────────────┘
```

## 八、BPMN 2.0 相比 ISO 5807 新增的核心能力

```
1. 角色与职责（泳道）
   ISO 5807：没有"谁来做"的概念
   BPMN 2.0：Pool 表示组织，Lane 表示角色

2. 事件系统
   ISO 5807：只有开始和结束
   BPMN 2.0：消息事件、定时事件、信号事件、错误事件、
             补偿事件、升级事件、边界事件...

3. 多种网关
   ISO 5807：只有判断（二选一或多选一）
   BPMN 2.0：排他(XOR)、并行(AND)、包含(OR)、
             事件网关、复杂网关

4. 跨组织协作
   ISO 5807：没有
   BPMN 2.0：消息流连接不同的池（组织）

5. 异常处理
   ISO 5807：没有
   BPMN 2.0：错误事件、补偿事件、取消事件、
             边界事件、事件子流程

6. 事务与补偿
   ISO 5807：没有
   BPMN 2.0：事务子流程（全部成功或全部回滚）、
             补偿处理器

7. 多种任务类型
   ISO 5807：只有"处理"
   BPMN 2.0：用户任务、服务任务、脚本任务、
             发送任务、接收任务、业务规则任务、手动任务

8. 数据建模
   ISO 5807：输入/输出符号
   BPMN 2.0：数据对象（带状态）、数据输入/输出、
             数据存储、数据集合、数据关联
```

# 流程图模型与节点原语设计

> 讨论如何将标准流程图（ISO 5807 / BPMN 2.0）的图形元素映射到 quantalithos-flow 的工作流模板，
> 使工作流模板能够完整表达流程图，支持可视化渲染。

---

## 一、问题背景

当前 flow 概要设计的工作流模板只有两种节点类型（task / session），只能表达线性流程 + 失败回退。
无法表达项目管理中常见的流程图元素：条件分支、并行分支、人工审批点、循环等。

如果要实现"用户在前端看到完整的项目流程图，并实时看到当前走到哪一步"，
工作流模板必须能完整表达标准流程图的所有图形元素。

---

## 二、标准参考文档

两份标准的完整描述见独立文档：

- [ISO 5807:1985 流程图标准](流程图标准-ISO5807.md) — 16 种基础符号，面向程序逻辑
- [BPMN 2.0 业务流程建模标准](流程图标准-BPMN2.md) — ~50 种符号，面向业务流程

## 三、ISO 5807 与 BPMN 2.0 对比

### 3.1 定位差异

```
ISO 5807 (1985)                         BPMN 2.0 (2013)
────────────────────────────────────────────────────────────────

面向：程序逻辑、数据处理               面向：业务流程、组织协作
年代：1985                              年代：2011 发布，2013 成为 ISO
符号：~16 种                            符号：~50 种
层次：单层                              层次：三层（描述/分析/可执行）
执行：不可执行                          执行：BPMN XML 可被引擎执行
组织：ISO                               组织：OMG → ISO/IEC 19510

一句话区别：
  ISO 5807 回答"程序怎么跑"
  BPMN 2.0 回答"业务怎么跑"
```

### 3.2 符号逐项对比

```
┌──────────────────┬──────────────────┬──────────────────────────┐
```

### 3.3 总结

```
ISO 5807 有但 BPMN 没有的（3 个）：
  - 准备符（Preparation）→ BPMN 用 Task 替代
  - 显示符（Display）→ BPMN 用 Task 替代
  - 手动输入符（Manual Input）→ BPMN 用 User Task 替代

BPMN 有但 ISO 5807 没有的（核心，15+ 个）：
  - 事件系统（30+ 种事件）
  - 多种网关（5 种）
  - 多种任务类型（8 种）
  - 多种子流程类型（5 种）
  - 泳道（Pool / Lane）
  - 消息流
  - 错误/补偿/升级/取消事件
  - 事务子流程
  - 边界事件
  - 活动标记（循环、多实例）
  - 数据对象状态
  - 分组

两者都有的（核心，8 个）：
  - 开始/结束
  - 处理/任务
  - 判断/排他网关
  - 并行
  - 子流程
  - 数据输入/输出
  - 注释
  - 连接符
```

### 3.4 对我们的启示

```
我们的平台是"AI Agent 协作完成软件研发"：

  ✅ 需要角色/职责划分 → 需要 BPMN 的泳道概念
  ✅ 需要多人协作 → 需要 BPMN 的消息流概念
  ✅ 需要等待用户确认 → 需要 BPMN 的事件概念
  ✅ 需要超时处理 → 需要 BPMN 的定时事件
  ✅ 需要错误处理 → 需要 BPMN 的错误事件
  ✅ 需要并行任务 → 需要 BPMN 的并行网关
  ✅ 需要条件分支 → 需要 BPMN 的排他网关
  ⚠️ 需要多人讨论 → ISO 5807 和 BPMN 都没有（我们的 session）
  ❌ 不需要跨组织协作 → 不需要 BPMN 的 Pool 间消息流
  ❌ 不需要事务回滚 → 不需要 BPMN 的事务子流程（Phase 1）

结论：以 BPMN 2.0 为主要参考，ISO 5807 作为基础图形补充。
     session（多人协作讨论）是我们独有的扩展，两个标准都没有。
```

### 4.2 我们独有的扩展：session

ISO 5807 和 BPMN 2.0 都没有直接对应 session（多人实时协作讨论）的图形。

BPMN 最接近的是 Ad-Hoc Sub-Process（临时子流程，内部活动没有固定顺序），但 Ad-Hoc Sub-Process 的参与者仍然是预定义的活动，不是"多人自由讨论"。

session 是我们的平台独有的扩展，保留为独立类型。

## 五、推荐方案：step 增加 type 字段

### 5.1 节点类型定义

```python
class StepType(str, Enum):
    """工作流节点类型 — 对应 ISO 5807 / BPMN 流程图图形"""

    # ── 核心类型（Phase 1 实现）──
    TASK = "task"                 # ┌───────┐  处理：一个 Agent 执行任务
    SESSION = "session"           # ┌─ ─ ─ ─┐  子流程：多人协作讨论

    # ── 流程控制类型（Phase 2 实现）──
    DECISION = "decision"         #   ╱╲      判断：根据上一步输出选择分支
    GATE = "gate"                 # ┌─👤──┐   人工审批：等待用户确认
    FORK = "fork"                 # ═══╤═══   并行分支：同时启动多个分支
    JOIN = "join"                 # ═══╧═══   并行合并：等待所有分支完成

    # ── ISO 5807 完整覆盖（Phase 2 定义，实现按需）──
    START = "start"               # ╭───╮     起始符：流程入口
    END = "end"                   # ╭─⊕─╮     终止符：流程出口
    SUB_PROCESS = "sub_process"   # ┌─+──┐    预定义处理：引用另一个完整工作流
    PREPARATION = "preparation"   # ┌────╲    准备符：初始化/环境准备
                                  # └────╱    Phase 1 用 task 替代，可视化时按此类型渲染
    IO = "io"                     # ╱    ╲    输入/输出：数据的输入或输出
                                  # ╲    ╱    Phase 1 用 input_refs/output_schema 替代
                                  #           可视化时作为 task 的附属图形渲染
    CONNECTOR = "connector"       #   ○       连接符：跨页/跨区域连接点
                                  #           Phase 1 不需要，前端渲染层处理
    MANUAL_OPERATION = "manual"   # ┌──────┐  手动操作：需要人类执行（非审批）
                                  #  ╲    ╱   如"用户手动验证线上环境"
                                  #   ╲──╱    Phase 1 用 gate 近似替代
    DATA_STORE = "data_store"     # ┌──────┐  数据存储：数据库/文件存储
                                  # └──────┘  Phase 1 不需要独立节点
                                  # (底部开口)  存储操作是 task 内部的工具调用
    DOCUMENT = "document"         # ┌──────┐  文档：产出的文档/产物
                                  # └──╮───┘  Phase 1 用 FlowArtifact 标注替代
    MULTI_DOCUMENT = "multi_doc"  # ┌──────┐  多文档：一组文档
                                  # ├──────┤  Phase 1 用 FlowArtifact 列表替代
                                  # └──╮───┘
    EVENT = "event"               #   ◎       中间事件：等待外部事件
                                  #           Phase 3 实现（CI 构建完成、API 回调等）
```

> **设计原则：定义完整，实现按需。**
>
> 所有 ISO 5807 标准图形都有对应的 StepType，保证数据模型的完整性。
> Phase 1 的 flow 引擎只处理 TASK 和 SESSION，遇到其他类型时：
> - PREPARATION → 当作 TASK 执行
> - IO / DOCUMENT / MULTI_DOCUMENT / DATA_STORE → 跳过（作为标注信息）
> - CONNECTOR → 跳过（前端渲染层处理）
> - MANUAL_OPERATION → 当作 GATE 处理
> - DECISION / GATE / FORK / JOIN / SUB_PROCESS / EVENT → Phase 2 实现
> - START / END → Phase 2 实现（Phase 1 隐含在 trigger: stage_entered 和 next: null）
>
> 前端可视化时，所有类型都可以渲染对应的图形，即使 flow 引擎还没实现该类型的执行逻辑。

**各类型的 Phase 1 降级策略：**

| 类型 | Phase 1 降级 | 可视化 |
|------|-------------|--------|
| task | ✅ 原生支持 | ┌───┐ 方框 |
| session | ✅ 原生支持 | ┌─ ─┐ 虚线框 |
| decision | 用 on_fail 近似 | ◇ 菱形 |
| gate | 定义在 pipeline 阶段边界 | ◇👤 带人形的菱形 |
| fork / join | TaskScheduler 代码逻辑 | ═══ 粗横线 |
| start / end | 隐含 | ○ / ⊕ 圆形 |
| sub_process | Agent 级 workflow 引用 | ┌─+─┐ 带加号的框 |
| preparation | 当作 task | ┌──╲ 六边形 |
| io | 跳过，用字段替代 | ╱╲ 平行四边形 |
| connector | 跳过 | ○ 小圆 |
| manual | 当作 gate | ┌──╲╱ 梯形 |
| data_store | 跳过 | ┌──┐ 底部开口框 |
| document | 跳过，用 artifact 替代 | ┌──╮ 卷角框 |
| multi_doc | 跳过，用 artifact 列表替代 | ┌──╮╮ 叠层卷角框 |
| event | Phase 3 | ◎ 双圈 |

### 5.2 各类型的 YAML 格式

**task — 处理节点（已有，不变）：**

```yaml
- id: implement
  type: task
  actor: developer
  action: "按任务卡要求实现功能"
  allowed_tools: [file_read, file_write, code_execute, git_commit]
  workflow: tdd_workflow
  output_schema: {...}
  next: review_decision
```

**session — 子流程节点（已有，不变）：**

```yaml
- id: brainstorm
  type: session
  session:
    moderator: tech_lead
    participants: [tech_lead, backend_dev, frontend_dev, tester]
    agenda: "讨论需求的可行性、风险和建议"
  allowed_tools: [file_read, search_docs]
  output_schema: {...}
  next: scope_refinement
```

**decision — 判断节点（新增）：**

```yaml
- id: review_decision
  type: decision
  description: "根据代码审查结果决定下一步"
  input_ref: code_review.output       # 读取上一步的输出
  conditions:
    - when: "verdict == 'approved'"
      next: testing
    - when: "verdict == 'needs_revision'"
      next: implement
  default: implement                   # 所有条件都不满足时的默认分支
```

**gate — 人工审批节点（新增）：**

```yaml
- id: user_direction_confirm
  type: gate
  description: "用户确认需求方向"
  gate_config:
    title: "需求方向确认"
    gate_type: hard
    timeout_minutes: 4320
    artifacts_from: [scope_refinement]
    actions:
      - { action_type: approve, label: "方向正确" }
      - { action_type: request_changes, label: "需要调整" }
      - { action_type: reject, label: "方向不对" }
  on_approve: write_prd
  on_request_changes: collect_requirements    # 回到需求收集
  on_reject: null                             # 终止流程
```

**fork — 并行分支节点（新增）：**

```yaml
- id: parallel_dev_start
  type: fork
  description: "多任务并行开发"
  branches:
    - task_001_workflow      # 每个分支是一个独立的工作流实例
    - task_002_workflow
    - task_004_workflow
  join: parallel_dev_end     # 指向对应的 join 节点
```

**join — 并行合并节点（新增）：**

```yaml
- id: parallel_dev_end
  type: join
  description: "等待所有并行任务完成"
  fork: parallel_dev_start   # 指向对应的 fork 节点
  next: integration_test     # 全部完成后进入集成测试
```

### 5.3 边类型

```python
class EdgeType(str, Enum):
    """流程线类型"""
    SEQUENCE = "sequence"           # ────>  顺序：next 字段
    CONDITIONAL = "conditional"     # ---->  条件：decision 的 conditions
    ON_FAIL = "on_fail"             # ╌╌╌>  失败回退：on_fail 字段

    ON_REJECT = "on_reject"         # ╳╳╳>  审批驳回：gate 的 on_reject
    FORK_BRANCH = "fork_branch"     # ═══>  并行分支：fork 的 branches
    JOIN_BRANCH = "join_branch"     # ═══>  并行合并：join 的 fork
```

## 六、改动前后对比

### 6.1 requirement_analysis 工作流

**改动前（只有 task/session + next/on_fail）：**

```
collect ──next──> brainstorm ──next──> write_prd ──next──> review_prd
                                          ↑                    │
                                          └────── on_fail ─────┘

问题：
  - 没有"用户方向确认"中间门禁
  - 没有"范围收敛"步骤

```

```
  ▼

         │
         ▼
┌─ ─ ─ ─ ─ ─ ─ ─ ┐
```

## 七、Phase 分期

### Phase 1（当前）

只实现 `task` 和 `session` 两种节点类型，用 `next` / `on_fail` 连接。
gate 仍然定义在 pipeline template 的阶段边界上。
并行调度仍然由 TaskScheduler 代码逻辑处理。

**Phase 1 的模板格式不变**，本文档的设计在 Phase 2 实现。

### Phase 2

引入完整节点类型：

| 节点类型 | 优先级 | 说明 |
|---------|--------|------|
| decision | 高 | 替代 on_fail 的隐含判断，支持多条件分支 |
| gate | 高 | 从 pipeline 下沉到 step 级，支持中间门禁 |
| fork / join | 中 | 将并行调度从代码逻辑提升到模板显式表达 |

引入后的好处：
- 工作流模板可以完整表达流程图
- 前端可以直接从模板渲染流程图，不需要额外的可视化逻辑
- 流程变更只改模板 YAML，不改代码

### Phase 1 → Phase 2 兼容性

Phase 1 的模板在 Phase 2 中仍然有效：
- `type` 默认为 `task`（不写 type 就是 task）
- `next` / `on_fail` 仍然工作
- 阶段边界的 gate_type 仍然工作

Phase 2 是增量扩展，不是破坏性变更。

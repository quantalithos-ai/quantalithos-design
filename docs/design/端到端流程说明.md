## 四、关键设计决策汇总

本文档涉及的所有设计决策，集中记录便于回溯。

### 4.1 策略注册表 vs visitor 模式

```
问题：同一个 BPMN 对象在 flow 和 runtime 中行为不同

  visitor 模式（废弃）：
    对象有 accept(visitor) → 对象知道 visitor 的存在
    新增节点类型 → 改所有 visitor（ISP 违反）

  标准策略模式（废弃）：
    对象持有 executor 策略实例
    序列化时 executor 丢失 → 从 YAML 加载时不知道注入哪个

  策略注册表（采纳）：
    对象完全不知道策略的存在（纯数据 + 领域行为）
    BPMNEngine 按 node_type 查表调用策略
    新增节点类型 = 加一个类 + 注册一个策略，不改任何已有代码
```

### 4.2 消息类型从 10 种精简为 6 种

```
问题：task_assign / session_start / session_end 是 BPMN 中不存在的概念

  旧设计：每种 BPMN 节点类型对应一种自造的消息类型
    flow 需要理解 runtime 的内部行为才能构造正确的消息

  新设计：节点执行统一为 node_execute，payload 带序列化的 FlowNode
    runtime 收到后反序列化为具体类型，按 node_type 查表调用策略
    和 BPMN 完全对齐

  6 种消息类型：
    生命周期：agent_create / agent_destroy / agent_suspend / agent_resume
    节点执行：node_execute / node_cancel
    消息路由：chat_message
```

### 4.3 StackState 从 5 种改为 3 种

```
问题：TASK / SESSION / REPLY / WAITING 把"在做什么"和"怎么做"混在一起

  旧设计：5 种状态（IDLE / TASK / SESSION / REPLY / WAITING）
    SESSION 和 TASK 平级，但 SESSION 只是 TASK 的一种子模式
    新增节点类型（ServiceTask）→ 要不要加新的 StackState？

  新设计：3 种主状态 + 上下文驱动
    IDLE / EXECUTING / SUSPENDED
    具体在做什么由 context.node_type 决定
    中断原因由 context.reason 决定（reply / waiting）
    新增节点类型 → 只改 context.node_type，不改 StackState
```

### 4.4 AdHocSubProcess 通用化

```
问题：moderator_id / participant_ids / agenda 是讨论专用字段

  BPMN 标准的 AdHocSubProcess = 内部活动没有固定顺序
  不只是"讨论"，还可以是"项目准备"（租办公室+招人+买设备）

  新设计：
    BPMN 标准字段：ordering / completion_condition / cancel_remaining
    通用扩展：participant_ids / coordinator_id / inner_activities
    场景配置：metadata dict（讨论：{agenda}，准备：{checklist}）
    不再有 session / moderator 概念
```

### 4.5 对象自治（领域行为封装在对象上）

```
问题：ExclusiveGateway 的条件评估放在 BPMNEngine 中

  旧设计：BPMNEngine.evaluate_exclusive() 承担了领域逻辑
  新设计：ExclusiveGateway.evaluate(edges, outputs) → 对象自己评估

  判断标准：
    引擎职责 = 和 Token 流转相关（遍历、推进、分裂、合并）
    对象行为 = 对象自己知道的事（不需要知道 Token 和引擎的存在）

  已封装的领域行为：
    ExclusiveGateway.evaluate()        → 条件评估
    ParallelGateway.get_fork_targets() → fork 目标
    ParallelGateway.is_join_complete() → join 判断
    EndEvent.is_terminate()            → 是否终止所有
    AbstractTask.validate_output()     → 输出校验
    AdHocSubProcess.is_complete()      → 完成条件评估
```

### 4.6 ProcessDefinition 传完整对象而非 ID

```
问题：runtime 收到 process_id 后需要再次请求 platform 加载

  旧设计：FlowMessage 传 process_id，runtime 再请求 platform
    → 两次网络请求
    → 执行过程中模板被修改 → 版本不一致

  新设计：flow 加载一次 ProcessDefinition，完整放入 FlowMessage
    → runtime 直接 from_dict()，不再请求 platform
    → 版本一致性保证（flow 发出时的版本 = runtime 执行的版本）
```

### 4.7 设计系统为什么不用 SharedRule

```
问题：Design Tokens 能否用 SharedRule 存储

  SharedRule 的设计初衷 = 跨角色共享的行为约束
    有 schema_def → 注入 prompt 第一层（硬约束）
    无 schema_def → 注入 prompt 第三层（软指引）

  SharedRule 能做到：Design Tokens（颜色/字体/间距）
    → 注入到前端开发 Agent 的 prompt 中

  SharedRule 做不到：组件库
    → 组件库不是"规则"，是"可复用的代码模板"
    → Agent 需要"拿到一个按钮组件直接用"
    → 不是"被告知按钮应该长什么样然后自己写"

  结论：platform 新增 hub-design 模块
    → Design Tokens + 组件库 + 原型管理
    → 独立于 SharedRule
```

### 4.8 TL 自定义工作流（fork + 从零创建）

```
问题：标准 tdd_workflow 不满足所有任务的需求

  标准 tdd_workflow：
    ○ → [写测试] → [运行红] → [写代码] → [运行绿] → ◇ → ⊕

  TASK-005 评论系统需要安全扫描：
    ○ → [写测试] → [运行红] → [写代码] → [安全扫描] → [运行绿] → ◇ → ⊕
                                           ↑ 新增步骤

  TL 有三种选择：
    选择 1：直接用标准流程（process_id: "tdd_workflow"）
    选择 2：不用工作流（control_level: "guided"）
    选择 3：自定义工作流
```

## 五、12 个子项目在博客项目中的角色

```
子项目              在博客项目中做了什么
──────              ──────────────────

core                BPMN 引擎驱动所有流程（6 个阶段 + TDD 工作流）
                    Token 管理（并行任务分裂/合并）
                    策略注册表（flow 和 runtime 各自注册策略）
                    SandboxProvider 接口（runtime 工具调用 sandbox）

runtime             运行 5 个 Agent（Assistant + TL + BE-1 + FE-1 + QA-1）
                    think→act 循环（LLM 调用 + 工具执行）
                    三级控制（Free / Guided / Enforced）
                    工具系统（file_write / code_execute / git_commit → sandbox）

flow                驱动 standard_pipeline（6 阶段）
                    驱动 requirement_analysis / design_and_planning 等阶段流程
                    监听 platform 事件 → 构造 FlowMessage
                    门禁控制（UserTask → GateCard）

platform            存储项目 / 工单 / 产物 / Agent 配置 / 快照
                    工单状态机（created → assigned → ... → completed）
                    任务调度（依赖图 + 波次 + 自动指派）
                    事件总线（WorkItemAssigned / TaskBecameReady）
                    hub-integration（Git 元数据 + 构建产物）
                    hub-design（Design Tokens + 组件库）

sandbox             dev 模式：5 个 Agent 容器 + PostgreSQL + Redis
                    Agent 的 file_write / code_execute 在容器内执行
                    preview 模式：统一部署 → 用户体验博客系统
                    build 模式：构建生产版本 → 上传 platform

gate                认证（JWT）+ 路由（转发到 platform/flow/runtime/sandbox）
                    preview URL 反向代理
                    WebSocket 事件推送（Phase 2）

sdk                 chat / console / runner 共用的 API 客户端
                    sdk-models（Rust 数据模型）
                    sdk-api（platform API 封装）
                    sdk-wasm（WASM 绑定给前端用）

chat                用户和 Agent 聊天的界面
                    门禁审批卡片
                    项目进度条
                    Agent 实时执行面板

console             项目管理仪表盘
                    Agent 配置编辑器（Monaco YAML）
                    Git 代码浏览器
                    沙箱监控（容器状态 + 日志）
                    构建管理

runner              用户体验博客系统的 App
                    从 platform 下载构建产物
                    WebView 容器运行博客系统
                    版本管理（更新 / 回滚）

sync                本地工作区同步
                    sync init → 创建本地项目目录
                    sync restore → 从 platform 拉取产物到本地

infra               Docker Compose（所有服务 + Gitea）
                    数据库迁移（13 张表）
                    初始数据（角色 + 规则 + 流程模板）
                    setup-dev.sh 一键启动
```

# 阶段 0 / 1 / 2 前置步骤补点映射（临时稿）

> 目的：将当前流程中相对缺失的前置步骤，映射回现有的 `阶段0 / 阶段1 / 阶段2`，避免额外硬拆新大阶段。

---

## 一、结论概览

缺失的前置步骤不一定要单独新增一个“大阶段”，更适合按职责分别补入现有阶段：

- `阶段0` 补：目标校准、项目类型与优先级识别
- `阶段1` 补：范围收敛、版本范围与 MVP 收敛、评审意见结构化、验收口径、非功能需求初版、阶段1交接包、最终批准门禁
- `阶段2` 补：技术可行性验证、外部依赖 readiness、非功能需求设计映射、实施前综合门禁

---

## 二、映射总表

| 缺失步骤 | 建议补入阶段 | 说明 |
|----------|-------------|------|
| 问题定义 / 目标校准 | `阶段0` | 这是项目启动语义，不应拖到需求或设计阶段 |
| 版本范围 / MVP 收敛 | `阶段1` | 属于需求边界确认，决定“本次到底做什么” |
| 产品原型 / 交互预演 | `阶段1` | 本质是帮助确认需求，而不是实施设计 |
| 技术可行性验证 / PoC | `阶段2` | 已进入“怎么做”的范畴，但还没到正式全面设计 |
| 非功能需求收口 | `阶段1` 初收口，`阶段2` 定稿 | 先确认要求，再转成设计约束 |
| 外部依赖 readiness check | `阶段2` | 与实施准备强相关，应作为开工前门禁 |
| 验收口径结构化 | `阶段1` | 本质属于需求完成定义，不能等到开发后再说 |

## 三、阶段 0 应补什么

### 1. 目标校准（推荐新增）

建议在 `project_application` 生成之后、正式建群或 TL 接管之前，补一个轻量的目标校准步骤。

建议回答：

- 这次要解决的核心问题是什么
- 这是新需求、优化、缺陷还是探索项
- 为什么现在做
- 目标用户是谁
- 成功标准是什么
- 当前版本优先级是什么

### 2. 为什么放在阶段 0

因为这一步不是需求细化，也不是设计，而是：

- 项目启动语义确认
- 任务类型识别
- 后续流程选择依据

如果这一步缺失，后面可能会出现：

- 在目标不清的情况下进入需求澄清
- 在方向未稳的情况下进入方案设计
- 做了很多设计，但优先级判断错误

### 3. 建议产物

- `project_intent_alignment`
- `goal_alignment_brief`
- 更新版 `project_application`

### 4. 建议在阶段 0 中的位置

```text
用户想法 / 填表
  -> project_application
  -> 目标校准
  -> 规模评估 / 团队组装
  -> 建群
  -> TL 接管
```

## 四、阶段 1 应补什么

### 1. 版本范围 / MVP 收敛（推荐新增）

建议在需求澄清与团队头脑风暴之后，显式增加一轮范围收敛，并把它正式化为阶段 1 的必经子步骤。

建议回答：

- 本次版本到底做什么
- 哪些功能进入 MVP / 当前版本范围
- 哪些明确延后
- 哪些不纳入本轮
- 本轮成功标准是什么
- 范围未收敛时应补问、暂停还是回退

### 2. 为什么放在阶段 1

因为它回答的是“这次做什么 / 不做什么”，本质仍然是需求边界，而不是设计边界。

同时它必须承接阶段 0 已形成的正式入口，而不是重新做目标校准：

- 阶段 1 输入基于 `assistant_startup_handoff + goal_alignment_brief`
- 只有 `alignment_status = passed` 且 `recommended_route = stage1_requirement_analysis` 时，才进入本步骤

### 3. 建议产物

- `version_scope_brief`
- `deferred_items`
- `acceptance_outline`
- `nfr_initial_profile`

其中 `version_scope_brief` 建议至少显式包含：

- `mvp_goal`
- `in_scope_items`
- `out_of_scope_items`
- `deferred_items`
- `scope_status`
- `followup_questions`
- `next_action`

并进一步补到正式契约层：

- 明确字段允许值、写入方、消费方、更新规则
- 为 `scope_status` 定义状态机
- 明确它与 `用户方向确认` 的状态推进关系
- 明确它与 `acceptance_outline`、`nfr_initial_profile` 的边界

### 4. 建议插入位置

```text
阶段1入口校验
  -> 初始需求收集
  -> 澄清回路
  -> 团队头脑风暴
  -> 版本范围 / MVP 收敛
  -> 用户方向确认
  -> 全员需求评审
```

当前已固定的默认插入位置：

8. `阶段2 / 实施前综合门禁`（已完成）

### 为什么按这个顺序讨论

因为这些补点之间存在明确依赖：

- 先定“为什么做、做到什么算有价值”
- 再定“这次到底做什么、什么不做”
- 再定“什么叫完成、以什么口径验收”
- 再补“约束条件与风险前提”
- 最后才讨论“技术是否可行、依赖是否就绪、能否正式开工”

如果跳过前面的目标、范围和验收定义，直接讨论 PoC 或 readiness，容易变成：

- 在尚未收敛的目标上做技术验证
- 在尚未明确完成标准的情况下评估是否可以开工

## 七、议题 1：阶段 0 的目标校准

### 1. 建议结论

我建议把 `目标校准` 定义为 `阶段0` 的正式子步骤。

它位于：

- `project_application` 生成之后
- `规模评估 / 团队组装` 之前

它的作用不是细化需求，也不是进入方案设计，而是确认：

- 这个项目为什么现在启动
- 当前工作项属于什么类型
- 这一轮到底想达成什么结果
- 后续应该进入哪条正式流程

一句话说：

> `目标校准` 负责形成进入 `阶段1` 之前的项目意图基线，而不是提前展开需求分析。

### 2. 它要解决什么问题

我建议把它要解决的问题先收敛为下面五类：

- 项目类型判断不稳：新项目、增强、缺陷、优化、探索项容易混淆
- 启动目标不清：用户有想法，但没有说明“为什么现在做”
- 优先级语义缺失：知道要做什么，但不知道为什么这轮优先
- 成功标准缺失：后续会讨论很多细节，但一开始没人定义“做到什么才算值”
- 流程路由不准确：有些项应走完整需求流程，有些应先走快修、原型或 PoC

### 3. 它不解决什么

为了避免阶段 0 膨胀，`目标校准` 不应承担以下工作：

- 不做详细需求澄清
- 不做产品方案对比
- 不做架构设计
- 不做任务拆解
- 不做详细技术选型
- 不做工期排期承诺

也就是说，它只回答“为什么启动、属于什么类型、这轮想达成什么”，不回答“具体怎么做”。

### 4. 它与 `project_application` 的关系

建议将两者关系定义为：

- `project_application`：原始申请输入
- `goal_alignment_brief`：对申请输入的校准结果

建议链路如下：

```text
user input
  -> project_application
  -> goal alignment
  -> calibrated_project_brief
  -> team assembly / Stage 1 entry
```

这里不建议用 `目标校准` 直接替代 `project_application`，而更建议：

- 保留原始申请表
- 生成校准产物
- 必要时回写补充字段到更新版申请表

这样可以同时保留：

- 用户原始表述
- 系统当前确认口径
- 后续阶段可消费的结构化入口

### 5. 它是否应为必经步骤

我的建议是：

- 它是正式必经步骤
- 但保持轻量

也就是说：

- 低复杂项目可快速通过
- 高不确定项目会触发补问或阻断

因此更合理的定位是：

- `必经的轻门禁`

而不是：

- 可有可无的按需动作

### 6. 最小字段建议

建议先把 `目标校准` 的最小字段控制在下面 6 项：

- `work_item_type`：新项目、增强、缺陷、优化、探索项
- `core_problem`：核心要解决的问题是什么
- `target_outcome`：这一轮希望得到什么结果
- `target_users_or_scope`：面向谁、影响范围多大
- `priority_reason`：为什么现在做、优先级依据是什么
- `success_signal`：出现什么现象，可以认为这轮启动是值得的

在此基础上，我建议再附加两个系统字段：

- `uncertainty_level`
- `recommended_route`

因为这两个字段会直接影响后续：

- 阶段 1 的提问强度
- 是否需要插入原型、PoC 或快修流程

### 7. 建议产物

建议阶段 0 新增一个轻量产物：

- `goal_alignment_brief`

可以先抽象为：

```yaml
goal_alignment_brief:
  work_item_type: enhancement
  core_problem: "现有博客系统缺少评论能力，用户无法形成互动"
  target_outcome: "交付可用的评论 MVP，并可进入后续验收"
  target_users_or_scope: "博客访客与文章作者"
  priority_reason: "评论能力是内容互动闭环的缺失项"
  success_signal:
    - "访客可提交评论"
    - "作者可查看评论"
    - "核心评论流程可演示"
  uncertainty_level: medium
  recommended_route: stage1_requirement_analysis
```

### 8. 出口条件

建议把 `目标校准` 的出口条件定义为：

- 能判断工作类型
- 能说清本轮目标
- 能给出优先级理由
- 能定义初步成功信号
- 能决定进入哪条后续流程

这一步不要求：

- 所有需求细节都清楚
- 所有边界条件都清楚
- 所有设计问题都清楚

它的通过标准不是“信息完整”，而是“信息已经足以支撑类型判断、目标确认与流程路由”。

### 9. 失败时的处理方式

如果 `目标校准` 未通过，建议不要直接进入 `阶段1`，而是按原因分流：

- 信息不足：`Tech Lead` 通过 Assistant 或群聊补问 1~3 个关键问题
- 目标冲突：先让用户完成目标层取舍，再决定是否进入 `阶段1`
- 类型不清：先完成类型校准，再决定走哪条流程
- 明显不适合走需求流程：改走缺陷、运维、调研或探索通道

### 10. 建议插回阶段 0 的位置

```text
用户输入 / 填表
  -> Assistant 整理申请
  -> project_application
  -> Tech Lead 执行目标校准
  -> 项目类型与路由判断
  -> 规模评估 / 团队组装
  -> 建群
  -> 项目 Tech Lead 接管
```

### 11. 当前收敛结论

这一议题当前建议先收敛为：

- `目标校准` 是 `阶段0` 的正式子步骤
- 它位于 Assistant 完成申请整理之后、团队组装之前
- 它是必经但轻量的步骤
- 它不做需求细化，只做目标、类型、优先级与成功信号校准
- 它的核心产物是 `goal_alignment_brief`
- 它的主要作用是为 `阶段1` 和流程分流提供稳定入口

## 八、最简版落地建议

如果只保留最必要的补点，我建议：

### 阶段 0

- 补 `目标校准`
- 补 `Assistant 标准启动流程`
- 补 `assistant_startup_handoff` 首版 Schema
- 补 `assistant_startup_handoff` 正式字段规范（允许值 / 写入方 / 消费方 / 更新规则）
- 补 `Assistant 启动状态机`

当前这部分已经进一步收敛为：

- `assistant_startup_handoff` 不只是示例对象，而是启动交接契约
- 它至少要明确字段分层、允许值、写入责任、消费责任和更新边界
- `Assistant` 负责创建并投递交接包，`Tech Lead` 从接手开始负责后续校准与推进
- 一旦交接被 `accepted`，主导责任就不应再回退给 Assistant
- `goal_alignment_brief` 也应升级为正式结构化产物，而不只是几条口头判断
- `阶段1` 的正式入口应基于 `assistant_startup_handoff + goal_alignment_brief`
- 只有当 `alignment_status = passed` 且 `recommended_route = stage1_requirement_analysis` 时，才进入 `阶段1`

### 阶段 1

- 补 `范围 / MVP 收敛`
- 补 `评审意见结构化`
- 补 `验收口径结构化`
- 补 `非功能需求初版`
- 补 `stage1_handoff_package` 正式交接契约
- 补 `stage1_approval_record` 最终批准门禁
- `原型 / 交互预演` 已 formalize 为条件触发侧线

### 阶段 2

- `技术可行性验证 / PoC` 已 formalize 为条件触发侧线
- `外部依赖 readiness check` 已 formalize 为条件触发侧线
- `非功能需求设计映射` 已 formalize 为主线必经步骤
- `实施前综合门禁` 已 formalize 为双 gate 收口机制

- `阶段0` 补“目标对不对”

- `阶段2` 补“技术行不行、依赖齐不齐、能不能开工”

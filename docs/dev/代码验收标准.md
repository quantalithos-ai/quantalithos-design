# 代码验收标准

> AI 编写的代码在合并前必须通过的验收检查。
> 适用于：所有子项目的每次阶段提交和 PR 审查。

---

## 一、为什么需要代码验收

本项目的代码全部由 AI 编写（Claude / Codex / ChatGPT 等）。AI 编码有几个已知的系统性风险：

| 风险 | 表现 | 后果 |
|------|------|------|
| 偏离设计文档 | AI 自由发挥，添加设计中没有的模块或改变接口签名 | 服务间对接失败，返工 |
| 走捷径 | 用 `unwrap()` / `panic!` / bare `except` 跳过错误处理 | 运行时崩溃，难以排查 |
| 密钥泄露 | 把 API Key 硬编码在代码或测试中 | 安全事故 |
| 协议不一致 | 不同 AI 各写各的，FlowMessage 字段名/类型不对齐 | 联调时序列化失败 |
| 注释质量差 | 写"做了什么"而非"为什么这样做" | 后续维护困难 |

代码验收的目标是**在合并前拦截这些问题**，而不是在联调时才发现。

## 二、验收维度

### 维度 A：设计一致性

**核心问题：代码是否忠实实现了设计文档？**

AI 最常见的偏离方式是"自作主张"——设计文档说用 Strategy 模式，AI 用了 if-else；设计文档定义了 5 个字段，AI 加了第 6 个。

#### A-1 目录结构

| 检查项 | 对照来源 | 判定标准 |
|--------|---------|---------|
| 代码目录结构与详细设计一致 | 详细设计 §一（目录结构） | 每个设计中定义的目录和文件都存在；没有设计中未定义的顶层模块 |
| 文件职责与设计描述一致 | 详细设计 §一（文件职责表） | 文件名和内容对应设计中的描述 |

**验证方法：**

```bash
# 列出代码目录结构
find . -name "*.rs" -o -name "*.py" -o -name "*.ts" | sort

# 与详细设计 §一 的目录树逐项对比
```

**常见偏离：**
- AI 把多个模块合并到一个文件（"我觉得放一起更方便"）→ 拒绝，按设计拆分
- AI 新增了设计中没有的 `utils.rs` / `helpers.py` → 审查是否必要，必要则补充设计文档

#### A-2 数据模型

| 检查项 | 对照来源 | 判定标准 |
|--------|---------|---------|
| struct / class 字段与详细设计一致 | 详细设计 §二（数据模型） | 字段名、类型、可选性完全匹配 |
| 枚举值与详细设计一致 | 详细设计 §二 | 枚举变体名称和含义一致 |
| 没有设计中未定义的字段 | — | AI 不得自行添加字段 |

**验证方法：**

```bash
# Rust：提取 struct 定义
grep -n "pub struct\|pub enum" src/**/*.rs

# Python：提取 class 定义
grep -n "class " quantalithos_*/**.py
```

**常见偏离：**
- AI 给 struct 加了 `created_by` 字段（设计中没有）→ 拒绝，除非有充分理由并更新设计
- AI 把 `Option<String>` 改成 `String`（去掉了可选性）→ 拒绝，可选性是契约的一部分

#### A-3 接口契约

| 检查项 | 对照来源 | 判定标准 |
|--------|---------|---------|
| API 路由路径与详细设计一致 | 详细设计 §三（API 路由表） | 路径、HTTP 方法、请求体、响应体完全匹配 |
| 函数签名与详细设计一致 | 详细设计（伪代码 / 骨架） | 参数名、参数类型、返回类型一致 |
| 错误类型与详细设计一致 | 详细设计 §六（错误处理） | 错误枚举变体和 HTTP 状态码映射一致 |

**常见偏离：**
- AI 把 `POST /api/projects` 改成 `POST /projects`（去掉了 `/api` 前缀）→ 拒绝
- AI 把返回类型从 `Result<Project, ServiceError>` 改成 `Result<Project, anyhow::Error>`（丢失了错误类型信息）→ 拒绝

#### A-4 设计模式

| 检查项 | 对照来源 | 判定标准 |
|--------|---------|---------|
| 使用的设计模式与设计文档一致 | 概要设计 + 设计模式使用规范 | Strategy / Observer / Repository 等模式按设计使用 |
| 没有引入设计中未规划的模式 | 设计模式使用规范 | AI 不得自行引入 Singleton / Service Locator 等 |

### 维度 B：代码质量与安全

**核心问题：代码是否健壮、安全、可维护？**

#### B-1 错误处理

| 语言 | 禁止项 | 替代方案 |
|------|--------|---------|
| Rust | `unwrap()` / `expect()` 在非初始化代码中使用 | `?` 操作符 + 自定义 Error enum |
| Rust | `panic!` 在库代码中使用 | 返回 `Result` |
| Python | bare `except:` / `except Exception:` | 捕获具体异常类型 |
| Python | `pass` 在 except 块中（静默吞掉错误） | 至少 log warning |
| TypeScript | `any` 类型 | 定义具体类型 |

**验证方法：**

```bash
# Rust：检查 unwrap/expect 使用
grep -rn "\.unwrap()\|\.expect(" src/ --include="*.rs" | grep -v "test\|#\[cfg(test)\]"

# Python：检查 bare except
grep -rn "except:" quantalithos_*/ --include="*.py"
grep -rn "except Exception" quantalithos_*/ --include="*.py"
```

**例外情况：**
- 初始化阶段（`main.rs` / `main.py`）的不可恢复错误可以用 `unwrap()` / `expect()`
- 测试代码中可以用 `unwrap()`

#### B-2 安全

| 检查项 | 判定标准 | 验证方法 |
|--------|---------|---------|
| 无硬编码密钥 | 代码中不包含 API Key / 密码 / JWT Secret 的字面值 | `grep -rn "sk-\|password\|secret" src/ --include="*.rs"` |
| 无 SQL 拼接 | 所有 SQL 使用参数化查询（sqlx `$1` / `?`） | `grep -rn "format!.*SELECT\|format!.*INSERT" src/` |
| 输入校验 | API 入参有长度/格式/范围校验 | 审查 handler 层的参数校验逻辑 |
| 敏感信息不入日志 | 日志中不打印 token / password / API Key | `grep -rn "log.*token\|log.*password\|log.*key" src/` |

#### B-3 注释质量

对照 `docs/design/实施计划书写规范.md` §前置条件 3 的注释规范：

| 检查项 | 判定标准 |
|--------|---------|
| struct / class 有文档注释 | 说明职责和使用场景 |
| 每个成员变量有注释 | 说明语义和约束（单位、格式、取值范围） |
| 函数有文档注释 | 说明作用、前置条件、返回值语义、可能错误 |
| 关键步骤有行内注释 | 说明"为什么这样做"而非"做了什么" |
| 易错处有 CAUTION / NOTE 标记 | 并发陷阱、超时歧义、边界条件 |

**常见问题：**
- AI 写 `// Create the project`（描述做了什么）→ 应该写 `// Must create project before workitems — workitems reference project_id`（描述为什么）
- AI 不写前置条件 → 调用方不知道传 None 会怎样

#### B-4 依赖合规

| 检查项 | 判定标准 |
|--------|---------|
| 依赖在设计文档选型范围内 | 概要设计 §技术选型 中列出的依赖 |
| 无不必要的依赖 | AI 不得引入设计中未规划的框架或库 |
| 依赖版本锁定 | Cargo.lock / requirements.txt / package-lock.json 已提交 |

**验证方法：**

```bash
# Rust：检查 Cargo.toml 依赖
cat Cargo.toml | grep "^\[dependencies" -A 50

# Python：检查 requirements.txt
cat requirements.txt
```

**常见偏离：**
- AI 引入 `anyhow` crate（设计中要求用自定义 Error enum）→ 拒绝
- AI 引入 `colorama`（设计中没有终端美化需求）→ 拒绝

### 维度 C：跨服务协议一致性

**核心问题：多个 AI 各自编写的服务，能否正确通信？**

这是 AI 编码项目最容易出问题的地方。每个服务可能由不同的 AI 在不同的会话中编写，它们对共享协议的理解可能不一致。

#### C-1 FlowMessage 协议

FlowMessage 是 flow → runtime 的核心通信协议，定义在 `quantalithos-core` 中。

| 检查项 | 验证方法 |
|--------|---------|
| flow 发送的 FlowMessage 字段与 core 定义一致 | 对比 flow 的 `runtime_client.py` 与 core 的 `FlowMessage` 模型 |
| runtime 接收的 FlowMessage 解析与 core 定义一致 | 对比 runtime 的 `main_loop.py` 与 core 的 `FlowMessage` 模型 |
| payload 类型（NodeExecutePayload / ChatMessagePayload）字段一致 | 逐字段对比 |

**验证方法：**

```bash
# 提取 core 中的 FlowMessage 定义
grep -A 20 "class FlowMessage" quantalithos-core/python/src/quantalithos_core/*.py

# 提取 flow 中的 FlowMessage 使用
grep -n "FlowMessage\|FlowMessageType" quantalithos-flow/quantalithos_flow/**/*.py

# 提取 runtime 中的 FlowMessage 使用
grep -n "FlowMessage\|FlowMessageType" quantalithos-runtime/quantalithos_runtime/**/*.py
```

#### C-2 NodeResult 协议

NodeResult 是 runtime → flow 的返回协议。

| 检查项 | 验证方法 |
|--------|---------|
| runtime 返回的 NodeResult 字段与 core 定义一致 | 对比 runtime 的 `main_loop.py` 返回值与 core 的 `NodeResult` 模型 |
| flow 解析的 NodeResult 与 core 定义一致 | 对比 flow 的 `event_loop.py` 解析逻辑与 core 模型 |
| result_type 枚举值一致 | `completed` / `failed` / `cancelled` / `suspended` |

#### C-3 platform API 协议

platform 的 API 被 gate（路由转发）、flow（事件轮询）、runtime（数据查询）三方调用。

| 检查项 | 验证方法 |
|--------|---------|
| gate 转发的路径与 platform 路由表一致 | 对比 gate 的路由配置与 platform 的 handler 注册 |
| flow 调用的 platform API 路径和参数一致 | 对比 flow 的 `platform_client.py` 与 platform 的路由表 |
| runtime 调用的 platform API 路径和参数一致 | 对比 runtime 的 `platform_client.py` 与 platform 的路由表 |

**验证方法：**

```bash
# 提取 platform 路由
grep -rn "\.route\|\.get\|\.post\|\.put\|\.delete" quantalithos-platform/src/ --include="*.rs" | grep -v test

# 提取 gate 路由配置
grep -rn "upstream\|proxy\|route" quantalithos-gate/src/ --include="*.rs"

# 提取 flow 的 platform 调用
grep -rn "platform_client\|/api/" quantalithos-flow/quantalithos_flow/ --include="*.py"
```

#### C-4 跨服务一致性验证脚本

建议在联调前执行以下自动化检查：

```bash
# 1. 检查 core 导出的模型是否被 flow 和 runtime 正确导入
cd quantalithos-core && python -c "from quantalithos_core import FlowMessage, NodeResult, FlowMessageType; print('core exports OK')"

cd quantalithos-flow && python -c "from quantalithos_core import FlowMessage, NodeResult; print('flow imports OK')"

cd quantalithos-runtime && python -c "from quantalithos_core import FlowMessage, NodeResult, FlowMessageType; print('runtime imports OK')"

# 2. 检查 FlowMessageType 枚举值在三方一致
python3 -c "
from quantalithos_core import FlowMessageType
print('FlowMessageType values:', [e.value for e in FlowMessageType])
"
```

## 三、验收流程

### 3.1 每次阶段提交前

```
开发者（AI）完成一个阶段
    │
    ▼
自检：对照本文档 A/B/C 三个维度逐项检查
    │
    ▼
运行自动化检查（grep 命令 + 测试）
    │
    ▼
全部通过 → commit
    │
有问题 → 修复后重新自检
```

### 3.2 联调前

```
所有服务代码就绪
    │
    ▼
维度 C 跨服务一致性检查（逐项对比协议）
    │
    ▼
运行跨服务验证脚本
    │
    ▼
全部通过 → 进入联调
    │
有不一致 → 以 core 定义为准，修改偏离方
```

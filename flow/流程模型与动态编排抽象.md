# 流程模型与动态编排抽象

> 本文档记录当前关于“不同项目不应强行走同一套流程，应将流程模型抽象出来，由 Tech Lead 提议、runtime 编译并执行”的讨论结论。

---

## 一、问题背景

随着阶段 1 的讨论逐步深入，可以发现一个关键事实：

**不同项目、不同需求条目，不应该强行走完全相同的一套流程。**

例如：

- 一个小型 enhancement（如“博客列表页增加排序功能”）不一定需要完整的头脑风暴、双门禁和多轮正式评审
- 一个明确 bugfix（如“登录接口 500 错误”）更适合走轻量化修复流程，而不是完整需求理解流程
- 一个探索性新项目（如“做一个 AI 助手，但方向还没定”）反而需要更多轮次的需求探索和范围收敛

如果把当前讨论出来的阶段 1 流程硬编码成唯一流程，最终会出现两类问题：

- 简单项目被过度流程化
- 复杂项目表达能力不足，只能不断打补丁

因此，后续实现时不应固化“唯一流程”，而应抽象“流程模型”。

---

## 二、核心结论

建议采用下面这条总体策略：

> **固定的不是某一条具体流程，而是流程元模型、制度边界、门禁机制、节点原语、artifact 原语；具体项目流程则由 Tech Lead 提议、runtime 校验并编译为项目级 workflow instance。**

更准确地说：

- Tech Lead 负责根据项目情况提出流程方案
- runtime 负责根据框架规则进行校验、裁剪、补全、落地
- agent 负责执行最终实例化后的流程节点

这意味着：

- 不是 TL 完全自由制定流程
- 也不是系统硬编码唯一流程
- 而是 **“TL 提议流程，runtime 编译流程，agent 执行流程”**

---

## 三、建议的四层抽象

### 1. 流程原语层

这一层定义“流程可以由什么积木拼出来”。

#### 节点原语

- `action`
- `discussion_subflow`
- `gate`
- `event_wait`
- `fork`
- `join`
- `decision`
- `subflow`

#### 边原语

- `sequence`
- `conditional`
- `loop`
- `event`
- `fork_branch`
- `join_branch`
- `subflow_return`

#### 状态原语

- `pending`
- `in_progress`
- `blocked`
- `completed`
- `cancelled`
- `skip_with_reason`

#### 对象原语

- `artifact`
- `task_card`
- `review_comment`
- `approval_record`
- `handoff_package`

这一层回答的是：

> **流程能由哪些基础组件构成。**

---

### 2. 规范与约束层

这一层定义“哪些积木可以怎么用，哪些不能乱用”。

例如：

- 阶段 1 结束前必须有用户最终批准
- 阶段 2 之前不能进入实现
- `gate` 不能被 agent 跳过
- `discussion_subflow` 必须有结构化产物
- `blocked` 必须带 `reason_code`

这一层不是具体流程，而是制度层。

这一层回答的是：

> **流程怎么变都可以，但不能违反哪些总规则。**

---

### 3. 流程模板层

这一层定义“有哪些常见流程模板可复用”。

例如：

- `requirement_analysis_full`
- `requirement_analysis_light`
- `bugfix_fast_path`
- `enhancement_medium`
- `exploration_discovery_flow`

这些模板都建立在前两层之上。

这一层回答的是：

> **有哪些常见路线可以直接拿来装配。**

---

### 4. 项目实例化层

这一层定义“某个项目当前真正运行的是哪条流程”。

例如：

- 项目 A 使用 `requirement_analysis_light`
- 项目 B 使用 `requirement_analysis_full`
- 项目 C 使用 `exploration_discovery_flow + role expansion`

这一层回答的是：

> **这个项目此刻到底走哪条具体流程。**

---

## 四、Tech Lead 在这个模型中的角色

### 不建议的做法

不建议让 Tech Lead 完全自由制定流程。这样会带来：

- 流程风格不一致
- 审计困难
- 容易跳过门禁
- 每个 TL 都变成流程设计器
- runtime 很难验证流程合法性

### 更合理的做法

建议把 Tech Lead 设计成：

> **流程装配提议者，而不是最终裁判。**

也就是说：

#### Tech Lead 负责

- 识别项目类型
- 判断复杂度
- 判断当前需求更像哪一类流程
- 提议：
  - 使用哪个模板
  - 裁掉哪些步骤
  - 增加哪些角色
  - 启用哪些议题
  - 是否采用轻量模式 / 完整模式

#### runtime 负责

- 校验 TL 的流程提议是否合法
- 补齐必需门禁
- 阻止违规裁剪
- 生成最终可执行的 workflow instance

因此正确模型不是：

```text
TL 直接制定流程
```

而是：

```text
TL 提议流程
   ->
runtime 校验与编译
   ->
生成项目实例流程
```

## 五、建议的核心组件：WorkflowFactory / FlowAssembler

如果要实现“不同项目走不同流程”，建议引入一个核心组件：

- `WorkflowFactory`
- 或 `FlowAssembler`

它的职责是：

> **根据项目特征、阶段、需求类型、团队能力和组织规则，生成当前项目的实际流程实例。**

### 输入建议

至少包括：

#### 1. 项目元信息

- `project_type`
- `scope`
- `feature_count`
- `has_frontend`
- `has_mobile`
- `priority`
- `constraints`

#### 2. 当前条目类型

- `new_project`
- `enhancement`
- `bugfix`
- `optimization`
- `ops`

#### 3. 团队能力画像

- 当前有哪些角色
- 哪些角色缺失
- 是否允许扩队

#### 4. 组织规则

- 是否强制保留双门禁
- 是否允许简化评审
- 是否允许跳过某类议题

#### 5. TL 的流程提议

例如：

- 推荐使用 `light_requirement_flow`
- 建议跳过正式头脑风暴
- 建议将“摘要形成”和“初始收集”合并
- 建议不拉 DevOps 进入阶段 1

### 输出建议

输出的不是简单标签，而是一份：

- `workflow_instance`

例如：

```yaml
workflow_instance:
  template: requirement_analysis_light
  stage: REQUIREMENT_ANALYSIS
  enabled_steps:
    - tl_takeover
    - collect_and_summarize
    - scope_refinement
    - user_direction_confirmation
    - prd_finalization
    - final_approval
  disabled_steps:
    - full_team_brainstorm
    - formal_review_round
  required_roles:
    - tech-lead
    - frontend-dev
    - backend-dev
  optional_roles:
    - tester
    - devops
  enforced_gates:
    - user_direction_confirmation
    - user_final_approval
```

## 六、建议抽象的五类“可变流程能力”

### 1. 步骤裁剪

例如：

- 小项目跳过完整团队头脑风暴
- bugfix 跳过方案整理
- 明确需求跳过多轮澄清

### 2. 步骤合并

例如：

- `初始需求收集 + 需求摘要形成`
- `正式需求评审 + PRD 定稿`

### 3. 角色裁剪

例如：

- 小项目阶段 1 不拉 DevOps
- 无界面项目不拉前端 / UI
- 复杂需求增加 UI 或安全审阅角色

### 4. 轮次裁剪

例如：

- 只保留一轮评论
- 保留两轮评论
- 关闭交叉回应
- 最大补充轮次从 3 改为 1

### 5. 门禁强度调整

例如：

- 某些场景保留两个用户门禁
- 某些轻量增强只保留最终批准
- 某些内部项目允许方向确认自动通过，但不能跳过最终批准

---

## 七、建议的实现抽象对象

建议不要把“流程变化”写成大量 if-else，而是抽象成以下对象：

### 1. `ProcessModel`

定义流程骨架的通用模型。

### 2. `Template`

定义某类场景的默认流程。

### 3. `TailoringPolicy`

定义允许怎样裁剪、合并、降级。

### 4. `WorkflowProposal`

Tech Lead 针对当前项目提出的流程建议。

### 5. `CompiledWorkflow`

runtime 最终编译出的可执行流程。

可以理解成：

```text
ProcessModel
   + Template
   + TailoringPolicy
   + WorkflowProposal(from TL)
   --------------------------------
   = CompiledWorkflow(for runtime)
```

## 八、两个实际例子

### 例子 A：简单 enhancement

用户提出：

- “给博客列表页加一个按时间排序”

#### TL 提议

- 使用 `requirement_analysis_light`
- 合并：
  - 收集 + 摘要
  - 评审 + 定稿
- 跳过完整团队头脑风暴
- 保留：
  - 用户方向确认
  - 用户最终批准

#### runtime 编译结果

得到轻量流程：

```text
TL 接管
 -> 轻量需求澄清与摘要
 -> 范围确认
 -> PRD 轻量定稿
 -> 用户最终批准
 -> 进入阶段2
```

### 例子 B：复杂新项目

用户提出：

- “做一个类似 Medium 的博客系统，有评论、标签、暗色模式、后台管理”

#### TL 提议

- 使用 `requirement_analysis_full`
- 保留完整多议题流程
- 拉入前端、后端、测试、DevOps
- 开启双门禁
- 允许两轮补充讨论

#### runtime 编译结果

得到完整流程，也就是当前阶段 1 文档中讨论出的完整需求理解流程。

## 九、实现时最重要的边界

如果要实现这个功能，必须守住一个边界：

> **TL 可以提议流程，但不能绕过框架的硬规则。**

例如 TL 不能提议：

- 跳过最终批准
- 阶段 1 直接进入实现
- 不生成任何结构化 artifact
- 让某个角色越权审批

因此应明确：

- **可变的是流程实例**
- **不可变的是制度底座**

## 十一、当前建议结论

如果后续进入实现，我建议采用下面这套方向：

- 固定层：
  - 流程原语
  - 状态原语
  - artifact 原语
  - gate 原语
  - 权限与校验规则
- 模板层：
  - 完整流程
  - 轻量流程
  - bugfix 流程
  - 探索型流程
- 裁剪层：
  - 步骤裁剪
  - 步骤合并
  - 角色裁剪
  - 轮次裁剪
  - 门禁强度调整
- 编译层：
  - TL 提议
  - runtime 校验
  - 生成 workflow instance

一句话收束：

> **把流程模型抽象出来，让 TL 基于模型提议，让 runtime 基于规则编译出当前项目的实际流程。**

## 十三、官方团队方案与 plugin 化集成设计

除了“让 Tech Lead 根据项目情况提议流程，再由 runtime 编译”这一条路径之外，还应考虑另一种更产品化的接入方式：

> **官方维护一套标准角色目录与标准流程目录，二者独立演进，再通过 plugin 作为组合与分发单元，对外提供可安装的开发团队方案。**

这种模式的价值在于：

- 用户不一定每次都需要 Tech Lead 重新拉团队、重新设计流程
- 平台可以维护一套官方推荐方案，降低接入门槛
- Tech Lead 仍可在规则允许范围内做项目级裁剪
- runtime 仍然掌握最终校验与编译权，不会失控

### 一、为什么这种设计更优雅

如果把“团队成员列表”和“流程定义”直接写死在一起，会过于僵硬；但如果把它们完全交给 TL 临场装配，又会过于依赖个人判断。

更优雅的做法是把它们拆成独立可维护的模块：

- 角色目录独立维护
- 流程目录独立维护
- 绑定规则独立维护
- plugin 负责组合、打包、发布与安装

这样既有产品化能力，也保留了足够的弹性。

### 二、建议拆成四类核心资源

#### 1. `RoleCatalog`

定义平台上有哪些标准角色可选。

例如：
- `tech-lead`
- `frontend-dev`
- `backend-dev`
- `tester`
- `devops`
- `ui-designer`

每个角色建议至少包含：
- `identity`
- `permissions`
- `default_task_types`
- `applicable_stages`
- `tool_scope`
- `prompt_templates` / `shared_rules`

这一层回答的是：

> **平台有哪些标准角色资源。**

#### 2. `WorkflowCatalog`

定义平台上有哪些标准流程模板可选。

例如：
- `requirement_analysis_full`
- `requirement_analysis_light`
- `design_and_planning_standard`
- `iterative_development_parallel`
- `bugfix_fast_path`

每个流程模板建议至少包含：
- 步骤定义
- 子流程定义
- gate 规则
- artifact schema
- `done_when`
- 角色依赖
- 可裁剪位

这一层回答的是：

> **平台有哪些标准流程资源。**

#### 3. `BindingRules`

定义角色和流程怎么匹配。

例如：
- 某个流程最少需要哪些角色
- 哪些角色是 optional
- 缺少某角色时能否降级
- 某种项目类型默认绑定哪条流程

例如可以表达成：
- `requirement_analysis_full` 需要 `tech-lead`、`frontend-dev`、`backend-dev`、`tester`
- `devops` 在涉及部署约束时从 optional 提升为 required

这一层回答的是：

> **团队和流程如何被安全组合。**

#### 4. `Plugin`

plugin 不应是“流程本体”或“团队本体”，而应是：

> **组合与分发单元。**

一个 plugin 可以打包：
- 一组角色定义
- 一组流程模板
- 一组绑定规则
- 一组裁剪策略
- 一组默认配置
- 安装与版本元数据

所以更准确地说：

```text
Plugin
  = RoleCatalog
  + WorkflowCatalog
  + BindingRules
  + TailoringPolicy
  + DefaultConfig
```

### 三、为什么不要把成员列表和流程强绑定写死

不建议直接做成：

```text
插件 A = 一组固定成员 + 一条固定流程
```

因为这样会导致：
- 同一团队无法支持多种流程
- 同一流程无法适配不同团队变体
- 后续 light / full / bugfix 模式难以共存

更好的方式是：

```text
插件 A = 一组成员能力 + 一组流程模板 + 一组绑定规则
```

这样就能做到：
- 同一个官方团队支持多种流程
- 同一条流程支持多种团队配置
- 同一官方方案可以覆盖 light / full / bugfix 等多个模式

### 四、推荐的两种使用方式

#### 方式 1：用户直接安装官方 plugin

适用于：
- 普通用户
- 快速开项目
- 不想理解底层流程模型的场景

典型体验：

```text
选择插件：官方标准开发团队
 -> 一键安装
 -> 自动创建角色
 -> 自动绑定默认流程
 -> 自动进入阶段 0 / 阶段 1
```

#### 方式 2：Tech Lead 基于 plugin 裁剪后启用

适用于：
- 复杂项目
- 特殊需求
- 需要在官方方案上切换 light / full 模式的场景

典型体验：

```text
选择插件：官方标准开发团队
 -> TL 提议：关闭 DevOps，启用 light requirement flow
 -> runtime 校验
 -> 生成项目实例流程
```

这意味着 plugin 提供的是“标准能力包”，而不是“不可调整的死配置”。

### 五、plugin 化之后的权责边界

即使采用 plugin 化集成，也应坚持前面已经建立的运行边界：

- 官方团队方案负责提供标准资源
- 用户可以直接启用方案
- Tech Lead 可以在允许范围内提议裁剪
- runtime 负责最终校验、补齐与编译
- agent 只执行最终实例化后的流程

所以 plugin 化不意味着 runtime 失去控制权；相反，它只是把“资源准备与方案分发”做成了产品级能力。

### 六、建议的 plugin 结构示意

可以用下面这种结构来表达一个官方方案包：

```yaml
plugin:
  id: official-standard-dev-team
  version: 1.0.0
  roles:
    - tech-lead
    - frontend-dev
    - backend-dev
    - tester
    - devops
  workflows:
    - requirement_analysis_full
    - requirement_analysis_light
    - design_and_planning_standard
    - iterative_development_parallel
    - bugfix_fast_path
  bindings:
    - project_type: new_project
      default_requirement_flow: requirement_analysis_full
    - project_type: enhancement
      default_requirement_flow: requirement_analysis_light
    - project_type: bugfix
      default_requirement_flow: bugfix_fast_path
  tailoring_policy:
    allow_disable_roles:
      - devops
      - tester
    allow_merge_steps:
      - collect_and_summarize
      - review_and_finalize
    required_gates:
      - final_approval
```

```text
| 用户直接安装方案   |       | TL 基于方案提议裁剪 |
+---------+---------+       +---------+---------+
          |                           |
          +-------------+-------------+
                        |
                        v
              +-------------------+
              | Runtime Compiler  |
              | (校验/补齐/编译)   |
              +---------+---------+
                        |
                        v
              +-------------------+
              | Workflow Instance |
              |  (实际运行流程)    |
              +---------+---------+
                        |
                        v
              +-------------------+
              | Agent Execution   |
              |   (节点执行层)     |
              +-------------------+
```

### 八、当前建议结论

基于当前讨论，我建议把这套设计收敛成下面这条原则：

> **官方维护角色目录与流程目录，二者独立演进；plugin 作为组合与分发单元，将角色、流程、绑定规则和裁剪策略打包成可安装方案；用户可直接启用，Tech Lead 可在规则允许范围内进行项目级裁剪。**

换句话说：
- 最优雅的模式不是“TL 每次重新拉团队和写流程”
- 也不是“官方写死一套不可变团队和流程”
- 而是“官方维护标准资源，plugin 负责组合分发，runtime 负责校验编译，TL / 用户负责按需启用”

## 十四、`TailoringPolicy` 的字段草案

既然系统允许“同一套流程模型在不同项目里被裁剪、合并、降级或增强”，那么就需要一个明确的数据对象来表达这种可变性约束。

这个对象就是：

- `TailoringPolicy`

它不是某个具体项目的流程提议，而是：

> **定义某套模板在实例化时，哪些地方允许调整、哪些地方禁止调整、哪些调整需要满足前置条件。**

### 一、`TailoringPolicy` 的职责

建议它至少回答以下问题：

- 哪些步骤可以删除
- 哪些步骤只能合并不能删除
- 哪些 gate 必须保留
- 哪些角色可以降级为 optional
- 哪些角色绝不能移除
- 哪些议题可以关闭
- 评论轮次最多可裁到什么程度
- 什么条件下允许使用 `light mode`

也就是说，`TailoringPolicy` 更像：

- 模板的裁剪规则说明书
- runtime 的编译边界
- TL 提议流程时的合法性依据

### 二、建议字段总览

建议 `TailoringPolicy` 至少包含以下几类字段：

| 字段组 | 作用 |
|--------|------|
| `policy_id` / `applies_to` | 标识这条裁剪策略属于谁 |
| `mode_support` | 支持哪些模式，如 full / light |
| `step_rules` | 哪些步骤可删除、可合并、必须保留 |
| `topic_rules` | 哪些议题可启用、可关闭、必须启用 |
| `role_rules` | 哪些角色 required / optional / removable |
| `gate_rules` | 哪些 gate 必须保留、哪些可弱化 |
| `round_rules` | 评论轮次、补充轮次的裁剪范围 |
| `artifact_rules` | 哪些 artifact 必须保留、哪些可降级 |
| `activation_conditions` | 什么条件下允许应用这条策略 |
| `compiler_constraints` | runtime 编译时必须额外校验的约束 |

### 三、建议结构草案

```yaml
tailoring_policy:
  policy_id: stage1_requirement_analysis_policy
  applies_to:
    stage: REQUIREMENT_ANALYSIS
    templates:
      - stage1_full_requirement_analysis
      - stage1_light_requirement_analysis

  mode_support:
    allowed_modes:
      - full
      - light
    default_mode_by_scope:
      small: light
      medium: full
      large: full

  step_rules:
    must_keep:
      - tl_takeover
      - scope_refinement
      - final_approval
    mergeable_groups:
      - id: collect_and_summarize
        steps:
          - initial_requirement_collection
          - requirement_summary_formation
      - id: review_and_finalize
        steps:
          - formal_requirement_review
          - prd_finalization
    removable_steps:
      - full_team_brainstorm
    non_removable_steps:
      - user_final_approval

  topic_rules:
    required_topics:
      - topic_1_goal_and_boundary
    optional_topics:
      - topic_2_main_flow
      - topic_3_loops_and_fallbacks
      - topic_4_roles_and_collaboration
      - topic_5_artifact_design
      - topic_6_gate_and_approval
      - topic_7_exceptions_and_sideflows
    forbidden_to_disable_when_large:
      - topic_2_main_flow
      - topic_5_artifact_design

  role_rules:
    required_roles:
      - tech-lead
      - backend-dev
    optional_roles:
      - frontend-dev
      - tester
      - devops
      - ui-designer
    removable_roles:
      - devops
      - tester
    conditional_required_roles:
      - role: frontend-dev
        when:
          - project.has_frontend == true
      - role: devops
        when:
          - project.has_deploy_requirement == true

  gate_rules:
    mandatory_gates:
      - final_approval
    recommended_gates:
      - direction_confirmation
    weakenable_gates:
      - direction_confirmation
    non_removable_gates:
      - final_approval

  round_rules:
    min_comment_rounds:
      small: 1
      medium: 1
      large: 2
    max_additional_rounds:
      small: 1
      medium: 2
      large: 3
    allow_cross_response:
      small: conditional
      medium: true
      large: true

  artifact_rules:
    mandatory_artifacts:
      - requirement_summary
      - prd_final
      - approval_record
      - stage1_handoff_package
    optional_artifacts:
      - discussion_notes
      - risk_notes
      - review_summary
    required_when_large:
      - topic_1_result
      - topic_2_result
      - topic_5_result

  activation_conditions:
    allow_light_mode_when:
      - project.scope == small
      - project.uncertainty <= medium
    deny_light_mode_when:
      - project.is_new_project == true
      - project.scope == large

  compiler_constraints:
    - no_workflow_without_final_approval
    - no_stage1_without_requirement_summary
    - no_disable_all_topics
```

### 四、字段设计说明

#### 1. `mode_support`

这一组字段解决：
- 当前模板支持哪些运行模式
- 默认情况下按项目规模应该落到哪个模式

#### 2. `step_rules`

这一组字段解决：
- 哪些步骤是底线步骤
- 哪些步骤可以合并
- 哪些步骤在某些场景下可以移除

建议重点区分：
- `must_keep`
- `mergeable_groups`
- `removable_steps`
- `non_removable_steps`

#### 3. `topic_rules`

这一组字段解决：
- 哪些议题必须开
- 哪些议题只是制度上建议
- 哪些议题在大项目下不能关闭

这部分对阶段 1 很关键，因为阶段 1 的复杂度大量来自议题数量。

#### 4. `role_rules`

这一组字段解决：
- 某个角色默认是 required 还是 optional
- 在什么条件下可移除
- 在什么条件下必须补进来

建议支持条件表达式，而不是只写死必选/可选。

#### 5. `gate_rules`

这一组字段解决：
- 哪些 gate 是制度底线
- 哪些 gate 只是建议保留
- 哪些 gate 可以弱化但不能彻底删除

#### 6. `round_rules`

这一组字段解决：
- 评论轮次的下限和上限
- 是否允许交叉回应
- 补充轮次最多开几轮

#### 7. `artifact_rules`

这一组字段解决：
- 哪些 artifact 是流程存在的最小证明
- 哪些 artifact 可在轻量模式里弱化
- 哪些 artifact 仅在大项目时强制保留

### 五、实现建议

从实现角度，`TailoringPolicy` 最好有两个特点：

#### 1. 可声明式校验

也就是 runtime 可以直接读取 policy，而不是写大量 if-else。

#### 2. 可叠加

例如：
- 平台默认 policy
- 官方 plugin policy
- 公司自定义 policy

最后通过优先级合并成一份最终 policy。

可以理解为：

```text
final_tailoring_policy
  = platform_policy
  + plugin_policy
  + org_policy
```

## 十五、`WorkflowProposal` 的结构草案

`WorkflowProposal` 不是最终执行对象，而是：

> **某个项目在某个阶段，由 TL 或系统给出的流程装配提议。**

它更像“候选方案”，供 runtime 校验与编译。

### 一、`WorkflowProposal` 的职责

它至少要回答：

- 这个项目建议采用哪套模板
- 当前阶段想用 full 还是 light 模式
- 哪些步骤要合并
- 哪些议题要启用/关闭
- 哪些角色是 required / optional
- 想保留哪些 gate
- 轮次如何设置
- 这样提议的理由是什么

### 二、建议字段总览

| 字段组 | 作用 |
|--------|------|
| `proposal_id` / `project_id` / `stage` | 标识这份提议属于哪个项目哪个阶段 |
| `base_template` | 提议基于哪套模板 |
| `mode` | full / light / custom |
| `step_adjustments` | 步骤合并、删除、重排建议 |
| `topic_adjustments` | 议题启用/关闭建议 |
| `role_plan` | 角色 required / optional / disabled 计划 |
| `gate_plan` | gate 保留 / 弱化 / 强化建议 |
| `round_plan` | 评论轮次、补充轮次建议 |
| `artifact_plan` | artifact 保留与降级建议 |
| `justification` | 为什么要这样提议 |
| `proposed_by` | 谁提出的提议 |

### 三、建议结构草案

```yaml
workflow_proposal:
  proposal_id: proposal_stage1_proj_001
  project_id: proj_001
  stage: REQUIREMENT_ANALYSIS
  proposed_by:
    actor: tech-lead
    source: project_runtime

  base_template: stage1_full_requirement_analysis
  mode: light

  step_adjustments:
    merge:
      - collect_and_summarize
      - review_and_finalize
    disable:
      - full_team_brainstorm
    keep:
      - tl_takeover
      - scope_refinement
      - final_approval

  topic_adjustments:
    enable:
      - topic_1_goal_and_boundary
      - topic_5_artifact_design
    disable:
      - topic_3_loops_and_fallbacks
      - topic_4_roles_and_collaboration
      - topic_7_exceptions_and_sideflows

  role_plan:
    required:
      - tech-lead
      - frontend-dev
      - backend-dev
    optional:
      - tester
      - devops
    disabled:
      - ui-designer

  gate_plan:
    keep:
      - final_approval
    weaken:
      - direction_confirmation
    remove: []

  round_plan:
    comment_rounds: 1
    max_additional_rounds: 1
    cross_response: conditional

  artifact_plan:
    keep:
      - requirement_summary
      - prd_final
      - approval_record
      - stage1_handoff_package
    optional:
      - discussion_notes
      - risk_notes
      - review_summary

  justification:
    - project.scope == small
    - requirement_is_clear == true
    - no_special_devops_constraints == true
```

### 四、字段设计说明

#### 1. `base_template` + `mode`

这两个字段决定提议的基底。

例如：
- 用完整模板做轻量裁剪
- 用专门的 light 模板直接生成

#### 2. `step_adjustments`

这一组字段表达：
- 哪些步骤要合并
- 哪些步骤建议关闭
- 哪些底线步骤必须保留

#### 3. `topic_adjustments`

这一组字段表达：
- 当前项目到底打算开哪些议题
- 哪些制度性议题在本项目中先不启用

#### 4. `role_plan`

这一组字段表达：
- 当前项目的角色参与方案
- 谁必须参与、谁按需参与、谁关闭

#### 5. `justification`

这组字段非常重要，因为 proposal 不只是结构变化，还应说明“为什么这么配”。

runtime 可以用它做：
- 日志记录
- 审计
- 后续建议生成

## 十六、`CompiledWorkflow` 的结构草案

`CompiledWorkflow` 是 runtime 校验 `WorkflowProposal` 并应用 `TailoringPolicy` 后得到的：

> **最终实际运行的流程实例。**

它不再是建议，而是执行对象。

### 一、`CompiledWorkflow` 的职责

它至少要回答：

- 当前项目到底跑哪套流程
- 当前启用了哪些步骤
- 哪些步骤被合并了
- 哪些议题真的会执行
- 哪些角色是最终 required / optional
- gate 最终如何配置
- 每个节点的依赖、输入、输出是什么

### 二、建议字段总览

| 字段组 | 作用 |
|--------|------|
| `workflow_id` / `project_id` / `stage` | 标识最终工作流实例 |
| `compiled_from` | 记录从哪个模板、哪份 proposal 编译而来 |
| `resolved_mode` | 最终模式 |
| `resolved_roles` | 最终角色配置 |
| `resolved_steps` | 最终步骤清单 |
| `resolved_topics` | 最终启用的议题子流程 |
| `resolved_gates` | 最终 gate 配置 |
| `resolved_artifacts` | 最终 artifact 需求 |
| `execution_graph` | runtime 真正执行的图 |
| `compiler_notes` | 编译时补齐、拒绝、修正的信息 |

### 三、建议结构草案

```yaml
compiled_workflow:
  workflow_id: wf_stage1_proj_001
  project_id: proj_001
  stage: REQUIREMENT_ANALYSIS

  compiled_from:
    template: stage1_full_requirement_analysis
    proposal_id: proposal_stage1_proj_001
    policy_id: stage1_requirement_analysis_policy

  resolved_mode: light

  resolved_roles:
    required:
      - tech-lead
      - frontend-dev
      - backend-dev
    optional:
      - tester
      - devops
    disabled:
      - ui-designer

  resolved_steps:
    - id: tl_takeover
      type: action
      enabled: true
    - id: collect_and_summarize
      type: merged_action
      merged_from:
        - initial_requirement_collection
        - requirement_summary_formation
      enabled: true
    - id: scope_refinement
      type: action_with_subflow
      enabled: true
    - id: review_and_finalize
      type: merged_action
      merged_from:
        - formal_requirement_review
        - prd_finalization
      enabled: true
    - id: final_approval
      type: gate
      enabled: true

  resolved_topics:
    enabled:
      - topic_1_goal_and_boundary
      - topic_5_artifact_design
    disabled:
      - topic_3_loops_and_fallbacks
      - topic_4_roles_and_collaboration
      - topic_7_exceptions_and_sideflows

  resolved_gates:
    direction_confirmation:
      type: soft
      enabled: true
    final_approval:
      type: hard
      enabled: true

  resolved_artifacts:
    mandatory:
      - requirement_summary
      - prd_final
      - approval_record
      - stage1_handoff_package
    optional:
      - discussion_notes
      - risk_notes
      - review_summary

  execution_graph:
    start: tl_takeover
    nodes:
      - tl_takeover
      - collect_and_summarize
      - scope_refinement
      - review_and_finalize
      - final_approval
    edges:
      - from: tl_takeover
        to: collect_and_summarize
      - from: collect_and_summarize
        to: scope_refinement
      - from: scope_refinement
        to: review_and_finalize
      - from: review_and_finalize
        to: final_approval

  compiler_notes:
    added_by_runtime:
      - final_approval
    rejected_changes:
      - remove_final_approval
    normalized_changes:
      - direction_confirmation changed from remove to soft
```

### 四、字段设计说明

#### 1. `compiled_from`

这一组字段用于追踪来源：
- 依据哪个模板
- 依据哪份 proposal
- 依据哪条 policy

这对审计和回放很重要。

#### 2. `resolved_*`

建议编译结果尽量用 `resolved_` 前缀，因为它强调：
- 这已经不是提议
- 而是 runtime 最终裁定后的结果

#### 3. `execution_graph`

这部分是最接近 runtime 执行引擎的数据：
- 真正执行哪些节点
- 节点如何连接
- 哪些步骤已经被合并

#### 4. `compiler_notes`

这部分非常重要，因为现实中 proposal 和 final workflow 不会完全一致。

例如：
- TL 想删掉某个 gate，但 runtime 补回来了
- TL 想禁用某个角色，但 policy 不允许

这些变化必须可追踪。

### 五、三者之间的关系

可以把三者关系简化成：

```text
Template
  + TailoringPolicy
  + WorkflowProposal
  -----------------
  = CompiledWorkflow
```

其中：
- `Template` 提供默认结构
- `TailoringPolicy` 提供合法边界
- `WorkflowProposal` 提供项目级意图
- `CompiledWorkflow` 是 runtime 可执行结果

### 六、当前建议结论

如果后续进入实现，我建议优先把这三个对象固定下来：

- `TailoringPolicy`：定义“允许怎么变”
- `WorkflowProposal`：定义“当前项目想怎么变”
- `CompiledWorkflow`：定义“最终实际怎么跑”

一旦这三者稳定下来，你们的“动态流程生成”就会从讨论概念，真正进入可落地的数据模型层。

## 十七、三者之间的编译状态 / 转换图

在数据模型定义清楚之后，下一步就需要明确：

- `Template`
- `TailoringPolicy`
- `WorkflowProposal`
- `CompiledWorkflow`

之间到底是如何流转的。

这里建议把它理解成一个**受控编译状态机**，而不是一个简单的“对象拼接过程”。

因为在真实实现里，runtime 不只是把三个对象拼起来，而是要经过：

- 提议接收
- 合法性检查
- 约束归一化
- 补齐默认值
- 冲突修正
- 图编译
- 最终冻结

### 一、核心状态图

```text
[Template Loaded]
       |
       v
[Policy Resolved]
       |
       v
[Proposal Received]
       |
       v
[Proposal Validating]
   | valid                 | invalid
   v                       v
[Proposal Accepted]    [Proposal Rejected]
       |
       v
[Constraint Normalizing]
       |
       v
[Workflow Compiling]
       |
       v
[CompiledWorkflow Draft]
   | pass final checks      | fail final checks
   v                        v
[CompiledWorkflow Frozen] [Back To Normalize / Reject]
       |
       v
[Runtime Executable]
```

这张图表达的是：
- `Template` 先提供默认流程结构
- `TailoringPolicy` 先被解析成当前编译上下文中的合法边界
- `WorkflowProposal` 再进入校验流程
- proposal 合法后不能直接执行，还要经过归一化和编译
- 最终只有被冻结的 `CompiledWorkflow` 才能进入 runtime 执行层

### 二、各状态的含义

#### 1. `Template Loaded`

含义：
- runtime 已选定基础模板
- 模板中的默认步骤、默认角色、默认 gate、默认 artifact 已可读

典型输入：
- `base_template`
- `stage`
- `project_type`

#### 2. `Policy Resolved`

含义：
- 当前应生效的 `TailoringPolicy` 已合并完成
- 平台级 policy、plugin policy、组织级 policy 已得到最终裁剪边界

可以抽象成：

```text
resolved_policy
  = platform_policy
  + plugin_policy
  + org_policy
```

这一状态结束后，runtime 已经知道：
- 什么能改
- 什么不能改
- 哪些条件下能改

#### 3. `Proposal Received`

含义：
- 收到一份 `WorkflowProposal`
- proposal 可能来自：
  - `Tech Lead`
  - 系统默认策略
  - 插件自动推荐

此时只是“收到提议”，并不代表提议合法。

#### 4. `Proposal Validating`

含义：
- runtime 正在检查 proposal 是否违反当前 policy
- 检查 proposal 字段是否完整、结构是否可解析

这里主要做三类校验：

- **结构校验**
  - proposal schema 是否完整
- **规则校验**
  - 是否试图移除非可裁剪步骤
  - 是否试图移除 mandatory gate
- **条件校验**
  - light mode 是否满足启用条件
  - 某角色是否真的可以降为 optional

#### 5. `Proposal Accepted`

含义：
- proposal 通过初步合法性检查
- 可以进入“编译前归一化”阶段

注意：
- accepted 不等于最终会原样执行
- 只是说明 proposal 没有被直接拒绝

#### 6. `Proposal Rejected`

含义：
- proposal 明显违反 policy 或缺少关键字段
- 无法进入编译阶段

例如：
- 请求删除 `final_approval`
- 请求禁用所有议题
- 请求在 `large` 项目中强行启用极度简化 light mode

这时 runtime 应返回：
- 拒绝原因
- 命中的 policy 规则
- 可接受替代建议

#### 7. `Constraint Normalizing`

含义：
- proposal 合法，但还不是最终执行结构
- runtime 正在补齐默认值、修正规则表达、把模糊提议转成确定配置

例如：
- TL 只写“轻量模式”，runtime 自动补齐默认评论轮次
- TL 想去掉方向确认，runtime 把它降级成 soft gate 而非彻底删除
- proposal 未显式写 artifact plan，runtime 用模板默认值补齐

这个状态很关键，它体现的是：

> **runtime 不只是检查 proposal，而是在 policy 允许范围内把 proposal 正规化。**

#### 8. `Workflow Compiling`

含义：
- runtime 正在把“模板 + policy + proposal”真正编译成执行图

这里主要发生的事情包括：
- 解析最终保留的步骤
- 合并步骤组
- 生成最终角色配置
- 生成最终 topic 启用列表
- 生成 gate 配置
- 生成 artifact 需求清单
- 构造 `execution_graph`

#### 9. `CompiledWorkflow Draft`

含义：
- 编译产物已经形成，但还没最终冻结
- runtime 正在做最后一轮一致性检查

主要检查：
- 是否还存在无 actor 的节点
- 是否存在没有出口 gate 的阶段
- 是否存在被禁用却仍被依赖的 topic / step
- execution graph 是否连通
- 是否存在必需 artifact 无法生成的情况

#### 10. `CompiledWorkflow Frozen`

含义：
- 编译结果已经通过一致性检查
- 可以作为项目当前阶段的正式执行对象

冻结后的特点：
- 进入 runtime 执行前不可随意隐式修改
- 如需调整，应重新发起 proposal 并重新编译

#### 11. `Runtime Executable`

含义：
- 最终 `CompiledWorkflow` 已被 runtime 接管
- 开始作为真实 workflow instance 执行

从这一步开始：
- TaskCardDispatcher 可以下发节点
- WorkflowEngine 可以推进状态
- EventBus 可以驱动流转

### 三、关键转换条件图

除了状态本身，还需要明确“状态怎么转”。

```text
Template Loaded
  -> when template exists and is parseable

Policy Resolved
  -> when all applicable policies are merged

Proposal Received
  -> when proposal is submitted or default proposal is generated

Proposal Validating
  -> when schema validation + policy validation starts

Proposal Accepted
  -> when no blocking rule violation exists

Proposal Rejected
  -> when mandatory gate/step/role constraints are violated

Constraint Normalizing
  -> when proposal accepted but needs default fill / downgrade / rewrite

Workflow Compiling
  -> when normalized config is complete enough to build execution graph

CompiledWorkflow Draft
  -> when execution graph + resolved config are generated

CompiledWorkflow Frozen
  -> when final consistency checks pass

Runtime Executable
  -> when compiled workflow is persisted and activated
```

### 四、失败与回退路径

这个编译流程不应该只有一条成功路径，还应明确失败和回退分支。

#### 1. proposal 被拒绝

```text
Proposal Validating
   -> Proposal Rejected
   -> 返回错误原因 / 命中规则 / 建议修正
   -> 等待新 proposal
```

#### 2. draft 编译失败

```text
Workflow Compiling
   -> CompiledWorkflow Draft
   -> final checks fail
   -> Back To Normalize
   -> 重新编译
```

#### 3. 归一化后仍无法成立

```text
Constraint Normalizing
   -> 发现 proposal 与 policy 虽不直接冲突，但组合后不可执行
   -> Proposal Rejected 或要求人工修正
```

### 五、一张更完整的状态 / 转换图

```text
+-------------------+
| Template Loaded   |
+---------+---------+
          |
          v
+-------------------+
| Policy Resolved   |
+---------+---------+
          |
          v
+-------------------+
| Proposal Received |
+---------+---------+
          |
          v
+----------------------+
| Proposal Validating  |
+----+------------+----+
     |            |
     | valid      | invalid
     v            v
+-------------------+     +-------------------+
| Proposal Accepted |     | Proposal Rejected |
+---------+---------+     +---------+---------+

          v                         v
```

### 六、这张图的实现价值

把三者之间的编译流程写成状态 / 转换图之后，后续实现会更清楚：

- 哪些对象是“输入对象”
- 哪些状态是“校验阶段”
- 哪些状态是“编译阶段”
- 哪些失败要拒绝，哪些失败可以自动修正
- runtime 何时真正拥有可执行的 workflow instance

也就是说，这张图把之前的数据模型补齐成了：

- 对象层：`Template` / `TailoringPolicy` / `WorkflowProposal` / `CompiledWorkflow`
- 编译层：验证、归一化、编译、冻结
- 执行层：runtime 真正加载并运行 workflow instance

### 七、当前建议结论

如果你们后续真的要把“动态流程生成”落地成系统，我建议把这张编译状态机视为必备设计，而不是补充说明。因为它直接决定：

- proposal 什么时候合法
- policy 什么时候生效
- runtime 什么时候可以开始执行
- 失败时到底回到哪里

换句话说：

> **只有把三者之间的状态 / 转换关系定义清楚，`TailoringPolicy`、`WorkflowProposal` 和 `CompiledWorkflow` 才不只是静态数据结构，而会变成一个真正可实现的编译流程。**

## 十八、从阶段 1 上收的平台通用机制清单

随着 `阶段1-需求理解.md` 的讨论不断展开，已经有一批内容明显超出了“需求理解阶段本身怎么跑”的范围，而更接近平台层的通用运行机制。

如果不主动把它们上收到平台抽象层，后面会出现两个问题：

- 平台能力被埋在阶段 1 细节里，不利于后续复用到阶段 0、阶段 2、bugfix、评审、发布等流程
- 阶段 1 文档会同时承载业务语义和 runtime 机制，边界越来越模糊

因此，这里建议明确一条分工原则：

> **平台抽象文档负责沉淀可跨阶段复用的机制；阶段文档负责描述这些机制在某个具体阶段中如何落地。**

### 一、建议上收的第一类：workflow 元模型与编译机制

这部分已经在本文前面展开，建议继续明确作为平台层核心能力保留：

- `Template`
- `TailoringPolicy`
- `WorkflowProposal`
- `CompiledWorkflow`
- 编译状态 / 转换图

原因：
- 它们不依赖“需求理解”这一业务语义
- 它们描述的是 runtime 如何编译任意 workflow instance

也就是说：
- 阶段 1 只是它们的第一个应用场景
- 不是它们的归属层级

### 二、建议上收的第二类：Gate / Approval Runtime

虽然阶段 1 中的双门禁把这类需求暴露得最明显，但门禁和批准机制本质上不是阶段 1 专有，而是平台通用控制能力。

建议作为平台层能力沉淀的内容包括：

- `GateDefinition`
- `GateInstance`
- `ApprovalRequest`
- `ApprovalResponse`
- `GateDecision`
- gate 生命周期状态机
- gate 前置条件检查
- gate reject 到 fallback 的对接规则

原因：
- 阶段 1 有 `用户方向确认`、`用户最终批准`
- 阶段 0、阶段 2、发布、验收、外部副作用动作也可能需要 gate

所以平台层要回答的是：

- gate 一般怎么定义
- approval 一般怎么建模
- runtime 一般怎么裁决

而阶段文档只回答：

- 阶段 1 具体在哪几个地方挂 gate
- 每个 gate 在阶段 1 中具体确认什么

### 三、建议上收的第三类：Fallback / Sideflow Runtime

阶段 1 已经把：
- 回环
- 回退
- 异常
- 侧线
- 重大变更

讨论得比较完整，但这些能力本质上属于 runtime 的通用控制机制。

建议上收的内容包括：

- `LoopDefinition`
- `FallbackSignal`
- `FallbackDecision`
- `FallbackPolicy`
- `exception_signal`
- `sideflow_decision`
- `exception_resolution_record`
- sideflow 回并主线的通用规则

原因：
- 任何复杂 workflow 都可能需要：
  - 合法回退
  - 短侧线处理
  - 结构性异常升级
  - 流程切换

因此平台层应沉淀：
- 如何统一表示异常
- 如何统一做回退裁决
- 如何统一让 sideflow 产出回并主线

### 四、建议上收的第四类：角色目录与协作元数据

阶段 1 里已经抽出了：
- 主持者
- 评论者
- 审批者
- 编排者

以及：
- `RoleCatalog`
- `WorkflowCatalog`
- `BindingRules`
- `Plugin`

这些都更像平台协作元数据，而不是阶段 1 专项结构。

建议平台层继续沉淀：

- 标准角色目录
- 角色权限边界
- 角色身份分类
- 团队与流程的绑定规则
- plugin 作为组合与分发单元的抽象

原因：
- 阶段 1 只是“角色协作”最先被详细展开的地方
- 但角色目录、权限边界、plugin 分发显然要服务整个系统

### 五、建议上收的第五类：artifact 系统通用能力

阶段 1 已经把 artifact 体系拉得比较深，甚至出现了很多明显的系统级能力诉求。

建议上收的平台层内容包括：

- artifact 生命周期状态
- `source_topics`
- `derived_from`
- `superseded / invalidated / archived`
- merge / conflict / reuse / invalidation 规则
- artifact 版本切换与审计规则

原因：
- 这些机制并不只属于需求文档
- 它们更像平台的结构化交付物系统能力

平台层应回答：
- artifact 一般怎么版本化
- artifact 一般怎么失效
- artifact 一般怎么标记来源

阶段 1 文档则回答：
- `requirement_summary`、`proposal`、`prd_final` 等具体对象在阶段 1 中代表什么

### 六、建议上收的第六类：确认式执行与动作级 gate 边界

最近讨论里又补出来一层新的平台问题：

- 流程级 gate vs 动作级 gate
- 高副作用动作是否需要人工确认
- runtime 如何控制 apply / reject / execute

这部分不应继续被阶段 1 文档单独吞掉，而更适合沉淀为平台层的能力边界。

建议平台层至少保留这个问题的当前结论：

- 当前架构已经具备流程级 gate
- 后续应考虑是否支持动作级 gate
- 如果扩展，优先覆盖高副作用动作
- 这属于平台通用机制，不只服务阶段 1

### 七、建议继续留在阶段文档中的内容

为了避免抽象过度，也要明确哪些内容仍应留在阶段文档中。

建议继续保留在 `阶段1-需求理解.md` 中的内容包括：

- 阶段 1 的目标、边界与出口条件
- 阶段 1 的主线步骤骨架
- 阶段 1 的议题拆分方式
- 阶段 1 的具体 artifact 语义
- 阶段 1 的双门禁位置与用途
- 阶段 1 的异常场景与侧线案例
- 阶段 1 的 full / light 实例化形态

也就是说：
- 平台文档讲机制
- 阶段文档讲该机制在阶段 1 中如何具体体现

### 八、一张简化的边界图

```text
平台通用机制层
  - workflow 编译模型
  - gate / approval runtime
  - fallback / sideflow runtime
```

### 九、当前建议结论

基于目前所有讨论，我建议把平台层和阶段层的关系收敛成下面这句话：

> **平台层负责抽象复用机制，阶段层负责承接并实例化这些机制。阶段 1 不应继续吞掉平台抽象，平台抽象也不应脱离阶段语义来源。**

- Gate / Approval Runtime

- `Template`

这几层对象拆清楚了；`阶段1-需求理解.md` 里也已经把阶段 1 的业务规则、议题、门禁、异常、full / light 两种跑法讨论得比较完整。

#### 1. `gates`

用于集中声明 gate，而不是只在 steps 里引用。

```yaml
gates:
  - gate_id: user_direction_confirmation_gate
    gate_kind: soft
    approver_roles:
      - user
  - gate_id: user_final_approval_gate
    gate_kind: hard
    approver_roles:
      - user
```

#### 2. `topics`

用于声明该模板默认启用哪些议题型子流程。

```yaml
topics:
  - topic_1_goal_and_boundary
  - topic_2_main_flow
  - topic_3_fallback_rules
  - topic_4_role_collaboration
  - topic_5_artifact_design
  - topic_6_gate_and_approval
  - topic_7_exception_and_sideflow
```

light mode 则可以只启用关键议题或把部分议题标成 implicit。

#### 3. `loops`

用于声明合法回环边。

```yaml
loops:
  - from: requirement_summary_formation
    to: initial_requirement_collection
    type: clarification_loop
  - from: scope_refinement
    to: team_discussion
    type: convergence_loop
  - from: user_direction_confirmation
    to: scope_refinement
    type: gate_rejection_loop
```

#### 4. `sideflows`

用于声明模板允许挂哪些标准侧线。

```yaml
sideflows:
  - role_expansion_sideflow
  - blocker_resolution_sideflow
  - reclassification_sideflow
  - major_change_sideflow
```

#### 5. `artifact_mapping`

用于描述议题结果、侧线结果如何回填主线 artifacts。

```yaml
artifact_mapping:
  topic_1_result:
    targets:
      - requirement_summary.stage1_goal
      - scope_decision_draft.scope_boundary
  topic_6_result:
    targets:
      - direction_confirmation.gate_rule_ref
      - approval_record.gate_rule_ref
```

### 五、编译后最小会变成什么样

如果把上面的 full template 编译成项目实例，runtime 最终拿到的对象至少应像这样：

```yaml
compiled_workflow:
  workflow_id: wf_stage1_proj_001
  compiled_from:
    template: stage1_full_requirement_analysis_template

  resolved_mode: full
  resolved_roles:
    required:
      - tech-lead

      - devops

  resolved_steps:
    - tl_takeover

    - user_direction_confirmation

    - prd_finalization

  resolved_topics:
    enabled:
      - topic_1_goal_and_boundary
      - topic_2_main_flow
      - topic_3_fallback_rules

      - topic_6_gate_and_approval

  resolved_sideflows:
    enabled:
      - role_expansion_sideflow

```

这说明模板草案的价值在于：
- 能被 policy 裁剪
- 能被 proposal 调整
- 最后能编译出 runtime 真正可执行的对象

### 六、这版模板草案的意义

这版草案最重要的意义，不是“写出了阶段 1 的最终模板”，而是验证了两件事：

#### 1. 前面的平台抽象确实能承接阶段 1

也就是：
- `Template`
- `TailoringPolicy`
- `WorkflowProposal`
- `CompiledWorkflow`

不是空抽象，而是能够真的落到一个复杂阶段。

#### 2. 阶段 1 文档里的大量讨论是可以被编译化的

也就是：
- 主线步骤
- gate
- loops
- sideflows
- topics
- artifact mapping

都已经可以逐步收敛成模板字段，而不只是文字说明。

### 七、当前建议结论

基于目前所有讨论，我建议把阶段 1 模板层先收敛成下面这版理解：

- 用两套模板承接阶段 1 的两种主要形态：
  - `stage1_full_requirement_analysis_template`
  - `stage1_light_requirement_analysis_template`
- 模板层负责提供默认骨架
- policy 层负责控制可裁剪边界
- proposal 层负责表达项目级意图
- compiled workflow 层负责生成最终可执行实例

换句话说：

> **阶段 1 现在已经不只是“讨论出一套流程”，而是已经接近可以抽成模板、交给 runtime 编译的程度。**

### 八、下一步建议

如果继续推进平台设计，最自然的下一步是：

1. 把 Gate / Approval Runtime 继续收成一版更完整的平台层设计
2. 把 Fallback / Sideflow Runtime 也补成同等粒度的通用设计

## 二十、Gate / Approval Runtime 的平台层设计

前面虽然已经在阶段 1 和模板草案里多次触及 gate，但那些内容大多还是“阶段 1 里哪里挂 gate、gate 在业务上确认什么”。

如果要把它真正提升为平台层能力，就需要回答下面这些更通用的问题：

- gate 在平台里到底是什么对象
- approval 请求和用户响应如何建模
- runtime 如何决定 gate 什么时候打开、什么时候关闭
- reject 如何和 fallback 机制对接
- gate 如何同时服务阶段 1、阶段 2、发布、验收乃至动作级确认

因此，这一节要解决的是：

> **把 gate / approval 从某个阶段的业务规则，收敛成平台可复用的运行时机制。**

### 一、设计目标

建议 Gate / Approval Runtime 至少满足以下目标：

- 支持任意 workflow step 挂 gate
- 支持不同类型的审批者，如 `user`、`tech-lead`、系统审批角色
- 支持 soft gate / hard gate
- 支持前置条件检查
- 支持审批请求、审批响应、runtime 裁决三层分离
- 支持 reject 后接入 fallback / sideflow
- 支持 reminder、timeout、取消、重发
- 支持后续扩展到动作级 gate

### 二、核心对象模型

建议平台层至少抽出下面五个对象。

#### 1. `GateDefinition`

表示 gate 的静态定义。

它回答：
- 这是什么 gate
- 谁能审批
- 审批的对象是什么
- 哪些前置条件必须满足
- 允许哪些审批结果
- 不同结果对应什么路径

示意：

```yaml
gate_definition:
  gate_id: user_final_approval_gate
  gate_name: 用户最终批准
  gate_kind: hard
  approver_roles:
    - user
  required_artifacts:
    - prd_final
    - review_summary
  allowed_decisions:
    - approved
    - rejected_minor_revision
    - rejected_review_gap
    - rejected_direction_misalignment
  reject_routes:
    rejected_minor_revision: prd_finalization
    rejected_review_gap: formal_requirement_review
    rejected_direction_misalignment: scope_refinement
```

#### 2. `GateInstance`

表示某个项目运行中的 gate 实例。

它回答：
- 这个 gate 在当前项目里是否已经打开
- 当前是否在等审批
- 当前等待谁
- 已经收到什么响应
- runtime 最终如何裁决

示意：

```yaml
gate_instance:
  gate_instance_id: gateinst_proj001_final_approval
  gate_id: user_final_approval_gate
  workflow_id: wf_stage1_proj001
  status: awaiting_user
  opened_at: 2026-04-18T10:00:00Z
  current_request_id: req_final_001
```

#### 3. `ApprovalRequest`

表示 runtime 发出的正式审批请求。

它不是普通消息，而是结构化对象。

它回答：
- 当前请求审批什么
- 给谁看
- 用户允许做哪些选择
- 这次审批引用哪些 artifacts

示意：

```yaml
approval_request:
  request_id: req_final_001
  gate_instance_id: gateinst_proj001_final_approval
  approver_role: user
  target_artifacts:
    - prd_final
    - stage1_handoff_package_draft
  approval_scope:
    - final_prd
    - handoff_readiness
  allowed_decisions:
    - approved
    - rejected_minor_revision
    - rejected_review_gap
    - rejected_direction_misalignment
```

#### 4. `ApprovalResponse`

表示审批者的结构化回复。

它回答：
- 审批者给出的明确决策是什么
- 如果拒绝，拒绝属于哪类
- 需要修改什么

示意：

```yaml
approval_response:
  request_id: req_final_001
  actor: user
  decision: rejected_review_gap
  comment: "测试口径仍不完整"
  requested_changes:
    - clarify_acceptance_criteria
```

#### 5. `GateDecision`

表示 runtime 的最终裁决结果。

它回答：
- 这次 gate 最终是通过、拒绝、超时还是取消
- 下一步怎么走
- 是否触发 fallback

示意：

```yaml
gate_decision:
  gate_instance_id: gateinst_proj001_final_approval
  resolved_as: rejected
  decision: rejected_review_gap
  next_step: formal_requirement_review
  fallback_level: L2
  fallback_target: formal_requirement_review
```

### 三、gate 生命周期状态机

建议 gate 不要完全复用 step 状态，而应有自己的运行时状态。

```text
not_ready
  -> ready_to_open
  -> awaiting_request_dispatch
  -> awaiting_response
  -> evaluating
  -> approved / rejected / expired / cancelled
```

#### 1. `not_ready`

前置条件尚未满足，gate 不能打开。

#### 2. `ready_to_open`

前置条件已满足，runtime 可以正式打开 gate。

#### 3. `awaiting_request_dispatch`

gate 已打开，但审批请求还未真正发送。

#### 4. `awaiting_response`

审批请求已发送，当前正在等待审批者回复。

#### 5. `evaluating`

审批响应已收到，runtime 正在校验并生成最终裁决。

#### 6. `approved / rejected / expired / cancelled`

表示 gate 的结束状态。

### 四、标准运行链路

建议统一成下面这条运行路径：

```text
step produces artifacts
   -> runtime checks gate prerequisites
   -> gate instance enters ready_to_open
   -> runtime dispatches approval_request
   -> approver submits approval_response
   -> runtime evaluates response
   -> gate_decision generated
   -> pass: next step
   -> reject: fallback / sideflow / terminate
```

这条链路的价值是：
- 把业务产物生成和审批行为拆开
- 把审批行为和 runtime 裁决拆开
- 让 gate 成为真正可审计的运行机制

### 五、和 workflow engine 的关系

在平台层，建议 gate 作为 workflow engine 的一类标准节点原语存在，但不是普通 action 节点。

也就是说：
- `action` 负责产出
- `gate` 负责裁决
- `event_wait` 负责等待外部事件
- `fallback_runtime` 负责 reject 后的回退路由

所以 gate 更接近：

```text
workflow primitive: gate
```

而不是简单 UI 按钮。

### 六、和阶段文档的分工

平台层需要回答：
- gate 一般怎么建模
- approval 一般怎么处理
- runtime 一般怎么裁决

阶段文档需要回答：
- 阶段 1 在哪些地方挂 gate
- `用户方向确认` 具体确认什么
- `用户最终批准` 具体确认什么
- reject 时在阶段 1 中退回哪里

### 七、和动作级 gate 的关系

这一节也为未来动作级 gate 留出了边界。

建议理解为：
- 当前重点先支持 **workflow-level gate**
- 未来如要扩展动作级 gate，可继续复用：
  - `GateDefinition`
  - `GateInstance`
  - `ApprovalRequest`
  - `ApprovalResponse`
  - `GateDecision`

只是审批对象会从“阶段产物”变成“某个具体动作”。

### 八、当前建议结论

基于目前讨论，平台层的 Gate / Approval Runtime 可以先收敛成下面这版理解：

- gate 是平台的标准运行时对象，不是某个阶段的局部技巧
- approval 必须分成 request / response / decision 三层
- gate 应有自己的生命周期状态机
- gate reject 必须能精确接入 fallback / sideflow
- 阶段文档描述 gate 的业务语义，平台文档描述 gate 的运行机制

## 二十一、Fallback / Sideflow Runtime 的平台层设计

和 gate 类似，阶段 1 已经把：
- 回环
- 回退
- 异常
- 侧线
- 重大变更

讨论得足够深入，说明这已经不是阶段 1 私有问题，而是一套平台层 runtime 能力诉求。

因此，这一节要解决的是：

> **如何把 fallback / sideflow 从阶段 1 的局部规则，提升为任意 workflow 都可复用的 runtime 机制。**

### 一、设计目标

建议 Fallback / Sideflow Runtime 至少满足以下目标：

- 支持 workflow 内合法回退
- 支持 step 级、局部、结构性三种不同层次的 fallback
- 支持短侧线处理后回并主线
- 支持重大异常触发重编排、流程切换或终止
- 支持 sideflow 产物回填主线 artifacts
- 支持和 gate reject、blocked、major_change 联动

### 二、核心对象模型

建议至少抽出下面六个对象。

#### 1. `LoopDefinition`

定义合法回环边。

它回答：
- 从哪个 step 能回到哪个 step
- 允许的 fallback level 是什么
- 哪些触发类型可以使用这条边

示意：

```yaml
loop_definition:
  from_step: user_direction_confirmation
  to_step: scope_refinement
  allowed_levels:
    - L2
  trigger_types:
    - gate_rejected
    - major_change
```

#### 2. `FallbackSignal`

表示某个 actor、gate 或系统检测器发出的“需要回退”信号。

示意：

```yaml
fallback_signal:
  source_step: user_final_approval
  trigger_type: gate_rejected
  suggested_level: L2
  reason_code: rejected_review_gap
```

#### 3. `FallbackDecision`

表示 runtime 的最终回退裁决。

示意：

```yaml
fallback_decision:
  level: L2
  target_step: formal_requirement_review
  requires_new_round: true
  invalidate_artifacts:
    - approval_record
```

#### 4. `ExceptionSignal`

表示运行中发现异常迹象，但尚未确定如何处理。

示意：

```yaml
exception_signal:
  type: role_gap_detected
  source_step: team_discussion
  severity: medium
  reason: "当前议题涉及部署约束，但尚未引入 devops"
```

#### 5. `SideflowDecision`

表示 runtime 决定开一条短侧线处理异常。

示意：

```yaml
sideflow_decision:
  resolved_as: role_expansion_sideflow
  keep_mainflow_paused: true
  create_subflow: true
  expected_return_step: team_discussion
```

#### 6. `ExceptionResolutionRecord`

表示侧线处理后的回并结果。

示意：

```yaml
exception_resolution_record:
  sideflow_id: sideflow_role_expansion_001
  resolution: completed
  artifacts_generated:
    - supplemental_role_feedback
  merged_back_to: team_discussion
```

### 三、三层处理模型

建议平台层把 fallback / sideflow 的处理分成三层：

#### 1. `local fallback`

特点：
- 在当前 workflow 内局部回退
- 不新开 sideflow
- 通常成本最低

例如：
- 小修回到上一步
- gate reject 回到定稿节点

#### 2. `sideflow handling`

特点：
- 主线暂停或半暂停
- 开一条短侧线处理特定问题
- 产出结果后回并主线

例如：
- 扩队
- blocker 处理
- 专项规则澄清

#### 3. `structural replan`

特点：
- 当前 workflow 假设被推翻
- 需要重大变更、流程切换或重启

例如：
- 项目类型判断错误
- light mode 无法继续承载复杂度
- 用户中途彻底改写目标

### 四、标准运行链路

#### 1. fallback 链路

```text
signal detected
   -> runtime checks valid loops
   -> fallback_decision generated
   -> runtime updates step / round / artifact status
   -> workflow resumes from target step
```

#### 2. sideflow 链路

```text
exception detected
   -> runtime classifies severity
   -> sideflow_decision generated
   -> subflow created
   -> sideflow executes
   -> exception_resolution_record generated
   -> mainflow resumed
```

#### 3. structural replan 链路

```text
major exception detected
   -> runtime marks current instance unstable
   -> replan / reclassification decision generated
   -> current instance frozen / terminated
   -> new workflow instance compiled
```

### 五、和 artifact system 的关系

Fallback / Sideflow Runtime 必须和 artifact system 强绑定，否则就会出现：
- 回退了但旧 artifact 仍被当成有效输入
- 侧线结果产出了，但主线不知道如何吸收

因此平台层必须支持：
- artifact invalidation
- artifact supersede
- artifact reuse
- artifact merge-back
- source tracking

也就是说，fallback / sideflow 不是单纯改 step 指针，而是会影响 artifact 状态图。

### 六、和 gate runtime 的关系

这两块机制必须能互相对接：

- gate reject 可以触发 fallback
- gate 前置条件不满足可以触发 sideflow
- sideflow 处理完成后可能重新打开 gate
- major change 可能直接使当前 gate instance 失效

因此在平台实现里，建议：
- Gate Runtime 和 Fallback / Sideflow Runtime 分模块实现
- 但在 runtime orchestration 层由统一协调器调度

### 七、和阶段文档的分工

平台层需要回答：
- fallback 一般怎么建模
- sideflow 一般怎么建模
- 异常一般怎么分类
- 侧线结果一般怎么回并主线

阶段文档则回答：
- 阶段 1 具体有哪些回环
- 阶段 1 具体有哪些异常场景
- 阶段 1 的异常分别如何处理

### 八、当前建议结论

基于目前讨论，Fallback / Sideflow Runtime 可以先收敛成下面这版理解：

- fallback 是平台层的合法回退机制，不只是阶段 1 的局部规则
- sideflow 是平台层的标准短流程能力，用于处理主线无法直接吸收的问题
- major change / reclassification 应进入 structural replan 层，而不是硬塞回普通回退
- fallback / sideflow 必须和 artifact system、gate runtime 联动
- 阶段文档描述业务场景，平台文档沉淀运行机制

### 九、下一步建议

如果继续推进平台设计，最自然的下一步是：

1. 把 artifact 生命周期系统继续收成一版更完整的平台层设计
2. 视情况再回头单独整理“确认式执行与动作级 gate”的平台边界

## 二十二、artifact 生命周期系统的平台层设计

前面在阶段 1 和平台文档中已经多次触及 artifact，但目前这些讨论仍然分散在：

- 阶段 1 的具体 artifact 语义
- 议题结果如何回填 artifact
- fallback / sideflow 对 artifact 的影响
- gate 前置条件对 artifact 完整性的要求

这说明我们实际上已经不只是在讨论“需求文档有哪些字段”，而是在暴露一个更底层的平台能力诉求：

> **平台需要一套统一的 artifact 生命周期系统，用来管理结构化交付物从创建、更新、引用、失效、合并到归档的全过程。**

也就是说，artifact 不应只是 workflow 里的静态文件名列表，而应是 runtime 可感知、可审计、可回溯、可失效、可复用的运行对象。

### 一、设计目标

建议 artifact 生命周期系统至少满足以下目标：

- 支持 artifact 的创建、更新、版本化和归档
- 支持 artifact 的来源追踪
- 支持 artifact 之间的引用与派生关系
- 支持 artifact 在 fallback / sideflow / major_change 下被失效、替代或复用
- 支持 gate 对 artifact 完整性的检查
- 支持 topic result、sideflow result 回填主线 artifact
- 支持审计、比较和回放

### 二、为什么 artifact 需要平台层建模

如果不把 artifact 提升为平台层对象，会出现几个长期问题：

- workflow 只能知道“某步产出了某文件”，却不知道这个对象是否仍有效
- fallback 发生后，旧产物仍可能被误当成当前事实
- sideflow 产出的结果无法稳定回并主线
- gate 无法可靠判断“审批对象是否齐备、是否为当前版本”
- runtime 难以做版本追踪、来源追踪和失效传播

因此平台层需要回答的，不是“PRD 里该写什么”，而是：

- artifact 一般怎么标识
- artifact 一般怎么进入新版本
- artifact 一般怎么失效
- artifact 一般怎么和其他 artifact 建立关系

### 三、核心对象模型

建议 artifact 生命周期系统至少抽出下面五个对象。

#### 1. `ArtifactDefinition`

表示某一类 artifact 的静态定义。

它回答：
- 这是什么 artifact
- 它属于哪类对象
- 它通常由哪些 step 产生
- 它需要满足什么 schema
- 它能否作为 gate 输入、handoff 输出、review 对象

示意：

```yaml
artifact_definition:
  artifact_type: prd_final
  category: structured_deliverable
  schema_ref: prd_final_schema
  produced_by_steps:
    - prd_finalization
  usable_for:
    - gate_input
    - stage_exit
    - handoff
```

#### 2. `ArtifactInstance`

表示某个项目里的某个具体 artifact 实例。

它回答：
- 这个 artifact 属于哪个项目 / workflow
- 当前版本是多少
- 当前状态是什么
- 最近一次由谁生成 / 更新
- 当前内容是否可作为有效输入

示意：

```yaml
artifact_instance:
  artifact_id: art_proj001_prd_final_v3
  artifact_type: prd_final
  project_id: proj_001
  workflow_id: wf_stage1_proj001
  version: 3
  status: active
  created_by: tech-lead
  updated_at: 2026-04-18T12:00:00Z
```

#### 3. `ArtifactRelation`

表示 artifact 与 artifact 之间的结构关系。

它回答：
- 这个 artifact 来源于谁
- 它引用了谁
- 它是否替代了谁
- 它是否由多个对象合并生成

示意：

```yaml
artifact_relation:
  from_artifact: art_proj001_prd_final_v3
  relation_type: derived_from
  to_artifact: art_proj001_prd_draft_v2
```

常见关系类型可以包括：
- `derived_from`
- `references`
- `supersedes`
- `merged_from`
- `feeds_into`

#### 4. `ArtifactVersionRecord`

表示某个 artifact 的版本演进记录。

它回答：
- 这个版本相对上一个版本改变了什么
- 为什么产生新版本
- 是正常更新、回退修订还是侧线回并

示意：

```yaml
artifact_version_record:
  artifact_id: art_proj001_prd_final_v3
  previous_version: art_proj001_prd_final_v2
  change_reason: fallback_revision
  triggered_by:
    - gate_rejected
    - fallback_decision_002
```

#### 5. `ArtifactStatusChange`

表示 artifact 状态流转记录。

它回答：
- 某个 artifact 何时从 active 变成 superseded / invalidated / archived
- 是由什么运行事件触发的

示意：

```yaml
artifact_status_change:
  artifact_id: art_proj001_proposal_v1
  from_status: active
  to_status: superseded
  reason: proposal_v2_generated_after_scope_refinement
```

### 四、建议的生命周期状态

建议平台层至少支持以下 artifact 状态：

- `draft`
- `active`
- `superseded`
- `invalidated`
- `archived`
- `cancelled`

#### 1. `draft`

含义：
- 已创建，但尚未成为当前阶段的正式有效对象

典型场景：
- `prd_draft_v1`
- 尚未被 TL 或 runtime 确认为主线输入的临时产物

#### 2. `active`

含义：
- 当前 workflow 下的有效对象
- 可以作为后续 step、gate 或 handoff 的正式输入

#### 3. `superseded`

含义：
- 曾经有效，但已被新版本替代
- 保留历史价值，但不再是当前事实来源

#### 4. `invalidated`

含义：
- 因 fallback / major_change / gate reject 等原因失效
- 不应再继续作为当前流程输入

#### 5. `archived`

含义：
- 生命周期已结束，作为历史对象保留
- 通常用于阶段完成后或流程切换后归档

#### 6. `cancelled`

含义：
- 该对象对应的生成路径被中止
- 不是被新版本替代，而是直接失去继续演进意义

### 五、标准运行链路

#### 1. 创建链路

```text
step completes
   -> runtime validates output schema
   -> artifact instance created
   -> initial status = draft / active
   -> relation + version record written
```

#### 2. 更新链路

```text
existing artifact selected for revision
   -> new artifact version created
   -> old version -> superseded
   -> new version -> active
   -> version diff + change reason recorded
```

#### 3. 失效链路

```text
fallback / major_change / reject occurs
   -> runtime identifies impacted artifacts
   -> impacted artifact status changes to invalidated
   -> downstream references marked for recheck
```

#### 4. 归档链路

```text
stage exit / workflow termination
   -> artifacts classified
   -> final active outputs retained
   -> historical versions archived
```

### 六、和 workflow engine 的关系

artifact 生命周期系统不应只是存储层，而应和 workflow engine 深度联动。

workflow engine 需要依赖 artifact 系统完成：
- step 输出校验
- gate 前置条件检查
- sideflow 结果回并
- fallback 后的失效传播
- stage exit 的交付物确认

因此可以理解为：

```text
workflow engine decides what should happen
artifact system decides what remains valid
```

### 七、和 Gate Runtime 的关系

Gate Runtime 对 artifact 生命周期系统至少有三类依赖：

#### 1. gate 打开前检查 artifact 完整性

例如：
- `user_direction_confirmation_gate` 打开前，必须有 `proposal` 和 `scope_decision_draft`
- `user_final_approval_gate` 打开前，必须有 `prd_final` 和 `review_summary`

#### 2. gate reject 会触发 artifact 失效或重修

例如：
- `approval_record` 可能直接 invalidated
- `prd_final` 可能进入 superseded 或 draft 修订链路

#### 3. gate pass 会确认某些 artifact 成为正式版本

例如：
- `prd_final` 在最终批准后成为阶段出口正式对象
- `stage1_handoff_package` 在 stage exit 时归档为 handoff 输出

### 八、和 Fallback / Sideflow Runtime 的关系

artifact 生命周期系统和 fallback / sideflow runtime 是强耦合的。

#### 1. fallback 不只是改 step，还会改 artifact 状态

例如：
- 回退到 `scope_refinement` 后，上一版 `proposal` 可能进入 superseded
- 回退到 `formal_requirement_review` 后，`approval_record` 应 invalidated

#### 2. sideflow 会生成新的临时或补充 artifact

例如：
- `role_expansion_sideflow` 生成 `supplemental_role_feedback`
- `blocker_resolution_sideflow` 生成 `blocker_analysis`

#### 3. sideflow 结束后需要回并主线 artifact

例如：
- 补充角色意见回并 `role_feedback_bundle`
- 重大变更结论回并 `proposal` / `prd_draft`

### 九、来源追踪与回填能力

为了支撑前面已经讨论过的“议题结果回填主线 artifacts”，平台层建议统一支持下面这些来源字段：

```yaml
source_topics:
  - topic_1_goal_and_boundary
  - topic_5_artifact_design

derived_from:
  - topic_1_result
  - topic_5_result

merged_from:
  - supplemental_role_feedback
  - blocker_analysis
```

这意味着 artifact 系统不仅记录“当前内容是什么”，还记录：
- 由哪些 topic result 支撑
- 由哪些 sideflow result 合并而来
- 当前版本是怎么形成的

### 十、冲突与复用规则

平台层建议明确下面几类通用规则：

#### 1. `merge_conflict`

当多个来源对象对同一字段产生冲突时，不做 silent overwrite，而应显式标记 `merge_conflict`。

#### 2. `artifact_reuse`

流程切换或重编排后，旧 artifact 不一定全部作废，应允许：
- 继续复用仍有效对象
- 显式记录复用计划

#### 3. `invalidation_propagation`

如果上游核心 artifact invalidated，下游强依赖对象也应被重新检查，而不是默认仍可用。

例如：
- `proposal` invalidated 后，依赖它的 `direction_confirmation_package` 应进入 recheck 状态

### 十一、一张简化的生命周期图

```text
create -> draft -> active -> superseded -> archived
                  |
                  +-> invalidated
                  |
                  +-> cancelled
```

如果放到 runtime 事件里看：

```text
step output
   -> artifact created
   -> gate pass / TL确认
   -> artifact active
   -> fallback / sideflow / revision
   -> superseded or invalidated
   -> stage exit / replan
   -> archived
```

### 十二、和阶段文档的分工

平台层需要回答：
- artifact 一般如何定义
- artifact 一般如何进入版本
- artifact 一般如何失效、替代、归档
- artifact 一般如何建立来源和关系

阶段文档则回答：
- `requirement_summary` 在阶段 1 中是什么意思
- `proposal` 和 `prd_final` 在阶段 1 中各自承担什么角色
- 哪些议题结果应回填哪些 artifact

### 十三、当前建议结论

基于目前讨论，artifact 生命周期系统可以先收敛成下面这版理解：

- artifact 是平台层的一等运行对象，不只是文件名或产出列表
- artifact 生命周期至少应支持：创建、激活、替代、失效、归档、取消
- artifact 系统必须和 workflow engine、Gate Runtime、Fallback / Sideflow Runtime 联动
- artifact 必须支持来源追踪、关系追踪、版本追踪和失效传播
- 阶段文档描述具体 artifact 的业务语义，平台文档沉淀 artifact 的通用生命周期能力

### 十四、下一步建议

如果继续推进平台设计，最自然的下一步是：

1. 单独整理“确认式执行与动作级 gate”的平台边界
2. 视情况把 Gate / Approval Runtime、Fallback / Sideflow Runtime、artifact system 合并成一版更完整的 runtime 总体架构图

## 二十三、确认式执行与动作级 gate 的平台边界

前面已经多次讨论到一个问题：

- 当前架构已经有明显的**流程级 gate**
- 但是否要进一步支持**动作级 gate**，还没有最终拍板

这个问题之所以值得单独整理，是因为它既不是纯粹的阶段 1 业务问题，也不是简单的 UI 交互细节，而是一个典型的平台边界问题：

> **AI 在系统里到底可以自主执行到什么程度，哪些动作应该自动放行，哪些动作应该经过 runtime 校验，哪些动作必须经过人工批准。**

也就是说，这一节要回答的，不是“某一步要不要确认”，而是：

- 什么叫确认式执行
- 什么叫动作级 gate
- 它和流程级 gate 的边界在哪里
- 平台当前是否应该支持它
- 如果支持，应该做到什么粒度

### 一、先明确几个概念

#### 1. 确认式执行

确认式执行指的是：

```text
AI 先提出修改或动作提议
   -> runtime 生成待确认对象
   -> 人或规则系统确认是否允许执行
   -> 才真正 apply
```

它强调的是：
- 先提议
- 再确认
- 后执行

而不是 AI 直接落盘、直接改状态、直接调用外部动作。

#### 2. 流程级 gate

流程级 gate 控制的是：

- 能不能进入下一 step
- 能不能进入下一阶段
- 能不能结束当前阶段

例如：
- `用户方向确认`
- `用户最终批准`

它关注的是：

> **流程状态迁移是否被允许。**

#### 3. 动作级 gate

动作级 gate 控制的是：

- 当前 step 内某个具体动作能不能真正执行
- 某个高副作用操作能不能 apply
- 某个状态变更、artifact 写入、外部动作是否要先过 gate

它关注的是：

> **某个具体执行动作是否被允许。**

### 二、为什么它是平台边界问题

这个问题必须放在平台层讨论，原因在于：

#### 1. 它不只服务阶段 1

动作级 gate 如果成立，不会只出现在：
- `prd_final` 写入
- 阶段 1 artifact 修改

它也会出现在：
- 阶段 0 项目初始化
- 阶段 2 方案拆解
- bugfix 流程
- 发布流程
- 外部副作用动作

#### 2. 它直接决定 agent 的自治边界

动作级 gate 本质上是在回答：
- agent 能不能直接 apply
- agent 能不能直接改 artifact 状态
- agent 能不能直接发审批请求
- agent 能不能直接调用外部动作

这显然属于平台运行边界，而不是某个阶段文档该单独定义的问题。

#### 3. 它会影响多个 runtime 子系统

一旦支持动作级 gate，就会影响：
- Gate / Approval Runtime
- Artifact System
- Workflow Engine
- Role Permission System
- Side Effect Control

因此它天然属于平台架构层级。

### 三、当前架构里已经有什么

目前架构里，已经明显存在下面这些能力：

- `Human-in-the-Loop` 风格的流程确认
- `Approval Gate` 风格的阶段门禁
- `Gated Autonomy` 风格的 agent 受控执行

具体体现为：
- `用户方向确认`
- `用户最终批准`
- `runtime / daemon` 负责 gate 是否开启、是否通过、是否回退
- `agent` 不能跳过 gate
- `agent` 不能自行推进主线状态

也就是说：

> **当前架构已经具备流程级的确认式执行机制，但还没有统一抽象出动作级 gate。**

### 四、为什么不应把所有动作都 gate 掉

如果动作级 gate 做得过重，会直接损伤系统可用性。

#### 1. 交互成本会爆炸

如果任何动作都要确认，就会出现：
- 生成草稿也要确认
- 更新一个中间字段也要确认
- 发一条普通结构化消息也要确认

这会让系统失去流畅性。

#### 2. runtime 复杂度会急剧上升

因为你不得不引入：
- 动作风险等级
- 不同动作对应不同审批人
- 自动批准 / runtime 校验 / 人工批准的层级
- reject 后的处理方式

如果没有明确的分层，系统会迅速变重。

#### 3. 会和流程级 gate 混淆

如果用户既要批准：
- “流程能不能往下走”
- 也要批准“某个具体动作要不要执行”

那就必须在平台层明确分层，否则语义会混乱。

### 五、建议的平台层结论：支持，但只支持高副作用动作

基于当前讨论，我建议平台层对动作级 gate 的态度先收敛成：

> **应该支持动作级 gate，但不应全面铺开；优先覆盖高副作用动作。**

这意味着：
- 保留现有流程级 gate 作为主控制面
- 动作级 gate 作为补充机制存在
- 只拦截那些风险高、影响大、难回滚的动作

### 六、建议的动作风险分层

建议平台层至少区分三档动作风险：

#### 1. `low-risk action`

特征：
- 无外部副作用
- 不改变正式状态
- 可随时重算

例如：
- 只读查询
- 草稿生成
- 信息抽取
- 普通讨论消息

建议策略：
- 自动放行
- 仅记录审计日志

#### 2. `medium-risk action`

特征：
- 会影响中间过程
- 但通常可回滚或重算
- 不直接改变最终出口对象

例如：
- 更新中间 artifact
- 创建局部 sideflow 草稿
- 标记某个 review 节点完成候选

建议策略：
- runtime 校验后执行
- 默认不需要人工逐次确认
- 必要时可由 policy 提升为 gate

#### 3. `high-risk action`

特征：
- 会改变正式交付物
- 会改变主线状态
- 会触发外部副作用
- 会造成破坏性后果或高恢复成本

例如：
- 写入 / 覆盖 `prd_final`
- 修改 `approval_record`
- 推进 workflow 状态到下一阶段
- 删除 artifact
- 触发外部系统动作
- 发送正式审批请求

建议策略：
- 必须经过动作级 gate
- 由 runtime 或人工批准后才可执行

### 七、建议优先纳入动作级 gate 的动作类型

结合当前讨论，平台层优先考虑纳入动作级 gate 的动作类型包括：

- `final_artifact_write`
- `workflow_state_transition`
- `external_side_effect_action`
- `destructive_action`

进一步可以展开为：

#### 1. `final_artifact_write`

例如：
- 写入 `prd_final`
- 覆盖 `stage1_handoff_package`
- 写入其他正式出口交付物

#### 2. `workflow_state_transition`

例如：
- 标记阶段完成
- 触发流程切换
- 执行结构性回退
- 改变 gate 最终状态

#### 3. `external_side_effect_action`

例如：
- 发送正式审批请求
- 发外部通知
- 调外部系统 API
- 触发部署 / 创建外部任务

#### 4. `destructive_action`

例如：
- 删除 artifact
- 清空当前实例的一部分产物
- 覆盖历史记录
- 取消当前主线实例

### 八、建议的最小对象模型

如果未来真的要把动作级 gate 引入平台层，建议最少抽出下面三个对象。

#### 1. `ActionDefinition`

定义一种动作的静态信息。

它回答：
- 这是什么动作
- 风险等级是什么
- 需要什么权限
- 默认执行策略是什么

示意：

```yaml
action_definition:
  action_type: final_artifact_write
  risk_level: high
  default_policy: approval_required
```

#### 2. `ActionPolicy`

定义某类动作在当前系统中的执行策略。

它回答：
- 自动放行还是 runtime 校验
- 是否必须 TL 批准
- 是否必须用户批准
- 被拒绝后如何处理

示意：

```yaml
action_policy:
  action_type: workflow_state_transition
  risk_level: high
  allowed_if:
    - current_gate_passed == true
  require_runtime_validation: true
  require_human_approval: conditional
```

#### 3. `ActionGateDecision`

表示 runtime 对某次动作执行的最终裁决。

示意：

```yaml
action_gate_decision:
  action_id: act_001
  resolved_as: approved
  executed_by: runtime
  reason: "final gate passed"
```

### 九、和现有 Gate Runtime 的关系

动作级 gate 最好不要另起炉灶，而应视为 Gate Runtime 的下沉形态。

也就是说：
- 流程级 gate 控制“能不能推进流程”
- 动作级 gate 控制“某个具体动作能不能执行”

两者最理想的关系是：

```text
Gate Runtime
  ├─ workflow-level gate
  └─ action-level gate
```

这样平台就不会出现两套完全不同的批准系统。

### 十、和 artifact / workflow / side effect control 的关系

动作级 gate 其实正好落在几个子系统的交叉处：

#### 1. 和 artifact system 的关系

- `final_artifact_write` 应能触发动作级 gate
- 覆盖正式 artifact 前可要求确认

#### 2. 和 workflow engine 的关系

- `workflow_state_transition` 应受动作级 gate 约束
- 不能因为 agent 误判就直接推进主线

#### 3. 和 side effect control 的关系

- 一切外部副作用动作都应优先纳入动作级 gate 的高风险域

### 十一、当前不拍板的部分

平台层目前可以先形成方向，但不必立刻做最终实现决策。

当前仍建议保留为待进一步决定的问题包括：

- 是否现在就全面引入动作级 gate
- medium-risk 动作是否全部走 runtime 校验，还是部分也要人工确认
- 动作级 gate 是否需要单独 UI 交互模型
- 它应否和阶段内 gate 共用完全同一套审批界面

### 十二、当前建议结论

基于目前所有讨论，我建议把“确认式执行与动作级 gate”的平台边界先收敛成下面这版理解：

- 当前架构已经具备流程级的确认式执行机制
- 动作级 gate 是后续值得补的能力，但应作为平台层机制讨论
- 动作级 gate 不应全面覆盖所有动作，而应优先覆盖高副作用动作
- 最理想的实现方式不是另起系统，而是在 Gate Runtime 之下扩展 workflow-level gate 与 action-level gate 两层能力

换句话说：

> **平台不应追求“所有动作都确认”，而应追求“高风险动作被正确 gate，低风险动作保持流畅执行”。**

### 十三、下一步建议

如果继续推进平台设计，最自然的下一步是：

1. 把 Gate / Approval Runtime、Fallback / Sideflow Runtime、artifact 生命周期系统、动作级 gate 合成一版 runtime 总体架构图
2. 视情况再回到阶段文档，标注哪些阶段动作未来可能接入动作级 gate

## 二十四、一版 runtime 总体架构图

到这一步，平台层已经逐步拆出了四块核心运行机制：

- `Gate / Approval Runtime`
- `Fallback / Sideflow Runtime`
- `Artifact Lifecycle System`
- `Action-level Gate / Confirmed Execution Boundary`

如果它们继续分散存在，虽然单块都讲清楚了，但整体关系仍然不够直观。因此，这里需要把它们重新收束成一版 **runtime 总体架构图**，回答一个更大的问题：

> **当一个 workflow 真正在系统里运行时，编译层、编排层、gate 层、fallback 层、artifact 层、动作执行层之间是如何协同工作的。**

### 一、总体理解

建议先把 runtime 看成由三层构成：

- **编译层**：把模板、policy、proposal 编译成可执行 workflow instance
- **运行控制层**：负责推进状态、裁决 gate、处理 fallback / sideflow、控制动作执行
- **对象系统层**：负责管理 artifact、角色、关系、审计记录

也就是说，不是所有逻辑都堆在一个 `WorkflowEngine` 里，而是由一组彼此配合的 runtime 子系统共同完成。

### 三、这张图里每一层在做什么

#### 1. 编译层

编译层负责回答：
- 当前项目到底跑哪条流程
- 当前模式是 full 还是 light
- 哪些步骤、gate、loops、sideflows 被启用

它的输入是：
- `Template`
- `TailoringPolicy`
- `WorkflowProposal`

它的输出是：
- `CompiledWorkflow`

也就是说：

```text
编译层负责决定“应该跑什么”
```

#### 2. 运行控制层

运行控制层负责回答：
- 当前正在跑到哪一步
- 当前 gate 是否应打开
- 当前 reject 应回退到哪
- 当前异常是否要开侧线
- 当前某个高副作用动作能否真正执行

也就是说：

```text
运行控制层负责决定“现在怎么跑”
```

#### 3. 对象系统层

对象系统层负责回答：
- 当前有哪些 artifact 是 active
- 哪些 artifact 已 superseded / invalidated
- 当前谁有权限执行哪个动作
- 当前系统应留下哪些审计和事件记录

也就是说：

```text
对象系统层负责决定“哪些运行对象仍然有效、可追踪、可被引用”
```

### 四、四块核心机制在图里的位置

#### 1. `Gate / Approval Runtime`

位于运行控制层，负责：
- gate 生命周期
- approval request / response / decision
- gate pass / reject 裁决
- 和 fallback 的衔接

#### 2. `Fallback / Sideflow Runtime`

位于运行控制层，负责：
- fallback signal / decision
- sideflow 创建与回并
- structural replan 触发
- major change / reclassification 处理

#### 3. `Artifact Lifecycle System`

位于对象系统层，负责：
- artifact 创建、更新、版本化
- supersede / invalidation / archive
- relation / source tracking
- merge-back / reuse / conflict

#### 4. `Action-level Gate`

位于运行控制层和执行边界之间，负责：
- 拦截高副作用动作
- 判断动作是否需 runtime 校验或人工确认
- 对正式 artifact 写入、流程状态变更、外部副作用动作做最后一层 gate

### 五、推荐的总控关系

建议在这几块之上，保留一个更高层的：

- `Runtime Orchestrator`

它不是所有细节都亲自实现，而是负责协调：

- `Workflow Engine`
- `Gate / Approval Runtime`
- `Fallback / Sideflow Runtime`
- `Action-level Gate`
- `Artifact Lifecycle System`
- `Role / Permission System`

也就是说：

- `Workflow Engine` 管主线 step
- `Gate Runtime` 管审批
- `Fallback Runtime` 管异常与回退
- `Artifact System` 管对象状态
- `Action Gate` 管高风险执行边界
- `Runtime Orchestrator` 负责把它们接成一条完整运行链路

### 六、一条典型运行链路示意

以阶段 1 中的 `PRD 定稿 -> 用户最终批准 -> 阶段退出` 为例：

```text
1. Workflow Engine 推进到 prd_finalization
2. tech-lead 产出 prd_final
3. Artifact Lifecycle System 创建 prd_final(vN)
4. Gate Runtime 检查 user_final_approval_gate 前置条件
5. Gate Runtime 打开 gate，并发出 ApprovalRequest
6. user 回复 ApprovalResponse
7. Gate Runtime 生成 GateDecision
8. 若 reject:
   -> Fallback Runtime 生成 FallbackDecision
   -> Artifact Lifecycle System 标记 approval_record invalidated
   -> Workflow Engine 回到 formal_requirement_review 或 prd_finalization
9. 若 approved:
   -> Action-level Gate 放行 workflow_state_transition
   -> Workflow Engine 进入 stage_exit
   -> Artifact Lifecycle System 归档最终输出
```

这条链路能说明：
- gate 不是孤立存在
- fallback 不是孤立存在
- artifact 状态也不是孤立存在
- 动作级 gate 不取代流程级 gate，而是给高风险动作补最后一层边界

### 七、为什么要把动作级 gate 放在这里

如果不把动作级 gate 画进总体图，平台会默认形成一种错觉：

- 只要流程级 gate 通过，所有动作都能直接执行

但实际上并不是这样。

例如：
- gate 通过后，`workflow_state_transition` 仍然是一个高影响动作
- 覆盖正式 artifact 仍然是一个高副作用动作
- 调用外部系统仍然是一个系统边界动作

所以动作级 gate 更像：

> **runtime 最后一层执行边界控制，而不是对流程级 gate 的替代。**

### 八、和阶段文档的分工

平台文档需要回答：
- runtime 各子系统如何配合
- gate、fallback、artifact、action gate 在架构图中的位置是什么
- 哪块负责编译，哪块负责编排，哪块负责对象状态

阶段文档需要回答：
- 阶段 1 具体挂哪些 gate
- 阶段 1 有哪些 sideflows
- 阶段 1 中哪些 artifact 会被回退或回并
- 阶段 1 中哪些动作未来值得接入动作级 gate

### 九、当前建议结论

基于目前所有讨论，我建议把 runtime 总体架构先收敛成下面这版理解：

- `Workflow Compiler` 决定“应该跑什么”
- `Workflow Engine` 决定“主线当前跑到哪里”
- `Gate / Approval Runtime` 决定“流程是否被允许推进”
- `Fallback / Sideflow Runtime` 决定“偏离主线后如何被吸收、回退或重编排”
- `Artifact Lifecycle System` 决定“哪些对象当前仍有效”
- `Action-level Gate` 决定“哪些高风险动作真的允许执行”
- `Runtime Orchestrator` 负责把这些子系统协调成一个完整运行面

换句话说：

> **runtime 不是一个单体模块，而是一组彼此协作的控制系统；只有把编译、编排、审批、回退、artifact 和动作执行边界同时放到一张图里，整个平台的运行模型才真正闭环。**

### 十、下一步建议

如果继续推进平台设计，最自然的下一步是：

1. 视情况把这张总体架构图再细化成“时序图”或“模块交互图”
2. 再回头检查阶段 0 / 阶段 1 / 阶段 2 分别会使用这张图中的哪些通用能力

总体架构图解决的是“系统由哪些部分组成”；但如果想进一步看清这几块在运行中是如何协作的，还需要补一版时序图。

这里建议先用一个典型场景来表示时序：

- 阶段 1 中 `PRD 定稿 -> 用户最终批准 -> 通过 / 拒绝 -> 推进 / 回退`

因为这个场景能同时覆盖：
- `Workflow Engine`
- `Gate / Approval Runtime`
- `Artifact Lifecycle System`
- `Fallback / Sideflow Runtime`
- `Action-level Gate`
- `Runtime Orchestrator`

### 二、这张时序图表达了什么

它强调了几件事情：

#### 1. 产物生成先于 gate 打开

也就是说：
- 不是用户先批，再生成对象
- 而是先形成待审批对象，再打开 gate

#### 2. `Gate Runtime` 只负责审批裁决，不负责直接修改 artifact

artifact 的创建、版本更新、失效标记仍然应由 `Artifact Lifecycle System` 负责。

#### 3. reject 不直接等于“回到某一步”

中间必须经过：
- `Fallback Runtime`
- 或 `Runtime Orchestrator`

来决定：
- 回退层级
- 回退目标
- 哪些 artifact 失效
- 是否要开 sideflow

#### 4. pass 后也不代表所有动作都能直接执行

例如：
- 推进到 `stage_exit`
- 标记阶段完成

这些仍然可能经过 `Action-level Gate` 的最后一层放行。

```text
  -> merge_back
  -> resume mainflow
```

这样会把正常审批流和异常侧线流都画全。

runtime 的时序视角最重要的价值在于，它把“模块存在”进一步推进成“模块怎么配合”。

换句话说：

> **总体架构图说明系统由哪些块组成；时序图说明这些块在一次真实运行中如何接力。**

### 二、这张图里最关键的关系

#### 1. `Workflow Engine <-> Runtime Orchestrator`

这是整个运行面的核心关系。

- `Workflow Engine` 负责推进主线 step
- `Runtime Orchestrator` 负责协调 gate、fallback、artifact、action gate 等子系统

#### 2. `Workflow Engine -> Artifact Lifecycle System`

主线 step 的输出，最终都要落到 artifact system。

#### 3. `Gate / Approval Runtime <-> Artifact Lifecycle System`

gate 打开前要检查 artifact；gate reject / pass 后又会影响 artifact 状态。

#### 4. `Fallback / Sideflow Runtime <-> Artifact Lifecycle System`

fallback 不只是跳 step，sideflow 不只是开支线，它们都会生成、失效、回并 artifact。

#### 5. `Action-level Gate -> SideEffect Executor`

动作级 gate 最终拦截的是：
- 正式写入
- 外部调用
- 破坏性动作
- 高风险状态迁移

#### 6. 所有模块 -> `Audit / Event Log`

建议所有关键运行模块都把：
- 状态变化
- 裁决结果
- sideflow 创建
- artifact 状态变化

写入统一的审计 / 事件日志层。

### 三、推荐的实现边界

如果后续真的落地模块实现，我会建议大致按下面方式分边界：

- `Workflow Compiler`
  - 只负责编译，不参与运行期裁决
- `Workflow Engine`
  - 只负责主线 step 编排
- `Gate / Approval Runtime`
  - 只负责审批流程与 gate 生命周期
- `Fallback / Sideflow Runtime`
  - 只负责回退、侧线和重编排
- `Artifact Lifecycle System`
  - 只负责对象状态与版本关系
- `Action-level Gate`
  - 只负责高风险动作的执行前边界
- `Runtime Orchestrator`
  - 负责跨模块协调

### 四、时序图与模块图的区别

这两张图最好一起看：

- **时序图** 适合看：
  - 某次真实运行时，动作按什么顺序发生
  - 哪些模块先后出场
- **模块交互图** 适合看：
  - 系统长期结构如何拆分
  - 哪些模块强依赖、哪些模块弱依赖

换句话说：

> **时序图解决“运行时如何流动”，模块交互图解决“系统应如何拆分”。**

### 五、当前建议结论

基于目前讨论，建议把 runtime 总体架构继续收敛成下面这版理解：

- 用总体架构图说明层次
- 用时序图说明典型运行流
- 用模块交互图说明模块边界

这样平台层设计就不会停留在概念词汇层，而会逐步逼近：
- 真正可实现的模块分工
- 真正可审计的运行链路
- 真正可扩展的 runtime 架构

```text
    |                 | 12. mark prd_final(v3) as draft/superseded for revision                         |
    |                 |--------------->|               |          |            |                   |                 |
    |                 | 13. recheck downstream refs (handoff_package_draft, gate inputs)               |
    |                 |--------------->|               |          |            |                   |                 |
    |                 |<---------------|               |          |            |                   |                 |
    |                 | 14. rollback to formal_requirement_review / prd_finalization                    |
    |<--------------- |               |               |          |            |                   |                 |
    |                 | 15. new review / revision round starts                                           |
    |---------------> |               |               |          |            |                   |                 |
    |                 | 16. revised prd_final(v4) created                                                |
    |                 |--------------->|               |          |            |                   |                 |
    |                 |<---------------|               |          |            |                   |                 |
    |                 | 17. reopen final approval gate                                                   |
    |                 |------------------------------->|          |            |                   |                 |
    |                 |                                | 18. new ApprovalRequest                         |
    |                 |                                |--------->|            |                   |                 |
    |                 |                                |          | 19. ApprovalResponse(approved)               |
    |                 |                                |<---------|            |                   |                 |
    |                 |                                | 20. GateDecision(pass)                         |
    |                 |                                |------------------------------->|                 |
    |                 |<-------------------------------|          |            |                   |                 |
    |                 | 21. request workflow_state_transition ----------------------------------------->|
    |                 |<--------------------------------------------------------------------------------|
    |                 | 22. enter stage_exit                                                           |
    |                 |--------------->| archive final outputs                                          |
    |                 |<---------------|                                                               |
```

### 二、这条时序图最关键的几个点

#### 1. gate reject 只是起点，不是结论

gate 拒绝后，系统不能简单理解为：
- “用户说不行”
- “直接回上一步”

中间至少还要经过：
- `Gate Runtime` 识别 reject 类型
- `Fallback Runtime` 生成 `fallback_decision`
- `Runtime Orchestrator` 协调后续处理

也就是说：

> **reject 是一个信号，不是最终状态迁移动作。**

#### 2. fallback 一定会触发 artifact 状态变化

如果 reject 之后只改 `current_step`，不改 artifact 状态，系统就会留下很多伪有效对象。

例如在上面这条链路里：
- `approval_record` 必须 `invalidated`
- `prd_final(v3)` 不能继续被当作当前出口版本
- 依赖它的 `handoff_package_draft`、approval input 等对象都要重新检查

也就是说：

> **fallback 是流程变化，也是对象状态变化。**

#### 3. 失效传播不一定等于全部作废

这里最重要的不是“全部清空”，而是：
- 哪些对象直接失效
- 哪些对象只是需要 `recheck`
- 哪些对象仍可继续复用

例如：
- `review_summary` 可能仍有参考价值
- `prd_final(v3)` 不能继续作为 active final output
- `approval_record` 必须直接失效

这正是 artifact 生命周期系统存在的意义。

#### 4. pass 后的推进仍可经过动作级 gate

即使用户已经批准，也不意味着所有动作都自动落地。

例如：
- `workflow_state_transition`
- `stage_exit finalize`
- 外部通知或下游启动动作

这些仍然可以被动作级 gate 作为最后一层边界控制。

### 三、一条更简化的失败路径公式

可以把这条链路抽象成：

```text
gate_reject
  -> fallback_signal
  -> fallback_decision
  -> artifact_invalidation / recheck
  -> workflow_rollback
  -> revised_artifact
  -> gate_reopen
  -> pass_or_reject_again
```

这个公式很重要，因为它说明了一件事：

> **审批拒绝不是单点事件，而是一条完整的运行链路。**

### 四、这条图对平台设计的价值

这张更完整的时序图，实际上验证了前面几块平台能力不是孤立存在：

- `Gate Runtime` 负责识别和裁决审批结果
- `Fallback Runtime` 负责把 reject 变成结构化回退
- `Artifact System` 负责让旧对象失效、新对象生效
- `Workflow Engine` 负责让主线回到正确节点
- `Action-level Gate` 负责守住最后的高风险执行边界
- `Runtime Orchestrator` 负责把这些动作接起来

换句话说：

> **只有把“拒绝后的完整恢复链路”画出来，runtime 架构才算真正闭环。**

## 二十八、阶段 0 / 阶段 1 / 阶段 2 对 runtime 通用能力的映射

前面我们已经把 runtime 的平台层能力拆得比较完整了，但还需要回答一个很实际的问题：

> **阶段 0、阶段 1、阶段 2 到底各自会使用 runtime 总体架构里的哪些通用能力。**

因为如果不做这一步映射，平台层很容易继续停留在抽象层，而无法验证这些能力是不是和阶段设计真的对上了。

### 一、先明确三类阶段的差异

#### 1. 阶段 0：项目启动

特点：
- 偏初始化和建队
- 偏项目定义、目标设立、资源准备
- 还没有进入完整需求理解和方案评审

#### 2. 阶段 1：需求理解

特点：
- 偏需求收敛
- 偏多角色协作
- 偏门禁、评审、回退和侧线处理

#### 3. 阶段 2：方案拆解 / 实施准备

特点：
- 偏结构化分解
- 偏任务拆分、接口契约、执行计划
- 偏把阶段 1 产物转成可执行工作单元

### 二、阶段 0 对 runtime 能力的使用映射

#### 1. 编译层

阶段 0 同样需要：
- `Template`
- `TailoringPolicy`
- `WorkflowProposal`
- `CompiledWorkflow`

只是它的模板更可能是：
- `stage0_project_bootstrap_template`

#### 2. Gate / Approval Runtime

阶段 0 通常用得更轻，但仍可能需要：
- 项目接管确认
- 团队方案确认
- 初始范围 / 初始方向确认

因此：
- gate 能力需要
- 但强度通常低于阶段 1

#### 3. Fallback / Sideflow Runtime

阶段 0 的异常更多表现为：
- 缺角色
- 项目类型判断错误
- 初始化信息不足

所以会更多使用：
- 扩队侧线
- reclassification
- 小回退

#### 4. Artifact Lifecycle System

阶段 0 典型 artifact 包括：
- 项目初始化记录
- 团队配置
- 初始目标描述
- 约束清单

这些同样需要版本化和来源追踪，但复杂度低于阶段 1。

#### 5. Action-level Gate

阶段 0 更可能用于：
- 创建正式项目实例
- 应用团队配置
- 启动后续阶段

也就是说，阶段 0 使用动作级 gate 的场景，通常偏“初始化落地动作”。

### 三、阶段 1 对 runtime 能力的使用映射

阶段 1 是目前最完整的样板阶段，几乎会用到全部 runtime 通用能力。

#### 1. 编译层

阶段 1 已明确存在：
- full / light 两种模板
- policy 裁剪
- proposal 编译
- compiled workflow 实例

#### 2. Gate / Approval Runtime

阶段 1 是最典型的 gate 密集阶段：
- `用户方向确认`
- `用户最终批准`

#### 3. Fallback / Sideflow Runtime

阶段 1 也是回退 / 侧线最复杂的阶段之一：
- clarification loop
- convergence loop
- 评审回退
- 终审回退
- 扩队侧线
- deferred_items
- major_change
- reclassification

#### 4. Artifact Lifecycle System

阶段 1 目前是 artifact 体系最丰富的阶段：
- `requirement_summary`
- `proposal`
- `prd_draft`
- `prd_final`
- `review_summary`
- `handoff_package`
- `topic_results`

#### 5. Action-level Gate

阶段 1 最值得未来接入动作级 gate 的动作也最清晰：
- `prd_final` 写入
- `approval_record` 更新
- `workflow_state_transition`
- `stage_exit finalize`

### 四、阶段 2 对 runtime 能力的使用映射

阶段 2 虽然当前还没像阶段 1 讨论得这么细，但从性质上看，也一定会复用大量 runtime 通用能力。

#### 1. 编译层

阶段 2 仍然需要：
- 模板
- policy
- proposal
- compiled workflow

只是模板可能更偏：
- 任务拆解
- 接口设计
- 开发计划编排

#### 2. Gate / Approval Runtime

阶段 2 很可能需要：
- 方案确认 gate
- 拆解结果确认 gate
- 进入实现前的 readiness gate

因此 gate 机制仍然是核心能力，只是审批对象从需求文档变成：
- 任务拆解结果
- 技术方案
- 执行计划

#### 3. Fallback / Sideflow Runtime

阶段 2 的 fallback / sideflow 更可能体现在：
- 方案拆解后发现阶段 1 输入不完整
- 接口边界冲突
- 任务拆分无法落地
- 发现需要补一轮设计侧线

#### 4. Artifact Lifecycle System

阶段 2 典型 artifact 可能包括：
- 任务树
- 接口契约
- 技术方案说明
- 实施计划
- 里程碑清单

这些比阶段 1 更偏执行准备，但同样需要生命周期管理。

#### 5. Action-level Gate

阶段 2 中动作级 gate 更可能作用于：
- 任务树定稿写入
- 进入开发执行阶段
- 下发正式任务到外部系统
- 创建外部里程碑 / 工单 / 分支计划

### 五、一张简化映射表

| runtime 通用能力 | 阶段 0 | 阶段 1 | 阶段 2 |
|------------------|--------|--------|--------|
| Workflow Compiler | 使用 | 强使用 | 使用 |
| Gate / Approval Runtime | 轻使用 | 强使用 | 中强使用 |
| Fallback / Sideflow Runtime | 中使用 | 强使用 | 中强使用 |
| Artifact Lifecycle System | 中使用 | 强使用 | 强使用 |
| Action-level Gate | 轻使用 | 有潜力重点接入 | 中强使用 |

### 六、这张映射图的价值

它说明了一件很重要的事：

> **阶段 1 并不是一个孤立特例，而是最先把平台能力暴露完整的样板阶段。**

也就是说：
- 平台能力不是为了阶段 1 单独设计的
- 只是阶段 1 恰好最适合把这些能力先讨论透

这也解释了为什么：
- 有些内容必须上收为平台通用机制
- 但阶段 1 仍然是最好的试验场和样板场

### 七、当前建议结论

基于目前讨论，我建议把阶段映射关系先收敛成下面这版理解：

- 阶段 0 使用 runtime 通用能力，但更偏初始化与轻量确认
- 阶段 1 是 runtime 通用能力最完整的样板阶段
- 阶段 2 会复用这些能力，但更偏拆解、计划和 readiness
- 平台层应先确保这些能力在阶段 1 跑通，再向阶段 0 / 阶段 2 平滑扩展

换句话说：

> **阶段 1 不只是业务阶段，也是平台能力的首个高复杂度验证场。**

### 八、下一步建议

如果继续推进平台设计，最自然的下一步是：

1. 视情况把阶段 0 / 阶段 2 也分别补出一版类似阶段 1 的模板草案
2. 或者回到 `流程全景图.md`，把这些平台能力和各阶段映射关系画成一张全景图

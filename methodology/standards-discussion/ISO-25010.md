# ISO/IEC 25010:2023 软件质量模型:讨论与对象抽象

> **⚠ 原文待补**:本文撰写时 `references/pdfs/` 目录下暂无 ISO/IEC 25010 原文 PDF。内容基于 ISO 官方公开摘要、25010:2011(旧版)公开文档、25010:2023(新版)公开摘要、以及 SQuaRE 系列标准的二手资料整理。**原文购入后本文需复核订正,特别是 25010:2023 相对 2011 版的具体结构变化。**
>
> 本文的目标不是把 25010 每个质量特性逐条照搬,也不是把它读成"又一份特性清单"。
>
> 当前做两件事:
> 1. **把 25010 的核心概念地基打牢** —— Quality Model 到底管什么、和 Quality in Use 是什么关系、与 25012(数据质量)/ 25019(IT 服务质量)的分工
> 2. **把 25010 理解为一个分层对象系统** —— 它不只是"给你一个质量特性清单",而是提供"从需求→度量→证据"的完整桥梁
>
> 你可以先把 `ISO/IEC 25010` 理解成:**"产品质量的国际参照系" —— 它不告诉你怎么造好产品,但它给了一个**让所有人用同一组词讨论"好"**的标准**。**
>
> 本文所参考的资料与建议阅读顺序,统一放在文末。

## 第零阶段:概念地基

> 25010 的核心价值在于它把"质量"的模糊词汇**分层结构化**。
>
> 没有 25010,团队讨论"好"或"不好"时用的词汇是散乱的 —— "好用"、"稳定"、"快"、"可扩展"…… 这些词各自含义重叠、缺失,很难拿来做需求工程或测试设计。25010 的贡献是:**给一个约定俗成的特性树,让大家至少用同一组词讨论**。

### 0.1 25010 的六层对象关系图

```text
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│   [L1]  使用上下文层                                             │
│         ──────────────                                           │
│         Stakeholders / Users / Context of Use /                  │
│         Purpose of System                                        │
│                                                                  │
│   [L2]  质量视角层                                               │
│         ──────────────                                           │
│         Quality in Use Model(从使用者角度)                     │
│         Product Quality Model(从产品本身角度)                  │
│         Data Quality Model(25012,独立标准)                     │
│                                                                  │
│   [L3]  质量特性层                                               │
│         ──────────────                                           │
│         Characteristics(Product: 8+1 个,QiU: 5 个)            │
│                                                                  │
│   [L4]  子特性层                                                 │
│         ──────                                                   │
│         Sub-characteristics(Product: 31 个)                    │
│                                                                  │
│   [L5]  质量属性层                                               │
│         ──────────                                               │
│         Quality Attributes(从子特性分解而来)                   │
│                                                                  │
│   [L6]  度量层(25023 独立标准)                                │
│         ────                                                     │
│         Quality Measures / Measurement Functions /               │
│         Measurement Methods                                      │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**读法**:
- **从下往上读**:度量(L6)汇聚成质量属性(L5),质量属性归纳成子特性(L4),子特性组成特性(L3),特性从两种视角(L2)描述一个系统,服务于具体上下文(L1)。
- **从上往下读**:明确使用上下文 → 选择质量视角 → 定义关键特性 → 展开子特性 → 设计质量属性 → 落实度量。

25010 **只覆盖 L2-L4**,L5 和 L6 交给 25023(度量标准)和各领域工程实践。

### 0.2 关键术语清单

#### 术语 A:`Quality Model`(质量模型)

**定义**:对一组质量特性及其之间关系的分类与表示。

**25010 给出三种 Quality Model**:
1. **Product Quality Model** — 产品本身的质量(静态角度)
2. **Quality in Use Model** — 产品被用时的质量(动态角度)
3. **Data Quality Model**(在 25012 独立标准) — 产品处理的数据的质量

#### 术语 B:`Quality Characteristic`(质量特性)

**定义**:质量模型的一级分类。

**Product Quality(25010:2023)的 9 个特性**:

> ⚠ 25010:2023 相对 2011 版的主要变化 —— 新增了 **Safety** 作为独立顶级特性,所以从 2011 的 8 个变为 2023 的 9 个。

1. **Functional Suitability**(功能适合性)
2. **Performance Efficiency**(性能效率)
3. **Compatibility**(兼容性)
4. **Usability** → 2023 改名为 **Interaction Capability**(交互能力)
5. **Reliability**(可靠性)
6. **Security**(安全性)
7. **Maintainability**(可维护性)
8. **Portability**(可移植性)
9. **Safety**(安全性-物理)[2023 新增]

**Quality in Use 的 5 个特性**:
1. **Effectiveness**(有效性)
2. **Efficiency**(效率)
3. **Satisfaction**(满意度)
4. **Freedom from Risk**(风险规避)
5. **Context Coverage**(上下文覆盖)

#### 术语 C:`Sub-characteristic`(子特性)

**定义**:Characteristic 的二级分解。

**总数**:Product Quality 约 31 个子特性。每个子特性更贴近工程语言。

**例子**:
- Functional Suitability → Functional Completeness / Correctness / Appropriateness
- Reliability → Maturity / Availability / Fault Tolerance / Recoverability
- Security → Confidentiality / Integrity / Non-repudiation / Accountability / Authenticity / **Resistance**(2023 新增)

#### 术语 D:`Quality Attribute`(质量属性)

**定义**:从子特性分解出的可度量工程属性。

**25010 不规定 Quality Attribute 清单** —— 留给具体项目定义。例子:
- 子特性 Availability 分解出质量属性:MTTF / MTTR / Service Level / Recovery Time
- 子特性 Fault Tolerance 分解出:Error Rate / Graceful Degradation Behavior / Redundancy Coverage

#### 术语 E:`Quality Measure`(质量度量)

**定义**:对质量属性的量化方法。

**独立标准**:25023 专门定义质量度量方法。25010 只给框架,不给具体公式。

**例子**:Availability 的度量 = uptime / (uptime + downtime)

#### 术语 F:`Quality in Use` vs `Product Quality`

**关键区分**:

| 维度 | Product Quality | Quality in Use |
|---|---|---|
| 视角 | 产品的内在属性 | 产品被使用时的效果 |
| 度量时机 | 开发/测试阶段 | 运行/使用阶段 |
| 度量对象 | 代码、架构、接口 | 用户任务完成情况、满意度 |
| 例子 | "接口响应 < 200ms" | "用户完成任务平均耗时 < 3 分钟" |

**关键洞察**:Product Quality 好不代表 Quality in Use 好,反之亦然。25010 要求**两种视角同时考虑**。

#### 术语 G:`Context of Use`(使用上下文)

**定义**:User + Task + Equipment + Environment 的组合。

**关键作用**:**同一产品在不同上下文下的 QiU 可能完全不同**。比如一个通用 Web App,在桌面浏览器的 QiU 可能高,在老旧手机 + 2G 网络下的 QiU 可能很低。25010 要求**声明目标 Context of Use**,不声明的质量度量没有意义。

### 0.3 三对最易混淆的术语

#### 辨析 1:Characteristic vs Attribute

| 维度 | Characteristic | Attribute |
|---|---|---|
| 层级 | 一级(25010 规定的 9 个) | 三级(项目定义) |
| 性质 | 概念性分类 | 可度量属性 |
| 用途 | 讨论质量视角 | 需求工程 / 测试设计 |
| 例子 | Reliability | MTTR = 2 hours |

#### 辨析 2:Performance Efficiency vs Usability

两者都容易被翻译成"好用":

| 维度 | Performance Efficiency | Usability(2023 → Interaction Capability) |
|---|---|---|
| 核心 | 系统的资源使用和响应能力 | 用户的操作流畅度 |
| 度量 | 响应时间、吞吐量、资源使用率 | 可学习性、可操作性、错误保护 |
| 关注方 | 开发/运维视角 | 用户体验视角 |

#### 辨析 3:Security vs Safety(2023 新增区分)

25010:2023 把 Safety 独立出来,之前在 2011 版里 Safety 是 Reliability 的一部分:

| 维度 | Security | Safety |
|---|---|---|
| 威胁来源 | 恶意行为者(人为主动) | 意外故障(系统/人/环境) |
| 关注 | 对抗性保护 | 防止伤害 |
| 例子 | SQL 注入、数据泄漏 | 控制故障导致物理伤害 |
| 对 AI | 对抗攻击、数据投毒 | AI 决策失误的后果 |

**在 Quantalithos 里**:AI 特有的安全考虑(prompt injection / jailbreak / hallucination)**跨 Security 和 Safety 两个特性**,不是单一特性。

### 0.4 25010 的五个常见误解

**误解 1:"只要按 25010 的 9 个特性写 NFR 就行"**

错。25010 只提供**分类**,具体 NFR 要从子特性展开到 Quality Attribute,再到可度量的 Measure。直接写"Performance: ≤ 200ms" 是粗糙的。

**误解 2:"Quality Model 是万能的"**

错。25010 明确不是所有项目都需要 9 个特性都覆盖。**按 Context of Use 和 Stakeholder Needs 选择相关特性**。

**误解 3:"高 Product Quality = 高 Quality in Use"**

错。Product Quality 是内在,QiU 是外在。一个技术上完美但界面反直觉的系统,Product Quality 可能高但 QiU 低。

**误解 4:"25010 能替代需求工程"**

错。25010 是 NFR 的**术语约定**和**分类框架**,不是需求工程方法。具体需求工程走 IEEE 29148。

**误解 5:"25010:2023 版和 2011 版差别不大"**

错。2023 版的关键变化:
- 新增 **Safety** 为顶级特性(从 Reliability 子特性升级)
- Usability 改名为 **Interaction Capability**
- Security 增加 **Resistance** 子特性
- 修订多个子特性的措辞以覆盖 AI 和自适应系统

## 第一阶段:整体架构 —— 把 25010 看成一个分层系统

### 1.1 25010 在 SQuaRE 系列里的位置

25010 属于 **SQuaRE(Systems and Software Quality Requirements and Evaluation)** 系列,即 25000 家族。完整生态:

```
                   25000  SQuaRE 概论 + 术语
                        │
    ┌───────────────────┼────────────────────────┐
    │                   │                        │
    ▼                   ▼                        ▼
25010-25019       25020-25029              25030-25059
Quality Model     Quality Measurement      Requirements & Evaluation
                                          
 25010 软件产品质量模型 ◄── 本文
 25011 IT 服务质量模型
 25012 数据质量模型
 25019 AI 质量模型(近期)
                     
 25020 度量框架
 25021 质量度量元素
 25022 Quality in Use 度量
 25023 Product Quality 度量
                                           
                                          25030 质量需求
                                          25040 评估过程
                                          25041 评估指南
                                          25045 可恢复性评估
                                          25051 COTS 评估
                                          25059 评估报告
```

**25010 的独特地位**:它是 SQuaRE 系列里**被引用最多**的标准,几乎所有讨论软件质量的文档最终都落到 25010 的特性清单。

### 1.2 25010 的双模型结构

```
┌─────────────────────────────────────────────────────┐
│                  25010 双模型                       │
├─────────────────────────────────────────────────────┤
│                                                     │
│   Product Quality Model     Quality in Use Model    │
│   ────────────────────      ────────────────────    │
│                                                     │
│   What the product          What happens when       │
│   inherently is             the product is used     │
│                                                     │
│   9 特性 + 31 子特性          5 特性 + 多个子特性     │
│                                                     │
│   测试 / 静态分析 / 架构评审    用户测试 / 使用调研    │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**两者的关系**:
- Product Quality 提供**潜在能力**
- Quality in Use 度量**实际表现**
- 两者不是因果关系,是**互补关系**

### 1.3 25010 是什么、不是什么

**是什么**:
- 一份**质量特性分类标准**(提供术语约定)
- 一份**质量模型参照系**(提供比较基准)
- 一份**需求工程的起点**(NFR 的框架)
- 一份**评估标准的基础**(被 25040 等引用)

**不是什么**:
- 不是具体度量方法(在 25023)
- 不是需求规格模板(在 29148)
- 不是测试方法(在 29119)
- 不是"好"的定义(只是术语约定)

## 第二阶段:对象系统 —— 25010 到底由哪些对象构成

### 2.1 主干对象关系

```
Stakeholders + Context of Use
        │
        │ 决定关注哪些
        ▼
Quality Characteristics(一级,9 个 Product + 5 个 QiU)
        │
        │ 分解为
        ▼
Sub-characteristics(二级,31 个 Product)
        │
        │ 项目分解为
        ▼
Quality Attributes(三级,项目定义)
        │
        │ 量化为
        ▼
Quality Measures(度量,25023 定义方法)
        │
        │ 用于
        ▼
Requirements + Tests + Evaluation Reports
```

| 对象 | 25010 章节 | 来源 | Quantalithos 对应 |
|---|---|---|---|
| Product Quality Model | §4 | 25010 定义 | 制品域 `QualityModel`(常量) |
| Quality in Use Model | §5 | 25010 定义 | 制品域 `QualityInUseModel`(常量) |
| Quality Characteristic | §4.2 | 25010 列 9 个 | 制品域 `QualityCharacteristic` 枚举 |
| Sub-characteristic | §4.3-§4.11 | 25010 列 31 个 | 制品域 `QualitySubCharacteristic` 枚举 |
| Quality Attribute | 项目定义 | 项目定义 | 制品域 `QualityAttribute` 实体 |

### 2.3 对象与 Quantalithos 六域的映射

| 25010 对象 | Quantalithos 六域对应 | 说明 |
|---|---|---|
| Quality Model(静态) | **制品域定义层 + 方法库常量** | 作为方法库里的"术语约定"资产 |
| Quality Characteristic | **制品域 Artifact 的 `quality_tags`** | 每个 Artifact 声明它服务于哪些质量特性 |
| Sub-characteristic | **制品域 Artifact 的 `quality_subtags`** | 更细粒度的标记 |
| Quality Attribute | **工作域 WorkItem(类型 = NFR)** | 作为需求存在,有自己的生命周期 |
| Quality Measure | **横切观测 → 指标事件** | 运行时度量,不在六域内 |
| Product Quality 评估 | **治理域 Gate(类型 = quality-gate)** | 评估结果经 Gate 批准 |
| Quality in Use 评估 | **对话域反馈 + 治理域 Gate** | 用户反馈驱动的 QiU 评估 |
| Context of Use | **工作域 Project 的核心属性** | 项目立项必须声明 |

**两个重要推论**:

1. **Quality Model 本身不是 Quantalithos 的动态域对象,而是方法库里的静态参照系**
2. **NFR 作为 WorkItem 的一种,进入工作域的常规管理流程** —— 不另设 NFR 跟踪系统

### 2.4 25010 对制品域状态机的影响

制品域 `Artifact` 的状态机需要扩展以承载质量评估:

```
draft → reviewed → approved → baselined → published → archived
                       │
                       │ 需要质量评估的 Artifact 在这个状态
                       │ 之前必须走 quality-gate
                       ▼
              quality-assessed
                       │
                       │ 评估结果被 Gate 批准后
                       ▼
                  approved
```

**Quality Assessment 的必要性判据**:
- **必须做**:Requirement / Design / Release(关键产物)
- **可选**:代码改动(走代码审查 Gate 即可)
- **不必做**:讨论记录 / 日志(非交付物)

## 第三阶段:Product Quality Model —— 9 个特性逐个讲

### 3.1 Functional Suitability(功能适合性)

**定义**:在指定条件下,产品或系统提供的功能**满足陈述或暗示的需求的程度**。

**子特性(3 个)**:
- **Functional Completeness** — 覆盖所有指定任务和用户目标
- **Functional Correctness** — 结果在所需精度内正确
- **Functional Appropriateness** — 功能恰好支撑指定的任务和目标,没有多余也没有欠缺

**与 AI 的交互**:
- Correctness 对 AI 特别难 —— 因为 AI 输出是概率性的
- Quantalithos 定义:AI 的 Correctness = 在预期场景下的成功率 + 置信度标注

### 3.2 Performance Efficiency(性能效率)

**定义**:在指定条件下,相对于所使用资源量的性能。

**子特性(3 个)**:
- **Time Behaviour** — 响应时间 / 处理时间 / 吞吐量
- **Resource Utilization** — CPU / 内存 / 带宽 / 存储的使用量
- **Capacity** — 最大限制(并发用户 / QPS / 数据量上限)

**AI 系统的特殊度量**:
- Tokens-per-second
- Cost-per-inference
- GPU Memory Footprint

### 3.3 Compatibility(兼容性)

**定义**:产品、系统或组件可与其他产品、系统或组件交换信息,或在相同环境共享资源的程度。

**子特性(2 个)**:
- **Co-existence** — 与其他产品共存而不相互削弱
- **Interoperability** — 与其他系统/组件交换和使用信息

**AI 特有考虑**:
- MCP 兼容性(能不能作为 MCP Client / Server)
- A2A 兼容性(能不能与其他 Agent 协作)
- 模型替换性(能不能从 Claude 换到 GPT)

### 3.4 Interaction Capability(交互能力)[2023 改名自 Usability]

**定义**:产品或系统在指定上下文中,使指定用户群能**高效、有效、满意地使用**的程度。

**子特性(6 个)**:
- **Appropriateness Recognizability** — 用户能识别产品是否适合自己需求
- **Learnability** — 用户能学会使用
- **Operability** — 易于操作和控制
- **User Error Protection** — 保护用户免于犯错
- **User Engagement** — 产品吸引用户保持参与
- **Inclusivity** — 覆盖不同能力的用户(含 Accessibility)

**25010:2023 的关键变化**:把 Usability 改名为 Interaction Capability —— 强调不仅是"好用",还包括**交互质量**整体(含 engagement 和 inclusivity)。

**对 Quantalithos 的启示**:这正好对应"用户是管理者不是开发者"的产品叙事。Quantalithos 必须在 Interaction Capability 上优于传统开发工具。

### 3.5 Reliability(可靠性)

**定义**:产品在指定条件下和指定时间内**执行指定功能**的程度。

**子特性(4 个)**:
- **Maturity** — 系统达到可靠性需求的程度(通常以故障频率衡量)
- **Availability** — 可用性(uptime / total_time)
- **Fault Tolerance** — 在硬件或软件故障下仍能运行
- **Recoverability** — 故障后恢复到指定状态的能力

**AI 特有**:
- Consistency — AI 输出的一致性(同样输入多次查询结果差异)
- Graceful Degradation — LLM 失败时的降级行为

### 3.6 Security(安全性)

**定义**:产品或系统**保护信息和数据免受未授权访问**,同时确保授权用户可访问的程度。

**子特性(6 个,2023 版新增 Resistance)**:
- **Confidentiality** — 机密性
- **Integrity** — 完整性
- **Non-repudiation** — 不可抵赖(行动可被证明)
- **Accountability** — 可问责
- **Authenticity** — 身份真实性
- **Resistance** [2023 新增] — 对已知攻击模式的抵抗

**AI 特有攻击面**(对应 Resistance):
- Prompt Injection
- Model Jailbreak
- Data Poisoning
- Model Extraction
- Adversarial Examples

### 3.7 Maintainability(可维护性)

**定义**:在指定的修改目标下,产品或系统可被**有效和高效地修改**的程度。

**子特性(5 个)**:
- **Modularity** — 模块化(改动限于局部)
- **Reusability** — 可重用
- **Analysability** — 可被分析(定位缺陷、估计改动影响)
- **Modifiability** — 可修改(不引入新缺陷)
- **Testability** — 可测试

**这是 Quantalithos 设计讨论最常引用的特性** —— 我们所有关于模块拆分、接口定义、依赖方向的讨论,本质都在优化 Maintainability 的五个子特性。

### 3.8 Portability(可移植性)

**定义**:产品或系统可被从一个环境转移到另一个环境的有效性和效率。

**子特性(3 个)**:
- **Adaptability** — 能适应不同环境
- **Installability** — 易安装
- **Replaceability** — 能替换系统中的其他指定产品

**对 Quantalithos 的启示**:
- Adaptability → 能在自托管 / SaaS / 混合部署下运行
- Replaceability → 能替换为其他 AI 工具(避免锁定)

### 3.9 Safety [2023 新增]

**定义**:产品或系统在指定上下文中**不产生不可接受的风险**(对生命、健康、财产、环境)。

**子特性(5 个)**:
- **Operational Constraint** — 运行约束
- **Risk Identification** — 风险识别能力
- **Fail Safe** — 故障时进入安全状态
- **Hazard Warning** — 危险预警
- **Safe Integration** — 与其他系统集成时的安全

**为什么 2023 版新增**:
- AI、自主系统、物联网的兴起使 Safety 不再是 Reliability 的子集
- Safety 和 Security 区别明晰(见 §0.3 辨析 3)

**对 Quantalithos 的启示**:
- AI 决策的后果评估(Fail Safe)
- 生成代码的安全审查(Hazard Warning)
- 发布前的影响评估(对应 42001 AIIA)

## 第四阶段:Quality in Use Model —— 5 个特性

Quality in Use 关注**产品被用时**的质量,从使用者和上下文角度度量。

### 4.1 Effectiveness(有效性)

**定义**:用户在指定上下文中**达到其目标的准确性和完整性**。

**关键区别于 Product Functional Correctness**:
- Functional Correctness 度量产品本身正确
- Effectiveness 度量用户借助产品**达成目标**

**Quantalithos 典型度量**:"用户发起一个'做博客'的请求到真正能用的博客的成功率"。这个度量**不只**取决于 AI 代码质量,还取决于需求澄清、过程、验收等全链路。

### 4.2 Efficiency(效率)

**定义**:达到目标时所**花费的资源**(时间、金钱、人力)相对于目标重要性的比例。

**Quantalithos 典型度量**:
- 项目从立项到第一个可用版本的 Lead Time
- 用户在项目里的人均介入时长(批准 / 回应等)
- 每单位项目价值的 LLM token 花费

### 4.3 Satisfaction(满意度)

**定义**:用户的**需求和期望**被满足的程度,在使用中产生的舒适和可接受度。

**子特性(4 个)**:
- **Usefulness** — 用户感知到的用处
- **Trust** — 对产品可靠性和结果的信任
- **Pleasure** — 使用产生的积极情绪
- **Comfort** — 物理和认知上的舒适

**对 Quantalithos 的启示**:
- **Trust 是核心** —— "用户信任 AI 团队"是产品命脉,对应"过程大于产物"的产品原则
- Satisfaction 度量必须从用户直接采集,不能由系统推断

### 4.4 Freedom from Risk(风险规避)

**定义**:产品**减轻**对人、商业、软件、财产、环境的风险的程度。

**子特性(3 个)**:
- **Economic Risk Mitigation** — 减轻经济风险
- **Health and Safety Risk Mitigation** — 减轻健康安全风险
- **Environmental Risk Mitigation** — 减轻环境风险

**对 Quantalithos**:
- Economic — AI 犯错不会造成严重经济损失(Gate 机制的根本意义)
- Health/Safety — 对 AI 做医疗 / 法律 / 金融项目的使用边界
- Environmental — AI 模型调用的碳足迹(新兴关注)

### 4.5 Context Coverage(上下文覆盖)

**定义**:产品在**指定和预期之外的上下文**中也能保持可用质量的程度。

**子特性(2 个)**:
- **Context Completeness** — 在所有指定上下文中保持指定的有效性、效率、满意度和风险规避
- **Flexibility** — 在开发时未指定的上下文中仍然可用

**对 Quantalithos**:
- Quantalithos 的 ProcessTemplate 从"小型 Web App"到"大型企业系统"的覆盖度
- 用户从"独立开发者"到"企业 CTO"的覆盖度

## 第五阶段:从质量模型到 NFR

### 5.1 25010 → 需求工程的标准链路

25010 给出的是**概念框架**,真正落到工程实践要走 IEEE 29148(需求工程)的链路:

```
25010 特性(9 Product + 5 QiU)
         │
         │ 项目选择相关的
         ▼
   关注的子特性
         │
         │ 分解为具体的
         ▼
   Quality Attributes
         │
         │ 量化为
         ▼
   NFR(29148 格式)
         │
         │ 验证方式
         ▼
   Acceptance Criteria
         │
         │ 落实为
         ▼
   Tests / Monitoring / Gate
```

### 5.2 NFR 的标准写法

从 25010 子特性写到可验证 NFR,应该遵循 SMART 原则。示例:

**错误示范**(只写到特性层):
> "系统必须 Reliable。"

**中等示范**(写到子特性):
> "系统必须有高 Availability。"

**正确示范**(写到属性 + 度量):
> "系统必须达到 Availability ≥ 99.9%,以 30 天滚动窗口内的 uptime / total_time 度量,monitoring 数据每 5 分钟采集一次,低于 99.9% 触发 Gate 事件。"

### 5.3 Quantalithos 的 NFR 模板

作为 WorkItem(type=NFR),包含:

```yaml
nfr_id:           NFR-2026-042
characteristic:   Reliability
sub_characteristic: Availability
target_attribute: Service Availability
measurement:
  method:          uptime / total_time
  window:          30d rolling
  threshold:       >= 99.9%
  datasource:      OTel metrics
verification:
  type:            [Continuous Monitoring + Gate]
  gate_trigger:    value < 99.9%
owner:            Platform Ops Member
traceability:
  stakeholder:     SaaS enterprise customers
  context_of_use:  production SaaS deployment
  rationale:       Enterprise SLA requirement
```

### 5.4 NFR 与 Gate 的关系

每个 NFR 应有对应的 Gate 机制:

| NFR 类型 | Gate 类型 | 触发时机 |
|---|---|---|
| Pre-release NFR(性能、安全) | release-gate | 发布前 |
| Continuous NFR(可用性、错误率) | threshold-violation-gate | 指标违反 |
| Quality in Use(用户满意度) | feedback-review-gate | 周期性 + 异常事件 |
| Safety NFR | safety-assessment-gate | 每次重大变更 |

## 第六阶段:25010 与其他标准的关系

### 6.1 与 ISO/IEC 25012(数据质量)的关系

25012 把 25010 的 Quality Model 思想扩展到**数据**。15 个数据质量特性(准确性、完整性、一致性、及时性、信用度、时效性等)。

**Quantalithos 里的用处**:
- AI 训练数据的质量(对应 42001 A.7 数据治理)
- 用户项目数据的质量评估

### 6.2 与 ISO/IEC 25019(AI 质量)的关系

25019 是较新的标准,专门覆盖 AI 特有质量特性。新增的特性包括:
- **Robustness** — AI 对扰动的鲁棒性
- **Explainability** — 可解释性
- **Fairness** — 公平性(减少偏见)
- **Controllability** — 可控性(人类可控程度)

**Quantalithos 的选择**:25010 + 25019 并用,AI 相关的 NFR 参考 25019 的 AI 特性,常规 NFR 参考 25010。

### 6.3 与 ISO/IEC 25023(质量度量)的关系

- 25010 提供**特性分类**
- 25023 提供**度量方法**

两者配套使用 —— 写 NFR 时,特性名字来自 25010,度量公式来自 25023。

### 6.4 与 IEEE 29148(需求工程)的关系

- 25010 提供**NFR 的术语体系**
- 29148 提供**需求文档的编写规范**

Quantalithos 的需求工程流程应该把两者结合:
- 需求模板字段用 29148 的结构(需要、愿景、SRS)
- NFR 字段的分类用 25010 的术语

### 6.5 与 ISO/IEC/IEEE 42010(架构描述)的关系

42010 要求架构描述覆盖**利益相关方关注点**。25010 提供一个**标准化的关注点清单**。

**组合使用**:
- 架构文档的 Stakeholder Concerns 章节,引用 25010 的相关特性
- 每个架构决策(ADR)说明影响哪些 25010 特性

### 6.6 与 ISO/IEC 42001(AI 管理系统)的关系

42001 要求组织度量 AI 系统的质量(§9.1),具体度量框架可参照 25010 + 25019:

```
42001 §9.1 要求监视测量
            │
            │ 引用
            ▼
25019 AI 质量模型
            │
            │ 扩展
            ▼
25010 Product / QiU Quality Model
            │
            │ 具体方法在
            ▼
25023 Quality Measures
```

## 第七阶段(总结):25010 对 Quantalithos 的根本意义

### 7.1 25010 为 Quantalithos 提供的四件事

1. **NFR 的术语标准** — 产品域 + 工作域在讨论质量时使用同一组词
2. **Gate 的分类骨架** — 治理域的 Gate 可以按 25010 特性分类
3. **ProcessTemplate 里的质量检查点** — 每个过程阶段出口对应一组 25010 子特性检查
4. **与 42001 / 25019 的对接桥梁** — AI 特有 NFR 走 25019,标准 NFR 走 25010

### 7.2 25010 对 Quantalithos 的关键约束

- **Project 必须声明 Context of Use** — 立项时的必填字段
- **Artifact 必须能标注 quality_tags** — 对应到 25010 特性
- **NFR 作为一等 WorkItem** — 不单设 NFR 系统
- **25010:2023 的 9 个特性中,Safety 和 Security 区分明确** — 治理域 Gate 分类里显式区分

### 7.3 25010 与 AI Member 设计的互动

对照前几轮的 AI Member 设计,25010 带来的补充:

1. **QA Member 角色能力画像** — 必须内置 25010 特性树 + 子特性检查清单
2. **ProcessTemplate 的 Quality Gate** — 每个阶段出口有质量评估 Gate
3. **ArchiveBundle 里的 Quality Evidence** — 归档包包含各 25010 特性的评估证据
4. **用户反馈通道对应 QiU** — 对话域的用户反馈直接映射到 Satisfaction 和 Trust 度量

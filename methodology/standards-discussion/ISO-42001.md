## 第零阶段:概念地基

> 在进入条款和控制项细节之前,先把 42001 里最核心的术语讲清楚。

### 0.1 42001 的六层对象关系图

42001 不是单一规范,而是一个由组织、治理、过程、控制、证据、责任链共同构成的六层对象体系:

```text
┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│   [L1]  组织与环境层                                                │
│         ──────────────                                              │
│         Organization / Context / Stakeholders /                     │
│         Interested Parties / Scope of AIMS                          │
│                                                                     │
│   [L2]  治理与方针层                                                │
│         ──────────────                                              │
│         AI Policy / AI Objectives / Leadership Commitment /         │
│         Roles & Responsibilities                                    │
│                                                                     │
│   [L3]  过程与生命周期层                                            │
│         ──────────────────                                          │
│         AI System Lifecycle / AI Development Process /              │
│         AI Deployment Process / AI Operation Process                │
│                                                                     │
│   [L4]  控制与保障层(附录 A)                                       │
│         ────────────────────                                        │
│         9 个控制族 × 38 个控制项                                    │
│                                                                     │
│   [L5]  证据与审计层                                                │
│         ──────────────                                              │
│         Documented Information / Records / Audit Trail /           │
│         Impact Assessment Records(AIIA)                           │
│                                                                     │
│   [L6]  责任链层                                                    │
│         ────────                                                    │
│         AI Provider / Developer / User / Operator /                 │
│         Partner / Subject / Regulator                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**读法**:

- 从下往上读:先明确**责任链**(谁对什么负责),再通过**证据**证明尽责,证据由**控制**产生,控制嵌在**过程**里,过程受**治理**约束,治理服务于**组织**的使命。
- 从上往下读:组织识别环境 → 建立方针 → 定义过程 → 落实控制 → 产出证据 → 分清责任。

42001 的独特贡献是:**它让 L6(责任链层)显式化了**。传统 MS 标准(9001/27001)都假设"组织自己对自己负责",但 AI 产品的责任链往往横跨多个法人主体(模型提供方、应用开发方、部署方、终端用户、数据主体),42001 把这层显式出来。

### 0.2 关键术语清单

#### 术语 A:`AI Management System(AIMS)`(AI 管理系统)

**定义**:组织为实现 AI 相关方针和目标,建立、实施、维护并持续改进的一套相互关联或相互作用的要素(方针、过程、规程、资源、角色、责任)。

**关键点**:
- AIMS **不是 AI 技术**,是治理 AI 技术的**管理系统**
- AIMS **不是新发明**,它沿用 ISO HLS 的管理系统骨架(和 27001/9001 同构)
- AIMS 的独特性在于**AI 特化的控制项和 AI 特有的生命周期考虑**

**在 Quantalithos 里**:整个**治理域 + 横切观测 + 方法库的 AI 政策部分**共同构成 AIMS。这不是一个单独的模块,是一个**横跨多个域的治理视图**。

#### 术语 B:`AI System`(AI 系统)

**定义(42001 采纳的 ISO/IEC 22989 定义)**:由显式或隐式的目标驱动、从其接收的输入推断如何产生预测、推荐、决策或内容的工程化系统,这些输出可以影响物理或虚拟环境。

**关键特征**:
- 有明确或隐含的**目标**
- 处理**输入 → 推断 → 输出**
- **输出会影响环境**(这是与普通软件的核心区别)
- 可能具有不同程度的**自主性**和**适应性**

**在 Quantalithos 里**:
- Quantalithos **本身**是一个 AI System(输出是"软件项目产物")
- Quantalithos 运行时**每一个 AI Member** 也是一个 AI System(输出是"代码、设计、评审意见")
- 这种"AI 系统套 AI 系统"的嵌套性,42001 允许,但要求**每一层都有自己的 AIMS 覆盖**

#### 术语 C:`AI Actor`(AI 参与者)

**定义**:与 AI 系统生命周期有关的任何个人或组织,包括但不限于:

- **AI Provider** — 把 AI 系统投放市场的一方(Quantalithos 公司)
- **AI Producer / Developer** — 设计开发 AI 系统的一方(Quantalithos 开发团队)
- **AI Customer** — 采购或部署 AI 系统的一方(企业用户)
- **AI User** — 使用 AI 系统的一方(最终用户 Alice)
- **AI Partner** — 为 AI 系统提供组件的一方(OpenAI / Anthropic 作为 LLM 提供商)
- **AI Subject** — 其数据被 AI 系统处理的一方(用户的私有数据主体)
- **Relevant Authority** — 监管方

**关键点**:42001 明确**同一组织可以扮演多个 AI Actor 角色**,每个角色有不同的责任。

**在 Quantalithos 里**:Quantalithos **同时是 Provider、Developer、Operator**(如果用户选择 SaaS 部署),**也是 Partner**(相对于 Anthropic / OpenAI 是 Customer 或 User)。必须清楚标识每种身份下的责任边界。

#### 术语 D:`AI Lifecycle`(AI 生命周期)

**定义**:AI 系统从立项到退役的完整时间范围,通常包括(参考 ISO/IEC 5338):

1. **Inception** — 立项、可行性
2. **Design and Development** — 设计与开发
3. **Verification and Validation** — 验证与确认
4. **Deployment** — 部署
5. **Operation and Monitoring** — 运行与监控
6. **Re-evaluation** — 再评估(数据漂移、性能下降触发)
7. **Retirement** — 退役

**与传统软件生命周期的区别**:
- 多了 **Re-evaluation** 阶段(AI 会随时间漂移,不像传统软件稳定)
- **Verification & Validation** 更复杂(需要数据集验证、偏见检测、对抗鲁棒性)
- **Operation** 阶段要求**持续监控模型性能**,不是只监控系统可用性

#### 术语 E:`AI Impact Assessment(AIIA)`(AI 影响评估)

**定义**:对 AI 系统在其预期用途和可合理预见的误用下,**对个人、群体、社会、环境**产生的影响的系统性评估。

**42005 专门标准**:AIIA 的完整方法论在 ISO/IEC 42005 独立标准中详述。

**关键输出**:
- 影响范围(受影响的利益相关方清单)
- 影响类型(福祉、权利、安全、公平、环境、经济)
- 影响可能性与严重度
- 缓解措施
- 残余风险

**在 Quantalithos 里**:
- **Quantalithos 本身需要 AIIA**(我们开发的是一个 AI 产品)
- **Quantalithos 服务的每个项目也需要微型 AIIA**(如果用户用我们做医疗、金融、司法项目,必须有影响评估)
- AIIA 是治理域 `Gate` 的特殊类型(`impact_assessment_gate`)

#### 术语 F:`AI Policy`(AI 方针)

**定义**:最高管理层正式发布的、关于组织 AI 战略方向、原则和承诺的声明。

**42001 要求的最小 AI Policy 内容**:
- AI 系统的**预期用途和约束**
- 对**伦理、法律、社会责任**的承诺
- 对**安全、可靠、公平、透明、隐私**的原则声明
- **利益相关方的承诺**
- **持续改进**的承诺

**与一般 MS 方针的区别**:AI Policy 必须明确**哪些用途禁止**(AI Policy 通常包含 "Prohibited Uses" 列表),例如不得用于特定类型的监控、评分、操纵。

#### 术语 G:`AI Objective`(AI 目标)

**定义**:实现 AI 方针的可度量目标。

**42001 要求**:
- 每个 AI Objective 必须可度量
- 必须与 AI Policy 对齐
- 必须被持续监控

**典型 AI Objective**:
- "AI 输出的准确率在目标场景下 ≥ X%"
- "AI 系统的偏见评分(如 Demographic Parity)在 [-Y%, +Y%] 范围内"
- "所有 AI 决策的可解释性证据保留 ≥ Z 年"

#### 术语 H:`Documented Information`(文档化信息)

**定义**:组织必须保留并管理的信息(沿用 9001/27001 定义)。

**42001 的两种文档化信息**(和 9001 一致):
- **指导型**(procedures, policies, work instructions) — "说你要做什么"
- **记录型**(records, evidence) — "证明你做了什么"

**42001 特有的文档化信息**:
- AI Impact Assessment Reports(AIIA 报告)
- AI Risk Treatment Plans(AI 风险处置计划)
- AI System Documentation(AI 系统文档,遵循 42001 附录 B 模板)
- Training Data Provenance Records(训练数据来源记录)
- Model Performance Logs(模型性能日志)
- Incident Response Logs(事件响应日志)

### 0.3 最容易混淆的三对术语

#### 辨析 1:AIMS vs AI System

| 维度 | AIMS | AI System |
|---|---|---|
| 本质 | 管理 AI 的**治理体系** | 被管理的**技术系统** |
| 持久性 | 组织级,跨多个 AI System | 系统级,有生命周期 |
| 覆盖范围 | 政策/过程/控制/证据/责任 | 输入/模型/输出/环境影响 |
| 42001 要求对象 | 这份标准要求组织建立 | 这份标准管理的对象 |
| 数量 | 组织通常 1 个 AIMS | 组织内可能有 N 个 AI System |

**经典混淆**:把"我们部署了一个 AI 系统"等同于"我们有 AIMS"。错 —— 前者是事实,后者是**治理承诺**。

#### 辨析 2:AI Impact Assessment vs AI Risk Assessment

| 维度 | AIIA | AI Risk Assessment |
|---|---|---|
| 关注点 | AI 对**外部**(人/社会/环境)的影响 | AI 对**组织**的风险(安全/合规/财务) |
| 方向 | 向外看 | 向内看 |
| 典型输出 | 受影响方清单 + 缓解措施 | 风险登记册 + 处置计划 |
| 触发时机 | AI 系统立项 + 重大变更 | 持续进行 |
| 专项标准 | ISO/IEC 42005 | ISO/IEC 23894 |

**关键区别**:这两者是**互补**的,不是替代。大多数组织只做 Risk Assessment 会忽略对外影响,只做 AIIA 会忽略对自己的风险。

#### 辨析 3:Full AIMS vs Integrated MS

| 维度 | Full AIMS | Integrated MS |
|---|---|---|
| 定义 | 独立的 AI 管理系统 | 把 AI 管理要求整合进现有 MS |
| 适用 | 没有其他 MS 的组织 | 已有 9001/27001 的组织 |
| 文档 | 独立文档集 | 现有文档集 + AI 扩展 |
| 认证 | 独立 42001 认证 | 多标准联合认证 |

**Quantalithos 的选择**:按 A 方案,Quantalithos 从零起步,直接建立 Integrated MS —— 以 42001 为核心,兼容 9001(质量)和 27001(信息安全)的要求。

### 0.4 42001 的五个常见误解

**误解 1:"42001 是 AI 伦理标准"**

部分正确但不精确。42001 包含伦理条款,但本质是**管理系统标准**,重点在"可审计的治理体系"而非"具体伦理原则"。具体伦理原则在 ISO/IEC 24368 等辅助标准里。

**误解 2:"有了 42001 就不需要 EU AI Act 合规"**

错。42001 是国际标准(推荐性),EU AI Act 是法律(强制性)。两者是桥梁关系 —— 42001 认证能帮助 EU AI Act 合规举证,但不免除法律义务。

**误解 3:"只有高风险 AI 才需要 42001"**

错。42001 适用于**任何部署 AI 的组织**,不限于高风险。风险级别影响**控制项的严格程度**,不影响**是否适用**。

**误解 4:"42001 只管模型训练阶段"**

错。42001 覆盖**整个生命周期**:立项、设计、开发、验证、部署、运行、再评估、退役。

**误解 5:"42001 要求具体的技术手段(比如强制可解释性模型)"**

错。42001 是**基于风险的**(risk-based),不强制任何具体技术。它要求组织**识别风险 + 选择缓解措施 + 证明有效性**,技术手段由组织选择。

## 第一阶段:整体架构 —— 把 42001 看成一个分层系统

### 1.1 42001 的 HLS 骨架

42001 完全遵循 ISO 管理体系的**高层结构(HLS / Annex SL)**,章节与 9001/27001 同构:

```
第 1 章   范围
第 2 章   规范性引用
第 3 章   术语和定义
第 4 章   组织环境         ─┐
第 5 章   领导             │  Plan
第 6 章   策划             ─┘
第 7 章   支持             ─┐  
第 8 章   运行             ─┘  Do
第 9 章   绩效评价         ─── Check
第 10 章  改进             ─── Act

附录 A    控制参考(38 个控制项,9 个控制族)
附录 B    控制项实施指南
附录 C    AI 相关风险来源
附录 D    各领域应用指南
```

### 1.2 42001 相对 9001 / 27001 的 AI 特化点

虽然 HLS 一致,42001 在以下方面**特化**:

| 章节 | 9001/27001 里的要求 | 42001 的 AI 特化 |
|---|---|---|
| §4.1 组织环境 | 一般内外部环境 | **必须考虑 AI 特有的环境**(AI 监管、社会期待、技术演进速度) |
| §4.2 相关方 | 一般干系人 | **必须包括 AI Subject 和 AI-affected parties** |
| §5.2 方针 | 一般方针 | **必须有 AI Policy,明确禁止用途** |
| §6.1 风险 | 一般风险 | **必须做 AIIA 和 AI Risk Assessment** |
| §7.2 能力 | 一般能力要求 | **必须包括 AI 伦理、AI 风险识别能力** |
| §8 运行 | 一般运行控制 | **必须覆盖 AI 生命周期的每个阶段** |
| §9.1 监视测量 | 一般 KPI | **必须包括模型性能漂移、偏见、鲁棒性** |
| §10.1 不符合 | 一般纠正 | **AI 事件必须有专项响应流程** |

### 1.3 42001 的双层结构

可以把 42001 看成两层:

```
┌──────────────────────────────────────────────────┐
│  [上层] 通用管理系统骨架(HLS)                     │
│                                                  │
│  章节 4-10,和 9001/27001 同构                    │
│  PDCA 循环,基于风险                              │
│                                                  │
└────────────────────┬─────────────────────────────┘
                     │ 通过附录 A 连接
                     ▼
┌──────────────────────────────────────────────────┐
│  [下层] AI 特化控制参考                           │
│                                                  │
│  附录 A 的 38 个控制项                           │
│  分 9 个控制族                                   │
│  每个控制项对应具体的 AI 治理要求                 │
│                                                  │
└──────────────────────────────────────────────────┘
```

**关键洞察**:组织**选择哪些控制项适用**(基于风险评估结果),**必须声明选择的理由**(适用性声明 SoA),和 27001 的机制一模一样。

                        │ 提供合规骨架
                        ▼
       ┌────────────────────────────────────────────────┐
       │  **[本层] ISO/IEC 42001**:AIMS 标准(顶级)       │
       └─────┬─────────────┬────────────┬───────────────┘
             │             │            │
             │             │            │

1. **AIMS 不是一个新增域,而是一个跨域治理视图** —— Quantalithos 架构不会因 42001 新增顶层域

| Deployment | 过程域的 Deployment 阶段 | DevOps Member |

**注意**:Quantalithos 本身**既是一个 AI System**(开发软件),**也帮用户开发 AI System**(如果用户项目是 AI 应用)。两种身份下的 AIMS 覆盖范围不同 —— 前者覆盖 Quantalithos 平台,后者可能扩展到用户项目。

## 第四阶段:附录 A —— 38 个控制项

42001 附录 A 给出 **9 个控制族 × 38 个控制项**。下面逐族讲清分工和对 Quantalithos 的影响。

> ⚠ 控制项的精确编号和措辞需要原文复核。本节按 42001 附录 A 的公开结构整理族的分工和重点项。

### 4.1 A.2 AI 相关政策(AI-related Policies)

**族的意图**:要求组织建立、维护、沟通一组 AI 相关政策。

**重点控制项**:
- 组织必须有 **written AI Policy**
- AI Policy 必须与其他 MS 政策(质量、信息安全、隐私)对齐
- AI Policy 必须**定期评审**(最少年度)

**Quantalithos 对应**:方法库的 `AIPolicy` 实体 + 治理域 `PolicyReviewCycle` 过程。

### 4.2 A.3 内部组织(Internal Organization)

**族的意图**:在组织内分配 AI 相关角色和责任。

**重点控制项**:
- 必须明确 AI Actor 责任链
- 必须指定 AI 系统的 **AI Role(决策者)**
- 必须在项目/系统级别报告和升级 AI 问题

**Quantalithos 对应**:身份域 Role 定义 + 治理域 RACI 矩阵。

### 4.3 A.4 AI 系统的资源(Resources for AI Systems)

**族的意图**:识别、记录、管理 AI 系统所需的资源(数据、工具、计算、人员)。

**重点控制项**:
- **Data Resources** — 训练/测试/验证数据的来源、许可、质量
- **Tooling Resources** — 使用的 AI 工具清单和治理
- **System and Computing Resources** — 部署环境、可伸缩性、冗余
- **Human Resources** — 人员能力要求

**Quantalithos 对应**:
- Data Resources → 方法库 `DataSource` 实体 + 制品域 `DatasetArtifact`
- Tooling Resources → capability-hub 的工具白名单
- Computing Resources → L4 基础设施层的配置清单
- Human Resources → 身份域 `Capability` 画像

**这是最关键的族之一** —— 它直接对应三条红线的**可追溯性**(数据/工具/资源都要追溯)。

### 4.4 A.5 评估 AI 系统的影响(Assessing Impacts of AI Systems)

**族的意图**:要求组织评估 AI 系统对个人、群体、社会、环境的影响。

**重点控制项**:
- 建立 AIIA 过程(遵循 ISO/IEC 42005)
- AIIA 覆盖 intended use 和 foreseeable misuse
- AIIA 包含对受影响群体的识别和评估
- AIIA 记录保留(长期)

**Quantalithos 对应**:
- `ImpactAssessment` 作为治理域的一等实体
- AIIA Gate 强制触发点:项目立项后 + 重大变更时
- AIIA 记录归档到 ArchiveBundle

### 4.5 A.6 AI 系统生命周期(AI System Life Cycle)

**族的意图**:覆盖 AI 系统从设计到退役的全生命周期治理。

**重点控制项**:
- **AI System Requirements** — 需求包含伦理/公平/鲁棒性要求
- **AI System Design** — 设计记录和决策追溯
- **V&V** — 独立验证确认
- **Deployment** — 部署前审批
- **Operation** — 持续监控
- **Retirement** — 退役流程

**Quantalithos 对应**:
- 过程域的 ProcessTemplate `ai-lifecycle` 覆盖 5338 的阶段
- 每个阶段的出口都是 Gate(强制审批)
- Retirement 对应项目归档流程

### 4.6 A.7 AI 系统的数据(Data for AI Systems)

**族的意图**:管理数据全生命周期(采集、处理、存储、使用、销毁)。

**重点控制项**:
- **Data Quality** — 数据质量标准和度量
- **Data Provenance** — 数据来源可追溯
- **Data Preparation** — 预处理过程记录
- **Data Privacy** — 隐私保护措施

**Quantalithos 对应**:
- 制品域 `DatasetArtifact` 的专用状态机
- 横切观测的 data-lineage 事件
- 与 ISO 27001 / 27701 协同

### 4.7 A.8 AI 系统的信息(Information for Interested Parties)

**族的意图**:向受影响方提供 AI 系统的透明信息。

**重点控制项**:
- **System Documentation for Users** — 用户文档包含 AI 能力和限制
- **External Reporting** — 对外报告机制(事件、投诉、申诉)
- **Communication of Incidents** — 事件对外通告流程

**Quantalithos 对应**:
- 每个用户项目的 `SystemDocumentation` 制品必须包含 AI 透明度声明
- 对话域的公开 Gate(用户反馈通道)
- 事件响应作为专用 ProcessTemplate

### 4.8 A.9 AI 系统的使用(Use of AI Systems)

**族的意图**:确保 AI 系统按 intended use 使用,防止误用。

**重点控制项**:
- **Processes for Responsible Use** — 负责任使用的流程
- **Objectives for Responsible Use** — 负责任使用的目标

**Quantalithos 对应**:
- 在对话域 + 治理域,每个 Member 发起高风险行为前必须经过 Responsible Use 检查
- prompt injection 防御直接对应此族

### 4.9 A.10 对 AI 系统伙伴和供应商的治理(Third-party and Customer Relationships)

**族的意图**:管理外部 AI Actor(供应商、客户、合作方)的关系。

**重点控制项**:
- **Allocation of Responsibilities** — 分清供应商/客户责任
- **Suppliers** — 供应商 AI 治理要求
- **Customers** — 客户侧的使用边界协议

**Quantalithos 对应**:
- 对**模型供应商**(Anthropic/OpenAI)的治理 → capability-hub 的 ProviderContract
- 对**企业客户**的使用边界 → Terms of Use + 用户侧 AIMS 对接
- 对**MCP 第三方 Server** → 白名单 + 审计

## 第五阶段:符合性与认证

### 5.1 42001 的符合性类型

42001 和其他 MS 标准一样,有三种符合性层级:

1. **自我声明(Self-declaration)** — 组织自己评估自己符合
2. **第二方确认(Second-party confirmation)** — 客户/合作方评估供应商
3. **第三方认证(Third-party certification)** — 独立认证机构按 IAF MD 23 要求审核

**Quantalithos 的选择**:初期 Self-declaration,中期争取 Third-party。

### 5.2 42001 认证的前置条件

根据 **IAF MD 23**(42001 认证要求):
- 认证机构必须按 ISO/IEC 17021 运作
- 审核员必须有 AI 专业能力
- 认证周期 3 年 + 年度监督
- 重大变更需要额外审核

### 5.3 Statement of Applicability(SoA)

**要求**:组织必须产出 SoA,声明:
- 附录 A 的哪些控制项适用
- 不适用的控制项的**理由**
- 已实施控制项的**实施状况**

**Quantalithos 落地**:
- SoA 作为治理域的 `SoADocument` 实体
- 每个 Control 的适用性决策有记录
- SoA 作为归档包 ArchiveBundle 的固定组成部分

### 5.4 与 EU AI Act 的桥接

42001 与 EU AI Act 的关系是"合规举证的桥梁":

| EU AI Act 要求 | 42001 对应机制 |
|---|---|
| Risk Management System | §6.1 AI Risk Assessment + 附录 A 控制项 |
| Data Governance | A.7 数据治理控制族 |
| Technical Documentation | §7.5 文档化信息 + A.6 生命周期记录 |
| Record-keeping | §7.5 + 横切观测审计日志 |
| Transparency to Deployers | A.8 信息提供族 |
| Human Oversight | A.6 + A.8 + Gate 机制 |
| Accuracy, Robustness, Cybersecurity | §9.1 监视测量 + 相关控制项 |

**注意**:42001 认证**不等于**EU AI Act 合规。42001 提供治理框架,但 EU AI Act 的具体技术要求(如高风险分类、合规评估程序)必须独立满足。

## 第六阶段:42001 与其他标准的关系

### 6.1 与 ISO 其他 MS 标准的 HLS 共骨架

42001 共用 HLS,所以和下面这些标准**可以集成**:

| 标准 | 领域 | 与 42001 集成点 |
|---|---|---|
| ISO 9001 | 质量管理 | §4-§10 章节结构完全一致 |
| ISO 27001 | 信息安全 | §6.1 风险评估 + SoA 机制 |
| ISO 27701 | 隐私(PII) | 数据治理控制族 |
| ISO 22301 | 业务连续性 | AI 事件响应流程 |
| ISO 31000 | 风险管理 | §6.1 风险评估方法论 |

**在 Quantalithos 里**:采用**Integrated MS**,用一套管理系统同时覆盖 42001 + 27001 + 9001 的核心要求,不建立多个独立系统。

### 6.2 与 AI 专项标准的协作

```
  ISO/IEC 42001(本文)
       │
       │ 依赖
       ├──────► ISO/IEC 22989(AI 概念术语)
       │        └─ 提供术语基础
       │
       ├──────► ISO/IEC 23894(AI 风险管理)
       │        └─ 深化 §6.1 风险方法论
       │
       ├──────► ISO/IEC 42005(AI 影响评估)
       │        └─ 深化 A.5 AIIA 实施细节
       │
       ├──────► ISO/IEC 5338(AI 生命周期过程)
       │        └─ 深化 A.6 生命周期实施
       │
       ├──────► ISO/IEC 24027(AI 偏见评估)
       │        └─ 支持 §9.1 监视指标
       │
       └──────► ISO/IEC 24368(AI 伦理考虑)
                └─ 支持 §5.2 AI Policy
```

### 6.3 与 NIST AI RMF 的对照

NIST AI RMF 和 42001 是**并行标准**:
- 42001 是管理系统(ISO 路径),结构化、可认证
- NIST AI RMF 是框架(NIST 路径),灵活、可自评估

**差异**:
- 42001 要求 **Documented Information**(必须有正式文档)
- NIST AI RMF 提供 **Playbook**(提供可执行清单)

**在 Quantalithos 里**:以 42001 为治理骨架,引用 NIST AI RMF 的具体实施指南。

## 第七阶段(总结):42001 对 Quantalithos 的根本意义

### 7.1 42001 为 Quantalithos 提供的五件事

1. **治理域的国际标准依据** — Gate / Policy / Control / Impact Assessment 都有 42001 条款支撑
2. **AI Actor 责任链的明确化** — 身份域的 Role 必须映射到 42001 的 AI Actor 分类
3. **文档化信息的最低要求** — 制品域 Artifact 的最小必须集由 42001 给出
4. **可审计基线** — 横切观测的审计事件覆盖 42001 的要求
5. **双层 AIMS 架构** — Quantalithos 本身的 AIMS + 每个用户项目的微型 AIMS

### 7.2 42001 对 Quantalithos 的关键约束(设计时必守)

- **§6.1 AIIA 必须在项目立项后完成** — Gate 机制在过程模板里强制前置
- **SoA 必须在归档包里** — 归档服务不能跳过
- **AI Actor 必须显式** — 身份域 Role 定义不能含糊
- **Control 必须可追溯到 AI Risk** — 治理域的 Control 和 RiskAssessment 必须有关联
- **持续监控必须覆盖模型漂移** — 横切观测必须有漂移检测指标

### 7.3 42001 补丁到 AI Member 设计的关键点

对照前几轮的 AI Member 设计,42001 补丁包括:

1. **新增 Auditor Member Role** — 内部审计过程需要独立 Role
2. **ComplianceDeclaration 的标准格式** — 继承 42001 SoA + AIIA + Conformance 三段
3. **Runtime reasoning trace 持久化** — 对应 42001 的可解释性要求
4. **capability-hub 扩展为 Provider 治理** — MCP Server 治理直接对应 A.10 族
5. **Nonconformity 事件链** — 横切观测新增此事件族

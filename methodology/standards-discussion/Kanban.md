# Kanban Method：讨论与对象抽象

> 本文的目标不是把 `Kanban` 简化成一块“待办 / 进行中 / 已完成”的看板，也不是把若干会议节奏抄成一种管理秘方。
>
> 当前先做四件事：
> 1. **先把 `Kanban Method` 的概念地基打牢**——知道它到底在定义什么、不在定义什么
> 2. **再把 `Kanban` 理解为一个分层对象系统**——像 `BPMN 2.0`、`Scrum`、`ISO/IEC 29110` 那样，先看清它如何用服务、工作、流动、约束、反馈与演进组织协作
> 3. **把官方术语压平成对象关系**——避免把 `board`、`workflow`、`WIP`、`pull`、`cadence`、`service` 混成口号
> 4. **最后把这些对象放回工程现场**——理解它为什么能进入团队协作、服务交付、跨团队治理与持续改进
>
> 你可以先把 `Kanban Method` 理解成：**一套面向知识型工作的服务交付管理方法。它不替换现有流程，而是在现有工作方式之上，通过可视化、限制在制品、管理流动、显式化规则、建立反馈环和实验式演进，让需求与能力逐步走向平衡。**

## 学习阶段总览

当前这份讨论与抽象文档，按 20 个阶段展开：

0. **第零阶段：概念地基**
   - 把 `Service`、`Demand`、`Capability`、`Work Item`、`Workflow`、`Kanban System`、`Policy`、`WIP`、`Pull`、`Cadence`、`Experiment` 等核心术语逐个讲清楚
   - 把最容易混淆的概念做对照辨析
   - 确保后续阅读不因术语含混而偏移
1. **第一阶段：整体架构——把 Kanban 看成一个分层系统**
   - 回答 `Kanban Method` 到底是什么
   - 建立“它是管理方法，不是流程模板大全”的基本认识
   - 用类似 `BPMN 2.0` 的“分层系统”视角先看全景
2. **第二阶段：对象系统主干——Kanban 到底由哪些对象构成**
   - 理解 `Customer -> Demand -> Service -> Work Item -> Workflow -> Delivery` 的主干关系
   - 理解 `Board`、`Policy`、`WIP Limit`、`Metrics`、`Cadences`、`Experiment` 如何围绕主干工作
3. **第三阶段：六种观察视角——Kanban 从哪些角度理解工作系统**
   - 服务视角、需求-能力视角、工作流视角、约束视角、反馈视角、演进视角
4. **第四阶段：六种视角之间的关系**
   - 理解这些视角不是替代关系，而是观察焦点迁移
5. **第五阶段：Kanban System——为什么它是 Kanban 的最小系统单位**
   - 理解为什么 `board` 只是外显，不是标准本体
6. **第六阶段：Board——为什么它只是系统投影，不是系统本身**
   - 理解列、泳道、卡片、缓冲区、承诺点、交付点的作用边界
7. **第七阶段：Flow——Kanban 为什么把“流动”置于中心**
   - 理解为什么管理流动比提高个人忙碌度更重要
8. **第八阶段：WIP / Pull——Kanban 的运行约束到底是什么**
   - 理解 `WIP Limit`、`Pull Signal`、`Pull System` 如何形成控制逻辑
9. **第九阶段：Policy——为什么规则是流动系统的一部分**
   - 理解规则不是文书负担，而是协作边界
10. **第十阶段：Metrics——如何把流动变成可观察对象**
    - 理解 `Lead Time`、`Throughput`、`WIP`、`CFD`、`Run Chart`、`SLE`
11. **第十一阶段：Cadences——Kanban 如何把反馈制度化**
    - 理解 `Kanban Meeting`、`Replenishment`、`Review`、`Retrospective` 的控制作用
12. **第十二阶段：类型与服务类别——工作为什么不能一视同仁**
    - 理解 `Work Item Type` 与 `Class of Service` 的差异
13. **第十三阶段：承诺与边界——从 Option 到 Delivery 的对象链条**
    - 理解 `Option`、`Commitment Point`、`System Lead Time`、`Customer Lead Time`
14. **第十四阶段：STATIK——Kanban 如何设计，而不是只会贴卡片**
    - 理解 `STATIK` 的六步设计逻辑
15. **第十五阶段：演进式改进——Kanban 为什么强调实验而不是大改造**
    - 理解 `Hypothesis`、`Experiment`、`Scientific Method`、`Evolutionary Change`
16. **第十六阶段：关系——Kanban 与 Scrum / BPMN / DevOps 的边界**
    - 理解它们的关注点差异与组合方式
17. **第十七阶段：对象字典与关系矩阵**
    - 把核心对象逐个定型
    - 用矩阵把依赖关系、控制关系、反馈关系压平
18. **第十八阶段：Kanban 在工程中的典型使用方式**
    - 理解团队级、服务级、多团队级、组织级的不同落地形态
19. **第十九阶段：常见失真模式——看起来像 Kanban，实际上不是**
    - 用失真模式反推哪些对象和关系一旦丢失，Kanban 就会空转
20. **第二十阶段：学习顺序与记忆框架**
    - 用最小结构把 `Kanban Method` 压缩成一个适合记忆的系统

### 0.1 Kanban 的六层对象关系图

`Kanban` 不是一块板，不是一句“限制 WIP”，也不是一组会议节奏，而是一个由服务语境、需求与能力、工作流、显式约束、反馈机制和演进机制共同构成的六层对象体系：

```text
┌─────────────────────────────────────────────────────────────────────┐
│                    Kanban 的六层对象体系                             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  第一层：服务与客户对象                                              │
│  ───────────────────────────────────────────────                    │
│  Customer                 —— 请求与验收的一方                        │
│  Service                  —— 承载交付的服务                          │
│  Service Delivery         —— 完成请求的一系列活动                    │
│  Demand                   —— 客户放入系统的工作请求                  │
│                                                                     │
│  第二层：工作与流动对象                                              │
│  ───────────────────────────────────────────────                    │
│  Work Item                —— 被交付的工作项                          │
│  Work Item Type           —— 行为相似的一组工作项                    │
│  Workflow                 —— 工作项经过的活动序列                    │
│  Activity                 —— 推进工作项的活动                        │
│  Delivery                 —— 工作从系统流出并交付                    │
│                                                                     │
│  第三层：系统与可视化对象                                            │
│  ───────────────────────────────────────────────                    │
│  Kanban System            —— 工作流的服务交付模型                    │
│  Kanban Board             —— 系统在可视层的投影                      │
│  Card / Ticket            —— 工作项的可视表示                        │
│  Column / Lane / Buffer   —— 活动、分流与容量分配                    │
│  Commitment / Delivery Pt —— 进入与离开系统的边界                    │
│                                                                     │
│  第四层：约束与治理对象                                              │
│  ───────────────────────────────────────────────                    │
│  Policy                   —— 处理工作的显式约定                      │
│  WIP Limit                —— 在制品约束                              │
│  Pull Signal              —— 可用容量的信号                          │
│  Pull System              —— 有需求且有容量时才交付                  │
│  Class of Service         —— 差异化处理规则                          │
│                                                                     │

│  ───────────────────────────────────────────────                    │
│  Lead Time                —— 工作穿越系统所花时间                    │
│  Throughput               —— 单位时间离开系统的工作量                │
│  WIP                      —— 系统中的工作量                          │
│  Metrics                  —— 观察系统行为的反馈                      │
│  Cadence / Review         —— 周期性反馈环                            │
│                                                                     │
│  第六层：改进与演进对象                                              │
│  ───────────────────────────────────────────────                    │
│  Dissatisfaction          —— 变革动因                                │
│  Hypothesis               —— 改进假设                                │
│  Experiment               —— 试验性变更                              │
│  Evolutionary Change      —— 渐进式演化                              │
│  STATIK                   —— 设计 Kanban 系统的方法                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

这张图的意义在于：

- `Kanban` 不是“贴卡片的方式”，而是一个从**客户请求 -> 服务交付 -> 流动控制 -> 数据反馈 -> 试验改进**的完整闭环
- 每一层回答不同的问题：为什么有这项工作、它如何流动、系统怎样被约束、怎样观察系统、怎样改变系统
- 只有先看清这个整体，后面学习 `WIP Limit`、`Pull`、`Cadence` 或 `STATIK` 时，才知道自己在理解哪一层
- **Kanban 的关键不是“每个人都很忙”，而是“让工作以可预测、可持续的方式流过系统”**

### 0.2 核心概念清单

下面把 `Kanban` 最重要的术语，按六层分组，逐个讲清楚。

#### 第一组：服务与客户

**Service——Kanban 的基本语境对象**

官方 Glossary 对 `Service` 的定义非常关键：它从客户请求开始，通过 `service delivery` 被满足，并以客户接受作为结果。

这意味着 `Kanban` 首先不是围绕“团队”组织的，而是围绕：

- 谁在提出请求
- 什么请求被处理
- 处理链条如何运作
- 请求何时算真正被交付和接受

所以要先记住一句话：

> `Kanban` 的第一观察单位不是组织架构图上的部门，而是能对外提供结果的 `Service`。

**Customer——请求与验收的来源**

客户可以是：

- 外部用户
- 业务部门
- 另一个内部服务
- 同一组织内的上下游单元

这说明 `Kanban` 天然支持服务网络视角：一个服务既可能有客户，也可能是另一个服务的供应者。

**Demand——被放入系统的请求**

`Demand` 是客户向服务提出的工作请求。

它不是任意待办事项堆，而是：

- 来自客户的请求
- 具有交付意义
- 需要服务能力来响应

官方强调，Kanban 的一个核心目标就是让 `Demand` 与 `Capability` 逐步平衡。

**Service Delivery——完成客户请求的一系列活动**

服务交付不是“某个人做完了任务”，而是：

- 一串活动形成了工作流
- 工作项穿越工作流
- 最终交付给客户并被接受

所以 `Kanban` 的视角天然比“任务追踪”更高一层，它关注的是：**请求如何穿越服务系统。**

#### 第二组：工作与流动

**Work Item——Kanban 的基本流动单元**

`Work Item` 是由于需求进入系统、将由服务处理并最终交付的对象。

它可以是：

- 缺陷
- 特性
- 用户故事
- 事故
- 招聘岗位
- 培训课程
- 项目包或产品包

也就是说，`Kanban` 不绑定某一种工件形式。

**Work Item Type——行为模式相似的一组工作项**

官方强调，工作项类型是“行为相似、遵循相同工作流”的分组。

所以它更像：

- 一类流经路径相近的工作
- 一类大小、节奏、风险模式相似的工作

而不是“业务标签”而已。

**Workflow——工作项通过系统的路径**

`Workflow` 是一系列活动，通常从请求开始，以交付结束。

它是 `Kanban` 中最容易被误学的概念之一，因为很多人会把它误读成理想流程图。官方恰恰强调：

- 要建模真实工作流，而不是理想化未来流程
- 它可以顺序、并行，或者部分无固定顺序
- 它是工作系统的真实行为路径

**Flow——工作在系统中的移动**

在 `Kanban` 语境里，`Flow` 不是抽象口号，而是工作项穿越系统的运动状态。

它的目标不是简单“更快”，而是：

- 更平滑
- 更可预测
- 更少阻塞
- 更少切换
- 更持续

**Delay / Blocker / Bottleneck——流动受损的三种典型现象**

- `Delay`：延迟，等待、依赖、切换、优先级插队等都可能造成延迟
- `Blocker`：某个工作项当前被阻碍
- `Bottleneck`：某个活动约束了整个工作流的流动率

把这三个概念分开很重要：

- `Blocker` 更像单项故障
- `Bottleneck` 更像系统性约束点
- `Delay` 是更广义的时间损耗现象

#### 第三组：系统与可视化

**Kanban System——Kanban 的最小系统单位**

官方定义非常直接：`Kanban System` 是一个 `kanban service delivery workflow` 的模型。

它包含：

- `Board`
- 以 `Card` 形式出现的 `Work Item`
- `Policies`
- `Metrics`
- `Cadences`

所以 `Kanban System` 不是板，而是**板 + 规则 + 反馈 + 节奏**的组合。

**Kanban Board——系统的可视投影**

`Board` 负责把工作项、活动、状态、限制与风险展示出来。

但它不是标准本体，而是：

- 系统的一种可视表示
- 流动与规则的显示面板
- 协作时“大家看到同一张图”的地方

**Card / Ticket——工作项的可视表示**

卡片不是任务便签本身，而是 `Work Item` 在可视层的一个表示。

也就是说：

- `Work Item` 是对象本体
- `Card` 是它的可视形式

#### 第四组：约束与决策

**Policy——显式规则**

`Kanban` 里的规则不是附录，而是系统本体的一部分。

规则可以定义：

- 何时补货
- 按什么条件拉动
- 什么叫完成
- 不同服务类别如何处理
- WIP 上限是多少
- 会议何时进行

官方特别强调，规则应当：

- 简洁
- 明确
- 可见
- 始终适用
- 可由服务提供者调整

**WIP / WIP Limit——工作量状态与进入约束**

- `WIP`：系统中尚未退出的工作项数量
- `WIP Limit`：允许进入某部分系统的最大工作量

它的核心作用不是“逼人忙起来”，而是：

- 防止系统过载
- 形成 `Pull System`
- 降低切换成本
- 改善时效、质量与可预测性

**Pull Signal / Pull System——由容量驱动，而不是由计划推动**

`Pull Signal` 的本质是：**下游还有容量。**

`Pull System` 的本质是：

- 有需求
- 且有可用交付容量
- 才让工作进入或向前移动

它与传统 `Push` 式项目管理有本质区别。

**Class of Service——差异化对待工作项的规则集**

服务类别是通过规则定义的一种差异化处理方式。

官方列出了四个常见原型：

- `Expedite`
- `Fixed Date`
- `Intangible`
- `Standard`

它反映的不是工作项是什么，而是：**这个工作项应该如何被服务系统对待。**

#### 第五组：反馈与度量

**Lead Time——时间视角的核心指标**

`Lead Time` 是工作在工作流两个点之间所经历的时间。

在 `Kanban` 里，它至少有几个重要变体：

- `Lead Time`：一般意义的流经时间
- `System Lead Time`：从承诺点到系统内某个起始列的时间定义版本
- `Customer Lead Time`：从客户请求到交付的时间

**Throughput / Delivery Rate——单位时间产出**

它关心的是在一段时间里，多少工作项离开系统。

这不是“每个人做了多少”，而是：

- 系统每周交付多少项
- 系统每月吞吐多少项

**Metrics——系统反馈的载体**

官方常用的度量包括：

- `Lead Time`
- `Throughput`
- `WIP`
- `Blockers`
- `Failure Demand`

这些度量的意义不在于绩效打分，而在于理解系统行为。

**Cadence / Feedback Loop——制度化反馈**

反馈如果不进入行动，就不算反馈环。

这句官方定义非常重要：

> `Feedback information without action is not a feedback loop.`

也就是说：

- 图表不是目的
- 会议不是目的
- 数据只有驱动了调整，才构成真正的反馈环

#### 第六组：设计与演进

**Change Management Principles——变革管理三原则**

官方列出三条：

- `Start with what you do now`
- `Agree to pursue improvement through evolutionary change`
- `Encourage acts of leadership at all levels`

它决定了 `Kanban` 的变革方法论不是大爆炸重构，而是渐进演化。

**Service Delivery Principles——服务交付三原则**

官方列出三条：

- 理解并关注客户需求与期望
- 管理工作，让人围绕工作自组织
- 定期审查服务网络及其规则，以改进结果

这说明 `Kanban` 的上位视角不是“团队排程术”，而是服务导向的组织理解方式。

**STATIK——设计 Kanban 系统的方法**

`STATIK` 不是板面模板，而是系统思考式的设计方法。

它至少包含六步：

- 识别不满来源
- 分析需求
- 分析能力
- 建模工作流
- 识别服务类别
- 设计系统

**Hypothesis / Experiment / Evolutionary Change——改进的基本语法**

`Kanban` 不鼓励口号式优化，而鼓励：

- 先观察
- 再提出假设
- 再试验
- 再收集数据
- 再决定保留或回滚

所以 `Kanban` 的改进单位不是“运动式改革”，而是**可回退的实验。**

### 0.3 最容易混淆的 12 组概念辨析

#### 0.3.1 Kanban Board vs Kanban System

- `Board` 是可视表示
- `System` 是交付工作流的完整模型
- 没有规则、度量、节奏的板，不等于完整的 `Kanban System`

#### 0.3.2 Work Item Type vs Class of Service

- `Work Item Type` 回答“这是什么类型的工作”
- `Class of Service` 回答“它应如何被差异化对待”

前者偏结构与行为模式，后者偏策略与优先规则。

#### 0.3.3 WIP vs Capacity

- `WIP` 是当前系统里有多少工作
- `Capacity` 是系统在高效流动前提下能承载多少工作

两者相关，但不等价。

#### 0.3.4 Lead Time vs Throughput

- `Lead Time` 看单个工作项穿越系统要多久
- `Throughput` 看单位时间有多少工作项穿越系统

一个偏时间长度，一个偏流出速率。

#### 0.3.5 Push vs Pull

- `Push`：不管下游是否有容量，先把工作塞进去
- `Pull`：只有下游有容量时，才允许工作进入或前进

#### 0.3.6 Option vs Committed Work

- `Option` 还处在上游判断阶段，可能有价值，但尚未承诺交付
- 过了 `Commitment Point` 之后，工作才真正进入交付系统

#### 0.3.7 Policy vs Work Instruction

- `Policy` 是协作边界与共同约定
- `Work Instruction` 更像细粒度操作手册

`Kanban` 需要的是使自组织成为可能的规则，而不是替代思考的说明书。

#### 0.3.8 Cadence vs Meeting

- `Meeting` 是一个事件
- `Cadence` 是带有固定目的和周期的反馈机制

不是所有会议都构成 `Cadence`，更不是所有 `Cadence` 都只是“开会”。

#### 0.3.9 Service vs Team

- `Team` 是组织单元
- `Service` 是交付单元

一个服务可能由一个团队承担，也可能跨多个团队。

#### 0.3.10 Flow Optimization vs Worker Utilization

- `Worker Utilization` 追求每个人都满载
- `Flow Optimization` 追求工作平滑、稳定、可预测地流过系统

`Kanban` 明确偏向后者。

#### 0.3.11 Kanban vs Scrum

- `Scrum` 更像围绕固定节奏、责任与工件的协作框架
- `Kanban` 更像围绕流动、约束、反馈与服务交付的管理方法

它们可以组合，不是互斥关系。

#### 0.3.12 Management Method vs Process Framework

- `Kanban` 不预设一整套统一流程模板
- 它不替换既有流程，而是在其之上叠加控制逻辑

这正是官方一再强调 `method without methodology` 的原因。

---

### 0.4 第零阶段最值得背下来的 8 句话

1. `Kanban` 首先是 `management method`，不是统一流程模板。
2. `Kanban` 关注的是 `service delivery`，不是任务墙美观度。
3. `Kanban` 管理的是工作，而不是让人更忙。
4. `WIP Limit` 的目标是建立 `pull`，不是机械限量。
5. `Board` 是系统的投影，不是系统本体。
6. `Metrics` 的意义是理解系统行为，不是先天等于绩效考核。
7. `Cadence` 的意义是形成行动型反馈闭环。
8. `Kanban` 的变革方式是实验式演化，不是颠覆式改造。

---

### 0.5 第零阶段最容易犯的 8 个错误

#### 误解 1：把 Kanban 学成“电子看板工具的使用说明”

这会把方法学问题降格为界面操作问题。

#### 误解 2：把 WIP 限制理解为“每个人最多同时做几个任务”

官方允许限额作用于列、泳道、类型、整套系统，而不只是个人。

#### 误解 3：以为 Kanban 只适合团队级任务追踪

官方明确强调它在管理层和组织层的收益更大。

#### 误解 4：把 Flow 理解成“尽量催快”

真正目标是平滑、可预测、可持续，而不是粗暴加速。

#### 误解 5：以为只要有板就已经“用了 Kanban”

没有规则、度量、反馈环和演进机制，通常只是在可视化任务。

#### 误解 6：把加急类工作当成默认通道

如果 `Expedite` 成为日常状态，系统设计通常已经失真。

#### 误解 7：只收集数据，不基于数据采取行动

官方明确指出：没有行动，就没有真正的反馈环。

#### 误解 8：试图先设计理想流程，再强行要求团队迁移过去

`Kanban` 的官方起点是现实工作方式，而不是先画乌托邦流程图。

- `Kanban` 为什么不是流程模板？
- `Board` 与 `Kanban System` 有什么区别？
- `Demand` 与 `Capability` 为什么要被平衡？
- `WIP Limit` 为什么是建立 `Pull System` 的关键？
- `Work Item Type` 与 `Class of Service` 为什么不是一回事？
- `Metrics` 和 `Cadence` 为什么共同构成反馈环？
- `STATIK` 为什么是设计方法，而不是板子样式？

## 第一阶段：把 Kanban 看成一个分层系统

### 1.1 第一层：Kanban 到底在表达什么

如果把 `BPMN 2.0` 的问题概括为“流程如何被表达”，那么 `Kanban` 的问题更接近：

- 服务如何响应客户请求
- 请求如何穿过工作系统
- 流动如何被约束和调节
- 系统如何通过反馈和实验持续改进

所以 `Kanban` 表达的不是静态流程步骤大全，而是**服务交付系统的运行与演化。**

它至少同时在表达四件事：

1. **服务现实**——谁向谁提出请求，谁对谁交付结果
2. **流动现实**——工作是如何穿越工作流的
3. **控制现实**——哪些规则、限额、节奏在约束系统
4. **改进现实**——系统如何根据反馈持续重构自身

### 1.2 第二层：Kanban 用什么来表达这些内容

如果把 `BPMN` 的表达对象看成 `Flow Objects / Connecting Objects / Swimlanes / Artifacts`，那么 `Kanban` 的表达对象更适合被看成：

```text
Kanban 的表达对象分工

服务语境层
  ├─ Customer / Demand / Service
  │    表达：为什么会有这些工作，以及服务关系是什么
  │
工作流动层
  ├─ Work Item / Workflow / Activity / Delivery
  │    表达：工作如何通过系统
  │
系统控制层
  ├─ Board / Policy / WIP Limit / Pull
  │    表达：工作如何被可视化与约束
  │
反馈学习层
  └─ Metrics / Cadences / Experiment
       表达：系统如何观察自己并持续改进
```

### 1.3 第三层：Kanban 为什么不只是“可视板方法”

很多人第一次接触 `Kanban` 时，会把它理解成“看板可视化管理”。这种理解只对了一小部分。

`Kanban Method` 至少同时包含下面几个层面：

- `Service-oriented paradigm` —— 以服务网络理解组织
- `Flow management` —— 以工作流动理解交付系统
- `Explicit constraints` —— 通过规则和 WIP 限制塑造系统行为
- `Feedback system` —— 通过度量与节奏形成可行动反馈
- `Evolutionary change` —— 通过实验式演进改变系统
- `Design method` —— 通过 `STATIK` 去设计系统，而不是只会使用系统

### 1.4 第四层：Kanban 最终想怎么落地

`Kanban` 的落地，不只是“把工作画出来”，而是至少包括官方所强调的六种通用实践：

- `Visualize`：让工作和风险变得可见
- `Limit WIP`：限制在制品，防止系统过载并为拉动创造条件
- `Manage Flow`：基于数据理解和改善流动
- `Make Policies Explicit`：把进入、移动、完成和差异化处理的规则显化出来
- `Use Feedback Loops`：用会议、评审和图表组织反馈
- `Evolve Experimentally`：通过小步试验持续重构系统

### 2.2 服务主轴：Customer / Demand / Service / Acceptance

这是 `Kanban` 的最上位主轴。

它回答的问题是：

- 谁在提出请求
- 请求进入哪项服务
- 服务通过什么路径响应这些请求
- 什么时刻才算真正交付与被接受

这条主轴决定了：`Kanban` 不是“团队内部把任务做完就结束”，而是**以服务交付结果是否被客户接受为边界来理解工作。**

### 2.3 流动主轴：Work Item / Workflow / Activity / Delivery

这是 `Kanban` 的运行主轴。

它回答的问题是：

- 工作的最小交付单位是什么
- 它经过哪些活动
- 工作是顺序、并行还是带缓冲地向前移动
- 最终何时从系统中流出

这条主轴决定了：`Kanban` 的主要观察对象不是项目计划，而是**工作项在系统中的运动。**

### 2.4 约束主轴：Policy / WIP Limit / Pull / Class of Service

这是 `Kanban` 的控制主轴。

它回答的问题是：

- 什么工作可以进入系统
- 什么时候可以前移
- 谁可以优先走
- 哪些工作必须等待容量

这条主轴的意义在于：`Kanban` 不是自然流动主义，而是**通过显式约束塑造系统行为。**

### 2.5 反馈主轴：Metrics / Cadences / Feedback Loops

这是 `Kanban` 的学习主轴。

它回答的问题是：

- 当前系统表现如何
- 流动变好了还是变差了
- 什么时候应该补货、回顾、检视风险
- 哪些调整真的起作用了

如果没有这条主轴，`Kanban` 很容易退化成“把工作贴出来”。

### 2.6 演进主轴：Dissatisfaction / Hypothesis / Experiment / Evolutionary Change

这是 `Kanban` 的改进主轴。

它回答的问题是：

- 为什么要改
- 改什么
- 如何验证
- 改动失败时如何回退

也就是说，`Kanban` 把“改进”也对象化了，而不是停留在泛泛口号上。

### 2.7 边界主轴：Upstream / Commitment / Delivery / Downstream

虽然很多团队只看到板中间那几列，但 `Kanban` 官方其实非常强调边界：

- 上游还有很多 `Options`
- 并不是所有需求都应立即进入系统
- 过了承诺点，工作才真正被交付系统接受
- 交付之后，还会进入客户接受与下游使用情境

所以 `Kanban` 的边界意识比“任务执行视角”更强。

## 第三阶段：六种观察视角——Kanban 到底从哪些角度理解工作系统

与 `BPMN 2.0` 的“四种建模视角”不同，`Kanban` 更适合被理解为六种观察视角。

### 3.1 第一种视角：Service 视角

看的是：

- 组织对外或对内提供什么服务
- 谁是客户
- 客户为什么发起请求
- 请求如何被接受和完成

这个视角回答：

> 这套工作系统到底在服务谁？

### 3.2 第二种视角：Demand-Capability 视角

看的是：

- 进入系统的需求量和需求类型
- 当前系统能交付多少、交付多快、是否稳定
- 两者是否平衡

这个视角回答：

> 为什么系统会拥堵、延迟或失控？

### 3.3 第三种视角：Workflow 视角

看的是：

- 工作项经过哪些活动
- 哪些活动顺序发生
- 哪些活动可并行
- 哪些地方是缓冲区、等待区、阻塞点

这个视角回答：

> 工作在真实世界里到底是怎么走的？

### 3.4 第四种视角：Policy-Constraint 视角

看的是：

- 什么规则支配工作进入与前移
- WIP 如何被约束
- 哪些条件构成拉动信号
- 服务类别如何差异化处理

这个视角回答：

> 工作为什么这样流，而不是那样流？

### 3.5 第五种视角：Feedback-Control 视角

看的是：

- 用什么数据理解系统行为
- 用什么节奏检视与协调
- 用什么会议机制做补货、风险评审、服务评审

这个视角回答：

> 系统如何感知自己，如何校正自己？

### 3.6 第六种视角：Evolutionary Change 视角

看的是：

- 不满从哪里来
- 改进假设是什么
- 实验怎样设计
- 结果怎样决定保留或回退

这个视角回答：

> 系统如何在不推翻现状的前提下持续进化？

---

## 第四阶段：六种视角之间的关系

### 4.1 先用一张总图看六种视角

```text
现实中的服务交付系统

├─ 视角 A：Service
│      看“谁为谁交付什么结果”
│
├─ 视角 B：Demand-Capability
│      看“请求量与交付能力是否平衡”
│
├─ 视角 C：Workflow
│      看“工作如何穿越活动序列”
│
├─ 视角 D：Policy-Constraint
│      看“规则与限制如何塑造流动”
│
├─ 视角 E：Feedback-Control
│      看“系统如何观察和校正自己”
│
└─ 视角 F：Evolutionary Change
       看“系统如何被实验式重构”
```

### 4.2 它们不是替代关系，而是观察焦点不同

| 视角 | 核心关注点 | 强调什么 | 弱化什么 |
|------|------------|----------|----------|
| `Service` | 服务与客户关系 | 请求、接受、交付边界 | 细节活动 |
| `Demand-Capability` | 请求与能力平衡 | 负载、速率、预测性 | 个别工作项细节 |
| `Workflow` | 工作通过路径 | 活动、顺序、状态转换 | 更高层服务网络 |
| `Policy-Constraint` | 行为约束 | WIP、拉动、规则、服务类别 | 业务价值语境 |
| `Feedback-Control` | 系统自我感知 | 度量、会议、评审、反馈环 | 单个步骤细节 |
| `Evolutionary Change` | 系统进化 | 假设、实验、演进 | 静态运行时状态 |

### 4.3 六种视角之间的层次感

可以把它们看成一条从“为什么存在”到“如何改变”的连续线：

```text
Service
  ↓
Demand-Capability
  ↓
Workflow
  ↓
Policy-Constraint
  ↓
Feedback-Control
  ↓
Evolutionary Change
```

这条线不是严格继承关系，而是说明：

- 越靠前，越贴近服务语境
- 越靠中间，越贴近运行机制
- 越靠后，越贴近反馈与改造

## 第五阶段：Kanban System——为什么它是 Kanban 的最小系统单位

### 5.1 为什么不是 Board，而是 System

如果把 `Board` 误当作最小单位，就会把 `Kanban` 理解成“任务展示工具”。

但官方定义非常明确：`Kanban System` 包含：

- 板
- 卡片
- 规则
- 度量
- 节奏

这意味着：

- 没有规则的板，不是完整系统
- 没有度量的板，不具备反馈能力
- 没有节奏的板，不具备协调能力
- 没有承诺边界的板，很难形成可解释的流动数据

### 5.2 Kanban System 的最小组成

可以先把 `Kanban System` 记成下面这个结构：

```text
Kanban System
  = Workflow Model
  + Visual Board
  + Work Item Representation
  + Policies
  + WIP Constraints
  + Metrics
  + Cadences
```

### 5.3 一个系统至少要有边界

官方 Guide 明确提到：

- 至少应有清晰的 `Commitment Point`
- 至少应有清晰的 `Delivery Point`

这两个点很重要，因为没有边界：

- `Lead Time` 很难定义
- 工作何时真正被系统接受会模糊
- 工作何时真正离开系统会模糊

### 5.4 一个系统总是情境化的

`Kanban` 反复强调：

- 每个系统是独特的
- 每块板也是独特的
- 设计必须从真实现状出发

所以不要用“万能板模板”去理解 `Kanban`。

---

## 第六阶段：Board——为什么它只是系统投影，不是系统本身

### 6.1 Board 的本体作用

`Kanban Board` 的核心作用不是“美观地展示任务”，而是：

- 把工作项显出来
- 把活动顺序显出来
- 把容量边界显出来
- 把规则与风险显出来
- 让参与者共享同一张操作图

### 6.2 Column——活动与缓冲区的可视化

板上的列通常代表：

- 一个活动
- 一组活动
- 一个缓冲区
- 一个状态边界

列不是越标准化越好，而是越真实映射实际工作越好。

### 6.3 Lane——类型、服务类别与容量分配

泳道常用来区分：

- 不同工作类型
- 不同项目或客户群
- 不同服务类别
- 容量分配策略

这说明板不是二维固定模板，而是一种可定制的信息投影。

### 6.4 Card——工作对象在板上的影子

卡片至少承担几类信息功能：

- 代表某个工作项
- 显示当前所处位置
- 可能携带类型、风险、类别、阻塞等附加信息

### 6.5 为什么“待办 / 进行中 / 已完成”通常不够

官方 Guide 明确提醒：板面通常不只是 `To Do / Doing / Done`。

因为如果过于粗糙：

- 真实瓶颈会被隐藏
- 缓冲区与等待区会被隐藏
- 并行与分流结构会被隐藏
- 规则的真正作用点会被隐藏

---

## 第七阶段：Flow——为什么 Kanban 把“流动”置于中心

### 7.1 为什么不是以资源利用率为中心

官方用高速公路隐喻说明了一个核心洞察：

- 道路满载不代表流动好
- 资源利用率满格，往往意味着拥堵
- 对知识工作而言，上下文切换会进一步恶化效果

所以 `Kanban` 关注的是：

- 工作是否顺畅
- 工作是否可预测
- 工作是否持续前进

而不是“每个人是否一直忙”。

### 7.2 Flow 的真正目标

管理流动的目标不是盲目加速，而是：

- 尽可能平滑
- 尽可能可预测
- 尽可能在可持续节奏下交付

这是一个系统优化问题，而不是个人努力程度问题。

### 7.3 Delay / Blocker / Bottleneck 为什么都与 Flow 有关

只要工作不在向价值交付方向稳定前进，流动就受损。

- `Delay` 让时间拉长
- `Blocker` 让个体停滞
- `Bottleneck` 让系统吞吐受限

因此 `Kanban` 把它们都视为流动问题的不同表现。

---

## 第八阶段：WIP / Pull——Kanban 最核心的运行约束

### 8.1 为什么 WIP Limit 是关键对象

官方明确指出：限制进入系统的工作，是减少延迟、切换和浪费的关键。

如果不限制：

- 新工作会不断被推进系统
- 下游即使没有容量也继续承压
- 结果是吞吐下降、预测性下降、质量下降

### 8.2 WIP Limit 为什么不是“反自由”

官方把它视为 `enabling constraint`，也就是“赋能型约束”。

它的作用是：

- 给团队聚焦
- 促进协作
- 强化完成而不是开启
- 使拉动系统成为可能

### 8.3 Pull Signal 是怎样产生的

`Pull Signal` 的本质是：

- 当前某个部分的 `WIP` 低于上限
- 下游有可用容量
- 因而上游工作才有资格进入或前移

也就是说，**容量是信号，不是管理者主观意志。**

### 8.4 Pull System 与 Push System 的差异

| 维度 | `Push` | `Pull` |
|------|--------|--------|
| 启动依据 | 计划或指令 | 需求 + 可用容量 |
| 下游是否可接收 | 可被忽略 | 必须考虑 |
| 典型后果 | 过载、排队、切换 | 更平稳、更受控 |
| 对已完成工作的态度 | 容易继续开新活 | 更重视完成 |

### 8.5 “Stop starting, start finishing” 为什么重要

这是 `Kanban` 最值得记住的文化短句之一。

它不是情绪口号，而是对系统行为的重新排序：

- 完成比开始更有价值
- 释放容量比堆积进展更有价值
- 减少半成品比制造忙碌感更有价值

---

## 第九阶段：Policy——为什么规则是流动系统的一部分

### 9.1 Kanban 里的规则是什么

规则是关于服务交付如何运作的显式协议。

常见规则包括：

- 补货标准
- 拉动标准
- 完成标准
- 服务类别处理方式
- WIP 限额
- 节奏与会议内容
- 协作协议

### 9.2 为什么规则必须显式化

因为如果规则隐含在每个人脑子里：

- 新成员很难进入系统
- 同一板面背后其实是多套规则
- 决策标准会不断漂移
- 争议会无法定位

### 9.3 显式规则的品质要求

官方给出的要求很清楚：

- 稀疏
- 简单
- 定义良好
- 可见
- 一贯适用
- 由服务提供者可随时调整

### 9.4 规则不是机械操作说明书

官方特别提醒：规则不是为了让人停止思考。

相反，它们应当支持：

- 自组织
- 协作判断
- 共同决策
- 持续调整

---

## 第十阶段：度量系统——如何把流动变成可观察对象

### 10.1 Lead Time——单项工作的时间画像

这是最核心的时间指标。

它回答：

- 一项工作进入系统后，多久离开
- 这种时间是否稳定
- 未来是否可预测

### 10.2 Throughput / Delivery Rate——系统输出速率

它回答：

- 系统一周能稳定交付多少项
- 一个月能离开多少项
- 变化趋势是上升、下降还是波动

### 10.3 WIP——系统当前负载

它回答：

- 现在系统里堆着多少工作
- 哪个部分积压最多
- 当前负载是否与能力匹配

### 10.4 常见图表：Run Chart / Lead Time Distribution / CFD

官方 Guide 提到三类最典型图表：

- `Run Chart`：看时间序列趋势
- `Lead Time Distribution`：看前置时间分布
- `CFD`：看不同活动之间的在制品流动结构

这三者合起来，分别回答：

- 趋势如何变化
- 波动范围多大
- 流动在哪些活动上堆积

### 10.5 Service Level Expectation (SLE)

Glossary 里提到 `SLE` 是基于历史表现形成的未来交付预期。

它的关键不在绝对承诺，而在概率表达：

- 例如过去稳定系统中，`85%` 的工作项在 `10` 天内完成
- 那就可以形成 `10` 天、`85%` 置信度的期望

这比拍脑袋给出截止日期更符合知识工作不确定性的本质。

### 10.6 Metrics 不是先天地等于 KPI

如果把度量直接当成绩效工具，常见后果是：

- 大家为数字而不是为流动优化
- 系统被游戏化
- 局部最优替代整体最优

官方也提醒：`you get what you measure`。

所以度量设计必须服务于：

- 流动理解
- 风险识别
- 反馈决策
- 系统改进

## 第十一阶段：Cadence——Kanban 如何把反馈制度化

### 11.1 Cadence 为什么不是普通会议清单

`Cadence` 是周期性的反馈机制，不只是会议日历上的一个格子。

它的重要性在于：

- 让系统定期被观察
- 让决策不依赖临时救火
- 让改进进入制度化节奏

### 11.2 Team Kanban Meeting

官方示例中，它通常是每日进行。

它关注的是：

- 工作状态与流动
- 哪些工作项卡住了
- 哪些工作可以继续前移
- 哪些容量已经释放

一个典型方法是 `walk the board`，常见问题不是“你昨天做了什么”，而是：

- 什么阻碍了这个工作项流动？
- 谁可以帮助它继续向前？

### 11.3 Replenishment Meeting

它的核心作用是：

- 审查准备进入系统的工作
- 在有容量的前提下拉入新的工作项

也就是说，它是 `Option -> Committed Work` 的关键控制点之一。

### 11.4 Retrospective / Review

官方 Guide 给出了团队回顾的例子，而 Glossary 又补充了 `Review` 类型，例如：

- `Service Delivery Review`
- `Risk Review`
- `Operations Review`

这些机制共同说明：`Kanban` 的反馈不仅面向团队协作，还可以面向：

- 服务绩效
- 风险模式
- 运营协调
- 跨服务网络改进

### 11.5 Cadence 可以继承已有会议

官方特别说明：

- 不必重造所有会议
- 可以识别已有会议里已经承担类似作用的那些
- 保留原名称也可以，重点是目的而不是标准命名

这再次体现了 `Kanban` 的“从现有做法开始”。

## 第十二阶段：类型与服务类别——工作为什么不能一视同仁

### 12.1 Work Item Type——结构差异

工作项类型描述的是工作本身的行为模式差异。

例如：

- 事故处理
- 缺陷修复
- 功能开发
- 需求澄清
- 信息请求

它更多回答：

> 这类工作通常怎样流过系统？

### 12.2 Class of Service——策略差异

服务类别描述的是工作该如何被对待。

它更多回答：

> 在这个系统里，这类工作应该按什么优先与规则被处理？

### 12.3 四种常见服务类别原型

#### `Standard`

符合通常条件的普通工作。

#### `Expedite`

延迟影响高且立即发生的工作。

#### `Fixed Date`

延迟影响会在特定日期集中显现的工作。

#### `Intangible`

延迟影响尚不明确，但不等于没有价值的工作。

### 12.4 Cost of Delay 为什么重要

`Class of Service` 经常与 `Cost of Delay` 相关。

因为服务类别本质上是在表达：

- 这项工作拖延的代价有多大
- 这种代价何时显现
- 是否值得打破常规流动顺序

## 第十三阶段：承诺与边界——从 Option 到 Delivery 的对象链条

### 13.1 Option——为什么官方不鼓励把一切都叫 Backlog

Glossary 里明确提到，在承诺点之前，更推荐把那些“可能有价值”的东西叫 `Options`。

这有两个含义：

- 它们尚未被承诺交付
- 它们需要与可用能力、紧迫度一起被筛选

### 13.2 Commitment Point——进入交付系统的边界

这是系统真正接收工作的时刻。

在这个点之前：

- 工作还在被考虑
- 还可能被放弃
- 还不应该算进系统交付时间

在这个点之后：

- 工作正式进入服务交付系统
- 相关度量开始具有清晰边界

### 13.3 Delivery Point——工作离开系统的边界

从系统角度看，这是：

- 工作不再处于系统内部
- 价值已被交付出去
- 相关前置时间结束

### 13.4 System Lead Time vs Customer Lead Time

- `System Lead Time`：更聚焦系统内部从承诺到流经的时间
- `Customer Lead Time`：从客户发出请求到最终交付的整体时间

两者都重要，但观察边界不同。

### 13.5 Upstream / Downstream

`Kanban` 天然有边界意识：

- 上游在过滤和塑形需求
- 系统内部在交付工作
- 下游在接受和消费成果

如果只盯着板中间几列，就会失去 `Kanban` 的服务视角。

## 第十四阶段：STATIK——Kanban 如何设计，而不是只会贴卡片

### 14.1 为什么需要 STATIK

一个常见问题是：

> 如果每块板都不同，那我怎么设计自己的系统？

`STATIK` 就是官方给出的回答。

它不是模板，而是一种**系统思考地引入 Kanban** 的设计方法。

### 14.2 STATIK 的六个步骤

1. 识别不满来源
2. 分析需求
3. 分析能力
4. 建模工作流
5. 识别服务类别
6. 设计 Kanban 系统

### 14.3 为什么第一步是“不满”而不是“先画板”

因为 `Kanban` 的改进不是为了形式统一，而是为了回应真实痛点。

没有足够清晰的不满来源：

- 变革动机不足
- 改进目标漂移
- 系统设计会沦为形式主义

### 14.4 为什么不是一次性顺序流程

官方明确说明，`STATIK` 是迭代式的：

- 后面的步骤可能暴露新信息
- 可能需要回到前面的步骤重看
- 它更像设计反馈环，而不是一次性流程清单

### 14.5 为什么必须让代表性人群参与

官方强调，`STATIK` 不应由某个 PM、Team Lead、教练或顾问独自完成。

因为：

- 每个人脑中对真实工作流的图景通常不同
- 设计过程的价值之一就是把这些图景对齐成共享视角

---

## 第十五阶段：演进式改进——Kanban 为什么强调实验而不是大改造

### 15.1 变革管理三原则的真正含义

#### 从现有做法开始

不是保守不变，而是承认：

- 组织已经有真实工作方式
- 变革必须从真实起点出发
- 否则很容易造成抵抗与失真

#### 认同通过渐进变化追求改善

不是拒绝变化，而是反对不经验证的大爆炸重构。

#### 激发各级领导力

不是只有管理层才能改进系统。

在 `Kanban` 里，领导力也可以体现为：

- 发现阻塞
- 提出假设
- 发起小实验
- 推动局部规则改进

### 15.2 科学方法为什么进入 Kanban

Glossary 把科学方法的步骤写得很清楚：

- 观察
- 假设
- 实验
- 收集数据
- 分析结果
- 接受或拒绝假设
- 重复

这说明 `Kanban` 的改进逻辑不是凭感觉，而是：

> 用受控反馈环改造服务交付系统。

### 15.3 Safe-to-fail 为什么重要

官方 Guide 也强调：

- 改动应该尽量是可回退的
- 结果好就保留
- 结果不好就退回原状态

这使 `Kanban` 非常适合复杂环境中的渐进改进。

## 第十六阶段：关系——Kanban 与 Scrum / BPMN / DevOps 的边界

### 16.1 Kanban vs Scrum

- `Scrum` 更强调固定节奏、责任主体、工件与经验闭环
- `Kanban` 更强调服务交付、流动管理、显式约束与实验性演进

两者都重视反馈，但组织方式不同。

### 16.2 Kanban with Scrum

官方生态里本来就存在 `Scrum Better with Kanban` 这样的组合路径。

常见组合方式是：

- 用 `Scrum` 提供 Sprint 节奏与责任结构
- 用 `Kanban` 提供流动可视化、WIP 控制与补货逻辑

### 16.3 Kanban vs BPMN 2.0

- `BPMN 2.0` 更偏流程表达标准
- `Kanban` 更偏工作系统管理方法

一个更关心“怎么表达流程”，另一个更关心“流程中的工作如何流动、被控制、被改进”。

### 16.4 Kanban vs DevOps

- `DevOps` 更强调开发与运维协作、自动化与交付链能力
- `Kanban` 更强调流动管理与服务交付治理

两者可以深度组合：

- `DevOps` 提供工程自动化能力
- `Kanban` 提供流动与反馈的管理框架

## 第十八阶段：Kanban 在工程中的典型使用方式

### 18.1 团队级：先让工作可见，再让流动受控

这是最常见起点。

典型关注点：

- 当前工作到底有哪些
- 哪些工作在卡住
- WIP 是否过多
- Daily 协调怎样从“人汇报”转向“看工作流”

### 18.2 服务级：从团队视角升级到交付视角

当一个服务由一个团队长期承载时，重点会转向：

- 请求类型结构
- 服务类别
- SLE
- Replenishment 与 Delivery Review
- 客户期望管理

### 18.3 多团队级：看服务网络而不是单板优化

当多个团队共同交付一个服务时，重点会转向：

- 上下游依赖
- 跨板流动
- 瓶颈迁移
- 风险评审与运营评审
- 需求与能力在多个系统间的平衡

### 18.4 组织级：把 Kanban 作为组织发展工具

官方材料特别强调，这也是 `Kanban` 收益最大的层面。

关注点会变成：

- 服务网络的治理
- 策略与交付能力之间的连接
- 组织层反馈机制
- 渐进式变革而非组织震荡

## 第十九阶段：常见失真模式——看起来像 Kanban，实际上不是

### 19.1 只有板，没有系统

现象：有板、有卡片，但没有规则、没有度量、没有节奏。

结果：只是任务可视化，不是完整 `Kanban System`。

### 19.2 只有 WIP 数字，没有 Pull 逻辑

现象：列头上写了限制数字，但并不真的阻止新工作进入。

结果：限额成为装饰，系统仍是 `Push` 模式。

### 19.3 只有日报，没有反馈环

现象：每天站在板前同步，但不使用数据、不基于问题采取行动。

结果：会议存在，但反馈闭环不存在。

### 19.4 只优化局部忙碌度，不优化整体流动

现象：哪个人空了就临时塞活。

结果：局部忙碌上升，系统前置时间与预测性反而下降。

### 19.5 把 Expedite 当常态

现象：大量工作被标成加急。

结果：服务类别失去意义，系统退回到长期救火状态。

### 19.6 先画理想流程，再要求现实硬套

现象：板反映的是希望中的流程，而不是现实中的流动。

结果：板越好看，数据越失真，改进越没有抓手。

## 第二十阶段：学习顺序与记忆框架

### 20.1 先记住一条主线

把 `Kanban Method` 压缩成一条主线：

> `Customer Request -> Demand -> Option -> Commitment -> Work Item Flow -> Delivery -> Feedback -> Experiment -> Evolution`

### 20.2 再记住“四横两纵”

#### 第一横：它服务什么

- `Customer`
- `Demand`
- `Service`

#### 第二横：它运行什么

- `Work Item`
- `Workflow`
- `Flow`

#### 第三横：它靠什么控制

- `Policy`
- `WIP Limit`
- `Pull`
- `Class of Service`

#### 第四横：它靠什么学习

- `Metrics`
- `Cadences`
- `Feedback Loops`
- `Experiment`

#### 第一纵：从请求到交付

`Option -> Commitment -> Flow -> Delivery`

#### 第二纵：从观察到演化

`Measure -> Review -> Hypothesis -> Experiment -> Evolve`

### 20.3 第一遍学习 Kanban 时，应该先建立什么直觉

1. `Kanban` 不是板，而是系统。
2. `Kanban` 不是替换现有流程，而是叠加在其上的管理方法。
3. `Kanban` 的中心不是人忙不忙，而是工作流得顺不顺、稳不稳。
4. `WIP Limit` 的意义在于建立 `Pull`。
5. `Metrics` 与 `Cadence` 一起构成行动型反馈环。
6. `STATIK` 和实验式演化说明 `Kanban` 同时关心“如何设计系统”和“如何改变系统”。

### 20.4 下一步继续学习 Kanban 时的建议顺序

#### 路线 A：先学对象主干

适合希望快速建立结构感的人：

1. `Service / Demand / Work Item / Workflow`
2. `Kanban System / Board / Policy / WIP`
3. `Metrics / Cadence / Feedback`
4. `STATIK / Experiment / Evolutionary Change`

#### 路线 B：先学运行逻辑

适合希望先抓住“为什么这样做”的人：

1. `Flow vs Utilization`
2. `WIP / Pull / Policy`
3. `Lead Time / Throughput / CFD`
4. `Cadence / Review / Experiment`

## 小结

如果把 `Kanban Method` 再压缩一次，可以记成下面这句话：

> `Kanban` 是一种围绕服务交付来组织知识型工作的管理方法。它通过把工作流可视化、限制在制品、用容量驱动拉动、用规则塑造协作、用度量与节奏构造反馈、再用实验式改进推动系统演进，让需求与能力逐步达到平衡。

再换一种更对象化的说法：

- 它不是先定义一套统一流程，再让所有人去遵守
- 它是先承认现实中已经存在某套工作系统
- 再把这套系统的 `服务`、`需求`、`工作项`、`流动`、`规则`、`约束`、`反馈` 和 `演进` 显化出来
- 最终把“工作如何被做”“为什么会卡住”“系统该如何变好”变成可观察、可讨论、可实验的问题

所以，真正学懂 `Kanban` 的标志，不是你会不会画一个看板，而是你是否已经开始把一个团队或一条服务线看成：

- 一个有边界的服务系统
- 一个需要平衡需求与能力的流动系统
- 一个可以通过反馈与实验持续进化的社会技术系统

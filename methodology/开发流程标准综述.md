# 软件开发流程标准 — 全景定义与对比分析

> 软件开发流程标准解决的核心问题是：**一群人如何有序地协作完成一个软件产品**。
> 不同的标准侧重不同层面——有的定义"流程长什么样"，有的评估"流程好不好"，有的规定"团队日常怎么跑"。
> 本文逐一说明每种标准如何定义，再系统分析它们之间的相同点与不同点。

---

## 一、标准分类总览

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      软件开发流程标准 — 四层模型                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  第一层：流程表达标准     —— 流程怎么画、怎么描述                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  BPMN 2.0 · UML Activity Diagram · SPEM 2.0 · DMN 1.4              │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  第二层：生命周期过程标准 —— 研发过程有哪些环节、每个环节做什么               │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  ISO/IEC/IEEE 12207 · ISO/IEC/IEEE 15288 · ISO/IEC 29110           │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  第三层：过程能力评估标准 —— 流程做到什么程度、成熟度如何                     │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  CMMI-DEV · ISO/IEC 15504 (SPICE) · ISO/IEC 330xx                  │   │
│  │  Automotive SPICE · ISO 9001                                        │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  第四层：执行方法与框架     —— 团队日常具体怎么干活                           │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  Scrum · Kanban · XP · SAFe · DevOps · ITIL · COBIT                │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  关系：上层定义"流程的结构与表达"，下层定义"流程的落地与执行"                   │
│        四层可以组合使用，不互斥                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 二、每种标准的定义

### 2.1 BPMN 2.0 — Business Process Model and Notation

**发布组织**：OMG（Object Management Group）
**最新版本**：BPMN 2.0.2（2014 年发布）
**标准性质**：正式国际规范（OMG Specification）

**定义方式**：

BPMN 2.0 是一种**业务流程建模与表示标准**，它定义了一套图形化的符号体系（Notation）和对应的元模型（Metamodel），用于：

- 用标准化的图形符号描述业务流程（流程图风格）
- 将流程图精确映射为可执行的软件过程组件（XML 序列化格式）
- 桥接业务人员（设计、管理流程的人）和技术人员（实现流程的人）之间的沟通

**核心定义要素**：

```
┌──────────────────────────────────────────────────┐
│  BPMN 2.0 的四大图形类别                           │
├──────────────────────────────────────────────────┤
│                                                  │
│  ① Flow Objects（流对象）                         │
│     · Events      — 开始、中间、结束事件          │
│     · Activities  — 任务、子流程                  │
│     · Gateways    — 排他、并行、包含网关          │
│                                                  │
│  ② Connecting Objects（连接对象）                  │
│     · Sequence Flow — 顺序流                     │
│     · Message Flow — 消息流（跨池）               │
│     · Association  — 关联                        │
│                                                  │
│  ③ Swimlanes（泳道）                              │
│     · Pool   — 参与者/组织                       │
│     · Lane   — 角色/部门                         │
│                                                  │
│  ④ Artifacts（制品）                              │
│     · Data Object  — 数据对象                    │
│     · Group        — 分组                        │
│     · Text Annotation — 文本注释                 │
│                                                  │
└──────────────────────────────────────────────────┘
```

**关键特征**：
- BPMN 不定义"流程应该包含哪些步骤"，只定义"怎么把流程画清楚"
- 它是**表达标准**，不是**过程标准**
- 支持从手动流程描述到自动化流程执行的全谱覆盖

### 2.2 SPEM 2.0 — Software & Systems Process Engineering Metamodel

**发布组织**：OMG（Object Management Group）
**发布时间**：2008 年 4 月
**标准性质**：正式国际规范（OMG Specification）

**定义方式**：

SPEM 2.0 是一种**软件与系统过程工程元模型**，它定义了描述软件开发方法（Method）和过程（Process）的元数据结构。它不规定"应该用什么开发方法"，而是提供一种标准化的方式来**定义、组装和裁剪**任何开发方法。

**核心定义要素**：

```
┌──────────────────────────────────────────────────────────────────┐
│  SPEM 2.0 的两大核心包                                           │
├──────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ① Method Content（方法内容）— "做什么"的知识库                    │
│     · Role       — 谁来做（角色定义）                             │
│     · Work Product — 做出什么（制品定义）                         │
│     · Task       — 怎么做（任务定义）                             │
│     · Guidance   — 辅助指引（模板、检查单、示例）                 │
│                                                                  │
│  ② Process（过程）— "什么时候、按什么顺序"做                      │
│     · Activity        — 活动（包含一组 Task 的执行）              │
│     · Phase           — 阶段                                     │
│     · Iteration       — 迭代                                     │
│     · Breakdown Element — 分解结构                                │
│                                                                  │
│  两者关系：Method Content 是食材，Process 是菜谱                  │
│           同样的食材可以组成不同的菜谱                             │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- SPEM 本身不包含任何预定义的开发方法，它只提供描述方法的元模型
- 可以用 SPEM 来描述 RUP、Scrum、瀑布模型等任何方法
- 适合用于**过程资产管理**和**方法工程**

### 2.3 ISO/IEC/IEEE 12207 — Systems and Software Engineering — Software Life Cycle Processes

**发布组织**：ISO / IEC / IEEE 联合发布
**最新版本**：2017 年版（含 2023 年修订）
**标准性质**：国际正式标准（International Standard）

**定义方式**：

ISO/IEC/IEEE 12207 是软件工程领域最核心的**生命周期过程标准**。它定义了软件从构思到退役全过程中应当包含的所有过程（Process）、每项过程的活动（Activity）和任务（Task）。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  ISO/IEC/IEEE 12207 的过程体系（三大类，共 30+ 过程）                │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ① 协议过程（Agreement Processes）                                   │
│     · 获取过程         · 供应过程                                    │
│                                                                     │
│  ② 组织级项目使能过程（Organizational Project-Enabling Processes）   │
│     · 生命周期模型管理  · 基础设施管理  · 项目组合管理               │
│     · 人力资源管理      · 质量管理                                  │
│                                                                     │
│  ③ 技术过程（Technical Processes）                                   │
│     · 利益相关方需求定义  · 系统需求分析  · 架构设计                 │
│     · 实现设计            · 实现        · 集成                      │
│     · 验证                · 确认        · 运行                      │
│     · 维护                · 处置                                    │
│                                                                     │
│  ④ 技术管理过程（Technical Management Processes）                    │
│     · 项目计划  · 项目评估与控制  · 项目测量                        │
│     · 风险管理  · 配置管理        · 决策管理                        │
│     · 需求管理  · 接口管理                                        │
│                                                                     │
│  整体逻辑：协议层 → 组织使能层 → 技术层 → 管理层                    │
│  每个过程 = 目的(Purpose) + 活动(Activities) + 任务(Tasks)          │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 12207 是**框架性标准**，定义"应该有哪些过程"，不规定"怎么执行"这些过程
- 组织需要根据自身情况做**裁剪（Tailoring）**
- 与 15288（系统生命周期过程）对齐，12207 是其在软件领域的专门化

---

### 2.4 ISO/IEC/IEEE 15288 — Systems and Software Engineering — System Life Cycle Processes

**发布组织**：ISO / IEC / IEEE 联合发布
**最新版本**：2023 年版
**标准性质**：国际正式标准（International Standard）

**定义方式**：

ISO/IEC/IEEE 15288 是**系统生命周期过程标准**，定义了涵盖软件、硬件、人员、设施等所有系统要素的全生命周期过程。它比 12207 的范围更广，适用于任何复杂系统的工程过程。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  ISO/IEC/IEEE 15288 的过程体系                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  与 12207 共享相同的四层过程框架：                                    │
│    协议过程 → 组织使能过程 → 技术过程 → 技术管理过程                │
│                                                                     │
│  但 15288 的技术过程覆盖范围更大：                                    │
│    · 业务/使命分析  · 利益相关方需求定义                             │
│    · 系统需求分析   · 架构设计（含硬件、软件、人员分配）             │
│    · 实现设计       · 实现（含硬件制造、软件编码、人员培训）         │
│    · 集成           · 验证  · 确认  · 运行  · 维护  · 处置         │
│                                                                     │
│  12207 是 15288 在纯软件领域的子集和专门化                           │
│  15288 更适合软硬件一体、嵌入式系统、系统工程场景                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 15288 的技术过程中，"实现"不仅包括编码，还包括硬件制造、人员培训
- 适合汽车电子、航空航天、国防等复杂系统工程

---

### 2.5 ISO/IEC 29110 — Systems and Software Engineering — Lifecycle Profiles for Very Small Entities

**发布组织**：ISO / IEC
**标准性质**：国际正式标准（International Standard）

**定义方式**：

ISO/IEC 29110 是专门面向**极小型组织（VSE, Very Small Entities，通常指 ≤ 25 人）**的软件工程生命周期标准。它从 12207 和 15288 中提取核心过程，简化为小型团队可以实际执行的流程框架。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  ISO/IEC 29110 的 Profile 结构                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  每个 Profile = 过程 + 制品 + 角色 + 任务 的最小可用集合             │
│                                                                     │
│  基本Profile（Entry）：                                              │
│    · 项目管理过程（PM）— 计划、执行、结项                           │
│    · 软件实现过程（SI）— 需求、设计、编码、测试                     │
│    · 共 4 个角色、10 个制品、约 30 个任务                           │
│                                                                     │
│  进阶Profile：                                                       │
│    · 在基本Profile 基础上逐步增加配置管理、质量保证等过程             │
│    · 可渐进式升级，直到与 12207 完整体系对齐                        │
│                                                                     │
│  核心理念：                                                          │
│    "标准不是大企业的专利，小团队也需要结构化的流程"                  │
│    "够用即可，渐进增强"                                              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 明确承认小团队资源有限，流程必须轻量
- 提供了从简到繁的渐进升级路径

### 2.6 CMMI-DEV — Capability Maturity Model Integration for Development

**发布组织**：ISACA（原 CMMI Institute，隶属 ISACA）
**最新版本**：CMMI V3.0（2023 年发布）
**标准性质**：行业框架（Industry Framework），非 ISO 标准，但被广泛采信

**定义方式**：

CMMI-DEV 是一种**过程能力成熟度模型**，它定义了一组最佳实践区域（Practice Areas），并提供了评估组织过程能力等级（Capability Level）和成熟度等级（Maturity Level）的方法。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  CMMI V2.0/V3.0 的核心结构                                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  四大能力域（Capability Areas）：                                    │
│                                                                     │
│  ① 行动（Doing）                                                    │
│     · 需求开发与管理  · 技术方案  · 产品集成                        │
│     · 验证与确认      · 同行评审                                    │
│                                                                     │
│  ② 管理（Managing）                                                 │
│     · 项目计划  · 项目监控  · 估算  · 风险与机会管理                │
│     · 供应商协议管理                                                 │
│                                                                     │
│  ③ 使能（Enabling）                                                 │
│     · 配置管理  · 过程与制品质量保证  · 原因分析与解决              │
│     · 决策分析  · 组织级培训                                        │
│                                                                     │
│  ④ 改进（Improving）                                                │
│     · 组织级过程焦点  · 组织级过程定义  · 组织级绩效管理            │
│                                                                     │
│  成熟度等级：                                                        │
│    ML1 — 初始级（无序）                                             │
│    ML2 — 已管理级（项目级可控）                                     │
│    ML3 — 已定义级（组织级标准化）                                   │
│    ML4 — 量化管理级（统计过程控制）                                 │
│    ML5 — 优化级（持续改进）                                         │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- CMMI 不定义具体流程步骤，而是定义"流程应该具备哪些能力"
- 通过正式评估（Appraisal）判定组织的成熟度等级
- ML3 是大多数组织的核心目标（组织级过程标准化）

### 2.7 ISO/IEC 15504 (SPICE) — Process Assessment

**发布组织**：ISO / IEC
**标准性质**：国际正式标准（已被 ISO/IEC 330xx 系列逐步替代）

**定义方式**：

ISO/IEC 15504（又称 SPICE，Software Process Improvement and Capability dEtermination）定义了一种**标准化的软件过程评估框架**。它规定了对软件开发过程进行评估的模型、方法和指标。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  ISO/IEC 15504 的评估框架                                           │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  过程参考模型（Process Reference Model）：                           │
│    · 定义要评估的过程及其目的、产出                                  │
│    · 基于 ISO/IEC 12207 的过程分类                                  │
│                                                                     │
│  过程评估模型（Process Assessment Model）：                          │
│    · 为每个过程定义评估指标（Process Attributes）                    │
│    · 6 个能力等级（Capability Levels）：                             │
│      Level 0 — 不完整                                              │
│      Level 1 — 已执行过程                                           │
│      Level 2 — 已管理过程                                           │
│      Level 3 — 已建立过程                                           │
│      Level 4 — 可预测过程                                           │
│      Level 5 — 优化过程                                             │
│                                                                     │
│  评估方法：                                                          │
│    · 证据收集 → 评分 → 能力画像                                     │
│    · 每个过程属性评分 0-4 分（N/P/L/F）                              │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- SPICE 是"评估框架"而非"过程框架"，它评价已有流程做得怎样
- 与 CMMI 相似但更细化（过程级评估 vs 组织级评估）
- Automotive SPICE 是其在汽车行业的专门化应用

---

### 2.8 ISO/IEC 330xx — Information Technology — Process Assessment

**发布组织**：ISO / IEC
**标准性质**：国际正式标准（15504 的替代系列）

**定义方式**：

ISO/IEC 330xx 是新一代的过程评估标准体系，继承了 15504（SPICE）的核心思想，但扩展了适用范围（不再限于软件），并优化了评估模型结构。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  ISO/IEC 330xx 系列结构                                             │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ISO/IEC 33001 — 概念与术语                                        │
│  ISO/IEC 33002 — 过程评估模型要求                                   │
│  ISO/IEC 33003 — 过程参考模型要求                                   │
│  ISO/IEC 33004 — 过程评估模型与参考模型使用指南                     │
│  ISO/IEC 33014 — 过程改进指南                                      │
│  ISO/IEC 33020 — 过程能力等级与属性                                │
│  ISO/IEC 33030 — 过程评估方法与工具                                │
│                                                                     │
│  关键变化（相对 15504）：                                            │
│    · 能力等级从 6 级改为更清晰的分级结构                             │
│    · 评估模型与被评估过程解耦（可评估任何领域的过程）                │
│    · 增加了过程改进的指导                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 是 SPICE 的演进版本，理论上适用于任何领域的过程评估
- 实际中汽车行业仍大量使用 Automotive SPICE（基于 15504）

### 2.9 Automotive SPICE

**发布组织**：VDA（德国汽车工业协会）牵头，欧洲汽车行业联合制定
**标准性质**：行业特定评估标准（基于 ISO/IEC 15504）

**定义方式**：

Automotive SPICE（ASPICE）是将 SPICE 评估框架专门化到汽车电子软件领域的版本。它定义了汽车软件开发中必须评估的过程及其能力等级，作为供应商准入和能力评价的标准。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  Automotive SPICE 的过程分类                                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  系统工程过程组（SYS）：                                             │
│    SYS.1 需求提取  SYS.2 系统需求分析  SYS.3 系统架构设计           │
│    SYS.4 系统集成与集成测试  SYS.5 系统合格测试                     │
│                                                                     │
│  软件工程过程组（SWE）：                                             │
│    SWE.1 软件需求分析  SWE.2 软件架构设计  SWE.3 软件详细设计       │
│    SWE.4 软件单元验证  SWE.5 软件集成与集成测试  SWE.6 软件合格测试 │
│                                                                     │
│  支持/管理过程组：                                                   │
│    · 项目管理  · 变更管理  · 配置管理  · 问题解决                   │
│    · 过程改进  · 风险管理                                           │
│                                                                     │
│  评估能力等级：Level 0~5（同 SPICE）                                │
│  OEM 通常要求供应商关键过程达到 Level 2 或 Level 3                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- 汽车行业供应链的事实标准，OEM 对 Tier-1/Tier-2 供应商的准入要求
- 强调 V 模型开发流程（需求→设计→实现→测试的逐层验证与确认）

### 2.10 ISO 9001 — Quality Management Systems

**发布组织**：ISO
**最新版本**：2015 版
**标准性质**：国际正式标准（International Standard），可认证

**定义方式**：

ISO 9001 是通用的**质量管理体系标准**，不限于软件行业。它定义了组织建立质量管理体系（QMS）应满足的要求，采用 PDCA（Plan-Do-Check-Act）循环和风险思维作为核心逻辑。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  ISO 9001:2015 的核心结构（高层结构 HLS）                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  4 组织环境     — 理解组织及其环境、相关方需求                       │
│  5 领导作用     — 质量方针、职责与权限                               │
│  6 策划         — 风险与机会的应对措施、质量目标                     │
│  7 支持         — 资源、能力、意识、沟通、文档化信息                 │
│  8 运行         — 产品/服务的需求→设计→生产→交付                    │
│  9 绩效评价     — 监视、测量、内审、管理评审                         │
│  10 改进        — 不合格与纠正措施、持续改进                         │
│                                                                     │
│  核心逻辑：                                                          │
│    PDCA 循环（策划→执行→检查→改进）× 风险思维                       │
│    "说你所做，做你所说，记你所做"                                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- ISO 9001 不针对软件，但软件企业可以把研发流程纳入 QMS 体系
- 强调"文档化信息"和"可追溯"，这与软件开发的过程管理天然契合
- 可通过第三方认证

### 2.11 Scrum

**发布组织**：Scrum.org / Scrum Alliance（非标准化组织）
**最新版本**：2020 Scrum Guide
**标准性质**：行业敏捷框架（Industry Agile Framework），非正式标准

**定义方式**：

Scrum 是一种**轻量级敏捷框架**，它定义了团队协作产生价值的最小必要结构：3 个角色、5 个事件、3 个工件。Scrum 不定义技术实践，只定义团队协作的规则与节奏。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  Scrum 的最小结构                                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  3 个角色：                                                          │
│    · Product Owner  — 最大化产品价值，管理产品待办列表               │
│    · Scrum Master   — 确保 Scrum 被正确理解和执行                   │
│    · Developers     — 创建可用增量的人                              │
│                                                                     │
│  5 个事件：                                                          │
│    · Sprint          — ≤4周的固定容器（其他事件都在其中）           │
│    · Sprint Planning — 规划本轮 Sprint 要做什么                     │
│    · Daily Scrum     — 每日 15 分钟同步与调整                       │
│    · Sprint Review   — 向利益相关方展示成果并获取反馈               │
│    · Sprint Retrospective — 团队反思与改进                          │
│                                                                     │
│  3 个工件：                                                          │
│    · Product Backlog      — 产品待办列表（所有待做事项）            │
│    · Sprint Backlog       — Sprint 待办列表（本轮承诺）             │
│    · Increment            — 可用增量（满足 Definition of Done）     │
│                                                                     │
│  核心理论：经验主义（透明→检视→适应）+ 精益思维                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- Scrum 是"故意不完整的"框架，只定义协作规则，不定义技术实践
- 需要补充 XP、DevOps 等技术实践才能完整运作
- Sprint 是所有节奏的心跳

### 2.12 Kanban Method

**发布组织**：Kanban University（David J. Anderson 创立）
**标准性质**：行业管理方法（Industry Management Method），非正式标准

**定义方式**：

Kanban Method 是一种**渐进式改进的管理方法**，它不定义新的流程，而是在现有流程之上施加一组原则和实践，使工作流动可视化、可管理、可持续改进。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  Kanban Method 的原则与实践                                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  6 个原则（Principles）：                                            │
│    ① 从你现在做的开始 — 不改变现有流程                              │
│    ② 追求增量式、进化式改变 — 不搞颠覆式改革                        │
│    ③ 尊重现有流程、角色、职责 — 先理解再改进                        │
│    ④ 鼓励领导力行为 — 从任何层级发起改进                            │
│                                                                     │
│  （前 4 条为变革原则，另有 2 条实施原则）                            │
│                                                                     │
│  6 个实践（Practices）：                                             │
│    ① 可视化工作 — 让工作流动可见                                    │
│    ② 限制在制品（WIP）— 防止过载，促进完成                          │
│    ③ 管理流动 — 监控和优化工作流动                                  │
│    ④ 显式化流程规则 — 让规则透明、可讨论                            │
│    ⑤ 建立反馈循环 — 定期检视和调整                                  │
│    ⑥ 协作式改进、实验性演进 — 基于数据的持续改进                    │
│                                                                     │
│  核心度量：前置时间、交付速率、在制品数量、质量                      │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

**关键特征**：
- Kanban 不替换现有方法，而是叠加在现有方法之上
- "从你现在做的开始"是其最鲜明的特征
- 通过限制 WIP 间接暴露瓶颈，从而驱动改进

### 2.13 Extreme Programming (XP)

**发布组织**：社区驱动（Kent Beck 创始）
**标准性质**：行业敏捷方法（Industry Agile Method），非正式标准

**定义方式**：

XP 是一种以**工程实践**为核心的敏捷方法，它定义了一组相互支撑的技术实践，确保软件质量的同时实现快速迭代。

**核心定义要素**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  XP 的五大价值观与核心实践                                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  五大价值观：沟通 · 简单 · 反馈 · 勇气 · 尊重                      │
│                                                                     │
│  核心实践：                                                          │
│    · 测试驱动开发（TDD）— 先写测试，再写实现                        │
│    · 持续集成（CI）— 频繁集成，每次集成自动构建测试                 │
│    · 结对编程 — 两人一台电脑，实时代码评审                           │
│    · 重构 — 持续改善代码设计，不改变外部行为                        │
│    · 简单设计 — 只做当前需要的，不为未来过度设计                     │
│    · 集体代码所有权 — 任何人可以修改任何代码                         │
│    · 可持续节奏 — 不加班，保持长期生产力                             │
│    · 现场客户 — 客户全程参与，实时回答问题                          │
│    · 规划游戏 — 小规模发布、迭代规划                                │
│    · 隐喻 — 用共同隐喻理解系统                                      │
│                                                                     │
│  与 Scrum 的关键区别：                                               │
│    Scrum 定义"怎么协作"，XP 定义"怎么写代码"                       │
│    两者经常组合使用                                                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 2.15 DevOps

**发布组织**：无单一组织（社区与企业实践共同演进）
**标准性质**：工程文化与实践体系，非正式标准

**定义方式**：

DevOps 不是单一标准或框架，而是一套**打破开发与运维壁垒的工程文化、实践和工具体系**。它强调自动化、持续交付、反馈循环和协作。

│    · 基础设施即代码（IaC）— 用代码管理基础设施                      │

```

## 四、不同标准的不同点分析

### 4.1 核心维度对比表

### 4.2 关键差异深度分析

#### 差异一：标准解决的核心问题不同

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  "你到底在解决什么问题？"                                                    │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────────────────────────────────────────┐                   │
│  │ 流程怎么画？                                        │                   │
│  │ → BPMN 2.0 · SPEM 2.0                               │                   │
│  │   这类标准只解决"表达"问题，不解决"内容"问题        │                   │
│  └─────────────────────────────────────────────────────┘                   │
│                          │ 供给内容                                         │
│                          ▼                                                  │
│  ┌─────────────────────────────────────────────────────┐                   │
│  │ 流程应该有哪些环节？                                │                   │
│  │ → 12207 · 15288 · 29110                             │                   │
│  │   这类标准定义"应该有什么过程"，但不评判做得好不好   │                   │
│  └─────────────────────────────────────────────────────┘                   │
│                          │ 需要评价                                         │
│                          ▼                                                  │
│  ┌─────────────────────────────────────────────────────┐                   │
│  │ 流程做得怎么样？                                    │                   │
│  │ → CMMI · SPICE · ISO 9001                           │                   │
│  │   这类标准评价"过程能力/成熟度"，不直接告诉你怎么改 │                   │
│  └─────────────────────────────────────────────────────┘                   │
│                          │ 需要落地                                         │
│                          ▼                                                  │
│  ┌─────────────────────────────────────────────────────┐                   │
│  │ 团队每天怎么干活？                                  │                   │
│  │ → Scrum · Kanban · XP · SAFe · DevOps               │                   │
│  │   这类标准规定"日常怎么执行"，但不关心流程建模      │                   │
│  └─────────────────────────────────────────────────────┘                   │
│                                                                             │
│  四层之间不是替代关系，而是互补关系                                          │
│  一个完整的研发体系通常需要从四层中各选至少一个                              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 差异二：定义的抽象层级不同

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  定义抽象层级光谱                                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  高抽象（只说原则/框架）                                                    │
│  ◄──────────────────────────────────────────────────────────────────►       │
│  ISO 9001    12207    CMMI    Scrum    SAFe    XP    DevOps                │
│  (原则级)    (框架级) (模型级) (框架级) (框架级) (实践级) (实践级)          │
│                                                                             │
│  · ISO 9001：只说"你要有质量方针"，不说"方针怎么写"                        │
│  · 12207：只说"你要有需求分析过程"，不说"用 JIRA 还是 Excel"              │
│  · CMMI：只说"你要管理需求"，不说"具体怎么管"                              │
│  · Scrum：只说"你要有 Sprint"，不说"代码怎么写"                           │
│  · SAFe：定义了更具体的角色/事件，但仍不涉及技术细节                        │
│  · XP：直接规定"先写测试再写代码"，最具体                                  │
│  · DevOps：直接规定"用 CI/CD 流水线"，最具体                               │
│                                                                             │
│  抽象层级越低 → 指导性越强，灵活性越低                                     │
│  抽象层级越高 → 灵活性越强，落地难度越大                                   │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 差异三：过程观不同

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  三种过程观：预测型 vs 适应型 vs 评估型                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  预测型（Plan-Driven）：                                                    │
│  ┌───────────────────────────────────────────────────────────┐             │
│  │ 12207 · 15288 · ASPICE · ISO 9001                         │             │
│  │ 假设：过程可以被预先定义，按阶段推进                       │             │
│  │ 特征：阶段清晰、门禁明确、文档完备、变更受控               │             │
│  │ 典型模型：瀑布、V 模型、阶段门禁                           │             │
│  └───────────────────────────────────────────────────────────┘             │
│                                                                             │
│  适应型（Change-Driven）：                                                  │
│  ┌───────────────────────────────────────────────────────────┐             │
│  │ Scrum · Kanban · XP · SAFe · DevOps                       │             │
│  │ 假设：需求会变化，过程应响应变化而非抵抗变化               │             │
│  │ 特征：迭代/增量、短反馈循环、拥抱变化、小批量交付           │             │
│  │ 典型模型：Sprint 迭代、看板流动、持续交付                   │             │
│  └───────────────────────────────────────────────────────────┘             │
│                                                                             │
│  评估型（Assessment-Driven）：                                              │
│  ┌───────────────────────────────────────────────────────────┐             │
│  │ CMMI · SPICE · ISO/IEC 330xx                              │             │
│  │ 假设：过程能力可以被客观评估，评估驱动改进                 │             │
│  │ 特征：能力等级、评估方法、评分体系、改进路径               │             │
│  │ 本身不规定预测还是适应，但 ML2 偏预测、ML3+ 支持适应      │             │
│  └───────────────────────────────────────────────────────────┘             │
│                                                                             │
│  注意：三种过程观不是互斥的                                                 │
│    CMMI ML3 + Scrum = 组织级标准化 + 团队级敏捷（常见组合）                │
│    12207 + DevOps = 全生命周期框架 + 持续交付实践（现代趋势）              │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 差异四：文档化要求的强度不同

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  文档化要求强度光谱                                                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  强文档化要求                                          弱文档化要求         │
│  ◄──────────────────────────────────────────────────────────────────►       │
│                                                                             │
│  ISO 9001  12207   ASPICE   CMMI   SAFe   ITIL   Scrum  Kanban  XP        │
│  (必文档)  (需文档) (需文档) (视等级) (轻文档)(中文档)(工作件)(可选)(最少)  │
│                                                                             │
│  · ISO 9001：所有过程必须有文档化信息                                       │
│  · 12207：每个过程有明确的制品要求                                          │
│  · ASPICE：过程产出物是评估的直接证据                                      │
│  · CMMI：ML2 要求项目级文档，ML3 要求组织级过程资产                        │
│  · Scrum：只要求 3 个工件（Product Backlog / Sprint Backlog / Increment）  │
│  · XP：代码即文档，测试即规格                                               │
│                                                                             │
│  选择建议：                                                                 │
│    合规性强的行业（汽车/医疗/军工）→ 强文档化                              │
│    互联网/产品型团队 → 弱文档化                                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

#### 差异五：适用场景与行业不同

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  行业-标准映射                                                              │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  互联网 / SaaS / 移动端：                                                   │
│    Scrum + Kanban + DevOps + XP（选配）                                     │
│    → 强调速度、反馈、持续交付                                               │
│                                                                             │
│  汽车电子 / 车载软件：                                                      │
│    Automotive SPICE + ISO 26262 + 12207                                     │
│    → 强调安全、可追溯、过程评估                                             │
│                                                                             │
│  航空航天 / 国防 / 军工：                                                   │
│    15288 + CMMI ML3+ + DO-178C                                              │
│    → 强调可靠性、可认证、严格门禁                                           │
│                                                                             │
│  金融 / 银行 / 保险：                                                       │
│    COBIT + ITIL + ISO 9001 + CMMI                                           │
│    → 强调治理、合规、风险管控                                               │
│                                                                             │
│  医疗器械软件：                                                              │
│    12207 + IEC 62304 + ISO 14971                                            │
│    → 强调安全、风险管理、可追溯                                             │
│                                                                             │
│  传统企业 IT / 政企信息化：                                                  │
│    12207 + ISO 9001 + ITIL                                                   │
│    → 强调规范、可控、服务管理                                               │
│                                                                             │
│  初创团队 / 小型开发组：                                                     │
│    29110 + Scrum + Kanban                                                    │
│    → 强调轻量、够用、渐进增强                                               │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 七、总结：如何选择适合自己的标准

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    标准选择的决策树                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  第一步：确定你属于哪类问题                                                 │
│  ──────────────────────                                                     │
│    想把流程画清楚？           → BPMN 2.0                                    │
│    想定义研发过程框架？       → 12207 / 15288 / 29110                       │
│    想评估/提升过程能力？      → CMMI / SPICE / ISO 9001                     │
│    想让团队日常跑起来？       → Scrum / Kanban / XP / DevOps                │
│    想管理 IT 服务和运维？     → ITIL                                        │
│    想做 IT 治理和合规？       → COBIT                                       │
│                                                                             │
│  第二步：确定你的约束                                                       │
│  ──────────────────────                                                     │
│    行业合规要求？             → 必须纳入对应行业标准                        │
│    团队规模？                 → 小团队选 29110+Scrum，大团队选 SAFe+CMMI   │
│    变化频率？                 → 高变化选敏捷，低变化选预测                  │
│    文档化要求？               → 强合规选 ISO 系列，弱合规选敏捷系列         │
│                                                                             │
│  第三步：组合搭配                                                           │
│  ──────────────────────                                                     │
│    从四层中各选一个，形成自己的体系                                         │
│    不要试图只用一个标准覆盖所有层面                                         │
│    先解决最痛的问题，再逐步补齐                                             │
│                                                                             │
│  记住：                                                                     │
│    标准是工具，不是目的。                                                    │
│    "用标准解决你的问题"，而不是"为标准而标准"。                             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

## 一、为什么是 10 个产品

### 1.1 从产品叙事反推

`product/最终目的.md` 的六条承诺里,每一条都需要一个或多个"用户可感知的产品入口"承载:

| 承诺 | 主要产品入口 |
|---|---|
| 用户是管理者 | Chat(对话)+ Console(管理台) |
| 员工是持久个体 | Chat(员工主页 / 登录员工)+ Console(员工管理) |
| 协作载体是对话 | Chat + Bridges(外部平台延伸) |
| 工作对象是软件项目 | Chat(项目群)+ Runner(运行产物) |
| 关键节点强制人类 | Chat(GateCard) |
| 过程始终可观察 | Chat + Console |

外加**三类平台功能**:
- **服务端** — Server + AI Members(非端侧)
- **生态接入** — SDK + Marketplace
- **品牌入口** — Website

合起来正好是 10 个。

### 1.2 不是 26 仓 → 10 产品的简单合并

10 ≠ 26 分组。关系是**制品层面**的组合:

- **专属仓**:某产品独有(chat / runner / console / sync / website / bridges / marketplace)
- **共享仓**:多个产品共用(core / bus / sdk / method-library / capability-hub / observability / archive / sandbox / identity / conversation / work / process / governance / artifact / member / runtime / tools / member-images / member-service)

**Server 是"组合产品"**:一次发布要拉 15 个仓的制品。
**AI Members 是"镜像产品"**:按 Role 输出 9+ 个容器镜像,背后是同一套代码。

### 2.3 五个共同产品原则

(以下原则对所有 10 产品有效,不重复在每个产品章节展开)

1. **对齐产品叙事** — 不允许产品界面出现与"用户是管理者"相违背的技术化表达
2. **与六域事件对齐** — 任何业务能力必须走六域 + 事件,不走私有 API
3. **使用 SDK 作为统一接入层** — 所有终端产品通过 SDK 连 Server,不私有连 L1 六域服务
4. **遵循 25010 Interaction Capability** — UI 产品必须覆盖 Learnability / Operability / User Error Protection / Inclusivity(含 Accessibility)
5. **可观察性内置** — 每个产品自身行为也要发事件进 observability,不是"只有业务发事件"

## 三、终端产品(4 个)

### 3.1 ① Chat — 协作入口

#### 使命

用户日常与 AI 员工协作的**主要界面**。群聊 + 频道 + 私聊 + GateCard + Artifact 预览的一站式集成。

#### 定位

Chat 是 Quantalithos 的**脸**。用户对产品的 80% 印象来自 Chat。

#### 主要用户

- **管理者**(Aris 画像)— 核心使用场景
- **旁观者** — 被邀请查看但不决策的用户
- **未来的人类员工** — 作为第一公民参与群聊(见 `最终目的.md` §11.5)

#### 形态

- **桌面** — macOS / Windows / Linux 原生(Tauri 或 Electron)
- **Web / PWA** — 浏览器可用
- **Mobile** — iOS / Android(优先处理审批,不是全功能)

#### 构成

**专属仓**:`quantalithos-chat`

**依赖的共享**:
- `quantalithos-sdk`(TypeScript 版本,必须)
- Server 所有六域的事件订阅
- Artifact 预览需要与 `quantalithos-artifact` 的 content_ref 协议对接

#### 域消费视图

```
Chat ──→ conversation   [主要] 全部事件,实时推送
     ──→ work           [次要] 项目卡片 + 成员列表 + WorkItem 进度
     ──→ governance     [必须] Gate 卡片 + 决策
     ──→ identity       [次要] 员工档案 + 登录视角
     ──→ artifact       [次要] 制品预览 + 引用
     ──→ process        [只读] 阶段进度指示器
```

#### 核心交互

- **群聊视图** ← Conversation(kind=group)
- **频道侧边栏** ← Conversation(kind=channel)
- **私聊列表** ← Conversation(kind=dm)
- **GateCard** ← governance.Gate 六段式可视化
- **员工登录** ← identity.GlobalMember + conversation 历史
- **项目进度栏** ← work.Project + process.ProcessInstance 状态

#### 刻意不做

- 不做 IDE 内嵌(那是开发者视角,偏离管理者叙事)
- 不做详细代码编辑(最多做 diff 预览)
- 不做管理员级配置(那在 Console)

#### 标准对齐

- **25010 Interaction Capability 全 6 子特性**(主要)
- **25010 QiU Satisfaction**(Trust / Pleasure / Comfort)
- **AG-UI 17 事件**(实时推送)
- **BPMN Collaboration**(群聊 + 频道抽象)

### 3.2 ② Runner — 运行产出

#### 使命

让**非开发者用户**一键运行 AI 团队产出的软件,不用懂部署、环境、依赖。

#### 定位

Runner 是 Quantalithos 独有的**"产出落地"**能力。竞品都停留在"给你代码/链接",我们负责"让你跑起来"。

#### 主要用户

- **非开发者管理者** — "我让 AI 做了个博客,我想用它"
- **演示者** — 给别人看项目效果时快速启动
- **采购者** — 从 Marketplace 买到的方案快速试用

#### 形态

- **桌面 App**(macOS / Windows / Linux)
- 提供 CLI 后备

#### 构成

**专属仓**:`quantalithos-runner`

**依赖**:
- `quantalithos-sdk`(用于认证 + Artifact 下载)
- `quantalithos-sandbox`(沙箱运行承载)
- Server 的 artifact 域事件(获取可运行包)

#### 域消费视图

```
Runner ──→ artifact     [主要] 下载 Release 包 + 依赖清单
       ──→ work         [只读] 项目身份验证
       ──→ (不消费其他域)
```

#### 核心交互

- 用户打开 Runner → 登录 → 看到自己项目的 Release 列表
- 选一个 Release → Runner 从 artifact 域拉取包 → 沙箱启动 → 返回本地 URL
- Runner 管理多个运行中的项目,一键停 / 重启 / 查看日志

#### 刻意不做

- 不做代码调试(开发者工具)
- 不做生产部署(那是 DevOps 流程,走 process + release Gate)
- 不允许用户自行改 Release 包(只读)

#### 标准对齐

- **25010 Portability**(Adaptability / Installability)
- **25010 Reliability**(Availability / Recoverability)
- **Research 沙箱加固**(Runner 不允许逃逸主机)

### 3.3 ③ Sync — 工作区同步

#### 使命

给**想把代码同步到本地**的用户(通常是开发者旁观或二次开发)提供工作区同步能力。

#### 定位

Sync 服务于一个边缘但必要的场景:**用户想看代码**。不强制存在于产品流程中,但**对开发者信任度**至关重要。

#### 主要用户

- **开发者旁观者** — 想在本地 IDE 看 AI 写的代码
- **项目接手人** — 要把 AI 阶段性产出接过来继续开发
- **代码评审者** — 本地审代码

#### 形态

- **CLI 工具**(主要)
- **小型 GUI**(可选,Tauri)

#### 构成

**专属仓**:`quantalithos-sync`

**依赖**:
- `quantalithos-sdk`
- Git / 文件系统接口(可移植的本地操作)

#### 域消费视图

```
Sync ──→ work      [次要] 项目列表
     ──→ artifact  [主要] Artifact(kind=code)的下载 + 双向同步
     ──→ (不消费其他域)
```

#### 核心交互

- `qs-sync clone <project>` — 把项目代码同步到本地
- `qs-sync pull` — 拉最新
- `qs-sync push-review` — 把本地修改作为"人类反馈"推回(进入评审 Gate)

#### 刻意不做

- 不替代 Git(Git 仍是底层,Sync 只是 Quantalithos 的包装)
- 不自动合并(冲突必须人类决策)
- 不给非项目成员(需要 ProjectMember 身份或用户所有权)

#### 标准对齐

- **25010 Compatibility Interoperability**(与 Git 共存)
- **42001 A.7 Data Provenance**(双向同步必须记录溯源)

### 3.4 ④ Website — 品牌 + 文档

#### 使命

外部来访者的**第一印象** + **文档站**。

#### 定位

Website 是 Quantalithos 对外的**门面**,不负责产品功能,负责**说服与导航**。

#### 主要用户

- **潜在客户**(未注册用户)
- **现有用户的查阅** — 文档 / 更新日志 / 定价
- **SEO 收录** — 让搜索引擎找到产品

#### 形态

- **静态站点**(Astro / Next.js SSG)
- **一级域名主站 + 二级 docs 站**

#### 构成

**专属仓**:`quantalithos-website`

**依赖**:无(独立部署,不对接 Server)

**间接依赖**:
- 注册 / 登录导流到 Server 的认证入口
- 文档同步从 `quantalithos-design` 仓的部分文档(如选定的公开文档)

#### 域消费视图

```
Website ──→ (不消费任何域 · 完全独立)
```

#### 核心交互

- 首页(hero + 产品定位)
- 产品页(10 产品分别介绍)
- 文档站(教程 / API / FAQ)
- 博客(Release notes + 思考)
- 定价(未来)

#### 刻意不做

- 不做动态应用功能(那不是 Website 职责)
- 不做登录后的复杂交互(那是 Chat / Console)
- 不做面向开发者的可执行 Demo(那是未来的 Playground,暂不做)

#### 标准对齐

- **25010 Interaction Capability Inclusivity**(WCAG AA Accessibility)
- **9001 Documented Information**(文档版本管理)

## 四、管理者产品(1 个)

### 4.1 ⑤ Console — 组织治理中心

#### 使命

**组织管理者 / 合规官 / 方法论制定者**的操作面板。管理员工、方法库、审计、指标看板。

#### 定位

Console 是 Quantalithos 的**另一半脸**,和 Chat 互补不重叠。Chat 是"个人协作视角",Console 是"组织治理视角"。

#### 主要用户

- **组织管理者**(企业用例的主要用户)
- **合规官 / 审计官** — 看审计日志、AIIA、SoA
- **方法论制定者** — 维护 ProcessTemplate / Role 定义
- **运营** — 看 DORA / EBM 指标

#### 形态

- **Web 应用**(SPA)

#### 构成

**专属仓**:`quantalithos-console`

**依赖**:
- `quantalithos-sdk`(TypeScript)
- Server 全六域的查询 API
- `quantalithos-observability` 的指标 API
- `quantalithos-method-library` 的 Method Content 编辑 API

#### 域消费视图

```
Console ──→ identity       [主要] 员工管理 / Role 编辑 / 生命周期
        ──→ work           [主要] 项目总览 / 跨项目查询
        ──→ process        [主要] Template 管理 / Profile 审核
        ──→ governance     [主要] Gate 审批总览 / Policy 下发 / SoA 编辑 / Control 实施
        ──→ conversation   [次要] 查看某对话历史
        ──→ artifact       [次要] Artifact 搜索 / Baseline 管理
        ──→ 方法库          [主要] Method Content 编辑
        ──→ 观测            [主要] 指标看板 / 审计日志 / 事件回放
        ──→ 能力池          [次要] MCP Registry 管理 / Provider Contract
```

#### 核心交互模块

1. **员工管理**(identity)— 招聘 / 编辑 / 暂停 / 退休
2. **项目监控**(work)— 全组织项目状态看板
3. **方法库编辑**(method-library)— Role / Template / Policy 定义
4. **治理面板**(governance)— Gate 总览 + SoA + Control + AIIA
5. **审计日志**(observability)— 事件回放 + 不变性验证 + 哈希链查看
6. **指标看板**(evaluation)— DORA / EBM / 自定义
7. **能力池管理**(capability-hub)— MCP Registry + Provider

#### 刻意不做

- 不做日常协作(那是 Chat)
- 不做项目立项(那是 Chat 发起)
- 不做代码编辑(不是 IDE)

#### 标准对齐

- **42001 §9.3 管理评审**(Management Review UI)
- **42001 SoA 编辑** + **Control 实施状况**
- **CMMI 能力成熟度可视化**
- **DORA / EBM 指标看板**
- **25010 Interaction Capability**(管理员效率优先)

## 五、服务端产品(2 个组合型)

### 5.1 ⑥ Server — 后端全栈

#### 使命

Quantalithos **所有业务能力**的承载者。端侧产品通过 SDK 对接到 Server。

#### 定位

Server 不是用户可感知的产品,但是**所有其他产品的前提**。自托管或 SaaS 两种部署形态。

#### 主要"用户"

- 端侧产品(Chat / Console / Sync / Runner / Bridges)
- SDK(作为 Server 的门户)

#### 形态

- **自托管部署包**(Docker Compose / Helm Chart / Terraform Module)
- **SaaS 实例**(Quantalithos 官方运营)

#### 构成(组合 15+ 仓)

```
L0 共享契约层
  ├─ quantalithos-core
  ├─ quantalithos-bus
  └─ quantalithos-sdk(作为 Server 自测试依赖)

L1 六域服务层(全部 6 仓)
  ├─ quantalithos-identity
  ├─ quantalithos-conversation
  ├─ quantalithos-work
  ├─ quantalithos-process
  ├─ quantalithos-governance
  └─ quantalithos-artifact

L3 方法能力层(2 仓)
  ├─ quantalithos-method-library
  └─ quantalithos-capability-hub

L4 基础设施层(3 仓)
  ├─ quantalithos-observability
  ├─ quantalithos-archive
  └─ quantalithos-sandbox

L2 Member 编排(1 仓,不含镜像)
  └─ quantalithos-member-service
```

共 **15 个仓**。

**不含**:L2 的 `member` / `runtime` / `tools` / `member-images`(这些是 AI Members 产品的组成,由 member-service 拉取运行)。

#### 域消费视图

Server 本身是六域的**服务端实现**,不"消费"域,它**就是**域。

#### 部署形态

- **Single-node**(开发 / 小规模 SaaS 用户)— Docker Compose 一键起
- **Cluster**(企业自托管)— Helm Chart + Kubernetes
- **Managed SaaS**(Quantalithos 官方)— 多租户隔离

#### 标准对齐

- **42001 AIMS** 全套
- **9001 QMS** 全套
- **25010 Reliability**(Availability / Fault Tolerance / Recoverability)

### 5.2 ⑦ AI Members — 员工镜像集合

#### 使命

所有**可用 AI 员工**的运行形态。按 Role 预构建的容器镜像集合。

#### 定位

AI Members 是 Quantalithos 的**"员工库"**本体。用户创建项目时,member-service 从这里拉取对应 Role 的镜像启动容器。

#### 主要"用户"

- `member-service` 拉取运行
- 间接:每个 Project 的 ProjectMember

#### 形态

- **容器镜像集合**(Docker registry / OCI-compatible registry)
- 版本化发布(semver)
- 每 Role 一个镜像

#### 构成(5 仓组合)

```
L2 Member 运行层(全部 5 仓)
  ├─ quantalithos-member          Rust 门面进程
  ├─ quantalithos-runtime         Python 大脑进程
  ├─ quantalithos-tools           Python 工具 monorepo
  ├─ quantalithos-member-images   Dockerfile 构建定义(ADR-0005)
  └─ quantalithos-member-service  容器编排服务(归 Server)
```

其中 `member-service` 归 Server 产品,**AI Members 产品 = member + runtime + tools + member-images = 4 仓组合产出镜像**。

#### 镜像集合(9 个初始 Role,ADR-0005)

```
ai-member-base                 所有 Role 共享的基础层
ai-member-tech-lead
ai-member-backend-dev
ai-member-frontend-dev
ai-member-qa
ai-member-ux
ai-member-devops
ai-member-auditor              ← ISO 42001 内部审计
ai-member-assistant
ai-member-observer             ← 旁观者(只读)
```

#### 标准对齐

- **SPEM 2.0 RoleDefinition → 镜像映射**(ADR-0005)
- **42001 A.4 Tooling Resources**
- **42001 A.6 AI System Life Cycle** Deployment 阶段

## 六、生态产品(3 个)

### 6.1 ⑧ Bridges — 外部平台桥

#### 使命

让用户**不离开既有团队协作平台**(Mattermost / Telegram / Slack / Discord)就能使用 AI 员工。

#### 定位

Bridges 是 Quantalithos 的**触达延伸**。很多用户不愿意为新工具切换,Bridges 让 Quantalithos 进到他们已有的工作流。

#### 主要用户

- **已深度使用 Mattermost/Slack 的团队** — 不愿再切换工具
- **个人用户的 Telegram 接入** — 随时随地审批
- **社区/玩家的 Discord 接入** — 轻量场景

#### 形态

- **Mattermost Plugin**(用户在 MM Channel 里@ 员工)
- **Telegram Bot**(用户和员工的私聊 / 群组)
- **Slack App**(用户在 Slack Channel 里协作)
- **Discord Bot**(类似 Slack)

#### 构成

**专属仓**:`quantalithos-bridges`(monorepo,每平台一个子模块)

**依赖**:
- `quantalithos-sdk`(Python / TypeScript)
- 各平台 SDK(Mattermost / Slack / Telegram / Discord)
- 映射配置(external_id ↔ GlobalMember)

#### 域消费视图

```
Bridges ──→ conversation   [主要] 双向映射消息
        ──→ governance     [次要] 在外部渲染 GateCard 的简化版
        ──→ identity       [次要] external_id ↔ member_id 映射
        ──→ (其他域不直接消费,通过 conversation 间接)
```

#### 核心映射

```
[Quantalithos 内]         [外部平台]
  Conversation             Channel / Group / DM
  Turn                     Message
  Mention                  @user
  GateCard                 Rich message / Interactive button
  Artifact 预览            Attachment / Link preview
  GlobalMember             Bot account / User
```

#### 权限边界

Bridges 有 **严格的权限边界**,对齐 42001 A.10:
- 外部平台的操作不能绕过 Quantalithos 的 Policy 和 Gate
- 外部 ID 必须映射到 GlobalMember,映射关系由组织管理
- 敏感 Gate(如 release / impact-assessment)不在外部平台渲染完整内容,只提示"请打开 Chat 审批"

#### 刻意不做

- 不做全功能协作(部分功能必须在 Chat 完成)
- 不做外部账号自动创建 GlobalMember(必须组织授权映射)
- 不做跨平台"一条消息多端发"(每个平台独立绑定)

#### 标准对齐

- **42001 A.10** 第三方治理
- **25010 Compatibility Interoperability**
- **9001 供应商管理**(Mattermost 等被视为组织使用的外部平台)

### 6.2 ⑨ SDK — 开发者接入层

#### 使命

让**第三方 / 组织内部开发者**以编程方式与 Quantalithos 六域交互,构建自己的集成。

#### 定位

SDK 是 Quantalithos 的**开放能力**。所有端侧产品(Chat / Console / Sync / Runner / Bridges)内部都走 SDK,外部开发者也用同样的 SDK。

#### 主要用户

- **所有 Quantalithos 端侧产品开发者**(内部用户)
- **企业内部的集成开发者**(把 Quantalithos 接进自家 IT 系统)
- **独立开发者**(做 Marketplace 的第三方插件)
- **研究人员 / 评测者**(用 SDK 做自动化评估)

#### 形态

- **Python SDK**(主要,AI / 数据领域)
- **Rust SDK**(性能敏感场景、L2 member 内部)
- **TypeScript SDK**(前端产品 + Node.js 集成)

三语言**独立发版**,但版本号保持同步(`x.y.z-<lang>`),类型定义从 `core` 的 proto 同版本生成。

#### 构成

**专属仓**:`quantalithos-sdk`

**依赖**:
- `quantalithos-core`(proto 与 CloudEvents schema 的类型来源)
- Server 的所有对外 gRPC / REST 接口

#### 域消费视图

```
SDK 不"消费"某个域,它为所有域提供客户端封装:
  ├─ identity  Client
  ├─ conversation Client
  ├─ work Client
  ├─ process Client
  ├─ governance Client
  ├─ artifact Client
  ├─ observability Client(只读)
  ├─ method-library Client
  └─ capability-hub Client
```

#### 核心能力

- **高层封装** — 不是裸 gRPC,提供领域化 API(`project.create()` / `gate.decide()`)
- **认证 / Token** — 处理 OAuth / API Key / mTLS
- **事件订阅** — WebSocket / SSE / gRPC Stream 的统一包装
- **Trace 传播** — 自动注入 W3C Trace Context
- **重试 / 退避** — 瞬时错误的处理
- **配置加载** — env + file + remote 的优先级
- **类型生成** — 从 core proto 自动生成 binding(不手写)

#### 刻意不做

- 不做 UI 组件(那是 Chat / Console 的责任)
- 不做身份管理(由调用方提供 token)
- 不做本地缓存(调用方决定缓存策略)

#### 标准对齐

- **25010 Interaction Capability Learnability**(API 易学)
- **25010 Compatibility Interoperability**(三语言一致体验)
- **9001 Documented Information**(SDK 文档必须完备)
- **MCP** — SDK 内置 MCP Client 能力,方便开发者构建 MCP-aware 工具

### 6.3 ⑩ Marketplace — 资产市场

#### 使命

**社区 + 组织 + 第三方**共享 / 购买 / 发布的资产市场,包括:
- ProcessTemplate(方法模板)
- Role 定义 + 对应的 AI Member 镜像
- 垂直领域的 MCP Tool 集合
- 完整的 Deployment Package(29110)

#### 定位

Marketplace 是 Quantalithos 的**生态飞轮**。一旦启动,社区贡献 > 官方输出,产品变成"平台"。

#### 主要用户

- **发布者** — 方法论咨询师、工具开发者、垂直领域专家
- **采购者** — 找"医疗项目模板"、"金融合规 Role"、"游戏开发工具包"的用户
- **组织内部** — 企业把自己的标准流程发到内部 Marketplace

#### 形态

- **Web 应用**(Marketplace 本身)
- **CLI**(发布者上传资产)
- **资产包格式**(Deployment Package 格式,对齐 29110)

#### 构成

**专属仓**:`quantalithos-marketplace`

**依赖**:
- `quantalithos-sdk`
- Server 的 method-library API(发布资产进入方法库)
- Server 的 capability-hub API(发布 MCP Tool)
- 支付 / 订阅 / 认证(未来的 billing 系统,暂不纳入本文)

#### 域消费视图

```
Marketplace ──→ method-library  [主要] 发布 / 订阅 Method Content
            ──→ capability-hub  [主要] 发布 / 订阅 MCP Tool
            ──→ identity        [次要] 发布者 Role 镜像
            ──→ (不直接消费六域业务)
```

#### 资产类型

| 资产 | 在方法库的位置 | 典型价格点 |
|---|---|---|
| ProcessTemplate | method-library.ProcessTemplate | 开源 / 付费 / 订阅 |
| Role 定义 + Member 镜像 | identity.Role + AI Members 产品镜像 | 付费 / 订阅 |
| MCP Tool 集合 | capability-hub.MCPRegistry | 开源 / 付费 |
| Deployment Package | 方法库 + 能力池联合 | 企业方案为主 |

#### 刻意不做

- 不做 LLM 模型本身(那是 Anthropic / OpenAI 的市场)
- 不做人力服务(那是 Upwork)
- 不做代码片段市场(那是 GitHub Gist)

#### 标准对齐

- **29110 Deployment Package** 格式
- **42001 A.10** 第三方治理(上架需审核)
- **9001 供应商管理**

3. **SDK 是"所有"** — 不因为 SDK 自己复杂,而是因为**每个端侧产品**都要连六域的不同子集,SDK 为他们提供统一的 client 封装。

## 九、版本发布节奏

### 9.1 发布节奏表

| 产品 | 发布节奏 | 版本策略 | 依赖对齐 |
|---|---|---|---|
| ⑥ Server | 每 2 周 | 主版本号驱动(x.y.z) | - |
| ⑦ AI Members | 每 2 周 | 跟 Server major.minor | Server |
| ⑨ SDK | 每 2 周 | 跟 Server 的 proto 版本 | Server (core proto) |
| ⑤ Console | 每 2 周 | 跟 Server | Server + SDK |
| ① Chat | 每 4 周 | 适配 SDK | SDK |
| ② Runner | 每 4 周 | 适配 SDK | SDK |
| ③ Sync | 每 4 周 | 适配 SDK | SDK |
| ⑧ Bridges | 按需(通常 2-4 周) | 适配 SDK | SDK |
| ⑩ Marketplace | 独立 | 适配 Hub/method-library API | method-library |
| ④ Website | 独立 | 无依赖 | - |

### 9.2 版本对齐规则

**硬规则**:
- Server / SDK / AI Members 三者**版本号同步**(x.y.z)
- 端侧产品(Chat / Runner / Sync / Bridges / Console)适配 **SDK 的 minor 版本**,允许相对 Server 落后 1 个 minor
- 端侧产品与 Server 的 **major 版本必须一致**

**软约定**:
- 端侧产品通常**滞后 Server** 1-2 个 minor(给端侧产品时间适配)
- SDK 的 **deprecated API** 至少给 2 个 minor 的过渡期

              ▼                   ▼
         Server 发版          SDK 发版(三语言)
              │                   │
              ▼                   │
         AI Members 发版          │
                                  ▼
                            Console 发版(依赖 SDK)
                                  │
                        ┌─────────┴─────────┐
                        ▼         ▼         ▼
                      Chat      Runner     Sync
                        │
                        ▼

### 9.4 发布 Gate

**关键节点必须经过 Gate**:
- Server major 发布 → release-confirm Gate(由产品负责人批)
- AI Members 新 Role 发布 → role-introduction Gate(由方法论负责人 + 产品负责人共批)
- SDK breaking change → breaking-change Gate(由 SDK 负责人 + 所有端侧产品负责人共批)
- Marketplace 新资产上架 → marketplace-review Gate(由合规 + 内容审核共批)

## 十一、关键设计决策汇总

| 决策 | 理由 |
|---|---|
| 10 个产品不合并 | 每个产品都有独立的主要用户画像和使命 |
| Chat 和 Console 严格互补 | 管理者视角 vs 治理视角,混在一起会淹没核心价值 |
| Runner / Sync 窄聚焦 | 只做一件事,做得极其好 |
| SDK 是"所有客户端的统一接入层" | 避免端侧直连 L1 造成的耦合 |
| Server 是 15+ 仓组合 | 不做"单 binary 大 monolith",但也不按功能过度拆成 service-a/b/c |
| AI Members 是镜像产品 | 对齐 ADR-0005 按 Role 预构建 |
| Bridges 有权限边界 | 42001 A.10 要求 |
| Marketplace 不做模型和代码片段 | 有限的范围才能形成飞轮 |
| Website 完全独立 | 不与业务耦合,能被 SEO 充分利用 |
| 发布 Gate 递归适用 | 产品自身也走 Gate,不例外 |

## 附录 B:设计原则审视

| 原则 | 本文体现 |
|---|---|
| **SRP 单一职责** | 每个产品使命明确,边界清晰 |
| **DRY** | SDK 作为共同接入层,避免端侧重复实现域对接 |
| **KISS** | 窄聚焦产品(Runner / Sync / Bridges)不堆功能 |
| **YAGNI** | "刻意不做"章节列出不做的事,避免功能泛滥 |
| **关注点分离** | Chat(协作)与 Console(治理)严格分离 |
| **可扩展性** | Bridges / Marketplace 天然支持外部扩展 |
| **可演进性** | 版本节奏有规则,breaking change 走 Gate |
| **可组合性** | Server 和 AI Members 是组合型产品,内部各仓独立演进 |
| **可观察性** | 每个产品自身行为发事件(§二.三 原则 5) |
| **最小接口** | SDK 作为统一接入,最小化端侧与 L1 的直连 |

# 公司开发体系：云端资产库清单

> 目的：梳理一个公司级研发体系中，云端通常会有哪些“库”，并给出每类库的典型职责，作为后续讨论“哪些资料放云端、哪些资料放本地”的基础参考。

---

## 一、核心结论

对于一个公司开发体系来说，云端通常不止有 `项目库`、`产品库`、`代码库`。

更完整地看，云端往往承载的是一组“逻辑资产库”：

- 面向业务协作的库
- 面向工程交付的库
- 面向运行治理的库
- 面向组织知识与 AI 协作的库

这些“库”不一定在物理上完全独立，但在系统设计上通常会被视为不同类型的资产域。

---

## 二、核心业务与研发协作类库

### 1. 项目库

用于管理项目级资产与生命周期。

典型内容：

- 项目基本信息
- 项目状态
- 项目成员
- 阶段进度
- 里程碑
- 项目之间的依赖关系

### 2. 产品库

用于管理产品线、模块与版本演进信息。

典型内容：

- 产品线
- 产品模块
- 产品版本
- Roadmap
- 产品归属关系

### 3. 需求库

用于管理需求级资产，是产品到研发的正式输入面。

典型内容：

- PRD
- 需求条目
- 用户故事
- 史诗
- 验收标准
- 需求变更记录
- 优先级

### 4. 任务库

用于承接需求拆解后的执行单元。

典型内容：

- 工单
- 任务卡
- 子任务
- 责任人
- 状态流转
- 排期
- 阻塞项

### 5. 缺陷库

用于管理 Bug 与修复闭环。

典型内容：

- Bug 条目
- 严重级别
- 复现步骤
- 影响范围
- 修复状态
- 回归验证结果

## 八、AI / Agent 驱动体系常见扩展库

如果公司研发体系引入 AI Agent，通常还会增加下面几类库。

### 32. Prompt/策略库

典型内容：

- 系统提示词
- 角色策略
- 流程策略
- 路由规则

### 33. Agent 模板库

典型内容：

- Tech Lead 模板
- 前端开发模板
- 后端开发模板
- 测试模板
- DevOps 模板

### 34. 上下文快照库

典型内容：

- 项目现场快照
- Agent 记忆片段
- 恢复包
- 运行状态快照
- 工作记录索引
- 会话恢复点

我建议把“快照恢复”和“工作记录”都纳入云端，但不要混成一个无限膨胀的大表，而应拆成两层：

- `snapshot objects`：负责恢复某个时点的可执行上下文，例如阶段快照、恢复包、运行状态冻结点
- `worklog objects`：负责记录 AI / 人在过程中的关键动作、判断、产出引用和切换原因

更合适的挂载方式是：

- **主归属平台**：`AI 编排与知识平台` 下的 `上下文快照库`
- **审计副本 / 索引**：高风险动作同步到 `合规/审计库`
- **运行关联索引**：与发布、事故、回滚强相关的记录，额外挂接 `发布运行平台`

也就是说：

- 能用于“恢复现场”的内容，优先放 `上下文快照库`
- 能用于“解释做过什么”的内容，优先放 `工作记录/worklog`，并可同步审计
- 涉及发布执行、回滚、事故处置的关键记录，不应只留在 AI 平台，还应在运行平台保留引用或副本

另外我建议这一层必须做成**可配置**，而不是一刀切。至少应允许按下面几个维度配置：

- 存储位置：`local_only` / `cloud_only` / `local_and_cloud`
- 同步策略：`realtime` / `checkpoint_only` / `manual`
- 保留时长：按会话、项目、阶段、环境分别配置 TTL
- 敏感度分级：`public_internal` / `restricted` / `secret`
- 恢复粒度：只恢复索引、恢复摘要、恢复完整上下文
- 审计策略：仅记录元数据，或记录全文与附件引用

这样才能同时兼顾恢复能力、成本、隐私和合规。

## 十一、用于后续讨论的一个关键提醒

这些“库”是**逻辑库**的概念，不一定等于物理上完全独立的数据库或系统。

实际落地时通常有三种情况：

- 一个大平台中划分多个逻辑域
- 多个专用系统分别承载不同资产
- 云端数据库 + 对象存储 + Git 仓库 + 搜索引擎共同组成“云端库体系”

所以后续真正要讨论“哪些资料放云端、哪些放本地”时，更应该按：

- 资料类型
- 访问方式
- 是否需要实时查询
- 是否需要 Git 管理
- 是否需要 Agent 直接读写

来做划分，而不是只看名字里是不是“库”。

## 十二、这些云端库如何与当前 AI 系统协同

如果把当前 AI 系统理解为“`Assistant + Tech Lead + 专业角色 Agent + 本地工作区 + 云端资产库 + daemon/编排层`”的组合，那么这些云端库不应只是给人看的后台系统，而应成为 AI 的正式上下文来源、约束来源、执行回写目标与审计面。

我建议把协同关系收敛成下面四层：

### 1. 上下文供给层

云端库向 AI 提供结构化上下文。

典型来源：

- 项目库：当前项目状态、成员、阶段、里程碑
- 产品库 / 需求库：产品目标、PRD、Roadmap、验收口径
- 任务库 / 缺陷库：当前执行单、阻塞项、优先级、责任人
- 文档库 / 接口库 / 数据模型库：设计边界、协议定义、Schema 约束
- 知识库 / 复盘库：历史经验、最佳实践、类似问题处理方式

这层解决的是：

- AI 不从零猜业务背景
- AI 不靠聊天记录拼上下文
- AI 能拿到正式、可追溯的项目事实

### 2. 规则约束层

云端库不仅提供资料，还应提供“AI 不能越过的边界”。

典型来源：

- 质量规则库：lint、review、覆盖率、质量门禁
- 流程模板库：阶段流转、审批模板、交接模板、done_when
- 用户与组织库：角色权限、审批权、责任边界
- 合规/审计库：哪些操作需要留痕、哪些资料不可外发
- 密钥/凭据库：安全访问方式与最小权限边界

这层解决的是：

- AI 不只是“知道该做什么”
- AI 还知道“什么不能做、做到什么程度才算完成”

### 3. 执行联动层

AI 在本地工作区执行，但要与云端库形成双向联动。

典型联动方式：

- 从任务库拉取任务 -> 在本地实现 -> 回写任务状态
- 从代码库检出仓库 -> 本地修改 -> 回写 PR / MR / 提交记录
- 从测试库拉取用例 -> 本地执行测试 -> 回写测试结果库
- 从发布库读取发布计划 -> 在阶段 5 执行发布 -> 回写灰度、回滚、结论
- 从监控库读取指标与告警 -> 驱动 `hold` / `rollback` 判定

这层解决的是：

- AI 的动作不悬空
- 云端系统能看到 AI 的推进结果
- 本地执行与云端治理保持一致

### 4. 记忆沉淀层

AI 不应只消费云端库，还应反向沉淀高价值结果。

典型沉淀目标：

- 文档库：设计说明、变更说明、复盘文档
- 复盘库：故障分析、改进项、经验教训
- 知识库：FAQ、通用方案、最佳实践
- Prompt/策略库：哪些策略在公司内效果好
- Agent 模板库：哪些角色模板需要优化

这层解决的是：

- AI 不只是执行器
- AI 还是组织经验的沉淀器和放大器

## 十三、这些库不应拆成“一个超级平台”，而应拆成哪些项目

我建议不要把这 30 多类逻辑库直接做成一个庞然大物，而应拆成几个相对稳定的平台项目。这样更接近大型公司的落地方式，也更适合和 AI 系统逐步集成。

### 1. 项目 A：协作与交付平台

这是最靠近业务协作面的平台，承载“项目到需求到任务到验收”的主线。

建议纳入：

- 项目库
- 产品库
- 需求库
- 任务库
- 缺陷库
- 验收库
- 复盘库（可先弱化）

AI 协同重点：

- Assistant / Tech Lead 从这里取项目事实与需求事实
- 阶段 1 到阶段 4 的大量正式对象主要从这里读取和回写
- 这是最适合先和 AI 打通的第一优先级平台

### 2. 项目 B：工程资产与研发平台

这是最靠近代码与工程交付面的平台。

建议纳入：

- 代码库
- 文档库
- 接口库
- 数据模型库
- 组件库
- 架构资产库
- 制品库
- 测试用例库
- 测试结果库
- 质量规则库

AI 协同重点：

- 代码生成、代码检索、文档生成、测试生成、接口对齐
- Tech Lead / 开发 / 测试 Agent 的主要工作台都依赖这一层
- 这是最接近 CodeArts / GitLab / GitHub Copilot Workspace 类能力的部分

### 3. 项目 C：发布与运行治理平台

这是阶段 5 与运行期控制的核心平台。

建议纳入：

- 发布库
- 配置库
- 环境库
- 监控库
- 日志库
- 事件/事故库
- 变更库
- 值守库
- 密钥/凭据库
- 合规/审计库

AI 协同重点：

- 发布前检查、灰度编排、观察窗决策、回滚执行、事故响应
- 阶段 5 的 `release_entry_packet`、`release_gate_signal`、`rollback_execution_record` 等对象都应与这一层强绑定
- 这是 AI 从“写代码助手”走向“运行控制助手”的关键层

### 4. 项目 D：AI 能力与组织知识平台

这是让 AI 能持续变强、持续守规则的基础平台。

建议纳入：

- 知识库
- 流程模板库
- Prompt/策略库
- Agent 模板库
- 上下文快照库
- 技能/工具库
- 模型配置库
- 用户与组织库

AI 协同重点：

- 决定 AI 用什么角色、什么流程、什么模型、什么权限、什么知识源
- 决定 AI 的组织级复用能力，而不是单项目临场发挥
- 这是 AI 系统和传统研发平台的最大差异点

### 5. 如果只拆成最小可落地的 3 个项目

如果不想一上来拆太细，我建议先落成下面三个项目：

- `协作项目台`：项目/需求/任务/缺陷/验收
- `工程研发台`：代码/文档/接口/测试/制品
- `AI 控制台`：知识/模板/Agent/模型/权限/快照

然后把发布与运行治理先挂在 `工程研发台` 或单独做二期。

这会更适合 MVP。

它值得参考的不是具体界面，而是：

如果对照你的体系，GitLab 更接近：

- Artifacts：制品

它的价值在于告诉我们：

- AI 如何嵌入开发者日常工作流

### 5. Jira + Confluence + Bitbucket / GitLab 组合

所以你的方向完全合理：

- 先按资产域拆平台

## 十六、我对当前体系的建议判断

如果你现在要把“云端资产库 + AI 系统”真正变成产品，我建议不要直接做“全家桶”，而是按下面顺序推进：

### 第一优先级

先做：

- `协作项目台`
- `工程研发台`
- `AI 编排与知识平台`

原因：

- 这三者已经足够支撑阶段 0 到阶段 4 的主闭环
- 也是 AI 最容易体现价值的地方
- 最接近 CodeArts、GitLab、Azure DevOps 中已经被验证过的价值区域

### 第二优先级

再做：

- `发布运行平台`

原因：

- 这层价值很大，但复杂度也最高
- 它需要更强的权限、安全、审计和运行数据接入
- 更适合作为二期深化，而不是一开始全上

### 一个最终建议

我建议把你的目标平台定义为：

> **一个以 AI 编排层为核心、以协作平台 + 工程平台 + 运行平台为三大事实面的大型研发操作系统。**

这比“做一个 AI IDE”要大，也比“做一个项目管理工具”更完整。

## 十七、3+1 平台之间的边界、主数据、事件流与权限流

> 本节回答：如果采用 `研发协作平台 + 工程执行平台 + 发布运行平台 + AI 编排与知识平台` 的 `3+1` 拆法，这四层之间到底如何分工？哪些对象是谁的主数据？事件如何流动？AI 的权限如何被约束？

### 1. 先固定一个总原则

我建议先把总原则钉死：

> **平台拆分不是为了把数据切碎，而是为了明确“谁是事实源、谁负责执行、谁负责治理、谁负责 AI 编排”。**

也就是说，`3+1` 不是四个彼此独立的孤岛，而是：

- 三个**事实面平台**
- 一个**AI 控制平面**

### 2. 四个平台的最小边界

#### 2.1 研发协作平台

负责回答：

- 我们在做什么项目
- 为什么要做
- 当前需求、缺陷、任务和验收处于什么状态

边界内对象：

- 项目
- 产品
- 需求
- 任务
- 缺陷
- 验收
- 复盘项

不负责：

- 代码正文管理
- 构建与发布执行
- AI 模型与 Agent 策略

#### 2.2 工程执行平台

负责回答：

- 代码和文档怎样被实现
- 接口、测试、质量、制品怎样形成
- 从需求到工程交付，产出了哪些正式工程资产

边界内对象：

- 仓库
- 分支
- PR/MR
- 文档
- 接口
- 数据模型
- 测试用例
- 测试结果
- 制品
- 质量规则

不负责：

- 项目级优先级决策
- 正式发布审批与运行期控制
- AI 横向权限策略

#### 2.3 发布运行平台

负责回答：

- 什么可以发
- 如何发
- 线上是否稳定
- 何时暂停、何时回滚、谁来响应

边界内对象：

- 发布计划
- 配置
- 环境
- 发布执行记录
- 灰度批次
- 指标与告警
- 日志索引
- 事故记录
- 变更记录
- 值守映射

不负责：

- 需求拆解与任务编排
- 代码正文管理
- AI 知识沉淀模板本身

#### 2.4 AI 编排与知识平台

负责回答：

- AI 该用什么角色、模型、技能、策略
- AI 当前能看到什么、能做什么、不能做什么
- AI 生成的中间记忆和知识资产如何沉淀

边界内对象：

- Prompt/策略
- Agent 模板
- Skill/工具编排
- 上下文快照
- 模型路由
- 权限策略
- AI 审计记录
- 组织级知识沉淀规则

不负责：

- 替代前三个平台成为业务事实主库
- 持有唯一的项目/代码/发布真相

### 3. 四个平台的主数据划分

我建议把“谁是 system of record”先固定下来，否则后面事件流一定会混乱。

| 对象类型 | 主数据平台 | 说明 |
|----------|------------|------|
| 项目、产品、需求、任务、缺陷、验收 | 研发协作平台 | 这是业务协作事实源 |
| 仓库、代码、PR、接口、测试用例、测试结果、制品 | 工程执行平台 | 这是工程事实源 |
| 发布单、环境、配置、灰度、监控、事故、回滚 | 发布运行平台 | 这是运行控制事实源 |
| Prompt、Agent 模板、Skill、模型策略、AI 快照 | AI 编排与知识平台 | 这是 AI 控制事实源 |

我建议再加一条硬规则：

> **AI 平台可以聚合视图，但不应偷偷成为项目、代码、发布等核心事实的唯一主库。**

### 4. 平台之间最小对象映射关系

我建议至少固定下面这组主映射：

```text
研发协作平台
  requirement_id
    -> task_id
    -> acceptance_id

工程执行平台
  task_id
    -> repo / branch / pr / test_result / artifact_version

发布运行平台
  artifact_version
    -> release_id
    -> rollout_batch
    -> observation_window
    -> rollback_record

AI 编排与知识平台
  project_id / requirement_id / task_id / release_id
    -> agent_context / prompt_policy / audit_trace
```

这样四个平台不是“各玩各的”，而是通过稳定 ID 链接成主链。

### 5. 事件流应该怎么设计

我建议不要让四个平台靠“轮询查状态”来协作，而应采用事件驱动主链。

最小事件流可以先固定为：

#### 5.1 协作平台 -> 工程执行平台

```text
REQUIREMENT_APPROVED
TASK_PLANNED
TASK_ASSIGNED
ACCEPTANCE_SCOPE_CONFIRMED
```

作用：

- 驱动代码实现、测试生成、工程任务开工

#### 5.2 工程执行平台 -> 协作平台

```text
PR_OPENED
TASK_BUILD_PASSED
TASK_VERIFIED
TASK_DELIVERED
INTEGRATION_PASSED
```

作用：

- 回写任务状态、可送验状态、阶段完成判断

#### 5.3 工程执行平台 -> 发布运行平台

```text
ARTIFACT_BUILT
ARTIFACT_SIGNED
RELEASE_CANDIDATE_READY
QUALITY_GATE_PASSED
```

作用：

- 驱动发布计划生成与 precheck 初始化

#### 5.4 发布运行平台 -> 协作平台 / AI 平台

```text
RELEASE_STARTED
ROLLOUT_BATCH_ADVANCED
RELEASE_HELD
ROLLBACK_TRIGGERED
RELEASE_COMPLETED
INCIDENT_OPENED
```

作用：

- 回写项目状态、通知相关角色、驱动 AI 切换策略

#### 5.5 AI 平台 -> 其他平台

我建议 AI 平台原则上**少做业务主事件源**，多做：

- 建议事件
- 自动化执行事件
- 审计事件

例如：

```text
AI_PLAN_PROPOSED
AI_TASK_DRAFTED
AI_CODE_CHANGE_SUBMITTED
AI_RELEASE_CHECK_COMPLETED
AI_AUDIT_LOG_WRITTEN
```

### 6. 权限流应该怎么设计

我建议权限流必须采用“双层控制”：

```text
组织/角色权限
    +
AI 执行权限
    =
最终可执行权限
```

也就是说：

- 用户/角色本身有什么权限，由组织与权限体系决定
- AI 在该角色下能否自动执行，由 AI 策略层二次约束

#### 6.1 组织权限层

来自：

- 用户与组织库
- 审批链
- 项目成员关系
- 值守责任映射

回答：

- 谁能看项目
- 谁能改需求
- 谁能合并代码
- 谁能批准发布
- 谁能执行回滚

#### 6.2 AI 执行权限层

来自：

- Agent 模板
- Tool 权限配置
- Prompt/策略规则
- 合规与审计策略

回答：

- AI 能否只读还是可写
- AI 能否提 PR 还是能直接合并
- AI 能否发起发布还是只能做 precheck
- AI 能否执行回滚还是只能生成建议

我建议固定一条原则：

> **高风险动作默认“人批准、AI执行”或“AI建议、人执行”，不要默认让 AI 单独闭环。**

### 7. 一个最小权限矩阵示例

| 动作 | 协作平台 | 工程执行平台 | 发布运行平台 | AI 默认权限 |
|------|----------|--------------|--------------|-------------|
| 读项目/需求/任务 | 允许 | 只读引用 | 只读引用 | 允许 |

| 发起发布 | 不负责 | 可建议 | 允许 | 默认建议态 |
| 执行回滚 | 不负责 | 不负责 | 高权限 | 默认不允许 |
| 写复盘/知识沉淀 | 允许 | 可附带生成 | 可附带生成 | 允许 |

## 十八、这一轮的最小结论

基于当前这一版，我建议先把 `3+1` 平台设计收敛成下面这些最小结论：

- 三个业务/工程/运行平台负责事实源，AI 平台负责控制平面与知识平面
- 主数据必须先明确 system of record，再谈 AI 聚合视图
- 平台协同应优先依赖事件流，而不是让 AI 直接到处轮询和拼凑状态
- 权限必须拆成“组织权限”与“AI 执行权限”两层
- 高风险动作默认不让 AI 独立闭环，而应走受控审批链
- 当前体系最适合的产品方向，是“多平台事实源 + AI 横向编排”的研发操作系统

## 十九、system of record、索引层、缓存层与 AI 视图层的固定规则

如果要让这套 `3+1` 平台长期可运行，我建议把对象分层再固定一层：

### 1. 四类数据层角色

| 层级 | 定义 | 是否允许成为唯一事实源 | 典型承载平台 |
|------|------|------------------------|--------------|
| system of record | 业务或工程或运行的正式主数据 | 允许 | 研发协作平台 / 工程执行平台 / 发布运行平台 |
| index / reference layer | 只保存 ID、索引、关联关系、跳转信息 | 不允许 | 三个平台均可，AI 平台也可 |
| cache / materialized view | 为了查询、检索、编排、分析而生成的投影视图 | 不允许 | AI 编排与知识平台为主 |
| AI working memory / snapshot | 为了阶段编排、Agent 执行、上下文冻结而形成的快照与契约 | 不允许 | AI 编排与知识平台 |

### 2. 一组必须钉死的硬规则

- `项目 / 需求 / 任务 / 缺陷 / 验收结论` 的正式状态，以研发协作平台为准
- `代码 / 分支 / PR / 接口 / 测试证据 / 制品` 的正式状态，以工程执行平台为准
- `发布计划 / 发布执行 / 灰度批次 / 观察窗 / 回滚 / 事故` 的正式状态，以发布运行平台为准
- `entry_contract`、`handoff_package`、`exit_packet`、`AI 快照` 可以放在 AI 平台，但默认只能引用事实，不应偷偷改写前三个平台的主事实
- AI 平台中的对象，只要内容来自前三个平台，就必须带 `source_*_id`、`source_version`、`snapshot_at`、`freshness_status`

### 3. 哪些对象天生更像 AI 视图层

我建议把下面这类对象统一视为 **AI 控制平面对象**，而不是业务事实主对象：

- 各阶段 `*_entry_contract`
- 各阶段 `*_handoff_package`、`*_exit_packet`
- `goal_alignment_brief`
- `stage2_gate_evaluation`
- `stage5_runtime_snapshot`
- Agent 执行产生的上下文快照、策略建议、审计轨迹

这些对象的职责是：

- 冻结某个时点的可消费上下文
- 把上游事实翻译成下游运行规则
- 为 AI 和角色协同提供受控入口
- 保留审计链，而不是替代正式主库

### 4. 一组推荐同步原则

#### 4.1 引用优先，不全文复制

能传 `id + version + status` 的，不复制全文。

例如：

- `stage3_entry_contract` 引用 `implementation_entry_packet`、`task_tree`、`ownership_map`
- `stage4_entry_contract` 引用 `acceptance_entry_packet`、`stage3_completion_report`
- `stage5_entry_contract` 引用 `release_entry_packet`、`stage4_exit_packet`

#### 4.2 过 gate 时允许做“冻结快照”

一旦进入阶段门禁或执行窗口，可以在 AI 平台生成快照，但要明确它是：

- 某一时刻的冻结视图
- 为下游执行服务
- 允许过期
- 不能反向覆盖事实源

#### 4.3 状态回写必须回到事实源

例如：

- `TASK_VERIFIED` 要回写工程执行平台与研发协作平台的任务状态
- `RELEASE_HELD`、`ROLLBACK_TRIGGERED` 要回写发布运行平台，并同步给协作平台项目状态
- `ACCEPTANCE_PASSED` 要回写研发协作平台的正式验收结论

#### 4.4 AI 视图失效要可判定

AI 平台中的快照对象建议至少带：

- `snapshot_at`
- `source_event_offset` 或 `source_version`
- `stale_after`
- `refresh_required_when`

这样 AI 才不会拿旧快照继续做新决策。

## 二十一、system of record 与 AI 视图层之间的同步机制

上面的挂载关系如果要真正跑起来，我建议同步机制也固定成一套标准动作，而不是“想到什么同步什么”。

### 1. 同步分成四种动作

| 同步动作 | 适用对象 | 谁发起 | 目标 |
|----------|----------|--------|------|
| event sync | 状态变化类对象 | 事实源平台 | 驱动下游感知变更 |
| snapshot sync | 阶段交接包、契约、出口包 | AI 平台 | 固化某时点可消费上下文 |
| status backwrite | 结论回写类对象 | 下游事实源或 AI 编排 | 回写上游协作状态 |
| audit sync | 高风险动作与 AI 行为 | AI 平台 / 发布平台 | 留痕与审计 |

### 2. 最小同步主链

#### 2.1 协作到工程

```text
stage1_approval_record / version_scope_brief / prd_final
-> stage2 方案与任务拆解
-> TASK_PLANNED / IMPLEMENTATION_READY
```

#### 2.2 工程到协作

```text
task_delivery_record / verification_result / integration_report
-> stage3_completion_report
-> 协作平台更新任务、缺陷、送验状态
```

#### 2.3 工程到发布

```text
release_readiness_report 所依赖的工程证据
<- artifact / test_result / quality_gate
-> release_entry_packet
-> stage5 runtime initialization
```

#### 2.4 发布到协作与 AI

```text
release_checkpoint / release_hold_record / rollback_execution_record / release_completion_record
-> 协作平台更新项目发布状态
-> AI 平台刷新 stage5_runtime_snapshot / stage5_exit_packet
```

### 3. 各类对象的同步建议

#### 3.1 `entry_contract` 类

- 主存放在 AI 平台
- 由上游 `entry_packet` 与事实源对象编译生成
- 一旦进入 `active`，默认冻结当前版本引用
- 若上游事实变更，不直接偷偷改 contract，而是触发 `rebuild_required`

#### 3.2 `handoff_package` / `exit_packet` 类

- 主存放在 AI 平台
- 只保存下游真正要消费的最小闭包
- 必须指向上游正式 `report/result/record`
- 下游只消费已出现在 `included_artifacts` 中的正式对象

#### 3.3 运行时主对象类

- 任务实例、验收用例、发布批次等，必须写回各自事实源平台
- AI 可读取、总结、建议，但不应独占保存唯一状态
- 高风险状态变化必须伴随审计事件

#### 3.4 结论与记录类

- `acceptance_result` 回写研发协作平台
- `release_readiness_report`、`release_completion_record` 回写发布运行平台
- `rollback_execution_record` 既是运行事实，也应同步到协作平台供项目状态可见

### 4. 我建议固定的字段级约束

AI 平台中凡是引用事实源对象的快照，建议统一带上：

- `source_object_type`
- `source_object_id`
- `source_platform`
- `source_version`
- `snapshot_at`
- `freshness_status`
- `rebuild_required`
- `last_event_id`

这样后面无论是 Agent 编排、自动刷新、审计回放，还是跨平台排障，都会稳定很多。

### 5. 快照恢复与工作记录的云端存储建议

对于你刚才提的建议，我的判断是：**可以放云端，而且应该放云端，但必须做成分层存储 + 策略可配置。**

我更建议采用下面这组归属规则：

| 内容类型 | 首选存放位置 | 辅助存放位置 | 原因 |
|----------|--------------|--------------|------|
| 会话快照、阶段快照、恢复包 | AI 编排与知识平台 / 上下文快照库 | 本地缓存 | 这是 AI 恢复上下文的主场景 |
| 一般工作记录、Agent 执行动作记录 | AI 编排与知识平台 / worklog 子域 | 合规/审计库 | 先服务恢复与协同，再按风险同步审计 |
| 高风险操作记录 | 合规/审计库 | AI 平台引用索引 | 审计可信度必须更高 |
| 发布/回滚/事故相关记录 | 发布运行平台 | AI 平台快照引用 | 这些本质上属于运行事实 |
| 本地临时草稿、短期记忆 | 本地工作区或本地缓存 | 可选异步上云 | 不必所有临时上下文都直接进云 |

我建议再固定一条原则：

> **恢复能力优先放 AI 平台，可信审计优先放审计平台，运行事实优先放运行平台。**

### 6. 建议做成可配置策略

我完全同意做成可配置的，而且这个配置最好不是一个总开关，而是分层策略：

#### 6.1 按对象类型配置

- `snapshot_policy`：快照是否上云、何时上云、保留多久
- `worklog_policy`：工作记录是否全文保存，还是只存摘要和引用
- `audit_policy`：哪些动作必须进审计库
- `recovery_policy`：恢复时允许恢复到什么粒度

#### 6.2 按作用域配置

- 组织级：默认规则、合规红线、最长保留期
- 项目级：是否允许云端恢复、是否允许跨成员共享工作记录
- 环境级：开发 / 测试 / 生产使用不同策略
- 角色级：Assistant、Tech Lead、Dev、Ops 的记录范围不同

#### 6.3 按敏感度配置

- 普通项目：允许云端保存完整快照
- 敏感项目：只允许保存结构化摘要、对象引用、脱敏结果
- 高保密项目：仅本地保存全文，云端只保留恢复索引和审计元数据

#### 6.4 按触发时机配置

- 每次关键步骤自动快照
- 仅在阶段切换时快照
- 仅在人工点击“保存恢复点”时快照
- 出错、回滚、切角色前强制落一份恢复点

### 7. 四类正式配置对象建议

如果后面要把“可配置”真正产品化，我建议不要只做零散配置项，而是正式抽成四类配置对象：

#### 7.1 `snapshot_policy`

用于定义“什么快照可以保存、保存到哪里、保留多久、谁能恢复”。

建议最小字段：

- `policy_id`
- `scope_type`：`org` / `project` / `environment` / `role`
- `scope_id`
- `snapshot_targets`：例如 `session_state`、`stage_context`、`release_runtime`
- `storage_mode`：`local_only` / `cloud_only` / `local_and_cloud`
- `sync_mode`：`realtime` / `checkpoint_only` / `manual`
- `retention_days`
- `encryption_level`
- `masking_required`
- `allowed_restore_roles`
- `enabled`

它回答的是：

- 哪些上下文允许形成恢复点
- 恢复点是否允许上云
- 恢复点保存多久
- 谁能把现场恢复回来

#### 7.2 `worklog_policy`

用于定义“工作记录记到什么程度、是否保存全文、是否允许共享”。

建议最小字段：

- `policy_id`
- `scope_type`
- `scope_id`
- `record_targets`：例如 `agent_action`、`decision_note`、`handoff_note`、`tool_trace`
- `content_level`：`metadata_only` / `summary_only` / `full_content`
- `share_mode`：`private` / `project_shared` / `org_shared`
- `retention_days`
- `sensitive_filter_profile`
- `index_only_for_cloud`
- `enabled`

它回答的是：

- 工作记录存元数据、摘要还是全文
- 记录是个人可见、项目共享还是组织共享
- 敏感信息是否必须过滤后再入云

#### 7.3 `audit_policy`

用于定义“哪些动作必须进审计、审计到什么粒度、保留多久、谁可查看”。

建议最小字段：

- `policy_id`
- `scope_type`
- `scope_id`
- `audit_targets`：例如 `release_action`、`rollback_action`、`permission_escalation`、`secret_access`
- `audit_level`：`metadata` / `summary` / `full_trace`
- `required_for_roles`
- `required_for_envs`
- `retention_days`
- `tamper_proof_required`
- `viewer_roles`
- `enabled`

它回答的是：

- 哪些动作必须保留可信审计链
- 哪些环境或角色必须强化审计
- 审计记录是否需要防篡改与长期保留

#### 7.4 `recovery_policy`

用于定义“恢复时能恢复到哪一层、允许恢复哪些对象、恢复前是否需要审批”。

建议最小字段：

- `policy_id`
- `scope_type`
- `scope_id`
- `recovery_targets`：例如 `session_resume`、`stage_resume`、`release_resume`
- `restore_granularity`：`index_only` / `summary` / `full_context`
- `approval_mode`：`self` / `lead_approval` / `security_approval`
- `cross_member_restore_allowed`
- `local_fallback_required`
- `integrity_check_required`
- `max_restore_age`
- `enabled`

它回答的是：

- 能恢复会话，还是能恢复到阶段级、发布级现场
- 恢复前是否要审批
- 是否允许跨成员接手并恢复他人的工作现场

#### 7.5 这四类对象之间的关系

我建议它们之间保持下面这组职责分工：

- `snapshot_policy` 决定“存什么快照”
- `worklog_policy` 决定“记什么过程”
- `audit_policy` 决定“哪些必须成为可信留痕”
- `recovery_policy` 决定“出了中断后怎么恢复”

可以把它们理解为：

```text
snapshot_policy  -> 决定保存恢复点
worklog_policy   -> 决定记录过程与上下文说明
 audit_policy    -> 决定关键动作进入可信审计链
recovery_policy  -> 决定允许如何恢复与接管
```

如果后面要落平台模块，我建议这四类对象主挂载在 `AI 编排与知识平台`，但其中：

- `audit_policy` 应与 `合规/审计库` 强绑定
- `recovery_policy` 在发布场景下应与 `发布运行平台` 联动

### 8. AI 开发数据流当前是否已保留到云端

如果问“当前 AI 开发过程中的数据流，是否已经被系统性保留到云端”，我建议把答案拆成三层，不要直接回答是或否。

#### 8.1 先区分三种状态

| 状态 | 定义 | 说明 |
|------|------|------|
| 已确认本地保存 | 可以明确看到本地持久化证据 | 例如本地 transcript、终端日志、工作区文件修改结果 |
| 已确认云端保存 | 可以明确确认已写入云端系统或云端事实源 | 需要有明确系统证据，而不是设计推断 |
| 仅完成架构设计 | 文档中已定义目标归属与同步策略，但尚未证明已真正落库 | 当前很多 AI 平台对象更接近这个状态 |

#### 8.2 对当前系统更谨慎的判断

基于当前可见信息，我更建议下这个判断：

- `AI 开发数据流并非完全无保存`
- `当前可以确认存在本地留痕`
- `但不能仅凭设计文档就断言已经完整上云`
- `是否已上云，必须看是否存在实际云端系统写入证据`

也就是说：

> **当前更像是“本地已保存，云端应当可保存，但是否已系统性上云仍需逐项核实”。**

#### 8.3 一张当前状态判断表

| 数据流类型 | 当前更可能的状态 | 建议归属 | 判断理由 |
|------------|------------------|----------|----------|
| 对话 transcript | 已确认本地保存 | AI 平台 / worklog 子域（目标态） | 当前能看到本地 transcript 证据，但未直接证明云端写入 |
| 终端执行日志 | 已确认本地保存 | AI 平台审计索引 / 审计库（目标态） | 当前可见本地 terminal log，但未证明云端归档 |
| 本地文件修改结果 | 已确认本地保存 | 协作平台 / 工程平台 / 知识库（按对象类型） | 结果落在本地工作区，可进一步回写云端平台 |
| 阶段快照 / 恢复包 | 仅完成架构设计 | AI 平台 / 上下文快照库 | 已定义归属，但未看到真实落库证据 |
| 工作记录 / worklog | 仅完成架构设计 | AI 平台 / worklog 子域 | 已建议云端保存与可配置策略，但未证明已启用 |
| 高风险审计记录 | 不可直接确认 | 合规/审计库 | 设计上应存在，但当前缺直接证据 |
| 发布/回滚/事故相关 AI 记录 | 不可直接确认 | 发布运行平台 + 审计库 | 理论上应写入运行事实，但当前仍需逐项核查 |

#### 8.4 一张“本地 / 云端 / 未落地”逐项核查表

为了避免把“能看到本地文件”误认为“已经系统性上云”，我建议再固定一张更适合落地排查的核查表：

| 数据流项 | 本地状态 | 云端状态 | 当前结论 | 说明 |
|----------|----------|----------|----------|------|
| 对话 transcript | 已确认 | 待核实 | 本地已保存，云端未知 | 当前能看到本地 transcript 文件，但未见云端对象证据 |
| 终端执行日志 | 已确认 | 待核实 | 本地已保存，云端未知 | 当前能看到本地 terminal log 文件，但未见云端归档证据 |
| 文档修改结果 | 已确认 | 待核实 | 本地已保存，结果可回写云端 | 工作区文件已持久化，但是否同步到协作/知识平台要看实际回写链路 |
| 工具调用轨迹 | 部分可见 | 待核实 | 本地可见片段，云端未知 | transcript 中可看到工具调用历史，但是否形成正式云端审计对象未知 |
| todo / 过程编排记录 | 部分可见 | 待核实 | 本地过程可见，云端未知 | 当前会话里能看到 todo 轨迹，但未见对应云端 worklog 实例 |
| 阶段快照 / 恢复包 | 未见本地正式对象 | 未见云端实例 | 当前偏“未落地” | 只有架构定义，尚未看到真实 snapshot object |
| worklog 正式对象 | 未见本地正式对象 | 未见云端实例 | 当前偏“未落地” | 已完成设计，但尚未看到正式对象实例或存储后端 |
| 高风险审计记录 | 待核实 | 待核实 | 需要单独核查 | 理论上应进入审计链，但当前缺本地或云端的直接证明 |
| 发布 / 回滚 / 事故 AI 记录 | 待核实 | 待核实 | 需要单独核查 | 理论上应进入发布运行平台或审计库，但当前无实例证据 |

我建议这张表后续就作为判断口径：

- `本地状态 = 已确认`，只说明看到了本地持久化证据
- `云端状态 = 已确认`，必须说明已经看到了云端对象或回写证据
- `当前偏未落地`，说明文档中已设计，但未见真实实例

#### 8.5 什么才算“真的已经上云”

我建议至少满足下面任一条，才能把某类数据流标记为“已确认云端保存”：

- 已知存在对应云端库，并能查到对象实例
- 已知存在 API / 事件回写链路，并能看到成功写入证据
- 已知存在审计记录、对象 ID、版本号、时间戳等云端元数据
- 已知恢复流程明确依赖云端对象，而不是只依赖本地缓存

如果这些证据都没有，就最多只能写成：

- `设计上应上云`
- `目标上归属于云端某平台`
- `当前是否已启用未知`

#### 8.6 我建议的表达口径

因此，在当前体系里，比较严谨的表达应是：

- `本地留痕能力已经可以确认存在`
- `云端归属与同步机制已经完成架构设计`
- `哪些数据流已真正进入云端，当前还需要一张逐项核实表`
- `不能把“已设计”误写成“已落地”`

### 9. 这一轮补充后的最小结论

到这里我建议把整套体系先收敛成下面几条：

- 前三个平台负责正式事实，AI 平台负责契约、快照、策略、审计
- `entry_packet -> entry_contract -> runtime -> result/record -> exit_packet` 这条同构主链，可以稳定挂到 `3+1` 平台上
- 阶段交接对象可以放在 AI 平台，但必须是“引用事实的受控快照”，不是新的事实主库
- 快照恢复与一般工作记录，适合主存于 AI 平台，但高风险记录要同步到审计或运行平台
- 发布执行相关正式运行对象，应明确收敛到发布运行平台，而不是散落在协作文档和聊天上下文中
- 跨平台同步应优先依赖事件和版本引用，而不是全文复制和人工对账
- 快照、恢复包、工作记录不应写死为单一存储方式，而应支持按项目、环境、敏感度做策略化配置
- 对“AI 数据流是否已上云”的表述，必须区分“已本地保存”“已云端保存”“仅完成设计”三种状态

如果继续下一步，我建议再往下展开两件事：

1. `把 AI 数据流逐项展开成“本地 / 云端 / 未落地”核查表`
2. `把 snapshot_policy / worklog_policy / audit_policy / recovery_policy 继续展开成字段级配置表`

### 10. 循环判断、回退与全流程完成记录

如果进一步追问“当前流程已经设计出来了，但中间可能发生循环判断、回退、reopen、hold、rollback，那么整个流程本身是否被完整记录了”，我建议把答案明确分成两层：

#### 10.1 阶段内与阶段间的局部闭环，其实已经基本有了

当前 formalization 里，阶段级完成与回退语义已经比较完整：

| 阶段 | 已有正式对象 | 能记录什么 |
|------|--------------|------------|
| 阶段 0 | `assistant_startup_handoff`、`goal_alignment_brief` | 启动交接、目标校准、是否进入阶段 1 |
| 阶段 1 | `stage1_handoff_package`、`stage1_approval_record` | 需求收敛结果、用户批准、是否允许进入阶段 2 |
| 阶段 2 | `stage2_gate_evaluation`、`stage2_handoff_package`、`implementation_entry_packet` | readiness / gate 判断、失败回退路由、是否允许进入阶段 3 |
| 阶段 3 | `task_state`、`blocker_record`、`rollback_decision`、`stage3_completion_report` | reopen、阻塞、局部回退、阶段完成判断 |
| 阶段 4 | `acceptance_result`、`release_readiness_report`、`final_signoff_record`、`stage4_exit_packet` | 验收通过/退回、发布准备门禁、最终签发 |
| 阶段 5 | `release_hold_record`、`rollback_decision_record`、`rollback_execution_record`、`release_completion_record`、`stage5_exit_packet` | hold、rollback、发布闭环、阶段出口 |

也就是说：

- `阶段内完成记录` 基本已经有了
- `阶段间出口对象` 也基本已经有了
- `回退`、`blocked`、`rerun`、`rollback` 在多个阶段都已被 formalize

#### 10.2 但“全流程是否已经完成记录”这件事，当前还不算完整

我更建议下一个更严格的判断：

> **当前已经形成“分阶段完成记录”，但还没有形成一个贯穿阶段 0 到阶段 5、能够吸收循环判断与回退链路的“全流程完成记录对象”。**

现在缺的不是单个阶段的 completion，而是一个能统一回答下面问题的顶层对象：

- 这一次流程实例从阶段 0 到阶段 5 一共经历了哪些阶段切换
- 哪些节点发生了 `blocked`、`rerun_alignment`、`reopen`、`hold`、`rollback`
- 某次回退是阶段内修复，还是跨阶段退回
- 最终是正常完成、带 followup 完成、回滚完成，还是中途终止
- 整个流程的正式结案结论是什么

#### 10.3 我建议补一个顶层对象：`workflow_completion_record`

如果要把“全流程完成记录”补齐，我建议新增一个顶层正式对象：`workflow_completion_record`。

它不是替代各阶段对象，而是：

- 聚合阶段级 completion / exit 结果
- 显式记录跨阶段切换与回退链
- 给整个项目工作流一个正式结案结论

建议最小结构可以先收敛成：

```yaml
workflow_completion_record:
  workflow_id: wf-001
  project_id: proj-001
  workflow_type: product_delivery
  workflow_status: running | completed | terminated | rolled_back

  current_stage: stage0 | stage1 | stage2 | stage3 | stage4 | stage5
  final_decision: success | partial_success | rolled_back | terminated | rerouted
  final_reason: "阶段5发布回滚完成，本轮流程正式结案，待重新规划下一次发布"

  stage_transitions:
    - from_stage: stage1
      to_stage: stage2
      transition_result: passed
      based_on_record: stage1_approval_record
    - from_stage: stage2
      to_stage: stage1
      transition_result: returned
      based_on_record: stage2_gate_evaluation
      return_reason: "阶段1范围前提被推翻"

  loop_events:
    - event_type: rerun_alignment | reopen | blocked | hold | rollback
      stage: stage3
      related_record: blocker_record
      disposition: resolved | escalated | caused_return

  attached_stage_records:
    - assistant_startup_handoff
    - stage1_approval_record
    - stage2_gate_evaluation
    - stage3_completion_report
    - acceptance_result
    - release_completion_record
    - stage5_exit_packet

  closure_status: draft | finalized
  closure_at: 2026-04-19T20:00:00Z
```

#### 10.4 `workflow_completion_record` 的字段级正式定义建议

如果继续把它推进到正式契约层，我建议至少把字段语义固定到下面这版。

```yaml
workflow_completion_record:
  workflow_id: string
  project_id: string
  workflow_type: product_delivery | issue_fix | ops_change | research_spike
  workflow_status: draft | running | completed | terminated | rolled_back | rerouted

  initiated_by: assistant | tech_lead | system
  started_at: datetime
  current_stage: stage0 | stage1 | stage2 | stage3 | stage4 | stage5
  current_owner_role: assistant | tech_lead | architect | developer | tester | devops | oncall

  final_decision: success | partial_success | rolled_back | terminated | rerouted
  final_reason: string
  final_stage: stage0 | stage1 | stage2 | stage3 | stage4 | stage5

  stage_transitions:
    - transition_id: string
      from_stage: stage0 | stage1 | stage2 | stage3 | stage4 | stage5
      to_stage: stage0 | stage1 | stage2 | stage3 | stage4 | stage5
      transition_type: forward | return | reroute | resume
      transition_result: passed | returned | blocked | resumed | cancelled
      based_on_record_type: string
      based_on_record_id: string
      triggered_by: user | assistant | tech_lead | gate | runtime_signal | system
      transition_reason: string
      occurred_at: datetime

  loop_events:
    - event_id: string
      event_type: rerun_alignment | reopen | blocked | hold | rollback | retry
      stage: stage0 | stage1 | stage2 | stage3 | stage4 | stage5
      related_record_type: string
      related_record_id: string
      disposition: resolved | escalated | caused_return | caused_reroute | ended_workflow
      event_reason: string
      opened_at: datetime
      closed_at: datetime | null

  attached_stage_records:
    - record_type: string
      record_id: string
      source_platform: collaboration | engineering | release_runtime | ai_control_plane
      record_status: active | superseded | closed

  closure_checks:
    all_required_stage_records_present: boolean
    no_open_blocking_loop_events: boolean
    final_route_confirmed: boolean
    followups_bound: boolean
    audit_trace_complete: boolean

  closure_status: draft | review_ready | finalized
  closure_reviewer: tech_lead | release_manager | system
  closure_at: datetime
```

#### 10.5 字段应该如何理解

我建议把最关键字段的职责写死：

- `workflow_status`：表示流程实例当前总状态，而不是某个阶段的局部状态
- `final_decision`：表示这次流程最终是成功、部分成功、回滚收口、终止还是改道
- `stage_transitions`：记录正式阶段切换，不记录每个细碎动作
- `loop_events`：专门记录循环判断、回退、重开、hold、rollback 这类会改变主链走向的事件
- `attached_stage_records`：只挂正式阶段记录，不把聊天碎片直接塞进来
- `closure_checks`：确保“流程结案”不是拍脑袋，而是满足最小闭环条件

#### 10.6 我建议先固定的状态语义

##### `workflow_status`

- `draft`：流程实例已创建，但尚未正式进入主链
- `running`：流程仍在推进，可能包含回退、重试、挂起后的恢复
- `completed`：流程已完成，并形成正式结案记录
- `terminated`：流程被正式终止，不再继续当前链路
- `rolled_back`：流程最终以回滚收口，属于正式结束态
- `rerouted`：流程没有按原主链走完，而是被正式改道到其他流程

##### `transition_type`

- `forward`：正常向下一阶段推进
- `return`：跨阶段退回上游
- `reroute`：切换到另一条流程主线
- `resume`：从 hold / blocked / interrupted 状态恢复

##### `transition_result`

- `passed`：切换成功
- `returned`：已正式退回
- `blocked`：尝试切换但被阻断
- `resumed`：恢复成功
- `cancelled`：本次切换请求被取消

##### `disposition`

- `resolved`：事件已在原阶段内消解
- `escalated`：事件升级处理，但未改变主链阶段
- `caused_return`：事件导致跨阶段退回
- `caused_reroute`：事件导致流程改道
- `ended_workflow`：事件直接导致流程终止或回滚收口

#### 10.7 与现有阶段对象的引用规则

我建议先固定几条硬规则：

- `workflow_completion_record` 只引用正式阶段对象，不直接引用聊天消息片段
- 若某阶段对象被重开或 superseded，`attached_stage_records.record_status` 必须同步更新
- 一个阶段可以有多个 `loop_event`，但最终只能有一个进入 `final_decision` 主结论
- `stage_transitions` 记录的是“阶段边界切换”，不是阶段内所有细步状态机
- 阶段 5 的 `release_completion_record` 与全局 `workflow_completion_record` 可以并存，前者回答“发布是否闭环”，后者回答“整个项目流程是否闭环”

#### 10.8 一张统一回退路由图

我建议把当前体系中的“回退”先统一分成三层，不然很容易把所有退回都混成一个词：

- **阶段内回环**：同一阶段内部因为缺信息、评审未收敛、任务 reopen、hold 等，回到本阶段上游步骤继续处理
- **跨阶段退回**：某阶段发现上游前提失效，正式退回上一阶段或更早阶段重新形成基线
- **发布运行回滚**：阶段 5 中已经进入运行控制后，因为风险信号触发 rollback，属于运行态回滚而不是文档态回退

```text
统一回退路由图

阶段内回环
  stage1: scope draft -> clarification -> draft
  stage2: readiness fail -> solution/task/plan 修订 -> gate re-evaluate
  stage3: task reopen / blocker -> 原任务链继续推进
  stage4: acceptance issue -> 验收修订 / 重新验证
  stage5: hold -> 补观察 / 补处置 -> resume

跨阶段退回
  stage2 --前提被推翻--> stage1
  stage3 --范围/方案失效--> stage2
  stage4 --验收结论不成立--> stage3
  stage5 --发布前置条件失效--> stage4

发布运行回滚
  stage5 runtime
    -> precheck
    -> rollout_batch
    -> observation_window
    -> release_gate_signal
         green  -> continue
         yellow -> hold
         red    -> rollback_decision_record
                   -> rollback_execution_record
                   -> release_completion_record
                   -> stage5_exit_packet
```

这张图想表达的核心是：

- `reopen / blocked / clarification / hold` 更偏**阶段内回环**
- `return to previous stage` 更偏**跨阶段退回**
- `rollback` 只在阶段 5 运行态里使用，不能和普通“退回讨论”混成一个概念

#### 10.9 三类回退在对象上的落点

我建议再把三类路由与正式对象绑定清楚：

| 回退类型 | 典型触发 | 首选正式对象 | 是否改变主阶段 |
|----------|----------|--------------|----------------|
| 阶段内回环 | 澄清不足、评审未收敛、任务 reopen、hold | `blocker_record`、`review_comments`、`acceptance_issue`、`release_hold_record` | 通常不改变 |
| 跨阶段退回 | 上游范围/方案/验收前提失效 | `stage2_gate_evaluation`、`change_request`、`acceptance_result`、`stage_transitions` | 会改变 |
| 发布运行回滚 | `release_gate_signal = red`、事故、关键指标劣化 | `rollback_decision_record`、`rollback_execution_record`、`release_completion_record` | 不回到文档阶段，而是进入运行收口 |

对应到 `workflow_completion_record` 中：

- 阶段内回环优先记进 `loop_events`
- 跨阶段退回同时记进 `loop_events` 和 `stage_transitions`
- 发布运行回滚记进 `loop_events`，并以阶段 5 的正式 completion / exit 对象收口

#### 10.10 这个对象最适合挂在哪里

我建议主挂载在 `AI 编排与知识平台`，因为它本质上是：

- 跨阶段编排视图
- 流程实例轨迹视图
- 回退与循环判断的聚合审计视图

但它必须强引用前三个平台的正式事实：

- 协作平台里的批准、验收、变更结果
- 工程平台里的 gate、任务、缺陷、completion 结果
- 发布平台里的 hold、rollback、release completion 结果

#### 10.11 三类回退的事件流建议

如果再往下走到可执行编排层，我建议把三类回退统一映射成事件，而不是只留对象定义。

##### 阶段内回环事件流

```text
LOOP_TRIGGERED
-> LOOP_ASSESSED
-> LOOP_OPENED
-> LOOP_REWORK_IN_PROGRESS
-> LOOP_RESOLVED | LOOP_ESCALATED
```

典型映射：

- 阶段 1：澄清不足、评审未收敛
- 阶段 2：方案补齐、依赖未就绪、gate 待补材料
- 阶段 3：任务 `reopen`、`blocker_record`
- 阶段 4：`acceptance_issue` 修复后重新验证
- 阶段 5：`release_hold_record` 后进入补观察 / 补处置

##### 跨阶段退回事件流

```text
RETURN_TRIGGERED
-> RETURN_ASSESSED
-> RETURN_APPROVED
-> STAGE_TRANSITION_RECORDED(return)
-> UPSTREAM_STAGE_REOPENED
-> NEW_BASELINE_PREPARED
```

典型映射：

- 阶段 2 发现阶段 1 范围前提失效
- 阶段 3 发现阶段 2 方案或接口基线失效
- 阶段 4 发现阶段 3 交付事实不足以支撑验收
- 阶段 5 发现阶段 4 放行条件在执行前已失效

##### 发布运行回滚事件流

```text
RELEASE_SIGNAL_RED
-> ROLLBACK_DECISION_REQUESTED
-> ROLLBACK_DECISION_APPROVED
-> ROLLBACK_EXECUTING
-> ROLLBACK_COMPLETED
-> RELEASE_COMPLETION_FINALIZED
-> STAGE5_EXIT_PACKET_FINALIZED
```

这里要强调：

- 前两类事件主要改变的是“阶段推进路径”
- 发布回滚改变的是“运行结果与发布结论”
- 它不等同于重新回到阶段 4 文档讨论，而是运行态正式收口

#### 10.12 三类回退的状态机建议

我建议把状态机也按三层拆开，不要混用一个通用 `status`。

##### 阶段内回环状态机

```text
idle
-> triggered
-> assessing
-> in_rework
-> resolved
-> escalated
```

状态含义：

- `triggered`：发现问题，但尚未判断是否影响主链
- `assessing`：正在确认是局部修复还是要升级处理
- `in_rework`：已确认留在本阶段内修补
- `resolved`：已完成本阶段内闭环
- `escalated`：已超出本阶段处理能力，需要升级或退回

##### 跨阶段退回状态机

```text
none
-> requested
-> approved
-> returned
-> upstream_reopened
-> rebaselined
```

状态含义：

- `requested`：已提出正式退回请求
- `approved`：退回被确认，不再继续当前下游阶段
- `returned`：阶段边界已切换回上游
- `upstream_reopened`：上游阶段正式重开
- `rebaselined`：新基线已形成，可重新进入主链

##### 发布运行回滚状态机

```text
none
-> deciding
-> approved
-> executing
-> completed
-> closed
```

状态含义：

- `deciding`：正在形成 `rollback_decision_record`
- `approved`：回滚已正式批准
- `executing`：回滚动作执行中
- `completed`：回滚动作已完成
- `closed`：已形成 `release_completion_record` 与 `stage5_exit_packet`

#### 10.13 与 `workflow_completion_record` 的映射关系

我建议把事件流和总账对象的关系固定成下面这版：

| 语义层 | 正式记录位置 | 说明 |
|--------|--------------|------|
| 阶段内回环事件 | `loop_events` | 记录触发、处理、解决或升级 |
| 跨阶段退回事实 | `loop_events` + `stage_transitions` | 既要记录事件，也要记录阶段边界变化 |
| 发布运行回滚 | `loop_events` + 阶段 5 正式对象 | 既记总账，也要保留运行事实 |
| 全流程结案 | `final_decision` + `closure_checks` | 回答整个流程最终怎么收口 |

进一步约束建议为：

- 没有 `STAGE_TRANSITION_RECORDED(return)`，就不应宣称已经发生正式跨阶段退回
- 没有 `ROLLBACK_COMPLETED` 与 `release_completion_record`，就不应宣称发布回滚已经闭环
- 阶段内回环若最终升级为跨阶段退回，应从 `loop_events.disposition = caused_return` 进入 `stage_transitions`

#### 10.14 事件主题命名建议

如果要继续往平台实现靠，我建议先把事件主题命名规则固定，不然后面会出现同义词泛滥。

##### 10.14.1 命名总原则

我建议统一采用：

```text
DOMAIN_ACTION_RESULT
```

例如：

- `LOOP_TRIGGERED`
- `RETURN_APPROVED`
- `ROLLBACK_COMPLETED`
- `STAGE_TRANSITION_RECORDED`

同时固定三条规则：

- 事件名只表达**发生了什么**，不表达处理建议
- 一个事件主题只承载一类事实，不混入多个语义
- `return` 只用于跨阶段退回，`rollback` 只用于运行回滚，`reopen` 只用于阶段内重开

##### 10.14.2 三类回退的推荐事件主题

| 语义层 | 推荐事件主题 |
|--------|--------------|
| 阶段内回环 | `LOOP_TRIGGERED`、`LOOP_ASSESSED`、`LOOP_OPENED`、`LOOP_REWORK_IN_PROGRESS`、`LOOP_RESOLVED`、`LOOP_ESCALATED` |
| 跨阶段退回 | `RETURN_TRIGGERED`、`RETURN_ASSESSED`、`RETURN_APPROVED`、`STAGE_TRANSITION_RECORDED`、`UPSTREAM_STAGE_REOPENED`、`NEW_BASELINE_PREPARED` |
| 发布运行回滚 | `RELEASE_SIGNAL_RED`、`ROLLBACK_DECISION_REQUESTED`、`ROLLBACK_DECISION_APPROVED`、`ROLLBACK_EXECUTING`、`ROLLBACK_COMPLETED`、`RELEASE_COMPLETION_FINALIZED`、`STAGE5_EXIT_PACKET_FINALIZED` |

##### 10.14.3 我建议避免的坏命名

为了避免后期语义漂移，我建议显式避免下面这些过于模糊的名字：

- `PROCESS_ROLLBACK`
- `STAGE_FAILED`
- `GO_BACK`
- `RETRY_STAGE`
- `FLOW_EXCEPTION_HANDLED`

原因是这些命名会混淆：

- 是阶段内修补，还是跨阶段退回
- 是运行回滚，还是文档态退回
- 是事实事件，还是系统建议动作

#### 10.15 消费方规则建议

事件流一旦固定，我建议消费方也同步固定，不然事件虽然发出来了，语义仍然会漂。

##### 10.15.1 阶段内回环事件的消费方

| 事件类 | 主消费方 | 次消费方 | 作用 |
|--------|----------|----------|------|
| `LOOP_*` | AI 编排层 / 当前阶段 Runtime | 协作平台 | 驱动本阶段内修补、重开、重新评审 |

建议规则：

- `LOOP_TRIGGERED` 不自动改变主阶段
- `LOOP_ESCALATED` 才允许升级为跨阶段退回评估
- 阶段内回环默认由当前阶段 owner 消费，不直接广播给全平台

##### 10.15.2 跨阶段退回事件的消费方

| 事件类 | 主消费方 | 次消费方 | 作用 |
|--------|----------|----------|------|
| `RETURN_*` | AI 编排层 + 协作平台 | 工程平台 / 发布平台 | 正式改变阶段边界，重开上游基线 |

建议规则：

- 没有 `RETURN_APPROVED`，下游阶段不能标记为正式退回
- `STAGE_TRANSITION_RECORDED` 是阶段边界切换的事实事件
- `UPSTREAM_STAGE_REOPENED` 必须触发上游阶段对象重新进入活跃态

##### 10.15.3 发布运行回滚事件的消费方

| 事件类 | 主消费方 | 次消费方 | 作用 |
|--------|----------|----------|------|
| `ROLLBACK_*` / `RELEASE_*` | 发布运行平台 | AI 编排层 / 协作平台 / 审计平台 | 驱动回滚执行、发布收口、状态回写、审计留痕 |

建议规则：

- `RELEASE_SIGNAL_RED` 只表示信号，不等于已回滚
- `ROLLBACK_DECISION_APPROVED` 之后才能进入执行态
- `ROLLBACK_COMPLETED` 后仍需有 `RELEASE_COMPLETION_FINALIZED`
- `STAGE5_EXIT_PACKET_FINALIZED` 才表示阶段 5 的正式出口已形成

#### 10.16 事件字段建议

为了避免不同平台消费同一个主题时理解不一致，我建议事件至少带上下面这些通用字段：

- `event_id`
- `event_type`
- `workflow_id`
- `project_id`
- `stage`
- `related_record_type`
- `related_record_id`
- `triggered_by`
- `occurred_at`
- `source_platform`
- `correlation_id`

其中：

- `workflow_id` 用来串全流程
- `correlation_id` 用来串同一次回环、退回或回滚链
- `related_record_*` 用来追到正式对象，而不是只看消息文本

#### 10.17 后端 Topic 命名建议

如果要把事件主题真正落到事件总线，我建议在逻辑事件名之外，再固定一层后端 topic 命名。

##### 10.17.1 Topic 命名格式

我建议统一采用：

```text
{domain}.{entity}.{event_version}.{event_name}
```

例如：

- `workflow.loop.v1.triggered`
- `workflow.return.v1.approved`
- `release.rollback.v1.completed`
- `workflow.stage-transition.v1.recorded`

约束建议：

- `domain` 用来区分业务域，例如 `workflow`、`release`
- `entity` 用来区分对象族，例如 `loop`、`return`、`rollback`、`stage-transition`
- `event_version` 固定采用 `v1`、`v2` 这类版本位，避免字段升级时硬破坏消费方
- `event_name` 统一用过去式或结果式，如 `triggered`、`approved`、`completed`、`recorded`

##### 10.17.2 三类回退推荐 Topic 对照表

| 语义层 | 逻辑事件名 | 推荐 topic |
|--------|------------|------------|
| 阶段内回环 | `LOOP_TRIGGERED` | `workflow.loop.v1.triggered` |
| 阶段内回环 | `LOOP_OPENED` | `workflow.loop.v1.opened` |
| 阶段内回环 | `LOOP_RESOLVED` | `workflow.loop.v1.resolved` |
| 跨阶段退回 | `RETURN_TRIGGERED` | `workflow.return.v1.triggered` |
| 跨阶段退回 | `RETURN_APPROVED` | `workflow.return.v1.approved` |
| 跨阶段退回 | `STAGE_TRANSITION_RECORDED` | `workflow.stage-transition.v1.recorded` |
| 发布运行回滚 | `ROLLBACK_DECISION_REQUESTED` | `release.rollback.v1.decision-requested` |
| 发布运行回滚 | `ROLLBACK_EXECUTING` | `release.rollback.v1.executing` |
| 发布运行回滚 | `ROLLBACK_COMPLETED` | `release.rollback.v1.completed` |
| 发布运行回滚 | `RELEASE_COMPLETION_FINALIZED` | `release.completion.v1.finalized` |

##### 10.17.3 Topic 设计边界建议

我建议同时固定下面几条边界：

- 一个 topic 对应一种稳定事实，不把多个动作塞进同一个 topic
- command 和 event 分离，不能把“请求执行回滚”与“回滚已完成”发到同一 topic
- 跨平台广播 topic 用事实语义，本平台内部状态更新可以保留内部 topic，不强行暴露
- topic 名不要直接绑定具体产品名，避免后期平台替换时命名失效

#### 10.18 字段契约建议

我建议把字段分成 `公共头`、`语义体`、`审计体` 三层，这样不同平台接入时更稳。

##### 10.18.1 公共头字段

| 字段 | 是否必填 | 说明 |
|------|----------|------|
| `event_id` | 是 | 事件唯一 ID |
| `event_type` | 是 | 逻辑事件名，如 `ROLLBACK_COMPLETED` |
| `topic` | 是 | 实际投递 topic |
| `event_version` | 是 | 契约版本，如 `v1` |
| `occurred_at` | 是 | 事件发生时间 |
| `source_platform` | 是 | 事件来源平台 |
| `correlation_id` | 是 | 同一次处理链路关联 ID |
| `causation_id` | 否 | 直接上游事件 ID |

##### 10.18.2 语义体字段

| 字段 | 是否必填 | 说明 |
|------|----------|------|
| `workflow_id` | 是 | 全流程 ID |
| `project_id` | 是 | 项目 ID |
| `stage` | 条件必填 | 当前事件所属阶段 |
| `entity_type` | 是 | 对象类型，如 `loop_event`、`rollback_decision_record` |
| `entity_id` | 是 | 对象实例 ID |
| `related_record_type` | 否 | 关联正式记录类型 |
| `related_record_id` | 否 | 关联正式记录 ID |
| `triggered_by` | 是 | 触发者类型 |
| `reason_code` | 否 | 标准原因码 |
| `reason_text` | 否 | 补充原因说明 |

##### 10.18.3 审计体字段

| 字段 | 是否必填 | 说明 |
|------|----------|------|
| `operator_id` | 否 | 实际操作人 / 系统主体 |
| `tenant_id` | 否 | 租户 / 组织边界 |
| `trace_id` | 否 | 追踪链路 ID |
| `idempotency_key` | 否 | 幂等处理键 |
| `payload_schema_ref` | 否 | 契约文档引用 |

##### 10.18.4 字段契约补充约束

- `event_id` 全局唯一，不因重试而改变
- `idempotency_key` 用于消费方去重，不能直接拿 `event_id` 替代业务幂等语义
- `reason_code` 建议优先枚举化，`reason_text` 只做补充描述
- `entity_type/entity_id` 指向这次事件主语，`related_record_*` 指向被引用的正式对象

#### 10.19 订阅关系建议

除了 topic 和字段，我建议把订阅关系也提前固定成表，不然每个平台都会各订各的。

##### 10.19.1 订阅关系总表

| topic | 主发布方 | 主订阅方 | 次订阅方 | 订阅目的 |
|-------|----------|----------|----------|----------|
| `workflow.loop.v1.triggered` | AI 编排层 / 当前阶段 Runtime | 当前阶段执行器 | 协作平台 | 开启阶段内修补链 |
| `workflow.loop.v1.resolved` | 当前阶段 Runtime | AI 编排层 | 协作平台 | 回写阶段内回环已解决 |
| `workflow.return.v1.approved` | AI 编排层 / 协作平台 | 上游阶段 Runtime | 工程平台 / 发布平台 | 启动正式跨阶段退回 |
| `workflow.stage-transition.v1.recorded` | AI 编排层 | 协作平台 | 工程平台 / 审计平台 | 回写正式阶段边界变化 |
| `release.rollback.v1.decision-requested` | 发布运行平台 | 发布审批器 / 发布控制器 | AI 编排层 | 发起运行回滚决策 |
| `release.rollback.v1.completed` | 发布运行平台 | AI 编排层 / 协作平台 | 审计平台 | 回写回滚完成事实 |
| `release.completion.v1.finalized` | 发布运行平台 | 协作平台 / AI 编排层 | 审计平台 | 形成阶段 5 正式收口 |

##### 10.19.2 订阅规则建议

- 主订阅方必须能对该事件做出确定性处理，不能只是“看看”
- 次订阅方以同步视图、审计留痕、搜索索引更新为主
- 同一平台若既是发布方又是订阅方，需区分内部处理链与跨平台广播链
- 对外广播 topic 应只发布正式事实，不发布临时草稿态噪音

#### 10.20 `workflow_completion_record` 的平台模块映射建议

如果继续往实现层落，我建议先把这个对象拆成“谁维护总账、谁提供事实、谁负责写入触发”。

##### 10.20.1 模块挂载建议

| 平台 | 模块 | 对 `workflow_completion_record` 的职责 | 是否主写入点 |
|------|------|--------------------------------------|--------------|
| AI 编排与知识平台 | `workflow_orchestrator` | 持有流程实例主视图、汇总阶段切换、编排回退与结案 | 是 |
| AI 编排与知识平台 | `workflow_ledger` | 存储 `workflow_completion_record` 正式版本与快照历史 | 是 |
| 研发协作平台 | `stage_fact_service` | 提供 `stage0~stage4` 正式记录引用与状态校验 | 否 |
| 工程执行平台 | `engineering_fact_service` | 提供任务、测试、构建、验收前工程事实 | 否 |
| 发布运行平台 | `release_runtime_service` | 提供 `release_completion_record`、`rollback_*`、`stage5_exit_packet` 等运行事实 | 否 |
| 审计/合规域 | `audit_sink` | 接收结案与关键迁移副本，形成审计留痕 | 否 |

我建议把职责边界写死成：

- `workflow_orchestrator` 负责拼装总账，但不自造业务事实
- 各平台事实服务只负责返回自己域内正式记录，不负责拼全流程结案对象
- `workflow_ledger` 是 `workflow_completion_record` 的正式落库点，但不是项目、代码、发布事实的主库

##### 10.20.2 模块间引用关系

```text
研发协作平台 / 工程执行平台 / 发布运行平台
  -> 提供正式阶段事实与运行事实
AI workflow_orchestrator
  -> 校验阶段切换与结案条件
  -> 生成 workflow_completion_record
AI workflow_ledger
  -> 持久化正式总账版本
审计域
  -> 接收 finalized 副本与关键迁移事件
```

#### 10.21 写入时机建议

我建议不要等到“整个流程最后一刻”才写这个对象，而是采用“持续补账 + 结案定版”的方式。

##### 10.21.1 主写入时机

| 时机 | 写入动作 | 说明 |
|------|----------|------|
| 流程启动 | 创建 `draft` 记录 | 建立 `workflow_id`、主链上下文、初始阶段 |
| 阶段正式通过 | 追加 `stage_transitions` | 记录一次 `forward` 迁移 |
| 阶段内回环被确认 | 追加 `loop_events` | 仅更新循环事实，不改变主阶段 |
| 跨阶段退回获批 | 追加 `loop_events` + `stage_transitions(return)` | 同时记录事件与阶段边界变化 |
| 阶段 5 运行回滚闭环 | 更新 `final_decision` 候选值并挂接 `release_completion_record` | 保留“流程可能以回滚收口”的事实 |
| 全流程正式结案 | 置 `closure_status = finalized` | 形成正式版本并发出 finalized 事件 |

##### 10.21.2 我建议避免的写法

- 不要只在流程结束时一次性倒灌全部历史
- 不要让下游阶段直接改写上游阶段迁移记录
- 不要让 `loop_events` 与 `stage_transitions` 共用一个混合数组
- 不要在草稿态就向全平台广播 finalized 事件

##### 10.21.3 写入责任归属

| 写入内容 | 第一责任模块 | 协同模块 |
|----------|--------------|----------|
| `workflow_status` / `current_stage` | `workflow_orchestrator` | 各平台事实服务 |
| `stage_transitions` | `workflow_orchestrator` | 触发该迁移的事实源平台 |
| `loop_events` | `workflow_orchestrator` | 当前阶段 Runtime / 发布运行平台 |
| `attached_stage_records` | `workflow_ledger` | 各平台事实服务 |
| `closure_checks` / `closure_status` | `workflow_orchestrator` | 审计域 / 事实校验器 |

#### 10.22 API 映射建议

如果要让这个对象进入真正的平台接口层，我建议至少拆成“查询类 API”和“结案/迁移写入类 API”。

##### 10.22.1 查询类 API

| API | 方法 | 作用 |
|-----|------|------|
| `/api/workflows/{workflow_id}/completion-record` | `GET` | 读取当前最新 `workflow_completion_record` |
| `/api/workflows/{workflow_id}/completion-record/versions` | `GET` | 读取历史版本与快照 |
| `/api/workflows/{workflow_id}/timeline` | `GET` | 聚合返回 `stage_transitions` + `loop_events` |
| `/api/workflows/{workflow_id}/closure-checks` | `GET` | 返回当前结案校验状态 |

##### 10.22.2 写入类 API

| API | 方法 | 作用 |
|-----|------|------|
| `/api/workflows/{workflow_id}/stage-transitions` | `POST` | 追加一次正式阶段迁移 |
| `/api/workflows/{workflow_id}/loop-events` | `POST` | 追加一次阶段内回环 / 退回 / rollback 事件 |
| `/api/workflows/{workflow_id}/attached-stage-records` | `POST` | 绑定正式阶段记录引用 |
| `/api/workflows/{workflow_id}/closure-review` | `POST` | 发起或更新结案审查 |
| `/api/workflows/{workflow_id}/finalize` | `POST` | 形成正式 finalized 版本 |

##### 10.22.3 API 设计约束

- `finalize` 必须依赖 `closure_checks` 全部满足，不能裸调成功
- `stage-transitions` 只能写正式迁移，阶段内细步状态不要混入
- `loop-events` 允许持续追加，但追加后必须可追到正式关联对象
- 所有写入 API 都应携带 `idempotency_key` 与 `operator_id`

#### 10.23 事件主题与总账写入点映射建议

我建议把 `workflow_completion_record` 自身也视为一个事件生产者，而不只是被动数据表。

##### 10.23.1 推荐事件主题

| 写入动作 | 推荐 topic | 触发时机 |
|----------|------------|----------|
| 创建草稿总账 | `workflow.completion-record.v1.drafted` | 流程实例创建后 |
| 记录阶段迁移 | `workflow.completion-record.v1.transition-recorded` | `stage_transitions` 追加后 |
| 记录回环事件 | `workflow.completion-record.v1.loop-event-recorded` | `loop_events` 追加后 |
| 更新结案检查 | `workflow.completion-record.v1.closure-checks-updated` | `closure_checks` 变化后 |
| 正式结案 | `workflow.completion-record.v1.finalized` | `closure_status = finalized` 后 |
| 流程改道/终止/回滚收口 | `workflow.completion-record.v1.disposition-updated` | `final_decision` 进入结束态后 |

##### 10.23.2 事件与落库顺序建议

我建议固定成：

```text
事实源记录完成
-> workflow_orchestrator 聚合校验
-> workflow_ledger 落库新版本
-> 发布 completion-record 事件
-> 订阅方更新视图 / 审计 / 搜索索引
```

也就是说：

- 先落库，再发正式广播事件
- 广播事件引用 `record_version` 或 `snapshot_version`
- 订阅方不能把收到的事件当成唯一事实源，仍应可回查正式记录

##### 10.23.3 主订阅方建议

| topic | 主订阅方 | 目的 |
|-------|----------|------|
| `workflow.completion-record.v1.transition-recorded` | 协作平台 / 工程平台 | 同步阶段边界变化与看板视图 |
| `workflow.completion-record.v1.loop-event-recorded` | 当前阶段 Runtime / 协作平台 | 同步回环与阻塞链视图 |
| `workflow.completion-record.v1.finalized` | 协作平台 / 发布平台 / 审计域 | 更新流程最终态、归档、审计入库 |
| `workflow.completion-record.v1.disposition-updated` | 协作平台 / 审计域 | 同步终止、改道、回滚收口结果 |

#### 10.24 这一题的最小结论

对这个问题，我建议把结论写成下面这版：

- `workflow_completion_record` 的主挂载平台应是 `AI 编排与知识平台` 下的 `workflow_orchestrator + workflow_ledger`
- 它的写入应采用“持续补账 + 最终定版”，而不是最后一次性拼装
- 各业务平台仍是分域事实源，`workflow_completion_record` 只做跨阶段总账与编排审计
- API、topic、落库顺序必须一起设计，否则容易出现“事件先飞了、正式记录还没定版”的不一致
- 因此下一步最自然的是：**把三类回退继续映射成具体状态字段枚举、状态迁移表与异常处理规则**

如果继续下一步，我建议直接进入：

1. `把三类回退映射成状态字段枚举与状态迁移表`
2. `把 workflow_completion_record 再细化成版本控制、快照保留与审计策略`

## 二十、这些云端库应同时具备 AI-native 接口层与人机共视前端

你这个建议我非常赞同。

如果这些云端库未来要真正成为 `AI + 人` 协同工作的基础设施，那么它们不能只做成“给人点点点的后台系统”，而应该同时具备两层能力：

- **对 AI 友好**：接口返回应尽量结构化、可判定、可追溯、低歧义
- **对人友好**：前端应能直观看出当前对象、当前阶段、当前项目到底是否达标、缺什么、卡在哪里

我建议把这个原则直接固定成：

> **同一份正式事实，至少要有一套 SoR 表达、一套 AI 消费表达、一套人机共视表达。**

### 1. 先固定“双通道输出”原则

我建议每个云端库都默认同时提供两种读取通道：

| 通道 | 面向对象 | 目标 | 典型形式 |
|------|----------|------|----------|
| 人类工作台通道 | 产品、研发、测试、运维、管理者 | 便于浏览、追踪、审批、钻取 | 页面、卡片、表格、时间线、看板 |
| AI 消费通道 | Assistant、Tech Lead、专业 Agent、编排器 | 便于理解、判断、生成动作、回写 | 稳定 JSON / YAML、事件流、契约包 |

这意味着：

- 不应让 AI 去解析复杂 HTML 页面才能拿到事实
- 也不应只提供机器接口，却让人看不出当前是否达标
- 更不应出现“页面看起来通过了，但 API 返回信息不完整”这种双标状态

### 2. 我建议补一层 AI-native 接口规范

如果进一步工程化，我建议每个云端库都提供一层 `AI-native API / Contract API`。

#### 2.1 AI-friendly 返回结构建议

我建议 AI 消费接口优先返回下面这类结构：

| 字段 | 作用 |
|------|------|
| `object_id` | 正式对象 ID |
| `object_type` | 对象类型 |
| `title` | 可读标题 |
| `summary` | 适合 AI 快速理解的短摘要 |
| `status` | 当前状态枚举 |
| `compliance_status` | 当前是否达标 |
| `required_checks` | 必须满足的检查项 |
| `passed_checks` | 已满足项 |
| `missing_items` | 缺失项 |
| `risk_flags` | 风险标记 |
| `next_actions` | 建议下一步动作 |
| `evidence_refs` | 证据链接或正式记录引用 |
| `source_of_record` | 事实源平台 |
| `source_record_id` | 事实源对象 ID |
| `freshness_status` | 数据是否过期 |
| `updated_at` | 最后更新时间 |

这样的好处是：

- AI 不需要先读长篇自然语言再猜状态
- AI 可以直接判断“是否达标”“差什么”“下一步应该做什么”
- 结果天然适合继续进入 `entry_contract`、`handoff_package`、`decision_packet`

#### 2.2 AI 接口应优先回答的 6 类问题

我建议接口天然能回答下面六个问题：

- 这是什么对象
- 当前状态是什么
- 是否达标 / 是否可进入下一阶段
- 还缺哪些证据或前置项
- 风险在哪里
- 下一步允许执行什么动作

也就是说，接口不只是“把数据库字段吐出来”，而是要更接近：

> **AI 可直接消费的决策包 / 就绪包 / 风险包 / 交接包。**

#### 2.3 AI-native 接口的设计约束

我建议再加几条硬约束：

- 返回必须优先结构化字段，长文本只能作为补充
- 枚举值必须稳定，不能一会儿叫 `ready`，一会儿叫 `ok`
- 必须带 `source_of_record`、`source_record_id`、`updated_at`、`freshness_status`
- 必须显式区分 `事实`、`判断`、`建议动作`
- 必须支持分页、过滤、增量拉取与事件订阅
- 必须提供面向 AI 的“最小必要字段集”，避免把噪音字段全量塞给模型

例如我建议把一个对象的 AI 返回固定成下面这类三层：

```yaml
ai_view_payload:
  facts:
    status: ready
    source_of_record: engineering
    source_record_id: readiness_report-001
  checks:
    required_checks:
      - dependency_ready
      - interface_confirmed
      - test_plan_bound
    missing_items: []
  actions:
    allowed_next_actions:
      - enter_stage3
    blocked_actions: []
```

### 3. 我建议再补一层“达标可视化前端”

除了 AI 接口，我非常建议这些云端库都要有一层“人机共视前端”，专门回答：**当前到底是否符合要求。**

#### 3.1 前端不只是展示对象，而要展示“达标态”

我建议页面默认不要只展示对象详情，而要优先展示：

- 当前状态
- 达标状态
- 缺失项
- 阻塞项
- 风险等级
- 证据完整度
- 最新校验时间
- 是否允许进入下一步

也就是说，页面首页更像：

- `Readiness Dashboard`
- `Compliance Board`
- `Stage Gate View`
- `Release Control Panel`

而不只是传统 CRUD 列表页。

#### 3.2 我建议前端统一采用一组达标字段

为了让“人看”和“AI 看”一致，我建议前后端统一一组达标字段：

| 字段 | 含义 |
|------|------|
| `compliance_status` | `not_ready / partially_ready / ready / blocked / expired` |
| `compliance_score` | 0-100 的达标评分 |
| `required_items_total` | 应满足项总数 |
| `fulfilled_items_total` | 已满足项数量 |
| `missing_items` | 仍缺的项 |
| `blocking_items` | 阻断项 |
| `risk_level` | `low / medium / high / critical` |
| `last_verified_at` | 最近一次校验时间 |
| `next_gate_allowed` | 是否允许进入下一 gate |

这样：

- 前端可以直接画红黄绿状态
- AI 也可以直接拿这些字段做判断
- 人和 AI 使用的是同一套达标语义，而不是两套口径

#### 3.3 前端建议优先做的 5 类视图

我建议至少先做下面五类页面或卡片视图：

| 视图 | 主要回答的问题 |
|------|----------------|
| 项目总览看板 | 这个项目当前卡在哪个阶段，整体是否可继续推进 |
| 阶段达标看板 | 每个阶段进入/退出条件满足了多少 |
| 对象证据面板 | 某个对象的必备证据是否齐全，缺什么 |
| 风险与阻塞面板 | 当前有哪些 blocker、hold、rollback 风险 |
| 发布控制台 | 当前是否可发布、是否需 hold、是否触发 rollback |

#### 3.4 我建议页面支持“钻取到正式证据”

前端不能只显示一个红灯或绿灯，还要允许用户和 AI operator 快速钻取：

- 这个结论基于哪条正式记录
- 缺失项具体缺哪一条
- 风险判断来自哪个检测结果 / 监控指标 / gate 记录
- 当前状态由哪个事件或审批动作推动而来

所以每张卡片都建议至少能跳到：

- `source_of_record`
- `source_record_id`
- `evidence_refs`
- `last_event`

### 4. 我建议把“AI 友好 + 人类可视”做成统一契约，而不是两个临时补丁

更好的做法不是“额外做个 AI 接口”和“额外做个大屏”，而是把底层对象统一扩成：

```text
正式事实对象
-> AI 消费视图对象
-> 人类工作台视图对象
```

也就是说：

- SoR 负责真实性
- AI view 负责可消费性
- UI view 负责可判断性

三者共享同一组核心 ID、状态枚举、达标字段、证据引用。

### 5. 放到你这套 3+1 平台里，我建议这样落

| 平台 | AI-friendly 重点 | 前端可视化重点 |
|------|------------------|----------------|
| 研发协作平台 | 需求摘要、验收口径、缺失项、下一步建议 | 项目看板、需求达标面板、验收通过率 |
| 工程执行平台 | 接口契约摘要、任务就绪度、测试覆盖与质量门禁 | 开发执行面板、接口变更面板、测试达标面板 |
| 发布运行平台 | 发布决策包、观察窗状态、回滚建议包 | 发布控制台、灰度进度、风险告警、回滚状态 |
| AI 编排与知识平台 | 汇总 AI 视图、生成阶段契约、编排决策包 | 全流程总览、阶段 gate 仪表盘、AI 结论可解释面板 |

### 6. 这一题我建议先固定的最小结论

我建议把结论收敛成下面这版：

- 云端库未来不应只做“给人操作的后台”，而应同时提供 `SoR + AI view + UI view`
- 面向 AI 的接口应优先输出结构化、可判定、可追溯、低歧义的数据包
- 面向人的前端应优先展示“是否达标、缺什么、能否进入下一步”，而不只是对象详情
- `compliance_status`、`missing_items`、`risk_level`、`evidence_refs` 这类字段应成为人机共用的核心语义
- 因此下一步很适合继续补：**统一的达标字段模型、AI 接口返回契约、前端看板信息架构**

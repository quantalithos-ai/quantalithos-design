## 一、为什么是六域

### 1.1 从产品叙事反推的五条能力缺口

`product/最终目的.md` 的六条叙事承诺反推出五条"模型必须覆盖但现有单一标准不够"的能力:

1. **员工身份** —— 有持久个体、有生涯、有记忆、可被"登录"
2. **协作媒介** —— 一等的对话空间,不是消息表附属
3. **用户位置** —— 用户始终在回路,关键决策必入
4. **工作定义** —— 软件项目有完整生命周期,不是一次问答
5. **可观察性** —— 任何时刻全局可见,任何变更可追溯

这五条缺口,单靠 BPMN / SPEM / 12207 / 42001 / Scrum 任何一份标准都无法给出完整模型。**六域分离 + 事件编织**是能同时对齐"管理者叙事"与"国际标准治理骨架"的唯一解。

### 1.2 六域的命名

```
Identity       (身份域)     员工是谁
Conversation   (对话域)     人们怎么说话
Work           (工作域)     在做什么软件项目
Process        (过程域)     按什么规矩推进
Governance     (治理域)     关键决策由谁定
Artifact       (制品域)     产出什么可审计资产
```

### 1.3 六域平权,不设主心骨

**关键架构决策**:六域**平权**,不存在"主域 / 辅域",不存在"某一域统治其他"。

- 对比 Phase 1:以 BPMN ProcessInstance 为主心骨,其他都是附属 —— A 方案废弃
- A 方案:六个域各自是**独立聚合根树**,跨域只通过**领域事件**通信
- 任何"多域一致性"需求走**Saga 模式**,不做分布式事务

### 1.4 六域与其他建模方式的对比

| 对比对象 | 结构 | 为什么不采用 |
|---|---|---|
| 三层架构(Presentation/Business/Data) | 技术分层 | 不是领域边界 |
| 单体 Service-based(User/Project/Workflow Service) | 按服务拆分 | "Service" 不等于"Context",易堆叠 |
| 以 BPMN 为骨干 + 周边附属 | 流程优先 | 对话/员工/制品被降格,不符合产品叙事 |
| CQRS + Event Sourcing 整体 | 技术模式 | 可作为局部实现手段,不作为全局建模方式 |

## 二、六域总览与交互规则

### 2.1 六域全景

```
                    ┌─────────────────┐
                    │   Event Bus     │
                    │  (L0 bus 仓)    │
                    └────────┬────────┘
                             │
       ┌────────┬────────┬───┼───┬────────┬────────┐
       ▼        ▼        ▼   ▼   ▼        ▼        ▼
   ┌──────┐ ┌──────┐ ┌─────┐ │ ┌──────┐ ┌──────┐ ┌──────┐
   │身份  │ │对话  │ │工作 │ │ │过程  │ │治理  │ │制品  │
   │Idty  │ │Conv  │ │Work │ │ │Proc  │ │Govn  │ │Arti  │
   └──────┘ └──────┘ └─────┘ │ └──────┘ └──────┘ └──────┘
                             │
                   ┌─────────┴─────────┐
                   │  四条横切能力       │
                   │  Observability    │
                   │  Capability Hub   │
                   │  Method Library   │
                   │  Evaluation       │
                   └───────────────────┘
```

### 2.2 域间通信规则(硬约束)

1. **跨域只通过事件** —— 不允许跨域直接 RPC、不允许跨域共享数据库事务
2. **事件走 CloudEvents** —— 所有事件包络统一
3. **事件命名**`<domain>.<aggregate>.<verb>`,过去式
   - 例:`identity.member.hired` / `governance.gate.decided`
4. **最终一致性** —— 跨域允许秒级延迟,不追求强一致
5. **事件幂等** —— 订阅方必须处理重复投递
6. **聚合内强一致** —— 单个聚合根的写操作必须事务性,不允许"半改"
7. **W3C Trace Context 贯穿** —— 跨域事件携带 trace_id,observability 能拼全链路
8. **事件不可变** —— 事件一旦发出不可撤销,错了只能发"补偿事件"

### 2.3 八条底层原则(六域设计不可妥协)

| # | 原则 | 体现 |
|---|------|------|
| A | 六域分离 | 各自聚合根树 + 事件通信 |
| B | Definition vs Use 严格分离 | Method Content vs Instance(SPEM) |
| C | Conversation 是一等聚合根 | 不是消息表附属 |
| D | 员工是持久性实体 | GlobalMember 跨项目存在 |
| E | Gate 是一等流程控制对象 | 不是 BPMN UserTask 特化 |
| F | 过程模板+裁剪+实例三段式 | Template → Profile → Instance |
| G | Artifact 带状态机 | 不是"写完就完事"的记录 |
| H | 可观察性内置 | 每个域每次写操作都发事件 |

### 2.4 六域与 26 仓的映射

```
L1 六域服务层 6 仓 = 六域聚合根的持久化与服务化

quantalithos-identity       → 身份域
quantalithos-conversation   → 对话域
quantalithos-work           → 工作域(含 ProjectMember 作为内部实体)
quantalithos-process        → 过程域
quantalithos-governance     → 治理域
quantalithos-artifact       → 制品域

L3 方法能力层 2 仓 = 横切能力的承载
quantalithos-method-library → 方法库
quantalithos-capability-hub → 能力池

L4 基础设施层 3 仓 = 横切基础设施
quantalithos-observability  → 观测横切
quantalithos-archive        → 归档横切
quantalithos-sandbox        → 执行隔离
```

## 三、身份域 Identity

### 3.1 使命

定义**员工是谁**。承载 Quantalithos 最独特的产品叙事承诺:**员工是有身份的个体,不是任务执行器**。

身份域回答:
- 这个员工叫什么、擅长什么、经历过什么?
- 系统里有哪些角色原型(Role)?每种角色有什么能力?
- 员工现在能被用吗?退休了吗?被暂停了吗?

### 3.2 聚合根

#### 3.2.1 `GlobalMember`(聚合根)

员工的**持久档案**,跨项目存在,独立于任何项目生命周期。

```
GlobalMember
├─ member_id          全局唯一 ULID(稳定,永不变)
├─ name               显示名(可变,允许重复)
├─ avatar             头像 URI(可变)
├─ profile            自由文本简介(可变)
├─ role_id            当前主职业(引用 Role)
├─ secondary_roles    兼任的其他角色(可为空)
├─ capability_profile 能力画像(引用 Capability 集合)
├─ semantic_memory_ref 外部向量库句柄(不存向量,只存引用)
├─ career_history     过去参与项目 + 成就 + 教训(按时间线)
├─ hired_at           招聘时间
├─ current_lifecycle  当前生命周期状态
└─ audit_metadata     谁 / 何时 / 为何创建和修改
```

**生命周期状态机**:

```
  [创建]
    │
    ▼
┌─────────┐
│ hired   │ 招聘中 —— 档案已建,但尚未激活,不能接任务
└────┬────┘
     │ activate
     ▼
┌─────────┐
│ active  │ 活跃 —— 可被分配到项目,正常工作
└────┬────┘
     │ pause / reactivate
     ▼
┌─────────┐
│ paused  │ 暂停 —— 档案保留,不接新项目,旧项目的 ProjectMember 也进 paused
└────┬────┘
     │ retire
     ▼
┌─────────┐
│ retired │ 退休 —— 不再接任何项目,档案只读,semantic_memory 保留
└────┬────┘
     │ tombstone(通常 ≥ 1 年后)
     ▼
┌──────────┐
│ tombstoned │ 墓碑 —— 档案归入冷存,semantic_memory 可能清理
└──────────┘
```

**不变量**:
- `member_id` 一旦分配永不复用
- `tombstoned` 状态单向,不能复活
- 同一 `role_id` 下的 GlobalMember 可以有多个(像公司里多个后端工程师)
- `semantic_memory_ref` 的 URI 在跨状态时可能变(hot → cold 存储迁移)
- `career_history` 只 append,不允许改写历史条目

**不做的事**:
- 不持有 ProjectMember(那是工作域的实体)
- 不直接存 semantic_memory 向量(只存引用)
- 不做容器编排(那是 L2 member-service)
- 不做对话(那是对话域)

#### 3.2.2 `Role`(聚合根)

**角色原型** —— 全平台有限枚举的职业定义。

```
Role
├─ role_id            Role 标识(如 tech-lead / backend-dev / qa)
├─ display_name       显示名("Tech Lead")
├─ description        职责描述
├─ required_capabilities  必需能力集
├─ default_capabilities   默认可选能力集
├─ image_variant      → member-images 的镜像 tag(ADR-0005)
├─ default_tool_scope 默认工具集
├─ policy_defaults    默认策略(可被 ProjectMember 覆盖)
├─ spec_source        SPEM Method Content 引用(→ method-library)
└─ version            Role 定义版本(semver)
```

**关键事实**:
- Role 是**SPEM 2.0 RoleDefinition 的领域化**
- Role 的具体内容由 method-library 的 Method Content 提供
- identity 仓持有 Role 的**索引与生命周期元数据**,不持有完整定义(那在 method-library)
- Role 变更有**严重下游影响**,变更必须走 ADR

**初始 Role 集合(9 个)**:
```
tech-lead / backend-dev / frontend-dev / qa /
ux / devops / auditor / assistant / observer
```

#### 3.2.3 `Capability`(值对象)

```
Capability
├─ capability_id      如 "python-3.12" / "code-review" / "figma-export"
├─ kind               language / skill / certification / tool-family
├─ level              mastery 级别(1-5)
├─ evidence_required  是否需要证据(如认证)
└─ evidence_refs      证据 Artifact 引用
```

Capability 是**值对象**(按值相等,不带 ID 可变),但当需要追踪"某 Member 的某 Capability 是如何获得的"时,会在 member 的 capability_profile 里有完整快照 + 证据链。

### 3.3 发布事件

```
identity.role.defined            新 Role 定义
identity.role.retired            Role 退役

identity.member.hired            招聘完成
identity.member.activated        从 hired/paused 转入 active
identity.member.paused           暂停
identity.member.retired          退休
identity.member.tombstoned       墓碑(通常延迟 ≥1 年)
identity.member.profile_updated  档案改动(name/avatar/profile)
identity.member.role_changed     主职业变更
identity.member.capability_updated 能力画像变更
identity.member.career_entry_added career_history 新增条目
```

### 3.4 订阅事件(来自其他域)

```
work.project.member_assigned     → 在 career_history 里预留一条 in-progress 条目
work.project.archived            → career_history 里该条目改为 completed
governance.gate.member_audited   → 如果 Member 涉及治理事件,记入 audit_metadata
```

### 3.5 与标准对齐

| 条目 | 对齐 |
|---|---|
| Role 定义 | **SPEM 2.0 RoleDefinition**(method-library 提供内容) |
| AI Actor 责任链 | **ISO 42001 §5.3 + A.3** |
| Capability 画像 | **9001 §7.2 能力** |
| career_history 审计 | **9001 + 三红线可审计性** |
| tombstoned 墓碑 | **42001 A.6 Retirement 阶段** |

### 3.6 关键设计决策

- **GlobalMember 是 Aggregate Root,不是 ProjectMember 的父级** —— ProjectMember 在工作域,引用 GlobalMember
- **Role 是 SPEM Method Content 的索引** —— 内容在 method-library,避免耦合
- **semantic_memory 外置** —— 向量库句柄存在档案里,实际向量在外部(S3/MinIO + Qdrant/pgvector),支撑冷热分层
- **Assistant 是特殊 Role** —— 每个用户开通时默认招聘一个 Assistant;Assistant 的生命周期绑定用户而非项目

## 四、对话域 Conversation

### 4.1 使命

定义**人们怎么说话**。承载产品叙事里"协作载体是对话"的承诺。

对话域是**协作的第一入口**。用户看到的一切业务(立项、决策、交付、审批)都以对话为载体。**对话不是消息表的包装,是领域本体**。

### 4.2 聚合根

#### 4.2.1 `Conversation`(聚合根)

一个独立的对话空间,有自己的生命周期、参与者、话题。

```
Conversation
├─ conversation_id    ULID
├─ kind               group / channel / dm / thread
├─ title              标题(可变)
├─ description        描述
├─ parent_conv_id     父对话(channel 和 thread 有)
├─ project_id         归属项目(group 和 channel 必有;dm/thread 可选)
├─ participants       参与者清单(GlobalMember 引用列表)
├─ visibility         open / closed / private
├─ created_by         创建人
├─ lifecycle          active / archived / locked
└─ last_turn_at       最新 turn 时间(冗余,加速查询)
```

**四种形态**:

| 形态 | 场景 | 特征 |
|---|---|---|
| `group` | 项目主群 | 一个项目一个 group,全体参与者可见 |
| `channel` | 项目下的子话题 | 组内可拉,参与者自选,组外不可见 |
| `dm`(direct message) | 两人私聊 | 只有两方,跨项目也可建 |
| `thread` | Turn 下的讨论串 | 绑定特定 Turn,不独立存在 |

**生命周期**:
- `active` — 正常
- `archived` — 归档,只读,仍可查
- `locked` — 锁定,不可新发 Turn(用于合规场景,通常人工触发)

**不变量**:
- `kind=group`:每个 Project 必须有且只有一个 group
- `kind=channel`:必须有 parent_conv_id 指向 group
- `kind=dm`:participants.length == 2
- `kind=thread`:必须有 parent_turn_id
- 一旦 `archived`/`locked` 不能回到 `active`

#### 4.2.2 `Turn`(Conversation 内实体)

一次对话发言。

```
Turn
├─ turn_id            ULID
├─ conversation_id    归属对话
├─ author             发言者(GlobalMember 或 system)
├─ kind               message / mention / decision / artifact / gate
├─ content            结构化内容(按 kind 不同)
├─ parent_turn_id     回复的 turn(可空)
├─ referenced_turns   引用的其他 turn(quote)
├─ artifacts          关联制品(引用 Artifact)
├─ gates              关联门禁(引用 Gate)
├─ created_at         发言时间
├─ visibility         全部参与者 / 特定参与者
└─ trace_id           W3C trace 上下文
```

**五种 kind**:

| kind | 说明 | 典型内容 |
|---|---|---|
| `message` | 普通消息 | 文本 + 可选 markdown |
| `mention` | @某人 | 被 @ 的 member_id 列表 |
| `decision` | 决策声明 | 决策内容 + 决策者 + 理由 |
| `artifact` | 制品引用 | 引用的 Artifact + 展示模式(预览/链接) |
| `gate` | 门禁卡片 | 引用的 Gate + 候选选项 + 证据链接 |

**不变量**:
- Turn 一旦创建不可修改内容(只能通过新 Turn 标记"edit")
- Turn 一旦创建不可删除(只能标记 `hidden`,Turn 本体永久保留)
- `kind=gate` 的 Turn 必须引用一个 active 的 Gate
- `kind=decision` 的 Turn 必须有 decision_maker 字段

### 4.3 发布事件

```
conversation.created          新建对话
conversation.archived         归档
conversation.locked           锁定
conversation.participant_added 参与者加入
conversation.participant_removed 参与者离开
conversation.turn_posted       新发言
conversation.turn_hidden       发言隐藏
conversation.mention_triggered @某人
conversation.decision_made     决策 Turn 发出
conversation.artifact_shared   制品分享 Turn
conversation.gate_raised       门禁卡片出现(由 governance 先发 gate.raised,conversation 跟发)
```

### 4.4 订阅事件

```
work.project.created          → 自动创建同名 group
work.project.archived         → 对应 group 自动 archived
governance.gate.raised        → 在相关 group / channel 发出 gate-kind Turn
governance.gate.decided       → 发出 decision-kind Turn
artifact.approved             → 可选:在相关对话发 artifact-kind Turn 通知
identity.member.paused        → 如果该 Member 在某 Conversation 的 participants,更新展示层(不踢人)
identity.member.retired       → 从所有 Conversation 的 participants 移除(但历史 Turn 保留作者引用)
```

### 4.5 与标准对齐

| 条目 | 对齐 |
|---|---|
| Conversation 四形态 | **BPMN 2.0 Collaboration View** + **Participant / MessageFlow** |
| Turn 五 kind | **BPMN Collaboration Message Type** |
| 5 事件(Planning/Daily/Review/Retro/Refinement) | **Scrum**,映射为 group / channel 内的规律性 Turn 序列 |
| 实时推送 | **AG-UI 17 事件** |
| 对话审计 | **9001 Documented Information**(对话即证据) |

### 4.6 关键设计决策

- **Conversation 是一等聚合根,不是"消息服务"** —— 这是产品叙事的核心,技术上对齐 BPMN Collaboration 概念
- **Turn 不可变** —— 对齐 9001 审计要求和 Event Sourcing 理念
- **thread 绑定 Turn,不是 Conversation 的独立形态** —— 避免 thread 爆炸
- **group 唯一绑定 Project** —— 项目就是群,没有"项目下无群"的设计,简化心智模型
- **外部桥接(bridges 仓)映射** —— Mattermost / Slack 等平台映射为 bridged Conversation 实例,kind=group,来源字段标 `bridged_from`

## 五、工作域 Work

### 5.1 使命

定义**在做什么软件项目**。承载产品叙事里"工作对象是软件项目"的承诺。

工作域回答:
- 这个项目是什么、做给谁、目标什么?
- 哪些员工参与这个项目?以什么项目级角色 / 工具 / 策略参与?
- 项目的需求 / 任务 / Bug / 原型是什么?
- 当前在哪个迭代?下一个里程碑什么?

### 5.2 聚合根

#### 5.2.1 `Project`(聚合根)

```
Project
├─ project_id         ULID
├─ owner_user_id      发起用户(通常是管理者)
├─ title              项目名
├─ description        目标描述
├─ context_of_use     使用上下文(25010 要求 / 42001 Scope)
│    ├─ target_users       目标用户画像
│    ├─ deployment_env     目标部署环境
│    └─ compliance_profile 需要符合的监管(GDPR / HIPAA / EU AI Act / ...)
├─ process_template_id  选用的过程模板(→ method-library)
├─ process_profile_id   裁剪后的 Profile(→ process.ProcessProfile)
├─ process_instance_id  当前运行的 ProcessInstance(→ process)
├─ current_iteration_id 当前迭代
├─ baseline_ids         冻结的 Baseline 集合(→ artifact)
├─ aiia_ref             AI 影响评估引用(42001 要求)
├─ lifecycle            draft / active / paused / archived / dissolved / restored
├─ created_at / started_at / archived_at / dissolved_at
└─ audit_metadata
```

**生命周期**:

```
[创建]
  │
  ▼
┌──────┐
│ draft│ 起草 —— 初始设置,尚未经 Gate 批准启动
└──┬───┘
   │ start(通常经 gate=project-kickoff 批准)
   ▼
┌──────┐
│active│ 活跃 —— 正常运行中
└──┬───┘
   │ pause(临时停 + paused-gate 决策)
   ▼
┌──────┐
│paused│ 暂停
└──┬───┘
   │ resume(经 gate)
   ▼ 回 active
   │
   │ archive(完成或中止)
   ▼
┌──────────┐
│ archived │ 归档 —— 可恢复,只读
└──┬───────┘
   │ restore(经 gate)       │ dissolve(不再保留可恢复)
   ▼                        ▼
回 active                  ┌──────────┐
                          │dissolved │ 解散 —— 只审计,不可恢复
                          └──────────┘
```

**不变量**:
- `dissolved` 单向,不能复活
- `baseline_ids` 只 append(一旦 Baseline,不能从列表中移除)
- `process_profile_id` 一旦选定,整个项目生命周期不允许更换(换等于新建项目)
- 同一时刻只有一个 `current_iteration_id`

#### 5.2.2 `ProjectMember`(Project 下的实体)

**双层 Member 模型的"项目层"**,参见 ADR-0004。

```
ProjectMember
├─ project_member_id  ULID(项目内唯一)
├─ project_id         归属项目
├─ global_member_id   引用身份域的 GlobalMember
├─ role_in_project    项目内角色(可覆盖 global 的 main role)
├─ tool_scope         项目级工具权限(29110 Profile 落地)
├─ policy_overrides   项目级策略裁剪
├─ memory_slot_ref    项目级记忆槽引用(外部存储)
├─ current_workitems  当前 assigned WorkItem 集合
├─ assigned_at
├─ lifecycle          assigned / active / paused / retired_from_project / archived
└─ career_entry_ref   对应 GlobalMember.career_history 的条目引用
```

**不变量**:
- 同一个 (project_id, global_member_id) 只能有一个 active ProjectMember
- `tool_scope` 必须是 Role.default_tool_scope 的**子集或扩展**,扩展必须有 policy_overrides 支持
- `retired_from_project` 单向
- Project 归档时,所有 ProjectMember 自动 archived(不是 retired_from_project)

#### 5.2.3 `Backlog`(Project 下的聚合)

```
Backlog
├─ backlog_id
├─ project_id
├─ workitems          有序列表(优先级决定顺序)
├─ refinement_state   未梳理 / 部分梳理 / 已梳理
└─ last_refined_at
```

**Scrum 借鉴**:Backlog 是 Product Backlog 的领域化。不区分 Product Backlog / Sprint Backlog,用**关联 Iteration**来表达 Sprint Backlog。

#### 5.2.4 `WorkItem`(Project 下的聚合)

```
WorkItem
├─ workitem_id        ULID
├─ project_id
├─ kind               story / task / bug / prototype / spike / review / nfr
├─ title
├─ description        markdown
├─ acceptance_criteria 验收条件
├─ assignee           ProjectMember 引用
├─ reviewers          评审者列表
├─ dependencies       前置 WorkItem 列表(DAG)
├─ related_artifacts  产出 / 引用的 Artifact 集合
├─ iteration_id       当前所在迭代(可空)
├─ state              todo / in_progress / blocked / in_review / done / cancelled
├─ estimated_effort   规模估计(可选)
├─ priority           优先级
└─ audit_metadata
```

**七种 kind**:

| kind | 含义 | 标准来源 |
|---|---|---|
| `story` | 用户故事 | Scrum |
| `task` | 工程任务 | 通用 |
| `bug` | 缺陷 | 通用 |
| `prototype` | 原型制作任务 | 24748-2 Prototype |
| `spike` | 技术探索 | XP |
| `review` | 评审任务 | 12207 V&V |
| `nfr` | 非功能性需求 | 25010 |

**不变量**:
- 依赖图必须是 DAG(无环)
- state=`done` 必须有至少一个关联 Artifact(approved)
- state=`blocked` 必须有 blocker 说明(可选字段变必填)
- 同一个 assignee 的 in_progress WorkItem 数量受 WIP limit 约束(Kanban)

#### 5.2.5 `Iteration`(Project 下的聚合)

```
Iteration
├─ iteration_id
├─ project_id
├─ sequence_num       第几次迭代
├─ goal               Sprint Goal / 迭代目标
├─ planned_workitems  计划完成的 WorkItem 集
├─ actual_workitems   实际完成(归档时写入)
├─ started_at / planned_end_at / ended_at
├─ retrospective_notes 回顾笔记(Scrum Retro)
└─ state              planned / in_progress / closed
```

**Scrum 对齐**:`Iteration` = Sprint;`goal` = Sprint Goal;`retrospective_notes` = Sprint Retrospective 产出。

### 5.3 发布事件

```
work.project.created
work.project.started
work.project.paused / resumed
work.project.archived / restored / dissolved
work.project.member_assigned            (ProjectMember 分配)
work.project.member_retired_from_project
work.project.aiia_attached              (AIIA 完成并挂载)
work.project.context_of_use_updated

work.workitem.created
work.workitem.state_changed
work.workitem.assigned
work.workitem.artifact_attached
work.workitem.dependency_added

work.iteration.planned
work.iteration.started
work.iteration.closed
work.iteration.retrospective_recorded

work.backlog.refined
```

### 5.4 订阅事件

```
identity.member.paused / retired  → 该 Member 在各 Project 的 ProjectMember 同步更新
identity.role.retired             → 所有用该 Role 的 ProjectMember 触发告警
governance.gate.decided(kickoff) → Project 从 draft → active
governance.gate.decided(archive) → Project 从 active → archived
governance.policy.updated        → 如影响 tool_scope,所有 active ProjectMember 需重评
artifact.approved                → 检查对应 WorkItem 是否可转 done
artifact.baselined                → 记入 Project.baseline_ids
process.activity.completed       → 对应 WorkItem 如 1:1 绑定则同步 done
process.gate_triggered           → 某些 WorkItem 可能进 in_review
```

### 5.5 与标准对齐

| 条目 | 对齐 |
|---|---|
| Project / SoI | **15288 SoI** + **42001 AIMS Scope** |
| context_of_use | **25010 Context of Use** + **42001 §4.3** |
| Backlog + WorkItem | **Scrum Product Backlog + Backlog Item** + **12207 技术过程 Work Products** |
| Iteration | **Scrum Sprint** + **Kanban Cadence** |
| WorkItem 七 kind | **Scrum story + 12207 Work Product kinds + XP spike + 25010 NFR** |
| 依赖 DAG | **Kanban Flow + BPMN 依赖表达** |
| WIP limit | **Kanban** |
| tool_scope / policy_overrides | **29110 Profile Tailoring** |

### 5.6 关键设计决策

- **ProjectMember 在 work 而不是 identity** —— 因为它是"项目的成员分配",不是"员工档案"的一部分。见 ADR-0004。
- **WorkItem 是"工作单位",ProcessInstance 是"规则管控"** —— 一个 Activity 可以对应多个 WorkItem(多个实现同一需求),一个 WorkItem 也可以跨多个 Activity(分阶段完成)。两者**弱绑定**,不是一一对应。
- **Iteration 是可选的**(Kanban 项目可以不分迭代)—— Backlog 才是必须的
- **NFR 作为 WorkItem kind** —— 不另建 NFR 系统,25010 对齐
- **Baseline 引用在 Project 上** —— Project 知道"我当前冻结了哪些 Artifact",但 Baseline 实体本身在 artifact 域管理

## 六、过程域 Process

### 6.1 使命

定义**按什么规矩推进**。承载产品叙事里"关键节点强制人类 + 过程可观察"的承诺里"过程"那半边;另一半(Gate)在治理域。

过程域回答:
- 这个项目用的是什么过程模板(瀑布 / 敏捷 / DevOps / …)?
- 模板被裁剪成什么样(Profile)?
- 当前运行到哪一步?下一步是什么?
- 发生了什么 Activity?产出了什么?

### 6.2 聚合根

三段式:`ProcessTemplate → ProcessProfile → ProcessInstance`。

这是对齐 **SPEM 2.0 Definition vs Use + 29110 Profile Tailoring** 的核心决策,也是八条原则中的"F"。

#### 6.2.1 `ProcessTemplate`(聚合根)

**通用过程模板**,不绑定任何项目。存储在 method-library 仓,process 仓持有**索引 + 运行时能力**。

```
ProcessTemplate
├─ template_id
├─ family             24748-2 家族(waterfall/v/incremental/evolutionary/
│                    iterative/spiral/agile/devops)
├─ display_name       展示名
├─ version            semver
├─ lifecycle_model    生命周期模型描述(对齐 24748-2)
├─ stages             阶段序列
├─ activities         活动定义(BPMN ElementTree)
├─ roles_required     需要的 Role(引用身份域 Role)
├─ artifacts_required 需要产出的 Artifact kind
├─ gates_required     强制的 Gate 点
├─ method_plugin_ref  SPEM MethodPlugin 引用
└─ source             core / community / org-defined
```

**初始模板家族(8 种)**:
- `waterfall-classic` — 瀑布
- `v-model` — V 模型
- `incremental-release` — 增量发布
- `evolutionary-discovery` — 演进式
- `iterative-standard` — 标准迭代(默认)
- `spiral-risk-driven` — 螺旋
- `agile/scrum` / `agile/kanban` / `agile/safe` — 敏捷家族
- `devops-continuous` — DevOps

每个家族都派生自 24748-2 的 8 种参考模型。

**不变量**:
- Template 一旦 publish 不可修改(要改发新版本)
- Template 必须指明 family(不允许"未分类")

#### 6.2.2 `ProcessProfile`(聚合根)

**被裁剪后的模板**,绑定具体 Project。

```
ProcessProfile
├─ profile_id
├─ project_id
├─ template_id        基于的 Template
├─ template_version
├─ tailoring_decisions 裁剪决策清单(24748-2 Tailoring Record 格式)
│    ├─ action         reduction / extension / adaptation
│    ├─ target         (被裁剪的元素 activity_id / gate_id / …)
│    ├─ rationale      裁剪理由
│    ├─ risk_mitigation 风险缓解
│    └─ approved_by
├─ profile_group      29110 Profile Group (entry/basic/intermediate/advanced/custom)
├─ tailoring_level    tight / moderate / loose
├─ effective_from     生效时间
└─ audit_metadata
```

**关键**:
- `tailoring_decisions` 遵循 **24748-2 §5.3 Tailoring Record 格式**(强约定)
- `profile_group` 可选 29110 的四级,也可以 `custom`
- Profile 一旦被 ProcessInstance 引用不可修改,要改发新 Profile(Project 可以选择切 Profile,但老 Instance 不动)

#### 6.2.3 `ProcessInstance`(聚合根)

**具体运行的一次过程**。

```
ProcessInstance
├─ instance_id
├─ project_id
├─ profile_id         引用 ProcessProfile
├─ current_stage      当前阶段(24748-2 Stage)
├─ current_activities 当前进行中的 Activity 集(可并行多个)
├─ completed_activities 已完成的 Activity
├─ pending_gates      当前挂起的 Gate 引用
├─ checkpoint         完整状态快照(每 Activity 完成后持久化)
├─ state              draft / running / paused / completed / failed / cancelled
├─ started_at / ended_at
└─ trace_id           整个 Instance 的根 trace
```

**持久执行**(参考 Temporal + LangGraph):
- 每个 Activity 完成**立即**更新 checkpoint
- 进程崩溃后重启,从 checkpoint 恢复,不重跑已完成 Activity
- 等待 Gate 决策 / 外部事件时状态 `paused`,不占运行资源

#### 6.2.4 `Activity`(Instance 下的实体)

```
Activity
├─ activity_id
├─ instance_id
├─ stage              所属 Stage
├─ definition_ref     对应 ProcessTemplate 的活动定义
├─ kind               user-task / service-task / manual-task / sub-process /
│                    gateway / event
├─ assignee           承担者(ProjectMember 或 system)
├─ inputs             输入 Artifact 集
├─ outputs            产出 Artifact 集
├─ workitems          关联 WorkItem(弱绑定)
├─ state              scheduled / in_progress / waiting_gate / completed / failed
├─ started_at / ended_at
└─ audit_metadata
```

**与 BPMN 的对应**:
- `user-task` ← BPMN UserTask
- `service-task` ← BPMN ServiceTask
- `sub-process` ← BPMN SubProcess
- `gateway` ← BPMN Gateway
- `event` ← BPMN Intermediate Event

但 `gate` 不是 Activity 的 kind —— Gate 在治理域是一等对象,Activity 通过 `waiting_gate` 状态引用它。

### 6.3 发布事件

```
process.template.published            (method-library 产生新 Template)
process.template.retired

process.profile.created               (Project 选择 Template + 裁剪)
process.profile.tailoring_recorded    每条裁剪决策

process.instance.created
process.instance.started
process.instance.paused / resumed
process.instance.completed / failed / cancelled
process.instance.checkpoint_saved

process.activity.scheduled
process.activity.started
process.activity.completed
process.activity.failed
process.activity.waiting_gate
process.activity.artifact_produced
process.stage.entered
process.stage.exited
```

### 6.4 订阅事件

```
work.project.started         → 创建 ProcessInstance,设为 running
work.project.paused          → ProcessInstance 进 paused
work.project.archived        → ProcessInstance 进 completed / cancelled
governance.gate.decided      → 挂起的 Activity 根据决策继续 / 终止 / 重试
artifact.approved            → 可能满足某 Activity 的出口条件,触发进度
identity.member.paused       → 分配给该 Member 的 Activity 重新调度
capability_hub.policy_updated → Profile 可能需要重裁剪(触发告警)
```

### 6.5 与标准对齐

| 条目 | 对齐 |
|---|---|
| Template → Profile → Instance 三段式 | **SPEM 2.0 Definition vs Use** + **29110 Profile** |
| Tailoring Record 格式 | **24748-2 §5.3** 强约定 |
| Activity kind 枚举 | **BPMN 2.0** Activity 类型 |
| 持久执行 | **Temporal Signal + Activity 重试** + **LangGraph Checkpoint** |
| 每步 checkpoint | 三红线"可追溯性" + Temporal |
| Stage 序列 | **24748-2 Stage** + **12207 生命周期阶段** |
| 8 种 Template 家族 | **24748-2** 八种参考模型 |
| 并行 Activity | **BPMN Parallel Gateway** + **Kanban Flow** |

### 6.6 关键设计决策

- **三段式不可合并** —— Template / Profile / Instance 不能合并成两段,因为:
  - Template 是"组织级资产",有版本,不绑项目
  - Profile 是"项目的裁剪决策",不是运行时
  - Instance 是"具体一次运行",有状态机
- **Activity 不是 Gate 的容器** —— Activity 等待 Gate 决策(state=waiting_gate),Gate 在治理域独立存在
- **持久执行 ≠ Event Sourcing** —— 每步 checkpoint 就够了,不需要从头重放事件流
- **WorkItem 和 Activity 弱绑定** —— 见 §5.6 的说明
- **Stage 是时间段,Activity 是工作能力** —— 对齐 24748-2 §0.3 辨析 1
- **不跑完整 SPICE 评估** —— 过程能力评估走"借鉴骨架",不做 CL/ML 实际打分(见标准对齐全景图 §3.6)

## 七、治理域 Governance

### 7.1 使命

定义**关键决策由谁定**。承载产品叙事里"关键节点强制人类"的产品原则,以及 ISO 42001 的整套 AIMS 要求。

治理域回答:
- 什么时候需要决策?谁来决策?候选选项是什么?
- 决策基于什么证据?
- 决策后的结果是什么?
- 整个组织的 AI 治理符合度如何?

治理域是 **Quantalithos 差异化的核心** —— Gate 是一等对象,不是"流程里可选的暂停点"。

### 7.2 聚合根

#### 7.2.1 `Gate`(聚合根)

一次审批请求。**六段式结构**,来自 24748-2 Decision Gate + 42001 Control 的综合。

```
Gate
├─ gate_id            ULID
├─ kind               kickoff / requirements-confirm / design-choice /
│                    prototype-approval / code-review / release-confirm /
│                    impact-assessment / quality-gate / archive-confirm / custom
├─ project_id         归属项目
├─ related_artifacts  相关制品
├─ related_activities 相关 Activity
├─ trigger            触发条件
│    ├─ raised_by         发起方(ProjectMember / ProcessInstance / system)
│    ├─ raised_at
│    └─ trigger_reason    触发原因(human-readable)
├─ decision_request   决策请求
│    ├─ question          要决策的问题
│    ├─ context_summary   上下文摘要
│    └─ urgency           low / normal / high / critical
├─ candidate_options  候选选项(通常 2-4 个)
│    └─ [ { id, label, description, consequences } ]
├─ evidence_requirement 证据要求
│    ├─ required_artifacts 必看的 Artifact
│    └─ required_reviews   必要的评审记录
├─ decision_maker     决策方(user / specific-member / approval-quorum)
├─ autonomy_level     Research 自主性 5 级(1=人批 ... 5=AI 全自主观察)
├─ timeout_policy     超时策略(auto-approve / auto-reject / escalate)
├─ resolution         决策结果(决策前为 null)
│    ├─ chosen_option_id
│    ├─ decided_by
│    ├─ decided_at
│    └─ decision_rationale
├─ audit_trail        审计链(每次状态变更都有条目)
├─ state              pending / in_review / decided / expired / cancelled
└─ trace_id
```

**十种默认 kind**:

| kind | 触发时机 | 典型 decision_maker |
|---|---|---|
| `kickoff` | 项目启动 | user |
| `requirements-confirm` | 需求整理完 | user |
| `design-choice` | 多个方案待选 | user 或 tech-lead |
| `prototype-approval` | 原型产出后 | user |
| `code-review` | 代码提交后 | tech-lead / peer reviewers |
| `release-confirm` | 发布生产前 | user |
| `impact-assessment` | AIIA 必须前置 | user + auditor |
| `quality-gate` | 某 25010 特性评估 | qa + user |
| `archive-confirm` | 项目归档前 | user |
| `custom` | 组织自定义 | 视情况 |

**六段式的意义**:每个 Gate 必须有完整的六段,缺任何一段都不能"通过审批",这是对齐 42001 §A.9 Responsible Use 的硬约束。

**不变量**:
- Gate 一旦 `decided` 不可修改 resolution(要改发新 Gate)
- `audit_trail` 只 append
- `autonomy_level=5`(AI 全自主)的 Gate 必须有对应的 Policy 显式授权

#### 7.2.2 `Policy`(聚合根)

**组织级策略**,下发到各域的约束规则。

```
Policy
├─ policy_id
├─ kind               tool-whitelist / data-access / release-policy /
│                    impact-assessment-required / role-permission / custom
├─ scope              organization / project / role / specific-member
├─ scope_target       (scope 的具体目标)
├─ rules              规则集(DSL 或 schema)
├─ effective_from / effective_until
├─ priority           冲突时的优先级(shared_rules 最高,见 Research 指令优先级)
├─ version
├─ approved_by
└─ lifecycle          draft / active / superseded / retired
```

**Policy 下发路径**:
```
Policy 发布
  └─ observability 记审计
  └─ Runtime PolicyCache 订阅更新(下次 LLM Loop 生效)
  └─ member-service 重评 ProjectMember.tool_scope
  └─ capability-hub 重评 MCP Server 白名单
```

#### 7.2.3 `Control`(聚合根)

**ISO 42001 附录 A 控制项的落地**。

```
Control
├─ control_id         (对齐 42001 编号如 A.4.2)
├─ category           42001 9 族之一
├─ display_name
├─ description
├─ applicability      applicable / not-applicable
├─ implementation_status  not_implemented / partially / implemented / verified
├─ evidence_refs      证据 Artifact 链接
├─ review_cycle       review 周期(年度 / 项目触发)
├─ owner              责任人
└─ last_reviewed_at
```

**Gate vs Control 区别**:
- **Gate** 是"事件驱动的一次性决策请求"
- **Control** 是"持续保障的控制项"

一个 Control 在运行中可能触发多个 Gate,但本身不是 Gate。

#### 7.2.4 `Approval`(Gate 内的实体)

当 `decision_maker` 是 `approval-quorum`(多人审批)时,记录每个参与者的投票。

```
Approval
├─ approval_id
├─ gate_id
├─ approver
├─ vote             approve / reject / abstain
├─ rationale
└─ voted_at
```

#### 7.2.5 `ImpactAssessment`(聚合根,与 Artifact 双身份)

42001 §8.2 要求的 AIIA,既是治理活动(聚合根)又是制品(Artifact)。

```
ImpactAssessment(AIIA)
├─ aiia_id
├─ project_id
├─ assessment_scope   评估的范围
├─ affected_parties   受影响方清单
├─ impact_types       福祉 / 权利 / 安全 / 公平 / 环境 / 经济 的六维评估
├─ impact_severity    low / medium / high / critical
├─ mitigation_plan    缓解措施清单
├─ residual_risk      残余风险
├─ conducted_by
├─ reviewed_by
├─ status             draft / in_review / approved / superseded
└─ artifact_ref       → 制品域的镜像 Artifact
```

**双身份**:
- 治理域把 AIIA 当**治理活动**(有状态机、可评审)
- 制品域把 AIIA 当**可审计资产**(带 artifact.kind=ImpactAssessmentReport)
- 同一个实体,两个视角,不是复制

├─ approved_by

```

### 7.5 与标准对齐

| 条目 | 对齐 |
|---|---|
| Gate 六段式 | **24748-2 Decision Gate** + **42001 Control** + **9001 Approval** 综合 |
| Gate 十 kind | **24748-2 典型 Gate 类型** + **42001 Control Families** |
| autonomy_level 5 级 | **Research 自主性 5 级(arxiv 2506.12469)** |
| Policy 优先级 | **Research 指令冲突优先级(arxiv 2509.23188)** |
| Control 38 项 | **42001 附录 A 直接映射** |
| AIIA | **42001 §8.2 + ISO/IEC 42005** |
| SoA | **42001 §6.1.3** + **27001 SoA 机制**(异曲同工) |
| 审计链 | **9001 §7.5** + **三红线可审计性** |
| 纠正措施 | **9001 §10.1 + 42001 §10.1** |

### 7.6 关键设计决策

- **Gate 是一等对象,不是 BPMN UserTask 的特化** —— 这是 Quantalithos 最核心的差异化,参见 `product/最终目的.md` §3.5
- **Gate 必须六段完整** —— 缺任何一段不允许决策,硬约束,不妥协
- **autonomy_level 不是"AI 可信度"** —— 是**用户刻意选择**让渡给 AI 多少自主权,用户可以随时收回
- **Policy 有优先级,shared_rules 不可覆盖** —— 对齐 Research 指令冲突优先级,防止 jailbreak
- **AIIA 有双身份(治理 + 制品)** —— 不做两份副本,用"视图"体现
- **治理事件都 append,审计链不可篡改** —— 对齐 9001 + 42001 + 三红线

## 八、制品域 Artifact

### 8.1 使命

定义**产出什么可审计资产**。承载产品叙事里"可观察"承诺的"可审计 / 可追溯"那一半。

制品域回答:
- 系统产出了什么?
- 谁产出的、基于什么 / 什么时候 / 哪次讨论?
- 当前版本、被哪些项目引用、质量如何?
- 哪些被冻结为 Baseline?

### 8.2 聚合根

#### 8.2.1 `Artifact`(聚合根)

**所有可审计产出的统一抽象**。

```
Artifact
├─ artifact_id        ULID
├─ project_id         归属项目(可空:组织级 Artifact)
├─ kind               requirement / design / adr / prototype / code /
│                    test-plan / test-report / user-doc / release /
│                    lessons-learned / dataset / impact-assessment /
│                    soa / compliance-declaration / operational-log / custom
├─ title
├─ description
├─ content_ref        内容位置(文件路径 / 对象存储 URI / inline)
├─ format             markdown / pdf / figma / notebook / git-ref / custom
├─ version            semver
├─ authors            作者列表(ProjectMember 引用)
├─ reviewers          评审者列表
├─ approved_by        批准人(进入 approved/baselined 时必填)
├─ produced_in_activity 产生此制品的 Activity 引用
├─ related_workitem    对应的 WorkItem 引用(可多个)
├─ conversation_refs   相关 Conversation Turn 引用
├─ quality_tags        25010 特性标签
├─ quality_subtags     25010 子特性标签
├─ compliance_role     合规角色(evidence / policy / reference / none)
├─ state               initiated / reviewed / approved / baselined /
│                     published / superseded / archived
├─ created_at / modified_at
└─ trace_id
```

**状态机**(24748-2 + 9001 结合):

```
  [创建]
    │
    ▼
┌─────────────┐
│ initiated   │ 初稿 —— 尚未评审
└──┬──────────┘
   │ submit-for-review
   ▼
┌─────────────┐
│ reviewed    │ 已评审 —— 评审意见记录但未批
└──┬──────────┘
   │ approve
   ▼
┌─────────────┐
│ approved    │ 已批准 —— 可被引用、可成为 baseline 候选
└──┬──────────┘
   │ baseline(经 Gate 批准)
   ▼
┌─────────────┐
│ baselined   │ 冻结基线 —— 进入 Project.baseline_ids
└──┬──────────┘
   │ publish(发布到外部 / 归档)
   ▼
┌─────────────┐
│ published   │ 发布 —— 对外可见
└──┬──────────┘
   │ supersede(新版本替代)   │ archive
   ▼                        ▼
┌─────────────┐          ┌──────────┐
│ superseded  │          │ archived │
└─────────────┘          └──────────┘
```

**关键不变量**:
- Artifact.content 一旦 `approved` 不可修改(要改发新版本)
- `baselined` 的 Artifact 纳入 Project.baseline_ids,变更必须经过变更控制流程(通常重新 Gate)
- `superseded` 必须指向后继 Artifact(supersedes_by 字段)
- 删除不允许,只能 `archived`(物理删除需要特殊合规流程,且留墓碑)

**16 种 kind 对齐**(见 §标准对齐):

| kind | 来源 |
|---|---|
| `requirement` | 12207 / 29148 |
| `design` | 12207 / 42010 |
| `adr` | 架构设计.md §7 |
| `prototype` | 24748-2 |
| `code` | 12207 |
| `test-plan` / `test-report` | 29119 / 12207 V&V |
| `user-doc` | 42001 A.8 |
| `release` | 12207 Release |
| `lessons-learned` | 9001 改进 / Scrum Retro |
| `dataset` | 25012 + 42001 A.7 |
| `impact-assessment` | 42001 §8.2 / 42005 |
| `soa` | 42001 §6.1.3 |
| `compliance-declaration` | 24748-2 + 42001 归档 |
| `operational-log` | 42001 §9.1 / 9001 |
| `custom` | 项目扩展 |

#### 8.2.2 `ArtifactRelation`(值对象)

```
ArtifactRelation
├─ from_artifact_id
├─ to_artifact_id
├─ relation_kind      derives-from / implements / verifies / validates /
│                    replaces / references / contains
└─ metadata
```

**七种关系**:
- `derives-from` — 设计源自需求
- `implements` — 代码实现设计
- `verifies` — 测试验证代码
- `validates` — UAT 确认满足需求(与 verifies 不同:前者是"做对了",后者是"做对了事情")
- `replaces` — 新版替代旧版(对齐 `supersedes_by`)
- `references` — 软引用
- `contains` — Release 包含多个 Artifact

这套关系是 **Artifact 血缘图** 的基础,对齐三红线"可追溯性"。

#### 8.2.3 `Baseline`(聚合根)

**Project 的 Baseline,是被冻结的 Artifact 集合**。

```
Baseline
├─ baseline_id
├─ project_id
├─ baseline_kind      requirements / design / product / release
├─ member_artifact_ids 组成的 Artifact 清单(每个 pin 到特定版本)
├─ name               如 "V1.0 Requirements Baseline"
├─ description
├─ frozen_at
├─ frozen_by
├─ gate_ref           触发冻结的 Gate 引用
└─ lifecycle          active / superseded / archived
```

**典型 Baseline**(24748-2 推荐):
- Requirements Baseline — 需求冻结
- Design Baseline — 设计冻结
- Product Baseline — 发布前的整体冻结
- Release Baseline — 发布版本的 Artifact 组合

**Baseline vs Artifact 的区别**:
- Artifact 有版本,但 Artifact 本身不是 Baseline
- Baseline 是"某时点的 Artifact 版本快照集合"
- Artifact 修改 ≠ Baseline 修改(修改某 Artifact 要发新版,旧版仍然被 Baseline 引用)

#### 8.2.4 `DatasetArtifact`(Artifact 的特化)

**AI 训练/验证/测试数据集**的特化。

```
DatasetArtifact(继承 Artifact)
├─ data_provenance     数据来源追溯(42001 A.7)
├─ data_license        许可
├─ data_quality_score  25012 数据质量评分
├─ bias_evaluation     偏见评估记录
├─ privacy_category    PII / sensitive / public 等
└─ retention_policy    数据保留策略
```

对齐 **ISO 25012 数据质量模型** 和 **42001 A.7 数据治理控制族**。

### 8.5 与标准对齐

| 条目 | 对齐 |
|---|---|
| Artifact 状态机 | **24748-2 Baseline** + **9001 文档生命周期** |
| 16 种 kind | 多标准综合(见上表) |
| 7 种 ArtifactRelation | **15288 SoI 血缘** + **12207 WorkProduct relation** |
| quality_tags | **25010 9 特性** |
| quality_subtags | **25010 31 子特性** |
| compliance_role | **42001 §7.5 文档化信息分类** |
| DatasetArtifact | **25012 数据质量** + **42001 A.7** |
| Baseline 概念 | **24748-2 Baseline** |

### 8.6 关键设计决策

- **Artifact 不可变更内容,只能发新版** —— 对齐 Event Sourcing 理念和 9001 审计
- **16 种 kind 枚举** —— 硬约定,新 kind 必须走 ADR(避免 kind 泛滥成"custom")
- **Baseline 是聚合根,不是 Artifact 的字段** —— 因为 Baseline 跨多个 Artifact,有自己的生命周期
- **DatasetArtifact 特化** —— AI 特有需求,不和通用 Artifact 混
- **validates 和 verifies 区分** —— V&V 的核心区别,对齐 12207 §6.4 V&V 过程
- **Artifact 血缘是图,不是树** —— 一个 Artifact 可有多个 derives-from(综合多个需求)

## 九、横切四条

六域之外,有四条**跨所有域**的横切能力。它们不是域,但是六域都要消费的基础设施。

### 9.1 观测横切(Observability)

**载体仓**:`quantalithos-observability`(L4)

**承载**:
- OTel GenAI 语义约定的 Span / Metric / Log 采集
- W3C Trace Context 贯穿
- 审计事件的不可变 append-only 存储(哈希链保护)
- Artifact / Turn / Activity / Gate 血缘查询 API
- DORA / EBM 指标聚合

**与六域的关系**:
- 每个域在每次写操作后**必须发事件**(不是可选)
- 每个事件**必须**携带 trace_id(不是可选)
- 事件进入 observability 的 append-only 存储后**不可修改**

**对齐三红线**:
- 可审计性:所有写操作留痕 + 哈希链不可篡改
- 可追溯性:从 Artifact 反向查到 Turn / Member / WorkItem / Activity 的全链路

### 9.2 能力池横切(Capability Hub)

**载体仓**:`quantalithos-capability-hub`(L3)

**承载**:
- MCP Server 注册表(Tool 工具集)
- A2A Node Directory(外部 Agent)
- Provider Contract(模型提供商如 Anthropic / OpenAI)
- Capability 到工具的映射(SPEM Capability → 具体 Tool)
- 白名单 + 审计 + 成本度量

**与六域的关系**:
- 身份域的 Role 声明"需要的能力"→ capability-hub 解析为具体 Tool 集
- 过程域的 Activity 通过 capability-hub 调用 MCP Tool
- 治理域的 Policy 下发到 capability-hub 作为白名单规则

**对齐**:**42001 A.10 第三方治理** + **MCP 安全(Research)**

### 9.3 方法库横切(Method Library)

**载体仓**:`quantalithos-method-library`(L3)

**承载**(4 类方法资产 + 2 类复用聚合):
- ProcessTemplate 的完整定义(SPEM Method Content)
- RoleDefinition / TaskDefinition / WorkProductDefinition
- **ViewProfile**(ADR-0009)—— 按 Role × 对象 kind 定义字段可见性 / 脱敏 / 派生字段,作为 SPEM Guidance 的延伸
- AIPolicy / AIObjective 的组织级声明(42001 §5.2)
- 过程模板的 Plugin 机制(MethodPlugin)
- 组织级方法集组装(MethodConfiguration + Variability)

**与六域的关系**:
- 身份域的 Role 引用 method-library 的 RoleDefinition(只存引用)
- 过程域的 ProcessTemplate 引用 method-library 的 Method Content;ActivityDef.completion_policy(ADR-0008)在本仓定义
- 治理域的 AIPolicy 定义存储在 method-library;governance.Policy 是运行时规则引用
- **UI 层(chat / console / mobile)消费 ViewProfile**(ADR-0009)渲染 Role 视图,L1 六域全量返数据、不按 Role 过滤

**对齐**:**SPEM 2.0 Method Content / Plugin / Configuration / Variability**

### 9.4 评估改进横切(Evaluation)

**载体仓**:暂无独立仓,分布在 observability(指标)+ console(可视化)+ governance(管理评审)

**承载**:
- DORA 四指标:Lead Time / Deployment Frequency / Change Failure Rate / Recovery Time
- EBM 四维度:Current Value / Unrealized Value / Time to Market / Ability to Innovate
- 25010 质量特性度量(映射到 Artifact.quality_tags)
- 42001 §9.1 监视测量(模型漂移 / 偏见 / 鲁棒性)

**与六域的关系**:
- 消费所有域的事件,不生产事件
- 反向驱动 governance 域的 Management Review
- 反向驱动 method-library 的 Template 演进(基于 lessons-learned)

**对齐**:**DORA + EBM + 42001 §9.1**

  └─ artifact_relation → derives-from requirement-v0.2
                         │
                         └─ (递归追溯 requirement-v0.2)
```

**任何一个 Artifact**,都能通过六域的交叉引用**追溯到**:
- 谁做的(identity)
- 在什么讨论里诞生(conversation)
- 对应什么需求(work + artifact 血缘)
- 走过什么规矩(process)
- 经过哪些批准(governance)

这就是**三红线可追溯性的技术落地**。

### 11.3 本文的修订纪律

- **不变量** 的任何修改必须经过 ADR
- **聚合根** 的新增或删除必须经过 ADR + 产品叙事检视
- **状态机** 的新增状态或转移必须经过 ADR
- **发布事件** 的字段新增属 minor,删除或改 semantic 属 major,都要 ADR
- **订阅事件** 的新增属 minor,不需要 ADR(因为只影响订阅方)
- **文字订正 / 示例补充** 不需要 ADR,但要在 git commit 里写清楚修改

## 附录 B:设计原则审视(对照 feedback_design_principles.md)

| 原则 | 本文体现 |
|---|---|
| **SRP(单一职责)** | 每个域一个使命,不越界;§1.3 平权原则 |
| **OCP(开闭原则)** | Artifact kind / Gate kind / WorkItem kind 枚举扩展走 ADR,不改既有代码 |
| **DIP(依赖倒置)** | 六域通过事件解耦,不直接依赖其他域的实现 |
| **DRY** | 同一概念只在一个域定义(ProjectMember 只在 work,不在 identity 重定义) |
| **KISS** | 每个域最多 5-6 个聚合根,不堆叠"防御性聚合" |
| **YAGNI** | `custom` kind 作为扩展入口,但默认不允许新 kind 无 ADR 落地 |
| **最小知识** | 订阅事件表最小化,只订必要的 |
| **关注点分离** | 横切四条独立承载,不混入六域 |
| **可扩展性** | ProcessTemplate Plugin / Role 扩展 / Policy 扩展 |
| **可演进性** | 每个聚合根的 version + semver,schema 向后兼容 |
| **可组合性** | 六域可独立部署,多项目多组织可组合 |
| **可观测性** | 强制每次写发事件,横切 observability 统一消费 |
| **不可变优先** | Artifact / Turn / AuditEvent / Baseline 都不可变 |
| **显式优于隐式** | 所有状态机都画出来,所有不变量都列出 |
| **幂等性** | 事件订阅方必须处理重复投递(§2.2 第 5 条) |
| **前置条件** | 每个聚合根状态机都有明确入口条件 |
| **后置条件** | 每个事件都有明确的"发出条件" |
| **不变量** | 每个聚合根章节都列了不变量清单 |
| **Fail Fast** | 状态机违法转移立即报错,不容忍"半合法"状态 |

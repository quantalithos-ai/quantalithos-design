## 一、一句话定位

**Quantalithos AI 是一个 AI 驱动的软件研发协作平台,让用户以"管理者"而非"开发者"的身份,通过创建机器人群聊委派任务,由一群有身份、有分工的 AI 员工在可观察的协作过程中自主完成软件项目,关键决策由用户把关,最终产出可运行的交付物。**

这一句里埋着六个不可妥协的产品定位,贯穿本文后续所有章节:

1. **用户是管理者** —— 不写代码、不画原型图、不填工单,只给出意图和批准决策
2. **员工是有身份的个体** —— 有名字、职业、能力、记忆、过往经验,可被"登录"查看在干什么
3. **协作载体是对话** —— 不是工单流转,也不是命令行,而是群聊 + 频道 + 私聊
4. **工作对象是软件项目** —— 不是单次 Q&A,不是一次性脚本,而是有生命周期、有迭代的软件系统
5. **关键节点强制人类** —— 门禁不是可选断点,而是治理结构的本体
6. **过程始终可观察** —— 任何时候打开 app,都能看见大家在干嘛、卡在哪、为什么这样决策

## 二、我们要解决什么问题

### 2.1 用户真实的痛点

对想要做软件的人而言,当前有两类尴尬处境:

**处境 A — 不是开发者,想把想法变成软件**

想做一个博客系统、一个工具、一个小型业务系统的人,今天的选择要么是找外包、要么是自己学编程、要么是用低代码平台(但又受限于平台提供的模块)。

即便用了 Cursor、Copilot 这类 AI 编程助手,仍然需要自己懂技术栈、会写代码、会管项目。AI 在帮"怎么写这行代码",但不帮"怎么做成一个完整的软件"。

**处境 B — 是开发者,但需要的是一个完整团队**

一个开发者一天做的事不只是写代码:需要想清楚需求、画出原型、做架构决策、写测试、做代码评审、跑部署、写文档、回应变更。

"多角色协作"是人类组织软件开发的成熟形态 —— 产品经理、技术负责人、后端工程师、前端工程师、测试、DevOps、UX 设计师各司其职。**而今天的 AI 工具全是"单 Agent 对一个人"**,没有一个产品让你拥有一整个可以互相讨论、分工、审查、交付的 AI 团队。

### 2.2 现有产品为什么不够

| 现有产品 | 形态 | 缺的是什么 |
|---|---|---|
| Cursor / GitHub Copilot | 单 Agent + IDE 内嵌 | 没有协作、没有流程、没有多角色 |
| Claude Code / Codex | 单 Agent + CLI | 同上,加上对非开发者不友好 |
| OpenClaw / Superpowers | 多 Agent CLI | 命令行形态,没有可见的协作过程 |
| Devin / Factory | 黑盒"AI 工程师" | 过程不可见、不可干预、不可组合;封闭生态 |
| Lovable / Bolt / v0 | 单 Agent + Web 生成器 | 只生成静态产物,没有项目生命周期 |
| Jira / Linear + AI 插件 | 工单系统 + AI 辅助 | AI 是工具,不是"员工"身份 |

共同缺口:**没有任何产品把"多 AI 员工作为一个开发团队协作"当作一等产品形态。**

### 2.3 我们填什么缺

我们不是再做一个 AI 编程助手,也不是再做一个项目管理平台。

我们做的是:**让"管理一个开发团队"这件事在 AI 上成为可能,且过程对管理者始终透明。**

这是一个**新品类**,而不是对现有品类的改良。它的最近邻近物不是开发工具,而是"虚拟办公室 + ERP + AI 员工"的结合。

## 三、核心产品叙事

从第一节的一句话定位展开为六条不可妥协的叙事承诺。这六条是产品的"不可拆解骨架",任何设计决策都不能违背其中任何一条。

### 3.1 用户是管理者,不是开发者

用户面对 Quantalithos 时,承担的角色是**管理者**:表达意图、做关键决策、看结果、提要求。

**用户不需要做的事**:
- 不需要知道用什么编程语言、框架、数据库
- 不需要写代码、看代码、改代码(除非主动选择)
- 不需要写需求文档、原型图、测试用例
- 不需要管理工单、分配任务、追进度
- 不需要懂 Git、CI、部署、沙箱

**用户需要做的事**:
- 讲清楚要做什么、为什么要做
- 在关键节点做判断:这个原型对不对、这个方案选哪个、这个验收通不通过
- 在过程中回应 AI 员工的提问和提议
- 管理自己的员工队伍:招聘、分组、下线

这条叙事约束了所有前端交互的默认语言 —— 不应该出现"编译失败请点这里"、"请选择分支策略"这种面向开发者的表述。如果某个操作必须让用户面对技术细节,说明产品设计失败了。

### 3.2 AI 员工是有身份的个体

AI 员工不是"任务执行器",也不是"对话实例",而是**有持久身份的个体**。

每个 AI 员工有:
- **唯一 ID 和名字**:ID 唯一,名字可以重复(像真实公司里可以有多个叫"张伟"的)
- **职业和能力画像**:后端工程师、QA、UX 设计师…;每种职业有特定技能和可用工具
- **记忆**:工作记忆(当前任务的上下文)、情景记忆(过往协作过的人和事)、语义记忆(习得的领域知识)
- **职业生涯**:过去参与过哪些项目、交付过什么、被谁夸奖过、犯过什么错
- **生命周期**:招聘(hire)→ 活跃(active)→ 暂停(paused)→ 退休(retired / archived)
- **可被"登录"**:用户可以进入某个员工的视角,看他当前在和谁聊什么、手头有什么任务

**从这条叙事衍生出的产品能力**:
- 员工列表页(像通讯录)
- 员工个人主页(像领英)
- 员工登录视图(像 Shadow)
- 员工能力编辑(像技能树)
- 员工绩效与审计视图(像 HR 系统)

这条叙事把"Agent 实例"从一个技术概念升级为一个**产品概念**。员工是**产品的第一公民**,不是运行时的副产品。

### 3.3 协作载体是对话

协作的主要载体是**对话**,不是工单,也不是看板。

**对话的三种形态**:
- **群聊**:一个项目一个群组,所有参与者可见,消息实时到达
- **频道**:群内子话题;参与方自己选,群聊对频道无感知;频道结果可反馈回群聊
- **私聊**:任意两人之间的点对点对话

**一切决策、讨论、门禁、产出都表现为对话消息或对话内的卡片**:
- 用户要立项 → 在和 Assistant 的私聊里说
- AI 员工要讨论方案 → 在项目群聊或频道里讨论
- 门禁要请求用户审批 → 在群聊里出现一张 GateCard
- 代码评审 → 在频道里讨论、投票、归并
- 交付验收 → 在群聊里推送预览 + 审批卡

这条叙事的深层含义是:**Conversation 是一等聚合根**。不是"某个消息服务的附属数据",而是独立的、有生命周期的、可搜索、可订阅、可审计的领域对象。

### 3.4 工作对象是软件项目

工作不是一次问答、不是一次代码生成,而是**软件项目** —— 有目标、有范围、有迭代、有版本、有交付物、有持续演进。

**项目的必备结构**:
- 项目有自己的身份、目标、当前阶段、Baseline
- 项目下有 Backlog(需求 / 任务 / Bug / 原型 / Spike / 评审)
- 项目内的 WorkItem 有依赖、状态、负责人
- 项目产出 Artifact(需求 / 设计 / 代码 / 测试 / 文档 / 发布包),Artifact 之间有血缘
- 项目可以结束、归档、复活、分叉

这条叙事的深层含义是:**不做一次性生成类产品**(那类产品是"Bolt / v0"的形态)。我们做的是**可持续演进的软件系统**,交付后还能接受需求变更、Bug 修复、新功能追加。

### 3.5 关键节点强制人类

门禁不是"可选的暂停点",而是治理结构的本体。

**门禁的四种典型触发**:
- 需求确认 —— AI 团队整理完需求清单和原型,用户必须批一次
- 方案选择 —— 架构 / 技术栈 / 外部依赖的关键决策,用户二选一或三选一
- 验收审批 —— 功能做完后用户验收
- 发布确认 —— 发布到生产前,最后一次确认

**门禁是一等对象**,不是某个状态机的附属字段。它有:
- 发起方(谁要求审批)
- 决策方(谁来批)—— 通常是用户,有时是特定员工
- 候选选项(通常两到三个)
- 证据要求(看什么原型 / 看什么报告才能批)
- 超时策略(多久不批怎么办)
- 决策后果(批了之后谁执行什么)
- 审计轨迹(每一次批拒都留痕)

这条叙事决定了:**用户被有意地、反复地拉回到决策回路里**。我们不提供"全自动、一键完成"的体验,因为那种体验在真实软件开发里不成立 —— 关键决策必须有人负责。

### 3.6 过程始终可观察

任何时候打开 app,用户都应该能看见:
- **全局**:哪些项目在跑、哪些在等审批、哪些卡住了
- **项目**:当前在做什么阶段、下一个节点是什么、关键瓶颈在哪
- **员工**:这个员工现在在干什么、和谁聊、在用什么工具、为什么这样判断
- **过程**:某个文件是谁写的、基于什么讨论、对应哪条需求、经过谁评审
- **审计**:任何写操作都有不可变记录,任何决策都可追溯到一句话、一次会议、一个门禁

**"可观察"不是运维的事,是产品的事**。它服务于两个目的:
1. **信任**:用户愿意把事情交给 AI,是因为随时能看、能介入、能叫停
2. **治理**:组织(尤其企业)使用 AI 做软件时必须能审计,符合 ISO 9001 / 27001 / 42001 的要求

这条叙事与三条横切红线(可审计性 / 可追溯性 / 可裁剪性)对齐 —— 那三条是它的技术实现形态。

## 四、谁是我们的用户

### 4.1 主要用户画像

**画像 A — 有想法但不是开发者的独立创造者**

- 懂自己要解决什么问题,但不会写代码
- 曾经尝试过外包、低代码、找朋友帮忙,都不满意
- 愿意为"自己能管理一个 AI 开发团队"付费
- 典型场景:做个人工具、副业产品、内部运营系统

**画像 B — 小团队管理者 / 产品经理 / 独立咨询师**

- 需要快速把需求变成可交付产品,不一定追求极致性能
- 手头同时跑多个项目,需要多线程作战能力
- 更在意"过程可控、可审计、可交代"而不是"最省事"
- 典型场景:创业公司 CTO、PM 自己带项目、为客户交付定制化系统

**画像 C — 企业内的创新负责人 / AI 主管**

- 被要求"把 AI 用于内部研发效率",但不满足于 Copilot 的个人效率
- 需要的是"组织级的 AI 研发能力",对审计、合规、可追溯有硬要求
- 愿意引入平台、做培训、做治理
- 典型场景:大企业 IT 部门、金融 / 医疗 / 制造业的数字化转型

### 4.2 次要用户画像

**画像 D — 经验丰富的开发者 / 架构师**

- 不是核心用户,但可能成为高级使用者
- 扮演"AI 团队的 Tech Lead"角色 —— 在关键架构决策上介入,在员工能力画像上定制
- 把 AI 员工当作"延伸自己的能力"的杠杆
- 对他们而言,Quantalithos 的价值是:**组织层面的杠杆,不是个人编辑器**

**画像 E — 方法论 / 规范制定者**

- 会深度使用 method-library,定义组织的标准流程 / 角色能力 / 审查规则
- 把 Quantalithos 当作"把自己的方法论实例化到 AI 上"的载体
- 典型场景:教练、咨询师、QA 专家、合规官

### 4.3 显式不服务的用户

清楚谁**不是**用户,能避免产品被稀释:

- **想用 AI 替代完整开发岗位的雇主** —— 我们不做"让 AI 替代开发者"的叙事。AI 员工是**放大管理者的能力**,不是"员工下岗替代品"
- **追求极致性能 / 极致成本优化的资深开发团队** —— 这类团队更适合用自己的 Cursor + 自己的工程实践
- **寻找通用 Chat 助手的用户** —— 我们不是 ChatGPT 的替代品;我们的对话是为了"做软件项目"而存在
- **低代码平台的目标用户** —— 那类用户更适合拖拽组件 + 配置表单,我们写真实代码、做真实系统
- **希望完全不干预、一键产出软件的用户** —— 门禁是我们的本体,不是障碍

## 五、核心体验 —— 一个端到端故事

用户 Alice 想做一个"博客系统",用来写自己的读书笔记。她从没写过代码。

### 时刻 0:进入

打开 Quantalithos app(桌面客户端、PWA、手机 App 均可),她看到自己的主界面:

- 左侧:收件箱(通知 / 审批)、我的项目(空)、我的员工(默认招聘了一位 Assistant)
- 中间:和 Assistant 的私聊
- 右侧:当前选中对象的详情面板

### 时刻 1:表达想法

Alice 在和 Assistant 的私聊里说:"我想做一个博客系统,用来写读书笔记。"

Assistant 并不直接开始写代码,而是问她几个澄清问题:
- 这个博客是给你自己写的,还是希望别人能订阅?
- 希望手机能看吗?
- 读书笔记会有书的封面、评分、分类吗?
- 大概希望什么时候有第一个能用的版本?

Alice 回答后,Assistant 提出:"我建议我们按'个人博客 + 读书专题'的小型 Web App 方法开始。我会为你组建一个 4 人小团队。"

她点"继续"。

### 时刻 2:团队组建

Assistant 建了一个群组叫"读书博客项目",自动拉入四位员工:
- **Marcus** — Tech Lead(团队负责人)
- **Zhao** — 后端工程师
- **Lee** — 前端工程师
- **Nina** — QA

四位员工各自在群里简短自我介绍:"我叫 Marcus,做过三个类似规模的项目,这次由我来做技术决策..."

Alice 感觉像在参加一个项目的 kickoff 会。

### 时刻 3:需求讨论

Marcus 在群里领头,引导其他员工和 Alice 一起整理需求。20 分钟后,Marcus 产出了一份需求文档 + 一个可点击的低保真原型。

群聊里弹出一张 **GateCard**:"请用户确认需求清单和原型。"附有文档链接和原型预览。

Alice 打开原型,点了几下,觉得评分那里不对,评论一句:"能不能把评分改成文字标签,比如'必读 / 值得一读 / 一般'?"

Marcus 回应、改动原型、再请批。Alice 这次点"通过"。

### 时刻 4:方案与实施

Marcus 拉了一个频道叫"技术方案讨论",和 Zhao / Lee 短暂讨论后拿出两个方案(分别以简洁性和可扩展性为重),发到群聊让 Alice 选。Alice 选了简洁性方案。

方案定了,Zhao 和 Lee 并行开工。群聊的侧边栏实时显示:
- 当前进度:需求完成 / 设计完成 / 开发 30%
- 当前在做的任务:Zhao 在做 API,Lee 在做首页
- Nina 在写测试用例

Alice 好奇点开 Zhao 的视角(登录员工),看到 Zhao 正在写数据库模型,旁边有他当前的思考:"Alice 提到要分类,我需要加 Category 表..."

Alice 觉得有趣但不干预,关闭视角回到群聊。

### 时刻 5:评审与验收

Zhao 提交第一个 PR,Marcus 和 Nina 在频道里评审。Nina 发现一个边界问题,Zhao 改,然后并入。

几轮之后,项目进入"验收阶段"。群聊里出现一张验收 GateCard:"博客系统已部署到预览环境,请您确认是否可以发布。"附有预览链接。

Alice 点开预览,发布了一篇测试文章,一切正常。她点"通过"。

### 时刻 6:上线与演进

系统被发布到 Alice 自己的域名(由 Quantalithos 的 runner / 部署能力处理)。Alice 开始用它写真实的读书笔记。

三周后,她回到群聊说:"我想加一个功能,让朋友能订阅 RSS。"

Marcus 回应:"好,让我们按同样的流程走一次。"需求 → 设计 → 实施 → 验收 → 发布。

这次流程更短 —— 员工记得这个项目的历史,不用再重新做架构决策;用户也更熟悉,对话更精简。

### 这个故事里隐含的产品要求

- 用户从头到尾**没有看到一行代码**(除非她主动要看)
- 用户从头到尾**只做了三类事**:说意图、回答澄清、批准决策
- 用户**能看到所有人在做什么**,但**不被信息淹没**
- 用户**可以选择深入**(登录某个员工),也可以**选择放手**(后台运行)
- **一切可追溯**:为什么这样做、谁做的、经过谁批准 —— 随时能查

## 六、能力要求(去阶段化,按能力族组织)

以下列出做到本产品叙事所必需的能力。**按能力族组织,不按 Phase 或层级排序** —— 阶段和层级属于 `roadmap/`,不属于本文。

每项能力后用方括号标注该能力属于哪个 L 层(L0 共享契约 / L1 六域服务 / L2 Member 运行 / L3 方法能力 / L4 基础设施 / L5 用户界面 / L6 生态),方便后续路线图映射。L 层定义参见 `architecture/开发路线图.md`(待写)。

### 6.1 项目启动能力族

- 用户意图识别 —— 从自然语言判断想做什么、规模多大、紧急度多高 [L2]
- 方法选择 —— 从方法库选择适配的过程模板(小型 Web App / 数据分析 / AI 项目 / …) [L1 Process 域 + L3 Method Library]
- 团队组建 —— 查询员工池、按 Profile 要求的角色分配员工 [L1 Identity 域]
- 项目身份建立 —— 创建 Project 聚合根、Baseline、群组、默认频道 [L1 Work + Conversation 域]

### 6.2 需求与设计能力族

- 对话式需求探索 —— 员工会主动提问、引导用户澄清目标 [L2]
- 原型生成与预览 —— 生成可点击原型,用户在对话内直接预览 [L1 Artifact 域 + L5 Chat 前端]
- 需求评审 —— 多员工在频道讨论、汇总意见回群 [L1 Conversation 域]
- 方案选择门禁 —— 提供 2-3 个方案让用户选,不替用户决策 [L1 Governance 域]
- 设计文档产出 —— 需求 / 设计 / ADR 都作为 Artifact,带血缘、带状态 [L1 Artifact 域]

### 6.3 实施能力族

- 编码 —— 员工能读写文件、运行代码、调用工具 [L2 Member + L2 Tools]
- 版本控制 —— 代码变更走 Git,每次提交有明确责任人和讨论引用 [L2 Tools + L4 Sandbox]
- 测试 —— 员工能写单测、跑测试、分析失败 [L2 Tools]
- 代码评审 —— 评审是频道讨论,打回→修改→重审是正式流程 [L1 Process + L1 Conversation]
- 并行实施 —— 多员工并行推进不同 WorkItem,依赖图约束执行顺序 [L1 Work + L1 Process]
- 跨员工协作 —— 员工可以 @ 另一个员工、建频道讨论、短暂求助 [L1 Conversation]
- 沙箱隔离 —— 所有代码执行在受控的沙箱里,不污染用户主机 [L4 Sandbox]

### 6.4 验收与发布能力族

- 集成测试 —— 在沙箱或预览环境跑完整套流程 [L4 Sandbox]
- 预览部署 —— 用户在对话内直接预览当前版本 [L4 Sandbox + L5 Chat 前端]
- 验收门禁 —— 用户对最终交付物做一次明确的 yes/no [L1 Governance]
- 部署执行 —— 推送到用户指定的环境(自托管 / SaaS / 用户账号) [L4 Sandbox + 外部集成]
- 发布确认门禁 —— 推生产前最后一次人类审批 [L1 Governance]

### 6.5 运行与演进能力族

- 监控与回滚 —— 发布后员工继续监控一段时间,异常触发回滚审批 [L1 Process + 外部集成]
- 需求变更 —— 项目不是"一次做完",支持后续新增功能、修复 Bug [L1 Work + L1 Process]
- 记忆跨迭代 —— 员工记得这个项目的历史,不用每次从零讨论 [L2 Runtime Memory]
- 项目归档 / 复活 —— 项目可以结束、归档、再次激活 [L1 Work]

### 6.6 管理与治理能力族

- 员工管理 —— 招聘 / 编辑 / 暂停 / 退休员工 [L1 Identity + L5 Console]
- 方法库管理 —— 定义 / 修改 / 发布过程模板、角色定义、工具白名单 [L3 Method Library + L5 Console]
- 组织级审计 —— 所有项目的决策、审批、产出都可查 [L1 Governance + 横切观测]
- 指标与评估 —— DORA / EBM / 自定义指标的可视化 [横切评估 + L5 Console]
- 合规与出口控制 —— 工具白名单、数据出境策略、模型使用策略 [L1 Governance + L3 Capability Hub]

### 6.7 接入与生态能力族

- 多端接入 —— 桌面 / Web / 移动 / PWA [L5]
- 外部平台桥接 —— 在 Mattermost / Telegram / Slack / Discord 里使用 [L6 Bridges]
- SDK 二次开发 —— 用户 / 第三方可以用 Python / Rust / TypeScript 接入 [L0 SDK]
- 资产市场 —— 社区发布 / 购买 / 分享 方法 / 工具 / 员工 [L6 Marketplace]
- MCP / A2A 互通 —— 作为 MCP Client 调用第三方工具,作为 A2A 节点与外部 Agent 协作 [L3 Capability Hub]

### 6.8 可观察与可审计能力族(横切)

- 事件驱动 —— 每个域的状态变化都发出领域事件 [L0 Bus + L1 所有六域]
- 可追溯链路 —— 每个 Artifact 变化可回溯到 Conversation Turn / Member / WorkItem / ProcessInstance [L1 所有六域 + 横切观测]
- 不可变审计日志 —— append-only + 防篡改哈希链 [L1 Governance + 横切观测]
- 实时投影 —— 所有相关事件实时呈现在聊天界面 [L1 Conversation + L5 Chat 前端]
- 标准化 OTel 埋点 —— 符合 OpenTelemetry GenAI 语义约定 [横切观测]

## 七、成功的标准

"成功"分三层,目标人群不同:

### 7.1 对个体用户的成功

- Alice 说"这个产品真的让我做出了我想要的东西",且**不是作为炫技,而是作为她的常规工具**
- 她的朋友看到后也想用,而且**第一次使用就能完成一个有意义的产品**
- 一个项目从想法到第一个可用版本,**对非开发者来说通常在 1-3 天之内完成**
- 用户使用过程中感受到的核心情绪是**掌控感**,不是**失控感**或**无力感**

### 7.2 对组织的成功

- 企业愿意把 Quantalithos 作为组织级研发能力的一部分部署
- 审计官 / 合规官能从系统里导出符合 ISO 9001 / 27001 / 42001 要求的证据
- 管理者能从 Console 里看到组织的研发健康度(DORA 指标)
- 小团队 / 独立咨询师能把 Quantalithos 作为"把个人方法论放大到团队"的杠杆

### 7.3 对生态的成功

- 第三方能用 SDK 接入 Quantalithos,开发自己的集成
- Marketplace 有来自社区的方法、工具、员工角色
- Bridges 覆盖主流团队协作平台,用户不必离开既有工作流
- 本产品的**某些核心原语**(比如"有身份的 AI 员工"、"一等 Conversation"、"Gate 作为一等对象")成为行业参考

## 八、显式不做的事(Non-goals)

以下事项属于"**有意选择不做**",不是"还没来得及做":

### 8.1 产品定位的 Non-goals

- **不做通用 Chat 助手** —— 不与 ChatGPT / Claude.ai 竞争对话质量
- **不做 IDE 内嵌工具** —— 不与 Cursor / Copilot 在"写这行代码"上竞争
- **不做低代码 / 拖拽平台** —— 我们写真实代码、输出真实系统
- **不做一次性生成器** —— 不做"一键生成一个 landing page"型产品
- **不做完全封闭的黑盒** —— 反 Devin 式的"你不知道里面发生了什么"
- **不做"AI 替代开发者"叙事** —— 产品语言始终是"放大管理者",不是"替代员工"

### 8.2 用户人群的 Non-goals

- **不服务 zero-intent 用户** —— 用户必须有明确的"想做什么",不是"帮我想一个项目"
- **不服务追求极致工程优化的资深团队** —— 他们的自有工具链更贴合
- **不服务游戏 / 嵌入式 / 底层系统开发** —— 早期目标域是 Web / 工具 / 小型业务系统

### 8.3 体验的 Non-goals

- **不做"全自动、一键完成"体验** —— 门禁是本体,强制用户在关键节点介入
- **不做"静默运行、发邮件通知"体验** —— 过程可观察,不是结果推送
- **不做"学会就不用动脑"的体验** —— 管理者需要做决策,产品不会替他想

### 8.4 技术的 Non-goals

这些暂时不在本文处理,但写在这里提醒下游文档:
- 不自研基础模型 —— 我们是 LLM 的消费者,不是提供者
- 不做跨平台模型训练能力
- 短期内不做模型微调 / RLHF

## 九、产品原则

从前述叙事反推的六条**产品原则**。这些是面向**产品设计和体验决策**的原则,与 `standards/*` 下面向**工程实现**的规范是两件事。工程规范由产品原则导出,不反向。

### 原则 1:先对话,后表单

**含义**:一切任务的发起和推进,**默认载体是自然对话**;只有当对话无法结构化表达时,才退化为表单或卡片。

**适用场景**:
- 创建项目 → 在和 Assistant 的私聊里说,不是填一个"新建项目"表单
- 评审意见 → 在频道讨论,不是"请在 textarea 里填写评审意见"
- 例外:结构化选择(门禁候选选项)用 GateCard;结构化数据(员工能力配置)用表单

**Why**:管理者的原生交互是"说",而不是"填"。

### 原则 2:过程大于产物

**含义**:用户对"过程"的信任感比"产物质量"更能决定留存。

**适用场景**:
- 不吝展示 AI 员工的思考过程、犹豫、讨论
- 不因"想让结果看起来完美"而隐藏中间失败
- 任何时候用户都能看见大家在干嘛

**Why**:信任不是靠"拿出完美结果"建立,是靠"让我看到你是怎么想到这个结果的"建立。

### 原则 3:决策必须留痕

**含义**:所有关键决策(门禁、方案选择、评审结果、发布确认)必须有明确的**谁 / 什么时候 / 基于什么证据**的轨迹。

**适用场景**:
- GateCard 记录批准人、时间、上下文
- 方案选择记录是谁选的、选前看了什么、选后推演了什么
- Artifact 变化引用"我为什么这样改"的讨论

**Why**:合规的基线,信任的底座,争议时的解药。

### 原则 4:默认具名,可以匿名

**含义**:员工、讨论、决策、代码变更的默认呈现都是**有署名的**;只有在极少数合规场景下才允许匿名。

**适用场景**:
- 代码评审意见有署名
- GateCard 的发起方、决策方都具名
- 只有监管要求的"匿名举报"等场景才例外

**Why**:署名产生责任感,匿名滋生推诿。

### 原则 5:少打扰,但总可查

**含义**:默认不给用户发通知;但用户**想查什么时**一定能立刻查到。

**适用场景**:
- 不自动推送"员工 Zhao 刚做了一次 commit"
- 但用户打开 Zhao 视角,**必须**立刻看到所有 commit
- 只有门禁和异常才触发主动通知

**Why**:管理者的注意力是最贵的资源。产品要保护它,不是消耗它。

### 原则 6:可裁剪大于可扩展

**含义**:支持"去掉某个步骤"比支持"新增某个步骤"更重要。

**适用场景**:
- 过程模板必须能裁剪(小型项目去掉方案评审,原型项目去掉集成测试)
- 角色配置必须能裁剪(简单项目不需要 QA)
- 审批门禁必须能裁剪(用户信任的场景下减少打断)

**Why**:现实里用户抱怨"流程太繁琐"远多于"功能不够"。裁剪能力是产品对用户**尊重程度**的量化。

## 十、与现有 AI 编程产品的区别

| 维度 | Cursor / Copilot | Claude Code / Codex | OpenClaw / Superpowers | Devin / Factory | **Quantalithos AI** |
|---|---|---|---|---|---|
| Agent 数量 | 单 | 单 | 多(CLI) | 单("虚拟工程师") | **多,有身份** |
| 交互形态 | IDE 内嵌 | 终端 | 终端 | 网页看板 | **群聊 + 频道 + 私聊** |
| 目标用户 | 开发者 | 开发者 | 高级开发者 | 开发者 / 管理者 | **管理者 + 开发者** |
| 过程可见性 | 低 | 低 | 低 | 中(但黑盒) | **高(实时可观察)** |
| 协作模型 | 人-AI | 人-AI | AI-AI(无可视化) | AI 独立完成 | **多 AI 协作 + 人监督** |
| 流程管控 | 无 | 无 | 有(Skill 约束) | 有(隐式) | **有(BPMN + Gate + Profile)** |
| 门禁机制 | 无 | 无 | 有(脚手架) | 无(或最小) | **一等对象** |
| 项目生命周期 | 无 | 无 | 无 | 有(有限) | **完整,支持演进** |
| 员工身份 | 无 | 无 | Role(文件) | 无 | **持久实体(有生涯)** |
| 记忆模型 | 会话级 | 会话级 | 文件级 | 项目级 | **员工级 + 项目级 + 组织级** |
| 工具集成 | 有(编辑器内) | 有(MCP) | 有(插件) | 有(封闭) | **MCP + A2A + 插件** |
| 组织治理 | 无 | 无 | 无 | 有限 | **一等能力(ISO 42001 对齐)** |
| 外部平台接入 | IDE 扩展 | 终端 | 终端 | 封闭 | **桥接 Mattermost/TG/Slack/Discord** |
| 二次开发 | 插件 | 受限 | 脚本 | 封闭 | **SDK + Marketplace** |

**最关键的一点**:我们的最小单位是**"一个团队做一个项目"**,不是**"一个对话做一件事"**。其他产品在"对话"这个单位上优化;我们在"团队 × 项目"这个单位上优化。

## 十一、面向未来的演进方向

以下是产品叙事**允许**的演进方向,但**不属于当前阶段的承诺**。放在这里是为了约束当前设计"**不要做死这些方向**"。

### 11.1 更深的专业化

- 从"通用软件项目"拓展到垂直领域:数据分析项目、AI 模型项目、硬件产品设计项目、论文写作项目
- 每个领域需要特定的方法模板、角色定义、工具集 —— method-library + capability-hub 需要支持这种扩展

### 11.2 更强的 Agent 间协作

- 当前聚焦内部员工协作;未来允许**跨组织协作**(通过 A2A)
- 一家公司的 TL 可以和另一家公司的后端 AI 员工协作完成跨组织项目
- 需要在身份、信任、审计上提前留接口

### 11.3 更丰富的生态

- Marketplace 从"方法 + 工具 + 员工"拓展到"完整的垂直模板"
- 社区能发布"律师事务所用的文档处理模板"、"教学机构用的课程开发模板"
- 需要在方法库、能力池、员工镜像的对外发布契约上留足扩展空间

### 11.4 组织间协同

- 现在服务于"单一组织内的管理者 + 员工 + 项目"
- 未来可能服务于"多组织协同"(甲方 + 乙方 + 外包)
- 角色、身份、审计、合同需要提前预留多租户语义

### 11.5 人类成员的一等化

当前"员工"叙事以 AI 为主;设计上应该允许**人类员工**(真实开发者)作为和 AI 员工对等的参与者加入群组 —— 不是"用户"不是"管理者",就是"员工"之一。

- 短期:Human Member 作为可登录身份,能接管某个 AI 员工的任务
- 长期:AI 和人类员工在同一产品里无缝协作

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是继续讲概念,而是让实现者能真正开始写代码。
因此在正式落文前,必须先确认下列内容已经收稳,否则容易把 03 写成“更细一点的概要设计”或“字段表堆砌稿”。

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不应直接从“字段表 / API / 表结构”开始。
在 Quantalithos 这类平台型系统中,更稳的写法是:
- 先承接 `02-概要设计.md` 已经确认的主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与事件
- 最后再进入横向的对象模型、流程、存储、投影、异常与测试细节

> **组织原则**:这里说的“主要部分”,不是“单个对象”或“单张表”。它应按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来组织。  
> **部分 = 实现责任单元 / 协作单元 / 设计单元**。一个主要部分内部通常由多个对象、多个函数、多个状态约束以及一段相对完整的外部交互链共同构成。  
> 因此本文应按“主要部分”展开实现内容,而不是按 `Project / WorkItem / Iteration` 这类对象顺排成章。对象定义和关键函数,应作为各个主要部分内部的构件继续展开。  
> 同时还应区分三层函数: **对象成员函数**(维护不变量)、**外层编排函数**(组织流程)、**repo / projection / policy 调用**(持久化、只读、策略校验)。

这样可以避免:
- `02` 讲的是“主要部分与交互”,`03` 却突然只剩字段表
- 实现者知道有对象,但不知道这些对象归哪个主要部分负责
- 流程、存储、事件和模块职责脱节
- 文档再次滑回“按对象堆砌”的旧写法

> 这里优先使用 **Rust 风格的结构体骨架**。  
> 结构体本身要用中文注释说明“这个结构体负责什么”; 每个成员变量也要用中文注释说明“这个字段的作用是什么”。

## 4. 五阶段定义

### 阶段 0:Spike(可选)

**何时需要**:新框架 / 性能存疑 / 外部接口未确认 / 核心算法未验证

**产出**:一次性验证代码(不合并主干)+ 结论文档(1 页以内)

### 阶段 1:骨架可启动

#### 目标
让系统"能跑起来",即使什么业务逻辑都没有。

#### 输入(引用详细设计)
- `02-详细设计.md` §3 代码目录结构
- `02-详细设计.md` §13 框架集成与代码骨架
- `02-详细设计.md` §5 接口定义(用于定义空路由)

#### 动作
1. 按目录结构创建所有包和文件
2. 把类骨架模板复制到对应文件,每个方法只写 `todo!()` 或 `throw NotImplemented`
3. 配置依赖注入 / 组件注册
4. 配置中间件 / 拦截器(顺序、作用范围)
5. 注册所有 API 路由(入参出参用空结构体,方法体为 TODO 桩)
6. 配置健康检查端点

#### 产出
一个**可以启动、可以接收请求、可以优雅退出**的系统。所有 API 返回 501 Not Implemented 或空结构体。

#### 检查点

- [ ] 进程能正常启动(`cargo run` / `python main.py` / `npm run dev` 无报错)
- [ ] 健康检查可达:`curl http://localhost:<port>/health` 返回 200
- [ ] API 路由已注册:`curl ...` 返回 501(而非 404)
- [ ] 依赖注入无遗漏(启动日志无 `NoSuchBean` 类错误)
- [ ] 进程可优雅退出:`kill -SIGTERM <pid>` 后进程正常关闭
- [ ] 单元测试框架就位(至少一个空测试通过)

#### 深度标尺
- 不足:只有目录结构,文件是空的,启动报错 ✗
- 适中:所有文件有骨架代码,系统能启动,路由返回 501 ✓
- 过度:在 TODO 桩里写了业务逻辑 ✗(阶段 1 不写业务)

---

### 阶段 2:数据层闭环

#### 目标
数据能存、能取、能校验。这一步完成后再写业务逻辑时,不需要关心数据怎么存取。

#### 输入
- `02-详细设计.md` §4 结构体定义
- `02-详细设计.md` §7 数据设计(DDL、缓存)

#### 动作
1. 在开发库执行 DDL(含索引、约束、分区)
2. 实现结构体(字段、默认值、校验)
3. 实现 Repository 层(CRUD + 乐观锁更新)
4. 实现缓存层(Key 构建、查询、失效、击穿防护)
5. 编写 Repository 单元测试:插入、查询、更新冲突、缓存穿透

#### 产出
数据层完全可用。通过 Repository 可以正确增删改查,缓存逻辑经过验证。

#### 检查点

- [ ] DDL 执行成功(表结构、索引、约束在开发库中存在)
- [ ] CRUD 单测通过:插入 → 查询 → 更新 → 查询,结果一致
- [ ] 乐观锁生效:并发更新同一行,一个成功一个 `OptimisticLockException`
- [ ] 缓存命中:首次查询走 DB,二次查询走缓存
- [ ] 缓存击穿防护:并发查询不存在的 Key,DB 只被查一次
- [ ] 数据所有权合规:每个 Repository 只操作本服务拥有的表

#### 深度标尺
- 不足:只实现部分 CRUD,缓存未做 ✗
- 适中:完整 CRUD + 乐观锁 + 缓存 + 击穿防护 + 单测全过 ✓
- 过度:在 Repository 里写业务逻辑(如状态校验)✗

---

### 阶段 3:核心链路贯通

#### 目标
最重要的业务路径能端到端走通。外部依赖用 Mock/Stub。

#### 输入
- `02-详细设计.md` §6 关键函数伪代码
- `02-详细设计.md` §8 核心流程(时序图 + 状态机)
- `02-详细设计.md` §5 接口定义(前置/后置条件)

#### 动作
1. 按伪代码填充 AppService / DomainService 的核心方法
2. 实现状态机转换函数(严格按转换矩阵)
3. 外部依赖用 Mock/Stub 实现(返回预定义合理数据)
4. 编写核心路径集成测试

#### Mock/Stub 标准

| 要求 | 说明 |
|---|---|
| 返回值合理 | 格式和真实接口一致 |
| 模拟延迟 | 可配置延迟,验证超时逻辑 |
| 模拟失败 | 可配置失败,验证异常路径 |
| 状态感知 | 返回值能根据输入变化 |

#### 产出
核心业务路径可端到端执行。如 "创建订单 → 支付 → 发货" 能用 curl 跑通。

#### 检查点

- [ ] 主路径走通:curl 创建订单 → 返回 ID → 查询状态为 CREATED
- [ ] 状态转换正确:支付后 PAID,发货后 SHIPPED
- [ ] 前置条件生效:未支付时发货返回错误
- [ ] 后置条件满足:创建订单后,订单总金额 = 行项金额之和
- [ ] 外部调用被 Mock(日志无真实 RPC 调用)

#### 深度标尺
- 不足:只有创建没有后续状态流转 ✗
- 适中:核心路径端到端 + 状态机转换正确 + 前后置条件生效 ✓
- 过度:把异常处理、补偿逻辑也一并实现 ✗(异常属于阶段 4)

---

### 阶段 4:防御性补全

#### 目标
让系统从"能跑"变成"能扛"——异常不丢数据,并发不出错。

#### 输入
- `02-详细设计.md` §9 异常处理与容错
- `02-详细设计.md` §10 并发与一致性

#### 动作
1. 实现每个 catch 块的补偿逻辑(按补偿逻辑表逐一实现)
2. 实现幂等检查(按幂等方案:键设计 + 窗口 + 实现方式)
3. 实现并发控制(乐观锁重试、CAS、分布式锁)
4. 实现超时处理(定时任务、延迟队列)
5. 编写异常路径测试和并发测试

#### 产出
系统具备完整的异常处理和并发控制能力。各种失败场景有明确处理策略。

#### 检查点

- [ ] 补偿完整:模拟库存预扣失败 → 订单不创建、库存不扣减
- [ ] 幂等生效:相同请求连续 3 次 → 只创建 1 个订单
- [ ] 并发安全:10 个线程并发创建 → 库存扣减数 = 订单数,无超卖
- [ ] 超时关单:创建订单后等超时 → 状态自动 CANCELLED
- [ ] 降级生效:外部服务不可用 → 返回降级结果或友好错误

#### 深度标尺
- 不足:只做 try-catch 打日志,无补偿和重试 ✗
- 适中:补偿 + 幂等 + 并发控制 + 超时处理全覆盖,异常路径测试通过 ✓
- 过度:实现超出设计文档的容错策略 ✗(超出设计范围)

---

### 阶段 5:生产化

#### 目标
让系统从"功能正确"变成"生产可用"。

#### 输入
- `02-详细设计.md` §5 接口定义(真实外部 API)
- `02-详细设计.md` §13 框架集成(配置中心)
- `02-详细设计.md` §14 部署与运维(监控、日志)

#### 动作
1. Mock/Stub 替换为真实外部服务调用
2. 配置超时、重试、熔断策略
3. 对接 MQ 发送/消费(如有)
4. 补充日志(关键路径 INFO,异常 WARN)
5. 补充监控指标(Counter / Gauge / Histogram)
6. 配置项绑定到配置中心
7. 编写集成测试(外部服务用 MockServer 或沙箱)

#### 产出
可在测试环境部署、可观测、可灰度的生产级系统。

#### 检查点

- [ ] 真实 RPC 调通(返回正确结果)
- [ ] 超时熔断生效:外部响应超阈值 → 熔断器打开
- [ ] MQ 收发正常:发送 → 消费端收到 → 处理正确
- [ ] 日志可检索(日志平台可查)
- [ ] 监控可观察(Grafana / 其他面板显示 QPS、延迟、错误率)
- [ ] 配置可动态更新(配置中心修改 → 运行时生效,无需重启)

#### 深度标尺
- 不足:还在用 Mock 调外部服务,无监控无告警 ✗
- 适中:真实调用 + 超时熔断 + 日志 + 监控 + 配置中心 ✓
- 过度:在阶段 5 做性能优化或架构重构 ✗(独立迭代中做)

## 5. 阶段依赖拓扑

### 5.1 基本依赖

```
Spike(可选) → 阶段1 → 阶段2 → 阶段3 → 阶段4 → 阶段5
```

### 5.2 并行机会

```
阶段1: 骨架可启动
   │
   ├──→ 阶段2a: 核心数据层(主表、核心缓存)──┐
   │                                          ├──→ 阶段3: 核心链路贯通
   └──→ 阶段2b: 辅助数据层(日志表、统计表)─┘
```

**并行规则**:
- 阶段 1 必须先完成(没骨架,代码无处放)
- 阶段 3 必须等阶段 2 完成(没数据层,业务无法运行)
- 阶段 4 必须等阶段 3 完成(没核心链路,异常处理没附着点)
- 阶段 5 必须等阶段 4 完成(没防御性代码,接真实服务会出事故)
- 阶段 2 内部可并行(不同表、不同缓存可并行实现)

**关键路径**:阶段 1 → 阶段 2a → 阶段 3 → 阶段 4 → 阶段 5。关键路径任何延迟都会导致整体延期。

## 6. 回退规则

### 6.1 核心原则

**如果某个阶段走不通,不是硬着头皮往下写,而是回头改设计。**

### 6.2 回退触发条件

| 阶段 | 回退触发条件 | 回退到 | 修正动作 |
|---|---|---|---|
| 阶段 1 | 依赖冲突导致框架无法启动 | 概要设计 | 重新评估技术选型 |
| 阶段 1 | 目录结构无法反映模块边界 | 详细设计 | 重新划分模块和目录 |
| 阶段 2 | DDL 无法满足查询(缺索引、缺字段)| 详细设计 | 补充数据设计 |
| 阶段 2 | 乐观锁/缓存策略不可行 | 详细设计 | 重新设计并发方案 |
| 阶段 3 | 伪代码逻辑有遗漏,无法翻译 | 详细设计 | 补充伪代码 |
| 阶段 3 | 状态机转换矩阵有遗漏 | 详细设计 | 补充转换矩阵 |
| 阶段 4 | 并发场景有遗漏 | 详细设计 | 补充竞态分析 |
| 阶段 4 | 补偿逻辑导致状态不一致 | 详细设计 | 重新设计补偿流程 |
| 阶段 5 | 真实外部服务行为与文档不一致 | 详细设计 + 外部文档 | 更新接口定义 |

### 6.3 回退流程

```
发现走不通
   │
   ▼
记录问题(什么场景、什么现象、为什么设计覆盖不到)
   │
   ▼
判断影响范围(仅当前模块 / 多模块 / 架构方向)
   │
   ├── 局部影响 → 修改详细设计对应模块 → 更新实施计划 → 继续执行
   │
   ├── 多模块影响 → 修改详细设计多模块 → 从受影响的最早阶段重新执行
   │
   └── 架构影响 → 回到概要设计重新评估 → 重新制定实施计划
```

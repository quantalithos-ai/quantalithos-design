## 1. 与 `product/` 的关系声明

L0-bus 是**通用基础设施子域**。`product/` 层面没有直接业务功能描述,但 `product/六域模型.md` 明确锁定了跨域通信规则:

- **不允许跨仓直接 RPC**
- 所有跨域协作走事件
- 事件用 CloudEvents 1.0 包络
- Trace Context 必须贯穿
- 最终一致 + 订阅方幂等

所以 L0-bus 的需求主要来自:
1. `product/六域模型.md` §2.2 的**跨域通信规则**
2. 七个域 README §四定义的**147 个事件**
3. `architecture/bus-draft/README.md` 的可靠性语义 / 多后端适配 / Outbox / DLQ

| 章节 | 本文内容的来源 | `product/` 对应章节 |
|---|---|---|
| 背景与问题 | 架构决策反推 | `product/六域模型.md` §2.2 |
| 目标 | 下游 25 仓共同需要 | `product/最终目的.md` 成功标准(间接) |
| 用户与角色 | 下游仓维护者 + SRE + observability | `product/六域模型.md` §三 身份域(间接) |
| 功能需求 | bus-draft 完整草案 + event-catalog | 无直接业务叙事 |
| 非功能需求 | 可靠性 / 性能 / 可观测性 | `architecture/标准对齐全景图.md` bus 仓条目 |

**定位原则**:
- 本仓不理解业务语义,只负责**把事件从发布方送到订阅方**,并保证契约层语义(at-least-once / trace / retry / DLQ)
- 成功标准以"下游仓是否能可靠收发事件"为准

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 是**事件编织型**架构。身份、对话、工作、过程、治理、制品六域平权,跨域协作通过事件完成。L2 Member Runtime、L3 capability-hub / method-library、L4 observability / archive、L5 UI、L6 bridges / marketplace 全部都要消费事件。

这意味着平台需要一个**统一的、可替换后端的事件总线**来承载:
- 发布 / 订阅
- Trace Context 传播
- DLQ / 重试
- Outbox 模式
- 全量 audit tap

没有 L0-bus,26 仓要么直接 RPC(违反六域平权),要么每仓各自实现 MQ(运维灾难)。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点描述 |
|---|---|---|
| 事件契约 | `event-catalog.md` 登记 147 个事件 | 只有文档,没有运行时主干 |
| bus 草案 | `architecture/bus-draft/README.md` 925 行 | 设计已足够,代码未落地 |
| 多后端适配 | 设计上支持 NATS / Redis / Kafka / InMem | 没有真实实现,无法验证抽象边界 |
| Outbox | 设计有 3 种部署形态候选 | 没有 worker 代码,无法验证最终一致性 |
| DLQ | 设计有语义 | 没有真实落库 / CLI / UI |
| observability tap | 设计要求全量 tap | 无法验证 147 事件高频时性能 |
| UI 依赖 | chat / console / runner / sync 都间接依赖 bus | bus 不就位,UI 无法观察实时变化 |

### 2.3 为什么要做(量化依据)

`architecture/开发路线图与优先级.md` 把 N0 定义为**契约地基**,其中 L0-bus 是 N0 的三仓之一。如果 L0-bus 不落地:
- N1 身份对话仓无法用真实事件联动(只能假消息)
- N2 工作/过程/治理/制品无法验证跨域编织
- N4 Member Runtime 无事件主干可接
- N5 observability 无全量 tap 来源

**量化影响**:N0 每延期 1 周,后续 N1-N5 的 17 个仓整体延期 1 周。

### 2.4 业务问题 vs 技术问题

- **业务问题**:六域事件编织必须有主干,否则平台无法闭环
- **技术问题**:可靠投递、幂等语义、多后端适配、DLQ、Outbox、trace 传播、tap 性能

## 3. 目标与非目标

### 3.1 目标(可验证)

| ID | 目标 | 验收指标 | 验收方式 |
|---|---|---|---|
| G-1 | 提供统一 EventBus 抽象 | 4 后端(NATS / Redis / Kafka / InMem)都实现同一 trait | 编译 + 集成测试 |
| G-2 | 默认投递语义为 at-least-once | 重复事件在订阅方幂等处理后无副作用 | 幂等测试 |
| G-3 | W3C Trace Context 自动传播 | 100% 事件携带 traceparent | 集成测试 + observability 验证 |
| G-4 | Outbox 支持业务事务 + 事件原子性 | 业务事务成功但 MQ 暂不可用时,事件最终送达 | 故障注入测试 |
| G-5 | DLQ 不丢事件 | 订阅方连续失败时,事件进入 DLQ 且可重放 | 故障注入测试 |
| G-6 | observability tap 能全量接收事件 | 147 事件全部可被 tap 订阅 | 事件回放测试 |
| G-7 | 单机 NATS 默认后端满足 MVP-M | 开发环境 500 QPS 稳定,lag < 1s | 压测 |
| G-8 | 下游仓接入成本低 | 发布方/订阅方示例代码 < 30 行 | 样例仓验证 |

### 3.2 非目标(明确不做)

| ID | 非目标 | 原因 | 归属 |
|---|---|---|---|
| NG-1 | **定义事件 schema 内容** | 事件语义归 L0-core + 各域 README | `quantalithos-core` / domain/* |
| NG-2 | **业务幂等逻辑** | bus 只提供 event.id + 幂等辅助,真正幂等由订阅方实现 | 各订阅方 |
| NG-3 | **审计持久化** | bus 提供 tap,append-only 落库存由 observability 负责 | `quantalithos-observability` |

| NG-6 | **多租户隔离终方案** | bus-draft Q4 已留后期,当前只支持单租户 / 逻辑租户 |
| NG-7 | **Exactly-once 全流默认** | 成本过高,默认 at-least-once |

## 5. 核心用例与用户故事

### 5.1 核心用例

1. **发布事件**:work 域发布 `work.project.created`,conversation 订阅后自动创建 group
2. **订阅事件**:process 订阅 `governance.gate.decided` 恢复 waiting_gate 的 Activity
3. **DLQ 处理**:artifact 订阅失败 3 次后,事件进入 DLQ,运维可重放
4. **Outbox 场景**:Order/WorkItem 写库成功但 MQ 短暂不可用,worker 稍后补发
5. **Tap 审计**:observability 全量接收 147 事件,构建审计链

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| **BR-001** | 事件发布成功 | 返回 event_id,语义 at-least-once |
| **BR-002** | 订阅方业务副作用未完成 | 不得 ack |
| **BR-003** | nack 次数超阈值 | 进入 DLQ |
| **BR-004** | 非 observability 身份尝试创建 tap-all | 拒绝,返回 `PERMISSION_DENIED` |
| **BR-005** | 事件缺 traceparent | 拒收,返回 `MISSING_TRACE_CONTEXT` |
| **BR-006** | 发布的事件前缀不属于本服务 scope | 拒绝,返回 `PUBLISH_SCOPE_VIOLATION` |
| **BR-007** | 切换后端实现 | 上层业务代码不改,只改注入 |
| **BR-008** | Outbox worker 轮询成功但发布失败 | 记录重试次数,不丢弃 |
| **BR-009** | 同一 event 重复投递 | 订阅方按 event.id + 业务幂等 key 去重 |
| **BR-010** | DLQ replay | 重新投递但保留原 event_id / trace_id |
| **BR-011** | 事件保留期到期 | 自动删除或归档,按 governance Policy 定 |
| **BR-012** | 自定义 EventFilter DSL 未启用 | `custom_predicate` 字段必须为空 |

## 8. 交互与界面需求

| 约束 | 说明 |
|---|---|

| tap-all 创建 | 仅 observability 身份可见入口 |

## 9. 数据需求

### 9.1 核心业务实体

L0-bus 本身只存**传输与重放相关元数据**,不存业务数据语义。

| 实体 | 归属 | 生命周期 |
|---|---|---|
| CloudEvent | L0-core 定义,L0-bus 承载 | publish → deliver → ack / nack / DLQ / expired |
| Delivery | bus 内部交付记录 | in-flight → acked / retried / dead-letter |
| ConsumerGroupOffset | bus 后端元数据 | create → advance → lagging → cleaned |
| OutboxRecord | 下游业务仓写,worker 读 | pending → published / failed |
| DLQEntry | L0-bus | failed → replayed / dropped / retained |

### 9.2 数据关系图

```
Business Tx (L1 service)
   │ commit
   ▼
OutboxRecord ──────▶ EventBus.publish() ──────▶ CloudEvent Stream
                                              │
                                      ┌───────┴────────┐
                                      ▼                ▼
                                Consumer Group A   Consumer Group B
                                      │                │
                                    ack/nack         ack/nack
                                      │                │
                                      └──────▶ DLQEntry ◀──────┘
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| 常规业务事件 | 90 天 | 可回放窗口内保留 | 到期删 |
| 审计流 / governance 事件 | 7 年 | observability append-only | 按 Policy 清理 |
| DLQEntry | 90 天(默认) | 可导出到 archive | replay 后标状态,不过期前不删 |
| OutboxRecord | 7-30 天(默认)| worker 定时清理 | 发布成功后异步清理 |

### 9.4 隐私与合规

L0-bus **不解释 payload 语义**,但 transport 层必须支持:
- 敏感事件 payload 加密透传(由发布方决定,总线不解密)
- `subject` / metadata 尽量不泄露 PII
- DLQ 查询权限最小化

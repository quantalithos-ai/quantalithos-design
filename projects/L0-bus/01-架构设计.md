## 1. 业务背景与驱动力

### 1.1 业务背景

Quantalithos 是**事件编织型**平台。身份、对话、工作、过程、治理、制品六域平权,跨域协作通过事件完成。L2 Member Runtime、L3 capability-hub / method-library、L4 observability / archive、L5 UI、L6 bridges / marketplace 全部都要消费事件。

L0-bus 不是可选优化,而是**平台的唯一主干**。没有它:
- 六域必须直接 RPC(违反六域平权)
- 事件语义无法统一落地
- observability 无法 tap-all
- archive 无法订阅生命周期事件
- runtime 无法被事件驱动

### 1.2 业务驱动力

**业务驱动力**:
- 六域事件编织的落地(产品叙事第 2 章)
- 企业合规要求:事件不可丢、决策要可追溯、DLQ 可审计
- MVP-M / MVP-C 必须能演示"立项→需求→代码→验收"的跨域流转

**技术驱动力**:
- 多后端适配(NATS / Redis / Kafka / InMemory)
- Outbox 模式(业务事务 + 事件原子性)
- W3C Trace Context 透传
- Tap-all 观测链
- DLQ / replay 运维闭环

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 功能 | 4 后端都实现同一 EventBus trait | 4/4 | 编译 + 套件测试 |
| 性能 | NATS publish P95 | < 50ms | benchmark |
| 性能 | consume-to-ack P95(empty handler) | < 100ms | benchmark |
| 可靠性 | DLQ 不丢事件 | 100% | 故障注入 |
| 追踪 | traceparent 透传覆盖率 | 100% | 集成测试 |
| 开发体验 | 后端切换上层代码改动 | 0 行 | 样例仓对比 |

## 2. 约束条件

### 2.1 不可变约束(必须遵守)

| 约束 | 来源 | 影响 |
|---|---|---|
| **CloudEvents 1.0 包络** | L0-core + `product/六域模型.md` | bus payload 必须以 CloudEvent 传递 |
| **W3C Trace Context** | 42001 可追溯性 + OTel | 所有 publish / delivery 必带 traceparent |
| **默认 at-least-once** | `bus-draft` §3 | 不追求全局 exactly-once |
| **订阅方幂等** | Research / event-driven 基本原则 | 下游必须自己处理重复投递 |
| **Outbox 模式** | `architecture/架构设计.md` §4.4 | 跨服务事务不许 2PC |
| **tap-all 特权** | observability 设计 | 仅 observability 可建全量 tap |
| **不理解业务语义** | 职责边界 | bus 不写 `if event_type == ...` 业务逻辑 |

| 约束 | 当前值 | 可调整空间 |
|---|---|---|

| custom_predicate DSL | 暂不启用 | 可后续加 CEL / Rego |
| effectively-once | 默认关闭 | 可按流类型开启 |

### 2.3 容量规划

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 后端实现 | 低到中 | 抽象 trait + 多 crate 隔离 |
| event filter 规则 | 中 | EventFilter 结构化字段优先,DSL 后置 |
| delivery semantics | 中 | DeliverySemantics 枚举 + 语义分级 |
| outbox 形态 | 中 | 独立 crate + worker handle 隔离 |
| 运维工具 | 中 | CLI 独立 crate |

### 3.2 架构风格决策框架

**候选风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **Port/Adapter + Strategy**(当前)| 上层不关心后端,NATS/Redis/Kafka 可替换 | 抽象层设计要求高 | ✅ 最匹配多后端 |
| 直接绑定 NATS | 实现快 | 后续切 Redis/Kafka 成本高 | ❌ 不满足 BS2 |
| 统一 MQ SDK 包装层 | 代码少 | 最小公倍数语义太弱 | ⚠️ 不够表达 Outbox / DLQ |

**最终选择**:**Port/Adapter + per-backend crate + shared EventBus trait**

**选择理由**:
1. 变化最大的是后端和运维形态,不是业务 API 本身
2. 后端差异大(NATS stream seq / Kafka offset / Redis stream id),不能强行抹平到最小公倍数
3. 把差异留在 adapter crate,上层只看 EventBus trait + Delivery 语义最稳

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 上层只依赖 EventBus trait | 切后端不改业务仓 | 需要维护 4 套 adapter |
| at-least-once 默认 | 实现简单、稳定 | 下游必须幂等 |
| tap-all 特权 | observability 审计完整 | 权限模型更复杂 |
| Outbox 独立 crate | 下游接入简单 | 需要 DB schema / worker 协同 |

```
┌─────────────────────────────────────────────────────────────────────┐
│                    External standards & ecosystem                    │
│  CloudEvents 1.0  ·  W3C Trace Context  ·  NATS/Redis/Kafka docs   │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ aligns with
                                ▼
                  ┌─────────────────────────────────┐
                  │        ★ quantalithos-bus ★     │
                  │  event bus abstraction +        │
                  │  adapters + outbox + dlq + tap │
                  └───────────────┬─────────────────┘
                                  │
        ┌──────────────┬──────────┴──────────┬──────────────┐
        ▼              ▼                     ▼              ▼
   L1 six domains   L2 runtime          L4 observability   L4 archive
   publish/subscribe consume events     tap-all            archive events
                     + tool events
                                  │
                                  ▼
                               L5/L6
                           via conversation / bridges
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ EventBus trait 定义
- ✅ NATS / Redis / Kafka / InMem 四后端适配
- ✅ Delivery/Subscription/ConsumerGroup 语义
- ✅ Ack/Nack/Retry/DLQ
- ✅ Outbox client + worker
- ✅ tap-all 机制
- ✅ bus-ops CLI

**不做什么**:
- ❌ 定义事件字段 schema(在 core)
- ❌ 解析事件业务含义(在订阅方)
- ❌ 审计持久化(在 observability)
- ❌ UI 推送(在 conversation)
- ❌ 业务补偿逻辑(在领域仓)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| NATS JetStream | 99.95% | Redis 轻量替代(非全语义) |
| PostgreSQL(Outbox) | 99.95% | 业务主库不可用时本服务本就不可用 |
| Redis Streams | 99.9% | InMem 仅本地测试 |
| Kafka | 99.95% | 仅企业环境启用 |

### 4.4 关键依赖风险

- 抽象过度导致最小公倍数语义太弱
- 某后端的 offset 语义不一致导致 replay 行为漂移
- tap-all 对主流造成性能拖累

## 5. 限界上下文与子域划分

### 5.1 子域分类

本仓是**通用子域**。

| 子域 | 分类 | 说明 |
|---|---|---|
| EventBus API | 通用子域 | 全仓共享能力 |
| Backend Adapter | 通用子域 | 对外隔离 MQ 差异 |
| Outbox | 支撑子域 | 支撑最终一致 |
| DLQ / Replay | 支撑子域 | 运维与可靠性 |
| Tap / Metrics | 支撑子域 | 观测支撑 |

### 5.2 限界上下文划分

```
API context      EventBus trait / SubscribeRequest / Delivery
Adapter context  NATS / Redis / Kafka / InMem implementation
Outbox context   OutboxEntry / worker / polling
Ops context      DLQ / replay / lag / CLI
```

| 上下文 | 职责 | 主要 crate |
|---|---|---|
| API | 抽象接口与共享类型 | `quantalithos-bus-api` |
| Adapter | 后端具体实现 | `quantalithos-bus-nats` / `-redis` / `-kafka` / `-inmem` |
| Outbox | 业务事务桥接 | `quantalithos-bus-outbox` |
| Ops | 运维入口 | `quantalithos-bus-cli` |

### 5.3 上下文映射关系

- API → Adapter:通过 trait 实现(典型 Strategy)
- API → Outbox:OutboxPublisher trait
- Adapter ↔ Ops:CLI 只调后端管理 API,不触碰业务语义

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| Delivery | 一次消费交付(含 event + offset + ack/nack handle)| 订阅方 |
| ConsumerGroup | 同组竞争消费,跨组广播 | 订阅语义 |
| DLQEntry | 失败进入死信队列的记录 | 运维 |
| Tap | 特权全量订阅通道 | observability |
| OutboxEntry | 业务事务中写入的待发布事件 | 最终一致 |

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| `quantalithos-bus-api` | EventBus trait + shared structs | Rust crate |
| `quantalithos-bus-nats` | 默认后端 | Rust + NATS JetStream client |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| 业务仓 → bus | Rust trait / SDK binding | 隔离后端差异 |
| bus → MQ backend | 原生客户端协议 | 不丢后端特性 |
| observability tap | 独立 consumer_group | 不阻断主流 |
| outbox worker → bus | 同 trait publish | 保持统一投递语义 |

### 6.4 数据存储归属(Single Writer)

| 数据 | 写入方 | 读取方 |
|---|---|---|
| 业务 Outbox 表 | 各业务仓 | outbox worker |
| MQ stream / topic | bus backend | 各订阅方 |
| DLQ entries | bus backend | bus-ops / Console / observability |
| consumer offsets | MQ backend | bus runtime |

### 6.5 部署拓扑

默认部署形态:
- **MVP-M**:单机 NATS + 各 L1 服务内嵌 outbox worker
- **MVP-C**:NATS JetStream 3 节点集群 + observability tap-all + archive 订阅
- **MVP-E**:Kafka / 多租户隔离(后续)

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
Event publishers / consumers
        │
        ▼
quantalithos-bus-api (trait + shared structs)
        │
        ├─▶ quantalithos-bus-nats
        ├─▶ quantalithos-bus-redis
        ├─▶ quantalithos-bus-kafka
        ├─▶ quantalithos-bus-inmem
        ├─▶ quantalithos-bus-outbox
        └─▶ quantalithos-bus-cli
```

### 7.2 层间约束规则

- API layer(abstract trait) **不得 import** 任何后端实现 crate
- Backend adapter **不得理解业务 event type 的语义**
- Outbox worker **不得修改业务表**,只读 outbox 表 + 写 publish 状态
- CLI **不得直接写业务队列数据**,只调管理接口或 replay API
- observability tap **独立 consumer group**,不得与业务 consumer 共享 group

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| `EventBus` | `quantalithos-bus-api` | `-nats` / `-redis` / `-kafka` / `-inmem` |
| `OutboxPublisher` | `quantalithos-bus-api` | `quantalithos-bus-outbox` |
| `Subscription` / `Delivery` | `quantalithos-bus-api` | 各后端 |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(所有仓依赖 bus-api) |
| 传出耦合 | 中(依赖 core + backend libs) |
| 不稳定性 | 中(API 稳定,adapter 可变) |
| 抽象度 | 高(api),低(adapter) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| CloudEvent stream | bus backend | 订阅方 | at-least-once | 重复投递 |
| consumer offsets | backend | bus runtime | backend 原生语义 | offset 漂移 |
| outbox rows | 业务仓 | outbox worker | DB 事务保证 | 发布延迟 |
| DLQEntry | bus backend | ops / Console | append-only | replay 误用 |

### 8.2 一致性层次

- **Level 1**:同一 backend 内 offset / ack 状态,依赖后端原语
- **Level 2**:Outbox 最终一致(事务写表 → worker 发布)
- **Level 3**:跨服务的最终一致由各域自己承担,总线不负责 2PC

### 8.3 补偿机制设计

| 场景 | 补偿动作 |
|---|---|
| publish 后 ack 前 crash | 订阅方重复收到 → 幂等去重 |
| outbox 发布失败 | 重试直到 DLQ / 人工介入 |
| consumer nack 超阈值 | 进入 DLQ,运维 replay |

| dlq threshold | 次数 + 时间窗 |

### 11.5 性能预算表

| 环节 | 预算 | 来源 |
|---|---|---|
| publish | < 50ms P95 | bus-draft §九 |
| consume | < 100ms P95 | 同上 |
| lag 恢复 | < 60s | ops 阈值 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| Redis / Kafka 实现未落地 | 只影响未来替换后端 | P1 |
| Outbox 形态未定 | 影响 N0 工程组织 | P0 |
| EventFilter DSL 未定 | 只影响高级过滤 | P2 |
| Console DLQ 面板未定 | 运维体验缺口 | P2 |

### 12.2 演进触发条件(可量化)

| 指标 | 阈值 | 演进动作 |
|---|---|---|
| publish P95 > 100ms | 连续 3 天 | 评估 Kafka / pipeline 优化 |
| 单租户事件 > 1e8 / 月 | 1 月 | 评估分租户 stream |
| governance / observability 流对重复投递敏感 | 真实 incident > 1 次 | 局部启 effectively-once |
| custom_predicate 需求 > 3 个稳定场景 | 2 Sprint | 起 DSL 决策 |

### 12.3 演进步骤

```
阶段 1: EventBus trait + NATS + InMem
阶段 2: Outbox + DLQ + replay + ops CLI
阶段 3: observability tap + metrics + alerting
阶段 4: Redis / Kafka adapter
阶段 5: 多租户 / DSL / Console 面板
```

### 12.4 目标架构

目标不是"支持无限后端",而是:
- 对上层 API **稳定**
- 对后端实现 **可替换**
- 对运维 **可观测**
- 对失败 **可恢复**

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| adapter 语义差异大 | 中 | 高 | 统一 API + 每后端单独契约测试 |
| nack/retry 策略被业务误用 | 中 | 中 | 订阅模板 + 文档严格说明 |
| DLQ replay 造成副作用重复 | 中 | 高 | event.id 保持不变 + 订阅方幂等 |
| outbox backlog 堵塞 | 中 | 高 | lag/backlog 告警 + worker 并行度控制 |

### 13.2 边缘风险

- tap-all 消费量极大时拖垮主流
- Kafka / NATS / Redis 三实现语义不可统一
- archlinux / headless / rootless 环境下某些驱动不稳定

|---|---|---|

| 是否为 observability 流开 effectively-once | N1 前 | Tech Lead |
| EventFilter DSL 是否启用 | N1 前 | bus + governance |

## 14. 上线策略

### 14.1 灰度方案

bus 仓没有直接用户流量,灰度发生在**下游样本仓接入**:
1. 先在 InMemory + 单机 NATS 验证
2. 选择 `identity` / `conversation` 两仓做样本
3. 样本仓 1 Sprint 内稳定后推广到 N2 仓

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| 样本仓事件丢失 | S | 回滚到 InMemory / 停止样本集成 |
| lag > 60s 长期不恢复 | A | 退回 NATS 单机配置 / 降低并发 |
| DLQ 快速增长 | A | 暂停新接入仓,查订阅方 bug |

### 14.3 监控指标

| 指标 | 阈值 | 告警 |
|---|---|---|
| outbox backlog > 1000 / 60s | major | Pager / Slack |
| consumer lag > 60s | major | Pager |
| DLQ 新增 > 10 / min | major | Slack |
| backend unavailable | critical | Pager |

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L0-bus` 不是某个 MQ 产品的部署说明,也不是“事件名字清单”。它是 **“共享传递主干契约仓”**。

你可以把它理解成:
- 正式事件、命令、回调和通知在跨仓传递时,该长什么样
- 哪些字段每条消息都必须带
- 哪些路由、trace、幂等、重试、死信和 replay 规则必须统一
- 上游仓怎样把自己的业务变化正式封装成可传递材料
- 下游仓怎样以同一套 envelope 语义去消费消息

这些事情,都由 `L0-bus` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L0-bus`,这些共享传递契约就会散落在:
- 各业务仓自己的 event 定义里
- runtime / tools / governance / process 的 callback 结构里
- 各 SDK / adapter 的自定义 envelope 里
- topic naming / routing / dead-letter / retry 规则的局部实现里

结果就会出现:
- 同样叫 event / command / callback,但每个仓的包络语义不同
- idempotency key / trace / severity / source 字段不统一
- 失败后的 retry / dead-letter / replay 各仓各写一套
- observability 能看到日志,却很难正式回放“到底传递过什么”
- bus 层只是 transport,没有统一正式契约

所以 `L0-bus` 必须独立存在,作为:
> **跨仓传递契约、统一包络、路由规则和失败恢复主干的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### EventEnvelope
就是:
> 一条正式领域事件在 bus 上的统一外层包络。

它不是领域对象正文,而是正文外面那层统一传递壳。

#### CommandEnvelope
就是:
> 一条正式命令在 bus 上的统一外层包络。

它不是业务仓自己的 command 本体,而是跨仓传递时的共享结构。

#### CallbackEnvelope
就是:
> 一条正式回调材料在 bus 上的统一外层包络。

它不是宿主层原始 callback,也不是上游仓真相本体。

#### IdempotencyKey
就是:
> 用来保证消息重复到达时仍能稳定处理的正式幂等锚点。

它不是业务对象 ID 的简单别名。

#### DeliverySemantic
就是:
> 这条消息是强一致前提、最终一致分发、还是允许重试/重放的正式语义类别。

它不是某个 MQ 配置参数。

#### DeadLetterEntry
就是:
> 一条消息正式进入死信路径后的记录。

它不是简单“打个错误日志”。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L0-bus/02` 时,先收稳以下前提:
- `L0-bus` 不应按 topic 列表拆,而应按消息契约类型和传递责任拆
- bus 至少应拆成“共享包络与消息骨架 / 路由与通道约束 / 幂等、重试与死信 / 总线审计与可追溯 / 观测与上游下游消费接缝”五个主要部分
- bus 自己拥有的真相不是业务正文真相,而是 envelope / routing / idempotency / retry / dead-letter / trace 这类传递契约真相
- `Project / WorkItem / Decision / ArtifactVersion / ExecutionInstance / MemberRuntimePersona / ToolDefinition` 等业务对象真相都不应进入 bus 正文层
- bus 只能消费 core 提供的共享 primitive 和上游业务 payload,不能反向发明业务对象真相
- 02 的重点不是“列有哪些 topic”,而是先把“bus 在平台里到底是什么、和 core/sdk/业务仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的消息主干心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,随着 L1/L2 主链仓逐步收稳,业务变化越来越依赖跨仓传递。用户真正需要的不是“各仓自己发点消息”,而是:
- 事件、命令、回调、通知都用一致的正式 envelope
- trace/source/actor/severity/idempotency 这些字段统一继承
- retry、dead-letter、replay 等失败恢复语义有统一主干表达
- runtime / governance / artifact / process / tools / member 等仓能基于同一套传递契约协作

如果把这些逻辑分别散落到:
- 各业务仓的私有 event 结构
- runtime / tools / governance 各自的 callback schema
- 各 SDK / adapter 自己的 transport wrapper
- MQ topic 和 consumer 逻辑的局部实现里

系统会快速退化成:
- 每个仓都在发“自己的 event”,但没有统一总线语义
- 同样是 retry / dead-letter / replay,规则和字段都不一致
- observability 只能看原始消息流,很难正式对账一条传递链
- 下游消费方要针对每个仓写一套不同 parser / correlation 逻辑

因此,本概要设计的任务就是:
> **把 `L0-bus` 写成一个新人也能看懂的“共享传递主干契约仓”,而不是把 MQ、event 和 callback 杂糅在一起的实现层笔记。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| envelope 统一性 | 各仓 event/callback 有分叉风险 | Event/Command/Callback 统一包络 | 需正式收敛 |
| trace / source / actor 元信息 | 有重复定义风险 | 统一继承 core metadata skeleton | 需固定基座 |
| retry / dead-letter / replay | 各仓容易各写一套 | bus 统一传递失败语义 | 需形成主要部分 |
| routing / topic 语义 | 易散在实现里 | 统一主干约束 | 需单列并固定 |
| 审计与观测 | 只看 raw logs 风险高 | bus 提供正式可回放链 | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让正式事件、命令、回调和通知在跨仓传递时使用同一套共享主干契约,并具备统一的 trace、幂等、重试和回放语义
- **技术问题**:EventEnvelope / CommandEnvelope / CallbackEnvelope / RoutingRule / IdempotencyKey / DeliverySemantic / DeadLetterEntry 之间的边界如何稳定建模,并与 `L0-core/L0-sdk/L1/L2` 清晰协作而不混层

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ L0-core                    │
                    │ - IDs / Refs               │
                    │ - DTO / metadata skeleton  │
                    └────────────┬───────────────┘
                                 │ shared primitives
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ L1/L2 domain projects      │   │ L0-bus                     │   │ L0-sdk                     │
│ - work / process / runtime │──▶│ - EventEnvelope            │──▶│ - SDK transport wrapper    │
│ - governance / artifact    │   │ - Command/CallbackEnvelope │   │ - developer-facing calls   │
│ - member / tools           │   │ - routing / idempotency    │   └────────────────────────────┘
└────────────────────────────┘   │ - retry / DLQ / replay     │
                                 └────────────┬───────────────┘
                                              │ audit / trace / delivery material
                                              ▼
                    ┌────────────────────────────┐
                    │ observability / governance │
                    │ - audit / trace consume    │
                    │ - escalated failure consume│
                    └────────────────────────────┘
```

### 4.2 位置解释

- `L0-bus` 自己负责“统一包络”“路由规则”“幂等与重试”“死信与重放”“总线级留痕”
- `L0-core` 提供 bus 需要继承的 shared primitive / metadata skeleton
- `L1/L2` 各业务仓提供正式业务 payload,而 bus 负责把它们包成统一传递契约
- `L0-sdk` 基于 bus 的 envelope / routing 契约做 developer-facing 封装
- `observability / governance` 消费的是 bus 的 trace、audit、delivery、escalated failure 材料

所以 `L0-bus` 在全局里的角色是:
> **基于 core 的共享 primitive,把全平台跨仓事件、命令、回调和通知统一封装、路由、追踪并可恢复地传递出去。**

### 4.3 系统边界

**做什么**:
- 定义 Event/Command/Callback/Notification 的正式 envelope
- 定义 routing / topic / stream / severity / idempotency / retry / dead-letter / replay 骨架
- 提供 bus 级 audit / trace / delivery 材料
- 为 sdk 和业务仓提供统一传递契约基础

**不做什么**:
- 不负责业务事件正文真相
- 不负责 core primitive 定义本体
- 不负责 SDK developer convenience API 本体
- 不负责 observability 存储真相
- 不负责 MQ 中间件产品部署细节

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| L0-core | 99.9% | core primitive 更新延迟时,保留上次稳定 envelope base,不擅自扩字段 |
| L1/L2 业务 payload 输入 | 99.9% | payload 延迟时,bus 不制造正文,只保留空缺调用或延后投递 |
| L0-sdk | 99.9% | sdk 延迟不影响 bus 本身对 envelope 的正式定义 |
| observability | 99.9% | trace / metrics 后到不影响 EventEnvelope / delivery / bus audit 真相 |
| governance | 99.9% | escalated failure 延迟消费时,dead-letter/replay 仍按 bus 主干继续留痕 |
| 下游 consumer | 99.9% | 下游暂不可用时,先保留正式 envelope 与 delivery semantic,进入 retry / dead-letter / replay,不伪装成已消费 |


### 4.5 关键依赖风险

- bus / core 边界不稳会导致 metadata skeleton 与 envelope 细节混层
- bus / 业务仓边界不稳会导致业务正文反向污染传递契约层
- bus / sdk 边界不稳会导致 developer-facing wrapper 字段倒灌 transport 契约层
- bus / observability 边界不稳会导致 raw log/trace 被误当 bus formal audit truth
- bus 若不显式区分 retry / dead-letter / replay,各仓会重新各写一套失败恢复逻辑
- 同一 payload 在不同 envelope 版本里解释不一致时,下游会看到“同一个业务变化”被多套总线语义包装
- idempotency key 缺失或误复用时,会导致重复消费与 replay 对账同时失真
- routing rule 看似一致但不同 consumer 实际绑定到不同 topic/stream 时,消息链会在总线层分叉
- bus-level delivery truth 与 observability trace 不一致时,会让 replay 与追责链失去共同基准

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **传递职责 + 消息类型差异 + 一致性规则 + 失败恢复差异** 来拆分。  
> 因此下面每一部分都可能包含多个共享契约对象,共同支撑同一段传递主链。

#### 共享包络与消息骨架部分

- **它是什么**: 这是 `L0-bus` 的包络真相层,一起回答“正式消息最小长什么样”
- **为什么单独有它**: 如果没有统一 envelope,event/command/callback 只会沦为“名字相似的不同结构”
- **负责什么**:
  - 定义 EventEnvelope / CommandEnvelope / CallbackEnvelope
  - 统一最小消息骨架
  - 统一从 core 继承 shared metadata 的方式
- **不负责什么 / 容易混淆点**:
  - 不负责业务 payload 正文真相
  - 不负责 bus transport 具体实现
  - 最容易和业务事件正文、sdk wrapper 混淆
- **与其他部分交互**:
  - 上游: core shared primitives / business payloads
  - 下游: routing / retry / audit / sdk
  - 交互类型: 正式包络定义型
- **后续详细设计展开点**:
  - Event/Command/Callback envelope skeleton

#### 路由与通道约束部分

- **它是什么**: 这是 bus 的消息通道层,一起回答“这条消息应该怎么走”
- **为什么单独有它**: 如果不单列,routing/topic/stream 规则会散在 MQ 配置和业务代码里
- **负责什么**:
  - 定义 TopicRef / StreamRef / RoutingRule
  - 统一 publisher / subscriber routing 约束
  - 给 retry / dead-letter / replay 提供通道基础
- **不负责什么 / 容易混淆点**:
  - 不负责事件正文语义
  - 不负责 bus 中间件部署参数
  - 最容易和 MQ 产品配置细节混淆
- **与其他部分交互**:
  - 上游: envelopes / delivery semantics
  - 下游: retry / dead-letter / audit / sdk
  - 交互类型: 路由控制型
- **后续详细设计展开点**:
  - topic / stream / route skeleton

#### 幂等、重试与死信部分

- **它是什么**: 这是 bus 的失败恢复层,一起回答“失败后怎样重试、终止、重放”
- **为什么单独有它**: 如果不单列,每个仓都会自己定义 retry/dead-letter/replay 语义
- **负责什么**:
  - 定义 IdempotencyKey
  - 定义 RetryHint / DeliverySemantic
  - 定义 DeadLetterEntry / replay eligibility
- **不负责什么 / 容易混淆点**:
  - 不负责业务失败语义本体
  - 不负责 observability 存储本体
  - 最容易和各仓业务 retry/recover 逻辑混淆
- **与其他部分交互**:
  - 上游: routing / envelopes
  - 下游: audit / observability / governance escalation
  - 交互类型: 失败恢复主干型
- **后续详细设计展开点**:
  - idempotency / retry / dead-letter / replay contract

#### 总线审计与可追溯部分

- **它是什么**: 这是 bus 的正式留痕层,一起回答“这条传递链怎样被正式回看”
- **为什么单独有它**: 如果不单列,bus 只能依赖 raw logs,无法形成正式总线审计真相
- **负责什么**:
  - 定义 BusAuditTrail
  - 定义 causality / delivery history / replay material
  - 为 bus 级 trace 与回放提供正式输入
- **不负责什么 / 容易混淆点**:
  - 不负责 observability 存储真相
  - 不负责业务仓状态机本体
  - 最容易和 raw metrics/logs 混淆
- **与其他部分交互**:
  - 上游: envelope / routing / retry
  - 下游: observability / governance / sdk consume views
  - 交互类型: 正式留痕型 + replay型
- **后续详细设计展开点**:
  - audit trail / delivery history / replay material

#### 观测与上游下游消费接缝部分

- **它是什么**: 这是 bus 的对外消费层,一起回答“谁怎样消费总线层材料”
- **为什么单独有它**: 如果不单列,SDK consume、operator consume 和 observability consume 会混在一起
- **负责什么**:
  - 输出 metrics / trace / status material
  - 提供 sdk / operators / observability 的 consume views
  - 输出 governance 可消费的 escalated failure material
- **不负责什么 / 容易混淆点**:
  - 不反向定义 envelope 真相
  - 不直接定义 sdk developer-facing 体验层
  - 最容易和 observability 本体、sdk wrapper 混淆
- **与其他部分交互**:
  - 上游: audit / delivery / retry
  - 下游: sdk / observability / governance / operators
  - 交互类型: 只读输出型
- **后续详细设计展开点**:
  - consume views / metrics / escalated failure material

### 5.3 主要组成部分汇总表

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 包络骨架层 + 路由约束层 + 幂等/重试/死信层 + bus-level 审计层 + 观测/消费层分层

**选择理由**:
- 把消息骨架、路由、失败恢复、审计观测分开
- 把业务 payload 与 envelope 分开
- 把 bus-level audit 与 observability 存储分开
- 把 bus transport 契约与 sdk wrapper 分开
- 为 `L0-sdk` 和后续各仓事件化承接提供稳定主干

### 7.2 模块划分与职责

```text
┌──────────────────────────────────────────────┐
│                  L0-bus                      │
│                                              │
│  ┌────────────────────┐                      │

│  │ Callback Envelope  │                      │
│  └──────────┬─────────┘                      │
│             ▼                                │
│  ┌────────────────────┐                      │
│  │ Topic / Stream /   │                      │
│  │ Routing Rule       │                      │
│  └──────────┬─────────┘                      │
│             ▼                                │
│  ┌────────────────────┐                      │
│  │ Idempotency /      │                      │
│  │ Retry / DLQ / Replay│                     │
│  └──────────┬─────────┘                      │
│             ▼                                │
│  ┌────────────────────┐                      │
│  │ BusAuditTrail /    │                      │
│  │ Delivery History   │                      │
```

| 模块 | 职责(一句话) | 依赖 |
|---|---|---|
| Event/Command/Callback Envelope | 定义正式消息包络骨架 | core / payload sources |
| Topic/Stream/Routing Rule | 定义消息路由与通道约束 | envelopes |
| Idempotency/Retry/DLQ/Replay | 定义失败恢复主干 | routing / delivery semantic |
| BusAuditTrail / DeliveryHistory | 定义总线级留痕与回放材料 | envelopes / routing / retry |
| Metrics/Trace/Escalation Views | 提供消费层和观测层材料 | audit / delivery history |

### 7.3 模块依赖关系

```text
core primitives ─▶ Event/Command/Callback Envelope
payload + envelope ─▶ Topic/Stream/Routing Rule
routing / delivery semantic ─▶ Idempotency/Retry/DLQ/Replay
envelope / routing / retry ─▶ BusAuditTrail / DeliveryHistory
audit / delivery / replay ─▶ Metrics/Trace/Escalation Views
```

### 7.4 层间约束规则(防退化)

- Envelope 只包 payload,不重新定义 payload 业务正文
- routing rule 不能退化成 MQ 配置细节说明
- retry/DLQ/replay 只定义共享传递语义,不吞并业务仓内部恢复逻辑
- BusAuditTrail 只定义总线级留痕,不等于 observability 存储本体
- sdk wrapper 不能倒灌 bus envelope 基础语义
- escalated failure 只是升级材料,不直接等于 governance decision

**bus 红线**:
- EventEnvelope / CommandEnvelope / CallbackEnvelope 不得被业务 payload 本体替代
- BusAuditTrail 不得退化成 raw MQ logs 的别名
- delivery semantic / retry / replay 语义不得散落回各仓私有实现
- transport wrapper 字段不得反向污染正式 bus envelope 语义

## 8. 关键技术选型

### 8.1 为什么 envelope 必须独立于业务 payload

| 维度 | 内容 |
|---|---|
| 当前选择 | event/command/callback 统一包络独立于业务 payload |
| 备选方案 | 每个仓自己在正文里顺带塞 trace/source/idempotency |
| 选择理由 | 防止消息主干语义漂移,保证跨仓统一传递 |
| 演进路径 | 后续可扩展 richer metadata,但 envelope 仍不吞业务正文 |

### 8.2 为什么幂等/重试/死信必须在 bus 层显式化

| 维度 | 内容 |
|---|---|
| 当前选择 | bus 统一定义 idempotency / retry / DLQ / replay 语义 |
| 备选方案 | 让每个仓各自处理消息重试和死信 |
| 选择理由 | 防止跨仓传递失败恢复逻辑碎片化 |
| 演进路径 | 后续可细化 delivery semantic,但主干归属仍在 bus |

### 8.3 为什么 bus-level audit 独立于 observability 原始日志

| 维度 | 内容 |
|---|---|
| 当前选择 | BusAuditTrail / DeliveryHistory 与 raw logs/metrics 分层 |
| 备选方案 | 完全依赖 observability 原始日志反推消息链 |
| 选择理由 | 防止总线正式回放语义依赖外部日志系统的非正式材料 |
| 演进路径 | 后续可扩展 trace/metrics 存储方式,但 bus-level 留痕语义仍独立 |

### 8.4 为什么 command / event / callback 共享最小 envelope 骨架

| 维度 | 内容 |
|---|---|
| 当前选择 | command/event/callback 共享最小 envelope skeleton,再按类型扩展 |
| 备选方案 | 三类消息完全各自独立定义 |
| 选择理由 | 防止 trace/source/idempotency/source metadata 在三类消息里再次分叉 |
| 演进路径 | 后续可细化各自扩展字段,但最小 envelope 骨架仍统一 |

### 8.5 为什么 escalation material 由 bus 层正式输出

| 维度 | 内容 |
|---|---|
| 当前选择 | governed/restricted failure 先由 bus 形成正式 escalation material |
| 备选方案 | 完全由上游业务仓或 observability 自行解释失败并升级 |
| 选择理由 | bus 最清楚消息是在传递链哪个阶段被阻断、重试或死信,必须先形成正式总线级失败材料 |
| 演进路径 | 后续可细化 escalation 分类,但输出归属仍保留在 bus 层 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: bus 独立为共享传递主干契约层(当前) | 方案 B: 各仓各自定义 event/command/callback 契约 |
|---|---|---|
| 包络一致性 | 高 | 低 |
| retry/DLQ/replay 一致性 | 高 | 低 |
| bus/sdk 承接成本 | 低 | 高 |
| 审计可回放性 | 高 | 低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 的跨仓协作已经不再是零散消息交换,而是需要统一 trace、幂等、重试、死信和回放语义的正式主干。如果继续让各仓各自定义 event/command/callback 结构,后续 runtime、governance、artifact、sdk、observability 都会各自长出兼容层,复杂度和漂移都会持续放大。

```text
  │
  ▼
resolve_delivery_semantic()
  │
  ▼
message enters normal delivery path
```

#### 数据流 C · failure → retry / dead-letter / replay 主线

```text
delivery fails or is blocked
  │
  ▼
classify retryable / governance_required / terminal
  │
  ├─▶ retry path
  ├─▶ dead-letter path
  └─▶ replay material generated
```

#### 数据流 D · bus material → sdk / observability / governance consume

```text
audit / trace / escalation material ready
  │
  ├─▶ sdk consumes transport base
  ├─▶ observability consumes metrics/trace
  └─▶ governance consumes escalated failure material
```

### 10.3 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 风险标注 |
|---|---|---|---|
| Event/Command/Callback Envelope | bus | domains / sdk / observe | 被 payload 或 wrapper 替代 |
| RoutingRule / TopicRef / StreamRef | bus | publishers / subscribers | 被 MQ 产品细节替代 |
| DeliverySemantic / RetryHint / DeadLetterEntry / ReplayMaterial | bus | runtime / governance / operators | 被单仓恢复逻辑替代 |
| BusAuditTrail / DeliveryHistory | bus | observability / operators | 被 raw log 替代 |
| payload 正文 | 上游业务仓 | 通过 bus 传递 | 被误当 bus 真相本体 |

## 11. 横切关注点

### 11.1 安全
- 未满足 routing/policy/semantic 约束的消息不得进入正式传递
- governed/restricted escalation 不得被普通 retry 掩盖
- payload 正文不得越过 envelope 骨架边界污染总线主干层

### 11.2 性能
- envelope 包装与 routing 判定不应拖垮上游主链
- retry / DLQ / replay 不应让正常传递链长时间阻塞

### 11.3 可用性
- observability 延迟不影响 envelope / delivery / audit 真相
- 上游暂时不可用时,bus 可保留 formal envelope 与 delivery semantic 而不是丢失主干语义
- sdk consume 延迟不影响 bus 本身对 envelope / retry / replay 的正式定义

### 11.4 可观测性
- envelope → route → delivery → retry/DLQ/replay 全链必须可追踪
- escalation / dead-letter 必须可单独审计和重放
- raw MQ logs / traces 必须能和正式 BusAuditTrail / DeliveryHistory 对账,但不能替代它们

### 11.5 传递一致性与失败升级边界
- EventEnvelope / CommandEnvelope / CallbackEnvelope 必须共享同一主干语义,不能各自漂移成独立 transport 方言
- escalated failure 只是 bus 输出的升级材料,不等于 governance decision 本体
- payload 正文和 envelope 必须始终分层,不得通过 replay / DLQ 流程重新混层

### 11.6 成本
- 不把 payload 正文、transport 细节和 sdk 便利层混进 bus,避免模型膨胀
- 不让每个仓继续维护自己的一套消息 envelope 和失败语义,降低长期维护成本

### 11.7 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| envelope wrapping | ≤ 100ms | 100ms |
| routing / delivery semantic resolve | ≤ 100ms | 200ms |
| audit / trace material write | ≤ 100ms | 300ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| envelope 语义被业务 payload 反向污染 | 中 | 高 | 在详细设计中继续固定 envelope 与正文边界 |
| routing 规则退化成 MQ 产品配置细节 | 中 | 高 | 单独建模 routing skeleton |
| retry/DLQ/replay 语义被各仓私有逻辑替代 | 中 | 高 | 固定 bus 侧失败恢复主干 |
| raw logs 被误当 bus-level audit truth | 中 | 高 | 固定 audit trail / delivery history 真相 |

### 12.2 边缘风险

- governed/restricted tool / action / event 分类若继续细化,会影响 escalation 路径
- bus 与 sdk wrapper 的边界若继续扩展,会影响 consume base 的层次
- replay 语义若进一步区分 manual / automatic / governance-driven,会带来更多状态分叉

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在最小样板上验证 `EventEnvelope / CommandEnvelope / CallbackEnvelope` 与最小 routing skeleton 主线
- **阶段 2**: 再验证 `idempotency / retry / dead-letter / replay` 主线
- **阶段 3**: 再引入 `bus-level audit / trace / metrics / escalated failure` 主线
- **阶段 4**: 最后再引入复杂 sdk consume wrapper、governed escalation 细分和更细 replay 场景

### 13.2 回滚策略
- 若 envelope 主模型不稳,先回退到“保留最小 EventEnvelope + 最小 routing skeleton”的保守路径
- 若 retry/DLQ/replay 语义不稳,先收紧为最小 retry + dead-letter 语义,暂缓复杂 replay 承接
- 若 audit/trace 材料不稳,先保留 formal delivery truth,暂停复杂观测聚合路径
- 若 sdk consume wrapper 反向拉扯 bus transport contract,先冻结 bus 主干契约,把额外便利字段留在 sdk 外层

### 13.3 监控指标
- envelope 构造成功率
- routing resolve 成功率
- retry / dead-letter 触发率
- replay 成功率
- bus-level audit / trace 漂移率

## 15. 结论

本概要设计的核心结论是:
- `L0-bus` 是跨仓事件、命令、回调和通知在传递时的共享主干契约层,不是 MQ 产品配置层或业务事件正文仓
- `L0-bus` 内部应按“共享包络与消息骨架部分 / 路由与通道约束部分 / 幂等、重试与死信部分 / 总线审计与可追溯部分 / 观测与上游下游消费接缝部分”来理解,而不是按 topic、queue 或 SDK wrapper 平铺理解
- core 提供 primitive,bus 组织 envelope 与传递语义,sdk 提供开发接口封装,业务仓提供 payload 正文,observability/governance 消费总线级材料
- envelope 不是 payload 本体,ToolCallback 不是 bus callback,raw logs 不是 bus-level replay truth
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把 envelope、routing、idempotency、retry/DLQ/replay 和 bus-level audit 正式化

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 EventEnvelope / CommandEnvelope / CallbackEnvelope 等共享传递主干契约真相
- 定义 routing / topic / stream / delivery semantic / idempotency / retry / dead-letter / replay 的统一骨架
- 持有 bus-level audit / delivery history / replay material / escalated failure material 等正式留痕与恢复材料
- 为 `L1/L2` 业务仓、`L0-sdk`、observability、governance、operators 提供统一总线接缝

**本模块不做什么**:
- 不持有任何业务 payload 正文真相
- 不持有 `L0-core` 的 ID / Ref / metadata skeleton 真相
- 不负责 MQ 产品部署、partition、consumer group 参数本体
- 不负责 observability 存储真相或 governance decision 真相
- 不把 sdk developer-facing wrapper 当成 bus transport contract 真相

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 bus“为什么存在”,而是让开发者可以直接开始实现:
- payload 如何进入统一 envelope
- envelope 如何绑定 routing 与 delivery semantic
- delivery failure 如何进入 retry / dead-letter / replay 主线
- bus audit / delivery history / replay material 如何形成正式留痕
- sdk / observability / governance / operators 如何消费 bus 的只读输出

如果不先把这些内容采集清楚,03 很容易退化成:
- MQ 配置说明书
- 事件名字或 topic 名字清单
- callback / event / command 混成一套没有边界的 transport 材料
- sdk wrapper、raw MQ log、observability trace 被误当 bus 真相

### 2.2 内容采集流程(先采集,再落文)

#### 第 0 步:确认 `02-概要设计` 已经稳定

先确认:
- `L0-bus` 是共享传递主干契约层,不是 MQ 配置层,也不是业务事件正文仓
- 五个主要部分已经稳定
- 与 `L0-core`、`L0-sdk`、`L1/L2`、observability、governance 的真相边界已经清楚

#### 第 1 步:列出要实现的核心对象

本仓 03 先按五组对象理解:
- 包络对象: EventEnvelope / CommandEnvelope / CallbackEnvelope / EnvelopeMetadata
- 路由对象: TopicRef / StreamRef / RoutingRule / ChannelBinding
- 传递与恢复对象: IdempotencyKey / DeliverySemantic / RetryHint / DeadLetterEntry / ReplayMaterial

#### 第 2 步:列出主流程与关键异常流

主流程至少有三条:
- payload → envelope 主线
- envelope → routing → delivery semantic 主线
- failure → retry / dead-letter / replay 主线

关键异常流至少包括:
- payload 缺少正式 metadata skeleton 输入
- envelope 结构成立但 routing rule 无法解析
- idempotency key 缺失或与 envelope 不匹配
- retry 已耗尽却没有 dead-letter 正式留痕
- replay 发生后 delivery history 与 audit trail 对不齐
- escalated failure 被误当 governance decision 本体

#### 第 3 步:列出要落库/持久化的对象与关系

必须先分清:
- 哪些是写模型: envelope registry / routing registry / delivery records / dead-letter records / replay records / bus audit trails
- 哪些是只读视图: sdk consume transport view / bus trace material / bus metrics snapshot / escalated failure material
- 哪些是 append-only: delivery history / replay history / audit trail history
- 哪些输入只作为来源引用,不能反向成为 bus payload truth 或 governance truth

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 `L0-core` primitive 与 `L1/L2` payload
- 哪些输出给 `L0-sdk`、observability、governance、operators
- 哪些失败只形成 bus escalation material,绝不能越权直接变成 governance decision
- 哪些 sdk consume 结构只能读 bus output,不能倒灌 transport contract

#### 第 5 步:列出最小测试输入

必须测:
- Envelope ≠ payload
- CallbackEnvelope ≠ raw callback
- DeliverySemantic ≠ MQ 配置
- BusAuditTrail ≠ raw MQ logs
- SdkConsumeTransportView ≠ bus truth
- EscalatedFailureMaterial ≠ governance decision
- retry / dead-letter / replay 链上的一致性与留痕成立

### 4.1 总流程图

- **真相写入**发生在: EventEnvelope / CommandEnvelope / CallbackEnvelope、RoutingRule、DeliverySemantic、DeadLetterEntry、BusAuditTrail 的正式持久化
- **传递推进**发生在: payload 被包成 envelope、路由被解析、delivery semantic 被绑定、失败被登记进入 retry / dead-letter / replay

- **只读输出**发生在: sdk consume transport view、bus trace material、bus metrics snapshot、escalated failure material 的构建
- **同步路径**主要是: BuildEnvelope / ResolveRoutingRule / RegisterRetry / AppendBusAuditTrail 主写链
- **异步最终一致**主要是: metrics 汇总、observability consume、operator replay review、governance escalation consume

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `EventEnvelope / TopicRef / DeadLetterEntry / BusAuditTrail` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 envelope / routing / recovery / audit / consume seam,`03` 却只剩字段表
- 实现者知道有 DeadLetterEntry,却不知道它归哪个责任单元控制

这些对象在该部分里分别承担:
- `EventEnvelope` 负责统一正式领域事件的传递壳
- `CommandEnvelope` 负责统一正式命令的传递壳
- `CallbackEnvelope` 负责统一正式回调材料的传递壳
- `EnvelopeMetadata` 负责把 core 提供的共享元信息骨架接到 bus 主线
- 三类 envelope 都只封装 payload,不接管 payload 真相本体

#### 5.2.4 关键函数代码片段

```rust
/// 把上游业务事件草稿收束成正式 EventEnvelope。
fn build_event_envelope(
    envelope_repo: &dyn EnvelopeRepo,
    draft: BuildEventEnvelopeDraft,
) {
    // [EventEnvelope::从草稿创建]
    // 先把 domain payload 与 core metadata skeleton 收束成正式事件包络。
    let envelope = EventEnvelope::from_draft(draft);

    // [envelope.校验包络边界]
    // 再校验 envelope 必须有正式 metadata,且 payload 不能反向成为 envelope 真相字段。
    envelope.validate_envelope_boundary();

    // [envelope_repo.保存事件包络]
    // 最后把正式事件包络写入 bus 真相层,供后续 routing 与 delivery 使用。
    envelope_repo.save_event(envelope);
}
```

这段实现守住的边界是:
- payload 必须先被包起来,再进入 routing / delivery 主线
- envelope 统一的是 transport 契约,不是业务正文真相
- callback 只能进入 `CallbackEnvelope`,不能把 raw callback 直接冒充正式 bus 材料

#### 5.2.5 该部分的边界与非职责
- 不负责业务 payload 正文本体
- 不负责 routing 决策
- 不负责 retry / replay 决策
- 不负责 sdk developer-facing wrapper

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `路由与通道约束部分` 提供统一 envelope 输入
- 向 `幂等、重试与死信部分` 提供 idempotency / delivery semantic 的载体
- 向 `总线审计与可追溯部分` 提供 causality 与 envelope base
- 从 `L0-core` 接收 metadata skeleton / refs

#### 5.2.7 该部分的状态 / 约束 / 易错点
- EventEnvelope / CommandEnvelope / CallbackEnvelope 不能被合并成一套无差别 payload wrapper
- `Envelope ≠ payload` 必须写死,否则业务正文会倒灌 transport 契约层
- `CallbackEnvelope ≠ raw callback` 必须写死,否则宿主层局部结构会污染总线主干

这些对象在该部分里分别承担:
- `TopicRef` 负责表达稳定 topic 归属

- `RoutingRule` 负责把 envelope 类别、route 与 delivery semantic 正式绑定起来
- `ChannelBinding` 负责记录某条消息被送往哪条正式通道
- 它们都定义传递主干约束,不定义底层 MQ 参数本体

#### 5.3.4 关键函数代码片段

```rust
/// 根据正式包络解析可落地的 RoutingRule 并绑定通道。
fn resolve_routing_rule(
    routing_repo: &dyn RoutingRuleRepo,
    envelope: FormalEnvelope,
) {
    // [RoutingRule::按包络解析]
    // 先根据 envelope kind、source ref 与消息类别解析出正式路由规则。
    let routing_rule = RoutingRule::resolve_for(envelope);

    // [routing_rule.校验可绑定]
    // 再校验 topic/stream 绑定与 delivery semantic 是否共同成立。
    routing_rule.validate_channel_contract();

    // [routing_repo.保存通道绑定]
    // 最后把包络到通道的正式绑定写入 bus routing 真相层。
    routing_repo.save_binding(ChannelBinding::from(envelope, routing_rule));
}
```

这段实现守住的边界是:
- routing rule 必须是 bus 主干契约,不能散落在业务仓或 MQ 配置里
- delivery semantic 与 route 同时绑定,但不等于任何中间件的具体开关
- 通道绑定先固定语义,再交给后端适配层执行

#### 5.3.5 该部分的边界与非职责
- 不负责 payload 正文
- 不负责 raw MQ 部署参数

- 不负责 sdk consume view 组装

```rust
/// 根据失败结果登记重试、死信或重放材料。
fn register_delivery_failure(
    delivery_repo: &dyn DeliveryRepo,
    failed_delivery: FailedDelivery,
) {
    // [failed_delivery.生成幂等键]
    // 先确认这次失败关联的正式幂等锚点,避免后续恢复链重复漂移。
    let idempotency_key = failed_delivery.build_idempotency_key();

    // [failed_delivery.判断是否可重试]
    // 再根据 delivery semantic 与 retry hint 判断应继续重试还是进入死信。
    if failed_delivery.can_retry() {
        delivery_repo.save_retry(idempotency_key, failed_delivery.to_retry_record());
        return;
    }

    // [DeadLetterEntry::从失败创建]
    // 当重试耗尽时,把失败正式收束成死信记录而不是普通错误日志。
    let dead_letter = DeadLetterEntry::from_failed_delivery(failed_delivery);

    // [delivery_repo.保存死信与重放材料]
    // 最后同时保存 dead-letter 与 replay material,为 operator 恢复链提供基线。
    delivery_repo.save_dead_letter(dead_letter);
    delivery_repo.save_replay_material(ReplayMaterial::from_failed_delivery(failed_delivery));
}
```

这段实现守住的边界是:
- 失败恢复必须围绕正式幂等锚点展开
- dead-letter 是正式主干记录,不是一条错误日志
- replay material 只能来自 bus 已知的正式留痕,不能临时拼凑

#### 5.4.5 该部分的边界与非职责

| DeadLetterEntry / BusAuditTrail | 真相对象 | 可以 | 把错误日志或 raw MQ logs 冒充正式留痕 |
| BusTraceMaterial / BusMetricsSnapshot | 投影对象 | 不可以 | 把观测视图反向当作 delivery truth |
| EscalatedFailureMaterial | 投影对象 | 不可以 | 把 failure material 当 governance decision |
| SdkConsumeTransportView | 投影对象 | 不可以 | 把 sdk consume wrapper 当 bus 真相 |
| ReplayMaterial | 执行对象 | 有条件 | 脱离 dead-letter/history 临时拼凑 replay 输入 |
| delivery history / audit history | 证据对象 | 不可以 | 用证据链覆盖主写模型 |

### 6.5 关键数据结构生命周期图(异步资源必须标注)

```text
[Payload draft]
      │
      ▼
[Envelope created] → [Routing bound] → [Delivered]
                                   │
                                   ├─▶ [Retried]
                                   │       │
                                   │       ├─▶ [Delivered]
                                   │       └─▶ [Dead-lettered]
                                   │                 │
                                   │                 └─▶ [Replay prepared] → [Replayed]
                                   │
                                   └─▶ [Audit appended / projections refreshed]
```

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| metadata skeleton 缺失 | 拒绝包络写入 |
| routing rule 无法解析 | 拒绝通道绑定并保留失败原因 |
| retry 已耗尽 | 进入 DeadLetterEntry |
| replay 输入链不完整 | 拒绝 replay 并提示补齐 audit/history |

### 11.1 重试 / 降级 / 熔断 / 补偿
- route 解析失败不可降级为默认 route,必须阻断
- projection 刷新失败可稍后重建,但不回滚已成立的 bus truth
- replay 失败需保留 replay history,不可静默覆盖原链路

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 共享包络与消息骨架部分 | payload 越界污染 envelope | envelope boundary validate | 拒绝写入 | 不适用 |
| 路由与通道约束部分 | route 无法解析 | channel contract validate | 拒绝绑定 | 修订 routing rule 后重试 |
| 幂等、重试与死信部分 | 幂等键缺失 / retry 耗尽 | idempotency check / retry policy | 进入 dead-letter 或阻断 | 允许基于正式材料 replay |
| 总线审计与可追溯部分 | audit chain 断裂 | append-only audit validate | 阻断 replay / escalation 输出 | 补齐 history 后重试 |
| 观测与上游下游消费接缝部分 | consume view 反向污染真相 | read-only boundary validate | 拒绝投影写回 | 重建 projection |

## 12. 实现红线 / 开发禁止事项

- 不允许把 payload 字段或业务正文真相直接并入 envelope 结构
- 不允许把 MQ 参数、consumer group 配置或部署细节写成 routing 真相
- 不允许把 DeadLetterEntry、BusAuditTrail、EscalatedFailureMaterial、SdkConsumeTransportView 混写成同一层对象
- 不允许用 raw MQ logs 代替正式 BusAuditTrail
- 不允许让 projection / consume view 反向成为正式写源

|---|---|---|
| 包络边界 | 包络构造测试、raw callback 负向测试 | Envelope 与 payload 不混层 |
| 路由与传递语义 | route / semantic 一致性测试 | DeliverySemantic 不等于 MQ 参数 |
| 失败恢复主链 | retry / dead-letter / replay 集成测试 | 死信与重放链可追溯 |
| 审计主链 | audit / history 对账测试 | BusAuditTrail 可正式回放 |
| 只读视图边界 | sdk / trace / escalation 投影测试 | 投影不反写真相 |

---

## 14. 最小可运行闭环

- 上游 payload 进入正式 envelope,完成 routing 绑定并留下一次 delivery history
- 一次 delivery failure 经 retry 耗尽进入 dead-letter,同时生成 replay material 与 audit trail
- observability / sdk / governance 各自从只读视图消费 bus 正式材料,且不反写主链

---

## 15. 结论

本详细设计的核心结论是：
- `L0-bus` 的实现主轴必须按五个主要部分组织,而不是按 topic 名或对象清单平铺
- bus 真相层只持有 envelope / routing / delivery recovery / audit 主链,不接管 payload、MQ 部署、governance decision 或 sdk wrapper 真相
- 所有 replay、trace、escalation、sdk consume 输出都必须建立在正式 delivery history 与 bus audit trail 之上

后续测试与验收文档,应直接围绕这套流程、对象模型、失败恢复链与只读边界展开.

### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L0-bus` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L0-bus` 是共享传递主干契约层,不是 MQ 配置层,也不是业务正文真相仓
- EventEnvelope / CommandEnvelope / CallbackEnvelope 构成正式包络真相层
- `Envelope ≠ payload`、`CallbackEnvelope ≠ raw callback` 两条核心边界必须成立
- RoutingRule / ChannelBinding / DeliverySemantic 构成正式路由与传递语义主干,且 `DeliverySemantic ≠ MQ 配置`
- retry / dead-letter / replay 必须围绕正式幂等锚点、delivery history 与 bus audit trail 运行
- `DeadLetterEntry ≠ 普通错误日志`、`BusAuditTrail ≠ raw MQ logs` 两条留痕边界必须成立
- sdk / observability / governance / operators 必须围绕 bus formal truth 消费只读输出,且 `SdkConsumeTransportView ≠ bus truth`、`EscalatedFailureMaterial ≠ governance decision`

因此,本次验收的目的不是笼统判断“能不能发消息”,而是判断 bus 的包络主干、路由主干、失败恢复主干、正式留痕主干与只读消费接缝是否真的成立,是否可作为后续阶段的稳定基线。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| 共享包络与消息骨架部分 | 是 | EventEnvelope、CommandEnvelope、CallbackEnvelope、EnvelopeMetadata |
| 路由与通道约束部分 | 是 | TopicRef、StreamRef、RoutingRule、ChannelBinding、DeliverySemantic |
| 幂等、重试与死信部分 | 是 | IdempotencyKey、RetryHint、DeadLetterEntry、ReplayMaterial |
| 总线审计与可追溯部分 | 是 | BusAuditTrail、DeliveryHistoryEntry、CausalityLink |
| 观测与上游下游消费接缝部分 | 是 | BusTraceMaterial、BusMetricsSnapshot、EscalatedFailureMaterial、SdkConsumeTransportView |
| MQ 后端产品内部实现细节 | 否 | 只验 bus 与 backend 接缝,不验 NATS/Redis/Kafka 内部产品逻辑 |
| observability / governance / sdk 全部仓内正文逻辑 | 否 | 只验 bus 对外输出接缝,不验下游仓全部细节 |
| 业务 payload 语义正确性 | 否 | 只验证 payload 如何被封装与传递,不判定业务正文含义 |

## 4. 功能验收门禁

| 功能/场景 | 门禁条件 | 证据 | 结论 |
|---|---|---|---|
| BuildEventEnvelope | payload + metadata skeleton 合法时,必须形成正式 EventEnvelope | API 响应 / DB 记录 / trace | [] |
| Envelope vs payload 边界 | payload 不得反向改写 envelope truth,不得把业务正文真相并入 envelope 字段 | boundary log / negative test / model review | [] |
| BuildCallbackEnvelope | callback draft 合法时,必须形成正式 CallbackEnvelope | API 响应 / DB 记录 | [] |
| Callback 边界 | raw callback 不得直接冒充正式 CallbackEnvelope | negative flow / error code | [] |
| ResolveRoutingRule | envelope 合法且 route 可解析时,必须形成 RoutingRule 与 ChannelBinding | routing bind log / DB 记录 | [] |
| DeliverySemantic 边界 | delivery semantic 必须与 route 同步成立,但不得退化为 MQ 参数映射 | contract compare / model review | [] |
| RegisterDeliveryFailure | retryable failure 必须进入 retry record,exhausted failure 必须进入 DeadLetterEntry | retry history / dead-letter record | [] |
| DeadLetter 边界 | DeadLetterEntry 必须绑定 envelope/history,不得退化成普通错误日志 | dead-letter snapshot / compare report | [] |
| PrepareReplay | 只有 dead-letter、delivery history、audit chain 完整时才允许生成 ReplayMaterial | replay material / replay history | [] |
| Replay 边界 | 未形成正式 dead-letter 链或 audit chain 断裂时必须拒绝 replay | negative flow / error code | [] |
| AppendBusAuditTrail | delivery result / retry / dead-letter / replay 阶段必须追加到正式 BusAuditTrail | audit trail / history append log | [] |
| Audit 边界 | BusAuditTrail 不得被 raw MQ logs、trace view 或 projection 替代 | model review / compare report | [] |
| BuildSdkConsumeView | sdk consume transport view 可读可重建,但不得反写 bus 主链 | projection diff / rebuild report | [] |
| BuildEscalatedFailureMaterial | dead-letter + audit summary 存在时,必须形成治理可读的 failure material | projection snapshot / consume trace | [] |
| Escalation 边界 | EscalatedFailureMaterial 只能表达 bus failure truth,不得直接生成 governance decision | negative flow / model review | [] |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | Envelope/Payload 混层 / replay 绕过 dead-letter / audit chain 断裂仍被放行 / projection 反写主链 |
| A | 视情况 | 主线可跑但 retry/dead-letter/replay/audit/projection 语义不稳 |
| B | 可带着走 | 非关键 metrics/trace/query 视图异常 |

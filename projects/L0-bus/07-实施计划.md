## 2. 实施目标与范围

> 校准来源：
> - `design-calibration/07_implementation_plan_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“实施目标表”“实施范围表”和“非范围表”小节，了解本轮为什么聚焦默认可验证事件传递主闭环，而不是实现全部 L0-bus 未来能力。

本轮最小可交付结果是一个可编译、可测试、可验收的 `/home/aris/Projects/quantalithos-bus` Rust workspace，能够通过 in-memory / fake 默认路径证明 L0-bus P0 事件传递主闭环成立。

| 范围项 | 优先级 | 实施口径 |
|---|---|---|
| 契约绑定发布材料接入 | P0 | 接收 core contract ref + payload ref / outbox fact,形成 accepted / rejected publication fact |
| 统一传递语义 | P0 | 从合法发布材料和 backend capability ref 派生 transport semantic |
| Delivery progression | P0 | 推进 delivery lifecycle,保留 delivery history |
| Feedback / idempotency | P0 | 记录 ack / fail / timeout / duplicate feedback 和 idempotency anchor |
| Retry / DLQ / replay preparation | P0 | 形成 retry plan、dead-letter material 和 replay preparation |
| 总线级审计、tap 与只读输出 | P0 | 输出 audit material、tap output、transport view 和 failure material |
| Outbox relay | P0-min | 承接携带 `core_event_ref`、`core_event_envelope_ref`、`delivery_mode`、`target_scope` 的 committed outbox fact,验证 duplicate 和 source ack failure |
| Backend / store / fixture 默认路径 | P0-min | 通过 port + in-memory / fake adapter 证明默认可验证路径 |
| 配置控制面与证据生成 | P0 | 实现 JSON config、profile、runtime graph、scripts、artifacts、reports 和 acceptance handoff |

本轮明确不实施 gateway、登录认证、token、TLS、生产级 MQ / durable DB adapter、业务 payload 正文真相、governance decision truth、长期 observability dashboard、SDK high-level client、config center、hot reload、admin override、multi-backend / multi-tenant 全量矩阵、exactly-once / effectively-once 承诺和部署运维 runbook。

### 3.1 状态与命名裁决口径

如果实现阶段遇到历史草案或中间产物中的旧口语状态名，以下表格作为代码实现口径。代码、测试名、DTO、报告证据和验收证据必须使用“正式实现名”，不得把旧口语名作为 enum 变体或 public API 名称。

| 主题 | 正式实现名 | 旧口语 / 禁止写法 | 说明 |
|---|---|---|---|
| Publication acceptance 初始状态 | `PublicationAcceptanceStatus::Pending` | `Draft` | 接入判定初始状态是 `Pending`，只允许进入 `Accepted` / `Rejected` |
| Publication material command factory | `PublicationMaterial::from_accept_publication_command(AcceptPublicationCommand command, ActorContext actor, CommandMetadata meta)` | `from_publish_command(...)`、`from_accept_command(...)` | 工厂名必须绑定实际协议命令 `AcceptPublicationCommand` |
| Publication acceptance factory | `PublicationAcceptance::start_pending(PublicationMaterial material, ActorContext actor)` | `start(...)` | 工厂只创建 pending fact，最终判定必须经 `accept(...)` / `reject(...)` |
| Delivery lifecycle | `Scheduled / Dispatching / Delivered / Completed / Failed / DeadLettered` | `dispatched`、`timed_out`、`retry_scheduled`、`dead_lettered` | `timed_out` 表达为 `FeedbackStatus::Timeout` + `DeliveryStatus::Failed`；retry reschedule 表达为 `Failed -> Scheduled` 并由 `RetryPlanStatus::Scheduled` 控制 |
| Retry plan | `RetryPlanStatus::Scheduled / Exhausted / Cancelled` | `Draft`、`Running`、`Completed` | due retry 不新增 `Running` 状态，只更新 attempt metadata |
| Dead letter | `DeadLetterStatus::Open / Reviewing / Closed` | `created`、`replay_prepared`、`archived` | replay preparation 是独立对象，不是 DLQ 状态 |
| Replay preparation | `ReplayPreparationStatus::Draft / Ready / Rejected / Superseded` | `running`、`completed` | ready 只是后续 replay 执行边界的准备结果 |

> 校准来源：

>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“暂停规则表”“回退规则表”“变更控制表”“门禁失败处理表”“外部依赖不可用处理表”和“恢复实施检查清单”小节。

本轮实施完成不能只以“代码写完”或“release gate 通过”裁决。完成判定必须同时满足范围覆盖、交付物完成、测试门禁、验收门禁、风险关闭、证据链完整、脱敏检查、提交纪律和 acceptance handoff 审查。

| 判定项 | 标准 | 证据 |
|---|---|---|

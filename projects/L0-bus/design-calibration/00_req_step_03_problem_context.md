## 3. 应问的问题与回答

### 3.1 当前业务背景是什么？

Quantalithos 已经按 27 仓、七层依赖、六域平权的方式拆分。`L0-core` 已经收稳为跨仓共享契约来源仓，但共享契约本身并不能完成跨仓协作。上层仓仍需要一个稳定的事件传递主干，把已提交的事实和事件从发布方可靠推进到订阅方，并让失败、重试、死信、重放和审计都有统一语义。

因此，`L0-bus` 的背景不是“选择一个 MQ 产品”，而是“让基于 `L0-core` 的跨仓事件协作真正可运行、可恢复、可追溯”。

### 3.2 当前主要痛点或机会点是什么？

| 问题 | 当前表现 | 影响 |
|---|---|---|
| 共享契约与传递运行之间缺少中间主干 | `L0-core` 只定义契约，不能负责 publish / subscribe / retry / DLQ | 上层仓即使引用同一事件契约，也可能各自实现投递语义 |
| 旧 bus 文档口径不一致 | 仍出现 26 仓、三语言 client、四后端全量 P0、`04-实施计划.md` 等旧表达 | 后续架构和实现会沿用过期边界 |
| schema、transport、SDK、observability 边界容易混杂 | 旧文档同时谈 event catalog、bus adapter、SDK binding、tap、DLQ | 容易形成 core / bus / sdk / observability 多重真相 |
| 失败恢复语义缺少统一需求基线 | retry、dead-letter、replay、operator review 在旧文档中更像设计对象 | 后续仓可能各自定义失败恢复链，导致不可审计和不可回放 |
| 下游事件消费样本多，但需求主线未收束 | L1 / L2 / L3 / L4 / L5 / L6 都会消费事件 | 如果 bus 需求不先收束，下游会把 bus 当成 MQ、SDK 或审计系统来用 |

### 3.3 这些问题能否量化？

可以做需求层量化，但不能沿用旧文档的推导式夸张量化。

| 维度 | 可用量化口径 |
|---|---|
| 影响仓数量 | 27 仓中，除少数纯静态 / 营销类仓外，大部分运行仓都直接或间接依赖事件传递 |
| 已稳定上游 | `L0-core` 已完成 `00`~`07`，bus 可以直接承接共享契约，不需要重新定义 |
| 旧文档缺口 | `L0-bus` 旧文档缺新版 `04-配置设计.md`、`07-实施计划.md` 和 `design-calibration/` |
| 事件规模样本 | `architecture/bus-draft/event-catalog.md` 可作为事件规模样本，但不是 bus schema 真相 |
| 高风险链路 | publish / subscribe / ack / retry / dead-letter / replay / tap / audit 均会影响多个上层仓 |

### 3.4 哪些是业务问题，哪些是技术问题？

| 类型 | 内容 |
|---|---|
| 业务问题 | 多仓协作需要统一事件传递主干；如果没有 `L0-bus`，工作、过程、治理、制品、运行时、观测、归档和产品入口之间无法形成稳定事件协作闭环。 |
| 技术问题 | 旧文档中 schema、transport、SDK、tap、DLQ、replay 和后端适配边界混杂；如果不重校准，后续会出现 core / bus / sdk / observability / governance 多重真相。 |

## 4. 改动前后差异

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 背景主语 | “六域事件编织必须有主干” | “`L0-core` 已有共享契约，但仍缺跨仓传递、恢复和留痕主干” |
| 问题量化 | 写 N0 延期导致 17 仓整体延期等推导 | 改为影响仓数量、旧文档缺口、事件规模样本和高风险链路 |
| 事件目录 | 147 事件像需求事实 | 事件目录只作为规模和消费样本，schema 真相由 `L0-core` 承接 |
| 技术问题 | 多后端、Outbox、DLQ、tap 等能力直接罗列 | 先描述边界混杂和多重真相风险，功能后移到 Step 9 |

## 5. 结构化中间产物

### 5.1 业务背景结论

`L0-core` 已经提供共享契约来源，但平台仍缺少一个统一的事件传递运行主干，把已提交事实可靠传递给订阅方，并提供失败恢复、重放、死信和总线级留痕。

### 5.2 现状与问题结论

| 问题编号 | 问题 | 当前表现 | 影响 |
|---|---|---|---|
| P-001 | 契约有来源，传递主干未收束 | `L0-core` 负责契约，旧 bus 仍混杂 schema / transport / SDK / tap | 上层仓可能各写一套投递语义 |
| P-002 | 旧文档口径过时 | 26 仓、三语言 client、四后端全量、缺 `04` / `07` | 不能直接作为新版需求基线 |
| P-003 | 边界混杂 | core、bus、sdk、observability、governance 职责未完全分清 | 后续架构和实现容易串线 |
| P-004 | 失败恢复缺统一需求语言 | retry / DLQ / replay 更像设计对象而非需求边界 | 事件失败链难以审计、重放和治理 |
| P-005 | 下游消费面广 | L1+ 多仓均依赖事件主干 | bus 需求漂移会放大到多个仓 |

### 5.3 问题分类结论

| 分类 | 问题编号 | 说明 |
|---|---|---|
| 业务问题 | P-001 / P-005 | 影响多仓协作闭环是否能够成立 |
| 技术问题 | P-002 / P-003 / P-004 | 影响文档基线、边界清晰度和后续实现一致性 |

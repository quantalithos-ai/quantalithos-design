## 3. 应问的问题与回答

### 3.1 哪些角色目标支撑核心能力闭环？

核心故事应覆盖发布、订阅、留痕、失败恢复、只读输出和维护边界：

- 发布方开发者需要把已提交事实交给 bus，而不关心后端差异。
- 订阅方开发者需要按统一 delivery 语义接收并反馈结果。
- SRE / operator 需要看到失败进入受控恢复链。
- Observability maintainer 需要受控消费 tap / audit material。
- Governance maintainer 需要读取 failure material，但不让 bus 越权下治理结论。
- SDK maintainer 需要消费 transport view，封装开发者体验。
- Bus maintainer 需要维护统一传递语义和边界。

### 3.2 哪些角色目标只是外围增强？

| 故事方向 | 为什么是外围增强 |
|---|---|
| 企业用户选择 Kafka / Redis 后端 | 多后端能力重要，但不是第一版主闭环成立条件 |
| Console 用户可视化 DLQ | UI 体验属于产品层，不决定 bus 主闭环 |
| 管理员配置复杂 filter DSL | 可提高订阅体验，但结构化订阅条件可先满足 P0 |
| 企业租户隔离 bus stream | 企业化能力，当前先保留风险与后续方向 |

### 3.3 哪些看起来像故事，但不应进入本仓？

| 候选故事 | 不进入原因 |
|---|---|
| “作为 SDK 用户，我想用 Python client 调 bus” | 高层 client 属于 `L0-sdk` |
| “作为业务用户，我想项目创建后自动建群聊” | 业务联动属于 `work` / `conversation` |
| “作为治理负责人，我想审批是否 replay” | 审批决策属于 `governance`，bus 只提供材料 |
| “作为观测用户，我想查询全链路报表” | 长期查询属于 `observability` |

## 4. 结构化中间产物

### 4.1 核心闭环故事结论

| 故事编号 | 用户故事 | 目标类型 | 业务价值 | 与核心能力闭环的关系 |
|---|---|---|---|---|
| US-001 | 作为发布方开发者，我希望把基于 `L0-core` 契约的已提交事实交给统一 bus，以便业务仓不各自实现传递语义。 | 核心闭环 | 降低跨仓事件投递分裂风险 | 支撑 CL-001 / CL-002 |
| US-002 | 作为订阅方开发者，我希望按统一 delivery 语义接收事件并反馈处理结果，以便订阅方不依赖具体 MQ 后端差异。 | 核心闭环 | 保证跨仓订阅语义一致 | 支撑 CL-003 / CL-004 |
| US-003 | 作为 SRE / operator，我希望失败事件进入受控 retry、dead-letter 和 replay preparation 路径，以便失败不是普通日志或静默丢失。 | 核心闭环 | 提升恢复与处置能力 | 支撑 CL-004 / CL-005 |
| US-004 | 作为 observability maintainer，我希望受控消费 bus tap 和 audit material，以便围绕同一传递事实构建观测和审计视图。 | 核心闭环 | 保证观测不替代 bus truth | 支撑 CL-006 |
| US-005 | 作为 governance maintainer，我希望读取 bus failure material，以便治理流程基于传递失败事实做后续判断。 | 核心闭环 | 支撑失败升级但不越权决策 | 支撑 CL-005 / CL-006 |
| US-006 | 作为 SDK maintainer，我希望消费 bus transport view，以便 SDK 封装开发者体验时不重新定义 bus 语义。 | 核心闭环 | 保持 SDK 与 bus 语义一致 | 支撑 CL-006 |
| US-007 | 作为 Bus maintainer，我希望维护统一传递语义和边界，以便后端适配、失败恢复和只读输出不会形成多套 truth。 | 核心闭环 | 保证 bus 作为 L0 主干稳定演进 | 支撑 CL-002 / CL-004 / CL-006 |

### 4.2 外围增强故事结论

| 故事编号 | 用户故事 | 目标类型 | 业务价值 | 当前处理 |
|---|---|---|---|---|
| US-P1-001 | 作为部署维护者，我希望在 NATS、Redis、Kafka 等后端之间选择，以便适配不同部署环境。 | 外围增强 | 提升部署适配性 | P1/P2，P0 先保留 adapter boundary |
| US-P1-002 | 作为 operator，我希望在 Console 中可视化 DLQ，以便更方便地处理失败事件。 | 外围增强 | 提升运维体验 | 移交产品层或后续阶段 |
| US-P1-003 | 作为订阅方开发者，我希望使用更复杂的 filter DSL，以便精细控制订阅范围。 | 外围增强 | 提升订阅灵活性 | 后续增强，P0 不阻塞 |

## 5. 改动前后差异

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 故事组织 | 按 publish、subscribe、tap-all、SRE、outbox、幂等等功能列故事 | 按核心闭环节点组织故事 |
| SDK 故事 | 下游开发者使用不同语言 binding | 高层 client 归 `L0-sdk`，本仓只保留 transport view 故事 |
| 后端故事 | 四后端切换进入 P0 故事 | 后端选择降为外围增强 |
| 业务联动故事 | work 创建项目触发 conversation 建群等具体业务事件 | 作为下游使用样本，不进入 bus 本仓故事 |

## 3. 应问的问题与回答

### 3.1 当前还有哪些尚未关闭的风险？

主要风险集中在五类：

- 旧文档留下的多后端、多语言 SDK、tap-all 等候选能力仍可能被重新误读为 P0。
- bus 和 `L0-core` 的契约边界如果不持续收紧，后续设计可能重新定义事件包络、错误、trace 或 metadata。
- bus 级 delivery 幂等与订阅方业务幂等容易混淆。
- tap、DLQ、replay、failure material 是敏感能力，若授权边界后续设计不清，会破坏安全验收。
- 性能 / 容量数字当前未在需求层写死，后续测试若不补基准值，容易变成不可验证质量要求。

### 3.2 这些风险会影响哪一层需求结构？

这些风险会影响定位边界、目标与非目标、功能需求、规则约束、数据归属、非功能需求和验收标准。尤其是 core / bus 边界、payload 禁止正文、replay 审计链、adapter 语义稳定性，一旦失守会影响一票否决项。

### 3.3 当前还有哪些待确认事项？

当前仍需在后续架构 / 概要 / 详细 / 测试阶段确认的事项包括：默认可验证后端路径、Outbox relay 的部署形态、授权边界由哪个上游安全层提供、性能基准值、完整 Redis / Kafka 适配阶段、replay 操作模型和多租户隔离是否进入后续版本。

### 3.4 哪些待确认项会影响前文结论是否成立？

如果默认可验证后端路径不存在，F-003 / F-008 和核心闭环会受影响；如果授权边界没有被后续设计承接，F-005 / F-006 和验收一票否决项会受影响；如果性能基准完全不补，Step 13 的性能判断口径会变弱。Redis / Kafka 完整适配、多租户、exactly-once 等不会影响当前前文结论成立，因为它们已被明确归为 P1/P2 或非目标。

### 3.5 哪些风险当前可接受，哪些会阻塞后续推进？

当前可接受的风险是：具体性能数字、完整多后端适配、Outbox relay 部署形态和完整 ops runbook 暂未定，因为它们已被约束为后续设计 / 测试 / 实施阶段处理。会阻塞后续推进的风险是：core / bus 契约边界混淆、payload 正文入仓、delivery / replay 无审计链、tap / DLQ / replay 无授权边界、无默认可验证 delivery path。

## 4. 结构化中间产物

### 4.1 风险清单

| 风险 | 影响范围 | 当前处理口径 |
|---|---|---|
| 旧文档中的四后端、三语言 client、tap-all 容易被重新误读为当前 P0 范围 | 影响 §4、§7、§9、§14 | 当前已按 P0 主闭环、P0-min 边界和 P1/P2 增强显式收口，后续按该边界审查。 |
| `L0-bus` 后续设计可能重新定义 `L0-core` 已拥有的 Event、Error、TraceContext、Metadata、ActorRef | 影响 §2、§6、§10、§12、§14 | 当前按“消费稳定上游契约，不重新定义”处理，并列入一票否决项。 |
| 业务 payload 正文、secret、governance decision body 或 observability long-term log body 可能被错误引入 bus 数据范围 | 影响 §2、§10、§11、§13、§14 | 当前已按 forbidden body 明确排除，并由数据归属和验收共同约束。 |
| bus 级幂等锚点与订阅方业务副作用幂等可能混淆 | 影响 §9、§10、§13、§14 | 当前按“bus 只负责 delivery / feedback 幂等，业务幂等归订阅方”处理。 |
| tap、DLQ 读取、replay preparation 和 failure material 输出若缺少授权边界，会成为安全缺口 | 影响 §9、§10、§12、§13、§14 | 当前按受控能力处理，不作为普通读写面暴露，并列入验收否决项。 |
| replay 如果脱离 dead-letter、delivery history 和 audit chain，会破坏恢复可信度 | 影响 §7、§9、§10、§14 | 当前按“未形成完整历史和审计链不得 replay”处理。 |
| 默认可验证 delivery path 若在后续架构中不能成立，P0-min 和核心闭环会失去落点 | 影响 §4、§7、§9、§12、§14 | 当前按强前置风险保留，后续架构必须承接 backend adapter boundary 和 default verifiable path。 |
| 性能、容量和恢复时间当前未写死数字，后续若不补测试基准会降低非功能可验证性 | 影响 §13、§14 | 当前在需求层只写判断口径，后续测试方案必须补默认路径基准值。 |
| failure material 可能被下游误当成 governance decision | 影响 §2、§6、§10、§11、§14 | 当前按只读失败事实材料处理，不允许直接生成治理决策。 |

### 4.2 待确认事项

| 待确认事项 | 影响章节 | 当前状态 |
|---|---|---|
| 默认可验证后端路径具体采用哪种后端或 fake / in-memory adapter | §4、§9、§12、§14 | 当前暂按“必须存在默认可验证路径”挂起，具体后端选择进入架构设计。 |
| Outbox relay 采用内嵌 worker、sidecar、CDC 或其他形态 | §4、§9、§12、§14 | 当前只确认 Outbox relay boundary，不在需求层决定部署形态。 |
| tap、DLQ、replay、failure material 的授权边界由安全入口、gateway、governance 还是运行配置承接 | §10、§12、§13、§14 | 当前只确认必须存在授权边界，具体承接方进入架构设计。 |
| 性能、容量、延迟、恢复时间的初始目标值 | §13、§14 | 当前保留为测试方案输入，需求层不虚构数字。 |
| Redis / Kafka 完整生产 adapter 进入哪个版本 | §4、§9、§14 | 当前暂按 P1/P2 增强处理，不进入当前 P0 主闭环。 |
| multi-tenant isolation 是否进入后续 bus 主线 | §4、§7、§13、§14 | 当前暂按企业化增强处理，不进入当前核心能力闭环。 |
| exactly-once / effectively-once 是否成为未来专项 | §4、§7、§10、§13 | 当前默认 at-least-once + subscriber idempotency，不进入当前需求目标。 |

### 4.3 待确认事项方案建议

| 待确认事项 | 方案 A | 方案 B | 推荐 |
|---|---|---|---|
| 默认可验证后端路径 | 直接选生产 MQ 作为默认路径 | 先在架构阶段选一条可测试、可替换的默认路径，生产 adapter 可后续增强 | 推荐 B。原因是需求目标是证明 bus 主闭环，不是绑定具体 MQ 产品 |
| Outbox relay 形态 | 需求层直接指定内嵌 worker / sidecar / CDC | 需求层只保留 boundary，架构 / 详细设计再选形态 | 推荐 B。原因是部署形态会受业务仓和运行环境影响 |
| 授权边界承接方 | 在需求层指定认证和权限实现 | 需求层只要求授权边界存在，架构阶段决定由 gateway / governance / runtime policy 承接 | 推荐 B。原因是安全实现不属于本仓需求层，但授权边界是验收红线 |
| 性能目标值 | 需求层写死初始 QPS / 延迟 | 测试方案基于默认路径给出基准值 | 推荐 B。原因是当前后端和部署形态未定，需求层写死数字风险高 |
| Redis / Kafka 完整 adapter | 当前版本全部进入 P0 | 后续作为 P1/P2 增强 | 推荐 B。原因是当前应优先完成统一 transport semantic 和 adapter boundary |
| exactly-once / effectively-once | 当前版本作为默认语义 | 当前版本默认 at-least-once + subscriber idempotency，未来专项再评估 | 推荐 B。原因是 exactly-once 会显著扩大一致性和业务边界 |

## 5. 改动前后差异

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 风险表达 | 旧文档多把不确定性混在设计目标或候选能力中 | 独立列出风险、影响范围和当前处理口径 |
| 待确认项 | 旧文档容易只写 TODO 或直接脑补确定方案 | 每个待确认项说明影响章节、当前挂起状态，并给出方案建议 |
| 多后端 | 旧口径中多后端像已确定 P0 | 明确完整多后端适配是后续增强，当前只保留 adapter boundary 和默认可验证路径风险 |
| 性能 | 旧口径可能混入固定 QPS 数字 | 当前不虚构数字，要求后续测试方案补基准 |
| 授权 | 旧文档不容易区分认证实现和授权边界 | 当前只把授权边界作为需求红线，具体实现后移 |

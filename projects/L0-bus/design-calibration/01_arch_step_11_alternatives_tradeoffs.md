### 3. SOP 问题回答

1. 这个仓有哪些主要可选架构方案？

   回答：主要方案包括当前推荐方案、直接绑定 NATS 的生产优先方案、抽象 trait + 四后端全量 P0 方案、纯抽象语义不提供默认可验证路径方案。

2. 为什么当前选择这一种？

   回答：当前方案能守住 core / bus / sdk / observability / governance 边界，提供默认可验证路径，并把后端差异吸收到 adapter 边界内，符合 P0 收口。

3. 被放弃方案的主要优点是什么？

   回答：NATS 方案更接近生产，四后端方案后端叙事完整，纯抽象方案最轻。

4. 为什么即便有这些优点，当前仍不采用？

   回答：NATS 会增加外部产品前置和语义泄漏风险；四后端会扩大 P0 实现和验收矩阵；纯抽象会让核心闭环不可验证。

5. 当前选择牺牲了什么，换来了什么？

   回答：牺牲了直接生产后端完整度和高级投递语义，换来边界清晰、可验证、低前置依赖和可演进的后端适配结构。

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A：当前推荐方案 | 边界清晰、P0 可验证、后端可演进 | 生产后端完整能力后移 | 采用 |
| 方案 B：直接绑定 NATS | 生产路径明确，生态成熟 | 增加部署前置，容易把 NATS 语义泄漏为平台语义 | 不采用为 P0 默认 |
| 方案 C：四后端全量 P0 | 后端替换叙事完整 | P0 过重，测试矩阵爆炸，语义统一风险高 | 不采用 |
| 方案 D：纯抽象语义，无默认路径 | 文档轻，初期实现少 | 核心闭环不可测试、不可验收 | 不采用 |

### 7. 结构化中间产物

#### 7.1 方案对比表

| 方案 | 边界清晰度 | 依赖代价 | 数据 / 一致性风险 | 可验证性 | 演进代价 | 结论 |
|---|---|---|---|---|---|---|
| 当前方案：ports and adapters + in-memory default path | 高 | 低 | 中，需 durable store 支撑 | 高 | 中 | 采用 |
| 直接绑定 NATS | 中 | 中，高于当前方案 | 中，NATS 语义可能泄漏 | 中 | 中 | 不采用为 P0 默认 |
| 四后端全量 P0 | 中 | 高 | 高，语义统一难 | 低，矩阵过大 | 高 | 不采用 |
| 纯抽象无默认路径 | 中 | 低 | 中 | 低 | 中 | 不采用 |

#### 7.2 最终选择结论

当前选择 `ports and adapters + unified transport semantic + at-least-once + durable bus store + in-memory default path`。它不是最终生产后端方案，而是当前阶段能同时满足边界稳定、可验证闭环和后续后端演进的架构基线。

#### 7.3 不采用原因结论

| 不采用方案 | 不采用原因 |
|---|---|
| 直接绑定 NATS | 不能让 P0 默认路径依赖外部 MQ 产品部署，也不能让 NATS 特性反向定义平台 transport semantic。 |
| 四后端全量 P0 | 当前 P0 的目标是验证事件传递主干，不是一次性完成所有生产后端适配。 |
| 纯抽象无默认路径 | 无法支撑测试方案和验收标准。 |
| 全局 exactly-once | 与当前 at-least-once + subscriber idempotency 需求口径冲突。 |

## 3. SOP 问题回答

### 3.1 是否存在旧配置需要迁移?

当前没有已发布配置需要迁移。

原因:

- `projects/L0-bus/04-配置设计.md` 尚未创建。
- Step 7 中的 `transport_backend`、`publisher`、`security_boundary` 等 key 尚未成为正式发布配置契约。
- 旧 `05/06` 不是配置契约来源,不能反向定义迁移项。
- 如果历史草稿出现过 `backend` 之类名称,在正式 `04` 发布前不视为已发布配置。

### 3.2 新配置如何引入?

未来新增配置必须遵守以下流程:

```text
new config need
  -> decide whether it changes 03 code contract
  -> update 04 Step 7 config item list
  -> update Step 8~11 if sensitive / load / change / failure behavior changes
  -> update Step 12 downstream handoff
  -> update 05 / 06 / 07 / 09 as needed
  -> implement with tests
```

新增配置不得直接写入实施计划、部署手册或代码实现。

### 3.3 旧配置如何废弃?

已发布配置废弃必须分阶段:

| 阶段 | 含义 | 行为 |
|---|---|---|
| active | 当前推荐配置 | 正常支持 |
| deprecated | 已废弃但仍兼容 | loader 接受,validator 给出 deprecation warning / report |
| retired | 不再推荐且准备移除 | 只允许在兼容窗口内迁移 |
| removed | 已移除 | loader 拒绝旧配置 |

P0 当前没有 deprecated / retired 配置。

### 3.4 是否需要兼容窗口?

当前无迁移项,因此无兼容窗口。

未来一旦某个正式配置项被重命名或替换,必须定义兼容窗口。默认建议:

- 至少一个正式版本或一个明确发布周期。
- 对安全边界配置不提供放宽兼容窗口;不安全旧值应立即拒绝。
- 对字段重命名可短期双读,但必须在报告中提示迁移。
- 对语义变化配置不得无提示复用旧字段名。

### 3.5 何时允许移除旧配置?

只有同时满足以下条件,才允许移除旧配置:

- 旧配置已在 `04` 中标记 deprecated / retired。
- 兼容窗口已结束。
- `05-测试方案.md` 已覆盖旧配置拒绝测试。
- `06-验收标准.md` 已更新移除门禁。
- `07-实施计划.md` 已安排 loader / validator 删除兼容路径。
- 部署与运维说明已提供迁移路径。
- 不存在未处理的 `03` 回写事项。

## 6. 配置设计取舍

### 6.1 草稿名称是否算已发布旧配置

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 不算,正式 `04` 发布前无迁移项 | 简洁,符合配置契约来源 | 需要读者理解草稿不是 contract | 采用 |
| B. 算,为所有草稿名写迁移 | 看似严谨 | 会制造不存在的兼容负担 | 不采用 |
| C. 只为 `backend -> transport_backend` 写迁移 | 保守 | 仍会把未发布草稿当 contract | 不采用 |

结论: 当前无已发布配置迁移项。

### 6.2 未来重命名是否双读

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 可短期双读,但必须有 deprecation report | 迁移平滑 | loader 稍复杂 | 采用 |
| B. 立即拒绝旧 key | 简单 | 对已发布配置破坏大 | 仅安全风险配置采用 |
| C. 永久双读 | 兼容性强 | 技术债长期存在 | 不采用 |

结论: 普通字段重命名可短期双读;安全红线相关旧配置不提供放宽兼容。

## 7. 结构化中间产物

### 7.1 配置迁移与废弃表

| 旧配置 | 新配置 | 状态 | 兼容窗口 | 迁移策略 | 移除条件 |
|---|---|---|---|---|---|
| 无 | 无 | 当前无迁移项 | 不适用 | 不适用 | 不适用 |

### 7.2 未来新增配置规则

| 场景 | 必须动作 | 禁止动作 |
|---|---|---|
| 新增普通配置项 | 更新 `04` Step 7、Step 9、Step 11 和下游承接 | 直接在代码或部署手册中新增 |
| 新增敏感配置项 | 先更新 Step 8,再更新 loader / validator / redaction tests | 把 material 当普通字符串 |
| 新增外部 adapter kind | 更新 `03` adapter contract、`04` config、`05/06/07/09` | 只改 JSON enum |
| 新增 reload / hot update | 先回写 `03`,再重开 Step 9 / Step 10 / Step 11 | 在实施计划中直接实现 |
| 新增 config center | 先重开来源链、失效模式、审计和回滚设计 | 把 config center 作为 P0 隐含来源 |

### 7.3 未来废弃配置规则

| 阶段 | loader 行为 | validator 行为 | 报告 / 审计 | 下游要求 |
|---|---|---|---|---|
| active | 接受新 key | 正常校验 | 正常摘要 | 测试新 key |
| deprecated | 接受旧 key 和新 key;冲突时 fail-fast | 给出 deprecation warning | 报告旧 key 使用 | 测试 warning 和冲突 |
| retired | 可选短期接受旧 key,但必须要求迁移 | warning 升级为 error 或 gate | 报告迁移阻塞 | 验收移除计划 |
| removed | 拒绝旧 key | unsupported config key | 报告旧 key rejected | 测试拒绝旧 key |

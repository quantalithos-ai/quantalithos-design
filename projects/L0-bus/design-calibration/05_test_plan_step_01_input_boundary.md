## 3. SOP 问题回答

### 3.1 当前测试方案要承接哪些需求、规则和非功能目标?

测试方案必须承接需求文档中已经收稳的主线:

| 类别 | 必须承接的输入 | 测试含义 |
|---|---|---|
| 核心能力闭环 | CL-001~CL-006 | 从 core contract input 到 read-only bus outputs 的 P0 闭环必须可验证 |
| 用户故事 | US-001~US-007 | 发布方、订阅方、SRE/operator、observability、governance、SDK、Bus maintainer 的核心诉求必须有测试证据 |
| 功能需求 | F-001~F-008 | 发布材料接入、传递语义、delivery 推进、结果留痕、失败恢复、只读输出、outbox relay、默认可验证路径必须有测试切口 |
| 业务规则 | BR-001~BR-012 | core 契约边界、payload 禁止正文、transport semantic、delivery history、replay 边界、只读输出、授权、outbox boundary、audit append-only 等必须验证 |
| 数据归属 | bus truth / snapshot / reference / forbidden body | 测试必须证明 truth、snapshot、reference 和 forbidden body 不混层 |
| 非功能目标 | 性能、可用性、安全、审计、幂等、一致性、可观测性 | 测试方案必须给出可执行验证口径和证据类型 |
| 需求验收方向 | 功能验收、一票否决项、需求追溯矩阵 | 测试方案必须提供可被 `06` 裁决的证据 |

当前旧版 `05` 中的 envelope / routing / callback 主线不再作为新版测试方案的中心。新版中心应为 publication / delivery / feedback / recovery / read-only output / config / observability / evidence。

### 3.3 哪些验收项需要测试方案提供证据?

当前 `06-验收标准.md` 是旧版,不能作为新版验收事实源。但 `00` §14 和 `04` §12 已明确新版验收方向。测试方案至少需要为以下验收方向提供证据:

| 验收方向 | 测试方案应提供的证据 |
|---|---|
| 核心能力闭环成立 | 从 publication acceptance 到 delivery、feedback、recovery、read-only output 的端到端或集成证据 |
| F-001~F-008 功能能力成立 | 每个功能需求对应的测试场景、用例、断言和证据 ID |
| core / bus 边界成立 | 不重新定义 core 契约、不保存 payload body、不保存 raw secret 的测试证据 |
| delivery / feedback / history 成立 | 状态迁移、幂等、history append、audit 证据 |
| replay 边界成立 | 无 dead-letter / history / audit chain 时拒绝 replay 的 negative test |
| 只读输出边界成立 | Query / projection / SDK transport view / failure material 不反写 truth 的测试证据 |
| 配置门禁成立 | config loader / validator / failure modes / redaction check / reload rejection 测试证据 |
| reports / artifacts 可验收 | `artifacts/test/<run_id>` 和 `reports/runs/<run_id>` 的证据归档规则 |

### 3.4 哪些内容不应在测试方案中重新定义?

测试方案不应重新定义:

- 需求编号、用户故事、功能需求和业务规则。
- 架构职责边界、依赖方向、通信方式和容器形态。
- 概要设计中的对象、接口、处理流、状态机和异常边界。
- 详细设计中的 Rust struct / enum / trait / function / DTO / error / state matrix。
- 配置设计中的 JSON key、来源优先级、profile、敏感配置口径、reload 口径和 fail-fast / fail-closed 规则。
- 验收标准的最终通过 / 否决裁决。
- 实施计划中的任务排期、commit boundary 和开发顺序。
- 部署运维手册中的真实路径、env 命名、provider 产品参数和命令。

测试方案只回答“如何验证这些结论”。

## 6. 测试设计取舍

### 6.1 是否在旧 `05` 上修补

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 删除旧 `05` 后重建 | 能彻底切换到新版主线 | Step 15 才会正式修改文件 | 采用 |
| B. 在旧 `05` 上追加新版章节 | 改动看似较小 | 新旧主线混杂,编号和用例漂移 | 不采用 |
| C. 保留旧 `05`,只新增中间产物 | 不影响旧文档 | 正式文档仍错误 | 不采用 |

结论: Step 1~14 只写中间产物;Step 15 删除旧 `05` 并按新文件标准重建。

### 6.2 是否以旧 `06` 作为测试输入事实源

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 只作为旧验收方向参考 | 避免旧验收反向污染新版测试 | 后续 `06` 还需重校准 | 采用 |
| B. 直接以旧 `06` 为测试基线 | 有现成门禁 | 门禁围绕旧 envelope/routing 主线 | 不采用 |
| C. 暂不看 `06` | 避免干扰 | 可能遗漏验收证据关系 | 不采用 |

结论: 测试方案以 `00~04` 为事实源,旧 `06` 只用于识别后续重校准风险。

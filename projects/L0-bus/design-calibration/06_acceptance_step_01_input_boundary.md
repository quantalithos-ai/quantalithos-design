## 3. SOP 问题回答

### 3.1 本轮验收依据哪些需求和设计?

本轮验收依据新版 `00~05`。旧版 `06-验收标准.md` 自身不作为事实源,只作为需要替换的旧草案。

| 来源文档 | 验收输入 | 本文如何裁决 |
|---|---|---|
| `00-需求文档.md` | L0-bus 定位、P0 主闭环、F-001~F-008、BR-001~BR-012、非目标和一票否决方向 | 转成验收目标、范围、功能门禁、边界红线和非功能门禁 |
| `01-架构设计.md` | core / bus / sdk / observability / governance / MQ / store 边界、依赖方向、数据所有权 | 转成架构红线、跨仓同步验收和不可越界项 |
| `02-概要设计.md` | 主要组成部分、关键对象、接口骨架、处理流、状态机和异常边界 | 转成功能验收门禁、状态机门禁和接口验收门禁 |
| `03-详细设计.md` | Rust workspace、模块契约、对象、trait、API、状态机、事务、错误、幂等、配置、观测和测试切口 | 转成实现契约验收、事务一致性验收、缺陷复验和证据要求 |
| `04-配置设计.md` | JSON profile、config loader / validator / runtime graph、secret ref、fail-fast / fail-closed、redaction | 转成配置验收、敏感信息红线、环境进入条件和证据门禁 |
| `05-测试方案.md` | `TC-BUS-*`、`EV-BUS-*`、`RP-BUS-*`、gate、reports、defect、risk、entry / exit | 转成验收基线、证据引用、通过条件、否决条件和风险接受规则 |

### 3.2 哪些测试证据会支撑验收裁决?

验收标准只引用证据,不复制完整测试日志。正式验收优先引用 `reports/runs/<run_id>` 和 `reports/acceptance`,必要时再回链 `artifacts/test/<run_id>`。

| 证据类别 | 来源 | 验收用途 |
|---|---|---|
| `TC-BUS-*` 用例结果 | `05` §6、gate suite results | 裁决功能、状态、接口、配置和恢复门禁 |
| `EV-BUS-*` 证据 | `artifacts/test/<run_id>`、`reports/runs/<run_id>/evidence` | 支撑具体验收项通过 / 不通过 |
| `RP-BUS-RED-001` | `reports/runs/<run_id>/redaction-check.md` | 裁决 payload body、raw secret、private body 泄漏红线 |
| `RP-BUS-SUM-001` | `reports/runs/<run_id>/summary.md`、`reports/acceptance/<run_id>-index.md` | 裁决证据链是否完整 |
| gate results | `reports/runs/<run_id>/gate-results.md` | 裁决 PR / main CI / release gate 是否满足 |
| coverage matrix | `reports/runs/<run_id>/coverage-matrix.md` | 裁决 P0 / P0-min 是否全覆盖 |
| config summary | `reports/runs/<run_id>/config-summary.md` | 裁决验收环境、profile 和 runtime graph 是否匹配 |
| risk acceptance | `reports/acceptance/risk-acceptance.md` | 裁决有条件通过时的 owner、期限和复验计划 |

### 3.3 哪些交付版本、环境和数据会成为基线?

当前还没有实现交付,因此 Step 1 不固定实际 commit 或 run_id。本轮只固定验收标准应如何绑定基线。

| 基线类型 | 当前口径 |
|---|---|
| 文档基线 | `00~05` 当前版本作为验收标准生成依据 |
| 代码版本基线 | 实施完成后由送验说明提供 commit / tag / build id |
| 测试运行基线 | 正式验收必须绑定固定 `<run_id>`,不得使用 `latest` |
| 证据路径基线 | `reports/runs/<run_id>`、`reports/acceptance` 优先;必要时回链 `artifacts/test/<run_id>` |
| 环境基线 | `ci-test`、`integration-test`、`operations-recovery` profile;P1 staging-like 不阻断当前 P0 |
| 数据基线 | `run_id` 隔离的 `DS-BUS-*` fixture 与 `TestRunBuilder` 输出 |
| 上游依赖基线 | `L0-core` shared contracts 本地 path dependency 可编译 |

### 3.4 哪些内容属于测试方案或实施计划,不应写进验收标准?

| 不应写进验收标准的内容 | 原因 | 正确位置 |
|---|---|---|
| 测试用例的完整执行步骤 | 验收只裁决,不替代测试方案 | `05-测试方案.md` |
| fixture builder 细节和数据生成顺序 | 属于测试数据设计 | `05-测试方案.md` §7 |
| gate script 内部命令 | 属于自动化和实施 | `05-测试方案.md` §9、`07-实施计划.md` |
| Rust struct / enum / trait / function 定义 | 属于详细设计 | `03-详细设计.md` |
| JSON 配置项全集和 profile demo | 属于配置设计 | `04-配置设计.md` |
| commit boundary、开发阶段、提交规范 | 属于实施计划 | `07-实施计划.md` |
| 真实 MQ / DB / KMS 产品部署参数 | 属于部署与运维文档 | 后续部署 / 运维文档 |
| 实际测试通过 / 失败结论 | 属于验收报告或送验材料 | `reports/acceptance/*` |

### 3.5 是否存在阻塞验收标准生成的上游缺口?

不存在阻塞 Step 1~Step 2 的上游缺口。新版 `00~05` 已足够启动验收标准校准。

非阻塞事项如下:

| 事项 | 是否阻塞 | 当前处理 |
|---|---|---|
| 当前 `06` 是旧版草案 | 否 | Step 15 删除旧文件并重建 |
| 目标实现仓尚未送验 | 否 | Step 3 固定基线规则,实际 commit / run_id 后续由送验说明提供 |

| 真实 production adapter 未实现 | 否 | 作为 P1-risk 或非范围进入 Step 13 |

## 4. 当前文档问题诊断

| 问题 | 表现 | 风险 | 本步处理 |
|---|---|---|---|
| 旧 `06` 主线过时 | 仍围绕 EventEnvelope / RoutingRule / CallbackEnvelope / DeadLetterEntry 展开 | 与新版 `00~05` 的 publication / delivery / feedback / recovery / read-only output / config / evidence 主线不一致 | Step 15 删除并重建 |
| 旧 `06` 混入执行结果占位 | 表格使用 `[]` 作为结论占位 | 验收标准会误变成验收报告 | 本步明确 `06` 不写实际执行结论 |
| 旧 `06` 未承接新版 `05` 的 reports / artifacts | 无固定 `run_id`、report、acceptance handoff 口径 | 无法裁决证据完整性 | 本步把 `05` 证据链作为验收输入 |
| 旧 `06` 缺少三值结论口径 | 缺少通过 / 有条件通过 / 不通过 | 结论容易模糊 | 后续 Step 14 收敛 |
| 旧 `06` 缺少 design-calibration 来源入口 | 无法追溯每章从哪一步讨论来 | 后续读者难以复核 | 正式文档每章保留校准来源 |

## 6. 验收设计取舍

### 6.1 是否在旧 `06` 上修补

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 删除旧 `06` 后重建 | 能彻底切换到新版主线 | Step 15 才正式修改文件 | 采用 |
| B. 在旧 `06` 上追加新版章节 | 改动看似较小 | 新旧口径混杂,验收项无法裁决 | 不采用 |
| C. 保留旧 `06`,只新增中间产物 | 不影响旧文档 | 正式文档仍错误 | 不采用 |

### 6.2 是否在验收标准中固定实际 run_id

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 当前直接写固定 run_id | 看起来具体 | 目标仓尚未送验,会虚构证据 |
| B. 先固定 run_id 绑定规则,实际 run_id 由送验说明提供 | 不虚构证据,又能约束验收 | 需要 Step 3 继续细化 | 采用 |
| C. 不提 run_id | 文档更短 | 验收引用会漂移到 `latest` | 不采用 |

### 6.3 是否把测试执行步骤写进验收标准

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 写完整测试执行步骤 | 使用者不用跳转 | 与 `05` 重复,且容易变成测试方案 |
| B. 只写验收门禁和证据要求,引用 `05` 的测试方案 | 边界清楚 | 读者需跳转 `05` | 采用 |
| C. 不引用测试方案 | 简洁 | 验收门禁无证据来源 | 不采用 |

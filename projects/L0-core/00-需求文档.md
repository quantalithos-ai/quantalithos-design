## 1. 与 `product/` 的关系声明

L0-core 是**通用基础设施子域**,`product/` 层面没有直接业务叙事对应。需求主要从**架构决策 + 下游仓需要**反推。

| 章节 | 本文内容的来源 | `product/` 对应章节 |
|---|---|---|
| 背景与问题 | **架构决策反推** | `product/六域模型.md` §2.2 "跨域通信规则" |
| 目标 | **下游 25 仓的共同需要** | `product/最终目的.md` §成功标准(间接) |

**定位原则**:

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 是 **六域平权 + 26 仓拆分 + 事件驱动**的 AI 员工协作系统。26 仓之间**不允许直接 RPC**(`product/六域模型.md` §2.2 规则 1),跨仓通信走**事件 + proto 契约**。

这意味着:
- 所有跨仓 RPC 必须通过 proto 定义
- 所有跨域事件必须有统一的包络(CloudEvent 1.0)
- 所有调用链必须能在 observability 中串起(W3C Trace Context)
- 所有错误必须有统一分类(ErrorCode)

**没有 L0-core,上述 4 件事就是 26 仓各自造轮子的必然 drift 灾难。**

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点描述 |
|---|---|---|
| proto 草案 | 7 文件 / ~3200 行(放在 design 仓的 architecture/proto-draft/) | 草案性质,未发版,下游不能依赖 |
| event-catalog | 147 事件主表(bus-draft/event-catalog.md) | 未落到 proto schema,运行时无类型保护 |
| ErrorCode | `common/v1/errors.proto` 有 enum 草案 | 未发版,下游自造错误码 |
| CloudEvent 包络 | `common/v1/events.proto` 骨架 | 未 CI 验证字段兼容性 |
| Trace Context | ADR-0001 决策 W3C Trace Context | 未作为 proto message 固化 |
| Breaking change 防护 | 无 | 改 proto 没机制检测下游破坏 |
| 三语言 binding | 无 | 下游仓每次复制 proto 手改 |

### 2.3 为什么要做(量化依据)

按开发路线图(`architecture/开发路线图与优先级.md` §三),N0 节点是**所有 L1+ 仓的前置**。L0-core 不完成,:
- N1 身份对话先行 → 无 proto 无法建 service
- N2 工作/过程/治理/制品 → 无事件 schema 无法订阅
- N4 Member Runtime → 无 CloudEvent 无法封包
- N5 observability → 无 Trace Context 无法关联链路

**量化影响**:N0 每延期 1 周,下游 N1-N5 的 17 个仓都延期 1 周 → 17 仓 × 1 周 = 17 仓周损失。

### 2.4 业务问题 vs 技术问题

- **业务问题**:无。L0-core 纯技术设施,不承载业务。
- **技术问题**:26 仓协作的契约 drift、breaking change 失控、三语言 binding 不一致、跨链路追踪断裂。

## 4. 用户与角色

### 4.1 目标用户群体

| 用户类型 | 描述 | 使用场景 |
|---|---|---|
| L1 六域开发者 | 实现 identity/conversation/work/process/governance/artifact 的工程师 | 依赖本仓 proto 实现 service + 发布事件 |
| L2 Member Runtime 开发者 | ai-member-runtime / member-service 工程师 | 消费 CloudEvent 包络 + 事件订阅 |
| L3 capability-hub 开发者 | MCP Registry 工程师 | 注册工具能力 + 订阅 Policy 事件 |
| L4 observability 审计方 | 审计查询 + 合规导出工程师 | 全链路基于 trace_id 串接 |
| L4 archive 归档方 | 冷存工程师 | 事件归档基于 CloudEvent 的 retention_policy |
| L5 UI 仓开发者 | chat / console / runner / sync / website | 从 proto 生成的 TS binding 消费 |
| L6 bridges / marketplace 开发者 | 外部平台适配 / 资产市场 | proto 契约 + 事件桥接 |
| 跨仓审计方 | 合规 / SRE | Breaking change 追溯 + Schema 版本查询 |

### 4.2 角色权限矩阵

L0-core 是**共享契约基石**,本仓的**写操作**是 proto / event schema 变更。权限矩阵如下:

| 操作 | 下游开发者 | Core 仓 Maintainer | Tech Lead | Admin / Owner |
|---|---|---|---|---|
| 读取 proto / event schema | ✅ | ✅ | ✅ | ✅ |
| 通过 CI 生成 binding | ✅ | ✅ | ✅ | ✅ |
| 提交 PR 修改 proto(non-breaking)| ✅ 提交 | ✅ 审核 | ✅ 合并 | ✅ 合并 |
| 提交 PR 修改 proto(breaking)| ✅ 提交 | ✅ 审核 | ❌ 单人不可合并 | ✅(需 ADR)|
| 发布新版本 tag | ❌ | ✅ | ✅ | ✅ |
| 修改版本策略文档 | ❌ | ❌ | ❌ | ✅(需 ADR)|
| 废弃某 proto message | ❌ | ✅ 提议 | ✅ 审核 | ✅(需 ADR)|

**原则**:
- 任何下游仓可读 + 可提 PR
- Breaking change 必须走 ADR + Tech Lead 或 Owner 批准
- 版本策略改动必须经 Admin/Owner + ADR

## 5. 核心用例与用户故事

### 5.1 核心用例

1. **下游仓消费 proto** · L1 域工程师在本仓的 service proto 上实现 service,从 proto 自动生成 stub
2. **发布跨域事件** · 本仓提供 CloudEvent 1.0 包络 + proto message,任何域将事件打包后发给 bus
3. **订阅跨域事件** · 订阅方从本仓的 proto 生成反序列化类型,解析 payload
4. **Trace 贯穿** · 所有事件 / RPC 携带 W3C Trace Context,observability 按 trace_id 拼链
5. **错误分类** · 本仓提供 ErrorCode enum,26 仓映射到自己的错误语义
6. **版本演进** · Breaking change 时本仓提供 v1→v2 路径并行能力
7. **三语言 binding 发布** · 本仓 CI 自动生成 Rust/Python/TypeScript binding 包并发布

## 8. 交互与界面需求

**本项目不适用** —— L0-core 是契约定义仓,无 UI / 交互界面。

下游开发者的"交互"发生在:
- **IDE 体验**:proto 生成的 Rust/Python/TS 类型能被 IDE 正确识别(本仓不承担,由各语言生态的 LSP 负责)
- **CI 体验**:PR 页面显示 buf lint / breaking 结果(本仓通过 `.github/workflows/` 提供)
- **文档体验**:本仓 README.md 是下游消费的第一入口

## 9. 数据需求

### 9.1 核心业务实体

L0-core **不存业务数据**,只定义**契约 schema**。"数据"范畴是 proto 文件本身和 CI 生成的 binding artifact。

| 实体 | 归属 | 生命周期 |
|---|---|---|
| proto 文件 | Git 版本控制 | 永久(breaking 通过 v1→v2 并行,不删旧版)|
| binding artifact(Rust crate / Python wheel / npm package)| crates.io / PyPI / npm | 永久(发布后不可删除,只能 yank)|
| buf lock 文件 | Git 版本控制 | 永久 |
| ADR 记录(本仓相关)| `architecture/adr/` | 永久 |

### 9.2 数据关系图

```
               ┌──────────────┐
               │  proto 源文件 │ (Git)
               └──────┬───────┘
                      │ buf generate
            ┌─────────┼─────────┐
            ▼         ▼         ▼
     ┌──────────┐ ┌───────┐ ┌──────┐
     │Rust crate│ │Python │ │npm   │
     │(tonic)   │ │wheel  │ │package│
     └──────────┘ └───────┘ └──────┘
            │         │         │
            ▼         ▼         ▼
         crates.io  PyPI     npm registry
            │         │         │
            ▼         ▼         ▼
       下游 L1-L6 仓依赖
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| proto 源文件 | 永久(Git 历史) | 随仓库备份 | 不删,breaking 走 v1→v2 并行 |
| CI artifact(binding)| 永久(注册表)| 注册表自管 | 不可删,安全漏洞时 yank |
| CI 日志 | 90 天(GitHub 默认)| - | 自动过期 |
| Breaking ADR | 永久 | `architecture/adr/` | 不删 |

### 9.4 隐私与合规

L0-core **不存 PII / 敏感数据**。proto schema 本身视为**公开契约**(可开源)。

唯一敏感面:
- **发版密钥**(crates.io token / PyPI token / npm token)→ 存 GitHub Secrets,不进代码

## 12. 风险与待确认事项

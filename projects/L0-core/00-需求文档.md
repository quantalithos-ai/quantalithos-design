## 2. 本仓定位与边界

> 校准来源：
> - `design-calibration/00_req_step_02_position_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_02_position_boundary.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓定位和边界如何收敛。

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L0-core` 是 Quantalithos 的跨仓共享契约来源仓。 |
| 本仓不是什么 | 它不是事件总线实现，不是 SDK 客户端封装，不是任何 L1 业务域服务，也不是观测、归档或运行时基础设施。 |
| 边界对象列表 | 仓：`L0-bus`；仓：`L0-sdk`；仓：L1 六域服务；仓：`L4-observability`；工件：`architecture/proto-draft`；工件：`architecture/bus-draft/event-catalog.md` |
| 单独成仓原因 | 跨仓契约变化速率最低、影响面最大且被所有下游仓复用，必须从事件投递、客户端封装和业务实现中独立出来。 |

`L0-core` 需要单独存在，因为跨仓契约是全系统最稳定、被依赖最广、变更影响最大的基线。它最容易与 `L0-bus`、`L0-sdk`、L1 六域服务和 `L4-observability` 混淆；这些边界必须分开，否则契约定义会被运行时投递、客户端封装、业务语义或观测存储反向牵引。

## 3. 背景与问题定义

> 校准来源：
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_03_problem_context.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解问题定义如何从旧口径收敛。

### 3.1 业务背景

Quantalithos 已采用六域平权、27 仓、七层依赖的系统拆分方式，跨仓协作必须建立在稳定共享契约上。`L0-core` 处于 N0 契约地基节点，是后续 L1+ 仓校准需求、设计和代码实现时共同引用的底层语义入口。

### 3.2 现状与问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 跨仓契约来源仍处于分散状态 | 契约事实分布在 proto 草案、事件目录、域 README、README 和旧需求文档中 | 下游仓难以判断哪个文件是需求基线，容易各自解释或复制契约 |
| 旧需求文档口径与最新架构不一致 | 仍出现 26 仓、下游 25 仓、纯技术设施等旧表达 | 后续文档校准和开发交接容易沿用过期口径 |
| 问题定义与目标 / 方案混写 | 背景章节直接列 proto、CloudEvent、ErrorCode、Trace、binding 等能力项 | 目标、核心闭环、功能需求会缺少清晰前置问题 |

### 3.3 业务问题 vs 技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | 多成员、多项目、跨阶段协作的产品闭环需要稳定共享契约作为共同语言；如果 `L0-core` 需求不先收束，MVP 和后续仓开发会缺少一致的协作前提。 |
| 技术问题 | 契约来源分散、旧口径残留、边界与相邻仓混淆，会让 proto、事件、错误、追踪等跨仓契约在设计和实现阶段发生 drift。 |

## 4. 目标与非目标

> 校准来源：
> - `design-calibration/00_req_step_04_goals_non_goals.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_04_goals_non_goals.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解目标与非目标如何收敛。

### 4.1 目标

| 目标 | 说明 | 验证方式 |
|---|---|---|
| 建立 `L0-core` 的跨仓契约需求基线 | 明确本仓承载的是所有下游仓共同引用的契约来源，而不是事件投递、SDK 封装或业务实现 | 后续章节均围绕“共享契约来源仓”展开，不再使用 26 仓、下游 25 仓或纯技术设施等旧口径 |
| 收束共享契约能力范围 | 将需求范围限制在跨仓共同引用的基础契约、六域服务契约、事件契约、追踪上下文契约、错误契约和版本兼容契约 | 核心能力闭环与功能需求能映射到这些契约范围，且不扩展到相邻仓运行职责 |
| 稳定相邻仓边界 | 明确 `L0-core` 与 `L0-bus`、`L0-sdk`、L1 六域、`L4-observability`、`L4-archive`、L2 运行层之间的职责边界 | 非目标、使用方与依赖、接口与依赖章节不把相邻仓职责写入 `L0-core` |
| 支撑后续设计文档可追溯 | 为架构、概要、详细、测试和验收文档提供统一需求输入 | 后续文档能从目标、闭环、功能需求和验收标准追溯回本需求文档 |

### 4.2 非目标

| 非目标 | 不做原因 |
|---|---|
| 事件总线投递实现 | 属于 `L0-bus`，`L0-core` 只定义事件契约，不负责 publish / subscribe / ack / dead-letter 等运行能力 |
| SDK 高层客户端封装 | 属于 `L0-sdk`，`L0-core` 只提供可派生的契约来源，不负责重试、配置、认证封装或开发者体验 |
| L1 六域业务实现 | 属于各 L1 领域服务，`L0-core` 不实现身份、对话、工作、过程、治理或制品的业务语义 |
| 观测采集、审计存储与追踪查询 | 属于 `L4-observability`，`L0-core` 只约束追踪上下文契约，不保存观测数据 |
| 归档存储与恢复流程 | 属于 `L4-archive`，`L0-core` 不承载归档包、冷热分层或恢复流程 |
| 成员运行时调度与工具调用 | 属于 L2 运行层，`L0-core` 不负责容器、工具、执行循环或调度策略 |
| 登录认证与权限裁决 | 属于安全入口、治理或授权能力，`L0-core` 不做身份校验或权限判定 |

### 6.3 外部系统依赖

| 方向 | 对方 | 提供 / 依赖内容 | 是否闭环前置 | 失效影响 |
|---|---|---|---|---|
| 无 | 当前阶段无正式外部系统依赖 | CloudEvents、W3C Trace Context、buf 等属于标准 / 工具链约束，不作为本章的正式外部系统依赖 | 否 | 不适用；相关约束后续在规则、非功能、测试或实施计划中展开 |

### 6.4 本章结论

`L0-core` 是依赖方向上的底座仓，当前需求闭环不以其他内部仓或正式外部系统为前置。它的关键关系是向 `L0-bus`、`L0-sdk`、L1 服务仓和其他上层仓输出稳定共享契约；后续核心能力闭环将基于这个输出关系展开。

## 7. 核心能力闭环

> 校准来源：
> - `design-calibration/00_req_step_07_core_capability_loop.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_07_core_capability_loop.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解核心闭环如何从工具项收敛为能力链。

### 7.1 闭环定义

`L0-core` 的核心能力闭环不是 proto、事件包络、错误码、追踪上下文和工具链的简单相加，而是：跨仓契约必须先被统一收束，再被稳定表达，随后能够受控演进，最终被下游仓基于同一基线稳定消费和派生。只要其中任一能力不能成立，`L0-core` 就无法作为跨仓共享契约来源仓支撑 27 仓协作。

### 7.2 核心能力闭环图

```text
Cross-repo contract scope is unified
  -> Contract semantics are expressed consistently
  -> Contract evolution stays compatible and traceable
  -> Downstream repos consume and derive from one baseline
```

本图只表达核心能力成立的逻辑依赖关系，不表达运行时调用顺序、接口时序、事件传播顺序、开发实施步骤或工具链执行顺序。

### 7.3 能力层级划分

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | 跨仓契约范围统一收束；跨仓契约语义稳定表达；跨仓契约演进兼容与可追溯；下游仓基于同一契约稳定消费和派生 |
| 外围增强能力 | 更多语言绑定；样例仓；契约可视化；高级兼容报告；自动发布体验；额外导出格式 |
| 边界外能力 | 事件投递；SDK 高层客户端封装；L1 业务语义实现；观测采集与存储；归档恢复；运行时调度；登录认证；权限裁决 |

### 7.4 能力线索回填映射

| 能力线索 | 支撑的闭环节点 | 处理口径 |
|---|---|---|
| 服务契约、事件契约、共享基础类型 | 跨仓契约语义能够被稳定表达 | 后续功能需求中展开为核心能力 |
| 错误、追踪上下文、审计上下文等共同语义 | 跨仓契约语义能够被稳定表达 | 后续功能需求中展开为核心能力 |
| 版本兼容、破坏性变更处理、废弃策略 | 跨仓契约演进能够保持兼容与可追溯 | 后续规则、非功能和验收中展开 |
| 下游可消费的契约来源与派生基础 | 下游仓能够基于同一契约稳定消费和派生 | 后续用户故事和功能需求中展开 |
| 三语言 binding、样例仓、自动发布体验 | 下游稳定消费的外围增强 | 不进入闭环图，可在功能需求或实施计划中按优先级处理 |
| 事件投递、SDK 高层封装、业务实现、观测存储 | 边界外能力 | 不进入 `L0-core` 功能需求 |

## 10. 业务规则与边界约束

> 校准来源：
> - `design-calibration/00_req_step_10_rules_boundary_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_10_rules_boundary_constraints.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解业务规则与边界约束如何收敛。

| 规则编号 | 规则类型 | 规则内容 | 约束对象 |
|---|---|---|---|
| BR-001 | 不变量 | `L0-core` 必须作为平台跨仓共享契约的正式来源，不能退化为单仓内部类型集合。 | 共享契约来源 |
| BR-002 | 不变量 | 进入 `L0-core` 的契约必须具有跨仓共享价值，不得只服务单个下游仓的内部实现。 | 契约范围 |
| BR-003 | 不变量 | 共享契约语义必须能够被下游仓稳定引用，不能依赖某个下游仓的局部解释成立。 | 契约语义 |
| BR-004 | 不变量 | 契约演进必须保持兼容与可追溯，不能让下游仓在无明确依据的情况下承受破坏性变化。 | 契约演进 |
| BR-005 | 禁止行为 | 下游仓不得在 `L0-core` 之外自建与平台共享契约冲突的跨仓 schema。 | 下游契约消费 |
| BR-006 | 禁止行为 | 不得把事件投递、SDK 高层客户端封装、L1 业务语义、观测存储、归档恢复、运行时调度、认证授权写入 `L0-core` 范围。 | 相邻仓边界 |
| BR-007 | 显式变化 | 共享契约的新增、废弃、兼容性变化和破坏性变化必须显式发生，并保留可追溯依据。 | 契约变化 |
| BR-008 | 显式变化 | 新跨仓事件契约或共享语义不得只在单个下游仓局部声明，必须进入正式共享契约收束路径。 | 事件契约与共享语义 |
| BR-009 | 边界约束 | `L0-core` 定义事件契约不代表承担事件发布、订阅、确认、重试或死信处理能力。 | `L0-core` / `L0-bus` 边界 |
| BR-010 | 边界约束 | `L0-core` 提供可派生契约来源不代表承担 SDK 高层客户端体验、认证封装、配置加载或重试策略。 | `L0-core` / `L0-sdk` 边界 |
| BR-011 | 边界约束 | `L0-core` 表达业务域服务和事件契约不代表实现 L1 领域聚合、状态机或业务规则。 | `L0-core` / L1 领域服务边界 |
| BR-012 | 边界约束 | `L0-core` 约束追踪、错误和审计上下文契约不代表保存观测数据、审计日志、归档包或运行时执行记录。 | `L0-core` / L4 与 L2 边界 |
| BR-013 | 治理约束 | 影响跨仓兼容性、共享错误语义、追踪语义或审计语义的变化必须经过正式评审。 | 高影响契约变化 |
| BR-014 | 审计约束 | 共享契约范围、语义和兼容性相关变化必须留下足以支持后续追溯的记录。 | 契约追溯 |

|---|---|---|---|

| 契约检查结果摘要 | 快照数据 | 契约检查结果摘要不拥有独立真相，只反映某次契约检查状态。 | 随检查上下文变化而更新，不形成独立契约真相。 |
| 兼容性报告摘要 | 快照数据 | 兼容性报告摘要不拥有独立真相，只反映契约兼容性判断结果。 | 随契约演进和评审结果变化而更新。 |
| 上游标准引用 | 引用数据 | 本仓只保存对上游标准的引用关系，不拥有标准正文真相。 | 随引用关系建立、变化或失效而变化，本仓不负责标准正文生命周期。 |
| 正式评审 / ADR 引用 | 引用数据 | 本仓只保存对正式评审或 ADR 的引用关系，不拥有其正文真相。 | 随引用关系建立、变化或失效而变化，本仓不负责评审正文生命周期。 |
| 下游仓消费关系引用 | 引用数据 | 本仓只保存对下游仓消费关系的引用或说明，不拥有下游实现真相。 | 随下游消费关系变化而变化，本仓不负责下游实现生命周期。 |
| L1 业务数据正文 | 禁止保存正文 | L1 业务数据正文不属于 `L0-core` 真相范围，本仓不得保存其正文。 | 不进入本仓生命周期。 |
| 事件实例 payload 正文 | 禁止保存正文 | 事件实例 payload 正文不属于 `L0-core` 真相范围，本仓不得保存其正文。 | 不进入本仓生命周期。 |
| 观测日志 / trace 正文 | 禁止保存正文 | 观测日志 / trace 正文不属于 `L0-core` 真相范围，本仓不得保存其正文。 | 不进入本仓生命周期。 |
| 归档包正文 | 禁止保存正文 | 归档包正文不属于 `L0-core` 真相范围，本仓不得保存其正文。 | 不进入本仓生命周期。 |
| 运行时执行记录正文 | 禁止保存正文 | 运行时执行记录正文不属于 `L0-core` 真相范围，本仓不得保存其正文。 | 不进入本仓生命周期。 |
| SDK 凭据 / token 正文 | 禁止保存正文 | SDK 凭据 / token 正文不属于 `L0-core` 真相范围，本仓不得保存其正文。 | 不进入本仓生命周期。 |

`L0-core` 的数据真相是“契约真相”，不是业务真相、事件实例真相、观测真相、归档真相或运行时真相。派生产物只能作为快照，外部标准和评审记录只能作为引用，业务与运行时正文必须明确排除。

## 12. 接口与依赖

### 12.1 能力接口边界图

```text
                         +------------------------------+
                         |            L0-core           |
                         |    shared contract source    |
                         +---------------+--------------+
                                         |
        +----------------------+---------+---------+----------------------+
        v                      v         v         v                      v
+---------------+      +------------+ +----------+ +--------------+ +--------------+
| change iface  |      | query iface| | event out| | background   | | reference    |
| scope/evolve  |      | read/trace | | change   | | check/derive | | guide/sample |
+---------------+      +------------+ +----------+ +--------------+ +--------------+
```

本图只表达需求层能力接口面。`event out` 表示契约变化可被下游感知的异步输出面，不表示 `L0-core` 实现业务事件投递、确认、重试或死信处理。

### 12.2 对外能力接口

| 接口类型 | 名称 | 说明 | 所属能力层级 |
|---|---|---|---|
| 变更接口 | 共享契约范围收束 | 对外体现为正式纳入、调整或移出跨仓共享契约范围的能力入口。 | 核心闭环能力 |
| 查询接口 | 跨仓契约语义读取与引用 | 对外体现为下游仓能够稳定读取、检索和引用共享契约语义的能力入口。 | 核心闭环能力 |
| 变更接口 | 契约演进兼容处置 | 对外体现为正式处理契约新增、废弃、兼容性变化和破坏性变化的能力入口。 | 核心闭环能力 |
| 事件输出 | 契约变化可消费输出 | 对外体现为契约变化、兼容性状态和追溯结果可被下游持续感知的输出面。 | 核心闭环能力 |
| 后台任务接口（按需） | 契约检查与派生辅助 | 对外体现为按需执行契约检查、兼容性辅助判断和派生快照生成的后台能力入口。 | 外围增强能力 |
| 查询接口 | 契约追溯查看 | 对外体现为查看契约范围、语义、版本、兼容性和评审依据的能力入口。 | 外围增强能力 |
| 查询接口 | 契约接入说明与示例获取 | 对外体现为获取契约接入说明、样例和消费指引的能力入口。 | 外围增强能力 |

### 12.3 外部依赖边界

| 依赖方向 | 依赖类型 | 说明 | 所属能力层级 |
|---|---|---|---|
| 输入 | 定义来源依赖 | 本仓需要接收候选契约需求、上游标准、架构结论和 ADR 引用，以判断哪些内容应进入共享契约范围。 | 核心闭环能力 |
| 输入 | 治理结论依赖 | 本仓在高影响契约变化、破坏性变化或共享语义争议场景下，需要正式评审或治理结论作为依据。 | 核心闭环能力 |
| 输出 | 下游消费依赖 | 本仓输出共享契约语义、兼容性状态、追溯依据和派生快照，供 `L0-bus`、`L0-sdk`、L1+ 仓持续消费。 | 核心闭环能力 |
| 输入 | 外部能力依赖（按需） | 当前阶段无必须纳入主线的外部运行系统能力依赖；工具链、注册表和 CI 平台后移到非功能、测试或实施计划。 | 外围增强能力 |

### 12.4 同步 / 异步边界

| 能力边界 | 边界类型 | 说明 |
|---|---|---|
| 共享契约范围收束 | 同步能力边界 | 需要围绕一次明确的范围变更形成可审查结果。 |
| 跨仓契约语义读取与引用 | 同步能力边界 | 下游仓需要即时读取或引用共享契约语义。 |
| 契约演进兼容处置 | 同步能力边界 | 高影响变化需要明确处理结果和追溯依据。 |
| 契约变化可消费输出 | 异步输出边界 | 下游可持续感知契约变化，但不要求 `L0-core` 承担运行时投递职责。 |
| 契约检查与派生辅助 | 后台任务边界 | 检查和派生可以以任务形式执行，不进入核心同步接口。 |
| 契约追溯查看 | 同步能力边界 | 审计或开发者需要按需查看追溯依据。 |
| 契约接入说明与示例获取 | 同步能力边界 | 使用方需要按需获取说明和样例。 |

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|
| 性能 | 共享契约读取、契约追溯、契约检查和派生辅助不应成为 27 仓协作主链的阻塞点。 | 至少能证明核心契约消费方可在常规开发和集成流程中完成读取、检查和派生；具体耗时阈值在测试方案或实施计划中定义。 |
| 可用性 | 外围增强能力、自动发布体验、工具链或注册表不可用时，核心契约真相的建立、读取、演进和追溯口径仍应成立。 | 核心闭环能力不因 binding 发布、样例、额外导出、注册表或 CI 平台异常而整体失效。 |
| 安全 | 本仓不得越权保存业务、运行、观测、归档正文和凭据，也不得承接认证、授权或运行时投递职责。 | 数据归属表中的禁止保存正文不得进入本仓；边界外能力不得被写成本仓职责。 |
| 审计 / 可追溯 | 共享契约范围、语义、兼容性、破坏性变化、废弃和退役必须可追溯到正式依据。 | 任一高影响契约变化都应能追溯到评审、ADR、标准或其他正式依据引用。 |
| 幂等 / 一致性 | 同一共享契约在平台范围内必须保持单一正式语义和兼容性状态。 | 不得出现同一契约在不同下游仓具有互相冲突的正式解释；重复处理同一候选或派生请求不得产生冲突真相。 |
| 可观测性 | 共享契约当前状态、关键变化、兼容性判断、检查 / 派生结果和异常边界应能被平台稳定观察。 | 至少能判断契约当前是否有效、是否发生关键变化、是否存在兼容性风险、检查或派生是否失败。 |

## 14. 验收标准

> 校准来源：
> - `design-calibration/00_req_step_14_acceptance_criteria.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_14_acceptance_criteria.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解验收标准如何从测试脚本口径收敛为需求验收条件。

### 14.1 验收标准表

| 验收类别 | 验收项 | 验收条件 |
|---|---|---|
| 核心能力闭环验收 | 跨仓契约范围统一收束 | 能够清楚判断哪些契约属于 `L0-core` 的共享契约范围，哪些属于相邻仓或下游仓。 |
| 核心能力闭环验收 | 跨仓契约语义稳定表达 | 服务、事件、共享基础类型、错误、追踪上下文等共同语义能够被下游仓以同一口径理解和引用。 |
| 核心能力闭环验收 | 契约演进兼容与可追溯 | 契约新增、废弃、兼容性变化和破坏性变化均能显式发生，并能追溯到正式依据。 |
| 核心能力闭环验收 | 下游稳定消费和派生 | `L0-bus`、`L0-sdk`、L1+ 仓能够基于同一契约基线进行消费、引用或派生，而不是各自维护冲突契约。 |
| 功能能力验收 | 共享契约范围管理 | 共享契约范围可以被正式纳入、调整或移出，并能排除单仓内部实现和边界外能力。 |
| 功能能力验收 | 跨仓契约语义表达 | 本仓能够表达跨仓服务、事件、共享基础类型、错误、追踪和审计上下文等共同语义。 |
| 功能能力验收 | 契约演进兼容与追溯 | 高影响契约变化能够被识别、评审、追溯，并保持明确兼容性状态。 |
| 功能能力验收 | 下游消费与派生基础 | 本仓能够提供下游稳定消费和派生所需的契约来源、状态和引用基础。 |
| 功能能力验收 | 外围增强能力入口 | 契约检查与派生辅助、契约追溯查看、接入说明与示例具备明确需求入口，但不替代核心闭环验收。 |
| 规则 / 边界验收 | 正式共享契约来源不被稀释 | `L0-core` 不退化为单仓内部类型集合，也不允许下游自建冲突的跨仓 schema。 |
| 规则 / 边界验收 | 相邻仓职责不进入本仓 | 事件投递、SDK 高层封装、L1 业务实现、观测存储、归档恢复、运行调度、认证授权不进入 `L0-core` 职责。 |
| 规则 / 边界验收 | 契约变化显式发生 | 共享契约新增、废弃、兼容性变化和破坏性变化不得通过局部实现或文档漂移隐式发生。 |
| 数据归属验收 | 契约真相归属正确 | 共享契约定义、范围、版本 / 兼容性状态和演进记录被明确为 `L0-core` 真相。 |
| 数据归属验收 | 快照和引用不冒充真相 | 派生产物、检查摘要、兼容性报告摘要只能作为快照；标准、评审、ADR 和下游消费关系只能作为引用。 |
| 数据归属验收 | 禁止保存正文不入仓 | L1 业务数据、事件实例 payload、观测日志 / trace 正文、归档包正文、运行时记录和凭据不进入本仓正文范围。 |
| 非功能验收 | 核心能力不成为主链阻塞点 | 共享契约读取、追溯、检查和派生辅助不应阻塞常规跨仓协作。 |
| 非功能验收 | 核心真相不依赖外围能力 | 外围增强、工具链、注册表或 CI 平台异常时，核心契约真相的建立、读取、演进和追溯口径仍成立。 |
| 非功能验收 | 契约一致性与可观测性成立 | 同一契约在平台范围内保持单一正式语义和兼容性状态，关键状态、变化、检查结果和异常可被观察。 |

### 14.2 一票否决项

- `L0-core` 不能作为跨仓共享契约正式来源成立。
- 跨仓契约范围、语义、演进或下游消费任一核心闭环节点缺失。
- `L0-bus`、`L0-sdk`、L1、L2、L4 等相邻仓职责被写入 `L0-core` 核心职责。
- 业务数据、事件实例 payload、观测日志 / trace 正文、归档包正文、运行时记录或凭据进入本仓正文范围。
- 契约变化不可追溯，或同一共享契约在不同下游仓形成冲突真相。
- 验收标准以工具链、CI、registry、测试脚本替代需求层能力和边界判断。

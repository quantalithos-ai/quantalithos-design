## 2. 业务背景与驱动力

> 校准来源：
> - `design-calibration/01_arch_step_02_arch_goals_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_02_arch_goals_constraints.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解架构目标如何从需求基线转译而来。

Quantalithos 的多仓协作、七层依赖和跨仓集成需要一个稳定的共享契约来源。需求文档已经确认 `L0-core` 不承载事件投递、SDK 高层封装、业务实现、观测存储、归档恢复、运行调度或认证授权；因此架构设计的核心任务不是选择某个工具链，而是把跨仓共享契约来源仓的系统边界、职责边界、数据真相边界和依赖方向稳定下来。

| 驱动力 | 说明 |
|---|---|
| 多仓协作需要稳定契约基线 | 否则上层仓会围绕不同解释实现，形成跨仓 schema drift。 |
| L0 底座层需要最低变化率和最强边界保护 | 否则底层契约会被上层运行时、SDK 或业务语义反向牵引。 |
| 共享契约必须有单一真相与明确派生边界 | 否则派生产物、检查摘要和外部引用会被误当成契约真相。 |
| 契约变化必须可被追溯和下游感知 | 否则高影响变更会以局部实现或文档漂移的方式发生。 |
| 标准对齐必须被架构承接，但不能变成运行时外部依赖 | 否则系统上下文会混淆标准、工具链和运行时系统。 |

| 架构目标 | 说明 |
|---|---|
| 承载跨仓共享契约的正式来源边界 | 否则 `L0-core` 会退化为工具链仓、文件集合或某个下游仓的内部类型集合。 |
| 支撑范围收束、语义表达、演进追溯和下游消费派生四段结构主线 | 否则核心能力闭环会被拆散成零散契约、事件、错误、追踪或生成任务。 |
| 守住 `L0-core` 与 `L0-bus`、`L0-sdk`、L1、L2、L4 等相邻仓职责边界 | 否则事件投递、客户端封装、业务实现、观测存储、归档恢复和运行调度会反向污染本仓。 |
| 守住契约真相、派生快照、外部引用和禁止正文的数据边界 | 否则本仓会吸收业务、事件实例、观测、归档、运行时或凭据正文。 |
| 允许下游仓基于同一契约基线稳定消费和派生 | 否则上层仓会各自维护冲突 schema，破坏七层依赖方向。 |
| 支撑高影响契约变化的兼容性与追溯边界 | 否则破坏性变化、废弃和退役会以局部实现或文档漂移方式发生。 |

## 3. 约束条件

> 校准来源：
> - `design-calibration/01_arch_step_02_arch_goals_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_02_arch_goals_constraints.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解不可变约束、当前取舍和架构非目标如何收敛。

### 3.1 不可变约束

| 约束 | 说明 |
|---|---|
| 不设计事件总线运行时 | 事件发布、订阅、确认、重试、死信属于 `L0-bus`，否则契约来源会与投递实现混淆。 |
| 不设计 SDK 高层客户端或包发布中心 | 重试、配置、认证封装、开发者体验和发布渠道属于 `L0-sdk` 或实施计划，否则本仓会变成客户端产品。 |
| 不设计 L1 业务域实现 | 身份、对话、工作、过程、治理、制品、工作空间的业务语义属于 L1 仓，否则共享契约会吸收业务真相。 |
| 不拥有业务、事件实例、观测、归档、运行时或凭据正文 | 这些正文真相属于相邻仓或外部系统，否则数据所有权会被打穿。 |
| 不允许上层仓反向拥有或覆盖共享契约真相 | 共享契约真相必须在 `L0-core` 收束，否则平台会形成冲突契约。 |
| 不把标准、工具链、注册表或 CI 平台写成运行时外部系统依赖 | CloudEvents / W3C 是标准对齐来源，工具链 / CI / registry 是后续技术或实施机制。 |

### 3.2 当前阶段可接受取舍

| 取舍 | 当前口径 |
|---|---|
| 多语言派生与生成产物 | 当前作为下游消费与派生支撑，不进入核心架构职责。 |
| 样例、可视化、自动发布和额外导出格式 | 当前作为外围增强处理，不进入核心能力闭环。 |
| 具体契约字段、ID 包装、字段编号策略 | 当前只保留契约语义和演进边界，具体形态后移到概要 / 详细设计。 |
| 工具链、CI、registry、语言生成器与包发布路径 | 当前不作为系统上下文外部依赖，后移到关键技术选型、测试方案或实施计划。 |
| 契约检查与派生辅助 | 当前保留为外围增强和后台任务边界，不作为判断核心架构成立的前提。 |

### 3.3 架构非目标

| 非目标 | 不展开原因 |
|---|---|
| 不设计事件投递架构 | 事件投递属于 `L0-bus`，不属于共享契约来源仓。 |
| 不设计 SDK 客户端架构 | SDK 高层封装和开发者体验属于 `L0-sdk`，本仓只提供可派生契约来源。 |
| 不设计 L1 领域服务架构 | L1 仓拥有业务语义和领域实现，`L0-core` 只承载共享契约语义边界。 |
| 不设计观测查询、审计存储或归档恢复架构 | 这些属于 `L4-observability` 和 `L4-archive`，本仓只约束相关契约与上下文。 |
| 不设计运行时调度、工具执行或容器编排架构 | 这些属于 L2 运行层，不属于本仓架构主线。 |
| 不设计认证、授权或权限裁决架构 | 这些属于安全入口、治理或授权能力，不属于共享契约来源仓。 |
| 不设计测试执行、CI 命令或包发布流程 | 这些属于测试方案或实施计划，不属于架构设计主线。 |

## 4. 职责边界

> 校准来源：
> - `design-calibration/01_arch_step_03_responsibility_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_03_responsibility_boundary.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓职责边界如何从需求基线和架构约束收敛而来。

`L0-core` 的职责是把跨仓共享契约收束为单一真相，并保持它的演进边界稳定；它不承载事件投递、SDK 客户端体验、L1 业务语义实现或观测 / 归档正文。

| 职责项 | 类型 | 说明 |
|---|---|---|
| 跨仓共享契约真相承载 | 做 | 这是本仓的核心职责，负责把平台级共享协议收束为单一正式来源。 |
| 共享契约版本与兼容性边界维护 | 做 | 若不由本仓维护，下游将围绕不同解释演进并产生 drift。 |
| 提供共享契约稳定引用入口 | 做 | 下游与上游标准都需要围绕同一入口消费契约，但不意味着本仓保存外部正文。 |
| 事件总线运行时 | 不做 | 事件投递、订阅、确认、重试和死信属于 `L0-bus`。 |
| SDK 高层客户端封装 | 不做 | 客户端体验、重试、配置和分发渠道属于 `L0-sdk`。 |
| L1 业务语义实现 | 不做 | 业务状态机、规则和领域实现属于各 L1 仓。 |
| 观测 / 归档正文存储与查询 | 不做 | 追踪、日志、审计和归档查询属于 `L4-observability` / `L4-archive`。 |
| 安全认证与权限裁决 | 不做 | 身份认证和授权治理属于安全入口或治理层。 |
| 共享契约与业务语义的桥接解释 | 易混淆职责 | 容易被误解为业务服务，实际上这里只能表达契约边界，不能承载业务语义。 |
| 真相与派生产物边界维护 | 易混淆职责 | 容易把派生快照、检查摘要或引用表误当成真相。 |

## 5. 系统边界与上下文

> 校准来源：
> - `design-calibration/01_arch_step_04_system_context.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_04_system_context.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓的正式上下文对象、输入面和输出面如何从共享契约定位收敛而来。

`L0-core` 不是运行时服务，它的系统边界围绕“契约来源”展开。它从上游接收需求、标准与设计态草案，向下游输出可消费的共享契约基线，而不是输出运行时 API 或业务流程。

| 方向 | 面 | 说明 |
|---|---|---|
| 输入 | 需求基线输入面 | 来自 `00-需求文档.md` 的仓级定位、边界、数据归属与能力结论。 |
| 输入 | 标准对齐输入面 | 来自 CloudEvents、W3C Trace Context 和相关工具链的约束。 |
| 输入 | 设计态草案输入面 | 来自 proto 草案与事件目录草案的契约形状候选。 |
| 输出 | 契约来源输出面 | 向下游输出共享契约的正式真相来源。 |
| 输出 | 兼容性输出面 | 向下游输出版本边界、演进节奏和派生入口。 |
| 输出 | 引用输出面 | 向所有消费仓提供统一引用口径。 |

```text
-------------------------+
| 标准对齐来源            |
| CloudEvents / W3C       |
+-----------+-------------+
            |
            | input
            v
+==============================================================+
| L0-core                                                      |
| 跨仓共享契约来源 / 单一真相锚点                              |
+==========+===============================+===================+
           | output                        | output
           v                               v
+----------------------+        +------------------------------+
| L0-bus / L0-sdk      |        | L1~L6 各业务与支撑仓          |
| 契约消费与派生        |        | 业务实现与运行消费            |
+----------------------+        +------------------------------+

设计态输入: proto 草案 / event catalog
需求输入: 00-需求文档.md
```

`L0-core` 的边界不是“谁调用谁”，而是“谁提供契约真相、谁消费契约真相”。本章只定义上下文对象、输入面、输出面与边界，不定义子域、数据所有权或接口协议。

## 6. 限界上下文与子域划分

> 校准来源：
> - `design-calibration/01_arch_step_05_bounded_context.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_05_bounded_context.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓内部语义结构如何分为共享契约核心、领域契约包和本地索引 / 投影 / 引用。

`L0-core` 内部可分为三层语义单元：共享契约核心、领域契约包和本地索引 / 投影 / 引用。共享契约核心承载全仓共享的基础语义、兼容规则和通用契约真相；各领域契约包围绕核心展开；本地索引 / 投影 / 引用只为稳定消费外部标准、目录和治理信息而存在。

| 名称 | 类型 | 作用 | 与其他部分的关系 |
|---|---|---|---|
| 共享契约核心 | 核心子域 | 承载全仓共享的基础契约真相、兼容规则和通用语义。 | 是所有领域契约包的共同基础，其他部分围绕它展开。 |
| 领域契约包 - identity | 支撑子域 | 承载身份域对外共享契约。 | 依附共享契约核心，不拥有基础真相。 |
| 领域契约包 - conversation | 支撑子域 | 承载对话域对外共享契约。 | 依附共享契约核心，与其他契约包并列消费核心。 |
| 领域契约包 - work | 支撑子域 | 承载工作域对外共享契约。 | 依附共享契约核心，不反向定义核心语义。 |
| 领域契约包 - process | 支撑子域 | 承载过程域对外共享契约。 | 依附共享契约核心，独立演进自己的契约边界。 |
| 领域契约包 - governance | 支撑子域 | 承载治理域对外共享契约。 | 依附共享契约核心，作为治理语义的正式出口。 |
| 领域契约包 - artifact | 支撑子域 | 承载制品域对外共享契约。 | 依附共享契约核心，为制品与产物语义提供契约出口。 |
| 标准映射索引 | 本地索引 / 投影 / 引用 | 提供标准对齐的本地视图，稳定映射外部标准概念。 | 只引用标准，不拥有标准正文。 |
| 事件目录引用 | 本地索引 / 投影 / 引用 | 提供事件目录的本地引用视图，稳定事件入口定位。 | 只保存目录引用，不拥有目录正文。 |
| 兼容性追溯索引 | 本地索引 / 投影 / 引用 | 提供版本兼容、弃用和追溯的本地治理视图。 | 只承载追溯入口，不替代核心契约真相。 |

```text
+==============================================================+
| L0-core 语义边界                                             |
|                                                              |
|  +-------------------------+                                 |
|  | 共享契约核心             |                                 |
|  | 基础语义 / 兼容边界      |                                 |
|  +-----------+-------------+                                 |
|              |                                               |
|              | foundation                                    |
|              v                                               |
|  +-------------------------+                                 |
|  | 领域契约包               |                                 |
|  | identity / conversation  |                                 |
|  | work / process / ...     |                                 |
|  +-----------+-------------+                                 |
|              |                                               |
|              | reference                                     |
|              v                                               |
|  +-------------------------+                                 |
|  | 本地索引 / 投影 / 引用    |                                 |
|  | 标准 / 事件目录 / 追溯    |                                 |
|  +-------------------------+                                 |
|                                                              |
+==============================================================+
```

`L0-core` 的内部层次不是按代码目录分，而是按语义稳定性、变化速率和真相归属分层。若把这些层混成一个上下文，核心真相、领域契约和引用索引就会互相污染。

## 7. 容器 / 部署架构

> 校准来源：
> - `design-calibration/01_arch_step_06_container_deployment.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_06_container_deployment.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解为什么 `L0-core` 的部署视图按无在线运行时契约仓表达。

`L0-core` 没有常驻在线运行时容器。它的正式承载结构由契约变更入口、契约源码承载、契约校验与派生处理单元、契约发布快照承载和契约工具链执行环境组成。

```text
                    +----------------------+
                    | 下游契约消费边界     |
                    | L0 / L1~L6           |
                    +----------^-----------+
                               |
                               | consume
                               |
      +======================================================+
      | L0-core 正式承载结构                                |
      |                                                      |
      |   +----------------------------------------------+   |
      |   | 契约变更入口单元                              |   |
      |   +----------------------+-----------------------+   |
      |                          |                           |
      |                          | carry                     |
      |                          v                           |
      |   +----------------------------------------------+   |
      |   | 契约源码承载                                  |   |
      |   +----------------------+-----------------------+   |
      |                          |                           |
      |                          | process                   |
      |                          v                           |
      |   +----------------------------------------------+   |
      |   | 契约校验与派生处理单元                        |   |
      |   +---------------+------------------+-----------+   |
      |                   |                  |               |
      |                   | carry            | depend        |
      |                   v                  v               |
      |          +----------------+   +------------------+   |
      |          | 契约发布快照    |   | 契约工具链执行    |   |
      |          | 承载            |   | 环境              |   |
      |          +----------------+   +------------------+   |
      |                                                      |
      +======================================================+
```

| 对象 | 类型 | 主要职责 | 运行关系 | 说明 |
|---|---|---|---|---|
| 契约变更入口单元 | 同步入口单元 | 承接正式契约变更输入。 | 将变更交给契约源码承载形成可校验基线。 | 这是变更进入本仓的入口，不是运行时业务 API。 |
| 契约源码承载 | 正式存储承载 | 承载共享契约真相与版本历史。 | 被校验与派生处理单元读取和处理。 | 这是本仓最核心的正式承载，不等同于数据库表。 |
| 契约校验与派生处理单元 | 后台处理单元 | 承接契约校验、兼容性检查和派生处理。 | 依赖工具链执行环境，并产出发布快照。 | 这是构建期后台处理，不是业务 worker。 |
| 契约发布快照承载 | 正式存储承载 | 承载可被下游消费的版本化契约快照。 | 被下游契约消费边界消费。 | 这是契约基线的发布承载，不等同于 SDK 客户端发布。 |
| 契约工具链执行环境 | 正式基础设施依赖 | 支撑契约校验与派生处理成立。 | 被校验与派生处理单元依赖。 | 这是构建期基础设施依赖，不是运行时外部系统。 |
| 下游契约消费边界 | 运行时对接的正式外部边界 | 消费契约发布快照并在各仓内实现自身职责。 | 从契约发布快照承载读取或引用基线。 | 它只作为消费边界出现，不属于本仓部署结构。 |

本章不引入 API 服务、数据库、缓存、消息消费者、包注册表或具体 CI 平台。

## 8. 依赖方向与层间约束

> 校准来源：
> - `design-calibration/01_arch_step_07_dependency_direction.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_07_dependency_direction.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓如何用依赖角色保护核心契约语义。

`L0-core` 的依赖方向以保护核心契约语义为中心。外部标准、草案、下游反馈和工具链都不能直接决定核心真相，必须通过外部接缝与契约承接 / 编排角色进入。

```text
      +====================================================+
      | L0-core 依赖边界                                  |
      |                                                    |
      |   +----------------------------+                   |
      |   | 外部接缝角色               |                   |
      |   | 标准 / 草案 / 下游反馈入口 |                   |
      |   +-------------+--------------+                   |
      |                 | boundary in                       |
      |                 v                                  |
      |        +----------------------------+              |
      |        | 契约承接 / 编排角色         |              |
      |        | 变更收口 / 校验编排         |              |
      |        +-------------+--------------+              |
      |                      | allowed dependency           |
      |                      v                             |
      |        +----------------------------+              |
      |        | 核心契约语义角色            |              |
      |        | 契约真相 / 兼容边界         |              |
      |        +----------------------------+              |
      |                                                    |
      |   +----------------------------+                   |
      |   | 技术承载角色               |                   |
      |   | 源码 / 快照 / 工具链支撑   |                   |
      |   +----------------------------+                   |
      |                                                    |
      +====================================================+
```

| 架构责任层 / 依赖角色 | 允许依赖 | 禁止依赖 | 说明 |
|---|---|---|---|
| 核心契约语义角色 | 只依赖本仓已确认的契约规则和兼容边界 | 禁止依赖外部标准正文、工具链结果、下游反馈、发布快照和 SDK 分发形态 | 该角色保护契约真相，不能被外部能力反向牵引。 |
| 契约承接 / 编排角色 | 允许依赖核心契约语义角色，并通过接缝接收外部输入 | 禁止绕过核心语义直接把外部输入写成契约真相 | 该角色负责把输入转译为可审查的契约变化。 |
| 外部接缝角色 | 允许接收标准、草案、需求输入和下游反馈，并交给承接 / 编排角色 | 禁止直接定义核心语义或直接改写共享契约真相 | 外部输入必须经过正式接缝和审查，不得直达核心。 |
| 技术承载角色 | 允许支撑源码承载、发布快照承载和工具链执行 | 禁止决定契约语义、兼容边界或领域契约归属 | 技术承载只是支撑条件，不是架构语义来源。 |
| 下游契约消费边界 | 允许消费发布快照和稳定引用入口 | 禁止反向拥有或覆盖共享契约真相 | 下游是消费方，不是本仓契约真相来源。 |

后续概要设计可以把这些依赖角色映射到具体结构，但不得打破本章定义的依赖红线。

## 9. 数据所有权与一致性策略

> 校准来源：
> - `design-calibration/01_arch_step_08_data_ownership_consistency.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_08_data_ownership_consistency.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓如何先确定数据归属，再确定一致性口径。

`L0-core` 的数据所有权只围绕契约真相成立。本地存在快照、投影、报告摘要或引用关系，不表示本仓拥有它们背后的外部正文或下游实现真相。

| 数据项 | 数据类型 | 归属说明 | 边界说明 |
|---|---|---|---|
| 共享契约定义 | 正式真相数据 | 由 `L0-core` 拥有正式真相。 | 这是本仓作为共享契约来源仓成立的核心数据。 |
| 共享契约范围 | 正式真相数据 | 由 `L0-core` 拥有正式真相。 | 范围进入或退出必须显式发生，不能由下游仓隐式决定。 |
| 契约版本 / 兼容性状态 | 正式真相数据 | 由 `L0-core` 拥有正式真相。 | 兼容状态保护下游消费基线，不能由工具链结果单独决定。 |
| 契约演进记录 | 正式真相数据 | 由 `L0-core` 拥有正式真相。 | 新增、变更、废弃和退役必须可追溯，不得隐式改写。 |
| 契约正式发布基线 | 正式真相数据 | 由 `L0-core` 对其契约状态负责。 | 它表示某一版本契约已正式收口，不等同于 SDK 包或注册表产物。 |
| 契约发布快照 | 快照 / 投影数据 | 本仓可保留从契约真相派生出的版本化快照。 | 快照必须可追溯到契约真相，但不反向拥有真相。 |
| 下游消费派生产物 | 快照 / 投影数据 | 下游消费派生产物来自共享契约真相。 | 派生产物不拥有独立真相，也不能反向改变契约定义。 |
| 契约检查结果摘要 | 快照 / 投影数据 | 只反映某次检查上下文下的结果。 | 检查摘要不是契约真相，失败也不能自动改写真相。 |
| 兼容性报告摘要 | 快照 / 投影数据 | 只反映某次兼容性判断结果。 | 报告摘要服务审查与追溯，不替代正式兼容状态。 |
| 上游标准引用 | 引用关系数据 | 本仓只保存对标准的引用关系。 | 标准正文真相不属于本仓。 |
| 设计态草案引用 | 引用关系数据 | 本仓只保存对 proto 草案和事件目录草案的引用。 | 草案是输入材料，不是正式契约真相本身。 |
| 正式评审 / ADR 引用 | 引用关系数据 | 本仓只保存对评审或 ADR 的引用关系。 | 评审正文和 ADR 正文不由本仓拥有。 |
| 下游仓消费关系引用 | 引用关系数据 | 本仓只保存消费关系引用或说明。 | 下游实现真相不属于本仓。 |
| L1 业务数据正文 | 明确不拥有的正文 / 真相 | 本仓不得保存其正文或主张其真相。 | 业务真相属于对应 L1 仓。 |
| 事件实例 payload 正文 | 明确不拥有的正文 / 真相 | 本仓不得保存事件实例正文。 | 本仓只定义事件契约，不拥有事件实例。 |
| 观测日志 / trace 正文 | 明确不拥有的正文 / 真相 | 本仓不得保存观测正文。 | 观测真相属于观测系统或相邻仓。 |
| 归档包正文 | 明确不拥有的正文 / 真相 | 本仓不得保存归档包正文。 | 归档真相属于归档系统或相邻仓。 |
| 运行时执行记录正文 | 明确不拥有的正文 / 真相 | 本仓不得保存运行时执行正文。 | 运行时真相不属于契约来源仓。 |
| SDK 凭据 / token 正文 | 明确不拥有的正文 / 真相 | 本仓不得保存凭据或 token 正文。 | 安全凭据不属于共享契约真相。 |
| 下游仓内部实现数据正文 | 明确不拥有的正文 / 真相 | 本仓不得保存下游实现正文。 | 下游实现真相属于各自仓。 |

| 数据关系 / 场景 | 关联数据类型 | 一致性口径 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 契约真相内部变更 | 正式真相数据到正式真相数据 | 强一致 | 阻断正式收口，不形成部分成功状态。 | 契约定义、范围、版本和演进记录必须同时成立。 |
| 契约真相到正式发布基线 | 正式真相数据到正式真相数据 | 发布门禁一致 | 发布基线不得形成，保留上一正式基线。 | 正式基线必须代表已经收口的契约状态。 |
| 契约真相到发布快照 | 正式真相数据到快照 / 投影数据 | 发布边界一致 | 挂起快照发布，保留旧快照或标记失败。 | 快照可以落后，但不能伪装成新基线。 |
| 契约真相到派生产物 | 正式真相数据到快照 / 投影数据 | 最终一致 | 保留旧派生产物或标记待刷新。 | 派生产物延迟不改变契约真相。 |
| 契约检查与兼容性报告 | 正式真相数据到快照 / 投影数据 | 审查一致 | 检查失败时阻断收口或标记报告失败。 | 检查和报告用于审查，不自动成为真相。 |
| 契约真相到外部引用 | 正式真相数据到引用关系数据 | 引用有效性一致 | 标记引用失效，不伪造正文补齐。 | 引用只要求关系有效，不表示拥有正文。 |
| 本仓与明确不拥有正文的边界 | 引用关系数据到明确不拥有的正文 / 真相 | 边界约束一致 | 拒绝正文进入本仓，必要时挂起或显式失败。 | 禁止正文进入是数据边界红线。 |
| 下游消费反馈到契约变更 | 引用关系数据到正式真相数据 | 接缝审查一致 | 未经接缝审查不得改写契约真相。 | 下游反馈是输入，不是契约真相来源。 |

```text
+-----------------------+        derive        +----------------------+
| 契约真相               | -------------------> | 发布快照 / 派生产物   |
| 定义 / 范围 / 版本     |                      | 只读消费 / 投影       |
+-----------+-----------+                      +----------+-----------+
            |                                             |
            | reference                                   | consume
            v                                             v
+-----------------------+                      +----------------------+
| 外部正文引用关系       |                      | 下游消费边界          |
| 标准 / 草案 / ADR      |                      | 不拥有契约真相        |
+-----------------------+                      +----------------------+

禁止进入 L0-core: 业务正文 / 事件实例正文 / 观测正文 / 归档正文 / 运行正文 / 凭据正文
```

一致性策略必须先服从归属边界：真相内部强一致，快照与派生可最终一致，引用失效必须显式表达，禁止正文必须拒绝进入。

## 10. 关键交互与通信方式

> 校准来源：
> - `design-calibration/01_arch_step_09_interactions_communication.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_09_interactions_communication.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本仓如何区分同步入口、异步事实传播和后台延后承接。

`L0-core` 的关键交互以契约真相保护为中心。需要即时判断是否成立、是否可读、是否可引用的场景走同步请求 / 响应类交互；已经成立的契约事实和状态变化适合异步传播；校验、派生和快照刷新适合后台延后承接。

| 交互场景 | 交互边界 | 交互目的 | 边界说明 |
|---|---|---|---|
| 契约范围与演进变更输入 | 外部接缝角色 -> 契约承接 / 编排角色 | 即时判断候选变更能否进入正式审查和收口边界 | 这是变更进入契约真相的入口，不是下游直接改写核心语义。 |
| 契约语义读取与引用 | 下游契约消费边界 -> 契约发布快照 / 稳定引用入口 | 让下游能读取或引用当前稳定契约基线 | 这是消费边界，不表示下游拥有或改写真相。 |
| 契约变化事实传播 | 契约发布基线 / 兼容性状态 -> 下游契约消费边界 | 让下游感知已经成立的契约变化和兼容性状态 | 这是事实传播，不是 `L0-core` 承担事件总线投递实现。 |
| 契约校验与派生处理 | 契约源码承载 -> 契约校验与派生处理单元 | 延后完成校验、兼容性辅助判断、派生快照和报告摘要 | 这些处理不应被硬塞进同步入口内伪装成立即完成。 |
| 发布快照刷新与消费 | 契约校验与派生处理单元 -> 契约发布快照承载 -> 下游消费边界 | 形成可被下游消费的版本化契约快照 | 快照是消费承载，不是 SDK 包发布中心，也不能反向拥有契约真相。 |
| 标准 / 草案 / 评审结论接入 | 外部输入面 -> 外部接缝角色 | 将标准、草案和评审结论转化为可审查的契约输入 | 外部正文和草案不能直接进入核心契约语义。 |
| 引用失效与待确认暴露 | 引用关系数据 -> 契约承接 / 编排角色 / 下游消费边界 | 显式暴露引用失效、待确认或不可收口状态 | 引用失效时不能伪造正文或继续表现为已确认基线。 |

| 交互场景 | 推荐通信方式 | 不宜采用的方式 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 契约范围与演进变更输入 | 同步请求 / 响应类交互 | 不宜以异步传播替代正式入口判断 | 明确失败或进入待审查状态，不伪装为已改写真相 | 该场景需要即时判断候选变更是否能进入正式边界。 |
| 契约语义读取与引用 | 同步请求 / 响应类交互 | 不宜依赖异步回调作为主路径 | 明确不可读、旧基线或引用失效状态 | 下游读取需要稳定、明确、可解释的当前视图。 |
| 契约变化事实传播 | 异步事件 / 回调类交互 | 不宜伪装成同步全下游闭环 | 保持未传播 / 待消费状态，不反向撤销契约真相 | 契约事实成立后可以被感知，但不要求所有下游同步完成。 |
| 契约校验与派生处理 | 后台任务 / 延后承接类交互 | 不宜硬写成同步入口内完成 | 挂起派生、保留旧快照或标记处理失败 | 校验与派生可能耗时或依赖工具链，不应阻塞入口完成全部工作。 |
| 发布快照刷新与消费 | 后台任务 / 延后承接类交互 | 不宜把快照刷新写成下游直接改写真相 | 挂起新快照，保留上一正式可消费基线 | 快照可延迟，但不能伪装成已发布的新基线。 |
| 标准 / 草案 / 评审结论接入 | 同步请求 / 响应类交互 | 不宜作为异步事实自动改写核心 | 标记输入不足、待确认或拒绝进入 | 外部输入需要先被正式接缝判断，不得直达核心。 |
| 引用失效与待确认暴露 | 异步事件 / 回调类交互 | 不宜通过同步读取时临时补造正文 | 暴露引用失效或待确认，不伪造正文 | 引用状态变化可以传播给消费方，但不能改变正文归属。 |

```text
+------------------+       sync        +----------------------+
| 外部输入 / 下游  | --------------->  | 契约承接 / 编排角色  |
| 反馈 / 读取请求  |                   | 入口判断 / 读取边界  |
+------------------+                   +----------+-----------+
                                                   |
                                                   | schedule
                                                   v
                                      +------------------------+
                                      | 校验 / 派生 / 快照刷新 |
                                      | 后台延后承接           |
                                      +----------+-------------+
                                                 |
                                                 | publish fact
                                                 v
+------------------+       async       +----------------------+
| 下游消费边界     | <---------------  | 发布基线 / 快照 / 状态 |
| L0 / L1~L6       |                   | 可感知输出面           |
+------------------+                   +----------------------+
```

本章不定义具体协议、API 路径、事件名、topic、队列、DTO、schema、工具命令或处理时序。后续概要设计可以将这些交互方式映射到接口轮廓和处理流，但不得突破本章定义的边界语义。

## 11. 关键技术选型

> 校准来源：
> - `design-calibration/01_arch_step_10_technology_choices.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_10_technology_choices.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章为什么按架构机制表达，而不是按工具名或产品名表达。

本章中的关键技术选型不是 Rust、proto、CI、registry 或某个框架清单，而是已经影响 `L0-core` 边界、真相、一致性和交互方式的架构机制。

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 | 说明 |
|---|---|---|---|---|
| 结构化契约源码作为单一真相承载 | 契约事实散落在草案、README、事件目录和下游实现中，容易形成多处解释 | `L0-core` 必须有可审查、可版本化、可追溯的契约真相承载，才能作为跨仓共享契约来源 | 需要持续维护源码组织、版本边界和变更记录，不能依赖临时文档或下游实现补齐 | 该机制决定契约真相如何被正式承载，属于架构层决定，不是单个文件格式选择。 |
| 正式承接层隔离外部输入与核心契约语义 | 标准、草案、评审结论和下游反馈可能直接打穿核心契约语义 | 外部输入必须先进入正式接缝，再转化为可审查的契约变更，避免外部来源直接改写真相 | 增加承接判断和审查成本，输入不足时必须挂起或拒绝进入 | 该机制保护核心语义边界，承接 Step 7 的依赖方向红线。 |
| 版本化发布基线与只读发布快照 | 下游若直接绑定核心真相或派生产物，会反向约束核心演进 | 发布基线表示已收口的契约状态，发布快照作为下游稳定消费面，二者隔离真相与消费 | 增加基线管理、快照刷新、旧快照保留和消费侧理解成本 | 该机制同时影响数据所有权、一致性和交互边界，不是简单发布产物。 |
| 兼容性门禁与演进追溯机制 | 新增、废弃、破坏性变化若无门禁，会让下游承担不可解释的契约漂移 | 高影响变化必须在正式收口前经过兼容性判断，并保留追溯依据 | 增加评审与追溯材料维护成本，可能延缓契约变更速度 | 该机制支撑 `L0-core` 作为低变化率底座成立，不能后移为普通测试脚本。 |
| 构建期校验 / 派生的后台承接机制 | 契约校验、兼容性辅助判断和派生快照可能耗时，若塞进同步入口会制造伪同步完成 | 后台延后承接允许校验、派生、报告摘要和快照刷新在正式入口之外收敛 | 会引入挂起、失败、旧快照保留和延迟一致性解释成本 | 该机制承接 Step 6 的无在线运行时和 Step 9 的后台交互边界。 |
| 契约事实变化的可感知输出边界 | 下游需要知道契约变化，但 `L0-core` 不应承担事件总线投递实现 | 将契约变化、发布基线和兼容性状态作为可感知事实输出，而不是实现 publish / subscribe / ack | 需要明确未传播、待消费和消费失败状态，避免被误解为全下游同步完成 | 该机制影响跨仓协作主链，但必须与 `L0-bus` 投递职责保持边界。 |
| 外部正文引用而非吸收机制 | 标准正文、ADR 正文、业务正文或事件实例正文被复制进本仓，会污染数据所有权 | 本仓只保存引用关系和追溯入口，不拥有外部正文真相 | 引用失效时必须显式暴露，不能通过复制正文掩盖失效 | 该机制保护 Step 8 的数据边界，防止引用关系变成正文所有权。 |

| 当前采用 | 当前不采用 | 边界原因 |
|---|---|---|
| 结构化契约源码 + 发布基线承载真相 | 在线 API 服务 + 数据库承载核心真相 | `L0-core` 不是运行时业务服务，当前主线是契约来源仓。 |
| 只读发布快照供下游消费 | 下游直接读取和绑定核心真相结构 | 保护核心演进空间，避免下游反向拥有真相。 |
| 构建期后台校验 / 派生 | 同步入口内完成全部校验、派生和发布 | 避免伪同步完成，允许挂起和失败状态显式存在。 |
| 契约事实可感知输出 | 本仓实现事件总线投递能力 | 下游需要感知变化，但投递、确认、重试和死信属于 `L0-bus`。 |
| 引用外部正文 | 复制外部正文进入本仓 | 本仓只拥有契约真相和引用关系，不拥有标准、ADR、业务、运行或观测正文。 |

## 12. 备选方案与取舍

> 校准来源：
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_11_alternatives_tradeoffs.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章为什么只比较相邻结构性替代路径。

当前主线方案是：`L0-core` 作为跨仓共享契约来源仓，以结构化契约源码承载契约真相，以发布基线和只读发布快照承接下游消费，以后台校验 / 派生和可感知事实输出支撑演进。

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 契约来源仓 + 发布基线 / 只读快照 + 后台承接 | 解决跨仓契约真相、下游消费、兼容演进和变化感知需要同时成立的问题 | 真相边界清晰，下游消费稳定，派生可延后，变化可被感知，且不侵入 `L0-bus` / `L0-sdk` | 初期结构更重，需要维护发布基线、快照、追溯和挂起状态 | 采用 | 这是当前主线方案，最符合 `L0-core` 作为共享契约底座的目标。 |
| 纯文档 / 草案聚合路径 | 解决契约资料分散、旧文档难查的问题 | 成本低，迁移快，适合早期整理资料 | 缺少正式真相边界、兼容门禁和下游稳定消费面，容易继续形成多处解释 | 不采用 | 该路径只能改善可读性，不能让 `L0-core` 成为正式契约来源。 |
| 工具链 / 生成物中心路径 | 解决契约检查、生成和多语言派生的工程效率问题 | 工程落地直观，能快速支撑生成物和自动化检查 | 工具链、binding 或注册表状态容易反向成为契约真相，并污染 `L0-core` / `L0-sdk` 边界 | 不采用 | 生成和检查重要，但只能作为承接机制，不能成为本仓架构主语。 |
| 下游自治契约路径 | 解决各下游仓局部迭代速度和自主适配问题 | 下游改动快，局部阻塞少，短期协作成本低 | 共享 schema 容易漂移，跨仓语义不一致，破坏 L0 到上层的单向依赖关系 | 不采用 | 该路径牺牲平台级共享契约一致性，不适合 L0 底座。 |
| 全同步收口路径 | 解决每次契约变化都希望即时完成校验、派生、快照和下游确认的问题 | 表面一致性强，入口结果感明确 | 把不适合同步完成的校验、派生和下游消费压进入口，容易形成高耦合和伪同步完成 | 不采用 | 同步边界只适合入口判断和读取，不适合作为全部承接主线。 |
| 全异步流水线路径 | 解决同步入口复杂、长流程难以即时完成的问题 | 入口耦合低，后台扩展性好，适合长耗时处理 | 候选变更是否能进入正式边界缺少即时判断，失败口径容易延迟暴露 | 不采用 | `L0-core` 仍需要同步入口判断，不能把所有正式边界都推迟到异步流水线。 |

| 当前方案得到什么 | 当前方案失去什么 | 取舍说明 |
|---|---|---|
| 契约真相边界清晰 | 不如纯文档路径轻量 | L0 底座需要正式真相，不能只做资料整理。 |
| 下游通过只读快照稳定消费 | 不如下游自治路径灵活 | 平台级一致性优先于单仓局部速度。 |
| 校验 / 派生可后台挂起 | 不如全同步路径有即时完成感 | 避免伪同步完成，显式暴露挂起和失败状态。 |
| 契约变化可被下游感知 | 不直接获得事件总线投递能力 | 变化感知属于契约边界，投递实现属于 `L0-bus`。 |
| 工具链作为支撑机制 | 不把生成效率作为唯一主线 | 工具链服务契约真相，不能反向定义契约真相。 |

在线业务服务、事件总线实现、SDK 客户端中心、L1 业务语义实现、外部正文托管都不是正式备选方案。

## 13. 横切关注点

> 校准来源：
> - `design-calibration/01_arch_step_12_cross_cutting.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_12_cross_cutting.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章如何把横切约束限定在契约来源仓主线之上。

`L0-core` 的横切关注点不是通用运行时服务清单，而是持续压在契约真相、外部接缝、下游消费、发布快照和后台承接之上的长期约束。

| 横切关注点 | 作用范围 | 约束要求 | 保护目标 | 说明 |
|---|---|---|---|---|
| 安全边界 | 外部输入、正式接缝、核心契约语义、明确不拥有正文 | 外部输入必须通过正式接缝进入；本仓不得吸收外部正文、业务正文、运行正文或凭据正文 | 保护核心契约语义和数据所有权不被外部输入打穿 | 这是边界主线和数据主线的长期约束，不是认证授权实现。 |
| 审计与可追溯 | 契约范围、契约语义、发布基线、兼容性判断、废弃 / 退役、引用失效 | 高影响契约变化和关键状态必须保留正式依据或引用 | 保护契约演进、争议复盘和合规审查能力 | 这是契约底座的长期质量要求，不是普通日志字段。 |
| 可观测性 | 契约真相状态、快照刷新、校验 / 派生结果、事实传播、失败 / 挂起状态 | 必须能判断当前基线是否成立、快照是否可消费、失败是否已暴露 | 保护主线是否真实成立的可见性 | 这里不定义监控系统，只定义关键状态必须可见。 |
| 韧性 / 恢复能力 | 后台校验 / 派生、发布快照、事实传播、引用关系 | 失败时不得伪装成功；必须允许挂起、保留旧快照、标记失败或引用失效 | 保护失败后的正式恢复和边界一致性 | 该约束横切数据一致性和交互承接，不是重试脚本。 |
| 性能 / 容量约束 | 契约读取、追溯、校验、派生、变化感知 | 不得把耗时处理和下游全量确认压入同步入口，避免主链同步放大 | 保护共享契约底座在多仓消费下仍可成立 | 具体耗时阈值后移到测试方案和实施计划。 |
| 配置与变更控制 | 契约范围、兼容性策略、发布基线、快照派生、事实输出 | 关键配置和变更不能绕开正式承接，也不能隐式改变核心真相或边界 | 保护已收稳架构主线不被配置层绕开 | 这是变更控制边界，不是配置文件清单。 |

## 14. 演进路线

> 校准来源：
> - `design-calibration/01_arch_step_13_evolution_roadmap.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_13_evolution_roadmap.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解哪些债务当前可接受，哪些触发条件会推动后续演进。

当前阶段不是“所有工具链和发布体验全做完”才算成立，而是先让 `L0-core` 的架构边界和主线判断稳定。

| 阶段 | 当前目标 / 范围 | 当前可接受债务 | 后续演进项 | 触发条件 | 说明 |
|---|---|---|---|---|---|
| 当前主线成立阶段 | 稳定契约来源仓边界、数据归属、发布基线 / 快照、依赖方向和关键交互 | 具体字段、目录、生成器、CI 命令、发布渠道暂不锁死 | 在概要 / 详细设计中映射为具体结构、接口和实现契约 | 需要进入代码实现前 | 当前阶段目标是架构基线成立，不是完成所有工程实现。 |
| 结构落地阶段 | 将架构机制落到契约源码组织、接口轮廓、校验 / 派生流程和快照形态 | 自动化深度、可视化和跨仓消费投影可暂缓 | 补齐兼容性检查、快照导出、消费关系视图和实现约束 | 概要 / 详细设计开始承接代码实现时 | 该阶段解决“如何写代码”，但不得改变当前架构边界。 |
| 自动化增强阶段 | 强化校验、派生、兼容性报告、事实输出和失败挂起能力 | 仍可不做产品级发布平台和全下游强确认 | 增强自动检查、消费方提醒、失败恢复和派生一致性 | 手工审查或手工派生开始压垮协作效率时 | 自动化只能服务契约真相，不能反向定义契约真相。 |
| 跨仓治理联动阶段 | 将高影响变化、破坏性变化、引用失效和下游反馈纳入更强治理闭环 | 不要求 `L0-core` 承担治理系统本体 | 补强治理引用、追溯证据、消费影响分析和变更裁决联动 | 多仓 schema drift、兼容性争议或引用失效频繁出现时 | 演进方向是强化接缝和追溯，不是吸收相邻仓职责。 |

## 15. 风险与待确认事项

> 校准来源：
> - `design-calibration/01_arch_step_14_risks_open_questions.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_14_risks_open_questions.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解哪些问题是风险，哪些只是后续设计缺失确认。

本章中的风险都不阻塞当前架构文档收口，但会约束后续概要、详细、测试和实施阶段。

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|
| 旧版工具链中心口径回流 | 职责边界、关键技术选型、备选方案 | 当前所有章节均以契约来源仓为主语，工具链只作为支撑机制 | 不阻塞 | 该风险来自旧版文档惯性，后续概要 / 详细设计必须继续防止回流。 |
| 派生产物或快照被误当成契约真相 | 数据所有权、一致性策略、下游消费 | 当前明确发布基线是真相边界，快照和派生产物只是消费或投影 | 不阻塞 | 若后续实现反向使用生成物定义真相，将打穿本仓核心边界。 |
| 下游反馈绕过正式接缝直接影响核心 | 依赖方向、外部接缝、契约演进 | 当前规定下游反馈只能作为输入，经正式接缝和承接层审查 | 不阻塞 | 该风险会在跨仓协作增强时增大，需要后续设计继续约束。 |
| 后台失败被误表现为发布成功 | 关键交互、快照刷新、可观测性、韧性 | 当前要求失败必须挂起、保留旧快照或显式失败，不能伪装成新基线 | 不阻塞 | 该风险主要影响后续测试和实施验证。 |
| 正式 L0-core ADR 文件尚未落地 | ADR 索引、长期决策追溯 | 当前先在架构文档中索引候选决策，后续按 ADR 流程补正式文件 | 不阻塞 | 不影响本次架构主线收口，但影响长期决策材料完整度。 |

| 待确认事项 | 影响范围 | 缺失确认 | 当前挂起口径 | 说明 |
|---|---|---|---|---|
| 具体契约源码目录与字段策略 | 概要设计、详细设计、代码实现 | 缺少概要 / 详细设计层结构定义 | 当前不回填为架构定论，只保留“结构化契约源码承载真相”的架构机制 | 这是实现结构问题，不影响当前架构边界。 |
| 具体工具链 / 生成器配置 | 测试方案、实施计划、派生能力 | 缺少代码仓技术约束和实施决策 | 当前只保留“构建期校验 / 派生后台承接”机制，不指定工具参数 | 避免把工具名提前写成架构真相。 |

当前没有已评审通过的 L0-core 专项 ADR。本章先记录需要后续补档的关键决策候选，不替代正式 ADR 文件。ADR 补档是治理和追溯增强项，不阻塞当前 L0-core P0 开发启动。

| ADR 编号 | 架构决策 | 解决的问题 | 关联主线 | 说明 |
|---|---|---|---|---|
| 后续补档 | 将 `L0-core` 定义为跨仓共享契约来源仓，而非工具链仓、bus 实现或 sdk 中心 | 解决共享契约真相被相邻仓职责和工具链口径污染的问题 | 职责边界 / 系统上下文 / 备选方案 | 该决策是本仓所有后续设计的根决策，值得补正式 ADR。 |
| 后续补档 | 通过发布基线和只读发布快照隔离契约真相与下游消费 | 解决下游直接绑定核心真相或派生产物反向拥有真相的问题 | 数据所有权 / 一致性策略 / 关键技术选型 | 该决策长期影响消费边界和演进空间。 |
| 后续补档 | 通过正式接缝隔离外部输入与核心契约语义 | 解决标准、草案、评审结论和下游反馈直接打穿核心的问题 | 依赖方向 / 关键交互 / 横切关注点 | 该决策长期保护核心语义边界。 |
| 后续补档 | 通过后台延后承接处理契约校验、派生和快照刷新 | 解决同步入口被耗时处理压垮和伪同步完成的问题 | 容器承载 / 关键交互 / 技术机制 | 该决策长期影响失败挂起、旧快照保留和恢复方式。 |
| 后续补档 | 将契约事实变化作为可感知输出，而不让 `L0-core` 实现事件总线投递 | 解决下游需要感知变化但本仓不能承担 bus 职责的问题 | 关键交互 / 备选方案 / 横切关注点 | 该决策长期保护 `L0-core` 与 `L0-bus` 边界。 |
| 后续补档 | 通过外部正文引用而非吸收机制保护数据所有权 | 解决标准、ADR、业务、观测和运行正文被复制进本仓的问题 | 数据所有权 / 横切关注点 / 风险 | 该决策长期保护本仓只拥有契约真相和引用关系。 |

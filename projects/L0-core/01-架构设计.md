## 1. 业务背景与驱动力

### 1.1 业务背景

Quantalithos 是一个由 AI 员工 + 人类协作的软件工程系统。**六域平权**(身份 / 对话 / 工作 / 过程 / 治理 / 制品)+ 26 仓拆分(L0~L6)+ 事件驱动架构。

26 仓之间**不允许直接 RPC**(`product/六域模型.md` §2.2 规则 1),跨仓通信走**事件 + proto 契约**。这要求:

1. **所有跨仓契约集中管理**,避免各仓自造导致 drift
2. **事件必须有统一包络**(CloudEvents 1.0),让订阅方可解析
3. **Trace 必须贯穿**(W3C Trace Context),让 observability 能串起全链路
4. **错误码必须统一**,避免 26 仓各自定义错误类型

L0-core 仓承担这四项使命,是**所有仓的编译期依赖**。

### 1.2 业务驱动力

**业务驱动力**:
- 六域平权的技术承载 —— 没有 core 仓,六域各自为政,集成成本爆炸
- 企业合规(42001 审计 / 9001 文档控制)—— 跨仓事件必须可追溯、可审计,需统一包络

**技术驱动力**:
- 三语言 SDK 生成(Rust / Python / TypeScript)—— proto 是 SDK 生成源头
- Breaking change 防护 —— 一处定义、全量检测,防止下游仓误改契约
- buf / Connect RPC 生态 —— 成熟的 proto 工具链,避免自研

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 | 来源 |
|---|---|---|---|---|
| 覆盖度 | 六域 service proto 完整度 | 100%(6/6)| 对照 `domain/{domain}/README.md §三` | 00-需求 G-1 |
| 事件覆盖度 | event-catalog 事件有 proto schema | ≥ 90%(147 × 0.9 = 132)| 对照 event-catalog.md | 00-需求 G-2 |
| Breaking 防护 | CI 拦截率 | 100% | 故意 breaking PR 测试 | 00-需求 G-4 |
| SDK 生成成功率 | 三语言 binding 生成 | 100% | buf generate 无报错 | 00-需求 G-3 |
| 下游无痛依赖 | 3 个样本仓接入 | 100% | `cargo add` / `pip install` / `npm install` 成功 | 00-需求 G-6 |

## 2. 约束条件

### 2.1 不可变约束(架构决策必须遵守)

| 约束 | 来源 | 影响 |
|---|---|---|
| **CloudEvents 1.0 Spec** | 对齐 Research / observability 标准 | 事件包络格式固定 |
| **W3C Trace Context** | OTel 生态 | traceparent / tracestate 字段固定 |
| **六域平权**(`product/六域模型.md` §2.3)| 产品叙事 | service 命名不能暗示某域为主 |
| **禁止跨仓直接依赖** | 仓库拆分原则 | L0-core 不能 import 任何 L1+ |
| **proto3 语法** | 生态主流 | 不用 proto2 的 required / extensions |
| **buf 工具链** | 段 1 已决策 | 不用其他 proto 生成器 |
| **147 事件契约兼容**(event-catalog)| 段 2 产出 | 事件命名、severity、retention 不得变更 |

### 2.2 可变约束(可通过协商改变)

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| 目录组织 | `<domain>/v1/` | 可改为 `<domain>/<aggregate>/v1/`,破坏性需迁移 |
| proto 插件 | buf.build/protocolbuffers/python + tonic + protobuf-es | 可换,需同步测试 |
| Breaking 过渡期 | 2 个 minor 版本 | 可按组织合规调整到 3-6 个月 |
| Rust MSRV | 1.75+ | 可滚动升级 |
| Python 版本 | 3.11+ | 可滚动升级 |
| Node.js 版本 | 20 LTS+ | 可滚动升级 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| proto 文件数 | ~30 个(6 service + 共享 + 扩展)| 一个 service proto ≤ 1500 行,超过拆分 |
| 事件 type 数 | 200(现 147)| event-catalog 登记 147 + 30% 扩容余量 |
| CI 构建时间 | < 5 分钟 | buf lint + breaking + generate 三语言 |
| binding artifact 大小 | Rust < 2MB / Python < 1MB / TS < 500KB | 插件生成原生规模 |
| PR 单次改动 | < 1000 行 | 人工评审可覆盖的粒度 |

## 3. 架构风格与选型

### 3.1 变化维度识别

本仓预期在以下维度发生变化:

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 事件 type 新增 | 每月 5-10 个(段 3 后期)| event-catalog.md 维护清单 + proto 扩展 |
| service RPC 新增 | 每个 Sprint 若干 | 按 domain 分 proto 文件,独立扩展 |
| 字段增删 | 高频(non-breaking)| proto 字段号保留机制(19000-19999)|
| 破坏性变更 | 季度 | v1→v2 路径并行 + 过渡期 |
| 新增 domain(未来扩域)| 年度 | 新 domain/v1/ 目录,无需改 common/ |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **Schema-first with Protobuf**(当前选择)| SDK 自动生成、breaking 检测成熟、生态广 | proto 学习曲线 | ✅ **最匹配**三语言 + 跨仓契约场景 |
| Code-first | 开发快、无中间 proto | 三语言同步困难、breaking 难检测 | ❌ 三语言场景不可行 |
| OpenAPI + JSON Schema | REST 生态好 | gRPC 场景不原生、事件包络弱 | ❌ 事件总线场景不合 |
| GraphQL SDL | schema 内置 | 高频事件场景性能差 | ❌ 事件总线不适 |

**最终选择**:**Schema-first with Protocol Buffers v3 + CloudEvents 1.0 envelope**

**选择理由**(三维权衡):

1. **变化维度匹配**:proto 的字段号机制天然支持字段增删的 non-breaking 变更,且 buf 可静态检测 breaking
2. **跨语言强制一致**:三语言从同一 proto 生成,不存在"Rust 和 Python 语义漂移"的问题
3. **事件总线原生**:CloudEvents 1.0 是事件总线的事实标准,直接包装 proto message,无需自造

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| proto 集中在 core 仓 | 单一真相源、无 drift | 任何变更需走本仓 PR |
| CloudEvents 强制包络 | observability 统一订阅、审计完整 | 事件 payload 多一层嵌套 |
| W3C Trace Context 贯穿 | 跨域链路可追 | 每个事件多 4 个字段(traceparent / tracestate / baggage / span_id)|
| buf 工具链 | 开箱即用 lint / breaking / 生成 | 团队必须学 buf |

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 定义 6 个 L1 域的 service proto(RPC 契约)
- ✅ 定义 CloudEvents 1.0 包络
- ✅ 定义共享类型(ids / audit / timestamps / errors)
- ✅ 维护 proto 版本策略(semver + breaking 过渡)
- ✅ 生成三语言 binding 的 CI 脚本
- ✅ 事件命名约定文档(`<domain>.<aggregate>.<verb>`)
- ✅ 发布 proto package 到三语言生态(crates.io / PyPI / npm)

**不做什么**:
- ❌ 事件总线实现(在 `quantalithos-bus`)
- ❌ SDK 客户端逻辑(在 `quantalithos-sdk`)
- ❌ service 业务实现(在 L1 六域各自仓)
- ❌ 事件 schema 校验逻辑(在订阅方)
- ❌ 配置管理、日志实现(在各仓 infra 层)
- ❌ **业务语义**(本仓不理解 `identity.member.hired` 的含义)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA 要求 | 依赖风险 | 降级策略 |
|---|---|---|---|
| buf.build 工具 | 无(构建期)| buf CLI 不可下载 | 本地缓存 + 备选 protoc 工具链 |
| crates.io / PyPI / npm | 99.9% | 发版失败 | 本地回滚 + 重试 CI |
| CloudEvents 1.0 Spec | N/A(Spec 稳定)| Spec 后续演进到 1.1 | 版本锁定 + ADR 评审升级 |
| GitHub Actions | 99.9% | CI 宕 | 降级手动发版(紧急) |

### 4.4 关键依赖风险

**无运行时依赖**(L0 只在编译期被消费)。主要风险在发布管道:

- **三语言生态漂移**:Rust tonic vs Python grpcio vs TypeScript protobuf-es 对同一 proto 的实现差异 → 在 CI 中加 "round-trip" 测试(同一 proto,三语言 encode/decode 必须一致)
- **buf 工具链断代**:已有备选方案,见 §10 备选方案

## 5. 限界上下文与子域划分

### 5.1 子域分类

本仓作为**通用子域**(Generic Subdomain),定位是**"基础设施契约"**,不承载任何业务逻辑:

| 子域 | 分类 | 说明 |
|---|---|---|
| Proto Contract | 通用子域 | 跨仓 RPC 契约,无业务 |
| Event Envelope | 通用子域 | CloudEvents 包络,无业务 |
| Trace Context | 通用子域 | W3C 标准的落地,无业务 |
| Error Taxonomy | 通用子域 | 错误码分类,无业务 |

```

### 5.3 上下文映射关系

- **Common Types → 其他 6 个上下文**:单向依赖(common 定义,其他 import)

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| CloudEvent | CloudEvents 1.0 规范的事件包络 | 所有跨域事件 |
| Envelope | 事件外层包装(CloudEvent)与内层 payload(proto message)的区分 | proto-draft 与 bus 层 |
| Trace Context | W3C Trace Context(traceparent + tracestate)| observability |
| Service Binding | 从 proto 生成的三语言客户端 + 服务端骨架 | sdk 仓 |
| Breaking Change | 违反 buf breaking 规则的变更 | 版本策略 |
| Field Reservation | proto 字段号保留范围(19000-19999)| 防误用 |
| Package Semver | `major.minor.patch` 版本号 | 发版 |
| v1/v2 路径并行 | Breaking change 时新开 `<domain>/v2/` 过渡 | 破坏性迁移 |
| ActorContext | 所有写操作携带的审计上下文 | 合规留痕 |
| ErrorCode | 25 类跨仓统一错误分类 | 错误映射 |

### 6.2 容器职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |

| proto → 下游 service | 依赖版本包(crates / pip / npm) | git submodule | 版本化清晰、无需复制文件 |
| CI → Registry 发版 | 官方 registry CLI / action | 自写脚本 | 稳定、已有生态 |

### 6.4 数据存储归属(Single Writer)

| 数据 | 写入者 | 读取者 |
|---|---|---|
| `proto/**/*.proto` | core Maintainer / PR 提交者 | 全仓开发者 |
| `docs/*.md` | core Maintainer | 全仓开发者 |

| npm package artifact | release workflow | TS 消费仓 |

### 6.5 部署拓扑

L0-core **不部署到线上业务集群**。部署拓扑只有两处:

1. **源码托管**:GitHub 仓库
2. **CI 执行**:GitHub Actions / 自托管 runner

因此本仓没有 Kubernetes / Docker / Pod 拓扑图,这也是和 L1-L6 仓最大的区别。

│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 7.2 层间约束规则

- **规则 1**:`common/v1/*` 可以被所有 service proto import;各 service proto **不能互相 import**
- **规则 2**:L0-core **不 import** 任何 L1-L6 的实现代码或业务类型
- **规则 3**:新增 shared type 优先放 `common/v1/*`;若该类型带强业务语义,不放 common,而放对应 domain service proto
- **规则 4**:事件名以 `event-catalog.md` 为单一真相源,proto 中不得自造 event type 字符串
- **规则 5**:breaking change 只能通过 `<domain>/v2/` 新路径实现,不得在 v1 原地破坏
- **规则 6**:所有写操作 request message 必须包含 `common.v1.ActorContext`
- **规则 7**:所有 CloudEvent 必须能映射 `traceparent` / `tracestate`

### 7.3 依赖倒置的接口点

L0-core 本身**没有业务层/基础设施层之分**,但对下游呈现出两个倒置点:

| 接口点 | 定义位置 | 实现位置 |
|---|---|---|
| `IdentityService` 等 service | `proto/{domain}/v1/*.proto` | 各 L1 仓 service 实现 |
| CloudEvent builder / decoder binding | 生成代码 | 各语言 SDK / 下游调用方 |
| ErrorCode enum | `common/v1/errors.proto` | 下游语言的 error mapper |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 极高(25 仓依赖本仓) |
| 传出耦合 | 极低(只依赖外部标准和 buf) |
| 不稳定性 | 接近 0(极稳定,应被依赖而不依赖业务仓) |
| 抽象度 | 高(proto / enum / schema 全是抽象契约) |

**结论**:本仓是**全平台最稳定的锚点**之一,任何不稳定逻辑都不应进入本仓。

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者(写入方) | 消费者(读取方) | 一致性级别 | 风险 |
|---|---|---|---|---|
| proto 源文件 | core Maintainer / PR 提交者 | 全仓 | Git 版本一致 | breaking 漏放行 |
| generated binding | release workflow | 下游语言仓 | 版本一致 | registry 发版失败 |
| ErrorCode enum | core Maintainer | 全仓错误映射 | 版本一致 | 下游仓自造错误码 |
| event type catalog(外部输入)| 设计仓维护者 | core / bus / observability / 所有域 | 文档最终一致 | drift |

### 8.2 一致性层次

**Level 1 · 聚合内一致性**:本仓无聚合存储,不适用。

**Level 2 · 契约内一致性**:同一 proto 文件内部字段变更保持 schema 一致(通过 buf lint + compile 检查)

**Level 3 · 跨语言一致性**:Rust / Python / TS 对同一 proto 的 binding 生成结果需 round-trip 一致。通过 CI 验证,不靠运行时修复。

### 8.3 补偿机制设计

本仓无业务事务补偿。主要补偿场景是**发版失败**:

| 场景 | 补偿动作 |
|---|---|
| Rust crate 发版失败 | 不标 tag stable,删除 release draft,重试 |
| Python wheel 发版失败 | 回滚 GitHub Release / 重试 |
| npm package 发版失败 | `npm deprecate` / 重发 |

**关键**:版本发版脚本必须幂等,重复执行不会发布多份不同内容的同版本包。

## 9. 关键技术选型

### 9.1 Protocol Buffers v3

| 维度 | 内容 |
|---|---|
| 当前选择 | Protocol Buffers v3 |
| 备选方案 | OpenAPI / GraphQL SDL / 手写 JSON Schema |
| 选择理由 | 跨语言生成成熟 + breaking check 生态完善 + gRPC 原生支持 + 字段号保留机制 |
| 演进路径 | 若未来 UI-only 场景更适合 JSON Schema,在 sdk 层额外导出,但不替换 proto |
| 不可逆程度 | **高** |

### 9.2 CloudEvents 1.0

| 维度 | 内容 |
|---|---|
| 当前选择 | CloudEvents 1.0 envelope |
| 备选方案 | 自定义 envelope / raw MQ payload |
| 选择理由 | 事件总线标准化 + observability / archive / bus 的共同契约 |
| 演进路径 | CloudEvents 1.1 出现兼容升级时,以扩展字段或 v2 envelope 方式演进 |
| 不可逆程度 | **中高** |

### 9.3 W3C Trace Context

| 维度 | 内容 |
|---|---|
| 当前选择 | traceparent + tracestate + baggage |
| 备选方案 | 自造 trace_id / OpenTelemetry proprietary headers |
| 选择理由 | 行业标准 + observability 可无缝接入 |
| 演进路径 | 保留 `baggage` 为空的兼容路径 |
| 不可逆程度 | **中** |

### 9.4 buf 工具链

| 维度 | 内容 |
|---|---|
| 当前选择 | buf lint / buf breaking / buf generate |
| 备选方案 | protoc + 自写脚本 |
| 选择理由 | 开箱即用的 lint / breaking / 生成统一入口 |
| 演进路径 | 若 buf 商业化风险上升,保留 protoc 备选流水线 |
| 不可逆程度 | **中** |

### 9.5 三语言生成器

| 语言 | 当前选择 | 备选 | 理由 |
|---|---|---|---|
| Rust | tonic + prost | grpc-rs | 与 async / axum 生态配合最好 |
| Python | grpcio + protobuf | betterproto | 官方生态更稳 |
| TypeScript | protobuf-es | ts-proto / Connect | ESM 兼容,前端生态更顺 |

## 10. 备选方案与取舍

### 10.1 统一契约层方案对比

| 维度 | 方案 A:Proto + CloudEvents(当前)| 方案 B:OpenAPI + JSON Event | 方案 C:GraphQL SDL + 自造事件 |
|---|---|---|---|
| 跨语言生成 | 强 | 中 | 中 |
| 事件总线适配 | 强 | 弱(需另造 envelope)| 弱 |
| Breaking 检测 | 强(buf)| 中(openapi-diff)| 弱 |
| 学习成本 | 中 | 低 | 中 |
| 长期稳定性 | 高 | 中 | 中 |

### 10.2 最终选择与理由

**选方案 A**。核心权衡:
- 我们的问题不是"REST 文档生成",而是"26 仓事件 + RPC 的统一契约"
- 事件总线是平台主干,CloudEvents + proto 的组合理解成本低于"OpenAPI + 自造 event schema"
- buf 的 breaking check 是刚需,不只是加分项

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| proto-draft 与真正 core 仓尚未拆分 | 发布前需要迁移,影响 N0 节奏 | P0 |
| method-library / capability-hub 等 proto 尚未补齐 | N3 前必须解决 | P1 |
| 三语言 round-trip 一致性测试未落地 | 可能潜伏 binding 漂移 | P1 |
| BSR(Buf Schema Registry) 是否启用未决 | 发布策略不确定 | P2 |

### 12.2 演进触发条件(可量化)

| 指标 | 阈值 | 演进动作 |
|---|---|---|
| event type > 200 | proto/common/events 过重 | 拆 `events/{domain}/v1` 子包 |
| 某个 service proto > 1500 行 | 可维护性差 | 拆分 message proto |
| 三语言生成时间 > 5 分钟 | 开发体验恶化 | 插件并行化 / 缓存 |
| breaking PR 频率 > 每月 2 次 | 契约过于不稳定 | 引入更严格的 ADR + tag 流程 |

### 12.3 演进步骤(可停在任意位置)

```
阶段 1 · 现状(proto-draft 在 design 仓)
   └─ 用设计文档迭代,不写代码

阶段 2 · N0 启动(core 仓落地)
   └─ 迁移 architecture/proto-draft/ → quantalithos-core/proto/
   └─ 建立 buf lint / breaking / generate CI

阶段 3 · 生成三语言包
   └─ 发布 crates.io / PyPI / npm 0.x 版本

阶段 4 · BSR / 额外导出
   └─ 视需要启用 Buf Schema Registry 或 JSON Schema 导出
```

### 12.4 目标架构(方向,不是终点)

目标不是让 core 仓变重,而是让它成为**稳定、薄、可审计**的基础设施契约层:
- 薄:只放契约,不放业务实现
- 稳:breaking 有严格门禁,非破坏性演化顺畅
- 审计:所有契约变更有 ADR / PR / tag 可追溯

## 14. 上线策略

### 14.1 灰度方案

本仓无线上常驻服务,所谓"上线"是**发布新版本给下游仓消费**。灰度策略体现在**版本渐进**:

1. 先发 prerelease / rc tag(如 `v0.2.0-rc1`)
2. 选 3 个样本仓(identity / bus / sdk)接入验证
3. 样本仓 1 Sprint 内稳定后转正式 tag

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| release workflow 失败 | A | 删除 draft release,修 CI 后重发 |
| 下游样本仓 build 失败 | A | 回滚 tag + yank 包(若已发) |
| breaking 漏放行导致下游大量失败 | S | 立刻 yank 最新包 + 恢复上一稳定 tag |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| CI 总时长 > 5 分钟 | warning | GitHub Actions + Slack |
| 发布失败率 > 5% | critical | GitHub Actions + Pager |
| 下游 sample build fail | critical | 阻断正式 tag |

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L0-core` 不是某个业务仓的上位总真相仓,也不是一个“公共杂物箱”。它是 **“共享契约稳定器”**。

你可以把它理解成:
- 哪些跨仓共享的 ID / Ref / enum / DTO 已经足够稳定,可以被统一抽出来
- 哪些对象结构适合成为 bus 和 sdk 的共同基座
- 哪些错误族、返回语义和元信息应该全平台用同一套表达
- 哪些东西还不能抽到 core,必须继续留在业务仓里

这些事情,都由 `L0-core` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L0-core`,这些共享契约就会散落在:
- `L1-work` 自己定义一套 refs / ids / enums
- `L1-process` 再定义一套近似结构
- `L1-governance` / `L1-artifact` / `L2-runtime` / `L2-member-service` 各自复制近似 DTO
- bus / sdk / service 再各自包装一层相近对象

结果就会出现:
- 同一种业务引用在不同仓有多套近似定义
- 事件层和 SDK 层难以共享统一对象骨架
- 一改上游名字或边界,下游就各自漂移
- 看起来都叫 ref/status/error,其实不是同一语义
- 后续抽 bus/sdk 契约时只能靠人工拼接

所以 `L0-core` 必须独立存在,作为:
> **跨仓最小稳定对象、引用和基础契约的单一共享基座。**

### 1.3 新人最容易混淆的几个词

#### Core
就是:
> 一组已经在多个仓中稳定存在、且需要统一表达的共享基元。

它不是“所有重要对象都归 core”。

#### Ref
就是:
> 跨仓稳定引用同一个正式对象的共享结构。

它不等于任何业务仓自己的主语对象正文。

#### Shared DTO
就是:
> 多个仓都需要用同一种结构表达的最小对象骨架。

它不是某个业务仓的全量对象复制品。

#### Error family
就是:
> 多个仓可以共用的一组错误类别或返回语义族。

它不是某个仓私有失败模式的全集上收。

#### Envelope / metadata skeleton
就是:
> 事件、请求、响应等跨仓材料需要共享的最小元信息骨架。

它不是 bus 本体,也不是 sdk 本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L0-core/02` 时,先收稳以下前提:
- `L0-core` 不应按“公共文件夹”思路拆,而应按共享契约类型拆
- core 至少应拆成“基础标识与引用 / 共享对象骨架与最小 DTO / 共享枚举与状态族 / 共享错误与返回语义 / 共享元信息与追踪骨架”五个主要部分
- core 自己拥有的真相不是业务真相,而是 ID / Ref / enum / DTO / metadata skeleton 这一类共享契约真相
- `Project / WorkItem / ProcessInstance / Decision / ArtifactVersion / ExecutionInstance / MemberRuntimePersona / ToolDefinition` 等强业务主语,当前都不应直接进入 core 作为主语真相本体
- core 只能收已经在多个仓里稳定重复出现、语义已收稳的共性对象,不能提前拍板仍在变化的业务语义
- 02 的重点不是“把公共的都放进来”,而是先把“哪些东西现在适合进入 core、哪些不能”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的共享契约心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,随着 L1/L2 主链仓逐步收稳,跨仓共享对象已经越来越多。用户真正需要的不是“每个仓都自己定义一套差不多的 ref / id / dto”,而是:
- 同一类正式对象在多个仓里有一致的引用方式
- 相同的错误类别和返回语义有统一表达
- 事件层和 SDK 层可以引用同一套共享基元
- 业务仓只负责业务真相,而不再各自重复发明底层公共契约

如果把这些逻辑分别散落到:
- work / process / governance / artifact / runtime / member 等仓各自的 types
- bus 层自己的 envelope 定义
- sdk 层自己的二次包装对象

系统会快速退化成:
- 同一种 ref / id / status 在多个仓里定义不同版本
- 事件和 SDK 难以稳定共享对象骨架
- 下游只能通过“看起来差不多”的命名猜语义
- 抽取公共契约时容易过早冻结或反复返工

因此,本概要设计的任务就是:
> **把 `L0-core` 写成一个新人也能看懂的“共享契约稳定器”,而不是把所有公共代码堆在一起的总仓。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 共享 ID/Ref | 各仓已有近似重复定义趋势 | core 提供统一稳定引用基元 | 需正式收敛 |
| 共享 DTO | 各仓和 bus/sdk 有重复骨架风险 | 最小稳定 DTO 统一抽取 | 需明确边界 |
| 共享错误族 | 各仓容易自定义近似错误语义 | core 提供统一基础错误/返回族 | 需避免过度抽象 |
| 元信息骨架 | trace/source/actor 等元信息有重复 | core 统一最小 metadata skeleton | 需正式定义 |
| 抽取时机 | 过早抽象风险高 | 只抽已在 L1/L2 收稳的共性 | 需写死原则 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何在不破坏各业务仓真相归属的前提下,为全平台提供稳定共享的对象、引用、错误和元信息表达
- **技术问题**:哪些 ID/Ref/enum/DTO/metadata skeleton 已经足够稳定可进入 core,以及 core 如何作为 bus/sdk/service 的共享基座而不反向统治业务语义

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 core 的共享契约职责 | ID / Ref / enum / DTO / metadata skeleton 职责无歧义 | 文档评审 |
| 明确哪些对象可进入 core | 已稳定共性对象进入,业务主语不越界上收 | 文档评审 + 后续测试 |
| 明确 core 与 L1/L2、bus、sdk 边界 | core 提供共享基元,不替代业务真相、事件总线和 SDK 本体 | 文档评审 |
| 支撑后续 bus/sdk | core 足以承接后续 L0-bus / L0-sdk 抽象输入 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文定义完整 bus event schema(留给 `L0-bus`)
- 不在本文定义 SDK developer-facing API 细节(留给 `L0-sdk`)
- 不在本文接管任一业务仓的主语对象和状态机正文
- 不在本文提前冻结仍在快速变化的业务对象
- 不在本文讨论代码生成、序列化、兼容策略等低层实现细节

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                  ┌────────────────────────────┐
                  │ L1 / L2 domain projects     │
                  │ - work / process / runtime  │
                  │ - governance / artifact     │
                  │ - member / tools            │
                  └────────────┬───────────────┘
                               │ stable shared object shapes
                               ▼
┌────────────────────────────┐  ┌────────────────────────────┐  ┌────────────────────────────┐
│ L0-core                    │  │ L0-bus                     │  │ L0-sdk                     │
│ - IDs / Refs               │──▶│ - event envelopes          │──▶│ - developer-facing APIs    │
│ - shared enums             │  │ - transport contracts      │  │ - SDK object wrappers      │
│ - minimal DTOs             │  └────────────────────────────┘  └────────────────────────────┘
│ - error / return families  │
│ - metadata skeletons       │
└────────────────────────────┘
```

### 4.2 位置解释

- `L0-core` 自己负责“跨仓共享对象和最小契约真相”
- `L1/L2` 各业务仓负责自己的领域主语与状态机,core 只在它们收稳之后抽取共性
- `L0-bus` 在 core 提供的共享基元之上形成事件 envelope 和 transport 契约
- `L0-sdk` 在 core 提供的共享基元之上形成开发者接口对象
- `L0-core` 的角色不是统治业务语义,而是稳定跨仓共性表达

所以 `L0-core` 在全局里的角色是:
> **在业务主语已初步收稳之后,把跨仓共享 ID、Ref、枚举、最小 DTO 和元信息骨架统一抽取为共享基座。**

### 4.3 系统边界

**做什么**:
- 定义共享 ID / Ref / relation ref / subject ref
- 定义共享 enum / status family / error family
- 定义最小稳定 DTO / envelope metadata skeleton
- 作为 L0-bus 与 L0-sdk 的共享对象基座

**不做什么**:
- 不持有 Project / WorkItem / ProcessInstance / Decision / ArtifactVersion / ExecutionInstance / MemberRuntimePersona / ToolDefinition 等业务主语真相
- 不定义完整 bus transport 契约
- 不定义 SDK 开发者体验层细节
- 不替代业务仓对领域边界的判断

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| L1/L2 各仓稳定对象输入 | 99.9% | 若上层对象仍在快速变化,则继续暂留业务仓,不强行上收 core |
| L0-bus | 99.9% | bus 延迟不影响 core 对共享基元的正式定义 |
| L0-sdk | 99.9% | sdk 延迟不影响 core 抽取共享对象 |
| 文档与契约评审流 | 99.9% | 评审未过时,宁可延迟抽取,不提前冻结未稳对象 |

### 4.5 关键依赖风险

- core / 业务仓边界不稳会导致强语义业务对象被过早上收
- core / bus 边界不稳会导致 event schema 细节污染共享对象层
- core / sdk 边界不稳会导致 developer-facing 便利对象反向污染最小契约层
- 抽取过早会冻结仍在变化的业务语义,后续返工成本极高
- 抽取过晚会让多仓复制近似结构越来越多,加重后续对齐成本

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **共享职责 + 跨仓稳定性 + 引用密度 + 对 bus/sdk 的支撑作用** 来拆分。  
> 因此下面每一部分都可能包含多个基础对象,共同支撑同一段共享契约链。

#### 基础标识与引用部分

- **它是什么**: 这是 `L0-core` 的最小共享锚点层,一起回答“跨仓怎样稳定指向同一个正式对象”
- **为什么单独有它**: 如果没有统一 ID / Ref,各仓就会各自定义近似结构,后续 bus/sdk 难以统一
- **负责什么**:
  - 定义共享 ID
  - 定义 Ref / subject ref / relation ref
  - 为下游提供稳定跨仓引用骨架
- **不负责什么 / 容易混淆点**:
  - 不负责任何业务主语正文
  - 不负责状态机真相
  - 最容易和业务仓自己的主语对象混淆
- **与其他部分交互**:
  - 上游: 各业务仓已收稳对象
  - 下游: DTO / enum / error / metadata / bus / sdk
  - 交互类型: 最小共享锚点型
- **后续详细设计展开点**:
  - ID / Ref / subject relation skeleton

#### 共享对象骨架与最小 DTO 部分

- **它是什么**: 这是 core 的对象骨架层,一起回答“哪些对象结构已经足够稳定可以共享”
- **为什么单独有它**: 如果不单列,shared DTO 很容易被某个业务仓全量对象拖进来
- **负责什么**:
  - 定义最小共享 DTO
  - 定义 lightweight object skeleton
  - 为 bus/sdk/service 复用提供最小结构
- **不负责什么 / 容易混淆点**:
  - 不负责全量业务对象
  - 不负责复杂业务规则
  - 最容易和业务仓自己的 rich model 混淆
- **与其他部分交互**:
  - 上游: ID/Ref 层
  - 下游: enum / error / metadata / bus / sdk
  - 交互类型: 共享骨架型
- **后续详细设计展开点**:
  - minimal DTO / shared object skeleton

#### 共享枚举与状态族部分

- **它是什么**: 这是 core 的共享语义分类层,一起回答“哪些类别和状态族已经不再是单仓私有语义”
- **为什么单独有它**: 如果不单列,各仓会继续复制近似 enum / status families
- **负责什么**:
  - 定义共享 enum
  - 定义 common status family
  - 提供一致的基础状态表达
- **不负责什么 / 容易混淆点**:
  - 不定义复杂业务状态机
  - 不决定仓内专属语义
  - 最容易和业务仓 state machine 混淆
- **与其他部分交互**:
  - 上游: shared object skeleton
  - 下游: error/return / metadata / bus / sdk
  - 交互类型: 共享分类语义型
- **后续详细设计展开点**:
  - enum family / shared result-status family

#### 共享错误与返回语义部分

- **它是什么**: 这是 core 的失败与返回语言层,一起回答“跨仓怎样统一表达失败和返回结果”
- **为什么单独有它**: 如果不单列,各仓会各自发明一套近似 error/return family
- **负责什么**:
  - 定义 error family
  - 定义 retryable / blocked / denied / fatal 等返回语义骨架
  - 让 bus/sdk/service 看到一致错误语言
- **不负责什么 / 容易混淆点**:
  - 不吸收每个仓的全部失败模式
  - 不决定仓内异常处理流程
  - 最容易和业务仓专属错误码混淆
- **与其他部分交互**:
  - 上游: enum/status family
  - 下游: bus / sdk / service outputs
  - 交互类型: 共享错误语义型
- **后续详细设计展开点**:
  - error code family / result category skeleton

#### 共享元信息与追踪骨架部分

- **它是什么**: 这是 core 的元信息层,一起回答“跨仓请求/响应/事件怎样共享最小 trace 和 actor metadata”
- **为什么单独有它**: 如果不单列,bus/sdk/service 会各自定义 trace/source/actor metadata
- **负责什么**:
  - 定义 trace metadata skeleton
  - 定义 request/response metadata skeleton
  - 定义 actor/caller/source 的最小共享字段
- **不负责什么 / 容易混淆点**:
  - 不定义 bus transport 本体
  - 不定义 sdk 便利包装层
  - 最容易和 bus envelope / sdk request wrapper 混淆
- **与其他部分交互**:
  - 上游: shared DTO / enum / error family
  - 下游: bus / sdk / service
  - 交互类型: 共享元信息基座型
- **后续详细设计展开点**:
  - metadata skeleton / trace/actor/request base

### 5.4 需求概要

#### 5.4.1 用户故事速览

| ID | 故事 | 优先级 |
|---|---|---|
| US-001 | 作为多个业务仓开发者,我想引用统一的 ID/Ref/DTO,以便不再各自复制近似结构 | P0 |

## 6. 本仓如何与其他模块交互

### 6.1 总交互图

```text
                  ┌────────────────────────────┐
                  │ L1 / L2 domain projects     │
                  │ - work / process / runtime  │
                  │ - governance / artifact     │
                  │ - member / tools            │
                  └────────────┬───────────────┘
                               │ stable shared object shapes
                               ▼
┌────────────────────────────┐  ┌────────────────────────────┐  ┌────────────────────────────┐
│ L0-core                    │  │ L0-bus                     │  │ L0-sdk                     │
│ - IDs / Refs               │──▶│ - event envelopes          │──▶│ - developer-facing APIs    │
│ - shared enums             │  │ - transport contracts      │  │ - SDK object wrappers      │
│ - minimal DTOs             │  └────────────────────────────┘  └────────────────────────────┘
│ - error / return families  │
│ - metadata skeletons       │
└────────────────────────────┘
```

### 6.2 总解释

- `L0-core` 自己负责“跨仓共享对象和最小契约真相”
- `L1/L2` 各业务仓的交互主要落在 **基础标识与引用部分**、**共享对象骨架与最小 DTO 部分** 与 **共享枚举与状态族部分**,把已收稳共性输入 core
- `L0-bus` 的交互主要落在 **共享元信息与追踪骨架部分**,以 core 提供的共享对象和 metadata skeleton 组织事件 envelope
- `L0-sdk` 的交互主要落在 **共享对象骨架与最小 DTO 部分** 与 **共享错误与返回语义部分**,以 core 提供的共享基元构造开发接口
- `L0-core` 不替代任何业务仓真相,也不接管 bus 或 sdk 本体

**读图方法**:
- 上游的 L1/L2 仓提供已经收稳的共享对象形状和引用需求
- 中间的 core 只抽最小稳定共性,不吸收业务主语正文
- 右侧的 bus 与 sdk 在 core 的基元之上继续组织事件和开发接口
- core 是共享基座,不是新的业务中心

### 6.3 分模块交互说明(逐个写)

#### 与 `L1/L2` 业务仓的交互

```text
┌────────────────────────────┐

             │ stable shared inputs

└────────────────────────────┘
```

- **交互类型**: 稳定对象输入型交互
- **主流程位置**: 多仓已经稳定重复使用同一类 ID/Ref/enum/DTO 时进入主流程
- **交互解释**:
  - 业务仓先定义和收稳自己的主语边界
  - core 只抽那些已经稳定出现的共享对象
  - core 不反向替业务仓定义主语真相
- **高风险异常流**:
  - 强语义业务对象被过早上收 core
- 后续 `03-详细设计.md` 继续展开:

- **交互解释**:
  - core 提供统一 ID/Ref/metadata skeleton
  - bus 在其之上组织 event envelope
  - core 不直接定义完整事件传输契约
- **高风险异常流**:
  - bus transport 细节反向污染 core 对象层

  - core 提供最小稳定对象骨架、错误族和元信息骨架

  - SDK 便利对象反向污染 core 最小契约层

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 共享标识层 + 共享 DTO 层 + 共享枚举状态层 + 共享错误语义层 + 共享元信息骨架层分层

**选择理由**:
- 把 ID/Ref 与 richer DTO 分开
- 把 enum/status family 与错误/返回语义分开
- 把 metadata skeleton 与 bus/sdk 封装层分开
- 避免 core 退化成“所有公共业务对象都往里塞”的大仓
- 为 `L0-bus` 和 `L0-sdk` 提供稳定基础

### 7.2 模块划分与职责

│             ▼                                │
│  ┌────────────────────┐                      │
│  │ minimal DTOs       │                      │
│  │ shared object base │                      │
│  └──────────┬─────────┘                      │
│             ▼                                │
│  ┌────────────────────┐                      │
│  │ enums / statuses   │                      │
│  │ shared families    │                      │
│  └──────────┬─────────┘                      │
│             ▼                                │
│  ┌────────────────────┐                      │

```text

shared object/error ──▶ metadata skeletons

```

### 7.4 层间约束规则(防退化)

- IDs / Refs 只定义共享引用,不定义业务主语正文
- shared DTO 只能保持最小骨架,不得吸收复杂业务语义
- shared enums / statuses 只收已跨仓稳定复用的语义族
- errors / returns 只定义共享骨架,不吞并所有仓内失败模式
- metadata skeletons 只做最小通用元信息,不直接变成 bus/sdk 本体

## 8. 关键技术选型

### 8.1 为什么 core 只在业务边界初步收稳后再抽共享对象

| 维度 | 内容 |
|---|---|
| 当前选择 | 先由 L1/L2 仓收稳对象语义,再抽核心共性进入 core |
| 备选方案 | 在业务仓未稳定前就预先上收公共对象 |
| 选择理由 | 避免过早冻结业务语义,减少返工 |
| 演进路径 | 后续随着更多对象收稳,可逐步补 core,但不提前上收未稳对象 |

### 8.2 为什么 IDs/Refs 与 richer DTO 分层

| 维度 | 内容 |
|---|---|
| 当前选择 | 先统一最小标识和引用,再统一最小 DTO |
| 备选方案 | 一开始就把大对象整体抽进 core |
| 选择理由 | 防止 core 变成业务对象全集仓 |
| 演进路径 | 后续只在确有必要时增加 richer DTO,但仍保持最小原则 |

### 8.3 为什么错误族与返回语义要独立于单仓错误码

| 维度 | 内容 |
|---|---|
| 当前选择 | core 只定义共享 error/return skeleton,不吞并仓内全部错误模式 |
| 备选方案 | 把每个业务仓错误码直接整体上收 |
| 选择理由 | 保持 core 足够薄,避免业务细节反向冻结到共享层 |
| 演进路径 | 后续可扩展共享类别,但仍保持业务特有失败留在业务仓 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: L0-core 作为共享契约稳定器(当前) | 方案 B: 各仓继续各自定义近似公共对象 |
|---|---|---|
| 共享对象一致性 | 高 | 低 |
| bus/sdk 承接成本 | 低 | 高 |
| 业务边界清晰度 | 高 | 中低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 已经进入多仓协作阶段,若继续让各仓各自定义近似 ID/Ref/DTO/error/metadata,后续 L0-bus 和 L0-sdk 只能在一堆相近但不完全一致的对象上做重复包装,成本和漂移都会持续放大。L0-core 的价值不在于抽更多业务对象,而在于用最薄的共享契约减少这种结构性漂移。

## 11. 横切关注点

### 11.1 安全
- 核心共享对象不得越界吸收业务主语真相
- 错误/返回/metadata skeleton 不得被单仓私有扩展反向覆盖

### 11.2 性能
- core 注册/查询共享对象不应成为业务仓主链阻塞点
- bus/sdk 对共享对象的读取应稳定且低成本

### 11.3 可用性
- bus / sdk 延迟不影响 core 本身对共享契约的正式定义
- 上游业务仓局部变化时,core 允许延迟上收,不强求同步冻结

### 11.4 可观测性
- 从业务仓到 core 的共享对象抽取关系应可追踪
- core 中 shared primitive 的变更应可审计

### 11.5 成本
- 不把业务细节提前抽进 core,避免后续大规模返工
- 不让每个仓继续重复定义近似公共对象,降低后续 bus/sdk 包装成本

### 11.6 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| shared primitive register/check | ≤ 100ms | 100ms |
| bus/sdk consume lookup | ≤ 50ms | 150ms |
| metadata skeleton read | ≤ 50ms | 200ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 过早上收业务对象 | 中 | 高 | 在详细设计中继续固定上收准入规则 |
| 各仓继续复制近似 ref/dto | 中 | 高 | 统一 shared primitive 注册与替换路径 |
| bus/sdk 便利层反向污染 core | 中 | 高 | 核心对象与 wrapper/transport 分层 |
| error family 被业务仓细节膨胀 | 中 | 高 | 只保留共享骨架 |

### 12.2 边缘风险

- 某些对象是否真的稳定,可能在 L0-bus / L0-sdk 推进时再次暴露边界争议
- 不同语言 SDK 对 shared DTO 的映射方式差异,可能反向要求 core 精细化
- 共享 metadata skeleton 可能随着 trace/actor/source 需求扩展而细化

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 哪些 enum/status family 现在已经足够稳定可以进入 core | 03 阶段 | core + 各域 TL |
| shared DTO 的“最小骨架”边界如何定义,避免 rich model 上收 | 03 阶段 | core |
| core 到 bus/sdk 的映射是引用同对象,还是允许各自外层 wrapper | 03 阶段 | core + bus + sdk |

## 13. 上线策略

### 13.1 灰度方案
- 先从最稳定的 ID / Ref / metadata skeleton 开始
- 再抽最小共享 DTO 与共享错误/返回骨架
- 最后再让 L0-bus / L0-sdk 正式消费这些 core primitives

### 13.2 回滚策略
- 若某对象上收过早,先回退到业务仓自有定义并保留 core 侧空位或占位说明
- 若 shared enum/error family 语义不稳,先收缩为更薄骨架,避免冻结细节
- 若 bus/sdk consume 层和 core 绑定过紧,先保持 wrapper 层独立,暂停进一步上收

### 13.3 监控指标
- shared primitive 注册成功率
- 共享对象替换重复定义成功率
- bus/sdk consume core primitive 成功率
- core object drift 报警次数

## 15. 结论

本概要设计的核心结论是:
- `L0-core` 是跨仓共享 ID、Ref、枚举、最小 DTO 和元信息骨架的共享契约稳定器,不是业务上位总真相仓
- `L0-core` 内部应按“基础标识与引用 / 共享对象骨架与最小 DTO / 共享枚举与状态族 / 共享错误与返回语义 / 共享元信息与追踪骨架”来理解,而不是按 util/公共代码平铺理解
- L1/L2 业务仓先收稳对象边界,core 再抽共享基元; bus 和 sdk 在其上构造 transport / developer-facing 契约
- shared DTO 不等于 rich business model, error family 不等于单仓错误全集, metadata skeleton 不等于 bus transport 本体
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把 shared ref/dto/enum/error/metadata 的准入规则、对象骨架与 bus/sdk 接缝正式化

## 1. 模块职责描述

**本模块做什么**:
- 持有正式共享 ID / Ref / relation skeleton / minimal DTO / shared enum/status / error/return family / metadata skeleton 真相
- 定义哪些共享 primitive 可以进入 core,以及何时不应进入 core
- 为 L0-bus / L0-sdk 提供稳定共享对象基座
- 把跨仓共享 primitive 的抽取、留痕、对账和替换路径正式化

**本模块不做什么**:
- 不持有任何业务仓主语对象和状态机正文真相
- 不承担 bus transport 契约本体或 sdk developer-facing wrapper 本体
- 不提前冻结仍在快速变化的业务语义

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 core“为什么存在”,而是让开发者可以直接开始实现:
- stable object 如何被判定为可进入 core
- ID / Ref / relation skeleton 如何正式建模
- minimal DTO / enum / error family / metadata skeleton 如何保持薄而稳定
- bus 和 sdk 如何消费这些 primitive 而不反向污染 core
- admission / replay / audit 如何正式留痕

如果不先把这些内容采集清楚,03 很容易退化成:
- 公共 util 仓说明书
- 一堆泛泛 DTO / error 类名清单
- 对 bus/sdk 的过早抽象替代
- rich business model 提前上收的总模型仓草稿

### 2.2 内容采集流程(先采集,再落文)

#### 第 0 步:确认 `02-概要设计` 已经稳定

先确认:
- `L0-core` 是共享契约稳定器,不是业务上位总真相仓
- 五个主要部分已经稳定
- 与 `L1/L2`、`L0-bus`、`L0-sdk` 的真相边界已经清楚
- `02` 中总交互图与分模块交互图已经能回答“谁给谁什么共享 primitive 语义”

#### 第 1 步:列出要实现的核心对象

本仓 03 先按四层对象理解:
- 标识与引用对象: CoreId / EntityRef / SubjectRef / RelationRef
- 共享骨架对象: CoreDto / BaseCommand / BaseQuery / BaseResponse / SharedObjectSkeleton

#### 第 2 步:列出主流程与关键异常流

主流程至少有三条:
- 共享对象抽取主线
- 跨仓引用统一主线
- bus/sdk 承接主线

关键异常流至少包括:
- 对象尚未收稳却试图上收 core
- shared DTO 其实仍含复杂业务语义
- shared enum 实际只在一仓内部成立

- core primitive 进入后发现仍在快速变化

#### 第 3 步:列出要落库/持久化的对象与关系

必须先分清:
- 哪些是写模型: shared_id_registry / shared_ref_registry / shared_dto_registry / shared_enum_registry / shared_error_registry / shared_metadata_registry
- 哪些是只读视图: primitive_catalog_view / bus_consume_base_view / sdk_consume_base_view / admission_audit_view
- 哪些是 append-only: registry history / admission history / replay audit history
- 哪些输入只作为来源引用,不能反向变成 core 主对象真相

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 L1/L2 稳定对象
- 哪些输出给 bus / sdk / service consumers
- 哪些 primitive 进入 core 后需要替换掉上层重复定义
- 哪些对象虽然看起来公共,但仍不能进入 core

#### 第 5 步:列出最小测试输入

必须测:
- 只有稳定共性才允许进入 core
- rich business model 禁止上收
- shared Ref / DTO / enum / error / metadata 的边界清晰
- bus/sdk 只能消费 core primitive,不能反向污染 core
- registry / replay / audit 一致性成立

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `ID / Ref / DTO / Enum / Error / Metadata` 这些名字平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、准入约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 shared primitive / DTO / enum / error / metadata,`03` 却变成一组没有准入边界的公共类型表
- 实现者知道有 shared DTO,却不知道它什么时候可以被正式上收到 core
- bus / sdk / domain consume 三条链路脱节

### 5.2 `基础标识与引用部分` 的实现要点

#### 5.2.1 该部分承接的概要输入
- 承接 `02` 中“基础标识与引用部分”的职责
- 承接 stable object → shared ref extraction 主线
- 承接 `Ref ≠ 主语正文` 这条硬边界

#### 5.2.2 输入 / 输出 / 外部交互图

┌────────────────────────────┐
│ L1/L2 stable object input  │
│ - stable IDs / refs        │
└────────────┬───────────────┘

             ▼
┌────────────────────────────┐
│ L0-core                    │
│ - CoreId                   │
│ - EntityRef                │
│ - SubjectRef               │
│ - RelationRef              │
└────────────┬───────────────┘
             │ shared primitive output
             ▼
┌────────────────────────────┐

#### 5.2.3 涉及的对象定义

```rust
/// 表示跨仓共享的最小标识骨架。
pub struct CoreId {
    /// 全局唯一值。
    pub value: String,
}

/// 表示跨仓稳定引用同一个正式对象的最小骨架。
pub struct EntityRef {
    /// 对象类别。
    pub kind: String,
    /// 对象主键。
    pub id: CoreId,
}

/// 表示作为关系起点/终点的共享主语引用。
pub struct SubjectRef {
    /// 主语自己的稳定引用。
    pub entity_ref: EntityRef,
}

/// 表示跨仓关系引用骨架。
pub struct RelationRef {
    /// 起始主语。
    pub from: SubjectRef,
    /// 目标主语。
    pub to: SubjectRef,
    /// 关系类别。
    pub relation_kind: String,
}

/// 表示一条正式登记进 core 的共享 primitive 记录。
pub struct PrimitiveRegistryEntry {
    /// primitive 自身标识。
    pub primitive_id: PrimitiveId,
    /// primitive 类型。
    pub primitive_kind: PrimitiveKind,
    /// 来源域引用。
    pub source_domain_ref: String,
}
```

这些对象在该部分里分别承担:
- `CoreId` 负责统一最小标识语义
- `EntityRef` 负责统一跨仓最小对象引用
- `SubjectRef` 负责统一关系中的主语表达
- `RelationRef` 负责统一跨仓关系骨架
- `PrimitiveRegistryEntry` 负责把 admitted primitive 正式登记进 core registry
- 它们都不替代任何业务仓自己的主语正文对象

#### 5.2.4 关键函数代码片段

```rust
/// 把已收稳的业务仓引用骨架注册为共享 Ref。
fn register_shared_ref(
    registry_repo: &dyn SharedPrimitiveRepo,
    draft: RegisterSharedRefDraft,
) {
    // [EntityRef::从草稿创建]
    // 先把业务仓给出的稳定引用草稿收束为正式共享 Ref 对象。
    let entity_ref = EntityRef::from_draft(draft);

    // [entity_ref.校验引用合法性]
    // 再校验 kind / id / relation 最小语义是否稳定成立。
    entity_ref.validate_stable_shape();

    // [registry_repo.保存共享引用]
    // 最后把共享 Ref 正式写入 core registry。
    registry_repo.save_ref(entity_ref);
}
```

这段实现守住的边界是:
- 只有 stable shape 才能进入 core
- Ref 只表达引用骨架,不表达业务正文
- 上层仓是来源真相,core 只是共享稳定器

#### 5.2.5 该部分的边界与非职责
- 不负责 rich business DTO
- 不负责业务状态机真相
- 不负责 bus envelope 细节
- 不负责 sdk wrapper 细节

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `共享对象骨架与最小 DTO 部分` 提供 ref/ID 基元
- 向 `共享元信息与追踪骨架部分` 提供 subject/entity 基元
- 给 bus/sdk/domain 提供统一引用骨架

#### 5.2.7 该部分的状态 / 约束 / 易错点
- shared Ref 必须稳定,不能只是“多个仓现在碰巧长得像”
- relation_kind 一旦进入 core,修改影响半径大,必须谨慎准入
- rich domain object 字段不得借 Ref 名义偷进 core

#### 5.3.4 关键函数代码片段

```rust
/// 把已收稳的最小对象结构注册为共享 DTO。
fn register_shared_dto(
    registry_repo: &dyn SharedPrimitiveRepo,
    draft: RegisterSharedDtoDraft,
) {
    // [CoreDto::从草稿创建]
    // 先把候选对象的最小字段结构收束成共享 DTO 骨架。
    let dto = CoreDto::from_draft(draft);

    // [dto.校验最小字段完备性]
    // 再确认这组字段足够表达共性,但没有越界吸收 rich model 语义。
    dto.validate_minimal_shape();

    // [registry_repo.保存共享 DTO]
    // 最后把共享 DTO 正式写入 core registry。
    registry_repo.save_dto(dto);
}
```

这段实现守住的边界是:
- 共享 DTO 只收最小稳定字段
- 一旦需要 rich context 才能解释的字段,就不应进入 core
- core 的 DTO 服务于 bus/sdk/domain 共享,而不是替代业务仓 rich model

#### 5.3.5 该部分的边界与非职责
- 不负责业务规则
- 不负责 shared enum / error family
- 不负责 bus envelope 正文
- 不负责 sdk developer convenience wrapper

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `基础标识与引用部分` 获取 shared refs
- 向 `共享错误与返回语义部分` 提供 response skeleton 语义
- 给 bus/sdk/service 提供最小交互骨架

#### 5.3.7 该部分的状态 / 约束 / 易错点
- DTO 一旦进入 core,不应继续快速加厚
- BaseCommand / BaseQuery 不能偷偷吸业务层动作语义
- 最小共享骨架必须能被多个仓稳定复用,而不是仅在两个仓临时共形

### 5.4 `共享枚举与状态族部分` 的实现要点

| 命令 | 权限校验 | 审批校验 | 责任链校验 | 不通过时处理 |
|---|---|---|---|---|
| RegisterSharedRef | source proposal 合法 | 无 | ref/subject/relation shape 合法 | 拒绝上收 |
| RegisterSharedDto | dto proposal 合法 | 无 | minimal shape 合法 | 拒绝上收 |
| RegisterSharedEnum | enum/status proposal 合法 | 无 | 跨仓稳定性成立 | 拒绝上收 |
| RegisterSharedErrorFamily | error/return proposal 合法 | 无 | 未超出共享边界 | 拒绝上收 |
| RegisterMetadataSkeleton | metadata proposal 合法 | 无 | 最小字段成立 | 拒绝上收 |

### 7.6 关键状态机 / 非法转换与约束

#### 状态机图

```text
shared primitive admission:
proposed → admitted
proposed → rejected
admitted → revised (如后续允许受控调整)
rejected → revised_required
```

#### 非法转换与约束表

| 场景 | 是否允许 | 说明 |
|---|---|---|
| rich business model 直接进入 core | ❌ | core 只收最小稳定骨架 |
| 单仓私有状态机直接上收 shared status family | ❌ | 必须先跨仓稳定复用 |
| sdk wrapper 直接替代 core metadata skeleton | ❌ | wrapper 不能倒灌 core |
| bus envelope 细节直接进入 core DTO | ❌ | transport 层不得污染 core |
| 未收稳对象直接 admitted | ❌ | 必须经过 admission check |
| rejected primitive 继续被 bus/sdk consume | ❌ | 未 admitted 的对象不得对外提供共享基座 |
| admitted primitive 直接被 rich 字段热扩张 | ❌ | 后续修改必须重新走 revised/admission 流 |

#### 关键约束说明

- `proposed → admitted` 的前提是“跨仓稳定复用 + 最小骨架成立 + 未越界吸收业务语义”同时成立
- `rejected → revised_required` 只是说明可以重提更薄版本,不意味着旧提案被自动修复
- `admitted → revised` 必须保留完整 admission history,避免 bus/sdk consume 漂移后无法对账

### 7.7 事件发布点与跨仓协作清单

| 动作 | 事件/调用 | 消费方 | 一致性语义 |
|---|---|---|---|
| shared primitive admitted | `core.primitive.registered` | domain / bus / sdk | 强一致真相 |
| shared primitive rejected | `core.primitive.rejected` | authors / audit | 强一致留痕 |
| shared primitive revised | `core.primitive.revised` | bus / sdk / audit | 强一致真相 + 最终一致视图 |
| metadata skeleton updated | `core.metadata.updated` | bus / sdk | 强一致真相 + 最终一致视图 |
| primitive catalog rebuilt | catalog/base rebuild material | bus / sdk / operators | 最终一致 |
| registry replay completed | `core.registry.replayed` | audit / operators | 最终一致 |


### 7.8 消息格式(MQ Topic / Event Schema)

对齐 core/bus/sdk consume 契约:

| 事件 | severity | 幂等 key | 字段 schema |
|---|---|---|---|
| `core.primitive.registered` | info | primitive_id | 参考 core registry contract |
| `core.primitive.rejected` | info | proposal_id | 参考 admission reject contract |

### 7.9 错误码定义

| 错误码 | 含义 | HTTP / RPC 映射 | 恢复策略 |
|---|---|---|---|
| `CORE_PRIMITIVE_INVALID` | primitive proposal 非法 | 400 | 修正输入 |
| `CORE_PRIMITIVE_ALREADY_REGISTERED` | primitive 已存在 | 409 | 去重 / 查询既有 registry |
| `CORE_ADMISSION_DENIED` | 对象不允许进入 core | 409 | 保留在业务仓 |
| `CORE_PRIMITIVE_NOT_STABLE_ENOUGH` | 对象尚未跨仓稳定 | 409 | 延后上收 |

### 7.10 返回值语义分类

| 类别 | 语义 | 处理建议 |

| 不可恢复异常 | admission denied / unstable primitive / consume drift unresolved | 保留在业务仓或暂停消费 |

## 11. 运行期主线场景

### 11.1 场景 A · shared Ref 抽取并被多仓消费

```text
多个业务仓稳定使用同一类引用
      │
      ▼
core admission check
      │
      ▼
register shared ref
      │
      ├─ work/process/runtime 改为消费同一 Ref
      └─ 后续 bus/sdk 基于该 Ref 继续封装
```

**开发者关注点**:
- Ref 只是共享锚点,不是业务正文
- admission 必须看稳定性,不是看“像不像”
- 一旦 admitted,后续变更半径变大

### 11.2 场景 B · bus 基于 core metadata skeleton 组织 envelope

```text
core metadata skeleton ready
      │
      ▼
bus consume metadata base
      │
      ▼
构造 event envelope
      │
      ▼
transport 层继续扩展,但不反向污染 core
```

**开发者关注点**:
- metadata skeleton 只做最小共享字段
- envelope 细节留在 bus
- wrapper/transport 便利字段不能倒灌 core

### 11.3 场景 C · sdk 基于 core DTO / error family 构造接口

```text
core dto / error family ready
      │
      ▼
sdk consume shared primitives
      │
      ▼
构造 developer-facing wrapper
      │
      ▼
wrapper 仅增强开发体验,不替代 core 真相
```

**开发者关注点**:
- shared DTO 不是 rich business model
- error family 只提供共享骨架
- sdk wrapper 不能把便利字段写回 core

### 11.4 场景 D · bus/sdk consume 漂移后的重建

```text
shared primitive registry 已稳定
      │
      ▼
bus/sdk consume base 发生漂移
      │
      ▼
ReplaySharedPrimitiveRegistry
      │
      ▼
rebuild primitive catalog / bus base / sdk base
      │
      ▼
consumer 再次对齐到同一 admitted primitive
```

**开发者关注点**:
- 重建修复的是 consume base 漂移,不是重新发明新的 primitive 真相
- admitted primitive 与 consume views 必须可对账
- replay 后 bus/sdk 应继续消费同一组 core primitive,而不是分叉成两套基座

### 11.5 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| L1/L2 stable object input | RegisterSharedRef / Dto / Enum / Error | 基础标识与引用部分 + DTO/enum/error 部分 | shared primitive admitted |
| bus consume demand | RegisterMetadataSkeleton / bus base consume | 共享元信息与追踪骨架部分 | envelope base |
| sdk consume demand | QuerySharedPrimitive / sdk base consume | DTO / error / metadata 部分 | sdk consume base |

## 12. 数据与存储设计

### 12.1 先分清写模型 / 读模型 / 证据引用

| 对象 | 类型 | 是否持久化 | 说明 |
|---|---|---|---|
| shared IDs / Refs / DTO / enum / error / metadata | 写模型 | 是 | 共享 primitive 真相 |
| primitive catalog / bus base / sdk base / admission audit | 读模型 | 是/可重建 | 消费与审计层 |
| source_domain_ref / source_object_ref | 引用 | 随真相持久化 | 来源锚点 |

### 12.2 关系与索引建议

| 表/集合 | 关键索引 |
|---|---|
| shared_ref_registry | `primitive_id`, `kind`, `source_domain` |
| shared_dto_registry | `primitive_id`, `dto_kind` |
| shared_enum_registry | `primitive_id`, `enum_family_name` |
| shared_error_registry | `primitive_id`, `family_name` |
| shared_metadata_registry | `primitive_id`, `metadata_kind` |
| admission_history | `proposal_id`, `decision` |
| primitive_consume_views | `primitive_id`, `consumer_kind` |

**索引理由**:
- `source_domain` 支撑追溯这个 primitive 最初来自哪个业务仓
- `proposal_id + decision` 支撑 admission/reject/revised 链回放
- `consumer_kind` 支撑 bus/sdk consume base 对账与 drift 检查
- `primitive_id` 全链一致,便于 replay registry 后统一重建各视图

### 12.3 持久化建议

| 对象 | 存储方式 | 理由 |
|---|---|---|
| shared primitive registries | 主表 | core 正式共享契约真相 |
| admission history / replay | append-only 表 | 上收与回退决策必须可追溯 |
| primitive catalog / bus/sdk consume base | 可重建读模型 | 对消费层友好,不污染主真相 |

**存储边界说明**:
- admitted primitive 与 rejected/revised history 应显式分开,避免“最终状态”覆盖 admission 过程
- bus/sdk consume base 只保存只读消费材料,不能回写 registry 主真相
- 若某 primitive 后续被 revised,旧版本消费基座仍应可回放,以支持 drift 对账与回滚分析

### 12.4 关键校验

- admitted primitive 必须先过稳定性与最小骨架校验
- rich business fields 不得进入 core registries
- metadata skeleton 必须保持最小通用字段集
- bus/sdk consume base 可重建,不得反写真相 registry

### 12.5 建议表结构草案

#### `shared_ref_registry`

| 字段 | 类型 | 说明 |
|---|---|---|
| primitive_id | uuid | 主键 |
| kind | text | ref kind |
| source_domain | text | 来源域 |
| ref_shape | jsonb | 引用骨架 |

#### `admission_history`

| 字段 | 类型 | 说明 |
|---|---|---|
| proposal_id | uuid | 上收提案 |
| decision | enum | admitted/rejected/revised |
| rationale | text/jsonb | 判定理由 |
| created_at | timestamptz | 留痕时间 |

## 13. 读模型与投影设计

### 13.1 总体结构

```text
primitive registries write model
   │
   ▼
projection builders
   ├─ primitive catalog
   ├─ bus consume base
   ├─ sdk consume base
   └─ admission audit view
```

### 13.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| PrimitiveCatalogView | shared registries | 可查询共享 primitive 列表 |
| BusConsumeBaseView | shared refs/dto/error/metadata | bus base material |
| SdkConsumeBaseView | shared dto/error/metadata | sdk base material |
| AdmissionAuditView | admission history | 上收/回退审计视图 |

### 13.3 一致性说明

- 读模型允许最终一致
- primitive catalog / bus base / sdk base / audit view 都只读
- bus/sdk consume base 只能从 admitted primitive 派生
- audit view 漂移时必须能从 registry + history 真相重建
- rejected / revised 的 primitive 不得继续被 bus/sdk 当作当前正式 consume base
- bus/sdk consume base rebuild 必须保持对同一 primitive_id 的稳定映射,不能生成并行双轨基座

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| primitive proposal 非法 | 拒绝注册 |
| object 未收稳仍试图上收 | admission denied |
| dto 过厚 / metadata 过重 | 收缩后重试 |
| registry 与 consume base 漂移 | 以 registry 真相重建 |

### 14.1 重试 / 降级 / 熔断 / 补偿
- 对象未收稳时允许延迟上收,不强求同步进入 core
- dto / metadata 过厚时允许缩减后重试,但不得先带病 admitted
- bus/sdk consume 层漂移时允许重建,但不得回写 registry 真相
- admitted primitive 后若被证明仍不稳定,应先走 revised/reject 流程并保留完整 admission history,不得直接静默覆盖
- registry 与 bus/sdk consume base 对账失败时,应以 registry + admission history 为真相来源重建 consume views

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 基础标识与引用部分 | ref 语义未稳 / relation 误抽 | admission trace | reject / 保留在业务仓 | replay ref admission |
| 共享对象骨架与最小 DTO 部分 | dto 过厚 / rich model 混入 | dto compare | 收缩字段 / reject | replay dto admission |
| 共享枚举与状态族部分 | 单仓私有状态误上收 | enum compare | reject / 回退 | replay enum admission |
| 共享错误与返回语义部分 | error family 膨胀 | error compare | 收缩骨架 | replay error admission |
| 共享元信息与追踪骨架部分 | metadata 过重 / wrapper 倒灌 | metadata compare | 收缩字段 / reject | replay metadata admission |

## 15. 实现红线 / 开发禁止事项

- 不允许把 rich business model 直接上收到 core
- 不允许把业务主语正文伪装成 shared DTO
- 不允许让 bus transport 细节倒灌 core metadata skeleton
- 不允许让 sdk wrapper 便利字段替代 core primitive 真相
- 不允许在未完成 admission 判定前把对象正式登记进 core
- 不允许 rejected primitive 继续被 bus/sdk consume 作为正式基座
- 不允许为“方便”把业务仓专属错误全集整体上收 core

## 17. 最小可运行闭环

- 从 L1/L2 已收稳对象中抽出一组共享 ID/Ref 进入 core
- 基于这些 primitive 形成最小 DTO / enum / error / metadata skeleton
- bus 和 sdk 能消费同一组 core primitives,且不会反向污染 core registry

## 18. 结论

本详细设计的核心结论是：
- `L0-core` 的实现必须围绕五个主要部分展开,而不是按 util/types/helpers 平铺
- shared Ref / DTO / enum / error / metadata 是正式共享 primitive 真相,primitive catalog / bus base / sdk base / audit view 是只读消费层
- L1/L2 的输入、bus/sdk 的消费和 admission/replay 的治理都必须围绕 core 的正式 registry 收口,不能再让重复定义和临时 wrapper 继续扩张
- 后续测试与验收文档,应直接围绕 shared primitive admission、rich model 拒绝上收、bus/sdk consume 一致性和 replay/audit 展开

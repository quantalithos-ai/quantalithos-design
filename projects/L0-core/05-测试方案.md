### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 core 的 registry 可写,而是系统验证 `L0-core` 是否真正满足“共享契约稳定器”的设计要求,尤其要证明以下几点成立:
- shared ID / Ref / minimal DTO / enum / error / metadata skeleton 构成正式共享 primitive 真相层
- `shared Ref ≠ 主语正文`、`minimal DTO ≠ rich business model`、`metadata skeleton ≠ bus envelope / sdk wrapper` 三条核心边界必须成立
- 只有已稳定、可跨仓复用的对象才能 admitted 进 core
- rejected / revised / admitted 的 admission 结果必须可回放和可审计
- bus / sdk consume base 只能消费 admitted primitive,不能继续吃 rejected 或 unstable 对象
- registry / catalog / bus base / sdk base 之间的漂移必须可检测、可重建、可对账

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 基础标识与引用部分 | 真相对象 | P0 | CoreId / Ref / subject / relation skeleton |
| 共享对象骨架与最小 DTO 部分 | 真相对象 | P0 | CoreDto / BaseCommand / BaseQuery / BaseResponse |
| 共享枚举与状态族部分 | 共享语义层 | P0 | SharedEnumFamily / SharedStatusFamily / ResultCategory |
| 共享错误与返回语义部分 | 共享错误层 | P0 | CoreErrorFamily / CoreReturnSemantic / RetryabilityHint |
| 共享元信息与追踪骨架部分 | 共享元信息层 | P0 | TraceMetadata / RequestMetadata / ResponseMetadata |
| bus 完整事件传输契约 | 非范围 | P2 | 只验 core primitive 对 bus consume 的支撑,不验 bus 全部实现 |
| sdk developer-facing convenience API | 非范围 | P2 | 只验 core primitive 对 sdk consume 的支撑,不验 sdk 上层包装体验 |
| 业务仓 rich model / 状态机 | 非范围 | P2 | 只验“是否应进入 core”的 admission 边界,不验业务仓内部全部实现 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数和局部不变量 | domain / policy owner | `entity_ref.validate_stable_shape`、`dto.validate_minimal_shape`、`family.validate_shared_admission`、`family.validate_shared_boundary`、`request_meta.validate_minimal_trace_shape` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + registry repo + admission policy + projection 联动 | backend / domain owner | `RegisterSharedRef`、`RegisterSharedDto`、`RegisterSharedEnum`、`RegisterSharedErrorFamily`、`RegisterMetadataSkeleton`、`ValidateCoreAdmission`、`RejectSharedPrimitive`、`BuildBusConsumeBase`、`BuildSdkConsumeBase`、`ReplaySharedPrimitiveRegistry` | 上收、拒绝、回放、消费基座同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | domain stable object → core register；core primitive → bus/sdk consume；metadata skeleton → bus envelope base；error family → sdk/base consume | 输入输出语义一致 |
| 恢复专项测试 | 验证 registry 与 consume base 漂移时是否可恢复 | architecture / QA | admitted primitive 后发现不稳、rejected primitive 误被消费、catalog/base drift、replay registry 后重建 | registry 真相不丢失,consume 可恢复 |
| 投影一致性测试 | 验证 primitive catalog / bus base / sdk base / audit view 与正式 registry 一致 | backend / QA | catalog rebuild、bus/sdk consume base compare、admission audit replay | 读模型只读且与真相一致 |
| 端到端主线测试 | 验证最小共享契约闭环 | QA / owner | register shared ref/dto/enum/error/metadata → bus/sdk consume → replay / rebuild | 共享 primitive 主干闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| 只有稳定共性才能进入 core | ValidateCoreAdmission + RegisterShared* | 集成测试 | 是 | admission trace / registry record |
| rich business model 禁止上收 | too-rich dto / rich ref / heavy metadata 被拒绝 | 单元 + 集成测试 | 是 | reject record / compare |
| shared ref / dto / enum / error / metadata 边界清晰 | 五类 primitive 各自注册、各自被验证 | 集成测试 | 是 | primitive compare |
| bus/sdk 只能 consume admitted primitive | rejected primitive 不得进入 consume base | 事件链 + 投影一致性测试 | 是 | consume base compare |
| registry / replay / audit 一致性 | replay 后视图与真相一致 | 恢复专项测试 | 是 | replay report / audit compare |

## 4. 环境与配置矩阵

| 环境 | 用途 | 依赖 | 关键配置 | 风险 |
|---|---|---|---|---|

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|
| S | rich business model 被 admitted / rejected primitive 继续被 bus/sdk consume / metadata skeleton 被 wrapper 倒灌 | 阻断放行,必须修复 |
| A | 主线可跑但 replay/audit/consume drift 语义不稳 | 原则上修复后再放行 |
| B | 非关键 primitive catalog、audit view 或低优先级查询异常 | 可带风险进入下一轮 |

---

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 shared ref / dto / enum / error / metadata admission 规则,都必须回归 admitted/rejected/revised 主线
- 每次改动 primitive registry,都必须回归 catalog / bus base / sdk base consume 一致性
- 每次改动 replay / audit 逻辑,都必须回归 registry replay 与 drift 重建主线
- 每次改动 wrapper / transport consume 逻辑,都必须回归“不能反向污染 core”边界

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| 随着更多仓收稳,某些 primitive 是否应进入 core 仍会持续变化 | 测试矩阵需扩充 | TL / 架构 |
| bus/sdk consume 若未来支持多语言/多封装层 | consume compare 样本需增加 | core + bus + sdk |
| metadata skeleton 若后续继续扩展 | minimal boundary 测试需增加分支 | Owner / TL |

### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L0-core` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L0-core` 是跨仓共享 ID、Ref、枚举、最小 DTO 和元信息骨架的共享契约稳定器,不是业务上位总真相仓
- shared Ref / DTO / enum / error / metadata 构成正式共享 primitive 真相层
- `shared Ref ≠ 主语正文`、`minimal DTO ≠ rich business model`、`metadata skeleton ≠ bus envelope / sdk wrapper` 三条核心边界必须成立
- 只有稳定共性对象才允许 admitted 进入 core
- rejected / revised / admitted 的 registry、catalog、bus/sdk consume base 必须可对账和可重建
- bus 和 sdk 只能消费 admitted primitive,不能反向污染 core

因此,本次验收的目的不是笼统判断“core 里是否有几份公共类型文件”,而是判断共享 primitive 的准入、注册、拒绝、回放和 bus/sdk 承接是否真的成立,是否可作为后续 L0-bus 与 L0-sdk 的稳定基座。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| 基础标识与引用部分 | 是 | CoreId / EntityRef / SubjectRef / RelationRef |
| 共享对象骨架与最小 DTO 部分 | 是 | CoreDto / BaseCommand / BaseQuery / BaseResponse |
| 共享枚举与状态族部分 | 是 | SharedEnumFamily / SharedStatusFamily / ResultCategory |
| 共享错误与返回语义部分 | 是 | CoreErrorFamily / CoreReturnSemantic / RetryabilityHint |
| 共享元信息与追踪骨架部分 | 是 | TraceMetadata / RequestMetadata / ResponseMetadata |
| L0-bus 完整 transport 契约 | 否 | 只验 core 是否提供稳定基座,不验 bus 全部实现 |
| L0-sdk 开发者包装层体验 | 否 | 只验 core primitive 是否可被 sdk consume,不验 sdk 上层 API 设计 |
| 各业务仓 rich model / 状态机正文 | 否 | 只验是否应进入 core 的 admission 边界 |

## 4. 功能验收门禁

| 功能/场景 | 门禁条件 | 证据 | 结论 |
|---|---|---|---|
| RegisterSharedRef | 已收稳的共享引用必须能进入 core registry,且 Ref 只表达引用骨架 | registry 记录 / trace / compare | [] |
| stable admission only | 未收稳对象不得 admitted 进入 core | admission trace / reject record | [] |
| rich model reject | rich business object / too-rich dto 不得进入 shared dto registry | reject record / dto compare | [] |
| shared enum/status family | 只有跨仓稳定复用的 enum/status family 才能进入 core | enum registry / compare report | [] |
| shared error/return family | 共享错误与返回语义必须是最小骨架,不得吞并业务仓错误全集 | error registry / compare report | [] |
| metadata skeleton | 共享 metadata skeleton 必须保持最小化,不得吸入 bus transport 或 sdk wrapper 细节 | metadata registry / compare | [] |
| bus consume base | bus 只能消费 admitted primitives,不得继续消费 rejected/unstable 对象 | bus base compare / reject visibility test | [] |
| sdk consume base | sdk 只能消费 admitted primitives,不得把 wrapper convenience 字段反向写回 core | sdk base compare / negative flow | [] |
| ReplaySharedPrimitiveRegistry | replay 后 registry、catalog、bus base、sdk base、audit view 必须重新一致 | replay report / before-after compare | [] |
| rejected primitive isolation | rejected primitive 不得进入任何正式 consume base | consume view check / negative test | [] |

| 红线 | 验收条件 | 证据 | 是否通过 |

## 7. 安全与治理门禁

| 门禁项 | 要求 | 证据 | 结论 |
|---|---|---|---|
| rich model 不可上收到 core | rich business object 进入 core 必须被阻断 | reject record / negative flow | [] |
| rejected primitive 不可被 bus/sdk consume | consume base 只能来自 admitted primitive | bus/sdk compare / negative view check | [] |
| metadata skeleton 不可退化成 bus/sdk 本体 | transport/wrapper 字段不得倒灌 core | metadata compare / model review | [] |
| shared error family 不可膨胀 | 单仓错误全集不得进入 core | error family compare / reject record | [] |
| registry replay 不可制造第二套 primitive 真相 | replay 后仍指向同一 admitted primitive 集合 | replay compare / primitive_id check | [] |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | rich business model 被 admitted / rejected primitive 继续被 bus/sdk consume / metadata skeleton 被 wrapper/transport 倒灌 |
| A | 视情况 | 主线可跑但 replay/audit/consume drift 语义不稳 |
| B | 可带着走 | 非关键 primitive catalog、audit view 或低优先级查询异常 |

## 9. 风险接受与遗留项

| 风险/遗留项 | 影响 | 处理策略 | 接受人 |
|---|---|---|---|
| 随着更多仓收稳,某些 primitive 是否应进入 core 仍会持续变化 | 验收矩阵需扩充 | 进入后续架构跟踪 | TL / 架构 |

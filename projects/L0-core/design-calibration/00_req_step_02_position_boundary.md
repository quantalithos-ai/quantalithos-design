### 3. SOP 问题回答

1. 本仓一句话定义是什么？

   回答：`L0-core` 是 Quantalithos 的跨仓共享契约来源仓，负责把所有下游仓共同引用的协议形状、事件包络、追踪上下文和通用错误契约收敛为稳定基线。

2. 为什么它需要单独成仓？

   回答：跨仓契约是全系统最稳定、被依赖最广、变更影响最大的内容，必须独立于事件投递实现、客户端封装和业务域实现，否则下游仓会各自复制契约并产生 drift。

3. 本仓不是什么？

   回答：它不是事件总线实现，不是 SDK 客户端封装，不是任何 L1 业务域服务，也不是 observability、archive、runtime 或具体业务语义的承载仓。

4. 最容易与哪些相邻仓或概念混淆？

   回答：最容易与 `L0-bus`、`L0-sdk`、L1 六域服务、`L4-observability`、`architecture/proto-draft` 和 `architecture/bus-draft/event-catalog.md` 混淆。混淆点分别是契约定义与事件投递、契约类型与客户端体验、契约形状与业务实现、追踪字段与观测存储、正式仓产物与设计态草案、事件目录与可生成 schema。

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A：把 core、bus、sdk 合成一个 L0 仓 | 初期仓数量少，开发入口集中 | 契约定义、事件投递和客户端封装变化速率不同，容易互相拖动版本节奏 | 不采用 |
| 方案 B：`L0-core` 只承载共享契约基线 | 边界清晰，依赖方向稳定，便于所有下游仓统一引用 | 需要与 bus、sdk、L1 仓保持严格协作约束 | 采用 |
| 方案 C：`L0-core` 同时承载运行时校验和观测存储 | 契约与运行反馈放在一起，查询方便 | 会把 observability、bus 和服务运行职责混入契约层 | 不采用 |

| 相邻对象 | 边界口径 | 不进入正式 §2 的内容 |
|---|---|---|
| `L0-bus` | `core` 定义事件契约，`bus` 负责事件投递能力 | publish / subscribe / ack / dead-letter 等能力细节 |

| `L4-observability` | `core` 约束追踪上下文字段，observability 负责采集、存储和追溯查询 | 审计存储、指标、日志、trace 查询 |
| `architecture/proto-draft` | 设计态 proto 草案是 `L0-core` 的输入材料，不是长期正式仓 | 目录迁移策略、生成器配置、文件布局 |
| `architecture/bus-draft/event-catalog.md` | event catalog 记录事件存在与治理信息，`core` 承载可生成和可引用的事件契约形状 | 订阅方矩阵、保留期治理、事件目录维护流程 |

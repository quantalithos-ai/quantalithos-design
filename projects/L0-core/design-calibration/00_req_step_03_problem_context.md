### 3. SOP 问题回答

1. 当前业务背景是什么？

   回答：Quantalithos 已采用六域平权、27 仓、七层依赖的系统拆分方式，L1+ 各仓都需要在同一套跨仓契约上协作。N0 契约地基是后续身份、对话、工作、过程、治理、制品、运行时、UI 和生态仓继续校准与开发的共同前置。

2. 当前的主要痛点或机会点是什么？

   回答：主要痛点不是缺少某个具体业务功能，而是跨仓契约仍散落在设计态 proto 草案、事件目录、域 README 和旧版需求表述中。若不先把问题收束为 L0-core 的仓级需求，后续仓容易各自解释契约边界、复制类型、漂移事件命名或把 bus / sdk / 业务域职责混入 core。

3. 这些问题能否量化？

   回答：能部分量化。最新架构是 27 仓 × 7 层；N0 明确包含 core / bus / sdk 三仓；旧文档仍出现 26 仓、下游 25 仓等旧口径；`architecture/bus-draft/event-catalog.md` 已登记跨域事件目录，`architecture/proto-draft/README.md` 已存在六域 service 与 common 契约草案，但它们仍是设计态输入而不是正式仓需求基线。

4. 哪些是业务问题，哪些是技术问题？

   回答：业务问题是产品的多成员、多项目、跨阶段协作闭环需要稳定契约支撑，否则 MVP 和后续仓开发会缺少共同语言。技术问题是契约来源分散、旧口径残留、边界混入相邻仓以及契约 drift 风险，会影响后续架构、概要、详细设计和代码实现的一致性。

### 7. 结构化中间产物

#### 7.1 业务背景

Quantalithos 已采用六域平权、27 仓、七层依赖的系统拆分方式，跨仓协作必须建立在稳定共享契约上。`L0-core` 处于 N0 契约地基节点，是后续 L1+ 仓校准需求、设计和代码实现时共同引用的底层语义入口。

#### 7.2 现状与问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 跨仓契约来源仍处于分散状态 | 契约事实分布在 proto 草案、事件目录、域 README、README 和旧需求文档中 | 下游仓难以判断哪个文件是需求基线，容易各自解释或复制契约 |
| 旧需求文档口径与最新架构不一致 | 仍出现 26 仓、下游 25 仓、纯技术设施等旧表达 | 后续文档校准和开发交接容易沿用过期口径 |
| 问题定义与目标 / 方案混写 | 背景章节直接列 proto、CloudEvent、ErrorCode、Trace、binding 等能力项 | Step 4 目标、Step 7 核心闭环、Step 9 功能需求会缺少清晰前置问题 |

#### 7.3 业务问题 vs 技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | 多成员、多项目、跨阶段协作的产品闭环需要稳定共享契约作为共同语言；如果 L0-core 需求不先收束，MVP 和后续仓开发会缺少一致的协作前提。 |
| 技术问题 | 契约来源分散、旧口径残留、边界与相邻仓混淆，会让 proto、事件、错误、追踪等跨仓契约在设计和实现阶段发生 drift。 |

### 3. SOP 问题回答

1. 这个仓必须满足哪些性能要求？

   回答：`L0-core` 的共享契约读取、追溯查看、契约检查和派生辅助不应成为 27 仓协作主链的阻塞点。需求层不直接写 proto 编译时间、CI 时长或包体积阈值，这些后移到测试方案或实施计划。

2. 这个仓必须满足哪些可用性要求？

   回答：外围增强能力、工具链、注册表或自动发布体验不可用时，核心契约真相的建立、读取、演进和追溯口径仍应成立。`L0-core` 的核心能力不能依赖外围能力全部正常才成立。

3. 这个仓必须满足哪些安全要求？

   回答：`L0-core` 不得越权保存业务数据、事件实例 payload、观测日志 / trace 正文、归档包正文、运行时执行记录、凭据或 token，也不得承接认证、授权和运行时投递职责。

4. 这个仓必须满足哪些审计 / 可追溯要求？

   回答：共享契约范围变化、共享语义变化、兼容性变化、破坏性变化、废弃和退役必须可追溯到正式依据。追溯要求属于本仓质量底线，不应只依赖下游仓局部记录。

5. 这个仓必须满足哪些幂等 / 一致性要求？

   回答：同一共享契约在平台范围内只能有一个正式语义和兼容性状态；重复处理同一候选契约、派生请求或演进记录时，不应制造多个相互冲突的契约真相。

6. 这个仓必须满足哪些可观测性要求？

   回答：共享契约当前状态、关键变化、兼容性判断、派生 / 检查结果和异常边界应能被平台稳定观察。本仓不保存观测正文，但必须让关键契约状态和异常具有可观察入口。

7. 哪些要求能量化，哪些只能给出判断口径？

   回答：需求层优先给出判断口径；性能、检查耗时、CI 时长、包体积、注册表可用性等具体数值可以在测试方案、验收标准或实施计划中量化。本章不把工具链数值误写成需求层核心质量要求。

### 4. 当前文档问题诊断

| 位置 | 当前问题 | 影响 |
|---|---|---|
| §7.1 非功能指标表 | 写 proto 编译时间、CI 端到端时间、三语言发版成功率、注册表可达率、binding 体积等 | 大量内容是工具链、发布和实施指标，不是需求层质量约束 |
| §7.1 兼容性 | 写 Rust MSRV、Python 版本、Node.js 版本 | 属于实施约束或代码仓技术选型，不应在需求层非功能主表展开 |
| §7.1 Breaking 防护 | 写 CI 拦截率和测试脚本 | 方向正确，但需求层应表达“破坏性变化必须可发现、可阻断、可追溯”，具体脚本后移 |
| §7.2 合规要求 | 将三红线、ISO、SLSA 与具体发版包签名混写 | 可追溯和安全要求应保留，供应链细节后移到实施计划 |
| §7 整体 | 未按性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性六类检查 | 与新版需求规范 4.13 不一致 |

### 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 分类方式 | 性能、可用性、Breaking、可追溯、审计、兼容性、binding 体积、合规 | 性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性 | 对齐需求规范 4.13 |
| 性能指标 | proto 编译 < 30 秒、CI < 5 分钟 | 核心契约读取、追溯、检查、派生不成为主链阻塞点 | 需求层写质量口径，具体数值后移 |
| 可用性 | 三语言发版和注册表可达 | 外围增强或工具链不可用时，核心契约真相仍成立 | 保护核心闭环，不把发布平台当核心能力 |
| 安全 | 第三方包签名、Secrets | 不保存越界正文，不承接认证授权和运行时职责 | 对齐 Step 11 数据边界 |
| 审计 / 可追溯 | TraceContext / ActorContext 覆盖、ADR | 契约范围、语义、兼容性、破坏性变化和退役必须可追溯 | 保留质量目标，避免字段级实现 |
| 一致性 | proto3、版本策略 | 同一契约只有一个正式语义和兼容性状态 | 对齐契约真相职责 |
| 可观测性 | 未单独成类 | 契约状态、关键变化、检查结果和异常边界可被观察 | 支撑后续验收和运维可见性 |

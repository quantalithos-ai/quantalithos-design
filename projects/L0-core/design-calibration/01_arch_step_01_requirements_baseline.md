### 3. SOP 问题回答

1. 当前架构设计依赖哪些需求结论？

   回答：依赖 `00-需求文档.md` 中已收稳的仓级定位、边界对象、核心能力闭环、功能需求、规则边界、数据归属、接口依赖、非功能要求、验收标准和需求追溯矩阵。

2. 这些需求结论里，哪些已经稳定？

   回答：已经稳定的是 `L0-core` 的正式定位、非目标边界、核心能力闭环、F-001~F-007 功能需求、BR-001~BR-014 规则、契约真相 / 快照 / 引用 / 禁止正文的数据归属，以及无内部前置输入仓的依赖口径。

3. 哪些需求结论仍然待确认？

   回答：当前没有阻塞架构设计的需求待确认项。具体 proto 字段形态、ID 包装方式、字段编号策略、TypeScript 客户端形态、BSR 分发、JSON Schema 导出、语言生成器选择、工具链故障备选路径属于后续架构细化、概要设计、详细设计、测试方案或实施计划的待确认项。

4. 哪些需求会直接影响架构边界？

   回答：`L0-core` 作为跨仓共享契约来源仓、相邻仓职责不得进入本仓、下游不得自建冲突跨仓 schema、事件投递 / SDK 高层封装 / L1 业务实现 / 观测存储 / 归档恢复 / 运行调度 / 认证授权均为边界外能力，这些结论直接决定职责边界和系统上下文。

5. 哪些需求会直接影响数据所有权？

   回答：共享契约定义、共享契约范围、契约版本 / 兼容性状态、契约演进记录为 `L0-core` 真相；下游消费派生产物、契约检查摘要、兼容性报告摘要为快照；标准、评审 / ADR、下游消费关系为引用；L1 业务数据、事件实例 payload、观测日志 / trace、归档包、运行时记录、SDK 凭据 / token 正文禁止保存。

6. 哪些需求会直接影响依赖方向或一致性策略？

   回答：`L0-core` 是七层依赖中的底座仓，当前不依赖其他内部仓先提供能力；它向 `L0-bus`、`L0-sdk`、L1~L6 输出共享契约语义。架构必须保证上层仓只消费本仓契约，不反向牵引本仓边界；同一共享契约在平台范围内必须保持单一正式语义和兼容性状态。

#### 7.1 架构需求基线清单

| 需求结论 | 来源章节 | 架构影响 | 稳定性 |

| 本仓不承接事件投递、SDK 高层封装、L1 业务实现、观测存储、归档恢复、运行调度、认证授权 | 需求 §4 / §10 / §14 | 决定职责边界和一票否决红线 | 稳定 |
| 核心闭环为范围收束、语义表达、演进追溯、下游消费派生 | 需求 §7 / §9 / §16 | 决定架构目标和主要结构主线 | 稳定 |
| `L0-core` 对内部仓无前置输入依赖,对 `L0-bus`、`L0-sdk`、L1~L6 输出契约基线 | 需求 §6 | 决定系统上下文和依赖方向 | 稳定 |

#### 7.2 架构硬约束清单

| 硬约束 | 约束影响 |
|---|---|
| 不得把 `L0-core` 设计成业务域服务 | 职责边界、限界上下文和数据所有权必须保持契约语义层 |
| 不得把 `L0-core` 设计成事件总线实现 | 关键交互只能表达契约变化输出面,不承接投递、确认、重试、死信 |
| 不得把 `L0-core` 设计成 SDK 高层客户端或包发布中心 | 派生和生成可以作为下游消费支撑,不能成为本仓核心架构职责 |
| 不得让上层仓反向拥有或覆盖共享契约真相 | 依赖方向必须从 L0-core 向上输出,共享契约真相只能在本仓收束 |
| 不得保存业务、运行、观测、归档正文或凭据 | 数据所有权必须明确排除正文真相 |
| 不得把标准、工具链、注册表或 CI 平台误写成当前需求闭环的运行时外部依赖 | 系统上下文必须区分标准对齐、工具链选型和运行时系统依赖 |

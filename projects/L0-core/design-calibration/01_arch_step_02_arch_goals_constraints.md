### 3. SOP 问题回答

1. 这个仓在架构层面要确保什么成立？

   回答：必须确保 `L0-core` 在架构层成为跨仓共享契约来源,并能承载契约范围收束、契约语义表达、契约演进追溯和下游稳定消费派生四段结构主线。同时必须保证契约真相、派生快照、外部引用和禁止保存正文之间的边界不被打穿。

2. 哪些约束是不可变的？

   回答：不可变约束包括：不做事件总线运行时;不做 SDK 高层客户端或包发布中心;不做 L1 业务语义实现;不保存业务、事件实例、观测、归档、运行时记录或凭据正文;不允许上层仓反向拥有共享契约真相;不把标准、工具链、注册表、CI 平台写成运行时外部系统依赖。

3. 哪些约束是当前阶段可以接受的取舍？

   回答：当前阶段可以接受将三语言 binding、样例、可视化、自动发布、额外导出格式作为外围增强或后续设计 / 实施事项处理;可以接受 proto 字段形态、语言生成器、分发渠道和工具链故障备选路径后移;可以接受先在架构层定义契约真相和边界,不提前展开文件布局、schema 或生成流程。

4. 哪些目标可以明确判断，甚至量化？

   回答：架构层目标不使用旧版“事件覆盖率 90%”“CI 拦截率 100%”“三语言生成成功率”等实施 / 测试指标。当前可明确判断的是结构性目标是否成立,例如是否存在单一契约来源、是否排除了相邻仓职责、是否区分了真相 / 快照 / 引用 / 禁止正文、是否保证依赖方向由 L0 向上输出。

5. 哪些事情虽然相关，但不是本仓架构当前要解决的问题？

   回答：事件投递、SDK 高层客户端体验、包发布、L1 业务实现、观测查询、归档恢复、运行时调度、认证授权、测试脚本、CI 命令、具体 proto 字段和 Rust 类型都不是当前架构主线。

### 7. 结构化中间产物

#### 7.1 业务背景结论

Quantalithos 的 27 仓、七层依赖和跨仓协作需要一个稳定的共享契约来源。需求文档已经确认 `L0-core` 不承载事件投递、SDK 高层封装、业务实现、观测存储、归档恢复、运行调度或认证授权;因此架构设计的核心任务不是选择某个 proto 工具链,而是把跨仓共享契约来源仓的系统边界、职责边界、数据真相边界和依赖方向稳定下来。

#### 7.2 驱动力结论

| 驱动力 | 说明 |
|---|---|
| 27 仓协作需要稳定契约基线 | 否则上层仓会围绕不同解释实现,形成跨仓 schema drift。 |
| L0 底座层需要最低变化率和最强边界保护 | 否则底层契约会被上层运行时、SDK 或业务语义反向牵引。 |
| 共享契约必须有单一真相与明确派生边界 | 否则派生产物、检查摘要和外部引用会被误当成契约真相。 |
| 契约变化必须可被追溯和下游感知 | 否则高影响变更会以局部实现或文档漂移的方式发生。 |
| 标准对齐必须被架构承接,但不能变成运行时外部依赖 | 否则系统上下文会混淆标准、工具链和运行时系统。 |

#### 7.3 架构目标表

| 架构目标 | 说明 |
|---|---|
| 承载跨仓共享契约的正式来源边界 | 否则 `L0-core` 会退化为工具链仓、文件集合或某个下游仓的内部类型集合。 |
| 支撑范围收束、语义表达、演进追溯和下游消费派生四段结构主线 | 否则核心能力闭环会被拆散成零散 proto、事件、错误、追踪或生成任务。 |
| 守住 `L0-core` 与 `L0-bus`、`L0-sdk`、L1、L2、L4 等相邻仓职责边界 | 否则事件投递、客户端封装、业务实现、观测存储、归档恢复和运行调度会反向污染本仓。 |
| 守住契约真相、派生快照、外部引用和禁止正文的数据边界 | 否则本仓会吸收业务、事件实例、观测、归档、运行时或凭据正文。 |
| 允许下游仓基于同一契约基线稳定消费和派生 | 否则上层仓会各自维护冲突 schema,破坏七层依赖方向。 |
| 支撑高影响契约变化的兼容性与追溯边界 | 否则破坏性变化、废弃和退役会以局部实现或文档漂移方式发生。 |

#### 7.4 不可变约束表

| 约束 | 说明 |
|---|---|
| 不设计事件总线运行时 | 事件发布、订阅、确认、重试、死信属于 `L0-bus`,否则契约来源会与投递实现混淆。 |
| 不设计 SDK 高层客户端或包发布中心 | 重试、配置、认证封装、开发者体验和发布渠道属于 `L0-sdk` 或实施计划,否则本仓会变成客户端产品。 |
| 不设计 L1 业务域实现 | 身份、对话、工作、过程、治理、制品、工作空间的业务语义属于 L1 仓,否则共享契约会吸收业务真相。 |
| 不拥有业务、事件实例、观测、归档、运行时或凭据正文 | 这些正文真相属于相邻仓或外部系统,否则数据所有权会被打穿。 |
| 不允许上层仓反向拥有或覆盖共享契约真相 | 共享契约真相必须在 `L0-core` 收束,否则平台会形成冲突契约。 |
| 不把标准、工具链、注册表或 CI 平台写成运行时外部系统依赖 | CloudEvents / W3C 是标准对齐来源,buf / CI / registry 是后续技术或实施机制。 |

#### 7.5 当前阶段可接受取舍表

| 取舍 | 当前口径 |
|---|---|
| 三语言 binding 与生成产物 | 当前作为下游消费与派生支撑,不进入核心架构职责。 |
| 样例、可视化、自动发布和额外导出格式 | 当前作为外围增强处理,不进入核心能力闭环。 |
| 具体 proto 字段、ID 包装、字段编号策略 | 当前只保留契约语义和演进边界,具体形态后移到概要 / 详细设计。 |
| buf、CI、registry、语言生成器与包发布路径 | 当前不作为系统上下文外部依赖,后移到关键技术选型、测试方案或实施计划。 |
| 契约检查与派生辅助 | 当前保留为外围增强和后台任务边界,不作为判断核心架构成立的前提。 |

#### 7.6 架构非目标表

| 非目标 | 不展开原因 |
|---|---|
| 不设计事件投递架构 | 事件投递属于 `L0-bus`,不属于共享契约来源仓。 |
| 不设计 SDK 客户端架构 | SDK 高层封装和开发者体验属于 `L0-sdk`,本仓只提供可派生契约来源。 |
| 不设计 L1 领域服务架构 | L1 仓拥有业务语义和领域实现,`L0-core` 只承载共享契约语义边界。 |
| 不设计观测查询、审计存储或归档恢复架构 | 这些属于 `L4-observability` 和 `L4-archive`,本仓只约束相关契约与上下文。 |
| 不设计运行时调度、工具执行或容器编排架构 | 这些属于 L2 运行层,不属于本仓架构主线。 |
| 不设计认证、授权或权限裁决架构 | 这些属于安全入口、治理或授权能力,不属于共享契约来源仓。 |
| 不设计测试执行、CI 命令或包发布流程 | 这些属于测试方案或实施计划,不属于架构设计主线。 |

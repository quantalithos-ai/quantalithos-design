### 3. SOP 问题回答

1. 这个仓具体做什么？

   回答：`L0-core` 负责把 Quantalithos 的跨仓共享契约收束为单一真相来源，包括共享协议形状、事件包络、追踪上下文和通用错误契约，并为下游仓提供稳定引用入口。

2. 这个仓具体不做什么？

   回答：`L0-core` 不承担事件投递与确认、不承担 SDK 高层客户端封装、不承担 L1 业务语义实现、不承担观测 / 归档正文存储或查询，也不承担认证、授权或运行时调度。

3. 哪些能力看起来相关但必须属于其他仓？

   回答：事件发布 / 订阅 / 重试属于 `L0-bus`，客户端体验与生成包分发属于 `L0-sdk`，成员、工作、流程等业务真相属于各 L1 仓，审计 / trace / 日志查询属于 `L4-observability` 或 `L4-archive`，身份认证与权限裁决属于安全入口或治理层。

4. 哪些行为绝不能隐式发生？

   回答：不能把共享契约真相藏到下游仓里，不能把业务正文放进 `L0-core`，不能把派生快照误写成真相，不能把投递实现、客户端体验或业务语义偷偷塞进职责定义。

5. 哪些边界如果不写清，后续设计最容易串线？

   回答：最容易串线的是“契约形状 vs 事件投递”“共享契约 vs SDK 体验”“共享契约 vs 业务语义”“真相 vs 派生物”“共享类型 vs 域类型”这五类边界。

### 4. 当前文档问题诊断

| 位置 | 当前问题 | 影响 |
|---|---|---|
| §4 标题 | 仍然把职责边界放在“系统边界与上下文”章节之下 | 章节层级错位,读者会把职责与上下文混在一起 |
| §4.2 结构 | 只有“做什么 / 不做什么”零散列表 | 不符合正式规范的 `职责项 / 类型 / 说明` 表结构 |
| §4.2 内容 | 只列出少量不做项,没有清楚列出做项 | 读者无法一眼看出本仓的正式承担范围 |
| §4.2 说明 | 容易把职责说明写成上下文说明或实现说明 | 后续章节会继续串线到系统边界或实现层 |
| 全文 | 缺少易混淆职责和边界红线清单 | 最容易引发后续误判的内容没有被显式收口 |

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A：继续把职责边界放在系统边界章节里 | 改动小 | 容易再次把职责、上下文和实现混在一起 | 不采用 |

### 7. 结构化中间产物

#### 7.1 职责边界总表

| 职责项 | 类型 | 说明 |
|---|---|---|
| 跨仓共享契约真相承载 | 做 | 这是本仓的核心职责,负责把平台级共享协议收束为单一正式来源。 |
| 共享契约版本与兼容性边界维护 | 做 | 若不由本仓维护,下游将围绕不同解释演进并产生 drift。 |
| 提供共享契约稳定引用入口 | 做 | 下游与上游标准都需要围绕同一入口消费契约,但不意味着本仓保存外部正文。 |
| 事件总线运行时 | 不做 | 事件投递、订阅、确认、重试和死信属于 `L0-bus`。 |
| SDK 高层客户端封装 | 不做 | 客户端体验、重试、配置和分发渠道属于 `L0-sdk`。 |
| L1 业务语义实现 | 不做 | 业务状态机、规则和领域实现属于各 L1 仓。 |
| 观测 / 归档正文存储与查询 | 不做 | 追踪、日志、审计和归档查询属于 `L4-observability` / `L4-archive`。 |
| 安全认证与权限裁决 | 不做 | 身份认证和授权治理属于安全入口或治理层。 |
| 共享契约与业务语义的桥接解释 | 易混淆职责 | 容易被误解为业务服务,实际上这里只能表达契约边界,不能承载业务语义。 |
| 真相与派生产物边界维护 | 易混淆职责 | 容易把派生快照、检查摘要或引用表误当成真相。 |

#### 7.2 边界红线清单

- 不得将事件投递、订阅、确认、重试和死信写入本仓职责。
- 不得将 SDK 重试、配置、认证和开发者体验写入本仓职责。
- 不得将 L1 业务状态、规则或领域实现写入本仓职责。
- 不得将日志、trace、审计或归档正文写入本仓职责。
- 不得让任何下游仓反向拥有共享契约真相。
- 不得把工具链、发布脚本或 CI 规则写成职责归属。

#### 7.3 收束说明

```text
`L0-core` 的职责是把跨仓共享契约收束为单一真相，并保持它的演进边界稳定。
它不承载事件投递、SDK 客户端体验、L1 业务语义实现或观测 / 归档正文。
```

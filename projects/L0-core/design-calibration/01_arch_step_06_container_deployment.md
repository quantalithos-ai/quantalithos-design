### 3. SOP 问题回答

1. 这个仓在运行时有哪些正式承载单元？

   回答：`L0-core` 没有常驻在线运行时容器。它的正式承载单元是契约变更入口、契约源码承载、契约校验与派生处理单元、契约发布快照承载和契约工具链执行环境。

2. 哪些单元承接同步入口，哪些承接后台处理或异步消费？

   回答：契约变更入口承接同步变更输入；契约校验与派生处理单元承接后台处理；本仓不承接运行时异步事件消费，也不作为消息消费者存在。

3. 哪些存储或基础设施依赖对这些运行承载成立是必要的？

   回答：契约源码承载和契约发布快照承载是必要的正式承载；契约工具链执行环境是构建期基础设施依赖。数据库、缓存、消息队列和服务注册不属于本仓必要运行承载。

4. 哪些外部对象需要作为运行时对接边界出现？

   回答：下游契约消费边界可以作为外部对接边界出现，用于表达契约发布快照被消费；标准、草案和需求输入不应作为运行时外部对象画入本章主图。

5. 哪些对象虽然相关，但不应进入本章主图？

   回答：`L0-bus` 的事件投递容器、`L0-sdk` 的客户端封装、L1 业务服务、观测系统、归档系统、包注册表、CI 具体平台和源码目录都不应进入本章主图。

### 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 运行时定位 | 泛化为基础设施仓或构建脚本仓 | 明确为无在线运行时的契约来源仓 | 对齐职责边界 |
| 承载单元 | 直接写 GitHub / CI / registry | 抽象为契约变更入口、源码承载、校验派生处理、发布快照承载和工具链执行环境 | 避免绑定具体平台 |
| 存储依赖 | 容易写成数据库或注册表 | 只承认源码承载与发布快照承载 | 本仓不保存业务正文或运行状态 |
| 异步消费 | 容易误写成事件消费者 | 明确无运行时异步消费单元 | 避免侵入 `L0-bus` 边界 |
| 外部边界 | 容易把所有下游仓画进部署图 | 只保留下游契约消费边界 | 部署图不重写系统上下文 |

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A：为 `L0-core` 设计在线 API 服务、数据库和后台 worker | 形态熟悉 | 与契约来源仓定位冲突，会制造不存在的运行时职责 | 不采用 |
| 方案 B：按无在线运行时契约仓表达正式承载单元 | 边界清楚，能解释契约真相如何被承载与派生 | 需要说明这不是传统业务服务容器图 | 采用 |
| 方案 C：直接写“无部署架构”并跳过本章 | 简短 | 无法支撑后续数据所有权、依赖方向和技术选型 | 不采用 |

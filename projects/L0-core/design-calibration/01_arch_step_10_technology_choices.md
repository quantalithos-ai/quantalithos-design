### 3. SOP 问题回答

1. 当前采用哪些关键架构机制？

   回答：当前建议采用七类关键架构机制：结构化契约源码作为单一真相承载、正式承接层隔离外部输入与核心契约语义、版本化发布基线与只读发布快照、兼容性门禁与演进追溯、构建期校验 / 派生的后台承接、契约事实变化的可感知输出边界、外部正文引用而非吸收机制。

2. 每个机制解决什么问题？

   回答：这些机制分别解决契约真相分散、外部输入打穿核心、下游直接绑定核心真相、破坏性变更不可控、校验 / 派生挤入同步入口、契约变化无法被下游稳定感知、外部正文被错误吸收到本仓等架构问题。

3. 为什么不用其他方案？

   回答：不采用在线 API 服务 + 数据库作为核心真相，不采用 SDK 包或注册表状态作为契约真相，不采用下游仓局部 schema 作为共享契约来源，不采用事件总线实现来承接契约变化传播，也不把具体工具链产品名作为架构选型本体。

4. 每个选型带来什么代价或新风险？

   回答：这些机制会带来额外的边界设计、发布基线管理、快照延迟、兼容性审查、校验 / 派生失败挂起、下游消费旧快照以及引用失效暴露等成本。它们不是“免费解耦”，必须在概要、详细、测试和实施文档中继续落到可执行规则。

5. 哪些选型是当前阶段必要的，哪些暂不引入？

   回答：当前阶段必要的是保护契约真相、下游消费、演进兼容和变化感知的架构机制。暂不引入的是在线运行时服务、业务数据库、消息消费者、SDK 包发布中心、产品级注册表策略、三语言 binding 细节、具体 CI 命令和工具链参数。

### 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 选型表达 | 产品名 / 工具名 / 语言名清单 | 架构层技术机制 / 架构手段 | 关键技术选型必须说明解决的问题和代价 |
| 契约真相承载 | 工具链或生成物容易被视为真相 | 结构化契约源码和发布基线承载真相 | 防止派生产物反向拥有真相 |
| 外部输入 | 标准、草案、下游反馈可能直接影响核心 | 通过正式承接层隔离并审查 | 保护核心契约语义不被外部打穿 |
| 下游消费 | 下游直接依赖核心结构或包发布状态 | 通过只读发布快照与稳定引用消费 | 支撑演进空间和消费稳定性 |
| 校验与派生 | 同步入口或 CI 脚本细节 | 构建期后台延后承接机制 | 保持入口边界清晰，避免伪同步完成 |
| 变化传播 | 事件总线实现或事件目录 | 契约事实变化可感知输出边界 | 让下游感知变化，同时不侵入 `L0-bus` |

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A：把 proto / buf / CI / registry / binding 作为关键技术选型主体 | 工程直觉强，方便后续实施联想 | 过早绑定实现与工具链，无法说明架构边界保护机制 | 不采用 |
| 方案 B：把已经影响边界、数据、一致性和交互的技术机制作为选型主体 | 能解释为什么这些机制是架构决定，且保留后续设计空间 | 抽象度高，需要概要 / 详细设计继续落到结构和接口 | 采用 |
| 方案 C：完全不写技术选型，避免提前锁死 | 最小化架构承诺 | 无法解释发布基线、只读快照、校验派生、事实传播等机制为什么成立 | 不采用 |

### 7. 结构化中间产物

#### 7.1 关键技术机制表

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 | 说明 |
|---|---|---|---|---|
| 结构化契约源码作为单一真相承载 | 契约事实散落在草案、README、事件目录和下游实现中，容易形成多处解释 | `L0-core` 必须有可审查、可版本化、可追溯的契约真相承载，才能作为跨仓共享契约来源 | 需要持续维护源码组织、版本边界和变更记录，不能依赖临时文档或下游实现补齐 | 该机制决定契约真相如何被正式承载，属于架构层决定，不是单个文件格式选择。 |
| 正式承接层隔离外部输入与核心契约语义 | 标准、草案、评审结论和下游反馈可能直接打穿核心契约语义 | 外部输入必须先进入正式接缝，再转化为可审查的契约变更，避免外部来源直接改写真相 | 增加承接判断和审查成本，输入不足时必须挂起或拒绝进入 | 该机制保护核心语义边界，承接 Step 7 的依赖方向红线。 |
| 版本化发布基线与只读发布快照 | 下游若直接绑定核心真相或派生产物，会反向约束核心演进 | 发布基线表示已收口的契约状态，发布快照作为下游稳定消费面，二者隔离真相与消费 | 增加基线管理、快照刷新、旧快照保留和消费侧理解成本 | 该机制同时影响数据所有权、一致性和交互边界，不是简单发布产物。 |
| 兼容性门禁与演进追溯机制 | 新增、废弃、破坏性变化若无门禁，会让下游承担不可解释的契约漂移 | 高影响变化必须在正式收口前经过兼容性判断，并保留追溯依据 | 增加评审与追溯材料维护成本，可能延缓契约变更速度 | 该机制支撑 `L0-core` 作为低变化率底座成立，不能后移为普通测试脚本。 |
| 构建期校验 / 派生的后台承接机制 | 契约校验、兼容性辅助判断和派生快照可能耗时，若塞进同步入口会制造伪同步完成 | 后台延后承接允许校验、派生、报告摘要和快照刷新在正式入口之外收敛 | 会引入挂起、失败、旧快照保留和延迟一致性解释成本 | 该机制承接 Step 6 的无在线运行时和 Step 9 的后台交互边界。 |
| 契约事实变化的可感知输出边界 | 下游需要知道契约变化，但 `L0-core` 不应承担事件总线投递实现 | 将契约变化、发布基线和兼容性状态作为可感知事实输出，而不是实现 publish / subscribe / ack | 需要明确未传播、待消费和消费失败状态，避免被误解为全下游同步完成 | 该机制影响跨仓协作主链，但必须与 `L0-bus` 投递职责保持边界。 |
| 外部正文引用而非吸收机制 | 标准正文、ADR 正文、业务正文或事件实例正文被复制进本仓，会污染数据所有权 | 本仓只保存引用关系和追溯入口，不拥有外部正文真相 | 引用失效时必须显式暴露，不能通过复制正文掩盖失效 | 该机制保护 Step 8 的数据边界，防止引用关系变成正文所有权。 |

#### 7.2 简化对照表

| 当前采用 | 当前不采用 | 边界原因 |
|---|---|---|
| 结构化契约源码 + 发布基线承载真相 | 在线 API 服务 + 数据库承载核心真相 | `L0-core` 不是运行时业务服务，当前主线是契约来源仓。 |
| 只读发布快照供下游消费 | 下游直接读取和绑定核心真相结构 | 保护核心演进空间，避免下游反向拥有真相。 |

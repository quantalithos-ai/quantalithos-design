### 3. SOP 问题回答

1. 当前阶段做到哪里才算足够？

   回答：当前阶段只要完成 `L0-core` 作为契约来源仓的架构边界：契约真相归属、发布基线 / 快照消费面、后台校验 / 派生、变化可感知输出、数据不越界和依赖方向红线，就足以支撑后续概要与详细设计。

2. 第一批必须守住哪些结构？

   回答：必须守住无在线运行时、核心契约语义不被外部输入打穿、下游只能消费发布基线 / 快照、派生产物不反向成为真相、外部正文不进入本仓、同步 / 异步 / 后台承接边界清晰。

3. 哪些能力或约束留到后续阶段演进？

   回答：具体契约源码目录、字段策略、生成器配置、兼容性检查实现、快照导出格式、三语言 binding、发布渠道、可视化、消费关系投影、治理联动和更强恢复能力均后移。

4. 哪些设计债务当前可接受，哪些不可接受？

   回答：可接受债务是具体实现形态未定，但边界和主线已定；不可接受债务是重新让工具链、下游仓、外部正文、事件总线或 SDK 发布状态反向定义契约真相。

5. 未来哪些触发条件会迫使架构调整？

   回答：当下游消费规模导致快照和派生延迟不可接受、兼容性变化频繁到手工审查无法承接、引用失效影响正式追溯、契约变化传播需要强消费确认、或多仓实现出现 schema drift 时，必须进入下一阶段演进。

### 4. 当前文档问题诊断

| 位置 | 当前问题 | 影响 |

#### 7.1 演进路线表

| 阶段 | 当前目标 / 范围 | 当前可接受债务 | 后续演进项 | 触发条件 | 说明 |
|---|---|---|---|---|---|
| 当前主线成立阶段 | 稳定契约来源仓边界、数据归属、发布基线 / 快照、依赖方向和关键交互 | 具体字段、目录、生成器、CI 命令、发布渠道暂不锁死 | 在概要 / 详细设计中映射为具体结构、接口和实现契约 | 需要进入代码实现前 | 当前阶段目标是架构基线成立，不是完成所有工程实现。 |
| 结构落地阶段 | 将架构机制落到契约源码组织、接口轮廓、校验 / 派生流程和快照形态 | 自动化深度、可视化和跨仓消费投影可暂缓 | 补齐兼容性检查、快照导出、消费关系视图和实现约束 | 概要 / 详细设计开始承接代码实现时 | 该阶段解决“如何写代码”，但不得改变当前架构边界。 |

| 跨仓治理联动阶段 | 将高影响变化、破坏性变化、引用失效和下游反馈纳入更强治理闭环 | 不要求 `L0-core` 承担治理系统本体 | 补强治理引用、追溯证据、消费影响分析和变更裁决联动 | 多仓 schema drift、兼容性争议或引用失效频繁出现时 | 演进方向是强化接缝和追溯，不是吸收相邻仓职责。 |

#### 7.2 触发条件小表

| 触发条件 | 必须演进的结构面 |
|---|---|
| 下游仓开始围绕不同契约解释实现 | 契约真相、发布基线、消费快照 |
| 兼容性变化频率超过人工审查可承接范围 | 兼容性门禁、演进追溯、校验报告 |
| 派生或快照延迟影响多仓集成 | 后台校验 / 派生、快照刷新、可观测性 |
| 引用失效影响正式追溯 | 引用关系、审计追溯、外部接缝 |
| 契约变化传播需要下游明确确认 | 可感知输出边界、消费状态视图、治理联动 |

#### 7.3 阶段边界说明短文

```text
当前阶段不是“所有工具链和发布体验全做完”才算成立，而是先让 `L0-core` 的架构边界和主线判断稳定。
具体实现形态可以作为可接受债务后移，但不能留下会打穿契约真相、下游消费或数据所有权的结构债务。
后续演进必须由明确的边界压力、规模压力、兼容性压力或漂移风险触发，不能把愿望池写成路线图。
```

## 3. SOP 问题回答

### 3.1 本次概要设计最主要要把哪些结构说清？

回答：

本次概要设计最主要要把以下结构说清，并且必须说到可以继续写详细设计的粒度：

| 结构 | 本章必须说清什么 | 交付给详细设计的结果 |
|---|---|---|
| 代码主体框架 | L0-core 的实现主体会分成哪些代码主体、实现层和模块组 | `02-概要设计.md` 可以据此展开 crate / module / file tree |
| 主要组成部分 | 哪些部分负责契约真相、发布基线、快照、引用、事实输出、后台承接和查询 | `03` 可以据此按功能模块继续展开实现契约 |
| 关键对象轮廓 | ContractDefinition、ContractScope、ReleaseBaseline、ReleaseSnapshot、CompatibilityReport、Reference、FactRecord 等对象的骨架 | `03` 可以据此展开 struct / enum / value object |
| API / 接口骨架 | Change / Query / Event / Operations Job 的概要级接口族和边界 | `03` 可以据此展开协议 schema 和逐接口处理流 |
| 关键处理流 | 契约范围收束、契约发布、快照派生、事实输出、引用失效、下游消费恢复等主流程 | `03` 可以据此展开函数级调用链、事务和错误分支 |
| 状态定义与状态流转 | 契约定义、发布基线、发布快照、事实输出、引用和任务状态边界 | `03` 可以据此展开状态转换矩阵和非法转换处理 |
| 详细设计承接清单 | 哪些对象、接口、流和状态必须继续往下写 | `03` 的 Step 1 输入边界可以直接使用 |

### 3.2 这一轮概要设计应停在什么深度，才算足够支撑进入详细设计？

回答：

这一轮概要设计应停在“代码主体骨架层”。

也就是说，本章要回答的是：

```text
这个仓会有哪些正式对象
这些对象分别属于哪个主要组成部分
这些对象的骨架长什么样
这些接口族的轮廓是什么
这些关键流程怎么串起来
这些状态怎么流转
```

但不能回答到：

```text
完整 Rust struct 字段全集
完整 Rust 函数实现
完整 HTTP / RPC / Event schema
SQL / DDL / 索引 / 事务实现
CI 命令、测试用例、实施步骤
```

换句话说，02 的职责不是“先把代码写出来”，而是“先把代码主体边界固定住”，让 03 能按模块继续展开实现契约。

### 3.3 哪些内容属于本次概要设计范围？

回答：

本次概要设计范围应围绕“契约来源仓如何被组织成可实现结构”展开，具体包括：

| 范围类别 | 具体内容 | 为什么属于本章 |
|---|---|---|
| 契约真相组织 | 共享契约定义、范围、版本、兼容性、演进记录、发布基线 | 这是 L0-core 的核心真相边界 |
| 发布与消费基线 | 发布快照、派生产物、只读消费面、事实输出面 | 这是下游消费和稳定引用的基础 |
| 引用与追溯 | 标准引用、评审引用、下游消费引用、失效引用状态 | 这是本仓作为来源仓必须维护的引用边界 |
| 查询与解析 | 获取、列举、版本读取、追踪、比较、解析视图配置 | 这是下游稳定消费的重要能力面 |
| 后台承接 | 校验、派生、快照刷新、事实重算、引用刷新 | 这是契约真相与消费面之间的结构性缓冲 |
| P1 承接 | MethodPlugin、MethodConfiguration、marketplace metadata 的后置边界 | 需要明确位置，但不阻塞 P0 主链 |
| 下游边界 | `L0-bus`、`L0-sdk`、L1、L2、L4 的职责隔离 | 这是本章要守住的非范围红线 |

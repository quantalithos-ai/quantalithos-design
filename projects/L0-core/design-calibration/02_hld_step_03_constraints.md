## 3. SOP 问题回答

### 3.1 哪些约束会直接影响本仓对象、接口、处理流或状态机设计？

回答：

会直接影响本章结构的约束，必须按“可指导后续对象和接口判断”的方式写出来。

| 约束 | 直接影响的设计面 | 为什么必须进入概要设计 |
|---|---|---|
| Definition / Use 必须分离 | 关键对象、数据归属、接口边界 | 否则会把下游使用真相写成本仓真相 |
| P0 / P1 必须分离 | 主要组成部分、接口优先级、状态流转 | 否则 P1 组装能力会反向拖慢 P0 发布主链 |
| 契约真相必须由 L0-core 拥有 | 代码主体框架、对象归属、数据边界 | 否则 L0-core 无法作为来源仓成立 |
| 发布必须经过 approved gate | 发布流、状态机、异常边界 | 否则发布主链会失去治理门禁 |
| 已发布内容不可原地改写 | 生命周期、版本、supersede、audit | 否则状态机无法表达正式演进 |
| fingerprint 必须由 canonical 内容生成 | 发布、重算、漂移对比、事实输出 | 否则下游消费面无法稳定判断变化 |
| 发布成功必须同时形成 audit 与 outbox | 发布流、事实输出、恢复路径 | 否则只能看见“改了内容”，看不见“正式成立” |
| 下游同步采用最终一致 | 接口骨架、后台承接、恢复机制 | 否则会把跨仓协作写成强事务 |
| Snapshot 是下游恢复兜底入口 | Query、恢复处理流、异常边界 | 否则错过事件后无法恢复消费基线 |
| ViewProfile 必须服务端解析 | Query、状态机、UI / console 边界 | 否则长期视图规则会散落到前端本地 |
| 引用必须可校验且可追溯 | 对象、关系边界、发布校验 | 否则外部标准和评审引用会失去治理价值 |
| P1 能力不得污染 P0 主链 | 主要组成部分、目标范围、承接清单 | 否则 Step 2 的范围口径会失效 |

### 3.2 哪些约束来自需求文档，哪些约束来自架构设计或全局设计？

回答：

| 来源 | 约束示例 | 在本章如何处理 |
|---|---|---|
| 需求文档 | L0-core 是共享契约来源仓；P0 / P1 分界；发布门禁；下游消费派生；ViewProfile / 事实输出 / 引用追溯等功能需求 | 转成对象、接口、流程和状态机必须遵守的结构性约束 |
| 架构设计 | 契约来源仓主线、发布基线 / 只读快照、后台承接、可感知事实输出、Definition / Use 分离 | 继承为本章的边界输入，不重新论证 |
| 全局设计 / 标准对齐 | SPEM 的定义 / 使用分离、标准引用、审计线索、责任边界 | 只保留影响命名、边界、引用和审计的约束，不展开标准正文 |

### 3.3 哪些边界如果不先写清，后续最容易串到相邻仓或详细设计？

回答：

最容易串仓的边界必须单独写出来。

| 边界 | 如果不写清会怎样 |
|---|---|
| ContractDefinition vs ContractUse | 会把定义真相和使用真相混成一个对象，导致来源仓职责失焦 |
| ContractDefinition vs ContractSnapshot | 会把快照、派生产物和正式真相混淆 |
| ReleaseBaseline vs DerivedSnapshot | 会把发布基线误当成缓存或派生物 |
| Reference vs正文 | 会把标准、评审、ADR、下游消费关系误写成正文真相 |
| Query / Snapshot / Replay | 会把只读消费、恢复兜底和事实传播混成一条线 |
| ViewProfile vs UI session state | 会把长期视图规则和前端临时状态混成一类对象 |
| P0 mainline vs P1 add-on | 会让插件组装和元数据能力反向影响 P0 主链 |

最容易提前写进详细设计的边界也要明确拒绝。

| 边界 | 本步处理方式 |
|---|---|
| 数据库表、索引、事务实现 | 只保留“必须可发布、必须可恢复、必须可追溯”的结构约束，不写 DDL |
| 完整协议 schema | 只保留 Command / Query / Event / Operations Job 的骨架约束，不写字段级协议 |
| 错误码和重试算法 | 只保留必须拒绝、必须挂起、必须恢复、必须重放的结构位置，不写完整错误表 |
| 容量规划数值 | 不作为本章主约束，只作为后续非功能或风险输入 |

### 3.4 哪些约束只是泛化工程原则，不应进入本章？

回答：

以下内容不应进入新版 §3 主约束表。

| 不进入本章的内容 | 原因 |
|---|---|
| “要高可用”“要高性能”“要可扩展”这类泛化原则 | 不能直接指导对象、接口、处理流或状态机设计 |
| 具体数据库索引、分区、锁策略 | 属于详细设计实现契约 |
| 具体缓存、搜索引擎、读模型选型 | 属于详细设计或可变实现策略 |
| 具体 QPS / 记录数容量目标 | 不是概要设计主约束，应后移到非功能、风险或实施假设 |
| 完整部署拓扑和资源配额 | 属于部署 / 实施计划 |
| P1 plugin dependency DAG 算法 | P1 后置，不应影响 P0 约束主表 |

## 7. 结构化中间产物

### 7.1 约束条件主表

| 约束 | 说明 |
|---|---|
| 契约真相必须由 `L0-core` 拥有 | 契约定义、范围、版本、兼容状态、演进记录、发布基线是本仓真相 |
| Definition / Use 必须分离 | 本仓只拥有方法定义真相，不得保存下游使用真相或运行实例真相 |
| P0 / P1 必须分离 | P0 先完成定义发布、版本、fingerprint、audit、outbox、snapshot 和下游同步闭环；P1 不得成为 P0 前置条件 |
| P0 范围必须稳定 | 概要设计对象、接口和流程必须覆盖当前收稳的 P0 范围，不得把未收稳的 P1 能力写成主链前提 |
| 下游 Use truth 不得写入本仓 | ProcessInstance、WorkItem、Artifact instance、policy enforce result、UI session state 等只能由对应下游仓拥有 |
| published 核心字段不可原地修改 | 已发布内容变更必须通过新版本、supersede、version、fingerprint 和 audit trace 表达 |
| publish 必须经过 approved gate | Publish 处理流必须携带 approved_gate_ref，并记录 actor_ref、时间、原因和 gate 结果 |
| fingerprint 必须由 canonical 内容生成 | fingerprint 是 drift、幂等、snapshot 和事件消费的核心语义标识，不得由下游猜测或自然语言描述替代 |
| 发布成功必须写 audit 与 outbox | content state、version、fingerprint、audit record、outbox event 必须在发布主链中一起成立 |
| 跨仓同步采用最终一致 | 下游通过 event、snapshot query、replay / resync 恢复索引，不得要求跨仓强事务 |
| Snapshot 是下游恢复兜底入口 | 下游错过事件、重建索引或校验 fingerprint 时，必须能拉取 Definition Snapshot |
| ViewProfile 必须服务端解析 | UI / console 通过 ResolveViewProfile 获取 active ViewProfile 和 fingerprint，生产环境未匹配默认 deny |
| 定义间引用必须可校验 | RoleDefinition、TaskDefinition、WorkProductDefinition、ProcessTemplateDef 等引用关系在发布前必须指向允许引用的定义版本 |
| P1 能力不得污染 P0 主链 | MethodPlugin、MethodConfiguration、marketplace metadata、variability、dependency DAG 只保留位置和边界，不展开为 P0 核心对象和主流程 |

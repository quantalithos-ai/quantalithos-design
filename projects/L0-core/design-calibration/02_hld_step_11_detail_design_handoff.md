## 3. SOP 问题回答

### 3.1 哪些代码主体框架已经由概要设计收稳,详细设计不能重新发明?

回答:

| 已由概要设计收稳 | 详细设计继续展开 |
|---|---|
| `L0-core` 的实现分层映射 | 具体目录、模块、文件和 trait / struct 落点 |
| 6 个业务主要组成部分 + 1 个支撑主体集合 | 每个主体的具体 service / port / repository 组织方式 |
| 关键对象族与对象卡片 | 具体字段集合、完整方法签名、内部不变量和 trait 实现 |
| Command / Query / Event / Job 骨架 | 请求 / 响应 DTO、协议映射、错误码、序列化 / 反序列化细节 |
| 关键处理流骨架 | 函数调用链、事务边界、 outbox 顺序、重试和补偿 |
| 主线状态族与允许 / 禁止迁移 | 具体状态码、状态持久化、状态守卫实现 |
| 关键异常和边界场景 | 错误码、失败恢复、重试策略、补偿脚本 |

### 3.2 哪些对象、接口、处理流和状态机已经成为详细设计输入?

回答:

详细设计必须直接承接以下输入:

- 代码主体框架
- 主要组成部分与职责边界
- `ContractDefinition`、`ContractLifecycle`、`ContractReleaseBaseline`、`ContractReleaseSnapshot`、`ContractFactRecord`、`DownstreamConsumptionRef`、`ContractReadModel`、`ContractTraceProjection`、`CompatibilityTraceIndex`、`ContractPackageLifecycle` 等关键对象族
- `CreateContractDraft`、`UpdateContractDraft`、`SubmitContractForReview`、`PublishContractBaseline`、`UpdateContractLifecycle`、`GetContractDefinition`、`TraceContractEvolution`、`ValidateContractChangeJob`、`DeriveReleaseSnapshotJob`、`RebuildContractIndexJob`、`RecalculateFingerprintJob`、`PublishContractFactJob` 等接口
- 草稿写路径、评审提交与基线发布路径、生命周期迁移路径、通用读路径、追溯读路径、后台校验 / 复算路径、快照派生路径、索引重建路径、事实发布路径
- `ContractLifecycle`、`CompatibilityStatus`、`ContractReleaseBaseline`、`ContractReleaseSnapshot`、`ContractFactRecord`、`DownstreamConsumptionRef`、`ContractReadModel`、`ContractTraceProjection`、`CompatibilityTraceIndex`、`ContractPackageLifecycle` 等状态族
- 幂等冲突、非法迁移、兼容性不通过、快照派生失败、读面 stale、事实发布失败、引用失效等异常边界

### 3.3 详细设计应继续展开哪些字段、协议、函数、事务、异常和测试内容?

回答:

| 详细设计继续展开 | 说明 |
|---|---|
| 具体字段定义 | 把 Step 6 的字段骨架展开成完整 Rust struct / enum / value object 字段 |
| 完整函数签名 | 把 Step 6 / Step 7 / Step 8 的骨架展开成完整方法签名和返回类型 |
| 协议与 DTO | 把 Command / Query / Event / Job 骨架展开成请求 / 响应 / envelope / metadata DTO |
| 事务边界 | 把 Step 8 的处理流展开成具体事务内外边界 |
| outbox / projection 细节 | 把 Step 8 / Step 9 的事实输出和读面重建展开成具体实现顺序 |
| 错误处理 | 把 Step 10 的异常轮廓展开成错误码、重试、补偿和恢复策略 |
| 测试矩阵 | 为接口、状态迁移、异常路径、读写一致性和 outbox / projection 设计测试 |

### 3.4 如果详细设计发现主语需要变更,应回退到哪里修正?

回答:

| 发现的问题 | 应回退的 Step | 原因 |
|---|---|---|
| 代码主体框架不对 | Step 4 | 这是实现分层和主语映射的起点 |
| 主要组成部分不对 | Step 5 | 组成部分边界决定后续对象和接口归属 |
| 关键对象要改名或增删 | Step 6 | 对象是后续接口、处理流和状态机的主语 |
| 接口名或输入 / 输出骨架要改 | Step 7 | 接口骨架已经是详细设计输入 |
| 函数数据流需要改 | Step 8 | 处理流决定调用链和事务边界 |
| 状态集合或迁移要改 | Step 9 | 状态机一旦变化,会影响发布与传播语义 |
| 异常语义要改 | Step 10 | 异常轮廓决定错误处理和恢复边界 |

### 3.5 哪些未闭环内容不能写入承接清单,而应进入风险与待确认事项?

回答:

- 仍然没有收稳的新对象名。
- 仍然没有收稳的新接口名。
- 仍然没有收稳的新状态名。
- 仍然没有收稳的新处理流边界。
- 仍然没有收稳的异常语义。
- 任何会改变 Step 4 ~ Step 10 既有结论的内容。

## 4. 当前文档问题诊断

| 位置 | 当前问题 | 影响 |
|---|---|---|
| 旧版 Step 11 缺位 | 原 `02` 没有把概要设计的收口项显式列给详细设计 | 详细设计容易在边界上重新发明主语 |
| 旧版承接 | 没有回退规则 | 详细设计发现问题后容易直接改实现草图 |
| 旧版展开边界 | 不清楚哪些内容应留给详细设计,哪些必须继续回到概要设计 | 会让概要与详细的职责边界模糊 |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 承接方式 | 没有显式清单 | 把已收稳内容逐项列为详细设计输入 | 让详细设计不再重新发明主语 |
| 回退规则 | 没有明确回退点 | 每类问题对应具体 Step 回退 | 保证修改发生在正确层级 |
| 展开粒度 | 不明确 | 明确字段、协议、函数、事务、异常和测试由详细设计继续展开 | 防止概要设计越界 |

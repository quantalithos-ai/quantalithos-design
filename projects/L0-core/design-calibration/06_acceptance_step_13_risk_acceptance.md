## 3. SOP 问题回答

1. 哪些风险可以支持有条件通过?

   回答：真实 L0-bus 投递未覆盖、真实下游仓库联调未覆盖、真实 secret provider / KMS 未覆盖、完整性能容量压测未覆盖、CI artifact 物理存储未固定、EV-NFR / nightly 未作为 release gate 必需时的未关闭风险,可以在 P0 门禁全部通过且无 S/A 缺陷、无一票否决时支持“有条件通过”。

2. 哪些风险不能接受?

   回答：任一 AC-BLOCKER、S/A 缺陷、P0 用例失败、P0 EV 缺失、release gate 失败、raw secret 或禁止正文泄露、truth / audit / outbox 半提交、audit 静默失败、失败伪成功、引用 fail open 都不能风险接受。

3. 每个风险的接受人是谁?

   回答：风险接受必须填写接受人。当前设计阶段只能给出角色占位,例如架构评审者、安全负责人、测试负责人、项目负责人。送验时必须替换为具体人员或明确授权角色;没有接受人的风险不能作为有条件通过依据。

4. 后续动作和截止时间是什么?

   回答：每个风险必须有后续动作和截止时间。动作应同步到相邻仓测试、系统级 E2E、安全设计、运维手册、实施计划或问题记录。截止时间不能写“后续处理”,必须绑定迭代、里程碑或验收前置节点。

5. 风险是否需要同步到实施计划或问题记录?

   回答：需要。所有被接受风险必须同步到 `07-实施计划.md`、相邻仓测试方案、系统级测试计划或 issue / risk register。06 只定义验收裁决口径,不替代后续执行跟踪。

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 风险来源 | 旧 shared primitive 演进 | 05 残余风险 + Step 9 未覆盖专项 + Step 12 B/C 缺陷 | 对齐新版测试和验收链 |
| 风险字段 | 风险 / 影响 / 处理策略 / 接受人 | 风险、影响、接受理由、后续动作、责任人、接受人、截止时间 | 满足 SOP |
| 可接受范围 | 未明确 | 只允许 P1/P2 或 B/C 非阻断风险 | 保护 P0 门禁 |

| 后续跟踪 | 未明确 | 必须同步实施计划、相邻仓或 issue | 防止风险失联 |

## 6. 验收裁决取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 不允许任何残余风险 | 最严格 | 会让真实下游未就绪等非本仓事项阻塞 L0-core 独立验收 | 不采用 |
| B. 所有未完成事项都可风险接受 | 推进快 | 会覆盖 P0 和一票否决 | 不采用 |
| C. 只允许非 P0 / 非否决 / 非 S/A 风险接受,且必须有接受人、期限和后续动作 | 边界清楚,可追踪 | 需要维护风险登记 | 采用 |

## 7. 结构化中间产物

### 7.1 风险接受表

| 风险 / 遗留项 | 影响 | 接受理由 | 后续动作 | 责任人 | 接受人 | 截止时间 |
|---|---|---|---|---|---|---|
| 真实 L0-bus 投递未覆盖 | 真实 publish / subscribe / ack / retry / dead-letter 问题不会在本仓暴露 | 本轮 P0 只验 outbox / CloudEvent / relay boundary | 转入 L0-bus 测试方案和系统级 E2E | L0-bus 负责人 | 架构评审者 | L0-bus 验收前 |
| 真实下游仓库联调未覆盖 | 下游消费适配问题可能后续暴露 | L0-core 不拥有下游业务实现,本轮只验契约输出接缝 | 下游仓建立 contract consume test | 下游仓负责人 | 架构评审者 | 对应下游仓验收前 |
| 真实 secret provider / KMS 未覆盖 | secret ref 轮换、权限、可用性问题后移 | P0 不实现 secret provider,只验 raw secret 禁止和 fail closed | 安全设计 / 运维手册 / secret provider 测试承接 | 安全负责人 | 安全负责人 | 安全接入验收前 |
| 完整性能容量压测未覆盖 | 无法证明生产规模下的容量上限 | 当前无生产负载模型,只能形成 baseline | 实施后补 benchmark baseline 和 release gate 阈值 | 测试负责人 | 项目负责人 | 首个 release candidate 前 |
| CI artifact 物理存储未固定 | EV 逻辑路径已定义,实际归档路径可能漂移 | 当前设计阶段无实现仓 CI | `07-实施计划.md` 固定 artifact 存储和索引规则 | 测试负责人 | 项目负责人 | 实施计划冻结前 |
| EV-NFR / EV-NIGHTLY 未作为 release gate 必需时的未关闭项 | 故障恢复或性能退化可能后续发现 | 当前仅作为风险证据,不默认阻断发布 | 标记是否进入 release gate;未进入则登记风险 | 测试负责人 | 项目负责人 | 送验前 |
| B/C 级非阻断缺陷 | 可能影响体验、报告或 P1 能力 | 不影响 P0、release gate 和一票否决 | 进入缺陷跟踪,补 owner、期限和复验方式 | 缺陷 owner | 验收负责人 | 下一迭代或指定日期 |

### 7.2 不可风险接受表

| 风险 / 问题 | 处理口径 |
|---|---|
| 任一 AC-BLOCKER | 不通过,修复并复验 |
| S 级缺陷 | 不通过,不得风险接受 |
| A 级缺陷 | 不通过,不得风险接受 |
| P0 用例失败 | 不通过 |
| P0 EV 缺失或证据泄露 | 不通过或送验不成立 |
| release gate 失败 | 不通过 |
| raw secret / 禁止正文泄露 | 一票否决 |
| truth / audit / outbox 半提交 | 一票否决 |

### 7.3 风险同步要求

| 同步目标 | 同步内容 |
|---|---|
| `07-实施计划.md` | artifact 归档、baseline 生成、release gate 补充动作 |
| 相邻仓测试方案 | L0-bus、L0-sdk、L1+ 的真实消费和联调风险 |
| 安全设计 / 运维手册 | secret provider / KMS / redaction / 凭据管理风险 |
| issue / risk register | B/C 缺陷、nightly 风险、性能容量风险 |

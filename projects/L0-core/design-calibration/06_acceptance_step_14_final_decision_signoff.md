## 3. SOP 问题回答

1. 结论只能有哪些取值?

   回答：最终结论只能是“通过”“有条件通过”“不通过”。不得使用“基本通过”“原则上通过”“大体没问题”“后面补一下”等模糊结论。

2. 何时允许进入下一阶段?

   回答：通过或有条件通过时可以进入下一阶段。通过要求所有 P0 门禁通过、无 S/A 缺陷、无一票否决、证据完整、风险已关闭或可接受。有条件通过要求 P0 主线成立、无一票否决、无 S/A 缺陷,且所有遗留风险都有接受人、期限和后续动作。

3. 何时允许发布准备?

   回答：只有通过或满足 release gate 条件的有条件通过才允许发布准备。若 release gate 证据缺失、EV-E2E-001 失败、P0 EV 缺失、S/A 缺陷未关闭或一票否决触发,不得进入发布准备。

4. 哪些角色必须签署?

   回答：至少需要验收负责人、项目负责人、架构评审者、测试负责人和安全负责人签署。若存在被接受的相邻仓风险,相关相邻仓负责人也应签署或确认承接。若签署人缺失,必须说明缺失影响;不能默认视为通过。

5. 签署是否代表风险接受?

   回答：签署本身不自动代表接受全部风险。只有在签署表中明确“接受风险范围”并关联 Step 13 风险项时,才代表该角色接受对应风险。否则签署只表示对验收结论或职责范围的确认。

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 结论取值 | 占位 | 通过 / 有条件通过 / 不通过三值规则 | 对齐书写规范 |
| 有条件通过 | 未定义 | P0 成立、无否决、无 S/A、风险被接受 | 支撑风险治理 |
| 发布准备 | 未定义 | release gate 满足才允许 | 防止条件通过误发布 |
| 签署 | 泛化角色 | 明确角色、责任、结论、风险接受范围、日期 | 可审计 |
| 风险接受 | 与签署关系不清 | 签署不自动接受风险,必须显式关联风险项 | 防止责任漂移 |

## 6. 验收裁决取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 只保留最终一句结论 | 简洁 | 无法审计为什么通过或不通过 | 不采用 |
| B. 有条件通过等同于可发布 | 推进快 | 风险可能未关闭就进入发布 | 不采用 |
| C. 三值结论 + 发布准备条件 + 签署责任分离 | 裁决清晰,风险可追踪 | 文档更严格 | 采用 |

## 7. 结构化中间产物

### 7.1 结论规则表

| 维度 | 结论 | 说明 |
|---|---|---|
| 全部 P0 门禁通过、无 S/A 缺陷、无一票否决、证据完整、无未接受风险 | 通过 | 可进入下一阶段;若 release gate 已满足,可进入发布准备 |
| P0 主线成立、无 S/A 缺陷、无一票否决、证据完整,但存在已接受 P1/P2 或 B/C 风险 | 有条件通过 | 可进入下一阶段;是否进入发布准备取决于 release gate 和风险范围 |
| 任一 P0 门禁失败、任一 S/A 缺陷未关闭、任一 AC-BLOCKER 触发、P0 EV 缺失、release gate 必需项失败 | 不通过 | 必须修复并复验后重新裁决 |
| 送验基线、run_id、commit、artifact 或证据索引缺失到无法复查 | 不通过 / 送验不成立 | 不得用口头确认替代 |

### 7.4 签署缺失处理

| 缺失项 | 处理 |
|---|---|
| 验收负责人未签署 | 不能形成最终结论 |
| 测试负责人未签署 | 不能确认证据和缺陷状态 |
| 安全负责人未签署且存在安全 / secret / redaction 风险 | 不能给出通过或有条件通过 |
| 架构评审者未签署且存在跨仓 / 数据边界风险 | 不能给出通过或有条件通过 |
| 相邻仓负责人未签署但风险已指定其承接 | 风险接受不成立 |

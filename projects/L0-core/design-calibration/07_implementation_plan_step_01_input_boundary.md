### 3. SOP 问题回答

1. 当前仓是否已经具备完整的 00 / 01 / 02 / 03 / 05 / 06 文档。

   回答：已经具备,并且额外具备 04-配置设计。当前实施计划输入应采用 `00~06` 全链路文档,其中 `04-配置设计.md` 位于详细设计与测试方案之间,必须纳入实施计划输入。

2. 哪些上游文档版本是本轮实施计划的基线。

   回答：本轮基线为 `00-需求文档.md` v0.2.0、`01-架构设计.md` v0.2.0、`02-概要设计.md` v0.2.0、`03-详细设计.md` v0.2.0、`04-配置设计.md` v0.1.0、`05-测试方案.md` v0.2.0、`06-验收标准.md` v0.2.0。这些文档虽然状态仍标为 Draft,但均已有对应 SOP 中间产物链路,本轮按当前已确认校准基线使用。

3. 详细设计是否已经足以支持 1:1 实现。

   回答：P0 范围足以支持实施计划制定。`03-详细设计.md` 已给出 workspace 多 crate 布局、模块实现契约、对象契约、trait / port / adapter、协议契约、函数流、状态机、持久化事务、一致性、错误恢复、并发幂等、配置引用、观测审计和测试切口。实施计划不得重写这些契约,只应把它们转成阶段、代码批次、任务顺序和提交边界。实际实现仓路径、CI 命令、artifact 物理路径和运行环境属于后续 Step 3 / Step 8 / Step 11 固定项,不阻塞 Step 1。

4. 测试方案和验收标准是否足以定义阶段门禁。

   回答：足以作为 P0 阶段门禁输入。`05-测试方案.md` 已定义测试对象、测试切口、测试分层、用例矩阵、测试数据、配置矩阵、自动化门禁、证据归档、回归策略和残余风险。`06-验收标准.md` 已定义 P0 功能门禁、架构红线、接口事件、一致性、非功能、证据、一票否决、缺陷分级、风险接受和最终结论口径。实施计划应把这些门禁嵌入每个阶段,不能把测试和验收留到最后。

5. 是否存在上游文档之间的冲突。

   回答：`00~06` 正式链路之间没有阻塞性冲突。需要注意的是 `projects/L0-core/README.md` 仍保留旧口径,例如 26 仓、proto 目录和 buf 配置主线等旧表达。该 README 不应作为本轮实施计划基线;实施计划应以新版 `00~06` 为准,并在 Step 3 阅读清单中提示实施者不要把 README 旧口径当作实现事实。

6. 哪些缺口会阻塞实施计划,哪些缺口可以记录为风险继续推进。

   回答：当前没有阻塞 Step 2 的缺口。非阻塞风险包括: L0-core 专项 ADR 仍待补、实现仓实际目录可能不在当前 design 仓、目标实现仓 CI 命令和 artifact 物理路径未固定、真实 L0-bus / L0-sdk / L1+ 联调不作为 P0 前置、README 旧口径可能误导实施者。这些应分别在 Step 3、Step 8、Step 9、Step 11 中继续收束。

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 只以 `03-详细设计.md` 制定实施计划 | 直接贴近代码实现 | 容易丢失需求、架构红线、配置、测试和验收门禁 | 不采用 |
| 以 `00~06` 全链路作为实施输入 | 能保持需求、架构、概要、详细、配置、测试、验收一致 | 需要在实施计划中维护更多追溯关系 | 采用 |
| 等 ADR、实现仓路径、CI 命令全部补齐后再开始实施计划 | 输入最完整 | 会阻塞阶段拆分和交付路径讨论,且这些更适合后续 Step 收束 | 不采用 |
| 当前先固定基线,把未定实现环境作为后续风险 / 前置条件处理 | 不阻塞 SOP 推进,同时保留缺口 | 后续 Step 必须认真收束,不能跳过 | 采用 |

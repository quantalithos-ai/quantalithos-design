## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 有 26 仓,并且同时面向:
- 内部仓之间的互调
- L2 runtime 的 Python 生态
- L5 UI 的 TypeScript 生态
- 第三方 / 企业开发者的外部集成

如果没有统一 SDK:
- 各语言各自封装一套 core proto + bus 协议
- 文档 / 类型 / 错误处理 / trace 注入会飘
- 第三方开发者接入门槛高

L0-sdk 的目标是:在 Rust / Python / TypeScript 三种语言里,**暴露一致的高层 API**,屏蔽 proto / CloudEvent / Trace / 认证等低层细节。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点描述 |
|---|---|---|
| sdk 草案 | `architecture/sdk-draft/README.md` 983 行 | 只有设计,无代码 |
| proto binding | 由 core 仓未来生成 | 三语言高层包装未定义 |
| bus 语义 | bus-draft 925 行 | SDK 层如何暴露 publish/subscribe 未实现 |
| 认证模型 | 文档中提到 token / mTLS / secret redaction | 三语言统一接口未定 |
| 示例 | 无真实 examples | 第三方难以 10 分钟上手 |

### 2.3 为什么要做(量化依据)

- 没有 SDK,每个 UI / runtime / 第三方都要自己写一层包装 → 25 仓重复劳动
- `product/产品矩阵.md` 里 SDK 是独立产品线,如果没有可发布包,这个产品线为空
- L5 / L6 的接入体验直接取决于 SDK 质量,影响 adoption

### 2.4 业务问题 vs 技术问题

- **业务问题**:第三方和端侧开发者能不能快速接入 Quantalithos
- **技术问题**:三语言一致性、文档质量、trace 自动传播、认证安全、版本兼容

| ID | 目标 | 验收指标 | 验收方式 |
|---|---|---|---|

## 5. 核心用例与用户故事

### 5.1 核心用例

1. **Rust 服务间调用**:L1 service 用 Rust SDK 调其他 service
2. **Python runtime 消费事件**:runtime 用 Python SDK 订阅 bus 事件
3. **TS UI 调服务**:chat / console 用 TS SDK 调后端服务
4. **第三方 10 分钟接入**:用 quickstart 发送第一个 API 请求 / 收到第一个事件
5. **自动 trace 传播**:SDK 自动把 traceparent 带到 RPC / EventBus 调用中

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| **BR-001** | core 版本变化 | SDK 必须同步使用同一 proto-ref 锁定 |
| **BR-002** | 三语言发版 tag | versions.toml 中 major.minor 必须同步 |
| **BR-003** | API deprecated | 至少保留 2 个 minor |
| **BR-004** | 敏感字段命名命中 `secret/password/token/key/credential/ssn` | 默认 redact 为 `***` |
| **BR-005** | trace 上下文已存在 | SDK 不重新生成,只透传 |
| **BR-006** | trace 上下文缺失 | SDK 自动生成新 traceparent |
| **BR-007** | 事件订阅失败 | 返回 idiomatic error,不直接泄露底层 MQ 原始对象 |
| **BR-008** | binding 生成失败 | 整体发版失败,不允许部分语言成功 |
| **BR-009** | Python / TS 生态风格与 Rust 不一致 | 保持概念一致,允许接口风格 idiomatic 差异 |

## 9. 数据需求

### 9.1 核心业务实体

L0-sdk 不存业务数据。主要数据是:

| 实体 | 归属 | 生命周期 |
|---|---|---|
| generated binding | 各语言发布包 | 版本化永久保留 |
| examples | SDK 仓源码 | 随版本演进 |
| versions.toml | SDK 仓源码 | 每次发版更新 |
| proto-ref.toml | SDK 仓源码 | core 升级时更新 |

### 9.2 数据关系图

```
quantalithos-core proto
        │ codegen
        ▼
  Rust / Python / TS binding
        │ package release
        ▼
crates.io / PyPI / npm
        │ install
        ▼
L1 / L2 / L5 / L6 / third-party developers
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| 发布包 | 永久(注册表) | 注册表管理 | 不删,仅 yank |
| CI artifact | 90 天 | GitHub 默认 | 自动过期 |
| examples / docs | Git 永久 | 仓库备份 | 不删 |

### 9.4 隐私与合规

L0-sdk 不存业务 PII,但最敏感的是:
- 开发者配置中的 token / secret / credential
- 异常消息中的请求头 / metadata

SDK 必须默认红线保护这些字段。

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 三语言 idiomatic 风格差异过大 | 中 | 中 | 保持概念一致,接口形式可语言特化 |
| 部分语言包发版失败 | 中 | 高 | 发布一致性脚本 + fail whole release |
| 下游跳过 SDK 直接调 proto | 中 | 中 | 提供更好 examples / docs 降低绕过动机 |
| secret redaction 漏掉某些命名 | 中 | 高 | 默认名单 + 安全回归测试 |

### 12.2 边缘风险

- TypeScript 生态切换到 Connect / gRPC-Web 影响现有 API 面
- Python runtime 需要单独 internal-sdk,与 public sdk 分叉
- 某语言的生成器对 proto 新特性支持滞后

| 问题 | 截止 | 负责人 |
|---|---|---|

| TS 走 protobuf-es 还是 Connect | N0 前 | UI Tech Lead |
| AG-UI 类型是否放 SDK 还是 conversation | N1 前 | conversation + sdk |
| MCP client 是否内置还是独立包 | N1 前 | capability-hub + sdk |

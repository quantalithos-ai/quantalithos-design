## 2. 本仓定位与边界

> 校准来源：
> - `design-calibration/00_req_step_02_position_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“改动前后对比”和“设计取舍”小节，了解本仓定位和边界如何收敛。

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L0-sdk` 是 Quantalithos 面向内部产品、AI runtime、运维脚本和第三方开发者的 Rust / Python / TypeScript 三语言官方客户端接入层仓。 |
| 本仓不是什么 | 它不是 core 契约真相仓，不是事件总线运行时，不是 L1+ 服务端聚合层，不是身份认证系统，不是 UI 组件库，也不是 runtime 执行框架。 |
| 边界对象列表 | `L0-core`、`L0-bus`、L1+ 服务端能力、L5/L6 产品、认证 / 安全网关、`L2-runtime`、`L3-capability-hub` |
| 单独成仓原因 | SDK 的开发者体验、三语言版本、兼容性和发布治理变化节奏独立于底层契约、事件总线和领域服务实现。 |

`L0-sdk` 最容易与 `L0-core`、`L0-bus`、L1+ 服务端能力、L5/L6 产品、认证网关和 `L2-runtime` 混淆。本文后续章节均按“客户端接入层”边界展开。

## 3. 背景与问题定义

> 校准来源：
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“当前文档问题诊断”和“设计取舍”小节，了解问题定义如何从稳定 `L0-core` / `L0-bus` 结论和旧 SDK 口径中收敛。

`L0-core` 与 `L0-bus` 已经稳定底层共享契约和事件传递语义，但平台还缺少把这些能力交给 Rust / Python / TypeScript 消费者的一致官方客户端接入层。

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 官方客户端接入层尚未按最新上游收束 | `L0-core` 与 `L0-bus` 已有 `00`~`07` 稳定文档，但 `L0-sdk` 仍停留在旧版三语言草案和旧文档 | L5/L6 产品、L2 runtime、运维脚本和第三方开发者会各自理解 core / bus 能力，形成重复封装 |
| 多语言与多消费者容易产生 drift | 旧文档没有按最新 core / bus 边界重新定义一致性、错误、trace、redaction 和事件封装问题 | 不同语言 SDK、端侧产品和 runtime 可能出现 API 名称、错误映射、trace 传播和敏感值处理不一致 |
| 旧文档口径混杂且部分过时 | 旧需求仍出现公共注册表发版作为 P0、MCP / REST / GraphQL / REPL 候选增强混入主线，并缺少新版 `04` / `07` 和中间产物 | 不能直接作为新版需求基线；后续架构和实现容易把 SDK 写成 binding 仓、服务端 facade 或过重产品层 |

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台需要让内部产品、AI runtime、运维脚本和第三方开发者以一致方式接入 Quantalithos 能力。 |
| 技术问题 | 已稳定的 `L0-core` / `L0-bus` 需要被三语言安全、一致地消费，避免类型、错误、trace、事件封装、版本兼容和 redaction 多套实现。 |

## 4. 目标与非目标

> 校准来源：
> - `design-calibration/00_req_step_04_goals_non_goals.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“当前文档问题诊断”和“设计取舍”小节，了解目标、非目标和当前范围如何从旧 SDK 草案中重新裁剪。

### 4.1 目标

| 目标 | 说明 | 验证方式 |
|---|---|---|
| 建立官方客户端接入层的需求边界 | SDK 是三语言官方 client，不是 binding-only、gateway、领域服务或 UI 层 | 后续章节不把服务端 truth、UI、runtime loop 写入 SDK |
| 建立对 `L0-core` / `L0-bus` 的稳定消费关系 | SDK 生成并包装 core 契约，封装 bus 事件视图，不重新定义底层语义 | 依赖与接口章节不出现 core / bus 双真相 |
| 收束三语言一致性目标 | Rust / Python / TypeScript 核心概念一致，语言接口可 idiomatic | 后续验收可检查概念、错误、trace、redaction 和事件封装一致 |
| 收束多消费者接入目标 | 支撑 L5/L6 产品、L2 runtime、运维脚本和第三方开发者使用同一官方接入口径 | 用户与角色、使用方与依赖章节能覆盖这些消费者 |
| 收束安全与可追踪默认目标 | trace 传播、错误映射和敏感信息保护是 SDK 横切目标 | 非功能和验收章节能定义 trace / redaction / error mapping 门禁 |
| 收束版本兼容与文档可学习目标 | SDK 需要有版本兼容、deprecated 过渡和文档 / 示例可学习性 | 后续验收能检查版本规则、迁移说明、quickstart 和 docstring |

### 4.2 非目标

| 非目标 | 不做原因 / 归属 |
|---|---|
| 定义 core proto / DTO、Error、TraceContext、CloudEvents schema、metadata | 归 `L0-core` |
| 实现 bus runtime 或重新定义 publish / subscribe / ack / retry / DLQ / replay 语义 | 归 `L0-bus` |
| 拥有 L1+ 服务端业务 API 真相和领域规则 | 归对应服务仓 |
| 作为服务端统一 gateway / facade | 会让 SDK 拥有服务端业务编排，破坏客户端边界 |
| 提供 UI 组件、页面状态和产品工作流 | 归 L5/L6 产品仓 |
| 实现登录认证、OAuth provider 或权限裁决 | 归安全入口、identity、gateway 或 governance |
| 完整 MCP Client、REST / GraphQL gateway、REPL / playground、本地缓存 / 离线状态策略 | 后续增强，不作为当前 P0 |
| 公共注册表正式发布 | 发布阶段目标，当前 P0 先保证本地可验证、版本规则和发布治理边界 |

## 6. 使用方与依赖

> 校准来源：
> - `design-calibration/00_req_step_06_consumers_dependencies.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“本仓依赖裁剪表”“本仓依赖类型分类表”和“依赖裁剪 ASCII 图”小节，了解 `L0-sdk` 如何从全局依赖基线中裁剪自己的依赖关系。

| 方向 | 对方 | 提供 / 依赖内容 | 是否闭环前置 | 失效影响 |
|---|---|---|---|---|
| 输入 | `L0-core` | 共享契约、生成类型、错误、trace、metadata 和基础 envelope | 是 | SDK 无法形成稳定类型、错误和追踪口径 |
| 输入 | `L0-bus` | 事件发布 / 订阅语义、delivery view、failure / replay / tap view | 是，对事件封装闭环是前置 | SDK 事件 client 只能停留在 stub / fake |
| 输入 | L1 服务仓 | 领域服务正式 API 边界和业务能力入口 | 是，对领域 client 封装闭环是前置 | SDK 无法证明领域能力接入层成立 |
| 输入 | L2 / L3 / L4 能力仓 | runtime、tools、method、capability、sandbox、observability、archive 等正式边界 | 否，按能力逐步纳入 | 对应高级 client 延迟，不阻塞基础 SDK 闭环 |
| 输入 | fake / fixture endpoint | 本地示例、smoke test 和 package candidate 验证目标 | 是 | 无法验证 SDK 最小接入路径可运行 |
| 输出 | L5 产品仓 | TypeScript SDK 和统一端侧接入口径 | 是，对端侧接入目标是前置 | 端侧产品可能继续私有直连 |
| 输出 | L6 生态仓 | SDK client、示例、版本兼容和外部集成接入口径 | 否 | 生态接入延迟，不阻塞 SDK 基础闭环 |
| 输出 | `L2-runtime` / 自动化脚本 | Python SDK 和自动化接入口径 | 是，对 runtime / automation 接入目标是前置 | runtime 或脚本会重复封装协议 |

`L0-sdk` 当前最关键的强前置是 `L0-core`、`L0-bus`、至少一个稳定服务边界或 fake endpoint，以及下游 smoke test。L1/L2/L3/L4 能力只能作为运行期封装目标进入设计，不得写成 SDK 的本地源码依赖；L5/L6 和部分内部仓是 SDK 下游消费者，不得反向污染 SDK 主体边界。

## 7. 核心能力闭环

> 校准来源：
> - `design-calibration/00_req_step_07_core_capability_loop.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“核心能力闭环图”“能力层级划分表”和“功能回填映射结论”小节，了解 `L0-sdk` 如何从旧功能清单收敛为官方客户端接入层的核心能力闭环。

`L0-sdk` 的不可替代性在于：它把底层共享契约、事件语义和服务边界，转译成 Rust / Python / TypeScript 三语言可用、可学习、可追踪、可保护敏感信息、可持续演进的官方客户端接入层。

```text
共享能力能够被三语言稳定承接
  -> 官方客户端概念能够跨语言一致成立
  -> 平台能力能够通过客户端完成最小可验证接入
  -> 错误、追踪与敏感信息保护能够默认一致生效
  -> 文档、示例与兼容演进能够持续约束使用体验
```

| 节点 | 能力 | 成立标准 |
|---|---|---|
| CL-001 | 三语言稳定承接 | 三语言能够稳定承接共享契约、事件语义、错误、trace 和 metadata，不另造 truth |
| CL-002 | 官方客户端一致 | 三语言核心概念一致，同时允许符合语言习惯的表达差异 |
| CL-003 | 最小可验证接入 | 至少通过稳定服务边界或 fake / fixture 证明 client 可运行、示例可执行 |
| CL-004 | 横切默认一致 | trace、error mapping、redaction 和凭据材料保护在三语言默认一致 |
| CL-005 | 文档与兼容演进 | quickstart、docstring、示例、版本同步和 deprecated 过渡持续约束使用体验 |

公共注册表正式发布、完整 MCP Client、REST / GraphQL gateway、REPL / playground、本地缓存 / 离线状态、全量 L1/L2/L3/L4 client 覆盖都是外围增强，不决定当前核心闭环是否成立。

## 10. 业务规则与边界约束

> 校准来源：
> - `design-calibration/00_req_step_10_rules_boundary_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“业务规则结论”“规则类型结论”和“规则保护闭环结论”小节，了解这些规则如何保护 SDK 核心能力闭环不串线。

| 规则编号 | 规则类型 | 规则内容 | 约束对象 |
|---|---|---|---|
| BR-001 | 不变量 | SDK 必须以 `L0-core` 的共享契约、错误、trace、metadata 为上游 truth，不得自行定义替代契约。 | core / SDK 契约边界 |
| BR-002 | 不变量 | SDK 必须以 `L0-bus` 的事件语义为上游 truth，不得自行定义 delivery、retry、dead-letter、replay 或 tap 语义。 | bus / SDK 事件边界 |
| BR-003 | 不变量 | Rust / Python / TypeScript 的核心 SDK 概念必须语义一致，语言习惯差异不得改变平台含义。 | 三语言官方 client |
| BR-004 | 不变量 | SDK 必须保持客户端接入层定位，不拥有 L1/L2/L3/L4 服务端业务事实和领域规则。 | 服务端 truth / SDK 边界 |
| BR-005 | 禁止行为 | SDK 不得执行身份生命周期、登录认证、权限裁决或治理审批。 | auth / identity / governance 边界 |
| BR-006 | 禁止行为 | SDK 不得把 UI 组件、页面状态、产品工作流或 runtime loop 写成自身核心能力。 | 产品 / runtime 边界 |
| BR-007 | 禁止行为 | SDK 不得在错误文本、日志材料、示例输出或诊断材料中泄露敏感凭据材料。 | 错误、日志、示例、诊断材料 |
| BR-008 | 显式变化 | 上游契约或 bus 语义变化后，SDK 必须显式形成兼容性判断、版本处理口径和跨语言验证证据。 | 上游版本变化 |
| BR-009 | 显式变化 | deprecated 能力必须显式标记迁移路径和过渡口径，不得静默移除或只在某一种语言移除。 | SDK 兼容演进 |
| BR-010 | 显式变化 | 外围增强能力进入当前主线前，必须重新进行需求边界裁剪，不得通过实现过程自然膨胀。 | MCP、REST / GraphQL、REPL、公共发布等外围能力 |
| BR-011 | 边界约束 | L1/L2/L3/L4 能力只能作为运行期正式边界或 fake / fixture 进入 SDK 需求，不得成为 SDK 源码 truth。 | 服务仓 / SDK 依赖边界 |
| BR-012 | 边界约束 | 公共注册表正式发布不属于当前 P0 闭环前置；当前必须先保证本地 package candidate 可安装、可验证。 | 发布边界 |
| BR-013 | 审计约束 | SDK candidate 必须留下跨语言 smoke、示例运行、错误 / trace 和 redaction 验证证据。 | candidate 验证证据 |
| BR-014 | 审计约束 | 破坏性变更必须留下兼容性判断、迁移说明或 deprecated 过渡记录。 | 版本兼容审计 |

| 规则 / 边界验收 | 服务端 / auth / UI / runtime 边界清晰 | SDK 不拥有服务端业务 truth、认证授权 truth、治理审批、UI 状态或 runtime loop。 |
| 数据归属验收 | 禁止正文不入仓 | 业务正文、事件正文、凭据正文、生产请求 / 响应、观测正文、UI / runtime 状态正文不进入 SDK 数据范围。 |
| 非功能验收 | 敏感信息保护达标 | redaction 和凭据保护验证中敏感值泄露次数为 0。 |
| 非功能验收 | 外围能力降级不破坏核心闭环 | 公共注册表、完整 MCP、REST / GraphQL、REPL 不可用时，F-001~F-010 仍可判断和验收。 |

### 14.2 一票否决项

- SDK 重定义 `L0-core` 契约 truth 或 `L0-bus` 事件语义 truth。
- SDK 只有单语言或双语言可用，无法形成三语言官方客户端闭环。
- 没有本地 package candidate，或没有稳定服务边界 / fake / fixture endpoint，导致最小接入无法验证。
- 错误、日志、示例、诊断或验证报告中泄露 token、secret、credential、password、private key 等敏感材料。
- SDK 保存业务正文、事件 payload 正文、生产请求 / 响应正文、trace 全量正文、UI 状态或 runtime loop 状态。
- SDK 执行身份认证、权限裁决、治理审批或服务端业务编排。
- deprecated / breaking change 无迁移口径，且三语言兼容状态无法追溯。

## 2. 业务背景与驱动力

> 校准来源：
> - `design-calibration/01_arch_step_02_arch_goals_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解业务背景、驱动力和架构目标如何收敛。

`L0-core` 和 `L0-bus` 已经分别稳定共享契约与事件语义，但这些底层能力还需要被 Rust / Python / TypeScript 消费者以一致方式使用。没有 `L0-sdk` 的架构边界，端侧产品、AI runtime、自动化脚本和第三方集成会各自复制协议、错误、trace、事件封装、redaction、版本兼容和示例材料，最终形成多套私有客户端接入口径。

`L0-sdk` 的架构设计重点不是“生成三种语言的包”或“发布到公共注册表”，而是明确官方客户端接入层如何承接上游 truth、如何保持跨语言一致、如何提供最小可验证路径、如何守住客户端与服务端 / bus / auth / UI / runtime 的边界。

| 驱动力 | 说明 |
|---|---|
| 多语言消费者需要统一官方接入口径 | Rust / Python / TypeScript 调用方不能形成多套私有 client 和错误处理习惯。 |
| `L0-core` / `L0-bus` truth 需要被消费而不是被复制 | SDK 不重新制造 proto、DTO、ErrorCode、TraceContext、CloudEvents 或 delivery 语义。 |
| 服务端能力需要客户端封装，但不能变成 SDK truth | SDK 封装调用入口，不吸收服务端业务事实和领域规则。 |
| 三语言 idiomatic 差异需要架构边界约束 | 语言习惯可以影响表达，不能演变成平台语义差异。 |
| 本地可验证路径需要先于公共发布成立 | 当前阶段先证明 SDK 可安装、可调用、可学习和可验证。 |
| 横切默认需要跨语言一致 | trace、error mapping、redaction 和凭据材料保护不能按语言漂移。 |

架构目标如下：

| 架构目标 | 说明 |
|---|---|
| 承载官方三语言客户端接入层边界 | 防止 SDK 退化为 binding-only 仓、发布脚本仓或某个产品的私有 client。 |
| 支撑 `L0-core` 与 `L0-bus` truth 的稳定消费 | 防止 SDK 成为第二契约或事件语义来源。 |
| 守住客户端封装与服务端业务 truth 的边界 | 防止运行期 API 封装演变为 server facade 或业务编排层。 |
| 允许三语言语义一致且表达 idiomatic | 保护共同平台心智，同时允许语言生态差异。 |
| 支撑本地 package candidate 与最小可验证接入路径 | 证明 SDK 不只是类型存在，而是可安装、可调用、可验证。 |
| 守住错误、trace、redaction 和凭据材料保护默认一致边界 | 保护安全、审计和可观测主线。 |
| 支撑版本兼容、deprecated 和文档示例的可追溯演进 | 让升级、示例和 breaking change 可复核。 |

## 3. 约束条件

> 校准来源：
> - `design-calibration/01_arch_step_01_requirements_baseline.md`
> - `design-calibration/01_arch_step_02_arch_goals_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“架构硬约束清单”“不可变约束表”“当前阶段可接受取舍表”和“架构非目标表”，了解本章约束如何从需求基线和目标约束收敛而来。

| 约束 | 说明 |
|---|---|
| 不重新定义 `L0-core` 已拥有的契约、错误、trace、metadata 和 CloudEvents schema | `L0-core` 是共享契约 truth，SDK 只能消费和派生语言视图。 |
| 不重新定义 `L0-bus` 已拥有的事件传递、订阅、确认、失败、死信、回放和 tap 语义 | `L0-bus` 是事件 truth，SDK 只能提供事件客户端视图。 |
| 不承载 L1/L2/L3/L4 服务端业务事实和领域规则 | 服务能力通过 formal API 或 fake boundary 运行期封装。 |
| 不执行身份认证、权限裁决、治理审批或身份生命周期 | 安全入口、identity、gateway 或 governance 承载这些职责。 |
| 不承载 UI 组件、页面状态、产品工作流或 runtime loop | L5/L6 产品仓和 L2 runtime 承载对应职责。 |
| 不保存业务正文、事件 payload 正文、生产请求响应正文、观测正文、UI / runtime 状态正文或凭据正文 | 这些正文不得进入 SDK truth、示例正文、错误材料或验证报告正文。 |
| 不把 L1/L2/L3/L4 服务仓写成 SDK 源码依赖 | 必须区分编译期依赖、运行期依赖和事件协作依赖。 |
| 不把公共注册表、完整 MCP、REST / GraphQL、REPL 或本地缓存写成当前 P0 前置 | 当前基础闭环以本地 package candidate 和最小可验证接入为准。 |

当前阶段可接受的取舍如下：

| 取舍 | 当前口径 |
|---|---|
| 公共注册表正式发布 | 作为发布阶段目标处理，当前 P0 先保证本地 package candidate 可安装、可验证。 |
| 全量 L1/L2/L3/L4 client 覆盖 | 当前不纳入核心闭环，先通过稳定服务边界或 fake / fixture endpoint 证明最小接入。 |
| 完整 MCP Client | 当前作为 P1 候选处理，不进入架构 P0 主线。 |
| REST / GraphQL wrapper、REPL / playground、本地缓存 / 离线状态 | 当前作为 P2 或产品侧增强处理，不进入架构 P0 主线。 |
| codegen、transport、语言包目录和 wrapper 风格 | 架构层只保留承接上游 truth 和三语言一致目标，具体方案后移。 |
| 性能阈值、candidate 报告、reports 和 artifacts 格式 | 架构层只保留可测量和可追溯要求，具体阈值与格式后移。 |

## 4. 职责边界

> 校准来源：
> - `design-calibration/01_arch_step_03_responsibility_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“职责边界表”“边界红线清单”和“收束说明”小节，了解本章职责边界如何收敛。

| 职责项 | 类型 | 说明 |
|---|---|---|
| 三语言官方客户端接入层承载 | 做 | 让 Rust / Python / TypeScript 使用同一官方接入口径。 |
| `L0-core` 契约消费与语言映射 | 做 | 消费共享契约并形成语言视图，不成为第二契约真相。 |
| `L0-bus` 事件语义客户端视图 | 做 | 提供事件客户端体验，但传递 truth 仍归 `L0-bus`。 |
| 正式服务边界的运行期客户端封装 | 做 | 封装调用入口，但不拥有服务端业务事实。 |
| 三语言核心概念一致性维护 | 做 | 维护共同平台心智，防止语言 drift。 |
| 错误映射、trace 传播和 redaction 默认边界 | 做 | 横切行为在三语言中保持一致且不泄露敏感正文。 |
| 本地 package candidate 与安装验证边界 | 做 | 当前 P0 先证明 SDK 可安装、可调用、可验证。 |
| quickstart、docstring 与示例口径维护 | 做 | 让开发者按官方示例完成最小接入。 |
| 版本兼容、deprecated 与迁移口径维护 | 做 | SDK 升级必须具备可追溯的兼容与迁移边界。 |
| 跨语言 smoke 和一致性验证证据维护 | 做 | 证明三语言核心概念和横切行为没有漂移。 |
| core proto / DTO / ErrorCode / TraceContext / CloudEvents schema 定义 | 不做 | 属于 `L0-core`。 |
| bus publish / subscribe / ack / retry / dead-letter / replay / tap runtime | 不做 | 属于 `L0-bus`。 |
| L1/L2/L3/L4 服务端业务事实和领域规则 | 不做 | 属于对应服务仓。 |
| 服务端统一 gateway / facade | 不做 | 会打穿客户端与服务端业务编排边界。 |
| 登录认证、OAuth provider、权限裁决和治理审批 | 不做 | 属于安全入口、identity、gateway 或 governance。 |
| UI 组件、页面状态和产品工作流 | 不做 | 属于 L5/L6 产品仓。 |
| AI runtime loop、tool invocation、memory 和 checkpoint | 不做 | 属于 L2 运行层仓。 |
| 公共注册表平台运营 | 不做 | SDK 可准备发布材料，但不运营 crates.io、PyPI 或 npm 平台。 |

边界收束为：

```text
-------------------------+
|         L0-sdk         |
| official client layer  |
+-----------+-------------+
            |
            | consume / wrap
            v
+-----------+-------------+
| core truth / bus truth |
| formal API boundaries  |
+-------------------------+

not owned:
  server business truth
  bus runtime truth
  auth / governance truth
  UI / runtime truth
  business bodies / credentials
```

## 5. 系统边界与上下文

> 校准来源：
> - `design-calibration/01_arch_step_04_system_context.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“系统上下文图”“上下游与输入 / 输出面表”和“边界说明结论”小节，了解系统上下文如何从职责边界和依赖关系收敛。

```text
                 +--------------------+       +--------------------+
                 |      L0-core       |       |      L0-bus        |
                 | shared truth       |       | event truth        |
                 +---------+----------+       +---------+----------+
                           |                            |
                           | 输入                       | 输入
                           v                            v
       +------------------+      +--------------------+      +------------------+
       | L1/L2/L3/L4 APIs |----->|       L0-sdk       |<-----| fake / fixture  |
       | runtime targets  |依赖  | official SDK       |依赖  | verification    |
       +------------------+      +---------+----------+      +------------------+
                                             |
                                             | 输出
                         +-------------------+-------------------+
                         |                   |                   |
                         v                   v                   v
              +----------+---------+  +------+-----------+  +----+----------------+
              | L5/L6 products    |  | runtime /        |  | package validation |
              | product consumers |  | automation       |  | smoke/docs runners |
              +-------------------+  +------------------+  +---------------------+
```

该图只表达本仓与正式上下文对象之间的边界关系与输入 / 输出方向，不表达接口、事件、实现组件或运行时顺序。

| 对象 | 关系方向 | 关系类型 | 输入 / 输出面 | 说明 |
|---|---|---|---|---|
| `L0-core` | 输入 | 来源 | 共享契约、错误、trace、metadata、基础 envelope | SDK 必须消费 core truth，不得重新定义。 |
| `L0-bus` | 输入 | 来源 | 事件语义、transport view、发布 / 订阅边界 | SDK 只封装事件 client 体验，不拥有 delivery truth。 |
| L1/L2/L3/L4 formal APIs | 输入 | 依赖 | 正式服务能力边界 | SDK 运行期封装服务能力，不源码依赖服务仓或拥有业务 truth。 |
| fake / fixture endpoint | 输入 | 依赖 | 最小验证目标 | 用于证明 package candidate、quickstart 和 smoke 可运行。 |
| L5/L6 product consumers | 输出 | 消费 | TypeScript / product-side client 接入口径 | 产品侧消费 SDK，不应维护私有协议封装。 |
| runtime / automation consumers | 输出 | 消费 | Python / automation client 接入口径 | runtime 和脚本消费 SDK，不应重复封装协议、错误和 trace。 |
| internal service / integration consumers | 输出 | 消费 | Rust / integration client 接入口径 | 内部服务和集成复用 SDK 的类型、错误、trace 和事件视图。 |
| third-party / enterprise integrations | 输出 | 消费 | 官方 client、文档示例和兼容承诺 | 外部集成通过 SDK 接入，不直接依赖裸协议。 |
| package validation / smoke / docs runners | 输入 / 输出 | 依赖 | candidate 验证反馈、示例运行证据 | runner 不拥有 SDK truth，但未通过验证时 candidate 不得标记为已验证。 |

公共注册表、完整 MCP provider、REST / GraphQL gateway、REPL / playground 和本地缓存当前不进入系统主图，因为它们属于发布阶段或外围增强。

## 6. 限界上下文与子域划分

>
> 延伸阅读：

统一语言如下：

| 术语 | 含义 |
|---|---|
| 官方客户端语义核心 | SDK 内部最稳定的 official client 共同语义和三语言一致性边界。 |
| 上游契约消费 | 从 core / bus / formal APIs 消费 truth 并形成 SDK 视图的语义边界。 |

| 横切默认行为 | SDK 默认错误、trace、redaction 和凭据材料保护语义。 |
| package candidate | 当前阶段用于证明 SDK 可安装、可调用、可验证的候选形态。 |
| 本地索引 / 投影 / 引用 | 为稳定消费、验证和追溯保留的 ref、snapshot 或 evidence entry，不拥有外部正文。 |

## 7. 容器 / 部署架构

> 校准来源：
> - `design-calibration/01_arch_step_06_container_deployment.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“容器 / 部署架构图”“运行单元说明表”和“部署关系结论”小节，了解 SDK 运行承载和验证承载如何收敛。

```text
                                             +----------------------+
                                             |  caller runtime      |
                                             |  product / script    |
                                             +----------+-----------+
                                                        |
                                                        | 入口
                                                        v

      +======================================================+
      |                 L0-sdk 正式运行承载                   |
      |                                                      |
      |   +----------------------+   承载 / 依赖   +----------------------+
      |   | package candidate    |--------------->| 嵌入式 SDK 运行承接 |
      |   | artifact             |                | client call surface |
      |   +----------^-----------+                +----------+-----------+
      |              |                                       |
      |              | 处理                                  | 处理 / 消费
      |   +----------+-----------+                           v
      |   | candidate 生成与验证 |                +----------+-----------+
      |   | smoke / docs / compat|                | 事件客户端承接单元 |
      |   +----------------------+                | event client surface|
      |                                           +----------------------+
      |                                                      |
      +======================================================+
                                                        |
                                                        | 依赖
                                                        v
                                             +----------+-----------+
                                             | fake / fixture       |
                                             | verification target  |
                                             +----------------------+
```

| 对象 | 类型 | 主要职责 | 运行关系 | 说明 |
|---|---|---|---|---|
| caller runtime | 运行时对接的正式外部边界 | 承载产品、runtime、脚本或集成代码中的 SDK 使用环境。 | 通过入口关系进入嵌入式 SDK 运行承接单元。 | 调用方运行边界不属于 SDK 仓部署结构。 |
| 嵌入式 SDK 运行承接单元 | 同步入口单元 | 承接调用方对平台服务能力的客户端访问。 | 随调用方部署并依赖 SDK package candidate。 | 它不是独立网络 gateway 或服务端 API。 |
| 事件客户端承接单元 | 异步消费单元 | 承接基于 bus 语义的事件客户端使用视图。 | 与嵌入式 SDK 运行承接单元共同消费上游事件语义。 | 它不拥有 bus delivery、retry、DLQ 或 replay truth。 |
| candidate 生成与验证处理单元 | 后台处理单元 | 形成本地 package candidate、运行 smoke、验证示例和兼容边界。 | 处理结果写入 package candidate artifact。 | 这是构建 / 验证期处理单元，不是线上业务 worker。 |
| package candidate artifact | 正式存储承载 | 承载本地 SDK candidate、示例材料和验证证据入口。 | 被调用方验证、runner 和后续发布阶段消费。 | 当前 P0 的正式承载，不等同于公共注册表发布。 |
| fake / fixture target | 运行时对接的正式外部边界 | 为 quickstart、smoke 和最小接入验证提供受控目标。 | 被验证处理单元依赖。 | 它不拥有业务生产 truth，只用于受控验证。 |

`L0-sdk` 不部署为独立线上服务，不需要业务数据库、缓存或消息队列作为运行承载。嵌入式 SDK 运行承接单元和事件客户端承接单元随调用方进程部署；candidate 生成、smoke、docs 示例验证和兼容检查属于构建 / 验证期边界。

## 8. 依赖方向与层间约束

> 校准来源：
> - `design-calibration/01_arch_step_07_dependency_direction.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“依赖角色划分表”“依赖方向图”“本仓依赖裁剪表”“禁止依赖表”和“依赖裁剪图”小节，了解本仓如何从全局依赖基线裁剪自己的依赖关系。

```text
+==============================================================+
|                       L0-sdk 依赖边界                        |
|                                                              |
|   +-------------------------------+                          |
|   | 验证 / 文档 / candidate 承载  |                          |
|   | evidence / docs / packages    |                          |
|   +---------------+---------------+                          |
|                   | 允许依赖                                  |
|                   v                                          |
|   +---------------+---------------+                          |
|   | 语言与 package 表达角色       |                          |
|   | Rust / Python / TypeScript    |                          |
|   +---------------+---------------+                          |
|                   | 允许依赖                                  |
|                   v                                          |
|   +---------------+---------------+                          |
|   | 能力访问与横切默认承接角色    |                          |
|   | service / event / defaults    |                          |
|   +---------------+---------------+                          |
|                   | 允许依赖                                  |
|                   v                                          |
|   +---------------+---------------+                          |
|   | 官方客户端语义核心            |                          |
|   | client semantics / consistency|                          |
|   +---------------+---------------+                          |
|                   | 允许依赖                                  |
|                   v                                          |
|   +---------------+---------------+                          |
|   | 上游契约来源边界              |                          |
|   | L0-core / L0-bus truth        |                          |
|   +-------------------------------+                          |
|                                                              |
+==============================================================+
```

| 关联项目 | 本仓角色 | 依赖类型 | 是否进入当前文档主链 | 裁剪理由 |
|---|---|---|---|---|
| `L0-core` | 依赖方 | 编译期 | 是 | SDK 必须消费共享契约、错误、trace、metadata 和 envelope。 |
| `L0-bus` | 依赖方 / 协作方 | 编译期 / 事件协作 | 是 | SDK 必须消费事件语义并封装事件 client，但不实现 bus runtime。 |
| L1 domain services | 依赖方 | 运行期 | 是 | SDK 需要封装稳定服务边界，但不得源码依赖服务仓。 |
| L2 / L3 / L4 capability services | 依赖方 | 运行期 | 是，按阶段进入 | 各能力按稳定度逐步封装。 |
| fake / fixture endpoint | 依赖方 | 运行期 | 是 | 支撑 quickstart、smoke 和本地 package candidate 最小验证。 |
| L5 product consumers | 被依赖方 | 下游运行期 / package 消费 | 是 | 产品侧通过 SDK 接入平台能力，不反向拥有 SDK truth。 |
| `L2-runtime` / automation consumers | 被依赖方 | 下游运行期 / package 消费 | 是 | Python / automation 消费 SDK，避免重复封装协议和错误。 |
| L6 ecosystem / third-party integrations | 被依赖方 | 下游运行期 / package 消费 | 是，非 P0 全量 | 生态和第三方按 SDK 官方口径接入。 |
| 公共注册表 | 外围发布渠道 | 发布阶段依赖 | 否 | 当前 P0 以本地 package candidate 验证为主。 |
| 完整 MCP / REST / GraphQL / REPL / local cache | 外围能力 | 运行期 / 产品增强 | 否 | 当前不进入核心闭环，后续重新裁剪。 |

禁止依赖如下：

| 禁止依赖 | 禁止原因 | 正确协作方式 |
|---|---|---|
| 源码直接依赖任一 L1/L2/L3/L4 服务仓实现 | 会把运行期服务封装误建模为源码耦合，并污染 SDK truth。 | 通过 formal API、adapter 或 fake / fixture endpoint 接入。 |
| 重新定义 `L0-core` 契约、错误、trace、metadata 或 CloudEvents schema | 会形成 core / SDK 双重真相。 | 编译期消费 `L0-core` 稳定契约。 |
| 重新定义 `L0-bus` delivery、retry、dead-letter、replay 或 tap 语义 | 会让 SDK 越界成为 bus runtime。 | 编译期消费 `L0-bus` 契约，事件能力通过 bus 语义封装。 |
| 语言 package 表达直接决定官方客户端语义核心 | 会让三语言各自形成平台语义。 | 语言表达依赖统一语义核心，差异只限 idiomatic API。 |
| 验证报告、示例、docstring 或 public registry 状态反向定义 SDK truth | 会让证据和发布渠道取代架构语义。 | 验证材料只证明已确认行为，公共发布后移。 |
| 下游产品、runtime、automation 或第三方集成反向拥有 SDK truth | 会让 SDK 变成某个消费方的私有 client。 | 下游通过正式 package / client 接口消费，反馈经正式变更流程进入。 |

## 9. 数据所有权与一致性策略

> 校准来源：
> - `design-calibration/01_arch_step_08_data_ownership_consistency.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“数据归属表”“一致性策略表”“简化关系示意图”和“数据边界说明短文”小节，了解 SDK 数据 truth、快照、引用和禁止正文如何划分。

```text
+------------------------------+
|        L0-sdk truth          |
| client semantics / mapping   |
| candidate / docs / defaults  |
| compatibility / evidence     |
+--------------+---------------+
               |
     +---------+----------+
     |                    |
     v                    v
+------------+     +-------------+
| snapshots  |     | references  |
| core/bus   |     | versions    |
| api views  |     | ADR/evidence|
+-----+------+     +------+------+
      |                   |
      | no ownership      | no body copy
      v                   v
+-------------------------------+
| explicitly not owned bodies   |
| payload / req-res / logs      |
| UI-runtime state / secrets    |
+-------------------------------+
```

| 数据类型 | 数据项 | 归属说明 |
|---|---|---|
| 正式真相数据 | 官方客户端公共概念与语言映射口径、SDK package candidate 状态、默认错误 / trace / redaction 行为、版本兼容与 deprecated 结论、quickstart / docstring / 示例内容、跨语言验证证据结论 | 由 `L0-sdk` 拥有正式 truth。 |
| 快照 / 投影数据 | `L0-core` 契约派生类型视图、`L0-bus` 事件语义客户端视图、L1/L2/L3/L4 服务边界客户端视图、ErrorCode / TraceContext / metadata 消费视图 | SDK 可保留语言消费视图，但上游 truth 仍归上游仓。 |
| 引用关系数据 | 上游版本引用、ADR / 标准 / 设计文档引用、fake / fixture endpoint 引用、reports / artifacts / 发布证据引用 | SDK 保存引用、入口和结论，不拥有外部正文。 |
| 明确不拥有的正文 / 真相 | 业务对象正文、事件实例 payload 正文、生产请求 / 响应正文、观测日志正文、UI / runtime 状态正文、凭据和密钥正文 | SDK 不保存、不拥有；可在运行期传输，但不得进入 SDK 持久 truth、示例或报告正文。 |

一致性策略如下：

| 场景 | 一致性口径 | 失败处理口径 |
|---|---|---|
| 官方客户端语义与语言映射 | 候选边界强一致 | 阻断 candidate 稳定结论。 |
| package candidate 状态与验证证据结论 | 验证门禁一致 | 不得标记 verified / stable，保持 rejected、failed 或 pending。 |
| 横切默认行为在三语言之间 | 发布候选强一致 | 阻断候选发布或标记对应语言 unsupported。 |
| 兼容 / deprecated 结论与迁移文档 | 变更门禁一致 | 阻断兼容结论或迁移说明进入 stable。 |
| 上游 core / bus truth 到 SDK 快照 | 最终一致 + 版本引用一致 | 标记 stale / pending，不伪造上游 truth。 |
| formal API 到 SDK client 视图 | 最终一致 | 标记 unsupported / stale，不进入 P0 stable 证明链。 |
| quickstart / docstring / 示例到 candidate | 验证边界一致 | 示例标记 failed / stale，不能作为可运行示例发布。 |
| reports / artifacts 引用到验证结论 | 引用有效性一致 | 标记 evidence missing / invalid，不补造证据正文。 |
| 禁止正文进入 SDK 材料 | 边界约束一致 | 拒绝、脱敏或使验证失败。 |

## 10. 关键交互与通信方式

> 校准来源：
> - `design-calibration/01_arch_step_09_interactions_communication.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“关键交互场景表”“通信方式判断表”“简化交互示意图”和“边界说明短文”小节，了解同步、异步和后台延后承接如何划分。

```text
+----------------------------+
| downstream caller runtime |
+-------------+--------------+
              |
              | 同步请求 / 响应
              v
      +-------+--------+
      |     L0-sdk     |
      | embedded client|
      +---+--------+---+
          |        |
          |        | 异步事件 / 回调
          |        v
          |  +-----+----------------+
          |  | L0-bus semantic      |
          |  | event client boundary|
          |  +----------------------+
          |
          | 同步请求 / 响应
          v
+---------+----------+
| formal API / fake  |
| service boundary   |
+--------------------+

后台任务 / 延后承接:
  L0-core / L0-bus truth -> SDK snapshot / candidate
  package candidate -> validation / docs evidence
  downstream feedback -> SDK change boundary
```

| 交互场景 | 推荐通信方式 | 失败处理口径 |
|---|---|---|
| 下游调用方通过 SDK 访问正式服务能力 | 同步请求 / 响应类交互 | 返回明确失败、unsupported 或 unavailable，不写入 SDK truth，不伪装成功。 |
| 下游调用方通过 SDK 使用事件客户端视图 | 异步事件 / 回调类交互 | 保持未送达、挂起、fake / stub 或明确失败，不补造 bus delivery truth。 |
| SDK 对齐上游契约与事件语义 | 后台任务 / 延后承接类交互 | 标记 stale / pending / unsupported，阻断 candidate 稳定结论。 |
| SDK 验证 package candidate 与文档示例 | 后台任务 / 延后承接类交互 | candidate 不得标记 verified，示例不得标记 runnable，证据引用保持 missing / invalid。 |
| 下游消费方加载和使用 SDK package | 同步请求 / 响应类交互 | 失败进入兼容或验证反馈，不反向改变 SDK 语义核心。 |
| 下游反馈进入 SDK 演进边界 | 后台任务 / 延后承接类交互 | 反馈保持 pending、accepted 或 rejected，待正式变更流程收口。 |

## 11. 关键技术选型

> 校准来源：
> - `design-calibration/01_arch_step_10_technology_choices.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“关键技术机制表”“简化对照表”和“技术边界说明短文”小节，了解本章为何只锁定架构机制而不提前锁定具体工具。

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 |
|---|---|---|---|
| 上游契约派生视图与官方语义封装分层 | raw binding 缺少官方 client 体验，手写替代契约会制造双真相 | 派生视图承接 `L0-core` / `L0-bus` truth，官方语义封装承接 SDK client truth | 需要维护派生视图与封装语义边界，快照落后时标记 stale / pending。 |
| 三语言语义基线与 idiomatic 表达分离 | 三语言按生态独立演进会形成三套平台语义 | 共享语义基线保护共同概念，语言表达层允许符合语言习惯 | 增加跨语言审查、命名映射、示例同步和 smoke 验证成本。 |
| 正式服务边界 adapter 机制 | SDK 需要访问 L1/L2/L3/L4 能力，但不能源码依赖服务仓 | formal API / fake boundary adapter 让 SDK 只封装运行期正式边界 | 需要维护 unsupported / unavailable / stale 等失败口径。 |
| `L0-bus` 语义事件客户端视图 | SDK 需要事件 client 体验，但不能重新定义事件传递 truth | 事件客户端视图只消费 `L0-bus` 语义 | 需要持续跟随 bus 语义变化，并明确未送达、挂起、fake / stub 或失败状态。 |
| 本地 package candidate 与验证证据链 | 公共发布或生成产物不能证明 SDK 当前可用 | 本地 candidate、smoke、docs runner 和 fake / fixture target 先证明 P0 闭环 | 需要维护 runner、fixture、reports / artifacts 引用和 not verified 状态。 |
| 跨语言横切默认策略机制 | error mapping、trace、redaction 和凭据材料保护若分散实现会漂移 | 将横切默认作为 SDK truth，要求三语言默认行为一致并可验证 | 增加默认策略维护、敏感值测试、错误文本审查和覆写边界说明成本。 |
| 版本兼容 / deprecated 治理与上游版本引用机制 | 上游变化和 SDK breaking change 若不可追溯会让下游升级不可控 | SDK candidate 必须引用上游版本，并形成兼容判断、deprecated 过渡和迁移口径 | 增加版本矩阵、迁移说明、旧能力保留和破坏性变更审查成本。 |

本章不锁定具体协议、生成器、包管理器、测试命令或公共发布平台。具体工具和实现形态在概要设计、详细设计、测试方案和实施计划中继续落地。

## 12. 备选方案与取舍

> 校准来源：
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“方案路径比较表”“边界外方向说明表”“轻量取舍对照表”和“方案边界说明短文”小节，了解当前主线为何被采用。

| 方案路径 | 当前结论 | 说明 |
|---|---|---|
| 官方语义封装主线：上游派生视图 + 官方语义封装 + 三语言表达 + formal API / fake adapter + event client view + candidate 验证 | 采用 | 最符合 SDK 作为官方客户端接入层的定位，能同时保护上游 truth、三语言一致、P0 可验证和兼容演进。 |
| Raw binding-only 路径 | 不采用 | 可作为底层派生视图，但不能提供官方 client 体验、横切默认和文档可学习性。 |
| 全手写 client 路径 | 不采用 | 短期体验自由，但容易重定义 core / bus / service 语义并制造维护漂移。 |
| 三语言各自独立 SDK 路径 | 不采用 | 每种语言都能最大化 idiomatic，但会导致平台概念、错误、trace、redaction、deprecated 语义分裂。 |
| 公共发布 / registry 先行路径 | 不采用为当前 P0 | 公共发布有后续价值，但当前先以本地 package candidate 和验证证据证明闭环。 |
| 全量能力覆盖先行路径 | 不采用为当前 P0 | 能力面完整，但 P0 范围过大，formal API 稳定度不足时会拖累基础闭环。 |

以下方向不作为正式备选方案重新打开：

| 方向 | 不作为正式备选方案的原因 | 正确处理口径 |
|---|---|---|
| SDK server gateway / facade | 违反客户端接入层边界，会让 SDK 拥有服务端业务编排 | 由正式服务边界、gateway 或对应服务仓承载。 |
| SDK 自定义 bus runtime | 会重定义 delivery、retry、dead-letter、replay、tap truth | SDK 只提供 `L0-bus` 语义下的事件客户端视图。 |
| SDK auth provider / governance executor | 会侵入身份认证、权限裁决和治理审批边界 | 由安全入口、identity、gateway 或 governance 承载。 |
| UI component library / runtime loop | 会混入产品层或运行时执行层职责 | 由 L5/L6 产品仓或 L2 runtime 承载。 |
| 完整 MCP、REST / GraphQL gateway、REPL、本地缓存 | 已被裁剪为外围增强或后续阶段 | 后续重新进入需求边界裁剪。 |

## 13. 横切关注点

> 校准来源：
> - `design-calibration/01_arch_step_12_cross_cutting.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“横切关注点约束表”“主线映射小表”和“横切影响说明短文”小节，了解横切约束如何压在边界、数据、交互、技术机制和方案取舍之上。

| 横切关注点 | 作用范围 | 约束要求 | 保护目标 |
|---|---|---|---|
| 安全边界：禁止正文与凭据进入 SDK truth | SDK truth、示例、错误、日志、诊断、reports / artifacts 引用、formal API / event client 边界 | 业务正文、事件 payload、生产请求 / 响应、观测正文、UI / runtime 状态正文、凭据正文不得进入 SDK truth 或报告正文；必须拒绝、脱敏或只保留引用 | 防止 SDK 越界拥有业务、事件、观测、凭据或运行时真相。 |
| 安全边界：SDK 不执行 auth / governance 决策 | caller runtime、formal API adapter、event client、credential handling | SDK 只能承接调用方提供的凭据材料保护口径，不执行身份认证、权限裁决或治理审批 | 保护 security / identity / gateway / governance 边界。 |
| 审计与可追溯：candidate 证明链 | package candidate、上游版本引用、smoke、docs runner、reports / artifacts、compatibility / deprecated 判断 | 每个 candidate 必须能追溯上游版本、验证结论、示例运行、横切默认和兼容治理材料 | 防止公共发布或局部成功掩盖不可验证。 |
| 可观测性：trace 与错误可定位但不吸收正文 | SDK call surface、formal API / fake adapter、event client view、error mapping、trace propagation | 错误和 trace 材料必须能定位语言、能力边界、candidate、上游版本和失败口径；不得保存观测日志正文或敏感正文 | 让失败可定位，同时守住数据边界。 |
| 韧性 / 恢复能力：显式失败与挂起 | formal API、`L0-bus` semantic boundary、core / bus snapshot、fake endpoint、validation runner、docs runner | 依赖未稳定或验证失败时必须显式失败、挂起或标记 stale / pending / unsupported / not verified，不得伪装成功或补造 truth | 保护同步、异步、后台承接的边界语义和候选验证可信度。 |
| 可用性：核心闭环不依赖公共注册表和全量覆盖 | 本地 package candidate、最小可验证接入、quickstart、fake / fixture target、下游消费面 | 当前 P0 必须在公共注册表、完整 MCP、REST / GraphQL、REPL、本地缓存和全量 client 缺失时仍能判断核心闭环 | 防止外围增强阻塞官方 client 基础能力。 |
| 性能 / 容量约束：SDK 不成为关键路径主瓶颈 | 嵌入式 SDK 调用、formal API adapter、event client view、error / trace / redaction 默认、docs / smoke 验证 | SDK 封装和横切默认不得成为最小接入和关键调用的主要瓶颈；长耗时验证应留在后台 / 验证边界 | 保护客户端接入体验和同步 / 后台边界。 |
| 配置与变更控制：配置不得绕开主线边界 | 三语言默认行为、trace、error mapping、redaction、credential handling、compatibility、candidate 验证 | 配置与覆写必须服从统一语义基线，不得让某语言绕开 redaction、trace、错误映射、兼容治理或上游 truth 引用 | 保护三语言一致和官方 client 语义。 |

## 14. 演进路线

> 校准来源：
> - `design-calibration/01_arch_step_13_evolution_roadmap.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“演进路线表”“触发条件小表”“当前不可接受债务表”和“阶段边界说明短文”小节，了解当前基础闭环与后续增强如何分阶段处理。

| 阶段 | 当前目标 / 范围 | 当前可接受债务 | 后续演进项 | 触发条件 |
|---|---|---|---|---|
| 当前基础闭环阶段 | 形成本地 package candidate；三语言官方语义一致；通过 formal API 或 fake / fixture 完成最小可验证接入；提供 `L0-bus` event client view；横切默认和兼容治理可追溯 | 公共注册表后移；只覆盖最小服务边界；报告格式和性能阈值后移；完整 MCP / REST / GraphQL / REPL / 本地缓存后移 | 进入公共发布、更多服务覆盖和生态增强前，先补齐对应设计裁剪 | candidate 已可重复验证，且下游消费需要稳定分发或更多能力面。 |
| 公共发布与分发阶段 | 在不改变 SDK truth 的前提下，把已验证 candidate 推向正式 package 分发渠道 | 仍可不覆盖全量 L1/L2/L3/L4；仍不承诺完整 MCP / REPL / 本地缓存 | 发布治理、包签名 / provenance、公共 release evidence、迁移公告和回滚口径 | 本地 candidate 多轮通过，且下游不再满足本地 path / workspace 消费。 |
| 服务能力覆盖扩展阶段 | 按 formal API 稳定度逐步扩展 L1/L2/L3/L4 client 覆盖 | 不要求一次覆盖全部服务；不稳定服务仍可保持 unsupported / pending | 服务 client 覆盖矩阵、能力分组、更多 fake / fixture target、跨服务一致性验证 | 多个服务边界稳定，且下游开始重复私有封装或绕开 SDK。 |
| 生态增强重新裁剪阶段 | 评估完整 MCP Client、REST / GraphQL gateway、REPL / playground、本地缓存 / 离线状态等是否进入主线 | 当前仍可不提供这些能力；缺失不影响基础闭环成立 | 若进入主线，必须重新生成需求、架构、概要和详细设计裁剪 | runtime、第三方或产品侧出现稳定需求，且现有 SDK 边界无法承接。 |
| 治理与自动化强化阶段 | 强化三语言一致性、redaction、trace、compatibility、deprecated、evidence 和 reports 的自动化治理 | 当前可先用较轻量验证证据；但不得无证据标记 verified / stable | 更强 drift 检测、兼容矩阵、报告规范、自动化迁移提示和安全回归门禁 | 手工审查无法承受 candidate 数量、语言差异或下游规模。 |

当前不可接受债务：

| 不可接受债务 | 原因 | 当前处理口径 |
|---|---|---|
| 三语言核心语义漂移 | 会破坏官方 SDK 共同心智 | 阻断 candidate stable / verified 结论。 |
| SDK 重定义 `L0-core` / `L0-bus` truth | 会形成双真相源 | 必须回到上游派生视图和 event client view。 |
| 业务正文、事件正文、观测正文或凭据正文进入 SDK truth | 会打穿数据所有权和安全边界 | 必须拒绝、脱敏或只保留引用。 |
| 无验证证据却标记 candidate verified / stable | 会让发布或使用结论不可复核 | 必须保持 not verified / failed / pending。 |
| SDK 演变为 server gateway、auth provider、UI 组件库或 runtime loop | 会越过职责边界 | 作为边界外方向处理，不进入主线。 |

## 15. 风险与待确认事项

> 校准来源：
> - `design-calibration/01_arch_step_14_risks_open_questions.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“风险表”“待确认事项表”和“当前处理口径说明短文”小节，了解哪些问题已经成为风险，哪些仍需挂起确认。

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 |
|---|---|---|---|
| SDK 随服务 client 增多而滑向 server facade | 职责边界、依赖方向、formal API adapter、服务端 truth 边界 | 当前只允许封装 formal API / fake boundary，不拥有服务端业务事实；全量覆盖后移并按服务稳定度触发 | 有条件阻塞 |
| `L0-core` / `L0-bus` 上游变化导致 candidate drift | 上游派生视图、event client view、版本引用、candidate 验证 | 要求上游版本引用、stale / pending 标记和跨语言验证结论；不伪造上游 truth | 有条件阻塞 |
| 三语言 idiomatic 差异造成平台语义漂移 | 三语言语义基线、语言表达、error / trace / redaction、deprecated | 以统一语义基线和跨语言 smoke 约束，语言表达只能 idiomatic，不能改变平台含义 | 阻塞 |
| fake / fixture endpoint 只能证明最小接入 | 最小可验证接入、candidate 验证、服务覆盖演进、验收范围 | 只声明证明最小接入，不把 fake / fixture 结果写成生产服务覆盖或业务 truth | 不阻塞 |
| redaction、trace 和 error mapping 在三语言中出现遗漏 | 横切默认、安全边界、可观测性、验收标准 | 以三语言验证和敏感值泄露一票否决约束；失败时不得标记 verified / stable | 阻塞 |
| 验证证据链不足以支撑 stable / verified 结论 | package candidate、reports / artifacts、docs runner、smoke、compatibility | 至少保留证据入口和验证结论；格式未定前不得用公共发布替代证据链 | 有条件阻塞 |
| 公共注册表、完整 MCP、REST / GraphQL、REPL、本地缓存重新混入当前 P0 | 目标与非目标、容器部署、备选方案、演进路线 | 按外围增强和后续重新裁剪处理，不作为当前基础闭环前置 | 不阻塞 |

| 待确认事项 | 影响范围 | 当前挂起口径 |
|---|---|---|
| P0 最小可验证接入采用哪个 stable formal API 或 fake / fixture target | 系统上下文、容器部署、关键交互、测试与验收 | 架构层保持“formal API 或 fake / fixture 均可”，不指定具体服务。 |
| 具体协议、transport、生成器和语言包管理选择 | 关键技术选型、概要设计、详细设计、实施计划 | 架构层只保留派生视图、adapter 和三语言语义基线，不锁定工具。 |
| 初始化耗时、包体积、微基准和关键路径性能阈值 | 横切关注点、测试方案、验收标准 | 架构层只保留“SDK 不成为主要瓶颈且必须可测量”的判断口径。 |
| SDK candidate reports / artifacts 的具体格式 | 数据所有权、横切审计、验收标准、实施计划 | 架构层只要求证据入口、验证结论和引用有效性，不规定格式。 |
| 公共发布渠道和正式发布阶段 | 演进路线、发布治理、实施计划 | 当前不纳入 P0，以本地 package candidate 作为基础闭环承载。 |
| 全量 L1/L2/L3/L4 client 覆盖顺序 | 服务能力覆盖、依赖方向、演进路线 | 当前只要求最小可验证接入，其他 client 保持 pending / unsupported。 |
| 完整 MCP、REST / GraphQL、REPL、本地缓存是否重新进入主线 | 生态增强、职责边界、演进路线 | 当前作为外围增强挂起；若后续进入，需要重新走需求、架构、概要和详细设计裁剪。 |

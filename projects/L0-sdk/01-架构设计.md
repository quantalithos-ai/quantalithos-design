## 1. 业务背景与驱动力

### 1.1 业务背景

Quantalithos 的 26 仓需要被多种技术栈消费:
- L1/L3/L4 Rust 服务
- L2 runtime 的 Python 生态
- L5 UI 的 TypeScript 生态
- 第三方 / 企业开发者

如果只有 `quantalithos-core` 的原始 proto binding:
- 使用门槛高
- 认证 / trace / 错误处理要重复封装
- 第三方开发者体验差

因此 L0-sdk 的任务不是"重复 core",而是提供**统一、友好、符合各语言习惯的高层接入层**。

### 1.2 业务驱动力

**业务驱动力**:
- SDK 是 `product/产品矩阵.md` 里的独立产品线
- 第三方接入 / 企业内部开发都需要统一入口
- UI / runtime / bridges 的接入体验直接取决于 SDK 质量

**技术驱动力**:
- 三语言 binding 版本一致性
- trace 自动传播
- ErrorCode 到语言 idiomatic error 的映射
- redaction 与安全默认值

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| Learnability | quickstart 上手时间 | ≤ 10 分钟 | 新人试用 |
| 一致性 | 三语言核心 API 名称一致率 | ≥ 90% | API diff 表 |
| 发版一致性 | 三语言包同版本齐备 | 10 分钟内 | CI |
| trace 传播 | 自动透传覆盖率 | 100% | 集成测试 |
| 安全 | redaction 命中率 | 100% | 安全测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| `quantalithos-core` 是唯一 proto 源 | L0-core 边界 | SDK 不能手写 schema |
| `quantalithos-bus` 是唯一事件主干 | L0-bus 边界 | SDK 的订阅能力只能封装 bus 语义 |
| 三语言都必须发布 | 产品矩阵 | 不能先只做某一种 |
| trace 自动传播 | observability 需求 | SDK 默认中间件必须注入 trace |
| 敏感值不落盘 | 安全红线 | 默认 redaction 开启 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| Python 包管理 | poetry / uv | 可切换 |
| TS 生成器 | protobuf-es(当前倾向) | 可切 Connect / ts-proto |
| Rust 打包形态 | 单 crate / workspace | 可调整 |
| public / internal split | 默认同一套 | 可分 `sdk-internal-python` |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| SDK 包体积 | Rust < 2MB / Python < 1MB / npm < 500KB | 安装体验 |
| CI 时长 | < 8 分钟(三语言生成 + smoke)| 开发体验 |
| example 数量 | ≤ 15 个 | 文档维护成本 |
| migration guide 数量 | 每个 major 1 份 | 可维护性 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| core proto 变更 | 中 | proto-ref 锁定 + 自动生成 |
| 各语言 idiomatic API | 中高 | 语言独立包装层 |
| 认证策略 | 中 | auth adapter 抽象 |
| trace / observability 语义 | 中 | middleware 统一注入 |
| 第三方体验 | 中 | examples + docstrings + quickstart |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **codegen + thin wrappers**(当前)| 类型一致 + 各语言体验友好 | 维护三套 wrapper |
| pure binding only | 实现最少 | 使用门槛高,体验差 | ❌ 不符合 SDK 产品定位 |
| hand-written clients | 可完全定制体验 | 漂移风险极高 | ❌ 违背 core 单一真相源 |

**最终选择**:**generated binding + language-specific thin wrapper**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 生成 binding 为底层 | 与 core 保持一致 | 生成器升级需适配 |
| wrapper 只做体验层 | 易维护 | 某些高级能力抽象有限 |
| 三语言统一版本 | 发布一致 | CI 更复杂 |
| 默认 trace / redaction | 安全、可追踪 | 调用方定制度略受限 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
External developers / L1-L6 repos
        │
        ▼
  ★ quantalithos-sdk ★
  - Rust SDK
  - Python SDK
  - TypeScript SDK
  - codegen pipeline
        │
   ┌────┴────┐
   ▼         ▼
quantalithos-core   quantalithos-bus
(proto source)      (event semantics)
```

### 4.2 职责边界

**做什么**:
- ✅ 生成三语言 binding
- ✅ 提供统一高层 client API
- ✅ 默认 auth / trace / error / redaction 封装
- ✅ 提供 quickstart / examples / migration guides

**不做什么**:
- ❌ 定义 proto schema(core)
- ❌ 实现事件总线(bus)
- ❌ 实现业务逻辑(L1+)
- ❌ 替代 UI 组件库

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| crates.io / PyPI / npm | 99.9% | 重试 + release rollback |
| GitHub Actions | 99.9% | 本地手动 generate(紧急) |
| core 包 | 100%(编译期)| 版本锁 + 回滚 |
| bus 包 | 100%(编译期)| mock event source |

### 4.4 关键依赖风险

- 三语言包装层语义漂移
- TS 生态对 gRPC / Connect 的选择未定
- 第三方示例过时导致上手失败

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Binding Generation | 通用子域 | 生成三语言类型 |
| Language Wrapper | 支撑子域 | 体验层封装 |
| Auth / Trace Middleware | 支撑子域 | 横切能力 |
| Docs / Examples | 支撑子域 | 采纳率关键 |

### 5.2 限界上下文划分

| 上下文 | 职责 | 主要目录 |
|---|---|---|
| Codegen | 生成原始 binding | `codegen/` |
| Rust SDK | Rust wrapper | `sdk-rust/` |
| Python SDK | Python wrapper | `sdk-python/` |
| TS SDK | TS wrapper | `sdk-typescript/` |
| Examples / Docs | 示例与文档 | `examples/` + `docs/` |

### 5.3 上下文映射关系

- Codegen → 三语言 wrapper(单向)
- core proto → codegen(单向)
- bus API → wrapper(可选事件能力)

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| Binding | 纯自动生成类型层 |
| Wrapper | 人工封装的高层 SDK API |
| Client | 调某个 service 的对象 |
| Subscription | 订阅事件流的高层封装 |
| Redaction | 日志 / 错误消息的敏感值遮蔽 |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

L0-sdk 同样无线上常驻业务容器,主要是源码仓 + CI + package registry。

### 6.2 容器职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| codegen runner | 生成三语言 binding | buf + shell |
| rust package build | 构建 / 测试 / 发版 | cargo |
| python package build | 构建 / 测试 / 发版 | poetry/uv + pytest |
| ts package build | 构建 / 测试 / 发版 | pnpm + tsup |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| wrapper → service | gRPC / Connect / HTTP(未来) | 语言生态适配 |
| wrapper → bus | 订阅 API 封装 | 统一事件体验 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| generated binding | codegen pipeline | 三语言 wrapper |
| docs / examples | SDK Maintainer | 开发者 |
| release metadata | CI workflow | 下游开发者 |

### 6.5 部署拓扑

仅 GitHub 仓库 + CI + package registries,无线上常驻进程。

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
quantalithos-core proto
        │
        ▼
codegen layer
   ├─▶ sdk-rust wrapper
   ├─▶ sdk-python wrapper
   └─▶ sdk-typescript wrapper
        │
        ▼
examples / docs / downstream developers
```

### 7.2 层间约束规则

- wrapper **不得手写与 proto 冲突的类型**
- wrapper 只做体验层,不改核心语义
- examples / docs 依赖 wrapper,不依赖 raw proto
- public SDK 与 internal helper 若分离,必须边界明确

### 7.3 依赖倒置接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| core proto | L0-core | codegen |
| bus event API | L0-bus | SDK wrapper |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(全部下游依赖) |
| 传出耦合 | 中(core + bus + registry tooling) |
| 不稳定性 | 中(wrapper 易变,codegen 稳定) |
| 抽象度 | 中高 |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| proto-ref.toml | SDK Maintainer | codegen | core 版本锁 | 版本漂移 |
| versions.toml | SDK Maintainer | release workflow | 三语言一致 | 发版不同步 |
| generated binding | codegen | wrapper | CI 校验 | 生成器漂移 |
| examples | SDK Maintainer | 开发者 | 文档一致性 | 示例过期 |

### 8.2 一致性层次

- **Level 1**:同语言包内部一致性(wrapper 与 generated binding 对齐)
- **Level 2**:三语言之间概念一致(不是方法名完全相同,而是抽象一致)
- **Level 3**:发版一致性(三语言同版本)

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| 某语言发版失败 | 整体 release 失败,其他语言不标 stable |
| codegen 结果不一致 | 阻断 merge,不发版 |
| 示例过时 | CI smoke test 失败,阻断 release |

## 9. 关键技术选型

### 9.1 codegen 基础: buf generate

| 维度 | 内容 |
|---|---|
| 当前选择 | buf + 三语言插件 |
| 备选方案 | 手写 wrapper + 每语言原生 proto 生成器 |
| 选择理由 | 与 core 仓统一,最小 drift |
| 演进路径 | 如某语言插件失效,局部替换插件,不改整体流水线 |
| 不可逆程度 | 中 |

### 9.2 TypeScript 包装

| 维度 | 内容 |
|---|---|
| 当前选择 | protobuf-es 倾向 |
| 备选方案 | Connect / ts-proto |
| 选择理由 | ESM 友好,与前端构建链兼容 |
| 演进路径 | N0 前最终定,后续如改需 migration guide |
| 不可逆程度 | 中 |

### 9.3 Python 包管理

| 维度 | 内容 |
|---|---|
| 当前选择 | poetry/uv 均可 |
| 备选方案 | pip only |
| 选择理由 | 开发体验优先 |
| 演进路径 | 以 CI 稳定性为准 |
| 不可逆程度 | 低 |

### 9.4 Redaction 策略

| 维度 | 内容 |
|---|---|
| 当前选择 | 默认关键字名单 + 自动脱敏 |
| 备选方案 | 调用方手动配置 |
| 选择理由 | secure by default |
| 演进路径 | 名单可扩展 / 允许用户覆写 |
| 不可逆程度 | 低 |

## 10. 备选方案与取舍

| 维度 | 方案 A:纯 binding | 方案 B:binding + thin wrapper(当前)| 方案 C:全手写 SDK |
|---|---|---|---|
| 使用门槛 | 高 | 低 | 中 |
| 漂移风险 | 低 | 低中 | 高 |
| 开发成本 | 低 | 中 | 高 |
| 体验 | 差 | 好 | 可定制但不稳定 |

**选择 B 的理由**:既保留 core 契约一致性,又提供高层体验。

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| TS transport 方案未定 | TS SDK 可能返工 | P0 |
| internal-python split 未定 | runtime 需求可能污染 public API | P1 |
| AG-UI 类型未定 | chat / console 接入不顺 | P1 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| 第三方接入失败率 > 20% | 1 Sprint | 重写 quickstart / API surface |
| migration guide 缺失导致升级失败 > 1 次 | 1 quarter | 强制每个 breaking 必带 guide |

### 12.3 演进步骤

```
阶段 1: generate raw binding
阶段 2: thin wrapper + auth/trace/error mapping
阶段 3: examples + docs + release automation
阶段 4: MCP / AG-UI / advanced tooling
```

### 12.4 目标架构

SDK 的目标不是"封装一切",而是**把常见接入路径变得顺手且一致**,复杂需求仍允许用户下潜到原生 binding 层。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| wrapper 层过厚 | 中 | 中 | 保持 thin wrapper 原则 |
| 三语言版本不同步 | 中 | 高 | versions.toml + 原子发版 |
| redaction 漏词 | 中 | 高 | 安全回归测试 |

### 13.2 边缘风险

- 某语言生态 breaking 变化过快
- 第三方需要 REST/GraphQL 而非 proto/gRPC
- 大模型调用链里 SDK 自动 trace 与上层 trace 冲突

### 13.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| TS 走 protobuf-es 还是 Connect | N0 前 | UI Tech Lead |
| runtime 是否独立 internal-python SDK | N0 前 | SDK Maintainer |
| MCP client 是内置还是插件 | N1 前 | capability-hub + sdk |

## 14. 上线策略

### 14.1 灰度方案

- 先发 prerelease / rc tag
- 选 3 个样本仓(identity / bus / chat)接入验证
- 稳定 1 Sprint 后转正式 tag

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚 |
|---|---|---|
| 某语言包不可安装 | S | yank 新版本 |
| 样本仓构建失败 | A | 回滚 proto-ref 版本 |
| redaction 漏敏感值 | S | yank + hotfix |

### 14.3 监控指标

| 指标 | 阈值 | 告警 |
|---|---|---|
| 三语言发版成功率 | < 100% | critical |
| quickstart 失败率 | > 5% | major |
| 样本仓 smoke fail | > 0 | critical |

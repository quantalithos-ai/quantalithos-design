## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L0-sdk` 不是 proto 生成结果打包目录,也不是 bus 的另一层真相仓。它是 **“开发者接入面”**。

你可以把它理解成:
- Rust / Python / TypeScript 三种语言里,开发者真正会 import 和 new 的那层统一入口
- 把 `L0-core` 的共享对象、错误语义和 metadata skeleton,变成开发者看得懂、用得顺手的高层 API
- 把 `L0-bus` 的发布、订阅、consume、trace 等总线语义,变成开发者不需要手写 transport 细节的接入接口
- 把认证、trace、错误映射、redaction、quickstart、examples、发版一致性收口到同一条接入主链里

这些事情,都由 `L0-sdk` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L0-sdk`,这些接入能力就会散落在:
- 各语言自己生成的 raw proto binding 里
- runtime / UI / bridges 各自私有的一层 wrapper 里
- 各仓自己的 auth / trace / error handling 工具函数里
- 第三方接入文档与 examples 的局部脚本里

结果就会出现:
- 三语言调用概念不一致,开发者得重新学习三套接口
- core / bus 契约虽然存在,但没有统一的 developer-facing 入口
- trace、认证、redaction、错误映射被各自重复封装
- 文档、examples、release 版本号漂移,第三方很难 10 分钟内接入

所以 `L0-sdk` 必须独立存在,作为:
> **把 core / bus 契约变成三语言一致且友好的开发者接入层的单一产品化入口。**

### 1.3 新人最容易混淆的几个词

#### Binding
就是:
> 从 `L0-core` 契约自动生成出来的原始语言类型层。

它不是开发者最终直接想用的 SDK 体验层。

#### Wrapper
就是:
> 在 binding 之上,按各语言习惯封装出的高层 SDK API。

它不是新的真相源,也不是手写 schema 层。

#### Client
就是:
> 开发者调用某类 service / capability 时真正拿在手里的高层对象。

它不是 proto stub 的原样暴露。

#### Subscription
就是:
> 在 SDK 里对 bus 订阅、消费、ack/nack、回调处理的一层高层封装。

它不是 bus consume truth 本体。

#### Redaction
就是:
> 对 token / secret / credential / password 等敏感值做默认脱敏处理。

它不是调用方可选的锦上添花,而是 secure-by-default 的基础能力。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L0-sdk/02` 时,先收稳以下前提:
- `L0-sdk` 不应按语言目录平铺理解,而应按开发者接入责任拆
- sdk 至少应拆成“binding 生成与契约对齐 / 三语言高层 client 封装 / 认证、trace 与错误映射横切 / 事件订阅与总线接入封装 / 文档、示例与发版一致性”五个主要部分
- sdk 自己拥有的真相不是 proto truth、bus truth 或业务 truth,而是 developer-facing 接入体验层真相
- `L0-sdk` 只能消费 `L0-core` 的共享基元和 `L0-bus` 的传递契约,不能反向定义 core primitive 或 bus transport truth
- 02 的重点不是“列有哪些 client 名字”,而是先把“SDK 在平台里到底是什么、和 core/bus/调用方怎么分层”讲清楚
- examples、quickstart、migration guide、release consistency 不是附属文档工作,而是 SDK 产品化接入面的组成部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的开发者接入心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,同一套平台能力要同时被 Rust 服务、Python runtime、TypeScript UI 和第三方开发者消费。用户真正需要的不是“拿到 proto binding 自己再封一层”,而是:
- 三语言里核心概念一致的高层 client API
- 默认带 auth / trace / error mapping / redaction 的安全接入体验
- bus 发布与订阅能力可直接通过 SDK 使用
- quickstart、examples、migration guide 与 release 版本一起演进

如果把这些逻辑分别散落到:
- 各语言自己的 proto 生成结果
- runtime / UI / bridges 私有 wrapper
- 文档仓里的局部脚本与示例

系统会快速退化成:
- 三语言概念一致,但开发体验不一致
- core / bus 契约存在,开发者却无法稳定、低门槛地消费
- 安全、追踪、错误语义被重复实现且容易漂移
- 第三方开发者接入速度慢,adoption 受阻

因此,本概要设计的任务就是:
> **把 `L0-sdk` 写成一个新人也能看懂的“三语言开发者接入面”,而不是把 codegen、wrapper 和文档脚本混在一起的发布仓。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 三语言 API 一致性 | 仅有 draft,无正式高层接口 | 核心概念一致率 ≥ 90% | 需正式收敛 |
| quickstart 上手时间 | 无正式 SDK 产品入口 | ≤ 10 分钟 | 需建立统一接入面 |
| trace 自动传播 | draft 已提出,无正式封装 | 100% 调用路径默认透传 | 需变成默认能力 |
| secret redaction | 只有原则,无统一实现 | 100% 命中敏感字段 | 需固定安全底座 |
| 三语言同步发版 | 仅草案约束 | 10 分钟内齐备 | 需形成产品化发版链 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让内部仓和第三方开发者都能快速、稳定、低门槛地接入 Quantalithos
- **技术问题**:如何在不破坏 `L0-core` / `L0-bus` 真相边界的前提下,把三语言 binding、wrapper、订阅接口、trace、安全与发版一致性收束成统一 SDK 接入层

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 sdk 的 developer-facing 职责 | binding / wrapper / trace / redaction / release 职责无歧义 | 文档评审 |
| 明确 sdk 与 core / bus / 调用方边界 | core 提供 primitive,bus 提供 transport contract,sdk 提供开发者接入面 | 文档评审 + 后续测试 |
| 明确三语言一致性主线 | Rust/Python/TS 核心概念一致率 ≥ 90% | cross-lang 对照 |
| 支撑后续 sdk 详细设计与测试 | 本文足以承接 `03-详细设计.md` 的 client、subscription、release 设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文定义 proto schema 本体(留给 `L0-core`)
- 不在本文定义 bus transport truth 本体(留给 `L0-bus`)
- 不在本文实现业务逻辑或 UI 组件库
- 不在本文替各语言完全抹平 idiomatic 差异
- 不在本文提前决定所有 playground / REPL / REST gateway 细节

## 4. 约束条件

### 4.1 技术约束

- `L0-core` 是唯一 proto / ErrorCode / metadata skeleton 输入源,SDK 不得手写与其冲突的契约类型
- `L0-bus` 是唯一事件传递与 consume contract 输入源,SDK 只能做封装,不能重写 transport truth
- 三语言都必须发布正式包,不能只做单语言试运行版本
- trace 自动传播必须默认开启,不能依赖调用方逐处手动补齐
- sensitive redaction 必须 secure-by-default,不能依赖调用方自觉配置

### 4.2 资源约束

- SDK 包体积必须受控,不能因为 wrapper 便利层无限长胖
- codegen + build + smoke 的 CI 时长必须受控,否则发版不可持续
- examples / docs 数量必须克制,优先保证每个示例可运行,而不是堆量

### 4.3 时间约束

- N0 阶段必须先收稳三语言统一接入主链,而不是先做 playground / REPL 等后置体验层
- TypeScript transport 方案、internal-python split、MCP client 归属等事项必须在后续详细设计前尽快收口,否则会反复牵动 API 面

### 4.4 合规约束

- secret/token/password/credential 等敏感值不得出现在日志、错误字符串或缓存持久化中
- deprecated API 至少保留 2 个 minor,并提供 migration guide
- 三语言 release 必须同版本发版,不得出现 stable 版本错位
- trace 上下文必须满足 W3C Trace Context 传播要求

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| Rust crate 包体积 | < 2MB | 安装与依赖负担 |
| Python wheel 包体积 | < 1MB | 运行时与分发成本 |
| npm package 包体积 | < 500KB | 前端加载与安装体验 |
| codegen + build + smoke CI 时长 | < 8 分钟 | SDK 维护体验 |
| quickstart 数量 | ≤ 15 个主示例 | 文档维护成本 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ L0-core                    │
                    │ - IDs / Refs               │
                    │ - DTO / Error / metadata   │
                    └────────────┬───────────────┘
                                 │ shared primitives
                                 ▼
                    ┌────────────────────────────┐
                    │ L0-bus                     │
                    │ - EventEnvelope            │
                    │ - routing / delivery       │
                    │ - subscribe consume truth  │
                    └────────────┬───────────────┘
                                 │ transport / consume contract
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ internal repos / UI / RT   │──▶│ L0-sdk                     │──▶│ developers                 │
│ - Rust services            │   │ - binding + wrapper        │   │ - Rust / Python / TS users │
│ - Python runtime           │   │ - auth / trace / errors    │   │ - third-party integrators  │
│ - TypeScript UI            │   │ - docs / examples / release│   └────────────────────────────┘
└────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L0-core` 负责共享 primitive 真相
- `L0-bus` 负责共享传递与 consume contract 真相
- `L0-sdk` 负责把这些下沉契约转成开发者真正使用的接入面
- `L1/L2/L5/L6` 以及第三方开发者是 SDK 的直接消费方
- `L0-sdk` 的角色不是再造 core/bus,而是把它们产品化为 developer-facing experience

所以 `L0-sdk` 在全局里的角色是:
> **在 core 和 bus 契约之上,把三语言开发者真正会接触的调用、订阅、认证、追踪和文档接入体验统一收束出来。**

### 5.3 系统边界

**做什么**:
- 生成三语言 binding
- 提供高层 client / subscription / auth / trace / error / redaction 封装
- 提供 quickstart / examples / migration guides
- 保证三语言 release consistency

**不做什么**:
- 不定义 proto schema 真相
- 不定义 bus transport / consume truth 真相
- 不实现业务逻辑本体
- 不替代 UI 组件层
- 不把 examples / docs 当成契约真相源

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| L0-core | 100%(编译期) | 版本锁 + 回滚,proto 变化未收稳时不发版 |
| L0-bus | 100%(编译期) | bus 接缝未稳定时,保留 mock / minimal subscription,不伪造 transport truth |
| crates.io / PyPI / npm | 99.9% | retry + release rollback,不允许部分语言标 stable |
| GitHub Actions | 99.9% | 紧急情况下本地手动 generate,但不绕过一致性门禁 |
| OTel / W3C Trace Context | 稳定 | 若缺 trace 上下文则本地生成新 traceparent |

### 5.5 关键依赖风险

- sdk / core 边界不稳会导致 wrapper 反向发明 schema 或 primitive
- sdk / bus 边界不稳会导致 convenience API 倒灌 transport truth
- 三语言包装层若只追求 idiomatic,会漂移掉核心概念一致性
- 文档与示例若脱离 wrapper 演进,quickstart 很快失效
- 某一语言先发版成功而另一语言失败时,会破坏统一版本承诺

### 6.2 主要组成部分说明

> 这里的“主要部分”不是单个语言目录,也不是单个包名。  
> 它按 **开发者接入职责 + 契约承接位置 + 横切能力 + 发版与采纳链** 来拆分。  
> 因此下面每一部分都可能跨越多个目录和语言实现,共同支撑同一段 SDK 接入主链。

#### Binding 生成与契约对齐部分

- **它是什么**: 这是 `L0-sdk` 的契约输入层,一起回答“三语言类型底座从哪里来”
- **为什么单独有它**: 如果不单列,binding 和 wrapper 会混成一层,开发者会把 codegen 结果误当 SDK 全部
- **负责什么**:
  - 锁定 core / bus 契约输入
  - 生成三语言原始 binding
  - 保证生成结果与上游契约一致
- **不负责什么 / 容易混淆点**:
  - 不负责 developer-facing 高层体验
  - 不负责手写业务语义
  - 最容易和高层 wrapper 混淆
- **与其他部分交互**:
  - 上游: `L0-core` / `L0-bus`
  - 下游: 三语言 client 封装
  - 交互类型: 契约输入型
- **后续详细设计展开点**:
  - proto-ref / versions 锁定
  - codegen pipeline / drift 校验

#### 三语言高层 Client 封装部分

- **它是什么**: 这是 SDK 的 developer-facing API 层,一起回答“开发者真正 import 的是什么”
- **为什么单独有它**: 如果不单列,调用方只能看到 raw binding,拿不到统一 client 体验
- **负责什么**:
  - 提供 Rust / Python / TS 高层 client
  - 吸收各语言 idiomatic 差异
  - 保持核心概念一致
- **不负责什么 / 容易混淆点**:
  - 不定义 core primitive truth
  - 不手写与 proto 冲突的 schema
  - 最容易和 binding 层混淆
- **与其他部分交互**:
  - 上游: binding 层
  - 下游: L1/L2/L5/L6 / 第三方开发者
  - 交互类型: developer-facing 调用型
- **后续详细设计展开点**:
  - client surface
  - cross-lang naming / idiomatic wrapper rule

#### 认证、Trace 与错误映射横切部分

- **它是什么**: 这是 SDK 的横切安全与可追踪层,一起回答“默认为什么安全、为什么好排错”
- **为什么单独有它**: 如果不单列,auth / trace / error / redaction 会被每种语言各写一套
- **负责什么**:
  - 统一 auth 封装
  - 自动 trace 传播
  - ErrorCode → idiomatic error 映射
  - 敏感值 redaction
- **不负责什么 / 容易混淆点**:
  - 不改写 core / bus 原有语义
  - 不成为独立业务逻辑层
  - 最容易和调用方自己的日志/重试逻辑混淆
- **与其他部分交互**:
  - 上游: client / subscription 调用链
  - 下游: docs / examples / runtime logs
  - 交互类型: 横切增强型
- **后续详细设计展开点**:
  - auth adapter
  - trace / redaction / error mapper

#### 事件订阅与总线接入封装部分

- **它是什么**: 这是 SDK 的 bus 接缝层,一起回答“事件能力怎样被开发者直接用起来”
- **为什么单独有它**: 如果不单列,每个调用方都会自己再封一层 subscribe / ack / callback 逻辑
- **负责什么**:
  - 封装 publish / subscribe
  - 封装 consume callback / ack / nack helper
  - 承接 bus consume contract
- **不负责什么 / 容易混淆点**:
  - 不定义 bus transport truth
  - 不实现 MQ backend 本体
  - 最容易和 bus 自身 truth 层混淆
- **与其他部分交互**:
  - 上游: `L0-bus`
  - 下游: runtime / UI / bridges / third-party consumers
  - 交互类型: 事件接入型
- **后续详细设计展开点**:
  - subscription API
  - ack/nack / callback boundary

#### 文档、示例与发版一致性部分

- **它是什么**: 这是 SDK 的产品化出口层,一起回答“开发者怎样真正学会、安装、升级和信任它”
- **为什么单独有它**: 如果不单列,examples / quickstart / release consistency 会被当成外围工作而失控
- **负责什么**:
  - quickstart / examples / docs
  - migration guides
  - 三语言版本一致性与 release consistency
- **不负责什么 / 容易混淆点**:

  - 不手写覆盖核心 wrapper 语义
  - 最容易和 marketing/demo 材料混淆
- **与其他部分交互**:
  - 上游: wrapper / codegen 结果
  - 下游: developers / package registries
  - 交互类型: 采纳与发布型
- **后续详细设计展开点**:
  - versioning / release orchestration
  - quickstart / example smoke chain

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ L0-core                    │
                    │ - service proto            │
                    │ - ErrorCode / metadata     │
                    └────────────┬───────────────┘
                                 │ contract input
                                 ▼
                    ┌────────────────────────────┐
                    │ L0-bus                     │

                    │ - consume truth            │
                    └────────────┬───────────────┘
                                 │ bus semantics input
                                 ▼
                    ┌────────────────────────────┐
                    │ L0-sdk                     │
                    │ - bindings / wrappers      │
                    │ - auth / trace / errors    │
                    │ - examples / release       │
                    └────────────┬───────────────┘
                                 │ developer-facing SDK
                                 ▼

└────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L0-sdk` 自己负责“高层 client 体验”“bus 接入体验”“auth/trace/error/redaction 横切”“文档与发版一致性”
- `L0-core` 的交互主要落在 **Binding 生成与契约对齐部分** 与 **三语言高层 Client 封装部分**,为 sdk 提供共享契约输入
- `L0-bus` 的交互主要落在 **事件订阅与总线接入封装部分** 与 **认证、Trace 与错误映射横切部分**,为 sdk 提供 publish/subscribe/consume 契约输入
- `L1/L2/L5/L6` 与第三方开发者的交互主要落在 **三语言高层 Client 封装部分**、**事件订阅与总线接入封装部分** 与 **文档、示例与发版一致性部分**,消费 developer-facing API
- quickstart、examples、migration guide 是接入主链的一部分,不是独立于架构之外的附属说明

### 7.3 分模块交互说明(逐个写)

#### 与 `L0-core` 的交互

```text
┌────────────────────────────┐
│ L0-core                    │
│ - proto / ErrorCode        │
│ - metadata skeleton        │
└────────────┬───────────────┘
             │ contract input
             ▼
┌────────────────────────────┐
│ L0-sdk                     │
│ - codegen / wrapper        │
└────────────────────────────┘
```

- `L0-core` 是 **sdk 的共享契约输入来源**
- **交互类型**: 契约输入型交互
- **主流程位置**: binding 生成、error mapping、trace metadata 接入时进入主流程
- **交互解释**:
  - core 提供 proto、ErrorCode、metadata skeleton
  - sdk 在其上生成 binding 并包出高层 client
  - sdk 不反向定义 core primitive 真相
- **高风险异常流**:
  - wrapper 手写类型反向污染 core 契约
- 后续 `03-详细设计.md` 继续展开:
  - codegen / proto-ref / error mapping contract

#### 与 `L0-bus` 的交互

```text
┌────────────────────────────┐
│ L0-bus                     │
│ - publish / subscribe      │
│ - consume truth            │
└────────────┬───────────────┘
             │ transport contract input
             ▼
┌────────────────────────────┐
│ L0-sdk                     │
│ - subscription wrapper     │
│ - event helper             │
└────────────────────────────┘
```

- `L0-bus` 是 **sdk 的事件接入契约来源**
- **交互类型**: transport/consume 输入型交互
- **主流程位置**: SDK 封装 publish / subscribe / callback / ack/nack 时进入主流程
- **交互解释**:
  - bus 提供正式传递与 consume contract
  - sdk 做开发者友好的事件接入封装
  - sdk 不直接承担 bus truth 层职责
- **高风险异常流**:
  - convenience API 反向污染 bus transport truth
- 后续 `03-详细设计.md` 继续展开:
  - subscription API / callback boundary / consume helper

#### 与 `L1/L2/L5/L6` 和第三方开发者的交互

```text
┌────────────────────────────┐
│ L0-sdk                     │
│ - clients / subscriptions  │
│ - docs / quickstart        │
└────────────┬───────────────┘
             │ developer-facing API
             ▼
┌────────────────────────────┐
│ developers                 │
│ - internal repos           │
│ - third-party integrators  │
└────────────────────────────┘
```

- 调用方是 **sdk 的直接消费层**
- **交互类型**: developer-facing consume 型交互
- **主流程位置**: service 调用、事件订阅、quickstart、upgrade guide 时进入主流程
- **交互解释**:
  - sdk 提供高层 client、subscription、error、auth、trace 体验
  - 调用方按语言习惯消费 SDK
  - 开发者体验的一致性高于原始 binding 暴露
- **高风险异常流**:
  - quickstart 与 wrapper 版本漂移导致接入失败
- 后续 `03-详细设计.md` 继续展开:
  - client surface / docs pipeline / release orchestration

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是接入层、哪个模块是接缝层、哪个模块是文档与发版层

本节**不**展开:
- 各语言具体 API 签名
- codegen 命令与 CI 细节
- subscription callback 低层实现
- migration guide 模板与版本脚本细节
- trace middleware 与 redaction 的代码级策略

这些内容留到 `03-详细设计.md` 中继续展开。

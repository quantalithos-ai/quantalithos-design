## 1. 模块职责描述

**本模块做什么**:
- 持有正式 proto-ref / versions / generated binding / wrapper contract / subscription helper / doc-release orchestration 真相
- 把 `L0-core` 的共享 primitive 与 `L0-bus` 的 transport/consume contract 落成三语言一致的 developer-facing 接入层
- 统一 auth / trace / error mapping / redaction 横切能力
- 把 quickstart / examples / migration guide / 三语言同步发版正式化

**本模块不做什么**:
- 不持有 proto schema / ErrorCode / metadata skeleton 真相
- 不持有 bus transport / consume truth 真相
- 不持有任何业务域对象和状态机正文真相
- 不把 examples、docs、playground 冒充契约源

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 sdk“为什么存在”,而是让开发者可以直接开始实现:
- core / bus 契约如何进入 codegen 与 wrapper 主线
- 三语言 client 如何在概念一致前提下做 idiomatic 封装
- auth / trace / error / redaction 如何作为横切能力进入调用链
- subscribe / publish / ack / nack helper 如何承接 bus 契约而不反向污染 bus truth
- quickstart / examples / release consistency 如何与 wrapper 和 codegen 同步演进

如果不先把这些内容采集清楚,03 很容易退化成:
- 三语言目录树说明书
- 只列几个 client 名字的 API 表
- codegen 脚本笔记
- 把 sdk wrapper 写成 bus truth 或 core truth 的替身层

#### 第 1 步:列出要实现的核心对象

- 契约输入对象: ProtoRefLock / BusContractRef / VersionLock / GeneratedBindingArtifact

#### 第 2 步:列出主流程与关键异常流

#### 第 3 步:列出要落库/持久化的对象与关系

必须先分清:
- 哪些是写模型: proto-ref lock / versions manifest / generated artifact manifest / release manifest / migration guide registry

- 哪些是 append-only: release history / deprecation history / smoke evidence history
- 哪些输入只能作为来源引用,不能反向变成 core truth 或 bus truth

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 `L0-core` 和 `L0-bus`
- 哪些输出给 Rust / Python / TS 调用方与第三方开发者
- 哪些发布动作必须在三语言一致性与 smoke 通过后才能继续
- 哪些 docs/example 只能消费 wrapper truth,不能反向定义契约

#### 第 5 步:列出最小测试输入

必须测:
- sdk wrapper ≠ core primitive truth
- sdk wrapper ≠ bus transport truth
- subscription convenience API ≠ bus consume truth
- developer-facing ergonomics ≠ cross-repo source of truth
- examples / docs ≠ contract source
- trace 自动传播、redaction 默认安全、三语言同步发版链成立

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `RustSdkClient / PythonSdkClient / TypeScriptSdkClient / QuickstartSpec` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 binding / wrapper / middleware / subscription / release 五段接入主链,`03` 却只剩语言目录说明书
- 实现者知道有 codegen,却不知道它如何与 wrapper、smoke、release 成为同一条主线
- quickstart、release、trace、subscription 各写一套互不相干的细节

### 5.2 `Binding 生成与契约对齐部分` 的实现要点

#### 5.2.1 该部分承接的概要输入
- 承接 `02` 中“Binding 生成与契约对齐部分”的职责
- 承接 core/bus contract → codegen → generated artifacts 主线
- 承接 `binding ≠ developer-facing SDK` 这条硬边界

#### 5.2.2 输入 / 输出 / 外部交互图

```text
┌────────────────────────────┐
│ L0-core / L0-bus           │
│ - proto / ErrorCode        │
│ - publish / consume API    │
└────────────┬───────────────┘
             │ contract input
             ▼
┌────────────────────────────┐
│ L0-sdk                     │
│ - ProtoRefLock             │
│ - GeneratedBindingArtifact │
│ - VersionLock              │
└────────────┬───────────────┘
             │ generated artifact output
             ▼
┌────────────────────────────┐
│ wrapper / smoke / release  │
└────────────────────────────┘
```

#### 5.2.3 涉及的对象定义

```rust
/// 表示 SDK 当前锁定的 core / bus 契约输入版本。
pub struct ProtoRefLock {
    /// core 契约引用版本。
    pub core_ref: String,
    /// bus 契约引用版本。
    pub bus_ref: String,
    /// 锁定文件的哈希摘要。
    pub digest: String,
}

/// 表示一次 codegen 产出的正式三语言 binding 工件。
pub struct GeneratedBindingArtifact {
    /// 工件自身标识。
    pub artifact_id: ArtifactId,
    /// 工件对应的语言类型。
    pub language: SdkLanguage,
    /// 工件来源的契约锁定。
    pub proto_ref_lock: ProtoRefLock,
    /// 工件产出路径摘要。
    pub artifact_path: String,
}

/// 表示本次 SDK 发版所采用的统一版本锁。
pub struct VersionLock {
    /// Rust 包版本。
    pub rust_version: String,
    /// Python 包版本。
    pub python_version: String,
    /// TypeScript 包版本。
    pub ts_version: String,
}

/// 表示三语言类别。
pub enum SdkLanguage {
    /// Rust SDK。
    Rust,
    /// Python SDK。
    Python,
    /// TypeScript SDK。
    TypeScript,
}
```

这些对象在该部分里分别承担:
- `ProtoRefLock` 负责固定上游契约输入
- `GeneratedBindingArtifact` 负责表达一次正式生成的语言工件
- `VersionLock` 负责固定三语言同步发版版本
- `SdkLanguage` 负责统一多语言工件分类语义
- 它们都只回答“契约怎样进入 SDK”,不回答开发者最终如何调用

#### 5.2.4 关键函数代码片段

```rust
/// 根据已锁定的 core / bus 契约生成三语言 binding 工件。
fn generate_bindings(
    codegen_repo: &dyn CodegenRepo,
    proto_ref_lock: ProtoRefLock,
) {
    // [proto_ref_lock.校验锁定一致性]
    // 先确认 core 与 bus 的输入锁定在本次生成链里是一致且可用的。
    proto_ref_lock.validate_locked_inputs();

    // [GeneratedBindingArtifact::从锁定生成]
    // 再按三语言逐个生成正式 binding 工件。
    let artifacts = GeneratedBindingArtifact::generate_all(proto_ref_lock);

    // [codegen_repo.保存生成工件]
    // 最后把生成结果写入 SDK 工件清单,供 wrapper、smoke 和 release 继续消费。
    codegen_repo.save_artifacts(artifacts);
}
```

这段实现守住的边界是:
- SDK 只能消费已锁定的上游契约,不能临时手写替代类型
- 先有 binding artifact,再有 wrapper contract
- 任一语言生成失败都应阻断后续 stable release 主线

#### 5.2.5 该部分的边界与非职责
- 不负责 high-level client API 体验
- 不负责 trace / redaction / error mapping 注入
- 不负责 quickstart 文案本体
- 不负责 bus consume helper 本体

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `三语言高层 Client 封装部分` 提供 generated binding 输入
- 向 `文档、示例与发版一致性部分` 提供 artifact 与 version 基线
- 从 `L0-core` / `L0-bus` 接收契约输入

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `binding ≠ developer-facing SDK` 必须写死
- proto-ref lock 与 version lock 必须可对账,不能各自漂移
- 三语言工件只要有一门失败,就不能宣称这次接入主链已完成

- 它们继承 core/bus 契约,但不反向改写 primitive 语义本体

#### 5.3.4 关键函数代码片段

```rust
/// 根据生成工件与目标服务构造高层 SDK client。
fn build_sdk_client(
    client_repo: &dyn ClientRepo,
    builder: ClientBuilder,
) {
    // [builder.校验工件兼容性]
    // 先确认目标语言、服务名和生成工件之间的契约兼容关系成立。
    builder.validate_artifact_compatibility();

    // [builder.构造语言侧 client]
    // 再按语言类别构造对应的高层 client 对象,并继承统一 auth / trace 骨架。
    let client = builder.build_language_client();

    // [client_repo.保存 client 描述]
    // 最后把 client 能力描述写入 SDK 只读目录,供 docs/example/smoke 使用。
    client_repo.save_client_descriptor(client);
}
```

这段实现守住的边界是:
- wrapper 只能站在 binding 之上生长,不能绕开 binding 手写契约
- 三语言可以 idiomatic,但必须共享同一套概念骨架
- developer-facing 便利层不得反向成为契约真相源

#### 5.3.5 该部分的边界与非职责
- 不负责 proto 输入锁定
- 不负责 redaction 规则本体
- 不负责 publish / subscribe 语义本体
- 不负责 release orchestration 主记录

```rust
fn inject_sdk_middleware(
    middleware_repo: &dyn MiddlewareRepo,
    auth_context: AuthContext,
    trace_context: Option<TraceContextCarrier>,
) {
    // [auth_context.校验认证上下文]
    // 先确认认证模式与摘要表达合法,且敏感值不会直接暴露给日志层。
    auth_context.validate_safe_shape();

    // [TraceContextCarrier::补全或透传]
    // 再优先透传已有 trace,缺失时才生成新的 traceparent。
    let trace = TraceContextCarrier::propagate_or_create(trace_context);

    // 最后把中间件快照写入 SDK 调用上下文,供 client、subscription 和 docs 示例统一复用。
```

```rust
/// 根据 bus consume contract 构造开发者可直接使用的订阅入口。
fn build_subscription(
    subscription_repo: &dyn SubscriptionRepo,
    handle: SubscriptionHandle,
) {
    // [handle.校验订阅契约]
    // 先确认事件类型、消费组与 bus contract 的最小成立条件一致。
    handle.validate_against_bus_contract();

    // [SubscriptionCallback::从句柄构造]
    // 再把底层 consume truth 收束成开发者可直接使用的高层 callback 入口。
    let callback = SubscriptionCallback::from_handle(handle);

    // [subscription_repo.保存订阅描述]
    // 最后把订阅描述写入 SDK 只读目录,供 runtime/UI/examples 统一消费。
```

### 7.10 错误码定义

| 错误码 | 含义 | HTTP / RPC 映射 | 恢复策略 |
|---|---|---|---|
| `PROTO_REF_MISMATCH` | proto-ref 与 wrapper / version 锁不一致 | 409 / FAILED_PRECONDITION | 重新锁定并生成 |
| `BUS_CONTRACT_MISMATCH` | subscription helper 与 bus consume contract 不匹配 | 409 / FAILED_PRECONDITION | 修正 helper / contract 对齐 |
| `REDACTION_RULE_MISSING` | 缺少默认安全脱敏规则 | 500 / INTERNAL | 补齐 rule set 后重试 |
| `RELEASE_MANIFEST_INCOMPLETE` | 三语言工件或 smoke 证据不完整 | 409 / FAILED_PRECONDITION | 补齐缺失语言/证据 |

### 7.11 返回值语义分类

| 类别 | 语义 | 处理建议 |
|---|---|---|
| 正常 | binding / client / subscription / release 正式建立成功 | 继续主线 |
| 可恢复异常 | 契约未对齐、某语言 smoke 失败、projection 延迟 | 修正后重试 |
| 不可恢复异常 | wrapper 越界污染 core/bus truth、sensitive 值泄露、release 证据链断裂 | 阻断并人工介入 |

### 8.1 场景 A · 契约输入进入三语言接入主链

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| proto-ref 与 artifact 不一致 | 阻断 codegen 与 release |
| 某语言 wrapper 概念漂移 | 阻断 cross-lang smoke 与发布 |
| trace 缺失 | 生成新的 traceparent 并继续 |
| redaction 未命中 | 阻断错误输出与 release |
| 某语言发版失败 | 整体 release 失败,其他语言不标 stable |

### 11.1 重试 / 降级 / 熔断 / 补偿
- codegen 某语言失败时可重试生成,但不得跳过该语言继续 stable release
- docs / smoke projection 失败可重建,但不回滚已成立的 artifact truth
- release 失败后必须保留 release history,不可静默覆盖版本状态

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| Binding 生成与契约对齐部分 | proto-ref 漂移 / 工件缺失 | lock validate / artifact completeness | 阻断生成或发布 | 重新生成 |
| 三语言高层 Client 封装部分 | wrapper 手写漂移 / service 未暴露 | client compatibility validate | 拒绝构造 client | 修订 wrapper 后重试 |
| 认证、Trace 与错误映射横切部分 | trace 缺失 / redaction 漏命中 | middleware validate | 补全 trace 或阻断输出 | 修订 rule set 后重试 |
| 事件订阅与总线接入封装部分 | subscription helper 越界污染 bus truth | bus contract validate | 拒绝构造 helper | 修订 helper 后重试 |
| 文档、示例与发版一致性部分 | quickstart 漂移 / smoke 失败 / 单语言发版成功 | release consistency validate | 阻断 release | 修订 examples / 重新 smoke |

## 12. 实现红线 / 开发禁止事项

- 不允许 wrapper 手写与 `L0-core` / `L0-bus` 冲突的契约类型
- 不允许 convenience API 反向要求 bus truth 长出 SDK 字段
- 不允许 examples / docs 成为契约源
- 不允许任一语言发版失败时仍宣称本次 SDK stable 版本完成
- 不允许 redaction 后置到日志输出之后才做

## 14. 最小可运行闭环

- core / bus 契约被正式锁定并生成三语言 binding,随后构造出至少一组可调用 client
- runtime 或 UI 侧通过高层 subscription helper 完成一次带 trace 的订阅接入,且不直接暴露底层 bus truth
- docs / examples 围绕同一 client/subscription descriptor 跑通 smoke,随后生成正式三语言 release manifest

## 15. 结论

本详细设计的核心结论是：
- `L0-sdk` 的实现主轴必须按 binding / wrapper / middleware / subscription / release 五个主要部分组织,而不是按语言目录平铺
- sdk 真相层只持有契约锁定、接入面描述、横切中间件、订阅 helper 与发版证据链,不接管 core / bus 真相本体
- 所有 quickstart、examples、smoke、release 与 migration 输出都必须建立在正式 artifact、descriptor 与 version lock 之上

后续测试与验收文档,应直接围绕这套接入主线、边界、证据链与三语言一致性展开.

### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L0-sdk` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L0-sdk` 是三语言开发者接入面,不是 proto 仓、bus 仓或 demo 仓
- `binding ≠ developer-facing SDK` 必须成立,raw binding 不能被误当高层体验层
- `sdk wrapper ≠ core primitive truth`、`sdk wrapper ≠ bus transport truth` 两条核心边界必须成立
- client / subscription 调用链必须默认具备 auth / trace / error mapping / redaction 横切能力
- `subscription convenience API ≠ bus consume truth` 必须成立,高层 helper 不得反向污染 bus truth
- examples / quickstart / migration guide / release manifest 必须围绕同一 artifact、descriptor 与 version lock 演进
- 三语言同步发版链必须成立,任一语言失败都应阻断 stable release

因此,本次验收的目的不是笼统判断“能不能生成包”,而是判断 SDK 的契约输入链、三语言接入链、默认安全链、bus 接缝链与发版证据链是否真的成立,是否可作为后续阶段的稳定基线。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| Binding 生成与契约对齐部分 | 是 | ProtoRefLock、VersionLock、GeneratedBindingArtifact |
| 三语言高层 Client 封装部分 | 是 | RustSdkClient、PythonSdkClient、TypeScriptSdkClient、ClientBuilder |
| 认证、Trace 与错误映射横切部分 | 是 | AuthContext、TraceContextCarrier、SdkErrorMapping、RedactionRuleSet |
| 事件订阅与总线接入封装部分 | 是 | PublishRequest、SubscriptionHandle、SubscriptionCallback、ConsumeAckHandle |
| 文档、示例与发版一致性部分 | 是 | QuickstartSpec、ExampleCase、MigrationGuide、ReleaseManifest |
| crates.io / PyPI / npm 产品内部实现细节 | 否 | 只验 SDK 发版接缝,不验注册表内部逻辑 |
| `L0-core` / `L0-bus` 真相本体 | 否 | 只验 SDK 如何消费其契约,不验上游仓全部细节 |
| playground / REPL / REST gateway 后置能力 | 否 | 当前不在 P0 接入主链内 |

## 4. 功能验收门禁

| 功能/场景 | 门禁条件 | 证据 | 结论 |
|---|---|---|---|
| GenerateBindings | core/bus 契约锁定一致时,必须形成三语言正式 binding artifact | codegen log / artifact 清单 / trace | [] |
| Binding 边界 | 仅有 binding 时不得宣称 SDK 已具备 developer-facing 接入能力 | artifact / descriptor compare / negative test | [] |
| BuildRustClient / BuildPythonClient / BuildTsClient | 各语言 wrapper 必须建立在正式 artifact 之上,形成高层 client descriptor | client descriptor / API 响应 / smoke | [] |
| Wrapper 边界 | wrapper 不得手写与 core primitive truth 冲突的 schema / primitive | model review / negative flow / contract compare | [] |
| InjectTrace | 缺 trace 时必须自动补全,已有 trace 时必须优先透传 | trace compare / integration log | [] |
| RedactOutput | secret/token/password/credential 命中时必须脱敏,不得原样输出 | error snapshot / security log | [] |
| BuildSubscription | bus consume contract 合法时,必须形成高层 SubscriptionHandle / Callback / AckHandle | subscription descriptor / consume trace | [] |
| Subscription 边界 | convenience helper 只能封装 bus truth,不得反向要求 bus 扩字段或改语义 | helper/bus compare / negative flow | [] |
| RunSmoke | quickstart / example 必须围绕同一 descriptor 跑通三语言 smoke | smoke report / quickstart log | [] |
| PublishReleaseManifest | 只有 smoke 全绿且三语言 version/artifact 对账一致时,才能形成正式 ReleaseManifest | release manifest / publish log / compare report | [] |
| Release consistency 边界 | 任一语言失败时不得宣称 stable release 已完成 | release CI log / registry dry-run | [] |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | wrapper 越界污染 core/bus truth / redaction 失效泄露敏感值 / 单语言成功仍发布 stable / docs 成为契约源 |
| A | 视情况 | 主线可跑但 cross-lang drift、trace 默认行为、subscription helper 边界不稳 |
| B | 可带着走 | 非关键 diff 视图、低优先级 example 或报告展示异常 |

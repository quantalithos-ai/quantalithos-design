## 3. SOP 问题回答

### 3.1 本仓一句话定义是什么？

`L0-sdk` 是 Quantalithos 面向内部产品、AI runtime、运维脚本和第三方开发者的三语言官方客户端接入层仓。

更精确地说，它不是“产生新业务能力”的仓，而是“把已经由 core、bus 和服务端定义好的能力，包装成开发者可安装、可学习、可追踪、可升级的 SDK”的仓。

### 3.2 为什么它需要单独成仓？

SDK 面向所有客户端和集成方，变化节奏与 `L0-core`、`L0-bus`、L1+ 服务端仓都不同。如果没有独立的 `L0-sdk`：

- L5/L6 产品会各自手写 client、错误映射、trace 注入和事件封装。
- L2 runtime 和运维脚本会重复封装 Python 接入能力。
- 第三方开发者会直接面对裸协议和不同服务的零散文档。
- core / bus 的底层契约会被迫承载开发者体验和语言包发布节奏。
- breaking change、deprecated API 和三语言版本同步缺少统一治理位置。

因此它必须单独成仓，作为稳定底层契约与上层消费者之间的官方接入面。

### 3.3 本仓不是什么？

| 非职责 | 原因 |
|---|---|
| 不是 core 契约真相仓 | proto / DTO、Error、TraceContext、CloudEvents schema 和 metadata 由 `L0-core` 承载 |
| 不是事件总线运行时 | 事件投递、ack、retry、dead-letter、replay 和 tap 语义由 `L0-bus` 承载 |
| 不是 L1+ 服务端聚合层 | 领域事实、业务规则和服务端 API 真相属于对应服务仓 |
| 不是身份认证系统 | SDK 可以消费 token / credential，但不拥有身份生命周期和登录鉴权真相 |
| 不是 UI 组件库 | Chat、Console、Website 等产品 UI 组件属于对应产品仓 |
| 不是本地缓存 / 状态管理库 | SDK 可以提供调用和订阅便利，但不拥有端侧状态策略 |
| 不是 runtime 执行框架 | agent loop、tool invocation、memory 和 checkpoint 属于 L2 runtime / tools 等仓 |

### 3.4 最容易与哪些相邻仓或概念混淆？

| 相邻对象 | 容易混淆点 | 边界结论 |
|---|---|---|
| `L0-core` | SDK 生成和暴露类型，容易被误认为拥有类型真相 | core 定义契约，SDK 生成并包装契约 |
| `L0-bus` | SDK 会提供事件发布 / 订阅体验，容易被误认为拥有总线语义 | bus 定义传递语义，SDK 提供客户端封装 |
| L1+ 服务仓 | SDK 暴露领域 client，容易被误认为拥有业务语义 | 服务仓拥有领域真相，SDK 只封装访问体验 |
| L5/L6 产品仓 | SDK 提供前端 / 集成调用入口，容易被误认为包含 UI 或产品工作流 | 产品仓拥有 UI 与用户流程，SDK 只提供编程接口 |
| 认证 / 安全网关 | SDK 处理 token、redaction 和请求头，容易被误认为做登录鉴权 | 网关 / identity / 调用方提供安全事实，SDK 只消费和保护凭据材料 |
| `L2-runtime` | runtime 会用 Python SDK，容易把 runtime 专用执行逻辑塞进 SDK | runtime 拥有执行 loop，SDK 只提供稳定客户端能力 |
| `L3-capability-hub` / MCP | SDK 可内置 MCP Client 能力，容易被误认为定义工具资格或 provider contract | capability-hub 定义能力和绑定，SDK 只封装调用入口 |

## 5. 改动前后对比

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 仓定位 | “三语言统一接入层” | “面向内部产品、AI runtime、运维脚本和第三方开发者的三语言官方客户端接入层仓” |
| core 关系 | 主要写 proto binding 来源 | core 是契约真相，SDK 只生成和包装类型 |
| bus 关系 | 写事件订阅接口 | bus 是事件传递语义真相，SDK 只做客户端封装 |
| 服务端关系 | 容易写成所有服务的统一 facade | SDK 不拥有服务端业务真相，只提供访问体验 |
| 产品关系 | 端侧产品通过 SDK 接入 | 产品仓拥有 UI 和用户流程，SDK 不做组件和产品工作流 |
| runtime 关系 | Python runtime 使用 SDK | runtime 执行逻辑不进入 SDK，SDK 只提供稳定客户端能力 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: SDK 只做生成 binding | 实现轻，边界极窄 | 不能解决认证、trace、错误映射、事件封装、quickstart 和跨语言体验问题 | 不采用 |
| 方案 B: SDK 做三语言官方客户端接入层 | 能统一开发者体验，减少端侧重复封装，承接产品矩阵 SDK 定位 | 需要严格防止滑成服务端聚合层或业务逻辑层 | 采用 |
| 方案 C: SDK 做跨所有服务的业务 facade / gateway | 调用方体验看似简单 | 会让 SDK 拥有业务语义和服务编排，破坏 L1+ 真相边界 | 不采用 |
| 方案 D: 各产品各自维护私有 SDK | 每个产品可快速贴合自身需求 | 类型、trace、错误、事件和版本会漂移，第三方体验不可控 | 不采用 |

## 7. 结构化中间产物

### 7.1 边界声明表

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L0-sdk` 是 Quantalithos 面向内部产品、AI runtime、运维脚本和第三方开发者的三语言官方客户端接入层仓。 |
| 本仓不是什么 | 它不是 core 契约真相仓，不是事件总线运行时，不是 L1+ 服务端聚合层，不是身份认证系统，不是 UI 组件库，也不是 runtime 执行框架。 |
| 边界对象列表 | 仓：`L0-core`；仓：`L0-bus`；层：L1+ 服务端能力；产品：L5/L6 端侧产品；能力：认证 / 安全网关；仓：`L2-runtime`；仓：`L3-capability-hub` |
| 单独成仓原因 | SDK 的开发者体验、三语言版本、兼容性和发布治理变化节奏独立于底层契约、事件总线和领域服务实现。 |

### 7.2 相邻边界说明

| 相邻对象 | 边界口径 | 不进入正式 §2 的内容 |
|---|---|---|
| `L0-core` | core 定义契约，SDK 生成并包装契约 | 具体 codegen 工具、类型目录、proto 文件布局 |
| `L0-bus` | bus 定义事件传递语义，SDK 提供客户端体验 | 具体 ack/retry/replay 实现、后端 adapter、DLQ 存储 |
| L1+ 服务仓 | 服务仓拥有业务事实，SDK 提供调用入口 | 领域状态机、业务规则、聚合根和服务端事务 |
| L5/L6 产品仓 | 产品仓拥有 UI、用户流程和页面状态，SDK 提供编程接口 | React/Vue 组件、页面路由、产品工作流 |
| 认证 / 安全网关 | 网关和调用方拥有安全事实，SDK 只消费和保护凭据材料 | 登录流程、OAuth provider 集成、权限判定 |
| `L2-runtime` | runtime 拥有执行 loop，SDK 只作为客户端依赖 | agent loop、tool invocation、memory、checkpoint |
| `L3-capability-hub` | capability-hub 定义 provider、tool、qualification 绑定，SDK 只封装调用入口 | provider contract、资格绑定、工具注册治理 |

### 7.3 单独成仓原因结论

`L0-sdk` 单独成仓，是因为它需要在稳定底层契约和多类消费者之间提供统一接入面，同时承担三语言版本同步、可学习性、错误保护、trace 传播和兼容治理；这些职责既不适合放进 `L0-core` / `L0-bus`，也不适合散落在每个产品仓或服务仓。

## 9. 待确认事项

| 编号 | 待确认事项 | 方案 A | 方案 B | 推荐 |
|---|---|---|---|---|
| Q-001 | 一句话定义是否强调“三语言官方客户端接入层” | 强调“类型生成仓” | 强调“三语言官方客户端接入层” | 推荐 B。原因是只写类型生成会低估 SDK 的产品定位和开发者体验职责 |
| Q-002 | 是否把 SDK 定义为服务端统一 gateway / facade | 作为所有能力的服务端聚合门面 | 只作为客户端接入层和语言封装 | 推荐 B。原因是 gateway / facade 会让 SDK 拥有业务语义和服务端编排，破坏仓际真相边界 |
| Q-003 | 是否把本地缓存和状态管理纳入定位 | 纳入 SDK 核心定位 | 明确排除，后续如需只作为可选增强讨论 | 推荐 B。原因是缓存和状态策略更贴近调用方产品，不应成为 SDK 主定位 |

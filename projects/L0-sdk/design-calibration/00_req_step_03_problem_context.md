## 3. SOP 问题回答

### 3.1 当前业务背景是什么？

Quantalithos 已经完成 `L0-core` 与 `L0-bus` 的深度校准，底层共享契约和事件传递语义开始稳定。接下来，L5/L6 产品、L2 runtime、运维脚本和第三方开发者都需要一种统一方式消费这些能力，而不是直接面对裸协议、零散服务接口和各仓自建 client。因此，`L0-sdk` 当前值得讨论的背景是：平台已经具备底层契约基础，但还缺少稳定的官方客户端接入层把这些能力交给多语言消费者使用。

### 3.2 当前的主要痛点或机会点是什么？

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 官方客户端接入层尚未按最新上游收束 | `L0-core` 与 `L0-bus` 已有 `00`~`07` 稳定文档，但 `L0-sdk` 仍停留在旧版三语言草案和旧 `00`~`06` 文档 | L5/L6 产品、L2 runtime、运维脚本和第三方开发者会各自理解 core / bus 能力，形成重复封装 |
| 多语言与多消费者容易产生 drift | 旧文档说明 Rust / Python / TypeScript 三语言，但没有按最新 core / bus 边界重新定义一致性、错误、trace、redaction 和事件封装问题 | 不同语言 SDK、端侧产品和 runtime 可能出现 API 名称、错误映射、trace 传播和敏感值处理不一致 |
| 旧文档口径混杂且部分过时 | 旧需求仍出现 26 仓、公共注册表发版作为 P0、MCP / REST / GraphQL / REPL 等候选增强混入主线，并缺少 `04-配置设计.md`、`07-实施计划.md` 和 `design-calibration` | 不能直接作为新版需求基线；后续架构和实现容易把 SDK 写成 binding 仓、服务端 facade 或过重产品层 |

### 3.3 这些问题能否量化？

可以做需求层量化，但不能把旧草案中的发布愿望直接当作当前 P0 问题。

| 维度 | 可用量化口径 |
|---|---|
| 稳定上游数量 | `L0-core` 与 `L0-bus` 两个直接上游已经完成 `00`~`07` 深度校准，SDK 必须重新承接它们 |
| 主要消费者数量 | 至少覆盖 L5 chat / console / runner / sync、L6 bridges / marketplace、L2 runtime、运维脚本和第三方开发者等多类消费者 |
| 语言维度 | Rust / Python / TypeScript 三语言同时存在，任何一端漂移都会放大维护成本 |
| 旧文档缺口 | 当前 `L0-sdk` 有旧 `00`~`03`、`05`、`06`，但缺新版 `04-配置设计.md`、`07-实施计划.md` 和逐 Step `design-calibration` |
| 高风险横切点 | error mapping、trace propagation、redaction、event subscription、version compatibility 都会跨语言和跨消费者复用 |

### 3.4 哪些是业务问题，哪些是技术问题？

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台需要让内部产品、AI runtime、运维脚本和第三方开发者以一致方式接入 Quantalithos 能力；如果没有官方 SDK，端侧产品和生态接入会依赖各自私有封装，开发者体验和产品协作会分裂。 |
| 技术问题 | 已稳定的 `L0-core` / `L0-bus` 需要被三语言安全、一致地消费；如果不先在需求层收束 SDK 边界，后续会出现类型生成、错误映射、trace 传播、事件封装、版本兼容和 redaction 多套实现。 |

## 7. 结构化中间产物

### 7.1 业务背景结论

`L0-core` 与 `L0-bus` 已经稳定底层契约和事件传递语义，但平台还缺少把这些能力交给 Rust / Python / TypeScript 消费者的一致官方客户端接入层。

### 7.2 现状与问题结论

| 问题编号 | 问题 | 当前表现 | 影响 |
|---|---|---|---|
| P-001 | 官方客户端接入层未按最新上游收束 | core / bus 已稳定，SDK 仍是旧版草案和旧文档 | 多类消费者会重复封装 core / bus 能力 |
| P-002 | 多语言与多消费者 drift 风险高 | Rust / Python / TypeScript 和多类消费者都需要 error、trace、event、redaction 一致口径 | API、错误、追踪和安全默认值可能漂移 |
| P-003 | 旧文档口径混杂且过时 | 26 仓、公共发包 P0、MCP / REST / REPL 候选增强、缺 `04` / `07` 和中间产物 | 无法直接驱动新版架构、详细设计和实现 |

### 7.3 问题分类结论

| 分类 | 问题编号 | 说明 |
|---|---|---|
| 业务问题 | P-001 / P-002 | 影响内部产品、AI runtime、运维脚本和第三方开发者是否能以一致方式接入平台能力 |
| 技术问题 | P-002 / P-003 | 影响类型、错误、trace、事件封装、redaction、版本兼容和后续设计实现的一致性 |

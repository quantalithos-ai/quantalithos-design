# Step 7. 核心能力闭环

> 对应 SOP: `standards/document/需求文档讨论流程_SOP.md` Step 7

## 1. 本步目标

从 `L0-sdk` 存在的必要性出发，收敛它成立所需的核心能力闭环；本步不按旧功能清单、语言包目录、接口时序、事件链路或实现阶段拆分。

---

## 2. 本步输入

| 输入 | 使用方式 |
|---|---|
| Step 2 本仓定位与边界 | 确认 SDK 是三语言官方客户端接入层，不是 core truth、bus runtime、server facade、UI 组件或 runtime 执行框架 |
| Step 4 目标与非目标 | 确认当前 P0 聚焦官方 client 接入、本地可验证、横切门禁、版本规则和文档可学习性 |
| Step 6 使用方与依赖 | 确认 `L0-core` / `L0-bus` 是强前置，L1/L2/L3/L4 是运行期封装目标，L5/L6 是下游消费者 |
| 旧 `00` / `sdk-draft` 功能线索 | 只作为功能回填来源，不直接把 codegen、package、MCP、REST、REPL 等清单当成闭环 |

## 3. SOP 问题回答

### 3.1 如果没有这个仓，系统会缺什么不可替代的能力或结构？

系统会缺少一个稳定的官方客户端接入层。即使底层共享契约、事件语义和服务端能力已经存在，端侧产品、AI runtime、运维脚本和第三方集成仍会各自封装类型、调用、事件、错误、trace、redaction、文档示例和版本兼容策略，最终形成多套私有 SDK 和多套开发者体验。

`L0-sdk` 的不可替代性不在于创造新的业务能力，而在于把已经稳定的底层契约和服务边界转译成可安装、可学习、可验证、可升级的三语言官方 client。

### 3.2 这个仓成立必须共同具备哪些能力？

`L0-sdk` 成立必须共同具备五个能力节点：

1. 三语言稳定承接能力：底层共享契约和事件语义能够被 Rust / Python / TypeScript 稳定承接。
2. 官方客户端一致能力：三语言能够形成同一套核心概念、错误语义和使用心智，同时保持语言习惯。
3. 最小可验证接入能力：开发者能够通过本地可验证的 client、示例和 fake / fixture 证明 SDK 不只是类型包。
4. 横切默认一致能力：trace、error mapping、redaction 和凭据材料保护能够在三语言默认一致。
5. 文档与兼容演进能力：quickstart、docstring、示例、版本同步和 deprecated 过渡能够持续约束 SDK 使用体验。

### 3.3 哪些能力缺一个，这个仓就不算真正成立？

| 缺失能力 | 后果 |
|---|---|
| 三语言稳定承接能力 | SDK 会退化成手写包装或单语言 client，无法承接底层稳定契约 |
| 官方客户端一致能力 | 三语言使用心智漂移，端侧产品和 runtime 会继续形成私有封装 |
| 最小可验证接入能力 | SDK 只能证明类型存在，无法证明开发者能真实完成接入 |
| 横切默认一致能力 | 错误、trace、redaction 和凭据保护会跨语言漂移，安全和观测门禁失效 |
| 文档与兼容演进能力 | SDK 难以被外部或跨团队使用，breaking change 和示例失效会直接破坏接入体验 |

### 3.4 哪些能力只是外围增强，而不是闭环核心？

| 外围增强能力 | 原因 |
|---|---|
| crates.io / PyPI / npm 公共注册表正式发布 | 重要发布阶段目标，但当前闭环可先通过本地 package candidate 验证 |
| 完整 MCP Client | 重要生态能力，但 Step 4 已裁剪为 P1 候选，不阻塞官方 client 主闭环 |
| REST / GraphQL gateway 封装 | 接入形态增强，当前不应让 SDK 变成 server facade |
| REPL / playground | 开发体验增强，不决定 SDK 主闭环是否成立 |
| 本地缓存 / 离线状态管理 | 产品侧或后续增强，不属于 SDK 当前主定位 |
| 覆盖所有 L1/L2/L3/L4 client | 完整度增强；当前闭环可先通过稳定服务边界和 fake / fixture 验证 |

### 3.5 哪些能力根本不属于这个仓？

| 边界外能力 | 归属 / 原因 |
|---|---|
| 共享契约、DTO、ErrorCode、TraceContext、CloudEvents schema 真相 | 属于 `L0-core` |
| 事件投递、ack、retry、dead-letter、replay、tap 的运行语义 | 属于 `L0-bus` |
| L1+ 服务端业务事实和领域规则 | 属于对应服务仓 |
| 登录认证、OAuth provider、权限裁决 | 属于安全入口、identity、gateway 或 governance |
| UI 组件、页面状态和产品工作流 | 属于 L5/L6 产品仓 |
| AI runtime loop、tool invocation、memory 和 checkpoint | 属于 L2 runtime / tools 等仓 |
| 公共注册表平台运营 | 属于发布阶段和基础设施流程，不是 SDK 需求闭环核心 |

## 4. 核心能力闭环图

```text
共享能力能够被三语言稳定承接
  -> 官方客户端概念能够跨语言一致成立
  -> 平台能力能够通过客户端完成最小可验证接入
  -> 错误、追踪与敏感信息保护能够默认一致生效
  -> 文档、示例与兼容演进能够持续约束使用体验
```

图示说明：

- 箭头表示能力成立的逻辑依赖，不表示运行时调用顺序、接口时序、事件传播顺序或实施顺序。
- 图中节点只写能力成立状态，不写接口名、事件名、对象字段、语言包目录、数据库动作或实现组件名。
- 公共注册表、完整 MCP、REST / GraphQL、REPL、本地缓存和全量领域 client 不进入本核心闭环图。

## 5. 改动前后对比

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 闭环组织方式 | 从三语言 API、codegen、package、认证、事件订阅、trace、redaction、发版等功能清单出发 | 从官方客户端接入层成立所需的五个能力状态出发 |
| 类型生成位置 | 容易成为闭环本身 | 作为“三语言稳定承接能力”的支撑方式之一 |
| 公共发布位置 | crates.io / PyPI / npm 像 P0 闭环前置 | 公共发布后移为发布阶段增强，当前先要求本地可验证 |
| MCP / REST / REPL | 容易混入核心能力 | 明确为 P1/P2 或开发体验增强 |
| 服务端能力 | SDK 像所有服务的统一 facade | SDK 只做客户端接入层，服务端业务 truth 不进入闭环 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 把旧功能清单直接作为核心闭环 | 迁移快，覆盖面广 | 会把 public release、MCP、REST、REPL、目录结构和实现动作混成闭环 | 不采用 |
| 方案 B: 以官方客户端接入层成立条件定义闭环 | 边界清楚，能承接用户故事、功能需求和验收 | 后续需要再把旧功能逐项映射回能力节点 | 采用 |
| 方案 C: 只把类型生成作为闭环 | 实现轻，前置少 | 无法支撑官方 client、事件封装、trace、error、redaction、文档和兼容治理 | 不采用 |
| 方案 D: 把完整生态体验作为闭环 | 目标完整 | 会把 P1/P2 增强变成当前前置，阻塞第一批实现 | 不采用 |

## 7. 结构化中间产物

### 7.1 仓存在必要性结论

`L0-sdk` 的不可替代性在于：它把底层共享契约、事件语义和服务边界，转译成 Rust / Python / TypeScript 三语言可用、可学习、可追踪、可保护敏感信息、可持续演进的官方客户端接入层。

### 7.2 核心能力闭环结论

| 节点编号 | 能力节点 | 成立标准 |
|---|---|---|
| CL-001 | 三语言稳定承接 | 三语言能够稳定承接共享契约、事件语义、错误、trace 和 metadata，不另造 truth |
| CL-002 | 官方客户端一致 | 三语言核心概念一致，同时允许符合语言习惯的表达差异 |
| CL-003 | 最小可验证接入 | 至少通过稳定服务边界或 fake / fixture 证明 client 可运行、示例可执行 |
| CL-004 | 横切默认一致 | trace、error mapping、redaction 和凭据材料保护在三语言默认一致 |
| CL-005 | 文档与兼容演进 | quickstart、docstring、示例、版本同步和 deprecated 过渡持续约束使用体验 |

### 7.3 能力层级划分表

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | 三语言稳定承接、官方客户端一致、最小可验证接入、横切默认一致、文档与兼容演进 |
| 外围增强能力 | 公共注册表正式发布、完整 MCP Client、REST / GraphQL gateway、REPL / playground、本地缓存 / 离线状态、全量 L1/L2/L3/L4 client 覆盖 |
| 边界外能力 | 共享契约真相、bus runtime、服务端业务事实、登录认证与权限裁决、UI 组件与页面状态、AI runtime loop、公共注册表平台运营 |

### 7.4 功能回填映射结论

| 能力节点 | 支撑它的功能线索 |
|---|---|
| 三语言稳定承接 | 类型生成、版本锁定、共享错误和 trace / metadata 承接 |
| 官方客户端一致 | 三语言高层 client、统一概念命名、语言 idiomatic 封装规则 |
| 最小可验证接入 | fake / fixture endpoint、quickstart 示例、cross-language smoke test、本地 package candidate |
| 横切默认一致 | trace 自动传播、ErrorCode 映射、redaction 默认规则、凭据材料不泄露 |
| 文档与兼容演进 | docstring、示例、migration guide、deprecated 过渡、版本同步和 breaking change gate |

## 9. 待确认事项

| 编号 | 待确认事项 | 方案 A | 方案 B | 推荐 |
|---|---|---|---|---|
| Q-001 | 是否把 public registry 正式发布放进核心闭环 | 放入核心闭环 | 作为发布阶段增强 | 推荐 B。原因是当前可先通过本地 package candidate 验证官方 client 闭环 |
| Q-002 | 是否把完整 MCP Client 放进核心闭环 | 放入核心闭环 | 作为 P1 增强 | 推荐 B。原因是完整 MCP 依赖 capability 口径继续收束，不阻塞 SDK 主闭环 |
| Q-003 | 是否把全量 L1/L2/L3/L4 client 覆盖放进核心闭环 | 全量覆盖才算闭环成立 | 至少一个稳定服务边界或 fake / fixture 证明接入成立，全量覆盖逐步扩展 | 推荐 B。原因是需求闭环要证明接入层成立，不应被全仓覆盖阻塞 |
| Q-004 | 是否把类型生成单独当成 SDK 闭环 | 是，类型生成即 SDK 成立 | 否，类型生成只是三语言稳定承接的支撑方式之一 | 推荐 B。原因是 SDK 不只是 binding 仓 |

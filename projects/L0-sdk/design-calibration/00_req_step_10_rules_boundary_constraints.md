# Step 10. 业务规则与边界约束

## 1. 本步目标

把 `L0-sdk` 已收敛的仓边界、核心能力闭环和功能需求钉成需求层硬规则，明确哪些不变量必须始终成立，哪些行为必须禁止，哪些变化必须显式发生，以及哪些边界不能被打穿。

## 3. SOP 问题回答

### 3.1 哪些不变量必须始终成立？

`L0-sdk` 的不变量集中在四个方向：

- SDK 必须消费 `L0-core` / `L0-bus` 的稳定契约和语义，不得创建另一套 truth。
- Rust / Python / TypeScript 的核心概念必须语义一致，语言习惯差异不得改变平台含义。
- SDK 必须保持客户端接入层定位，不拥有服务端业务事实、bus runtime、UI 状态或 runtime loop。
- 错误、trace、redaction、凭据材料保护和版本兼容必须跨语言一致可验证。

### 3.2 哪些行为必须禁止？

必须禁止的行为包括：

- 在 SDK 内定义 proto / DTO、CloudEvents schema、ErrorCode、TraceContext 或 bus delivery 语义真相。
- 在 SDK 内实现 retry、dead-letter、replay、tap 决策或 MQ 后端差异处理 truth。
- 在 SDK 内执行身份生命周期、登录认证、权限裁决或治理审批。
- 在 SDK 内隐藏服务端业务编排，使调用方误以为 SDK 拥有领域规则。
- 在错误、日志、示例输出或诊断材料中泄露 token、secret、credential、password、key 等敏感材料。

### 3.3 哪些状态变化必须显式发生，不能隐式发生？

SDK 需求层需要显式发生的变化包括：

- 上游契约或 bus 语义变化后，必须显式形成 SDK 兼容性判断和版本处理口径。
- deprecated 能力必须显式标记、说明迁移路径和过渡口径，不得静默移除。
- 三语言 candidate 发布前必须显式完成一致性验证，不得默认某一种语言通过即代表全部通过。
- 外围增强能力进入主线前必须显式重新裁剪范围，不得通过实现过程自然膨胀。

### 3.4 哪些边界不能被打穿？

不能被打穿的边界包括：

- `L0-core` 与 `L0-sdk` 的契约真相边界。
- `L0-bus` 与 `L0-sdk` 的事件语义和运行时边界。
- L1/L2/L3/L4 服务端 truth 与 SDK 客户端封装边界。
- 网关 / identity / governance 与 SDK 的认证、授权、治理边界。
- L5/L6 产品 UI / 状态与 SDK 编程接口边界。
- 公共发布平台与当前本地 package candidate 闭环边界。

### 3.5 哪些操作必须附带治理、审计或引用条件？

- 破坏性变更必须附带兼容性判断、迁移说明或 deprecated 过渡结论。
- SDK candidate 必须附带跨语言 smoke、示例运行和敏感信息保护验证证据。
- 任何对上游契约或 bus 语义的引用必须能追溯到稳定上游版本或正式边界。
- 外围增强升级为当前主线能力时，必须回到需求边界重新决策。

## 4. 当前文档问题诊断

| 位置 | 当前表现 | 问题 | 本步处理 |
|---|---|---|---|
| 旧 `00` §6.2 | 把 core 版本、versions.toml、deprecated、redaction、trace 等规则写在功能章节里 | 方向有价值，但功能和规则混写，且部分表达像实现方案 | 抽取为需求层规则 |
| 旧 `00` §3 | 三语言公共注册表同步发布像硬规则 | 与当前 P0 本地 candidate 闭环冲突 | 改为发布阶段增强，不作为当前核心规则 |
| 旧 `00` §10 | 认证、registry、MCP、Trace Context 混在外部依赖表 | 容易把外部系统依赖当成 SDK 内部规则 | 本步只写边界约束，依赖细节留到 Step 12 |
| 旧文档整体 | 没有明确禁止 SDK 重定义 core / bus / 服务端 truth | 最容易导致实现阶段越界 | 补入禁止行为和边界约束 |

## 5. 改动前后对比

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 规则位置 | 混在功能需求和接口依赖章节 | 独立形成业务规则与边界约束 |
| 契约规则 | core 版本变化时 SDK 同步 proto-ref | SDK 必须引用上游 truth，不得重定义契约或语义 |
| 版本规则 | 三语言 public release 同步 | 当前要求 candidate、兼容判断、deprecated 和迁移治理显式可验证 |
| 安全规则 | 命中字段名就 redaction | 扩展为错误、日志、示例、诊断和凭据材料保护 |
| 边界规则 | 旧文档缺少明确禁止项 | 明确禁止 SDK 成为 core truth、bus runtime、server facade、auth provider、UI 状态层 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 只保留旧 BR-001~BR-009 | 迁移快 | 规则仍偏实现和旧 P0，缺少仓边界禁止项 | 不采用 |
| 方案 B: 按不变量 / 禁止行为 / 显式变化 / 边界约束 / 审计约束重写 | 与 SOP 一致，能直接保护核心闭环 | 需要后续 Step 11~14 继续分解数据、接口和验收 | 采用 |
| 方案 C: 把规则写成接口校验条件 | 方便开发落码 | 过早进入接口和实现层，需求文档会失焦 | 不采用 |
| 方案 D: 把所有安全、发布和治理都放到非功能需求 | 非功能章节更集中 | 会漏掉 SDK 仓边界和能力不变量 | 不采用 |

## 9. 待确认事项

| 编号 | 待确认事项 | 方案 A | 方案 B | 推荐 |
|---|---|---|---|---|
| Q-001 | 是否把认证接口写成 SDK 业务规则 | 写成 SDK 统一认证规则 | 只规定 SDK 不做认证 / 授权 truth，并保护凭据材料 | 推荐 B。原因是认证 provider 和权限裁决不属于 SDK |
| Q-002 | 是否保留公共注册表同步发布为当前 P0 规则 | 保留为 P0 | 改为发布阶段增强，当前要求本地 candidate 可验证 | 推荐 B。原因是 Step 4 已裁剪公共发布前置 |
| Q-003 | 是否把 codegen 成功写成独立规则 | 独立写 codegen 规则 | 写成上游契约承接和语言产物一致规则 | 推荐 B。原因是 codegen 是实现支撑方式 |
| Q-004 | 是否要求所有外部增强能力现在就遵守完整规则 | 是，全部纳入 | 只把外围增强升级主线的决策规则写入本步 | 推荐 B。原因是当前需求只需防止范围膨胀 |

当前建议：接受上述推荐后进入 Step 11。

## 10. 进入下一步条件

- 已明确 SDK 不得重定义 core 契约和 bus 语义。
- 已明确 SDK 不得拥有服务端业务 truth、认证授权 truth、UI 状态和 runtime loop。
- 已明确跨语言概念一致、横切安全、版本兼容和 candidate 验证的需求层规则。
- 规则已覆盖不变量、禁止行为、显式变化、边界约束和审计约束。
- 没有把接口签名、数据库约束、handler 校验逻辑、事务边界或具体异常码写进规则表。

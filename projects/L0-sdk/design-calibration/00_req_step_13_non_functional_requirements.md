## 1. 本步目标

定义 `L0-sdk` 在需求层必须满足的质量约束，覆盖性能、可用性、安全、审计 / 可追溯、幂等 / 一致性和可观测性；本步不写监控平台配置、日志字段、重试算法、缓存参数、加密实现或测试方案。

## 3. SOP 问题回答

### 3.1 这个仓必须满足哪些性能要求？

`L0-sdk` 当前不是服务端高吞吐运行时，因此性能要求不应写成服务 SLA。性能重点是 SDK 不能成为客户端接入的明显瓶颈：

- package candidate 必须能在本地开发环境完成安装和 smoke 验证。
- quickstart 和示例路径必须在可接受时间内完成。
- SDK 初始化、错误映射、trace 注入和 redaction 不得成为最小接入路径的主要耗时来源。
- 具体微基准阈值可在测试方案中落地，本需求阶段给出可判断口径。

### 3.2 这个仓必须满足哪些可用性要求？

核心 SDK 闭环不得被外围能力阻断：

- 公共注册表不可用时，当前阶段仍可通过本地 package candidate 验证。
- 完整 MCP、REST / GraphQL、REPL 不可用时，核心 SDK 仍应成立。
- 至少必须有 fake / fixture endpoint 或稳定服务边界支持最小可验证接入。
- 单一语言验证失败时，不得默认整体验证通过。

### 3.3 这个仓必须满足哪些安全要求？

安全要求集中在“不越权”和“不泄露”：

- SDK 不做身份认证、权限裁决或治理审批。
- 凭据材料不得进入错误文本、日志、示例输出、诊断材料或验证报告正文。
- redaction 默认规则必须跨语言一致。
- SDK 不得保存生产请求 / 响应正文、事件 payload 正文、业务对象正文或 trace 全量正文。

### 3.4 这个仓必须满足哪些审计 / 可追溯要求？

- 每个 SDK candidate 必须能追溯到 `L0-core` / `L0-bus` 的上游版本引用。
- candidate 验证必须留下跨语言 smoke、示例运行、错误 / trace 和 redaction 证据。
- deprecated、breaking change 和迁移说明必须可追溯。
- 外围增强能力升级为主线能力时，必须能追溯需求边界重新裁剪结论。

### 3.5 这个仓必须满足哪些幂等 / 一致性要求？

- 相同上游版本和相同 SDK 配置下，三语言 candidate 的核心概念映射应保持一致。
- 三语言错误、trace、redaction 和事件语义封装不得因语言差异改变平台含义。
- repeated candidate validation 对同一输入应给出一致结论或明确说明环境差异。
- deprecated 过渡不得只在某一种语言中单独发生。

### 3.6 这个仓必须满足哪些可观测性要求？

- SDK 调用必须支持 trace 传播和错误映射可观察。
- candidate 验证必须输出可供维护者和评审者读取的证据入口。
- 失败材料必须能定位到上游版本、语言、示例或 candidate，但不得包含敏感正文。
- 示例和 smoke 失败必须可区分是 core / bus / 服务边界 / SDK 封装 / 环境问题。

### 3.7 哪些要求能量化，哪些只能给出判断口径？

可量化项包括 quickstart 完成时间、redaction 泄露次数、三语言验证覆盖、candidate 验证通过率、trace 传播覆盖和版本引用完整率。性能微基准、包体积和具体初始化耗时受实现方案影响较大，本需求阶段只给判断口径，后续测试方案再落具体测量方式。

## 4. 当前文档问题诊断

| 位置 | 当前表现 | 问题 | 本步处理 |

## 5. 改动前后对比

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 非功能分类 | Learnability、Operability、Error Protection、性能、可追溯性、兼容性等混合 | 统一按性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性检查 |
| 性能要求 | 初始化 <50ms、包体积阈值等具体数值 | 当前先要求不能成为接入瓶颈，并在测试方案中落测量阈值 |
| 发布可用性 | 公共注册表 10 分钟齐备 | 当前核心闭环以本地 package candidate 可验证为准 |
| 安全要求 | 主要写字段名 redaction | 扩展为凭据保护、禁止正文、auth 边界和跨语言一致 |
| 可追溯 | trace 自动传播和版本同步 | 扩展为上游版本、candidate、验证证据、deprecated 和外围增强裁剪可追溯 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 原样保留旧非功能指标 | 快速，数值看起来明确 | 部分指标过早绑定实现，公共发布目标与当前 P0 冲突 | 不采用 |
| 方案 B: 按六类框架重写并保留可判断口径 | 对齐规范，能支撑后续测试和验收 | 部分具体阈值需在测试方案中继续细化 | 采用 |
| 方案 C: 只写安全和兼容性 | 篇幅短，重点清楚 | 会漏掉 candidate 可用性、trace、观测和跨语言一致性 | 不采用 |
| 方案 D: 把所有阈值推迟到测试方案 | 避免需求阶段过细 | 需求文档缺少完成判断口径 | 不采用 |

## 7. 结构化中间产物

### 7.1 非功能需求结论

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|
| 性能 | SDK 不得成为最小接入路径的主要性能瓶颈。 | quickstart、示例和 candidate smoke 必须记录耗时；若 SDK 本身成为主要耗时来源，则不得判定为通过。 |
| 性能 | 初始化、错误映射、trace 注入和 redaction 必须可测量。 | 测试方案必须定义对应测量点；需求阶段不固定具体微基准阈值。 |
| 可用性 | 当前核心闭环不得依赖公共注册表正式发布。 | 在公共注册表不可用时，本地 package candidate 仍能完成安装和验证。 |
| 可用性 | 完整 MCP、REST / GraphQL、REPL 缺失不得阻塞核心 SDK。 | 这些能力缺失时，F-001~F-010 仍可验收。 |
| 可用性 | 最小可验证接入必须有稳定服务边界或 fake / fixture endpoint。 | 没有可运行验证目标时，不得判定 SDK 核心闭环成立。 |
| 安全 | SDK 不得执行认证、授权或治理决策。 | 文档、功能和接口边界中不得出现 SDK 拥有 auth / governance truth 的表达。 |
| 安全 | 凭据和敏感正文不得进入错误、日志、示例、诊断或验证报告正文。 | redaction 测试中敏感值泄露次数必须为 0。 |
| 安全 | 禁止保存正文边界必须被保持。 | 业务正文、事件 payload、生产请求 / 响应、trace 全量正文、UI / runtime 状态不得成为 SDK 数据。 |
| 审计 / 可追溯 | SDK candidate 必须可追溯到上游 core / bus 版本。 | 每个 candidate 都必须有上游版本引用。 |
| 审计 / 可追溯 | SDK candidate 必须留下跨语言验证证据。 | smoke、示例、错误 / trace、redaction 验证均需有证据入口。 |
| 审计 / 可追溯 | deprecated 和破坏性变更必须可追溯。 | 每个 deprecated / breaking change 都必须有迁移说明或过渡结论。 |
| 幂等 / 一致性 | 三语言核心概念必须语义一致。 | 同一能力在 Rust / Python / TypeScript 中不得表达不同平台含义。 |
| 幂等 / 一致性 | 同一输入下 candidate 验证结论必须稳定。 | 重复验证结果应一致；若受环境影响，必须明确说明差异来源。 |
| 幂等 / 一致性 | deprecated 过渡不得单语言漂移。 | 不允许只在某一种语言静默移除或改变语义。 |
| 可观测性 | SDK 调用必须支持 trace 传播和错误映射观察。 | trace 和错误材料能够定位语言、能力边界和上游版本，且不泄露敏感正文。 |
| 可观测性 | 示例和 smoke 失败必须可定位。 | 失败必须能区分 core / bus / 服务边界 / SDK 封装 / 环境问题。 |

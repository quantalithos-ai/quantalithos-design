## 1. 本步目标

显式收纳 `L0-sdk` 需求主链中尚未完全关闭的风险和待确认事项，避免后续架构、设计、测试或实施阶段为了填满内容而脑补确定性结论。

## 3. SOP 问题回答

### 3.1 当前还有哪些尚未关闭的风险？

当前主要风险不是“功能不够多”，而是 SDK 边界和证据链在后续阶段被写偏：

- SDK 可能随着领域 client 增多而滑向 server facade。
- core / bus 上游变化可能导致三语言 candidate 漂移。
- 三语言 idiomatic 差异可能造成概念语义不一致。
- fake / fixture endpoint 可能只能证明最小闭环，不能代表真实服务覆盖。
- redaction 和 trace 行为可能因语言生态差异产生遗漏。
- 测试报告和证据格式若后续不统一，会影响验收追溯。
- 公共注册表、完整 MCP、REST / GraphQL、REPL 可能被重新推回当前 P0。

### 3.2 这些风险会影响哪一层需求结构？

这些风险分别影响边界、功能、数据、接口、非功能和验收章节。其中最关键的是边界风险和证据风险：前者会导致 SDK 拥有不该拥有的 truth，后者会导致三语言一致性和安全要求无法被判断。

### 3.3 当前还有哪些待确认事项？

仍需挂起的待确认事项包括：

- P0 最小可验证接入到底选择哪一个稳定服务边界或 fake / fixture endpoint。
- 性能微基准、包体积、初始化耗时等具体阈值如何在测试方案中确定。
- SDK candidate 验证报告和 artifacts / reports 证据的具体格式。
- 公共注册表正式发布进入哪个阶段。
- 完整 MCP Client、REST / GraphQL、REPL 和本地缓存何时重新评估。
- 全量 L1/L2/L3/L4 client 覆盖的阶段边界。

### 3.4 哪些待确认项会影响前文结论是否成立？

若没有任何稳定服务边界或 fake / fixture endpoint，最小可验证接入无法成立，会影响核心闭环和验收。若无法形成统一 candidate 验证证据，跨语言一致、安全和可追溯验收会受影响。公共注册表、完整 MCP、REST / GraphQL、REPL、本地缓存和全量领域 client 覆盖不影响当前 P0 结论，因为前文已将其裁剪为外围增强或后续阶段事项。

### 3.5 哪些风险是当前阶段可接受的，哪些会阻塞后续推进？

当前可接受的风险：公共注册表未定、完整 MCP 未定、REST / GraphQL 未定、REPL 未定、全量领域 client 覆盖未定、具体性能阈值未定。

会阻塞后续推进的风险：没有可验证目标、无法追溯上游 core / bus 版本、三语言 candidate 不能同时形成、redaction 泄露、SDK 重定义上游 truth、SDK 存储禁止正文。

## 4. 当前文档问题诊断

| 位置 | 当前表现 | 问题 | 本步处理 |
|---|---|---|---|
| 旧 `00` §12.1 | 写三语言风格差异、发版失败、下游绕过 SDK、redaction 漏项 | 有合理风险，但和新版边界、candidate、本地验证口径未对齐 | 迁移并重写为当前风险 |
| 旧 `00` §12 | 待确认事项不够系统 | 缺少对 P0 最小可验证目标、证据格式、外围增强阶段的挂起说明 | 补充待确认事项表 |
| Step 8~Step 14 | 每步都有 Q-001~Q-004 推荐方案 | 多数已由当前链路推荐收口，不应重复当作未定 | 只保留仍影响后续设计 / 测试 / 实施的事项 |
| 当前主链 | 公共注册表、MCP、REST / GraphQL、REPL 多次出现 | 容易被后续重新误写成 P0 | 风险表和待确认表共同约束为外围增强 |

## 5. 改动前后对比

| 项 | 旧口径 | 新口径 |
|---|---|---|
| 风险范围 | 偏发布、语言差异和 redaction | 扩展到边界膨胀、上游漂移、三语言一致、fake 覆盖、证据追溯、外围增强反弹 |
| 待确认事项 | 不够明确 | 明确哪些挂起会阻塞 P0，哪些只是外围增强 |
| 公共注册表 | 像当前发版风险 | 作为外围增强阶段待确认，不阻塞当前 P0 |
| 性能阈值 | 旧文档直接写阈值 | 当前挂到测试方案中继续确认 |
| 证据格式 | 旧文档未强调 | 当前作为影响验收追溯的待确认项 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 把每个 Step 的 Q 项全部搬进本章 | 信息完整 | 会重复大量已决策内容，让真正未确认项失焦 | 不采用 |
| 方案 B: 只保留仍影响后续设计、测试、验收或实施的风险和待确认事项 | 聚焦，符合本章目的 | 需要判断哪些 Q 已被推荐方案收口 | 采用 |
| 方案 C: 不写待确认事项，直接进入追溯矩阵 | 进度最快 | 后续阶段会重新争论 P0 边界和证据口径 | 不采用 |
| 方案 D: 把风险都写成解决方案 | 看似可执行 | 违反 SOP，本章不负责做设计或实施方案 | 不采用 |

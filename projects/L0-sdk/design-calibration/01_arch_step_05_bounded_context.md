### 3. SOP 问题回答

1. 本仓内部有哪些子域或本地上下文？

   回答：本仓内部可划分为官方客户端语义核心、上游契约消费上下文、平台能力访问上下文、横切默认行为上下文、package candidate 与验证上下文、文档与兼容演进上下文,以及本地索引 / 投影 / 引用层。

2. 哪些是核心子域？

   回答：核心子域是官方客户端语义核心。它承载 SDK 作为官方 client 的共同语义、核心概念、语言映射边界和三语言一致性要求。

3. 哪些是支撑子域？

   回答：支撑子域包括上游契约消费、平台能力访问、横切默认行为、package candidate 与验证、文档与兼容演进。它们围绕官方客户端语义核心存在,但各自承载不同变化方向。

4. 哪些只是外部上下文的本地索引 / 投影 / 引用？

   回答：上游版本引用、契约派生快照、服务边界引用、fake / fixture endpoint 引用、验证证据引用、ADR / 标准 / 设计文档引用都属于本地索引 / 投影 / 引用。它们只稳定消费外部上下文,不拥有外部正文或上游 truth。

5. 它们之间的上下文映射关系是什么？

   回答：官方客户端语义核心是中心;上游契约消费为核心提供稳定输入;平台能力访问、事件客户端视图和横切默认行为围绕核心提供使用语义;candidate / 验证与文档 / 兼容演进共同证明并约束这些语义;本地索引 / 投影 / 引用只服务追溯、验证和稳定消费,不反向定义核心。

6. 为什么这些部分不能混成一个上下文？

   回答：它们的真相归属、变化速率和职责不同。官方 client 语义需要稳定一致;上游快照会随 core / bus 变化;服务访问随正式 API 变化;横切默认行为直接影响安全和观测;candidate、文档和验证面向可用性和兼容治理;引用和投影不能反向成为 SDK 或上游 truth。

### 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 核心子域 | Binding Generation 或语言 wrapper 像核心 | 官方客户端语义核心作为中心 | SDK 不是 binding-only,核心是 official client 语义 |
| 支撑上下文 | 按 codegen、语言目录、docs 拆 | 按契约消费、能力访问、横切默认、candidate 验证、文档兼容拆 | 按语义职责和变化方向划分 |
| 本地影子结构 | 未显式区分 | 单列上游版本、派生快照、服务边界、证据、标准引用 | 防止外部 truth 或证据正文变成本仓真相 |
| 语言差异 | Rust/Python/TS 分别作为上下文 | 三语言作为同一官方语义核心下的表达差异 | 避免语言包形态主导架构语义 |
| 关系图 | 类似生成链路 | 表达核心、支撑和影子层关系 | 对齐规范的限界上下文图目的 |

### 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A：按 Rust / Python / TypeScript 三语言分别划分上下文 | 语言差异清楚 | 会造成三套语义中心,削弱官方 client 一致性 | 不采用 |
| 方案 B：以官方客户端语义核心为中心,语言表达作为支撑约束 | 符合 SDK 定位,能保护三语言一致性 | 后续需要在概要 / 详细设计再展开语言包结构 | 采用 |
| 方案 C：以 codegen / wrapper / docs / release 作为上下文 | 接近旧实现草案 | 把实现流程和发布流程当成语义边界 | 不采用 |
| 方案 D：只保留一个 SDK 上下文 | 简单 | 无法表达上游快照、服务封装、横切默认、验证和兼容治理的不同变化方向 | 不采用 |

### 3. SOP 问题回答

1. 当前还有哪些尚未关闭的架构风险？

   回答：主要风险包括 SDK 随服务 client 增多而滑向 server facade、上游 core / bus 变化导致 candidate drift、三语言 idiomatic 差异造成语义漂移、fake / fixture 只能证明最小接入、redaction / trace / error mapping 漏洞、验证证据链不足、外围增强重新混入 P0。

2. 这些风险会影响哪一层架构结构？

   回答：它们分别影响职责边界、依赖方向、数据所有权、一致性策略、关键交互、技术机制、横切关注点、演进路线和后续验收。最严重的风险会直接影响 SDK 是否仍是官方客户端接入层。

3. 当前还有哪些待确认事项？

   回答：待确认事项包括 P0 最小可验证目标、具体协议 / 生成器 / 包管理、性能阈值、candidate reports / artifacts 格式、公共发布渠道与阶段、全量服务覆盖顺序、完整 MCP / REST / GraphQL / REPL / 本地缓存是否重新进入主线。

4. 哪些待确认项会影响前文结论是否成立？

   回答：P0 最小可验证目标和 evidence 格式会影响当前基础闭环能否被验证；协议、生成器和包管理会影响概要 / 详细设计落地但不改变当前架构边界；公共发布、全量覆盖和生态增强会影响演进路线，但不改变当前 P0 成立标准。

5. 哪些风险是当前阶段可接受的，哪些会阻塞后续推进？

   回答：fake / fixture 只能证明最小接入、公共发布后移、全量覆盖后移、性能阈值后移属于可接受约束，不阻塞当前架构继续推进。三语言语义漂移、重定义上游 truth、正文或凭据进入 SDK truth、无验证证据标记 stable、SDK 越界成为 gateway / auth / runtime 是阻塞性红线。

### 7. 结构化中间产物

#### 7.1 风险表

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|
| SDK 随服务 client 增多而滑向 server facade | 职责边界、依赖方向、formal API adapter、服务端 truth 边界 | 当前只允许封装 formal API / fake boundary，不拥有服务端业务事实；全量覆盖后移并按服务稳定度触发 | 有条件阻塞 | 一旦 SDK 开始承接服务端业务编排，则阻塞当前架构主线。 |
| `L0-core` / `L0-bus` 上游变化导致 candidate drift | 上游派生视图、event client view、版本引用、candidate 验证 | 当前要求上游版本引用、stale / pending 标记和跨语言验证结论；不伪造上游 truth | 有条件阻塞 | 变化本身不阻塞，但未形成兼容判断和验证证据时阻塞 stable / verified。 |
| 三语言 idiomatic 差异造成平台语义漂移 | 三语言语义基线、语言表达、error / trace / redaction、deprecated | 当前以统一语义基线和跨语言 smoke 约束，语言表达只能 idiomatic，不能改变平台含义 | 阻塞 | 三语言语义一致是当前基础闭环条件，漂移会直接破坏主线。 |
| fake / fixture endpoint 只能证明最小接入 | 最小可验证接入、candidate 验证、服务覆盖演进、验收范围 | 当前只声明证明最小接入，不把 fake / fixture 结果写成生产服务覆盖或业务 truth | 不阻塞 | 这是当前可接受债务，但会限制验收声明范围。 |
| redaction、trace 和 error mapping 在三语言中出现遗漏 | 横切默认、安全边界、可观测性、验收标准 | 当前以三语言验证和敏感值泄露一票否决约束；失败时不得标记 verified / stable | 阻塞 | 该风险直接影响安全、审计和可观测主线。 |
| 验证证据链不足以支撑 stable / verified 结论 | package candidate、reports / artifacts、docs runner、smoke、compatibility | 当前要求至少保留证据入口和验证结论；格式未定前不得用公共发布替代证据链 | 有条件阻塞 | 如果证据缺失，阻塞 candidate stable / verified；格式细节本身后移。 |
| 公共注册表、完整 MCP、REST / GraphQL、REPL、本地缓存重新混入当前 P0 | 目标与非目标、容器部署、备选方案、演进路线 | 当前按外围增强和后续重新裁剪处理，不作为当前基础闭环前置 | 不阻塞 | 风险在于范围膨胀；只要继续按裁剪口径处理，不阻塞当前主线。 |

#### 7.2 待确认事项表

| 待确认事项 | 影响范围 | 缺失确认 | 当前挂起口径 | 说明 |
|---|---|---|---|---|
| P0 最小可验证接入采用哪个 stable formal API 或 fake / fixture target | 系统上下文、容器部署、关键交互、测试与验收 | 缺具体目标边界和可运行验证对象确认 | 架构层保持“formal API 或 fake / fixture 均可”，不指定具体服务 | 不影响架构边界，但会影响后续测试和实施落点。 |
| 具体协议、transport、生成器和语言包管理选择 | 关键技术选型、概要设计、详细设计、实施计划 | 缺具体技术栈和语言生态决策 | 架构层只保留派生视图、adapter 和三语言语义基线，不锁定工具 | 这些选择影响实现，但不应反向改变当前架构主线。 |
| 初始化耗时、包体积、微基准和关键路径性能阈值 | 横切关注点、测试方案、验收标准 | 缺性能预算的具体阈值和测量方法 | 架构层只保留“SDK 不成为主要瓶颈且必须可测量”的判断口径 | 阈值需要测试方案承接，当前不预支数字。 |
| SDK candidate reports / artifacts 的具体格式 | 数据所有权、横切审计、验收标准、实施计划 | 缺报告目录、字段、命名和证据格式确认 | 架构层只要求证据入口、验证结论和引用有效性，不规定格式 | 格式未定不阻塞架构，但会影响后续验收和实现交接。 |
| 公共发布渠道和正式发布阶段 | 演进路线、发布治理、实施计划 | 缺进入公共 registry 的阶段、渠道和治理规则确认 | 当前不纳入 P0，以本地 package candidate 作为基础闭环承载 | 公共发布有价值，但不能替代当前可验证闭环。 |
| 全量 L1/L2/L3/L4 client 覆盖顺序 | 服务能力覆盖、依赖方向、演进路线 | 缺各 formal API 稳定度和下游需求排序确认 | 当前只要求最小可验证接入，其他 client 保持 pending / unsupported | 覆盖顺序需要随服务稳定度和下游重复封装压力确定。 |
| 完整 MCP、REST / GraphQL、REPL、本地缓存是否重新进入主线 | 生态增强、职责边界、演进路线 | 缺稳定需求、边界压力和重新裁剪结论 | 当前作为外围增强挂起，不写入当前主线 | 若后续进入，需要重新走需求、架构、概要和详细设计裁剪。 |

#### 7.3 当前处理口径说明短文

本章把已经明确会影响 SDK 主线成立的问题写成风险，把仍缺具体目标、格式、阶段或技术栈确认的问题写成待确认事项。已被前文确认的红线不重复包装成待确认项；可接受债务也不自动升级为风险，除非它开始影响 candidate、三语言一致、数据边界或验收结论。当前处理口径只说明如何约束、挂起或保守承接，不在本章给出实现方案。

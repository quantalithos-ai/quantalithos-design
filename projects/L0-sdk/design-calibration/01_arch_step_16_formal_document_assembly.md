#### 7.2 术语统一表

| 统一术语 | 使用口径 |
|---|---|
| `L0-sdk` | 固定使用仓名，不写成 SDK 仓、sdk 层或 sdk-draft 主线 |
| 官方客户端接入层 | 本仓一句话定位，避免写成 binding-only、gateway、auth provider、UI 或 runtime |
| 上游契约派生视图 | 从 `L0-core` / `L0-bus` / formal APIs 派生出的 SDK 消费视图，不拥有上游 truth |
| 官方语义封装 | SDK 自身拥有的 client 语义、默认行为和三语言一致边界 |
| 三语言语义基线 | Rust / Python / TypeScript 共享平台语义，语言表达可 idiomatic |
| formal API / fake boundary adapter | 运行期服务边界和最小验证边界的接入机制，不是源码依赖服务仓 |
| `L0-bus` 语义事件客户端视图 | SDK 的事件 client 体验，不拥有 delivery、retry、DLQ、replay 或 tap truth |
| package candidate | 当前 P0 的本地候选承载，不等同于公共注册表发布 |
| verified / stable / not verified / stale / pending / unsupported | 候选、快照、接口或证据的状态表达，禁止用成功词掩盖缺证据或未稳定 |

#### 7.3 正式文档整理规则

- 正式文档按 `架构设计书写规范.md` 的 18 章主链重建。
- 每个正式章节开头必须列出具体 `design-calibration` 校准来源。
- 正式文档只摘录和整理 Step 1~15 已确认结论，不新增架构判断。
- Step 与正式章节不是机械复制关系；跨章结论按正式章节语义重组。
- 未确认项保留在 §15，不得在正文前置章节写成确定结论。
- `ADR 索引` 只写候选，不创造正式 ADR 编号。
- `参考` 章节只列来源，不重复需求追溯矩阵和 ADR 候选内容。

#### 7.4 交叉引用结论

| 引用方向 | 处理方式 |
|---|---|
| 正式章节到中间产物 | 每章用“校准来源”和“延伸阅读”引用具体文件 |
| 架构到需求 | §1 引用 `00-需求文档.md`，§16 用追溯矩阵关联需求章节 |
| 架构到后续文档 | 文档元信息列出 `02`~`07`，正文不提前定义概要、详细、测试或实施细节 |
| 架构到全局标准 | §18 列 `全局项目依赖关系与裁剪规则.md`、`子项目遵循规范清单.md` 和相关 architecture 文档 |
| ADR 与参考 | §17 保留候选索引；§18 只保留参考来源 |

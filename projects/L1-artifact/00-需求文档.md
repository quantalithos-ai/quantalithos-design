## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的每一次需求、设计、代码、测试、发布、复盘,最终都要沉淀为**制品(Artifact)**。制品不是附件,而是平台里的第一类业务对象:
- work 需要用它判断 WorkItem 是否 done
- governance 需要用它承载 AIIA / SoA 双身份
- process 需要用它承接 Activity outputs
- archive 需要用它打归档包

因此 artifact 域必须提供:
- 16 种 kind 的状态机
- 7 种关系的血缘图
- Baseline 冻结语义
- DatasetArtifact 数据治理扩展
- hash 防篡改

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点 |
|---|---|---|
| 设计文档 | `domain/artifact/README.md` 1074 行 | 设计完整,仓级需求层未显式定义 |
| 16 种 kind | 已设计 | 仓级验收标准未落地 |
| 7 种关系 | 已设计 | 血缘查询与性能目标未映射到仓级需求 |
| Baseline | 已设计 | 与 process / governance / work 联动尚未代码验证 |
| DatasetArtifact | 已设计 | provenance / bias / quality 语义重,需明确样板 |

### 2.3 为什么要做(量化依据)

- 没有 artifact 域,平台没有"可审计产出"这一根基
- 预计规模:5000w Artifact × 1.5 亿 Relation,是平台最重的持久化仓之一
- `artifact.content_tampered` 是全平台最严重的审计事件之一

### 2.4 业务问题 vs 技术问题

- **业务问题**:如何把软件工程中的所有产出统一成可管理、可审计、可追溯的对象
- **技术问题**:内容存储抽象、关系血缘图、Baseline pin、hash 防篡改、多后端内容存储、Dataset 治理

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 创建 requirement / design / code / test-report 等 Artifact
2. 把 Artifact 通过 7 种关系连成血缘图
3. 冻结 Baseline(需求 / 设计 / 发布)
4. 通过 hash 校验发现篡改并发 critical 事件
5. DatasetArtifact 承载 provenance / bias / quality 信息

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **开发者**,我想要 **创建代码制品并关联到 WorkItem**,以便 **后续能被审查、批准、归档** |
| 优先级 | P0 |
| 验收条件 | **Given** WorkItem 存在 **When** CreateArtifact(kind=code) **Then** 返回 Artifact.state=initiated 且可附 relation |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **Reviewer**,我想要 **审批制品并触发 work 域 done 判据**,以便 **项目状态可自动推进** |
| 优先级 | P0 |
| 验收条件 | **Given** Artifact reviewed **When** ApproveArtifact **Then** 发 `artifact.approved` 且下游 work 可据此判断 |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **Auditor**,我想要 **从任意发布制品回溯到需求 / 设计 / 测试的血缘链**,以便 **追责和审计** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个 release artifact **When** 调 GetLineage(depth=5) **Then** 返回全链路关系图 |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **治理系统**,我想要 **让 AIIA / SoA 同时是 Governance 对象和 Artifact**,以便 **双边都能引用同一版本事实** |
| 优先级 | P0 |
| 验收条件 | **Given** governance 发布 AIIA/SoA **When** artifact 同步 **Then** 双身份状态一致 |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **平台**,我想要 **在内容被篡改时立即发 critical 事件**,以便 **快速触发审计介入** |
| 优先级 | P0 |
| 验收条件 | **Given** 每日 hash 扫描发现不匹配 **When** 检测到篡改 **Then** 发 `artifact.content_tampered` |

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 聚合 / 类型 | 生命周期 |
|---|---|---|
| Artifact | 聚合根 | initiated → reviewed → approved / published / archived |
| ArtifactRelation | 值对象 / 关系 | append-only |
| Baseline | 聚合根 | created → superseded |
| DatasetArtifact | Artifact 特化 | 同 Artifact |

### 9.2 数据关系

```
Artifact
  ├─ relations[] (contains / derives_from / verifies / ...)
  ├─ quality_tags
  ├─ content_ref
  └─ hash

Baseline
  └─ members[] (artifact_id + version + hash)
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| approved / published Artifact | 长期 | archive |
| archived Artifact | 冷存 | restore 可选 |
| Baseline | 长期 | 永久引用 |
| tampered 事件证据 | 长期 | observability / archive |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 血缘查询递归过深变慢 | 中 | 高 | 深度限制 + 索引 |
| 多后端内容存储一致性 | 中 | 高 | hash / metadata 为统一真相 |
| AIIA/SoA 双身份不同步 | 中 | 高 | 对账 + replay |
| tampered 误报 | 低 | 高 | hash + 签名双重校验 |

### 12.2 边缘风险

- GDPR 物理删除要求与 baseline 永久 pin 冲突
- 大型 Dataset provenance 体量过大
- 跨项目复用 artifact 带来引用复杂度

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 内容存储统一抽象层具体形式 | N2 前 | artifact |
| GDPR 物理删除策略 | N2 前 | artifact + governance |
| lineage 查询是否引入 graph 引擎 | N2 后 | artifact + SRE |

|---|---|

| 本仓不是什么 | L1-artifact 不是工作事实仓、过程执行仓、治理决策仓、对话显化仓、workspace 视图仓、observability 审计存储仓、archive 归档恢复仓、method-library 定义仓、runtime / capability-hub 执行仓或具体内容存储后端。 |

## 3. 背景与问题定义

> 校准来源：
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_03_problem_context.md` 的“结构化中间产物”“回填草稿”和相关停审小节,了解本章结论如何从讨论收敛而来。

### 3.1 业务背景

Quantalithos 的需求、设计、代码、测试、发布和复盘都会形成需要长期引用的制品事实。这些事实必须可审计、可追溯、可冻结,不能退化为附件、日志、视图、归档包或相邻仓的临时状态。

随着 work、process、governance、conversation、workspace、observability 和 archive 都会引用或消费 Artifact,平台需要先把 `L1-artifact` 的问题层重新收束,避免旧材料中的功能、标准、性能和实现想象直接替代需求问题定义。

### 3.2 现状与问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 制品事实缺少新版需求层收束 | 旧 README 和旧 `00-需求文档.md` 已把业务背景、对象清单、功能设想、性能数字、技术栈、事件和验收混写,本轮需要重新把这些内容压回需求问题层。 | 后续 `01~07` 容易继承未闭口的对象、规则、接口、NFR 或实现假设,导致需求、设计、测试和实施边界反复串线。 |
| 制品事实容易被相邻仓各自解释 | work、process、governance、conversation、workspace、observability 和 archive 都会引用、消费、展示或封存 Artifact,但它们不拥有 Artifact 正文、版本、血缘与基线事实。 | 若问题层不先收束,相邻仓可能复制正文、重建血缘、私自冻结基线或把视图、日志、归档包当成 Artifact 真相,形成多真相。 |
| 问题、方案和量化指标容易混层 | 旧材料把多后端内容存储、hash 防篡改、`GetLineage`、`artifact.content_tampered`、P95、规模数字和 kind / relation 数量写进背景或痛点。 | 若本章直接继承这些说法,会把方案、功能、NFR 或测试指标伪装成问题定义,后续实现阶段容易缺正式 schema、port、state、mapper、config 或 evidence 真相源。 |

### 3.3 业务问题 vs 技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | Quantalithos 缺少统一的可审计制品事实语言,难以稳定说明平台产出了什么、哪个版本、基于什么、是否可追溯、是否已冻结为基线;相邻仓和审计方容易对同一 Artifact 正文、版本、血缘与基线事实产生不同理解。 |
| 技术问题 | 如果需求层不先收束制品事实边界和问题定义,后续设计与实现容易继承旧材料中的对象清单、事件名、性能数字、存储方案和验收想象,进而在 schema、port、state、mapper、config、evidence 等正式真相源上出现缺口或私补口。 |

### 3.4 量化与旧材料处理口径

旧材料中的 P95、容量、覆盖率、hash 校验耗时、`16 kind`、`7 relation`、功能清单、事件名和技术栈,不作为本章已经确认的问题量化或设计结论。这些内容只作为后续核心能力、功能、业务规则、数据归属、接口、非功能和验收阶段的审计输入。

| 非目标 | 不做原因 |

| audit log store / trace storage / metrics / alert stream / 观测物理存储 | 属于 `L4-observability`;`L1-artifact` 不替代观测和审计日志存储。 |
| 归档包 / 长期保留策略 / 恢复编排 / 跨域快照包 | 属于 `L4-archive`;`L1-artifact` 不拥有归档包装和恢复编排真相。 |
| MethodContent / WorkProductDefinition / Artifact kind 定义来源 / ProcessTemplateDef | 属于 `L3-method-library`;`L1-artifact` 不拥有方法定义或 artifact 类型定义源。 |
| runtime 执行 / 工具调用 / 自动化策略执行 / policy cache | 属于 `L2-runtime` 等执行边界;`L1-artifact` 不执行运行时策略。 |
| capability registration / tool adapter / whitelist runtime decision | 属于 `L3-capability-hub`;`L1-artifact` 不拥有能力注册或工具调用真相。 |
| 外部内容存储 / 向量检索系统 / Git / S3 / inline / URL / PostgreSQL 等具体基础设施选型 | 属于后续架构、配置或外部基础设施;本章不把实现后端写成需求目标。 |
| 具体功能清单、业务规则、数据归属、接口、NFR、验收、架构、配置和实施计划定稿 | 分别后置到后续需求章节和后续设计文档;本章只收束目标与非目标。 |

### 4.3 范围收束

本次需求范围收束在可审计制品事实主题,即 Artifact 正文、版本、血缘与基线事实的需求边界。`L1-artifact` 不接管工作、过程、治理、对话、工作台、观测、归档、方法定义、运行执行、能力注册或基础设施选型真相;旧材料中的对象、功能、规则、性能、容量和技术方案只能作为后续需求与设计讨论的审计输入。

## 5. 用户与角色

> 校准来源：
> - `design-calibration/00_req_step_05_users_roles.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_05_users_roles.md` 的“结构化中间产物”“回填草稿”和相关停审小节,了解本章结论如何从讨论收敛而来。

### 5.1 角色识别口径

本章只识别会接触 `L1-artifact` 制品事实的身份角色。这里的制品事实指 Artifact 正文、版本、血缘与基线事实。

角色识别不以相邻仓、接口动作、状态结果或权限操作为依据。`L1-work`、`L1-process`、`L1-governance`、`L4-archive`、`L4-observability` 等是后续使用方与依赖线索,不是本章角色。创建、更新、Approve、Baseline、Archive、lineage 查询、integrity / tampered 检查等动作后移到后续能力、功能、规则、数据、接口和验收章节。

### 5.2 角色说明表

| 角色 | 类型 | 使用场景 | 边界 |
|---|---|---|---|
| 制品作者 / 产出者 | 人类产出角色 | 产出或提交候选制品,使工作产物进入 Artifact 正文、版本和血缘事实语境。 | 不定义创建接口、Artifact kind、状态流转或权限规则。 |
| AI member / 自动化产出者 | 平台成员 / 自动化来源角色 | 在受控自动化语境中产生候选制品输入,使自动化产出能够进入可审计制品事实链。 | 身份、runtime 执行、工具调用和能力授权真相不归 `L1-artifact`。 |
| 制品审查者 / Reviewer / QA | 人类审查角色 | 在审查语境中查看制品版本、正文摘要、血缘和基线候选,为后续制品事实稳定提供审查输入。 | 不定义 approve / reject 状态、审查规则、测试流程或验收条件。 |
| 制品负责人 / Owner | 人类管理 / 责任角色 | 在责任语境中确认制品事实归属、可引用性、版本稳定性和基线准备。 | 不定义 admin 权限、Gate 决策、Baseline pin 规则或组织权限模型。 |
| 项目 / 领域负责人 | 人类业务消费角色 | 在项目、过程、工作或发布语境中消费制品事实,理解产出状态和跨域引用关系。 | 不拥有 Artifact truth,也不把 WorkItem、process output 或发布状态写入本仓角色。 |
| 审计者 / 合规查看者 | 人类审计角色 | 查看与复核制品版本、血缘、基线和完整性证据,确认制品事实可追溯。 | 不拥有 observability 存储、审计报表、tampered 规则或查询接口契约。 |
| 制品系统 actor | 系统接触角色 | 代表平台以受控方式提交、消费或维护制品事实,用于系统级自动化接触语境。 | 不展开为具体相邻仓、事件名、consumer、RPC 或 adapter。 |
| 运维 / 后台任务 | 系统维护角色 | 在技术维护语境中执行重建、对账、扫描准备和派生维护,不创造业务制品结论。 | 不定义 job、repository、schema、配置、扫描规则或业务裁决。 |

### 5.3 权限差异口径

本章不形成正式权限矩阵。旧材料中的创建、更新、Approve、Baseline、Archive 已经属于功能、规则、数据、接口或验收粒度,不能作为本章权限规则。

当前仅保留角色差异方向:产出角色使候选产物进入 Artifact 事实语境;审查角色接触版本、正文摘要、血缘和基线候选;责任角色承担归属、可引用性、版本稳定性和基线准备语境;消费角色消费制品事实但不拥有 Artifact truth;审计角色复核版本、血缘、基线和完整性证据;系统接触和维护角色只表达受控接触语境,不创造业务结论。

## 7. 核心能力闭环

> 校准来源：

`L1-artifact` 的核心能力闭环围绕可审计制品真相成立:先通过“制品事实承载”让平台产出成为正式 Artifact truth;再通过“制品版本化”形成可长期引用、替代和比较的版本事实;随后通过“制品血缘关联”表达来源、影响、替代和追溯语义;再通过“制品基线冻结”形成受控 Artifact 版本集合;最后通过“制品事实可消费表达”让相邻仓稳定引用和消费 Artifact truth,而不复制、重建或私自解释这些事实。

### 7.3 能力层级划分

核心能力固定为 5 个:制品事实承载、制品版本化、制品血缘关联、制品基线冻结、制品事实可消费表达。搜索、浏览、projection、读模型、报表、通知、归档消费、观测消费、console / sync / SDK 友好输出属于外围增强,可在后续功能、接口、NFR 或验收中讨论,但不进入核心闭环。work、process、governance、conversation、workspace、archive、observability、method-library、runtime、capability-hub 的 truth 只能作为依赖、消费或相邻仓边界讨论,不属于 `L1-artifact` 核心能力。

Artifact 搜索 / 浏览 / 列表发现、Artifact / lineage / baseline 预览、读模型 / projection / 报表、通知 / 事件感知、归档消费友好输出、观测 / 审计消费友好输出、SDK / console / sync 友好输出可以作为后续功能、接口、NFR 或体验增强讨论输入,但不作为核心闭环成立前置,也不占用 `FR-ART` 编号。

WorkItem done、Project baseline、工作状态管理、Activity output、Process status、Governance Gate、AIIA、SoA、conversation message、workspace layout、archive package、observability trace、method definition、runtime job、capability registration 等候选不得进入 `L1-artifact` 正式功能需求表。

## 10. 业务规则与边界约束

## 12. 接口与依赖

> 校准来源：
> - `design-calibration/00_req_step_12_interfaces_dependencies.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_12_interfaces_dependencies.md` 的“结构化中间产物”“回填草稿”和相关停审小节,了解本章结论如何从讨论收敛而来。

本章只定义 `L1-artifact` 在需求层的能力级接口与依赖边界,不定义 API 路径、Command / Query 名、DTO、事件 payload、port、adapter、repository、projection、cache、存储后端、配置、NFR、验收或实施边界。

### 12.1 对外能力接口

`L1-artifact` 的对外能力接口沿五个核心能力节点组织:

| 能力节点 | 对外能力接口 |
|---|---|
| 制品事实承载 | 正式制品事实纳管、自动化产出事实收束、Artifact fact 读取与引用、Artifact fact 与派生材料区分、Artifact fact 变化可感知。 |
| 制品版本化 | 稳定版本事实形成、自动化迭代版本收束、Artifact version 读取与引用、历史版本追溯读取、Artifact version 变化可感知。 |
| 制品血缘关联 | 正式血缘语境建立、自动化产出关系收束、Artifact lineage 读取与引用、血缘审计追溯读取、Artifact lineage 变化可感知。 |
| 制品基线冻结 | 受控版本集合形成、基线候选与冻结语境收束、Artifact baseline 读取与引用、历史基线审计追溯读取、Artifact baseline 变化可感知。 |
| 制品事实可消费表达 | 稳定 Artifact truth 引用表达、跨仓消费边界表达、自动化 / runtime 消费边界表达、审查责任与协作消费一致、跨仓审计回指与事实解释、Artifact truth 消费变化可感知。 |

外围增强能力只改善发现、展示、通知、归档、观测、访问或同步体验。Artifact 搜索 / 浏览 / 列表发现、Artifact / lineage / baseline 预览、读模型 / projection / 报表、通知 / 事件感知、归档消费友好输出、观测 / 审计消费友好输出、SDK / console / sync 友好输出不得成为 Artifact fact、version、lineage、baseline 或可消费表达成立的前置条件。

### 12.2 外部依赖边界

`L1-artifact` 的外部依赖边界承接第 6 章依赖裁剪结果,但本章只表达能力级输入 / 输出边界。`L0-core` 是唯一编译期依赖;运行期和事件协作关系不得被写成 package dependency。

| 关联方 | 依赖边界 |
|---|---|
| `L0-core` | 提供共享 ID、typed ref、trace、error 和基础契约语义,支撑 Artifact fact、version、lineage、baseline 和可消费引用稳定表达。 |
| `L0-bus` | 作为变化协作主干让相邻仓感知 Artifact truth 变化,但不保存正文、版本、血缘、基线、成员集合或下游副本。 |
| `L1-work` / `L1-process` / `L1-governance` | 可以提供工作、过程、治理语境或消费 Artifact truth,但各自状态、正文、裁决、policy、approval 和 Gate truth 不归 `L1-artifact`。 |
| `L1-conversation` / `L1-workspace` / `L4-archive` / `L4-observability` / `L0-sdk` / `L5-console` / `L5-sync` | 只能展示、分享、回链、封存、观测、访问、管理或同步 Artifact truth,不得形成私有 Artifact truth。 |
| `L3-method-library` / `L2-runtime` / `L3-capability-hub` | 当前只作为后续定义来源、运行输出或能力产物线索;相关材料必须经正式 Artifact 能力边界收束后才可影响本仓 truth。 |

### 12.3 接口类型与依赖类型

| 类型 | 使用口径 |
|---|---|
| 查询接口 | 用于 Artifact fact、version、lineage、baseline、可消费引用、跨仓回指、搜索 / 浏览、预览、归档消费和观测消费读取边界。 |
| 变更接口 | 用于正式制品事实纳管、稳定版本事实形成、正式血缘语境建立、受控版本集合形成,以及各阶段显式收束语境。 |
| 事件输出 | 用于 fact、version、lineage、baseline、可消费引用和外围通知的变化可感知边界。 |
| 事件输入 | 用于自动化产出事实收束、自动化迭代版本收束、自动化产出关系收束、基线候选与冻结语境收束;具体事件 schema 后续设计再定。 |
| 后台任务接口 | 只在外围增强中保留读模型、projection、报表或维护线索;不作为核心 truth 成立前置。 |

依赖类型使用口径: `L0-core` 是定义来源依赖;`L1-governance` 可提供治理证据、审查、批准或质量语境但不迁移治理 truth;`L0-bus`、work、process、governance、conversation、workspace、archive、observability、SDK、console、sync 是下游消费或协作边界;runtime、capability、method、workspace 等只能作为后续线索或经正式 Artifact 边界收束后的外部能力语境。

### 12.4 后置与裁剪

## 14. 验收标准

> 校准来源：
> - `design-calibration/00_req_step_14_acceptance_criteria.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_14_acceptance_criteria.md` 的“结构化中间产物”“回填草稿”和相关停审小节,了解本章结论如何从讨论收敛而来。

本文验收按核心能力闭环、功能能力、规则 / 边界、数据归属和非功能五类组织。验收标准来源于 `design-calibration/00_req_step_14_acceptance_criteria.md` 的能力级验收条件、五类覆盖审计和一票否决项。

### 14.1 核心能力闭环验收

`L1-artifact` 必须能够以 Artifact fact、version、lineage、baseline 和 consumption backref 形成可审计制品真相闭环。

### 14.2 功能能力验收

`FR-ART-001~020` 必须在五个核心能力节点中找到承接位置,不得出现孤儿功能。

### 14.3 规则 / 边界验收

`BR-ART-001~025` 必须防止 truth 串线、禁止覆盖、禁止补造、禁止 truth 转移和跨仓回指失效。

### 14.4 数据归属验收

真相 / 快照 / 引用 / 禁止保存正文四类边界必须成立,外部正文和消费副本不得进入正式 truth。

### 14.5 非功能验收

第 13 章的能力级 / 全局 NFR 必须有承接,但无来源硬指标不得升级为当前硬门禁。

### 14.6 一票否决项

五个核心能力节点任一无法成立、外部正文或消费副本进入正式 truth、正式 version / lineage / baseline 无法稳定追溯或冻结、消费方可以反写 Artifact truth,均构成一票否决。

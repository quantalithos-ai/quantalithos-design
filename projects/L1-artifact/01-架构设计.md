## 1. 业务背景与驱动力

### 1.1 业务背景

Artifact 是 Quantalithos 一切"值得持久保留、值得审计追溯"的产出。从需求文档、设计、代码、测试报告,到 AIIA / SoA / lessons-learned / dataset,都以 Artifact 形式存在。

它的价值不只是"存文件",而是:
- 可追溯(血缘关系)
- 可冻结(Baseline)
- 可校验(hash)
- 可双身份(治理对象同时是制品)
- 可归档(cold storage)

### 1.2 业务驱动力

**业务驱动力**:
- work 域要用 approved Artifact 判断 done
- governance 要用 AIIA / SoA 双身份产出合规证据
- process 要把 Activity 输出落成 Artifact

**技术驱动力**:
- 16 kind + 7 relation kind 硬枚举
- 多后端内容存储抽象
- lineage 查询
- hash 篡改检测
- baseline pin version+hash

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | Artifact 写 P95(不含内容上传) | < 200ms | benchmark |
| 性能 | GetLineage P95(depth=5) | < 500ms | benchmark |
| 性能 | hash 校验 | < 50ms | benchmark |
| 规模 | Artifact 总量 | 5000w | 压测 |
| 规模 | Relation 总量 | 1.5 亿 | 压测 |
| 安全 | tampered 事件触发率 | 100% 发现即报 | 回归测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| 16 种 kind 硬枚举 | AR2 | 新 kind 必走 ADR |
| 7 种 relation kind 硬枚举 | AR3 | 关系图谱受控 |
| approved 后内容不可改 | INV-2 | 更新需发新版本 |
| Baseline 必须 pin 到 version+hash | AR4 | baseline 不能只指 artifact_id |
| quality_tags 用 25010 9 特性 + 31 子特性 | AR5 | 不自造质量维度 |
| DatasetArtifact provenance 必填 | AR6 | 数据治理硬要求 |
| 禁止物理删除 | AR7 | 只能 archived |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| 内容后端 | Git / S3 / inline / URL | 可扩展更多后端 |
| 全文检索 / 语义检索 | 不在本仓主线 | 可后续加辅助索引 |
| lineage 查询实现 | 递归 CTE 起步 | 可后续评估 graph engine |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| Artifact 总量 | 5000w | README |
| Relation 总量 | 1.5 亿 | README |
| lineage 深度 | 5(主要场景) | 业务追溯 |
| 内容上传 | 大小不在本仓路径里 | 只管理 metadata + ref |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| Artifact kind 新增 | 低 | ADR |
| content backend 切换 | 中 | content adapter 抽象 |
| lineage 查询复杂度 | 中 | relation graph + query strategy |
| governance 双身份联动 | 中 | 明确同步边界 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **metadata-first + external content store**(当前)| 内容后端可替换,审计清晰 | 内容读取需二跳 |
| 全量 DB 存储 | 查询简单 | 大文件 / 代码 / 二进制不适 |
| Git-only | 对代码友好 | 不适合图片 / 数据集 / PDF |

**最终选择**:**metadata-first + content_ref 外置 + 血缘关系图 + baseline pin**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| content_ref 外置 | 后端可换、对象大也能管 | 预览需跳内容后端 |
| baseline pin hash | 审计强 | baseline 写入更重 |
| append-only archived | 审计与归档清晰 | 无法“删错文件” |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
Developers / AI Members / Reviewers
          │
          ▼
     ★ quantalithos-artifact ★
     - Artifact metadata
     - relations / lineage
     - baseline
     - dataset governance
          │
   ┌──────┼──────────────┬──────────────┬──────────────┐
   ▼      ▼              ▼              ▼              ▼
 process  work        governance       archive      observability
 outputs  done rule   AIIA/SoA dual    cold store   tampered / lineage audit
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ Artifact 聚合 + 生命周期
- ✅ ArtifactRelation 血缘图
- ✅ Baseline 冻结
- ✅ DatasetArtifact 扩展
- ✅ hash 校验与 tampered 检测

**不做什么**:
- ❌ 编辑器(Figma / IDE / 文本编辑)
- ❌ 评审决策(governance)
- ❌ 过程编排(process)
- ❌ UI 预览(chat / runner)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则阻断 |
| Git / S3 / URL backend | 99.9% | 换后端 / 暂只读 |
| archive | 99.9% | 延迟归档 |
| governance | 99.9% | 双身份最终一致 |

### 4.4 关键依赖风险

- content backend 漂移导致 hash 不一致
- lineage 查询在深度 5 以上性能恶化
- AIIA/SoA 双身份状态不同步

### 5.2 限界上下文划分

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
artifact-api
   │
   ▼
application layer
   ├─▶ domain(Artifact / Baseline / DatasetArtifact)
   ├─▶ lineage query
   ├─▶ content adapters(Git / S3 / inline / URL)
   └─▶ hash checker / subscriptions
        │
        ├─▶ PostgreSQL(metadata + relations + baselines)
        ├─▶ content backends
        └─▶ bus(outbox)
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| artifact-api | RPC/HTTP 入口 | Rust |
| artifact-domain | 元数据聚合逻辑 | Rust |
| lineage-engine | 血缘查询 | Rust + PostgreSQL recursive CTE |
| content-adapters | Git/S3/inline/URL 后端 | Rust |
| hash-scan worker | 每日校验内容 hash | Rust |
| postgres | metadata / relations / baselines / outbox | PostgreSQL |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| process → artifact | 事件 + ref | outputs 最终一致 |
| work ← artifact | artifact.approved 事件 | done 判据解耦 |
| content backend 访问 | adapter 模式 | 后端可替换 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| `artifacts` | artifact | artifact / work / governance / archive |
| `artifact_relations` | artifact | artifact / lineage |
| `baselines` | artifact | work / governance / archive |
| `implementation_plans`(若独立物化) | artifact | work / runtime / chat / console |
| 内容后端数据 | 外部 backend | artifact(通过 ref) |

### 6.5 部署拓扑

- 主服务 + PG 起步
- 大内容存外部后端
- hash-scan 可内嵌或独立 worker

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api
 │
 ▼
application
 │
 ▼
domain(Artifact / Baseline / DatasetArtifact)
 ▲
 │ interfaces
infra(Postgres / content adapters / hash worker / bus)
```

### 7.2 层间约束规则

- domain 不直接依赖具体内容后端
- lineage 查询不成为写源
- hash worker 只读内容,不改业务元数据(除发 tampered 事件)
- AIIA / SoA 双身份同步通过 application 用例,不直接跨仓改状态

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| ContentStore | domain/application | GitStore / S3Store / InlineStore / UrlStore |
| LineageReader | application | infra recursive query |
| HashVerifier | application | infra hash worker |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(process / work / governance / archive) |
| 传出耦合 | 中(PG + content backends + bus) |
| 不稳定性 | 中 |
| 抽象度 | 中高 |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Artifact metadata | artifact | work / governance / archive | 聚合内强一致 |
| Relations graph | artifact | lineage query / audit | 聚合内强一致 |
| Baseline | artifact | work / governance / archive | 强一致 + pin version/hash |
| Content bytes | 外部 backend | artifact / previewers | 最终一致 | backend drift |
| tampered event | artifact | governance / observability | 事件最终一致 |

### 8.2 一致性层次

- Metadata / Relation / Baseline 聚合内强一致
- Artifact metadata ↔ content backend 通过 hash 校验维护最终一致
- governance / work / process / archive 通过事件最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| 内容上传成功但 metadata 写失败 | 外部对象标 orphan,后台清理 |
| metadata 成功但内容 backend 失败 | Artifact state 保持 initiated,允许重试 |
| AIIA/SoA 双身份不同步 | 对账 + replay |
| tampered 误报 | 重算 hash + 人工复核 |

## 9. 关键技术选型

### 9.1 metadata-first + content_ref 外置

| 维度 | 内容 |
|---|---|
| 当前选择 | metadata-first + content_ref |
| 备选方案 | 全量 DB / Git-only |
| 选择理由 | 兼容代码 / 文档 / 二进制 / 数据集等多种内容 |
| 演进路径 | 新增后端 adapter |
| 不可逆程度 | 中 |

### 9.2 lineage 查询: PostgreSQL recursive CTE

| 维度 | 内容 |
|---|---|
| 当前选择 | recursive CTE |
| 备选方案 | graph DB |
| 选择理由 | 起步快,单库一致 |
| 演进路径 | 若 depth>5 / 性能恶化,评估 graph engine |
| 不可逆程度 | 低 |

### 9.3 content tampered 检测

| 维度 | 内容 |
|---|---|
| 当前选择 | 每日扫描 + approve 时 hash 校验 |
| 备选方案 | 实时 watcher |
| 选择理由 | 成本与收益平衡 |
| 演进路径 | 重要 Artifact 可提高频率 |
| 不可逆程度 | 低 |

## 10. 备选方案与取舍

| 维度 | 方案 A:metadata-first(当前)| 方案 B:全量对象存储 | 方案 C:全量 Git |
|---|---|---|---|
| 类型覆盖 | 高 | 中 | 低 |
| 查询能力 | 高(metadata 可查) | 低 | 中 |
| 运维复杂度 | 中 | 中 | 高 |
| 审计性 | 高 | 中 | 高 |

**最终选择**:A。需要同时兼容 code / docs / dataset / release 等多种制品。

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| graph engine 未引入 | lineage 深度复杂场景性能 | P1 |
| GDPR 物理删除策略未细化 | 合规冲突 | P1 |
| content backend 抽象还未验证 | 多后端一致性 | P1 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| GetLineage P95 > 500ms | 持续 1 周 | 评估 graph engine |
| tampered 误报 > 1 / 周 | 1 月 | 调整校验策略 |
| content backend drift 频繁 | > 3 / 月 | 增强一致性扫描 |

### 12.3 演进步骤

```
阶段 1: Artifact / Relation / Baseline 基础落地
阶段 2: DatasetArtifact 与质量标签细化
阶段 3: lineage 性能优化 / graph engine 评估
阶段 4: GDPR / content retention 深化
```

### 12.4 目标架构

artifact 域的目标是:
- 统一承载所有可审计产出
- 把 metadata / content / lineage / baseline 分清
- 为 work / process / governance / archive 提供可靠制品事实

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-artifact` 不是对象存储桶,也不是附件上传服务。它是 **“正式制品真相仓”**。

你可以把它理解成:
- 一份设计文档、测试报告、实施计划、评审记录、发布物在系统里怎样正式存在
- 同一份制品哪个版本才是正式版本
- 哪些制品已经被批准、被采纳、被冻结成 baseline
- 哪些制品能够被 work / process / governance / conversation / runtime 正式引用
- 为什么 conversation 里能看到 artifact 摘要,但真正的正文真相不在 conversation

这些事情,都由 `L1-artifact` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L1-artifact`,这些制品事实就会散落在:
- `work` 的 related_artifacts 字段里
- `governance` 的 evidence refs 里
- `process` 的 outputs 记录里
- `conversation` 的 artifact turn 摘要里
- 本地目录、外部对象存储和临时链接里

结果就会出现:
- 同一份制品到底哪个版本是正式可引用版本说不清
- baseline 和 approved/adopted 的语义散落在别的仓
- work / governance / process 各自偷偷定义“什么算正式证据”
- ImplementationPlan、设计文档、测试报告、发布物没有统一真相层
- conversation 里看到了摘要,却不知道哪一份才是正式正文

所以 `L1-artifact` 必须独立存在,作为:
> **正式制品正文、版本、证据引用与基线冻结关系的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Artifact
就是:
> 一份正式存在、可被引用、可被版本化、可被批准/冻结的制品对象。

它可以是:
- 设计文档
- 测试报告
- ImplementationPlan
- 发布物
- 评审记录
- 基线材料

#### ArtifactVersion
就是:
> 某份 Artifact 在某一时刻的正式版本快照。

它回答的是:
- 现在到底是哪一版
- 哪一版被批准/冻结/发布
- 后续引用应该指向哪一版

#### Evidence Ref
就是:
> 别的仓引用某份 artifact 作为依据时使用的稳定引用。

它不是治理结论本身,也不是“这份证据已经被正式采纳”的同义词。

#### Baseline
就是:
> 一组已经被冻结、后续不能静默漂移的正式制品集合。

它不是普通版本列表,而是带治理和冻结语义的制品快照集合。

#### Approved / Adopted
就是:
> 某个 artifact 或 version 已经被正式批准 / 采纳用于下游判断。

这两个词都很关键,但它们不等于 artifact 正文本身,而是 artifact 被消费时附着的治理语义。

#### ImplementationPlan
就是:
> 一种正式制品,用于承载执行路线图、步骤安排和实施证据语义。

它不是 work 真相对象,也不是 runtime 真相对象。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L1-artifact/02` 时,先收稳以下前提:
- `L1-artifact` 不应按对象数拆,而应按主要部分拆
- artifact 至少应拆成“制品主语与正文真相 / 版本与演化链 / 证据与采纳接缝 / 基线与冻结 / 投影与下游消费接缝”五个主要部分
- artifact 自己拥有的真相是 Artifact / ArtifactVersion / ContentRef / Baseline / Evidence relation / version lineage
- `Project / WorkItem / Gate / Decision / ProcessInstance / Conversation / Runtime state` 都不是 artifact 真相
- artifact 可以被这些域引用,但不能接管它们的业务真相
- 02 的重点不是“存哪种文件”,而是先把“artifact 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,真正参与软件工程协作的不只是消息、任务和流程,还包括大量正式制品。用户真正需要的不是“我能上传一个文件”,而是:
- 一份设计文档能成为正式 artifact
- 一份测试报告能成为正式 evidence
- 一组制品能被冻结成 baseline
- 一份 ImplementationPlan 能作为执行路线图被稳定引用
- work / governance / process / conversation / runtime 都能围绕同一份正式制品真相协作

如果把这些逻辑分别散落到:
- work 的 related_artifacts
- governance 的 evidence refs
- process 的 outputs
- conversation 的 artifact 摘要消息
- 对象存储链接和本地文件路径

系统会快速退化成:
- 同一份制品到底哪个版本才有效说不清
- baseline 只是“大家觉得差不多冻结了”,而不是正式对象
- governance 引用过证据,但 artifact 自己没有“被采纳/被冻结”的稳定边界
- conversation 能展示摘要,却没法回到正式正文真相
- ImplementationPlan、设计、测试、发布物四处飘散,没有统一制品真相层

因此,本概要设计的任务就是:
> **把 `L1-artifact` 写成一个新人也能看懂的“正式制品真相仓”,而不是把文件存储、证据引用、基线冻结和下游展示混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 制品真相归属 | 易散落在 work/governance/process/conversation 中 | Artifact/Version/Baseline 成为正式真相层 | 需写死边界 |
| 版本语义 | 同一制品容易只剩“当前文件”概念 | ArtifactVersion 成为正式引用单位 | 需正式落图 |
| 证据语义 | evidence ref 与 adopted/approved 语义易混 | 证据引用与采纳结论严格分层 | 需形成主要部分 |
| baseline 冻结 | 容易退化成“当前目录状态” | baseline 成为正式冻结集合 | 需单列并固定 |
| 下游消费 | work/process/governance/conversation/runtime 各自裁剪摘要 | artifact 统一输出正式可引用对象 | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让设计、测试、计划、发布物和证据材料成为正式、可追溯、可冻结、可被多仓统一引用的制品真相
- **技术问题**:Artifact / ArtifactVersion / Baseline / Evidence relation / ContentRef / downstream views 之间的边界如何稳定建模,并与 `work/governance/process/conversation/runtime` 清晰协作而不混层

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 artifact 的制品真相职责 | Artifact / Version / Baseline / Evidence relation 职责无歧义 | 文档评审 |
| 明确 artifact 与 governance/work/process 边界 | 正文真相、任务真相、治理结论、流程输出不混层 | 文档评审 + 后续测试 |
| 明确版本与冻结边界 | 哪一版可被正式引用、何时进入 baseline 无歧义 | 文档评审 |
| 明确证据与采纳边界 | evidence ref 不等于 adopted/approved 结论 | 文档评审 |
| 支撑后续详细设计 | 本文足以承接 `03-详细设计.md` 的对象模型、版本链、baseline 与接缝设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文定义对象存储、分块、去重、hash 算法细节(留给 `03-详细设计.md`)
- 不在本文定义全文检索/索引引擎实现细节
- 不在本文接管 `Project / WorkItem / Decision / ProcessInstance / Conversation / Runtime` 的正式对象模型
- 不在本文决定下游如何展示 artifact 摘要卡片的 UI 细节
- 不在本文给出完整 schema / DDL / replay / archive 实现细节

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ conversation               │
                    │ - artifact turn            │
                    │ - summary / notification   │
                    └────────────┬───────────────┘
                                 │ visible artifact summary
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ work                       │   │ artifact                   │   │ governance                 │
│ - related_artifacts        │◀──│ - Artifact                 │──▶│ - evidence refs            │
│ - done criterion refs      │   │ - ArtifactVersion          │   │ - adopted basis            │
│ - plan/proof links         │   │ - Baseline                │   └────────────────────────────┘
└────────────────────────────┘   │ - content / evidence rel   │
                                 └────────────┬───────────────┘
                                              │ outputs / baseline / plan refs
                                              ▼
                    ┌────────────────────────────┐
                    │ process / runtime          │
                    │ - outputs                  │
                    │ - ImplementationPlan refs  │
                    │ - execution reports        │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `artifact` 自己负责“正式制品正文”和“正式制品版本链”
- `work` 消费的是 artifact refs、done criterion 所需的 approved artifacts,但不拥有 artifact 正文真相
- `governance` 消费的是 evidence refs / adopted basis,但不拥有 artifact 正文真相
- `process` 生产 outputs 并引用 artifact,`artifact` 则保存这些输出物本体和 baseline 关系
- `runtime` 围绕 ImplementationPlan / report / result materials 消费 artifact,但不把 artifact 正文并入运行态真相
- `conversation` 展示的是 artifact 摘要和通知,而不是 artifact 正文主真相

所以 `L1-artifact` 在全局里的角色是:
> **把多域协作中形成的正式文档、报告、计划、证据和基线集合统一收拢为可版本化、可冻结、可被正式引用的制品中枢。**

### 4.3 系统边界

**做什么**:
- 保存正式 Artifact / ArtifactVersion / Baseline 真相
- 保存正文内容引用、版本链和制品间引用关系
- 为 work / governance / process / conversation / runtime 提供正式可引用制品对象
- 为 approved / adopted / published / baselined 等语义提供制品侧真相承载
- 提供制品审计链、浏览摘要和下游消费视图

**不做什么**:
- 不负责 Project / WorkItem / Iteration 真相
- 不负责 Gate / Decision / RiskAcceptance 真相
- 不负责 ProcessInstance / waiting_gate / Token 真相
- 不负责 Conversation / Turn 真相
- 不负责 runtime 执行状态正文
- 不把别的仓的投影摘要收编为自己的正文真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| work | 99.9% | related_artifact 更新延迟,但 artifact 正文和版本真相继续存在; done criterion 引用可延后对齐 |
| governance | 99.9% | adopted/approved/baselined 语义延迟回写,但 artifact 主真相与版本链不受影响 |
| process | 99.9% | outputs / baseline membership 输入延迟,制品主真相继续存在; 允许稍后补挂到 process 语义上 |
| conversation | 99.9% | artifact 通知延迟,但 artifact 正文真相不受影响; summary/notification 可后补 |
| runtime | 99.9% | plan/report/result refs 延迟,但 artifact 主真相继续存在; runtime 可保持旧稳定 ref |
| object storage / content backend | 99.9% | metadata 与 refs 仍可保留; 大正文读取降级,但版本与引用关系不丢; 未成功上传正文时不得发布正式 version |
| search / browse index | 99.9% | 搜索和摘要视图可延迟重建; history/query 可回退到正式 Artifact / Version 真相直接查询 |

### 4.5 关键依赖风险

- artifact / work 边界不稳会导致 task truth 和 artifact truth 混层
- artifact / governance 边界不稳会导致 evidence ref 被误当作正式治理结论
- artifact / process 边界不稳会导致 outputs 与运行态语义混在一起
- artifact / conversation 边界不稳会导致 artifact summary 被误当正文真相
- artifact / runtime 边界不稳会导致 ImplementationPlan 被误当执行状态本体
- 同一 ArtifactVersion 被多个下游引用时,若正式引用单位不清,会出现“同名制品不同语义版本”漂移
- baseline 冻结后若还能静默替换成员,下游会误以为自己在消费稳定快照
- content ref 存在但正文实际不可读时,会出现“形式上存在、实际上不可消费”的假真相
- approved / adopted relation 回写滞后时,work / governance / process 对同一制品的消费语义会分叉

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 制品主语与正文真相部分

- **它是什么**: 这是 `L1-artifact` 的正文真相层,一起回答“这份正式制品本体是什么”
- **为什么单独有它**: 如果不单列,artifact 很容易被写成“版本 + 文件路径”的附属表,看不见正文真相本体
- **负责什么**:
  - 定义 Artifact 主语
  - 定义 ArtifactKind
  - 定义正文内容引用和基本元信息
- **不负责什么 / 容易混淆点**:
  - 不负责 Project / WorkItem / Decision 真相
  - 不负责 conversation 展示层摘要
  - 最容易和 conversation artifact turn、work related_artifacts 混淆
- **与其他部分交互**:
  - 上游: process / runtime / authoring entry
  - 下游: 版本与演化链部分、投影与下游消费接缝部分
  - 交互类型: 正文真相写入型
- **后续详细设计展开点**:
  - Artifact / ArtifactKind / ContentRef 模型
  - 正文与元数据边界

#### 版本与演化链部分

- **它是什么**: 这是 `L1-artifact` 的版本层,一起回答“哪个版本才是正式可引用版本”
- **为什么单独有它**: 如果把版本语义混进 artifact 主语层,后续 approved / published / baseline 都会不清楚到底针对哪一版
- **负责什么**:
  - 定义 ArtifactVersion
  - 定义 lineage / replace / supersede / current version
  - 为下游提供稳定版本引用单位
- **不负责什么 / 容易混淆点**:
  - 不负责 baseline 冻结集合本身
  - 不负责 governance 采纳结论本体
  - 最容易和“当前文件内容”或 conversation 里展示的最新摘要混淆
- **与其他部分交互**:
  - 上游: 制品主语与正文真相部分
  - 下游: 证据与采纳接缝部分、基线与冻结部分
  - 交互类型: 版本固定型 + 正式引用型
- **后续详细设计展开点**:
  - ArtifactVersion 模型
  - supersede / publish / current 规则

#### 证据与采纳接缝部分

- **它是什么**: 这是 artifact 与 work/governance/process 之间的证据引用层,一起回答“哪些制品被正式拿去当证据”
- **为什么单独有它**: evidence ref、approved、adopted 容易被误写成下游字段,而失去 artifact 侧的稳定归属
- **负责什么**:
  - 提供 artifact refs / evidence refs
  - 记录 adopted / approved / published 关系
  - 为 work done criterion、governance adopted basis、process output 采纳提供制品侧支撑
- **不负责什么 / 容易混淆点**:
  - 不负责 governance 是否正式批准的决策真相
  - 不负责 work 是否 done 的业务裁决真相
  - 最容易和 governance adopted basis、work done criterion 混淆
- **与其他部分交互**:
  - 上游: 版本与演化链部分
  - 下游: work / governance / process / runtime
  - 交互类型: 证据引用型 + 采纳接缝型
- **后续详细设计展开点**:
  - evidence relation 模型
  - approved / adopted / published 规则

#### 基线与冻结部分

- **它是什么**: 这是 artifact 的冻结层,一起回答“哪些制品集合已经被冻结,后续不能静默漂移”
- **为什么单独有它**: 如果 baseline 只是“当前目录状态”或“最新版本集合”,后续任何引用都不稳定
- **负责什么**:
  - 定义 Baseline
  - 定义 baseline membership
  - 定义 freeze / publish / immutable snapshot 语义
- **不负责什么 / 容易混淆点**:
  - 不负责治理是否采纳该 baseline
  - 不负责 process 的运行态 checkpoint
  - 最容易和普通 version list、governance evidence package 混淆
- **与其他部分交互**:
  - 上游: 版本与演化链部分、证据与采纳接缝部分
  - 下游: work / process / governance / archive
  - 交互类型: 冻结集合型 + 正式引用型
- **后续详细设计展开点**:
  - Baseline 模型
  - membership / freeze 规则

#### 投影与下游消费接缝部分

- **它是什么**: 这是 artifact 的浏览、摘要和下游消费层,一起回答“怎样把制品真相安全地输出给别的仓”

- **负责什么**:

  - 提供 work / governance / process / conversation / runtime 消费所需的只读视图和 refs
  - 提供 search / list / recent / baseline browse 等读模型
- **不负责什么 / 容易混淆点**:
  - 不反向成为写源
  - 不拥有正式正文真相
  - 最容易和主语与正文真相部分、conversation artifact turn 混淆
- **与其他部分交互**:
  - 上游: Artifact / Version / Baseline 真相层
  - 下游: work / governance / process / conversation / runtime / archive
  - 交互类型: 只读查询型 + 下游消费型
- **后续详细设计展开点**:
  - summary / browse / notification view
  - search / index / downstream ref 规则

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 制品主语层 + 版本链层 + 证据接缝层 + baseline 冻结层 + 投影/消费层分层

- 把“可被人看到的摘要/通知”和“正式正文真相”分开

### 7.4 层间约束规则(防退化)

- evidence ref 只表示引用关系,不直接等于 adopted/approved 决策真相
- Baseline 一旦冻结,后续不得静默漂移
- summary / search / notification view 只读,不得反写真相
- 下游仓必须引用稳定 ArtifactVersion / Baseline member,不得直接消费“当前最新内容”
- ImplementationPlan 作为 artifact 时,不得自动等同于 work 真相或 runtime 状态真相

**artifact 红线**:
- Baseline 冻结后成员不得静默漂移
- artifact summary / notification 不得替代正文真相
- evidence ref 不得替代 adopted / approved relation
- ArtifactVersion 不得被“当前最新内容”替代
- 下游仓不得绕过 artifact 正式版本引用机制自己拼制品真相

## 8. 关键技术选型

### 8.1 为什么采用“正文主语层 / 版本层”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | Artifact 与 ArtifactVersion 分层 |
| 备选方案 | 只保留一个“当前制品”对象 |
| 选择理由 | 避免所有引用都退化成“当前版本”,无法稳定回放和冻结 |
| 演进路径 | 后续可扩展版本分支与 lineage,但不破坏正文/版本分层 |

### 8.2 为什么 evidence ref 与 adopted/approved 分离

| 维度 | 内容 |
|---|---|
| 当前选择 | evidence ref 只表示引用,adopted/approved 语义单独记录 |
| 备选方案 | 只要被引用就默认算已采纳 |
| 选择理由 | 防止 evidence ref 被误当成治理或完成判据真相 |
| 演进路径 | 后续可扩展 evidence package / adopted relation,但不合并语义 |

### 8.3 为什么 baseline 要单独成正式对象

| 维度 | 内容 |
|---|---|
| 当前选择 | Baseline 作为独立冻结集合对象 |
| 备选方案 | 用“当前版本列表”替代 baseline |
| 选择理由 | 只有独立 Baseline 才能承载冻结、不漂移和正式引用语义 |
| 演进路径 | 后续可扩展 baseline family / archive,但不把 baseline 退回普通列表 |

### 8.4 为什么下游必须引用正式 ArtifactVersion / Baseline

| 维度 | 内容 |
|---|---|
| 当前选择 | 下游统一引用稳定 ArtifactVersion 或 Baseline 成员 |
| 备选方案 | 默认引用“当前最新内容”或临时链接 |
| 选择理由 | 防止多下游在不同时间看到不同正文,导致 done criterion、governance basis、process outputs 漂移 |
| 演进路径 | 后续可扩展更复杂 lineage / branch,但引用单位仍保持稳定版本或冻结集合 |

### 8.5 为什么 ImplementationPlan 放在 artifact 侧承载

| 维度 | 内容 |
|---|---|
| 当前选择 | ImplementationPlan 作为正式制品由 artifact 承载 |
| 备选方案 | 放到 runtime / work 侧作为内部状态或局部字段 |
| 选择理由 | 它更像正式计划正文与可引用制品,需要版本化、可审计、可被 work/governance/runtime 共同引用 |
| 演进路径 | 后续可细化其 kind / version 规则,但不把其正文真相拉回 runtime/work |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的正式设计、测试、计划、发布与证据材料不能只是“大家都指一份文件链接”。它们必须以正式 Artifact / Version / Baseline 的形态存在,才能稳定支持 work 的 done criterion、governance 的 adopted basis、process 的 outputs 与 baseline、runtime 的 plan/report/result,以及 conversation 的摘要通知。

## 11. 横切关注点

### 11.1 安全
- 已冻结 Baseline 不得被静默修改
- content ref 与 metadata 变更必须留痕
- 只读视图不得越权暴露正文细节

### 11.2 性能
- 创建 artifact 与发布 version 的主写路径不应拖垮下游引用链
- browse/search/history 查询应支撑高频读侧消费

### 11.3 可用性
- search / summary / notification 延迟不影响 artifact 正文与版本真相
- object storage 短时故障时,metadata 与 ref 链不得丢失
- content ref 已存在但正文不可达时,不得把该版本继续当作正式可消费版本对外推荐

### 11.4 可观测性
- Artifact → Version → Evidence → Baseline 全链必须可追踪
- adopted / approved / baselined 变更必须可审计
- 下游引用的 artifact version / baseline member 必须可对账

### 11.5 冻结与不可变性
- Baseline freeze 后,成员集合不得静默漂移
- 已 published / frozen 的正式 ArtifactVersion 不得被“当前最新内容”替换含义
- supersede 只能形成新版本链,不能回写旧版本正文真相

### 11.6 成本
- 不把 work/governance/process 的业务真相并入 artifact,避免模型膨胀
- 不让每个仓自己再维护一份制品版本逻辑,降低长期维护成本

### 11.7 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| CreateArtifact | ≤ 100ms | 100ms |
| PublishArtifactVersion | ≤ 150ms | 250ms |
| summary / browse 更新 | 最终一致 | 不做强一致预算 |

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在单项目样板中验证 `Artifact → ArtifactVersion → summary` 三条最小主线
- **阶段 2**: 再验证 `evidence/adopted relation → governance/work/process consume` 三条接缝主线
- **阶段 3**: 再引入 `Baseline / freeze / immutable snapshot` 主线,验证冻结后引用不漂移
- **阶段 4**: 最后再引入 `ImplementationPlan / report / output artifact / archive` 等复杂演化路径

### 13.2 回滚策略
- 若 ArtifactVersion 主模型不稳,先回退到“保留 Artifact 主语 + 最小版本链”的保守路径
- 若 adopted/evidence 接缝不稳,先保留正文真相和版本真相,暂停复杂采纳关系自动化
- 若 Baseline 语义不稳,先关闭 baseline family / 批量冻结路径,只保留单一冻结集合
- 若 ImplementationPlan / report / output artifact 的 kind 边界不稳,先收缩到最小 kind 集,避免把 runtime/work 语义拉进 artifact 真相层

### 13.3 监控指标
- artifact 创建成功率
- version 发布成功率
- approved/adopted/baselined 关系变更成功率
- summary / browse drift 率
- baseline freeze 失败率

## 15. 结论

本概要设计的核心结论是:
- `L1-artifact` 是正式制品正文、版本、证据引用与基线冻结关系的真相层,不是对象存储桶或附件仓
- `L1-artifact` 内部应按“制品主语与正文真相部分 / 版本与演化链部分 / 证据与采纳接缝部分 / 基线与冻结部分 / 投影与下游消费接缝部分”来理解,而不是按对象平铺理解
- `work` 管任务真相,`governance` 管决策真相,`process` 管推进真相,`conversation` 管消息可见层,`runtime` 管执行真相,而 `artifact` 负责把正式制品、版本和 baseline 收拢为统一可引用真相
- evidence ref 不是 adopted/approved 结论,artifact summary 不是 artifact 正文真相,baseline 不是普通版本列表
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把对象模型、版本链、baseline、evidence relation 和 downstream views 正式化

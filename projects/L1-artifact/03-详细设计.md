## 1. 模块职责描述

**本模块做什么**:
- 持有正式 Artifact / ArtifactVersion / Baseline / adopted relation / approved relation 真相
- 持有正文引用、版本链、冻结成员集与稳定引用关系
- 为 work / governance / process / runtime / conversation 提供正式可引用制品对象和只读消费视图
- 保证版本、证据采纳、baseline freeze 和下游消费边界清晰可审计

**本模块不做什么**:
- 不持有 `Project` / `WorkItem` / `Decision` / `ProcessInstance` / `Conversation` / `Turn` / `RuntimeState` 真相
- 不承担全文检索引擎、对象存储底层算法或聊天前端渲染正文
- 不负责下游仓对 artifact 的业务判断正文,只负责提供正式制品真相与关系

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 artifact“为什么存在”,而是让开发者可以直接开始实现:
- Artifact 主语和 ArtifactVersion 如何分层
- version lineage / supersede / current 指针如何维护
- evidence / adopted / approved relation 如何落成正式关系
- baseline 如何冻结并阻止静默漂移
- summary / browse / notification view 如何只读提供给下游

如果不先把这些内容采集清楚,03 很容易退化成:
- 把 artifact 写成文件上传服务说明
- 只写对象存储和 metadata 表,看不见制品真相主线
- 把 adopted / approved / baseline 关系写进下游仓字段而不是 artifact 自己的关系层
- 把 ImplementationPlan、测试报告、输出物正文和 conversation 摘要混成一层

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `Artifact / ArtifactVersion / Baseline / EvidenceRef` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与关系
- 最后再进入横向的对象模型、流程、存储、投影、异常与测试细节

这样可以避免:
- `02` 讲的是正文/版本/证据/baseline/投影,`03` 却只剩 metadata 表
- 实现者知道有 ArtifactVersion,却不知道它归哪个责任单元控制
- adopted relation、baseline freeze、notification view 三条链路脱节

```rust
/// 表示一份正式制品的主语对象,回答“这份制品本体是什么”。
pub struct Artifact {
    /// 制品唯一标识。
    pub artifact_id: ArtifactId,
    /// 制品类型,决定后续版本、采纳和下游消费语义。
    pub kind: ArtifactKind,
    /// 当前制品的主状态。
    pub status: ArtifactStatus,
    /// 当前制品指向的正文引用。
    pub content_ref: ContentRef,
    /// 制品的基础元信息。
    pub metadata: ArtifactMetadata,
}

/// 表示制品类型,区分设计、测试、计划、发布等不同语义。
pub enum ArtifactKind {
    /// 设计类制品。
    DesignDoc,
    /// 测试类制品。
    TestReport,
    /// 实施计划类制品。
    ImplementationPlan,
    /// 发布物类制品。
    ReleaseBundle,
    /// 执行结果或运行报告。
    ExecutionReport,
}

/// 表示正文内容的稳定引用,它不等于正文本体文件系统路径。
pub struct ContentRef {
    /// 内容引用标识。
    pub content_ref_id: ContentRefId,
    /// 具体内容所在后端位置。
    pub locator: String,
    /// 内容可达性状态。
    pub availability: ContentAvailability,
}
```

这些对象在该部分里分别承担:
- `Artifact` 回答“这份正式制品本体是什么”
- `ArtifactKind` 决定 ImplementationPlan / TestReport / ReleaseBundle 等后续消费语义
- `ContentRef` 把正文可达性与正文主语分开,避免“对象存在 ≠ 正文可消费”被混成一件事

#### 5.2.4 关键函数代码片段

```rust
/// 创建一个正式 Artifact 主语,并把内容引用固定为后续版本链的起点。
fn create_artifact(artifact_repo: &dyn ArtifactRepo, draft: CreateArtifactDraft) {
    // [Artifact::从草稿创建]
    // 先把输入草稿收束为正式 Artifact 对象。
    let artifact = Artifact::from_draft(draft);

    // [artifact.校验可创建]
    // 再校验 kind、metadata、content_ref 的最小成立条件。
    artifact.validate_creatable();

    // [artifact_repo.保存制品]
    // 最后把正式制品主语写入真相层,为后续版本链和引用链提供锚点。
    artifact_repo.save(artifact);
}
```

这段实现守住的边界是:
- Artifact 主语先于 ArtifactVersion 存在
- content ref 只是正文入口,不能被误当作版本本体
- summary / notification 等读模型还没有资格定义这份制品“是什么”

#### 5.2.5 该部分的边界与非职责
- 不负责 publish/supersede/version line 细节
- 不负责 adopted/approved relation 真相
- 不负责 baseline freeze
- 不负责下游摘要展示层

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `版本与演化链部分` 提供 Artifact 主语与 content origin
- 向 `投影与下游消费接缝部分` 提供基础元信息
- 从 process/runtime/authoring 接收内容输入,但不吸收它们的业务真相

#### 5.2.7 该部分的状态 / 约束 / 易错点
- Artifact 主语存在不等于已有正式可引用版本
- ContentRef 可存在但正文不可达,此时不得伪装成“正式可消费正文”
- ImplementationPlan 作为 ArtifactKind 只定义制品语义,不定义 runtime state

```rust
/// 表示一份 Artifact 的正式版本快照,它是下游稳定引用单位。
pub struct ArtifactVersion {
    /// 版本唯一标识。
    pub artifact_version_id: ArtifactVersionId,
    /// 归属的 Artifact。
    pub artifact_id: ArtifactId,
    /// 版本号或逻辑版本标识。
    pub version_label: String,
    /// 当前版本状态。
    pub status: ArtifactVersionStatus,
    /// 指向该版本正文的稳定引用。
    pub content_ref: ContentRef,
}

/// 表示版本状态,区分待发布、正式发布、被替代和被冻结语义。
pub enum ArtifactVersionStatus {
    /// 新版本已创建但尚未正式发布。
    Pending,
    /// 正式可被下游引用的版本。
    Published,
    /// 已被新版本替代,但仍可能被历史 baseline 或 adopted relation 引用。
    Superseded,
    /// 因进入 baseline 或冻结语义而不可再变更解释的版本。
    Frozen,
}

/// 表示版本之间的演化链关系。
pub struct ArtifactLineage {
    /// lineage 自己的标识。
    pub lineage_id: ArtifactLineageId,
    /// 当前版本引用。
    pub current_version: ArtifactVersionId,
    /// 被替代的上一个版本引用。
    pub previous_version: Option<ArtifactVersionId>,
}

/// 表示一个明确的 supersede 关系,用于表达“新版本替代旧版本”。
pub struct SupersedeRelation {
    /// 旧版本引用。
    pub previous_version: ArtifactVersionId,
    /// 新版本引用。
    pub next_version: ArtifactVersionId,
}

/// 表示当前正式版本指针,给下游快速定位“当前推荐版本”。
pub struct CurrentVersionPointer {
    /// 归属的 Artifact。
    pub artifact_id: ArtifactId,
    /// 当前正式版本引用。
    pub current_version: ArtifactVersionId,
}
```

这些对象在该部分里分别承担:
- `ArtifactVersion` 是正式引用单位
- `ArtifactVersionStatus` 负责把 published / superseded / frozen 的语义显式化
- `ArtifactLineage` 负责记录完整演化链
- `SupersedeRelation` 负责把“替代”写成正式关系,而不是只改 current pointer
- `CurrentVersionPointer` 只是“当前推荐版本”快捷入口,但不替代完整版本历史

#### 5.3.4 关键函数代码片段

```rust
/// 发布一个正式 ArtifactVersion,并把它接入版本演化链。
fn publish_artifact_version(
    version_repo: &dyn ArtifactVersionRepo,
    lineage_repo: &dyn ArtifactLineageRepo,
    artifact: &Artifact,
    draft: PublishVersionDraft,
) {
    // [ArtifactVersion::从草稿创建]
    // 先根据 Artifact 主语和新的内容引用生成正式版本对象。
    let version = ArtifactVersion::from_draft(artifact.artifact_id, draft);

    // [version.校验可发布]
    // 再校验当前版本标签、正文可达性和 supersede 关系是否合法。
    version.validate_publishable();

    // [version_repo.保存版本]
    // 正式写入 ArtifactVersion 真相。
    version_repo.save(version.clone());

    // [lineage_repo.更新当前版本指针]
    // 把这次发布接入 lineage,并更新 current_version 指针。
    lineage_repo.advance_current(artifact.artifact_id, version.artifact_version_id);
}
```

这段实现守住的边界是:
- 正式版本必须显式发布,不能被“当前最新内容”自动替代
- current version 是 pointer,不是整个历史链
- supersede 应通过新版本推进,而不是回写旧版本正文

#### 5.3.5 该部分的边界与非职责
- 不负责 adopted/approved relation 判断
- 不负责 baseline membership 冻结集合本体
- 不负责 conversation summary 输出
- 不负责 work/governance 的业务判断真相

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `制品主语与正文真相部分` 接收 Artifact 主语

- 向 `基线与冻结部分` 提供 baseline 可选成员
- 向 `投影与下游消费接缝部分` 提供 browse/history 输入

#### 5.3.7 该部分的状态 / 约束 / 易错点
- current version 只是推荐入口,不能覆盖版本历史
- supersede 后旧版本仍可能被 baseline 或治理链正式引用
- 发布失败不能留下“有 current 指针但无版本真相”的破链状态

```rust
/// 记录某个 ArtifactVersion 被下游正式采纳的关系。
fn adopt_artifact_as_evidence(
    relation_repo: &dyn ArtifactRelationRepo,
    version: &ArtifactVersion,
    target_ref: ArtifactTargetRef,
    relation_kind: AdoptedRelationKind,
) {
    // [version.校验可被正式引用]
    // 先确认该版本确实是正式可引用版本,而不是草稿或无效内容。
    version.ensure_referenceable();

    // [AdoptedRelation::创建]
    // 再把“谁采纳了哪个版本、用于什么语义”固定成关系对象。
    let relation = AdoptedRelation::new(version.artifact_version_id, target_ref, relation_kind);

    // [relation_repo.保存采纳关系]
    // 最后把 adopted relation 正式写入关系层。
    relation_repo.save_adopted(relation);
}
```

这段实现守住的边界是:
- adopted relation 针对的是 ArtifactVersion,不是“当前最新内容”
- evidence ref 不自动升级成 adopted relation
- governance/work/process 采纳的是稳定版本,不是临时文件路径

#### 5.4.5 该部分的边界与非职责
- 不负责 governance 是否 approve/reject 的决策真相
- 不负责 work 是否 done 的最终业务判断

- 不负责下游 summary / notification 呈现

#### 5.4.6 该部分与其他主要部分的接缝

```rust
/// 把一组正式 ArtifactVersion 冻结成不可漂移的 Baseline。
fn freeze_baseline(
    baseline_repo: &dyn BaselineRepo,
    version_refs: Vec<ArtifactVersionId>,
    summary: String,
) {
    // [Baseline::从版本集合创建]
    // 先把待冻结版本集合收束成正式 Baseline 对象。
    let baseline = Baseline::from_versions(version_refs, summary);

    // [baseline.校验成员完整性]
    // 再确认这些成员全部是正式可冻结版本,且没有缺项和冲突。
    baseline.validate_freezable();

    // [baseline_repo.保存并冻结]
    // 最后把 baseline 持久化为正式不可漂移的快照集合。
    baseline_repo.save_and_freeze(baseline);
}
```

这段实现守住的边界是:
- baseline 只冻结 ArtifactVersion,不冻结“当前最新内容”
- baseline 成员必须显式列出,不能靠查询时动态拼装
- freeze 后变更必须通过新 baseline,而不是原 baseline 静默改写

#### 5.5.5 该部分的边界与非职责
- 不负责 governance 是否采用该 baseline
- 不负责 process 运行时 checkpoint 本体
- 不负责 conversation 通知展示层
- 不负责正文去重/压缩算法

#### 5.5.7 该部分的状态 / 约束 / 易错点
- baseline 一旦 freeze,成员不可静默漂移
- baseline 不是“当前版本列表的别名”
- supersede 新版本产生后,旧 baseline 成员仍保持原引用不变

```rust
fn refresh_projection(
    projection_repo: &dyn ArtifactProjectionRepo,
    artifact: &Artifact,
    version: &ArtifactVersion,
```

### 7.6 关键状态机 / 非法转换与约束

#### 状态机图

```text
Artifact:
draft → active → retired

ArtifactVersion:
pending → published → superseded
published → frozen (if part of baseline)

Baseline:
draft → frozen → archived
```

#### 非法转换与约束表

| 场景 | 是否允许 | 说明 |
|---|---|---|
| 无 Artifact 主语直接创建 ArtifactVersion | ❌ | 版本必须依附 Artifact |
| 用“当前最新内容”替代正式 ArtifactVersion | ❌ | 正式引用单位必须是版本 |
| baseline freeze 后静默替换成员 | ❌ | freeze 后不可漂移 |
| evidence ref 直接充当 adopted/approved relation | ❌ | 引用与采纳语义必须分层 |
| summary view 反向更新 Artifact 正文 | ❌ | 只读视图不能写真相 |
| ContentRef 不可达时仍发布正式 version | ❌ | 正文必须可消费 |
| 非 published 版本直接进入 baseline | ❌ | freeze 只允许正式版本进入 |
| superseded 版本被 current pointer 静默替代关系引用 | ❌ | 历史 adopted/baseline 引用必须保持原版本 |
| frozen baseline 重新 append member | ❌ | 新成员必须走新 baseline |

#### 关键约束说明

- `ArtifactVersion.published` 才能成为默认正式引用单位
- `ArtifactVersion.superseded` 仍可被旧 baseline / adopted relation / governance 历史链引用
- `ArtifactVersion.frozen` 只说明该版本进入了 baseline 冻结语义,不等于它成为当前最新版本
- `Baseline.frozen` 后,成员集合只能查询和引用,默认不允许 reopen / append / replace

## 11. 运行期主线场景

### 11.1 场景 A · process 输出物化为 artifact

```text
process 产出阶段结果
      │
      ▼
artifact 创建 Artifact 主语
      │
      ▼
artifact 发布 ArtifactVersion
      │
      ├─ governance 可引用 evidence ref
      ├─ work 可引用 related / done proof
      └─ conversation 可见摘要更新
```

**开发者关注点**:
- outputs 不等于 process 真相本体
- version 发布必须先于下游正式引用
- summary 更新延迟不影响 ArtifactVersion 真相成立

### 11.2 场景 B · artifact 被采纳为治理/完成依据

```text
governance / work 需要 formal basis
      │
      ▼
读取 ArtifactVersion
      │
      ▼
写入 adopted / approved relation
      │
      ├─ governance 形成 adopted basis
      └─ work 形成 done criterion input
```

**开发者关注点**:
- 引用的是 ArtifactVersion,不是“最新文件”
- evidence ref 与 adopted relation 必须分开
- approved relation 不能替代 governance/work 自己的业务真相

### 11.3 场景 C · baseline 冻结并被后续消费

```text
selected versions ready
      │
      ▼
create baseline
      │
      ▼
freeze baseline
      │
      ├─ process 引用 frozen snapshot
      ├─ governance 引用 stable basis set
      └─ archive 接收 immutable members
```

**开发者关注点**:
- baseline 不是当前版本列表
- freeze 后不得静默替换成员
- 新版本产生后旧 baseline 成员引用不变

### 11.4 场景 D · 新版本发布后旧 baseline 不漂移

```text
旧 baseline 已 frozen
      │
      ▼
新 ArtifactVersion 发布
      │
      ▼
current version pointer 更新
      │
      ├─ 新下游引用看到新 current version
      └─ 旧 baseline 继续保持旧 members
```

**开发者关注点**:
- baseline 浏览必须按 frozen members 重建,不能动态追 current version
- supersede 新版本不应静默迁移旧 baseline 成员
- adopted / approved relation 若绑定旧版本,也不得因 current pointer 更新而漂移

### 11.5 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| process/runtime output | CreateArtifact / PublishArtifactVersion | 制品主语与正文真相部分 + 版本与演化链部分 | Artifact / ArtifactVersion |
| governance/work/process consume evidence | AdoptArtifactAsEvidence / relation flow | 证据与采纳接缝部分 | adopted/approved relation |
| baseline request | CreateBaseline / FreezeBaseline | 基线与冻结部分 | frozen baseline |
| conversation / downstream browse | BuildArtifactSummary / notification material | 投影与下游消费接缝部分 | summary / browse / notification view |

## 12. 数据与存储设计

### 12.1 先分清写模型 / 读模型 / 证据引用

| 对象 | 类型 | 是否持久化 | 说明 |
|---|---|---|---|
| Artifact | 写模型 | 是 | 制品主语真相 |
| ArtifactVersion | 写模型 | 是 | 正式版本真相 |
| Baseline / BaselineMember | 写模型 | 是 | 冻结集合真相 |
| AdoptedRelation / ApprovedRelation | 关系写模型 | 是 | 证据/采纳关系真相 |
| ArtifactSummaryView / HistoryView / BrowseView | 读模型 | 是/可重建 | 高读压只读视图 |
| ContentRef / ArtifactTargetRef | 证据/引用 | 随真相持久化 | 只存 ref |

### 12.2 关系与索引建议

| 表/集合 | 关键索引 |
|---|---|
| artifacts | `artifact_id`, `kind`, `status` |
| artifact_versions | `artifact_version_id`, `artifact_id + version_label`, `status` |
| artifact_lineage | `artifact_id`, `current_version`, `previous_version` |
| artifact_relations | `artifact_version_ref`, `target_ref`, `relation_kind` |
| baselines | `baseline_id`, `status` |
| baseline_members | `baseline_id + artifact_version_ref` |
| content_refs | `content_ref_id`, `availability` |

**索引理由**:
- `artifact_id + version_label` 支撑稳定版本查找与重复发布拦截
- `current_version` 支撑快速定位当前正式推荐版本
- `artifact_version_ref + target_ref + relation_kind` 支撑 adopted / approved relation 去重与查询
- `baseline_id + artifact_version_ref` 支撑 frozen members 精确重建
- `availability` 支撑 content ref 可达性巡检与发布前校验

### 12.3 持久化建议

| 对象 | 存储方式 | 理由 |
|---|---|---|
| Artifact / ArtifactVersion | 主表 | 正式正文与版本真相 |
| Adopted / ApprovedRelation | 关系表 | 下游正式采纳关系 |
| Baseline / BaselineMember | 主表 | freeze 后不可漂移 |
| Summary / Browse / Notification views | 可重建读模型 | 高读压与写链解耦 |

**存储边界说明**:
- `ContentRef` 默认绑定到 `ArtifactVersion`,而不是只挂在 Artifact 主语上,避免“同一正文 ref 对应多条版本语义”混乱
- `AdoptedRelation / ApprovedRelation` 必须挂在稳定 `ArtifactVersion` 上,不能只挂 Artifact 主语
- `BaselineMember` 必须显式保存冻结时的 `ArtifactVersion`,不得运行时动态解析 current version
- `ArtifactSummaryView / ArtifactHistoryView / BaselineBrowseView / ArtifactNotificationView` 都属于派生层,允许重建,不得反写 Artifact / Version 真相

### 12.4 关键校验

- ArtifactVersion 发布前必须校验 ContentRef 可达性
- adopted / approved relation 必须绑定合法 ArtifactVersion 与 target_ref
- baseline freeze 前必须校验成员完整性和可冻结性
- summary / browse / notification 更新失败不能反写 Artifact 正文真相

### 12.5 建议表结构草案

#### `artifact_versions`

| 字段 | 类型 | 说明 |
|---|---|---|
| artifact_version_id | uuid | 主键 |
| artifact_id | uuid | 所属 Artifact |
| version_label | text | 版本标识 |
| status | enum | pending/published/superseded/frozen |
| content_ref | jsonb/text | 正文引用 |

#### `baseline_members`

| 字段 | 类型 | 说明 |
|---|---|---|
| baseline_id | uuid | 所属 baseline |
| artifact_version_ref | uuid | 冻结成员 |
| member_role | text/enum | 成员角色 |

## 13. 读模型与投影设计

### 13.1 总体结构

```text
Artifact / Version / Baseline write model
   │
   ▼
projection builders
   ├─ summary
   ├─ history
   ├─ browse
   └─ notification material
```

### 13.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| ArtifactSummaryView | Artifact + current version | 高频摘要 |
| ArtifactHistoryView | ArtifactVersion + lineage | 历史链回看 |
| BaselineBrowseView | Baseline + members | frozen snapshot 浏览 |
| ArtifactNotificationView | version/relation events | conversation / downstream 通知材料 |

### 13.3 一致性说明

- 读模型允许最终一致
- summary / history / browse / notification view 都只读
- `ArtifactSummaryView` 服务高频列表,可以短暂滞后,但不得漂移到错误版本
- `ArtifactHistoryView` 服务完整 lineage 浏览,必须能回到正式 ArtifactVersion 真相
- `BaselineBrowseView` 必须只基于 frozen members 重建,不能动态拼 current version
- `ArtifactNotificationView` 只提供给 conversation / 下游展示层,不能替代 artifact 正文真相
- content ref 可达性异常只影响“能否消费正文”,不改变 Artifact / Version 真相是否存在
- browse/history/notification 漂移时,重建顺序必须是: reset projection → replay Artifact / Version / Baseline / Relation truth → regenerate views

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| ContentRef 不可达 | 拒绝正式发布 version |
| adopted relation 写入失败 | 重试关系写入,不回滚已存在的 ArtifactVersion 真相 |
| baseline 不可冻结 | 阻断 freeze,返回成员问题 |
| browse / notification 漂移 | 以 Artifact / Version / Baseline 真相重建 |

### 14.1 重试 / 降级 / 熔断 / 补偿
- object storage 短时失败时允许保留 Artifact 主语,但不得发布正式 version
- adopted/approved relation 失败时允许稍后补写,但不得伪装成已经成功采纳
- browse/search/notification 失败允许暂时返回陈旧视图,后台重建
- current version pointer 错位时必须通过 lineage 真相修复,不得直接改 summary 欺骗下游
- baseline browse 漂移时必须从 frozen members 重建,不得按 current version 动态纠偏
- ContentRef 恢复可达后,可重新尝试发布/恢复下游消费,但不能伪造已发布历史

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 制品主语与正文真相部分 | ContentRef 无效 / metadata 不合法 | create trace | 拒绝创建 / 修正输入 | recreate draft |
| 版本与演化链部分 | version 重复发布 / lineage 断裂 | version log | 阻断发布 / 修复 pointer | replay publish |
| 证据与采纳接缝部分 | adopted relation 错 target / approved 漏写 | relation log | 阻断关系写入 / 修正目标 | replay relation write |
| 基线与冻结部分 | baseline 成员缺失 / freeze 后漂移 | baseline compare | 拒绝冻结 / 回滚非法变更 | rebuild baseline views |
| 投影与下游消费接缝部分 | summary / notification 漂移 | projection lag | 重建视图 | full rebuild |

## 15. 实现红线 / 开发禁止事项

- 不允许把 ArtifactVersion 简化成“当前最新内容”
- 不允许把 evidence ref 直接等同于 adopted/approved 结论
- 不允许 baseline freeze 后静默替换成员
- 不允许让 summary / notification / browse view 反向定义 artifact 正文真相
- 不允许把 ImplementationPlan artifact 偷偷变成 work/runtime 状态对象
- 不允许在 ContentRef 不可达时仍写出正式 published version
- 不允许用 current pointer 覆盖历史 adopted relation / baseline member 的版本引用
- 不允许通过修改 summary/browse 来“修复”正式版本或 baseline 真相

## 18. 结论

本详细设计的核心结论是：

### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L1-artifact` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L1-artifact` 是正式制品正文、版本、证据引用与基线冻结关系的真相层,不是对象存储桶或附件仓
- Artifact / ArtifactVersion / Baseline 构成正式制品真相层
- ArtifactVersion 是正式引用单位,不能被“当前最新内容”替代
- `evidence ref ≠ adopted / approved relation` 必须成立
- baseline freeze 后成员不可静默漂移
- summary / browse / notification 只读且不反写真相
- `ImplementationPlan` 作为 artifact 时只是一种正式制品,不会偷变成 work/runtime 状态对象

因此,本次验收的目的不是笼统判断“能不能存文件”,而是判断 artifact 的正文真相、版本真相、证据采纳关系、baseline 冻结和下游消费边界是否真的成立,是否可作为后续阶段的稳定基线。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| 制品主语与正文真相部分 | 是 | Artifact、ArtifactKind、ContentRef、metadata |
| 版本与演化链部分 | 是 | ArtifactVersion、lineage、supersede、current pointer |
| 证据与采纳接缝部分 | 是 | EvidenceRef、AdoptedRelation、ApprovedRelation |
| 基线与冻结部分 | 是 | Baseline、BaselineMember、freeze |
| 投影与下游消费接缝部分 | 是 | summary / history / browse / notification |
| 对象存储底层算法与分块实现 | 否 | 只验 ContentRef 可达性语义,不验底层存储算法 |
| conversation 前端卡片展示细节 | 否 | 只验 ArtifactNotificationView,不验 UI 表现 |
| work / governance / process / runtime 内部正文逻辑 | 否 | 只验 artifact 与它们的接缝,不验下游全部内部实现 |

## 4. 功能验收门禁

| 功能/场景 | 门禁条件 | 证据 | 结论 |
|---|---|---|---|
| CreateArtifact | 合法 kind + content ref + metadata 输入后必须形成正式 Artifact 主语 | API 响应 / DB 记录 / trace | [] |
| PublishArtifactVersion | ArtifactVersion 必须作为正式引用单位被发布,不能被“当前最新内容”替代 | version 记录 / current pointer / lineage | [] |
| SupersedeArtifactVersion | 新版本 supersede 后,旧版本仍保留历史与被 baseline/adopted relation 正式引用的能力 | lineage compare / old refs trace | [] |
| SetCurrentVersion | current pointer 更新后,新下游引用可看到新版本,旧正式关系不漂移 | summary compare / refs compare | [] |
| EvidenceRef | 证据引用必须只是 ref,不能直接替代 adopted/approved relation | relation compare / negative test | [] |
| AdoptArtifactAsEvidence | ArtifactVersion 被正式采纳为 basis/proof/output 时,必须形成 AdoptedRelation | relation record / consumer trace | [] |
| ApproveArtifactVersion | ArtifactVersion 被正式标记为 approved 时,必须形成 ApprovedRelation | relation record / downstream consume material | [] |
| CreateBaseline / FreezeBaseline | 一组合法 ArtifactVersion 必须能形成 frozen baseline,且成员 freeze 后不可静默漂移 | baseline record / member compare | [] |
| ImplementationPlan artifact 边界 | ImplementationPlan 作为 artifact 时,只作为正式制品引用被消费,不得被下游当状态对象解释 | kind check / downstream trace | [] |
| Summary/Browse/Notification | 下游消费的 summary/history/browse/notification 必须只读且可从正式真相重建 | rebuild log / view compare | [] |

## 7. 安全与治理门禁

| 门禁项 | 要求 | 证据 | 结论 |
|---|---|---|---|
| ArtifactVersion 不可被当前最新内容替代 | 下游正式引用必须绑定明确 version ref | refs trace / negative flow | [] |
| evidence ref 不可替代 adopted / approved relation | 引用和采纳必须严格分层 | relation compare / negative test | [] |
| frozen baseline 不可漂移 | freeze 后成员不可 append / replace / drift | baseline compare / negative flow | [] |
| summary / notification 不可反写真相 | 只读投影不能反向更新 Artifact / Version / Baseline | rebuild test / architecture check | [] |
| ImplementationPlan artifact 不可偷变状态对象 | 计划制品只能被引用消费,不能替代 runtime/work 状态真相 | kind check / downstream trace | [] |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | Artifact/Version 混层 / evidence ref 替代 adopted relation / baseline freeze 失效 / ContentRef 不可达仍发布正式 version |
| A | 视情况 | 主线可跑但 relation / projection / baseline browse / current pointer 不稳 |
| B | 可带着走 | 非关键浏览视图、通知材料或低优先级查询异常 |

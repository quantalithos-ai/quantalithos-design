## 5. 模块思考记录

### 5.1 模块 1:业务背景候选:先思考

#### 5.1.1 问题回答

Step 3 的业务背景要解释“为什么现在值得讨论 L1-artifact”,而不是重复 Step 2 的边界定义,也不是提前写目标。基于 Step 1 / Step 2 结论,当前背景主线应围绕三点:

| 背景主线 | 当前判断 | Step 3 表达边界 |
|---|---|---|
| 平台产出需要成为可审计资产 | Quantalithos 的需求、设计、代码、测试、发布和复盘都会形成可被长期引用的制品。 | 可以说明“制品事实需要被收束”,不能列功能或对象字段。 |
| 制品被多个相邻仓共同引用 | work、process、governance、conversation、workspace、observability、archive 都会引用或消费 Artifact。 | 可以说明多真相风险,不能写依赖裁剪或事件订阅。 |
| 旧材料已把背景、目标、功能、性能和实现混写 | 旧 README / 旧 00 有价值线索,但没有按当前 SOP 把问题层收干净。 | 可以说明“当前需要重建需求问题层”,不能继承旧进度或数字。 |

因此,业务背景候选应表达:

- Quantalithos 需要把平台产出的可审计资产作为正式需求主题收束。
- Artifact 正文、版本、血缘与基线事实会被多个相邻仓长期引用,不能依赖相邻仓各自解释。
- 当前重新讨论 L1-artifact,是为了把旧材料中的制品叙事、标准线索和历史功能想象,先收敛成干净的问题定义。

#### 5.1.2 诊断

旧材料中有几类背景表达需要区分:

| 旧表达 | 可取之处 | 问题 |
|---|---|---|
| “每一次需求、设计、代码、测试、发布、复盘最终都要沉淀为制品” | 能解释制品域的业务背景。 | 后文马上列 16 kind、7 relation、hash 和 Baseline,滑入能力 / 功能 / 规则。 |
| “制品不是附件,而是第一类业务对象” | 能支撑 artifact 不应退化为文件存储。 | “第一类业务对象”在 Step 3 只能作背景,不能展开对象模型。 |
| “work / governance / process / archive 都需要它” | 能说明跨仓引用背景。 | 不能在 Step 3 写成使用方与依赖表,应后置到 Step 6 / Step 12。 |
| “预计规模 5000w Artifact × 1.5 亿 Relation” | 可能是后续容量 / NFR 线索。 | 当前没有正式测量来源,不能在 Step 3 伪量化为问题。 |
| “Rust + PostgreSQL + Git / S3 / inline / URL” | 可能是旧实现想象。 | 属于架构 / 配置候选,不能进入业务背景。 |

当前背景段落应避免两类偏差:

- 偏业务口号:只说“产出都很重要”,但没有说明为什么需要在需求层收束。
- 偏实现方案:把背景写成“需要多后端内容存储、hash、防篡改、血缘查询和事件联动”。

#### 5.1.3 取舍

| 方案 | 背景表达 | 优点 | 缺点 | 当前取舍 |
|---|---|---|---|---|
| 方案 A | L1-artifact 是一切可审计产出的承载者。 | 简短,承接六域模型和旧材料。 | 太像 Step 2 定位,不足以解释当前问题背景。 | 不单独采用。 |
| 方案 B | Quantalithos 的需求、设计、代码、测试、发布和复盘都需要形成可审计、可追溯、可冻结的制品事实,而这些事实会被多仓长期引用。 | 能解释当前为什么需要讨论 artifact 问题层。 | 后续仍需在模块 2 具体列出现状与问题。 | 采用为主线。 |
| 方案 C | L1-artifact 需要支持 16 kind、7 relation、Baseline、DatasetArtifact 和 hash 防篡改。 | 贴近旧 00。 | 已经进入功能、规则和数据对象,不符合 Step 3。 | 不采用。 |
| 方案 D | L1-artifact 是最重持久化仓,需要支撑 5000w Artifact 和 1.5 亿 Relation。 | 看似量化。 | 数字无当前正式来源,且是 NFR / 测试线索。 | 不采用。 |

当前推荐把业务背景收束为“平台产出需要统一成为可审计制品事实,且这些事实会被多个相邻仓长期引用”。这能承接 Step 2 的边界,同时不会提前进入目标、功能、依赖或性能。

### 5.2 模块 1:业务背景候选:再写入

#### 5.2.1 业务背景结论

```text
Quantalithos 的需求、设计、代码、测试、发布和复盘都会形成需要长期引用的制品事实,这些事实必须可审计、可追溯、可冻结,不能退化为附件或相邻仓的临时状态。随着 work、process、governance、conversation、workspace、observability 和 archive 都会引用或消费 Artifact,平台需要先把 L1-artifact 的问题层重新收束,避免旧材料中的功能、标准、性能和实现想象直接替代需求问题定义。
```

#### 5.2.2 背景结论拆解

| 要点 | 采用内容 | 说明 |
|---|---|---|
| 产品 / 系统背景 | 需求、设计、代码、测试、发布和复盘都会形成制品事实。 | 解释 artifact 为什么不是普通附件主题。 |
| 当前阶段原因 | 多个相邻仓会长期引用或消费 Artifact。 | 解释为什么需要在需求层先收束问题。 |
| 本步目的 | 重新收束问题层,不让旧功能、标准、性能和实现想象替代问题定义。 | 防止 Step 3 滑向目标、功能、NFR 或方案。 |

#### 5.2.3 不采用表达

| 表达 | 不采用原因 |
|---|---|
| `L1-artifact` 要支持 16 kind、7 relation、Baseline、DatasetArtifact。 | 这是能力 / 功能 / 数据候选,不是业务背景。 |
| `L1-artifact` 要实现多后端内容存储和 hash 防篡改。 | 这是方案、规则或 NFR 候选,不属于 Step 3 背景。 |
| `L1-artifact` 需要支撑 5000w Artifact 和 1.5 亿 Relation。 | 旧数字无当前正式测量来源,后置到非功能或验收。 |
| `L1-artifact` 的目标是统一管理所有产出。 | “目标是”会进入 Step 4,当前只写背景与问题。 |

#### 5.2.4 后续约束

模块 2 需要继续把背景转成 1~3 个主要问题,并遵守以下限制:

- 问题必须写“当前表现”和“影响范围 / 后果”。
- 能量化的问题才量化;旧 P95、规模和覆盖率不得伪装成当前问题量化。
- 不把解决方案写成问题。
- 不把 Artifact kind、relation kind、Baseline 规则、Dataset 字段或 content backend 写成问题本身。

### 5.3 模块 2:现状与问题候选:先思考

#### 5.3.1 问题回答

模块 2 要把业务背景转成 1~3 个主要问题。当前不能把旧 `P95`、`5000w Artifact`、`1.5 亿 Relation`、`16 kind`、`7 relation` 当成已确认问题量化,因为这些来自旧材料或主题线索,没有在本轮 Step 1 / Step 2 中形成正式测量来源。本步应采用“当前表现 + 影响范围 / 后果”的方式表达问题。

候选问题应围绕三条主线收束:

| 问题主线 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 制品事实缺少新版需求层收束 | 旧 README 和旧 `00` 已把背景、目标、对象、功能、性能、实现和验收混写。 | 后续 `01~07` 容易继承未闭口对象、规则、接口或 NFR,导致需求到设计链路不稳。 |
| 制品事实容易被相邻仓各自解释 | work、process、governance、conversation、workspace、observability、archive 都会引用或消费 Artifact。 | Artifact 正文、版本、血缘和基线事实可能散落到相邻仓,形成多真相。 |
| 问题、方案和量化指标容易混层 | 旧材料把多后端存储、hash、防篡改、事件、P95、规模数字写进背景 / 痛点。 | Step 3 若继承这些说法,会把方案、NFR 或测试指标伪装成问题定义。 |

#### 5.3.2 诊断

当前问题定义不能写成“缺少某个功能”或“需要某个方案”。例如:

| 不合规问题写法 | 诊断 |
|---|---|
| 缺少 `GetLineage(depth=5)`。 | 这是功能 / 查询能力命名,应后置到功能需求或核心能力讨论。 |
| 缺少 Git / S3 / inline / URL 多后端内容存储。 | 这是架构 / 配置候选,不是业务问题。 |
| 缺少 `artifact.content_tampered` critical 事件。 | 这是事件 / 规则 / 验收候选,不是 Step 3 的问题表主语。 |
| 需要 16 种 kind 和 7 种 relation。 | 这是对象 / 枚举 / 规则候选,不是当前问题定义。 |
| 性能问题是写入 P95、血缘查询 P95 和 hash 校验耗时。 | 旧数字无本轮测量来源,不能作为 Step 3 已量化问题。 |

更合规的表达应是:

- “制品事实需求层未重新收束”。
- “制品正文、版本、血缘和基线容易被相邻仓复制或重建”。
- “旧材料把问题、方案、对象、NFR 和验收混在一起,会污染后续设计真相源”。

#### 5.3.3 量化口径

| 量化对象 | 当前判断 | 处理口径 |
|---|---|---|
| 旧规模数字 `5000w Artifact × 1.5 亿 Relation` | 不是本轮确认的事实或测量结果。 | 后置到 Step 13 / Step 14,作为容量 / 非功能候选再审。 |

## 5. 模块思考记录

### 5.1 模块 1:主要角色候选:先思考

#### 5.1.1 问题回答

模块 1 要回答“哪些身份会直接接触 `L1-artifact` 的制品事实”。这里的角色不是仓名、依赖方、API 调用方或用户故事主语,而是在业务语境中产出、审查、维护、消费或审计 Artifact 正文、版本、血缘与基线事实的身份。

基于 Step 2 / Step 4 的边界,角色候选必须满足以下判定:

| 判定问题 | 可进入角色候选 | 不进入角色候选 |
|---|---|---|
| 是否以身份接触 Artifact 正文、版本、血缘或基线事实 | 制品作者、审查者、负责人、审计者、系统维护 actor。 | `L1-work`、`L1-process`、`L1-governance`、`L4-archive` 等仓名。 |
| 是否描述接触场景而非接口动作 | 产出制品、审查制品、维护基线语境、查看血缘和审计证据。 | `CreateArtifact`、`Approve`、`GetLineage`、事件订阅、RPC 调用。 |
| 是否避免提前写用户故事 | 角色身份和接触场景。 | “作为某角色,我希望……”的故事句式。 |
| 是否避免提前写权限实现 | 角色之间存在差异的方向。 | 权限矩阵、Command 权限、状态机、字段、ACL 或 policy 规则。 |

因此,模块 1 的角色候选应从“接触制品事实的身份”出发,而不是从旧文档里的操作表、用例表或相邻仓关系反推。

#### 5.1.2 旧角色材料诊断

旧 `00-需求文档.md` §4 有角色线索,但混入了仓际依赖、权限动作和后续功能:

| 旧表达 | 可保留线索 | 当前问题 | Step 5 处理 |
|---|---|---|---|
| 开发者 / AI 成员 | 有“制品产出者”线索。 | 把人类开发者和 AI / 自动化产出者混在一起,且使用场景写成 create / update / approve。 | 拆成制品作者 / 产出者与 AI member / 自动化产出者候选;接口动作后置。 |
| QA / Reviewer | 有“制品审查者”线索。 | 使用场景写成 approved / rejected,已经滑入状态和操作。 | 保留审查者候选;审查规则和状态后置。 |
| Governance | 有“治理消费 artifact 事实”线索。 | `L1-governance` 是相邻仓,不是角色。 | 不写成角色;后移 Step 6 / Step 12。 |
| Work / PM | PM / 项目负责人可能是人类业务角色。 | `Work` 仓和 WorkItem 关闭是依赖 / 功能 / 规则,不是角色说明。 | 只保留项目 / 领域负责人候选;Work 仓后移。 |
| Auditors | 有“审计者 / 合规查看者”线索。 | 查 baseline / tampered 已接近功能和规则。 | 保留审计者候选;查询能力和篡改规则后置。 |
| 普通成员 / Reviewer / QA / Owner / Admin / Auditor / 系统 权限矩阵 | 有作者、审查者、负责人、审计者、系统 actor 线索。 | 矩阵操作包含创建、更新、Approve、Baseline、Archive,属于后续功能、规则、接口或验收。 | 不继承权限矩阵;只提取角色身份线索。 |

旧材料最容易污染 Step 5 的点是把仓名当角色、把接口动作当场景、把权限矩阵当需求结论。当前只能保留身份线索,不能保留旧操作项。

#### 5.1.3 角色候选主轴取舍

| 方案 | 角色主轴 | 优点 | 缺点 | 当前取舍 |
|---|---|---|---|---|
| 方案 A | 沿用旧表:开发者 / AI 成员、QA / Reviewer、Governance、Work / PM、Auditors。 | 简短,承接旧文档。 | 仓名、角色、接口动作和故事混写。 | 不采用。 |
| 方案 B | 按制品事实接触方式拆:产出、审查、负责 / 维护、消费、审计、系统维护。 | 能回指 Artifact 正文、版本、血缘与基线事实,且不把仓际依赖写成角色。 | 需要后续模块再细分角色类型和使用场景。 | 采用。 |
| 方案 C | 只写普通成员、Reviewer、Owner、Auditor、系统。 | 接近旧权限矩阵。 | 太抽象,且容易把权限矩阵带回来。 | 不采用。 |
| 方案 D | 把所有相邻仓消费方写成系统角色。 | 看起来覆盖协作关系。 | 违反 Step 5,会把 Step 6 使用方与依赖提前写入角色章。 | 不采用。 |
| 方案 E | 按 Artifact kind 写角色,如 code 作者、design 作者、test-report 作者。 | 细。 | 提前固定 kind 和功能范围,违反 Step 4 后置审计边界。 | 不采用。 |

当前推荐采用方案 B,先把角色候选收束到接触制品事实的身份类别,再由模块 2 进一步区分人类角色、平台成员角色、系统角色、审计 / 维护类角色。

#### 5.1.4 当前推荐方向

模块 1 再写入时,建议将主要角色候选收束为以下方向:

| 候选角色方向 | 接触制品事实的方式 | 边界说明 |
|---|---|---|
| 制品作者 / 产出者 | 产出或提交需要成为 Artifact 正文、版本和血缘事实的工作产物。 | 不写 CreateArtifact、update、kind 或状态流转。 |
| AI member / 自动化产出者 | 作为平台成员或自动化来源产生受控制品输入。 | 身份真相不归 artifact;runtime 执行和工具调用不归 artifact。 |
| 制品审查者 / Reviewer / QA | 在审查语境中接触制品版本、正文摘要、血缘和基线候选。 | 不写 approve / reject 状态、规则或权限矩阵。 |
| 制品负责人 / Owner | 对制品事实的归属、可引用性和基线准备承担业务责任语境。 | 不写 admin 权限、Gate 决策或 baseline pin 规则。 |
| 项目 / 领域负责人 | 在项目、过程、工作或发布语境中消费制品事实。 | 不把 `L1-work`、`L1-process` 或发布流程写成角色。 |
| 审计者 / 合规查看者 | 查看制品版本、血缘、基线和完整性相关证据。 | 不写查询功能、审计日志存储或 tampered 规则。 |
| 制品系统 actor | 代表平台以受控方式提交、消费或维护制品事实。 | 不写具体相邻仓名、事件名或接口。 |
| 运维 / 后台任务 | 执行重建、对账、扫描准备或派生维护等技术维护语境。 | 不通过维护动作创造业务制品结论。 |

这些仍是角色候选,不是最终角色说明表。上述候选已整理为模块 1 结论,并作为下一步模块 2 `角色类型与系统角色` 分类诊断的输入。

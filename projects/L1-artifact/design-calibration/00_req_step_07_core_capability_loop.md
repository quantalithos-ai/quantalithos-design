## 2. 开工判断

### 2.1 本步目标

Step 7 要从 `L1-artifact` 作为可审计制品真相仓的存在必要性出发,收敛“这个仓成立所需的核心能力骨架”。本步不是功能列表、用户故事、接口清单、事件清单或实施阶段计划。

本步需要回答:

- 如果 `L1-artifact` 缺少哪些能力,就不再是完整的 Artifact truth 仓。
- 这些能力之间的逻辑依赖关系是什么。
- 核心能力闭环应拆成哪些稳定能力节点。
- 哪些能力只是外围增强,哪些能力属于边界外。
- 旧材料中的功能线索分别支撑哪些能力节点,还是应后置或裁剪。

### 2.2 本步不做

本步不做以下事项:

- 不写用户故事或“作为...我想...”句式。
- 不写功能需求编号、优先级、P0 / P1 或版本阶段。
- 不写业务规则、数据归属、接口协议、事件名、DTO、port、repository、handler 或事务流程。
- 不写对象字段、状态机细节、数据库表、索引、配置项或测试用例。
- 不把旧功能清单直接当作核心能力闭环。
- 不把运行时调用顺序、事件传播顺序、开发实施顺序画成核心能力闭环。

## 5. 整体模块搭建:先思考

### 5.1 拆分原则

Step 7 的核心风险是过早把旧功能、接口、事件、状态机或技术机制当成“核心能力”。因此模块顺序必须先建立能力判断框架,再逐步落到节点、顺序和映射。

拆分时应遵守以下原则:

- 先复核 `L1-artifact` 的仓存在必要性,只从 Artifact truth 不可替代缺口出发。
- 再提炼 3~5 个核心能力候选,每个候选必须回答“缺少它时仓是否不成立”。
- 能力闭环图必须晚于候选提炼,避免先画图后补理由。
- 外围增强和边界外能力必须单独裁剪,防止 search、projection、archive、observability、workspace、console、sync 或外部存储误入核心。
- 旧材料功能只能最后回填映射,不能作为能力节点来源。
- 当前只搭模块顺序,不直接命名核心能力节点、画 ASCII 图或写正式草稿。

### 5.2 建议模块顺序

| 顺序 | 模块 | 讨论目的 | 不提前写入的内容 |
|---:|---|---|---|
| 1 | 仓存在必要性复核 | 回到 Step 2 / 3 / 4 / 6,说明没有 `L1-artifact` 时平台缺什么不可替代能力。 | 不列功能清单,不写对象字段、接口或旧功能编号。 |
| 2 | 核心能力候选提炼 | 从必要性中提炼 3~5 个必须共同成立的能力候选。 | 不先画图,不写用户故事、功能需求或业务规则。 |
| 3 | 能力闭环与执行顺序 | 判断能力之间的逻辑前置关系,形成闭环短文和节点讨论顺序。 | 不把箭头解释为调用、事件、事务或开发顺序。 |
| 4 | 外围增强与边界外能力 | 区分哪些能力重要但不进核心,哪些完全不属本仓。 | 不把归档、观测、搜索、同步、外部存储等写成核心前置。 |
| 5 | 旧材料功能回填映射 | 将旧功能和能力线索回贴到核心、外围或边界外。 | 不继承旧优先级、SLA、接口名、事件名或技术方案。 |
| 6 | 结构化中间产物 | 汇总闭环定义短文、ASCII 图、能力节点顺序、能力层级表和回填映射。 | 不新增前面模块未确认的能力节点。 |
| 7 | 回填草稿 | 形成正式第 7 章候选正文,等待 Step 17 统一装配。 | 不直接修改正式 `00-需求文档.md`。 |
| 8 | 自检与停审 | 核对 SOP、书写规范和后续 Step 8 输入,判断是否允许进入 Step 8。 | 不越过未解决 blocker。 |

### 5.3 为什么按这个顺序

如果先提炼核心能力候选,容易把旧 `CreateArtifact`、`PublishVersion`、`Baseline`、`GetLineage` 等动作直接搬进闭环。先做“仓存在必要性复核”可以迫使讨论回到 Artifact truth 的不可替代性:正文、版本、血缘、基线和可消费事实是否共同成立。

如果先画 ASCII 图,容易把事件传播或接口调用画成闭环。所以图必须等候选节点和逻辑前置关系明确后再写。

外围增强与边界外能力要放在旧功能映射之前,因为旧材料里有很多 search、browse、storage、hash、archive、observability、projection、notification、SLA 和技术栈线索。先划分层级,才能防止旧材料反向污染核心能力。

### 5.4 本步需要重点防止的错误

| 错误 | 影响 | 本步处理 |
|---|---|---|
| 把旧功能动作当成核心能力节点 | 核心闭环退化为功能清单 | 旧功能只在模块 5 回填映射。 |
| 把内容存储或多后端写成核心能力 | 把实现机制误写成需求能力 | 外部系统和存储后端已在 Step 6 裁剪,Step 7 不写技术方案。 |
| 把事件协作画成闭环图 | 把事件传播误写成能力成立关系 | 闭环图只表达逻辑依赖,不写事件名或 payload。 |
| 把下游消费方写成核心前置 | 让消费退化反向阻塞 Artifact truth | Step 6 已将消费方定义为输出消费或退化关系。 |
| 一次性展开所有后续需求 | 后续 Step 8~14 无法按能力节点小循环追溯 | 本步只输出能力节点、顺序和层级,不写故事 / 功能 / 规则 / 数据 / 接口 / 验收。 |

| 缺口 | 表现 | 为什么不能由相邻仓替代 |
|---|---|---|
| 制品正文缺少唯一来源 | 同一产出可能作为 WorkItem 附件、Activity output、对话预览、归档材料或外部链接分别存在。 | 相邻仓保存的是工作、过程、对话、视图或归档语境,不是 Artifact 正文真相。 |

### 11.3 闭环方向候选

当前候选闭环方向建议为:

```text

  -> 制品血缘关联
  -> 制品基线冻结
  -> 制品事实可消费表达
  -> 回到制品事实承载 / 版本化 / 血缘 / 基线的稳定引用
```

这条闭环表达的含义是:

- Artifact 首先需要成为正式制品事实。
- 正式制品事实需要版本化,才能被长期引用和比较。
- 版本化制品需要血缘关联,才能被追溯、影响分析和审计。
- 可引用且可追溯的制品集合需要基线冻结,才能形成受控状态。
- 受控制品事实需要可消费表达,让相邻仓引用而不复制 truth。
- 相邻仓的消费、引用和反馈不能反向拥有 truth,只能推动新的制品事实、版本、血缘或基线需求继续进入本仓闭环。

## 13. 模块 4 外围增强与边界外能力:先思考

### 13.1 本模块要回答的问题

模块 4 要在核心闭环已经固定后,诊断哪些事项只能作为外围增强,哪些事项属于边界外能力,哪些事项应推迟到后续 Step 或后续文档。这个模块的作用是保护 5 个核心能力节点不被旧功能、技术机制、消费体验或相邻仓职责污染。

本模块仍只做诊断,不直接固化最终能力层级表。最终表格留到 `模块 4 外围增强与边界外能力:再写入`。

| 判断问题 | 当前口径 |
|---|---|
| 某事项是否是 Artifact truth 成立前置 | 只有缺失后会让正文、版本、血缘、基线或可消费 truth 不成立的事项,才可能进入核心。 |
| 某事项是否只是提升使用体验或消费效率 | 若只是让查询、展示、同步、归档或观测更方便,应列为外围增强。 |
| 某事项是否属于相邻仓 truth | 若事实归属在 work、process、governance、conversation、workspace、archive、observability、runtime、method-library 或 capability-hub,应列为边界外。 |
| 某事项是否是实现 / 架构 / 配置 / NFR | 若是存储后端、索引、hash、缓存、数据库、加密、容量、P95 或部署选择,不进入 Step 7 核心闭环。 |
| 某事项是否只是旧材料功能名 | 旧功能名必须等模块 5 映射,不能在本模块反向生成新核心节点。 |

### 13.2 分类标准

后续再写入时建议使用四层分类:

| 分类 | 判定标准 | 进入核心闭环 |
|---|---|---|
| 核心能力 | 缺失后 `L1-artifact` 不再能作为可审计制品真相仓成立。 | yes |
| 外围增强 | 不改变 Artifact truth 归属,但提升查询、展示、同步、消费、审计或运维体验。 | no |
| 边界外能力 | truth 归属在其他仓,或属于外部系统 / 实现平台能力。 | no |
| 后续 Step / 后续文档处理 | 主题相关,但粒度属于用户故事、功能、规则、数据、接口、NFR、验收、架构、配置或实施计划。 | no |

该分类标准要防止两类误判:

- 把“重要”误判为“核心”。重要的消费体验、完整性要求、索引和归档能力仍可能不是 Step 7 核心节点。
- 把“常见实现手段”误判为“需求能力”。数据库、对象存储、hash、projection、cache 等不能替代 Artifact truth 能力。

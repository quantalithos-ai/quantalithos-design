## 3. 开工确认 / 必读文档:先思考

### 3.1 本步目标诊断

Step 12 要把 Step 6 的依赖裁剪、Step 7 的核心能力、Step 9 的功能需求、Step 10 的业务规则和 Step 11 的数据归属,转成需求层接口与依赖边界。这里的接口不是 API、DTO、事件 payload 或 port,而是能力级接口面:

- `L1-artifact` 对外提供哪些正式制品能力入口或读取 / 引用面。
- `L1-artifact` 消费哪些外部能力级输入,但不接管外部 truth。
- 哪些边界属于查询接口、变更接口、事件输入、事件输出或后台任务能力。
- 哪些外部关系属于定义来源依赖、治理结论依赖、下游消费依赖或外部能力依赖。
- 哪些全局依赖类型只能是编译期、运行期或事件协作,不能被误写成 package dependency。

本小步只确认后续需要读什么、按什么粒度写、不能混入什么。正式接口依赖表和第 12 章候选草稿要等后续模块逐步确认后再写。

### 3.4 初步关注点

后续 Step 12 需要重点防止以下混层:

- 把接口与依赖写成 API 路径、Command 名、函数名、SDK 方法或 console 页面。
- 把接口能力边界写成 DTO / JSON / proto / event payload 字段。
- 把 `L0-bus` 事件协作写成 `L1-artifact` 对业务仓的编译期依赖。
- 把 `L1-work`、`L1-process`、`L1-governance`、`L1-conversation`、`L1-workspace` 等消费或引用关系写成 truth ownership 转移。
- 把 `L2-runtime`、`L3-capability-hub`、tool、model 和运行材料通过接口写成 Artifact truth 输入。
- 把 `L4-archive`、`L4-observability`、`L5-console`、`L5-sync`、`L0-sdk` 等消费 / 显化通道写成新的核心 truth 来源。
- 把 Step 6 的仓依赖表原样复制到 Step 12,而没有说明这些关系如何体现为能力级输入 / 输出边界。
- 把搜索、projection、cache、分页排序、重试、fallback、relay、事务、outbox 或配置写入需求接口章节。
- 生成无法回指核心能力节点、FR-ART、BR-ART 或 Step 6 依赖裁剪的接口边界。

### 3.5 接口与依赖类型初步使用口径

| 类型 | Step 12 中的初步用途 | 当前禁区 |
|---|---|---|
| 查询接口 | 表达外部使用者读取、检索、引用 Artifact fact、version、lineage、baseline 和可消费表达的能力面。 | 不写查询 API、参数、分页字段、索引、缓存或 read model。 |
| 变更接口 | 表达外部语境把材料显式收束为 Artifact fact、version、lineage 或 baseline 的正式变更能力面。 | 不写命令名、状态机、事务、并发控制、handler 或 repository。 |
| 事件输出 | 表达 Artifact truth 变化可被相邻仓持续消费的输出能力。 | 不写事件名、payload、topic、subscription、outbox 或 retry。 |
| 事件输入 | 表达本仓可从外部持续接收协作线索,但需要正式收束后才影响 truth。 | 不写订阅实现、投影、幂等、broker 或 event handler。 |
| 后台任务接口 | 仅在需求层表达维护、审计准备、对账或后续整理的能力入口。 | 不写 job 名、调度、队列、锁、重试或执行流程。 |
| 定义来源依赖 | 表达 Artifact 能力需要引用上游定义、方法、模板或语义来源。 | 不保存定义正文,不写运行协议或 package dependency。 |
| 治理结论依赖 | 表达某些能力边界需要消费正式治理结论或批准语境。 | 不保存治理正文,不把治理裁决写成 Artifact truth。 |
| 下游消费依赖 | 表达本仓能力必须被 work、process、governance、archive、observability、workspace、SDK、console、sync 等持续消费。 | 不让下游拥有 Artifact truth,不写下游接口实现。 |
| 外部能力依赖 | 表达 runtime、capability、tool、model、workspace 等外部能力只提供输入或消费语境。 | 不保存外部正文,不接管外部生命周期。 |

## 5. 整体模块搭建:先思考

### 5.1 模块搭建目标

Step 12 的模块骨架要把接口与依赖讨论固定在“核心能力节点 -> 能力级接口面 -> 能力级依赖边界 -> 类型判断 -> 来源映射”的顺序上。这里不能从旧 API、Command、DTO、事件名、仓依赖表或 UI 入口出发,也不能把 Step 6 的仓际依赖裁剪表原样复制成第 12 章。

### 5.2 模块主轴判断

| 候选组织方式 | 判断 | 原因 |
|---|---|---|
| 按五个核心能力节点组织 | 采用 | Step 7~11 已沿用同一主轴;接口与依赖也应回到同一能力闭环,便于追溯 FR-ART、BR-ART 和数据边界。 |
| 按接口类型组织 | 不采用为主轴 | 查询、变更、事件输入 / 输出和后台任务是每个能力模块内的分类维度,作为主轴会割裂能力来源。 |
| 按外部仓 / 关联方组织 | 不采用为主轴 | 容易变成 Step 6 依赖表复制,无法解释能力级输入 / 输出边界。 |
| 按旧 API / Command / event 组织 | 不采用 | 会提前锁定协议和实现契约,违反 Step 12 粒度。 |
| 按数据类型组织 | 不采用为主轴 | 真相、快照、引用和禁止正文是接口边界约束,不是接口模块主轴。 |

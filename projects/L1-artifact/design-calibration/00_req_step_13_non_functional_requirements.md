## 3. 开工确认 / 必读文档:先思考

### 3.1 本步目标诊断

Step 13 要把 Step 7 的核心能力、Step 10 的业务规则、Step 11 的数据归属和 Step 12 的接口依赖边界,转成需求层质量约束。这里的非功能需求不是测试方案、SLO 仪表盘、数据库优化、缓存策略、加密方案或运行配置,而是说明 `L1-artifact` 作为可审计制品真相仓必须满足哪些质量底线。

本步需要回答:

- 哪些非功能要求能回指具体核心能力节点。
- 哪些非功能要求覆盖全仓,不能强行归入某个能力节点。
- 本仓在性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性六类上分别需要什么判断口径。
- 哪些要求可以在后续阶段量化,哪些当前只能给出清晰判断口径。
- 每项非功能要求后续应由 Step 14 的哪些验收条件承接。

本小步只确认后续要读什么、按什么粒度写、不能混入什么。正式 NFR 表、目标值 / 判断口径表和第 13 章候选草稿要等后续模块逐步确认后再写。

### 3.4 初步关注点

后续 Step 13 需要重点防止以下混层:

- 把“高性能、高可用、高安全”写成空洞口号,没有判断口径。
- 直接继承旧文档里的 P95、容量、SLA、审计覆盖率或存储目标,但没有当前来源。
- 把缓存、索引、数据库优化、对象存储、多后端、加密方案、监控平台、日志字段或告警规则写成需求层 NFR。
- 把 archive、observability、workspace、console、sync、SDK 的消费体验写成核心 Artifact truth 可用性的成立前置。
- 把事件输出、projection、搜索、报表、归档准备或高级浏览延迟写成可以反向修改 Artifact truth 的理由。
- 把 work、process、governance、conversation、method-library、runtime、capability-hub 的正文处理要求写成本仓安全或数据要求。
- 把全仓质量约束硬塞到某一个能力节点,或把能力级约束写成没有能力 / 目标来源的孤儿 NFR。
- 提前写 Step 14 验收项、测试用例、Given-When-Then、VETO、证据文件或实施门禁。

## 5. 整体模块搭建:先思考

### 5.1 模块组织问题诊断

Step 13 的核心不是把“性能、可用性、安全”等六个标题逐项填满,也不是把旧文档里的 SLA、容量、P95 / P99、缓存、索引、监控和日志配置搬进需求层。非功能需求要回答的是: `L1-artifact` 作为制品真相仓,在核心能力成立时必须守住哪些质量底线;当外围依赖、消费链路或增强能力不可用时,哪些事实仍然必须保持清晰、不可伪造、可追溯和可判断。

因此 Step 13 的主轴应先按“能力级 NFR”和“全局 NFR”拆分,再用六类非功能类别做横向审计:

- 能力级 NFR 用来约束五个核心能力节点,确保每个核心能力不只是“能做”,还要在性能、可用性、安全、审计 / 可追溯、幂等 / 一致性和可观测性上有需求层判断口径。
- 全局 NFR 用来约束跨能力的仓级质量底线,例如单一 Artifact truth、外部正文不归属、本仓不反写相邻仓 truth、依赖降级不得伪造 truth、边界异常必须可观察。
- 六类类别审计用于发现遗漏,不是第一组织轴。否则容易写成按类别堆口号,看不出每条要求来自哪个能力或全仓目标。
- 判断口径 / 目标值取舍要单独成段,避免把无来源的数字硬写成正式需求,也避免所有要求都停留在“高性能 / 高可用 / 可观测”的空话。

### 5.2 能力级 NFR 主轴

能力级 NFR 应围绕 Step 7 固定的五个核心能力节点展开。每个能力节点至少需要回答“质量要求保护什么”“失败或降级时不得发生什么”“该要求如何回指功能 / 规则 / 数据 / 接口输入”。

| 能力节点 | Step 13 关注点 | 不应写入的内容 |
|---|---|---|
| 制品事实承载 | Artifact fact 作为本仓 truth 入口时,其纳管、引用、边界和变更必须具备可判断的稳定性、安全边界和可追溯性。 | 不写存储后端、对象存储、hash 算法、表结构、权限实现或导入流程细节。 |
| 制品版本化 | Artifact version 必须保护版本语义不被无声覆盖,同一版本含义在平台内保持一致,版本变更具备可追踪依据。 | 不写锁、事务、冲突算法、版本号生成策略或数据库唯一索引。 |
| 制品血缘关联 | Artifact lineage 必须能表达正式来源 / 派生 / 关联语义,不能由消费方、外部正文或外围视图补造。 | 不写图数据库、遍历算法、搜索索引、批处理或图谱展示实现。 |
| 制品基线冻结 | Artifact baseline 必须能冻结一组已确认制品事实,后续消费或外围变化不得改写冻结时的正式语义。 | 不写快照表、存储压缩、归档策略、签名算法或发布流水线配置。 |
| 制品事实可消费表达 | 可消费表达必须让下游获得足够的正式引用、状态和边界信息,同时不转移 Artifact truth ownership。 | 不写 SDK API、event payload、projection schema、dashboard 或订阅重试策略。 |

### 5.3 全局 NFR 主轴

全局 NFR 不应硬塞进某个能力节点。它们来自 Step 6、10、11、12 的跨仓边界和数据归属结论,用于保护整个 `L1-artifact` 的质量底线。

| 全局质量主题 | 需要表达的需求层判断 |
|---|---|
| 单一 Artifact truth | 同一 Artifact fact / version / lineage / baseline / consumption backref 在平台内不得出现多个正式含义。 |
| 外部正文不归属 | 本仓不得因性能、安全、可用性或可观测性诉求而保存 work、process、governance、conversation、runtime、method-library 等相邻仓正文。 |
| 依赖降级不伪造 truth | 外部依赖、事件协作、消费方或外围增强不可用时,本仓可以暴露等待、不可用或降级状态,但不得生成伪 truth 填补空缺。 |
| 消费失败不反写核心事实 | archive、observability、console、sync、SDK 或其他消费者的问题不得成为修改 Artifact truth 的理由。 |
| 边界异常可观察 | ownership 串线、外部正文越界、依赖缺失、消费回指异常、核心语义冲突等关键异常必须在需求层要求可被识别。 |

### 5.4 六类 NFR 审计定位

六类非功能类别应作为横向检查表使用。每一类都需要检查“能力级是否有要求”“全局是否有要求”“是否误写成实现方案”。

| 类别 | 在 Step 13 中的定位 | 审计重点 |
|---|---|---|
| 性能 | 判断核心 truth 能力和消费表达不应成为平台主链的系统性阻塞。 | 是否写成无来源 P95 / P99、容量、索引、缓存、批处理或 DB 优化。 |
| 可用性 | 判断依赖降级、外围失败、消费链路异常时核心 truth 的成立 / 等待 / 失败口径。 | 是否把所有外围能力都承诺为核心可用性,或让降级反向修改 truth。 |
| 安全 | 判断本仓不越权拥有相邻仓 truth、外部正文、运行材料和消费者私有材料。 | 是否滑入认证、授权、加密、密钥和权限模型实现。 |
| 审计 / 可追溯 | 判断关键事实、版本、血缘、基线和消费回指变化必须可追溯。 | 是否滑入审计表、日志字段、trace schema、event payload 或存储结构。 |
| 幂等 / 一致性 | 判断同一正式语义在重复请求、重复消费、外围重放和依赖异常下不产生多义 truth。 | 是否滑入幂等 key、锁、事务、repository、重试算法或冲突实现。 |
| 可观测性 | 判断关键状态、边界异常、依赖失败和消费异常必须能被平台稳定观察。 | 是否滑入 metrics 名、dashboard、alert rule、采集 agent 或日志平台配置。 |

### 7.3 六类 NFR 在能力级的适用判断

六类非功能类别在五个能力节点上都适用,但落点不同。后续写入时应避免每个能力都机械复制六类标题,而是选择能保护该能力主语义的质量要求。

| 类别 | 能力级使用方式 | 写入时的约束 |
|---|---|---|
| 性能 | 关注核心 truth 能力不成为平台主链的系统性阻塞,尤其是事实入口、版本定位、血缘读取、基线读取和消费回指。 | 只能写判断口径,不写 P95 / P99、吞吐、容量、索引、缓存、批处理或 benchmark。 |
| 可用性 | 关注外部依赖、事件协作、下游消费和外围增强不可用时,核心能力应给出成立、等待、不可用或降级的清晰语义。 | 不承诺搜索、预览、归档、观测、SDK、console、sync 等外围能力永远可用。 |
| 安全 | 关注正文 ownership、相邻仓 truth、runtime / tool / model 输出、消费方私有材料不得越界进入 Artifact truth。 | 不写认证、授权、加密、密钥、权限模型或安全组件。 |
| 审计 / 可追溯 | 关注事实纳管、版本形成、血缘关系、基线冻结和跨仓消费回指的关键变化可解释。 | 不写审计日志 schema、trace 字段、event payload、存储表或观测平台。 |
| 幂等 / 一致性 | 关注重复输入、重复消费、自动化再生成、相邻仓重放或事件协作延迟下,同一 Artifact 语义不分裂。 | 不写幂等 key、锁、事务、冲突算法、repository 或重试流程。 |
| 可观测性 | 关注未收束材料被误当 truth、版本覆盖、血缘补造、基线补造、消费反写等边界异常能被识别。 | 不写 metrics 名、dashboard、alert rule、采集 agent 或日志字段。 |

### 7.4 能力级候选取舍

能力级 NFR 应优先保留能直接保护 FR / BR / 数据 / 接口闭环的质量要求。无法回指能力节点或只描述外围体验的内容,应放入全局 NFR、外围增强审计或后续文档。

| 候选主题 | 归属判断 | 原因 |
|---|---|---|
| 正式 Artifact fact 入口稳定、可追溯、可观察 | 保留为制品事实承载能力级 NFR | 直接保护 FR-ART-001~004、BR-ART-001~005 和 Step 11 fact truth。 |
| 自动化产出显式收束质量 | 保留为事实 / 版本 / 血缘 / 基线相关能力级 NFR | 自动化材料在多个能力中都必须经正式语境收束,但每个能力的语义不同。 |
| 历史版本和历史基线可审计 | 保留为版本化 / 基线冻结能力级 NFR | 直接保护 FR-ART-008、FR-ART-016、BR-ART-010、BR-ART-020。 |
| 跨仓消费回指质量 | 保留为制品事实可消费表达能力级 NFR | 直接保护 FR-ART-020、BR-ART-025 和 Step 12 下游消费边界。 |
| 搜索、列表、预览、报表、projection 性能 | 不进入能力级核心 NFR | 属于外围增强或后续读侧设计,不能成为核心 truth 成立前置。 |
| hash 校验、tampered 扫描、签名、加密 | 暂不写入能力级 NFR | 可作为后续完整性 / 安全候选线索,当前缺正式来源和需求层判断口径。 |
| API 可用率、SDK 延迟、console 操作体验 | 不进入能力级核心 NFR | 属于访问通道或产品体验,不能反向定义 Artifact truth 质量。 |
| outbox、retry、transaction、lock、cache | 裁剪出 Step 13 | 属于实现、架构或详细设计机制,不是需求层 NFR。 |

### 7.5 下一步写入结构建议

`能力级非功能要求:再写入` 应把上述候选收敛成能力级 NFR 表。建议每个能力节点只保留能回指 FR / BR / 数据 / 接口输入的要求,并按以下字段写入:

| 字段 | 写法 |
|---|---|
| 能力节点 | 固定使用五个核心能力节点。 |
| NFR 类别 | 使用性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性之一。 |
| 要求 | 写需求层判断句,表达必须成立或不得发生的质量约束。 |
| 判断口径 | 写需求层可判断条件,不写测试用例、指标采集或实现机制。 |

写入时应控制粒度:不必为每个能力机械写满六类,但每个能力至少应覆盖其主语义所必需的稳定性、边界、安全 / ownership、追溯和一致性要求。性能和可用性若暂时无法量化,应写判断口径,不要填旧数字。

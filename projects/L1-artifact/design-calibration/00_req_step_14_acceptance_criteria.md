## 3. 开工确认 / 必读文档:先思考

### 3.1 本步目标诊断

Step 14 要把前面已经确认的需求结论收束成“怎样算通过”。它不是测试方案,也不是 CI / QA / 证据执行清单。验收标准只回答需求层的验收对象、验收类别和通过条件。

本步需要承接:

- Step 7 的五个核心能力节点,判断核心闭环如何算成立。
- Step 9 的 FR-ART-001~020,判断功能能力如何算完成。
- Step 10 的 BR-ART-001~025,判断规则和边界如何算没有串线。
- Step 11 的真相 / 快照 / 引用 / 禁止保存正文边界,判断数据归属如何算正确。
- Step 12 的接口与依赖边界,判断外部协作和外围增强如何不打穿能力边界。
- Step 13 的能力级 / 全局 NFR,判断质量底线如何算达标。

验收项必须写成可判断条件,不能只复述目标或功能名。每条验收项都必须能回指能力节点、功能、规则、数据归属、接口依赖或非功能要求。无法回指来源的验收项不得进入正式验收标准。

### 3.4 初步关注点

Step 14 需要重点防止以下混层:

- 把验收标准写成测试步骤、接口调用、脚本、CI、QA 工具或证据文件路径。
- 把验收项写成目标复述,没有“怎样算通过”。
- 把 Step 9 功能、Step 10 规则、Step 11 数据、Step 13 NFR 原文整段搬进验收章,缺少收敛。
- 把外围增强、搜索、预览、projection、报表、归档、观测、SDK、console、sync 缺口写成核心需求一票否决。
- 把旧 P95 / P99、容量、SLA、可用率或审计覆盖率写成当前需求层硬验收。
- 把一票否决项写得过宽,导致普通缺陷、可后续修复问题或外围增强缺口变成整体失败。
- 遗漏数据归属验收,导致外部正文、相邻仓 truth、运行材料或消费方私有材料仍可能进入 Artifact truth。
- 遗漏规则 / 边界验收,导致 truth 不转移、禁止覆盖、禁止补造、消费回指等硬规则无验收承接。

## 5. 整体模块搭建:先思考

### 5.1 模块组织问题诊断

Step 14 不能直接生成一张全仓验收清单。`L1-artifact` 的验收标准必须证明前面 13 个 Step 形成的需求链条已经闭合:核心能力能成立,功能需求有通过口径,规则 / 边界没有被打穿,数据 ownership 没有串线,接口与依赖没有把外部实现反推成本仓 truth,非功能要求有可判断的质量底线。

因此本 Step 的主轴应采用“能力级收敛 + 类别级审计”的双层结构:

- 先围绕 Step 7 固定的五个核心能力节点逐一收敛验收候选,避免验收项脱离能力闭环。
- 每个能力节点内只回答需求层“怎样算通过”,不写测试步骤、API 调用、字段、端口、证据文件或执行脚本。
- 五个能力节点形成候选后,再用五类验收类别横向审计覆盖:核心能力闭环、功能能力、规则 / 边界、数据归属、非功能验收。
- 一票否决项最后单独收束,只覆盖仓定位失效、核心闭环断裂、truth ownership 串线、相邻仓 truth 被接管、关键变化不可追溯等整体失败条件。
- 结构化中间产物必须能回指 Step 7 / 9 / 10 / 11 / 12 / 13,不得新增前序没有确认过的验收要求。

### 5.2 能力级验收主轴

能力级验收应按五个核心能力节点推进。每个能力节点至少要诊断四件事:该能力闭环怎样算成立;哪些 FR 必须被覆盖;哪些 BR / 数据 / 接口边界不能被打穿;哪些 NFR 是该能力的质量底线。

| 能力节点 | 验收思考重点 | 当前不得写入 |
|---|---|---|
| 制品事实承载 | Artifact fact 能成为本仓正式 truth 入口;外部正文、运行材料、消费方材料不能替代或污染 fact;事实纳管、读取、引用和变化感知有通过口径。 | 不写创建 API、上传流程、对象存储、hash 算法、字段 schema、权限实现或测试数据。 |
| 制品版本化 | Artifact version 能表达稳定、可追溯、不可无声覆盖的版本事实;候选修订、历史版本和被替代版本有需求层验收口径。 | 不写版本号生成、锁、事务、状态机、比较算法、数据库唯一约束或发布流水线。 |
| 制品血缘关联 | Artifact lineage 能表达正式来源、派生、依赖、影响和替代语义;血缘不得由 runtime trace、消费视图、工具输出或外部正文补造。 | 不写 relation enum、图数据库、递归查询、搜索索引、影响分析算法或 `GetLineage` 协议。 |
| 制品基线冻结 | Artifact baseline 能冻结受控版本集合事实;治理结论、发布口径、归档包或项目状态不能替代冻结语义。 | 不写 baseline 表结构、集合排序、签名算法、archive package、Gate 流程或发布配置。 |
| 制品事实可消费表达 | 下游能稳定引用和消费 Artifact truth,并获得必要状态 / 边界信息;消费失败、私有副本或下游语义不能反写本仓 truth。 | 不写 SDK、event payload、projection schema、workspace view、console 页面、sync 协议或 dashboard。 |

### 5.3 五类验收类别审计定位

五类验收类别不是五个并列大清单,而是对能力级候选的横向审计维度。每一类都应检查是否存在遗漏、重复、越界或不可判断项。

| 验收类别 | 审计问题 | 不通过的典型信号 |
|---|---|---|
| 核心能力闭环 | 五个能力节点是否共同构成“可审计制品真相”闭环,且无孤立能力或外围增强前置。 | 把搜索、预览、归档、观测、SDK、console、sync 当成核心闭环成立前置。 |
| 功能能力 | FR-ART-001~020 是否都被验收项覆盖,且每项功能只描述外部可见完成口径。 | 验收项直接写 handler、repository、DTO、port、event payload 或内部流程。 |
| 规则 / 边界 | BR-ART-001~025 是否都有防串线验收承接,尤其 truth 入口、禁止覆盖、禁止补造、禁止 truth 转移。 | 相邻仓可以补造 Artifact truth,或消费方失败可以反写核心事实。 |
| 数据归属 | 真相 / 快照 / 引用 / 禁止保存正文四类边界是否可验收。 | 外部正文、运行材料、消费方私有材料或 projection 结果进入 Artifact truth 生命周期。 |
| 非功能验收 | Step 13 的能力级 / 全局 NFR 是否有可判断的通过口径,并且没有无来源硬指标。 | 旧 P95 / P99、容量、SLA、覆盖率或实现方案被升级成当前硬验收。 |

### 5.4 来源映射和裁剪规则

Step 14 的每个验收候选都必须至少回指一个正式来源。映射规则应先宽后严:候选可以来自能力节点、FR、BR、数据归属、接口依赖或 NFR,但进入结构化产物前必须能说明它验收的是哪一类需求结论。

| 来源 | 进入验收的方式 | 裁剪规则 |
|---|---|---|
| Step 7 核心能力 | 作为能力级验收主轴和核心闭环验收来源。 | 不能新增第六个核心能力;外围增强只能作边界审计。 |
| Step 9 功能需求 | 作为功能能力验收来源,按 FR-ART-001~020 覆盖。 | 不能把实现动作、协议细节或内部对象写成验收项。 |
| Step 10 业务规则 / 边界 | 作为规则 / 边界验收和一票否决候选来源。 | 普通规则缺陷不自动升格为一票否决;只有打穿仓定位和 truth ownership 的才进入否决项。 |
| Step 11 数据归属 | 作为数据归属验收来源。 | 字段、表、存储后端和加密实现后置;正文越界、快照反向定义 truth、引用接管外部生命周期必须保留。 |
| Step 12 接口与依赖 | 作为接口 / 依赖边界是否保持需求层清晰的验收约束。 | 不写 API path、payload、topic、port、adapter、retry、transaction 或运行配置。 |
| Step 13 非功能需求 | 作为非功能验收来源。 | 无来源硬数字、旧指标、基础设施方案、监控实现和测试工具不得进入硬验收。 |

### 5.5 一票否决窄口径

一票否决不应用来承载所有失败。它只负责标出一旦发生就说明 `L1-artifact` 需求不成立的严重问题。候选应从以下方向收敛:

- `L1-artifact` 不再是 Artifact fact / version / lineage / baseline / consumption backref 的正式 truth owner。
- 相邻仓、消费方、runtime、archive、observability、console、sync 或 SDK 可以补造、覆盖或重解释 Artifact truth。
- 外部正文、运行材料、工具结果、projection、快照或私有消费副本进入 Artifact truth 生命周期。
- 五个核心能力中的任一节点无法成立,导致可审计制品真相闭环断裂。
- 关键 fact / version / lineage / baseline / consumption backref 变化不可追溯、不可判断或无法被平台观察。

以下内容不应进入一票否决:

- 搜索、预览、报表、归档准备、观测展示、console、SDK、sync 等外围增强缺失。
- 旧文档中的 P95 / P99、容量、SLA、覆盖率、hash 耗时或 benchmark 未定稿。
- 可由后续架构、测试、配置或实施阶段细化的实现策略。
- 普通缺陷、局部可修复问题、候选目标未量化或证据路径未确定。

### 11.1 本模块目标

一票否决项不是普通缺陷清单,也不是把所有未完成项都升格为失败条件。它只负责描述那些一旦发生就说明 `L1-artifact` 作为制品真相仓的需求结论不成立的严重情形。

本模块需要先判断哪些候选真的属于“整体失败”,哪些应留给功能、规则、数据、接口、NFR、后续设计或实现阶段处理。

### 11.2 诊断原则

| 原则 | 含义 |
|---|---|
| 先仓定位,后严重性 | 只有会破坏 `L1-artifact` 仓定位的情形才可能进入一票否决。 |
| 先核心闭环,后外围增强 | 外围增强、搜索、预览、projection、归档、观测、SDK、console、sync 的缺失不能直接升格为一票否决。 |
| 先 truth 边界,后局部缺陷 | 能打穿 truth ownership、让外部正文进入 truth、或让消费方反写 truth 的,才考虑否决。 |
| 先整体失败,后可修复项 | 能通过后续架构 / 测试 / 实现修复的普通缺陷,不应进入否决项。 |
| 先需求层,后实现层 | 否决项只描述需求层不可接受的结局,不描述代码错误或执行失败。 |

### 11.3 候选否决方向

| 候选方向 | 为什么可能进入否决 | 当前裁剪倾向 |
|---|---|---|
| 核心能力闭环失效 | 如果五个核心能力节点任一缺失,`L1-artifact` 失去制品真相仓定位。 | 保留为高优先级候选。 |
| truth ownership 串线 | 外部正文、运行材料、消费副本或相邻仓 truth 进入正式 truth,说明边界已被打穿。 | 保留为高优先级候选。 |
| 版本 / 血缘 / 基线不可追溯 | 核心事实无法形成稳定版本、正式血缘或可冻结基线,说明仓无法承载制品真相。 | 保留为高优先级候选。 |
| 消费反写 truth | 下游、观测、归档、console 或 sync 结果反过来修改 Artifact truth。 | 保留为高优先级候选。 |
| 外围增强缺失 | 搜索、预览、报表、SDK、console、sync 不可用。 | 裁剪,不直接否决。 |
| 旧性能指标未定稿 | 旧 P95 / SLA / 容量尚未进入当前需求层确认。 | 裁剪,不直接否决。 |

### 11.4 诊断结论

一票否决项候选应只从仓定位失效、核心闭环断裂、truth 边界被打穿、消费反写 truth 这些方向收束。外围增强缺失和未定稿指标不能混入,否则会把普通缺陷变成整体失败。

下一步应进入 `一票否决项:再写入`,把上述高优先级候选收束成最窄的一票否决项表。

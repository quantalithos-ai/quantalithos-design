## 1. 本步目标

确认当前概要设计依赖的需求结论和架构结论已经收敛到足以支撑“代码主体框架、主要组成部分、对象骨架、接口骨架、关键处理流与状态机”展开的程度,并识别哪些上游边界会直接影响当前概要设计的范围与深度。

本步只确认概要设计可承接什么,不重新讨论需求目标、架构边界、代码主体框架、对象轮廓、接口骨架、处理流或状态机。

## 3. SOP 问题回答

### 3.1 当前概要设计要承接哪些需求结论?

当前概要设计要承接以下需求结论:

- `L1-artifact` 是可审计制品真相仓,负责承载 Artifact 正文、版本、血缘、基线和可消费回指事实。
- 核心能力闭环围绕五条主线成立:制品事实承载、制品版本化、制品血缘关联、制品基线冻结、制品事实可消费表达。
- 本仓拥有 Artifact fact、Artifact version、Artifact lineage、Artifact baseline、consumable reference / backref 和 traceability / audit backref 等正式 truth。
- 本仓不拥有 work、process、governance、conversation、workspace、archive、observability、method-library、runtime 或 capability-hub 的 truth。
- 相邻仓可以引用、消费、展示、封存或观测 Artifact truth,但不能复制、反写、补造或迁移 Artifact truth ownership。
- 外部正文、运行材料、方法正文、归档包正文、观测正文和消费方私有材料不得进入本仓正式 truth。
- 自动化产出、过程产出、治理证据和人工提交都必须经正式收束后才可形成 Artifact fact / version / lineage / baseline 语义。
- 搜索、预览、projection、report、reconciliation、archive preparation 和下游同步只能消费或派生 Artifact truth,不得替代本仓 truth。

### 3.2 当前概要设计要承接哪些架构结论?

当前概要设计要承接以下架构结论:

- 架构主线是独立 Artifact truth,而不是附件库、内容后端、视图仓、归档包或观测记录仓。
- 内部语义结构围绕制品事实核心、制品版本核心、制品血缘核心、制品基线核心、输入收束、责任审查、自动化产出边界、消费表达、派生维护和本地引用 / 投影层展开。
- 正式运行承载包括同步入口、异步输入消费、真相存储承载、后台维护与派生、派生消费承载、事件协作 / 追溯交接边界和外部正文 / 内容来源边界。
- `L0-core` 是唯一编译期依赖;其余相邻仓和外部系统只能通过运行期、引用、快照、事件、safe summary 或 handoff 协作。
- 数据边界明确区分 Artifact truth、external reference、snapshot、derived material 和 forbidden body。
- 一致性采用核心强一致 + 外围最终一致;fact、version、lineage、baseline 和 backref 同步成立或拒绝,派生和交接可延迟。
- 同步 / 异步 / 后台三类路径分离;下游传播、读侧派生、对账、归档和观测交接不得拖重核心事实成立。
- 技术机制只在机制级收稳,不锁定数据库、对象存储、Git、hash、graph、search、message、完整事件溯源和旧性能数字。

### 3.3 哪些结论已经足够稳定,可以直接作为概要设计输入?

足够稳定、可以直接作为概要设计输入的结论包括:

- 仓定位、职责边界、非目标和一票否决红线。
- 五条核心能力闭环和 fact / version / lineage / baseline / backref 的正式 truth 主轴。
- 相邻仓只引用 / 消费 / 展示 / 交接,不拥有 Artifact truth 的边界口径。
- `L0-core` 唯一编译期依赖、其余边界运行期协作的依赖裁剪结论。
- Artifact truth / external reference / snapshot / derived material / forbidden body 的数据边界。
- 核心强一致、外围最终一致和同步 / 异步 / 后台三类路径分离的交互口径。
- 外部正文禁止入仓、派生不反写、交接不反写真相的结构性约束。
- 旧 hash / tamper / content backend / graph / search / P95 / 容量数字只作为后续候选输入,不直接升级为概要设计硬结论。

### 3.4 哪些结论虽然相关,但仍未收稳,因此当前不能直接往下展开?

以下结论仍未收稳,当前不能作为已定概要设计输入直接展开:

- 正式代码主体框架和主要组成部分的命名、层次和分工。
- 正式关键对象清单、对象类型、字段骨架、成员函数骨架和工厂函数骨架。
- 正式 API、Command、Query、Event、Operations Job 名称、参数和返回骨架。
- 关键处理流 / 重要函数数据流的入口、service、domain、port、event 和派生连接骨架。
- Artifact fact、version、lineage、baseline、consumption / audit backref 的详细状态集合和状态迁移矩阵。
- 异常与边界场景的正式分类、错误语义和回退口径。
- 配置影响轮廓中的正式受影响部分、禁止配置化边界和后续配置承接方式。
- 详细设计承接清单、对象 schema、状态机细节、持久化契约、交接 schema、测试切口和实现 boundary。
- Artifact classification、identity key、definition source、relation taxonomy、integrity candidate 和外部内容可用性细节。

### 3.5 哪些边界、非目标和约束会直接决定概要设计当前不该展开到哪里?

以下边界直接决定概要设计当前不该越界:

- 不重新定义需求目标、用户故事、验收标准和上游仓定位。
- 不重新定义系统上下文、子域划分、数据所有权原则、关键技术机制和方案取舍。
- 不展开完整 Rust 字段、完整函数实现、DDL、协议 schema、配置 JSON、测试用例或实施 commit boundary。
- 不让 work / process / governance / conversation / workspace / archive / observability / method-library / runtime / capability 的 truth 进入 Artifact truth。
- 不让 search、preview、projection、report、reconciliation、archive preparation、sync copy 或 maintenance job 反写业务 Artifact truth。
- 不把数据库、对象存储、Git、hash、graph、search、消息中间件、容量数字或运维流程写成当前概要设计结论。

### 7.2 本文不再回答

- 不再回答 `L1-artifact` 是否是可审计制品真相仓。
- 不再回答 Artifact fact、version、lineage、baseline 和可消费回指是否属于本仓 truth。
- 不再回答系统上下文、职责边界、依赖方向、数据所有权和关键技术机制。
- 不再回答具体数据库、对象存储、Git、hash、search、graph、消息系统、容量和运维问题。
- 不再回答相邻仓是否拥有 Artifact truth,也不再回答外部正文是否可入仓。

### 7.3 本文必须回答

- `L1-artifact` 的代码主体框架如何从架构语义结构映射到可实现骨架。
- 主要组成部分有哪些,每个部分承担什么职责、不承担什么职责、包含哪些代码主体 / 模块候选。
- 从主要组成部分中能发现哪些对象候选,哪些对象会在第 6 章正式成立。
- API / 接口骨架如何按入口、消费、派生、交接和相邻边界分类。
- 关键处理流 / 重要函数数据流如何连接 intake、version、lineage、baseline、consumption、derived 和 handoff 主线。
- 状态集合和状态流转如何表达 fact、version、lineage、baseline、可消费回指、派生维护和交接语义。
- 异常与边界场景如何覆盖外部正文不可用、上游引用缺失、自动化来源异常、血缘依据不足、基线冻结失败、派生延迟和交接失败。
- 配置影响只识别哪些主要部分受配置影响、哪些边界禁止配置化、哪些配置细节交给详细设计。
- 详细设计需要继续展开哪些对象、接口、处理流、状态机、配置契约和测试切口。

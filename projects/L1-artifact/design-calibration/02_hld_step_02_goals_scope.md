## 3. SOP 问题回答

### 3.1 本次概要设计最主要要把哪些结构讲清?

本次概要设计最主要要讲清以下结构:

- `L1-artifact` 如何从“可审计制品真相仓”的需求 / 架构结论映射到代码主体框架。
- 围绕 Artifact fact、version、lineage、baseline 四条核心 truth 主线,系统应拆成哪些主要组成部分,它们之间如何协作。
- 输入收束、责任审查、自动化产出边界、消费表达、派生维护和本地引用层如何围绕核心 truth 工作,而不是抢占 truth ownership。
- 哪些关键对象足以承接核心 truth、回指、派生、引用和维护语义。
- 同步入口、异步输入、后台维护、消费读取、交接 / 事件边界分别需要什么接口骨架。
- 事实纳管、版本形成、血缘建立、基线冻结、消费回指和派生维护几条关键处理流如何形成闭环。
- 哪些状态集合和状态流转是进入详细设计前必须先稳定下来的。

### 3.2 这一轮概要设计应停在什么深度,才算足够支撑进入详细设计?

本轮概要设计应停在“可实现结构骨架”深度,具体包括:

- 可以正式收敛代码主体框架、主要组成部分、关键对象类别、接口分类、关键处理流主线和状态集合。
- 可以点名正式对象名、接口名、处理流名和关键字段 / 参数骨架,但不展开字段全集、完整函数签名、协议 schema 或 repository / DDL 细节。
- 可以明确哪些部分会受配置影响、哪些边界禁止配置化,但不写配置项清单、JSON 示例或部署参数。
- 可以明确哪些内容必须交给 `03-详细设计.md`、`04-配置设计.md`、`05-测试方案.md`、`06-验收标准.md` 和未来 `07-实施计划.md`,而不是在 02 抢写下游文档内容。

换言之,本轮 02 的完成标准不是“把 Artifact 全部设计完”,而是“把进入详细设计前必须稳定的结构主语讲清”。

### 3.3 哪些内容属于本次概要设计范围?

当前属于本次概要设计范围的内容包括:

- 从需求五条核心能力闭环映射到概要设计主线,确认哪些结构围绕制品事实承载、制品版本化、制品血缘关联、制品基线冻结和制品事实可消费表达展开。
- 从架构的核心 / 支撑上下文映射到代码主体框架,确认 02 应如何承接制品事实核心、版本核心、血缘核心、基线核心及其外围支撑上下文。
- 围绕同步入口、异步输入消费、真相存储承载、后台维护与派生、派生消费承载和交接边界,形成接口骨架和处理流骨架的讨论范围。
- 围绕 Artifact truth、external reference、snapshot、derived material 和 forbidden body 的数据边界,形成对象轮廓和异常边界的讨论范围。
- 围绕核心强一致、外围最终一致和三类路径分离,形成后续处理流和状态机的骨架约束。
- 识别配置影响、详细设计承接项和当前风险口径,但不提前替代后续文档。

### 3.4 哪些内容虽然相关,但当前不进入概要设计范围?

以下内容虽然相关,但当前明确不进入概要设计范围:

- 重新定义需求目标、用户故事、功能需求、业务规则、验收标准。
- 重新定义系统上下文、子域划分、依赖方向、数据所有权原则和技术方案取舍。
- 完整 Rust struct / enum / value object 字段全集。
- 完整函数签名、伪代码、调用链、handler / service / repository 级细化职责。
- DTO / JSON / Event / RPC / handoff schema、DDL、索引、事务细节和存储模型。
- 数据库、对象存储、hash、tamper、graph、search、消息系统和性能数字等技术产品 / 指标选型。
- 测试用例、验收门禁、实施 boundary、commit 切分和运行证据。
- 旧文档里偏“术语解释”“新人导览”“存储心智”“历史技术说明”的长篇叙事。

### 3.5 哪些内容应留给详细设计,而不应在本章提前展开?

应明确留给详细设计或后续文档的内容包括:

- 每个 truth / reference / view / projection / report / handoff 对象的完整字段、类型和不变量。
- Command / Query / Event / Operations Job 的完整输入输出 schema、错误返回和鉴权 / 幂等 / replay 细节。
- repository、port、adapter、transaction、outbox、snapshot、projection rebuild 和 persistence 细节。
- 配置项级契约、配置文件结构、环境变量、部署参数和运维操作。
- 测试切口、验证矩阵、验收判据和实施 boundary / gate / evidence 流程。

## 4. 当前文档问题诊断

| 旧 `02-概要设计.md` 倾向 | 问题 | 本轮处理 |
|---|---|---|
| 先讲“本仓怎么理解”“几个术语容易混”“文件怎么存” | 主线回滑到解释型材料,不利于收敛概要设计真正的结构目标 | 当前 §2 改为先锁定结构目标、非范围和设计深度 |
| 把 Artifact / Version / Baseline 等概念直接写成全篇结构 | 容易跳过代码主体框架和主要组成部分层,直接贴近对象说明书 | 本轮先确认 02 需要讲清哪些结构,后续 Step 4~6 再逐层收稳 |
| 混入 storage / hash / tamper / lineage query / preview 等历史技术心智 | 容易让外围增强或技术方案反向主导概要设计主线 | 当前把它们降为非范围、边界线索或后续设计输入 |
| 把概要设计写成功能 / 接口 / 实现清单 | 会越级进入详细设计或实施层 | 当前明确 02 只收可实现结构骨架,不收 schema、DDL、测试和实施边界 |

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 |
|---|---|---|
| 本次目标表达 | 易被旧文档带成概念解释或功能愿望池 | 改为“结构目标 + 非范围 + 设计深度”三件套 |
| 范围边界 | 需求、架构、概要、详细设计和实施层容易混写 | 明确哪些内容属于 02,哪些留在上游或下游文档 |
| 主线聚焦 | fact / version / baseline 等概念容易直接变成对象叙事 | 先锁定代码主体框架、组成部分、对象 / 接口 / 流程 / 状态骨架是本轮主语 |
| 深度控制 | 容易过早进入字段、函数、schema 和技术后端 | 明确停在“可实现结构骨架”层级 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 直接按五条核心能力写成功能清单 | 容易快速展开 | 会回滑成需求文档续写,不是概要设计结构目标 | 不采用 |
| 方案 B: 直接按核心对象名定义本轮范围 | 容易显得具体 | 会跳过代码主体框架和主要组成部分层,过早进入对象说明 | 不采用 |
| 方案 C: 以“代码主体框架 + 主要组成部分 + 对象 / 接口 / 流程 / 状态骨架”定义范围 | 能稳定承接需求与架构,也能给详细设计明确输入 | 需要后续 Step 逐步展开 | 采用 |
| 方案 D: 把技术产品、存储方案、schema 和实施计划一并纳入 02 | 细节看起来完整 | 会越权覆盖 03~07 文档责任 | 不采用 |

## 7. 结构化中间产物

### 7.1 设计目标表

| 设计目标 | 说明 | 验证方式 |
|---|---|---|
| 建立 Artifact 概要设计的代码主体骨架主线 | 必须先把需求 / 架构结论转成“本仓如何被组织成可实现结构”的主线,避免停留在概念解释或架构复述 | Step 4 能稳定输出代码主体框架总览,且主语不再漂移回术语解释或功能清单 |
| 建立围绕四条核心 truth 与外围支撑上下文的主要组成部分划分 | 必须说明核心 truth、输入收束、消费表达、派生维护和引用层分别由哪些主要部分承接 | Step 5 能稳定划分主要组成部分,且每部分都能回指需求 / 架构边界 |
| 建立进入详细设计所需的关键对象轮廓 | 需要让 fact、version、lineage、baseline 及其回指 / 引用 / 派生对象在概要层先有存在理由 | Step 6 能从组成部分导出对象候选池和正式关键对象,不再临时发明主语 |
| 建立同步 / 异步 / 后台 / 消费 / 交接的接口骨架 | 概要设计必须说明主要入口和边界如何分类,否则后续详细设计无法稳定拆接口 | Step 7 能围绕入口类型和边界类型形成接口骨架表,而不是零散接口名清单 |
| 建立核心 truth 闭环和外围维护的关键处理流骨架 | 需要让事实纳管、版本形成、血缘建立、基线冻结、消费回指和派生维护的流转主线先稳定下来 | Step 8 能覆盖核心闭环主线和关键维护流,且不再回到功能列表叙事 |
| 建立核心 truth 与外围语境的状态主语 | 没有状态主语,后续对象和处理流会缺少一致的语义边界 | Step 9 能形成状态集合与流转方向,且能回指对象和处理流 |
| 建立配置影响与详细设计承接边界 | 概要设计要明确哪些部分受配置影响、哪些实现细节后置到详细设计和后续文档 | Step 11~12 能在不越界的前提下完成配置影响和详细设计承接清单 |

### 7.3 当前阶段设计深度口径

当前阶段设计深度口径如下:

- 本轮 02 必须足够支撑后续详细设计判断“该拆哪些主要部分、对象、接口、流程和状态”。
- 本轮 02 不负责把这些主语写成完整 schema、完整 Rust 类型、完整协议或完整持久化设计。
- 本轮 02 允许出现正式对象名、接口分类名、处理流名、状态名和关键字段 / 参数骨架,但它们都服务于结构轮廓,不是实现契约。
- 本轮 02 对外围增强能力只做到“边界归属与结构接入点”级别,不把 search、preview、archive handoff、observability explain、sync copy 写成核心主线。
- 本轮 02 对配置只做到“哪些部分可能受影响、哪些边界禁止配置化、哪些内容后置到 03 / 04”级别。

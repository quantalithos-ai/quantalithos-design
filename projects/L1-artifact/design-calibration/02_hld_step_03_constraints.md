## 3. SOP 问题回答

### 3.1 哪些约束会直接影响本仓对象、接口、处理流或状态机设计?

直接影响后续设计判断的约束主要有:

- Artifact fact、version、lineage、baseline 和 consumable backref 的 truth ownership 只能留在 `L1-artifact`,不能漂移到相邻仓、派生视图或外部系统。
- 外部正文、运行材料、workspace 视图、归档包、观测记录、sync 私有副本和事件材料不能被写成正式 Artifact truth。
- 核心 truth、外部引用、快照摘要、派生材料和 forbidden body 必须持续分层,否则后续对象和接口会混层。
- 核心 truth 成立必须保持强一致;派生、报告、交接和维护允许最终一致,但不得借由延迟路径隐式推进业务事实。
- 同步入口、异步输入和后台维护三类路径必须分离,否则处理流和状态机会失去清晰边界。
- search、preview、projection、report、reconciliation、archive handoff、observability explain 和 sync material 只能作为只读派生或交接材料,不能升级成核心主链。
- 概要设计只能继续收“可实现结构骨架”,不能下沉到 schema、DDL、完整函数签名、配置项和实施 boundary。

### 3.2 哪些约束来自需求文档,哪些约束来自架构设计或全局设计?

主要来源分布如下:

- 来自需求文档的约束: 单一 Artifact truth、五条核心能力闭环、相邻仓不得复制 / 重建 / 迁移 truth、跨仓消费必须可回指正式 truth、外围增强不是核心前置。
- 来自架构设计的约束: 不可变 truth ownership、外部正文与 truth 分离、派生只读、`L0-core` 之外无编译期依赖、核心强一致 + 外围最终一致、同步 / 异步 / 后台三类路径分离、配置不得改变 ownership 和边界。
- 来自概要设计自身层次要求的约束: 本轮只能收代码主体框架、组成部分、对象 / 接口 / 流程 / 状态骨架,不能越级进入详细设计和实施层。

### 3.3 哪些边界如果不先写清,后续最容易串到相邻仓或详细设计?

最容易失真的边界有:

- “消费表达”与“下游私有视图 / 副本”的边界。若不先写清,后续很容易把 SDK / console / sync / workspace 侧材料写成正式主语。
- “外部正文引用”与“Artifact truth”的边界。若不先写清,后续对象和流程容易把外部正文生命周期吸进本仓。
- “派生维护”与“核心写路径”的边界。若不先写清,后续 report / projection / archive preparation / reconciliation 会被误写成业务写源。
- “概要骨架”与“详细实现契约”的边界。若不先写清,后续对象表、接口表和流程图会迅速膨胀成完整 schema / repository / DDL 设计。

### 3.4 哪些约束只是泛化工程原则,不应进入本章?

以下内容当前不应作为本章约束写入:

- 一般性的“代码要清晰”“要高性能”“要高可用”“要便于测试”等泛化工程口号。
- 具体技术产品、数据库 / 存储 / 消息 / 搜索 / hash 方案和运维产品要求。
- 完整错误码、完整权限矩阵、完整测试策略和实施证据流程。
- 与 `L1-artifact` 结构主语无直接关系的跨仓通用开发纪律。

### 3.5 每条约束是否能指导后续章节的设计判断?

本步保留的每条约束都必须能直接指导至少一类后续判断:

- 约束主要组成部分能不能成立。
- 约束对象应被归到 truth、reference、snapshot 还是 derived。
- 约束接口属于同步入口、异步输入还是后台维护。
- 约束处理流是否允许改变核心事实。
- 约束状态机里哪些状态能出现在核心 truth,哪些只能出现在派生 / handoff 语境。

## 7. 结构化中间产物

### 7.1 约束边界说明

概要设计是在已收稳的需求与架构边界下继续向可实现结构展开,因此必须先把 truth ownership、外部正文边界、派生只读、路径分离和层次深度约束钉住。若这些约束不先写清,后续主要组成部分、对象、接口、处理流和状态机就会在相邻仓消费语境、派生语境和详细设计语境之间反复串层,最终把 `L1-artifact` 的 truth 主线写散。

### 7.2 约束条件表

| 约束 | 作用范围 | 当前要求 |
|---|---|---|
| 只承接已收稳需求与架构结论,不重写上游主线 | Step 4~13 全部章节 | `02-概要设计.md` 后续各章只承接 `00/01` 已确认的定位、闭环、边界和机制,不重新定义需求目标、架构边界、子域划分或技术取舍 |
| Artifact truth ownership 必须保持单一 | 主要组成部分、关键对象、状态机 | fact、version、lineage、baseline 和 consumable backref 只能由 `L1-artifact` 核心 truth 主线承接;相邻仓、消费视图、归档 / 观测 / 同步材料不得升级为正式主语 |
| 外部正文、运行材料和派生材料不得进入正式 truth | 关键对象、接口骨架、处理流 | 后续对象与流程必须持续区分 Artifact truth、external reference、snapshot、derived material 和 forbidden body;外部正文只能以引用、摘要或完整性线索形式出现 |
| 消费表达不得转移 truth ownership | 主要组成部分、接口骨架、异常边界 | SDK、console、workspace、sync、archive、observability、report 和 conversation 只能消费 / 展示 / 交接正式 truth,不得在 02 中被写成第二 truth center |
| 派生视图与维护路径只读,不得反写核心事实 | 主要组成部分、处理流、状态机 | search、preview、projection、report、reconciliation、archive preparation、observability explain 和 maintenance 只能从核心 truth 派生,允许 stale / rebuilding / unavailable,但不能改变业务 Artifact 结论 |
| 核心强一致 + 外围最终一致持续生效 | 关键对象、处理流、状态机 | 后续流程与状态必须默认 fact / version / lineage / baseline / backref 同步成立或拒绝;派生、报告、交接和维护允许延迟、重建和重试 |
| 同步 / 异步 / 后台三类路径必须分离 | 代码主体框架、接口骨架、处理流 | 同步路径负责即时 truth 判断,异步路径负责变化送达 / 传播,后台路径负责派生、维护、对账和交接;不得把后台或异步路径写成核心业务写入口 |
| 编译期依赖不得越过 `L0-core` | 代码主体框架、组成部分边界 | 后续概要设计不得把 `L1-work`、`L1-process`、`L1-governance`、`L4-*`、`L5-*` 或外部系统写成编译期内聚主体;它们只能以运行期边界、引用、safe summary 或交接协作出现 |
| 外围增强不是核心闭环前置 | 主要组成部分、接口骨架、详细设计承接 | search、preview、report、archive handoff、observability、SDK / console 友好输出、sync material 等只能作为外围消费能力,不能反向定义核心组成部分顺序和对象存在理由 |
| 当前概要设计只停在结构骨架层 | 关键对象、接口骨架、处理流、配置影响 | 后续章节允许点名对象名、接口分类名、处理流名、状态名和关键字段 / 参数骨架,但不得提前展开 schema、完整函数签名、repository / DDL、配置项、测试矩阵或实施 boundary |
| 配置不得改变 truth ownership 和路径边界 | 配置影响轮廓、详细设计承接 | 到 Step 11 时,只能讨论哪些部分受配置影响,不得让配置层改变核心 truth owner、外部正文边界、同步 / 异步 / 后台分工或派生不反写原则 |

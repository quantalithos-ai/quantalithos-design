## 1. 业务背景与驱动力

### 1.1 业务背景

对话是 Quantalithos 用户体验的第一入口。它不是聊天 UI 的附属,而是**六域之一的核心领域**:
- 用户通过对话表达需求
- AI 成员通过对话协作
- Gate 决策通过对话通知人
- Artifact 生命周期通过对话反馈
- Bridges 通过对话映射到 Slack / Mattermost 等外部渠道

因此 L1-conversation 的职责是把对话作为**可持久化、可推送、可审计的业务对象**来承载。

### 1.2 业务驱动力

**业务驱动力**:
- 用户需要一个自然的协作入口
- Governance 需要一个可视化 / 可确认的 Gate 载体
- Chat / Console / Bridges 都需要同一个对话真相源

**技术驱动力**:
- Turn append-only 审计要求
- AG-UI 17 事件实时推送
- 月分区存储 / 大规模历史对话承载

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | PostTurn P95 | < 100ms | benchmark |
| 性能 | StreamEvents P95 | < 500ms | benchmark |
| 规模 | Turn/月 | 1.5 亿 | 压测 |
| 审计 | Turn 原地 UPDATE 次数 | 0 | 数据库审计 |
| 联动 | gate / artifact / work 事件转 Turn 成功率 | 100% 核心事件 | 回归测试 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| Turn kind 扩展 | 中 | enum + append-only 扩展 |
| 推送协议 | 中 | StreamEvents 抽象层 |
| 检索后端 | 中 | PG 起步,后续替换 |
| 桥接平台 | 高 | 让 bridges 适配,conversation 不知外部协议 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **聚合驱动 + append-only + push layer**(当前)| 审计清晰,推送自然,桥接友好 | 查询模型复杂 |
| 简单聊天表 + UI 轮询 | 实现快 | 不可审计、实时性差 | ❌ |
| CQRS/ES 全事件溯源 | 最强审计 | 过重 | ⚠️ 暂不需要 |

**最终选择**:**Conversation 聚合 + Turn append-only + StreamEvents 推送层**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| Turn 不可变 | 审计强 | 编辑 UX 复杂 |
| StreamEvents 独立层 | UI / bridges 解耦 | 需要维护映射逻辑 |
| 四形态强约束 | 业务清晰 | 查询模型复杂 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
User / AI Member / Chat UI
        │
        ▼
   ★ quantalithos-conversation ★
   - Conversation + Turn source of truth
   - StreamEvents / AG-UI mapping
        │
   ┌────┼───────────────┬────────────┬────────────┐
   ▼    ▼               ▼            ▼            ▼
 work  governance     artifact     identity      bridges
 project events       gate events  artifact events participant sync  external channels
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ Conversation / Turn 聚合持久化
- ✅ participants 管理
- ✅ Gate / Artifact / Work 事件转 Turn
- ✅ StreamEvents(AG-UI 17 事件)实时推送
- ✅ 全文检索 / archive 边界

**不做什么**:
- ❌ Gate 决策(governance)
- ❌ Artifact 正文存储(artifact)
- ❌ 外部平台协议转换(bridges)
- ❌ UI 组件实现(chat/console)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则服务阻断 |
| bus | 99.95% | backlog 可短时积压 |
| Chat / Bridges | 99.9% | 内部 Turn 保留,下游重连 |

### 4.4 关键依赖风险

- 高并发写下 Turn 分区热点
- gate/artifact 事件映射漏转
- bridges 延迟让外部用户感知不一致

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Conversation Store | 核心域 | 对话真相源 |
| StreamEvents | 支撑子域 | 实时推送 |
| Search | 支撑子域 | 全文检索 |
| Bridge-facing projection | 支撑子域 | 给 bridges 的投影 |

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Conversation | 对话聚合 | Conversation |
| Turn Stream | Turn 持久化 / 排序 | Turn |
| Push Projection | AG-UI 映射 | StreamEvent |
| Search Index | 检索索引 | Turn summary |

### 5.3 上下文映射关系

- work → conversation: project.created / archived / member_assigned 事件驱动
- governance → conversation: gate raised / decided → gate turn
- artifact → conversation: artifact approved / published → artifact turn
- conversation → bridges: 通过桥接投影而非直接改协议

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |
|---|---|---|
| Conversation | 一段可持久化的对话空间 | Conversation |
| Turn | 对话中的单条不可变记录 | Turn Stream |
| StreamEvent | 面向 UI 的推送事件 | Push Projection |
| participant | 对话参与者 | Conversation |
| gate turn | 由 governance 事件投影出的 Turn | Turn Stream |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
User / AI / Chat UI
       │ HTTP / WS / SSE
       ▼
conversation-api
       │
       ▼
application layer
       │
       ▼
domain (Conversation / Turn)
       │
   ┌───┴────────────┬───────────────┐
   ▼                ▼               ▼
PostgreSQL      StreamEvents      subscriptions
(partitioned)   (AG-UI map)       (work/governance/artifact/identity)
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| conversation-api | gRPC/HTTP 入口 | Rust + axum/tonic |
| conversation-domain | 聚合逻辑 | Rust |
| stream-layer | AG-UI 映射 + push | Rust + WS/SSE |
| postgres | Conversation / Turn 存储 | PostgreSQL + 月分区 |
| search(可选) | 全文检索 | PG tsvector / OpenSearch |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| UI 实时更新 | SSE / WS | 流式推送优于轮询 |
| 下游事件输入 | bus 订阅 | 六域平权 |
| 内部查询 | gRPC / HTTP | 明确接口 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| `conversations` | conversation | conversation / UI 查询 |
| `turns` | conversation | conversation / search / bridges |
| `conversation_events_outbox` | conversation | outbox worker |

### 6.5 部署拓扑

- 单服务 + PG 起步
- Push 层可内嵌同进程
- Turn 表按月分区

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api / streaming
     │
     ▼
application
     │
     ▼
domain (Conversation / Turn)
     ▲
     │ interfaces
infra (pg / bus subscribers / push transport)
```

### 7.2 层间约束规则

- domain 不依赖 infra
- stream-layer 不写业务状态,只映射 Turn → AG-UI events
- subscriptions 不直接写 DB,只调 application 用例
- search index 不可反向成为写入源

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| TurnStore | domain/application | infra pg |
| PushTransport | application | infra sse/ws |
| EventSubscriber | application | infra bus subscriber |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(UI / bridges / governance / work 都依赖) |
| 传出耦合 | 中(PG / bus / push layer) |
| 不稳定性 | 中 |
| 抽象度 | 中高 |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Conversation | conversation | UI / bridges | 聚合内强一致 | 无 |
| Turn | conversation | UI / search / archive | append-only + 最终一致投影 |
| StreamEvent | conversation(push projection) | chat / console / sync | 最终一致 | 短时延迟 |
| Search index | conversation/search | UI 查询 | 最终一致 | 延迟索引 |

### 8.2 一致性层次

- 聚合内:Conversation / Turn 本地事务强一致
- 投影层:Turn → StreamEvent / search index 最终一致
- 跨域:gate / project / artifact 事件通过 bus 输入,最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| gate 事件转 Turn 失败 | retry + DLQ |
| StreamEvents 推送失败 | last_event_id 续传 |
| search index 更新失败 | 后台重建 |

## 9. 关键技术选型

### 9.1 PostgreSQL 月分区

| 维度 | 内容 |
|---|---|
| 当前选择 | PG 按月分区 |
| 备选方案 | 单表 / OpenSearch 主存 |
| 选择理由 | 1.5 亿 Turn/月需要热冷分层,但首期不引入额外后端 |
| 演进路径 | 若检索负载过高,引入 OpenSearch |
| 不可逆程度 | 中 |

### 9.2 SSE / WS 推送

| 维度 | 内容 |
|---|---|
| 当前选择 | SSE + WS 双支持 |
| 备选方案 | 轮询 |
| 选择理由 | AG-UI 17 事件天然适合流式 |
| 演进路径 | 以 SSE 为默认,WS 处理高互动场景 |
| 不可逆程度 | 低 |

### 9.3 Turn 不可变模型

| 维度 | 内容 |
|---|---|
| 当前选择 | append-only + 覆盖显示 |
| 备选方案 | 原地 UPDATE |
| 选择理由 | 审计要求 + 历史可追溯 |
| 演进路径 | UI 层可优化展示策略,底层不变 |
| 不可逆程度 | 高 |

| 维度 | 方案 A: append-only(当前)| 方案 B: mutable edit | 方案 C: event-sourcing 全量 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| OpenSearch 是否需要未定 | 搜索能力后期扩展 | P1 |
| Turn 编辑 UX 未定 | 前端体验差异 | P1 |
| bridge lifecycle 对齐未实现 | 外部平台一致性 | P2 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| 月度 Turn > 1.5 亿 | 持续 2 月 | 评估拆分 search 存储 |
| StreamEvents P95 > 500ms | 持续 1 周 | 拆 push 层 / 优化 fan-out |
| bridges 平台 > 3 种 | 1 Sprint | 增加桥接投影专层 |

### 12.3 演进步骤

```
阶段 1: Conversation + Turn 基础落地
阶段 2: StreamEvents / AG-UI 映射稳定
阶段 3: 全文检索增强
阶段 4: archive / bridge 深度集成
```

### 12.4 目标架构

把 conversation 做成:
- 对话真相源
- 实时推送中心
- 事件在 UI 上的人类可见层

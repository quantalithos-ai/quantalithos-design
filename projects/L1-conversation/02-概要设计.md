## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-conversation` 不是聊天前端,也不是项目任务系统。它是 **“协作对话真相仓”**。

你可以把它理解成:
- 用户和 AI 成员平时在哪个正式空间里说话
- 一个群聊、私聊、thread 里到底说过什么
- Gate、Artifact、Project、Process 等关键事件怎样被翻译成人能看懂的对话记录
- Chat / Console / Bridges 怎样实时看到这些变化
- 为什么历史对话能被审计、回放、检索

这些事情,都由 `L1-conversation` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L1-conversation`,系统里仍然可能有:
- `work` 的项目和任务
- `process` 的阶段和节奏
- `governance` 的 Gate 决策
- `artifact` 的产物变化
- `identity` 的成员身份

但这些事实不会自然变成人能协作消费的对话界面。最终会变成:
- 各域有各自事件,却没有统一的人类协作入口
- Chat / Console / Bridges 各自拼装一份聊天数据,最后彼此漂移
- Gate 通知、产物通知、项目协作消息混在 UI 临时状态里
- Turn 历史无法形成 append-only 审计链
- 讨论记录和系统事件记录断裂,无法回放“当时发生了什么”

所以 `L1-conversation` 必须独立存在,作为:
> **协作对话空间、Turn 历史和实时推送语义的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Conversation
就是:
> 一个正式存在、可持久化、可授权、可归档的对话空间。

它可以是:
- group
- channel
- dm
- thread

它不是某次页面临时会话状态。

#### Turn
就是:
> 对话中的一条正式记录。

它可以是:
- 用户说的话
- AI 成员说的话
- 系统提示
- Gate 通知
- Artifact 通知

最重要的一点是:
> Turn 一旦写入,原记录不能直接修改。

#### participant
就是:
> 谁被正式纳入这个对话空间,谁有资格读/发/参与这个会话。

它不是 identity 真相本体,而是 conversation 里的参与关系。

#### gate turn
就是:
> `governance` 域的 Gate 事件,被 conversation 翻译后落成的一条对话记录。

它不是 Gate decision 真相本体。

#### artifact turn
就是:
> `artifact` 域的产物事件,被 conversation 翻译后落成的一条对话记录。

它不是 Artifact 正文本体。

#### StreamEvents
就是:
> conversation 把内部对话变化实时推给 Chat / Console / Bridges 的流式输出层。

它不是对话真相本体,而是对话真相对外可消费的实时映射层。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L1-conversation/02` 时,先收稳以下前提:
- `L1-conversation` 不应按对象数拆,而应按主要部分拆
- conversation 至少应拆成“对话空间与参与者 / Turn 事实流 / 事件转对话接缝 / 实时推送与 AG-UI 映射 / 检索与只读投影”五个主要部分
- conversation 自己拥有的真相是 Conversation / Turn / participant / visibility / archive / lock / 推送映射结果
- `Project / WorkItem / Iteration / GlobalMember / ProjectMember / ProcessInstance / Gate decision / Artifact 正文` 都不是 conversation 真相
- conversation 可以消费这些域的事件、引用和投影语义,但不能把它们收编为自己的正式业务真相
- 02 的重点不是“聊天功能列表”,而是先把“conversation 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,协作首先发生在人和 AI 成员能共同看到、共同留下痕迹的对话空间里。用户真正需要的不是一个临时聊天框,而是:
- 能持续承载项目协作的 group / channel
- 能承载一对一澄清的 dm
- 能围绕某个主题继续深入的 thread
- 能把 Gate / Artifact / Project / Process 的关键事件翻译成人类可读记录的消息流
- 能在 Chat / Console / Bridges 中被统一消费的对话真相源

如果把这些逻辑分别散落到:
- 前端本地状态
- 各域各自的通知逻辑
- 临时推送通道
- 外部桥接协议适配层

系统会快速退化成:
- 对话只剩展示层,没有稳定业务真相
- 同一条系统事件在不同前台出现不同表述
- Turn 无法形成正式历史链,审计和回放断裂
- group / dm / thread 的权限和参与关系漂移
- Chat / Console / Bridges 各自缓存一份聊天事实,最后不同步

因此,本概要设计的任务就是:
> **把 `L1-conversation` 写成一个新人也能看懂的“协作对话真相仓”,而不是把聊天 UI、通知推送、业务事件展示和业务真相混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 对话真相归属 | 容易被误解为 Chat/Console 前端状态 | Conversation/Turn 成为正式真相源 | 需写死边界 |
| 事件展示 | work/governance/artifact/process 事件容易各自为政 | 关键事件统一转为 Turn | 需正式落图 |
| Turn 审计 | append-only 原则已在 00/01 明确 | 02 需让新人理解其业务意义 | 需用人话讲清 |
| 实时推送 | 已有 StreamEvents / AG-UI 方向 | 仍易与对话真相本体混淆 | 需单列主要部分 |
| 相邻仓边界 | conversation 易与 work/process/governance 混层 | 只消费事件/投影,不拥有业务真相 | 需固定交互边界 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让用户、AI 成员和系统关键事件在同一个正式协作空间里留下可审计、可回放、可推送的对话记录
- **技术问题**:Conversation / Turn / participant / 事件转 Turn / StreamEvents / 检索投影之间的边界如何稳定建模,并与 `identity/work/process/governance/artifact/runtime` 清晰协作而不混层

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ identity                   │
                    │ - member summary           │
                    │ - lifecycle projection     │
                    └────────────┬───────────────┘
                                 │ participant identity / lifecycle view
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ chat / console / bridges   │   │ conversation               │   │ work                       │
│ - UI / external channels   │◀──│ - Conversation             │──▶│ - project / board events   │
│ - live collaboration       │   │ - Turn                     │   │ - participant sync source  │
│ - realtime consume         │   │ - participants             │   └────────────────────────────┘
└────────────────────────────┘   │ - gate/artifact turns      │
                                 │ - StreamEvents             │
                                 └────────────┬───────────────┘
                                              │ gate/artifact/process/project events → turns
                                              ▼
                    ┌────────────────────────────┐
                    │ governance / artifact      │
                    │ - gate raised / decided    │
                    │ - artifact approved        │
                    └────────────┬───────────────┘
                                 │ stage / progress / execution messages
                                 ▼
                    ┌────────────────────────────┐
                    │ process / runtime          │
                    │ - timeline / progress      │
                    │ - member execution feedback│
                    └────────────────────────────┘
```

### 4.2 位置解释

- `conversation` 自己负责“正式对话空间”和“正式 Turn 历史”
- `identity` 提供参与者相关的身份摘要和生命周期投影,但不把身份真相让渡给 conversation
- `work` 提供项目、群聊归属、成员分配和项目事件语义,但 project / workitem 真相仍在 work
- `governance` 提供 Gate raised / decided 等治理事件,conversation 把它们翻译成人能消费的 gate turn
- `artifact` 提供制品生命周期事件,conversation 把它们翻译为 artifact turn
- `process / runtime` 提供阶段、进度、执行反馈等可见语义,conversation 消费这些语义并形成对话记录或只读视图
- `chat / console / bridges` 消费的是 conversation 的 Turn 真相和实时推送,而不是自行定义新的对话真相源

所以 `L1-conversation` 在全局里的角色是:
> **把多域协作事件、人类消息和 AI 消息汇总为统一正式对话记录,并把这些记录实时推向前台和桥接通道的协作中枢。**

### 4.3 系统边界

**做什么**:
- 保存正式对话空间真相
- 保存 Turn 历史真相
- 管理 participant / visibility / archive / lock
- 把关键跨域事件翻译成对话记录
- 向 Chat / Console / Bridges 提供实时推送与检索能力

**不做什么**:
- 不负责项目、任务、迭代真相
- 不负责过程实例、Token、checkpoint 真相
- 不负责身份主真相和项目成员主真相
- 不负责 Gate 决策真相
- 不负责 Artifact 正文真相
- 不把外部桥接协议适配器当成仓内主对象

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| identity | 99.9% | participant 身份摘要延迟,但对话真相继续存在; 前台暂时展示旧摘要,后续靠投影刷新纠正 |
| work | 99.9% | project/member 同步延迟,但已有对话历史不受影响; group 建立或 participant 更新可进入补偿队列 |
| governance | 99.9% | gate turn 延迟到达; 不阻断用户直接发言主线 |
| artifact | 99.9% | artifact turn 延迟到达; 历史查询仍以既有 Turn 真相为准 |
| process / runtime | 99.9% | 进度类 turn / view 延迟; 不影响 Conversation / Turn 正式写入 |
| search backend | 99.9% | 搜索能力短时降级; history query 仍可直接读取正式 Turn 历史 |
| chat / console / bridges | 99.9% | 推送失败时保留 Turn 真相,等待重连 / 补发; 可临时退回历史拉取 + 续传模式 |

### 4.5 关键依赖风险

- conversation / work 边界不稳会导致 group/project 视图被误当项目真相
- conversation / governance 边界不稳会导致 gate turn 被误当 Gate decision 本体
- conversation / artifact 边界不稳会导致 artifact 摘要替代 artifact 正文真相
- conversation / push 边界不稳会导致 StreamEvents 被误当对话真相源
- conversation / bridges 边界不稳会导致外部平台协议细节反向污染内部模型
- 外部事件重复消费会导致 gate / artifact / progress turn 重复写入,破坏人类对历史的信任
- participant 同步延迟会导致可见性判断与最新成员状态短时错位,影响“谁能看到什么”的前台体验
- push backlog 过高会导致“正式历史已写入、前台却晚到”的感知分叉,需要依赖续传与历史查询补齐

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 对话空间与参与者部分

- **它是什么**: 这是 `L1-conversation` 的空间与授权边界层,一起回答“在哪说、谁能看、谁能发”
- **为什么单独有它**: 如果把 Conversation、participant、archive/lock 混进 Turn 历史或推送层,读者会搞不清“空间边界”和“消息记录边界”谁先谁后
- **负责什么**:
  - 定义 group / channel / dm / thread 四种正式对话空间
  - 定义 participants、visibility、archive、lock 等空间级约束
  - 为后续 Turn 记录、事件映射和推送提供稳定锚点
- **不负责什么 / 容易混淆点**:
  - 不负责 identity 真相
  - 不负责 work 中的项目主真相
  - 最容易和 `identity` 的成员真相、`work` 的项目群真相混淆
- **与其他部分交互**:
  - 上游: identity / work
  - 下游: Turn 事实流部分、检索与只读投影部分
  - 交互类型: 空间锚点型 + 授权边界型
- **后续详细设计展开点**:
  - Conversation / participant 对象模型
  - visibility / archive / lock 规则

#### Turn 事实流部分

- **它是什么**: 这是 `L1-conversation` 的核心正式记录层,一起回答“说过什么、发生过什么、历史如何保留”
- **为什么单独有它**: 如果不单列,对话真相会被误降级为“只是 UI 显示的数据流”
- **负责什么**:
  - 保存 user / member / system / gate / artifact 等正式 Turn
  - 维持 append-only 历史链
  - 为回放、审计、检索和推送提供正式输入
- **不负责什么 / 容易混淆点**:
  - 不负责 Gate 决策正文
  - 不负责 Artifact 正文
  - 最容易和事件转对话接缝部分、实时推送部分混淆
- **与其他部分交互**:
  - 上游: 对话空间与参与者部分、事件转对话接缝部分
  - 下游: 实时推送与 AG-UI 映射部分、检索与只读投影部分
  - 交互类型: 正式记录写入型
- **后续详细设计展开点**:
  - Turn kind 模型
  - append-only 与覆盖显示机制

#### 事件转对话接缝部分

- **它是什么**: 这是 `conversation` 与其他业务仓之间的翻译层,一起回答“外部业务事件如何变成对话记录”
- **为什么单独有它**: 这是 conversation 最容易越界的地方; 不单列就会把外部业务真相和 conversation 自己的记录真相混成一锅
- **负责什么**:
  - 消费 work / governance / artifact / process / identity 等事件或投影语义
  - 决定哪些外部变化要进入对话
  - 把外部业务事件翻译为 Turn
- **不负责什么 / 容易混淆点**:
  - 不拥有外部业务真相
  - 不替代外部仓的事件定义
  - 最容易和 Turn 事实流部分、相邻业务域真相混淆
- **与其他部分交互**:
  - 上游: work / governance / artifact / process / identity
  - 下游: Turn 事实流部分
  - 交互类型: 事件输入型 + 语义翻译型
- **后续详细设计展开点**:
  - event → turn 映射规则
  - 多域事件落点策略

#### 实时推送与 AG-UI 映射部分

- **它是什么**: 这是 `conversation` 的实时输出层,一起回答“对话变化怎样被实时推到界面和桥接系统”
- **为什么单独有它**: 如果和 Turn 真相层混写,读者会把“记录已经写成真相”和“变化已经推送出去”误当同一件事
- **负责什么**:
  - 把 Conversation / Turn 的变化实时推送给 Chat / Console / Bridges
  - 把内部变化映射为 AG-UI 事件
  - 承担实时连接层的输出语义
- **不负责什么 / 容易混淆点**:
  - 不成为正式对话真相源
  - 不决定业务事件是否存在
  - 最容易和 Turn 事实流部分、bridges 协议适配层混淆
- **与其他部分交互**:
  - 上游: Turn 事实流部分
  - 下游: chat / console / bridges
  - 交互类型: 实时映射输出型
- **后续详细设计展开点**:
  - StreamEvents 模型
  - SSE / WS / AG-UI 映射策略

#### 检索与只读投影部分

- **它是什么**: 这是 `conversation` 的高频读侧和二级消费层,一起回答“历史怎么查、摘要怎么给、桥接如何只读消费”
- **为什么单独有它**: 如果不单列,高频查询和桥接视图会被迫直接啃写模型,读写边界会变模糊
- **负责什么**:
  - 提供 search / summary / history query
  - 提供只读桥接消费视图
  - 为回看、审计和跨端展示提供读模型
- **不负责什么 / 容易混淆点**:
  - 不反向成为写源
  - 不拥有 Turn 主真相
  - 最容易和 Turn 事实流部分、bridges 协议层混淆
- **与其他部分交互**:
  - 上游: 对话空间与参与者部分、Turn 事实流部分
  - 下游: chat / console / bridges / archive / observability
  - 交互类型: 只读查询型 + 投影输出型
- **后续详细设计展开点**:
  - search / summary / history 读模型
  - projection consistency 规则

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 对话真相层 + 事件翻译接缝层 + 实时推送层 + 检索投影层分层

**选择理由**:
- 把“正式对话记录”和“实时推送结果”分开
- 把“外部业务事件”和“conversation 自己的 Turn 真相”分开
- 把“高频查询视图”和“写模型”分开
- 为 `03-详细设计.md` 提供稳定的按主要部分展开骨架

### 7.2 模块划分与职责

```text
┌──────────────────────────────────────────────┐
│                  L1-conversation             │
│                                              │
│  ┌──────────────────────────────┐            │
│  │ 对话真相层                    │            │
│  │ - Conversation               │            │
│  │ - Turn                       │            │
│  │ - participants               │            │
│  └──────────────┬───────────────┘            │
│                 ▼                            │
│  ┌──────────────────────────────┐            │
│  │ 事件翻译接缝层                │            │
│  │ - event → turn mapping       │            │
│  │ - locator / refs             │            │
│  └──────────────┬───────────────┘            │
│                 ▼                            │
│  ┌──────────────────────────────┐            │
│  │ 实时推送层                    │            │
│  │ - StreamEvents               │            │
│  │ - SSE / WS / AG-UI mapping   │            │
│  └──────────────┬───────────────┘            │
│                 ▼                            │
│  ┌──────────────────────────────┐            │
│  │ 读模型与检索层                │            │
│  │ - summary / history / search │            │
│  │ - bridge-facing view         │            │
│  └──────────────────────────────┘            │
└──────────────────────────────────────────────┘
```

| 模块 | 职责(一句话) | 依赖 |
|---|---|---|
| 对话真相层 | 定义正式会话、正式 Turn 与 participant 关系 | identity / work |
| 事件翻译接缝层 | 把跨域事件翻译为 Turn 或只读视图更新 | work / governance / artifact / process / identity |
| 实时推送层 | 把已确认的对话变化实时推向前台和桥接层 | 对话真相层 |
| 读模型与检索层 | 提供高频查询、历史回看、bridge-facing 只读视图 | 对话真相层 / 推送层 |

**层次解释**:
- 对话真相层拥有正式业务事实
- 事件翻译接缝层只翻译语义,不拥有外部业务真相
- 实时推送层只负责“如何送出去”,不负责“消息是否存在”
- 读模型与检索层只负责“如何高效读到”,不负责“真相如何写入”

### 7.3 模块依赖关系

```text
identity / work ─────▶ Conversation / participants
Conversation ────────▶ Turn history
work / governance / artifact / process / identity ─▶ event → turn mapping
Turn history ────────▶ StreamEvents / AG-UI mapping
Conversation / Turn ─▶ search / summary / history query
Stream / query ──────▶ chat / console / bridges
```

### 7.4 层间约束规则(防退化)

- Conversation / Turn 是正式对话真相,StreamEvents 不是
- event → turn mapping 只翻译外部语义,不接管外部业务真相
- search / summary / bridge-facing projection 只读,不反向成为写源
- group / project / gate / artifact / process 相关消息只作为 Turn 或投影存在,不替代原仓对象
- bridges / 前端组件协议不能反向决定 conversation 核心模型

|---|---|
| 当前选择 | Conversation / Turn 真相层 + StreamEvents 推送层 |
| 备选方案 | 由前端或桥接层自行拼接实时聊天状态 |
| 选择理由 | 保证正式历史、实时输出和多端消费有统一真相源 |
| 演进路径 | 后续可扩展推送协议,但不破坏对话真相归属 |

### 8.2 为什么 Turn 必须 append-only

| 维度 | 内容 |
|---|---|
| 当前选择 | Turn 写入后不原地改写,修改通过新增 Turn 覆盖显示 |
| 备选方案 | 原地 UPDATE 对话记录 |
| 选择理由 | 保住审计链、回放链和 Documented Information 语义 |
| 演进路径 | 后续优化展示层编辑体验,底层历史链不变 |

### 8.3 为什么事件先翻译成 Turn 再推送

| 维度 | 内容 |
|---|---|
| 当前选择 | 外部事件先进入 conversation,落成 Turn 或只读视图,再统一推送 |
| 备选方案 | 每个外部仓直接推给前端 |
| 选择理由 | 避免前台消费多套语义,保证事件的人类可见记录有统一落点 |
| 演进路径 | 后续增加更多事件类型时,继续沿 event→turn 接缝扩展 |

### 8.4 为什么 StreamEvents 不直接等于对话真相

| 维度 | 内容 |
|---|---|
| 当前选择 | StreamEvents 只作为实时映射层存在 |
| 备选方案 | 直接把实时推送事件当作聊天状态真相 |
| 选择理由 | 推送可能失败、重连、补发,而正式真相必须稳定、可回放、可审计 |
| 演进路径 | 后续可演进推送协议与续传机制,但 Turn 真相层不受影响 |

### 8.5 为什么搜索先依赖 PG / 可后续外置

| 维度 | 内容 |
|---|---|
| 当前选择 | 首期以 PG 读模型 / 检索起步 |
| 备选方案 | 一开始就引入独立搜索集群 |
| 选择理由 | 先保住对话真相与查询链闭环,避免首期把 conversation 拆成过多基础设施依赖 |
| 演进路径 | 检索压力显著上升后,再把 search backend 外置,但对 Turn 真相与 search document 接口保持稳定 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: conversation 作为对话真相源(当前) | 方案 B: 前端/桥接层拼装聊天数据 |
|---|---|---|
| 历史审计性 | 高 | 低 |
| 多端一致性 | 高 | 低 |
| 事件展示统一性 | 高 | 中低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的对话不是单纯 UI 体验,而是人、AI 成员和多域关键事件共同留下正式协作痕迹的地方。如果 conversation 不是正式真相源,后续 Chat / Console / Bridges、Gate 通知、Artifact 通知和项目协作消息都会分裂成多套不一致的数据来源。

## 11. 横切关注点

### 11.1 安全
- participant / visibility 必须受正式授权边界约束
- 对外桥接和前台消费只能读允许范围内的 Conversation / Turn
- gate / artifact / process 相关消息只能展示被允许暴露的摘要语义

### 11.2 性能
- PostTurn P95 < 100ms
- StreamEvents P95 < 500ms
- 历史查询和高频推送不能彼此拖垮

### 11.3 可用性
- 推送失败不影响 Turn 真相落库
- 外部域事件延迟时允许消息延迟到达,但不允许篡改已落地 Turn 历史

### 11.4 可观测性
- event → turn → stream 全链必须可追踪
- append-only 历史链和覆盖显示链必须可审计

### 11.5 成本
- 不把外部业务真相并入 conversation,避免模型膨胀
- 不把外部桥接协议细节拖入核心模型,避免后续多平台演化成本失控

### 11.6 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| PostTurn 写路径 | ≤ 100ms | 100ms |
| Stream push | ≤ 500ms | 500ms |
| 历史查询 | ≤ 300ms | 300ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在单项目样板中验证 dm / group / Turn 主线,只收最基本的人/AI 直接发言链
- **阶段 2**: 再验证 work / governance / artifact 三类事件转 Turn 主线,确保“系统事件进入对话”成立
- **阶段 3**: 再引入 process / runtime 消息与实时 StreamEvents,观察 push lag 与重连续传行为
- **阶段 4**: 最后接入 bridges 与 search / archive,验证多端消费和历史检索演化路径

### 13.2 回滚策略
- 若 Turn append-only 或事件转 Turn 逻辑不稳,先回退到“保留基础对话真相、不扩展复杂事件映射”的保守路径
- 若推送层不稳,先保留 Turn 真相和历史查询,临时降级实时推送能力
- 若 search backend 或 bridge-facing projection 不稳,先关闭对应读侧增强能力,保留 Conversation / Turn 主链
- 若 event target conversation 定位规则出现误落点,立即暂停相关事件族映射并回放修正

### 13.3 监控指标
- PostTurn 成功率与 P95
- StreamEvents 延迟与断连恢复情况
- gate / artifact / process 事件转 Turn 成功率
- 历史查询延迟与月分区增长情况

## 15. 结论

本概要设计的核心结论是:
- `L1-conversation` 是协作对话真相层,不是前端 UI 仓
- `L1-conversation` 内部应按“对话空间与参与者部分 / Turn 事实流部分 / 事件转对话接缝部分 / 实时推送与 AG-UI 映射部分 / 检索与只读投影部分”来理解,而不是按对象平铺理解
- `identity` 管身份真相,`work` 管项目与任务真相,`process` 管节奏语义,`governance` 管决策真相,`artifact` 管产物真相,而 `conversation` 负责把这些可见语义编织进正式协作对话记录
- Turn 是正式记录,StreamEvents 是实时映射,两者不能混成一个层
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把对象模型、event→turn 规则、推送策略、检索与只读投影规则正式化

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 Conversation / Turn / participant 真相
- 把外部业务事件翻译为对话记录并实时推送
- 提供检索、历史查询、桥接消费视图与只读摘要

**本模块不做什么**:
- 不持有 `GlobalMember` / `ProjectMember` / `Project` / `WorkItem` / `Iteration` / `ProcessInstance` / `Gate decision` / `Artifact` 正文真相
- 不直接承担 chat / console 组件实现
- 不承担 bridges 的外部协议适配正文

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再解释“conversation 是什么”,而是让开发者能够直接开始实现:
- Conversation / Turn / participant 的真相模型
- event → turn 的翻译入口
- StreamEvents 的实时推送路径
- search / summary / history query 的读模型路径

如果不先把这些内容采集清楚,03 很容易退化成:
- 再讲一次 UI 感知层概念
- 按对象表平铺,丢掉主要部分主轴
- 把 work / governance / artifact / process 的真相混进 conversation 内部模型

### 2.2 内容采集流程(先采集,再落文)

#### 第 0 步:确认 `02-概要设计` 已经稳定

先确认:
- `L1-conversation` 是协作对话真相仓,不是前端 UI 仓
- 五个主要部分已经稳定
- 与 `identity/work/governance/artifact/process/runtime` 的真相边界已经清楚
- `02` 中的总交互图与分模块交互图已经能回答“谁给谁什么语义”

#### 第 1 步:列出要实现的核心对象

本仓 03 先按四层对象理解:
- 真相对象: Conversation / Turn / ParticipantMembership / ArchiveState / VisibilityPolicy / LockState
- 接缝对象: DomainEventEnvelope / EventTurnMapping / ConversationLocator / ConversationRef
- 推送对象: StreamEvent / StreamCursor / DeliveryCheckpoint
- 读模型对象: ConversationSummary / TurnHistoryPage / BridgeFacingMessageView / SearchDocument

#### 第 2 步:列出主流程与关键异常流

主流程至少有两条:
- 人/AI 直接发言 → Turn 追加 → projection 更新 → Stream 推送
- 外部事件输入 → event→turn mapping → Turn 追加 → projection 更新 → Stream 推送

关键异常流至少包括:
- 无权限 participant 写入
- event 找不到落点 Conversation
- 事件重复导致幂等冲突
- 推送失败但 Turn 已写入
- projection 延迟 / 损坏后重建

#### 第 3 步:列出要落库/持久化的对象与关系

必须先分清:
- 哪些是写模型: conversations / participants / turns
- 哪些是读模型: summaries / history page cache / bridge-facing views / search docs
- 哪些是 append-only: turns / event-derived turn history / stream delivery watermark(若保留历史)
- 哪些 ref 只能作为引用,不能反向变成正式写源

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些上游事件会进入 event→turn mapping
- 哪些只刷新只读视图,哪些真正生成 Turn
- Chat / Console / Bridges 的实时消费如何与 Turn 真相解耦
- last_event_id / cursor 如何只服务推送续传,不反向定义 Turn 真相

#### 第 5 步:列出最小测试输入

必须测:
- Turn append-only
- event→turn 幂等
- participant 权限边界
- Stream 失败不丢真相
- projection 可重建
- gate / artifact / project 事件稳定落到正确 conversation

### 4.1 总流程图

```text

             ▼
[对话空间与参与者部分]
```

### 4.2 总解释

- **真相写入**发生在: Conversation 建立、participant 变更、Turn 追加
- **接缝翻译**发生在: 外部业务事件被翻译为 system / gate / artifact / progress 类 Turn
- **投影刷新**发生在: summary / history / bridge-facing view / search doc 更新
- **实时输出**发生在: Turn 或可见状态变化被映射为 StreamEvent 推送
- **同步路径**主要是: CreateConversation / PostTurn / AppendSystemTurnFromEvent 主写链
- **异步最终一致**主要是: projection 刷新、search 更新、bridge-facing view 与重放恢复

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `Conversation / Turn / StreamEvent` 三个对象开始平铺。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与事件
- 最后再进入横向的对象模型、流程、存储、投影、异常与测试细节

这样可以避免:
- `02` 讲的是空间/消息/接缝/推送/投影,`03` 却只剩字段表
- 实现者知道有 Turn,却不知道它归哪个责任单元控制
- event→turn、stream、projection 这三段链路脱节

#### 5.2.3 涉及的对象定义

```rust
/// 表示一个正式存在、可持久化、可授权、可归档的对话空间。
pub struct Conversation {
    /// 对话空间的唯一标识。
    pub conversation_id: ConversationId,
    /// 对话空间的形态,决定 participant 和可见性约束。
    pub kind: ConversationKind,
    /// 对话空间当前的生命周期状态。
    pub state: ConversationState,
    /// 当前对话空间的参与者集合。
    pub participants: Vec<ParticipantMembership>,
    /// 当前对话空间的可见性规则。
    pub visibility: VisibilityPolicy,
    /// 对话空间当前是否被锁定。
    pub lock_state: LockState,
    /// 对话空间是否已归档。
    pub archive_state: ArchiveState,
    /// 对应项目、Gate、Artifact 或 thread 的关联引用。
    pub related_refs: ConversationRelatedRefs,
}

/// 表示对话空间的类型,决定空间边界和参与规则。
pub enum ConversationKind {
    /// 项目组或团队协作群聊。
    Group,
    /// 广播或主题频道。
    Channel,
    /// 两方私聊。
    Dm,
    /// 依附于父会话的主题分支。
    Thread,
}

/// 表示会话当前的生命周期状态。
pub enum ConversationState {
    /// 可正常读写的活动状态。
    Active,
    /// 已归档,默认只读。
    Archived,
    /// 已锁定,只允许特定系统动作。
    Locked,
}

/// 表示一个参与者在某对话空间中的正式参与关系。
pub struct ParticipantMembership {
    /// 参与者自己的稳定引用,而不是身份真相本体。
    pub participant_ref: ParticipantRef,
    /// 参与者在该会话中的角色语义。
    pub role_in_conversation: ConversationRole,
    /// 当前是否允许读取该会话。
    pub can_read: bool,
    /// 当前是否允许发言。
    pub can_post: bool,
}

/// 表示会话级可见性策略,负责定义谁能看到什么范围的内容。
pub struct VisibilityPolicy {
    /// 是否仅参与者可见。
    pub participant_scoped: bool,
    /// thread 是否继承父会话可见性。
    pub inherit_from_parent: bool,
    /// 对桥接层允许暴露的最小信息范围。
    pub bridge_visibility: BridgeVisibilityScope,
}

/// 表示会话归档状态的附加信息。
pub struct ArchiveState {
    /// 当前是否已归档。
    pub archived: bool,
    /// 归档发生时间。
    pub archived_at: Option<Timestamp>,
    /// 归档操作者引用。
    pub archived_by: Option<ActorRef>,
}

/// 表示会话锁定状态的附加信息。
pub struct LockState {
    /// 当前是否已锁定。
    pub locked: bool,
    /// 锁定原因。
    pub reason: Option<LockReason>,
    /// 锁定发生时间。
    pub locked_at: Option<Timestamp>,
}
```

这些对象在该部分里分别承担:
- `Conversation` 是空间聚合根,回答“在哪协作”
- `ParticipantMembership` 是会话内参与关系,回答“谁能读/发”
- `VisibilityPolicy` 负责把读范围、thread 继承和 bridge 可见性固定为静态边界
- `ArchiveState` / `LockState` 把“会话是否还能正常写入”写成正式状态而不是临时标记
- `ConversationKind` / `ConversationState` 一起维护空间边界,但都不替代外部身份或项目真相

#### 5.2.4 关键函数代码片段

> 该部分除了 `add_participant` 外,还必须至少补出 Create / Archive / Lock 三类典型动作,否则开发者看不到空间生命周期如何落地。

```rust
/// 在会话内增加一个正式参与者,同时校验该空间形态是否允许这样做。
fn add_participant(conversation: &mut Conversation, membership: ParticipantMembership) {
    // [conversation.校验可新增参与者]
    // 先根据会话类型和锁定/归档状态校验这次参与者变更是否合法。
    conversation.validate_participant_mutation(&membership);

    // [conversation.追加参与关系]
    // 只有通过空间级约束后,才把新的参与关系写入会话真相。
    conversation.participants.push(membership);

    // [VisibilityPolicy::重算]
    // 静态策略重算当前会话可见性边界,确保 query / stream 层读到的是新规则。
    conversation.visibility = VisibilityPolicy::rebuild(&conversation.kind, &conversation.participants);
}

/// 创建一个新的 Conversation,并在创建时冻结最小可用的空间边界。
fn create_conversation(conversation_repo: &dyn ConversationRepo, draft: CreateConversationDraft) {
    // [Conversation::从草稿创建]
    // 先把输入草稿收束成正式 Conversation 聚合根。
    let conversation = Conversation::from_draft(draft);

    // [conversation.校验初始状态]
    // 创建时立即校验 dm/group/thread 的初始 participant 和 related refs 是否成立。
    conversation.validate_initial_state();

    // [conversation_repo.保存会话]
    // 把正式会话真相写入主表,为后续 Turn 和 projection 提供锚点。
    conversation_repo.save(conversation);
}

/// 归档一个 Conversation,让其进入默认只读状态。
fn archive_conversation(conversation_repo: &dyn ConversationRepo, conversation: &mut Conversation, actor: ActorRef) {
    // [conversation.归档]
    // 先把会话生命周期迁移到 archived,同时记录归档操作者和时间。
    conversation.archive(actor);

    // [conversation_repo.更新会话状态]
    // 只更新会话状态本体,不触碰历史 Turn。
    conversation_repo.update_state(conversation);
}
```

这些代码片段一起说明:
- 创建、参与者调整、归档都属于空间聚合根职责
- 空间层写的是 Conversation 真相,不是 query / push 的派生结果
- 历史 Turn 不因会话状态变化而被重写,只改变后续写入可行性

#### 5.2.5 该部分的边界与非职责
- 不负责 `GlobalMember` 真相同步
- 不负责 `ProjectMember` 的项目承担真相
- 不负责 Turn 历史写入
- 不直接负责外部事件翻译

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `Turn 事实流部分` 提供“这次 post 是否允许”的空间上下文
- 向 `检索与只读投影部分` 提供 participant 和 visibility 边界
- 从 `identity/work` 消费稳定 ref 与分配语义,但不反向持有其真相对象

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `Dm` 默认只允许双边参与
- `Archived` / `Locked` 会影响可写性
- participant membership 不能替代外部身份真相
- thread 的可见性继承最容易出错,必须留到细化实现时单列校验

```rust
pub struct Turn {

    pub turn_id: TurnId,
    /// 该 Turn 所属的 Conversation。

    /// Turn 的记录类别,决定其来源和展示语义。

    /// 该 Turn 的正式作者或系统来源引用。
    pub author_ref: TurnAuthorRef,

    pub payload: TurnPayload,
    /// 与项目、Gate、Artifact、父 Turn 等相关的引用集合。

    pub idempotency_key: Option<IdempotencyKey>,
```

> 该部分除了 `append_turn` 外,还必须至少补出 supersede 与历史查询边界,否则 append-only 设计仍然不够可实施。

```rust
/// 在通过空间校验后,向会话历史中追加一条正式 Turn。
fn append_turn(turn_repo: &dyn TurnRepo, conversation: &Conversation, turn: Turn) {
    // [conversation.校验允许发言]
    // 先确保该会话当前允许这个作者在当前状态下发出这条 Turn。
    conversation.ensure_post_allowed(&turn.author_ref, &turn.kind);

    // [turn.校验引用边界]
    // 再确保这条 Turn 携带的相关引用不会越界伪装成外部真相对象。
    turn.validate_related_refs();

    // [turn_repo.追加记录]
    // 这里必须走 append-only 写入,不能覆盖已有历史记录。
    turn_repo.append(turn);
}

/// 通过新增 supersede Turn 表达“编辑后覆盖显示”,而不是原地改写旧 Turn。
fn supersede_turn(turn_repo: &dyn TurnRepo, previous_turn: &Turn, replacement: Turn) {
    // [replacement.绑定 supersede 引用]
    // 先把新的 Turn 显式关联到被覆盖的旧 Turn,形成展示层覆盖链。
    let replacement = replacement.with_supersede(previous_turn.turn_id);

    // [turn_repo.追加记录]
    // 再把新的替代 Turn 追加到历史链,旧 Turn 保持不变。
    turn_repo.append(replacement);
}
```

这些代码片段一起说明:
- append-only 是 repo 硬语义,不是展示层习惯
- supersede 是“新增一条替代记录”,不是“修改旧记录”
- 后续 history / summary / stream 都必须从这条正式历史链派生

#### 5.3.5 该部分的边界与非职责
- 不负责 participant 同步真相
- 不负责外部事件语义解释
- 不负责流式推送协议细节
- 不负责搜索索引与聚合查询逻辑

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `对话空间与参与者部分` 拿可写上下文
- 从 `事件转对话接缝部分` 接收已经翻译好的 system/gate/artifact/progress turn draft
- 向 `实时推送与 AG-UI 映射部分` 发出新 Turn 写入结果
- 向 `检索与只读投影部分` 提供稳定历史输入

#### 5.3.7 该部分的状态 / 约束 / 易错点
- Turn 一旦写入不可原地修改
- event-derived turn 不得伪装成 `User` / `Member`
- supersede 只是展示层覆盖,不是历史层回写
- progress / gate / artifact 的 kind 分层不能被偷懒合并成 `System`

```rust
/// 把外部领域事件翻译成 conversation 可接受的 Turn 写入动作。
fn append_system_turn_from_event(
    locator: &dyn ConversationLocator,
    policy: &dyn EventTurnMappingPolicy,
    turn_repo: &dyn TurnRepo,
    event: DomainEventEnvelope,
) {
    // [locator.定位对话落点]
    // 先根据 project/gate/artifact/thread 等引用找到本次事件应该进入的 Conversation。
    let conversation_ref = locator.locate(&event.related_refs);

    // [policy::决定事件映射]
    // 再由静态策略根据事件类型决定是否生成 Turn、生成什么 kind、正文如何组织。
    let mapping = policy.decide(&event, &conversation_ref);

    // 最后按事件幂等键写入 append-only 历史,避免重复事件造成重复 Turn。
    turn_repo.append_event_derived(mapping, &event.idempotency_key);
}
```

```rust
/// 把已落库的 Turn 变化映射为可实时推送的 StreamEvent。
fn emit_stream_event(
    mapper: &dyn StreamEventMapper,
    push_transport: &dyn PushTransport,
    turn: &Turn,
    cursor: &StreamCursor,
) {
    // [mapper::映射流事件]
    // 先把 Turn 或可见性变化翻译为前台可增量消费的流事件。
    let event = mapper.map_turn(turn, cursor);

    // [push_transport.推送]
    // 再通过 SSE / WS 等传输层把流事件送给在线消费方。
    push_transport.push(event);

/// 在消费方断线重连后,按 last_event_id 补发缺失的流事件。
fn resume_stream_from_last_event_id(
    stream_repo: &dyn StreamCursorRepo,
    push_transport: &dyn PushTransport,
    consumer_ref: &StreamConsumerRef,
    last_event_id: Option<StreamEventId>,
) {
    // [stream_repo.查找缺失事件]
    // 先根据 last_event_id 取出该消费方尚未收到的流事件片段。
    let missed_events = stream_repo.list_after(consumer_ref, last_event_id);

    // [push_transport.批量补发]
    // 再按顺序补发,保证消费方恢复到连续流位置。
    push_transport.push_batch(missed_events);
}
```

```rust
/// 根据最新 Turn 与会话状态刷新对话摘要与只读投影。
fn refresh_projection(
    projection_repo: &dyn ProjectionRepo,
    conversation: &Conversation,
    turn: &Turn,
) {
    // [projection_repo.更新摘要]
    // 先刷新会话列表页最需要的 summary 视图。
    projection_repo.refresh_summary(conversation, turn);

    // [projection_repo.更新历史页物料]
    // 再把这条 Turn 加入 history query 所需的只读页数据或索引材料。
    projection_repo.refresh_history_material(conversation, turn);

    // [projection_repo.更新桥接视图]
    // 最后生成给桥接层消费的只读视图,但不回写任何会话真相。
    projection_repo.refresh_bridge_view(conversation, turn);

/// 从正式 Turn 历史重新构建 conversation 的全部只读投影。
fn rebuild_conversation_projection(
    turn_repo: &dyn TurnRepo,
    projection_repo: &dyn ProjectionRepo,
    conversation: &Conversation,
) {
    // [turn_repo.读取全量历史]
    // 先把该会话的正式历史按时间顺序完整读出。
    let turns = turn_repo.list_all(conversation.conversation_id);

    // [projection_repo.清空旧投影]
    // 再删除旧的 summary / history material / bridge view / search doc。
    projection_repo.reset(conversation.conversation_id);

    // [projection_repo.按真相重放]
    // 最后只根据正式 Conversation / Turn 真相重新生成所有只读视图。
    projection_repo.replay(conversation, turns);
}
```

这些代码片段一起说明:
- projection 是派生层,可以重建
- refresh 与 rebuild 是两条不同责任链
- rebuild 的唯一输入源必须是 Conversation / Turn 真相

#### 5.6.5 该部分的边界与非职责
- 不负责正式 Turn 写入
- 不负责事件语义翻译
- 不负责 Stream push 实时协议
- 不负责 participant 主授权判定逻辑

#### 5.6.6 该部分与其他主要部分的接缝
- 从 `Conversation / Turn` 真相层消费稳定输入
- 向 chat / console / bridges / search 提供只读视图
- 与 `实时推送与 AG-UI 映射部分` 并行服务读侧,但不共享写源职责

#### 5.6.7 该部分的状态 / 约束 / 易错点
- projection 延迟是可接受的,但不可反写真相
- history / summary / bridge view 的字段裁剪规则可能不同,不能复用成一份模糊对象
- rebuild 时必须以 Turn 真相为唯一来源

### 7.4 关键函数/命令级伪代码

#### `CreateConversation`

```text
function CreateConversation(input):

    2. 校验 dm / thread / group 的空间边界规则
    3. 构造 Conversation 聚合根
    4. 持久化 Conversation 与 ParticipantMembership
    5. 初始化 summary / history / stream cursor 基础物料
    6. 返回 Conversation
```

#### `PostTurn`

```text
function PostTurn(input):
    1. 读取 Conversation
    2. 校验 participant 是否有权读/发
    3. 构造 Turn
    4. 校验 Turn kind 与 related refs 边界
    5. append-only 持久化 Turn
    6. 刷新 summary / history / bridge-facing projection
    7. 生成 StreamEvent
    8. 推送给在线消费方
    9. 返回 Turn / cursor
```

#### `AppendSystemTurnFromEvent`

```text
function AppendSystemTurnFromEvent(event):
    1. 校验 event envelope 与 idempotency key
    2. 根据 refs 定位目标 Conversation
    3. 按 event mapping policy 决定是否生成 Turn
    4. 若生成 Turn,构造 event-derived Turn
    5. append-only 按幂等键持久化
    6. 刷新相关 projection
    7. 生成并推送 StreamEvent
    8. 返回 mapping 结果
```

#### `ArchiveConversation`

```text
function ArchiveConversation(input):
    1. 读取 Conversation
    2. 校验 actor 是否有权归档
    3. 校验当前 state 是否允许 archived
    4. 更新 archive_state / state
    5. 持久化 Conversation 状态
    6. 刷新 summary / visibility 相关投影
    7. 生成 archived 相关 StreamEvent
    8. 返回新状态
```

#### `ResumeStreamFromLastEventId`

```text
function ResumeStreamFromLastEventId(input):
    1. 校验 consumer 是否可读该 Conversation
    2. 读取 last_event_id 之后的缺失 StreamEvents
    3. 按 cursor 顺序补发
    4. 更新 delivery checkpoint
    5. 切回实时推送模式
```

```text
function RebuildConversationProjection(conversation_id):
    1. 读取 Conversation 真相
    2. 全量读取 Turn 历史
    3. 清空旧 summary / history material / bridge view / search doc
    4. 按时间顺序重放 Turn
    5. 重建所有只读投影
```

### 7.6 关键状态机 / 非法转换与约束

#### 状态机图

```text
Conversation:
active → locked → active
active → archived
archived → [只读,默认不回 active]

ParticipantMembership:
invited/attached → active
active → paused_readonly
active → removed

Turn visibility chain:
created → visible
created → superseded_visible
superseded_visible → hidden_from_default_view
```

#### 非法转换与约束表

| 场景 | 是否允许 | 说明 |
|---|---|---|
| archived 会话继续直接 PostTurn | ❌ | 归档后默认只读 |
| locked 会话被普通 participant 发言 | ❌ | 锁定期只允许受限系统动作 |
| 原地 UPDATE Turn | ❌ | 必须新增 supersede Turn |
| event-derived turn 伪装成 user turn | ❌ | 必须显式 kind 区分 |
| summary 反向改写 Conversation.state | ❌ | 读模型不能写真相 |
| removed participant 继续读取历史 | ❌(默认) | 具体例外由 visibility policy 决定 |
| 无 parent conversation 的 thread 单独创建 | ❌ | thread 必须依附父会话 |
| dm 超过双边 participant | ❌ | dm 形态必须守住双边边界 |

#### 关键约束说明

- `Conversation.state=archived` 后,默认只允许 query / audit / replay,不允许普通写入
- `Conversation.state=locked` 后,允许少量受控系统动作,但禁止普通 participant 继续 post
- participant membership 的 `paused_readonly` 表示“仍可见历史,但不可继续发言”,不能偷懒复用 remove
- supersede 后旧 Turn 仍属于正式历史,只是默认视图优先展示新 Turn

## 11. 运行期主线场景

### 11.1 场景 A · 用户在项目 group 发言

```text
用户进入 Project group
      │
      ▼
Conversation 校验 participant 可发言
      │
      ▼
追加 user Turn
      │
      ├─ 刷新 summary / history
      └─ 生成 StreamEvent
               │
               ▼
Chat / Console 看到实时更新
```

**开发者关注点**:
- participant 授权必须先于 Turn 写入
- Stream 失败不能影响 Turn 真相落库
- summary 刷新与 history 刷新都不能回写真相

### 11.2 场景 B · Gate 事件进入 conversation

```text
governance 发出 gate.raised
      │
      ▼
conversation subscriber 接收事件
      │
      ▼
定位目标 Conversation
      │
      ▼
生成 gate Turn
      │
      ├─ append-only 写入
      ├─ 刷新 history / summary
      └─ 推送 gate StreamEvent
```

**开发者关注点**:
- gate turn 不是 Gate decision 真相本体
- 幂等键必须拦截重复事件
- 找不到 Conversation 落点时不能误写到别的 group

### 11.3 场景 C · Artifact approved 进入 conversation

```text
artifact 发出 approved 事件
      │
      ▼
conversation subscriber 接收事件
      │
      ▼
根据 artifact refs 定位目标 Conversation
      │
      ▼
生成 artifact Turn
      │
      ├─ append-only 写入
      ├─ 刷新 summary / history / bridge view / search doc
      └─ 推送 artifact StreamEvent
```

**开发者关注点**:
- artifact turn 只持有 ref 与摘要,不持有 artifact 正文真相
- 若同一 approved 事件重复到达,必须由幂等键拦截
- bridge-facing view 与 search doc 的刷新失败不能回滚正式 Turn

### 11.4 场景 D · 重连后续传实时流

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| chat / console reconnect | StreamConversationEvents(last_event_id) | 实时推送与 AG-UI 映射部分 | 续传缺失流事件 |

| participant_memberships | `conversation_id + participant_ref` |
| turns | `conversation_id + created_at`, `idempotency_key`, `kind` |
| conversation_summaries | `conversation_id`, `last_activity_at` |
| bridge_views | `conversation_id`, `source_turn_ref` |
| search_documents | `source_turn_ref`, `indexed_refs`, `searchable_text` |

**索引理由**:
- `conversation_id + created_at` 支撑 history query 与 rebuild replay 的时间顺序读取
- `idempotency_key` 支撑 event-derived turn 的幂等保护
- `kind` 便于 gate/artifact/progress 等系统消息分类查询
- `last_activity_at` 支撑 conversation list 页按最近活跃排序
- `source_turn_ref` 保证 bridge/search 视图能稳定回到正式 Turn 真相

### 12.3 持久化建议

| 对象 | 存储方式 | 理由 |
|---|---|---|
| Conversation | 主表 | 会话真相 |
| Turn | append-only 表 / 分区表 | 历史链不可变 |
| Summary/Search/View | 可重建读模型 | 高读压下与写路径解耦 |
| DeliveryCheckpoint | 小表或轻量 kv | 续传状态与真相写路径分离 |

**存储边界说明**:
- `Conversation` / `ParticipantMembership` / `Turn` 属于正式写模型,必须先写成功才算主链完成
- `ConversationSummary` / `TurnHistory material` / `BridgeFacingMessageView` / `SearchDocument` 都是派生读模型,允许异步重建
- `DeliveryCheckpoint` 只服务流式续传,不能作为 Turn 顺序或真相完整性的证明
- append-only 约束应由 repo 写路径 + DB 约束双重保证,不能只靠应用层约定

### 12.4 关键校验

- Turn append-only 写入必须由 repo 层强约束
- event-derived turn 的 `idempotency_key` 必须可重放校验
- participant 可读/可发边界必须先于 PostTurn 主流程

## 13. 读模型与投影设计

### 13.1 总体结构

```text
Conversation / Turn write model
   │
   ▼
projection builders
   ├─ summary
   ├─ history material
   ├─ bridge-facing view
   └─ search document
```

### 13.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| ConversationSummary | Conversation + latest Turn | 列表页摘要 |
| TurnHistoryPage | Turn history + visibility rules | 分页历史 |
| BridgeFacingMessageView | Turn + visibility trimmed payload | 桥接只读消息 |
| SearchDocument | Turn payload + refs | 搜索文档 |

### 13.3 一致性说明

- 读模型允许最终一致
- `ConversationSummary` 主要服务列表页,允许比 Turn 真相短暂落后
- `TurnHistoryPage` 默认应直接依赖正式历史或其最薄的历史物料,不能依赖容易漂移的二次摘要
- `BridgeFacingMessageView` 只做字段裁剪与桥接消费准备,不生成新业务真相
- `SearchDocument` 允许异步更新,但 rebuild 时必须从正式 Turn 历史重放
- 被 supersede 的旧 Turn 仍保留历史,但展示层默认指向最新版本
- projection 绝不能反向成为正式写源
- rebuild 顺序必须是: reset projection → replay Conversation/Turn truth → regenerate summary/history/bridge/search

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| PostTurn 越权 | 直接拒绝 |
| event 找不到 conversation 落点 | 重试 / 死信 |
| push 失败 | 重试推送,不回滚真相 |
| projection 损坏 | 以 Turn 真相重建 |

### 14.1 重试 / 降级 / 熔断 / 补偿
- push 失败允许只保留 Turn 真相,推送异步补发
- projection 失败允许暂时返回陈旧读模型,后台重建
- `CONVERSATION_EVENT_TARGET_NOT_FOUND` 先重试定位,超过阈值后进入 dead-letter,由人工或离线规则补落点
- event-derived turn 幂等冲突默认跳过重复写入,但必须记录 compare 日志用于审计
- stream backlog 过高时,优先保证 Turn 写入与 history query,推送层可短时降级为补发模式
- search / bridge view 更新失败不阻断主写链,但必须进入 rebuild 队列

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 对话空间与参与者部分 | participant 边界错判 | 授权日志 | 拒绝写入 / 修正 membership | refetch membership |
| Turn 事实流部分 | append-only 被破坏 | DB 审计 | 阻断发布 | 修复写路径 |
| 事件转对话接缝部分 | 重复事件 / 错误落点 | 幂等日志 / trace | 跳过重复 / 死信 | replay event |
| 实时推送与 AG-UI 映射部分 | push 丢失 | push lag 指标 | 重试 / 续传 | last_event_id replay |
| 检索与只读投影部分 | summary/search 漂移 | 对账任务 | rebuild projection | full rebuild |

## 15. 实现红线 / 开发禁止事项

- 不允许原地 UPDATE Turn 替代 append-only
- 不允许把 `Project / WorkItem / Gate decision / Artifact 正文 / ProcessInstance` 嵌入为 conversation 真相对象
- 不允许把 StreamEvent 当作正式对话真相源
- 不允许让 projection / search / bridge view 反向改写 Conversation / Turn
- 不允许让外部桥接协议结构倒灌进核心领域对象

## 18. 结论

本详细设计的核心结论是：
- `L1-conversation` 的实现必须围绕五个主要部分展开,而不是按对象平铺
- Conversation / Turn 是正式真相,StreamEvent / summary / search / bridge view 都是派生层
- work / governance / artifact / process / identity 的输入都必须先经过 event→turn 接缝翻译,再进入 conversation 可见层
- 后续测试与验收文档,应直接围绕 append-only、幂等、权限边界、推送补偿和投影可重建展开

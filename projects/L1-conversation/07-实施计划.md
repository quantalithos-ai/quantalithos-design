| commit-08-b | 所有 P0 / P0-supporting EV、gate results、acceptance handoff 和 veto checklist 齐全后 | final reports、evidence index、acceptance handoff、risk / open issues | 新业务代码、生产 adapter、未审查通过结论 | full release gate、`EV-CONV-GATE-001`、`EV-CONV-ACCEPT-001` |

### 6.3 开工前设计闭环复核

每个 commit boundary 开工前，必须复核字段 / DTO、状态 / 事务、证据 / phase boundary。任一项无法闭合时，暂停当前 boundary，记录 blocker，回到 design repo 修正文档后再继续。

| 复核项 | 要求 |
|---|---|
| 字段 / DTO | DTO 输入能构造目标 domain / service 对象，不临时补字段 |
| 状态 | enum / state transition 使用正式名称，不使用口语别名 |
| 事务 / 幂等 | UnitOfWork、rollback、duplicate、conflict 和 rerun 口径与 `03/05/06` 一致 |
| phase boundary | 不依赖后续 phase 的对象、port、证据或状态 |
| 证据 | 当前 boundary 的 TC、EV、artifact 和 report 可生成 |
| redaction | forbidden body、raw secret、raw payload 不进入 truth / event / log / report |

## 10. 回退、暂停与变更控制

> 校准来源:
> - `design-calibration/07_implementation_plan_step_10_rollback_change_control.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“暂停规则表”“回退规则表”“变更控制表”“恢复条件表”“证据保留规则”和“与提交边界的关系”小节，了解实现 agent 遇到设计缺口、门禁失败、依赖不可用或验收冲突时应如何停手、回写和恢复。

| 触发条件 | 动作 | 恢复条件 |
|---|---|---|
| design commit 未固定 | 暂停实现交接 | design repo 提交完成并给实现 agent 完整 hash |
| `core-contracts` 不可读、不可编译或类型不匹配 | 暂停当前 boundary | core 修复或设计移除该类型；重跑 `cargo check` |
| 字段 / DTO / 状态 / flow / AC 无法 1:1 落码 | 暂停当前 boundary，回写 design repo | `03/05/06` 和 calibration 收敛并提交新 baseline |
| phase boundary 越界 | 暂停当前 boundary，回写实施计划或详细设计 | 设计明确前移对象或调整 boundary，并提交 |
| 目录、crate、package、binary 命名偏离规范 | 暂停当前 boundary | 修正后重跑命名检查和 `cargo check` |
| P0 TC、release redline、VETO、redaction 或 EV 缺失 | 暂停进入下一阶段 | 修复并重跑直接 TC / 同组 TC / 相关 suite |
| fake / controlled seam 被写成 production success | 暂停 PH-05~PH-08 或 acceptance | 修正 marker 和报告，必要时回写验收风险 |
| artifact / report path 出现 `<project>` 层级或 `latest` | 暂停当前 script / report boundary | 修正路径并重跑 |

回退只能针对当前未验证 boundary 或当前 boundary 的错误实现。不得回退或改写已验证阶段来掩盖当前问题。变更后必须重新执行受影响 boundary 的开工前复核。

## 11. 提交、评审与交付纪律

> 校准来源:
> - `design-calibration/07_implementation_plan_step_11_commit_review_delivery.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“提交纪律表”“提交 message 结构”“Type / Scope 裁剪”“提交前检查清单”“评审纪律表”和“交付纪律表”小节，了解实现 agent 在 `/home/aris/Projects/quantalithos-conversation` 中如何提交、评审和交付证据。

### 11.1 提交纪律

| 项 | 要求 |
|---|---|
| git user.name | `quantalithos-labs` |
| git user.email | `quantalithos.ai@gmail.com` |
| 提交粒度 | 一笔提交对应一个 Step 6 `commit-xx-*` boundary |
| 实现仓语言 | commit message 全英文；源码标识符、rustdoc、普通注释和测试名默认英文 |
| 标题格式 | `type(scope): subject`，scope 不得省略 |
| footer | 固定 `Co-Authored-By: Codex <noreply@openai.com>`，footer 前真实空行 |
| 格式控制 | 需要精确控制时使用 `git commit -F` 或 `git commit --amend -F` |

当前 design 文档仓是例外: `type` 使用英文，subject / body 可以中文，footer 固定同上。该例外不得迁移到 `quantalithos-conversation` 实现仓。

实现仓可用 scope:

```text
scaffold / config / space / scope / fact / query / manifestation / consumer
trace / handoff / outbox / jobs / reports / release
```

### 11.2 实现仓 commit 模板

```text
feat(space): add space and visibility domain contracts

Add the initial space and visibility domain boundary for commit-02-a:

Domain contracts:
- space.rs (+96): add conversation space state, identity, and lifecycle guards.
- visibility.rs (+74): add sealed visibility policy and negative cases.

Protocol fixtures:
- commands.rs (+58): add create space and participant scope command DTOs.
- space_fixtures.rs (+42): add valid and hidden scope fixtures for contract tests.

Co-Authored-By: Codex <noreply@openai.com>
```

body 文件条目只写文件名，不写完整路径；带大致改动量；bullet 之间不插空行；body 中不得出现字面量 `\n`。

### 11.3 交付纪律

| 交付物 | 交付规则 | 禁止事项 |
|---|---|---|
| commit hash | 每个 boundary 提供实现仓 commit hash | 引用浮动工作树 |
| design baseline | 交接时提供 design repo 完整 commit hash | 只说“最新设计” |
| gate artifact | 使用 `artifacts/test/<run_id>/<suite>` | 使用 `latest` 或 `<project>` 层级 |
| run report | 使用 `reports/runs/<run_id>` | 粘贴完整 stdout / stderr 代替 report |
| acceptance handoff | PH-08 生成并审查 `reports/acceptance/handoff.md` | 未审查脚本初稿直接送验 |
| veto checklist | PH-08 生成并审查 `reports/acceptance/veto-checklist.md` | VETO 未覆盖或被风险接受 |

## 12. 实施完成判定

> 校准来源:
> - `design-calibration/07_implementation_plan_step_12_completion_criteria.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“实施完成判定表”“设计与实现闭环判定表”“交付证据判定表”“未完成项处理表”“最终交付清单”和“最终结论规则”小节，了解本项目何时可以宣称实现完成、何时必须阻断、何时只能有条件通过。

| 判定项 | 标准 | 证据 | 结论 |
|---|---|---|---|
| 需求覆盖 | `FR-CONV-001~008`、P0-supporting、`BR/NFR` 均有实现或明确非范围 / 风险接受记录 | trace matrix、EV、acceptance handoff | 通过 / 不通过 |
| 交付物完成 | Step 4 交付物全部有实现落点、测试落点或明确不适用说明 | commit list、workspace tree、delivery checklist | 通过 / 不通过 |
| 阶段测试门禁 | PH-02~PH-08 的 direct TC、同组 TC、suite 和 release redline 均通过 | `artifacts/test/<run_id>`、`gate-results.md` | 通过 / 不通过 |
| 验收门禁 | AC-FUNC、AC-RED、AC-SYNC、AC-STATE、AC-TX、AC-IDEM、AC-NFR、AC-EVID 可判定且通过 | EV pages、handoff、veto checklist | 通过 / 不通过 |
| VETO | `VETO-CONV-001~014` 全部有结论且未命中 | `reports/acceptance/veto-checklist.md` | 通过 / 不通过 |
| Redaction | artifact、report、logs、audit、event 和 evidence 中无 forbidden body / raw secret / raw payload | `redaction-check.md` | 通过 / 不通过 |
| 风险闭环 | P0 blocker 全部关闭；S2/S3、P1/P2 风险有 owner、影响、截止点和复验计划 | `risk-acceptance.md`、`open-issues.md` | 通过 / 不适用 / 不通过 |
| 设计闭环 | 无未关闭字段、DTO、状态、命名、phase boundary 或正式文档 / calibration 冲突 | design baseline hash、review checklist | 通过 / 不通过 |

最终结论只允许:

| 结论 | 允许条件 |
|---|---|
| 通过 | 所有 P0 功能、测试、验收、redaction、EV、VETO、设计闭环和交付审查通过 |
| 有条件通过 | P0 全部通过，仅存在 S2/S3、P1/P2 非范围风险，且 risk acceptance 已审查 |
| 不通过 | 任一 P0 blocker、VETO、S0/S1、redaction failure、设计冲突或证据缺失未关闭 |
| 不适用 | 明确非范围或无需生成的证据项 |

禁止使用模糊完成结论。未完成项必须进入 blocker、延期项、风险接受或不适用说明。

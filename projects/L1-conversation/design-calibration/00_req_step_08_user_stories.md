## 3. SOP 问题回答

### 3.1 哪些角色目标在支撑本仓的核心能力闭环？

支撑核心闭环的角色目标集中在五类:

1. 终端管理者 / 项目负责人需要围绕项目、主题或团队协作建立清晰的对话空间与参与范围。
2. 项目参与者和 AI member 需要让协作过程中的发言、回应和系统可见事实沉淀为同一条对话历史。
3. 下游应用开发者、AI member、项目参与者和审计者需要按授权视野稳定消费同一份对话事实。
4. 系统事件 actor 需要把治理、产物、项目等关键跨域事实以引用方式显化到对话中。
5. 审计者 / 合规查看者和项目负责人需要基于对话历史追溯决策上下文与协作过程。

这些故事共同支撑 Conversation 的真相仓成立。

### 3.2 哪些角色目标只是外围增强？

外围增强故事包括:更高效地检索长历史、更低延迟地接收更新、更细粒度地支持富媒体 / 卡片展示、更方便地做运维重建、更完整地对接外部平台同步。这些目标提升体验、运维或生态集成,但不决定 Conversation 的基础对话真相是否成立。

### 3.3 哪些看起来像故事,但其实不应进入本仓？

以下目标不进入本仓用户故事表:设计 Chat 页面交互、组织 Workspace 个人首页、适配 Mattermost / Slack 协议、执行 LLM 推理、裁决 Gate / Policy、保存 Artifact 正文、创建成员身份、执行登录认证或权限裁决。这些属于相邻仓或横切能力。

### 3.4 每条故事分别支撑闭环中的哪个能力节点？

核心故事必须映射到 Step 7 的五个闭环节点之一或多个节点。外围故事只映射到外围增强能力,不得伪装成核心闭环。边界外故事只作为错误示例说明,不进入正式故事表。

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 故事来源 | 从旧核心用例和功能直接改写 | 从角色目标和核心能力闭环推导 | 避免功能名伪装成故事 |
| 故事粒度 | 写具体动作、事件、延迟和验收条件 | 写目标、价值和闭环映射 | Step 8 不写功能 / 接口 / 验收 |
| Chat / Bridges | 作为故事主体或结果混入 | 只通过下游应用开发者或使用方边界表达消费 | 它们不是 Conversation 角色或事实所有者 |
| 核心 / 外围 | 未区分 | 明确分为核心闭环故事与外围增强故事 | 为 Step 9 功能需求做结构锚点 |
| 边界外故事 | 未显式排除 | 单独列为不进入本仓的故事类型 | 防止相邻仓职责回流 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 继承旧用户故事,只删除接口细节 | 快,保留旧材料多 | 旧故事仍围绕功能和接口,不围绕核心闭环 | 不采用 |
| 方案 B: 按角色目标重写故事,并逐条映射到 Step 7 闭环 | 结构清晰,能支撑 Step 9 功能归并 | 需要后续步骤继续展开功能和验收 | 采用 |
| 方案 C: 只写核心故事,删除所有外围增强故事 | 闭环更干净 | 重要增强目标会失去追溯入口 | 不采用 |
| 方案 D: 把 Chat / Workspace / Bridges / Runtime 都写成故事主体 | 看起来覆盖下游 | 会重新把仓际使用方误写成角色 | 不采用 |

## 7. 结构化中间产物

### 7.1 用户故事表

| 用户故事 | 目标类型 | 业务价值 | 与核心能力闭环的关系 |
|---|---|---|---|
| US-CONV-001: 作为终端管理者 / 项目负责人,我希望围绕项目、主题或团队协作形成明确的对话空间和参与范围,以便相关人员和 AI member 在同一上下文中协作。 | 核心闭环 | 让协作不是散落消息,而是有明确归属和可见边界的对话事实。 | 支撑“对话空间与参与范围能够被独立确立” |
| US-CONV-002: 作为项目参与者,我希望自己的协作发言和回应能够沉淀到相关对话历史中,以便团队后续能理解讨论脉络。 | 核心闭环 | 让人类协作过程成为可持续引用的事实记录。 | 支撑“多来源协作事实能够以追加方式沉淀” |
| US-CONV-003: 作为 AI member,我希望在授权范围内读取对话上下文并把回应沉淀回同一对话历史,以便人类和 AI 围绕同一事实协作。 | 核心闭环 | 让 AI member 参与对话但不拥有身份或推理真相。 | 支撑“多来源协作事实能够以追加方式沉淀”和“对话事实能够按授权视野被稳定消费” |
| US-CONV-004: 作为下游应用开发者,我希望通过正式能力边界稳定消费对话事实,以便 Chat、Workspace、Bridge 或 Console 集成围绕同一份对话真相工作。 | 核心闭环 | 避免下游各自复制消息语义,保证跨端消费一致。 | 支撑“对话事实能够按授权视野被稳定消费” |
| US-CONV-005: 作为系统事件 actor,我希望把治理、产物、项目等关键跨域事实以引用方式显化到相关对话中,以便用户能在协作上下文里看见重要变化。 | 核心闭环 | 让系统事实进入对话视野,但不接管相邻仓原始真相。 | 支撑“关键跨域事实能够以引用方式显化到对话” |
| US-CONV-006: 作为终端管理者 / 项目负责人,我希望能够回看项目或团队相关对话历史,以便理解关键决策、协作过程和后续责任边界。 | 核心闭环 | 支撑用户管理 AI 团队时的复盘和信任建立。 | 支撑“对话历史能够被追溯并持续支撑协作复盘” |
| US-CONV-007: 作为审计者 / 合规查看者,我希望在授权范围内查看对话历史和关键上下文,以便追溯协作事实和决策背景。 | 核心闭环 | 让对话历史具备审计和合规追溯价值。 | 支撑“对话历史能够被追溯并持续支撑协作复盘” |
| US-CONV-008: 作为运维 / 后台任务,我希望在不改变业务事实的前提下维护对话索引、投影或重建结果,以便对话事实可以被稳定消费和追溯。 | 外围增强 | 提升消费稳定性和维护能力,但不创造对话业务事实。 | 支撑外围增强: 运营维护、索引 / 投影重建 |
| US-CONV-009: 作为项目参与者,我希望能够更快定位较长对话历史中的相关内容,以便减少重复询问和上下文丢失。 | 外围增强 | 提升长历史使用效率。 | 支撑外围增强: 全文检索 / 历史定位 |
| US-CONV-010: 作为下游应用开发者,我希望对话事实变化可以以适合客户端的方式及时被感知,以便减少全量刷新并改善协作体验。 | 外围增强 | 提升实时体验和客户端效率。 | 支撑外围增强: 实时流 / 客户端消费优化 |

### 7.2 核心闭环故事结论

| 闭环节点 | 支撑故事 |
|---|---|
| 对话空间与参与范围能够被独立确立 | US-CONV-001 |
| 多来源协作事实能够以追加方式沉淀 | US-CONV-002, US-CONV-003 |
| 对话事实能够按授权视野被稳定消费 | US-CONV-003, US-CONV-004 |
| 关键跨域事实能够以引用方式显化到对话 | US-CONV-005 |
| 对话历史能够被追溯并持续支撑协作复盘 | US-CONV-006, US-CONV-007 |

### 7.3 外围增强故事结论

| 外围增强方向 | 支撑故事 | 处理口径 |
|---|---|---|
| 索引 / 投影 / 重建维护 | US-CONV-008 | 后续可进入功能需求或非功能需求,但不作为核心闭环节点 |
| 长历史检索与定位 | US-CONV-009 | 后续判断功能范围和性能要求 |
| 及时感知对话变化 | US-CONV-010 | 后续进入接口与非功能讨论,不在本步写协议形态 |

## 3. SOP 问题回答

### 3.1 这个仓必须满足哪些性能要求？

核心对话事实追加、授权消费和历史追溯不能成为 Chat、Workspace、Runtime 等主协作路径的长期瓶颈。外围增强能力,例如长历史定位、辅助结果维护和及时感知,不得反向阻塞核心对话真相形成与读取。

当前需求阶段不强行给出吞吐和延迟数字,因为缺少正式负载模型。可判断口径应是:后续架构、测试和验收必须证明核心闭环能力不会被外围增强或相邻仓正文解析拖住。

### 3.2 这个仓必须满足哪些可用性要求？

核心对话真相已经形成后,外围增强能力或下游消费方失效不应导致已形成的对话事实不可用或被改写。相邻仓短暂不可用时,Conversation 不得补造相邻仓正文,也不得丢失自身已拥有的对话真相。

### 3.3 这个仓必须满足哪些安全要求？

Conversation 必须严格遵守授权视野和数据归属边界。它不得越权保存 Chat UI、Workspace、外部平台协议、Runtime 推理、Governance、Artifact、Identity、认证凭据、全局观测日志或长期归档正文。

### 3.4 这个仓必须满足哪些审计 / 可追溯要求？

对话空间、参与范围、可见范围、对话事实追加、跨域引用显化和维护性辅助动作都必须可追溯。追溯口径应能支持协作复盘、责任边界判断和相邻仓引用核验。

### 3.5 这个仓必须满足哪些幂等 / 一致性要求？

同一对话事实、同一跨域显化和同一消费辅助结果不得在需求层形成多种互相冲突的正式语义。重复输入或重复消费不能制造彼此冲突的对话真相,辅助结果也不能替代原始对话事实。

### 3.6 这个仓必须满足哪些可观测性要求？

平台必须能够稳定判断 Conversation 的关键能力是否成立,包括对话空间建立、事实追加、授权消费、跨域显化、历史追溯、外围维护和异常边界。这里要求的是可观察的业务状态和异常结果,不是具体监控平台或字段设计。

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 非功能表达 | 指标、协议、存储和推送方案混写 | 按性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性六类表达 | 对齐需求规范 §4.13 |
| 性能口径 | 容易提前写吞吐、延迟或基础设施方案 | 当前只要求核心闭环不成为主链瓶颈,量化目标后续由设计和测试承接 | 需求阶段缺正式负载模型 |
| 可用性口径 | 侧重实时通道或外部平台可用 | 侧重核心对话真相在外围能力降级时仍成立 | Conversation 真相不能依赖外围体验 |
| 安全口径 | 分散在权限、可见性和数据章节 | 统一为授权视野 + 不越权保存正文 | 对齐 Step 10 / Step 11 |
| 可追溯口径 | 审计、archive、日志容易混写 | 要求关键变化可追溯,不指定具体日志字段或归档实现 | 避免进入实现层 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 沿用旧非功能章节,保留容量和实时指标 | 看起来更具体 | 缺少当前负载依据,且容易提前进入技术方案 | 不采用 |
| 方案 B: 按六类非功能底线重写,以判断口径替代无依据指标 | 符合 SOP,能支撑验收标准和后续测试方案 | 后续设计仍需补充具体测试指标 | 采用 |
| 方案 C: 只写安全和审计,忽略性能 / 可用性 | 边界更保守 | 无法说明核心协作路径是否可用 | 不采用 |
| 方案 D: 把所有非功能要求都量化 | 便于测试 | 当前阶段缺少负载模型,容易制造虚假精确性 | 不采用 |

## 7. 结构化中间产物

### 7.1 非功能类别适用性检查

| 非功能类别 | 适用性 | 说明 |
|---|---|---|
| 性能 | 适用 | Conversation 位于 Chat、Workspace、Runtime 等协作路径上,核心事实追加和授权消费不能成为主链瓶颈。 |
| 可用性 | 适用 | 核心对话真相必须在外围增强或下游消费方降级时保持成立。 |
| 安全 | 适用 | 本仓直接处理授权视野和跨域引用,必须防止越权消费和越权持有正文。 |
| 审计 / 可追溯 | 适用 | 对话历史承担协作复盘和责任边界追溯,关键变化必须可追溯。 |
| 幂等 / 一致性 | 适用 | 多来源事实、事件输入和下游消费会造成重复或歧义风险,必须保持单一正式语义。 |
| 可观测性 | 适用 | 平台需要判断对话事实形成、消费、显化、追溯和异常边界是否稳定发生。 |

### 7.2 非功能需求表

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|
| 性能 | NFR-CONV-001: 对话事实追加和授权消费不应成为平台核心协作路径的长期瓶颈。 | 后续设计和测试必须证明核心追加、读取和追溯不会因历史规模增长或相邻仓正文不可解析而无法成立。 |
| 性能 | NFR-CONV-002: 外围增强能力不得反向阻塞核心对话真相形成。 | 长历史定位、辅助结果维护或及时感知不可用时,核心空间建立、事实追加和授权消费仍能判断成立。 |
| 可用性 | NFR-CONV-003: 已形成的对话真相不得因下游消费方不可用而丢失或被改写。 | Chat、Workspace、Runtime、Bridges、Observability 或 Archive 降级时,Conversation 已拥有的对话事实仍保持正式语义。 |
| 可用性 | NFR-CONV-004: 相邻真相域不可用时,Conversation 不得补造相邻仓正文。 | Identity、Work、Governance 或 Artifact 暂不可解析时,本仓只能保留自身真相、快照或引用状态,不能生成来源仓正文。 |
| 安全 | NFR-CONV-005: 对话事实消费必须受授权视野约束。 | 任何消费方只能获得其可见范围内的对话事实、快照或引用信息。 |
| 安全 | NFR-CONV-006: 本仓不得越权保存相邻仓正文或敏感凭据。 | Step 11 禁止保存正文清单中的对象不得进入 Conversation 数据归属。 |
| 审计 / 可追溯 | NFR-CONV-007: 对话空间、参与范围、可见范围和事实追加的关键变化必须可追溯。 | 后续验收应能判断关键变化的责任主体、发生时点、来源依据和影响范围是否可复盘。 |
| 审计 / 可追溯 | NFR-CONV-008: 跨域事实显化和维护性辅助动作必须可追溯。 | 后续验收应能判断显化引用来自哪个正式来源,维护动作依据哪些既有对话事实。 |
| 幂等 / 一致性 | NFR-CONV-009: 重复输入或重复消费不得形成互相冲突的对话真相。 | 同一业务意图被重复提交或重复感知时,结果不得产生多个互相矛盾的正式事实。 |
| 幂等 / 一致性 | NFR-CONV-010: 辅助结果和下游消费结果不得替代原始对话事实。 | 索引、投影、检索定位、变化感知和归档引用只能服务消费,不能成为新的业务事实来源。 |
| 可观测性 | NFR-CONV-011: 平台必须能稳定观察 Conversation 核心能力是否成立。 | 至少能判断空间建立、事实追加、授权消费、跨域显化和历史追溯是否成功或异常。 |
| 可观测性 | NFR-CONV-012: 平台必须能稳定观察依赖降级和边界违规风险。 | 至少能判断相邻依赖不可用、越权消费、正文越界保存、重复事实冲突等风险是否发生。 |

### 7.3 非功能类别结论

| 非功能类别 | 本步结论 |
|---|---|
| 性能 | 当前不设无依据吞吐 / 延迟指标,但要求核心追加、授权消费和追溯不成为主协作路径瓶颈。 |
| 可用性 | 核心对话真相必须独立于外围增强和下游消费方降级而保持成立。 |
| 安全 | 授权视野和数据归属是安全底线,本仓不得越权消费或保存相邻仓正文。 |
| 审计 / 可追溯 | 关键变化、跨域显化和维护性辅助动作必须支持复盘和责任边界追溯。 |
| 幂等 / 一致性 | 多来源事实和重复输入不得造成正式语义冲突,辅助结果不能替代业务事实。 |
| 可观测性 | 核心能力状态、依赖降级和边界违规风险必须能被平台稳定观察。 |

### 7.4 本章结论

`L1-conversation` 的非功能底线不是“高性能、高可用、高安全”这类口号,而是保护对话真相闭环在现实协作路径中可用、可控、可追溯。当前阶段不制造缺少依据的具体数字指标;后续测试方案和验收标准应把这些判断口径转化为可执行的验证条件。

## 10. 进入下一步条件

- 已按性能、可用性、安全、审计 / 可追溯、幂等 / 一致性、可观测性六类逐项检查适用性。
- 每项非功能要求都有判断口径或目标值。
- 要求没有退化为空洞口号,也没有滑入实现方案。
- 已明确当前不强行设置缺少依据的吞吐 / 延迟数字。

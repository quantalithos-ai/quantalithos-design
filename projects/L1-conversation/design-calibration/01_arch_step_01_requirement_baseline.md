## 3. SOP 问题回答

### 3.1 当前架构设计依赖哪些需求结论？

架构设计依赖以下需求结论:

- `L1-conversation` 是平台对话真相仓。
- Conversation 必须独立拥有对话空间、参与范围、可见范围、对话事实历史、对话内跨域显化记录和对话追溯上下文。
- Chat、Workspace、Bridges、Runtime、Governance、Artifact、Identity、Observability、Archive 均不能拥有 Conversation 真相。
- 核心能力闭环为“对话空间与参与范围确立 -> 协作事实追加沉淀 -> 授权视野消费 -> 跨域事实引用显化 -> 历史追溯与复盘”。
- 外围增强能力包括索引 / 投影维护、长历史定位、对话变化及时感知,不能反向改变 Conversation 真相。

### 3.2 哪些需求结论已经稳定？

已稳定结论包括:

- 仓定位稳定:`L1-conversation` 是对话真相仓。
- 数据归属稳定:Conversation 拥有对话域真相,相邻仓正文禁止保存。
- 使用方 / 依赖稳定:`L0-core`、`L0-bus`、`L0-sdk`、`L1-identity` 是稳定上游或接入前提;`L5-chat`、`L1-workspace`、`L6-bridges`、`L2-runtime`、`L4-observability`、`L4-archive` 等为使用方或协作方。
- 规则边界稳定:不得由 Conversation 执行 UI 展示状态、Workspace 聚合、外部平台协议、LLM 推理、治理裁决、产物正文、成员生命周期等职责。
- 验收底线稳定:核心能力闭环缺失、授权视野失效、跨域事实接管来源仓真相、相邻仓正文进入 Conversation 均为一票否决。

### 3.3 哪些需求结论仍然待确认？

当前仍待确认但不阻塞架构主线的需求事项:

| 待确认事项 | 对架构影响 | 当前处理口径 |
|---|---|---|
| 外围增强能力中哪些进入当前交付阶段 | 影响容器 / 子域是否拆出索引、变化感知和辅助维护边界 | 架构先把外围增强作为可选能力边界,不作为核心真相路径 |
| 正式协议、事件、DTO、API 名称和字段 | 影响后续概要 / 详细设计接口契约 | 架构只收敛能力级接口和通信方向,不在本步定字段 |
| 核心追加、授权消费、追溯等能力的量化目标 | 影响技术选型、容量和测试方案 | 架构保留可扩展与可观测约束,不写具体吞吐 / 延迟数字 |
| 快照数据的新鲜度和失效显示口径 | 影响数据一致性策略和降级表现 | 架构将其归入快照 / 引用一致性策略,不改真相归属 |
| 与 `L4-archive` 的长期归档交接边界 | 影响演进路线和数据生命周期 | 架构先确认 Archive 是下游归档协作方,具体交接后续细化 |

### 3.4 哪些需求会直接影响架构边界？

- “平台对话真相仓”决定本仓必须有独立 domain / application 边界,不能被 Chat、Workspace 或 Runtime 吸收。
- “相邻仓正文禁止保存”决定本仓架构必须区分快照、引用和真相数据。
- “跨域事实引用显化”决定本仓需要承接来自 Work / Governance / Artifact 等正式事实的输入边界,但不得拥有来源事实。
- “授权视野消费”决定查询和变化感知不能绕过可见范围边界。

### 3.5 哪些需求会直接影响数据所有权？

- 对话空间、参与范围、可见范围、对话事实历史、对话内跨域显化记录和追溯上下文属于 Conversation 真相数据。
- 成员展示摘要、项目 / 工作上下文摘要、跨域事实显示摘要属于快照数据。
- 成员引用、项目引用、治理引用、产物引用属于引用数据。
- Chat UI、Workspace、Bridges、Runtime、Governance、Artifact、Identity、Observability、Archive 正文禁止进入 Conversation 数据所有权。

### 3.6 哪些需求会直接影响依赖方向或一致性策略？

- `L0-core` 是编译期共享契约来源。
- `L0-bus` 是事件协作主干,但不能替代本仓业务真相。
- `L1-identity`、`L1-work`、`L1-governance`、`L1-artifact` 是定义来源或正式事实来源,Conversation 只保存引用 / 快照 / 显化记录。
- `L0-sdk`、`L5-chat`、`L1-workspace`、`L2-runtime`、`L6-bridges`、`L4-observability`、`L4-archive` 是消费方或协作方,不得反向定义 Conversation 真相。
- 快照、索引、投影、检索、变化感知必须从 Conversation 真相派生,不得成为新业务事实来源。

## 4. 当前文档问题诊断

| 旧架构内容 | 问题 | 本轮处理 |
|---|---|---|
| 开头将项目定位写成“Conversation 四形态 + Turn 五 kind + AG-UI 17 事件映射” | 把详细设计对象、协议映射和功能线索放在架构第一层 | 改为先以对话真相仓、系统边界、职责边界、数据所有权为架构主线 |
| 业务驱动力直接使用 PostTurn P95、StreamEvents P95、1.5 亿 Turn/月 | 量化指标尚未由新版需求基线确认 | 后移到技术选型、风险或后续测试方案,本步只保留“核心路径不应长期瓶颈” |
| 系统上下文图让 governance / artifact / work 事件转 Turn 成为中心 | 容易让 Conversation 接管来源仓真相 | 改为跨域事实引用显化,来源事实仍归来源仓 |
| 旧文档缺少明确需求基线与中间产物追溯 | 后续架构结论难以回到需求来源 | 本轮每个正式架构章节必须引用具体 `design-calibration` 中间产物 |

## 5. 结构化中间产物

### 5.1 架构需求基线清单

| 基线编号 | 需求结论 | 影响的架构问题 |
|---|---|---|
| ARB-CONV-001 | `L1-conversation` 是平台对话真相仓 | 系统边界、职责边界、容器划分 |
| ARB-CONV-002 | 核心能力闭环必须完整成立 | 子域划分、关键交互、验收追溯 |
| ARB-CONV-003 | 对话空间、参与范围、可见范围、对话事实历史、显化记录和追溯上下文由本仓拥有 | 数据所有权、一致性策略 |
| ARB-CONV-004 | 相邻仓正文禁止保存 | 数据模型边界、依赖方向、安全约束 |
| ARB-CONV-005 | 跨域事实只能以引用方式显化 | 事件输入、引用解析、降级策略 |
| ARB-CONV-006 | 授权视野约束所有消费路径 | 查询边界、变化感知、下游接口 |
| ARB-CONV-007 | 索引、投影、检索、变化感知不得改变真相 | 支撑子域、异步派生、一致性策略 |

### 5.2 架构硬约束清单

| 约束编号 | 硬约束 | 架构含义 |
|---|---|---|
| AHC-CONV-001 | Conversation 不能被 Chat / Workspace / Runtime 吸收 | 必须保留独立服务 / crate / domain 边界 |
| AHC-CONV-002 | Conversation 不执行 LLM 推理、治理裁决、成员生命周期或外部平台协议生命周期 | 必须通过外部边界协作,不能内聚这些职责 |
| AHC-CONV-003 | 授权视野失效是一票否决 | 查询、订阅、事件输出和后台维护都必须经过可见范围约束 |
| AHC-CONV-004 | 相邻仓正文进入 Conversation 是一票否决 | 数据层必须只保存本仓真相、快照或引用 |
| AHC-CONV-005 | 关键变化必须可追溯 | 架构必须保留 audit / trace / outbox / evidence 接缝 |

### 5.3 未关闭需求风险清单

| 风险 | 当前架构处理 |
|---|---|
| 外围增强进入当前交付范围未定 | 架构先作为可选支撑能力边界处理 |
| 具体 API / event / DTO 未定 | 架构只固定能力面、方向和一致性语义 |
| 量化性能指标未定 | 架构保留可扩展和可观测约束,不提前定数值 |
| 快照新鲜度与失效显示未定 | 架构后续在数据一致性策略中单独约束 |
| Archive 长期交接未定 | 架构后续在演进路线中挂起 |

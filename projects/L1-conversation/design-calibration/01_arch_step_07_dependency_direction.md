## 3. SOP 问题回答

### 3.1 本仓内部层次如何划分？

本章中的“层次”不是代码目录、crate、模块或运行进程,而是架构责任层 / 依赖角色。`L1-conversation` 应收敛为五类依赖角色:

- `Conversation 核心语义角色`:承载对话空间、参与范围、可见范围、对话事实历史、跨域显化记录和追溯上下文的核心规则。
- `Conversation 编排 / 承接角色`:承接正式输入、授权消费、跨域显化、追溯读取和后台派生触发,并把外部输入转换为核心可接受的变化。
- `外部能力接缝角色`:承接来自 identity / work / governance / artifact / runtime / bridges / sdk / chat / workspace / observability / archive 等外部能力的正式边界。
- `派生消费辅助角色`:承接投影、索引、变化感知和检索辅助,只能从核心真相派生。
- `技术承载角色`:承载真相存储、派生承载和事件协作所需技术支撑,但不拥有业务语义定义权。

### 3.2 允许哪些依赖方向？

允许的依赖方向是外层依赖内层、接缝依赖正式边界、派生依赖核心真相、技术承载依赖核心规则或正式承载契约。核心语义角色只允许依赖 `L0-core` 级共享契约和本仓内部语义规则,不得依赖下游消费方、外部来源仓、事件主题、数据库产品或展示逻辑。

### 3.3 禁止哪些反向依赖？

禁止下游消费方、外部平台、Runtime 推理过程、Workspace 聚合视图、Chat 展示状态、治理 / 产物 / 项目正文、派生索引或技术存储反向定义 Conversation 真相。也禁止把 `L1-work`、`L1-governance`、`L1-artifact`、`L1-identity`、`L5-chat`、`L1-workspace`、`L2-runtime`、`L6-bridges` 等运行期或事件协作关系写成编译期源码依赖。

### 3.4 外部系统通过哪些正式边界接入？

外部能力必须通过 `外部能力接缝角色` 进入,并由 `Conversation 编排 / 承接角色` 转换为核心语义可接受的引用、快照、显化记录、授权读取或事实追加。任何外部对象都不能直接写 `Conversation 核心语义角色`,也不能绕过可见范围把数据放入派生视图。

### 3.5 本仓在全局依赖基线中涉及哪些跨仓依赖边？

本仓直接涉及:

- `L0-core`:唯一编译期依赖。
- `L0-bus`:事件协作主干。
- `L1-identity`、`L1-work`、`L1-governance`、`L1-artifact`:运行期或事件协作来源边界。
- `L0-sdk`、`L5-chat`、`L1-workspace`、`L2-runtime`、`L6-bridges`:消费或协作边界。
- `L4-observability`、`L4-archive`:追溯、观测、归档消费边界。

`L5-console`、`L6-marketplace` 和外部聊天平台协议不进入当前架构主链。

### 3.6 哪些依赖必须倒置？

来源仓、下游消费方、事件总线、存储、检索、推送和归档能力都必须通过正式边界倒置到 `Conversation 编排 / 承接角色` 或 `技术承载角色`,不能让这些外部或技术对象直接进入核心语义。核心语义只声明自己需要的引用、范围、事实、显化和追溯规则,外部适配和技术实现服从这些规则。

## 4. 当前文档问题诊断

| 旧架构内容 | 问题 | 本轮处理 |
|---|---|---|
| 依赖图容易写成 `api -> application -> domain -> repository -> db` | 这是代码实现层,不是架构依赖角色 | 改为核心语义、编排承接、外部接缝、派生辅助、技术承载 |
| 旧文档把 Chat / Workspace / Runtime / Bridges 的需求直接拉进 Conversation | 容易让消费方反向定义对话真相 | 统一要求外部能力经正式接缝进入 |
| `work / governance / artifact` 事件被描述为直接转 Turn | 容易把来源仓正文变成本仓 truth | 改为引用 / 快照 / 显化记录,来源真相不转移 |
| `StreamEvents`、Search、Archive 边界靠近核心 | 派生和外围消费容易反写核心 | 改为派生消费辅助和外部交接边界 |
| 跨仓依赖未区分编译期、运行期、事件协作 | 后续实现可能把运行关系写成 Cargo dependency | 按全局依赖裁剪规则输出三张表和裁剪图 |

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 层次主语 | API / application / domain / repository | 架构责任层 / 依赖角色 | 本章讨论依赖保护,不是代码组织 |
| 核心保护 | 对话事实、投影、事件和搜索容易混在一起 | 核心语义只被正式承接角色依赖,派生不得反写 | 防止第二 truth |
| 外部来源 | 相邻仓事实直接进入 Conversation | 相邻仓只通过引用 / 快照 / 显化边界进入 | 防止来源真相漂移 |
| 下游消费 | Chat / Workspace / Runtime 需求可反推核心 | 下游只能经正式边界消费或协作 | 防止消费体验统治核心模型 |
| 跨仓依赖 | 未区分依赖类型 | `L0-core` 编译期,其他按运行期 / 事件协作处理 | 防止实现阶段依赖失控 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 按代码分层写 controller / service / domain / repository | 对开发者熟悉 | 会提前进入概要 / 详细设计,且无法表达跨仓依赖红线 | 不采用 |
| 方案 B: 按核心语义、编排承接、外部接缝、派生辅助、技术承载写依赖角色 | 能保护 Conversation 真相,并承接 Step 5 / Step 6 结论 | 后续仍需在概要设计映射到代码主体 | 采用 |
| 方案 C: 把所有上下游仓都画成直接依赖 | 看似完整 | 会把运行期和事件协作误写为源码依赖 | 不采用 |
| 方案 D: 只写 `L0-core` 和 `L0-bus`,忽略下游消费方 | 图更简单 | 会遗漏 Chat / Workspace / Runtime / Bridges 的反向依赖风险 | 不采用 |

```text
|                 | 边界接入                          | 允许依赖    |

|        +--------+-----------------------------------+------+      |
|        | Conversation 编排 / 承接角色                      |      |
|        | formal intake / consume / manifestation / trace   |      |
|        +----------------------+----------------------------+      |
|                               | 允许依赖                          |
|                               v                                   |
|        +----------------------+----------------------------+      |
|        | Conversation 核心语义角色                         |      |
|        | space / scope / facts / manifestation / trace     |      |
|        +----------------------+----------------------------+      |
|                               ^                                   |
|                               | 允许依赖                          |
|        +----------------------+----------------------------+      |
|        | 派生消费辅助角色                                   |      |
|        | projection / index / search / change cursor       |      |
|        +---------------------------------------------------+      |
|                                                                    |
+====================================================================+
```

图示说明:

- 箭头只表示允许依赖或边界接入,不表示运行调用顺序、协议时序或代码调用链。
- `Conversation 核心语义角色` 是被保护的中心,外部来源、下游消费、技术承载和派生辅助都不能反向定义它。
- `派生消费辅助角色` 可以依赖核心真相和授权范围,但不得形成第二 truth。
- `技术承载角色` 只服从正式承载契约,不决定业务语义、状态流转或数据归属。

### 7.2 层间约束表

| 架构责任层 / 依赖角色 | 允许依赖 | 禁止依赖 | 说明 |
|---|---|---|---|
| `Conversation 核心语义角色` | `L0-core` 共享契约和本仓内部语义规则 | 下游消费方、来源仓正文、外部平台对象、事件主题、数据库产品、派生索引 | 保护对话空间、范围、事实、显化和追溯规则不被外部反向定义。 |
| `Conversation 编排 / 承接角色` | 核心语义角色、正式外部接缝、正式承载边界 | 绕过核心直接写存储;把外部事实原文变成本仓 truth;把下游展示状态写入核心 | 承接输入和消费,但必须把外部能力转换为核心允许的引用、快照、显化或事实追加。 |
| `外部能力接缝角色` | 正式边界、编排 / 承接角色、必要的运行期协作对象 | 直接依赖核心存储结构;直接改变核心语义;越过授权范围输出事实 | 外部能力只能通过受控接缝进入或消费,不能打穿核心。 |
| `派生消费辅助角色` | 核心语义角色、授权范围和正式派生规则 | 生成新业务事实;覆盖核心事实;绕过可见范围向下游输出 | 投影、索引、检索和变化感知都只是消费辅助,可重建且不得反写。 |
| `技术承载角色` | 核心定义的正式状态、派生规则和承载契约 | 决定业务状态、可见范围、跨域显化含义或追溯语义 | 存储、事件、索引、缓存等技术选择只能支撑架构,不能定义架构。 |

### 7.3 依赖倒置结论

| 需要倒置的依赖 | 倒置方式 | 保护目标 |
|---|---|---|
| `L1-identity` 成员 / actor 来源 | 核心只保存 actor / participant 引用和展示快照,解析与同步经正式接缝进入 | 防止身份生命周期进入 Conversation 真相 |
| `L1-work` 项目 / 工作上下文 | 核心只保存项目 / 工作引用、摘要或显化记录 | 防止项目与工作状态正文进入 Conversation |
| `L1-governance` / `L1-artifact` 来源事实 | 治理 / 产物事实以引用、快照或显化记录进入 | 防止裁决和产物正文转移归属 |
| `L2-runtime` 和 `L6-bridges` 协作输入 | 只允许通过正式输入边界追加结果性事实 | 防止推理过程或外部平台生命周期侵入核心 |
| `L0-bus` 事件协作 | 事件协作通过正式发布 / 消费边界承接 | 防止 event topic / relay 机制定义核心语义 |
| 存储 / 搜索 / 缓存 / 归档 | 作为技术承载或消费交接实现,服从核心定义 | 防止技术产品成为 truth source |

### 7.6 本仓禁止依赖表

| 禁止依赖 | 禁止原因 | 正确协作方式 |
|---|---|---|
| `L1-conversation -> L5-chat` | Chat 是产品入口和展示层,不能反向决定对话真相 | Chat 经 SDK / 正式服务边界消费授权对话事实 |
| `L1-conversation -> L1-workspace` | Workspace 是聚合视图,不拥有 Conversation 空间真相 | Workspace 只读消费查询、投影或事件协作结果 |
| `L1-conversation -> L2-runtime` | Runtime 拥有推理循环和临时上下文,不拥有对话历史 | Runtime 读取授权上下文并通过正式边界追加结果性事实 |
| `L1-conversation -> L6-bridges` | Bridges 适配外部平台协议,Conversation 不接管外部平台生命周期 | Bridges 通过正式边界映射输入 / 输出 |
| `L1-conversation -> L1-governance` 编译期依赖 | 治理裁决真相需要与对话显化解耦 | 使用治理引用、运行期边界或事件协作 |
| `L1-conversation -> L1-artifact` 编译期依赖 | 产物正文、版本和证据链不应变成 Conversation 源码依赖 | 使用产物引用、运行期边界或事件协作 |
| `L1-conversation -> L1-work` 编译期依赖 | 项目 / WorkItem 真相不应与 Conversation 源码耦合 | 使用项目引用、项目成员快照或事件协作 |
| 派生视图 / 索引 -> Conversation 真相反写 | 派生结构可延迟和重建,不能成为第二 truth | 从核心真相派生,必要时重建派生结果 |
| 存储 / 搜索 / 缓存产品 -> 核心语义 | 技术产品不能定义业务状态、可见范围或显化语义 | 技术承载服从核心规则和正式承载契约 |

### 7.8 依赖边界说明

`L1-conversation` 的依赖方向以保护 Conversation 真相为中心:外部来源可以提供引用、快照或显化材料,下游可以消费授权事实,技术承载可以支撑存储和派生,但它们都不能反向定义核心语义。`L0-core` 是唯一可进入编译期的共享契约基线,其余跨仓关系必须按运行期或事件协作处理。这个边界让后续概要设计可以继续展开代码主体骨架,但不会把 UI、Runtime、外部平台、治理裁决、产物正文或技术产品提前写进 Conversation 核心。

## 3. SOP 问题回答

### 3.1 这个仓有哪些主要可选架构方案？

在已确认 `L1-conversation` 必须作为独立对话真相仓的前提下,可进入本章比较的相邻路径包括:

- 当前主线:独立 Conversation 真相核心 + 正式承接层 + 引用 / 快照 / 显化 + 派生只读视图 + 事件最终一致 + 后台延后承接。
- 直连核心路径:下游和来源边界直接读写核心真相结构。
- 完整事件溯源优先路径:以完整 Event Sourcing / CQRS 作为 P0 主体架构。
- 全同步收口路径:所有写入、传播、投影、归档和观测都在同步边界完成。
- 全异步命令 / 事件路径:所有变更和读取都围绕异步承接设计。
- Projection-first / Search-first 路径:把投影、检索或变化感知结构提升为主要消费和组织核心。

Chat UI、Workspace 聚合视图、Runtime memory、Bridges 外部平台副本直接拥有 Conversation 真相,已经被前文职责和非目标排除,不再作为正式候选方案比较。

### 3.2 为什么当前选择这一种？

当前主线能同时满足四个条件:保护 Conversation 独立真相边界;允许跨域事实可见但不转移来源真相;让核心成立判断保持强一致和同步收口;让下游传播、派生视图、检索、观测和归档以最终一致或后台承接方式演进。它牺牲了直接暴露核心、一次同步全完成和早期产品级技术路线锁定的简单感,换来更稳的边界、依赖方向、数据归属和演进空间。

### 3.3 被放弃方案的主要优点是什么？

被放弃方案都有局部优点。直连核心路径初期接入快;完整事件溯源路径对历史和重放表达更强;全同步路径即时结果感更强;全异步路径解耦更彻底;Projection-first 路径对下游读体验和搜索体验更直接。

### 3.4 为什么即便有这些优点,当前仍不采用？

这些优点不能抵消它们对当前核心边界的代价。直连核心会让外部消费和来源输入反向绑定核心;完整事件溯源会在当前尚未完成对象 / 状态细化前提前锁定实现范式;全同步会把投影、归档和观测压入核心链路;全异步会削弱空间、范围、事实追加和授权读取的即时成立判断;Projection-first 会让派生结构靠近 truth center。

### 3.5 当前选择牺牲了什么,换来了什么？

当前选择牺牲了最短调用路径、单次同步全完成、最强事件溯源一致范式和下游直接读核心结构的便利。换来的是:核心真相不被下游或来源仓污染,跨域事实不转移正文归属,同步和异步职责分清,派生辅助不反写,后续概要 / 详细设计可以在稳定边界下继续细化对象、接口、状态和实现结构。

## 7. 结构化中间产物

### 7.1 当前主线方案

当前采用的主线方案是:

```text
独立 Conversation 真相核心
  + 正式承接层隔离外部输入
  + 引用 / 快照 / 显化记录承接跨域事实
  + 追加式对话事实历史
  + 授权视野强制消费边界
  + 派生只读视图 / 索引承接下游消费
  + 事件最终一致承接跨边界传播
  + 后台延后承接派生、刷新和重建
  + 追溯 / 审计 / 归档交接接缝
```

该方案的核心判断是:Conversation 的 truth center 必须独立稳定,外部能力只能经正式边界进入,下游消费不能直接绑定核心结构,派生和交接可以延迟收敛但不能反写真相。

### 7.2 方案路径比较表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 独立真相核心 + 正式承接 + 引用 / 快照 / 显化 + 派生只读 + 事件最终一致 + 后台承接 | 同时保护 Conversation 真相、跨域事实可见、授权消费、派生消费和追溯交接。 | 边界稳定,来源真相不漂移,下游不反向绑定核心,核心链路不被派生拖重。 | 边界层更多,状态解释更严格,后续实现必须处理未解析、旧视图、待交接等状态。 | 采用 | 这是当前唯一同时满足 Step 2 约束、Step 8 数据归属和 Step 9 通信方式的主线。 |
| 直连核心路径:外部来源和下游消费直接读写核心真相结构 | 缩短接入路径,减少承接层。 | 初期实现和理解更直接,下游接入更快。 | 外部输入和下游消费会反向绑定核心模型,来源正文和展示状态更容易进入 truth center。 | 不采用 | 该路径破坏 Step 7 的依赖方向和核心保护边界。 |
| 完整事件溯源优先路径:以完整 ES / CQRS 作为 P0 主体架构 | 强化历史重放、事实演进和读写分离表达。 | 历史表达强,天然强调追加和重放,对审计叙事友好。 | 在对象、状态和协议尚未细化前过早锁定实现范式,提高 P0 复杂度和一致性解释成本。 | 保留观察 | 当前采用追加式事实历史和事件协作,但不把完整 ES 作为 P0 必选方案。 |
| 全同步收口路径:所有写入、传播、投影、归档和观测都在同步边界完成 | 追求一次交互内全链路完成。 | 即时结果感强,表面一致性清晰。 | 会把投影、检索、归档、观测和外部快照刷新压入核心链路,制造高耦合和伪一致。 | 不采用 | 该路径与 Step 8 最终一致和 Step 9 后台延后承接口径冲突。 |
| 全异步命令 / 事件路径:所有变更和读取都围绕异步承接设计 | 最大化解耦和吞吐弹性。 | 跨边界传播压力小,适合高并发事件处理。 | 对话空间、范围、事实追加和授权读取缺少即时成立 / 失败判断,容易让调用方无法确认正式状态。 | 不采用 | 核心真相成立判断必须有同步收口,不能全部异步化。 |
| Projection-first / Search-first 路径:以投影、检索或变化感知作为主要消费和组织核心 | 优先满足下游读取、搜索和实时感知体验。 | 下游体验更直接,读模型可以快速服务 UI 和聚合场景。 | 派生结构会靠近 truth center,容易形成第二事实来源,并让下游需求反向塑造核心。 | 不采用 | 检索、投影和变化感知只能从 Conversation 真相派生,不得反写。 |
| Source-copy 路径:把来源仓正文或摘要深拷贝进 Conversation 统一管理 | 降低跨仓读取和来源不可用时的展示成本。 | 本地读取简单,短期降级显示能力强。 | 直接打穿数据归属边界,让 Work / Governance / Artifact / Identity 正文漂移进本仓。 | 不采用 | 该路径与 Step 8 “明确不拥有正文 / 真相”冲突,不作为正式主线。 |

### 7.3 不进入本章正式比较的方向

| 方向 | 不进入比较的原因 | 正确处理 |
|---|---|---|
| Chat UI 拥有 Conversation truth | 前文已确认 Chat 是产品入口和展示层,不是对话真相仓。 | Chat 经 SDK / 正式边界消费对话事实。 |
| Workspace 聚合视图拥有 Conversation truth | 前文已确认 Workspace 只聚合个人 / 项目视野,不拥有对话空间真相。 | Workspace 只读消费查询、投影或事件协作结果。 |
| Runtime memory / agent loop 拥有 Conversation truth | 前文已确认 Runtime 推理过程和 memory 不属于对话事实历史。 | Runtime 读取授权上下文并通过正式边界追加结果性事实。 |
| Bridges 外部平台副本拥有 Conversation truth | 前文已确认外部平台协议和生命周期归 Bridges。 | Bridges 映射外部输入 / 输出,Conversation 只承接正式结果。 |
| Governance / Artifact / Identity / Work 正文并入 Conversation | 前文已确认这些来源仓拥有各自正文和生命周期真相。 | Conversation 只保存引用、快照或显化记录。 |

### 7.4 轻量取舍对照表

| 当前主线得到什么 | 当前主线失去什么 |
|---|---|
| 稳定独立的 Conversation truth center | 不能用最短路径直接暴露核心给下游 |
| 来源事实可见但正文归属不转移 | 需要维护引用、快照、显化和未解析状态 |
| 核心成立判断可同步收口 | 不能把所有工作都推给异步后台 |
| 传播、派生、归档可最终一致 | 需要解释旧视图、待交接和延迟收敛 |
| 下游消费不反向绑定核心结构 | 需要额外派生只读视图和消费边界 |
| 关键变化可追溯 | 需要维护追溯交接材料和失败状态 |

### 7.5 方案边界说明

本章只比较在 `L1-conversation` 已经是独立对话真相仓这个前提下的相邻结构路径,不重新打开 Chat、Workspace、Runtime、Bridges 或来源仓拥有对话真相的讨论。完整事件溯源、全同步、全异步和 Projection-first 都是可能改变主线结构的有效替代路径,因此进入比较;具体数据库、消息产品、协议和框架只是实现载体,不进入本章。当前采用的方案不是最短路径,但它最能同时守住真相边界、来源归属、授权消费、派生不反写和跨边界演进空间。

## 3. SOP 问题回答

### 3.1 哪些架构决定需要沉淀为 ADR？

建议后续沉淀为 ADR 的决策包括:

- 将 `L1-conversation` 定义为独立平台对话真相仓,而不是 Chat UI、Workspace 聚合视图、Bridges 适配层、Runtime 推理系统或来源仓副本。
- 将对话空间、参与范围、可见范围、对话事实历史、跨域显化记录和追溯上下文定义为 Conversation truth center。
- 通过正式承接层隔离 Chat、Workspace、Runtime、Bridges、Work、Governance、Artifact、Identity 等外部输入。
- 通过引用 / 快照 / 显化记录承接跨域事实,禁止复制来源仓正文或外部平台正文。
- 将授权视野作为所有读取、订阅、变化感知、追溯读取和派生消费的强制边界。
- 将派生读模型、搜索索引、变化流和消费辅助结果限定为只读、可重建、最终一致,不得成为第二 truth。
- 采用核心同步收口、跨边界事件最终一致、派生 / 刷新 / 交接后台延后承接的通信结构。
- 采用追加式对话事实历史,但不在当前架构阶段锁定完整 ES / CQRS 为主体实现范式。
- 只保留 Observability / Archive 追溯交接接缝,不让 Conversation 拥有全局日志或长期归档正文。

### 3.2 每个关键架构决定对应哪些需求、约束或风险来源？

这些决策分别承接 `00-需求文档.md` §2 本仓定位、§4 目标与非目标、§6 使用方与依赖、§7 核心能力闭环、§9 功能需求、§10 业务规则与边界约束、§11 数据需求与数据归属、§12 接口与依赖、§13 非功能需求、§14 验收标准和 §15 风险与待确认事项。

### 3.3 是否存在没有需求来源的架构设计？

当前没有影响主线的孤儿架构判断。具体 API / event / DTO / protocol 字段、具体数据库 / 搜索 / 队列 / 缓存产品、实时消费协议、量化容量模型、快照生命周期、Archive / Observability 交接协议和完整 ES / CQRS 是否升级为主体范式仍保持待确认或后续设计承接,没有被写成已定架构结论。

### 3.4 是否存在没有架构承接的核心需求或关键约束？

当前没有核心闭环需求未被架构承接。`FR-CONV-001` ~ `FR-CONV-005` 已由职责边界、限界上下文、数据所有权、关键交互、关键技术机制和横切关注点承接;`FR-CONV-006` ~ `FR-CONV-008` 被承接为外围增强、派生辅助或演进路线,没有被误提升为当前核心 truth 成立条件。

### 3.5 哪些取舍和红线必须长期可追溯？

必须长期可追溯的红线包括:Conversation 不能被 Chat / Workspace / Runtime / Bridges 吸收;相邻仓正文不得进入 Conversation truth;授权视野不得被任何消费路径绕过;派生视图和检索结果不得反写真相;同步成功不得伪装异步传播、投影重建或归档交接完成;Conversation 不拥有治理、产物、成员、外部平台、全局观测或长期归档主体职责。

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 追溯来源 | 旧四形态、Turn、AG-UI、接口和事件线索容易成为隐性来源 | 以新版 `00-需求文档.md` 的定位、目标、FR、BR、数据、接口、NFR、验收和风险为来源 | 对齐当前需求基线 |
| 追溯方式 | 容易写成章节目录对照或“已覆盖” | 写成需求结论 / 约束 -> 架构承接结果 -> 承接位置 -> 成立理由 | 对齐书写规范 §4.16 |
| ADR 主语 | 没有稳定专项 ADR 或容易把技术机制清单当 ADR | 只列长期影响主线的架构决策候选 | 对齐书写规范 §4.17 |
| 待确认处理 | 可能在追溯阶段脑补协议、产品或量化指标 | 保留为漏项检查或待确认,不提前闭合 | 防止生成伪确定性 |
| 边界红线 | 分散在职责、数据、交互、横切和风险章节 | 在追溯矩阵和 ADR 候选中建立长期索引 | 便于后续概要 / 详细设计继承 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 只列需求章节到架构章节的目录对照 | 短,容易写 | 不能证明具体承接关系,也无法发现孤儿结论 | 不采用 |
| 方案 B: 建立需求追溯矩阵、漏项检查表和 ADR 决策候选索引 | 能说明来源、承接、落点、缺口和长期决策 | 文档更长,需要避免新增结论 | 采用 |
| 方案 C: 本步直接创建正式 ADR 文件 | ADR 体系看起来完整 | 超出当前 Step 范围,且会绕过后续 ADR 评审 | 不采用 |
| 方案 D: 把所有关键技术机制都写成 ADR | 看似全面 | 会把局部机制和实现选择噪音化,削弱真正长期决策 | 不采用 |

## 1. 业务背景与驱动力

### 1.1 业务背景

治理域是 Quantalithos 的**合规与关键决策中心**。它把产品原则"关键节点强制人类"和 ISO 42001 AIMS 的要求,落成可执行的技术机制:
- Gate 六段式结构化决策
- Policy 规则下发与优先级
- Control / SoA / AIIA / Nonconformity 的合规闭环
- 自主性 5 级权限控制(autonomy_level)

没有治理域,AI 可以直接绕过关键决策点,平台无法证明自己在受控运行。

### 1.2 业务驱动力

**业务驱动力**:
- 用户需要对关键决策有最终控制权
- 平台需要可出具 42001 / 9001 证据链
- 企业客户需要 Policy / SoA / AIIA 等治理资产

**技术驱动力**:
- `gate.decided` 是六域扇出中心事件
- Policy 需要下发给 runtime / capability-hub
- SoA 必须覆盖 38 控制项
- shared_rules 不可被低优先级覆盖

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | RaiseGate P95 | < 150ms | benchmark |
| 性能 | DecideGate P95 | < 200ms | benchmark |
| 性能 | GetApplicablePolicies P95 | < 50ms | benchmark |
| 传播 | Policy 下发到 runtime 生效 | < 30s | 集成测试 |
| 合规 | SoA 38 控制项覆盖 | 100% | 静态校验 |
| 审计 | audit_trail append-only 覆盖率 | 100% | DB 审计 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| Gate 六段式必须完整 | GV1 / domain README | 决策前强校验 |
| audit_trail 只 append | GV2 | 决策历史不可改 |
| resolution 决定后不可修改 | GV3 | 纠正需新 Gate |
| autonomy_level=5 必须 policy_auto 授权 | GV4 | AI 全自主有硬门槛 |
| shared_rules 不被低 scope 覆盖 | GV5 | Policy 求值必须有硬优先级 |
| SoA 覆盖 38 控制项 | GV6 / 42001 | SoA 发布校验固定 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| Policy DSL | 未定(CEL / Rego 候选) | 可后续决策 |
| Gate kind 扩展 | custom + metadata | 未来可细化 |
| AIIA 自动化 | 不自动 | 可后续加 draft assist |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| Gate 总量 | 200w | README |
| Policy 记录 | 1000w(含历史) | README |
| 控制项 | 38(42001 附录 A) | 标准硬约束 |
| applicable policy 求值 QPS | 高频(运行时) | GetApplicablePolicies P95 < 50ms |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| Gate kind 扩展 | 中 | custom + metadata + event 驱动 |
| Policy 规则变更 | 高频 | append-only 版本链 + active/superseded |
| AIIA / SoA 模板变化 | 中 | 双身份 + artifact 协作 |
| 自主性边界 | 中 | autonomy_level + policy_auto |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **聚合驱动 + append-only 审计链**(当前)| 符合治理对象特性,审计强 | 规则求值复杂 | ✅ |
| 纯规则引擎服务 | 对 Policy 友好 | Gate / SoA / AIIA / Nonconformity 语义弱 | ❌ |
| GRC 外部系统集成 | 省开发 | 失去产品内生能力 | ❌ |

**最终选择**:**Gate / Policy / Control / AIIA / SoA / Nonconformity 六聚合 + append-only 审计**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 六段式 Gate | 决策结构化、可审计 | 录入更重 |
| shared_rules 优先级硬编码 | 安全边界稳定 | Policy 求值更复杂 |
| SoA 38 控制项强覆盖 | 合规清晰 | 维护成本高 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
Owners / Approvers / Auditors
         │
         ▼
   ★ quantalithos-governance ★
   - Gate / Policy / Control / AIIA / SoA / Nonconformity
         │
   ┌─────┼────────────┬────────────┬────────────┬────────────┐
   ▼     ▼            ▼            ▼            ▼
conversation process   work       artifact      runtime/capability-hub
Gate Turn  waiting_gate project    双身份        Policy cache
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ Gate 六段式
- ✅ Policy 定义 + 作用域 + 优先级
- ✅ 38 Control 项管理
- ✅ AIIA / SoA 生命周期
- ✅ Nonconformity + corrective action

**不做什么**:
- ❌ Gate 卡片 UI 渲染(conversation / console)
- ❌ Artifact 正文存储(artifact)
- ❌ runtime 工具白名单执行(capability-hub / runtime)
- ❌ process 的 Activity 实际执行(process)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则阻断 |
| artifact | 99.9% | 双身份可延迟同步 |
| runtime / capability-hub | 99.9% | 下发延迟告警 |
| conversation | 99.9% | UI 可能看不到 gate turn,但治理对象仍在 |

### 4.4 关键依赖风险

- Policy 冲突导致下游行为不可预测
- SoA 覆盖错误破坏合规结论
- Gate 候选方案设计不合理导致业务卡死

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
api / rpc
   │
   ▼
application
   ├─ Gate / Approval use cases
   ├─ Policy evaluation / applicable policies
   ├─ Compliance assets(AIIA / SoA / Control)
   └─ Nonconformity / corrective loop
        │
        ├─▶ PostgreSQL
        ├─▶ bus(outbox)
        ├─▶ artifact sync
        └─▶ runtime / capability-hub distribution
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| governance-api | gRPC/HTTP 入口 | Rust |
| governance-domain | Gate / Policy / Control 等聚合 | Rust |
| policy-distributor | 下发 Policy 变更 | Rust |
| subscriptions | 消费 process/work/artifact/identity 事件 | Rust |
| postgres | 六聚合 + Approval + outbox | PostgreSQL |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| 下游获取适用 Policy | RPC / query | 高频读,明确契约 |
| Gate 决策扇出 | 事件 | 六域解耦 |
| SoA / AIIA 双身份 | 事件 + ref | 避免重复正文存储 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| gates / approvals | governance | governance / down-stream via events |
| policies | governance | runtime / cap-hub / work / process |
| controls | governance | governance |
| aiia / soa metadata | governance | artifact / audit |
| nonconformities | governance | governance / observability |

### 6.5 部署拓扑

- 单服务 + PostgreSQL 起步
- policy-distributor 可内嵌同进程
- 高可用要求高于一般 L1 服务

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api
 │
 ▼
application
 │
 ▼
domain(Gate / Policy / Control / AIIA / SoA / Nonconformity)
 ▲
 │ ports
infra(Postgres / Bus / Artifact adapter / Runtime distributor)
```

### 7.2 层间约束规则

- domain 不直接依赖 infra
- Policy 求值不直接访问 runtime,通过分发接口
- AIIA / SoA 只维护治理态,不写 Artifact 正文
- Nonconformity 只记录治理语义,不直接修业务数据

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| PolicyDistributor | application/domain | infra runtime / cap-hub adapter |
| ArtifactSync | application/domain | infra artifact adapter |
| GateEventPublisher | application | infra outbox |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 极高(所有六域都依赖 gate.decided) |
| 传出耦合 | 中(artifact / runtime / bus / pg) |
| 不稳定性 | 中 |
| 抽象度 | 高(domain 聚合清晰) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Gate | governance | process / work / artifact / identity / conversation | 聚合内强一致 + 事件扇出 |
| Policy | governance | runtime / capability-hub / work | 聚合内强一致 + 下发最终一致 |
| Control | governance | governance / audit | 强一致 |
| AIIA / SoA 元数据 | governance | artifact / audit | 双身份最终一致 |
| Nonconformity | governance | observability / owners | 强一致 |

### 8.2 一致性层次

- Gate / Policy / Control / AIIA / SoA / Nonconformity 各聚合内强一致
- Gate.decided 扇出到各域最终一致
- Policy 下发到 runtime / cap-hub 最终一致
- AIIA / SoA 与 artifact 双身份最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| gate.decided 扇出下游失败 | replay 事件 |
| Policy 下发失败 | 重试 + lag 告警 |
| AIIA/SoA 双身份不同步 | 对账 + 回放 |
| Nonconformity 状态漏更新 | replay + 审计修复 |

### 9.1 Rust + PostgreSQL

| 维度 | 内容 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| Policy DSL 未定 | 规则表达能力 | P0 |
| Gate kind 扩展机制未定 | 用户可见类型演进 | P1 |
| Deviation/change-request 后续设计未落地 | GUIDED / STRICT 扩展 | P2 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| Policy 下发 lag > 30s | 持续 1 周 | 重构分发层 |
| Gate 总量 > 200w | 1 月 | 分区 / 冷存优化 |
| control.violated 高频 | > 10/min | 规则 / 告警链优化 |

### 12.3 演进步骤

```
阶段 1: Gate / Policy 核心闭环
阶段 2: Control / SoA / AIIA 稳定
阶段 3: Nonconformity 自动化增强
阶段 4: DSL / 多组织继承 / 高级治理自动化
```

### 12.4 目标架构

治理域的目标是:
- 成为平台的"决策与约束中枢"
- 不是 GRC 套件,而是贴着产品运行时的治理能力
- 对内主导 Gate / Policy / 合规证据,对外通过 UI 与审计输出呈现

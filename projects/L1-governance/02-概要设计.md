## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-governance` 不是流程引擎,也不是项目任务系统。它是 **“治理决策真相仓”**。

你可以把它理解成:
- 这件事现在能不能继续推进
- 这次 Gate 到底是谁批的
- 为什么批、为什么不批
- 哪些例外被允许通过
- 哪些风险被显式接受
- 某个高风险动作到底是正式放行了,还是只是消息里看起来像被放行了

这些事情,都由 `L1-governance` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L1-governance`,这些治理事实就会散落在:
- `process` 的 waiting_gate 节点里
- `work` 的状态字段里
- `artifact` 的证据引用里
- `conversation` 的 gate turn 消息里
- 人工口头决策和临时备注里

结果就会出现:
- 系统知道“停下来了”,但不知道正式结论是什么
- conversation 里看得到通知,却不知道哪个才是正式 decision 真相
- work / process / runtime 各自偷偷带一套审批逻辑
- 风险接受、例外放行、责任链确认没有统一归属
- 审计时无法回答“谁批准的、依据什么批准、谁承担风险”

所以 `L1-governance` 必须独立存在,作为:
> **治理结论、Gate 收口、例外裁决和责任链确认的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Gate
就是:
> 一件事推进到某个关键点时,必须停下来等正式治理判断的那个治理节点。

它不是 process 的普通 Activity,也不是 conversation 里的一张卡片。

#### Decision
就是:
> 对某个 Gate / 请求对象作出的正式治理结论。

它回答的是:
- approve / reject / request change / waive / accept risk
- 谁做的
- 为什么这样决定

#### Governance Request
就是:
> 某个仓把“这件事需要治理判断”这件事正式提交给 governance 的请求对象。

它不是 decision 本身,而是 decision 的输入入口。

#### Exception / Waiver / Risk Acceptance
就是:
> 正常规则本来不允许,但这次被显式作为例外、豁免或风险接受来处理。

它不是普通 approve 的别名,而是治理层的特殊裁决语义。

#### Responsibility Chain
就是:
> 这次决策谁有资格批、谁必须批、谁负最终责任的正式关系链。

它不是 identity 的身份真相本体,而是这次治理动作里的审批与责任关系。

#### Gate Turn
就是:
> `conversation` 把 governance 的治理事件翻译出来给人看的消息记录。

它不是正式 decision 真相本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L1-governance/02` 时,先收稳以下前提:
- `L1-governance` 不应按对象数拆,而应按主要部分拆
- governance 至少应拆成“治理请求与 Gate 主语 / 决策与裁决真相 / 责任链与审批关系 / 例外与风险接受 / 治理审计与下游通知接缝”五个主要部分
- governance 自己拥有的真相是 Gate / request / decision / approver relation / rationale / exception / risk acceptance / audit trail
- `Project / WorkItem / ProcessInstance / Artifact 正文 / Conversation / Turn / GlobalMember / Runtime` 都不是 governance 真相
- governance 可以消费这些域的引用、投影和证据,但不能把它们收编为自己的正式主真相
- 02 的重点不是“审批表长什么样”,而是先把“governance 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,项目推进不只是“能不能做出来”的问题,还包括“能不能正式放行、谁来承担责任、依据是否充分”。用户真正需要的不是在流程里随便停一下,而是:
- 当事情走到关键节点时,系统能正式发起治理判断
- 某个高风险动作能明确谁批准、谁驳回、谁要求补证据
- 某个例外放行能明确是谁接受风险、范围是什么、有效期到哪里
- work / process / runtime / artifact / conversation 都能围绕同一个正式治理结论继续工作

如果把这些逻辑分别散落到:
- `process` 的等待节点
- `work` 的生命周期字段
- `artifact` 的 evidence refs
- `conversation` 的通知消息
- 人工临时协商

系统会快速退化成:
- process 能挂起,但没有正式 Gate decision 真相
- work 看起来被放行了,但不知道谁批准的
- artifact 提供了证据,却不知道证据有没有被正式采纳
- conversation 展示了“已批准”,但消息和正式 decision 可能漂移
- 例外、豁免、风险接受无法形成可追溯治理闭环

因此,本概要设计的任务就是:
> **把 `L1-governance` 写成一个新人也能看懂的“治理决策真相仓”,而不是把审批消息、流程停点、项目状态和证据引用混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| Gate 真相归属 | 易被误解为 waiting_gate 或 gate turn | governance 持有正式 Gate/Decision 真相 | 需写死边界 |
| 治理 vs 流程 | process 停点与治理结论容易混层 | process 管等待时机,governance 管正式结论 | 需正式落图 |
| 例外放行语义 | 易被当作普通 approve | waiver / exception / risk acceptance 独立成立 | 需形成主要部分 |
| 审批责任链 | actor 身份、审批资格、最终责任易混 | 责任链独立成为治理约束部分 | 需单列并固定 |
| 下游通知 | conversation / work / runtime 各自消费治理结果的边界易漂移 | governance 统一输出正式结论语义 | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让“是否放行、谁批准、谁承担风险、基于什么证据”成为正式、可追溯、不可绕过的治理事实
- **技术问题**:Gate / request / decision / approver chain / exception / audit trail 之间的边界如何稳定建模,并与 `work/process/artifact/conversation/identity/runtime` 清晰协作而不混层

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |

| 明确 governance 的治理真相职责 | Gate / request / decision / exception / audit 职责无歧义 | 文档评审 |

| 明确责任链与风险接受边界 | approver chain / risk acceptance 有正式归属 | 文档评审 |
| 支撑后续详细设计 | 本文足以承接 `03-详细设计.md` 的对象模型、决策流与审计设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文定义具体 policy engine / 规则语言实现(留给 `03-详细设计.md`)
- 不在本文定义 Gate 卡片在 conversation 里的前端展示细节

- 不在本文持有 Artifact 正文、Project 真相、ProcessInstance 真相或 Runtime 执行正文
- 不在本文给出完整 decision schema、索引、重放与补偿机制细节

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ identity                   │
                    │ - approver identity        │
                    │ - role / capability        │
                    └────────────┬───────────────┘
                                 │ actor capability / approver ref
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ conversation               │   │ governance                 │   │ work                       │
│ - gate turn                │◀──│ - Gate / Request           │──▶│ - project/work lifecycle   │
│ - decision notification    │   │ - Decision                 │   │ - gated actions            │
│ - visible audit summary    │   │ - exception / risk accept  │   └────────────────────────────┘
└────────────────────────────┘   │ - approver chain           │
                                 └────────────┬───────────────┘
                                              │ gate request / evidence refs / resume decision
                                              ▼
                    ┌────────────────────────────┐
                    │ process / artifact         │
                    │ - waiting_gate             │
                    │ - evidence / baseline refs │
                    └────────────┬───────────────┘
                                 │ execution continue / block / waive
                                 ▼
                    ┌────────────────────────────┐
                    │ runtime / observability    │
                    │ - execution restricted     │
                    │ - audit / trace consume    │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `governance` 自己负责“正式治理请求”和“正式治理结论”
- `identity` 提供 approver 身份、角色与能力边界,但不让渡“这次谁有资格批”的治理判断本体
- `work` 提供项目和工作事实,governance 决定某些 lifecycle 或高风险动作能否继续推进
- `process` 提供 waiting_gate / 节奏停点,governance 负责在这个停点上形成正式结论
- `artifact` 提供证据正文、baseline 与 evidence refs,governance 基于这些引用作出裁决,但不持有正文真相
- `conversation` 消费 governance 的结果并翻译为 gate turn / decision notification,但不拥有正式 decision 真相
- `runtime` 消费 governance 的允许/拒绝/暂停/例外语义,但不负责治理结论本身

所以 `L1-governance` 在全局里的角色是:
> **把多域的关键推进动作、证据引用和责任链输入收拢为统一正式治理结论,并把这些结论输出回下游执行与协作链的治理中枢。**

### 4.3 系统边界

**做什么**:
- 保存正式 Gate / request / decision 真相
- 保存 approver relation / responsibility chain / rationale / exception / risk acceptance
- 基于输入证据与请求对象形成治理结论
- 向 work / process / conversation / runtime 输出正式治理结果语义
- 提供治理审计链与结论回放基础

**不做什么**:
- 不负责项目、任务、迭代真相
- 不负责流程运行态真相
- 不负责 Artifact 正文真相
- 不负责 Conversation / Turn 真相
- 不把 identity 的成员身份真相收编进治理层
- 不负责 runtime 执行正文推进

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| identity | 99.9% | approver 身份摘要或 capability 查询延迟时,request 可保持 pending,已形成的治理结论不受影响 |
| work | 99.9% | lifecycle / gated action 输入延迟,治理请求可排队等待,不允许 work 本地直接放行 |
| process | 99.9% | waiting_gate / resume 信号延迟,governance 真相继续存在; process 继续保持 suspended 而不是猜测已批准 |
| artifact | 99.9% | evidence refs 延迟或不足时,Gate 可保持 waiting / request change,不允许无证据直接放行 |
| conversation | 99.9% | decision notification 延迟,但正式 decision 真相不受影响; gate turn 可补发 |
| runtime | 99.9% | 执行限制与继续信号延迟时,默认保持受限而不是默认放开 |
| observability / archive | 99.9% | audit 投影延迟,治理主真相链不受影响; 后续通过 audit replay 补齐 |

### 4.5 关键依赖风险

- governance / process 边界不稳会导致 waiting_gate 被误当正式 decision 真相
- governance / conversation 边界不稳会导致 gate turn 被误当 decision 本体
- governance / artifact 边界不稳会导致 evidence ref 替代正式证据采纳结论
- governance / work 边界不稳会导致项目状态字段偷偷带审批逻辑
- governance / runtime 边界不稳会导致执行层临时判断绕过正式治理收口
- approver capability 或 delegated authority 同步滞后,会导致错批 / 漏批 / 越权批准
- evidence refs 已到但证据语义不足时,系统若误判为可放行,会导致“有 ref 但无充分依据”的治理失真
- 下游仓若对同一 emitted result 各自二次解释,会导致 process / work / runtime 对同一 decision 的执行漂移
- exception / waiver / risk acceptance 若没有单独收口,会让治理系统长期退化为“任何事都能特批”

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 治理请求与 Gate 主语部分

- **它是什么**: 这是 `L1-governance` 的入口层,一起回答“现在到底在审什么、为什么要进入治理”
- **为什么单独有它**: 如果把 request、target ref 和最终 decision 混在一起,读者会分不清“请求进入治理”和“治理已经给出结论”是两件不同的事
- **负责什么**:
  - 接住来自 work / process / runtime / artifact 的治理请求
  - 标记被审对象、请求类型、当前等待的治理动作
  - 为后续 decision 和 audit 提供稳定锚点
- **不负责什么 / 容易混淆点**:
  - 不负责生成最终治理结论
  - 不负责持有项目、流程、制品正文真相
  - 最容易和 process waiting_gate、work 状态流混淆
- **与其他部分交互**:
  - 上游: work / process / runtime / artifact
  - 下游: 决策与裁决真相部分、责任链与审批关系部分
  - 交互类型: 请求输入型 + 目标锚点型
- **后续详细设计展开点**:
  - governance request 模型
  - gate target ref / request type

#### 决策与裁决真相部分

- **它是什么**: 这是 `L1-governance` 的核心真相层,一起回答“正式结论是什么、为什么是这个结论”
- **为什么单独有它**: 如果不单列,approve / reject / waive / accept risk 会被误写成流程节点结果或消息文案
- **负责什么**:
  - 保存正式 decision
  - 保存 approve / reject / request change / waive / accept risk 等裁决语义
  - 保存 rationale / policy basis / decision timestamp
- **不负责什么 / 容易混淆点**:
  - 不负责证据正文本体
  - 不负责前台通知文案本体
  - 最容易和 conversation gate turn、artifact evidence ref 混淆
- **与其他部分交互**:
  - 上游: 治理请求与 Gate 主语部分、责任链与审批关系部分、例外与风险接受部分
  - 下游: 治理审计与下游通知接缝部分
  - 交互类型: 正式结论写入型
- **后续详细设计展开点**:
  - decision 对象模型
  - decision rationale / policy basis

#### 责任链与审批关系部分

- **它是什么**: 这是治理资格与责任分配层,一起回答“谁能批、谁必须批、谁承担责任”
- **为什么单独有它**: 如果把 approver chain 混进 decision,会让“结论”和“谁有资格给出结论”失去边界
- **负责什么**:
  - 定义 approver chain
  - 定义 delegated authority
  - 定义 required approver / final accountability
- **不负责什么 / 容易混淆点**:
  - 不重新定义成员身份真相
  - 不直接产生项目推进事实
  - 最容易和 identity capability、work ownership 混淆
- **与其他部分交互**:
  - 上游: identity
  - 下游: 决策与裁决真相部分、例外与风险接受部分
  - 交互类型: 资格校验型 + 责任确认型
- **后续详细设计展开点**:
  - approver chain 模型
  - delegated authority 规则

#### 例外、豁免与风险接受部分

- **它是什么**: 这是 `governance` 的例外治理层,一起回答“本来不允许的事为什么这次被放行”
- **为什么单独有它**: waiver / exception / risk acceptance 不是普通 approve 的别名,如果不单列,后续会把例外放行写成普通通过
- **负责什么**:
  - 保存 exception / waiver / risk acceptance
  - 保存接受人、范围、时限、理由
  - 为下游形成“受控例外继续执行”的依据
- **不负责什么 / 容易混淆点**:
  - 不负责项目/流程正文推进
  - 不负责证据正文管理
  - 最容易和 decision 普通通过、work 的临时 override 混淆
- **与其他部分交互**:
  - 上游: 决策与裁决真相部分、责任链与审批关系部分、artifact evidence refs
  - 下游: 治理审计与下游通知接缝部分
  - 交互类型: 例外裁决型 + 风险承担型
- **后续详细设计展开点**:
  - exception / waiver / risk acceptance 模型
  - scope / expiry / acceptor 规则

#### 治理审计与下游通知接缝部分

- **它是什么**: 这是治理结果对外分发和审计留痕层,一起回答“治理结论怎么被别人消费、怎么被审计”
- **为什么单独有它**: 如果不单列,conversation / process / work / runtime 会各自解释 decision,最终让正式结论传播漂移
- **负责什么**:
  - 向 process 发 resume / continue / block 语义
  - 向 work 输出 lifecycle gate result
  - 向 conversation 输出 notification refs / gate turn 输入
  - 向 observability / archive 保留审计链
- **不负责什么 / 容易混淆点**:
  - 不持有 conversation / process / work 的正文真相
  - 不生成新的主决策真相
  - 最容易和下游仓内部状态迁移逻辑混淆
- **与其他部分交互**:
  - 上游: 决策与裁决真相部分、例外与风险接受部分
  - 下游: process / work / conversation / runtime / observability
  - 交互类型: 正式结果输出型 + 审计输出型
- **后续详细设计展开点**:
  - decision emitted 规则
  - 下游接缝 DTO / refs

### 7.4 层间约束规则(防退化)

- request 不等于 decision,两者不得混成一个对象语义
- waiting_gate 只表示“在等治理”,不表示“治理已经同意”
- evidence ref 只表示“看过什么依据”,不表示“正文被治理层拥有”
- gate turn / decision notification 只表示“给人看的输出”,不表示“正式真相本体”
- runtime / work 不得各自复制正式审批逻辑来绕过 governance
- exception / waiver / risk acceptance 必须显式留痕,不得伪装成普通 approve
- emitted result 必须由 governance 统一输出,下游仓不得各自重新定义同一 decision 的含义

**治理红线**:
- waiting_gate 不得替代正式 decision
- gate turn 不得替代正式 decision
- artifact evidence ref 不得替代证据采纳结论
- work / runtime 不得本地复制审批逻辑绕过 governance
- exception / risk acceptance 必须显式带 acceptor / scope / rationale

## 8. 关键技术选型

### 8.1 为什么采用“请求层 / 决策真相层”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | request / gate subject 与 decision truth 分层 |
| 备选方案 | request 与 decision 混成一个对象 |
| 选择理由 | 防止“进入治理”和“正式结论成立”被混成同一步 |
| 演进路径 | 后续可增强 decision schema,但不破坏 request / decision 分层 |

### 8.2 为什么等待点不等于治理结论

| 维度 | 内容 |
|---|---|
| 当前选择 | process 的 waiting_gate 只作为等待时机,正式结论只在 governance |
| 备选方案 | 让 process 节点状态直接代表审批结果 |
| 选择理由 | 避免流程层越界成为治理真相源 |
| 演进路径 | 后续只增强 waiting_gate 与 decision 的接缝,不合并两者归属 |

### 8.3 为什么例外放行与普通 approve 分离

| 维度 | 内容 |
|---|---|
| 当前选择 | waiver / exception / risk acceptance 独立成治理语义 |
| 备选方案 | 统一归并为 approve |
| 选择理由 | 普通放行和显式担责是两种不同治理含义,不能混写 |
| 演进路径 | 后续可扩展例外类型,但不把风险接受重新压回普通 approve |

### 8.4 为什么 governance 只持有 evidence refs,不持有 artifact 正文

| 维度 | 内容 |
|---|---|
| 当前选择 | governance 只持有 evidence / baseline refs 与 adopted basis |
| 备选方案 | 把 artifact 正文或完整基线直接复制进 governance |
| 选择理由 | 避免治理层膨胀为制品正文仓,同时保持“看到过什么依据”和“正文真相归谁拥有”两件事分离 |
| 演进路径 | 后续可增强 evidence ref 结构,但不改变 artifact 正文仍归 artifact 的边界 |

### 8.5 为什么 emitted result 必须统一由 governance 输出

| 维度 | 内容 |
|---|---|
| 当前选择 | governance 形成统一 emitted result contract 给下游消费 |
| 备选方案 | 让 work / process / runtime 各自解释 decision |
| 选择理由 | 避免同一 decision 在不同下游出现不同语义,导致恢复、放行、通知和审计漂移 |
| 演进路径 | 后续可扩展不同结果类型,但统一由 governance 输出正式结论语义 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: governance 独立为治理真相仓(当前) | 方案 B: 把治理分散进 work/process/conversation |
|---|---|---|
| 审计性 | 高 | 低 |
| 边界清晰度 | 高 | 低 |
| 多域一致性 | 高 | 低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的治理不是附属消息,也不是流程节点旁边的一个状态字段。它必须单独持有“正式请求、正式裁决、责任链、例外接受和审计输出”这整套治理真相,否则后续 work / process / artifact / conversation / runtime 都会各自长出一套隐形审批逻辑。

#### 数据流 A · Request → Decision → Emitted Result 主线

```text

  │
  ▼

  │  → [记录 request 与 target refs]
  ▼

  ├─▶ emit_result_to_work()
  ├─▶ emit_notification_to_conversation()
  └─▶ publish_audit_trail()
```

#### 数据流 B · waiting_gate → decision → process resume 主线

```text
process waiting_gate entered
  │
  ▼
RaiseGovernanceRequest
  │
  ▼
CheckApproverEligibility + evidence review
  │
  ▼
DecideGate
  │
  ▼
EmitDecisionResult
  │
  ▼

```

#### 数据流 C · exception / risk acceptance 主线

```text
normal rule says no
  │
  ▼

  │
  ▼

  │
  ▼
RecordRiskAcceptance / formal exception decision
  │
  ▼

```

```text

  │
  ▼

  ▼

  │
  ▼
```

|---|---|---|---|

## 11. 横切关注点

### 11.1 安全
- 非授权 actor 不得写入正式治理结论
- delegated authority 只能在正式规则下生效
- 例外放行必须带 acceptor / scope / expiry / rationale
- 受治理约束动作不得通过本地判断绕过 governance

### 11.2 性能
- 普通 request / decision 链路不应阻塞关键主线过长
- query history 和审计回放要保证稳定查询性能

### 11.3 可用性
- conversation / process / runtime 等下游通知延迟不影响正式治理真相落库
- evidence refs 延迟时允许 request 保持等待,但不允许跳过治理直接推进
- identity capability 查询延迟时,默认保持 pending 或 restricted,而不是默认放行

### 11.4 可观测性
- request → decision → emitted result 全链必须可追踪
- 例外放行 / 风险接受必须可单独审计
- emitted result 在 process / work / conversation / runtime 的消费结果应可对账

### 11.5 不可绕过性
- waiting_gate 不是正式结论,因此 process 不得自行 resume 视作“已批准”
- gate turn 不是正式结论,因此 conversation 不得反向成为治理写源
- work / runtime 不得各自内置“默认审批通过”逻辑
- exception / risk acceptance 若缺 acceptor / scope / rationale,必须视为无效

### 11.6 成本
- 不把 artifact 正文和 process/work 状态机整体并入 governance,避免模型膨胀
- 不让下游各仓各自复制审批逻辑,降低长期维护成本

### 11.7 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| RaiseGovernanceRequest | ≤ 100ms | 100ms |
| DecideGate 写路径 | ≤ 150ms | 250ms |
| emitted result 下游通知 | 最终一致 | 不做强一致预算 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| request 与 decision 混层 | 中 | 高 | 在详细设计中继续固定对象边界 |
| waiting_gate 被误当 decision 真相 | 中 | 高 | 固定 process / governance 交互边界 |
| 普通 approve 与 risk acceptance 混层 | 中 | 高 | 单独建模例外裁决部分 |
| 下游仓重新解释 emitted result 造成漂移 | 中 | 高 | 固定统一输出 contract |

### 12.2 边缘风险

- delegated authority 若后续继续扩展,可能引入更复杂责任链模型
- 多级 exception / waiver 叠加后,审计和展示语义会变复杂
- 若 governance 同时接更多域的高风险动作,request 分类可能继续细分

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| risk acceptance 是否必须显式带 expiry / scope | 03 阶段 | governance + TL |
| request change 与 reject 的边界是否继续细分 | 03 阶段 | governance |
| delegated authority 是否允许多级委托 | 03 阶段 | governance + identity |
| 多 approver 关系是 all-of / any-of / ordered chain 哪一种 | 03 阶段 | governance |
| evidence 不足时默认是 request change、reject 还是保持 waiting | 03 阶段 | governance + artifact |
| exception / waiver / risk acceptance 三者是并列关系还是层级关系 | 03 阶段 | governance |
| process 在长时间未收到 decision 时的兜底策略是继续等待还是人工升级 | 03 阶段 | governance + process |

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在单项目样板中只验证最小 Gate 主线,即 `raise request → approve/reject → emitted result`
- **阶段 2**: 再接 `waiting_gate → decision → process resume` 与 `work lifecycle gate result` 两条主接缝
- **阶段 3**: 再接 conversation gate turn / decision notification,验证“正式结论”和“人类可见消息”分层成立
- **阶段 4**: 最后引入 exception / waiver / risk acceptance 等复杂裁决路径,验证受控例外继续执行

### 13.2 回滚策略
- 若 decision 主模型不稳,先回退到“只保留 request + minimal approve/reject”的保守路径
- 若 emitted result 接缝不稳,先保留治理真相与审计链,暂停自动下游传播
- 若 conversation notification 链不稳,只暂停 gate turn / decision notification,不影响正式 decision 真相
- 若例外裁决语义不稳,先关闭 waiver / risk acceptance 自动路径,退回人工明确放行
- 若 delegated authority 规则不稳,先收紧为“只允许直接 approver”模型

### 13.3 监控指标
- governance request 创建成功率
- decision 写入成功率
- request → decision 延迟
- emitted result 漂移率
- exception / risk acceptance 使用频率与失败率

## 15. 结论

本概要设计的核心结论是:
- `L1-governance` 是治理决策真相层,不是流程仓、消息仓或项目状态扩展仓
- `L1-governance` 内部应按“治理请求与 Gate 主语部分 / 决策与裁决真相部分 / 责任链与审批关系部分 / 例外、豁免与风险接受部分 / 治理审计与下游通知接缝部分”来理解,而不是按对象平铺理解
- `process` 管等待治理的时机,`governance` 管正式结论,`artifact` 管证据正文,`conversation` 管人类可见通知,`work/runtime` 消费治理结果
- Gate turn 不是 Gate 真相,waiting_gate 不是 decision 真相, evidence ref 不是治理正文真相
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把对象模型、决策流、责任链、例外裁决和 emitted result 接缝正式化

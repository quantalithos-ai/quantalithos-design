## 1. 模块职责描述

**本模块做什么**:
- 持有正式 GovernanceRequest / Gate / Decision / Exception / RiskAcceptance 真相
- 校验 approver chain / delegated authority / eligibility
- 基于 evidence refs、rationale 与治理规则形成正式结论
- 把 emitted result 分发给 process / work / conversation / runtime,并保留完整审计链

**本模块不做什么**:
- 不持有 `Project` / `WorkItem` / `ProcessInstance` / `Artifact` 正文 / `Conversation` / `Turn` / `GlobalMember` 真相
- 不直接承担 conversation 卡片展示和前端渲染
- 不承担 runtime 内部执行正文与 process 内部控制流正文

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 governance“为什么存在”,而是让开发者可以直接开始实现:
- request / gate subject 如何进入治理
- decision / rationale / adopted basis 如何落成正式真相
- approver chain / delegated authority 如何校验
- risk acceptance / waiver / exception 如何与普通 approve 分层
- emitted result / audit trail 如何向下游输出

如果不先把这些内容采集清楚,03 很容易退化成:
- 把 governance 写成 process waiting_gate 的附属说明
- 把 governance 写成 conversation gate turn 的后端来源说明
- 按对象平铺,但看不见治理主线是怎么跑的
- 把 evidence refs 和 artifact 正文混层

必须测:

### 4.1 总流程图

```text
[gated action / waiting_gate / evidence / actor capability input]
```

### 4.2 总解释

- **真相写入**发生在: GovernanceRequest、Decision、RiskAcceptance、AuditEntry 的正式持久化

- **例外裁决**发生在: normal no 分支进入 waiver / exception / risk acceptance
- **对外输出**发生在: emitted result 向 process / work / conversation / runtime / observability 下发
- **同步路径**主要是: RaiseGovernanceRequest / DecideGate / RecordRiskAcceptance 主写链
- **异步最终一致**主要是: emitted result 下游消费、conversation 通知、audit 投影与 replay

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `Request / Decision / Gate / RiskAcceptance` 四五个对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与事件
- 最后再进入横向的对象模型、流程、存储、审计、异常与测试细节

这样可以避免:
- `02` 讲的是 request / decision / responsibility / exception / emitted result,`03` 却只剩字段表
- 实现者知道有 Decision,却不知道它归哪个责任单元控制
- emitted result、audit、request-change 这几条链路脱节

### 5.2 `治理请求与 Gate 主语部分` 的实现要点

- 承接 `governance` 与 `work/process/runtime/artifact` 的交互链
- 承接“request ≠ decision”“waiting_gate ≠ decision”两条硬边界

```text
│ work / process / runtime   │
│ - gated action             │
│ - waiting_gate             │
```

#### 5.2.3 涉及的对象定义

```rust
/// 表示一次正式进入治理的请求,它是 Decision 的输入锚点,不是 Decision 本身。
pub struct GovernanceRequest {
    /// 治理请求的唯一标识。
    pub request_id: GovernanceRequestId,
    /// 这次治理请求对应的 Gate 主语。
    pub gate: Gate,
    /// 当前请求的状态。
    pub status: GovernanceRequestStatus,
    /// 被治理对象的稳定引用。
    pub target_ref: GovernanceTargetRef,
    /// 发起治理请求的来源动作。
    pub request_kind: GovernanceRequestKind,
    /// 请求方给出的理由摘要。
    pub reason: String,
    /// 本次请求关联的证据引用集合。
    pub evidence_refs: Vec<EvidenceRef>,
}

/// 表示一个治理 Gate,它定义这次治理动作的边界与阶段。
pub struct Gate {
    /// Gate 的唯一标识。
    pub gate_id: GateId,
    /// Gate 的分类,例如 kickoff / archive / aiia / override 等。
    pub gate_kind: GateKind,
    /// 当前 Gate 的状态。
    pub status: GateStatus,
    /// 谁创建了这个 Gate 请求。
    pub raised_by: ActorRef,
}

/// 表示这次治理请求针对的正式业务对象引用。
pub struct GovernanceTargetRef {
    /// 关联的项目引用。
    pub project_ref: Option<ProjectRef>,
    /// 关联的工作项引用。
    pub workitem_ref: Option<WorkItemRef>,
    /// 关联的流程等待点引用。
    pub waiting_gate_ref: Option<WaitingGateRef>,
    /// 关联的运行时操作引用。
    pub runtime_operation_ref: Option<RuntimeOperationRef>,
}
```

这些对象在该部分里分别承担:
- `GovernanceRequest` 回答“这次治理到底在审什么”
- `Gate` 回答“这是一类什么治理入口,现在处于什么治理阶段”
- `GovernanceTargetRef` 负责把 request 稳定锚到外部域对象上,但不把外部真相带进来

#### 5.2.4 关键函数代码片段

```rust
/// 把上游输入收束成一个正式 GovernanceRequest。
fn raise_governance_request(request_repo: &dyn GovernanceRequestRepo, input: GovernanceRequestInput) {
    // [GovernanceRequest::从输入创建]
    // 先把 work/process/runtime/artifact 输入收束成正式 request 对象。
    let request = GovernanceRequest::from_input(input);

    // [request.校验可进入治理]
    // 再校验 target ref、request kind 与 evidence refs 的最小成立条件。
    request.validate_enter_governance();

    // [request_repo.保存请求]
    // 最后把治理请求写入正式真相层,供后续 decision 与 audit 使用。
    request_repo.save(request);
}
```

这段实现守住的边界是:
- request 与 decision 是两步,不能合并成一步
- waiting_gate 只是 request 输入来源之一,不是 decision 本体
- target ref 只是锚点,不会把 project / process / runtime 正文拉进 governance

#### 5.2.5 该部分的边界与非职责
- 不负责形成正式 approve / reject / request change 结论
- 不负责计算 approver eligibility
- 不负责 conversation 通知输出
- 不持有 artifact 正文本体

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `责任链与审批关系部分` 提供被审对象与 request context
- 向 `决策与裁决真相部分` 提供 request 和 evidence refs
- 向 `治理审计与下游通知接缝部分` 提供 request lifecycle 事件

#### 5.2.7 该部分的状态 / 约束 / 易错点
- request 不能在没有 target ref 的情况下进入治理
- request 进入治理后,其“被审对象是谁”不能漂移
- waiting_gate 来源与 work gated action 来源要统一成治理请求语义,不能分裂为两套模型

#### 5.3.3 涉及的对象定义

```rust
/// 表示一次正式治理结论,它是 governance 的核心真相对象。
pub struct Decision {
    /// 决策的唯一标识。
    pub decision_id: DecisionId,
    /// 本次决策对应的 request。
    pub request_id: GovernanceRequestId,
    /// 正式裁决动作。
    pub action: DecisionAction,
    /// 本次决策的状态。
    pub status: DecisionStatus,
    /// 做出决策的 actor 引用。
    pub decided_by: ActorRef,
    /// 决策形成时间。
    pub decided_at: Timestamp,
    /// 决策依据摘要。
    pub rationale: DecisionRationale,
}

/// 表示治理结论的类型语义。
pub enum DecisionAction {
    /// 正式批准通过。
    Approve,
    /// 正式拒绝。
    Reject,
    /// 要求补件或修改后重新提交。
    RequestChange,
    /// 以豁免方式放行。
    Waive,
    /// 显式接受风险后放行。
    AcceptRisk,
}

/// 表示治理层记录的决策依据。
pub struct DecisionRationale {
    /// 规则层面采用了哪些 basis。
    pub policy_basis: Vec<PolicyBasisRef>,
    /// 证据层面采用了哪些 refs。
    pub adopted_evidence_refs: Vec<EvidenceRef>,
    /// 决策说明文本。
    pub summary: String,
}

/// 表示正式决策状态,用于区分已提交、被替代或撤销等语义。
pub enum DecisionStatus {
    /// 已正式提交并可对外成为 emitted result 来源。
    Committed,
    /// 决策被后续正式治理动作替代,但原记录仍保留审计价值。
    Superseded,
    /// 决策被治理层正式撤销,通常只允许在严格规则下发生。
    Withdrawn,
}
```

这些对象在该部分里分别承担:
- `Decision` 是正式治理结论真相
- `DecisionAction` 负责区分普通 approve/reject 与 waive/accept risk 等例外语义
- `DecisionRationale` 负责把“为什么这么批”固定下来,而不是让下游自己猜
- `DecisionStatus` 负责把“当前这条 decision 还能不能继续作为正式结果来源”写成显式状态

#### 5.3.4 关键函数代码片段

```rust
/// 基于 request、approver 资格和 evidence refs 形成正式治理结论。
fn decide_gate(
    decision_repo: &dyn DecisionRepo,
    request: &GovernanceRequest,
    eligibility: &EligibilityResult,
    rationale: DecisionRationale,
    action: DecisionAction,
) {
    // [eligibility.校验可决策]
    // 先确认当前 actor 在这次 request 上有资格做出这个层级的治理动作。
    eligibility.ensure_can_decide(&action);

    // [request.校验仍可被决策]
    // 再确认 request 还处于待决状态,没有被重复关闭或过期覆盖。
    request.ensure_open_for_decision();

    // [Decision::创建]
    // 最后创建正式 Decision,把 adopted basis 和 action 一起固定下来。
    let decision = Decision::from_request(request, action, rationale);

    // [decision_repo.保存结论]
    // 正式把治理结论写入真相层。
    decision_repo.save(decision);
}
```

这段实现守住的边界是:
- eligibility 先于 decision 写入
- request 必须仍处于待决窗口
- rationale / adopted basis 必须与 decision 一起落库,不能只在消息层出现

#### 5.3.5 该部分的边界与非职责
- 不负责 delegated authority 规则计算
- 不负责 risk acceptance 的额外 scope/expiry 规则
- 不负责下游 emitted result 的传输
- 不负责 audit 投影展示层

- request change 不是 reject 的文案别名,它必须保留“可补件再来”的语义
- waive / accept risk 不得复用普通 approve 的状态和审计字段

```rust
/// 校验某个 actor 在当前治理请求上是否具备正式审批资格。
fn check_approver_eligibility(
    chain: &ApproverChain,
    actor_ref: &ActorRef,
    actor_capability: &ActorCapabilitySnapshot,
) -> EligibilityResult {
    // [chain.校验是否在审批链内]
    // 先看这个 actor 是否属于 required approver 或合法 delegate。
    let in_chain = chain.contains_or_delegates(actor_ref);

    // [DelegatedAuthority::校验是否可代理]
    // 再根据 scope 与有效期判断代理资格是否仍然成立。
    let delegated_ok = chain.delegated_authority.as_ref().map(|d| d.is_valid_for(actor_ref)).unwrap_or(false);

    // [ApproverChain::生成资格结果]
    // 最后结合 capability 快照返回正式 eligibility result 给决策层使用。
    ApproverChain::build_eligibility_result(in_chain, delegated_ok, actor_capability)
}
```

这段实现守住的边界是:
- identity 提供 capability 输入,但不直接告诉 governance“你就能批”
- governance 自己根据 approver chain 与 delegation 规则形成 eligibility 结论
- required approver 不全时,不能偷懒落普通 approve

#### 5.4.5 该部分的边界与非职责

- 不负责持有 actor 身份主真相

- 不负责 evidence adoption 本体

#### 5.4.6 该部分与其他主要部分的接缝
- 从 identity 消费 capability / actor refs
- 向 `决策与裁决真相部分` 提供 eligibility result
- 向 `例外、豁免与风险接受部分` 提供 acceptor / delegate 的合法性判定

#### 5.4.7 该部分的状态 / 约束 / 易错点

```rust
/// 记录一次正式风险接受,并校验其边界是否完整。
fn record_risk_acceptance(
    risk_repo: &dyn RiskAcceptanceRepo,
    eligibility: &EligibilityResult,
    request: &GovernanceRequest,
    acceptance: RiskAcceptance,
) {
    // [eligibility.校验可承担风险]
    // 先确认当前 actor 有资格代表该责任链承担风险。
    eligibility.ensure_can_accept_risk();

    acceptance.validate_boundary();

    risk_repo.save(request.request_id, acceptance);
```

```rust
/// 把正式治理结论统一打包后输出给下游仓消费。
fn emit_decision_result(
    publisher: &dyn DecisionResultPublisher,
    audit_repo: &dyn GovernanceAuditRepo,
    decision: &Decision,
    target_ref: &GovernanceTargetRef,
) {
    // [DecisionResultEnvelope::从决策创建]
    // 先把 decision 转成统一 emitted result,避免下游各自解释同一结论。
    let result = DecisionResultEnvelope::from_decision(decision, target_ref);

    // [publisher.发布治理结果]
    // 再把这份统一结果发给 process / work / conversation / runtime 等消费方。
    publisher.publish(result);

    // [audit_repo.追加审计记录]
    // 最后把这次 emitted result 行为写入治理审计链。
    audit_repo.append_emission(decision.decision_id);
}
```

这段实现守住的边界是:
- governance 自己统一 emitted result 语义
- conversation gate turn / process resume / work lifecycle result 都消费同一个正式源
- emitted result 行为本身也必须被审计

#### 5.6.5 该部分的边界与非职责
- 不负责下游仓内部状态迁移细节
- 不负责重新决定 formal decision
- 不负责 artifact 证据解释正文
- 不负责前台 UI 组件与消息渲染

#### 5.6.6 该部分与其他主要部分的接缝
- 从 `决策与裁决真相部分` 接收 formal decision
- 从 `例外、豁免与风险接受部分` 接收 exception / risk acceptance 补充语义
- 向 process / work / conversation / runtime 发布统一结果
- 向 observability / archive 追加审计链

#### 5.6.7 该部分的状态 / 约束 / 易错点
- emitted result 不得被下游各自再发明一层语义
- conversation notification 只是人类可见层,不得替代 audit 真相
- process resume / work continue / runtime allow 这些动作必须可对账到同一个 decision_id

#### 写路径

```text

   │

   │
   ▼

   │
   ▼
```

```text

   │
   ▼
```

### 7.6 关键状态机 / 非法转换与约束

#### 状态机图

```text
GovernanceRequest:
pending → under_review → closed
pending → closed(reject)
pending → closed(request_change)

Decision:
committed
  ├─ approve
  ├─ reject
  ├─ request_change
  ├─ waive
  └─ accept_risk
  │
  └─ superseded / withdrawn (严格受控)

RiskAcceptance:
created → active → expired
created → revoked(严格受控)
```

#### 非法转换与约束表

| 场景 | 是否允许 | 说明 |
|---|---|---|
| waiting_gate 直接充当 Decision | ❌ | 必须通过 governance 正式落 decision |
| conversation gate turn 直接充当 Decision | ❌ | 通知层不能替代真相层 |
| evidence ref 为空时直接普通 approve | ❌ | 至少要满足治理规则的最小 basis |
| 无资格 actor 直接 DecideGate | ❌ | 必须先过 eligibility |
| 缺 acceptor/scope 的 risk acceptance | ❌ | 风险接受边界不完整 |
| request 已 closed 后再次正式决策 | ❌ | 避免重复关闭或多版本漂移 |
| required approver 不全时直接 approve | ❌ | 必须满足审批链闭合 |
| exception / waiver 缺 rationale 就落库 | ❌ | 例外裁决必须可解释 |
| superseded decision 继续作为 emitted result 来源 | ❌ | 统一结果必须只来自当前有效 decision |
| expired risk acceptance 继续被下游当作有效 | ❌ | 过期后只能作为历史审计记录 |

#### 关键约束说明

- `GovernanceRequest.closed` 后,只能查询、审计、回放,默认不允许再次进入正常决策写路径
- `DecisionStatus.superseded` 只表示“被更新结论替代”,不表示原记录可删除
- `DecisionStatus.withdrawn` 只能由受控治理动作触发,不得被下游仓自由改写
- `RiskAcceptance.active → expired` 代表受控例外失效,不等于历史记录被删除

## 11. 运行期主线场景

### 11.1 场景 A · waiting_gate 进入治理并恢复 process

```text
process 进入 waiting_gate
      │
      ▼
governance 建立 request
      │
      ▼
校验 approver chain / evidence refs
      │
      ▼
形成 approve / request_change / reject decision
      │
      ▼
发 emitted result
      │
      ▼
process resume / remain suspended / block
```

**开发者关注点**:
- waiting_gate 只代表“等治理”,不代表正式结论
- process resume 必须能回溯到唯一 decision_id
- conversation 通知延迟不影响正式 decision 主链

### 11.2 场景 B · artifact 证据不足导致 request change

```text
gated action raised
      │
      ▼
governance request created
      │
      ▼
读取 evidence refs
      │
      ▼
判定 basis 不足
      │
      ▼
形成 request_change decision
      │
      ├─ work/process 保持等待或退回补件
      └─ conversation 显示补件通知
```

**开发者关注点**:
- evidence ref 到了不等于证据充分
- request_change 不得退化成 reject 文案
- adopted basis 与 artifact 正文本体必须保持分层

### 11.3 场景 C · 风险接受后受控继续

```text
normal rule says no
      │
      ▼
risk acceptance request raised
      │
      ▼
校验 acceptor / scope / expiry / rationale
      │
      ▼
生成 accept_risk decision + risk acceptance record
      │
      ▼
emit controlled continue result
      │
      ▼
work/process/runtime 在受控例外下继续
```

**开发者关注点**:
- risk acceptance 不是普通 approve
- acceptor / scope / expiry 缺一不可
- 下游必须能识别“这是例外继续,不是普通放行”

### 11.4 场景 D · emitted result 漂移后的对账与 replay

```text
formal decision committed
      │
      ▼
emitted result 已发出
      │
      ▼
某个下游仓未消费 / 误消费
      │
      ▼
governance 读取 audit + emission history
      │
      ▼
发现 drift
      │
      ▼
生成 replay emitted result
      │
      ▼
下游重新对齐到同一 decision_id
```

**开发者关注点**:
- replay 修复的是 emitted result 传播链,不是重新发明新 decision
- drift 对账必须能回到 request / decision / emission 三段正式链
- replay 后下游状态必须能继续回溯到原始 decision_id

### 11.5 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| work gated action | RaiseGovernanceRequest | 治理请求与 Gate 主语部分 | governance request |
| process waiting_gate | RaiseGovernanceRequest | 治理请求与 Gate 主语部分 | waiting request |
| approver action | DecideGate | 决策与裁决真相部分 | formal decision |
| exception / risk request | RecordRiskAcceptance / waiver flow | 例外、豁免与风险接受部分 | controlled exception |
| downstream publish | EmitDecisionResult | 治理审计与下游通知接缝部分 | emitted result + audit |

## 13. 读模型与投影设计

### 13.1 总体结构

```text
GovernanceRequest / Decision / Exception write model
   │
   ▼
projection builders
   ├─ pending request summary
   ├─ decision history
   ├─ notification material
   └─ audit replay material
```

### 13.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| PendingRequestSummary | GovernanceRequest + Gate + status | 待处理治理清单 |
| DecisionHistoryView | Decision + Rationale + AuditEntry | 历史回放 |
| DecisionNotificationView | DecisionResultEnvelope + target refs | conversation 通知输入 |
| AuditReplayMaterial | Request/Decision/Emission/Audit chain | 审计与重放材料 |

### 13.3 一致性说明

- 读模型允许最终一致
- pending summary / history / notification view 都只读
- `DecisionHistoryView` 服务“看治理历史”,`AuditReplayMaterial` 服务“重建治理链路”,两者不能混成同一视图
- `DecisionNotificationView` 只提供给 conversation 的人类可见输入材料,不能反向成为正式 decision 真相
- emitted result 状态记录可用于 drift 检测与 replay,但不能替代 request / decision 正式真相
- audit replay material 必须始终可回到 request / decision / emission / audit 四段正式链
- rebuild 顺序必须是: reset read model → replay request/decision/emission/audit truth → regenerate pending/history/notification views

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| 无资格 approver 尝试决策 | 直接拒绝 |
| evidence 不足 | request change / waiting / reject |
| emitted result 发送失败 | 重试发射,不回滚 decision 真相 |
| audit 投影损坏 | 以 append-only 审计链重建 |

### 14.1 重试 / 降级 / 熔断 / 补偿
- emitted result 失败允许只保留正式 decision 真相,输出异步补发
- audit / pending summary 失败允许暂时返回陈旧视图,后台重建
- identity capability 查询失败时默认保持 pending / restricted,不允许默认放行
- evidence 不足时默认走 request_change / waiting / reject 分支,不得静默 approve
- emitted result 漂移时必须以 request / decision / emission / audit 四段链做对账,必要时 replay
- replay 只能修复传播链,不能伪造一个新的 decision 替代历史真相

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 治理请求与 Gate 主语部分 | request 重复 / target ref 缺失 | request log | 拒绝或去重 | replay request input |
| 决策与裁决真相部分 | decision 重复提交 / basis 不足 | decision trace | 阻断提交 / request change | replay decision attempt |
| 责任链与审批关系部分 | actor 越权 / delegate 失效 | eligibility log | 拒绝决策 | refetch identity capability |
| 例外、豁免与风险接受部分 | acceptor/scope 缺失 | risk acceptance validation | 拒绝记录 | replay after fix |
| 治理审计与下游通知接缝部分 | emitted result 丢失 / 下游未消费 | emit lag 指标 | 重试 / 对账 | replay emitted result |

---

## 15. 实现红线 / 开发禁止事项

- 不允许让 waiting_gate 直接充当正式 decision 真相
- 不允许让 gate turn / notification 替代 governance 主真相
- 不允许把 artifact 正文整体并入 governance,只允许 evidence refs / adopted basis
- 不允许让 work / runtime 各自内置审批通过逻辑绕过 governance
- 不允许把 risk acceptance 写成普通 approve 的附加备注
- 不允许把 `request_change` 简化成 `reject` 的文案别名
- 不允许在 adopted basis 未形成前写出普通 approve
- 不允许让 superseded / withdrawn decision 继续作为 emitted result 来源

## 17. 最小可运行闭环

- process waiting_gate 发起一个治理 request,经过 eligibility 与 evidence 校验后生成 formal decision,再把 resume 结果发回 process
- work 某个 gated lifecycle action 发起 request,经 governance approve 后发出 lifecycle gate result
- 一次 risk acceptance 被正式记录,并把 controlled continue 结果发给 runtime / work / process

## 18. 结论

本详细设计的核心结论是：
- `L1-governance` 的实现必须围绕五个主要部分展开,而不是按对象平铺
- GovernanceRequest / Decision / RiskAcceptance 是正式真相,DecisionResultEnvelope / notification / history view 都是派生或输出层
- identity / work / process / artifact / runtime 的输入都必须先经过治理请求、责任链和裁决层收口,再由 governance 统一输出正式结果
- 后续测试与验收文档,应直接围绕 request/decision 分层、eligibility、exception 边界、emitted result 一致性和不可绕过性展开

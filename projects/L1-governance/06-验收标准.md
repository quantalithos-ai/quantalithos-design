### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L1-governance` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L1-governance` 是治理决策真相仓,不是流程仓、消息仓或项目状态扩展仓
- GovernanceRequest / Gate / Decision / RiskAcceptance 构成正式治理真相层
- `request ≠ decision`、`waiting_gate ≠ decision`、`gate turn ≠ decision` 三条核心边界必须成立
- approver chain / delegated authority / eligibility 构成正式审批资格约束
- `exception / waiver / risk acceptance` 必须独立成立,不能退化成普通 approve
- emitted result 必须由 governance 统一输出,process / work / conversation / runtime 消费同一正式结论语义

因此,本次验收的目的不是笼统判断“有没有审批接口”,而是判断 governance 的请求层、决策真相层、责任链层、例外裁决层和审计输出层是否真的边界清晰、不可绕过、可追溯并能统一约束下游。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| 治理请求与 Gate 主语部分 | 是 | request、Gate、target ref、request 状态 |
| 决策与裁决真相部分 | 是 | approve / reject / request_change / waive / accept_risk |
| 责任链与审批关系部分 | 是 | approver chain、delegated authority、eligibility |
| 例外、豁免与风险接受部分 | 是 | risk acceptance / waiver / exception |
| 治理审计与下游通知接缝部分 | 是 | emitted result、audit trail、drift/replay |
| conversation 通知展示细节 | 否 | 只验 notification input,不验 UI 表现 |
| artifact 正文语义充分性本体 | 否 | 只验 governance 如何消费 refs,不验 artifact 内部正文逻辑 |
| process / work / runtime 内部状态机正文 | 否 | 只验 governance 输出结果接缝,不验下游全部内部实现 |

## 4. 功能验收门禁

| 功能/场景 | 门禁条件 | 证据 | 结论 |
|---|---|---|---|
| RaiseGovernanceRequest | 合法 target ref + request kind 输入后必须形成正式 request 与 Gate 主语 | API 响应 / DB 记录 / audit entry | [] |
| CheckApproverEligibility | approver chain / delegation / capability 校验必须正确判断 actor 能否决策 | eligibility trace / rule log | [] |
| DecideGate(approve/reject/request_change) | request 必须先存在且仍待决,再独立形成 formal decision | decision 记录 / request state / audit chain | [] |
| waiting_gate → decision 边界 | `waiting_gate` 只能代表等待时机,不得替代正式 decision 真相 | process trace / negative test / decision compare | [] |
| gate turn → decision 边界 | conversation 里的 gate turn 只能是通知,不得替代 decision 真相 | notification trace / decision record | [] |
| evidence ref → adopted basis 边界 | evidence ref 必须只是引用,正式 adopted basis 必须在 rationale 中被明确采纳 | rationale / evidence refs / compare | [] |
| RequestChange | evidence 不足时必须能形成 request_change,而不是退化成 reject 或静默通过 | decision(action=request_change) / audit log | [] |
| RecordRiskAcceptance | risk acceptance 必须显式带 acceptor / scope / expiry / rationale | risk_acceptance record / audit trace | [] |
| RecordWaiver / Exception | waiver / exception 必须独立成立,不混同普通 approve | exception record / decision action / trace | [] |
| EmitDecisionResult | process / work / conversation / runtime 必须消费统一 emitted result 语义 | emitted result compare / downstream traces | [] |
| ReplayGovernanceAuditTrail | drift 发生后必须能基于 request / decision / emission / audit 链 replay 并修复一致性 | replay log / before-after compare | [] |

| 门禁项 | 要求 | 证据 | 结论 |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | request/decision 混层 / waiting_gate 替代 decision / risk acceptance 边界失效 / 下游绕过 governance |
| A | 视情况 | 主线可跑但 emitted result / audit / delegation / evidence 分支不稳 |
| B | 可带着走 | 非关键历史视图、通知材料或低优先级查询异常 |

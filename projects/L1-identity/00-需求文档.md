本文讨论的主题是:上游“AI 员工是有身份的个体”这一产品承诺在 `L1-identity` 仓中的需求收束方式。本文不重新定义 AI 员工、六域模型或仓库分层,只把已成立的身份域主题整理成仓级需求边界、核心能力和验收口径。

本文的需求真相源优先级如下:

1. 产品与全局架构文档只提供身份域存在的上位理由和分层边界。
2. 本文只定义 `L1-identity` 在需求层必须回答的问题、能力和验收口径。
3. 旧版 identity 设计文档只作为历史输入,不得反向约束新版需求结论。
4. 后续 `01~07` 文档必须从本文和对应 `design-calibration/00_req_step_*` 中间产物继续推导,不得直接继承旧对象、旧接口、旧事件或旧技术栈。

因此,本文不是实现规格,也不是旧 identity 方案的压缩版。它的作用是先把“身份真相归谁、边界在哪里、哪些能力必须成立、哪些东西不得进入 identity”讲清楚,让后续架构、概要、详细、测试、验收和实施计划能沿同一条需求主线展开。

## 2. 本仓定位与边界

> 校准来源:
> - `design-calibration/00_req_step_02_position_boundary.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“当前文档问题诊断”“结构化中间产物”和“边界说明”小节,了解旧口径如何被裁剪。

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L1-identity` 是平台级 AI 员工身份真相仓。 |
| 本仓不是什么 | 它不是认证系统、授权裁决系统、ProjectMember 管理仓、RoleDefinition 正文仓、memory/archive 正文仓、runtime 容器编排仓或 UI 展示仓。 |
| 边界对象列表 | 层：认证 / ActorContext;仓：`L1-work`;仓：`L3-method-library`;仓：`L2-member-service`;能力：memory / archive 正文;仓：`L1-workspace` / UI 展示 |
| 单独成仓原因 | 平台需要一个独立于项目、运行实例、对话和外部正文的成员身份真相,让 AI 员工可以长期存在、被稳定引用和被审计。 |

`L1-identity` 单独存在,是因为平台级成员身份必须独立于某个项目、某次运行或某段对话。它与 `L1-work` 的边界是 GlobalMember 与 ProjectMember 的分层,与 `L3-method-library` 的边界是成员身份侧角色引用和角色定义正文的分层,与认证 / runtime / memory 的边界是“身份真相”和“登录校验 / 执行实例 / 外部正文”的分层。

### 2.1 边界判定口径

判断某个能力是否属于 `L1-identity`,优先回答以下问题:

| 判定问题 | 落入 identity 的情况 | 不落入 identity 的情况 |
|---|---|---|
| 它是否回答“这个 AI 员工是谁” | 建立、读取、追溯平台级成员身份主语 | 登录认证、credential 校验、session 管理 |
| 它是否影响成员全局可用性 | 暂停、退役、墓碑化等全局身份生命周期 | 项目内成员状态、runtime 容器状态、任务执行状态 |
| 它是否解释成员的身份侧职业 / 能力 | 保存角色来源引用、能力摘要、证据引用 | 编辑方法正文、维护能力定义正文、自动评分算法 |
| 它是否记录成员长期经历的身份侧事实 | 追加生涯记录、保存 memory refs、记录迁移引用状态 | 保存项目 truth、work item truth、memory 原文或向量 |
| 它是否帮助相邻仓消费身份事实 | 提供身份锚点、状态摘要、变化追溯和对账摘要 | 让相邻仓反写 identity truth 或共享数据库事务 |

边界裁剪的核心不是“某个功能看起来和成员有关就归 identity”,而是“该功能是否需要 identity 拥有平台级成员身份真相”。例如 ProjectMember 与成员有关,但它回答的是“成员在某个项目中承担什么”,因此归 `L1-work`;RoleDefinition 与成员能力有关,但它回答的是“角色 / 方法定义是什么”,因此归 `L3-method-library`;memory 与成员成长有关,但正文和向量不是身份真相,identity 只保存引用。

## 3. 背景与问题定义

> 校准来源:
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“业务背景”“现状与问题”和“业务问题 vs 技术问题”小节,了解问题如何从旧文档中重新裁剪。

Quantalithos 的产品叙事要求 AI 员工像真实员工一样跨项目长期存在,并拥有身份、职业、能力、记忆和生涯轨迹。随着平台进入多项目、多成员、多仓协作,成员身份必须能被稳定引用和审计,因此需要把身份主题独立收束为 `L1-identity` 的仓级需求。

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 平台级成员身份缺少新版需求闭口 | 旧文档直接混合需求、概要、详细设计和实现口径 | 后续 01~07 会继续继承旧口径,实现 agent 难以判断什么是需求真相 |
| GlobalMember 与 ProjectMember 容易混层 | 旧文档中同时讨论平台成员、项目成员、角色、职业和任务承担 | `L1-work` 与 `L1-identity` 的 truth 边界会漂移 |
| 身份真相与外部定义 / 正文 / 运行实例容易混层 | RoleDefinition、memory、runtime、认证主体都可能被写入 identity 主职责 | method-library、archive/memory、member-service、认证层会被错误拉入 identity |

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台需要统一回答“这个 AI 员工是谁、是否可用、是什么职业和能力、有哪些生涯和记忆引用”,否则管理者无法稳定管理 AI 员工队伍。 |
| 技术问题 | 若需求层不先区分 GlobalMember / ProjectMember、RoleDefinition / identity role summary、memory body / memory ref、runtime instance / member identity,后续对象契约、接口、事件和测试都会无法 1:1 落码。 |

### 3.1 需要解决的需求断裂

Identity 的需求断裂主要体现在三个层面:

| 断裂点 | 具体表现 | 需求层必须给出的答案 |
|---|---|---|
| 主语断裂 | 同一个 AI 员工可能被项目、对话、runtime 或外部记录以不同方式引用 | 谁拥有稳定、不可复用的成员身份锚点 |
| 边界断裂 | 角色、项目成员、记忆、审计和运行信息都可能被误写进 identity | 哪些数据是 identity truth,哪些只是引用,哪些禁止保存正文 |
| 消费断裂 | 下游仓需要成员状态和摘要,但不应绕过身份真相边界 | identity 对外提供哪些能力级消费面和追溯面 |

如果这些问题不在需求层先收束,后续设计很容易把 identity 做成“成员相关所有信息的容器”。这会导致仓际职责扩张、运行期依赖变成编译期依赖、外部正文泄漏、生命周期和项目状态混层,最终让实现 agent 无法判断哪些对象、字段、port 和测试是真正必要的。

## 4. 目标与非目标

> 校准来源:
> - `design-calibration/00_req_step_04_goals_non_goals.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“目标表”“非目标表”和“待确认事项”小节,了解目标与后移事项的边界。

| 目标 | 说明 | 验证方式 |
|---|---|---|
| G-ID-001 建立平台级成员身份真相边界 | 明确 identity 管的是长期存在的 AI 员工身份,不是认证主体、项目成员或运行实例 | 后续章节不再把认证、ProjectMember 或 runtime instance 写入 identity truth |
| G-ID-002 收束成员生命周期需求范围 | 明确成员从建档、可用、暂停、退役到墓碑化的需求主题和风险边界 | 生命周期相关故事、功能、规则和验收均能稳定落在 identity |
| G-ID-003 收束角色与能力身份侧需求 | 明确 identity 只承载成员身份侧角色引用、可用性摘要和能力画像,不拥有方法定义正文或评估算法 | 角色能力相关数据归属不保存 method body 或评估模型 |
| G-ID-004 收束生涯与记忆引用需求 | 明确 identity 可保存成员生涯轨迹和 memory refs,但不拥有项目真相、记忆正文或向量 | 数据归属表能区分 career truth、外部 truth ref 和禁止正文 |
| G-ID-005 支撑身份事实消费与追溯 | 明确相邻仓可以稳定消费成员摘要、状态变化、身份引用和审计追溯 | 接口与依赖、验收标准覆盖消费边界和追溯边界 |

| 非目标 | 不做原因 |
|---|---|
| 登录、token、session、credential 校验 | 属于认证入口或 gateway / API layer,不是成员身份真相。 |
| 授权裁决和高风险决策真相 | 属于 governance 或安全入口,identity 只消费授权 / 治理结论。 |
| ProjectMember 和项目内角色分配 | 属于 `L1-work`,identity 只提供 GlobalMember 身份锚点。 |
| RoleDefinition / CapabilityDefinition 正文 | 属于 `L3-method-library`,identity 只保存身份侧引用和摘要。 |
| memory 原文、向量、检索索引和 archive package | 属于 memory / archive / artifact 等外部或相邻承载方。 |
| runtime 容器、工具执行和成员进程编排 | 属于 `L2-member-service`、`L2-runtime` 和工具层。 |
| Conversation / Console / Workspace UI 展示状态 | 属于 conversation、workspace 和 L5 产品层。 |
| 数据库、框架、消息总线实现和代码目录 | 属于架构、详细设计和实施计划,不进入需求目标。 |

### 4.1 目标之间的闭环关系

这些目标不是平铺清单。`G-ID-001` 先确认平台级成员身份主语,`G-ID-002` 让该主语具备可用性边界,`G-ID-003` 解释该主语的职业 / 能力含义,`G-ID-004` 体现成员长期存在的生涯和记忆引用,`G-ID-005` 让这些身份事实能被相邻仓消费并被审计。

因此,如果后续某个设计只实现建档和查询,但没有生命周期、角色能力、生涯记忆和消费追溯,它只能算成员目录,不能满足本文定义的 identity 闭环。如果某个设计试图把项目事实、方法正文、运行容器和记忆正文都纳入 identity,则超出目标并违反非目标。

### 5.1 角色边界说明

本文中的“用户”包括人类角色和系统角色,但它们代表的是需求视角,不是认证主体模型。平台管理员、组织 / 项目管理者、审计者和 AI 员工自身描述的是不同业务目标;系统调用方和后台维护任务描述的是相邻仓或维护流程对 identity 能力的消费方式。

角色边界需要遵守以下口径:

| 角色边界 | 正确理解 | 错误理解 |
|---|---|---|
| 平台管理员 | 可发起身份建档、生命周期和角色能力维护 | 可以绕过治理 / 授权约束处理高风险生命周期 |
| 组织 / 项目管理者 | 可读取可见身份摘要并发起相关请求 | 可以直接维护 GlobalMember truth 或 ProjectMember truth |
| AI 员工自身 | 可读取自身可见身份摘要和部分生涯 / 记忆引用摘要 | 可以自行改写生命周期、能力声明或历史记录 |
| 审计者 | 可读取变化追溯和依据摘要 | 可以修复 truth 或读取外部正文 |
| 系统调用方 | 通过正式边界消费身份事实 | 可以共享 identity 存储或反向写入 identity truth |
| 后台维护任务 | 可对账、重建、发现漂移 | 可以绕过正式能力修复相邻仓 truth |

这些边界会在后续用户故事、功能需求、业务规则、数据归属和验收标准中反复出现。只要某个场景需要“绕过正式边界直接改写身份真相”,它就不是本文允许的角色能力。

## 6. 使用方与依赖

> 校准来源:
> - `design-calibration/00_req_step_06_consumers_dependencies.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“内部仓依赖表”“依赖裁剪表”“禁止依赖表”和“依赖裁剪图”小节,了解依赖类型裁剪。

| 方向 | 对方 | 提供 / 依赖内容 | 是否闭环前置 | 失效影响 |
|---|---|---|---|---|
| 输入 | `L0-core` | 共享 identity、actor、trace、error、metadata 等基础契约 | 是 | 无法形成跨仓可识别身份引用 |
| 协作 | `L0-bus` | 身份变化、角色能力变化和生涯变化的事件协作主干 | 是 | 相邻仓无法及时消费身份事实变化 |
| 输入 | `L3-method-library` | 角色 / 能力定义来源和版本语义 | 是,对角色能力闭环 | 角色能力摘要无法稳定校验或对账 |
| 输入 | `L1-work` | 项目参与、生涯追加和 ProjectMember 分层来源 | 是,对生涯闭环 | career history 无法由正式项目事实支撑 |
| 输入 | `L1-governance` | 高风险生命周期处置或授权约束的治理结论 | 否,但阻塞高风险处置 | 高风险生命周期动作只能暂停或进入待审 |
| 输出 | `L1-work` | GlobalMember 身份锚点和成员状态摘要 | 是 | work 无法稳定建立 ProjectMember 与平台成员分层 |
| 输出 | `L1-process` | actor / participant 身份摘要和可追溯成员引用 | 否 | process 只能降级为 opaque actor ref,可读性和追溯受限 |
| 输出 | `L1-conversation` | 成员显示身份、参与者摘要和身份变化 | 否 | 对话显示和成员上下文会降级或延迟 |
| 输出 | `L1-governance` | actor responsibility chain 所需成员身份引用 | 否,但影响治理追溯 | 治理证据中成员身份链不完整 |
| 输出 | `L1-workspace` | 成员视图、inbox 和跨项目身份摘要 | 否 | workspace 视图无法显示稳定成员上下文 |
| 输出 | `L2-member-service` / `L2-runtime` | 成员生命周期、角色能力摘要和可运行性信号 | 否 | 运行编排无法稳定响应身份变化 |
| 输出 | `L4-archive` / `L4-observability` | 身份追溯、归档触发和审计引用 | 否 | 冷存、审计和追溯材料不完整 |
| 输出 | `L0-sdk` / L5 产品 | 对外封装的成员查询和管理能力 | 否 | UI / 生态只能绕开 SDK 或暂不可用 |

当前需求阶段不把具体数据库、消息后端、向量库、审计平台或外部身份提供商写成正式外部系统依赖。它们可能在架构、配置或实施阶段成为 adapter / profile 选型,但不构成 `00-需求文档.md` 的核心能力前置。

- 箭头表达依赖 / 消费 / 协作方向,不表达调用顺序或事件时序。

### 6.1 依赖裁剪原则

`L1-identity` 的依赖裁剪遵循“身份真相最小化”原则。它可以消费外部来源,也可以向外提供身份事实,但不能因为需要协作就把相邻仓对象、正文、表结构或运行状态纳入自身真相。

| 依赖类型 | 需求层含义 | 后续设计约束 |
|---|---|---|
| 编译期依赖 | 本仓需要共享基础 ref、actor、trace、error、metadata 等契约 | 当前只允许 `L0-core` 作为候选;不得引入 L1/L2/L3 业务仓循环依赖 |
| 运行期依赖 | 本仓在业务能力执行时需要读取或校验外部来源 | 必须通过正式边界表达,不得共享数据库事务或假设外部内部表结构 |
| 事件协作 | 本仓与相邻仓通过变化事实协作 | 事件只传递可公开消费的身份事实或引用,不得携带外部正文 |
| 下游消费 | 相邻仓读取或订阅 identity 提供的身份摘要 | 下游只能消费,不能反向定义 identity truth |
| 降级协作 | 外部依赖不可用时保留核心身份锚点能力 | 降级不能伪造角色能力、生涯、记忆或治理结论 |

这意味着 identity 的闭环前置不是“所有相邻仓都必须实现完毕”。C-ID-1 和 C-ID-2 需要在外围依赖不可用时仍然有明确需求口径;C-ID-3、C-ID-4 和 C-ID-5 则需要在来源缺失、来源不可见或来源变化时给出更新、失效、待对账或不可见结果,而不是把外部缺口隐藏成完整身份事实。

## 7. 核心能力闭环

> 校准来源:
> - `design-calibration/00_req_step_07_core_capability_loop.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“闭环定义”“核心能力闭环图”“能力层级划分表”和“能力节点停审清单”小节,了解后续章节的能力主轴。

`L1-identity` 的核心闭环是:先建立可长期引用的 AI 员工身份锚点,再管理该身份的全局可用性,再说明该身份的职业 / 能力语义,再沉淀其生涯与记忆引用,最后让相邻仓能消费这些身份事实并追溯变化。五类能力必须共同成立,否则 identity 要么只是通讯录,要么只是运行实例缓存,要么只是角色索引,都不能成为平台级 AI 员工身份真相仓。

```text
C-ID-1 Identity Anchor
  平台存在稳定、唯一、可长期引用的 AI 员工身份主语
        |
        v
C-ID-2 Lifecycle Availability
  身份主语具备全局生命周期和可用性边界
        |
        v
C-ID-3 Role Capability Summary
  身份主语具备职业、能力和证据引用语义
        |
        v
C-ID-4 Career Memory References
  身份主语沉淀项目经历和记忆引用,但不拥有外部正文
        |
        v
C-ID-5 Consumption Traceability
  相邻仓可消费身份事实,身份变化可审计和追溯
```

| 能力编号 | 能力节点 | 类型 | 成立条件 | 不包含 |
|---|---|---|---|---|
| C-ID-1 | 身份锚定 | 核心闭环 | 平台可以创建、引用和查询稳定 AI 员工身份主语 | 登录认证、token、ProjectMember |
| C-ID-2 | 生命周期可用性 | 核心闭环 | 平台可以判断成员是否可用、暂停、退役或墓碑化 | 运行容器启停、项目内状态 |
| C-ID-3 | 角色能力摘要 | 核心闭环 | 成员身份具备角色 / 能力来源、摘要和证据引用语义 | RoleDefinition 正文、能力评估算法 |
| C-ID-4 | 生涯与记忆引用 | 核心闭环 | 成员项目经历可追加追溯,memory refs 可保存和迁移 | 项目 truth、memory 原文、向量 |
| C-ID-5 | 消费与追溯 | 核心闭环 | 相邻仓可消费身份事实,变化可审计、投影和对账 | UI 展示状态、observability 存储正文 |

外围增强包括自动能力评级、绩效评分、高级员工主页、外部 HR / IdP 深度集成、复杂组织结构和全量 event sourcing。边界外能力包括 ProjectMember 分配、过程执行状态、Gate / policy 裁决 truth、RoleDefinition 正文、runtime 执行、对话正文和外部正文存储。

### 7.1 能力节点说明

| 能力节点 | 需求说明 | 缺失后果 |
|---|---|---|
| C-ID-1 身份锚定 | 平台必须先有一个可长期引用的成员身份主语,它不是账号、token、进程、项目成员或显示名称。 | 下游只能用临时名称、runtime id 或项目内成员来指代 AI 员工,无法跨项目追溯。 |
| C-ID-2 生命周期可用性 | 身份主语必须有全局可用性边界,用于判断成员是否可继续被选择、调用、展示或归档。 | 暂停、退役、墓碑化等动作会散落在项目、runtime 或 UI 中,无法统一约束。 |
| C-ID-3 角色能力摘要 | 成员身份需要表达职业 / 能力语义,但只能保存身份侧摘要、来源和证据引用。 | 平台无法解释成员“适合做什么”,或把方法定义正文和评估算法错误塞入 identity。 |
| C-ID-4 生涯与记忆引用 | 长期身份需要保留经历和记忆引用,但历史必须追加,正文必须外部归属。 | AI 员工无法体现跨项目成长;若保存正文则会破坏隐私、归属和归档边界。 |
| C-ID-5 消费与追溯 | 身份事实必须能被 work、process、conversation、governance、workspace、runtime 等消费,并能追溯变化。 | identity 会变成孤立目录;下游可能各自维护成员副本并产生漂移。 |

能力节点之间是逻辑递进,不是开发顺序或 API 调用顺序。后续实施可以分 phase,但每个 phase 都必须说明它覆盖了哪些能力节点、保留了哪些 reserved 边界,以及不会用临时实现破坏最终闭环。

按能力节点阅读时,故事含义如下:

| 能力节点 | 故事组说明 | 需求边界 |
|---|---|---|
| C-ID-1 | 建档、读取和自身可见摘要 | 关注“身份主语成立”,不处理登录认证或项目内承担 |
| C-ID-2 | 生命周期调整、可用性读取和高风险追溯 | 关注“成员全局是否可用”,不处理容器启停或任务状态 |

### 9.1 功能分组说明

功能需求按业务能力组织,不按 CRUD、API、Command、事件或对象组织。每项功能都只表达需求层的输入边界、结果边界和失败场景;具体 protocol、object contract、flow、transaction、error code 和 repository 读取面由后续 02/03 文档根据这些功能继续推导。

| 功能组 | 功能范围 | 后续设计必须保留的需求约束 |
|---|---|---|
| 身份锚定 | FR-ID-001~003 | 创建和读取必须分离;读取不得隐式写入;身份引用不得复用 |
| 生命周期 | FR-ID-004~005 | 生命周期变化必须显式、有原因、有操作者上下文;高风险处置必须有依据 |
| 角色能力 | FR-ID-006~008 | 只维护身份侧摘要、来源和证据引用;来源变化不能静默污染摘要 |
| 生涯记忆 | FR-ID-009~011 | 生涯只能追加;memory / archive 只保存引用和状态,不保存正文 |
| 消费追溯 | FR-ID-012~014 | 相邻仓只能消费身份事实;追溯和对账不能反向修复相邻仓 truth |

需求层允许功能失败并返回不可见、不存在、失效、待对账或拒绝等结果。失败不是设计缺口,而是 identity 保护边界的必要部分。真正的设计缺口是在后续文档中无法说明这些失败结果的来源、状态、验收或测试映射。

### 10.1 规则解释与反例

业务规则用于保护功能需求不越界。它们不是实现校验代码,也不是字段约束清单,而是后续设计必须保留的需求不变量和禁止行为。

| 规则组 | 正确口径 | 反例 |
|---|---|---|
| 身份锚定规则 | 成员身份建立后可改名、暂停或墓碑化,但身份引用不复用 | 删除旧成员后把同一个 ref 分配给新成员 |
| 读取 / 写入边界 | 查询只返回可见摘要或失败结果,不产生 truth | 下游读取未知成员时自动创建 GlobalMember |
| 生命周期规则 | 生命周期变化来自显式意图、原因和可信操作者上下文 | 后台定时任务静默退役成员且没有依据 |
| 角色能力规则 | 成员能力摘要必须有来源或证据引用 | 管理员直接填写“高级能力等级”且没有任何来源 |
| 生涯记忆规则 | 历史追加、正文外部归属、引用可追溯 | 直接修改旧项目经历或把 memory 原文写入 identity |
| 消费追溯规则 | 下游消费身份事实,维护任务报告漂移 | 对账任务直接修改 work、method-library 或 archive truth |

这些规则会影响后续状态矩阵、协议、错误语义、事务一致性和测试设计。任何后续方案如果为了实现便利绕开这些规则,都应视为需求冲突,而不是实现自由度。

### 11.1 数据归属判定

数据归属按“真相、快照、引用、禁止正文”四类判断:

| 类别 | 判断标准 | identity 中的处理方式 |
|---|---|---|
| 真相数据 | 如果没有 identity,平台无法回答成员身份本身的问题 | 由 identity 拥有生命周期、变化原因和追溯边界 |
| 快照 / 投影数据 | 可以从 truth 或外部来源重建,用于读取或消费便利 | 可保存可重建摘要,必须允许失效、重建或对账 |
| 引用数据 | 真相归相邻仓或外部承载方,identity 只需要稳定指向它 | 保存 ref、来源摘要、状态和可追溯原因 |
| 禁止正文 | 不是身份真相,且保存会破坏隐私、归属或边界 | 不进入 identity 存储、事件、报告或诊断正文 |

特别需要注意的是,引用数据不是“弱 truth”。identity 可以拥有“某成员关联了某个 memory ref”这一身份侧关系,但不拥有 memory 正文;可以拥有“某成员具有某角色来源引用”这一身份侧摘要,但不拥有 RoleDefinition 正文;可以拥有“某项目经历被追加到成员生涯”这一身份侧历史,但不拥有项目事实本身。

### 11.2 正文排除口径

正文排除适用于写路径、读路径、事件协作、审计追溯、诊断报告和维护对账。只要某个内容属于 method body、memory body、artifact body、conversation body、runtime context body、credential、secret 或外部证据正文,即使它对排查问题有帮助,也不得直接进入 identity truth。后续设计只能通过引用、摘要、可见 marker 或安全 issue ref 表达关联。

### 12.1 能力接口边界说明

本章中的“接口”是需求层能力面,不是 API 路径、RPC 名、command 名、event 名或 DTO schema。后续详细设计可以把同一能力边界拆成多个 command/query/event/job,但拆分后的每个 public surface 都必须能回指到本章的能力接口和第 9 章功能需求。

| 能力接口 | 消费者关心的问题 | 不应提前写入需求层的内容 |
|---|---|---|
| 成员身份建档能力 | 能否建立稳定成员主语,失败如何被拒绝 | 创建命令名、字段 schema、数据库唯一键 |
| 成员身份摘要读取能力 | 能否在可见范围内读取成员摘要 | 查询路径、分页结构、view DTO 字段 |

| 生涯 / memory ref 能力 | 能否追加经历和保存外部引用 | archive adapter、handoff record 字段 |
| 消费追溯 / 对账能力 | 下游能否消费、审计和发现漂移 | outbox topic、job DTO、report artifact |

这种写法是为了给后续设计留出合理实现空间,同时防止实现空间变成边界漂移。设计可以选择具体协议,但不能改变本章定义的能力归属、依赖类型和正文排除规则。

当前最硬的非功能底线是安全、正文排除、身份引用稳定、查询不写入、历史追加和相邻仓 truth 不被维护任务改写。这些底线即使在后续 phase 切分、降级运行或 fake adapter 场景中也不能被放松。性能、可用性和观测性则必须在后续测试方案和验收标准中形成可执行基线、sample 或评审规则,不得用“未重新评审的旧指标”直接宣告通过。

### 14.1 验收使用方式

本章验收标准用于判断需求闭环是否被后续设计和实现承接,不是完整测试方案。后续 `05-测试方案.md` 需要把这些验收条件细化为 test case、suite、fixture、artifact 和 evidence;`06-验收标准.md` 需要给出正式 pass / conditional pass / veto 口径。

验收时需要同时看正向能力和反向否决:

| 验收视角 | 需要证明 | 典型失败 |
|---|---|---|
| 核心能力闭环 | C-ID-1~C-ID-5 均有功能、规则、数据、接口和验收承接 | 只实现成员目录,没有生命周期、角色能力、生涯或追溯 |
| 边界保护 | 认证、ProjectMember、RoleDefinition、memory body、runtime body 不进入 identity truth | 为了方便查询把相邻仓正文复制进 identity |
| 来源追溯 | 高风险变化、能力声明、生涯追加和 memory ref 变化都有可见来源 | 变化可执行但无法解释依据 |
| 依赖裁剪 | 运行期 / 事件协作不变成业务仓源码依赖 | L1 仓之间形成编译期循环 |
| 一票否决 | 任何 veto 触发时不得宣告通过 | 把“后续修复”当作通过条件 |

### 15.1 风险处理原则

风险和待确认事项不是允许后续随意发挥的空白区。它们只表示“需求层已经识别问题,但正式闭口应发生在更合适的后续文档”。后续文档处理这些事项时必须回指本章,并在闭口后同步更新 traceability、测试和验收映射。

例如,`OQ-ID-001` 不能在实现阶段由 agent 自行决定事件或查询协议;它应在架构 / 详细设计中正式选择并给出 port、flow、失败语义和测试切口。`OQ-ID-005` 也不能由实现报告中的某次 sample 数字直接替代;它需要在测试方案或验收标准中形成明确基线或评审规则。

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的核心设定是**AI 成员不是临时进程,而是有身份、可成长、可追溯的员工**。这与传统"Agent 每次请求现建现销"完全不同。

因此系统必须有一个域来回答:
- 员工是谁(身份档案)
- 员工的主职业 / 次职业是什么(Role)
- 员工具备哪些能力(Capability)
- 员工参与过哪些项目(career_history)
- 员工的长期记忆挂在哪里(semantic / episodic memory refs)

这个域就是 L1-identity。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点描述 |
|---|---|---|
| 设计文档 | `domain/identity/README.md` 1171 行 | 设计已清晰,但仓级需求层还未显式定义 |
| 角色定义 | method-library 设计已完成 | 身份域如何索引 / 同步 / 漂移治理仍需仓级需求落地 |
| 双层 Member 模型 | ADR-0004 已锁 | code 层未起,无可运行验证 |
| Memory 归属 | ADR-0006 已锁 | 语义记忆 / episodic 句柄落地路径还未进入仓实施计划 |
| 事件契约 | 147 事件主表已定 | `identity.member.*` 与下游协作的验收标准未写 |

### 2.3 为什么要做(量化依据)

如果没有身份域:
- 所有"员工是谁"的信息会散落在 work / conversation / runtime 等仓里
- career_history 无法集中维护
- audit 时无法回答"这个 AI 成员在过去做过什么" 
- 42001 / 9001 的角色与责任链无法落地

**量化影响**:
- downstream 至少 5 个仓(work / conversation / member-service / governance / archive)直接依赖身份域事件
- `product/最终目的.md` §3.2 的核心承诺(员工是有身份的个体)会彻底落空

### 2.4 业务问题 vs 技术问题

- **业务问题**:AI 成员需要像员工一样被管理、成长、追溯
- **技术问题**:如何把身份、职业、能力、记忆引用、career_history 与下游仓事件解耦 yet 一致

## 5. 核心用例与用户故事

### 5.1 核心用例

1. **招聘 AI 成员**:创建 GlobalMember + 指定主职业 + 初始能力画像
2. **角色变更**:Role 升级 / 降级 / 追加 secondary_roles
3. **生命周期管理**:paused / retired / tombstoned
4. **career_history 同步**:收到 work.project.member_assigned 事件后追加条目
5. **Role 索引刷新**:method-library RoleDefinition 发布后本仓更新 catalog
6. **Memory 引用变更**:semantic / episodic memory refs 更新

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **Owner**,我想要 **招聘一个新 AI 成员**,以便 **把它纳入团队,后续可分配项目** |
| 优先级 | P0 |
| 验收条件 | **Given** role_id 有效且非 retired **When** 调用 `HireGlobalMember` **Then** 创建 `GlobalMember{state=hired}` 并发 `identity.member.hired` |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **work 域**,我想要 **在成员被分配到项目时自动写入 career_history**,以便 **所有项目参与轨迹都集中在身份域** |
| 优先级 | P0 |
| 验收条件 | **Given** 收到 `work.project.member_assigned` 事件 **When** identity 订阅处理 **Then** `career_history` append 新条目,state=in_progress |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **member-service**,我想要 **成员暂停/退休时收到统一事件**,以便 **及时暂停或关闭容器** |
| 优先级 | P0 |
| 验收条件 | **Given** `PauseMember` 成功 **When** 事务提交 **Then** 发 `identity.member.paused`; `RetireMember` 成功则发 `identity.member.retired` |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **method-library**,我想要 **RoleDefinition 发布后 identity 自动刷新 Role 索引**,以便 **运行时始终用最新角色元数据** |
| 优先级 | P0 |
| 验收条件 | **Given** 收到 `method_library.role_definition.published` **When** identity 处理 **Then** 本地 Role 索引更新并发 `identity.role.catalog_updated` |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **Auditor**,我想要 **查看任何成员的完整身份、职业、生涯、记忆 ref 变更轨迹**,以便 **满足 42001/9001 审计** |

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| BR-001 | `role_id` 指向 retired Role | 拒绝 hire / role change |
| BR-002 | `career_history` 更新 | 只 append,不可就地改历史 |
| BR-003 | `state=tombstoned` | 单向,不可恢复 |
| BR-004 | `semantic_memory_ref` 缺失 | 允许为空,不能因此阻止成员创建 |
| BR-005 | 收到 `work.project.archived` | 对应 career entry → completed |
| BR-006 | 收到 `work.project.member_retired_from_project` | 对应 career entry → completed / abandoned |
| BR-007 | 收到 `method_library.content.fingerprint_changed` 且 RoleDefinition 漂移 | 发 `identity.role.source_drift` |

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 聚合 / 类型 | 生命周期 |
|---|---|---|
| GlobalMember | 聚合根 | hired → active → paused / retired → tombstoned |
| Role | 聚合根(索引型) | defined → published → deprecated → retired |
| Capability | 值对象 | 跟随 Member / Role |
| CareerEntry | append-only 记录 | in_progress → completed / abandoned |

### 9.2 数据关系

```
GlobalMember
  ├─ role_id (主职业)
  ├─ secondary_roles[]
  ├─ capability_profile
  ├─ semantic_memory_ref
  ├─ episodic_memory_refs[]
  └─ career_history[] (append-only)
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| active / retired member 档案 | 长期 | 热数据 |
| tombstoned member | 归档前只留最小审计 ref | archive 接管 | 合规后删 |
| career_history | 永久(默认) | 可冷归档 | 不删历史 |
| semantic / episodic refs | 跟随 archive 迁移 | update ref | 不在本仓删向量 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Role 索引与 method-library 漂移 | 中 | 高 | fingerprint 对账 + source_drift 事件 |
| career_history 被错误修改历史 | 低 | 高 | append-only DB 约束 + 单测 |
| tombstone 误用 | 低 | 极高 | 严格权限 + 双人审计(未来) |
| memory ref 指向失效 | 中 | 中 | archive / memory service 对齐协议 |

### 12.2 边缘风险

- 一个成员被多项目并行使用时,career entry 事件乱序
- secondary_roles 与 role 变更冲突
- memory provider 切换导致 ref 不兼容

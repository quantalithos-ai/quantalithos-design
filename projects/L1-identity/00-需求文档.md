## 1. 与 `product/` 的关系声明与需求边界

L1-identity 是**产品叙事直推型**需求仓。`product/六域模型.md` 已明确身份域是六域之一,本文做的是**仓级需求细化**,不是重写产品叙事。

### 1.1 一句话需求定义

L1-identity 要提供一个**可审计、可事件联动的 AI 员工身份真相源**,让平台能够稳定回答:

- 这个 AI 成员是谁
- 当前是否可被项目使用
- 它的主职业 / 次职业 / 能力画像是什么
- 它参与过哪些项目
- 它的长期记忆与项目记忆句柄在哪里
- 它的身份变化如何同步给 work / member-service / conversation / governance / archive

| 章节 | 本文内容的来源 | `product/` 对应 |
|---|---|---|
| 背景与问题 | 直接细化产品叙事 | `product/最终目的.md` §3.2 "员工是有身份的个体" |
| 目标 | 直接细化 | `product/六域模型.md` §三 身份域 |
| 用户与角色 | 直接细化 | `product/六域模型.md` §三 + §九 方法库横切 |
| 数据需求 | 细化为 GlobalMember / Role / Capability / career_history / memory refs | `product/六域模型.md` 字段草案 |
| 非功能需求 | 来源于标准与架构约束 | `architecture/标准对齐全景图.md` identity 条目 |

### 1.2 需求边界

| 边界项 | L1-identity 负责 | L1-identity 不负责 |
|---|---|---|
| Member | GlobalMember 档案、全局生命周期、身份审计 | ProjectMember 分配、项目内成员状态 |
| Role | Role 索引、Role 生命周期摘要、spec_source / fingerprint | RoleDefinition 正文、方法内容编排 |
| Capability | 成员能力画像、能力证据引用 | 能力评估算法、自动评级模型 |
| Memory | semantic_memory_ref / episodic_memory_refs 句柄 | 向量、对话原文、记忆检索算法 |
| Career | career_history append-only 记录 | 项目计划、任务分配、绩效评价算法 |
| Runtime | 向 member-service 发布身份变化事件 | 容器创建、进程调度、工具执行 |

**定位原则**:
- 本文聚焦"身份域服务要实现什么能力"
- 本仓的核心真相是 GlobalMember,不是 ProjectMember
- Role 内容在 method-library,identity 只持有可运行索引
- Memory 内容在外部 memory service / archive,identity 只持有 ref
- 不展开具体表结构 / API 签名 / 目录树,这些由下游设计文档承接
- 用户故事中的"用户"既包括终端用户,也包括下游仓的开发者和运维角色

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的核心设定是**AI 成员不是临时进程,而是有身份、可成长、可追溯的员工**。这与传统"Agent 每次请求现建现销"完全不同。

因此系统必须有一个域来回答:

| 问题 | identity 的回答方式 |
|---|---|
| 员工是谁 | GlobalMember 档案 |
| 员工当前是否可用 | hired / active / paused / retired / tombstoned 生命周期 |
| 员工的主职业 / 次职业是什么 | role_id / secondary_roles,引用 method-library 的 RoleDefinition |
| 员工具备哪些能力 | CapabilityProfile + evidence refs |
| 员工参与过哪些项目 | career_history append-only |
| 员工的长期记忆挂在哪里 | semantic_memory_ref / episodic_memory_refs |
| 身份变化如何影响其他域 | identity.member.* / identity.role.* 事件 |

这个域就是 L1-identity。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点描述 |
|---|---|---|
| 设计文档 | `domain/identity/README.md` 1171 行 | 设计已清晰,但仓级需求层还未显式定义 |
| 角色定义 | method-library 设计已完成 | 身份域如何索引 / 同步 / 漂移治理仍需仓级需求落地 |
| 双层 Member 模型 | ADR-0004 已锁 | code 层未起,无可运行验证 |
| Memory 归属 | ADR-0006 已锁 | 语义记忆 / episodic 句柄落地路径还未进入仓实施计划 |
| 事件契约 | 147 事件主表已定 | `identity.member.*` 与下游协作的验收标准未写 |

### 2.3 为什么要做(量化依据)

如果没有身份域:
- 所有"员工是谁"的信息会散落在 work / conversation / runtime 等仓里
- career_history 无法集中维护
- audit 时无法回答"这个 AI 成员在过去做过什么" 
- 42001 / 9001 的角色与责任链无法落地

**量化影响**:
- downstream 至少 5 个仓(work / conversation / member-service / governance / archive)直接依赖身份域事件
- `product/最终目的.md` §3.2 的核心承诺(员工是有身份的个体)会彻底落空

### 2.4 业务问题 vs 技术问题

- **业务问题**:AI 成员需要像员工一样被管理、成长、追溯
- **技术问题**:如何把身份、职业、能力、记忆引用、career_history 与下游仓事件解耦但保持一致

### 2.5 第一批需求收敛口径

第一批实现不追求"完整员工管理平台",而是先让 identity 具备被其他仓依赖的最小稳定能力:

| 层次 | 第一批必须成立 |
|---|---|
| 真相层 | GlobalMember 可创建、查询、更新,member_id 不复用 |
| 生命周期 | hired / active / paused / retired / tombstoned 五态可执行,非法转移拒绝 |
| 角色层 | Role 索引可从 method-library 同步,retired Role 不可用于新 hire / role change |
| 能力层 | CapabilityProfile 可维护,变更带 evidence ref |
| 生涯层 | career_history 只能 append,由 work 事件驱动 |
| 记忆层 | 只保存 memory ref,不保存向量或原文 |
| 事件层 | 关键身份事件可发布、可追溯、可被下游消费 |

## 3. 目标与非目标

### 3.1 目标(可验证)

| ID | 目标 | 验收指标 | 验收方式 |
|---|---|---|---|
| G-1 | GlobalMember 生命周期完整 | hired → active, active ↔ paused, active/paused → retired → tombstoned; 非法转移全部拒绝 | 状态机测试 |
| G-2 | 双层 Member 边界清晰 | 本仓只存 GlobalMember,ProjectMember 只在 work | 代码审查 + 依赖检查 |
| G-3 | Role 索引同步可用 | method_library.role_definition.published 后 identity.role.catalog_updated 发出 | 集成测试 |
| G-4 | career_history append-only | 所有 Project 参与记录只 append,不回改 | DB 审计 + 单测 |
| G-5 | semantic / episodic memory 句柄可持久化 | 外部 memory ref 可写 / 更新 / 归档 | 集成测试 |
| G-6 | 下游 5 仓事件联动成功 | work / conversation / member-service / governance / archive 都能消费身份事件 | 端到端测试 |
| G-7 | 读性能达标 | P95 读 < 50ms | benchmark |
| G-8 | 写性能达标 | P95 写 < 200ms | benchmark |
| G-9 | 身份审计链完整 | lifecycle / role / capability / memory ref / career 变化均可追溯 | 审计查询 + 事件回放测试 |

### 3.2 非目标(明确不做)

| ID | 非目标 | 原因 | 归属 |
|---|---|---|---|
| NG-1 | **ProjectMember 管理** | 双层 Member 模型分离 | `quantalithos-work` |
| NG-2 | **RoleDefinition 正文内容存储** | 内容在 method-library,本仓只存索引 + 生命周期元数据 | `quantalithos-method-library` |
| NG-3 | **容器编排** | 身份域只管身份,不管运行时进程 | `quantalithos-member-service` |
| NG-4 | **向量记忆存储** | 只存 ref,不存向量本体 | 外部向量库 / memory service |
| NG-5 | **能力评估算法** | Capability 是声明性的,不做技能等级推断 | future analytics / governance |
| NG-6 | **对话 / 过程 / 治理业务** | 六域平权,各归其域 | conversation / process / governance |
| NG-7 | **工具执行 / skill 调度** | identity 只描述成员身份与能力,不决定 runtime 如何调用工具 | runtime / member-service |

## 4. 用户与角色

### 4.1 使用方分类

identity 的"用户"不只包含人类操作员,也包含 AI 协作方、上游来源系统、下游消费系统和审计方。

| 使用方类型 | 使用方 | 一句话定义 | 核心诉求 |
|---|---|---|---|
| 人类管理方 | Owner / Admin | 对 AI 员工身份拥有管理权限的人 | hire / activate / pause / retire / role change |
| 人类审计方 | Auditor | 只读查看身份责任链的人 | 查看 lifecycle / role / career / memory ref 审计链 |
| AI 协作方 | Assistant | 帮用户发起组建项目组和成员建档流程的 AI 助手 | 查询 Role、推荐成员、发起 hire / activate 请求 |
| AI 协作方 | AI Member 自身 | 被 identity 建档和追踪的 AI 员工 | 读取自身 profile / role / capability / memory refs |
| 上游来源 | method-library | RoleDefinition 的定义来源 | 发布 RoleDefinition 后驱动 identity 刷新 Role 索引 |
| 上游来源 | memory service / archive | 记忆内容和归档位置的实际承载方 | 更新 semantic / episodic memory refs,执行冷存迁移 |
| 下游消费 | work | ProjectMember 和项目任务的真相源 | 校验 GlobalMember 可用性,把项目参与事件同步给 career_history |
| 下游消费 | member-service / runtime | AI 成员运行容器和执行上下文的承载方 | 消费 lifecycle / role / capability 变化以启停或刷新容器 |
| 下游消费 | conversation / console | 对话和管理视图 | 展示成员身份、状态、角色、审计摘要 |
| 下游消费 | governance / observability | 治理、审计和监控 | 建立 actor responsibility chain,落审计事件和合规证据 |

## 5. 核心用例与用户故事

| UC-001 | 创建 AI 成员档案 | Owner / Admin; Assistant 可发起授权请求 | 授权通过后创建 GlobalMember,state=hired,发布 `identity.member.hired` |

## 9. 数据需求

### 9.1 数据分层

identity 的数据不按"表"来定义需求,而按数据职责分为四层。

| 层次 | 数据类型 | 写入来源 | 需求约束 |
|---|---|---|---|
| 真相层 | GlobalMember / RoleCatalogEntry / CapabilityProfile | identity 写接口 + method-library 事件 | identity 对这些对象负责一致性和状态约束 |
| 追加记录层 | CareerEntry / LifecycleTraceEntry / RoleCapabilityChangeEntry / MemoryRefChangeEntry | work 事件 / identity 写操作 / memory 事件 | 只能 append,不能改写历史 |

| RoleCapabilityChangeEntry | append-only 记录 | 是 | 记录 role / secondary_roles / capability 变化和 evidence refs |

| EpisodicMemoryRef | 引用对象 | 只拥有 ref | 指向项目级记忆,通常关联 ProjectRef / ProjectMemberRef |

### 10.1 依赖关系总览

| 依赖 | 关系方向 | 交互类型 | identity 依赖内容 | 失败影响 |

| PostgreSQL | identity → DB | 同步读写 | GlobalMember、RoleCatalogEntry、append-only records、outbox、projection | 主库不可用时写操作失败; 查询能力视缓存策略而定 |

| `quantalithos-method-library` | method-library → identity | 异步事件 + 查询引用 | RoleDefinition 发布、退役、fingerprint 变化 | Role catalog 陈旧; 不允许创建未知 Role |
| `quantalithos-work` | work ↔ identity | 查询 + 事件 | work 查询成员可用性; identity 消费项目成员事件 | career_history 延迟,ProjectMember 真相仍在 work |
| `quantalithos-member-service` / runtime | member-service ← identity | 查询 + 事件 | lifecycle / role / capability / memory refs | 容器启停或上下文刷新延迟 |
| memory service / archive | memory / archive ↔ identity | ref 更新 + 冷存协作 | semantic / episodic memory refs, cold storage refs | memory ref 延迟或 tombstone pending |
| governance | governance ↔ identity | Gate 决策 + 审计引用 | member-lifecycle Gate、授权约束、责任链 | 需要 Gate 的写操作不得绕过 |
| observability | identity → observability | 审计 tap / trace | audit trace、security audit、事件链引用 | 主流程可继续,但必须告警并保留待补偿记录 |

### 10.2 同步 API 需求

同步 API 分为 Command 和 Query。本文只定义需求级接口,具体 proto 字段由 L0-core 和详细设计承接。

#### Command API

| API | 触发方 | 前置要求 | 成功结果 | 对应功能 |
|---|---|---|---|---|
| `HireGlobalMember` | Owner / Admin; Assistant 可发起授权请求 | Role 存在且非 retired; 授权通过 | 创建 `state=hired` 的 GlobalMember | F-001 / F-013 |
| `ActivateMember` | Owner / Admin / Gate 决策 | state 为 hired 或 paused; Gate 满足要求 | state 变为 active | F-003 / F-013 |
| `PauseMember` | Owner / Admin | state 为 active | state 变为 paused | F-003 / F-013 |
| `RetireMember` | Owner / Admin | state 为 active 或 paused | state 变为 retired | F-003 / F-013 |
| `TombstoneMember` | Owner / Admin + governance Gate | state 为 retired; archive 条件满足或有 Gate 决策 | state 变为 tombstoned 或进入 pending | F-012 / F-013 |
| `ChangeRole` | Owner / Admin; Assistant 可建议 | 新 Role 存在且非 retired | 更新 role_id / secondary_roles | F-005 / F-013 |
| `UpdateCapabilityProfile` | Owner / Admin; Assistant 可建议 | evidence refs 有效; 成员非 tombstoned | 更新 capability_profile | F-006 / F-013 |
| `UpdateMemoryRefs` | Owner / Admin / memory service / archive | 成员非 tombstoned,或处于 tombstone 冷存流程 | 更新 semantic / episodic refs | F-008 / F-009 / F-012 |

### 10.5 下游消费契约

| 下游 | 主要消费方式 | identity 保证 | identity 不保证 |
|---|---|---|---|
| work | 查询 `GetMemberSummary`; 消费 lifecycle / role 事件 | lifecycle 顺序可追,member_id 稳定不复用 | 不替 work 管 ProjectMember |
| member-service / runtime | 消费 lifecycle / role / capability / memory ref 事件; 查询成员摘要 | 事件可重放,查询投影可重建 | 不负责容器编排和工具执行 |
| conversation / console | 查询成员摘要和审计摘要; 消费 participant 展示相关事件 | 展示状态与身份真相一致 | 不负责对话消息存储 |
| governance | 消费 actor / role / lifecycle 事件; 发布 Gate 决策 | 责任链可追溯,Gate 决策可落入 trace | 不替 governance 做政策判断 |
| archive | 消费 retired / tombstoned / memory ref 事件; 发布 cold migration 事件 | tombstone 状态单向,冷存结果可追踪 | 不直接删除外部 memory 内容 |
| observability | 消费 identity audit / security trace | 关键写操作都有 trace 或待补偿记录 | 不由 identity 承担全局日志存储 |

### 10.6 依赖失败与降级策略

| 场景 | 需求级策略 |
|---|---|
| PostgreSQL 不可用 | 写操作失败; 不允许假成功; 是否提供只读缓存由概要设计决定 |
| bus 不可用 | 主事务写 outbox,后台重试; 不得静默丢失 identity 事件 |
| method-library 不可用 | 使用本地 RoleCatalogEntry 缓存; 不允许创建未知 Role 或使用 retired Role |
| work 事件乱序 / 重复 | 通过 source_event_id / trace_id 幂等处理; 不改写 append-only 历史 |
| memory service 不可用 | hire 不因 memory ref 缺失失败; memory ref 更新可延迟 |
| archive 不可用 | tombstone 冷存协作进入 pending 或失败; 不允许假装 tombstone 完成冷存 |
| observability 不可用 | 主业务可继续,但 audit outbox / compensation record 必须保留并告警 |
| governance Gate 不可用 | 需要 Gate 的写操作不得绕过执行 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Role 索引与 method-library 漂移 | 中 | 高 | fingerprint 对账 + source_drift 事件 |
| career_history 被错误修改历史 | 低 | 高 | append-only DB 约束 + 单测 |
| tombstone 误用 | 低 | 极高 | 严格权限 + 双人审计(未来) |
| memory ref 指向失效 | 中 | 中 | archive / memory service 对齐协议 |

### 12.2 边缘风险

- 一个成员被多项目并行使用时,career entry 事件乱序
- secondary_roles 与 role 变更冲突
- memory provider 切换导致 ref 不兼容

|---|---|---|

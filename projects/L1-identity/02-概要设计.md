## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-identity` 不是项目任务系统,也不是流程引擎,也不是登录 / token / credential 校验系统。它是 **“AI 员工身份真相仓”**。

你可以把它理解成:
- 平台里“这个 AI 员工是谁”
- 这个成员当前在全局范围内是 hired / active / paused / retired / tombstoned 哪种状态
- 这个成员引用了哪个 `RoleCatalogEntry`
- 这个成员有什么 `CapabilityProfile`
- 这个成员参与过哪些项目,形成了哪些 `career_history`
- 这个成员的 semantic / episodic memory refs 在哪里
- 这些变化如何通过 audit / outbox / query projection 被追溯和消费

这些事情,都由 `L1-identity` 负责。

但有三件事不由 `L1-identity` 负责:
- 不负责登录、token、session、credential 校验;这些由 Gateway / API Layer 完成
- 不根据外部身份是否存在来自动创建成员;创建成员必须走显式 command
- 不在查询接口里隐式创建成员;查询不到就返回 NotFound

### 1.2 为什么要单独有这个仓

如果没有 `L1-identity`,这些身份事实就会散落在:
- `work` 的 assignee 字段里
- `process` 的执行人上下文里
- `conversation` 的用户显示信息里
- `runtime` 的执行代理里
- `memory / archive` 的记忆句柄里
- `governance / audit` 的审计记录里

结果就会出现:
- 平台里到底“谁是谁”说不清
- 全局身份状态和项目内承担关系混在一起
- 各仓各自缓存一份成员真相,最后彼此漂移
- 平台级权限、项目级角色、执行代理身份被混成一层
- 创建成员、查询成员、外部身份校验三类职责被混成一层

所以 `L1-identity` 必须独立存在,作为:
> **AI 员工身份、生命周期、角色索引、能力画像、生涯记录、记忆句柄和身份审计的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### GlobalMember
就是:
> 平台里的全局成员主语。

它回答的是:
- 这个成员是谁
- 当前在平台层是否 still active
- 全局身份是否还有效

#### ProjectMember
就是:
> `GlobalMember` 在某个具体项目里的承担分身。

它不是“谁是谁”的全局真相,而是:
- 这个成员在该项目里承担什么角色
- 当前是否可以承接项目内工作

#### Gateway / ActorContext

就是:
> 在请求进入 identity 之前,负责完成身份校验并注入可信操作者上下文的边界层。

它回答的是“谁在发起这个请求”,不是“要不要创建一个 AI 员工”。`L1-identity` 消费可信的 `ActorContext`,但不负责登录、token、session、credential 校验。

#### Create 和 Get

就是:
> 创建成员和获取成员必须是两类不同接口。

创建成员必须走显式 command,例如 `HireGlobalMember`。查询成员必须走 query,例如 `GetGlobalMember` / `GetMemberSummary`。

如果 query 查不到成员,只能返回 `NotFound`,不能自动创建成员。

#### 平台级角色 / 能力
就是:
> 某个成员在平台范围内具有什么角色、能力和权限边界。

它不等同于项目内角色。

#### 分身映射 / 身份接缝
就是:
> 其他仓如何稳定消费 identity,而不直接持有一份新的成员真相。

#### 审计投影 / 身份摘要
就是:
> 把身份变化、角色变化、绑定变化做成只读视图给外部看。

它不是主真相层。

### 1.4 内容采集结论(本仓当前重写基线)

本次校准 `L1-identity/02` 时,先收稳以下前提:
- `L1-identity` 不应按外部认证源建模,而应按 AI 员工身份真相和第一批开发能力建模
- identity 的第一批核心能力包括 `GlobalMember lifecycle`、`RoleCatalogEntry`、`CapabilityProfile`、`career_history`、memory refs、audit / outbox / query projection、Gate / Tombstone
- `GlobalMember` 与 `ProjectMember` 必须严格分层
- “创建成员”和“获取成员”不是同一类接口
- “身份校验”和“身份真相管理”不是同一层;身份校验在 Gateway / API Layer,identity 消费可信 `ActorContext`
- `RoleCatalogEntry` 和 `RoleDefinition` 正文不是同一层;RoleDefinition 归 method-library
- memory refs 和 memory 原文 / 向量不是同一层;identity 只保存 ref
- 平台级角色 / 能力和项目内承担角色不是同一层
- 对外系统接缝和只读审计投影也不是同一层

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,AI 成员身份不是项目内的一个附属字段,而是平台级的根事实之一。用户真正需要的是:
- 平台里“谁是谁”有统一真相
- 这个成员当前是否 still active / paused / retired 能被稳定判断
- 创建成员必须由明确的业务 command 触发,不能因为某个外部 subject 不存在就自动创建
- 查询成员必须是纯 query,查不到就返回 NotFound
- 登录、token、credential 校验由 Gateway / API Layer 完成,identity 只消费可信 `ActorContext`
- 成员的 RoleCatalogEntry、CapabilityProfile、career_history、memory refs 和 audit trace 能被统一追溯
- work / process / conversation / runtime 都能消费同一套身份锚点,而不是各自维护一份成员真相

如果把这些身份逻辑分别塞到:
- `work` 的 assignee / ProjectMember
- `process` 的 actor context
- `conversation` 的用户显示
- `runtime` 的执行代理
- `memory / archive` 的 ref 记录
- Gateway 的登录态或 token 校验结果

系统会快速退化成:
- 平台里到底“谁是谁”说不清
- 全局身份状态和项目内承担关系混在一起
- 平台级角色能力和项目级角色混层
- 查询接口可能产生副作用,甚至在读取时自动建档
- 登录 / 身份校验逻辑污染 identity 业务真相
- 不同仓看到的同一个成员状态不一致

因此,本概要设计的任务就是:
> **把 `L1-identity` 写成一个新人也能看懂的“AI 员工身份真相仓”,而不是把成员创建、成员查询、身份校验、角色索引、记忆句柄和投影混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 全局成员真相 | 容易被各仓局部字段替代 | `GlobalMember` 成为唯一身份锚点 | 需写死边界 |
| 身份 vs 承担关系 | `GlobalMember` 与 `ProjectMember` 易混 | 全局身份与项目分身严格分层 | 需正式落图 |
| 身份校验 vs 身份真相 | 易把登录 / token / credential 校验写进 identity | Gateway 负责身份校验,identity 消费可信 ActorContext | 需写死边界 |
| 创建 vs 查询 | 旧接口容易让同步 / 查询流程自动创建成员 | 创建走显式 command,查询查不到返回 NotFound | 需写死接口语义 |
| Role 与能力 | 易和项目内角色混层,也易复制 RoleDefinition 正文 | RoleCatalogEntry + CapabilityProfile 独立存在,RoleDefinition 归 method-library | 需形成主要部分 |
| 生涯与记忆 | career_history / memory refs 易散落在 work、runtime、memory | identity 维护 career_history append-only 和 memory refs | 需补核心模块 |
| 只读投影 | 易直接暴露真相对象给外部 | summary / trace / audit 投影只读 | 需明确投影边界 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让全平台对“AI 员工是谁、当前是否有效、是什么角色、有什么能力、参与过哪些项目、记忆句柄在哪里”有统一判断,而不是各仓各自保存一份成员真相
- **技术问题**:`GlobalMember`、显式创建 command、纯查询 query、RoleCatalogEntry、CapabilityProfile、career_history、memory refs、outbox、query projection、Gate/Tombstone 之间的边界如何稳定建模,并支持后续测试、验收和实现

### 4.2 位置解释

总图只说明 `L1-identity` 可能和哪些模块发生交互。具体通信方式和接口语义在 §6 分模块说明。

| 模块 | 与 identity 的关系 | 主要通信方式 |
|---|---|---|
| Gateway / API Layer | 完成身份校验并注入可信 `ActorContext` | HTTP headers / request context |
| Owner / Admin / Assistant | 发起成员创建、生命周期、角色能力、查询等操作 | HTTP JSON |
| method-library | RoleDefinition 来源,identity 保存 RoleCatalogEntry 索引 | Event Bus + RPC/HTTP |
| work | ProjectMember 真相源,向 identity 提供项目成员事件 | Event Bus + HTTP Query |
| process | 消费成员身份引用、生命周期和能力摘要用于流程执行上下文 | Event Bus + HTTP Query |
| member-service / runtime | 消费 lifecycle / role / capability / memory refs,刷新运行上下文 | Event Bus + HTTP Query |
| conversation / console | 消费成员摘要、审计轨迹和管理视图 | HTTP JSON |
| governance | 提供 Gate 决策,identity 记录 GateDecisionRef | RPC / HTTP |
| memory / archive | 提供 memory refs 校验和 tombstone 冷存结果 | HTTP/RPC + async event |
| L0-bus | 承载 identity 事件发布和跨域事件消费 | Outbox Publisher + Event Consumer |
| observability / audit | 接收审计 trace、指标和告警信号 | HTTP/RPC/Event Sink |

所以 `L1-identity` 在全局里的角色是:
> **AI 员工身份真相源,通过 HTTP/RPC/Event Bus 为其他模块提供稳定身份事实,但不接管其他模块的业务真相。**

### 4.3 系统边界

**做什么**:
- 保存平台级 `GlobalMember` 真相与生命周期状态
- 保存 `RoleCatalogEntry` 运行时索引和 `CapabilityProfile`
- 维护 `career_history` append-only 记录
- 保存 semantic / episodic memory refs,不保存记忆内容
- 提供成员查询投影、审计 trace 和 identity events
- 经 outbox 向 L0-bus 发布身份事实事件

**不做什么**:
- 不负责登录、token、credential 校验
- 不负责 `ProjectMember` 真相
- 不负责 `WorkItem` assignee 历史真相
- 不负责 RoleDefinition 正文和方法内容
- 不负责 memory 原文、向量和检索算法
- 不直接承担 process / runtime 的业务状态正文
- 不把投影视图反向当成身份真相写源
- 不把项目级角色分配当成平台级角色真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| Gateway / API Layer | 99.9% | 不可用时外部 command/query 受阻,identity 不接管身份校验 |
| L0-bus | 99.9% | 不可用时 outbox 保留事件并重试,不得丢 identity 事件 |
| method-library | 99.9% | 使用本地 RoleCatalogEntry 缓存读取,不得创建未知 Role |
| work | 99.9% | ProjectMember 事件延迟时 career_history 延迟追加,但不改写历史 |
| member-service / runtime | 99.9% | lifecycle / role / capability 消费延迟只影响运行态刷新,不反写 identity |
| governance | 99.9% | Gate 不可用时受控写操作不得绕过 |
| memory / archive | 99.9% | memory ref 可延迟校验;tombstone 冷存不可假完成 |
| conversation / console | 99.9% | 身份摘要投影延迟,不影响主真相层 |
| observability / audit | 99.9% | 不可用时保留 audit/outbox/compensation record 并告警 |

### 4.5 关键依赖风险

- 若 `GlobalMember` 与 `ProjectMember` 边界不清,identity 和 work 会发生真相混层
- 若 Gateway 身份校验和 identity 业务真相混层,identity 会被迫承担登录 / credential 复杂度
- 若平台级角色能力和项目级承担角色混层,后续权限、治理和执行会出现语义漂移
- 若 RoleCatalogEntry 与 RoleDefinition 边界不清,identity 会复制 method-library 正文
- 若 memory refs 与 memory 内容边界不清,identity 会吞进记忆原文或向量
- 若 outbox 被绕过,身份事实变化可能无法可靠通知下游
- 若投影层被误当成写源,conversation / console 的展示数据可能反向污染 identity 真相

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 全局成员真相与生命周期部分

- **它是什么**: 这是 `L1-identity` 的全局身份真相层,一起回答“这个 AI 员工是谁、当前生命周期是否仍有效”
- **为什么单独有它**: 如果没有独立的全局成员真相,后续 work/process/runtime 各自都会保存一份成员真相,最后必然漂移
- **负责什么**:
  - 定义 `GlobalMember`、`member_id` 及其全局生命周期
  - 执行 hired / active / paused / retired / tombstoned 状态迁移约束
  - 作为其他部分的身份根对象
- **不负责什么 / 容易混淆点**:
  - 不负责项目内承担关系
  - 不负责登录、token、credential 校验
  - 最容易和 `ProjectMember` 混淆
- **内含关键对象 / 机制**:
  - `GlobalMember`
  - lifecycle state
  - `member_id`
  - created_by / actor trace
- **与其他部分交互**:
  - 下游: 角色索引与能力画像、项目生涯记录、记忆引用与归档、审计事件与投影
  - 外部: Gateway / Owner / Assistant / work / member-service / runtime / console
  - 交互类型: command / query / event
- **后续详细设计展开点**:
  - `GlobalMember` 对象模型
  - lifecycle state machine
  - create / get 分离的 command/query 语义

#### 角色索引与能力画像部分

- **它是什么**: 这是成员角色索引和能力画像层,一起回答“这个成员是什么角色、具备什么能力、这些能力有什么证据”
- **为什么单独有它**: RoleDefinition 正文在 method-library,identity 只保存可运行索引;CapabilityProfile 是成员画像,不是项目内承担角色
- **负责什么**:
  - 保存 `RoleCatalogEntry` 的 role_id、version、fingerprint、spec_source、lifecycle 摘要
  - 维护成员 main_role_id / secondary_roles 引用
  - 维护 `CapabilityProfile` 和 evidence refs
  - 向 runtime、process、console 提供角色与能力摘要
- **不负责什么 / 容易混淆点**:
  - 不保存 RoleDefinition 正文
  - 不负责 `ProjectMember` 项目内承担角色
  - 不负责能力评估算法
  - 最容易和 method-library 的角色定义正文混淆
- **内含关键对象 / 机制**:
  - `RoleCatalogEntry`
  - main_role_id / secondary_roles
  - `CapabilityProfile`
  - evidence refs
  - role fingerprint drift 检测
- **与其他部分交互**:
  - 上游: method-library 的 RoleDefinition 事件
  - 下游: 审计事件与只读投影、对外协作边界
  - 交互类型: event + RPC/HTTP reconciliation
- **后续详细设计展开点**:
  - RoleCatalogEntry 同步模型
  - role assignment 规则
  - CapabilityProfile 更新与 evidence 校验

#### 项目生涯记录部分

- **它是什么**: 这是 AI 员工项目参与轨迹层,一起回答“这个成员参与过哪些项目、项目经历如何追溯”
- **为什么单独有它**: career_history 由 work 事件驱动,具有 append-only 语义和审计价值,不应混进 ProjectMember 真相或普通投影
- **负责什么**:
  - 消费 work 的项目成员分配、退出、归档事件
  - 追加 `career_history` / `CareerEntry`
  - 按 source_event_id 幂等处理重复事件
  - 向审计和查询投影提供生涯记录
- **不负责什么 / 容易混淆点**:
  - 不创建或维护 `ProjectMember`
  - 不负责项目计划、任务分配、WorkItem
  - 不改写历史记录
- **内含关键对象 / 机制**:
  - `CareerEntry`
  - project_id
  - project_member_id
  - source_event_id
  - append-only records
- **与其他部分交互**:
  - 上游: work 事件
  - 下游: 审计事件与只读投影
  - 交互类型: inbound event + append-only write
- **后续详细设计展开点**:
  - career event consumer
  - CareerEntry 去重与关闭记录
  - career_history 查询投影

#### 记忆引用与归档协作部分

- **它是什么**: 这是成员记忆句柄和冷存协作层,一起回答“这个成员的长期记忆、项目记忆和归档引用在哪里”
- **为什么单独有它**: memory 内容属于 memory service / archive,identity 只保存 ref;如果边界不清,identity 会吞进记忆原文或向量
- **负责什么**:
  - 保存 semantic_memory_ref
  - 保存 episodic_memory_refs
  - 保存 archive_ref / tombstone operation refs
  - 与 archive 协作完成 retired -> tombstoned 冷存闭环
- **不负责什么 / 容易混淆点**:
  - 不保存 memory 原文
  - 不保存向量
  - 不负责记忆检索算法
- **内含关键对象 / 机制**:
  - semantic_memory_ref
  - episodic_memory_refs
  - archive_ref
  - tombstone operation refs
- **与其他部分交互**:
  - 上游/下游: memory service / archive
  - 下游: 审计事件与只读投影
  - 交互类型: HTTP/RPC + async status/event
- **后续详细设计展开点**:
  - MemoryRef schema
  - archive job / status 模型
  - tombstone flow 与失败补偿

#### 审计、事件与只读投影部分

- **它是什么**: 这是 identity 的可追溯、可靠通知和只读消费层,一起回答“身份变化如何审计、事件如何可靠发布、外部如何读取摘要”
- **为什么单独有它**: audit、outbox、projection 都不是业务主语,但它们是 identity 能被开发、运维、审计可靠消费的关键机制
- **负责什么**:
  - 记录 lifecycle / role / capability / career / memory 变化 audit trace
  - 写入 outbox events 并交给 L0-bus 发布
  - 维护 member summary / lifecycle trace / audit projection
  - 支持 conversation / console / auditor 的只读查询
- **不负责什么 / 容易混淆点**:
  - 不反写真相
  - 不绕过 outbox 直接发布领域事件
  - 不替代全局 observability / audit 系统
- **内含关键对象 / 机制**:
  - audit trace
  - outbox events
  - query projection
  - member summary
  - lifecycle trace
- **与其他部分交互**:
  - 上游: 所有写模型变化
  - 下游: L0-bus、conversation / console、observability / audit
  - 交互类型: outbox publish + query projection
- **后续详细设计展开点**:
  - outbox schema / publisher
  - projection rebuild
  - audit trace query

#### 对外协作边界部分

- **它是什么**: 这是 identity 和其他模块之间的通信边界,一起回答“哪些操作走 HTTP、哪些事实走 Event Bus、哪些决策走 RPC”
- **为什么单独有它**: 如果不单列,开发容易把 command、query、event、Gate 校验混成一种交互方式,导致职责和失败语义不清
- **负责什么**:
  - 定义 command / query boundary
  - 定义 inbound / outbound event boundary
  - 消费 Gateway 注入的可信 `ActorContext`
  - 约束对 method-library、work、governance、memory/archive、L0-bus 的交互语义
- **不负责什么 / 容易混淆点**:
  - 不做 Gateway 的登录 / token / credential 校验
  - 不用 Event Bus 接收创建成员命令
  - 不把外部模块的业务状态拉进 identity
- **内含关键对象 / 机制**:
  - ActorContext
  - command/query boundary
  - inbound events
  - outbound events
  - GateDecisionRef
- **与其他部分交互**:
  - 上游/下游: Gateway、Owner/Admin/Assistant、method-library、work、process、runtime、governance、memory/archive、L0-bus、observability
  - 交互类型: HTTP JSON + Event Bus + RPC/HTTP internal
- **后续详细设计展开点**:
  - API boundary
  - event consumer / publisher boundary
  - external port traits

## 6. 本仓如何与其他模块交互

### 6.1 总交互图(只列通信类型)

```text
                       HTTP JSON
Owner/Admin/Assistant ─────────────┐
Console/Conversation ──────────────┤
Gateway / API Layer ───────────────┤
                                   ▼
                           ┌──────────────┐
Event Bus + Outbox ◀──────▶│ L1-identity │◀──────▶ RPC / HTTP internal
L0-bus / work / method-lib │              │        governance / memory
process / runtime          └──────────────┘        archive / method-lib
                                   │
                                   ▼
                           observability / audit
                           HTTP/RPC/Event Sink
```

### 6.2 总解释

`L1-identity` 的交互不采用单一通信方式,而是按语义分三类:

| 通信方式 | 用途 | 典型交互 |
|---|---|---|
| HTTP JSON | 同步 command / query | 创建成员、更新生命周期、查询摘要 |
| Event Bus + Outbox | 跨域事实事件传播 | `identity.member.*`、`work.project.member_assigned` |
| RPC / HTTP internal | 内部同步校验或拉取 | Gate 校验、RoleCatalogSource 拉取、archive job 查询 |
| HTTP/RPC/Event Sink | 审计与指标上报 | audit trace、outbox lag、projection lag |

关键约束:
- HTTP / RPC 负责“现在要做什么 / 查什么”
- Event Bus 负责“事实已经发生了”
- identity 不用 Event Bus 接收创建成员命令
- identity 不做 Gateway 的身份校验

### 6.3 分模块交互说明(逐个写)

#### 与 `Gateway / API Layer` 的交互

```text
┌──────────────────────┐
│ Gateway / API Layer  │
└──────────┬───────────┘
           │ HTTP headers / trusted ActorContext
           ▼
┌──────────────────────┐
│ L1-identity          │
└──────────────────────┘
```

- **通信方式**: HTTP headers / request context
- **Gateway 提供**: `ActorContext`、trace_id、tenant/project context、请求来源
- **identity 返回**: 业务结果、业务拒绝原因、trace_id
- **边界**: identity 不验证 token / session / credential,只消费可信 `ActorContext`

#### 与 `work` 的交互

```text
┌──────────────────────┐          Event Bus          ┌──────────────────────┐
│ work                 │ ───────────────────────────▶│ L1-identity          │
│ ProjectMember truth  │  project member events      │ career_history       │
└──────────┬───────────┘                              └──────────┬───────────┘
           │ HTTP Query                                          │ Event Bus
           ▼                                                     ▼
┌──────────────────────┐                              ┌──────────────────────┐
│ GetMemberSummary     │                              │ identity.career.*    │
└──────────────────────┘                              └──────────────────────┘
```

- **通信方式**: Event Bus + HTTP Query
- **identity 消费**: `work.project.member_assigned`、`work.project.member_removed`、`work.project.archived`
- **identity 提供**: `GetGlobalMember`、`GetMemberSummary`、`identity.career.appended`
- **边界**: `ProjectMember` 归 work,identity 只追加 `career_history`,不接管项目任务或 assignee 真相

#### 与 `process` 的交互

```text
┌──────────────────────┐          HTTP Query/Event   ┌──────────────────────┐
│ process              │ ───────────────────────────▶│ L1-identity          │
│ actor context use    │  member / role query        │ identity projection  │
└──────────────────────┘                              └──────────────────────┘
```

- **通信方式**: HTTP Query + Event Bus
- **identity 提供**: `GetMemberSummary`、lifecycle、role/capability 摘要、identity lifecycle 事件
- **process 消费目的**: 确认流程参与者身份、流程执行上下文和责任链引用
- **边界**: process 管流程实例和执行节奏,identity 不保存 process 状态

#### 与 `method-library` 的交互

```text
┌──────────────────────┐          Event Bus          ┌──────────────────────┐
│ method-library       │ ───────────────────────────▶│ L1-identity          │
│ RoleDefinition truth │  role definition events     │ RoleCatalogEntry     │
└──────────┬───────────┘                              └──────────┬───────────┘
           │ RPC / HTTP pull                                      │ Event Bus
           ▼                                                       ▼
┌──────────────────────┐                              ┌──────────────────────┐
│ RoleCatalogSource    │                              │ identity.role.*      │
└──────────────────────┘                              └──────────────────────┘
```

- **通信方式**: Event Bus 为主,RPC / HTTP 拉取为辅
- **identity 消费**: `method_library.role_definition.published`、`method_library.role_definition.retired`
- **identity 请求**: `GetRoleCatalogSource`、`VerifyRoleFingerprint`
- **identity 提供**: `identity.role.catalog_updated`、`identity.role.source_drift`
- **边界**: identity 只保存 RoleCatalogEntry,不复制 RoleDefinition 正文

#### 与 `member-service / runtime` 的交互

```text
┌──────────────────────┐          Event Bus          ┌──────────────────────┐
│ L1-identity          │ ───────────────────────────▶│ member-service       │
│ lifecycle / role     │  lifecycle / role events    │ runtime context      │
└──────────┬───────────┘                              └──────────┬───────────┘
           ▲ HTTP Query                                          │
           └─────────────────────────────────────────────────────┘
```

- **通信方式**: Event Bus + HTTP Query
- **identity 提供事件**: `identity.member.*`、`identity.role.changed`、`identity.capability.updated`、`identity.memory_ref.updated`
- **identity 提供查询**: `GetMemberSummary`
- **边界**: identity 不负责容器调度、工具执行、skill 调度

#### 与 `conversation / console` 的交互

```text
┌──────────────────────┐          HTTP JSON          ┌──────────────────────┐
│ conversation/console │ ───────────────────────────▶│ L1-identity          │
│ read-only views      │  query                      │ query projection     │
└──────────────────────┘                              └──────────────────────┘
```

- **通信方式**: HTTP JSON
- **identity 提供**: `GetMemberSummary`、`ListMembersByLifecycle`、`GetCareerHistory`、`GetAuditTrace`
- **边界**: conversation / console 只读投影,不反写真相

#### 与 `governance` 的交互

```text
┌──────────────────────┐          RPC / HTTP         ┌──────────────────────┐
│ L1-identity          │ ───────────────────────────▶│ governance           │
│ controlled command   │  VerifyGateDecision         │ policy / Gate        │
└──────────┬───────────┘                              └──────────┬───────────┘
           ◀─────────────────────────────────────────────────────┘
                    GateDecision allow / deny
```

- **通信方式**: RPC / HTTP
- **identity 请求**: `VerifyGateDecision`
- **governance 返回**: allow / deny、GateDecisionRef、policy reason
- **边界**: governance 决定策略,identity 记录 GateDecisionRef 并执行受控状态迁移

#### 与 `memory / archive` 的交互

```text
┌──────────────────────┐          HTTP/RPC           ┌──────────────────────┐
│ L1-identity          │ ───────────────────────────▶│ memory / archive     │
│ memory refs          │  ValidateMemoryRef          │ content owner        │
│ tombstone flow       │  ArchiveMemberRefs          │ cold storage         │
└──────────┬───────────┘                              └──────────┬───────────┘
           ◀──────────────── async status/event ─────────────────┘
```

- **通信方式**: HTTP/RPC + async event
- **identity 请求**: `ValidateMemoryRef`、`ArchiveMemberRefs`、`GetArchiveStatus`
- **identity 保存**: semantic_memory_ref、episodic_memory_refs、archive_ref
- **边界**: identity 只保存 ref,不保存 memory 原文或向量

#### 与 `L0-bus` 的交互

```text
┌──────────────────────┐          outbox             ┌──────────────────────┐
│ L1-identity          │ ───────────────────────────▶│ L0-bus               │
│ outbox publisher     │  identity.* events          │ event transport      │
└──────────┬───────────┘                              └──────────┬───────────┘
           ◀──────────────── inbound events ─────────────────────┘
```

- **通信方式**: Outbox Publisher + Event Consumer
- **identity 发布**: `identity.member.*`、`identity.role.*`、`identity.capability.*`、`identity.career.*`、`identity.memory_ref.*`
- **identity 消费**: method-library / work / archive 等来源事件
- **边界**: domain 不直接绕过 outbox 发布事件

#### 与 `observability / audit` 的交互

```text
┌──────────────────────┐       HTTP/RPC/Event Sink   ┌──────────────────────┐
│ L1-identity          │ ───────────────────────────▶│ observability/audit  │
│ audit trace          │  trace / metrics / alerts   │ trace / metrics      │
└──────────────────────┘                              └──────────────────────┘
```

- **通信方式**: HTTP/RPC/Event Sink
- **identity 提供**: IdentityAuditTrace、IdentityMetric、security event、outbox lag、projection lag
- **边界**: 外部观测不可用时,identity 仍保留本地审计依据和补偿记录

### 6.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 每条交互的通信方式
- 哪个模块是真相源、哪个模块是只读投影层、哪个模块只承载传输

本节**不**展开:
- HTTP request / response payload
- 事件 payload
- 状态机完整迁移
- 表结构与索引
- 角色能力计算细节

这些内容留到 `03-详细设计.md` 中继续展开。

### 6.5 关键交互清单

| 对方 | 通信方式 | `L1-identity` 消费什么 | `L1-identity` 提供什么 |
|---|---|---|---|
| Gateway / API Layer | HTTP context | trusted ActorContext / trace_id | 业务结果 / 拒绝原因 |
| Owner / Admin / Assistant | HTTP JSON | command / query 请求 | member_id / summary / lifecycle result |
| method-library | Event Bus + RPC/HTTP | RoleDefinition 事件 / RoleCatalogSource | RoleCatalogEntry 同步结果 / source_drift |
| work | Event Bus + HTTP Query | ProjectMember 事件 | member summary / career appended event |
| process | HTTP Query + Event Bus | 成员身份 / 角色能力查询需求 | lifecycle / role / capability 摘要 |
| member-service / runtime | Event Bus + HTTP Query | 运行态查询请求 | lifecycle / role / capability / memory refs |
| conversation / console | HTTP JSON | 只读查询请求 | summary / career / audit trace |
| governance | RPC / HTTP | Gate decision result | command context / GateDecisionRef 引用 |
| memory / archive | HTTP/RPC + async event | memory ref 状态 / archive job 状态 | member refs / tombstone context |
| L0-bus | Outbox + Event Consumer | inbound domain events | identity.* events |
| observability / audit | HTTP/RPC/Event Sink | 指标和审计接收能力 | audit trace / metrics / security event |

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 分层架构 + 端口适配器 + 事件驱动 + outbox / projection

**选择理由**:
- `identity` 的核心职责是维护身份真相,不是承接外部认证协议
- 外部 HTTP / RPC / Event 协议应隔离在 adapter 层,避免污染 domain model
- 创建、生命周期更新、角色索引同步、记忆引用更新、tombstone 等用例需要由 application service 编排
- `GlobalMember`、`RoleCatalogEntry`、`CapabilityProfile`、`career_history`、`memory refs` 的规则应沉到 domain model
- outbox 与 query projection 是可靠事件发布和读取性能的基础设施,不应混入业务规则

### 7.2 模块划分与职责

```text
┌──────────────────────────────────────────────────────────────┐
│                         L1-identity                          │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Inbound Adapters                                      │  │
│  │ - HTTP Command API                                    │  │

│  │ - Event Consumers                                     │  │
│  └──────────────────────────┬─────────────────────────────┘  │
│                             ▼                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Application Services                                  │  │
│  │ - MemberLifecycleCommandService                       │  │
│  │ - RoleCatalogSyncService                              │  │
│  │ - CareerEventConsumerService                          │  │
│  │ - MemoryRefService                                    │  │
│  │ - TombstoneFlowService                                │  │

│  └──────────────────────────┬─────────────────────────────┘  │
│                             ▼                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Domain Model                                          │  │
│  │ - GlobalMember lifecycle rules                        │  │
│  │ - RoleCatalogEntry rules                              │  │
│  │ - CapabilityProfile rules                             │  │

│  └──────────────────────────┬─────────────────────────────┘  │
│                             ▼                                │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ Persistence / Data Store                              │  │
│  │ - write model                                         │  │

│  └────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

| 分层 | 职责(一句话) | 不应承担 |
|---|---|---|
| Inbound Adapters | 承接 HTTP / Event 等输入协议,解析请求并转换为 application command / query | 不写业务规则,不做身份校验 |
| Application Services | 编排业务用例、事务、repository、port 和 outbox 写入 | 不把生命周期规则写成脚本 |
| Domain Model | 维护身份、角色索引、能力画像、生涯、记忆引用等业务规则 | 不关心 HTTP、数据库、消息队列 |
| Persistence / Data Store | 保存 write model、append-only history、query projection、outbox | 不反向决定业务含义 |
| Outbound Adapters | 调用 method-library、governance、memory/archive、L0-bus、audit 等外部能力 | 不把外部协议泄漏进 domain |

### 7.3 模块依赖关系

```text
Owner/Admin/Assistant/Console/Runtime/Process/Bus
        │
        ▼
Inbound Adapters
        │
        ▼
Application Services
        │
        ├──────────────▶ Repository / UnitOfWork ─▶ Persistence
        │                                      │
        │                                      ├─ write model
        │                                      ├─ append-only records
        │                                      ├─ query projection
        │                                      └─ outbox
        │
        ├──────────────▶ Outbound Ports ──────▶ external modules
        │                    │
        │                    ├─ MethodLibraryPort
        │                    ├─ GovernancePort
        │                    ├─ MemoryArchivePort
        │                    ├─ BusPublisherPort
        │                    └─ AuditTracePort
        │
        ▼
Domain Model
```

依赖方向以 `Application Services` 为编排中心:
- inbound adapter 只能调用 application service
- application service 可以调用 domain、repository、outbound port
- domain model 不直接调用 repository、bus、HTTP/RPC client 或外部模块
- persistence 不反向调用 domain 以外的业务服务
- outbound adapter 只实现 port,不定义业务语义

### 7.4 层间约束规则(防退化)

- inbound adapter 只处理协议解析、格式校验和 `ActorContext` 传递,不做登录、token、session、credential 校验
- application service 负责用例编排和事务边界,不把 domain 规则散落到 controller 或 repository
- domain model 负责 lifecycle、append-only、ref-only、tombstone 等核心不变量
- persistence 负责 write model、append-only records、query projection 和 outbox,不把 projection 当成真相写源
- outbound adapter 负责隐藏外部模块协议,domain 不直接依赖 method-library、work、process、memory/archive、governance 或 L0-bus
- outbox 是 identity 发布 domain event 的唯一可靠通道
- query projection 只能服务查询,不得反向覆盖 `GlobalMember` 真相
- `identity` 只消费 Gateway / API Layer 注入的可信 `ActorContext`,不自行实现身份校验机制
- platform role / capability 不直接承担项目级承担角色语义
- `ProjectMember` 只存在于 work 域,不回写 identity 真相

## 8. 关键技术选型

### 8.1 为什么采用“全局身份真相 / 项目分身”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | `GlobalMember` 与 `ProjectMember` 分层 |
| 备选方案 | 各仓各持一份成员真相 / 不区分全局成员与项目成员 |
| 选择理由 | `GlobalMember` 回答平台范围内“这个成员是谁”,`ProjectMember` 回答某个项目内“这个成员承担什么” |
| 约束 | `ProjectMember` 属于 work 域,不得反写 `GlobalMember` 真相 |
| 演进路径 | 后续 work / process / runtime 可以持有各自的稳定引用或投影,但身份真相仍锚定在 identity |

示例:

```text
identity:
  GlobalMember GM-001 backend-dev
    lifecycle: active
    main_role_id: backend-engineer

work:
  ProjectMember P-100/GM-001
    project_role: 后端负责人

  ProjectMember P-200/GM-001
    project_role: 普通后端开发
```

### 8.2 为什么 identity 不做身份校验,只消费 ActorContext

| 维度 | 内容 |
|---|---|
| 当前选择 | Gateway / API Layer 完成 login / token / session / credential 校验,identity 只消费可信 `ActorContext` |
| 备选方案 | 在 identity 内实现认证、绑定 credential、根据外部身份自动创建成员 |
| 选择理由 | 避免 identity 退化成认证系统,也避免查询接口隐式创建成员 |
| 约束 | `HireGlobalMember` 是显式创建 command;`GetMemberSummary` 等查询接口不得自动创建成员 |
| 演进路径 | 未来认证源变化只影响 Gateway / API Layer,不拖动 identity domain model |

核心流向:

```text
Caller
  |
  v
Gateway / API Layer
  - validate token/session/credential
  - inject trusted ActorContext
  |
  v
L1-identity
  - execute member command/query
  - never login/verify token here
```

### 8.3 为什么平台级角色能力与项目级角色分离

| 维度 | 内容 |
|---|---|
| 当前选择 | platform role / capability 独立于 project role |
| 备选方案 | 用同一套角色字段覆盖平台层与项目层 |
| 选择理由 | 避免权限模型和承担模型混层,便于 governance / runtime / work 各自消费 |
| 约束 | platform role / capability 不直接表达某个项目内的承担关系 |
| 演进路径 | 后续可扩展能力域映射,但不把项目承担角色拉回全局身份真相 |

### 8.4 为什么 RoleDefinition 属于 method-library,identity 只保存 RoleCatalogEntry

| 维度 | 内容 |
|---|---|
| 当前选择 | method-library 拥有 `RoleDefinition` 正文,identity 保存 `RoleCatalogEntry` 索引和引用 |
| 备选方案 | identity 直接保存完整角色定义、职责、技能要求、流程绑定和任务模板 |
| 选择理由 | 角色方法论属于 method-library;identity 只需要知道成员引用了哪个角色目录项 |
| 约束 | identity 不复制 `RoleDefinition` 正文,只保存 role_id、name、version、source_ref、status 等索引信息 |
| 演进路径 | method-library 的角色定义可独立演进,identity 通过事件或同步接口刷新目录索引 |

边界示例:

```text
method-library:
  RoleDefinition backend-engineer
    responsibilities
    required_skills
    task_definitions

identity:
  RoleCatalogEntry backend-engineer
    role_id
    name
    version
    source_ref
    status

  GlobalMember GM-001
    main_role_id: backend-engineer
```

### 8.5 为什么 CapabilityProfile 属于 identity

| 维度 | 内容 |
|---|---|
| 当前选择 | `CapabilityProfile` 作为成员全局能力画像由 identity 承载 |
| 备选方案 | work / process / runtime 各自维护成员能力字段 |
| 选择理由 | 能力画像描述的是成员自身能力,需要跨项目、跨流程、跨运行态复用 |
| 约束 | `CapabilityProfile` 不表达项目内临时分工,也不替代 `ProjectMember` |
| 演进路径 | 可由执行证据、评估结果、治理结论逐步更新,但必须保留可审计来源 |

主要消费者:

```text
CapabilityProfile
  |
  +--> work:       分配 WorkItem 时做能力匹配
  +--> process:    选择 Activity 执行候选人
  +--> runtime:    判断 agent 是否能执行某类任务
  +--> governance: 判断高风险任务是否需要额外 Gate
```

### 8.6 为什么 career_history 采用 append-only

| 维度 | 内容 |
|---|---|
| 当前选择 | `career_history` 采用追加式记录 |
| 备选方案 | 在 `GlobalMember` 上覆盖 current_project、last_role、last_task 等字段 |
| 选择理由 | 成员经历需要可审计、可复盘、可解释,覆盖式字段会丢失历史 |
| 约束 | 历史记录不直接修改;错误修正应通过 correction / supersede 记录表达 |
| 演进路径 | 后续可从 work / process 事件自动追加项目经历、任务经历和角色变化 |

示例:

```text
career_history:
  1. GM-001 joined project P-100 as backend-dev
  2. GM-001 completed WI-101
  3. GM-001 became backend-owner in P-100
  4. GM-001 left project P-100
```

### 8.7 为什么 memory 采用 ref-only

| 维度 | 内容 |
|---|---|
| 当前选择 | identity 只保存 semantic / episodic / archive memory refs |
| 备选方案 | identity 直接保存记忆正文、embedding、向量索引和归档内容 |
| 选择理由 | identity 是身份真相源,不是记忆系统;记忆内容和检索能力属于 memory / archive |
| 约束 | identity 只保存引用、状态和必要审计信息,不保存 memory 原文或向量 |
| 演进路径 | tombstone / archive 时通过 ref 与 memory / archive 协作完成归档或清理 |

边界示例:

```text
identity:
  GlobalMember GM-001
    semantic_memory_ref: mem://semantic/GM-001
    episodic_memory_refs:
      - mem://episode/GM-001/P-100

memory / archive:
  memory content
  embedding
  retrieval index
  cold archive
```

### 8.8 为什么事件发布采用 outbox

| 维度 | 内容 |
|---|---|
| 当前选择 | 写模型变化与 outbox event 在同一事务内提交,再由 publisher 异步发布到 L0-bus |
| 备选方案 | 业务写入成功后直接同步调用 bus publish |
| 选择理由 | 避免“数据库已提交但事件发布失败”导致下游永远不知道事实变化 |
| 约束 | domain event 不绕过 outbox;outbox 记录必须可重试、可追踪、可补偿 |
| 演进路径 | 后续可增加 outbox lag 指标、重放工具和失败补偿任务 |

核心流程:

```text
Application Service
  |
  | transaction
  v
write GlobalMember / lifecycle / career
write outbox(identity.member.*)
  |
  | commit
  v
Outbox Publisher
  |
  v
L0-bus
```

### 8.9 为什么读取采用 query projection

| 维度 | 内容 |
|---|---|
| 当前选择 | 高频查询读取 `member_summary_projection` 等只读投影 |
| 备选方案 | 每次查询都聚合 write model、history、role catalog、capability、memory refs |
| 选择理由 | 下游多为读多写少场景,投影能稳定返回摘要并降低跨表聚合复杂度 |
| 约束 | projection 只读,不能反向覆盖 `GlobalMember` / `CapabilityProfile` / `career_history` 真相 |
| 演进路径 | 后续可按 consumer 场景扩展 projection,但不新增第二套真相源 |

示例:

```text
write model
  |
  +--> global_member
  +--> lifecycle_history
  +--> role_catalog_entry
  +--> capability_profile
  +--> career_history
  +--> memory_refs
        |
        v
projection builder
        |
        v
member_summary_projection
        |
        v
GetMemberSummary
```

### 8.10 为什么 Tombstone 需要 GateDecisionRef

| 维度 | 内容 |
|---|---|
| 当前选择 | `TombstoneMember` 必须关联治理通过后的 `GateDecisionRef` |
| 备选方案 | 普通管理员 command 直接 tombstone 成员 |
| 选择理由 | tombstone 会影响 work / process / runtime / memory / audit 等多域引用,属于高风险操作 |
| 约束 | 未通过 Gate 不得 tombstone;通过后必须记录 gate_decision_ref、影响范围和后续归档状态 |
| 演进路径 | 后续可把 tombstone flow 与 archive job、downstream projection cleanup、audit report 串联 |

核心流程:

```text
TombstoneMember
  |
  v
Governance Gate
  |
  +-- reject --> command rejected
  |
  +-- allow
        |
        v
      identity records:
        - lifecycle: tombstoned
        - gate_decision_ref
        - tombstone_record
        - outbox(identity.member.tombstoned)
```

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: 分层模型(当前) | 方案 B: 身份 / 承担 / 认证混合模型 |
|---|---|---|
| 全局身份一致性 | 高 | 低 |
| 多仓边界清晰度 | 高 | 低 |
| 入口安全机制变更成本 | 低 | 高 |
| 项目内角色扩展弹性 | 高 | 低 |
| 前台展示接入复杂度 | 中 | 低(表面) |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 不是单一用户系统,而是多仓协作平台。它既需要稳定的全局成员真相,也需要允许 work / process / runtime / conversation 在各自边界内消费身份。如果把身份真相、入口安全机制、平台级角色、项目承担关系和只读展示混成一层,后续任何入口或下游仓变化都会拖动整个 identity 模型,长期不可维护。

## 10. 关键接口与数据流

### 10.1 核心接口列表(概要级)

本节只定义概要级接口族和调用边界,不展开完整 request / response payload。

#### Command API

Command API 用于改变 identity 真相。调用方身份校验由 Gateway / API Layer 完成,identity 只消费可信 `ActorContext`。

| 接口 | 输入概要 | 成功结果 | 幂等性 | 关键约束 |
|---|---|---|---|---|
| `HireGlobalMember` | `ActorContext`、role_id、profile、capability_seed、request_id | 创建 `GlobalMember{state=hired}`、写 lifecycle history、写 outbox `identity.member.hired` | 是 | role_id 必须存在且非 retired;创建必须显式 command |
| `ActivateMember` | `ActorContext`、member_id、reason、gate_ref? | lifecycle 变为 active、写 lifecycle history、写 outbox | 是 | 只能从 hired / paused 迁移 |
| `PauseMember` | `ActorContext`、member_id、reason | lifecycle 变为 paused、写 lifecycle history、写 outbox | 是 | 只能从 active 迁移 |
| `RetireMember` | `ActorContext`、member_id、reason | lifecycle 变为 retired、写 lifecycle history、写 outbox | 是 | 只能从 active / paused 迁移 |
| `TombstoneMember` | `ActorContext`、member_id、gate_decision_ref、archive_policy | lifecycle 变为 tombstoned 或进入 pending、写 tombstone_record、写 outbox | 是 | 必须有关联 Gate 决策;通常要求 member 已 retired |
| `ChangeRole` | `ActorContext`、member_id、role_id、secondary_roles? | 更新成员 role 引用、写 audit、写 outbox `identity.role.changed` | 是 | role_id 必须来自有效 `RoleCatalogEntry` |
| `UpdateCapabilityProfile` | `ActorContext`、member_id、capability_patch、evidence_refs | 更新 `CapabilityProfile`、写 audit、写 outbox | 是 | evidence refs 必须可追溯;不得表达项目内临时分工 |
| `UpdateMemoryRefs` | `ActorContext`、member_id、semantic_ref?、episodic_refs?、archive_ref? | 更新 memory refs、写 audit、写 outbox `identity.memory_ref.updated` | 是 | identity 只保存 ref,不保存 memory 原文或向量 |

#### Query API

Query API 用于读取 projection 或审计视图。查询接口不得自动创建成员。

| 接口 | 输入概要 | 输出概要 | 幂等性 | 关键约束 |
|---|---|---|---|---|
| `GetMemberSummary` | member_id / name | member_id、name、lifecycle、role、capability 摘要、memory refs 摘要 | 是 | 查询不到返回 NotFound,不得隐式创建 |
| `GetMemberLifecycleTrace` | member_id | lifecycle 变化轨迹、actor、reason、gate_ref、trace_id | 是 | 面向 Owner / Admin / Auditor / governance |
| `GetRoleCatalog` | filter、version? | 可用 `RoleCatalogEntry` 列表和 fingerprint | 是 | 返回 role 索引,不返回完整 `RoleDefinition` 正文 |
| `ListMembersByLifecycle` | lifecycle、page | 成员摘要列表 | 是 | 走 query projection,不扫写模型聚合 |
| `GetMemberAuditTrace` | member_id、time_range?、event_types? | lifecycle / role / capability / memory / career 审计链 | 是 | 按调用方权限裁剪敏感字段 |

#### Inbound Event Consumer

Inbound event 用于接收其他模块已经发生的事实。event consumer 必须幂等,并在需要时追加本地记录或刷新 projection。

| 事件 | 来源 | identity 处理 | 关键约束 |
|---|---|---|---|
| `method_library.role_definition.changed` | method-library | 刷新 `RoleCatalogEntry` 索引 | 不复制 `RoleDefinition` 正文 |
| `work.project_member.changed` | work | 追加 `career_history` 或刷新 career projection | `ProjectMember` 真相仍属于 work |
| `process.activity.member_used` | process | 可追加执行经历或能力证据引用 | 不把 process runtime state 写成身份真相 |
| `memory.archive.status_changed` | memory / archive | 更新 memory ref / archive ref 状态 | identity 只保存 ref 与状态 |
| `governance.gate_decision.completed` | governance | 记录 `GateDecisionRef`,驱动 tombstone 等高风险流程 | governance 拥有决策正文 |

#### Outbound Event

Outbound event 必须先写入 outbox,再由 publisher 异步发布到 L0-bus。

| 事件 | 触发来源 | 主要消费者 | 说明 |
|---|---|---|---|
| `identity.member.hired` | `HireGlobalMember` | work / process / runtime / conversation | 新成员已创建 |
| `identity.member.lifecycle_changed` | lifecycle command | work / process / runtime / governance | 成员生命周期变化 |
| `identity.role_catalog.synced` | role catalog sync | runtime / console / governance | 角色目录索引已刷新 |
| `identity.capability.updated` | `UpdateCapabilityProfile` | work / process / runtime / governance | 能力画像已更新 |
| `identity.career.appended` | career append flow | console / audit / recommendation | 生涯记录已追加 |
| `identity.memory_ref.updated` | `UpdateMemoryRefs` / archive event | runtime / memory / archive / audit | 记忆引用已更新 |
| `identity.member.tombstoned` | `TombstoneMember` | work / process / runtime / memory / audit | 成员已 tombstone |

## 11. 横切关注点

### 11.1 安全与授权

identity 管理的是 AI 员工身份真相,但不负责登录、token、session 或 credential 校验。外部入口由 Gateway / API Layer 完成身份校验,identity 只消费可信 `ActorContext`。

| 维度 | 策略 |
|---|---|
| 服务入口 | Gateway / API Layer 校验调用方并注入 `ActorContext`;identity 不实现登录或 token 校验 |
| Command 授权 | `HireGlobalMember`、lifecycle command、`ChangeRole`、`UpdateCapabilityProfile`、`UpdateMemoryRefs`、`TombstoneMember` 必须按 actor 权限和业务规则校验 |
| Assistant 权限 | Assistant 可以发起建议、创建请求或触发受控流程,不得绕过授权直接改写身份真相 |
| Gate 绑定 | tombstone 等高风险 command 必须记录 `GateDecisionRef` |
| Query 字段裁剪 | `GetMemberSummary` 可按调用方裁剪字段;敏感 memory refs / audit refs 需要额外权限 |
| 数据最小化 | tombstone 后只保留最小身份、归档引用和审计引用 |
| 安全审计 | 未授权写、Gate 拒绝、敏感字段读取必须进入 audit trace |

### 11.2 性能

性能预算只约束 identity 自身能控制的路径。外部审批、归档和人工决策不伪装成同步低延迟能力。

| 环节 | 预算 | 说明 |
|---|---|---|
| `GetMemberSummary` | < 50ms P95 | 走 query projection,避免跨域实时 join |
| `ListMembersByLifecycle` | < 100ms P95 | 依赖 lifecycle 索引和分页 |
| Command 写入 | < 200ms P95 | 覆盖校验、write model、append-only records、outbox 写入 |
| `RoleCatalogEntry` 同步滞后 | < 5s | method-library 正常可用时的目标 |
| outbox 发布滞后 | < 30s P95 | L0-bus 正常可用时的目标 |
| projection 滞后 | < 30s P95 | 事件正常消费时的目标 |
| tombstone flow | 不承诺同步完成 | 归档、Gate、延迟期完成前不得假成功 |

### 11.3 可用性与恢复

| 场景 | 正确策略 | 禁止做法 |
|---|---|---|
| L0-bus 暂时不可用 | write model 与 outbox 同事务提交,等待 publisher 重试 | domain 直接调用 bus 并在失败时丢弃事件 |
| query projection 异常 | 从 append-only records / outbox checkpoint 重建投影 | 手工改 projection 反写真相 |
| method-library 暂时不可用 | 读取已有 `RoleCatalogEntry` 缓存;依赖未知 role 的写操作拒绝或等待 | 临时复制 `RoleDefinition` 正文到 identity |
| governance Gate 不可用 | 需要 Gate 的 command 失败或等待,保留 trace | 绕过 Gate 直接写高风险状态 |
| memory / archive adapter 不可用 | 保留 memory ref 与失败证据,由补偿任务重试 | 将 memory 原文或向量复制进 identity |
| tombstone 未闭环 | 标记 pending / failed,暴露给人工审查 | 提前物理删除或提前标记完成 |

### 11.4 可观测性

可观测性围绕“身份状态是否可信、事件是否送达、投影是否滞后、敏感操作是否可追溯”展开。

| 观测对象 | 推荐信号 | 用途 |
|---|---|---|
| command 写入 | success / failure / reject count,latency | 判断身份写路径是否健康 |
| lifecycle transition | from / to / actor / rejection reason | 追踪非法状态迁移与治理拒绝 |
| outbox | pending count,max pending age,publish failure | 发现事件堆积与 bus 故障 |
| query projection | lag,rebuild count,last source event | 发现读模型陈旧或重建异常 |
| role catalog sync | source_drift,unknown_role_reference | 发现 method-library 与 identity 本地索引漂移 |
| unauthorized write | actor,command,resource,decision | 安全审计与异常行为分析 |
| tombstone flow | pending count,failed count,archive ref status | 发现销毁流程未闭环 |
| consumer replay | replay count,idempotency hit | 验证事件消费幂等性 |

### 11.5 配置管理

| 配置项 | 说明 | 调整原则 |
|---|---|---|
| PostgreSQL 连接 | write model / append-only / projection / outbox 共用存储配置 | 需要支持连接池、超时和迁移版本 |
| outbox worker | poll interval,batch size,retry backoff | 优先保证可靠投递,再优化延迟 |
| bus endpoint | 事件发布目标与 topic 映射 | 不写入 domain 层,只在 adapter 配置 |
| role sync reconciliation | 与 method-library 的同步周期和漂移检测阈值 | 不影响 `RoleDefinition` 单一真相源 |
| projection rebuild | batch size,checkpoint interval | 支持可控重建和回放 |
| memory / archive adapter | memory ref 与 archive ref 的服务端点 | identity 只保存 ref,不保存内容 |
| Gate policy mapping | 哪些 command 需要 `GateDecisionRef` | 由 governance 策略驱动 |
| observability sink | metrics / logs / traces / audit sink | 故障时不得丢失关键审计线索 |
| tombstone retention | 延迟期、归档窗口、最小保留字段 | 与治理和合规策略保持一致 |

### 11.6 成本

- 不把所有下游展示需求直接并入 identity 主真相层,避免模型膨胀
- 不复制 `RoleDefinition` 正文,避免 method-library 与 identity 双真相
- 不保存 memory 原文或向量,避免 identity 变成记忆系统
- 不把 projection 当写源,避免为了读性能牺牲事实一致性
- 不为了降低短期接入成本绕过 outbox / Gate / audit trace

## 12. 风险与待确认事项

### 12.1 常见风险

identity 的主要风险不是单个字段设计错误,而是身份真相源与外部域协作时出现边界漂移、事件丢失、权限绕过或销毁流程未闭环。

| 风险 | 概率 | 影响 | 触发信号 | 缓解 |
|---|---|---|---|---|
| `GlobalMember` 与 `ProjectMember` 边界混层 | 中 | 高 | identity 出现 project role / assignment 真相字段 | `ProjectMember` 保持在 work 域,identity 只持稳定引用或 career 记录 |
| `RoleCatalogEntry` 与 method-library 漂移 | 中 | 高 | source_drift / fingerprint mismatch | 固定 role_id、version、fingerprint,增加 reconciliation worker |
| lifecycle 状态迁移非法 | 中 | 高 | command reject rate 上升 / 异常 from-to | domain 层集中校验状态机,敏感迁移绑定 `GateDecisionRef` |
| Gate 被绕过或不可用 | 中 | 高 | 缺失 `GateDecisionRef` / Gate timeout | 需要 Gate 的 command 失败或等待,不得降级为直接写 |
| outbox 堆积或发布失败 | 中 | 高 | pending age 超阈值 / publish failure | outbox retry、告警、人工 replay,write model 不直接发 bus |
| 事件乱序或重复导致投影错误 | 中 | 中 | idempotency miss / projection lag | source_event_id 幂等、checkpoint、rebuild |
| `career_history` 顺序或体量失控 | 中 | 中 | append count 激增 / 查询变慢 | append-only 记录 trace_id,按成员分页,后续冷热分层 |
| tombstone flow 未闭环 | 中 | 高 | tombstone pending / failed > 0 | archive ref、retention、Gate、audit 全部完成后才进入 tombstoned |
| `MemoryRef` 无法解析或权限不匹配 | 中 | 中 | ref resolve failure / unauthorized ref read | 固定 ref scheme,读取时做权限裁剪,不保存原文和向量 |
| ownership 边界被扩大 | 低 | 高 | identity 出现 `RoleDefinition` 正文、memory 内容、runtime state | 架构评审阻断,保持 catalog-only / ref-only |

### 12.2 边缘风险

| 边缘风险 | 影响 | 建议处理 |
|---|---|---|
| secondary_roles 与 main_role 并发变更 | 角色视图短暂不一致 | role attach / detach 使用版本号或乐观锁 |
| 同名 `GlobalMember` 在 Chat / Console 中混淆 | 人工操作误选成员 | query projection 提供 display_name + global_member_id + lifecycle |
| Assistant 重复发起 hire 请求 | 可能重复创建成员 | command 使用 request_id / idempotency key |
| `ActorContext` 缺失 trace_id | 审计链断裂 | Gateway 必须注入 trace_id,identity 缺失时拒绝写 command |
| projection 读取到短暂旧数据 | 下游看到延迟状态 | 对敏感写后读场景返回 write result 或提示 projection lag |

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| `RoleCatalogEntry` 同步契约是否固定 role_id / version / fingerprint / source_ref | 03 阶段 | identity + method-library |
| 哪些 command 必须携带 `GateDecisionRef` | 03 阶段 | identity + governance |
| tombstone 延迟期、归档窗口和最小保留字段 | 03 阶段 | identity + governance + archive |
| MemoryRef URI / 权限语义是否统一 | 03 阶段 | identity + memory/archive |
| projection rebuild 的 checkpoint、batch size、replay 范围 | 03 阶段 | identity |
| audit event taxonomy 是否与 L0-audit / L0-bus 对齐 | 03 阶段 | identity + observability |

### 13.2 回滚策略

| 场景 | 回滚 / 降级策略 | 不允许的回滚 |
|---|---|---|
| Command 写入异常 | 暂停相关 command,保留 write model、append-only records 和 audit trace | 静默删除已提交事实 |
| outbox 堆积 | 暂停或扩容 publisher,从 outbox 重试 / replay | 跳过 outbox 直接发布事件 |
| projection 异常 | 暂停依赖该投影的读入口,从 checkpoint rebuild | 手工修改 projection 覆盖真相 |

| memory / archive ref 写错 | 暂停 adapter,保留失败证据,通过补偿任务修正 ref | 把 memory 内容写入 identity |
| tombstone flow 失败 | 标记 pending / failed,进入人工审查 | 提前物理删除或假完成 |

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-identity` 不是项目任务系统,也不是流程引擎。它是 **“全局身份真相仓”**。

你可以把它理解成:
- 平台里“谁是谁”
- 某个成员当前在全局范围内是否 active / paused / retired
- 平台怎样认出这个成员
- 这个成员具有什么平台级角色和能力
- 其他仓如何稳定地引用或映射这个成员

这些事情,都由 `L1-identity` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L1-identity`,这些身份事实就会散落在:
- `work` 的 assignee 字段里
- `process` 的执行人上下文里
- `conversation` 的用户显示信息里
- `runtime` 的执行代理里
- 外部认证源的瞬时回调里

结果就会出现:
- 平台里到底“谁是谁”说不清
- 全局身份状态和项目内承担关系混在一起
- 各仓各自缓存一份成员真相,最后彼此漂移
- 平台级权限、项目级角色、执行代理身份被混成一层

所以 `L1-identity` 必须独立存在,作为:
> **全局身份真相与身份映射边界的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### GlobalMember
就是:
> 平台里的全局成员主语。

它回答的是:
- 这个成员是谁
- 当前在平台层是否 still active
- 全局身份是否还有效

#### ProjectMember
就是:
> `GlobalMember` 在某个具体项目里的承担分身。

它不是“谁是谁”的全局真相,而是:
- 这个成员在该项目里承担什么角色
- 当前是否可以承接项目内工作

#### 身份凭证 / 认证来源
就是:
> 平台是如何认出某个成员的外部接入方式。

它回答的是“怎么认出他”,不是“他是谁”。

#### 平台级角色 / 能力
就是:
> 某个成员在平台范围内具有什么角色、能力和权限边界。

它不等同于项目内角色。

#### 分身映射 / 身份接缝
就是:
> 其他仓如何稳定消费 identity,而不直接持有一份新的成员真相。

#### 审计投影 / 身份摘要
就是:
> 把身份变化、角色变化、绑定变化做成只读视图给外部看。

它不是主真相层。

### 1.4 内容采集结论(本仓当前重写基线)

本次重写 `L1-identity/02` 时,先收稳以下前提:
- `L1-identity` 不应按对象数拆,而应按主要部分拆
- identity 至少应拆成“全局成员主语 / 身份凭证与认证接缝 / 全局角色与能力映射 / 对外身份映射与分身接缝 / 身份审计与只读投影”五个主要部分
- `GlobalMember` 与 `ProjectMember` 必须严格分层
- “这个成员是谁”和“系统怎么认出他”不是同一层
- 平台级角色/能力和项目内承担角色不是同一层
- 对外系统接缝和只读审计投影也不是同一层

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,成员身份不是项目内的一个附属字段,而是平台级的根事实之一。用户真正需要的是:
- 平台里“谁是谁”有统一真相
- 这个成员当前是否 still active / paused / retired 能被稳定判断
- 平台如何认出这个成员,且能稳定地绑定外部认证源
- work / process / conversation / runtime 都能消费同一套身份锚点,而不是各自维护一份成员真相

如果把这些身份逻辑分别塞到:
- `work` 的 assignee / ProjectMember
- `process` 的 actor context
- `conversation` 的用户显示
- `runtime` 的执行代理
- 外部认证源的临时回调

系统会快速退化成:
- 平台里到底“谁是谁”说不清
- 全局身份状态和项目内承担关系混在一起
- 平台级角色能力和项目级角色混层
- 外部 auth source 一变化,内部身份模型也跟着抖动
- 不同仓看到的同一个成员状态不一致

因此,本概要设计的任务就是:
> **把 `L1-identity` 写成一个新人也能看懂的“全局身份真相仓”,而不是把成员、角色、凭证、投影混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 全局成员真相 | 容易被各仓局部字段替代 | `GlobalMember` 成为唯一身份锚点 | 需写死边界 |
| 身份 vs 承担关系 | `GlobalMember` 与 `ProjectMember` 易混 | 全局身份与项目分身严格分层 | 需正式落图 |
| 认证接缝 | 易把 auth source 细节写进核心身份模型 | 外部认证与核心真相解耦 | 需单列接缝部分 |
| 平台级能力 | 易和项目内角色混层 | 平台级能力映射独立存在 | 需形成主要部分 |
| 只读投影 | 易直接暴露真相对象给外部 | summary / trace / audit 投影只读 | 需明确投影边界 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让全平台对“谁是谁、当前是否有效、具有什么平台级能力”有统一判断,而不是各仓各自保存一份成员真相
- **技术问题**:`GlobalMember`、认证接缝、平台级角色能力、下游身份映射、只读审计投影之间的边界如何稳定建模,并支持后续测试、验收和实现

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ external auth / org source │
                    │ - login source             │
                    │ - member directory         │
                    └────────────┬───────────────┘
                                 │ credential / member source
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ conversation / console     │   │ identity                   │   │ work                       │
│ - member summary view      │◀──│ - GlobalMember             │──▶│ - ProjectMember            │
│ - lifecycle trace          │   │ - credential binding       │   │ - assignee refs            │
│ - audit projection         │   │ - platform role/capability │   └────────────────────────────┘
└────────────────────────────┘   └────────────┬───────────────┘
                                              │ identity refs / capability mapping
                                              ▼
                    ┌────────────────────────────┐
                    │ process / runtime          │
                    │ - execution identity       │
                    │ - actor context            │
                    └────────────┬───────────────┘
                                 │ audit / role / lifecycle consume
                                 ▼
                    ┌────────────────────────────┐
                    │ governance / observability │
                    │ - policy / audit use       │
                    │ - trace / record           │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `external auth / org source` 提供外部认证和成员来源,`identity` 负责把这些输入稳定映射成平台级全局成员真相
- `work` 不负责“谁是谁”的全局真相,只消费 `identity` 提供的 `GlobalMember` 引用并映射为 `ProjectMember`
- `process` / `runtime` 消费的是 identity 提供的执行身份、角色能力和 actor context,但不反向定义身份真相
- `conversation / console` 主要消费 identity 的只读摘要与审计投影,用于展示和调试
- `governance / observability` 消费 identity 的角色、能力和变更轨迹,用于策略和审计

所以 `L1-identity` 在全局里的角色是:
> **全平台身份真相、认证映射、角色能力边界和身份投影的根仓。**

### 4.3 系统边界

**做什么**:
- 保存平台级 `GlobalMember` 真相与生命周期状态
- 接收并映射外部认证源 / 成员来源
- 定义平台级角色与能力映射
- 向 work / process / conversation / runtime 暴露稳定身份引用与投影
- 提供身份相关的审计与只读摘要

**不做什么**:
- 不负责 `ProjectMember` 真相
- 不负责 `WorkItem` assignee 历史真相
- 不直接承担 process / runtime 的业务状态正文
- 不把投影视图反向当成身份真相写源
- 不把项目级角色分配当成平台级角色真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| external auth source | 99.9% | 保留已同步身份真相,新登录/绑定受阻 |
| external org/member directory | 99.9% | 使用最后一次稳定成员索引 + source drift 告警 |
| work | 99.9% | assignee / ProjectMember 同步延迟,但不改 identity 真相 |
| process / runtime | 99.9% | actor context 同步延迟,但不改 identity 真相 |
| conversation / console | 99.9% | 身份摘要投影延迟,不影响主真相层 |

### 4.5 关键依赖风险

- 若 `GlobalMember` 与 `ProjectMember` 边界不清,identity 和 work 会发生真相混层
- 若认证接缝和全局成员主语混层,更换外部 auth source 时会拖动整个 identity 真相模型
- 若平台级角色能力和项目级承担角色混层,后续权限、治理和执行会出现语义漂移
- 若投影层被误当成写源,conversation / console 的展示数据可能反向污染 identity 真相

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 全局成员主语部分

- **它是什么**: 这是 `L1-identity` 的全局身份真相层,一起回答“平台里谁是谁、当前身份是否仍有效”
- **为什么单独有它**: 如果没有独立的全局成员主语,后续 work/process/runtime 各自都会保存一份成员真相,最后必然漂移
- **负责什么**:
  - 定义 `GlobalMember` 及其全局生命周期
  - 提供全局唯一身份锚点
  - 作为其他部分的身份根对象
- **不负责什么 / 容易混淆点**:
  - 不负责项目内承担关系
  - 不负责外部认证源正文
  - 最容易和 `ProjectMember` 混淆
- **与其他部分交互**:
  - 上游: 身份凭证与认证接缝部分
  - 下游: 全局角色与能力映射部分、对外身份映射与分身接缝部分、身份审计与只读投影部分
  - 交互类型: 全局真相输入型
- **后续详细设计展开点**:
  - `GlobalMember` 对象模型
  - lifecycle state 与变更轨迹

#### 身份凭证与认证接缝部分

- **它是什么**: 这是 identity 与外部认证/目录系统之间的接入层,一起回答“系统如何认出某个成员”
- **为什么单独有它**: “这个成员是谁”和“系统怎么认出他”不是一回事,如果混写,一旦换 auth source,核心身份模型也会被拖动
- **负责什么**:
  - 接收外部认证源/凭证源
  - 把外部身份绑定到内部全局成员主语
  - 提供 credential / auth source 映射
- **不负责什么 / 容易混淆点**:
  - 不负责全局成员真相本体
  - 不直接承担项目内角色分配
  - 最容易和全局成员主语部分混淆
- **与其他部分交互**:
  - 上游: 外部认证源 / 目录源
  - 下游: 全局成员主语部分
  - 交互类型: 认证接入型 + 身份绑定型
- **后续详细设计展开点**:
  - credential binding / auth source ref
  - 认证接缝 DTO

#### 全局角色与能力映射部分

- **它是什么**: 这是平台级权限与能力边界层,一起回答“这个成员在平台范围内具有什么角色和能力”
- **为什么单独有它**: 平台级能力与项目内承担角色不是一回事,不单列会把平台权限和项目角色混成一层
- **负责什么**:
  - 定义平台级角色
  - 定义能力映射与授权来源
  - 为其他仓提供平台级权限边界输入
- **不负责什么 / 容易混淆点**:
  - 不负责 `ProjectMember` 项目内承担角色
  - 不直接负责 UI 展示摘要
  - 最容易和项目级 role 混淆
- **与其他部分交互**:
  - 上游: 全局成员主语部分
  - 下游: 对外身份映射与分身接缝部分、身份审计与只读投影部分
  - 交互类型: 平台能力映射型
- **后续详细设计展开点**:
  - role / capability 模型
  - platform-level policy 输入

#### 对外身份映射与分身接缝部分

- **它是什么**: 这是 identity 和其他仓之间的稳定接缝层,一起回答“其他仓如何消费 identity 而不复制一份新真相”
- **为什么单独有它**: 这是 identity 的多仓边界核心,不单列的话,下游仓会直接耦合 identity 内部模型
- **负责什么**:
  - 暴露稳定 member refs
  - 支持 `work/process/conversation/runtime` 消费身份
  - 支撑分身或局部映射的建立
- **不负责什么 / 容易混淆点**:
  - 不负责只读展示摘要
  - 不直接等同 `ProjectMember` 真相
  - 最容易和身份审计与只读投影部分混淆
- **与其他部分交互**:
  - 上游: 全局成员主语部分、全局角色与能力映射部分
  - 下游: `work / process / conversation / runtime`
  - 交互类型: 稳定引用接缝型
- **后续详细设计展开点**:
  - member ref / downstream sync 模型
  - identity event / ref 协议

#### 身份审计与只读投影部分

- **它是什么**: 这是 identity 的只读展示与审计层,一起回答“外部如何读取身份变化与身份摘要”
- **为什么单独有它**: 如果不单列,conversation / console / admin UI 会直接读 identity 真相对象,导致投影和真相混层
- **负责什么**:
  - 提供 member summary
  - 提供 lifecycle trace / role trace
  - 提供审计投影
- **不负责什么 / 容易混淆点**:
  - 不拥有成员真相
  - 不反向成为写源
  - 最容易和对外身份映射与分身接缝部分混淆
- **与其他部分交互**:
  - 上游: 全局成员主语部分、认证接缝部分、角色与能力映射部分、对外身份接缝部分
  - 下游: `conversation / console / admin / observability`

## 8. 关键技术选型

### 8.1 为什么采用“全局身份真相 / 项目分身”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | `GlobalMember` 与 `ProjectMember` 分层 |
| 备选方案 | 各仓各持一份成员真相 / 不区分全局成员与项目成员 |
| 选择理由 | 避免多仓身份漂移,同时保留项目内承担关系独立演化能力 |
| 演进路径 | 后续可在更多仓引入下游分身,但不破坏全局真相锚点 |

### 8.2 为什么认证接缝与身份真相分离

| 维度 | 内容 |
|---|---|
| 当前选择 | auth / credential source 与 `GlobalMember` 真相分离 |
| 备选方案 | 把认证源字段直接并入核心身份对象 |
| 选择理由 | 降低外部认证源变化对核心身份模型的冲击 |
| 演进路径 | 后续可接更多认证源,但 identity 主真相结构保持稳定 |

### 8.3 为什么平台级角色能力与项目级角色分离

| 维度 | 内容 |
|---|---|
| 当前选择 | platform role / capability 独立于 project role |
| 备选方案 | 用同一套角色字段覆盖平台层与项目层 |
| 选择理由 | 避免权限模型和承担模型混层,便于 governance / runtime / work 各自消费 |
| 演进路径 | 后续可扩展能力域映射,但不把项目承担角色拉回全局身份真相 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: 分层模型(当前) | 方案 B: 身份 / 承担 / 认证混合模型 |
|---|---|---|
| 全局身份一致性 | 高 | 低 |
| 多仓边界清晰度 | 高 | 低 |
| 外部 auth source 变更成本 | 低 | 高 |
| 项目内角色扩展弹性 | 高 | 低 |
| 前台展示接入复杂度 | 中 | 低(表面) |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 不是单一用户系统,而是多仓协作平台。它既需要稳定的全局成员真相,也需要允许 work / process / runtime / conversation 在各自边界内消费身份。如果把身份真相、认证接缝、平台级角色、项目承担关系和只读展示混成一层,后续任何一个外部源或下游仓变化都会拖动整个 identity 模型,长期不可维护。

## 11. 横切关注点

### 11.1 安全
- 身份真相与认证接缝必须分层,防止外部 auth source 直接污染核心模型
- platform role / capability 不能与 project role 混层
- 下游只能消费稳定引用或投影,不能回写全局身份真相

### 11.2 性能
- GlobalMember 查询与 summary 投影查询应支持高频读
- 身份同步写路径不应被投影更新阻塞

### 11.3 可用性
- 外部认证源短时不可用时,保留最后一次稳定全局身份真相
- 下游分身同步可延迟,但不得篡改主真相

### 11.4 可观测性
- lifecycle 变化、绑定变化、角色变化都必须可追踪
- identity 事件和下游消费链应可审计

### 11.5 成本
- 不把所有下游展示需求直接并入 identity 主真相层,避免模型膨胀

### 11.6 性能预算表(端到端延迟分解)

|---|---|---|

| ResolveMemberRef 查询 | ≤ 50ms | 50ms |
| summary projection 查询 | ≤ 100ms | 100ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |

| 投影层被误当写源 | 中 | 中 | 强化只读边界与审计检查 |

- 若未来引入更多外部 auth source,credential binding 模型可能需要扩展

## 13. 上线策略

## 3. 技术风险评估与 Spike

### 3.1 风险评估表

| 风险项 | 影响范围 | 是否需要 Spike | 验证方式 | 通过标准 |
|---|---|---|---|---|
| 本地事务 + outbox + audit + idempotency 同事务写入 | 所有 Command / Event 写路径 | 是 | 写最小 `HireGlobalMember` transaction prototype | member、history、audit、outbox、idempotency 同成同败 |
| sqlx 初始 schema 与编译期 SQL 校验 | 数据层、CI | 是 | 建最小 migration + sqlx query check | CI 中 SQL 校验可运行,字段类型可编译 |
| Outbox 发布状态机 | Operations、L0-bus | 是 | 用 stub bus 模拟 success / fail / retry | success 标记 published,fail 标记 failed / next_retry_at,不回滚 write model |
| Projection rebuild + checkpoint | Query、恢复能力 | 是 | 用 outbox event 重建 member summary | 按顺序 apply,失败时 checkpoint 不越过失败事件 |
| Event consumer 幂等与 dead-letter | Inbound Event | 是 | 重复事件、坏事件、依赖失败三类输入 | 重复不重复写,坏事件留 dead-letter,失败可 replay |
| Gate / Tombstone 协作 | 高风险 lifecycle | 可选 | governance stub 返回 approved / rejected / unavailable | 无 approved Gate 不进入 tombstoned |
| GetMemberSummary P95 | Query 性能 | 可选 | projection query benchmark | 第一批记录基线,不得实时拼装外部正文 |

### 3.2 Spike 产出要求

每个 Spike 必须产出一页以内结论,写清:

```text
验证了什么
使用了什么最小代码或脚本
结果是什么
结论: 可行 / 需调整 / 不可行
对 03-详细设计 和 07-实施计划 是否有影响
```

Spike 代码是一次性验证代码,不直接合入主干。若结论为“需调整”或“不可行”,必须先修订对应设计文档,再进入 Phase 1。

## 5. 阶段依赖拓扑

### 5.1 总体关键路径

```text
Phase 0  阅读确认 + Spike
   |
   v
Phase 1  骨架可启动
   |
   v
Phase 2  数据层闭环
   |
   v
Phase 3  P0 主链路贯通
   |
   v
Phase 4  防御性补全
   |
   v
Phase 5  生产化与验收收口
```

关键路径是:

```text
基础类型 / 服务骨架
      -> UnitOfWork / Repository / Outbox / Projection
      -> SyncRoleCatalog
      -> HireGlobalMember
      -> PublishOutboxEvents
      -> RebuildMemberSummaryProjection
      -> GetMemberSummary
      -> Redline / Recovery / Observability / Acceptance
```

### 5.2 Phase 2 内部可并行项

```text
Phase 2 数据层闭环
   |
   +--> write model repository
   |
   +--> append-only / audit repository
   |
   +--> outbox / idempotency store
   |
   +--> projection / checkpoint store
```

并行规则:

| 规则 | 说明 |
|---|---|
| Phase 1 必须先完成 | 没有可启动骨架,后续代码无稳定落点 |

## 10. 结论

`L1-identity` 第一批实现应优先跑通 P0 最小闭环,而不是按对象清单平均推进。

推荐开发节奏是:

```text
先理解边界
再验证事务 / outbox / projection 风险
再搭骨架
再做数据层
再贯通 P0 主链路
最后补防御、运维和验收证据
```

只要严格遵守该顺序,实现者可以在最早阶段暴露最大风险,并避免在未验证事务与事件模型前堆叠大量业务代码。

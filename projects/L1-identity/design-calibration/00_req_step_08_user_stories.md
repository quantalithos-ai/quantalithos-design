## 4. 当前文档问题诊断

| 旧表现 | 问题 | 新处理 |
|---|---|---|
| 用户故事混合人类用户、上游系统、下游系统和具体操作 | 角色目标与系统依赖混层 | 按角色和能力节点重写 |
| 使用接口或命令名表达故事 | 过早进入 protocol 设计 | 改成“作为...我希望...以便...”的业务目标 |
| 认证、项目成员、runtime 和 method 编辑场景混入 | 越过 Step 2 边界 | 列为边界外故事 |
| 外围增强与核心闭环故事混在一起 | 核心需求优先级不清 | 分离外围增强故事 |
| 审计和后台维护故事不足 | 消费追溯能力缺少角色来源 | 补充 US-ID-014 / US-ID-015 |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 故事分组 | 按旧功能或系统调用分组 | 按 `C-ID-1`~`C-ID-5` 分组 | 贯彻能力小循环 |
| 故事主体 | 混合仓、服务和人类 | 人类角色、AI 主体、系统调用方、后台维护任务 | 对齐 Step 5 |
| 故事表达 | 可能含 API / event / command | 只表达业务目标和价值 | 避免实现化 |
| 边界外故事 | 容易进入核心故事 | 单独列出归属 | 防止串仓 |
| 外围增强 | 不易识别 | 单独记录,不进入核心表 | 保持核心闭环紧凑 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 按角色一次性列所有故事 | 阅读直观 | 容易漏掉能力闭环和追溯关系 | 不采用 |
| 方案 B: 按核心能力节点列核心故事 | 能保证故事到功能、规则、数据和验收可追溯 | 需要重复考虑同一角色在不同能力下的目标 | 采用 |
| 方案 C: 把所有系统消费方都写成独立故事 | 覆盖全面 | 故事数量膨胀,且与 Step 6 / Step 12 重叠 | 不采用 |

### 7.2 外围增强故事

| 故事 | 处理口径 |
|---|---|
| 作为管理者,我希望查看员工绩效评分和成长曲线 | 外围增强,不进入当前核心闭环 |
| 作为管理员,我希望连接外部 HR / IdP 自动同步员工 | 外部集成增强,后续阶段 |
| 作为用户,我希望有精美员工主页和社交动态 | UI / workspace 增强,不定义 identity truth |
| 作为平台,我希望自动计算能力等级 | 分析 / 评估能力,不进入当前需求主链 |

### 7.3 边界外故事

| 边界外故事 | 归属 |
|---|---|
| 创建或管理项目内 ProjectMember | `L1-work` |
| 登录、换 token 或验证 credential | 认证入口 / gateway |
| 编辑 RoleDefinition 或方法正文 | `L3-method-library` |
| 启停 AI 员工容器 | `L2-member-service` / `L2-runtime` |
| 检索或存储 memory 向量正文 | memory / archive / external store |

### 7.4 能力级故事停审

| 能力节点 | 停审结论 |
|---|---|
| C-ID-1 | 故事只围绕身份主语建立和读取,未滑入认证或 ProjectMember。 |
| C-ID-2 | 故事只围绕全局生命周期和审计,未滑入 runtime 编排。 |
| C-ID-3 | 故事只围绕角色能力摘要和来源,未保存 definition body。 |
| C-ID-4 | 故事只围绕生涯与记忆引用,未保存正文或项目 truth。 |
| C-ID-5 | 故事只围绕消费、追溯和对账,未把 UI / observability 当 truth。 |

## 4. 当前文档问题诊断

| 旧表现 | 问题 | 新处理 |
|---|---|---|
| 旧文档过早出现 RPC、Command、Query、Outbox 和事件名 | protocol 先于需求边界 | 改成能力级接口 |
| 读取接口可能隐式补数据 | 违反查询不写入规则 | 明确读取只返回结果或失败 |
| 外部来源读取未和数据归属绑定 | 可能读取外部正文 | 依赖输入只允许 refs、summary、state |
| 维护接口可能修复相邻仓 truth | 越过 identity 边界 | 明确对账只报告或修复 identity 派生状态 |
| 事件协作可能写成源码依赖 | 违反依赖裁剪 | 明确协议后移,依赖类型不变 |

---

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 接口表达 | RPC / command / event 名 | 能力级接口 | 避免锁定协议 |
| 依赖表达 | 具体系统或实现后端 | 相邻能力输入和依赖类型 | 对齐 Step 6 |
| 数据边界 | 字段 / payload 倾向 | 不携带禁止正文 | 对齐 Step 11 |
| 维护能力 | 可能执行修复 | 投影 / 引用对账能力边界 | 避免越权 |
| 下游消费 | 可能共享存储 | 查询 / 事件协作消费 | 保持 truth ownership |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 直接列 command/query/event/job | 后续实现方便 | 会提前形成不完整 schema,易触发 1:1 blocker | 不采用 |
| 方案 B: 只列能力级接口和依赖边界 | 稳定,可由详细设计推导多种协议 | 需要后续 `03` 补齐具体 schema | 采用 |
| 方案 C: 接口全后移,需求层不写 | 避免过早设计 | 后续无法知道哪些能力必须对外可见 | 不采用 |

### 7.3 能力边界与全局依赖类型映射

| 能力边界 | 依赖类型承接 | 禁止误写 |
|---|---|---|
| IF-ID-001 / IF-ID-002 | 依赖 `L0-core` 共享 refs;不直接依赖 UI 或 gateway 源码 | 不写登录认证协议 |
| IF-ID-004 | 与 method-library 运行期 / 事件协作 | 不写 method-library path dependency |
| IF-ID-005 | 与 work 运行期 / 事件协作 | 不写 ProjectMember schema |
| IF-ID-006 | 与 archive / memory 边界协作 | 不保存正文或向量 |
| IF-ID-007 | 通过查询 / 事件提供消费 | 不让消费方反写 identity truth |
| IF-ID-009 | 维护对账只操作 identity 自身投影 / 引用 | 不修复相邻仓 truth |

### 7.4 跨能力接口审计

| 检查项 | 结论 |
|---|---|
| 每个接口 / 依赖是否回指功能需求 | 通过 |
| 是否写 API path、DTO schema 或 trait | 未写 |
| 是否把全局仓依赖表原样重抄 | 未重抄,已转为能力边界 |
| 是否把运行期 / 事件依赖写成编译期依赖 | 未写 |

## 1. 业务背景与驱动力

### 1.1 业务背景

过程域回答的不是"做什么",而是**"按什么规矩推进"**。在 Quantalithos 中:
- Project 是否 active,由 work 域决定
- WorkItem 是否 done,由 work / artifact 决定
- 但**整个项目当前在第几个阶段、下一个该执行哪个 Activity、何时该停下来等人类决策、崩溃后从哪恢复**——都由 process 域负责

L1-process 是平台的**过程引擎**。它把:
- SPEM Definition vs Use
- BPMN Activity / Gateway / Event / SequenceFlow
- 24748-2 8 种生命周期模型
- 29110 Tailoring
- Temporal / LangGraph 的持久执行理念

综合成一个能真正推进项目的运行时系统。

### 1.2 业务驱动力

**业务驱动力**:
- 用户不只是要一个聊天机器人,而是要一个**按过程推进的软件团队**
- 项目必须能够有阶段、里程碑、审批、回滚、恢复

**技术驱动力**:
- Template/Profile/Instance 三段式
- checkpoint 每步持久化
- Gate 挂起 / 恢复
- BPMN 2.0 的控制流语义
- completion_policy 与 WorkItem 两轨交汇

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | CompleteActivity P95 | < 200ms | benchmark |
| 性能 | Checkpoint inline P95 | < 50ms | benchmark |
| 恢复 | 小 Instance 崩溃恢复 | < 30s | fault injection |
| 规模 | 活跃 Instance | 10w | 压测 |
| 规模 | 年 Activity 量 | 5000w | 压测 |
| 可靠性 | checkpoint 覆盖率 | 100% 每次 Activity 完成 | 回归测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| Template 家族新增 / 演进 | 中 | method-library source sync |
| Tailoring 决策变化 | 中 | Profile 冻结 + supersede |
| Activity 状态流转 | 高频 | state machine + event stream |
| checkpoint 大小 | 高频 | inline/external 双模 |
| future Deviation/GUIDED | 中 | 先不锁实现,留接口位置 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **流程引擎 + persisted state machine**(当前)| 最贴近需求,可恢复,可挂 Gate | 实现复杂 | ✅ |
| 纯工作流编排(Saga only) | 简单 | 无法承载 Template/Profile/Instance |
| 纯聊天驱动 | 开发快 | 无法表达正规过程与审计 |

**最终选择**:**Template/Profile/Instance 三段式 + Activity/Token 状态机 + checkpoint 链**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 三段式 | Definition / Use 边界清晰 | 需要多聚合协调 |
| checkpoint 每步写 | 崩溃恢复可靠 | 写放大 |
| method-library source sync | 不重复定义 | 需要 drift 对账 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
Owner / PM / AI Runtime
        │
        ▼
   ★ quantalithos-process ★
   - Template / Profile / Instance
   - BPMN engine
   - checkpoint / recovery
        │
   ┌────┼────────────┬────────────┬──────────────┐
   ▼    ▼            ▼            ▼              ▼
method- governance   work       artifact      member-service
library  gate flow   project    outputs       activity execution
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ Template 索引 / Profile / Instance / Activity / Token
- ✅ BPMN 控制流推进
- ✅ checkpoint 链
- ✅ waiting_gate / gate 恢复
- ✅ activity outputs 事件

**不做什么**:
- ❌ Method Content 正文(method-library)
- ❌ Gate 决策(governance)
- ❌ WorkItem 主状态机(work)
- ❌ Artifact 内容持久化(artifact)
- ❌ 容器执行(member-service/runtime)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则阻断 |
| object storage | 99.9% | inline 降级 / 暂停大实例 |
| method-library | 99.9% | 使用最后同步索引 + source_drift 告警 |
| governance | 99.9% | waiting_gate 挂起 |
| member-service | 99.9% | scheduled backlog |

### 4.4 关键依赖风险

- checkpoint 写频繁拖慢主流程
- Template source drift 导致新 Profile 冻结
- nested process / GUIDED 后续加入会增加复杂度

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Process Definition Index | 支撑子域 | Template 索引 |
| Runtime Execution | 核心域 | Instance / Activity / Token |
| Checkpoint & Recovery | 核心域 | 持久执行 |
| Gate Coordination | 支撑子域 | waiting_gate / resume |

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Definition | Template / Profile | ProcessTemplate / ProcessProfile |
| Runtime | Instance / Activity / Token | ProcessInstance / Activity / Token |
| Recovery | checkpoint / restore | Checkpoint |
| Coordination | gate suspend / resume | pending_gates |

### 5.3 上下文映射关系

- method-library → Definition: Customer-Supplier(source sync)
- work → Runtime: Project.start / pause / archive 驱动状态
- governance → Coordination: gate.decided → resume
- artifact → Runtime: approved/baselined 驱动流程推进
- Sprint Planning / refinement 这类 Activity 只表达节奏与选择,Backlog / Iteration / WorkItem 真相仍归 work

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |
|---|---|---|
| Template | 过程模板(Definition)| Definition |
| Profile | Tailoring 后的固定版本 | Definition |
| Instance | 正在跑的过程实例 | Runtime |
| Activity | Instance 内执行单元 | Runtime |
| Token | BPMN 控制流位置 | Runtime |
| Checkpoint | 恢复快照 | Recovery |
| waiting_gate | 等治理决策的挂起状态 | Coordination |

### 5.4 工作事实与流程节奏边界

```text
Backlog / WorkItem / Iteration
  = work 域真相

Sprint Planning / Backlog Refinement / Review / Retro
  = process 域 Activity / 节奏节点
```

**解释**:
- process 负责“什么时候整理、什么时候 planning、什么时候 review”
- work 负责“当前有哪些工作项、哪些进入 Backlog、哪些进入 Iteration”
- 因此 Sprint Planning 不创建 Backlog,只在时机到达时驱动对 Backlog 的选择与收口

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
process-api / operator
        │
        ▼
application / engine
   ├─ template/profile management
   ├─ instance runner
   ├─ token engine
   ├─ checkpoint manager
   └─ subscriptions
        │
        ├─▶ PostgreSQL
        ├─▶ object storage(large checkpoints)
        ├─▶ bus(outbox)
        └─▶ member-service / governance / artifact
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| process-api | RPC/HTTP 入口 | Python |
| engine | BPMN 推进 + state machine | Python |
| checkpoint worker | 恢复 / 大对象管理 | Python |
| subscriptions | 消费 work/governance/artifact 事件 | Python |
| postgres | templates/profiles/instances/activities/checkpoints/outbox | PostgreSQL |
| object storage | 大 checkpoint blob | S3 / MinIO |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| work → process | 事件驱动 | 六域平权 |
| governance → process | gate.decided 事件 | process 不直接轮询 |
| process → member-service | 调度 / 事件 | 隔离运行时 |
| process → artifact | activity outputs 事件 | 不存内容 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| `process_templates` | process(sync from method-library)| process |
| `process_profiles` | process | process / work |
| `process_instances` | process | process / work / observability |
| `activities` | process | process / member-service |
| `checkpoints` | process | process / observability |
| `process_events_outbox` | process | bus worker |

### 6.5 部署拓扑

- 单服务 + PostgreSQL 起步
- checkpoint manager 可内嵌
- object storage 只在大 checkpoint 场景启用

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api / rpc
   │
   ▼
application / engine
   │
   ▼
domain(Runtime / Definition / Recovery)
   ▲
   │ interfaces
infra(Postgres / object storage / bus / subscriptions)
```

### 7.2 层间约束规则

- engine 不直接理解 work 的业务语义,只消费 process_profile_id / workitem refs
- checkpoint 层不直接写业务聚合,只写 checkpoint chain
- subscriptions 不直接改 DB,走 application 用例
- Template 内容正文不落 process 仓,只存结构化索引

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| TemplateSource | application/domain | method-library sync adapter |
| CheckpointStore | domain | postgres + object storage |
| RuntimeDispatcher | application | member-service adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(work / governance / artifact / member-service 依赖) |
| 传出耦合 | 中(method-library / bus / pg / object storage) |
| 不稳定性 | 中 |
| 抽象度 | 中高 |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Template 索引 | process(sync) | process | 最终一致 + fingerprint |
| Profile | process | work / process | 聚合内强一致 |
| Instance | process | work / observability | 聚合内强一致 |
| Activity | process | member-service / artifact / governance | 聚合内强一致 + 事件 |
| Checkpoint | process | observability / recovery | append-only |

### 8.2 一致性层次

- Definition / Runtime 聚合内强一致
- method-library → process 同步最终一致
- work / governance / artifact / member-service 与 process 通过事件最终一致
- Checkpoint append-only,不修改历史

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| artifact.approved 延迟 | 等待该事件,不强推进 |
| gate.expired | 按 timeout_policy 处理 |
| member-service 执行失败 | retry / fail Activity |
| checkpoint 写失败 | 3 次重试后 Instance fail |

## 9. 关键技术选型

### 9.1 Python 作为实现语言

| 维度 | 内容 |
|---|---|
| 当前选择 | Python |
| 备选方案 | Rust / Go |
| 选择理由 | BPMN 引擎生态丰富,集成快 |
| 演进路径 | 若性能不够,核心 engine 可后迁 Rust |
| 不可逆程度 | 中 |

### 9.2 inline + external checkpoint

| 维度 | 内容 |
|---|---|
| 当前选择 | ≤256KB inline,>256KB external blob |
| 备选方案 | 全量 DB / 全量对象存储 |
| 选择理由 | 小实例快,大实例不压 DB |
| 演进路径 | 阈值可调 |
| 不可逆程度 | 低 |

### 9.3 method-library source sync

| 维度 | 内容 |
|---|---|
| 当前选择 | 本仓存执行索引 + source_fingerprint |
| 备选方案 | 每次运行时远程查 method-library |
| 选择理由 | 运行时性能与可用性优先 |
| 演进路径 | 可以加 cache / snapshot |
| 不可逆程度 | 中 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| GUIDED / Deviation 未落地 | 只影响后续模式扩展 | P2 |
| Nested process 只做占位 | 复杂场景无法跑 | P1 |
| Template 版本演进策略未完全细化 | method-library 升级复杂 | P1 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| Checkpoint P95 > 50ms | 持续 1 周 | 调整 inline/external 策略 |
| recovery > 30s | 持续 3 次 | 优化恢复流程 |
| source_drift > 3 / 月 | 1 月 | 增加更强一致的同步机制 |

### 12.3 演进步骤

```
阶段 1: iterative / waterfall 两模板跑通
阶段 2: 完整 Gateway / Token 语义稳定
阶段 3: Nested process 支持
阶段 4: GUIDED / Deviation 支持
```

### 12.4 目标架构

目标不是做"一个通用 BPMN 产品",而是做**为 Quantalithos 定制的过程引擎**:
- 对外坚持 Template/Profile/Instance 三段式
- 对内保证 checkpoint / gate / artifact / member-service 协调稳定

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| checkpoint 开销过高 | 中 | 高 | inline/external 分层 |
| gateway / token 语义实现 bug | 中 | 高 | exhaustive transition tests |
| waiting_gate 链断裂 | 低 | 高 | replay + observability trace |

### 13.2 边缘风险

- Nested process(CallActivity/SubProcess)引入复杂同步 bug
- GUIDED 模式使状态机急剧膨胀
- 大实例 checkpoint 链在 archive / restore 时复杂度上升

### 13.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| assignee 算法(轮询/负载/能力) | N2 前 | process + member-service |
| GUIDED / Deviation 何时转 Accepted | N2 后 | process + governance |
| nested process 的优先级 | N2 前 | process |

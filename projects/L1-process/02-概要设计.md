## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-process` 不是任务池,也不是审批系统。它是 **“项目过程节奏仓”**。

你可以把它理解成:
- 这个项目按什么过程模板推进
- 当前处在第几个阶段
- 现在该做 refinement、planning、implementation、review 还是 retro
- 什么时候要停下来等人审批
- 如果运行崩溃了,应该从哪一步恢复

这些事情,都由 `L1-process` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L1-process`,系统虽然可能还有:
- 对话
- 任务
- 审批
- 产物
- 运行时执行

但这些东西不会自动形成“按规矩推进的软件工程过程”。最终会变成:
- 大家知道有哪些任务,却不知道什么时候做 planning
- 工作项存在,但没有阶段与节奏
- 审批发生了,却没有和过程恢复点对齐
- runtime 执行了步骤,但系统不知道下一步该是什么
- 方法模板存在,却无法被裁剪成某个项目真正采用的过程

所以 `L1-process` 必须单独存在,作为:
> **项目过程节奏与运行实例状态的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Template
就是:
> 某类项目通常应该怎么推进的标准过程定义。

它更像一份标准蓝图,不是正在运行的实例。

#### Profile
就是:
> 在某个具体项目里,从 Template 裁剪出来的固定版本。

它回答的是:这个项目最终采用了哪种过程配置。

#### ProcessInstance
就是:
> 当前项目实际正在跑的那条过程实例。

它不是定义,而是运行态对象。

#### Activity
就是:
> 过程实例中的某一个执行节点。

例如:
- Backlog Refinement
- Sprint Planning
- Review
- Gate Approval Wait

#### waiting_gate
就是:
> 当前过程推进到这里,必须先等治理/人类决策,才能继续。

#### Checkpoint
就是:
> 当前过程跑到某一步时保存下来的恢复快照。

#### 和 `L1-work` 的区别
最关键的一句是:

```text
process 管“什么时候做什么”
work    管“有哪些正式工作事实”
```

所以:
- `Sprint Planning` 是 process 的节奏节点
- `Backlog / WorkItem / Iteration` 是 work 的工作事实

### 1.4 内容采集结论(本仓当前重写基线)

本次重写 `L1-process/02` 时,已经先收稳以下前提:
- `L1-process` 内部不应按对象数拆,而应按主要部分拆
- process 至少应拆成“定义与裁剪 / 实例运行 / 节奏节点 / 挂起恢复 / 协作投影”五个主要部分
- `Template / Profile` 属于定义与裁剪部分,不等同于运行实例
- `ProcessInstance / Activity / Token` 属于运行态真相,不等同于具体节奏动作
- planning / refinement / review / retro / gate entry 属于节奏节点管理部分,不是工作事实写入点
- waiting_gate / checkpoint / recovery 是独立能力,不只是普通节点名
- timeline / trace / progress summary 属于投影部分,不是真相源

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,项目不只是一个任务列表,也不只是一个聊天空间。用户真正需要的是:
- 项目能够按某种方法推进
- 在合适的时候做 refinement / planning / implementation / review / retro
- 在关键点暂停等待治理决策
- 崩溃之后还能恢复到上一次稳定进度

如果把这些节奏逻辑全部塞到 `work`、`governance`、`artifact` 或 `runtime` 里,最后会导致:
- 工作事实和过程节拍混层
- 审批点和执行点错位
- 恢复逻辑没有归属
- 模板/裁剪/实例无法清晰区分
- timeline / trace 与真相层混写

因此,本概要设计的任务就是:
> **把 `L1-process` 写成一个新人也能看懂的“过程节奏与运行实例仓”,而不是抽象的流程引擎术语集合。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 节奏边界 | 已有规则,但新人仍易与 work 混淆 | process 只负责节奏与推进 | 需更直白地解释 |
| planning 归属 | 易误解为创建 backlog 的地方 | planning 只做选择与收口时机 | 需正式落图 |
| waiting_gate 语义 | 架构层已明确 | 能被新人理解为“暂停等待审批” | 需用自然语言和流程图表达 |
| checkpoint / recovery | 已讨论成熟 | 能承接详细设计 | 需形成高层骨架 |
| 定义与运行态区别 | 已讨论,但仍容易口头滑混 | Template/Profile/Instance 边界清楚 | 需写成主要部分结构 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让项目真正“按规矩推进”,而不是只有任务和消息却没有过程节奏
- **技术问题**:Template / Profile / ProcessInstance 三段式、planning/review/gate 节奏节点、checkpoint/recovery、以及 process 与 work / governance / artifact / runtime 的边界如何稳定建模

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 process 的节奏职责 | planning/refinement/review/retro/gate 的角色无歧义 | 文档评审 |
| 明确 process 与 work 边界 | Sprint Planning 不创建 Backlog 真相 | 文档评审 + 后续测试 |
| 明确 checkpoint / gate / recovery 骨架 | 可承接 `03-详细设计.md` | 设计评审 |
| 明确 Template / Profile / ProcessInstance 主流程 | 运行链路可解释 | 文档评审 |
| 明确 process 内部主要部分拆分 | 读者能区分定义层 / 运行态 / 节奏层 / 恢复层 / 投影层 | 文档评审 |

### 3.2 非目标(明确不做)

- 不在本文定义 BPMN 节点级伪代码与状态机细节(留给 `03-详细设计.md`)
- 不在本文定义完整 child WorkItem proposal / accepted / rejected 流程(归 `L1-work` 与后续详细设计)
- 不在本文决定 `Deviation / GUIDED` 的最终机制(留给未来正式阶段)
- 不在本文接管 `Backlog / WorkItem / Iteration` 的真相定义(归 `L1-work`)
- 不在本文持有 Artifact 正文或 Runtime 执行正文模型

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ method-library             │
                    │ - process template         │
                    │ - tailoring source         │
                    └────────────┬───────────────┘
                                 │ template / profile source
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ conversation / console     │   │ process                    │   │ work                       │
│ - timeline / trace view    │◀──│ - Template / Profile       │──▶│ - Backlog / WorkItem facts │
│ - progress summary         │   │ - ProcessInstance          │   │ - Iteration commitment     │
│ - activity projection      │   │ - Activity / Token         │   └────────────────────────────┘
└────────────────────────────┘   │ - waiting_gate / checkpoint │
                                 └────────────┬───────────────┘
                                              │ gate wait / evidence outputs / execution timing
                                              ▼
                    ┌────────────────────────────┐
                    │ governance / artifact      │
                    │ - gate decision            │
                    │ - approved outputs         │
                    │ - baseline refs            │
                    └────────────┬───────────────┘
                                 │ execution intent / progress feedback
                                 ▼
                    ┌────────────────────────────┐
                    │ runtime / member-service   │
                    │ - activity execution       │
                    │ - runtime feedback         │
                    │ - retry / resume signal    │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `method-library` 提供过程定义与裁剪源头,`process` 负责同步、裁剪并运行这些定义
- `work` 负责保存正式工作事实,`process` 负责决定何时 planning / review / gate / retro
- `governance` 负责审批和策略决策,`process` 负责在 waiting_gate 时挂起与恢复
- `artifact` 提供过程输出的制品化落点和证据引用
- `runtime / member-service` 负责实际执行与反馈,而 `process` 只负责推进执行时机和实例状态
- `conversation / console` 消费 `process` 的 timeline / trace / progress projection,但不拥有运行实例真相

所以 `L1-process` 在全局里的角色是:
> **把方法定义、项目节奏、审批暂停、恢复能力和执行时机编织成一个可运行的过程引擎层。**

### 4.3 系统边界

**做什么**:
- 定义与运行过程节奏
- 驱动 planning / refinement / review / retro / waiting_gate 等节点
- 管理 Template / Profile / ProcessInstance / Activity / Token / checkpoint / recovery
- 向 runtime / member-service 发出执行意图,向 governance 发出等待决策请求
- 向 conversation / console 提供过程投影视图

**不做什么**:
- 不创建 Backlog / WorkItem / child WorkItem 真相
- 不决定 Gate 的最终审批结果
- 不持有 Artifact 正文真相
- 不接管 Runtime 内部执行正文与容器细节
- 不把投影视图反向当成真相写源

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| method-library | 99.9% | 使用最后同步索引 + source_drift 告警 |
| work | 99.9% | planning 节奏可阻塞,但不改写 work 真相 |
| governance | 99.9% | waiting_gate 挂起直到恢复 |
| artifact | 99.9% | outputs 事件延迟,不阻断主定义模型 |
| runtime / member-service | 99.9% | scheduled backlog / retry / resume |

### 4.5 关键依赖风险

- process 与 work 边界一旦不清,planning 节点就会偷做任务系统的工作
- checkpoint / recovery 若与运行时语义错位,恢复后会产生执行漂移
- waiting_gate 若与 governance 状态联动不稳,会让人类审批链失真
- timeline / trace 若被误当真相源,会导致 process 投影反写真相

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 过程定义与裁剪部分

- **它是什么**: 这是 `L1-process` 的定义层与裁剪层,一起回答“某类项目通常怎么推进、某个具体项目最终采用哪套过程配置”
- **为什么单独有它**: 如果把 Template / Profile 和运行实例混写,读者会把“过程定义”和“正在运行的过程”混成一件事
- **负责什么**:
  - 承接 method-library 的过程模板
  - 形成项目级固定的 ProcessProfile
  - 为运行态提供稳定过程定义来源
- **不负责什么 / 容易混淆点**:
  - 不负责保存当前实例运行位置
  - 不负责工作事实真相
  - 最容易和过程实例运行部分混淆
- **与其他部分交互**:
  - 上游: method-library
  - 下游: 过程实例运行部分
  - 交互类型: 定义输入型 + 裁剪输出型
- **后续详细设计展开点**:
  - Template / Profile 对象模型
  - source sync / drift 检测

#### 过程实例运行部分

- **它是什么**: 这是 `L1-process` 的运行态真相层,一起回答“当前项目过程实际跑到哪里、哪个节点活跃、控制流如何前进”
- **为什么单独有它**: 如果没有这一层,process 就只剩模板说明,没有真正可运行的实例语义
- **负责什么**:
  - 保存 ProcessInstance / Activity / Token
  - 推进节点执行与控制流位置
  - 为挂起恢复、节奏节点、投影提供运行态基础
- **不负责什么 / 容易混淆点**:
  - 不负责定义模板来源
  - 不直接等同于某个 planning / review 动作
  - 最容易和节奏节点管理部分混淆
- **与其他部分交互**:
  - 上游: 过程定义与裁剪部分
  - 下游: 节奏节点管理部分 / 挂起与恢复部分 / 协作视图与投影部分
  - 交互类型: 运行态真相推进型
- **后续详细设计展开点**:
  - ProcessInstance / Activity / Token 模型
  - 状态机与推进规则

#### 节奏节点管理部分

- **它是什么**: 这是 `L1-process` 的工程触发层,一起回答“什么时候该 planning、review、retro、gate”
- **为什么单独有它**: 如果把 planning / review / gate 只当普通 Activity 名字写,就会丢掉 process 作为工程节奏触发器的意义
- **负责什么**:
  - 触发 refinement / planning / review / retro / gate entry
  - 把运行态节点转换成工程世界中的时机信号
  - 驱动 work / governance / artifact / runtime 参与进来
- **不负责什么 / 容易混淆点**:
  - 不负责创建 backlog 或 work 真相
  - 不负责治理决策最终结论
  - 最容易和 work 的正式事实写入混淆
- **与其他部分交互**:
  - 上游: 过程实例运行部分
  - 下游: work / governance / artifact / runtime
  - 交互类型: 节奏触发型
- **后续详细设计展开点**:
  - planning/review/gate 节点模型
  - 时机触发接口与输出事件

#### 挂起与恢复部分

- **它是什么**: 这是 `L1-process` 的暂停与续跑能力层,一起回答“过程推进被治理或故障打断后怎么办”
- **为什么单独有它**: waiting_gate / checkpoint / recovery 不是普通节点说明,而是一整套独立恢复能力
- **负责什么**:
  - 在 waiting_gate 时挂起实例
  - 保存 checkpoint
  - 从 checkpoint 恢复实例
- **不负责什么 / 容易混淆点**:
  - 不直接决定 Gate 结果
  - 不负责 Runtime 内部执行正文
  - 最容易和节奏节点管理部分混淆
- **与其他部分交互**:
  - 上游: 过程实例运行部分 / 节奏节点管理部分
  - 下游: 恢复后回到过程实例运行部分
  - 对外: governance / runtime
  - 交互类型: 挂起恢复型
- **后续详细设计展开点**:
  - checkpoint / recovery 对象与状态流
  - waiting_gate → resume 链路

#### 协作视图与投影部分

- **它是什么**: 这是 `L1-process` 的只读展示层,一起回答“过程运行态怎样被 timeline / trace / progress summary 展示出来”
- **为什么单独有它**: 如果不单列,conversation / console 会被迫直接消费 ProcessInstance / Activity 原始状态
- **负责什么**:
  - 提供 timeline / trace / progress summary
  - 把运行态、节奏节点、恢复链投影给协作界面
- **不负责什么 / 容易混淆点**:
  - 不拥有过程真相
  - 不反向成为写源
  - 最容易和过程实例运行部分混淆
- **与其他部分交互**:
  - 上游: 过程实例运行部分 / 节奏节点管理部分 / 挂起与恢复部分
  - 下游: conversation / console
  - 交互类型: 投影输出型
- **后续详细设计展开点**:
  - process timeline / activity trace / progress DTO
  - 最终一致与过滤规则

### 5.3 主要组成部分汇总表

| 组成部分 | 作用 | 归属 | 上下游 | 后续详细设计展开点 |
|---|---|---|---|---|
| 过程定义与裁剪部分 | 承接模板并形成项目级过程配置 | process 定义层 | method-library / 实例运行部分 | Template/Profile 模型与 drift |

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 定义层 + 运行态真相层 + 节奏触发层 + 恢复能力层 + 协作投影层分层

- 把定义、运行态、节奏节点、恢复能力和投影层明确拆开

## 8. 关键技术选型

### 8.1 为什么采用 Template / Profile / ProcessInstance 三段式

| 维度 | 内容 |
|---|---|
| 当前选择 | 三段式 |

| 当前选择 | process 只负责 planning/review/gate 时机 |
| 备选方案 | process 同时持有 backlog/workitems |
| 选择理由 | 避免流程引擎越界成为项目任务真相源 |
| 演进路径 | 后续仅增强节奏表达和恢复能力 |

### 8.3 为什么 waiting_gate / checkpoint / recovery 要单独成能力

| 维度 | 内容 |
|---|---|
| 当前选择 | 作为独立能力层处理 |
| 备选方案 | 混在普通 Activity 状态里 |
| 选择理由 | 挂起语义、恢复语义与普通推进节点不同,需要独立表达 |
| 演进路径 | 后续在详细设计中细化 checkpoint 介质与 resume 策略 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: process 只管节奏与实例(当前) | 方案 B: process 兼管工作事实 |
|---|---|---|
| 边界清晰度 | 高 | 低 |
| 与 work 协作成本 | 中 | 低(表面) |
| 审计/追溯一致性 | 高 | 低 |
| 恢复能力表达 | 高 | 中 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 需要把“流程节奏”和“项目工作事实”分层,才能同时让 work、governance、artifact、runtime 各自保持真相边界清晰,同时保留 process 自己的挂起恢复语义。

## 11. 横切关注点

### 11.1 安全
- Gate 进入与恢复必须受治理决策约束
- process 不得伪造治理结果或工作事实

### 11.2 性能
- CompleteActivity P95 < 200ms
- Checkpoint write P95 < 50ms inline / < 500ms external
- trace / timeline 投影更新不阻塞主真相推进

### 11.3 可用性
- method-library / governance / runtime 延迟时允许挂起或最终一致,但不得篡改 process 真相边界
- projection 可读侧延迟,但不影响运行态写入

### 11.4 可观测性
- ProcessInstance / Activity / waiting_gate / checkpoint / recovery 主线必须全链留痕
- timeline / trace 必须可还原实例推进顺序

### 11.5 成本
- 不把 Artifact 正文与 Runtime 执行正文并入 process,避免模型膨胀与恢复负担放大

### 11.6 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| AdvanceActivity | ≤ 200ms | 200ms |
| Checkpoint write | ≤ 50ms inline | 250ms |
| 投影更新 | 最终一致 | 不计入强一致预算 |

## 15. 结论

本概要设计的核心结论是:
- `L1-process` 是项目过程节奏与运行实例真相层
- `L1-process` 内部应按“过程定义与裁剪部分 / 过程实例运行部分 / 节奏节点管理部分 / 挂起与恢复部分 / 协作视图与投影部分”来理解,而不是按对象平铺理解
- `work` 管工作事实,`process` 管推进节奏与运行实例,`governance` 管治理决策,`artifact` 管产物真相,`runtime` 管执行正文
- Sprint Planning / Refinement / Review / Retro 属于 process 节奏节点,而不是任务真相创建器
- waiting_gate / checkpoint / recovery 是 process 最关键的独立能力骨架
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把对象模型、状态流、时机触发、恢复链和投影规则正式化

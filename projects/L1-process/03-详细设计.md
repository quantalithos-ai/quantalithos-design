## 1. 模块职责描述

**本模块做什么**:
- 保存项目过程节奏与运行实例真相(Template / Profile / ProcessInstance / Activity / Token)
- 提供 planning / refinement / review / retro / gate 等节奏节点推进
- 提供 waiting_gate / checkpoint / recovery 的挂起与恢复能力
- 为 work / governance / artifact / runtime / conversation / console 提供过程节奏锚点与只读投影

**本模块不做什么**:
- 不负责正式工作事实真相(work)
- 不负责 Gate 决策(governance)
- 不负责 Artifact 正文与基线正文存储(artifact)
- 不负责 Runtime 执行正文与容器细节(runtime)
- 不把投影视图反向当成真相写源

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是继续讲概念,而是让实现者能真正开始写代码。
因此在正式落文前,必须先确认下列内容已经收稳,否则容易把 03 写成“更细一点的概要设计”或“字段表堆砌稿”。

### 2.2 内容采集流程(先采集,再落文)

- 每个主要部分是否已经说明“为什么单独存在、负责什么、不负责什么、如何交互”

### 2.4 详细设计的最低成功标准

一个没参与过该仓开发的人,看完本文后至少应能:
- 知道代码放哪
- 知道对象怎么建
- 知道主流程怎么写
- 知道状态机怎么跑
- 知道数据怎么落
- 知道事件在哪发
- 知道异常和补偿怎么做
- 知道哪些动作需要权限 / 审批 / 责任链校验
- 知道测试至少该测什么
- 知道 `05-测试方案.md` / `06-验收标准.md` 应该直接继承哪些输入

如果还做不到,说明本文仍偏浅。

## 3. 代码目录结构

### 3.1 先按模块组织,再按文件展开

`03-详细设计` 优先采用“**先模块,后文件**”的写法。
不要一上来只堆完整目录树,否则新人容易看到很多文件名,却不知道这些文件共同支撑哪条主流程。

推荐顺序:
1. 先列技术模块(如 api / application / domain / infra / projection)
2. 再说明这些技术模块分别为哪一个主要部分服务
3. 最后把目录树与文件职责对齐到主要部分

### 3.5 仓整体运行主流程

```text
method-library publishes process template
                │
                ▼
过程定义与裁剪部分
- sync template
- build / bind profile
                │
                ▼
过程实例运行部分
- create ProcessInstance
- create initial Activity / Token
                │
                ▼
节奏节点管理部分
- advance activity
- emit planning / review / retro / gate timing
      │                │                  │
      │                │                  ├──────────────▶ governance
      │                ├──────────────────▶ work
      │
      ├──────────────▶ artifact
      └──────────────▶ runtime / member-service
                │
                ▼
挂起与恢复部分
- enter waiting_gate
- write checkpoint
- recover / resume
                │
                ▼
协作视图与投影部分
- timeline projection
- activity trace
- progress summary
                │
                ▼
conversation / console consume process views
```

**总解释**:
- `L1-process` 的运行主线不是“先有对象表,再有别的”,而是“定义进入 → 运行态启动 → 节奏节点对外触发 → 挂起恢复 → 投影刷新”
- 其中真正承载真相写入的是: 过程定义与裁剪部分、过程实例运行部分、挂起与恢复部分
- 节奏节点管理部分负责把运行态翻译成 engineering timing
- 协作视图与投影部分只消费写模型结果

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不应直接从“字段表 / API / 表结构”开始。
在 Quantalithos 这类平台型系统中,更稳的写法是:
- 先承接 `02-概要设计.md` 已经确认的主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与事件
- 最后再进入横向的对象模型、流程、存储、投影、异常与测试细节

> 这里的“主要部分”,不是“单个对象”或“单张表”。它应按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来组织。  
> 同时还应区分三层函数: **对象成员函数**(维护不变量)、**外层编排函数**(组织流程)、**repo / projection / policy 调用**(持久化、只读、策略校验)。

### 5.2 过程定义与裁剪部分

#### 5.2.1 该部分承接的概要输入
- 来自 `02` 的“过程定义与裁剪部分”
- `method-library` 提供 Template / tailoring source
- 项目必须先绑定稳定 Profile,再启动 ProcessInstance

#### 5.2.3 涉及的对象定义

```rust
/// 过程模板对象，表示某类项目通常如何推进的标准定义。
pub struct ProcessTemplate {
    /// 模板唯一标识，用于在 process 与 method-library 之间稳定回链。
    pub template_id: ProcessTemplateId,
    /// 模板名称，用于展示和调试。
    pub name: String,
    /// 模板版本，用于识别升级与 drift。
    pub version: String,
    /// 模板节点定义，用于生成运行态实例。
    pub node_defs: Vec<ActivityDef>,
    /// 模板来源指纹，用于检测 method-library 漂移。
    pub source_fingerprint: String,
}

/// 项目级过程裁剪对象，表示某个具体项目最终采用的固定过程版本。
pub struct ProcessProfile {
    /// Profile 唯一标识。
    pub profile_id: ProcessProfileId,
    /// 该 profile 基于哪个模板生成。
    pub template_id: ProcessTemplateId,
    /// 绑定到哪个项目。
    pub project_id: ProjectId,
    /// 当前项目对模板的裁剪结果。
    pub tailoring_rules: Vec<TailoringRule>,
    /// 当前 profile 是否已冻结并可供实例启动使用。
    pub frozen: bool,
}
```

这里把 `ProcessTemplate` 与 `ProcessProfile` 放在同一个主要部分中,是因为它们共同承担“定义层 / 裁剪层”的实现责任。`Template` 回答“某类项目通常怎么推进”,`Profile` 回答“这个具体项目最终采用哪套固定过程配置”。两者都不属于运行态,因此必须与 `ProcessInstance` 严格分层。

#### 5.2.4 关键函数代码片段

```rust
/// 同步 method-library 中的模板定义,并在本地更新模板索引。
fn sync_template_index(source: TemplateSourceEvent) {
    // TemplateSourceParser::parse
    // 先把外部模板源解析成 process 可消费的模板定义。
    let template = TemplateSourceParser::parse(source);

    // ProcessTemplateRepository.save
    // 持久化模板真相对象,供后续 profile 裁剪和实例启动使用。
    process_template_repo.save(&template);

    // TemplateDriftDetector::record_fingerprint
    // 记录来源指纹,后续可用于 drift 检测。
    TemplateDriftDetector::record_fingerprint(&template);
}

/// 为某个项目绑定并冻结一个可运行的 ProcessProfile。
fn bind_process_profile(project_id: ProjectId, template_id: ProcessTemplateId) -> ProcessProfile {
    // ProcessTemplateRepository.get
    // 先读取模板定义,作为当前项目裁剪的基础。
    let template = process_template_repo.get(template_id);

    // ProcessProfileBuilder::build_from_template
    // 基于模板和项目上下文生成裁剪后的 profile。
    let mut profile = ProcessProfileBuilder::build_from_template(project_id, &template);

    // ProcessProfile.freeze
    // 冻结 profile,保证后续实例启动使用的是稳定过程配置。
    profile.freeze();

    // ProcessProfileRepository.save
    // 持久化项目级固定过程配置。
    process_profile_repo.save(&profile);
    profile
}
```

#### 5.2.5 该部分的边界与非职责
- 不负责保存当前实例运行位置
- 不直接生成或推进 Activity / Token
- 不创建 Backlog / WorkItem / Iteration 真相
- 不把 method-library 模板正文直接并入运行态对象

#### 5.2.6 该部分与其他主要部分的接缝
- 从外部 `method-library` 接收模板与裁剪源
- 向 **过程实例运行部分** 提供稳定可运行的 Profile
- 向 **协作视图与投影部分** 提供模板名、版本与 profile 摘要信息

#### 5.2.7 该部分的状态 / 约束 / 易错点
- Template 与 Profile 必须分层,不能把项目裁剪结果直接写回模板定义
- frozen 的 Profile 才允许被实例启动使用
- `source_fingerprint` 必须可回链,否则 drift 无法检测
- 最容易把 Profile 当成 ProcessInstance 的运行态配置对象

```rust
/// 节奏触发节点，表示某类工程动作应在何时被触发。
pub struct TimingNode {

/// 过程节奏输出对象，表示 process 向外部仓发出的时机信号。

}
```

`TimingNode` 与 `TimingSignal` 放在同一个主要部分中,是因为它们共同承担“把运行态节点翻译成工程世界时机信号”的责任。一个表示内部节点,一个表示对外输出,两者一起把 process 从“运行态引擎”连接到 work / governance / artifact / runtime。

#### 5.4.4 关键函数代码片段

```rust
/// 在实例推进到特定节点时,向外部发出节奏信号。
fn emit_timing_signal(activity: &Activity) -> TimingSignal {
    // TimingNodeFactory::build_from_activity
    // 先从当前活动生成节奏节点语义。
    let node = TimingNodeFactory::build_from_activity(activity);

    // TimingPolicy::map_to_signal
    // 把内部节点映射成外部可消费的时机信号。
    let signal = TimingPolicy::map_to_signal(&node);

    // TimingSignalPublisher.publish
    // 向对应外部模块发布工程节奏信号。
    timing_signal_publisher.publish(&signal);
    signal
}

/// 进入 gate 节点时,构造治理入口请求。
fn enter_gate(activity: &Activity) -> GateEntryRequest {
    // GateEntryBuilder::build
    // 基于当前活动构造治理入口请求。
    GateEntryBuilder::build(activity)
}
```

#### 5.4.5 该部分的边界与非职责
- 不负责创建 Backlog / WorkItem / Iteration 真相
- 不负责治理决策最终结论
- 不负责 Artifact 正文落盘
- 不直接等同于运行态实例本体

#### 5.4.6 该部分与其他主要部分的接缝
- 从 **过程实例运行部分** 接收当前活跃节点与推进结果
- 向 **挂起与恢复部分** 提供 waiting_gate 入口
- 向外部 `work / governance / artifact / runtime` 发出时机信号
- 向 **协作视图与投影部分** 提供节点触发记录

#### 5.4.7 该部分的状态 / 约束 / 易错点
- timing signal 必须是节点触发结果,不是新真相源
- planning / review / retro / gate 必须区分 signal type,不能只用一个通用节点名混过去
- gate entry 与 gate decision 分层,前者属于 process,后者属于 governance
- 最容易把 Sprint Planning 写成 backlog 创建逻辑

### 5.5 挂起与恢复部分

#### 5.5.1 该部分承接的概要输入

- waiting_gate / checkpoint / recovery 是独立恢复能力
- 挂起与恢复不能被降格成普通 Activity 状态切换

```rust
    /// 当前等待的是哪个 gate。

    /// 挂起发生时的活动引用。
    pub activity_id: ActivityId,
    /// 当前挂起是否已经恢复。

/// 过程恢复快照，表示某一时刻可用于恢复推进的稳定状态。
```

这里把 `WaitingGateState` 与 `Checkpoint` 放在同一个主要部分中,是因为它们共同承担“挂起后怎样恢复”的实现责任。`WaitingGateState` 表示为什么停住,`Checkpoint` 表示从哪里恢复。两者一起组成恢复链。

#### 5.5.4 关键函数代码片段

```rust
/// 在进入 waiting_gate 前写入恢复快照并挂起实例。
fn suspend_for_gate(instance: &ProcessInstance, activity: &Activity) -> WaitingGateState {
    // CheckpointWriter::write
    // 先把当前实例快照落成 checkpoint,保证后续可恢复。
    let checkpoint = CheckpointWriter::write(instance, activity);

    // WaitingGateStateBuilder::build
    // 再构造 waiting_gate 状态对象,把 gate 与 activity 绑定起来。
    let waiting = WaitingGateStateBuilder::build(instance, activity, checkpoint.checkpoint_id);

    // WaitingGateRepository.save
    // 持久化挂起状态,供 resume 使用。
    waiting_gate_repo.save(&waiting);
    waiting
}

/// 基于 checkpoint 恢复实例推进。
fn recover_instance(checkpoint_id: CheckpointId) -> ProcessInstance {
    // CheckpointRepository.get
    // 读取先前写入的稳定恢复快照。
    let checkpoint = checkpoint_repo.get(checkpoint_id);

    // ProcessRecovery::restore
    // 基于 token / activity snapshot 重建实例运行位置。
    ProcessRecovery::restore(&checkpoint)
}
```

#### 5.5.5 该部分的边界与非职责
- 不决定 Gate 的最终审批结论
- 不负责 Runtime 执行正文逻辑
- 不负责 timeline / trace 展示规则
- 不负责普通节奏节点的时机触发

#### 5.5.6 该部分与其他主要部分的接缝
- 从 **过程实例运行部分** 接收当前运行位置
- 从 **节奏节点管理部分** 接收 gate entry / failure suspend 信号
- 向 **过程实例运行部分** 返回恢复后的实例状态
- 向 **协作视图与投影部分** 提供 checkpoint / waiting_gate trace 输入

#### 5.5.7 该部分的状态 / 约束 / 易错点
- 进入 waiting_gate 前必须有可恢复 checkpoint
- resume 必须可回链到对应 gate / checkpoint / activity
- checkpoint 是恢复真相,不是展示投影
- 最容易把 waiting_gate 误当普通 Activity 状态

## 6. 核心结构体与对象定义

#### 5.3.5 该部分的边界与非职责
- 不负责定义模板来源与裁剪规则
- 不直接生成 planning / review / gate 的工程动作语义
- 不负责治理决策结论正文
- 不把 timeline / trace 当运行态真相

#### 5.3.6 该部分与其他主要部分的接缝
- 从 **过程定义与裁剪部分** 接收稳定可运行的 Profile
- 向 **节奏节点管理部分** 提供当前活跃节点与推进时机
- 向 **挂起与恢复部分** 提供 suspend / resume 运行态基础
- 向 **协作视图与投影部分** 提供 ProcessInstance / Activity / Token 状态输入

- ProcessInstance / Activity / Token 必须分层,不能把 token 语义塞进 Activity 自身
- running / suspended / completed 等实例状态必须和 Activity 状态区分开
- Activity 推进失败时,不能直接跳过恢复链进入下一个节点
- 最容易把“当前节点是什么”和“当前该触发什么工程动作”混成一层

### 6.6 支撑构件职责说明

#### 6.6.1 定义与裁剪部分的支撑构件

- `TemplateSourceParser`
  - **类型**: parser
  - **职责**: 把 method-library 发来的模板源事件解析成 process 可消费的 `ProcessTemplate` 对象
  - **为什么单独存在**: 外部模板载荷格式和 process 内部模板真相对象不应耦合在一起

- `TemplateDriftDetector`
  - **类型**: detector
  - **职责**: 记录并比较模板来源指纹,识别 method-library 与本地模板索引的漂移
  - **为什么单独存在**: drift 检测是定义层治理能力,不应塞进模板对象或 repo 中

- `ProcessProfileBuilder`
  - **类型**: builder
  - **职责**: 基于 `ProcessTemplate` 与项目上下文生成冻结前的 `ProcessProfile`
  - **为什么单独存在**: 裁剪规则是定义层到项目层的转换逻辑,不属于 Template 或 Profile 自身真相字段

- `ProcessTemplateRepository`
  - **类型**: repository
  - **职责**: 持久化与读取 `ProcessTemplate` 真相对象
  - **为什么单独存在**: 定义层模板真相应通过独立仓储接口管理,不能混进实例 repo

- `ProcessProfileRepository`
  - **类型**: repository
  - **职责**: 持久化与读取 `ProcessProfile` 真相对象
  - **为什么单独存在**: 项目级裁剪结果应独立于模板与实例存储

#### 6.6.2 节奏节点管理部分的支撑构件

- `TimingNodeFactory`
  - **类型**: factory
  - **职责**: 从当前 `Activity` 推导出内部节奏节点语义
  - **为什么单独存在**: Activity 是运行态节点,TimingNode 是工程时机节点,两者不能混写

- `TimingPolicy`
  - **类型**: policy
  - **职责**: 把 `TimingNode` 映射成对外可消费的 `TimingSignal`
  - **为什么单独存在**: trigger 规则属于策略层,不应散落在 publisher 或 activity 对象里

- `TimingSignalPublisher`
  - **类型**: publisher
  - **职责**: 向 work / governance / artifact / runtime 发布工程节奏信号
  - **为什么单独存在**: 对外交互副作用应和节点判断逻辑分离

- `GateEntryBuilder`
  - **类型**: builder
  - **职责**: 基于活动状态构造结构化 `GateEntryRequest`
  - **为什么单独存在**: gate 入口请求是 process → governance 的接缝对象,不应直接由 Activity 真相对象拼装

#### 6.6.3 挂起与恢复部分的支撑构件

- `CheckpointWriter`
  - **类型**: writer
  - **职责**: 把当前实例状态序列化并写成 `Checkpoint`
  - **为什么单独存在**: checkpoint 写入策略与恢复算法不同,不应混在同一个组件里

- `CheckpointRepository`
  - **类型**: repository
  - **职责**: 持久化与读取 `Checkpoint`
  - **为什么单独存在**: 恢复快照是真相对象,需要独立的存储边界

- `WaitingGateStateBuilder`
  - **类型**: builder
  - **职责**: 基于实例、活动与 checkpoint 构造 `WaitingGateState`
  - **为什么单独存在**: waiting_gate 既关联治理入口,又关联恢复快照,组装逻辑不应塞进实例对象本身

- `WaitingGateRepository`
  - **类型**: repository
  - **职责**: 持久化与读取挂起状态对象
  - **为什么单独存在**: waiting_gate 是恢复链中的真相对象,需要独立读写边界

- `ProcessRecovery`
  - **类型**: recovery component
  - **职责**: 基于 `Checkpoint` 重建 `ProcessInstance / Activity / Token` 的运行态位置
  - **为什么单独存在**: 恢复逻辑是独立算法能力,不应和 checkpoint 存储或实例对象本身混在一起

#### 6.6.4 协作视图与投影部分的支撑构件

- `TimelineBuilder`
  - **类型**: builder
  - **职责**: 从实例推进事件中收集并组装 `TimelineProjection`
  - **为什么单独存在**: timeline 是投影,其构建规则不属于实例真相对象

- `ProgressSummaryBuilder`
  - **类型**: builder
  - **职责**: 从实例状态、挂起态和完成度推导 `ProgressSummaryDTO`
  - **为什么单独存在**: 摘要生成是只读展示逻辑,不应混进 ProcessInstance 真相层

## 8. 运行期主线场景

### 8.1 场景 A · 从 Template/Profile 启动一个项目过程

```text
method-library publishes template
      │
      ▼
过程定义与裁剪部分同步 Template
      │
      ▼
BindProcessProfile(project_id, template_id)
      │
      ▼
Profile frozen
      │
      ▼
StartProcessInstance(project_id, profile_id)
      │
      ▼
ProcessInstance(draft → running)
      │
      ▼
create initial Activity / Token
```

**开发者关注点**:
- Template 与 Profile 必须先稳定,再启动实例
- frozen 前的 Profile 不得直接用于实例启动
- 启动时必须同时建立实例与首个 token,否则运行态是不完整的

### 8.2 场景 B · 运行到 planning/review/gate 节点

```text
ProcessInstance running
      │
      ▼
AdvanceActivity(activity_id, runtime feedback)
      │
      ▼
Activity / Token moved to timing node
      │
      ▼
TimingNodeFactory.build_from_activity()
      │
      ▼
TimingPolicy.map_to_signal()
      │
      ├──────────────▶ work (planning / review timing)
      ├──────────────▶ governance (gate entry)
      ├──────────────▶ artifact (outputs timing)
      └──────────────▶ runtime / member-service (execution timing)
```

**开发者关注点**:
- timing signal 是对外时机信号,不是新真相源
- Sprint Planning / Review / Gate 都应通过 signal type 区分,不能混成一个 generic 节点
- process 只触发时机,不负责写 work 真相或治理结论

### 8.3 场景 C · waiting_gate 挂起后从 checkpoint 恢复

```text
gate entry reached
      │
      ▼
WriteCheckpoint(instance, activity)
      │
      ▼
build WaitingGateState
      │
      ▼
ProcessInstance running → suspended
      │
      ▼
governance returns decision
      │
      ▼
RecoverInstance(checkpoint_id)
      │
      ▼
ProcessRecovery.restore()
      │
      ▼
ProcessInstance suspended → running
```

**开发者关注点**:
- 进入 waiting_gate 前必须先落 checkpoint
- resume 不应凭“当前内存状态”直接继续,而应基于稳定快照恢复
- recovery 后必须把恢复后的实例状态重新持久化,避免再次漂移

### 8.4 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| method-library template source | `template_sync_service` | 过程定义与裁剪部分 | 更新 Template / drift fingerprint |
| work / project start | `process_service.start_process_instance` | 过程实例运行部分 | 创建并启动 ProcessInstance |
| runtime feedback | `activity_service.advance_activity` | 过程实例运行部分 | 更新 Activity / Token |
| governance decision | `recovery_service.resume_process_instance` | 挂起与恢复部分 | 恢复实例推进 |
| conversation / console timeline query | `projection_query_service.get_process_timeline` | 协作视图与投影部分 | 返回只读 timeline / trace / summary |

- **协作视图与投影部分**:
  - projection 不得反写真相

### 10.1 总体结构

```text
write model
   ├─ process_instances
   ├─ process_activities
   ├─ process_tokens
   ├─ process_waiting_gates
   └─ process_checkpoints
        │
        ▼
projection builders
   ├─ TimelineBuilder
   ├─ ActivityTraceBuilder
   └─ ProgressSummaryBuilder
        │
        ▼
timeline / trace / progress APIs
```

### 10.2 关键读模型说明

| 读模型 | 所属主要部分 | 输入 | 输出 |
|---|---|---|---|
| `TimelineProjection` | 协作视图与投影部分 | instance events / checkpoint refs / timing records | timeline view |

### 10.3 一致性说明

- **协作视图与投影部分** 允许最终一致
- ProcessInstance / Activity / Token / Checkpoint / WaitingGateState 才是真相层输入
- timeline / trace / progress 只能用于展示,不能反向成为实例真相写源
- waiting_gate / checkpoint 若存在短暂延迟,投影视图可短时滞后,但恢复链不得依赖投影数据

## 11. 异常与补偿设计

### 11.1 重试 / 降级 / 熔断 / 补偿

- **过程定义与裁剪部分**: method-library 源事件异常时,优先保留最后一次稳定模板索引并发出 drift / sync 告警
- **过程实例运行部分**: Activity 推进失败时,禁止静默跳过节点,应进入 failed 或 recovery 路径
- **节奏节点管理部分**: timing signal 发布失败时,允许重试或补发,但不得重写 work 真相
- **挂起与恢复部分**: checkpoint 写入失败时,禁止进入 waiting_gate 完整挂起链
- **协作视图与投影部分**: projection 落后时允许只读降级,不影响运行态真相推进

### 11.2 高风险跨仓失败模式

| 场景 | 主要落点部分 | 失败点 | 补偿 / 对账 / replay |
|---|---|---|---|
| method-library 模板更新未完整同步 | 过程定义与裁剪部分 | template / fingerprint 不一致 | 保留旧模板 + drift 告警 + 重新 sync |
| work 未消费 planning timing | 节奏节点管理部分 | timing signal 丢失 | replay timing event / 幂等补发 |
| governance 决策未返回 | 挂起与恢复部分 | instance 长停于 waiting_gate | 保持 suspended + 告警 + 人工恢复 |
| runtime 反馈缺失 | 过程实例运行部分 | activity 卡在 running | 超时转 failed / recovery |
| artifact 输出引用延迟 | 协作视图与投影部分 | trace / outputs 摘要不完整 | 最终一致补写 / projection 重建 |

### 11.3 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 过程定义与裁剪部分 | Template drift 未检测到 | source fingerprint compare | 标记 source_drift,阻断新实例启动 | resync template source |
| 过程实例运行部分 | Activity 推进非法 | activity advance validation | 拒绝推进,保持原状态 | retry / recover |
| 节奏节点管理部分 | signal type 错发 | timing mapping validation | 丢弃错误信号,重新映射 | replay timing signal |
| 挂起与恢复部分 | checkpoint 不可恢复 | checkpoint load / restore | 标记 recovery_failed | 选择上一个 checkpoint |
| 协作视图与投影部分 | timeline 与实例真相不一致 | projection rebuild check | 重建投影 | rebuild projection |

## 12. 实现红线 / 开发禁止事项

- 不要让 planning / review / retro / gate 节点直接创建 Backlog / WorkItem / Iteration 真相
- 不要把 governance 决策正文并入 process 真相; process 只保存 GateRef 和挂起恢复链
- 不要把 artifact 正文并入 process 真相; process 只保存 ArtifactRef / BaselineRef 等稳定引用
- 不要让 projection 反写真相; timeline / trace / summary 只能用于只读展示
- 不要把 runtime 执行正文直接并入 ProcessInstance / Activity / Token
- 不要在 waiting_gate 前跳过 checkpoint 写入,否则恢复链不成立

第一版最少应打通以下闭环,系统就能形成可运行的 `L1-process` 主干:

1. **过程定义与裁剪部分**
   - SyncTemplateIndex
   - BindProcessProfile
2. **过程实例运行部分**
   - StartProcessInstance
   - AdvanceActivity
3. **节奏节点管理部分**
   - EmitTimingSignal
4. **挂起与恢复部分**
   - WriteCheckpoint
   - EnterWaitingGate
   - RecoverInstance
5. **协作视图与投影部分**
   - BuildTimelineProjection
   - BuildProgressSummary

> 只要这 5 条最小闭环打通,开发者就已经能验证: 模板能进入系统、Profile 能冻结、实例能启动并推进、节奏信号能对外发出、waiting_gate / checkpoint / recovery 能形成闭环、timeline / summary 能对外展示。

## 15. 结论

本详细设计的核心结论是:
- `L1-process` 的实现结构应按 5 个主要部分组织,而不是按对象顺排
- 过程定义与裁剪部分负责“这个项目按什么过程推进”
- 过程实例运行部分负责“这个项目过程当前跑到哪里”
- 节奏节点管理部分负责“什么时候触发 planning / review / retro / gate”
- 挂起与恢复部分负责“停住后如何续跑”
- 协作视图与投影部分负责“外部如何只读查看过程运行态”
- process 管节奏与运行实例,不管 work 真相、不管治理结论真相、不管 artifact 正文真相
- waiting_gate / checkpoint / recovery 是独立核心能力,不是普通节点细节
- 后续 `05-测试方案.md` / `06-验收标准.md` 应围绕这 5 个主要部分建立测试与验收映射

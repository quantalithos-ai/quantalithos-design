## 3. SOP 问题回答

### 3.1 本仓有哪些主要角色？

`L1-process` 的主要角色分为三类:

1. 人类 / AI 成员角色:项目发起 / 管理者、过程协调 / 技术负责人、执行成员、审计 / 观察者。
2. 系统角色:内部系统调用方、Activity 执行反馈方、运维 / 后台任务。
3. 不作为本章角色的相邻仓:method-library、work、governance、artifact、runtime、member-service、conversation、workspace、observability、archive 等,它们在 Step 6 使用方与依赖中讨论。

### 3.2 哪些是人类角色,哪些是系统角色？

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 项目发起 / 管理者 | 人类角色 | 需要理解项目采用什么过程、当前过程处于哪个阶段、为什么停住、能否继续推进 |
| 过程协调 / 技术负责人 | 人类角色 | 关注过程节奏、Activity 分派语境、阶段推进、review / gate / retro 等时机是否合理 |
| 执行成员 | 人类或 AI 成员角色 | 在被分配或被提示执行某个 Activity 时,需要理解该 Activity 的过程上下文和反馈边界 |
| 审计 / 观察者 | 人类角色 | 查看过程实例、Activity 轨迹、waiting gate、checkpoint 和恢复链路是否可解释 |
| 内部系统调用方 | 系统角色 | 平台内部系统以受控方式消费或提交过程执行事实相关变化 |
| Activity 执行反馈方 | 系统角色 | 承接 Activity 执行意图并返回完成、失败、重试或恢复反馈,但不把内部执行正文交给 process 拥有 |
| 运维 / 后台任务 | 系统角色 | 执行恢复、重建、对账、报告或维护类动作时接触过程执行事实 |

### 3.3 这些角色分别在什么场景下接触本仓？

| 角色 | 典型接触场景 | 本步边界 |
|---|---|---|
| 项目发起 / 管理者 | 查看过程阶段、理解当前停顿原因、知道下一步是否需要人类决策 | 不写启动过程接口、不写审批动作 |
| 过程协调 / 技术负责人 | 确认过程节奏是否符合项目语境,识别 Activity / WorkItem / gate timing 是否串线 | 不写 Profile 裁剪算法、不写 Activity 状态机 |
| 执行成员 | 接收过程上下文,知道自己当前承担的 Activity 与项目工作事实的关系 | 不写 runtime 执行细节、不写工具调用 |
| 审计 / 观察者 | 复盘过程实例如何推进、何时进入 waiting gate、哪个 checkpoint 可恢复 | 不写审计查询接口、不写 evidence schema |
| 内部系统调用方 | 以受控方式消费过程状态、提交过程反馈或读取投影 | 具体仓际依赖后移 Step 6 |
| Activity 执行反馈方 | 承接执行意图,返回状态反馈,参与恢复反馈闭环 | 不把具体 `runtime` 或 `member-service` 仓写成本章角色 |
| 运维 / 后台任务 | 处理卡住实例、恢复任务、派生视图重建、报告和对账 | 不写 job 列表或实现机制 |

### 3.4 是否存在管理、审计或维护类角色？

存在:

- 管理类角色:项目发起 / 管理者、过程协调 / 技术负责人。
- 审计类角色:审计 / 观察者。
- 维护类角色:运维 / 后台任务。

这些角色只用于需求层场景分类,不在本步展开具体权限、接口、后台任务或报告格式。

### 3.5 是否需要进一步补权限矩阵？

需要轻量权限差异矩阵。原因是 `L1-process` 涉及过程查看、过程协调、Activity 执行反馈、恢复、审计和维护,不同角色的接触方式差异明显。但矩阵必须保持能力级粒度,不写 API、Command、事件名或状态机。

| 操作类型 | 项目发起 / 管理者 | 过程协调 / 技术负责人 | 执行成员 | 审计 / 观察者 | 内部系统调用方 | Activity 执行反馈方 | 运维 / 后台任务 |
|---|---|---|---|---|---|---|---|
| 查看过程状态与阶段 | 是 | 是 | 受限 | 是 | 受控 | 受控 | 是 |
| 协调过程节奏 | 受限 | 是 | 否 | 只读 | 受控 | 否 | 否 |
| 提交 Activity 执行反馈 | 否 | 否 | 受控 | 否 | 受控 | 是 | 按任务 |
| 查看 waiting gate / checkpoint 轨迹 | 是 | 是 | 受限 | 是 | 受控 | 受控 | 是 |
| 执行恢复 / 维护类动作 | 否 | 受限 | 否 | 否 | 受控 | 受控 | 是 |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 角色分类 | 用户类型、系统仓和依赖混写 | 人类 / AI 成员角色、系统角色、相邻仓依赖分开 | 对齐 SOP,避免把依赖写成角色 |

| 权限矩阵 | 操作较具体,混入接口和状态机动作 | 能力级权限差异 | 避免滑入功能、规则和接口 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 沿用旧角色表 | 保留旧内容,速度快 | 把 Governance / Artifact / Work / Runtime 写成用户角色,违反 Step 5 粒度 | 不采用 |
| 方案 B: 按人类 / AI 成员角色、系统角色、相邻仓依赖分开 | 角色清楚,能为 Step 6 留出依赖边界 | 需要后续 Step 6 再展开仓际关系 | 采用 |
| 方案 C: 只写人类角色,不写系统角色 | 简洁 | 忽略 Activity 执行反馈和恢复维护等 process 核心接触场景 | 不采用 |
| 方案 D: 直接写完整权限矩阵和接口动作 | 看似完整 | 会提前进入功能、规则和授权设计 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把 Governance / Artifact / Work / Runtime 写成系统角色？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成系统角色 | Step 5 与 Step 6 混杂,后续依赖裁剪重复 |
| 方案 B | 不写成角色,后移 Step 6 使用方与依赖 | 角色章节更干净,依赖章节可按全局基线裁剪 |

推荐方案 B。原因是这些是仓际协作方,不是“以什么身份接触本仓”的角色定义。

#### 是否保留执行成员作为角色？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 不保留,只写系统执行反馈方 | 简化角色表,但会丢掉人类 / AI 成员理解 Activity 上下文的需求场景 |
| 方案 B | 保留执行成员,但不写 runtime 执行细节 | 能表达 Activity 与 ProjectMember / AI member 的接触场景,又不越界到 runtime |

推荐方案 B。原因是 process 需要表达 Activity 对执行成员的过程语境,但执行正文不归 process。

#### 是否在 Step 5 写权限矩阵？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 不写权限矩阵 | 简短,但角色差异不够明确 |
| 方案 B | 写轻量能力级权限差异矩阵 | 能约束后续用户故事和功能需求,不滑入接口 |

推荐方案 B。原因是 Process 涉及管理、协调、执行反馈、审计和维护,角色差异明显。

## 7. 结构化中间产物

### 7.1 角色结论

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 项目发起 / 管理者 | 人类角色 | 需要理解项目采用什么过程、当前过程处于哪个阶段、为什么停住、能否继续推进 |

| 审计 / 观察者 | 人类角色 | 查看过程实例、Activity 轨迹、waiting gate、checkpoint 和恢复链路是否可解释 |

### 7.2 系统角色结论

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 内部系统调用方 | 系统角色 | 平台内部系统以受控方式消费或提交过程执行事实相关变化 |

### 7.3 使用场景结论

| 角色 | 场景结论 |
|---|---|
| 项目发起 / 管理者 | 关心项目是否按选定过程推进、当前是否等待人类决策、过程是否可被看见和解释 |
| 过程协调 / 技术负责人 | 关心过程节奏是否正确触发 planning / review / gate / retro,并避免 Activity 与 WorkItem / runtime step 混淆 |
| 执行成员 | 关心自己被提示执行的 Activity 处于什么过程语境,以及反馈边界是什么 |
| 审计 / 观察者 | 关心过程实例能否解释阶段、Activity、等待点、恢复点和关键协作引用 |
| 内部系统调用方 | 关心能否以受控方式消费或提交过程执行事实变化 |
| Activity 执行反馈方 | 关心能否提交执行结果或恢复反馈,同时不把内部执行正文转交给 process |
| 运维 / 后台任务 | 关心维护动作能否在不改变相邻仓真相的前提下处理恢复、派生和一致性问题 |

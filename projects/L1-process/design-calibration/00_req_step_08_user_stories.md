## 3. SOP 问题回答

### 3.1 哪些角色目标在支撑本仓的核心能力闭环？

支撑核心闭环的故事必须围绕过程执行事实成立,而不是围绕 UI、接口或相邻仓动作成立:

| 闭环节点 | 支撑它的角色目标 |
|---|---|
| C-1 运行时过程形态成立 | 过程协调 / 技术负责人需要把方法定义转成项目可执行过程形态;项目发起 / 管理者需要理解项目采用的过程语境 |
| C-2 项目过程实例成立 | 项目发起 / 管理者需要看到项目正在按某个正式过程运行;内部系统调用方需要稳定引用同一个过程实例 |
| C-3 节点与流控位置成立 | 过程协调 / 技术负责人、执行成员和 Activity 执行反馈方需要理解当前过程节点、承担语境和推进位置 |
| C-4 暂停等待恢复连续成立 | 项目发起 / 管理者、过程协调 / 技术负责人、Activity 执行反馈方和运维 / 后台任务需要理解为什么停住、等待什么、从哪里恢复 |
| C-5 可消费可追溯成立 | 审计 / 观察者、内部系统调用方和运维 / 后台任务需要围绕同一份过程执行事实进行追溯、消费、重建和对账 |

### 3.2 哪些角色目标只是外围增强,而不决定闭环是否成立？

外围增强故事可以保留为后续能力线索,但不能压过核心闭环:

| 外围增强目标 | 角色 | 原因 |
|---|---|---|
| 更丰富的 timeline、dashboard、筛选和展示偏好 | 项目发起 / 管理者、审计 / 观察者 | 依赖 Process 事实,但属于消费展示增强 |
| 完整 BPMN / 嵌套过程可视化 | 过程协调 / 技术负责人 | 表达力增强,不决定基本过程事实成立 |
| 模板刚度分层和高级裁剪策略 | 过程协调 / 技术负责人 | 与 Proposed ADR-0010 相关,后续再确认 |
| 自动调度、自动重试和复杂补偿建议 | 运维 / 后台任务、Activity 执行反馈方 | 可提升效率,但不决定过程事实连续性 |
| 容量、P95 和恢复 SLO 可视化 | 项目发起 / 管理者、运维 / 后台任务 | 属于非功能和规模治理,后移 Step 13 |

### 3.3 哪些看起来像故事,但其实不应进入本仓？

| 看似故事 | 不进入原因 | 正确归属 |
|---|---|---|
| 作为方法管理员,我希望维护任务定义正文,以便项目可使用模板 | 方法定义正文不是 Process | `L3-method-library` |
| 作为项目协调者,我希望创建 WorkItem,以便团队执行工作 | WorkItem truth 不是 Process | `L1-work` |
| 作为审批人,我希望批准或拒绝 Gate,以便决定项目能否继续 | Gate / approval 决策真相不是 Process | `L1-governance` |
| 作为执行器,我希望调用工具和推进计划步骤,以便完成任务 | agent loop 和 plan item progress 不是 Process | `L2-runtime` |
| 作为用户,我希望上传 Artifact 正文,以便保存交付物 | Artifact 正文和 evidence 正文不是 Process | `L1-artifact` |
| 作为成员管理员,我希望暂停成员身份,以便控制权限 | 成员生命周期不是 Process | `L1-identity` |
| 作为用户,我希望在聊天中发送过程消息,以便讨论进展 | 对话事实和聊天呈现不是 Process | `L1-conversation` / 产品入口 |
| 作为工作台用户,我希望管理跨域 dashboard,以便总览项目 | 聚合视图状态不是 Process | `L1-workspace` |

### 3.4 每条故事分别支撑闭环中的哪个能力节点？

每条正式故事必须能映射到 C-1~C-5 或明确标记为外围增强。故事不直接映射到接口、事件、数据库对象或 implementation phase。

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 故事组织方式 | 按旧用例 / 功能动作排列 | 按核心闭环 C-1~C-5 与外围增强排列 | 保证故事服务仓存在必要性 |
| 故事粒度 | 出现接口名、状态名、事务和 Given / When / Then 验收句 | 使用“作为角色,我希望目标,以便价值”的目标级句式 | 避免提前进入接口、规则和测试 |
| 边界处理 | method-library / work / governance / runtime / artifact 容易作为故事主体出现 | 边界外故事单独列为排除结论 | 避免把相邻仓真相写进 Process |
| checkpoint 处理 | 容易写成“每次 Activity 完成后写 checkpoint” | 写成“暂停等待恢复能够保持同一过程事实连续”的目标 | 保留恢复价值,不提前写机制 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 沿用旧 US-001~US-005 | 快,已有验收句式 | 含接口名、状态名、验收动作和边界外角色,无法支撑最新闭环 | 不采用 |
| 方案 B: 按核心能力闭环重写故事 | 故事能直接支撑 Step 9 功能归并和 Step 16 追溯 | 需要后续再补功能、规则和验收 | 采用 |
| 方案 C: 按角色分别列大量故事 | 角色覆盖完整 | 容易变成普通故事清单,核心闭环被稀释 | 不采用 |
| 方案 D: 只写核心故事,不写外围增强 | 文档干净 | 会丢失旧文档中有价值但非核心的增强线索 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否保留“每个 Activity 完成后立即写 checkpoint”故事？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 作为核心故事原样保留 | 会把机制和事务口径提前写进用户故事 |
| 方案 B | 改写为“过程停住或故障后能从同一过程事实中恢复”的目标故事 | 保留恢复价值,把机制后移到规则 / 详细设计 |

推荐方案 B。原因是 Step 8 应写角色目标,不是机制和事务动作。

#### 是否把 governance 写成故事角色？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写“作为 governance,我希望收到 Gate 请求” | 把相邻仓写成角色,且容易越界到治理决策 |
| 方案 B | 写内部系统调用方和过程协调者围绕等待决策语境消费过程事实 | 保留协作诉求,不转移决策真相 |

推荐方案 B。原因是 Step 5 已确认具体相邻仓不作为本章角色。

#### 是否把完整 dashboard / timeline 写入核心故事？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 作为核心故事 | 会把 workspace / 产品展示能力写入 Process 核心 |
| 方案 B | 基础消费与追溯进入核心故事,高级展示作为外围增强 | 能支撑可消费性,但不越界到 workspace |

推荐方案 B。原因是 Process 事实必须可消费,但展示形态不是核心闭环条件。

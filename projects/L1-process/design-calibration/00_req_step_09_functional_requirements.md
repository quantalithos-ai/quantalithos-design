## 3. SOP 问题回答

### 3.1 根据这些用户故事,系统必须提供哪些业务能力？

`L1-process` 必须提供的业务能力不是旧文档中的 `ProcessTemplate 索引`、`ProcessInstance 状态机`、`RecoverInstance` 这类功能名或接口动作,而是围绕过程执行事实闭环形成的能力主题:

1. 运行时过程形态形成能力。
2. 项目过程实例成立能力。
3. 过程节点与流控位置表达能力。
4. Activity 执行语境与反馈绑定能力。
5. 暂停等待与恢复语境表达能力。
6. 过程事实恢复连续性维护能力。
7. 过程执行事实消费与追溯能力。
8. 过程执行事实维护与对账能力。

这些能力共同支撑核心闭环。旧文档中的 checkpoint、gateway、waiting_gate、artifact outputs、workitem completion policy 等只作为后续规则、数据归属、接口或设计线索,不能在需求层被直接写成功能清单。

### 3.2 每个能力的输入、输出、触发条件、失败情况是什么？

需求阶段只写能力级输入、输出、触发和失败,不写字段、DTO、函数、事件 schema、状态枚举或事务处理:

| 能力 | 能力级输入 | 能力级输出 | 触发条件 | 失败情况 |
|---|---|---|---|---|
| 运行时过程形态形成能力 | 方法定义引用、项目过程选择语境、裁剪意图和约束 | 可用于项目执行的运行时过程形态 | 项目需要采用或更新过程语境 | 定义来源不可用;裁剪结果无法解释;与已运行过程语境冲突 |
| 项目过程实例成立能力 | 项目语境、运行时过程形态、启动意图和 actor 语境 | 可被引用和追溯的项目过程实例 | 项目进入正式过程运行语境 | 缺少项目或过程形态前置;重复或冲突的运行事实 |
| 过程节点与流控位置表达能力 | 当前过程实例、节点承担语境、执行反馈和推进约束 | 可解释的当前节点、活跃位置和推进状态 | 过程需要推进、等待或解释当前位置 | 节点不属于当前过程形态;推进语境不完整;流控关系不合法 |
| Activity 执行语境与反馈绑定能力 | 过程节点语境、执行反馈方反馈、工作 / 成员 / runtime 引用 | 绑定到正式过程节点的执行反馈结果 | 执行方返回完成、失败、重试或恢复反馈 | 反馈来源不可识别;反馈与当前节点不匹配;反馈试图写入 runtime 正文 |
| 暂停等待与恢复语境表达能力 | 等待原因、治理 / 执行 / 外部反馈语境、当前过程位置 | 可解释的暂停、等待和恢复语境 | 过程到达关键决策点、外部等待点或异常暂停点 | 等待原因不清;决策真相被误写进 process;恢复依据不完整 |
| 过程事实恢复连续性维护能力 | 当前过程事实、恢复点、故障或中断语境、维护 actor 语境 | 可从同一过程事实继续服务的恢复结果 | 故障恢复、派生失衡、后台维护或人工恢复 | 恢复点不可用;恢复会产生多份过程真相;恢复试图重写相邻仓真相 |
| 过程执行事实消费与追溯能力 | 过程状态、节点、等待、恢复和相邻引用的读取需求 | 可授权消费和可解释的过程事实视图 | 管理者、审计者或相邻仓需要理解过程推进 | 请求方无权读取;派生视图滞后且无法解释;相邻引用失效 |
| 过程执行事实维护与对账能力 | 派生结果、投影、外部协作状态和一致性检查需求 | 对账结果、重建结果或维护证据 | 后台任务或运维需要维护消费面一致性 | 维护动作试图改变业务真相;对账来源不完整 |

### 3.3 哪些能力共同构成闭环核心?哪些只是外围增强?

核心闭环能力是没有它就无法成立 `L1-process` 的能力;外围增强能力可以提升表达力、自动化、展示或管理分析,但不决定过程执行事实是否成立。

| 分类 | 能力 |
|---|---|
| 核心闭环能力 | 运行时过程形态形成能力;项目过程实例成立能力;过程节点与流控位置表达能力;Activity 执行语境与反馈绑定能力;暂停等待与恢复语境表达能力;过程事实恢复连续性维护能力;过程执行事实消费与追溯能力;过程执行事实维护与对账能力 |
| 外围增强能力 | 高级过程投影视图能力;完整 BPMN / 嵌套过程表达能力;模板刚度与高级裁剪策略能力;自动调度 / 重试 / 补偿建议能力;容量、延迟和恢复趋势分析能力 |
| 边界外能力 | 方法定义管理;项目工作事实管理;治理决策;产物正文管理;runtime 执行推进;成员生命周期管理;conversation fact;workspace 聚合 dashboard |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 功能组织方式 | 对象 / 状态机 / gateway / checkpoint / 协作事件 | 核心闭环能力 + 外围增强能力 | 对齐需求规范,支撑追溯矩阵 |
| Template 表达 | ProcessTemplate 索引 | 运行时过程形态形成 | 防止 process 接管 method-library 定义真相 |
| Instance 表达 | ProcessInstance 状态机 | 项目过程实例成立 | 避免在 Step 9 展开状态集和迁移规则 |
| Activity / Token 表达 | Activity 状态机和 Token/Gateway 推进 | 过程节点与流控位置表达 | 保留推进位置能力,不写机制细节 |
| Checkpoint 表达 | Checkpoint 链 / RecoverInstance | 过程事实恢复连续性维护 | 保留恢复价值,不提前写事务和性能指标 |
| 相邻仓协作 | governance / artifact / work / runtime 作为功能项 | 作为能力触发、约束或后续接口依赖线索 | 防止 Process 接管相邻仓 truth |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 保留旧 F-001~F-013 | 覆盖面广,接近旧实现想象 | 状态机、接口、事件、规则、非功能和 ADR 混写,无法直接追溯闭环 | 不采用 |
| 方案 B: 按核心闭环归并能力主题 | 能从故事追到能力,也能给规则、数据、验收提供结构锚点 | 后续需要再拆规则、接口和对象 | 采用 |
| 方案 C: 按旧概要的五个主要部分直接做功能 | 比旧功能清单更清楚 | 主要部分偏概要结构,仍不是完整功能需求 | 部分吸收 |
| 方案 D: 把外围增强全部删除 | 核心非常清晰 | 会丢失旧文档中已识别的增强线索 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把 checkpoint 写成独立核心功能?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成“Checkpoint 链”核心功能 | 可强调恢复重要性,但容易滑向机制、事务和性能要求 |
| 方案 B | 归入“过程事实恢复连续性维护能力” | 保持能力级表达,规则和非功能后移 |

推荐方案 B。原因是 checkpoint 是恢复连续性的关键线索,但 Step 9 应先表达能力主题。

#### 是否把 waiting gate 写成独立功能?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成“waiting_gate -> governance 流转” | 容易把治理决策和接口协作写进功能章节 |
| 方案 B | 归入“暂停等待与恢复语境表达能力” | 保留过程等待意图,决策和接口后移 |

推荐方案 B。原因是 Process 拥有 waiting gate 意图和过程状态,不拥有 governance decision truth。

#### 是否把完整 BPMN / 嵌套过程写成核心功能?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成核心功能 | 会把高级表达力和 Proposed ADR-0011 过早硬化 |
| 方案 B | 作为外围增强能力 | 保留线索,不加重核心闭环 |

推荐方案 B。原因是基础节点与流控位置已足以支撑当前核心闭环。

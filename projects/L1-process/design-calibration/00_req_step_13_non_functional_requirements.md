## 3. SOP 问题回答

### 3.1 这个仓必须满足哪些性能要求?

性能要求集中在过程执行事实主链不成为项目推进瓶颈,同时不因高级展示或恢复机制把正文依赖拉入主链:

| 性能关注点 | 判断口径 |
|---|---|
| 运行时过程形态形成 | 形成或采用过程形态不应成为项目启动和过程绑定的主链瓶颈 |
| 过程实例和节点推进 | ProcessInstance、Activity 和流控位置变化不应成为协作主链瓶颈 |
| 暂停等待与恢复 | waiting gate、恢复和维护能力不应让过程产生不可解释的长时间阻塞 |
| 基础过程事实读取 | 管理者、执行成员、审计者和相邻仓读取基础过程状态不应被高级 timeline / dashboard 阻断 |
| 外部正文依赖 | 过程能力不得为了性能或便利而拉取并保存 method-library、artifact、runtime、conversation 等正文 |

旧文档中的 `CompleteActivity P95 < 200ms`、`Checkpoint write P95 < 50ms inline / < 500ms external`、`小 Instance 恢复 < 30s` 当前只能作为后续架构 / 测试阶段的候选目标或容量假设,不在需求 Step 13 直接定为已验证硬指标。

### 3.2 这个仓必须满足哪些可用性要求?

| 可用性关注点 | 判断口径 |
|---|---|
| 核心闭环可用 | 外围增强能力失效时,运行时过程形态、项目过程实例、节点流控、暂停恢复和追溯能力仍应成立 |
| 外部依赖降级 | method-library、work、identity、governance、artifact、runtime、conversation 等外部输入延迟时,不得篡改 Process 真相边界 |
| 等待与恢复降级 | governance 决策、runtime 反馈或人工处理延迟时,过程应能保持可解释等待,而不是静默丢失或伪造恢复 |
| 读写分离口径 | timeline、投影或消费视图延迟时,不得影响 Process 真相写入和审计 |
| 维护任务降级 | 对账、报告或重建失败时,不得隐式修改业务真相 |

### 3.3 这个仓必须满足哪些安全要求?

| 安全关注点 | 判断口径 |
|---|---|
| 正文边界 | Process 不得保存 method-library、work、governance、artifact、runtime、identity、conversation、workspace、observability、archive 的正文 |
| 授权边界 | 查询和变更必须遵守 actor、项目语境、过程承担、可见性和治理结论边界 |
| 高风险变化 | 高风险裁剪、强制 gate 移除、关键过程规矩变更和恢复动作不得绕过治理或方法定义约束 |
| 相邻仓边界 | Process 不得通过接口、快照、投影或维护任务接管相邻仓真相 |

### 3.4 这个仓必须满足哪些审计 / 可追溯要求?

| 审计 / 可追溯关注点 | 判断口径 |
|---|---|
| 运行时过程形态 | 运行时过程形态的来源、采用、调整和切换必须可追溯 |
| 过程实例和节点推进 | ProcessInstance、Activity、Token / Gateway 的关键变化必须可解释 |
| 暂停等待与恢复 | waiting gate、等待原因、外部依据、恢复点和恢复结果必须可追溯 |
| 执行反馈绑定 | Activity 执行反馈必须能追溯到正式过程节点语境,但不保存 runtime 正文 |
| 相邻引用 | work、governance、artifact、runtime、conversation 等相邻引用必须能解释来源和失效状态 |
| 维护对账 | 对账、重建和报告必须能解释来源、范围和结果 |

### 3.5 这个仓必须满足哪些幂等 / 一致性要求?

| 幂等 / 一致性关注点 | 判断口径 |
|---|---|
| 单一正式语义 | runtime process shape、ProcessProfile、ProcessInstance、Activity、waiting gate、checkpoint / recovery 不得在需求层出现多真相 |
| 重复变更 | 重复提交同一正式变化不得产生重复过程事实 |
| 外部输入一致性 | 外部快照和引用滞后时,不得让 Process 生成相互矛盾的正式事实 |
| 恢复一致性 | 从恢复语境继续服务时不得产生第二份过程真相 |
| 投影一致性 | 消费视图可滞后,但必须能解释其来源和滞后状态 |

### 3.6 这个仓必须满足哪些可观测性要求?

| 可观测性关注点 | 判断口径 |
|---|---|
| 核心变化可观察 | 运行时过程形态、ProcessInstance、Activity、waiting gate、checkpoint / recovery 的关键变化必须能被平台观察 |
| 边界异常可观察 | 外部正文试图进入 Process、process 试图写 work / governance / runtime truth 等异常必须可发现 |
| 依赖延迟可观察 | method-library、work、governance、artifact、runtime、conversation 等外部输入延迟或缺失必须可识别 |
| 维护状态可观察 | 对账、重建、报告、投影滞后和恢复状态必须有可判断状态 |

### 3.7 哪些要求能量化,哪些只能给出判断口径?

| 类型 | 当前口径 |
|---|---|
| 可候选量化 | Activity 推进路径、基础查询路径、checkpoint / recovery 路径、投影滞后窗口、对账完成时间、事件输出延迟 |
| 当前只给判断口径 | 正文边界、安全越界、waiting gate 可解释、恢复连续性、引用失效、读模型不成为写源 |
| 不在本步定死 | 旧 `200ms / 50ms / 500ms / 30s` 指标,后续测试与容量阶段验证后再决定是否成为正式目标 |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 性能目标 | 直接使用旧 P95 和恢复数字 | 写成主链不阻塞 + 候选量化目标 | 避免没有验证来源的硬指标 |
| 可用性 | 单点性能 / 恢复指标 | 核心闭环可用 + 外围增强可降级 + 等待可解释 | 更贴合 Process 真相仓边界 |
| 安全 | 分散在边界和合规描述中 | 明确正文边界、授权边界、高风险变化和相邻仓边界 | 承接 Step 10 / Step 11 |
| 可追溯 | checkpoint / waiting_gate 覆盖 | 具体到运行时过程形态、实例、节点、等待、恢复、反馈和相邻引用 | 更能支撑验收 |
| 可观测性 | 简短写全链留痕 | 增加边界异常、依赖延迟和维护状态可观察 | 适合后续测试 / 验收 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 原样保留旧 P95 / checkpoint / 30s 指标 | 看起来可量化 | 当前缺稳定来源,容易误导实施和验收 | 不采用 |
| 方案 B: 写判断口径,旧指标作为候选目标 | 保留量化线索,同时避免伪量化 | 后续测试阶段还需验证具体值 | 采用 |
| 方案 C: 只写六类口号 | 简短 | 不可验收 | 不采用 |
| 方案 D: 写实现层 SLO / 监控配置 | 接近落地 | 超出需求层 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把 `CompleteActivity P95 < 200ms` 定为正式需求?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 直接定为正式需求 | 可能形成无来源硬指标 |
| 方案 B | 作为后续架构 / 测试阶段候选目标 | 保留性能方向,避免伪量化 |

推荐方案 B。原因是当前没有真实测量或稳定上游基线。

#### 是否把 `Activity complete 必写 checkpoint` 转成非功能硬要求?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成 100% 每完成一步 checkpoint | 会提前锁定机制和触发时机 |
| 方案 B | 写成关键变化和恢复连续性必须可追溯,checkpoint 细节后移设计 | 保留恢复目标,不提前写机制 |

推荐方案 B。原因是 Step 13 关注质量判断口径,不是 checkpoint 写入机制。

#### 外部依赖失效时是否要求 Process 仍完全可用?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 完全可用 | 不现实,method-library / governance / runtime 等会影响特定判断 |
| 方案 B | 核心真相边界不被篡改,受影响能力等待或降级 | 更符合 Process 的依赖边界 |

推荐方案 B。原因是外部依赖延迟时,Process 应保持真相不被污染,而不是伪装所有能力可用。

## 7. 结构化中间产物

### 7.1 非功能类别结论

| 非功能类别 | 适用性 | 说明 |
|---|---|---|
| 性能 | 适用 | Process 是过程执行事实主链,不应成为项目推进瓶颈 |
| 可用性 | 适用 | 核心闭环能力必须和外围增强降级分开 |
| 安全 | 适用 | Process 存在大量相邻仓正文和决策边界 |
| 审计 / 可追溯 | 强适用 | 过程形态、实例、节点、等待、恢复和反馈必须可解释 |
| 幂等 / 一致性 | 强适用 | Process 需要防止多真相、重复推进和恢复分叉 |
| 可观测性 | 适用 | 关键变化、边界异常、依赖延迟和维护状态需要可发现 |

### 7.2 非功能要求结论

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|
| 性能 | 运行时过程形态形成不应成为项目启动和过程绑定主链瓶颈。 | 后续架构 / 测试阶段可验证形态形成路径延迟;旧指标不直接适用。 |
| 性能 | ProcessInstance、Activity 和流控位置变化不应成为协作主链瓶颈。 | 后续架构 / 测试阶段可验证推进路径延迟;旧 `CompleteActivity P95 < 200ms` 仅作为候选目标。 |
| 性能 | waiting gate、恢复和维护能力不应让过程产生不可解释的长时间阻塞。 | 后续可验证等待 / 恢复路径延迟;旧 `小 Instance 恢复 < 30s` 仅作为候选目标。 |
| 性能 | 基础过程事实读取不应被高级 timeline / dashboard 阻断。 | 基础查询 / 引用能力应可独立于高级展示成立。 |
| 可用性 | 外围增强失效时,核心闭环能力仍应成立。 | 高级投影视图、完整 BPMN / 嵌套过程、模板刚度、高级自动化和容量趋势失效不影响 C-1~C-5 成立。 |
| 可用性 | 外部输入延迟时,Process 不得篡改真相边界。 | method-library、work、governance、artifact、runtime、conversation 延迟时,对应能力可等待或降级,但不得隐式造真相。 |
| 可用性 | governance 决策、runtime 反馈或人工处理延迟时,过程应保持可解释等待。 | waiting gate / pause context 能说明等待原因和受影响能力,不得静默丢失。 |
| 可用性 | 消费视图延迟时不得影响 Process 真相写入。 | timeline / 投影滞后可解释,不能反向改变业务真相。 |
| 安全 | Process 不得保存相邻仓正文。 | 数据归属中明确禁止 method-library、work、governance、artifact、runtime、identity、conversation、workspace、observability、archive 正文进入 Process。 |
| 安全 | 高风险裁剪、强制 gate 移除、关键过程规矩变更和恢复动作不得绕过治理或方法定义约束。 | 必须引用正式约束来源或治理结论,不得由 Process 自行发明决策。 |
| 安全 | 查询和变更不得越过 actor、项目语境、过程承担、可见性和治理边界。 | 未授权主体不能读取或改变不属于其可见范围的过程执行事实。 |
| 审计 / 可追溯 | 运行时过程形态的来源、采用、调整和切换必须可追溯。 | 能说明定义来源、裁剪语境、变化原因和结果。 |
| 审计 / 可追溯 | ProcessInstance、Activity、Token / Gateway 的关键变化必须可解释。 | 能说明变化来源、actor / 来源方、业务理由和结果。 |
| 审计 / 可追溯 | waiting gate、等待原因、外部依据、恢复点和恢复结果必须可追溯。 | 能追溯到外部依据引用或 Process 内正式理由,不保存外部正文。 |
| 审计 / 可追溯 | Activity 执行反馈必须能追溯到正式过程节点语境。 | 能说明反馈来源、对应过程节点和结果,不保存 runtime 正文。 |
| 幂等 / 一致性 | 同一正式过程事实不得因重复输入产生重复真相。 | 重复正式变化只能得到同一业务结果或被识别为冲突。 |
| 幂等 / 一致性 | 恢复时不得产生第二份过程真相。 | 从恢复语境继续服务时必须回到同一 ProcessInstance / 过程事实。 |
| 幂等 / 一致性 | Process 真相、外部快照、引用和消费视图之间必须保持可解释一致。 | 快照 / 投影可滞后,但必须能说明来源和滞后状态。 |
| 可观测性 | 核心过程事实变化必须能被平台稳定观察。 | 运行时过程形态、ProcessInstance、Activity、waiting gate、checkpoint / recovery 变化有可观察记录。 |
| 可观测性 | 边界越界尝试和外部依赖延迟必须可发现。 | 能识别外部正文写入尝试、Process 越界写相邻 truth 尝试、依赖输入延迟或缺失。 |
| 可观测性 | 维护对账和消费视图状态必须可观察。 | 能判断投影 / 报告 / 对账 / 恢复是否成功、滞后或失败。 |

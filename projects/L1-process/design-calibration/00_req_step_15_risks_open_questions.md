## 3. SOP 问题回答

### 3.1 当前还有哪些尚未关闭的风险?

当前风险不是“功能还没实现”,而是后续设计和实现中容易重新串线的需求边界风险:

| 风险 | 当前判断 |
|---|---|
| ProcessTemplate runtime index 与 ProcessTemplateDef 在后续设计中再次混写 | 高风险。它会直接破坏 method-library / Process 边界。 |
| ProcessInstance / Activity / Token 与 WorkItem / Iteration / runtime step 在后续设计中再次混写 | 高风险。它会导致 Process 接管 work 或 runtime 真相。 |
| waiting gate 被写成 governance Gate / Policy / decision 真相 | 高风险。它会导致 Process 接管治理决策。 |
| checkpoint / recovery 被写成 runtime 微步 checkpoint、reasoning trace 或归档包正文 | 高风险。它会破坏 Instance 级恢复边界。 |
| 外部正文或运行时执行正文通过快照、引用或维护任务进入 Process | 高风险。它会破坏数据归属和一票否决项。 |
| 旧性能数字被误认为需求层硬指标 | 中风险。它会让后续验收伪量化。 |
| 完整 BPMN、嵌套过程、模板刚度、高级投影视图和自动化恢复建议被误升级为核心闭环能力 | 中风险。它会加重当前需求范围。 |
| 需求层未定义 API / 状态机 / 存储后,后续 Agent 可能自行补设计 | 中风险。它会在概要 / 详细设计前形成隐含口径。 |

### 3.2 这些风险会影响哪一层需求结构?

| 风险类型 | 主要影响范围 |
|---|---|
| 定义 / 运行时索引边界风险 | §2 本仓定位、§7 核心闭环、§9 功能需求、§10 业务规则、§11 数据归属、§14 验收标准 |
| 过程 / 工作 / runtime 边界风险 | §2 本仓定位、§6 使用方与依赖、§9 功能需求、§10 业务规则、§14 验收标准 |
| 治理与恢复边界风险 | §7 核心闭环、§9 功能需求、§10 业务规则、§11 数据归属、§14 验收标准 |
| 需求粒度漂移风险 | §9 功能需求、§12 接口与依赖、后续概要 / 详细设计 |
| 非功能伪量化风险 | §13 非功能需求、§14 验收标准、后续测试方案 |
| 外围增强误入核心风险 | §7 核心闭环、§8 用户故事、§9 功能需求、§14 验收标准 |

### 3.3 当前还有哪些待确认事项?

待确认事项只保留会影响后续设计口径的问题。前序 Step 中已经明确推荐并被后续决策吸收的问题,不在本步重复列为待确认。

当前仍需挂起的问题集中在后续设计阶段的细化口径:

1. Process 具体 API / Command / Query / Event 名称和字段形态。
2. ProcessProfile、ProcessInstance、Activity、Token / Gateway、waiting gate 和 recovery 的详细状态集和迁移规则。
3. checkpoint 的具体触发点、粒度、外置策略和与 runtime / observability 的边界。
4. mandatory gate / 强制 gate / 高风险裁剪的具体判断来源和治理前置。
5. 完整 BPMN / 嵌套过程和模板刚度分层是否进入后续版本主线。
6. 旧性能 / 恢复候选指标是否会在测试和容量阶段转为正式目标。
7. PostgreSQL、object storage 或其他存储实现是否进入正式配置和实施基线。

### 3.4 哪些待确认项会影响前文结论是否成立?

这些待确认项不会推翻当前需求结论,但会影响后续文档如何细化:

| 待确认类型 | 对前文结论的影响 |
|---|---|
| API / Command / Event 细节 | 不影响需求层能力边界;影响详细设计和实施计划 |
| 状态集和迁移规则 | 不影响“显式变化”和“过程执行事实”原则;影响详细设计状态矩阵 |
| checkpoint 触发点和存储策略 | 不影响恢复连续性原则;影响详细设计、配置设计和测试方案 |
| mandatory gate / 高风险裁剪前置 | 不影响“不得绕过治理或方法定义约束”;影响后续依赖和协议设计 |
| 完整 BPMN / 嵌套过程 / 模板刚度 | 不影响当前核心闭环是否成立;影响外围增强或后续版本范围 |
| 性能候选指标 | 不影响核心闭环是否成立;影响测试方案和容量验收 |
| 存储实现 | 不影响需求层数据归属;影响架构、配置和实施计划 |

### 3.5 哪些风险当前阶段可接受,哪些会阻塞后续推进?

| 分类 | 风险 / 待确认项 | 当前判断 |
|---|---|---|
| 当前可接受 | API 名称、状态集、存储实现、checkpoint 机制、具体证据格式尚未细化 | 属于概要 / 详细 / 配置设计职责,不阻塞需求文档进入 Step 16。 |
| 当前可接受 | 旧性能数字未转为硬指标 | 已作为候选目标暂存,不阻塞需求文档。 |
| 当前可接受 | 完整 BPMN / 嵌套过程 / 模板刚度未纳入核心闭环 | 已按外围增强处理,不阻塞核心需求。 |
| 后续若发生则阻塞 | Process 接管 method-library、work、governance、artifact、runtime、identity、conversation、workspace、observability 或 archive 真相 | 命中一票否决,必须回退修正。 |
| 后续若发生则阻塞 | ProcessInstance / Activity / Token 被写成 WorkItem、Iteration、plan item 或 runtime step truth | 命中过程执行事实污染,必须回退修正。 |
| 后续若发生则阻塞 | 恢复产生第二份过程真相或关键变化不可追溯 | 命中恢复连续性和审计否决项,必须回退修正。 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 原样汇总 Step 1~14 所有 Q 表 | 信息完整 | 大量问题已被后续步骤吸收,会制造重复待确认 | 不采用 |
| 方案 B: 只保留仍需显式约束的风险和后续设计细化事项 | 高信号,便于后续审查 | 需要判断哪些问题已收口 | 采用 |
| 方案 C: 不写待确认事项,认为前序已完全收敛 | 文档干净 | 会掩盖后续设计仍需细化的口径 | 不采用 |
| 方案 D: 在本步解决所有待确认事项 | 看似完整 | 违反 Step 15 职责,会越界进入概要 / 详细设计 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把每个前序 Q 都列入正式待确认事项?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 全部列入 | 会让已收口的边界重新变成未定 |
| 方案 B | 只列后续设计仍需细化的问题 | 保持需求结论稳定 |

推荐方案 B。原因是 Step 15 的目标是约束不确定性,不是重开所有选择。

#### 是否把外围增强能力写成风险?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成“未实现完整 BPMN / 嵌套过程 / 模板刚度”的风险 | 会把后续增强误写成当前缺陷 |
| 方案 B | 写成“外围增强误入核心闭环”的范围风险 | 保持当前核心需求边界 |

推荐方案 B。原因是外围增强本身不是风险,误升级才是风险。

#### 是否把具体 API / 状态机未定写成阻塞风险?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成需求文档阻塞 | 会让需求层承担详细设计职责 |
| 方案 B | 写成后续设计待确认,当前不阻塞需求 Step 16 | 对齐文档分层 |

推荐方案 B。原因是需求文档只负责能力、边界和验收口径。

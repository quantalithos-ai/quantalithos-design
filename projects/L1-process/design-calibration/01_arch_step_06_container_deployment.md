## 3. SOP 问题回答

### 3.1 这个仓运行时有哪些正式容器或运行单元?

当前架构层将 `L1-process` 的运行承载划分为五类运行对象:

| 运行对象 | 类型 | 判断 |
|---|---|---|
| Process 同步入口单元 | 同步入口单元 | 承接变更、查询、管理和正式同步触发流量。 |
| Process 异步消费单元 | 异步消费单元 | 承接来自总线或外部回调 / 信号的正式异步输入面。 |
| Process 后台处理单元 | 后台处理单元 | 承接恢复、投影重建、对账、报告和长时维护工作。 |
| Process 正式状态存储 | 正式存储承载 | 承载 Process truth、checkpoint、派生状态和维护证据所需的正式状态。 |
| Process 基础设施依赖 | 正式基础设施依赖 | 承接事件协作、外部正文 / 大对象引用、定时触发或运行支撑等结构性依赖。 |

### 3.2 同步入口在哪里?

同步入口由 Process 同步入口单元承接。它不是具体 API handler 或 service 名,而是运行承载层的入口角色,用于承接:

| 同步入口流量 | 边界 |
|---|---|
| 运行时过程形态和 ProcessProfile 变更入口 | 必须校验 method-library / governance / work 相关边界,不得接管外部 truth |
| ProcessInstance / Activity / waiting gate / recovery 变更入口 | 必须保持同一 Process truth 和显式变化 |
| 查询与消费视图入口 | 必须只读或读取派生结果,不得隐式写业务真相 |
| 运维 / 管理触发入口 | 必须进入维护边界,不得绕过业务规则 |

### 3.3 异步消费者或后台任务在哪里?

异步输入和后台处理拆成两个运行角色:

| 运行角色 | 承接内容 |
|---|---|
| Process 异步消费单元 | 消费 method-library、work、governance、artifact、runtime、conversation 等能力级变化或反馈输入,并把有效变化送入 Process 运行边界。 |
| Process 后台处理单元 | 执行 checkpoint / recovery 维护、projection rebuild、reconciliation、report、archive / observability handoff 和其它长时维护工作。 |

拆分原因是:异步消费强调外部输入接入和幂等 / 去重 / 隔离,后台处理强调本仓派生状态维护和恢复对账。二者可在物理部署上同部署,但在架构语义上需要分开表达。

### 3.4 数据库 / 缓存 / 总线如何接入?

本步只表达运行承载角色,不定具体产品或表结构:

| 承载对象 | 当前口径 |
|---|---|
| 正式状态存储 | 用于承载 Process 主事实、checkpoint / recovery、消费派生状态和维护证据;具体存储产品和 schema 后续技术选型 / 详细设计 / 配置设计收敛。 |
| 总线基础设施 | 作为事件协作基础设施依赖接入,不成为 Process 的业务真相存储。 |
| 外部正文 / 大对象存储 | 仅作为外部正文或大对象引用承载候选;Process 不保存相邻仓正文。 |
| 缓存 | 当前不作为架构硬前提;若后续引入,只能服务读取或派生性能,不得成为业务真相写源。 |

### 3.5 哪些运行单元必须分开部署,哪些可以同部署?

| 运行单元 | 当前部署口径 |
|---|---|
| Process 同步入口单元 | 架构语义上必须与后台 / 异步承接职责分开;物理上可同部署,但不能混淆入口职责和维护职责。 |
| Process 异步消费单元 | 架构语义上独立,用于隔离外部异步输入、重放和幂等处理;物理上可与后台处理同部署。 |
| Process 后台处理单元 | 架构语义上独立,用于长时维护和恢复对账;物理上可按运行规模与入口分离。 |
| 正式状态存储 | 必须作为独立承载表达;不能内嵌到入口或 worker 运行单元中。 |
| 基础设施依赖 | 必须在架构层表达为外部承载或基础设施依赖,不能被写成本仓核心真相。 |

### 3.6 哪些通信关系是正式主路径?

| 主路径 | 当前口径 |
|---|---|
| 外部入口 -> 同步入口单元 | 入口关系,承接变更、查询和管理流量。 |
| 总线 / 外部反馈 -> 异步消费单元 | 处理 / 消费关系,承接能力级变化和执行反馈输入。 |
| 同步入口 / 异步消费 -> 正式状态存储 | 承载 / 依赖关系,用于 Process truth 和派生状态持久化。 |
| 后台处理单元 -> 正式状态存储 | 承载 / 依赖关系,用于恢复、对账、投影和维护证据。 |
| 运行单元 -> 基础设施依赖 | 承载 / 依赖关系,用于事件协作、定时触发、外部正文引用或交接。 |
| 运行单元 -> 外部消费 / handoff 边界 | 入口 / 处理 / 承载关系的外部对接,不在本步展开协议。 |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 运行承载表达 | API / worker / DB / object storage 倾向 | 同步入口 / 异步消费 / 后台处理 / 正式状态存储 / 基础设施依赖 | 对齐架构规范 4.7 |
| 存储表达 | 候选产品直接出现 | 先表达正式状态存储角色 | 避免提前锁定技术 |
| 消费与维护 | 混在 worker 中 | 异步消费和后台处理分开 | 区分外部输入接入与本仓维护工作 |
| 图主语 | 容易重画系统上下文或实现模块图 | 以本仓运行承载边界框为主语 | 防止章节串线 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 直接沿用旧 API / worker / PostgreSQL / object storage 图 | 接近实现 | 旧技术假设残留,且容易变成实现模块图 | 不采用 |
| 方案 B: 使用运行承载角色图 | 与规范一致,可承接后续技术选型 | 技术细节要后移 | 采用 |
| 方案 C: 当前不画存储和基础设施依赖 | 图更简短 | 无法表达 checkpoint / recovery 和事件协作的运行承载前提 | 不采用 |
| 方案 D: 在本步确定 PostgreSQL / object storage / BPMN engine | 方便后续设计 | 越过 Step 10 技术选型和配置设计 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把 PostgreSQL 写成正式存储产品?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 直接写 PostgreSQL | 提前锁定技术,与需求 §15 的待确认事项冲突 |
| 方案 B | 写正式状态存储角色,产品留到 Step 10 | 保持架构层与技术选型分离 |

推荐方案 B。

#### 是否把 BPMN engine 写成运行单元?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写独立 BPMN engine | 会把完整 BPMN / 引擎选型提前硬化 |
| 方案 B | 不写具体引擎,只在同步入口 / 后台处理中保留过程推进承载 | 与外围增强和技术选型后移口径一致 |

推荐方案 B。

## 7. 结构化中间产物

### 7.1 容器 / 部署架构图

```text
                    +--------------------------+
                    | external entry / triggers |
                    +------------+-------------+
                                 |
                                 | entry
                                 v

      +=======================================================+
      |              L1-process runtime boundary              |
      |                                                       |
      |   +-------------------------+                         |
      |   | Process sync entry unit |                         |
      |   +------------+------------+                         |
      |                |                                      |
      |                | process / consume                    |
      |                v                                      |
      |   +-------------------------+     +----------------+  |
      |   | Process async consumer  |<----| event backbone |  |
      |   | unit                    |     +----------------+  |
      |   +------------+------------+                         |
      |                |                                      |
      |                | process                              |
      |                v                                      |
      |   +-------------------------+                         |
      |   | Process background unit |                         |
      |   +------------+------------+                         |
      |                |                                      |
      |                | carry / depend                       |
      |                v                                      |
      |   +-------------------------+     +----------------+  |
      |   | Process state store     |<--->| infra boundary |  |
      |   +-------------------------+     +----------------+  |
      |                                                       |
      +=======================================================+
                                 |
                                 | handoff / consume
                                 v
                    +--------------------------+
                    | consumers / handoff sinks |
                    +--------------------------+
```

图示说明:

- 图中主语是 `L1-process` 运行承载边界,不是系统上下文、子域结构或代码模块图。
- Process sync entry unit、Process async consumer unit、Process background unit 是运行角色名,不代表具体文件、handler、service 或 worker 实现。
- Process state store 表达正式状态承载角色,不在本步锁定具体数据库产品或 schema。
- event backbone、infra boundary、consumers / handoff sinks 只作为运行时对接边界出现,不表达协议、topic、事件名或调用顺序。

### 7.2 运行单元说明表

| 对象 | 类型 | 主要职责 | 运行关系 | 说明 |
|---|---|---|---|---|
| external entry / triggers | 运行时对接的正式外部边界 | 承接 SDK、上层入口、相邻仓或运维触发流量的外部来源。 | 入口到 Process sync entry unit | 只表示正式入口来源,不表示用户角色或 API 路径。 |
| Process sync entry unit | 同步入口单元 | 承接同步变更、查询、管理和正式触发流量。 | 入口后处理 Process truth 或读取消费面 | 该对象表达入口运行角色,不是 handler / service 代码结构。 |
| Process async consumer unit | 异步消费单元 | 承接总线、回调、反馈或异步输入面。 | 从 event backbone 消费,并处理进入 Process 边界 | 该对象用于隔离外部异步输入、幂等和重放语义。 |
| Process background unit | 后台处理单元 | 承接恢复、投影重建、对账、报告、归档 / 观测交接和长时维护。 | 从 Process 状态和触发源处理维护工作 | 该对象不得被写成业务真相的隐式写源。 |
| Process state store | 正式存储承载 | 承载 Process 主事实、checkpoint / recovery、派生状态和维护证据所需的正式状态。 | 被同步入口、异步消费和后台处理承载 / 依赖 | 当前只固定正式状态承载角色,具体产品和 schema 后续收敛。 |
| event backbone | 正式基础设施依赖 | 承接跨仓事件协作基础。 | 为异步消费和变化输出提供基础设施边界 | 它不是 Process 的业务真相存储。 |
| infra boundary | 正式基础设施依赖 | 承接定时触发、外部正文 / 大对象引用、运行支撑或交接设施边界。 | 被运行单元按需承载 / 依赖 | 本步不锁定对象存储、调度器或其它具体实现。 |
| consumers / handoff sinks | 运行时对接的正式外部边界 | 承接 SDK、conversation、workspace、observability、archive、artifact 等消费或交接。 | 从 Process 运行边界消费或接收 handoff | 只表达运行时外部对接身份,不表达协议或数据格式。 |

### 7.3 部署说明短文

本图把 `L1-process` 运行承载分成同步入口、异步消费、后台处理、正式状态存储和基础设施依赖五类角色,用于保护入口职责、外部输入接入、长时维护和状态承载不混写。同步入口、异步消费和后台处理在物理上可按规模同部署或分离部署,但架构语义必须分开。PostgreSQL、object storage、BPMN engine、queue implementation、timer implementation 等具体技术不在本步定稿,后续由技术选型、配置设计和实施计划收敛。本章不表达 API 路径、事件名、DTO、表结构、部署参数或运维拓扑。

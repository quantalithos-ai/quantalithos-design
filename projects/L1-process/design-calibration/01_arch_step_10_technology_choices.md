## 3. SOP 问题回答

### 3.1 当前采用哪些关键架构机制?

当前正式采用的关键技术机制是:

1. 外部输入通过正式承接边界隔离核心语义。
2. 非 `L0-core` sibling repo 通过运行期接缝、事件协作、引用或快照倒置接入。
3. 运行时过程形态使用本地索引 / 快照 / ref 机制承接 method-library 定义来源。
4. Process 主真相采用持久化状态与 checkpoint / recovery 连续性机制。
5. 同步主真相判断、异步结果承接、后台维护分离。
6. 派生 read model / projection 与写模型隔离。
7. 异步输入和恢复输入采用幂等、重复识别和顺序保护机制。
8. 已成立 Process fact 通过可靠传播 / handoff 边界对外消费。
9. 外部快照和引用采用 stale / unresolved / waiting / invalid 等显式状态标记。
10. 关键变化和维护动作采用 traceability / evidence 记录机制。
11. 技术产品和语言栈暂不作为架构层硬选型。

### 3.2 每个机制解决什么问题?

| 机制 | 解决的问题 |
|---|---|
| 正式承接边界 | 防止外部入口、事件输入或运维触发直接打穿 Process truth。 |
| 运行期接缝和依赖倒置 | 防止 method-library、work、governance、runtime 等相邻仓变成编译期依赖或第二真相。 |
| 本地索引 / 快照 / ref | 让 Process 能使用过程定义来源,但不拥有定义正文。 |
| 持久化状态与 recovery 连续性 | 防止实例推进、暂停、恢复和 checkpoint 分叉成多份过程真相。 |
| 同步 / 异步 / 后台分离 | 防止外部结果和派生维护阻塞主真相,也防止后台任务隐式写业务事实。 |
| read model / projection 隔离 | 防止查询、timeline、workspace 或 report 成为业务写源。 |
| 幂等和顺序保护 | 防止重复事件、乱序反馈或重放恢复输入产生重复事实或状态回退。 |
| 可靠传播 / handoff 边界 | 让已成立事实能够被下游消费和追溯交接,但不要求下游同步确认后才成立主真相。 |
| 显式外部状态标记 | 防止外部快照缺失或过期时由 Process 自造外部 truth。 |
| traceability / evidence 记录 | 让关键变化、等待、恢复、对账和交接可审计、可复盘。 |
| 暂缓产品 / 语言硬选型 | 防止旧 Draft 中的 Python、PostgreSQL、BPMN engine 等假设在未论证前成为正式架构事实。 |

### 3.3 为什么不用其他方案?

| 未采用方案 | 不采用原因 |
|---|---|
| 外部入口直接调用核心语义 | 会绕过承接、校验、幂等、授权和边界判断。 |
| 直接依赖相邻仓源码 | 会破坏 `L0-core` 唯一编译期依赖和 L1 / L2 / L3 真相域边界。 |
| 复制 method-library 定义正文 | 会让 Process 接管定义真相。 |
| 用下游消费成功作为 Process 主真相成立条件 | 会把 workspace、conversation、observability 或 archive 的滞后反向压到主路径。 |
| 让 read model / report / reconciliation 直接推进业务状态 | 会让派生面成为隐式写源。 |
| 现在硬化完整 BPMN engine | 当前需求只要求基础 Activity、Token / Gateway、waiting gate 和 recovery 主线;完整 BPMN 是演进事项。 |
| 现在硬化具体数据库、消息中间件或对象存储 | 架构层已经确定承载角色,具体产品需要在详细设计、配置设计和实施计划中基于数据规模、事务边界和运维约束收敛。 |

### 3.4 每个选型带来什么代价或新风险?

| 机制 | 代价 / 风险 |
|---|---|
| 正式承接边界 | 增加入口层和承接规则,后续必须为每类输入定义明确的 accepted / rejected / pending 口径。 |
| 运行期接缝和依赖倒置 | 增加 ref、snapshot、adapter 和解析失败处理,不能直接复用相邻仓内部模型。 |
| 本地索引 / 快照 / ref | 需要处理定义来源过期、不可解析和版本漂移。 |
| 持久化状态与 recovery 连续性 | 增加状态一致性、恢复证据和冲突处理复杂度。 |
| 同步 / 异步 / 后台分离 | 增加跨边界状态可见性、排队、延迟和维护状态解释成本。 |
| read model / projection 隔离 | 需要暴露 stale / rebuilding / unavailable 等读取状态,并接受消费面短暂滞后。 |
| 幂等和顺序保护 | 需要稳定身份、顺序依据和重复识别依据,否则无法解释重放输入。 |
| 可靠传播 / handoff 边界 | 需要记录待传播、失败、重试或交接状态,并避免把下游失败误写成主真相失败。 |
| 显式外部状态标记 | 查询和业务判断需要承接 unresolved / stale 等状态,用户体验与调用方处理会更复杂。 |
| traceability / evidence 记录 | 增加证据面和追溯材料维护成本,但不能把外部正文顺带存入 Process。 |
| 暂缓产品 / 语言硬选型 | 后续详细设计仍需补充产品级论证,当前不能用具体产品能力替代架构机制。 |

### 3.5 哪些选型是当前阶段必要的,哪些暂不引入?

| 类别 | 当前口径 |
|---|---|
| 当前阶段必要 | 正式承接边界、依赖倒置、本地索引 / 快照 / ref、持久化 Process truth、checkpoint / recovery 连续性、同步 / 异步 / 后台分离、projection 隔离、幂等 / 顺序保护、可靠传播 / handoff、显式外部状态标记、traceability / evidence |
| 当前阶段暂不引入为硬选型 | 具体语言栈、具体数据库产品、具体消息中间件、具体对象存储、完整 BPMN engine、缓存作为主真相、外部正文入仓、非 `L0-core` sibling 编译期依赖 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 直接继承旧 Python / PostgreSQL / BPMN engine 选型 | 快速形成实现方向 | 与新版需求、依赖裁剪和待确认事项冲突 | 不采用 |
| 方案 B: 先固化架构层技术机制,产品级选型后移 | 可保护边界,避免旧假设污染 | 后续仍需详细设计补产品级论证 | 采用 |
| 方案 C: 当前完全不写技术机制 | 避免误选产品 | 后续详细设计缺少结构性依据 | 不采用 |
| 方案 D: 把所有机制都写成可选 | 灵活 | 主真相、依赖和一致性边界会失去约束力 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否当前选择完整 BPMN engine?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 当前采用完整 BPMN engine 作为架构硬选型 | 会提前扩大表达力范围,并可能让引擎语义反向定义 Process truth |
| 方案 B | 当前采用基础过程推进机制,完整 BPMN engine 保留为后续演进 / 替代方案 | 与 C-1~C-5 核心闭环和当前阶段取舍一致 |

推荐方案 B。

#### 是否当前选择具体数据库 / 消息中间件 / 对象存储?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 当前写入具体产品 | 便于实现规划,但缺数据规模、事务边界和运维约束论证 |
| 方案 B | 当前只固定正式状态存储、事件协作和外部正文引用承载机制 | 保持架构层清晰,产品后续收敛 |

推荐方案 B。

#### 是否允许缓存或 projection 成为主真相加速手段?

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 允许缓存 / projection 在必要时推进主状态 | 会破坏写 / 读边界 |
| 方案 B | 缓存 / projection 只能作为读取和派生性能手段,不得反写业务真相 | 守住 Process truth |

推荐方案 B。

## 7. 结构化中间产物

### 7.1 关键技术机制表

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 | 说明 |
|---|---|---|---|---|
| 通过正式承接边界隔离外部输入与核心语义 | 防止同步入口、异步事件、反馈和运维触发直接打穿 Process truth | `L1-process` 需要同时面对 SDK、method-library、work、governance、runtime、conversation 等外部输入,若不隔离会迅速串仓 | 增加承接层判断、输入状态和错误口径 | 该机制决定外部能力如何进入核心边界,属于架构层结构性决定。 |
| 通过运行期接缝和依赖倒置承接非 core sibling 仓 | 防止相邻仓源码和外部 truth 进入 Process 编译期依赖 | `L0-core` 是唯一编译期依赖,其它仓只能以 ref、snapshot、事件、adapter 或 handoff 协作 | 增加解析、快照、失败标记和适配成本 | 该机制影响跨仓依赖结构,不是局部实现便利。 |
| 使用本地索引 / 快照 / ref 承接运行时过程形态 | 让 Process 使用 method-library 定义来源,但不拥有定义正文 | Process 需要形成可运行过程语境,同时必须守住 definition truth 不入仓 | 需要处理版本漂移、stale、unresolved 和重建 | 该机制直接保护 Runtime Process Shape 与定义正文的边界。 |
| 持久化 Process truth 并保持 checkpoint / recovery 连续性 | 防止实例推进、等待、恢复和 checkpoint 产生多真相 | ProcessInstance、Activity、Token / Gateway、waiting gate 和 recovery 必须围绕同一事实链成立 | 增加状态冲突、恢复依据和审计证据维护成本 | 该机制决定主真相如何保持连续,不是单纯存储选择。 |
| 同步主真相判断、异步结果承接、后台维护三类路径分离 | 防止外部结果阻塞主路径,也防止后台维护隐式推进业务事实 | Step 9 已确认三类通信方式分别服务即时判断、事实传播 / 结果送达和派生维护 | 增加状态可见性、延迟解释和运行承载分工 | 该机制决定关键交互如何承接,属于架构层通信结构。 |
| 写模型与 read model / projection 隔离 | 防止查询、timeline、workspace、report 或 dashboard 成为业务写源 | Step 8 已确认派生视图最终一致,滞后不得反写主真相 | 需要 stale / rebuilding / unavailable 等读取状态 | 该机制影响数据所有权和一致性策略,不是局部查询优化。 |
| 异步输入、反馈和恢复输入采用幂等与顺序保护 | 防止重复输入、乱序反馈或重放恢复导致重复事实或状态回退 | Process 需要承接事件协作、外部反馈和恢复重放,这些输入天然可能重复或延迟 | 需要稳定身份、顺序依据和重复识别依据 | 该机制保护过程事实唯一性和 recovery 连续性。 |
| 已成立 Process fact 采用可靠传播 / handoff 边界对外消费 | 防止下游滞后阻塞主真相,同时保证变化可被消费和追溯 | conversation、workspace、observability、archive 等下游需要消费已成立事实,但不应反向决定主事实成立 | 需要 pending / failed / retryable / delivered 等交接语义 | 该机制影响最终一致传播和追溯交接,属于架构层决定。 |
| 外部快照和引用使用显式状态标记 | 防止外部 truth 缺失、过期或不可解析时由 Process 自行补真相 | Process 只拥有引用和摘要,外部正文和正式 truth 必须保持在仓外 | 调用方和查询结果必须承接 stale / unresolved / waiting / invalid | 该机制直接保护数据所有权边界。 |
| 关键变化和维护动作采用 traceability / evidence 记录 | 让过程推进、等待、恢复、对账和交接可解释、可审计 | Process 是过程规矩推进的事实仓,关键变化缺证据会影响复盘和归档 | 增加证据面维护成本,且不能把外部正文混入证据 | 该机制支撑跨仓追溯和恢复解释,不是普通日志选择。 |
| 产品 / 语言 / 框架选型延后到后续设计 | 防止旧 Draft 技术假设未经论证进入正式架构 | 当前架构已能确定承载角色和机制,但尚缺产品级输入和实施约束 | 后续仍需在概要 / 详细 / 配置 / 实施阶段补齐产品选择 | 该机制本质是架构治理手段,用于保护真相源闭环。 |

### 7.2 简化对照表

| 当前采用 | 当前不采用 | 边界说明 |
|---|---|---|
| 正式承接边界 | 外部入口直接触达核心语义 | 入口必须经过边界判断。 |
| 运行期接缝 / ref / snapshot / event / handoff | 非 `L0-core` sibling 编译期依赖 | 保护仓际依赖裁剪。 |
| 本地运行时过程形态索引 | 复制 method-library 定义正文 | 保护定义 truth。 |
| 持久化 Process truth 和 recovery 连续性 | 用派生视图或下游状态替代主真相 | 保护过程事实唯一性。 |
| 同步 / 异步 / 后台分离 | 所有交互统一同步或统一异步 | 保护主路径和维护路径边界。 |
| projection 隔离 | read model / report 反写业务真相 | 保护写 / 读边界。 |
| 幂等和顺序保护 | 重复输入直接重新执行 | 防止重复事实和状态回退。 |
| 可靠传播 / handoff 边界 | 下游确认作为主真相成立前置 | 保护最终一致消费口径。 |
| stale / unresolved / waiting / invalid 显式标记 | 外部缺失时本仓补写外部 truth | 保护外部真相边界。 |
| traceability / evidence 记录 | 仅靠运行日志解释关键变化 | 保护可审计和可恢复性。 |
| 延后产品硬选型 | 当前锁定 Python / PostgreSQL / BPMN engine / queue 产品 | 防止旧假设污染新版架构。 |

### 7.3 技术边界说明短文

本章采用的是架构层技术机制,不是产品、框架或部署清单。这些机制之所以进入架构主线,是因为它们直接影响 `L1-process` 如何保护 Process truth、跨仓依赖、数据一致性和关键交互承接。具体语言、数据库、消息中间件、对象存储、BPMN engine、缓存和部署方式仍需在后续概要设计、详细设计、配置设计和实施计划中基于更细输入收敛。任何后续产品选择都不得推翻本章已经确定的边界机制。

## 3. SOP 问题回答

### 3.1 安全边界如何处理?

安全边界不写成认证、密钥、权限系统或制度手册,而写成 Process truth 不被外部能力打穿的架构约束:

| 安全边界 | 当前口径 |
|---|---|
| 外部输入边界 | SDK、总线、runtime feedback、governance decision、method definition、运维触发都必须通过正式承接边界进入。 |
| 核心语义边界 | 外部接缝、技术承载、下游消费和维护任务不得直接改写核心 Process truth。 |
| 数据正文边界 | method-library、work、governance、artifact、runtime、identity、conversation、workspace、observability、archive 正文不得进入 Process。 |
| 高风险变化边界 | 高风险裁剪、强制 gate 移除、关键过程规矩变更和恢复动作不得绕过正式来源或治理约束。 |
| 依赖边界 | 除 `L0-core` 外,非 core sibling 仓不得成为编译期依赖。 |

### 3.2 可观测性需要覆盖哪些正式对象和关键链路?

可观测性覆盖的是主线是否成立、边界是否被越过、失败是否可定位,不是监控平台配置:

| 可观测对象 / 链路 | 需要可见的状态 |
|---|---|
| Runtime Process Shape / ProcessProfile | 来源、采用、调整、切换、stale / unresolved 等状态 |
| ProcessInstance / Activity / Token / Gateway | 建立、推进、暂停、恢复、结束、冲突或失败 |
| waiting gate / pause context | 等待原因、外部依据、等待时长、恢复结果 |
| checkpoint / recovery | 恢复依据、恢复点、恢复结果、恢复失败或挂起 |
| projection / read model / report | rebuilding、stale、unavailable、failed、已重建 |
| event / feedback / handoff | 已承接、重复、乱序、pending、failed、retryable、delivered |
| 边界异常 | 外部正文入仓尝试、Process 越界写相邻 truth、查询 / 维护反写尝试 |

### 3.3 可用性和韧性需要守住什么底线?

韧性 / 恢复能力的底线是失败后保持真相边界和恢复连续性,不得伪装成功:

| 失败 / 降级场景 | 底线 |
|---|---|
| 同步主真相判断失败 | 明确失败或保持原状态,不得写成部分完成。 |
| 外部快照缺失 / 过期 | 标记 stale / unresolved / waiting,不得自造外部 truth。 |
| 异步输入重复 / 乱序 | 幂等识别或拒绝回退,不得产生重复事实。 |
| 下游消费 / handoff 失败 | 保持 pending / failed / retryable,不改变 Process truth 含义。 |
| projection / read model 重建失败 | 暴露 stale / rebuilding / failed,不得反写业务真相。 |
| recovery 依据不足 | 挂起或失败,不得创建第二份 Process truth。 |

### 3.4 性能预算是否需要给出口径?

当前不把旧 `200ms / 50ms / 500ms / 30s` 直接写成架构硬指标,但必须给出性能 / 容量判断口径:

| 性能 / 容量关注点 | 架构口径 |
|---|---|
| 主真相同步判断 | 不能被外部正文读取、完整下游确认或后台维护拖入主路径。 |
| 基础过程事实读取 | 不能被高级 timeline、dashboard、报告或投影重建阻塞。 |
| 异步结果承接 | 必须能解释积压、重复、乱序和延迟,不能回退主真相。 |
| projection / handoff | 允许延迟,但必须有 stale / pending / failed / retryable 等状态。 |
| 候选指标 | 旧 P95、checkpoint 和恢复数字保留为后续测试 / 容量输入,不在本章定死。 |

### 3.5 配置如何管理,哪些配置不应散落?

配置与变更控制关注“配置不能绕过架构主线”,不是配置项清单:

| 配置 / 变更类型 | 架构约束 |
|---|---|
| 边界行为配置 | 不得通过配置让外部入口绕过正式承接边界。 |
| 依赖 / adapter 配置 | 不得通过配置引入非 core sibling 编译期依赖或外部正文入仓。 |
| recovery / checkpoint 配置 | 不得让恢复创建第二份 Process truth 或跳过正式恢复依据。 |
| projection / report 配置 | 不得让派生面成为业务写源。 |
| handoff / event 配置 | 不得让下游确认成为主真相成立前置。 |
| 高风险变化配置 | 不得绕过 method-library / governance 约束或追溯要求。 |

### 3.6 审计与可追溯性如何被正式保证?

审计与可追溯覆盖关键状态变化、关键判断结果和正式承接,不是普通日志:

| 追溯范围 | 必须可解释的内容 |
|---|---|
| 运行时过程形态 | 定义来源、采用语境、裁剪 / 调整原因、切换结果 |
| ProcessInstance / Activity / Token / Gateway | 变化来源、actor / 来源方、前后状态、业务理由 |
| waiting gate / resume | 等待原因、外部依据、恢复依据、恢复结果 |
| runtime feedback | 外部反馈来源、对应过程节点、结果摘要,不保存 runtime 正文 |
| checkpoint / recovery | 恢复点、恢复依据、恢复动作、失败或挂起原因 |
| projection / reconciliation / report | 维护范围、来源、结果、滞后或失败状态 |
| handoff / propagation | 交接材料引用、目标、pending / delivered / failed / retryable 状态 |

### 3.7 哪些横切项与本仓无关,不应机械照抄模板?

| 不进入本章的事项 | 原因 |
|---|---|
| 登录认证体系设计 | 属于安全入口或 identity / platform 相关能力,本仓只承接 actor / authorization 边界。 |
| 密钥轮换、双人审批、值班制度 | 属于制度 / 运维 / 安全实施细节。 |
| 具体监控平台、日志字段、告警阈值 | 属于可观测性实施方案,不属于架构横切约束。 |
| 具体数据库容量、索引和压测脚本 | 属于详细设计、测试计划或实施计划。 |
| 具体配置文件和部署参数 | 属于配置设计和实施计划。 |
| 完整 BPMN 表达力覆盖 | 属于演进路线或方案取舍,不是横切关注点。 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 只列安全、性能、可用性等类别 | 简短 | 没有作用范围和保护目标 | 不采用 |
| 方案 B: 按横切关注点约束表展开 | 可审查,能承接前序主线 | 表格较长 | 采用 |
| 方案 C: 写监控 / 告警 / SLO / 配置实施方案 | 接近落地 | 越过架构层边界 | 不采用 |
| 方案 D: 把所有非功能需求逐条复制进来 | 覆盖全面 | 会重写需求文档,缺架构主线判断 | 不采用 |

## 7. 结构化中间产物

### 7.1 横切关注点约束表

| 横切关注点 | 作用范围 | 约束要求 | 保护目标 | 说明 |
|---|---|---|---|---|
| 安全边界 | 外部输入、外部接缝、核心语义、数据正文、依赖边界、高风险变化 | 外部能力必须通过正式承接边界进入;外部正文不得入仓;高风险变化不得绕过正式来源或治理约束 | 保护 Process truth 不被外部输入、相邻仓正文或配置变化反向统治 | 该要求横切职责边界、依赖方向、数据归属和关键交互,不是单个接口的权限规则。 |
| 审计与可追溯 | 运行时过程形态、ProcessInstance、Activity、Token / Gateway、waiting gate、runtime feedback、checkpoint / recovery、projection / reconciliation、handoff | 关键状态变化、关键判断结果、正式承接和维护动作必须保留可追溯材料,不得只保留瞬时结果 | 保护过程推进、等待、恢复、对账和交接在事后可解释 | 该要求横切主真相、派生维护和交接主线,不是普通日志留存要求。 |
| 可观测性 | 运行承载、同步入口、异步消费、后台处理、projection、handoff、外部依赖和边界异常 | 必须能看见关键状态是否成立、关键传播是否送达、关键失败如何暴露、边界异常是否发生 | 保护架构主线是否按预期成立的可见性 | 该要求不是监控平台配置,而是架构层对可见状态面的正式约束。 |
| 韧性 / 恢复能力 | 同步失败、外部快照缺失、异步重复 / 乱序、下游消费失败、projection 重建失败、recovery 依据不足 | 可恢复失败必须明确失败、挂起、延后收敛或进入 retryable / failed 状态,不得伪装完成或创建第二份 Process truth | 保护失败后的真相边界、恢复连续性和最终一致收敛 | 该要求横切一致性策略、通信方式和后台维护,不是 oncall 手册。 |
| 性能 / 容量约束 | 主真相同步判断、基础过程事实读取、异步结果承接、projection / handoff、后台维护 | 不得让外部正文读取、完整下游确认、高级展示或长时维护进入主路径并放大延迟;候选指标后续验证 | 保护核心推进和基础读取不被不当承接方式拖垮 | 该要求不是压测方案,而是对主线路径承接方式的结构性约束。 |
| 配置与变更控制 | 边界行为、依赖 / adapter、recovery / checkpoint、projection / report、handoff / event、高风险变化 | 配置和变更不得绕过正式承接边界、改变主真相成立前置、让派生面反写真相或引入正文入仓 | 保护已收稳架构主线不被配置层绕开 | 该要求不是配置清单,而是对配置影响范围的架构约束。 |

### 7.2 主线映射小表

| 横切关注点 | 主要作用主线 |
|---|---|
| 安全边界 | 职责边界;依赖方向;数据所有权;关键交互;方案取舍 |
| 审计与可追溯 | 数据一致性;关键技术机制;handoff;recovery;验收否决项 |
| 可观测性 | 容器 / 运行承载;关键交互;失败降级;projection / handoff |
| 韧性 / 恢复能力 | 数据一致性;同步 / 异步 / 后台分离;checkpoint / recovery;可靠传播 |
| 性能 / 容量约束 | 同步主路径;基础查询;异步承接;后台维护;projection |
| 配置与变更控制 | 技术机制;方案取舍;依赖边界;recovery;handoff |

### 7.3 横切影响说明短文

这些横切要求必须进入架构层,是因为它们持续作用于 `L1-process` 的 Process truth、仓际边界、一致性、交互承接、恢复和消费主线。如果只留到实现层或运维层,外部输入、配置变化、派生维护、下游交接或恢复脚本都可能绕过已收敛的架构边界。本章不定义具体监控工具、告警阈值、安全制度、压测脚本或配置文件,这些内容后续在详细设计、配置设计、测试方案和实施计划中承接。后续任何实现选择都不得削弱本章约束。

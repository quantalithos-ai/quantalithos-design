## 3. SOP 问题回答

### 3.1 当前阶段做到哪里才算足够?

当前阶段做到“独立 Process truth + 正式边界协作主线”成立即可,不要求完整 BPMN、完整产品级技术栈、所有外围增强或全部高级视图同时完成。

当前阶段必须成立的结构包括:

| 当前阶段必须成立结构 | 判断口径 |
|---|---|
| 独立 Process truth | Runtime Process Shape、ProcessProfile、ProcessInstance、Activity、Token / Gateway、waiting gate、checkpoint / recovery 能作为同一过程执行事实链条成立。 |
| 正式承接边界 | 同步入口、异步消费、后台维护和外部接缝不能绕过核心规则。 |
| 依赖倒置 | 只有 `L0-core` 作为编译期依赖;其它 sibling 仓只能通过运行期 / 事件 / handoff / ref / snapshot 协作。 |
| 数据归属 | Process 只拥有过程执行事实,外部正文和外部 truth 不入仓。 |
| 一致性分层 | 主真相内部强一致;派生消费、外部快照和下游 handoff 最终一致。 |
| 恢复连续性 | recovery 不产生第二份 Process truth。 |
| 可消费可追溯 | read model / projection、handoff 和 traceability / evidence 只消费或解释事实,不得反写真相。 |

### 3.2 第一批必须守住哪些结构?

第一批必须守住的是会导致仓定位失效的一票否决结构:

1. method-library definition 与 Process runtime index 分离。
2. Activity / Token 与 WorkItem / Iteration / runtime step 分离。
3. waiting gate 与 governance decision 分离。
4. checkpoint / recovery 与 runtime checkpoint、reasoning trace、archive package 正文分离。
5. query / projection / report / reconciliation 不反写真相。
6. 非 `L0-core` sibling repo 不进入编译期依赖。
7. 外部正文不通过快照、引用、证据或维护任务进入 Process。

### 3.3 哪些能力或约束留到后续阶段演进?

| 后续演进项 | 当前口径 |
|---|---|
| 完整 BPMN / 复杂网关 / 嵌套过程 | 后续表达力增强,不作为当前主线成立前置。 |
| 模板刚度分层和高级裁剪策略 | 后续与 method-library / governance 共同收敛,当前只保留边界约束。 |
| 产品级存储、总线、对象存储和语言栈选择 | 后续概要 / 详细 / 配置 / 实施阶段收敛,不得推翻架构边界。 |
| checkpoint 具体触发点、粒度和外置策略 | 后续详细设计和测试计划收敛,当前只固定 recovery 连续性。 |
| projection / handoff / event 的可靠传播机制 | 后续详细设计和配置设计收敛,当前只固定边界和状态口径。 |
| 可观测字段、SLO、告警阈值和压测目标 | 后续测试 / 配置 / 运维承接,当前只固定横切约束。 |
| 高级 timeline / dashboard / 趋势分析 | 后续消费面增强,不得进入 Process 主真相结构。 |
| 自动调度、自动重试、补偿建议 | 后续维护和治理增强,当前不得成为隐式业务写源。 |

### 3.4 哪些设计债务当前可接受,哪些不可接受?

| 债务类型 | 当前判断 |
|---|---|
| API / Command / Query / Event 名称和字段未定 | 可接受。属于详细设计职责,不影响当前架构边界成立。 |
| 状态机细节未定 | 可接受。当前已固定显式变化、主真相连续和一票否决边界。 |
| 存储产品和 schema 未定 | 可接受。当前只固定正式状态存储角色和数据所有权。 |
| checkpoint / evidence 字段级 schema 未定 | 可接受。当前只固定 recovery 连续性和追溯要求。 |
| 候选性能目标未定 | 可接受。旧数字作为后续验证输入,不作为当前硬指标。 |
| 完整 BPMN / 嵌套过程未进入主线 | 可接受。当前核心闭环不依赖这些表达力。 |
| 相邻仓正文入仓 | 不可接受。会直接打穿数据归属。 |
| 非 core sibling 编译期依赖 | 不可接受。会破坏全局依赖裁剪。 |
| 派生面反写真相 | 不可接受。会破坏写 / 读 / 维护边界。 |
| recovery 产生第二份 Process truth | 不可接受。会破坏恢复连续性。 |

### 3.5 未来哪些触发条件会迫使架构调整?

| 触发条件 | 需要调整的结构面 |
|---|---|
| 基础 Activity / Token / Gateway 已无法表达实际过程路线 | 进入复杂过程表达力演进,评估完整 BPMN / 复杂网关 / 嵌套过程。 |
| method-library 模板变化、治理裁剪和项目采用关系出现多层冲突 | 进入模板刚度、裁剪策略和治理联动演进。 |
| projection / handoff 延迟或失败开始影响下游关键消费 | 强化可靠传播、重建、失败可见性和消费 SLA 口径。 |
| checkpoint / recovery 的现有粒度无法解释恢复结果 | 细化 recovery evidence、checkpoint 粒度和恢复状态矩阵。 |
| 外部快照 stale / unresolved 成为常态且阻塞主线判断 | 强化 snapshot refresh、引用解析和依赖降级策略。 |
| 旧候选性能目标被测试验证为必须硬化 | 将候选 SLO 转入测试计划、配置设计和容量约束。 |
| 配置变更开始影响边界行为或恢复口径 | 强化配置治理、变更审查和架构约束映射。 |

## 7. 结构化中间产物

### 7.1 演进路线表

| 阶段 | 当前目标 / 范围 | 当前可接受债务 | 后续演进项 | 触发条件 | 说明 |
|---|---|---|---|---|---|
| 当前主线成立阶段 | 让独立 Process truth、正式承接边界、依赖倒置、数据归属、一致性分层、恢复连续性和可消费可追溯成立 | API / event / job 名称未定;状态机细节未定;存储产品未定;checkpoint / evidence schema 未定;候选性能目标未硬化 | 进入详细状态机、协议、存储和证据设计 | 进入概要 / 详细 / 配置 / 测试文档时 | 当前目标不是全功能完成,而是让主线边界稳定成立。 |
| 协作可靠性增强阶段 | 在不改变主真相边界的前提下强化 projection、handoff、event、snapshot refresh 和 recovery 的可靠承接 | 当前只固定 pending / failed / retryable / stale / unresolved 等口径 | 可靠传播机制、重建机制、失败可见性、引用解析策略 | 下游消费延迟、handoff 失败、snapshot stale 开始影响关键协作 | 该阶段强化最终一致承接,不得反写主真相。 |
| 过程表达力增强阶段 | 扩展基础 Activity / Token / Gateway / waiting gate 之外的复杂过程表达 | 当前不覆盖完整 BPMN、复杂网关、嵌套过程和 CallActivity | 完整 BPMN 评估、复杂网关、嵌套过程、模板刚度分层 | 基础过程模型无法解释实际项目过程路线或方法库表达力要求 | 该阶段必须避免让引擎语义反向定义 Process truth。 |
| 治理联动增强阶段 | 强化模板裁剪、高风险过程变化、mandatory gate 和 governance decision 之间的正式协作 | 当前只固定不得绕过 method-library / governance 约束 | 治理前置细化、裁剪策略、gate 恢复依据、审计证据增强 | 高风险裁剪、强制 gate 移除或治理等待成为常态需求 | 该阶段增强协作边界,不得让 Process 接管 decision truth。 |
| 规模与运维治理阶段 | 将候选性能目标、容量约束、配置治理和可观测状态面硬化为可执行约束 | 当前旧 P95 / checkpoint / recovery 数字只作为候选;配置项和监控字段未定 | SLO、容量模型、配置清单、告警 / 观测状态、变更控制策略 | 测试或运行数据证明候选目标必须硬化,或配置变更开始影响边界行为 | 该阶段由真实规模和运维压力触发,不是提前锁工具。 |

### 7.2 触发条件小表

| 触发条件 | 进入的演进方向 |
|---|---|
| 下游消费或 handoff 延迟开始影响关键业务协作 | 协作可靠性增强 |
| 外部 snapshot stale / unresolved 频繁阻塞主线判断 | 协作可靠性增强 |
| 基础 Activity / Token / Gateway 无法表达实际路线 | 过程表达力增强 |
| method-library 模板和项目裁剪出现多层冲突 | 过程表达力增强 / 治理联动增强 |
| mandatory gate、高风险裁剪和治理等待成为常态 | 治理联动增强 |
| recovery 结果不可解释或恢复粒度不足 | 协作可靠性增强 / 规模与运维治理 |
| 候选性能目标被验证为必须硬化 | 规模与运维治理 |
| 配置变更开始绕开边界行为或恢复口径 | 规模与运维治理 |

### 7.3 阶段边界说明短文

当前阶段不是“全做完才算成立”,而是先让 `L1-process` 的独立 Process truth、边界协作、依赖裁剪、一致性和恢复连续性稳定成立。完整 BPMN、复杂网关、嵌套过程、高级投影、自动化建议、产品级技术栈和硬 SLO 都是后续结构压力出现后才进入主线的演进项。当前可接受债务必须满足一个前提:不打穿相邻仓边界、不让派生面反写真相、不破坏 recovery 连续性、不引入非 core 编译期依赖。任何演进都必须由明确触发条件驱动,不能把未来愿望池写成当前架构承诺。

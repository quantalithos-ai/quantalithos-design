## 1. 业务背景与驱动力

### 1.1 业务背景

在 Quantalithos 里,真正的业务主语不是"一次对话"或"一个 Agent",而是**软件项目(Project)**。项目包含:
- 谁参与(ProjectMember)
- 做哪些事(WorkItem)
- 当前积压什么(Backlog)
- 这次承诺做什么(Iteration)
- 绑定哪个过程模板(process_profile_id / instance_id)

L1-work 是六域里最贴近业务的主干仓之一,把软件工程管理对象落地成可持久化、可编排、可度量的聚合根。

### 1.2 业务驱动力

**业务驱动力**:
- 用户需要管理项目的完整生命周期
- 软件交付必须以 WorkItem / Iteration 的形式组织
- 双层 Member 模型要求项目内分配层(ProjectMember)

**技术驱动力**:
- WorkItem DAG 需要真实约束与性能设计
- 与 process / governance / artifact / conversation 形成跨域事件链
- 看板 / 依赖图 / spillover / baseline 等都依赖本仓模型

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | CreateWorkItem P95 | < 100ms | benchmark |
| 性能 | GetProjectBoard P95 | < 300ms | benchmark |
| 规模 | 活跃 WorkItem | 500w | 压测 |
| 状态一致性 | done 判据满足率 | 100% | 集成测试 |
| DAG 健康 | 环依赖写入 | 0 | 约束测试 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| WorkItem 状态流转 | 高频 | 聚合内状态机 + 事件发布 |
| ProjectMember 授权 | 中 | tool_scope / policy_overrides 抽象 |
| 看板视图 | 高频读 | read model / board projection |
| process 绑定 | 中 | 引用型字段,不嵌入 process 逻辑 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **聚合驱动 + read model**(当前)| 聚合边界清晰,读写分层可扩展 | board 物化视图增加复杂度 | ✅ 最匹配 |
| 纯 CRUD + SQL 视图 | 实现快 | 语义弱、状态机散落 | ❌ |
| event-sourcing 全量 | 审计强 | 过重 | ⚠️ 暂不需要 |

**最终选择**:**Project 聚合 + WorkItem 聚合 + Iteration 聚合 + Project 内嵌 ProjectMember / Backlog + board 投影**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| Project 作为 SoI 聚合根 | 业务主语明确 | 聚合较大 |
| ProjectMember 内嵌 Project | 边界清晰 | 查询要展开聚合 |
| board 读模型可分离 | 读性能高 | 多一份投影维护 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```text
Owner / PM / AI Members
        │
        ▼
   ★ quantalithos-work ★
   - Project
   - ProjectMember
   - Backlog(empty pool allowed)
   - WorkItem / child WorkItem
   - Iteration(planned_workitems subset)
        │
   ┌────┼────────────┬────────────┬────────────┬────────────┐
   ▼    ▼            ▼            ▼            ▼
identity conversation process   governance   artifact / archive
member    project group   planning timing  gate      done criterion / evidence
lifecycle                                 decisions  / baseline / archive
```

**任务拆分层次(当前正式模型)**:

```text
Backlog / WorkItem / child WorkItem
  = 团队协作与项目管理事实层

Iteration
  = 从 Backlog 中选出的时间窗口承诺子集

ImplementationPlan / checklist
  = 个人或局部执行计划层(不默认进入 Backlog 真相)

TaskDefinition.steps
  = 某类任务的标准方法步骤(方法资产层)

Process Activity
  = 规划 / refinement / review / gate 等节奏节点
```


### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ Project 生命周期
- ✅ ProjectMember 项目分配层
- ✅ Backlog / WorkItem / Iteration
- ✅ WorkItem DAG
- ✅ tool_scope / policy_overrides
- ✅ 看板查询

**不做什么**:
- ❌ GlobalMember(identity)
- ❌ 流程编排(process)
- ❌ Gate 决策(governance)
- ❌ Artifact 内容存储(artifact)
- ❌ Conversation group 本体(conversation)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| PostgreSQL | 99.95% | 无(主业务阻断) |
| identity | 99.9% | ProjectMember 新建受阻 |
| process | 99.9% | 项目无法启动 / 暂停 |
| artifact | 99.9% | done 判据延迟 |
| governance | 99.9% | lifecycle Gate 保持等待 |

### 4.4 关键依赖风险

- WorkItem DAG 查询成本高
- process / governance / artifact 三方联动复杂
- board 高并发读可能压主库

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |

| Project | 项目身份与生命周期 | Project |

### 5.3 上下文映射关系

- identity → Assignment: Conformist(GlobalMember 生命周期事件)

- process → Project: Customer-Supplier(process_profile_id / instance_id)
- governance → Project: kickoff / archive / aiia gate decisions
- artifact → Planning: approved artifacts 驱动 done 判据

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |
|---|---|---|
| Project | 软件项目 SoI | Project |

| Iteration | 从 Backlog 选出的承诺子集 | Planning |
| WorkItem | 具体工作项,先进入 Backlog,再按 Iteration / Board / Gate 流转 | Planning |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
users / AI members
      │
      ▼
work-api
  │
  ▼
application layer
  │
  ├─▶ domain(Project / WorkItem / Iteration)
  │
  ├─▶ board read model
  │
  ├─▶ subscriptions(identity/process/governance/artifact)
  │
  └─▶ postgres + outbox
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| work-api | RPC / HTTP 入口 | Rust |
| work-domain | 聚合逻辑 | Rust |
| board-projection | 看板读模型 | Rust + PG view / materialized view |
| subscriptions | 事件订阅 | Rust |
| postgres | 项目 / 工作项持久化 | PostgreSQL |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| 下游读看板 | RPC / HTTP | 类型明确 |
| 上游事件输入 | bus | 六域平权 |
| process 绑定 | 引用 + 事件 | 避免嵌入编排逻辑 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| `projects` | work | work / read model |
| `project_members` | work | work |
| `work_items` | work | work / artifact / board |
| `iterations` | work | work / board |
| `work_events_outbox` | work | outbox worker |

### 6.5 部署拓扑

- 单仓单服务起步
- board 先与主服务同进程
- 若读压高,未来可拆 projection 服务

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Project | work | process / governance / conversation | 聚合内强一致 | lifecycle 联动 |
| ProjectMember | work | member-service / conversation | 聚合内强一致 | identity 事件延迟 |
| WorkItem | work | board / artifact / process | 聚合内强一致 + 事件最终一致 | done 判据延迟 |
| Iteration | work | board / process | 强一致 | spillover 漏算 |
| Board projection | work | UI / read-side | 最终一致 | 延迟 |

### 8.2 一致性层次

- 聚合内:Project / WorkItem / Iteration 本地事务强一致
- 聚合间:Backlog / Iteration / Artifact done 判据 最终一致
- 跨服务:Kickoff / Archive Gate / Process bind 通过事件最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| artifact.approved 延迟 | workitem done 延迟判断 |
| process.instance 创建失败 | project 保持 active 但无 instance,告警 + 重试 |
| governance gate 决策失败 / 丢失 | 事件回放 |

### 8.4 任务拆分与进入计划规则

```text
Project 创建
  ▼
Backlog 创建为空池
  ▼
需求 / refinement / 对话 / 模板建议 / review / gate
  ▼
产生 WorkItem, 进入 Backlog
  ▼
Sprint Planning / Iteration Planning Activity 到达
  ▼
从 Backlog 选择 WorkItem 形成 Iteration.planned_workitems
```

**规则**:
- Backlog 先存在,可以为空; Sprint Planning 不创建 Backlog 真相
- child WorkItem 仍属于 work 域正式工作事实,只是 `parent_workitem_id` 指向父项
- `ImplementationPlan` 是执行层/产物层对象,默认不进入 Backlog; 只有升级为 child WorkItem 后才进入正式协作计划
- WorkItem 是否进入当前 Iteration,取决于它是否构成本轮承诺子集,而不是取决于它是否存在

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| board 读模型是否独立拆分未定 | 高读场景时扩展性 | P1 |
| 跨项目依赖未支持 | 大规模项目管理能力 | P2 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| GetProjectBoard P95 > 300ms | 持续 1 周 | 拆 projection |
| 活跃 WorkItem > 500w | 持续 1 月 | 分片 / 归档策略 |
| DAG 查询 > 100ms | 持续 1 周 | 评估图引擎 |

### 12.3 演进步骤

```
阶段 1: Project / WorkItem / Iteration 基础落地
阶段 2: board projection 优化
阶段 3: Kanban / Scrumban 差异细化
阶段 4: 跨项目依赖 / 高阶授权
```

### 12.4 目标架构

work 域的目标是:
- 成为"软件项目"这个业务对象的单一真相源
- 清晰承载 backlog / iteration / workitem / projectmember 语义
- 与 process / governance / artifact 以事件清晰编织

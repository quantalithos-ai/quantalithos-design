## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L1-work` 不是流程引擎,也不是聊天系统。它是 **“项目工作事实仓”**。

你可以把它理解成:
- 这个项目现在有哪些正式待办
- 这些待办的优先级如何
- 这一轮(Iteration / Sprint)真正承诺做哪些
- 每个任务归谁负责
- 哪些任务互相依赖
- 哪些任务真的可以判定为 done

这些事情,都由 `L1-work` 负责保存和管理。

### 1.2 为什么要单独有这个仓

如果没有 `L1-work`,这些工作事实就会散落在:
- 对话记录里
- 流程节点里
- 个人 checklist 里
- PR / 评审记录里
- 执行计划或运行时上下文里

结果就会出现:
- 项目里到底有哪些正式任务说不清
- 哪些是团队协作任务、哪些只是个人步骤混在一起
- Sprint Planning 和 Backlog 本体混在一起
- 审计时无法回答“这项工作是谁提出的、谁批准的、为什么现在算完成”

所以 `L1-work` 必须独立存在,作为:
> **项目层工作事实的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Project
就是:
> 平台里真正被推进、被管理、被审计的那个软件项目主体。

在 Quantalithos 里,项目(Project)不是某次会话,也不是某个 Agent,而是整个软件工程协作的业务主语。

#### ProjectMember
就是:
> GlobalMember 在某个具体项目里的分身。

它回答的不是“这个成员是谁”,而是:
- 他在这个项目里是什么角色
- 当前是否 active / paused
- 被允许承接什么工作

#### Backlog
就是:
> 项目里所有还没做完、值得被正式跟踪的待办全集。

它可以一开始是空的。它不是流程节点,也不是某个人的私有 TODO。

#### WorkItem
就是:
> 团队需要正式跟踪的一条工作。

例如:
- 实现登录 API
- 实现登录页面
- 增加登录 E2E 测试

它会被:
- 分配
- 排优先级
- 建依赖
- 进入迭代
- 被验收

#### child WorkItem
就是:
> 某个 WorkItem 被拆成更小、但仍然需要团队协作跟踪的正式子任务。

关键点:它不是“执行步骤”,而是新的正式协作任务。

#### Iteration
就是:
> 从 Backlog 里选出来的“这一轮承诺做的那部分任务”。

它不是 backlog 全集,而是 backlog 的时间窗口子集。

#### ImplementationPlan
就是:
> 某个 WorkItem 的执行路线图。

它回答:
- 先做哪一步
- 哪一步先验证风险
- 哪些步骤只是个人执行动作
- 哪些步骤如果变复杂,应该升级成 child WorkItem

最重要的一句区别是:

```text
WorkItem / child WorkItem = 团队协作事实
ImplementationPlan         = 个人或局部执行计划
```

#### promote
就是:
> 把原本只存在于 ImplementationPlan 中的某个计划项,升级成正式 child WorkItem。

只有当它进入协作、依赖、排期、验收、风险视野时,才应该 promote。

### 1.4 内容采集结论(本仓当前重写基线)

本次重写 `L1-work/02` 时,已经先收稳以下前提:
- `L1-work` 的核心主线不是“所有任务系统功能平均展开”,而是先把 WorkItem / child WorkItem / ImplementationPlan 这条主线讲清楚
- Backlog 先存在,可以为空池
- Sprint Planning 不创建 Backlog,而是从 Backlog 中选择 WorkItem 形成 Iteration 承诺子集
- child WorkItem 是协作级拆分后的正式工作事实
- ImplementationPlan 是执行计划层对象,默认不进入 Backlog 真相
- 只有进入协作、依赖、排期、验收、风险视野的 plan item 才应 promote 为 child WorkItem

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,真正需要长期管理和审计的,不是某个瞬时流程节点,也不是某个 Agent 当下的内部步骤,而是:
- 项目(Project)
- 项目成员(ProjectMember)
- 待办全集(Backlog)
- 协作级工作单元(WorkItem / child WorkItem)
- 某个时间窗口内承诺完成的子集(Iteration)

如果这些对象和:
- Sprint Planning
- 个人执行 checklist
- review / retro 节奏节点
- ImplementationPlan
- 运行时局部执行状态

混在一起,后续系统会快速退化成:
- backlog 被个人步骤污染
- planning 节奏与工作事实混层
- child WorkItem 和 plan item 语义混淆
- process 引擎接管了本该归 `work` 的真相
- runtime 或 artifact 被误当成任务真相源

因此,本概要设计的任务就是:
> **用对新人也清楚的方式,把 `L1-work` 的项目工作事实模型、主要组成部分和交互方式讲清楚。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| Backlog 粒度 | 讨论中容易混入个人步骤 | Backlog 只保留协作级工作事实 | 需沉淀清晰分层图 |
| Planning 归属 | 易误解为创建任务真相 | Planning 只负责节奏与选择 | 需用主流程图固定 |
| child WorkItem | 会话中已成熟,正式文档吸收不足 | 协作级拆分边界清楚 | 需承接到详细设计 |
| ImplementationPlan | 已开始吸收,但读者容易混淆 | 明确为执行计划层对象 | 需用人话与例子解释 |
| promote 语义 | 已形成高层判断,但缺统一入口表达 | 只在协作条件触发升级 | 需写成固定边界 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:项目管理系统如何只保留团队真正需要跟踪的工作事实,而不是把所有个人步骤都抬升成正式任务
- **技术问题**:Backlog / WorkItem / child WorkItem / Iteration / ImplementationPlan / Process Activity 之间的边界如何稳定建模,并支持后续测试、验收和实现

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确工作事实层边界 | Backlog / WorkItem / child WorkItem / Iteration 职责无歧义 | 文档评审 |
| 明确 planning 边界 | Sprint Planning 不创建 Backlog 真相 | 文档评审 + 后续测试 |
| 明确执行计划边界 | ImplementationPlan 与 WorkItem 不混淆 | 文档评审 |
| 明确 promote 原则 | 只有进入协作视野的 plan item 才升级 | 文档评审 + 后续测试 |
| 支撑后续详细设计 | 本文足以承接 `03-详细设计.md` 的对象模型、流程图与交互边界 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文定义完整 API 字段和数据库 DDL(留给 `03-详细设计.md`)
- 不在本文定义 child WorkItem 的完整 proposal / accepted / rejected 状态流(留给详细设计)
- 不在本文决定 `ImplementationPlan` 是否正式进入 artifact kind 枚举(该问题由 artifact/runtime 继续深化)
- 不在本文接管 process / governance / artifact / runtime 的正式对象模型
- 不在本文给出完整表结构、索引、错误码和补偿机制

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ identity                   │
                    │ - GlobalMember             │
                    │ - lifecycle state          │
                    └────────────┬───────────────┘
                                 │ member lifecycle
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ conversation               │   │ work                       │   │ process                    │
│ - project group view       │◀──│ - Project                  │──▶│ - planning / review timing │
│ - board projection         │   │ - Backlog                  │   │ - ProcessInstance state    │
│ - task summary             │   │ - WorkItem / child WI      │   │ - gate / checkpoint timing │
└────────────────────────────┘   │ - Iteration                │   └────────────────────────────┘
                                 │ - ProjectMember            │
                                 └────────────┬───────────────┘
                                              │ gate decisions / evidence refs / plan execution refs
                                              ▼
                    ┌────────────────────────────┐
                    │ governance / artifact      │
                    │ - gate decisions           │
                    │ - approved evidence        │
                    │ - implementation-plan ref  │
                    └────────────┬───────────────┘
                                 │ execution plan consume / promote trigger
                                 ▼
                    ┌────────────────────────────┐
                    │ runtime                    │
                    │ - assignee execution       │
                    │ - plan item progress       │
                    │ - child WI promote need    │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `identity` 负责“谁是谁”的真相
- `work` 负责“谁在这个项目里承担什么工作”的真相
- `conversation` 展示项目群、任务和协作投影; 它不拥有工作事实真相
- `process` 决定 refinement / planning / review / gate 的时机; 它不拥有 Backlog 真相
- `governance` 决定 kickoff / archive / AIIA 等治理决策
- `artifact` 提供 approved evidence / baseline / implementation-plan 关联对象
- `runtime` 负责围绕某个已分配 WorkItem 推进执行计划,并在必要时把某些计划项 promote 成正式 child WorkItem

所以 `L1-work` 在全局里的角色是:
> **项目管理层正式工作事实的锚点仓。**

### 4.3 系统边界

**做什么**:
- 保存项目工作事实真相
- 维护 Project / ProjectMember / Backlog / WorkItem / child WorkItem / Iteration
- 为 planning、board、artifact done 判据、governance gate 决策、runtime promote 提供正式状态基础

**不做什么**:
- 不负责流程节拍编排(process)
- 不负责 Gate 决策(governance)
- 不负责执行路线图的具体读写与推进(runtime / artifact 承接)
- 不负责 Artifact 内容存储与版本冻结
- 不把运行时局部计划直接当成正式工作事实

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| identity | 99.9% | ProjectMember 新建受阻 |
| process | 99.9% | planning / refinement 时机延迟 |
| governance | 99.9% | kickoff/archive Gate 等待 |
| artifact | 99.9% | done 判据延迟 |
| runtime | 99.9% | ImplementationPlan 进度更新延迟,但不改 work 真相边界 |

### 4.5 关键依赖风险

- work / process 边界不稳会导致 planning 节奏污染工作事实
- work / artifact 边界不稳会导致 `ImplementationPlan` 被误建模成任务真相
- work / runtime 边界不稳会导致局部执行步骤直接污染 Backlog
- child WorkItem 与个人执行步骤混淆会导致 Backlog 膨胀

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 项目主语与成员承担部分

- **它是什么**: 这是 `L1-work` 的项目身份与承担关系部分,一起回答“项目是谁、谁在项目里承担什么工作”
- **为什么单独有它**: 如果把 Project 和 ProjectMember 拆成彼此孤立的对象说明,读者会看到两个对象,却看不出它们共同构成项目主语层
- **负责什么**:
  - 定义 Project 作为 SoI 的存在边界
  - 定义 ProjectMember 作为 GlobalMember 的项目内分身
  - 为后续 WorkItem / Iteration / governance / process 提供统一项目锚点
- **不负责什么 / 容易混淆点**:
  - 不负责流程推进节奏
  - 不负责 Artifact 正文或执行路线图内容
  - 最容易和 process 的 ProcessInstance 主语、identity 的 GlobalMember 真相混淆
- **与其他部分交互**:
  - 上游: identity / governance / process
  - 下游: Backlog 与正式工作项管理部分、协作视图与投影部分
  - 交互类型: 生命周期锚点型 + 成员承担映射型
- **后续详细设计展开点**:
  - Project / ProjectMember 对象定义
  - 生命周期状态与同步规则

#### Backlog 与正式工作项管理部分

- **它是什么**: 这是 `L1-work` 的核心正式协作事实部分,一起回答“哪些工作正式存在、如何拆分、如何依赖、如何进入 backlog”
- **为什么单独有它**: 如果按 Backlog / WorkItem / child WorkItem 各自拆开,会把一条完整的正式工作流打散成对象清单
- **负责什么**:
  - 保存项目待办全集
  - 表达 WorkItem / child WorkItem 的正式状态
  - 表达 depends_on / blocks 依赖关系
  - 承接 child WorkItem proposal / accepted / rejected 等正式流程
- **不负责什么 / 容易混淆点**:
  - 不负责个人执行顺序
  - 不把 ImplementationPlan 当 child WorkItem
  - 最容易和 process Activity、ImplementationPlan、conversation suggestion 混淆
- **与其他部分交互**:
  - 上游: 项目主语与成员承担部分、governance corrective action、ImplementationPlan / promote 接缝部分
  - 下游: Iteration 承诺子集管理部分、协作视图与投影部分、artifact done 判据
  - 交互类型: 正式事实写入型 + 依赖约束型 + 证据约束型
- **后续详细设计展开点**:
  - WorkItem / child WorkItem 对象模型
  - proposal/accepted/rejected 机制
  - DAG / done 规则

#### Iteration 承诺子集管理部分

- **它是什么**: 这是 `L1-work` 里专门管理“当前时间窗口承诺子集”的部分
- **为什么单独有它**: 如果把 Iteration 混进 Backlog / WorkItem 部分,就会重新把“全集”和“当前承诺子集”写混
- **负责什么**:
  - 从 Backlog 中选择本轮承诺项
  - 表达 planned / actual / spillover
  - 承接 Sprint / Iteration planning 的结果
- **不负责什么 / 容易混淆点**:
  - 不负责创建 Backlog
  - 不等同于全部 WorkItem
  - 最容易和 Backlog 本体混淆
- **与其他部分交互**:
  - 上游: Backlog 与正式工作项管理部分 + process planning timing
  - 下游: 协作视图与投影部分
  - 交互类型: 节奏触发型 + 承诺收口型
- **后续详细设计展开点**:
  - draft/start/close 流程
  - planned_workitems 冻结规则

#### 协作视图与投影部分

- **它是什么**: 这是 `L1-work` 的只读查询与协作视图部分,一起回答“正式工作事实如何被前台协作界面消费”
- **为什么单独有它**: 如果不单列,conversation / chat 会被迫直接消费写模型细节,读写边界会模糊
- **负责什么**:
  - 提供项目群、看板、任务树、依赖视图
  - 向协作界面暴露正式状态摘要
  - 形成 board / task summary / rollup 等投影视图
- **不负责什么 / 容易混淆点**:
  - 不反向成为写源
  - 不拥有正式工作事实
  - 最容易和 Backlog / WorkItem 真相对象混淆
- **与其他部分交互**:
  - 上游: 项目主语与成员承担部分、Backlog 与正式工作项管理部分、Iteration 承诺子集管理部分
  - 下游: conversation / board / task summary
  - 交互类型: 投影输出型
- **后续详细设计展开点**:
  - read model / DTO
  - 最终一致策略

#### ImplementationPlan / promote 接缝部分

- **它是什么**: 这是 `work` 与 artifact/runtime 之间的执行计划接缝部分,专门处理 plan 引用与 promote 边界
- **为什么单独有它**: 这是当前最容易混边界的地方; 不单列就会把个人步骤、执行证据和正式协作任务写成一锅
- **负责什么**:
  - 说明 work 如何引用 execution plan
  - 说明何时允许从 plan item promote 为 child WorkItem
  - 保护 work 真相不被局部执行步骤污染
- **不负责什么 / 容易混淆点**:

  - 不直接等同 child WorkItem
  - 最容易和 artifact kind / runtime execution object / WorkItem 真相混淆
- **与其他部分交互**:
  - 上游: artifact / runtime
  - 下游: Backlog 与正式工作项管理部分
  - 交互类型: 执行计划接缝型 + promote 触发型
- **后续详细设计展开点**:
  - promote 触发条件
  - child WorkItem 正式化流程接缝

### 6.2 总解释

- `identity` 的交互主要落在 **项目主语与成员承担部分**,让 `ProjectMember` 能和 `GlobalMember` 对齐
- `process` 的交互主要落在 **Backlog 与正式工作项管理部分** 以及 **Iteration 承诺子集管理部分**,负责提供 refinement / planning / review / gate 的时机
- `governance` 的交互主要落在 **项目主语与成员承担部分** 与 **Backlog 与正式工作项管理部分**,决定项目生命周期与某些高风险约束能否推进
- `artifact` 的交互主要落在 **Backlog 与正式工作项管理部分** 与 **ImplementationPlan / promote 接缝部分**,提供 done 判据、baseline 和 plan 引用
- `runtime` 的交互主要落在 **ImplementationPlan / promote 接缝部分**,围绕当前 WorkItem 推进行动,必要时提出 promote 信号
- `conversation` 消费的是 **协作视图与投影部分** 的产出,把正式工作事实投影到协作界面中

**读图方法**:
- 中间的 `work` 是工作事实真相源,但内部不是按对象平铺理解,而是按 5 个主要部分理解
- 上侧、右侧与下侧模块向 `work` 输入“成员生命周期 / 过程节奏 / 治理决策 / 证据关联 / 执行接缝信号”
- 左侧的 `conversation` 主要消费 `work` 的投影视图,而不是反向成为写源
- 箭头上的文字表示“发生了什么交互”,不是简单的模块相邻关系

### 6.5 Backlog / Sprint Planning / Iteration 主流程

```text
Project created
    │
    ▼
Backlog created (can be empty)
    │
    ├─ requirement / refinement
    ├─ conversation suggestion
    ├─ template suggestion
    ├─ review finding
    └─ gate corrective action
            │
            ▼
      WorkItem enters Backlog
            │
            ▼
Sprint / Iteration Planning Activity
            │
            ▼
Select WorkItems from Backlog
            │
            ▼
Form Iteration.planned_workitems
```

**关键解释**:
- Backlog 先存在,可以为空
- WorkItem 先进入 Backlog,再根据 planning 被选入 Iteration
- Sprint Planning 是 process 节奏节点,不创建 Backlog
- Iteration 表示当前阶段/时间窗口内的承诺子集,不是工作事实全集

### 6.6 child WorkItem 与 ImplementationPlan 的关系

```text
WorkItem
  ├─ child WorkItem      -> 协作级拆分,正式进入 work 真相
  └─ ImplementationPlan  -> 个人/局部执行路线图,默认不进入 Backlog
```

**升级原则**:
- ImplementationPlan 中的某一步,若只是个人执行顺序,保留在 plan
- 若进入协作、依赖、排期、验收、风险视野,则 promote 为 child WorkItem
- promote 后的对象要走 work 域正式流程,并可能进入 Backlog / Iteration

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 聚合驱动 + 工作事实层 / 执行计划接缝层分层

**选择理由**:
- 把正式工作事实和个人执行计划分开
- 让 process / governance / artifact / runtime 各自保持边界
- 让 `03-详细设计.md` 能按“真相对象 / 投影对象 / 执行接缝”继续展开

### 7.2 模块划分与职责

```text
┌──────────────────────────────────────────────┐
│                  L1-work                     │
│                                              │
│  ┌────────────┐  ┌────────────────────────┐  │
│  │ Project    │  │ Backlog / WorkItem     │  │
│  │ root       │──│ child WorkItem / DAG   │  │
│  └────────────┘  └────────────┬───────────┘  │
│                                │              │
│                        ┌───────▼───────┐      │
│                        │ Iteration     │      │
│                        │ commitment    │      │
│                        └───────┬───────┘      │
│                                │              │
│                   ┌────────────▼───────────┐  │
│                   │ board / summary view   │  │
│                   └────────────────────────┘  │
└──────────────────────────────────────────────┘
```

| 模块 | 职责(一句话) | 依赖 |
|---|---|---|
| Project / ProjectMember | 定义项目主语与成员承担关系 | identity / governance / process |
| Backlog / WorkItem | 保存正式工作事实与依赖 | artifact / runtime / process |
| Iteration | 表达承诺子集 | Backlog / process |
| View / board | 提供协作投影 | conversation |
| plan boundary | 保护 ImplementationPlan 接缝边界 | artifact / runtime |

### 7.3 模块依赖关系

```text
identity ─────▶ ProjectMember
process ──────▶ Backlog / Iteration timing
governance ───▶ Project lifecycle constraints
artifact ─────▶ done criterion / plan refs
runtime ──────▶ promote trigger boundary
work view ────▶ conversation
```

### 7.4 层间约束规则(防退化)

- work 只持有正式工作事实,不把 execution plan 直接并入真相层
- process 只提供节奏和时机,不创建 Backlog 真相
- runtime 只能围绕 WorkItem 推进行动,不能直接写正式工作事实
- board / summary 只读,不反向成为写源
- child WorkItem 与 ImplementationPlan 不得互相替代

## 8. 关键技术选型

### 8.1 为什么采用“工作事实层 / 执行计划层”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | 分层模型(协作事实 vs 执行计划) |
| 备选方案 | 所有拆分都进入 WorkItem |
| 选择理由 | 防止 Backlog 膨胀,保留团队协作层语义,同时允许执行计划存在 |
| 演进路径 | 后续再细化 child WorkItem proposal/accepted/rejected 与 ImplementationPlan 正式对象模型 |

### 8.2 为什么 Sprint Planning 不持有 Backlog 真相

| 维度 | 内容 |
|---|---|
| 当前选择 | planning 只做节奏与选择 |
| 备选方案 | planning 创建/维护 backlog |
| 选择理由 | 避免 process 越界进入 work 真相层 |
| 演进路径 | 后续在 process/work 详细设计中钉死接口与状态流 |

### 8.3 为什么 promote 必须经过 work 正式流程

| 维度 | 内容 |
|---|---|
| 当前选择 | plan item 满足协作条件后,经 work 正式入口升级 |
| 备选方案 | runtime 本地直接把 plan item 变成任务 |
| 选择理由 | 避免局部执行步骤静默污染 Backlog 与 child WorkItem 真相 |
| 演进路径 | 后续在 `03-详细设计.md` 中展开正式入口与校验点 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: 所有拆分都进 WorkItem | 方案 B: 分层模型(当前) |
|---|---|---|
| PM 可见性 | 高 | 中高 |
| Backlog 清洁度 | 低 | 高 |
| 个人执行步骤表达 | 弱 | 强 |
| 模型复杂度 | 低 | 中 |
| 与 process / artifact / runtime 的边界兼容性 | 低 | 高 |

### 9.2 最终结论

选择方案 B。
因为 Quantalithos 不是单一任务系统,而是平台型系统。它既需要正式工作事实层,也需要执行计划层。如果把所有步骤都做成 WorkItem,后续的 process / artifact / runtime / chat / console 都会被迫消费过细且被污染的任务真相。

## 11. 横切关注点

### 11.1 安全
- 项目生命周期迁移必须受 governance 约束
- done 判据必须引用 approved evidence
- promote 不得绕过正式工作流入口

### 11.2 性能
- CreateWorkItem P95 < 100ms
- GetProjectBoard P95 < 300ms
- Iteration 选择路径不应拖垮主写路径

### 11.3 可用性
- identity / process / governance / artifact 延迟时允许最终一致,但不得篡改 work 真相边界
- board 可读侧延迟,但不影响真相写入

### 11.4 可观测性
- Project / WorkItem / Iteration / promote 主线必须全链留痕
- done 判据链与 artifact 证据链必须可追溯

### 11.5 成本
- 不把 execution plan 整体并入 work,避免模型膨胀与投影放大

### 11.6 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| CreateWorkItem 写路径 | ≤ 100ms | 100ms |
| Board 读取 | ≤ 300ms | 300ms |
| artifact done 判据联动 | 最终一致 | 不做强一致预算 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| child WorkItem 升级条件不清 | 中 | 高 | 在详细设计中固化 promote 规则 |
| ImplementationPlan 归属不稳 | 中 | 高 | 在 artifact / runtime / work 三仓继续收敛 |
| planning 与 backlog 边界松动 | 中 | 高 | 在 process 详细设计中继续钉死 |
| runtime 越界污染正式任务真相 | 中 | 高 | 明确 promote 正式入口 |

### 12.2 边缘风险

- `ImplementationPlan` 是否正式进入 artifact kind 枚举,仍可能影响后续文档写法
- child WorkItem 若引入独立 planning_status,可能让 work 模型复杂度上升
- board / task summary 若消费过多 execution plan 细节,会再次混层

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| `ImplementationPlan` 是否正式进入 artifact kind | 后续 03 / artifact 设计阶段 | work + artifact |
| child WorkItem 是否单独有 planning_status | 03 阶段 | work |
| `accepted` 后一定进入 Backlog 还是允许例外 | 03 阶段 | work + process |

- WorkItem.done 与 approved artifact 一致性
- promote 触发次数与误升级率

## 15. 结论

本概要设计的核心结论是:
- `L1-work` 是项目工作事实真相层
- `L1-work` 内部应按“项目主语与成员承担部分 / Backlog 与正式工作项管理部分 / Iteration 承诺子集管理部分 / 协作视图与投影部分 / ImplementationPlan / promote 接缝部分”来理解,而不是按对象平铺理解
- `process` 管节奏,`work` 管事实,`artifact` 管证据,`runtime` 管执行推进
- `ImplementationPlan` 是执行计划层对象,不默认进入 Backlog 真相
- 只有进入协作视野的 plan item 才升级为 child WorkItem
- 后续 `03-详细设计.md` 应围绕这些主要部分,继续把对象模型、promote 机制、状态约束、事件链和存储规则正式化

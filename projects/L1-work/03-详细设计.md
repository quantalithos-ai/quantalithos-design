## 1. 模块职责描述

**本模块做什么**:
- 保存项目工作事实真相(Project / ProjectMember / Backlog / WorkItem / child WorkItem / Iteration)
- 提供 child WorkItem 从 promote / proposal 到 accepted / rejected、再到 Backlog / Iteration 的正式流程
- 把 `ImplementationPlan` 作为挂在 WorkItem 上的执行型对象/产物进行引用,但不把它误当成 WorkItem 真相
- 为 process / governance / artifact / conversation / runtime 提供正式工作事实锚点

**本模块不做什么**:
- 不负责流程节拍编排(process)
- 不负责 Gate 决策(governance)
- 不负责 `ImplementationPlan` 的具体执行(runtime)与正文持久化策略(artifact)
- 不负责 Artifact 内容存储与 Baseline 冻结
- 不把个人执行顺序直接提升为正式工作事实

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是继续讲概念,而是让实现者能真正开始写代码。
因此在正式落文前,必须先确认下列内容已经收稳,否则容易把 03 写成“更细一点的概要设计”或“字段表堆砌稿”。

### 2.2 内容采集流程(先采集,再落文)

#### 第 0 步:确认 `02-概要设计` 已经稳定

先确认:
- 仓定位是否清楚
- 与其他模块的关系是否清楚
- 主要组成部分是否清楚
- 真相源 / 投影层 / 节奏层 / 证据层 / 执行接缝层边界是否清楚
- `02-概要设计.md` 里的总交互图与分模块交互图是否已经能回答“谁给谁什么语义”
- 每个主要部分是否已经说明“为什么单独存在、负责什么、不负责什么、如何交互”

**产出**:
- 一份可继续下钻的概要设计基线
- 一份“03 必须继续展开的交互链”清单

**作用**:
- 防止在 03 里一边补“仓到底是什么”,一边又写字段和 API

- 表/集合清单

#### 第 4 步:列出事件与外部协作点

## 3. 代码目录结构

### 3.1 先按模块组织,再按文件展开

`03-详细设计` 优先采用“**先模块,后文件**”的写法。
不要一上来只堆完整目录树,否则新人容易看到很多文件名,却不知道这些文件共同支撑哪条主流程。

推荐顺序:
1. 先列技术模块(如 api / application / domain / infra / projection)
2. 再说明这些技术模块分别为哪一个主要部分服务
3. 最后把目录树与文件职责对齐到主要部分

### 3.2 模块到概要交互链映射

| 模块 | 承接的概要交互链 / 主流程 | 服务的主要部分 | 主要职责 |

| application | Backlog / promote / iteration / governance / artifact / runtime 交互编排 | 5 个主要部分之间的编排层 | 把跨聚合与跨仓流程落成用例 |

### 3.5 仓整体运行主流程

```text
[CreateProject]
      │
      ▼
[项目主语与成员承担部分建立 Project / ProjectMember]
      │
      ▼
[Backlog 与正式工作项管理部分创建空 Backlog]
      │
      ▼
[CreateWorkItem / CreateChildWorkItem / dependency maintenance]
      │
      ├──────────────▶ [协作视图与投影部分更新 board / tree / summary]
      │
      ├──────────────▶ [artifact approved 到达 → 正式工作项部分更新 done criterion]
      │
      ├──────────────▶ [process planning timing 到达 → Iteration 承诺子集管理部分形成/冻结承诺集合]
      │
      └──────────────▶ [runtime promote signal 到达 → ImplementationPlan / promote 接缝部分转入 child WorkItem 正式流程]
```

**总解释**:
- `L1-work` 仓的运行主线不是“先有对象表,再有别的”,而是“项目主语建立 → 正式工作事实进入 → 承诺子集收口 → 投影刷新 → 证据与 promote 接缝回写”
- 其中真正承载真相写入的是: 项目主语与成员承担部分、Backlog 与正式工作项管理部分、Iteration 承诺子集管理部分
- 协作视图与投影部分只消费写模型结果
- ImplementationPlan / promote 接缝部分只负责把 execution plan 的升级需求转入正式工作流,不直接污染真相层

## 4. 按主要部分展开实现要点

### 4.1 为什么要先按主要部分展开

`03-详细设计` 不应直接从“字段表 / API / 表结构”开始。
在 Quantalithos 这类平台型系统中,更稳的写法是:
- 先承接 `02-概要设计.md` 已经确认的主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与事件
- 最后再进入横向的对象模型、流程、存储、投影、异常与测试细节

> 这里的“主要部分”,不是“单个对象”或“单张表”。它应按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/投影/接缝差异** 来组织。

这样可以避免:
- `02` 讲的是“主要部分与交互”,`03` 却突然只剩字段表
- 实现者知道有对象,但不知道这些对象归哪个主要部分负责
- 流程、存储、事件和模块职责脱节
- 文档再次滑回“按对象堆砌”的旧写法

### 4.2 项目主语与成员承担部分

#### 4.2.1 该部分承接的概要输入
- 来自 `02` 的“项目主语与成员承担部分”
- identity → ProjectMember 的成员真相输入

#### 4.2.2 输入 / 输出 / 外部交互图

```text
│ identity                   │
│ - GlobalMember lifecycle   │
└────────────┬───────────────┘

             ▼
```

#### 4.2.3 涉及的对象定义

```rust
/// 项目主语，负责保存项目的正式身份、生命周期与外部流程/治理引用。
pub struct Project {
    /// 项目唯一标识，用于把成员、工作项、迭代挂到同一个项目主语下。
    pub project_id: ProjectId,
    /// 项目名称，供协作界面、审计和对外显示使用。
    pub title: String,
    /// 项目当前生命周期状态，决定是否允许继续推进工作流。
    pub state: ProjectState,
    /// 项目绑定的过程模板，用于声明项目按哪种方法推进。
    pub process_profile_id: ProcessProfileId,
    /// 当前项目对应的过程实例，用于和 process 域回链。
    pub process_instance_id: Option<ProcessInstanceId>,
    /// 项目当前持有的治理决策引用，如 kickoff / archive 等 gate。
    pub gate_refs: Vec<GateRef>,
    /// 项目当前关联的基线引用，用于对齐阶段性冻结结果。
    pub baseline_refs: Vec<BaselineRef>,
}

/// 项目内成员分身，负责把全局成员映射成项目内承担关系。
pub struct ProjectMember {
    /// 项目内成员唯一标识。
    pub project_member_id: ProjectMemberId,
    /// 所属项目，用于回到项目主语层。
    pub project_id: ProjectId,
    /// 对应 identity 域中的全局成员引用。
    pub global_member_id: GlobalMemberId,
    /// 该成员在当前项目中的角色。
    pub role: ProjectRole,
    /// 该成员在当前项目中的有效状态，用于控制是否还能承接任务。
    pub state: ProjectMemberState,
}
```

这里把 `Project` 和 `ProjectMember` 放在同一个主要部分中,不是因为它们总是一起持久化,而是因为它们共同承担“项目主语是谁、谁在项目里承担工作”的实现责任。`Project` 负责项目主语和生命周期锚点,`ProjectMember` 负责把 identity 中的全局成员映射成项目内的承担关系。

#### 4.2.4 关键函数代码片段

```rust
/// 根据 identity 域传入的全局成员生命周期，收缩项目内成员状态。
fn sync_project_member_from_identity(
    project: &Project,
    member: &mut ProjectMember,
    lifecycle: GlobalMemberLifecycle,
) {
    ...
    // 只有当全局成员被暂停或退役时，项目内成员状态才同步收缩。
    if lifecycle.is_paused() || lifecycle.is_retired() {
        // 这里不改写 GlobalMember 真相，只更新项目内分身状态。
        member.state = ProjectMemberState::Paused;
    }
    ...
}
```

这段代码的关键不在于“如何同步字段”,而在于守住边界: `identity` 负责 `GlobalMember` 真相,`work` 只把这个真相投影成项目内承担关系。`ProjectMember` 的状态变化必须由 identity 生命周期驱动,而不能在 work 内部随意发明新的全局成员状态。

#### 4.2.5 补充关键函数代码片段

```rust
/// 项目主语对象，负责维护项目生命周期相关不变量。
impl Project {
    pub fn activate(&mut self, process_instance_id: ProcessInstanceId) {
        // Project::assert_draft
        // 只有 draft 项目才允许被激活。
        self.assert_draft();

        // Project.activate
        // 激活后项目正式进入可承接工作事实的状态。
        self.state = ProjectState::Active;

        // Project.activate
        // 记录当前项目绑定的过程实例，保证后续可与 process 回链。
        self.process_instance_id = Some(process_instance_id);
    }

    pub fn archive(&mut self, gate_ref: GateRef) {
```

#### 4.6.4 关键函数代码片段

```rust
/// 把 execution plan 中满足条件的计划项升级为正式 child WorkItem。
fn promote_plan_item_to_child_workitem(
    request: PromoteRequest,
    parent: &WorkItem,
) -> WorkItem {
    ...
    // 先校验这次升级是否真的进入了协作/依赖/验收/风险视野。
    ensure_promote_eligible(&request.reason);
    // 通过正式入口创建 child WorkItem，而不是直接往 Backlog 里塞数据。
    let child = create_child_workitem_from_plan(parent, &request.plan_item_ref);
    // 升级后必须保留 plan ↔ child 的可追溯回链。
    record_plan_origin_link(child.workitem_id, &request.plan_item_ref);
    ...
    child
}
```

这段代码的关键不是“又创建了一个 WorkItem”,而是把 promote 变成一个正式接缝行为: 先验证资格,再进入正式 child WorkItem 流程,最后保留 plan ↔ child 的可追溯回链。这样 runtime 就不会把局部步骤静默提升成正式工作事实。

- 从外部 `runtime / artifact` 接收 execution plan 与 promote 相关信号
- 向 **Backlog 与正式工作项管理部分** 交付 child WorkItem 正式化入口
- 向 **协作视图与投影部分** 提供可见性控制信息(如 rejected 是否可见)

#### 4.6.8 该部分的状态 / 约束 / 易错点
- work 只持 plan 引用和 promote 回链
- runtime 不得直接把 plan item 写入 Backlog
- child WorkItem 的正式流与 plan 状态回写必须可追踪
- 最容易把 ImplementationPlan 误判为 WorkItem 真相层对象

#### 4.6.9 建议开发顺序

1. **项目主语与成员承担部分**
   - 先把 Project / ProjectMember 的主语层与身份映射层立住,否则后续 WorkItem / Iteration 都没有稳定项目锚点。
2. **Backlog 与正式工作项管理部分**
   - 在主语层稳定后,先实现 Backlog / WorkItem / child WorkItem 真相与 DAG 规则,因为它是整个仓的核心正式事实层。
3. **Iteration 承诺子集管理部分**
   - 当 accepted workitems 已能稳定存在后,再实现 Iteration draft / start / close 才不会把全集与承诺子集写混。
4. **ImplementationPlan / promote 接缝部分**
   - 只有正式工作项管理部分稳定后,才能安全接入 plan item promote,否则很容易让 runtime 越界写真相。
5. **协作视图与投影部分**
   - 最后实现 board / tree / rollup / summary,因为投影层依赖前面四个部分的真相与接缝都已经收稳。

  - **为什么单独存在**: 树形视图需要独立的只读组织方式

- `RollupCalculator`
  - **类型**: calculator
  - **职责**: 根据 child 状态计算父项 rollup 汇总
  - **为什么单独存在**: 汇总计算是派生视图逻辑,不是真相字段直接写入

- **RPC / command 接口**:

- **事件发布 / 订阅**:

  - 典型事件: `work.project.*` / `work.workitem.*` / `work.iteration.*` / `artifact.approved`

### 6.6 关键函数/命令级伪代码

#### 项目主语与成员承担部分

```text
CreateProject:
  1. 校验 process_profile_id 存在且 active
  2. 构造 Project(state = draft)
  3. 持久化 Project
  4. 创建空 Backlog(project_id)
  5. 记录 state_history(created/draft)
  6. 发 work.project.created
  7. 返回 Project

SyncProjectMemberFromIdentity:
  1. 读取 ProjectMember
  2. 根据 GlobalMember lifecycle 映射项目内状态
  3. 若成员 paused / retired，则收缩 assignment state
  4. 发 work.project_member.updated
```

#### Backlog 与正式工作项管理部分

```text
CreateWorkItem:
  1. 校验 project 存在且未 dissolved
  2. 校验 assignee 若存在,其 ProjectMember 必须 active
  3. 构造 WorkItem(planning_status = accepted, state = todo)
  4. 持久化 WorkItem
  5. 追加到 Backlog.ordered_workitems
  6. 发 work.workitem.created

CreateChildWorkItem:
  1. 校验 parent WorkItem 存在且可拆
  2. 构造 child WorkItem(planning_status = proposed)
  3. 校验 parent graph 与 depends_on 不形成环
  4. 若来自 promote,记录 origin_plan_item_id
  5. 持久化 child WorkItem
  6. 发 work.workitem.proposed

AcceptChildWorkItem:
  1. 校验 child 为 proposed
  2. 校验 approver 权限与责任链
  3. 更新 planning_status = accepted
  4. 追加到 Backlog
  5. 若必要,加入 Iteration.planned_workitems
  6. 发 work.workitem.accepted
```

#### Iteration 承诺子集管理部分

```text
DraftIteration:
  1. 校验 selected ids 全部存在于 Backlog
  2. 校验 selected ids 全部为 accepted
  3. 创建 Iteration(state = planned)
  4. 写入 planned_workitems 顺序

StartIteration:
  1. 校验 Iteration.state = planned
  2. 冻结 planned_workitems
  3. 更新 state = in_progress
  4. 发 work.iteration.started

CloseIteration:
  1. 校验 state = in_progress
  2. 统计 actual_completed 与 spillover
  3. 更新 state = closed
  4. 发 work.iteration.closed
```

#### 协作视图与投影部分

```text
BuildBoardProjection:
  1. 读取 accepted workitems 与 iteration membership
  2. 过滤 rejected / draft child items
  3. 按执行状态与迭代归属分组
  4. 输出 BoardProjection
```

#### ImplementationPlan / promote 接缝部分

```text
PromotePlanItemToChildWorkItem:
  1. 读取 WorkItem 与 PlanItemRef
  2. 校验该 PlanItem 满足协作/依赖/排期/验收/风险视野条件
  3. 校验 runtime 不能直接创建 backlog item
  4. 调用 CreateChildWorkItem(origin_plan_item_id = plan_item_id)
  5. 记录 plan ↔ child 回链
  6. 返回 child WorkItem(proposed)
```

### 6.8 关键状态机 / 非法转换与约束

#### 项目主语与成员承担部分

```text
Project.state:
draft -> active -> paused -> archived
   │
   └──────────────────────▶ dissolved

ProjectMember.state:
assigned -> active -> paused -> retired
```

#### Backlog 与正式工作项管理部分

```text
WorkItem.state:
todo -> in_progress -> in_review -> done
  │         │             │
  │         └────────────▶ blocked
  │
  └──────────────────────▶ cancelled

WorkItem.planning_status:
proposed -> accepted
    │
    └-> rejected
```

#### Iteration 承诺子集管理部分

```text
Iteration.state:
planned -> in_progress -> closed
```

#### 非法转换与约束表

| 场景 | 所属主要部分 | 是否允许 | 说明 |
|---|---|---|---|
| `Project.dissolved` 后恢复 | 项目主语与成员承担部分 | ❌ | 生命周期硬边界 |
| `planning_status=rejected` 后直接 `state=in_progress` | Backlog 与正式工作项管理部分 | ❌ | 未 accepted 的 child 不进入正式执行态 |
| `planning_status=accepted` 后再改回 `proposed` | Backlog 与正式工作项管理部分 | ❌ | proposal 是一次性决策流 |
| parent `done` 时仍有 required children 未完成 | Backlog 与正式工作项管理部分 | ❌ | 必须阻断 / defer |
| child WorkItem accepted 前加入 Iteration | Iteration 承诺子集管理部分 | ❌ | 先 accepted 再进入承诺子集 |
| 从 `ImplementationPlan` 直接修改 Backlog 真相 | ImplementationPlan / promote 接缝部分 | ❌ | 必须先 promote 再走正式流程 |

| `work.iteration.started` | Iteration 承诺子集管理部分 | info | `iteration_id + started_at` | iteration_id, planned_workitems |

### 6.11 错误码定义

| 错误码 | 所属主要部分 | 含义 | HTTP / RPC 映射 | 恢复策略 |
|---|---|---|---|---|
| `WORK_PROJECT_DISSOLVED` | 项目主语与成员承担部分 | 项目已解散不可写 | 409 / FAILED_PRECONDITION | 提示新建项目 |
| `WORK_MEMBER_INACTIVE` | 项目主语与成员承担部分 | assignee 当前不可承接工作 | 409 / FAILED_PRECONDITION | 更换成员或等待恢复 |
| `WORK_DEPENDENCY_CYCLE` | Backlog 与正式工作项管理部分 | 依赖成环 | 400 / INVALID_ARGUMENT | 调整依赖后重试 |
| `WORK_CHILD_NOT_APPROVED` | Backlog 与正式工作项管理部分 | child 尚未 accepted | 409 / FAILED_PRECONDITION | 先走 proposal 决策 |
| `WORK_ITERATION_INVALID_SELECTION` | Iteration 承诺子集管理部分 | 迭代选择不合法 | 400 / INVALID_ARGUMENT | 调整 backlog 选择 |
| `WORK_PROMOTE_NOT_ELIGIBLE` | ImplementationPlan / promote 接缝部分 | plan item 不满足升级条件 | 400 / FAILED_PRECONDITION | 保留在 plan |

### 6.12 返回值语义分类

| 类别 | 适用主要部分 | 语义 | 处理建议 |
|---|---|---|---|
| 正常 | 全部部分 | 业务成功 | - |
| 可恢复异常 | Iteration / 投影 / promote 接缝部分 | 重试 / 降级可解 | 实施重试策略 |
| 不可恢复异常 | 项目主语 / 正式工作项管理部分 | 业务失败 | 返回给上游 |

|---|---|---|---|
| 项目主语与成员承担部分 | Project / ProjectMember | `projects` / `project_members` | 保持项目主语与成员承担关系清晰 |
| Backlog 与正式工作项管理部分 | Backlog 顺序 | 单独表 `backlog_items` | 便于 reorder 与 accepted 过滤 |
| Backlog 与正式工作项管理部分 | child WorkItem | 仍存 `work_items` 表,仅 `parent_workitem_id` 不为空 | 保持真相统一 |
| Iteration 承诺子集管理部分 | planned / actual / spillover | `iterations` / `iteration_items` | 保持承诺子集独立建模 |
| 协作视图与投影部分 | Board / tree / rollup | projection tables / 可重建视图 | 只读、最终一致 |
| ImplementationPlan / promote 接缝部分 | Plan ↔ child link | 单独表 `workitem_plan_links` | promote 回链可审计 |

### 7.4 关键校验

- **项目主语与成员承担部分**:
  - `Project.dissolved` 后不得继续创建/变更工作事实
  - assignee 必须引用 active 的 `ProjectMember`
- **Backlog 与正式工作项管理部分**:
  - `parent_workitem_id` 不得形成父子环
  - `depends_on / blocks` 不得形成依赖环
  - `planning_status=accepted` 的 child WorkItem 才能进入 Backlog / Iteration
- **Iteration 承诺子集管理部分**:
  - `iteration_items` 中不得出现 `planning_status!=accepted` 的 workitem
  - `planned_workitems` 在 Start 后默认冻结
- **ImplementationPlan / promote 接缝部分**:
  - `origin_plan_item_id` 若存在,必须可回链到对应 ImplementationPlan
  - promote 必须保留 plan ↔ child 审计链

## 8. 运行期主线场景

### 8.1 场景 A · 创建项目并形成第一个 Backlog

```text
CreateProject
   │
   ▼
项目主语与成员承担部分建立 Project
   │
   ▼
Backlog 与正式工作项管理部分创建空 Backlog
   │
   ▼
Assign / Sync ProjectMember
   │
   ▼
CreateWorkItem
   │
   ▼
协作视图与投影部分更新 board / summary
```

**开发者关注点**:
- 先确保 Project 能独立存在,再创建空 Backlog
- ProjectMember 必须是项目内承担分身,不是 GlobalMember 直写
- 第一个 WorkItem 进入 backlog 后,board 才开始有正式协作数据

### 8.2 场景 B · Sprint Planning 形成 Iteration

```text
Backlog 中已有 accepted workitems
   │
   ▼
process 发 planning timing
   │
   ▼
Iteration 承诺子集管理部分 DraftIteration
   │
   ▼
StartIteration
   │
   ▼
冻结 planned_workitems
   │
   ▼
协作视图与投影部分更新 iteration board
```

**开发者关注点**:
- Sprint Planning 不是 backlog 创建器,只是承诺子集收口器
- 只有 accepted workitems 才允许进入 Iteration
- Start 后必须冻结 planned_workitems

### 8.3 场景 C · plan item 升级为 child WorkItem

```text
runtime 发现 plan item 进入协作视野
   │
   ▼
ImplementationPlan / promote 接缝部分生成 PromoteRequest
   │
   ▼
Backlog 与正式工作项管理部分 CreateChildWorkItem(proposed)
   │
   ▼
approved / accepted
   │
   ▼
进入 Backlog / 视情况加入 Iteration
   │
   ▼
协作视图与投影部分更新 tree / board
```

**开发者关注点**:
- promote 必须走正式 child WorkItem 流程
- plan item 不能直接写成 backlog item
- accepted 前的 child WorkItem 不能进入正式执行面

### 8.4 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| identity lifecycle | `member_service` / subscription | 项目主语与成员承担部分 | 更新 ProjectMember state |
| process planning timing | `iteration_service` / subscription | Iteration 承诺子集管理部分 | Draft / Start Iteration |
| governance gate decision | `project_service` / subscription | 项目主语与成员承担部分 + 正式工作项管理部分 | lifecycle / constraint update |
| artifact approved | `workitem_service` / subscription | Backlog 与正式工作项管理部分 | done criterion 更新 |
| runtime promote request | `promote_service` | ImplementationPlan / promote 接缝部分 | proposed child WorkItem |
| conversation board query | `board_query_service` | 协作视图与投影部分 | 返回只读 projection |

## 11. 异常与补偿设计

### 11.1 重试 / 降级 / 熔断 / 补偿

- **项目主语与成员承担部分**: identity 生命周期延迟时允许延迟同步,但不伪造成员真相
- **Backlog 与正式工作项管理部分**: child proposal 失败时保留 proposed / rejected 审计链,不写入 backlog
- **Iteration 承诺子集管理部分**: planning 选择失败时拒绝 draft,不半写入承诺集合
- **协作视图与投影部分**: board projection 落后时允许只读降级,不影响真相写入
- **ImplementationPlan / promote 接缝部分**: promote 失败优先回退为 execution plan 内部步骤,不污染真相层

### 11.2 高风险跨仓失败模式

| 场景 | 主要落点部分 | 失败点 | 补偿 / 对账 / replay |
|---|---|---|---|
| runtime 发出 promote 信号但 work 拒绝 | ImplementationPlan / promote 接缝部分 | promote 资格不成立 | 回写 plan item 保持 local-only |
| artifact.approved 丢失 | Backlog 与正式工作项管理部分 | done 判据无法成立 | replay artifact 事件 / 对账 |
| governance 未返回批准 | Backlog 与正式工作项管理部分 | child 卡在 proposed | 保持待决,不进入 backlog |
| process planning 事件重复 | Iteration 承诺子集管理部分 | 重复 draft/start | 幂等校验 + 丢弃重复事件 |

### 11.3 按主要部分归属的失败模式

> 本节应能回收到第 4 节各主要部分和第 6 节关键流程里已经出现过的失败点。它的作用是把这些失败模式系统化汇总,而不是重新发明一套和正文脱节的异常集合。

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 项目主语与成员承担部分 | kickoff 未通过仍启动 | lifecycle transition | 阻断 active | replay gate decision |
| 项目主语与成员承担部分 | identity 状态滞后 | assignment sync | 延迟更新 / 只读告警 | replay member event |
| Backlog 与正式工作项管理部分 | plan item 越界升级 | promote eligibility check | 拒绝升级 | 回写 plan |
| Backlog 与正式工作项管理部分 | dependency 写入成环 | dependency validation | 拒绝写入 | 调整依赖重试 |
| Iteration 承诺子集管理部分 | 未 accepted item 混入 | DraftIteration validate | 拒绝 draft | 重新选择 |
| 协作视图与投影部分 | rejected item 出现在主板 | projection filter | 重建投影 | rebuild projection |
| ImplementationPlan / promote 接缝部分 | rejected 后无法回链原 plan | plan link audit | 标记 inconsistent | replay link repair |

## 12. 实现红线 / 开发禁止事项

- 不要把 `PlanItem` 直接写入 Backlog; 必须先经过 promote 正式入口
- 不要让 projection / board / summary 反写真相层
- 不要让 `process` 成为 Backlog 的写源; 它只提供节奏与时机
- 不要把 `artifact` 正文并入 `work` 真相层; `work` 只保存引用和判据
- 不要把 `GlobalMember` 逻辑下沉到 `work`; `work` 只维护 `ProjectMember`
- 不要绕过 accepted / rejected 正式流直接推进 child WorkItem

## 14. 最小可运行闭环

第一版最少应打通以下闭环,系统就能形成可运行的 `L1-work` 主干:

1. **项目主语与成员承担部分**
   - CreateProject
   - SyncProjectMemberFromIdentity
2. **Backlog 与正式工作项管理部分**
   - CreateWorkItem
   - CreateChildWorkItem(proposed)
3. **Iteration 承诺子集管理部分**
   - DraftIteration
   - StartIteration
4. **协作视图与投影部分**
   - BuildBoardProjection
   - GetProjectBoard
5. **ImplementationPlan / promote 接缝部分**
   - PromotePlanItemToChildWorkItem 的最小正式入口
6. **证据联动**
   - artifact.approved → work done criterion 最小回链

> 只要这 6 条最小闭环打通,开发者就已经能验证: 项目能创建、工作项能进入 Backlog、Iteration 能收口、board 能展示、promote 能进入正式 child WorkItem 流程、done 判据能受证据驱动。

## 15. 结论

本详细设计的核心结论是:
- `L1-work` 的实现结构应按 5 个主要部分组织,而不是按对象顺排
- 项目主语与成员承担部分负责项目身份与承担关系锚点
- Backlog 与正式工作项管理部分负责正式协作事实与 child WorkItem 流程
- Iteration 承诺子集管理部分负责时间窗口内的正式承诺集合
- 协作视图与投影部分只负责展示与只读消费,不反写真相
- ImplementationPlan / promote 接缝部分只负责 execution plan 的正式接入与升级边界,不把 plan 本身并入真相层
- 后续测试与验收文档,也应围绕这 5 个主要部分建立映射关系

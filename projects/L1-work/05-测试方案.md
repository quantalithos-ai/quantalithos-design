### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 API 可调用,而是系统验证 `L1-work` 是否真正满足“项目工作事实真相层”的设计要求,尤其要证明以下几点成立:
- Project / ProjectMember / Backlog / WorkItem / child WorkItem / Iteration 的正式事实边界成立
- Sprint Planning 只做节奏与选择,不创建 Backlog 真相
- `ImplementationPlan` 只作为执行计划接缝存在,不会被误判为 WorkItem 真相对象
- child WorkItem 的 proposal / accepted / rejected 流程完整成立
- `plan item → child WorkItem` 的 promote 路径可追溯且不污染 Backlog
- 协作投影(board / tree / rollup / summary)只读且不反写真相
- artifact done criterion 与 approved evidence 关联成立

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| Project / ProjectMember 真相层 | 真相对象 | P0 | 项目主语、成员承担关系与生命周期收缩 |
| Backlog / WorkItem / child WorkItem | 真相对象 | P0 | 正式协作事实与 proposal 流 |
| Iteration | 真相对象 | P0 | 承诺子集形成、冻结、关闭 |
| promote 接缝 | 接缝逻辑 | P0 | `ImplementationPlan` 升级为 child WorkItem 的正式路径 |
| board / tree / rollup 投影 | 读模型 | P0 | 只读展示、一致性与过滤规则 |
| artifact done criterion | 跨仓接缝 | P0 | approved evidence 与完成判据联动 |
| process planning timing 联动 | 跨仓接缝 | P1 | 验证 planning 只提供时机,不写真相 |
| UI 视觉细节 | 非范围 | P2 | 本文不覆盖前端像素级视觉验收 |
| Runtime 执行正文 | 非范围 | P2 | 只验证 promote 接缝,不验证 runtime 内部执行细节 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数和规则不变量 | domain / policy owner | `Project::activate`、`WorkItem::accept/reject`、`Iteration::start/close`、`PromotePolicy` | 状态与不变量符合设计 |
| 集成测试 | 验证 service + repo + outbox + projection 联动 | backend / domain owner | CreateProject、CreateWorkItem、CreateChildWorkItem、AcceptChildWorkItem、DraftIteration、artifact.approved | 真相写入、事件发布、投影刷新都成立 |
| 事件链测试 | 验证跨仓事件消费与输出 | integration / platform owner | process planning timing、artifact.approved、runtime promote request | 输入事件被正确消费,输出语义正确 |
| 恢复/边界专项测试 | 验证非法转换、依赖环、投影只读、promote 越界 | architecture / QA | dependency cycle、rejected 误入主板、plan item 直入 backlog | 设计红线不被突破 |
| 端到端主线测试 | 验证最小可运行闭环 | QA / owner | CreateProject → Backlog → Iteration → board → artifact done → promote | 主干场景完整跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| Backlog 是待办全集且可为空池 | 项目创建后生成空 Backlog | 集成测试 | 是 | DB / API 响应 |
| Sprint Planning 不创建 Backlog 真相 | planning timing 只选择 accepted items | 事件链测试 + 集成测试 | 是 | timing event / iteration membership |
| child WorkItem 是正式协作事实 | proposal → accepted / rejected → backlog | 集成测试 | 是 | 状态流 / event / repo |
| `ImplementationPlan` 不是 WorkItem 真相 | plan item 不得直接入 backlog | 边界专项测试 | 是 | promote rejection / audit |
| promote 必须可追溯 | child WorkItem 与 plan item 双向回链 | 集成测试 | 是 | plan link / workitem refs |
| board / tree / summary 只读 | projection 不反写真相 | 投影专项测试 | 是 | query trace / no write side effect |
| done 判据依赖 approved evidence | artifact.approved 驱动状态变化 | 事件链测试 | 是 | event / workitem state / refs |

## 6. 核心测试场景

| 场景 ID | 场景 | 前置条件 | 步骤摘要 | 预期结果 |
|---|---|---|---|---|
| TC-001 | 创建项目后生成空 Backlog | 无 | CreateProject → 查询 backlog | backlog 已存在且为空 |
| TC-002 | 创建顶层 WorkItem | active Project / active assignee | CreateWorkItem | workitem = accepted + todo,并进入 backlog |
| TC-003 | child WorkItem proposal 后 rejected | parent 已存在 | CreateChildWorkItem → RejectChildWorkItem | child 不进入 backlog / iteration,保留审计链 |
| TC-004 | child WorkItem accepted 后进入 backlog | proposal 已存在 | AcceptChildWorkItem | planning_status=accepted,追加到 backlog |
| TC-005 | 只有 accepted workitems 进入 Iteration | backlog 已有 accepted/proposed items | DraftIteration / StartIteration | 仅 accepted items 被承诺 |
| TC-006 | Iteration 启动后冻结承诺集合 | draft iteration 已存在 | StartIteration | planned_workitems 冻结 |
| TC-007 | promote 只在协作条件成立时成功 | runtime 提出 promote 请求 | PromotePlanItemToChildWorkItem | child(proposed) 创建 + plan 回链 |
| TC-008 | promote 越界被阻断 | plan item 只是个人步骤 | PromotePlanItemToChildWorkItem | 返回 `WORK_PROMOTE_NOT_ELIGIBLE` |
| TC-009 | artifact.approved 驱动 done criterion | workitem 已存在 | 消费 artifact.approved | workitem 更新 evidence / done 可达 |
| TC-010 | rejected child 不进入主 Board | rejected child 已存在 | GetProjectBoard | rejected child 不出现在主协作板 |

> 若本系统涉及 Backlog / WorkItem / child WorkItem / ImplementationPlan,应至少覆盖:
> - Backlog 为空池时的初始化与 planning 选择路径
> - child WorkItem 提案 / accepted / rejected / 进入 Backlog / Iteration
> - ImplementationPlan 只作为执行计划,不被误判为 WorkItem 真相
> - PlanItem promote 为 child WorkItem 的升级路径与审计证据

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|
| S | 真相层混层 / promote 越界 / done 判据失效 | 阻断放行,必须修复 |
| A | 关键主线通过但投影错误 / 审计链不完整 | 原则上修复后再放行 |
| B | 非关键视图或辅助场景异常 | 可带风险进入下一轮 |

---

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 WorkItem / Iteration / promote / artifact done 相关逻辑,都必须回归最小可运行闭环
- 每次改动 projection 逻辑,都必须回归 board/tree/rollup 一致性和只读门禁

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| `ImplementationPlan` artifact kind 归属后续可能微调 | promote 测试矩阵需跟着调整 | TL / 架构 |
| process timing 与 work planning 边界仍可能在后续实现细化时再收口 | 部分集成测试需迭代更新 | Owner / TL |

## 3. SOP 问题回答

### 3.1 本仓有哪些主要角色？

`L1-work` 的主要角色分为三类：

1. 人类角色：项目发起 / 管理者、项目协调 / 技术负责人、项目成员 / 执行者、审计 / 观察者。
2. 系统角色：内部系统调用方、运维 / 后台任务。
3. 不作为本章角色的相邻仓：identity、conversation、method-library、process、governance、artifact、runtime、workspace 等，它们在 Step 6 使用方与依赖中讨论。

### 3.2 哪些是人类角色，哪些是系统角色？

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 项目发起 / 管理者 | 人类角色 | 发起项目、维护项目基本工作事实、组织 Backlog 和 Iteration 的管理语境 |
| 项目协调 / 技术负责人 | 人类角色 | 协调正式工作项、拆分协作级 child WorkItem、处理优先级、阻塞、承担关系和工作边界 |
| 项目成员 / 执行者 | 人类或 AI 成员角色 | 作为 ProjectMember 承担正式 WorkItem，围绕当前工作事实查看、更新和提出升级需求 |
| 审计 / 观察者 | 人类角色 | 查看项目工作事实、任务演进、成员承担、迭代承诺和完成依据的历史轨迹 |
| 内部系统调用方 | 系统角色 | 平台内部系统以受控方式消费或提交项目工作事实相关变化 |
| 运维 / 后台任务 | 系统角色 | 执行重建、对账、归档准备、报告生成或维护类动作时接触项目工作事实 |

### 3.3 这些角色分别在什么场景下接触本仓？

| 角色 | 典型接触场景 | 本步边界 |
|---|---|---|
| 项目发起 / 管理者 | 项目从想法进入正式管理语境，项目工作事实需要被组织、维护和审计 | 不写创建项目接口、不写启动流程细节 |
| 项目协调 / 技术负责人 | 正式工作项需要拆分、排序、协调承担关系或处理阻塞 | 不写 WorkItem 状态机、不写具体规则 |
| 项目成员 / 执行者 | 成员需要知道自己在项目内承担的正式工作，并区分正式任务与个人执行步骤 | 不写用户故事、不写 runtime 执行细节 |
| 审计 / 观察者 | 需要复盘项目里哪些工作正式存在、由谁承担、何时进入承诺范围、为何完成 | 不写审计查询接口、不写证据 schema |
| 内部系统调用方 | 其他内部系统围绕项目工作事实进行受控消费或协作 | 具体仓际依赖后移 Step 6 |
| 运维 / 后台任务 | 维护项目工作事实的派生视图、报告或一致性状态 | 不写 job 列表或实现机制 |

### 3.4 是否存在管理、审计或维护类角色？

存在：

- 管理类角色：项目发起 / 管理者、项目协调 / 技术负责人。
- 审计类角色：审计 / 观察者。
- 维护类角色：运维 / 后台任务。

这些角色只用于需求层场景分类，不在本步展开具体权限、接口、后台任务或报告格式。

### 3.5 是否需要进一步补权限矩阵？

需要轻量权限差异矩阵。原因是 `L1-work` 涉及项目管理、任务承担、协作拆分、审计和维护，不同角色的接触方式差异明显。但矩阵必须保持能力级粒度，不写 API、Command、事件名或状态机。

| 操作类型 | 项目发起 / 管理者 | 项目协调 / 技术负责人 | 项目成员 / 执行者 | 审计 / 观察者 | 内部系统调用方 | 运维 / 后台任务 |
|---|---|---|---|---|---|---|
| 维护项目工作事实 | 是 | 受限 | 受限 | 只读 | 受控 | 按任务 |
| 协调正式工作项 | 是 | 是 | 受限 | 只读 | 受控 | 否 |
| 提出执行步骤升级 | 可参与 | 可参与 | 是 | 否 | 受控 | 否 |
| 查看项目工作轨迹 | 是 | 是 | 受限 | 是 | 受控 | 是 |
| 执行维护类动作 | 否 | 否 | 否 | 否 | 受控 | 是 |

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 角色分类 | 用户类型、系统仓和依赖混写 | 人类角色 / 系统角色 / 相邻仓依赖分开 | 对齐 SOP，避免把依赖写成角色 |
| 人类角色 | Owner / PM、ProjectMember、Tech Lead、Auditor 分散在不同章节 | 项目发起 / 管理者、项目协调 / 技术负责人、项目成员 / 执行者、审计 / 观察者 | 更贴合需求层场景 |
| 系统角色 | “系统”泛称或 Governance / Process / Artifact | 内部系统调用方、运维 / 后台任务 | 既保留系统接触场景，又不把具体仓际依赖提前展开 |
| 权限矩阵 | 操作较具体，混入 gate、tool_scope、dissolved | 能力级权限差异 | 避免滑入功能、规则和接口 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 沿用旧角色表 | 保留旧内容，速度快 | 把 Governance / Process / Artifact 写成用户角色，违反 Step 5 粒度 | 不采用 |
| 方案 B: 按人类角色、系统角色、相邻仓依赖分开 | 角色清楚，能为 Step 6 留出依赖边界 | 需要后续 Step 6 再展开仓际关系 | 采用 |
| 方案 C: 只写人类角色，不写系统角色 | 简洁 | 忽略内部系统调用方和维护任务接触 Work 的需求场景 | 不采用 |
| 方案 D: 直接写完整权限矩阵 | 看似完整 | 会提前进入功能、规则和授权设计 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把 Governance / Process / Artifact 写成系统角色？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 写成系统角色 | Step 5 与 Step 6 混杂，后续依赖裁剪重复 |
| 方案 B | 不写成角色，后移 Step 6 使用方与依赖 | 角色章节更干净，依赖章节可按全局基线裁剪 |

推荐方案 B。原因是这些是仓际协作方，不是“以什么身份接触本仓”的角色定义。

#### 是否保留 Tech Lead 作为独立人类角色？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 合并到项目管理者 | 简化角色表，但会弱化技术协调、拆分和边界处理场景 |
| 方案 B | 保留为项目协调 / 技术负责人 | 能表达 WorkItem 拆分、阻塞和 promote 相关场景 |

推荐方案 B。原因是 `L1-work` 的 child WorkItem / ImplementationPlan promote 边界需要一个项目内技术协调语境。

#### 是否在 Step 5 写权限矩阵？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 不写权限矩阵 | 简短，但角色差异不够明确 |
| 方案 B | 写轻量能力级权限差异矩阵 | 能约束后续用户故事和功能需求，不滑入接口 |

推荐方案 B。原因是 Work 涉及管理、协调、执行、审计和维护，角色差异明显。

## 7. 结构化中间产物

### 7.1 角色结论

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 项目发起 / 管理者 | 人类角色 | 发起项目、维护项目基本工作事实、组织 Backlog 和 Iteration 的管理语境 |
| 项目协调 / 技术负责人 | 人类角色 | 协调正式工作项、拆分协作级 child WorkItem、处理优先级、阻塞、承担关系和工作边界 |

### 7.2 系统角色结论

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 内部系统调用方 | 系统角色 | 平台内部系统以受控方式消费或提交项目工作事实相关变化 |
| 运维 / 后台任务 | 系统角色 | 执行重建、对账、归档准备、报告生成或维护类动作时接触项目工作事实 |

### 7.3 使用场景结论

| 角色 | 场景结论 |
|---|---|
| 项目发起 / 管理者 | 关心项目是否进入正式工作管理语境，以及项目事实是否可组织和复盘 |
| 项目协调 / 技术负责人 | 关心正式工作项如何拆分、排序、协调和避免被个人步骤污染 |
| 项目成员 / 执行者 | 关心自己作为 ProjectMember 承担哪些正式工作，以及执行步骤何时需要升级 |
| 审计 / 观察者 | 关心项目工作事实能否解释责任、承诺、变更和完成依据 |
| 内部系统调用方 | 关心能否以受控方式消费或提交项目工作事实变化 |
| 运维 / 后台任务 | 关心维护动作能否在不改变业务真相的前提下处理派生和一致性问题 |

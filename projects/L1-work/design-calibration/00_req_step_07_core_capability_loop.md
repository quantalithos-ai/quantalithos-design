## 3. SOP 问题回答

### 3.1 如果没有这个仓，系统会缺什么不可替代的能力或结构？

如果没有 `L1-work`，平台会缺少统一的项目工作事实结构。项目会退化成对话主题、流程实例、执行计划、产物证据或工作台视图里的局部信息，系统无法稳定回答：

- 这个软件项目是否已经成为正式工作对象。
- 哪些成员在项目内承担工作。
- 哪些工作是正式协作任务，哪些只是个人执行步骤或对话建议。
- 哪些工作进入当前承诺范围。
- 相邻仓消费的是哪一份项目事实。

### 3.2 这个仓成立必须共同具备哪些能力？

`L1-work` 的核心能力闭环不是功能列表，而是一组必须共同成立的项目工作事实能力：

1. 项目主语能够作为正式工作对象成立。
2. 项目内成员承担关系能够成立。
3. 正式工作全集能够成立，并能区分协作任务、子任务和执行步骤。
4. 承诺子集能够从正式工作全集中成立。
5. 项目工作事实能够被持续消费和追溯。

### 3.3 哪些能力缺一个，这个仓就不算真正成立？

| 能力 | 缺失后果 |
|---|---|
| 项目主语成立 | Work 失去项目事实锚点，WorkItem、Iteration 和 ProjectMember 都没有稳定归属 |
| 项目内承担成立 | Work 无法表达谁在项目内承担工作，GlobalMember / ProjectMember 边界会失效 |
| 正式工作全集成立 | Backlog、WorkItem、child WorkItem 和 plan item 会混淆，正式任务边界失真 |
| 承诺子集成立 | 项目无法表达当前时间窗口内承诺完成的工作范围 |
| 可消费可追溯成立 | 相邻仓和产品入口会各自解释项目状态，项目事实无法成为跨仓锚点 |

### 3.4 哪些能力只是外围增强，而不是闭环核心？

| 外围增强能力 | 为什么不是闭环核心 |
|---|---|
| 高级看板 / 多视图展示 | 依赖项目工作事实，但属于展示和聚合增强 |
| 复杂容量规划和性能指标 | 重要，但属于非功能和规模阶段 |
| 高级 tool_scope / policy override 管理 | 与项目成员承担相关，但依赖治理和方法定义进一步收敛 |
| 自动解除阻塞 / 自动 spillover | 可减少人工维护，但不决定项目工作事实是否成立 |
| 跨项目依赖和多 owner | 是后续增强，不阻塞单项目工作事实闭环 |
| 完整归档恢复和观测报表 | 重要但属于 archive / observability 协作增强 |

### 3.5 哪些能力根本不属于这个仓？

| 边界外能力 | 归属原因 |
|---|---|
| 平台级成员身份管理 | 属于 `L1-identity` |
| 对话事实和聊天呈现 | 属于 `L1-conversation` 或上层产品入口 |
| 方法定义和视图策略 | 属于 `L3-method-library` |
| 流程执行和 Activity 状态 | 属于 `L1-process` |
| Gate / Policy / Approval 决策 | 属于 `L1-governance` |
| Artifact / evidence / baseline 正文 | 属于 `L1-artifact` |
| agent loop、工具调用和执行计划推进 | 属于 `L2-runtime` |
| PersonalWorkspace / ProjectWorkspace 聚合视图 | 属于 `L1-workspace` |

### 3.6 当前已有或预期功能中，哪些是在支撑这些核心能力？

| 旧功能 / 用例线索 | 支撑的核心能力节点 | 处理口径 |
|---|---|---|
| 用户立项并启动 Project | 项目主语成立 | 保留为后续故事和功能线索，不在本步写接口 |
| 分配 ProjectMember | 项目内承担成立 | 保留，但 GlobalMember 真相不归 Work |
| Backlog 管理 / WorkItem 管理 | 正式工作全集成立 | 保留，后续按能力而不是 CRUD 展开 |
| WorkItem 依赖 DAG | 正式工作全集成立 | 属于工作事实规则，后移 Step 10 展开 |
| child WorkItem / promote | 正式工作全集成立 | 是区分协作任务和执行步骤的关键边界 |
| 创建 Iteration / 拉入 Sprint | 承诺子集成立 | 保留为承诺子集能力线索 |
| GetProjectBoard / 看板 | 可消费可追溯成立或外围增强 | 基础消费能力进入闭环，高级看板作为外围增强 |
| artifact 关联 / done 判据 | 可消费可追溯成立或规则增强 | 后移规则、数据和验收章节展开 |
| process / governance / runtime 联动 | 可消费可追溯成立或外围协作 | 后续依赖、接口、测试中展开，不进入闭环图细节 |

## 4. 核心能力闭环结论

### 4.1 闭环定义

`L1-work` 的核心能力闭环是：项目必须先作为正式工作对象成立，再能表达项目内成员承担关系；成员承担关系稳定后，正式工作全集才能被组织、拆分和区分执行步骤；正式工作全集稳定后，当前承诺子集才能成立；这些项目工作事实最终必须能被持续消费和追溯。只要其中任何一环缺失，Work 仓就会退化成普通任务列表、流程附属物、对话投影或执行计划存放处。

### 4.2 核心能力闭环图

```text
项目主语能够作为正式工作对象成立
  -> 项目内成员承担关系能够成立
  -> 正式工作全集能够被组织并区分执行步骤
  -> 当前承诺子集能够从正式工作全集中成立
  -> 项目工作事实能够被持续消费和追溯
```

本图只表达能力成立的逻辑依赖关系，不表达运行时调用顺序、接口时序、事件传播顺序、开发实施步骤或对象字段。

### 4.3 能力层级划分表

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | 项目主语成立；项目内成员承担成立；正式工作全集成立；承诺子集成立；项目工作事实可消费可追溯 |
| 外围增强能力 | 高级看板 / 多视图展示；复杂容量规划；高级 tool_scope / policy override；自动解除阻塞；跨项目依赖；完整归档恢复；观测报表 |
| 边界外能力 | 平台级成员身份；对话事实；方法定义；流程执行；治理决策；产物正文；runtime 执行推进；workspace 聚合视图 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 把旧 F-001~F-012 功能清单当闭环 | 快，覆盖面多 | 是功能列表，不是能力成立结构 | 不采用 |
| 方案 B: 以项目工作事实成立过程定义闭环 | 对齐仓存在必要性，能约束后续故事和功能 | 需要后续 Step 9 再细化功能 | 采用 |
| 方案 C: 以跨仓事件协作定义闭环 | 能体现依赖关系 | 会把事件链和依赖链误写成能力闭环 | 不采用 |
| 方案 D: 把 runtime promote 作为单独闭环节点 | 强调当前重要边界 | 会让 runtime 执行看起来进入核心闭环；更适合放在正式工作全集节点中 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把高级看板放入核心闭环？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 放入核心闭环 | 闭环会偏向 UI / workspace 展示 |
| 方案 B | 基础消费与追溯进入闭环，高级看板作为外围增强 | 保护 Work 真相边界 |

推荐方案 B。原因是 Work 必须可消费可追溯，但高级看板展示不是 Work 成立的必要条件。

#### 是否把 done 判据放入核心闭环图？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 放入图中作为单独节点 | 图会混入规则和 artifact 协作 |
| 方案 B | 放入“可消费可追溯”与后续规则 / 验收映射，不进闭环图 | 保持闭环图能力层级干净 |

推荐方案 B。原因是 done 判据是重要规则和验收方向，但不是能力闭环图的独立节点。

#### 是否把 ImplementationPlan promote 作为单独核心节点？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 单独列为核心节点 | 容易误导 Work 拥有 runtime 执行推进 |
| 方案 B | 放入“正式工作全集能够被组织并区分执行步骤”节点 | 能守住边界且不越界 |

推荐方案 B。原因是 promote 的价值在于保护正式工作事实边界，而不是让 Work 成为执行计划仓。

`L1-work` 不可替代的能力是统一项目工作事实。没有它，项目会散落为对话、流程、执行计划、产物证据和视图中的局部信息，平台无法稳定表达项目主语、项目内成员承担、正式工作全集、当前承诺子集和跨仓可追溯事实。

## 3. SOP 问题回答

### 3.1 哪些角色目标在支撑本仓的核心能力闭环？

支撑核心闭环的故事必须围绕项目工作事实成立，而不是围绕 UI、接口或相邻仓动作成立：

| 闭环节点 | 支撑它的角色目标 |
|---|---|
| C-1 项目主语成立 | 项目发起 / 管理者需要把软件项目放入正式工作管理语境；内部系统调用方需要稳定引用项目工作事实 |
| C-2 项目内成员承担成立 | 项目发起 / 管理者和项目协调 / 技术负责人需要把 GlobalMember 的项目内承担关系表达清楚；项目成员 / 执行者需要知道自己在项目内承担什么 |
| C-3 正式工作全集成立 | 项目协调 / 技术负责人需要区分正式协作任务、child WorkItem 和个人执行步骤；项目成员 / 执行者需要在执行步骤跨入协作边界时提出升级 |
| C-4 承诺子集成立 | 项目发起 / 管理者和项目协调 / 技术负责人需要从正式工作全集中形成当前 Iteration 承诺范围；项目成员 / 执行者需要理解当前承诺工作 |
| C-5 可消费可追溯成立 | 审计 / 观察者、内部系统调用方和运维 / 后台任务需要围绕项目工作事实进行追溯、消费、重建和对账 |

### 3.2 哪些角色目标只是外围增强，而不决定闭环是否成立？

外围增强故事可以保留为后续能力线索，但不能压过核心闭环：

| 外围增强目标 | 角色 | 原因 |
|---|---|---|
| 更丰富的看板、多维过滤和展示偏好 | 项目成员 / 执行者、项目协调 / 技术负责人 | 依赖 Work 事实，但属于消费展示增强 |
| 自动解除阻塞、自动 spillover 提示 | 项目协调 / 技术负责人 | 可降低维护成本，但人工维护不影响核心事实成立 |
| 容量规划和负载均衡建议 | 项目发起 / 管理者、项目协调 / 技术负责人 | 属于高级管理分析，不是项目工作事实成立条件 |
| 高级 tool_scope / policy override 协同 | 项目协调 / 技术负责人 | 与 ProjectMember 相关，但需要 governance / method-library 进一步约束 |
| 跨项目依赖和组合项目视图 | 项目发起 / 管理者 | 属于多项目增强，不阻塞单项目事实闭环 |

### 3.3 哪些看起来像故事，但其实不应进入本仓？

| 看似故事 | 不进入原因 | 正确归属 |
|---|---|---|
| 作为管理员，我希望创建 GlobalMember，以便成员可以进入平台 | 平台级身份真相不是 Work | `L1-identity` |
| 作为用户，我希望在聊天中发送项目消息，以便讨论工作 | 对话事实和聊天呈现不是 Work | `L1-conversation` / 产品入口 |
| 作为流程引擎，我希望推进 Activity，以便执行流程模板 | Activity 执行真相不是 Work | `L1-process` |
| 作为审批人，我希望批准高风险工作，以便通过 Gate | Gate / Approval 决策真相不是 Work | `L1-governance` |
| 作为执行器，我希望推进计划步骤，以便完成任务 | agent loop 和 plan item progress 不是 Work | `L2-runtime` |
| 作为用户，我希望上传 Artifact 正文，以便保存交付物 | Artifact 正文和 evidence 正文不是 Work | `L1-artifact` |
| 作为工作台用户，我希望查看跨域聚合 dashboard，以便总览项目 | 聚合视图不是 Work 真相 | `L1-workspace` |

### 3.4 每条故事分别支撑闭环中的哪个能力节点？

每条正式故事必须能映射到 C-1~C-5 或明确标记为外围增强。故事不直接映射到接口、事件、数据库对象或 implementation phase。

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 故事组织方式 | 按旧用例 / 功能动作排列 | 按核心闭环 C-1~C-5 与外围增强排列 | 保证故事服务仓存在必要性 |
| 故事粒度 | 出现接口名、状态名和 Given / When / Then 验收句 | 使用“作为角色，我希望目标，以便价值”的目标级句式 | 避免提前进入接口、规则和测试 |
| 边界处理 | Governance / Process / Artifact 等容易作为故事主体出现 | 边界外故事单独列为错误示例 | 避免把相邻仓真相写进 Work |
| promote 处理 | 容易写成 runtime 执行计划管理故事 | 写成执行步骤进入协作边界时的升级诉求 | 保留 Work 的 promote 边界，不越界到 runtime |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 沿用旧 US-001~US-005 | 快，已有验收句式 | 含接口名、功能名和外围增强，无法支撑最新闭环 | 不采用 |
| 方案 B: 按核心能力闭环重写故事 | 故事能直接支撑 Step 9 功能归并和 Step 16 追溯 | 需要后续再补功能、规则和验收 | 采用 |
| 方案 C: 按角色分别列大量故事 | 角色覆盖完整 | 容易变成普通故事清单，核心闭环被稀释 | 不采用 |
| 方案 D: 只写核心故事，不写外围增强 | 文档干净 | 会丢失旧文档中有价值但非核心的增强线索 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否保留“自动解除 blocked”故事？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 作为核心故事 | 会把自动化维护能力误写成 Work 成立条件 |
| 方案 B | 作为外围增强故事 | 保留线索，同时不加重核心闭环 |

推荐方案 B。原因是阻塞关系和依赖规则重要，但自动解除属于增强，不是核心事实闭环成立条件。

#### 是否把 tool_scope / policy override 写入核心故事？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 作为 ProjectMember 核心故事 | 容易把 governance / method-library 约束提前写进 Work |
| 方案 B | 作为外围增强故事 | 保留项目成员权限扩展线索，后续再与 governance / method-library 对齐 |

推荐方案 B。原因是 ProjectMember 承担关系是核心，复杂授权调整不是核心闭环条件。

#### 是否把 “GetProjectBoard” 保留为用户故事？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 原样写入 | 这是功能 / 接口名，不是目标级故事 |
| 方案 B | 改写为“成员希望理解当前正式工作事实和承诺范围” | 能支撑可消费可追溯闭环，不提前绑定接口 |

推荐方案 B。原因是需求阶段应描述消费目标，而不是固定查询接口名。

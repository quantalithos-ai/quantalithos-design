## 3. SOP 问题回答

### 3.1 这个仓必须满足哪些性能要求？

性能要求集中在 Work 真相写入、读取消费和 Iteration / promote 主线不成为协作主链阻塞点：

| 性能关注点 | 判断口径 |
|---|---|
| 项目工作事实变更 | 建立 Project、ProjectMember、WorkItem、child WorkItem、Iteration 等核心变化不应成为协作主链瓶颈 |
| 项目工作事实读取 | 成员和相邻仓读取项目工作状态不应因高级展示或投影滞后而阻断核心消费 |
| Iteration 选择路径 | 承诺子集形成不应拖垮正式工作全集的主写路径 |
| promote 边界 | plan item promote 判断不应迫使 Work 拉取或保存完整执行计划正文 |

旧文档中的 `CreateWorkItem P95 < 100ms`、`GetProjectBoard P95 < 300ms`、`10w 项目 x 50 WorkItem` 当前只能作为后续架构 / 测试阶段的候选目标或容量假设，不在需求 Step 13 直接定为已验证硬指标。

### 3.2 这个仓必须满足哪些可用性要求？

| 可用性关注点 | 判断口径 |
|---|---|
| 核心闭环可用 | 外围增强能力失效时，项目主语、成员承担、正式工作全集、承诺子集和追溯能力仍应成立 |
| 外部依赖降级 | identity、process、governance、artifact、runtime 等外部输入延迟时，不得篡改 Work 真相边界 |
| 读写分离口径 | 看板、投影或消费视图延迟时，不得影响 Work 真相写入和审计 |
| 维护任务降级 | 对账、报告或重建失败时，不得隐式修改业务真相 |

### 3.3 这个仓必须满足哪些安全要求？

| 安全关注点 | 判断口径 |
|---|---|
| 正文边界 | Work 不得保存 identity、conversation、method-library、process、governance、artifact、runtime、workspace 的正文 |
| 授权边界 | 查询和变更必须遵守项目内成员承担、可见性和治理结论边界 |
| 高风险变化 | 高风险项目终止、归档、恢复、风险拆分、promote 或工具能力调整不得绕过治理或方法定义约束 |
| 相邻仓边界 | Work 不得通过接口、快照或维护任务接管相邻仓真相 |

### 3.4 这个仓必须满足哪些审计 / 可追溯要求？

| 审计 / 可追溯关注点 | 判断口径 |
|---|---|
| 项目主语和成员承担 | Project、ProjectMember 的关键变化必须可追溯 |
| 正式工作全集 | WorkItem、child WorkItem、依赖、阻塞、完成和取消等关键变化必须可解释 |
| Iteration 承诺 | 工作进入或离开承诺子集必须可追溯 |
| promote 链路 | plan item promote 为 child WorkItem 必须能追溯来源、理由和结果 |
| 完成依据 | WorkItem 完成必须能追溯到外部依据引用，但不保存正文 |
| 维护对账 | 对账、重建和报告必须能解释来源、范围和结果 |

### 3.5 这个仓必须满足哪些幂等 / 一致性要求？

| 幂等 / 一致性关注点 | 判断口径 |
|---|---|
| 单一正式语义 | Project、ProjectMember、Backlog、WorkItem、child WorkItem、Iteration 不得在需求层出现多真相 |
| 重复变更 | 重复提交同一正式变化不得产生重复项目工作事实 |
| 外部输入一致性 | 外部快照和引用滞后时，不得让 Work 生成相互矛盾的正式事实 |
| 投影一致性 | 消费视图可滞后，但必须能解释其来源和滞后状态 |
| 依赖关系一致性 | 工作依赖、阻塞和解除依据必须保持可解释，不得形成不可解释的关系循环或孤儿关系 |

### 3.6 这个仓必须满足哪些可观测性要求？

| 可观测性关注点 | 判断口径 |
|---|---|
| 核心变化可观察 | Project、ProjectMember、WorkItem、child WorkItem、Iteration、promote 的关键变化必须能被平台观察 |
| 边界异常可观察 | 外部正文试图进入 Work、runtime 越界写 Backlog、process 越界写任务等异常必须可发现 |
| 依赖延迟可观察 | identity、process、governance、artifact、runtime 等外部输入延迟或缺失必须可识别 |
| 维护状态可观察 | 对账、重建、报告和投影滞后必须有可判断状态 |

### 3.7 哪些要求能量化，哪些只能给出判断口径？

| 类型 | 当前口径 |
|---|---|
| 可候选量化 | WorkItem 写路径、核心查询路径、看板消费路径、Iteration 选择路径、投影滞后窗口、对账完成时间 |
| 当前只给判断口径 | 正文边界、安全越界、promote 可追溯、依赖延迟降级、读模型不成为写源 |
| 不在本步定死 | 旧 `100ms / 300ms / 500w` 指标，后续测试与容量阶段验证后再决定是否成为正式目标 |

| 项 | 改动前 | 改动后 | 原因 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 原样保留旧 P95 / SLA / 500w 指标 | 看起来可量化 | 当前缺稳定来源，容易误导实施和验收 | 不采用 |
| 方案 B: 写判断口径，旧指标作为候选目标 | 保留量化线索，同时避免伪量化 | 后续测试阶段还需验证具体值 | 采用 |
| 方案 C: 只写六类口号 | 简短 | 不可验收 | 不采用 |
| 方案 D: 写实现层 SLO / 监控配置 | 接近落地 | 超出需求层 | 不采用 |

### 6.1 待确认问题的方案选择

#### 是否把 `CreateWorkItem P95 < 100ms` 定为正式需求？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 直接定为正式需求 | 可能形成无来源硬指标 |
| 方案 B | 作为后续架构 / 测试阶段候选目标 | 保留性能方向，避免伪量化 |

推荐方案 B。原因是当前没有真实测量或稳定上游基线。

#### 是否要求外部依赖失效时 Work 仍完全可用？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 完全可用 | 不现实，identity / governance / artifact 等会影响特定判断 |
| 方案 B | 核心真相边界不被篡改，受影响能力可等待或降级 | 更符合 Work 的依赖边界 |

推荐方案 B。原因是外部依赖延迟时，Work 应保持真相不被污染，而不是伪装所有能力可用。

#### 是否把高级看板性能作为核心要求？

| 方案 | 内容 | 影响 |
|---|---|---|
| 方案 A | 核心要求 | 会让外围增强压过核心闭环 |
| 方案 B | 外围增强要求，不能阻塞核心写真相和基础消费 | 对齐 Step 8 / Step 9 |

推荐方案 B。原因是基础消费追溯是核心，高级展示不是核心闭环条件。

## 7. 结构化中间产物

### 7.1 非功能类别结论

| 非功能类别 | 适用性 | 说明 |
|---|---|---|
| 性能 | 适用 | Work 是项目工作事实主链，不应成为协作主链瓶颈 |
| 可用性 | 适用 | 核心闭环能力必须和外围增强降级分开 |
| 安全 | 适用 | Work 存在大量相邻仓正文和决策边界 |
| 审计 / 可追溯 | 强适用 | Project、WorkItem、Iteration、promote 和完成依据必须可解释 |
| 幂等 / 一致性 | 强适用 | Work 需要防止多真相和重复正式事实 |
| 可观测性 | 适用 | 关键变化、边界异常和依赖延迟需要可发现 |

### 7.2 非功能要求结论

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|
| 性能 | 核心项目工作事实变更不应成为协作主链瓶颈。 | 后续架构 / 测试阶段可验证写路径延迟；旧 `CreateWorkItem P95 < 100ms` 仅作为候选目标。 |
| 性能 | 基础项目工作事实读取不应被高级看板或投影增强阻断。 | 基础查询 / 引用能力应可独立于高级展示成立；旧 `GetProjectBoard P95 < 300ms` 仅作为候选目标。 |
| 性能 | Iteration 承诺子集形成和 promote 判断不得要求 Work 拉取或保存外部正文。 | 能在只使用引用 / 摘要 / 快照的前提下完成需求层判断。 |
| 可用性 | 外围增强失效时，核心闭环能力仍应成立。 | 高级看板、容量分析、自动化建议失效不影响项目主语、承担、正式工作、承诺子集和追溯。 |
| 可用性 | 外部输入延迟时，Work 不得篡改真相边界。 | identity、process、governance、artifact、runtime 延迟时，对应能力可等待或降级，但不得隐式造真相。 |
| 可用性 | 消费视图延迟时不得影响 Work 真相写入。 | 看板 / 投影滞后可解释，不能反向改变业务真相。 |
| 安全 | Work 不得保存相邻仓正文。 | 数据归属中明确禁止 identity、conversation、method-library、process、governance、artifact、runtime、workspace 正文进入 Work。 |
| 安全 | 高风险工作变化不得绕过治理或方法定义约束。 | 高风险项目终止 / 归档 / 恢复、风险拆分、promote、工具能力调整必须引用正式约束来源。 |
| 安全 | 查询和变更不得越过项目内承担和可见性边界。 | 未授权角色不能读取或改变不属于其可见范围的项目工作事实。 |
| 审计 / 可追溯 | Project、ProjectMember、WorkItem、child WorkItem、Iteration 和 promote 的关键变化必须可追溯。 | 能说明变化来源、操作者 / 来源方、业务理由和结果。 |
| 审计 / 可追溯 | 完成、阻塞、解除阻塞、spillover 和维护对账必须可解释。 | 能追溯到外部依据引用或 Work 内正式理由，不保存外部正文。 |
| 幂等 / 一致性 | 同一正式项目工作事实不得因重复输入产生重复真相。 | 重复正式变化只能得到同一业务结果或被识别为冲突。 |
| 幂等 / 一致性 | Work 真相、外部快照、引用和消费视图之间必须保持可解释一致。 | 快照 / 投影可滞后，但必须能说明来源和滞后状态。 |
| 幂等 / 一致性 | 正式工作依赖和阻塞关系不得出现不可解释的循环或孤儿关系。 | 关系变更必须能解释其正式对象、来源和影响范围。 |
| 可观测性 | 核心工作事实变化必须能被平台稳定观察。 | Project、ProjectMember、WorkItem、child WorkItem、Iteration、promote 变化有可观察记录。 |
| 可观测性 | 边界越界尝试和外部依赖延迟必须可发现。 | 能识别外部正文写入尝试、runtime / process 越界写入尝试、依赖输入延迟或缺失。 |
| 可观测性 | 维护对账和消费视图状态必须可观察。 | 能判断投影 / 报告 / 对账是否成功、滞后或失败。 |

### 7.3 判断口径 / 目标值结论

| 类别 | 当前口径 |
|---|---|
| 正式目标 | 核心闭环不因外围增强失效而整体不可用；Work 不保存相邻仓正文；关键变化可追溯；重复输入不产生重复真相；边界越界可发现 |
| 候选目标 | `CreateWorkItem P95 < 100ms`、`GetProjectBoard P95 < 300ms`、`10w 项目 x 50 WorkItem` 容量假设 |
| 待后续验证 | 写路径延迟、基础查询延迟、投影滞后窗口、对账完成时长、事件输出延迟 |

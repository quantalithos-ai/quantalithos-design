## 3. SOP 问题回答

### 3.1 当前采用哪些关键架构机制？

当前采用的关键机制包括:

- 通过正式承接层隔离外部输入与 Work 核心语义。
- 通过显式 formalize / promote 边界把外部建议、计划步骤或执行来源升级为正式 Work 结果。
- 采用 truth / snapshot / reference / derived separation 区分正式真相、快照、引用和派生消费结果。
- 采用 Work 核心真相内部强一致,外部快照和派生消费最终一致。
- 采用只读派生视图 / 对账承接下游消费和维护解释。
- 采用事件最终一致承接跨仓事实传播和外部结果送达。
- 采用后台延后承接处理投影、快照刷新、引用刷新、对账、重建和维护报告。
- 采用追溯 / 审计 / 归档交接接缝保留关键变化可解释性。
- 采用单一编译期依赖和运行期 / 事件协作依赖纪律保护 L1 平权真相域。

这些都是机制级架构选择,不是产品或实现清单。

### 3.2 每个机制解决什么问题？

这些机制分别解决外部来源打穿 Work 真相、计划步骤污染正式任务全集、来源正文漂移、核心事实局部成立、下游消费反向绑定核心、跨仓传播压重同步链路、维护任务阻塞业务写入、关键变化不可复盘和跨仓编译依赖失控等架构层问题。

### 3.3 为什么不用其他方案？

不采用“外部来源直接写 Work 核心”,因为会让 conversation、process、governance、artifact、runtime 或 workspace 反向定义 Work 真相。
不采用“把 ImplementationPlan / PlanItem / conversation suggestion 直接落入 Backlog”,因为会污染正式协作级工作全集。
不采用“复制相邻仓正文”,因为会把 identity、method-library、process、governance、artifact、runtime 等来源真相转移给 Work。
不采用“直接暴露核心真相结构给下游消费”,因为会让 workspace、runtime、member-service 或产品入口绑定 Work 核心模型。
不采用“全部同步强收口”或“全部异步化”,因为核心事实成立需要同步判断,传播、派生和交接又不应阻塞核心写入。

### 3.4 每个选型带来什么代价或新风险？

这些机制共同带来的代价是:边界层更多、状态表达更严格、引用和快照状态需要显式维护、派生延迟需要可解释、异步传播和后台承接需要追踪、后续概要 / 详细设计不能绕开 formalize / promote 和数据归属红线。它们降低了 Work 真相被污染的风险,但提高了对象状态、边界校验和运维证据的设计成本。

### 3.5 哪些选型是当前阶段必要的,哪些暂不引入？

当前阶段必要的是正式承接层、formalize / promote 边界、truth / snapshot / reference / derived separation、核心强一致、派生只读视图、事件最终一致、后台延后承接、追溯交接接缝和依赖纪律。当前暂不引入或不锁定的是具体数据库产品、图数据库、递归 CTE、物化视图、缓存、搜索后端、消息产品、outbox 实现、完整事件溯源方案、具体协议、具体 P95 / 容量数值和代码分层实现。

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 选型主语 | 数据库、递归查询、物化视图、性能数字和事件 worker | 架构层机制 / 架构手段 | Step 10 只锁会影响边界、一致性和交互主链的技术机制 |
| 外部输入 | 可被流程、治理、产物、对话或 runtime 结果直接推入 Work | 经正式承接层和 formalize / promote 进入 | 保护正式工作事实边界 |
| 计划步骤 | 可能直接变成 Backlog / child WorkItem | 只有显式升级后的结果属于 Work | 防止执行计划正文和局部步骤污染正式任务全集 |
| 数据归属 | Project、WorkItem、Iteration、projection 和外部依据混列 | truth / snapshot / reference / derived separation | 防止来源正文和派生辅助形成第二 truth |
| 读模型 | 倾向直接锁 board projection 或 materialized view | 只确认只读派生消费机制 | 具体产品和实现后移 |
| 一致性 | 补偿流程和聚合边界混写 | 核心强一致,传播和派生最终一致 | 对齐 Step 8 / Step 9 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 直接继承旧 PostgreSQL / 递归 CTE / 物化视图 / outbox 方案 | 看起来实施路径明确 | 过早锁定技术产品和实现细节,会把候选实现误当架构真相 | 不采用 |
| 方案 B: 按架构机制说明解决的问题、采用理由和代价 | 能承接职责、依赖、数据和通信结论 | 后续概要 / 详细设计还需落到具体实现 | 采用 |
| 方案 C: 把完整事件溯源、图数据库或 CQRS 作为当前强制架构 | 对复杂关系和追溯看似完整 | 当前缺必要性证明,会显著抬高 P0 复杂度 | 不采用 |
| 方案 D: 不写关键技术机制,全部留到详细设计 | 避免过早承诺 | 后续设计缺少机制级红线,容易反复串仓 | 不采用 |

## 7. 结构化中间产物

### 7.1 关键技术机制表

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 | 说明 |
|---|---|---|---|---|
| 通过正式承接层隔离外部输入与 Work 核心语义 | 防止外部来源、下游消费和运行层输入直接打穿项目工作事实真相。 | Work 必须独立拥有 Project、ProjectMember、Backlog、WorkItem、child WorkItem、Iteration 和 promote 后结果,不能被外部仓反向定义。 | 增加输入转换、引用校验、拒绝状态和边界审查成本。 | 该机制改变外部能力如何进入 Work,属于架构层结构决定。 |
| 显式 formalize / promote 边界 | 防止 conversation suggestion、ImplementationPlan step、runtime plan item 或 artifact 来源直接污染正式工作全集。 | Work 只拥有显式升级后的正式协作级结果,不拥有外部建议、计划正文或执行推进。 | 需要保存来源引用、升级理由、结果状态和拒绝原因。 | 该机制保护 Backlog / child WorkItem 的正式性,不是某个接口的局部规则。 |
| truth / snapshot / reference / derived separation | 防止来源正文、外部生命周期、消费视图和维护材料混入 Work 真相。 | Step 8 已确认 Work 只拥有项目工作事实,外部能力只能通过快照、引用、摘要或派生结果参与。 | 需要为旧快照、未解析引用、过期视图和派生延迟提供显式状态。 | 该机制同时影响数据归属、一致性和后续对象建模。 |
| Work 核心真相内部强一致 | 防止 Project、ProjectMember、Backlog、WorkItem、child WorkItem、依赖、Iteration 和 promote 结果形成局部成立或孤儿状态。 | 核心工作事实一旦成立就会影响协作、执行、追溯和下游消费,必须在同步边界内明确成立或失败。 | 核心写路径需要更严格的校验和拒绝口径,不能以后台补写伪装成功。 | 该机制定义 Work 正式状态如何成立,不是具体事务实现。 |
| 只读派生视图 / 对账承接下游消费 | 防止 workspace、runtime、member-service、看板或报告直接依赖核心真相结构,也防止派生结果反写真相。 | 下游需要稳定消费和聚合展示,但核心模型不能被展示、查询和报表形态反向绑定。 | 增加派生滞后、重建、对账和延迟解释成本。 | 该机制影响运行承载、数据边界和消费方式,属于架构层决定。 |
| 事件最终一致承接跨仓传播 | 防止已成立 Work 事实传播、外部结果送达、观测和归档交接全部压入同步链路。 | Work 核心事实成立与下游消费完成应解耦,传播失败不应回滚已经成立的业务真相。 | 增加未送达、未消费、待交接、重放和证据追踪成本。 | 该机制改变跨边界状态传播主路径,不是队列产品选择。 |
| 后台延后承接派生、刷新和重建 | 防止投影、快照刷新、引用解析、对账、维护报告或归档准备阻塞核心写入。 | 这些能力服务消费、维护和解释,可以延迟、挂起和重建,不得成为核心成立前置条件。 | 需要可见的挂起、过期、失败、重建中和对账异常状态。 | 该机制保护核心同步边界不被外围增强拖重。 |
| 追溯 / 审计 / 归档交接接缝 | 防止项目、成员承担、正式工作、Iteration、promote 和完成依据变化不可复盘。 | Work 需要保留本域关键变化解释,同时不能接管 observability 和 archive 的主体职责。 | 需要维护交接材料、审计引用和交接失败状态。 | 该机制影响可审计性和横切协作边界。 |
| 单一编译期依赖与运行期 / 事件协作依赖纪律 | 防止 L1 平权真相域因源码依赖形成循环或让外部实现进入 Work 核心。 | `L0-core` 是唯一编译期依赖,其他仓通过运行期、引用、快照或事件协作进入。 | 后续实现需要通过边界契约和 adapter 处理外部能力,不能偷用相邻仓源码对象。 | 该机制直接保护依赖方向和仓级边界,属于架构层决定。 |

### 7.2 当前不采用口径表

| 不采用口径 | 不采用原因 | 正确落点 |
|---|---|---|
| 具体数据库产品作为当前关键选型 | 产品选择属于实现承载,当前只需锁定真相承载与派生承载边界。 | 概要设计、详细设计或实施计划 |
| 递归 CTE / 图数据库作为当前硬选型 | Work 关系需要可解释和防非法关系,但具体关系查询实现尚未比较。 | Step 11 备选方案或详细设计 |
| board 物化视图 / read model 产品形态作为当前硬选型 | 只读派生消费机制已成立,具体承载方式不应反向定义架构。 | 概要设计、详细设计或配置设计 |
| outbox worker、consumer group、topic 命名作为当前选型 | 这是事件协作实现细节,不是本章机制级结论。 | 详细设计、测试方案或实施计划 |
| 完整事件溯源作为当前必选 | Work 需要追溯和事件传播,但不等于必须采用完整 ES。 | Step 11 备选方案与取舍 |
| 所有交互同步强收口 | 会让派生、归档、观测和外部刷新阻塞核心写入。 | Step 9 通信方式分层 |
| 所有交互异步化 | 会让 Project、WorkItem、Iteration 和 promote 缺少即时成立 / 失败口径。 | Step 9 通信方式分层 |
| 旧 P95、容量数字作为架构选型 | 当前缺新版需求基线下的正式负载模型。 | 测试方案、验收标准或容量验证 |
| 除 `L0-core` 之外的编译期仓依赖 | 会破坏 L1 平权真相域和全局依赖裁剪规则。 | 运行期边界、事件协作或 SDK 接入 |

### 7.3 技术边界说明

本章采用的是机制级技术选型,不是产品清单或实现方案。`L1-work` 当前最需要被显式固定的是项目工作事实如何避免被外部来源、派生消费和运行层污染,因此正式承接层、formalize / promote、数据分层、核心强一致、只读派生、事件最终一致、后台延后承接、追溯交接和依赖纪律都进入架构主线。具体数据库、查询策略、物化视图、缓存、消息产品、outbox、协议、P95 和容量数值只有在不反向改变这些机制的前提下,才可以在后续概要 / 详细设计、测试方案和实施计划中继续选择。若后续技术实现与本章机制冲突,应以本章机制为架构真相源。

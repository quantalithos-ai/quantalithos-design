## 3. SOP 问题回答

### 3.1 这个仓有哪些主要可选架构方案？

在已确认 `L1-work` 必须作为独立项目工作事实真相仓的前提下,可进入本章比较的相邻路径包括:

- 当前主线:独立 Work 真相核心 + 正式承接层 + 显式 formalize / promote + truth / snapshot / reference / derived separation + 只读派生 + 事件最终一致 + 后台延后承接。
- 直连核心路径:外部来源和下游消费直接读写 Work 核心真相结构。
- 外部主导路径:由 process、workspace、runtime、conversation 或 artifact 等相邻仓主导 Work 事实形成。
- 完整事件溯源 / CQRS 优先路径:以完整 Event Sourcing / CQRS 作为 P0 主体架构。
- Graph-first / DAG-first 路径:以工作关系图或 DAG 查询模型作为主组织核心。
- 全同步收口路径:所有写入、传播、投影、归档和观测都在同步边界完成。
- 全异步命令 / 事件路径:所有变更和读取都围绕异步承接设计。
- Projection-first / Board-first 路径:把看板、投影或消费视图提升为主要组织核心。

具体数据库、递归 CTE、物化视图、缓存、消息产品、topic 命名和 crate 分层是实现或详细设计问题,不进入本章正式比较。

### 3.2 为什么当前选择这一种？

当前主线能同时满足四个条件:保护 Work 独立真相边界;允许外部来源通过引用、快照、摘要或 formalize / promote 影响 Work,但不转移正文归属;让核心成立判断保持强一致和同步收口;让下游传播、派生视图、对账、观测和归档以最终一致或后台承接方式演进。它牺牲了直接暴露核心、一次同步全完成和早期产品级技术路线锁定的简单感,换来更稳的边界、依赖方向、数据归属和演进空间。

### 3.3 被放弃方案的主要优点是什么？

被放弃方案都有局部优点。直连核心路径初期接入快;外部主导路径可以贴近 process、workspace、runtime 或 artifact 的已有节奏;完整事件溯源路径对历史重放表达更强;Graph-first 路径对复杂依赖查询更直接;全同步路径即时结果感更强;全异步路径解耦更彻底;Projection-first 路径对看板和下游读体验更直接。

### 3.4 为什么即便有这些优点,当前仍不采用？

这些优点不能抵消它们对当前核心边界的代价。直连核心会让外部消费和来源输入反向绑定核心;外部主导会让 Work 退化为相邻仓视图或执行副产物;完整事件溯源会在对象、状态和事件契约尚未细化前提前锁定实现范式;Graph-first 会让关系查询模型压过项目工作事实边界;全同步会把投影、归档和观测压入核心链路;全异步会削弱 Project、WorkItem、Iteration 和 promote 的即时成立判断;Projection-first 会让派生结构靠近 truth center。

### 3.5 当前选择牺牲了什么,换来了什么？

当前选择牺牲了最短调用路径、外部仓直接落事实的便利、单次同步全完成、最强事件溯源范式、图查询优先和下游直接读核心结构的便利。换来的是:核心真相不被下游或来源仓污染,正式任务全集不被计划步骤和展示视图污染,同步和异步职责分清,派生辅助不反写,后续概要 / 详细设计可以在稳定边界下继续细化对象、接口、状态和实现结构。

## 7. 结构化中间产物

### 7.1 当前主线方案

当前采用的主线方案是:

```text
独立 Work 真相核心
  + 正式承接层隔离外部输入
  + 显式 formalize / promote 升级外部来源
  + truth / snapshot / reference / derived separation
  + Work 核心真相内部强一致
  + 只读派生视图 / 对账承接消费
  + 事件最终一致承接跨仓传播
  + 后台延后承接派生、刷新和重建
  + 追溯 / 审计 / 归档交接接缝
  + 单一编译期依赖和运行期 / 事件协作依赖纪律
```

该方案的核心判断是:Work 的 truth center 必须独立稳定,外部能力只能经正式边界进入,下游消费不能直接绑定核心结构,派生和交接可以延迟收敛但不能反写真相。

### 7.2 方案路径比较表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 独立 Work truth + 正式承接 + promote + 数据分层 + 派生只读 + 事件最终一致 + 后台承接 | 同时保护 Work 真相、外部来源、正式升级、下游消费和追溯交接。 | 边界稳定,来源正文不漂移,正式任务全集不被污染,下游不反向绑定核心,核心链路不被派生拖重。 | 边界层更多,状态解释更严格,后续实现必须处理未解析、旧视图、待交接和拒绝状态。 | 采用 | 这是当前唯一同时满足 Step 2 约束、Step 8 数据归属、Step 9 通信方式和 Step 10 技术机制的主线。 |
| 直连核心路径:外部来源和下游消费直接读写核心真相结构 | 缩短接入路径,减少承接层。 | 初期实现和理解更直接,下游接入更快。 | 外部输入和下游消费会反向绑定核心模型,来源正文和展示状态更容易进入 truth center。 | 不采用 | 该路径破坏 Step 7 的依赖方向和核心保护边界。 |
| 外部主导路径:由 process / workspace / runtime / conversation / artifact 主导 Work 事实形成 | 让 Work 更贴近相邻仓已有节奏或展示体验。 | 与某个外部仓的短期协作路径更直接。 | Work 会退化为流程视图、workspace task card、runtime progress、conversation suggestion 或 artifact 依据副本。 | 不采用 | 该路径与 Work 作为独立项目工作事实真相仓的定位冲突。 |
| 完整事件溯源 / CQRS 优先路径 | 强化历史重放、事实演进和读写分离表达。 | 历史表达强,天然强调追加和重放,对审计叙事友好。 | 在对象、状态和事件契约尚未细化前过早锁定实现范式,提高 P0 复杂度和一致性解释成本。 | 保留观察 | 当前采用追溯、事件协作和派生重建机制,但不把完整 ES / CQRS 作为 P0 必选方案。 |
| Graph-first / DAG-first 路径:以工作关系图或 DAG 查询模型作为主组织核心 | 优先解决依赖、阻塞、无环和路径查询问题。 | 对复杂关系查询、影响分析和可视化更直接。 | 关系模型会压过 Project / Backlog / WorkItem / Iteration 的项目工作事实边界,并提前锁定查询实现。 | 不采用 | Work 关系必须可解释,但图或递归实现只是后续详细设计候选。 |
| 全同步收口路径:所有写入、传播、投影、归档和观测都在同步边界完成 | 追求一次交互内全链路完成。 | 即时结果感强,表面一致性清晰。 | 会把投影、对账、归档、观测和外部快照刷新压入核心链路,制造高耦合和伪一致。 | 不采用 | 该路径与 Step 8 最终一致和 Step 9 后台延后承接口径冲突。 |
| 全异步命令 / 事件路径:所有变更和读取都围绕异步承接设计 | 最大化解耦和吞吐弹性。 | 跨边界传播压力小,适合高并发事件处理。 | Project、WorkItem、Iteration、promote 和追溯读取缺少即时成立 / 失败判断,容易让调用方无法确认正式状态。 | 不采用 | 核心真相成立判断必须有同步收口,不能全部异步化。 |
| Projection-first / Board-first 路径:以看板、投影或消费视图作为主要组织核心 | 优先满足下游读取、看板和聚合展示体验。 | 下游体验更直接,读模型可以快速服务 UI 和分析场景。 | 派生结构会靠近 truth center,容易形成第二事实来源,并让下游需求反向塑造核心。 | 不采用 | 看板、投影和任务摘要只能从 Work 真相派生,不得反写。 |
| Source-copy 路径:把来源仓正文或摘要深拷贝进 Work 统一管理 | 降低跨仓读取和来源不可用时的展示成本。 | 本地读取简单,短期降级显示能力强。 | 直接打穿数据归属边界,让 identity / method / process / governance / artifact / runtime 正文漂移进本仓。 | 不采用 | 该路径与 Step 8 “明确不拥有正文 / 真相”冲突,不作为正式主线。 |

### 7.3 不进入本章正式比较的方向

| 方向 | 不进入比较的原因 | 正确处理 |
|---|---|---|
| Identity 拥有 ProjectMember 生命周期并直接替代 Work ProjectMember | 前文已确认 ProjectMember 是 Work 的项目内承担事实,GlobalMember 生命周期才归 Identity。 | Identity 提供成员 / actor 来源,Work 拥有项目内承担事实。 |
| Process 拥有 Backlog / WorkItem / Iteration 真相 | 前文已确认 process planning 和 review timing 只是节奏输入。 | Process 通过正式边界影响 planning 背景,不直接维护 Work truth。 |
| Conversation suggestion 直接生成 WorkItem | 前文已确认对话建议不能直接污染正式工作全集。 | Conversation 来源必须经过 formalize / promote。 |
| Artifact / ImplementationPlan 正文进入 Work | 前文已确认 Artifact 和 ImplementationPlan 正文归 Artifact / Runtime 边界。 | Work 只保存引用、摘要和 promote 后结果。 |
| Workspace 拥有项目任务视图并反写 Work truth | 前文已确认 Workspace 是聚合视图和消费入口。 | Workspace 只读消费查询、投影或事件协作结果。 |
| Runtime plan item progress 直接成为 child WorkItem | 前文已确认 runtime 执行步骤不等于正式协作级子任务。 | Runtime 只能通过显式 promote 提交升级请求。 |

### 7.4 轻量取舍对照表

| 当前主线得到什么 | 当前主线失去什么 |
|---|---|
| 稳定独立的 Work truth center | 不能用最短路径直接暴露核心给下游 |
| 来源事实可参与判断但正文归属不转移 | 需要维护引用、快照、摘要和未解析状态 |
| formalize / promote 保护正式任务全集 | 需要额外表达来源、理由、拒绝和升级结果 |
| 核心成立判断可同步收口 | 不能把所有工作都推给异步后台 |
| 传播、派生、对账、归档可最终一致 | 需要解释旧视图、待交接和延迟收敛 |
| 下游消费不反向绑定核心结构 | 需要额外派生只读视图和消费边界 |
| 关键变化可追溯 | 需要维护追溯交接材料和失败状态 |
| 依赖纪律稳定 | 不能偷用相邻仓源码对象简化实现 |

### 7.5 方案边界说明

本章只比较在 `L1-work` 已经是独立项目工作事实真相仓这个前提下的相邻结构路径,不重新打开 Identity、Process、Conversation、Artifact、Runtime 或 Workspace 拥有 Work 真相的讨论。完整事件溯源、Graph-first、全同步、全异步和 Projection-first 都是可能改变主线结构的有效替代路径,因此进入比较;具体数据库、消息产品、协议、递归查询和框架只是实现载体,不进入本章。当前采用的方案不是最短路径,但它最能同时守住项目工作事实、来源归属、正式升级、派生不反写、跨边界传播和后续演进空间。

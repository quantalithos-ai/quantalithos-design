## 3. SOP 问题回答

### 3.1 安全边界如何处理？

安全边界以项目内承担、正式承接、数据归属和派生不反写为核心。任何外部输入、下游消费、维护动作、对账、投影重建或配置变化都不得绕过 ProjectMember / Actor 边界、不得吸收相邻仓正文、不得让 conversation suggestion、process planning、artifact evidence、runtime plan item 或 workspace view 直接改写 Work 真相。

### 3.2 可观测性需要覆盖哪些正式对象和关键链路？

可观测性必须覆盖 Project、ProjectMember、Backlog、WorkItem、child WorkItem、依赖 / 阻塞、Iteration、formalize / promote、同步边界判断、异步传播送达、派生视图收敛、外部引用可解析性、未解析 / 过期 / 待交接状态和边界违规风险。这里要求的是“架构状态可见”,不是指定监控平台、日志字段或告警阈值。

### 3.3 可用性和韧性需要守住什么底线？

已经成立的 Work 核心真相不得因下游消费方、派生视图、看板、对账、外部来源解析、观测或归档交接失败而丢失、回滚或被改写。可恢复失败必须表达为明确失败、拒绝、暂不可处理、挂起、未解析、旧视图、待交接或延后收敛,不能伪装为已完成。

### 3.4 性能预算是否需要给出口径？

当前不写缺少依据的吞吐、延迟或容量数字,但必须给出结构性性能口径:Project、ProjectMember、WorkItem、Iteration 和 promote 的核心同步收口链路不得被派生、看板、对账、归档、观测、外部快照刷新或下游 fan-out 拖重。复杂依赖关系、长项目历史和看板消费能力必须通过派生、后台承接或后续实现选择扩展,不能反压核心事实成立。

### 3.5 配置如何管理,哪些配置不应散落？

配置和变更控制必须围绕边界行为、通信承接方式、派生能力开关、追溯交接、容量预算、降级策略和外部依赖接缝统一治理。任何配置都不得偷偷改变 Work 真相归属、正式工作全集边界、ProjectMember / GlobalMember 分层、formalize / promote 口径、同步 / 异步 / 后台承接边界、派生不反写原则或唯一编译期依赖纪律。具体配置文件和配置项属于后续配置设计或详细设计。

### 3.6 审计与可追溯性如何被正式保证？

Project、ProjectMember、WorkItem、child WorkItem、依赖 / 阻塞、Iteration、formalize / promote、完成依据、spillover、对账、重建和追溯 / 归档交接都必须能留下可复盘的正式材料或状态。追溯要求用于保护协作复盘、责任边界和来源核验,不等同于全局日志平台或长期归档正文由本仓拥有。

### 3.7 哪些横切项与本仓无关,不应机械照抄模板？

本章不纳入 identity 认证凭据生命周期、method-library 定义版本治理、process 执行 checkpoint 规则、governance 审批制度、artifact 内容扫描、runtime 工具执行沙箱、workspace UI 可访问性、全局日志存储治理和长期归档恢复手册。这些事项可能重要,但其主体职责不属于 `L1-work`;本仓只保留与项目工作事实、正式升级、引用快照、追溯交接和授权消费有关的横切约束。

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 横切表达 | 通用质量词或实现条目 | 长期作用于 Work 主线的正式约束 | 对齐 4.13 书写规范 |
| 安全 | 泛化权限要求 | 项目内承担 + 正式承接 + 正文排除 + 派生不反写 | Work 的安全核心是边界不被打穿 |
| 可观测 | 监控 / 日志实现倾向 | 核心对象、传播、派生、引用和违规状态可见 | 先定义观察对象,后续再选实现 |
| 韧性 | 重试和恢复实现 | 失败状态必须显式表达,不得伪成功 | 对齐 Step 8 / Step 9 |
| 配置 | 未形成架构约束 | 配置不得绕过核心边界、依赖纪律和承接方式 | 防止实现阶段暗改架构 |

## 7. 结构化中间产物

### 7.1 横切关注点约束表

| 横切关注点 | 作用范围 | 约束要求 | 保护目标 | 说明 |
|---|---|---|---|---|
| 安全边界:项目内承担和可见边界强制生效 | 同步变更、查询、追溯读取、下游消费、派生视图和维护动作 | 所有读取、变更、追溯和派生消费都必须受 ProjectMember / Actor / 项目可见边界约束,不得绕过项目内承担输出或修改事实。 | 保护项目工作事实不被越权消费或越权修改。 | 该要求横切读、写、维护、投影和追溯,不是单个接口权限校验。 |
| 安全边界:外部输入正式承接 | conversation、process、governance、artifact、runtime、workspace、运维 / 审计入口和相邻真相域输入 | 外部能力必须经正式承接层转换为引用、快照、摘要、正式变化或 promote 结果,不得直接写核心语义。 | 保护 Work 核心真相不被外部输入反向定义。 | 该要求横切依赖方向、数据归属和交互承接。 |
| 数据边界:明确不拥有正文 | formalize / promote、完成依据、外部快照、归档交接、维护动作和配置变化 | 禁止通过业务写入、配置、维护、派生或降级路径吸收 identity、conversation、method、process、governance、artifact、runtime、workspace、observability 或 archive 正文。 | 保护来源真相归属和 Work 数据边界。 | 该要求不是数据表规则,而是所有进入路径都必须遵守的横切红线。 |
| 正式升级边界:formalize / promote 可审查 | conversation suggestion、ImplementationPlan step、runtime plan item、artifact 来源和人工拆分输入 | 外部来源形成 WorkItem / child WorkItem 时必须显式升级,并能说明来源、理由、结果和拒绝状态。 | 保护 Backlog / child WorkItem 的正式协作级边界。 | 该要求横切职责、数据、通信、审计和测试,不是单个 command 规则。 |
| 审计与可追溯:关键变化可复盘 | Project、ProjectMember、WorkItem、child WorkItem、依赖 / 阻塞、Iteration、promote、完成依据 | 关键状态变化和关键判断结果必须保留可追溯材料或状态,不得只留下最终结果。 | 保护协作复盘、责任边界和来源核验能力。 | 该要求横切核心真相、一致性、维护和交接,不是普通日志保留要求。 |
| 审计与可追溯:交接边界可解释 | 观测、归档、追溯材料形成、跨仓事件协作和维护报告 | 交接材料必须能说明它来自哪些 Work 真相、引用或快照状态,交接失败不得改写业务事实。 | 保护 observability / archive 协作边界不反写真相。 | 该要求让追溯交接可审查,但不把全局日志或归档正文归入本仓。 |
| 可观测性:核心对象状态可见 | Project、ProjectMember、Backlog、WorkItem、child WorkItem、依赖 / 阻塞、Iteration、promote | 架构必须能区分成功、失败、拒绝、不可见、不可解析、暂不可处理和挂起等正式状态。 | 保护主线是否真实成立的可见性。 | 该要求不是监控字段设计,而是架构层状态可辨识性约束。 |
| 可观测性:传播与派生状态可见 | 异步传播、下游消费、派生视图、看板、对账、维护报告、快照刷新和引用解析 | 架构必须能区分已传播、未送达、未消费、旧视图、过期、未解析、待重建和重建失败等状态。 | 保护最终一致和后台承接的可解释性。 | 若这些状态不可见,最终一致会退化成不可审查的不确定性。 |
| 韧性 / 恢复能力:失败不伪成功 | 同步收口、异步送达、后台承接、引用解析、对账和归档交接 | 未成立状态不得被返回或记录为已成立;可恢复失败必须显式挂起、失败、拒绝、未解析或延后收敛。 | 保护核心真相和失败口径不被伪同步完成破坏。 | 该要求横切 Step 8 一致性和 Step 9 通信方式。 |
| 韧性 / 恢复能力:外围降级不污染核心 | 派生视图、看板、任务摘要、对账、快照刷新、观测、归档和下游消费 | 外围增强或下游消费失败时,已成立的 Work 真相不得丢失、回滚或被派生结构覆盖。 | 保护核心真相在降级情况下仍独立成立。 | 该要求明确外围可降级,但核心 truth 不随外围失败漂移。 |
| 性能 / 容量约束:核心链路不被外围拖重 | 同步写入、基础读取、Iteration 承诺、promote、异步传播和后台派生 | 派生、看板、对账、归档、观测、快照刷新和下游 fan-out 不得成为核心事实成立的同步前置。 | 保护核心协作路径在规模增长下仍可成立。 | 当前不写具体数值,但先固定结构性预算口径。 |
| 性能 / 容量约束:复杂关系与长历史可扩展 | 工作依赖、阻塞、影响分析、长项目历史、看板消费和追溯读取 | 复杂关系和长历史必须依附合适的关系约束、派生或后台承接扩展,不得迫使核心模型按图查询或 UI 需求组织。 | 保护核心模型不被读体验、图查询和展示体验反向塑造。 | 该要求不是数据库或图技术选型,而是扩展边界。 |
| 配置与变更控制:边界行为不可被配置绕开 | 项目可见边界、数据归属、formalize / promote、派生不反写、传播和后台承接 | 配置不得改变 Work 真相归属、正文排除规则、正式升级边界、同步 / 异步 / 后台边界或派生不反写原则。 | 保护已收稳架构主线不被配置层暗改。 | 具体配置项后移配置设计,本章只固定配置不可越界。 |
| 配置与变更控制:依赖纪律不可被配置绕开 | 本地开发依赖、运行期接缝、事件协作、adapter 和 SDK 接入 | 配置不得把 `L0-bus` 或其他 L1 / L2 / L3 仓变成 Work 编译期业务依赖,也不得让本地路径依赖替代正式边界。 | 保护全局依赖裁剪和 L1 平权真相域。 | 本地依赖路径可用于开发,但不能改变架构依赖类型。 |

### 7.4 横切影响说明

`L1-work` 的横切关注点不是通用质量清单,而是长期压在项目工作事实、正式升级、外部引用、派生辅助和追溯交接之上的结构约束。安全、审计、可观测、韧性、性能和配置控制都必须保护同一个主线:核心真相稳定,外部正文不漂移,正式工作全集不被污染,派生不反写,失败可解释。具体工具、配置项、告警阈值和恢复脚本只有在不改变这些横切约束的前提下,才能在后续设计和实施阶段继续细化。

## 3. SOP 问题回答

### 3.1 当前阶段做到哪里才算足够？

当前阶段只要能稳定成立 `L1-work` 的独立项目工作事实真相仓主线,就算架构成立。具体边界是:Project、ProjectMember、Backlog、WorkItem、child WorkItem、依赖 / 阻塞、Iteration、formalize / promote 结果和 Work 追溯记录由本仓拥有;外部输入必须经正式承接层进入;下游消费必须经项目内承担和可见边界;跨仓传播、派生、对账、外部快照刷新和归档交接可以最终一致或后台延后承接,但不得反写真相。

当前阶段不要求完整事件溯源、Graph-first、递归 CTE、物化视图、具体数据库、具体看板产品、长期归档协议、具体 P95 / 容量数字或完整外部来源生命周期策略全部落入架构主线。

### 3.2 第一批必须守住哪些结构？

第一批必须守住以下结构:

- 独立 Work 真相核心。
- Project / ProjectMember / Backlog / WorkItem / child WorkItem / Iteration 的正式归属边界。
- formalize / promote 正式升级边界。
- truth / snapshot / reference / derived separation 数据边界。
- 核心真相内部强一致。
- 派生只读视图和对账不反写。
- 事件最终一致传播边界。
- 后台派生、快照刷新、引用解析、重建和交接承接边界。
- 审计 / trace / evidence / archive handoff 接缝。
- `L0-core` 唯一编译期依赖纪律。

这些结构不一定在当前阶段全部细化到字段、接口或协议,但架构方向必须固定,后续概要设计和详细设计不能反向推翻。

### 3.3 哪些能力或约束留到后续阶段演进？

后续才进入演进主线的能力包括:

- 完整事件溯源 / CQRS 是否成为主体实现范式。
- 更强的复杂依赖关系查询、影响分析和无环维护承接。
- 更细的外部引用解析、新鲜度、快照生命周期和引用失效恢复策略。
- 更强的看板、投影、任务摘要、对账和维护报告能力。
- 与 `L4-observability`、`L4-archive` 的长期追溯 / 归档交接协议。
- 明确负载模型后的容量分层、读写隔离、冷热路径和重建隔离策略。
- 更多来源仓或外部平台接入后的 formalize / promote 来源扩展。

这些能力都必须以“不改变 Work 真相归属、不复制来源正文、不让派生反写、不让下游消费反向绑定核心模型、不引入非 core 编译期仓依赖”为前提进入。

### 3.4 哪些设计债务当前可接受,哪些不可接受？

当前可接受债务:

- 暂不量化吞吐、延迟、项目数、WorkItem 数和依赖关系规模,因为新版需求尚未形成正式负载模型。
- 暂不锁定 PostgreSQL、递归 CTE、图数据库、物化视图、缓存、搜索和消息产品,因为架构只需先固定真相、派生、关系和事件承接边界。
- 暂不把完整事件溯源 / CQRS 作为 P0 主体范式,因为对象、状态、事件契约和重放需求仍需详细设计继续验证。
- 暂不展开长期 Archive / Observability 交接协议,因为当前只需要保留追溯 / 归档接缝和待交接状态。
- 暂不展开所有外部来源的生命周期策略,因为当前只要求引用、快照、摘要和 formalize / promote 边界成立。

当前不可接受债务:

- 不允许核心真相边界不清。
- 不允许 ProjectMember 与 GlobalMember 生命周期混写。
- 不允许 Backlog / WorkItem / child WorkItem 被 personal step、conversation suggestion 或 runtime plan item 污染。
- 不允许外部正文或来源真相进入 Work truth。
- 不允许派生视图、看板、对账或维护报告成为第二 truth。
- 不允许同步成功伪装下游传播、归档交接或投影重建已经完成。
- 不允许除 `L0-core` 外形成编译期业务依赖。

### 3.5 未来哪些触发条件会迫使架构调整？

触发条件必须来自边界压力、规模压力、一致性压力、恢复压力或下游消费压力,而不是模糊的“以后可能需要”。典型触发包括:

- 工作依赖、阻塞、影响分析和无环判断压力让当前关系承接不足。
- 看板、workspace、runtime、member-service 或审计消费开始反压核心同步链路。
- 外部引用、快照和 formalize / promote 来源增多,导致未解析、旧快照或来源不可用状态影响核心判断和复盘。
- 审计、复盘或合规要求明确需要事件级重放、时间旅行或更强不可变事实模型。
- Archive / Observability 要求从简单交接引用升级为正式交接协议和恢复验证。
- 量化负载模型证明单一读写承载或当前分层无法保持核心事实成立路径稳定。

### 3.6 当前主线演进时,最先改变的结构面是什么？

最先改变的结构面通常不是核心 truth center,而是外围承接层:派生只读视图、关系查询辅助、看板 / 任务摘要、引用解析、新鲜度管理、追溯 / 归档交接和事件传播恢复。只有当审计重放、容量隔离、复杂依赖或强恢复要求明确压到核心事实模型时,才考虑把完整事件溯源、Graph-first 关系承载、分区冷热路径或更强状态生命周期纳入核心主线。

## 4. 当前文档问题诊断

| 旧架构内容 | 问题 | 本轮处理 |
|---|---|---|
| 旧文档把 P95、项目数、WorkItem 数和 DAG 查询当作成功标准 | 当前新版需求没有正式负载模型,直接继承会形成伪约束 | 放入后续容量演进触发条件,不作为当前阶段硬指标 |
| 旧文档把 PostgreSQL、递归 CTE、物化视图和 board projection 靠近主线 | 技术承载可能反向定义架构 | 当前只保留 truth、关系、派生和对账承接边界,产品后移 |
| 旧文档把 process / governance / artifact 联动写成强主线 | 外部真相可能主导 Work | 当前只保留引用、快照、正式结果送达和 formalize / promote 边界 |

| 旧文档缺少演进触发条件 | 后续可能把愿望池当架构路线 | 以边界、规模、一致性、恢复和消费压力触发演进 |

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 演进主语 | 功能、技术产品、性能数字和实现方案混杂 | 架构主线阶段、结构债务和触发条件 | 对齐书写规范 §4.14 |
| 当前阶段边界 | 容易理解为所有能力都要现在完成 | 当前先让独立 Work truth、边界、归属、一致性和交互成立 | 架构不是项目排期 |
| 后续演进项 | 像愿望池或 TODO | 只保留会改变架构承接方式的结构演进项 | 避免扩张主线 |
| 设计债务 | 未区分可接受和不可接受 | 可接受债务有理由,不可接受债务是边界红线 | 防止实现阶段绕过核心约束 |
| 触发条件 | 泛泛“后续再优化” | 以规模、边界、一致性、恢复、审计压力触发 | 演进必须由事实驱动 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 把旧文档的性能、DAG、projection、archive 全部列为后续路线图 | 看起来覆盖完整 | 会把未确认内容包装成承诺,形成愿望池 | 不采用 |
| 方案 B: 按架构主线阶段写当前边界、可接受债务、后续演进项和触发条件 | 能说明当前为什么足以成立,也能给后续演进留下判断门槛 | 需要后续设计继续补量化和实现细节 | 采用 |
| 方案 C: 当前阶段直接把完整 ES / CQRS、Graph-first、具体数据库和 Archive 交接全部定死 | 后续实现方向明确 | 过早锁定实现范式,并可能打穿已收稳边界 | 不采用 |
| 方案 D: 完全不写演进路线 | 文档更短 | 后续容易把可接受债务和边界红线混淆 | 不采用 |

| 引用 / 快照生命周期增强阶段 | 加强外部引用可解析性、快照新鲜度、来源不可用状态和 formalize / promote 来源恢复能力。 | 允许当前只表达旧快照、未解析、待刷新和挂起状态,不做完整生命周期策略。 | 引用状态机、快照新鲜度策略、来源不可用降级、promote 来源恢复和引用失效审计。 | 当外部来源增多,未解析引用和旧快照开始影响工作判断、完成依据、复盘或下游稳定展示时。 | 该阶段仍不复制来源正文,只强化引用和快照承接。 |
| 事件 / 追溯增强阶段 | 在 Work 追溯记录和事件协作基础上评估是否需要更强事件模型、重放、时间旅行和审计追溯能力。 | 当前不把完整 ES / CQRS 作为 P0 主体范式,只保留追溯记录、事件协作和派生重建机制。 | 完整事件溯源、事件版本治理、重放窗口、时间旅行读取、审计 replay evidence。 | 当合规、复盘、恢复或跨仓重放明确要求事件级重放,且当前追溯记录不足以解释状态变化时。 | 该阶段才考虑改变核心事实模型的内部表达方式。 |
| 归档 / 观测交接增强阶段 | 将 Work 追溯材料从简单交接引用升级为更正式的 Observability / Archive 协作协议。 | 当前只保留 Work 域追溯记录、交接引用和待交接状态。 | 归档交接协议、观测材料 schema、交接失败恢复、归档回链验证。 | 当 `L4-observability` / `L4-archive` 需要稳定消费和恢复验证,且简单事件或引用交接不足以支撑审计要求时。 | 该阶段不让 Work 拥有全局日志或长期归档正文。 |
| 容量 / 隔离增强阶段 | 基于正式负载模型增强读写隔离、分区、冷热路径、后台重建和容量保护。 | 当前不继承旧 P95、项目数、WorkItem 数和 DAG 查询规模作为硬约束。 | 容量分层、读写隔离、冷热历史策略、投影重建隔离、批量维护限流。 | 当测试、验收或生产负载模型证明核心同步路径、派生维护、关系查询或历史读取存在结构瓶颈时。 | 该阶段由量化事实触发,不是凭旧数字提前定方案。 |

### 7.2 当前阶段边界说明

当前阶段的目标不是把所有外围展示、复杂关系实现、数据库产品、归档协议和容量策略一次性定完,而是先让 `L1-work` 作为独立项目工作事实真相仓的结构成立。只要核心 truth center、正式承接层、数据归属、formalize / promote、派生不反写、事件传播和后台承接边界稳定,后续能力就可以在不打穿边界的前提下演进。当前可接受债务之所以可接受,是因为它们暂不影响本仓是否拥有正确的项目工作事实;一旦这些债务开始影响核心边界、正式升级、追溯复盘或容量稳定,就必须进入下一阶段。

### 7.3 可接受债务与不可接受债务表

| 债务类型 | 当前是否可接受 | 理由 | 后续处理 |
|---|---|---|---|
| 未量化吞吐 / 延迟 / 项目数 / WorkItem 数 / 依赖关系规模 | 可接受 | 当前缺新版正式负载模型,提前继承旧数字会形成伪约束。 | 测试方案、验收标准和实施计划形成量化依据后触发容量增强阶段。 |

| 未把完整 ES / CQRS 作为 P0 主体范式 | 可接受 | 当前已采用追溯记录、事件协作和派生重建机制,但完整 ES 需要对象、状态、事件和重放需求共同支撑。 | 审计 / 重放压力明确后进入事件 / 追溯增强阶段。 |
| 未展开长期 Archive / Observability 交接协议 | 可接受 | 当前只需保留追溯记录、交接引用和待交接状态,不接管横切系统主体职责。 | Archive / Observability 形成正式消费需求后进入归档 / 观测交接增强阶段。 |
| 未展开所有外部来源生命周期策略 | 可接受 | 当前只要求引用、快照、摘要和 formalize / promote 边界成立。 | 外部来源增多或未解析状态影响判断时进入引用 / 快照生命周期增强阶段。 |
| 核心真相边界不清 | 不可接受 | 会使本仓退化为 process 视图、workspace task card、runtime progress 或 conversation suggestion 副本。 | 必须在当前阶段修正。 |
| ProjectMember 与 GlobalMember 生命周期混写 | 不可接受 | 会打穿 identity / Work 边界。 | 必须在当前阶段修正。 |
| Backlog / WorkItem / child WorkItem 被外部计划步骤污染 | 不可接受 | 会破坏正式工作全集。 | 必须在当前阶段修正。 |
| 外部正文或来源真相进入 Work truth | 不可接受 | 会造成数据归属漂移和串仓。 | 必须在当前阶段修正。 |
| 派生视图 / 看板 / 对账反写真相 | 不可接受 | 会形成第二 truth。 | 必须在当前阶段修正。 |
| 同步成功伪装异步传播 / 归档 / 投影已完成 | 不可接受 | 会破坏一致性和失败可解释性。 | 必须在当前阶段修正。 |
| 除 `L0-core` 外形成编译期业务依赖 | 不可接受 | 会破坏全局依赖裁剪和 L1 平权真相域。 | 必须在当前阶段修正。 |

### 7.4 触发条件小表

| 触发条件 | 触发的演进方向 | 最先改变的结构面 | 不应改变的边界 |
|---|---|---|---|
| 依赖、阻塞、影响分析或无环判断反压核心链路 | 复杂关系增强 | 关系查询辅助、影响分析投影、异常关系对账 | 不让 Graph-first 反向定义 Work truth |
| 下游高频读取、看板或变化感知反压核心链路 | 派生消费增强 | 只读投影、看板、任务摘要、游标、重建承接 | 不直接暴露核心 truth 结构 |
| 外部来源增多导致未解析 / 旧快照影响判断和复盘 | 引用 / 快照生命周期增强 | 引用状态、快照新鲜度、来源恢复 | 不复制来源仓正文 |
| 合规或恢复要求明确事件级重放 / 时间旅行 | 事件 / 追溯增强 | 事实事件模型、版本治理、重放窗口 | 不让事件流接管外部仓 truth |
| Observability / Archive 要求正式恢复验证和回链 | 归档 / 观测交接增强 | 交接协议、回链验证、待交接恢复 | 不拥有全局日志或归档正文 |
| 正式负载模型证明单一承载不足 | 容量 / 隔离增强 | 读写隔离、分区、冷热路径、后台重建隔离 | 不降低核心一致性和项目可见边界 |
| 新外部来源或执行平台接入造成 promote 语义压力 | 引用 / 快照生命周期增强 / 正式升级边界增强 | 正式承接层、promote 来源状态、来源适配 | 不让来源仓或 runtime 直接写核心 |

### 7.6 演进边界说明

`L1-work` 的演进必须优先保护现有主线,而不是扩张职责。能先在派生层、关系辅助层、引用层、交接层、后台承接层解决的问题,不应直接改变核心 truth center;只有当审计重放、容量隔离、复杂关系或恢复要求明确证明当前事实模型不足时,才考虑核心结构演进。每个后续阶段都必须继续满足五条底线:不复制来源正文,不让外部计划步骤污染正式工作全集,不让派生反写,不让下游消费反向绑定核心模型,不引入非 core 编译期仓依赖。

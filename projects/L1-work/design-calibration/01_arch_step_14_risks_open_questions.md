## 3. SOP 问题回答

### 3.1 当前还有哪些尚未关闭的架构风险？

当前尚未关闭的架构风险集中在九类:

- 旧 Project / WorkItem / Iteration 聚合、PostgreSQL、递归 CTE、board projection 和 P95 指标回流为架构主线。
- process、workspace、runtime、conversation、artifact 或 governance 反向定义 Work truth。
- ProjectMember 与 GlobalMember / Role / Actor 生命周期在后续设计中混写。
- ImplementationPlan step、runtime plan item、personal checklist 或 conversation suggestion 污染 Backlog / child WorkItem。
- 相邻仓正文、外部 evidence body 或 runtime 执行正文因展示便利进入 Work truth。
- 派生视图、看板、任务摘要、对账或维护报告成为第二 truth。
- 同步成功被误写成异步传播、投影重建、归档交接或观测交接已经完成。
- 除 `L0-core` 外的仓被实现或配置变成编译期业务依赖。
- 缺少正式负载模型导致旧 P95、项目数、WorkItem 数和 DAG 查询规模回流为硬约束。

### 3.2 这些风险会影响哪一层架构结构？

这些风险分别影响职责边界、系统上下文、依赖方向、数据所有权、一致性策略、关键交互、横切关注点和演进路线。最严重的风险会直接破坏 `L1-work` 作为独立项目工作事实真相仓的成立条件,因此必须在架构风险章节中显式列出。

### 3.3 当前还有哪些待确认事项？

当前待确认事项主要是还缺后续设计或测试阶段输入的问题,包括正式 API / command / query / event / DTO 字段、Project / WorkItem / Iteration 详细状态集、关系约束实现、formalize / promote 详细对象、外部引用与快照生命周期、Archive / Observability 交接协议、完整 ES / CQRS 是否升级为主体范式、量化容量模型、具体数据库 / 投影 / 缓存 / 消息产品。

### 3.4 哪些待确认项会影响前文结论是否成立？

这些待确认项不会推翻当前已收稳的架构边界:Work 仍是项目工作事实真相仓,只拥有自身 truth、引用、快照、摘要、派生辅助和 formalize / promote 后结果,不拥有外部正文。它们会影响后续概要设计、详细设计、测试方案和实施计划如何落地;如果后续选择打穿外部正文排除、formalize / promote、派生不反写、同步 / 异步边界或依赖纪律,才会反向破坏前文结论。

### 3.5 哪些风险是当前阶段可接受的,哪些会阻塞后续推进？

当前可接受并可带约束推进的风险是:旧实现口径回流风险、协议 / 产品未定、量化负载模型未定、完整 ES / CQRS 未定、Archive / Observability 交接格式未定、复杂关系实现未定。会阻塞后续推进的是:核心 truth 边界不清、外部正文进入 Work truth、ProjectMember 接管 GlobalMember、正式工作全集被执行步骤污染、派生结构反写真相、同步成功伪装异步 / 后台工作完成、非 core 仓成为编译期业务依赖。

## 4. 当前文档问题诊断

| 旧 / 前序内容 | 问题 | 本轮处理 |
|---|---|---|
| 旧文档中的 Project / WorkItem / Iteration 聚合、PostgreSQL、递归 CTE、board projection | 容易回流为架构第一层结构 | 只作为历史候选输入暂存,不得高于新版架构主线 |
| 旧性能数字和 DAG 查询规模 | 缺少新版需求确认的负载模型 | 写成待确认事项或演进触发条件,不作为当前硬指标 |
| Process / Governance / Artifact 联动 | 容易扩张成外部仓主导 Work truth | 当前只允许引用、快照、正式结果送达和 formalize / promote |
| Projection / Board / Report 靠近主线 | 可能成为第二 truth | 明确只作为派生只读能力,不得反写真相 |
| Artifact evidence / ImplementationPlan / runtime progress 与 WorkItem 混写 | 展示和执行便利可能诱导保存外部正文 | 当前用引用 / 摘要 / promote 结果约束,正文不得进入 truth |
| 本地开发路径依赖约定 | 后续实现可能把本地路径依赖误当编译期架构依赖 | 当前只允许 `L0-core` 编译期依赖,其他为运行期 / 事件协作 |

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 风险表达 | 分散在需求风险、演进债务和旧文档问题中 | 汇总成正式风险表,写清影响范围、当前处理口径和阻塞性 | 对齐书写规范 §4.15 |
| 待确认事项 | 容易混入 TODO、方案或演进愿望 | 只保留缺确认且会影响后续主线判断的问题 | 防止脑补确定性结论 |
| 阻塞判断 | 可接受债务和不可接受债务容易混淆 | 明确阻塞 / 不阻塞 / 有条件阻塞 | 支撑是否能进入 ADR 与需求追溯 |
| 旧口径处理 | 旧细节可能继续影响架构主线 | 统一按历史输入暂存,不得反向定义 Work truth | 防止旧文档回流 |
| 边界红线 | 分散在多个 Step | 在风险表中集中约束 | 便于后续概要 / 详细设计继承 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 只写“暂无阻塞风险” | 文档短,推进快 | 会掩盖旧口径回流、正式工作全集污染、派生第二 truth 等关键风险 | 不采用 |
| 方案 B: 风险与待确认事项拆成两张表,并给出阻塞判断 | 可审查,能承接后续设计和测试 | 文档更长,需要避免重复前文已定结论 | 采用 |
| 方案 C: 把所有未定能力都写成风险 | 显得谨慎 | 会把可接受债务、演进项和技术选型缺口误写成阻塞风险 | 不采用 |
| 方案 D: 在本步直接解决全部待确认事项 | 看似闭环 | 违反本步边界,会把详细设计、测试和实施问题提前脑补成架构定论 | 不采用 |

| 完整 ES / CQRS 或 Graph-first 被过早锁定或被完全遗忘 | 技术机制、备选方案、演进路线、后续详细设计 | 当前只固定追溯记录、事件协作和复杂关系可解释,完整范式保留观察 | 不阻塞 | 当前阶段可不锁定实现范式,但详细设计需继续评估状态、事件、关系和重放压力。 |

| 外围增强能力中哪些进入当前交付范围 | 功能裁剪、演进路线、测试与验收 | 缺当前阶段交付边界和优先级确认 | 当前按外围增强挂起,不作为核心 truth 成立条件 | 包括高级看板、容量趋势、自动化建议和更强对账能力。 |

### 7.3 当前处理口径说明短文

本章把已经明确会打穿 Work 主线边界的问题写成风险,把仍缺接口、状态、协议、量化模型、产品或后续仓协作确认的问题写成待确认事项。风险的当前处理口径只说明现在如何约束或暂存,不写最终解决方案;待确认事项只说明缺什么确认和如何挂起,不预支后续设计结论。已被前文确认的边界红线不再伪装成待确认项,但一旦后续实现打穿这些红线,就会转化为阻塞问题。

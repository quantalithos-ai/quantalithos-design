## 3. SOP 问题回答

### 3.1 哪些架构决定需要沉淀为 ADR？

建议后续沉淀为 ADR 的决策包括:

- 将 `L1-work` 定义为独立项目工作事实真相仓,而不是 process 视图、workspace task card、runtime progress、conversation suggestion 或 artifact 副本。
- 将 Project、ProjectMember、Backlog、WorkItem、child WorkItem、依赖 / 阻塞、Iteration、formalize / promote 结果和 Work 追溯记录定义为 Work truth center。
- 将 ProjectMember 定义为 Work 的项目内承担事实,并与 GlobalMember / Role / Actor 生命周期分离。
- 通过 formalize / promote 边界隔离 conversation suggestion、ImplementationPlan step、runtime plan item 和外部来源。
- 通过 truth / snapshot / reference / derived separation 承接外部事实,禁止复制来源仓正文。
- 将派生视图、看板、任务摘要、对账和维护报告限定为只读、可重建、最终一致,不得成为第二 truth。
- 采用核心同步收口、跨边界事件最终一致、派生 / 刷新 / 交接后台延后承接的通信结构。
- 将 `L0-core` 固定为唯一编译期依赖,其他仓通过运行期、引用、快照或事件协作进入。
- 当前不把完整 ES / CQRS、Graph-first、具体数据库或物化视图作为 P0 主体架构。
- 只保留 Observability / Archive 追溯交接接缝,不让 Work 拥有全局日志或长期归档正文。

### 3.2 每个关键架构决定对应哪些需求、约束或风险来源？

这些决策分别承接 `00-需求文档.md` §2 本仓定位、§4 目标与非目标、§6 使用方与依赖、§7 核心能力闭环、§9 功能需求、§10 业务规则与边界约束、§11 数据需求与数据归属、§12 接口与依赖、§13 非功能需求、§14 验收标准和 §15 风险与待确认事项。

### 3.3 是否存在没有需求来源的架构设计？

当前没有影响主线的孤儿架构判断。具体 API / command / query / event / DTO 字段、Project / WorkItem / Iteration 详细状态集、复杂关系实现、具体数据库 / 投影 / 缓存 / 消息产品、量化容量模型、Archive / Observability 交接协议和完整 ES / CQRS 是否升级为主体范式仍保持待确认或后续设计承接,没有被写成已定架构结论。

### 3.4 是否存在没有架构承接的核心需求或关键约束？

当前没有核心闭环需求未被架构承接。`FR-WORK-001` ~ `FR-WORK-008` 已由职责边界、限界上下文、数据所有权、关键交互、关键技术机制和横切关注点承接;`FR-WORK-E01` ~ `FR-WORK-E05` 被承接为外围增强、派生辅助或演进路线,没有被误提升为当前核心 truth 成立条件。

### 3.5 哪些取舍和红线必须长期可追溯？

必须长期可追溯的红线包括:Work 不能被 process / workspace / runtime / conversation / artifact / governance 吸收;ProjectMember 不能接管 identity 生命周期;ImplementationPlan step、runtime plan item、personal checklist 或 conversation suggestion 不能直接进入 Backlog / child WorkItem;相邻仓正文不得进入 Work truth;派生视图和看板不得反写真相;同步成功不得伪装异步传播、投影重建或归档交接完成;除 `L0-core` 外不得形成编译期业务依赖。

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 追溯来源 | 旧实现对象、数据库、DAG、性能数字容易成为隐性来源 | 以新版 `00-需求文档.md` 的定位、目标、FR、BR、数据、接口、NFR、验收和风险为来源 | 对齐当前需求基线 |
| 追溯方式 | 容易写成章节目录对照或“已覆盖” | 写成需求结论 / 约束 -> 架构承接结果 -> 承接位置 -> 成立理由 | 对齐书写规范 §4.16 |
| ADR 主语 | 没有稳定专项 ADR 或容易把技术机制清单当 ADR | 只列长期影响主线的架构决策候选 | 对齐书写规范 §4.17 |
| 待确认处理 | 可能在追溯阶段脑补 API、产品、状态或量化指标 | 保留为漏项检查或待确认,不提前闭合 | 防止生成伪确定性 |
| 边界红线 | 分散在职责、数据、交互、横切和风险章节 | 在追溯矩阵和 ADR 候选中建立长期索引 | 便于后续概要 / 详细设计继承 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 只列需求章节到架构章节的目录对照 | 短,容易写 | 不能证明具体承接关系,也无法发现孤儿结论 | 不采用 |
| 方案 B: 建立需求追溯矩阵、漏项检查表和 ADR 决策候选索引 | 能说明来源、承接、落点、缺口和长期决策 | 文档更长,需要避免新增结论 | 采用 |
| 方案 C: 本步直接创建正式 ADR 文件 | ADR 体系看起来完整 | 超出当前 Step 范围,且会绕过后续 ADR 评审 | 不采用 |
| 方案 D: 把所有关键技术机制都写成 ADR | 看似全面 | 会把局部机制和实现选择噪音化,削弱真正长期决策 | 不采用 |

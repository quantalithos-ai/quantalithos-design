## 3. SOP 问题回答

### 3.1 哪些已确认结论应分别回填到哪些正式章节？

Step 1 支撑来源承接、约束条件和需求追溯矩阵。Step 2 回填业务背景与驱动力、约束条件。Step 3 ~ Step 15 分别回填职责边界、系统上下文、限界上下文、容器 / 部署、依赖方向、数据所有权、关键交互、关键技术机制、备选方案、横切关注点、演进路线、风险与待确认、需求追溯和 ADR 索引。参考章节只收纳正式参考材料,不承接新的架构判断。

### 3.2 哪些结论需要拆分吸收到多个章节,而不是机械复制？

需求基线拆分到 §1、§3 和 §16。formalize / promote 同时支撑职责边界、限界上下文、数据所有权、关键交互、技术机制、横切关注点和 ADR 候选。truth / snapshot / reference / derived separation 同时支撑数据所有权、依赖方向、关键技术机制、风险和追溯。`L0-core` 唯一编译期依赖同时支撑依赖方向、技术机制、横切配置和实施约束。

### 3.3 哪些术语、编号或交叉引用需要统一？

正式文档统一使用 `L1-work`、`项目工作事实真相仓`、`项目工作事实真相核心`、`ProjectMember 项目内承担事实`、`正式工作全集`、`child WorkItem`、`Iteration 承诺子集`、`formalize / promote`、`派生消费辅助`、`本地索引 / 投影 / 引用层`、`truth / snapshot / reference / derived separation`、`L0-core 唯一编译期依赖` 等术语。旧 Project 聚合、PostgreSQL、递归 CTE、board projection、旧 P95 和容量数字只作为历史风险,不得回流为正式主线。

### 3.4 哪些内容仍应继续保留为风险或待确认,不能润色成定论？

正式 API / command / query / event / DTO 字段、Project / WorkItem / Iteration 详细状态机、formalize / promote 对象级契约、复杂关系实现、引用 / 快照生命周期、Archive / Observability 交接协议、完整 ES / CQRS 是否升级为主体范式、具体数据库 / 投影 / 缓存 / 消息产品和量化容量模型,都必须继续保留为待确认或后续设计承接项。

### 3.5 参考项应如何收口,不与 ADR 或追溯重复？

参考章节只保留正式参考材料和用途说明,包括当前需求文档、需求追溯中间产物、架构 SOP、架构书写规范、全局依赖裁剪规则以及已完成的 L0 / L1 / L3 上游设计材料。ADR 候选保留在 §17,需求到架构的承接关系保留在 §16,参考章节不重复追溯矩阵或 ADR 索引。

## 6. 术语统一结论

| 正式术语 | 统一含义 | 禁止替代表达 |
|---|---|---|
| `L1-work` | 项目工作事实真相仓 | process 视图、workspace task card、runtime progress、conversation suggestion 副本 |
| 项目工作事实真相核心 | 本仓唯一核心子域 | Project / WorkItem / Iteration 多 truth center |
| ProjectMember 项目内承担事实 | GlobalMember 在项目内承担工作的正式事实 | 平台成员生命周期、role 生命周期 |
| 正式工作全集 | Backlog 与协作级 WorkItem / child WorkItem 范围 | personal checklist、runtime step、chat suggestion |
| formalize / promote | 外部来源进入正式 Work 结果的显式升级边界 | 直接创建任务、后台补写任务 |
| 派生消费辅助 | 看板、投影、任务摘要、对账和维护报告 | 第二 truth、反写核心 |
| 本地索引 / 投影 / 引用层 | 为稳定消费、降级显示、判断和追溯保留的影子结构 | 来源仓正文副本 |
| truth / snapshot / reference / derived separation | 数据归属和一致性主机制 | 外部正文统一复制进 Work |

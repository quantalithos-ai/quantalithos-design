## 1. 本步目标

在已经确认可承接的上游需求与架构输入前提下,明确本次概要设计要收敛到什么深度、重点把哪些代码主体、对象骨架、接口骨架、处理流和状态机讲清,以及哪些内容当前不进入概要设计范围。

本步只回答“这轮概要设计要收什么、不收什么、停在什么深度”,不提前拆对象字段、接口 schema、函数实现、持久化细节或测试用例。

## 3. SOP 问题回答

### 3.1 本次概要设计最主要要把哪些结构说清？

本次概要设计最主要要把 `L1-work` 从“项目工作事实真相仓架构结论”转译为可进入详细设计的代码主体骨架。具体要说清:

- 代码主体框架如何承接项目工作事实真相核心、支撑上下文、本地索引 / 投影 / 引用层和运行承载角色。
- 主要组成部分如何划分,每个组成部分承担什么、不承担什么、包含哪些代码主体 / 模块候选。
- 每个主要组成部分能发现哪些对象候选,哪些对象后续会正式成为关键对象。
- 关键对象的所属部分、对象类型、主要责任、关键字段骨架、成员函数骨架、工厂函数骨架和禁止事项。
- Command / Query / Event / Operations Job / 外部接缝的接口骨架。
- 核心处理流和重要函数数据流如何连接入口、application service、domain 对象、repository / port、event / projection / audit。
- Project、ProjectMember、Backlog、WorkItem、child WorkItem、dependency / blocker、Iteration、formalize / promote、派生维护等关键状态如何定义和流转。
- 配置只影响哪些运行承载、接缝或策略,哪些边界绝不能配置化。

### 3.2 这一轮概要设计应停在什么深度,才算足够支撑进入详细设计？

这一轮概要设计应停在“代码主体骨架层”:

- 可以点名正式主要组成部分、代码主体 / 模块候选、关键对象名、接口名、处理流名和状态名。
- 可以给出关键字段骨架,字段必须写明类型名,但不写完整字段全集和序列化 / 数据库列定义。
- 可以给出成员函数 / 工厂函数骨架,参数必须写明类型名和参数名,但不写完整 Rust 实现和调用链脚本。
- 可以画处理流和状态流转的 ASCII 图,但不写完整时序图、依赖图算法、重试算法、事务脚本和协议 schema。
- 可以识别配置影响,但不写配置 JSON 示例、配置项默认值和配置加载实现。

### 3.3 哪些内容属于本次概要设计范围？

本次概要设计范围包括:

- 与上游文档的关系声明。
- 本次设计目标、范围和深度口径。
- 约束条件。
- 代码主体框架总览。
- 主要组成部分、职责与边界。
- 关键对象轮廓。
- API / 接口骨架。
- 关键处理流 / 重要函数数据流。
- 状态定义与状态流转。
- 异常与边界场景轮廓。
- 配置影响轮廓。
- 详细设计承接清单。
- 设计风险与待确认事项。
- 参考。

### 3.4 哪些内容虽然相关,但当前不进入概要设计范围？

当前不进入概要设计范围的内容包括:

- 需求目标、用户故事、功能需求、验收标准。
- 架构系统上下文、职责边界、依赖方向、数据所有权、技术机制和方案取舍。
- 完整 Rust struct / enum / value object 实现契约。
- 完整 Command / Query / Event / Job DTO schema、JSON / proto / CloudEvent 数据格式。
- 完整函数签名、伪代码、调用链、事务边界和 repository 函数。
- DDL、索引、迁移脚本、存储产品、队列产品、搜索产品和缓存策略。
- 配置完整文档、配置 demo 和配置项逐项说明。
- 测试方案、验收标准、实施计划和 commit boundary。

### 3.5 哪些内容应留给详细设计,而不应在本章提前展开？

以下内容留给 `03-详细设计.md`:

- Rust struct / enum / value object 的完整字段、枚举值注释、成员函数签名和工厂函数签名。
- 每个 API 的完整函数签名、请求 / 响应 DTO、JSON 或 proto schema、错误码和幂等语义。
- 每个 Command / Query / Event / Operations Job 的独立数据流图、函数调用链和事务边界。
- repository / port / adapter trait 签名、持久化模型、索引、迁移和一致性实现。
- 状态机的完整状态矩阵、转移函数、错误状态和测试切口。
- 配置加载、配置结构体、配置项默认值、配置使用位置和禁止配置化校验。

## 4. 当前文档问题诊断

| 旧 `02-概要设计.md` 内容 | 问题 | 本轮处理 |
|---|---|---|
| “先用人话理解本仓”篇幅较大 | 停留在新人解释层,没有明确本轮概要设计交付代码主体骨架 | 改为明确本轮要输出代码主体框架、对象、接口、流程、状态机和详细设计承接 |
| 以 Project / ProjectMember / Backlog / WorkItem / Iteration / ImplementationPlan 逐词解释为主 | 把对象解释直接当作概要主线,没有先定义代码主体和组件边界 | 后续 Step 4~6 重新建立代码主体、组成部分和关键对象 |
| promote、ImplementationPlan、planning timing、done 判定提前展开 | 这些内容混合了概要、详细设计和相邻仓边界 | 本轮只把它们列入处理流、状态和异常边界候选,不提前写完整规则 |
| 旧目标偏“让读者理解为什么这样做” | 不足以判断是否能支撑详细设计 1:1 展开 | 改为以“详细设计能继续落对象、接口、流程、状态和配置契约”为目标 |
| 非目标列表未系统排除配置、测试、验收和实施计划内容 | 容易把后续文档内容提前写进概要设计 | 本步补充范围边界和详细设计承接边界 |

## 5. 改动前后对比

| 维度 | 改动前 | 改动后 |
|---|---|---|
| 设计目标 | 让新人理解 Work、明确 Project / WorkItem / Iteration 等业务词 | 让详细设计可以按概要设计 1:1 展开代码主体、对象、接口、流程和状态机 |
| 范围边界 | 偏“什么不做”的非目标列表 | 明确“本概要设计收什么、不收什么、哪些交给详细设计” |
| 深度口径 | 停留在领域解释和系统心智 | 下沉到代码主体骨架层,但不进入完整实现契约 |
| 旧对象线索 | 直接进入主线 | 作为候选线索,后续 Step 按对象发现与正式化规则筛选 |
| 下游承接 | 泛化为支撑详细设计 | 明确详细设计需要继续展开的对象、接口、处理流、状态机和配置契约 |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方案 A: 概要设计只做系统心智解释 | 易读 | 无法支撑详细设计 1:1 展开 | 不采用 |
| 方案 B: 概要设计下沉到代码主体骨架层,但不写完整实现 | 能承接详细设计,也不越界 | 需要后续 Step 逐步补对象、接口、流程和状态 | 采用 |
| 方案 C: 概要设计直接写完整 Rust 契约、DTO 和数据流 | 对开发最直接 | 抢占详细设计职责,容易导致文档层级混乱 | 不采用 |
| 方案 D: 先按旧 Project / Backlog / ImplementationPlan 教学线索写范围 | 迁移成本小 | 旧线索会遮蔽项目工作事实真相仓主线 | 不采用 |

## 7. 结构化中间产物

### 7.1 设计目标表

| 目标 | 说明 | 交付给详细设计的结果 |
|---|---|---|
| 收稳代码主体框架 | 把架构责任层和运行承载映射为可实现的代码主体骨架 | 详细设计可继续落 crate / module / service / port / adapter / storage 边界 |
| 收稳主要组成部分 | 明确主要组成部分、职责、不承担职责、包含的代码主体 / 模块候选和边界接缝 | 详细设计可按组成部分展开实现契约 |
| 建立对象候选池并正式化关键对象 | 第 5 章发现对象候选,第 6 章筛选正式关键对象 | 详细设计可为每个关键对象补完整 struct / enum / value object 契约 |
| 收稳 API / 接口骨架 | 按 Command / Query / Event / Operations Job / 外部接缝分类点名正式接口 | 详细设计可逐接口展开签名、DTO、JSON / proto、错误码和幂等 |
| 收稳关键处理流 | 点名关键处理流和重要函数数据流,说明入口、service、domain、port、event / projection / audit 的关系 | 详细设计可逐处理流展开函数调用链、事务和测试切口 |
| 收稳状态定义与状态流转 | 明确 Project、ProjectMember、WorkItem、child WorkItem、dependency / blocker、Iteration、formalize / promote、派生维护等关键状态集合和流转方向 | 详细设计可展开状态矩阵、转移函数和异常状态 |
| 收稳配置影响轮廓 | 识别受配置影响的组成部分和禁止配置化边界 | 详细设计和配置设计可继续定义配置结构、默认值和加载规则 |
| 收稳详细设计承接清单 | 明确哪些主语已经足够稳定,哪些需要 03 继续展开 | 后续 agent 能按清单继续写 `03-详细设计.md` |

### 7.3 当前阶段设计深度口径

- 本轮概要设计必须强到足以支撑其他 agent 继续写 `03-详细设计.md`。
- 本轮概要设计要点名正式主语,包括代码主体、主要组成部分、关键对象、接口、处理流、状态和配置影响。
- 字段和函数可以写骨架,但字段必须带类型名,函数参数必须带类型名和参数名。
- 不写完整 Rust 实现、完整 DTO schema、完整状态矩阵、完整事务脚本、完整配置 demo 或完整测试用例。
- Project、ProjectMember、Backlog、WorkItem、child WorkItem、Iteration、ImplementationPlan promote 只作为对象 / 流程 / 状态候选进入后续 Step,不得直接替代代码主体框架。

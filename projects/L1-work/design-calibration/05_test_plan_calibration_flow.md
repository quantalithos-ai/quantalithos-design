## 三、本轮校准总目标

本轮不是在旧 `05-测试方案.md` 上追加用例,而是把新版 `00/01/02/03/04` 中已收稳的需求、架构、概要、详细设计和配置结论转化为可执行、可追溯、可留证的测试方案。

目标输出:

```text
1. 05 只承接 00/01/02/03/04 的结论,不重新定义它们。
2. 05 按测试方案书写规范的 15 章主链组织。
3. 05 明确 L1-work 的测试对象、测试切口、测试层级、覆盖矩阵、用例、数据、环境、自动化门禁、专项测试、缺陷复验、进入退出准则和证据归档。
4. 05 必须回指详细设计中的正式对象、协议、状态、错误、事务、幂等、配置、观测和最小验证清单。
5. 05 必须承接 04 的 profile、配置项、敏感配置、加载校验、失效策略和证据边界。
6. 05 为 06-验收标准提供证据编号和测试结论输入。
7. 05 不写验收裁决、不写开发排期、不写部署命令、不重新定义 Rust struct / enum / trait / function。
8. 如果 05 发现必须改变需求、架构、概要、详细设计或配置设计,必须先回写对应上游文档。
```

## 五、执行纪律

- 每个 Step 必须先形成中间产物,不得直接重写正式 `05-测试方案.md`。
- 每个 Step 必须逐项回答 SOP 的“应问的问题”。
- 每个 Step 必须包含当前文档问题诊断和改动前后对比。
- 每个 Step 必须包含测试设计取舍。
- 每个 Step 必须包含“对上游设计的影响判定”。
- 每个 Step 必须包含至少一个结构化产物: 表格、ASCII 图、矩阵、清单或回填草稿。
- 每个 Step 如涉及图示,必须遵守测试方案 ASCII 图统一格式。
- Step 状态从 `[~]` 改为 `[x]` 后,才能进入下一 Step。
- 未确认事项不得写成正式测试方案契约。
- 测试方案不得自行发明字段、状态、接口、错误或证据口径。
- P0 用例必须能回指详细设计契约并形成可交给 `06-验收标准.md` 的证据。

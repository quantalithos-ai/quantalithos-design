## 10. 回退、暂停与变更控制

> 校准来源：
> - `design-calibration/07_implementation_plan_step_10_rollback_pause_change_control.md`
>
> 延伸阅读：建议继续阅读上述中间产物的“暂停规则”“回退规则”“变更控制”和“恢复条件”小节。

### 10.1 暂停触发与处理

| 触发条件 | 动作 | 责任方 | 保留材料 | 恢复条件 |
|---|---|---|---|---|
| 字段/DTO/状态/port/version/source/boundary 不闭合 | 停止当前 boundary；登记具体缺口 | implementer + designer | 文件行号、blocker note、当前 diff | owning design 回写并固定新 baseline，重新闭环审计 |
| owner/bus/visibility/attention seam 缺失 | 只允许已列明的 local negative/controlled slice；正向停 | designer + owner | manifest 缺口、blocked reason | versioned formal manifest 与用户授权 |
| gate failed/blocked/not_run/infrastructure_failed | 不进下一阶段、不提交；保留原始输出 | implementer | raw/log/status/report | 修复后新 `<run_id>`，重跑受影响 gate |
| redaction/dependency/ownership boundary 失败 | 立即停止交付；禁止风险接受覆盖 | security/architecture owner | scanner output、diff、report | clean fixed run 与复核记录 |
| 用户未授权 commit 或 scope 越界 | 保持 working tree，不 stage/commit 越界内容 | implementation owner | diff、台账、授权记录 | 明确授权且 staged scope 回到单一 boundary |
| design baseline 改变 | 关闭旧 boundary gate，重新读取 00~07 和 calibration | designer | 旧 baseline 指针、影响矩阵 | 新 baseline 固定并完成全量 P0 影响审计 |

### 10.2 回退边界

已验证的未来 boundary 只可在其门禁和证据仍可追溯时回退；不得删除或改写旧 raw/report，不得擅自回退用户已有改动、已验证提交或其他 Phase。失败实现的 git 回退属于未来实现仓流程，本设计仓不执行。提交结果 unknown 时先通过权威 lookup/operation resolve 判断，不换 key 盲目重做。

### 10.3 变更控制矩阵

| 变化类型 | 必须重开 | 影响追溯 | 处理 |
|---|---|---|---|
| public DTO、ref、error、protocol schema | 03、05、06、07 受影响 Step | TC/EV、AC、boundary | 回写真相源，固定新 baseline，新 run |
| state、phase、generation、cursor、transaction/idempotency/unknown | 03、05、06、07 | STATE/REC/TXN/IDEM、VETO | 重新做状态/一致性审计，不保留旧通过假设 |
| visibility/no-write/owner boundary | 00/01/03/05/06/07 | BOUND/VIS/QRY/SEC、VETO | fail-closed，禁止局部放宽 |
| profile、binding、secret、crypto、resource limit | 04、05、06、07 | CONFIG/RES/SEC、AC-NFR | 新 profile/run；不改业务 truth |
| suite、script、artifact/report/EV schema | 05、06、07 | evidence/VETO、report integrity | 新 run；旧证据只读保留 |
| phase、batch、commit boundary 或 handoff 规则 | 07 及 boundary 台账 | implementation ledger、提交审计 | 同步新增/废止 skeleton，重新做跨 boundary 审计 |

恢复实施必须同时满足：blocker 已由 owner/设计修复或明确仍 blocked；新 baseline 已固定；当前 boundary 重新通过 Design/Scope Gate；工作区只含授权改动；受影响门禁和 evidence 以新 run 可追溯；未满足时保持 `wait_design`、`blocked` 或 `waiting`。

## 11. 提交、评审与交付纪律

> 校准来源：
> - `design-calibration/07_implementation_plan_step_11_commit_review_delivery.md`
>
> 延伸阅读：建议继续阅读上述中间产物的“提交前规则”“Commit Gate / Handoff Gate”“提交信息与配置”“评审与交付”小节，并对照 `standards/document/实施计划书写规范.md` §4.9。

### 11.1 Commit Gate 与 Handoff Gate

| 项 | 要求 | 检查方式 | 当前 |
|---|---|---|---|
| design_baseline | 记录正式 00~07 的 immutable baseline；当前仅 `not_fixed_until_handoff` | baseline manifest/diff audit（future） | pending |
| required_reads | 读取项目/实施/boundary 台账、正式 00~07、scoped calibration 和适用规范 | 台账与阅读记录（future） | pending |
| allowed_scope | 只改当前 boundary 的 crate/module/scripts/tests/docs | staged diff 与 boundary ledger | planned |
| forbidden_scope | 禁止私补 schema/port/state/mapper/config/evidence，禁止 owner/outbound/archive 写 | static boundary scan | planned |
| required_checks | fmt、lint/check、targeted tests、redaction/dependency/report（按 boundary） | fixed run raw/report | pending |
| Commit Gate | 门禁通过、staged scope 精确匹配一个 BND、无用户无关改动、message/whitespace 合格且用户明确授权 | `git diff --cached`、gate report、授权记录 | 未满足 |
| Handoff Gate | 真实 hash/message、剩余 blocker、未跑测试、下一 boundary、用户改动保护和固定 evidence 路径 | implementation/boundary ledger（future） | 未满足 |

### 11.2 提交时机与粒度

future 实现仓只有在一个 `BND-*` 的批次、设计闭环、测试/验收门禁和 diff 审查均完成，并取得用户明确授权后才允许一笔提交。不得按单个 struct、函数、文件或当天工作量拆 commit，也不得把无关功能、格式化、后续 Phase 或设计变更混在一起。若提交前发现设计偏离，先回写 03/04/05/06/07、固定新 baseline，再重新跑受影响门禁。

### 11.3 Commit message 规则

实现代码仓默认使用英文标题和正文，格式固定为：

```text
<type>(<scope>): <subject>

One-sentence summary for this commit boundary:

Sub-feature group:
- file.rs (+12): concise functional summary.

Co-Authored-By: Codex <noreply@openai.com>
```

`type` 可用 `feat`、`fix`、`refactor`、`docs`、`test`、`chore`、`perf`、`ci`、`style`；`scope` 必填并应对应 `workspace`、`config`、`contract`、`domain`、`query`、`projection`、`consumer`、`recovery`、`adapter`、`api`、`worker`、`job`、`report`、`release` 或 `handoff` 等实施边界。正文先用一句话概括 boundary，再按子功能分组列文件；文件只写文件名并标记 `(+n)`、`(-n)`、`(~n)` 或组合改动量；bullet 之间不插空行，正文不得出现字面量 `\\n`，footer 前必须有真实空行。需要精确控制格式时，写入完整 message 文件并使用 `git commit -F` 或 `git commit --amend -F`。

当前 `quantalithos-design` 若未来获授权提交，`type` 使用英文、subject/body 使用中文，并保留固定 footer `Co-Authored-By: Codex <noreply@openai.com>`；该规则不适用于实现代码仓。实现仓提交前必须在目标仓读取项目提交规范和历史合格提交，并使用 project-local 配置：

```bash
git config user.name "quantalithos-labs"
git config user.email "quantalithos.ai@gmail.com"
git config user.name
git config user.email
```

上述命令是未来检查合同，不是本轮已执行记录；不使用 `--global`。

### 11.4 提交前自检、评审与交付

| 检查项 | 通过条件 |
|---|---|
| worktree/diff | 只含当前 boundary 授权文件；用户已有 dirty 改动未被改写或 stage |
| design closure | 字段、DTO、state、ref identity、validation truth、UoW/idempotency、projection/rebuild、artifact materialization 和 phase boundary 均可回指 |
| required gates | 该 boundary 的 fmt/check/test/redaction/dependency/report 门禁均有固定 run 记录；未跑项保持 not_run |
| message | subject/body/footer、英文实现仓规则、文件名与改动量标记符合规范 |
| docs sync | 设计偏离、接口变化、AC/TC/EV 变化已回写相应真相源和台账 |
| evidence | raw→report→EV/AC/VETO 配对完整；不存在静态 pass、latest 或跨 run 拼接 |
| handoff | 只在真实 future commit 后填写 hash/message、剩余 blocker、未跑测试、下一 boundary；当前不填写 |

评审按 boundary、design baseline、required checks、AC/VETO 和 evidence path 进行；blocked、缺 raw、未审 acceptance 草案不能当 ready。交付只允许交付真实生成且审查过的固定 run 材料或明确的 planned/blocked 设计状态，不得交付伪造 verdict、signoff 或 readiness。

| 结果 | 条件 | 当前适用性 |
|---|---|---|
| `complete` | 全部 P0 交付、formal seam、证据、VETO、S/A、review、handoff 满足并由授权角色确认 | 不适用；不得预填 |

### 12.3 交付前整体审计

在移交实现或建立新 baseline 前，设计者必须按 `设计真相源闭环与可落码性标准.md` 对正式 03/04/05/06/07 做一次 Phase/BND 级闭环审计：检查字段/DTO、状态/版本、ref/validation、事务/幂等/unknown、projection/rebuild、artifact/report/evidence materialization、依赖分类和 phase 越界。任一适用项不通过，保持 `wait_design`，先回写设计并重新审计；实现者只做二次核验，不得现场补口。

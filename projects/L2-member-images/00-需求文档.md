## 2. 本仓定位与边界

> 校准来源:
> - `design-calibration/00_req_step_02_position_boundary.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_02_position_boundary.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节,了解镜像域 truth 与相邻 owner 边界如何收敛。

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L2-member-images` 是 AI 成员运行层中的成员镜像资产与构建产物供给层,负责把受控 Role 映射和已固定版本的静态装配输入转化为可追溯、可发布、可回滚且可被实例化消费的镜像供给事实。 |
| 本仓不是什么 | 它不是成员主体、runtime loop、tool execution / capability registry、外部 adapter truth、live state、容器 lifecycle、sandbox / governance / observability truth、marketplace、产品入口或通用 Artifact truth 仓。 |
| 边界对象列表 | 仓:`L3-method-library`;仓:`L1-artifact`;仓:`L2-runtime`;仓:`L2-tools`;仓:`L2-member`;仓:`L2-member-service`;仓:`L4-sandbox`;概念:template / seed / build output;概念:runtime live state。 |
| 单独成仓原因 | 平台需要把 Role 运行环境的构建期静态装配与供给事实从运行编排、运行内容和通用制品生命周期中独立出来。 |

| 归类 | 需求边界 |
|---|---|
| 本仓拥有 | image family / variant 与 persona 装配定义;component / extras / seed placement 绑定;variant revision / derivation;build intent / input-output / digest / provenance 绑定;镜像 eligibility / availability / rollback / retire 与入口语义 |
| 本仓只消费 / 引用 | RoleDefinition 与 Role mapping;member / runtime / tools 发布产物;seed template 来源;正式 Artifact 消费引用;builder / registry / applicable evidence 的安全结果 |
| 本仓禁止拥有 | 相邻仓正文和生命周期;member / runtime live state;实际 container / sandbox / tool execution;approval / observed / marketplace / product truth;通用 Artifact version / lineage / baseline |

本仓物理装配外部 component 或 template,不转移其语义与发布 truth owner。静态输入和运行时状态必须始终满足以下红线:

```text
template / seed / pinned component / build input / candidate output
  -> 本仓只承接静态身份、版本、placement 和镜像域绑定

container / run / turn / live memory / checkpoint / credential / observed result
  -> 属于运行期或相邻 owner,不得进入本仓 truth 或构建输入
```

## 3. 背景与问题定义

> 校准来源:
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_03_problem_context.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节,了解问题主线与无 authority 数字的排除依据。

AI Member 以 Role 对应的受控运行环境启动。该环境由 member、runtime、tools、角色 extras 与 policy / memory / workspace seed template 等多来源静态资产组成,必须在实例化前形成可验证的 pinned 镜像入口。若没有独立镜像域 owner,映射、输入 pin、构建结果、digest / provenance 和 availability 会散落在脚本、registry 或下游编排中,无法证明某个入口由哪些受控输入派生。

| ID | 类型 | 问题 | 影响 | 当前判断边界 |
|---|---|---|---|---|
| `P-MI-001` | 业务 | 缺少唯一的成员镜像资产与供给 owner | 下游无法稳定判断哪个入口可实例化 | 必须有单一镜像域 truth,不由 CI / registry / member-service 拼接 |
| `P-MI-002` | 治理 | Role -> variant mapping 可能在构建仓或下游被 hardcode | 形成第二映射真相并发生漂移 | 只能消费方法库正式来源;不可验证时阻断受影响路径 |
| `P-MI-003` | 技术一致性 | member / runtime / tools / extras 输入可能未固定或互不兼容 | 同名镜像不可复现,能力上限不可解释 | 必要输入必须 pinned;兼容结论缺失时显式 pending / blocked |
| `P-MI-004` | 边界 | seed template 与 live memory / workspace / policy truth 容易混写 | 静态镜像反向拥有运行态或治理 truth | 只承接 template ref、版本与 placement,不承载 live state |
| `P-MI-005` | 供应链 | 构建输入、candidate digest 和 provenance 未形成稳定绑定 | 无法证明输出来自哪些受控输入 | 每个候选必须回指完整 input snapshot 与 digest / provenance |
| `P-MI-006` | 归属 | 镜像域 revision / availability 与 Artifact version / lineage / baseline 容易重复定义 | 出现通用制品双写源 | 本仓只持 Artifact 正式消费引用;image handoff 缺口显式 pending |
| `P-MI-007` | 下游协作 | 可实例化 manifest / variant / ref 缺少正式消费合同 | member-service 可能自行解析 mapping 或使用不可验证引用 | 只提供 pinned、可验证入口;合同缺失时 positive launch lane 阻断 |
| `P-MI-008` | 运行可靠性 | nightly、变化输入、事件触发和失败语义可能被压成单一成功 / 失败 | 重复构建、unknown 或部分结果被误报 ready | 触发来源和失败类别必须可区分;不可验证结果不进入 availability |
| `P-MI-009` | 事件边界 | 入站构建 event schema 与出站 event authority 均未闭合 | 事件可能被误当 truth 或形成无授权合同 | 只承接已验证入站意图;当前不定义 event output |

当前没有可复用的 workload、measurement baseline 或已发生实现证据支撑旧时延、大小、成功率、覆盖率或保留天数。本文以完整 pin、owner 唯一、digest / provenance 可回链和 fail-closed 作为可判断问题边界。

| seam | 关联方 | 本仓如何协作 | 禁止推导 |
|---|---|---|---|
| compile | `L0-core` | 只使用经正式认定的 shared contract | pending image schema 不得本地 shadow |
| runtime | `L3-method-library`;`L2-member-service` | 消费 mapping;供给 pinned entry | 不等于 sibling source / package dependency |
| event | `L0-bus` | 按需消费已验证镜像构建 event | 当前无 event output |
| ref | L2 components、seed owner、`L1-artifact`、registry | 绑定 pinned input / formal reference / safe snapshot | 不拥有外部正文或生命周期 |
| adapter | scheduler / builder / registry / applicable evidence / Artifact handoff | 产品中立地交接外部能力 | adapter success 不等于 domain outcome |
| fake | 所有未就绪 seam 的后续验证替身 | 只验证 isolated negative / parity semantics | 不得进入 production composition 或证明 readiness |

### 6.4 禁止依赖

| 禁止依赖 | 正确协作方式 |
|---|---|
| 对 method-library 的 source / path dependency | runtime / ref / pinned snapshot |
| 对 runtime / tools / member 的 source / package dependency | component release ref |
| 对 member-service 的反向 source dependency | runtime / ref supply contract |
| 本地定义 `ArtifactVersion` / lineage / baseline | `ConsumableArtifactReference` + pending handoff |
| 本地 capability / tool registry | 受控 component / capability refs |
| Bus event 承载镜像 truth或默认 event output | 本地 accepted truth + 仅已授权 event boundary |
| Registry / builder / evidence SDK 进入 domain truth | product-neutral adapter + 后续配置绑定 |
| 写入 runtime / member-service / Sandbox / governance / observability truth | ref / handoff / safe conclusion |
| fake 进入生产组合或作为 readiness evidence | 正式 adapter + 真实 qualification |

## 7. 核心能力闭环

> 校准来源:

>
> 延伸阅读:

本仓的不可替代性不在于“执行一次容器构建”,而在于让 Role 静态运行环境从定义来源、pinned 装配、candidate、digest / provenance / eligibility 到可实例化入口保持同一条可归责链。

```text
  -> [C-MI-4] 候选输出的 digest / provenance / eligibility 能够被验证
  -> [C-MI-5] 供给可用性、回滚与可实例化入口能够显式成立
```

该图只表示能力成立的逻辑前置,不表示 API、event、CI 或实施时序。

| 节点 | 能力成立描述 | 进入条件 | 退出条件 | 本仓 owner | 外部 owner / pending |
|---|---|---|---|---|---|
| `C-MI-1` 受控定义 | image family / variant 与 persona 装配身份可稳定识别并回指正式 mapping | mapping 来源存在且可验证 | 定义和来源 resolved;异常显式 | 镜像域定义与 mapping 消费状态 | mapping truth 归 method;`MI-UP-003` |

| `C-MI-3` 构建候选 | nightly 或获准输入形成唯一 intent,attempt 有完整 snapshot 和明确结果 | C2 完整;来源获准 | candidate ref / digest 或 failed / blocked / unknown 可追 | intent / attempt / snapshot / candidate binding | scheduler / builder / registry 外置;`MI-UP-005` |
| `C-MI-4` provenance 与 eligibility | candidate digest 与 provenance 绑定,适用 gate 和 Artifact gap 可解释 | C3 有 candidate | eligible / blocked / pending 有充分来源 | digest / provenance binding 与 image eligibility | evidence / policy / Artifact 外置;`Q-MI-004`,`MI-UP-007` |

|---|---|

| 边界外 | Role / tool / runtime / member / Artifact / container / Sandbox / governance / observability / marketplace / product truth 与基础设施产品本体 |

## 10. 业务规则与边界约束

以下规则约束需求层 truth、变化与 owner 边界,不规定状态机字段、事务、API、CI 或 adapter 实现。Pending seam 适用同样的保守规则,但规则存在不表示对应正向合同已 ready。

| 规则编号 | 规则类型 | 规则内容 | 约束对象 |

| `BR-MI-006` | 不变量 | 可构建 variant revision 的全部静态输入必须完整、来源可验证且 pinned。 | Assembly baseline |

| `BR-MI-008` | 不变量 | 装配完整性不得通过猜版本、复制外部正文或把未知来源标为可用来补齐。 | 完整性判定 |
| `BR-MI-009` | 显式变化 | Derivation、装配差异和 revision 变化必须形成可区分新修订,不得覆盖历史。 | Revision history |
| `BR-MI-010` | 边界约束 | Component、tool contract、seed 正文和 Artifact 通用 truth 保持外部 owner。 | Input owner boundary |
| `BR-MI-011` | 治理约束 | Nightly 必须保留;其他变化 / event 只有具有 authority 且可验证时才能形成有效 intent。 | Intent source |
| `BR-MI-012` | 不变量 | 每个有效 attempt 必须唯一关联 intent、variant revision 和完整 immutable input snapshot。 | Attempt / snapshot |
| `BR-MI-013` | 禁止行为 | Intent rejected / pending、input incomplete、builder 未确认或结果 failed / blocked / unknown 时不得生成或宣称 candidate digest / ref。 | Candidate condition |
| `BR-MI-014` | 显式变化 | Candidate、failed、blocked、unknown 与 retry 必须可区分,新结果不得覆盖既有 attempt。 | Outcome history |
| `BR-MI-015` | 边界约束 | Scheduler、builder、registry 与 Bus carrier truth 不属于本仓;交接成功不等于构建成功。 | Adapter / event boundary |
| `BR-MI-016` | 不变量 | Candidate digest 必须与 intent、snapshot、revision 和全部来源形成完整一致的 provenance。 | Digest / provenance |

| `BR-MI-019` | 显式变化 | Image eligibility 与 Artifact handoff / formal ref 状态必须分别形成、分别解释。 | Cross-domain status |
| `BR-MI-020` | 边界约束 | Evidence body、供应链工具 / key truth 与 Artifact 通用 truth 不属于本仓。 | Evidence / Artifact boundary |
| `BR-MI-021` | 不变量 | 只有满足供给条件且 digest / ref 可验证的 pinned 版本才能进入 supply;生产禁 mutable selector。 | Availability / entry |
| `BR-MI-022` | 显式变化 | Publish、replace、rollback 与 retire 必须显式发生并保留历史。 | Availability lifecycle |
| `BR-MI-023` | 边界约束 | 镜像 entry 不表达 container 创建、启动、健康、升级决定或 observed consumption。 | Consumer boundary |
| `BR-MI-024` | 禁止行为 | 合同 / authority 未闭口时不得伪报通知、确认、升级或实例化,也不得私造 event output。 | Handoff / event boundary |
| `BR-MI-025` | 审计约束 | Availability、entry、handoff attempt 与 consumer gap 必须可区分且可追溯。 | Supply audit |

## 11. 数据需求与数据归属

> 校准来源:

>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_11_data_ownership.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节,了解 truth、snapshot、ref 与 forbidden body 四类归属。

正式数据类型只有四类。本仓基于外部 ref / safe conclusion 形成的 mapping validation、eligibility 和 handoff gap 属于本仓派生 truth,不是第五类数据;物理 materialization 不转移 component / template 的语义 owner。

| 数据类型 | 判断口径 | 生命周期口径 |
|---|---|---|
| 真相数据 | 镜像域定义、binding、attempt、derived conclusion 和 supply transition 由本仓拥有 | 通过显式建立 / revision / transition 形成;历史不得原地覆盖 |
| 快照数据 | 为稳定消费或一次 attempt / evaluation 固定上游安全目录 / 摘要 | 随消费语境形成;不获得上游 truth 生命周期 |
| 引用数据 | 只保存与外部对象的 binding | 随引用建立、替代或失效变化;正文生命周期外置 |
| 禁止保存正文 | 外部语义正文、live state、secret、backend / Artifact / container truth | 不进入本仓领域生命周期 |

### 12.3 Seam 纪律

| seam | 纪律 |
|---|---|
| compile | 仅 DEP-MI-002 的正式 Core shared contract;pending schema 不得本地 shadow |
| runtime | DEP-MI-001/014 的 mapping consumption / downstream supply,不等于 package dependency |
| event | DEP-MI-007 conditional inbound only;当前无 event output authority |
| ref | 只 binding 外部 object / safe snapshot,不拥有 body 或外部 lifecycle |
| adapter | 产品中立;request / adapter success 不等于 domain outcome |
| fake | 只用于后续 isolated negative / parity verification,不进入生产或证明 readiness |

Pending external seam 只能支撑 fail-closed 需求和 contract gap,不能证明 positive integration。Registry / Artifact 边在 C-MI-5 复用既有依赖,不建立第二份外部 truth。

## 13. 非功能需求

> 校准来源:
> - `design-calibration/00_req_step_13_non_functional_requirements.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_13_non_functional_requirements.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节,了解六类质量要求与无 measurement baseline 时的判断口径。

性能、可用性、安全、审计 / 可追溯、幂等 / 一致性和可观测性是本仓的六类最小质量检查框架。当前没有获 authority 的 workload、measurement baseline 或实现 evidence,因此不伪造任何量化 SLA / SLO、build duration、image size、architecture count 或 retention 数值;现阶段以离散状态、禁止行为、链完整性和历史不覆盖作为判断口径。

### 13.1 能力级非功能需求

| 非功能需求 | 类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|---|
| `NFR-MI-001` | 性能 | 已有 variant / persona definition 与 mapping conclusion 的读取不得成为定义校准和下游解析的主链阻塞点。 | 已有事实读取不触发 build、registry 或 instantiation;source 不可达时返回明确状态。当前无数值 baseline。 |
| `NFR-MI-002` | 可用性 | Mapping exact seam 或 source unavailable 时,既有定义仍可追,新 revision 不得以 stale / default 冒充 resolved。 | 既有 truth 与本次判断可区分;missing / stale / conflict / unavailable 时变化 fail closed。 |
| `NFR-MI-003` | 审计 / 可追溯 | Definition、mapping snapshot / ref 与 validity conclusion 必须回指正式来源和判断语境。 | 当前 / 历史结论可关联来源,不保存 RoleDefinition / mapping body。 |
| `NFR-MI-004` | 安全 | 静态装配不得承接 secret、live memory、checkpoint、workspace live content 或外部 semantic body。 | 只允许获准 pinned refs / templates 与 placement;forbidden body 出现即无有效 baseline。 |
| `NFR-MI-005` | 审计 / 可追溯 | 每个 assembly baseline、variant revision 和 derivation 必须追溯全部必要 pinned input。 | 可回指 predecessor / base、diff rationale、component / extras / seed refs 和 placement。 |
| `NFR-MI-006` | 幂等 / 一致性 | 重复校准不得产生 conflict baseline;input 或 derivation 变化必须形成新 revision。 | 相同语境无冲突 current baseline;变化保留旧 revision。 |
| `NFR-MI-007` | 可用性 | Event lane 或 scheduler / builder / registry 失效不得取消 nightly 语义或伪改既有 build truth。 | Event / nightly 可区分;失效只形成 rejected / blocked / failed / unknown,不形成虚假 candidate。 |
| `NFR-MI-008` | 幂等 / 一致性 | Duplicate intent 或 retry 不得覆盖原 intent / attempt 或混写多次结果。 | 同一 intent 保持关联;每次实际尝试形成独立 attempt / outcome。 |
| `NFR-MI-009` | 可观测性 | Intent、snapshot、attempt 与 candidate / failed / blocked / unknown 必须稳定可区分。 | 无需 external job / log body 即可判断领域阶段、结果和阻塞 owner。 |
| `NFR-MI-010` | 安全 | 正式 applicable gate missing / failed / conflict / unknown 时,eligibility 必须 fail closed。 | 只有正式适用来源齐备才形成对应 positive conclusion;未确权 kind 保持 pending / blocked。 |
| `NFR-MI-011` | 审计 / 可追溯 | Candidate digest provenance 必须回指定义、revision、input snapshot、attempt 和 gate source。 | Digest 可沿本仓关系追至完整来源链并区分 Artifact handoff gap。 |
| `NFR-MI-012` | 幂等 / 一致性 | 同一 digest 的原 provenance 不得因 reevaluation 或 Artifact status 变化被改写。 | 新语境形成新 evaluation / gap,旧 binding 和 eligibility context 可追。 |
| `NFR-MI-013` | 性能 | 已有 availability、variant 和 pinned entry resolve 不得依赖 container creation 或 consumer confirmation。 | 基于本仓 truth / ref 返回 entry 或 gap;registry 不可验证时明确 unresolved / unavailable。当前无数值 baseline。 |
| `NFR-MI-014` | 可用性 | Registry、Artifact 或 member-service unavailable 时,既有 availability 不得被反写,不合格新 entry 不得发布。 | Local supply / handoff / consumer confirmation 分层;外部失效只形成 gap / unavailable。 |
| `NFR-MI-015` | 审计 / 可追溯 | Publish / replace / rollback / retire 与 handoff attempt 必须回指 eligible digest、pinned ref 和 prior availability。 | Transition 可追至发起语境和前序状态;rollback / retire 保留历史。 |
| `NFR-MI-016` | 幂等 / 一致性 | 重复 supply transition 不得形成矛盾 availability;entry binding 必须与 availability / pinned ref 一致。 | 相同语境无冲突结果;重复变化复用既有效果或形成关联 transition。 |

### 13.2 全局非功能需求

| 非功能需求 | 类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|---|
| `NFR-MI-017` | 性能 | 已有镜像域事实的 query、calibration judgment 和 status resolve 不得成为 L2 消费主链主要阻塞点。 | 读取不执行 build / instantiation 或获取 external body;等待可归因。量化目标等待正式 baseline。 |

| `NFR-MI-019` | 安全 | 本仓不得持有相邻 owner 的 secret / live / external body truth;生产禁 mutable ref,applicable gate 不得绕过。 | Forbidden body 不入仓;entry pinned 且禁 `latest`;owner / gate veto 成立。 |
| `NFR-MI-020` | 审计 / 可追溯 | Definition -> revision -> intent -> attempt -> provenance -> eligibility -> availability -> handoff 必须连续可追。 | Entry 可反查来源,失败 / rollback / retire / gap 可定位节点,history 不覆盖。 |
| `NFR-MI-021` | 幂等 / 一致性 | 跨节点重复 calibration、intent、retry、reevaluation 和 rollback 不得制造第二 truth 或改写事实。 | 重复动作复用既有效果或形成关联新事实;current definition / eligibility / supply 不矛盾。 |
| `NFR-MI-022` | 可观测性 | 关键 status、transition、blocking owner 和 gap 必须以 safe domain conclusion 稳定可观察。 | 可区分 source / build / eligibility / availability / handoff 状态和 local / external owner;不保存 raw observed body。 |

这些要求定义质量底线,不表示任何实现测量、测试结果或 SLO 已成立。未来量化指标只能在正式 workload、measurement baseline、owner 和需求变更流程齐备后进入。

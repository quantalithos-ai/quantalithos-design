## 2. 背景与问题定义

### 2.1 业务背景

AI 成员不是一个抽象 Role,而是要变成一个可拉取、可启动、可审计的镜像实例。member-service 只能启动镜像,不能临时组装一个运行环境；因此 member、runtime、tools、supervisord、角色 extras、基础安全配置都必须被预先构建成标准化镜像。L2-member-images 就是这层“运行镜像工厂”。没有它,RoleDefinition 到 image_variant 的映射无法真正落地,member-service 也就无法按角色稳定起容器。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末 / 段 3 当前) | 痛点 |
|---|---|---|
| 仓设计 | 只有 README 骨架 | 仓级需求未显式化 |
| 角色镜像集合 | 9 个 Role 已定义方向 | 镜像矩阵尚未确权为正式需求 |
| 运行依赖 | member/runtime/tools 已拆仓 | 缺少统一装配与版本钉住规则 |
| 安全发布 | 已提出扫描 / BOM / cosign | 验收口径与阻断条件未成文 |
| N4 Exit Criteria | 要求每晚构建 9 个 Role 镜像 | 当前尚无仓级需求文档承接 |

### 2.3 为什么要做(量化依据)

- 路线图 N4 明确要求:`member-images` 仓要支持 **9 个 Role 镜像每晚 CI 构建**
- 没有预构建镜像,`StartMember P95 < 5s(不含拉镜像)` 这个目标无法稳定达成
- README 已明确要求 BOM、签名、扫描、禁用 `latest`,说明这是平台级交付物而不是可选工程细节

### 2.4 业务问题 vs 技术问题

- **业务问题**:如何把“角色”稳定变成可运行、可审计、可升级的 AI 成员实例
- **技术问题**:base image 复用、role extras 裁剪、nightly CI、多架构构建、漏洞阻断、签名、版本钉住、与 method-library / member-service 的镜像契约对齐

## 5. 核心用例与用户故事

### 5.1 核心用例

1. nightly CI 构建 base image 和 9 个 Role 镜像
2. runtime / tools / member 发新 tag 后重建对应 Role 镜像
3. member-service 根据 RoleDefinition.image_variant 选择镜像并启动成员
4. 漏洞扫描阻断高危镜像发布
5. 生成 BOM 与签名,供审计和回溯

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **member-service**,我想要 **根据 Role 拉取一个预构建镜像**,以便 **快速启动对应 AI 成员** |
| 优先级 | P0 |
| 验收条件 | **Given** `backend-dev` Role 已发布 **When** StartMember **Then** 解析到 `ai-member-backend-dev:<semver>` 并成功拉取 |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **镜像维护者**,我想要 **每晚自动构建 9 个 Role 镜像**,以便 **保持运行时产物最新且可回归** |
| 优先级 | P0 |
| 验收条件 | **Given** nightly workflow 触发 **When** member/runtime/tools 版本有效 **Then** 9 个 Role 构建完成 |

## 6. 功能需求

### 6.1 功能清单与优先级

| ID | 功能名称 | 优先级 | 依赖 | 描述 |
|---|---|---|---|---|
| F-001 | `ai-member-base` 基础镜像 | P0 | member/runtime/tools | 所有 Role 共享基础层 |
| F-002 | 9 个 Role 镜像 | P0 | F-001 + RoleDefinition | assistant / tech-lead / backend-dev / frontend-dev / qa / ux / devops / auditor / observer |
| F-003 | supervisord 组合启动 | P0 | member + runtime | 统一双进程入口 |
| F-004 | nightly 构建流水线 | P0 | CI | 每晚自动构建全部角色 |
| F-005 | tag 触发重建 | P1 | runtime/tools/member 发布 | 增量重建相关镜像 |
| F-006 | 漏洞扫描 | P0 | Trivy / Grype | 高危漏洞阻断 |
| F-007 | cosign 签名 | P0 | registry / key | 供应链签名 |
| F-008 | BOM 产出 | P0 | build pipeline | 依赖清单可追溯 |
| F-009 | 多架构构建 | P1 | buildx | amd64 + arm64 |
| F-010 | Role extras 装配 | P0 | L2-tools | 按角色装配差异工具集 |
| F-011 | IPC schema 兼容性检查 | P0 | member/runtime/core | member ↔ runtime 版本兼容 |
| F-012 | 发布通知 member-service | P1 | member-service | 新镜像可选启用,不自动升级 |

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| BR-001 | 一 Role 一镜像 | 镜像名固定为 `ai-member-<role>:<semver>` |
| BR-002 | 生产使用镜像 | 禁止 `latest` tag |
| BR-003 | 发现 Critical 漏洞 | 阻断发布 |
| BR-004 | RoleDefinition.image_variant 变化 | 后续构建必须对应新的镜像变体 |
| BR-005 | member/runtime IPC schema 不兼容 | 拒绝发布 |
| BR-006 | 发现签名或 BOM 缺失 | 视为未完成发布 |
| BR-007 | retired Role 镜像 | 归档至少 1 年 |

```

   ├─▶ supervisord 组合启动
   └─▶ extras 装配

构建流水线
   ├─▶ 兼容性检查
   ├─▶ 漏洞扫描
   ├─▶ BOM
```

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 类型 | 生命周期 |
|---|---|---|
| BaseImageRelease | 发布记录 | built → scanned → signed → published / retired |
| RoleImageRelease | 发布记录 | built → scanned → signed → published / retired |
| ImageBOM | 工件 | append-only |
| CompatibilityReport | 检查报告 | per build |

### 9.2 数据关系

```
ai-member-base
  └─ RoleImageRelease[]
       ├─ role
       ├─ semver / digest
       ├─ extras bundle
       ├─ ImageBOM
       └─ CompatibilityReport
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| 活跃镜像 tag/digest | 热存 | registry + release metadata |
| BOM / scan / sign 工件 | 长期 | 冷存可查 | 不随意删除 |
| retired Role 镜像 | ≥ 1 年 | archive | 到期后按审计策略处理 |
| nightly 中间构建工件 | 短期 | CI 工件保留策略 | 自动清理 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| role extras 依赖冲突 | 中 | 中 | 分层 bundle + 构建回归 |
| runtime / tools / member 版本漂移 | 中 | 高 | 版本钉住 + 兼容性 gate |
| 漏洞扫描频繁阻断 | 中 | 中 | base image 更新节奏 + 安全补丁直发 |
| registry 发布失败 | 中 | 高 | 重试 + backlog + 不自动升级 |

### 12.2 边缘风险

- 某些架构(如 arm64)依赖链与 amd64 不一致,造成构建漂移
- auditor / observer 这类特殊角色是否需要更强只读或收缩镜像
- nightly 大规模并行构建导致 CI 资源瓶颈

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| Auditor Role 是否需要特殊只读镜像 | L2 后 | member-images + governance |
| 多架构构建的最小支持集是否固定为 amd64/arm64 | L2 前 | SRE + member-images |
| 新镜像发布通知是否走 bus 还是 registry metadata pull | L2 后 | member-images + member-service |

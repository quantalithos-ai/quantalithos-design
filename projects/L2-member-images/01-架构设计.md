## 2. 业务背景与驱动力

> 校准来源：
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读：
> - 建议继续阅读该中间产物的“业务背景与驱动力”“架构目标”“当前阶段可接受取舍”和“架构非目标”小节，了解为何需要独立镜像域。

成员运行环境由 Method Library、Member、Runtime、Tools、角色 extras、base 与 seed 等多个 owner 的静态资产组合而成，却必须由下游通过一个固定、可验证的镜像入口消费。若定义来源、装配 revision、构建结果、资格和供给事实散落在脚本、builder、registry 或 Member Service 中，同名镜像无法证明对应同组输入，外部适配器成功也容易被误报为镜像可用。

本仓因此需要成为独立的成员镜像资产与构建产物供给 truth owner：把多来源静态资产收束成连续的 definition -> candidate -> eligibility -> availability 事实链，同时让 Role mapping、component、Artifact、运行时 live state 和 container lifecycle 留在各自 owner。

### 2.1 架构驱动力

| 驱动力 | 若不处理会破坏什么 |
|---|---|
| 多 owner 静态输入需要单一装配归责 | 同一 variant 会由不同来源组合，无法解释或重复构建 |
| Role mapping 需要唯一来源 | 本仓或下游会形成 hardcode / copy 的第二 mapping truth |
| 构建适配器与领域结果必须分离 | Request、job 或 push 成功会被误报为 candidate / eligible / available |
| 供应链资格需要连续来源 | Digest、provenance 与 applicable gate 会变成互不关联的标签 |
| 供给与消费生命周期必须分离 | Registry、Artifact、container 或 consumer 状态会反向改写镜像 truth |
| 跨仓消费需要依赖裁剪 | 物理装配会被错误升级为 package 依赖或 owner 转移 |

### 2.2 架构目标

| ID | 架构目标 | 必须确保成立的结构 |
|---|---|---|
| `AG-MI-001` | 承载独立且连续的成员镜像域真相 | Definition、candidate、eligibility、availability 均有唯一 owner 和可追历史 |
| `AG-MI-002` | 受控关联 Role 来源与 image variant / persona assembly identity | Mapping 只从正式 owner 进入，本仓不 hardcode 或复制正文 |
| `AG-MI-003` | 支撑完整 pinned 静态装配与显式派生历史 | Component、extras、base、seed 的必要引用完整、可验证且不可变 |
| `AG-MI-004` | 分离 build intent、input snapshot、external outcome 与 candidate formation | 接受或执行成功不自动形成候选，unknown 不被提升为成功 |
| `AG-MI-005` | 连续解释 digest、provenance、applicable gate 与 image eligibility | 候选输出能回指正式来源，适用 gate 缺失即 fail closed |
| `AG-MI-006` | 让 availability 历史与 pinned instantiable entry 稳定成立 | 下游无需猜版本或依赖 mutable selector |
| `AG-MI-007` | 守住 truth、snapshot、ref、adapter outcome 与 consumer truth 的边界 | 物理装配和消费不反转相邻 owner |
| `AG-MI-008` | 允许开放 seam 在 fail-closed 状态下演进 | 缺少 exact contract 时局部返回 gap，不伪装 ready，也不阻塞稳定语义设计 |

### 3.1 不可变约束

| ID | 约束 | 架构影响 |
|---|---|---|
| `IC-MI-001` | 不定义、复制或 fallback RoleDefinition / Role -> variant mapping truth | Method Library 保持唯一 owner，本仓只保存来源 binding / snapshot / validity conclusion |
| `IC-MI-002` | 不拥有 member、runtime loop、tool execution 或 capability registry truth | Component 被装入镜像不转移其语义与执行 owner |
| `IC-MI-003` | 不保存 secret、live memory、checkpoint、workspace live content 或 observed state | 镜像只承接静态模板、seed 与 build materialization |
| `IC-MI-004` | 不拥有 container lifecycle、Sandbox policy / backend / execution | Pinned entry 不表示容器已创建、健康或隔离已生效 |
| `IC-MI-005` | 不拥有 governance approval / policy truth、Artifact 通用 truth 或 observability backend | 只消费正式 ref / safe conclusion / gap，不复制正文 |
| `IC-MI-006` | 不允许 mutable selector、`latest`、猜版本或默认值补齐必要输入 | 完整 pin 是 resolved baseline 和 candidate 的前提 |
| `IC-MI-007` | 不把 adapter / event 接受或 registry 存在视为领域成功 | Candidate、eligibility、availability 分别由本仓规则成立 |
| `IC-MI-008` | Missing / stale / conflict / failed / unknown / gap 不得降级为 positive | 所有不可验证路径 fail closed，只冻结受影响 lane |
| `IC-MI-009` | Revision、attempt、evaluation 或 availability 历史不得原地覆盖 | 恢复通过新语境、supersede 或显式 transition 发生 |
| `IC-MI-010` | 非 Core 消费关系不得自动形成 compile dependency | Runtime / event / ref / adapter / fake 必须分别标注并裁剪 |
| `IC-MI-011` | Authority 未闭口时不得声明 event output、Artifact ref、consumer confirmation 或 readiness | `MI-UP-*` / `Q-MI-*` 只能产生 pending、blocked、unavailable 或 gap |

### 3.2 当前阶段取舍

| 事项 | 当前架构口径 |
|---|---|
| 运行架构维度 | 核心先保持单一受控维度与平台中立；multi-architecture 仍为 `Q-MI-002` conditional |
| Restricted / read-only variant | `Q-MI-001` 未裁定，不枚举 Role，不改变 Role / governance truth |
| 快速安全重建 | 仅为外围增强，仍必须经过全部 pin、provenance 与 applicable gate |
| Hardened base | `MI-UP-008` future-only，不进入当前核心图或完成分母 |
| Supply usage summary | `F-MI-E05` / `R-MI-010` future read-only projection，不反写 eligibility / availability |
| Builder / registry / evidence backend | `Q-MI-003` 保持 product-neutral adapter，不锁产品或部署形态 |
| Evidence kind / priority | `Q-MI-004` 未闭口，只要求 authority-driven applicable gate，不枚举当前 gate 清单 |
| 数值型质量目标 | 无正式 workload / measurement baseline，只使用离散结构判断，不设 SLA / SLO、时延、吞吐、大小或保留期硬值 |

### 3.3 架构非目标

本文不设计 Role / method 资产管理、member 主体与 persona live behavior、runtime loop、memory / checkpoint、tool execution、外部 MCP / A2A / API adapter、capability registry、container 编排、Sandbox execution、Artifact 通用生命周期、governance approval、observability backend、marketplace、产品 UI / CLI 或基础设施产品本体。字段、DTO、状态枚举、数据库、语言、crate、目录、测试用例与实施排期均属于后续 `02~07`，且必须等待相应 authority。

### 8.3 六类依赖与 seam

| 类型 | 关联对象 | 本仓用法 | 权限上限 |

本仓可以物理构建和存储镜像内容，但物理 materialization 不授予 component、template、policy、evidence 或 Artifact 的语义所有权。

### 9.2 按架构单元的数据边界

| 架构单元 | 拥有的 truth | Snapshot / ref | Forbidden body / write |
|---|---|---|---|
| BC-MI-01 | Definition、source validity、assembly baseline、revision / derivation | Mapping snapshot / ref、component / seed refs | External body、live input、mutable fallback |
| BC-MI-02 | Intent、attempt、local outcome、candidate formation | Immutable input snapshot、builder / registry / trigger refs | Job / log body、incomplete snapshot、adapter success as candidate |
| BC-MI-03 | Digest / provenance binding、gate evaluation、image eligibility | Policy / evidence snapshot、evidence / Artifact refs | Policy / approval / evidence / Artifact body、missing gate as pass |
| BC-MI-04 | Availability history、entry binding、local handoff / consumer gap | Immutable registry / Artifact refs、conditional consumer snapshot | Container / health / observed body、consumer state as local truth |
| BC-MI-05 | Ref / snapshot intake validity、derived gap / trace conclusion | LS-MI-01~04 的全部受控影子 | 创建 core positive state、projection / fake / cache 反写 |

### 9.3 一致性策略

| 关系 / 决策语境 | 一致性口径 | 失败上限 |
|---|---|---|
| Definition 与 source validity | 本地决策强一致 | Missing / stale / conflict / gap 时不形成 resolved definition |
| Variant revision 与完整 assembly baseline | 本地决策强一致 | Necessary pin 未共同成立时 revision 不进入 buildable 语境 |
| Intent、attempt 与 immutable snapshot | 本地决策强一致 | 无完整 snapshot 不交接 execution，保留 rejected / pending / blocked |
| External execution outcome -> candidate | Ref validity + 本地决策强一致 | Failed / unknown / invalid ref 时无 candidate / digest |
| Candidate -> digest / provenance | 本地决策强一致 | 来源链不完整时不进入 eligibility，记录 provenance gap |
| Eligibility 与 applicable gates | 本地决策强一致 | 任一 applicable input missing / failed / unverifiable 即 blocked / pending |
| Eligibility 与 Artifact handoff | 分域最终一致 | 保留 image eligibility 与 Artifact gap，不互相伪写 |
| Availability transition 与 pinned entry | 本地决策强一致 | 不产生 partial available / mutable entry，失败显式且原事实不变 |
| Local availability 与 consumer confirmation | 分域最终一致 | 记录 handoff / consumer gap，不回滚或提升 local truth |
| External snapshot refresh | 有来源的最终一致 | 标记 stale / unavailable，挂起新的 positive decision |
| Core truth -> derived view | 最终一致 | Projection 可重建并表达滞后，不得反写 truth |
| Revision / attempt / evaluation / availability history | 历史连续性约束 | 通过新语境、supersede / transition 恢复，不删除或覆盖旧事实 |

这里的强一致只约束本仓单个正式 decision context，不要求跨仓共享事务。Ref 用于跨 owner 回链，snapshot 用于固定判断语境，projection 用于只读解释；三者都不能替代外部 truth。

### 9.4 恢复与补偿原则

| 失败 | 允许的恢复 | 禁止的补偿 |
|---|---|---|
| External source unavailable / stale | 保留既有历史，阻断受影响的新 decision | Hardcode、`latest`、copied body、cached default |
| Partial local invariant | 整个 positive decision 不成立，显式 failed / blocked | Partial candidate / eligibility / available |
| Adapter timeout / unknown | 保留 attempt / unknown，通过新 attempt 解释恢复 | 推断成功或复用无来源 digest |
| Ref invalid / revoked | 标记失效并挂起依赖路径，保留原 binding history | 将 ref body 复制为永久本地 truth |
| Projection lag / rebuild failure | 标记 stale / rebuilding / unavailable，从 truth 重建 | 从 projection 回填核心状态 |
| Artifact / consumer gap | 分层记录 gap，等待 owner-side formal result | 自造 formal ref、launch、confirmation 或 readiness |
| Rollback / retire | 追加 availability transition，指向既有 eligible entry | 删除 candidate、重写 digest 或抹去旧 availability |

| `IX-MI-01` 定义与装配基线校准 / 读取 | 与 mapping、component / seed source 协作，即时判断 definition / revision 是否 resolved、complete、pinned、static-safe | 同步请求 / 响应类 | Missing / stale / conflict / incomplete / blocked；不写 partial positive |
| `IX-MI-02` 构建意图与候选形成 | Nightly / conditional input 经 external build / registry 延后形成 candidate 或明确失败 | 后台任务 / 延后承接；conditional event 仅为未来输入 | Intent / attempt 保持 pending / failed / blocked / unknown；新 attempt 恢复 |
| `IX-MI-03` Provenance、资格与 Artifact handoff | Candidate 汇聚 provenance / gate safe conclusion，并独立交接 Artifact 或形成 gap | 后台任务 / 延后承接 | Missing / failed / unverifiable gate -> blocked；handoff pending / rejected / unavailable |
| `IX-MI-04` Supply availability transition | 即时决定 publish / replace / rollback / retire 是否成立 | 同步请求 / 响应类 | 明确 rejected / blocked，原 availability 不变；恢复走新 transition |
| `IX-MI-05` Pinned entry 与 handoff / consumer gap 读取 | Member Service 在实例化前获得 immutable entry 或明确 gap | 同步请求 / 响应类 | Unavailable / contract-gap；不猜 ref、不声明 launch / confirmation |
| `IX-MI-06` 派生 trace、projection 与维护恢复 | 延后形成 / 重建 source trace、history view、gap 和 maintenance explanation | 后台任务 / 延后承接 | Stale / rebuilding / unavailable；派生失败不反写 core truth |

### 10.2 通信边界

- 同步边界只承诺即时领域判断，不承诺 build、gate、Artifact handoff 或 container work 已完成。
- Nightly、构建执行、provenance / gate evaluation、Artifact handoff、snapshot refresh 与 projection rebuild 由后台路径承接。
- `MI-UP-005` 关闭前，conditional event input 为 rejected / unavailable；即使关闭，也必须先验证 source authority，再形成本地 intent。
- 当前没有任何镜像域 outbound event；`MI-UP-009` 不能由 availability transition 或通知愿望代替。
- Registry callback、event arrival、adapter acceptance 与 consumer confirmation 均不能自动改变 local candidate、eligibility 或 availability。
- Exact transport、API、DTO、schema、topic、delivery、idempotency key、timeout 与 retry 算法属于后续设计。

本章不绘制单一交互时序图。六条交互是并列的边界类别而非一条必经 pipeline；将其串联会错误暗示所有 definition、build、gate、Artifact handoff、availability 与 consumer resolve 在一次运行时序中连续完成。

## 11. 关键技术选型

### 11.1 关键架构机制

| ID / 机制 | 解决的问题 | 采用理由 | 代价 / 约束 |
|---|---|---|---|
| `TM-MI-001` 向内防腐与正式 seam | External DTO / SDK / body / product 侵入核心 | 先转换为 ref / snapshot / safe conclusion，保护镜像 truth 与 owner | 增加 validation、translation、gap 和 parity 维护成本 |
| `TM-MI-002` Immutable pinned input snapshot | 构建输入随 external latest 漂移 | Attempt 必须绑定唯一、完整且确定的输入语境 | Snapshot 必须检查完整性、来源状态与不可变性 |
| `TM-MI-003` 分阶段领域判定 | Pipeline success 自动变成 eligible / available | Candidate、eligibility、availability 的前提、owner 与失败不同 | 增加显式中间结果和跨阶段 gap |
| `TM-MI-004` Digest / provenance content identity binding | 输出引用不能证明与 revision / input 一致 | Immutable digest 与完整 provenance 稳定识别 candidate | 任一来源不可回链即阻断后续 positive decision |
| `TM-MI-005` Authority-driven fail-closed gate | 未知或缺失 gate 被默认跳过 / 通过 | Applicable set 只由正式 authority 决定，异常不能产生 positive eligibility | Authority / evidence 不可用时 positive lane 降级为 pending / blocked |
| `TM-MI-006` Append / supersede / explicit transition history | Revision、attempt、evaluation 或 availability 原地覆盖 | Rollback、审计与 provenance 需要原语境持续可解释 | 增加历史量、superseding relation 与读取复杂度 |
| `TM-MI-007` Truth 与派生读取分离 | Catalog / trace / cache / report 反写领域 | Projection 可滞后和重建，核心 truth 仍唯一 | 读侧必须表达 stale / rebuilding / unavailable |
| `TM-MI-008` 即时判断与后台延后承接分离 | 长时 build / gate / handoff 被同步接口伪装完成 | 本地 decision 即时收口，外部工作保留 pending / unknown | Consumer 必须区分 accepted 与 completed |
| `TM-MI-009` Product-neutral external adapters | 基础设施产品决定领域语义 | 产品可替换，outcome 经本仓规则才能成为 local input | Adapter parity、错误映射和后续配置需独立维护 |
| `TM-MI-010` Image / Artifact / consumer state separation | Image ready 被误报为 Artifact / container / product ready | 三个 owner 分别成立，外部失败只形成 gap | 下游必须处理多层状态，不能依赖单一 ready 布尔值 |

### 11.2 采用边界

| 当前采用 | 当前不硬化 |
|---|---|
| Inward seams、pinned snapshot、staged decisions、digest / provenance、fail-closed gates、append history、projection separation、background handoff、neutral adapters、cross-domain state separation | Language、framework、DB、cache、queue、CI、builder、registry、scanner、signer、secret store、transport、schema、deployment product |
| Nightly 作为受控 intent 语义 | Scheduler / cron / workflow 产品和时间配置 |
| Conditional inbound event seam | Event family / topic / schema / positive consumer readiness / outbound event |
| Explicit history semantics | Full event sourcing、outbox、retention duration |
| Immutable image ref 语义 | Image format、registry layout、tag convention、platform matrix |

这些机制是后续实现必须保持的结构边界，不是已实现组件、已选产品或已通过验证的能力。当前也不存在任何真实 digest、provenance、gate report 或 qualification evidence 可由本章声明。

## 12. 备选方案与取舍

> 校准来源：
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读：
> - 建议继续阅读该中间产物的“当前主线方案”“方案路径比较”“不进入正式比较的方向”和“轻量取舍对照”小节。

### 12.1 当前主线

```text
Independent image-domain control plane
  + controlled definition / pinned assembly baseline
  + staged candidate / eligibility / availability decisions
  + immutable digest / provenance identity
  + append / supersede / explicit transition history
  + inward compile / runtime / event / ref / adapter / fake seams
  + synchronous local decisions + background external handoff
  + separate image / Artifact / consumer states
```

这里的 control plane 是架构责任描述，不表示已选择常驻服务、数据库、queue、CI 或 registry 产品。实现可以保持较薄、同置的承载，但不能丢失 truth、failure、gap 与 history 语义。

### 12.2 路径比较

| 方案 | 收益 | 代价 / 风险 | 结论 |
|---|---|---|---|
| 独立镜像域控制面 + staged decisions + external seams | Owner 唯一，各阶段 failure / rollback 可解释，产品可替换，pending 可局部挂起 | 需要显式 contexts、refs、snapshots、gaps、history 与 adapter parity | 采用 |
| 纯声明资产仓 + external pipeline 作为运行事实来源 | 仓结构简单，声明 review 直观 | Attempt、eligibility、availability / rollback 与 consumer gap 会散落在 CI / registry / scripts | 不采用；声明文件只能是实现载体之一 |
| 单一 image lifecycle state machine | 查询和顺序表面简单 | Adapter success 易自动推进，Artifact / consumer gap 污染 local state，unknown 难分层 | 不采用 |
| 每个阶段独立部署服务 | 故障隔离、独立伸缩与 ownership 显性 | 无 workload 依据，过早引入分布式 consistency、operation 与 recovery 成本 | 当前不采用；保留语义边界并允许同置 |
| Consumer-driven on-demand build / resolve | 低频 variant 可减少预构建库存 | 违反 nightly / 预构建方向，实例化被长时 build / gate 阻塞，无法预先提供 pinned entry | 不采用 current core |
| 完整 event-sourced control plane | History replay 与派生表达强 | 需要稳定 event taxonomy / ordering / replay contract；`MI-UP-005/009` 未闭口 | 当前不采用；只锁 append / supersede history semantics |

### 12.3 Owner 主导方案的排除

| 排除方向 | 排除原因 | 正确边界 |
|---|---|---|
| Artifact-centric image lifecycle | Artifact 通用 truth 不归本仓，也不能替代 image eligibility / availability | Image state 与 Artifact ref / gap 分域 |
| Member Service / container-centric supply truth | Container lifecycle 与 confirmation 不归本仓 | 本仓提供 pinned entry，consumer 管理运行 |
| Method Library-centric build ownership | Method Library 只拥有 Role / mapping truth | 本仓通过 runtime + ref 消费 mapping |
| Registry-as-source-of-truth | Registry 是技术 adapter / ref owner | Immutable registry ref + local availability history |
| Governance / scanner / signer owns eligibility | 外部 authority 只提供 applicable set / safe conclusion | BC-MI-03 形成 local image eligibility |
| Marketplace / product owns image catalog | 产品层不得反向定义镜像供给 | Future read-only consumption / listing 另行设计 |

当前方案牺牲了纯声明仓和单一状态机的表面简洁，也不提前获得每阶段独立伸缩或 full replay；换取的是完整镜像域 truth、阶段独立失败与恢复、稳定 pinned entry、产品中立和 owner 不反转。Future path 只有在正式 authority、scope、workload 或 measurement 到达后才能重开，不能从本章推导已排期或 ready。

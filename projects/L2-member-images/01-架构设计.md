## 1. 业务背景与驱动力

### 1.1 业务背景

member-images 不是普通 CI 仓,而是 L2 运行面的**产物真相层**。member-service 能启动的不是抽象的 Role,而是一个已经把 member 门面、runtime 大脑、tools 工具集、supervisord 启动编排和基础依赖装配好的镜像版本。它把 method-library 的 `RoleDefinition.image_variant` 与真实可运行工件接上,并把“怎么组装运行环境”的复杂度固定在构建期而不是运行期。

### 1.2 业务驱动力

**业务驱动力**:
- 平台需要让不同角色成员以不同能力边界启动,而不是所有成员共享同一臃肿镜像
- 审计与安全要求镜像来源、依赖、漏洞状态、签名都可追溯,否则无法为运行中的 AI 员工举证

**技术驱动力**:
- 需要统一 base image 复用,避免 9 个 Role 镜像各自漂移
- 需要把 tools extras、member/runtime 版本、IPC 兼容性、安全扫描与多架构构建收进同一条发布流水线

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 覆盖 | 9 个 Role 镜像 | 9/9 | CI |
| 可用性 | nightly 构建成功率 | 100% 样本角色 | CI |
| 安全 | Critical 漏洞通过数 | 0 | Trivy / Grype |
| 供应链 | BOM + 签名覆盖率 | 100% | 工件检查 |
| 兼容性 | member/runtime IPC 兼容率 | 100% 发布镜像 | compatibility gate |
| 运行时适配 | member-service 按 Role 拉起样本成功率 | 100% 样本验证 | E2E |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| Role extras 组合 | 高 | base + extras layering |
| member/runtime/tools 版本演进 | 高 | pin + compatibility gate |
| 安全基线增强 | 中高 | build pipeline security stages |
| 目标架构矩阵 | 中 | buildx matrix 抽象 |
| RoleDefinition.image_variant 变化 | 中 | resolver 契约与镜像命名解耦 |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **base image + role overlays + security pipeline**(当前) | 复用高、差异面清晰、便于治理 | 需要维护分层依赖 | ✅ |
| 每个 Role 独立全量 Dockerfile | 职责隔离表面清晰 | 重复太多、漂移高 | ❌ |
| 运行时按需动态装配工具 | 构建轻 | 启动慢、不可审计、不可重现 | ❌ |
| 单一全功能镜像 | 构建简单 | 角色边界模糊、体积膨胀 | ❌ |

**最终选择**:**共享 base image + Role overlay + 构建期安全门禁链**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| base / overlay 分层 | 共享大部分层,减少漂移 | 需要维护清晰的层边界 |
| 构建期而非运行期装配 | 启动快、结果可重现 | CI 复杂度提高 |
| 安全门禁必须阻断发布 | 供应链证据完整 | 某些夜构会因漏洞中断 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
member / runtime / tools / method-library / security
                    │
                    ▼
          ★ quantalithos-member-images ★
          - base image assembly
          - role overlays / extras
          - compatibility checks
          - scan / sign / BOM / publish
             │                 │
             │                 └────────▶ registry / audit artifacts
             └──────────────────────────▶ member-service pull & run
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 组装 `ai-member-base` 与 9 个 Role 镜像
- ✅ 固定 member/runtime/tools 版本组合与启动入口
- ✅ 执行兼容性检查、漏洞扫描、签名、BOM 产出
- ✅ 向下游暴露可拉取的 tag / digest / metadata

**不做什么**:
- ❌ 不实现 member/runtime/tools 业务逻辑
- ❌ 不决定 RoleDefinition 真相与业务语义
- ❌ 不执行容器启动、停止、恢复(member-service)
- ❌ 不托管运行时 secrets 或生产集群策略

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| member/runtime/tools 发布物 | 构建期必须可用 | 缺任一产物无法装配 | 阻断构建 |
| method-library / identity image_variant | 99.9% | Role → image 映射漂移 | 锁定已知版本,不发布新镜像 |
| image registry | 99.9% | 发布不可达 | backlog / retry / 不自动升级 |
| Trivy / Grype / cosign | 高 | 无法完成门禁 | 阻断发布 |
| CI / buildx | 高 | 多架构构建失败 | 手工重跑 / 局部回退 |

### 4.4 关键依赖风险

- 若 base image 与 Role overlay 边界失控,9 个镜像会快速演变为 9 条独立产品线
- 若 compatibility gate 不严格,member/runtime 版本不兼容会在运行期才爆炸
- 若安全门禁被跳过,member-images 会成为整个平台最脆弱的供应链入口

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Base Assembly | 核心域 | 构建共享基础运行层 |
| Role Packaging | 核心域 | 为不同 Role 叠加 extras 与差异配置 |
| Release Validation | 核心域 | 兼容性检查、扫描、签名、BOM |
| Publish & Retention | 支撑子域 | 推送 registry、保留与归档 |
| Build Orchestration | 支撑子域 | nightly / on-tag / matrix workflow |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Base | 组装基础镜像与共用入口 | BaseImageRelease |
| Role | 组装角色差异层 | RoleImageRelease / ExtraBundleRef |
| Validation | 校验兼容性与安全门禁 | CompatibilityReport / ScanReport |
| SupplyChain | 签名、BOM、digest 元数据 | ImageBOM / SignatureRef |
| Publish | 推送与保留策略 | PublishRecord |

### 5.3 上下文映射关系

- member/runtime/tools → Base / Role: **Customer-Supplier**，上游产物变化驱动新镜像生成
- method-library → Role: **Conformist**，镜像侧遵从 `image_variant` 真相
- member-service ← Publish: **Customer-Supplier**，下游消费 tag/digest,不改写构建逻辑
- security / audit ← Validation / SupplyChain: **Open Host Service**，产出扫描、BOM、签名证据

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| ai-member-base | 所有 Role 共享的基础镜像层 | Base |
| Role overlay | 在 base 之上叠加的角色差异层 | Role |
| ExtraBundleRef | 某 Role 对应的 tools extras 引用 | Role |
| CompatibilityReport | member/runtime/tools 组合兼容性报告 | Validation |
| ImageBOM | 某镜像版本完整依赖清单 | SupplyChain |
| PublishRecord | 镜像推送、签名、digest 与保留策略记录 | Publish |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
CI workflow / tag trigger
         │
         ▼
┌───────────────────────────────────────────┐
│      member-images build orchestrator     │
│  base build / role build / validate / sign│
└───────────┬──────────────┬────────────────┘
            │              │
            ▼              ▼
      buildx runners   scan/sign/BOM tools
            │              │
            └──────┬───────┘
                   ▼
              image registry
                   │
                   ▼
            member-service pull
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| build orchestrator | 组织 base/role 构建流程 | CI workflow + shell | 构建控制面 |
| buildx runner | 构建 amd64/arm64 镜像 | Docker buildx | 高 CPU / cache 需求 |
| scan/sign step | 漏洞扫描、签名、BOM | Trivy / Grype / cosign | 安全门禁 |
| image registry | 存放发布镜像 | 外部 registry | 长期保留 |
| member-service consumer | 拉取镜像并启动容器 | 下游服务 | 只读消费 |

### 6.3 通信方式与选择理由

| 通信场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| CI → buildx | 标准容器构建调用 | 自写构建器 | 保持生态兼容与多架构支持 |
| build pipeline → scan/sign tools | 标准 CLI / action | 自研安全流程 | 降低供应链工具维护成本 |
| registry → member-service | 镜像 pull + digest | 手工分发 tarball | 满足运行时直接拉起与版本定位 |
| member-images → 下游通知 | metadata / release record | 运行时现场探测 | 把版本可见性前移到发布阶段 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| BaseImageRelease metadata | member-images | SRE / audit / publish logic |
| RoleImageRelease metadata | member-images | member-service / SRE |
| CompatibilityReport | member-images | build gate / maintainers |
| ImageBOM / signature refs | member-images | security / audit |

### 6.5 部署拓扑

- 构建平面运行在 CI 环境,不是常驻在线服务
- registry 为长期制品存储
- 构建结果由 member-service 在运行期按需拉取,不做内嵌分发

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
source artifacts(member/runtime/tools)
                │
                ▼
        base assembly
           │
           ├─▶ role packaging
           ├─▶ compatibility validation
           ├─▶ scan / sign / BOM
           └─▶ publish / retention
```

### 7.2 层间约束规则

- Base 层只承载所有 Role 共享内容,不得偷偷塞入单角色特化依赖
- Role overlay 只做差异化,不得回写 base 或复制共用逻辑
- Validation gate 失败时必须阻断 publish,不允许“先发再说”
- Publish 层只发布已签名且有 BOM 的镜像
- member-service 只消费发布结果,不介入构建细节

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| ArtifactSource | build domain | member/runtime/tools release adapters |
| ExtraBundleResolver | role packaging domain | tools metadata adapter |
| CompatibilityChecker | validation domain | schema/version gate implementation |
| SecurityGate | validation domain | Trivy / Grype / cosign adapters |
| PublishSink | publish domain | registry / metadata writer |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中高(member/runtime/tools/method-library) |
| 传出耦合 | 中(registry / CI / scan/sign tools) |
| 不稳定性 | 中 |
| 抽象度 | 中(base / role / validation / publish 分层清晰) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者(写入方) | 消费者(读取方) | 一致性级别 | 风险标注 |
|---|---|---|---|---|
| BaseImageRelease | member-images | role build / SRE | 强一致(单次构建事实) | — |
| RoleImageRelease | member-images | member-service / SRE | 强一致(单次构建事实) | — |
| ExtraBundleRef | tools 为真相,member-images 消费 | role build | 最终一致 | tools 元数据漂移需 gate |
| CompatibilityReport | member-images | validation gate / maintainers | append-only | 未阻断则运行期风险高 |
| ImageBOM / SignatureRef | member-images | audit / security | append-only | 丢失则供应链不可追溯 |

### 8.2 一致性层次

- **Level 1 · 构建内强一致**:单次 build 中 base、role、scan、sign、publish 形成一致产物链
- **Level 2 · 上游产物最终一致**:member/runtime/tools tag 更新后触发重建,镜像与源码版本通过 pin 保持最终一致
- **Level 3 · 运行期消费一致性**:member-service 通过 semver/digest 拉取指定镜像,与构建期 metadata 对齐

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| base 构建成功但 role 构建失败 | role overlay 失败 | 阻断该 Role 发布并保留 base 结果 | `build_id + role` |
| 扫描失败 | Critical 漏洞命中 | 不发布并记录失败工件 | `build_id + digest` |
| 签名失败 | cosign 失败 | 阻断 publish | `build_id + digest` |
| registry 推送失败 | push error | 重试或 backlog,不通知 member-service | `build_id + digest` |

## 9. 关键技术选型

### 9.1 base image + role overlay 分层

| 维度 | 内容 |
|---|---|
| 当前选择 | `ai-member-base` + 各 Role overlay |
| 备选方案 | 每个 Role 全量 Dockerfile |
| 选择理由 | 共享 member/runtime/tools 主体层,把角色差异限制在 extras 与局部配置 |
| 演进路径 | 后续可继续细分到 capability bundle 层 |
| 不可逆程度 | 中高 |

### 9.2 buildx 多架构构建

| 维度 | 内容 |
|---|---|
| 当前选择 | buildx 构建 amd64 + arm64 |
| 备选方案 | 单架构发布 |
| 选择理由 | 运行环境异构是现实需求,构建期一次解决比运行期补救更稳 |
| 演进路径 | 依需求缩放支持矩阵 |
| 不可逆程度 | 中 |

### 9.3 扫描 + 签名 + BOM 供应链门禁

| 维度 | 内容 |
|---|---|
| 当前选择 | Trivy / Grype + cosign + BOM |
| 备选方案 | 仅构建成功即发布 |
| 选择理由 | member-images 是运行入口工件,若无供应链门禁,后续审计与事故追查都会失效 |
| 演进路径 | 后续可增强 provenance / attestation |
| 不可逆程度 | 高 |

### 9.4 semver/digest 双重定位

| 维度 | 内容 |
|---|---|
| 当前选择 | 语义版本 + digest |
| 备选方案 | 只用 tag |
| 选择理由 | 既保留人类可读版本,又保留不可变定位 |
| 演进路径 | 下游逐步更偏向 digest pin |
| 不可逆程度 | 中 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:base + overlays + security gates(当前) | 方案 B:全角色单镜像 | 方案 C:每角色独立全量构建 |
|---|---|---|---|
| 角色边界 | 高 | 低 | 高 |
| 复用性 | 高 | 高 | 低 |
| 漂移风险 | 中低 | 高 | 高 |
| 构建复杂度 | 中 | 低 | 中高 |
| 适配 N4 | 高 | 低 | 中 |

### 10.2 最终选择与理由

选择 A,因为 L2-member-images 既要支持 Role 差异,又要控制供应链与维护成本。B 会把角色边界打平,与 method-library 的 RoleDefinition 设计冲突；C 则把重复劳动和漂移风险放大。A 是复用、边界和治理三者之间的平衡点。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 重试 | registry push / 拉取元数据失败可有限重试 |
| 降级 | 某 Role 构建失败不应污染已通过 Role 的历史版本 |
| 隔离 | base build、role build、scan/sign、publish 分阶段隔离 |
| 回退 | 发布失败时保留上一个稳定 digest 供 member-service 继续使用 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | build start / role matrix / scan result / sign result / publish result |
| 指标 | build duration / role success rate / scan failures / push latency |
| 追踪 | build_id 贯穿 base → role → scan → sign → publish |
| 健康检查 | 关注 nightly 成功率、registry 可达性、工件完整性 |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| 供应链 | scan + sign + BOM 必过 |
| 凭据管理 | registry / cosign key 在 CI secret / KMS 管理,不进镜像 |
| 最小暴露 | 镜像不内置业务 secrets,运行时注入 |
| 版本控制 | 生产禁止 latest,用 semver/digest |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | 构建矩阵、目标架构、scan 阈值、registry 目标全部外部化 |
| 环境隔离 | dev / staging / prod 可用不同 registry / promotion 策略 |
| 动态更新 | nightly / on-tag / manual promote 策略可调 |
| 配置五要素 | 每项构建参数明确 name / type / default / constraint / source |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| nightly role build completeness | 9/9 | CI | N4 Exit Criteria |
| security artifact completeness | 100% | 工件检查 | README |
| compatibility gate coverage | 100% | CI gate | README |
| member-service sample launch readiness | 100% 样本角色 | E2E | L2 运行面需求 |

**端到端交付分解**(镜像发布必须形成完整供应链证据):

```
一次可发布镜像 = 构建成功
             + 兼容性检查通过
             + 漏洞扫描通过
             + BOM 生成
             + 签名完成
             + 推送 registry 成功
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| auditor / observer 是否需要更强只读镜像未定 | 影响 role overlay 粒度 | P1 |
| 多架构支持矩阵可能继续扩张 | 影响 CI 成本 | P1 |
| 发布通知模型(bus vs metadata pull)未定 | 影响与 member-service 联动方式 | P1 |
| provenance / attestation 尚未展开 | 影响更高等级供应链举证 | P2 |

### 12.2 演进触发条件(可量化)

| 指标 | 阈值 | 演进动作 |
|---|---|---|
| role extras 冲突频发 | > 阈值 | 拆细 bundle / 重构 overlay |
| 某架构构建失败率异常 | 持续 1 周 | 调整目标架构或修复专用依赖 |
| 安全门禁阻断率过高 | 持续 1 周 | 升级 base 或优化补丁节奏 |
| member-service 启动失败与镜像问题相关 | > 阈值 | 强化 compatibility gate 与 smoke test |

### 12.3 演进步骤

```
阶段 1: base image + 9 个 Role + nightly build 跑通
   └─ 可停止点:member-service 可拉起样本角色

阶段 2: scan / sign / BOM / compatibility gate 全量收口
   └─ 可停止点:供应链证据链闭环

阶段 3: 多架构稳定 + 更细粒度 Role overlay
   └─ 可停止点:支持更复杂角色矩阵与企业发布要求
```

### 12.4 目标架构

member-images 的目标不是“把东西打包出来”这么简单,而是成为 **L2 运行面唯一可信的镜像产物层**:Role 语义、工具裁剪、版本兼容、安全证据和可拉起性都在这里被一次性固化。未来角色再增加,应增加的是 overlay 与验证规则,而不是重新发明构建逻辑。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| role extras 依赖冲突 | 中 | 中 | overlay review + 构建回归 |
| member/runtime/tools 版本漂移 | 中 | 高 | compatibility gate + pin |
| 漏洞扫描阻断频繁 | 中 | 中 | base 升级节奏 + 快速补丁通道 |
| registry push 失败 | 中 | 高 | retry + backlog + 不自动切换 |

### 13.2 边缘风险

- arm64 与 amd64 的依赖表现差异导致隐性功能不一致
- 特殊 Role(如 auditor)需要更严格镜像裁剪,当前模型不够细
- CI 资源瓶颈导致 nightly 大面积超时,影响 N4 交付节奏

### 13.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| Auditor Role 是否用特殊只读镜像 | L2 后 | member-images + governance |
| 多架构最小支持集是否固定为 amd64/arm64 | L2 前 | SRE + member-images |
| 发布通知是 bus 事件还是 metadata pull | L2 后 | member-images + member-service |

## 14. 上线策略

### 14.1 灰度方案

```
阶段 1: 先构建 ai-member-base + assistant / backend-dev 两个样本角色
阶段 2: 扩到 9 个 Role,验证 nightly 与安全门禁
阶段 3: 接入 member-service 样本环境按 Role 拉起
阶段 4: 推广到多架构与完整发布流水线
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| 新镜像无法启动 member/runtime | S 级 | 回滚到上一个稳定 digest |
| 扫描/签名链异常 | A 级 | 停止新镜像发布,保留旧稳定版本 |
| 某 Role extras 构建冲突 | B 级 | 回退该 Role overlay,不影响其他 Role |
| 多架构某一分支异常 | B 级 | 暂停该架构发布,保留其他架构 |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| nightly build success rate | < 9/9 | major |
| scan critical count | > 0 | critical |
| signature/BOM completeness | < 100% | major |
| member-service sample launch failure | > 阈值 | major |
| registry push latency/fail rate | > 阈值 | warning |

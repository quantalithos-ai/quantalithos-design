## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L2-member-images` 不是 `member` 主体真相仓,也不是 runtime 执行仓,更不是简单的 prompt 模板文件夹。它是 **“成员镜像资产层 / persona-image 供给层”**。

你可以把它理解成:
- 平台当前有哪些正式可用的成员镜像
- 一个成员镜像默认带哪些 persona、prompt、toolset、policy overlay、memory seed、workspace seed
- 这些镜像怎样和 role、method、capability、runtime 初始化动作衔接
- 镜像怎样版本化、派生、启用、冻结和退役

这些事情,都由 `L2-member-images` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L2-member-images`,这些成员装配事实就会散落在:
- `member` 各自维护的初始化字段里
- `identity` 附带的 role 元信息里
- runtime 各自拼装的 startup prompt / workspace 初始化逻辑里
- `method-library` 与 `capability-hub` 下游手工拼接的 persona/tool/policy 组合里
- 各类测试脚本、seed 文件和手工配置里

结果就会出现:
- “某类成员到底该长什么样”没有统一正式模板
- role、persona、toolset、policy、workspace seed 会在不同仓逐渐漂移
- 成员实例和镜像模板混层,难以判断当前运行态是模板定义还是运行期偏移
- 派生镜像、版本升级和批量替换缺乏正式主线
- 后续 member/runtime 初始化只能靠人工拼接

所以 `L2-member-images` 必须独立存在,作为:
> **把成员 persona、prompt、工具装配、策略覆盖和初始化材料正式化为可版本化、可派生、可实例化的镜像资产层。**

### 1.3 新人最容易混淆的几个词

#### MemberImage
就是:
> 一个正式成员镜像模板。

它不是一个已存在的 `Member` 实体。

#### ImageRoleBinding
就是:
> 某个镜像适配哪些 role 的声明。

它不是 `identity` 里的 role truth 本体。

#### ImagePersona
就是:
> 镜像默认的人格、语气、交互风格与 prompt seed。

它不是运行中的 live persona state,也不是 conversation history。

#### ImageToolset
就是:
> 镜像默认挂接的一组工具和能力引用。

它不是 capability-hub 的 capability contract truth。

#### MemorySeed
就是:
> 镜像初始化时提供的记忆种子或记忆引用。

它不是 live memory store。

#### WorkspaceSeed
就是:
> 镜像初始化时提供的工作区种子、starter files 或 starter refs。

它不是 active workspace truth。

#### ImageDerivation
就是:
> 一个镜像从另一个镜像派生出来的版本或变体关系。

它不是 member 实例生命周期本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L2-member-images/02` 时,先收稳以下前提:
- `L2-member-images` 不应按 prompt / tools / workspace / avatar 横向平铺理解,而应按成员镜像装配主链责任拆
- member-images 至少应拆成“镜像定义与身份适配 / Persona 与交互种子装配 / 工具能力与策略覆盖装配 / 记忆与工作区初始化材料 / 版本派生与实例化出口”五个主要部分
- member-images 自己拥有的真相不是 member 实例、identity role truth、runtime live state 或 capability contract,而是 image definition / seed / overlay / derivation / instantiation 这类镜像资产真相
- `L2-member-images` 只能为 member、runtime、conversation/UI 等系统提供可实例化模板,不能替这些系统持有各自运行态真相
- 02 的重点不是“列有哪些默认 prompt / 文件 / 能力”,而是先把“成员镜像层在平台里到底是什么、和 identity/member/runtime/method-library/capability-hub 怎么分层”讲清楚
- persona seed、memory seed、workspace seed、policy overlay、toolset 装配不是零散配置,而是镜像主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的成员镜像心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,一个 AI 成员并不只是“有个名字”。用户真正需要的不是“启动时给他塞一点 prompt”,而是:
- 某类成员默认应该长成什么样
- 它适配哪些 role / method / capability / policy 组合
- 它启动时带什么 persona、工具集、memory seed、workspace seed
- 这些模板可以被版本化、派生、启用、替换和批量实例化

如果把这些逻辑分别散落到:
- `member` 当前实例字段
- `identity` 的角色信息
- runtime 本地 startup 逻辑
- capability-hub / method-library 的下游手工绑定

系统会快速退化成:
- 模板与实例混层
- 相同角色的成员在不同场景下表现不一致
- 派生和升级没有正式链路
- 工具装配、策略覆盖、记忆与工作区种子彼此漂移
- 后续需要重新生成成员时无法稳定复用同一份模板资产

因此,本概要设计的任务就是:
> **把 `L2-member-images` 写成一个新人也能看懂的“成员镜像资产层”,而不是把 persona、prompt、toolset、memory、workspace 各写在不同地方。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 成员模板统一性 | 分散在 member/runtime/seed 脚本 | 正式 MemberImage 主线 | 需正式收敛 |
| role → image 绑定 | 手工拼接风险高 | ImageRoleBinding 统一主线 | 需固定边界 |
| tool/policy 组装 | 下游漂移风险高 | image toolset / overlay 正式化 | 需正式建模 |
| memory/workspace 初始化 | 分散 | seed 可版本化且可实例化 | 需形成正式资产 |
| 派生与替换 | 无统一版本链 | derivation / publish / retire 主线 | 需收稳演进机制 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把成员模板从一堆零散启动配置提升为正式可管理、可派生、可实例化的资产,以保证不同成员类型长期一致可控
- **技术问题**:MemberImage、ImagePersona、ImageToolset、MemorySeed、WorkspaceSeed、ImageDerivation 与 identity / member / runtime / method-library / capability-hub 之间的边界如何稳定建模,并形成统一装配主链

- 不在本文替代 capability-hub contract truth
- 不在本文持有 conversation history 或 live memory 正文

## 4. 约束条件

### 4.1 技术约束

- 所有正式镜像都必须以 MemberImage 进入主线
- image role binding 只能引用 role truth,不能复制或改写 role truth
- toolset / policy overlay 只能装配 capability / policy 引用,不能发明 contract truth
- memory seed / workspace seed 只能提供初始化材料,不能直接持有 live state
- image 派生与版本链必须显式可追溯,不能依赖脚本隐式覆盖

### 4.2 资源约束

- 镜像数量和派生层次会持续增长,必须接受模板树与版本链扩张
- starter files / workspace seed / prompt bundle 不能无限长胖,否则初始化成本会迅速上升
- 镜像 catalog 查询会高频发生,索引复杂度必须受控

### 4.3 时间约束

- 当前阶段先收稳镜像资产主链,而不是先做复杂的自动生成或高级 persona 演化能力
- definition、persona/tool/policy 装配、memory/workspace seed、derive/instantiate 五条主线必须优先稳定,否则后续 member/runtime 接入会长期漂移

### 4.4 合规约束

- image 不能包含未经批准的 capability / policy 组合
- memory seed / workspace seed 不得混入运行时秘密或不可审计状态
- retire 后镜像不得继续被默认实例化
- 派生和替换必须留正式版本证据

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| member images | 中高 | 多角色 / 多场景成员模板增长 |
| derived images | 高 | 组织级变体与实验派生需求 |
| memory/workspace seeds | 高 | 初始化材料累积 |
| image catalog queries | 高频 | member/runtime/UI 高频消费 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ identity / method / hub     │
                    │ - role / method / capability│
                    │ - policy / config inputs    │
                    └────────────┬───────────────┘
                                 │ image assembly input
                                 ▼
                    ┌────────────────────────────┐
                    │ L2-member-images          │
                    │ - image / seed / overlay  │
                    │ - version / derive        │
                    └────────────┬───────────────┘
                                 │ instantiate / catalog / summary output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ member / runtime           │   │ conversation / UI / console│   │ artifact / observability   │
│ - instantiate / bootstrap  │   │ - image display / summaries│   │ - version / activation refs│
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L2-member-images` 自己负责镜像定义、persona/tool/policy/memory/workspace 装配、版本与派生、实例化出口
- `identity`、`method-library`、`capability-hub` 提供角色、方法、能力和策略的来源输入,但 member-images 不拥有这些 source truth
- `member` / `runtime` 消费 image 结果并实例化或初始化运行上下文
- `conversation` / UI / console 只消费 image 摘要和只读展示材料
- 这个仓的角色不是“成员已经是什么”,而是“成员应该如何被装配出来”

所以 `L2-member-images` 在全局里的角色是:
> **把成员 persona、prompt、工具装配、策略覆盖和初始化材料统一沉淀为可版本化、可派生、可实例化的镜像资产层。**

### 5.3 系统边界

**做什么**:
- 定义 MemberImage
- 管理 role binding / persona seed / prompt style / toolset / policy overlay
- 管理 memory seed / workspace seed / starter refs
- 管理 image version / derivation / publish / retire
- 提供 instantiate / catalog / summary 出口

**不做什么**:
- 不持有 Member 正式实例真相
- 不持有 role truth / capability contract / live memory / workspace truth
- 不直接推进 runtime 执行状态
- 不替代 conversation history 或 UI state

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| identity / role catalog | 99.9% | role ref 缺失时阻断 image publish,不伪造 role |
| method-library | 99.9% | method/profile 缺失时降级到 image 仍可读但不可发布 |
| capability-hub | 99.9% | toolset/overlay 缺能力 ref 时阻断激活或实例化 |
| member / runtime | 99.9% | 下游不可用不影响 image truth,但 instantiate backlog 需留痕 |
| storage / bundle assets | 99.9% | seed bundle 丢失时阻断实例化,不伪造默认材料 |

### 5.5 关键依赖风险

- image 与 role/method/capability 漂移会让成员模板长期失真
- memory/workspace seed 若和 live state 混层,会污染运行态与归档态边界
- toolset/policy overlay 若越权引用 capability/policy,会直接绕过上游治理主线
- 派生链失控会造成镜像树不可维护
- member/runtime 若直接绕过 image 层自行拼装,模板资产价值会被削弱

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把 prompt / tools / memory / workspace 横向平铺。  
> 它按 **成员镜像装配主链职责 + 定义 / persona / capability / seed / instantiation 差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象和机制,共同支撑同一段镜像资产主链。

#### 镜像定义与身份适配部分

- **它是什么**: 这是 `L2-member-images` 的模板真相入口层,一起回答“平台到底有哪些正式成员镜像”
- **为什么单独有它**: 如果没有独立 image 定义层,member 的实例状态、identity 的 role 视图和 runtime 的初始化逻辑会直接混到一层
- **负责什么**:
  - 定义 `MemberImage`
  - 定义 image metadata / usage scope / image status
  - 定义 role binding 与适配范围
- **不负责什么 / 容易混淆点**:
  - 不持有 Member 正式实例真相
  - 不持有 role truth 本体
  - 不负责 runtime live state
  - 最容易和 Member、identity role catalog、实例化结果混淆
- **与其他部分交互**:
  - 下游: persona 装配、toolset/overlay、memory/workspace seeds、实例化出口
  - 外部: identity / member / runtime / UI
  - 交互类型: template definition 型 + role adapt 型
- **后续详细设计展开点**:
  - MemberImage 模型
  - usage scope / role binding 主线

#### Persona 与交互种子装配部分

- **它是什么**: 这是 member-image 的人格与交互起始层,一起回答“这个镜像默认表现成什么样”
- **为什么单独有它**: persona、prompt、tone 是成员差异的重要来源,但又不能和运行中的 conversation/live persona 混成一层
- **负责什么**:
  - 定义 ImagePersona
  - 定义 default prompt / style / tone / starter behaviors
  - 为实例化提供 persona seed bundle
- **不负责什么 / 容易混淆点**:
  - 不持有 conversation history
  - 不持有 live runtime persona state
  - 不直接生成对话真相
  - 最容易和 conversation history、system prompt、runtime live state 混淆
- **与其他部分交互**:
  - 上游: 镜像定义与身份适配部分
  - 下游: 实例化出口 / UI 展示 / runtime bootstrap
  - 交互类型: persona seed 型 + interaction style 型
- **后续详细设计展开点**:
  - prompt/style bundle
  - persona seed / starter behavior 主线

#### 工具、能力与策略覆盖装配部分

- **它是什么**: 这是镜像默认能力装配层,一起回答“这个成员默认带什么工具和约束”
- **为什么单独有它**: toolset / policy overlay 不是 persona 附件,也不是 capability contract / governance policy 真相,必须单独治理
- **负责什么**:
  - 定义 image toolset
  - 绑定 capability refs
  - 绑定 policy overlay / provider preference / restriction
- **不负责什么 / 容易混淆点**:
  - 不发明 capability contract truth
  - 不替代 governance policy 真相
  - 不替代 runtime access decision
  - 最容易和 capability-hub contract、governance rule、本地工具配置混淆
- **与其他部分交互**:
  - 上游: capability-hub / method-library / governance 输入
  - 下游: runtime / member instantiation
  - 交互类型: capability binding 型 + overlay 型
- **后续详细设计展开点**:
  - image toolset / overlay / provider preference 模型

#### 记忆与工作区初始化材料部分

- **它是什么**: 这是镜像的启动材料层,一起回答“首次拉起时给它什么上下文材料”
- **为什么单独有它**: memory seed / workspace seed 最容易被误当成运行态真相,必须明确分出“初始化材料”和“live state”的边界
- **负责什么**:
  - 定义 memory seed
  - 定义 workspace seed / starter files / starter refs
  - 定义初始化 bundle 引用
- **不负责什么 / 容易混淆点**:
  - 不持有 live memory store
  - 不持有 active workspace truth
  - 不持有 runtime 中途产生的新文件状态
  - 最容易和 live memory、workspace truth、artifact outputs 混淆
- **与其他部分交互**:
  - 上游: method-library / artifact / source refs
  - 下游: runtime / member instantiate / UI preview
  - 交互类型: bootstrap seed 型 + starter material 型
- **后续详细设计展开点**:
  - memory/workspace seed bundle
  - starter refs / integrity 主线

#### 版本、派生与实例化出口部分

- **它是什么**: 这是镜像演进与下游交付层,一起回答“镜像怎样演进并交给下游使用”
- **为什么单独有它**: 镜像不是静态模板,有版本、派生、publish、retire 与 instantiate。若不单列,版本链、派生链和实例化出口会混成一锅
- **负责什么**:
  - 管理 image version / derivation / inherit / fork
  - 管理 publish / activate / retire
  - 提供 instantiate / materialize hooks 与 catalog output
- **不负责什么 / 容易混淆点**:
  - 不等于 member lifecycle
  - 不直接修改实例化后的 member / runtime live state
  - 不等于 UI catalog 展示本体
  - 最容易和 member lifecycle、publish 实例状态、历史对话版本混淆
- **与其他部分交互**:
  - 上游: 前四个主要部分
  - 下游: member / runtime / conversation / UI / observability / artifact
  - 交互类型: versioning/derivation 型 + instantiate 出口型
- **后续详细设计展开点**:
  - version / derive / retire 状态机
  - instantiate / materialize contract

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ identity / method / hub     │
                    │ - role / method / capability│
                    │ - policy / config inputs    │
                    └────────────┬───────────────┘
                                 │ image assembly input
                                 ▼
                    ┌────────────────────────────┐
                    │ L2-member-images          │
                    │ - image / seed / overlay  │
                    │ - version / derive        │
                    └────────────┬───────────────┘
                                 │ instantiate / catalog / summary output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ member / runtime           │   │ conversation / UI / console│   │ artifact / observability   │
│ - instantiate / bootstrap  │   │ - image display / summaries│   │ - version / activation refs│
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L2-member-images` 自己负责“定义成员镜像”“装配 persona/toolset/policy/memory/workspace seeds”“管理 version/derivation”“输出实例化入口和目录摘要”
- `identity` / `method-library` / `capability-hub` 的交互主要落在 **镜像定义与身份适配部分** 与 **工具、能力与策略覆盖装配部分**,为 image 提供 role / method / capability / policy 来源输入
- `member` / `runtime` 的交互主要落在 **记忆与工作区初始化材料部分** 与 **版本、派生与实例化出口部分**,消费 image bundle 完成实例化和启动
- `conversation` / UI / console 的交互主要落在 **Persona 与交互种子装配部分** 与 **版本、派生与实例化出口部分**,消费 image 摘要与展示材料
- `artifact` / observability 的交互主要落在 **记忆与工作区初始化材料部分** 与 **版本、派生与实例化出口部分**,消费 starter refs、activation 结果与版本链证据

### 7.3 分模块交互说明(逐个写)

#### 与 `identity` 的交互

```text
┌────────────────────────────┐
│ identity                   │
│ - role truth / catalog     │
└────────────┬───────────────┘
             │ role input
             ▼
┌────────────────────────────┐
│ member-images              │
│ - MemberImage              │
│ - ImageRoleBinding         │
└────────────────────────────┘
```

- `identity` 是 **role 来源输入方**
- **交互类型**: role binding 输入型交互
- **主流程位置**: image draft、publish、retire、instantiate 时进入主流程
- **交互解释**:
  - member-images 只引用 role truth
  - role binding 只表达适配关系
  - 不复制也不改写 role truth
- **高风险异常流**:
  - image role binding 漂移后继续被实例化
- 后续 `03-详细设计.md` 继续展开:
  - role binding contract
  - image publish precheck 主线

#### 与 `method-library / capability-hub` 的交互

```text
┌────────────────────────────┐
│ method-library / hub       │
│ - method / policy / cap    │
└────────────┬───────────────┘
             │ assembly input
             ▼
┌────────────────────────────┐
│ member-images              │
│ - toolset / overlay        │
│ - provider preference      │
└────────────────────────────┘
```

- 它们是 **能力与方法来源输入方**
- **交互类型**: capability / policy / method 输入型交互
- **主流程位置**: image 装配、publish 校验、instantiate 预检查时进入主流程
- **交互解释**:
  - image 只装配 refs / overlays
  - capability-hub 和 method-library 才持有 source truth
  - image 不发明 contract truth
- **高风险异常流**:
  - image toolset 带入 capability-hub 不允许的能力
- 后续 `03-详细设计.md` 继续展开:
  - toolset / overlay contract
  - image capability validation 主线

#### 与 `member / runtime` 的交互

```text
┌────────────────────────────┐
│ member-images              │
│ - image bundle             │
│ - memory/workspace seed    │
└────────────┬───────────────┘
             │ instantiate/bootstrap output
             ▼
┌────────────────────────────┐
│ member / runtime           │
│ - member creation          │
│ - runtime bootstrap        │
└────────────────────────────┘
```

- `member / runtime` 是 **镜像实例化消费方**
- **交互类型**: instantiate / bootstrap 输出型交互
- **主流程位置**: instantiate、bootstrap、version switch、derive-replace 时进入主流程
- **交互解释**:
  - image 提供可实例化 bundle
  - member 形成正式成员实例
  - runtime 用 seeds 初始化上下文
  - image 不等于 live state
- **高风险异常流**:
  - instantiate 时 image bundle 不完整仍被放行
- 后续 `03-详细设计.md` 继续展开:
  - instantiate contract
  - bootstrap bundle 主线

#### 与 `conversation / UI / console` 的交互

```text
┌────────────────────────────┐
│ member-images              │
│ - persona/style summary    │
│ - image catalog            │
└────────────┬───────────────┘
             │ display/query output
             ▼
┌────────────────────────────┐
│ conversation / UI / console│
│ - display / select / view  │
└────────────────────────────┘
```

- 这些系统是 **镜像目录与展示消费方**
- **交互类型**: catalog / summary 只读输出型交互
- **主流程位置**: image query、catalog 列表、镜像选择、摘要展示时进入主流程
- **交互解释**:
  - member-images 提供 persona/style/description 的只读展示材料
  - conversation/UI 只读消费这些摘要
  - 不反向形成运行期对话真相
- **高风险异常流**:
  - default prompt/style 被误当 conversation history
- 后续 `03-详细设计.md` 继续展开:
  - catalog query
  - summary projection 主线

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是模板资产层、哪个模块是实例化消费方、哪个模块是只读目录消费方

本节**不**展开:
- prompt 具体字段结构细节
- toolset / capability resolve 算法细节
- workspace seed 文件系统布局细节
- version/derivation 代码级状态机细节
- instantiate hook 执行细节

这些内容留到 `03-详细设计.md` 中继续展开。

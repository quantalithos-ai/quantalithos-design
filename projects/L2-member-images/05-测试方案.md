## 2. 本次测试目标与范围

> 校准来源：
> - `design-calibration/05_test_plan_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读该中间产物的“范围与非范围表”“VETO 关联”和“结构化中间产物”小节，了解优先级与非范围如何划分。

本轮测试设计的目标是验证本仓 local image definition、static assembly、build/qualification/supply 分阶段 truth、typed protocol、状态/一致性/安全边界是否可被证明或明确拒绝越界输入。它不把 staged local state、配置装配、fake 或外部 marker 升格为 build、Artifact、consumer、runtime 或 overall readiness。

| 范围项 | 类型 | 优先级 | 验证目标 | 非目标 / 说明 |
|---|---|---:|---|---|
| definition、mapping ref、variant revision | 功能 / local truth | P0 | 定义不变量、来源引用、非法迁移、replacement 与历史边界。 | 不验证 RoleDefinition 或 mapping body。 |
| baseline、component、seed、static/live 边界 | 功能 / 安全 | P0 | immutable pin、完整性与 static seed 不混入 live state。 | 不固化 live memory/checkpoint/workspace。 |
| build intent、snapshot、attempt、candidate | 状态 / 协议 | P0 | 字段校验、阶段隔离、blocked/unknown 与重开前置。 | 不声明真实 builder、registry、candidate 或 digest 成功。 |
| provenance、gate、eligibility、Artifact handoff | 资格 / owner boundary | P0 | body-free provenance、gap 与保守 disposition。 | 不创建 scanner/signer/gate/Artifact truth。 |
| availability、entry、consumer gap | 供给 / 查询 | P0 | pinned entry、append-only transition 与 consumer gap 隔离。 | 不验证 launch、health、manifest 或 confirmation。 |
| 10 Command、10 Query、2 inbound、6 Job、0 outbound | 协议 | P0 | DTO、正式错误、zero-effect/no-write/marker/zero inventory。 | 不绑定 transport、topic、scheduler 或外部 adapter 成功。 |
| UoW、version、idempotency、concurrency、recovery | 一致性 | P0 | duplicate/conflict、commit unknown、rollback 和 no-repair 语义。 | B01/B02 与 PF 未闭合时不验证 accepted mutation/replay/recovery。 |
| strict config、profile、redaction | 配置 / 安全 | P0 | 五域 21 key、source priority、TestOnly 隔离、startup-only 与 fail-closed。 | 不绑定 secret provider、endpoint 或线上 reload。 |
| controlled adapter、durable-like store | 集成 seam | P1 | local failure mapping 和 fake parity。 | owner 未闭合时不形成正向外部结果。 |
| production capacity/SLO、真实 registry/consumer、复杂扫描签名 | 产品 / 运维 | P2 | 后续由权威 owner 定义验证 oracle。 | 当前无 baseline、阈值或授权。 |

|---|---|---|
| member 主体、runtime loop、tool execution、live memory/checkpoint/workspace | Member、Runtime、Tools 与相应 owner。 | 只验证 template/static seed/ref 不替代 live truth。 |
| container lifecycle、sandbox policy/backend、governance approval、observability backend | Sandbox、Governance、Observability owner。 | 不将 image `Assembled` 或 safe signal 当作外部 readiness。 |
| Artifact 真相、marketplace/product entry、外部 MCP/A2A/API adapter truth | Artifact、产品和 adapter owner。 | 仅验证本仓 ref/gap/blocked seam。 |

P0 以当前正式契约的可验证边界为分母。P1/P2、owner gap、环境缺失或 B01/B02/PF 阻断均不能计为 P0 pass、skip 或 readiness。

## 4. 测试策略与分层

> 校准来源：
> - `design-calibration/05_test_plan_step_04_strategy_layers.md`
>
> 延伸阅读：
> - 建议继续阅读该中间产物的“测试分层图”“分层表”和“切口到层级映射”小节，了解风险为何在最早可判定层级验证。

#### 测试分层图: L2-member-images 风险前移验证结构

```text
[Release / evidence gate]
  - cross-entry aggregate, redaction and dependency checks, evidence index
                         ^
[API / Worker / Job entry contract]
  - logical DTO / error / marker / bounded-action boundary
                         ^
[Controlled integration]
  - repository / version / UoW / projection / config / adapter failure mapping
                         ^
[Application service]
  - command/job stop, query no-write, idempotency and ordering
                         ^
[Contract + domain unit]
  - typed refs, guards, states, static/live and append/supersede rules
```

关键说明：

- 风险在拥有正式 oracle 的最早层发现；上层组合测试不补偿下层对象、状态或 no-write 缺口。
- Command/Job accepted mutation、inbound accepted path 与外部 positive result 不进入当前 gate 通过条件，直到 blocker 关闭并重开受影响设计。
- 图不表示已有实现、CI、真实 registry/bus、container、scheduler、环境或 run。

| 层级 | 目标 | 典型内容 | 计划执行时机 | 失败处理 |
|---|---|---|---|---|
| contract / unit | 局部 schema、不变量、guard、正式 enum 与 redaction。 | typed ref、DTO、非法 transition、body rejection。 | PR / CI。 | P0 断言失败阻断。 |
| application service | 编排顺序与零副作用边界。 | Command/Job B01 stop、Query no-write、idempotency template。 | PR / CI。 | P0 断言失败阻断；未闭合 owner lane 保留 blocked。 |
| controlled integration | store/UoW/version/projection/config/adapter failure。 | rollback、commit unknown、freshness marker、strict JSON、failure mapping。 | CI / planned nightly。 | P0 失败阻断；P1 owner gap 不能伪作 pass。 |
| API / Worker / Job entry | logical protocol 边界。 | mapper、marker-only inbound、bounded job scope。 | CI。 | DTO、marker 或 boundary 违规阻断。 |
| release / evidence gate | 最小跨入口组合与证据完整性。 | local composition、cross-entry aggregate、redaction/dependency scan。 | future staging / release。 | 环境或 owner 缺失为 blocked；不得以此产生 pass。 |

| 切口 | 首要层级 | 辅助层级 | 不可由 E2E 代替的断言 |
|---|---|---|---|
| contracts / domain / state | unit / contract | entry | 精确字段、错误、enum、不变量。 |
| Command / Job orchestration | service | entry / integration | B01/B02 stop、UoW 语义与 zero-effect。 |
| Query no-write | service | entry | 无 reserve/save/gap/trace/freshness write、refresh/rebuild 或 adapter call。 |
| repository / UoW / projection | integration | service | version、rollback、append-only、`Unavailable` no-repair。 |
| config / redaction | config / integration | release gate | unknown key、source conflict、secret/body no-output、fake isolation。 |
| inbound / outbound boundary | entry / contract | release scan | `accepted_input=false` 与 outbound zero inventory。 |

| 敏感数据 | opaque placeholder 可用；raw secret、credential、endpoint 和外部 body 不进入 fixture 输出。 | 在 stdout、snapshot、report 或错误中回显 sentinel。 |
| 清理 | 每个 namespace、store、marker、临时文件都有 rollback/truncate/discard。 | 共享测试数据库、跨 run 残留或依赖隐式顺序。 |

## 11. 缺陷管理与复验规则

> 校准来源：
> - `design-calibration/05_test_plan_step_11_defects_retest.md`
>
> 延伸阅读：
> - 建议继续阅读该中间产物的“缺陷严重级别”“复验矩阵”和“缺陷生命周期与禁止动作”小节，了解 defect、blocker、重开和证据的边界。

设计 blocker 与未来 observed defect 必须分开记录：`DDD-*`、`MI-UP-*`、`Q-MI-*`、`PF-*` 是 pending/blocked 设计输入，不能被当作实现 bug，也不能通过静态文本、fake 或手工确认关闭。

| 级别 | 定义 | 示例 | 处理要求 | 是否阻断 |
|---|---|---|---|---|
| `S` | 一票否决或安全/真相边界破坏。 | raw secret/body、Query write、fake pass、staged ready、unauthorized outbound。 | 立即阻断；修复并全量 P0 回归；不得风险接受。 | 是 |
| `A` | P0 主线契约或一致性失败，未直接越过 VETO。 | version/UoW/replay、状态迁移、strict config、错误映射。 | 修复后受影响族回归；是否接受由 future 06 owner 裁决。 | 通常是 |
| `B` | 非核心可用性、文档或诊断缺陷。 | safe reason 文案、非关键报告格式、future P1 seam。 | 排期修复；不改变 P0 结论。 | 否 |
| `C` | 纯编辑/格式问题。 | 链接、表格排版、拼写。 | 修订并复核。 | 否 |

| 缺陷触点 | 首先复验 | 必须追加 | 设计回写条件 |
|---|---|---|---|
| contracts / DTO | 原协议 roundtrip、missing/unknown。 | API/worker/job entry mapping。 | field/schema/error 改动 -> 03 Step 8。 |
| domain / state | 原合法/非法 transition。 | 邻接 terminal/replacement、history。 | enum/factory/guard 改动 -> 03 Step 6/10。 |
| application / UoW | 原 TC、rollback/replay。 | concurrency、commit unknown、Query no-write。 | flow/store/idempotency 改动 -> 03 Step 7/9/11~13。 |
| infra / config | 原 profile/source case。 | redaction、startup freeze、failure matrix。 | key/source/builder/error 改动 -> 03/04。 |
| worker / jobs | marker/bounded scope。 | no scheduler/receipt/repair、duplicate。 | inbound/job contract 改动 -> 03 Step 8/9。 |
| evidence / report | 原 EV mapping。 | path、redaction、TC-to-AC index。 | evidence schema/threshold 改动 -> 05/06 重开。 |

```text
planned/blocked -> observed (future run only) -> triaged -> fixed or accepted -> retested -> closed
```

当前阶段只可记录 planned blocker；不得填写 observed run、修复 commit、报告链接、owner signoff 或 close 结论。若修复改变正式字段、状态、port、error、flow 或配置语义，必须先重开对应 calibration Step，再调整测试 oracle。

### 12.1 进入准则

进入未来测试执行前，必须全部满足：

- [ ] 当前 00~04、对应 calibration 与本方案版本已由项目门禁确认；任何设计差异已登记。
- [ ] 目标实现仓、工具链、测试框架和可写证据目录由 future 07/执行 owner 核验；本文不代替核验。
- [ ] P0 fixture 可按第 7 章重复构造，隔离键、清理方式和脱敏边界明确。
- [ ] `local-dev`/`ci-test` 配置可严格解析；invalid config、fake/profile 混用与 raw secret 负向样本齐备。
- [ ] P0 suite、TC、EV、脚本和 report path 有规划映射；没有实际可写路径时测试必须停止，不得手工补证据。

### 12.2 退出准则

只有在 future 执行阶段同时满足以下条件，才可将测试报告交给 06：

- [ ] 所有 P0 planned TC 已执行或有正式 blocker 记录；未执行项不能标为通过。
- [ ] 所有 S 级/VETO 用例通过；Query no-write、inbound marker-only、outbound zero 与 redaction/dependency gate 无违规。
- [ ] P0 阻断缺陷为 0；A 级缺陷有修复证据或 06 明确风险接受；B/C 有跟踪。
- [ ] 每个 suite 产生固定 run 的 artifact、report 与 EV-to-TC-to-requirement 索引；不使用 `latest`。
- [ ] owner 未闭合的正向 lane 明确为 blocked/pending，不纳入 readiness 或 release pass 分母。
- [ ] 退出报告与 06 的验收引用、残余风险和 signoff 角色完成交接；本文不代写裁决。

| 情况 | 处理 | 是否算通过 |
|---|---|---|
| 实现仓或环境不存在 | 标记 `environment_blocked`，停止该 suite。 | 否 |
| owner contract 未闭合 | 标记对应 `MI-UP/Q-MI`，保留 negative seam。 | 不算正向通过 |

| evidence path 或 report generation 失败 | suite failure，修复工具后重新执行。 | 否 |

真实性与脱敏规则：失败 suite 仍须保留 report/stdout/stderr/failure reason；blocked 与 failed 不互换；artifact、报告、evidence index 与 acceptance draft 不得包含 raw secret、credential、endpoint、完整外部正文、live state、伪造 digest 或结果。EV family 可由多个 TC 共享，但实际实例必须带固定 run、suite、path 与 case mapping。本文不创建任何上述目录或实例。

## 1. 一句话定位

`L2-member-images` 是平台 AI 成员运行层中的**成员镜像资产与构建产物供给层**:它拥有“一个 AI 成员 Role 如何被装配成可实例化镜像”的 variant / persona 装配定义、构建输入绑定、镜像域构建与发布状态、provenance / digest 绑定和交接语义,并向 `L2-member-service` 提供可实例化的镜像入口(manifest / variant / ref)。当构建输出被登记为平台 Artifact 时,其 Artifact 正文、版本、血缘与基线真相仍归 `L1-artifact`;本仓只保存镜像域事实及 `L1-artifact` 正式签发的消费引用,不得建立第二套通用制品真相。

对照相邻仓的一句话区分:

| 仓 | 拥有的真相 | 与本仓的关系 |
|---|---|---|
| `L3-method-library` | RoleDefinition、Role -> image variant 的**定义映射来源** | 本仓消费该映射,不得 hardcode 或反向定义 |
| `L2-tools` | 工具身份、工具契约、canonical invocation 语义 | 本仓只装配受控工具产物到镜像,不拥有工具契约 / 执行 |
| `L2-runtime` | run / loop / turn 运行语义、checkpoint、recovery | 本仓只装配 runtime 产物,不拥有任何运行时 live state |
| `L2-member` | 成员门面进程(嘴耳) | 本仓只装配 member 产物;成员主体真相不归本仓(pending 输入) |
| `L2-member-service` | 容器生命周期编排、镜像**选择与拉取** | 本仓是其镜像供给上游;起停 / 注册 / 心跳不归本仓(pending 输入) |
| `L1-artifact` | Artifact 正文、版本、血缘、基线真相 | 本仓拥有构建输入到 digest / release eligibility 的镜像域绑定事实;构建输出一旦正式化为 Artifact,只持有其正式 `ConsumableArtifactReference`;精确 handoff / reference schema 仍 pending,本仓不得自造 version / lineage ref 类型 |
| `L4-sandbox` | 隔离执行环境真相 | 未来加固基础镜像是消费关系;sandbox policy / backend 不归本仓 |

## 2. 为什么必须单独存在

1. **冷启动经济性(ADR-0005 已裁决)**:member-service 只能启动镜像,不能运行时现装;"装"的代价必须前移到构建期。这条装配链需要一个唯一 owner。
2. **模板 / 种子 / 构建产物与运行时 live state 必须分离**:policy / memory / workspace 的**seed 模板化承接**、image variant 定义消费、构建产物 digest 属于"静态资产"世界;run、checkpoint、live memory 属于"运行"世界。没有独立仓,这两个世界会在 member-service 或 runtime 中混写。
3. **供应链可审计性(三红线)**:镜像 digest、构建输入 provenance、发布 / 回滚交接以及适用策略要求的供应链证据引用,是审计证据链的一环(ISO 42001 A.4 / A.6)。镜像域绑定事实不能只散落在 CI 脚本或 registry metadata 里;若输出进入正式 Artifact 生命周期,则通过 ref 交给 `L1-artifact`,不得复制其版本 / 血缘真相。
4. **权限上限的物理承载**:"镜像里没有的工具,运行时也用不了"——Role 能力上限由镜像 variant 物理固化,这是治理红线的构建期表达,需要有 owner 对"某 variant 里到底装了什么"负责。

## 3. 本仓拥有 / 只消费 / 禁止拥有

按 `L2-runtime 00` §2 同款三列口径:

| 主题 | 本仓拥有(truth) | 只消费 / 引用 / 交接 | 禁止拥有 |
|---|---|---|---|
| image / persona 定义 | image family、variant 目录、persona 装配定义、base -> variant 装配派生规则 | RoleDefinition ref、Role -> variant 映射(归 method-library) | Role 业务定义正文、member 主体真相、`ArtifactLineageLink` truth |
| 装配输入 | 装配清单(哪个 variant 装配哪些组件产物、角色 extras)、版本 pin 事实 | runtime / tools / member 的**发布产物 ref**(component release ref) | 工具契约、runtime loop、capability registry、外部 MCP/A2A/API adapter truth |
| seed 模板 | policy / memory / workspace seed 的**模板化承接事实**(seed 模板身份、版本、进入哪个 variant) | policy 定义(governance / method-library)、memory / workspace 语义(各自 owner) | governance approval truth、live memory / checkpoint、workspace 运行态 |
| 镜像域修订 / 派生 / 可用性 | variant definition revision、base -> variant 装配派生规则、版本 pin 绑定、supersede / retire / release eligibility 状态 | 上游组件版本事实;正式 `ConsumableArtifactReference`(精确 handoff schema pending) | 上游组件发布真相;通用 Artifact 正文、版本、血缘、基线真相 |
| 构建 | 构建请求 / 构建记录、构建输入快照、候选输出 digest / ref 绑定、失败分类 | CI / builder backend 能力(adapter)、registry 能力(adapter)、正式 Artifact 交接(pending) | CI 平台真相、registry 后端真相、通用 Artifact 生命周期、容器生命周期 |
| provenance / digest | 构建输入到输出 digest 的绑定事实、provenance 记录;适用策略要求的 BOM / 扫描 / 签名等证据 ref 候选 | builder / registry 输出;BOM / scanner / signer 输出(adapter,pending);Artifact ref | 漏洞库真相、密钥管理真相、通用 Artifact 版本 / 血缘真相 |
| 发布 / 回滚 | 镜像供给面的 publish / rollback / retire / availability 交接语义、可用 variant 目录 | `ConsumableArtifactReference`、member-service 消费回执(不反写) | Artifact baseline / version truth;member-service 是否实际升级 / 启动的决定权 |
| 可实例化入口 | image manifest / variant / ref 的查询与解析语义 | 下游按 ref 拉取(registry adapter) | 实例化本身(容器起停) |

**红线**:所有"模板 / 种子 / 构建产物"与"运行时 live state"必须严格区分。本仓交付的一切都是**运行前静态资产**;任何运行期产生的状态(容器、心跳、live memory、checkpoint、tool execution 结果)都不进入本仓真相。

## 4. 设计取舍(定位层)

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 本仓 = 纯 CI 产出仓(旧 README 口径: Dockerfile + CI 脚本,无自身领域模型) | 简单,贴近现状直觉 | 无法承载 variant 目录、seed 模板承接、provenance、发布 / 回滚交接这些需要唯一真相源的事实;审计链断在 CI 日志里;与设计仓当前"真相仓"方法论不符 | 不采用 |
| B. 本仓 = 镜像资产真相仓 + 构建产物供给层(拥有镜像域对象与构建 / 发布状态,CI / registry 是 adapter,通用 Artifact truth 走 ref) | 装配、构建、provenance 和交接有明确 owner;不与 `L1-artifact` 建第二套版本 / 血缘;与 L2-runtime / L2-tools 的 owner-seam 方法论一致 | 需要定义镜像域对象和 Artifact handoff,比“纯 CI 仓”重 | **采用** |
| C. 并入 member-service(镜像构建作为编排的子能力) | 少一个仓 | 混写"静态资产真相"与"运行编排真相";违反 ADR-0005 分仓结论;member-service 尚未重校准,反而扩大 pending 面 | 不采用 |

## 5. 与旧 README 定位的差异(摘要)

旧 README 把本仓定位为"CI 产出仓,不是运行时代码",并直接锁定技术栈(Dockerfile + GitHub Actions + buildx)、9 个固定 Role 清单、nightly 节奏和目录结构。按 full-restart 口径:

- Accepted ADR-0005 已锁定的“一 Role 一镜像”“每晚 CI 构建”“Role -> image variant 映射归方法库”“镜像版本必须 pinned”“生产禁用 `latest`”——**作为 authority 保留**,进入 00 时只做需求层承接,不得当作旧 README 假设废弃;
- 具体技术栈、CI 平台、固定 Role 数量 / 清单、各 Role 工具清单和实现目录——**降为 historical_material**;ADR 明确不锁定具体 Role 工具清单,本仓也不得固化方法库拥有的 Role 目录;
- base -> role/variant 派生、digest / provenance 属于任务明确要求的设计方向;BOM / 扫描 / 签名是供应链证据候选,是否构成当前 P0 发布门禁须在 00 按正式 policy authority 重新确权;
- 旧定位缺失的部分——variant 资产对象模型、seed 模板承接、发布 / 回滚交接语义、与 member-service 的 manifest 入口——**本次补齐为定位主体**。

详细逐条审计见 `05_旧材料差异审计与待确认.md`。

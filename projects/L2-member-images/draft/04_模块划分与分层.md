## 1. 拆分原则

1. 按**功能职责主线**拆主要组成部分,不按对象拆、不按 CI 步骤拆(与 governance §5 一致)。
2. 每个组成部分承接 `03` 中至少一个能力节点,且写明"不承担什么"。
3. 组成部分(what)与责任层次(how)正交;六层只作为**适用性检查框架**,不预设每个组成部分都必须有独立 inbound、application service、持久化仓储或 outbox。
4. 外部后端(builder / registry / policy-required evidence tools)一律通过 port / adapter 隔离;derived / 查询面不反写真相。具体进程、package、数据库与 CI 产品由 01~04 后续裁定。

## 3. 候选责任分层(参照 governance §4,不预设部署形态)

```text
+==================================================================+
|              L2-member-images code subject map (草案)              |
+==================================================================+
| Image asset truth core          -> domain truth / trace / guards  |
| Variant and mapping mgmt        -> variant service / mapping intake|
| Assembly input mgmt             -> assembly service / pin resolver |
| Seed template intake            -> seed intake service             |
| Image revision / derivation     -> image-domain binding / guards   |
| Build trigger/orchestration     -> build use case / builder port   |
| Provenance / evidence gate      -> digest binding / evidence ports |
| Release and instantiable surface-> release service / manifest query|
| External mirror / derived       -> snapshot / projection support   |
+==================================================================+
```

以下“分层”表示需要被明确安放的责任,不是已确定的 package、进程或物理存储。若后续选择以静态构建声明、CI workflow 或薄控制面实现,仍可满足对应责任而不创建完整六层服务。

| 责任层次 | 候选职责 | 本仓边界 |
|---|---|---|
| Inbound / Operations | command(variant 变更、构建请求、availability / rollback)、query(manifest / 目录 / provenance)、event consumer(镜像构建事件及获准的上游变化)、nightly / job trigger 进入系统 | 不做业务判定;出站事件不属于本层,且当前仍 pending |
| Application Services | 编排用例、事务 / 原子边界、幂等、domain 调用、ports 与条件型 handoff / outbox | 不替代 domain invariant;outbox 仅在对应出站合同获 authority 后适用 |
| Domain Model and Policies | variant / 装配 / seed、镜像域 revision / derivation / eligibility、构建记录、digest / provenance、availability 及已确权门禁 guard | 不直接读配置或外部正文;不定义通用 ArtifactVersion / lineage |
| Ports and External Seams | method-library mapping intake、component release ref、builder、registry、policy-required evidence、bus input、Artifact handoff、member-service supply surface | 外部 truth 不进入本仓;适用 adapter 不可用即对应路径 blocked |
| Persistence / Projection | 在确需持久状态时保存镜像域 truth、trace、输入快照及目录 / 装配派生视图 | 是否需要独立 persistence 由 01/02 决定;projection 不反写真相,不复制 Artifact truth |
| Handoff / Conditional Outbox | `ConsumableArtifactReference` 交接、publish / rollback handoff;仅当出站事件合同获 authority 后才引入 outbox | Artifact image handoff 的精确 schema pending;当前不得假设本仓已有出站构建 / 发布事件;delivery / observed 归各 owner |

### 3.1 组成部分对责任层次的适用性

`R` 表示该职责必须有等价承载,不代表必须有独立 package / service;`C` 表示仅在 01/02 选择对应实现形态或合同闭口后适用;`N` 表示不应为该组成部分单独创建该层。

| 组成部分 | Inbound | Application | Domain | Ports | Persistence / Projection | Handoff / Outbox |
|---|---|---|---|---|---|---|
| Image asset truth core | N | C | R | N | C | C |
| Variant and mapping management | C | R | R | R | C | N |
| Assembly input management | C | R | R | R | C | N |
| Seed template intake | C | R | R | R | C | N |
| Image revision / derivation / availability | C | R | R | R | C | C(Artifact handoff) |
| Build trigger / orchestration / record | R | R | C | R | C | C |
| Provenance and evidence gate | C | R | R | R | C | R(Artifact ref / eligibility) |
| Release and instantiable surface | C | R | R | R | C | R(member-service handoff) |
| External context mirror / derived maintenance | C | C | N | R | C | N |

## 5. 与 L1-governance 粒度的对照自检

| governance 做法 | 本 draft 对应 | 一致性 |
|---|---|---|
| 10 个业务主要组成部分,含 1 个 truth core + 1 个 mirror/derived 横切 | 9 个组成部分,含 truth core 与 mirror/derived | 一致(规模相当,按业务量收敛) |
| 组成部分按功能职责拆,写明"不承担什么" | 每行均有"不承担什么" | 一致 |
| 实现责任按 Inbound / Application / Domain / Ports / Persistence / Outbox-Handoff 检查 | 使用同一检查维度,另加逐组成部分适用性矩阵 | 方法一致,不机械复制服务形态 |
| 接口五类:Command / Query / Consumer / Outbound Event / Operations Job | 以五类作为完整性检查;Command / Query / Consumer / Job 为候选入口,Outbound Event 因无 authority 保持 pending | 方法一致,不预造出站合同 |
| 派生只读、handoff / outbox 与 truth 分离、配置不可越界 | 已写入分层边界;outbox 仅在出站事件合同闭口后适用 | 一致且保留 pending |

## 6. 设计取舍(模块层)

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 按 CI 阶段拆模块(build / scan / sign / push) | 直观 | 模块=脚本步骤,无法承载 truth / guard / 交接语义;governance 粒度对不上 | 不采用 |
| B. 按对象拆模块(Image / BOM / Release 各一模块) | 对象清晰 | 概要层主要部分应表达功能责任,不是对象清单(中间产物规范正例明文) | 不采用 |
| C. 按功能职责主线拆 9 部分 + 六层责任适用性检查 | 与 governance 的职责粒度一致;能力节点全部有承接;不会预设每部分都有常驻服务 / persistence / outbox | 需要维护组成部分与责任层次两个正交维度 | **采用** |

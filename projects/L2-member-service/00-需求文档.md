## 2. 本仓定位与边界

> 校准来源：
> - `design-calibration/00_req_step_02_position_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“边界判定口径”和“四语义层区分”小节。

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L2-member-service` 是 AI 成员执行宿主与编排控制面真相仓，拥有成员宿主实例从编排决定、装配、启动、注册、会话、心跳健康到恢复清理的宿主侧事实。 |
| 本仓不是什么 | 它不是运行循环仓、成员门面进程仓、镜像内容仓、隔离执行仓、身份真相仓、项目工作事实仓、治理裁决仓，也不是容器编排平台产品本体。 |
| 边界对象列表 | 仓：`L2-runtime`、`L2-member`、`L2-member-images`、`L4-sandbox`、`L1-identity`、`L1-work`、`L1-governance`、`L3-method-library`；概念：runtime session、SandboxBinding、launch credential；后端：容器运行时 / 编排平台。 |
| 单独成仓原因 | 宿主生命周期、注册、健康、装配与恢复语义必须在多上游、多下游之间唯一。Runtime 与 Sandbox 的停审文档已从两侧把该真相划归本仓；并入相邻仓会造成 owner 反转或宿主内进程管理自身生命周期的自举矛盾。 |

“成员拥有一个受控执行宿主”独立于“成员是谁”（Identity）、“成员被分配了什么”（Work）、“成员如何思考行动”（Runtime）和“执行如何被隔离”（Sandbox）。如果这些边界不分开，host failure、session failure、runtime failure 与 isolation failure 会被压成一个状态，恢复和审计都无法归责。

### 2.1 边界判定口径

| 判定问题 | 落入本仓 | 不落入本仓 |
|---|---|---|
| 是否回答“该成员现在有没有可用执行宿主” | 宿主实例、endpoint、健康与 host session 事实 | 成员是谁；成员在项目中承担什么 |
| 是否决定“要不要 / 怎样把成员变成运行实例” | launch / stop / restart / relocate 编排决定与装配输入组织 | 分配意图本身；run 内部推进 |
| 是否描述“宿主里运行内容怎么思考和行动” | 否 | Runtime run / turn / decision / checkpoint |
| 是否定义“宿主里装的是什么” | 否；只消费正式镜像供给引用与装配输入 | 镜像内容；Role 映射定义 |
| 是否执行受限动作的隔离 | 否；只保存宿主级 binding / release 关联、装配结果与允许反馈 | ToolInvocation、逐动作 execute、隔离边界与 enforcement |
| 是否裁决“允许不允许” | 否；fail closed 消费正式结论 | Governance / Capability 决策 truth |

### 2.2 四语义层

| 层 | 含义 | 归属 |
|---|---|---|
| control plane | 是否及如何启停、装配、恢复的编排决定 | 本仓 |
| host truth | 宿主身份、装配结果、endpoint、健康、失败分类与清理 | 本仓 |
| runtime session | 宿主与 Runtime 运行的会话关联；host session 壳归本仓，会话内运行语义归 Runtime | 分层共存 |
| execution handoff | 宿主级 SandboxBinding 装配、bind / release 关联及允许反馈归本仓；逐动作 execute caller 归 Tools / Runtime；隔离 truth 归 Sandbox | 分层共存 |

## 3. 背景与问题定义

> 校准来源：
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“业务问题 vs 技术问题”和“待确认事项”小节。

### 3.1 业务背景

Quantalithos 要求 AI 员工作为有身份的个体长期真实运行。平台上游已经停审成员身份、项目分配、受控运行循环、工具契约、治理裁决与隔离执行的真相边界，Layer 3 成员运行面并行窗口随之开启。当前需要收束的是：已经成立的成员与项目事实，如何获得并保持一个受控执行宿主。

### 3.2 当前问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 宿主真相无有效 owner 基线 | Runtime 显式排除 member host lifecycle；Sandbox 把 MemberExecutionHost / SandboxBinding 装配 truth、session、worker、health 与 callback material 划归本仓；本仓旧文档却未承接当前边界 | 上游合同对端悬空，同窗口 Member / Member Images 无法引用稳定宿主边界 |
| 宿主编排语义存在塌陷风险 | 缺少统一控制面时，业务域可能直连容器 API、Runtime 自管宿主、Sandbox 交接被旁路、镜像映射被本地重解 | 多套宿主语义并存，启停、健康、恢复不可归责，审计与隔离红线失效 |
| 旧文档基线失效 | 旧 README 与正式 `00~03/05/06` 早于 Runtime / Sandbox 停审，携带无 authority 的指标、技术栈和实现组件 | 直接继承会把过时边界与伪量化写回正式链，必须 full-restart |

### 3.3 业务问题与技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台缺少“成员分配事实如何变成可用、可恢复、可审计运行实体”的正式需求；AI 员工持续在岗、故障恢复与下线交代无法稳定兑现。 |
| 技术问题 | 宿主生命周期、装配输入、注册与会话、心跳健康、SandboxBinding 交接、恢复清理和宿主侧反馈的唯一 owner 与失败语义未闭合；不同失败层若不先分层，后续设计会持续串线。 |

## 4. 目标与非目标

### 4.1 目标

| ID | 目标 | 完成方向 |
|---|---|---|
| `G-MS-001` | 宿主真相与编排决定成立 | 宿主实例具有唯一身份、显式生命周期状态与可追溯决定来源；意图受理、拒绝和等待可判定。 |
| `G-MS-002` | 装配边界成立 | Identity / Work refs、Member Images 正式 pinned 供给、环境需求、宿主凭据与适用 SandboxBinding 按 owner / ref / freshness 组织；不直接解析 Role / image mapping，partial 不伪装 ready。 |
| `G-MS-003` | 注册、会话与健康分层成立 | 宿主内来源凭正式凭据注册；endpoint 与 host session 唯一；健康分层为 host / session / backend / unknown，不与业务或 Runtime 状态混写。 |
| `G-MS-004` | 隔离交接与恢复清理语义成立 | 宿主级隔离装配与交接 refs 可归责；异常宿主按显式决定处置，重启形成新实例，下线清理与孤儿对账可追溯。 |
| `G-MS-005` | 宿主事实对外交接分层成立 | 已提交宿主事实以 body-free 形态交接；attempt / gap 与 delivered / observed / accepted 分层，外部失败不回滚本地 truth。 |

| `NG-MS-003` | 镜像内容、构建、签名、BOM truth | `L2-member-images` |
| `NG-MS-004` | 隔离边界、policy enforcement、capture、cleanup 的 isolation truth | `L4-sandbox` |
| `NG-MS-005` | GlobalMember / Role 身份真相与认证凭据体系 | `L1-identity` / 安全 owner |

## 5. 用户与角色

> 校准来源：
> - `design-calibration/00_req_step_05_users_roles.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“授权尾注”和“待确认事项”小节。

### 5.1 人类角色

| 角色 | 使用场景 |
|---|---|
| 平台运维 / SRE | 维护编排后端与装配输入边界，使用安全的启停、恢复和下线入口；不修改业务 truth，不绕过控制面直连容器。 |
| 宿主问题调查者 | 沿宿主实例、装配、注册、会话、健康、失败分类、恢复决定与清理事实的关联，定位启动失败、失联、恢复异常或孤儿实例。 |
| 安全 / 边界审查者 | 审查凭据复用、fail-open、host fallback、正文 / secret 泄漏、宿主直连旁路和 owner 串线。 |

### 5.2 系统角色

| 角色 | 使用场景 |
|---|---|
| 宿主意图触发方 | 以正式来源的分配 / 回收事实、身份生命周期变化或运维请求触发宿主编排意图。 |
| 正式事实提供方 | 以 typed ref、safe summary 或事件提供身份摘要、分配事实、生效策略与正式镜像供给；源 truth 仍归提供方。 |
| 宿主内注册与心跳来源 | 宿主内来源凭正式凭据注册并报告存活和状态；Member 拥有请求 / 信号 / 报告，本仓拥有接受 / registry / session / 健康判定。 |
| 隔离能力协作方 | 按 Sandbox 正式边界承接宿主级 binding / release 并返回允许的失败 / cleanup refs；逐动作 execute caller 不归本仓。 |
| 宿主事实消费方 | 消费 body-free 宿主状态、生命周期事实或 safe view，不反写本仓 truth。 |

这些角色只描述职责与接触场景，不授予 authorization。principal、scope、allow / deny 必须来自 Governance、Identity 等正式 owner；任何角色不得代表本仓声明 delivered、observed 或 accepted。

## 6. 使用方与依赖

> 校准来源：
> - `design-calibration/00_req_step_06_consumers_dependencies.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“依赖裁剪图”“path dependency 判定”和“待确认事项”小节。

本仓向正式宿主意图触发方提供受理与控制能力，向宿主内来源提供注册承接，向 Runtime 提供宿主与 host session 承载边界，向 Bus / Observability 交接已提交的 body-free 宿主事实。Identity、Work、正式镜像供给、容器承载和适用的宿主级 SandboxBinding 构成核心输入；正向合同未闭口时必须 fail closed。

### 6.1 内部仓依赖

| 方向 | 对方 | 提供 / 依赖内容 | 是否闭环前置 | 失效影响 |
|---|---|---|---|---|
| 输入 | `L0-core` | 共享 ID / ref / metadata / error / trace / envelope 契约类别 | 是 | 无法形成平台一致契约类别时不得本地 shadow。 |
| 输入 | `L0-sdk` | 全局矩阵规定的编译期正式客户端合同 / Server 自测试基线 | 否 | 不阻塞宿主运行；准确 dependency target 未闭口时阻塞实现边界声明。 |
| 输入 | `L1-identity` | GlobalMember 身份锚、生命周期与可运行性信号 | 是 | 新装配拒绝 / 等待；存量宿主显式 stale。 |
| 输入 | `L1-work` | ProjectMember 项目执行主语及分配 / 回收事实 | 是 | 无可验证执行主语时不得启动项目型宿主。 |
| 输入 | `L2-member-images` | 正式 pinned image ref / manifest 与允许的 provenance refs | 是 | 需求级供给方向已正式停审；exact contract 仍 pending，不可验证时 launch blocked。 |
| 输入 | `L4-sandbox` | 宿主级 binding / release、failure 与 cleanup 反馈边界 | 条件性是 | 要求隔离的宿主 binding 不成立时不得 host fallback。 |
| 输入 / 输出 | `L2-member` | launch / register / heartbeat / status 协作 | 是 | 需求级 owner 分工已停审；详细合同未闭口时不得声明宿主 ready。 |
| 输入 / 输出 | `L2-runtime` | 宿主会话承载、Runtime entry / feedback ref 边界 | 是 | `Q-L2R-001` 未闭口时只保留 capability-level seam。 |
| 输入 | `L1-governance` | 生效 policy 事件 / ref 的边界背景 | 否 | 传递 owner 与当前功能未确认；不得补造裁决、接口或默认放行。 |
| 输入 / 输出 | `L0-bus` | 上游事件协作与已提交宿主事实传播主干 | 否 | delivery gap 显式，不回滚本地 truth。 |
| 输出 | `L4-observability` | body-free 宿主材料与 handoff attempt / gap | 否 | 交接失败形成 gap，不声明 observed。 |

`L3-method-library` 是 `L2-member-images` 的正式定义来源，不是本仓直接输入。`L2-tools` 拥有逐动作工具执行与相应 Sandbox handoff，本仓不形成直接执行依赖。

### 6.2 外部系统依赖

| 方向 | 对方 | 提供 / 依赖内容 | 是否闭环前置 | 失效影响 |
|---|---|---|---|---|
| 输入 / 输出 | 容器运行时 / 编排平台 | 宿主物理承载与生命周期动作的 adapter 能力 | 是 | 新启动 blocked；存量宿主进入可解释的 unknown / degraded。 |

### 6.3 依赖裁剪

| 关联项目 / seam | 本仓角色 | 依赖类型 | 进入主链 | 当前边界 / 失效后果 |
|---|---|---|---|---|
| `L0-core` | 依赖方 | 编译期 | 是 | specific schema pending，不本地 shadow。 |
| `L0-sdk` | 编译 / 自测试依赖方 | 编译期 | 非运行主链 | 遵守全局基线；准确 target 后移，不进入 host truth。 |
| `L1-identity` | 依赖方 | 运行期 + 事件 | 是 | 不可用时新装配拒绝 / 等待，存量显式 stale。 |
| `L1-work` | 依赖方 | 运行期 + 事件 | 是 | 意图或项目主语缺失 / 冲突时不受理。 |
| `L1-governance` | 协作方 | 事件 | 非当前功能前置 | Policy 传递 owner 无当前 FR，保持 pending。 |
| `L3-method-library` | 间接上游 | 无直接边 | 否 | 本仓不得建立 Role -> image 第二解析路径。 |
| `L2-member-images` | 依赖方 | 运行期 + ref（详细合同 pending） | 是 | pinned entry 供给方向已正式成立；exact manifest / variant / ref / confirmation contract 仍 pending。 |
| `L2-member` | 协作方 | 运行期（详细合同 pending） | 是 | 需求级分工成立，字段 / IPC / 凭据 / 联调 waiting。 |
| `L2-runtime` | 协作方 / 消费方 | 运行期（pending） | 是 | host session 与 entry surface 双侧 pending。 |
| `L4-sandbox` | 依赖方 | 运行期 + ref | 条件性是 | 宿主 binding 失败则 blocked；逐动作 execute 不归本仓。 |
| `L0-bus` | 协作方 | 事件 | 是 | 交接已提交事实，delivery 失败不回滚 truth。 |
| `L4-observability` | 协作方 | 事件 | 是 | 只输出 body-free material / attempt / gap。 |
| 容器运行时 / 编排平台 | 依赖方 | 基础设施 adapter | 是 | 不可用时新启动 blocked，存量状态显式 unknown / degraded。 |
| 镜像 registry | 依赖方 | 基础设施 adapter | 是 | 拉取失败不伪装成功。 |
| 产品 / Workspace / Archive 消费方 | 被依赖方 | 下游消费候选 | 否 | 未校准，不反向定义本仓。 |
| `L2-tools` / `L3-capability-hub` / `L1-artifact` | 边界排除 | 无直接边 | 否 | 不转移工具执行、能力 registry 或制品 truth。 |

### 6.4 依赖类型

| 依赖类型 | 关联项目 | 本仓如何使用 / 提供能力 |
|---|---|---|
| 编译期依赖 | `L0-core`、`L0-sdk` | shared contract 类别与正式客户端 / Server 自测试基线；SDK 具体 target pending。 |
| 运行期依赖 | Identity、Work、Sandbox、Member、Member Images、Runtime | 正式事实消费、pinned 供给、宿主 binding、宿主内合同和会话承载。 |
| 事件协作依赖 | Bus、Identity、Work、Governance、Observability | 消费正式变化，交接已提交宿主事实与观测材料。 |
| ref seam | 适用外部 owner 对象 | body-free 关联表达，不改变 compile / runtime / event 类型。 |
| 基础设施 adapter | 容器运行时 / 编排平台、镜像 registry | 承载与资产拉取的可替换后端；adapter 不取得 authority。 |
| fake seam | runtime / event / adapter 的受控替身 | 只证明语义可控，不证明真实 backend、route 或对端 readiness。 |

### 6.5 禁止依赖

| 禁止依赖 | 禁止原因 | 正确协作方式 |
|---|---|---|
| 非 `L0-core` / `L0-sdk` sibling 的源码 / path / package 依赖 | 运行期或事件 seam 不得伪装编译期 | runtime / event / ref / adapter seam |
| SDK runtime client / transport 进入宿主 domain truth | compile 基线不等于运行期反向依赖 | 仅在正式编译 / 自测试边界消费 |
| 本仓反写 Identity / Work / Governance / Runtime / Sandbox truth | owner 反转 | 只消费正式事实，以事件 / handoff 反馈 |
| Work 或产品入口直连容器运行时 | 绕过宿主控制面 | 宿主生命周期统一经本仓 |
| 本仓 hardcode / 重解析 Role -> image | 形成第二映射 truth | 只消费 Member Images 正式 pinned 供给 |
| 本仓自建 policy allowlist / 本地裁决 | 吞并 Governance truth | 消费正式结论，unknown fail closed |
| 本仓提交 ToolInvocation 或推进逐动作 Sandbox execute | 吞并 Tools execution / Runtime progression | 只拥有宿主级 binding / release 与允许反馈 |
| 容器平台产品概念定义需求或对象语义 | 载体反向定义 truth | 在 adapter seam 内消化差异 |

### 6.6 Path dependency 判定

| 关联项目 | 依赖类型 | 允许写入 package dependency | 当前处理 |
|---|---|---|---|
| `L0-core` | 编译期 | 是，限正式发布 contract | 后续设计 / 实施按正式边界引入。 |
| `L0-sdk` | 编译期 / Server 自测试基线 | 是，但准确 target pending | 01 / 03 必须防止 runtime client 反向污染 domain。 |
| 其余全部 | 运行期 / 事件 / adapter / 下游 | 否 | 使用 API / event / ref / adapter / fake seam。 |

## 7. 核心能力闭环

> 校准来源：
> - `design-calibration/00_req_step_07_core_capability_loop.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“闭环定义”“核心能力节点表”“能力层级划分”和“待确认事项 / blocker”小节。

`L2-member-service` 的核心闭环是：正式宿主意图和执行主语能够被安全受理；宿主能够按正式镜像供给与运行环境约束装配到可判定的隔离就绪状态；宿主内来源能够注册并建立可用 host session；宿主健康与失败能够触发显式恢复或终止决定；清理、对账与已提交宿主事实最终能够闭合。

### 7.1 核心能力节点

| 节点 | 能力成立描述 | 本仓拥有 | 外部 owner / pending 边界 |
|---|---|---|---|
| `C-MS-1` 宿主意图与执行主语可受理 | 正式来源的 launch / stop / restart / relocate / no-action 意图可验证、去重并形成显式决定；项目型宿主具备 ProjectMember 执行主语和 GlobalMember 身份锚 | 受理判断、编排决定及历史 | Identity / Work truth 外置；当前版非项目型 launch fail closed |
| `C-MS-2` 宿主装配与隔离就绪可判定 | 正式 pinned 镜像供给、环境需求、宿主凭据和适用的宿主级 SandboxBinding 共同成立；partial 不伪装 ready | 宿主实例、分项装配结果、host readiness | Images 合同、credential owner、binding 字段 pending；镜像内容和 isolation truth 外置 |
| `C-MS-3` 注册与运行会话可用 | 宿主内来源凭正式凭据注册，endpoint 与 host session 关联唯一、可查询、可失效；Runtime run 只以 ref 关联 | 注册受理、endpoint、host session 壳与关联历史 | Member 详细合同和 Runtime entry pending；Member 内部与 run truth 外置 |
| `C-MS-4` 健康、恢复与终止受控 | 健康可判定并区分 host / session / backend / unknown；恢复、重启、停止、终止或 hold 均由显式决定触发，新实例不改写旧历史 | 健康判定、宿主失败分类、恢复 / 终止决定 | Runtime failure / checkpoint、业务影响、observed truth 外置 |
| `C-MS-5` 生命周期事实、清理与对账闭合 | 注册失效、宿主停止、binding release 关联、残留 / 孤儿对账和已提交事实交接可追溯；attempt / gap 不冒充外部完成 | 本地清理事实、对账结论、handoff attempt / gap、safe material 来源 | Sandbox cleanup、Bus delivery、Observability observed 与下游 accepted truth 外置 |

### 7.2 核心能力闭环图

```text
宿主意图与执行主语可被安全受理
  -> 宿主装配与隔离就绪可被可靠判定
  -> 注册与运行会话能够稳定可用
  -> 健康、恢复与终止能够受控
  -> 生命周期事实、清理与对账能够闭合
  -> 新的正式意图可以基于已闭合历史再次受理
```

该图只表达能力成立的逻辑依赖，不表达调用、事件、协议、运行顺序或实施步骤。

### 7.3 能力层级

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | C-MS-1 意图与执行主语；C-MS-2 装配与隔离就绪；C-MS-3 注册与会话；C-MS-4 健康、恢复与终止；C-MS-5 清理、对账与事实闭合 |
| 外围增强能力 | 容量 / 放置建议、正式资产预热、forensic body-free 关联材料、聚合宿主安全视图 |
| 边界外能力 | run / turn / checkpoint、Tool execution、逐动作 Sandbox execute、Member 内部门面、镜像构建 / 签名 / BOM、isolation truth、治理裁决、L1 truth、Observability backend、产品 UI、编排平台产品本体 |
| owner-pending 背景 | policy 到宿主传递路径与 launch credential 签发 / 撤销 owner；前者无当前 FR，二者都不得由本仓预建 truth |

任一正向合同未闭口时，对应节点只能处于 pending、waiting、blocked、degraded 或 unknown，不得声明 ready。

### 10.4 C-MS-4：健康、恢复与终止

| 规则编号 | 规则类型 | 规则内容 | 约束对象 |
|---|---|---|---|
| `BR-MS-027` | 不变量 | 健康判断必须保留信号来源、适用时点与新鲜度，并区分 host、session、backend 和 unknown 层级。 | 宿主健康与失败分类 |
| `BR-MS-028` | 禁止行为 | 心跳缺失本身不得直接等同 crashed、restart 或 terminate；进程存活本身也不得等同业务成功、Runtime 进度或隔离有效。 | 健康信号解释 |

| `BR-MS-030` | 显式变化 | 宿主健康结论和失败分类的建立、变化、恢复或 unknown 必须显式发生；迟到或冲突信号不得逆写当前结论。 | 健康与失败变化 |

| `BR-MS-034` | 禁止行为 | 外部副作用或提交结果 unknown 时不得盲重试、创建竞争宿主或升格为成功，必须保持 hold / blocked / unknown 语义。 | unknown fence |

### 12.4 Seam 类型与禁止转换

| seam | 当前语义 | 禁止转换 |
|---|---|---|
| compile | 仅 `L0-core` / `L0-sdk` 的正式契约与自测试基线 | 不把未闭口 schema 或 runtime client 当作已存在源码依赖 |
| runtime | Identity、Work、Member、Member Images、Runtime、Sandbox 的运行期能力协作 | 不写成 sibling path / package 依赖 |
| event | Bus 主干及 Identity、Work、Observability 的事件协作 | 不以 event 输出声明 delivered / observed / accepted |
| ref | 对外部对象的 body-free 关联表达，不改变其 compile / runtime / event 分类 | 不复制外部正文或建立第二 truth |
| adapter | 容器运行时 / 编排平台和镜像 registry 的可替换基础设施接缝 | 不让 Docker / Kubernetes 等产品概念定义宿主领域语义 |
| fake | runtime / event / adapter seam 的受控验证替身 | fake 通过不证明真实 backend、route 或对端 readiness |

禁止直接依赖：`L3-method-library`、`L2-tools`、`L3-capability-hub`、`L1-artifact` 不形成当前直接依赖边；本仓不得解析 Role -> image、提交 ToolInvocation、推进 Runtime run、拥有 artifact 正文或通过外部仓的源码路径取得运行期能力。

| 审计 / 可追溯 | `NFR-MS-012` 宿主实例世代、迟到 / 重复 / 冲突反馈和结论替代必须保留连续历史。 | 新事实回链旧事实且不原地抹写；可解释当前实例为何生效以及旧实例、反馈和缺口如何处置。 |
| 幂等 / 一致性 | `NFR-MS-013` 等价宿主意图在相同已提交事实下必须产生稳定结论，不得因重复或并发形成第二套生效决定或宿主。 | 对相同意图语境的重复和并发输入，当前决定、宿主关联和冲突语义唯一可判定。 |
| 幂等 / 一致性 | `NFR-MS-014` 同一当前宿主实例的活动注册、endpoint 和 host session 关联必须唯一；迟到、重放或旧实例输入不得覆盖当前关联。 | duplicate、replay、out-of-order、instance mismatch 和 replacement 场景中最多只有一个可判定当前关联，历史均保留。 |
| 幂等 / 一致性 | `NFR-MS-015` 装配 ready、健康、cleanup 和 handoff 各层语义必须保持单一正式含义，partial、attempt、receipt 或 snapshot 不得升格为完成 truth。 | 对 partial / unknown / stale / duplicate fixture 检查状态分层；不存在以局部结果替代整体或外部 owner 结论。 |
| 幂等 / 一致性 | `NFR-MS-016` 外部副作用或本地提交结果 unknown 时不得自动重放不可逆动作、竞争创建实例或改写既有事实。 | unknown 场景保持 hold / blocked / reconciliation-needed，直到新正式结论形成；不以“消除差异”为由删历史。 |
| 可观测性 | `NFR-MS-017` 宿主意图、装配、注册、会话、健康、处置、清理、对账和 handoff 的关键状态、变化与异常必须能形成最小、body-free、可关联材料。 | 即使 Observability backend 不可用，本地 safe material、查询结果或 handoff gap 仍足以判断是否发生及关联哪个宿主实例。 |
| 可观测性 | `NFR-MS-018` host、session、backend、binding 和 unknown 失败层级，以及依赖 unavailable、stale、conflict、partial 状态必须可区分。 | 任一异常均能定位到能力阶段和来源类别；不得把进程存活等同业务成功，也不得把外部失败压平为 host truth。 |
| 可观测性 | `NFR-MS-019` 事件 / 观测交接的本地 attempt、失败、重复和 gap 必须可见，但不得改变源宿主事实的成功或失败语义。 | 关闭或故障化 Bus / Observability 后仍可判断本地提交与交接状态，且源 truth 不回滚、不升格。 |
| 审计 / 可追溯 | `NFR-MS-020` 设计、测试、验收和实施材料必须持续区分 planned、waiting、blocked、not_run、fake-qualified 和真实 readiness。 | 任一正向合同或真实依赖未闭口时，不得出现无对应证据的 pass、ready、artifact、verdict 或 signoff。 |

### 13.2 判断口径与未来量化门禁

| 门禁 | 当前判断 |
|---|---|
| owner / scope | 无外部 truth 反转；非项目或授权不可证时 fail closed |
| forbidden-body / secret | 本仓 truth、查询、事件与证据材料中不得出现，发现即不通过 |
| readiness | 必要前置共同成立；partial / pending / fake 不得计为真实 ready |
| single truth | 无第二活动注册、第二 host session、竞争当前宿主或历史抹写 |
| result layering | local / attempt / delivered / observed / accepted 和 cleanup 各层不可混写 |
| evidence honesty | planned / blocked / not_run 不得写成 pass、artifact、verdict 或 signoff |

量化目标只有在以下信息同时具备 authority 后才能进入正式基线：稳定 workload 与宿主规模、执行环境、能力阶段边界、外部依赖状态、成功 / 失败 / unknown 定义、是否包含资产拉取、采样与统计口径、证据 owner、变更规则。缺一时只能记录候选测量维度，不能倒填目标或验收结果。

| 可候选量化维度 | 当前状态 | 后续落点 |
|---|---|---|
| 意图受理、当前事实查询、注册 / 信号受理延迟 | candidate_without_authority | 05 测试方案建立 workload 后讨论 |
| 装配、启动、恢复、终止和清理的分阶段耗时 | candidate_without_authority | 03 / 04 定义边界后，05 建立测量方法 |
| 并发宿主、信号和对账 workload | candidate_without_authority | 04 配置设计与 05 测试方案闭口 |
| handoff attempt 到外部反馈的延迟 | blocked_by_route_contract | Bus / Observability route 和 receipt owner 闭口后讨论 |

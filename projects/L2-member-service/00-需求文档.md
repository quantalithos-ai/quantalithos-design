## 2. 背景与问题定义

### 2.1 业务背景

Member 容器不是静态进程,而是根据项目、角色、Policy 动态创建、暂停、恢复、退休。需要一个容器外服务来管理:
- 启动 / 停止 / 删除容器
- 维护 endpoint registry
- 监控心跳
- 下发 Policy 更新
- 从 identity / method-library 拉身份与镜像信息

这就是 `quantalithos-member-service`。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点 |
|---|---|---|
| 设计文档 | README + ai-member 设计有描述 | 仓级需求未显式化 |
| Orchestrator 抽象 | Docker / k8s / local 已有方向 | 统一验收口径未固化 |
| Heartbeat | 30s × 3 失败策略已定 | 恢复与取证流程未仓级化 |
| Policy Proxy | 规则已提及 | 下发时延 / 行为边界未仓级化 |
| Identity Cache | 方向清晰 | 同步延迟容忍度未明确 |

### 2.3 为什么要做(量化依据)

- 没有 member-service,work 分配成员后无法真正启动对应容器
- README 目标明确:StartMember P95 < 5s(不含镜像拉取),单实例并发管理容器数 ≥ 500,heartbeat QPS ≥ 500
- L2 的其他 4 仓都直接受它驱动或影响

### 2.4 业务问题 vs 技术问题

- **业务问题**:如何让“成员分配”真的变成“一个可用的 AI 员工实例”
- **技术问题**:编排后端抽象、注册表、心跳、缓存、镜像映射、Policy 下发、崩溃恢复

## 5. 核心用例与用户故事

### 5.1 核心用例

1. ProjectMember 分配后启动成员容器
2. 成员容器定期 heartbeat
3. Policy 更新下发到容器
4. Role → image_variant 映射后拉对应镜像
5. crashed 成员自动重启并恢复 checkpoint

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **work 域**,我想要 **在 ProjectMember 分配后自动启动对应 AI 容器**,以便 **成员真正可用** |
| 优先级 | P0 |
| 验收条件 | **Given** AssignMember 成功 **When** 调 StartMember **Then** 容器启动并注册 endpoint |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **member 进程**,我想要 **周期性发送 heartbeat**,以便 **外部系统知道我还活着** |
| 优先级 | P0 |
| 验收条件 | **Given** member 在线 **When** 30s 周期 heartbeat **Then** member-service 更新最后心跳时间 |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **SRE**,我想要 **在 heartbeat 连续 3 次失败时标记成员 crashed 并重启**,以便 **减少静默失败** |
| 优先级 | P0 |
| 验收条件 | **Given** 3 次连续 heartbeat 失败 **When** 检测触发 **Then** member 标记 crashed + restart |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **治理系统**,我想要 **下发新的 Policy 到正在运行的容器**,以便 **规则动态生效** |
| 优先级 | P0 |
| 验收条件 | **Given** governance.policy.updated **When** policy proxy 分发 **Then** 30s 内容器侧拿到新规则 |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **Owner**,我想要 **用 Role → image_variant 选择正确镜像**,以便 **不同角色拿到合适工具集** |
| 优先级 | P0 |
| 验收条件 | **Given** role_in_project=backend-dev **When** 启动成员 **Then** 拉取 `ai-member-backend-dev` |

### 6.2 业务规则表

|---|---|---|
| BR-001 | 30s × 3 心跳失败 | 标记 crashed |

| BR-003 | Policy 更新 | 30s 内下发到容器 |
| BR-004 | 容器重启 | 重新签发 launch_token |

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 类型 | 生命周期 |
|---|---|---|
| ActiveMember | 记录 | starting → active / paused / crashed / retired |
| EndpointRecord | 映射 | create / update / delete |
| HeartbeatRecord | 时序记录 | append/update |
| PolicySnapshot | 缓存 | active / superseded |

### 9.2 数据关系

```
ActiveMember
  ├─ GlobalMemberId
  ├─ ProjectMemberId
  ├─ Role / image_variant
  ├─ EndpointRecord
  ├─ HeartbeatRecord
  └─ PolicySnapshot
```

### 9.3 数据生命周期与归档

热状态为主;历史启停/崩溃事件进入 observability / archive。

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| image 拉取失败 | 中 | 高 | 重试 / warm cache |
| cache 漂移 | 中 | 中 | periodic reconcile |
| k8s / docker 抽象不一致 | 中 | 高 | capability matrix |

### 12.2 边缘风险

- 心跳抖动导致误判 crashed
- 大规模并发启动压垮 registry
- launch_token 刷新与 runtime 恢复乱序

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| local binary 后端保留范围 | L2 后 | member-service |
| k8s / Docker feature parity | L2 后 | SRE + member-service |
| endpoint registry 冷清理策略 | L2 后 | member-service |

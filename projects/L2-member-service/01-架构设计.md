## 1. 业务背景与驱动力

### 1.1 业务背景

member-service 不是一个普通控制面 API,而是 L2 五仓里真正把“项目分配出来的 AI 成员”变成“可运行容器实例”的编排中枢。它把 work 域的 `ProjectMember`、identity 域的成员身份、method-library 的角色镜像定义、member/runtime 的容器内进程,接成一条可启动、可恢复、可审计的运行链路。没有它,成员分配只停留在业务状态,不会落成真正可连接、可心跳、可治理的运行实体。

### 1.2 业务驱动力

**业务驱动力**:
- 平台需要把 `work.project.member_assigned` 之类的业务事实,稳定转化为实际容器生命周期
- 容器启停、崩溃、恢复、Policy 下发必须可审计,否则 AI 员工运行过程不可追责

**技术驱动力**:
- 需要统一抽象 Docker / k8s / local 三类编排后端,避免上游直接绑定具体环境
- 需要把注册表、心跳、镜像映射、identity cache、恢复流程统一收口,否则 L2 运行面会碎片化

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | StartMember P95 | < 5s(不含拉镜像) | benchmark |
| 性能 | Heartbeat 处理 QPS | ≥ 500 | benchmark |
| 容量 | 单实例并发管理容器数 | ≥ 500 | benchmark |
| 延迟 | policy 下发延迟 | < 30s | 集成测试 |
| 一致性 | identity cache 同步延迟 | < 5min | 集成测试 |
| 可追溯性 | start/stop/crash/restart 事件覆盖 | 100% | 回归测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| 只管理 **ProjectMember 容器**,不管理 GlobalMember 业务实体 | ADR-0004 | 边界固定在运行实例,不侵入 identity 聚合 |
| Role → image_variant 必须来自 method-library / identity,不得硬编码镜像 | ADR-0005 | 启动链路必须保留镜像解析与缓存层 |
| 心跳 30s × 连续 3 次失败判 crashed | README + 需求文档 | 健康模型、恢复模型、告警模型固定 |
| 重启后必须重新签发 launch_token,不复用旧 token | README + runtime/member 边界 | 恢复链路必须串联 identity / member |
| 所有容器生命周期关键动作都要发事件留痕 | 三红线 + observability 约束 | 架构必须内建审计事件出口 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| 编排后端优先级 | Docker / k8s / local | 可按环境裁剪支持矩阵 |
| Endpoint Registry 落盘方式 | PG + 内存缓存 | 可演进到分层缓存 |
| policy 下发模式 | 订阅后主动推送 | 可演进为混合 pull/push |
| identity cache 形式 | 事件增量 + 周期 reconcile | reconcile 周期可调 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| 单实例并发容器数 | ≥ 500 | README |
| Heartbeat QPS | ≥ 500 | README |
| 启动延迟 | P95 < 5s | README |
| policy 生效延迟 | < 30s | README |
| identity cache 延迟 | < 5min | README |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 编排后端能力差异 | 中 | Orchestrator adapter 抽象 + capability matrix |
| 角色镜像映射规则 | 中高 | image resolver 独立模块 + cache |
| 容器健康与恢复策略 | 中 | heartbeat / recovery 独立上下文 |
| policy 下发方式 | 中高 | policy proxy 与 registry 解耦 |
| 上下游事件契约 | 中 | 统一 bus adapter + 事件 schema 锁定 |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **控制面分层 + 事件驱动编排**(当前) | 上游解耦、审计链清晰、恢复路径可插拔 | 模块较多 | ✅ |
| 纯同步 RPC 编排中心 | 流程直观 | 与 bus / replay / 异步恢复不匹配 | ❌ |
| 直接让 work 调 Docker/k8s | 实现快 | 边界塌陷、不可审计、不可迁移 | ❌ |
| 每种后端各自独立服务 | 后端最自由 | 重复实现 registry / heartbeat / policy | ❌ |

**最终选择**:**容器外控制面服务 + 事件驱动协同 + 后端适配器抽象**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 编排入口统一收敛到 member-service | 启停、心跳、恢复、审计口径统一 | member-service 成为关键控制面 |
| 编排后端必须走 adapter 接口 | Docker / k8s / local 可裁剪 | 需要维护能力差异矩阵 |
| 关键状态变化通过事件扩散 | observability / archive / chat / console 可订阅 | 引入最终一致性与补偿逻辑 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
work / process / governance / console / chat
                 │
                 │ RPC + events
                 ▼
        ★ quantalithos-member-service ★
        - orchestrator control plane
        - registry / heartbeat / recovery
        - image resolve / identity cache
        - policy propagation
           │         │         │
           │         │         └────────▶ governance policy events
           │         └──────────────────▶ identity / method-library
           └────────────────────────────▶ member containers(runtime + member)
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 启动 / 停止 / 重启 / 删除 ProjectMember 对应容器
- ✅ 维护 ActiveMember / Endpoint / Heartbeat / Launch 状态
- ✅ 解析 Role → image_variant,协调 identity / method-library / member-images
- ✅ 向运行容器下发 policy,并对 crash / recovery 进行编排

**不做什么**:
- ❌ 不维护 GlobalMember / Role 的业务真相(属于 identity)
- ❌ 不承担容器内推理、事件收发、IPC(属于 member / runtime)
- ❌ 不负责镜像构建与打包(属于 member-images)
- ❌ 不负责 ProjectMember 业务流程状态机(属于 work / process)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| `quantalithos-identity` | 99.9% | 启动时身份解析失败 | retry + last-known cache |
| `quantalithos-method-library` | 99.9% | image_variant 不可解析 | cache + drift warning |
| Docker / k8s API | 99.9% | 无法创建/销毁容器 | fail fast + backlog + degraded |
| image registry | 99.9% | 镜像拉取失败 | retry + warm cache |
| `quantalithos-bus` | 99.95% | 生命周期事件积压 | outbox / replay |
| 运行中 member 容器 | 高 | 心跳缺失或 endpoint 失效 | crashed 标记 + restart |

### 4.4 关键依赖风险

- orchestrator 抽象过薄会把 Docker/k8s 差异泄漏到上层,破坏可裁剪性
- identity / method-library 数据漂移会导致错误镜像启动或 policy 误下发
- bus 或 observability 不可用时,若没有补发链路,容器启停将失去审计证据

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Orchestration | 核心域 | 把业务上的成员分配转成真实容器生命周期 |
| Health & Recovery | 核心域 | 管理心跳、crash 判定、重启与恢复 |
| Registry | 核心域 | 维护 active member / endpoint 单一运行视图 |
| Policy Delivery | 支撑子域 | 向运行中成员传播治理规则 |
| Identity/Image Resolution | 支撑子域 | 身份、角色、镜像、launch_token 准备 |
| Audit & Event Bridge | 通用子域 | 生命周期事件发布与审计留痕 |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Launch | 启停、重启、删除、迁移编排 | LaunchRequest / ActiveMember |
| Registry | endpoint 与运行态登记 | EndpointRecord / ActiveMemberView |
| Health | heartbeat、crashed、restart 决策 | HeartbeatRecord / HealthState |
| Policy | 订阅并传播治理规则 | PolicySnapshot / DeliveryState |
| Resolution | Member / Role / image_variant / token 准备 | ResolvedMember / ImageSelection |
| Audit | 事件留痕与 replay 钩子 | LifecycleEvent / AuditEnvelope |

### 5.3 上下文映射关系

- work / process → Launch: **Customer-Supplier**，上游给生命周期意图,member-service 负责实现
- identity / method-library → Resolution: **Conformist + Cache**,member-service 遵从上游真相,本地只做缓存与漂移告警
- governance → Policy: **Open Host Service + Event Consumer**,通过标准事件触发下发
- member/runtime → Health / Registry: **Customer-Supplier**,member-service 拥有外部健康真相

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| ActiveMember | 一个已被 member-service 管理的项目级运行成员实例 | Launch / Registry |
| EndpointRecord | `member_id -> endpoint` 的可连接映射 | Registry |
| HealthState | `starting / active / degraded / crashed / retired` 等健康视图 | Health |
| ImageSelection | 由 Role / image_variant 解析出来的镜像决策结果 | Resolution |
| LaunchToken | 每次启动/重启签发的新运行令牌 | Resolution / Launch |
| PolicySnapshot | 当前应下发到容器的一组治理规则快照 | Policy |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
                     ┌──────────────────────────┐
                     │   member-service api     │
                     │  launch / stop / query   │
                     └────────────┬─────────────┘
                                  │
                                  ▼
        ┌─────────────────────────────────────────────────┐
        │             member-service core                 │
        │  orchestrator / registry / heartbeat / policy  │
        └───────┬─────────────┬──────────────┬────────────┘
                │             │              │
                ▼             ▼              ▼
         PostgreSQL       Event Bus      Docker / k8s API
                │                            │
                └──────────────┬─────────────┘
                               ▼
                    member container fleet
                   (member process + runtime)
```

### 6.2 每个容器的职责与技术栈

| 容器 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| member-service api/core | 启停编排、注册表、心跳、policy、恢复 | Rust | 控制面常驻进程 |
| PostgreSQL | active_members / endpoints / heartbeats / outbox | PostgreSQL | 持久化状态单写入者 |
| Event Bus adapter | 生命周期与治理事件传播 | Rust + bus client | 异步出站 |
| Docker / k8s adapter | 调后端创建/销毁容器 | Rust adapter | 受环境影响 |
| member container fleet | 实际成员执行体 | member(Rust) + runtime(Python) | 按角色镜像规模变化 |

### 6.3 通信方式与选择理由

| 通信场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| work / console → member-service | gRPC/结构化 RPC | REST | 生命周期命令明确、错误码可控 |
| member-service ↔ Docker / k8s | 官方 API / SDK | shell 执行 | 减少命令拼接风险,提升审计性 |
| member-service ↔ member 容器 | register / heartbeat / policy RPC | 纯事件 | 健康与下发需要低延迟可确认交互 |
| member-service → observability / archive | CloudEvents | 直写外部表 | 统一事件主干,便于 replay |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| ActiveMember | member-service | work / console / chat / observability |
| EndpointRecord | member-service | chat / console / runtime callers |
| HeartbeatRecord | member-service | SRE / observability / recovery logic |
| PolicyDeliveryState | member-service | governance / observability |
| Lifecycle outbox | member-service | bus / archive |

### 6.5 部署拓扑

- 生产默认:member-service 多实例 + PostgreSQL HA + k8s 编排后端
- 开发环境:单实例 member-service + Docker backend
- local backend 只作为开发/调试能力,不作为默认生产路线

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
control api / event intake
          │
          ▼
 launch orchestration
   ├─▶ resolution(image / identity / token)
   ├─▶ orchestrator adapters(docker / k8s / local)
   ├─▶ registry / heartbeat / recovery
   └─▶ audit / outbox / observability
```

### 7.2 层间约束规则

- Launch 层只表达生命周期意图,不直接拼接 Docker / k8s 细节
- Registry 是 `ActiveMember` 与 `EndpointRecord` 的单一写入者,其他模块只读
- Health 只能基于已登记的 ActiveMember 运作,不自建并行运行真相
- Policy 模块只负责传播与确认,不解释治理规则语义
- Audit/outbox 只承载事件留痕,不回写业务决策

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| OrchestratorAdapter | launch domain | docker / k8s / local adapter |
| MemberResolver | resolution domain | identity/method-library client |
| PolicyDeliveryClient | policy domain | member RPC adapter |
| LifecycleEventSink | audit domain | bus / observability adapter |
| RegistryStore | registry domain | postgres repository |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中高(work / console / governance / member) |
| 传出耦合 | 高(identity / method-library / docker / k8s / bus / observability) |
| 不稳定性 | 中 |
| 抽象度 | 中高(后端与外部依赖需 adapter 化) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者(写入方) | 消费者(读取方) | 一致性级别 | 风险标注 |
|---|---|---|---|---|
| ActiveMember | member-service | work / console / observability | 强一致(本地事务) | — |
| EndpointRecord | member-service | chat / console / routing callers | 强一致(本地事务) | — |
| HeartbeatRecord | member-service | health logic / observability | 最终一致(周期更新) | 心跳抖动可能误判 |
| ImageSelection cache | member-service | launch logic | 最终一致 | 上游漂移需告警 |
| PolicySnapshot | governance 为真相,member-service 为传播缓存 | member-service / containers | 最终一致 | 下发延迟受 bus 影响 |
| LifecycleEvent | member-service | observability / archive | append-only | bus 延迟需 outbox 保证 |

### 8.2 一致性层次

- **Level 1 · 本地强一致**:ActiveMember、EndpointRecord、Launch 状态迁移在单库事务内提交
- **Level 2 · 聚合间最终一致**:identity cache、image_variant cache、heartbeat 更新通过事件/周期 reconcile 对齐
- **Level 3 · 跨服务一致性**:启动成员属于长事务——解析身份 → 选镜像 → 创建容器 → 注册成功 → 发事件；任一步失败都需补偿或回滚

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| 容器创建成功但注册失败 | orchestrator success / member register timeout | 标记 launching_failed,执行 stop + cleanup | `launch_request_id` |
| policy 下发失败 | member 无 ack / timeout | 重试 + 标记 degraded + 记录 lag 事件 | `policy_version + member_id` |
| heartbeat 连续 3 次失败 | 周期检测 | 标记 crashed,签发新 token 并重启 | `member_id + crash_epoch` |
| image 拉取失败 | backend 返回 pull error | 终止启动并发失败事件 | `launch_request_id` |

## 9. 关键技术选型

### 9.1 Rust 控制面实现

| 维度 | 内容 |
|---|---|
| 当前选择 | Rust |
| 备选方案 | Go / Python |
| 选择理由 | 控制面常驻、并发多、需要明确资源边界；相比 Python 更稳,相比 Go 更易与现有 Rust L1/L0 栈一致 |
| 演进路径 | 外部 API 与 adapter 保持隔离,必要时边缘工具可多语言 |
| 不可逆程度 | 中 |

### 9.2 PostgreSQL 作为运行状态单写入存储

| 维度 | 内容 |
|---|---|
| 当前选择 | PostgreSQL |
| 备选方案 | 纯内存 + Redis / etcd |
| 选择理由 | ActiveMember / Endpoint / Heartbeat 既要查询又要追溯,PG 比纯缓存方案更适合作为控制面事实库 |
| 演进路径 | 热路径可加缓存,但单写真相仍保留在 PG |
| 不可逆程度 | 中 |

### 9.3 Adapter 化编排后端

| 维度 | 内容 |
|---|---|
| 当前选择 | Docker / k8s / local 统一 adapter |
| 备选方案 | 只支持单一后端 / 直接 shell |
| 选择理由 | L2 需要可裁剪且可迁移的运行面,后端差异应被限制在 adapter 层 |
| 演进路径 | 后续可新增 Nomad / serverless backend adapter |
| 不可逆程度 | 高 |

### 9.4 事件主干 + outbox 审计链

| 维度 | 内容 |
|---|---|
| 当前选择 | CloudEvents + outbox/replay |
| 备选方案 | 直接同步写 observability |
| 选择理由 | 生命周期动作不能因下游短暂不可用而丢审计,事件主干更符合可追溯与回放要求 |
| 演进路径 | 下游可增加 archive / alerting tap,不改变主写模型 |
| 不可逆程度 | 中高 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:统一控制面 + adapter(当前) | 方案 B:work 直接编排 | 方案 C:按后端拆多服务 |
|---|---|---|---|
| 核心思路 | member-service 统一承接生命周期 | 上游业务服务直接调容器后端 | Docker/k8s/local 各自服务化 |
| 优势 | 边界清晰、审计统一、恢复统一 | 路径短、初期实现快 | 各后端灵活 |
| 劣势 | 控制面复杂度集中 | 范围污染、不可迁移 | 重复建设 registry/heartbeat |
| 成本 | 中 | 低起步高维护 | 高 |
| 适配度 | 高 | 低 | 中低 |

### 10.2 最终选择与理由

选择 A,因为当前真正需要保护的不是“调用后端 API”这一步,而是容器生命周期的统一边界、审计链和恢复模型。B 虽快,但会让 work 域承担运行时复杂度；C 虽灵活,但过早把后端差异放大成服务边界,成本高于收益。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 超时 | launch / register / heartbeat / policy ack 都有明确超时,超时即进入失败或重试路径 |
| 重试 | image resolve、identity lookup、policy delivery 采用有限次重试 + 退避 |
| 降级 | method-library / identity 短时不可用时允许用短期缓存启动受控成员 |
| 熔断 | 后端 API 持续失败时暂停新启动请求,保护控制面 |
| 限流 | 启动风暴时按项目 / 实例总量做并发门控 |
| 隔离 | launch、heartbeat、policy、audit 分离执行通道,避免互相拖垮 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | launch decision / image resolve / restart / policy lag / crash forensic |
| 指标 | start latency / running count / heartbeat lag / restart rate / policy delivery lag |
| 追踪 | `trace_id` 贯穿 work 请求、容器启动、member register、policy delivery |
| 健康检查 | 控制面自身 liveness/readiness + backend adapter readiness |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| 认证 | 上游生命周期调用需受控身份,member register/heartbeat 使用 launch_token / service auth |
| 授权 | 只有受权系统可发起强制重启、stop、配置变更 |
| 审计 | start/stop/restart/crash/policy 全留痕并进入 observability |
| 密钥管理 | registry / backend / token 签发依赖统一密钥源,支持轮换 |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | backend 类型、heartbeat 周期、policy timeout、image registry 参数全部外部化 |
| 环境隔离 | dev 默认 Docker,prod 默认 k8s,local backend 仅开发启用 |
| 动态更新 | policy timeout、并发阈值、cache TTL 可动态调节 |
| 配置五要素 | 每个配置明确 name / type / default / constraint / source |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| launch orchestration(不含拉镜像) | < 5s P95 | benchmark | README |
| heartbeat ingest | ≥ 500 QPS | benchmark | README |
| policy delivery | < 30s | integration | README |
| identity cache reconcile lag | < 5min | integration | README |

**端到端延迟分解**(StartMember P95 < 5s,不含拉镜像):

```
P95 总预算 = 5s

  ┌ 身份/角色解析        ≤ 800ms
  ├ 镜像选择与参数组装    ≤ 500ms
  ├ backend create/start ≤ 2500ms
  ├ register / endpoint   ≤ 800ms
  └ 审计与回写            ≤ 400ms
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| local backend 的保留边界未定 | 影响 adapter 范围 | P1 |
| k8s / Docker feature parity 未细化 | 影响 capability matrix | P1 |
| endpoint 冷清理策略未定 | 影响 registry 漏洞与脏数据 | P1 |
| crash forensic 10 分钟保留策略细节未展开 | 影响运维成本 | P2 |

### 12.2 演进触发条件(可量化)

| 指标 | 阈值 | 演进动作 |
|---|---|---|
| 单实例容器管理数逼近 500 | 持续 2 周 | 拆分 launch / heartbeat / registry 热路径 |
| policy lag > 30s | 持续 1 周 | 优化 delivery pipeline / fanout 模型 |
| identity cache 漂移告警频发 | > 阈值 | 强化 reconcile / 缩短 TTL |
| backend 差异逻辑在上层蔓延 | 评审触发 | 下沉 capability matrix 到 adapter 层 |

### 12.3 演进步骤

```
阶段 1: Docker backend + registry + heartbeat + launch 跑通
   └─ 可停止点:单机开发环境能稳定启停成员

阶段 2: k8s backend + policy delivery + recovery 闭环
   └─ 可停止点:生产默认路径具备可用性

阶段 3: forensic / replay / 更细粒度 capacity control
   └─ 可停止点:控制面生产化增强
```

### 12.4 目标架构

目标不是把 member-service 做成“万能控制塔”,而是把它稳定收敛为 **L2 运行面的统一编排控制面**:上游只表达生命周期意图,下游只承接容器内执行,中间所有启动、恢复、审计、传播复杂度由 member-service 吞掉且可演进。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| image 拉取失败或镜像缺失 | 中 | 高 | warm cache + retry + fail fast |
| Docker / k8s 抽象不一致 | 中 | 高 | capability matrix + adapter 契约测试 |
| heartbeat 抖动导致误判 crashed | 中 | 中 | 30s×3 + grace window + forensic 保留 |
| identity / role 缓存漂移 | 中 | 中 | reconcile + drift warning |

### 13.2 边缘风险

- 大规模并发启动压垮 registry 或 backend API
- launch_token 刷新与 runtime checkpoint 恢复乱序,导致新旧实例混淆
- bus 不可用期间发生大量启停,若 outbox 回放不稳会造成审计缺口

### 13.3 待确认问题

| 问题 | 待定时限 | 负责人 |
|---|---|---|
| local binary backend 生产外是否保留 | L2 后 | member-service |
| k8s / Docker feature parity 口径 | L2 后 | SRE + member-service |
| endpoint registry 冷清理策略 | L2 后 | member-service |

## 14. 上线策略

### 14.1 灰度方案

```
阶段 1: 单开发项目 + Docker backend 样本成员
阶段 2: 扩到多角色镜像 + heartbeat / restart 验证
阶段 3: 切入 k8s backend 灰度项目
阶段 4: 打开 policy delivery 与 crash recovery 全链路
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| member-service 启动失败 | S 级 | 立即回滚版本并停止新启动请求 |
| StartMember P95 明显超标 | A 级 | 回退新 launch path 或关闭增量特性 |
| policy delivery 异常 | A 级 | 关闭下发通道,回退到 last-known-good policy |
| registry 冷清理异常 | B 级 | 停自动清理,人工核查并修复 |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| StartMember P95 | > 5s | warning |
| heartbeat lag / fail streak | > 阈值 | major |
| crash restart rate | > 阈值 | major |
| policy delivery lag | > 30s | major |
| identity cache drift | > 阈值 | warning |

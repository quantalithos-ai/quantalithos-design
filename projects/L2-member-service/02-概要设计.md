## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L2-member-service` 不是执行主脑,也不是工具目录。它是 **“成员执行宿主仓”**。

你可以把它理解成:
- runtime 发来的执行动作最终由谁真正承载
- 某个 AI 成员当前跑在什么执行载体上
- 成员上下文、tool scope、capability 是怎样被挂进执行环境的
- sandbox / tool / member 执行单元怎样真正开始、结束、失败和回收
- 执行单元的真实反馈怎样回给 runtime

这些事情,都由 `L2-member-service` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L2-member-service`,这些执行宿主事实就会散落在:
- `runtime` 的 dispatch 逻辑里
- `tools` 的调用适配层里
- `sandbox` 的隔离环境里
- 本地 worker / 容器 / 进程管理脚本里
- `conversation` 的执行反馈消息里

结果就会出现:
- runtime 同时背执行主线和执行宿主两套职责
- tool 挂载、sandbox 绑定、actor 上下文混在一起
- 某个成员到底在什么宿主上跑、为什么失败,没有统一归属
- sandbox / capability / actor context 的边界漂移
- 成员执行环境异常时,没有正式宿主真相层来解释发生了什么

所以 `L2-member-service` 必须独立存在,作为:
> **成员执行载体、运行环境挂载与执行宿主管理的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Member Execution Host
就是:
> 某个成员当前实际承载执行动作的正式宿主单元。

它回答的是:
- 这个成员当前在哪个执行载体里运行
- 当前这个宿主是否健康
- 它承载了哪些执行动作

#### Runtime Action
就是:
> runtime 发给 member-service 的正式执行动作。

它不是 member-service 自己发明的新业务动作,而是来自 runtime 的上游执行指令。

#### Capability Mount
就是:
> 某个成员在当前执行宿主里被挂载了哪些能力、工具范围、上下文限制。

它不是 capability-hub 本身的定义真相,而是成员宿主侧的装配结果。

#### Sandbox Binding
就是:
> 当前成员执行宿主绑定到哪个隔离环境、以什么边界运行。

它不是 sandbox 仓本体真相,而是 member-service 对 sandbox 的使用结果。

#### Host Failure
就是:
> 承载执行的宿主单元本身出问题了。

它不等于业务执行失败,也不等于 runtime 真相已经完成或失败。

#### Execution Feedback
就是:
> 宿主层把真实执行结果、错误和健康状态反馈回 runtime 的正式输出。

它不是 conversation 消息,也不是 artifact 正文本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L2-member-service/02` 时,先收稳以下前提:
- `L2-member-service` 不应按对象数拆,而应按主要部分拆
- member-service 至少应拆成“成员执行宿主与运行会话 / 能力挂载与上下文绑定 / 动作承接与实际执行 / 失败、重启与宿主恢复 / 执行反馈与宿主观测接缝”五个主要部分
- member-service 自己拥有的真相是 host/session/worker/health/capability mount/sandbox binding/execution handle
- `ExecutionInstance / WorkItem / ProcessInstance / Decision / Artifact 正文 / Conversation / Tool definition` 都不是 member-service 真相
- member-service 可以消费这些域的 refs、snapshots、signals,但不能把它们收编为自己的主真相
- 02 的重点不是“怎么跑容器”,而是先把“member-service 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,真正让成员“开始干活”的,不是流程本身,也不是工具目录本身,而是具体的成员执行宿主。用户真正需要的不是“runtime 决定了一步该做什么”,而是:
- 某个成员的执行动作能被真正承载起来
- capability、tool scope、sandbox、actor context 能被正确挂进执行环境
- 宿主层健康、失败、重启、回收有正式状态归属
- runtime 能得到稳定的执行反馈,而不是只看底层日志

如果把这些逻辑分别散落到:
- runtime 的 dispatch 代码
- tools 的适配层
- sandbox 的隔离环境
- 本地脚本和容器管理层
- conversation 的执行消息

系统会快速退化成:
- runtime 和 member-service 职责混层
- 成员宿主是否存活、为什么失败没有正式归属
- capability mount 和 actor identity 绑定逻辑漂移
- sandbox 是谁在控制、何时绑定、失败后怎么回收说不清
- 执行反馈散在日志中,无法成为正式上游输入

因此,本概要设计的任务就是:
> **把 `L2-member-service` 写成一个新人也能看懂的“成员执行宿主仓”,而不是把 runtime 指令、sandbox 隔离、tool 挂载和宿主健康混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 执行宿主归属 | 易散落在 runtime/tools/sandbox 中 | MemberExecutionHost 成为正式宿主真相层 | 需写死边界 |
| capability mount | 易和 capability definition 混层 | 宿主侧挂载结果独立存在 | 需正式落图 |
| sandbox bind | 易被视为基础设施细节 | sandbox binding 成为执行边界显式部分 | 需形成主要部分 |
| host failure | 易与业务执行失败混淆 | 宿主失败与业务失败严格分层 | 需单列并固定 |
| feedback 回流 | 易退化成日志输出 | member-service 正式反馈 runtime | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让 runtime 发出的正式执行动作真正落到成员宿主上运行,并把宿主健康、失败和反馈变成正式可消费真相
- **技术问题**:host/session/capability mount/sandbox bind/action execution/feedback/restart 之间的边界如何稳定建模,并与 `runtime/tools/sandbox/identity/work/process` 清晰协作而不混层

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ identity                   │
                    │ - actor identity           │
                    │ - capability snapshot      │
                    └────────────┬───────────────┘
                                 │ actor / capability bind
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ runtime                    │   │ member-service             │   │ tools                      │
│ - ExecutionInstance        │──▶│ - MemberExecutionHost      │──▶│ - tool invocation          │
│ - current step / state     │   │ - session / worker         │   │ - tool adapter             │
│ - dispatch intent          │   │ - capability mount         │   └────────────────────────────┘
└────────────────────────────┘   │ - sandbox binding          │
                                 │ - host health / feedback   │
                                 └────────────┬───────────────┘
                                              │ sandbox / health / execution feedback
                                              ▼
                    ┌────────────────────────────┐
                    │ sandbox / observability    │
                    │ - isolation boundary       │
                    │ - host metrics / logs      │
                    └────────────┬───────────────┘
                                 │ execution feedback / visible host state
                                 ▼
                    ┌────────────────────────────┐
                    │ work / process /           │
                    │ conversation               │
                    │ - upstream consume via runtime│
                    └────────────────────────────┘
```

### 4.2 位置解释

- `member-service` 自己负责“成员执行宿主”“运行会话”“能力挂载结果”“宿主健康”和“执行反馈”
- `runtime` 提供正式执行主线与 dispatch intent,member-service 负责承接并真正落地到宿主层
- `tools` 提供工具能力,member-service 负责把这些能力挂进宿主执行环境
- `sandbox` 提供隔离边界,member-service 负责绑定和使用,而不拥有 sandbox 本体真相
- `identity` 提供 actor / capability snapshot,member-service 消费并形成宿主侧 capability mount
- `work / process / conversation` 不直接消费 member-service 主真相,而主要经由 runtime 获取执行反馈和可见摘要

所以 `L2-member-service` 在全局里的角色是:
> **把 runtime 发出的正式执行动作真正承载到具体成员执行宿主上,并向上游返回宿主健康、执行结果和失败反馈的运行承载中枢。**

### 4.3 系统边界

**做什么**:
- 保存 MemberExecutionHost / session / worker / host health 真相
- 挂载 capability / tool scope / actor context
- 绑定 sandbox 执行环境
- 承接 runtime 发来的 dispatch action 并真正执行
- 回传 execution feedback / host failure / host health

**不做什么**:
- 不负责 WorkItem / child WorkItem 真相
- 不负责 ExecutionInstance / CurrentStep 真相
- 不负责 Governance decision 真相
- 不负责 Artifact 正文本体真相
- 不负责 Conversation / Turn 真相
- 不把 tools 或 sandbox 的本体定义并入 member-service 真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| runtime | 99.9% | dispatch intent 延迟时,现有 host/session 可保持当前状态,但不擅自发起新业务动作 |
| identity | 99.9% | capability snapshot 延迟时,默认保持最小 capability bind,不做越权挂载 |
| tools | 99.9% | 某工具能力不可用时,成员宿主进入 degraded / retryable 状态并回报 runtime |
| sandbox | 99.9% | 无法获得隔离环境时,不执行受限动作,而进入 blocked / host unavailable |
| observability | 99.9% | metrics/logs 延迟不影响宿主真相,但告警和观测会后到 |

### 4.5 关键依赖风险

- member-service / runtime 边界不稳会导致执行主线与执行宿主混层
- member-service / tools 边界不稳会导致 tool capability 定义与挂载结果混层
- member-service / sandbox 边界不稳会导致隔离边界变成隐式实现细节
- member-service / identity 边界不稳会导致 actor 真相与 capability mount 结果混层
- member-service / conversation 边界不稳会导致宿主反馈消息被误当正式宿主真相

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/接缝/能力差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 成员执行宿主与运行会话部分

- **它是什么**: 这是 `L2-member-service` 的宿主真相层,一起回答“这次执行由哪个正式宿主承载”
- **为什么单独有它**: 如果没有独立宿主主语,worker、session、container、执行状态会散落在 runtime 和基础设施里
- **负责什么**:
  - 定义 MemberExecutionHost
  - 定义 session / worker / host lifecycle / health
  - 维持 member-service 自己的宿主状态真相
- **不负责什么 / 容易混淆点**:
  - 不负责 ExecutionInstance 真相
  - 不负责 WorkItem / ProcessInstance 真相
  - 最容易和 runtime execution truth 混淆
- **与其他部分交互**:
  - 上游: runtime / identity
  - 下游: capability bind、dispatch、recover、feedback
  - 交互类型: 宿主锚点型
- **后续详细设计展开点**:
  - MemberExecutionHost / session / worker / health 模型
  - host lifecycle 规则

#### 能力挂载与上下文绑定部分

- **它是什么**: 这是宿主准备层,一起回答“执行前把哪些能力和上下文挂进去”
- **为什么单独有它**: capability 定义和 capability mount 不是一回事; 不单列就会把 capability-hub 和 member-service 混层
- **负责什么**:
  - 挂 capability snapshot
  - 绑定 tool scope
  - 绑定 actor / member context
  - 绑定 sandbox 环境约束
- **不负责什么 / 容易混淆点**:
  - 不定义 capability 本身
  - 不定义 sandbox 本体真相
  - 最容易和 tools / sandbox / identity 混淆
- **与其他部分交互**:
  - 上游: identity / runtime / tools / sandbox
  - 下游: 动作承接与实际执行部分
  - 交互类型: 执行前装配型
- **后续详细设计展开点**:
  - capability mount / sandbox bind / actor context 模型

#### 动作承接与实际执行部分

- **它是什么**: 这是 member-service 的动作执行层,一起回答“runtime 发来的动作怎样真正落到宿主层执行”
- **为什么单独有它**: 如果不单列,member-service 会退化成工具调用 adapter,看不见宿主层执行职责
- **负责什么**:
  - 接受 runtime action
  - 路由到 worker / tool / sandbox
  - 真正开始执行
  - 收敛动作级 handle
- **不负责什么 / 容易混淆点**:
  - 不负责 runtime 的业务执行主线决策
  - 不负责 tools 的能力定义真相
  - 最容易和 runtime dispatch / tools invoke 混淆
- **与其他部分交互**:
  - 上游: runtime action intent / capability bind
  - 下游: 失败、重启与宿主恢复部分 / 执行反馈与宿主观测接缝部分
  - 交互类型: 动作承接型 + 真执行型
- **后续详细设计展开点**:
  - action intake / host dispatch / handle model

#### 失败、重启与宿主恢复部分

- **它是什么**: 这是宿主故障层,一起回答“宿主出问题时怎么处理”
- **为什么单独有它**: host failure、worker crash、sandbox fault 和业务执行失败不是一回事; 不单列就会全部退化成 runtime failed
- **负责什么**:
  - 记录 host crash / unhealthy / recycle
  - 区分可恢复与不可恢复宿主故障
  - 负责 restart / recycle / host recovery
- **不负责什么 / 容易混淆点**:
  - 不负责 runtime 的业务恢复主线真相
  - 不定义 governance decision 真相
  - 最容易和 runtime recover / process wait 混淆
- **与其他部分交互**:
  - 上游: 动作承接与实际执行部分 / sandbox / health signals
  - 下游: 执行反馈与宿主观测接缝部分
  - 交互类型: 宿主故障恢复型
- **后续详细设计展开点**:
  - host restart / recycle / recoverable host failure 模型

#### 执行反馈与宿主观测接缝部分

- **它是什么**: 这是 member-service 的正式输出层,一起回答“宿主层真实反馈如何交回上游”
- **为什么单独有它**: 如果不单列,反馈会退化成 stdout/log 输出,无法成为 runtime 的正式输入
- **负责什么**:
  - 产出 execution feedback
  - 产出 host health report
  - 产出 runtime callback material
  - 为 observability 提供宿主侧观测材料
- **不负责什么 / 容易混淆点**:
  - 不直接决定 runtime 的 step progression 真相
  - 不负责 conversation 真相层
  - 最容易和 logs / conversation / runtime feedback 真相混淆
- **与其他部分交互**:

### 6.2 总解释

- `member-service` 自己负责“成员执行宿主”“运行会话”“能力挂载结果”“宿主健康”和“执行反馈”
- `runtime` 的交互主要落在 **成员执行宿主与运行会话部分**、**动作承接与实际执行部分** 与 **执行反馈与宿主观测接缝部分**,把正式执行动作交给 member-service 并拿回正式反馈
- `tools` 的交互主要落在 **能力挂载与上下文绑定部分** 与 **动作承接与实际执行部分**,由 member-service 把工具能力挂入宿主并实际调用
- `sandbox` 的交互主要落在 **能力挂载与上下文绑定部分** 与 **失败、重启与宿主恢复部分**,提供隔离边界并反馈宿主级异常
- `identity` 的交互主要落在 **能力挂载与上下文绑定部分**,把 actor/capability snapshot 引入宿主环境
- `work / process / conversation` 不直接消费 member-service 的主真相,而主要通过 runtime 获取正式整理过的执行反馈与可见摘要
- `observability` 消费的是 member-service 的 host health / logs / metrics / callback material

**读图方法**:
- 中间的 `member-service` 是执行宿主真相源,但内部不是按对象平铺理解,而是按 5 个主要部分理解
- 左侧输入的是 runtime 的 dispatch intent 和 identity 的上下文约束
- 右侧提供工具能力,下侧提供隔离和观测环境
- 真正给 work/process/conversation 的业务反馈,主要经 runtime 收口后再输出,member-service 不直接定义那些业务真相

## 7. 总体架构设计

### 7.1 架构风格与分层

## 8. 关键技术选型

### 8.1 为什么采用“宿主真相层 / runtime 真相层”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | runtime 持执行主线真相,member-service 持宿主承载真相 |
| 备选方案 | 把宿主状态直接并进 runtime |
| 选择理由 | 防止执行主线与执行载体混层,保住 runtime 与 member-service 职责分离 |
| 演进路径 | 后续可扩展更多宿主形态,但 execution truth 归属仍在 runtime |

### 8.2 为什么 capability 定义与 capability mount 分离

| 维度 | 内容 |
|---|---|
| 当前选择 | identity/tools 定义 capability,member-service 只持挂载结果 |
| 备选方案 | member-service 自己复制 capability 定义 |
| 选择理由 | 防止能力定义真相和宿主装配结果漂移 |
| 演进路径 | 后续可增强 mount 规则,但 capability 真相源不变 |

### 8.3 为什么宿主故障与业务执行失败分离

| 维度 | 内容 |
|---|---|
| 当前选择 | host crash / unhealthy / recycle 与 runtime business failed 分层 |
| 备选方案 | 所有宿主失败都直接变成业务 failed |
| 选择理由 | 宿主故障未必意味着业务执行不可恢复,需要给 runtime 正式恢复判断空间 |
| 演进路径 | 后续可细化 host recover 策略,但不把它们混回统一失败态 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: member-service 独立为执行宿主仓(当前) | 方案 B: 把宿主逻辑散进 runtime/tools/sandbox |
|---|---|---|
| 宿主真相清晰度 | 高 | 低 |
| capability/sandbox 边界 | 高 | 低 |
| 宿主故障可解释性 | 高 | 低 |
| 多层协作一致性 | 高 | 低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的正式执行不只是“runtime 发了个动作”。还必须有一个正式宿主层来承载成员执行单元、挂 capability、绑定 sandbox、记录宿主健康并返回正式反馈。如果把这些都散进 runtime/tools/sandbox,最后就没有一个仓能正式回答“是谁在承载这次执行、为什么这个宿主失败、这次反馈是否来自健康宿主”。

| AllocateExecutionHost | runtime action + actor/capability snapshot | MemberExecutionHost | 是 | 分配错误 |
| BindExecutionContext | host ref + capability/tool/sandbox context | bound host context | 是 | 绑定错误 |
| ExecuteRuntimeAction | host ref + runtime action | execution handle / initial feedback | 否 | 执行错误 |
| RecycleExecutionHost | host ref + reason | recycled host state | 是 | 宿主错误 |
| ReportExecutionFeedback | host ref + feedback | callback material | 是 | 回流错误 |
| QueryHostHealth | host ref | health / session / worker state | 是 | 查询错误 |

### 10.2 核心数据流(至少一条路径精确到函数调用链)

```text
runtime dispatch intent arrived
  │
  ▼
member-service selects or creates execution host
  │
  ▼
member-service binds capability / tool scope / sandbox context
  │
  ▼
member-service executes action on host
  │
  ▼
member-service returns structured feedback to runtime
  │
  ├─▶ runtime updates execution truth
  ├─▶ observability records host state
  └─▶ host stays alive / restarts / recycles
```

### 10.3 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 风险标注 |
|---|---|---|---|
| MemberExecutionHost / session / worker / health | member-service | runtime / observability | 被 runtime business truth 替代 |
| capability/tool/sandbox mount result | member-service(装配结果),定义真相在 identity/tools/sandbox | runtime / host dispatch | 与 capability 定义混层 |
| execution feedback / host callback material | member-service 输出, runtime 消费 | runtime / observability | 被 conversation 消息替代 |
| runtime action intent | runtime 真相,member-service 只消费 | member-service | 被 member-service 反向定义业务语义 |

## 11. 横切关注点

### 11.1 安全
- 未完成 capability / sandbox bind 的宿主不得执行正式动作
- member-service 不得越权扩大 capability / tool scope
- host recycle / restart 不得悄悄丢失正式失败反馈

### 11.2 性能
- Allocate / Bind / Execute 主链不应拖垮 runtime 反馈主线
- host restart / recycle 不应让上游长时间失去反馈能力

### 11.3 可用性
- observability 延迟不影响宿主真相和 feedback 回流
- sandbox 短时不可用时,host 可以进入 unavailable / blocked,但不能伪装成成功执行

### 11.4 可观测性
- runtime action → host execute → feedback / crash / recycle 全链必须可追踪
- host failure 与 business failure 必须能分别审计

### 11.5 成本
- 不把 runtime / tools / sandbox 真相并入 member-service,避免模型膨胀
- 不让每层都维护自己的“成员宿主状态”,降低长期维护成本

### 11.6 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| AllocateExecutionHost | ≤ 100ms | 100ms |
| BindExecutionContext | ≤ 100ms | 200ms |
| ExecuteRuntimeAction 发起 | ≤ 100ms | 300ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| MemberExecutionHost 与 ExecutionInstance 混层 | 中 | 高 | 在详细设计中继续固定 host truth 与 execution truth 边界 |

| sandbox 故障被误当业务失败 | 中 | 高 | host fault 与 execution failure 分层 |
| runtime 直接消费原始宿主日志替代正式 feedback | 中 | 高 | 固定 callback material contract |

- sandbox 与 tools 的能力差异若放大,宿主执行路径会继续分叉

## 13. 上线策略

### 13.1 灰度方案
- 先在单成员样板中验证 `AllocateHost → BindContext → Execute → Feedback` 最小主线
- 再验证 host crash / restart / recycle 与 runtime callback 主线
- 最后再引入复杂 capability mount、sandbox bind 和多工具执行路径

### 13.2 回滚策略
- 若 MemberExecutionHost 主模型不稳,先回退到“单宿主 + 最小健康状态”的保守路径
- 若 capability/sandbox bind 语义不稳,先收紧为最小能力集与最小隔离策略
- 若 feedback 回流不稳,先保留宿主真相与 observability,暂停复杂 callback 聚合路径

### 13.3 监控指标
- host 分配成功率
- context bind 成功率
- action 执行成功率
- host crash / restart / recycle 频率
- runtime callback 延迟与漂移率

## 15. 结论

本概要设计的核心结论是:
- `L2-member-service` 是成员执行载体、运行环境挂载与宿主管理的真相层,不是 runtime、tools 或 sandbox 的附属脚本层
- `L2-member-service` 内部应按“成员执行宿主与运行会话部分 / 能力挂载与上下文绑定部分 / 动作承接与实际执行部分 / 失败、重启与宿主恢复部分 / 执行反馈与宿主观测接缝部分”来理解,而不是按对象平铺理解
- `runtime` 管执行业务主线,`member-service` 管执行载体宿主; `tools` 管能力定义,`sandbox` 管隔离边界,`identity` 管 capability 来源,而 `member-service` 负责把它们真正装配进成员执行环境
- host failure 不等于 business failure,callback material 不等于 conversation 消息,capability mount 不等于 capability 定义
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把 host/session/worker、capability bind、sandbox bind、execution callback 和 host recovery 正式化

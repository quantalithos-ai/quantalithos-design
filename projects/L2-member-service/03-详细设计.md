## 1. 模块职责描述

**本模块做什么**:
- 持有正式 MemberExecutionHost / session / worker / health / capability mount / sandbox binding 真相
- 承接 runtime 发来的正式执行动作
- 将 capability、tool scope、actor context 挂进宿主环境
- 处理 host crash / restart / recycle / recoverable failure
- 把 execution feedback / host health / callback material 正式回给 runtime 与 observability

**本模块不做什么**:
- 不持有 `ExecutionInstance` / `CurrentStep` / `WorkItem` / `ProcessInstance` / `Decision` / `Artifact` 正文 / `Conversation` 真相
- 不等于 tools 本体或 sandbox 本体
- 不直接承担业务执行主线决策,也不直接承担前端展示正文

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 member-service“为什么存在”,而是让开发者可以直接开始实现:
- MemberExecutionHost / session / worker 如何建立
- capability / tool scope / actor context / sandbox 如何绑定
- runtime action 如何真正落到宿主层执行
- host crash / restart / recycle 如何处理
- execution feedback / host health 如何正式回流给 runtime / observability

如果不先把这些内容采集清楚,03 很容易退化成:
- 把 member-service 写成容器脚本说明
- 把宿主状态混进 runtime 执行主线真相
- 把 capability 定义和 capability mount 结果写混
- 把 sandbox 本体和 sandbox bind 写混
- 把宿主反馈退化成日志文本

## 4. 仓整体运行主流程

### 4.1 总流程图

```text
[runtime action / actor / capability / sandbox input]
                         │
                         ▼
[成员执行宿主与运行会话部分]
                         │
                         ├────────▶ [能力挂载与上下文绑定部分]
                         ├────────▶ [动作承接与实际执行部分]
                         ├────────▶ [失败、重启与宿主恢复部分]
                         └────────▶ [执行反馈与宿主观测接缝部分]
```

### 4.2 总解释

- **真相写入**发生在: MemberExecutionHost、MemberRuntimeSession、CapabilityMount、SandboxBinding、HostFailureReport、ExecutionFeedbackEnvelope 的正式持久化
- **执行前装配**发生在: capability / tool scope / actor context / sandbox bind
- **动作承载**发生在: runtime action intake → host dispatch → tool/sandbox execution
- **宿主恢复**发生在: crash / unhealthy / recycle / restart / recoverable host fault
- **反馈输出**发生在: runtime callback、host health、metrics/logs/traces 输出
- **同步路径**主要是: AllocateHost / BindExecutionContext / ExecuteRuntimeAction 主写链
- **异步最终一致**主要是: observability 指标、日志、部分 callback 物料消费

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `Host / Session / Worker / ToolCall / SandboxBind` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与反馈
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是宿主真相 / 装配 / 承接执行 / 宿主恢复 / 正式反馈,`03` 却只剩 worker 表
- 实现者知道有 host,却不知道 capability bind 和 callback 属于谁的责任
- sandbox bind、host crash、runtime callback 三条链路脱节

- 承接 `MemberExecutionHost ≠ ExecutionInstance`、`host failure ≠ business failure` 两条硬边界

#### 5.2.3 涉及的对象定义

```rust
/// 表示某个成员当前承载执行动作的正式宿主对象。
pub struct MemberExecutionHost {
    /// 宿主唯一标识。
    pub host_id: MemberExecutionHostId,
    /// 归属的成员引用。
    pub member_ref: MemberRef,
    /// 宿主当前生命周期状态。
    pub lifecycle_state: HostLifecycleState,
    /// 当前活跃运行会话。
    pub active_session: Option<MemberRuntimeSession>,
    /// 当前健康状态。
    pub health_state: HostHealthState,
}

/// 表示成员宿主当前的一次运行会话。
pub struct MemberRuntimeSession {
    /// 运行会话唯一标识。
    pub session_id: MemberRuntimeSessionId,
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// 当前承载的 runtime action 引用。
    pub runtime_action_ref: RuntimeActionRef,
}

/// 表示宿主生命周期状态。
pub enum HostLifecycleState {
    /// 宿主尚未准备好承载执行。
    Provisioning,
    /// 宿主可以承载执行动作。
    Ready,
    /// 宿主正在承载执行。
    Busy,
    /// 宿主已下线或被回收。
    Recycled,
}

/// 表示宿主健康状态。
pub enum HostHealthState {
    /// 宿主健康可用。
    Healthy,
    /// 宿主可用性下降,但可能仍可恢复。
    Degraded,
    /// 宿主不可用。
    Unhealthy,
}

/// 表示宿主内一个可承载执行的 worker 槽位。
pub struct WorkerSlot {
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// worker 槽位自身标识。
    pub slot_id: WorkerSlotId,
    /// 当前该槽位是否活跃。
    pub active: bool,
}
```

这些对象在该部分里分别承担:
- `MemberExecutionHost` 回答“这次执行是由哪个正式宿主承载的”
- `MemberRuntimeSession` 把“当前一次承载中的运行会话”写成正式对象
- `HostLifecycleState` / `HostHealthState` 把宿主级生命周期和健康显式化
- `WorkerSlot` 把宿主内部具体承载资源槽位显式化
- 它们都不替代 runtime 的 ExecutionInstance 真相

#### 5.2.4 关键函数代码片段

```rust
/// 为 runtime action 分配一个正式宿主并建立运行会话。
fn allocate_execution_host(
    host_repo: &dyn HostRepo,
    session_repo: &dyn SessionRepo,
    draft: AllocateHostDraft,
) {
    // [MemberExecutionHost::从草稿分配]
    // 先根据成员、能力快照和运行模式选定或创建宿主。
    let host = MemberExecutionHost::from_draft(draft);

    // [host.校验可承载]
    // 再校验宿主当前生命周期和健康状态是否允许承接执行动作。
    host.validate_assignable();

    // [host_repo.保存宿主]
    // 把正式宿主状态写入真相层。
    host_repo.save(host.clone());

    // [session_repo.创建运行会话]
    // 为本次 runtime action 创建正式运行会话。
    session_repo.create(MemberRuntimeSession::new(host.host_id));
}
```

这段实现守住的边界是:
- host truth 与 runtime execution truth 分开
- 宿主先被分配并验证健康状态,再进入执行动作绑定
- 运行会话不是 tool invoke log,而是正式宿主承载对象

#### 5.2.5 该部分的边界与非职责
- 不负责 capability 定义真相
- 不负责 sandbox 本体真相
- 不负责 runtime 执行业务主线决策
- 不负责 conversation 可见消息层

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `能力挂载与上下文绑定部分` 提供 host/session
- 向 `动作承接与实际执行部分` 提供 ready host
- 向 `失败、重启与宿主恢复部分` 提供 lifecycle / health 主语

#### 5.2.7 该部分的状态 / 约束 / 易错点
- host ready 不等于业务执行已开始
- runtime action ref 只是输入绑定,不等于 ExecutionInstance 真相本体
- unhealthy host 不得继续承载新动作

```rust
/// 表示当前宿主上已经挂载好的能力集合结果。
pub struct CapabilityMount {
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// 来自 identity/tools 的能力快照引用。
    pub capability_snapshot_ref: CapabilitySnapshotRef,
    /// 当前挂载是否成功。
    pub mounted: bool,
}

/// 表示当前宿主上绑定的工具范围。
pub struct ToolScopeBinding {
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// 当前允许的工具范围快照。
    pub tool_scope_snapshot_ref: ToolScopeSnapshotRef,
}

/// 表示当前宿主上的 actor 上下文绑定。
pub struct ActorContextBinding {
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// 当前 actor 引用。
    pub actor_ref: ActorRef,
}

/// 表示当前宿主绑定到的 sandbox 环境。
pub struct SandboxBinding {
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// sandbox 策略引用。
    pub sandbox_policy_ref: SandboxPolicyRef,
    /// 当前是否绑定成功。
    pub bound: bool,
}

/// 表示一次执行上下文绑定的整体结果。
pub struct EnvironmentBindingResult {
    /// 归属宿主。
    pub host_id: MemberExecutionHostId,
    /// capability mount 是否成立。
    pub capability_ready: bool,
    /// tool scope bind 是否成立。
    pub tool_scope_ready: bool,
    /// sandbox bind 是否成立。
    pub sandbox_ready: bool,
}
```

这些对象在该部分里分别承担:
- `CapabilityMount` 负责记录“能力已经被挂到宿主上”的结果
- `ToolScopeBinding` 负责记录工具范围挂载结果
- `ActorContextBinding` 负责记录当前 actor 上下文绑定结果
- `SandboxBinding` 负责记录隔离环境绑定结果
- `EnvironmentBindingResult` 负责把 capability/tool/sandbox 三类前置条件汇总成“宿主是否真正 ready”的正式判断

#### 5.3.4 关键函数代码片段

```rust
/// 在宿主真正执行前,把 capability、tool scope、actor 和 sandbox 环境绑定进去。
fn bind_execution_context(
    bind_repo: &dyn BindingRepo,
    host: &MemberExecutionHost,
    draft: BindExecutionContextDraft,
) {
    // [CapabilityMount::从草稿创建]
    // 先把 capability snapshot 和 actor context 固化成宿主侧挂载结果。
    let capability_mount = CapabilityMount::from_draft(host.host_id, &draft);

    // [capability_mount.校验可挂载]
    // 再确认能力快照、工具范围和 sandbox 策略都满足最小执行条件。
    capability_mount.validate_bindable();

    // [bind_repo.保存挂载结果]
    // 最后把 capability/tool/sandbox bind 结果正式写入真相层。
    bind_repo.save_bindings(host.host_id, capability_mount, draft.tool_scope_binding(), draft.sandbox_binding());
}
```

这段实现守住的边界是:
- capability mount 是宿主结果,不是能力定义真相本体
- sandbox binding 必须显式成功后,宿主才可进入可执行状态
- actor context bind 和 tool scope bind 不应被隐含在工具调用参数里

#### 5.3.5 该部分的边界与非职责
- 不负责 host 分配主语
- 不负责 dispatch 本身
- 不负责 observability 输出
- 不负责 runtime 执行业务推进真相

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `成员执行宿主与运行会话部分` 获取 host/session
- 向 `动作承接与实际执行部分` 提供 ready host context
- 向 `失败、重启与宿主恢复部分` 提供 bind failure 原因

#### 5.3.7 该部分的状态 / 约束 / 易错点
- bind 成功是执行前条件,不是执行结果
- capability definition 改变不应直接等于 mount result 已更新
- sandbox 未绑定成功时不得承载正式执行动作

#### 5.4.4 关键函数代码片段

```rust
/// 把 runtime action 真正落到宿主层执行,并获得宿主侧执行句柄。
fn execute_runtime_action(
    adapter: &dyn HostExecutionAdapter,
    handle_repo: &dyn HandleRepo,
    intake: &RuntimeActionIntake,
) {
    // [HostDispatchAction::从输入创建]
    // 先把 runtime action 翻译成宿主层可执行动作。
    let dispatch = HostDispatchAction::from_intake(intake);

    // [adapter.发起执行]
    // 再调用 tool/sandbox/member execution adapter 真正开始执行。
    let handle = adapter.execute(dispatch);

    // [handle_repo.保存执行句柄]
    // 把宿主层执行句柄正式保存,供反馈与恢复链使用。
    handle_repo.save(handle);
}
```

这段实现守住的边界是:
- member-service 只承接 runtime action,不重新定义业务主线
- dispatch 动作与执行句柄必须显式存在
- 工具层或 sandbox 的瞬时 handle 不能只留在 adapter 内部

#### 5.4.5 该部分的边界与非职责
- 不负责 runtime 的业务执行状态推进
- 不负责 host recovery 决策
- 不负责 callback summary 最终格式
- 不负责 capability 定义真相

#### 5.4.6 该部分与其他主要部分的接缝
- 从 `能力挂载与上下文绑定部分` 获取 ready context
- 向 `失败、重启与宿主恢复部分` 提供 host-level failure signals
- 向 `执行反馈与宿主观测接缝部分` 提供 execution handles 与底层反馈原料

#### 5.4.7 该部分的状态 / 约束 / 易错点
- dispatch success 不等于业务执行 success
- runtime action 未真正进入 host 时,不能伪造 callback material
- sandbox / tool invoke 失败必须可区分是 bind failure 还是 execute failure

```rust
/// 在宿主 crash / unhealthy / bind fail 时,记录正式宿主失败并执行重启或回收。
fn recycle_execution_host(
    host_repo: &dyn HostRepo,
    failure_repo: &dyn HostFailureRepo,
    host: &MemberExecutionHost,
    failure: HostFailureReport,
) {
    // [host.进入不健康状态]
    // 先把宿主主状态切换到 degraded/unhealthy。
    host.transition_to_unhealthy();

    // [failure_repo.记录宿主失败]
    // 再把宿主失败报告正式写入真相层。
    failure_repo.save(failure);

    // [host_repo.回收宿主]
    // 最后视故障类型决定回收/重启路径。
    host_repo.recycle_or_restart(host);
}
```

这段实现守住的边界是:
- host failure 必须正式记录
- 可恢复与不可恢复宿主故障必须区分
- recycle/restart 是宿主层动作,不是 runtime 业务状态本体

#### 5.5.5 该部分的边界与非职责
- 不负责 runtime 的业务 retry/recover 语义
- 不负责 tools 能力定义真相
- 不负责 conversation 展示层
- 不负责 artifact 正文真相

#### 5.5.6 该部分与其他主要部分的接缝

#### 5.5.7 该部分的状态 / 约束 / 易错点

- recoverable=false 时不得自动 restart
- host recycle 后旧 session / handle 不得继续被当活跃执行句柄

### 7.6 关键状态机 / 非法转换与约束

#### 状态机图

```text
HostLifecycleState:
provisioning → ready → busy
busy → ready / recycled
ready → recycled

HostHealthState:
healthy → degraded → unhealthy
unhealthy → healthy (after restart/recover)

MemberRuntimeSession:
created → active → closed
active → abandoned
closed / abandoned → [terminal]
```

#### 非法转换与约束表

| 场景 | 是否允许 | 说明 |
|---|---|---|
| 未 bind 完成的宿主直接承接正式执行动作 | ❌ | capability/tool/sandbox 都必须先完成绑定 |
| host crash 直接等于 business failed | ❌ | 宿主故障与业务失败必须分层 |
| sandbox 未绑定成功时执行受限动作 | ❌ | 隔离边界必须先建立 |
| conversation 直接消费原始宿主日志替代 callback material | ❌ | 原始日志不能替代正式反馈 |
| recycled host 继续复用旧 active session | ❌ | 回收后 session/handle 必须失效 |
| unhealthy host 被重新标记 ready 而无恢复过程 | ❌ | 必须经过正式 restart/recover |
| abandoned session 再次被标记 active | ❌ | 旧会话必须以新 session 重建 |
| degraded host 在未通过 assignable 检查前继续接新动作 | ❌ | degraded ≠ ready |

#### 关键约束说明

- `HostLifecycleState.ready` 只表示宿主可承载,不表示已经执行中
- `HostLifecycleState.busy` 下是否允许并发新动作必须显式受 host/session 规则约束,不能默认允许
- `HostHealthState.degraded` 不能被当作“逻辑上完全可用”
- `MemberRuntimeSession.abandoned` 代表旧 session 不可再复用,必须走 restart/new session 流程

## 11. 运行期主线场景

### 11.1 场景 A · runtime action 被成员宿主承接

```text
runtime 发 dispatch intent
      │
      ▼
allocate host
      │
      ▼
bind capability / tool scope / sandbox / actor context
      │
      ▼
execute on host
      │
      ▼
return formal execution feedback
```

**开发者关注点**:
- host truth 与 runtime truth 必须分开
- bind 成功先于 execute
- callback material 必须正式化后才能交 runtime

### 11.2 场景 B · 宿主 crash 后恢复

```text
host crash / unhealthy
      │
      ▼
record HostFailureReport
      │
      ▼
restart / recycle host
      │
      ▼
return formal host failure / recovery callback
```

**开发者关注点**:
- host crash 不等于 business failed
- restart/recycle 必须留痕
- 旧 session / handle 在回收后必须失效

### 11.3 场景 C · sandbox / capability bind 失败

```text
runtime action arrives
      │
      ▼
bind capability / sandbox
      │
      ├─ success → continue execute
      └─ fail    → host unavailable / bind failure callback
```

**开发者关注点**:
- bind failure 必须与 execute failure 区分
- 未 bind 完成不得进入正式执行
- observability 能看到宿主级失败链

### 11.4 场景 D · host 已执行但 callback material 写回失败

```text
host execute success
      │
      ▼
raw host result ready
      │
      ▼
callback material persistence failed
      │
      ▼
observability 先看到 host result / health
      │
      ▼
member-service 重试写 callback material
      │
      ▼
runtime 最终收到正式 callback
```

**开发者关注点**:
- 原始日志/结果和正式 callback material 必须区分
- callback material 回流失败不能抹掉“宿主实际执行过”的事实
- runtime 只有拿到正式 callback material 后,才算正式消费宿主反馈

### 11.5 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| runtime action | AllocateExecutionHost / ExecuteRuntimeAction | 成员执行宿主与运行会话部分 + 动作承接与实际执行部分 | host/session/handle |
| identity capability | BindExecutionContext | 能力挂载与上下文绑定部分 | capability/actor mount |
| tools / sandbox failure | host failure / callback path | 失败、重启与宿主恢复部分 | crash/unhealthy/recycle state |
| execution result | ReportExecutionFeedback | 执行反馈与宿主观测接缝部分 | runtime callback / host health |

## 12. 数据与存储设计

### 12.1 先分清写模型 / 读模型 / 证据引用

| 对象 | 类型 | 是否持久化 | 说明 |
|---|---|---|---|
| MemberExecutionHost / Session / WorkerSlot | 写模型 | 是 | 宿主主真相 |
| CapabilityMount / ToolScopeBinding / SandboxBinding | 写模型 | 是 | 装配结果真相 |
| HostFailureReport / HostHealthState | 写模型 | 是 | 宿主恢复与健康真相 |
| ExecutionFeedbackEnvelope / RuntimeCallbackMaterial | 输出写模型 | 是 | 正式反馈材料 |
| HostHealthView / FailureReportView / CallbackMaterialView | 读模型 | 是/可重建 | 只读消费与观测层 |
| runtime_action_ref / capability_snapshot_ref / sandbox_policy_ref | 引用 | 随真相持久化 | 只存 ref / snapshot |

### 12.2 关系与索引建议

| 表/集合 | 关键索引 |
|---|---|
| member_execution_hosts | `host_id`, `member_ref`, `lifecycle_state`, `health_state` |
| member_runtime_sessions | `session_id`, `host_id`, `runtime_action_ref` |
| capability_mounts | `host_id`, `capability_snapshot_ref` |
| sandbox_bindings | `host_id`, `sandbox_policy_ref`, `bound` |
| host_failure_reports | `host_id`, `failure_kind`, `recoverable` |
| execution_callbacks | `runtime_action_ref`, `host_id`, `callback_id` |
| host_metrics_snapshots | `host_id`, `captured_at` |

**索引理由**:
- `member_ref + lifecycle_state` 支撑快速定位某成员当前可用宿主
- `runtime_action_ref` 支撑 runtime callback 对账与重复回调去重
- `failure_kind + recoverable` 支撑宿主故障分流与恢复策略选择
- `sandbox_policy_ref + bound` 支撑隔离绑定状态巡检
- `captured_at` 支撑健康与指标时间序列回放

### 12.3 持久化建议

| 对象 | 存储方式 | 理由 |
|---|---|---|
| Host / Session / WorkerSlot | 主表 | 宿主真相不可丢 |
| Bindings | 主表 | 装配结果必须可审计 |
| HostFailure / Callback | 主表 / append-only history | 故障与反馈链必须留痕 |
| Health / Failure / Callback views | 可重建读模型 | 观测与消费侧解耦 |

**存储边界说明**:
- `MemberExecutionHost` 持有宿主主真相,但不得回写 runtime 的 ExecutionInstance 业务状态
- `CapabilityMount / SandboxBinding` 是装配结果,建议显式持久化,避免只存在启动时内存态
- `ExecutionFeedbackEnvelope / RuntimeCallbackMaterial` 建议 append-only 保存回调历史,以便上游对账和重放
- `HostFailureReport` 与 `HostHealthState` 要分层持久化,避免健康波动覆盖掉正式故障记录

### 12.4 关键校验

- host 分配前必须校验 member / actor / capability 输入最小成立条件
- bind 阶段必须在 capability/tool/sandbox 三类约束齐备后才允许继续
- host unhealthy/recycled 后不得继续承载旧 active session
- callback material 不得只保存在原始日志里而不正式写回

### 12.5 建议表结构草案

#### `member_execution_hosts`

|---|---|---|
| host_id | uuid | 主键 |

| lifecycle_state | enum | provisioning/ready/busy/recycled |
| health_state | enum | healthy/degraded/unhealthy |
| active_session_id | uuid nullable | 当前会话 |

#### `execution_callbacks`

| 字段 | 类型 | 说明 |
|---|---|---|
| callback_id | uuid | 主键 |
| host_id | uuid | 来源宿主 |
| runtime_action_ref | jsonb/text | 上游动作引用 |
| payload | jsonb | 正式 callback material |
| created_at | timestamptz | 回调时间 |

### 13.1 总体结构

```text

   │
   ▼
projection builders
   ├─ host health view
```

### 13.2 关键读模型说明

|---|---|---|

- 原始宿主日志、metrics 与正式 callback material 必须严格分层
- rebuild 顺序必须是: replay host/session truth → replay bind results → replay failures/callbacks → regenerate health/failure/callback views

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| host 分配失败 | 拒绝 allocate,返回 host invalid / unavailable |
| capability bind 失败 | 拒绝执行,返回 bind failure |
| sandbox bind 失败 | 拒绝受限动作,进入 host unavailable / recoverable failure |
| host crash | 记录 HostFailureReport,再按 restart/recycle 策略处理 |
| callback material 写回失败 | 保留原始反馈,重试正式 callback 持久化 |

### 14.1 重试 / 降级 / 熔断 / 补偿
- host degraded / sandbox bind fail 时允许重试装配,但未成功前不得执行正式动作
- host crash 若可恢复,允许 restart/recycle 后重新承载,但必须正式上报 failure
- callback material 回流失败允许稍后补写,但不得伪装成已成功回流
- raw host result 已存在但 callback material 未正式落库时,必须保留回放入口,不能只依赖临时日志
- recycled host 的旧 session/handle 必须统一失效,不得由 runtime 继续引用旧句柄

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 成员执行宿主与运行会话部分 | host 分配失败 / 会话冲突 | host allocation trace | 拒绝分配 / 重新选择宿主 | retry allocate |
| 能力挂载与上下文绑定部分 | capability/sandbox bind fail | bind trace | 拒绝执行 / 重试绑定 | replay bind |
| 动作承接与实际执行部分 | host 未真正接住动作 / handle 丢失 | execution handle trace | 重新发起 / 标记失败 | replay execute |
| 失败、重启与宿主恢复部分 | crash / restart 失控 | host failure trace | recycle / restart / mark unrecoverable | replay failure report |
| 执行反馈与宿主观测接缝部分 | callback material 漂移 / health report 延迟 | callback trace / metrics lag | 重试 callback / 补发 health | replay callback |

## 15. 实现红线 / 开发禁止事项

- 不允许把 MemberExecutionHost 简化成 runtime execution truth 的附加字段
- 不允许把 capability mount 结果直接当 capability 定义真相
- 不允许 sandbox 未绑定完成时承接正式执行动作
- 不允许 host crash 直接被误当成业务执行 failed
- 不允许把原始宿主日志直接当作 runtime 正式 callback material
- 不允许 degraded/unhealthy host 在未通过 assignable 校验前继续接收新动作
- 不允许 recycled host 继续持有旧 active session / execution handle
- 不允许用 observability 延迟来解释宿主真相未变化

| Host ≠ Execution truth | 主线测试 / 模型边界测试 | 一票否决项 |
| capability/sandbox bind | 装配测试 | 安全与治理门禁 |
| host crash / restart / recycle | 恢复主线测试 | 恢复门禁 |
| callback material 正式回流 | 接缝一致性测试 | 正式反馈门禁 |

---

## 17. 最小可运行闭环

- runtime 下发一个正式 action,member-service 成功 allocate host、bind context、execute action,并回给 runtime 正式 callback material
- 宿主发生一次 crash,member-service 正式记录 HostFailureReport,完成 recycle/restart,再把宿主故障反馈回 runtime
- observability 拿到宿主健康与 callback 材料,但不反向改变宿主真相

---

## 18. 结论

本详细设计的核心结论是：
- `L2-member-service` 的实现必须围绕五个主要部分展开,而不是按 host/session/tool/sandbox 对象平铺
- MemberExecutionHost / Session / Bindings / FailureReport 是正式宿主真相,callback/health/material 是正式输出层,但都不替代 runtime 执行业务真相
- runtime / identity / tools / sandbox / observability 的输入和输出都必须围绕 member-service 的正式宿主真相收口,不能再让原始脚本、日志和临时 worker 状态成为事实来源
- 后续测试与验收文档,应直接围绕 host truth、bind 边界、host failure/recover 和 callback material 展开

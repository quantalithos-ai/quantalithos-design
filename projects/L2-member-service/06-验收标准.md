## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收范围表”“只验接缝的下游 / 外部能力”“P0 / P1 / P2 裁决口径”和“范围项到 VETO 候选”小节，了解范围如何收敛。

本轮验收目标是裁决 `L2-member-service` 是否能作为成员执行宿主控制面成立：以 `ProjectMemberRef` 为执行主语、`GlobalMemberRef` 为身份锚，维护 Host Truth、装配 / readiness、registration / session、health / recovery、closure / reconciliation 和 body-free handoff；在无效、越权、重复、并发、迟到、依赖不可用和 unknown 场景下保持 fail-closed。

| 验收范围项 | 类型 | 优先级 | 裁决目标 | 非范围 / 说明 |
|---|---|---|---|---|
| 意图与决定闭环 | Host Truth | P0 | 双锚、project scope、显式决定、稳定重复 / 冲突和可追溯 history 成立 | 不裁决 L1 Identity / Work 正文 |
| 装配与就绪闭环 | Host Truth + seam | P0 | pinned supply、credential ref、carrier / binding、generation、readiness 分项可判定 | Images / Sandbox / runtime backend 正向产品行为后置 |
| 注册与会话闭环 | Host Truth + runtime seam | P0 | registration、endpoint、HostSession、single-active、generation 关联可判定 | 不创建 Runtime run / turn / checkpoint |
| 健康与处置闭环 | Host Truth | P0 | host / session / backend / unknown 分层，恢复 / 重启 / 停止 / hold 显式 | 不把心跳或进程存活当业务成功 |
| 清理、对账与交接闭环 | Host Truth + handoff | P0 | local closure、cleanup attempt、residual / case、immutable material 和四层 handoff 独立 | 不宣称外部 cleanup / delivery / observed / accepted |
| Command / Query / Consumer / Job | protocol | P0 | 10 / 6 / 5 / 7 入口的字段、写集、状态和 negative seam 可验证 | 不要求 sibling 内部实现 |
| material helper / outbox | event seam | P0 | `HostFactMaterialEventCandidate` 和 stored outbox material immutable、body-free、可回链 | Core/Bus event family、route、receipt 仍 pending |
| 数据和架构红线 | boundary | P0 | owner、不保存正文、不反写、依赖分类和 no-bypass 成立 | 不验证外部领域真相 |
| 非功能结构性门禁 | quality | P0 | 性能 sample、降级、恢复、幂等、redaction、观测和证据诚实可判定 | 无 authority 的硬 P95/SLA 不作为当前目标 |
| 容量 / 放置建议 | 外围增强 | P1 | 仅从 safe summary 派生，不改变 Host Truth | 不阻断 P0，需 selected-run |
| 资产预热 / forensic / 安全视图 | 外围增强 | P1 | attempt、safe ref、只读视图不成为写源 | 不保存外部正文或 evidence/report 内容 |
| 真实 provider / production-like | 产品接缝 | P1/P2 | 作为 selected-run、future 或 residual | 不以 unavailable 伪装 P0 passed |

P0 的固定分母为 5 个核心闭环、`AC-MS-001~039`、`VF-MS-001~009`、7 个实现模块、29 个业务对象、10 Command、6 Query、5 Inbound Consumer、1 个 `HostFactMaterialEventCandidate` 和 7 个 Operations Job。P1/P2 未完成不自动阻断 P0，但越界、伪装 ready 或反写 truth 时仍会触发对应 VETO。

## 4. 进入条件与退出条件

> 校准来源：
> - `design-calibration/06_acceptance_step_04_entry_exit.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“进入条件”“退出条件”“暂停 / 不可裁决条件”和“进入 / 退出来源追溯”小节，了解验收何时可开始和结束。

### 4.1 进入条件

- [ ] `00~05` source refs 已固定且送验交付与其一致。
- [ ] implementation commit、build id 和 image digest 已固定；不得以未实现或未知交付物送验。
- [ ] Core / core-contracts ref 已固定，或明确记录 `MSVC-UP-007/008` pending，不伪造 compile readiness。
- [ ] P0 profile、config digest、fixture / replay root、依赖 availability 和 blocker status 已固定。
- [ ] 使用固定且非 `latest` 的 `run_id`。
- [ ] 每个 P0 blocking suite 均有 `artifacts/test/<run_id>` raw artifact、case refs、stdout/stderr 和 digest。
- [ ] `reports/runs/<run_id>` 至少有 summary、gate-results、suite reports、evidence-index、redaction-check、dependency-boundary 和 report-audit。
- [ ] `reports/acceptance/handoff.md`、`veto-checklist.md`、`open-issues.md` 已生成；有 eligible residual 时还需 risk-acceptance。
- [ ] 未关闭 S / VETO、redaction、dependency 或 report-integrity 阻断项为零。

### 4.2 退出条件

- [ ] `AC-MS-001~039` 每项都有通过 / 失败 / 不适用的正式理由。
- [ ] `VF-MS-001~009` 均由真实 evidence / report / defect 状态检查，未静态默认未触发。
- [ ] 14 个固定 P0 EV 均能从 evidence-index 回指 TC、suite artifact、report path、digest 和 AC/VF。
- [ ] 10 Command、6 Query、5 Consumer、1 material helper、7 Job 的 P0 切口均有结论；Query no-write、Job no-truth-repair、generation / key fence、immutable material 和四层 handoff 有证据。
- [ ] redaction-check、dependency-boundary、report-audit 均通过；任一失败则总体不通过或暂停。
- [ ] S=0；A 已修复并复验，或逐项有合规风险接受且不触发 VETO；B/R 已进入开放项 / 风险文件。
- [ ] 最终结论只使用“通过”“有条件通过”“不通过”，签署角色和日期齐备。

### 4.3 暂停 / 不可裁决条件

| 条件 | 裁决 |
|---|---|
| 缺 source ref、implementation ref、run_id、raw artifact 或 report pair | 暂停；不得通过或有条件通过 |
| evidence index 静态生成、orphan EV、digest / TC / AC / VF 断裂 | `not_evaluable`；修复证据链后重验 |
| redaction / dependency / report-audit 失败 | 不通过或暂停；可能触发 VF-MS-005/008/009 |
| 上游 exact contract 未闭合但只影响明确 P1 正向 seam | P0 可在 controlled / disabled seam 裁决，正向部分列 residual |
| 上游 exact contract 未闭合且本仓无法证明负向 / fail-closed | 暂停受影响 AC；不得用 placeholder positive 替代 |
| 设计 source 与交付 source、profile、fixture 或 report 不一致 | 暂停并生成新基线 / 新 run |

进入验收不等于验收通过；退出条件必须由真实 run、artifact、report、EV、VETO、缺陷和风险状态共同证明。

| generation / cursor fence | old-generation feedback、older cursor 只写 late / unknown / gap / no-op，不覆盖 current。 | 旧反馈改变 current 或新 projection。 | `EV-MS-CONSUMER-001`、`EV-MS-IDEMP-001` | P0 失败。 |

### 8.2 一致性失败裁决

| 失败场景 | 必须保持 | 禁止动作 | 结论影响 |
|---|---|---|---|
| expected revision conflict | 回滚当前写集并返回 `Conflict`。 | merge、last-write-wins 或覆盖 current。 | 覆盖时不通过。 |
| stored result missing | 标记 consistency defect，按原 key 查证。 | 从 current truth 重算成功结果。 | 不得通过。 |
| external timeout / commit unknown | 保留原 effect / cleanup / publication / handoff key，进入 hold / gap。 | 换 key 盲重放。 | 可能触发 VETO-MS-006/007。 |
| projection rebuild failure | source truth 不变，view 为 `Stale / Degraded / Unavailable`。 | Query 内修复或反写 source。 | 触发 no-write 失败。 |
| duplicate consumer / publisher / job | replay stored receipt / report 或 reload / skip。 | 二次 mutation。 | 触发幂等失败。 |
| old generation feedback | late / unknown / gap / history，current 不变。 | 覆盖 current。 | 触发 generation fence 失败。 |

状态、UoW、幂等和结果层门禁必须在 `AC-MS-001~039` 的相关功能、红线和非功能项中同时满足；任一层以“最终报告”补写缺失事实均不构成通过。

## 12. 缺陷分级、复验与放行规则

> 校准来源：
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“缺陷分级表”“S 级与 VETO 升级表”“复验矩阵”“缺陷状态和关闭证据”和“放行判定矩阵”小节，了解缺陷状态如何与固定 run、原始材料和三值结论联动。

### 12.1 缺陷分级

| 级别 | 定义 | 对验收结论 | 关闭 / 复验要求 |
|---|---|---|---|
| S | VETO 命中，或破坏 Host Truth、owner、安全、redaction、依赖、证据完整性、Query no-write、Job no-truth-repair 或 P0 配置硬边界。 | 未关闭只能“不通过”；不可风险接受。 | 修复后跑原 TC、同族 blocking suite、全量相关 P0 和 redaction / dependency / report audit；新 run 证明未再触发。 |
| A | 未命中 VETO，但影响 P0 主线、sidecar、状态、UoW、幂等或关键报告。 | 默认阻断；仅在不影响硬边界、有完整证据和正式接受人时可“有条件通过”。 | 原 TC、相关 suite、影响范围回归；保留 failed run、fixed run 和 reviewer note。 |
| B | 不影响 P0 truth、安全和证据的局部质量问题。 | 可进入风险接受，不阻断 P0。 | 定向复验或后续维护；不得改写 P0 结果。 |
| R | 外部合同、真实产品、容量、保留策略或 future 能力未闭合。 | 记录为 residual；若为本轮必要前置则暂停 / 不通过。 | 合同 / 产品 / authority 闭合后新基线和 selected/full run；不得标记 fixed。 |

### 12.2 复验和关闭

修复不得覆盖原失败 run。最少必须保留 `failed run -> fixed change -> new run -> evidence/report -> reviewer` 的双向关联；复验范围按触发面扩大：

| 触发区域 | 最小复验 | 需要追加的门禁 | 主要证据 |
|---|---|---|---|
| subject / intent / decision | `TC-INTENT-*`、`TC-DECISION-*`、`TC-IDEMP-001~003` | owner / state 变化时全量 P0 | `EV-MS-CONTRACT-001`、`EV-MS-CMD-001` |
| qualification / assembly / readiness | `TC-QUAL-*`、`TC-ASSEMBLY-*`、`TC-DOMAIN-003`、`TC-CONFIG-*` | no-bypass 或 required seam 变化时全量 P0 | `EV-MS-DOMAIN-001`、`EV-MS-CONFIG-001` |
| registration / session | `TC-REG-*`、`TC-SESSION-*`、`TC-CONSUMER-002` | generation / single-active 变化时 operations replay | `EV-MS-CONSUMER-001`、`EV-MS-DOMAIN-001` |
| health / recovery | `TC-HEALTH-*`、`TC-RECOVERY-*`、`TC-IDEMP-005~008` | restart / unknown 变化时 operations replay | `EV-MS-DOMAIN-001`、`EV-MS-IDEMP-001` |
| closure / cleanup / reconciliation | `TC-CLOSE-*`、`TC-JOB-003/004/007` | external completion layering 变化时全量 P0 | `EV-MS-JOB-001`、`EV-MS-MATERIAL-001` |
| material / outbox / projection | `TC-MATERIAL-*`、`TC-JOB-005/006`、`TC-IDEMP-009/010` | cursor / immutable payload 变化时全量 P0 | `EV-MS-MATERIAL-001`、`EV-MS-JOB-001` |
| Query / Job no-write | `TC-QUERY-001~006`、`TC-QUERY-NEG-001`、`TC-JOB-NEG-001` | 任一 write-audit 变化时全量 P0 | `EV-MS-QUERY-001`、`EV-MS-JOB-001` |
| config / redaction / dependency | `TC-CONFIG-*`、`TC-REDACTION-*`、`TC-ARCH-001` | 任一硬门禁变化时全量 P0 | `EV-MS-CONFIG-001`、`EV-MS-REDACTION-001`、`EV-MS-ARCH-001` |
| report / evidence integrity | report-audit checks、`TC-REPORT-*` | 全部 blocking suite + evidence index | `EV-MS-REPORT-001` |

`fixed` 只表示责任人声明已修复，不等于通过；`blocked / waiting` 不能被关闭；失败再次出现时保留原 key、generation、run 和关联，不能用新 key 隐藏重复。

> 延伸阅读：

风险接受只适用于 B/R residual、明确不属于本轮 P0 的 P1/P2/future 项，或不影响硬边界且有完整证据、接受人、期限和后续动作的受限 A。当前所有候选均为 `pending`，不代表已接受。

### 13.2 风险接受文件要求

`reports/acceptance/risk-acceptance.md` 的每条记录必须包含：`risk_id`、`scope`、`impact`、`acceptance_reason`、真实 `evidence_refs`、`owner`、`acceptor`、`deadline_or_trigger`、`follow_up_ref` 和 `status`。设计期 `status` 只能为 `pending`；缺少接受人、期限 / trigger、证据或后续引用时，不得作为“有条件通过”依据。

以下事项不可风险接受：任何 `VETO-MS-001~009` / `VF-MS-001~009` 命中；S 级缺陷；owner truth 越界；forbidden body / secret / endpoint / manifest 泄漏；required seam fail-open；第二 current / session；unknown 盲重放或历史抹写；Query / projection / reconciliation / handoff / Job 反写 truth；非 Core / SDK sibling compile 依赖；evidence index、report、redaction、dependency 或 P0 config hard gate 失败；blocking suite `not_run` 被记录为通过。

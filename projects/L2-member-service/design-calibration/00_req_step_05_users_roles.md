## 3. SOP 问题回答

1. 本仓有哪些主要角色？

   回答：人类角色三类(平台运维 / SRE、宿主问题调查者、安全 / 边界审查者);系统角色五类(宿主意图触发方、正式事实提供方、宿主内注册与心跳来源、隔离能力协作方、宿主事实消费方)。

2. 哪些是人类角色,哪些是系统角色？

   回答：见 §7 两表。work / identity / governance / sandbox / member / runtime 等仓际关系一律作为系统角色的"来源 / 协作 / 消费"分类表达,不写成用户群体。

3. 这些角色分别在什么场景下接触本仓？

   回答：见 §7 使用场景列。

4. 是否存在管理、审计或维护类角色？

   回答：存在——运维 / SRE(维护编排边界与安全启停入口)、安全 / 边界审查者(审查 fail-open、凭据复用、正文泄漏、owner 串线)。

5. 是否需要进一步补权限矩阵？

   回答：不在需求层补具体权限矩阵。角色表只描述职责与接触场景;principal / scope / allow-deny 必须来自 Governance / Identity 正式 owner,本仓 fail-closed 消费。旧 00 §4.2 的角色权限矩阵(普通成员 / Tech Lead / Owner 等)预设了平台权限模型,无当前 authority,不继承。

## 5. 改动前后对比

| 项 | 改动前 | 改动后 | 原因 |
|---|---|---|---|
| 角色组织 | 用户群体表混合人类与仓 | 人类角色 / 系统角色两表 | 4.5 要求区分;仓际关系移到 Step 06 |
| 权限矩阵 | 预设平台授权模型 | 删除;角色不授予 authorization 尾注 | 授权真相归 governance / identity |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 保留旧用户群体 + 权限矩阵 | 连续 | 依赖当角色 + 越权定义授权 | 不采用 |
| 人类 / 系统角色两表 + 不授权尾注(runtime 范式) | 与已停审上游一致;边界干净 | 权限细节后置 | 采用 |

## 7. 结构化中间产物

### 人类角色表(正式 §5.1 候选)

| 角色 | 使用场景 |
|---|---|
| 平台运维 / SRE | 维护编排后端与装配输入边界,使用安全的启停 / 恢复 / 下线运维入口;不修改业务 truth,不绕过控制面直连容器 |
| 宿主问题调查者 | 沿宿主实例、装配、注册、会话、心跳、失败分类、恢复决定与清理事实的关联,定位启动失败、心跳缺失、恢复异常或孤儿实例 |
| 安全 / 边界审查者 | 审查凭据复用、fail-open、host fallback、正文 / secret 泄漏、宿主直连旁路和 owner 串线 |

### 系统角色表(正式 §5.2 候选)

| 角色 | 使用场景 |
|---|---|
| 宿主意图触发方 | 以正式来源(分配 / 回收事实、身份生命周期变化、运维请求)触发宿主编排意图 |
| 正式事实提供方 | 以 typed ref / safe summary / 事件提供身份摘要、分配事实、生效策略与 member-images pinned image ref / manifest，源 truth 仍归提供方 |
| 宿主内注册与心跳来源 | 宿主内进程凭正式凭据注册、上报心跳与状态(合同对端为并行未停审的 `L2-member`,seam pending) |
| 隔离能力协作方 | 按 `L4-sandbox` 正式边界承接宿主级 binding / release 并返回允许的失败 / cleanup refs；逐动作 execute caller 不归本仓 |
| 宿主事实消费方 | 消费 body-free 宿主状态 / 生命周期事件 / safe view,不反写本仓 truth |

### 授权尾注(正式 §5 尾注候选)

角色表只描述职责与接触场景,不授予 authorization。principal、scope、allow / deny 必须来自 Governance / Identity 等正式 owner;任何角色不得代表本仓声明 delivered、observed 或 accepted。

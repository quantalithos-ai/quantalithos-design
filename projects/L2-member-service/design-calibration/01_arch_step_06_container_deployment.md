## 2. SOP 问题回答

### 2.1 本仓有哪些正式运行承载角色

| 运行角色 | 承接范围 | 为什么独立表达 |
|---|---|---|
| 宿主控制入口单元 | 宿主意图、控制请求、注册受理、当前状态安全查询和必要的同步资格判断 | 需要在正式边界即时返回 accepted / rejected / waiting / conflict / unknown，而非伪装后台完成。 |
| 宿主生命周期推进单元 | 装配、宿主承载动作协调、恢复 / 终止、cleanup / release 和长时外部副作用收束 | 外部动作可能延迟、部分成功或结果未知，不能绑在同步入口成功语义上。 |
| 宿主信号与维护单元 | Member / backend / Sandbox 允许信号、上游变化、健康判定、残留对账、safe view 与事实交接 | 持续信号、周期维护和外围传播不应阻塞核心同步入口。 |

这三者是运行承载角色，不是源码模块或强制独立进程。当前可同部署，但必须在语义、失败和可扩缩边界上保持逻辑分离。

### 2.2 哪些正式承载依赖不可缺

- 宿主 truth 状态承载：保存本仓正式决定、实例世代、装配、注册 / session、健康、恢复、收束和 handoff gap；具体数据库产品未定。
- 事件 carrier：承接上游正式变化与本仓已提交 body-free 材料传播；它不保存本仓业务 truth。
- 宿主基础设施能力：承载实际成员宿主和 pinned 资产获取；只经 adapter 参与。
- Sandbox 能力边界：承接 required 宿主级隔离协作；本仓不运行 isolation backend。

### 2.3 哪些对象不应进入本仓部署图

- 受本仓管理的 Member 宿主实例不是 member-service 自身部署单元，只是外部承载能力所创建 / 管理的运行对象。
- Runtime、Member、Images、Identity、Work、Observability 的内部容器不属于本仓部署结构。
- Role / image definition、Tool execution、policy backend、artifact / archive storage 和产品 UI 不决定本仓运行承载，不进入主图。

### 2.4 哪些角色可同部署，哪些必须分离表达

| 关系 | 当前部署口径 |
|---|---|
| 控制入口与生命周期推进 | 可同部署，但同步接受结论不得等同后台副作用完成。 |
| 生命周期推进与信号 / 维护 | 可同部署，但长时动作、持续信号和对账必须有独立失败 / 恢复边界。 |
| 三类运行角色与正式状态承载 | 必须分离表达，承载产品可后选；运行角色不能以内存状态代替正式 truth。 |
| 本仓与宿主基础设施 / Sandbox | 必须通过外部能力边界分离；后端产品模型不得进入核心语义。 |
| 本仓与事件 carrier | 必须分离表达；事件传播失败不得回滚已提交本地 truth。 |

### 4.2 运行单元说明

| 对象 | 类型 | 主要职责 | 运行关系 | 说明 |
|---|---|---|---|---|
| 宿主控制入口单元 | 同步入口单元 | 承接正式意图、控制、注册和安全查询的即时边界判断 | 接收入站语境，将长时推进交给生命周期单元，读写正式状态承载 | 不声明外部动作、delivery 或 observed 已完成。 |
| 宿主生命周期推进单元 | 后台处理单元 | 推进装配、承载动作、恢复 / 终止和 local cleanup / release 的长时收束 | 消费已提交决定，经外部能力边界推进并提交本地结果 | partial / timeout / unknown 必须显式，不 host fallback。 |
| 宿主信号与维护单元 | 异步消费 / 后台处理单元 | 承接允许信号与上游变化，形成健康、对账、safe view 和 handoff gap | 消费外部材料与本地 truth，维护最终一致的外围结果 | 不把信号、投影或 receipt 作为核心写源。 |
| 宿主 truth 状态承载 | 正式存储承载 | 承载 A1~A5 正式 truth、必要 P1 / P2 影子和 P3 可重建投影 | 被三类内部运行角色依赖 | 不预设数据库、表、缓存或复制拓扑。 |
| 事件 carrier | 正式基础设施依赖 | 承接上游变化材料和已提交宿主材料传播 | 与信号 / 维护单元形成事件协作 | 不拥有 host truth、delivery 以外的业务完成状态。 |
| 宿主基础设施能力 | 运行时对接的正式外部边界 | 提供宿主物理承载、生命周期动作和 pinned 资产获取能力 | 被生命周期推进单元经 adapter 使用 | 资源存在不等于正式宿主存在。 |
| Sandbox 能力边界 | 运行时对接的正式外部边界 | 提供宿主级隔离 bind / release 与允许反馈能力 | 被生命周期推进 / 维护单元经正式 seam 使用 | 字段、caller、receipt pending；不表示真实集成 ready。 |

### 4.3 部署关系结论

当前基线采用“一个仓级运行边界、三个逻辑运行角色、一个正式状态承载、若干外部能力端口”的结构。三个运行角色可同部署，以降低未有规模证据时的运维复杂度；其语义、失败与扩缩边界仍须分开，后续只有 workload、故障隔离或吞吐证据出现时才讨论物理拆分。正式状态承载必须独立于单个运行实例表达，但产品与拓扑后移。受管理的 Member 宿主永远不视为 member-service 自身部署副本。

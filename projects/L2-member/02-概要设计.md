## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L2-member` 不是身份档案仓,也不是执行宿主仓。它是 **“AI 成员运行态主体仓”**。

你可以把它理解成:
- 一个 AI 成员在系统里如何作为“主体”出现
- 外界怎样和这个成员交互
- 成员当前对外暴露哪些能力、角色语义和行为接口
- runtime 怎样通过成员主体层去驱动执行
- conversation 里出现的那个“成员”为什么不是单纯一条消息或一个名字

这些事情,都由 `L2-member` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L2-member`,这些成员主体事实就会散落在:
- `identity` 的静态身份字段里
- `runtime` 的 execution actor 引用里
- `conversation` 的 participant / sender 消息里
- `member-service` 的宿主和 session 里
- `tools` 的 capability 列表里

结果就会出现:
- 成员“是谁”和“怎样作为运行态主体出现”混在一起
- runtime 知道要让谁执行,但没有正式成员主体层来承接
- conversation 里看得到成员发言,却不知道正式成员接口归谁
- capability 定义、成员可用能力出口、宿主承载彼此漂移
- member-service 的宿主真相和 member 的主体真相混在一起

所以 `L2-member` 必须独立存在,作为:
> **AI 成员运行态主体、对外交互接口与能力出口的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### Member Runtime Persona
就是:
> 某个 AI 成员在运行态对外呈现的主体画像。

它回答的是:
- 这个成员现在以什么方式出现
- 对外该被如何识别和调用

它不是 identity 的员工档案本体。

#### Member Interaction Endpoint
就是:
> 外界和某个成员交互时,正式进入 member 主体层的接口入口。

它不是 conversation 消息真相本身,也不是 runtime 的执行主线本体。

#### Exposed Capability
就是:
> 这个成员当前对外实际暴露和允许调用的能力出口。

它不是 capability-hub 或 tools 的定义真相本体,而是 member 侧的运行态暴露结果。

#### Execution Actor Binding
就是:
> runtime 在执行时把哪一个正式成员主体绑定为当前 actor。

它不是 ExecutionInstance 真相本体,也不是宿主层 host/session 真相。

#### Member Visible Summary
就是:
> 给 conversation / UI / 其他消费方看的成员摘要材料。

它不等于 member 主体真相本体,而只是对外可见层。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L2-member/02` 时,先收稳以下前提:
- `L2-member` 不应按对象数拆,而应按主要部分拆
- member 至少应拆成“成员主体与运行态画像 / 成员对外交互接口 / 成员能力暴露与行为出口 / 成员与执行主线接缝 / 成员可见摘要与下游消费接缝”五个主要部分
- member 自己拥有的真相是运行态 persona、主体接口、可暴露能力出口、execution actor binding、visible summary material
- `GlobalMember / ExecutionInstance / MemberExecutionHost / Conversation / Tool definition` 都不是 member 真相
- member 可以消费这些域的 refs、snapshots、signals,但不能把它们收编成自己的主真相
- 02 的重点不是“成员会不会说话”,而是先把“member 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,成员不是一个静态身份条目,也不是一个正在执行动作的 worker。用户真正需要的是:
- 这个成员如何作为一个运行态主体被看见、被调用、被协作
- 这个成员当前对外能提供哪些能力
- runtime 怎样以正式成员主体来承接执行,而不是直接对着 ID 或宿主动作说话
- conversation 看到的是成员主体发言,而不是底层宿主或工具直接发声

如果把这些逻辑分别散落到:
- `identity` 的静态档案
- `runtime` 的执行 actor 绑定
- `member-service` 的宿主和 session
- `conversation` 的 participant / sender 视图
- `tools` 的 capability 列表

系统会快速退化成:
- 成员档案、成员能力、成员执行主体和成员可见消息彼此混层
- runtime 可以执行,但不知道“是哪个正式成员主体在执行”
- conversation 能展示消息,但成员主体语义只是临时拼接
- capability 暴露没有稳定边界,导致成员侧接口和能力真相漂移

因此,本概要设计的任务就是:
> **把 `L2-member` 写成一个新人也能看懂的“成员运行态主体仓”,而不是把身份、执行、宿主、能力与消息表现混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 成员主体归属 | 易散落在 identity/runtime/conversation 中 | member 成为正式运行态主体层 | 需写死边界 |
| 对外交互接口 | 易与消息层或执行层混层 | member interaction endpoint 独立存在 | 需正式落图 |
| 能力暴露 | 易和 capability definition 混层 | exposed capability 成为成员侧运行态出口 | 需形成主要部分 |
| 成员与执行主线接缝 | 易直接用 actor ID 替代成员主体 | execution actor binding 独立成立 | 需单列并固定 |
| 可见摘要 | 易被误写成主体真相 | visible summary 明确只是下游消费层 | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让 AI 成员在平台里以稳定主体出现、承接交互、暴露能力,并与执行、消息、宿主层保持分层
- **技术问题**:member runtime persona、interaction endpoint、exposed capability、execution actor binding、visible summary 之间的边界如何稳定建模,并与 `identity/runtime/member-service/tools/conversation/capability-hub` 清晰协作而不混层

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ identity                   │
                    │ - GlobalMember             │
                    │ - role / capability profile│
                    └────────────┬───────────────┘
                                 │ static identity / capability input
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ conversation               │   │ member                     │   │ runtime                    │
│ - participant / sender view│◀──│ - runtime persona          │──▶│ - execution actor bind     │
│ - visible member summary   │   │ - interaction endpoint     │   │ - execution mainline       │
│ - member-facing material   │   │ - exposed capability       │   └────────────────────────────┘
└────────────────────────────┘   │ - visible summary          │
                                 └────────────┬───────────────┘
                                              │ host / capability / tool outlet consume
                                              ▼
                    ┌────────────────────────────┐
                    │ member-service / tools     │
                    │ - host/session             │
                    │ - tool capability          │
                    └────────────┬───────────────┘
                                 │ advanced capability catalog / composition
                                 ▼
                    ┌────────────────────────────┐
                    │ capability-hub             │
                    │ - capability graph         │
                    │ - capability composition   │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `member` 自己负责“运行态成员主体”“成员交互入口”“成员能力暴露”和“成员可见摘要材料”
- `identity` 提供静态成员身份、角色与 capability profile,但不直接定义运行态成员主体语义
- `runtime` 提供执行主线与 execution actor 绑定,但不直接承担 member 的主体层定义
- `member-service` 提供成员执行宿主与 session 承载,而 `member` 只定义主体层与对外接口层
- `tools` / `capability-hub` 提供能力定义和组合输入,而 `member` 决定成员当前如何对外暴露这些能力
- `conversation` 消费的是 member 的 visible summary 和成员主体材料,而不是静态身份真相或宿主真相

所以 `L2-member` 在全局里的角色是:
> **把静态身份、运行时执行、宿主承载与能力定义,收束成一个正式可交互、可引用、可暴露能力的成员主体层。**

### 4.3 系统边界

**做什么**:
- 保存 member runtime persona / interaction endpoint / exposed capability 真相
- 维护 execution actor binding 和成员对外交互接口
- 维护成员可见摘要与对下游消费的主体材料
- 为 runtime / conversation / tools / capability-hub 提供成员主体层接口

**不做什么**:
- 不负责 GlobalMember 静态身份真相
- 不负责 ExecutionInstance / CurrentStep 真相
- 不负责 MemberExecutionHost / session / worker 真相
- 不负责 Conversation / Turn 真相
- 不负责 tool definition / capability catalog 真相
- 不负责 WorkItem / ProcessInstance / Decision / Artifact 真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| identity | 99.9% | capability profile / role 输入延迟时,保留上次稳定 persona 和 capability snapshot,不自动扩权 |
| runtime | 99.9% | execution actor bind 延迟时,member 仍可作为主体存在,但不扩展为正式执行状态真相 |
| member-service | 99.9% | 宿主承载延迟时,member 主体仍存在,但不声称已实际承接执行；visible summary 可保留“可见但暂不可执行”语义 |
| tools | 99.9% | 可暴露能力列表可降级,但不伪装仍具备实际工具可用性 |
| capability-hub | 99.9% | 高阶能力组合延迟时,先保留基础 exposed capability |
| conversation | 99.9% | visible summary / member-facing material 延迟,但主体真相不受影响; 可回退到上次稳定可见摘要 |
| UI / readers | 99.9% | 前端延迟时只影响外显材料消费,不影响 member 主体层与 execution bind 真相 |

### 4.5 关键依赖风险

- member / identity 边界不稳会导致静态身份真相与运行态主体混层
- member / runtime 边界不稳会导致 execution actor binding 直接替代成员主体层
- member / member-service 边界不稳会导致宿主真相替代成员主体真相
- member / conversation 边界不稳会导致成员可见摘要被误当成员真相本体
- member / tools / capability-hub 边界不稳会导致能力定义、能力暴露和能力组合彼此漂移
- identity 已更新但 runtime persona / visible summary 未同步时,不同下游看到的“同一个成员”会发生主体漂移
- execution actor bind 已指向某成员,但 UI / conversation 仍展示旧主体材料时,会造成“谁在执行”解释分叉
- member-service 宿主已不可用但 member 仍被外显为“可执行”时,会让主体可见性与真实承载能力脱节
- capability-hub 暴露了新能力但 member 当前不应对外开放时,会造成能力出口越界

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/运行态/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 成员主体与运行态画像部分

- **它是什么**: 这是 `L2-member` 的主体真相层,一起回答“这个成员在运行态以什么主体出现”
- **为什么单独有它**: 如果不单列,成员主体会退化成 identity 档案字段、runtime actor ID 或 conversation sender 的拼装结果
- **负责什么**:
  - 定义 member runtime persona
  - 定义 member 的 behavior mode / availability / visible role semantics
  - 为交互接口和能力暴露提供稳定主体锚点
- **不负责什么 / 容易混淆点**:
  - 不负责 GlobalMember 静态身份真相
  - 不负责宿主层 host/session 真相
  - 最容易和 identity profile、conversation sender view 混淆
- **与其他部分交互**:
  - 上游: identity / runtime / capability-hub
  - 下游: interaction endpoint、capability exposure、visible summary
  - 交互类型: 主体锚点型
- **后续详细设计展开点**:
  - runtime persona / availability / mode 模型

#### 成员对外交互接口部分

- **它是什么**: 这是 `member` 的对外入口层,一起回答“外界怎样和这个成员打交道”
- **为什么单独有它**: 如果不单列,conversation 消息、runtime action 和成员接口会混在一起,看不见正式主体接口边界
- **负责什么**:
  - 定义 inbound interaction endpoint
  - 定义 member reply / action interface
  - 收敛对外调用 member 的正式入口语义
- **不负责什么 / 容易混淆点**:
  - 不负责 Conversation / Turn 真相
  - 不负责 runtime 执行业务主线
  - 最容易和 conversation input / runtime action intake 混淆
- **与其他部分交互**:
  - 上游: conversation / runtime / UI / external callers
  - 下游: execution actor binding、visible summary
  - 交互类型: 对外交互输入型
- **后续详细设计展开点**:
  - interaction endpoint / member-facing command/reply contract

#### 成员能力暴露与行为出口部分

- **它是什么**: 这是 member 的运行态能力出口层,一起回答“这个成员当前对外能做什么”
- **为什么单独有它**: capability definition、capability catalog 与 exposed capability 不是同一层,不单列就会把 capability-hub 和 member 混层
- **负责什么**:
  - 暴露 exposed capability
  - 定义 member-facing tool outlet
  - 对外呈现成员当前可用的行为接口
- **不负责什么 / 容易混淆点**:
  - 不负责 tools 的能力定义真相
  - 不负责 capability-hub 的能力编目真相
  - 最容易和 tools/capability-hub 混淆
- **与其他部分交互**:
  - 上游: identity / tools / capability-hub
  - 下游: interaction endpoint、runtime actor bind
  - 交互类型: 能力暴露型 + 行为出口型
- **后续详细设计展开点**:
  - exposed capability / outlet contract

#### 成员与执行主线接缝部分

- **它是什么**: 这是 member 与 runtime 的接缝层,一起回答“runtime 怎样通过成员主体层驱动执行”
- **为什么单独有它**: 如果不单列,execution actor binding 会直接替代成员主体层,让 runtime 和 member 合并
- **负责什么**:
  - 定义 execution actor binding
  - 维护 runtime-facing member context
  - 把“执行主脑的动作”接到“哪个成员主体”上
- **不负责什么 / 容易混淆点**:
  - 不负责 ExecutionInstance 真相
  - 不负责 MemberExecutionHost 真相
  - 最容易和 runtime / member-service 混淆
- **与其他部分交互**:
  - 上游: runtime / member-service / identity
  - 下游: visible summary、capability exposure
  - 交互类型: 执行主体绑定型
- **后续详细设计展开点**:
  - execution actor bind / member runtime context model

#### 成员可见摘要与下游消费接缝部分

- **它是什么**: 这是 member 的只读外显层,一起回答“别的仓如何安全消费成员主体层”
- **为什么单独有它**: 如果不单列,conversation / UI 会直接消费 member 主体真相对象,把外显和真相混成一层
- **负责什么**:
  - 提供 visible member summary
  - 提供 conversation/UI-facing material
  - 提供下游只读消费接口
- **不负责什么 / 容易混淆点**:
  - 不反向成为写源
  - 不拥有 execution truth / identity truth / host truth

## 8. 关键技术选型

### 8.1 为什么采用“静态身份 / 运行态主体”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | identity 保留静态身份真相,member 保留运行态主体真相 |
| 备选方案 | 让 identity 直接承载运行态成员主体 |
| 选择理由 | 防止静态身份和运行态交互语义混层 |
| 演进路径 | 后续可扩展 persona / mode,但静态身份真相归属不变 |

### 8.2 为什么成员主体层独立于 runtime 和 member-service

| 维度 | 内容 |
|---|---|
| 当前选择 | runtime 管执行主线,member-service 管宿主承载,member 管主体层 |
| 备选方案 | 把成员主体语义散进 runtime 或宿主层 |
| 选择理由 | 防止执行真相和主体真相、宿主真相互相覆盖 |
| 演进路径 | 后续可扩展更细 actor bind / outlet 规则,但主体层仍独立 |

### 8.3 为什么成员能力暴露与 capability 定义分离

| 维度 | 内容 |
|---|---|
| 当前选择 | tools/capability-hub 定义能力,member 只定义当前对外暴露出口 |
| 备选方案 | 直接把 capability catalog 暴露给外界 |
| 选择理由 | 防止“系统定义了什么能力”和“这个成员现在可对外做什么”混成一层 |
| 演进路径 | 后续可扩展 member-facing outlet 规则,但定义真相归属不变 |

### 8.4 为什么 visible summary 独立于 persona 真相

| 维度 | 内容 |
|---|---|
| 当前选择 | visible summary 作为只读外显层独立存在 |
| 备选方案 | 直接把 persona 对象作为 conversation/UI 展示对象 |
| 选择理由 | 防止下游为渲染和排序需要去修改主体真相,同时允许外显层延迟、裁剪和重建 |
| 演进路径 | 后续可扩展更多 member-facing material,但主体真相与外显层分离不变 |

### 8.5 为什么 execution actor binding 不直接挂在 identity 上

| 维度 | 内容 |
|---|---|
| 当前选择 | execution actor binding 作为 member/runtime 接缝独立存在 |
| 备选方案 | 直接用 static member id 或 identity profile 替代 |
| 选择理由 | 防止静态身份直接覆盖运行态主体语义,并保留 member 层对 actor 呈现方式和行为接口的控制 |
| 演进路径 | 后续可扩展多角色/多入口绑定规则,但 execution actor bind 仍不回退到纯静态身份字段 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: member 独立为运行态主体仓(当前) | 方案 B: 把成员主体散进 identity/runtime/conversation |
|---|---|---|
| 主体真相清晰度 | 高 | 低 |
| 对外交互边界 | 高 | 低 |
| 能力出口一致性 | 高 | 低 |
| 执行/宿主/消息分层 | 高 | 低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的“成员”既不是静态身份档案,也不是单次执行句柄,更不是一条聊天消息。它必须有一个单独的运行态主体层,把 identity 的静态身份、runtime 的执行主线、member-service 的宿主承载、tools/capability-hub 的能力输入和 conversation 的可见材料收拢为一致的成员主体接口。否则后续所有上层协作都会再次退化成临时拼接。

## 11. 横切关注点

### 11.1 安全
- 未暴露的 capability 不得被 member 对外宣称可用
- execution actor binding 必须以正式 member 主体层为准
- visible summary 不得暴露超出成员当前外显边界的信息

### 11.2 性能
- persona 构建与 visible summary 生成不应拖垮运行时交互主线
- exposed capability 查询应支持高频读侧消费

### 11.3 可用性
- conversation / UI 延迟不影响 member 主体真相存在
- capability profile 短时延迟时,不应错误扩权
- member-service 宿主暂不可用时,member 可继续作为可见主体存在,但不得伪装成“当前可执行”

### 11.4 可观测性
- identity → member persona → execution actor bind / visible summary 全链必须可追踪
- exposed capability 与 visible summary 变更必须可审计
- 同一成员在 runtime / conversation / UI 三侧的外显材料应可对账

### 11.5 主体一致性与外显边界
- persona 与 visible summary 必须能相互映射,但 visible summary 不能覆盖 persona 真相
- visible member ≠ executable member,外显可见性与当前可执行性必须分开表达
- exposed capability 必须只表达当前对外可用出口,不得偷带 capability catalog 全量

### 11.6 成本
- 不把 runtime/member-service/tools/capability-hub 真相并入 member,避免模型膨胀
- 不让每个仓各自临时拼成员主体,降低长期维护成本

### 11.7 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| CreateMemberPersona | ≤ 100ms | 100ms |
| ExposeMemberCapability | ≤ 100ms | 200ms |
| visible summary build | ≤ 100ms | 300ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| member / identity 边界不稳 | 中 | 高 | 在详细设计中继续固定静态身份与主体真相边界 |
| member / runtime 边界不稳 | 中 | 高 | 单独建模 execution actor binding |
| member / member-service 边界不稳 | 中 | 高 | 把宿主真相和主体真相明确分层 |
| visible summary 被误当主体真相 | 中 | 高 | 固定 visible material 只读边界 |

### 12.2 边缘风险

- member mode / availability 若后续细化更多运行态,会影响 exposed capability 规则
- capability-hub 若继续强化组合能力语义,member 的出口层可能扩展
- conversation / UI 若增加更多成员可见层需求,visible material 结构可能继续细分

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| member mode / availability 的最小状态集是否继续细分 | 03 阶段 | member |
| execution actor binding 是否允许一对多角色呈现(如同一成员多入口) | 03 阶段 | member + runtime |
| exposed capability 是否只暴露当前可用能力,还是允许同时暴露潜在能力与受限能力 | 03 阶段 | member + tools + capability-hub |
| visible summary 是否只拼 persona,还是允许拼接 execution-facing 状态提示 | 03 阶段 | member + conversation + UI |
| member 当前“可见”与“可执行”的状态是否继续拆分成两套显式字段 | 03 阶段 | member + runtime + member-service |

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在单成员样板中验证 `persona → visible summary → execution actor binding` 最小主线
- **阶段 2**: 再验证 `exposed capability → runtime / conversation / callers consume` 主线
- **阶段 3**: 再引入 `member-facing execution context → member-service consume` 主线,验证主体层与宿主层分离
- **阶段 4**: 最后再引入更复杂的 member mode / capability composition / multi-entry member contexts

### 13.2 回滚策略
- 若 runtime persona 主模型不稳,先回退到“最小主体画像 + 最小 execution actor bind”的保守路径
- 若 exposed capability 语义不稳,先收紧为基础能力暴露集
- 若 visible summary 不稳,先保留主体真相与 execution bind,暂停复杂 UI-facing material
- 若 member-facing execution context 不稳,先禁止其向 member-service 扩展更多主体语义,退回最小执行 actor 绑定材料

### 13.3 监控指标
- member persona 创建成功率
- execution actor bind 成功率
- exposed capability 查询成功率
- visible summary 漂移率
- member-facing material 回放一致率

## 15. 结论

本概要设计的核心结论是:
- `L2-member` 是 AI 成员运行态主体、对外交互接口与能力出口的真相层,不是 identity、runtime、member-service 或 conversation 的附属层
- `L2-member` 内部应按“成员主体与运行态画像部分 / 成员对外交互接口部分 / 成员能力暴露与行为出口部分 / 成员与执行主线接缝部分 / 成员可见摘要与下游消费接缝部分”来理解,而不是按对象平铺理解
- `identity` 管静态身份真相,`runtime` 管执行主线真相,`member-service` 管宿主真相,`tools/capability-hub` 管能力定义与编目,而 `member` 负责把这些输入收束为正式成员主体层
- visible summary 不是主体真相,execution actor binding 不是 ExecutionInstance 真相,exposed capability 不是 capability definition 真相
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把 runtime persona、interaction endpoint、exposed capability、execution actor binding 和 visible material 正式化

## 3. SOP 问题回答

1. 如果没有这个仓,系统会缺什么不可替代的能力或结构?

   回答: 缺少"成员容器对外交互边界"的唯一 owner——Runtime 将直接暴露于事件主干与宿主,入站风险无预筛,出站发布无决定记录,成员在场无人表达;或者这些语义散落在 Runtime / 宿主 / bus 适配层形成多真相。

2. 这个仓成立必须共同具备哪些能力?

   回答: 五项——可验证执行主语下的运行态在场成立;入站筛选与受控投递成立;出站承接与发布成立;交互事实可追溯成立;摘要与能力出口成立。

3. 哪些能力缺一个,这个仓就不算真正成立?

   回答: 前四项。缺在场则听说无主体;缺入站则 Runtime 裸暴露;缺出站则成员输出无决定层;缺追溯则筛选 / 发布决定不可审计,门面退化为管道(旧文档的结构性缺陷)。第五项(摘要 / 能力出口)是派生消费面——但"成员状态可被外部安全理解"仍是门面存在的一部分,故保留为核心第五节点,其中能力出口子项可裁剪。

4. 哪些能力只是外围增强?

   回答: 筛选统计 / 误拦截诊断摘要、交互历史浏览、订阅 / 出站配置的可解释视图、能力出口的比较 / 检索体验。

5. 哪些能力根本不属于这个仓?

   回答: 运行决策链(loop / plan / memory / checkpoint)、工具契约与执行、capability registry / 外呼 adapter、容器编排与健康裁决、镜像构建、隔离执行、approval / policy truth、对话真相、observability backend、身份生命周期。

6. 当前已有或预期功能中,哪些在支撑这些核心能力?

   回答: draft 02 §2 的 FR 候选 15 项按节点映射(C1:001~003;C2:004~007;C2/C3:006、008~009;C4:010~012;C5:013~014;横切:015),Step 9 逐节点复核。

7. 核心能力闭环应拆成哪些能力节点?

   回答: `C-L2M-1` 运行态在场与宿主协作;`C-L2M-2` 入站筛选与受控投递;`C-L2M-3` 出站承接与安全发布;`C-L2M-4` 交互追溯与安全材料;`C-L2M-5` 成员摘要与能力出口。

8. 这些能力节点应按什么顺序逐个讨论?

   回答: C1 → C2 → C3 → C4 → C5。C1 是主体前提;C2 / C3 是"听"与"说"两条主线;C4 横切依附于 C2/C3 的已提交事实;C5 是派生消费面。

9. 每个能力节点完成停审时,必须证明哪些内容已经收敛?

   回答: 该节点的用户故事、功能需求、规则、数据归属、接口边界、质量约束和验收条件全部回指该节点且无孤儿项(Step 8~14 逐步承接)。

## 6. 结构化中间产物

### 6.1 闭环定义短文(候选)

`L2-member` 的核心能力闭环不是订阅、过滤、发布等动作的功能串联,而是:一个项目型成员实例必须以 `ProjectMemberRef` 执行主语、关联的 `GlobalMemberRef` 身份锚与可验证启动语境进入在场状态;在场成员必须能对入站事实形成受控的筛选结论与投递决定;必须能对运行结果形成受控的出站决定与发布尝试;上述交互事实必须可安全追溯;成员状态与可承接范围必须能被外部安全理解。任一能力缺失,本仓都会退化为转发管道、第二个运行决策 owner 或不可审计的黑盒,无法承担成员交互边界真相源。非项目型实例在正式执行主语闭口前不进入正向闭环。

### 6.2 核心能力闭环图

```text
运行态成员能够以可验证语境进入在场状态
  -> 入站事实能够形成受控的筛选结论与投递决定
  -> 运行结果能够形成受控的出站决定与安全发布
  -> 成员交互事实能够被安全追溯
  -> 成员状态与可承接范围能够被外部安全理解
```

本图只表达能力成立的逻辑依赖关系,不是每次交互的运行时路径(入站与出站在运行中并发存在),也不是接口时序、事件传播顺序或实施步骤。

### 6.3 核心能力节点表

| 顺序 | 节点 | 能力成立描述 | member owner | 外部 owner 边界 | 缺失后果 |
|---:|---|---|---|---|---|
| 1 | `C-L2M-1` 运行态在场与宿主协作 | 项目型成员实例以 `ProjectMemberRef` 执行主语、关联的 `GlobalMemberRef` 身份锚与可验证启动语境进入在场,具备就绪 / 降级 / 退出语义,并向宿主提供注册请求 / 存活信号 / 状态报告 | 本地 presence 语义、启动语境受理、请求 / 信号 / 报告及尝试记录 | ProjectMember truth(work)、GlobalMember truth(identity)、凭据签发、注册接受 / endpoint registry / host session / 健康判定 / 编排(member-service)、容器生命周期 | 听说无主体可归属;宿主只能猜测成员状态,或身份锚被误作执行主语。 |
| 2 | `C-L2M-2` 入站筛选与受控投递 | 订阅范围决定、入站筛选结论(通过 / 降级 / 阻断 / 待定)与向 Runtime 的投递决定成立且可解释 | 订阅决定、筛选结论、投递决定与记录 | bus delivery truth、policy 裁决(governance)、Runtime 受理处置 | Runtime 裸暴露于事件主干;注入类风险无预筛;投递无决定记录。 |
| 3 | `C-L2M-3` 出站承接与安全发布 | 从 Runtime committed safe material 形成出站决定、body-free 材料与发布尝试 / gap | 出站决定、材料准备、attempt / gap | Runtime outcome truth、bus delivery、对话 / 制品 / observed truth | 成员输出各处直发;outcome→发布→delivery→accepted 四层被压平。 |
| 4 | `C-L2M-4` 交互追溯与安全材料 | 在场变化、筛选结论、投递决定、出站尝试可按同一关联语境安全追溯,并形成 body-free 低敏观测材料 | 本地交互事实追溯、安全材料准备与交接尝试 | observability backend / observed truth、evidence verdict | 筛选与发布决定不可审计;门面退化为不可解释的管道。 |
| 5 | `C-L2M-5` 成员摘要与能力出口 | body-free 成员状态摘要与(可裁剪的)能力出口安全视图可从已提交事实与上游 ref 派生、可重建 | 摘要投影、能力出口派生视图 | Runtime safe view source、ToolDefinition / method body truth | 宿主与下游只能各自猜测成员状态与可承接范围。 |

### 6.4 进入 / 退出条件与禁止误写

| 节点 | 进入条件 | 退出条件 | 禁止误写 |
|---|---|---|---|
| `C-L2M-1` | 项目型 `ProjectMemberRef`、关联 `GlobalMemberRef` 与可验证启动语境存在 | 本地在场状态可区分,注册请求 / 存活信号 / 状态报告可形成;任一主语、关联或凭据不可验证时 fail closed | 以 GlobalMember / Workspace view 代替执行主语、凭据形态(JWT 等)、注册接受 / session truth、健康阈值、容器编排动作 |
| `C-L2M-2` | C1 在场成立;订阅范围有来源 | 筛选结论与投递决定可区分、可回链规则来源;Runtime 不可用只 waiting 不代答 | 事件协议、过滤算法、本地 allowlist、Runtime 受理语义 |
| `C-L2M-3` | C1 在场成立;存在 Runtime committed safe material | 出站决定与发布尝试可区分;材料不合格拒绝出站;delivery 失败不回滚决定 | delivered / observed / accepted 声明、对话事实写入、协议 / topic |
| `C-L2M-4` | C2 / C3 已形成本地已提交事实 | 交互事实按关联语境可追溯;安全材料 body-free;route 未闭口只 attempt / gap | observed truth、完整日志、hidden reasoning、evidence verdict |
| `C-L2M-5` | C1~C4 有已提交事实;上游 ref 可用(能力出口路径) | 摘要 / 出口视图可派生、可重建、不反写;ref 失效显式 stale / gap | 定义正文复制、第二 registry、写源语义 |

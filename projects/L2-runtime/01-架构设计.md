## 2. 业务背景与驱动力

> 校准来源：
> - `design-calibration/01_arch_step_01_requirement_baseline.md`
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读：建议继续阅读上述中间产物的“架构目标”“硬约束”“取舍”和“非目标”小节，了解驱动力如何被收束为结构目标。

`L2-runtime` 需要在多个正式 truth owner 之间维持一次受控运行的决策连续性。它必须把目标、运行上下文、模型判断、行动选择、外部反馈和恢复位置组织成可解释的本地历史，同时避免把 Tools、Capability、Method、Governance、Sandbox、Artifact、Observability、provider 或 durable memory 的正文与真相吸收到自身。

| 架构目标 | 必须确保成立的结构 |
|---|---|
| 独立受控运行真相 | run、turn、goal / plan working state、显式状态和 local outcome 由 Runtime 单一拥有。 |
| 可验证上下文与记忆中介 | context source 带 owner / ref / scope / freshness；working memory 与 durable memory 分层。 |
| provider-neutral 模型决定 | Runtime 拥有 intent / logical selection / disposition，不拥有 physical route / secret / quota / cost。 |
| 可治理的行动与委派 | Tool / sub-agent action 有正式前置、有限 scope / budget 和结果关联，选择不等于执行。 |
| 可恢复且不重复副作用 | immutable history、stable checkpoint、recovery-as-new-decision 和 unknown-side-effect fence 持续成立。 |
| 本地真相优先的安全交接 | local outcome 先成立；handoff eligibility / attempt / gap 与 delivery / observed / accepted 分层。 |
| 可替换的外部 seam | owner 合同通过 runtime / event / ref / adapter 接入，未闭口时 fail closed。 |
| 可裁剪的外围增强 | replay、analytics、下游产品消费和长期记忆可后置，不成为核心 run 隐式前置。 |

## 3. 约束条件

> 校准来源：
> - `design-calibration/01_arch_step_02_goals_constraints.md`
> - `design-calibration/01_arch_step_07_dependency_direction.md`
> - `design-calibration/01_arch_step_12_cross_cutting_concerns.md`
>
> 延伸阅读：建议继续阅读上述中间产物的“硬约束”“依赖裁剪表”“横切关注点约束表”和“门禁”小节。

| 约束类别 | 正式约束 | 架构影响 |
|---|---|---|
| Owner separation | Runtime 不拥有 Tools execution、Hub registry、Method body、Governance truth、Sandbox isolation、Observability backend、Artifact / Evidence body、provider control 或 durable memory body。 | 所有外部能力必须经正式 seam 进入，不能共享数据库或直接写核心。 |
| Dependency discipline | 只有 `L0-core` 是 compile 候选；runtime / event / ref / adapter / fake 不得伪装成 Cargo / package 依赖。 | SDK / Member / Products 是下游 consumer，不反向决定核心。 |
| Source anchoring | principal、scope、goal、definition、policy、capability、result 必须可验证来源。 | 字符串、display text、route、cursor、私有索引不能推断 owner / authorization。 |
| Fail closed | governed、capability-bound、sandbox-required action 的前置缺失、冲突、stale 或 unknown 时不得推进。 | 允许 reject / waiting / blocked / unavailable，不允许本地 allowlist、自我授权或 host fallback。 |
| Truth integrity | history immutable；recovery / reflection 形成新决定；late / duplicate / out-of-order feedback 不逆写历史。 | checkpoint 必须表示 stable point；commit / side-effect unknown 禁止盲重试。 |
| Minimal exposure | method / policy / tool / capture / artifact / evidence / durable memory body、secret、raw provider response、hidden reasoning 不进入 Runtime truth / checkpoint / handoff。 | 只允许 typed ref、safe snapshot、candidate、redacted marker 或 safe decision summary。 |
| Local truth first | Runtime outcome 与 submission attempt、delivery、observed、acceptance 分层。 | 外围传播失败只形成 gap / degraded / stale，不回滚已提交本地事实。 |
| Pending preservation | `L2R-UP-001~008` 未闭口前不得伪造 schema、route、adapter、receipt、evidence 或 readiness。 | 相关正向设计、配置、测试、证据和验收保持 blocked。 |
| Evidence-bound NFR | 当前没有真实 workload、测量或 evidence authority。 | 不固定 P95、SLA、QPS、cost、retry 次数或 checkpoint 频率。 |

本文不选择具体语言、框架、数据库、缓存、vector store、queue、scheduler、provider、SDK、API、gRPC、UDS、event catalog 或部署产品。这些实现载体只有在不改变上述边界且后续文档具备来源时才可确定。

## 4. 职责边界

> 校准来源：
> - `design-calibration/01_arch_step_03_responsibility_boundary.md`
>
> 延伸阅读：建议继续阅读该中间产物的“上游 owner 对照”“职责边界表”“边界红线”和“待确认与 blocker”小节。

### 4.1 做 / 不做 / 易混淆职责

| 类型 | 职责边界 |
|---|---|
| 做 | controlled run；goal / plan working state；context composition / working memory；episodic / semantic retrieval mediation；provider-neutral model intent / selection / disposition；action choice；Tool / sub-agent orchestration；checkpoint / resume；reflection / recovery；Runtime local outcome；safe handoff eligibility、attempt / gap。 |
| 不做 | Tools execution / Tool truth；capability registry / adapter descriptor；method / role / process body；Governance approval / policy truth；Sandbox isolation truth；Observability backend / observed truth；Artifact / Evidence / report body；provider secret / physical route / quota / cost；durable memory body / index / retention / deletion；member-service / image / marketplace / product lifecycle。 |
| 易混淆职责 | action choice vs execution；logical model selection vs physical route；goal / plan working state vs Work / Process / Artifact truth；delegation vs member / container lifecycle；checkpoint / recovery vs external truth repair；handoff attempt vs delivery / observed / acceptance。 |

### 4.2 边界红线

| 红线 | 违反后果 |
|---|---|
| 不得让入口、member、SDK、Tools 或下游产品成为第二个 Runtime run / outcome truth owner。 | 状态、恢复点和终态分叉。 |
| 不得因编排而接管 Tools、Hub、Method、Governance、Sandbox、Observability、Artifact 或 durable memory truth。 | consumer / coordinator 被错误升级为 owner。 |
| 不得把 action choice 写成已授权、已执行、已隔离、已观察或已接受。 | 外部 owner 状态被压平。 |
| 不得把 logical selection 写成 provider route、secret、quota、cost 或 billing 决定。 | Runtime 越过 provider control owner。 |
| 不得在前置不明时自我授权、host fallback 或旁路执行。 | 高影响 action fail-open。 |
| 不得在 commit / side-effect unknown 或迟到反馈下盲重试、重复副作用或逆写历史。 | 运行历史不可归责。 |
| 不得将 delivery、receipt、observed、report 或 acceptance 反写 local outcome。 | 外部传播状态污染 Runtime truth。 |
| 不得保存 forbidden body、secret、raw body 或 hidden reasoning。 | 正文 owner 和最小暴露边界失效。 |
| 不得将非 Core sibling、SDK、Member、Products 写成 Runtime package 依赖。 | 全局依赖顺序倒置。 |
| 不得以 fake、目录、静态设计或旧文档声明正向 readiness。 | 后续 qualification、证据与验收失真。 |

## 7. 容器 / 部署架构

> 校准来源：
> - `design-calibration/01_arch_step_06_container_deployment.md`
>
> 延伸阅读：建议继续阅读该中间产物的“容器 / 部署架构图”“运行单元说明表”和“部署边界结论”小节。

本章中的运行单元是正式承载角色，不声明物理进程、容器、实例或部署已经存在。入口、推进、恢复 / continuation、feedback consumption 和 Runtime state responsibility 必须逻辑分离；它们当前可以同部署，但不能因此共享外部私有 truth、绕过正式 seam 或压平失败状态。

### 7.1 运行承载图

```text
 +==========================================================+
 |                 L2-runtime runtime boundary              |
 |                                                          |
 |  +----------------------+                                |
 |  | Runtime entry       |  入口                           |
 |  | acceptance boundary |                                |
 |  +----------+-----------+                                |
 |             | 处理                                       |
 |             v                                            |
 |  +----------------------+    +----------------------+     |
 |  | Run progression     |<-->| Feedback consumption |     |
 |  | controlled loop     |    | correlation boundary |     |
 |  +----------+-----------+    +----------------------+     |
 |             | 处理 / 承载                                  |
 |             v                                            |
 |  +----------------------+    +----------------------+     |
 |  | Recovery/background |--->| Runtime state        |     |
 |  | continuation        |    | truth carrier        |     |
 |  +----------------------+    +----------------------+     |
 +==========================================================+
          ^                         |
          | 入口 / 对接              | 依赖 / 对接
 +--------+---------+        +------+------------------+
 | Entry consumers  |        | Tools / Sandbox /      |
 | Member / SDK     |        | model / Bus / Obs      |
 +------------------+        +-------------------------+
```

### 7.2 正式承载单元

| 对象 | 类型 | 主要职责 | 边界说明 |
|---|---|---|---|
| Runtime entry acceptance boundary | 同步入口单元 | 受理 / 拒绝 trigger、control 和 safe query | 不拥有产品 UI、member host 或 SDK lifecycle。 |
| Run progression | 后台处理单元 | 推进 controlled run、goal / plan、context、decision 与 action waiting | 不预设 worker 产品、语言或进程。 |
| Recovery / background continuation | 后台处理单元 | 承接 resume、recovery、reflection、等待恢复和 handoff continuation | unknown side effect 不进入盲重试。 |
| Feedback consumption boundary | 异步消费单元 | 关联 Tool / Sandbox / model / child / Bus 的异步反馈 | 反馈到达不等于 local outcome。 |
| Runtime state truth carrier | 正式存储承载 | 承载 run / working / decision / checkpoint / outcome 的状态责任 | 物理存储、schema、事务和原子性后移。 |
| Entry consumers | 外部运行边界 | 提供受控触发并消费 safe views | 下游未校准，不反向决定部署。 |
| External action / event boundaries | 外部运行边界 | 承接 Tools / Sandbox / model / Bus / Observability seams | 多项正向 contract / readiness 仍 pending。 |

Tools execution、Sandbox isolation、provider / durable memory backend、Bus / Observability backend 和 member lifecycle 必须外置。具体共进程、分部署、伸缩和故障域只能在真实承载条件与 workload 证据形成后决定。

### 8.1 依赖方向

```text
 +====================================================+
 |             L2-runtime dependency boundary         |
 |                                                    |
 | +------------------------------+                   |
 | | External seam role           |                   |
 | | runtime / event / ref/adapter|                   |
 | +---------------+--------------+                   |
 |                 | 边界接入                         |
 |                 v                                  |
 | +------------------------------+                   |
 | | Runtime orchestration role   |                   |
 | +---------------+--------------+                   |
 |                 | 允许依赖                         |
 |                 v                                  |
 | +------------------------------+                   |
 | | Core runtime semantic role   |                   |
```

箭头仅表示允许依赖或边界接入，不表示调用、事件、部署或执行顺序。外部能力必须先经过正式 seam 承接，技术载体不能反向定义 run、decision、checkpoint 或 outcome 语义。

### 8.2 跨仓依赖裁剪

| 关联项目 / 能力 | Runtime 角色 | 依赖类型 | 架构约束 |
|---|---|---|---|
| `L0-core` | 依赖方 | compile | 唯一 shared contract authority；只有真实发布的 Core contract 可进入 package graph。 |
| `L0-bus` | 协作方 | event | 只承载已提交 body-free fact；delivery truth 独立。 |
| `L0-sdk` | 被依赖方 | downstream runtime | SDK 封装消费面，不反向成为 Runtime package。 |
| `L2-tools` | 依赖方 | runtime / ref / adapter | Runtime 编排，Tools 拥有 Tool definition / canonical contract / normalized outcome。 |
| `L3-capability-hub` | 依赖方 | runtime / ref | 消费 identity / exposure / safe descriptor，不复制 registry。 |
| `L3-method-library` | 依赖方 | runtime / ref | 消费 definition ref / safe view，不保存正文。 |
| `L1-governance` | 依赖 / 协作方 | runtime / event / ref | 消费 formal result；unknown fail closed。 |
| `L4-sandbox` | 依赖方 | runtime / adapter | sandbox-required action 不旁路，正向 mapping pending。 |
| `L4-observability` | 协作方 | event | 只输出 safe material / attempt / gap，不声明 observed。 |
| `L1-artifact` | 依赖 / 协作方 | runtime / event / ref | 正文、lineage、evidence、verdict 不归 Runtime。 |
| model adapter | 依赖方 | runtime / adapter | provider-neutral；owner / route / secret / quota / cost pending。 |
| durable memory owner | 依赖方 | runtime / ref / adapter | working-only 可降级，durable truth 外置。 |
| Member / Products | 被依赖方 | downstream runtime | 下游入口 / 消费候选，不反向成为 authority。 |

### 8.3 Seam 分类与禁止依赖

| Seam | 是否为 package 依赖 | 当前要求 |
|---|---|---|
| compile | 仅 Core 可以 | 必须来自正式 shared contract authority。 |
| runtime | 否 | owner、availability、failure 与 scope 明确。 |
| event | 否 | committed source 与 delivery / observed 状态分层。 |
| ref | 否 | typed owner、resolution、freshness、forbidden body 明确。 |
| adapter | 否 | provider-neutral；合同未闭口即 blocked。 |
| fake | 否 | 仅证明语义 seam 可控，不证明真实 readiness。 |

禁止非 Core sibling Cargo / path / package 依赖、SDK / Member / Product 反向依赖、provider / vector / memory 产品 SDK 进入核心、外部 MCP / A2A / API 直建 registry、Governance 本地真相缓存、Sandbox host fallback、外部正文存储，以及 Observability / Bus 外部状态反写 Runtime truth。

## 9. 数据所有权与一致性策略

> 校准来源：
> - `design-calibration/01_arch_step_08_data_ownership_consistency.md`
>
> 延伸阅读：建议继续阅读该中间产物的“数据归属表”“一致性策略表”“按架构单元数据所有权与停审”和“跨数据边界审计”小节。

### 9.1 数据归属

| 数据项 | 数据类型 | 所有权与边界 |
|---|---|---|
| Run identity / scope / disposition | 正式真相数据 | Runtime 拥有；入口 / member / downstream 不维护可覆盖副本。 |
| Goal / plan working state | 正式真相数据 | Runtime 拥有运行内推进决定；不等于 Work / Process / Artifact / Method body。 |
| Context composition / working memory | 正式真相数据 | Runtime 拥有 source selection、budget / gap 和短期工作语境；外部正文 owner 不迁移。 |
| Model intent / selection / disposition | 正式真相数据 | Runtime 拥有 provider-neutral decision；raw response、route、secret、cost 不归 Runtime。 |
| Action choice / delegation / incorporation | 正式真相数据 | Runtime 拥有选择、父子 scope / budget 和纳入决定；Tool outcome、approval、Sandbox run 外置。 |
| Checkpoint / recovery / reflection decision | 正式真相数据 | Runtime 拥有 stable point 与新决定；不保存 forbidden body。 |
| Runtime local outcome | 正式真相数据 | Runtime 拥有本地终态和 safe summary source；delivery / observed / accepted 不替代。 |
| Handoff eligibility / attempt / gap | 正式真相数据 | Runtime 拥有材料准备、尝试和本地缺口；receipt / observed / acceptance 外置。 |
| Definition / Governance / capability / result safe view | 快照 / 投影数据 | 带 owner / freshness / scope，可 stale / conflict / missing；不冒充 source truth。 |
| Safe Runtime status / outcome view | 快照 / 投影数据 | 从已提交 Runtime truth 派生，可延迟 / 重建、不能写源。 |
| Method / Work / Artifact / Tool / Sandbox / memory refs | 引用关系数据 | 只保存 typed correlation；resolution 失败显式。 |
| Memory retrieval ref / write candidate | 引用关系数据 | 记录检索使用与候选交接；durable accept / delete truth 不归 Runtime。 |
| Method / policy / tool / capture / artifact / evidence / memory body | 明确不拥有的正文 / 真相 | 不得进入 Runtime truth、checkpoint、safe view 或 handoff。 |
| Secret / credential / raw headers / hidden reasoning | 明确不拥有的正文 / 真相 | 只允许 secret ref、redacted marker 或 safe reason category。 |

### 9.2 一致性策略

| 数据关系 / 场景 | 一致性口径 | 失败处理 |
|---|---|---|
| Run 状态与 goal / plan 推进 | 同一本地提交边界内一致 | 失败保持原状态；unknown 不写部分完成。 |
| Decision 与 action / checkpoint | source-correlated 一致 | correlation 不完整即 blocked，不猜测补齐。 |
| Stable point 与恢复起点 | 历史不可变、单向追加 | commit unknown 挂起，不盲重试或覆盖。 |
| External truth 到 safe snapshot | 消费时点一致，允许过期显式 | stale / conflict / missing -> wait / degraded / fail closed。 |
| External object 到 Runtime ref | 引用完整性可验证 | unresolved / wrong owner -> reject / gap。 |
| 外部反馈到 Runtime decision | 关联后形成新本地事实 | late / duplicate / out-of-order -> 新事实或 pending，不逆写。 |
| Runtime truth 到 Safe Runtime Views | 最终一致、可重建 | projection gap 独立，不回滚 truth。 |
| Runtime outcome 到 Bus / Observability / downstream | local truth first，外部独立收敛 | attempt / gap；不声明 delivered / observed / accepted。 |
| Memory candidate 到 durable owner | 候选交接、由 owner 决定 | pending / rejected / unavailable；不声明 committed。 |
| Parent / child history | 父 scope 与 incorporation 一致 | child unknown / late 形成等待或新事实，不共享 mutable working body。 |

Checkpoint persistence 的 transaction / unit-of-work、version、atomicity 与 commit-unknown 物理合同仍为 pending；本章不以逻辑一致性伪造物理持久化 readiness。

## 10. 关键交互与通信方式

> 校准来源：
> - `design-calibration/01_arch_step_09_interactions_communication.md`
>
> 延伸阅读：建议继续阅读该中间产物的“关键交互场景表”“通信方式判断表”“按架构单元交互方式与停审”和“跨交互边界审计”小节。

### 10.1 三类通信语义

| 通信方式 | 适用语义 | 失败姿态 |
|---|---|---|
| 同步请求 / 响应 | 正式 trigger / control 受理、source / precondition 判断、safe query 和即时拒绝 | reject / blocked / unavailable / unknown；不返回伪完成。 |
| 异步事件 / 回调 | 已提交事实传播、Tool / Sandbox / model / child 结果送达、跨 owner 协作 | pending / duplicate / late / unresolved；不逆写历史。 |
| 后台任务 / 延后承接 | 长时 run、resume / recovery、reflection、projection、handoff continuation | waiting / paused / blocked / gap；不以后台补写掩盖入口判断。 |

### 10.2 关键交互边界

| 交互场景 | 语义边界 | 约束 |
|---|---|---|
| Runtime trigger / control 受理 | Entry consumers 与 Runtime entry | accepted / rejected / blocked 不等于 run 完成。 |
| Status / safe outcome 查询 | Consumers 与 Safe Runtime Views | 只读、body-free，不触发 truth mutation。 |
| Definition / decision / capability ref 解析 | Runtime 与 external truth sources | 必须验证 owner、scope、freshness；不能从字符串猜 source。 |
| Model turn | Model Decision 与 model adapter | provider-neutral intent 与关联 disposition；route / secret 外置。 |
| Tool action 前置 / 提交 | Action 与 Governance / Tools / Sandbox | choice 不等于 authorization / execution / receipt。 |
| 外部结果送达 | External owners 与 feedback boundary | late / duplicate / out-of-order 形成新关联事实。 |
| Committed fact 传播 | Runtime 与 Bus / Observability / consumers | local truth first，传播失败只形成 gap。 |
| Run continuation / recovery | Runtime state 与后台承接 | 从 stable point 恢复，unknown side effect 不盲重试。 |
| Safe view / handoff 维护 | Runtime truth 与 projection / handoff | 可延迟、可重建，不成为业务写源。 |
| Durable memory retrieval / candidate | Context & Memory 与 pending memory owner | candidate 不直接成为 durable truth。 |

一次运行可以组合三类通信方式，但每类方式负责不同语义：同步只收口即时判断，异步只传播已成立或明确未知的外部事实，后台只承接长时或可延后的继续动作。当前不锁 API、topic、RPC、队列、调度器或事件 schema。

## 11. 关键技术选型

> 校准来源：
> - `design-calibration/01_arch_step_10_technology_choices.md`
>
> 延伸阅读：建议继续阅读该中间产物的“关键技术机制表”“当前不采用口径”和“按架构单元机制适用”小节。

| 技术机制 | 架构问题 | 当前采用理由与代价 |
|---|---|---|
| Source-anchored controlled state transition | 防止 prompt、入口或外部反馈隐式推进 run | 让状态变化可解释；代价是需要显式 source、scope、decision 和非法迁移语义。 |
| 正式承接边界隔离外部输入 | 防止 definition、policy、capability、tool、sandbox、provider 直写核心 | 外部输入先转为 ref / snapshot / result / gap；增加接缝和失败表达。 |
| Provider-neutral adapter 与 logical / physical split | 防止 provider route / secret / quota / cost 统治 model decision | Runtime 只需 intent / selection / disposition；adapter 合同和 unavailable 语义仍需闭口。 |
| Truth / snapshot / ref / candidate / forbidden body separation | 防止外部正文或候选升级为 Runtime truth | 保护 owner separation；代价是 stale / conflict / missing / resolution 状态增加。 |
| Immutable history + stable checkpoint + recovery-as-new-decision | 防止 resume / reflection / retry 原地改写历史 | 支撑 unknown 和迟到反馈；物理持久化和事务仍 pending。 |
| Unknown-side-effect fence | 防止 commit / side-effect unknown 后重复副作用 | 正确性优先于自动可用性；可能需要等待、外部 resolution 或人工介入。 |
| Local-truth-first + safe projection / handoff | 防止 delivery / observed / accepted 污染 outcome | 核心可独立成立；增加 attempt / gap / projection lag 的解释成本。 |
| 同步判断 / 异步传播 / 后台 continuation 分离 | 防止全同步长链或全异步缺少即时裁定 | 三类路径各守语义；增加关联与故障处理复杂度。 |
| Idempotency / ordering / correlation | 防止重复、迟到、乱序、replay 产生分叉 | 要求稳定 identity、causation 和 duplicate handling；具体算法后移。 |
| Fail-closed precondition gating | 防止 Governance / capability / Sandbox 不明时自我授权 | 高影响 action 安全优先；availability 下降但 blocked 语义可审查。 |
| Working context budgets + bounded delegation | 防止 context / memory / sub-agent 无界增长 | 所有工作集有 scope / budget / exhaustion；当前不定 token / 并发数字。 |
| Body-free safe summary / redacted projection | 防止 hidden reasoning、secret、raw body 扩散 | 最小暴露；调查能力依靠 owner ref 和安全分类而非完整推理正文。 |

本章不把 StateGraph、LangGraph、Temporal、Rust、Python、数据库、cache、vector store、queue、scheduler、provider、SDK、API 或完整 event sourcing 写成当前硬选型。它们只能在后续文档中作为实现载体候选，并且不得改变本文的 owner、truth、failure 和 dependency 约束。

## 12. 备选方案与取舍

> 校准来源：
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读：建议继续阅读该中间产物的“当前主线方案”“方案路径比较表”“不进入正式比较的方向”和“轻量取舍对照”小节。

### 12.1 当前主线

```text
独立 Runtime controlled-run truth
  + 五核心语境与入口 / 外部视图 / 安全投影分层
  + 正式接缝隔离外部 owner
  + provider-neutral model / action orchestration
  + immutable history / stable checkpoint / unknown fence
  + local-truth-first outcome / safe handoff
  + 同步判断 / 异步送达传播 / 后台 continuation
  + fail-closed / idempotency / ordering / correlation
```

### 12.2 路径比较

| 方案路径 | 当前结论 | 主要收益 | 主要代价 / 不采用原因 |
|---|---|---|---|
| 独立 Runtime truth + 正式接缝 + 混合通信主线 | 采用 | owner 清楚、历史可恢复、外部 seam 可替换、失败可解释 | 状态、关联、adapter、projection、gap 复杂度较高。 |
| 无状态 request coordinator | 不采用 | 入口简单 | 无法承载长时 run、checkpoint、late feedback、unknown side effect 和恢复历史。 |
| 单一“大脑”聚合上下文 / 工具 / provider / memory | 不采用 | 初期调用链直观 | 吞并外部 truth，形成第二 owner，违反边界。 |
| 通用状态图 / workflow engine 主导 | 保留为实现候选 | 可能提供可视化与恢复承载 | 框架不能替代 Runtime 语义、owner 合同或 unknown fence。 |
| 全同步端到端闭环 | 不采用 | 调用方心智简单 | 长链耦合，容易伪同步完成和级联失败。 |
| 全异步事件化主线 | 不采用 | 长时和跨仓传播自然 | 缺少即时受理 / 拒绝边界。 |
| 完整 event sourcing 主线 | 保留观察 | 追加历史和回放自然 | 外部副作用不能靠本地 replay 重演，当前没有 persistence authority。 |
| 每步 checkpoint + 自动 retry | 不采用 | 表面恢复率高 | 可能没有 stable 语义，并重复 unknown side effect。 |
| Core truth 直接对外暴露 | 不采用 | 读取直接 | 下游绑定核心结构并可能反写 delivery / accepted；采用 Safe Runtime Views。 |

当前方案换取 owner separation、恢复合法性和 fail-closed，承担更多状态、关联、投影和 gap 解释成本；不以早期直连、共享 DB 或固定产品组合换取表面简化。

## 13. 横切关注点

> 校准来源：
> - `design-calibration/01_arch_step_12_cross_cutting_concerns.md`
>
> 延伸阅读：建议继续阅读该中间产物的“横切关注点约束表”“按架构单元横切适用与停审”和“跨横切审计”小节。

| 横切关注点 | 正式约束 |
|---|---|
| 安全边界 | principal / scope / capability / Governance / Sandbox 前置不可验证时拒绝、等待或 blocked；不得自我授权或 host fallback。 |
| 最小暴露 | secret、raw body、capture、Artifact / Evidence / memory body、hidden reasoning 不进入 truth、checkpoint、view 或 handoff。 |
| 审计与追溯 | 关键状态、决定、action、checkpoint、feedback、handoff 可回链 owner / source / purpose / run / turn；不等于完整日志或 reasoning trace。 |
| Immutable history | 新反馈、reflection、recovery 形成新事实，不原地抹写历史。 |
| 可观测性分层 | active / waiting / blocked / unknown / failed / terminal 等本地语义与 delivered / observed / accepted 外部语义分开。 |

| 配置 / 变更 | 配置不能绕过 owner、fail-closed、unknown fence、forbidden body、依赖分类或 local truth first；会改变运行决定的配置必须可回链。 |

上述约束适用于 Run & Goal-Plan、Context & Memory、Model Decision、Action & Delegation、Checkpoint / Recovery / Handoff、Entry & Control、External Truth Views 和 Safe Runtime Views 八个架构单元。它们是架构边界，不是监控产品、密钥脚本、告警配置或压测结果。

## 14. 演进路线

> 校准来源：
> - `design-calibration/01_arch_step_13_evolution_path.md`
>
> 延伸阅读：建议继续阅读该中间产物的“当前阶段边界”“演进阶段结论”“已知设计债务”和“触发条件表”小节。

当前阶段是 Runtime 逻辑主线成立阶段：Runtime 能独立表达 controlled run、goal / plan working state、context / working memory、provider-neutral model decision、Tool / sub-agent orchestration、checkpoint / recovery / reflection、local outcome 和安全 handoff attempt；外部 owner 只通过正式 seam 被消费。当前不要求具体语言、框架、数据库、部署、provider route、durable memory 正文、Tools execution、Sandbox isolation、Observability backend 或下游产品入口已经具备。

| 演进阶段 | 结构目标 | 进入条件 | 必须保持 |
|---|---|---|---|
| P1 本地 Runtime 逻辑主线成立 | 闭合 run / 五核心语境 / checkpoint / recovery / local outcome 的本地语义 | 架构结论已停审，不依赖未闭合正向 seam | Runtime truth、immutable history、stable point、unknown fence、fail-closed。 |

| P4 需求驱动的外围消费增强 | 扩展 Member / Product、replay、analytics、reflection candidate 等消费 | 下游 boundary、event source family 和消费语义正式闭口 | 外围失败可独立降级、重建和追溯，不成为核心同步前置。 |

正式 owner contract、正向 adapter / route、真实部署承载或 workload / failure evidence 只有在改变边界、所有权、一致性或失败姿态时，才触发受影响架构 Step 回开；旧框架、API、SLA 或对象回流也必须先标记为 historical pollution。

`L2R-UP-001~008` 不阻塞架构逻辑完成，但阻塞正向 schema、adapter、route、配置激活、测试执行、evidence、acceptance 和 implementation readiness；本章不把这些开放项改写成解决方案。

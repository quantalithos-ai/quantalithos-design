## 1. 业务背景与驱动力

### 1.1 业务背景

runtime 是 AI 成员的**决策中枢**。它把上下文、记忆、目标、工具、规则聚合在一起,形成真正的执行主循环。member 提供“嘴耳”,runtime 提供“大脑”。

### 1.2 业务驱动力

**业务驱动力**:
- AI 员工必须能在稳定边界内做自主决策
- 所有决策都要可恢复、可追踪、可解释

**技术驱动力**:
- StateGraph 代替纯 prompt 控制
- prompt 分层优先级
- 三层记忆
- tool invoker guardrails
- checkpoint / reasoning trace
- sub-agent 独立上下文

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| loop 开销 | 单步(不含模型调用) | < 50ms | benchmark |
| checkpoint 写 | P95 | < 100ms | benchmark |
| 记忆检索 | P95 | < 500ms | benchmark |
| reasoning trace 覆盖 | 100% | 回归测试 |
| tool guardrail 拦截率 | 100% 高危路径 | 安全测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| StateGraph 硬约束 | RT1 | loop 不能纯 prompt 驱动 |
| prompt 四层 shared_rules→role→policy→context | RT2 | composer 排序固定 |
| working / episodic / semantic 三层记忆不混写 | RT3 | memory 模块边界固定 |
| Tool 前后置 Guardrails | RT4 | invoker 前后必须校验 |
| 每步 checkpoint | RT5 | loop 每步写持久化 |
| reasoning_trace 完整持久化 | RT6 | 所有步骤都得留 trace |
| Sub-Agent 独立上下文 | RT7 | 不能直接共享 working memory |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| LLM provider | capability-hub 动态选 | 可扩模型集 |
| sub-agent 策略 | 当前可选 | 可更细分 |
| memory provider | vector store 候选 | 可替换 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| loop 开销 | <50ms | README |
| checkpoint 写 | <100ms | README |
| memory retrieval | <500ms | README |
| concurrent sub-agents | 受容器资源限制 | 后续评估 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| prompt 层策略 | 中高 | composer 抽象 |
| memory provider | 中 | ref / adapter 抽象 |
| tool set 扩展 | 高 | invoker + registry |
| routing 策略 | 中 | capability-hub / routing hook |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **StateGraph + modular runtime**(当前)| 可解释、可恢复、边界清晰 | 结构较重 | ✅ |
| 单大循环 + prompt 拼接 | 实现快 | 不可控、不可恢复 | ❌ |
| 多 agent 并发默认 | 灵活 | 上下文失控 | ❌ 起步不稳 |

**最终选择**:**StateGraph + 9 子模块 + 每步 checkpoint**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 每步 checkpoint | 恢复可靠 | IO 开销 |
| prompt 四层固定 | 规则边界清晰 | 灵活性略降 |
| sub-agent 独立上下文 | 主上下文稳定 | 调度复杂度上升 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
member IPC / capability-hub / tools / vector store
                    │
                    ▼
          ★ quantalithos-runtime ★
          - stategraph loop
          - prompt composer
          - memory / checkpoint / trace
                    │
             tool invoker / sub-agent
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ LLM loop / planner / memory / invoker / checkpoint / trace
- ✅ 聚合上下文并做决策
- ✅ 调用工具与 sub-agent

**不做什么**:
- ❌ 外部接入层(member)
- ❌ 工具具体实现(tools)
- ❌ 白名单决策(capability-hub)
- ❌ 容器编排(member-service)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| member IPC | 高 | reconnect |
| capability-hub | 99.9% | last-known-good cache |
| tools | 99.9% | tool unavailable path |
| vector store | 99.9% | degrade without semantic recall |
| observability | 99.95% | backlog / retry |

### 4.4 关键依赖风险

- prompt layering 实现错误导致 shared_rules 失效
- checkpoint 粒度过粗恢复失真
- sub-agent 滥用导致上下文爆炸

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Loop | 核心域 | ReAct / StateGraph |
| Prompt | 核心域 | 规则与上下文组合 |
| Memory | 核心域 | 三层记忆 |
| Execution | 支撑子域 | tool invoker |
| Recovery | 支撑子域 | checkpoint / restore |
| SubAgent | 支撑子域 | 上下文分叉 |

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Loop | 主循环 | LoopState |
| Prompt | prompt 组装 | PromptContext |
| Memory | working / episodic / semantic | MemoryView |
| Tools | tool request / result | ToolInvocation |
| Recovery | checkpoint / trace | Checkpoint / ReasoningTrace |
| ExecutionPlan | implementation-plan read/write / promote | ImplementationPlanRef / PlanItem |
| AgentSplit | sub-agent spawn / merge | SubAgentHandle |

### 5.3 上下文映射关系

- member → Loop / Prompt(输入)
- capability-hub → Tools / PolicyCache
- tools / sandbox → Execution
- work / artifact → ExecutionPlan(current WorkItem truth + implementation-plan artifact)
- observability ← Recovery / Trace

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |
|---|---|---|
| StateGraph | 约束 loop 的状态机 | Loop |
| Prompt Layer | shared_rules / role / policy / context | Prompt |
| Working Memory | 当前任务内短时状态 | Memory |
| Episodic / Semantic | 长期 ref | Memory |
| Tool Invocation | 一次工具调用 | Execution |
| ImplementationPlanRef | 当前 WorkItem 关联的执行路线图引用 | ExecutionPlan |
| PlanItem | ImplementationPlan 中的单个执行步骤 / 风险验证项 | ExecutionPlan |
| ReasoningTrace | 推理留痕 | Recovery |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
member (IPC bridge)
      │ UDS gRPC
      ▼
runtime-api / loop entry
   ├─ C1 loop
   ├─ C2 composer
   ├─ C3 memory
   ├─ C4 goal/plan
   ├─ C5 context
   ├─ C6 policy cache
   ├─ C7 checkpoint
   ├─ C8 sub-agent
   └─ C9 tool invoker
        │
        ├─▶ tools / sandbox
        ├─▶ capability-hub
        ├─▶ vector store
        └─▶ observability
```

### 6.2 每个容器/进程职责与技术栈

| 进程 / 模块 | 职责 | 技术栈 |
|---|---|---|
| runtime main | loop 启动 / dispatch | Python |
| composer | prompt 组合 | Python |
| memory | 三层 memory 管理 | Python |
| tool invoker | schema + policy + guardrails | Python |
| checkpoint store | 每步持久化 | Python |
| subagent spawner | 独立上下文代理 | Python |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| member ↔ runtime | UDS gRPC | 不暴露外网 |
| runtime ↔ capability-hub | Python SDK | 高层调用统一 |
| runtime ↔ tools | in-process / sandbox bridge | 最短路径 |
| runtime → observability | async trace/event emit | 不阻塞主 loop |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| working memory | runtime | runtime |
| episodic/semantic refs | runtime(通过 provider) | runtime |
| checkpoint | runtime | runtime / process / observability |
| reasoning trace | runtime | observability / auditors |

### 6.5 部署拓扑

- 与 member 同容器双进程运行
- Python runtime 依赖外部 provider / vector store / tools
- 不直接暴露外部监听端口

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
IPC / control inputs
      │
      ▼
loop orchestration
      │
      ├─▶ prompt / context / goal
      ├─▶ memory / policy cache
      ├─▶ tool invoker
      ├─▶ checkpoint / trace
      └─▶ sub-agent
```

### 7.2 层间约束规则

- C1 Loop 只调子模块接口,不直接写 provider / SDK 细节
- C2 Prompt Composer 只做组合,不执行策略判断
- C3 Memory 只管理 memory 读写边界,不直接决定行为
- C9 Tool Invoker 在 guardrails 通过前不执行工具
- C8 Sub-Agent 默认独立上下文,不共享 working memory

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| MemoryProvider | runtime domain | vector store adapters |
| ToolExecutor | runtime | tools / sandbox adapter |
| TraceSink | runtime | observability adapter |
| CapabilityQuery | runtime | sdk / capability-hub |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(member / control / policy) |
| 传出耦合 | 高(tools / vector / capability-hub / observability) |
| 不稳定性 | 中高 |
| 抽象度 | 高(9 子模块职责清晰) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| WorkingMemory | runtime | runtime | 进程内强一致 |
| Episodic/Semantic refs | runtime/provider | runtime | 最终一致 |
| Checkpoint | runtime | runtime / observability | append-only |
| ReasoningTrace | runtime | observability | append-only |
| Tool call state | runtime | runtime / tools | 单步强一致 |

### 8.2 一致性层次

- loop 内部状态强一致
- checkpoint / reasoning trace append-only
- memory provider / capability query / tool execution 与外部系统最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| tool 执行失败 | guardrails + error path |
| memory provider timeout | degrade without semantic recall |
| checkpoint 写失败 | retry / fail loop |
| sub-agent 失败 | 主 agent 接收错误结果,决定重试 / 放弃 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| LLM routing 是否 runtime 内建未定 | 结构边界 | P1 |
| memory provider 细节未定 | 性能与恢复 | P1 |
| sub-agent 触发策略未细化 | 上下文复杂度 | P2 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| loop overhead > 50ms | 持续 1 周 | 优化模块边界 / 提取热路径 |
| checkpoint > 100ms | 持续 1 周 | 改存储策略 |
| memory retrieval > 500ms | 持续 1 周 | cache / provider 优化 |

### 12.3 演进步骤

```
阶段 1: loop + prompt + memory + tool + checkpoint 基础落地
阶段 2: sub-agent / routing / reasoning trace 稳定
阶段 3: advanced reflection / memory optimization
```

### 12.4 目标架构

runtime 的目标是:
- 成为可解释、可恢复、可约束的 AI 决策引擎
- 在“大脑”内部保持模块边界,避免“万能单文件 loop”

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L2-runtime` 不是流程图本身,也不是工具集合。它是 **“正式执行主脑仓”**。

你可以把它理解成:
- 某个正式 WorkItem 到了可以执行的时候,到底是谁把它真正跑起来
- 一份 `ImplementationPlan` 如何从文档变成真实执行步骤
- 当前执行到哪一步、为什么停住、接下来该做什么
- 哪一步只是局部执行动作,哪一步已经应该升级成正式协作任务
- 执行结果怎样回流成 artifact、怎样回报给 process / work / conversation

这些事情,都由 `L2-runtime` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L2-runtime`,这些执行事实就会散落在:
- `process` 的 activity 状态里
- `work` 的 assignee / child WorkItem 字段里
- `artifact` 的 ImplementationPlan 文本里
- `conversation` 的执行反馈消息里
- `tools / member-service / sandbox` 的底层调用日志里

结果就会出现:
- 系统知道“该执行了”,却不知道“现在怎样在执行”
- process 知道时机到了,但没有正式执行主线
- work 知道任务存在,但不知道局部执行怎样推进
- plan 只是一份文档,不能真正变成运行态步骤
- promote、retry、block、resume 没有统一真相层
- conversation 看得到执行反馈,却不知道哪个才是正式执行状态

所以 `L2-runtime` 必须独立存在,作为:
> **正式执行实例、步骤推进、阻断恢复和执行结果回流的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### ExecutionInstance
就是:
> 一次正式执行活动在 runtime 里的运行实例。

它回答的是:
- 现在到底在执行哪份正式工作
- 当前由谁执行
- 当前处于什么执行状态

#### ImplementationPlan
就是:
> 一份正式制品,用于告诉 runtime“这次大致应该怎样推进”。

它不是 runtime 的状态对象,也不是 work 真相对象。

#### current step
就是:
> 当前执行实例真正跑到的那一步。

它不是 process 的 Activity 真相本体,也不是 conversation 里的一条消息。

#### promote
就是:
> 某个局部执行步骤已经超出个人/局部执行边界,需要正式升级成协作级 child WorkItem。

它不是“自己再多做一点”的别名,而是正式交回 `work` 的升级动作。

#### blocked / waiting_input / suspended
就是:
> runtime 当前不能继续,但这不等于执行失败。

它可能是:
- 等治理
- 等外部输入
- 等依赖
- 等恢复

#### execution feedback
就是:
> tools/member-service/sandbox 返回给 runtime 的结构化执行结果。

它不是 artifact 正文真相,但可以被 artifact 物化成正式报告或结果材料。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L2-runtime/02` 时,先收稳以下前提:
- `L2-runtime` 不应按对象数拆,而应按主要部分拆
- runtime 至少应拆成“执行主语与运行实例 / 执行计划展开与步骤推进 / 动作调度与执行反馈 / 阻断、恢复与治理接缝 / 结果回流与协作升级接缝”五个主要部分
- runtime 自己拥有的真相是 ExecutionInstance / current step / execution state / feedback / retry/resume/recover / promote request
- `Project / WorkItem / ProcessInstance / Decision / Artifact 正文 / Conversation / Tool` 都不是 runtime 真相
- runtime 可以消费这些域的 ref / signal / snapshot / plan,但不能把它们收编为自己的主真相
- 02 的重点不是“能调哪些工具”,而是先把“runtime 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,真正推进交付的不只是任务、流程和治理结果,还包括“执行本身”。用户真正需要的不是“任务存在于 backlog 里”,而是:
- 当 process 给出 execution timing 后,系统能真的开始执行
- 当有 ImplementationPlan 时,系统能按 plan 推进 step,而不是停在文档层
- 当前执行为什么停住、是失败还是等待、要不要升级为协作任务,都能被正式解释
- 执行结果能回流成 artifact,同时回报给 process / work / conversation

如果把这些逻辑分别散落到:
- `process` 的运行态节点
- `work` 的 child WorkItem 结构
- `artifact` 的 plan/report 正文
- `conversation` 的执行消息
- `tools/member-service/sandbox` 的底层实现

系统会快速退化成:
- 任务看起来“开始了”,但没有正式执行实例真相
- plan 只是文档,不会转成真实推进步骤
- promote、retry、resume、governance wait 没有统一归属
- 执行结果四处回流,却没有 runtime 作为编排主脑收口
- conversation 能看到执行消息,却无法回到正式执行状态

因此,本概要设计的任务就是:
> **把 `L2-runtime` 写成一个新人也能看懂的“正式执行主脑仓”,而不是把流程停点、工具调用、执行日志和协作升级混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 执行真相归属 | 易散落在 process/work/conversation/tools 中 | ExecutionInstance 成为正式真相层 | 需写死边界 |
| plan 到执行 | ImplementationPlan 易停留在文档层 | plan item / step 能进入正式执行推进 | 需正式落图 |
| promote 语义 | 易被当作局部 TODO 膨胀 | 升级为 child WorkItem 的边界清晰 | 需形成主要部分 |
| wait/retry/resume | 易被统称为“失败” | blocked / suspended / waiting_input / retry 分层成立 | 需单列并固定 |
| 下游回流 | artifact/process/work/conversation 各自接收结果,但执行主线易漂移 | runtime 统一编排与回流 | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让正式工作、正式计划、正式治理边界和正式执行反馈真正组成一条可推进、可恢复、可升级的执行主线
- **技术问题**:ExecutionInstance / step progression / dispatch / feedback / block-resume / promote / result backflow 之间的边界如何稳定建模,并与 `work/process/governance/artifact/conversation/tools/member-service` 清晰协作而不混层

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ conversation               │
                    │ - progress / failure view  │
                    │ - promote / wait notice    │
                    └────────────┬───────────────┘
                                 │ visible execution summary
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ work                       │   │ runtime                    │   │ process                    │
│ - WorkItem / child WI      │──▶│ - ExecutionInstance        │◀──│ - execution timing         │
│ - assignee / backlog truth │   │ - current step / state     │   │ - activity / resume        │
│ - promote target           │   │ - dispatch / feedback      │   └────────────────────────────┘
└────────────────────────────┘   │ - block / retry / recover  │
                                 └────────────┬───────────────┘
                                              │ allow/block/plan/result refs
                                              ▼
                    ┌────────────────────────────┐
                    │ governance / artifact      │
                    │ - allow / waive / risk     │
                    │ - ImplementationPlan / report│
                    └────────────┬───────────────┘
                                 │ actual execution capability
                                 ▼
                    ┌────────────────────────────┐
                    │ tools / member-service     │
                    │ - tool invocation          │
                    │ - sandboxed execution      │
                    └────────────────────────────┘
```

### 4.2 位置解释

- `runtime` 自己负责“正式执行实例”“当前步骤”“执行状态”“执行反馈”
- `work` 提供正式工作主语与 promote 目标,但不让渡 work 真相
- `process` 提供 execution timing / resume expectation,但不接管 runtime 执行状态真相
- `governance` 提供 allow / block / waive / accept-risk 结果,但不接管执行正文
- `artifact` 提供 `ImplementationPlan` / reports / result materials,并承接 runtime 的结果回流
- `conversation` 消费 runtime 的执行摘要、失败原因、等待原因、promote 提示,但不拥有 execution truth
- `tools / member-service / sandbox` 提供执行能力,而 runtime 负责对这些能力进行编排

所以 `L2-runtime` 在全局里的角色是:
> **把 work 给出的正式工作、process 给出的执行时机、governance 给出的放行边界、artifact 给出的计划与结果材料,真正编排成执行过程的运行主脑。**

### 4.3 系统边界

**做什么**:
- 保存正式 ExecutionInstance / current step / execution state 真相
- 展开 ImplementationPlan 并推进 step
- 调度 tools / member-service / sandbox 等执行能力
- 处理 blocked / waiting_input / retry / resume / recover / promote
- 向 artifact / process / work / conversation 回流执行结果与状态

**不做什么**:
- 不负责 Project / WorkItem / child WorkItem 真相
- 不负责 ProcessInstance / Activity / Token 真相
- 不负责 Decision / RiskAcceptance / Waiver 真相
- 不负责 Artifact 正文本体真相
- 不负责 Conversation / Turn 真相
- 不把 tools/member-service/sandbox 的能力实现并入 runtime 真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| work | 99.9% | promote / completion 回流延迟,但当前 ExecutionInstance 真相继续存在; promote 无法落回 work 时,ExecutionInstance 进入受控等待 |
| process | 99.9% | execution timing / resume 信号延迟,但 runtime 本地状态继续存在; 等待 process 信号时进入 suspended |
| governance | 99.9% | allow/block/waive 输入延迟时,默认保持 blocked / waiting,不允许默认放行 |
| artifact | 99.9% | ImplementationPlan / report / output refs 延迟时,执行实例可等待或保留中间结果; 结果物化延迟不抹除 execution truth |
| conversation | 99.9% | 执行摘要/失败提示延迟,但 execution truth 不受影响 |
| tools / member-service / sandbox | 99.9% | 动作调度失败时进入 retry / blocked / failed 分支,不直接吞掉执行状态; 若 capability 层恢复可从稳定点 resume |

### 4.5 关键依赖风险

- runtime / process 边界不稳会导致 execution timing 与 execution truth 混层
- runtime / work 边界不稳会导致局部执行步骤直接污染 child WorkItem 真相
- runtime / governance 边界不稳会导致执行层本地放行,绕过正式治理结果
- runtime / artifact 边界不稳会导致 ImplementationPlan 被误当状态对象,或结果材料被误当执行状态本体
- runtime / conversation 边界不稳会导致执行摘要消息被误当正式执行真相
- promote 判定过松会导致大量局部 step 被抬升为协作任务,污染 backlog 与 child WorkItem 体系
- promote 判定过严会导致本该协作升级的问题长期困在局部执行层,无法被正式治理和排期
- recover / resume 后若 current step 漂移,会导致 artifact 结果、process 进度与实际执行点不一致
- tool/member-service 执行成功但 artifact/process/work 回流失败时,会出现“实际做过了,系统主线却没收口”的裂缝

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 真相/接缝差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 执行主语与运行实例部分

- **它是什么**: 这是 `L2-runtime` 的执行真相入口层,一起回答“这次到底围绕什么在执行”
- **为什么单独有它**: 如果没有独立执行实例主语,后续 step、retry、promote、反馈都会变成临时消息或局部状态
- **负责什么**:
  - 定义 ExecutionInstance
  - 绑定 work ref / process ref / plan ref / actor / capability snapshot
  - 维持 runtime 自己的主状态
- **不负责什么 / 容易混淆点**:
  - 不负责 WorkItem 真相
  - 不负责 ProcessInstance 真相
  - 最容易和 work 真相层、process activity 真相层混淆
- **与其他部分交互**:
  - 上游: work / process / governance / artifact / identity
  - 下游: step 推进部分、阻断恢复部分、结果回流部分
  - 交互类型: 运行主语锚点型
- **后续详细设计展开点**:
  - ExecutionInstance 模型
  - execution context / actor binding / state

#### 执行计划展开与步骤推进部分

- **它是什么**: 这是 `runtime` 的局部推进层,一起回答“现在执行到哪一步、下一步该做什么”
- **为什么单独有它**: 如果不单列,ImplementationPlan 就只是一份 artifact 文档,不会转成可推进运行态
- **负责什么**:
  - 读取并展开 ImplementationPlan
  - 定位 current step / next step
  - 管理 step progression 和局部推进顺序
- **不负责什么 / 容易混淆点**:
  - 不负责 Artifact 正文本体
  - 不负责 WorkItem 真相升级收口
  - 最容易和 artifact plan 正文本体、process 节点推进混淆
- **与其他部分交互**:
  - 上游: 执行主语与运行实例部分、artifact plan refs
  - 下游: 动作调度与执行反馈部分、结果回流与协作升级接缝部分
  - 交互类型: 计划展开型 + 步骤推进型
- **后续详细设计展开点**:
  - plan item / current step 模型
  - next step 选择规则

#### 动作调度与执行反馈部分

- **它是什么**: 这是 `runtime` 的动作执行层,一起回答“这一步是如何被真正执行的”
- **为什么单独有它**: 如果不单列,runtime 会退化成 tools/member-service 的薄包装,看不见真正的编排职责
- **负责什么**:
  - 调度 tool invocation
  - 调用 member-service / sandbox
  - 收集 stdout / result / error / structured feedback
- **不负责什么 / 容易混淆点**:
  - 不等于 tools 本体
  - 不等于 member-service / sandbox 本体
  - 最容易和能力层、底层执行层混淆
- **与其他部分交互**:
  - 上游: 执行计划展开与步骤推进部分
  - 下游: 阻断恢复部分、结果回流部分
  - 交互类型: 执行动作型 + 反馈输入型
- **后续详细设计展开点**:
  - dispatch contract
  - feedback model / action result

#### 阻断、恢复与治理接缝部分

- **它是什么**: 这是 `runtime` 的非 happy path 层,一起回答“为什么现在不能继续、怎样合法恢复”
- **为什么单独有它**: blocked / waiting_input / suspended / retry / resume / recover 不是同一件事,不单列就会都被写成“失败”
- **负责什么**:
  - 区分 blocked / waiting_input / suspended / retry / failed
  - 承接 governance 决策输入
  - 承接恢复、重试、重入执行
- **不负责什么 / 容易混淆点**:
  - 不负责 formal governance decision 真相
  - 不负责 process waiting_gate 真相
  - 最容易和 governance / process 混淆

### 7.4 层间约束规则(防退化)

- ExecutionInstance 是正式执行真相,conversation progress 不是
- ImplementationPlan 是 artifact 真相,step progression 只是其运行时展开结果
- blocked / waiting_input / suspended / retry 不能全部退化成 failed
- promote request 只能交回 work,不能在 runtime 内部偷偷升级成 child WorkItem
- tools / member-service / sandbox 是能力层,不能替代 runtime 自己的执行真相
- governance 未放行的高风险动作不得被 dispatch 层本地默认执行
- output/report/result 回流失败不等于 execution truth 自动回滚

**runtime 红线**:
- promote 不是局部 TODO,而是正式回流 work 的升级动作
- blocked / waiting_input / suspended / failed 不得混成一个模糊状态
- execution summary / conversation message 不得替代 ExecutionInstance 真相
- ImplementationPlan artifact 不得偷变成 runtime 内部状态对象
- 高风险动作不得绕过 governance 正式结果

## 8. 关键技术选型

### 8.1 为什么采用“执行实例层 / 计划推进层”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | ExecutionInstance 与 step progression 分层 |
| 备选方案 | 直接把 plan step 写进 process 或 work |
| 选择理由 | 防止 work/process 直接承受执行局部状态,保住 runtime 作为执行真相层 |
| 演进路径 | 后续可扩展更多 step 类型,但不把执行局部状态重新并回 work/process |

### 8.2 为什么 promote 必须回流给 work

| 维度 | 内容 |
|---|---|
| 当前选择 | 当局部执行步骤超出边界时,由 runtime raise promote request 给 work |
| 备选方案 | runtime 内部直接创建协作任务 |
| 选择理由 | 防止 runtime 污染正式任务真相 |
| 演进路径 | 后续可细化 promote 判定条件,但 promote 目标仍然是 work 真相层 |

### 8.3 为什么阻断/等待/恢复独立于普通失败

| 维度 | 内容 |
|---|---|
| 当前选择 | blocked / waiting_input / suspended / retry / recover 独立成正式执行语义 |
| 备选方案 | 全部并进 failed / retried |
| 选择理由 | 运行主线里“暂时不能继续”和“真正失败”是不同业务语义 |
| 演进路径 | 后续可扩展更细恢复策略,但不把这些状态压回一个 failed |

### 8.4 为什么 execution truth 不直接挂在 process activity 上

| 维度 | 内容 |
|---|---|
| 当前选择 | ExecutionInstance 在 runtime 独立持有,process 只持有 timing/activity 真相 |
| 备选方案 | 直接把执行状态塞进 Process Activity |
| 选择理由 | 防止流程时机与实际执行状态混层,保住“何时执行”和“如何执行”两条主线的边界 |
| 演进路径 | 后续可增强 progress feedback 细度,但 execution truth 归属仍在 runtime |

### 8.5 为什么 runtime 只消费 plan,不复制 artifact 正文真相

| 维度 | 内容 |
|---|---|
| 当前选择 | runtime 只消费 `ImplementationPlan` / report / output refs,不复制 artifact 正文真相 |
| 备选方案 | runtime 内部复制 plan 正文并把它当执行状态来源 |
| 选择理由 | 防止 artifact 正文和 runtime 状态耦死,同时保证 plan/report/result 仍然回到 artifact 侧承载 |
| 演进路径 | 后续可细化 plan 展开缓存,但不改变 artifact 仍是计划正文真相源 |

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: runtime 独立为执行主脑仓(当前) | 方案 B: 把执行逻辑散进 process/work/tools |
|---|---|---|
| 执行真相清晰度 | 高 | 低 |
| promote / retry / resume 边界 | 高 | 低 |
| 多域协作一致性 | 高 | 低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的执行不只是“某个工具跑了一下”。它必须围绕正式工作、正式执行时机、正式治理边界和正式计划形成一条统一可推进、可恢复、可升级、可回流的执行主线。如果把这些逻辑拆散到 process / work / tools / conversation,最终就会没有一个仓能正式回答“当前到底在怎么执行”。

## 10. 关键接口与数据流

### 10.1 核心接口列表(概要级,不写细节)

| 接口 | 输入 | 输出 | 幂等性 | 错误分类 |
|---|---|---|---|---|
| StartExecutionInstance | work ref + process timing + plan ref + actor | ExecutionInstance | 是 | 状态错误 |
| AdvanceExecutionStep | execution ref + current step feedback | updated execution state | 否 | 执行错误 |
| RaiseGovernedActionRequest | execution ref + governed action ref | governance request | 是 | 治理边界错误 |
| RaisePromoteRequest | execution ref + plan item ref | promote request | 是 | 边界错误 |
| SuspendExecution | execution ref + reason | execution suspended state | 是 | 状态错误 |
| ResumeExecution | execution ref + resume signal | execution resumed state | 是 | 恢复错误 |
| RecoverExecutionInstance | execution ref + stable point ref | recovered execution state | 是 | 恢复错误 |
| PublishExecutionResult | execution ref + result/report/output refs | output materialization result | 是 | 回流错误 |
| QueryExecutionHistory | execution ref | execution history / trace | 是 | 查询错误 |
| PublishExecutionSummary | execution ref + summary material | visible execution summary | 是 | 输出错误 |

### 10.2 核心数据流(至少一条路径精确到函数调用链)

#### 数据流 A · StartExecutionInstance 主线

```text
work ref + execution timing + governance allow + plan ref ready
  │
  ▼
runtime_api.start_execution_instance()
  │  → [读取 WorkItem / actor / plan refs]
  ▼
runtime_app_service.handle_start()
  │  → [构造 ExecutionInstance]
  │  → [绑定 process/activity / capability snapshot]
  ▼
execution_repo.save_instance()
  │
  ▼
step_selector.pick_current_step()
```

#### 数据流 B · AdvanceExecutionStep / dispatch / feedback 主线

```text
current step ready
  │
  ▼
runtime dispatches action
  │
  ├─▶ tools.invoke()
  ├─▶ member-service.execute()
  └─▶ sandbox.run()
          │
          ▼
      execution feedback returned
          │
          ▼
AdvanceExecutionStep
  │
  ├─▶ next step
  ├─▶ complete
  ├─▶ blocked / waiting_input / retry
  └─▶ output/report/result backflow
```

#### 数据流 C · blocked / retry / resume / recover 主线

```text
governance wait / missing input / tool failure / dependency missing
  │
  ▼
ExecutionInstance enters blocked / suspended / waiting_input
  │
  ▼
ResumeExecution / RecoverExecutionInstance
  │
  ▼
return to stable step
```

#### 数据流 D · promote 回流主线

```text
plan item exceeds local execution boundary
  │
  ▼
RaisePromoteRequest
  │
  ▼
work receives promote target
  │
  ▼
runtime remains waiting / controlled transition
```

#### 数据流 E · result backflow 主线

```text
step / execution result committed
  │
  ├─▶ artifact receives output/report/result refs
  ├─▶ process receives progress / complete / failed
  ├─▶ work receives completion / promote-related feedback
  └─▶ conversation receives visible execution summary
```

### 10.3 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 风险标注 |
|---|---|---|---|
| ExecutionInstance / current step / execution state | runtime | process / conversation / work / audit | 被消息或 process 节点替代 |
| ImplementationPlan ref | artifact 真相, runtime 只消费展开 | runtime / work / governance | 被误当 runtime 状态对象 |
| actor capability / tool scope snapshot | identity/governance 输入, runtime 使用其快照 | runtime | 与 identity/governance 主真相混层 |
| promote request | runtime 输出, work 消费收口 | work | 运行时直接污染 child WorkItem 真相 |
| output/report/result feedback | runtime 输出, artifact/process/conversation 消费 | artifact / process / conversation | 被误留在运行时局部状态里 |
| execution summary | runtime 输出, conversation 消费 | conversation | 被误当 execution truth 本体 |

## 11. 横切关注点

### 11.1 安全
- governance 未放行的高风险动作不得被 runtime 默认执行
- actor capability / tool scope 必须先于动作分派校验
- promote 不能绕过 work 真相层

### 11.2 性能
- StartExecutionInstance 与 step progression 不应拖垮执行反馈主线
- retry / resume / recover 不应让执行链长时间失去可观测性

### 11.3 可用性
- conversation 通知延迟不影响 execution truth
- tools/member-service 短时故障时,runtime 必须保住 blocked / retry / recover 状态真相
- process resume 信号延迟时,execution truth 必须保持 suspended 而不是漂移到 completed/failed

### 11.4 可观测性
- ExecutionInstance → step → feedback → output/promote 全链必须可追踪
- blocked / retry / resume / recover 必须可单独审计
- process/work/artifact/conversation 消费的 execution summary / feedback 应可对账到同一 execution ref

### 11.5 不可越权执行
- governance 未正式 allow/waive/accept-risk 的高风险动作不得被 dispatch
- tool capability 不足时,必须进入 blocked / request-governance / fail 之一,不能“先执行再补治理”
- promote 必须经过 work 收口,不能由 runtime 直接制造协作真相

### 11.6 成本
- 不把 work/process/governance/artifact 真相并入 runtime,避免模型膨胀
- 不让每个仓自己维护一套局部执行状态,降低长期维护成本

### 11.7 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| StartExecutionInstance | ≤ 100ms | 100ms |
| AdvanceExecutionStep 调度前主链 | ≤ 150ms | 250ms |
| summary / result 回流 | 最终一致 | 不做强一致预算 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在单项目样板中验证 `StartExecutionInstance → current step → dispatch → feedback` 最小执行主线
- **阶段 2**: 再验证 `blocked / retry / resume / recover` 主线与 governance consume 主线
- **阶段 3**: 再引入 `promote request → work 收口` 与 `artifact report/output/result 回流` 两条关键接缝主线
- **阶段 4**: 最后再引入 `conversation progress summary`、复杂 governed actions 与更细恢复分支

### 13.2 回滚策略
- 若 ExecutionInstance 主模型不稳,先回退到“只保留最小执行状态 + 不做复杂 promote/recover”的保守路径
- 若 governance consume 接缝不稳,先保持默认 blocked,暂停高风险动作自动执行
- 若 promote 语义不稳,先关闭自动 promote,退回人工确认后升级 child WorkItem
- 若 artifact 结果回流语义不稳,先保留 execution truth 和 process 反馈,暂缓正式结果物化

### 13.3 监控指标
- execution instance 创建成功率
- step progression 成功率
- blocked / retry / recover 频率
- promote request 触发率与误触发率
- artifact/process/conversation 回流漂移率

## 15. 结论

本概要设计的核心结论是:
- `L2-runtime` 是正式执行主脑层,不是流程仓、工具仓或消息仓
- `L2-runtime` 内部应按“执行主语与运行实例部分 / 执行计划展开与步骤推进部分 / 动作调度与执行反馈部分 / 阻断、恢复与治理接缝部分 / 结果回流与协作升级接缝部分”来理解,而不是按对象平铺理解
- `work` 管任务真相,`process` 管执行时机,`governance` 管放行边界,`artifact` 管计划与结果正文,`conversation` 管可见摘要,而 `runtime` 负责把它们真正编排成执行过程
- promote 不是局部 TODO,blocked 不等于 failed,summary 不等于 execution truth
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把对象模型、step progression、dispatch、recover、promote 和 result backflow 正式化

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 ExecutionInstance / current step / execution state / execution feedback 真相
- 展开 `ImplementationPlan` 并推进 step
- 调度 tools / member-service / sandbox 等执行能力
- 处理 blocked / waiting_input / retry / resume / recover / promote
- 把结果正式回流到 artifact / process / work / conversation

**本模块不做什么**:
- 不持有 `Project` / `WorkItem` / `child WorkItem` / `ProcessInstance` / `Decision` / `Artifact` 正文 / `Conversation` 真相
- 不等于 tools/member-service/sandbox 本体
- 不负责前端消息展示正文或工具协议细节正文

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 runtime“为什么存在”,而是让开发者可以直接开始实现:
- ExecutionInstance 如何建立
- current step / next step 如何推进
- dispatch / feedback 如何闭环
- blocked / waiting_input / retry / resume / recover 如何分层
- promote 如何正式交回 work
- output/report/result 如何正式回流 artifact / process / conversation

如果不先把这些内容采集清楚,03 很容易退化成:
- 把 runtime 写成 tools 调用脚本层
- 把 runtime 写成 process activity 的附属状态块
- 把 promote 当成普通 TODO 扩展
- 把 artifact 的 plan / report 正文真相吸进 runtime 内部对象

### 2.2 内容采集流程(先采集,再落文)

#### 第 1 步:列出要实现的核心对象

#### 第 2 步:列出主流程与关键异常流

必须先分清:

- 哪些 ref 只能作为输入和输出,不能反向变成 execution truth 本体

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 work / process / governance / artifact / tools/member-service
- 哪些结果输出给 artifact / process / work / conversation
- 哪些动作在 governance 未放行时绝不能进入 dispatch
- promote request、progress summary、artifact output material 谁拥有正式真相、谁只消费信号

#### 第 5 步:列出最小测试输入

必须测:
- ExecutionInstance ≠ Process Activity
- blocked / waiting_input / suspended / failed 分层
- promote 只能回流 work

## 4. 仓整体运行主流程

### 4.1 总流程图

```text
[work ref / timing / plan / governance allow]

                   ▼
[执行主语与运行实例部分]
                   │
```

### 4.2 总解释

- **真相写入**发生在: ExecutionInstance、CurrentStep、ExecutionFeedback、BlockedState、PromoteRequest 的正式持久化
- **计划推进**发生在: plan item 展开、当前步骤定位、下一步选择
- **动作执行**发生在: tool/member-service/sandbox 的能力调用与反馈回收
- **阻断恢复**发生在: governance wait、missing input、tool failure、resume/recover 主线
- **结果回流**发生在: artifact output/report、process progress、work promote/completion、conversation summary
- **同步路径**主要是: StartExecutionInstance / AdvanceExecutionStep / Suspend/Resume 主写链
- **异步最终一致**主要是: artifact 回流、conversation summary、部分 process/work 信号输出

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `ExecutionInstance / CurrentStep / PromoteRequest` 等对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与回流
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 execution truth / step progression / dispatch / recover / backflow,`03` 却只剩几个状态字段表
- 实现者知道有 CurrentStep,却不知道它归哪个责任单元控制
- promote、recover、artifact output、conversation summary 四条链路脱节

### 5.2 `执行主语与运行实例部分` 的实现要点

#### 5.2.1 该部分承接的概要输入
- 承接 `02` 中“执行主语与运行实例部分”的职责
- 承接 `runtime` 与 `work/process/governance/artifact/identity` 的交互链
- 承接 `ExecutionInstance ≠ Process Activity`、`execution summary ≠ execution truth` 两条硬边界

#### 5.2.2 输入 / 输出 / 外部交互图

```text
┌────────────────────────────┐
│ work / process / artifact  │
│ - WorkItem ref             │
│ - execution timing         │
│ - ImplementationPlan ref   │
└────────────┬───────────────┘
             │ execution start context
             ▼
┌────────────────────────────┐
│ runtime                    │
│ - ExecutionInstance        │
│ - execution context        │
│ - actor/capability binding │
└────────────┬───────────────┘
             │ execution truth ready
             ▼
┌────────────────────────────┐
│ step progression / dispatch│
└────────────────────────────┘
```

#### 5.2.3 涉及的对象定义

```rust
/// 表示一次正式执行活动在 runtime 中的主语对象。
pub struct ExecutionInstance {
    /// 执行实例唯一标识。
    pub execution_instance_id: ExecutionInstanceId,
    /// 本次执行关联的正式工作引用。
    pub workitem_ref: WorkItemRef,
    /// 本次执行关联的流程活动引用。
    pub process_activity_ref: ProcessActivityRef,
    /// 本次执行消费的计划引用。
    pub implementation_plan_ref: ImplementationPlanRef,
    /// 当前执行状态。
    pub state: ExecutionState,
    /// 当前执行 actor 的稳定引用。
    pub actor_ref: ActorRef,
    /// 当前能力/工具范围快照。
    pub capability_snapshot: CapabilitySnapshot,
}

/// 表示执行状态,用于区分 running / blocked / waiting / failed / completed 等语义。
pub enum ExecutionState {
    /// 已创建但尚未真正进入 running。
    Pending,
    /// 正在执行。
    Running,
    /// 因治理/依赖/输入等原因被阻断。
    Blocked,
    /// 等待外部输入。
    WaitingInput,
    /// 已暂停,等待恢复。
    Suspended,
    /// 执行完成。
    Completed,
    /// 执行失败。
    Failed,
}
```

这些对象在该部分里分别承担:
- `ExecutionInstance` 回答“这次正式执行到底是什么执行”
- `ExecutionState` 把 running / blocked / waiting / suspended / failed 显式化
- work/process/artifact/governance 的输入只进入 execution context,不变成对方真相本体

#### 5.2.4 关键函数代码片段

```rust
/// 根据正式工作、执行时机和计划引用启动一个 ExecutionInstance。
fn start_execution_instance(
    execution_repo: &dyn ExecutionRepo,
    draft: StartExecutionDraft,
) {
    // [ExecutionInstance::从草稿创建]
    // 先把 work/process/artifact/governance/actor 输入收束成正式执行主语。
    let execution = ExecutionInstance::from_draft(draft);

    // [execution.校验可启动]
    // 再校验执行时机、治理边界、actor snapshot 与计划引用的最小成立条件。
    execution.validate_startable();

    // [execution_repo.保存执行实例]
    // 最后把 ExecutionInstance 写入 runtime 真相层。
    execution_repo.save(execution);
}
```

这段实现守住的边界是:
- execution truth 必须独立存在,不能只隐含在 process/work 中
- 计划、治理、actor 都以 ref/snapshot 方式进入 execution context
- 执行启动先于 step 细化,不把 CurrentStep 与主语对象混写

#### 5.2.5 该部分的边界与非职责
- 不负责推进具体 step
- 不负责 dispatch 真正执行动作
- 不负责 artifact 输出正文写入
- 不负责 conversation 摘要展示层

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `执行计划展开与步骤推进部分` 提供 execution context
- 向 `阻断、恢复与治理接缝部分` 提供当前 execution state 主语
- 从 work/process/artifact/governance/identity 接收 refs / snapshots

#### 5.2.7 该部分的状态 / 约束 / 易错点
- ExecutionInstance 存在不等于已经开始 dispatch
- capability snapshot 是输入快照,不是 identity/governance 真相本体
- execution state 不能被 conversation 消息反向定义

### 5.3 `执行计划展开与步骤推进部分` 的实现要点

#### 5.3.1 该部分承接的概要输入

#### 5.3.3 涉及的对象定义

```rust
/// 表示运行时对一份正式计划的绑定结果。
pub struct ExecutionPlanBinding {
    /// 对应的执行实例。
    pub execution_instance_id: ExecutionInstanceId,
    /// 被展开的计划引用。
    pub implementation_plan_ref: ImplementationPlanRef,
    /// 当前活跃的计划项绑定。
    pub current_plan_item: Option<PlanItemBinding>,
}

/// 表示一条计划项在运行态中的绑定结果。
pub struct PlanItemBinding {
    /// 归属执行实例。
    pub execution_instance_id: ExecutionInstanceId,
    /// 来自正式计划的计划项引用。
    pub plan_item_ref: PlanItemRef,
    /// 这条计划项当前是否可被执行。
    pub executable: bool,
}

/// 表示当前正在执行的步骤。
pub struct CurrentStep {
    /// 对应执行实例。
    pub execution_instance_id: ExecutionInstanceId,
    /// 当前步骤标识。
    pub step_id: StepId,
    /// 对应的计划项引用。
    pub plan_item_ref: PlanItemRef,
    /// 当前步骤的推进状态。
    pub progress: StepProgress,
}

/// 表示步骤推进状态。
pub enum StepProgress {
    /// 尚未开始。
    NotStarted,
    /// 正在执行。
    Running,
    /// 已完成。
    Completed,
    /// 已失败。
    Failed,
    /// 当前被阻断。
    Blocked,
}

/// 表示下一步该执行什么的判定结果。
pub struct NextStepDecision {
    /// 当前是否还有下一步。
    pub has_next: bool,
    /// 若有,下一步的计划项引用。
    pub next_plan_item_ref: Option<PlanItemRef>,
    /// 若没有,为什么结束。
    pub terminal_reason: Option<TerminalReason>,
}
```

这些对象在该部分里分别承担:
- `ExecutionPlanBinding` 负责把 artifact 中的计划引用转换成运行时绑定关系
- `PlanItemBinding` 负责把“计划正文中的某一项”变成 runtime 里的正式执行对象
- `CurrentStep` 负责把“现在到底跑到哪一步”写成正式真相
- `StepProgress` 把 running/completed/failed/blocked 显式化
- `NextStepDecision` 负责把下一步选择显式化,而不是让调度层自己临时判断

#### 5.3.4 关键函数代码片段

```rust
/// 从正式计划引用中选出当前执行实例的下一步。
fn select_next_step(
    step_repo: &dyn StepRepo,
    execution: &ExecutionInstance,
    binding: &ExecutionPlanBinding,
) {
    // [binding.读取当前计划项]
    // 先从 execution 绑定的正式计划中定位当前 plan item。
    let next = binding.decide_next_step();

    // [CurrentStep::从判定结果创建]
    // 再把下一步正式固化成 CurrentStep,供 dispatch 层消费。
    let step = CurrentStep::from_decision(execution.execution_instance_id, next);

    // [step_repo.保存当前步骤]
    // 把这次步骤推进写入正式运行时真相。
    step_repo.save(step);
}
```

这段实现守住的边界是:
- 计划真相仍在 artifact,但 step progression 真相在 runtime
- 下一步选择必须被显式化
- CurrentStep 是 runtime 真相,不是 artifact plan 文本的投影截图

#### 5.3.5 该部分的边界与非职责
- 不负责 Artifact 正文本体
- 不负责真正 dispatch 动作
- 不负责 promote 正式回流收口
- 不负责 conversation 摘要输出

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `执行主语与运行实例部分` 接收 execution context
- 向 `动作调度与执行反馈部分` 提供 dispatch-ready CurrentStep
- 向 `结果回流与协作升级接缝部分` 提供 promote 判定的上游输入

#### 5.3.7 该部分的状态 / 约束 / 易错点
- CurrentStep 不能由 artifact 的正文更新直接替代
- NextStepDecision 与 dispatch 结果不能混写成一个对象
- plan item 超出局部执行边界时,不能继续假装是普通 next step

#### 5.4.4 关键函数代码片段

```rust
/// 根据当前步骤把动作分派给具体执行能力层,并收回执行反馈。
fn dispatch_current_step(
    dispatcher: &dyn ActionDispatcher,
    feedback_repo: &dyn FeedbackRepo,
    step: &CurrentStep,
) {
    // [DispatchAction::从当前步骤创建]
    // 先把运行时步骤翻译成一个正式 DispatchAction。
    let action = DispatchAction::from_step(step);

    // [dispatcher.发起执行]
    // 把该动作交给 tools/member-service/sandbox 等能力层执行。
    let result = dispatcher.dispatch(action);

    // [feedback_repo.记录执行反馈]
    // 把能力层返回的正式反馈写入 runtime 真相层。
    feedback_repo.save(result);
}
```

这段实现守住的边界是:
- dispatch 层不直接定义 work/process/governance 真相
- 成功发起 dispatch 不等于 step 已完成
- ActionResult 必须正式写回 runtime,不能只存在临时日志里

#### 5.4.5 该部分的边界与非职责
- 不负责 governance 决策真相
- 不负责 artifact 正文真相
- 不负责 child WorkItem promote 收口
- 不负责 conversation 真相本体

#### 5.4.6 该部分与其他主要部分的接缝

- 向 `阻断、恢复与治理接缝部分` 传递失败/阻断反馈
- 向 `结果回流与协作升级接缝部分` 提供成功/输出结果

#### 5.4.7 该部分的状态 / 约束 / 易错点
- dispatch 成功不代表 execution success
- tool/member-service/sandbox 的低层日志不能替代 runtime feedback 真相
- 一个 step 的多次重试必须有明确反馈链,不能覆盖旧结果

#### 5.5.4 关键函数代码片段

```rust
/// 在高风险动作未获放行或执行依赖未满足时,把执行实例转入正式阻断状态。
fn suspend_execution(
    execution_repo: &dyn ExecutionRepo,
    blocked_repo: &dyn BlockedRepo,
    execution: &ExecutionInstance,
    blocked: BlockedState,
) {
    // [execution.进入阻断状态]
    // 先把主执行状态切到 blocked / suspended 等正式状态。
    execution.transition_to_blocked();

    // [blocked_repo.记录阻断原因]
    // 再把阻断原因正式写入 runtime 真相层。
    blocked_repo.save(blocked);

    // [execution_repo.更新执行实例]
    // 最后提交 execution truth 状态变化。
    execution_repo.update_state(execution);
}
```

这段实现守住的边界是:
- blocked 与 failed 分层明确
- governance 未放行与 tool 执行失败都能形成正式阻断语义,但原因必须区分
- 恢复前必须有稳定执行点,不能从模糊“上次差不多的位置”继续

#### 5.5.5 该部分的边界与非职责

- 不负责 process waiting_gate 真相
- 不负责 artifact 正文真相

- retry 不是 recover,两者必须有不同语义和记录方式

```rust
/// 把执行结果回流给 artifact / process / work / conversation 等下游仓。
fn publish_execution_result(
    publisher: &dyn RuntimeBackflowPublisher,
    execution: &ExecutionInstance,
    result_signal: ArtifactOutputSignal,
    progress_signal: ProcessProgressSignal,
    summary: ExecutionSummary,
) {

    // 先把正式 output/report/result material 发回 artifact。
```

### 7.4 关键函数/命令级伪代码

#### `StartExecutionInstance`

```text
function StartExecutionInstance(input):
    1. 校验 work ref / process timing / plan ref / governance allow
    2. 构造 ExecutionInstance
    3. 持久化 ExecutionInstance
    4. 选择 current step
    5. 返回 execution context
```

#### `CheckExecutionReadiness`

```text
function CheckExecutionReadiness(input):
    1. 读取 execution context / capability snapshot / governance state
    2. 校验当前 step 是否具备执行前置条件
    3. 校验 tool scope / actor capability / dependency completeness
    4. 返回 ready / blocked / governance_required / input_missing 结果
```

#### `AdvanceExecutionStep`

```text
function AdvanceExecutionStep(input):
    1. 读取 CurrentStep 与 ExecutionInstance
    2. dispatch 当前步骤动作
    3. 收到执行反馈
    4. 更新 step progress
    5. 若成功则选下一步
    6. 若失败则进入 blocked/retry/recover 分支
    7. 返回新的 execution state
```

#### `DispatchCurrentStep`

```text
function DispatchCurrentStep(input):
    1. 校验当前步骤可执行
    2. 构造 DispatchAction
    3. 选择 tools/member-service/sandbox 路径
    4. 发起真实执行动作
    5. 返回 dispatch handle / initial execution ref
```

#### `HandleExecutionFeedback`

```text
function HandleExecutionFeedback(input):
    1. 读取 dispatch action / execution instance / current step
    2. 保存 ActionResult
    3. 判断 success / blocked / failed / retryable
    4. 选择推进、阻断、重试、恢复或回流路径
```

#### `RaisePromoteRequest`

```text
function RaisePromoteRequest(input):
    1. 读取当前 plan item / execution state
    2. 校验是否满足 promote 边界
    3. 构造 WorkPromoteSignal
    4. 发回 work
    5. 当前 execution 进入受控等待或转移态
```

#### `RetryExecutionStep`

```text
function RetryExecutionStep(input):
    1. 读取 RetryState / CurrentStep
    2. 校验该失败是否允许重试
    3. 增加 attempt 计数
    4. 重新 dispatch 当前步骤
    5. 记录 retry trace
```

#### `RecoverExecutionInstance`

```text
function RecoverExecutionInstance(input):
    1. 读取 RecoverState / stable point
    2. 校验恢复点合法
    3. 让 execution 回到稳定 step
    4. 重新建立 current step / progress context
    5. 返回 recovered state
```

#### `PublishExecutionResult`

```text
function PublishExecutionResult(input):
    1. 读取 step result / execution feedback
    2. 构造 artifact output/report/result refs
    3. 发回 artifact
    4. 发回 process progress/complete
    5. 发回 conversation summary
    6. 记录 backflow completion status
```

#### `MarkExecutionCompleted / MarkExecutionFailed`

```text
function MarkExecutionCompleted(input):
    1. 校验没有剩余步骤
    2. 切换 execution state = completed
    3. 触发 result / summary / process complete backflow

function MarkExecutionFailed(input):
    1. 记录最终失败原因
    2. 切换 execution state = failed
    3. 触发 failure summary / process failed backflow
```

| 命令 | 权限校验 | 审批校验 | 责任链校验 | 不通过时处理 |
|---|---|---|---|---|
| StartExecutionInstance | actor / assignee 合法 | governance allow | plan/work/process refs 合法 | 拒绝启动 |
| AdvanceExecutionStep | 当前步骤可推进 | 高风险动作前需 allow | step 与 plan 绑定合法 | 进入 blocked / fail |
| RaisePromoteRequest | promote 条件满足 | 无 | promote target 合法 | 拒绝升级 |
| Suspend/Resume/Recover | 当前 state 可转换 | governed wait/resume 合法 | stable point 存在 | 拒绝恢复 |
| PublishExecutionResult | result/output 合法 | 无 | artifact/process/work/conversation refs 合法 | 延迟回流 / 重试 |

### 7.6 关键状态机 / 非法转换与约束

#### 状态机图

```text
ExecutionInstance:
pending → running
running → blocked / waiting_input / suspended / completed / failed
blocked/suspended → running (after resume/recover)

CurrentStep:
not_started → running → completed
running → blocked / failed
blocked → running (after retry/resume)
```

#### 非法转换与约束表

| 场景 | 是否允许 | 说明 |
|---|---|---|
| governance 未 allow 时 dispatch 高风险动作 | ❌ | 必须先 consume formal result |
| blocked / waiting_input / suspended 全压进 failed | ❌ | 三者与失败语义不同 |
| runtime 内部直接创建 child WorkItem 真相 | ❌ | promote 只能交回 work |
| conversation summary 反向定义 execution state | ❌ | summary 只是只读输出 |
| 无 plan ref 时启动 execution | ❌ | ImplementationPlan 是正式输入之一 |
| recover 后 current step 随意跳点 | ❌ | 必须回到稳定执行点 |
| blocked 状态直接跳 completed | ❌ | 必须先 resume/recover 再推进 |
| promote request 发出后继续无界推进原局部 step | ❌ | promote 后必须进入受控等待/转移态 |
| waiting_input 被错误当成 governance pending | ❌ | 两种等待必须区分原因 |

#### 关键约束说明

- `ExecutionState.blocked` 代表“当前不允许继续”,但未必失败
- `ExecutionState.waiting_input` 代表需要外部输入,默认不能自动恢复成 running
- `ExecutionState.suspended` 代表等待恢复信号或稳定恢复点,与 blocked / failed 不同
- `CurrentStep.running → completed/failed/blocked` 必须通过正式 feedback 或治理/依赖信号推进,不能靠消息层猜测

## 11. 运行期主线场景

### 11.1 场景 A · 正常执行一步步推进

```text
StartExecutionInstance
      │
      ▼
选 current step
      │
      ▼
dispatch action
      │
      ▼
receive feedback
      │
      ▼
advance next step
      │
      ▼
complete and backflow outputs
```

**开发者关注点**:
- 当前步骤推进必须正式落到 runtime 真相层
- dispatch 成功不等于 step 完成
- outputs / progress summary 只是在成功后回流

### 11.2 场景 B · 高风险动作被治理阻断并恢复

```text
current step hits governed action
      │
      ▼
raise governance request
      │
      ▼
ExecutionInstance enters blocked / suspended
      │
      ▼
governance allows / waives
      │
      ▼
ResumeExecution / RecoverExecutionInstance
      │
      ▼
return to stable step and continue
```

**开发者关注点**:
- governance pending 不是 failed
- blocked / suspended 必须留痕
- 恢复后 current step 不能漂移

### 11.3 场景 C · 局部执行升级为正式协作任务

```text
plan item exceeds local execution boundary
      │
      ▼
RaisePromoteRequest
      │
      ▼
work receives promote target
      │
      ▼
runtime remains in controlled waiting
      │
      ▼
work creates/accepts child WI path
```

**开发者关注点**:
- promote 不是内部 TODO
- runtime 不直接落 child WorkItem 真相
- promote 前后回链必须稳定

### 11.4 场景 D · artifact 回流失败但 execution truth 保留

```text
step 完成
      │
      ▼
execution truth 先提交 completed/current result
      │
      ▼
artifact backflow 失败
      │
      ▼
runtime 记录 backflow lag / retry state
      │
      ▼
conversation / process 看到“执行完成但结果回流待补齐”
      │
      ▼
backflow retry 成功后收口
```

**开发者关注点**:
- execution truth 与 artifact 回流必须分两段看
- artifact 回流失败不能抹掉 step 已完成事实
- retry 修复的是 backflow 链,不是重新发明 execution result

### 11.5 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| work/process/plan ready | StartExecutionInstance | 执行主语与运行实例部分 | execution truth created |
| step ready | AdvanceExecutionStep / dispatch | 执行计划展开与步骤推进部分 + 动作调度与执行反馈部分 | progress / feedback |
| govern wait / resume | SuspendExecution / ResumeExecution / RecoverExecutionInstance | 阻断、恢复与治理接缝部分 | blocked / resumed |
| local step exceeds boundary | RaisePromoteRequest | 结果回流与协作升级接缝部分 | promote signal |
| result ready | PublishExecutionResult | 结果回流与协作升级接缝部分 | artifact/process/conversation backflow |

## 12. 数据与存储设计

### 12.1 先分清写模型 / 读模型 / 证据引用

| 对象 | 类型 | 是否持久化 | 说明 |
|---|---|---|---|
| ExecutionInstance | 写模型 | 是 | 正式执行真相 |
| CurrentStep / StepProgress | 写模型 | 是 | 当前步骤真相 |
| ExecutionFeedback | 写模型 | 是 | 执行反馈真相 |
| Blocked/Retry/Recover state | 写模型 | 是 | 非 happy path 真相 |
| PromoteRequest | 写模型 | 是 | 协作升级请求真相 |
| ExecutionSummary / failure / promote notice | 读模型 | 是/可重建 | 人类可见和只读消费物料 |
| plan/work/process/governance/artifact refs | 引用 | 随真相持久化 | 只存 ref / snapshot |

### 12.2 关系与索引建议

| 表/集合 | 关键索引 |
|---|---|
| execution_instances | `execution_instance_id`, `state`, `workitem_ref` |
| execution_steps | `execution_instance_id + step_id`, `progress` |
| execution_feedbacks | `execution_instance_id + step_id`, `feedback_time` |
| execution_blocked | `execution_instance_id`, `reason_kind` |
| execution_promotes | `execution_instance_id + plan_item_ref`, `state` |
| execution_outputs | `execution_instance_id`, `result_ref`, `report_ref` |
| execution_recover_points | `execution_instance_id`, `stable_step_id` |

**索引理由**:
- `execution_instance_id + step_id` 支撑 current step、feedback 与 retry/recover 对账
- `state` 支撑 pending/running/blocked/suspended 实例列表查询
- `reason_kind` 支撑 blocked / governance wait / dependency failure 分类回放
- `plan_item_ref` 支撑 promote request 去重与 work 收口对账
- `stable_step_id` 支撑 recover 时快速定位合法恢复点

### 12.3 持久化建议

| 对象 | 存储方式 | 理由 |
|---|---|---|
| ExecutionInstance / Step / Feedback | 主表 | 正式执行主线真相 |
| Blocked/Retry/Recover | 主表 | 恢复主线不可丢 |
| PromoteRequest | 主表 | 协作升级必须留痕 |
| Summary / progress / notice views | 可重建读模型 | 高读压与写链解耦 |

**存储边界说明**:
- `ExecutionFeedback` 建议 append-only 记录,避免后续 recover / replay 丢失历史执行证据
- `RecoverState` 必须显式绑定 stable step,不能只靠最后一条 summary 反推恢复点
- `PromoteRequest` 是 runtime 主真相的一部分,不能只发事件不落库
- artifact/process/conversation backflow 状态建议独立记录,避免“执行已完成”和“回流已收口”混成一个布尔状态

### 12.4 关键校验

- StartExecutionInstance 前必须校验 plan/work/process/governance 输入齐备
- dispatch 前必须校验 capability / tool scope / governance allow
- recover 必须基于稳定执行点
- promote 必须绑定明确 plan item 与 reason

### 12.5 建议表结构草案

#### `execution_instances`

| 字段 | 类型 | 说明 |
|---|---|---|
| execution_instance_id | uuid | 主键 |
| workitem_ref | jsonb/text | 正式工作引用 |
| process_activity_ref | jsonb/text | 执行时机来源 |
| implementation_plan_ref | jsonb/text | 正式计划引用 |
| state | enum | pending/running/blocked/waiting_input/suspended/completed/failed |
| actor_ref | jsonb/text | 执行 actor |

#### `execution_steps`

| 字段 | 类型 | 说明 |
|---|---|---|
| execution_instance_id | uuid | 所属 execution |
| step_id | text/uuid | 当前步骤 |
| plan_item_ref | jsonb/text | 对应计划项 |
| progress | enum | not_started/running/completed/failed/blocked |

## 13. 读模型与投影设计

### 13.1 总体结构

```text
ExecutionInstance / Step / Feedback write model
   │
   ▼
projection builders
   ├─ execution summary
   ├─ failure reason material
   ├─ promote notice material
   └─ progress view
```

### 13.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| ExecutionSummary | ExecutionInstance + CurrentStep + last feedback | conversation 可见摘要 |
| FailureReasonView | blocked / failed / retry state | 人类可见失败与等待原因 |
| PromoteNoticeView | PromoteRequest + step context | promote 提示 |
| ProgressView | step progression + result state | process / conversation 消费视图 |

### 13.3 一致性说明

- 读模型允许最终一致
- summary / failure / promote / progress view 都只读
- process / conversation 读到的是 execution truth 的投影,不是 execution truth 本体
- promote notice 只表达升级需求,不替代 work 正式 child WorkItem 真相
- artifact/process/conversation 的 backflow 允许晚到,但必须能对账到同一 execution ref 与 step
- blocked / recover / retry 的对外摘要必须可回到正式 BlockedState / RecoverState / RetryState 真相
- rebuild / repair 顺序必须是: replay execution truth → replay step/feedback → replay blocked/recover → regenerate summary/backflow material

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| plan ref 缺失 | 拒绝 start execution |
| governance 未 allow | 进入 blocked / waiting |
| dispatch fail | retry / blocked / failed 分流 |
| artifact 回流失败 | 记录回流失败并重试,不抹除 execution truth |

### 14.1 重试 / 降级 / 熔断 / 补偿
- tools/member-service 故障时允许 retry / suspended,但 execution truth 不丢
- governance 迟到时默认保持 blocked,不允许默认继续
- artifact/process/conversation 回流失败时允许稍后补发,但不得伪装成已回流成功
- dispatch 成功但 feedback 丢失时,必须保留“已发起执行但反馈未闭环”的中间状态并支持 replay
- promote request 发出但 work 未收口时,ExecutionInstance 必须保持受控等待,不得继续无界推进原局部 step
- process 已推进而 runtime 未稳定写回时,必须以 execution truth 为主进行对账,必要时补发 progress/backflow 信号

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 执行主语与运行实例部分 | start 条件不全 | execution start trace | 拒绝启动 / 修正输入 | restart draft |
| 执行计划展开与步骤推进部分 | current step 漂移 / next step 错选 | step trace | 阻断推进 / 修正 plan binding | replay step selection |
| 动作调度与执行反馈部分 | dispatch fail / feedback 丢失 | dispatch log | retry / blocked / fail | replay feedback ingest |
| 阻断、恢复与治理接缝部分 | recover 点错误 / governance 迟到 | recover trace | 保持 blocked / 重新选择恢复点 | replay resume |
| 结果回流与协作升级接缝部分 | promote 未收口 / output 回流失败 | backflow lag | 重试输出 / 等待 work consume | replay backflow |

## 15. 实现红线 / 开发禁止事项

- 不允许把 ExecutionInstance 简化成 process activity 的附加状态
- 不允许把 blocked / waiting_input / suspended / failed 混成一个失败状态
- 不允许在 governance 未 allow 时 dispatch 高风险动作
- 不允许在 runtime 内部直接制造 child WorkItem 真相
- 不允许把 conversation summary 反向当作 execution truth 来源
- 不允许把 ImplementationPlan artifact 偷偷变成 runtime 内部状态主语
- 不允许在 promote request 发出后继续无界推进原局部 step
- 不允许用 summary / failure view 反推 recover stable point

## 17. 最小可运行闭环

- work + process + governance + plan ready 后,StartExecutionInstance 建立正式 execution truth 并推进至少一个 current step
- 该 step 完成后形成 output/report/result 并回流 artifact,同时把 progress 回给 process、summary 回给 conversation
- 遇到一个需要升级的局部 step 时,RaisePromoteRequest 把它正式交回 work 收口

---

## 18. 结论

本详细设计的核心结论是：
- `L2-runtime` 的实现必须围绕五个主要部分展开,而不是按对象平铺
- ExecutionInstance / CurrentStep / BlockedState / PromoteRequest 是正式真相,summary / failure / promote notice 只是只读消费层
- work / process / governance / artifact / conversation / tools 的输入与输出都必须围绕 runtime 的正式 execution truth 收口,不能再各自维护一套执行状态语义
- 后续测试与验收文档,应直接围绕 execution truth、step progression、recover、promote、artifact/process/conversation backflow 展开

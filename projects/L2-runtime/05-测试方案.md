### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 runtime 的接口可调用,而是系统验证 `L2-runtime` 是否真正满足“正式执行主脑仓”的设计要求,尤其要证明以下几点成立:
- ExecutionInstance / CurrentStep / ExecutionFeedback 构成正式执行真相层
- `ExecutionInstance ≠ Process Activity`、`ImplementationPlan ≠ runtime state` 两条核心边界成立
- blocked / waiting_input / suspended / retry / failed 必须严格分层
- governance 未 allow 的高风险动作不能被 dispatch
- promote 只能正式回流给 work,不能在 runtime 内部偷造 child WorkItem 真相
- artifact / process / work / conversation 围绕同一 execution truth 接收回流,不会漂移成多套语义
- recover 只能回到稳定执行点,不能任意跳点恢复

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 执行主语与运行实例部分 | 真相对象 | P0 | ExecutionInstance、execution context、主状态 |
| 执行计划展开与步骤推进部分 | 真相对象 | P0 | CurrentStep、PlanItemBinding、step progression |
| 动作调度与执行反馈部分 | 调度/反馈 | P0 | dispatch、feedback、tool/member-service/sandbox 接缝 |
| 阻断、恢复与治理接缝部分 | 恢复/阻断 | P0 | blocked / waiting_input / suspended / retry / recover |
| 结果回流与协作升级接缝部分 | 输出/升级 | P0 | artifact/process/work/conversation 回流与 promote |
| tool SDK / sandbox 内部实现细节 | 非范围 | P2 | 只验证 runtime 与能力层接缝,不验工具内部逻辑 |
| process / work / governance / artifact / conversation 的全部内部正文逻辑 | 非范围 | P2 | 只验 runtime 与它们的接缝,不验下游仓全部细节 |
| 前端展示像素级行为 | 非范围 | P2 | 只验证 execution summary material,不验 UI 组件 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数和局部不变量 | domain / policy owner | `execution.validate_startable`、`binding.decide_next_step`、`CurrentStep::from_decision`、`execution.transition_to_blocked`、promote boundary validation | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + dispatcher + publisher 联动 | backend / domain owner | `StartExecutionInstance`、`AdvanceExecutionStep`、`DispatchCurrentStep`、`HandleExecutionFeedback`、`SuspendExecution`、`ResumeExecution`、`RecoverExecutionInstance`、`RaisePromoteRequest`、`PublishExecutionResult`、`PublishExecutionSummary` | 执行、恢复、升级、回流链同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | process timing → runtime、governance allow/block → runtime、runtime output → artifact、runtime progress → process、runtime promote → work、runtime summary → conversation | 输入输出语义一致 |
| 恢复专项测试 | 验证 dispatch 成功但反馈丢失、backflow 失败、recover 漂移等异常链 | architecture / QA | feedback missing、artifact backflow failed、promote 未收、recover from stable point | 真相不丢失、链路可恢复 |
| 投影一致性测试 | 验证 summary / failure / promote / progress view 与 execution truth 一致 | backend / QA | blocked/waiting/suspended 展示差异、summary rebuild、promote notice rebuild | 投影只读且与真相一致 |
| 端到端主线测试 | 验证最小运行闭环 | QA / owner | start → step → feedback → artifact/process/conversation backflow；governance block → resume；promote → work | 主干执行闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| ExecutionInstance 独立于 Process Activity | start execution 后 runtime 自己持有正式执行真相 | 集成测试 | 是 | DB / API / trace |
| ImplementationPlan 是输入真相而不是 runtime state | plan 只被展开为 step,不替代 execution truth | 边界专项测试 | 是 | plan ref / current step compare |
| blocked / waiting_input / suspended / failed 分层成立 | 非 happy path 不混写 | 单元 + 集成测试 | 是 | state transition / negative flow |
| governance 未 allow 不得 dispatch 高风险动作 | governed action 进入 blocked / wait | 集成 + 事件链测试 | 是 | governance result / dispatch trace |
| promote 只能回流给 work | local step 超界时 RaisePromoteRequest | 集成测试 | 是 | promote signal / work consume |
| artifact/process/conversation 回流来自同一 execution truth | step 完成后多下游一致回流 | 事件链测试 | 是 | compare traces |
| recover 只能回到稳定执行点 | invalid recover point 被拒绝 | 恢复专项测试 | 是 | recover trace / error code |

## 6. 核心测试场景

| 场景 ID | 场景 | 前置条件 | 步骤摘要 | 预期结果 |
|---|---|---|---|---|
| TC-001 | StartExecutionInstance 成功创建 ExecutionInstance | work ref / timing / plan ref / allow 合法 | StartExecutionInstance | execution truth 创建成功 |
| TC-002 | 缺 plan ref 时拒绝启动 | implementation_plan_ref 缺失 | StartExecutionInstance | 返回 `RUNTIME_PLAN_REF_MISSING` |
| TC-003 | governance 未 allow 时阻止高风险 dispatch | governed action step + no allow | CheckExecutionReadiness → Dispatch | 进入 blocked / waiting |
| TC-004 | AdvanceExecutionStep 正常推进到下一步 | current step + success feedback | AdvanceExecutionStep | next step 正确选出 |
| TC-005 | Dispatch 成功但 feedback 丢失后进入可恢复状态 | action dispatched / no feedback | Dispatch → timeout | 进入 retry / suspended / recoverable state |
| TC-006 | blocked / waiting_input / suspended 三种等待语义区分成立 | 三类阻断输入存在 | state transitions | 三种状态不混淆 |
| TC-007 | ResumeExecution 继续推进 | governance allow / input ready | ResumeExecution | 从 blocked/suspended 回到 running |
| TC-008 | RecoverExecutionInstance 回到 stable point | recover point 合法 | RecoverExecutionInstance | current step 回到稳定点 |
| TC-009 | RaisePromoteRequest 交回 work | plan item 超界 | RaisePromoteRequest | work 收到正式 promote signal |
| TC-010 | artifact/process/conversation 三路 backflow 一致 | step completed | PublishExecutionResult / Summary | 多下游消费一致 |
| TC-011 | artifact 回流失败但 execution truth 保留 | output publish fails | PublishExecutionResult | execution truth 保持成立,backflow lag 可追踪 |
| TC-012 | conversation summary 不反写真相 | summary rebuild / drift | PublishExecutionSummary / rebuild | summary 只读,不改 execution truth |

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|
| S | ExecutionInstance/ProcessActivity 混层 / governance 未 allow 仍执行 / promote 绕过 work / recover 漂移 | 阻断放行,必须修复 |
| A | 主线可跑但 blocked/retry/resume/recover/backflow 语义不稳 | 原则上修复后再放行 |
| B | 非关键摘要视图、通知材料或低优先级查询异常 | 可带风险进入下一轮 |

---

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 ExecutionInstance / execution context,都必须回归 start execution 主线
- 每次改动 CurrentStep / NextStepDecision,都必须回归 step progression 与 terminal reason
- 每次改动 dispatch / feedback,都必须回归 dispatch succeed/feedback missing / retry 主线
- 每次改动 blocked/recover 逻辑,都必须回归 stable point 与 governance resume
- 每次改动 promote 逻辑,都必须回归 promote → work consume 主线
- 每次改动 artifact/process/conversation 回流,都必须回归多下游一致性

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| promote 判定后续若引入更多风险/耗时阈值 | 测试矩阵需扩充 | TL / 架构 |
| recover 语义若继续细分 checkpoint/replay | 恢复测试需增加更多分支 | runtime |
| tools/member-service 能力差异扩大 | dispatch contract 测试需增加适配器样本 | Owner / TL |

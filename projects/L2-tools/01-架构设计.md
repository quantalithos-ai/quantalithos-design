## 1. 业务背景与驱动力

### 1.1 业务背景

tools 不是一个普通工具库,而是 runtime 真正“伸手做事”的执行层。runtime 负责思考和决策,但它不能直接写 shell、随意出网、自由调用第三方能力；所有行动都必须被压缩成可声明、可校验、可审计的 ToolDescriptor 与调用结果。L2-tools 的职责,就是把这些行动能力组织成可复用、可裁剪、可安全约束的 monorepo,并作为 member-images 的一部分进入不同角色镜像。

### 1.2 业务驱动力

**业务驱动力**:
- AI 成员必须能真正读写文件、检索代码、跑测试、访问白名单外部能力,否则 runtime 无法完成软件交付任务
- 工具调用必须可解释、可追责、可按 Role 裁剪,否则不同角色镜像边界会失控

**技术驱动力**:
- 每个工具都必须有 input/output schema,以便 runtime 在调用前后做强校验
- 危险执行必须统一转交 sandbox,外部能力必须统一经过 capability-hub,防止直接出网和越权调用

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 安全 | 危险工具绕过 sandbox 次数 | 0 | 安全测试 |
| 安全 | Tool schema 覆盖率 | 100% | 回归测试 |
| 审计 | ToolInvoked / Completed / Failed 事件覆盖率 | 100% | 回归测试 |
| 兼容性 | 外部 MCP Tool 全部经 capability-hub | 100% | 集成测试 |
| 裁剪 | Role extras 样本构建成功率 | 100% | 镜像构建测试 |
| 性能 | 常用 in-process tool 调用框架开销 | 低于 runtime 单步预算 | benchmark |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| 每个 Tool 必须声明 input/output schema | TL1 + README | registry 与调用协议必须 schema-first |
| 危险 Tool 必须 `requires_policy_check=true` 且走 sandbox | TL2 + sandbox 边界 | 执行模式需先分类后实现 |
| 每次调用都必须发 ToolInvoked / ToolCompleted / ToolFailed 事件 | TL3 | tool runtime 必须内建审计钩子 |
| 外部 MCP Tool 只能走 capability-hub 白名单 | TL4 | MCP client 不得直连第三方 server |
| Tool 实现不得直接出网 | TL5 | browse/search/MCP 等外联能力必须经 hub 或 sandbox |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| MCP transport | client + hub 代理 | 可演进多 transport adapter |

| builtin tool 集合 | file/code/git/test/docs 起步 | 可按 N4 集成需要扩展 |
| schema 实现形态 | Python 数据模型 + descriptor | 可细化到更强静态生成 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| Tool schema 覆盖率 | 100% | 需求文档 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 工具种类增加 | 高 | ToolDescriptor registry + plugin-like module layout |
| 风险分类变化 | 中高 | execution mode / risk flags 独立建模 |
| Role extras 组合变化 | 高 | extras 分层打包 |
| MCP / capability-hub 协议演进 | 中 | MCP adapter 与 hub client 解耦 |
| schema 演进 | 中高 | descriptor versioning + validator 层 |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **schema-first monorepo + execution-mode 分层**(当前) | 易统一校验、审计口径一致、便于按 Role 裁剪 | 目录和描述层较重 | ✅ |
| 纯函数工具集合 | 实现快 | 风险分类与审计容易漂移 | ❌ |
| 每类工具独立小服务 | 隔离强 | 对 N4 起步过重,上下文切碎 | ❌ |
| runtime 内联工具实现 | 最少调用层 | runtime 边界坍塌、无法复用 | ❌ |

**最终选择**:**Python monorepo + ToolDescriptor registry + in-process/sandbox/mcp 三态执行模型**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 所有工具先注册后可调用 | 调用边界、schema、风险元数据统一 | 新增工具流程更严格 |
| 执行模式必须显式建模 | 危险路径不混入安全路径 | 需要维护 mode-specific adapter |
| extras 与核心工具解耦 | member-images 可按角色裁剪 | 打包矩阵复杂度上升 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
runtime / member-images / security / capability-hub
                    │
                    ▼
            ★ quantalithos-tools ★
            - tool registry
            - builtin tools
            - sandbox proxy
            - MCP client proxy
            - role extras bundles
             │          │          │
             │          │          └────────▶ capability-hub
             │          └──────────────────▶ sandbox
             └─────────────────────────────▶ observability(bus)
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 定义 ToolDescriptor / schema / risk flags / execution mode
- ✅ 提供 file/code/git/test/docs 等内置工具实现
- ✅ 提供 sandbox_exec 与 MCP client 代理
- ✅ 提供按 Role 打包的 extras 工具集

**不做什么**:
- ❌ 不决定何时调用哪个工具(属于 runtime)
- ❌ 不决定外部能力白名单与 Policy(属于 capability-hub / governance)
- ❌ 不提供隔离执行底座本身(属于 sandbox)
- ❌ 不负责镜像构建与发布流程(属于 member-images)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| `quantalithos-core` | 100%(编译期) | schema / proto 漂移 | 版本锁 |
| `quantalithos-capability-hub` | 99.9% | MCP 查询与外联能力不可用 | deny by default |
| `quantalithos-sandbox` | 99.9% | 危险工具不可执行 | fail closed |
| 本地依赖(git/pytest/lsp 等) | 环境依赖 | 某些工具不可用 | descriptor 层暴露 unavailable |
| observability / bus | 99.95% | 审计事件滞后 | backlog / replay |

### 4.4 关键依赖风险

- 若 tool registry 与 runtime invoker 的 schema 语义漂移,会出现“能注册但不能稳定调用”的隐性错误
- 若 MCP client 允许绕过 capability-hub,整条外联安全边界会失效
- 若 extras 打包没有稳定边界,不同 Role 镜像可能携带超出职责的工具能力

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Tool Registry | 核心域 | 统一描述工具、schema、风险与执行模式 |
| Builtin Execution | 核心域 | 内置工具的实际执行逻辑 |
| External Access | 支撑子域 | MCP client / capability-hub 代理 |
| Sandbox Mediation | 支撑子域 | 危险执行代理与回传 |
| Packaging Extras | 支撑子域 | Role-specific 工具包组织 |
| Tool Audit | 通用子域 | 调用事件留痕 |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Descriptor | ToolDescriptor 注册与校验 | ToolDescriptor / SchemaRef |
| Builtin | file/code/git/test/docs 具体实现 | ToolInvocation / ToolResult |
| SandboxProxy | 受控执行转发 | SandboxRequest / SandboxResult |
| MCPProxy | capability-hub 查询与外联代理 | CapabilityQuery / McpInvocation |
| Extras | Role 工具包声明 | ExtraBundle |
| Audit | 事件封装与发出 | ToolAuditEvent |

### 5.3 上下文映射关系

- runtime → Descriptor / Builtin / SandboxProxy / MCPProxy: **Customer-Supplier**，runtime 消费工具但不拥有定义
- capability-hub → MCPProxy: **Conformist**，tools 遵从 hub 的 allowlist / contract 决策
- sandbox → SandboxProxy: **Open Host Service**，tools 通过统一隔离执行接口转发
- member-images → Extras: **Customer-Supplier**，按 Role 消费工具包而不改写定义

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| ToolDescriptor | 一个工具的统一描述,含 schema、风险、执行模式、元数据 | Descriptor |
| execution_mode | `in_process / sandbox / mcp` 三种执行方式 | Descriptor / Runtime |
| ExtraBundle | 面向某个 Role 的可选工具集合 | Extras |
| ToolInvocation | 一次具体工具调用上下文 | Builtin / Audit |
| ToolResult | 结构化工具结果,必须过 output schema | Builtin / Runtime |
| requires_policy_check | 工具在调用前必须通过 Policy / sandbox / hub 边界检查 | Descriptor |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
member runtime process
        │ in-process call
        ▼
┌──────────────────────────────────────────────┐
│         quantalithos-tools package           │
│  registry / builtin / sandbox_proxy / mcp   │
└──────────────┬───────────────┬───────────────┘
               │               │
               ▼               ▼
        sandbox service   capability-hub
               │               │
               └──────┬────────┘
                      ▼
                observability(bus)
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| tools package | registry + builtin tools + adapters | Python | 跟随 runtime 进程 |
| sandbox proxy path | 危险执行转发 | Python + SDK client | 受 sandbox 限制 |
| MCP proxy path | capability-hub 外联代理 | Python + SDK client | 高频小请求 |
| audit emitter | 事件发出 | Python + bus client | 异步非阻塞 |
| extras bundles | Role-specific 依赖集合 | Python packaging | 由镜像构建时装配 |

### 6.3 通信方式与选择理由

| 通信场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| runtime → tools | 进程内调用 | 单独 RPC 服务 | tools 与 runtime 同栈,减少调用开销 |
| tools → sandbox | SDK / RPC | 本地 shell | 隔离能力必须交给统一底座 |
| tools → capability-hub | SDK / 结构化 RPC | 直接第三方连接 | 保持白名单、成本、审计边界 |
| tools → observability | 事件发出 | 同步写库 | 不阻塞主调用路径 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| ToolDescriptor registry | tools | runtime / member-images |
| ToolInvocation audit | tools | observability / audit |
| ExtraBundle metadata | tools | member-images |
| allowlist view(只读) | capability-hub 为真相 | tools 只读消费 |

### 6.5 部署拓扑

- tools 作为 Python 包随 runtime 一起装入 member 镜像
- 核心 builtin tool 与 runtime 同进程、同容器执行
- sandbox 与 capability-hub 作为外部服务/侧向依赖,不被内嵌进 tools 包

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
runtime tool invoker
        │
        ▼
 descriptor / dispatch
   ├─▶ builtin safe tools
   ├─▶ sandbox proxy
   ├─▶ mcp proxy
   └─▶ audit emitter
```

### 7.2 层间约束规则

- Descriptor 层只负责描述与校验,不执行工具逻辑
- Builtin safe tools 不得自行出网,若需外联必须转 MCPProxy 或 SandboxProxy
- SandboxProxy 只做代理,不在本地重实现隔离策略
- MCPProxy 只消费 capability-hub 的 allowed view,不维护独立白名单真相
- AuditEmitter 不改变调用结果语义,只负责留痕

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| ToolRegistry | descriptor domain | builtin registry implementation |
| ToolExecutor | dispatch domain | builtin / sandbox / mcp executors |
| SandboxGateway | sandbox proxy domain | sandbox SDK adapter |
| CapabilityGateway | mcp proxy domain | capability-hub SDK adapter |
| AuditSink | audit domain | bus / observability adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(runtime / member-images / tests) |
| 传出耦合 | 中高(sandbox / capability-hub / bus / local deps) |
| 不稳定性 | 中 |
| 抽象度 | 中高(registry 与 executor 分离) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者(写入方) | 消费者(读取方) | 一致性级别 | 风险标注 |
|---|---|---|---|---|
| ToolDescriptor | tools | runtime / member-images | 强一致(包内静态真相) | — |
| ToolInvocation audit event | tools | observability | append-only | bus 延迟可重放 |
| ExtraBundle | tools | member-images | 强一致(版本化) | role 组合爆炸需治理 |
| Capability allowlist view | capability-hub | tools | 最终一致 | hub 不可用需 deny |
| Sandbox execution result | sandbox 为真相,tools 为消费方 | runtime | 最终一致(调用内确认) | 失败需 fail closed |

### 8.2 一致性层次

- **Level 1 · 包内强一致**:ToolDescriptor、ExtraBundle、builtin executor 注册关系在单版本包内一致
- **Level 2 · 外部能力最终一致**:allowlist、sandbox policy、MCP server 可用性都从外部系统拉取并最终一致
- **Level 3 · 跨服务调用补偿**:调用开始后若 sandbox / hub 失败,tools 必须给 runtime 返回结构化失败并发审计事件

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| ToolInvoked 已发但执行失败 | executor raise error | 发 ToolFailed,返回结构化错误结果 | `invocation_id` |
| sandbox 调用超时 | sandbox 无响应 | fail closed + ToolFailed + 标记 timeout | `invocation_id` |
| capability-hub deny / 不可用 | allowlist query fail | 直接拒绝外联调用 | `invocation_id + tool_name` |
| output schema 校验失败 | executor 返回非法结果 | 拒绝返回给 runtime,转 ToolFailed | `invocation_id` |

## 9. 关键技术选型

### 9.1 Python 与 runtime 同栈

| 维度 | 内容 |
|---|---|
| 当前选择 | Python |
| 备选方案 | Rust / Go |
| 选择理由 | tools 与 runtime 高耦合且多依赖 AI / 测试 / LSP 生态,同栈能降低桥接成本 |
| 演进路径 | 热路径或高风险代理后续可局部下沉到独立实现 |
| 不可逆程度 | 中 |

### 9.2 ToolDescriptor schema-first 模型

| 维度 | 内容 |
|---|---|
| 当前选择 | 每 Tool 显式 input/output schema + risk flags |
| 备选方案 | 只靠文档约定 / 运行时弱校验 |
| 选择理由 | runtime 需要稳定、可验证的调用边界；弱约定会让 Agent 行为不可控 |
| 演进路径 | 可从手写 descriptor 演进到生成式 descriptor |
| 不可逆程度 | 中高 |

### 9.3 三态执行模型(in-process / sandbox / mcp)

| 维度 | 内容 |
|---|---|
| 当前选择 | 明确三态执行模型 |
| 备选方案 | 所有工具都当本地函数 / 所有工具都远程化 |
| 选择理由 | 本地安全工具、危险执行、外部能力三类边界本就不同,强行统一只会模糊风险 |
| 演进路径 | 后续可加 `agent_delegate` 等新 mode |
| 不可逆程度 | 高 |

### 9.4 Role extras 打包策略

| 维度 | 内容 |
|---|---|
| 当前选择 | 核心工具 + Role extras 组合 |
| 备选方案 | 所有角色全量安装 / 每角色单独维护完整工具仓 |
| 选择理由 | 兼顾镜像体积、职责边界与维护成本 |
| 演进路径 | 细化到更多 bundle 或按 capability group 组合 |
| 不可逆程度 | 中 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:monorepo + registry + 三态执行(当前) | 方案 B:纯本地函数库 | 方案 C:每类工具拆独立服务 |
|---|---|---|---|
| 安全边界 | 高 | 低 | 高 |
| 审计一致性 | 高 | 中低 | 中 |
| 实施复杂度 | 中 | 低 | 高 |
| 运行开销 | 中低 | 低 | 高 |
| 适配 N4 | 高 | 中低 | 低 |

### 10.2 最终选择与理由

选择 A,因为 L2-tools 的核心问题不是“函数怎么写”,而是“调用边界怎么被控制、审计和裁剪”。B 起步虽快,但无法稳定承接 sandbox / capability-hub / extras；C 则把 N4 阶段本该统一收敛的问题过早分布式化,不合当前粒度。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 超时 | sandbox / MCP 调用必须有默认 timeout |
| 重试 | 对外联代理采用有限次重试,本地工具默认不隐式重试 |
| 降级 | capability-hub / sandbox 不可用时按 deny 或 fail closed 处理 |
| 限流 | 高频外联工具由上层或 hub 控制,tools 本层保留本地节流点 |
| 隔离 | builtin / sandbox / mcp 三类 executor 分离,避免故障串扰 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | descriptor load / invocation start / policy deny / schema fail |
| 指标 | invocation count / fail rate / schema rejection / sandbox timeout |
| 追踪 | `trace_id` 贯穿 runtime → tools → sandbox/hub → audit events |
| 健康检查 | 包级自检关注 descriptor 完整性与依赖可用性 |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| schema 校验 | 输入输出都必须过校验 |
| 授权 | 危险工具必须显式 requires_policy_check |
| 审计 | 所有调用都发事件留痕 |
| 出网控制 | 本层不直接外联,统一走 hub 或 sandbox |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | timeout / feature enable / dependency path 外部化 |
| 环境隔离 | dev / test / prod 可启不同 extras 与依赖检测 |
| 动态更新 | allowlist 与 hub contract 由外部系统动态提供 |
| 配置五要素 | 每项配置标明 type / default / constraint / source |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| descriptor lookup | 低毫秒级 | benchmark | runtime 高频路径 |
| safe builtin dispatch | 低毫秒级 | benchmark | 不应吃掉 loop 预算 |
| sandbox proxy overhead | 尽量低于 sandbox 启动主耗时 | benchmark | sandbox 架构 |
| capability query overhead | 依赖 hub,本层只加最小包装 | benchmark | capability-hub |

**端到端延迟分解**(单次工具调用框架开销尽量小于 runtime 单步预算):

```
总预算 = runtime 可接受的单步工具框架开销

  ┌ descriptor 解析与校验   ≤ 小量固定开销
  ├ executor 路由           ≤ 小量固定开销
  ├ 外部代理包装            ≤ 最小附加开销
  └ audit 发出              ≤ 异步不阻塞主路径
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| sandbox 集成深度(Tool 自声明 vs Policy override)未定 | 影响危险工具分类策略 | P1 |
| MCP transport 细节未定 | 影响外联代理边界 | P1 |
| AG-UI tool result 类型未与 conversation 侧完全对齐 | 影响前端结果展示 | P2 |
| extras 依赖冲突治理未展开 | 影响 role 镜像稳定性 | P2 |

### 12.2 演进触发条件(可量化)

| 指标 | 阈值 | 演进动作 |
|---|---|---|
| schema 校验失败率异常 | > 阈值 | 强化 descriptor 生成或测试 |
| 外联工具 deny 过多 | 持续 1 周 | 调整 allowlist / docs / role extras |
| extras 依赖冲突频发 | > 阈值 | 拆细 bundle 或重构打包边界 |
| 某类工具代理复杂度过高 | 评审触发 | 从 monorepo 中抽独立 adapter 层 |

### 12.3 演进步骤

```
阶段 1: ToolDescriptor + file/code/git/test/docs + audit 跑通
   └─ 可停止点:runtime 能用最小工具集完成本地任务

阶段 2: sandbox_exec + MCP proxy + capability-hub 联动
   └─ 可停止点:危险与外联调用有统一边界

阶段 3: role extras 稳定 + richer tool taxonomy
   └─ 可停止点:多角色镜像可裁剪构建
```

### 12.4 目标架构

L2-tools 的目标不是堆更多工具,而是成为 **runtime 的统一行动契约层**:所有动作都能被描述、验证、约束、裁剪和审计。未来即便工具种类增长,核心边界仍应保持稳定——新增的是 capability,不是新的调用哲学。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| schema 不完善导致 runtime 调用失败 | 中 | 中 | registry validation + contract tests |
| 危险工具被误标为安全工具 | 低 | 高 | security review + mode 审核 |
| capability-hub / MCP 协议漂移 | 中 | 高 | SDK version lock + adapter tests |
| extras 包膨胀或交叉污染 | 中 | 中 | role bundle review + image tests |

### 13.2 边缘风险

- 某 Role extras 引入的系统依赖与基础镜像冲突
- sandbox 与本地 safe tool 行为在同名场景下不一致
- tool result 结构与上游 UI / runtime 消费者产生隐性漂移

### 13.3 待确认问题

| 问题 | 待定时限 | 负责人 |
|---|---|---|
| sandbox 集成深度(Tool 自声明 vs Policy override) | L2 后 | tools + sandbox |
| MCP client transport 选型 | L2 后 | tools + capability-hub |
| AG-UI tool result 类型对齐方式 | L2 后 | tools + conversation |

## 14. 上线策略

### 14.1 灰度方案

```
阶段 1: 仅启用 file/code/git/test/docs 最小内置工具
阶段 2: 接入 sandbox_exec,验证危险路径
阶段 3: 接入 capability-hub 代理的外部 MCP Tool
阶段 4: 按 backend-dev / qa / devops 等 Role 打开 extras
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| 危险工具绕过 sandbox | S 级 | 立即停用对应 ToolDescriptor / 回滚版本 |
| schema 校验大面积失败 | A 级 | 回滚 descriptor 版本或禁用新增工具 |
| MCP 代理异常导致外联普遍失败 | A 级 | 暂停 MCP tools,保留 builtin tools |
| extras 构建冲突 | B 级 | 回退对应 Role bundle |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| ToolFailed rate | > 阈值 | warning |
| schema rejection rate | > 阈值 | warning |
| sandbox timeout | > 阈值 | major |
| direct-network violation | > 0 | critical |
| MCP deny count | > 阈值 | warning / security |

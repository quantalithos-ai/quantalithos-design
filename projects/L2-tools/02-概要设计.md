## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L2-tools` 不是脚本收纳仓,也不是能力目录仓。它是 **“正式工具能力仓”**。

你可以把它理解成:
- 平台里到底有哪些正式可调用工具
- 这些工具能力被怎样定义、怎样调用、怎样返回结果
- 哪些工具可以在当前上下文里被谁调用
- 工具调用失败时,是普通错误、可重试错误还是需要升级成执行阻断/治理动作
- 为什么 runtime 和 member 不该直接各自维护一套工具调用约束和结果语义

这些事情,都由 `L2-tools` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L2-tools`,这些工具能力事实就会散落在:
- `runtime` 的 dispatch 逻辑里
- `member-service` 的 host execute 里
- `sandbox` 的执行环境里
- 本地脚本、外部 SDK、adapter 代码里
- `capability-hub` 的能力目录里

结果就会出现:
- 工具定义和工具调用混在一起
- 哪些是正式暴露能力、哪些是内部实现细节说不清
- runtime/member 不得不直接知道每个工具的调用细节
- tool policy / scope / result 结构没有统一归属
- 工具失败、越权、审计记录各处散落,没有正式能力层来收口

所以 `L2-tools` 必须独立存在,作为:
> **正式工具能力、调用约束、结果结构与观测审计的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### ToolDefinition
就是:
> 一个正式可被平台调用的工具能力定义。

它回答的是:
- 这是什么工具
- 接收什么输入
- 返回什么结果
- 允许在哪些上下文里被调用

它不是某段临时脚本或某个 adapter 函数名。

#### ToolInvocationRequest
就是:
> runtime/member 发给 tools 的正式工具调用请求。

它不是 runtime 的整个执行主线,也不是 conversation 里的一条指令文本。

#### ToolPolicy / ToolScope
就是:
> 这个工具在当前上下文里能不能被调用、能调用到什么程度的正式约束。

它不是 sandbox 本体,也不是 capability-hub 的目录标签。

#### ToolInvocationResult
就是:
> 一次工具调用返回给上游的正式结构化结果。

它不只是 stdout,也不只是日志片段,而是 tools 层承认的正式结果对象。

#### ToolAuditEntry
就是:
> 一次工具调用的正式留痕与审计记录。

它不是 observability 的原始日志替代品,而是 tools 层自己的正式审计事实。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L2-tools/02` 时,先收稳以下前提:
- `L2-tools` 不应按对象数拆,而应按主要部分拆
- tools 至少应拆成“工具定义与契约 / 工具调用入口与请求校验 / 工具权限与策略约束 / 工具执行结果与失败分流 / 工具审计与观测接缝”五个主要部分
- tools 自己拥有的真相是 ToolDefinition / ToolContract / ToolInvocationRequest / ToolInvocationResult / ToolPolicy / ToolAuditEntry / ToolHealth/Availability
- `ExecutionInstance / MemberRuntimePersona / Sandbox / Conversation / CapabilityCatalog` 都不是 tools 真相
- tools 可以消费这些域的 refs、scopes、signals,但不能把它们收编为自己的主真相
- 02 的重点不是“有哪些工具名字”,而是先把“tools 在平台里到底是什么、和相邻仓怎么分层”讲清楚

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的系统心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,执行主脑和成员主体都不会直接“自己什么都做”,它们最终要通过正式工具能力去访问文件、搜索、命令、网络和外部接口。用户真正需要的不是“系统里有一些工具函数”,而是:
- 哪些能力是正式工具能力
- 这些工具在什么上下文里能被调用
- 调用前会不会做边界与策略校验
- 调用结果怎样被结构化返回给 runtime/member
- 调用失败时是否可以重试、是否需要治理、是否需要阻断执行主线

如果把这些逻辑分别散落到:
- runtime 的 dispatch 代码
- member-service 的宿主适配层
- sandbox 的执行环境
- capability-hub 的目录关系
- 各类本地脚本和外部 SDK 包装里

系统会快速退化成:
- 工具定义、工具权限、工具结果和工具审计彼此漂移
- runtime/member 需要自己判断每个工具怎么调、能不能调
- 工具失败时没有统一的结构化返回语义
- tool scope / policy / sandbox 约束没有独立归属
- 工具调用留痕只能靠原始日志,没有正式审计入口

因此,本概要设计的任务就是:
> **把 `L2-tools` 写成一个新人也能看懂的“正式工具能力仓”,而不是把 adapter、脚本、sandbox 和 dispatch 混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 工具能力归属 | 易散落在 runtime/member-service/sandbox 中 | ToolDefinition 成为正式真相层 | 需写死边界 |
| 调用入口 | 易与 runtime dispatch 或消息文本混层 | ToolInvocationRequest 独立存在 | 需正式落图 |
| 权限约束 | 易被隐含在宿主或 sandbox 代码中 | ToolPolicy / ToolScope 成为显式边界 | 需形成主要部分 |
| 结果语义 | 易退化成 stdout/logs | ToolInvocationResult 成为正式结构化返回 | 需单列并固定 |
| 审计观测 | 易只剩 observability 原始日志 | ToolAuditEntry 成为正式留痕层 | 需固定接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让正式工具能力被稳定定义、被受控调用、被结构化返回、被可追溯审计,而不让运行主线和宿主层各自实现一套工具逻辑
- **技术问题**:ToolDefinition / ToolInvocationRequest / ToolPolicy / ToolInvocationResult / ToolAuditEntry 之间的边界如何稳定建模,并与 `runtime/member/member-service/sandbox/capability-hub` 清晰协作而不混层

## 4. 本仓在全局架构中的位置

### 4.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ capability-hub             │
                    │ - capability graph         │
                    │ - capability composition   │
                    └────────────┬───────────────┘
                                 │ capability catalog / composition input
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ runtime                    │   │ tools                      │   │ sandbox                    │
│ - dispatch intent          │──▶│ - ToolDefinition           │──▶│ - isolation boundary       │
│ - governed action flow     │   │ - ToolInvocationRequest    │   │ - execution restriction    │
│ - result consume           │   │ - ToolPolicy / ToolScope   │   └────────────────────────────┘
└────────────────────────────┘   │ - ToolInvocationResult     │
                                 └────────────┬───────────────┘
                                              │ tool result / audit / health
                                              ▼
                    ┌────────────────────────────┐
                    │ member / member-service    │
                    │ - exposed capability       │
                    │ - host-side invocation     │
                    └────────────┬───────────────┘
                                 │ visible call effect / logs / metrics
                                 ▼
                    ┌────────────────────────────┐
                    │ observability / governance │
                    │ - audit / trace            │
                    │ - escalated failure consume│
                    └────────────────────────────┘
```

### 4.2 位置解释

- `tools` 自己负责“正式工具定义”“正式工具调用请求”“正式工具结果”“工具权限与审计”
- `runtime` 发起工具调用需求,但不拥有工具能力真相
- `member` 决定成员当前对外暴露哪些工具能力出口,但不拥有工具定义真相
- `member-service` 真正承接宿主层执行,但不拥有工具定义和调用契约真相
- `sandbox` 提供隔离环境与限制边界,tools 决定哪些调用必须受这些边界约束
- `capability-hub` 提供能力目录/组合输入,但不替代正式工具契约层
- `observability / governance` 消费的是 tools 的审计、健康和失败升级结果

所以 `L2-tools` 在全局里的角色是:
> **把平台中正式可调用的工具能力、调用约束、执行结果与审计观测统一收拢为一个正式能力层。**

### 4.3 系统边界

**做什么**:
- 保存 ToolDefinition / ToolContract / ToolInvocationRequest / ToolInvocationResult 真相
- 保存 ToolPolicy / ToolScope / ToolAvailability 等正式约束
- 向 runtime/member/member-service 提供正式可调用工具能力
- 向 observability / governance 提供工具调用审计、健康和失败升级材料

**不做什么**:
- 不负责 ExecutionInstance / CurrentStep 真相
- 不负责 MemberRuntimePersona 真相
- 不负责 MemberExecutionHost / Session 真相
- 不负责 Sandbox 本体真相
- 不负责 CapabilityCatalog 真相
- 不负责 Conversation / Turn 真相

### 4.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| runtime | 99.9% | dispatch intent 延迟时,tools 保持已注册能力真相,不自行制造业务执行主线 |
| member | 99.9% | 成员能力暴露延迟时,tools 仍保留正式定义,但不声称当前一定可被成员暴露 |
| member-service | 99.9% | 宿主层承载延迟时,tools 保持可调用契约真相,但回传 host unavailable / deferred execute |
| sandbox | 99.9% | 无法获得隔离环境时,受限工具进入 blocked / denied / retryable 结果分支；不允许“先执行后补限制” |
| capability-hub | 99.9% | 组合能力延迟时,保留基础 ToolDefinition 与最小 ToolScope |
| observability | 99.9% | metrics/logs 延迟不影响 ToolInvocationResult 真相,但观测结果后到；ToolAuditEntry 仍应先正式留痕 |
| governance | 99.9% | governed tool 需要升级治理时,可先返回 governance_required / blocked,不得默认放行 |

### 4.5 关键依赖风险

- tools / runtime 边界不稳会导致工具调用主线与执行主线混层
- tools / member 边界不稳会导致 exposed capability 被误当 ToolDefinition 真相
- tools / member-service 边界不稳会导致宿主执行细节反向污染工具契约层
- tools / sandbox 边界不稳会导致隔离限制退化成隐式实现细节
- tools / capability-hub 边界不稳会导致能力目录与正式工具定义彼此漂移
- 同一 ToolDefinition 在不同 host-side adapter 上返回不一致结果时,上游会看到同一工具出现多套结果语义
- runtime 视为 retryable 的失败,若 tools 层未显式分类,会导致执行链错误恢复
- raw stdout 看似成功而 structured result 实际失败时,若不分层,会让上游错误推进执行主线
- ToolInvocationResult 已生成但 ToolAuditEntry 未成功写入时,工具调用会失去正式审计闭环

### 5.2 主要组成部分说明

> 这里的“主要部分”不是单个对象,也不是单张表或单组 CRUD。  
> 它按 **独立职责 + 主交互链位置 + 稳定边界 + 定义/调用/策略/结果/观测差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象,共同支撑同一段职责与协作链。

#### 工具定义与契约部分

- **它是什么**: 这是 `L2-tools` 的定义真相层,一起回答“这个正式工具能力是什么”
- **为什么单独有它**: 如果不单列,工具定义会退化成 adapter 函数集合或 capability-hub 标签,无法形成正式调用契约
- **负责什么**:
  - 定义 ToolDefinition
  - 定义 ToolKind / ToolContract
  - 统一工具参数和返回的正式语义边界
- **不负责什么 / 容易混淆点**:
  - 不负责 runtime 的执行主线调度
  - 不负责 member 的主体能力暴露真相
  - 最容易和 capability-hub 目录标签、member exposed capability 混淆
- **与其他部分交互**:
  - 上游: capability-hub / tools adapters
  - 下游: invocation request / policy / result / audit
  - 交互类型: 能力定义型
- **后续详细设计展开点**:
  - ToolDefinition / ToolContract / ToolKind 模型

#### 工具调用入口与请求校验部分

- **它是什么**: 这是 tools 的正式调用入口层,一起回答“谁在调、调什么、是否允许这样调”
- **为什么单独有它**: 如果不单列,工具调用请求会散在 runtime dispatch 和宿主 adapter 里,失去工具层的正式入口语义
- **负责什么**:
  - 定义 ToolInvocationRequest
  - 做参数校验、preflight check、调用前请求归一化
  - 给权限和执行层提供正式请求对象
- **不负责什么 / 容易混淆点**:
  - 不负责 tool policy 本体
  - 不负责实际宿主执行承载
  - 最容易和 runtime action、conversation command 文本混淆
- **与其他部分交互**:
  - 上游: runtime / member / callers
  - 下游: policy / execute / audit
  - 交互类型: 正式调用入口型
- **后续详细设计展开点**:
  - invocation request / validation / preflight 模型

#### 工具权限与策略约束部分

- **它是什么**: 这是 tools 的策略边界层,一起回答“这个工具在当前上下文能不能被调用”
- **为什么单独有它**: 如果不单列,policy / scope / restricted tool 的判断会散进 runtime、member-service 或 sandbox 里
- **负责什么**:
  - 定义 ToolPolicy / ToolScope
  - 定义受治理约束的工具分类
  - 在执行前给出 allow / deny / require-governance 等判断
- **不负责什么 / 容易混淆点**:
  - 不负责 sandbox 本体真相
  - 不负责 execution truth 真相
  - 最容易和 governance / sandbox / capability-hub 混淆
- **与其他部分交互**:
  - 上游: ToolInvocationRequest / governance / sandbox / capability inputs
  - 下游: invocation result / audit / runtime
  - 交互类型: 权限约束型 + 调用裁决型
- **后续详细设计展开点**:
  - tool scope / policy / governed tool class 模型

#### 工具执行结果与失败分流部分

- **它是什么**: 这是 tools 的结果层,一起回答“调用后返回什么、失败如何分类”
- **为什么单独有它**: 如果不单列,stdout、structured result、retryable failure 会退化成宿主日志或 runtime 临时判断
- **负责什么**:
  - 定义 ToolInvocationResult
  - 区分 success / retryable / denied / blocked / failed
  - 为上游提供正式可消费结果
- **不负责什么 / 容易混淆点**:
  - 不负责 runtime 的业务推进真相
  - 不负责 member-service 的宿主健康真相
  - 最容易和 raw stdout / host failure 混淆
- **与其他部分交互**:
  - 上游: request / policy / member-service / sandbox execution
  - 下游: runtime / audit / observability
  - 交互类型: 正式结果输出型
- **后续详细设计展开点**:
  - result / retryable failure / denied/blocked result 模型

#### 工具审计与观测接缝部分

- **它是什么**: 这是 tools 的留痕与观测层,一起回答“工具调用如何被正式记录、怎样被观测”
- **为什么单独有它**: 如果不单列,工具调用留痕会退化成 raw logs,难以成为正式审计输入
- **负责什么**:
  - 定义 ToolAuditEntry
  - 输出 metrics / traces / logs / callback material
  - 给 observability / governance / runtime 提供正式观测材料
- **不负责什么 / 容易混淆点**:
  - 不负责 observability 自己的存储真相
  - 不负责 runtime execution truth
  - 最容易和 raw logs / sandbox telemetry 混淆
- **与其他部分交互**:
  - 上游: invocation / policy / result
  - 下游: observability / governance / runtime
  - 交互类型: 审计输出型 + 观测输出型
- **后续详细设计展开点**:
  - audit entry / metrics / trace / callback material 模型

### 6.2 总解释

- `tools` 自己负责“正式工具定义”“正式工具调用请求”“正式工具结果”“工具权限与审计”
- `runtime` 的交互主要落在 **工具调用入口与请求校验部分**、**工具权限与策略约束部分** 与 **工具执行结果与失败分流部分**,发起工具调用并消费结构化结果
- `member` 的交互主要落在 **工具定义与契约部分** 与 **工具权限与策略约束部分**,通过 tools 看到“哪些正式能力可以暴露”,但不拥有工具定义真相
- `member-service` 的交互主要落在 **工具执行结果与失败分流部分**,承接工具真正执行的宿主侧调用,但不替代工具能力定义真相
- `sandbox` 的交互主要落在 **工具权限与策略约束部分**,作为受限工具的隔离与约束来源
- `capability-hub` 的交互主要落在 **工具定义与契约部分**,为 tools 提供能力目录和组合输入
- `observability / governance` 消费的是 tools 的审计、指标、trace 和失败升级材料,而不是自己定义工具主真相

**读图方法**:
- 中间的 `tools` 是正式工具能力真相源,但内部不是按对象平铺理解,而是按 5 个主要部分理解
- 左侧输入的是 dispatch intent 和成员能力暴露需求
- 右侧输入的是隔离环境和能力目录
- 下侧消费的是正式结构化结果与审计观测材料,而不是 raw host logs 本体

## 7. 总体架构设计

### 7.1 架构风格与分层

**架构风格**: 工具定义层 + 正式调用入口层 + 权限策略层 + 结果分流层 + 审计观测层分层

**选择理由**:
- 把“工具是什么”和“谁来调、怎么调、能不能调、调完返回什么”分开
- 把工具能力和成员能力暴露分开
- 把工具结果和宿主原始日志分开
- 把审计/观测层从主调用链中分离出来
- 为 `03-详细设计.md` 提供稳定的按主要部分展开骨架


### 7.4 层间约束规则(防退化)

- ToolDefinition 不是 capability catalog 标签集合
- ToolInvocationRequest 不是 runtime action 本体
- ToolPolicy / ToolScope 不能隐含在 host 执行代码里
- ToolInvocationResult 不是 raw stdout / raw logs 的别名
- ToolAuditEntry 只读留痕,不得反写 invocation 真相
- member-facing exposed capability 只能引用 ToolDefinition,不得替代 ToolDefinition 本体
- governed/restricted tool 必须显式分类,不得靠调用方自行猜测

**tools 红线**:
- structured ToolInvocationResult 不得退化成 raw stdout 文本
- ToolAuditEntry 不得完全依赖 observability 原始日志替代
- ToolPolicy / ToolScope 不得隐藏进 sandbox 或宿主实现细节
- member/runtime 不得绕过 ToolInvocationRequest 直接内嵌工具调用逻辑

## 8. 关键技术选型

### 8.1 为什么采用“工具定义层 / 调用入口层”分层

| 维度 | 内容 |
|---|---|
| 当前选择 | ToolDefinition/ToolContract 与 ToolInvocationRequest 分层 |
| 备选方案 | 让 runtime/member 直接持有工具调用定义 |
| 选择理由 | 防止调用主线和能力定义主线混层 |
| 演进路径 | 后续可扩展更多 adapter/contract 类型,但定义归属仍在 tools |

### 8.2 为什么工具权限与 sandbox 绑定分层

| 维度 | 内容 |
|---|---|
| 当前选择 | ToolPolicy / ToolScope 在 tools 明确表达,sandbox 只提供隔离边界 |
| 备选方案 | 把工具权限完全隐含在 sandbox 或宿主层 |
| 选择理由 | 防止调用边界退化成隐式基础设施细节 |
| 演进路径 | 后续可细化 governed/restricted tool class,但 policy 归属仍在 tools |

### 8.3 为什么工具结果与 raw log 分离

| 维度 | 内容 |
|---|---|
| 当前选择 | ToolInvocationResult / ToolAuditEntry 与 raw stdout/logs 分层 |
| 备选方案 | 直接把原始输出当正式结果 |
| 选择理由 | 防止上游 runtime/member 依赖日志文本而不是正式结构化结果 |
| 演进路径 | 后续可扩展 richer result schema,但 raw logs 仍不替代正式结果真相 |

### 8.4 为什么 ToolInvocationResult 独立于宿主 callback

| 维度 | 内容 |
|---|---|
| 当前选择 | tools 层对宿主原始 callback 做统一结果归一化后再形成 ToolInvocationResult |
| 备选方案 | 直接把 member-service 宿主 callback 作为正式工具结果 |
| 选择理由 | 防止宿主执行细节和正式工具结果语义混层,保证上游 runtime/member 消费一致格式 |
| 演进路径 | 后续可扩展更多 host-side adapter,但 ToolInvocationResult 仍保持统一 contract |

### 8.5 为什么 governed tool 分类保留在 tools 侧

| 维度 | 内容 |
|---|---|
| 当前选择 | tools 显式标注 governed/restricted tool classes,再与 governance/sandbox 协作 |
| 备选方案 | 完全把高风险分类外包给 governance 或 sandbox |
| 选择理由 | 只有 tools 自己最清楚某调用契约的能力边界与风险面,若不在本层显式化,调用方就会各自推断 |
| 演进路径 | 后续可细化更多受限类目,但分类归属仍保留在 tools 层 |

---

## 9. 备选方案与取舍

### 9.1 方案对比

| 维度 | 方案 A: tools 独立为正式工具能力仓(当前) | 方案 B: 把工具逻辑散进 runtime/member-service/sandbox |
|---|---|---|
| 工具真相清晰度 | 高 | 低 |
| 调用边界稳定性 | 高 | 低 |
| 结果与失败分流一致性 | 高 | 低 |
| 审计可追溯性 | 高 | 低 |
| 实现复杂度 | 中 | 低 |
| 长期维护性 | 高 | 低 |

### 9.2 最终结论

选择方案 A。
因为 Quantalithos 里的工具能力不是一些零散脚本或 adapter 的总和。它们必须以 ToolDefinition、ToolInvocationRequest、ToolPolicy、ToolInvocationResult 和 ToolAuditEntry 的形式正式存在,才能让 runtime/member 以一致方式调用,让 member-service/sandbox 以一致方式承载和限制,让 observability/governance 以一致方式理解调用发生了什么。

### 10.1 核心接口列表(概要级,不写细节)

| 接口 | 输入 | 输出 | 幂等性 | 错误分类 |
|---|---|---|---|---|
| RegisterToolDefinition | tool spec / contract input | ToolDefinition | 是 | 校验错误 |
| ValidateToolInvocation | invocation request + context | validation result | 是 | 权限/参数错误 |
| QueryToolPolicy | tool ref + runtime/member context | ToolPolicy / ToolScope | 是 | 查询错误 |
| InvokeTool | ToolInvocationRequest | ToolInvocationResult | 否 | 执行错误 |
| NormalizeToolResult | raw callback / stdout / structured payload | ToolInvocationResult | 是 | 归一化错误 |
| RecordToolAudit | invocation + result + failure info | ToolAuditEntry | 是 | 留痕错误 |
| QueryToolInvocationHistory | tool ref / invocation ref | invocation history | 是 | 查询错误 |
| ReplayToolAudit | invocation ref | replay material | 是 | 回放错误 |

### 10.2 核心数据流(至少一条路径精确到函数调用链)

#### 数据流 A · ToolDefinition 定义主线

```text
capability-hub / adapter input ready
  │
  ▼
register_tool_definition()
  │  → [构造 ToolDefinition / ToolContract]
  ▼
tool_repo.save_definition()
  │
  ▼
runtime/member can discover formal tool ability
```

#### 数据流 B · ToolInvocationRequest → validation → policy → execution 主线

```text
runtime/member issues tool request
  │
  ▼
validate_tool_invocation()
  │
  ▼
query_tool_policy()
  │
  ▼
member-service / sandbox host-side invoke
  │
  ▼
normalize_tool_result()
  │
  ▼
ToolInvocationResult returned
```

#### 数据流 C · result → audit / metrics / trace 主线

```text
ToolInvocationResult produced
  │
  ▼
record_tool_audit()
  │
  ├─▶ runtime consumes structured result
  ├─▶ observability consumes metrics/trace
  └─▶ governance consumes escalated failure if needed
```

#### 数据流 D · governed / restricted tool 升级主线

```text
tool request hits governed/restricted boundary
  │
  ▼
ToolPolicy returns denied / governance_required / blocked
  │
  ▼
runtime/member receives restricted result
  │
  ▼
optional governance escalation / execution block
```

### 10.3 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 风险标注 |
|---|---|---|---|
| ToolDefinition / ToolContract | tools | runtime / member / adapters | 被 capability catalog 替代 |
| ToolInvocationRequest | tools 接口层 | runtime / member / member-service | 被 runtime action 或 command 文本替代 |
| ToolPolicy / ToolScope | tools | runtime / sandbox / governance | 被 sandbox 细节替代 |
| ToolInvocationResult | tools | runtime / audit / observability | 被 raw stdout 替代 |
| ToolAuditEntry | tools | observability / governance | 被原始日志替代 |
| host-side raw callback / stdout | member-service / sandbox 原始执行层 | tools 做归一化输入 | 被误当正式工具结果 |

## 11. 横切关注点

### 11.1 安全
- 未获允许的工具调用不得进入正式执行
- governed / restricted tool 必须显式经过 policy / scope 判断
- raw stdout/logs 不得越权替代正式结构化结果

### 11.2 性能
- request validate / preflight 不能拖垮 runtime 主线
- result split / audit write 不应让正式结果长期阻塞

### 11.3 可用性
- member-service 或 sandbox 短时故障时,tools 必须返回正式 retryable / denied / blocked 结果,而不是沉默失败
- observability 延迟不影响 ToolInvocationResult 真相存在
- runtime 暂时未消费结果时,ToolInvocationResult 与 ToolAuditEntry 仍应先正式成立

### 11.4 可观测性
- request → policy → execute → result → audit 全链必须可追踪
- governed / denied / retryable 分支必须可单独审计
- 同一调用的 structured result、audit、metrics/trace 应可对账

### 11.5 结果规范性与边界
- ToolInvocationResult 必须独立于 raw stdout / raw callback / raw log
- member-facing exposed capability 不得反向替代 ToolDefinition / ToolContract 真相
- governed / restricted tool 分类必须显式表达,不能只隐藏在 host/sandbox 实现里

### 11.6 成本
- 不把 runtime/member-service/sandbox/capability-hub 真相并入 tools,避免模型膨胀
- 不让每层都维护一套工具结果/权限语义,降低长期维护成本

### 11.7 性能预算表(端到端延迟分解)

| 环节 | 预算 | 累计 |
|---|---|---|
| ValidateToolInvocation | ≤ 100ms | 100ms |
| Policy / Scope 判定 | ≤ 100ms | 200ms |
| InvokeTool 发起 | ≤ 100ms | 300ms |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| ToolDefinition 与 capability catalog 混层 | 中 | 高 | 在详细设计中继续固定定义与目录边界 |
| ToolInvocationRequest 与 runtime action 混层 | 中 | 高 | 单独建模调用入口对象 |
| ToolPolicy 被隐含进 sandbox / host 执行细节 | 中 | 高 | 把 policy/scope 显式建模 |
| raw logs 被误当正式调用结果 | 中 | 高 | 固定 ToolInvocationResult / ToolAuditEntry 结构 |

### 12.2 边缘风险

- capability-hub 若继续强化组合能力语义,ToolContract 派生规则可能继续扩展
- governed tool 分类若继续增多,policy/scope 规则会细化
- host-side invocation 若支持更多后端,adapter 路径会继续分叉

## 13. 上线策略

### 13.1 灰度方案
- **阶段 1**: 先在单主线样板中验证 `ToolDefinition → ToolInvocationRequest → ToolInvocationResult` 最小主线
- **阶段 2**: 再验证 `ToolPolicy / ToolScope → governed/restricted tool` 主线与 sandbox consume 主线
- **阶段 3**: 再引入 `ToolAuditEntry / metrics / trace` 与 `structured result normalization` 主线
- **阶段 4**: 最后再引入复杂 capability composition、member-facing capability exposure 与多 adapter host-side 分流

### 13.2 回滚策略
- 若 ToolDefinition / ToolContract 主模型不稳,先回退到“最小正式工具定义 + 最小结果结构”的保守路径
- 若 ToolPolicy / ToolScope 语义不稳,先收紧为默认 deny / minimal allow 能力集
- 若 ToolAuditEntry / metrics 输出不稳,先保留正式 ToolInvocationResult 真相,暂停复杂观测聚合路径
- 若 member-facing capability exposure 输入不稳,先限制 tools 向 member 暴露的能力范围,避免越界外显

### 13.3 监控指标
- tool definition 注册成功率
- invocation validate 成功率
- governed / denied / retryable 分支频率
- structured result 返回成功率
- tool audit / trace 漂移率

## 15. 结论

本概要设计的核心结论是:
- `L2-tools` 是正式工具能力、调用约束、结果结构与观测审计的真相层,不是 runtime、member-service、sandbox 或 capability-hub 的附属层
- `L2-tools` 内部应按“工具定义与契约部分 / 工具调用入口与请求校验部分 / 工具权限与策略约束部分 / 工具执行结果与失败分流部分 / 工具审计与观测接缝部分”来理解,而不是按脚本、adapter 或调用函数平铺理解
- `runtime` 管执行主线,`member` 管主体与能力暴露,`member-service` 管宿主承载,`sandbox` 管隔离边界,`capability-hub` 管能力目录,而 `tools` 负责把这些输入收束成正式工具能力层
- ToolInvocationRequest 不是 runtime action 本体,ToolInvocationResult 不是 raw stdout,ToolPolicy 不是 sandbox 内部细节
- 后续 `03-详细设计.md` 应围绕这 5 个主要部分,继续把 ToolDefinition、Invocation、Policy、Result、Audit/Trace 正式化

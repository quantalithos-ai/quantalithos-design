## 1. 模块职责描述

**本模块做什么**:
- 持有正式 ToolDefinition / ToolContract / ToolInvocationRequest / ToolInvocationResult / ToolPolicy / ToolAuditEntry 真相
- 定义工具调用入口、参数校验、权限边界与结果语义
- 把 runtime/member 的调用收束为受控工具调用,并把结果规范化输出给上游
- 把 governed/restricted tool 调用留痕并输出 metrics / traces / escalated failure 材料

**本模块不做什么**:
- 不持有 `ExecutionInstance` / `CurrentStep` / `MemberRuntimePersona` / `Sandbox` / `CapabilityCatalog` / `Conversation` 真相
- 不等于 runtime 的执行主线,也不等于 member-service 的宿主执行真相
- 不直接承担 UI 消息展示或外部日志系统的存储真相

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 tools“为什么存在”,而是让开发者可以直接开始实现:
- ToolDefinition / ToolContract 如何形成
- ToolInvocationRequest 如何被校验、归一化和执行前检查
- ToolPolicy / ToolScope 如何裁决 allow / deny / governance_required
- ToolInvocationResult 如何与 raw stdout / raw callback 分层
- ToolAuditEntry / metrics / trace / escalated failure 如何正式输出

如果不先把这些内容采集清楚,03 很容易退化成:
- 把 tools 写成脚本清单
- 把调用约束和 sandbox 限制隐含在 adapter 或宿主实现里
- 把 structured result 和 raw log 混成一层
- 把 governance escalation 和普通错误分流写混

#### 第 4 步:列出事件与外部协作点

- 哪些结果输出给 runtime / observability / governance / member
- 哪些调用在 policy 未放行前绝不能执行

#### 第 5 步:列出最小测试输入

必须测:
- ToolDefinition ≠ capability catalog
- ToolInvocationRequest ≠ runtime action
- ToolPolicy / ToolScope 显式存在

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `ToolDefinition / ToolInvocationRequest / ToolPolicy / Result / Audit` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与观测
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是定义/调用/策略/结果/审计,`03` 却只剩一堆 adapter 与 shell 封装
- 实现者知道有 ToolInvocationResult,却不知道它与 raw stdout 和 ToolAuditEntry 的边界归属
- invocation、policy、result、audit 四条链路脱节

### 5.2 `工具定义与契约部分` 的实现要点

#### 5.2.1 该部分承接的概要输入
- 承接 `02` 中“工具定义与契约部分”的职责
- 承接 capability-hub/adapter input → ToolDefinition 主线
- 承接 `ToolDefinition ≠ capability catalog` 这条硬边界

#### 5.2.2 输入 / 输出 / 外部交互图

```text
┌────────────────────────────┐
│ capability-hub / adapters  │
│ - capability graph         │
│ - adapter spec             │
└────────────┬───────────────┘
             │ definition input
             ▼
┌────────────────────────────┐
│ tools                      │
│ - ToolDefinition           │
│ - ToolContract             │
│ - ToolKind                 │
└────────────┬───────────────┘
             │ discoverable tool ability
             ▼
┌────────────────────────────┐
│ runtime / member           │
```

#### 5.2.3 涉及的对象定义

```rust
/// 表示一个正式可被平台调用的工具能力定义。
pub struct ToolDefinition {
    /// 工具唯一标识。
    pub tool_id: ToolId,
    /// 工具类型。
    pub kind: ToolKind,
    /// 工具当前可用性状态。
    pub availability: ToolAvailability,
    /// 工具契约。
    pub contract: ToolContract,
}

/// 表示工具类型。
pub enum ToolKind {
    /// 文件类工具。
    File,
    /// 搜索类工具。
    Search,
    /// 命令类工具。
    Command,
    /// 网络/外部接口类工具。
    Network,
}

/// 表示正式工具调用契约。
pub struct ToolContract {
    /// 参数 schema 摘要。
    pub input_schema: String,
    /// 返回 schema 摘要。
    pub output_schema: String,
    /// 默认 tool scope。
    pub default_scope: ToolScope,
}
```

这些对象在该部分里分别承担:
- `ToolDefinition` 负责定义正式工具能力本体
- `ToolKind` 负责区分工具语义族类
- `ToolContract` 负责把输入/输出/默认 scope 固定为正式契约
- 它们都不替代 capability catalog 本体真相

#### 5.2.4 关键函数代码片段

```rust
/// 把 capability/adapters 输入收束为正式 ToolDefinition。
fn register_tool_definition(
    tool_repo: &dyn ToolDefinitionRepo,
    draft: RegisterToolDraft,
) {
    // [ToolDefinition::从草稿创建]
    // 先把 capability/adapters 输入转成正式工具定义对象。
    let definition = ToolDefinition::from_draft(draft);

    // [definition.校验可注册]
    // 再校验工具类型、契约和默认 scope 是否成立。
    definition.validate_registerable();

    // [tool_repo.保存工具定义]
    // 最后把 ToolDefinition 正式写入真相层。
    tool_repo.save(definition);
}
```

这段实现守住的边界是:
- capability catalog 是输入,不是 ToolDefinition 本体
- ToolContract 必须正式存在,不能只藏在 adapter 内部
- runtime/member 发现的是正式工具能力,不是临时函数列表

#### 5.2.5 该部分的边界与非职责
- 不负责 invocation request 本体
- 不负责 policy 判定逻辑执行
- 不负责宿主执行承载
- 不负责 raw logs/metrics 的消费展示

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `工具调用入口与请求校验部分` 提供正式契约
- 向 `工具权限与策略约束部分` 提供默认 scope 和 governed tool 分类输入
- 向 member 提供 capability exposure 所需的正式工具定义输入

#### 5.2.7 该部分的状态 / 约束 / 易错点
- ToolDefinition 存在不等于当前 member 必须对外暴露它
- ToolContract 缺失时不得允许正式注册
- governed/restricted 工具分类若不显式化,后续 policy 会散进其它层

```rust
/// 表示一次正式工具调用请求。
pub struct ToolInvocationRequest {
    /// 本次调用的唯一标识。
    pub invocation_id: ToolInvocationId,
    /// 要调用的工具引用。
    pub tool_ref: ToolId,
    /// 调用方上下文摘要。
    pub context: InvocationContext,
    /// 原始参数负载。
    pub raw_payload: String,
}

/// 表示调用上下文。
pub struct InvocationContext {
    /// 来自 runtime 的动作引用。
    pub runtime_action_ref: Option<RuntimeActionRef>,
    /// 来自 member 的主体引用。
    pub member_persona_ref: Option<MemberPersonaId>,
    /// 当前 tool scope 快照。
    pub tool_scope_snapshot_ref: Option<ToolScopeSnapshotRef>,
}

/// 表示 preflight 校验结果。
pub struct PreflightValidationResult {
    /// 本次调用是否通过前置校验。
    pub valid: bool,
    /// 失败原因摘要。
    pub reason_summary: Option<String>,
}
```

这些对象在该部分里分别承担:
- `ToolInvocationRequest` 负责把所有正式调用入口统一收束成工具层请求对象
- `InvocationContext` 负责把 runtime/member/current scope 这些上下文显式化
- `PreflightValidationResult` 负责把“能不能继续”在进入 policy 之前写成正式结果

#### 5.3.4 关键函数代码片段

```rust
/// 对一次工具调用请求做参数和上下文层面的正式前置校验。
fn validate_tool_invocation(
    validation_repo: &dyn ValidationRepo,
    request: &ToolInvocationRequest,
    definition: &ToolDefinition,
) {
    // [request.校验参数]
    // 先按 ToolContract 校验参数负载是否满足输入 schema。
    request.validate_against(definition.contract.clone());

    // [request.校验上下文]
    // 再确认当前 caller / runtime/member / scope 快照是否最小完备。
    let result = request.preflight();

    // [validation_repo.保存校验结果]
    // 把本次 preflight 结果正式保存,供后续 policy 和 audit 使用。
    validation_repo.save(result);
}
```

这段实现守住的边界是:
- runtime action 不等于 ToolInvocationRequest
- 参数校验必须依附正式 ToolContract
- preflight 失败时不得继续进入实际执行

#### 5.3.5 该部分的边界与非职责
- 不负责 ToolPolicy 最终裁决
- 不负责 host-side 实际执行
- 不负责 ToolResult 结构化输出
- 不负责审计/观测最终展示层

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `工具定义与契约部分` 获取 ToolDefinition/Contract
- 向 `工具权限与策略约束部分` 提供 validated request
- 向 `工具审计与观测接缝部分` 提供 preflight 结果输入

#### 5.3.7 该部分的状态 / 约束 / 易错点
- 请求校验通过不等于 policy 允许
- context 缺失时不得“猜测”默认 scope
- member-facing request 不得直接绕过 formal invocation request 对象

这些对象在该部分里分别承担:

- `ToolScope` 负责定义当前调用边界
- `PermissionCheckResult` 负责把 allow/deny/governance_required 显式化

#### 5.4.4 关键函数代码片段

```rust
/// 在正式执行前判断当前工具调用是否允许继续。
fn query_tool_policy(
    policy_repo: &dyn ToolPolicyRepo,
    request: &ToolInvocationRequest,
) {
    // [policy_repo.读取工具策略]
    // 先读取该工具在当前调用上下文对应的正式策略。
    let policy = policy_repo.find_for(&request.tool_ref, &request.context);

    // [policy.校验调用范围]
    // 再根据 ToolScope 和 governed/restricted 分类做裁决。
    let result = policy.evaluate(&request.context);

    // [PermissionCheckResult::返回]
    // 把 allow / deny / governance_required 结果显式返回给上游。
    PermissionCheckResult::from_policy(result)
}
```

这段实现守住的边界是:
- policy 决策层必须显式存在
- governed / restricted 分类不应藏在 sandbox 或宿主层内部
- deny / governance_required / allowed 三种结果必须分开

#### 5.4.5 该部分的边界与非职责
- 不负责宿主执行本体
- 不负责 ToolInvocationResult 结构化输出
- 不负责 governance decision 真相
- 不负责 raw logs/metrics 最终观测展示

#### 5.4.6 该部分与其他主要部分的接缝
- 从 `工具调用入口与请求校验部分` 接收 validated request
- 向 `工具执行结果与失败分流部分` 输出 policy-approved 调用
- 向 `工具审计与观测接缝部分` 输出 denied/governed 留痕材料

#### 5.4.7 该部分的状态 / 约束 / 易错点
- governance_required 不等于 denied
- restricted 不等于不可调用,而是需要特定 scope / sandbox 条件
- policy 结果必须可审计,不能只是一句 if 判断

```rust
/// 把宿主层返回的原始结果归一化成正式 ToolInvocationResult。
fn normalize_tool_result(
    result_repo: &dyn ToolResultRepo,
    raw_callback: HostSideToolCallback,
) {
    // [StructuredResult::从原始结果构造]
    // 先把 raw stdout / payload 转成正式结构化结果对象。
    let structured = StructuredResult::from_raw(&raw_callback);

    // [structured.校验结果结构]
    // 再确认结果结构和 ToolContract 的返回语义一致。
    structured.validate_shape();

    // [result_repo.保存正式结果]
    // 最后把 ToolInvocationResult 正式写入真相层。
    result_repo.save(ToolInvocationResult::from_parts(raw_callback, structured));
}
```

- denied / blocked / fatal 必须是不同结果族,不能压成统一 error 字符串

| 错误码 | 含义 | HTTP / RPC 映射 | 恢复策略 |
|---|---|---|---|
| `TOOLS_DEFINITION_INVALID` | 工具定义输入不合法 | 400 | 修正输入 |
| `TOOLS_INVOCATION_INVALID` | 调用请求不合法 | 400 | 修正请求 |
| `TOOLS_POLICY_DENIED` | policy / scope 明确拒绝调用 | 403/409 | 收紧调用 / 终止 |
| `TOOLS_GOVERNANCE_REQUIRED` | 当前调用必须升级治理 | 409 | 等待 governance 决策 |
| `TOOLS_RESULT_INVALID` | structured result 无法构造 | 500/409 | retry / mark failed |
| `TOOLS_AUDIT_WRITE_FAILED` | audit entry 写入失败 | 500/409 | retry audit / alert |

### 7.10 返回值语义分类

| 类别 | 语义 | 处理建议 |
|---|---|---|
| 正常 | definition registered / invocation validated / result normalized | 正常推进 |
| 可恢复异常 | retryable failure / blocked / governance_required | 等待重试或治理 |
| 不可恢复异常 | invalid definition / invalid invocation / denied / fatal result | 返回给上游并阻断当前调用 |

## 11. 运行期主线场景

### 11.1 场景 A · 正常工具调用

```text
runtime/member 发 ToolInvocationRequest
      │
      ▼
validate / preflight
      │
      ▼
policy / scope allow
      │
      ▼
host-side execute
      │
      ▼
normalize structured result
      │
      ▼
runtime consume result
```

**开发者关注点**:
- ToolInvocationRequest 必须正式存在
- raw stdout 不等于 final result
- runtime 消费的是 normalize 后结果,不是宿主原始输出

### 11.2 场景 B · 受限工具被阻断

```text
request hits restricted/governed tool
      │
      ▼
policy / scope check
      │
      ▼
returns blocked / governance_required
      │
      ▼
runtime stops or escalates
```

**开发者关注点**:
- denied / blocked / governance_required 必须明确分层
- 不能在未 allow 前继续 host-side execute
- governed tool 升级是 tools 的正式输出,不是 governance 真相本体

### 11.3 场景 C · 结果写审计并输出观测

```text
ToolInvocationResult formed
      │
      ▼
write ToolAuditEntry
      │
      ▼
publish metrics / trace
      │
      ▼
observability / governance consume material
```

**开发者关注点**:
- audit 失败不能抹除正式结果真相
- metrics / trace 只是观测材料
- structured result / audit / metrics 三者必须可对账

### 11.4 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| capability/adapters input | RegisterToolDefinition | 工具定义与契约部分 | ToolDefinition |
| runtime/member request | ValidateToolInvocation / InvokeTool | 工具调用入口与请求校验部分 + 工具执行结果与失败分流部分 | invocation / result |
| governance/sandbox context | QueryToolPolicy | 工具权限与策略约束部分 | allow / deny / governance_required |
| result/failure | RecordToolAudit | 工具审计与观测接缝部分 | audit / metrics / trace |

### 12.1 先分清写模型 / 读模型 / 证据引用

| ToolAuditEntry | 写模型 / append-only | 是 | 正式留痕 |

### 12.2 关系与索引建议

### 12.3 持久化建议

| 对象 | 存储方式 | 理由 |
|---|---|---|
| ToolDefinition / ToolContract / ToolPolicy | 主表 | 工具能力与约束真相 |
| InvocationRequest / InvocationResult | 主表 | 正式调用与结果真相 |

### 12.4 关键校验

- ToolDefinition 注册前必须校验 contract / scope / kind 最小成立条件

- structured result 构造失败时不得伪装成成功调用
- ToolAuditEntry 写入失败必须单独告警和补偿

## 13. 读模型与投影设计

### 13.1 总体结构

```text
Definition / Invocation / Result / Audit write model
   │
   ▼
projection builders
   ├─ invocation history
   ├─ trace material
   ├─ metrics snapshot
   └─ escalated failure view
```

### 13.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| ToolInvocationHistoryView | request + result + audit | 调用历史浏览 |
| ToolTraceMaterial | request + policy + result | 工具 trace 材料 |
| ToolMetricsSnapshot | result + timing + failure split | 指标快照 |
| EscalatedToolFailureView | blocked / governance_required / fatal | 治理或执行主线可消费失败材料 |

### 13.3 一致性说明

- 读模型允许最终一致
- invocation history / trace / metrics / failure views 都只读
- raw stdout / host callback 只是输入材料,不能直接替代 ToolInvocationResult
- audit / metrics / trace 延迟不得反向影响正式结果真相是否已经成立

## 14. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| ToolDefinition 不完整 | 拒绝注册 |
| invocation request 非法 | 拒绝调用 |
| policy denied / governance required | 不执行,返回正式分支结果 |
| structured result 无法构造 | 标记 result invalid / retryable/fatal |
| ToolAuditEntry 写入失败 | 单独告警并重试,不抹除正式结果 |

### 14.1 重试 / 降级 / 熔断 / 补偿
- sandbox / member-service 短时故障时允许 retryable 结果,但不得沉默失败
- governed tool 未获允许时允许返回 governance_required,而不是直接 fatal
- audit 写入失败允许稍后补写,但不得伪装“已正式留痕”
- structured result 构造失败时必须保留原始输入材料供重放/补偿

### 14.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 工具定义与契约部分 | definition 不完整 / contract 漂移 | definition trace | 拒绝注册 / 修正定义 | replay definition register |
| 工具调用入口与请求校验部分 | request 参数非法 / context 缺失 | invocation trace | 拒绝请求 | replay request after fix |
| 工具权限与策略约束部分 | policy 误判 / governed tool 未升级 | policy trace | deny / governance_required / 修正策略 | replay policy decision |
| 工具执行结果与失败分流部分 | result invalid / raw stdout 假成功 | result normalize trace | 标记 retryable/fatal / 阻断继续 | replay normalize |
| 工具审计与观测接缝部分 | audit 丢失 / metrics 漂移 | audit trace / metrics lag | 重写 audit / 补发 metrics | replay audit |

## 15. 实现红线 / 开发禁止事项

- 不允许把 ToolDefinition 简化成 capability catalog 标签集合
- 不允许把 ToolInvocationRequest 简化成 runtime action 文本
- 不允许把 ToolPolicy / ToolScope 隐含进 sandbox 或宿主执行细节
- 不允许把 ToolInvocationResult 简化成 raw stdout / raw logs
- 不允许把 ToolAuditEntry 完全交给 observability 原始日志替代

## 18. 结论

本详细设计的核心结论是：
- `L2-tools` 的实现必须围绕五个主要部分展开,而不是按脚本、adapter 和调用函数平铺
- ToolDefinition / ToolInvocationRequest / ToolPolicy / ToolInvocationResult 是正式真相或正式调用对象,ToolAuditEntry / metrics / trace 是正式留痕与观测层
- runtime / member / member-service / sandbox / capability-hub / observability 的输入与输出都必须围绕 tools 的正式能力层收口,不能再让原始脚本、stdout 和 host callback 成为事实来源
- 后续测试与验收文档,应直接围绕工具定义、调用边界、结果规范化和审计观测展开

### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 tools 的接口可调用,而是系统验证 `L2-tools` 是否真正满足“正式工具能力仓”的设计要求,尤其要证明以下几点成立:
- ToolDefinition / ToolContract / ToolPolicy / ToolInvocationRequest / ToolInvocationResult 构成正式工具能力真相层
- `ToolDefinition ≠ capability catalog`、`ToolInvocationRequest ≠ runtime action`、`ToolInvocationResult ≠ raw stdout` 三条核心边界必须成立
- governed / restricted tool 调用必须经过明确 policy/scope 裁决,不能靠宿主或 sandbox 细节隐式限制
- structured result、retryable / denied / blocked / fatal 分流必须成立
- ToolAuditEntry 必须独立存在,不能只依赖 observability 原始日志
- runtime / member / member-service / observability / governance 围绕同一正式 tool truth 消费结果,不会漂移成多套语义

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 工具定义与契约部分 | 真相对象 | P0 | ToolDefinition / ToolContract / ToolKind |
| 工具调用入口与请求校验部分 | 调用入口 | P0 | invocation request / preflight / validation |
| 工具权限与策略约束部分 | 策略对象 | P0 | ToolPolicy / ToolScope / governed/restricted split |
| 工具执行结果与失败分流部分 | 结果对象 | P0 | structured result / retryable / denied / blocked / fatal |
| 工具审计与观测接缝部分 | 审计/观测层 | P0 | ToolAuditEntry / trace / metrics / escalated failure |
| sandbox / member-service / capability-hub 内部实现细节 | 非范围 | P2 | 只验 tools 与它们的接缝,不验下游内部实现 |
| UI 展示与聊天表现 | 非范围 | P2 | 只验 member-facing capability consume 和 structured result 输出,不验 UI |
| runtime / member 业务主线正文 | 非范围 | P2 | 只验 tools 与它们的接缝,不验上游业务主线全部细节 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数和局部不变量 | domain / policy owner | `definition.validate_registerable`、`request.validate_against(contract)`、`request.preflight`、`policy.evaluate`、`structured.validate_shape` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + adapter + policy + audit 联动 | backend / domain owner | `RegisterToolDefinition`、`ValidateToolInvocation`、`QueryToolPolicy`、`InvokeTool`、`NormalizeToolResult`、`RecordToolAudit`、`ReplayToolAudit` | 定义、请求、策略、结果、审计链同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | runtime dispatch intent → ToolInvocationRequest、member exposed capability consume → ToolDefinition/Policy、host-side callback → structured result、sandbox restriction → blocked/denied/governance_required、governance consume escalated failure | 输入输出语义一致 |
| 恢复专项测试 | 验证 result / audit / metrics / callback 中断后能否稳定恢复 | architecture / QA | structured result invalid、audit write fail、metrics lag、host callback partial loss、retryable failure replay | 正式结果与留痕链不丢失 |
| 投影一致性测试 | 验证 invocation history / trace / metrics / escalated failure 与正式真相一致 | backend / QA | history rebuild、trace-to-result compare、escalation view rebuild、raw logs 不替代 result/audit | 读模型只读且与真相一致 |
| 端到端主线测试 | 验证最小工具闭环 | QA / owner | register definition → request → validate/policy → execute → normalize → audit/metrics → runtime consume | 主干工具闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| ToolDefinition 与 capability catalog 分层 | capability input → ToolDefinition | 集成测试 | 是 | definition record / compare |
| ToolInvocationRequest 独立于 runtime action | runtime request 进入 tools 后形成正式 request 对象 | 集成测试 | 是 | invocation trace / request record |
| ToolPolicy / ToolScope 显式存在 | governed/restricted 调用都通过显式裁决返回 | 单元 + 集成测试 | 是 | policy decision trace |
| ToolInvocationResult 独立于 raw stdout | raw 输出和 structured result 分层存在 | 集成 + 投影一致性测试 | 是 | result compare / normalize trace |
| ToolAuditEntry 独立存在 | result 成立后必须正式留痕 | 集成测试 | 是 | audit entry record |
| governed/restricted tool 分流成立 | denied / blocked / governance_required / retryable / fatal 正式区分 | 集成 + 事件链测试 | 是 | result_kind compare |
| member-facing capability consume 不越界 | member 看到的只是允许暴露的工具能力 | 事件链 + 边界测试 | 是 | outlet compare |
| host-side callback 不替代 tool result | callback 是输入材料,正式结果仍由 tools 归一化 | 恢复专项测试 | 是 | callback trace / result trace |

| 环境 | 用途 | 依赖 | 关键配置 | 风险 |

## 6. 核心测试场景

| 场景 ID | 场景 | 前置条件 | 步骤摘要 | 预期结果 |
|---|---|---|---|---|
| TC-001 | RegisterToolDefinition 成功注册正式工具定义 | capability/adapter 输入完整 | RegisterToolDefinition | ToolDefinition / ToolContract 建立成功 |
| TC-002 | ToolDefinition 不完整被拒绝 | contract 或 scope 缺失 | RegisterToolDefinition | 返回 `TOOLS_DEFINITION_INVALID` |
| TC-003 | ValidateToolInvocation 成功 | request 参数与 context 合法 | ValidateToolInvocation | preflight 通过 |
| TC-004 | invocation 参数非法被拒绝 | payload 缺失/越界 | ValidateToolInvocation | 返回 `TOOLS_INVOCATION_INVALID` |
| TC-005 | governed tool 返回 governance_required | governed tool + 未获许可 | QueryToolPolicy | 返回 `TOOLS_GOVERNANCE_REQUIRED` |
| TC-006 | restricted tool 在无 sandbox 约束时被 blocked/denied | restricted tool + no sandbox | QueryToolPolicy / InvokeTool | 不进入正式执行 |
| TC-007 | host-side execute 成功后 normalize structured result | allowed request + raw callback | InvokeTool → NormalizeToolResult | ToolInvocationResult 成立 |
| TC-008 | raw stdout 看似成功但 structured result 无效 | raw callback inconsistent | NormalizeToolResult | 返回 invalid/retryable/fatal 分流 |
| TC-009 | ToolAuditEntry 成功写入 | invocation result 已形成 | RecordToolAudit | ToolAuditEntry 正式存在 |
| TC-010 | ToolAuditEntry 写入失败后补偿 | audit write fail | RecordToolAudit retry | result 保留,审计补写成功 |
| TC-011 | invocation history / trace / metrics 重建 | projection 损坏 | ReplayToolAudit / rebuild views | history/trace/metrics 恢复 |
| TC-012 | escalated failure 正式输出给 governance consume | governed/restricted failure | escalation flow | governance consume material 成立 |

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 ToolDefinition / ToolContract,都必须回归 definition register 与 capability input mapping 主线
- 每次改动 request / preflight,都必须回归 invocation validate 与非法参数阻断
- 每次改动 policy / scope,都必须回归 allow/deny/governance_required / restricted 分流
- 每次改动 result normalize,都必须回归 structured result / raw stdout 分层
- 每次改动 audit / trace / metrics,都必须回归 ToolAuditEntry 与观测对账链

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| governed / restricted 分类若后续继续细化 | 测试矩阵需扩充 | TL / 架构 |
| 一个 ToolDefinition 若允许多 adapter 并存 | 结果一致性测试需增加适配器差异样本 | tools + member-service |
| capability-hub 组合能力继续扩张 | ToolContract 派生测试需增加更多组合样本 | Owner / TL |

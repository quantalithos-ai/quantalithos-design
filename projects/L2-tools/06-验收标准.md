### 1.1 验收标准的回答边界

本文必须回答：固定送验范围如何进入、哪些 P0 条件必须成立、什么证据可消费、何时触发一票否决、缺陷如何复验、哪些 residual 可以风险接受，以及如何形成三值结论和签署。

本文不回答：测试如何执行、fixture/CI/runner 如何实现、代码 boundary/commit 如何规划、部署如何操作、外部 owner 是否真实 ready、实际测试是否通过，或真实人员是否批准。这些内容分别归属 `05`、未来 `07`、实现/发布执行和相邻 owner。

### 1.2 证据消费边界

```text
formal 00~04 contracts + formal 05 concrete cases
  -> one fixed ci-test release run
  -> same-run raw cases / suite reports / mandatory checks
  -> evidence-index.json (derivation only)
  -> gate-summary.json (final machine eligibility)
  -> four exact-byte acceptance projections + projection-manifest.json
  -> 06 AC/VF/defect/risk/signoff decision
```

验收只能消费同一 `gate_id=release`、`config_profile=ci-test`、`status=passed` 的 final seal 及其 matching index、manifest、raw/report/check 和四份投影。`EV-CAND-L2T-*`、`evidence-index.json`、draft/fixed Markdown、manifest、review note 或测试计划都不能单独产生 evidence eligibility 或验收结论。

### 1.3 开放上游输入

## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/06_acceptance_step_02_scope.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解验收目标、优先级、接缝范围和 VETO 边界如何收敛。

### 2.1 验收目标

本轮验收要裁决 `L2-tools` 是否在不吞并相邻 owner 的前提下，形成稳定、可消费、可追溯且 body-free 的 runtime 行动契约/工具执行契约：

| 目标 ID | 裁决目标 | 成立方向 | 失败影响 |
|---|---|---|---|
| `OBJ-L2T-ACC-01` | 五能力本地 truth 闭环 | identity/definition -> binding -> invocation -> precondition/handoff -> outcome/audit/safe handoff 的适用链成立 | 核心定位不成立；相关 VF 可触发 |
| `OBJ-L2T-ACC-02` | 17 个核心功能可消费 | `AC-L2T-006~022` 均有正式 protocol/flow/state/result/error 和 eligible evidence | 对应 P0 功能不得通过 |
| `OBJ-L2T-ACC-03` | 外围增强隔离 | 外围缺失不阻塞核心；存在时只读/派生、不反写、不扩权 | isolation failure 是 P0 hard failure |
| `OBJ-L2T-ACC-04` | 规则、数据和 owner 红线 | `AC-L2T-024~033` 成立且所有 VF 未触发 | 架构/安全边界失效 |
| `OBJ-L2T-ACC-05` | 结构性 NFR 与配置安全 | `AC-L2T-034~039`、`NFR-L2T-001~019` 和配置安全 gate 以有来源阈值成立 | correctness/security/evidence 不足 |
| `OBJ-L2T-ACC-06` | 证据与结论可信 | single release seal、exact projection、缺陷/风险/签署和三值裁决无环闭合 | 不可进入或不得形成通过结论 |

### 2.2 范围与优先级

| 验收范围项 | 类型 | 优先级 | 裁决目标 | 非范围 / 说明 |
|---|---|---:|---|---|
| `C-L2T-1~5` 五核心能力 | 核心闭环 | P0 | 五节点共同成立；条件节点按适用 path 裁决 | 不要求每次 invocation 固定穿越所有外仓 |
| `FR-L2T-001~017` / `AC-L2T-006~022` | 核心功能 | P0 | identity、evolution、binding、invocation、precondition、outcome/audit/handoff 正式语义成立 | 不以 fake/provider/health/readiness 替代语义 |
| `FR-L2T-E01~E06` / `AC-L2T-023` | 外围增强隔离 | P0 boundary；feature P1/P2 | absent 不阻塞；present 时 bounded/read-only/no-repair/no-owner-expansion | search/diff/index/diagnostic/SDK/UI 产品完成度不属 P0 |
| `AC-L2T-024~033` | 规则、配置、数据和架构红线 | P0 | owner、write/effect、body/ref、dependency 和 local-truth-first 成立 | 不吸收相邻仓内部 truth |
| 37 个 formal protocol | public contract seam | P0 logical | logical schema、carrier parity、error/state/effect、replay 可裁决 | 不验证物理 endpoint/topic/group/DLQ/cron |
| 六状态族、UoW、幂等和 phase fence | consistency | P0 | 合法迁移、原子副作用、单赢家、exact replay、unknown fence 成立 | 外部 accepted/delivered/observed 不作本地状态 |
| `AC-L2T-034~039` / `NFR-L2T-001~019` | 非功能 | P0 structural | 可用性、安全、追溯、一致性、观测和结构性能成立 | 数字性能、容量、SLO 属 future qualification |
| Hub/Auth/Sandbox/Bus/Obs/Core schema positive | external qualification | P1 conditional | owner contract、profile、source、mapping 和独立 positive evidence 闭合 | 当前开放 blocker 不得被 local fake 关闭 |
| production-like、SDK client、marketplace/provider inventory | product/future | P2/excluded | 未来单独定基线和门禁 | 缺失不影响当前 P0；不得声明 ready |

### 2.3 只验接缝的相邻能力

| 相邻 owner | 本文只验 | 本文明确不验 / 不拥有 |
|---|---|---|
| L2-runtime | canonical invocation/result/error/audit 可消费，carrier 不分叉 | agent loop、LLM planning、runtime orchestration、retry/recovery/checkpoint |
| L3-capability-hub | typed capability ref/snapshot/assessment/gap 和 blocked behavior | registry truth、inventory、visibility truth 或 capability lifecycle |
| authorization owner | requirement 与 formal result consumption 分离，missing/stale/conflict fail closed | effective authorization decision、自有 policy engine、默认 allow |
| L4-sandbox | canonical handoff/source seam、Prepared/one-call/unknown/no-host | isolation/execution/run/capture/receipt/cleanup/DLQ truth |
| L0-bus | body-free semantic material、local attempt、status ref separation | route/topic/delivery/ack/replay store truth |
| L4-observability | safe observation material、independent status、redaction | producer/route/store/readiness 或 Observed truth |
| L0-sdk | future server contract 可消费性和 guidance 不越权 | 现成 tools client、SDK package 反向依赖 |
| provider/marketplace | typed ref/blocked boundary | external MCP/A2A/API registry、provider control、listing/inventory truth |

### 2.4 范围对结论的影响

- `AC-L2T-001~022` 任一适用 P0 failure 都使总体不得“通过”；若命中 VF 或 hard gate，只能“不通过”。
- 外围产品能力未实现不使 `AC-L2T-023` 失败，但外围反写 truth、成为核心前置或扩张 owner 是 P0 hard failure。
- 未纳入 scope manifest 的 P1/P2 缺失不影响 P0；纳入送验 scope 后仍缺 owner/evidence 时，该目标不可通过，只有满足 §13 的 residual 才可能条件化。
- VETO、S、current-P0 A、evidence/config/security/dependency hard gate 不得因“非范围”或 risk acceptance 豁免。

### 3.2 Release seal 准入谓词

```text
release_seal_acceptable :=
  schema and self-digest valid
  AND gate_id = release
  AND config_profile = ci-test
  AND status = passed
  AND run/profile/context are identical across every reference
  AND suite_report_refs cover exactly 11 P0 owning suites
  AND same-run release-local-smoke aggregate is present
  AND check_refs equal the exact 11-check closed set
  AND every report/check digest verifies
  AND same-run evidence_index_ref/digest verifies
  AND evidence_eligibility slot set/order equals the successful index
  AND acceptance_projection_status = published
  AND projection manifest ref/digest verifies
  AND redaction_status = clean
```

seal 的 `status=passed` 只证明 release 测试门禁与 evidence eligibility 完整，是验收的必要条件而非验收结论。06 仍须逐 AC/VF 解释、处理缺陷和 residual，并完成授权审查与签署。

### 3.3 固定证据路径

| 对象 | 固定路径 | 用途 | 禁止替代 |
|---|---|---|---|
| raw root | `artifacts/test/<run_id>/` | machine truth | `artifacts/test/<project>/<run_id>`、临时目录 |
| final seal | `artifacts/test/<run_id>/gate-summary.json` | final eligibility 唯一机器来源 | index item、Markdown summary、health marker |
| pre-check index | `artifacts/test/<run_id>/evidence-index.json` | evidence derivation 和追溯 | final eligibility |
| human reports | `reports/runs/<run_id>/...` | 人工审查与 raw 回链 | 无 raw pairing 的手写报告 |
| acceptance staging | `reports/runs/<run_id>/acceptance-draft/{handoff,veto-checklist,risk-acceptance,open-issues}.md` | pre-seal exact source | verdict、签署或 accepted risk |
| publication manifest | `reports/acceptance/projection-manifest.json` | 四文件 publication marker 和 digest binding | mtime、目录存在、单个 fixed file |
| fixed handoff | `reports/acceptance/handoff.md` | reviewed scope/baseline handoff | oral handoff、unbound draft |
| fixed VETO | `reports/acceptance/veto-checklist.md` | 13 VF review input | 静态全部 passed |
| fixed risk | `reports/acceptance/risk-acceptance.md` | risk proposal/record input | 无 acceptor 的 accepted risk |
| fixed issues | `reports/acceptance/open-issues.md` | blocker/residual/defect input | 隐藏问题清单 |
| review records | `reports/review/reviewer-notes.md`、`reports/review/agent-review.md` | append-only explanation/dispute | machine eligibility rewrite |

### 3.4 Projection snapshot 消费算法

```text
1. Read projection-manifest.json as snapshot M1; verify schema/self-digest.
2. Capture matching seal, index, four staging files and four fixed files.
3. Verify run/index/seal tuple, role order, exact paths, front matter and byte digests.
4. Read manifest again as M2 and require digest(M1) = digest(M2).
5. Use only bytes captured at step 2; do not reopen mutable fixed paths.
6. Any missing, mixed, mismatch or drift invalidates the whole projection;
   never fall back to a prior fixed set.
```

### 3.5 基线漂移规则

| 漂移 | 必须动作 | 旧 evidence |
|---|---|---|
| 正式 `00~06` 内容或 digest 变化 | new design baseline + affected full release run | 只读保留，不提升 |
| implementation source / delivery 变化 | new delivery ref + new release run | 只读保留 |
| config/profile/dataset/blocker snapshot 变化 | new safe digest + new release run | 不跨 run 拼接 |
| suite/check/TC/EV/schema 变化 | 先更新正式 05，再执行新 full release | 旧 schema 不合并 |
| blocker close/reopen | freeze new ledger；先跑受影响 negative；positive 单独 qualification | 旧 blocked 状态保留 |
| defect 修复 | new fixed run + impact-defined regression | 原 failure 不覆盖 |
| reviewer 解释修正 | 同 source tuple append superseding review block | machine seal 不变 |

## 4. 进入条件与退出条件

> 校准来源：
> - `design-calibration/06_acceptance_step_04_entry_exit.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/06_acceptance_step_04_entry_exit.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解 process state、formal entry、暂停分流和退出条件如何收敛。

### 4.1 验收过程状态

| State | 含义 | 允许动作 | 禁止声明 |
|---|---|---|---|
| `not_entered` | baseline/evidence/送验尚未成立 | 补交付、执行 release、修复输入 | pass/fail/signoff |
| `in_review` | entry predicate 成立，正在逐门禁审查 | 只读 captured evidence、追加 review、登记 finding | 改写 seal/index/fixed snapshot |
| `paused` | 出现可恢复的设计、baseline、evidence 或评审缺口 | 回 owning source、new baseline/run | 用旧 tuple 继续裁决 |
| `not_decidable` | required fact/authority 未绑定或冲突 | 记录 blocker 和 reopen evidence | 把 unknown 当 pass/fail |
| `closed` | 全部 exit predicate 成立且有 verdict/signoff | 按 verdict 进入下一阶段 | 原地覆盖；变化须新 instance |

这些是过程状态，不是第四类 verdict。正式 verdict 只允许“通过 / 有条件通过 / 不通过”。

### 4.2 送验前置条件

| ID | 条件 | 检查入口 | 不满足处理 |
|---|---|---|---|
| `ENT-L2T-001` | scope manifest 明确 P0/P1/P2/excluded，无 hidden optional denominator | scope ref/digest | `not_entered` |
| `ENT-L2T-002` | 正式 `00~06` source set immutable 且 digest 可验证 | design baseline | `not_entered`；`L2T-RR-007` |
| `ENT-L2T-003` | implementation source 和 delivery ref 可定位、可重现 | source/delivery baseline | `not_entered`；`L2T-RR-012` |
| `ENT-L2T-004` | `ci-test` config safe digest、dataset manifest、blocked ledger 固定 | run metadata | `not_entered`/invalid |
| `ENT-L2T-005` | release run 展开全部 234 concrete TC，由 11 owning suites 承接且无 hidden filter | context/case manifest | invalid/failed send-off |
| `ENT-L2T-006` | matching release seal 满足 §3.2 | gate-summary parser | 无送验则 `not_entered`；submitted invalid 则不得通过 |
| `ENT-L2T-007` | index/seal/manifest/staged+fixed snapshot 完整且 redaction clean | §3.4 consumer | invalid evidence / pause |
| `ENT-L2T-008` | 无 open S/VF-triggering defect；current-P0 A 已修复并 new run | defect/retest record | block entry |
| `ENT-L2T-009` | acceptance owner、required reviewer 和 risk/signoff authority 可定位 | review contract | `not_decidable` |

```text
formal_entry :=
  ENT-L2T-001..009 all satisfied
  AND every required final evidence slot is eligible or explicitly pending_review
  AND no P0 hard-gate slot is invalid/ineligible/unavailable
  AND captured manifest snapshot remains stable
```

`pending_review` 只允许进入相应人工审查，不使 gate pass。仅 P1 positive unavailable 且未进入 P0 scope 时，可以继续 local P0 review；不得声明该 positive seam ready。

### 4.3 暂停、不可裁决与失败分流

| Trigger | Process handling | Verdict impact | Recovery |
|---|---|---|---|
| formal field/state/protocol 无法定位 | `paused` | 对应 gate 不得通过 | 修正 owning `00~05`；new baseline/run |
| baseline/manifest double-read drift | `paused` | captured snapshot invalid | new baseline/run |

### 8.1 公共一致性 oracle

```text
state_consistency_pass :=
  exact formal state variant and owning flow are used
  AND legal transition commits every named local side effect atomically
  AND illegal/terminal/late transition leaves forbidden effects at zero
  AND duplicate/CAS/append/watermark winner is deterministic
  AND unknown remains unknown until formal resolution or manual action
  AND same-run concrete TC, raw/report pair and final eligibility exist
```

所有 candidate 只是 planned slot，实际资格只来自 matching final seal。后续 Sandbox accepted/run、Bus delivered、Observability observed、Runtime checkpoint 等不属于本地状态机，也不能作为本章通过条件。

### 9.1 共同 NFR oracle

```text
nfr_gate_pass :=
  every applicable structural NFR oracle has eligible same-run evidence
  AND all related mandatory checks pass in the matching release seal
  AND no VF trigger or invalid/missing artifact exists
```

NFS 是专项方法 ID，不是 concrete TC。NFR candidate 必须展开并回指同一 run 的 concrete case、raw/report 和 check，不得生成 synthetic test result。

### 9.3 阈值 authority 与未覆盖分流

| 要求 / 情况 | 当前合法口径 | 禁止结论 |
|---|---|---|
| forbidden body/secret/credential | applicable surfaces 出现数为零；hard P0/VETO | “已脱敏所以 body 可保存” |

## 11. 一票否决项

> 校准来源：

> 延伸阅读：
> - 建议继续阅读 `design-calibration/06_acceptance_step_11_veto.md` 的“一票否决项主表”“检查与证据消费合同”“NC 辅助映射”和“跨 VETO 覆盖审计”小节，了解 13 个 VF 如何逐项停审。

### 11.1 VETO 状态与强制裁决

| 状态 | 含义 | 总体影响 |
|---|---|---|
| `not_triggered` | matching release run 中负向注入被拒绝、发布结构无禁止项，相关 case/suite/check/final eligibility 全部闭合 | 只满足该 VF；不能单独推导总体通过 |
| `triggered` | 实现、配置、依赖图、artifact/report 或交付物包含、接受、持久化、暴露或依赖禁止行为 | 固定为 S；总体强制“不通过”；不可风险接受 |
| `not_evaluated` | 无 matching run，或适用 case/check 未执行 | VF 未闭合；不得“通过/有条件通过” |
| `blocked` | 适用检查因依赖、环境或 authority 缺失不可执行 | 不等于 `not_triggered`；保持不可裁决或 submitted failure |
| `invalid` | artifact/report/digest/redaction/pairing/source tuple 无效 | 证据不可消费；必要时 evidence integrity 自身触发 VF |

负向 fixture 中出现禁止材料不是触发；系统未拒绝/隔离/保持零副作用，或交付物实际包含违规，才是 `triggered`。`not_triggered` 必须来自同一 matching release final seal，不能由“未发现”“未执行”或口头确认推断。

## 12. 缺陷分级、复验与放行规则

> 校准来源：
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/06_acceptance_step_12_defects_retest_release.md` 的“执行状态到分级”“影响清单与复验层级”“关闭状态机”“放行规则”和“停审与跨 Step 审计”小节，了解缺陷与 evidence 状态如何分离。

### 12.1 Authority 与状态分层

case/suite/check status 只描述一次执行；finding 只是一条 safe 异常引用；defect record 才拥有根因、severity、scope、owner、修复与关闭；blocker 表示无法执行/裁决的正式原因；residual 是排除 hard gate 后的剩余影响。`reports/acceptance/open-issues.md` 只是 working projection，不是 defect authority 或放行决定。

| 执行 / evidence 状态 | 是否自动为缺陷 | 当前处理 |
|---|---|---|
| `failed` | 否 | 按 VF/hard invariant/current P0/非 P0 根因分 S/A/B；归类前阻断 gate |
| `blocked_dependency` | 否 | applicable P0 阻断进入/退出；P1/future 可进入 R candidate，绝不计 pass |
| `unavailable` | 否 | expected degraded branch 可通过；执行缺失使对应 gate 不通过 |
| business `unknown` | 否 | 按 formal manual fence 保持可通过；折叠或 blind retry 为 S |
| `not_evaluated/cancelled` | 否 | current P0 未完成，不得通过或条件通过 |
| `invalid_artifact` | 否 | evidence gate 无效；伪造/integrity breach 为 S，harness fault 为 A |
| `pending_review` | 否 | authorized disposition 前不能关闭 AC/VF/defect |

### 12.2 缺陷分级

| 级别 | 定义与典型触发 | 对结论的影响 | 最低复验 | 风险接受 |
|---|---|---|---|---|
| `S` | 任一 VF，或 P0 truth/security/atomicity/dependency/config/evidence hard redline；如 forbidden body、self-auth/no-host bypass、half pair、unknown blind retry、Query write/Job repair、sibling compile、static evidence | open 时总体只能“不通过”；送验前已知则阻断 entry | `RT-L2T-2`；命中全量条件必须 `RT-L2T-3` | 禁止 |
| `A` | current P0 非 VETO semantic failure，或使 P0 evidence 不可裁决的 harness/environment/generator defect | open 时不得通过或有条件通过；阻断下一阶段 | `RT-L2T-2`；shared/integrity 变化升级 `RT-L2T-3` | current P0 禁止 |
| `B` | 已证明不影响 current P0/hard gate 的一般、维护性、P1 或 safe report 可读性问题 | 不计 P0 pass；未关闭时由 §13 判定是否条件化 | `RT-L2T-1` 或影响 suite/check | 可成为 risk candidate |
| `R` | 正式 out-of-scope/future/open-authority residual，非已验证能力 | 不改变 P0；若影响下一阶段必须逐项接受 | owner contract/scope 触发后 new baseline + 新验证 | 可成为 risk candidate |

severity 与 responsibility 分离：即使根因在外部/harness，只要仍影响 current P0，就不能降为 B/R。任何 reclassification 必须 append 旧/新级别、scope/oracle 依据、authorized role 和时间，禁止原地降级绕过 release。

### 12.3 Direct S 与 current-P0 A

| 触发面 | Direct S oracle / 主要 VF | 必须检查 |
|---|---|---|
| 核心/owner | 五节点缺失、第二 identity/definition、相邻 owner takeover；`VF-L2T-001/002/010` | dependency、case manifest |
| Binding/auth | 复制 Hub truth、self-authorize、missing/stale/conflict fail-open；`VF-L2T-003/005` | blocker truth、profile isolation |
| Runtime/invocation | carrier 分叉或吸收 loop/planning/recovery；`VF-L2T-004` | dependency、phase/unknown |
| Sandbox/fact | isolation bypass 或 fabricated run/receipt/delivery；`VF-L2T-005/006` | phase/unknown、blocker、no-static |
| outcome/audit | external source 替 pair、half pair/terminal overwrite；`VF-L2T-007/011` | pair、phase/unknown |
| forbidden material | body leak 或四门不全仍 material/Port；`VF-L2T-008` | redaction、pairing |
| reverse write/recovery | Bus/Obs/SDK/Runtime/Query/Job 反写或 retry/repair；`VF-L2T-009` | query no-write、job boundedness、phase |
| dependency/open seam | sibling compile；pending/future/open=ready；`VF-L2T-010/012` | dependency、blocker、profile、no-static |
| historical/evidence | old contract/metric/signoff 或 candidate/fake/health promoted；`VF-L2T-013` | no-static、pairing、blocker、redaction |
| concurrency/config | second winner/effect、stale overwrite、unknown retry、invalid-high fallback、partial graph、unsafe override | pair、phase、profile、redaction、dependency |

current P0 oracle failure 未命中 S 时为 A；P0 suite/check 因 runner/fixture/Clock/ID/environment/generator 无法可信执行也为 A。正式开放的 P1 positive blocker 可以是 blocker + R candidate，但如果它导致 current local/negative P0 denominator 缺失，则仍阻断 entry/exit，不能裁剪。

### 12.4 Impact manifest 与三级复验

每个 S/A 修复必须在执行前冻结 `retest_impact_manifest`，包含 original finding/defect、formal AC/VF/FR/BR/DR/NFR、original TC、同 family positive/negative/duplicate/no-write/unknown/late 分支、owning/adjacent suites、Store/UoW/Port/entry、checks、candidate slots、config/profile/data、blocker snapshot，以及 full-P0 判定。多个影响面取并集，禁止手工删除失败/blocked case。

| Level | 固定范围 | 可证明 | 不能证明 |
|---|---|---|---|
| `RT-L2T-1` targeted diagnostic | original TC + exact fixture/assertion + owning suite segment | 修复方向、B 局部确认 | S/A closure、release eligibility |
| `RT-L2T-2` affected regression | original TC + family representative + owning/adjacent suites + checks + exact reports | 影响面复验 | 触发 full P0 后的 closure |
| `RT-L2T-3` full P0 release | 11 P0 suites + release-local-smoke + 11 checks + complete seal/index/manifest/projection | formal defect closure、重新进入和放行输入 | external provider/P1 readiness |

S/A 修复即使 RT-2 通过，也必须在同一新 baseline 完成 RT-3 后才能进入正式 06 closure；不得把 RT-1/2 与另一 run 拼成 final eligibility。

以下任一变化强制 RT-3：public field/ref/version/variant/error/carrier；六状态族/terminal；Store/UoW/CAS/pair/idempotency/replay；phase/unknown/one-call；NC/VF/security/redaction；dependency/public export；config root/item/source/profile/V0~V8/B0~B8；Query no-write/Job no-repair；suite/check/artifact/report/evidence schema/derivation；blocker truth；S/P0 A 修复；source/delivery baseline。

### 12.5 修复、关闭与记录

```text
finding recorded
  -> triaged
  -> fix_in_progress
  -> ready_for_retest (new baseline + impact manifest)
  -> retest_running (new fixed run)
  -> retest_failed -> fix_in_progress
  -> retest_passed -> closure_review
  -> closed_fixed
```

`closed_duplicate` 必须指向 canonical defect；`closed_not_defect` 必须证明 expected oracle/错误测试假设并在需要时修正测试后跑 new release；`deferred` 只允许 B/R。

S/A 的 `closed_fixed` 必须同时满足：original failure 只读可定位；根因/formal refs/fix source+delivery/impact manifest 完整；new baseline/run 非 latest 且不混用；original/family/suite/check closed；matching seal passed 且 index/manifest/four projections exact；candidate eligible 且 review 无 dispute；S 对应 VF 在新 run 为 `not_triggered`，A 对应 P0 gate pass；防回归进入 concrete TC/fixture/check；authorized closure record append-only。任何 blocked/unavailable/not-evaluated/cancelled/invalid/pending_review 都不能关闭。

future defect record 至少包含 identity、classification/reclassification、formal impact、failure provenance、fix provenance、retest tuple、closure review 和 regression/risk follow-up；本文当前不创建 defect ID 或填充真实 commit/run。

### 12.6 放行矩阵

| 当前状态 | Formal entry | 通过 | 有条件通过 | 下一阶段 | 必须动作 |
|---|---|---|---|---|---|
| open S 或 triggered VF | 禁止 | 禁止 | 禁止 | 禁止 | fix + RT-3 + VF not_triggered |
| open current-P0 A | 禁止/暂停 | 禁止 | 禁止 | 禁止 | fix harness/product + RT-3 |
| P0 failed/blocked/not-evaluated/cancelled/invalid | 禁止/暂停 | 禁止 | 禁止 | 禁止 | complete matching release chain |
| hard check 非 passed | 禁止 | 禁止 | 禁止 | 禁止 | fix security/dependency/profile/purity/phase/pair/blocker/pairing/no-static |
| S/A closed 但 closure 缺 old/new pairing | 禁止 | 禁止 | 禁止 | 禁止 | 补 provenance；不得人工 waive |
| 仅 open B | 可审查 | 只有关闭/证明无影响且无需接受时 | §13 逐项接受后 | 有条件 | owner/acceptor/deadline/reopen |
| 仅 R/P1/future blocker | local P0 可审查 | 完全不适用且无影响时 | 影响下一阶段时须接受 | 按 condition | 禁止 external readiness claim |
| 无 open defect/residual 且 exit 成立 | 允许 | 候选 | 不需要 | 候选 | §14 final decision/signoff |

放行不由 `gate-summary.json status=passed` 自动输出；它只是验收输入。当前没有真实 defect、closure、run 或放行实例。

### 13.1 风险接受资格

只有排除 current P0 denominator、VETO、S、current-P0 A 和 evidence/config/security/dependency hard gate 后的 B/R residual，才可能支持有条件通过；`eligible_candidate` 仍不等于 `accepted`。

```text
eligible_residual(r) :=
  r.registry_ref in L2T-RR-001..016
  AND r.scope not in current_P0_denominator
  AND r does_not_trigger VF-L2T-001..013
  AND (r.severity in {B,R} OR r is a formal non-defect blocker)

  AND impact/mitigation/owner/acceptor/deadline_or_trigger are non-empty
  AND follow_up_ref/reopen_trigger are resolvable
  AND no secret/raw body/fabricated run/commit/digest exists
```

以下任一条件使记录必须为 `ineligible/blocked`：VF triggered；S/current-P0 A；required slot ineligible/unavailable/invalid/unresolved pending；baseline/source/delivery/seal/manifest mismatch；通过删减 P0、删除 failed case、cross-run、static candidate、health/old report 来“消除”风险；缺 owner/acceptor/deadline/follow-up/reopen；含 forbidden body 或伪造事实；声称仍 open 的 provider/Sandbox/Bus/Obs/SDK readiness 已完成。

### 13.3 风险记录 schema 与接受顺序

| 阶段 | 固定入口 | Authority boundary |
|---|---|---|
| pre-seal proposal | `reports/runs/<run_id>/acceptance-draft/risk-acceptance.md` | 只引用 same-run source/candidate/RR；不能写 accepted/verdict |
| fixed working projection | `reports/acceptance/risk-acceptance.md` | exact-byte review input；无 acceptor 不能支撑 conditional pass |
| risk review block | append to `reports/review/reviewer-notes.md` 或 `agent-review.md` | 记录 inspected/accepted/rejected/deferred/disputed；不回写 seal/index |
| final reference | §14 decision package | 只消费 matching reviewed risk record；signoff 不反推 acceptance |

每行至少包含 `risk_ref`、scope/priority、impact、acceptance_reason、same-run evidence refs、owner role、authorized acceptor role/ref、absolute deadline 或 observable trigger、follow_up_ref、reopen_trigger 和 closed status enum。`not_bound`、`<role>`、空字段或 team 名不能作为 acceptor。

```text
registry -> scope/baseline -> exclude VF/S/P0/hard gate
  -> same-run evidence -> impact/mitigation/owner/acceptor/deadline/reopen
  -> authorized risk review -> §14 conditional decision reference
```

任何一步失败都保持 blocked/review_required。记录 append-only；修正必须新 record 或 supersedes ref。影响实现/测试/运维/上游闭口的 accepted residual 未来必须交接 `07` 或相应运维文档，但本章不创建 implementation ledger 或真实 issue。

## 14. 最终结论与签署

> 校准来源：
> - `design-calibration/06_acceptance_step_14_final_decision_signoff.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/06_acceptance_step_14_final_decision_signoff.md` 的“状态、结论与准入分层”“裁决优先级”“五维结论合同”“签署角色与责任”和“Final decision package”小节，了解三值 verdict 如何形成。

### 14.1 状态、结论与准入分层

| 层 | 允许值 | Authority | 当前值 |
|---|---|---|---|
| process state | `not_entered/in_review/paused/not_decidable/closed` | §4 acceptance process | `not_entered` |
| machine gate status | case/check/seal closed enum | matching raw + gate-summary | no instance |
| function decision | 通过/有条件通过/不通过 | authorized reviewer + captured evidence | `not_formed` |
| nonfunctional decision | 通过/有条件通过/不通过 | authorized reviewer + captured evidence | `not_formed` |
| release-readiness decision | 通过/有条件通过/不通过 | authorized reviewer + final package | `not_formed` |
| overall verdict | 通过/有条件通过/不通过 | acceptance owner + complete package | `none` |
| next-stage disposition | 是/有条件/否 | overall verdict + condition manifest | `not_formed` |
| signoff | six-role append-only records | authorized role assignments | `not_bound` |

禁止“基本通过、原则通过、大体没问题、待补后通过”。完全未送验时保持 `not_entered/none`，不能伪造“不通过”；已进入后有可验证 failure 时必须“不通过”，不能用 `not_decidable` 隐藏。

### 14.2 固定裁决优先级

```text
1. formal entry and stable baseline
2. release evidence integrity and exact denominator
3. VF-L2T-001..013
4. AC-L2T-001..039 and subordinate P0 gates
5. defect severity and retest closure
6. eligible + authorized accepted residuals
7. required signoff and package linkage
8. dimension decisions -> overall verdict -> next-stage disposition
```

| Highest matching condition | Process / dimension handling | Overall verdict eligibility | Next stage |
|---|---|---|---|
| 未送验，required baseline/run absent | `not_entered` | 不形成 verdict | `not_formed` |
| review 中 baseline/manifest drift 或 authority conflict | `paused/not_decidable` | 不形成 final verdict；new baseline/run | 否，直至恢复 |
| 任一 VF triggered | 记录 finding；相关/总体 dimension 不通过 | 只能“不通过” | 否 |
| evidence/config/security/dependency hard gate failed/invalid | release dimension 不通过；相关 AC 不通过 | 只能“不通过” | 否 |
| 任一 applicable P0 failed/unavailable/not-evaluated | 对应 dimension 不通过 | 只能“不通过” | 否 |
| open S/current-P0 A 或 retest closure invalid | 对应 dimension 不通过 | 只能“不通过” | 否 |
| P0/VF/defect/evidence 全闭合，仅有 authorized accepted B/R | 受影响 dimension 可有条件通过 | “有条件通过”候选 | 有条件 |
| 全部 hard/P0/signoff 闭合，无 relevant condition | 各 dimension 通过 | “通过”候选 | 是 |
| required signer/risk acceptor missing | `not_decidable`；不能 closed | 不形成 final verdict | 否 |

### 14.3 五维结论合同

| 维度 | 通过条件 | 有条件通过条件 | 不通过条件 | Authority |
|---|---|---|---|---|
| 功能 | `AC-L2T-001~033` applicable P0 closed pass；37 protocol、六状态族、data/owner/redline 闭合；无 VF/S/P0 A | P0 全 pass，只剩不改 L2 truth 的 accepted B/R/P1 future residual | 任一 function/rule/data/protocol/state gate fail/missing，或相关 VF/S/A | §5~§8、§11~§13 + matching evidence/review |
| 非功能 | `AC-L2T-034~039`、`NFR-L2T-001~019` structural P0 pass；无无 authority number | structural P0 pass，只剩 accepted measurement/capacity/retention/future residual | correctness/security/audit/consistency/observability fail、redaction leak、旧 SLA 伪 pass | §9~§10 + NFR candidate/checks |
| 发布准备 | ENT/EXT、source/delivery、ci-test release seal、30 slot、11 suite+smoke+11 checks、manifest/projection/review/defect closure 全闭合 | hard release gates closed，只剩不影响 P0 的 accepted ops/future residual | source/delivery/denominator/seal/manifest/pairing/redaction/dependency/profile/blocker/no-static/closure/signoff 缺失或失败 | §3~§4、§10~§14 final package |
| 总体 | 三个维度均通过，required signoff 完整，无 relevant condition | P0/hard release 成立，至少一维因 accepted B/R conditional；无 VF/S/P0 A | 任一维不通过、VF、open S/P0 A、hard evidence failure | acceptance owner decision record |
| 进入下一阶段 | overall 通过 -> 是 | overall 有条件通过 -> 有条件，并绑定 condition manifest | overall 不通过 -> 否；无 verdict -> not_formed | overall + immutable conditions |

维度有条件通过不得掩盖本维度 P0 failure。test seal passed 不等验收通过；signoff 也不能覆盖 machine failure。

### 14.4 Condition manifest 与有效期

“有条件通过”必须形成 immutable `condition_manifest_ref`，绑定 accepted risk refs、受影响维度、owner、acceptor、action、deadline/trigger、follow-up、reopen condition、禁止声明和 source decision tuple。条件过期、scope 扩张、owner contract 变化、baseline drift、同类 defect 再现或 evidence 被推翻时，原 next-stage disposition 自动失效并触发新验收，不原地改 verdict。

有条件进入只授权 manifest 明确范围，不授权 production-like、external provider readiness、SDK client、marketplace、Runtime orchestration 或其它 excluded owner 能力。

### 14.5 六类签署责任

| 角色 | 必须确认 | 不得替代 | 当前 assignment |
|---|---|---|---|
| 验收负责人 | baseline/snapshot、precedence、dimension/overall verdict、condition 和完整签署 | test result、逐项 risk acceptance | `not_bound` |
| 产品/领域负责人 | 五能力、scope、功能 AC、业务影响与条件 | architecture owner、eligibility、安全裁决 | `not_bound` |
| 架构负责人 | truth ownership、dependency、protocol/state/data redline、open seam 未伪闭 | test result、delivery source、risk acceptance | `not_bound` |
| 测试/证据负责人 | 234 TC、11 suite+smoke、11 checks、raw/report/seal/manifest、retest | 最终业务 verdict、产品风险接受 | `not_bound` |
| 实现/交付负责人 | implementation source/delivery/config/profile/change scope/reproducibility | test pass、defect closure、risk acceptance | `not_bound` |
| 运维/安全负责人 | redaction/body、isolation/fail-closed、retention/profile/ops residual | provider/Bus/Obs readiness、hard gate waiver | `not_bound` |

同一自然人未来可承担多个角色，但 decision record 必须逐角色记录 responsibility、authority source 和 disposition；不能用一个“同意”省略责任面。本文不虚构姓名或组织分离规则。

每份 signoff 至少包含 opaque `signoff_ref`、exact baseline/run/index/seal/manifest/review `source_tuple`、role/authority_ref、dimension dispositions、明确的 accepted/rejected/not-applicable risk refs、S/A closure refs、RFC3339 `signed_at` 和 append-only supersedes ref。当前这些字段均未绑定。

签署“通过”只表示固定 scope 的 P0/release package 成立，不表示 P1/P2/production/provider/SDK 完成；“有条件通过”不豁免 VF/S/P0 A；“不通过”表示已进入后有可验证阻断，不表示项目终止或旧 failure 可删除；risk acceptance 不改 machine status、不关闭 defect、不替 final signoff。

### 14.6 Final decision package

正式关闭一个验收实例必须形成可回链 package，至少包含：acceptance baseline/scope、implementation source/delivery、captured manifest/seal/index/four projection bytes、per-AC decision、per-VF disposition、evidence gate audit、defect/retest closure、accepted/rejected residual、condition manifest（如适用）、六类 signoff、overall verdict 和 next-stage disposition。

所有 refs 必须属于同一 source tuple 或存在明确 append-only review relation。decision package 不回写 `gate-summary.json`、`evidence-index.json` 或 fixed projection；baseline/scope/delivery 任一变化必须创建新 acceptance instance。

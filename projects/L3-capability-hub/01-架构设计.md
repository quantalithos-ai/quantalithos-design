## 2. 业务背景与驱动力

> 校准来源:
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/01_arch_step_02_goals_constraints.md` 的“架构目标表”“不可变约束表”和“架构非目标表”。

`L3-capability-hub` 需要独立成仓,因为外部 MCP、A2A 和 API 能力会同时被 runtime、tools、governance、method-library、SDK、console 和生态入口引用。如果没有独立的 capability access truth,这些能力事实会散落在运行配置、方法正文、治理缓存、SDK 封装、搜索视图或 marketplace 目录中,最终形成多套不一致的能力接入真相。

### 2.1 架构驱动力

| 驱动力 | 架构含义 |
|---|---|
| 外部能力需要稳定 identity | 目录、描述、治理接缝、方法关系和下游消费都必须围绕同一 capability identity 协作。 |
| registry 需要独立 truth | 正式接入目录不能退化为 allowlist、runtime cache、listing 或搜索结果。 |
| adapter descriptor 需要独立成立 | 外部接入方式、能力类型和边界约束不能被 provider runtime、secret 或 SDK client 反向定义。 |
| governance / method 需要保持接缝而非合仓 | capability-hub 只能承接治理结果和方法关系,不能接管 approval / Policy truth 或方法正文。 |
| formal exposure 需要与 consumer view 分层 | runtime、tools、SDK 和外围入口必须消费同一正式暴露边界,但不能把本地消费表达写回服务端 truth。 |
| 变化与追溯需要可解释 | identity、registry、descriptor、seam、relation 和 exposure 的变化必须可被说明、下游感知和审计回看。 |
| 核心闭环必须与外围增强隔离 | search、export、生态发现、console 和 observability 不能成为核心 capability access truth 成立前置。 |

### 2.2 架构目标

| 架构目标 | 说明 |
|---|---|
| 承载独立 capability access truth | 防止 capability 接入语义被 runtime、SDK、marketplace 或 observability 分叉。 |
| 守住 capability identity、registry 和 descriptor 主轴 | 让正式能力接入事实先于消费、执行或展示语境成立。 |
| 支撑 governance seam 与 body-free method relation | 让治理结果和方法关系可解释,但不迁入相邻仓正文。 |
| 支撑 formal exposure 与 controlled consumer view 分层 | 保护服务端能力边界不被 runtime / tools / SDK / 查询视图反写。 |
| 支撑同步裁定、异步传播和后台派生的分工 | 保护核心 truth 成立语义,同时允许变化传播和派生维护延后完成。 |
| 支撑 traceability、impact 和 handoff 语义 | 让变化、消费影响和交接摘要可被追溯和解释。 |
| 守住依赖裁剪和 forbidden body 边界 | 防止 sibling 源码耦合、秘密正文、治理正文、方法正文和执行正文串仓。 |

## 3. 约束条件

> 校准来源:
> - `design-calibration/01_arch_step_01_requirement_baseline.md`
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/01_arch_step_01_requirement_baseline.md` 的“架构需求基线”和 `design-calibration/01_arch_step_02_goals_constraints.md` 的“不可变约束表”“当前阶段可接受取舍表”。

### 3.1 需求基线约束

| 需求基线结论 | 架构承接方式 |
|---|---|
| `L3-capability-hub` 是外部 MCP / A2A / API capability identity、capability registry 与 adapter descriptor 的能力接入真相仓。 | 架构围绕 identity、registry、descriptor、seam、relation、exposure 组织。 |
| governance approval / Policy truth、method body、SDK client、runtime execution、tool execution、marketplace listing、secret / KMS、cost / billing 不归本仓。 | 架构通过 ref、safe summary、controlled consumer view 或外围只读接缝协作。 |
| `C-CH-1~C-CH-5` 核心闭环必须成立。 | 架构目标必须覆盖 identity、registry、descriptor、governance / method seam 和 formal exposure / change awareness。 |
| `L0-core` 是唯一编译期依赖候选。 | 依赖方向和后续实施计划必须执行依赖裁剪。 |
| 派生视图、搜索、导出、只读生态发现和审计摘要不得反写真相。 | 架构必须区分 truth、snapshot、ref 和 forbidden body。 |
| 旧 `Provider Contract / QueryCapabilities / Cost / KMS / Policy 30s / P95` 口径仅作 historical material。 | 架构可承接结构性问题,不得继承旧对象和旧指标。 |

### 3.2 架构硬约束

| 硬约束 | 影响章节 |
|---|---|
| capability identity 不得被 URL、provider 名、tool config、runtime config、SDK client 或 listing 替代。 | `§4`;`§6`;`§9` |
| registry 不得退化为 allowlist、runtime cache、availability bit、listing 或 search index。 | `§4`;`§6`;`§9` |
| adapter descriptor 不得承载 secret、provider runtime、quota、route、cost、failover、retry truth。 | `§4`;`§9`;`§11` |
| governance seam 只能承接治理结果引用或允许摘要,不得生成 approval / Policy truth。 | `§4`;`§8`;`§9`;`§10` |
| capability-method relation 必须是 body-free relation,不得迁入方法正文。 | `§4`;`§8`;`§9` |
| formal exposure 必须与 controlled consumer view 分层。 | `§4`;`§9`;`§10`;`§12` |
| 除 `L0-core` 外不得形成 sibling 编译期依赖。 | `§8`;`§15` |
| 派生维护、搜索、导出、审计摘要和外围发现不得创造或更正正式接入结论。 | `§7`;`§9`;`§10`;`§13` |

### 3.3 不可变约束

| 约束 | 说明 |
|---|---|
| 不拥有 runtime / tools execution truth | 执行步骤、调用结果、provider lookup 和 allow / deny enforcement 留在执行侧。 |
| 不拥有 governance truth | approval、Policy effective fact、shared_rules 和治理执行状态留在 `L1-governance`。 |
| 不拥有 method body truth | Method Content、TaskDefinition、AIPolicyDef、ProcessTemplateDef 等正文留在 `L3-method-library`。 |
| 不拥有 SDK client truth | client 默认行为、多语言 package、developer experience 留在 `L0-sdk`。 |
| 不拥有 secret / KMS / Vault truth | 只允许 secret ref 和安全 safe summary。 |
| 不拥有 cost / billing / finance truth | provider 原始账单、结算和成本中心不进入本仓。 |
| 不拥有 marketplace listing / transaction truth | 生态入口只能只读消费能力可发现线索。 |
| 不拥有 observability store truth | trace、metric、log、alert、audit store 不得定义 capability access truth。 |
| 不允许 consumer view、search、export、candidate discovery 或 maintenance 反写核心 truth | 这些都只能从正式 truth 派生且可重建。 |

### 3.4 当前阶段可接受取舍

| 取舍 | 当前口径 |
|---|---|
| governance seam 的具体承载字段 | 当前只闭口为 result ref / safe summary / relation 边界,字段后移。 |
| method relation 摘要强度 | 当前只闭口为 body-free relation + method asset ref。 |
| descriptor taxonomy 和协议类别切分 | 当前只闭口“外部 MCP / A2A / API 接入对象 + descriptor truth”,细分后移。 |
| secret safe summary 的最小内容 | 当前只闭口为允许摘要而非 secrets 平台。 |
| formal exposure 到 `L0-sdk` 的 handoff contract | 当前只闭口为服务端 exposure boundary 与 SDK consumer 边界分层。 |
| observability / marketplace / console / finance / KMS 的正式只读接缝 | 当前只保留为外围候选,不阻塞核心闭环。 |
| 量化性能与传播目标 | 当前保留结构性判断,不继承旧 P95 或 `30s`。 |
| DB / cache / broker / protocol / topic / payload / deployment 形态 | 当前不固定,后续文档在不打破边界前提下再闭口。 |

### 3.5 架构非目标

| 非目标 | 不展开原因 |
|---|---|
| runtime execution / tools execution 架构 | 属于 `L2-runtime` / `L2-tools`。 |
| provider runtime / retry / failover / routing / quota 架构 | 属于运行时或 provider adapter 边界。 |
| governance approval / Policy truth 架构 | 属于 `L1-governance`。 |
| method asset definition body 架构 | 属于 `L3-method-library`。 |
| SDK client / package / DX 架构 | 属于 `L0-sdk`。 |
| secret / KMS / Vault 平台架构 | 属于安全基础设施。 |
| cost accounting / billing / finance ledger 架构 | 属于财务或观测边界。 |
| marketplace listing / transaction 架构 | 属于 `L6-marketplace`。 |
| observability 物理存储与审计平台架构 | 属于 `L4-observability`。 |
| API / DTO / 状态机 / 数据库表 / 事件 payload / 部署脚本 | 属于 `02~07` 后续文档。 |

## 4. 职责边界

> 校准来源:
> - `design-calibration/01_arch_step_03_responsibility_boundary.md`
>
> 延伸阅读:
> - 建议继续阅读该文件的“做什么清单”“不做什么清单”“易混淆职责表”和“边界红线清单”。

### 4.1 做 / 不做 / 易混淆清单

| 类型 | 清单 |
|---|---|
| 做 | capability access truth、capability identity、capability registry、adapter descriptor、descriptor risk / constraint summary、governance seam relation、access review responsibility separation、body-free method relation、formal exposure、formal visibility / applicability、traceability / change / impact fact、派生维护 / safe summary 边界 |
| 不做 | runtime execution、tool execution、provider runtime、secret platform、cost / billing、governance approval / Policy truth、method body、SDK client、marketplace listing / transaction、observability store、LLM routing、外部协议正文、UI 状态 |
| 易混淆职责 | external source vs identity;registry vs allowlist / listing;descriptor vs Provider Contract;access review vs governance approval;governance seam vs Policy truth;method relation vs method body;formal exposure vs consumer view;SDK exposure vs SDK client;derived summary vs truth;observability summary vs audit store |

### 4.2 职责边界表

| 职责项 | 类型 | 说明 |
|---|---|---|
| capability identity 语义承载 | 做 | 为外部能力提供稳定主体锚点和身份风险解释语境。 |
| capability registry 承载 | 做 | 为正式能力接入目录、可见性和生命周期语义提供真相源。 |
| adapter descriptor 承载 | 做 | 为接入方式、能力类型、风险和约束摘要提供正式语义。 |
| governance seam relation 承载 | 做 | 承接 capability 与治理结果之间的关系和允许摘要。 |
| access review responsibility separation 承载 | 做 | 保持接入审查事实与 governance approval 的职责分离。 |
| capability-method body-free relation 承载 | 做 | 维护 capability 与 method asset 的无正文关系。 |
| formal exposure 与 formal visibility 承载 | 做 | 为 runtime、tools、SDK 和外围只读消费提供正式能力边界。 |
| traceability / change / impact 承载 | 做 | 为变化、消费影响和交接摘要提供可追溯事实。 |
| 派生维护 / safe summary / 外围只读发现边界承载 | 做 | 支撑 search、browse、export、discovery 和 audit-friendly handoff,但这些都不是 truth。 |
| runtime / tools execution truth | 不做 | 调用结果、执行状态和 provider invocation 正文不归本仓。 |
| governance approval / Policy / shared_rules truth | 不做 | capability-hub 只能承接 seam,不能执行或拥有治理真相。 |
| method asset body / definition source truth | 不做 | 方法正文、模板和定义生命周期不归本仓。 |
| SDK client / package / binding truth | 不做 | capability-hub 只负责服务端暴露边界。 |
| secret / KMS / Vault truth | 不做 | 只允许 secret ref 和安全 safe summary。 |
| marketplace / observability / finance truth | 不做 | 只允许 read-only discovery、audit summary 或事件协作边界。 |

### 4.3 边界红线

- 不得把 runtime / tools execution、allow / deny 拦截、provider lookup 或调用结果写成本仓真相。
- 不得把 governance approval、Policy effective fact、shared_rules 或治理缓存写成本仓真相。
- 不得把 Method Content、TaskDefinition、AIPolicyDef、ProcessTemplateDef 或方法版本正文写入本仓。
- 不得把 SDK client、多语言 package、client cache、binding 或 developer convenience 写入本仓正式边界。
- 不得把 secret 正文、KMS / Vault truth、quota、route、cost、failover、retry 或 provider runtime 写入 descriptor 或其它核心 truth。
- 不得让 consumer view、search、export、candidate discovery、marketplace summary 或 observability summary 反写 identity、registry、descriptor、seam、relation 或 formal exposure。
- 不得让除 `L0-core` 外的 sibling repo 进入编译期依赖。

### 5.1 系统上下文图

```text
+----------------------------+       +----------------------------+
| L0-core / L0-bus          |       | External MCP / A2A / API   |
| shared and event base     |       | capability sources         |
+-------------+--------------+       +--------------+-------------+
              |                                     |
              | 输入 / 依赖                         | 输入 / 依赖
              v                                     v

+----------------------------+   +----------------------------+   +----------------------------+
| L1-governance              |<->| L3-capability-hub          |<->| L3-method-library          |
| governance result seam     |   | capability access truth    |   | method asset relation      |
+----------------------------+   +-------------+--------------+   +----------------------------+
                                                |
                                                | 输出
                                                v
                         +----------------------+----------------------+
                         |                                             |
                         v                                             v
              +----------+-------------+                 +-------------+----------+
              | L2-runtime / L2-tools  |                 | L0-sdk                |
              | execution consumers    |                 | SDK exposure consumer |
              +------------------------+                 +-----------------------+
```

图示说明:

- `L3-capability-hub` 位于外部能力来源、governance、method-library 和下游执行 / SDK 消费之间,中心职责是 capability access truth。
- `L0-core / L0-bus` 提供共享契约和事件协作基础,不是本仓业务 truth 的替代来源。
- 外部 MCP / A2A / API 只作为接入对象来源进入本仓,不代表本仓负责外部调用执行。
- `L1-governance` 和 `L3-method-library` 通过 seam / relation 协作,不发生 truth 合仓。
- `L2-runtime`、`L2-tools` 和 `L0-sdk` 消费本仓正式暴露边界,但不得反向定义本仓 truth。

| 外部 MCP / A2A / API 来源 | 外部对象不可访问或语境不足 | 新建 / 更新 identity、registry、descriptor 时保持候选、草稿或 unresolved,不得补造正式能力事实。 |
| `L1-governance` | governance result ref 或 safe summary 不可解析 | 依赖治理结果的 formal exposure / visibility 进入 pending 或 unresolved,不得由 access review、本地目录状态或缓存替代。 |
| `L3-method-library` | method asset ref 不可解析 | relation 变更或读取挂起,不得复制 method body。 |
| `L2-runtime` / `L2-tools` | 下游消费不可用 | 只影响消费和反馈,不得改变本仓 formal exposure、registry 或 descriptor truth。 |
| `L0-sdk` | SDK 封装不可用 | 服务端 exposure boundary 仍归本仓,不得由 SDK client 反向定义。 |
| `L5-console` / `L6-marketplace` / `L4-observability` | 外围入口或审计消费不可用 | 只影响外围体验和只读输出,不阻塞核心闭环。 |

### 5.4 边界说明

`L3-capability-hub` 的系统上下文围绕“外部能力来源输入、基础契约与事件协作、治理 / 方法关系接缝、下游正式消费”四类关系展开。secret / KMS / Vault、finance / billing、external provider runtime、PostgreSQL、cache、outbox 和旧 `Provider Contract / Cost / QueryCapabilities` 只作为历史冲突或后续技术候选,不构成当前系统上下文主语。

|---|---|---|

### 7.3 部署关系说明

本章只固定逻辑运行承载结构,不固定部署平台、进程边界、存储产品或消息产品。`同步入口承载`、`异步协作承载` 和 `后台维护与派生承载` 在早期可以同部署,但架构上必须保持逻辑可分,以便分别处理同步入口压力、外部变化输入失败、派生重建、消费快照维护和审计摘要交接。

`access truth 承载` 与 `受控消费 / 追溯派生承载` 即使物理同库也必须语义分离。PostgreSQL、cache、search backend、outbox、KMS / Vault、provider adapter 等产品级设施均后移到后续文档闭口。

| 关联项目 | 依赖类型 | 当前角色 | 裁剪结论 |
|---|---|---|---|

| `L0-bus` | 事件协作 | 协作方 | 只做能力接入事实变化协作,不得写成业务源码依赖。 |
| 外部 MCP / A2A / API | 运行期 | 依赖方 | 只作为接入对象来源和 descriptor 目标。 |

### 8.4 依赖倒置边界

| 需要倒置的依赖 | 倒置方式 | 保护目标 |
|---|---|---|
| 外部 MCP / A2A / API 来源 | 只通过 external source ref、接入对象语境和 descriptor 摘要进入正式承接角色。 | 防止 provider runtime、外部协议正文和调用结果进入核心。 |
| `L1-governance` result | 只保存 governance result ref、policy result ref、allowed safe summary 或 seam relation。 | 防止 approval / Policy / shared_rules truth 入仓。 |
| `L3-method-library` method asset | 只保存 method asset ref 和 body-free relation。 | 防止 method body 和 definition source truth 串仓。 |
| `L2-runtime` / `L2-tools` 消费需求 | 下游只消费 formal exposure、controlled consumer view、descriptor 摘要和变化感知。 | 防止 execution truth 或 consumer cache 反写核心。 |
| `L0-sdk` official exposure | SDK 通过服务端 exposure boundary 封装能力。 | 防止 SDK client / package 反向定义服务端 truth。 |
| `L0-bus` 事件协作 | 只承接 access fact 变化输出和外部变化输入。 | 防止 topic / payload / outbox 定义业务语义。 |
| `L5-console` / `L6-marketplace` / `L4-observability` | 只允许只读管理、只读发现或 audit-safe handoff。 | 防止 UI、listing、audit store 成为第二 truth。 |

### 8.5 禁止依赖

- `L3-capability-hub -> L2-runtime / L2-tools` 的源码级业务依赖。
- `L3-capability-hub -> L1-governance` 的 approval execution / Policy client 依赖。
- `L3-capability-hub -> L3-method-library` 的正文 / 源码依赖。
- `L3-capability-hub -> L0-sdk` 的编译期或客户端实现依赖。
- `L3-capability-hub -> finance / billing / raw provider billing` 的 truth 依赖。
- `L3-capability-hub -> L6-marketplace` listing / transaction 依赖。
- 派生消费辅助角色或技术承载角色反写核心语义角色。

## 9. 数据所有权与一致性策略

> 延伸阅读:

### 9.1 数据类型与归属

| 数据类型 | 本仓内容 |
|---|---|
| 正式真相数据 | capability identity、registry entry、registry visibility / lifecycle semantics、adapter descriptor、descriptor risk / constraint summary、governance seam relation、access review responsibility separation fact、capability-method body-free relation、formal exposure boundary、formal visibility / applicability、capability access traceability record、capability change / consumer impact fact |
| 快照 / 投影数据 | governance safe summary、secret handling safe summary、directory search / browse summary、exported capability access summary、controlled consumer view、downstream consumption impact summary、candidate discovery summary、read-only ecosystem discovery summary、observability / audit safe summary |
| 引用关系数据 | external capability source ref、governance result / policy result ref、method asset ref、secret ref、runtime / tools consumer ref、SDK exposure consumer ref、observability / audit ref、external standard / protocol / document ref、marketplace ecosystem object ref |
| 明确不拥有的正文 / 真相 | provider secret、KMS / Vault truth、runtime / tools execution、provider runtime、quota、route、failover、retry、cost / billing、governance approval / Policy / shared_rules、method body、SDK client、marketplace listing / transaction、observability store、production payload、LLM routing |

### 9.2 一致性策略

| 一致性对象 | 一致性口径 |
|---|---|
| 本仓正式 truth 内部关系 | 强一致 |
| 正式 truth 到派生 view / search / export / consumer summary | 最终一致 |
| 正式 truth 到外部对象 | 引用有效性一致 |
| forbidden body 出现时 | 边界约束一致,只能拒绝、挂起或转化为 ref / allowed safe summary |

### 9.3 数据边界说明

- capability-hub 只拥有 capability access truth,不拥有相邻仓主体 truth。
- controlled consumer view、search / browse、export、audit-friendly summary、SDK 说明摘要和生态发现摘要都只是 projection,可重建且可滞后。
- governance、method-library、secret、runtime / tools、SDK、marketplace、observability 和 external document 在本仓都只能以 ref 或允许的 safe summary 承接。
- `CapabilityDecision-style summary` 只允许作为 consumer view 类快照,不得被误写为 formal exposure truth。

### 9.4 数据红线

- 不得把 provider key、token、password、private key、KMS / Vault truth 写入本仓。
- 不得把 approval、Policy、shared_rules、Method Content、TaskDefinition、AIPolicyDef、runtime execution、tool result、SDK client、listing / transaction、audit store 写入本仓。
- 不得让 projection / cache / search / export / discovery 更正 identity、registry、descriptor、seam、relation 或 formal exposure。

### 10.1 关键交互场景表

| 交互场景 | 通信方式 | 交互目的 | 边界约束 | 失败口径 |
|---|---|---|---|---|
| 外部能力接入语境建立与 identity 建立 / 调整 | 同步请求 / 响应类交互 | 形成或调整 capability identity truth | 不引入 provider runtime、URL 或临时配置作为 truth | pending / unresolved / rejected |
| registry 纳入 / 退出 / 可见性变化 | 同步请求 / 响应类交互 | 形成正式 registry fact | 不退化为 allowlist、cache 或 listing | accepted / rejected / pending |
| adapter descriptor 建立 / 替换 | 同步请求 / 响应类交互 | 形成 descriptor truth | 不承接 secret、provider runtime、quota、route、cost truth | accepted / rejected / unresolved |
| governance seam 挂接 / 失效与 access review 分离 | 同步请求 / 响应类交互 | 收口治理结果关系和审查事实 | 不生成 approval / Policy truth | pending / unresolved / forbidden |

| formal exposure / formal visibility 成立或调整 | 同步请求 / 响应类交互 | 形成服务端正式暴露边界 | consumer view、SDK client、runtime query 不得反写 | accepted / pending / unavailable |
| 正式 truth 读取 | 同步请求 / 响应类交互 | 读取 identity、registry、descriptor、seam、relation、exposure truth | 只读路径不得隐式更正 truth | not_found / unresolved / unavailable |
| controlled consumer view 读取 | 同步请求 / 响应类交互 | 向 runtime、tools、SDK 或目录浏览提供受控快照 | consumer view 只能来自 formal truth 派生 | stale / rebuilding / unavailable |
| capability access fact 变化传播 | 异步事件 / 回调类交互 | 向下游传播已成立事实和变化上下文 | 不传播 governance truth、method body、secret 或 production payload 正文 | delayed / stale / pending_delivery |
| 外部治理 / 方法 / 来源结果送达 | 异步事件 / 回调类交互 | 承接外部结果或变化线索 | 只承接 ref、safe summary 或变化上下文 | unresolved / retry_later / pending |
| 下游消费影响回报 | 异步事件 / 回调类交互 | 回收 consumer impact 线索 | 不把下游执行状态写回核心 truth | partial / delayed / ignored |
| registry maintenance / reconciliation | 后台任务 / 延后承接类交互 | 派生维护、一致性检查和目录修复 | 维护不得创造新业务结论 | stale / rebuilding / unavailable |
| consumer view / search / browse / export 派生维护 | 后台任务 / 延后承接类交互 | 维护只读消费快照和导出摘要 | projection 不得反写真相 | stale / rebuilding / unavailable |
| 外围发现 / observability / audit / external document handoff | 后台任务 / 延后承接类交互 | 形成只读生态摘要和 audit-friendly handoff | handoff 只能输出摘要或 ref | delayed / partial / unavailable |
| secret ref / safe summary 承接与刷新 | 后台任务 / 延后承接类交互 | 刷新 secret handling safe summary 或敏感边界说明 | secret 正文永远 forbidden | unresolved / unavailable |

### 10.2 通信方式判断

| 通信类别 | 使用场景 | 采用原因 | 不在本章展开 |
|---|---|---|---|
| 同步请求 / 响应类交互 | 核心 truth 读取与裁定 | 调用方需要即时获得正式结果、失败、挂起或不可见口径 | API path、DTO、transport、repository、handler |
| 异步事件 / 回调类交互 | 已成立事实传播、外部结果送达、下游影响回报 | 交互主体是“已成立事实”或“外部变化线索”,不应阻塞核心 truth 成立 | event name、topic、payload、outbox、consumer group |
| 后台任务 / 延后承接类交互 | 派生维护、对账、搜索、导出、discovery、handoff、引用刷新 | 这些都服务最终一致和派生收敛,不应阻塞核心 truth 成立 | job name、调度、重试、补偿算法、projection schema |

### 10.3 失败与降级口径

- 核心 truth 的同步裁定失败,只能返回 failed / rejected / pending / unresolved,不能伪装为成功。
- 外部结果缺失或引用不可解析时,保持 pending、unresolved、unknown 或 unavailable,不得补造相邻 truth。
- 派生、搜索、导出、consumer view、audit summary 或 ecosystem discovery 失败时,保留已成立 truth,并显式标记 stale、rebuilding、partial 或 unavailable。
- 下游消费失败不回滚本仓正式 truth;外围 handoff 失败也不否定已成立的 capability access fact。

| governance seam 与 body-free method relation | 只保留能力边界所需关系与允许摘要 | 防止 governance truth 和 method body 入仓 |
| ref / safe summary 优先 | 相邻系统优先以引用或安全摘要协作 | 防止复制外部正文 |
| traceability / impact / handoff 可解释 | 对变化、消费影响和交接摘要保留可解释语义 | 支撑审计、复盘和后续测试 |
| 逻辑可分运行承载 | 同步入口、异步协作、truth 承载和派生承载可逻辑分离 | 支撑后续容量、隔离和恢复扩展 |

## 12. 备选方案与取舍

> 校准来源:
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读:
> - 建议继续阅读该文件的“当前主线方案”“方案路径比较表”“轻量取舍对照表”和“方案边界说明”。

### 12.1 当前主线

当前采用的主线是:

```text
独立 capability access truth
  -> 正式承接边界隔离外部输入
  -> identity / registry / descriptor / seam / relation / exposure 作为核心 truth
  -> ref / safe summary / body-free relation 承接相邻系统
  -> formal exposure 与 controlled consumer view 分层
  -> 核心同步裁定
  -> 已成立事实异步传播
  -> 派生 / 对账 / 导出 / handoff 后台承接
  -> 核心闭环与外围增强隔离
```

### 12.2 方案路径比较

| 方案路径 | 优点 | 致命问题 | 结论 |
|---|---|---|---|
| 独立 capability access truth 与分层承接方案 | truth owner 清楚、依赖可裁剪、正文可隔离、后续可落码 | 需要接受 ref / summary / async / background 的边界复杂度 | 采用 |
| runtime / tools execution gateway 主导 | 看起来集中、易于把接入和调用放一起 | execution truth 会吞没 registry / descriptor / exposure 边界 | 不采用 |
| Provider Contract / provider platform 主导 | 容易承接 provider 配置 | 会把 secret、quota、route、cost、failover、retry、runtime 全带回本仓 | 不采用 |
| governance approval / Policy truth 主导 | 看起来能统一安全约束 | governance truth 会吞没 capability access truth | 不采用 |
| method-library definition 合并 | 关系和定义看似更近 | 会把 method body 和 capability access truth 混成一仓 | 不采用 |
| SDK client / gateway-first 主导 | 便于客户端体验 | 会让服务端 capability exposure 被客户端封装反向定义 | 不采用 |
| marketplace listing / ecosystem directory 主导 | 便于发现和展示 | listing / transaction 会覆盖正式 registry truth | 不采用 |
| QueryCapabilities / consumer view 主导 | 便于查询消费 | consumer view 会变成第二 truth,formal exposure 失守 | 不采用 |
| 全同步端到端闭环 | 形式上确定性强 | 外围传播、审计和发现会拖垮核心裁定链路 | 不采用 |
| 全异步事件化 access truth | 看起来松耦合 | 正式成立口径消失,容易伪成功 | 不采用 |

### 12.3 取舍结论

当前方案牺牲了“所有信息都本地拥有”和“所有路径都即时完成”的表面完整性,换来以下确定性:

- capability access truth 的唯一性。
- governance、method-library、runtime / tools、SDK、marketplace、observability 的边界清晰。
- forbidden body 可被长期审计。
- formal exposure 不被 consumer view、SDK wrapper 或查询层反写。
- 后续 `02~07` 可以围绕现有边界继续细化,而不是重新选边。

## 1. 业务背景与驱动力

### 1.1 业务背景

Quantalithos 的 AI 成员不应直接触碰外部能力。所有外部 MCP Server、A2A Node、LLM Provider 都应通过一个**统一、受控、可审计的能力入口**暴露给 runtime / tools。

capability-hub 解决的是:
- 允许哪些能力被调用
- 调用某个能力前需要哪些 Policy 约束
- provider 的 key / quota / cost 怎么管
- 第三方能力接入如何审计

### 1.2 业务驱动力

**业务驱动力**:
- 平台要安全使用第三方能力,不能让 runtime 自行到处配置 key
- 企业客户需要看到成本、额度和白名单边界
- MCP / A2A / Provider 会持续增长,必须有统一接入层

**技术驱动力**:
- governance Policy 下发
- runtime 高频 QueryCapabilities
- audit / cost accounting / KMS 集成

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 安全 | 未白名单调用拦截率 | 100% | 安全测试 |
| 安全 | 明文 key 落盘次数 | 0 | grep / 测试 |
| 性能 | QueryCapabilities P95 | < 50ms | benchmark |
| 延迟 | Policy 刷新生效 | < 30s | 集成测试 |
| 审计 | cost record 覆盖率 | 100% 外部调用 | 回归测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| 未白名单 MCP Server 必拒绝 | README 安全条目 | deny-by-default |
| A2A Node 注册必须认证 | CH2 | 不允许匿名 |
| Provider key 不落盘明文 | CH3 | 必须集成 KMS/Vault |
| Policy 可动态刷新白名单 | CH4 | QueryCapabilities 不能静态写死 |
| 外部调用必须发成本记账事件 | CH5 | 成本记录不可省略 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| LLM routing | 可选后置 | 可拆独立服务 |
| A2A 认证方式 | 未定 | 证书 / token / DID |
| 成本粒度 | 未定 | 请求级 / token 级 / 时间窗 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| MCP Server 数 | < 500 | 企业规模预估 |
| Provider Contract | < 100 | 主流供应商 + 自建模型 |
| QueryCapabilities QPS | 高频(runtime 路径) | <50ms 目标 |
| cost records/day | 高 | 每次外部调用都记账 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| MCP/A2A 协议演进 | 中高 | 适配器层隔离 |
| provider 种类增加 | 中 | Contract 抽象 |
| governance Policy 变化 | 高频 | 动态刷新 |
| 成本模型变化 | 中 | CostRecord 抽象 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **统一 Registry + Contract + Policy-aware query**(当前)| 安全边界集中,审计清晰 | 模型较多 | ✅ |
| 各 runtime 自己配外部能力 | 实现快 | 安全与审计失控 | ❌ |
| 只做 provider registry,不做 MCP/A2A | 简化 | 无法承载更广能力池 | ❌ |

**最终选择**:**Registry / Directory / Contract / Accounting 四子域集中在一仓**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| deny-by-default | 安全边界强 | 接入流程更重 |
| key 必过 KMS/Vault | 合规 | 接入复杂 |
| cost record 必发 | 成本透明 | 存储量增加 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
runtime / tools / external developers
              │
              ▼
       ★ quantalithos-capability-hub ★
       - MCP Registry
       - A2A Directory
       - Provider Contract
       - Cost Accounting
              │
   ┌──────────┼──────────────┬──────────────┬──────────────┐
   ▼          ▼              ▼              ▼              ▼
 governance  runtime/tools   providers       KMS/Vault     marketplace
 policy      query + use     Anthropic etc   key mgmt      metadata publish
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ MCP Registry
- ✅ A2A Directory
- ✅ Provider Contract
- ✅ QueryCapabilities
- ✅ Cost Accounting
- ✅ governance Policy 消费

**不做什么**:
- ❌ 真正执行外部 tool 调用(runtime/tools)
- ❌ 持有业务对话 / 业务流程语义
- ❌ 变成完整 KMS/Vault 产品
- ❌ 替代 Marketplace 交易逻辑

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| KMS/Vault | 99.9% | 管理操作阻断,不降级明文 |
| provider API | 99.9% | provider failover / retry |
| governance | 99.9% | last-known-good capability cache |
| bus | 99.95% | backlog / replay |

### 4.4 关键依赖风险

- runtime 绕过 hub 直连外部能力
- Policy 刷新滞后导致白名单不一致
- key 管理错误造成严重泄露

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Capability Registry | 核心域 | 能力目录 |
| Provider Contract | 核心域 | 模型/API 合同 |
| Cost Accounting | 支撑子域 | 外部调用成本 |
| Access Decision | 支撑子域 | QueryCapabilities / whitelist |

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| MCP Registry | MCP servers | MCPServer |
| A2A Directory | A2A nodes | A2ANode |
| Provider Contract | LLM/API provider | ProviderContract |
| Cost | external cost records | CostRecord |

### 5.3 上下文映射关系

- governance → Access / Registry(policy.updated)
- runtime/tools ← Access(QueryCapabilities)
- marketplace ↔ MCP Registry(metadata)

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |

| ProviderContract | LLM/API 提供商配置 | Contract |
| CapabilityDecision | 当前可用能力集合 | Access |
| CostRecord | 单次或聚合成本记账 | Cost |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
runtime / tools / admins
        │
        ▼
capability-hub-api
   ├─ registry services
   ├─ provider services
   ├─ access decision service
   ├─ cost accounting
   └─ subscriptions(governance)
        │
        ├─▶ PostgreSQL
        ├─▶ KMS/Vault
        ├─▶ bus(outbox)
        └─▶ external providers / MCP / A2A nodes
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| hub-api | RPC/HTTP 入口 | Rust |
| registry service | MCP / A2A 管理 | Rust |
| provider service | provider contracts + key mgmt | Rust |
| access service | QueryCapabilities | Rust |
| cost worker | 成本聚合 / 事件发出 | Rust |
| postgres | registry/contracts/cost/outbox | PostgreSQL |
| KMS/Vault | key envelope encryption | 外部系统 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| runtime 查询能力 | RPC | 高频读,结构化 |
| governance 刷新白名单 | 事件 | 最终一致 + 重放 |
| provider 调用 | runtime/tools 发起,hub 提供 contract | 职责分离 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| mcp_servers | capability-hub | runtime / admins |
| a2a_nodes | capability-hub | runtime / admins |
| provider_contracts | capability-hub | runtime / admins |
| cost_records | capability-hub | admins / finance / audit |
| outbox | capability-hub | outbox worker |

### 6.5 部署拓扑

- 单服务 + PG + KMS/Vault 起步
- QueryCapabilities 高频读可加 cache
- cost worker 可内嵌或独立

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api
 │
 ▼
application
 │
 ▼
domain(Registry / Contract / Access / Cost)
 ▲
 │ ports
infra(Postgres / KMS/Vault / bus / external protocol adapters)
```

### 7.2 层间约束规则

- domain 不直接持有明文 key
- access decision 不直接调外部 provider,只给出 allow/deny + contract view
- registry 和 cost 分层,查询能力不带写成本副作用
- subscriptions 只消费治理事件,不做业务逻辑判断

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| SecretStore | application/domain | KMS/Vault adapter |
| ProviderRegistry | domain | postgres |
| CapabilityQuery | application | access service |
| CostSink | application | cost worker / outbox |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(runtime/tools/admins/governance) |
| 传出耦合 | 高(KMS/Vault + providers + bus + pg) |
| 不稳定性 | 中高 |
| 抽象度 | 中 |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| MCPServer registry | capability-hub | runtime / tools | 强一致 |
| A2ANode directory | capability-hub | runtime / tools | 强一致 |
| ProviderContract | capability-hub | runtime / tools | 强一致 |
| CapabilityDecision cache | capability-hub | runtime / tools | 最终一致(policy refresh) |
| CostRecord | capability-hub | admins / audit | append-only |

### 8.2 一致性层次

- Registry / Directory / ProviderContract 聚合内强一致
- governance Policy 刷新到 CapabilityDecision 最终一致
- CostRecord append-only,与外部 provider 调用日志最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| Policy 更新未及时生效 | last-known-good + replay |
| provider 调用成功但成本记录失败 | retry + backlog |
| key rotate 失败 | 保留旧 key 不切换 |

## 9. 关键技术选型

### 9.1 Rust + PostgreSQL + KMS/Vault

| 维度 | 内容 |
|---|---|
| 当前选择 | Rust + PostgreSQL + 外部 KMS/Vault |
| 备选方案 | Go + pg / 自研加密 |
| 选择理由 | 类型安全 + 不自造密钥系统 |
| 演进路径 | 可切云 KMS |
| 不可逆程度 | 中高 |

### 9.2 QueryCapabilities 模型

| 维度 | 内容 |
|---|---|
| 当前选择 | 预计算 / 查询时求值混合 |
| 备选方案 | 每次全量现算 |
| 选择理由 | 兼顾性能与简单性 |
| 演进路径 | 高频场景引入 cache |
| 不可逆程度 | 中 |

### 9.3 Cost Accounting 粒度

| 维度 | 内容 |
|---|---|
| 当前选择 | 先请求级记录 |
| 备选方案 | token 级 / 时间窗聚合 |
| 选择理由 | 起步简单,审计可接受 |
| 演进路径 | 后续细化到 token 级 |
| 不可逆程度 | 低 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| LLM routing 是否本仓内建未定 | 影响 scope | P1 |
| A2A 认证方式未定 | 影响目录模型 | P1 |
| 成本粒度未定 | 影响财务分析 | P2 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| QueryCapabilities P95 > 50ms | 持续 1 周 | 引入 cache / 预计算 |
| denied calls > 100/day | 1 周 | 调整 allowlist / docs |
| provider failover 需求 > 2 个稳定场景 | 1 Sprint | 设计 failover 模块 |

### 12.3 演进步骤

```
阶段 1: MCP Registry + Provider Contract + QueryCapabilities
阶段 2: Cost Accounting + Audit
阶段 3: A2A Directory
阶段 4: LLM routing / advanced provider orchestration
```

### 12.4 目标架构

capability-hub 的目标是:
- 成为所有外部能力的统一入口
- 把“能不能用、花了多少钱、凭什么能用”三件事锁在一个仓里
- 让 runtime 不再直接持有 provider / tool 的敏感配置

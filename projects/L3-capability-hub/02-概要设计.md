## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L3-capability-hub` 不是工具执行仓,也不是 provider 本体仓,更不是单纯配置中心。它是 **“能力接入中心”**。

你可以把它理解成:
- 平台当前正式允许接入哪些外部能力
- 哪些 MCP Server、A2A Node、LLM/API Provider 可以被 runtime / tools 看见和使用
- 某个能力在当前 role / project / shared_rules / policy 下能不能被访问
- provider 的 key / quota / cost 规则怎样被统一管理
- 外部能力调用怎样被审计、记账和治理

这些事情,都由 `L3-capability-hub` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L3-capability-hub`,这些能力接入事实就会散落在:
- `runtime` 自己维护的 provider 配置里
- `tools` 自己拼装的 MCP / A2A 连接参数里
- 各个环境里的本地 key / token 文件里
- governance 自己维护的一套 whitelist 规则里
- audit / finance 各自补做的调用记账里

结果就会出现:
- 外部能力接入边界碎裂,不同调用方看到不同能力集合
- runtime / tools 容易直接持有 key 和 provider 细节,安全边界失控
- whitelist、quota、policy、cost 各自一套口径,下游无法对账
- capability marketplace 只知道挂了什么元数据,却不知道这些能力是否真的可用、是否被允许
- 未白名单能力的拦截、成本留痕和审计告警都无法收口到一个统一主链里

所以 `L3-capability-hub` 必须独立存在,作为:
> **平台访问外部能力的统一受控入口、可见性裁决层与成本审计中心。**

### 1.3 新人最容易混淆的几个词

#### MCPServer
就是:
> 一个被平台注册并可被查询的外部 MCP Server 目录项。

它不是 `tools` 里的 `ToolDefinition`。

#### A2ANode
就是:
> 一个可被平台注册与发现的外部 Agent / Node 目录项。

它不是 runtime 当前正在运行的 agent 真相。

#### ProviderContract
就是:
> 平台和某个 LLM/API provider 之间的正式接入合同对象。

它不是 provider 自己的运行时服务本体,也不是明文 key 文件。

#### CapabilityDecision
就是:
> 在当前 policy / whitelist / quota 约束下,某个调用方真正可见、可用的能力集合。

它不是 runtime 的执行决策主线本体。

#### CostRecord
就是:
> 一次外部能力调用对应的正式平台成本记账记录。

它不是 provider 原始账单本体。

#### Secret envelope encryption
就是:
> Provider key 通过 KMS / Vault 引用或包裹加密后进入 capability-hub 的受控接入方式。

它不是 capability-hub 自己实现了一整套 secrets 平台。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L3-capability-hub/02` 时,先收稳以下前提:
- `L3-capability-hub` 不应按 MCP / A2A / Provider 横向平铺理解,而应按能力接入主链责任拆
- capability-hub 至少应拆成“能力注册与目录 / Provider 合同与密钥托管接缝 / 能力可见性与访问裁决 / 成本记账与审计事件 / 下游消费与分发出口”五个主要部分
- capability-hub 自己拥有的真相不是 runtime execution、tool definition、provider runtime 或 marketplace 交易真相,而是 registry / directory / contract / decision / cost 这类接入控制真相
- `L3-capability-hub` 只能为 runtime / tools / marketplace / observability 提供受控接入面,不能替它们持有各自业务真相
- 02 的重点不是“列有哪些 provider 或 server 名字”,而是先把“能力接入中心在平台里到底是什么、和 runtime/tools/governance/KMS/marketplace 怎么分层”讲清楚
- deny-by-default、policy refresh、secret envelope encryption、cost accounting、QueryCapabilities 这些不是零散特性,而是能力接入主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的能力接入心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,AI 成员和运行主线不应直接触碰外部能力。用户真正需要的不是“runtime 能连某个 provider”,而是:
- 哪些外部能力被正式允许接入
- 哪些 MCP Server、A2A Node、Provider 在当前策略下可见
- provider key / quota / cost / whitelist 是否被统一管理
- governance 更新后能力边界能否快速收紧
- 外部调用是否可被审计、可被计费、可被追责

如果把这些逻辑分别散落到:
- runtime 的本地配置
- tools 的 adapter 参数
- 各环境的 secret 文件
- governance 的局部策略缓存
- finance / audit 的事后统计脚本

系统会快速退化成:
- 能力可见性不一致
- 外部 key 管理失控
- 白名单与共享规则口径不统一
- 未白名单调用难以及时阻断
- 外部调用成本与审计难以全链追溯

因此,本概要设计的任务就是:
> **把 `L3-capability-hub` 写成一个新人也能看懂的“能力接入中心”,而不是把 registry、provider、policy、cost 和 runtime 调用关系写成一堆局部配置。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 未白名单调用拦截 | 目标明确,仓级主链未收稳 | 拦截率 100% | 需正式收敛 |
| 明文 key 落盘风险 | 原则已提出,无正式接入链 | 明文落盘次数 0 | 需固定安全底座 |
| QueryCapabilities 性能 | 高频查询需求明确 | P95 < 50ms | 需形成高频只读主线 |
| Policy 刷新延迟 | 目标已提出 | < 30s 生效 | 需固定刷新口径 |
| 外部调用成本覆盖 | 目标明确 | CostRecord 覆盖率 100% | 需形成审计记账主链 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让平台安全、可审计、可计费地使用外部能力,而不是让 runtime / tools 各自维护一套外部接入逻辑
- **技术问题**:MCP Registry、A2A Directory、Provider Contract、CapabilityDecision、CostRecord 与 governance / KMS / runtime / tools / marketplace 之间的边界如何稳定建模,并形成统一能力接入主链

## 4. 约束条件

### 4.1 技术约束

- 未白名单 MCP Server 必拒绝,必须 deny-by-default
- A2A Node 注册必须带认证,不能匿名接入
- Provider key 不得明文落盘,必须通过 KMS / Vault 接缝托管
- governance Policy 必须可动态刷新白名单 / shared_rules
- 所有外部调用都必须进入成本记账与审计主链

### 4.2 资源约束

- Provider / MCP / A2A 数量会持续增长,模型不能只适配单一 provider
- QueryCapabilities 是 runtime 高频路径,读侧复杂度必须被控制
- 成本记录会长期累计,必须从一开始就接受 append-only 规模增长

### 4.3 时间约束

- 当前阶段先收稳统一能力接入主链,而不是先做复杂 routing 或跨 provider 优化
- whitelist / cost / secret / audit 这四条基础控制链必须优先稳定,否则后续外部能力接入会失控

### 4.4 合规约束

- 明文 key 落盘次数必须为 0
- 未白名单调用成功率必须为 0
- 成本记账和拒绝调用都必须留审计事件
- shared_rules 禁止的能力不得被局部 allowlist 放开

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| MCP Server 数 | < 500 | 企业规模预估 |
| Provider Contract | < 100 | 主流供应商 + 自建模型 |
| QueryCapabilities QPS | 高频(runtime 路径) | 高频查询目标 |
| cost records/day | 高 | 每次外部调用都要记账 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ governance / admins         │
                    │ - policy / shared_rules     │
                    │ - registry / provider ops   │
                    └────────────┬───────────────┘
                                 │ policy / registration input
                                 ▼
                    ┌────────────────────────────┐
                    │ L3-capability-hub         │
                    │ - registry / directory    │
                    │ - provider contracts      │
                    │ - access / cost / audit   │
                    └────────────┬───────────────┘
                                 │ capability decision / contract view
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ runtime / tools            │   │ observability / finance    │   │ marketplace                │
│ - query + use              │   │ - audit / cost consume     │   │ - capability metadata      │
│ - external capability use  │   └────────────────────────────┘   └────────────────────────────┘
└────────────────────────────┘
```

### 5.2 位置解释

- `L3-capability-hub` 自己负责能力注册、目录、provider 合同、访问裁决、成本与审计接缝
- `runtime / tools` 只消费 QueryCapabilities / provider lookup 结果,不拥有接入控制真相
- `governance` 提供 policy / shared_rules 输入,但 capability-hub 负责将其转成能力可见性结果
- KMS / Vault 提供密钥托管能力,capability-hub 消费它而不替代它
- marketplace 只消费能力资产元数据,不拥有 registry / contract 真相

所以 `L3-capability-hub` 在全局里的角色是:
> **把平台访问外部能力的注册、合同、白名单、访问裁决、成本和审计收敛为统一受控入口。**

### 5.3 系统边界

**做什么**:
- 管理 MCP Registry
- 管理 A2A Directory
- 管理 Provider Contract
- 提供 QueryCapabilities / allow-deny / contract view
- 记录 CostRecord 与审计事件
- 消费 governance Policy 刷新能力边界

**不做什么**:
- 不真正执行外部调用
- 不持有 runtime execution truth
- 不持有 ToolDefinition 真相
- 不持有 provider runtime 真相
- 不承担 marketplace 交易真相
- 不替代 KMS / Vault 产品

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| KMS / Vault | 99.9% | 管理操作阻断,绝不降级成明文 |
| provider API | 99.9% | provider failover / retry,但 contract truth 不失真 |
| governance | 99.9% | 使用 last-known-good capability cache,同时记录刷新滞后 |
| L0-bus | 99.95% | backlog / replay,不静默丢审计与成本事件 |
| runtime / tools | 99.9% | 调用方不可用不影响 hub 自身 registry / contract truth |

### 5.5 关键依赖风险

- runtime 绕过 capability-hub 直连外部能力会直接破坏能力边界
- Policy 刷新滞后会导致 whitelist 不一致
- key 管理错误会造成严重泄露
- cost accounting 如果脱离调用主链,会让审计与计费失真
- marketplace 元数据需求可能反向污染接入控制模型

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把 MCP / A2A / Provider 三类对象横向平铺。  
> 它按 **能力接入主链职责 + 注册 / 合同 / 裁决 / 审计 / 分发差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象和机制,共同支撑同一段能力接入主链。

#### 能力注册与目录部分

- **它是什么**: 这是 `L3-capability-hub` 的能力真相入口层,一起回答“平台当前登记了哪些外部能力”
- **为什么单独有它**: 如果没有独立 registry / directory 层,能力是否存在、是否已启用、是否已退役会散落到 runtime 和 tools 的本地配置里
- **负责什么**:
  - 定义 `MCPServer`
  - 定义 `A2ANode`
  - 保存注册、验证、启停、退役等目录状态
- **不负责什么 / 容易混淆点**:
  - 不定义工具业务语义本体
  - 不负责 runtime 当前执行动作
  - 不负责 provider key 管理本体
  - 最容易和 ToolDefinition、runtime agent 运行态、外部系统自身状态混淆
- **与其他部分交互**:
  - 下游: Provider 合同与密钥托管接缝、能力可见性与访问裁决、下游消费与分发出口
  - 外部: admins / governance / marketplace / runtime / tools
  - 交互类型: 注册管理型 + 只读消费型
- **后续详细设计展开点**:
  - MCPServer / A2ANode 对象模型
  - registry lifecycle / verify / retire 主线

#### Provider 合同与密钥托管接缝部分

- **它是什么**: 这是 capability-hub 的 provider 接入合同层,一起回答“provider 怎样被正式接入平台”
- **为什么单独有它**: provider 合同、密钥托管、quota 和 cost 规则不是 registry 本体,如果不单列就会散到 runtime / tools / env file 中
- **负责什么**:
  - 定义 `ProviderContract`
  - 维护 provider key 引用、quota、route 与 cost 规则
  - 承接 KMS / Vault 的 secret envelope encryption 接缝
- **不负责什么 / 容易混淆点**:
  - 不执行 provider runtime 调用
  - 不替代 KMS / Vault 产品
  - 不等于 runtime 本地 provider client
  - 最容易和 provider runtime、本地 secret 文件、调用方配置混淆
- **与其他部分交互**:
  - 上游: admins / KMS / Vault
  - 下游: 能力可见性与访问裁决、成本记账与审计事件、下游消费与分发出口
  - 交互类型: 合同配置型 + secret 接缝型
- **后续详细设计展开点**:
  - ProviderContract / key ref / quota / route 模型
  - secret store / envelope encryption 主线

#### 能力可见性与访问裁决部分

- **它是什么**: 这是 capability-hub 的 policy-aware access 层,一起回答“当前谁能看到和使用哪些能力”
- **为什么单独有它**: 注册了能力不代表就能用。这里才是真正把 governance policy 变成可见能力集合的地方
- **负责什么**:
  - 定义 `CapabilityDecision`
  - 提供 `QueryCapabilities`
  - 组合 whitelist / shared_rules / contract / registry 状态生成 allow/deny 结果
- **不负责什么 / 容易混淆点**:
  - 不执行外部能力调用
  - 不替代 governance 的业务裁决真相
  - 不持有 runtime execution truth
  - 最容易和 policy 本体、runtime dispatch decision、provider runtime 调用混淆
- **与其他部分交互**:
  - 上游: registry / directory、provider contract、governance policy
  - 下游: runtime / tools
  - 交互类型: 访问裁决型 + 高频只读查询型
- **后续详细设计展开点**:
  - CapabilityDecision / allow-deny / cache / refresh 主线

#### 成本记账与审计事件部分

- **它是什么**: 这是 capability-hub 的审计与成本主链层,一起回答“外部能力调用如何被记账和留痕”
- **为什么单独有它**: registry / contract / access 都不能替代审计和成本链,否则调用边界虽存在,但企业侧看不到代价和责任链
- **负责什么**:
  - 定义 `CostRecord`
  - 生成 cost / deny / audit 事件
  - 为 observability / finance / audit 提供 append-only 记录
- **不负责什么 / 容易混淆点**:
  - 不等于 provider 原始账单本体
  - 不等于 runtime 业务日志
  - 不负责 finance 系统真相
  - 最容易和 provider billing、runtime log、observability raw event 混淆
- **与其他部分交互**:
  - 上游: ProviderContract、CapabilityDecision、runtime/tools 调用结果
  - 下游: 下游消费与分发出口、observability / finance
  - 交互类型: 记账审计型 + append-only 输出型
- **后续详细设计展开点**:
  - CostRecord / cost event / deny event 模型
  - append-only 记账与 replay 规则

#### 下游消费与分发出口部分

- **它是什么**: 这是 capability-hub 向 runtime / tools / marketplace / observability 提供稳定消费面的层,一起回答“能力怎样被稳定消费和分发出去”
- **为什么单独有它**: hub 不只是“内部存一下”,而是要持续向外部提供统一能力视图、provider lookup 和元数据出口
- **负责什么**:
  - 提供 runtime / tools 的 capability view
  - 提供 marketplace 的 capability metadata 出口
  - 提供 observability / finance 的 audit / cost 输出接缝
- **不负责什么 / 容易混淆点**:
  - 不承担外部能力实际执行
  - 不承担 marketplace 交易逻辑
  - 不承担 provider runtime 客户端行为
  - 最容易和 runtime 本地 cache、marketplace listing、provider runtime view 混淆
- **与其他部分交互**:
  - 上游: registry / contract / decision / cost
  - 下游: runtime / tools / marketplace / observability / finance
  - 交互类型: 只读消费型 + 分发出口型
- **后续详细设计展开点**:
  - capability view / provider lookup / metadata output / cost sink 接缝

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ governance / admins         │
                    │ - policy / shared_rules     │
                    │ - registry / contract ops   │
                    └────────────┬───────────────┘
                                 │ policy / registration input
                                 ▼
                    ┌────────────────────────────┐
                    │ L3-capability-hub         │
                    │ - registry / directory    │
                    │ - provider contracts      │
                    │ - access / cost / audit   │
                    └────────────┬───────────────┘
                                 │ capability decision / contract view
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ runtime / tools            │   │ observability / finance    │   │ marketplace                │
│ - query + use              │   │ - audit / cost consume     │   │ - capability metadata      │
│ - external capability use  │   └────────────────────────────┘   └────────────────────────────┘
└────────────────────────────┘
```

### 7.2 总解释

- `L3-capability-hub` 自己负责“注册能力”“管理 provider 合同”“裁决当前可见能力集合”“记录成本与审计”“输出统一能力消费面”
- `governance` 的交互主要落在 **能力可见性与访问裁决部分**,为 hub 提供 policy / shared_rules 输入
- `runtime / tools` 的交互主要落在 **能力可见性与访问裁决部分** 与 **下游消费与分发出口部分**,消费 allow/deny 能力集与 provider lookup 结果
- KMS / Vault 的交互主要落在 **Provider 合同与密钥托管接缝部分**,为 hub 提供 secret 托管能力
- `observability / finance` 的交互主要落在 **成本记账与审计事件部分** 与 **下游消费与分发出口部分**,消费审计与成本输出
- marketplace 的交互主要落在 **下游消费与分发出口部分**,消费能力元数据,而不拥有注册表或 provider contract 真相

### 7.3 分模块交互说明(逐个写)

#### 与 `governance` 的交互

```text
┌────────────────────────────┐
│ governance                 │
│ - policy.updated           │
│ - shared_rules             │
└────────────┬───────────────┘
             │ policy input
             ▼
┌────────────────────────────┐
│ capability-hub             │
│ - CapabilityDecision       │
│ - whitelist refresh        │
└────────────────────────────┘
```

- `governance` 是 **能力边界规则输入方**
- **交互类型**: policy 输入型交互
- **主流程位置**: whitelist 变化、deny-by-default 刷新、shared_rules 收紧时进入主流程
- **交互解释**:
  - governance 提供 policy / shared_rules
  - capability-hub 把它转成当前 capability decision
  - hub 不替代治理业务裁决真相
- **高风险异常流**:
  - policy 更新后白名单刷新滞后导致能力边界不一致
- 后续 `03-详细设计.md` 继续展开:
  - policy refresh contract
  - last-known-good 主线

#### 与 `runtime / tools` 的交互

```text
┌────────────────────────────┐
│ runtime / tools            │
│ - query capabilities       │
│ - provider lookup          │
└────────────┬───────────────┘
             │ access query
             ▼
┌────────────────────────────┐
│ capability-hub             │
│ - CapabilityDecision       │
│ - contract view            │
└────────────────────────────┘
```

- `runtime / tools` 是 **能力消费方**
- **交互类型**: 高频只读查询型交互
- **主流程位置**: QueryCapabilities、provider lookup、allow/deny 判断时进入主流程
- **交互解释**:
  - runtime / tools 查询当前可见能力
  - capability-hub 只返回 decision 和 contract view
  - hub 不执行实际外部调用
- **高风险异常流**:
  - runtime 绕过 hub 直连外部能力
- 后续 `03-详细设计.md` 继续展开:
  - QueryCapabilities contract
  - allow/deny / contract view 模型

#### 与 `KMS / Vault` 的交互

```text
┌────────────────────────────┐
│ KMS / Vault                │
│ - key store                │
│ - envelope encryption      │
└────────────┬───────────────┘
             │ secret input/output
             ▼
┌────────────────────────────┐
│ capability-hub             │
│ - ProviderContract         │
│ - secret reference         │
└────────────────────────────┘
```

- KMS / Vault 是 **密钥托管能力来源**
- **交互类型**: secret 托管接缝型交互
- **主流程位置**: provider 注册、key rotate、quota 更新时进入主流程
- **交互解释**:
  - capability-hub 保存密文或引用
  - KMS / Vault 承担实际密钥托管
  - hub 不自造 secrets 平台
- **高风险异常流**:
  - 管理操作失败后退化成明文 key 落盘
- 后续 `03-详细设计.md` 继续展开:
  - secret store adapter
  - envelope encryption contract

#### 与 `observability / finance` 的交互

```text
┌────────────────────────────┐
│ capability-hub             │
│ - CostRecord               │
│ - deny / audit events      │
└────────────┬───────────────┘
             │ audit/cost output
             ▼
┌────────────────────────────┐
│ observability / finance    │
│ - audit consume            │
│ - cost consume             │
└────────────────────────────┘
```

- `observability / finance` 是 **审计和成本消费方**
- **交互类型**: append-only 输出型交互
- **主流程位置**: provider 调用成功/失败、未白名单拒绝、quota 告警时进入主流程
- **交互解释**:
  - capability-hub 发 cost / deny / audit 事件
  - observability / finance 消费这些记录
  - hub 不替代审计中心或财务真相系统
- **高风险异常流**:
  - provider 调用发生了,但成本记录未写入
- 后续 `03-详细设计.md` 继续展开:
  - cost record / audit event contract
  - retry / backlog 主线

#### 与 `marketplace` 的交互

```text
┌────────────────────────────┐
│ capability-hub             │
│ - MCP/A2A/provider meta    │
└────────────┬───────────────┘
             │ capability metadata output
             ▼
┌────────────────────────────┐
│ marketplace                │
│ - listing / distribution   │
└────────────────────────────┘
```

- marketplace 是 **能力资产元数据消费方**
- **交互类型**: 元数据分发型交互
- **主流程位置**: registry publish、provider 上架、能力目录查询时进入主流程
- **交互解释**:
  - capability-hub 提供 capability metadata
  - marketplace 承担 listing / 分发 / 交易
  - hub 不接管商业流程真相
- **高风险异常流**:
  - marketplace 诉求反向要求 registry / contract 模型长胖
- 后续 `03-详细设计.md` 继续展开:
  - metadata export contract
  - listing boundary

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是访问裁决层、哪个模块是密钥托管来源、哪个模块是审计消费方

本节**不**展开:
- MCP / A2A / provider 协议细节
- QueryCapabilities 具体求值算法
- key rotate 低层实现
- cost 聚合规则细节
- runtime 真实外部调用执行链

这些内容留到 `03-详细设计.md` 中继续展开。

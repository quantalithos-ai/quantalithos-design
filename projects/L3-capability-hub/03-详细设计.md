## 3. 实现约束与编码规范承接

> 校准来源：
> - `design-calibration/03_ddd_step_03_constraints.md` §§5~7
> - `design-calibration/03_ddd_step_14_config_external_binding.md` §§118~135

### 3.1 Rust与仓库约束

| 约束 | 正式契约 |
|---|---|
| language | Rust；优先与已审计sibling基线对齐Rust 2024 / rust-version 1.93，目标仓创建后必须核实真实Cargo基线 |
| identifiers/source comments/tests | English |
| sibling compile dependency | 唯一允许`core-contracts = { path = "../quantalithos-core/crates/contracts" }` |
| non-core relations | Port、adapter、typed event、snapshot、safe summary或handoff；禁止sibling Cargo dependency |
| async traits | 33/33 async Port/repository trait固定`async-trait 0.1.89`、`Send` future，禁止`?Send` |
| runtime | Worker/Jobs exact runtime ownership以Step 14为准；host不得注入改变non-cancelling语义的executor |
| error classification | exhaustive typed matching；禁止`Display`/`Debug`/string/status私自分类 |
| unsafe/generic escape | 不用`unsafe`、generic bytes/value、private finder或hidden state绕过契约 |

### 3.2 Rustdoc与结构体注释门禁

所有 public Rust declaration 都必须有英文 `///`。该要求逐项覆盖：

- public struct/newtype及其每一个field；
- public enum及其每一个variant；
- struct-like enum variant的每一个payload field，且field不得带field-level `pub`；
- public trait、trait method和其他public callable；
- Command、Query、Inbound/Outbound Event、Job、View、Receipt、Report和Error carrier。

不得只注释结构体而遗漏字段，也不得用模块说明替代variant/payload/callable注释。规范性Rust声明位于Step 6/7/8/12/14的exact sections；实现必须承接其Rustdoc-complete版本，禁止根据本文摘要另造简化schema。

### 3.3 安全和数据边界

| Gate | Rule |
|---|---|
| forbidden body | secret、governance、method、runtime execution、raw audit、marketplace transaction、cost和external document body永不入local object/DTO/store/event/log |
| Query | 33/33严格no-write，不begin UoW、不reserve、不refresh/rebuild |
| Inbound consumer | 只写其body-free reference/feedback owner，不直接修core truth |
| Job | 不修identity/registry/descriptor/relation/exposure truth，不用report触发隐式Command |
| post-commit collaboration | external failure不回滚local truth |
| configuration | 不得改变truth owner、state redline、protocol identity或forbidden-body边界 |

### 3.4 Git与实施前检查

目标实现仓当前不存在，因此本文不声称其`.git`、branch、Cargo或git identity状态。正式07和实施preflight必须核实仓路径、worktree、project-level `user.name`/`user.email`及项目提交规范。当前设计工作不创建实现commit。

### 5.1 `contracts`

| Item | Contract |
|---|---|
| responsibility | public typed ref、metadata、Command/Query/Event/Job/View/Receipt/Report/Error和canonical codec bytes |
| files | `refs.rs`、`metadata.rs`、`commands.rs`、`queries.rs`、`events.rs`、`jobs.rs`、`views.rs`、`errors.rs` |
| dependencies | only `core-contracts`; no domain/application/infra type leakage |
| public inventory | 250 public types；five closed protocol-name families；typed generic carriers and exact per-protocol DTO |
| critical functions | validation、closed-name mapping、canonical field encoding、one-way public page/view mapping |
| errors | 10-variant `ContractValueError`; no generic string/value fallback |
| test cut | roundtrip、validation、canonical bytes、schema version、metadata authority、all public Rustdoc |

Metadata是actor、trace、idempotency、source event、job run和schema authority；payload不得复制这些authority。Contracts只承载body-free、安全、可序列化surface，不承载domain invariant或外部正文。

`CapabilitySafeText` 的安全边界由 `design-calibration/03_ddd_step_06_object_contracts.md` §7.2.1 的 closed marker contract 唯一规定。实现只做一次 Rust Unicode `trim()`，对 trimmed UTF-8 bytes 按固定声明顺序检查八个大小写敏感的 ASCII marker literal：`external-capability-source`、`governance`、`method`、`secret`、`external-document`、`runtime-execution-payload`、`sdk-client`、`observability`。marker 可出现在任意位置；重复命中返回同一 typed category；多类别命中按该声明顺序返回，而不是按文本位置返回。实现不得做 normalization、case-fold、percent/base64/JSON/PEM 解码、语义关键词推断或 scanner 专用长度裁剪，并且不得在错误、日志、报告、artifact、cleanup 或 evidence 中回显输入、marker、命中片段、URL、digest、hash、长度或诊断正文。无 marker 只表示 structural guard 未命中，不是任意自然语言 DLP 清除；拥有 raw external body 的 source/Port/decoder/mapper 必须在调用该 primitive 前 fail-closed，不能把 raw body 降级为 safe text。

### 10.3 Version、index、cursor 与 fence

| Mutation | Only legal token | Failure meaning |
|---|---|---|
| create versioned owner | `expected_version=None` | unique/current owner conflict or Port failure |
| update truth/relation/summary/material/state | matching repository returned `Loaded<T>.expected_version` | `OptimisticConflict`; never retry in-place blindly |
| append trace successor | current trace revision's expected version | concurrent successor wins; no revision overwrite |
| complete idempotency | token returned with winning `Reserved` record | loser preserves winner and result ref |
| bind capture intent | exact loaded capture token | reload `IntentBound` or retry same stable candidate only |
| Job target/final save | latest exact journal token | preserve terminal target/final winner |

Current indexes are owner-specific predicates over non-terminal states, not a second status field. Terminal history remains exact-readable where the repository contract provides it. Dependency scans are collect-only: consume all pages, verify cursor scope/continuity, deduplicate typed refs, then mutate each exact owner with its own token. A source fence must reject a stale material refresh even if the material's own CAS still matches.

Cursor identity includes repository method, validated scope, stable sort definition and last stable key. Cursor is not a business reference、version token、public protocol field or Job resume record. Durable and deterministic-fake adapters must agree on ordering、empty pages、next cursor、scope mismatch and phantom/fence outcomes.

For every persisted union:

```text
typed ref variant
  == stored object variant
  == owner-key family
  == related state/result/source variant
```

Any mismatch is `ConsistencyDefect`; it is never normalized to not-found or repaired by parsing strings/table names.

### 10.5 Required save order

Every fresh write uses this ordering skeleton, narrowed by its exact Step 9 flow card:

```text
validate typed envelope/body/metadata
  -> form closed operation identity, normalized key and canonical digest
  -> exact duplicate preflight
  -> begin UoW and reserve atomically
  -> load prerequisites and retain every exact expected version
  -> invoke the declared factory/member/policy
  -> save source-owned truth/reference state
  -> append required change/trace records
  -> collect the complete affected union, then save actual stale revisions
  -> serialize and insert declared event snapshot/capture
  -> insert immutable channel-specific result/surface/envelope
  -> complete the winning reservation with the same result ref
  -> commit
  -> invoke only the declared post-commit handoff/collaboration
```

A source revision, required sidecars and stored replay surface cannot be partially accepted. An exact no-op performs the zero effects fixed by its flow; it may store a stable no-op response only where that protocol explicitly requires it. Post-commit external outcome never rewrites local truth or the stored response disposition.

Job execution is split deliberately: planning freezes all targets before the initial UoW; each target commits its own effect and terminal outcome; a failed target may be terminalized in a journal-only UoW only after effect rollback is authoritative; final assembly reads journal outcomes only and cannot rescan source truth or rerun targets.

### 10.6 Isolation, commit resolution and crash visibility

| Subject | Required guarantee | Forbidden downgrade |
|---|---|---|
| owner mutation | strong local consistency + current uniqueness + CAS | eventual winner choice、timestamp ordering |
| source + required sidecars | same-UoW local required | source-first commit followed by repair |
| affected material | stable complete candidate scan + source fences + own CAS | mutate while paging、best-effort stale subset |
| duplicate winner | linearizable normalized-key read/reserve | cache/replica guess、raw-key-only lookup |
| commit recovery | stable transaction identity + `Durable/NotDurable/Unknown` | empty-read/sleep/connection-close as rollback proof |
| external collaboration | post-commit, stable candidate/intent | distributed transaction or local delivery truth |

Before commit, the application copies `CapabilityTransactionRef`. If commit is ambiguous it calls the same persistence authority's `resolve_commit` within the formal 04 observation budget:

1. `Durable`: cross a linearizable read barrier, then read the complete declared winner/owner/sidecar set and return only an exact symmetric replay/effect.
2. `NotDurable`: this is proof about the original transaction identity; exact winner and owner reads must still show no competing change before retrying with the same operation identity.
3. `Unknown` or budget exhaustion: return `CommitOutcomeUnknown`; perform no Clock/ID/domain/resolver/handoff/collaboration/write call.

One absent row is never proof of rollback. `Durable` with a missing/asymmetric sidecar is a consistency defect, not permission to rerun. The complete failure/crash/recovery matrix is normative in Step 11 §§13~15 and Step 13 §§18~21.

### 10.7 Durable/fake parity and persistence redlines

Deterministic fakes must implement the same 22/110 surface, CAS/unique/index/cursor/fence semantics, UoW staging visibility, rollback, three-state commit resolution, read barrier, crash injection and typed-union verification as durable adapters. A fake cannot map every unknown to not-durable, skip constraints, expose staged writes early or accept stale tokens.

No adapter may introduce DB-trigger state transitions, generic upsert, hidden retries that change winner selection, current-truth reconstruction of immutable history/result, local collaboration status, or a cache/search index that overrides its formal owner. These are design violations, not implementation conveniences.

### 11.6 Rollback and side-effect precedence

| Failure point | Local action | External action | Returned authority |
|---|---|---|---|
| before begin | no rollback | no call except declared pre-UoW resolver | original typed error |
| after begin, before commit | rollback complete staged UoW | external observation cannot be undone | original error only if rollback succeeds |
| rollback fails | durability not inferred | no compensating business call | `TransactionRollbackFailed` / controlled resolution |
| commit confirmed not durable | discard tokens/IDs from attempt | post-commit action forbidden | `TransactionCommitFailed` then exact retry policy |
| commit unknown | freeze mutation path and resolve original transaction | no new resolver/handoff/collaboration | `CommitOutcomeUnknown` until decided |
| commit Durable | exact sidecar/winner verification | execute only declared post-commit call | stored result/effect authority |
| post-commit Port typed failure | local truth remains Durable | typed retry/handoff owner handles it | never rewrite accepted result |

Business record、public issue、operational visibility and event capture have different owners. An issue code is not an audit record; a log is not a durable fact; event capture is not delivery evidence; a typed failure does not authorize a compensating truth mutation.

### 11.7 Recovery redlines

- Never reconstruct an immutable result、receipt、report、snapshot or trace revision from current truth.
- Never retry a changed request under the winning idempotency key.
- Never classify raw text/status as retryable or business rejection.
- Never convert persistence inconsistency into missing/degraded success.
- Never mark a Job target failed until any attempted effect is authoritatively rolled back.
- Never use external collaboration result to roll back source truth or claim delivery evidence.
- Never persist conflict against the winner; conflict is an observation with zero winner mutation.

### 12.3 Idempotency lifecycle and winner preservation

`CapabilityIdempotencyState` has exactly two active variants: `Reserved` and `Completed`. The only current transition is `Reserved -> Completed`; `Completed -> Reserved` is illegal. Conflict is never persisted and there is no `mark_conflict`.

| Channel | Durable `Reserved` meaning | Legal reentry |
|---|---|---|
| Command | no legal committed orphan after successful atomic UoW | exact `Completed` replay or absence after confirmed not-durable |
| Inbound | same as Command | typed receipt replay or confirmed fresh retry |
| Job | required with a matching complete `Planned` journal | resume exact frozen journal or pure final assembly |
| Query | forbidden | current read only |

`IdempotencyInProgress` is valid only when the concrete transaction/unique authority proves a matching transient owner is still active. A visible orphan `Reserved` Command/Inbound row is `ConsistencyDefect`, not a delayed business operation.

Duplicate decision order is fixed:

1. Exact `Completed` key/channel/operation/digest and, for Job, run identity: load and verify the immutable channel-specific surface, then return response-only duplicate disposition with zero business/Port/write calls.
2. `Completed` mismatch: `IdempotencyConflict`; preserve and hide the winner body.
3. `Completed` with missing/corrupt/asymmetric sidecar: `ConsistencyDefect` or `CodecFailure`; never rerun.
4. `Reserved` Job: exact matching journal required; resume first planned ordinal or final assembly.
5. `Reserved` Command/Inbound: transient in-progress only with authority proof; otherwise consistency defect.
6. Atomic reserve loser: discard all uncommitted IDs/plans, exact-read winner and follow the rows above.

### 12.4 Concurrency authority and canonical resource order

| Control | Protects | Does not replace |
|---|---|---|
| atomic normalized-key reserve | request/event/job duplicate winner | business current-owner uniqueness or object CAS |
| owner optimistic CAS | one loaded versioned owner | key reserve or dependency fence |
| conditional current uniqueness | owner-specific current identity | stored replay |
| append/insert uniqueness | immutable record/report/result/snapshot | mutable owner CAS |
| reference `(kind,digest)` uniqueness | duplicate body-free reference + canonical subject state | request identity |
| per-source dependency fence | source successor vs stale material write | material's own CAS |
| event `(source,schema)` uniqueness | second snapshot/capture | external stable-intent contract |
| Job journal CAS | target/final terminal winner | external-effect idempotence |

Logical acquisition/validation order is:

```text
normalized key
  -> core truth/relation refs
  -> canonical reference subjects
  -> current-owner compound keys
  -> dependency source fences
  -> mutable material refs
  -> append-only record/trace/report IDs
  -> event source+schema capture key
  -> immutable result/surface refs
  -> idempotency completion CAS
```

An adapter may implement this with serializable validation、predicate locks or ordered row locks, but process mutex、random delay、timestamp order、last-write-wins and generic upsert are not correctness authorities. Retry/backoff limits are formal 04 technical policy and cannot change winner selection.

### 12.6 Reentry by channel

| Crash/reentry point | Exact authority | Required action |
|---|---|---|
| Command response lost after Durable | stored completed surface | exact replay; no truth/change/trace/material/capture/handoff rerun |
| Command/Inbound confirmed rollback | absent winner/effect under authority read | same identity may execute fresh; discard old generated values |
| Inbound redelivery | completed typed receipt | replay; zero resolver/local writes |
| source committed before collaboration | `Captured` + immutable snapshot | use stored candidate; never remap current source |
| external intent formed, bind absent | stable candidate -> same intent | repeat collaborate, validate, bind exact capture CAS |
| capture already bound | stored exact intent | call external `get`; never second collaborate/bind |
| Job after initial commit | `Reserved + Planned journal` | resume first planned target; never rescan scope |
| Job target committed before loop response | terminal journal outcome | skip target and continue next ordinal |
| all targets terminal, final rollback | journal-only authority | pure report assembly; no source/Port/target reread |

For trace handoff, same-key exact duplicate only replays and makes zero Port calls. A new key against the exact current trace creates exactly one new `HandoffPending` revision, stores/completes it, then performs one post-commit call. There is no new-key zero-revision continuation because persisted trace does not prove equality of the previous handoff scope.

### 12.7 Commit-outcome-unknown algorithm

```text
freeze the original transaction ref, normalized key and request digest
  -> perform no Clock, ID, domain, resolver, handoff, collaboration or write call
  -> resolve original transaction through the same authority
  -> Durable: cross read barrier; verify every winner/owner/sidecar relation
  -> NotDurable: exact-read key and all owner tokens; retry only if no competing winner/change
  -> Unknown/error/budget exhausted: return CommitOutcomeUnknown
```

Job initial recovery reads key + journal; target recovery reads journal + exact planned owner/capture; final recovery reads key + typed report/surface + journal. A completed symmetric final set replays; a reserved all-terminal unfinalized journal after confirmed rollback permits pure final retry. No branch may use report-by-run、generic decode、scope replan or target re-execution.

### 12.8 Stored surface and outbound envelope integrity

Stored result creation serializes the exact public DTO once, rejects empty bytes, computes the result digest, then stores bytes、digest、shell、typed envelope and `Completed` result ref in one UoW. Read recomputes from stored bytes before typed mapping. Current DTO reserialization and current-truth reconstruction are forbidden.

Outbound candidate digest covers the complete serialized envelope including name、schema、source、occurred time、trace、routing key and payload. Snapshot and capture retain the same digest; collaboration receives those stored bytes unchanged. A codec representation change requires a new event schema/domain and cannot rewrite historical bytes.

### 13.8 Eight Job runners and owned runtime

The Jobs entry has exactly eight arms: `RunCapabilityRegistryReconciliation`、`RefreshControlledConsumerView`、`RebuildDirectorySearchBrowseProjection`、`PrepareAuditFriendlyExportSummary`、`RebuildReadOnlyEcosystemDiscoverySummary`、`RunDerivedMaterialReconciliation`、`RefreshExternalReferenceResolution` and `RepairCapabilityAccessEventCollaboration`. ### 14.1 Six layers, four planes and one-way authority

| Layer | Owner and meaning | Never proves or replaces |

### 14.6 Off/Redacted, redaction and observer failure

`CapabilityDiagnosticMode` has exactly `Off` and `Redacted`:

| Mode | Construction and emission | Business behavior |
|---|---|---|
| `Off` | return before field construction; no sink、redaction diagnostic、span/event or Gauge refresh | unchanged |
| `Redacted` | select static profile, read only its typed allowlist, apply required/optional/atomic gates, then call sink once | unchanged even if projection/sink fails |

Ten material classes are closed: static closed values、bounded scalar、correlation ref、attribution、safe text、integrity、diagnostic、serialized material、transport-private material and external body. Safe free text is omitted from all observer planes even if legal in a business carrier. Serialized material、raw/private transport material and external bodies are always rejected. Whole-object serialization、`Debug`/`Display`、hash/truncate/length of forbidden data、dynamic category construction and synthetic fallback IDs/times/traces are always rejected.

Required-source failure rejects the whole profile; optional-source failure omits the field; an atomic correlation group is all-or-none. No empty/`unknown`/redacted placeholder may satisfy a field. A genuine forbidden-material submission may produce at most one non-sensitive, independent redaction-violation diagnostic. Sink failure may produce at most one independent non-recursive fallback; fallback failure stops silently. Observer code cannot panic、retry itself、open a UoW、call a business Port、alter status/result or cancel a future.

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 MCP Registry / A2A Directory / ProviderContract / CapabilityDecision / CostRecord / secret reference / audit event 真相
- 把外部能力注册、目录、合同、白名单、访问裁决、成本与审计收束成统一受控入口
- 把 governance policy / shared_rules 转换成 runtime / tools 可消费的 QueryCapabilities 结果
- 通过 KMS / Vault 接缝托管 provider key,并为审计与 finance 输出 append-only 记录

**本模块不做什么**:
- 不真正执行外部 capability 调用
- 不持有 ToolDefinition、runtime execution truth 或 provider runtime 真相
- 不替代 KMS / Vault 产品本体
- 不承担 marketplace 交易真相或业务对话/流程语义真相

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 capability-hub“为什么存在”,而是让开发者可以直接开始实现:
- MCP / A2A / Provider 如何形成统一 registry / contract 真相层
- governance policy / shared_rules 如何进入 CapabilityDecision 主线
- QueryCapabilities 如何在高频路径下给 runtime / tools 提供稳定 allow/deny 结果
- Provider key 如何通过 KMS / Vault 接缝被受控托管
- 外部调用成功/失败如何进入 CostRecord、deny event 与 audit 主线

如果不先把这些内容采集清楚,03 很容易退化成:
- provider 配置表说明书
- MCP / A2A 名单清单
- KMS/Vault 接入脚本笔记
- runtime 如何调用 provider 的业务说明,从而反向混掉 access / execution 边界

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `MCPServer / ProviderContract / CapabilityDecision / CostRecord` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是能力接入主链,`03` 却退化成 provider / registry 配置表清单
- 实现者知道有 QueryCapabilities,却不知道它如何与 policy refresh、secret 托管、cost 记账形成一条统一主线
- registry、contract、audit、metadata 各写一套,彼此脱节

这些对象在该部分里分别承担:
- `MCPServer` 负责表达外部 MCP 能力注册真相
- `A2ANode` 负责表达 A2A 外部节点目录真相
- `RegistryLifecycleState` 负责统一注册项状态语言
- `RegistryHealthSnapshot` 负责给后续消费方提供健康摘要输入
- 它们共同回答“平台允许登记了什么”,而不是“运行时现在正在执行什么”

#### 5.2.4 关键函数代码片段

```rust
/// 把一个新的 MCP Server 注册到能力目录中。
fn register_mcp_server(
    registry_repo: &dyn RegistryRepo,
    draft: RegisterMcpServerDraft,
) {
    // [MCPServer::从草稿创建]
    // 先把注册输入收束成正式目录项对象。
    let server = MCPServer::from_draft(draft);

    // [server.校验目录边界]
    // 再校验它只是接入目录项,而不是工具定义或执行状态对象。
    server.validate_registry_boundary();

    // [registry_repo.保存目录项]
    // 最后把目录项写入 registry 真相层,供 access / metadata 主线继续消费。
    registry_repo.save_mcp_server(server);
}
```

这段实现守住的边界是:
- registry 必须先稳定成立,后续才能做 access / metadata 输出
- MCPServer 只表达“可登记的外部能力项”,不表达工具业务语义本体
- 目录项真相和运行时当前调用状态必须分层

#### 5.2.5 该部分的边界与非职责
- 不负责 provider key 管理
- 不负责 QueryCapabilities 裁决
- 不负责 cost / deny / audit 记录本体
- 不负责工具执行与宿主调用链

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `Provider 合同与密钥托管接缝部分` 提供可关联目录项输入
- 向 `能力可见性与访问裁决部分` 提供 registry 状态输入
- 向 `下游消费与分发出口部分` 提供 capability metadata 输入

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `MCP Registry ≠ ToolDefinition` 必须写死
- `Registry / Directory ≠ external capability truth` 必须写死
- registry 若与 provider / decision / runtime 调用状态混写,后续能力边界会失控

#### 5.3.4 关键函数代码片段

```rust
/// 根据 provider 输入和 secrets 托管结果建立正式接入合同。
fn register_provider_contract(
    contract_repo: &dyn ProviderContractRepo,
    secret_store: &dyn SecretStore,
    draft: RegisterProviderDraft,
) {
    // [secret_store.写入密钥引用]
    // 先把原始 key 交给外部托管系统,禁止 capability-hub 直接持有明文。
    let secret_ref = secret_store.store_enveloped_secret(draft.raw_secret);

    // [ProviderContract::从草稿创建]
    // 再用受控引用、配额和 provider 元数据构造正式接入合同。
    let contract = ProviderContract::from_draft(draft, secret_ref);

    // [contract_repo.保存 provider 合同]
    // 最后把正式合同写入 contract 真相层,供 access / cost / metadata 继续消费。
    contract_repo.save(contract);
}
```

这段实现守住的边界是:
- hub 绝不直接持有明文 key
- provider contract 先站稳,后续 access / cost / metadata 才有共同基线
- secret 托管能力来自 KMS/Vault,不是 capability-hub 自造

#### 5.3.5 该部分的边界与非职责
- 不负责实际 provider runtime 调用
- 不负责 allow/deny 结果裁决
- 不负责 finance 记账真相本体

#### `RotateProviderSecret`

```text
function RotateProviderSecret(input):
    1. 校验 provider_contract 是否存在
    2. 校验新 secret 不会以明文落盘
    3. 调用 KMS/Vault 写入受控引用
    4. 更新 ProviderContract.secret_ref
    5. 写入 secret rotate 审计记录
    6. 刷新相关 capability decision
    7. 返回新的 secret reference
```

#### `RecordDeniedInvocation`

```text
function RecordDeniedInvocation(input):

    2. 构造 DeniedInvocationAudit
    3. 追加 deny history
    4. 发 denied audit event
    5. 更新 denied metrics
    6. 返回 denied audit id
```

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| 未白名单 MCP 被请求 | 直接拒绝并记录 deny 审计 |
| A2A 匿名注册 | 拒绝注册 |
| Provider key 托管失败 | 阻断合同落库 |
| policy 刷新滞后 | 使用 last-known-good 并记录 refresh lag |
| 外部调用成功但成本记录失败 | backlog + retry |

### 11.1 重试 / 降级 / 熔断 / 补偿
- policy 刷新失败时可使用 last-known-good capability cache,但必须显式记 lag 证据
- cost / audit 记录失败时可 backlog + retry,但不得静默忽略
- provider failover 可以作为运行期补偿输入,但不能污染 contract truth

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 能力注册与目录部分 | registry 项目与外部能力状态混写 | registry boundary validate | 拒绝落库 | 修正目录输入后重试 |
| Provider 合同与密钥托管接缝部分 | secret 托管失败 / 合同与明文耦合 | secret store validate | 阻断保存 | 通过 KMS/Vault 重试 |
| 能力可见性与访问裁决部分 | shared_rules 未覆盖局部 allowlist / decision 漏刷 | decision input validate | 重新刷新 capability decision | replay refresh |
| 成本记账与审计事件部分 | cost 记录丢失 / deny 不留痕 | billable / append validate | backlog + retry | replay / backlog recovery |
| 下游消费与分发出口部分 | runtime 看到错误 capability view / marketplace 元数据反写 | read-only boundary validate | 拒绝输出或重建视图 | 重建投影 |

- 管理员注册一个受控 provider 合同并通过 KMS/Vault 托管 key,随后 runtime 能通过 QueryCapabilities 看到它

## 15. 结论

本详细设计的核心结论是：
- `L3-capability-hub` 的实现主轴必须按 registry / contract / decision / cost / distribution 五个主要部分组织,而不是按 MCP/A2A/provider 名单平铺
- capability-hub 真相层只持有能力注册、provider 合同、访问裁决、成本与审计真相,不接管 runtime / tools / marketplace / KMS 的本体真相
- 所有 QueryCapabilities、metadata output、deny/cost/audit 事件都必须建立在正式 registry、contract、decision 与 append-only 证据链之上

后续测试与验收文档,应直接围绕这套能力接入主链、边界、审计与成本链展开.

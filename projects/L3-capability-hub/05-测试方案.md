### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 capability-hub“能登记一条配置”,而是系统验证 `L3-capability-hub` 是否真正满足“能力接入中心”的设计要求,尤其要证明以下几点成立:
- registry / directory / provider contract 构成正式接入真相层
- `capability access ≠ capability execution` 成立,hub 只做接入控制和分发,不推进运行执行主线
- `MCP Registry ≠ ToolDefinition`、`ProviderContract ≠ provider runtime`、`CapabilityDecision ≠ runtime execution truth`、`CostRecord ≠ provider raw billing source` 等核心边界成立
- QueryCapabilities 能在 policy / shared_rules 刷新后稳定生成新的 allow/deny 结果
- secret 托管严格通过 KMS/Vault 接缝完成,明文 key 不落盘
- 外部调用成功/失败都能进入 cost / deny / audit 记录主链
- marketplace / observability / finance 消费的都是只读视图或 append-only 记录,不会反写真相

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 能力注册与目录部分 | registry / directory 真相对象 | P0 | MCPServer、A2ANode、RegistryLifecycleState、RegistryHealthSnapshot |
| Provider 合同与密钥托管接缝部分 | contract / secret 对象 | P0 | ProviderContract、SecretEnvelopeRef、ProviderQuota、ProviderRouteRule |
| 能力可见性与访问裁决部分 | access decision 对象 | P0 | CapabilityDecision、CapabilityDecisionInput、SharedRuleSnapshot、AllowDenyEntry |
| 成本记账与审计事件部分 | append-only 记录对象 | P0 | CostRecord、DeniedInvocationAudit、CapabilityAuditEntry、CostEventMaterial |
| 下游消费与分发出口部分 | 只读输出对象 | P0 | CapabilityDecisionView、ProviderLookupView、CapabilityMetadataView、CapabilityCostSummaryView |
| runtime / tools 实际外部调用实现 | 非范围 | P2 | 只验 hub 提供的 decision / contract / metadata,不验下游执行器实现 |
| provider 原始账单、KMS/Vault 产品本体 | 非范围 | P2 | 只验 capability-hub 的接缝与托管规则 |
| marketplace 交易 / 购买 / 计费逻辑 | 非范围 | P2 | 只验 metadata 分发接缝 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数与局部不变量 | domain / policy owner | `server.validate_registry_boundary`、`input.validate_decision_input`、`usage.validate_billable_usage`、`decision.validate_read_only_boundary` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + secret store + projection + publisher 联动 | backend / domain owner | `RegisterMcpServer`、`RegisterProvider`、`RefreshCapabilityDecision`、`RecordCost`、`RecordDeniedInvocation`、`GetCapabilityMetadata` | registry、contract、decision、cost、分发链同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | governance.policy.updated → decision refresh、decision → runtime/tools、cost/deny → observability/finance、metadata → marketplace | 输入输出语义一致 |
| 恢复专项测试 | 验证 secret 托管失败、policy 刷新滞后、cost backlog、runtime 绕过 hub 等异常链 | architecture / QA | secret fail、refresh stale、cost append fail、runtime bypass | 真相不丢失、错误被正确阻断或留证 |
| 投影一致性测试 | 验证 capability decision view / provider lookup / metadata / cost summary 与真相一致 | backend / QA | decision view rebuild、lookup rebuild、metadata rebuild、cost summary rebuild | 投影只读且与真相一致 |
| 端到端主线测试 | 验证最小能力接入闭环 | QA / owner | register provider → query allowlist → deny/allow → cost/audit output | 主干接入闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| `capability access ≠ capability execution` | hub 只给出 decision / contract view,不推进执行真相 | 单元 + 集成测试 | 是 | model review / negative flow |
| `MCP Registry ≠ ToolDefinition` | registry 只登记外部能力项,不定义工具语义本体 | 单元 + 集成测试 | 是 | payload compare / model review |
| `ProviderContract ≠ provider runtime` | contract 只表达接入合同和 secret ref,不执行 provider runtime | 单元 + 集成测试 | 是 | contract row / adapter trace |
| `CapabilityDecision ≠ runtime execution truth` | QueryCapabilities 只返回 allow/deny 结果,不写 runtime 状态 | 单元 + 集成测试 | 是 | decision snapshot / negative flow |
| `CostRecord ≠ provider raw billing source` | 成本记录是平台 append-only 记账记录,不等于 provider 原始账单 | 集成 + 恢复专项测试 | 是 | cost row / compare report |
| 明文 key 不落盘 | RegisterProvider / RotateProviderSecret 只保存 SecretEnvelopeRef | 集成 + 安全测试 | 是 | DB scan / secret adapter log |
| 未白名单调用必须拒绝 | deny-by-default 成立 | 集成 + 事件链测试 | 是 | denied audit / error response |
| Policy 刷新生效 | governance 更新后 QueryCapabilities < 30s 生效 | 事件链 + 集成测试 | 是 | refresh trace / decision compare |
| marketplace metadata 只读 | metadata 输出不能反写 registry / contract 真相 | 投影一致性测试 | 是 | metadata diff / negative flow |

## 6. 核心测试场景

| 场景 ID | 场景 | 前置条件 | 步骤摘要 | 预期结果 |
|---|---|---|---|---|
| TC-001 | RegisterMcpServer 成功登记 MCP 能力 | registry draft 合法 | RegisterMcpServer | MCPServer 创建成功 |
| TC-002 | A2A 匿名注册被拒绝 | auth_summary 缺失 | RegisterA2ANode | 返回 `A2A_NODE_ANONYMOUS_FORBIDDEN` |
| TC-003 | RegisterProvider 成功建立 provider 合同 | provider draft 合法 + secret store 可用 | RegisterProvider | ProviderContract 创建成功且只保存 secret ref |
| TC-004 | secret 托管失败时阻断合同落库 | KMS/Vault 返回失败 | RegisterProvider | 返回 secret 持久化错误 |
| TC-005 | RefreshCapabilityDecision 成功刷新 allow/deny 集合 | registry / contract / policy 完整 | RefreshCapabilityDecision | CapabilityDecision 更新成功 |
| TC-006 | shared_rules 禁止项不得被局部 allowlist 放开 | policy 冲突样本存在 | RefreshCapabilityDecision | deny 结果优先 |
| TC-007 | QueryCapabilities 高频读取只读决策视图 | decision snapshot 已存在 | QueryCapabilities | 返回 CapabilityDecisionView |
| TC-008 | RecordCost 成功追加平台成本记录 | provider usage 成功 | RecordCost | CostRecord 创建成功 |
| TC-009 | RecordDeniedInvocation 成功追加拒绝审计 | allow/deny 结果为 deny | RecordDeniedInvocation | DeniedInvocationAudit 创建成功 |
| TC-010 | provider 调用成功但成本记录失败进入 backlog | cost append fail | RecordCost | backlog / retry 证据生成 |
| TC-011 | marketplace metadata 只读输出成立 | registry / contract 已存在 | GetCapabilityMetadata | 输出 CapabilityMetadataView,不反写真相 |
| TC-012 | runtime 绕过 hub 直连 provider 被视为异常链 | direct provider config 样本存在 | negative flow / audit check | hub 无法放行且留审计告警输入 |

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|
| S | 未白名单能力被放行 / 明文 key 落盘 / CapabilityDecision 越界成执行真相 / 成本与审计完全失联 | 阻断放行,必须修复 |
| A | 主线可跑但 policy refresh、provider secret rotate、cost backlog、metadata 边界不稳 | 原则上修复后再放行 |
| B | 非关键统计、低优先级 metadata 视图或展示异常 | 可带风险进入下一轮 |

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 MCP / A2A registry,都必须回归 registry lifecycle 与白名单主线
- 每次改动 ProviderContract / SecretStore,都必须回归 secret 托管与 rotate 主线
- 每次改动 policy / shared_rules 刷新,都必须回归 QueryCapabilities 与 allow/deny 主线
- 每次改动 cost / audit 逻辑,都必须回归 append-only 记账与 deny 审计主线
- 每次改动 metadata / lookup / decision view,都必须回归只读视图边界主线

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| A2A 认证模型后续细化 | 测试矩阵需扩充 | TL / 架构 |
| LLM routing 未来并入 | access / contract 测试需增加更多样本 | capability-hub / runtime |
| 成本粒度从请求级演进到 token 级 | cost 测试与 finance 对账需扩充 | finance / platform |

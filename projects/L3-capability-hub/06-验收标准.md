  -> 02 概要 / component / object / flow grouping
  -> 03 详细 / exact type / protocol / state / TX / observation
  -> 04 配置 / profile / binding / activation / failure
  -> 05 测试 / TC-DS-EV / suite / gate / report contract
  -> 06 验收 / pass-fail / veto / risk / conclusion

| 来源 | 本文消费的内容 | 本文不承担的内容 |
|---|---|---|
| `00-需求文档.md` | 5 个 core closure、16 FR、37 BR、20 NFR、37 AC、13 VF、责任和数据红线 | 重新定义需求、优先级或验收项含义 |
| `01-架构设计.md` | bounded ownership、依赖方向、数据与安全红线、跨仓 seam | 选择具体产品、部署拓扑或外部系统实现 |

### 1.2 本文回答的问题

- 哪些 P0/P1/P2 能力和跨仓接缝进入本轮裁决。
- 哪个不可变 baseline、run、raw artifact、report 和 review 组合才具备验收资格。

### 1.3 本文不回答的问题

本文不重新定义需求、架构、对象、协议、状态、配置或测试用例；不安排实施 phase、代码任务、commit boundary、部署步骤或运维 runbook；不拥有 runtime execution、tools execution、governance approval truth、method body/source、marketplace listing/transaction、provider route/quota/cost、SDK client/cache 或 observability backend truth。

### 1.4 历史材料处理

旧版正式 `06-验收标准.md`、README 中的旧职责简写和无 provenance 的 API/DB/log/review 结果均为 `historical_material`。旧 `MCPServer`、`A2ANode`、`ProviderContract`、`CapabilityDecision`、`CostRecord`、allowlist/runtime truth、旧 P95/30s/99.9% 阈值和旧拓扑不通过改名、别名或局部迁移重新进入本文。

### 1.5 证据与执行事实边界

本文中的 `TC-CH-*`、`DS-CH-*`、`EV-CH-*` 是测试/数据/证据合同身份，不是已执行实例或别名。只有未来显式 `(run_id, EV-CH-*)` 通过同 run raw/report/digest、redaction、pairing、no-static 和授权 review 门禁后，才可作为对应验收项的证据输入。当前不声明任何真实执行事实。

## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收目标”“四层范围”“P0 scope matrix”“相邻系统接缝范围”“AC coverage partition”和“Veto scope”小节。

### 2.1 验收目标

本轮验收判断 Capability Hub 是否作为能力接入真相所有者闭合以下五个核心闭环：

| Core closure | 必须成立的结果 |
|---|---|
| `C-CH-1` 稳定身份 | 外部 MCP/A2A/API 能力形成稳定 `CapabilityIdentity`，后续语义围绕同一 identity 协作 |
| `C-CH-2` 受控目录 | `CapabilityRegistry` 管理 lifecycle、visibility 和 current/history 语义，不退化为 allowlist、cache 或 runtime state |
| `C-CH-3` 接入描述 | `AdapterDescriptor` 表达接入方式、能力类型、风险/约束和 safe reference，不保存 secret/provider runtime/cost truth |
| `C-CH-4` 治理/方法接缝 | governance result ref、access review fact 和 body-free method relation 可追溯，但 approval/Policy truth 和 method body 留在所属系统 |
| `C-CH-5` 受控消费表达 | formal exposure、visibility、consumer view、change/impact 和 SDK server boundary 可消费且不反写真相 |

### 2.2 P0/P1/P2 范围

| 层级 | 本轮含义 | 验收处理 |
|---|---|---|
| P0 | product-neutral formal semantics、truth/ownership、83 flows、638 pairs、strict config、safe observation、evidence integrity | 必须有完整门禁；任何失败或不可裁决均不能形成 P0 通过 |
| P1 | selected durable/external/source/route/TLS/observer parity 和跨仓真实接缝 | 按 immutable scope manifest 单独裁决；不可替代 P0 |
| P2 | production capacity、numeric SLO、multi-region、advanced discovery/UI、长期运维和未来演进 | 当前不形成通过声明；缺失必须保持 `not_claimed` 或 residual |

### 2.3 In scope

- capability identity、registry lifecycle/visibility、adapter descriptor、risk/constraint summary。
- governance/policy approval seam 的 typed relation/ref 和 access-review separation。
- method-library asset relation 的 body-free identity/ref 语义。
- formal exposure/visibility/applicability、controlled consumer view、traceability/impact。
- MCP/A2A/API external integration contract；不执行其 runtime invocation。
- SDK server exposure/ref boundary；不实现 SDK client、cache 或 language package。
- 250 protocol、36 Port、83 flow、24 state family、22 transaction/repository consistency 和 strict configuration contract。
- safe observation、audit carrier、test artifact/report/evidence provenance 和验收交接门禁。

### 2.4 Out of scope

| 非范围 | 所属责任 | 本文只做的边界检查 |
|---|---|---|
| runtime execution、tools execution、quota、route、result | runtime/tools 项目 | formal exposure、consumer ref、zero reverse-write |
| governance approval、Policy、shared rules | `L1-governance` | typed seam、safe summary、职责分离 |
| method body/source/publication/execution | `L3-method-library` | body-free asset relation |
| marketplace listing、ranking、pricing、transaction、fulfillment | marketplace owner | optional body-free relation，不纳入核心通过 |
| provider route、cost/billing、secret value、KMS/Vault truth | 外部 provider/secret/finance owner | descriptor/ref/safe failure/no-body |
| SDK client、cache、generated package、release | `L0-sdk` | server exposure boundary |
| observability backend、dashboard、retention、alert/runbook | observability/operations owner | safe projection、redaction、no business effect |

### 2.5 相邻接缝裁决

相邻系统只在本文声明的 typed interface、event、ref、snapshot、capture、consumer boundary 和 no-write/no-body 条件上被裁决。相邻系统内部不可用不会自动否定完整 P0 semantics；但若 immutable scope manifest 将其列为当前 required selected/release claim，则该层保持 `blocked_dependency`，不得被写成 passed，也不得用 P0 controlled run 补偿。

### 2.6 验收项覆盖分区

| AC 分区 | 数量 | primary 章节 |
|---|---:|---|
| `AC-CH-001..005` core closures | 5 | §5 |
| `AC-CH-006..021` FR capabilities | 16 | §5 |
| `AC-CH-022` peripheral isolation | 1 | §5 |
| `AC-CH-023..028` rules/boundary | 6 | §6/§7/§8 |
| `AC-CH-029..032` data ownership | 4 | §6 |
| `AC-CH-033..037` NFR | 5 | §9/§10 |
| **合计** | **37** | **孤儿 0** |

## 3. 验收基线

> 校准来源：
> - `design-calibration/06_acceptance_step_03_baseline.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收基线矩阵”“固定 artifact、report 与 acceptance 路径”“基线变化与新 run 规则”和“非法基线与无效化规则”小节，了解本章的 provenance 和分母约束。

### 3.1 必须冻结的基线

正式验收只能绑定一组不可变 source、delivery、configuration、environment、data 和 evidence manifest。下表中的“未建立”是当前设计期事实，不是通过或失败结果。

| 基线 | 必须冻结的内容 | 当前状态 | 缺失影响 |
|---|---|---|---|
| requirement/design | `00`~`05` source refs、design revision、calibration manifest | 文件已重建；送验 ref 未建立 | 不能开始真实验收 |
| implementation | implementation repository/ref、immutable source revision、build ID | 未建立 | 无送验对象 |
| core dependency | `L0-core`/`core-contracts` source ref 或 package version | 未建立 | dependency gate 未完成 |
| configuration | profile、entry、config artifact、config digest、activation result | 未建立 | 无法归因运行结果 |
| environment | environment ID、toolchain、adapter kind、scope manifest | 未建立 | P0/P1 适用性不可判定 |
| data | 189 DS manifest、fixture/replay root、seed/snapshot digest、cleanup result | 未建立 | 数据证据不可复验 |
| test run | 唯一显式 `run_id`、gate/suite/check manifest | 未建立 | 无 evidence instance |
| raw/report | raw digest、report digest、same-run pairing、report-generation audit | 未建立 | 证据链不可裁决 |
| review/handoff | acceptance handoff、VETO checklist、open issues、必要时 risk acceptance、review refs | 未建立 | 不能进入最终结论 |

### 3.2 Canonical denominator

| 维度 | 固定分母 | 验收约束 |
|---|---:|---|
| canonical test cases | 189 | 唯一 primary owner；缺失、额外、重复或跨 suite 重复均为 invalid |
| canonical test data | 189 | `TC -> DS -> EV` 一对一链；DS identity 不随环境改变 |
| formal evidence contracts | 189 | `EV-CH-*` 是合同；实际证据必须带 explicit `(run_id, evidence_id)` |
| state-pair registry | 638 | 24 families，`239 current + 98 reserved + 301 illegal`；禁止采样 |
| flows | 83 | `26 Command + 33 Query + 6 Inbound + 10 Outbound + 8 Job` |
| suites / gates / checks / builders | 10 / 5 / 9 / 4 | inventory 进入 run manifest；check 不增加 EV 分母 |
| acceptance consumers | 37 AC / 13 VF | AC primary coverage 37/37；VF non-waivable 13/13 |

任何分母、正式名称或 owner 差异必须回开对应的 `00`~`05` source Step。验收标准不能通过改写正文修复上游计数。

### 3.3 固定路径合同

| 用途 | 固定路径 | 最低要求 | 无效引用 |
|---|---|---|---|
| raw artifact | `artifacts/test/<run_id>/` | run manifest、case/suite/check raw、attempt history、digest、失败留证 | `latest`、项目名二级目录、跨 run 合并 |
| run report | `reports/runs/<run_id>/` | raw-derived summary、gate summary、suite/check reports、evidence index、redaction、dependency、report audit | `reports/<project>`、手工复制结果 |
| acceptance handoff | `reports/acceptance/handoff.md` | baseline、scope、explicit run IDs、失败/未覆盖项、review refs | 静态 passed 模板 |
| VETO checklist | `reports/acceptance/veto-checklist.md` | 每个 VF 和过程 VETO 的来源、证据方向、状态 | 空 checklist 默认通过 |
| risk acceptance | `reports/acceptance/risk-acceptance.md` | 仅 eligible residual、真实 acceptor、期限/触发、后续动作 | 设计期预填姓名或结论 |
| open issues | `reports/acceptance/open-issues.md` | defect、retest、blocked、dispute、residual、reopen | 只写“无问题” |
| review | `reports/review/reviewer-notes.md`、`agent-review.md` | 审查版本、引用、争议和 provenance | 无 run 的泛化评语 |

### 3.4 基线漂移与新 run

以下任何变化都必须重新固定受影响 manifest，并按 `05` 的 R0~R4 规则创建新 run 或重跑受影响范围：

- `00`~`06` 的 AC、VF、ownership、flow/state/TX/BIND/OBS 或 evidence schema 变化。
- implementation source、build、image/package、`core-contracts` 版本变化。
- profile、entry、config digest、fixture/replay root 或 dependency kind 变化。
- suite、gate、check、report builder、artifact schema 或 report schema 变化。
- selected P1 product、route、TLS、observer 或 release-required scope 变化。

旧 run 必须保留为 immutable historical material，不能被 retry pass、手工报告或新 run 覆盖。`latest`、隐式 current run、跨 run 拼接、无 digest pairing、静态 status map 和旧数字阈值均不能作为正式基线。

### 3.5 当前基线结论

当前只完成设计期 contract，尚未建立 delivery、environment、run、raw、report、review、risk 或 signoff 实例。因此当前验收状态是 `not_entered`，不是 `不通过`，也不是任何形式的“通过”。

## 4. 进入条件与退出条件

> 校准来源：
> - `design-calibration/06_acceptance_step_04_entry_exit.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收进入条件”“分层进入规则”“验收退出条件”“暂停、阻断与不可裁决矩阵”和“结论状态语义”小节。

### 4.1 进入条件

正式验收启动前，以下条件必须全部满足；勾选框是未来执行记录字段，当前不作任何勾选声明。

- [ ] `00`~`05` source refs、implementation source/build/image 和 `core-contracts` ref 已冻结。
- [ ] scope manifest 明确 P0 semantic、P1 selected、R4 release 和 P2 operations 的适用层。
- [ ] profile、entry、config artifact/digest、environment ID、fixture/replay root 和 dependency kind 已冻结。
- [ ] 唯一显式 `run_id` 已分配，raw root 精确为 `artifacts/test/<run_id>/`，且不存在预存输出。
- [ ] report root 精确为 `reports/runs/<run_id>/`，并由同 run raw 生成。
- [ ] 189 TC、189 DS、189 EV contract manifest 和 638 state-pair registry 已冻结。
- [ ] 所有适用 P0 suite/check 有 raw-derived result 或明确的 non-pass raw；不得缺 cell 后人工补表。
- [ ] redaction、dependency、responsibility、report-generation 和 artifact/report pairing checks 有可追溯入口。
- [ ] `reports/acceptance/handoff.md`、`veto-checklist.md`、`open-issues.md` 已引用同一 baseline/run；只有 eligible residual 才要求 risk acceptance。
- [ ] confirmed S、当前 P0 A、design blocker、P0 prerequisite 和 invalid artifact 均已清零或被明确阻断。

### 4.2 分层进入规则

| 层级 | 进入条件 | 缺失时状态 | 是否可补偿其他层 |
|---|---|---|---|
| P0 semantic | 189 contract manifest、638 registry、P0 profiles、main suites/checks、同 run roots齐备 | `not_entered` 或 `blocked_dependency` | 不可由 P1/R4 补偿 |
| P1 selected | immutable selected product/config/TLS/source/route/observer manifest、typed unavailable/failure、cleanup proof | `selected_blocked` | 不改写 P0 |
| R4 release | P0 main、release-required selected refs、release smoke、9 checks、report/handoff/review | `release_not_eligible` | 不产生 acceptance verdict |
| P2 operations | 后续正式 operations baseline、numeric target、capacity/retention/production evidence | `not_claimed` | 不影响当前 P0 |

`not_applicable_by_manifest` 只有在 immutable scope manifest 明确证明不适用时才成立。缺产品、缺环境或缺证据不能自动转换为该状态。

### 4.3 退出条件

P0 semantic exit 必须同时满足：

- 37 个 AC 均有唯一 primary owner，且每项结论能回指正式设计、TC/DS/EV、same-run raw/report 和裁决影响。
- 13 个 VF 均有非空 negative evidence direction，且没有未处理的 VETO finding。
- 189/189/189 合同和 638/638 state pairs 完整；无 missing、duplicate、orphan、unclassified 或 sampling。
- 10 个 primary suites 和所有适用 main checks 的 raw-derived worst status 均满足要求；任一 non-pass 阻断。
- typed terminal、zero-effect、Query no-write、Job no-truth-repair、strict config、Rustdoc、redaction、dependency 和 responsibility gates 有证据。
- open S、当前 P0 A、design blocker、P0 prerequisite、invalid artifact 为 0。
- 无 active numeric threshold 时，性能/容量等数值只保留 `not_evaluated`，不得伪造数值通过。

### 4.4 暂停、阻断与不可裁决

| 触发条件 | 状态 | 处理 |
|---|---|---|
| baseline、scope 或 run 未冻结 | `not_entered` | 补 manifest；不启动验收 |
| raw/report 路径错误、digest 缺失、跨 run 拼接 | `invalid_artifact` | 保留材料；新 run 或重建 report |
| suite/check/evidence cell 缺失 | `not_decided` | 不得用 aggregate count 补齐 |
| required P0 dependency unavailable | `blocked_dependency` | 保留 typed reason；不能标 passed |
| redaction/dependency/report audit failed | `failed` / `blocked` | 修复并按影响面复验 |
| VF、S 或 current P0 A 存在 | `failed` | 不可风险接受；修复后 distinct retest |
| source/config drift | `paused` | 旧 run 转历史；新 baseline/new run |
| design oracle 无法绑定正式字段/状态/flow | `design_blocker` | 回开 owning design Step |

### 4.5 结论状态词

`passed`、`failed`、`blocked_dependency`、`invalid_artifact`、`not_evaluated` 和 `not_decided` 是证据/门禁状态，不是总体结论。总体结论只在 §14 使用 `通过`、`有条件通过` 或 `不通过`；缺输入或缺授权审查时内部保持 `paused/not_decided`。

## 5. 功能验收门禁

> 校准来源：
> - `design-calibration/06_acceptance_step_05_function_gate.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“五个核心闭环功能门禁”“FR-CH-001..016 功能验收门禁”“外围增强隔离门禁”“证据选择与公共 pass/fail 规则”和“跨功能门禁裁决审计”小节。

### 5.1 公共功能门禁合同

每条功能验收项必须满足以下闭环：

```text
AC-CH-* -> formal 03 contract -> TC-CH-* / DS-CH-* / EV-CH-*
        -> artifacts/test/<run_id>/... -> reports/runs/<run_id>/...
        -> pass/fail/blocked -> verdict impact
```

通过条件是：正式设计字段、状态、owner、effect、版本/幂等规则和负向分支全部有对应 raw-derived evidence；失败条件包括 selector 缺失、名称漂移、非法输入静默接受、禁止副作用、证据不完整或责任越界。日志文本、Debug/Display、mock count 或报告存在本身不能替代业务 oracle。

### 5.2 核心闭环门禁

| 验收项 | 核心闭环与正式契约 | TC/DS/EV selector | 通过条件 | 失败条件 | 结论影响 |
|---|---|---|---|---|---|

> - `design-calibration/06_acceptance_step_11_veto.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“13 个正式 VF 一对一 VETO 表”“过程硬红线 VETO 表”“VETO 闭环矩阵”“一票否决项停审记录”和“跨 VETO 覆盖审计”小节。

任一 VETO 命中时，总体结论不得为“通过”或“有条件通过”。VETO 不得由风险接受、P1/P2 证据、release smoke、人工口头说明或签署覆盖。缺少 VETO 证据不是“未命中”，而是不可裁决/阻断。

### 11.1 需求与架构红线 VETO

| VETO | 否决条件 | 最低检查/证据方向 | 触发影响 |
|---|---|---|---|
| `VETO-CH-001` | 五个 core closure 任一无法成立 | AC-CH-001..005、FOUNDATION/CMD/STATE/TX evidence | 直接不通过 |
| `VETO-CH-002` | identity 被 URL/provider/config/SDK/listing/derived 替代 | AC-CH-001/006/007、identity negative cases、redaction | 直接不通过 |
| `VETO-CH-003` | registry 退化为 allowlist/runtime/cache/listing/provider availability | AC-CH-002/009..011、STATE/TX/QUERY | 直接不通过 |
| `VETO-CH-004` | descriptor 保存 secret 或 provider runtime/quota/route/cost/failover/retry truth | AC-CH-003/012..014/032、OBS/CONFIG | 直接不通过 |
| `VETO-CH-005` | Hub 生成/保存 governance approval、Policy/shared rules，或 review 替代 approval | AC-CH-004/015/016/027、INBOUND/OBS | 直接不通过 |
| `VETO-CH-006` | method relation 保存 method body/source/正文版本或执行定义 | AC-CH-004/017、STATE/INBOUND/redaction | 直接不通过 |
| `VETO-CH-007` | runtime/tools/SDK/product/query/export/event/job 反写 identity、registry、descriptor、seam、relation、exposure | AC-CH-005/019/021/024/028、TX/no-write | 直接不通过 |
| `VETO-CH-008` | draft/candidate/undescribed/ungoverned/incomplete 能力被正式暴露或消费 | AC-CH-005/010/020、STATE/NFR | 直接不通过 |
| `VETO-CH-009` | 关键 identity/registry/descriptor/seam/relation/exposure/impact 变化不可追溯 | AC-CH-018/021/025/036、trace/capture/evidence | 直接不通过 |
| `VETO-CH-010` | duplicate proposal/discovery/feedback/job 产生 duplicate truth、split descriptor 或 split exposure | AC-CH-002/006/011/021、IDEM/TX/STATE | 直接不通过 |
| `VETO-CH-011` | cost/billing、observer store、marketplace transaction/listing 或 production request/response body进入 Hub truth | AC-CH-003/024/031/032/035/037、redaction | 直接不通过 |
| `VETO-CH-012` | 非 `L0-core/core-contracts` sibling 成为源码级 owner/compile dependency | AC-CH-026、dependency-boundary、static contract | 直接不通过 |
| `VETO-CH-013` | 旧 `QueryCapabilities`、Policy 30s、旧百分比/P95/SLA、CostRecord/KMS/Vault等 historical 口径回流为新版主线 | AC-CH-023/033、source audit、README/formal scan | 直接不通过 |

### 11.2 过程与证据真实性 VETO

| VETO | 否决条件 | 最低检查/证据方向 | 触发影响 |
|---|---|---|---|
| `VETO-CH-P-001` | canonical 189 TC/DS/EV、638 pairs、83 flows、37 AC 或 13 VF 缺失、重复、孤儿或被改分母掩盖 | manifest equality、case/pair audit、evidence index | 不通过/不可裁决 |
| `VETO-CH-P-002` | raw/report/evidence 使用 `latest`、错误 root、跨 run 拼接或 digest mismatch | report-audit、path/digest checks | 不通过 |
| `VETO-CH-P-003` | static JSON/Markdown、手工 status map 或空模板伪造 passed/evidence/VETO | no-static、generation provenance、review audit | 不通过 |
| `VETO-CH-P-004` | failed/timeout/invalid raw 被删除、覆盖或由 retry pass 替换 | immutable artifact/attempt history、distinct run audit | 不通过 |
| `VETO-CH-P-005` | redaction scan 发现 secret/body/full sensitive ref，或 finding 回显原文 | artifact/report redaction check | 不通过 |
| `VETO-CH-P-006` | dependency/responsibility/report audit 缺失或被人工“clean”覆盖 | check raw/report pairing | 不通过 |
| `VETO-CH-P-007` | P0 config/profile 缺失、silent fallback、partial activation、forbidden override 或 unavailable 标 passed | configuration-strict、binding、activation barrier | 不通过 |
| `VETO-CH-P-008` | Query/Job/derived/report/consumer 发生 reverse write、truth repair 或 observer 改变业务结果 | zero-write/no-repair/TX/OBS evidence | 不通过 |
| `VETO-CH-P-009` | accepted truth 缺 source/version/trace/history/capture/stored result，或 duplicate/commit-unknown 造成第二次 mutation | state/TX/idempotency/report audit | 不通过 |
| `VETO-CH-P-010` | handoff/review/risk/signoff 缺真实 provenance、责任域或授权主体，或签署批量接受未列风险 | acceptance/review schema and authorized record | 不通过/不可裁决 |

### 11.3 VETO 共同规则

VETO 检查必须逐项有 formal source、TC/DS/EV 或 check direction、raw/report path 和状态。`not_evaluated`、missing、blocked、invalid 或 evidence gap 不能计为“未命中”。VETO 的失败集合只要非空，总体结论即为 `不通过`；若无法判断是因为缺 baseline/evidence/review，则内部保持 `paused/not_decided`，完成输入后仍须重新裁决。

## 12. 缺陷分级、复验与放行规则

> 校准来源：
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“观察分类”“S/A/B/R 分级表”“R0~R4 复验层级”“immutable impact manifest”“复验触发矩阵”“关闭证据合同”和“跨规则审计”小节。

### 12.1 观察分类先于缺陷分级

| Observation class | 判定 | 验收处理 |
|---|---|---|
| `OBS-CLASS-IMPLEMENTATION` | valid baseline/case/data/harness 下违反 formal `00~04` oracle | 进入 S/A/B 分级，修复并复验 |
| `OBS-CLASS-TEST-SYSTEM` | manifest、fixture、runner、check、report builder 或 evidence generator 错误 | 保留 non-pass raw，修测试系统；不能产生产品 pass |
| `OBS-CLASS-DESIGN-BLOCKER` | source 矛盾、缺 canonical oracle、义务不能一一映射 | 暂停 affected scope，回开 owning design Step |
| `OBS-CLASS-PREREQUISITE` | implementation repo、core dependency、selected product、环境、配置或授权不可用 | `blocked_dependency`；不能转成普通 B |
| `OBS-CLASS-NUMERIC-SAMPLE` | 有数值样本但没有 active threshold | 保留 provenance；numeric=`not_evaluated`，不是 defect |
| `OBS-CLASS-EXPECTED-ORACLE` | 预期 unavailable/timeout/error 完全符合 typed oracle、zero-effect 和 cleanup | 该 negative case 可 passed，不扩大为环境总体通过 |
| `OBS-CLASS-INCOMPLETE-RUN` | cancel、unexpected timeout、缺 cell、raw/report 失败或根因未定 | 保留 partial raw；保持 non-pass/not_decided |

无法复现不改变已有 valid failure 的事实；失败 raw/report 不得被 retry pass 覆盖。

### 12.2 S/A/B/R 分级

| 级别 | 定义 | 典型触发 | 结论影响 | 关闭要求 |
|---|---|---|---|---|
| `S` | 任一 VETO，或 truth/security/ownership/evidence/config hard redline | forbidden body/secret、reverse write、second truth、static evidence、dependency越界、silent fallback | 只能 `不通过` 或暂停；不可风险接受或有条件通过 | 修复后新 run；原 case、同 family、affected suite/check/audit，按触发条件 R2/R4 |
| `A` | current P0 canonical contract、typed oracle、state/TX/config/observation/Rustdoc 或 blocking proof 失败但未命中 S | wrong typed outcome、pair缺失、P0 profile缺失、Rustdoc omission、P0 report cell不可证明 | P0 exit/handoff 前必须修复复验；不得作为当前 residual 接受 | 原 case/parameter、primary suite、affected checks/reports；影响不明默认 R2 |
| `B` | 已确认 non-P0、P1 selected、报告可读性或维护性问题，无 P0/VF/evidence/provenance 影响 | 非 release-required selected parity、safe wording/ergonomics、非阻断 report issue | 可作为有条件通过候选，但必须进入 §13 的真实 risk record | 按 impact manifest 做 R1/R3 或补充 review；真实接受后才可放行 |
| `R` | 当前范围外、future、生产运维政策、容量/SLO、vendor 深层行为或未选产品残余 | production-like capacity、retention/alert/runbook、future schema | 不改变 P0；不能被写成已验证，是否接受遵循 §13 | 明确 owner、trigger、follow-up；升级范围时重新 baseline |

S、当前 P0 A、VETO、P0 evidence integrity、redaction、dependency/responsibility、strict-config hard failure 和设计/P0 prerequisite 永远不能降级为可接受 residual。

### 12.3 R0~R4 复验层级

| 层级 | 目的 | 必须包含 | 可以证明 | 不能证明 |
|---|---|---|---|---|
| `R0-targeted-diagnostic` | 精确重现/归因 | exact TC/DS/EV、parameter、safe raw attempt | 单参数诊断 | family、P0 完整性或放行 |
| `R1-minimum-change` | 覆盖有界变更和直接消费者 | immutable impact manifest、changed cases、same family、primary/consumer suites、checks/reports | 有界相邻面未破坏 | 完整 P0 denominator，除非恰好等于 R2 |
| `R2-full-main` | 重建 product-neutral P0 baseline | 10 suites、189 TC/DS/EV、638 pairs、9 checks、raw/report/provenance | P0 semantic exit 必要测试条件 | selected parity、release 或最终 acceptance |
| `R3-selected-integration` | 验证 manifest 选定产品/adapter/config/TLS/observer | selected manifest、exact subset、typed unavailable/failure、cleanup、独立 raw/report | selected claim（仅适用时） | P0 substitute；unavailable 不能变 pass |
| `R4-release-requalification` | 形成 release/handoff 下游资格 | compatible lower refs、release checks/smoke、report/evidence/review-ready handoff | release evidence readiness | 自行生成 acceptance verdict、risk acceptance 或 signoff |

R0/R1 不能缩小 R2；R3 不能补偿 P0；R4 不能自行生成 acceptance verdict。任何 source/config 在 run 开始后漂移，旧 run 失去 current eligibility，必须建立新 baseline/run，旧 raw/report 仍保留历史。

### 12.4 Immutable impact manifest 与复验触发

每个修复或变更在执行前必须冻结 `change_id`、formal source refs、changed files/surfaces、affected AC/VF、TC/DS/EV、primary suites、checks、evidence/report impact、rollback/pause rule 和 regression level。以下变化至少触发 R2：

- shared protocol/DTO/codec、public field/enum/variant/Rustdoc、state generator/transition、repository authority/UoW/CAS/idempotency。
- Command/Query/Inbound/Outbound/Job shared mapper、error taxonomy、config graph/profile/activation、redaction/dependency/responsibility/evidence builder。
- 影响多个 truth owner、多个 suite、全量 state pair 或 evidence denominator 的任何 change。

release-required scope 的变化还必须运行 R4；selected product、TLS、route 或 observer 的变化按 manifest运行 R3。影响不明时默认扩大，不得选择最小复验规避风险。

### 12.5 放行规则

| 条件 | 是否允许放行 |
|---|---|
| 任一 VETO 或未关闭 S | 否 |
| 任一 current P0 A、P0 evidence integrity、redaction、dependency、responsibility 或 strict config hard failure | 否 |
| P0 required cell 缺失、blocked_dependency 或 invalid_artifact | 否/不可裁决 |
| 仅有合格、已授权的 B/R residual，且 P0 主线完整 | 可进入有条件通过候选；最终结论依 §13/§14 |
| P1 selected unavailable 且 manifest 明确非当前 required claim | 不影响 P0；selected 维度保留 residual |
| P1 selected unavailable 但 release manifest required | 否；保持 `blocked_dependency` |
| 仅有 numeric sample 且无 threshold | 不形成 numeric pass；按 residual 处理 |
| evidence/report 由静态文件、人工汇总或 cross-run 生成 | 否 |

### 12.6 关闭证据合同

S/A 关闭必须包含 defect reference、级别/归因理由、失败前 `run_id`、失败 raw/report、修复说明、新 distinct retest `run_id`、复验 suite/check/report、关联 `TC/DS/EV`、AC/VF、digest/pairing/redaction/no-static 和防回归说明。B/R 至少包含影响面、owner、后续动作、deadline/trigger、follow-up 和真实 review；缺字段不能作为放行依据。

## 13. 风险接受与遗留项

> 校准来源：
> - `design-calibration/06_acceptance_step_13_risk_acceptance.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“风险状态与资格模型”“eligible residual predicate”“可接受风险分类”“当前 16 项风险登记”“不可风险接受矩阵”“风险接受记录合同”和“后续同步矩阵”小节。

### 13.1 风险状态

| 状态 | 条件 | 是否支持有条件通过 |
|---|---|---:|
| `not_eligible` | 设计债务、实现前置、formal 文档缺失、责任未定、缺 oracle | 否 |
| `pending_not_accepted` | selected/operations/future residual已识别但证据或授权不完整 | 否 |
| `eligible_for_review` | 真实 evidence、归因完成、影响有界、无 VETO/S/P0-A/P0 evidence impact | 仅进入审查 |
| `accepted_residual` | eligible 且有授权 acceptor、理由、期限、follow-up、provenance | 是，但仅影响该 residual |
| `rejected_or_blocked` | 命中不可接受项、字段缺失、证据 invalid 或影响不明 | 否 |
| `expired_or_reopened` | trigger/deadline 到期、source drift、影响扩大或复验失败 | 否，须重新审查 |

当前 `accepted_residual = 0`。设计期风险行不是实际 acceptance record。

### 13.2 Eligible residual predicate

未来风险只有同时满足下列条件才可进入 `eligible_for_review`，全部真实授权完成后才可成为 `accepted_residual`：

```text
real_observation_or_prerequisite_record
AND classification_is_eligible
AND bounded_formal_impact
AND p0_contamination_check == no
AND veto_set == empty
AND open_S == 0
AND open_current_P0_A == 0
AND evidence_provenance_complete
AND owner_present
AND acceptor_present
AND deadline_or_trigger_present
AND follow_up_ref_present
AND authorized_review_provenance_present
```

### 13.3 可接受风险类别

| 类别 | 示例 | 可接受前提 | 当前状态 |
|---|---|---|---|
| `B-non-P0` | 不影响 P0 truth/provenance 的维护性或呈现问题 | real evidence、bounded impact、follow-up | 未接受 |
| `P1-selected-unavailable` | 非 required 的 adapter/source/route/TLS/observer parity | P0 独立成立且 manifest 明确非 required | 未接受；required 时 blocked |
| `P2-operations` | dashboard、retention、runbook、capacity policy | 不冒充当前 P0/release claim | 未接受 |
| `numeric-not-evaluated` | 有 sample/trend 但无 active threshold | 只保留 provenance，后续建立阈值 | 不形成 numeric pass |
| `future-evolution` | v1 后 schema/consumer/dynamic control | 明确 scope 外并设重开 trigger | 未接受 |
| `cross-repo-E2E` | 未锁定的真实跨仓联调 | current seam/no-write/ownership不受影响 | 未接受 |

以下项目即使有 acceptor 也不可接受：任一 VETO、S、current P0 A、design contradiction、P0 prerequisite absence、forbidden body/secret、dependency/responsibility failure、static/raw-less/cross-run evidence、P0 denominator 缺失、P0 config hard failure、fake review/signature 或 impact unknown。

### 13.4 当前风险登记

承接 `05_test_plan_step_14_regression_risks.md` 的 16 个 canonical risk IDs：`CH-TEST-R01..R16`。当前全部保持 `not_eligible` 或 `pending_not_accepted`，`accepted=0`。其中实现仓/Cargo/workspace、gate/check/report harness、formal 07/implementation ledger 属实施前置；selected product、observer、numeric threshold、retention、运维政策和未来 schema 属 selected/P2/future residual；README 污染属于边界审计事项。本文不创建 owner、acceptor、deadline、run 或 evidence 实例。

### 13.5 风险记录字段

未来 `reports/acceptance/risk-acceptance.md` 每条记录必须包含：

| 字段组 | 必填内容 |
|---|---|
| identity/source | `risk_id`、`source_ref`、exact `00~06`/TC/DS/EV/AC/VF refs |
| scope/classification | scope、S/A/B/R、observation class、eligible 状态 |
| impact | P0/selected/release/operations 影响、`p0_contamination_check` |
| evidence | baseline ref、failed/retest run（如适用）、raw/report/digest/pairing/redaction/no-static |
| decision | acceptance reason、mitigation、reopen trigger、status |
| accountability | owner、acceptor、deadline_or_trigger、review_point、follow_up_ref |
| provenance | authorized review、decision provenance、实际时间/签署；设计阶段为空 |

缺 `acceptor`、deadline/trigger、follow-up、evidence 或授权 provenance 时，不能支持有条件通过。最终签署不自动批量接受未列风险。

### 13.6 风险对结论和下游的影响

| 风险状态 | P0 semantic | selected/release | 总体结论 |
|---|---|---|---|
| `not_eligible` / `pending_not_accepted` | 涉及 P0 时阻断；不作为放行依据 | 对应层 blocked/not-decided | 不能支持有条件通过 |
| `eligible_for_review` | 等待授权，不产生通过 | 等待授权或 blocked | `not_decided` |
| `accepted_residual` 且无 P0/VF/evidence impact | 不否定独立 P0 exit | 依 manifest 和记录 scope | 可作为有条件通过候选 |
| 任一 VETO/S/P0-A | 阻断 | 阻断 | `不通过` 或暂停 |
| invalid/missing/cross-run evidence | 阻断 | 阻断 | 不可裁决或不通过 |

实现/测试 tooling 风险必须同步 `07` boundary、implementation ledger 和 issue；配置/selected/运维/跨仓/future 风险必须同步对应 manifest、ADR、后续文档或受控 reopen，不能只存在于验收报告。

## 14. 最终结论与签署

> 校准来源：
> - `design-calibration/06_acceptance_step_14_final_decision_signoff.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“最终结论定义”“分层准入矩阵”“结论判定矩阵”“最终验收包与固定入口”“签署角色与责任合同”和“签署含义与风险接受分离”小节。

### 14.1 三值总体结论

最终总体结论只允许：

- `通过`
- `有条件通过`
- `不通过`

禁止“基本通过”“原则通过”“大体没问题”“待观察通过”等模糊词。缺 baseline、run、raw/report、evidence、design oracle、review provenance 或授权签署时，内部状态只能是 `paused/not_decided`，不能映射为通过或有条件通过。

### 14.2 结论判定矩阵

| 条件 | 通过 | 有条件通过 | 不通过/暂停 |
|---|---|---|---|
| P0 functional/data/interface/state/NFR | 全部适用且 raw-derived 通过 | 同左 | 任一失败、缺失或不可裁决 |
| `VETO-CH-001..013`、`VETO-CH-P-001..010` | 全部未命中且证据完整 | 全部未命中且证据完整 | 任一命中、缺证据或状态不明 |
| open S | 0 | 0 | >0 |
| current P0 A | 0 | 0 | >0 或未完成复验 |
| evidence integrity | same-run、digest、redaction、pairing、no-static clean | 同左 | missing/orphan/static/cross-run/digest mismatch |
| dependency/responsibility/config | clean、strict、无 silent fallback | 同左 | 任一 hard failure |
| B/R residual | 无，或不影响当前 claim | 每项已真实接受且字段完整 | 未记录、未接受或影响不明 |
| selected unavailable | 不适用或 manifest 排除 | eligible residual 且非 required | required selected unavailable |
| release/handoff/review | 另行满足 R4/handoff；不由 P0自动推断 | 同左 | 缺 required ref/check/report/review |

`通过` 与 `有条件通过` 都要求 P0 主线真实可裁决；设计期静态 `pass-designed` 不满足此矩阵。

### 14.3 分层准入

| 层级 | 必须具备 | 允许状态 | 不足时 |
|---|---|---|---|
| P0 semantic exit | immutable baseline、189 contract/instance chain、638 pairs、10 suites、9 checks、VETO/S/P0-A closure | `eligible_for_decision` | blocked/not_decided |
| selected integration | P0 exit、selected manifest、R3 raw/report、typed unavailable/failure、cleanup | `selected_ready` | `selected_blocked` |
| release requalification | compatible R2、required R3、R4 smoke/check/report/handoff/review | `release_ready` | `release_not_eligible` |
| acceptance handoff | handoff、VETO checklist、open issues、必要 risk acceptance、review provenance | `handoff_ready` | `not_decided` |
| final decision | handoff ready、责任角色核对、risk set一致 | 三值结论之一 | `paused/not_decided` |

R4 只能证明 release evidence readiness，不能自行产生 acceptance verdict；签署也不能替代缺失 evidence 或 risk record。

### 14.4 最终验收包

真实验收包至少包含：

- `reports/runs/<run_id>/summary.md`
- `reports/runs/<run_id>/gate-summary.md`
- `reports/runs/<run_id>/evidence-index.md`

### 14.5 签署责任合同

组织可以由同一主体承担多个角色，但六类责任域不能省略；实际姓名、时间、结论和签名在真实流程填写，当前为空。

| 角色责任域 | 必须确认 | 不得代表 |
|---|---|---|
| Owner / 业务 | 目标、范围、P0/P1/P2业务影响、已接受 residual 和下一阶段影响 | 技术 evidence、架构边界或他人风险接受 |
| 架构负责人 | identity/registry/descriptor/seam/relation/exposure ownership、依赖裁剪、VETO | runtime/tools execution、governance approval、provider cost |
| 测试负责人 | 189 TC/DS/EV、10 suites、638 pairs、checks、raw/report pairing、defect/retest | 产品修复或风险接受 |
| 实施负责人 | source/build/config、实现范围、技术风险、rollback/pause、follow-up | 测试通过、架构批准或业务接受 |
| 运维/安全/合规 | profile/entry、redaction、dependency、evidence access/retention policy、handoff | 修改 Hub truth、代替 governance 或业务签署 |
| 验收负责人 | scope、baseline、P0/VETO、risk/open issues、review refs 与结论一致 | 创造 evidence、替代专业签署、批量接受风险 |

签署记录至少包含 `role`、`person_or_account`、`scope_confirmed`、`baseline_refs`、`decision_value`、`open_issue_refs`、`risk_refs`、`review_ref`、`signed_at` 和 `signature_or_attestation`。设计阶段所有实际值为空；签署不自动接受未列风险。

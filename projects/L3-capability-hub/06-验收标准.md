### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L3-capability-hub` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L3-capability-hub` 是能力接入中心,不是工具执行仓、provider 本体仓或市场交易仓
- registry / directory / provider contract 构成正式接入真相层
- `capability access ≠ capability execution` 必须成立,hub 只做接入控制和分发,不推进运行执行主线
- `MCP Registry ≠ ToolDefinition`、`ProviderContract ≠ provider runtime`、`CapabilityDecision ≠ runtime execution truth`、`CostRecord ≠ provider raw billing source` 等核心边界必须成立
- QueryCapabilities 必须在 policy / shared_rules 刷新后稳定生成新的 allow/deny 结果
- secret 托管必须严格通过 KMS/Vault 接缝完成,明文 key 不得落盘
- 外部调用成功/失败都必须进入 cost / deny / audit 记录主链
- marketplace / observability / finance 消费的都必须是只读视图或 append-only 记录,不能反写真相

因此,本次验收的目的不是笼统判断“能不能登记外部 provider”,而是判断 capability-hub 的 registry 主线、secret 托管主线、policy-aware access 主线、cost/audit 主线与只读分发出口主线是否真的成立,是否可作为后续阶段的稳定基线。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| 能力注册与目录部分 | 是 | MCPServer、A2ANode、RegistryLifecycleState、RegistryHealthSnapshot |
| Provider 合同与密钥托管接缝部分 | 是 | ProviderContract、SecretEnvelopeRef、ProviderQuota、ProviderRouteRule |
| 能力可见性与访问裁决部分 | 是 | CapabilityDecision、CapabilityDecisionInput、SharedRuleSnapshot、AllowDenyEntry |
| 成本记账与审计事件部分 | 是 | CostRecord、DeniedInvocationAudit、CapabilityAuditEntry、CostEventMaterial |
| 下游消费与分发出口部分 | 是 | CapabilityDecisionView、ProviderLookupView、CapabilityMetadataView、CapabilityCostSummaryView |
| runtime / tools 实际外部调用实现 | 否 | 只验 hub 提供的 decision / contract / metadata,不验下游执行器实现 |
| provider 原始账单、KMS/Vault 产品本体 | 否 | 只验 capability-hub 的接缝与托管规则 |
| marketplace 交易 / 购买 / 计费逻辑 | 否 | 只验 metadata 分发接缝 |

## 4. 功能验收门禁

| 功能/场景 | 门禁条件 | 证据 | 结论 |
|---|---|---|---|
| RegisterMcpServer / RegisterA2ANode | 合法输入时必须形成正式 registry / directory truth | API 响应 / DB 记录 / trace | [] |
| Registry 边界 | registry 只登记外部能力项,不得混入 ToolDefinition 或 runtime 执行状态 | model review / negative flow / payload compare | [] |
| RegisterProvider | secret 托管成功后必须形成正式 ProviderContract,且只保存受控引用 | contract row / secret store log | [] |
| Secret 托管边界 | Provider key 不得明文落盘,托管失败时不得保存合同 | DB scan / negative test / secret adapter trace | [] |
| RefreshCapabilityDecision | governance 规则变化后必须形成新的 allow/deny 决策快照 | decision snapshot / refresh log | [] |
| Access 决策边界 | shared_rules 禁止的能力不得被局部 allowlist 放开,CapabilityDecision 不得冒充 runtime execution truth | compare report / negative flow | [] |
| QueryCapabilities | runtime / tools 必须只能读到只读 capability decision view | decision view / response snapshot | [] |
| RecordCost | 成功调用必须形成正式 CostRecord | cost row / append log | [] |
| RecordDeniedInvocation | deny 结果必须形成 DeniedInvocationAudit | denied audit row / event log | [] |
| Cost / audit 边界 | CostRecord 只能表示平台侧记账真相,不得由 provider 原始账单或 runtime 业务日志替代 | compare report / model review | [] |
| GetCapabilityMetadata / GetProviderLookup | marketplace / runtime / tools / finance 消费的必须是只读视图或元数据输出 | projection snapshot / response log | [] |
| Metadata / lookup 边界 | metadata / lookup 不得反写 registry / contract 真相,也不得表达 marketplace 交易状态 | negative flow / diff report | [] |

## 7. 安全与治理门禁

| 门禁项 | 要求 | 证据 | 结论 |

| deny-by-default 不可绕过 | 未白名单能力不得被放行 | denied audit / security regression | [] |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | 未白名单能力被放行 / 明文 key 落盘 / CapabilityDecision 越界成执行真相 / 成本与审计完全失联 |
| A | 视情况 | 主线可跑但 policy refresh、provider secret rotate、cost backlog、metadata 边界不稳 |
| B | 可带着走 | 非关键统计、低优先级 metadata 视图或展示异常 |

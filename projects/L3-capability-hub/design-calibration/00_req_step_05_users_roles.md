## 3. SOP 问题回答

### 3.1 本仓有哪些主要角色？

`L3-capability-hub` 的主要角色不是相邻仓名称,而是会直接发起、管理、审查、查看或系统性消费“能力接入事实”的身份。当前可收敛为以下角色:

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 能力接入管理员 | 人类管理角色 | 维护外部 MCP / A2A / API 能力进入正式接入语境所需的注册、描述、可见性和生命周期管理语境。 |
| 能力接入提议者 / 技术负责人 | 人类协作角色 | 提出新外部能力接入、能力描述调整或接入范围变更的业务 / 技术语境,供后续审查和治理接缝使用。 |
| 安全 / 接入审查者 | 人类审查角色 | 从安全、外部连接、身份可信、接入约束和治理接缝角度审查能力能否进入正式接入语境。 |
| 审计 / 合规查看者 | 人类审计角色 | 查看能力身份、注册目录、接入描述、治理引用和历史变更线索,确认能力接入事实可解释、可追溯。 |
| 能力目录浏览者 | 人类只读角色 | 在管理或生态入口中理解哪些外部能力已处于正式接入语境,以及其基本描述和适用边界。 |
| 系统消费方 | 系统角色 | 以受控方式消费能力身份、注册目录、接入描述或接缝摘要,用于自身运行、展示或封装语境;具体消费仓后移 Step 6。 |
| 能力接入维护任务 | 系统维护角色 | 执行能力目录派生、索引重建、一致性检查、历史对账或可见性刷新等维护语境,但不创造新的业务接入结论。 |

`runtime`、`tools`、`governance`、`SDK`、`marketplace` 以及具体外部 provider 都不在本章写成角色。它们是 Step 6 / Step 12 要裁剪的使用方、依赖或外部协作边。

### 3.2 哪些是人类角色,哪些是系统角色？

人类角色包括能力接入管理员、能力接入提议者 / 技术负责人、安全 / 接入审查者、审计 / 合规查看者、能力目录浏览者。系统角色包括系统消费方和能力接入维护任务。

这里不额外引入“平台成员角色”一层,因为 capability-hub 的核心不是成员身份治理,而是能力接入事实治理。谁是成员、成员具备什么身份和正式角色定义,仍由 `L1-identity` 与 `L3-method-library` 承接。

### 3.3 这些角色分别在什么场景下接触本仓？

| 角色 | 典型接触场景 | 本步边界 |
|---|---|---|
| 能力接入管理员 | 维护 capability identity、registry 和 adapter descriptor 的正式接入语境 | 不写管理接口、字段、状态机或存储实现 |
| 能力接入提议者 / 技术负责人 | 在业务 / 技术语境中提出新外部能力接入或能力接入变更 | 不写提议流程、审批链或故事卡片 |
| 安全 / 接入审查者 | 评估外部连接、安全、身份可信和接入约束是否满足正式接入前提 | 不写 policy truth、审批结论或安全平台实现 |
| 审计 / 合规查看者 | 查看能力接入事实及其历史线索,判断接入事实是否可解释和可追溯 | 不写 observability 存储、真实 evidence 或验收签署 |
| 能力目录浏览者 | 以只读方式理解哪些外部能力已处于正式接入语境 | 不写控制台页面、listing 或交易体验 |
| 系统消费方 | 在自身运行或封装语境中消费能力接入事实或接缝摘要 | 不点名具体 runtime / tools / SDK / console / marketplace |
| 能力接入维护任务 | 执行派生、重建、检查或对账类维护动作 | 不通过维护动作创造新的业务 truth |

### 3.4 是否存在管理、审计或维护类角色？

存在。

管理类角色包括能力接入管理员。它负责能力接入事实的管理语境,但不等同于全平台管理员、secret 管理员或成本管理员。

审计 / 审查类角色包括安全 / 接入审查者和审计 / 合规查看者。前者关注接入前提与约束,后者关注事实可解释和可追溯,两者都不拥有 governance approval truth、observability 物理存储或 provider 运行状态。

维护类角色包括能力接入维护任务。它可以执行目录派生、索引重建、一致性检查、历史对账或可见性刷新,但不能替代人类角色作出接入结论或治理裁决。

### 3.5 是否需要进一步补权限矩阵？

本步不形成正式权限矩阵。原因是旧矩阵已经混入 `QueryCapabilities`、`RegisterProvider`、调用执行、成本查看等功能、接口和执行语义;若在 Step 5 直接保留,会提前进入 Step 8~12 的内容。

本步只保留能力级差异方向:

- 管理: 能力接入管理员维护能力接入事实
- 提议: 能力接入提议者 / 技术负责人提出接入或变更语境
- 审查: 安全 / 接入审查者审查接入前提与约束
- 查看: 审计 / 合规查看者和能力目录浏览者以只读方式理解能力接入事实
- 系统消费: 系统消费方以受控方式消费能力接入事实
- 维护: 能力接入维护任务执行派生和一致性维护

这些差异后续在用户故事、功能需求、业务规则、数据归属和接口章节继续展开。

| 系统消费角色 | 系统消费方 | 抽象系统角色,具体 runtime、tools、SDK、console 等消费方后移 Step 6。 |
| 系统维护角色 | 能力接入维护任务 | 执行派生 / 重建 / 检查 / 对账,不创造业务 truth。 |

### 7.3 权限差异结论

本步不形成正式权限矩阵。当前只确认以下能力级差异方向:

| 差异方向 | 说明 | 后续落点 |
|---|---|---|
| 管理 | 能力接入管理员在管理语境中维护能力接入事实。 | Step 8 / Step 9 / Step 10 |
| 提议 | 能力接入提议者 / 技术负责人提出新能力或变更语境。 | Step 8 / Step 9 |
| 审查 | 安全 / 接入审查者评估外部能力是否适合进入正式接入语境。 | Step 8 / Step 10 / Step 11 |
| 查看 | 审计 / 合规查看者和能力目录浏览者以只读方式理解能力接入事实。 | Step 8 / Step 9 / Step 12 |
| 系统消费 | 系统消费方以受控方式消费能力接入事实。 | Step 6 / Step 12 |
| 维护 | 能力接入维护任务执行派生和一致性维护。 | Step 9 / Step 10 / Step 13 |

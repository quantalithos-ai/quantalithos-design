## 2. 本仓定位与边界

> 校准来源:
> - `design-calibration/00_req_step_02_position_boundary.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_02_position_boundary.md` 的“结构化中间产物”“旧材料差异审计”和“自检与停审”小节,了解本章边界如何收敛。

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L3-method-library` 是 L3 方法能力层中负责方法资产定义、版本发布与分发语义的真相仓。 |
| 本仓不是什么 | 它不是流程执行仓,不是成员身份仓,不是治理裁决仓,不是外部能力注册仓,也不是 marketplace 交易或 UI 渲染仓。 |
| 边界对象列表 | 仓:`L1-process`;仓:`L1-identity`;仓:`L1-governance`;仓:`L3-capability-hub`;仓:`L6-marketplace`;概念:方法定义 / 运行时使用分离。 |
| 单独成仓原因 | 平台需要一个独立于运行时实例、成员状态、治理执行、外部能力注册和交易流程的方法资产定义源。 |

`L3-method-library` 需要单独存在,因为平台的方法资产必须先作为可版本化、可发布、可分发的定义真相成立,再被相邻仓消费。它最容易与 `L1-process` 的执行实例、`L1-identity` 的成员身份、`L1-governance` 的治理裁决、`L3-capability-hub` 的外部能力注册以及 `L6-marketplace` 的交易分发混淆;这些边界如果不分开,后续需求会把“方法定义”误写成“运行时使用”或“交易体验”。

## 3. 背景与问题定义

> 校准来源:
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_03_problem_context.md` 的“结构化中间产物”“旧材料差异审计”和“自检与停审”小节,了解本章问题定义如何收敛。

### 3.1 业务背景

Quantalithos 不只是执行任务和流程的平台,还需要在业务真相域、运行层和体验层之间稳定表达“按什么方法做”。当前架构把 method-library 放在 L3 方法能力层,用于承接 SPEM Method Content、生命周期模型、裁剪 / 分发语义、AI 方针和视图策略等方法资产主题。本轮讨论 method-library,是为了先把方法资产定义源的需求背景收束清楚,避免后续消费仓各自定义局部方法语义。

### 3.2 现状与问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 方法资产定义源不统一 | 上游材料显示 process、identity、governance、UI/console 等相邻仓都会引用或消费方法资产语义;如果本仓边界不成立,这些语义会散落在消费仓。 | Definition vs Use 分离失效,消费仓容易各自 hardcode 方法定义,后续需求和设计会出现多真相源。 |
| 方法定义与运行时使用容易混写 | ProcessTemplate、RoleDefinition、AIPolicy、ViewProfile 等主题天然连接运行、身份、治理和体验,但这些仓只应消费或执行,不应拥有定义正文。 | 过程执行、成员状态、治理裁决和 UI 渲染会反向污染方法资产需求,导致边界、规则和数据归属难以收敛。 |
| 方法资产版本和分发语义缺少统一背景 | 路线图要求 N3 产出“怎么做”和“用什么”两套资产,但若没有统一的定义与发布语义,下游难以判断所消费资产的稳定性和可追溯性。 | 下游能力只能依赖文档约定或本地快照,跨仓协作、审计和验收都会缺少一致锚点。 |

### 3.3 业务问题 vs 技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台需要把方法论、生命周期模型、角色视角、AI 方针和视图策略变成可治理、可复用、可分发的资产语义;如果缺少统一定义源,产品层无法稳定表达“按什么方法做”。 |
| 技术问题 | 如果方法资产定义不独立,后续需求、架构、详细设计和实现会在定义源、运行时使用、成员身份、治理执行、外部能力和交易体验之间反复串线,产生多真相源和不可落码边界。 |

## 4. 目标与非目标

> 校准来源:
> - `design-calibration/00_req_step_04_goals_non_goals.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_04_goals_non_goals.md` 的“结构化中间产物”“旧材料差异审计”和“自检与停审”小节,了解本章目标与非目标如何收敛。

### 4.1 目标

| 目标 | 说明 | 验证方式 |
|---|---|---|
| 建立方法资产定义真相边界 | 明确本仓承载方法资产定义、版本发布与分发语义,相邻仓只按边界引用、消费或执行。 | 后续章节不把流程实例、成员状态、治理裁决、外部能力注册、交易流程或 UI 渲染写成本仓真相。 |
| 收束 Definition vs Use 分离 | 明确本仓讨论“定义”,不讨论相邻仓的运行时“使用”状态。 | Step 6/10/11 中所有相邻仓关系都能保持定义源与使用方分离。 |
| 收束当前方法资产主题范围 | 明确本轮需求围绕 SPEM Method Content、生命周期模型、AI 方针、视图策略和方法资产分发语义展开,不从旧对象模型反推范围。 | Step 7/9/11 的能力、功能和数据项均能回指当前方法资产主题,无法回指的项进入待确认或排除。 |
| 支撑方法资产版本与发布语义 | 为后续讨论版本稳定性、发布后不可随意修改、可追溯分发和下游消费建立目标边界。 | Step 10/11/14 能分别承接版本 / 发布规则、数据归属和验收口径,且不需要由消费仓补定义。 |
| 明确相邻仓职责不反向侵入 | 将 process、identity、governance、capability-hub、marketplace、UI/console 等职责排出本仓目标范围。 | 后续功能、接口、数据和验收中若出现相邻仓运行职责,必须被标为外部依赖、边界背景、外围增强或非目标。 |

### 4.2 非目标

| 非目标 | 不做原因 |
|---|---|
| 流程执行、ProcessInstance 状态和运行时编排 | 属于 `L1-process` / L2 runtime 的运行职责;本仓只收束方法资产定义。 |
| 成员身份、成员生命周期、成员具备哪些角色或资格的状态 | 属于 `L1-identity` 或相关成员仓;本仓不拥有成员状态真相。 |
| Gate 决策、治理裁决、策略 enforce 和运行时合规执行 | 属于 `L1-governance` / runtime;本仓只讨论方法资产中的定义性方针或被引用语义。 |
| MCP/A2A/provider/tool 外部能力注册、绑定和访问裁决 | 属于 `L3-capability-hub` 及治理协作边界;本仓不管理外部能力接入。 |
| marketplace 定价、购买、结算、订单和商业分发流程 | 属于 `L6-marketplace`;本仓最多作为方法资产定义源或包来源被后续讨论。 |
| UI 页面渲染、字段过滤执行和前端交互体验 | 属于 `L5-chat`、`L5-console`、mobile 或其他体验仓;本仓只收束视图策略作为方法资产的定义边界。 |
| Artifact 正文、外部文件、证据正文和制品生命周期状态 | 属于 `L1-artifact` / archive 等相邻仓;本仓不保存或管理外部正文生命周期。 |
| 认证登录、权限系统和操作主体鉴权实现 | 属于身份、治理或平台安全边界;本仓需求只讨论方法资产的仓级职责。 |

## 5. 用户与角色

> 校准来源:
> - `design-calibration/00_req_step_05_users_roles.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_05_users_roles.md` 的“结构化中间产物”“旧材料差异审计”和“自检与停审”小节,了解本章角色如何收敛。

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 方法资产作者 | 人类角色 | 创建和维护方法资产定义内容,使方法资产在进入审核或发布前具备明确语义。 |
| 方法资产审核 / 批准者 | 人类角色 | 从方法完整性、适用性和发布风险角度审查方法资产是否可以进入正式使用语境。 |
| 方法资产管理员 | 人类角色 | 维护方法资产目录、组织级使用范围和资产治理秩序,处理跨团队的方法资产管理需求。 |
| 审计者 | 人类角色 | 查看方法资产定义、版本、发布依据和变更线索,判断方法资产是否可追溯。 |
| 方法资产浏览者 | 人类角色 | 在控制台或其他体验入口查看可用方法资产、版本说明和适用语境。 |
| 下游消费系统 | 系统角色 | 以受控方式消费方法资产定义语义或快照,用于自身运行、展示或治理判断。 |
| 方法资产维护任务 | 系统角色 | 执行方法资产索引维护、过期检查、重建或一致性检查等后台维护动作。 |
| 分发 / 同步自动化 | 系统角色 | 在资产发布或组织使用范围变化后,推动方法资产元信息进入分发或同步语境。 |
| 审计证据采集方 | 系统角色 | 采集与方法资产版本、发布和引用相关的证据线索,供审计或验收材料使用。 |

当前不在本章展开权限矩阵。角色之间的操作差异需要等核心能力、功能需求和业务规则收敛后,再以能力级动作表达;本章只负责确认谁以什么身份接触本仓。

## 6. 使用方与依赖

### 6.5 本仓禁止依赖表

| 禁止依赖 | 禁止原因 | 正确协作方式 |
|---|---|---|
| `L1-process -> L3-method-library` 源码级依赖 | process 运行期消费模板定义,不能因为消费关系直接依赖本仓源码。 | 运行期能力边界 / SDK / 正式查询或快照边界。 |

## 7. 核心能力闭环

> 校准来源:
> - `design-calibration/00_req_step_07_core_capability_loop.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_07_core_capability_loop.md` 的“结构化中间产物”“旧材料差异审计”和“自检与停审”小节,了解本章核心能力闭环如何收敛。

`L3-method-library` 的核心能力闭环不是方法资产的功能清单,而是:方法资产必须能够被统一定义和识别,能够以稳定版本进入正式使用语境,能够被下游按边界消费,并且在变化后仍能被追溯和保护消费一致性。只要这些能力不能共同成立,本仓就会退化为静态文档库或下游私有模型集合,无法承担方法资产定义真相源。

```text
方法资产能够被统一定义和识别
  -> 方法资产能够以稳定版本进入正式使用语境
  -> 正式方法资产能够被下游按边界消费
  -> 方法资产变化能够被追溯并保护消费一致性
```

本图只表达能力成立的逻辑依赖关系,不是运行时调用顺序、接口时序、事件传播顺序、开发顺序或实施计划。

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | 方法资产统一定义与识别;稳定版本进入正式使用语境;下游按边界消费;变化可追溯并保护消费一致性。 |
| 外围增强能力 | MethodPlugin / MethodConfiguration 资产包与组织级方法集;29110 Deployment Package 导出;marketplace 生态分发;高级 ViewProfile 匹配与体验优化;AIPolicy override 深化;更丰富的合规/成熟度材料。 |
| 边界外能力 | 流程执行;成员生命周期和成员状态;治理裁决和 policy enforce;外部工具/MCP/A2A/provider 注册;marketplace 交易/结算/订单;UI 渲染执行;Artifact 正文和外部文件生命周期;认证登录和权限系统实现。 |

### 12.3 事件协作边界

| 事件协作能力 | 方向 | 能力说明 | 不得包含 |

| 方法资产正式化变化感知 | 输出 | 方法资产进入正式使用语境时,下游体系应能感知其可消费语义。 | 不写事件名、payload、outbox、重试或订阅实现。 |

| 下游消费影响回报输入 | 输入 | 本仓可接收下游消费影响摘要,用于支撑一致性保护。 | 不写回报协议、轮询、订阅或对账算法。 |

## 13. 非功能需求

> 校准来源:
> - `design-calibration/00_req_step_13_non_functional_requirements.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/00_req_step_13_non_functional_requirements.md` 的“结构化中间产物”“旧材料差异审计”和“自检与停审”小节,了解本章非功能要求如何由能力、规则、数据和接口边界收敛。

| 编号 | 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|---|
| NFR-ML-001 | 性能 | 方法资产目录识别、正式定义读取和下游受控消费不应成为当前主链能力的阻塞点。 | 后续验收至少应证明核心查询 / 消费路径不会阻塞 process、identity、runtime、member-images 的主链消费。 |
| NFR-ML-002 | 性能 | 方法资产证据线索查看和追溯查看不应阻塞正式化、受控消费或一致性维护的主链判断。 | 后续验收应能判断证据线索和追溯能力不会反向拖垮核心闭环。 |
| NFR-ML-003 | 性能 | 方法资产正式化和版本语义变化优先保证一致性、追溯和边界正确性,不得为追求低延迟牺牲定义真相完整性。 | 验收时若性能与一致性冲突,以定义真相、版本语义和追溯完整为优先判断。 |
| NFR-ML-004 | 可用性 | 外围增强能力失效时,核心方法资产定义、正式化、受控消费和追溯能力仍应成立。 | MethodPlugin、MethodConfiguration、marketplace、console、标准映射材料等外围能力不可用时,核心闭环不应整体不可用。 |
| NFR-ML-005 | 可用性 | 条件型外部治理或候选下游依赖不可用时,本仓不得丢失或改写已成立的方法资产定义真相。 | 外部治理、artifact、marketplace、console 等候选关系不可用时,已存在定义真相和正式版本语义仍可被判断。 |
| NFR-ML-006 | 可用性 | 下游消费方不可用或回报延迟时,本仓不得把下游运行状态当作自身定义真相。 | 下游不可用只能影响消费影响摘要或协作判断,不能改变本仓定义真相归属。 |
| NFR-ML-007 | 安全 | 本仓不得越权拥有流程运行、成员状态、治理执行、外部能力注册、交易履约、UI 渲染、artifact/archive 正文或鉴权实现正文。 | 数据归属和接口边界中应持续排除这些正文或运行真相。 |
| NFR-ML-008 | 安全 | 下游消费能力不得绕过本仓定义真相边界创建或修改方法资产定义。 | 验收应能判断下游只能按引用、快照、索引或正式消费边界使用方法资产语义。 |
| NFR-ML-009 | 审计 / 可追溯 | 方法资产正式化、版本语义变化和影响既有消费的变化必须可追溯。 | 后续验收应能追溯这些变化的定义来源、变化语境和影响范围。 |
| NFR-ML-010 | 审计 / 可追溯 | 正式消费应能回溯到被消费的方法资产定义来源和版本语境。 | 下游正式消费不应只留下不可解释的本地约定。 |
| NFR-ML-011 | 审计 / 可追溯 | 方法资产版本、发布和引用相关证据线索必须能承接正式验收或审计语境。 | 证据线索应能说明其来源、关联的方法资产语境和用途,但本 Step 不定义证据 schema。 |
| NFR-ML-012 | 幂等 / 一致性 | 方法资产定义真相在平台范围内应保持单一正式语义。 | 同一方法资产定义不得同时由本仓和消费仓各自形成互相冲突的正式真相。 |
| NFR-ML-013 | 幂等 / 一致性 | 重复读取、重复变化感知、重复证据线索查看或后台维护不得改变方法资产定义正文或制造重复正式语义。 | 重复执行同类消费或维护动作时,应能判断其没有产生第二定义真相。 |
| NFR-ML-014 | 幂等 / 一致性 | 正式版本语义变化必须保持显式、可区分,不得静默覆盖既有正式引用含义。 | 任何影响正式版本语义的变化都应能被识别为显式变化。 |
| NFR-ML-015 | 可观测性 | 方法资产正式化状态、版本语义变化、消费影响变化、证据线索状态和边界异常应能被平台稳定观察。 | 后续验收应能判断这些状态或异常是否发生,但不要求本 Step 定义具体指标名。 |
| NFR-ML-016 | 可观测性 | 可观测材料不得成为方法资产定义真相的替代存储。 | observability、audit material 或 telemetry 只能支持观察和追溯,不能替代本仓定义真相。 |

### 14.2 一票否决项

- 方法资产定义真相不能明确归属本仓。
- 方法资产正式版本语义可被静默覆盖。
- 下游消费仓可以创建、修改或替代方法资产定义真相。
- 未正式化或不稳定的方法资产可作为正式消费依据。
- process、identity、governance、capability-hub、marketplace、UI、artifact/archive 或认证鉴权实现正文进入本仓真相范围。
- 正式化、版本语义变化、消费影响变化或证据线索不可追溯。
- 运行期依赖或事件协作依赖被写成本仓与消费仓的源码级拥有关系。
- 外围增强能力被作为核心闭环成立的前置。
- 可观测材料被作为方法资产定义真相的替代存储。

## 1. 业务背景与驱动力

### 1.1 业务背景

Quantalithos 不只是代码系统,也是**方法系统**。如果不把 Qualification / RoleDefinition / TaskDefinition / WorkProductDefinition / ProcessTemplateDef / ViewProfile / AIPolicyDef 做成可管理的资产,那么:
- process 只能运行写死在代码里的模板
- identity 只能硬编码角色,且 QualificationProfile 缺少统一定义来源
- capability-hub 的 QualificationBinding 缺少统一语义锚点
- artifact 缺少 WorkProductDefinition 的权威来源
- UI 不能按方法资产来渲染 ViewProfile
- governance 的 AI Policy 没有权威源
- Marketplace 无法分发"方法"本身

因此 method-library 必须成为"怎么做"的单一真相源。

### 1.2 业务驱动力

**业务驱动力**:
- 产品需要把方法论产品化,而不只是写进文档
- 组织需要发布自己的 Role / Template / Policy / ViewProfile
- Marketplace 需要分发方法资产包

**技术驱动力**:
- Definition vs Use 分离(SPEM)
- Template 家族与 Tailoring
- fingerprint drift 防护
- Plugin / Configuration 组装机制
- ViewProfile 为 UI 提供角色视图规则

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 功能 | P0 MethodContent 7 类可用 | 7/7 | 集成测试 |
| 功能 | 种子 9 Role + 8 Template 家族 | 100% | seed 验证 |
| 功能 | Qualification 可发布、版本化、同步 | identity / capability-hub 可消费 | 集成测试 + E2E |
| 性能 | GetContent P95 | < 50ms cache / < 200ms PG | benchmark |
| 性能 | ResolveViewProfile P95 | < 30ms | benchmark |
| 一致性 | fingerprint_changed 覆盖率 | 100% | 回归测试 |
| 同步 | identity / process / capability-hub / artifact / governance / UI 同步成功率 | 100% 样本链 | E2E |

### 1.4 需求基线与架构输入

本文以 `00-需求文档.md` 已完成校准后的结论作为架构基线。架构设计不得重新扩大本仓职责,也不得绕过需求文档中已经确认的 P0 / P1 分界。

P0 MethodContent:

```text
Qualification
RoleDefinition
TaskDefinition
WorkProductDefinition
ProcessTemplateDef
ViewProfile
AIPolicyDef
```

P0 主链路:

```text
Create Draft
  -> Submit Review
  -> Publish
  -> Generate Fingerprint
  -> Write Audit Record
  -> Write Outbox Event
  -> Export Definition Snapshot
  -> Downstream Sync
```

P0 下游同步口径:

| 定义资产 | P0 下游 | 架构含义 |
|---|---|---|
| Qualification | identity / capability-hub | identity 建立 QualificationCatalogEntry,capability-hub 建立 QualificationBinding 语义锚点 |
| RoleDefinition | identity | identity 同步 RoleCatalogEntry |
| TaskDefinition | process | process 在 ProcessTemplateDef / Activity / TaskUse 中引用 |
| WorkProductDefinition | artifact | artifact 对齐 kind、acceptance template、evidence 类型 |
| ProcessTemplateDef | process | process 建立流程模板执行索引 |
| ViewProfile | UI / console | UI / console 解析字段可见性与视图策略 |
| AIPolicyDef | governance | governance 同步 policy source index |

P1 后置能力:

```text
MethodPlugin
MethodConfiguration
Plugin dependency DAG
Variability application
Marketplace package distribution
```

架构硬约束:

| 约束 | 正确归属 | 本仓处理方式 |
|---|---|---|
| Qualification 定义真相 | method-library | 拥有正文、版本、fingerprint、生命周期 |
| QualificationProfile | identity | 只允许下游引用 Qualification,不得写入本仓 |
| QualificationBinding | capability-hub | 只允许下游引用 Qualification,不得写入本仓 |
| CapabilityAccessDecision | capability-hub / governance | 本仓不做运行时能力访问裁决 |

| WorkItem / Backlog / Iteration | work | 本仓不保存项目任务事实 |
| Artifact 实例正文 | artifact | 本仓只定义 WorkProductDefinition |
| Policy enforce result | governance | 本仓只定义 AIPolicyDef |

待确认但不阻塞本轮架构设计的问题:

| 问题 | 当前口径 | 后续处理 |

## 2. 约束条件

### 2.0 架构目标

| 目标 | 含义 | 需求来源 |
|---|---|---|
| 定义真相稳定 | 7 类 P0 MethodContent 的正文、版本、fingerprint、生命周期由 method-library 统一拥有 | G-1 / G-8 / §9 数据归属 |
| 下游同步可靠 | identity / process / capability-hub / artifact / governance / UI 可通过 event / snapshot 同步定义 | P0 主链路 / F-005 |
| 发布链可审计 | publish 必须经过 gate,并留下 actor、version、fingerprint、audit record、outbox event | F-002 / F-004 / §7 非功能 |
| 边界红线可验证 | 本仓不能保存 QualificationProfile / QualificationBinding / ProcessInstance / WorkItem / Artifact 实例等外部事实 | NG-6~NG-8 / §11.4 |
| P0 / P1 清晰分离 | P0 先跑通 7 类定义资产发布闭环,Plugin / Configuration / Marketplace 后置 | §3.1.1 / §11.6 |

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| Definition vs Use 严格分离 | SPEM 2.0 | 本仓只定义,不执行 |
| Qualification 定义真相归 method-library | ADR draft 0014 / 需求 G-8 | identity / capability-hub 只能消费定义,不能反向创建或改写 |
| QualificationProfile 不归本仓 | 需求 NG-6 | 成员实际能力画像归 identity |
| QualificationBinding 不归本仓 | 需求 NG-7 | tool / provider / MCP / A2A 绑定归 capability-hub |
| ProcessTemplateDef 是 method-library 权威源 | `domain/process/README.md` | process 只存执行索引 |
| TaskDefinition 的 P0 下游是 process | 需求 §3.1.1 | work 直接消费 TaskDefinition 保持 P1 / 待确认 |
| published 内容核心字段不可改 | INV-ML-3 | 变更必须 supersede |
| fingerprint 变化必发事件 | INV-ML-4 | drift 防护强约束 |
| 发布成功必须写入 audit 与 outbox | 需求 §7 / §11 | state、version、fingerprint、audit record、outbox event 必须一致 |
| ViewProfile 归本仓 | ADR-0009 | UI 不直接自定义长期规则 |
| 8 家族对齐 24748-2 | INV-ML-21/22 | 家族枚举受控 |
| publish 必经 Gate | INV-ML-2 | 无直接发布 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| DSL(派生字段 / Policy / Variability patch) | P0 不固化复杂 DSL | 后续 ADR 或 P1 细化 |
| Plugin 签名机制 | P1 后置 | 可从 fingerprint-only 升级 |
| 搜索实现 | PG tsvector 起步 | 可换 ES / Typesense,不影响定义真相 |
| Configuration 继承 | P1 暂不继承 | 企业版可扩展 |
| ViewProfile 复杂优先级 | P0 只保留 role + object_kind + scope | 后续可加 preset / override |
| MethodPlugin / MethodConfiguration 实现时机 | P1 | P0 闭环完成后再细化 |

### 2.3 一致性约束

| 范围 | 一致性策略 | 补偿机制 |
|---|---|---|
| MethodContent 聚合内部 | 强一致 | 事务内同时处理 state、version、fingerprint、audit record、outbox event |
| MethodPlugin / MethodConfiguration(P1) | 聚合内部强一致 | supersede / retry / audit |
| 下游同步 | 最终一致 | event replay、snapshot query、fingerprint compare |
| object storage blob | ref 最终一致 | 元数据可查,blob 失败时阻断 publish 或稍后恢复 |
| 下游 drift | 最终修复 | CompareFingerprint / DetectDefinitionDrift(P1) |

### 2.4 阶段性容量规划假设

| 资源 | 上限 | 量化依据 |
|---|---|---|
| MethodContent 记录 | 2000w(含历史版本) | 10w 组织 × 200 内容 |
| Plugin | 5w-50w | Marketplace 预估 |
| Configuration | 百万级 | 组织 / 项目 / 角色范围 |
| ResolveViewProfile QPS | 5000 | UI 高频消费 |

这些容量值是目标架构假设,不是 P0 首批实现承诺。P0 首批优先保证定义真相、发布一致性、下游同步和边界红线。

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 新方法资产种类 | 低 | 子类扩展 + ADR |
| 内容版本演进 | 中高 | semver + supersede |
| 组织方法集切换 | 中 | Configuration active / supersede |
| ViewProfile 规则变化 | 中 | role × object_kind × scope 匹配 |
| 下游 drift 风险 | 中 | fingerprint + source_drift |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **元模型驱动 + 版本化内容仓**(当前)| SPEM 对齐、下游统一消费 | 模型复杂 | ✅ |
| 文档仓 + 手工约定 | 成本低 | 无法执行 / 无法同步 / 无 drift 防护 | ❌ |
| 过程引擎内嵌模板 | 起步快 | 打破 Definition/Use 分离 | ❌ |

**最终选择**:**MethodContent 元模型 + Plugin + Configuration + fingerprint drift 机制**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 内容发布需 Gate | 资产可审计 | 发布流程更重 |
| supersede 而不直接改 | 版本历史清晰 | 内容膨胀 |
| Plugin / Configuration 双层 | 分发与组装分离 | 模型学习成本高 |

### 4.2 职责边界(做什么 / 不做什么)

**P0 做什么**:
- ✅ 管理 7 类 MethodContent 定义真相:Qualification / RoleDefinition / TaskDefinition / WorkProductDefinition / ProcessTemplateDef / ViewProfile / AIPolicyDef
- ✅ 管理 draft / review / publish / deprecate / retire / supersede 生命周期
- ✅ 生成 version / fingerprint,并维护 supersede 关系
- ✅ 记录 audit chain,包含 actor、gate、版本、fingerprint 和原因
- ✅ 写 outbox event,支持下游 event replay
- ✅ 导出 definition snapshot,支持下游同步与对账
- ✅ 支持 ResolveViewProfile,为 UI / console 提供视图策略定义
- ✅ seed 初始方法基线,包括基础 Qualification、9 Role、8 Template 家族、基础 ViewProfile / AIPolicyDef

**P1 做什么**:
- ✅ 管理 MethodPlugin
- ✅ 管理 MethodConfiguration
- ✅ 管理 plugin dependency DAG
- ✅ 管理 variability application
- ✅ 输出 marketplace package metadata

**不做什么**:
- ❌ 不执行流程:ProcessInstance / Activity runtime 属于 process
- ❌ 不管理成员实际能力:QualificationProfile 属于 identity
- ❌ 不绑定工具:QualificationBinding 属于 capability-hub
- ❌ 不做能力访问裁决:CapabilityAccessDecision 属于 capability-hub / governance
- ❌ 不管理任务事实:WorkItem / Backlog / Iteration 属于 work
- ❌ 不保存实际制品:Artifact 实例正文、证据文件属于 artifact
- ❌ 不执行 policy:policy enforce result 属于 governance
- ❌ 不做交易:listing / transaction / installation 属于 marketplace
- ❌ 不渲染 UI:session state / frontend rendering 属于 UI / console / chat

相关能力归属:

| 相关能力 | 归属 | method-library 的关系 |
|---|---|---|
| Qualification | method-library | 拥有定义真相 |
| QualificationProfile | identity | 只允许引用 Qualification |
| QualificationBinding | capability-hub | 只允许引用 Qualification |
| CapabilityAccessDecision | capability-hub / governance | 不进入本仓 |
| ProcessInstance / Activity runtime | process | 只消费 ProcessTemplateDef / TaskDefinition |
| WorkItem / Backlog / Iteration | work | 当前不作为 P0 下游 |
| Artifact 实例 / 证据文件 | artifact | 只消费 WorkProductDefinition |
| Policy enforce result | governance | 只消费 AIPolicyDef |
| Marketplace 交易 / 安装记录 | marketplace | 只消费 Plugin metadata(P1) |

绝不隐式发生:

```text
发布 Qualification 不会自动给任何成员增加 QualificationProfile。
发布 Qualification 不会自动创建任何 tool / provider / MCP / A2A 绑定。
发布 TaskDefinition 不会自动创建 WorkItem。
发布 ProcessTemplateDef 不会自动创建 ProcessInstance。
发布 WorkProductDefinition 不会自动创建 Artifact 实例。
发布 AIPolicyDef 不会自动执行 policy enforce。
发布 MethodPlugin 不会自动产生 marketplace 交易或安装记录。
```

### 4.3 外部系统可用性约束

| 外部依赖 | 交互方式 | SLA 假设 | 降级 |
|---|---|---|---|
| PostgreSQL | 强一致读写 | 99.95% | 不可用则阻断写入与强一致查询 |
| L0-bus | outbox relay / event replay | 99.95% | 事件先写 outbox / backlog,恢复后 replay |
| object storage | blob ref | 99.9% | 元数据可查;blob 失败时阻断 publish 或稍后恢复 |
| governance | gate result / policy source sync | 99.9% | gate 不可用时阻断 publish,不阻断 draft / query |
| identity / process / capability-hub / artifact / UI | event + snapshot | 99.9% | 下游不可用不阻断发布,通过 event replay / snapshot query 恢复 |
| marketplace(P1) | plugin metadata | 99.9% | P1 下游不可用时先组织内发布 |

### 4.4 关键依赖风险

- MethodContent 与下游索引 drift:通过 fingerprint、snapshot query、event replay 和 drift detection 缓解
- Qualification 边界混淆:identity / capability-hub 只能消费 Qualification,不得反向创建或改写定义
- ProcessTemplateDef / TaskDefinition 到 process 索引不匹配:后续架构和概要设计需要单独校准映射模型
- WorkProductDefinition 与 artifact kind / evidence 类型不一致:通过 snapshot version 和 downstream sync 验证
- ViewProfile 匹配逻辑出错影响整批 UI:P0 只保留 role + object_kind + scope 与唯一 active 约束
- Plugin 环依赖或 Configuration 过度复杂:P1 后置,不得阻塞 P0 发布闭环

## 5. 限界上下文与子域划分

### 5.3 上下文映射关系


上下文映射约束:

### 6.5 部署拓扑

- P0 起步可以采用单服务部署:`method-library-api + application + domain + snapshot exporter + operations job` 同仓交付。

- PostgreSQL 是定义真相、审计、outbox 的主存储。
- object storage 只保存 guidance / example / package blob,不保存结构化定义真相。
- L0-bus 负责跨仓事件分发,下游不可用时通过 outbox / replay 恢复。
- 高频 ResolveViewProfile 可以先用进程内 LRU,后续按 QPS 引入 Redis。
- P1 package 产物可以复制到 Marketplace storage,但 marketplace 不拥有 MethodContent 正文真相。

- ResolveViewProfile 是只读路径,不得在 resolve 路径中修改 MethodContent。
- Plugin / Configuration(P1) 只引用 content_id / plugin_id,不得复制 MethodContent 正文。
- P1 Plugin / Configuration 不得反向改变 P0 MethodContent 的定义真相边界。
- published content 核心字段不可原地修改,只能通过新版本 + supersede 演进。

```text
CapabilityAccessDecision
ProcessInstance
Activity runtime state
WorkItem / Backlog / Iteration
Artifact instance / evidence file
Policy enforce result
Marketplace transaction / installation record
UI session state
```

红线验证要求:

| 红线 | 架构约束 |
|---|---|
| 不保存 QualificationProfile | identity 只通过 QualificationSnapshot 建立本地 catalog / profile 引用 |
| 不保存 QualificationBinding | capability-hub 只消费 Qualification,绑定关系不回写本仓 |
| 不保存 ProcessInstance | process 只消费 ProcessTemplateDef / TaskDefinition,运行实例留在 process |
| 不保存 WorkItem | work 直接消费 TaskDefinition 仍为 P1 / 待确认,不进入 P0 |
| 不保存 Artifact 实例 | artifact 只消费 WorkProductDefinition,实际产物和证据留在 artifact |
| 不保存 Policy enforce result | governance 只消费 AIPolicyDef,运行裁决留在 governance |

## 9. 关键技术选型

### 9.1 MethodContent 元模型 + kind 扩展

| 项 | 内容 |
|---|---|
| 当前选择 | 使用 MethodContent 抽象承载 7 类 P0 定义资产 |
| 解决的问题 | Qualification / Role / Task / WorkProduct / ProcessTemplate / ViewProfile / AIPolicyDef 需要统一生命周期、版本、fingerprint、审计和发布链 |
| 替代方案 | 每类定义单独建仓或单独建一套发布模型 |
| 为什么选择 | 统一发布治理和下游同步,同时保留 kind-specific 校验 |
| 代价 / 风险 | 元模型复杂度上升,需要清晰区分通用字段和 kind-specific 字段 |
| 演进路径 | 新增 MethodContent kind 必须通过 ADR 或等价设计决策 |

### 9.2 PostgreSQL 作为定义真相存储

| 项 | 内容 |
|---|---|
| 当前选择 | PostgreSQL 保存 definition truth、version、fingerprint、audit、outbox |
| 解决的问题 | 发布事务需要强一致,审计和查询需要结构化能力 |
| 替代方案 | Git-only / 文档仓 / NoSQL |
| 为什么选择 | PostgreSQL 能同时支持事务、索引、约束和审计查询 |
| 代价 / 风险 | 需要控制大字段和历史版本膨胀 |
| 演进路径 | 高频查询可加 cache / search,但真相仍在 PostgreSQL |

### 9.3 object storage 外置 blob

| 项 | 内容 |
|---|---|
| 当前选择 | guidance / example / package blob 存 object storage,本仓只保存 ref / hash |
| 解决的问题 | 避免大段文档、示例包、资产包污染结构化定义真相 |
| 替代方案 | 全部塞入 PostgreSQL / 全部放 Git |
| 为什么选择 | 结构化定义和大对象生命周期不同,分离后更容易扩展 |
| 代价 / 风险 | 需要处理 blob ref 可用性和 hash 校验 |
| 演进路径 | P1 package 可引入签名、扫描、供应链校验 |

### 9.4 Outbox + L0-bus

| 项 | 内容 |
|---|---|
| 当前选择 | 发布事务内写 outbox,再由 outbox-relay 发布到 L0-bus |
| 解决的问题 | 防止数据库写入成功但事件发布失败 |
| 替代方案 | 直接发事件 / 双写数据库与 bus |
| 为什么选择 | outbox 可以和定义状态同事务提交,事件可重放 |
| 代价 / 风险 | 需要 relay、重试、backlog 监控和幂等消费 |
| 演进路径 | dead-letter、按下游 replay cursor、批量重放 |

### 9.5 Definition Snapshot Exporter

| 项 | 内容 |
|---|---|
| 当前选择 | 下游通过 ExportDefinitionSnapshot 获取完整定义 |
| 解决的问题 | 事件不适合携带大段定义正文,下游首次同步和对账需要完整快照 |
| 替代方案 | 事件直接携带完整定义 / 下游直接查库 |
| 为什么选择 | event 保持轻量,禁止跨库读取,同步边界清晰 |
| 代价 / 风险 | snapshot schema 需要版本治理 |
| 演进路径 | 批量 snapshot、historical snapshot、snapshot registry |

### 9.6 schema version

| 项 | 内容 |
|---|---|
| 当前选择 | definition / snapshot / event 都携带 schema version |
| 解决的问题 | 下游多,定义资产后续会演进 |
| 替代方案 | 不带版本,靠字段兼容 |
| 为什么选择 | 可以显式处理兼容范围和消费者升级 |
| 代价 / 风险 | 版本治理复杂度上升 |
| 演进路径 | compatibility matrix、schema registry、consumer contract test |

### 9.7 canonical fingerprint

| 项 | 内容 |
|---|---|
| 当前选择 | canonical definition hash |
| 解决的问题 | 支持跨仓 drift 检测和历史版本追溯 |
| 替代方案 | 原文 hash / 数据库更新时间戳 / semver-only |
| 为什么选择 | canonical hash 更适合跨语言、跨存储稳定比较定义语义 |
| 代价 / 风险 | canonical serialization 必须稳定,字段纳入规则要受控 |
| 演进路径 | P1 可引入签名、供应链校验和 fingerprint compatibility |

### 9.8 ResolveViewProfile 服务端解析

| 项 | 内容 |
|---|---|
| 当前选择 | 服务端按 role + object_kind + scope 解析 active ViewProfile |
| 解决的问题 | 避免 UI / console 各自硬编码字段可见性规则 |
| 替代方案 | 前端本地拼规则 / 每个下游自定义视图规则 |
| 为什么选择 | ViewProfile 真相归 method-library,UI 只消费解析结果 |
| 代价 / 风险 | ResolveViewProfile 位于渲染前置路径,需要性能预算和缓存策略 |
| 演进路径 | preset、override、缓存、灰度发布 |

### 9.9 P1 Plugin / Configuration 后置

| 项 | 内容 |
|---|---|
| 当前选择 | P0 先实现 7 类 MethodContent 发布闭环,MethodPlugin / MethodConfiguration 留在 P1 |
| 解决的问题 | 防止分发、组装、variability 复杂度拖慢定义真相闭环 |
| 替代方案 | P0 同时实现 Plugin / Configuration / Marketplace |
| 为什么选择 | P0 价值在定义资产可发布、可同步、可追溯 |
| 代价 / 风险 | 初期无法完整支持组织级方法集切换和 marketplace 分发 |
| 演进路径 | P0 稳定后进入 Packaging / Composition / Marketplace Distribution |

### 9.10 边界校验机制

| 项 | 内容 |
|---|---|
| 当前选择 | 在架构、接口、数据模型、测试中持续校验禁止数据不得进入本仓 |
| 解决的问题 | 防止 QualificationProfile / QualificationBinding / ProcessInstance / WorkItem 等运行时事实污染定义真相 |
| 替代方案 | 只靠文档约定 |
| 为什么选择 | method-library 的核心风险是边界污染,需要工程化防线 |
| 代价 / 风险 | 需要额外边界测试和审查规则 |
| 演进路径 | 架构检查、schema lint、contract test、CI 边界扫描 |

## 10. 备选方案与取舍

### 10.1 仓定位方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方法资产元模型仓 | 边界清晰,可发布、可同步、可追溯 | 学习成本高,元模型复杂 | 采用 |
| 文档仓 / Git-only | 简单、低成本、适合人工阅读 | 无法结构化同步、无法 enforce 关系、难以 drift 检测 | 不采用 |
| 嵌入各下游仓 | 下游实现快,短期耦合少 | 定义分裂,Role / Task / Policy / ViewProfile 各自漂移 | 不采用 |

最终选择:

```text
method-library 作为方法资产元模型仓。
```

原因:

```text
只有元模型仓能同时满足 definition truth、版本、fingerprint、audit、snapshot 和 event sync。
```

### 10.2 Qualification 归属方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Qualification 属于 method-library | 符合 SPEM Qualification 语义,Role / Task 可统一引用 | identity / capability-hub 需要同步 catalog | 采用 |
| Qualification 属于 identity | 成员画像实现方便 | 混淆“能力定义”和“成员实际能力” | 不采用 |
| Qualification 属于 capability-hub | 工具绑定方便 | 混淆“能力定义”和“工具接入能力” | 不采用 |

关键取舍:

```text
method-library 定义 Qualification 是什么。
identity 记录谁具备哪些 Qualification。
capability-hub 记录 Qualification 如何绑定工具 / provider / MCP / A2A。
```

### 10.3 发布同步方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Outbox + L0-bus | 可靠、可重放,可避免 DB 成功但事件丢失 | 需要 relay、backlog、幂等和监控 | 采用 |
| 直接发事件 | 实现简单 | DB 成功但事件失败会造成下游丢同步 | 不采用 |
| 下游轮询 | 下游控制节奏,实现直观 | 延迟大、压力高,不适合多下游 | 不作为主路径 |

关键取舍:

```text
跨仓事实传播必须异步。
发布事务只保证本仓 definition truth + outbox 强一致。
下游通过 event replay / snapshot query 达成最终一致。
```

### 10.4 Snapshot 同步方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| event 只放元数据 + snapshot_ref | 事件轻量,下游可按需拉取完整定义 | 需要 snapshot exporter | 采用 |
| event 携带完整正文 | 下游一次拿全 | 事件变大,replay 和 schema 演进成本高 | 不采用 |
| 下游直接查库 | 实现快 | 破坏边界,造成跨库耦合 | 禁止 |

关键取舍:

```text
event 用来通知“发生了什么”。
snapshot 用来承载“完整定义是什么”。
```

### 10.5 P0 / P1 范围方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| P0 先做 7 类 MethodContent | 快速跑通定义发布、fingerprint、audit、event、snapshot | 暂时没有完整 marketplace 分发 | 采用 |
| P0 同时做 Plugin / Configuration / Marketplace | 一次性完整 | 风险大,复杂度拖慢定义真相闭环 | 不采用 |
| 完全不做 Plugin / Configuration | P0 最简单 | 未来方法资产分发和可裁剪性不足 | 不采用,P1 后置 |

关键取舍:

```text
P0 的成功标准是定义资产可发布、可同步、可追溯。
Plugin / Configuration 是重要能力,但不应阻塞 P0。
```

### 10.6 边界校验方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 文档 + 架构 + 测试共同约束边界 | 能持续防止边界污染 | 需要额外检查和维护 | 采用 |
| 只靠文档约定 | 成本低 | 容易在实现中把外部事实写入本仓 | 不采用 |
| 接受少量跨仓数据冗余 | 查询方便 | 长期会破坏 source of truth | 不采用 |

关键取舍:

```text
method-library 最大风险不是功能缺失,
而是被 QualificationProfile / QualificationBinding / ProcessInstance / WorkItem 等运行时事实污染。
```

## 11. 横切关注点

### 11.1 安全与边界

本仓不负责统一身份认证,安全入口由外层 gateway / nginx-like 层负责。但本仓必须保留可审计的 actor_ref、gate_ref 和边界拒绝记录。

| 关注点 | 架构约束 |
|---|---|
| actor_ref | 所有 Command 必须携带 actor_ref |
| approved_gate_ref | PublishMethodContent 必须携带 approved_gate_ref 或等价 gate result |
| 查询安全 | Query 不改变定义状态,但必须保留调用上下文用于审计 |
| 边界违规 | 对 QualificationProfile / QualificationBinding / ProcessInstance / WorkItem / Artifact instance 等写入请求直接拒绝 |
| P1 分发 | marketplace 只消费 metadata / package blob,不拥有 MethodContent 正文 |

### 11.2 韧性与失败隔离

| 场景 | 策略 |
|---|---|
| L0-bus 不可用 | 写入 outbox backlog,恢复后 replay |
| 下游不可用 | 不阻断本仓发布,下游通过 event replay / snapshot query 恢复 |
| governance gate 不可用 | 阻断 publish,不阻断 draft / query |
| object storage 不可用 | 元数据可查;publish 依赖 blob 时阻断 publish |
| cache 不可用 | 回源 PostgreSQL / snapshot-exporter |
| ResolveViewProfile 高频读 | 读缓存与写路径隔离 |
| P1 Plugin / Configuration 失败 | 不影响 P0 MethodContent 发布闭环 |

### 11.3 可观测性

| 指标 / 信号 | 用途 |
|---|---|
| publish_success_total / publish_failure_total | 观察发布稳定性 |
| outbox_backlog_size | 观察事件积压 |
| event_replay_total | 观察重放与恢复 |
| snapshot_export_total | 观察下游拉取和对账 |
| downstream_sync_lag_seconds | 观察下游同步延迟 |
| fingerprint_changed_total | 观察定义变化频率 |
| definition_drift_detected_total | 观察 drift 风险 |
| boundary_violation_rejected_total | 观察边界污染尝试 |
| resolve_view_profile_latency_ms | 观察视图解析性能 |
| seed_success_total / seed_failure_total | 观察初始化稳定性 |

日志与 trace 必须覆盖:

```text
audit record 写入
outbox 写入与 relay
snapshot 导出

boundary violation rejection
```

### 11.4 审计与追溯

审计链必须能回答:

```text
谁改了定义
什么时候改
改了什么
为什么改
从哪个版本到哪个版本
approved_gate_ref 是什么
```

## 12. 演进路线

### 12.1 当前状态与已知债务

当前阶段仍处于文档校准与 P0 架构收敛阶段。第一批实现目标不是完成整个方法资产生态,而是跑通 7 类 P0 MethodContent 的定义发布闭环。

| 债务项 | 当前处理 | 影响阶段 |
|---|---|---|
| Qualification level_model 是否固化 | P0 先支持基础等级模型 | 概要 / 详细 |
| work 是否直接消费 TaskDefinition | P1 / 待确认 | L1-work 需求校准 |
| ProcessTemplateDef 到 process runtime 映射 | P0 先同步定义索引 | 架构 / 概要 |
| AIPolicyDef 与 governance Policy DSL | source/ref 先行 | governance 架构设计 |
| ViewProfile 优先级 | P0 只支持 role + object_kind + scope | P0 增强 |
| Plugin / Configuration | P1 后置 | Phase 2 |
| schema registry | 暂不引入 | Phase 3 |
| Plugin 签名机制 | P1 / Phase 3 | 供应链增强 |

### 12.2 触发条件

| 触发 | 动作 |
|---|---|
| P0 7 类 MethodContent 发布闭环稳定 | 进入 Phase 2 |
| 下游 sync lag 或 replay 需求上升 | 强化 outbox / replay / downstream cursor |
| ResolveViewProfile deny 或 latency 异常 | 引入缓存、优先级优化或 ViewProfile 规则增强 |
| fingerprint drift 持续出现 | 启动主动 drift 对账增强 |
| Plugin 需求开始阻塞组织采用方法集 | 启动 P1 Packaging |
| MethodConfiguration 成为组织方法集切换刚需 | 启动 P1 Composition |
| Marketplace 分发成为真实需求 | 启动 Phase 3 |
| snapshot / event schema 兼容问题出现 | 引入 schema registry / compatibility matrix |
| boundary violation rejection 持续出现 | 强化接口 contract 和架构检查 |

### 12.3 演进步骤

```
Phase 0: 文档校准
  - 需求 / 架构 / 概要 / 详细对齐
  - Qualification 边界确认
  - P0 / P1 边界确认

Phase 1: P0 定义发布闭环
  - 7 类 MethodContent
  - Command / Query
  - Publish / fingerprint / audit / outbox
  - Definition snapshot export
  - seed 最小基线
  - identity / process / capability-hub / artifact / governance / UI 样本同步

Phase 2: P0 增强 + P1 起步
  - replay / drift 对账增强
  - richer ViewProfile
  - MethodPlugin
  - MethodConfiguration
  - Plugin dependency DAG

Phase 3: 生态分发与治理增强
  - Marketplace 分发
  - package signing
  - schema registry
  - compatibility matrix
  - 更复杂 variability
```

### 12.4 目标架构

method-library 的目标是:
- 成为 7 类 P0 MethodContent 的单一定义真相源
- 让 identity / process / capability-hub / artifact / governance / UI 不再硬编码方法定义
- 通过 version、fingerprint、audit、outbox、snapshot 实现长期可追溯和可同步
- 通过 P1 Plugin / Configuration 支持组织级方法资产组装与可裁剪性
- 通过 Phase 3 marketplace / signing / schema registry 支持方法资产生态分发

目标架构图景:

```text
Method Definition Truth(P0)
  -> Reliable Publish Chain
  -> Snapshot / Event Sync
  -> Downstream Local Index
  -> P1 Packaging / Composition
  -> Phase 3 Marketplace Distribution
```

## 13. 风险与待确认事项

### 13.1 架构风险总览

| 风险 ID | 类型 | 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|---|---|
| R-001 | 边界风险 | Qualification / QualificationProfile / QualificationBinding 混淆 | 中 | 高 | 在架构、概要、详细和测试中持续保留边界红线 |
| R-002 | 反向写入风险 | identity / capability-hub 反向创建或改写 Qualification | 中 | 高 | 下游只消费 event / snapshot;新增定义必须走 method-library 发布流程 |
| R-003 | 同步风险 | event 丢失、snapshot 不兼容、下游 index drift | 中 | 高 | outbox、event replay、snapshot version、fingerprint compare |
| R-004 | 模型映射风险 | ProcessTemplateDef / TaskDefinition 到 process runtime 不匹配 | 中 | 高 | process 架构 / 概要阶段单独校准映射 |
| R-005 | work 边界风险 | TaskDefinition 直接变成 WorkItem 模板导致 L1-work 过早强绑定 | 中 | 中 | work 直接消费保持 P1 / 待确认 |
| R-006 | governance 风险 | AIPolicyDef 与 governance Policy DSL 分叉 | 中 | 高 | 当前采用 source/ref 关系,后续由 governance 架构确认 |
| R-007 | P1 污染风险 | Plugin / Configuration 反向拖慢 P0 定义发布闭环 | 中 | 中 | P1 后置,不得改变 P0 MethodContent 边界 |
| R-008 | 审计一致性风险 | published 但缺 audit / fingerprint / outbox | 低 | 高 | 发布事务必须同事务写 state、version、fingerprint、audit、outbox |
| R-009 | 视图风险 | ViewProfile 匹配规则过早复杂化或错配 | 中 | 中 | P0 只保留 role + object_kind + scope 与唯一 active 约束 |
| R-010 | 标准映射风险 | Qualification 与 SPEM 语义对齐不足 | 低 | 中 | ADR draft 0014 后续升级或并入正式 ADR |

### 13.2 高风险场景处置

| 场景 | 处置 |
|---|---|
| 下游同步延迟或漏消费 | 通过 ReplayDefinitionEvents 和 ExportDefinitionSnapshot 恢复 |
| fingerprint drift | CompareFingerprint / DetectDefinitionDrift(P1) 定位差异 |
| gate result 不可用 | publish 阻断,保持 draft / in_review |
| object storage blob 不可用 | 元数据可查;publish 依赖 blob 时阻断 publish |
| boundary violation | 拒绝请求,记录 boundary_violation_rejected_total 和审计日志 |
| P1 Configuration 激活错误 | supersede 回前版,并通过 event replay 通知下游 |

## 2. 业务背景与驱动力

> 校准来源:
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/01_arch_step_02_goals_constraints.md` 的“业务背景与驱动力”“架构目标表”和“当前阶段可接受取舍表”。

`L3-method-library` 的架构需要独立收敛,因为方法资产会被流程、身份、运行时、成员镜像、治理、体验和生态分发语境引用。如果没有独立定义源,方法资产定义会散落到消费仓、旧实现同步链或人工文档约定中,从而破坏版本稳定、受控消费和追溯一致性。

核心驱动力:

- 平台需要一个独立于流程实例、成员状态、治理执行和交易流程的方法资产定义源。
- 方法资产必须在正式版本语境中被稳定消费,而不是被下游本地约定替代。
- 方法资产变化必须可追溯,并能保护既有消费不被静默破坏。
- 外围增强和条件型依赖必须与核心闭环隔离,避免当前架构范围失控。

架构目标:

| 架构目标 | 说明 |
|---|---|
| 承载独立的方法资产定义真相 | 否则方法定义会退化为 process、identity、runtime 或 UI 的本地私有模型。 |
| 守住 Definition vs Use 的结构边界 | 否则本仓会吸收流程执行、成员状态、治理执行、交易或正文生命周期等相邻仓职责。 |
| 支撑正式方法资产版本稳定 | 否则下游正式引用会被静默变化破坏,无法形成可靠消费语境。 |
| 支撑下游按边界受控消费 | 否则消费仓需要复制或改写方法定义正文,定义真相会出现多源。 |
| 允许方法资产变化被追溯并保护消费一致性 | 否则正式化、版本语义变化和消费影响只能依赖人工约定或实现细节。 |
| 隔离核心闭环与外围增强 | 否则外围能力会拖垮核心架构判断。 |
| 保留条件型外部协作的可接入位置 | 否则治理结论、artifact 引用、console / SDK 体验等后续协作会被误写成核心前置或完全无法承接。 |

## 3. 约束条件

> 校准来源:
> - `design-calibration/01_arch_step_01_requirement_baseline.md`
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/01_arch_step_01_requirement_baseline.md` 的“架构硬约束表”和 `design-calibration/01_arch_step_02_goals_constraints.md` 的“不可变约束表”。

### 3.1 不可变约束

| 约束 | 架构含义 | 禁止的架构漂移 |
|---|---|---|
| 方法资产定义真相必须归属本仓 | 架构必须设置本仓为定义源,下游只能引用、消费或索引。 | 让 process、identity、governance、marketplace、UI 或 artifact 成为定义真相源。 |
| Definition vs Use 必须成立 | 本仓架构只表达定义源和正式消费边界,不承接运行时执行状态。 | 把流程实例、成员状态、治理执行、UI 渲染或 artifact 正文写成本仓核心能力。 |
| 正式版本语义不得静默变化 | 架构必须保留显式正式化、版本变化和追溯约束。 | 用覆盖更新、隐式同步或下游本地约定改变正式语义。 |
| 未正式化资产不得作为正式消费依据 | 架构必须区分非正式调整语境与正式使用语境。 | 让读取、引用、同步或运行时使用隐式触发正式化。 |
| 下游不得创建、修改或替代方法资产定义真相 | 下游消费面只能围绕正式引用、读取材料或能力边界设计。 | 允许消费仓反写定义正文或拥有替代定义。 |
| 运行期 / 事件协作不得写成源码级拥有关系 | 跨仓依赖必须按编译期、运行期、事件协作分层裁剪。 | 让下游仓链接本仓业务实现或把事件协作当作源码依赖。 |
| 治理结论只能作为正式化输入或依据引用 | 架构可承接治理结论,但不得承接治理裁决执行或 policy enforce。 | 把 Gate 流程、策略执行结果、治理运行状态写成本仓子域。 |
| artifact / archive 正文不得入仓 | 本仓只可定义 work product 语义或保存引用。 | 保存 artifact、证据文件、archive 正文或生命周期状态。 |
| marketplace 交易履约不得入仓 | 本仓最多提供方法资产定义或分发语义来源。 | 把定价、订单、购买、结算、安装记录写入本仓架构。 |
| 外围增强不得改变核心定义真相边界 | 外围能力只能作为后续增强。 | 让外围能力成为核心闭环成立前置。 |

### 3.2 当前阶段可接受取舍

| 取舍 | 当前口径 |
|---|---|
| Qualification / CapabilityDefinition 不作为当前核心资产独立项 | 当前保持待确认;若纳入需回写需求与架构全链。 |
| MethodPlugin / MethodConfiguration 不进入核心闭环 | 当前作为外围增强和演进方向处理。 |
| marketplace 生态发现只保留分发语义 | 当前不展开上架、交易、购买、安装和履约架构。 |
| AIPolicy override 和高级 ViewProfile 匹配不做深 | 当前只保留定义主题和外围增强承接。 |
| governance 正式化不写成强制主链 | 当前按条件型治理结论或依据引用处理。 |
| artifact 核心消费关系不提前闭口 | 当前只保留 WorkProductDefinition 语义和正文禁止边界。 |
| 下游消费影响回报机制不在本章定义 | 当前只保留一致性保护需求和摘要候选。 |
| 具体 P95 / SLO / 指标集不在架构目标层固定 | 当前只保留不阻塞主链、追溯可判断、关键状态可观察的架构要求。 |

### 3.3 架构非目标

| 非目标 | 不展开原因 |
|---|---|
| 不设计流程执行架构 | 流程执行、实例状态和编排属于 `L1-process` / runtime。 |
| 不设计成员身份和成员能力画像架构 | 成员身份、生命周期和成员实际能力属于 `L1-identity` 或相关成员仓。 |
| 不设计治理执行架构 | 治理裁决、Gate 和 policy enforce 属于 governance。 |
| 不设计 marketplace 交易架构 | 定价、订单、安装和履约不是方法资产定义源职责。 |
| 不设计 UI 渲染和会话架构 | 本仓最多定义可被消费的视图策略语义。 |
| 不设计外部正文、artifact、archive 生命周期 | 本仓只能保存摘要或引用。 |
| 不固定数据库、缓存、消息、协议、事件格式、指纹算法或部署平台 | 这些属于后续概要、详细、配置或实施文档。 |

## 4. 职责边界

> 校准来源:
> - `design-calibration/01_arch_step_03_responsibility_boundary.md`
>
> 延伸阅读:
> - 建议继续阅读该文件的“做什么清单”“不做什么清单”“易混淆职责表”和“边界红线清单”。

### 4.1 做什么

| 职责项 | 类型 | 说明 |
|---|---|---|
| 方法资产定义真相承载 | 做 | 这是本仓存在的核心职责,否则方法资产会散落到消费仓或文档约定。 |
| 方法资产身份与目录语义承载 | 做 | 没有稳定身份和目录语义,版本、消费和追溯都没有锚点。 |
| 方法资产正式化与版本语义承载 | 做 | 正式版本边界由本仓定义,否则下游正式引用无法稳定。 |
| 方法资产定义性关系承载 | 做 | 方法资产之间的定义性关联需要在定义源处保持一致。 |
| 方法资产分发语义承载 | 做 | 本仓可作为资产包或分发语义来源,但不承担 marketplace 交易。 |
| 方法资产变更与追溯依据承载 | 做 | 正式化、版本语义变化和影响消费的变化需要可追溯来源。 |
| 正式方法资产受控消费支撑 | 做 | 本仓为下游按边界消费提供结构前提,但不迁入下游运行真相。 |
| 外部依据摘要或引用边界承接 | 做 | governance、标准、artifact 或 marketplace 等外部语义只能以摘要或引用支撑本仓定义语境。 |

### 4.2 不做什么

| 职责项 | 类型 | 说明 |
|---|---|---|
| 流程执行和 ProcessInstance 状态 | 不做 | 该职责属于 `L1-process` / runtime。 |
| 成员身份、成员生命周期和成员实际角色状态 | 不做 | 该职责属于 `L1-identity` 或成员相关仓。 |
| 治理裁决、Gate 执行和 policy enforce | 不做 | 本仓最多承接结论或依据引用。 |
| 外部工具、MCP、A2A、provider 注册和访问裁决 | 不做 | 该职责属于 `L3-capability-hub` 及治理协作边界。 |
| marketplace 定价、订单、购买、结算、安装和履约 | 不做 | 本仓只可作为定义或分发语义来源。 |
| UI 渲染、会话、组件状态和交互执行 | 不做 | 本仓只定义可被消费的视图策略语义。 |
| artifact、证据文件、archive 或外部文档正文生命周期 | 不做 | 正文和制品生命周期属于相邻仓或外部系统。 |
| 认证登录、权限系统和操作主体鉴权实现 | 不做 | 这些属于身份、安全或治理边界。 |

### 4.3 易混淆职责

| 职责项 | 说明 |
|---|---|
| RoleDefinition 与成员实际角色状态边界 | 本仓可定义角色等方法语义,但成员是否具备某角色属于 identity / 成员状态。 |
| ProcessTemplate / TaskDefinition 与流程执行边界 | 本仓可定义模板和任务语义,但执行实例、活动状态和编排属于 process / runtime。 |
| AIPolicy 定义与治理执行边界 | 本仓可定义 AI 方针或目标语义,但裁决、enforce 和 Gate 执行属于 governance。 |
| ViewProfile 定义与 UI 渲染边界 | 本仓可定义视图策略语义,但字段渲染、页面状态和交互执行属于体验层。 |
| WorkProductDefinition 与 artifact 正文边界 | 本仓可定义 work product 语义,但 artifact、证据和 archive 正文生命周期不归本仓。 |
| MethodPlugin / MethodConfiguration 与 marketplace 交易边界 | 本仓可保留资产包或方法集组织语义,但交易、安装和履约不归本仓。 |
| 下游消费影响摘要与下游运行状态边界 | 本仓可保留一致性保护所需摘要候选,但不能拥有下游运行真相。 |

### 4.4 边界红线

- 不得把方法资产定义真相迁移到 process、identity、runtime、member-images、governance、marketplace、UI 或 artifact。
- 不得把流程执行状态、成员状态、治理执行、外部能力注册、交易履约、UI 渲染或 artifact / archive 正文作为方法资产定义成立条件。
- 不得让未正式化或仍处于调整语境的方法资产成为正式消费依据。
- 不得通过读取、引用、同步或运行时使用隐式触发正式化。
- 不得用下游本地约定静默覆盖正式方法资产版本语义。

| `L6-marketplace` | 输出 | 外围消费 | 方法资产包或分发语义来源 | 当前只保留外围生态发现和分发语义,交易履约不入仓。 |
| `L5-console` / `L0-sdk` | 输出 | 入口候选 | 方法资产管理与读取入口候选 | 当前作为体验 / 封装入口候选,不成为核心闭环前置。 |

### 5.2 边界说明

当前系统上下文以方法资产定义真相和核心下游受控消费为中心,因此主图只纳入 `L0-core`、`L0-bus`、`L1-process`、`L1-identity`、`L2-runtime` 和 `L2-member-images`。`L1-governance`、`L1-artifact`、`L6-marketplace`、`L5-console` / `L0-sdk` 与本仓相关,但当前只按条件型、候选或外围关系记录。外围或条件型对象不可用时,不得改写已成立的方法资产定义真相。

| 读取与追溯承载 | 正式存储承载 | 承载正式读取、目录识别、追溯查看和消费支撑所需读取材料。 | 被同步入口和后台维护依赖。 | 不指定 read model、cache、index 或 projection 实现。 |

### 7.2 部署说明

本章只固定逻辑运行承载结构,不固定部署平台或进程边界。同步入口承载、异步协作承载和后台维护承载在早期可以同部署,但架构上必须保持逻辑可分。正式状态承载必须独立于下游消费仓,读取与追溯承载也不得成为第二定义真相。`L0-bus` 是运行对接边界,不是 method-library 内部实现模块。

| 核心语义角色 | 允许依赖本仓内部已收敛的核心规则和正式摘要 / 引用语义。 | 禁止依赖外部系统正文、下游运行状态、UI 入口、marketplace 交易、governance 执行、技术承载实现细节。 | 核心语义必须保持最稳定。 |
| 支撑与摘要角色 | 允许依赖核心语义角色和正式外部摘要 / 引用。 | 禁止替代核心语义成为定义真相;禁止保存外部正文、下游运行状态或交易履约事实。 | 支撑分发、关系、外部依据和消费影响,但只以摘要 / 引用形态存在。 |
| 技术承载角色 | 允许被正式承接角色依赖,承载正式状态和读取材料。 | 禁止反向规定核心语义、状态词表、跨仓边界或业务规则。 | 技术承载是支撑条件,不是方法资产定义边界的来源。 |

### 9.2 一致性策略

| 数据关系 / 场景 | 关联数据类型 | 一致性口径 | 失败处理口径 | 说明 |

| 方法资产定义内部变化 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 明确失败,不形成部分完成的正式定义变化。 | 核心 truth 漂移会破坏定义源边界。 |
| 正式化与版本语义建立 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 未能同时成立时保持非正式或未完成口径。 | 正式使用语境和版本稳定必须一起成立。 |
| 定义性关系变化 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 不接受只改一侧语义的部分完成口径。 | 方法资产关系不能靠消费仓隐式修正。 |
| 正式真相到正式读取材料 | 正式真相数据 ↔ 读取 / 投影数据 | 最终一致 | 读取材料可保持旧视图或显式待收敛,不得改写 truth。 | 只读承接延迟不等于正式真相失效。 |
| 正式真相到下游消费材料 | 正式真相数据 ↔ 读取 / 投影数据 | 最终一致 | 下游暂未感知时保持待收敛或不可感知口径。 | 受控消费不要求下游即时同步成功。 |
| 正式化依赖外部治理结论 | 正式真相数据 ↔ 摘要 / 引用数据 | 前置一致 / 引用有效性一致 | 结论缺失或不可判定时挂起正式化。 | 外部治理可作为前置依据,但不迁入治理执行 truth。 |
| 方法资产与外部正文关系 | 正式真相数据 ↔ 引用关系数据 | 引用有效性一致 | 引用失效时显式失效或挂起相关能力,不得复制正文补齐。 | 引用有效不等于本仓拥有正文。 |
| 下游消费影响承接 | 正式真相数据 ↔ 摘要数据 | 最终一致 / 摘要一致 | 下游影响摘要缺失时保留未知或待确认口径。 | 本仓只承接正式摘要,不拥有下游运行 truth。 |
| 外围包 / 方法集组织与核心定义 | 正式真相数据 ↔ 正式真相数据 | 边界内强一致 | 不满足核心定义引用时不形成有效外围组织语义。 | 外围增强不能独立漂移为第二方法资产来源。 |
| 本仓与明确不拥有正文的边界 | 引用关系数据 ↔ 明确不拥有的正文 / 真相 | 边界约束一致 | 不回填为本仓真相;必要时挂起、拒绝或显式不可用。 | 外部正文和运行真相只能被引用或排除。 |

| 正式真相数据              |
| 方法资产定义 / 正式版本   |
+-------------+-------------+
              |
              | 派生 / 承接
              v
+---------------------------+
| 读取 / 投影 / 摘要数据    |

+-------------+-------------+
              |

+---------------------------+

- 引用关系只保存关系,不保存外部正文。
- 明确不拥有的正文 / 真相不得因引用、读取或运行需要进入本仓。

## 10. 关键交互与通信方式

> 校准来源:
> - `design-calibration/01_arch_step_09_interactions_communication.md`
>
> 延伸阅读:
> - 建议继续阅读该文件的“关键交互场景表”“通信方式判断表”和“交互方式停审记录”。

### 10.1 关键交互场景

| 交互场景 | 交互边界 | 交互目的 | 边界说明 |
|---|---|---|---|
| 方法资产定义建立与调整 | 外部同步入口边界 ↔ 本仓核心定义边界 | 让方法资产定义、身份和目录语义在本仓形成明确结果。 | 直接影响本仓正式真相,需要即时明确成功或失败。 |
| 方法资产正式化与版本变化 | 外部同步入口边界 ↔ 正式化与版本语义边界 | 让方法资产进入正式使用语境,或显式表达版本语义变化。 | 正式化和版本变化会影响下游消费前提。 |
| 方法资产目录、正式定义与追溯读取 | 下游或管理读取边界 ↔ 读取与追溯承载边界 | 支撑下游、管理入口和审计视角读取正式方法语义或追溯依据。 | 读取需要清晰可见、不可见或不可用口径。 |
| 方法资产变化可感知传播 | 本仓异步协作边界 ↔ `L0-bus` 协作边界 ↔ 下游消费边界 | 让正式化、版本变化或消费影响变化成为下游可感知信号。 | 不要求所有下游同步完成后本仓 truth 才成立。 |
| 外部治理结论送达 | `L1-governance` 条件型协作边界 ↔ 本仓正式承接边界 | 承接正式化所需的外部治理结论或依据引用。 | 本仓只消费结论或引用,不读取治理执行过程。 |
| 下游消费影响回报 | 下游消费边界 ↔ 本仓正式承接边界 | 承接下游对方法资产变化的正式影响摘要。 | 本仓只承接摘要,不扫描或拥有下游运行状态。 |
| 目录、读取和追溯材料维护 | 后台维护承载 ↔ 读取与追溯承载 | 推进由正式 truth 派生的目录、读取材料和追溯材料收敛。 | 不要求在同步入口内全部完成。 |
| 一致性保护与恢复承接 | 后台维护承载 ↔ 正式状态 / 读取材料 / 外部协作边界 | 检查并恢复变化感知、引用有效性、消费摘要和读取材料的收敛状态。 | 不得反向改写核心 truth。 |
| 外围资产包和方法集组织交互 | 外围入口或生态消费边界 ↔ 方法资产包与方法集组织语义边界 | 支撑包、方法集、分发语义或生态发现类外围能力。 | 当前不作为核心闭环前置。 |

### 10.2 通信方式判断

| 交互场景 | 推荐通信方式 | 失败处理口径 | 说明 |
|---|---|---|---|
| 方法资产定义建立与调整 | 同步请求 / 响应类交互 | 明确失败,不形成部分完成的正式定义变化。 | 核心 truth 内部要求强一致和明确裁定。 |
| 方法资产正式化与版本变化 | 同步请求 / 响应类交互 | 前置不足或外部结论缺失时挂起或失败。 | 正式化是本仓核心语义变化,但下游感知可以异步。 |
| 方法资产目录、正式定义与追溯读取 | 同步请求 / 响应类交互 | 返回明确可读、不可见、不可用或待收敛口径。 | 读取交互需要清晰结果,但读取材料可最终一致。 |
| 方法资产变化可感知传播 | 异步事件 / 回调类交互 | 保持待传播、待承接或可恢复状态。 | 核心 truth 不因传播延迟回滚。 |
| 外部治理结论送达 | 异步事件 / 回调类交互 | 结论未送达或不可判定时保持正式化挂起或依据缺失。 | 外部治理是条件型结论来源。 |
| 下游消费影响回报 | 异步事件 / 回调类交互 | 缺失时保持未知、待承接或待确认口径。 | 本仓只拥有影响摘要,不拥有下游运行 truth。 |
| 目录、读取和追溯材料维护 | 后台任务 / 延后承接类交互 | 失败时保持旧读取材料、待收敛或显式不可用。 | 派生材料服务读取和追溯,适合最终一致。 |
| 一致性保护与恢复承接 | 后台任务 / 延后承接类交互 | 保持待恢复、待确认或显式异常状态。 | 恢复类交互关注收敛,不改变 truth 来源边界。 |
| 外围资产包和方法集组织交互 | 同步入口用于管理;异步或后台用于传播和维护 | 外围依赖不可用时降级为外围不可用或待承接。 | 外围增强必须与核心闭环隔离。 |

#### 简化交互示意图

```text
+---------------------------+
| 同步请求 / 响应类交互     |
| 定义 / 正式化 / 读取裁定  |
+-------------+-------------+
              |
              | truth 成立后传播
              v
+---------------------------+
| 异步事件 / 回调类交互     |
| 变化感知 / 结论送达 / 回报 |
+-------------+-------------+
              |
              | 延后收敛
              v
+---------------------------+
| 后台任务 / 延后承接类交互 |
| 读取材料 / 追溯 / 恢复     |
+---------------------------+
```

图后说明:

- 同步交互只用于需要明确裁定的定义、正式化和读取边界。
- 异步交互用于跨边界事实传播、外部结果送达和下游摘要回报。
- 后台承接用于最终一致材料、追溯材料和恢复收敛。
- 图不表达运行时调用顺序、协议路径、事件传播链或实现组件。

## 11. 关键技术选型

> 校准来源:
> - `design-calibration/01_arch_step_10_technology_choices.md`
>
> 延伸阅读:
> - 建议继续阅读该文件的“关键技术机制表”“技术边界说明”和“必须废弃的旧口径”。

本文固定的是架构机制,不是具体技术栈。

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 |
|---|---|---|---|
| 通过正式承接层隔离外部输入与核心语义 | 防止治理结论、下游影响、外围入口或外部引用直接打穿方法资产定义 truth。 | 外部事实必须通过正式接缝和承接进入。 | 后续设计必须明确哪些输入是结论、摘要或引用。 |
| 核心 truth 与只读消费材料分层 | 防止下游读取或管理视图直接绑定核心 truth 结构。 | 正式真相与读取材料职责不同。 | 需要派生材料收敛、过期解释和读取不可用口径。 |
| 采用异步最终一致承接跨边界变化传播 | 防止下游可用性或外部承接结果变成本仓 truth 成立前提。 | 方法资产变化传播、治理结论送达和下游影响回报都跨边界。 | 引入传播延迟、待承接和失败恢复责任。 |
| 采用后台延后承接维护读取、追溯和恢复材料 | 防止目录、追溯、影响摘要和一致性恢复全部压入同步入口。 | 派生材料和恢复适合延后收敛。 | 需要待收敛、待恢复、显式不可用等状态口径。 |
| 采用引用 / 摘要优先而非复制外部正文 | 防止标准、治理、artifact、marketplace、下游运行状态或 UI 状态进入本仓形成第二 truth。 | 本仓只可保存摘要和引用,不得拥有外部正文。 | 需要处理引用失效、摘要缺失和外部不可用。 |
| 采用稳定正式版本与显式变化边界 | 防止正式方法资产被静默覆盖。 | 正式引用、追溯和下游消费都依赖稳定版本。 | 后续必须区分正式化、版本变化、替代/废弃等语义。 |
| 采用核心闭环与外围增强隔离 | 防止外围能力拖垮核心定义架构。 | 当前阶段先稳定定义、正式化、消费和追溯主线。 | 后续演进必须说明外围能力何时进入。 |
| 采用共享契约和正式引用基线 | 防止本仓重新定义跨仓共享概念。 | `L0-core` 是共享契约来源。 | 不能在本仓私造跨仓基础引用语义。 |

技术边界:

- 不固定数据库、缓存、消息、HTTP/RPC、对象存储、指纹算法、事件格式、任务调度、部署环境和代码目录。
- 后续概要、详细、配置和实施文档可以选择具体载体,但必须服从本章已收敛的承接、分层、异步、后台和引用边界。
- 旧实现机制只有在后续文档重新闭口后才能成为实现事实,不能从旧材料直接继承。

## 12. 备选方案与取舍

> 校准来源:
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读:
> - 建议继续阅读该文件的“当前主线方案”“方案路径比较表”和“方案边界说明”。

### 12.1 当前主线方案

当前采用“独立定义真相与分层承接方案”:

```text
独立方法资产定义 truth
  -> 正式承接层隔离外部输入
  -> 只读消费材料对外供给
  -> 异步最终一致传播跨边界变化
  -> 后台延后承接维护和恢复
  -> 外围增强与核心闭环隔离
```

该主线只表达结构路径,不表达数据库、缓存、事件、对象存储、指纹算法、API、DTO、repository 或 worker 实现。

### 12.2 方案路径比较

| 方案路径 | 当前结论 | 说明 |
|---|---|---|
| 独立定义真相与分层承接方案 | 采用 | 承接 Step 2/7/8/9/10 的全部核心结论。 |
| 文档 / Git 式方法资产仓 | 不采用 | 可作为外部正文或来源引用存在,但不能替代本仓定义 truth。 |
| 下游私有模型方案 | 不采用 | 会形成多源定义 truth,破坏 Definition vs Use。 |
| 共享数据库 / 共享 truth 方案 | 不采用 | 会造成编译期、运行期和数据所有权耦合。 |
| 直接暴露核心 truth 给下游读取 | 不采用 | 下游会绑定核心结构,核心演进成本上升。 |
| 同步等待所有下游确认方案 | 不采用 | 下游可用性会反向决定本仓 truth。 |
| 复制外部正文入仓方案 | 不采用 | 会形成外部 truth 副本,正文生命周期和权限边界失控。 |
| 全量外围能力前置方案 | 不采用为当前主线 | 外围增强保留演进位置,但不作为当前核心前置。 |
| 强治理前置方案 | 不采用为默认主线 | 当前只保留条件型治理结论或引用,不迁入治理执行。 |
| 全后台异步写入方案 | 不采用 | 核心 truth 裁定必须同步明确结果。 |

### 12.3 取舍说明

当前主线得到的是清晰的定义 truth、稳定的下游消费边界、外部输入隔离和未来演进空间。代价是需要维护正式承接层、只读消费材料、异步传播、后台维护、引用有效性和边界解释成本。这些成本是保护方法资产定义源的必要代价。

## 13. 横切关注点

| 核心消费稳定强化阶段 | 强化 process、identity、runtime、member-images 对正式方法资产的稳定消费和追溯能力。 | 当前只定义受控消费和变化感知口径。 | 更细粒度读取材料、消费影响摘要、兼容性和恢复承接。 | 核心下游消费出现不可解释滞后、引用漂移或消费材料不足。 |
| 条件型治理与外部依据增强阶段 | 在不迁入治理执行的前提下增强治理结论、标准依据、外部引用对正式化和追溯的支撑。 | 当前 governance 只作为条件型结论 / 引用。 | 更明确的治理结论接入、外部依据状态、引用失效和挂起口径。 | 某类方法资产正式化必须依赖治理结论或外部依据可判定。 |
| 外围包 / 方法集组织阶段 | 将外围包、方法集组织和分发语义纳入受控外围能力。 | 当前仅保留外围增强位置。 | 包组织、方法集组装、生态发现和分发语义承接。 | 组织采用方法集、生态发现或包分发成为方法资产消费前置。 |
| 观测与恢复强化阶段 | 强化关键状态、传播、读取材料、引用缺失和一致性恢复的可见性与正式恢复口径。 | 当前只给架构判断口径。 | 指标化、报告化、恢复流程化和验收化。 | 下游消费滞后、传播失败、引用失效或后台收敛失败影响验收裁决。 |
| 资产范围 / 下游范围扩展阶段 | 在已有主线基础上正式纳入新的资产类型或新的核心下游。 | Qualification / CapabilityDefinition、artifact 核心消费、console / SDK 前置仍挂起。 | 回写需求、系统上下文、依赖、数据、交互、横切和验收。 | 新资产类型或新核心下游被正式确认进入本轮范围。 |

当前阶段不是“全做完才算成立”,而是先让方法资产定义 truth、正式版本、受控消费和追溯一致性稳定成立。外围包 / 方法集、强治理接入、具体观测恢复和资产范围扩展都需要由明确边界压力触发,不能作为愿望池提前进入主线。

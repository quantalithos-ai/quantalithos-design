## 1. 业务背景与驱动力

### 1.1 业务背景

Quantalithos 不只是代码系统,也是**方法系统**。如果不把 RoleDefinition / TaskDefinition / WorkProductDefinition / ProcessTemplateDef / ViewProfile / AIPolicyDef 做成可管理的资产,那么:
- process 只能运行写死在代码里的模板
- identity 只能硬编码角色
- UI 不能按方法资产来渲染 ViewProfile
- governance 的 AI Policy 没有权威源
- Marketplace 无法分发"方法"本身

因此 method-library 必须成为"怎么做"的单一真相源。

### 1.2 业务驱动力

**业务驱动力**:
- 产品需要把方法论产品化,而不只是写进文档
- 组织需要发布自己的 Role / Template / Policy / ViewProfile
- Marketplace 需要分发方法资产包

**技术驱动力**:
- Definition vs Use 分离(SPEM)
- Template 家族与 Tailoring
- fingerprint drift 防护
- Plugin / Configuration 组装机制
- ViewProfile 为 UI 提供角色视图规则

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 功能 | MethodContent 6 子类可用 | 6/6 | 集成测试 |
| 功能 | 种子 9 Role + 8 Template 家族 | 100% | seed 验证 |
| 性能 | GetContent P95 | < 50ms cache / < 200ms PG | benchmark |
| 性能 | ResolveViewProfile P95 | < 30ms | benchmark |
| 一致性 | fingerprint_changed 覆盖率 | 100% | 回归测试 |
| 同步 | process / identity / governance / UI 同步成功率 | 100% 样本链 | E2E |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| Definition vs Use 严格分离 | SPEM 2.0 | 本仓只定义,不执行 |
| ProcessTemplateDef 是 method-library 权威源 | `domain/process/README.md` | process 只存执行索引 |
| published 内容核心字段不可改 | INV-ML-3 | 变更必须 supersede |
| fingerprint 变化必发事件 | INV-ML-4 | drift 防护强约束 |
| ViewProfile 归本仓 | ADR-0009 | UI 不直接自定义长期规则 |
| 8 家族对齐 24748-2 | INV-ML-21/22 | 家族枚举受控 |
| publish 必经 Gate | INV-ML-2 | 无直接发布 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| DSL(派生字段 / Policy / Variability patch) | 未定 | 后续 ADR |
| Plugin 签名机制 | 未定 | 可从 fingerprint-only 升级 |
| 搜索实现 | PG tsvector 起步 | 可换 ES / Typesense |
| Configuration 继承 | 暂不继承 | 企业版可扩展 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| MethodContent 记录 | 2000w(含历史版本) | 10w 组织 × 200 内容 |
| Plugin | 5w-50w | Marketplace 预估 |
| Configuration | 百万级 | 组织 / 项目 / 角色范围 |
| ResolveViewProfile QPS | 5000 | UI 高频消费 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 新方法资产种类 | 低 | 子类扩展 + ADR |
| 内容版本演进 | 中高 | semver + supersede |
| 组织方法集切换 | 中 | Configuration active / supersede |
| ViewProfile 规则变化 | 中 | role × object_kind × scope 匹配 |
| 下游 drift 风险 | 中 | fingerprint + source_drift |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **元模型驱动 + 版本化内容仓**(当前)| SPEM 对齐、下游统一消费 | 模型复杂 | ✅ |
| 文档仓 + 手工约定 | 成本低 | 无法执行 / 无法同步 / 无 drift 防护 | ❌ |
| 过程引擎内嵌模板 | 起步快 | 打破 Definition/Use 分离 | ❌ |

**最终选择**:**MethodContent 元模型 + Plugin + Configuration + fingerprint drift 机制**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 内容发布需 Gate | 资产可审计 | 发布流程更重 |
| supersede 而不直接改 | 版本历史清晰 | 内容膨胀 |
| Plugin / Configuration 双层 | 分发与组装分离 | 模型学习成本高 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
Method Authors / Tech Leads / Console Admins
                 │
                 ▼
       ★ quantalithos-method-library ★
       - MethodContent
       - Plugin / Configuration
       - fingerprint drift source
                 │
   ┌─────────────┼─────────────┬─────────────┬─────────────┐
   ▼             ▼             ▼             ▼             ▼
 process       identity     governance      UI        marketplace
 template sync role sync    ai policy src   ViewProfile cache  asset publish
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ MethodContent 6 子类
- ✅ MethodPlugin / MethodConfiguration
- ✅ fingerprint 管理
- ✅ ResolveViewProfile
- ✅ 种子数据(9 Role / 8 Template)

**不做什么**:
- ❌ Process execution(process)
- ❌ Role lifecycle(identity)
- ❌ Policy enforce(governance/runtime)
- ❌ Marketplace 交易流程(marketplace)
- ❌ UI 渲染(chat/console)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则阻断 |
| object storage | 99.9% | 只读元数据降级 |
| marketplace | 99.9% | 先组织内发布 |
| process / identity / governance | 99.9% | source_drift 告警,稍后重放 |

### 4.4 关键依赖风险

- MethodContent 与下游索引 drift
- ViewProfile 匹配逻辑出错影响整批 UI
- Plugin 环依赖或 Configuration 过度复杂

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
method-library-api
      │
      ▼
application / content services
   ├─▶ content domain
   ├─▶ plugin / configuration services
   ├─▶ fingerprint manager
   ├─▶ view profile resolver
   └─▶ subscriptions / publish pipeline
         │
         ├─▶ PostgreSQL
         ├─▶ object storage(guidance/examples/packages)
         └─▶ bus(outbox)
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| method-library-api | gRPC/HTTP 入口 | Rust |
| content domain | MethodContent 聚合逻辑 | Rust |
| plugin/config service | Plugin / Configuration 逻辑 | Rust |
| fingerprint manager | canonical JSON + drift detection | Rust |
| view resolver | ResolveViewProfile 高频查询 | Rust + cache |
| postgres | 元数据 / payload / plugin / config | PostgreSQL |
| object storage | guidance / examples / package blobs | S3 / MinIO |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| 下游获取内容 | RPC / query | 类型清晰 |
| 下游同步 | bus 事件 | 解耦 + replay |
| marketplace 分发 | plugin metadata + package blob | 分离交易与资产源 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| method_contents | method-library | process / identity / governance / UI |
| plugins | method-library | marketplace |
| configurations | method-library | 各下游仓 |
| content blobs | object storage | UI / packager / human readers |

### 6.5 部署拓扑

- 单服务 + PG + object storage 起步
- 高频 ResolveViewProfile 可加 Redis/LRU 缓存
- package 产物可直接复制到 Marketplace storage

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api
 │
 ▼
application
 │
 ▼
domain(Content / Plugin / Configuration)
 ▲
 │ ports
infra(PG / object storage / bus / cache)
```

### 7.2 层间约束规则

- domain 不依赖具体存储 / marketplace
- ViewProfile resolve 只读,不在 resolve 路径里改内容
- Plugin / Configuration 只引用 content_id,不复制正文
- published content 核心字段不可修改,只能 supersede

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| ContentStore | application/domain | PG / object storage adapter |
| FingerprintHasher | domain | infra serializer |
| DownstreamPublisher | application | bus outbox |
| ViewProfileResolver | application | cache + query adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(process / identity / governance / UI / marketplace) |
| 传出耦合 | 中(PG / object storage / bus) |
| 不稳定性 | 中 |
| 抽象度 | 高(method content 元模型) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| MethodContent | method-library | 下游索引仓 | 聚合内强一致 + event sync |
| Plugin | method-library | marketplace / installers | 强一致 |
| Configuration | method-library | 下游仓 / UI | 强一致 + 下发最终一致 |
| fingerprint | method-library | 下游 drift detector | 强一致 |
| blobs | object storage | readers / package consumers | ref 最终一致 |

### 8.2 一致性层次

- MethodContent / Plugin / Configuration 聚合内强一致
- 下游同步通过事件最终一致
- fingerprint_changed 是 drift 核心保护点

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| publish 事件下游漏消费 | replay + source_drift 检测 |
| object storage 写失败 | content 保持 draft,不 publish |
| Configuration 激活后下游未更新 | lag 告警 + replay |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| DSL(派生字段/patch)未定 | 复杂度后置 | P1 |
| Plugin 签名机制未定 | 供应链可信度 | P1 |
| process template 到 engine 的映射实现未验证 | 下游 process 同步 | P1 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| ResolveViewProfile > 30ms | 持续 1 周 | 引入更强缓存 |
| fingerprint drift > 3 / 月 | 1 月 | 强化同步机制 |
| Plugin 发布失败率 > 5% | 1 月 | 重写分发流程 |

### 12.3 演进步骤

```
阶段 1: MethodContent 6 子类落地
阶段 2: Plugin / Configuration / seed 数据
阶段 3: ViewProfile 高频消费优化
阶段 4: Marketplace 深度集成 / DSL / 签名
```

### 12.4 目标架构

method-library 的目标是:
- 定义平台方法资产的单一真相源
- 让 process / identity / governance / UI 不再硬编码方法论
- 通过 fingerprint 和版本链实现长期可演化

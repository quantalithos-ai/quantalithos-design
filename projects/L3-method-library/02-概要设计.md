## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L3-method-library` 不是文档资料库,也不是流程执行仓,更不是 UI 规则临时脚本仓。它是 **“方法定义资产中心”**。

你可以把它理解成:
- 平台里正式可被引用、发布、版本化的方法定义资产到底有哪些
- Qualification、RoleDefinition、TaskDefinition、WorkProductDefinition、ProcessTemplateDef、ViewProfile、AIPolicyDef 这 7 类 P0 MethodContent 的权威源在哪里
- 这些定义资产怎样从 draft 演进到 published / deprecated / retired
- 这些定义资产怎样生成 fingerprint、snapshot 和 outbox event
- 下游仓怎样稳定同步这些定义,并通过 fingerprint 感知 drift
- P1 阶段一组方法资产怎样被打包成 MethodPlugin,再怎样被组装成 MethodConfiguration

这些事情,都由 `L3-method-library` 负责。

它的核心边界可以用一句话概括:

```text
method-library 管 Definition truth,
identity / process / work / artifact / governance / UI 管各自的 Use truth。
```

### 1.2 为什么要单独有这个仓

如果没有 `L3-method-library`,这些方法资产事实就会散落在:
- `identity` 各自维护的 role / qualification 定义副本里
- `process` 各自维护的 task / template 内容里
- `capability-hub` 各自维护的 qualification 语义锚点里
- `artifact` 各自维护的 work product 定义副本里
- `governance` 自己写死的 policy 配置里
- `UI` 本地维护的 view profile 规则里
- marketplace 的上架元数据或包元数据里
- 各类 markdown / README / 会议纪要里

结果就会出现:
- 平台里到底“应该怎么做”没有统一权威源
- `Qualification`、`RoleDefinition`、`TaskDefinition`、`WorkProductDefinition`、`ProcessTemplateDef`、`ViewProfile`、`AIPolicyDef` 在不同仓逐步漂移
- 下游能执行,但不知道当前执行的是否还是同一版方法资产
- capability-hub 能绑定工具能力,但缺少统一 Qualification 定义锚点
- artifact 能保存制品实例,但缺少统一 WorkProductDefinition 定义锚点
- Marketplace 可以分发包,却不能证明包里的资产和平台当前权威定义一致
- 方法论只能写在文档里,无法成为可发布、可验证、可同步的正式资产

所以 `L3-method-library` 必须独立存在,作为:
> **平台 Qualification、角色、任务、制品、流程模板、视图策略与 AI Policy 定义资产的单一真相源。**

P1 的 MethodPlugin / MethodConfiguration 是围绕这些定义资产的打包、组装和分发能力,不是 P0 阶段替代 7 类 MethodContent 的主线。

### 1.3 新人最容易混淆的几个词

#### MethodContent
就是:
> 一类正式方法资产的抽象基类。

它不是一篇说明文档,而是平台真正承认的资产对象。

#### Qualification
就是:
> 一个正式胜任力 / 资质定义资产。

它描述某类能力、知识、经验或职责资格的定义来源。它不是某个成员已经具备哪些能力的个人画像。

#### QualificationProfile
就是:
> `identity` 中某个成员实际具备哪些 Qualification 的画像。

它不属于 `L3-method-library`。method-library 只定义 Qualification,不记录某个成员是否具备它。

#### QualificationBinding
就是:
> `capability-hub` 中 Qualification 与工具、provider、MCP / A2A 能力入口之间的绑定关系。

它不属于 `L3-method-library`。method-library 只提供 Qualification 定义锚点,不决定某个能力入口如何接入。

#### RoleDefinition
就是:
> 一个正式角色定义资产。

它不是 `identity` 里的 `RoleCatalogEntry`。前者是权威定义,后者是运行时索引。

#### TaskDefinition
就是:
> 一个正式任务定义资产,描述某类方法任务应该怎样被过程模板引用。

它不是 `work` 里的 `WorkItem`。前者是方法定义,后者是项目中的协作任务事实。

#### WorkProductDefinition
就是:
> 一个正式制品定义资产,描述某类制品的定义、约束、验收口径和证据要求。

它不是 `artifact` 里的具体制品实例或正文。前者是定义,后者是项目运行中产生的实际产物。

#### ProcessTemplateDef
就是:
> 一个正式过程模板定义。

它不是 `process` 里的 `ProcessInstance`,也不是运行中的流程执行真相。

#### ViewProfile
就是:
> 一个正式视图策略定义,回答某种 role × object_kind × scope 下应该怎么看。

它不是 UI 本地临时渲染规则。

#### AIPolicyDef
就是:
> 一个正式 AI Policy 定义资产。

它不是 governance runtime 当下正在 enforce 的那条运行规则本体。

#### MethodPlugin
就是:
> 一组方法资产的打包单元。

它不是 marketplace 上的交易条目本体,也不是 P0 定义发布闭环的替代物。它属于 P1 的资产组装与分发能力。

#### MethodConfiguration
就是:
> 一组 plugin 的激活与组装结果。

它不是下游运行时状态本体,而是方法资产组合真相。P0 阶段只需要明确它的远期位置,不让它污染 7 类 MethodContent 主链。

#### fingerprint
就是:
> 用 canonical JSON 计算出来的内容哈希,用于识别方法资产语义是否变化。

它不是版本号,也不是下游自己猜出来的 drift 标志。

#### 1.4.1 需求基线

概要设计必须继承 `00-需求文档.md` 中已经确认的 P0 / P1 分界。

P0 MethodContent 为 7 类:

```text
Qualification
RoleDefinition
TaskDefinition
WorkProductDefinition
ProcessTemplateDef
ViewProfile
AIPolicyDef
```

P0 主链路为:

```text
Draft MethodContent
  -> Review / Publish Gate
  -> Publish MethodContent
  -> Generate Fingerprint
  -> Write Audit Record
  -> Write Outbox Event
  -> Export Definition Snapshot
  -> Downstream Sync
```

P1 后置能力为:

```text
MethodPlugin
MethodConfiguration
Plugin dependency DAG
Variability application
Marketplace package distribution
Downstream active reconciliation
```

本文后续涉及用户故事、功能需求、目标和非目标时,只引用需求文档中的:

```text
US-001~US-011
F-001~F-011
G-1~G-8
NG-1~NG-8
```

不得在概要设计中重新创造一套仓内编号。

#### 1.4.2 边界基线

method-library 拥有:

```text
MethodContent 定义真相
version / lifecycle / fingerprint
definition snapshot
publish audit
outbox event source
```

method-library 不拥有:

```text
QualificationProfile        -> identity
QualificationBinding        -> capability-hub
CapabilityAccessDecision    -> capability-hub / governance
ProcessInstance             -> process
WorkItem / Backlog          -> work
Artifact 实例正文           -> artifact
Policy enforce result       -> governance
Marketplace 交易记录        -> marketplace
```

Qualification 三仓边界必须保持清晰:

```text
L3-method-library
  owns Qualification definition

L1-identity
  owns QualificationProfile

L3-capability-hub
  owns QualificationBinding
```

#### 1.4.3 架构基线

概要设计必须承接 `01-架构设计.md` 中已经确认的机制:

```text
MethodContent 元模型
PostgreSQL 定义真相存储
object storage 保存 blob / package ref
outbox + L0-bus
Definition Snapshot Exporter
schema version
canonical fingerprint
server-side ResolveViewProfile
boundary validation
```

这些不是零散功能点,而是方法资产发布、同步、追溯和漂移防护主链的一部分。

#### 1.4.4 当前概要设计的校准原则

后续章节必须遵守:

- `L3-method-library` 不应按 P0 7 类 MethodContent 名字平铺理解,而应按方法资产主链责任拆分
- 本文重点不是列对象清单,而是讲清主要组成部分、职责边界、外部交互、接口族、数据流和数据所有权
- method-library 只能向下游提供 Definition,不能替下游持有 Use truth
- Plugin / Configuration / Marketplace 相关能力在本文中可说明远期位置,但不能污染 P0 定义发布闭环
- 概要设计不写 Rust 结构体、数据库 DDL、事务伪代码或单元测试用例

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的方法资产心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,平台不只要运行代码,还要运行方法。用户真正需要的不是“把方法写在 README 里”,而是:
- Qualification、角色、任务、制品、过程模板、视图规则、AI Policy 都有正式定义源
- 这些定义可以发布、弃用、退役,并保留版本与 fingerprint
- `identity`、`process`、`capability-hub`、`artifact`、`governance`、`UI` 都能基于同一套方法定义资产协作
- P1 阶段 plugin 与 configuration 可以把方法资产变成可打包、可启用、可分发的组合单元
- 下游仓能知道自己正在消费哪一版权威资产,以及何时 drift

如果把这些逻辑分别散落到:
- 各业务仓自己的本地定义
- 各类 markdown / README / 会议记录
- UI 本地规则配置
- capability-hub / artifact 本地锚点
- marketplace 元数据或包元数据

系统会快速退化成:
- Qualification、角色定义、任务定义、制品定义、模板定义、AI Policy 和视图策略逐渐分叉
- 下游仓可以运行,但无法证明所用资产仍是当前权威定义
- capability-hub 的 QualificationBinding 缺少统一语义锚点
- artifact 的 artifact kind / acceptance template 缺少统一定义来源
- P1 plugin / configuration 失去稳定组合基础
- 方法论无法产品化、可验证化、可分发化

因此,本概要设计的任务就是:
> **把 `L3-method-library` 写成一个新人也能看懂的“方法定义资产中心”,而不是把定义、执行、画像、绑定、实例、分发和消费索引混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| MethodContent 正式化 | 设计已存在,仓级主链未收稳 | P0 7 类 MethodContent 形成正式资产真相 | 需正式收敛 |
| Template / Role / Policy 漂移 | 下游各自同步风险高 | fingerprint_changed 覆盖率 100% | 需固定 drift 主链 |
| ViewProfile 权威源 | UI 本地拼接风险高 | ResolveViewProfile 成为权威解析入口 | 需单列并固定 |
| Plugin / Configuration 组装 | 仅架构草案 | 可打包、可启用、可分发 | 需形成产品化主线 |
| 下游同步链 | process / identity / capability-hub / artifact / governance / UI 各自消费 | 同步成功率 100% 样本链 | 需收稳接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把平台的 Qualification、角色、任务、制品、过程模板、视图策略和 AI Policy 变成可管理、可发布、可追溯、可被下游稳定消费的正式定义资产
- **技术问题**:P0 7 类 MethodContent、publish gate、version、fingerprint、snapshot、outbox event、ResolveViewProfile 与下游同步之间如何稳定建模,并与 identity / process / capability-hub / artifact / governance / UI 清晰协作而不混层
- **P1 后置问题**:MethodPlugin、MethodConfiguration、Plugin dependency DAG、Variability 与 Marketplace 分发属于资产组装与生态分发能力,需要在概要设计中保留位置,但不能反向污染 P0 定义发布同步闭环

## 3. 目标与非目标

### 3.1 目标来源

本文不重新创造概要设计专属目标,而是继承 `00-需求文档.md` 的 `G-1~G-8`。概要设计的职责是说明这些目标分别由哪些主要组成部分、交互方式、接口族、数据流和数据所有权承接。

### 3.2 目标承接方式

| 需求目标 | 目标含义 | 概要设计承接点 |
|---|---|---|
| G-1 | MethodContent 7 类可 CRUD + 发布 | 方法定义真相部分、发布治理部分、查询与审计追溯部分 |
| G-2 | 8 种 Template 家族入种子数据 | 初始方法基线装载、关系校验、查询出口 |
| G-3 | 9 种 RoleDefinition 种子 | 方法定义真相部分、identity 同步边界、snapshot / event |
| G-4 | ViewProfile 可供下游消费 | ResolveViewProfile、查询解析出口、UI / console 交互 |
| G-5 | ProcessTemplate 发布后 process 可同步索引 | 下游同步与漂移防护、Definition Snapshot Exporter、outbox event |
| G-6 | RoleDefinition 发布后 identity 刷索引成功 | identity 下游同步、RoleCatalogEntry 外部索引边界、fingerprint |
| G-7 | fingerprint drift 检测可用 | canonical fingerprint、fingerprint_changed event、source_drift 追溯 |
| G-8 | Qualification 定义真相可发布、可版本化、可同步 | Qualification 定义归属、identity / capability-hub 同步、QualificationProfile / QualificationBinding 边界 |

这些目标在本文中不会展开成具体函数、表结构或测试用例。函数、事务、异常和测试细节进入 `03-详细设计.md` 与测试方案。

### 3.3 非目标来源

本文不重新创造概要设计专属非目标,而是继承 `00-需求文档.md` 的 `NG-1~NG-8`。概要设计需要把这些非目标转化为明确的模块边界和数据所有权边界。

### 3.4 非目标承接方式

| 非目标 | 不做什么 | 正确归属 / 边界 |
|---|---|---|
| NG-1 | 不执行流程编排 | process 拥有 ProcessInstance 和执行真相 |
| NG-2 | 不管理角色生命周期状态机 | identity 管成员生命周期;method-library 只定义 RoleDefinition |
| NG-3 | 不执行 Policy enforce | governance / runtime 执行 enforce;method-library 只定义 AIPolicyDef |
| NG-4 | 不做 Marketplace 交易逻辑 | marketplace 拥有上架、交易、计费记录;method-library 只提供资产源和 P1 package metadata |
| NG-5 | 不实现 UI 渲染 | L5 / L6 渲染 UI;method-library 只提供 ViewProfile 和解析结果 |
| NG-6 | 不管理成员 QualificationProfile | identity 拥有成员画像;method-library 只定义 Qualification |
| NG-7 | 不管理 QualificationBinding / tool-provider 接入绑定 | capability-hub 拥有能力入口绑定;method-library 只提供 Qualification 定义锚点 |
| NG-8 | 不做 CapabilityAccessDecision | capability-hub / governance 做运行时访问裁决;method-library 不判断上下文是否允许访问工具或 provider |

非目标不是“以后可能忘了做”的空白区,而是明确的系统边界。后续主要组成部分、外部交互和数据所有权矩阵都必须持续维护这些边界。

## 4. 约束条件

### 4.1 技术约束

这里的技术约束不是通用口号,而是会直接影响后续主要组成部分、接口族、数据流和数据所有权的硬约束。

| 约束 | 设计影响 |
|---|---|
| Definition vs Use 必须分离 | method-library 只拥有定义真相;下游仓拥有使用真相 |
| P0 / P1 必须分离 | P0 先完成 7 类 MethodContent 发布同步闭环;Plugin / Configuration / Marketplace 后置 |
| P0 MethodContent 固定为 7 类 | 后续主要组成部分不能再按旧 6 子类或临时功能清单展开 |
| Qualification 三仓边界必须稳定 | method-library owns Qualification;identity owns QualificationProfile;capability-hub owns QualificationBinding |
| published 核心字段不可原地修改 | 必须有发布治理、version、supersede 和 audit trace |
| fingerprint 必须由 canonical 内容生成 | drift 判断不能依赖自然语言描述或下游猜测 |
| outbox + L0-bus 是跨仓同步底座 | 发布成功后必须可异步传播、重试和重放 |
| Definition Snapshot Exporter 是下游兜底入口 | 下游错过事件或需要重建索引时,必须能拉取 snapshot |
| ViewProfile 必须服务端解析 | UI / console 不应长期本地拼接权威视图规则 |
| 下游不得反向改写定义真相 | process / identity / capability-hub / artifact / governance / UI 只能消费或建立本地索引 |

### 4.2 资源约束

| 资源约束 | 设计影响 |
|---|---|
| MethodContent 与历史版本会长期增长 | 需要版本链、查询出口和审计追溯,不能为了节省记录破坏 supersede |
| object storage 只保存 blob / guidance / package ref | 元数据、生命周期、fingerprint 和关系真相仍在定义仓主库 |
| P1 Plugin / Configuration 复杂度高 | P0 文档只保留位置和边界,不让依赖 DAG / variability 影响 P0 主链 |
| 查询与追溯会高频读取 | 后续需要 read model / cache / projection 预留,但概要阶段不写具体索引 |
| 下游同步会有重放和补偿 | outbox backlog、snapshot export、event replay 必须在模块划分中有位置 |

### 4.3 时间约束

| 阶段 | 必须先做 | 暂不展开 |
|---|---|---|
| P0 | 7 类 MethodContent 草稿、发布、版本、fingerprint、audit、outbox、snapshot、下游同步 | MethodPlugin 完整包管理 |
| P0 | identity / process / capability-hub / artifact / governance / UI 的定义同步接缝 | Marketplace 分发闭环 |
| P0 | ViewProfile 服务端解析 | 复杂 UI preset / override 策略 |
| P0 | Qualification 三仓边界 | 运行时 CapabilityAccessDecision |
| P1 | Plugin / Configuration / Variability / Marketplace | 不阻塞 P0 发布同步闭环 |

`TaskDefinition` 是否直接给 `work` 作为 WorkItem 模板来源,当前仍为 P1 / 待确认,等待 `L1-work` 校准。P0 只要求 `process` 可以消费 TaskDefinition。

### 4.4 合规与审计约束

| 约束 | 设计影响 |
|---|---|
| publish 必须有 approved gate_ref | 发布治理部分必须接入 gate 结果,不得无审批直接 published |
| 发布、废弃、退役必须有 actor_ref | 审计追溯必须能回答谁在什么时候做了什么 |
| audit trace 必须串起 version / fingerprint / event / snapshot | 后续数据流不能只写内容表,还要包含审计和 outbox |
| AIPolicyDef 是 policy source | governance 才拥有 enforce result,method-library 不保存执行裁决 |
| drift 发现必须留痕 | fingerprint_changed / source_drift 不能静默吞掉 |
| 标准口径必须保持 | SPEM / 24748 / 29110 / 42001 对齐内容不能被本仓私有命名随意替换 |

### 4.5 一致性与降级约束

| 范围 | 一致性要求 | 降级 / 补偿 |
|---|---|---|
| MethodContent 发布事务 | 本仓内部强一致 | state、version、fingerprint、audit、outbox 同事务或同一 unit of work |
| 跨仓同步 | 最终一致 | outbox retry、event replay、snapshot resync |
| 下游索引 | 最终一致 | 下游保存 source_version / fingerprint,必要时重建 |
| object storage blob | 元数据优先,blob ref 可恢复 | publish 前关键 blob 缺失应阻断;非关键 blob 可标记 degraded |
| L0-bus 暂不可用 | 不丢事件 | 写入 outbox backlog,等待 relay 恢复 |

### 4.6 容量规划假设

| 资源 | 上限 | 量化依据 |
|---|---|---|
| MethodContent 记录 | 2000w(含历史版本) | 多组织长期资产增长 |
| Plugin | 5w-50w | Marketplace 与组织内分发预估 |
| Configuration | 百万级 | 组织 / 项目 / 场景级组合 |
| ResolveViewProfile QPS | 5000 | UI 高频消费 |

这些容量值是目标架构假设,不是 P0 首批实现承诺。P0 首批只承诺:

```text
7 类 MethodContent 发布闭环
下游同步闭环
Definition / Use 边界红线
audit / fingerprint / outbox / snapshot 主链
```

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text

                         | Method Author / Reviewer  |

                                       |

                           | - WorkProductDef     |                |

                    +---------------------------------------------------------+
```

### 5.2 位置解释

- `L3-method-library` 位于方法能力层,负责 P0 7 类 MethodContent 的 Definition truth
- 方法作者、审核者、管理员和审计者通过 Command / Query 入口维护、发布和查询方法定义资产
- governance 在发布前提供 gate,也在 AIPolicyDef 发布后作为下游消费者同步 policy source
- `L0-bus` 承载 published、fingerprint_changed、source_drift 等定义事件
- 下游仓通过事件和 snapshot 消费定义,建立各自本地索引或运行态引用
- marketplace 只在 P1 消费 MethodPlugin package metadata,不阻塞 P0 发布同步闭环
- 这个仓的角色不是“执行方法”,而是“定义方法并让别人稳定消费”

所以 `L3-method-library` 在全局里的角色是:
> **把平台的 Qualification、角色、任务、制品、流程模板、视图策略与 AI Policy 收敛为可发布、可版本化、可审计、可同步的定义资产中心。**

### 5.2.1 通信方式总览

| 方向 | 通信方式 | 说明 |
|---|---|---|
| 人 / 管理入口 -> method-library | Command / Query | 创建草稿、提交审核、发布、废弃、退役、查询追溯 |
| method-library <-> governance | Gate / definition sync | 发布前 gate;AIPolicyDef 发布后 governance 消费 policy source |
| method-library -> L0-bus | Outbound Event | 发布 `*.published`、`fingerprint_changed`、`source_drift` 等事件 |
| 下游 -> method-library | Snapshot Query | 下游重建索引、错过事件、主动对账或冷启动同步 |
| UI / console -> method-library | Query / Resolve | 调用 `ResolveViewProfile` 或只读查询 |
| marketplace(P1) <- method-library | package metadata / event | P1 阶段消费 MethodPlugin,不拥有方法资产正文真相 |

### 5.3 系统边界

**做什么**:
- 持有 P0 7 类 MethodContent 定义真相
- P1 持有 MethodPlugin / MethodConfiguration 组合真相
- 管理 publish / supersede / deprecate / retire 生命周期
- 生成与维护 fingerprint / source_drift 信号
- 维护 audit record、outbox event source 与 definition snapshot
- 提供 ResolveViewProfile 等只读解析出口

**不做什么**:
- 不执行 process runtime
- 不拥有 identity 成员真相、RoleCatalogEntry 或 QualificationProfile
- 不拥有 capability-hub 的 QualificationBinding 或 CapabilityAccessDecision
- 不拥有 artifact 的制品实例、正文或 evidence instance
- 不执行 governance policy enforce result
- 不渲染 UI
- 不承担 marketplace listing / transaction / install record 真相

### 5.3.1 Definition truth / Use truth 边界

| 模块 | method-library 提供 | 对方拥有 |
|---|---|---|
| identity | RoleDefinition / Qualification definition | RoleCatalogEntry、QualificationCatalogEntry、QualificationProfile、成员生命周期 |
| process | TaskDefinition / ProcessTemplateDef | ProcessInstance、Activity execution、执行索引 |
| capability-hub | Qualification definition | QualificationBinding、能力入口绑定、部分访问裁决上下文 |
| artifact | WorkProductDefinition | Artifact instance、artifact body、evidence instance |
| governance | AIPolicyDef | gate / enforce result、runtime decision |
| UI / console | ViewProfile / ResolveViewProfile | rendering state、前端交互状态 |
| marketplace(P1) | MethodPlugin package metadata | listing、transaction、install record |

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则阻断写入与发布 |
| object storage | 99.9% | guidance / example / package blob 暂不可读时,保留元数据只读 |
| L0-bus | 99.95% | publish backlog / replay,不得静默丢失 drift 信号 |
| process / identity / capability-hub / artifact / governance / UI | 99.9% | 下游延迟只影响消费,method-library 仍保留权威定义、outbox backlog 与 snapshot 兜底 |
| marketplace(P1) | 99.9% | P1 package metadata 分发失败不阻断 P0 定义仓本体 |

### 5.5 关键依赖风险

- MethodContent 与下游索引 drift 会让 process / identity / capability-hub / artifact / governance / UI 基于过期定义运行
- L0-bus 或 outbox relay 延迟会放大下游索引滞后,必须依赖 snapshot / replay 兜底
- Qualification 边界不清会让 identity 的 QualificationProfile 或 capability-hub 的 QualificationBinding 反向污染定义仓
- WorkProductDefinition 边界不清会让 artifact instance 或 evidence 误入 method-library
- ViewProfile 匹配错误会影响整批 UI 消费面
- P1 Plugin 依赖环或 Configuration 组合爆炸会让方法资产失去可控组装能力
- Marketplace 的商业化诉求可能反向污染 P0 定义内容模型

## 6. 本仓由哪些主要组成部分构成

### 6.1 划分原则

主要组成部分不是对象列表,不是代码目录,也不是用户故事或功能需求列表。

```text
用户故事 = 需求来源
功能需求 = 系统能力
主要组成部分 = 架构承接方式
```

本仓主要组成部分按以下依据划分:

| 依据 | 在本仓中的含义 |
|---|---|
| 职责边界 | 每个部分负责什么、不负责什么必须能清楚说明 |
| 数据所有权 | 哪些部分拥有 MethodContent 定义真相、事件、snapshot、审计追溯或组合真相 |
| 主流程位置 | 对应 P0 从 draft 到 publish、fingerprint、outbox、snapshot、downstream sync 的阶段 |
| 变化原因 | 发布治理、关系校验、同步、查询、P1 打包组装的变化原因不同 |
| 外部交互 | Command / Query、governance gate、L0-bus、下游 snapshot query、UI resolve 等交互链不同 |
| 不变量 / 规则 | published 不可原地修改、Definition/Use 分离、Qualification 三仓边界等规则需要独立保护 |
| P0/P1 优先级 | P0 先完成定义发布同步闭环,P1 再进入 Plugin / Configuration / Marketplace |

反例:

```text
不要拆成:
- Qualification 部分
- RoleDefinition 部分
- TaskDefinition 部分
- US-001 部分
- F-001 部分
```

这些是对象、需求来源或系统能力,不是概要设计中的主要组成部分。

### 6.3 主要组成部分说明

#### A. 对外入口与访问部分

- **它是什么**: method-library 的入口层,负责接收外部 command、query、event consumer 和 operations job 触发
- **为什么单独有它**: 外部入口变化频率高,但不应污染定义真相、发布规则和边界校验
- **负责什么**:
  - 接收 Create / Update draft、Publish、Deprecate、Retire、ResolveViewProfile、GetDefinitionTrace 等入口请求
  - 接收必要的外部事件或 operations job 触发
  - 进行基础请求校验、幂等键、调用方上下文传递
- **不负责什么 / 容易混淆点**:
  - 不拥有 MethodContent 定义真相
  - 不做 publish 规则裁决
  - 不直接写 outbox 或 snapshot 语义
- **与其他部分交互**:
  - 下游: 应用编排与发布治理部分、查询解析与追溯部分
  - 外部: 管理入口、UI / console、downstream consumers、operations
- **后续详细设计展开点**:
  - Command / Query / Job / Event Consumer 接口族
  - 幂等和调用元信息传递

#### B. 应用编排与发布治理部分

- **它是什么**: P0 主流程编排层,负责把草稿、发布门禁、生命周期变化、版本、fingerprint、审计和 outbox 串成一致流程
- **为什么单独有它**: 发布不是普通 CRUD。published 不可原地修改、publish gate、supersede、audit trace 都需要统一编排
- **负责什么**:
  - 编排 draft / in_review / published / deprecated / retired 生命周期
  - 接入 governance gate 结果
  - 编排 version、supersede、canonical fingerprint、audit record、outbox event
  - 保证发布链的一致性边界
- **不负责什么 / 容易混淆点**:
  - 不拥有 MethodContent 正文真相
  - 不替下游确认消费成功
  - 不执行 governance enforce result
- **与其他部分交互**:
  - 上游: 对外入口与访问部分
  - 下游: 方法定义真相与规则部分、关系校验与边界保护部分、事件与快照同步部分、查询解析与追溯部分
  - 外部: governance gate
  - 交互类型: 应用编排型 + 发布治理型
- **后续详细设计展开点**:
  - Publish / Supersede / Deprecate / Retire 主流程
  - gate_ref、actor_ref、expected_version、幂等策略

#### C. 方法定义真相与规则部分

- **它是什么**: method-library 的核心定义真相层,回答“平台到底有哪些正式方法定义资产”
- **为什么单独有它**: 没有独立定义真相层,Qualification、Role、Task、WorkProduct、Template、ViewProfile、AIPolicyDef 会散落到下游仓和文档里
- **负责什么**:
  - 拥有 P0 7 类 MethodContent 定义真相:
    `Qualification / RoleDefinition / TaskDefinition / WorkProductDefinition / ProcessTemplateDef / ViewProfile / AIPolicyDef`
  - 维护定义资产的核心元信息、内容结构、生命周期可变性规则和引用锚点
  - 为版本、fingerprint、snapshot 和下游索引提供稳定定义来源
- **不负责什么 / 容易混淆点**:
  - 不保存 QualificationProfile、QualificationBinding、ProcessInstance、WorkItem、Artifact instance、Policy enforce result
  - 不按 7 类对象分别拆成 7 个主要部分
  - 不保存 markdown 说明的非结构化权威副本作为真相
- **与其他部分交互**:
  - 上游: 应用编排与发布治理部分
  - 下游: 关系校验与边界保护部分、事件与快照同步部分、查询解析与追溯部分、P1 资产打包与配置组装部分
  - 交互类型: 定义真相型 + 领域规则型
- **后续详细设计展开点**:
  - MethodContent meta-model
  - 7 类 MethodContent 的最小对象模型
  - lifecycle 与内容可变性规则

#### D. 关系校验与边界保护部分

- **它是什么**: method-library 的发布前关系校验和边界红线保护层
- **为什么单独有它**: 本仓最容易出错的不是 CRUD,而是把下游 Use truth 误写回 Definition truth
- **负责什么**:
  - 校验 MethodContent 之间的引用关系
  - 校验 TaskDefinition 对 WorkProductDefinition、Qualification、ProcessTemplateDef 的引用
  - 保护 Qualification / QualificationProfile / QualificationBinding 三仓边界
  - 保护 WorkProductDefinition / Artifact instance 边界
  - 阻止下游通过同步或 API 反向改写定义真相
- **不负责什么 / 容易混淆点**:
  - 不决定下游如何执行任务、分配成员或渲染 UI
  - 不保存下游本地索引、运行实例或访问裁决
  - 不把边界校验写成某个对象自己的零散字段校验
- **与其他部分交互**:
  - 上游: 应用编排与发布治理部分、方法定义真相与规则部分
  - 下游: 事件与快照同步部分、查询解析与追溯部分
  - 外部: identity、process、capability-hub、artifact、governance、UI 的边界契约
  - 交互类型: 引用校验型 + 边界保护型
- **后续详细设计展开点**:
  - reference validation policy
  - boundary violation error
  - publish 前校验链

#### E. 事件与快照同步部分

- **它是什么**: method-library 面向下游仓的定义传播层,负责 outbox event、L0-bus 和 Definition Snapshot Exporter
- **为什么单独有它**: 权威定义只有被稳定同步、可重放、可兜底拉取,下游才知道自己是否消费了同一版定义
- **负责什么**:
  - 写入并发布 content published / deprecated / retired / fingerprint_changed / source_drift 事件
  - 提供 Definition Snapshot Exporter
  - 支持下游错过事件后的 replay / resync / cold start
  - 向 identity / process / capability-hub / artifact / governance / UI 输出定义变化
- **不负责什么 / 容易混淆点**:
  - 不替下游执行同步后的业务逻辑
  - 不保证下游立即强一致
  - 不保存下游本地索引真相
- **与其他部分交互**:
  - 上游: 应用编排与发布治理部分、方法定义真相与规则部分、关系校验与边界保护部分
  - 下游: 查询解析与追溯部分、基础设施适配部分、所有 definition consumers
  - 交互类型: 事件同步型 + snapshot 分发型 + 漂移告警型
- **后续详细设计展开点**:
  - outbox event catalog
  - snapshot payload 轮廓
  - replay / lag / dead letter / resync 规则

#### F. 查询解析与追溯部分

- **它是什么**: method-library 的读取、解析、追溯和对账入口层
- **为什么单独有它**: 发布主链和高频读取 / 追溯查询变化原因不同,尤其 `ResolveViewProfile` 不能混入发布事务
- **负责什么**:
  - 提供 content / version / lifecycle / fingerprint / audit trace 查询
  - 提供 `ResolveViewProfile`
  - 提供 downstream snapshot query 入口
  - 提供 guidance / example / package blob ref 的只读分发出口
  - 支持 Auditor 查询方法资产追溯链
- **不负责什么 / 容易混淆点**:
  - 不负责 UI 最终渲染
  - 不负责 marketplace 交易
  - 不负责下游将内容转成自己的执行真相
  - 不绕过发布治理直接暴露未发布内容给下游运行态
- **与其他部分交互**:
  - 上游: 方法定义真相与规则部分、事件与快照同步部分、P1 资产打包与配置组装部分
  - 下游: UI / console、process、identity、capability-hub、artifact、governance、Auditor、marketplace(P1)
  - 交互类型: 只读查询型 + 解析型 + 审计追溯型
- **后续详细设计展开点**:
  - ResolveViewProfile 匹配逻辑
  - GetDefinitionTrace
  - read model / cache / projection 边界

#### G. P1 资产打包与配置组装部分

- **它是什么**: 方法资产从单个定义走向打包、组织级组装和 Marketplace 分发的后置能力
- **为什么单独有它**: MethodPlugin / MethodConfiguration 很重要,但不应阻塞 P0 的 7 类 MethodContent 发布同步闭环
- **负责什么**:
  - 管理 MethodPlugin 与一组 MethodContent 的打包关系
  - 管理 MethodConfiguration、selected_plugins、variability_applications、effective_content_set
  - 为 marketplace 提供 package metadata
- **不负责什么 / 容易混淆点**:
  - 不属于 P0 首批闭环
  - 不承担 marketplace listing / transaction / install record
  - 不替代 MethodContent 定义真相
- **与其他部分交互**:
  - 上游: 方法定义真相与规则部分、发布治理部分
  - 下游: 查询解析与追溯部分、事件与快照同步部分、marketplace(P1)
  - 交互类型: 打包组装型 + P1 分发型
- **后续详细设计展开点**:
  - Plugin dependency DAG
  - Configuration active freeze
  - effective_content_set 计算规则

#### H. 基础设施适配部分

- **它是什么**: 承接存储、事件、blob、缓存和外部 adapter 的技术接缝
- **为什么单独有它**: PostgreSQL、object storage、L0-bus、cache 等依赖有独立失败模式,但不能把技术细节泄漏进领域真相和应用编排
- **负责什么**:
  - 适配 PostgreSQL 定义真相存储
  - 适配 object storage 的 blob / package ref
  - 适配 L0-bus event publish / subscribe
  - 为查询和同步提供必要 cache / projection 支撑
- **不负责什么 / 容易混淆点**:
  - 不拥有业务规则
  - 不决定 MethodContent lifecycle
  - 不把数据库表、repository 或 adapter 名称变成主要业务概念
- **与其他部分交互**:
  - 上游: 应用编排、方法定义真相、事件与快照同步、查询解析与追溯
  - 外部: PostgreSQL、object storage、L0-bus、cache
  - 交互类型: 技术适配型 + 可靠性支撑型
- **后续详细设计展开点**:
  - repository port / adapter
  - outbox relay adapter
  - object storage ref resolver

#### 6.8.3 判断规则

如果后续出现新对象,先按以下顺序判断:

```text
1. 它是否只是现有主要组成部分内部的状态、记录、ref、projection 或 adapter?
   是 -> 放入已有主要组成部分。

2. 它是否代表新的职责轴、数据真相、外部交互链、失败模式或不变量?
   是 -> 才考虑新增主要组成部分。

3. 它是否属于下游 Use truth?
   是 -> 不进入 method-library,只保留 ref、snapshot 或事件边界。
```

反例:

```text
不要因为有 Qualification 就新增 Qualification 部分。
不要因为有 OutboxEvent 就新增 Outbox 业务层。
不要因为有 Repository 就把 repository 当成主要业务组成部分。
```

#### 与 `identity` 的交互


  - gate 不可用时阻断 publish,不能绕过审批直接 published
  - governance 错过 AIPolicyDef 事件时,通过 snapshot query 重建 policy source index
- **主要承接部分**: B、C、D、E、F、H

#### 与 `UI / console` 的交互

```text
┌────────────────────────────┐
│ L3-method-library          │
│ - ViewProfile              │
│ - ResolveViewProfile       │
│ - read / trace query       │
└────────────┬───────────────┘
             │ query / resolve
             ▼
┌────────────────────────────┐
│ UI / console               │
│ - field visibility         │
│ - rendering state          │
│ - admin / audit view       │
└────────────────────────────┘
```

- **交互目的**: UI / console 查询方法定义资产、解析 ViewProfile、展示审计追溯
- **通信方式**: query、ResolveViewProfile、read-only trace query
- **method-library 提供**:
  - `ViewProfile`
  - ResolveViewProfile result
  - definition summary / trace / fingerprint
- **method-library 消费 / 请求**:
  - 不消费 UI 本地渲染状态
  - 不接受 UI 本地规则反向覆盖 ViewProfile 权威定义
- **数据边界**:
  - method-library 拥有 ViewProfile definition truth 和 resolve 规则
  - UI / console 拥有 rendering state、前端交互状态和页面缓存
- **失败与降级**:
  - ResolveViewProfile 未匹配时按需求口径默认 deny 或返回受控空视图
  - UI cache 失效时重新 query / resolve,不能长期绕开服务端解析
- **主要承接部分**: A、C、F、H

#### 与 `L0-bus` 的交互

```text
┌────────────────────────────┐
│ L3-method-library          │
│ - outbox event source      │
│ - snapshot source          │
└────────────┬───────────────┘
             │ publish / retry / replay
             ▼
┌────────────────────────────┐
│ L0-bus                     │
│ - definition events        │
│ - drift events             │
└────────────┬───────────────┘
             │ consume
             ▼
┌────────────────────────────┐
│ downstream consumers       │
└────────────────────────────┘
```

- **交互目的**: 通过异步事件把定义变化可靠传播给下游
- **通信方式**: outbox relay、event publish、event replay
- **method-library 提供**:
  - published / deprecated / retired events
  - fingerprint_changed / source_drift events
  - replay 所需的事件源和 snapshot 兜底
- **method-library 消费 / 请求**:
  - 不从 L0-bus 读取下游本地同步结果作为定义真相
  - 可消费 bus publish ack / failure 作为 outbox relay 状态输入
- **数据边界**:
  - method-library 拥有 outbox event source
  - L0-bus 负责传输,不拥有 MethodContent definition truth
- **失败与降级**:
  - L0-bus 暂不可用时,事件留在 outbox backlog
  - relay 恢复后重试 / replay,不得静默丢失 definition event
- **主要承接部分**: E、H

#### 与 `object storage` 的交互

```text
┌────────────────────────────┐

└────────────────────────────┘
```

- **交互目的**: 保存 guidance、example、package 等大体积或非结构化内容引用
- **通信方式**: blob put / get by ref
- **method-library 提供**:
  - blob ref 元数据
  - package / guidance / example 的访问入口
- **method-library 消费 / 请求**:
  - 读取 blob 内容用于查询或分发
  - 写入 blob 内容并保存 ref
- **数据边界**:
  - method-library 主库拥有 metadata、lifecycle、fingerprint 和关系真相
  - object storage 只保存 blob,不拥有定义资产元数据真相
- **失败与降级**:
  - 关键 blob 缺失时阻断 publish 或标记不可发布
  - 非关键 blob 暂不可读时,查询可返回 metadata + degraded ref 状态
- **主要承接部分**: F、H

#### 与 `marketplace(P1)` 的交互

- **交互目的**: P1 阶段将 MethodPlugin package metadata 提供给 marketplace 上架和分发
- **通信方式**: P1 package metadata query / event、package blob ref
- **method-library 提供**:
  - MethodPlugin metadata
  - package blob ref
  - version / fingerprint / lifecycle
- **method-library 消费 / 请求**:
  - 不消费交易、安装、计费记录作为方法定义真相
  - 可消费 marketplace 上架状态作为展示或运营信息(P1),但不反向改变 MethodContent 正文
- **数据边界**:
  - method-library 拥有 MethodPlugin / MethodConfiguration 组合真相
  - marketplace 拥有 listing、transaction、install record
- **失败与降级**:
  - marketplace 不可用不阻断 P0 定义发布同步闭环
  - marketplace 诉求不得反向污染 P0 MethodContent 元模型

## 8. 总体架构设计

### 8.1 架构风格

`L3-method-library` 采用:

```text
分层架构
  + 端口 / 适配器
  + 定义真相仓
  + outbox 事件同步
  + snapshot 查询兜底
```

这个架构选择服务于四个目标:

| 目标 | 架构含义 |
|---|---|
| 定义真相稳定 | P0 7 类 MethodContent 的正文、生命周期、version、fingerprint 由本仓统一拥有 |
| 发布链可审计 | publish / deprecate / retire 必须经过应用编排、gate、audit、outbox |
| 下游同步可靠 | 通过 outbox + L0-bus 输出事件,通过 Definition Snapshot Exporter 兜底 |
| 边界红线可验证 | 通过关系校验与边界保护阻止 Use truth 反向污染 Definition truth |

概要设计阶段只定义分层、依赖方向和职责约束,不展开 Rust struct、数据库 DDL、事务伪代码或具体 repository 实现。

### 8.3 模块依赖关系

| 依赖 | 含义 |
|---|---|
| A -> B / F | 对外入口接收 command / query / job,写入类请求进入 B,读取类请求进入 F |
| B -> C / D / E / F | 应用编排串起发布、校验、审计、事件、查询可见性 |
| C -> D | 定义真相在发布或引用前需要经过关系校验与边界保护 |
| B -> E | 发布成功后由 B 触发 outbox 与 snapshot 同步 |
| F -> C / E | 查询解析读取定义真相、audit trace、snapshot 和事件追溯 |
| G -> C / B / E / F | P1 打包配置消费已发布定义,复用发布治理、同步和查询出口 |
| A~G -> H | 各部分通过 port 使用基础设施适配,而不是直接依赖具体存储或消息实现 |

### 8.4 层间约束规则

| 规则 | 说明 |
|---|---|
| A 不直接修改 C | 对外入口不能绕过应用编排直接改 MethodContent 真相 |
| B 不保存下游 Use truth | 应用编排只处理本仓发布主链,不保存 ProcessInstance、WorkItem、Artifact instance 等 |
| C 不调用外部运行时 | 方法定义真相层不直接调用 process / identity / governance / UI |
| D 不产生业务结果 | 关系校验只做 validation / guard,不替下游执行任务或裁决访问 |
| E 不绕过 B 发事件 | 事件和 snapshot 必须来自已完成的发布 / 变更编排 |
| F 不绕过发布治理暴露未发布内容 | 查询解析必须尊重 lifecycle、visibility 和 publish 状态 |
| G 不阻塞 P0 主链 | P1 打包配置不能成为 P0 MethodContent 发布同步闭环的前置条件 |
| H 不反向决定业务规则 | 基础设施适配只实现 port,不能决定 lifecycle、fingerprint、边界红线 |

### 8.5 P0 主链穿透方式

```text
Command
  -> A. 对外入口与访问部分
  -> B. 应用编排与发布治理部分
  -> C. 方法定义真相与规则部分
  -> D. 关系校验与边界保护部分
  -> B. 生成 version / fingerprint / audit
  -> E. 写 outbox / snapshot
  -> H. 持久化 / event adapter
  -> F. 查询追溯可读
```

这条链路承接 P0:

```text

  -> Review / Gate
  -> Publish
  -> Generate Fingerprint
  -> Audit
  -> Outbox Event
  -> Snapshot Export
  -> Downstream Sync
```

### 8.6 P1 Sidecar 规则

`G. P1 资产打包与配置组装部分` 是 sidecar,不是 P0 主链。

它可以消费:

```text
已发布 MethodContent
已冻结 version / fingerprint
package blob ref
MethodPlugin / MethodConfiguration metadata
```

它不允许:

```text
反向修改 MethodContent 正文
阻塞 P0 发布同步闭环
把 marketplace listing / transaction / install record 写入 Definition truth
把 P1 variability 复杂度提前推入 P0 MethodContent 元模型
```

### 8.9 实现分层依赖约束

允许的依赖方向:

```text
Inbound adapters
  -> Application services
  -> Domain model / Domain services

Workers / Operations Jobs
  -> Application services
  -> Domain model / Domain services

Query services
  -> Application services
  -> Persistence / Data Store

Application services
  -> Repository / UnitOfWork
  -> Outbound Ports
  -> Domain model / Domain services

Outbound Ports
  -> Outbound Adapters
```

禁止的依赖:

| 禁止项 | 原因 |
|---|---|
| Domain 直接依赖 PostgreSQL / L0-bus / object storage | 领域规则不能被基础设施和外部协议细节污染 |
| Inbound adapter 直接写 MethodContent truth | 必须经过 application 编排和 domain 规则 |
| Persistence / Outbound adapter 决定 lifecycle / fingerprint / boundary | adapter 只做技术实现,不决定业务规则 |
| Worker 绕过 application / domain 直接修复真相 | replay / rebuild / seed 也必须遵守同一套规则 |
| Query / projection 反写真相 | read model / projection 可重建,不能成为 Definition truth |
| P1 service 阻塞 P0 publish 主链 | Plugin / Configuration 是后置 sidecar |

## 9. 关键技术选型

### 9.1 选型总览

本节继承 `01-架构设计.md` §9 的技术选型结论,但只从概要设计角度说明:

```text
为什么这些机制必须存在
它们解决哪类概要设计问题
它们影响 A~H 哪些主要组成部分
后续详细设计应展开什么
```

本节不展开 Rust 结构体、数据库 DDL、索引、事务伪代码、具体 service 名称或 adapter 实现。

| 技术选型 | 解决的问题 | 主要影响部分 |
|---|---|---|
| MethodContent 元模型 + kind 扩展 | 统一承载 7 类 P0 方法定义资产 | C、D、E、F |
| PostgreSQL 作为定义真相存储 | 保证 definition truth、version、fingerprint、audit、outbox 的一致性 | B、C、E、F、H |
| object storage 外置 blob | 避免 guidance / example / package blob 污染结构化定义真相 | F、G、H |
| Outbox + L0-bus | 保证定义变化事件可重试、可重放、不静默丢失 | B、E、H |
| Definition Snapshot Exporter | 支持下游冷启动、漏消费补偿和对账 | E、F、H |
| schema version | 支持 definition / snapshot / event 演进 | C、E、F |
| canonical fingerprint | 支持跨仓 drift 检测和历史追溯 | B、C、E、F |
| server-side ResolveViewProfile | 避免 UI / console 各自硬编码视图规则 | C、F、H |
| P1 Plugin / Configuration 后置 | 防止打包组装复杂度污染 P0 发布同步闭环 | G,并约束 B、C、E |
| 边界校验机制 | 防止 Use truth 反向污染 Definition truth | D,并贯穿 A、B、C、E、F |

### 9.2 MethodContent 元模型 + kind 扩展

| 项 | 内容 |
|---|---|
| 当前选择 | 用 `MethodContent` 抽象承载 `Qualification / RoleDefinition / TaskDefinition / WorkProductDefinition / ProcessTemplateDef / ViewProfile / AIPolicyDef` 7 类 P0 定义资产 |
| 解决的问题 | 这些资产都需要统一生命周期、版本、fingerprint、审计、发布和下游同步机制 |
| 为什么适合本仓 | 本仓的定位是方法定义资产中心,核心不是 7 个孤立对象,而是一条统一的定义发布同步主链 |
| 影响的主要组成部分 | C. 方法定义真相与规则部分;D. 关系校验与边界保护部分;E. 事件与快照同步部分;F. 查询解析与追溯部分 |
| 代价 / 风险 | 元模型复杂度上升,需要严格区分通用字段、kind-specific 内容和下游 Use truth |
| 后续详细设计展开点 | MethodContent 最小对象模型、kind-specific 校验、扩展 kind 的 ADR / 设计决策流程 |

### 9.3 PostgreSQL 作为定义真相存储

| 项 | 内容 |
|---|---|
| 当前选择 | PostgreSQL 保存 definition truth、version、fingerprint、audit、outbox 和必要只读投影 |
| 解决的问题 | 发布事务需要强一致;审计、追溯和查询需要结构化能力 |
| 为什么适合本仓 | MethodContent 发布成功后,state、version、fingerprint、audit 和 outbox 必须保持一致,不能分散在多个无法同事务控制的存储里 |
| 影响的主要组成部分 | B. 应用编排与发布治理部分;C. 方法定义真相与规则部分;E. 事件与快照同步部分;F. 查询解析与追溯部分;H. 基础设施适配部分 |
| 代价 / 风险 | 历史版本和审计记录会长期增长,需要在详细设计中考虑查询模型和存储边界 |
| 后续详细设计展开点 | repository port、事务边界、读写模型、审计查询、outbox 持久化 |

### 9.4 object storage 外置 blob

| 项 | 内容 |
|---|---|
| 当前选择 | guidance、example、package blob 放入 object storage,本仓结构化记录只保存 ref、hash 和必要元数据 |
| 解决的问题 | 大段说明、示例包和资产包正文不应挤入 MethodContent 结构化定义真相 |
| 为什么适合本仓 | 结构化定义、版本、fingerprint 和发布状态需要强一致;大对象正文有独立容量、可用性和生命周期 |
| 影响的主要组成部分 | F. 查询解析与追溯部分;G. P1 资产打包与配置组装部分;H. 基础设施适配部分 |
| 代价 / 风险 | 需要处理 blob ref 可用性、hash 校验和 object storage 降级 |
| 后续详细设计展开点 | blob ref 校验、hash 校验、缺失 blob 的发布阻断或降级规则、P1 package blob 处理 |

### 9.5 Outbox + L0-bus

| 项 | 内容 |
|---|---|
| 当前选择 | 发布事务内写 outbox,再由 relay 发布到 L0-bus |
| 解决的问题 | 防止 MethodContent 已发布但定义变化事件丢失 |
| 为什么适合本仓 | 本仓是定义事件源,下游 identity / process / capability-hub / artifact / governance / UI 依赖事件感知版本变化和 fingerprint drift |
| 影响的主要组成部分 | B. 应用编排与发布治理部分;E. 事件与快照同步部分;H. 基础设施适配部分 |
| 代价 / 风险 | 需要 relay、重试、backlog、dead letter、消费者幂等和 replay 机制 |
| 后续详细设计展开点 | outbox event catalog、relay worker、重试策略、幂等键、事件重放和积压监控 |

### 9.6 Definition Snapshot Exporter

| 项 | 内容 |
|---|---|
| 当前选择 | 下游通过 Snapshot Query / ExportDefinitionSnapshot 获取完整定义快照 |
| 解决的问题 | 事件只适合承载变化摘要,不适合携带完整定义正文;下游冷启动、漏消费或对账时需要完整快照 |
| 为什么适合本仓 | Definition truth 归 method-library,下游不应跨库读取,也不应自己拼装权威定义 |
| 影响的主要组成部分 | E. 事件与快照同步部分;F. 查询解析与追溯部分;H. 基础设施适配部分 |
| 代价 / 风险 | snapshot schema 需要版本治理,不同下游需要按 content kind 消费 |
| 后续详细设计展开点 | snapshot payload 轮廓、schema version、historical snapshot、批量导出、下游 resync |

### 9.7 schema version

| 项 | 内容 |
|---|---|
| 当前选择 | definition、snapshot、event 都携带 schema version |
| 解决的问题 | MethodContent 内容结构和下游消费契约会演进,需要显式兼容边界 |
| 为什么适合本仓 | 本仓有多个下游,一旦契约隐式变化,会造成索引漂移、解析失败或运行时错误 |
| 影响的主要组成部分 | C. 方法定义真相与规则部分;E. 事件与快照同步部分;F. 查询解析与追溯部分 |
| 代价 / 风险 | 版本治理和兼容性测试成本上升 |
| 后续详细设计展开点 | schema version 字段语义、兼容矩阵、consumer contract test、历史版本读取策略 |

### 9.8 canonical fingerprint

| 项 | 内容 |
|---|---|
| 当前选择 | 基于 canonical definition 内容生成稳定 fingerprint |
| 解决的问题 | 下游需要判断自己消费的定义是否与权威源一致,审计者需要追溯语义变化 |
| 为什么适合本仓 | version 表达发布顺序,fingerprint 表达内容语义;二者合用才能支撑 drift 检测和追溯 |
| 影响的主要组成部分 | B. 应用编排与发布治理部分;C. 方法定义真相与规则部分;E. 事件与快照同步部分;F. 查询解析与追溯部分 |
| 代价 / 风险 | canonical serialization 必须稳定,哪些字段参与 fingerprint 必须受控 |
| 后续详细设计展开点 | canonical 序列化规则、字段纳入规则、fingerprint_changed 事件、CompareFingerprint / drift report |

### 9.9 ResolveViewProfile 服务端解析

| 项 | 内容 |
|---|---|
| 当前选择 | 服务端按 role、object_kind、scope 解析 active ViewProfile |
| 解决的问题 | 避免 UI / console 各自硬编码字段可见性、布局策略和视图规则 |
| 为什么适合本仓 | ViewProfile 是方法定义资产,权威解析应靠近定义真相,UI 只消费解析结果 |
| 影响的主要组成部分 | C. 方法定义真相与规则部分;F. 查询解析与追溯部分;H. 基础设施适配部分 |
| 代价 / 风险 | ResolveViewProfile 位于 UI 渲染前置路径,需要明确性能预算和缓存策略 |
| 后续详细设计展开点 | 匹配优先级、默认 deny / fallback、缓存边界、灰度和 preset / override 规则 |

### 9.10 P1 Plugin / Configuration 后置

| 项 | 内容 |
|---|---|
| 当前选择 | P0 先完成 7 类 MethodContent 发布同步闭环,MethodPlugin / MethodConfiguration 留在 P1 |
| 解决的问题 | 防止打包、组装、variability 和 marketplace 分发复杂度拖慢 P0 定义真相闭环 |
| 为什么适合本仓 | P0 价值是让方法定义资产可发布、可同步、可追溯;P1 价值是组织级组装和生态分发 |
| 影响的主要组成部分 | G. P1 资产打包与配置组装部分;同时约束 B. 应用编排、C. 定义真相、E. 同步部分 |
| 代价 / 风险 | 初期无法完整支持组织级方法集切换和 marketplace 分发 |
| 后续详细设计展开点 | MethodPlugin、MethodConfiguration、Plugin dependency DAG、effective_content_set、Marketplace metadata 边界 |

### 9.11 边界校验机制

| 项 | 内容 |
|---|---|
| 当前选择 | 在架构、接口、数据模型、测试和审查中持续校验 Definition / Use 边界 |
| 解决的问题 | 防止 QualificationProfile、QualificationBinding、ProcessInstance、WorkItem、Artifact instance、Policy enforce result 等运行时事实污染 method-library |
| 为什么适合本仓 | method-library 的核心风险不是少一个字段,而是边界污染导致定义真相与使用真相混在一起 |
| 影响的主要组成部分 | D. 关系校验与边界保护部分;并贯穿 A. 入口、B. 编排、C. 真相、E. 同步、F. 查询 |
| 代价 / 风险 | 需要额外 contract test、边界测试、schema lint 或审查规则 |
| 后续详细设计展开点 | boundary violation error、引用校验策略、禁止字段清单、下游 contract test、CI 边界扫描 |

## 10. 备选方案与取舍

### 10.1 取舍总览

本节继承 `01-架构设计.md` §10 的取舍结论,从概要设计角度说明:

```text
有哪些可选方案
为什么采用当前方案
为什么不采用其他方案
采用方案带来什么收益和代价
这些取舍如何保护 A~H 主要组成部分边界
```

本节不是重新做架构选型,而是把已经确认的关键取舍写成开发者可理解、可遵守的边界说明。

| 取舍主题 | 最终采用 | 不采用 |
|---|---|---|
| 仓定位 | method-library 作为方法资产元模型仓 | 文档仓 / Git-only、嵌入各下游仓 |
| Qualification 归属 | Qualification 属于 method-library | 属于 identity、属于 capability-hub |
| 发布同步 | Outbox + L0-bus | 直接发事件、下游轮询作为主路径 |
| Snapshot 同步 | event 只放元数据 + snapshot_ref | event 携带完整正文、下游直接查库 |
| P0 / P1 范围 | P0 先做 7 类 MethodContent,Plugin / Configuration P1 后置 | P0 同时做 Plugin / Configuration / Marketplace、完全不做 P1 |
| 边界校验 | 文档 + 架构 + 测试共同约束边界 | 只靠文档约定、接受跨仓运行时事实冗余 |

### 10.2 仓定位方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 方法资产元模型仓 | 边界清晰,能统一支持 definition truth、version、fingerprint、audit、snapshot 和 event sync | 学习成本更高,元模型复杂度更高 | 采用 |
| 文档仓 / Git-only | 简单、适合人工阅读、版本历史天然存在 | 难以承载发布门禁、结构化查询、事件同步、snapshot、drift 检测和下游契约 | 不采用 |
| 嵌入各下游仓 | 下游局部实现快,短期少一个中心仓 | 定义会分裂,Role / Task / Policy / ViewProfile / Qualification 会各自漂移 | 不采用 |

关键取舍:

```text
method-library 必须是方法资产元模型仓。
它不是 README 仓,也不是每个下游仓内部的一份本地配置。
只有元模型仓能同时支撑可发布、可同步、可追溯、可对账的 Definition truth。
```

对主要组成部分的影响:

```text
C. 方法定义真相与规则部分成为本仓核心。
E. 事件与快照同步部分成为下游消费的稳定出口。
F. 查询解析与追溯部分承接审计和只读消费。
```

### 10.3 Qualification 归属方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Qualification 属于 method-library | 符合 SPEM Qualification 语义,Role / Task / ProcessTemplate 可统一引用 | identity / capability-hub 需要同步 catalog 或 snapshot | 采用 |
| Qualification 属于 identity | 成员画像实现方便 | 混淆“能力定义”和“成员实际具备哪些能力” | 不采用 |
| Qualification 属于 capability-hub | 工具绑定和 provider 接入实现方便 | 混淆“能力定义”和“工具 / provider / MCP / A2A 接入绑定” | 不采用 |

关键取舍:

```text
method-library 定义 Qualification 是什么。
identity 记录成员具备哪些 Qualification。
capability-hub 记录 Qualification 如何绑定工具、provider、MCP / A2A 能力入口。
```

对主要组成部分的影响:

```text
C. 方法定义真相与规则部分拥有 Qualification definition。
D. 关系校验与边界保护部分阻止 QualificationProfile / QualificationBinding 进入本仓。
E / F 只向 identity 与 capability-hub 输出 snapshot、event 和查询结果。
```

### 10.4 发布同步方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Outbox + L0-bus | 发布事件可靠、可重试、可重放,避免 DB 成功但事件丢失 | 需要 relay、backlog、幂等消费和监控 | 采用 |
| 直接发事件 | 实现简单、链路短 | 发布事务成功但事件发送失败时,下游会永久漏同步 | 不采用 |
| 下游轮询作为主路径 | 下游可自行控制同步节奏 | 延迟大、压力高、多下游扩散明显,不适合作为主同步机制 | 不作为主路径 |

关键取舍:

```text
跨仓事实传播必须异步。
发布事务只保证本仓 definition truth + outbox 强一致。
下游通过 event replay 和 snapshot query 达成最终一致。
```

对主要组成部分的影响:

```text
B. 应用编排与发布治理部分负责把 outbox 写入纳入发布链。
E. 事件与快照同步部分负责事件发布、重试、重放和同步出口。
H. 基础设施适配部分负责 L0-bus 与 outbox relay 的技术接缝。
```

### 10.5 Snapshot 同步方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| event 只放元数据 + snapshot_ref | 事件轻量,易重放,完整定义可按需拉取 | 需要 Snapshot Exporter 和 schema version 治理 | 采用 |
| event 携带完整正文 | 下游收到事件即可拿到完整定义 | 事件变大,replay 成本高,schema 演进和兼容复杂 |
| 下游直接查库 | 初期实现快 | 破坏仓边界,造成跨库耦合,绕过 method-library 的查询和版本契约 | 禁止 |

关键取舍:

```text
event 用来通知“发生了什么”。
snapshot 用来承载“完整定义是什么”。
下游不能直接查 method-library 的数据库。
```

对主要组成部分的影响:

```text
E. 事件与快照同步部分负责 snapshot 生成和导出。
F. 查询解析与追溯部分提供 snapshot query 和 trace 查询入口。
H. 基础设施适配部分支撑 snapshot 存储、读取和可用性。
```

### 10.6 P0 / P1 范围方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| P0 先做 7 类 MethodContent | 能快速跑通定义发布、fingerprint、audit、event、snapshot 和下游同步闭环 | 初期不具备完整组织级方法集切换和 Marketplace 分发能力 | 采用 |
| P0 同时做 Plugin / Configuration / Marketplace | 一次性完整,产品形态更丰满 | 复杂度高,会拖慢 P0 定义真相闭环,也容易污染 MethodContent 主模型 | 不采用 |
| 完全不做 Plugin / Configuration | P0 最简单 | 未来缺少方法资产打包、组织级配置和可裁剪性支撑 | 不采用,改为 P1 后置 |

关键取舍:

```text
P0 的成功标准是定义资产可发布、可同步、可追溯。
Plugin / Configuration 是重要能力,但不应阻塞 P0。
Marketplace 分发只能消费 package metadata,不能拥有 MethodContent 正文真相。
```

对主要组成部分的影响:

```text
G. P1 资产打包与配置组装部分以 sidecar 方式存在。
G 可以消费已发布 MethodContent,但不能反向修改 C 的定义真相。
G 的失败不能阻塞 B/E 的 P0 发布同步主链。
```

### 10.7 边界校验方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 文档 + 架构 + 测试共同约束边界 | 能持续防止边界污染,适合多仓协作 | 需要额外审查、contract test 和边界测试 | 采用 |
| 只靠文档约定 | 成本低,初期快 | 实现时容易把外部运行时事实写入本仓 | 不采用 |
| 接受少量跨仓数据冗余 | 查询方便,短期少一次同步 | 长期破坏 source of truth,导致 Definition truth 和 Use truth 混淆 | 不采用 |

关键取舍:

```text
method-library 最大风险不是功能缺失,
而是被 QualificationProfile、QualificationBinding、ProcessInstance、WorkItem、
Artifact instance、Policy enforce result 等运行时事实污染。
```

对主要组成部分的影响:

```text
D. 关系校验与边界保护部分必须成为独立职责块。
A. 对外入口必须拒绝明显越界的写入请求。
B. 应用编排不能保存下游 Use truth。
C. 方法定义真相与规则部分只能保存 Definition truth。
E / F 输出给下游的是 definition event、snapshot 和 query result,不是下游运行态真相。
```

### 10.8 取舍结论

本仓的核心取舍可以收束为:

```text
1. 用 method-library 承载 Definition truth,不把定义散落到文档或下游仓。
2. 用 Qualification definition / QualificationProfile / QualificationBinding 三分法保护边界。
3. 用 outbox + L0-bus 做定义变化传播,不用直接发事件承担可靠性。
4. 用 snapshot 承载完整定义,不用事件正文或跨库查询承载完整同步。
5. 用 P0 / P1 分界保护首批开发节奏,不让 Plugin / Configuration 拖慢定义主链。
6. 用工程化边界校验保护 Definition / Use 分离,不只靠口头约定。
```

这些取舍共同服务于同一个目标:

```text
让 L3-method-library 成为稳定的方法定义资产中心,
同时让 identity / process / capability-hub / artifact / governance / UI
保留各自的 Use truth 和运行时事实。
```

## 11. 核心接口列表

### 11.1 接口分组原则

本节继承 `00-需求文档.md` §10 的接口需求,只给出概要级接口族。

概要设计阶段只说明:

```text
谁调用本仓
调用本仓做什么
哪些接口改变 Definition truth
哪些接口只读
哪些事件发给下游
哪些边界不能通过接口打开
```

本节不展开 DTO、函数签名、HTTP / RPC 路径、错误码、权限校验细节或具体 handler 实现。

接口分组:

```text
Command
  -> 改变 method-library 自己的 Definition truth
  -> 例如创建草稿、提交审核、发布、废弃、退役

Query
  -> 读取 Definition truth、snapshot、trace 或 view resolve
  -> 不改变状态

Outbound Event
  -> 本仓向外通知定义变化
  -> 通过 outbox + L0-bus 发布

Inbound Event / 外部依赖
  -> 本仓消费外部 gate 或依赖外部服务
  -> 例如 governance gate、PostgreSQL、object storage、L0-bus

Operations Job
  -> 运维或系统触发的维护动作
  -> 例如 seed、replay、recalculate fingerprint
```

接口与主要组成部分的关系:

```text
A. 对外入口与访问部分
  -> 承接 Command / Query / Job / Event Consumer 入口

B. 应用编排与发布治理部分
  -> 承接会改变定义状态的 Command

E. 事件与快照同步部分
  -> 承接 Outbound Event、snapshot、replay

F. 查询解析与追溯部分
  -> 承接 Query、ResolveViewProfile、GetDefinitionTrace、CompareFingerprint

H. 基础设施适配部分
  -> 承接 PostgreSQL、object storage、L0-bus、cache 等技术依赖
```

### 11.2 Command 接口族

P0 Command 聚焦 7 类 MethodContent 的定义生命周期。Command 是同步接口,调用方需要立即知道状态变化是否成功。

| 接口 | 优先级 | 调用方 | 用途 | 是否同步 | 是否发布事件 |
|---|---|---|---|---|---|
| `CreateMethodContentDraft` | P0 | 方法作者 / Admin | 创建方法资产草稿 | 是 | 否 |
| `UpdateMethodContentDraft` | P0 | 方法作者 / Admin | 更新草稿内容 | 是 | 否 |
| `SubmitMethodContentForReview` | P0 | 方法作者 / Admin | 提交发布审核 | 是 | 否 |
| `PublishMethodContent` | P0 | 方法审核者 / 批准者 / Admin | 发布定义资产 | 是 | 是 |
| `DeprecateMethodContent` | P0 | 方法审核者 / 批准者 / Admin | 废弃定义资产 | 是 | 是 |
| `RetireMethodContent` | P0 | 方法审核者 / 批准者 / Admin | 退役定义资产 | 是 | 是 |
| `SupersedeMethodContent` | P0 | 方法审核者 / 批准者 / Admin | 用新版本替代旧版本并建立 supersede 链 | 是 | 是 |
| `PublishMethodPlugin` | P1 | 方法审核者 / Admin | 发布方法资产包 | 是 | 是 |
| `ActivateMethodConfiguration` | P1 | Owner / Admin | 激活组织方法集 | 是 | 是 |

Command 的共同要求:

```text
必须携带 actor_ref。
必须校验 expected_version 或等价并发控制字段。
必须记录 audit record。
发布类 Command 必须校验 approved_gate_ref 或等价 gate result。
不得让下游系统绕过 Command 直接改写定义正文。
```

Command 与主要组成部分:

| 接口族 | 主要承接部分 | 说明 |
|---|---|---|
| Draft / Update / Submit | A、B、C、D、F、H | 入口接收、编排状态变化、写入定义真相、记录审计 |
| Publish / Deprecate / Retire / Supersede | A、B、C、D、E、F、H | 发布链必须串起 gate、校验、version、fingerprint、audit、outbox |
| P1 Plugin / Configuration Command | A、G、E、F、H | P1 sidecar,不得阻塞 P0 MethodContent 主链 |

### 11.3 Query 接口族

Query 是同步只读接口,用于读取定义资产、导出快照、解析视图和查询追溯。Query 不得改变 MethodContent 状态。

| 接口 | 优先级 | 调用方 | 用途 | 是否同步 |
|---|---|---|---|---|
| `GetMethodContent` | P0 | 下游系统 / Console / Auditor | 获取指定方法资产当前定义 | 是 |
| `ListMethodContents` | P0 | Console / Auditor | 查询方法资产列表 | 是 |
| `GetMethodContentVersion` | P0 | Auditor / 下游系统 | 获取指定历史版本 | 是 |
| `ExportDefinitionSnapshot` | P0 | identity / process / capability-hub / artifact / governance | 导出可同步定义快照 | 是 |
| `ResolveViewProfile` | P0 | UI / console | 解析当前应使用的视图策略 | 是 |
| `GetDefinitionTrace` | P0 | Auditor | 查询定义追溯链 | 是 |
| `CompareFingerprint` | P0 | 下游系统 / Auditor | 比较下游指纹与源定义是否一致 | 是 |
| `ListMethodPlugins` | P1 | marketplace / Console | 查询方法资产包 | 是 |
| `GetMethodConfiguration` | P1 | Owner / Admin / Console | 查询组织方法集配置 | 是 |

Query 的共同要求:

```text
读取接口不得改变定义状态。
snapshot 必须包含 content_id、kind、version、fingerprint、lifecycle。
历史版本查询必须保留审计与追溯语义。
ResolveViewProfile 未匹配时生产环境默认 deny 或返回受控空视图。
Query 可以使用 read model / cache,但返回结果必须能追溯到 Definition truth。
```

Query 与主要组成部分:

| 接口族 | 主要承接部分 | 说明 |
|---|---|---|
| Content / Version Query | A、C、F、H | 读取定义真相和历史版本 |
| Snapshot Query | E、F、H | 下游冷启动、漏消费补偿和对账 |
| ResolveViewProfile | A、C、F、H | 服务端解析 ViewProfile,UI 不拥有权威规则 |
| Trace / Fingerprint Query | B、E、F、H | 追溯 audit、version、event、fingerprint 和 drift |
| P1 Plugin / Configuration Query | G、F、H | 只读查询 P1 package / configuration 信息 |

### 11.4 Outbound Event 接口族

`L3-method-library` 在定义变化后通过 outbox + L0-bus 发布事件,供下游建立本地索引、触发同步或执行对账。

| 事件 | 优先级 | 触发条件 | 主要消费者 | 用途 |
|---|---|---|---|---|
| `method_library.content.published` | P0 | 任一 MethodContent 发布 | 通用订阅方 | 通知定义资产发布 |
| `method_library.content.retired` | P0 | 任一 MethodContent 退役 | 通用订阅方 | 通知定义资产退役 |
| `method_library.content.fingerprint_changed` | P0 | fingerprint 变化 | 通用订阅方 / Auditor | 通知定义语义变化 |
| `method_library.qualification.published` | P0 | Qualification 发布 | identity、capability-hub | 同步 Qualification 定义 |
| `method_library.qualification.retired` | P0 | Qualification 退役 | identity、capability-hub | 同步 Qualification 退役 |
| `method_library.qualification.fingerprint_changed` | P0 | Qualification fingerprint 变化 | identity、capability-hub | 触发 Qualification drift 感知 |
| `method_library.role_definition.published` | P0 | RoleDefinition 发布 | identity | 同步角色定义 |
| `method_library.task_definition.published` | P0 | TaskDefinition 发布 | process | 同步任务定义 |
| `method_library.work_product_definition.published` | P0 | WorkProductDefinition 发布 | artifact | 同步制品定义 |
| `method_library.process_template_def.published` | P0 | ProcessTemplateDef 发布 | process | 同步流程模板定义 |
| `method_library.view_profile.published` | P0 | ViewProfile 发布 | UI / console | 同步视图策略变化 |
| `method_library.ai_policy_def.published` | P0 | AIPolicyDef 发布 | governance | 同步 AI Policy 定义 |
| `method_library.plugin.published` | P1 | MethodPlugin 发布 | marketplace / Console | 同步资产包 metadata |
| `method_library.configuration.activated` | P1 | MethodConfiguration 激活 | Console / organization runtime | 同步组织方法集激活结果 |

事件规则:

```text
通用 content 事件用于统一订阅。
子类事件用于下游精确订阅。
事件必须通过 outbox 发布,不得绕过发布事务直接发 bus event。
事件必须可重放。
消费者必须按 content_id + version + fingerprint 幂等处理。
事件载荷应携带 snapshot_ref 或等价引用,避免在事件中塞入完整定义正文。
```

### 11.5 Inbound Event / 外部依赖接口

本仓的 Inbound Event 很少。核心是接收或引用 governance 的发布 gate 结果;其他更多是基础设施依赖或外部服务依赖。

| 来源 | 接口 / 依赖 | 优先级 | 用途 | 边界 |
|---|---|---|---|---|
| governance | `governance.publish_gate.approved` / `approved_gate_ref` | P0 | 允许 `PublishMethodContent` 使用 gate 结果发布 | 本仓只保存 gate_ref 和审计引用,不保存 enforce result |
| PostgreSQL | definition truth / audit / outbox storage | P0 | 持久化定义真相、审计和 outbox | 数据库是本仓存储,不是跨仓查询接口 |
| object storage | blob ref / hash | P0 / P1 | 存放 guidance / example / package blob | 本仓保存 ref / hash,不把大 blob 当结构化定义真相 |
| L0-bus | event publish / replay | P0 | 发布定义变化事件 | 事件发布经 outbox relay |
| quantalithos-core | shared contract / shared type | P0 | 统一契约、基础类型和跨仓约定 | 不承载业务真相 |

Inbound / 外部依赖规则:

```text
governance gate 不可用时,阻断 publish,不阻断 draft / query。
object storage 不可用时,元数据查询可降级;publish 依赖的关键 blob 缺失时应阻断。
L0-bus 不可用时,写入 outbox backlog,恢复后 replay。
下游系统不可用不阻断本仓发布,下游通过 event replay / snapshot query 恢复。
```

### 11.6 Operations Job 接口族

Operations Job 用于初始化、重放、修复和对账。它们不应绕过定义真相和审计规则。

| Job | 优先级 | 触发方 | 用途 | 是否改变定义正文 |
|---|---|---|---|---|
| `SeedInitialMethodAssets` | P0 | 系统 / 运维 | 初始化基础方法资产 | 是,但必须走受控 seed 版本和审计 |
| `ReplayDefinitionEvents` | P0 | 运维 / 系统 | 重放定义发布事件,帮助下游恢复索引 | 否 |
| `RecalculateFingerprint` | P0 | 运维 / Auditor | 重新计算指定内容 fingerprint 并生成对比结果 | 否 |
| `ExportAllSnapshots` | P1 | 运维 / 系统 | 批量导出当前所有可同步定义 snapshot | 否 |
| `DetectDefinitionDrift` | P1 | 运维 / Auditor / 系统 | 根据下游回报或抽样对比识别 source drift | 否 |

Operations Job 规则:

```text
seed 必须有 seed_version 和 actor_ref / system_actor_ref。
replay 不得改变定义正文,只重放已存在事件或重新导出 snapshot。
fingerprint recalculation 必须留下审计记录或对账记录。
P1 drift detection 不得替下游自动改写本地索引,只能输出 drift 结果或修复建议。
```

### 11.7 接口边界红线

本仓对外接口只围绕方法定义资产展开。任何接口都不能打开下列写入路径:

```text
method-library 不提供创建或更新 QualificationProfile 的接口。
method-library 不提供创建或更新 QualificationBinding 的接口。
method-library 不提供创建或更新 CapabilityAccessDecision 的接口。
method-library 不提供创建或更新 ProcessInstance / Activity execution 的接口。
method-library 不提供创建或更新 WorkItem / Backlog / Iteration 的接口。
method-library 不提供保存 Artifact instance 正文或 evidence instance 的接口。
method-library 不提供执行 Policy enforce result 的接口。
method-library 不提供 marketplace listing / transaction / install record 的写入接口。
```

如果未来出现新接口,必须先判断:

```text
1. 它是否改变 method-library 的 Definition truth?
   是 -> 归 Command,必须走应用编排、边界校验、审计和必要 outbox。

2. 它是否只读取定义、snapshot、trace 或 view resolve?
   是 -> 归 Query,不得改变状态。

3. 它是否只是通知下游定义变化?
   是 -> 归 Outbound Event,必须通过 outbox。

4. 它是否属于 seed、replay、fingerprint、drift 维护?
   是 -> 归 Operations Job,不得绕过审计和边界规则。

5. 它是否试图写入下游 Use truth?
   是 -> 拒绝进入 method-library。
```

## 12. 核心数据流

### 12.1 数据流图读法

本节的数据流图采用“外部调用 + 内部关键函数 + 交互形式”的表达方式。

它不是 A~H 主要组成部分分层图,而是回答:

```text
外部谁调用?
通过什么形式进入? Command / Query / Event / Snapshot Query / Job
入口接口是什么?
内部哪个概要级关键用例函数接住?
内部做哪些关键领域 / 策略动作?
哪些数据被写入或读取?
通过什么形式输出给下游? Event / Snapshot / Query Result
```

本节允许出现概要级关键函数名,用于表达数据流节点,例如:

```text
publish_method_content()
validate_publish_boundary()
calculate_canonical_fingerprint()
enqueue_outbox_event()
```

但本节不展开 Rust 函数签名、DTO 字段、SQL、错误码、事务实现或 handler 代码。

核心数据流:

| 数据流 | 交互形式 | 优先级 | 目的 |
|---|---|---|---|
| `PublishMethodContent` 写路径 | Command + Outbound Event | P0 | 将方法定义资产发布为权威定义 |
| Downstream Sync 同步路径 | Outbound Event + Snapshot Query | P0 | 让下游消费定义变化并重建索引 |
| `ResolveViewProfile` 查询路径 | Query | P0 | 为 UI / console 解析权威视图策略 |
| Operations / Recovery 路径 | Job / Operations Query | P0 / P1 | 支持 seed、replay、fingerprint 复算和 drift 对账 |
| Plugin / Configuration 路径 | Command + Outbound Event | P1 | 支持方法资产打包、组装和分发 |

### 12.2 PublishMethodContent 写路径

`PublishMethodContent` 是 P0 最核心的写路径。它不是普通 update,而是把 MethodContent 从待发布状态推进到可被下游消费的 published definition。

```text
Method Reviewer / Admin
  |
  | Command: PublishMethodContent
  v
Command API
  |
  v
publish_method_content()
  - load MethodContent draft
  - verify approved_gate_ref
  - check expected_version
  |
  v
validate_publish_boundary()
  - validate lifecycle
  - validate MethodContent references
  - reject Use truth fields
  |
  v
MethodContent.publish()
  - set lifecycle=published
  - assign version
  - freeze published body
  |
  v
calculate_canonical_fingerprint()
  - canonicalize definition body
  - compute fingerprint
  |
  v
append_audit_record()
  - actor_ref
  - approved_gate_ref
  - version
  - fingerprint
  |
  v
enqueue_outbox_event()
  - event: method_library.content.published
  - content_id / kind / version / fingerprint / snapshot_ref
  |
  v
commit boundary
  |
  v
Outbox Relay
  |
  | Event: method_library.content.published
  v
L0-bus
  |
  v
identity / process / capability-hub / artifact / governance / UI
```

关键数据写入:

| 数据 | 写入原因 | 所有权 |
|---|---|---|
| MethodContent lifecycle / version | published definition 的正式状态 | method-library |
| canonical fingerprint | 支撑 drift 检测与审计追溯 | method-library |
| audit record | 记录 actor、gate、版本和原因 | method-library |
| outbox event | 保证定义变化可靠发布 | method-library |
| snapshot_ref | 让下游按需拉取完整定义 | method-library 生成 |

边界说明:

```text
PublishMethodContent 不创建 ProcessInstance。
PublishMethodContent 不创建 WorkItem。
Qualification 发布不创建 QualificationProfile。
Qualification 发布不创建 QualificationBinding。
WorkProductDefinition 发布不保存 Artifact instance 正文。
AIPolicyDef 发布不保存 policy enforce result。
```

失败点与补偿:

| 失败点 | 处理方式 |
|---|---|
| approved_gate_ref 缺失或无效 | 阻断 publish,内容状态不变 |
| expected_version 冲突 | 阻断 publish,要求调用方重新读取 |
| lifecycle / reference / boundary 校验失败 | 阻断 publish,返回边界违例 |
| outbox relay 失败 | outbox 保留 backlog,恢复后 replay |
| 下游不可用 | 不阻断本仓发布,下游通过 event replay / snapshot query 恢复 |

禁止出现:

```text
content 已 published 但没有 fingerprint / audit / outbox。
event 已发布但本仓没有对应 published definition。
下游同步的数据没有 version / fingerprint。
```

### 12.3 Downstream Sync 同步路径

Downstream Sync 使用 event + snapshot 两段式:

```text
event 通知“发生了什么”
snapshot 承载“完整定义是什么”
fingerprint 用于判断“是否还是同一份语义定义”
```

以 `RoleDefinition` 同步到 identity 为例:

```text
Outbox Relay
  |
  | Event: method_library.role_definition.published
  v
L0-bus
  |
  v
identity RoleDefinition consumer
  - read content_id / role_definition_id
  - read version / fingerprint / snapshot_ref
  |
  v
ExportDefinitionSnapshot
  |
  | Snapshot Query
  v
method-library Snapshot Exporter
  - return RoleDefinition snapshot
  - include schema_version
  - include version / fingerprint / lifecycle
  |
  v
identity sync_role_catalog()
  - upsert RoleCatalogEntry
  - store source_ref / source_version / fingerprint
  - do not copy RoleDefinition body as identity truth
```

其他下游同理:

| 下游 | 订阅事件 | Snapshot 用途 | 下游写入 |
|---|---|---|---|
| identity | `qualification.*` / `role_definition.published` | 同步 Qualification / RoleDefinition 定义摘要 | catalog entry / profile 引用锚点 |
| process | `task_definition.published` / `process_template_def.published` | 同步流程与任务定义 | template / task runtime index |
| capability-hub | `qualification.*` | 同步 Qualification 语义锚点 | QualificationBinding 引用来源 |
| artifact | `work_product_definition.published` | 同步制品定义 | artifact kind / acceptance index |
| governance | `ai_policy_def.published` | 同步 policy source | policy source index |
| UI / console | `view_profile.published` | 同步视图策略 | view cache / render config |

边界说明:

```text
下游可以保存 source_version / fingerprint。
下游可以建立本地 catalog / index / cache。
下游不能反向改写 MethodContent definition。
下游不能把 snapshot 当成本仓以外的第二份定义真相。
```

失败点与补偿:

| 失败点 | 处理方式 |
|---|---|
| 下游漏消费 event | `ReplayDefinitionEvents` |
| 下游需要重建索引 | `ExportDefinitionSnapshot` |
| 下游 fingerprint 不一致 | `CompareFingerprint` / `DetectDefinitionDrift(P1)` |
| snapshot schema 版本不兼容 | schema_version + consumer contract |
| 下游短时不可用 | 不影响 method-library definition truth |

### 12.4 ResolveViewProfile 查询路径

`ResolveViewProfile` 是 UI / console 的高频只读路径。它读取 ViewProfile 定义,不改变 MethodContent 状态。

```text
UI / console
  |
  | Query: ResolveViewProfile(role, object_kind, scope)
  v
Query API
  |
  v
resolve_view_profile()
  - read role
  - read object_kind
  - read scope
  |
  v
load_active_view_profiles()
  - use cache if available
  - fallback to definition truth
  - only consider active ViewProfile
  |
  v
match_view_profile()
  - apply matching priority
  - choose best active ViewProfile
  - if no match, default deny or controlled empty view
  |
  v
return query result
  - view_profile_id
  - version
  - fingerprint
  - resolved view policy
```

关键规则:

```text
ResolveViewProfile 是 Query,不得改变 MethodContent。
UI / console 不拥有权威 ViewProfile 规则。
cache / read model 只是优化,不是真相。
返回结果必须可追溯到 ViewProfile definition、version 和 fingerprint。
```

失败点与补偿:

| 失败点 | 处理方式 |
|---|---|
| cache 不可用 | 回源 definition truth |
| ViewProfile 未匹配 | default deny 或受控空视图 |
| UI 持有旧 fingerprint | 通过 view_profile.published event 或重新 query 刷新 |
| 查询延迟过高 | 通过 read model / cache 优化,不改变定义归属 |

### 12.7 数据流共同约束

所有数据流必须遵守:

| 约束 | 说明 |
|---|---|
| Definition / Use 分离 | 本仓只拥有 Definition truth,下游拥有 Use truth |
| Command / Query 分离 | Command 可改状态,Query 不得改状态 |
| 发布链一致 | publish 成功必须同时具备 state、version、fingerprint、audit、outbox |
| Event / Snapshot 分离 | event 通知变化,snapshot 承载完整定义 |
| fingerprint 可追溯 | 下游同步和审计都必须能看到 source version / fingerprint |
| outbox 可靠发布 | 跨仓事件必须经过 outbox,不得直接从领域逻辑发 bus event |
| P1 不污染 P0 | Plugin / Configuration 不得成为 P0 MethodContent 发布前置条件 |
| cache 不是真相 | cache / read model / projection 可重建,不能成为 Definition truth |

数据流边界红线:

```text
不得在 PublishMethodContent 中创建 ProcessInstance。
不得在 PublishMethodContent 中创建 WorkItem。
不得在 Qualification 发布时创建 QualificationProfile。
不得在 Qualification 发布时创建 QualificationBinding。
不得在 WorkProductDefinition 发布时保存 Artifact instance 正文。
不得在 AIPolicyDef 发布时保存 policy enforce result。
不得让 UI / console 本地规则覆盖 ViewProfile definition truth。
```

### 13.1 所有权分类图

### 13.9 数据所有权判定规则

新增数据或对象时,按以下顺序判断:

```text
1. 它是否描述方法定义本身?
   是 -> 候选 Definition truth,归 method-library。

2. 它是否描述方法定义的发布状态、版本、fingerprint 或审计?
   是 -> 归 method-library 的发布与追溯数据。

3. 它是否只是给下游同步或查询的产物?
   是 -> 归 snapshot / event / query result,由 method-library 生成,下游消费。

4. 它是否是外部系统拥有的正文、决策或大对象?
   是 -> method-library 只保存 ref / hash / source_ref。

5. 它是否是为了查询性能构建的读模型?
   是 -> projection / cache,可重建,不得反写真相。

6. 它是否描述下游使用、执行、绑定、实例、交易或运行状态?
   是 -> 属于下游 Use truth,不得进入 method-library。

7. 它是否是 P1 资产打包或组织配置?
   是 -> 归 P1 Plugin / Configuration,但不得污染 P0 Definition truth。
```

最终结论:

```text
method-library 拥有 Definition truth。
method-library 拥有发布、版本、fingerprint、audit 和 outbox 源。
method-library 生成 event / snapshot / query result。
method-library 只保存 gate / blob / schema / standard 等外部 ref。
method-library 的 projection 只读且可重建。
method-library 不拥有任何下游 Use truth。
P1 Plugin / Configuration 是组合真相,但不能污染 P0 Definition truth。
```

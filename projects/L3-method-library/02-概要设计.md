## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L3-method-library` 不是文档资料库,也不是流程执行仓,更不是 UI 规则临时脚本仓。它是 **“方法资产中心”**。

你可以把它理解成:
- 平台里正式可被引用、发布、版本化的方法资产到底有哪些
- 角色定义、任务定义、制品定义、过程模板、视图策略、AI Policy 这些内容的权威源在哪里
- 这些方法资产怎样从 draft 演进到 published / deprecated / retired
- 一组方法资产怎样被打包成 plugin,再怎样被组装成 configuration
- 下游仓怎样稳定同步这些定义,并通过 fingerprint 感知 drift

这些事情,都由 `L3-method-library` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L3-method-library`,这些方法资产事实就会散落在:
- `identity` 各自维护的 role 定义副本里
- `process` 各自维护的 template 内容里
- `governance` 自己写死的 policy 配置里
- `UI` 本地维护的 view profile 规则里
- marketplace 的上架元数据里
- 各类 markdown / README / 会议纪要里

结果就会出现:
- 平台里到底“应该怎么做”没有统一权威源
- `RoleDefinition`、`ProcessTemplateDef`、`ViewProfile`、`AIPolicyDef` 在不同仓逐步漂移
- 下游能执行,但不知道当前执行的是否还是同一版方法资产
- Marketplace 可以分发包,却不能证明包里的资产和平台当前权威定义一致
- 方法论只能写在文档里,无法成为可发布、可验证、可同步的正式资产

所以 `L3-method-library` 必须独立存在,作为:
> **平台角色、任务、制品、流程模板、视图策略、AI Policy 与方法组装能力的单一真相源。**

### 1.3 新人最容易混淆的几个词

#### MethodContent
就是:
> 一类正式方法资产的抽象基类。

它不是一篇说明文档,而是平台真正承认的资产对象。

#### RoleDefinition
就是:
> 一个正式角色定义资产。

它不是 `identity` 里的 `RoleCatalogEntry`。前者是权威定义,后者是运行时索引。

#### ProcessTemplateDef
就是:
> 一个正式过程模板定义。

它不是 `process` 里的 `ProcessInstance`,也不是运行中的流程执行真相。

#### ViewProfile
就是:
> 一个正式视图策略定义,回答某种 role × object_kind × scope 下应该怎么看。

它不是 UI 本地临时渲染规则。

#### AIPolicyDef
就是:
> 一个正式 AI Policy 定义资产。

它不是 governance runtime 当下正在 enforce 的那条运行规则本体。

#### MethodPlugin
就是:
> 一组方法资产的打包单元。

它不是 marketplace 上的交易条目本体。

#### MethodConfiguration
就是:
> 一组 plugin 的激活与组装结果。

它不是下游运行时状态本体,而是方法资产组合真相。

#### fingerprint
就是:
> 用 canonical JSON 计算出来的内容哈希,用于识别方法资产语义是否变化。

它不是版本号,也不是下游自己猜出来的 drift 标志。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L3-method-library/02` 时,先收稳以下前提:
- `L3-method-library` 不应按 6 个子类名字平铺理解,而应按方法资产主链责任拆
- method-library 至少应拆成“方法内容定义 / 方法版本与发布治理 / 资产打包与配置组装 / 下游同步与漂移防护 / 查询解析与分发出口”五个主要部分
- method-library 自己拥有的真相不是 process execution、identity 索引、governance enforce runtime 或 UI 渲染逻辑,而是 MethodContent / Plugin / Configuration 这类方法资产定义真相
- `L3-method-library` 只能向下游提供 Definition,不能替下游持有 Use truth
- 02 的重点不是“列有哪些资产类名”,而是先把“方法资产中心在平台里到底是什么、和 process/identity/governance/UI/marketplace 怎么分层”讲清楚
- fingerprint、publish gate、supersede、plugin、configuration、resolve view 这些不是零散机制,而是方法资产主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的方法资产心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,平台不只要运行代码,还要运行方法。用户真正需要的不是“把方法写在 README 里”,而是:
- 角色、任务、制品、过程模板、视图规则、AI Policy 都有正式定义源
- 这些定义可以发布、弃用、退役,并保留版本与 fingerprint
- `identity`、`process`、`governance`、`UI`、marketplace 都能基于同一套方法资产协作
- plugin 与 configuration 可以把方法资产变成可打包、可启用、可分发的组合单元
- 下游仓能知道自己正在消费哪一版权威资产,以及何时 drift

如果把这些逻辑分别散落到:
- 各业务仓自己的本地定义
- 各类 markdown / README / 会议记录
- UI 本地规则配置
- marketplace 元数据

系统会快速退化成:
- 角色定义、模板定义、AI Policy 和视图策略逐渐分叉
- 下游仓可以运行,但无法证明所用资产仍是当前权威定义
- plugin / configuration 失去稳定组合基础
- 方法论无法产品化、可验证化、可分发化

因此,本概要设计的任务就是:
> **把 `L3-method-library` 写成一个新人也能看懂的“方法资产中心”,而不是把定义、发布、分发和消费索引混成一锅。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| MethodContent 正式化 | 设计已存在,仓级主链未收稳 | 6 子类形成正式资产真相 | 需正式收敛 |
| Template / Role / Policy 漂移 | 下游各自同步风险高 | fingerprint_changed 覆盖率 100% | 需固定 drift 主链 |
| ViewProfile 权威源 | UI 本地拼接风险高 | ResolveViewProfile 成为权威解析入口 | 需单列并固定 |
| Plugin / Configuration 组装 | 仅架构草案 | 可打包、可启用、可分发 | 需形成产品化主线 |
| 下游同步链 | process / identity / governance / UI 各自消费 | 同步成功率 100% 样本链 | 需收稳接缝 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把平台的方法论、角色、模板、视图和 AI Policy 变成可管理、可发布、可分发、可被下游稳定消费的正式资产
- **技术问题**:MethodContent、fingerprint、publish gate、MethodPlugin、MethodConfiguration、ResolveViewProfile 与下游同步事件之间的边界如何稳定建模,并与 identity/process/governance/UI/marketplace 清晰协作而不混层

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 method-library 的方法资产职责 | MethodContent / Plugin / Configuration / ResolveViewProfile / fingerprint 职责无歧义 | 文档评审 |
| 明确与下游仓边界 | Definition/Use 分离清晰,下游只消费权威定义 | 文档评审 + 后续测试 |
| 明确 drift 防护主线 | fingerprint_changed 传播正确率 100% | 集成测试 |
| 支撑后续详细设计与测试 | 本文足以承接 `03-详细设计.md` 的对象模型、发布主线和同步主线 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文执行 process runtime 本体
- 不在本文管理 `identity` 的 RoleCatalogEntry 或成员生命周期
- 不在本文执行 governance policy enforce runtime
- 不在本文实现 UI 渲染细节
- 不在本文承接 marketplace 交易、购买与计费流程

## 4. 约束条件

### 4.1 技术约束

- Definition vs Use 必须严格分离,method-library 只定义不执行
- `ProcessTemplateDef` 是模板权威源,不能被 process 反向改写
- published 内容核心字段不可直接修改,只能 supersede
- fingerprint 变化必须显式发出 drift 信号,不能依赖下游自行猜测
- `ViewProfile` 的权威源必须留在 method-library,不能由 UI 长期本地化持有

### 4.2 资源约束

- 内容与历史版本数量会长期增长,必须接受内容膨胀而非为了省量放弃 supersede
- Plugin / Configuration 必须可组合,但复杂度不能无限失控
- object storage 只能承载 blob / guidance / package,不应代替元数据主库

### 4.3 时间约束

- 当前阶段先收稳方法资产中心主链,而不是先做复杂商业化与 Marketplace 扩展
- `RoleDefinition → identity`、`ProcessTemplateDef → process`、`AIPolicyDef → governance`、`ViewProfile → UI` 这些主接缝必须优先收稳

### 4.4 合规约束

- publish 必须经 Gate,不得无审批直接生效
- 方法资产版本链必须可审计、可回溯
- Tailoring / profile group / policy source 等口径必须符合既有标准约束
- drift 发现后必须留痕,不能静默漂移

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| MethodContent 记录 | 2000w(含历史版本) | 多组织长期资产增长 |
| Plugin | 5w-50w | Marketplace 与组织内分发预估 |
| Configuration | 百万级 | 组织 / 项目 / 场景级组合 |
| ResolveViewProfile QPS | 5000 | UI 高频消费 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ method authors / leads      │
                    │ - draft / review / publish  │
                    └────────────┬───────────────┘
                                 │ method asset input
                                 ▼
                    ┌────────────────────────────┐
                    │ L3-method-library          │
                    │ - MethodContent            │
                    │ - Plugin / Configuration   │
                    │ - fingerprint / ViewProfile│
                    └────────────┬───────────────┘
                                 │ published definition / drift signal
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ identity / process / gov   │   │ UI / console               │   │ marketplace                │
│ - role sync                │   │ - ResolveViewProfile       │   │ - plugin distribution      │
│ - template / policy sync   │   │ - view cache               │   │ - package metadata         │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L3-method-library` 自己负责方法资产定义、打包、组装、发布和 drift 权威源
- `identity`、`process`、`governance` 只消费对应定义,不拥有这些定义真相
- `UI` 消费 `ViewProfile`,但不持有其权威定义
- marketplace 消费 plugin 元数据和包,但不拥有方法资产内容真相
- 这个仓的角色不是“执行方法”,而是“定义方法并让别人稳定消费”

所以 `L3-method-library` 在全局里的角色是:
> **把平台中正式可复用的方法、角色、模板、视图与 AI Policy 收敛为可发布、可版本化、可同步、可分发的资产中心。**

### 5.3 系统边界

**做什么**:
- 持有 MethodContent 6 子类真相
- 持有 MethodPlugin / MethodConfiguration 真相
- 管理 publish / supersede / deprecate / retire 生命周期
- 生成与维护 fingerprint / source_drift 信号
- 提供 ResolveViewProfile 等只读解析出口

**不做什么**:
- 不执行 process runtime
- 不拥有 identity 成员真相
- 不执行业务治理动作
- 不渲染 UI
- 不承担 marketplace 交易真相

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| PostgreSQL | 99.95% | 不可用则阻断写入与发布 |
| object storage | 99.9% | guidance / example / package blob 暂不可读时,保留元数据只读 |
| L0-bus | 99.95% | publish backlog / replay,不得静默丢失 drift 信号 |
| process / identity / governance / UI | 99.9% | 下游延迟只影响消费,method-library 仍保留权威定义与 drift 告警 |
| marketplace | 99.9% | 先组织内发布,不阻断定义仓本体 |

### 5.5 关键依赖风险

- MethodContent 与下游索引 drift 会让 process / identity / governance / UI 基于过期定义运行
- ViewProfile 匹配错误会影响整批 UI 消费面
- Plugin 依赖环或 Configuration 组合爆炸会让方法资产失去可控组装能力
- Marketplace 的商业化诉求可能反向污染核心内容模型

### 6.2 主要组成部分说明

> 这里的“主要部分”不是 6 个子类名字顺排,也不是简单 CRUD 分组。  
> 它按 **资产定义职责 + 生命周期治理 + 组装分发主线 + 下游同步接缝 + 查询解析出口** 来拆分。  
> 因此下面每一部分都可能包含多个对象和机制,共同支撑同一段方法资产主链。

#### 方法内容定义部分

- **它是什么**: 这是 `L3-method-library` 的资产真相层,一起回答“平台到底有哪些正式方法资产”
- **为什么单独有它**: 如果没有独立定义层,角色、模板、视图、Policy 会散落到下游仓和文档里,失去统一权威源
- **负责什么**:
  - 定义 MethodContent 抽象基类
  - 定义 `RoleDefinition`、`TaskDefinition`、`WorkProductDefinition`、`ProcessTemplateDef`、`ViewProfile`、`AIPolicyDef`
  - 提供这些资产的正式元数据、生命周期入口和引用锚点
- **不负责什么 / 容易混淆点**:
  - 不负责 process execution 真相
  - 不负责 identity 的运行时索引真相
  - 不负责 governance enforce runtime
  - 最容易和 README / markdown 方法说明、identity RoleCatalogEntry、UI 本地视图规则混淆
- **与其他部分交互**:
  - 下游: 方法版本与发布治理、下游同步与漂移防护、查询解析与分发出口
  - 外部: process / identity / governance / UI / marketplace
  - 交互类型: 资产定义型 + 只读消费型
- **后续详细设计展开点**:
  - MethodContent 抽象模型
  - 6 子类对象骨架
  - Definition/Use 边界规则

#### 方法版本与发布治理部分

- **它是什么**: 这是方法资产生命周期与发布门禁层,一起回答“这些资产怎样安全发布与演进”
- **为什么单独有它**: 如果不单列,内容定义和内容发布裁决会混成一层,published 内容可变与版本不可追溯问题会同时出现
- **负责什么**:
  - 管理 draft / in_review / published / deprecated / retired 生命周期
  - 管理 publish gate、supersede、version 与 fingerprint
  - 确保 published 内容核心字段不可直接修改
- **不负责什么 / 容易混淆点**:
  - 不负责下游同步是否成功消费
  - 不负责 configuration 的运行时启用状态本体
  - 最容易和普通内容编辑流程、下游缓存更新混淆
- **与其他部分交互**:
  - 上游: 方法内容定义部分
  - 下游: 下游同步与漂移防护、查询解析与分发出口
  - 交互类型: 生命周期治理型 + 发布裁决型
- **后续详细设计展开点**:
  - publish / supersede / retire 状态机
  - fingerprint 生成规则
  - gate 约束链

#### 资产打包与配置组装部分

- **它是什么**: 这是方法资产从单个定义走向组合与分发的层,一起回答“方法资产怎样被打包和组合”
- **为什么单独有它**: Plugin 与 Configuration 不是内容本体,也不是运行时状态,但它们是方法资产产品化和组织化使用的关键层
- **负责什么**:
  - 定义 `MethodPlugin`
  - 定义 `MethodConfiguration`
  - 管理 selected_plugins、variability、effective content set
- **不负责什么 / 容易混淆点**:
  - 不负责 marketplace listing / 交易流程
  - 不负责 process / identity / governance 的运行时状态本体
  - 最容易和 package 元数据、组织运行态配置混淆
- **与其他部分交互**:
  - 上游: 方法内容定义部分、方法版本与发布治理部分
  - 下游: 查询解析与分发出口、下游同步与漂移防护、marketplace
  - 交互类型: 打包组装型 + 分发前置型
- **后续详细设计展开点**:
  - Plugin / Configuration 对象模型
  - dependency DAG / active freeze 规则
  - effective content set 计算骨架

#### 下游同步与漂移防护部分

- **它是什么**: 这是 method-library 面向下游仓的同步与 drift 控制层,一起回答“下游怎样稳定同步、怎样发现漂移”
- **为什么单独有它**: method-library 的权威性不只来自“定义存在”,还来自“下游知道自己是不是在消费同一版定义”
- **负责什么**:
  - 发出 fingerprint_changed / published / retired / source_drift 相关信号
  - 支撑 process / identity / governance / UI / marketplace 同步主链
  - 定义 drift 的权威检测依据
- **不负责什么 / 容易混淆点**:
  - 不替下游执行同步后的业务逻辑
  - 不把 source_drift 处理成下游本地缓存私事
  - 最容易和下游自己做的 reconcile / cache refresh 混淆
- **与其他部分交互**:
  - 上游: 方法版本与发布治理部分、资产打包与配置组装部分
  - 下游: process / identity / governance / UI / marketplace
  - 交互类型: 事件同步型 + 漂移告警型
- **后续详细设计展开点**:
  - downstream publisher
  - fingerprint verify / source_drift 流程
  - replay / lag / 对账输入

#### 查询解析与分发出口部分

- **它是什么**: 这是 method-library 的读取、解析和分发消费层,一起回答“资产怎样被读取、解析和分发出去”
- **为什么单独有它**: method-library 不只要写得对,还要让下游稳定读到正确内容,特别是 `ResolveViewProfile` 这种高频消费面不能混到发布主链里
- **负责什么**:
  - 提供 content / plugin / configuration 只读查询
  - 提供 `ResolveViewProfile`
  - 提供 guidance / example / package blob 的只读分发出口
- **不负责什么 / 容易混淆点**:
  - 不负责 UI 最终渲染
  - 不负责 marketplace 交易
  - 不负责下游将内容转成自己的执行真相
  - 最容易和 UI cache、本地页面规则、marketplace listing 混淆
- **与其他部分交互**:
  - 上游: 方法内容定义部分、资产打包与配置组装部分
  - 下游: UI / process / identity / governance / marketplace / human readers
  - 交互类型: 只读查询型 + 解析分发型
- **后续详细设计展开点**:
  - ResolveViewProfile 匹配逻辑
  - package / blob query 出口
  - read model / cache 边界

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                ┌────────────────────────────┐
                │ method authors / leads      │
                │ - draft / review / publish  │
                └────────────┬───────────────┘
                             │ asset input
                             ▼
                ┌────────────────────────────┐
                │ L3-method-library          │
                │ - MethodContent            │
                │ - Plugin / Configuration   │
                │ - fingerprint / view rules │
                └────────────┬───────────────┘
                             │ published definition / drift signal
                             ▼
┌────────────────────────────┐ ┌────────────────────────────┐ ┌────────────────────────────┐
│ process / identity / gov   │ │ UI / console               │ │ marketplace                │
│ - template / role / policy │ │ - ResolveViewProfile       │ │ - plugin distribution      │
│ - downstream sync          │ │ - view cache               │ │ - package metadata         │
└────────────────────────────┘ └────────────────────────────┘ └────────────────────────────┘
```

### 7.2 总解释

- `L3-method-library` 自己负责“定义方法资产”“治理方法资产版本”“打包和组装方法资产”“向下游发布定义变化”“提供只读解析出口”
- `L0-core` 的交互主要落在 **方法内容定义部分** 与 **查询解析与分发出口部分**,为资产对象提供共享基元与类型契约
- `L0-bus` 的交互主要落在 **下游同步与漂移防护部分**,承载 published / fingerprint_changed / source_drift 等事件主线
- `identity`、`process`、`governance` 的交互主要落在 **方法内容定义部分** 与 **下游同步与漂移防护部分**,消费 RoleDefinition / ProcessTemplateDef / AIPolicyDef
- UI 的交互主要落在 **查询解析与分发出口部分**,消费 ResolveViewProfile 与只读查询
- marketplace 的交互主要落在 **资产打包与配置组装部分** 与 **查询解析与分发出口部分**,消费 plugin/package 元数据而不拥有内容真相

### 7.3 分模块交互说明(逐个写)

#### 与 `process` 的交互

```text
┌────────────────────────────┐
│ L3-method-library          │
│ - ProcessTemplateDef       │
│ - fingerprint              │
└────────────┬───────────────┘
             │ template publish / drift signal
             ▼
┌────────────────────────────┐
│ process                    │
│ - template sync index      │
│ - execution reference      │
└────────────────────────────┘
```

- `process` 是 **模板定义的执行侧消费方**
- **交互类型**: 定义消费型 + drift 同步型交互
- **主流程位置**: `ProcessTemplateDef` 发布、supersede、retire 与 drift 识别时进入主流程
- **交互解释**:
  - method-library 提供模板定义与 fingerprint
  - process 建自己的执行索引
  - method-library 不接管 process execution 真相
- **高风险异常流**:
  - process 继续运行过期模板且未识别 drift
- 后续 `03-详细设计.md` 继续展开:
  - template publish event
  - process sync contract

- **高风险异常流**:
  - `RoleDefinition` 与 `RoleCatalogEntry` 漂移导致成员引用错误角色元数据

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是索引消费方、哪个模块是执行消费方、哪个模块是分发消费方

本节**不**展开:
- 具体 event schema
- 具体 ViewProfile 匹配算法
- Plugin 打包结构细节
- supersede / drift 的代码实现细节
- cache / replay / object storage 低层实现

这些内容留到 `03-详细设计.md` 中继续展开。

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 MethodContent / MethodPlugin / MethodConfiguration / fingerprint / publish gate / ResolveViewProfile / downstream sync 真相
- 把角色、任务、制品、模板、视图、AI Policy 等方法资产正式化、版本化、可发布化
- 管理 supersede / deprecate / retire 演进主线
- 把 package / blob / metadata / query / drift signal 统一收敛到方法资产主链中

**本模块不做什么**:
- 不执行 process runtime
- 不持有 identity 成员真相或 role catalog 索引真相
- 不持有 governance enforce runtime 真相
- 不承担 UI 渲染或 marketplace 交易真相
- 不把 README / markdown / examples 冒充方法资产权威源

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 method-library“为什么存在”,而是让开发者可以直接开始实现:
- MethodContent 6 子类如何作为正式资产对象落地
- publish / supersede / fingerprint / drift 如何形成统一版本治理主线
- Plugin / Configuration 如何在不复制内容正文的前提下完成打包与组装
- ResolveViewProfile 如何成为 UI 等下游的权威解析出口
- process / identity / governance / UI / marketplace 如何通过事件与查询稳定消费这些定义

如果不先把这些内容采集清楚,03 很容易退化成:
- 六种内容类型的字段表清单
- 模板和角色的 README 搬运稿
- plugin / configuration 的概念笔记
- 下游同步与 drift 机制各写一套、互不对账

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `RoleDefinition / ProcessTemplateDef / ViewProfile / MethodPlugin` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分

- 最后再进入横向的对象模型、流程、存储、异常与测试细节

#### 5.2.4 关键函数代码片段

```rust
/// 根据方法作者提交的草稿创建正式方法资产草稿对象。
fn draft_method_content(
    content_repo: &dyn ContentRepo,
    draft: DraftMethodContentDraft,
) {
    // [MethodContent::从草稿创建]
    // 先把统一资产头与具体子类草稿收束成正式方法资产对象。
    let content = MethodContent::from_draft(draft);

    // [content.校验定义边界]
    // 再校验该对象只承载定义语义,不承载下游使用真相。
    content.validate_definition_boundary();

    // [content_repo.保存草稿]
    // 最后把草稿写入内容仓,等待后续评审与发布治理主线继续承接。
    content_repo.save_draft(content);
}
```

这段实现守住的边界是:
- content 必须先形成统一资产头,再进入发布主线
- method-library 只能定义资产,不能写入运行时使用状态
- RoleDefinition / ProcessTemplateDef / ViewProfile / AIPolicyDef 只承载定义语义,不替代 identity / process / UI / governance 真相

#### 5.2.5 该部分的边界与非职责
- 不负责 publish gate 裁决
- 不负责下游同步成功确认
- 不负责 plugin / configuration 组合
- 不负责 UI 渲染或 process runtime

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `方法版本与发布治理部分` 交付 draft content
- 向 `资产打包与配置组装部分` 提供已发布内容引用
- 向 `查询解析与分发出口部分` 提供权威内容读取输入

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `MethodContent ≠ 文档正文文件` 必须写死
- `Definition ≠ Use` 必须写死,否则下游执行真相会倒灌回来
- ViewProfile 若被当成 UI 运行规则碎片而非权威资产,后续 drift 会失控

    // [gate_ref.校验发布批准]
    // 先确认这次发布有正式 Gate 决策引用,不能无审批直接生效。
    gate_ref.validate_publishable();

    // [content.生成新 fingerprint]
    // 再根据 canonical JSON 生成当前发布版本的权威指纹。
    let published = content.publish_with_fingerprint(Fingerprint::from_content(content));

    // [content_repo.保存已发布版本]
    // 最后以正式发布版本写入内容仓,供下游同步与查询主线消费。
    content_repo.save_published(published, gate_ref);
}
```

这段实现守住的边界是:
- 发布是治理动作,不是普通保存动作
- published 内容必须冻结核心字段,后续修改只能 supersede
- fingerprint 是发布主链的权威比较基线,不能延后补算

#### 5.3.5 该部分的边界与非职责
- 不负责 process / identity / governance / UI 的同步结果落地
- 不负责 plugin 打包本体
- 不负责 view resolve 查询本体

#### 5.3.6 该部分与其他主要部分的接缝

/// 在内容发布后向下游发送正式指纹变化信号,并记录同步检查点。
fn emit_fingerprint_changed(
    sync_repo: &dyn SyncRepo,
    signal: FingerprintChangedSignal,
) {
    // [signal.校验目标与内容匹配]
    // 先确认这条 signal 与内容种类、下游目标之间的同步关系成立。
    signal.validate_target_contract();

    // [sync_repo.保存同步检查点]
    // 再记录一次待同步检查点,作为后续 replay 与 drift compare 的基线。
    sync_repo.save_checkpoint(DownstreamSyncCheckpoint::from_signal(signal));

    // [sync_repo.发布指纹变化信号]
    // 最后向 bus 主线发出正式同步信号,供下游消费并对账。
    sync_repo.publish_signal(signal);
}
```

这段实现守住的边界是:
- drift 是 method-library 的权威比较结果,不是下游自己的猜测逻辑
- 先有 checkpoint,再有广播,便于 replay 与 source_drift 对账
- process / identity / governance / UI 的同步逻辑各自不同,但都要使用统一 signal 语义

### 7.5 关键函数/命令级伪代码

#### `SupersedeContent`

```text
function SupersedeContent(input):
    1. 校验旧内容已发布且允许被替代
    2. 校验新内容草稿与旧内容类型一致
    3. 生成新的 version 与 fingerprint
    4. 建立 SupersedeLink
    5. 保存新 published 版本与 supersede history
    6. 发 fingerprint_changed / published 事件
    7. 返回新 content_id / version
```

#### `VerifyContentFingerprint`

```text
function VerifyContentFingerprint(input):
    1. 读取权威 MethodContent fingerprint
    2. 读取下游上报 fingerprint
    3. 比较两者是否一致
    4. 若不一致则创建 SourceDriftRecord
    5. 写入 drift report 与 checkpoint 证据
    6. 返回 match / drift 结果
```

## 8. 运行期主线场景

### 8.1 场景 A · 正式内容从草稿进入发布主线

```text
Draft content
   │
   ▼
Gate approved
   │
   ▼
Published + fingerprint fixed
   │
   ▼
publish history written
   │
   ▼
fingerprint_changed emitted
```

**开发者关注点**:
- publish 与 fingerprint 是否同步成立
- published 内容是否冻结核心字段
- 发布后是否能稳定进入下游同步链

### 8.2 场景 B · 下游仓同步并识别 drift

```text
Published content changed
   │
   ▼
FingerprintChangedSignal emitted
   │
   ├─▶ process syncs template index
   ├─▶ identity syncs role catalog
   ├─▶ governance syncs policy source
   └─▶ UI refreshes view cache
```

**开发者关注点**:
- drift 是谁来判定
- checkpoint 与 replay 是否能对账
- 下游同步失败是否会形成 source_drift 证据

### 8.3 场景 C · 一组内容进入 plugin/configuration 与只读解析出口

```text
Published content set
   │
   ▼
MethodPlugin created
   │
   ▼
MethodConfiguration activated
   │
   ├─▶ ResolveViewProfile
   ├─▶ ContentSummary query
   └─▶ Package/blob distribution
```

**开发者关注点**:
- plugin 是否只引用内容而不复制正文
- configuration 是否保持 active 后稳定
- query/resolve 是否仍基于已发布 active 内容

### 8.4 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| 方法作者 / leads | DraftContent / PublishContent | 方法内容定义部分 + 方法版本与发布治理部分 | 形成正式方法资产 |

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| publish 无 gate | 拒绝发布 |
| published 内容被直接修改 | 拒绝修改并要求走 supersede |
| plugin 依赖成环 | 拒绝创建或发布插件 |
| ViewProfile 唯一命中失败 | 返回歧义错误并阻断 resolve |
| 下游同步失败 | 写 checkpoint / source_drift / replay evidence |
| object storage 写失败 | 保持 draft,不进入 published |

### 11.1 重试 / 降级 / 熔断 / 补偿
- 下游同步失败可通过 replay 重试,但不得静默丢失 drift 信号
- object storage 暂不可用时,元数据可只读,但内容不得假发布
- resolve / query 缓存失败可降级到主读模型,但不能读草稿或 retired 内容

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 方法内容定义部分 | 资产定义混入下游使用语义 | definition boundary validate | 拒绝保存内容 | 修正文稿后重试 |
| 方法版本与发布治理部分 | 无 gate 发布 / supersede 断链 | lifecycle / gate / link validate | 拒绝发布或替代 | 补齐 gate / 版本链 |
| 资产打包与配置组装部分 | plugin 依赖成环 / effective set 漂移 | DAG / active freeze validate | 拒绝创建或激活 | 修订依赖后重试 |
| 下游同步与漂移防护部分 | signal 丢失 / drift 未留痕 | checkpoint / drift validate | 记录 lag / drift 并重发 | replay / resync |
| 查询解析与分发出口部分 | resolve 歧义 / query 读到未发布内容 | resolve / read boundary validate | 拒绝返回成功结果 | 修正 active 集合或缓存 |

## 15. 结论

本详细设计的核心结论是：
- `L3-method-library` 的实现主轴必须按内容定义 / 版本治理 / 打包组装 / 同步漂移 / 查询分发五个主要部分组织,而不是按 6 子类名字顺排
- method-library 真相层只持有方法资产定义、版本治理、组装配置与 drift 权威源,不接管 process / identity / governance / UI / marketplace 的使用真相
- 所有下游同步、resolve、package、replay 与 drift 对账都必须建立在正式 MethodContent、fingerprint、plugin/configuration 与 checkpoint 证据链之上

后续测试与验收文档,应直接围绕这套方法资产主链、边界、同步机制与 drift 防护展开.

## 2. 验收目标与范围

> 校准来源:
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“验收目标”“验收范围表”“只验接缝的下游 / 外部能力”“P0 / P1 / P2 裁决口径”和“范围项到一票否决候选”小节。

本轮验收目标是裁决 `L3-method-library` 是否作为方法资产定义、正式化、版本、受控消费、分发、追溯、一致性保护、证据线索和边界安全的事实真相仓成立。

| 验收目标 | 裁决口径 |
|---|---|
| 方法资产定义 truth 归属本仓 | 定义、身份目录、正式化版本、关系、分发、追溯和证据线索不得被消费仓、运行仓、外部正文或观测材料替代。 |
| 正式化与版本稳定成立 | 正式版本语义稳定;正式 / 非正式语境可区分;版本变化显式并可追溯。 |
| 受控消费与分发成立 | 下游只能通过正式引用、safe shell、summary、handoff 或受控消费边界使用方法资产语义。 |
| 追溯、一致性和证据线索成立 | formalization、version semantic change、impact、lineage、audit、evidence 和 report 可回指源。 |
| 配置、安全、依赖和可观测边界成立 | P0 profile、config fail-fast、dependency boundary、redaction、safe diagnostic 和 body-free signal 成立。 |

| 范围等级 | 纳入内容 | 验收地位 | 禁止误用 |
|---|---|---|---|
| P0 core | definition truth、identity/catalog、formalization/version、controlled consumption、distribution/handoff、external summary/reference、traceability/impact/evidence、operations job/report、config profile、dependency boundary、redaction、observability boundary。 | 必须可裁决通过 / 失败 / VETO 影响。 | 不得用口头说明、静态证据、`latest` 或 P1 selected-run 替代。 |
| P1 selected-run | durable / real-like adapter、真实外部服务、staging-like profile、selected-run。 | 可作为增强验收或 residual。 | 不得替代 P0 controlled suite 缺口。 |
| P2 future | production-like capacity、multi-region、tenant profile、高级 dashboard、复杂 marketplace / package 等 future 能力。 | 只作为 residual、后续验收或运维准备输入。 | 不得进入当前 pass/fail 前置。 |

process、identity、runtime、member-images、governance、capability-hub、marketplace、UI/console、external provider 和 artifact/archive 只验 typed ref、safe shell、summary、handoff、adapter availability、redaction 和不可反写真相;不验对方内部 truth、产品体验或生产 SLA。

## 3. 验收基线

> 校准来源:
> - `design-calibration/06_acceptance_step_03_baseline.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“验收基线表”“证据入口基线表”“P0 环境 / 配置基线”“EV-ML 证据基线”“基线变更处理规则”和“不可接受基线引用”小节。

| 基线类型 | 必须固定的内容 | 缺失影响 |
|---|---|---|
| 文档 / 设计基线 | `00`~`05` 的 design commit / source ref。 | 不得进入正式验收。 |
| 标准基线 | 验收 SOP、验收书写规范、中间产物规范、可落码性标准的 source ref。 | 不得裁决验收闭环。 |
| 交付基线 | implementation commit、build id、image digest、package digest 或等价交付标识。 | 无固定交付物不得通过。 |
| core upstream 基线 | `L0-core` 或等价 core contract / package version。 | typed ref / base contract 不可裁决。 |
| 环境 / 配置基线 | P0 profile、config digest、runtime config source、adapter mode、fixture / seed / replay root。 | P0 evidence 不可信。 |
| 证据基线 | 唯一非 `latest` 的 `<run_id>`、`EV-ML-*` evidence families、evidence index。 | 缺失即不可裁决。 |

| 证据入口 | 固定路径 | 验收用途 |
|---|---|---|
| 原始 artifact | `artifacts/test/<run_id>/...` | 复核机器原始证据、suite result、case artifact、stdout/stderr 或 safe failure evidence。 |
| suite report | `reports/runs/<run_id>/suites/<suite>.md` | 阅读单 suite 结论;必须由 raw artifact 推导。 |
| run summary | `reports/runs/<run_id>/summary.md` | 汇总 run 状态,不得替代 suite report 或 raw artifact。 |
| evidence index | `reports/runs/<run_id>/evidence-index.md` | 将 `EV-ML-*` 绑定 TC、suite、artifact、report、AC/VETO。 |
| acceptance handoff | `reports/acceptance/handoff.md` | 汇总送验范围、baseline、run_id、P0/P1/P2、未覆盖项和 residual。 |
| veto checklist | `reports/acceptance/veto-checklist.md` | 逐项判断 `VETO-ML-*` 是否触发,不得静态默认 passed。 |
| risk acceptance | `reports/acceptance/risk-acceptance.md` | 支撑有条件通过和 residual 接受,不得覆盖 P0 hard gate。 |
| open issues | `reports/acceptance/open-issues.md` | 支撑不通过、有条件通过或待修复结论。 |

不可接受基线引用包括 `latest`、无 artifact/report pair 的单侧材料、静态 JSON 直接生成 EV/VETO passed、泛化测试环境、P1 unavailable 计入 P0 passed、source-missing stop 被默认值绕过。

## 4. 进入条件与退出条件

> 校准来源:
> - `design-calibration/06_acceptance_step_04_entry_exit.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“进入条件”“退出条件”“暂停 / 不可裁决条件”“风险接受前置”和“进入 / 退出来源追溯”小节。

### 4.1 进入条件

| 条件 | 判定 |
|---|---|
| `00`~`05` source refs、standards refs、implementation commit、core upstream ref、P0 profile、config digest、fixture / seed / replay root 已固定。 | 必须满足。 |
| `<run_id>` 已固定且不是 `latest`。 | 必须满足。 |
| `artifacts/test/<run_id>` 与 `reports/runs/<run_id>` 均存在,且 blocking suite 有 raw artifact / generated report pair。 | 必须满足。 |
| `reports/acceptance/handoff.md`、`veto-checklist.md`、必要的 `risk-acceptance.md` 与 `open-issues.md` 已准备。 | 必须满足。 |
| redaction、dependency、config redline、report audit、P0 profile 装配均无已知阻断项。 | 必须满足。 |
| 当前无未关闭 S 级缺陷、未复验 VETO 修复或被私补的 source-missing stop。 | 必须满足。 |

### 4.2 退出条件

| 条件 | 判定 |
|---|---|
| 每个 P0 验收项都有明确结论,并能回指正式需求 / 设计契约、`TC-ML-*`、`EV-ML-*` 和 report path。 | 必须满足。 |
| Step 5~Step 11 的 P0 门禁、证据门禁和 VETO 均已完成停审。 | 必须满足。 |
| 所有 P0 blocking suite 均有 raw artifact / run report pairing;`EV-ML-*` 无 orphan EV、无静态造证据、无缺 report path。 | 必须满足。 |
| `VETO-ML-*` 有真实 evidence 支撑未触发;S=0。 | 必须满足。 |
| A 级缺陷已修复或正式接受且不触发 VETO;B/R residual 已进入 risk acceptance 或 open issues。 | 必须满足。 |
| `release-main-smoke` 只证明代表性闭环,未替代底层 suite。 | 必须满足。 |
| 最终结论三值口径和签署角色可执行。 | 必须满足。 |

缺 source refs、implementation commit、config digest、run_id、artifact/report、handoff、veto checklist、evidence index,或出现 `latest`、静态 evidence、P0 unavailable marked passed、baseline 变化未回归、设计闭口缺失时,验收必须暂停或不可裁决。

## 6. 数据边界与架构红线验收

| ML-RL-004 | 外部正文禁止入仓 | 外部标准、ADR、artifact、archive、evidence、API response、下游回报只以 ref / summary / marker / digest / safe reason 承接。 | 任一 truth、material、audit、report、handoff、observable output 保存外部正文、raw payload 或 provider body。 | `EV-ML-REDACTION-001`;`EV-ML-REPORT-001` |

| ML-RL-006 | 运行期 / 事件协作不得写成源码级拥有 | 只有 `L0-core` 作为编译期基础依赖;运行期和事件协作通过正式 ref、adapter、event、handoff 或 fake seam。 | 下游业务仓源码级依赖本仓业务实现,或事件协作被写成编译期拥有关系。 | `EV-ML-DEPENDENCY-001` |

任一 `VETO-ML-001~014` 命中时,最终结论不得为“通过”或“有条件通过”。VETO 不得被风险接受、P1 selected-run、residual、人工口头确认、后续补证据或签署覆盖。

## 12. 缺陷分级、复验与放行规则

> 校准来源:
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“缺陷分级表”“S 级阻断判定表”“修复后复验矩阵”“放行规则”“关闭证据清单”和“非阻断 / 后移边界表”小节。

| 级别 | 定义 | 对验收结论的影响 | 复验要求 | 风险接受 |
|---|---|---|---|---|
| S | 一票否决项、P0 truth / boundary / security / evidence integrity 破坏,或 P0 阻断证据失真。 | 未关闭时只能不通过或暂停修复后重验;不得通过或有条件通过。 | 修复后跑原 TC、same family、owning blocking suite、相关 redaction/dependency/report audit;必要时 P0 regression。 | 不允许。 |
| A | P0 主线或 blocking suite 风险,未命中 S/VETO,但影响核心闭环可信证明。 | 未关闭且未正式接受时不得通过;可导致有条件通过或暂停。 | 修复后跑原 TC、相关 suite、artifact/report pair 和受影响 audit。 | 严格条件候选,不得覆盖 S/VETO。 |
| B | P1/P2、selected-run、报告可读性、非阻断维护性或体验问题。 | 不阻断 P0;可进入有条件通过风险清单或 open issues。 | 视影响复跑 selected suite、补 report review 或抽样复验。 | 允许,但不得计入 P0 passed。 |
| R | 范围外、future、设计未闭口、capacity/SLA/dashboard/retention 等 residual。 | 不阻断当前 P0,但不得伪装成已验证。 | 后续升级为 P0/P1 时重新基线、回 owning Step 并重测。 | 允许,必须记录 owner、触发条件和后续动作。 |

| 放行条件 | 是否可放行 | 裁决口径 |
|---|---|---|
| 存在未关闭 S 级缺陷或任一 VETO 命中 | 否 | 只能不通过或暂停修复后重验。 |
| redaction/dependency/report audit failed | 否 | 属 hard gate failure,不得风险接受。 |
| P0 evidence index / artifact/report pair 不完整 | 否 | 验收不可裁决,不得用 handoff 或人工说明替代。 |
| 存在未关闭 A 级缺陷 | 通常否 | 仅当不触发 S/VETO、P0 truth 成立、证据完整且 Step 13 风险接受闭口时,才可作为有条件通过候选。 |
| 仅存在 B 级缺陷 | 可有条件通过 | 必须进入 risk acceptance 或 open issues,不得计入 P0 passed evidence。 |
| 仅存在 R 级 residual | 可有条件通过或通过 | 必须记录 owner、触发条件、后续动作和升级规则。 |

修复后必须复跑原 TC、same family、owning suite、相关 audit 和 report-generation audit;`release-main-smoke` 不得替代底层 suite。缺陷关闭证据必须能回指 defect ref、AC/TC/EV、失败 run、修复后 run、suite report、artifact/report pair、修复说明和复验结果方向。

## 13. 风险接受与遗留项

> 校准来源:
> - `design-calibration/06_acceptance_step_13_risk_acceptance.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“风险接受表”“不可风险接受项”“Risk acceptance 文件字段要求”“同步方向表”和“风险接受停审记录”小节。

| 风险 ID | 风险 / 遗留项 | 当前处理 |
|---|---|---|
| RISK-ML-001 | P1 real-like selected-run 不作为 P0 阻断。 | P0 已由 fake / controlled seam 证明;selected-run 不计入 P0 passed,后续可补验。 |
| RISK-ML-002 | durable storage / bus / external resolver 产品行为未覆盖。 | 当前 P0 只验 port / repository / seam 语义;产品基线确定后补 P1/P2 adapter and failure tests。 |
| RISK-ML-003 | production-like capacity / long-run 未覆盖。 | 当前无正式容量模型、负载模型和部署基线;进入 future / operations readiness。 |
| RISK-ML-004 | performance hard threshold 未定义。 | 当前只有 sample/trend,无硬阈值来源;后续基于 sample 建立 baseline。 |
| RISK-ML-005 | advanced package / marketplace / dashboard 未覆盖。 | 当前不属于 core P0 闭环前置;产品需求确定后回写设计、测试和验收范围。 |
| RISK-ML-006 | evidence retention period 未固定。 | 当前只要求验收和复验期间可追溯;后续进入运维标准或验收补充。 |
| RISK-ML-007 | B 级报告可读性或非阻断维护性问题。 | raw artifact、report pairing 和 P0 断言完整时进入 open issues 或 review backlog。 |
| RISK-ML-008 | 严格限制的 A 级缺陷候选。 | 不触发 VETO/S、不破坏 P0 truth、证据完整且逐项接受时,可作为有条件通过候选。 |

`reports/acceptance/risk-acceptance.md` 必须包含 `risk_id`、`scope`、`impact`、`acceptance_reason`、`evidence_refs`、`owner`、`acceptor`、`deadline_or_trigger`、`follow_up_action` 和 `follow_up_ref`。缺接受人、缺后续动作、缺截止条件或缺证据引用的风险不能作为有条件通过依据。

`VETO-ML-*`、S 级缺陷、redaction leak、dependency boundary failed、evidence integrity failure、source-missing stop 被私补、query/job/observability 反写真相和 P0 config silent fallback 不得风险接受。

## 14. 最终结论与签署

> 校准来源:
> - `design-calibration/06_acceptance_step_14_final_decision_signoff.md`
>
> 延伸阅读:
> - 建议继续阅读上述中间产物的“三值结论规则”“最终结论表”“结论判定矩阵”“签署角色表”“签署含义表”和“最终裁决审计表”小节。

最终结论只允许“通过”“有条件通过”“不通过”。缺 baseline、run_id、evidence index、artifact/report pair、veto checklist、risk acceptance 必填入口或 design closure 时,不得宣称通过或有条件通过。

| 结论 | 必须满足 | 允许动作 | 禁止 |
|---|---|---|---|
| 通过 | 全部 P0 门禁通过;VETO 未命中;S=0;A=0 或已修复;证据完整;无未接受 residual。 | 可进入下一阶段或发布准备。 | 不得隐含 P1/P2/future 能力已完成。 |
| 有条件通过 | P0 主线成立;VETO 未命中;S=0;证据完整;仅存在已接受 A/B/R residual,且 risk acceptance 字段完整。 | 可有条件进入下一阶段,必须跟踪条件和截止。 | 不得覆盖 VETO、S、P0 hard gate 或缺证据。 |
| 不通过 | 任一 P0 门禁失败;VETO 命中;S 未关闭;证据不可裁决;hard audit failed;P0 config silent fallback。 | 必须修复、复验并重新裁决。 | 不得用签署或风险接受改成有条件通过。 |

| 维度 | 结论取值 | 说明 |
|---|---|---|
| 功能验收 | 通过 / 有条件通过 / 不通过 | 由 §5、§7、§8 和 §12 共同决定。 |
| 数据边界与架构红线 | 通过 / 有条件通过 / 不通过 | 由 §6、dependency boundary 和 `VETO-ML-*` 决定。 |
| 非功能验收 | 通过 / 有条件通过 / 不通过 | 由 §9、config/redaction/dependency/report audit 和 residual 决定。 |
| 证据与可观测性 | 通过 / 有条件通过 / 不通过 | 由 §10 evidence index、artifact/report pair、no latest、no static evidence 和 observability not truth 决定。 |
| 缺陷与复验 | 通过 / 有条件通过 / 不通过 | 由 §12 S/A/B/R、复验和关闭证据决定。 |
| 风险接受 | 通过 / 有条件通过 / 不通过 | 由 §13 risk acceptance 完整性决定;缺 acceptor 不得有条件通过。 |
| 发布准备 | 通过 / 有条件通过 / 不通过 | 仅表示可进入发布准备,不替代正式发布或实施计划。 |
| 总体结论 | 通过 / 有条件通过 / 不通过 | 必须由上述维度收敛,且不得与任一 hard gate 冲突。 |
| 是否允许进入下一阶段 | 是 / 有条件 / 否 | “有条件”必须回指 `reports/acceptance/risk-acceptance.md`。 |

| 角色 | 姓名 / 责任 | 结论 | 日期 |
|---|---|---|---|
| 验收负责人 | `<name>`;确认最终结论、证据入口、VETO、缺陷、风险接受和签署表一致。 | `<signoff>` | `<date>` |
| 产品 / 业务负责人 | `<name>`;确认验收目标、P0/P1/P2 范围、业务 residual 和有条件通过影响。 | `<signoff>` | `<date>` |
| 架构负责人 | `<name>`;确认 truth ownership、Definition vs Use、依赖裁剪、架构红线和 design blocker 已闭口。 | `<signoff>` | `<date>` |
| 测试负责人 | `<name>`;确认 P0 suite、EV、report、缺陷、复验和 evidence integrity。 | `<signoff>` | `<date>` |
| 实施负责人 | `<name>`;确认送验 commit / build / config / implementation scope 与验收基线一致。 | `<signoff>` | `<date>` |
| 运维 / 安全 / 合规负责人 | `<name>`;确认 redaction、dependency、retention residual、handoff 和合规风险。 | `<signoff>` | `<date>` |

签署不自动代表风险接受;风险必须在 `reports/acceptance/risk-acceptance.md` 逐项记录。最终签署确认结论与 evidence / veto / risk / defect 状态一致,不替代 raw artifact、suite report、evidence index 或 implementation boundary。

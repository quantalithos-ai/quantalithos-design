## 4. 模块思考记录

### 4.1 模块 1:业务背景

问题回答:

- Quantalithos 不只需要执行流程,还需要表达“按什么方法做”和“使用哪类方法资产”。
- method-library 位于 L3 方法能力层,承接方法论、生命周期模型、角色 / 任务 / 工作产品定义、AI 方针和视图策略等上游主题。
- 当前重新讨论它,是为了让方法资产定义源先稳定,避免 process、identity、governance、UI 或 marketplace 各自定义局部方法语义。

诊断:

- 如果背景写成“需要 CRUD 方法资产”,会把问题降格为功能缺失。
- 如果背景列出全部 MethodContent 子类,会提前进入目标、功能或数据归属。
- 如果背景写发布事件、同步方式或查询方式,会提前进入接口方案。

取舍:

- 背景用“平台需要统一方法资产定义源”表达。
- 方法资产类型只作为上游语义背景出现,不在 Step 3 裁定 P0 覆盖范围。

### 4.2 模块 2:现状与问题

问题回答:

- 主要问题一: 方法资产定义源不统一时,Definition vs Use 分离会失效。
- 主要问题二: 方法定义和运行时使用容易混写,相邻仓会反向污染方法资产需求。
- 主要问题三: 方法资产版本和分发语义缺少统一背景时,下游难以稳定消费和审计。

诊断:

- 当前无法给真实数量指标,因为这是需求重启讨论,不能继承旧稿伪量化。
- 可判断表现是上游材料已经说明多个仓会引用 method-library 语义;如果缺少统一定义源,这些引用会退化为 hardcode、文档约定或私有模型。

取舍:

- 问题表只列 3 个核心问题。
- 不写“通过发布事件解决”“提供查询接口”“实现 MethodContent CRUD”等方案句。

### 4.3 模块 3:业务问题 vs 技术问题

问题回答:

- 业务问题是平台无法把方法论、生命周期模型、角色视角、AI 方针和视图策略变成可治理、可复用、可分发的资产语义。
- 技术问题是需求和后续设计无法稳定区分定义源、运行时使用、成员身份、治理执行、外部能力和交易体验。

诊断:

- 业务问题不是缺少管理页面,而是缺少一致工作方式的定义基础。
- 技术问题不是缺少数据库表,而是缺少稳定真相源会导致对象、协议、状态和测试出现多定义。

取舍:

- 分类只说明影响。
- 目标和非目标放到 Step 4。

## 6. 结构化中间产物

### 6.1 业务背景结论

Quantalithos 不只是执行任务和流程的平台,还需要在业务真相域、运行层和体验层之间稳定表达“按什么方法做”。当前架构把 method-library 放在 L3 方法能力层,用于承接 SPEM Method Content、生命周期模型、裁剪 / 分发语义、AI 方针和视图策略等方法资产主题。本轮讨论 method-library,是为了先把方法资产定义源的需求背景收束清楚,避免后续消费仓各自定义局部方法语义。

### 6.2 现状与问题结论

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 方法资产定义源不统一 | 上游材料显示 process、identity、governance、UI/console 等相邻仓都会引用或消费方法资产语义;如果本仓边界不成立,这些语义会散落在消费仓。 | Definition vs Use 分离失效,消费仓容易各自 hardcode 方法定义,后续需求和设计会出现多真相源。 |
| 方法定义与运行时使用容易混写 | ProcessTemplate、RoleDefinition、AIPolicy、ViewProfile 等主题天然连接运行、身份、治理和体验,但这些仓只应消费或执行,不应拥有定义正文。 | 过程执行、成员状态、治理裁决和 UI 渲染会反向污染方法资产需求,导致边界、规则和数据归属难以收敛。 |
| 方法资产版本和分发语义缺少统一背景 | 路线图要求 N3 产出“怎么做”和“用什么”两套资产,但若没有统一的定义与发布语义,下游难以判断所消费资产的稳定性和可追溯性。 | 下游能力只能依赖文档约定或本地快照,跨仓协作、审计和验收都会缺少一致锚点。 |

### 6.3 问题分类结论

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台需要把方法论、生命周期模型、角色视角、AI 方针和视图策略变成可治理、可复用、可分发的资产语义;如果缺少统一定义源,产品层无法稳定表达“按什么方法做”。 |
| 技术问题 | 如果方法资产定义不独立,后续需求、架构、详细设计和实现会在定义源、运行时使用、成员身份、治理执行、外部能力和交易体验之间反复串线,产生多真相源和不可落码边界。 |

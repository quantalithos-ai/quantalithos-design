## 2. 整体模块骨架

Step 4 拆为三个模块:

| 模块 | 输出 | 不输出 |
|---|---|---|
| 目标 | 本轮需求完成后应成立的状态、边界或能力范围。 | 不写功能名、接口名、事件名或实现路径。 |
| 非目标 | 虽然相关但不纳入本仓当前需求范围的事项。 | 不写空泛“不做所有扩展”。 |
| 范围收束 | 当前目标与非目标如何约束后续 Step。 | 不写核心能力闭环步骤或数据归属矩阵。 |

## 3. 模块思考记录

### 3.1 目标

问题回答:

- 目标必须回应 Step 3 的问题:方法资产定义源不统一、定义与使用混写、版本/分发语义缺少统一背景。
- 当前目标应先钉住“定义真相边界”和“方法资产范围”,再为后续核心能力闭环、功能需求和验收提供结构锚点。
- N3 路线图中提到 CRUD、8 种模板、9 种 Role,但 Step 4 不应直接把这些实现或功能项写成目标。

诊断:

- 旧稿 G-1 到 G-8 多数是功能或测试验收句,不适合作为本轮 Step 4 目标原文继承。
- 如果目标写成“支持 PublishContent / ResolveViewProfile / 事件同步”,会越过当前 Step,进入功能或接口设计。
- 如果目标只写“提升一致性”,又不可验证。

取舍:

- 目标写成可验证的需求状态:定义真相边界成立、Definition vs Use 分离成立、方法资产当前范围可收束、版本/发布/分发语义可被后续章节承接、相邻仓消费不反向拥有定义。
- 验证方式用后续章节检查口径表达,不写具体测试动作。

### 3.2 非目标

问题回答:

- 非目标必须把相邻仓职责排出去,尤其是 process 执行、identity 成员状态、governance 裁决、capability-hub 外部能力注册、marketplace 交易、UI 渲染和 artifact 正文。
- 非目标不是说这些主题不重要,而是说明本仓只提供方法资产定义源或边界语义,不接管相邻仓运行职责。

诊断:

- 旧稿的非目标方向大体可保留,但包含旧对象名和旧消费关系,需要按本轮边界重写。
- 部分旧非目标如 QualificationProfile、QualificationBinding 与当前本轮是否纳入 P0 仍未裁定,应避免在 Step 4 强行细化到具体对象。

取舍:

- 非目标按职责归属写,不按旧对象模型写。
- 对 marketplace、ViewProfile、AIPolicy 这类可能有边界争议的主题,写成“不做交易/渲染/执行”,而不是排除其定义主题。

### 3.3 范围收束

问题回答:

- Step 4 之后,后续章节必须围绕“方法资产定义源”展开,而不是围绕相邻仓执行流程展开。
- 目标支撑 Step 7 核心能力闭环,但不在本 Step 画闭环。
- 非目标将作为 Step 6 依赖、Step 10 规则边界、Step 11 数据归属、Step 14 验收的一票否决输入。

诊断:

- 如果此处不明确范围收束,后续用户角色和依赖章节容易重新把 process、identity、governance 的运行职责拉回本仓。

取舍:

- 范围收束只写后续承接原则。
- 不写角色、故事、功能、数据或接口细节。

## 5. 结构化中间产物

### 5.1 目标表

| 目标 | 说明 | 验证方式 |
|---|---|---|
| 建立方法资产定义真相边界 | 明确本仓承载方法资产定义、版本发布与分发语义,相邻仓只按边界引用、消费或执行。 | 后续章节不把流程实例、成员状态、治理裁决、外部能力注册、交易流程或 UI 渲染写成本仓真相。 |
| 收束 Definition vs Use 分离 | 明确本仓讨论“定义”,不讨论相邻仓的运行时“使用”状态。 | Step 6/10/11 中所有相邻仓关系都能保持定义源与使用方分离。 |
| 收束当前方法资产主题范围 | 明确本轮需求围绕 SPEM Method Content、生命周期模型、AI 方针、视图策略和方法资产分发语义展开,不从旧对象模型反推范围。 | Step 7/9/11 的能力、功能和数据项均能回指当前方法资产主题,无法回指的项进入待确认或排除。 |
| 支撑方法资产版本与发布语义 | 为后续讨论版本稳定性、发布后不可随意修改、可追溯分发和下游消费建立目标边界。 | Step 10/11/14 能分别承接版本/发布规则、数据归属和验收口径,且不需要由消费仓补定义。 |
| 明确相邻仓职责不反向侵入 | 将 process、identity、governance、capability-hub、marketplace、UI/console 等职责排出本仓目标范围。 | 后续功能、接口、数据和验收中若出现相邻仓运行职责,必须被标为外部依赖、边界背景、外围增强或非目标。 |

### 5.2 非目标表

| 非目标 | 不做原因 |
|---|---|
| 流程执行、ProcessInstance 状态和运行时编排 | 属于 `L1-process` / L2 runtime 的运行职责;本仓只收束方法资产定义。 |
| 成员身份、成员生命周期、成员具备哪些角色或资格的状态 | 属于 `L1-identity` 或相关成员仓;本仓不拥有成员状态真相。 |
| Gate 决策、治理裁决、策略 enforce 和运行时合规执行 | 属于 `L1-governance` / runtime;本仓只讨论方法资产中的定义性方针或被引用语义。 |
| MCP/A2A/provider/tool 外部能力注册、绑定和访问裁决 | 属于 `L3-capability-hub` 及治理协作边界;本仓不管理外部能力接入。 |
| marketplace 定价、购买、结算、订单和商业分发流程 | 属于 `L6-marketplace`;本仓最多作为方法资产定义源或包来源被后续讨论。 |
| UI 页面渲染、字段过滤执行和前端交互体验 | 属于 `L5-chat`、`L5-console`、mobile 或其他体验仓;本仓只收束视图策略作为方法资产的定义边界。 |
| Artifact 正文、外部文件、证据正文和制品生命周期状态 | 属于 `L1-artifact` / archive 等相邻仓;本仓不保存或管理外部正文生命周期。 |
| 认证登录、权限系统和操作主体鉴权实现 | 属于身份、治理或平台安全边界;本仓需求只讨论方法资产的仓级职责。 |

### 5.3 范围收束结论

本轮 `L3-method-library` 需求的目标,不是把所有与方法论相关的系统行为都放进本仓,而是把方法资产定义源、版本发布语义、分发语义和相邻仓消费边界先收束清楚。后续用户、依赖、核心能力、功能、规则、数据、接口和验收都必须围绕这些目标展开;凡是落到运行时执行、成员状态、治理裁决、外部能力注册、交易流程、UI 执行或外部正文管理的内容,都不能作为本仓目标进入当前主线。

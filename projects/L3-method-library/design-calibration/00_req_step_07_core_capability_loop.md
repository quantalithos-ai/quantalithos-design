## 4. 模块思考记录

### 4.1 模块 1:仓存在必要性

问题回答:

- 没有本仓,平台缺少的不是若干 CRUD,而是可被长期引用的方法资产定义源。
- 本仓成立必须让方法资产能被定义和识别、能稳定正式化、能被下游按边界消费、能在变化时追溯并保护消费一致性。
- 只有定义无正式化,下游无法判断可用性;只有正式化无消费,定义不能支撑平台运行;只有消费无追溯,变化会破坏下游一致性。

诊断:

- 旧 P0 闭环把草稿、Gate、fingerprint、事件、下游同步串成流程,这些是后续功能 / 规则 / 接口线索,不是能力图。
- Step 7 必须把这些流程词抽象成能力成立关系。

取舍:

- 使用四个核心能力节点。
- 不把 MethodPlugin、marketplace、ViewProfile 高频匹配等外围能力放进核心图。

### 4.2 模块 2:核心能力节点

问题回答:

- 能力 1: 方法资产能够被统一定义和识别。
- 能力 2: 方法资产能够以稳定版本进入正式使用语境。
- 能力 3: 正式方法资产能够被下游按边界消费。
- 能力 4: 方法资产变化能够被追溯并保护消费一致性。

诊断:

- 草稿维护、发布审批、事件同步、缓存失效都是后续功能或接口候选。
- 资产类型清单不应进入闭环图,否则图会变成对象列表。

取舍:

- 图中不出现仓名、角色、事件名、接口名、对象字段。
- 图后明确箭头不是运行时顺序。

### 4.3 模块 3:能力层级

问题回答:

- 核心闭环围绕定义、正式化、消费、追溯。
- 外围增强包括资产包/配置、生态分发、高级 ViewProfile 匹配、AIPolicy override、合规/成熟度材料。
- 边界外能力继承 Step 4 非目标。

诊断:

- 外围增强未来重要,但若进入核心闭环会使当前需求边界失控。
- 边界外能力必须显式列出,避免后续膨胀。

取舍:

- MethodPlugin / MethodConfiguration 当前列为外围增强。
- ViewProfile 定义主题可回指核心能力,高级匹配和体验优化列为外围增强。

### 4.4 模块 4:停审清单

问题回答:

- 后续 Step 8~14 必须按能力节点展开,每个节点停审时都要证明故事、功能、规则、数据、接口和验收可回指该节点。
- 消费语义不能早于定义和正式化;追溯一致性必须覆盖已消费的正式资产变化。

诊断:

- 如果后续一次性生成全仓故事和功能,会丢掉能力结构,形成孤儿功能和孤儿验收。

取舍:

- 本 Step 只给停审清单,不填故事、功能和验收。

## 6. 结构化中间产物

### 6.1 闭环定义

`L3-method-library` 的核心能力闭环不是方法资产的功能清单,而是:方法资产必须能够被统一定义和识别,能够以稳定版本进入正式使用语境,能够被下游按边界消费,并且在变化后仍能被追溯和保护消费一致性。只要这些能力不能共同成立,本仓就会退化为静态文档库或下游私有模型集合,无法承担方法资产定义真相源。

### 6.2 核心能力闭环图

```text
方法资产能够被统一定义和识别
  -> 方法资产能够以稳定版本进入正式使用语境
  -> 正式方法资产能够被下游按边界消费
  -> 方法资产变化能够被追溯并保护消费一致性
```

本图只表达能力成立的逻辑依赖关系,不是运行时调用顺序、接口时序、事件传播顺序、开发顺序或实施计划。

### 6.3 核心能力节点讨论顺序

| 顺序 | 能力节点 | 为什么在此顺序讨论 |
|---:|---|---|
| 1 | 方法资产能够被统一定义和识别 | 没有统一定义和识别,版本发布、消费和追溯都没有稳定对象。 |
| 2 | 方法资产能够以稳定版本进入正式使用语境 | 没有稳定正式化语义,下游消费无法判断哪些定义可用。 |
| 3 | 正式方法资产能够被下游按边界消费 | 没有受控消费,本仓无法支撑主链下游关系。 |
| 4 | 方法资产变化能够被追溯并保护消费一致性 | 没有追溯和一致性保护,发布后的变化会破坏下游引用稳定性。 |

### 6.4 能力层级划分表

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | 方法资产统一定义与识别;稳定版本进入正式使用语境;下游按边界消费;变化可追溯并保护消费一致性。 |
| 外围增强能力 | MethodPlugin / MethodConfiguration 资产包与组织级方法集;29110 Deployment Package 导出;marketplace 生态分发;高级 ViewProfile 匹配与体验优化;AIPolicy override 深化;更丰富的合规/成熟度材料。 |
| 边界外能力 | 流程执行;成员生命周期和成员状态;治理裁决和 policy enforce;外部工具/MCP/A2A/provider 注册;marketplace 交易/结算/订单;UI 渲染执行;Artifact 正文和外部文件生命周期;认证登录和权限系统实现。 |

### 6.5 能力节点停审清单

| 能力节点 | 后续展开前必须证明 |
|---|---|
| 方法资产能够被统一定义和识别 | 故事、功能、规则、数据和接口候选都能回指“方法资产定义源”,且不把运行时实例、成员状态、治理执行或交易体验写成本仓真相。 |
| 方法资产能够以稳定版本进入正式使用语境 | 后续规则和数据必须能承接版本稳定、发布后不可随意修改、正式化前后语义区分,且不提前写治理裁决实现。 |
| 正式方法资产能够被下游按边界消费 | 后续依赖和接口必须保持 Definition vs Use 分离,不把运行期消费关系写成源码依赖或定义真相迁移。 |
| 方法资产变化能够被追溯并保护消费一致性 | 后续规则、数据、接口和验收必须能说明变化如何被识别、追溯和用于保护下游引用稳定性,但不得在需求层写事件 schema 或具体实现机制。 |

### 6.6 功能回填映射结论

后续功能需求必须先归入上述四个能力节点。无法归入这些节点的功能候选,应先进入外围增强能力或待确认事项;若功能候选落入 Step 4 非目标或 Step 7 边界外能力,不得进入当前主线。

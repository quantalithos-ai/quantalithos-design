## 3. 模块思考记录

### 3.1 仓存在必要性

问题回答:

- 如果没有本仓,平台缺少的不是若干 CRUD,而是一个可被长期引用的方法资产定义源。
- 本仓成立必须让方法资产能被定义、被稳定发布、被下游消费、并能在变化时保持可追溯和不漂移。
- 这几个能力缺一不可:只有定义无发布,下游不能稳定消费;只有发布无消费,定义无法支撑平台运行;只有消费无追溯,变更会破坏下游一致性。

诊断:

- 旧 P0 闭环把草稿、Gate、fingerprint、事件、下游同步串成流程,方向有价值,但已混入角色、治理和事件时序。
- Step 7 需要抽象成“能力成立关系”,而不是沿用旧流程步骤。

取舍:

- 使用 4 个核心能力节点:方法资产定义范围成立、方法资产版本发布成立、方法资产消费语义成立、方法资产变更可追溯成立。
- 不把具体 MethodContent 子类、Gate、事件、接口或下游仓名写进图。

### 3.2 核心能力节点

问题回答:

- 能力 1: 方法资产能够被统一定义和识别。
- 能力 2: 方法资产能够以稳定版本进入正式使用语境。
- 能力 3: 已正式化的方法资产能够被下游按边界消费。
- 能力 4: 方法资产变化能够被追溯并保护消费一致性。

诊断:

- “草稿维护”“发布审批”“事件同步”“缓存失效”都是后续功能或接口候选,不是能力节点。
- “marketplace 分发”“MethodPlugin/Configuration”“ViewProfile 高频匹配”重要,但它们可能是外围增强或具体功能,不应直接进入核心图。

取舍:

- 图中不出现仓名、角色、事件名、接口名、对象字段。
- 图后说明箭头只表示能力成立的逻辑依赖关系。

### 3.3 能力层级划分

问题回答:

- 核心能力闭环应围绕定义、正式化、消费、追溯四件事。
- 外围增强包括资产包/配置、marketplace 生态分发、更多组织级裁剪、复杂视图策略、高级合规材料等。
- 边界外能力包括流程执行、成员生命周期、治理裁决、外部能力注册、交易结算、UI 渲染、外部正文管理。

诊断:

- 外围增强可能在未来很重要,但如果现在进入核心闭环,会使 P0 边界失控。
- 边界外能力已经在 Step 4 非目标中钉住,必须在能力层级表再次显式列出,防止后续膨胀。

取舍:

- 能力层级表用短语聚合,不展开为功能项。
- 将 MethodPlugin/MethodConfiguration、29110 package/export、marketplace、ViewProfile高级匹配等放入外围增强候选。

### 3.4 能力节点停审清单

问题回答:

- 后续 Step 8~14 需要按能力节点展开,每个节点停审时都要证明故事、功能、规则、数据、接口和验收可回指该节点。
- 节点之间存在逻辑依赖:消费语义不能早于定义和正式化;追溯一致性必须覆盖已消费的正式资产变化。

诊断:

- 如果后续一次性写所有用户故事和功能,会重新回到旧稿的全仓故事清单,丢掉能力结构。

取舍:

- 本 Step 只给停审清单,不填用户故事、功能和验收。

## 5. 结构化中间产物

### 5.1 闭环定义

`L3-method-library` 的核心能力闭环,不是方法资产的功能清单,而是:方法资产必须能够被统一定义和识别,能够以稳定版本进入正式使用语境,能够被下游按边界消费,并且在变化后仍能被追溯和保护消费一致性。只要这些能力不能共同成立,本仓就会退化为静态文档库或下游私有模型集合,无法承担方法资产定义真相源。

### 5.2 核心能力闭环图

```text
方法资产能够被统一定义和识别
  -> 方法资产能够以稳定版本进入正式使用语境
  -> 正式方法资产能够被下游按边界消费
  -> 方法资产变化能够被追溯并保护消费一致性
```

本图只表达能力成立的逻辑依赖关系,不是运行时调用顺序、接口时序、事件传播顺序、开发顺序或实施计划。

### 5.3 核心能力节点执行顺序

| 顺序 | 能力节点 | 为什么在此顺序讨论 |
|---:|---|---|
| 1 | 方法资产能够被统一定义和识别 | 没有统一定义和识别,版本发布、消费和追溯都没有稳定对象。 |
| 2 | 方法资产能够以稳定版本进入正式使用语境 | 没有稳定正式化语义,下游消费无法判断哪些定义可用。 |
| 3 | 正式方法资产能够被下游按边界消费 | 没有受控消费,本仓无法支撑 process、identity、runtime、member-images 等主链关系。 |
| 4 | 方法资产变化能够被追溯并保护消费一致性 | 没有追溯和一致性保护,发布后的变化会破坏下游引用稳定性。 |

### 5.4 能力层级划分表

| 分类 | 内容 |
|---|---|
| 核心能力闭环 | 方法资产统一定义与识别;稳定版本进入正式使用语境;下游按边界消费;变化可追溯并保护消费一致性。 |
| 外围增强能力 | MethodPlugin / MethodConfiguration 资产包与组织级方法集;29110 Deployment Package 导出;marketplace 生态分发;高级 ViewProfile 匹配与体验优化;AIPolicy override 深化;更丰富的合规/成熟度材料。 |
| 边界外能力 | 流程执行;成员生命周期和成员状态;治理裁决和 policy enforce;外部工具/MCP/A2A/provider 注册;marketplace 交易/结算/订单;UI 渲染执行;Artifact 正文和外部文件生命周期;认证登录和权限系统实现。 |

### 5.5 能力节点停审清单

| 能力节点 | 后续展开前必须证明 |
|---|---|
| 方法资产能够被统一定义和识别 | 用户故事、功能、规则、数据和接口候选都能回指“方法资产定义源”,且不把运行时实例、成员状态、治理执行或交易体验写成本仓真相。 |
| 方法资产能够以稳定版本进入正式使用语境 | 后续规则和数据必须能承接版本稳定、发布后不可随意修改、正式化前后语义区分,且不提前写治理裁决实现。 |
| 正式方法资产能够被下游按边界消费 | 后续依赖和接口必须保持 Definition vs Use 分离,不把运行期消费关系写成源码依赖或定义真相迁移。 |
| 方法资产变化能够被追溯并保护消费一致性 | 后续规则、数据、接口和验收必须能说明变化如何被识别、追溯和用于保护下游引用稳定性,但不得在需求层写事件 schema 或具体实现机制。 |

### 5.6 功能回填映射结论

后续功能需求必须先归入上述四个能力节点。无法归入这些节点的功能候选,应先进入外围增强能力或待确认事项;若功能候选落入 Step 4 非目标或 Step 7 边界外能力,不得进入当前主线。

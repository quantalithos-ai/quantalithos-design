## 3. 模块思考记录

### 3.1 性能要求

问题回答:

- 方法资产定义读取、目录识别和正式消费支撑在下游主链中可能被频繁使用,不能成为主链阻塞点。
- 正式化和版本变化是强一致、可追溯动作,不应为了低延迟牺牲语义完整性。

诊断:

- 旧稿给出多个 P95 目标,但这些目标依赖接口、缓存和存储方案,当前需求重启阶段不能继承。

取舍:

- 写成判断口径:不会成为主链瓶颈;正式化优先保证一致性和追溯,不承诺具体毫秒值。

### 3.2 可用性要求

问题回答:

- 核心闭环必须能与外围增强隔离。
- 外部治理、marketplace、console、artifact 等候选/外围关系失效时,不能让方法资产定义真相本身失效。
- 下游不可用不应导致本仓定义真相被改写或丢失。

诊断:

- 旧稿写了 PG、object storage、cache、bus 的降级策略,这些是设计层。

取舍:

- 只写需求层可用性边界:核心闭环、外围增强、候选依赖、下游消费恢复。

### 3.3 安全要求

问题回答:

- 本仓的安全重点不是认证系统,而是不能越权拥有相邻仓职责、正文或运行真相。
- 对外能力必须保持 Definition vs Use,避免消费仓绕过本仓改写定义。

诊断:

- 旧材料中的 actor_ref、gate_ref、表达式语言、签名、加密等属于后续设计或安全方案。

取舍:

- 安全 NFR 只写越界持有、正文保存和边界绕过风险。

### 3.4 审计 / 可追溯要求

问题回答:

- 正式化、版本语义变化、消费影响变化必须可追溯。
- 正式消费需要能回到定义来源和版本语境。

诊断:

- 旧稿中的 audit_log_ref、trace_id、fingerprint、gate、outbox 是实现或详细设计材料。

取舍:

- 用需求层追溯句表达,不规定记录字段。

### 3.5 幂等 / 一致性要求

问题回答:

- 方法资产定义真相必须单一,正式版本语义不得歧义。
- 重复消费、重复感知或后台维护不能制造第二定义真相。
- 下游消费边界必须保持一致:消费方可以有引用/快照/索引,不能拥有正文真相。

诊断:

- 旧稿中的 idempotency key、content_id+version+fingerprint、事务原子性等都属于后续设计。

取舍:

- 写成语义一致性和需求层幂等要求,不写机制。

### 3.6 可观测性要求

问题回答:

- 平台需要观察方法资产是否已正式化、是否发生影响消费的变化、是否存在下游消费不一致风险。
- 观察要求不能把 observability 仓变成方法资产真相存储。

诊断:

- 旧稿中具体指标名可作为后续设计线索,当前不继承。

取舍:

- 写“状态、变化、异常可观察”的需求口径,不写指标名。

## 4. 结构化中间产物

### 4.1 非功能需求表

| 编号 | 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|---|
| NFR-ML-001 | 性能 | 方法资产目录识别、正式定义读取和下游受控消费不应成为当前主链能力的阻塞点。 | 后续验收至少应证明核心查询 / 消费路径不会阻塞 process、identity、runtime、member-images 的主链消费。 |
| NFR-ML-002 | 性能 | 方法资产正式化和版本语义变化优先保证一致性、追溯和边界正确性,不得为追求低延迟牺牲定义真相完整性。 | 验收时若性能与一致性冲突,以定义真相、版本语义和追溯完整为优先判断。 |
| NFR-ML-003 | 可用性 | 外围增强能力失效时,核心方法资产定义、正式化、受控消费和追溯能力仍应成立。 | MethodPlugin、MethodConfiguration、marketplace、console 等外围能力不可用时,核心闭环不应整体不可用。 |
| NFR-ML-004 | 可用性 | 条件型外部治理或候选下游依赖不可用时,本仓不得丢失或改写已成立的方法资产定义真相。 | 外部治理、artifact、marketplace、console 等候选关系不可用时,已存在定义真相和正式版本语义仍可被判断。 |
| NFR-ML-005 | 安全 | 本仓不得越权拥有流程运行、成员状态、治理执行、外部能力注册、交易履约、UI 渲染或 artifact/archive 正文。 | 数据归属和接口边界中应持续排除这些正文或运行真相。 |
| NFR-ML-006 | 安全 | 下游消费能力不得绕过本仓定义真相边界创建或修改方法资产定义。 | 验收应能判断下游只能按引用、快照、索引或正式消费边界使用方法资产语义。 |
| NFR-ML-007 | 审计 / 可追溯 | 方法资产正式化、版本语义变化和影响既有消费的变化必须可追溯。 | 后续验收应能追溯这些变化的定义来源、变化语境和影响范围。 |
| NFR-ML-008 | 审计 / 可追溯 | 正式消费应能回溯到被消费的方法资产定义来源和版本语境。 | 下游正式消费不应只留下不可解释的本地约定。 |
| NFR-ML-009 | 幂等 / 一致性 | 方法资产定义真相在平台范围内应保持单一正式语义。 | 同一方法资产定义不得同时由本仓和消费仓各自形成互相冲突的正式真相。 |
| NFR-ML-010 | 幂等 / 一致性 | 重复读取、重复变化感知或后台维护不得改变方法资产定义正文或制造重复正式语义。 | 重复执行同类消费或维护动作时,应能判断其没有产生第二定义真相。 |
| NFR-ML-011 | 幂等 / 一致性 | 正式版本语义变化必须保持显式、可区分,不得静默覆盖既有正式引用含义。 | 任何影响正式版本语义的变化都应能被识别为显式变化。 |
| NFR-ML-012 | 可观测性 | 方法资产正式化状态、版本语义变化、消费影响变化和边界异常应能被平台稳定观察。 | 后续验收应能判断这些状态或异常是否发生,但不要求本 Step 定义具体指标名。 |
| NFR-ML-013 | 可观测性 | 可观测材料不得成为方法资产定义真相的替代存储。 | observability、audit material 或 telemetry 只能支持观察和追溯,不能替代本仓定义真相。 |

| 幂等 / 一致性 | 方法资产定义真相在平台范围内应保持单一正式语义。 | 同一方法资产定义不得同时由本仓和消费仓各自形成互相冲突的正式真相。 |
| 幂等 / 一致性 | 重复读取、重复变化感知或后台维护不得改变方法资产定义正文或制造重复正式语义。 | 重复执行同类消费或维护动作时,应能判断其没有产生第二定义真相。 |
| 幂等 / 一致性 | 正式版本语义变化必须保持显式、可区分,不得静默覆盖既有正式引用含义。 | 任何影响正式版本语义的变化都应能被识别为显式变化。 |
| 可观测性 | 方法资产正式化状态、版本语义变化、消费影响变化和边界异常应能被平台稳定观察。 | 后续验收应能判断这些状态或异常是否发生,但不要求本 Step 定义具体指标名。 |
| 可观测性 | 可观测材料不得成为方法资产定义真相的替代存储。 | observability、audit material 或 telemetry 只能支持观察和追溯,不能替代本仓定义真相。 |

## 4. 模块思考记录

### 4.1 性能要求

问题回答:

- 方法资产目录识别、正式定义读取、受控消费和证据线索查看会被下游主链使用,不应成为主链阻塞点。
- 正式化和版本语义变化优先保证一致性、追溯和边界正确性。

诊断:

- 旧 P95、缓存命中率、PG/Redis 等指标依赖架构和实现,当前不能继承。

取舍:

- 使用判断口径表达“不得成为主链瓶颈”和“一致性优先”。

### 4.2 可用性要求

问题回答:

- 核心闭环必须与外围增强隔离。
- 外部治理、marketplace、console、artifact 等候选/外围关系不可用时,本仓不得丢失或改写已成立的定义真相。
- 下游不可用不应导致本仓定义真相丢失或被反向改写。

诊断:

- 旧降级策略和存储不可用处理是架构/详细设计问题。

取舍:

- 只写核心闭环、外围增强、条件型依赖和下游失效的需求层可用性边界。

### 4.3 安全要求

问题回答:

- 本仓安全重点是守住定义真相和正文边界,不是实现认证系统。
- 下游消费不得绕过本仓定义真相边界创建或修改方法资产定义。

诊断:

- actor、gate、签名、表达式沙箱、加密等是后续设计或 ADR。

取舍:

- 安全要求聚焦越权持有、正文保存、鉴权实现排除和下游绕过风险。

### 4.4 审计 / 可追溯要求

问题回答:

- 方法资产正式化、版本语义变化、消费影响变化必须可追溯。
- 正式消费应能回到定义来源和版本语境。
- 证据线索必须能承接验收或审计语境。

诊断:

- audit_log_ref、trace_id、fingerprint、outbox 等是实现机制。

取舍:

- 写需求层追溯句,不规定记录字段和存储方式。

### 4.5 幂等 / 一致性要求

问题回答:

- 方法资产定义真相必须保持单一正式语义。
- 重复读取、重复变化感知、重复证据线索查看或后台维护不得产生第二定义真相。
- 正式版本语义变化必须显式、可区分。

诊断:

- 幂等 key、事务原子性、hash 算法属于详细设计。

取舍:

- 写语义一致性和需求层幂等要求。

### 4.6 可观测性要求

问题回答:

- 平台需要观察方法资产是否正式化、是否发生版本语义变化、是否影响下游消费、是否出现边界违规风险。
- 可观测材料不能替代方法资产定义真相。

诊断:

- 指标名、告警规则、仪表盘和采样策略属于观测设计。

取舍:

- 写“状态、变化、异常可观察”和“观测材料不替代真相”。

| NFR-ML-003 | 性能 | 方法资产正式化和版本语义变化优先保证一致性、追溯和边界正确性,不得为追求低延迟牺牲定义真相完整性。 | 验收时若性能与一致性冲突,以定义真相、版本语义和追溯完整为优先判断。 |
| NFR-ML-004 | 可用性 | 外围增强能力失效时,核心方法资产定义、正式化、受控消费和追溯能力仍应成立。 | MethodPlugin、MethodConfiguration、marketplace、console、标准映射材料等外围能力不可用时,核心闭环不应整体不可用。 |

| NFR-ML-006 | 可用性 | 下游消费方不可用或回报延迟时,本仓不得把下游运行状态当作自身定义真相。 | 下游不可用只能影响消费影响摘要或协作判断,不能改变本仓定义真相归属。 |

| NFR-ML-009 | 审计 / 可追溯 | 方法资产正式化、版本语义变化和影响既有消费的变化必须可追溯。 | 后续验收应能追溯这些变化的定义来源、变化语境和影响范围。 |
| NFR-ML-010 | 审计 / 可追溯 | 正式消费应能回溯到被消费的方法资产定义来源和版本语境。 | 下游正式消费不应只留下不可解释的本地约定。 |

| NFR-ML-013 | 幂等 / 一致性 | 重复读取、重复变化感知、重复证据线索查看或后台维护不得改变方法资产定义正文或制造重复正式语义。 | 重复执行同类消费或维护动作时,应能判断其没有产生第二定义真相。 |
| NFR-ML-014 | 幂等 / 一致性 | 正式版本语义变化必须保持显式、可区分,不得静默覆盖既有正式引用含义。 | 任何影响正式版本语义的变化都应能被识别为显式变化。 |

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|
| 性能 | 方法资产目录识别、正式定义读取和下游受控消费不应成为当前主链能力的阻塞点。 | 后续验收至少应证明核心查询 / 消费路径不会阻塞 process、identity、runtime、member-images 的主链消费。 |
| 性能 | 方法资产证据线索查看和追溯查看不应阻塞正式化、受控消费或一致性维护的主链判断。 | 后续验收应能判断证据线索和追溯能力不会反向拖垮核心闭环。 |
| 性能 | 方法资产正式化和版本语义变化优先保证一致性、追溯和边界正确性,不得为追求低延迟牺牲定义真相完整性。 | 验收时若性能与一致性冲突,以定义真相、版本语义和追溯完整为优先判断。 |
| 可用性 | 外围增强能力失效时,核心方法资产定义、正式化、受控消费和追溯能力仍应成立。 | MethodPlugin、MethodConfiguration、marketplace、console、标准映射材料等外围能力不可用时,核心闭环不应整体不可用。 |
| 可用性 | 条件型外部治理或候选下游依赖不可用时,本仓不得丢失或改写已成立的方法资产定义真相。 | 外部治理、artifact、marketplace、console 等候选关系不可用时,已存在定义真相和正式版本语义仍可被判断。 |
| 可用性 | 下游消费方不可用或回报延迟时,本仓不得把下游运行状态当作自身定义真相。 | 下游不可用只能影响消费影响摘要或协作判断,不能改变本仓定义真相归属。 |
| 安全 | 本仓不得越权拥有流程运行、成员状态、治理执行、外部能力注册、交易履约、UI 渲染、artifact/archive 正文或鉴权实现正文。 | 数据归属和接口边界中应持续排除这些正文或运行真相。 |
| 安全 | 下游消费能力不得绕过本仓定义真相边界创建或修改方法资产定义。 | 验收应能判断下游只能按引用、快照、索引或正式消费边界使用方法资产语义。 |
| 审计 / 可追溯 | 方法资产正式化、版本语义变化和影响既有消费的变化必须可追溯。 | 后续验收应能追溯这些变化的定义来源、变化语境和影响范围。 |
| 审计 / 可追溯 | 正式消费应能回溯到被消费的方法资产定义来源和版本语境。 | 下游正式消费不应只留下不可解释的本地约定。 |
| 审计 / 可追溯 | 方法资产版本、发布和引用相关证据线索必须能承接正式验收或审计语境。 | 证据线索应能说明其来源、关联的方法资产语境和用途,但本 Step 不定义证据 schema。 |
| 幂等 / 一致性 | 方法资产定义真相在平台范围内应保持单一正式语义。 | 同一方法资产定义不得同时由本仓和消费仓各自形成互相冲突的正式真相。 |
| 幂等 / 一致性 | 重复读取、重复变化感知、重复证据线索查看或后台维护不得改变方法资产定义正文或制造重复正式语义。 | 重复执行同类消费或维护动作时,应能判断其没有产生第二定义真相。 |
| 幂等 / 一致性 | 正式版本语义变化必须保持显式、可区分,不得静默覆盖既有正式引用含义。 | 任何影响正式版本语义的变化都应能被识别为显式变化。 |
| 可观测性 | 方法资产正式化状态、版本语义变化、消费影响变化、证据线索状态和边界异常应能被平台稳定观察。 | 后续验收应能判断这些状态或异常是否发生,但不要求本 Step 定义具体指标名。 |
| 可观测性 | 可观测材料不得成为方法资产定义真相的替代存储。 | observability、audit material 或 telemetry 只能支持观察和追溯,不能替代本仓定义真相。 |

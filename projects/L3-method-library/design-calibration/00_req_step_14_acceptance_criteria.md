## 2. 整体模块骨架

Step 14 按五类验收和一票否决收敛:

| 模块 | 输出 | 不输出 |
|---|---|---|
| 核心能力闭环验收 | 四个能力节点是否共同成立。 | 不写执行步骤或测试链路。 |
| 功能能力验收 | 核心功能 FR-ML-001~007 是否被满足。 | 不写 API 调用、Command 或 Query。 |
| 规则 / 边界验收 | BR-ML 规则和相邻仓边界是否被满足。 | 不写实现校验逻辑。 |
| 数据归属验收 | 真相、快照、引用、禁止正文边界是否正确。 | 不写字段、表、接口或测试断言代码。 |
| 非功能验收 | NFR 质量底线是否成立。 | 不写压测、监控或 CI 方案。 |
| 一票否决项 | 一旦发生就不能判定需求通过的情况。 | 不放一般缺陷或外围增强缺口。 |

## 3. 模块思考记录

### 3.1 核心能力闭环验收

问题回答:

- 核心闭环必须验“能力共同成立”,不是验某个旧流程是否跑通。
- 四个节点都要可判断:定义与识别、正式化与版本、下游消费、追溯一致性。

诊断:

- 旧稿用 Create -> Publish -> Event -> Snapshot -> Downstream Sync 的流程作为主链验收,已经混入接口、事件和实现机制。

取舍:

- 用能力条件表达验收,不写测试动作和旧 API 名。

### 3.2 功能能力验收

问题回答:

- FR-ML-001~007 都要有验收项,但不需要每条功能完全复制成一条。
- 功能验收应覆盖核心定义、正式化、受控消费、追溯一致性。

诊断:

- 旧功能验收使用 Given/When/Then 和具体对象字段,需要抽象为能力通过条件。

取舍:

- 用 6 条核心功能验收覆盖 FR-ML-001~007,外围增强单独验收。

### 3.3 规则 / 边界验收

问题回答:

- 验收必须证明方法资产真相不串仓、Definition vs Use 不破、边界外职责不进入本仓。
- 治理结论和审计要求只验边界是否清楚,不验治理流程实现。

诊断:

- 旧验收强调数据模型和接口不存在某路径,这已经接近实现检查;需求层只写通过条件。

取舍:

- 验收条件写“需求层边界清晰且不混入”,不写怎么检查。

### 3.4 数据归属验收

问题回答:

- 真相数据必须归本仓。
- 快照和引用不得形成第二真相源。
- 禁止保存正文项必须不进入本仓生命周期。

诊断:

- 旧稿的 QualificationProfile / Binding 红线方向有价值,但 Qualification 本身是否纳入核心还待确认。

取舍:

- 验收围绕当前 Step 11 数据归属表,不继承旧 Qualification 专项 P0 验收。

### 3.5 非功能验收

问题回答:

- 质量验收要覆盖性能、可用性、安全、追溯、一致性和可观测性。
- 不继承旧 P95 和指标名,因为当前需求层未授权具体实现。

诊断:

- 如果把旧 P95 直接写进 Step 14,后续设计会被旧缓存 / PG 假设绑死。

取舍:

- 写可判断的质量通过条件,具体数值留给后续设计或测试计划。

## 4. 结构化中间产物

### 4.1 验收标准表

| 验收类别 | 验收项 | 验收条件 |
|---|---|---|
| 核心能力闭环验收 | 方法资产统一定义与识别成立 | 方法资产能够作为本仓统一定义语义被建立、识别和引用,不依赖散落文档或消费仓私有模型。 |
| 核心能力闭环验收 | 稳定版本进入正式使用语境成立 | 方法资产能够区分非正式调整语境和正式使用语境,正式版本语义稳定且变化必须显式。 |
| 核心能力闭环验收 | 下游按边界消费成立 | process、identity、runtime、member-images 等主链消费方能够按边界消费正式方法资产语义,且不拥有定义真相。 |
| 核心能力闭环验收 | 变化追溯与消费一致性保护成立 | 方法资产正式化、版本语义变化和影响消费的变化能够被追溯,并能保护既有正式消费不被静默破坏。 |

| 功能能力验收 | 方法资产正式化与版本稳定能力 | FR-ML-003 和 FR-ML-004 所要求的正式化、正式/非正式区分和版本稳定边界能够共同成立。 |

| 功能能力验收 | 方法资产消费一致性保护能力 | FR-ML-007 所要求的影响识别和引用稳定性保护能力能够成立。 |
| 功能能力验收 | 外围增强能力不阻塞核心闭环 | FR-ML-E-* 未完成时不得影响核心闭环验收;若实现外围增强,必须遵守核心定义真相边界。 |

| 规则 / 边界验收 | 禁止行为未发生 | BR-ML-005~008 所禁止的下游反向拥有定义、消费未正式资产、运行职责进入本仓和源码依赖误写没有进入需求结论。 |
| 规则 / 边界验收 | 显式变化规则成立 | BR-ML-009~011 所要求的正式化、版本语义变化和消费影响变化均为显式变化,不得隐式发生。 |
| 规则 / 边界验收 | 相邻仓边界清晰 | BR-ML-012~018 所列 process、identity、governance、capability-hub、marketplace、UI、artifact/archive 边界不被打穿。 |
| 规则 / 边界验收 | 治理与审计边界清晰 | BR-ML-019~021 所要求的治理结论引用、正式化追溯和正式消费追溯能够成立,且不迁入治理执行。 |

| 非功能验收 | 主链性能判断口径成立 | NFR-ML-001~002 所要求的主链不阻塞和一致性优先口径能够被后续验收承接。 |
| 非功能验收 | 核心闭环可用性成立 | NFR-ML-003~004 所要求的核心闭环不被外围能力或条件型依赖失效整体拖垮。 |
| 非功能验收 | 安全边界成立 | NFR-ML-005~006 所要求的越权持有禁止和下游绕过定义真相禁止能够成立。 |

### 4.2 一票否决项

| 否决项 | 否决原因 |
|---|---|
| 方法资产定义真相不能明确归属本仓 | 核心能力闭环第一节点不成立,本仓会退化为下游私有模型集合。 |
| 方法资产正式版本语义可被静默覆盖 | 破坏版本稳定、审计追溯和正式消费一致性。 |
| 下游消费仓可以创建、修改或替代方法资产定义真相 | 破坏 Definition vs Use 和本仓存在边界。 |
| 未正式化或不稳定的方法资产可作为正式消费依据 | 破坏正式使用语境和受控消费能力。 |
| process、identity、governance、capability-hub、marketplace、UI 或 artifact/archive 的边界外正文进入本仓真相范围 | 造成跨仓数据归属错误和职责串线。 |
| 正式化、版本语义变化或消费影响变化不可追溯 | 破坏审计、验收和消费一致性保护。 |
| 运行期依赖或事件协作依赖被写成本仓与消费仓的源码级拥有关系 | 破坏全局依赖裁剪规则并导致仓际耦合错误。 |
| 外围增强能力被作为核心闭环成立的前置 | 使 P0 边界失控,无法判断核心需求是否完成。 |

#### 14.1 验收标准表

| 验收类别 | 验收项 | 验收条件 |
|---|---|---|

| 核心能力闭环验收 | 下游按边界消费成立 | process、identity、runtime、member-images 等主链消费方能够按边界消费正式方法资产语义,且不拥有定义真相。 |
| 核心能力闭环验收 | 变化追溯与消费一致性保护成立 | 方法资产正式化、版本语义变化和影响消费的变化能够被追溯,并能保护既有正式消费不被静默破坏。 |
| 功能能力验收 | 方法资产定义建模与目录识别能力 | FR-ML-001 和 FR-ML-002 所要求的统一定义、身份识别、目录语义和适用语境能够共同成立。 |
| 功能能力验收 | 方法资产正式化与版本稳定能力 | FR-ML-003 和 FR-ML-004 所要求的正式化、正式/非正式区分和版本稳定边界能够共同成立。 |
| 功能能力验收 | 正式方法资产受控消费能力 | FR-ML-005 所要求的受控消费能力能够成立,且消费方不会迁移定义真相。 |
| 功能能力验收 | 方法资产追溯能力 | FR-ML-006 所要求的版本、变更依据和引用语境可追溯能力能够成立。 |
| 功能能力验收 | 方法资产消费一致性保护能力 | FR-ML-007 所要求的影响识别和引用稳定性保护能力能够成立。 |
| 功能能力验收 | 外围增强能力不阻塞核心闭环 | FR-ML-E-* 未完成时不得影响核心闭环验收;若实现外围增强,必须遵守核心定义真相边界。 |
| 规则 / 边界验收 | 方法资产定义真相归属清晰 | BR-ML-001~004 所要求的定义真相、身份语境、Definition vs Use 和正式版本稳定边界在需求层清晰成立。 |
| 规则 / 边界验收 | 禁止行为未发生 | BR-ML-005~008 所禁止的下游反向拥有定义、消费未正式资产、运行职责进入本仓和源码依赖误写没有进入需求结论。 |
| 规则 / 边界验收 | 显式变化规则成立 | BR-ML-009~011 所要求的正式化、版本语义变化和消费影响变化均为显式变化,不得隐式发生。 |
| 规则 / 边界验收 | 相邻仓边界清晰 | BR-ML-012~018 所列 process、identity、governance、capability-hub、marketplace、UI、artifact/archive 边界不被打穿。 |
| 规则 / 边界验收 | 治理与审计边界清晰 | BR-ML-019~021 所要求的治理结论引用、正式化追溯和正式消费追溯能够成立,且不迁入治理执行。 |
| 数据归属验收 | 真相数据归属正确 | Step 11 所列方法资产定义、身份目录、正式化版本、关系、追溯和分发语义由本仓拥有正式真相。 |
| 数据归属验收 | 快照与引用不形成第二真相源 | Step 11 所列治理摘要、标准摘要、下游回报摘要和外部引用不形成独立正式真相生命周期。 |
| 数据归属验收 | 禁止保存正文边界成立 | Step 11 所列流程运行、成员状态、治理执行、外部能力、交易、UI、artifact/archive 等正文不进入本仓生命周期。 |
| 接口与依赖验收 | 能力接口不泄漏协议实现 | Step 12 所列对外能力接口均停留在能力边界,不依赖 API 路径、DTO、event schema、port 或 adapter 表达才能成立。 |
| 接口与依赖验收 | 依赖类型与全局裁剪一致 | Step 12 所列 `L0-core`、`L0-bus`、process、identity、runtime、member-images 等依赖边界与 Step 6 的依赖类型判断一致。 |
| 非功能验收 | 主链性能判断口径成立 | NFR-ML-001~002 所要求的主链不阻塞和一致性优先口径能够被后续验收承接。 |
| 非功能验收 | 核心闭环可用性成立 | NFR-ML-003~004 所要求的核心闭环不被外围能力或条件型依赖失效整体拖垮。 |
| 非功能验收 | 安全边界成立 | NFR-ML-005~006 所要求的越权持有禁止和下游绕过定义真相禁止能够成立。 |
| 非功能验收 | 追溯、一致性和可观测性成立 | NFR-ML-007~013 所要求的追溯、单一正式语义、显式变化和关键状态可观察能够成立。 |

#### 14.2 一票否决项

- 方法资产定义真相不能明确归属本仓。
- 方法资产正式版本语义可被静默覆盖。
- 下游消费仓可以创建、修改或替代方法资产定义真相。
- 未正式化或不稳定的方法资产可作为正式消费依据。
- process、identity、governance、capability-hub、marketplace、UI 或 artifact/archive 的边界外正文进入本仓真相范围。
- 正式化、版本语义变化或消费影响变化不可追溯。
- 运行期依赖或事件协作依赖被写成本仓与消费仓的源码级拥有关系。
- 外围增强能力被作为核心闭环成立的前置。

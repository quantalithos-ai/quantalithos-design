## 5. 模块思考记录

### 5.1 架构目标:先思考

问题回答:

- `L3-method-library` 值得单独做架构设计,不是因为它有一组方法资产 CRUD,而是因为它必须在平台中承载方法资产定义真相、正式版本语义和下游消费边界。
- 架构目标必须回答“哪些结构必须成立”,不能复制需求目标、功能需求、接口能力、对象清单或旧实现流程。
- Step 1 已确认核心主线为统一定义与识别、稳定正式化、下游边界消费、变化追溯与一致性保护;Step 2 的目标应围绕这四段能力成立。
- 当前目标还必须显式容纳外部协作的不确定性:governance、artifact、marketplace、SDK/console 等不能被写成核心前置,但架构也不能完全封死未来承接位置。

诊断:

- 旧正式 `01-架构设计.md` 的目标方向大体与新版 00 一致,但它的 completed 状态和后续章节不能被继承;本轮必须从 ARB-ML / AHC-ML / ARR-ML 重新推导。
- “不做流程执行 / 不做成员状态 / 不做 marketplace 交易”等是约束或非目标,不应混写进架构目标。
- “发布、查询、同步、导出、事件传播”等是功能或交互候选,不应成为架构目标。
- 如果目标不包含外围增强隔离,后续 MethodPlugin、MethodConfiguration、marketplace、AIPolicy override 和高级 ViewProfile 容易反向扩大核心边界。
- 如果目标不包含条件型协作承接,后续 governance 结论、artifact 引用和下游影响摘要会在系统上下文或交互设计中被迫私自补口。

取舍:

- 架构目标收敛为七项:定义真相、Definition vs Use、正式版本稳定、下游受控消费、变化追溯与一致性保护、核心与外围隔离、条件型外部协作承接。
- 不把数据四分法单独写成目标,而在“定义真相”和“变化追溯”目标中承接,并在不可变约束中展开。
- 不把 NFR 写成目标口号;只保留“语义正确性优先”和“外围不拖垮核心”的结构性结果。
- 不关闭 ARR-ML-001~009 的未确认项,只在目标中保留可扩展 / 可承接位置。

| 是否写成结构性结果 | pass | 目标候选均表达架构必须确保成立的结构。 |

### 5.2 架构目标:再写入

#### 5.2.1 业务背景与驱动力

`L3-method-library` 的架构需要独立收敛,因为方法资产会被流程、身份、运行时、成员镜像、治理、体验和生态分发语境长期引用。若没有独立定义源和正式版本语义,方法定义会散落到消费仓、旧实现同步链或人工文档约定中,从而破坏 Definition vs Use、受控消费和追溯一致性。

核心驱动力:

- 平台需要一个独立于流程实例、成员状态、治理执行、交易履约和 UI 渲染的方法资产定义源。
- 方法资产必须在正式版本语境中被稳定消费,不能被下游本地约定替代。
- 方法资产变化必须可追溯,并能保护既有正式消费不被静默破坏。
- 外围增强和条件型依赖必须与核心闭环隔离,避免当前架构范围失控。
- 后续 governance、artifact、marketplace、SDK/console 等协作需要可承接位置,但不能反向成为核心前置。

#### 5.2.2 架构目标表

| 架构目标 | 说明 |
|---|---|
| 承载独立的方法资产定义真相 | 否则方法定义会退化为 process、identity、runtime、UI 或生态侧的本地私有模型。 |
| 守住 Definition vs Use 的结构边界 | 否则本仓会吸收流程执行、成员状态、治理执行、交易履约、UI 渲染或外部正文生命周期等相邻仓职责。 |
| 支撑正式方法资产版本稳定 | 否则下游正式引用会被静默变化破坏,无法形成可靠消费语境。 |
| 支撑下游按边界受控消费 | 否则消费仓需要复制或改写方法定义正文,定义真相会出现多源。 |
| 允许方法资产变化被追溯并保护消费一致性 | 否则正式化、版本语义变化和消费影响只能依赖人工约定或实现细节。 |
| 隔离核心闭环与外围增强 | 否则 MethodPlugin、MethodConfiguration、marketplace、高级 ViewProfile 或 AIPolicy override 会拖垮核心架构判断。 |
| 保留条件型外部协作的可承接位置 | 否则治理结论、artifact 引用、下游影响摘要、console / SDK 体验等后续协作会被误写成核心前置或完全无法承接。 |

### 5.3 不可变约束:先思考

问题回答:

- 不可变约束应回答“什么边界一旦被打穿,本仓架构就不成立”,而不是重复架构目标或列出所有业务规则。
- Step 1 的 AHC-ML-001~010 已经给出硬约束全集,本模块需要将其压缩成正式架构 3.1 可直接承载的红线。
- 约束必须具体到仓级职责、数据所有权、正式版本语义、依赖方向和外部协作边界。
- ARR-ML 风险不是不可变约束本体,但它们要求约束表不得把未闭口项写成强依赖或核心前置。

诊断:

- “承载定义真相”在目标中是正向结果,在约束中要改写成“不得让定义真相漂移出本仓”。
- Definition vs Use 容易被系统上下文图打穿,因此约束必须禁止将相邻仓运行真相纳入本仓。
- 正式版本稳定和未正式化不得正式消费是一组硬约束,后续状态机可以另行设计,但架构层不能绕过这组语义。
- 数据边界必须在 Step 2 先钉住,否则 Step 8 可能为了查询、投影、缓存或审计把外部正文写成本仓数据。
- 治理、artifact、marketplace 和事件协作可以作为外部关系存在,但不能成为本仓定义真相、交易真相或源码级拥有关系。

取舍:

- 不可变约束压缩为十项,对应真相源、Definition vs Use、版本变化、正式消费、下游反写、依赖方向、治理边界、artifact 边界、marketplace 边界、外围隔离。
- 不在约束表中写“架构含义 / 禁止漂移”三列表,而按书写规范使用“约束 / 说明”两列。
- 不写具体技术选型、状态名、协议、事件、表或缓存方案。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否写成不可变红线 | pass | 约束候选均为破坏后会打穿仓边界的红线。 |
| 是否区分目标和约束 | pass | 目标中的正向结果已改写为负向边界约束。 |
| 是否避免实现机制 | pass | 未写状态机、接口、事件、表或技术方案。 |
| 是否可进入“不可变约束:再写入” | pass | 可转成两列表。 |

### 5.4 不可变约束:再写入

| 约束 | 说明 |
|---|---|
| 不允许方法资产定义真相漂移出本仓 | 否则 process、identity、runtime、governance、marketplace、UI 或 artifact 会形成第二定义源。 |
| 不允许 Definition vs Use 被合并 | 否则流程实例、成员状态、治理执行、UI 渲染或 artifact 正文会被误建模为本仓核心能力。 |
| 不允许正式版本语义被静默改变 | 否则既有正式引用会在没有显式变化的情况下改变含义。 |
| 不允许未正式化资产成为正式消费依据 | 否则读取、引用、同步或运行时使用会绕过正式化语义。 |
| 不允许下游创建、修改或替代方法资产定义真相 | 否则消费仓会从使用方变成定义方,破坏单一真相源。 |
| 不允许运行期消费或事件协作变成源码级拥有关系 | 否则跨仓依赖会反向侵入本仓业务实现。 |
| 不允许治理执行进入本仓 | 治理结论可以作为前置或依据引用,但 Gate、裁决执行和 policy enforce 不属于本仓架构。 |
| 不允许 artifact / archive 正文进入本仓 | 本仓只能定义 work product 语义或保存正式允许的摘要 / 引用边界。 |
| 不允许 marketplace 交易履约进入本仓 | 本仓最多作为方法资产定义或分发语义来源,不承载定价、订单、购买、结算或安装记录。 |
| 不允许外围增强改变核心闭环成立条件 | MethodPlugin、MethodConfiguration、marketplace、高级策略变体和标准映射材料不得成为核心定义、正式化、消费和追溯的前置。 |

### 5.5 当前阶段取舍:先思考

问题回答:

- 当前阶段取舍只处理“可能与本仓有关,但当前有意识不做深”的事项,不处理已经明确边界外的流程执行、成员状态、治理执行、交易履约等事项。
- 取舍的核心来源是 ARR-ML-001~009 和 00 Step 15 的待确认项。
- 取舍必须给出当前口径:作为外围增强、候选消费关系、条件型依赖、最小承接或后续文档暂存,而不是写“以后再说”。

诊断:

- Qualification / CapabilityDefinition 一旦纳入核心,会影响资产范围、数据归属、接口和验收,因此当前只能挂起,不能局部插入后续架构。
- MethodPlugin / MethodConfiguration 和 marketplace 与方法资产分发相关,但当前若做深会把核心闭环拖入生态和商业流程。
- AIPolicy override、高级 ViewProfile、组织级策略变体属于定义主题的复杂扩展,应保留可承接位置,不能成为核心目标。
- governance、artifact、下游影响回报、SDK/console 体验都是可能协作面,但当前不能写成核心强依赖。
- P95/SLO、指标集和验收执行方式属于后续测试/验收或 NFR 细化,不能在架构目标层固定。

取舍:

### 5.7 架构非目标:先思考

问题回答:

- 架构非目标用于排除明确不属于当前架构主线的范围,不是阶段性延期项。

诊断:

- 流程执行、成员身份、治理执行、外部能力接入、marketplace 交易、UI 渲染、artifact 正文、认证鉴权均已被需求层排除为相邻职责。

- 非目标表保留八项边界外架构范围和一项技术方案非目标。
- 每项只写不展开原因,不替相邻仓设计,不提出后续实现建议。

## 7. 回填草稿

### 2. 业务背景与驱动力

> 校准来源:
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读:
> - 建议继续阅读 `design-calibration/01_arch_step_02_goals_constraints.md` 的“架构目标表”和“当前阶段可接受取舍表”。

`L3-method-library` 的架构需要独立收敛,因为方法资产会被流程、身份、运行时、成员镜像、治理、体验和生态分发语境长期引用。若没有独立定义源和正式版本语义,方法定义会散落到消费仓、旧实现同步链或人工文档约定中,从而破坏 Definition vs Use、受控消费和追溯一致性。

核心驱动力:

- 平台需要一个独立于流程实例、成员状态、治理执行、交易履约和 UI 渲染的方法资产定义源。
- 方法资产必须在正式版本语境中被稳定消费,不能被下游本地约定替代。
- 方法资产变化必须可追溯,并能保护既有正式消费不被静默破坏。
- 外围增强和条件型依赖必须与核心闭环隔离,避免当前架构范围失控。
- 后续 governance、artifact、marketplace、SDK/console 等协作需要可承接位置,但不能反向成为核心前置。

| 架构目标 | 说明 |
|---|---|
| 承载独立的方法资产定义真相 | 否则方法定义会退化为 process、identity、runtime、UI 或生态侧的本地私有模型。 |
| 守住 Definition vs Use 的结构边界 | 否则本仓会吸收流程执行、成员状态、治理执行、交易履约、UI 渲染或外部正文生命周期等相邻仓职责。 |
| 支撑正式方法资产版本稳定 | 否则下游正式引用会被静默变化破坏,无法形成可靠消费语境。 |
| 支撑下游按边界受控消费 | 否则消费仓需要复制或改写方法定义正文,定义真相会出现多源。 |
| 允许方法资产变化被追溯并保护消费一致性 | 否则正式化、版本语义变化和消费影响只能依赖人工约定或实现细节。 |
| 隔离核心闭环与外围增强 | 否则 MethodPlugin、MethodConfiguration、marketplace、高级 ViewProfile 或 AIPolicy override 会拖垮核心架构判断。 |
| 保留条件型外部协作的可承接位置 | 否则治理结论、artifact 引用、下游影响摘要、console / SDK 体验等后续协作会被误写成核心前置或完全无法承接。 |

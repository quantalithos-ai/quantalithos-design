## 3. 模块思考记录

### 3.1 核心子域

#### 问题回答

核心子域应从核心能力闭环推导:定义与目录、正式化与版本、受控消费语义、追溯与一致性保护。这四类语义共同决定本仓是否能作为方法资产定义真相源存在。

#### 诊断

旧材料容易从 MethodContent 子类、目录结构或服务模块倒推子域,例如把 `method_content`、`process_templates`、`ai_policies`、`deployment_package` 直接当子域。这会把对象或实现目录误认为限界上下文。

#### 取舍

核心子域按“承载的语义”命名,不按旧对象名、API 名、目录名或技术机制命名。具体资产类型在后续数据所有权和详细设计中再下沉。

### 3.2 支撑子域

#### 问题回答

支撑子域围绕核心语义存在,包括方法资产关系与分发语义、外部依据承接、包/方法集组织等。它们可以支撑核心闭环或外围演进,但不应成为核心真相本体。

#### 诊断

MethodPlugin / MethodConfiguration、29110 package/export、marketplace 生态发现等旧方向可能很重要,但新版 00 已将它们列为外围增强或待确认。若放进核心子域,会扩大 P0 架构。

#### 取舍

将“方法资产关系与分发语义”作为支撑子域,因为它支撑受控消费;将“方法资产包与方法集组织语义”作为支撑/外围子域,明确不阻塞核心闭环。

### 3.3 本地索引 / 投影 / 引用边界

#### 问题回答

本仓可以承接治理结论摘要、标准来源摘要、下游消费影响摘要、artifact/archive 引用、marketplace 生态对象引用等影子结构,但这些都不能成为本仓的核心真相。

#### 诊断

旧材料中的 snapshot、fingerprint、outbox、audit record、downstream sync 很容易把影子结构写成核心子域。新版 00 要求它们先停留在摘要、引用或后续设计机制层。

#### 取舍

本 Step 只划出本地引用/摘要上下文,不定义 snapshot schema、fingerprint 算法、event payload、outbox 或对账机制。

### 6.3 统一语言词汇结论

| 词汇 | 架构层含义 | 禁止混淆 |
|---|---|---|
| 方法资产定义 | 本仓拥有的定义性方法语义。 | 不等同于流程实例、成员状态、治理执行或 UI 渲染。 |
| 目录语义 | 用于稳定识别方法资产身份和适用语境的语义。 | 不等同于搜索索引或数据库目录表。 |
| 正式化 | 方法资产进入正式使用语境的显式语义变化。 | 不等同于治理 Gate 执行流程或任意读取行为。 |
| 版本语义 | 正式方法资产可被稳定引用的语义边界。 | 不等同于字段版本、hash 或具体 semver 算法。 |
| 受控消费 | 下游按边界消费正式方法资产语义。 | 不等同于下游拥有定义正文或源码依赖。 |
| 追溯 | 对正式化、版本变化和消费影响的解释能力。 | 不等同于日志表、trace id 或 outbox。 |
| 摘要 / 引用 | 本仓对外部依据或下游影响的有限承接。 | 不等同于外部正文或外部系统 truth。 |

## 5. 模块思考记录

### 5.1 核心子域:先思考

问题回答:

- 核心子域应从核心能力闭环推导,而不是从旧 MethodContent 子类、旧目录结构或旧 service 名称推导。
- 本仓成立所必需的核心语义是:方法资产定义与目录、正式化与版本、受控消费、追溯与一致性保护。
- 这四个核心子域共同保护本仓作为方法资产定义 truth 的存在:定义提供对象锚点,正式化提供使用语境,消费提供边界输出,追溯提供变化解释。

诊断:

- 如果按 RoleDefinition、TaskDefinition、WorkProductDefinition、ProcessTemplate、ViewProfile、AIPolicy 切子域,会把对象类型清单误写成限界上下文。
- 如果按 draft/publish/fingerprint/outbox 切子域,会把状态机或实现机制误写成架构语义结构。
- 如果把治理、artifact 或下游消费状态放进核心子域,会产生多 truth 或外部运行职责回流。

取舍:

- 核心子域收敛为四项:定义与目录、正式化与版本、受控消费、追溯与一致性保护。
- 不单列具体 SPEM 内容类型为子域;它们后续属于定义语义内部资产范围,不是 Step 5 的上下文边界。
- 不把 Qualification / CapabilityDefinition 写入核心子域,保持 Step 15 待确认口径。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否从核心能力推导 | pass | 四项均对应核心能力闭环。 |
| 是否避免对象清单 | pass | 未按具体 MethodContent 子类划分。 |
| 是否避免实现机制 | pass | 未写状态机、fingerprint、outbox 或目录结构。 |
| 是否可进入“核心子域:再写入” | pass | 可转成核心子域表项。 |

### 5.3 支撑子域:先思考

问题回答:

- 支撑子域围绕核心语义存在,但不是核心 truth 本体。
- 方法资产关系与分发语义支撑受控消费,因为下游需要理解资产之间关系和分发语境,但它不替代定义与版本语义。
- 方法资产包与方法集组织语义可承接 MethodPlugin / MethodConfiguration 等外围增强,但当前不作为核心闭环前置。

诊断:

- MethodPlugin / MethodConfiguration、29110 package/export、marketplace 生态发现等旧方向可能重要,但新版 00 把它们列为外围增强或待确认。
- 如果把包、方法集或 marketplace 分发写成核心子域,会扩大本轮架构主线。
- 如果完全删除分发语义,又会无法解释 Step 2 和 Step 10 中“方法资产分发语义承载”的职责。

取舍:

- 保留“方法资产关系与分发语义”为支撑子域,因为它支撑核心受控消费。
- 保留“方法资产包与方法集组织语义”为支撑 / 外围子域,明确不阻塞核心闭环。
- 不写 marketplace 交易、安装、履约或包导出实现。

本模块门禁:

|---|---|---|

| 是否避免 marketplace 交易越界 | pass | 未写交易、安装或履约。 |

### 5.5 本地影子边界:先思考

问题回答:

- 本地影子结构包括外部依据摘要与引用、下游消费影响摘要。
- 它们用于稳定承接外部上下文,但不拥有治理、标准、artifact、marketplace 或下游运行状态的 truth。
- 这些结构应归为本地索引 / 投影 / 引用,而不是核心子域或支撑子域。

诊断:

- governance 正式化结论摘要和治理依据引用容易被误写成治理执行子域。
- artifact/archive 引用容易借 WorkProductDefinition 进入本仓正文生命周期。
- 下游消费影响摘要容易被写成下游运行状态或强制同步机制。
- 旧 snapshot、fingerprint、drift report、outbox 都是机制候选,不能在 Step 5 变成内部上下文。

取舍:

- 本地影子边界只列两类:外部依据摘要与引用、下游消费影响摘要。
- 具体摘要 schema、引用有效性、对账、事件和存储策略留到后续设计。
- 对外部正文和运行状态保持禁止拥有。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否把影子结构降级 | pass | 摘要和引用均未写成核心 truth。 |
| 是否覆盖外部依据和下游影响 | pass | governance、标准、artifact、marketplace、下游影响均有承接口径。 |
| 是否避免 schema 和机制 | pass | 未写 snapshot schema、fingerprint、outbox 或对账。 |
| 是否可进入“本地影子边界:再写入” | pass | 可转成本地索引 / 投影 / 引用表项。 |

### 5.7 关系图与统一语言:先思考

问题回答:

- 内部关系图要表达定义、正式化、消费、追溯、支撑、影子承接之间的语义依附关系。
- 核心子域应位于上层,支撑子域位于核心之后,本地影子位于底层。
- 统一语言需要重点区分定义、目录、正式化、版本、受控消费、追溯、摘要 / 引用这些高频词。

诊断:

- 旧图如果看起来像流程顺序,会被误读成运行时调用链。
- 图中不能出现外部上下文对象,例如 `L1-governance`、`L1-artifact` 或 `L6-marketplace`。
- 图中也不能出现接口名、事件名、数据库表或实现组件。

取舍:

- 关系图使用直线层次图,不表达调用顺序。
- 统一语言表只说明架构层含义和禁止混淆,不写字段或对象定义。
- 图和词汇均服务后续 Step 6~9,不替后续文档下沉。

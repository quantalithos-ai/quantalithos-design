## 5. 模块思考记录

### 5.1 运行承载角色:先思考

问题回答:

- 本仓至少需要同步入口承载、后台维护承载、异步协作承载、正式状态承载、读取与追溯承载。
- 同步入口承载覆盖定义、正式化、目录读取、正式定义读取和追溯查看等同步能力面。
- 后台维护承载覆盖目录、追溯、一致性和恢复类长时处理。
- 异步协作承载覆盖变化可感知输出、外部治理结论输入和下游消费影响输入。
- 正式状态承载和读取与追溯承载是逻辑承载角色,不代表已选择数据库、缓存、索引或 projection。

诊断:

- 旧材料把 `rpc`、`infra`、migration、PG、对象存储和缓存写得很早,容易把运行承载误写成实现目录或技术栈。
- 当前 Step 还没有进入技术选型,不能决定数据库、缓存、消息后端或对象存储。
- 如果把 outbox、snapshot、fingerprint 单独画成运行容器,会把后续机制候选误写成当前架构主语。

取舍:

- 使用运行角色名表达承载单元。
- 保留正式状态承载和读取与追溯承载,但只说明承载正式状态 / 读取材料,不定义表、索引、projection 或缓存。
- 不把 MethodPlugin、marketplace 或治理裁决作为独立运行单元。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否使用正式运行角色 | pass | 运行单元均来自 4.7 允许对象类型。 |
| 是否避免实现模块 | pass | 未写 service、repository、handler、crate、bin 或目录。 |
| 是否避免技术选型 | pass | 未指定 PG、Redis、对象存储、消息后端。 |
| 是否可进入“运行承载角色:再写入” | pass | 可转成运行单元表项。 |

### 5.5 部署关系和通信方式:先思考

问题回答:

- 同步入口、后台维护和异步协作需要逻辑可分,因为入口压力、异步失败和维护恢复的节奏不同。
- 当前阶段可以同部署,但架构上不能把它们混成一个不可拆运行单元。
- 正式状态承载必须独立于下游消费仓,读取与追溯承载也不得成为第二定义真相。
- 通信方式只表达同步入口、处理 / 消费、承载 / 依赖和事件协作运行边界,不表达协议。

诊断:

- 旧路线图和 README 可能暗示本仓是单个 Rust 服务配 PG/对象存储,但架构层不应把“单服务起步”写成不可变部署结构。
- 如果写 Docker、K8s、端口、资源、实例数或环境变量,会进入实施和运维。
- 如果写 repository、事务、锁、cache、projection,会越过到概要/详细设计。

取舍:

- 保留“逻辑可分、阶段可同部署”的口径。
- 部署平台、存储引擎、消息后端和缓存策略留给 Step 10 或后续配置 / 实施文档。
- 通信方式结论只列关系口径和不展开项。

|---|---|---|

### 5.6 部署关系和通信方式:再写入

#### 5.6.1 部署说明

本章只固定逻辑运行承载结构,不固定部署平台或进程边界。同步入口承载、异步协作承载和后台维护承载在早期可以同部署,但架构上必须保持逻辑可分,以便分别处理入口压力、异步失败和维护恢复。正式状态承载必须独立于下游消费仓,读取与追溯承载也不得成为第二定义真相。`L0-bus` 是运行对接边界,不是 method-library 内部实现模块。

#### 5.6.2 通信方式结论

| 通信关系 | 架构口径 | 不在本 Step 展开 |
|---|---|---|
| 外部同步入口 -> 同步入口承载 | 同步入口关系。 | API、route、DTO、auth、SDK。 |
| 同步入口承载 -> 正式状态承载 | 承载 / 依赖关系。 | repository、事务、表、锁。 |
| 同步入口承载 -> 读取与追溯承载 | 承载 / 依赖关系。 | cache、projection、index。 |
| 后台维护承载 -> 正式状态 / 读取与追溯承载 | 处理 / 承载关系。 | job 名、调度、重试、补偿算法。 |
| 异步协作承载 <-> `L0-bus` 运行对接边界 | 事件协作运行边界。 | event name、topic、payload、outbox。 |

## 3. 模块思考记录

### 3.1 运行单元

#### 问题回答

本仓至少需要同步入口承载、异步协作承载、后台维护承载、正式状态承载和读取/追溯承载。它们分别支撑变更/查询入口、变化可感知输出和输入、维护与恢复、定义真相保存、稳定读取和追溯查看。

#### 诊断

旧材料把 `rpc`、`infra`、migrations、PG、对象存储和缓存写得很具体,容易把运行承载误写成实现目录或技术栈。当前 Step 还没有进入技术选型,不能决定数据库、缓存、消息后端或对象存储。

#### 取舍

使用运行角色名表达承载单元。正式状态和读取/追溯承载只说明“承载正式状态/读取材料”,不定义表、索引、projection 或缓存。

### 3.2 外部边界

#### 问题回答

同步入口承接方法资产定义建立/调整、正式化/版本变化、目录/正式定义/追溯读取等能力面;异步协作承接方法资产变化输出、外部治理结论输入和下游消费影响输入;后台维护承接目录、追溯、一致性和恢复类运行职责。

#### 诊断

如果在图中写 `CreateMethodContent`、`process.template.published`、`outbox` 或 `snapshot` 等旧名,会把 Step 6 变成 Step 9/12/03。

#### 取舍

图中只使用“入口 / 处理 / 消费 / 承载 / 依赖”关系标注,不写协议、事件和具体任务名。

### 3.3 部署约束

#### 问题回答

同步入口、异步协作和后台维护需要逻辑可分,因为它们的入口压力、失败模式和恢复节奏不同。当前阶段可以同部署,但架构上不能把它们混成一个不可拆运行单元。正式状态承载必须独立于下游消费仓,否则定义真相会迁移。

#### 诊断

旧路线图和 README 可能暗示本仓是单个 Rust 服务配 PG/对象存储,但架构层不应把“单服务起步”写成不可变部署结构。

#### 取舍

保留“逻辑可分、阶段可同部署”的口径。部署平台、存储引擎、消息后端和缓存策略留给 Step 10 或后续配置/实施文档。

## 4. 架构单元小循环记录

本 Step 不新增语义架构单元小循环。

| 正式状态承载 | 承载本仓 truth,不得与下游运行状态合并。 | 通过 |
| 读取与追溯承载 | 服务受控消费和审计读取,不得成为独立定义源。 | 通过 |

## 6. 结构化中间产物

### 6.1 容器 / 部署架构图

```text
+-----------------------------+
| 外部同步入口边界            |
| 管理 / 下游读取 / 条件触发  |
+--------------+--------------+
               |
               | 入口
               v
+---------------------------------------------+
| L3-method-library 运行边界                   |
|                                             |
|  +-----------------------+                  |
|  | 同步入口承载          |                  |
|  +-----------+-----------+                  |
|              | 处理                         |
|              v                              |
|  +-----------------------+                  |
|  | 后台维护承载          |                  |
|  +-----------+-----------+                  |
|              | 处理 / 消费                  |
|              v                              |
|  +-----------------------+                  |
|  | 异步协作承载          |                  |
|  +-----------+-----------+                  |
|                                             |
+--------------+------------------------------+
               |
               | 承载 / 依赖
               v
+-----------------------+   +-----------------------+
| 正式状态承载          |   | 读取与追溯承载        |
+-----------------------+   +-----------------------+
               ^
               | 依赖
               |
+--------------+--------------+
| L0-bus 运行对接边界          |
+-----------------------------+
```

该图仅表达本仓运行承载角色与正式运行边界,不表达接口协议、事件名、实现组件、数据库表或运行时调用顺序。

图示说明:

- 同步入口承载负责承接外部同步入口流量,但不定义具体 API 或协议。
- 后台维护承载负责长时维护、恢复和一致性材料推进,但不定义任务清单或重试算法。
- 异步协作承载负责本仓与事件协作边界的运行对接,但不定义 topic、event schema 或 outbox。
- 正式状态承载和读取与追溯承载是逻辑承载角色,不代表已选定数据库、缓存或索引技术。

### 6.2 运行单元说明表

| 对象 | 类型 | 主要职责 | 运行关系 | 说明 |
|---|---|---|---|---|
| 外部同步入口边界 | 运行时对接的正式外部边界 | 承接管理、下游读取和条件型触发流量。 | 入口到同步入口承载。 | 只表示入口来源,不写 API 或 SDK 细节。 |
| 同步入口承载 | 同步入口单元 | 承接方法资产定义、正式化、目录读取、正式定义读取和追溯查看的同步入口。 | 处理后进入后台维护或依赖正式状态/读取承载。 | 不等同于具体 API service 或 handler。 |
| 后台维护承载 | 后台处理单元 | 承接目录维护、追溯材料维护、一致性检查和恢复补偿。 | 处理同步入口或异步输入后形成维护动作。 | 不定义具体 job 名、调度方式或重试策略。 |
| 异步协作承载 | 异步消费单元 | 承接方法资产变化输出、外部治理结论输入和下游消费影响输入的运行对接。 | 消费 / 处理来自 `L0-bus` 的协作边界。 | 不写 event 名、topic、payload 或 outbox。 |
| 正式状态承载 | 正式存储承载 | 承载方法资产定义、正式化版本、关系和分发语义等正式状态。 | 被同步入口、后台维护和异步协作依赖。 | 不指定存储引擎、表结构或事务策略。 |
| 读取与追溯承载 | 正式存储承载 | 承载正式读取、目录识别、追溯查看和消费支撑所需读取材料。 | 被同步入口和后台维护依赖。 | 不指定 read model、cache、index 或 projection 实现。 |
| `L0-bus` 运行对接边界 | 正式基础设施依赖 | 支撑变化可感知输出和正式异步输入。 | 与异步协作承载形成依赖关系。 | 不形成业务仓源码依赖。 |

### 6.3 部署说明

本章只固定逻辑运行承载结构,不固定部署平台或进程边界。同步入口承载、异步协作承载和后台维护承载在早期可以同部署,但架构上必须保持逻辑可分,以便分别处理入口压力、异步失败和维护恢复。正式状态承载必须独立于下游消费仓,读取与追溯承载也不得成为第二定义真相。`L0-bus` 是运行对接边界,不是 method-library 内部实现模块。

### 6.4 通信方式结论

| 通信关系 | 架构口径 | 不在本 Step 展开 |
|---|---|---|
| 外部同步入口 -> 同步入口承载 | 同步入口关系。 | API、route、DTO、auth、SDK。 |
| 同步入口承载 -> 正式状态承载 | 承载/依赖关系。 | repository、事务、表、锁。 |
| 同步入口承载 -> 读取与追溯承载 | 承载/依赖关系。 | cache、projection、index。 |
| 后台维护承载 -> 正式状态/读取与追溯承载 | 处理/承载关系。 | job 名、调度、重试、补偿算法。 |
| 异步协作承载 <-> `L0-bus` 运行对接边界 | 事件协作运行边界。 | event name、topic、payload、outbox。 |

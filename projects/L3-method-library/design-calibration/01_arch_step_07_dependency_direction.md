## 3. 模块思考记录

### 3.1 内部依赖角色

#### 问题回答

本仓依赖方向应保护核心语义角色。外部接缝角色只能把同步入口、事件协作、条件型外部依据和下游消费关系带到正式承接角色;正式承接角色再依赖核心语义角色和支撑/摘要角色。支撑/摘要角色围绕核心语义存在,不得反向成为核心定义真相。技术承载角色只承载正式状态和读取材料,不得反向决定方法资产定义语义。

#### 诊断

旧材料把 `application services`、`domain model`、`repository`、`outbox`、`snapshot exporter`、PostgreSQL、object storage、cache 等写进依赖图。那些名称要么是代码组织,要么是运行承载或技术选型,不能作为本 Step 的架构责任层主语。

#### 取舍

使用抽象依赖角色表达规则:外部接缝角色、正式承接角色、核心语义角色、支撑与摘要角色、技术承载角色。图中的箭头只表示允许依赖或边界接入,不表达调用顺序、协议交互、事件传播或实现层函数调用。

### 3.2 跨仓依赖裁剪

#### 问题回答

当前主链跨仓依赖保持需求 Step 6 和架构 Step 4 的收敛结果:`L0-core` 是编译期依赖;`L0-bus` 是事件协作依赖;`L1-process`、`L1-identity`、`L2-runtime`、`L2-member-images` 是运行期消费关系。`L1-governance`、`L1-artifact`、`L6-marketplace`、`L5-console`、`L0-sdk`、`L4-observability` 与本仓相关,但当前不作为核心主链依赖。

#### 诊断

最容易失控的点是把“下游消费 method-library”误写成“下游源码依赖 method-library”,或把治理/marketplace/console 这种相关关系写成核心前置。另一个风险是把 `L0-bus` 当成业务仓可直接依赖的事件 schema 来源,而不是事件协作主干。

#### 取舍

只把闭环成立必需的跨仓关系写入主链。候选、外围和条件型关系保留在裁剪表中,但明确不形成当前主链前置。运行期和事件协作关系只进入后续边界、事件协作或读取材料讨论,不得进入源码依赖。

### 3.3 依赖倒置边界

#### 问题回答

外部治理结论、下游消费影响、artifact/archive 引用、marketplace 分发语义和 console/SDK 入口都必须通过外部接缝和正式承接进入。核心语义角色不能直接依赖外部系统正文、外部运行状态、UI 入口、marketplace 交易、governance 执行或下游索引。

#### 诊断

如果核心语义直接读取下游运行状态或外部正文,就会形成第二 truth source。若后续概要设计需要这些输入,必须先定义正式摘要、引用或边界输入;架构 Step 7 只能规定依赖方向,不能私自补 schema。

#### 取舍

依赖倒置规则写成边界红线:外部事实必须被归约成正式摘要/引用/结论后进入,并且只能支撑正式化、追溯或消费一致性判断,不能替代本仓方法资产定义真相。

## 4. 结构化中间产物

### 4.1 依赖方向图

```text
+==============================================================+
|               L3-method-library 依赖边界                     |
|                                                              |
|   外部接缝角色                                               |
|   +-------------------------------+                          |
|   | 外部入口 / 协作 / 消费接缝     |                          |
|   +---------------+---------------+                          |
|                   | 边界接入                                  |
|                   v                                          |
|        +-------------------------------+                     |
|        | 正式承接角色                  |                     |
|        +----------+-------------+------+                     |
|                   |             |                            |
|                   | 允许依赖    | 允许依赖                   |
|                   v             v                            |
|        +----------------+  +-------------------------------+ |
|        | 核心语义角色   |  | 支撑与摘要角色                | |
|        +----------------+  +---------------+---------------+ |
|                   ^                         | 允许依赖        |
|                   |                         |                |
|                   +-------------------------+                |
|                                                              |
|   技术承载角色                                               |
|   +-------------------------------+                          |
|   | 正式状态 / 读取材料承载        |                          |
|   +-------------------------------+                          |
|                                                              |
+==============================================================+
```

图示说明:

- 外部接缝角色只表达外部能力通过正式边界进入,不代表 API、event、SDK、worker 或 adapter。
- 正式承接角色可以依赖核心语义角色、支撑与摘要角色和技术承载角色,但不能把外部运行事实直接送入核心。
- 支撑与摘要角色围绕核心语义存在,只能依赖核心语义或正式摘要/引用,不得成为第二定义真相。
- 技术承载角色只承载状态和读取材料,不能反向决定核心语义边界。
- 该图不表达调用顺序、运行拓扑、事件传播、代码层依赖或部署结构。

### 4.2 层间约束表

| 架构责任层 / 依赖角色 | 允许依赖 | 禁止依赖 | 说明 |
|---|---|---|---|
| 外部接缝角色 | 允许边界接入到正式承接角色。 | 禁止直接依赖核心语义角色、支撑与摘要角色或技术承载角色的内部细节。 | 外部入口、事件协作、条件型依据和下游消费必须先被正式承接,不能打穿核心。 |
| 正式承接角色 | 允许依赖核心语义角色、支撑与摘要角色、技术承载角色和外部接缝输入的正式结果。 | 禁止拥有独立方法资产定义真相;禁止绕过核心语义直接采纳外部正文或下游运行状态。 | 该角色负责把外部输入和内部核心连接起来,但不重新定义方法资产语义。 |
| 核心语义角色 | 允许依赖本仓内部已收敛的核心规则和正式摘要/引用语义。 | 禁止依赖外部系统正文、下游运行状态、UI 入口、marketplace 交易、governance 执行、技术承载实现细节。 | 核心语义必须保持最稳定,保护方法资产定义真相、正式版本、受控消费和追溯边界。 |
| 支撑与摘要角色 | 允许依赖核心语义角色和正式外部摘要/引用。 | 禁止替代核心语义成为定义真相;禁止保存外部正文、下游运行状态或交易履约事实。 | 支撑分发、关系、外部依据和消费影响,但只以摘要/引用形态存在。 |
| 技术承载角色 | 允许被正式承接角色依赖,承载正式状态和读取材料。 | 禁止反向规定核心语义、状态词表、跨仓边界或业务规则。 | 技术承载是支撑条件,不是方法资产定义边界的来源。 |

### 4.3 依赖倒置结论

| 外部能力 / 关系 | 必须通过的边界 | 不得直接依赖 | 保护目标 |
|---|---|---|---|
| `L0-core` 共享契约 | 作为编译期基础契约来源进入。 | 不得在本仓重新定义上游共享概念。 | 保持跨仓公共类型和引用语义唯一。 |
| `L0-bus` 事件协作 | 通过事件协作接缝进入/输出。 | 不得把事件协作写成本仓源码依赖或核心定义真相。 | 保持事件只是协作信号,不替代方法资产 truth。 |
| `L1-process` 消费 | 通过受控消费边界读取正式方法语义。 | 不得让 process 执行状态、索引或实例反向定义模板。 | 保护 Definition vs Use。 |
| `L1-identity` 消费 | 通过受控消费边界读取角色等定义语义。 | 不得让成员状态或成员实际角色反向定义 RoleDefinition。 | 保护定义与成员状态分离。 |
| `L2-runtime` 消费 | 通过运行期消费边界获得方法语义。 | 不得让 runtime 本地约定反向成为定义源。 | 保护执行语境不拥有定义真相。 |
| `L2-member-images` 消费 | 通过运行期消费边界获得 Role -> image 语义。 | 不得 hardcode 或反向改写角色镜像映射。 | 保护构建输入与定义源分离。 |
| `L1-governance` 条件型结论 | 通过正式治理结论 / 引用接缝进入。 | 不得把治理执行、Gate 状态或 policy enforce 迁入核心。 | 保持本仓只消费结论或依据,不执行治理。 |
| `L1-artifact` 候选消费 | 通过定义语义或引用边界进入。 | 不得保存 artifact 正文、证据文件或 archive 生命周期。 | 保护 artifact truth 不迁入本仓。 |
| `L6-marketplace` 外围消费 | 通过资产来源或分发语义边界消费。 | 不得让定价、订单、安装或履约成为本仓依赖。 | 保护生态分发与交易边界。 |
| `L5-console` / `L0-sdk` 入口候选 | 通过正式入口边界或能力封装进入。 | 不得让 UI/SDK 入口决定核心语义。 | 保护体验入口不反向塑造定义 truth。 |

### 5.3 本仓禁止依赖表

|---|---|---|
| `L1-process -> L3-method-library` 源码级依赖 | process 运行期消费模板定义,不能因为消费关系直接依赖本仓源码。 | 运行期能力边界 / 正式读取或快照边界。 |
| `L1-identity -> L3-method-library` 源码级依赖 | identity 只引用或消费角色定义语义,不得把方法资产定义正文并入身份仓。 | 运行期能力边界 / 快照 / 引用。 |
| `L2-runtime -> L3-method-library` 源码级依赖 | runtime 消费方法语义,但执行语境不拥有定义 truth。 | 运行期能力边界 / 受控消费材料。 |

| `L3-method-library -> L1-identity` 反向成员状态依赖 | 本仓不拥有成员生命周期或成员实际具备哪些角色的状态。 | 只保留角色定义语义输出,成员状态归 identity。 |
| `L3-method-library -> L1-governance` 策略执行依赖 | 本仓不执行治理裁决、Gate 或 policy enforce。 | 治理结论通过正式治理边界或引用进入。 |
| `L3-method-library -> L6-marketplace` 交易依赖 | marketplace 交易、订单、结算、安装和履约不是本仓目标。 | marketplace 通过正式资产来源 / 分发语义消费。 |
| `L3-method-library -> L4-observability` 直接真相写入 | observability 是横切观测,不能成为方法资产 truth store。 | 通过事件协作或审计材料边界协作。 |
| `L3-method-library -> L0-bus` 业务定义依赖 | `L0-bus` 是事件协作主干,不定义业务对象语义。 | 业务定义留在本仓核心语义,事件协作只传播变化信号。 |

| marketplace 是否进入当前阶段 | 当前只保留外围分发语义,交易和履约不入本仓。 |
| console / SDK 是否作为 P0 管理入口 | 当前作为入口候选,不改变核心语义依赖方向。 |
| Qualification / CapabilityDefinition 是否改变 capability-hub 关系 | 当前不建立 direct dependency;若未来纳入需回写 Step 3~7。 |

### 9.3 进入下一步条件

可以进入 Step 8。

进入 Step 8 前提:

- 内部架构责任层和依赖方向已分清。
- 跨仓依赖已完成本仓裁剪,并区分编译期、运行期、事件协作。
- 每个 Step 5 架构单元已有依赖规则和停审结论。
- 未把运行拓扑、协议交互、代码目录、实现机制或技术选型写入依赖方向。

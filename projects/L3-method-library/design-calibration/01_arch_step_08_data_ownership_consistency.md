## 2. 整体模块骨架

Step 8 先回答“谁拥有正式真相”,再回答“这些关系如何一致”。它不是存储设计、对象模型设计或同步实现设计。

| 模块 | 本 Step 回答的问题 | 本 Step 不回答的问题 |
|---|---|---|
| 数据归属 | 哪些数据由本仓拥有正式真相,哪些只是快照/投影、引用关系或明确不拥有正文。 | 不写字段、表、索引、对象模型、schema、cache key 或存储引擎。 |
| 一致性策略 | 在归属已明确的前提下,哪些关系要求强一致、最终一致、引用有效性一致或边界约束一致。 | 不写事务机制、事件机制、outbox、retry、projection、worker 或补偿实现。 |
| 架构单元数据规则 | Step 5 每个架构单元拥有什么、不拥有什么,本地存在是否只是影子或引用。 | 不重划子域,不定义 DTO、repository、port 或测试用例。 |

## 3. 模块思考记录

### 3.1 数据归属

#### 问题回答

本仓正式真相集中在方法资产定义、身份目录、正式化版本、受控消费前提、追溯依据、定义性关系和分发/组织语义。治理结论、外部标准、下游影响这类内容如果本地存在,只能是快照 / 投影或引用关系。流程实例、成员状态、治理执行、外部能力绑定、marketplace 交易、UI 执行、artifact/archive 正文必须明确不属于本仓。

#### 诊断

旧材料把数据归属和实现机制混在一起,例如把具体指纹、快照、事件、审计记录、数据库、对象存储、缓存、回放机制放入架构数据边界。这样会让后续实现把某个技术机制误当作正式数据真相。

#### 取舍

使用架构层数据类别表达归属。下游定义快照属于由本仓 truth 派生的消费材料,不是第二 truth;外部治理、标准、artifact、marketplace 只可作为摘要或引用进入,不能变成本仓拥有的正文。

### 3.2 一致性策略

#### 问题回答

本仓正式真相内部要求强一致,否则方法资产定义、正式化和版本语义会互相漂移。正式真相到只读消费材料、下游消费影响摘要或外部协作信号可以最终一致。正式真相到外部引用关系要求引用有效性一致;外部正文与边界外真相要求边界约束一致,失败时不得回填成本仓 truth。

#### 诊断

如果把“下游必须即时同步成功”写成强一致,会把运行期消费压回本仓并打穿 Definition vs Use。如果把外部正文不可用写成“本仓补齐正文”,会直接形成第二 truth source。

#### 取舍

一致性口径不写低层方案,只写架构原则:内部 truth 变化失败则不形成部分完成;派生读取材料延迟不改变 truth;引用失效保持显式失效或挂起;外部正文缺失不得由本仓伪造。

### 3.3 架构单元数据规则

#### 问题回答

核心子域拥有正式真相;支撑子域拥有围绕核心存在的定义性 truth 或外围增强 truth;本地索引/投影/引用单元只拥有影子、摘要或引用关系,不得拥有外部正文或下游运行状态。

#### 诊断

Step 5 中“外部依据摘要与引用”和“下游消费影响摘要”容易被后续实现误读为外部 truth 被迁入本仓。Step 8 必须明确这些单元只拥有本地承接材料,不拥有上游或下游正文。

#### 取舍

逐架构单元列出 truth、snapshot/projection、reference 和 forbidden body。凡无法确定的数据不写成已拥有 truth,进入待确认事项。

### 4.2 一致性策略表

| 数据关系 / 场景 | 关联数据类型 | 一致性口径 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 方法资产定义内部变化 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 明确失败,不形成部分完成的正式定义变化。 | 核心 truth 漂移会直接破坏定义源边界。 |
| 正式化与版本语义建立 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 未能同时成立时保持非正式或未完成口径。 | 正式使用语境和版本稳定必须一起成立。 |
| 定义性关系变化 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 不接受只改一侧语义的部分完成口径。 | 方法资产之间的定义关系不能靠消费仓隐式修正。 |
| 正式真相到正式读取材料 | 正式真相数据 ↔ 快照 / 投影数据 | 最终一致 | 读取材料可保持旧视图或显式待收敛,不得改写 truth。 | 只读承接延迟不等于正式真相失效。 |
| 正式真相到下游消费材料 | 正式真相数据 ↔ 快照 / 投影数据 | 最终一致 | 下游暂未感知时保持待收敛或不可感知口径,不阻止 truth 成立。 | 受控消费不要求下游即时同步成功。 |
| 正式化依赖外部治理结论 | 正式真相数据 ↔ 快照 / 投影数据 / 引用关系数据 | 前置一致 / 引用有效性一致 | 结论缺失或不可判定时挂起正式化,不得伪造治理结论。 | 外部治理可作为前置依据,但不迁入治理执行 truth。 |
| 方法资产与外部正文关系 | 正式真相数据 ↔ 引用关系数据 | 引用有效性一致 | 引用失效时显式失效或挂起相关能力,不得复制正文补齐。 | 引用关系有效不等于本仓拥有正文。 |
| 方法资产与 artifact/archive 关系 | 正式真相数据 ↔ 引用关系数据 | 引用有效性一致 | 引用缺失或不可用时保持显式不可用,不吸收 artifact 正文。 | WorkProductDefinition 与制品正文必须分离。 |
| 下游消费影响承接 | 正式真相数据 ↔ 快照 / 投影数据 | 最终一致 / 摘要一致 | 下游影响摘要缺失时保留未知或待确认口径,不得读取下游内部状态补齐。 | 本仓只承接正式摘要,不拥有下游运行 truth。 |
| 外围包 / 方法集组织与核心定义 | 正式真相数据 ↔ 正式真相数据 | 边界内强一致 | 不满足核心定义引用时不形成有效外围组织语义。 | 外围增强不能独立漂移为第二方法资产来源。 |
| 本仓与明确不拥有正文的边界 | 引用关系数据 ↔ 明确不拥有的正文 / 真相 | 边界约束一致 | 不回填为本仓真相;必要时挂起、拒绝或显式不可用。 | 外部正文和运行真相只能被引用或排除。 |
| 技术承载与核心真相关系 | 正式真相数据 ↔ 快照 / 投影数据 | 承载一致 | 承载材料不可用时不能反向改变核心语义。 | 技术承载只支持读取和保存,不定义业务 truth。 |

### 4.3 简化关系示意图

```text
+---------------------------+
| 正式真相数据              |
| 方法资产定义 / 正式版本   |
+-------------+-------------+
              |
              | 派生 / 承接
              v
+---------------------------+
| 快照 / 投影数据           |
| 读取材料 / 摘要 / 影响    |
+-------------+-------------+
              |
              | 只保存关系
              v
+---------------------------+
| 引用关系数据              |
| 治理 / 标准 / 外部正文 ref |
+-------------+-------------+
              |
              | 不拥有
              v
+---------------------------+
| 明确不拥有的正文 / 真相   |
| 运行状态 / 外部正文       |
+---------------------------+
```

图示说明:

- 正式真相数据是本仓数据边界的中心,其他数据存在都不得反向改写它。
- 快照 / 投影数据可以支撑读取和消费,但只能从 truth 派生或从外部正式摘要承接。
- 引用关系数据只保存关系,不保存外部正文。
- 明确不拥有的正文 / 真相不得因引用、快照或运行需要进入本仓。

### 4.4 数据边界说明

`L3-method-library` 的数据所有权以方法资产定义 truth 为中心,本地存在的读取材料、摘要和引用都不能被误读成第二 truth source。治理、标准、artifact、marketplace、console/SDK、process、identity、runtime、member-images 等相关关系只能通过正式摘要、引用或消费材料进入,不得把它们的正文和运行状态保存为本仓数据。正式真相内部变化要求强一致,跨边界读取、下游消费和外部摘要承接允许最终一致或引用有效性一致。当前 Step 不决定数据库、缓存、投影、事件、outbox 或事务实现。

## 5. 按架构单元组织的数据所有权

### 5.1 架构单元数据所有权表

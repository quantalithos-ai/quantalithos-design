## 5. 模块思考记录

### 5.1 关键交互场景:先思考

问题回答:

- 值得进入本章的交互场景集中在四类:核心 truth 的建立和调整、正式化与版本裁定、读取与受控消费、跨边界变化传播和外部结果送达。
- 目录、读取、追溯材料维护和一致性保护不应压入同步交互,更适合后台延后承接。
- 外围资产包、方法集组织、marketplace 生态和 artifact 候选关系只能作为外围或候选交互,不能成为核心 truth 成立前置。

诊断:

- 旧材料已经出现接口名、事件名、fingerprint、outbox、snapshot、PG、cache 和同步链路表达。如果直接继承,本章会滑到协议设计或实现时序。
- 旧 P0 下游同步链路容易把“下游全部同步成功”误写成本仓 truth 成立条件。
- governance 结论和下游消费影响摘要如果被写成同步查询,会打穿 Step 7 的依赖倒置和 Step 8 的数据归属。

取舍:

- 使用场景级名称表达交互,不使用旧 API、event、job 或对象名。
- 核心 truth 需要明确同步裁定;跨边界事实传播和外部结果送达走异步;派生读取材料和恢复走后台延后承接。
- 外围增强交互保留,但明确不阻塞核心闭环。

### 5.3 通信方式判断:先思考

问题回答:

- 方法资产定义建立 / 调整、正式化 / 版本变化、目录 / 定义 / 追溯读取适合同步请求 / 响应类交互,因为调用方需要即时得到状态判断或明确失败口径。
- 方法资产变化传播、外部治理结论送达、下游消费影响回报适合异步事件 / 回调类交互,因为它们是跨边界事实传播或结果送达,不能变成直接穿透核心的同步链。
- 目录 / 读取 / 追溯材料维护和一致性保护 / 恢复适合后台任务 / 延后承接类交互,因为它们服务最终一致和恢复,不要求在当前同步边界完成。

诊断:

- 如果把所有交互都写成同步,会把 process、identity、runtime、member-images、governance 或 marketplace 的可用性压成本仓 truth 成立前提。
- 如果把核心定义变更写成异步,会让调用方无法得到明确失败口径,破坏正式 truth 强一致。
- 如果把后台维护写成协议实现,会提前落入技术选型或详细设计。

取舍:

- 同步只用于本仓边界内需要立即裁定的能力。
- 异步用于跨仓事实传播和外部结果送达。
- 后台用于派生材料、追溯材料、一致性检查和恢复。
- 失败口径只写架构原则:同步失败不形成部分 truth,异步失败保留待送达或待承接,后台失败保持待恢复或显式不可用。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否使用正式通信方式类型 | pass | 只使用同步请求 / 响应、异步事件 / 回调、后台任务 / 延后承接。 |
| 是否给出不宜方式 | pass | 每个场景说明不宜采用的通信类别。 |
| 是否给出失败口径 | pass | 每个场景均有失败、挂起、待承接、未知或不可用口径。 |
| 是否可进入“通信方式判断:再写入” | pass | 可形成通信方式判断表。 |

### 5.4 通信方式判断:再写入

| 交互场景 | 推荐通信方式 | 不宜采用的方式 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 方法资产定义建立与调整 | 同步请求 / 响应类交互 | 不宜作为纯异步事件完成,否则调用方无法得知定义 truth 是否成立。 | 明确失败,不形成部分完成的正式定义变化。 | 核心 truth 内部要求强一致和明确裁定。 |
| 方法资产正式化与版本变化 | 同步请求 / 响应类交互 | 不宜依赖下游同步完成作为成功条件;不宜用后台任务替代正式裁定。 | 前置不足或外部结论缺失时挂起或失败,不伪造正式化成功。 | 正式化是本仓核心语义变化,但下游感知可以异步。 |
| 方法资产目录、正式定义与追溯读取 | 同步请求 / 响应类交互 | 不宜通过异步事件来回答单次读取;不宜暴露内部维护流程。 | 返回明确可读、不可见、不可用或待收敛口径。 | 读取交互需要清晰结果,但读取材料可最终一致。 |
| 方法资产变化可感知传播 | 异步事件 / 回调类交互 | 不宜作为核心变更同步裁定的一部分;不宜要求下游逐一确认后才成立。 | 保持待传播、待承接或可恢复状态,核心 truth 不因传播延迟回滚。 | 保护 Definition vs Use,避免下游可用性压回本仓。 |
| 外部治理结论送达 | 异步事件 / 回调类交互 | 不宜由本仓同步查询治理执行过程或直接读取治理内部状态。 | 结论未送达或不可判定时保持正式化挂起或依据缺失。 | 外部治理是条件型结论来源,不是本仓执行职责。 |
| 下游消费影响回报 | 异步事件 / 回调类交互 | 不宜同步扫描下游内部状态;不宜把缺失回报当作无影响。 | 缺失时保持未知、待承接或待确认口径。 | 本仓只拥有影响摘要,不拥有下游运行 truth。 |
| 目录、读取和追溯材料维护 | 后台任务 / 延后承接类交互 | 不宜要求每次核心变更同步完成全部派生材料。 | 失败时保持旧读取材料、待收敛或显式不可用,不得改写 truth。 | 派生材料服务读取和追溯,适合最终一致。 |
| 一致性保护与恢复承接 | 后台任务 / 延后承接类交互 | 不宜作为外部同步入口的强制内联步骤;不宜由下游直接驱动核心修改。 | 保持待恢复、待确认或显式异常状态,不伪造成已修复。 | 恢复类交互关注收敛,不改变 truth 的来源边界。 |
| 外围资产包和方法集组织交互 | 同步请求 / 响应类交互用于管理裁定;异步事件 / 回调类交互或后台任务 / 延后承接类交互用于传播和维护 | 不宜把外围生态交互写成核心正式化前置。 | 外围依赖不可用时降级为外围不可用或待承接,不影响核心定义 truth。 | 外围增强可演进,但必须与核心闭环隔离。 |

#### 5.4.2 边界说明

`L3-method-library` 的关键交互选择服务于方法资产定义 truth 边界。核心 truth 的建立、调整、正式化、版本裁定和读取需要同步明确裁定;跨仓变化传播、治理结论送达和下游影响回报需要异步承接;派生读取材料、追溯材料和一致性恢复需要后台延后收敛。这样的划分不是技术偏好,而是为了避免下游运行状态、治理执行过程或外围生态依赖反向决定本仓核心 truth。

### 5.5 架构单元交互规则:先思考

问题回答:

- 核心子域主要通过同步入口形成明确状态判断,通过异步输出让变化被下游感知,通过后台承接派生材料维护。
- 支撑子域可以有同步管理入口和异步传播,但外围失效不得影响核心 truth 成立。
- 本地索引 / 投影 / 引用单元需要更强调异步输入和后台维护,避免把外部正文或下游运行状态直接纳入同步核心。

诊断:

- “外部依据摘要与引用”不能变成同步查询 governance 执行状态或标准正文的通道。
- “下游消费影响摘要”不能变成同步扫描 process、identity、runtime 或 member-images 内部状态的通道。
- “方法资产包与方法集组织语义”不能让 marketplace 交易、安装或 UI 激活状态成为核心交互。

取舍:

- 逐单元记录同步、异步、后台和失败口径。
- 凡外部结果缺失或不可判定,只允许挂起、未知、待承接或显式不可用,不得由本仓伪造成功结果。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否覆盖 Step 5 单元 | pass | 覆盖 8 个架构单元。 |
| 是否匹配数据所有权 | pass | truth 裁定同步;摘要、引用、派生材料异步或后台承接。 |
| 是否避免直接穿透 | pass | 未要求同步读取 governance 执行或下游运行状态。 |
| 是否可进入“架构单元交互规则:再写入” | pass | 可形成架构单元通信方式表和停审记录。 |

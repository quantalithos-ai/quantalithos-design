## 5. 模块思考记录

### 5.1 架构机制识别:先思考

问题回答:

- 能进入本章的机制必须保护 `L3-method-library` 的定义 truth 边界,或影响一致性、依赖方向、运行承载、关键交互主线。
- 正式承接层隔离外部输入、核心 truth 与只读消费材料分层、异步最终一致传播、后台延后承接、引用 / 摘要优先、稳定版本显式变化、外围增强隔离、共享契约基线和逻辑可分运行承载都满足这个条件。
- 这些机制不是产品名或实现名,而是后续概要 / 详细设计必须服从的结构规则。

诊断:

- 旧文档中出现大量技术名词,例如 Rust、PostgreSQL、对象存储、RPC、HTTP、cache、outbox、snapshot、fingerprint、schema version、P95。这些有的将来可能仍有价值,但当前直接写入 Step 10 会把架构机制误写成实现清单或旧详细设计倒灌。
- “outbox / snapshot / fingerprint”这类旧词有方向价值,但新版 01 当前只授权异步传播、读取材料分层和显式变化边界,没有授权具体机制名。
- 若此处固定数据库、缓存、消息或协议,后续实现 agent 会倾向按旧 schema 或旧 port 私补。

取舍:

- 本 Step 保留架构机制,不保留技术产品。
- 机制必须能回指 Step 6~9 或 00 的规则 / NFR。
- 具体载体和实现方式在后续文档中重新论证。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否解决架构层问题 | pass | 机制均影响边界、数据、一致性、交互或运行承载。 |
| 是否避免产品名和局部实现名 | pass | 未把 Rust、PG、cache、MQ、HTTP / RPC 等写成选型事实。 |
| 是否每项机制都有来源 | pass | 均可回指 Step 2/6/7/8/9 或 00 规则 / NFR。 |
| 是否可进入“架构机制识别:再写入” | pass | 可形成关键技术机制表。 |

### 5.3 技术边界判断:先思考

问题回答:

- 当前不固定具体数据库、缓存、消息中间件、HTTP / RPC、对象存储、指纹算法、事件 envelope、任务调度、重试或部署平台。
- 这些事项只有在后续概要 / 详细 / 配置 / 实施阶段具备对象、协议、状态和测试口径后才能落定。
- 当前可以说“异步最终一致传播”,不能说“outbox + topic + event payload”;可以说“只读消费材料分层”,不能说“projection 表 / cache key”。

诊断:

- 如果此处提前固定某个实现机制,后续文档会被旧实现口径牵引,出现 schema、port、状态或 adapter 的私补。
- 技术机制和技术产品之间的分界必须写清,否则 Step 11 的取舍会把局部实现比较误当成架构路径比较。

- 使用“机制而非产品”的表达。
- 对旧材料中有价值但未闭口的机制名统一降级到后续文档重新论证。

### 5.4 技术边界判断:再写入

#### 5.4.1 技术边界说明

本章记录的是架构层技术机制,不是具体技术栈。凡是会改变边界保护、一致性方式、跨仓交互、运行承载或演进主线的机制,才进入 Step 10;凡是数据库、缓存、消息、HTTP / RPC、对象存储、指纹算法、事件格式、任务调度、部署环境和代码目录,当前都不作为架构选型事实写入。后续概要、详细、配置和实施文档可以选择具体载体,但必须服从本章已收敛的承接、分层、异步、后台、引用、版本、外围隔离、共享契约和逻辑可分承载边界。

#### 5.4.2 简化对照表

| 当前采用的机制 | 当前不采用 / 不固定的相邻思路 | 边界原因 |
|---|---|---|
| 正式承接层隔离外部输入 | 外部系统直接读写核心语义 | 保护方法资产定义 truth 不被外部正文或运行状态污染。 |
| 核心 truth 与只读消费材料分层 | 直接暴露核心 truth 给下游消费 | 保留下游消费稳定性和核心模型演进空间。 |
| 异步最终一致传播跨边界变化 | 同步等待所有下游确认后才成立 truth | 避免下游可用性反向决定本仓核心变化。 |
| 后台延后承接维护和恢复 | 在同步入口内完成所有派生材料和恢复 | 避免同步入口承担非即时收敛职责。 |
| 引用 / 摘要优先 | 复制治理、artifact、marketplace、下游运行正文 | 避免形成外部 truth 的本地副本。 |
| 稳定版本与显式变化 | 静默覆盖正式资产语义 | 保护正式引用、追溯和下游消费一致性。 |
| 核心闭环与外围增强隔离 | 外围增强作为核心前置 | 避免当前核心架构被生态、体验或高级策略变体拖垮。 |
| 共享契约和正式引用基线 | 本仓私造跨仓基础引用语义 | 保持平台级引用和依赖裁剪一致。 |
| 逻辑可分运行承载 | 把所有运行职责固定成不可拆单体 | 保留不同失败节奏、通信方式和后续演进空间。 |

### 5.5 机制代价与约束:先思考

问题回答:

- 每项机制都会给后续设计增加具体成本,包括承接面、派生材料收敛、异步失败、后台恢复、引用失效、版本语义、外围演进、共享契约遵循和运行职责拆分。
- 这些代价必须在 Step 10 暴露,否则后续 Step 11 会只比较收益,实现阶段也容易把困难藏到私有约定里。
- 代价不是阻止采用机制的理由,而是说明该机制已经足够重要,值得承担后续设计负担。

诊断:

- 旧材料常用“可靠同步”“drift 防护”“可追溯”表达收益,但代价经常落到实现章节才出现。
- 如果代价写得太泛,例如“增加复杂度”,无法支撑 Step 11 的路径比较。

取舍:

- 按机制逐项停审代价,但不展开完整替代方案。
- 将具体实现成本留给后续概要 / 详细 / 实施计划。

本模块门禁:

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否每项机制都有代价 | pass | 主表和停审表均列出后续约束。 |
| 是否代价具体 | pass | 代价指向承接、收敛、恢复、引用、版本和演进等具体方向。 |
| 是否未展开完整方案比较 | pass | 没有做路径级替代方案矩阵。 |
| 是否可进入“机制代价与约束:再写入” | pass | 可形成机制代价停审表。 |

### 5.7 旧材料差异审计

#### 5.7.1 可保留为架构机制方向的旧材料

| 旧方向 | 本轮吸收方式 |
|---|---|
| Definition vs Use 分离 | 收敛为正式承接层、引用 / 摘要优先和核心 truth 分层机制。 |
| 发布后变化需要下游感知 | 收敛为异步最终一致传播,不继承事件名、outbox 或 topic。 |

### 6.1 可回填到 `01-架构设计.md` 的关键技术机制表

> 校准来源:

> 延伸阅读:
> - 建议继续阅读 `design-calibration/01_arch_step_10_technology_choices.md` 的“架构机制识别:再写入”“技术边界判断:再写入”“机制代价与约束:再写入”和“旧材料差异审计”小节,了解本章技术机制如何由运行承载、依赖方向、数据归属和关键交互收敛。

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 | 说明 |
|---|---|---|---|---|
| 通过正式承接层隔离外部输入与核心语义 | 防止外部输入直接打穿方法资产定义 truth。 | 外部事实必须通过正式接缝和承接进入。 | 后续必须明确输入是结论、摘要还是引用。 | 影响系统结构和依赖方向。 |
| 核心 truth 与只读消费材料分层 | 防止下游读取或管理视图直接绑定核心 truth 结构。 | 正式 truth 与读取材料的数据归属不同。 | 增加派生材料收敛和过期解释成本。 | 影响数据所有权和消费稳定性。 |
| 采用异步最终一致承接跨边界变化传播 | 防止下游可用性变成本仓 truth 成立前提。 | 变化感知、外部结论送达和影响回报均是跨边界协作。 | 增加传播延迟和失败恢复责任。 | 影响一致性策略和交互主链。 |
| 采用后台延后承接维护读取、追溯和恢复材料 | 防止派生材料和恢复全部压入同步入口。 | 后台维护承载已是运行结构的一部分。 | 需要明确待收敛、待恢复和不可用口径。 | 影响运行承载和失败边界。 |
| 采用引用 / 摘要优先而非复制外部正文 | 防止外部正文或下游运行状态形成第二 truth。 | 数据所有权已明确外部正文不入仓。 | 需要处理引用失效和摘要缺失。 | 影响安全和跨仓边界。 |
| 采用稳定正式版本与显式变化边界 | 防止正式资产被静默覆盖。 | 正式版本稳定是受控消费和追溯前提。 | 后续需区分不同变化语义。 | 影响核心语义和下游消费契约。 |
| 采用核心闭环与外围增强隔离 | 防止外围增强拖垮核心定义架构。 | 外围能力当前不是核心闭环前置。 | 演进时必须显式说明进入条件。 | 影响阶段边界和演进路线。 |
| 采用共享契约和正式引用基线 | 防止本仓私造跨仓共享概念。 | `L0-core` 是编译期共享契约来源。 | 必须遵守共享契约边界。 | 影响跨仓可引用性和依赖裁剪。 |
| 采用逻辑可分运行承载 | 防止不同运行职责被固定成不可拆结构。 | 同步、异步、后台和读取承载需要不同承接节奏。 | 后续实现可同部署,但设计职责必须可分。 | 影响运行承载和故障隔离。 |

### 6.2 可回填的技术边界说明

本章记录的是架构层技术机制,不是具体技术栈。数据库、缓存、消息、HTTP / RPC、对象存储、指纹算法、事件格式、任务调度、部署环境和代码目录当前都不作为架构选型事实写入。后续概要、详细、配置和实施文档可以选择具体载体,但必须服从本章已收敛的承接、分层、异步、后台、引用、版本、外围隔离、共享契约和逻辑可分承载边界。

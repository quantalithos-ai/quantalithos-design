## 5. 模块思考记录

### 5.1 当前主线识别:先思考

问题回答:

- 当前主线方案是“独立定义真相与分层承接方案”:本仓独立拥有方法资产定义 truth,通过正式承接层隔离外部输入,通过只读消费材料对外供给,通过异步最终一致传播跨边界变化,通过后台延后承接维护和恢复,并把外围增强与核心闭环隔离。
- 该主线不是“使用某个数据库 / 缓存 / outbox / snapshot / fingerprint”的实现包,而是 Step 2/7/8/9/10 已收敛的结构路径。
- 主线必须同时解释为什么不走更简单的文档仓、下游私有模型、共享数据库、直接暴露核心 truth 或同步等待所有下游。

诊断:

- 旧架构中“元模型仓 + PostgreSQL + outbox + snapshot + fingerprint”的表达有方向价值,但混合了路径级方案和具体实现机制。
- 如果主线命名包含实现词,后续 Step 12/13/15 和 02/03 容易被旧实现倒灌。
- 如果不显式写主线代价,当前方案会看起来像唯一自然选择,无法支撑 ADR 和后续评审。

取舍:

- 主线命名为“独立定义真相与分层承接方案”。
- 保留结构路径,不继承旧技术栈、对象清单、协议细节或实施参数。
- 在比较表中把主线与相邻路径放在同一表中比较。

### 5.2 当前主线识别:再写入

当前采用“独立定义真相与分层承接方案”:

```text
独立方法资产定义 truth
  -> 正式承接层隔离外部输入
  -> 只读消费材料对外供给
  -> 异步最终一致传播跨边界变化
  -> 后台延后承接维护和恢复
  -> 外围增强与核心闭环隔离
```

该主线只表达结构路径,不表达数据库、缓存、消息、对象存储、指纹算法、API、DTO、repository、worker 或部署实现。

### 5.3 相邻替代路径筛选:先思考

问题回答:

- 有效替代路径必须会改变主线结构判断,并且仍处在当前已收稳边界附近。
- 有效路径包括:文档 / Git 式方法资产仓、下游私有模型、共享数据库 / 共享 truth、直接暴露核心 truth、同步等待所有下游、复制外部正文、全量外围能力前置、强治理默认前置、全后台异步写入。
- 已被 Step 3 排除的流程执行入仓、成员状态入仓、治理执行入仓、marketplace 交易入仓、UI 渲染入仓和 artifact 正文入仓,不再作为合法候选。

诊断:

- PostgreSQL vs NoSQL、HTTP vs RPC、outbox vs 直接发送、cache vs 不 cache 都是点级技术或实现差异,不够格进入本 Step 主比较。
- Qualification / CapabilityDefinition 是否纳入核心是待确认事项,不是当前主线的已选路径或已放弃路径。
- P0 / P1 这类阶段标签如果不落到结构路径,也不能成为方案路径。

取舍:

- 只比较路径级结构替代。
- 边界外事项只在边界说明中排除,避免把职责边界重新打开。
- 未闭口事项继续挂起,不写成当前采用或不采用的最终结论。

### 5.5 取舍收束:先思考

问题回答:

- 当前主线牺牲初期简单性、即时全链成功感、外部正文本地完整性和外围能力完整性,换来定义 truth 稳定、下游消费边界清晰、跨仓传播不压垮同步入口、外部正文不入仓和后续演进可控。
- 当前取舍的关键不是“做得更多”,而是先让方法资产定义源、正式版本、受控消费和追溯一致性成立。
- 被放弃路径中仍可保留局部材料,例如文档 / Git 可作为外部正文或来源引用,marketplace 可作为外围消费面,governance 可作为条件型结论来源。

诊断:

- 若只写“不采用某方案”,没有写当前失去什么,后续很容易在 Step 13 或 03 中重新隐式采用。
- 若把“不采用为当前主线”误写成“永不采用”,会封死外围增强和条件型协作演进空间。

取舍:

- 用轻量取舍表收束“得到 / 失去”。
- 用边界说明区分“结构性替代路径”和“不配进入本章的事项”。

| 检查项 | 结论 | 说明 |
|---|---|---|
| 是否写出当前得到和失去 | pass | 对照表列出收益和承担成本。 |

当前采用“独立定义真相与分层承接方案”:本仓拥有独立方法资产定义 truth,通过正式承接层隔离外部输入,通过只读消费材料对外供给,通过异步最终一致传播跨边界变化,通过后台延后承接维护和恢复,并把外围增强与核心闭环隔离。

### 6.2 可回填的方案路径比较表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 独立定义真相与分层承接方案 | 让方法资产定义、正式版本、受控消费和追溯一致性稳定成立。 | truth 边界清楚,下游消费稳定,后续演进空间更大。 | 增加承接、读取材料、异步传播和后台维护成本。 | 采用 | 当前主线。 |
| 文档 / Git 式方法资产仓 | 用文档或版本库管理方法资产正文。 | 初期低成本。 | 难以形成稳定受控消费、正式版本裁定和跨仓追溯。 | 不采用 | 可作为外部来源引用,不能替代定义 truth。 |
| 下游私有模型方案 | 让下游各自维护所需方法语义。 | 下游起步快。 | 形成多源定义 truth,Definition vs Use 被破坏。 | 不采用 | 直接违背本仓存在必要性。 |
| 共享数据库 / 共享 truth 方案 | 多仓直接访问同一套方法资产数据。 | 表面上减少同步和转换。 | 数据所有权耦合,下游容易反向绑定或改写核心模型。 | 不采用 | 正式边界不能被共享存储替代。 |
| 直接暴露核心 truth 给下游读取 | 省去读取承接层。 | 初期接入简单。 | 下游绑定核心结构,写读边界混层。 | 不采用 | 当前采用 truth 与只读消费材料分层。 |
| 同步等待所有下游确认方案 | 核心变化在同步入口内等待所有下游确认。 | 即时一致感强。 | 下游可用性反向决定本仓 truth。 | 不采用 | 当前采用异步最终一致传播。 |
| 复制外部正文入仓方案 | 本地持有外部治理、标准、artifact、marketplace 或下游正文。 | 本地查询看似完整。 | 形成外部 truth 副本,正文生命周期和权限边界失控。 | 不采用 | 当前采用引用 / 摘要优先。 |
| 全量外围能力前置方案 | P0 同时纳入外围生态和高级策略能力。 | 初始能力更完整。 | 核心闭环被外围复杂度拖垮。 | 不采用为当前主线 | 外围增强保留演进位置。 |
| 强治理默认前置方案 | 所有方法资产正式化都强依赖治理执行或 Gate 可用。 | 合规控制更强。 | 本仓 truth 可用性受治理执行牵制。 | 不采用为默认主线 | 当前只保留条件型治理结论或引用。 |
| 全后台异步写入方案 | 将定义建立、正式化和版本变化也全部异步化。 | 同步入口轻。 | 调用方无法获得明确裁定。 | 不采用 | 核心 truth 裁定必须同步明确结果。 |

### 6.3 可回填的取舍说明

当前方案牺牲了初期简单性、即时全链成功感、外部正文本地完整性和外围能力完整性,换来定义 truth 稳定、下游消费边界清晰、跨仓传播不压垮同步入口、外部正文不入仓和后续演进可控。

## 3. 模块思考记录

### 3.1 当前主线识别

#### 问题回答

当前主线方案是:独立方法资产定义 truth,通过正式承接层隔离外部输入,通过只读消费材料对外供给,通过异步最终一致传播跨边界变化,通过后台延后承接维护和恢复材料,并把外围增强与核心闭环隔离。

#### 诊断

旧架构中“元模型仓 + PostgreSQL + outbox + snapshot + fingerprint”的表达有方向价值,但把架构路径和具体实现机制混在一起。新版 Step 11 需要比较的是结构路径,不是旧实现包。

#### 取舍

主线命名为“独立定义真相与分层承接方案”。它保留方法资产定义源和下游消费的结构关系,但不继承旧技术栈、对象清单或协议细节。

### 3.2 相邻替代路径筛选

#### 问题回答

有效替代路径包括:文档/Git 式方法资产仓、下游私有模型方案、共享数据库/共享 truth 方案、同步等待所有下游方案、直接暴露核心 truth 方案、复制外部正文方案、全量外围能力前置方案、强治理前置方案。这些路径会改变边界、依赖、数据、一致性或交互方式,因此配进入比较。

#### 诊断

流程执行入仓、成员状态入仓、marketplace 交易入仓等已经被 Step 3 明确排除,不再作为合法候选。PostgreSQL vs NoSQL、HTTP vs RPC、outbox vs 直接发送属于技术或实现层,不能作为本 Step 主比较。

#### 取舍

只比较结构性路径。被前文排除的边界外事项只在说明中点名“不进入本章”,避免把边界重新打开。

### 3.3 取舍收束

#### 问题回答

当前主线牺牲了初期简单性、即时感和外围能力完整性,换来定义 truth 稳定、下游消费边界清晰、跨仓传播不压垮同步入口、外部正文不入仓和后续演进可控。

#### 诊断

若只写当前方案优点,后续评审无法理解为什么不走更简单的文档仓、直接同步或共享库方案。Step 11 必须把代价写出来。

#### 取舍

表格逐项写“收益 / 代价 / 当前结论”。阶段延后能力只写为“当前不采用为核心前置”或“保留后续演进”,不伪装成已完成能力。

## 4. 结构化中间产物

### 4.1 当前主线方案

当前采用“独立定义真相与分层承接方案”:

```text
独立方法资产定义 truth
  -> 正式承接层隔离外部输入
  -> 只读消费材料对外供给
  -> 异步最终一致传播跨边界变化
  -> 后台延后承接维护和恢复
  -> 外围增强与核心闭环隔离
```

该主线只表达结构路径,不表达数据库、缓存、事件、对象存储、指纹算法、API、DTO、repository 或 worker 实现。

### 4.2 方案路径比较表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 独立定义真相与分层承接方案 | 让方法资产定义、正式版本、受控消费和追溯一致性在本仓稳定成立。 | truth 边界清楚,下游消费稳定,外部输入不打穿核心,后续演进空间更大。 | 增加正式承接层、只读材料、异步传播、后台维护和边界解释成本。 | 采用 | 这是当前主线,承接 Step 2/7/8/9/10 的全部核心结论。 |
| 文档 / Git 式方法资产仓 | 用文档或版本库管理方法资产正文。 | 初期低成本,适合人工阅读和轻量评审。 | 难以形成稳定受控消费、正式版本裁定、跨仓追溯和下游变化感知。 | 不采用 | 它可作为外部正文或来源引用存在,但不能替代本仓定义 truth。 |
| 下游私有模型方案 | 让 process、identity、runtime、member-images 各自维护所需方法语义。 | 下游起步快,短期减少本仓建模压力。 | 形成多源定义 truth,Definition vs Use 被破坏,版本和追溯不可统一。 | 不采用 | 该路径直接违背本仓存在必要性和核心目标。 |
| 共享数据库 / 共享 truth 方案 | 让多个仓直接访问同一套方法资产数据。 | 表面上减少同步和转换,读取路径更直接。 | 编译期、运行期和数据所有权耦合,下游容易反向绑定或改写核心模型。 | 不采用 | 运行期消费必须通过正式边界,不能用共享存储替代边界。 |
| 直接暴露核心 truth 给下游读取 | 省去只读消费材料和读取承接层。 | 初期接入简单,少一层派生材料维护。 | 下游绑定核心结构,读取边界和写入边界混层,核心演进成本上升。 | 不采用 | 当前采用 truth 与只读消费材料分层。 |
| 同步等待所有下游确认方案 | 核心变化在同步入口内等待所有下游确认。 | 即时一致感强,运维上似乎更容易判断“全链成功”。 | 下游可用性反向决定本仓 truth,同步入口耦合所有消费方,失败时易形成伪一致。 | 不采用 | 当前采用异步最终一致传播,核心 truth 成立不等待所有下游。 |
| 复制外部正文入仓方案 | 把治理、标准、artifact、marketplace 或下游正文复制到本仓以便本地判断。 | 本地查询看似完整,减少跨边界读取。 | 形成外部 truth 副本,正文生命周期和权限边界失控。 | 不采用 | 当前采用引用 / 摘要优先,外部正文不入仓。 |
| 全量外围能力前置方案 | P0 同时纳入 MethodPlugin、MethodConfiguration、marketplace、console/SDK、高级策略变体。 | 初始能力更完整,生态场景更丰富。 | 核心闭环被外围复杂度拖垮,正式 truth、版本和消费边界无法先稳定。 | 不采用为当前主线 | 外围增强保留演进位置,但不作为当前核心前置。 |
| 强治理前置方案 | 所有方法资产正式化都强依赖治理执行或 Gate 可用。 | 合规控制更强,发布口径更统一。 | 本仓 truth 可用性受治理执行可用性牵制,治理执行职责可能迁入本仓。 | 不采用为默认主线 | 当前只保留条件型治理结论或引用,不迁入治理执行。 |
| 全后台异步写入方案 | 将定义建立、正式化和版本变化也全部异步化。 | 同步入口轻,对外响应压力低。 | 调用方无法获得明确裁定,核心 truth 可能长时间处于不可解释状态。 | 不采用 | 核心 truth 裁定必须同步明确结果。 |

### 4.3 轻量取舍对照表

| 当前得到什么 | 当前失去 / 承担什么 |
|---|---|
| 独立方法资产定义 truth | 需要正式承接层和清晰边界维护成本。 |
| 下游按边界稳定消费 | 需要维护只读消费材料和待收敛口径。 |
| 跨边界变化不压垮同步入口 | 需要接受最终一致、传播延迟和恢复责任。 |
| 外部正文不入仓 | 需要处理引用失效、摘要缺失和外部不可用。 |
| 核心闭环先稳定 | 外围增强、marketplace 和高级变体不能一次性进入主线。 |

### 4.4 方案边界说明

本章只比较会改变主线结构的相邻方案路径。流程执行入仓、成员状态入仓、治理执行入仓、marketplace 交易入仓、UI 渲染入仓和 artifact 正文入仓已经被职责边界排除,不再作为正式候选方案。数据库、缓存、消息、HTTP/RPC、对象存储、指纹算法、事件格式和任务调度属于后续设计或实施层,不进入本章主比较。

### 12. 备选方案与取舍

> 校准来源:
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读:

#### 12.1 当前主线方案

当前采用“独立定义真相与分层承接方案”:本仓拥有独立方法资产定义 truth,通过正式承接层隔离外部输入,通过只读消费材料对外供给,通过异步最终一致传播跨边界变化,通过后台延后承接维护和恢复,并把外围增强与核心闭环隔离。

#### 12.2 方案路径比较

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 独立定义真相与分层承接方案 | 让方法资产定义、正式版本、受控消费和追溯一致性稳定成立。 | truth 边界清楚,下游消费稳定,后续演进空间更大。 | 增加承接、读取材料、异步传播和后台维护成本。 | 采用 | 当前主线。 |
| 文档 / Git 式方法资产仓 | 用文档或版本库管理方法资产正文。 | 初期低成本。 | 难以形成稳定受控消费、正式版本裁定和跨仓追溯。 | 不采用 | 可作为外部来源引用,不能替代定义 truth。 |
| 下游私有模型方案 | 让下游各自维护所需方法语义。 | 下游起步快。 | 形成多源定义 truth,Definition vs Use 被破坏。 | 不采用 | 直接违背本仓存在必要性。 |
| 共享数据库 / 共享 truth 方案 | 多仓直接访问同一套方法资产数据。 | 表面上减少同步和转换。 | 数据所有权耦合,下游容易反向绑定或改写核心模型。 | 不采用 | 正式边界不能被共享存储替代。 |
| 直接暴露核心 truth 给下游读取 | 省去读取承接层。 | 初期接入简单。 | 下游绑定核心结构,写读边界混层。 | 不采用 | 当前采用 truth 与只读消费材料分层。 |
| 同步等待所有下游确认方案 | 核心变化在同步入口内等待所有下游确认。 | 即时一致感强。 | 下游可用性反向决定本仓 truth。 | 不采用 | 当前采用异步最终一致传播。 |
| 全量外围能力前置方案 | P0 同时纳入外围生态和高级策略能力。 | 初始能力更完整。 | 核心闭环被外围复杂度拖垮。 | 不采用为当前主线 | 外围增强保留演进位置。 |

#### 12.3 取舍说明

当前方案牺牲了初期简单性、即时全链成功感和外围能力完整性,换来定义 truth 稳定、下游消费边界清晰、跨仓传播不压垮同步入口、外部正文不入仓和后续演进可控。

| 检查项 | 结论 | 说明 |

## 1. 与 `product/` 的关系声明

L4-archive 是**架构反推型**需求仓。它不是终端用户产品,但它承担平台长期可审计、可恢复、可冷存的底线能力。

| 章节 | 本文来源 | 对应文档 |
|---|---|---|
| 背景与问题 | `product/六域模型.md` 归档与横切语义 + `SEGMENT-2-COMPLETE.md` 段 3 入口 | product / architecture |
| 功能需求 | ArchiveBundle / Restore / ComplianceDeclaration | README + 各域 slice 需求 |
| 非功能需求 | 长期保留 / 冷存 / 恢复时长 | README 性能条目 |

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的项目不会永远处于 active。项目会:
- archived(只读,可恢复)
- dissolved(解散,不可恢复)
- 满足长期保留 / 合规存证要求

L4-archive 的任务是把跨六域的数据打成**ArchiveBundle**,并保证:
- hot / warm / cold 分层
- Conformance Claim / SoA / AIIA 一起归档
- 后续可恢复(project.restored)
- 哈希与签名保证包不被篡改

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点 |
|---|---|---|
| 设计文档 | 只有仓 README 骨架,无仓级需求样板 | 归档边界未被系统化定义 |
| six-domain slices | 在 README 中口头定义 | 还没有仓级验收口径 |
| Restore 语义 | 已在 work / process 中提过 | 没有统一归档中心 |
| 长期保留 | 42001 / 9001 / 24748-2 要求存在 | 冷存与取回策略未成型 |

### 2.3 为什么要做(量化依据)

- 没有 archive,所有"合规完成后的长期保留"都只能分散在各仓
- project.archived / dissolved 没有真正的落点
- README 目标明确:500 WorkItem / 10 Baseline 的大项目归档 < 5 分钟,Restore 小项目 < 2 分钟

### 2.4 业务问题 vs 技术问题

- **业务问题**:如何长期保留一个项目的全部可审计事实,并在必要时恢复
- **技术问题**:六域切片打包、冷存、Restore、签名/哈希、防篡改、跨版本兼容

## 3. 目标与非目标

### 3.1 目标(可验证)

| ID | 目标 | 验收指标 | 验收方式 |
|---|---|---|---|
| G-1 | ArchiveBundle 包含六域切片 | 6/6 | 集成测试 |
| G-2 | 大项目归档耗时 | < 5 分钟 | benchmark |
| G-3 | 小项目恢复耗时 | < 2 分钟 | benchmark |
| G-4 | 归档包签名+哈希有效 | 100% | 校验测试 |
| G-5 | Conformance Claim 可生成 | 100% | 集成测试 |

### 3.2 非目标(明确不做)

| ID | 非目标 | 原因 | 归属 |
|---|---|---|---|
| NG-1 | **业务执行恢复到运行时中间态**(超细粒度 replay) | 只恢复项目可运行骨架 | process / runtime 后续协作 |
| NG-2 | **替代 observability 冷存** | archive 关注 bundle,observability 仍保留自己的链 |
| NG-3 | **替代 artifact 主存** | 只封装归档结果,不成为主存 |
| NG-4 | **删除合规历史** | 合规要求长期保留 |

## 5. 核心用例与用户故事

### 5.1 核心用例

1. archived 项目打包成 ArchiveBundle
2. dissolved 项目走不可恢复归档
3. 生成 Conformance Claim / ComplianceDeclaration
4. 从归档包恢复小项目
5. 按 retention policy 迁移 hot → warm → cold

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **Owner**,我想要 **在项目归档时自动打包六域数据**,以便 **后续可以审计与恢复** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个 archived 项目 **When** 执行 ArchiveProject **Then** 生成包含六域切片的 ArchiveBundle |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **Auditor**,我想要 **在归档包中看到 SoA / AIIA / Conformance Claim**,以便 **证明项目合规完成** |
| 优先级 | P0 |
| 验收条件 | **Given** 某项目已 archive **When** 查看 bundle manifest **Then** 必含 SoA / AIIA / ComplianceDeclaration |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **Admin**,我想要 **把 archived 项目恢复到 active**,以便 **继续推进项目** |
| 优先级 | P1 |
| 验收条件 | **Given** archived 项目 **When** RestoreProject **Then** 2 分钟内恢复小项目骨架 + 发 `project.restored` |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **系统**,我想要 **按保留策略自动把老数据迁入冷存**,以便 **满足 7 年保留又控制热存成本** |
| 优先级 | P1 |
| 验收条件 | **Given** 数据超过热存窗口 **When** retention job 跑 **Then** 数据迁入 cold 且 metadata 仍可查 |

### 5.3 辅助流程

- dissolve 场景不可恢复
- restore 只支持 archived,不支持 dissolved
- 冷存回查先读 metadata,再按需拉取 blob

### 6.1 功能清单与优先级

| ID | 功能名称 | 优先级 | 依赖 | 描述 |
|---|---|---|---|---|
| F-001 | ArchiveBundle 组装 | P0 | 六域读取接口 | 六域切片打包 |
| F-002 | slice 收集器 | P0 | L1 六域 | identity/work/conversation/process/governance/artifact/observability |
| F-003 | ComplianceDeclaration / Conformance Claim | P0 | governance / artifact | 24748-2 + 42001 |
| F-004 | 签名 + 哈希 | P0 | object storage | 防篡改 |

| F-006 | Restore | P1 | work / process / conversation / artifact | archived → active |
| F-007 | retention policy 执行 | P1 | governance policy | 到期自动迁移 / 处理 |

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| BR-001 | project.archived | 可打包 / 可恢复 |

| BR-005 | archived → restore | 必须走 restore 链路,不能手工改状态 |
| BR-006 | 冷存到期策略 | 按 governance.RetentionPolicy 执行 |

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 类型 | 生命周期 |
|---|---|---|
| ArchiveBundle | 聚合根 | created → sealed → cold |
| Slice | 值对象 / 子结构 | 打包内嵌 |
| RestoreJob | 聚合 / 过程记录 | requested → running → done / failed |
| RetentionSchedule | 规则记录 | active / expired |

### 9.2 数据关系

```
ArchiveBundle
  ├─ identity slice
  ├─ work slice
  ├─ conversation slice
  ├─ process slice
  ├─ governance slice
  ├─ artifact slice
  └─ observability slice(summary)
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| hot bundles | 热存窗口内 | object storage hot tier |
| warm bundles | 近 1 年 | warm tier |
| cold bundles | 7 年+ | cold tier | 按 policy 到期 |
| restore logs | 长期 | metadata 保留 |

## 11. 验收标准

### 11.1 功能验收标准

| 功能 ID | 验收场景 | Given-When-Then | 执行方式 |
|---|---|---|---|
| F-001/F-002 | 归档打包 | **Given** archived 项目 **When** 执行 archive **Then** bundle 含 6+1 slice |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| bundle 缺 slice | 中 | 高 | 打包前 completeness 校验 |
| restore 跨版本兼容 | 中 | 高 | versioned bundle schema |
| cold storage 取回慢 | 中 | 中 | metadata 热存 + 预热 |

### 12.2 边缘风险

- GDPR 删除与永久保留冲突
- 大项目恢复超 2 分钟
- 老 bundle 在新系统无法恢复

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 冷存选型(Glacier / 自建) | L4 前 | archive + SRE |
| Restore 时间窗口限制 | L4 前 | archive + work |
| 物理删除 vs 永久保留平衡 | L4 前 | archive + governance + legal |

## 1. 业务背景与驱动力

### 1.1 业务背景

archive 不是简单的对象存储包装。它承担的是**项目生命周期的长期收口**:
- 项目 archived / dissolved 时,把六域事实打成可审计 bundle
- 把 SoA / AIIA / Conformance Claim 一起冻结
- 在需要时可恢复 archived 项目
- 满足长期保留和冷存成本控制

### 1.2 业务驱动力

**业务驱动力**:
- 平台必须能长期保留完整项目事实
- 审计和合规需要 bundle 级证据而不是散落在各仓的数据
- archived 与 dissolved 的差异必须被系统承载

**技术驱动力**:
- 六域切片组装
- 热 / 温 / 冷分层
- Restore 逆向重建
- 哈希 / 签名防篡改

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | 归档大项目 | < 5 分钟 | benchmark |
| 性能 | Restore 小项目 | < 2 分钟 | benchmark |
| 完整性 | six-domain slice 覆盖率 | 100% | 集成测试 |
| 安全 | bundle 校验通过率 | 100% | hash/signature test |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| ArchiveBundle 必含六域切片 + SoA + Conformance Claim | AV1 | completeness 校验固定 |
| bundle 必须签名 + 哈希 | AV2 | 输出格式受约束 |
| Restore 只支持 archived,不支持 dissolved | 业务规则 | 生命周期边界固定 |
| 不丢 reasoning trace | AV5 | observability slice 必须保留 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| 冷存介质 | S3 / MinIO / Glacier 候选 | 可后续切换 |
| retention period | 默认 7 年 | governance / legal 可调 |
| restore 粒度 | 小项目全量恢复 | 可演进更细粒度 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| 大项目打包 | 500 WorkItem / 10 Baseline | README |
| Restore 小项目 | < 2 分钟 | README |
| 冷存迁移 | 月批处理 | README |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 六域数据模型演进 | 中 | bundle versioned schema |
| 冷存介质切换 | 中 | storage adapter |
| retention policy 变化 | 中 | policy-driven scheduler |
| restore 策略细化 | 中 | restore pipeline 抽象 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **bundle-first + slices + restore pipeline**(当前)| 结构清晰,跨域事实可打包 | 实现复杂 | ✅ |
| 各仓各自归档 | 简单 | 无全局 bundle / 合规证据散裂 | ❌ |
| 纯 DB snapshot | 快 | 不可读 / 跨版本恢复难 | ⚠️ 不够产品化 |

**最终选择**:**六域切片 + bundle manifest + versioned restore pipeline**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| six-domain slice 完整性 | 归档可审计 | 打包前要读多仓数据 |
| versioned bundle schema | 跨版本恢复可能性 | schema 管理复杂 |
| 冷存分层 | 降低热存成本 | 检索与 restore 复杂度提升 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
project lifecycle events
        │
        ▼
   ★ quantalithos-archive ★
   - bundle assembly
   - retention
   - restore
        │
   ┌────┼─────────────┬──────────────┬──────────────┐
   ▼    ▼             ▼              ▼              ▼
 work  process     governance      artifact       observability
 state slices      instance slices compliance     asset slices  audit summary
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ ArchiveBundle 组装
- ✅ slice collectors
- ✅ Conformance Claim / ComplianceDeclaration bundle
- ✅ retention policy 执行
- ✅ Restore 逆向重建

**不做什么**:
- ❌ 业务主数据源(各 L1 仓仍是源)
- ❌ observability append-only 主存
- ❌ artifact 正文主存
- ❌ governance 决策逻辑

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| object storage | 99.9% | 延迟迁移 / 暂存热层 |
| 各 L1 仓读 API | 99.9% | 缺 slice 则归档失败 |
| observability summary | 99.9% | 摘要可后补 |

### 4.4 关键依赖风险

- 六域数据拉取顺序 / 时点不一致
- 大 bundle 校验耗时高
- 跨版本 restore 失败

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
archive-api / operator
      │
      ▼
application
  ├─ bundle assembly
  ├─ slice collectors
  ├─ compliance bundle builder
  ├─ retention executor
  └─ restore pipeline
      │
      ├─▶ PostgreSQL(bundle index / schedules)
      ├─▶ object storage(hot / warm / cold)
      ├─▶ bus(outbox)
      └─▶ six-domain readers
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| archive-api | 归档 / restore API | Rust |
| bundle-builder | 六域切片组装 | Rust |
| retention-worker | 热温冷迁移 | Rust |
| restore-worker | 恢复流程 | Rust |
| postgres | bundle index / schedule / restore logs | PostgreSQL |
| object storage | archive bundle blob | S3 / MinIO / Glacier |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| 六域数据拉取 | RPC / query | 只读收集 |
| 归档完成通知 | 事件 | 下游解耦 |
| 恢复完成通知 | 事件 | work/process/conversation 同步 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| bundle metadata | archive | archive / console / audit |
| bundle blob | archive | archive / auditors / restore |
| retention schedule | archive | retention worker |
| restore logs | archive | SRE / auditors |

### 6.5 部署拓扑

- archive 服务 + PG + object storage 起步
- retention / restore worker 可内嵌或分离
- cold store 后端可替换

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api
 │
 ▼
application
 │
 ▼
domain(Bundle / Slices / Retention / Restore)
 ▲
 │ ports
infra(Postgres / object storage / bus / domain readers)
```

### 7.2 层间约束规则

- archive 不成为任何 L1 仓的写入源(restore 除外,且通过正式恢复流程)
- slice collectors 只读各域,不改各域主数据
- bundle manifest 是 archive 的单一真相源
- restore 只能针对 archived,不允许恢复 dissolved

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| SliceReader | application/domain | 各域 adapter |
| BundleStore | domain | object storage |
| RetentionPolicySource | application | governance / local config |
| RestoreOrchestrator | application | restore worker |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(work / console / governance / audit) |
| 传出耦合 | 高(六域 + storage + pg + bus) |
| 不稳定性 | 中高 |
| 抽象度 | 中 |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| bundle metadata | archive | console / auditors | 强一致 |
| bundle blob | archive | restore / auditors | object storage 最终一致 |
| retention schedules | archive | retention worker | 强一致 |
| restored project plan | archive → work/process/... | 事件最终一致 |

### 8.2 一致性层次

- bundle metadata / schedule / restore log 强一致
- 各 slice 收集时跨域最终一致(按归档时点快照)
- restore 跨域重建最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| 某 slice 拉取失败 | 整体归档失败,不生成半包 |
| blob 写入成功但 metadata 写失败 | orphan blob 清理任务 |
| restore 中途失败 | 标记 failed,不半活跃化 project |

## 9. 关键技术选型

### 9.1 object storage 分层

| 维度 | 内容 |
|---|---|
| 当前选择 | hot / warm / cold tier on S3-compatible storage |
| 备选方案 | 单一桶 / 本地文件系统 / 磁带库 |
| 选择理由 | 保留期与成本平衡 |
| 演进路径 | Glacier / Tape 后置 |
| 不可逆程度 | 中 |

### 9.2 bundle-first

| 维度 | 内容 |
|---|---|
| 当前选择 | Bundle + manifest + signatures |
| 备选方案 | 各仓自己归档 |
| 选择理由 | 合规与恢复都需要全局包 |
| 演进路径 | versioned schema |
| 不可逆程度 | 中高 |

### 9.3 Restore pipeline

| 维度 | 内容 |
|---|---|
| 当前选择 | archive orchestrates restore |
| 备选方案 | 各域自恢复 |
| 选择理由 | 入口统一、可审计 |
| 演进路径 | 小项目自动恢复,大项目半自动 |
| 不可逆程度 | 中 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| bundle schema versioning 未定 | 跨版本 restore | P1 |
| cold store 选型未定 | 成本 / 合规 | P1 |
| GDPR delete 与 baseline pin 冲突未解 | 合规边界 | P1 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| archive build > 5min | 持续 1 周 | 优化 slice pipeline / parallelism |
| restore > 2min | 持续 3 次 | 优化 restore pipeline |
| cold backlog | > 阈值 | 扩 tier worker |

### 12.3 演进步骤

```
阶段 1: Bundle + metadata + restore baseline
阶段 2: hot/warm/cold retention
阶段 3: versioned bundle schema / compatibility adapters
阶段 4: deep compliance retention & deletion policy
```

### 12.4 目标架构

archive 的目标是:
- 成为项目生命周期的最终收口点
- 让“归档”和“恢复”成为平台的一等能力
- 以 bundle 形式固定全局事实,而不是散落在六域里各自处理

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |

## 14. 上线策略

### 14.1 灰度方案

- 样本 archived 项目 1 个
- 样本 restore 项目 1 个
- 先不接 dissolved restore(明确禁止)

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚 |
|---|---|---|
| bundle manifest 错误 | S | 停止发布,删除坏包,重建 |
| restore 失败 | A | 标记 failed,不恢复 project |
| retention 误迁移 | A | 保持热存副本 |

### 14.3 监控指标

| 指标 | 阈值 | 告警 |
|---|---|---|
| archive build time | > 5min | warning |
| restore time | > 2min | warning |
| missing slice | > 0 | critical |
| cold backlog | > 阈值 | major |

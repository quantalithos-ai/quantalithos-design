## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L4-archive` 不是 artifact 真相仓,也不是 observability 主汇聚仓,更不是单纯的对象存储目录。它是 **“历史保留、归档沉淀与冷存追溯层”**。

你可以把它理解成:
- 哪些正式对象、执行材料、审计证据、结果物化材料要进入长期归档
- 热数据与冷数据怎样分层
- 归档后的快照怎样保持可检索、可引用、可追溯、可回放
- 法务、治理、复盘、审计时怎样从 archive 层拿到可信历史材料
- 某些材料何时被保留、何时进入 legal hold、何时允许清理

这些事情,都由 `L4-archive` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L4-archive`,这些历史沉淀事实就会散落在:
- `artifact` 自己保留的活跃对象与附件里
- `sandbox` 临时输出目录和残留文件里
- `observability` 的实时或中期观测材料里
- `governance` / `method-library` / `capability-hub` 各自的局部历史记录里
- 各种对象存储桶、备份目录和手工导出包里

结果就会出现:
- 平台到底“哪些历史材料已经正式归档”没有统一真相源
- 活跃对象、冷存对象、证据包、审计导出包彼此混层
- 归档后材料可能存在,但不可检索、不可对账、不可恢复
- legal hold、retention class、销毁边界无法被统一治理
- 复盘、审计、法务、长期分析会反复回到源仓拼数据

所以 `L4-archive` 必须独立存在,作为:
> **把平台正式对象、执行材料、审计证据和结果快照转入长期可信、可检索、可追溯、可恢复的历史沉淀层。**

### 1.3 新人最容易混淆的几个词

#### ArchivedSnapshot
就是:
> 某个源对象在某个时点进入归档时被冻结下来的正式快照。

它不是当前 source truth 本体。

#### ArchiveRecord
就是:
> 一条正式归档记录,描述某个对象/证据/材料已经进入 archive 层。

它不是源仓对象本体。

#### ArchiveIndex
就是:
> 归档材料的检索和定位入口。

它不是业务主索引,也不是实时查询主仓。

#### RetentionClass
就是:
> 一类归档材料的保留等级和保留周期分类。

它不是 governance policy 真相本体。

#### LegalHold
就是:
> 某类材料因法务/审计/事故调查被强制保留、暂不可删除的约束状态。

它不是普通的“长期不删”标签。

#### RestoreRequest
就是:
> 为了取证、复盘、导出或恢复材料而发起的正式取回请求。

它不等于 source system rollback,也不等于业务重新激活。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L4-archive/02` 时,先收稳以下前提:
- `L4-archive` 不应按 storage / index / restore / delete 技术动作平铺理解,而应按归档沉淀主链责任拆
- archive 至少应拆成“归档对象接入与快照固化 / 归档索引与检索定位 / 保留策略、分层存储与 legal hold / 恢复、导出与审计取证 / 历史观察与长期复盘出口”五个主要部分
- archive 自己拥有的真相不是 artifact 活跃对象、observability 实时事件流或各业务仓活跃真相,而是 archive snapshot / archive record / retention / restore 这类归档层真相
- `L4-archive` 只能沉淀 source truth 的历史快照和证据副本,不能反过来替代这些 source systems 的当前真相
- 02 的重点不是“列有哪些存储桶或目录”,而是先把“归档沉淀层在平台里到底是什么、和 artifact/observability/sandbox/governance/method-library/capability-hub 怎么分层”讲清楚
- cold query、retention、legal hold、restore、evidence export 这些不是零散机制,而是 archive 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的历史沉淀与冷存追溯心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,平台不仅要运行当前系统,还要保住历史。用户真正需要的不是“旧数据别删”,而是:
- 哪些正式对象、执行证据、输出材料、审计记录应进入长期可信归档
- 热路径和冷路径怎样分离
- 被归档材料怎样支持长期检索、对账、追溯、法务导出和事故复盘
- 归档后材料怎样根据 retention class、legal hold、destroy guard 被持续治理
- 从 archive 恢复材料时怎样不污染 source truth,又能支持复盘、取证和重放

如果把这些逻辑分别散落到:
- `artifact` 自己的活跃对象存储
- `observability` 的实时/短期事件存储
- `sandbox` 的临时输出目录
- 各个业务仓的局部历史表和对象桶

系统会快速退化成:
- 活跃数据和冷存数据混层
- 某些材料“存在”,但没人知道它是不是正式归档版
- legal hold 与 retention 执行边界不清
- 恢复和导出依赖手工脚本
- 长期复盘和审计要跨多个仓拼接材料

因此,本概要设计的任务就是:
> **把 `L4-archive` 写成一个新人也能看懂的“历史保留、归档沉淀与冷存追溯层”,而不是把对象存储、索引、导出和清理混在一起。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 正式归档主线 | 多仓局部历史散落 | 统一 archive 主线 | 需正式收敛 |
| cold query 能力 | 依赖源仓和脚本 | 统一 archive query 入口 | 需建立检索面 |
| retention / legal hold | 分散 | 正式化治理 | 需形成治理链 |
| 恢复与取证 | 手工脚本为主 | 正式 restore/export 流程 | 需收稳控制口径 |
| 历史复盘可追溯性 | 依赖人工拼接 | 100% 证据链可回放 | 需固定证据主线 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把正式对象、执行材料、审计证据和结果快照长期可信地沉淀下来,以服务审计、法务、复盘和长期治理
- **技术问题**:ArchivedSnapshot、ArchiveRecord、ArchiveIndex、RetentionClass、LegalHold、RestoreRequest 与 artifact / observability / sandbox / governance / method-library / capability-hub 等系统之间的边界如何稳定建模,并形成统一归档主链

- 不在本文替代业务系统回滚逻辑

## 4. 约束条件

### 4.1 技术约束

- 所有正式归档都必须以 ArchivedSnapshot / ArchiveRecord 形式进入主线
- archive copy 只能冻结 source truth 某一时点的副本,不能反向替代 active source truth
- 冷存检索必须通过 archive index / timeline / refs 统一定位,不得依赖源仓实时查询
- retention / purge / legal hold 必须显式规则化,不得散落在脚本里
- restore/export 只能恢复材料和证据,不得直接改写 source truth

### 4.2 资源约束

- 归档数据会长期增长,必须接受多层冷热存储与索引分离
- 历史检索不能拖垮主业务查询面,archive 查询复杂度必须受控
- 大对象、附件、导出包、证据包不能长期堆在热存储层

### 4.3 时间约束

- 当前阶段先收稳统一 archive 主链,而不是先做复杂跨区域冷备与高级历史分析
- snapshot、index、retention、restore、historical review 五条主线必须优先稳定,否则 archive 无法形成正式平台能力

### 4.4 合规约束

- legal hold 材料不得被误删
- retention 执行必须有审计证据链
- restore/export 必须可追溯,不得匿名或无票据执行
- observation retention 与 artifact retention 必须分离配置

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| archived records/day | 高 | 多仓历史材料汇入 |
| cold objects | 高 | 附件 / 证据 / 快照长期保留 |
| archive queries | 中高 | 审计 / 复盘 / 历史检索需求 |
| restore/export jobs | 中 | 法务/复盘/事故恢复需求 |

```text
                    ┌────────────────────────────┐

                                 ▼
                    ┌────────────────────────────┐
                    │ L4-archive                 │
                    │ - snapshot / index         │
                    │ - retention / restore      │
                    │ - evidence export          │
                    └────────────┬───────────────┘
                                 │ cold query / restore / evidence pack
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ audit / legal / governance │   │ operators / TL / owners    │   │ console / backoffice       │
│ - evidence / hold / export │   │ - review / replay / RCA    │   │ - historical query         │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L4-archive` 自己负责历史快照固化、归档索引、保留治理、恢复/导出和长期复盘出口
- artifact / sandbox / observability / governance / method-library / capability-hub / runtime 等系统是历史材料来源方,但 archive 不拥有它们的活跃真相
- audit / legal / governance / operators / TL / owners / console 是 archive 的历史消费方
- 这个仓的角色不是“决定当前系统状态”,而是“保住过去某个状态及其证据链”

所以 `L4-archive` 在全局里的角色是:
> **把平台正式对象、执行材料、审计证据和结果快照统一沉淀为长期可信、可检索、可恢复、可取证的历史层。**

### 5.3 系统边界

**做什么**:
- 固化 ArchivedSnapshot / ArchiveRecord
- 建 ArchiveIndex / timeline / refs
- 执行 retention / tiering / legal hold
- 提供 restore / export / evidence package
- 提供 historical query / review / replay 输入出口

**不做什么**:
- 不替 source systems 持有活跃真相
- 不承担实时业务查询主路径
- 不直接执行业务回滚或重新激活
- 不替代对象存储 / 备份平台本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| artifact / sandbox / observability / source systems | 99.9% | 来源短暂失联时保留现有 archive index,标记 source gap |
| object / cold storage | 99.9% | 元数据和索引先写热层,冷对象延迟入库但不得丢失引用 |
| query / index engine | 99.9% | 降级到 cached archive index / limited query |
| export / restore worker | 99.9% | backlog / retry,但保留 restore/export ticket |
| legal hold control | 99.9% | hold 状态优先于 purge,宁可延迟清理 |

### 5.5 关键依赖风险

- archive copy 与 source truth 漂移会让恢复和审计误判
- archive index 若不能稳定定位对象,归档会退化成“存在但不可用”
- retention / legal hold 规则错误会造成误删或无限保留
- restore/export 如果无正式 ticket 和 evidence chain,会破坏审计可信性
- cold query 若被当实时主查询面,会拖慢历史层并污染业务边界

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把 storage / index / restore / delete 技术动作横向平铺。  
> 它按 **历史沉淀主链职责 + 快照 / 检索 / 保留 / 取证 / 复盘差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象和机制,共同支撑同一段 archive 主链。

#### 归档对象接入与快照固化部分

- **它是什么**: 这是 `L4-archive` 的入口层,一起回答“哪些材料进入归档以及冻结什么”
- **为什么单独有它**: 归档最关键的是在进入 archive 时明确冻结边界,否则后续 restore、检索、legal hold 都没有共同基线
- **负责什么**:
  - 接收 archive request
  - 固化 source snapshot
  - 建立 digest / chain of custody
  - 形成 ArchiveRecord / ArchivedSnapshot
- **不负责什么 / 容易混淆点**:
  - 不替代 source truth 当前状态迁移
  - 不负责历史检索出口本体
  - 不负责 legal hold 规则本体
  - 最容易和 artifact 活跃对象、source state transition、备份快照混淆
- **与其他部分交互**:
  - 下游: archive index / retention / restore / historical review
  - 外部: artifact / sandbox / observability / governance / source systems
  - 交互类型: snapshot 固化型 + 证据锚点型
- **后续详细设计展开点**:
  - ArchivedSnapshot / ArchiveRecord 模型
  - digest / custody 主线

#### 归档索引与检索定位部分

- **它是什么**: 这是 archive 的历史检索层,一起回答“归档后怎样还能被找到和定位”
- **为什么单独有它**: 归档如果只有对象存储没有稳定索引,未来就无法支撑审计、复盘和恢复
- **负责什么**:
  - 建立 ArchiveIndex / lookup keys / timeline refs
  - 形成 cold query 入口
  - 支持 archive 查询、定位、跳转 source refs
- **不负责什么 / 容易混淆点**:
  - 不替代业务主索引
  - 不承担实时查询主路径
  - 不等于 observability dashboard 本体
  - 最容易和 primary business index、operational query store、活跃列表页混淆
- **与其他部分交互**:
  - 上游: 归档对象接入与快照固化部分
  - 下游: restore/export、历史观察与长期复盘出口
  - 交互类型: 检索定位型 + 冷查询型
- **后续详细设计展开点**:
  - ArchiveIndex / timeline / ref lookup 模型
  - historical query contract

#### 保留策略、分层存储与 legal hold 部分

- **它是什么**: 这是 archive 的生命周期治理层,一起回答“归档后放哪里、留多久、何时冻结删”
- **为什么单独有它**: archive 不是一存了之,必须持续治理 retention、tiering、expiration、hold,不单列就会走向“永不删”或“乱清理”
- **负责什么**:
  - 定义 RetentionClass
  - 管理 hot/warm/cold tiering
  - 管理 expiration / purge eligibility / legal hold / destruction guard
- **不负责什么 / 容易混淆点**:
  - 不等于 governance policy 真相本体
  - 不直接决定 source truth 保留策略
  - 不负责 restore/export 请求本体
  - 最容易和 storage lifecycle、本地清理脚本、artifact retention 混淆
- **与其他部分交互**:
  - 上游: 归档对象接入与快照固化部分、governance 输入
  - 下游: 恢复/导出、历史观察与复盘出口
  - 交互类型: retention 治理型 + hold 保护型
- **后续详细设计展开点**:
  - retention class / legal hold 状态机
  - tiering / purge guard 主线

#### 恢复、导出与审计取证部分

- **它是什么**: 这是 archive 的取回与取证层,一起回答“归档材料怎样被取回和取证”
- **为什么单独有它**: archive 的核心价值之一是未来能拿回来做复盘、法务、审计。如果不单列,恢复与导出会散到各仓和脚本中
- **负责什么**:
  - 管理 RestoreRequest / ExportRequest / EvidencePackage
  - 管理 replay input material / audit/legal export
  - 记录 restore/export ticket 与链路证据
- **不负责什么 / 容易混淆点**:
  - 不直接回滚 source system
  - 不重新激活业务对象
  - 不替代 source system 的恢复逻辑
  - 最容易和 rollback、业务恢复、人工复制文件混淆
- **与其他部分交互**:
  - 上游: archive index / retention / snapshot
  - 下游: audit / legal / operators / RCA
  - 交互类型: 取证恢复型 + 导出包型
- **后续详细设计展开点**:
  - restore/export ticket
  - evidence package / replay input 主线

#### 历史观察与长期复盘出口部分

- **它是什么**: 这是 archive 的长期消费面层,一起回答“人和系统怎样消费历史沉淀材料”
- **为什么单独有它**: archive 的价值不只在存和取,还在于支持长期复盘、跨周期对账和历史分析。若不单列,archive 会退化成死存储
- **负责什么**:
  - 提供 historical query / timeline / evidence pack
  - 提供 incident/postmortem / RCA 取材出口
  - 提供长期趋势、跨周期历史观察补充面
- **不负责什么 / 容易混淆点**:
  - 不替代 observability 实时 dashboard
  - 不替代活跃业务查询界面
  - 不直接修改 archive 主记录
  - 最容易和 live dashboard、BI 工具、审计命令执行器混淆
- **与其他部分交互**:
  - 上游: archive index / restore/export / retention
  - 下游: operators / audit / legal / owners / backoffice
  - 交互类型: 冷查询消费型 + 长期复盘型
- **后续详细设计展开点**:
  - historical review views
  - RCA / evidence timeline

```text

│ - evidence / hold / export │   │ - review / replay / RCA    │   │ - historical query         │
```

### 7.2 总解释

- `L4-archive` 自己负责“冻结归档快照”“建立历史索引”“执行 retention/hold”“输出 restore/export 证据包”“提供长期复盘查询面”
- `artifact` / `sandbox` / `observability` 的交互主要落在 **归档对象接入与快照固化部分** 与 **归档索引与检索定位部分**,把正式结果物、执行证据和观测切片沉淀到 archive
- `governance` 的交互主要落在 **保留策略、分层存储与 legal hold 部分** 与 **恢复、导出与审计取证部分**,为 archive 提供 retention / hold / export 规则输入
- `method-library` / `capability-hub` / `runtime` / `process` / `conversation` 的交互主要落在 **归档对象接入与快照固化部分** 与 **历史观察与长期复盘出口部分**,提供历史快照来源或消费历史复盘结果
- audit / legal / operators / owners / console 的交互主要落在 **恢复、导出与审计取证部分** 与 **历史观察与长期复盘出口部分**,消费冷查询、证据包、timeline 和 RCA 视图

### 7.3 分模块交互说明(逐个写)

#### 与 `artifact / sandbox / observability` 的交互


  - archive 不接管这些系统的活跃真相

  - 活跃对象和归档快照漂移或回写混层

  - archive 保存它们的历史材料
  - archive 为后续 replay / review / RCA 提供冷材料出口
  - archive 不直接回滚或激活源系统

  - 历史查询直接被当实时主查询通道使用

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是历史沉淀层、哪个模块是规则输入方、哪个模块是冷查询消费方

本节**不**展开:
- 对象存储 / 冷存引擎实现细节
- digest / hash 算法细节
- query / export worker 的低层实现

这些内容留到 `03-详细设计.md` 中继续展开。

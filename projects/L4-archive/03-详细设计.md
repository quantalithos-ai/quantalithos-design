## 1. 模块职责描述

**本模块做什么**:
- 持有正式 ArchivedSnapshot / ArchiveRecord / ArchiveIndex / RetentionClass / LegalHold / RestoreRequest / EvidencePackage 等 archive 层真相
- 把 artifact、sandbox、observability、governance、method-library、capability-hub、runtime 等来源材料冻结成可检索、可追溯、可恢复的历史快照
- 管理 retention / tiering / legal hold / purge guard 规则与执行证据链
- 为 audit / legal / operators / owners / console 提供 cold query、restore/export、RCA / evidence timeline 出口

**本模块不做什么**:
- 不持有各 source systems 的活跃真相
- 不承担实时业务查询主路径
- 不直接执行业务回滚或重新激活
- 不替代对象存储、备份平台、artifact retention 或 observability 实时流本体

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 archive“为什么存在”,而是让开发者可以直接开始实现:
- 多仓 source 材料怎样进入正式 archive request 与 snapshot freeze 主线
- ArchiveIndex 怎样在冷数据层仍保持可检索、可引用、可 timeline 化定位
- retention / legal hold / purge guard 怎样持续治理 archive 生命周期
- restore / export / evidence package 怎样在不回滚 source truth 的前提下满足审计、法务、复盘需求
- cold query / RCA / long-range review 怎样成为长期消费面而不是实时主查询通道

如果不先把这些内容采集清楚,03 很容易退化成:
- 对象存储目录结构说明书
- 备份脚本或归档批处理说明
- restore/export worker 的零散命令笔记
- snapshot、index、hold、restore、review 各写一套,彼此脱节

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 artifact / sandbox / observability / governance / source systems
- 哪些输出给 audit / legal / operators / owners / console
- 哪些 hold / purge / restore 动作必须在 ticket / approval / rule 校验通过后才能继续
- 哪些 query/export/restore 只能消费冷材料而不能反向活化 source truth

#### 第 5 步:列出最小测试输入

必须测:
- archived snapshot ≠ active source truth
- archive request ≠ source state transition
- archive index ≠ primary business index
- cold query ≠ operational query
- restored material ≠ source system rollback

- snapshot / index / retention / restore / review 五条主链成立

### 4.1 总流程图


### 4.2 总解释

- **真相写入**发生在: ArchivedSnapshot、ArchiveRecord、ArchiveIndex、LegalHold、RestoreTicket、EvidencePackage 的正式持久化
- **快照固化**发生在: source material 进入 archive request、digest 生成、custody chain 建立
- **保留治理**发生在: retention class 应用、tiering、hold、purge eligibility 判定
- **正式留痕**发生在: custody chain history、retention history、restore/export history、purge history 的 append-only 记录
- **只读输出**发生在: archive query、timeline、evidence pack、historical review、long-range trend 的视图生成
- **同步路径**主要是: FreezeSnapshot / BuildArchiveIndex / ApplyLegalHold / CreateRestoreTicket 主写链
- **异步最终一致**主要是: cold tier materialization、long-range trend、historical query view、部分 export pack 组装和 replay compare

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `ArchivedSnapshot / ArchiveIndex / LegalHold / RestoreRequest` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 archive 主链,`03` 却退化成对象存储、搜索、脚本、导出命令的技术清单
- 实现者知道有 restore/export,却不知道它如何与 retention、snapshot、timeline 构成同一条主线
- 快照、索引、hold、review 各写一套,彼此断裂

#### 5.2.4 关键函数代码片段

```rust
/// 根据来源材料冻结一个正式归档快照。
fn freeze_archived_snapshot(
    snapshot_repo: &dyn ArchiveSnapshotRepo,
    request: ArchiveRequest,
    material: SourceArchiveMaterial,
) {
    // [request.校验归档输入]
    // 先确认 source ref 和 archive request 都已正式建立。
    request.validate_archive_request();

    // [ArchivedSnapshot::从来源材料冻结]
    // 再把来源材料收束成只读归档快照,并生成 digest。
    let snapshot = ArchivedSnapshot::freeze(material, request);

    // [snapshot_repo.保存快照与归档记录]
    // 最后把快照、归档记录和 custody entry 写入 archive 主线。
    snapshot_repo.save_snapshot(snapshot);
}
```

这段实现守住的边界是:
- archive 只冻结来源副本,不回写 source truth
- digest 与 custody chain 必须在归档时同步建立
- snapshot 成立后,后续索引、hold、restore 才有共同基线

#### 5.2.5 该部分的边界与非职责
- 不负责 cold query 主路径
- 不负责 retention / legal hold 决策本体
- 不负责 restore / export 请求本体
- 不负责 source system 当前状态更新

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `归档索引与检索定位部分` 提供 archive record 和 snapshot 输入
- 向 `保留策略、分层存储与 legal hold 部分` 提供 retention class 作用对象输入
- 向 `恢复、导出与审计取证部分` 提供 frozen material 输入

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `Archived snapshot ≠ active source truth` 必须写死
- `archive request ≠ source state transition` 必须写死
- 若 digest / custody chain 迟于 snapshot 才建立,归档可信性会断裂

#### 5.3.4 关键函数代码片段

```rust
/// 为一个已固化的归档记录建立正式检索索引。
fn build_archive_index(
    index_repo: &dyn ArchiveIndexRepo,
    record: ArchiveRecord,
) {
    // [record.校验可索引]
    // 先确认归档记录已正式固化且可进入冷检索主线。
    record.validate_indexable_record();

    // [ArchiveIndex::从归档记录创建]
    // 再把记录和来源引用收束成正式 archive index。
    let index = ArchiveIndex::from_record(record);

    // [index_repo.保存索引]
    // 最后把索引写入冷检索层,供 query/restore/review 继续消费。
    index_repo.save_index(index);
}
```

这段实现守住的边界是:
- archive index 只服务历史定位,不替代业务主索引

```text
   │    [校验导出边界]
   ├─▶ [restore_repo.build_package_from_request()]
   │    [根据索引与规则定位材料]
   ├─▶ [restore_repo.save_evidence_package()]
   │    [保存证据包与票据]
   └─▶ [build_historical_timeline()]
        [进入长期复盘出口]
```

#### 写路径

```text

   │
   ▼

   │
   ▼
snapshot/index/lifecycle rules
   │
   ▼
persistence / export / audit history
```

#### 读路径

```text

   │
   ▼

   │
   ▼
```

#### 关键说明

- cold query、timeline、evidence pack、long-range trend 属于可最终一致读路径
- ArchiveQueryResult / HistoricalTimelineView 绝不能反向成为 source truth 或 archive 主记录写源
- restore/export/review 的分歧必须回收到 digest、custody、ticket 与 archive refs 对账主线

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| source material 不可归档 | 拒绝 archive request |
| snapshot digest 校验失败 | 阻断 archive record sealing |
| archive index 未就绪 | 阻断 restore/export/query 并标记 backlog |
| legal hold 生效后仍尝试 purge | 拒绝 purge 并留 hold conflict 证据 |
| export package 缺失部分材料 | 阻断导出并标 evidence incomplete |
| cold storage 延迟 | 保留索引与 ticket,等待对象层追平 |

### 11.1 重试 / 降级 / 熔断 / 补偿
- 冷对象入库失败时可 backlog + retry,但不得丢失 archive request / snapshot refs
- index / query 失败可降级到 cached archive index,但不能回到 source systems 做实时主查
- restore/export worker 失败可重试,但必须保留 ticket 与 attempt history

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 归档对象接入与快照固化部分 | snapshot 冻结不完整 / digest 失配 | archive request / digest validate | 拒绝 sealing | 补齐来源材料后重试 |
| 归档索引与检索定位部分 | index 缺 source refs / cold query 无法定位 | indexable record / query boundary validate | 阻断 query/restore | 重建索引 |
| 保留策略、分层存储与 legal hold 部分 | hold 与 purge 冲突 / tiering 丢索引 | retention / hold validate | 阻断 purge / 回退层级操作 | 重评估 / replay governance input |
| 恢复、导出与审计取证部分 | export 缺料 / restore 越权 | export boundary / evidence completeness validate | 拒绝导出/恢复 | 修复材料后重试 |
| 历史观察与长期复盘出口部分 | timeline 无法回指三层证据链 | historical query boundary / refs validate | 阻断视图输出 | 重建 review projection |

## 15. 结论

本详细设计的核心结论是：
- `L4-archive` 的实现主轴必须按 snapshot / index / retention / restore / review 五个主要部分组织,而不是按 storage/index/export/delete 技术动作平铺
- archive 真相层只持有归档快照、冷索引、保留治理、恢复票据和历史消费视图,不接管 artifact / observability / source systems 的活跃真相
- 所有 cold query、restore/export、RCA、legal hold 和 purge 都必须建立在正式 ArchivedSnapshot、ArchiveIndex、RetentionClass、ticket 与 custody evidence chain 之上

后续测试与验收文档,应直接围绕这套历史沉淀主链、冷查询边界、保留治理与取证恢复主线展开.

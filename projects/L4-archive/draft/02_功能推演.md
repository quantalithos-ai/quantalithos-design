# 02 · L4-archive 功能推演（draft）

> 状态：`draft / pre-calibration`，非正式设计真相源\
> 前置：`draft/01_项目作用与交互对象.md`\
> 本文回答：Archive 需要形成哪些外部可见能力闭环；归档、验证、存储、生命周期执行和恢复如何互相衔接；哪些输入缺失时必须保持 pending / blocked。\
> 不做：不锁 API/DTO、数据库、对象存储供应商、签名算法、密钥、压缩、保留期限、性能数字或跨域事务。

## 1. 核心能力闭环（候选）

Archive 的核心不是“把若干文件上传”，而是从一个有依据的请求开始，形成可验证包，再通过受控恢复交接把材料交给各真相 owner：

```text
[A1 受理归档请求与范围]
              |
              v
[A2 source snapshot/export + fence 收集]
              |
              v
[A3 slice binding + manifest/content closure]
              |
              v
[A4 integrity digest/signature verification]
              |
              v
[A5 storage placement + lifecycle state]
              |
              +------> [A6 query / verify / audit read]
              |
              v
[A7 restore request + package validation]
              |
              v
[A8 owner-specific restore material + handoff]
              |
              v
[A9 partial/conflict/unknown/compensation records]
```

| 节点 | 能力成立描述 | Archive 拥有 | 外部 owner / 接缝 | 缺失时上限 |
|---|---|---|---|---|
| `A1` | 接收带主体、范围、依据和幂等语境的归档请求 | request、作业、输入校验结果 | 项目状态、批准/授权 | `rejected` / `blocked` |
| `A2` | 按 source matrix 获取每个切片的 approved snapshot/export/ref，并记录 fence/version/coverage | source binding、capture attempt、缺口 | L1 owner query/export/snapshot | `partial` / `blocked` |
| `A3` | 对 manifest 声明的条目形成可计算内容闭包，避免遗漏或越界材料 | bundle、manifest、slice inventory、closure result | Artifact/Observability 等 source material | `incomplete` / `blocked` |
| `A4` | 对包、分片和签名/摘要引用执行完整性验证 | verification result、failure reason、history | digest/signature service、KMS/secret authority | `integrity-failed` / `pending` |
| `A5` | 将验证通过的包绑定到存储位置与层级，保留可取回状态 | location ref、tier state、migration job | 外部存储、取回/迁移服务 | `storage-pending` / `unavailable` |
| `A6` | 只读查询 manifest、来源、coverage、完整性、生命周期和审计材料 | archive index/read status | SDK、Console、Sync、Observability consumer | 不得回源冒充 operational query |
| `A7` | 接收恢复申请并验证包版本、完整性、授权与目标 owner | restore request、validation result、plan | governance/owner restore eligibility | `rejected` / `blocked` |
| `A8` | 为每个 owner 生成最小恢复材料并通过正式 handoff | material ref、handoff record、ack/outcome | owning domain import/restore/command/handoff | `partial` / `commit-unknown` |
| `A9` | 记录每项恢复结果、重试、补偿和未决冲突，不隐藏局部失败 | outcome、compensation/retry record | owner 的最终事实和状态 | `failed` / `conflicting` |

## 2. 候选功能清单

| ID | 功能 | 外部可见语义 | 关键边界 |
|---|---|---|---|
| `FR-AR-001` | 创建归档请求 | 声明主体、目标 scope、所需切片集合、依据和幂等语境 | 不改变项目生命周期，不把请求当批准 |
| `FR-AR-002` | 归档范围解析 | 固化 source-authority matrix 版本与请求范围 | 不把“六域”或 workspace 自动当必选集合 |
| `FR-AR-003` | source snapshot/export 收集 | 每个 source 单独记录 version/watermark/fence/coverage/material kind | no-write；不读取内部表或共享事务 |
| `FR-AR-004` | Bundle manifest 组装 | 声明 schema/version、切片、条目、来源绑定和闭包规则 | 不复制未授权正文；缺项不可静默补齐 |
| `FR-AR-005` | 内容闭包验证 | 检查 manifest 声明与实际内容/引用集合一致 | 缺失、越界、重复、冲突必须显式结果 |
| `FR-AR-006` | 完整性校验 | 记录 digest/signature verification 的状态和引用 | 不私造 digest、签名算法、密钥或成功状态 |
| `FR-AR-007` | sealing / immutable handoff | 仅在范围、闭包和完整性条件满足后形成不可变包状态 | sealed 不代表业务状态已归档 |
| `FR-AR-008` | 存储位置与层级管理 | 记录 hot/warm/cold 候选状态、迁移和取回状态 | 具体供应商、策略和 RTO pending |
| `FR-AR-009` | retention/hold/delete 接缝执行 | 消费正式 owner decision 并产生执行记录/阻断原因 | 不自行创建 policy、hold 或销毁授权 |
| `FR-AR-010` | manifest / package verification query | 只读返回 provenance、coverage、integrity、version compatibility | 不回源做 operational query，不泄露隐藏元数据 |
| `FR-AR-011` | 创建恢复申请与计划 | 校验目标 owner、包版本、授权和恢复范围 | 不直接把 bundle 写回上游数据库 |
| `FR-AR-012` | 恢复材料生成 | 按 owner 生成 source-specific material、引用和缺口 | workspace projection 不能升级为 canonical restore input |
| `FR-AR-013` | owner handoff | 通过正式 import/restore/command/handoff 接缝交接并记录 outcome | accepted / committed 由 owner 决定 |
| `FR-AR-014` | 恢复验证与补偿 | 表达 partial、stale、missing、conflicting、unsupported-version、integrity-failed、commit-unknown | 不用“包存在”覆盖 owner 失败 |
| `FR-AR-015` | 版本兼容判断 | 判断 manifest/schema/source version 是否支持验证或恢复 | 不自动迁移未知 schema，不猜兼容 |
| `FR-AR-016` | 归档作业重试与幂等 | 同一请求/作业键可重放既有结果，冲突键拒绝 | retry 不重复上传、交接或生成第二 truth |

### 2.1 不作为当前核心的外围候选

| ID | 能力 | 当前处理 |
|---|---|---|
| `FR-AR-E01` | 跨包全文搜索、趋势分析、RCA | 留给 observability/产品或后续归档查询专题 |
| `FR-AR-E02` | 自动合规声明、SoA/AIIA、Conformance Claim 生成 | 等 governance 正式 authority 与 schema；当前只接收 ref/decision |
| `FR-AR-E03` | 跨区域复制、自动灾备编排 | 等存储/运维 owner 闭合；不能写成默认能力 |
| `FR-AR-E04` | 一键把项目恢复为 Active | 明确禁止；必须经 `L1-work` 等 owner 的正式状态命令 |

## 3. 归档与恢复状态姿态（候选）

| 维度 | 状态候选 | 含义 |
|---|---|---|
| request/job | `requested` / `collecting` / `assembling` / `verifying` / `sealed` / `failed` / `blocked` | Archive 作业自身进度，不代表业务状态 |
| source slice | `missing` / `captured` / `partial` / `stale` / `conflicting` / `unsupported-version` | 单个来源的证据边界 |
| content closure | `open` / `complete` / `incomplete` / `overfull` / `invalid` | manifest 与实际材料关系 |
| integrity | `unchecked` / `verified` / `integrity-failed` / `unknown` | 摘要/签名验证结论 |
| storage | `location-pending` / `hot` / `warm` / `cold` / `retrieval-pending` / `unavailable` | 存储位置和可取回状态 |
| lifecycle execution | `not-requested` / `eligible` / `held` / `blocked` / `executed` / `unknown` | 对正式 retention/hold/delete decision 的执行记录 |
| restore owner item | `planned` / `material-ready` / `handed-off` / `accepted` / `rejected` / `partial` / `commit-unknown` / `compensation-required` | 每个 owning domain 独立 outcome |
| compatibility | `supported` / `unsupported-version` / `needs-migration` / `unknown` | 验证或恢复兼容性；未知不得放行 |

`sealed` 只表示 Archive 自有条件满足；`accepted` 只表示 owning domain 明确接收（若它提供该状态），`committed` 或 `restored` 必须由 owning domain 产生。任何局部状态不可推导全局成功。

## 4. 异常与恢复矩阵（候选）

| 场景 | Archive 处理 | 对外状态上限 | 禁止行为 |
|---|---|---|---|
| source query timeout/unavailable | 保留失败来源、重试线索和已捕获切片 | `partial` / `blocked` | 用 workspace/cache 补齐 |
| source version/fence 冲突 | 停止该 slice，要求重新 capture 或 owner resolution | `conflicting` | 取最后写入者覆盖 |
| manifest 缺条目或多出条目 | 关闭 sealing，记录 closure finding | `incomplete` / `invalid` | 缺后补、忽略多余内容 |
| digest/signature mismatch | 隔离包/材料，保留失败证据 | `integrity-failed` | 重算成“成功”或换用未知 key |
| storage put/transition unknown | 记录 commit-unknown，禁止重复副作用前盲重试 | `commit-unknown` / `storage-pending` | 假设未写入或已写入 |
| retention/hold decision missing | 阻断迁移/删除/销毁动作 | `blocked` | 默认 7 年、默认无 hold 或默认允许 purge |
| owner restore receiver unavailable | 保存材料和未交接状态，有限重试 | `pending` / `unavailable` | 直接写 owner DB |
| owner rejects or partially accepts | 记录 item-level outcome 与 compensation requirement | `partial` / `rejected` | 以 Archive package 覆盖 owner 决策 |
| unsupported source/schema version | 不解析、不转换、不交接 | `unsupported-version` | 猜测兼容或静默降级 |

## 5. 一致性、幂等与 fence 方向

1. 归档请求、source capture、manifest assembly、integrity verification、storage placement、restore handoff 是不同阶段；任一阶段成功不隐含其他阶段成功。
2. 每个 source 使用独立 `source version/watermark + snapshot fence + coverage`；不得用单一全局时间戳宣称跨域一致。
3. 归档作业的幂等键至少绑定请求范围、source binding 语境和输入 digest；同键同摘要可重放已存结果，同键不同摘要必须冲突。
4. 存储和 handoff 的 `commit-unknown` 不能靠重复副作用解决；必须先 query/verify 或进入人工/受控补偿路径。
5. restore 的事务边界只覆盖 Archive 本地材料和 handoff record；owner 的业务提交由 owner 自己的 UoW/command 收口。
6. 任何 query/verify 入口保持 no-write；显式 refresh、rebuild、retry 或 compensation 才能改变 Archive local state。

## 6. 当前 pending / blocker

| ID | 影响的能力 | 现阶段处理 |
|---|---|---|
| `AR-UP-001/002` | A1~A3 source capture、生命周期前置 | owner-safe export、状态与 fence 未闭合，保持 blocked |
| `AR-UP-003` | A5/A9 retention、hold、delete/destruction | 治理 owner 和授权链缺失，fail-closed |
| `AR-UP-004/005` | A4/A5 integrity、storage、兼容 | 算法、密钥、供应商、压缩与迁移未闭合，不发明参数 |
| `AR-UP-006/007/008` | Artifact、Observability、Workspace slice | 只接收明确 approved material/ref；投影不升格 |
| `AR-UP-009` | A7~A9 restore/handoff | 接收方、partial/commit-unknown/compensation 反馈未闭合 |

## 7. 本篇讨论结论

当前可确认的最小闭环是：显式请求 → 逐 source capture → manifest/内容闭包 → integrity 状态 → 存储/生命周期执行接缝 → 验证读取 → 按 owner 生成恢复材料并 handoff → 独立记录局部结果与补偿。缺少 owner 合同、签名/存储产品或治理授权时，闭环停在 blocked/pending，不能把包生成、上传或 handoff 发起写成归档成功或恢复成功。

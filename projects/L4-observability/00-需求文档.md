## 1. 与 `product/` 的关系声明

L4-observability 是**架构反推型**需求仓。它不是直接面向终端用户的业务仓,但它承载了 Quantalithos 三红线中的第一条——**可审计性**,同时也是可追溯性的技术基础。

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 不是单体工具,而是 26 仓 × 6 域 × 多产品线的系统。没有统一的可观测与审计中心,平台将失去:
- 对跨域事件链的可追踪性
- 对关键决策(Gate / Policy / AIIA / SoA)的合规证明
- 对业务结果(Artifact / Turn / Activity / WorkItem)的反向血缘查询
- 对 DORA / EBM / 42001 §9.1 的度量能力

L4-observability 负责把这些“横切能力”做成单一真相源。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 2 末) | 痛点 |
|---|---|---|
| event-catalog | 147 事件已登记 | 只在设计文档中,无真实 append-only 审计链 |
| trace 语义 | W3C Trace Context 已在 core/bus 锁定 | 还没有统一 trace 重建服务 |
| 审计链 | README 中有 append-only + 哈希链设计 | 还没有冷存策略与验证流程 |
| DORA/EBM | 已在观测横切叙事里提及 | 还没成为可查询的指标 API |
| lineage API | 各域引用需求存在 | 还没统一到同一查询面 |

### 2.3 为什么要做(量化依据)

- 所有 147 事件最终都要能被审计查询
- `artifact.content_tampered` / `identity.audit.*` / `governance.*` 这些关键事件没有 append-only 链就不可信
- L5-console 要做仪表板,必须有稳定的数据源

### 2.4 业务问题 vs 技术问题

- **业务问题**:平台如何证明自己在受控运行、如何回溯关键操作与产出链路
- **技术问题**:append-only 存储、哈希链、trace 重建、事件 tap、metrics 聚合、冷热分层、读权限控制

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 通过 bus tap-all 接收全量事件并写入 append-only 审计链
2. 从任意 Artifact / Turn / Activity / Gate 反查相关 trace / lineage
3. 查询 DORA / EBM / 42001 §9.1 指标
4. 定期验证哈希链完整性并告警
5. 给 Console 提供仪表板和审计视图数据源

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **Auditor**,我想要 **查看某个 Gate 从 raised 到 decided 的完整审计链**,以便 **证明关键决策过程合规** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个 gate_id **When** 调查询 API **Then** 返回触发、证据、审批、决策、关联 Artifact / Turn / Activity |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **SRE**,我想要 **从某个 trace_id 还原跨域完整调用树**,以便 **定位故障发生在哪个仓 / 哪个聚合** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个 trace_id **When** 查询 **Then** 返回 span / event / aggregate timeline |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **Owner**,我想要 **在 Console 看到 DORA / EBM / 质量基线指标**,以便 **了解项目和团队的健康度** |
| 优先级 | P1 |
| 验收条件 | **Given** 项目有足够事件历史 **When** 打开 dashboard **Then** 返回 8 个核心指标 |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **系统**,我想要 **定期校验审计链哈希并在断链时告警**,以便 **防止篡改或数据损坏** |
| 优先级 | P0 |
| 验收条件 | **Given** 某条链被篡改 **When** nightly verify **Then** 发 critical 告警 |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **archive**,我想要 **把旧审计数据迁移到冷存但仍可按需回查**,以便 **满足 7 年甚至更久的保留要求** |
| 优先级 | P1 |
| 验收条件 | **Given** 超过热存期的数据 **When** 迁移 **Then** metadata 仍可查,内容可从 cold 恢复 |

## 6. 功能需求

### 6.1 功能清单与优先级

| ID | 功能名称 | 优先级 | 依赖 | 描述 |
|---|---|---|---|---|
| F-001 | append-only 审计事件存储 | P0 | bus tap | 审计记录只增不改 |
| F-002 | 哈希链保护 | P0 | F-001 | 断链检测 + 告警 |
| F-003 | trace 重建 | P0 | core / bus | 从事件 / span / aggregate 重建调用树 |
| F-004 | 指标聚合 | P0 | bus / service metrics | Prometheus / TimescaleDB |
| F-005 | 日志汇聚 | P1 | structured logs | 按 trace / service / severity 查询 |
| F-006 | 血缘反查 API | P0 | artifact / conversation / process / governance | 从对象反查上下游链 |
| F-007 | DORA / EBM 指标计算 | P1 | F-004 | 部署频率 / CFR / MTTR 等 |
| F-008 | 42001 §9.1 监测指标 | P1 | F-004 | 偏差 / drift / bias / usage 监测 |
| F-009 | 冷热分层存储 | P0 | object storage / archive | 7 年保留 |
| F-010 | 告警规则引擎 | P0 | F-002/F-004 | 4 类默认告警 |
| F-011 | Query API 权限控制 | P0 | governance / auth | 只允许合规角色看敏感审计链 |
| F-012 | dashboard 数据源 | P1 | console | 给仪表板返回聚合指标 |

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| BR-001 | 审计事件写入 | 不允许 UPDATE/DELETE |
| BR-002 | 哈希链断裂 | 立即 critical 告警 |
| BR-003 | 无权限查询全量审计链 | 拒绝访问 |
| BR-004 | 数据超过热存窗口 | 迁冷存,metadata 保留 |
| BR-005 | 某对象(trace/artifact/turn/gate/activity)查询 | 必须能反向追到关联事件 |

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 类型 | 生命周期 |
|---|---|---|
| AuditEvent | append-only 记录 | 永久 / 冷存 |
| TraceTree | 查询视图 | 即时重建 |
| MetricSeries | 时间序列 | 热存 / 聚合 / 冷存 |
| AlertRecord | 事件 | created / acknowledged / resolved |
| ColdArchivePointer | ref | metadata 长期保留 |

### 9.2 数据关系

```
AuditEvent chain
  ├─ previous_hash
  ├─ current_hash
  ├─ trace_id
  ├─ aggregate_refs[]
  └─ lineage_refs[]

MetricSeries
  └─ aggregate over AuditEvent / service metrics
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| 热审计事件 | 90 天(默认) | 冷存前仍高频可查 | 不删 |
| 冷审计事件 | 7 年(默认) | object storage | 到期按 Policy |
| 指标聚合结果 | 1-2 年 | 压缩聚合 | 过期清理 |
| 告警记录 | 长期 | archive | 不删历史 |

## 12. 风险与待确认事项

### 12.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| tap-all 拖慢总线 | 中 | 高 | 独立 consumer group + 只读路径 |
| hash chain 过长校验慢 | 中 | 高 | 分片策略 / 分段校验 |
| 冷存回查慢 | 中 | 中 | metadata 索引 + 异步恢复 |
| 读权限控制不严 | 低 | 极高 | authz + 审计二次留痕 |

### 12.2 边缘风险

- 审计链跨租户隔离复杂
- DORA / EBM 口径争议
- GenAI OTel 语义快速演进

### 12.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 哈希链分片策略(单链 vs 多链) | L4 前 | observability + SRE |
| 冷存保留 7 年还是更长 | L4 前 | governance + legal |
| OTel Collector 具体选型 | L4 前 | SRE |

## 1. 业务背景与驱动力

### 1.1 业务背景

Observability 不是辅助工具,而是 Quantalithos 三红线中**可审计性 / 可追溯性**的技术载体。它把:
- 147 个事件
- 所有跨域 trace
- 关键 aggregate 的血缘链
- DORA / EBM / 42001 §9.1 指标

统一成平台级观测与审计中心。

### 1.2 业务驱动力

**业务驱动力**:
- 平台必须证明自己在受控运行
- 审计员要能反查 Gate / Artifact / Turn / Activity 链条
- Console 要有可用的仪表板与审计视图

**技术驱动力**:
- append-only + hash chain 防篡改
- tap-all 消费 bus 全量事件
- trace reconstruction
- 冷热分层存储
- lineage API

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| audit write | P95 | < 50ms | benchmark |
| hash verify | 10w events | < 5s | benchmark |
| lineage query | P95 | < 500ms | benchmark |
| tap coverage | 147 事件 | 100% | 回归测试 |
| SLA | availability | ≥ 99.95% | 监控 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| append-only 审计链 | OB1 / 9001 §7.5 | 不允许 UPDATE/DELETE |
| 哈希链保护 | OB2 | 必须可校验 |
| OTel / W3C Trace Context | core / 42001 | trace reconstruction 模型固定 |
| 147 事件全量 tap | event-catalog | 观测中心必须消费全量 |
| 读权限控制 | OB6 | 敏感审计链不得开放给普通成员 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| TimescaleDB | 当前倾向 | 可换 PG + 列存 / ClickHouse |
| hash chain 分片 | 未定(单链/多链) | 可后续演进 |
| 冷存保留期 | 默认 7 年 | legal/governance 可调 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| event types | 147 | event-catalog |
| audit write latency | < 50ms | README |
| hash chain verify | 10w / batch | README |
| scrape interval | 15s | README |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| event volume | 高频 | append-only + cold tier |
| query patterns | 中 | lineage API + dashboard projections |
| metric dimensions | 中高 | label model + aggregation pipeline |
| retention policy | 中 | governed retention rules |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **audit-chain + metrics hub**(当前)| 满足审计与观测双要求 | 模型稍重 | ✅ |
| 纯日志平台 | 便宜 | 不能做强审计链和 lineage | ❌ |
| 纯 tracing system | trace 强 | 指标 / 审计不足 | ❌ |

**最终选择**:**append-only 审计链 + trace reconstruction + metrics hub**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| append-only | 审计可靠 | 存储成本高 |
| hash chain | 防篡改 | 校验成本 |
| full tap | 全局可追踪 | ingest 压力 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
all L0/L1/L2/L3 services
          │ events / metrics / logs / trace
          ▼
   ★ quantalithos-observability ★
   - audit chain
   - trace reconstruction
   - metrics hub
   - lineage API
          │
   ┌──────┼──────────────┬──────────────┬──────────────┐
   ▼      ▼              ▼              ▼              ▼
 console  governance     archive        SRE           auditors
 dashboards audit proof  cold storage   alerting      evidence query
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 审计事件 append-only 存储
- ✅ 哈希链校验
- ✅ trace 重建
- ✅ 指标聚合 / DORA / EBM / 42001 §9.1
- ✅ lineage 反查 API

**不做什么**:
- ❌ 事件主干(bus)
- ❌ 业务逻辑执行
- ❌ Console 仪表板前端
- ❌ Artifact 正文归档(archive)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| bus tap-all | 99.95% | backlog / replay |
| TimescaleDB | 99.95% | 不可用则阻断 |
| object storage | 99.9% | 延迟冷存 |
| Grafana | 99.9% | API 仍可查 |

### 4.4 关键依赖风险

- tap-all 吞吐对 bus 造成回压
- 冷存回查延迟
- hash chain 分片策略错误导致校验成本爆炸

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Audit Chain | 核心域 | append-only 审计链 |
| Trace Reconstruction | 核心域 | 跨域 trace 树 |
| Metrics Hub | 支撑子域 | DORA / EBM / OTel metrics |
| Lineage Query | 支撑子域 | 反向血缘查询 |
| Alerting | 支撑子域 | 规则与告警记录 |

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Audit | 审计事件链 | AuditEvent |
| Trace | trace / span / event tree | TraceTree |
| Metrics | timeseries / aggregation | MetricSeries |
| Query | lineage / reverse lookup | QueryProjection |
| Alerts | 告警规则与记录 | AlertRecord |

### 5.3 上下文映射关系

- bus → Audit / Trace
- artifact / governance / conversation / process / work → Query
- Metrics ← all services OTel export
- archive ← cold storage pointers

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |
|---|---|---|
| AuditEvent | append-only 审计记录 | Audit |
| TraceTree | 某 trace_id 的全链结构 | Trace |
| MetricSeries | 时间序列指标 | Metrics |
| LineageQuery | 反向血缘查询请求 | Query |
| AlertRecord | 告警事件 | Alerts |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
OTel sources / bus tap
       │
       ▼
ingest layer
  ├─ audit chain writer
  ├─ trace reconstruction service
  ├─ metrics aggregator
  ├─ lineage query API
  └─ alerting engine
       │
       ├─▶ TimescaleDB / audit DB
       ├─▶ object storage(cold)
       ├─▶ Prometheus / Grafana
       └─▶ console / governance / archive consumers
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| ingest-api | 接收 bus tap / OTel metrics |
| audit-writer | append-only + hash chain |
| trace-service | trace tree 重建 |
| metrics-aggregator | 聚合指标 / DORA / EBM |
| lineage-api | 反查 API |
| alert-engine | 告警规则 |
| timescaledb | 热审计 / 指标 |
| cold storage | 冷存 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| bus tap → ingest | 事件订阅 | 全量事件流 |
| service metrics → ingest | OTel / Prometheus scrape | 业界标准 |
| console → query API | RPC / HTTP | dashboard / drill-down |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| audit_events | observability | auditors / lineage / governance |
| trace_trees | observability | SRE / auditors |
| metric_series | observability | console / SRE |
| alert_records | observability | SRE / governance |
| cold pointers | observability / archive | archive / auditors |

### 6.5 部署拓扑

- ingest / query / alert 可先同进程
- TimescaleDB 热存
- object storage 冷存
- Grafana / Prometheus 外接

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
ingest / query api
      │
      ▼
application
      │
      ▼
domain(Audit / Trace / Metrics / Query / Alerts)
      ▲
      │ ports
infra(TimescaleDB / object storage / bus / otel exporters)
```

### 7.2 层间约束规则

- audit chain writer 不可 UPDATE/DELETE 历史记录
- query API 只读,不直接改审计链
- metrics aggregator 不理解业务语义,只做聚合
- alert engine 不直接执行业务修复,只发告警事件

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| AuditStore | domain/application | TimescaleDB |
| ColdArchiveStore | application | object storage |
| EventTapSource | application | bus subscriber |
| MetricSource | application | OTel / Prom exporter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 极高(全平台事件 / metrics) |
| 传出耦合 | 中(TimescaleDB / object storage / Grafana) |
| 不稳定性 | 中 |
| 抽象度 | 高(查询 / 存储 / 聚合均解耦) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| audit events | observability | auditors / governance / query API | append-only 强一致 |
| trace reconstruction | observability | SRE / query API | 最终一致(由事件重建) |
| metric series | observability | console / SRE | scrape / aggregate |
| lineage projections | observability | console / auditors | 最终一致 |
| alert records | observability | SRE / governance | 强一致 |

### 8.2 一致性层次

- append-only 审计链内强一致
- trace / lineage 重建为最终一致投影
- metrics 为 scrape / aggregation 最终一致
- cold archive pointer 与 archive 仓最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| bus tap 短时断流 | replay / resume |
| cold store 写失败 | 保持热存 + 重试 |
| hash chain 断裂 | critical 告警 + 审计介入 |

## 9. 关键技术选型

### 9.1 TimescaleDB

| 维度 | 内容 |
|---|---|
| 当前选择 | TimescaleDB |
| 备选方案 | PostgreSQL + 分区 / ClickHouse |
| 选择理由 | 时序指标与审计热存兼容较好 |
| 演进路径 | 超大规模可拆 ClickHouse |
| 不可逆程度 | 中 |

### 9.2 append-only + hash chain

| 维度 | 内容 |
|---|---|
| 当前选择 | DB append-only + hash chain |
| 备选方案 | 纯对象存储 / 区块链式外部账本 |
| 选择理由 | 可查 + 可证伪 + 可审计 |
| 演进路径 | 分片策略可演进 |
| 不可逆程度 | 中高 |

### 9.3 OTel Collector / Prometheus / Grafana

| 维度 | 内容 |
|---|---|
| 当前选择 | OTel + Prom + Grafana |
| 备选方案 | vector / fluent + custom metrics |
| 选择理由 | 生态成熟,跨语言一致 |
| 演进路径 | collector 选型后置 |
| 不可逆程度 | 中 |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| hash chain 分片策略未定 | 校验成本 | P1 |
| cold retention 期限未定 | 合规成本 | P1 |
| lineage API 还未在所有对象类型上验证 | 查询准确性 | P1 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| verify > 5s | 持续 1 周 | 评估多链 / 分片 |
| audit write > 50ms | 持续 1 周 | 优化写入路径 / 分库 |
| lineage query > 500ms | 持续 1 周 | 加 projection / cache |

### 12.3 演进步骤

```
阶段 1: append-only + metrics 基础落地
阶段 2: hash chain + lineage API
阶段 3: DORA / EBM / 42001 dashboards
阶段 4: cold archive / long retention / partition strategy
```

### 12.4 目标架构

observability 的目标是:
- 让平台能证明自己在受控运行
- 让任何关键对象都可反向追溯
- 让指标和审计成为一体化基础设施而非零散面板

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| hash chain 校验成本过高 | 中 | 高 | 分片 / 批处理 |

- 监管要求 10 年甚至永久保留

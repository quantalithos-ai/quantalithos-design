## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L4-observability` 不是业务真相仓,也不是执行决策仓,更不是单纯的日志仓。它是 **“平台观测与证据汇聚层”**。

你可以把它理解成:
- 平台里发生了什么,是否可见、可解释、可追溯
- trace、metric、log、audit、cost、drift、usage 这些材料怎样被统一接住
- 来自 runtime、sandbox、capability-hub、method-library、governance 等多个仓的正式留痕怎样被汇总成可查询、可告警、可诊断的观测视图
- 人类和系统怎样基于这些观测材料判断健康度、异常、趋势和根因

这些事情,都由 `L4-observability` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L4-observability`,这些观测材料就会散落在:
- runtime 各自的局部执行日志里
- sandbox 自己的 stdout/stderr / usage 快照里
- capability-hub 各自的 cost / deny / audit 记录里
- method-library 的 drift / publish / replay 证据里
- governance 自己的裁决与审计留痕里
- 各类 dashboard、grep、SQL 和临时脚本里

结果就会出现:
- 平台到底“发生了什么”没有统一观测面
- trace、metric、audit、cost、drift 和 usage 各自成链,无法对账
- 健康摘要和告警规则没有共同事实基线
- owner / oncall / operator 看到的是多套互相不一致的数据
- 需要定位根因时,只能去不同仓拼接日志和状态

所以 `L4-observability` 必须独立存在,作为:
> **把全平台 trace、metric、audit、cost、drift、usage 和状态证据统一汇聚成可查询、可告警、可诊断的观测层。**

### 1.3 新人最容易混淆的几个词

#### ObservabilityEvent
就是:
> 一条被统一接入到观测层的正式观测材料。

它不是 source domain truth 本体。

#### HealthSummary
就是:
> 对某个系统、仓、能力或链路当前健康状态的聚合判断结果。

它不是运维控制命令本体。

#### DriftReport
就是:
> method-library、capability-hub、runtime 等链路中检测到的漂移/不一致报告视图。

它不是这些系统各自的权威真相本体。

#### CostDashboard
就是:
> 从成本事件和用量事件聚合出的运营观察面。

它不是 finance ledger 真相本体。

#### AlertRule
就是:
> 根据观测事件和指标定义的告警判断规则。

它不是 governance / runtime / capability policy 本体。

#### Trace / metric / log
就是:
> 对运行事实的不同观测表达形式。

它们都不直接等于业务真相本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L4-observability/02` 时,先收稳以下前提:
- `L4-observability` 不应按 log / metric / trace / audit 技术维度平铺理解,而应按观测证据主链责任拆
- observability 至少应拆成“观测事件采集与统一接入 / 执行与资源观测 / 治理、审计与漂移观测 / 成本、用量与经营观察 / 查询、告警与诊断出口”五个主要部分
- observability 自己拥有的真相不是 runtime execution、sandbox output、capability cost ledger、method definition 或 governance decision,而是观测事件、聚合视图、告警与诊断结果这类观测层真相
- `L4-observability` 只能为 operators、SRE、owners、console 提供可见性与诊断面,不能替这些上游系统持有业务或执行真相
- 02 的重点不是“列有哪些表和图”,而是先把“平台观测层在全局里到底是什么、和 runtime/sandbox/capability-hub/method-library/governance/artifact 怎么分层”讲清楚
- health summary、alert rule、cost dashboard、drift report 这些不是散碎视图,而是观测主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的观测与证据心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,平台不仅要能执行,还要能被看见。用户真正需要的不是“某个仓有日志”,而是:
- 多个系统发生的运行、治理、成本、漂移、产物和交互事实能被统一汇聚
- 所有观测材料都可以被查询、聚合、告警和诊断
- owners / operators / oncall / TL 能用同一套观察面看问题
- 成本、drift、deny、retry、replay、cleanup、publish、summary 等材料能彼此对账
- 健康摘要、趋势、TopN、异常波动和根因分析有统一基线

如果把这些逻辑分别散落到:
- 各仓本地日志
- 各种手写 SQL 或 grep
- 局部 dashboard
- cost / audit / drift 各自独立的聚合脚本

系统会快速退化成:
- 观测材料不统一
- 告警与根因判断没有共同事实源
- 成本、审计、执行状态彼此对不上
- 系统健康度和风险演化难以稳定把握

因此,本概要设计的任务就是:
> **把 `L4-observability` 写成一个新人也能看懂的“平台观测与证据汇聚层”,而不是把日志、指标、审计和成本各写一套局部查询。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 统一观测接入 | 多仓各自输出 | 统一观测事件入口 | 需正式收敛 |
| 执行与资源可见性 | 分散在 runtime / sandbox | 单一执行观测面 | 需形成统一投影 |
| drift / audit 对账 | 多链分散 | 100% 可关联 | 需固定主线 |
| 成本运营观察 | capability-hub 局部记录 | owner 可用经营视图 | 需产品化观察面 |
| 告警与诊断 | 局部脚本化 | 统一告警与健康摘要 | 需形成出口 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让平台里的执行、能力、治理、方法、成本和产物证据被统一观察、解释、告警和追责
- **技术问题**:ObservabilityEvent、HealthSummary、DriftReport、CostDashboard、AlertRule 与 runtime / sandbox / capability-hub / method-library / governance / artifact 之间的边界如何稳定建模,并形成统一观测主链

## 4. 约束条件

### 4.1 技术约束

- 所有进入 observability 的材料都必须被统一 source tagging 和 event normalize
- trace、metric、log、audit、cost、drift、usage 必须能关联到共同上下文锚点
- 查询和聚合层只能读 source truth 派生的观测事件,不得反写源仓
- alert rule 只能基于观测材料求值,不得替代 source policy
- retention、aggregation、sampling 等策略必须显式可配置,不能写死在消费逻辑里

### 4.2 资源约束

- 事件量和日志量会持续增长,必须接受 append-only 历史规模增长
- dashboard 查询和 health summary 是高频路径,聚合复杂度必须受控
- cost / drift / usage / audit 的多维聚合不能过度依赖 source 仓在线查询

### 4.3 时间约束

- 当前阶段先收稳统一观测主链,而不是先做复杂跨租户 BI 分析或高级智能诊断
- ingestion、execution visibility、audit/drift、cost、alert 这五条主线必须优先稳定,否则后续告警和治理无共同事实源

### 4.4 合规约束

- 观测事件不得替代源仓真相
- 成本与审计观测必须可留痕、可追溯、可回放
- 安全/治理类告警不得由本地脚本静默决定,必须走正式规则链
- 观测保留周期与 artifact 保留周期必须分离配置

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| observability events/day | 高 | 全平台多仓事件汇聚 |
| dashboards / queries | 高频 | oncall / owner / operator 观察面 |
| alert evaluations | 高频 | 多条主链告警需求 |
| retention storage | 高 | append-only 证据链长期保留 |

│ operators / oncall         │   │ owners / TL / console      │   │ automation / alert system  │

└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘

### 5.2 位置解释

- `L4-observability` 自己负责统一接入观测材料、做聚合与投影、生成健康摘要、告警和诊断视图
- runtime / sandbox / capability-hub / method-library / governance / artifact 是观测材料来源方,但 observability 不拥有它们的源真相
- operators / oncall / owners / console / automation 是观测消费方,通过 observability 读取统一视图
- 这个仓的角色不是“决定业务真相或运维动作”,而是“提供统一可见性与证据面”

所以 `L4-observability` 在全局里的角色是:
> **把全平台运行、治理、成本、漂移和证据材料统一汇聚成可查询、可告警、可诊断的观测层。**

### 5.3 系统边界

**做什么**:
- 统一接入 trace / metric / log / audit / cost / drift / usage 事件
- 聚合 execution / resource / audit / cost / drift 观察面
- 生成 health summary / alert / diagnostic 视图
- 为 operators / owners / console / automation 提供统一只读观察面

**不做什么**:
- 不反写真相到 runtime / sandbox / capability-hub / method-library / governance / artifact
- 不直接执行 kill / retry / replay / business decision
- 不替代 finance ledger、artifact retention、governance decision truth

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| runtime / sandbox / hub / method / gov 事件源 | 99.9% | 单源短暂失联时保留现有视图并标记 source gap |
| bus / event stream | 99.95% | backlog / replay,不静默丢审计与成本观测 |
| object / log storage | 99.9% | 保留元数据与摘要视图,延迟加载原始材料 |
| dashboard / query engine | 99.9% | 降级到 cached summary / prebuilt views |
| alert channel | 99.9% | 告警重试 / backlog,但保留触发证据 |

### 5.5 关键依赖风险

- 上游 source truth 与 observability projection 漂移会让 operators 做错判断
- cost / audit / drift 只聚合不对账会造成错误根因判断
- alert rule 若混入 source policy 语义会导致边界污染
- health summary 若被误当操作命令会放大自动化风险
- retention 策略若和 artifact / source truth 混层,会造成证据丢失或重复保留

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把 log / metric / trace / audit 技术维度横向平铺。  
> 它按 **观测证据主链职责 + 采集 / 执行 / 治理 / 成本 / 查询差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象和机制,共同支撑同一段观测主链。

#### 观测事件采集与统一接入部分

- **它是什么**: 这是 `L4-observability` 的入口层,一起回答“观测材料怎样进入统一主线”
- **为什么单独有它**: 如果没有独立 ingest 层,trace、metric、audit、cost、drift 会各自一套采集口径,后续所有聚合和诊断都会漂移
- **负责什么**:
  - 接入 trace / metric / log / audit / cost / drift / usage 材料
  - 做 source tagging、normalize、context binding
  - 形成统一 ObservabilityEvent 主线
- **不负责什么 / 容易混淆点**:
  - 不决定 source truth 状态迁移
  - 不负责 runtime / sandbox / governance 等业务真相本体
  - 不负责运维控制命令
  - 最容易和 source domain truth、本地日志采集器、业务事件总线混淆
- **与其他部分交互**:
  - 下游: 执行与资源观测、治理/审计/漂移观测、成本/经营观察、查询/告警出口
  - 外部: runtime / sandbox / capability-hub / method-library / governance / artifact
  - 交互类型: ingest 接入型 + 统一上下文型
- **后续详细设计展开点**:
  - ObservabilityEvent 模型
  - source tagging / context binding 主线

#### 执行与资源观测部分

- **它是什么**: 这是 observability 的运行观测层,一起回答“执行面现在跑得怎么样”
- **为什么单独有它**: runtime 和 sandbox 这条主线的执行、usage、queue、latency、retry 观测是平台实时健康的核心来源,不单列就会和 audit/cost 混成一层
- **负责什么**:
  - 聚合 execution progress / step status / wait / fail / completion
  - 聚合 sandbox usage / stdout/stderr 摘要 / timeout / retry / replay / kill / cleanup 事件
  - 形成执行与资源观察面
- **不负责什么 / 容易混淆点**:
  - 不等于 runtime execution truth
  - 不等于 sandbox 原始输出真相
  - 不直接发控制命令
  - 最容易和 runtime 真相、sandbox output 本体、运维控制动作混淆
- **与其他部分交互**:
  - 上游: runtime / sandbox
  - 下游: 查询、告警与诊断出口
  - 交互类型: 运行状态聚合型 + 健康判断输入型
- **后续详细设计展开点**:
  - execution health model
  - usage / latency / queue 视图

#### 治理、审计与漂移观测部分

- **它是什么**: 这是 observability 的合规与一致性观测层,一起回答“平台有没有越权、漂移、断链”
- **为什么单独有它**: governance audit、capability deny、method drift、policy refresh 都不是普通运行指标,它们更接近平台可信度与一致性观察面
- **负责什么**:
  - 汇聚 governance 审计、capability deny / policy refresh、method-library drift / fingerprint_changed
  - 形成 audit / drift / compliance 视图
  - 支撑对账与异常定位
- **不负责什么 / 容易混淆点**:
  - 不等于 governance decision 真相
  - 不等于 method-library 权威定义真相
  - 不替代 capability-hub allow/deny 真相
  - 最容易和 source policy、本地 drift 记录、业务裁决日志混淆
- **与其他部分交互**:
  - 上游: governance / capability-hub / method-library / runtime
  - 下游: 查询、告警与诊断出口
  - 交互类型: 合规汇聚型 + 漂移诊断型
- **后续详细设计展开点**:
  - drift report / audit aggregation
  - cross-system compare 主线

#### 成本、用量与经营观察部分

- **它是什么**: 这是 observability 的经营观察层,一起回答“平台到底花了多少、用了多少”
- **为什么单独有它**: 成本与使用趋势是 owner / TL 关心的运营面,既不同于原始 cost event,也不同于财务正式总账
- **负责什么**:
  - 聚合 capability-hub cost event、usage event
  - 形成 provider / tool / session / project / role 等维度的成本与用量视图
  - 输出 trend / TopN / anomaly 经营观察面
- **不负责什么 / 容易混淆点**:
  - 不等于 finance ledger truth
  - 不等于 capability-hub 原始 CostRecord 真相
  - 不直接做预算裁决
  - 最容易和财务系统、provider 原始账单、source usage 事件混淆
- **与其他部分交互**:
  - 上游: capability-hub / runtime / sandbox usage
  - 下游: 查询、告警与诊断出口 / owner 视角
  - 交互类型: 聚合分析型 + 经营观察型
- **后续详细设计展开点**:
  - cost dashboard / anomaly / trend 视图

#### 查询、告警与诊断出口部分

- **它是什么**: 这是 observability 的消费面层,一起回答“人和系统怎样读这些观测材料”
- **为什么单独有它**: 观测系统的价值不在于采集成功,而在于 operators / owners / automation 能查、能告警、能定位。若不单列,采集与消费会混成一锅
- **负责什么**:
  - 提供 query / dashboard / API
  - 提供 health summary / alert rule / detector / diagnostic 视图
  - 为 operators / oncall / owners / console / automation 提供统一只读出口
- **不负责什么 / 容易混淆点**:
  - 不等于控制命令执行层
  - 不替代 governance / runtime / capability policy 真相
  - 不替代 artifact retention 规则
  - 最容易和运维命令系统、source policy、BI 工具本体混淆
- **与其他部分交互**:
  - 上游: 前四个主要部分
  - 下游: operators / owners / console / automation
  - 交互类型: 查询消费型 + 告警诊断型
- **后续详细设计展开点**:
  - health summary / alert rule / dashboard API
  - detector / root cause 视图

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ runtime / sandbox / hub     │
                    │ method / gov / artifact     │
                    │ - trace / metric / audit    │
                    │ - cost / drift / usage      │
                    └────────────┬───────────────┘
                                 │ observability input
                                 ▼
                    ┌────────────────────────────┐
                    │ L4-observability           │
                    │ - ingest / aggregate       │
                    │ - cost / drift / health    │
                    │ - alert / diagnostic       │
                    └────────────┬───────────────┘
                                 │ dashboards / alerts / diagnosis
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ operators / oncall         │   │ owners / TL / console      │   │ automation / alert system  │
│ - inspect / triage         │   │ - trend / cost / drift     │   │ - thresholds / routes      │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L4-observability` 自己负责“接入观测材料”“聚合执行/资源/治理/成本/漂移视图”“生成 health/alert/diagnostic 出口”
- `runtime` / `sandbox` 的交互主要落在 **观测事件采集与统一接入部分** 与 **执行与资源观测部分**,为 observability 提供执行、usage、timeout、retry、replay、kill 等材料
- `capability-hub` / `method-library` / `governance` 的交互主要落在 **治理、审计与漂移观测部分** 与 **成本、用量与经营观察部分**,为 observability 提供 deny、cost、audit、drift、policy refresh 等材料
- `artifact` 的交互主要落在 **观测事件采集与统一接入部分** 与 **查询、告警与诊断出口部分**,为 observability 提供产物结果材料并消费只读观察面
- operators / owners / console / automation 的交互主要落在 **查询、告警与诊断出口部分**,消费 health summary、dashboards、alerts 和 diagnostic 视图

### 7.3 分模块交互说明(逐个写)

#### 与 `runtime / sandbox` 的交互

```text
┌────────────────────────────┐
│ runtime / sandbox          │
│ - execution / usage        │
│ - timeout / replay / kill  │
└────────────┬───────────────┘
             │ execution observability input
             ▼
┌────────────────────────────┐
│ observability              │
│ - execution views          │
│ - health summaries         │
└────────────────────────────┘
```

- `runtime / sandbox` 是 **执行观测来源方**
- **交互类型**: execution / usage / control 事件输入型交互
- **主流程位置**: progress、fail、timeout、retry、replay、cleanup 时进入主流程
- **交互解释**:
  - runtime / sandbox 提供执行与资源相关观测材料
  - observability 把它们聚合成统一执行观察面
  - observability 不替代 runtime / sandbox 的源真相
- **高风险异常流**:
  - 只看到 trace / log 摘要却错误推断 execution truth
- 后续 `03-详细设计.md` 继续展开:
  - execution event ingest contract
  - health summary 主线

#### 与 `capability-hub / method-library / governance` 的交互

```text
┌────────────────────────────┐
│ hub / method / governance  │
│ - cost / deny / drift      │
│ - audit / policy refresh   │
└────────────┬───────────────┘
             │ compliance / cost input
             ▼
┌────────────────────────────┐
│ observability              │
│ - drift report             │
│ - cost dashboards          │
│ - audit views              │
└────────────────────────────┘
```

- 这些仓是 **合规、漂移与成本观测来源方**
- **交互类型**: audit / drift / cost 输入型交互
- **主流程位置**: deny、policy refresh、fingerprint_changed、cost recorded 时进入主流程
- **交互解释**:
  - observability 汇聚这些材料形成统一观察面
  - drift / cost / audit 只是观测视图,不反写真相
  - observability 不替代 source systems 的主判断
- **高风险异常流**:
  - drift report 被误当权威定义或 audit 聚合被误当治理裁决
- 后续 `03-详细设计.md` 继续展开:
  - audit aggregation
  - cost/drift projection contract

#### 与 `artifact` 的交互

```text
┌────────────────────────────┐
│ artifact                   │
│ - artifact result refs     │
│ - output material summary  │
└────────────┬───────────────┘
             │ artifact observability input
             ▼
┌────────────────────────────┐
│ observability              │
│ - result / summary views   │
└────────────────────────────┘
```

- `artifact` 是 **结果材料来源方之一**
- **交互类型**: result material 输入型交互
- **主流程位置**: artifact 结果物化、summary 生成、产物异常时进入主流程
- **交互解释**:
  - observability 观察 artifact 结果和趋势
  - observability 不反向定义 artifact 真相
- **高风险异常流**:
  - observation retention 与 artifact retention 混层
- 后续 `03-详细设计.md` 继续展开:
  - artifact result projection
  - retention boundary

#### 与 `operators / owners / console / automation` 的交互

```text
┌────────────────────────────┐
│ observability              │
│ - health / alert / diag    │
└────────────┬───────────────┘
             │ read / alert output
             ▼
┌────────────────────────────┐
│ operators / owners / auto  │
│ - inspect / dashboard      │
│ - alert consume            │
└────────────────────────────┘
```

- 这些系统和角色是 **观测消费方**
- **交互类型**: 只读查询型 + alert consume 型交互
- **主流程位置**: health 检查、threshold 触发、dashboard 查询、diagnostic drilldown 时进入主流程
- **交互解释**:
  - observability 给出统一观察与告警出口
  - 消费方可以根据结果决定后续动作
  - observability 本身不执行控制命令
- **高风险异常流**:
  - health summary 被误当成运维命令自动执行
- 后续 `03-详细设计.md` 继续展开:
  - dashboard API
  - alert rule / detector 主线

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是观测汇聚层、哪个模块是只读消费方、哪个模块是告警消费方

本节**不**展开:
- trace / metric / log 存储引擎细节
- query / BI / dashboard 实现细节
- detector / anomaly 算法细节
- retention / sampling 低层参数
- 自动化响应的执行逻辑

这些内容留到 `03-详细设计.md` 中继续展开。

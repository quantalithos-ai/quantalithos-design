## 1. 模块职责描述

**本模块做什么**:
- 持有正式 ObservabilityEvent / HealthSummary / DriftReport / CostDashboard / AlertRule / DiagnosticView 等观测层真相
- 把 runtime、sandbox、capability-hub、method-library、governance、artifact 等多仓输出的观测材料统一接入、归一化、聚合和投影
- 为 operators / oncall / owners / console / automation 提供统一的 dashboard、alert、diagnostic 和只读查询出口
- 管理 retention、aggregation、sampling、source tagging、context binding 等观测层规则

**本模块不做什么**:
- 不持有 runtime、sandbox、capability-hub、method-library、governance、artifact 的 source truth 本体
- 不直接执行 kill / retry / replay / business decision 等控制命令
- 不替代 finance ledger、artifact retention、governance decision truth 或 source policy 本体

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 observability“为什么存在”,而是让开发者可以直接开始实现:
- 多仓 trace / metric / audit / cost / drift / usage 事件如何进入统一 ingest 主线
- execution / resource、audit / drift、cost / usage 三种观察面怎样分别聚合而不混层
- health summary、alert rule、diagnostic view 怎样建立在统一上下文与只读投影之上
- dashboard / query / API 怎样面向 operators、owners、automation 提供稳定出口
- retention、sampling、source gap、replay 怎样成为观测层的正式规则链

如果不先把这些内容采集清楚,03 很容易退化成:
- ELK/Prometheus/Grafana 工具清单
- metric name 和 dashboard 名字表
- 各仓日志采集脚本说明
- alert / diagnostic / cost / drift 各写一套没有统一上下文的视图

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `ObservabilityEvent / HealthSummary / DriftReport / AlertRule` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是观测主链,`03` 却退化成日志、指标、报表、告警的技术清单
- 实现者知道有 drift report,却不知道它如何和 audit / cost / execution health 形成统一上下文
- dashboard、alert、retention 各写一套,彼此断裂

```rust
    pub source_module: String,

pub struct ContextBinding {
    /// trace 关联标识。
    pub trace_id: String,
    /// execution 关联标识。

    /// project 关联标识。
```

这些对象在该部分里分别承担:

- `ContextBinding` 负责把分散材料绑定到共同上下文
- `EventEnvelopeRef` 负责回指 bus 主线中的原始事件壳

#### 5.2.4 关键函数代码片段

```rust
/// 把来自上游系统的观测材料规范化为正式 ObservabilityEvent。
fn ingest_observability_event(
    ingest_repo: &dyn ObservabilityIngestRepo,
    raw_event: RawObservationEvent,
) {
    // [raw_event.校验最小输入]
    // 先确认来源系统、事件类别和最小上下文引用齐全。
    raw_event.validate_ingestable_shape();

    // [ObservabilityEvent::从原始事件创建]
    // 再把原始材料收束成统一观测事件对象。
    let event = ObservabilityEvent::from_raw_event(raw_event);

    // [ingest_repo.保存规范化事件]
    // 最后把统一事件写入观测主线,供下游聚合和告警继续消费。
    ingest_repo.save_event(event);
}
```

这段实现守住的边界是:
- observability 只吸收观测材料,不重写 source truth
- source tagging 和 context binding 必须先成立,后续聚合才可靠
- ingest 成功不代表 source 系统状态迁移成功

#### 5.2.5 该部分的边界与非职责
- 不负责 source truth 状态推进
- 不负责告警规则求值本体
- 不负责 dashboard 展示逻辑本体
- 不负责业务控制命令

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `执行与资源观测部分` 提供 execution / usage 事件输入
- 向 `治理、审计与漂移观测部分` 提供 audit / drift / deny 输入
- 向 `成本、用量与经营观察部分` 提供 cost / usage 输入
- 向 `查询、告警与诊断出口部分` 提供 health / diagnostic 原始事件基线

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `ObservabilityEvent ≠ source domain truth` 必须写死
- `ingestion ≠ source system state transition` 必须写死
- context binding 若不稳定,后续 audit/cost/drift 对账会整体失真

```rust
/// 根据 runtime / sandbox 事件重建执行与资源观察面。
fn build_execution_health_view(
    projection_repo: &dyn ExecutionObserveRepo,
    event: ObservabilityEvent,
) {
    // [event.校验执行观察输入]
    // 先确认当前事件确实属于 execution / usage 主线。
    event.validate_execution_observe_input();
```

```text
   │
   ▼
dashboards / health summaries / alerts / diagnostics
```

#### 关键说明

- ObservabilityEvent、HealthSummary、AlertTriggerRecord 属于强一致写路径
- execution views、drift reports、cost dashboards、diagnostic views 属于可最终一致读路径
- ExecutionHealthView / DriftReport / CostDashboard 绝不能反向成为 source truth 写源
- query / alert / diagnostic 的分歧必须回收到 event history 与 context binding 对账主线

### 7.5 关键函数/命令级伪代码

#### `BuildDriftReport`

```text
function BuildDriftReport(input):
    1. 校验输入事件属于 drift / audit / refresh 主线
    2. 读取 source refs 与 context binding
```

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| source event 缺失上下文 | 拒绝进入统一主线或标记 source gap |
| execution / drift / cost 视图上下文不一致 | 阻断 summary 构建 |
| alert backlog 积压 | backlog + retry,保留触发证据 |
| retention 规则误删仍需诊断材料 | 阻断清理并记录 retention conflict |
| dashboard 投影延迟 | 允许最终一致,但保留 stale 标识 |

### 11.1 重试 / 降级 / 熔断 / 补偿
- source systems 短暂失联时可保留现有视图并标 source gap,不得伪造事件
- alert channel 失败时可 backlog + retry,但不得静默丢失 AlertTriggerRecord
- dashboard / diagnostic 构建失败可重建投影,但不回滚 event truth

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 观测事件采集与统一接入部分 | 缺 source tag / 缺 context binding | ingestable shape validate | 拒绝写入或标记 gap | 补齐事件后重放 |
| 执行与资源观测部分 | execution 多源事件无法对账 | execution observe input validate | 阻断健康聚合 | 重新绑定上下文后重建视图 |
| 治理、审计与漂移观测部分 | drift / audit 视图缺 source refs | compliance observe input validate | 阻断 drift report | 补齐 refs 后重建 |
| 成本、用量与经营观察部分 | cost / usage 维度错位 | business observe input validate | 阻断 dashboard 更新 | 重聚合后回放 |
| 查询、告警与诊断出口部分 | health/alert 无法回指原始证据 | summary / rule scope validate | 阻断触发或输出 | 重建 summary / rule |

## 15. 结论

本详细设计的核心结论是：
- `L4-observability` 的实现主轴必须按 ingest / execution / compliance / cost / delivery 五个主要部分组织,而不是按 log/metric/trace 工具维度平铺
- observability 真相层只持有统一观测事件、聚合视图、告警与诊断结果,不接管各 source systems 的主真相
- 所有 health、alert、dashboard、diagnostic 输出都必须建立在正式 ObservabilityEvent、统一 context binding 与 append-only 证据链之上

后续测试与验收文档,应直接围绕这套统一观测主链、投影边界、告警出口与证据链展开.

### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 observability“能收事件”,而是系统验证 `L4-observability` 是否真正满足“平台观测与证据汇聚层”的设计要求,尤其要证明以下几点成立:
- ObservabilityEvent 构成统一观测接入主线,并能正确 source tagging / context binding
- `observability projection ≠ source truth` 成立,投影视图不会反写 runtime / sandbox / capability-hub / method-library / governance / artifact 真相
- `Trace / metric / log ≠ execution truth`、`Audit aggregation ≠ governance decision`、`Cost dashboard ≠ finance ledger truth`、`Drift report ≠ method-library truth` 等核心边界成立
- execution / drift / cost 三类观察面可以统一聚合并彼此对账
- health summary / alert / diagnostic 始终建立在正式观测证据链之上,且 `Health summary ≠ operational command`、`Alert rule ≠ source policy truth`
- retention / replay / source gap 主线成立,不会越权清理仍需诊断或对账的证据材料

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 观测事件采集与统一接入部分 | ingest / normalize 对象 | P0 | ObservabilityEvent、SourceTag、ContextBinding、EventEnvelopeRef |
| 执行与资源观测部分 | execution / usage 观察对象 | P0 | ExecutionHealthView、ResourceUsageView、RetryReplayView、QueueLatencyView |
| 治理、审计与漂移观测部分 | compliance / drift 对象 | P0 | AuditAggregationView、DriftReport、PolicyRefreshTrace、DenyTrendView |
| 成本、用量与经营观察部分 | cost / analytics 对象 | P0 | CostDashboard、UsageTrendView、ProviderCostSlice、ProjectCostSlice |
| 查询、告警与诊断出口部分 | delivery / alert 对象 | P0 | HealthSummary、AlertRule、AlertTriggerRecord、DiagnosticView、DashboardQuery |
| runtime / sandbox / capability-hub / method-library / governance / artifact 真相本体 | 非范围 | P2 | 只验 observability 如何消费其观测材料,不验这些仓的 source truth 全部实现 |
| 自动化响应执行逻辑 | 非范围 | P2 | 只验告警输出与证据链,不验下游执行命令 |
| finance 正式总账 | 非范围 | P2 | 只验成本观察面,不验财务系统本体 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数与局部不变量 | domain / policy owner | `raw_event.validate_ingestable_shape`、`event.validate_execution_observe_input`、`event.validate_compliance_observe_input`、`event.validate_business_observe_input`、`execution_view.validate_observe_summary_input` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + pipeline + projection + publisher 联动 | backend / domain owner | `IngestObservation`、`BuildExecutionHealth`、`BuildDriftReport`、`BuildCostDashboard`、`BuildHealthSummary`、`EvaluateAlertRules` | ingest、聚合、summary、alert 主线同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | runtime/sandbox → execution view、hub/method/gov → drift/audit/cost、artifact → result summary、summary → alert | 输入输出语义一致 |
| 恢复专项测试 | 验证 source gap、alert backlog、retention conflict、projection stale、context mismatch 等异常链 | architecture / QA | missing context、stale projection、retention overreach、alert retry | 证据不丢失、错误被正确阻断或留证 |
| 投影一致性测试 | 验证 execution/drift/cost/diagnostic 视图与主事件流一致 | backend / QA | execution view rebuild、drift report rebuild、cost dashboard rebuild、diagnostic rebuild | 投影只读且与主线一致 |
| 端到端主线测试 | 验证最小统一观测闭环 | QA / owner | ingest multi-source → aggregate → summary → alert / dashboard query | 观测闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| `observability projection ≠ source truth` | 所有视图和摘要只能读 source event,不能反写源仓 | 单元 + 集成测试 | 是 | model review / negative flow |
| `Trace / metric / log ≠ execution truth` | execution 健康面只能作为观察结果,不冒充 runtime/sandbox 真相 | 单元 + 事件链测试 | 是 | compare report |
| `Audit aggregation ≠ governance decision` | audit 聚合视图不能替代治理裁决真相 | 单元 + 集成测试 | 是 | payload compare / negative flow |
| `Cost dashboard ≠ finance ledger truth` | 成本看板只能表达经营观察面 | 单元 + 集成测试 | 是 | dashboard / ledger compare |
| `Drift report ≠ method-library truth` | drift 视图必须回指 source refs,不能冒充定义真相 | 集成 + 恢复测试 | 是 | drift report / compare |
| `Health summary ≠ operational command` | summary 只提供观察面,不直接触发运维动作 | 单元 + 事件链测试 | 是 | summary / control separation |
| `Alert rule ≠ source policy truth` | alert 规则只能消费观察视图,不替代上游策略 | 单元 + 集成测试 | 是 | alert rule scope / negative flow |
| retention 不可越权 | retention 不得清理仍需对账/诊断的材料 | 恢复专项测试 | 是 | retention conflict log |
| source gap 可识别 | 缺上下文或缺 source 材料时必须形成 gap/拒绝聚合 | 集成 + 恢复测试 | 是 | source gap record |

## 4. 环境与配置矩阵

| 环境 | 用途 | 依赖 | 关键配置 | 风险 |

| staging | 端到端演练 | real-like source events / query engine / dashboard read / alert consume dry-run | retention / backlog / stale mark / alert routing enabled | 聚合延迟与高并发 source 差异放大 |

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|
| S | 投影视图反写真相 / health summary 越界成控制命令 / drift 报告冒充权威真相 / retention 越权清理证据 / alert 污染 source policy |
| A | 主线可跑但 source gap、dashboard stale、alert backlog、cost/drift 对账不稳 | 原则上修复后再放行 |
| B | 非关键视图、低优先级 trend 或展示异常 | 可带风险进入下一轮 |

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 ingest / source tagging / context binding,都必须回归统一 ObservabilityEvent 主线
- 每次改动 execution / usage 聚合,都必须回归 execution health 与 summary 主线
- 每次改动 drift / audit / deny / refresh 聚合,都必须回归 compliance 观察面主线
- 每次改动 cost / usage dashboard,都必须回归经营观察面与 slices 主线
- 每次改动 alert / dashboard / diagnostic / retention,都必须回归 evidence、scope、只读输出与保留规则主线

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| 多租户 BI 与高级分析后续细化 | 测试矩阵需扩充 | TL / 架构 |
| 告警路由与自动化响应未来增强 | alert 规则与输出测试需增加更多样本 | observability / ops |
| retention / storage 成本增长 | 证据保留与重放策略测试需扩充 | platform / finance |

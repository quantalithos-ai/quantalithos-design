## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收目标表”“P0/P1/P2/Forbidden 裁决口径”“接缝与非范围表”和“核心闭环停审记录”小节，了解本轮验收为何以 observation boundary 而非业务真相聚合为主语。

本轮验收裁决五个核心闭环及其可落码边界：

1. 规范接入、安全处置、redaction 和 correlation 成立。
2. 审计投影与 body-free evidence linkage 成立。
3. safe log、metric、trace 和 signal projection 成立，且不冒充 execution truth。
4. Query、diagnostic、report handoff 和 authenticity hint 只读、可降级、可追溯。
5. retention protection、rebuild/replay、UoW、幂等和 no-write 边界成立。

| 范围项 | 优先级 | 验收目标 | 本轮不裁决 |
|---|---:|---|---|
| 五个核心能力闭环 `C-OBS-1~5` | P0 | 正向、负向、状态、证据和红线均可判定 | 外部产品内部 truth |
| 16 Command | P0 | exact request/result/error、accepted side effect、duplicate 和失败边界 | 新增 command |
| 14 Query | P0 | exact response、缺失/不可见/降级和 strict zero-write | Query inline repair |
| 9 Inbound Consumer | P0 | header/schema/binding、local landing、ack-after-commit、fail-closed | 相邻仓业务 truth |
| 12 Outbound Event | P0 | committed immutable snapshot、binding、publication marker | downstream consumed truth |
| 9 Operations Job | P0 | immutable plan、claim/fence、item/report fold、derived-only | 未闭合 H13 的 positive replay |
| 27 formal state owner + 1 technical state | P0 | legal/illegal/terminal/reserved transition 和副作用 | technical state 作为业务 truth |
| UoW、幂等、CAS、并发、恢复 | P0 | accepted effect set、rollback、probe、same-token 和 no-write | 具体物理数据库产品 |
| 三 profile / 六 lane / 五 script-check | P0 结构合同 | 配置、真实性和证据可判定 | 未建立环境的通过结论 |
| real-like adapter / external product / cross-repo E2E | P1 或 selected scope | product-neutral seam、availability、binding 和降级 | 默认成为 P0 前置 |
| capacity、硬 P95/SLO、长期 retention 天数 | P2 / future | 仅在来源冻结后验证 | 没有来源的数字门禁 |
| dashboard、alert、analytics、APM/GRC 深度 UX | P2 / future | 只验证消费边界和不污染 truth | 本仓核心 truth 或最终裁决 |

以下内容为 forbidden：raw request/event/log/metric/trace/provider/runtime/archive body、secret/credential、full
sensitive ref、外部 source truth 正文、静态 evidence/verdict/signoff、Query/job/report 对 source truth 的写入、非
`L0-core/core-contracts` sibling 编译期依赖、历史材料直接升级为 current gate。

### 3.1 Canonical evidence roots

```text
artifacts/test/<run_id>/
reports/runs/<run_id>/
reports/acceptance/
reports/review/
```

机器原始证据只能位于 `artifacts/test/<run_id>/`；人类可读运行报告只能位于 `reports/runs/<run_id>/`；验收交接和
风险记录只能位于 `reports/acceptance/`；人工/Agent 审查材料只能位于 `reports/review/`。禁止 `latest`、项目名前缀
root、临时绝对路径、跨 run 拼接和静态手写 evidence index。

### 3.2 Current evidence truthfulness

`TC-OBS-<family>-<nnn>` 是稳定测试用例 ID，`DS-OBS-<family>-<nnn>` 是稳定数据集 ID，`EV-CAND-OBS-<family>-<nnn>` 是 planned candidate linkage，
`<run_id>` 才是真实 invocation 身份。当前没有真实 run、artifact、report 或 evidence；因此正文不填写任何正式
`EV-OBS-<family>-<nnn>` alias、artifact digest、passed、verdict、signoff 或 review approval。

### 4.3 暂停与退出

| 情形 | 流程状态 | 恢复/裁决动作 |
|---|---|---|
| baseline/run/artifact/report 不可证明 immutable 或 same-run | `pause_not_adjudicable` | 修复 provenance，建立新 baseline/run |
| raw body/secret/forbidden material 进入证据或报告 | `fail_veto_and_pause` | 保留 finding，修复后按受影响面重跑 |
| static evidence、`latest`、手写 passed/verdict | `fail_veto_and_pause` | 删除伪权威关系，基于真实 raw 重新生成 |
| required runner/lane 不可用但有完整 unavailable record | `blocked_adjudicable` | 可裁决为阻断/不通过，不得 fallback |
| inherited owner gap 仍开放 | `blocked_positive_path` | 回写 owner、更新测试映射和 baseline |
| commit/external completion indeterminate | `indeterminate` | 依正式 probe/manual 路径收口，禁止盲重试 |
| handoff/review 未完成 | `handoff_incomplete` | 完成人工/Agent review，final decision 为空 |

未被低等级结果替代；缺陷、风险、handoff、review 和签署字段完整；最终只允许 `通过`、`有条件通过`、`不通过`。
当前这些真实退出条件均未执行。

### 5.5 功能验收裁决

`AC-OBS-001~031` 的真实状态必须逐项来自同一验收基线和真实 run。任一 required P0 AC 失败，最终结论不得为
`通过`；若失败同时命中 `VF-OBS-001~010` 或 `S` 级缺陷，不得通过风险接受转为 `有条件通过`。`planned_conditional`、
`planned_blocked_controlled`、`planned_not_evaluated` 只能表示设计期或执行期的限制，不能进入正向通过计数。

`AC-OBS-001~005` 组成五个核心闭环，`AC-OBS-006~018` 覆盖功能能力，`AC-OBS-019~024` 覆盖规则和架构边界，
`AC-OBS-025~028` 覆盖数据归属，`AC-OBS-029~031` 覆盖非功能与验收完整性。正式验收时必须做反向 orphan 审计：
每个 AC 都要能回到至少一个 exact TC 和 candidate linkage；每个 P0 TC 也必须能回到至少一个 AC，不能通过
“证据见测试报告”建立隐式关系。

当前状态：31 个 AC 均为 `designed_not_executed`；真实实现、run、artifact、report、evidence、review 和 signoff
均不存在，不填写任何 `passed`、`failed` 或最终结论。

### 6.5 红线裁决

验收必须对 7 个 owned data family、4 个 projection/snapshot/idempotency family、4 个 reference/digest/order/correlation
boundary、4 个 forbidden material family 和 8 个 architecture/product/history redline 分别留存结果。真实 dependency
graph、writer scan、redaction scan 和 raw/report 扫描未建立时，状态必须为 `not_run` 或 `not_evaluated`，不得以
设计表的完整性替代执行通过。

任何 source truth writer、forbidden body/secret、non-core compile edge、static evidence、历史材料 fallback 或产品
truth ownership 转移都属于 hard failure；不得通过风险接受弱化。I05 缺 schema/binding 时只允许 pre-parse/schema/binding
fail-closed，J06 只允许 controlled `Blocked/manual`，不能由本章发明 positive DTO、owner 或 completion。

当前新上游 blocker 为 `none`；12 项 inherited affected 仍开放，详见 §13。当前红线执行状态全部未建立。

### 7.8 协议门禁裁决

| Family | exact 数量 | Current 设计闭环 | 正向限制 |
|---|---:|---|---|

| **总计** | **60** | **60/60，0 orphan，0 duplicate** | **`designed_with_affected_open`** |

## 10. 可观测性、审计与证据门禁

> 校准来源：
> - `design-calibration/06_acceptance_step_10_observability_evidence.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“本仓观测材料分层与 truth boundary”“Redaction / forbidden material 门禁”“Runtime observation/audit evidence gates”“Acceptance run evidence gates”“Canonical paths 与交接审查”和“跨证据裁决审计”小节，了解运行观测材料如何与验收证据链分离。

本章验收两个必须分离但可相互追溯的链：runtime observation chain 和 acceptance evidence chain。前者只产生本仓
observation-side fact、projection、marker、handoff 和 safe telemetry；后者只从同一 `<run_id>` 的原始 artifact、
suite、check、report 和审查材料形成验收输入。二者都不得拥有业务 source truth、外部正文、最终 verdict 或 signoff。

### 10.1 观测材料分层与归属

| 层 | 允许承载 | 必须具备 | 明确禁止 |
|---|---|---|---|
| Layer A：runtime telemetry | safe log、metric、trace、correlation、causation、phase 和 typed outcome | finite field/label allowlist、redaction 前置、post-commit timing、sink failure suppression | raw body、secret、credential、provider/runtime/archive body、业务 truth |
| Layer B：durable observation fact | receipt、safety/disposition、correlation link、audit projection、signal、gap、retention marker、no-write violation | 唯一 owner、版本/状态、history 或 membership、body-free ref、同一 UoW 的结果关系 | 外部 source truth、证据正文、由 telemetry 猜测 durable 状态 |
| Layer C：propagation / execution material | immutable snapshot、outbox event、delivery/export intent、job plan/item/report、rebuild progress | committed snapshot、binding、token、claim/fence、phase-local finalize、失败/阻断可追溯 | 把 publish/deliver/job completion 当下游 truth 或最终验收结论 |
| Layer D：read / handoff surface | Query response、diagnostic composite、report handoff、authenticity hint、review input ref | 每次 request 独立 visibility/freshness/gap、strict zero-write、canonical path 和 provenance | Query repair、source truth 写入、静态 evidence/verdict/signoff |

以上四层的 accepted mutation、状态迁移、外部 phase 和 handoff 均必须回指 `03` 的 exact owner、协议、UoW 和错误
契约。log、metric、trace、audit event 只提供安全观测、关联或审计投影，不能反向成为任何业务真相的 authority。

### 10.2 观测材料门禁

| Gate | 主题 | 通过条件 | 失败条件 | Exact 入口与影响 |
|---|---|---|---|---|

### 10.3 Redaction、correlation 与 no-write 裁决

验收必须证明 redaction 发生在 serialization、durable append、outbox append、report generation 和 acceptance/review
交接之前。负向 corpus 命中时，系统必须返回明确的 rejected、quarantined、blocked 或 manual 结果，并保留安全的
失败关系；不能以空字符串、截断正文、hash/base64 或 debug dump 代替脱敏。metric label 只能来自有限枚举，不能
承载 ref、idempotency key、digest、自由文本或动态 handler/route。

correlation id、trace id、causation id 和 source identity 只用于把事件、投影、结果和报告关联起来。它们不得推导
不存在的业务状态，也不得覆盖已持久化的 trusted context。缺失、部分绑定、不可比较和 stale 必须作为显式状态或
gap 输出。Query、diagnostic、report、export、rebuild、replay、telemetry 和 acceptance generator 均不得写入
业务 source truth；任一 source writer call 或 truth delta 非零都属于硬失败，并按 `VF-OBS-004/005` 裁决。

### 10.6 Canonical evidence roots 与真实性

未来 raw artifact 只能位于 `artifacts/test/<run_id>/`；人类可读 run report 只能位于

### 11.1 否决证据与状态规则

每项 VF 必须在未来 `reports/acceptance/veto-checklist.md` 中逐项记录正式来源、适用 AC/NFR/TC、同 run evidence
或 raw/report path、review 状态和 finding/缺证原因。合法的运行期状态至少区分：

| 状态 | 含义 | 是否可作为“未触发” |
|---|---|---|
| `triggered` | 真实材料证明红线命中 | 否；总体不通过 |
| `not_triggered_reviewed` | required evidence 完整，具名 reviewer 完成逐项审查且确认未命中 | 是，仅作为该 VF 输入 |
| `blocked` | required runner、raw、report、resolver 或审查材料缺失，但缺失原因可追溯 | 否；不可正向裁决 |
| `not_evaluated` | 该 VF 不在冻结 scope，或其前置条件明确未选择 | 否；不得等同未触发 |
| `planned` | 设计期 gate 合同，尚无真实执行材料 | 否；当前正式文档只能处于此语义 |

`EV-CAND-OBS-<family>-<nnn>` 不能把 `planned` 自动转换为 `not_triggered_reviewed`。`Delivered`、`RealEvidenceLinked`、metric
clean、audit append、suite summary 或人工说明都不能单独产生 VF 结论。缺 evidence、wrong run、scanner 未执行、
静态 passed、`latest` 或 report provenance 断裂时，优先按证据完整性门禁暂停，不得用“未发现问题”替代审查。

### 11.2 VF 与风险接受、缺陷的关系

1. 任一 `VF-OBS-001~010` finding 直接升级为 `S` 级缺陷；不得改写成 `A/B/R`。
2. VF、S 级缺陷、forbidden body、truth owner 反转、source writer 非零、protected delete 和证据真实性失败均禁止
   风险接受。
3. 修复后的 VF 必须按 §12 创建新的 `<run_id>`，保留失败前 raw artifact/report，执行受影响 family、suite、check
   和必要的 full release gate；`RetestPassedCandidate` 不等于 VF 已关闭。
4. 只有真实 reviewer 在新证据链上完成逐项复核，且缺陷生命周期达到 `Closed`，才能把该项作为最终裁决输入；不由
   report generator、telemetry 或 final signer 自动填充。

当前实现仓、CI、真实 run、artifact、report、evidence、review 和 signoff 均不存在，因此本章不填写任何 VF 的实际
“未触发”或“已触发”结论。12 项 inherited affected 继续开放；I05 维持 fail-closed，J06 维持 controlled
`Blocked/manual`，不得借本章的设计覆盖审计制造 positive capability。

## 12. 缺陷分级、复验与放行规则

> 校准来源：
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“缺陷等级与结论影响”“S 级不可降级判定”“修复后复验范围决策矩阵”“缺陷生命周期与状态约束”“关闭证据清单”和“放行规则”小节，了解缺陷如何影响验收裁决、复验范围和最终放行。

本章使用唯一的 `S/A/B/R` 缺陷等级。缺陷记录描述真实运行或审查中发现的事实；设计期只固定分级和复验合同，
不填写真实 defect ref、run、finding、severity、修复结论或关闭签署。

### 12.1 缺陷等级与结论影响

| 等级 | 定义 | Observability 例子 | 对验收结论的影响 | 可否风险接受 |
|---|---|---|---|---|
| `S` | 命中任一 `VF-OBS-001~010`，或 P0 truth、redaction、body-free、no-write、active retention、dependency、evidence authenticity、commit-unknown 二写等硬红线失守 | raw body 入 report；Query 写 source truth；protected material 被删；forbidden sibling edge；静态伪造 evidence；stale worker 二写 | 未关闭只能“不通过”；不得有条件通过 | 否 |
| `A` | P0 用例或 blocking suite 失败，或 P0 能力无法稳定证明，但尚未证实 VF 或 truth corruption | typed error mapping 错误；配置半激活但已 fail closed；required report 缺非真实性字段；harness 无法复现 P0 case | 默认阻断；仅严格满足 §13 条件时进入有条件通过候选 | 仅严格条件下候选 |
| `B` | 不影响当前 P0 语义、主证据链或退出硬门禁的一般实现、报告或环境问题 | 非阻断可读性；无来源数字的 duration sample；P1 adapter 维护性问题 | 不阻断 P0；必须记录并跟踪 | 可，需记录 |
| `R` | 当前非范围、外部前置未建立或未来能力 residual，不构成当前实现 failure | production capacity、未建立 RuntimeLike 深层行为、未选外部产品 SLA | 不自动阻断当前范围；不能写成已验证能力 | 可作为 residual 候选 |

### 12.2 S 级不可降级规则

下列任一事实必须定为 `S`，且不能降为 `A/B/R` 或交由风险接受：

1. 五个核心闭环失守、duplicate/commit unknown 导致第二次 owner mutation、accepted partial commit 或 stale fence 二写。
2. forbidden body、secret、credential、full sensitive ref、high-cardinality label 或 report 二次泄露。
3. observation/telemetry/handoff 被当作业务、治理、Artifact、Identity、runtime execution 或 archive truth。
4. Query、diagnostic、rebuild、replay、report、export 或 telemetry 发生 source write、truth repair 或执行控制越权。
5. active、held 或 referenced material 被删除，或 retention marker/active protection 被绕过。
6. 静态 evidence、wrong run、`latest`、fake verdict/signoff、cross-run 拼接或 report provenance 伪造。
7. 非允许 sibling 编译期依赖、`L0-bus` package dependency、外部产品成为 truth source/hard prerequisite，或历史材料升级为 current truth。

任何新 finding 命中 `VF-OBS-001~010` 时立即按 `S` 处理。scanner 未执行、raw/report 缺失或 provenance 无法证明时，
不应擅自判为“未命中”；按证据完整性规则保持 `blocked/not_evaluated`，并阻断正向放行。

### 12.3 修复后复验范围

每次复验必须创建新的 invocation 和 `<run_id>`，保留失败前 raw artifact/report，并保持失败前后 run identity 不同。
复验不是修改旧报告、复制 artifact 或只运行一个绿色单例。

| 影响面 | 最小复验 | 必须追加 | 进入 full release gate 的条件 |
|---|---|---|---|
| 单一 fixture/assertion，未改共享契约 | 原失败 TC、同切口正/负向 | 该 TC 的 primary suite | 该 TC 属于 release evidence 或核心组合 |
| public DTO、enum、state、typed error、transition | 原失败 TC | `S-OBS-CONTRACT-DOMAIN`、关联 `S-OBS-SERVICE-FLOW` | 触及 VF、核心闭环或跨协议状态 |
| UoW、repository、idempotency、commit unknown、stored result | 受影响 `TC-OBS-UOW-001~008` | `S-OBS-REPOSITORY-CONFORMANCE`、`S-OBS-SERVICE-FLOW`、`TC-OBS-REB-001~006` | 总是；这些语义影响 accepted truth/evidence chain |
| Query、diagnostic、visibility、freshness、no-write | 受影响 `TC-OBS-QRY-001~004`、`TC-OBS-DIA-001~004`、`TC-OBS-DEG-001~005` | `TC-OBS-NW-001~005`、`S-OBS-SERVICE-FLOW`、`S-OBS-STATIC-REDLINE` | 进入 release read/report chain或触及 `VF-OBS-005` |
| redaction、serializer、log、metric、trace | 受影响 `TC-OBS-RED-001~004`、`TC-OBS-SIG-001~006` | `S-OBS-TELEMETRY-SAFETY`、`scripts/checks/check_redaction.sh`、`scripts/checks/check_metric_labels.sh`、全 root scan | 总是；安全和证据真实性不可局部放行 |
| audit、evidence linkage、authenticity | 受影响 `TC-OBS-AUD-001~004`、`TC-OBS-EVD-001~004`、`TC-OBS-AUT-001~003` | `S-OBS-SERVICE-FLOW`、`S-OBS-ENTRY-CAPABILITY`、`S-OBS-TELEMETRY-SAFETY`、`report-audit.md` | 触及 P0 evidence、`VF-OBS-003/006` 或 handoff |
| outbox、external phase、Job、replay、fence、report fold | 受影响 `TC-OBS-UOW-006~008`、`TC-OBS-REB-001~006`、`TC-OBS-RPT-001~005`、`TC-OBS-EXT-001~003` | `S-OBS-REPOSITORY-CONFORMANCE`、`S-OBS-RECOVERY-REPLAY`、`TC-OBS-RPT-003~004`、`TC-OBS-UOW-007~008` | 触及 delivery 或 report release path |
| retention、active protection、cleanup | 受影响 `TC-OBS-RET-001~005` | repository suite、no-delete capability scan、handoff cases | 触及 active material、legal hold 或 `VF-OBS-007` |
| config、runtime builder、profile activation | 受影响 `TC-OBS-CFG-001~006` | `S-OBS-CONFIG-REDLINE`、受影响 profile contract smoke | required profile 或 `VF-OBS-009/010` 受影响 |
| dependency、ownership、historical corpus | 受影响 `TC-OBS-DEP-001~003`、`TC-OBS-OWN-001~004`、`TC-OBS-HIST-001~002`、`TC-OBS-TRUTH-001~003`、`TC-OBS-NW-001~005` | `S-OBS-STATIC-REDLINE`、`scripts/checks/check_dependency_boundary.sh`、documentation/report audit | 总是；静态红线不能局部关闭 |
| report generation、evidence provenance | 受影响 `TC-OBS-RPT-001~005`、`TC-OBS-AUT-001~003` | `S-OBS-TELEMETRY-SAFETY`、`S-OBS-STATIC-REDLINE`、`report-audit.md`、`evidence-index.md`、`scripts/checks/check_redaction.sh` | 总是；没有同 run provenance 不能关闭 |
| RuntimeLike 或未来 external behavior | 同 lane/family 的受影响 case | 保留真实性等级，不能用 CI/controlled 替代 | 只有正式升级为 required P0 时才进入 |

### 12.4 缺陷生命周期与关闭证据

| 状态 | 进入条件 | 允许动作 | 禁止动作 |
|---|---|---|---|
| `Reported` | 有 failed run/case/reason，或设计期记录 planned rule gap | triage，关联 TC/suite/VF/AC | 直接写 closed/passed |
| `Triaged` | severity、owner、影响面、复验范围已确认 | 修复或记录外部 blocker | 将 S/VF 降级为风险 |
| `InFix` | fix boundary、设计基线和影响面已固定 | 在受影响实现边界修复 | 顺手改无关 truth/baseline |
| `ReadyForRetest` | 修复检查完成，新的复验输入齐全 | 按本章范围执行 | 用旧 run/candidate EV 代替新证据 |
| `RetestFailed` | targeted、family、gate 任一失败 | reopen、升级、扩大范围 | 关闭或接受 S |
| `RetestPassedCandidate` | 所需复验完成且报告可回指 | 请求 reviewer/Agent 审查关闭材料 | 自动生成 verdict/signoff |
| `Closed` | 关闭清单完整，S/A 有审查，失败前材料保留 | 归档并加入回归集 | 删除失败证据、重写历史 finding |
| `Residual` | 仅 B/R，且有 owner、trigger、follow-up | 交 §13/§14 风险处理 | 冒充 P0 已验证 |

S/A 缺陷至少需要 defect ref、severity、affected AC/VF/TC、失败前 `<run_id>`、raw/report、failure reason、design
baseline、fix boundary、复验 `<run_id>`、targeted/family/gate report、必要的 redaction/metric/dependency/provenance
check、before/after 分析和 reviewer closure note。B/R 按影响保留同样的可追溯字段。缺 required artifact/report、
wrong run、orphan candidate、`latest`、静态 passed 或 scanner 未执行时，缺陷不得关闭。

`RetestPassedCandidate` 只表示满足复验清单的关闭候选；`Closed` 只产生 defect closure fact，不生成 acceptance
verdict、正式 evidence alias、final decision 或 signoff。

### 12.5 放行规则

| 条件 | 正向放行 | 处理 |
|---|---|---|
| 未关闭 `S` 或任一 VF 命中 | 否 | 不通过或暂停；按 full affected scope 修复复验 |
| redaction、metric、dependency、report provenance failed | 否 | 证据链无效；同 run 或新 run 补齐并复验 |
| required P0 suite/check 未执行，或 artifact/report 缺失 | 否 | 保持 `blocked/not_run`；不得由低等级 lane 或 summary 填充 |
| source writer 非零、truth delta 非零、Query/Job truth repair | 否 | S 级阻断；修复 capability/flow 后全量受影响复验 |
| 未关闭 `A` 影响 P0 或正式退出条件 | 否 | 修复并复验；不能直接接受 |
| 未关闭 `A` 不影响 P0 truth/evidence，且满足 §13 eligibility | 仅有条件候选 | 逐项记录风险，不自动放行 |
| 仅有 B/R 且有完整 residual 记录 | 视 §13/§14 | 不得写成无条件 P0 通过 |

本章不产生真实缺陷或放行事实。当前 target implementation、CI、真实 run、artifact、report、evidence 和 signer 均
不存在；12 项 inherited affected 继续开放，I05/J06 仍按 fail-closed/controlled 规则处理。

## 13. 风险接受与遗留项

> 校准来源：
> - `design-calibration/06_acceptance_step_13_risk_acceptance.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“Eligibility 判定合同”“测试侧 residual 来源处置”“风险接受记录合同”“生命周期、失效与重开”“Inherited blocker / affected 隔离”和“风险接受到最终裁决的输入规则”小节，了解哪些遗留项可进入有条件通过候选，以及哪些缺口必须回到设计或真实证据链。

风险接受只处理在真实证据下已经证明不污染 P0 truth/evidence 的受限 residual。它不是修复缺陷、补齐证据、关闭上游
owner gap 或改变验收范围的替代机制。风险记录属于验收流程 truth，不属于 Observability runtime truth，也不得反写
业务、治理、Artifact、Identity、runtime execution 或 archive truth。

### 13.1 Eligibility 判定

风险条目只有同时满足下列条件，才可进入 `EligibilityChecked`，并由授权角色决定是否接受：

| Gate | 必须满足 | 不满足时 |
|---|---|---|
| `ELG-OBS-01` source | 有稳定 source ref：B/R defect、P1/P2/future/operations item 或未冻结的非 P0 条件 | `Draft`，不得裁决 |
| `ELG-OBS-02` no-veto | `VF-OBS-001~010` 均未因该风险命中，且条目不是 S 级 | `Ineligible` |
| `ELG-OBS-03` p0 | 全部受影响 P0 AC、required suite/check 和退出条件有独立真实证据 | `blocked`，不能风险接受 |
| `ELG-OBS-04` integrity | raw artifact、suite report、candidate linkage、report audit 同 run 且可追溯 | `blocked`，先补证据 |
| `ELG-OBS-05` boundary | 不改变 truth owner、writer capability、redaction、body-free、dependency 或 retention protection | `Ineligible` |
| `ELG-OBS-06` scope | 影响面、排除面、release/review/baseline/run set 明确 | `Draft` |
| `ELG-OBS-07` accountability | owner 与具名、获授权的 acceptor 均存在，职责不混淆 | 不得支持有条件通过 |
| `ELG-OBS-08` closure | 有可验证 action、follow-up ref、deadline/trigger、补验范围和重开规则 | 不得支持有条件通过 |
| `ELG-OBS-09` affected | 不把 §12 或本章 inherited affected 的未闭合 positive capability 写成 residual 完成 | `Ineligible`，回上游/设计闭合 |
| `ELG-OBS-10` currency | 接受记录未到期，绑定输入没有变化 | `Expired`，重新审查 |

下列事项永远不可接受：任一 VF、任一 S 级；P0 required execution/evidence 缺失；source writer/truth delta 非零；
raw body、secret、full sensitive ref 或 evidence 正文越权；非法 sibling dependency；protected material 被删除；静态
run/evidence/verdict/signoff；以及通过风险记录伪造 I05/J06 或其他 inherited affected 的 positive capability。

### 13.2 Residual 来源与边界

| Residual | 候选分类 | 只有在下列条件下可讨论 | 升级为阻断的条件 |
|---|---|---|---|
| `RR-OBS-001` 真实产品 seam 未认证 | `candidate_product_binding` | 本次只要求 product-neutral seam，且 exact contract/no-write 有真实证据 | 本次 release 绑定该产品，或产品行为成为 required P0 |
| `RR-OBS-002` RuntimeLike 未建立 | `candidate_scope_dependent` | `ENV-STG-RT` 未列为 required，且不声称 RuntimeLike pass | release profile 将其列为 required |
| `RR-OBS-003` capacity / 硬 P95/SLO 未验证 | `candidate_threshold_absent` | 没有正式 workload、样本、阈值、统计 owner，只记录 sample/trend | 需求冻结 numeric gate，或出现结构性资源/正确性 failure |
| `RR-OBS-004` 完整跨仓 E2E 未执行 | `candidate_scope_dependent` | current P0 只要求 product-neutral seam 与 truth boundary | 送验范围要求真实多仓工作流 |
| `RR-OBS-005` 长期 retention 天数未固定 | `candidate_operations` | marker/hold/reference/cleanup protection 已独立验证，只缺期限/介质策略 | active/held/referenced material 可能被清理，或法规期限成为 P0 |
| `RR-OBS-006` 外部 archive/APM/GRC/dashboard 未验证 | `candidate_product_binding` | 外部产品不是 truth owner、不是当前硬前置 | release 绑定该产品或其行为成为 required |
| `RR-OBS-007` 高级 dashboard/analytics/alert UX 未覆盖 | `candidate_p2` | 明确属于 Out of Scope/P2，不反向改变本仓 schema/state/gate | 正式需求升级为 required |
| `RR-OBS-008` 真实 evidence alias / 签署不存在 | `ineligible_prerequisite_absent` | 无；这是当前验收事实缺失，不是 residual | 始终阻断真实正向结论，直至真实执行和裁决完成 |
| `RR-OBS-009` affected positive path 未闭合 | `separated_inherited_affected` | 不进入普通风险接受，只按 owner/设计/实现边界闭合 | 伪造 positive DTO、Completed、owner 或 evidence 时按 VF/S 裁决 |

`RR-OBS-001~009` 是候选来源分类，不是已接受风险，也不自动创建 risk ID。无来源的性能、容量、长期保留数字只允许作为
sample/trend 记录；不得升级为当前 pass/fail threshold。

### 13.3 风险接受记录合同

真实 `reports/acceptance/risk-acceptance.md` 每条记录至少包含：

| 字段 | 必填 | 约束 |
|---|---|---|
| `risk_id`、`source_ref`、`residual_class` | 是 | 稳定唯一；回指 B/R、`RR-OBS-001~009` 或正式待确认项，不使用自由文本标题代替 |
| `review_version`、`baseline_refs` | 是 | 绑定需求、设计、配置、测试、delivery 和本次 review；禁止 `latest` |
| `affected_scope`、`excluded_redlines`、`impact` | 是 | 逐项列 AC/NFR/protocol/profile/lane/release；明确不覆盖 VF/S/truth/redaction/no-write/dependency/evidence/retention |
| `acceptance_reason`、`p0_non_contamination_proof` | 是 | 说明为何是 residual，并以独立 P0 evidence 证明不污染主线 |
| `evidence_refs` | 是 | 真实同 run raw/report/index/review refs；candidate ID 单独不足 |
| `owner`、`acceptor` | 是 | 均须具名；acceptor 必须拥有对应授权范围 |
| `follow_up_action`、`follow_up_ref` | 是 | 可执行、可验证，不能写“持续观察”或“后续优化” |
| `deadline_or_trigger`、`retest_scope` | 是 | 明确日期或客观事件，以及 targeted/family/suite/check/full gate 组合 |
| `expiry_rule`、`reopen_conditions` | 是 | release/review/baseline/run 变化、期限、VF/S、新证据、复发或范围升级均可失效/重开 |
| `decision_status`、`decision_ref` | 是/条件 | 状态遵循 §13.4；当前不得预填 `Accepted`，接受时必须有独立决定记录 |

风险表不得包含 secret、raw body、credential、evidence/artifact body 或 full sensitive ref，只能使用 body-free ref、
digest、run identity 和 canonical report path。

### 13.4 生命周期、失效与重开

| 状态 | 含义 | 是否支持有条件通过 |
|---|---|---|
| `Draft` | 候选来源或字段/证据未齐 | 否 |
| `EligibilityChecked` | 已完成机械 eligibility 检查，尚未授权接受 | 否 |
| `Accepted` | 具名授权 acceptor 在有效 scope 内接受，记录完整且未失效 | 是，但只作为 §14 输入 |
| `Rejected` | 不在授权范围、影响不可接受或应先修复 | 否 |
| `Expired` | 截止/触发已到或绑定输入变化 | 否 |
| `Closed` | follow-up 完成且新证据复核通过 | 否；关闭不是历史 release 的重新签署 |
| `Reopened` | 复发、新证据或范围变化使原判断失效 | 否，重新进入 eligibility |

`Accepted` 在 review version、release candidate、需求/设计/配置/测试 baseline、绑定 run set、受影响 AC/NFR/VF/协议/状态、
deadline/trigger、owner/acceptor、evidence refs 或 scope 发生变化时立即失效。出现 VF/S、redaction leak、source write、
dependency violation、evidence mismatch、protected cleanup 或同类缺陷复发时必须重开。旧记录只读保留，新记录通过
`supersedes_ref` 或原 risk ID 建立 lineage，不得滚动延长期限、删除历史或覆盖原决定。

### 13.5 Inherited affected 隔离与下游承接

以下 12 项继续开放，不能进入普通风险接受，也不能由“有条件通过”宣称其 positive capability 已完成：

`S08-E-I05-PAYLOAD-SCHEMA-01`、`S08-E-I05-PRODUCER-EVENT-BINDING-01`、`R06.6-F2-H13-UPSTREAM`、
`R06-F-AFFECT-UOW-01`、`S08-RECOVERY-CLASS-OWNER-01`、`R07-EXTERNAL-PHASE-LINK-01`、
`R07-EXTERNAL-PHASE-RETRY-ACCOUNTING-01`、`S08-CONSUMER-OUTBOX-SURFACE-01`、
`S08-CONSUMER-INDETERMINATE-COMPLETION-01`、`S08-JOB-REPORT-REF-OWNER-01`、
`S08-M1-SECONDARY-TYPE-OWNER-01`、`03-RPR-S09-PER-FLOW`。

处置规则：

1. I05 只允许 pre-parse/schema/binding fail-closed；不得本地发明 payload DTO、producer binding 或 positive landing。
2. J06 只允许 observation-side controlled `Blocked/manual`；不得发明 H13 positive execution、external receipt、
   `Completed`、真实 run 或 evidence alias。
3. UoW、recovery、external phase、consumer completion、report ref、secondary owner 和 per-flow proof 保持
   `open/controlled/blocked/conditional`，由正式 owner 和后续 implementation boundary 闭合。
4. 若未来 release 正式排除相关 capability，必须先通过 baseline/scope 变更重新审查受影响 AC/TC/VF；不能只写风险
   记录完成降级。
5. affected 的存在本身不是 defect 或 risk acceptance；只有实际违反 fail-closed、发生 source write、伪造 positive
   或破坏证据时，才按实际 finding 进入 VF/S。

下游实施计划可以承接 implementation/protocol/owner、RuntimeLike/E2E、external binding、性能、retention 和 P2
遗留，但本章不修改 `07`。每个 follow-up 必须能回到具体 boundary、issue、ADR、runbook 或新的测试/证据基线，只有
自由文本承诺的条目保持 `Draft`。

### 13.6 风险接受到最终裁决的输入

| 当前材料 | 交给 §14 的状态 | 允许的总体候选 |
|---|---|---|
| 无 residual，全部 required P0 真实通过，无 VF/S | 无风险接受输入 | `通过`候选 |
| 只有完整、有效、未过期的 `Accepted` residual，全部 P0 独立成立 | 带 risk record 进入签署 | `有条件通过`候选 |
| `Draft`/`EligibilityChecked`，缺 acceptor/action/deadline/evidence | open | 不得正向裁决 |
| `Rejected`/`Expired`/`Reopened` | invalid | 不得有条件通过 |
| 任一 VF/S、required P0 未执行、证据失真或 affected 被伪造完成 | blocked/failed | `不通过`或流程暂停，由 §14 聚合 |

单项 `Accepted` 永远不直接生成总体结论。当前没有真实实现、run、artifact、report、evidence、risk acceptor 或 signer，
因此本章不填写任何实际风险接受、条件通过或最终结论。

## 14. 最终结论与签署

> 校准来源：
> - `design-calibration/06_acceptance_step_14_final_decision_signoff.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“三值最终结论合同”“结论维度与聚合矩阵”“进入下一阶段与发布准备”“签署角色与最小职责”“签署记录字段合同”“Canonical 验收与审查包”和“签署含义与失效”小节，了解最终裁决如何在证据、缺陷、风险和专业签署全部一致后形成。

本章定义最终验收记录的裁决合同，不生成当前结论。`通过`、`有条件通过`、`不通过`是唯一允许的最终结论；
`pause_not_adjudicable`、`blocked_adjudicable`、`review_in_progress` 和 `retest_required` 是流程状态，不是第四种
结论。当前 target implementation、delivery、CI、RuntimeLike、真实 run、artifact、report、evidence、risk record
和 signer 均不存在，因此本章只保留未来字段和判定规则。

### 14.1 三值最终结论

| 最终结论 | 必须同时满足 | 明确禁止 | 后续语义 |
|---|---|---|---|
| `通过` | baseline/selected run 固定；全部 required P0 门禁通过；10 个 VF 有真实 `not_triggered_reviewed` 输入；S=0、A=0；无影响结论的 open residual；证据与签署完整 | blocked/not_run/not_evaluated 冒充 pass；风险记录代替 P0 evidence；低真实性 lane 替代 required lane | 可进入下一阶段和独立发布准备评估，不等于 production release |
| `有条件通过` | 与 `通过` 相同的 P0、VF、S 和 evidence 硬前提；仅剩逐项有效、未过期且获授权的 A/B/R/P1/P2/future/operations residual | 任一 VF/S、required P0 缺失、硬门禁失败、affected positive 未闭合或无 acceptor/deadline/action | 可按条件进入下一阶段；条件失效即重开 |
| `不通过` | 至少一个可复核 P0/VF/S/hard gate failure，或 baseline 明确 required 的 capability 有真实 blocked/not_run record | 用模糊“不通过”掩盖无法定位被测物、run 或证据篡改 | 修复后按 §12 新 run 复验并重新裁决 |

`failed`、`blocked`、`not_run`、`not_evaluated`、`conditional` 和 `indeterminate` 是门禁或流程输入，必须先保留原
状态，再按本章聚合。没有合法 baseline、run identity、raw/report provenance 或审查材料时，final decision 字段必须为空；
人工说明不能把不可裁决转换成通过。

### 14.2 流程状态与聚合优先级

| 流程状态 | 触发条件 | 唯一动作 | `final_decision` |
|---|---|---|---|
| `pause_not_adjudicable` | delivery/baseline/run identity 不存在，raw/report provenance 无法定位，材料被篡改或 scope 冲突 | 冻结评审，补基线/设计/证据并保留 finding | 为空 |
| `blocked_adjudicable` | required runner/capability 不可用，但有完整 unavailable record 且 baseline 明确 required | 可作为阻断输入聚合为不通过，或先走范围变更 | 仅在裁决后填写 |
| `review_in_progress` | 材料齐备但专业审查或签署未完成 | 完成审查；不得发布 draft verdict | 为空 |
| `retest_required` | 缺陷修复、风险失效、baseline 或 scope 变化 | 按 §12 建立新 invocation/run，旧记录只读 | 旧值只读，新值为空 |
| `superseded` | 新 review version 以明确 lineage 替代旧决定 | 保留旧记录，不作为当前 release input | 旧值不可改写 |

聚合优先级固定如下：

```text
不可裁决前置缺失
  -> pause；不产生 final decision

可裁决输入中存在 VF / S / required P0 / hard gate failure
  -> 不通过

无上述 failure，但存在有效且允许的 Accepted residual
  -> 有条件通过

无 failure、无 conditional residual，全部 required gate 与签署完整
  -> 通过
```

任一维度的 hard failure 不能被其他维度的通过抵消；evidence integrity failure 优先于绿色 suite summary。inherited
affected 不自动等于 finding，但相关 positive capability 未闭合时，不得把受影响 AC 写成无条件通过。

### 14.3 必审维度

| 维度 | Current 主键 | 正向要求 | 阻断/暂停输入 |
|---|---|---|---|
| 功能能力 | `AC-OBS-001~031` | 31/31 由 exact TC、planned-to-real linkage 和同 run report 独立证明 | required AC failure、orphan 或 evidence 缺失 |
| 数据/架构 | §6 redline | observation-side owner、body-free、writer graph、only-core 全成立 | truth/body/dependency violation |
| 协议/跨仓 | 16 Command、14 Query、9 Consumer、12 Event、9 Job | exact schema、binding、failure、ack/effect/no-write 可判定 | required positive 缺失、I05/J06 伪造 positive |
| 状态/事务 | 27 formal + 1 technical、`TX-OBS-001~023` | legal/illegal、UoW、幂等、并发、恢复和 zero-write 成立 | partial commit、blind retry、stale write、unknown guess、source write |
| 非功能 | `NFG-OBS-001~008`、`NFR-OBS-001~024` | required structural gate 和 selected profile/lane 成立 | hard gate failure、无来源数字被硬化 |
| 证据 | `EVG-OBS-001~009`、99/99 TC/EV、82 DS、9 suite、5 checks | same-run raw/report/index/provenance 完整 | wrong run、`latest`、static pass、orphan、缺 required review |
| 一票否决 | `VF-OBS-001~010` | 每项有真实 evidence 和 reviewer 的逐项输入 | 任一 triggered；缺证不等于未触发 |
| 缺陷 | `S/A/B/R` | S=0；A 满足严格条件；关闭和复验材料完整 | 未关闭 S、影响 P0 的 A 或关闭证据缺失 |
| 风险 | `ELG-OBS-01~10`、`RR-OBS-001~009` | conditional 使用的风险逐项 `Accepted`、有效、未过期 | Draft、Rejected、Expired、Reopened 或 affected 被伪造关闭 |
| 交接/签署 | acceptance/review package | selected run、open issues、角色签署和最终输入一致 | handoff 未审、角色缺失、digest/scope 漂移 |

### 14.4 下一阶段与发布准备边界

| 场景 | 是否可进入下一阶段 | 是否可进入发布准备 | 约束 |
|---|---|---|---|
| `通过` 且签署完整 | 是 | 可进入独立发布准备评估 | 仍需实施、部署、运维、安全和组织门禁 |
| `有条件通过` 且每项条件在授权范围 | 有条件 | 仅在条件不影响 release hard gate 时 | 按 deadline/trigger 跟踪，失效即重开 |
| `不通过` | 否 | 否 | 修复、复验、新 review 后重新裁决 |
| `pause_not_adjudicable` / `review_in_progress` | 否 | 否 | final decision 为空 |
| 文档 Step 15 完成 | 可由用户另行决定启动 `07` 设计 | 不适用 | 只表示设计链完整，不是产品放行 |

`06` 不授予 production deploy、traffic enable、data migration、cleanup、archive deletion 或 external product
activation authority。`RetentionMarker`、handoff `Delivered`、Job `Completed`、telemetry clean 和 report generated
均不是 release authorization。

### 14.5 签署角色与职责分离

| 角色能力 | 必须确认 | 必须拒签的情形 |
|---|---|---|
| scope / product owner | P0/P1/P2、Out of Scope、用户影响和下一阶段条件 | scope 与 baseline 不一致、required 能力被隐式降级 |
| architecture / truth-boundary owner | observation owner、no-write、only-core、协议和 affected 边界 | source truth 反写、非法依赖、产品成为 truth、affected 被伪造关闭 |
| test / evidence owner | selected run、99 TC/82 DS/9 suite/5 check、same-run provenance 和 before/after | missing raw/report、wrong run、`latest`、static pass、required lane 替代 |
| implementation / delivery owner | immutable delivery ref、build/config/dependency manifest、实现范围和 open technical issue | 被测物不固定、实现范围与送验声明不一致 |
| operations / security / compliance owner | redaction、safe telemetry、retention protection、profile、external handoff 和运维 residual | forbidden body/secret、高基数、protected cleanup、未授权 external binding |
| final acceptance authority | 三值聚合、VF、defect、risk、open issue 和全部专业签署一致 | required role 缺失、风险过期、digest 漂移或结论模糊 |

角色可以由组织合并，但必须记录 authority scope，不能因合并删除 test/evidence 或 truth-boundary 审查。risk
acceptor 的授权仍遵守 §13；final authority 不能代替专业角色补签。

### 14.6 签署字段合同

实际受控签署记录至少包含：

| 字段 | 必填 | 约束 |
|---|---|---|
| `review_version` | 是 | 与 acceptance/review package 一致；禁止 `latest` |
| `baseline_id` / `baseline_digest` | 是 | 回指 design/delivery/config/data/dependency baseline |
| `selected_run_refs` | 是 | 一个合法选择集合；不得跨 run 拼接 |
| `acceptance_package_digest` | 是 | 固定 handoff、VF、risk、open-issues 和 review 输入 |
| `decision_dimension_results` | 是 | §14.3 十个维度逐项输入或暂停原因 |
| `final_decision` | 最终裁决时是 | 只能 `通过`、`有条件通过`、`不通过` |
| `decision_reason` | 是 | 回指 gate、VF、defect、risk，不写“综合考虑” |
| `accepted_risk_refs` | conditional 时是 | 只引用有效、未过期的 `Accepted` 记录 |
| `blocking_refs` | fail 时是 | 回指真实 finding/defect/report，不只写摘要 |
| `next_stage_disposition` | 是 | `allow` / `allow_with_conditions` / `deny`，与三值一致 |
| `release_preparation_disposition` | 是 | 只表示准备评估，不等于 production release |
| `role` / `principal_ref` | 是 | 具名主体和职责角色，不能只有“团队” |
| `authority_scope_ref` | 是 | 证明主体对对应范围有签署 authority |
| `role_decision` / `exceptions` | 是 | `agree` / `reject` 及具体异常，禁止模糊同意 |
| `signed_at` / `signature_ref` | 是 | 由真实签署系统生成；设计期不得预填 |
| `supersedes_ref` | 条件必填 | 新 review 替代旧决定时保持 lineage |

runtime 和 report generator 只能提供 body-free input refs/digests，不能生成 principal、authority、signature 或
final decision。当前组织尚未冻结实际签署系统和 backing path，因此本文不伪造其绑定。

### 14.7 Canonical 验收与审查包

| 材料 | 必需性 | 用途 | 不得表达 |
|---|---|---|---|
| `reports/acceptance/handoff.md` | 必需 | selected run、scope、baseline、roots、open state 交接 | generator final verdict/signoff |
| `reports/acceptance/veto-checklist.md` | 必需 | 10 VF 的 evidence/finding/review 输入 | 缺证据自动未触发 |
| `reports/acceptance/open-issues.md` | 必需 | defect、affected、blocked、pending、owner 和恢复路径 | 删除或改写开放项 |
| `reports/acceptance/risk-acceptance.md` | conditional 必需 | 引用有效 Accepted residual | 接受 VF/S/缺 P0 evidence |
| `reports/review/reviewer-notes.md` | 必需 | 人工专业复核、冲突、回流和决定输入 | 修改 raw/report 或代签 |
| `reports/review/agent-review.md` | 按流程 | provenance review 辅助输入 | 作为唯一签署主体或自动通过 |
| `reports/runs/<run_id>/evidence-index.md` | 必需 | 99-row evidence join | 手写 alias 或跨 run 拼接 |
| `reports/runs/<run_id>/gate-results.md` | 必需 | suite/check/profile/lane/status 汇总 | 吞掉 blocked/failed/not_run |
| `reports/runs/<run_id>/redaction-check.md` | 必需 | forbidden material 全 root scan | 未执行却写 clean |
| `reports/runs/<run_id>/metric-label-check.md` | 必需 | label allowlist/cardinality | 只查 descriptor 不查 sample |
| `reports/runs/<run_id>/dependency-boundary.md` | 必需 | only-core、writer/product/history 边界 | 只扫描直接 manifest |
| `reports/runs/<run_id>/report-audit.md` | 必需 | raw/report/index same-run provenance | summary 代替 raw relation |

所有材料只能使用 `artifacts/test/<run_id>/`、`reports/runs/<run_id>/`、`reports/acceptance/` 和 `reports/review/` 四类
canonical root；不新增第二套 evidence identity。

### 14.8 签署含义、失效与当前状态

签署只表示本次冻结输入下对应角色对其职责范围的确认或拒绝。`有条件通过`不接受 VF、S、缺 P0 evidence 或 inherited
affected positive capability；`不通过`不允许删除失败材料；专业签署不替代其他角色或 final authority。

签署在 baseline、selected run、scope、gate result、risk set、open issue、authority 或 package digest 变化时失效。
旧记录必须只读保留，新 review 通过 `supersedes_ref` 建立 lineage，不得修改旧日期、签名或结论。当前没有真实
final decision、principal、signed_at、signature_ref、run、evidence alias 或 release authorization。

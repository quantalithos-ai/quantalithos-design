## 1. 业务背景与驱动力

### 1.1 业务背景

sandbox 是 Quantalithos 的安全底线之一。runtime / tools / runner 需要执行:
- 用户或 AI 生成的代码
- 外部 tool 调用
- 测试 / lint / build / 运行时任务

这些都不能直接在宿主机上执行。L4-sandbox 通过统一接口提供隔离执行、资源限制、默认无出网和审计事件。

### 1.2 业务驱动力

**业务驱动力**:
- 平台必须能安全运行不受信代码或工具
- Runner 与 Member Runtime 需要共享同一套隔离底座

**技术驱动力**:
- Docker + gVisor 两后端
- deny-by-default 出网
- 审计事件(SandboxInvoked / SandboxExited / EscapeDetected)

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 性能 | Docker 启动时延 | < 1s | benchmark |
| 性能 | gVisor 启动时延 | < 2s | benchmark |
| 安全 | 未授权出网拦截率 | 100% | 安全测试 |
| 复用 | Runner 与 Runtime 共用接口 | 100% | 集成测试 |

### 2.1 不可变约束

| 约束 | 来源 | 影响 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| backend 类型 | 中 | trait + adapters |
| network allowlist | 高频 | policy-aware access layer |
| execution use cases | 高频 | runtime / runner 共享服务接口 |

### 3.2 架构风格决策框架

**候选**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **统一 SandboxService + backend adapters**(当前)| 可复用、易切换 | 需要适配多 backend 语义 | ✅ |
| runtime / runner 各自实现 | 起步快 | DRY 失效、策略漂移 | ❌ |
| 只用 Docker | 实现快 | 安全性不足 | ❌ |

**最终选择**:**统一 SandboxService 接口 + Docker/gVisor adapters + Policy-aware network gate**

### 3.3 约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| deny-by-default 出网 | 安全边界强 | 体验略重 |
| 双 backend | 可按场景选择安全性 / 性能 | 维护两实现 |
| 审计事件 | 可追溯 | 事件量增加 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```
runtime / tools / runner
        │
        ▼
   ★ quantalithos-sandbox ★
   - isolated execution
   - resource limits
   - network gate
   - audit events
        │
   ┌────┼─────────────┬──────────────┬──────────────┐
   ▼    ▼             ▼              ▼              ▼
 capability-hub   Docker         gVisor         observability   SRE
 allowlist        backend        backend        audit sink      ops
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 隔离执行
- ✅ 资源限制
- ✅ 默认无出网 + allowlist
- ✅ 审计事件

**不做什么**:
- ❌ 工具业务逻辑(runtime/tools)
- ❌ 白名单决策(capability-hub / governance)
- ❌ 镜像构建(member-images)
- ❌ 前端提示(console / runner UI)

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 降级 |
|---|---|---|
| Docker / containerd | 99.9% | 切 gVisor / local test |
| gVisor | 99.9% | 低安全环境退 Docker |
| capability-hub policy | 99.9% | deny by default |
| observability | 99.95% | backlog |

### 4.4 关键依赖风险

- backend escape 风险
- allowlist 刷新延迟
- runner / runtime API 漂移

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Execution | 核心域 | 沙箱执行 |
| Isolation Backend | 核心域 | Docker / gVisor |
| Policy Gate | 支撑子域 | allowlist / network gate |
| Audit | 支撑子域 | sandbox events |

### 5.2 限界上下文划分

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Sandbox API | 对外统一接口 | SandboxExecution |
| Backends | 各 backend 适配 | DockerSandbox / GVisorSandbox |
| Limits | 资源限制 | LimitSet |
| Audit | 审计记录 | SandboxAuditEvent |

### 5.3 上下文映射关系

- capability-hub → Limits / PolicyGate
- runtime / runner → Sandbox API
- observability ← Audit

### 5.4 统一语言词汇表

| 术语 | 定义 | 上下文 |
|---|---|---|
| SandboxExecution | 一次受控执行 |
| LimitSet | CPU / RAM / disk / timeout |
| Allowlist | 允许的网络出口 |
| EscapeDetected | 逃逸迹象事件 |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```
runtime / tools / runner
        │
        ▼
sandbox-api
  ├─ execution orchestrator
  ├─ limits / policy gate
  ├─ backend adapter
  └─ audit emitter
        │
   ┌────┼────────────┬──────────────┬──────────────┐
   ▼    ▼            ▼              ▼              ▼
 Docker gVisor   local_process    capability-hub   observability
 backend backend (test only)      allowlist       audit sink
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 |
|---|---|---|
| sandbox-api | 对外统一接口 | Rust |
| execution orchestrator | 组织一次执行 | Rust |
| limits / policy gate | limit + allowlist 判定 | Rust |
| backend adapter | Docker / gVisor / local_process | Rust |
| audit emitter | SandboxInvoked / Exited / EscapeDetected | Rust |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 理由 |
|---|---|---|
| runtime → sandbox | RPC | 高层统一调用 |
| runner → sandbox | 同一 RPC / SDK | 共用接口 |
| sandbox → capability-hub | 查询 allowlist | 动态授权 |
| sandbox → observability | 事件 | 审计留痕 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| sandbox execution metadata | sandbox | observability / SRE |
| network allowlist snapshot | sandbox(policy view) | sandbox |
| backend capability flags | sandbox config | sandbox |

### 6.5 部署拓扑

- sandbox-api 与 orchestrator 可同进程
- Docker/gVisor backend 通过系统 daemon / shim 交互
- local_process backend 仅测试环境启用

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```
api
 │
 ▼
application
 │
 ▼
domain(SandboxExecution / LimitSet / PolicyView)
 ▲
 │ ports
infra(Docker/gVisor/local adapters / bus / policy lookup)
```

### 7.2 层间约束规则

- domain 不直接依赖具体 backend
- allowlist / policy 判断发生在执行前,backend 不自行放权
- local_process backend 不能出现在生产环境
- audit emitter 不阻塞主执行路径(失败时也不放弃 sandbox 执行结果返回)

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| SandboxBackend | domain/application | Docker / gVisor / local_process |
| PolicyViewProvider | application | capability-hub adapter |
| AuditPublisher | application | observability event adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(runtime / tools / runner) |
| 传出耦合 | 中高(Docker / gVisor / capability-hub / observability) |
| 不稳定性 | 中 |
| 抽象度 | 高(api / backend 解耦) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| SandboxExecution metadata | sandbox | observability / SRE | 强一致 |
| allowlist snapshot | capability-hub → sandbox view | sandbox | 最终一致(policy refresh) |
| audit events | sandbox | observability | 最终一致 |

### 8.2 一致性层次

- 执行 metadata 聚合内强一致
- allowlist / policy 刷新最终一致
- 审计事件通过总线最终一致

### 8.3 补偿机制设计

| 场景 | 补偿 |
|---|---|
| audit 事件发送失败 | backlog / replay |
| policy lookup 失败 | deny by default |
| backend 初始化失败 | fallback 下一个后端(若策略允许) |

## 12. 演进路线

### 12.1 当前状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| Firecracker 未纳入 | 高安全场景能力不足 | P1 |
| allowlist 粒度未细化 | 安全控制粗糙 | P1 |
| nested sandbox 场景未处理 | runner/runtime 复杂场景 |

### 12.2 触发条件

| 指标 | 阈值 | 动作 |
|---|---|---|
| gVisor 启动 > 2s | 持续 1 周 | 优化或引入 Firecracker |
| deny count 异常 | > 阈值 | 分析 allowlist / docs |
| escape_detected | 任意一次 | 立即安全事件处理 |

### 12.3 演进步骤

```
阶段 1: Docker + gVisor + deny-by-default
阶段 2: Runner/runtime 统一接口稳定
阶段 3: allowlist 粒度增强 + local_process 测试后端
阶段 4: Firecracker / nested scenarios
```

### 12.4 目标架构

sandbox 的目标是:
- 成为所有执行类能力的统一安全底座
- 把“怎么执行”与“能不能执行”解耦
- 让 runtime 和 runner 不再各自发明隔离策略

## 13. 风险与待确认事项

### 13.1 常见风险

## 14. 上线策略

### 14.1 灰度方案

- 先给 runtime 样本工具 1 个接入
- 再给 runner 样本应用 1 个接入
- 先 Docker,后 gVisor

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚 |
|---|---|---|
| 未授权出网误放行 | S | 立即停用版本 |
| sandbox 启动延迟过高 | A | 切回 Docker 后端 |
| runner 集成失败 | A | 暂停 runner 接入 |

### 14.3 监控指标

| 指标 | 阈值 | 告警 |
|---|---|---|
| Docker startup | > 1s | warning |
| gVisor startup | > 2s | warning |
| deny count | > 阈值 | major |
| escape_detected | > 0 | critical |

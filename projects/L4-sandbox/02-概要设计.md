## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L4-sandbox` 不是 runtime 主真相仓,也不是 tools 定义仓,更不是“跑命令的脚本目录”。它是 **“受控执行隔离层”**。

你可以把它理解成:
- 平台某一步动作真正落地执行时,它是在什么隔离环境里跑的
- 命令、脚本、容器、会话、临时工作区怎样被创建、限制、回收
- 网络、文件系统、资源配额、权限模型怎样被控制
- stdout / stderr / 输出文件 / 资源使用快照怎样被安全带回上游
- 一次执行怎样可审计、可中断、可重放、可回收

这些事情,都由 `L4-sandbox` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L4-sandbox`,这些执行隔离事实就会散落在:
- `runtime` 自己拼装的 shell / container 逻辑里
- `tools` 各自带的一套执行脚本里
- capability-hub 下游各自直接访问 provider / network 的本地配置里
- UI / operator 临时 SSH 或手工命令里
- artifact / observability 后补的输出归档逻辑里

结果就会出现:
- 平台到底“怎么安全执行动作”没有统一边界
- 资源配额、文件系统、网络限制和权限模型各自一套口径
- 输出日志、文件产物和执行证据无法统一回收
- retry / replay / kill / cleanup 行为缺少一致语义
- runtime、tools、capability-hub、artifact、observability 之间的执行接缝会长期漂移

所以 `L4-sandbox` 必须独立存在,作为:
> **把平台动作放进受控隔离环境里执行、限制、观察、回收并安全交还上游的统一执行壳。**

### 1.3 新人最容易混淆的几个词

#### SandboxExecution
就是:
> 一次正式进入隔离执行层的执行记录。

它不是 runtime 的业务执行真相本体。

#### SandboxSession
就是:
> 一段隔离环境生命周期,如容器、进程组或临时工作区会话。

它不等于业务任务生命周期。

#### SandboxCommand
就是:
> 某次在沙箱里实际落地执行的命令或入口动作。

它不是 `ToolDefinition`。

#### SandboxPolicy
就是:
> 沙箱执行层落实的限制规则,如网络、挂载、资源、权限约束。

它不是 governance 的业务裁决本体。

#### SandboxOutput
就是:
> 一次执行产生的 stdout / stderr / 文件输出 / 资源使用摘要等结果材料。

它不是 artifact 真相本体。

#### replay / retry
就是:
> 对执行层动作进行重试、重放或重跑。

它不是重新做一遍业务决策。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L4-sandbox/02` 时,先收稳以下前提:
- `L4-sandbox` 不应按 container / command / file / log 平铺理解,而应按受控执行主链责任拆
- sandbox 至少应拆成“执行请求与会话建立 / 隔离环境与资源约束 / 命令执行与外部能力接缝 / 输出回收与审计留痕 / 失败恢复与运维控制”五个主要部分
- sandbox 自己拥有的真相不是 runtime execution、tool definition、governance decision、artifact truth 或 provider contract,而是 session / isolation / execution / output / control 这类执行隔离真相
- `L4-sandbox` 只能为 runtime、tools、artifact、observability、operators 提供受控执行面,不能替这些仓持有各自业务真相
- 02 的重点不是“列有哪些容器参数或命令样例”,而是先把“执行隔离层在平台里到底是什么、和 runtime/tools/capability-hub/artifact/observability 怎么分层”讲清楚
- network policy、resource quota、stdout/stderr capture、output file 回收、kill/replay/cleanup 这些不是零散机制,而是执行隔离主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的受控执行心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,AI 成员和工具主线不应直接把命令丢到宿主环境里跑。用户真正需要的不是“能执行命令”,而是:
- 一次执行在哪个隔离环境里发生
- 哪些网络、文件系统、provider、挂载和资源是被允许的
- 输出如何被安全带回给 artifact / observability / conversation
- kill / timeout / retry / replay / cleanup 是否有一致边界
- operators 是否能在不破坏上游业务真相的前提下诊断和干预执行

如果把这些逻辑分别散落到:
- runtime 的本地 shell / process 逻辑
- tools 的脚本包装层
- capability-hub 下游各自访问 provider 的方式
- UI / console 的临时人工命令

系统会快速退化成:
- 执行隔离边界不一致
- 文件、网络、资源限制难以统一
- stdout/stderr / 输出文件 / 审计留痕无法对账
- retry / replay / cleanup 缺少权威语义
- 任何一个调用点都可能绕开安全控制

因此,本概要设计的任务就是:
> **把 `L4-sandbox` 写成一个新人也能看懂的“受控执行隔离层”,而不是把容器、命令、日志和清理逻辑分别写在各个仓里。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 执行隔离统一性 | 分散在 runtime / tools / scripts | 统一 sandbox 执行壳 | 需正式收敛 |
| 未受控网络/文件访问 | 风险高 | 未授权访问成功率 0 | 需固定隔离底座 |
| 输出可回收性 | 各调用点各自处理 | stdout/stderr/output files 回收率 100% | 需形成统一出口 |
| retry / replay / kill 语义 | 分散 | 正式化并可审计 | 需形成控制主线 |
| 资源约束 | 不统一 | CPU / memory / wall-time 全覆盖 | 需写死约束模型 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让平台在执行真实动作时既能完成任务,又不失控、不泄露、不绕过治理与审计
- **技术问题**:SandboxExecution、Session、Command、IsolationPolicy、OutputCapture、Kill/Retry/Replay/Cleanup 与 runtime / tools / capability-hub / artifact / observability / operators 之间的边界如何稳定建模,并形成统一执行隔离主链

## 4. 约束条件

### 4.1 技术约束

- 所有执行都必须进入正式 SandboxSession / SandboxExecution 主线
- 未授权网络、挂载、provider、路径访问必须拒绝
- 资源约束必须覆盖 CPU / memory / wall-time / process count
- stdout / stderr / output files 必须可回收、可审计
- kill / retry / replay / cleanup 必须留痕且不得静默修改上游业务真相

### 4.2 资源约束

- 沙箱会话会频繁创建与销毁,会话管理开销必须受控
- 输出文件与日志量会快速增长,必须接受 append-only 证据链规模增长
- 高并发执行下,隔离成本不能无限长胖

### 4.3 时间约束

- 当前阶段先收稳统一执行隔离主链,而不是先做复杂多集群调度或高级容器优化
- 文件系统、网络、资源、输出、运维控制五条基础链必须优先稳定,否则后续 runtime/tools 接入会失控

### 4.4 合规约束

- 未授权外联成功率必须为 0
- 未授权路径 / 挂载访问成功率必须为 0
- 所有 kill / timeout / deny / replay / cleanup 都必须留审计证据
- sandbox 不得持有超出 capability-hub / governance 授权范围的外部访问能力

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| active sessions | 高 | runtime 并发执行需求 |
| stdout/stderr volume | 高 | 每步执行输出都要留痕 |
| output files/session | 中高 | 工件候选与中间结果 |
| replay / retry records | 高 | 控制链长期证据 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ runtime / tools / gov       │
                    │ - execution request         │
                    │ - tool binding / policy     │
                    └────────────┬───────────────┘
                                 │ execution input
                                 ▼
                    ┌────────────────────────────┐
                    │ L4-sandbox                 │
                    │ - session / isolation      │
                    │ - command / output / ctrl  │
                    └────────────┬───────────────┘
                                 │ outputs / audit / resource usage
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ artifact / conversation    │   │ observability / operators  │   │ capability-hub             │
│ - output / summary consume │   │ - logs / audit / control   │   │ - external access limits   │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L4-sandbox` 自己负责执行请求接入、隔离环境建立、命令落地、输出回收、失败控制与运维接缝
- `runtime` / `tools` 提供执行意图和工具语义,但不持有隔离执行真相
- `capability-hub` 提供外部能力可访问边界,而 sandbox 在执行面落实这些边界
- `artifact` / `conversation` / `observability` / `operators` 消费执行输出、证据、摘要和控制接口
- 这个仓的角色不是“决定执行什么”,而是“把动作放进受控环境里安全执行”

所以 `L4-sandbox` 在全局里的角色是:
> **把平台动作转换成受控隔离环境中的正式执行会话,并把执行结果、日志、资源与控制证据统一收口。**

### 5.3 系统边界

**做什么**:
- 管理 SandboxExecution / SandboxSession
- 管理隔离环境、挂载、网络、资源配额
- 执行 SandboxCommand 与能力调用桥接
- 回收 stdout / stderr / output files / resource usage
- 提供 kill / retry / replay / cleanup / inspect 控制面

**不做什么**:
- 不决定 runtime 为什么要执行某一步
- 不持有 ToolDefinition 真相
- 不持有 capability-hub 的 contract / decision 真相
- 不把输出直接确认为 artifact 真相
- 不替代容器平台 / OS / secrets 平台本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| runtime | 99.9% | 上游不可用不影响 sandbox 已存在会话回收与审计 |
| tools | 99.9% | tool binding 缺失时阻断执行,不伪造命令 |
| capability-hub | 99.9% | 使用 last-known-allowed contract/cache,但不得越权放行 |
| artifact | 99.9% | 输出先保留在 sandbox 证据链,待 artifact 回收 |
| observability | 99.9% | backlog / replay,不静默丢审计与输出摘要 |

### 5.5 关键依赖风险

- runtime 绕过 sandbox 直接落地执行会直接破坏隔离边界
- capability-hub 的 access 决策如果未在执行面落实,会导致越权外联
- 输出回收链若和 artifact truth 混层,会导致产物真相不清
- cleanup / kill / replay 若无统一证据链,会让 operators 无法对账
- 资源限制不一致会造成宿主污染和执行面失控

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把 container / command / log / files 横向平铺。  
> 它按 **执行接入主链职责 + 会话 / 隔离 / 执行 / 输出 / 控制差异** 来拆分。  
> 因此下面每一部分都可能包含多个对象和机制,共同支撑同一段受控执行主链。

#### 执行请求与会话建立部分

- **它是什么**: 这是 `L4-sandbox` 的执行入口层,一起回答“这次到底在隔离环境里执行什么”
- **为什么单独有它**: 如果没有独立 execution/session 层,runtime 的业务执行真相和 sandbox 的执行壳会直接混层
- **负责什么**:
  - 定义 `SandboxExecution`
  - 定义 `SandboxSession`
  - 绑定 actor / work / step / tool / request 输入
- **不负责什么 / 容易混淆点**:
  - 不决定为什么要执行这一任务
  - 不决定业务流程推进真相
  - 不负责具体资源限制本体
  - 最容易和 runtime execution truth、conversation 交互、业务任务生命周期混淆
- **与其他部分交互**:
  - 下游: 隔离环境与资源约束、命令执行与外部能力接缝、失败恢复与运维控制
  - 外部: runtime / tools / governance
  - 交互类型: 执行接入型 + 会话锚点型
- **后续详细设计展开点**:
  - SandboxExecution / Session 模型
  - create / attach / close 主线

#### 隔离环境与资源约束部分

- **它是什么**: 这是 sandbox 的环境承载层,一起回答“这次执行在什么受控环境里跑”
- **为什么单独有它**: container、process、filesystem、network、quota 是一条完整主线,不单列就会被 runtime / command / output 打散
- **负责什么**:
  - 管理 container / process / temp workspace
  - 管理 CPU / memory / wall-time / process count quota
  - 管理 network policy / mount / env injection
- **不负责什么 / 容易混淆点**:
  - 不裁决 capability 是否允许访问
  - 不负责 finance 成本真相
  - 不替代宿主 OS 或容器平台本体
  - 最容易和 capability access control、resource billing、host infra 本体混淆
- **与其他部分交互**:
  - 上游: 执行请求与会话建立部分、capability-hub / governance 输入
  - 下游: 命令执行与外部能力接缝、输出回收与审计留痕
  - 交互类型: 环境建立型 + 资源约束型
- **后续详细设计展开点**:
  - isolation policy
  - network / fs / quota 模型

#### 命令执行与外部能力接缝部分

- **它是什么**: 这是 sandbox 的动作落地层,一起回答“动作怎样真正落到执行面”
- **为什么单独有它**: tool invocation、shell command、provider bridge 如果不单列,会和 ToolDefinition、provider contract、runtime dispatch 混成一层
- **负责什么**:
  - 定义 `SandboxCommand`
  - 执行 command runner
  - 承接 tool invocation bridge 与 capability-hub allowlist / provider bridge
- **不负责什么 / 容易混淆点**:
  - 不定义工具语义本体
  - 不持有 capability-hub contract / decision 真相
  - 不负责 artifact 归档决策
  - 最容易和 ToolDefinition、capability access control、runtime dispatch 决策混淆
- **与其他部分交互**:
  - 上游: 执行请求与会话建立部分、隔离环境与资源约束部分、capability-hub
  - 下游: 输出回收与审计留痕、失败恢复与运维控制
  - 交互类型: 动作执行型 + 外部能力桥接型
- **后续详细设计展开点**:
  - SandboxCommand 模型
  - shell / tool / provider bridge 主线

#### 输出回收与审计留痕部分

- **它是什么**: 这是 sandbox 的结果回收层,一起回答“结果怎样被安全带回并留下证据”
- **为什么单独有它**: stdout、stderr、输出文件、资源快照和审计证据不是同一对象,但它们必须在执行层统一收口
- **负责什么**:
  - 回收 stdout / stderr / output files
  - 记录 resource usage snapshot
  - 生成 execution summary 与 audit trail
- **不负责什么 / 容易混淆点**:
  - 不负责 artifact 最终真相归档
  - 不等于 observability 原始日志中心
  - 不负责业务对话摘要真相
  - 最容易和 artifact truth、raw telemetry、conversation summary 混淆
- **与其他部分交互**:
  - 上游: 命令执行与外部能力接缝部分
  - 下游: artifact / observability / conversation / operators
  - 交互类型: 结果回收型 + 审计证据型
- **后续详细设计展开点**:
  - output capture / usage snapshot / audit model

#### 失败恢复与运维控制部分

- **它是什么**: 这是 sandbox 的非 happy path 和控制面,一起回答“失败、中断、回收时怎样处理”
- **为什么单独有它**: 真实复杂度大量集中在 timeout、cancel、kill、retry、replay、cleanup,不单列就会被写成零散错误处理
- **负责什么**:
  - timeout / cancel / kill / inspect
  - retry / replay / rerun
  - cleanup / GC / orphan session 回收
- **不负责什么 / 容易混淆点**:
  - 不重新做业务裁决
  - 不等于 runtime 的任务状态机
  - 不等于 artifact 的保留策略
  - 最容易和 business decision、task lifecycle、log cleanup 混淆
- **与其他部分交互**:
  - 上游: 执行请求与会话建立部分、命令执行与外部能力接缝部分、输出回收与审计留痕部分
  - 下游: operators / runtime / observability
  - 交互类型: 控制恢复型 + 运维干预型
- **后续详细设计展开点**:
  - kill / timeout / replay / cleanup 主线
  - evidence + control contract

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ runtime / tools / gov       │
                    │ - execution request         │
                    │ - tool binding / policy     │
                    └────────────┬───────────────┘
                                 │ execution input
                                 ▼
                    ┌────────────────────────────┐
                    │ L4-sandbox                 │
                    │ - session / isolation      │
                    │ - command / output / ctrl  │
                    └────────────┬───────────────┘
                                 │ outputs / audit / resource usage
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ artifact / conversation    │   │ observability / operators  │   │ capability-hub             │
│ - output / summary consume │   │ - logs / audit / control   │   │ - external access limits   │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L4-sandbox` 自己负责“建立执行会话”“落实隔离环境”“执行命令/桥接外部能力”“回收输出与证据”“提供 kill/replay/cleanup 控制面”
- `runtime` / `tools` 的交互主要落在 **执行请求与会话建立部分** 与 **命令执行与外部能力接缝部分**,为 sandbox 提供执行意图和工具语义输入
- `capability-hub` 的交互主要落在 **隔离环境与资源约束部分** 与 **命令执行与外部能力接缝部分**,限制外联和 provider 使用范围
- `artifact` / `conversation` 的交互主要落在 **输出回收与审计留痕部分**,消费执行输出与摘要
- `observability` / `operators` 的交互主要落在 **输出回收与审计留痕部分** 与 **失败恢复与运维控制部分**,消费日志、审计、控制与诊断输出

### 7.3 分模块交互说明(逐个写)

#### 与 `runtime` 的交互

```text
┌────────────────────────────┐
│ runtime                    │
│ - execution request        │
│ - work / step context      │
└────────────┬───────────────┘
             │ sandbox request
             ▼
┌────────────────────────────┐
│ sandbox                    │
│ - SandboxExecution         │
│ - SandboxSession           │
└────────────────────────────┘
```

- `runtime` 是 **执行请求输入方**
- **交互类型**: execution request 输入型交互
- **主流程位置**: create / attach / close / retry / replay 时进入主流程
- **交互解释**:
  - runtime 告诉 sandbox 现在要执行哪一步
  - sandbox 负责怎么把它安全放进隔离环境里跑
  - sandbox 不替代 runtime 的执行主真相
- **高风险异常流**:
  - runtime 绕过 sandbox 直接在宿主执行
- 后续 `03-详细设计.md` 继续展开:
  - SandboxExecution request contract
  - session lifecycle 主线

#### 与 `tools` 的交互

```text
┌────────────────────────────┐
│ tools                      │
│ - ToolDefinition           │
│ - invocation binding       │
└────────────┬───────────────┘
             │ command binding input
             ▼
┌────────────────────────────┐
│ sandbox                    │
│ - SandboxCommand           │
│ - command runner           │
└────────────────────────────┘
```

- `tools` 是 **工具语义输入方**
- **交互类型**: tool binding 输入型交互
- **主流程位置**: command build、tool bridge、exit code 回收时进入主流程
- **交互解释**:
  - tools 提供语义能力与调用绑定
  - sandbox 负责真实命令或动作落地执行
  - sandbox command 不等于 tool definition
- **高风险异常流**:
  - ToolDefinition 被误当成可直接执行命令
- 后续 `03-详细设计.md` 继续展开:
  - command bridge contract
  - stdin/stdout/exit code 主线

#### 与 `capability-hub` 的交互

```text
┌────────────────────────────┐
│ capability-hub             │
│ - allow/deny               │
│ - provider/contract view   │
└────────────┬───────────────┘
             │ access limit input
             ▼
┌────────────────────────────┐
│ sandbox                    │
│ - network / provider gate  │
│ - external bridge          │
└────────────────────────────┘
```

- `capability-hub` 是 **外部能力边界输入方**
- **交互类型**: capability access limit 输入型交互
- **主流程位置**: 外联执行、provider bridge、network policy 建立时进入主流程
- **交互解释**:
  - capability-hub 告诉 sandbox 当前能访问什么
  - sandbox 在执行面落实这些边界
  - sandbox 不自己生成 provider 合同或 access decision 真相
- **高风险异常流**:
  - sandbox 使用 last-known-allowed 之外的能力仍被放行
- 后续 `03-详细设计.md` 继续展开:
  - provider bridge contract
  - network policy enforcement 主线

#### 与 `artifact / conversation` 的交互

```text
┌────────────────────────────┐
│ sandbox                    │
│ - stdout/stderr/files      │
│ - execution summary        │
└────────────┬───────────────┘
             │ output / summary output
             ▼
┌────────────────────────────┐
│ artifact / conversation    │
│ - artifact candidate       │
│ - human-readable summary   │
└────────────────────────────┘
```

- `artifact / conversation` 是 **输出与摘要消费方**
- **交互类型**: result material 输出型交互
- **主流程位置**: output capture、summary emit、artifact candidate 回收时进入主流程
- **交互解释**:
  - sandbox 负责把输出材料安全带回
  - artifact 决定哪些输出成为正式产物
  - conversation 只消费摘要
- **高风险异常流**:
  - 输出文件被误当正式 artifact 真相直接入库
- 后续 `03-详细设计.md` 继续展开:
  - output capture contract
  - artifact candidate 主线

#### 与 `observability / operators` 的交互

```text
┌────────────────────────────┐
│ sandbox                    │
│ - audit / usage / control  │
└────────────┬───────────────┘
             │ logs / control output
             ▼
┌────────────────────────────┐
│ observability / operators  │
│ - diagnose / kill / replay │
└────────────────────────────┘
```

- `observability / operators` 是 **审计与控制消费方**
- **交互类型**: append-only 输出型 + control consume 型交互
- **主流程位置**: timeout、kill、replay、cleanup、resource overrun 时进入主流程
- **交互解释**:
  - sandbox 发日志、审计、资源快照和控制结果
  - operators 可消费 kill / inspect / replay 能力
  - sandbox 不替代 runtime 主状态机
- **高风险异常流**:
  - kill/replay 发生了但没有证据链
- 后续 `03-详细设计.md` 继续展开:
  - control contract
  - replay / cleanup evidence 主线

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是执行隔离层、哪个模块是输出消费方、哪个模块是控制消费方

本节**不**展开:
- 容器 / OS / namespace 具体实现细节
- resource quota 低层参数
- stdout/stderr 捕获协议细节
- replay / cleanup 代码级控制逻辑
- provider bridge 的底层 client 实现

这些内容留到 `03-详细设计.md` 中继续展开。

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 SandboxExecution / SandboxSession / SandboxCommand / IsolationPolicy / SandboxOutput / usage snapshot / control event 真相
- 把 runtime / tools 的执行请求落到受控隔离环境中,并对网络、文件系统、资源和 provider 使用边界进行落实
- 回收 stdout / stderr / output files / execution summary / audit evidence
- 提供 timeout / cancel / kill / retry / replay / cleanup / inspect 控制面

**本模块不做什么**:
- 不决定 runtime 为什么要执行某一步
- 不持有 ToolDefinition、provider contract 或 capability decision 真相
- 不直接把输出确认为 artifact 真相
- 不替代容器平台、宿主 OS、KMS/Vault 或 observability 本体

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 sandbox“为什么存在”,而是让开发者可以直接开始实现:
- execution request 如何进入正式 SandboxSession / SandboxExecution 主线
- 隔离环境怎样建立并承接 fs / network / quota / env injection 约束
- command / tool / provider bridge 如何真正落地到执行面
- stdout / stderr / output files / usage snapshot 怎样被统一回收并进入证据链
- kill / retry / replay / cleanup / inspect 怎样形成一致控制主线

如果不先把这些内容采集清楚,03 很容易退化成:
- 容器参数说明书
- shell/command 片段清单
- cleanup 脚本笔记
- runtime / tools / capability-hub / artifact 之间的接缝各写一套,彼此脱节

#### 第 2 步:列出主流程与关键异常流

- artifact 未接收成功但输出材料已存在
- replay 发生后证据链和原始执行无法对账
- cleanup 提前删除仍需回放或审计的会话材料

#### 第 4 步:列出事件与外部协作点

要回答:

- 哪些输出给 artifact / conversation / observability / operators
- 哪些管理动作必须在 policy、quota、network/fs 检查通过后才能继续
- 哪些控制动作必须 append-only 留证

#### 第 5 步:列出最小测试输入

必须测:
- sandbox execution ≠ runtime execution truth
- SandboxCommand ≠ ToolDefinition
- Isolation boundary ≠ capability access control
- SandboxOutput ≠ Artifact truth

- Replay/retry execution ≠ repeat business decision

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `SandboxSession / SandboxCommand / SandboxOutput / ReplayRequest` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是受控执行主链,`03` 却退化成 container 参数与 shell 命令清单
- 实现者知道有 stdout/stderr capture,却不知道它如何与 artifact、observability、replay 形成同一条主线
- isolation、command、output、cleanup 各写一套,彼此断裂

```rust
/// 表示一次正式进入隔离执行层的执行记录。
pub struct SandboxExecution {
    /// 执行记录标识。
    pub execution_id: SandboxExecutionId,
    /// 上游 runtime execution 引用。
    pub runtime_execution_ref: String,
    /// 对应的执行请求。
    pub request: ExecutionRequest,
    /// 当前会话引用。
    pub session_ref: SandboxSessionId,
}

/// 表示一段正式沙箱会话。
pub struct SandboxSession {
    /// 会话标识。
    pub session_id: SandboxSessionId,
    /// 当前会话生命周期状态。
    pub lifecycle_state: SessionLifecycleState,
    /// 对应的 actor 绑定摘要。
    pub actor_summary: String,
}

/// 表示一次执行请求的最小输入骨架。
pub struct ExecutionRequest {
    /// 对应 work 标识。
    pub work_id: String,
    /// 对应 step 标识。
    pub step_id: String,
    /// 对应 tool 绑定摘要。
    pub tool_binding_summary: String,
}

/// 表示沙箱会话生命周期状态。
pub enum SessionLifecycleState {
    /// 已创建。
    Created,
    /// 已附着并可执行。
    Attached,
    /// 执行中。
    Running,
    /// 已关闭。
    Closed,
}

/// 表示一次 execution 与外部上下文绑定结果。
pub struct ExecutionBinding {
    /// execution 标识。
    pub execution_id: SandboxExecutionId,
    /// 绑定到的 session 标识。
    pub session_id: SandboxSessionId,
}
```

这些对象在该部分里分别承担:
- `SandboxExecution` 负责表达正式执行记录
- `SandboxSession` 负责表达执行所依附的会话壳
- `ExecutionRequest` 负责表达上游请求最小输入
- `SessionLifecycleState` 负责统一会话生命周期语言
- `ExecutionBinding` 负责表达 execution 与 session 之间的正式锚点关系

#### 5.2.4 关键函数代码片段

```rust
/// 根据 runtime / tools 提交的执行请求创建正式 SandboxExecution 与会话锚点。
fn create_sandbox_session(
    session_repo: &dyn SandboxSessionRepo,
    request: ExecutionRequest,
) {
    // [request.校验执行输入]
    // 先确认 work、step、tool 绑定输入完整,且这是一次正式受控执行请求。
    request.validate_execution_request();

    // [SandboxExecution::从请求创建]
    // 再把执行请求收束成正式 SandboxExecution 与会话绑定骨架。
    let execution = SandboxExecution::from_request(request);

    // [session_repo.保存执行与会话锚点]
    // 最后把 execution/session 写入真相层,供 isolation 和 command 主线继续承接。
    session_repo.save_execution_anchor(execution);
}
```

这段实现守住的边界是:
- execution request 必须先进入正式 session 主线,再开始真正动作执行
- sandbox execution 只是隔离执行记录,不替代 runtime 真相
- 会话生命周期与业务任务生命周期必须分层表达

#### 5.2.5 该部分的边界与非职责
- 不负责隔离参数具体求值
- 不负责 command 真实执行
- 不负责输出回收本体
- 不负责业务任务状态推进

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `隔离环境与资源约束部分` 提供 session 锚点输入
- 向 `命令执行与外部能力接缝部分` 提供 execution / tool 绑定输入
- 向 `失败恢复与运维控制部分` 提供 control 主线锚点

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `SandboxExecution ≠ runtime execution truth` 必须写死
- `session lifecycle ≠ business task lifecycle` 必须写死
- execution 若未建立正式 session 就进入 command 执行,会破坏统一控制链

```rust
/// 根据 execution 会话与 capability 限制应用正式隔离策略。
fn apply_isolation_policy(
    isolation_repo: &dyn IsolationRepo,
    session: SandboxSession,
    policy: IsolationPolicy,
) {
    // [policy.校验隔离边界]
    // 先确认网络、挂载、资源约束满足最小安全条件。
    policy.validate_isolation_boundary();

    // [isolation_repo.绑定隔离策略]
    // 再把隔离策略正式绑定到当前会话,形成受控执行环境。
    isolation_repo.bind_policy(session.session_id, policy);

    // [isolation_repo.保存环境约束]
    // 最后保存 fs/network/quota 结果,供 command 执行和控制主线消费。
    isolation_repo.save_environment_constraints(session.session_id);
}
```

这段实现守住的边界是:
- capability access 是外部输入,但 sandbox 自己负责把访问限制落到执行面
- 资源配额是执行约束,不是成本结算真相
- 隔离环境先建立,命令执行后进入

#### 5.3.5 该部分的边界与非职责
- 不负责 provider allow/deny 业务裁决
- 不负责 finance 成本真相
- 不负责 artifact 产物归档
- 不负责宿主 OS 或容器引擎本体

#### 5.3.6 该部分与其他主要部分的接缝
- 从 `执行请求与会话建立部分` 接收 session 输入
- 从 capability-hub / governance 接收 network/provider 限制输入
- 向 `命令执行与外部能力接缝部分` 提供 ready 环境输入
- 向 `失败恢复与运维控制部分` 提供 quota / timeout 基线

#### 5.3.7 该部分的状态 / 约束 / 易错点
- `isolation boundary ≠ capability access control` 必须写死
- `resource quota ≠ finance cost truth` 必须写死
- 若隔离环境未完全建立就开始执行命令,会放大越权风险

```rust
/// 在执行失败、超时或人工干预时执行统一控制链。
fn control_sandbox_execution(
    control_repo: &dyn SandboxControlRepo,
    request: ReplayRequest,
) {
    // [request.校验控制边界]
    // 先确认这是执行层 replay 控制请求,而不是业务层决策重做。
    request.validate_control_boundary();

    // [control_repo.记录 replay 证据]
    // 再把 replay 请求写入控制证据链,保留可追溯原因。
    control_repo.append_replay_record(request);

    // [control_repo.触发受控重放]
    // 最后在保持原始执行证据可追溯的前提下重新进入 sandbox 主线。
    control_repo.trigger_replay();
}
```

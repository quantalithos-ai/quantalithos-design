### 1.2 本文裁决的Sandbox边界

本文只裁决`L4-sandbox`拥有的以下事实和接缝:

1. execution environment identity、actor / responsibility / caller refs和统一受理责任链。
2. resource、filesystem、network、process四维coherent boundary的裁定与真实落实。
3. 对给定body-free launch / isolation policy的验证、执行和fail-closed行为。
4. run、stdout / stderr / file / usage、artifact candidate和observability material的捕获、分层与handoff。
5. typed failure classification、control、lease、orphan、cleanup / reaper和security redline containment。
6. 正式协议、状态、事务、幂等、并发、配置、审计和evidence integrity是否满足上游契约。

以下内容不属于Sandbox验收主体,本文只验正式接缝和“不越权拥有”边界:

| 非Sandbox主体 | 本文只验 | 本文不验 |
|---|---|---|
| `L2-tools` | tool / launch safe refs、统一入口、failure / capture返回 | ToolDefinition、ToolPolicy、semantic execution和工具结果真相 |
| `L2-runtime` | runtime context ref、run / failure / control / capture反馈 | agent loop、checkpoint / recover和runtime业务状态机 |
| `L2-member-service` | member / host safe ref和sandbox outcome | host、session、worker、health与member lifecycle orchestration |
| identity / work / governance / policy owner | body-free refs / summary、freshness、conflict和fail-closed | identity、work、approval、allowlist、policy正文和生命周期 |
| `L1-artifact` / archive | candidate material ref、handoff marker和cleanup guard | Artifact、version、baseline、formal evidence和archive truth |
| `L4-observability` | safe hook / envelope、backpressure和outage接缝 | telemetry store、query、retention与alert truth |

### 1.3 Evidence成熟度与消费边界

```text
AHG / EHR requirement
  -> planned ESLOT-SBX-*
  -> fixed run raw + human-readable report + validation checks
  -> runtime EV-SBX-* alias
  -> fixed RELEASE evidence index / gate results
  -> acceptance packet / independent review
  -> final decision and signoff
```

| 单元 | 当前成熟度 | 可以证明 | 不能证明 |
|---|---|---|---|
| AHG-01~19 / EHR-01~20 | designed handoff | 下游必须承接的门禁 /证据要求 | 已实现、已运行或已验收 |
| TC-SBX-* / suite / gate | planned test contract | 测试输入、操作、断言和producer职责 | 任何case已Passed / Failed |
| ESLOT-SBX-001~021 | planned evidence slot | 未来证据类型、producer和consumer位置 | runtime EV、digest或结果存在 |
| `EV-SBX-*` | 仅真实fixed run后派生 | 某个run-scoped证据项的稳定alias | 可在设计阶段静态预造 |
| acceptance / review文件 | 未来固定入口 | 同一RELEASE的交接、VETO、风险、问题和review | 空模板或draft可授权下游 |

### 1.4 Historical material与blocker原则

旧`README.md`和重建前的旧`06-验收标准.md`只作historical material。旧`SandboxExecution / SandboxSession / SandboxCommand / SandboxOutput / Control`五段主线、旧十章结构、泛化“API / DB / trace”证据、无来源阈值、空checkbox、静态风险接受和签署不得进入当前裁决。

当前目标实现仓、suite / script / CI、环境实例、candidate、四个source run、RELEASE、runtime evidence和acceptance packet均未形成。这些是未来实际验收的entry blocker,不阻塞本文规则设计;任何缺失在实际送验时必须传播为`EntryBlocked / Blocked / absent_not_adjudicated`,不得伪填示例值或降级为可接受风险。

范围闭集规则:

### 4.1 验收过程状态

验收过程状态只允许`NotEntered / EntryBlocked / InReview / Paused / DecisionReady / Closed`。它们不是Sandbox业务状态、测试状态或最终三值结论。

```text
NotEntered
  -> EntryBlocked --(全部AENT重新满足)--> InReview
  -> InReview --(APAUSE触发)--> Paused --(合法resume)--> InReview
  -> InReview / Paused-terminal --(AEXT +候选原子写入)--> DecisionReady
  -> DecisionReady --(全部适用签署生效)--> Closed
```

当前没有实际送验batch、entry record或fixed RELEASE,过程状态为`NotEntered`。这不等于“不通过”。

### 5.7 单项证据定位与裁决

每个功能AC必须形成以下小循环,不得从suite总状态直接抄结论:

```text
canonical FR / AC
  -> fixed design object / flow
  -> required positive + negative TC / parameter / assertion
  -> P0-C source result [+ applicable P0-Q qualification]
  -> runtime evidence item with exact tc_refs / ac_refs
  -> raw / suite report / RELEASE evidence detail / evidence-index.md
  -> independent item disposition
```

| Source role | 固定报告入口 | 证明限制 |
|---|---|---|
| MAIN-CONTRACT | `reports/runs/<main_contract_run_id>/suites/<suite_id>.md`及case JSON | P0-C主证,不证明真实隔离 |
| MAIN-SEAM | `reports/runs/<main_seam_run_id>/suites/<suite_id>.md` | controlled seam补强,不替代主证 / P0-Q |
| OPS | `reports/runs/<ops_run_id>/suites/<suite_id>.md` | simulation补强,不证明真实lifecycle |
| P0Q | `reports/runs/<p0q_run_id>/suites/SUITE-SBX-013.md`和qualification result | candidate / capability / template / environment / provider identity缺一即Blocked |
| RELEASE | `reports/runs/<release_run_id>/evidence/<evidence_id>.md`及`evidence-index.md` | 只聚合四源,不得改source status |

单项未来disposition只允许`Pass / Fail / Disputed / NotEvaluated`作为review词汇;它不是Sandbox业务状态。当前18项均为门禁设计已停审、runtime `NotEvaluated`,不得写Pass。

### 8.2 31个canonical状态enum entry

### 11.3 证据与传播规则

|---|---|---|
| 任一`Triggered` | VETO命中 | 只能`不通过`;禁止有条件通过 |
| 无Triggered但有Blocked / Disputed / NotEvaluated | 尚未完成裁决 | 不得DecisionReady或进入最终通过判断 |
| 17项全部NotTriggered | VETO维度满足 | 只允许继续聚合其他维度,不自动通过 |

Triggered后必须:

1. 不可变保留原fixed run、raw、report、check、evidence tuple、checklist和review。
2. 建立S级缺陷,阻断gate / RELEASE;安全事件先停止新launch并保持containment。
3. 即使缺陷编号尚未建立,checklist仍保持Triggered;缺defect是额外流程缺口。
4. 修复后至少执行L-R5,形成新四source run、新RELEASE和新packet。
5. 新packet可证明新revision NotTriggered,但不得改写或删除原Triggered历史。

### 12.3 S / A / B分级

| 等级 | 定义与典型触发 | 对结论影响 | 最低复验 /风险边界 |
|---|---|---|---|
| S | 任一VETO、安全 / truth / evidence硬红线或P0正式语义失真:host / fake formal success、四维degrade、policy fail-open、泄漏、truth二写 /升格、replay重算、先删证据、redline脱管、非法依赖、造证 /篡改 | 禁止通过 /有条件通过;可terminal不通过;必须contain / preserve | 至少L-R5新四源 + RELEASE、全部受影响TC / suite / checks / review;不可风险接受 |
| A | P0功能、协议、状态、错误、可用性或测试能力失败,尚未命中S | EntryBlocked或Paused;open A=0前禁止通过 /有条件通过 | 至少原TC + family +完整suite,共享面升L-R3 /4 /5;不可风险接受 |

### 12.4 缺陷生命周期与记录


`absent_not_adjudicated`只描述尚无结论,不是第四种最终结论;当前未进入验收也不等于已经裁决为不通过。本文经用户审查后从`06`进入`07`属于设计文档流程,不生成也不依赖上述runtime authorization。

### 14.3 九维输入与结论传播

每个维度只允许输出三值;输入不完整时不输出维度结论,过程保持未DecisionReady。

| 维度 | 通过条件 | 有条件通过边界 | 不通过 /不可裁决边界 |
|---|---|---|---|
| 功能验收 | AC-SBX-006~023全部适用P0闭环Passed | 仅非P0 residual有效Accepted | mandatory功能AC Failed为不通过;Blocked / missing不可裁决 |
| 数据 /架构红线 | AC-SBX-026~035、RL-SBX-001~016和双轴断言成立 | P0 /红线无窗口,只允许scope披露 | mandatory红线Failed / VETO predicate为不通过;P0-Q Blocked不可裁决 |
| 接口 /事件 /同步 | 55 protocol、SYNC-SBX-001~014和mandatory shared seam成立 | 仅consumer联合E2E后置且RR-SBX-004有效Accepted | formal surface / mandatory seam Failed为不通过 |
| 状态 /事务 /一致性 | 31个canonical enum entry按30个owner-level machine归属、14事务 /重放、19 race及canonical slices成立 | P0 truth /一致性无窗口 | 非法状态、partial UoW、未commit先外呼、二写、重算或双winner为不通过 |
| 非功能 | AC-SBX-036~041的mandatory P0-C / P0-Q和零容忍成立 | 仅未激活量化 / P1 residual有效Accepted | mandatory NFR Failed为不通过;required Blocked不可裁决 |
| Evidence / review | 21 slot适用集、九schema / control、fixed report和独立review完整 | 无条件窗口 | integrity Failed为不通过;missing / disputed不可裁决 |
| VETO | 17项全部NotTriggered | 无条件窗口 | 任一Triggered为不通过;Blocked / Disputed / NotEvaluated不可裁决 |
| 缺陷 /复验 | open S / A / B=0且关闭 / supersede完整 | 仅合格open B有效Accepted | open S / A或确认失败为不通过 / Paused;未接受B不可裁决 |
| 风险 /遗留 | accepted_set为空且catalog /披露 /关闭项对账完整 | 仅有效Accepted非P0项 | 非法Accepted、Rejected blocker或DesignReopen为不通过 / Paused;Pending等不可裁决 |

任一维度不通过支配总体结论;维度有条件通过不能抵消其他维度失败。normal路径任一维度尚不可裁决时,不得生成总体三值。

### 14.4 唯一三值算法

```text
1. RequireSourceProcessState(InReview or Paused-with-terminal-trigger)
2. ValidateCommonExit(AEXT-SBX-001~013, FDQ-SBX-001~008)
3. SelectExactlyOnePath(AEXT-SBX-015 or AEXT-SBX-016)
4. FreezeDecisionInputDigests(RELEASE, acceptance files, review files)
5. EvaluateNineDimensionsWithoutStatusCoercion()
6. ApplyVetoSeverityAndRiskDominance()
7. ComputeExactlyOneDecisionCandidate()
8. ValidateAEXT-SBX-014(candidate, signoff contract, authorization contract)
9. AtomicallyPersist(DecisionReady, Draft, candidate, input digest)
10. DeriveExplicitNextStageAndReleasePreparationAuthorizations()
11. CollectRequiredSignoffsAgainstFrozenDecisionDigest()
12. MarkClosedAndEffectiveOnlyWhenAllRequiredSignoffsAreValid()
```

| 总体结论 | 必须全部满足 | 禁止条件 | 未签署时 |
|---|---|---|---|
| 通过 | NormalComplete;九维全通过;P0完整;17 VETO全NotTriggered;open S / A / B=0;`accepted_set`真实为空;争议=0 | Accepted risk、Failed / Blocked / missing / invalidated、DesignReopen或未评估mandatory项 | Draft / PendingSignoff,不得消费 |
| 有条件通过 | NormalComplete;硬门禁全通过;仅有有效Accepted非P0风险;open S / A=0;仅关联B可open;condition / expiry / follow-up有效 | VETO、P0、truth、安全、evidence、execution blocker、A或Pending / Proposed / Expired风险 | Draft / PendingSignoff,不得条件进入 |
| 不通过 | NormalComplete中任一维度确认不通过,或TerminalRejection完整成立 | 不得把未进入 /缺材料本身伪造成不通过;terminal不得局部通过 | Draft / PendingSignoff,仍不授权下游 |

规范结论汇总载体必须保留以下五行。运行期只在对应输入完整后填写实际值;本文不预填结果。

| 维度 | 结论 | 说明 |
|---|---|---|
| 功能验收 | `通过 / 有条件通过 / 不通过` | 聚合功能、数据 /架构、接口 /同步、状态 /事务四维;P0失败则不通过,mandatory输入未完成则不填值 |
| 非功能验收 | `通过 / 有条件通过 / 不通过` | 聚合非功能、evidence / review、VETO、缺陷 /复验和风险;VETO、S / A、P0-Q和evidence硬门禁无窗口 |
| 发布准备 | `通过 / 有条件通过 / 不通过` | 按§14.5独立判断;目标stage未包含release或release前置缺失时不得写通过 /有条件通过 |
| 总体结论 | `通过 / 有条件通过 / 不通过` | 仅按本节对九维、risk set和normal / terminal路径聚合一次,不得人工提升 |
| 是否允许进入下一阶段 | `是 / 否 / 有条件` | 总体结论Effective后显式写入target stage、允许 /禁止动作及stop / expiry trigger |

若发布准备属于frozen target的mandatory目标,其不通过使总体不通过;若target只到implementation,必须记录“当前不授权发布准备”,不得写N/A,也不得借此否定scope内已经成立的component结论。

### 14.5 下一阶段与发布准备双授权

| 最终结论 /状态 | 进入下一阶段 | 发布准备 |
|---|---|---|
| 通过 + Effective | `是`,或按target stage显式`否` | 仅release target且附加前置全满足时`是`;否则`否` |
| 有条件通过 + Effective | 仅可`有条件`,每项condition须有下游承接和pre-boundary stop gate | 仅release target、条件不涉及硬前置且release authority签署时可`有条件`;否则`否` |
| 不通过 + Effective | `否` | `否` |
| Draft / PendingSignoff / Invalidated / Superseded | `否` | `否` |
| 无最终结论 | `否` | `否` |

发布准备非“否”时,还必须满足:

1. target stage和claim明确包含release / pre-release。
2. 同一RELEASE的P0-C和P0-Q均有效Passed,无candidate / provider / lab / identity缺口。
3. 适用physical rollout / rollback / drift、soak / reaper、alert / response、retention / media前置具有真实carrier、runbook、evidence和authority。
4. 真实material适用时anti-leak、least privilege、provider native audit及cleanup / containment资格完整。
5. release / operations相关Accepted风险有有效stop gate,且不延期P0、VETO、S / A、安全或evidence前置。
6. Release / operations authority签署且decision / signoff未失效。

因此设计完成、进入编码实施或component acceptance均不表示release-ready。任何Accepted过期都会使相关条件授权立即失效。

### 14.6 唯一归档入口与记录契约

最终结论唯一写入`reports/acceptance/handoff.md`的`Final Decision and Signoff`受控section。禁止创建`final-decision.md`、`acceptance-summary.md`或其他同义入口。

| 字段组 | 必需内容 | 禁止替代 |
|---|---|---|
| decision identity | RELEASE、四source refs / digest、design / subject / core / harness / config identity、claim、target stage | branch、latest、路径名或签署日期 |
| decision input | AEXT / FDQ、九维、VETO / risk / issues / human review / agent review版本和digest | “全部通过”自由文本 |
| decision | exact三值、normal / terminal path、reason codes、unmet / condition refs | 模糊结论、N/A吞并未评估 |
| authorization | next-stage / release-preparation独立三值、允许 /禁止动作、stop / expiry trigger | 从总体结论自动推断 |
| signoff | required role set、actual authority identity / source、逐角色disposition / time / reason、decision digest | 姓名占位、checkbox或单一总签 |
| lifecycle | 生效状态、invalidation reason / time、superseding ref | 覆盖旧记录 |

handoff draft不得预填结论或签署。final section由Final acceptance authority基于immutable packet形成,任何补充都不得改写raw、report、EV、VETO、defect或risk事实。

### 14.7 签署角色与生效

| 签署角色 | 适用性 | 必须确认 | 不得越权 |
|---|---|---|---|
| Final acceptance authority | 必签 | identity、九维、三值、双授权、required set与packet一致 | 单方面改专业finding或接受风险 |
| Sandbox / architecture owner | 必签 | execution truth、模块 /依赖、四维boundary、protocol和seam | 代替test / security确认runtime结果 |
| Delivery / implementation authority | 必签 | subject / build / core / harness / config generation与送验声明一致 | 用commit存在证明测试通过或改变设计 |
| Test / evidence authority | 必签 | 250 P0、四source、21 slot、raw / report、checks、缺陷 /复验和review | 手写EV、吞Blocked或接受风险 |
| Security / safety authority | 必签 | policy fail-closed、redaction、containment、cleanup / lease / reaper / redline | 解除containment或VETO |
| Release / operations authority | 条件必签 | release / ops前置和相关Accepted risk | 在不适用时宣称release-ready |
| Consumer / system acceptance authority | 条件必签 | joint E2E claim、shared baseline、consumer lifecycle和跨仓condition | 把tools / runtime / member语义移入Sandbox |

条件角色的适用性必须从frozen claim、target stage与Accepted风险集合可审计派生。每个有效签署必须记录actual principal / role / authority source、decision digest、RELEASE /四source digest、packet / review version、`Approve / Reject / Disputed`、责任声明、时间和必要reason / finding refs。

正式实例使用以下四列表;空值不构成签署,本文不填写实际主体、结论或日期。

| 角色 | 姓名 / 责任 | 结论 | 日期 |
|---|---|---|---|
| Final acceptance authority | 实际principal identity与authority source;负责最终聚合和双授权 | 实际`Approve / Reject / Disputed` | 实际签署时间 |
| Sandbox / architecture owner | 实际principal identity与authority source;负责truth、boundary、依赖、protocol和seam | 实际`Approve / Reject / Disputed` | 实际签署时间 |
| Delivery / implementation authority | 实际principal identity与authority source;负责交付identity与送验范围 | 实际`Approve / Reject / Disputed` | 实际签署时间 |
| Test / evidence authority | 实际principal identity与authority source;负责P0、四source、evidence、缺陷 /复验和review | 实际`Approve / Reject / Disputed` | 实际签署时间 |
| Security / safety authority | 实际principal identity与authority source;负责policy、redaction、containment、cleanup / redline | 实际`Approve / Reject / Disputed` | 实际签署时间 |
| Release / operations authority | 适用时填实际identity与authority source;负责release / ops前置 | 实际值;不适用须有可审计推导 | 实际签署时间 |
| Consumer / system acceptance authority | 适用时填实际identity与authority source;负责joint claim与跨仓condition | 实际值;不适用须有可审计推导 | 实际签署时间 |

生效顺序为:冻结decision input并形成Draft;四个专业必签角色和适用条件角色分别签署;任一Reject / Disputed使状态为RejectedBySignoff并进入Paused或新不通过Draft;Final acceptance authority最后核对并签署;只有required set全部有效Approve且绑定同一digest,结论才成为Effective,过程才可Closed并按显式授权交接。签署不是风险接受,Approve也不能覆盖未在risk文件中逐项接受的事项。

### 14.8 失效、Supersede与历史保留

| 触发 | 原记录 | 过程与授权动作 |
|---|---|---|
| RELEASE /四source / subject / config / claim / target stage变化 | Invalidated并保留immutable历史 | 新batch全量AENT;撤销双授权 |
| evidence / review / defect / VETO / risk失效或重开 | Invalidated | 立即Paused;停止消费旧结论 |
| Accepted过期、follow-up变化 /删除或B升A / S | Invalidated | 撤销条件授权;按§12~§13重判 |
| signer authority / delegation失效或decision digest不匹配 | Invalidated | 重新签署或重裁决,不得只补日期 |
| 新完整packet形成新结论 | 原记录Superseded,新记录有独立identity / digest | 旧结论不得继续授权 |
| 仅非语义排版 /说明修正 | 保留input digest并形成新record version | 任一语义字段变化都须重新签署 |

失败run、terminal未评估清单、旧decision和旧risk必须保留。物理retention期限由后续`07/09`选择,但不能越过验收、缺陷、P0-Q处置和调查关闭guard。

当前没有fixed RELEASE、runtime evidence、review、defect / risk记录、decision input、authority主体或签署。因此九维没有实例结论,双授权均不存在,不得从本文设计完成状态推导任何验收或发布事实。

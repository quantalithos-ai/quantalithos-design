## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的主入口不是 IDE、不是工单系统、也不是命令行,而是**对话协作界面**。用户通过 Chat 和 Assistant 私聊发起想法,在项目群聊里和 AI 员工协作,在频道里围观局部讨论,在 GateCard 上做关键审批,并随时登录某个员工查看他当前在做什么。没有 Chat,前面已经建立好的 identity / conversation / work / process / governance / artifact 六域就无法被用户以“管理者视角”消费,产品也会退化成一组后端能力而不是可用的软件研发协作平台。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 3 当前) | 痛点 |
|---|---|---|
| 仓文档 | 只有 README 骨架 | 端侧产品型样板尚未建立 |
| 对话真相源 | `L1-conversation` 已有完整 00/01 | UI 消费方式与验收口径未仓级化 |
| 实时推送 | AG-UI 17 事件已在 conversation / sdk 草案中定义 | Chat 端如何承接事件流尚未显式化 |
| Gate 流程 | governance 与 conversation 已定义 Gate 事件链 | 用户审批体验、卡片形态、超时反馈未落到仓级需求 |
| 多端形态 | README 已提出 desktop/web/mobile | 多端差异、离线与同步策略尚无正式需求 |

### 2.3 为什么要做(量化依据)

- `product/产品矩阵.md` 明确 Chat 是 10 个产品中的 **① 主入口产品**
- `product/最终目的.md` 将“协作载体是对话”“关键节点强制人类”“过程始终可观察”都直接落在 Chat 体验上
- `L1-conversation` 已给出 `PostTurn P95 < 100ms`、`StreamEvents P95 < 500ms` 的后端能力目标,Chat 需要围绕这些能力定义端侧可感知成功标准
- 若没有 Chat 样板,后续 `L5-console / L5-runner / L6-bridges` 都缺少端侧产品型写法参照

### 2.4 业务问题 vs 技术问题

- **业务问题**:管理者如何以自然、低门槛、可观察的方式管理一支 AI 软件团队
- **技术问题**:多端同步、对话四形态渲染、AG-UI 事件承接、GateCard 六段式交互、Artifact 预览、员工登录、权限可见性、弱网与大群性能

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 用户在和 Assistant 的私聊中表达新项目想法
2. 系统创建项目群聊,用户在群里与多名 AI 员工协作
3. 用户在频道或线程中围观某个子议题讨论
4. Gate raised / decided 被渲染成 GateCard 并要求用户审批
5. 用户点击员工头像进入“登录员工”视图查看当前上下文
6. 用户在聊天中查看 WorkItem / child WorkItem 的协作层状态,必要时进入更细的执行计划视图

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **管理者**,我想要 **在和 Assistant 的私聊里发起一个项目想法**,以便 **不用理解技术细节也能启动软件项目** |
| 优先级 | P0 |
| 验收条件 | **Given** 用户进入私聊 **When** 发送自然语言需求 **Then** 在 500ms 内看到自己的 Turn 并收到 Assistant 初步回应占位 |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **项目 Owner**,我想要 **在项目群聊里看到 AI 员工协作与系统进度**,以便 **随时知道项目当前在做什么** |
| 优先级 | P0 |
| 验收条件 | **Given** 项目 group 已创建 **When** 新的 member/system/gate/artifact Turn 到达 **Then** 群聊实时更新并显示正确渲染 |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **审批者**,我想要 **在 Chat 内直接处理 GateCard**,以便 **不离开协作上下文就能做关键决策** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个 active Gate 被推送 **When** 用户打开 GateCard 并选择选项 **Then** 请求成功提交且群聊里出现对应 decision 反馈 |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **管理者**,我想要 **登录某个 AI 员工查看他当前在干什么**,以便 **在不直接看代码的前提下理解进展与阻塞** |
| 优先级 | P1 |
| 验收条件 | **Given** 某成员 active 且有当前上下文 **When** 用户点击“登录员工” **Then** 可看到该成员当前任务、相关对话与最近活动 |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **用户**,我想要 **在聊天流里预览 Artifact 与其引用关系**,以便 **在审批或讨论时不用切换到其他产品** |
| 优先级 | P1 |
| 验收条件 | **Given** 某 Turn 引用了 Artifact **When** 用户展开预览 **Then** 可看到摘要/预览/相关链接,并能回到原对话上下文 |

### 5.3 替代流程

- 网络抖动 / 重连 → 使用 `last_event_id` 或等效游标续传,不要求用户手动刷新页面
- 无权查看某 conversation / employee context → 显示无权限状态,不泄漏正文内容
- GateCard 已过期 / 已决策 → 卡片变为只读历史状态,用户仍可查看证据与结果
- Artifact 无法预览 → 保底显示标题、类型、引用链接与错误提示

| F-014 | 大群 / 长流性能优化 | P1 | F-001 / F-003 | 500+ 参与者与长历史加载 |

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| BR-001 | conversation kind=dm | 只展示两方上下文,不出现项目群侧栏 |
| BR-002 | 新 Turn 到达 | 必须在当前视图中按 kind 正确渲染 |
| BR-003 | GateCard 被审批 | 立即进入 pending / submitted / decided 中的正确状态 |
| BR-004 | 用户无权限读某对话 | 不显示任何正文与成员细节 |
| BR-005 | 员工登录 | 必须是只读观察,不改变该员工真实工作状态 |
| BR-006 | Chat 展示 WorkItem / child WorkItem | 只展示团队协作级工作事实,不默认把所有个人执行步骤都抬升为任务卡片 |
| BR-007 | 展开 ImplementationPlan 视图 | 必须是受控、只读或受限编辑入口,且不得与 WorkItem 真相混淆 |
| BR-008 | 移动端打开复杂页面 | 优先保障审批、消息阅读和关键预览,非核心面板可降级 |
| BR-009 | 多端同时在线 | 同一用户的已读/当前会话状态应最终一致 |

### 8.2 关键 UX 约束

| 约束 | 说明 |

| 弱网可恢复 | 重连后能恢复到最近上下文 |

| Conversation | conversation | Conversation | active / archived / locked |

### 9.2 数据关系图

```text
Chat UI
  ├─ Conversation / Turn timeline
  ├─ GateCard(gate ref)
  ├─ Project progress(project ref)
  ├─ Member login(global_member ref)
  └─ Artifact preview(artifact ref)
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| 本地会话缓存 | 短期 | 本地缓存可重建 | 自动淘汰 |
| 已读/当前视图状态 | 会话级 | 本地/云端轻量同步 | 可重建 |
| GateCard 历史视图 | 跟随 Conversation / Gate 历史 | 只读回看 | 不在 UI 侧硬删 |
| Artifact 预览缓存 | 短期 | 本地可失效 | 自动淘汰 |

### 9.4 隐私与合规要求

| 数据字段 | 敏感级别 | 保护措施 | 合规依据 |
|---|---|---|---|
| 私聊正文 | 高 | 严格按 conversation 权限控制显示 | 隐私与审计基线 |
| 审批证据链接 | 中高 | 仅授权者可见 | ISO 42001 / 9001 |
| 员工当前上下文 | 中高 | 登录员工仅对授权人开放 | 最小权限原则 |

## 11. 验收标准

### 11.1 功能验收标准

| 功能 ID | 验收场景 | Given-When-Then | 执行方式 |
|---|---|---|---|
| F-001 | 四形态对话切换 | **Given** 已存在 group/channel/dm/thread **When** 用户进入对应入口 **Then** 看到正确布局与上下文 | E2E |
| F-004 | GateCard 审批 | **Given** 一个 active Gate 被推送 **When** 用户选择通过/拒绝/候选方案 **Then** 结果提交成功且卡片状态刷新 | E2E |
| F-006 | 员工登录 | **Given** 某 active Member 有上下文 **When** 用户点击登录 **Then** 展示当前任务、相关对话与最近活动 | E2E |
| F-007 | Artifact 预览 | **Given** Turn 引用了 Artifact **When** 用户展开预览 **Then** 可看到摘要/预览/跳转链接 | E2E |
| F-009 | 收件箱通知 | **Given** 新 Gate / mention / 项目更新到达 **When** 用户打开收件箱 **Then** 能看到正确分类与状态 | E2E |
| F-011 | 无障碍关键路径 | **Given** 键盘 / 屏幕阅读器用户 **When** 完成私聊发言与 Gate 审批 **Then** 核心路径可独立完成 | accessibility audit |

### 11.2 非功能验收标准(量化)

| 维度 | 指标 | 验收命令 / 工具 | 通过阈值 |
|---|---|---|---|
| 响应性 | 新 Turn 可见延迟 | E2E / benchmark | < 500ms |
| 响应性 | 首屏进入主会话 | RUM / Lighthouse / Web Vitals | < 2s |
| 可用性 | 关键路径可用率 | 监控 dashboard | ≥ 99.9% |
| 无障碍 | WCAG 2.2 AA 核心路径 | axe / 手工审计 | 100% 核心页面 |
| 性能 | 大群/长流可用性 | 压测 + 手测 | 500+ 参与者可用 |

### 11.3 "主功能完成"的总验收口径

## 12. 风险与待确认事项

### 12.1 已知风险(分常见 / 边缘)

**常见风险**:

| ID | 风险 | 影响 | 缓解策略 |
|---|---|---|---|
| R-001 | 长消息流导致用户被 system/gate/artifact Turn 淹没 | 高 | 明确视觉层级 + 过滤/折叠策略 |
| R-002 | GateCard 复杂度过高影响审批效率 | 高 | 六段式信息分层 + 默认最小必读 |
| R-003 | 多端状态同步不一致 | 中 | 在线状态最终一致 + 明确重连语义 |
| R-004 | 员工登录暴露过多内部细节 | 高 | 只读观察 + 权限分层 |

**边缘风险**:

| ID | 风险 | 影响 | 缓解策略 |
|---|---|---|---|
| RE-001 | 500+ 参与者大群使渲染与滚动显著退化 | 高 | 虚拟列表 + 分段加载 |
| RE-002 | AG-UI 事件语义与 conversation 实际投影漂移 | 高 | 契约测试 + SDK 版本锁 |
| RE-003 | 移动端承担过多桌面级功能导致体验崩坏 | 中 | 首期严格限制移动端目标 |

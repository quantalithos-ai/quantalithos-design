## 1. 业务背景与驱动力

### 1.1 业务背景

Chat 是 Quantalithos 对用户的主入口,承载“用户是管理者、协作载体是对话、关键节点强制人类、过程始终可观察”四条最直接的产品承诺。它不是一个普通消息客户端,而是把 conversation、gate、artifact、project、member 几类业务对象编织成统一协作界面的端侧产品。没有 Chat,六域只能停留在服务设计层；有了 Chat,这些服务才第一次以管理者能理解、能控制、能信任的方式被消费。

### 1.2 业务驱动力

**业务驱动力**:
- 管理者需要通过自然对话而不是技术界面来发起、监督和审批软件项目
- 关键决策必须在协作上下文里完成,不能跳出到另一个陌生管理系统
- 用户对平台的信任建立在“随时可看、可问、可介入”的体验上

**技术驱动力**:
- 需要把 conversation 的 StreamEvents、governance 的 Gate、work 的项目状态、artifact 的预览能力收敛到一个实时多端界面
- 需要在 desktop / web / mobile 上保持足够一致的交互模型,同时允许按端降级

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 响应性 | 新 Turn 可见延迟 | < 500ms | E2E / benchmark |
| 响应性 | 首屏进入主会话 | < 2s | RUM / Web Vitals |
| 可用性 | 管理者主路径可用率 | ≥ 99.9% | 监控 |
| 交互 | GateCard 六段式完整展示 | 100% | E2E |
| 无障碍 | WCAG 2.2 AA 关键路径 | 100% | accessibility audit |
| 一致性 | desktop + web 主路径一致 | 100% 样本流 | 手工验收 + E2E |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| Chat 必须是管理者视角,不是开发者视角 | `product/最终目的.md` §3.1 | 文案、导航、默认动作都不能技术化 |
| 四形态对话(group/channel/dm/thread)必须完整承接 | `产品矩阵.md` §3.1 + conversation 域 | 布局不能只支持单一聊天流 |
| GateCard 六段式必须完整展示与审批 | README + governance 模型 | 审批组件必须是一等模块 |
| 所有端侧产品必须通过 SDK 连 Server,不能绕过 | `sdk-draft` + `产品矩阵.md` 通用原则 | Chat 只能消费 SDK 暴露的接口 |
| AG-UI 17 事件是实时流标准入口 | README + conversation 域 | 流式状态层必须围绕事件驱动设计 |
| 历史对话永久可查且可审计 | README + 9001 文档要求 | 本地状态不能成为真相源 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| 前端框架 | React / Svelte 候选 | 可在仓内最终定型 |
| 桌面外壳 | Tauri 优先 | Electron 作为备选 |
| 移动端范围 | 可选,偏审批/阅读 | 后续可扩全功能 |
| 流传输 | SSE / WS | 可按场景双持 |
| 本地缓存策略 | 会话级缓存 | 可演进离线能力 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| 新 Turn 可见延迟 | < 500ms | conversation 流目标 |
| 主会话首屏 | < 2s | 主入口体验要求 |
| 大群参与者 | 500+ | README 开放问题 |
| 并发在线用户 | 10w 级长期目标 | conversation 域容量规划 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 对话 UI 形态演进 | 高 | 会话容器与消息渲染分层 |
| Gate / Artifact 等特殊卡片种类 | 中高 | timeline item registry |
| 多端差异 | 中高 | shared core + platform shell |
| 实时流协议 | 中 | event transport adapter |
| 权限可见性规则 | 中 | SDK/domain projection 与 UI 展示分离 |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **事件驱动客户端 + 共享状态核心 + 多端壳层**(当前) | 最贴合实时协作、便于多端复用 | 状态管理较重 | ✅ |
| 传统页面路由 + 请求后刷新 | 简单 | 违背实时协作体验 | ❌ |
| 每端独立重写状态逻辑 | 平台自由度高 | 交互漂移、维护成本高 | ❌ |
| 完全本地优先离线应用 | 离线强 | 当前不符合主协作路径 | ❌ |

**最终选择**:**SDK 驱动的事件型客户端架构 + 共享 UI/状态核心 + desktop/web/mobile 壳层**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| UI 围绕事件流而不是轮询建模 | 协作实时感强 | 状态同步复杂 |
| 多端共享核心状态层 | 行为口径一致 | 抽象层更厚 |
| 特殊 Turn 渲染组件化 | Gate / Artifact / system 可持续扩展 | 初始组件体系更重 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```text
管理者 / 参与者 / 审批者
          │
          ▼
      ★ quantalithos-chat ★
      - conversation views
      - GateCard approvals
      - member login view
      - artifact previews
      - inbox / notifications
        │        │        │
        │        │        └────────▶ observability(前端事件)
        │        └─────────────────▶ sdk(events/rpc)
        └──────────────────────────▶ desktop/web/mobile shells
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 承载 group/channel/dm/thread 的协作界面
- ✅ 渲染普通 Turn、系统 Turn、GateCard、Artifact 预览
- ✅ 提供项目协作主入口、收件箱与员工登录视图
- ✅ 在用户上下文内完成审批与查看关键进展

**不做什么**:
- ❌ 不持有 Conversation / Gate / Project / Artifact 的业务真相
- ❌ 不提供组织治理总台与全局管理(属于 Console)
- ❌ 不提供代码编辑器或开发者工作台
- ❌ 不直接调用六域服务私有 API,只能经 SDK

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| SDK(core/events) | 100%(编译期) | 客户端接口漂移 | 版本锁 |
| conversation 流服务 | 99.9% | 新消息/历史流中断 | 重连 + 续传 |
| governance 查询/审批 | 99.9% | GateCard 提交失败 | 回退到只读 + 重试 |
| artifact 预览 | 99.9% | 预览失败 | 显示摘要/链接占位 |
| identity / work / process 查询 | 99.9% | 成员状态/进度栏不完整 | 局部 skeleton / stale data |

### 4.4 关键依赖风险

- StreamEvents 与本地状态模型若不一致,会造成重复消息、乱序更新或 Gate 状态错乱
- 员工登录若跨越权限边界过深,会暴露 runtime 内部不该给管理者看的细节
- 多端壳层若各自演化,Chat 会快速分裂成不同产品体验

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Conversation Experience | 核心域 | 会话流、切换、阅读与发言体验 |
| Gate Interaction | 核心域 | 审批卡片与关键决策交互 |
| Member Perspective | 支撑子域 | 登录员工、成员详情、状态面板 |
| Artifact Projection | 支撑子域 | 聊天上下文内的制品预览与引用 |
| Notification / Inbox | 支撑子域 | 待办、提醒、聚合入口 |
| Platform Shell | 通用子域 | desktop/web/mobile 宿主差异 |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Timeline | 会话流展示与增量更新 | TimelineItem / ConversationView |
| Gate UI | GateCard 渲染与决策交互 | GateCardView |
| Member Lens | 员工登录与状态观测 | MemberContextView |
| Artifact View | 制品引用与预览 | ArtifactPreviewView |
| Work Projection | WorkItem / child WorkItem 协作层投影 | WorkItemView / WorkTreeView |
| Execution Lens | ImplementationPlan / plan item 执行视图 | ImplementationPlanView |
| Inbox | 通知与待审批聚合 | InboxItem |
| Shell | 多端导航、窗口、生命周期 | AppShellState |

### 5.3 上下文映射关系

- conversation → Timeline: **Conformist**，Chat 直接遵从 Turn/Conversation 真相与事件流
- governance → Gate UI: **Customer-Supplier**，Chat 需要把 Gate 变成人类可操作的界面
- identity/work/process → Member Lens / Work Projection / Timeline side panels: **Conformist + Projection**
- artifact → Artifact View / Execution Lens: **Open Host Service**，Chat 只消费预览元数据与 execution artifacts
- observability ← 所有 UI 交互：前端行为也要留痕

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| TimelineItem | 聊天时间线中的统一渲染单元,可对应 message/gate/artifact/system | Timeline |
| GateCard | 人类审批与选择的可交互卡片 | Gate UI |
| Member Lens | 用户临时进入某个员工视角的只读观察模式 | Member Perspective |
| WorkTreeView | 面向聊天协作层展示的 WorkItem / child WorkItem 树视图 | Work Projection |
| ImplementationPlanView | 面向受控展示的执行计划与 plan item 视图 | Execution Lens |
| InboxItem | 与当前会话无关但需要用户关注的聚合事件 | Inbox |
| Shell | 承载共享聊天核心的具体平台壳层 | Platform Shell |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```text
user devices
  ├─ desktop shell(Tauri/Electron)
  ├─ web shell(PWA/SPA)
  └─ mobile shell(optional)
           │
           ▼
   shared chat core
   ├─ timeline state
   ├─ gate interaction state
   ├─ inbox / notifications
   ├─ artifact preview adapters
   └─ sdk adapters(events/rpc)
           │
           ▼
      Quantalithos SDK
           │
           ▼
   conversation / governance / work / identity / artifact services
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| shared chat core | 共享状态、事件流、业务交互编排 | TypeScript | 逻辑核心 |
| web shell | 浏览器/PWA 承载 | TypeScript + React/Svelte | 主入口 |
| desktop shell | 原生桌面窗口、通知、系统集成 | TypeScript + Tauri/Electron | 深桌面集成 |
| mobile shell | 审批与阅读优先的轻量端 | TypeScript + RN/其他 | 可选 |
| sdk adapters | RPC / event / auth 封装 | TypeScript SDK | 对接真相源 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 会话实时更新 | SDK events over SSE/WS | 轮询 | 满足实时协作与 Gate 体验 |
| 查询详情 / 提交审批 | SDK RPC / HTTP | 自写 fetch | 保持契约一致 |
| 多端共享逻辑 | shared packages | 每端独写 | 避免行为漂移 |
| 桌面系统通知 | shell adapter | 浏览器通知单一实现 | 平台差异需要隔离 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| 会话真相 | conversation 服务 | chat core |
| Gate 真相 | governance 服务 | Gate UI |
| 本地视图状态 | chat client | chat client |
| 前端交互留痕 | chat client / observability pipeline | observability |

### 6.5 部署拓扑

- shared chat core 作为 monorepo 内共享包
- web / desktop / mobile 是不同壳层,共享核心状态和组件逻辑
- 端侧不自建后端中间层,直接通过 SDK 接 Server

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```text
platform shells
      │
      ▼
shared ui + state core
      │
      ├─▶ timeline / gate / inbox / previews
      └─▶ sdk adapters
              │
              ▼
           server truth
```

### 7.2 层间约束规则

- shell 只处理平台差异,不实现业务协作逻辑
- shared chat core 不直接依赖某个具体平台 API,通过 shell adapter 注入
- Gate UI 不自行推断业务状态,只消费 governance/SDK 暴露的状态机
- Timeline 渲染层不改写 Turn 真相,只做排序、折叠、投影与局部 UI 状态
- SDK adapters 是唯一服务接入边界,禁止页面组件直接拼 RPC

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| EventStreamAdapter | shared core | web/desktop/mobile sdk adapters |
| NotificationAdapter | shared core | shell implementations |
| NavigationAdapter | shared core | shell/router implementations |
| ArtifactPreviewProvider | shared core | artifact SDK projection adapter |
| AuditEmitter | shared core | observability-aware adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(用户主入口,所有主协作流汇聚) |
| 传出耦合 | 中高(conversation/governance/work/identity/artifact/sdk) |
| 不稳定性 | 中 |
| 抽象度 | 中高(多端共享核心 + shell adapter) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Conversation / Turn | conversation | chat timeline | 最终一致(事件流) | 重连与乱序处理 |
| Gate state | governance | Gate UI | 最终一致 | 过期/重复提交 |
| Project / iteration summary | work / process | side panels / inbox | 最终一致 | 短时旧数据 |
| Member context | identity / runtime projection | Member Lens | 最终一致 + 权限限制 | 暴露过深 |
| 本地 UI state | Chat client | Chat client | 本地强一致 | 可重建 |

### 8.2 一致性层次

- 会话正文与 Gate 真相来自服务端,Chat 只做最终一致消费
- 本地导航、折叠、已读、弹层状态由客户端强一致维护
- 多端状态同步只保证会话级最终一致,不要求所有微交互实时同步

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| 事件流断开 | SSE/WS 中断 | 通过 last_event_id / 游标重连补拉 | `event_id` |
| Gate 提交失败 | 网络 / 后端错误 | 保留卡片状态为待重试或只读错误态 | `gate_id + actor_id` |
| 重复事件到达 | reconnect / replay | timeline 去重 | `event_id` |
| Artifact 预览失败 | 下游不可用 | 保底显示 metadata 与跳转链接 | `artifact_id` |

## 9. 关键技术选型

### 9.1 shared chat core + platform shells

| 维度 | 内容 |
|---|---|
| 当前选择 | 共享核心状态与组件逻辑,外层多端壳层 |
| 备选方案 | 每端独立实现 |
| 选择理由 | Chat 是主产品入口,行为漂移成本极高,共享核心比完全独立更稳 |
| 演进路径 | 特定平台能力可在 shell 层渐进增强 |
| 不可逆程度 | 中高 |

### 9.2 SDK-first 接入

| 维度 | 内容 |
|---|---|
| 当前选择 | 所有服务访问都经 TypeScript SDK |
| 备选方案 | 前端直接请求各服务 |
| 选择理由 | 契约统一、版本演进可控、便于未来 bridges/mobile 共用 |
| 演进路径 | SDK 可增强 streaming helpers / auth adapters |
| 不可逆程度 | 高 |

### 9.3 timeline item registry

| 维度 | 内容 |
|---|---|
| 当前选择 | 不同 Turn/事件类型走统一 timeline item 注册机制 |
| 备选方案 | 在单一消息组件里堆条件分支 |
| 选择理由 | GateCard、Artifact、system、future cards 都会持续增加,注册机制更利于演进 |
| 演进路径 | 可从简单 registry 演化到插件式渲染 |
| 不可逆程度 | 中 |

### 9.4 SSE/WS 双持流模型

| 维度 | 内容 |
|---|---|
| 当前选择 | 以 SSE 为默认,WS 处理更互动场景 |
| 备选方案 | 仅轮询 / 仅 WS |
| 选择理由 | 兼顾实现成本、实时性与多环境兼容性 |
| 演进路径 | 根据规模与交互复杂度调整主协议 |
| 不可逆程度 | 低 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:共享核心 + 多端壳层 + 事件驱动(当前) | 方案 B:传统页面应用 | 方案 C:每端独立实现 |
|---|---|---|---|
| 实时协作能力 | 高 | 中低 | 高 |
| 一致性 | 高 | 中 | 低 |
| 维护成本 | 中 | 低 | 高 |
| 多端扩展 | 高 | 中 | 中 |
| 适配产品叙事 | 高 | 中低 | 中 |

### 10.2 最终选择与理由

选择 A,因为 Chat 是管理者最常驻的主入口,产品叙事要求它既实时、又一致、又可跨端。B 无法承接“过程始终可观察”的实时协作感；C 虽灵活,但会迅速产生端间体验漂移,削弱产品信任感。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 重连 | 事件流断开后自动续传 |
| 降级 | 下游某域查询失败时局部 skeleton / 只读回退 |
| 隔离 | timeline、gate、preview、shell 之间状态隔离 |
| 恢复 | 页面刷新后恢复最近会话和必要上下文 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | 会话进入、Gate 提交、流重连、预览失败 |
| 指标 | 首屏耗时、Turn 可见延迟、审批完成率、重连次数 |
| trace | 前端动作 → SDK → 后端事件链可关联 |
| 健康检查 | 关注流连接状态与 SDK error budget |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| 认证 | 全部通过统一 SDK auth |
| 授权 | conversation/gate/member lens 权限显式控制 |
| 审计 | 审批与关键视图切换进入 observability |
| 隐私 | 无权限对象不泄漏正文与敏感元数据 |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | server endpoint、feature toggles、shell capabilities 外部化 |
| 环境隔离 | desktop/web/mobile/staging/prod 可配置不同接入点 |
| 动态更新 | 通知策略、实验性 UI 能力可灰度 |
| 配置五要素 | type / default / source / scope / constraints 明确 |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| 首屏主会话进入 | < 2s | RUM / Web Vitals | 主入口体验 |
| 新 Turn 可见 | < 500ms | E2E / benchmark | conversation 流目标 |
| GateCard 提交反馈 | 用户可感知即时反馈 | E2E | 审批主路径 |
| 大群可用性 | 500+ 参与者可浏览 | 压测 / 手测 | README 开放问题 |

**端到端延迟分解**(新 Turn 可见 < 500ms):

```text
总预算 = 500ms

  ┌ 后端生成/推送         ≤ 上游 conversation 预算
  ├ SDK 接收与分发         ≤ 小量固定开销
  ├ 本地状态更新           ≤ 小量固定开销
  └ UI 渲染提交            ≤ 小量固定开销
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| 多端同步策略未定 | 影响 desktop/web/mobile 一致性 | P1 |
| 员工登录暴露范围未定 | 影响权限模型与 UX | P1 |
| 大群与长流优化策略未细化 | 影响规模化体验 | P1 |
| 移动端是否首批全功能未定 | 影响壳层范围 | P2 |

### 12.2 触发条件(可量化)

| 指标 | 阈值 | 动作 |
|---|---|---|
| 新 Turn 可见 > 500ms | 持续 1 周 | 优化流分发或渲染批处理 |
| 大群滚动卡顿投诉增多 | > 阈值 | 引入更强虚拟化 / 分段加载 |
| GateCard 完成率下降 | > 阈值 | 复盘审批信息层级与交互复杂度 |
| 多端行为偏差回归失败 | 连续 2 次 | 收紧 shared core 边界 |

### 12.3 演进步骤

```text
阶段 1: 私聊 / 群聊 / GateCard 主路径跑通
   └─ 可停止点:管理者能从私聊发起到群聊审批

阶段 2: 员工登录 / Artifact 预览 / Inbox 稳定
   └─ 可停止点:协作闭环可见性足够

阶段 3: 多端增强 / 大群优化 / 有限离线能力
   └─ 可停止点:端侧产品型样板成熟
```

### 12.4 目标架构

Chat 的目标架构不是“聊天界面”,而是 **Quantalithos 的协作操作系统前台**:用户在这里发起、观察、审批、追问、登录员工、预览产物。未来再增加功能,也必须围绕“管理者视角 + 对话载体 + 可观察协作”三条主线收敛,不能退化成杂糅的开发者工具箱。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 长消息流信息噪音过高 | 中 | 高 | timeline 分层、折叠、过滤 |
| GateCard 过重影响审批效率 | 中 | 高 | 六段式分层、默认摘要 |
| 多端状态不一致 | 中 | 中 | shared core + 续传语义 |
| 权限边界显示错误 | 低 | 极高 | SDK contract tests + UI guards |

### 13.2 边缘风险

- 500+ 参与者大群导致 timeline 和参与者侧栏退化严重
- AG-UI 与 Conversation 事件映射漂移,造成前端状态机异常
- 移动端强行承载复杂管理路径,稀释 Chat 的主入口体验

### 13.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 多端同步是否做云端会话状态 | 批次 6 内 | Chat + SDK |
| 移动端首批范围(审批/阅读 vs 全功能) | 批次 6 内 | Chat + Product |
| 员工登录默认显示哪些运行细节 | 批次 6 内 | Chat + Runtime + Governance |
| 大群性能优化的首批阈值与降级策略 | 批次 6 内 | Chat + SRE |

## 14. 上线策略

### 14.1 灰度方案

```text
阶段 1: web 端最小主路径(私聊 / 群聊 / GateCard)
阶段 2: desktop 壳层接入与通知整合
阶段 3: 员工登录 / Artifact 预览 / Inbox 打开
阶段 4: 视情况扩到移动端审批场景
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| 主会话无法接收新 Turn | S 级 | 回滚事件流相关版本或切只读重连模式 |
| GateCard 提交失败率异常 | A 级 | 回退审批交互改动,保留只读卡片 |
| 员工登录泄露权限外信息 | S 级 | 立即关闭该功能入口 |
| 大群性能明显不可用 | B 级 | 暂停相关增强能力,启用简化渲染 |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| 新 Turn 可见延迟 | > 500ms | major |
| 首屏主会话进入 | > 2s | warning |
| GateCard 提交失败率 | > 阈值 | major |
| 流重连频率 | > 阈值 | warning |
| 权限拒绝异常 | > 阈值 | security |

## 2. 业务背景与驱动力

> 校准来源：
> - `design-calibration/01_arch_step_01_requirements_baseline.md`
> - `design-calibration/01_arch_step_02_arch_goals_constraints.md`
>
> 延伸阅读：建议阅读上述中间产物的“架构需求基线”“架构目标表”和“当前阶段可接受取舍表”小节，了解本章目标如何从需求边界收敛。

### 2.1 业务背景

Quantalithos 的正式协作能力分布在对话、身份、工作、治理、制品、工作区、成员和运行等多个 owner。`L5-chat` 是这些能力面向协作者、项目负责人、审批者和旁观者的客户端入口：它需要让用户在被授权的语境中阅读变化、理解安全摘要、发起受控意图并知道结果是否已由 owner 确认。

Chat 的架构价值不是复制这些领域，而是把安全的 owner material 组织成连续的客户端体验，并在断线、撤销、重启、跨端和部分不可用时保持可解释。没有稳定的客户端边界，页面、缓存、optimistic 状态或平台能力很容易被误认为业务 truth；没有正式 SDK seam，客户端会绕过授权和版本治理；没有结果门控，按钮点击和 transport ACK 会被错误呈现为业务成功。

### 2.2 结构性驱动力

| 驱动力 | 架构含义 |
|---|---|
| 多 owner 协作入口 | 客户端必须能组合 safe view/ref/summary，同时保留来源、visibility、freshness 和不可用原因。 |
| 实时变化与恢复 | 客户端必须承接正式 change/resume，并显式表达 duplicate、乱序、gap、stale、revoked 和 unknown。 |
| 受控治理与其他副作用 | intent、attempt、receipt/result、confirmed/rejected 和 unknown 必须分层，不能由 UI 自行确认。 |
| Desktop-first 跨平台体验 | 共享语义 core 与平台 shell 分离；平台差异不能改变权限、结果或 owner 生命周期。 |
| 最小披露和设备持有面 | 正文、credential、secret、raw log 和未脱敏 payload 不进入客户端不必要的持有、缓存、通知或诊断生命周期。 |
| 未闭合上游合同 | 需要安全的 `blocked`、`read-only`、`stale`、`unavailable`、`deferred`、`unknown` 和 `needs-action` 姿态，不以私有协议填补缺口。 |

### 2.3 架构目标

| ID | 架构目标 | 说明 |
|---|---|---|
| `AG-CHAT-001` | 承载共享客户端产品 core | 让语境进入、正式显化、受控意图、变化和恢复在共享语义下成立。 |
| `AG-CHAT-002` | 守住 owner truth 与客户端局部状态分离 | Chat 只持有 route、selection、draft、attempt、recovery、展示偏好和状态姿态。 |
| `AG-CHAT-003` | 让正式 safe material 可组合、可回链、可降级 | 多 owner 内容可以在同一入口显化，但不被组合成第二真相。 |
| `AG-CHAT-004` | 支撑受控意图与结果分层 | 页面动作、local intent、receipt/result、confirmed/rejected 和 unknown 各有独立语义位置。 |
| `AG-CHAT-005` | 支撑正式变化与恢复连续性 | 变化、重连、缺口、过期、撤销、断线和重启均可解释。 |
| `AG-CHAT-006` | 让跨端 shell 不改变业务语义 | Desktop、Web 和 Mobile shell 只提供宿主能力和等价表达。 |
| `AG-CHAT-007` | 守住最小披露与本地安全边界 | 预览、缓存、通知、深链、诊断和持久化只接受获准 safe material。 |
| `AG-CHAT-008` | 允许未闭合合同安全降级 | 上游能力缺失时保持真实的 blocked / deferred / unknown，不伪造 ready。 |
| `AG-CHAT-009` | 让客户端变化可观测但不越权 | 低敏诊断支持定位连接/缓存/恢复问题，但不升级为 Observability truth。 |
| `AG-CHAT-010` | 统一项目详情与分层流程体验 | 项目详情组织概览、项目进度、关联群聊、工作项和证据；整体流程、阶段子流程和节点详情保持当前项目及来源语境。 |
| `AG-CHAT-011` | 支撑独立成员范围与双向入口 | 关联群聊可往返项目；公司目录、项目成员、群聊成员各自依正式可见性展示，不能相互推导。 |

### 3.1 不可变约束

| ID | 约束 | 架构影响 |
|---|---|---|
| `IC-CHAT-001` | 不拥有 Conversation、Turn、Participant、Project、Member、Gate/Decision、Artifact、Workspace、Runtime 或 Observability backend truth。 | 对象生命周期、授权、状态、正文和审计归正式 owner。 |
| `IC-CHAT-002` | 业务 query、command、formal change、resume 和 ref 只能经 `L0-sdk`。 | 禁止页面直连私有 API、内部 bus、共享数据库或 owner package。 |
| `IC-CHAT-003` | 不把 Chat-local 状态升级为业务结果。 | route、selection、draft、optimistic、cache、按钮、toast、通知和 transport ACK 都不构成 confirmed。 |
| `IC-CHAT-004` | 不把 owner safe material 组合为跨域真相。 | view composer 只能组合展示，不推断权限、完成、生命周期、审批或运行结果。 |
| `IC-CHAT-005` | 不以缓存、深链、空列表、对象名称或错误差异推断可见性/存在性。 | actor、scope、visibility 无法验证时必须 fail-closed。 |
| `IC-CHAT-006` | 正式变化只能由 SDK 提供。 | reducer 不猜 topic、offset、墙上时间顺序或 broker delivery。 |
| `IC-CHAT-007` | unknown 不得盲重放可能产生副作用的命令。 | 进入查询、探测、等待或用户决策路径。 |
| `IC-CHAT-008` | 缓存、离线展示和重启恢复不得延长授权或确认业务完成。 | 快照保留版本/visibility/freshness；撤销/过期时清理或裁剪。 |
| `IC-CHAT-009` | 外部正文、credential、token、secret、raw log、provider/tool/runtime/bridge body 和未脱敏 payload 不得进入 Chat 持有面。 | 渲染、缓存、错误、诊断、导出、通知和深链均适用。 |
| `IC-CHAT-010` | 平台 shell 不拥有业务权限、结果或生命周期。 | 宿主 API 返回不等于业务成功。 |
| `IC-CHAT-011` | 运行期/事件协作依赖不写成源码依赖。 | 只有正式共享契约可成为 compile candidate；owner 能力经 SDK seam 消费。 |
| `IC-CHAT-012` | 未闭合合同不得表述为 ready、integrated、verified 或 accepted。 | 正文和后续实施边界必须保持 pending/blocked/deferred/unknown。 |
| `IC-CHAT-013` | 流程拓扑、Activity、Token/Gateway、并行汇聚属于 Process；Gate/Decision 属于 Governance。 | BPMN 只读显化；不根据 WorkItem、Runtime 或分支颜色计算完成与批准。 |
| `IC-CHAT-014` | 一群聊最多绑定一项目、一项目可关联多个群聊是目标约束，正式关系由 owner 提供。 | Chat 只读绑定 projection；不保存关系 truth，不以路由或成员集合验证关系。 |
| `IC-CHAT-015` | 公司目录、ProjectMember、Conversation Participant 和运行在场不是同一集合。 | 逐来源授权、清理与分页；人类/AI 公司目录覆盖仍待 provider 合同，不从身份摘要推断访问权。 |

### 3.2 当前阶段可接受取舍

| 取舍 | 当前口径 |
|---|---|
| V1 平台范围 | Desktop-first；Web 保留扩展面，Mobile 不作为 V1 前置。 |
| Desktop shell | Tauri 是候选承载，不是已绑定实现；窗口模型和 native seam 后置。 |
| Shared UI/core | React/TypeScript 是候选方向；架构层先固定共享语义与平台隔离。 |
| Mobile | 暂保留 Capacitor 类共享 UI 复用候选；移动特有能力不进入 V1 主线。 |
| Exact SDK/owner surface | 先固定 adapter 角色、输入输出类别和降级姿态；方法名、DTO、协议和 schema 等待正式合同。 |
| 离线能力 | 允许受限阅读缓存、草稿和恢复提示；不允许离线审批成功、离线业务写入或完全离线工作流。 |
| 搜索、通知、富文本、附件 | 外围增强；只有正式 owner/平台合同具备时启用。 |
| 精确性能、可用率和兼容矩阵 | 只保留行为级安全、有界恢复、fail-closed 和等价可访问性口径，不写无 authority 数字。 |
| 低敏诊断 | 保留 client-side intent、错误类别和安全 correlation；exact handoff envelope 后置。 |

### 3.3 架构非目标

Chat 不设计各 owner 的 truth、通用 SDK、认证/传输/重试/错误协议、内部 bus、Runtime 推理、Tools 执行、Capability/Sandbox、Bridges 外部平台映射、Workspace projection truth、完整离线业务系统、离线审批、跨域统一授权中心或 Observability backend。本文也不定义 API path、DTO、事件 schema、topic、offset、代码目录、数据库、配置键、测试步骤、运行证据或部署脚本。

### 3.4 未闭合前提

`CHAT-UP-001~007`、`WS-UP-001~008`、`CHAT-NF-Q-001~005`、`CHAT-AC-Q-001~004` 和 `OPEN-CHAT-001~015` 继续保持 pending / blocked / deferred / stale / unavailable / unknown / needs-action 等真实姿态。其中 OPEN-CHAT-013～015 覆盖绑定/撤销、流程层级/版本与成员目录；新增 Process authority 与全公司目录 provider 缺口在 §15 继续承接。它们可以阻塞正向接口、平台扩展、数值化质量和诊断闭环，但不授权 Chat 用私有协议、缓存或推断填补缺口。

### 4.1 Chat 负责的职责

| 职责 | 架构含义 |
|---|---|
| 跨平台协作客户端产品体验承载 | 把正式协作能力组织成用户可理解、可操作、可恢复的入口和界面。 |
| 安全协作语境进入、路由和导航 | 进入、保持和离开当前客户端语境，但不拥有 scope/visibility truth。 |
| owner safe view/ref/summary 的展示组合 | 组合获准材料并保留来源、可见性、新鲜度和降级姿态。 |
| Turn、Gate、Artifact、成员/项目/运行摘要的安全显化 | 负责表现层语义和可访问路径，不重定义对象生命周期。 |
| 项目详情、整体流程、阶段子流程和节点详情 | 项目进度属于项目详情；只读图形与列表等价显化正式拓扑、来源状态和节点关联引用。 |
| 项目/关联群聊双向入口与公司成员目录 | 保持导航返回语境；逐入口重新验证权限，区分公司目录、项目成员、群聊参与者和运行在场。 |
| draft、selection、focus、展开和 local intent 的局部状态 | 这些是 Chat-owned local truth，不是 owner 业务结果。 |
| 发送与治理意图的受控发起和结果反馈 | 提供 intent、等待、结果、unknown 和重试路径，经 SDK 交给 owner。 |
| formal change/resume 的客户端消费 | 维护页面连续性和 reducer 语义，不拥有 bus delivery 或事件 truth。 |
| 本地展示缓存、重启恢复和离线提示 | 恢复安全展示和草稿，但不延长授权或离线确认业务。 |
| Desktop/Web/Mobile shell 的体验适配 | 适配窗口、输入、通知、存储、深链和辅助技术，不改变业务语义。 |
| 客户端安全、可访问性和低敏诊断入口 | 提供 fail-closed、等价路径和可理解的连接/恢复解释。 |

### 4.2 Chat 明确不负责的职责

| 外部职责 | 正式 owner / 处理边界 |
|---|---|
| Conversation、Turn、Participant truth 与生命周期 | `L1-conversation`；Chat 只消费 safe view/ref/change。 |
| Identity/Member、认证、credential、session 和成员生命周期 | `L1-identity`、`L2-member` 及正式安全边界；Chat 不签发或裁决权限。 |
| Project、ProjectMember、WorkItem、Iteration 与工作进度 truth | `L1-work`；Workspace 只提供正式只读 view，Chat 不据其摘要推断过程完成。 |
| ProcessInstance、Activity、Token/Gateway、阶段和并行汇聚事实 | `L1-process`；Chat 只读正式流程投影，不执行流程，不由 WorkItem/Runtime 状态反推汇聚。 |
| Gate、Decision、Policy、Approval 和治理裁决 | `L1-governance`；GateCard 不生成或确认 Decision。 |
| Artifact、Evidence、Baseline 正文、版本与血缘 | `L1-artifact`；Chat 只消费 body-free ref/preview。 |
| Workspace projection、attention、freshness 和 export truth | `L1-workspace`；Chat 不重建跨域视图。 |
| Runtime run/decision/checkpoint/outcome、Tools、Capability、Sandbox | `L2-runtime` 及相关 owner；Chat 只显示 safe status 或提供受控入口。 |
| 通用 SDK、认证/传输/重试/错误/事件实现 | `L0-sdk`；Chat 只适配正式 surface。 |
| 内部 bus、broker、topic、offset、replay、delivery truth | `L0-bus` / SDK 正式 seam；Chat 不直订。 |
| Observability backend、正式 audit/evidence/report truth | `L4-observability`；Chat 只产生低敏诊断意图或 handoff。 |
| 外部平台映射和外部消息正文 | `L6-bridges`；其未停审设计不进入 Chat 正式输入。 |
| 完整离线业务工作流和离线审批 | 当前只支持展示缓存、草稿、恢复和待处理提示。 |

### 4.3 易混淆职责与解释

| 易混淆关系 | 正确边界 |
|---|---|
| route/context 与 owner scope/visibility | route 是 Chat-local 位置；scope/visibility 必须来自正式 owner。 |
| view model 与 owner truth | view model 只组合安全材料和本地状态，不能成为第二真相。 |
| GateCard 状态与 Governance Decision | 卡片可显示 submitted/pending/unknown；confirmed 依赖正式 owner result。 |
| command attempt 与 owner receipt/result | attempt 只表示客户端意图/尝试，不能代替 receipt/result。 |
| transport ACK 与业务提交 | 网络或 SDK 层确认不代表 owner 已接受或完成。 |
| formal change cursor 与 bus delivery cursor | Chat 只保存 SDK consumer 语境，不拥有 broker offset/delivery truth。 |
| local cache 与当前 owner truth | cache 是带版本/visibility 的受限展示材料，不能放行权限。 |
| Workspace attention 与 Chat notification/read state | Chat 可显示和本地隐藏，不能改变 Workspace attention 或 source read receipt。 |
| shell 登录/窗口状态与认证/Member lifecycle | shell 生命周期不是认证成功，也不是成员状态。 |
| BPMN gateway 与 Governance Gate | 前者是 Process 流控，后者是 Governance 决策；图上邻接不等于状态或权限等价。 |
| 绑定入口与关系 truth | project/conversation ref 只能经正式关系投影建立导航；不能由 URL、群名或成员集合猜测绑定。 |
| 公司目录与项目/群聊成员 | 各集合分别消费、分页和撤销；公司目录入口不授予项目、群聊或 DM 创建权限。 |

### 4.4 边界红线

1. Chat 不直接创建、修改、删除或确认 owner truth；被授权的用户意图可经 SDK 正式 command 提交，结果只能由 owner 确认。
2. Chat 不私自授予 actor、scope、visibility、Gate 操作资格或预览权限。
3. Chat 不把跨 owner view 组合成新的统一业务对象或生命周期结论。
4. Chat 不把 reducer、cache、draft、selection、notification 或 platform state 写回 owner truth。
5. Chat 不绕过 `L0-sdk` 调用 owner 私有 API、内部 bus、共享数据库或 provider/tool/runtime。
6. Chat 不把外部原始正文、secret、credential、raw log、runtime/provider/tool/bridge body 或未脱敏 payload 保存到客户端 store/cache/诊断；正式 safe preview 或获准预览入口不因此被禁止，消费及释放须遵守 owner 披露规则。
7. Chat 不把未知、未送达、局部成功、transport ACK 或缓存命中显示为 confirmed。
8. Chat 不在 unknown 下盲重放可能产生副作用的命令。
9. Chat 不以墙上时间、连接状态、topic 或 offset 推断正式变化顺序。
10. Chat 不让平台 shell 差异改变业务状态、owner 权限或结果语义。
11. Chat 不把低敏客户端诊断升级为 Observability、audit、evidence 或验收结论。
12. Chat 不把 `L6-bridges` 外部平台对象、消息正文或映射状态写成内部 Conversation truth。

### 6.3 上下文职责与边界

| 上下文 | 主要职责 | 明确不承担 |
|---|---|---|
| 协作体验语境 | 组织 owner-safe 材料形成可进入、可理解、可访问的体验；表达 Turn、线程、GateCard、Artifact 引用和安全摘要。 | 不创建 owner truth，不推断权限、完成、顺序或生命周期。 |
| 项目与流程消费主题（归协作体验语境） | 组织项目详情五标签、整体/阶段流程与节点详情，分立显示 Work、Process、Governance、Artifact、Conversation、Runtime 材料。 | 不新增流程领域；不把工作项、运行统计或测试摘要当作过程完成/批准证据。 |
| 受控协作意图 | 表达草稿、选择、发送/重试/治理动作的 local intent/attempt 和结果姿态。 | 不执行 owner command，不生成 Decision，不以 ACK 或 optimistic 状态确认业务。 |
| 安全语境与导航 | 组织进入、保持、切换、撤销、登出清理和导航位置。 | 不认证、签发 credential、裁决 Policy 或从深链推断存在性。 |
| 变化与恢复连续性 | 解释 formal change/resume、gap、重复、乱序、重连、重查和 unknown。 | 不直订 bus，不拥有 delivery/offset，不修复 owner truth。 |
| 平台体验与可访问性 | 适配宿主能力、通知、存储、深链、辅助技术和等价路径。 | 不定义业务状态、授权、owner 结果或平台专属业务生命周期。 |
| owner-safe 材料镜像 | 消费并保留最小 safe view/ref/summary/preview/result/change。 | 不保存正文，不合并跨域生命周期，不自行决定可见性。 |
| 本地展示与恢复投影 | 支持重绘、离线只读、草稿恢复、重启和局部重连。 | 不延长授权、不确认离线成功、不替代正式 change/resume。 |

### 6.4 本地投影与统一语言边界

本地影子结构必须保留来源、visibility、版本/水位和 freshness；来源不明、scope 改变、撤销、过期、冲突或恢复失败时只能进入 `stale`、`partial`、`restricted`、`unavailable`、`blocked` 或 `unknown`。`confirmed` 只表示正式 owner result/change 已满足结果门控；`unknown` 表示无法安全判断副作用是否成立，不能被当作失败、成功或自动重放许可。`GateCard` 是治理语境的客户端显化和受控入口；`Artifact 引用/预览` 是 body-free safe ref、摘要或正式 preview 结果。

`整体流程/阶段子流程` 是正式 Process 材料的两层只读表现；`并行网关` 与 `Governance Gate` 不同。`节点详情` 组合各 owner 的获准引用与摘要，不建立节点的跨域业务实体。`公司目录`、`ProjectMember`、`Conversation Participant` 与 `Member 在场` 均按正式来源分立。

```text
      |                          v                                     |
      |   +-----------------------------------------------+          |
```

图只表达用户设备上的运行承载、入口、处理/消费和承载/依赖关系，不表达协议、调用顺序、源码模块、数据表或部署参数。同步入口和连续性承接职责分开，但 V1 可以同部署；owner truth、内部 bus 和共享数据库不进入本仓容器。

### 7.2 运行单元说明

| 运行单元 | 主要职责 | 运行关系 | 失败姿态 |
|---|---|---|---|
| 客户端同步入口单元 | 承接用户/平台输入，呈现页面、导航、当前 Chat-local 体验和同步边界判断。 | 接收平台宿主能力和 `L0-sdk` 正式边界；与连续性承接协同。 | SDK/owner 能力缺失时入口 blocked/read-only/unavailable。 |
| 客户端连续性承接单元 | 承接 formal change/resume，表达重连、缺口、过期、重启和 unknown。 | 接收 `L0-sdk` 正式变化；依赖本地受限状态承载。 | stale/gap/reconnecting/requery/unknown；不直订 bus、不执行副作用。 |
| 本地受限状态承载 | 保存草稿、选择、恢复上下文和带来源语境的最小安全展示材料。 | 被同步入口和连续性承接使用；不向 owner 反写。 | 失败时内存态或重新查询；不将本地写入当 owner 成功。 |
| `L0-sdk` 客户端实例 | 提供正式业务材料、受控结果、变化和恢复的运行时接入。 | 客户端包可在设备内承载；其协议和通用实现归 SDK 仓；远端 owner 服务独立部署。 | exact capability 未闭合时保持 blocked/deferred。 |
| 平台宿主能力 | 提供窗口、生命周期、输入、通知、存储、深链和辅助技术。 | 承载同步入口和本地状态。 | 能力缺失只显示 unavailable/needs-action。 |
| 低敏诊断对接边界 | 在正式能力存在时承接低敏连接、错误、恢复和关联提示。 | 可选支链，不承载 owner truth。 | sink 不可用时保留本地安全提示，不影响业务。 |

### 7.3 部署关系

V1 的正式部署范围是用户设备上的 Desktop 客户端包。同步入口、连续性承接和本地受限状态在同一产品部署范围内协同运行；同步入口与连续性承接的职责和状态源必须分开，即使共享宿主生命周期或同一安装包。Chat 不需要独立服务端业务容器，也不把 owner truth 复制成 Chat 服务。

Web 和 Mobile 后续可以分别拥有平台 shell 与打包边界，但沿用同一同步入口、连续性承接和本地受限状态的语义分工。当前它们只是候选承载面，不产生兼容矩阵、后台执行能力或正式 readiness 结论。平台差异用 `unavailable`、`needs-action`、受限恢复或只读姿态表达。

`L0-sdk` 客户端包是外部维护的应用依赖，可随客户端分发；各正式 owner/API 与可选诊断后端在 Chat 设备部署之外。Chat 不部署服务端业务 worker、内部 bus consumer、共享缓存、owner projection 服务、BPMN 执行引擎、外部平台桥接或诊断后端。Desktop renderer/native 的精确 SDK transport、认证材料提供与受控存储位置须待正式能力和安全合同，不在此发明 IPC 或跨进程权限面。

### 7.4 通信与部署降级

| 运行关系 | 类型 | 失败时的 Chat 姿态 |
|---|---|---|
| 平台宿主能力 → 同步入口 | 入口 | 页面路径保持，局部 unavailable/needs-action。 |
| `L0-sdk` → 同步入口 | 入口 | 对应入口 blocked/read-only/unavailable；不 fallback。 |
| `L0-sdk` → 连续性承接 | 入口 | stale/gap/unknown/requery；不猜顺序或直订 bus。 |
| 同步入口 ↔ 连续性承接 | 客户端处理/消费 | 局部隔离受影响语境；不把连接恢复显示为业务确认。 |
| 运行单元 → 本地受限状态 | 承载/依赖 | 读写失败时最小内存态或恢复受限；不写 owner。 |
| 运行承载 → 低敏诊断 | 可选入口 | sink 失败不影响业务结果、授权或恢复上限。 |

## 8. 依赖方向与层间约束

> 校准来源：
> - `design-calibration/01_arch_step_07_dependency_direction.md`
>
> 延伸阅读：建议阅读上述中间产物的“层次划分与依赖方向结论”“本仓依赖裁剪表”“本仓禁止依赖表”和“依赖单元总审计”。

### 8.1 依赖层次

| 依赖角色 | 位置 | 允许依赖方向 |
|---|---|---|
| 核心语义角色：客户端产品语义 | 内层 | 只依赖 Chat-local 语义契约和需求边界。 |
| 编排 / 承接角色：客户端状态与意图承接 | 中间层 | 依赖核心语义，承接 safe material、formal result/change 和本地状态。 |
| 外部接缝角色：SDK / 平台 / 诊断 | 外层 | 依赖编排/承接定义的本地边界，接入正式外部能力。 |
| 技术承载角色：本地受限状态和宿主 | 外层 | 依赖编排/承接定义的承载语义，只提供存储和宿主能力。 |

```text
      +-----------------------------------------------------------+
      |                  L5-chat 依赖边界                         |
      |  外部接缝角色：SDK / 平台 / 诊断正式接缝                  |
      |                  | 允许依赖                              |
      |                  v                                        |
      |  编排 / 承接角色：客户端状态与意图承接  <--- 技术承载角色 |
      |                  | 允许依赖                              |
      |                  v                                        |
      |  核心语义角色：客户端产品语义                            |
      +-----------------------------------------------------------+
```

箭头只表示允许依赖方向，不表示调用顺序、运行拓扑或协议交互。核心语义不直接依赖 SDK、owner、平台、存储或诊断实现；必要能力通过边界倒置进入。

### 8.2 层间约束

| 层 / 角色 | 允许依赖 | 禁止依赖 |
|---|---|---|
| 核心语义 | Chat-local 状态语义、来源/visibility/freshness 解释、结果姿态契约 | SDK 方法/DTO、owner 私有 API、内部 bus、平台存储、诊断后端、共享 DB、外部生命周期。 |
| 编排/承接 | 核心语义、正式 safe material/result/change、本地承载边界 | 直接调用 owner、直接订 bus、ACK 当 confirmed、projection 反写 owner。 |
| SDK 接缝 | `L0-sdk` 正式导出与 Chat-local 边界；`L0-core` 仅在正式 re-export 或已核对共享 compile surface 成立时使用 | owner 私有 package/API、bus broker、共享 DB、页面直接写入、任意复制或解析 owner DTO。 |
| 流程 renderer / 图形载体 | 共享只读展示模型、局部布局/缩放/焦点边界 | 作为 BPMN 执行/建模引擎、从库模拟 token 推完成、编辑拓扑后反写 owner。 |
| 平台接缝 | 宿主能力和输入/通知/存储/深链/AT 边界 | 平台直接改业务状态、直接调用 owner、凭通知确认结果。 |
| 诊断接缝 | 允许的低敏分类、关联 ref 和 handoff 语义 | raw body、credential、raw log、audit/evidence 写入和业务结果依赖。 |
| 本地受限承载 | 编排定义的持久化和清理语义、平台存储能力 | owner truth、共享缓存、远端 DB、权限表。 |

### 8.3 跨仓依赖裁剪

| 关联边 | 当前处理 |
|---|---|
| `L0-core` | 仅作为正式共享安全/错误/引用契约的编译期候选。 |
| `L0-sdk` | 唯一编译期 + 运行期业务接缝；exact surface 保持 blocker。 |
| L1 Conversation/Identity/Work/Process/Governance/Artifact/Workspace | 仅通过 SDK 运行期消费 safe view/ref/summary/preview/result/change；Process 投影和目录 provider 的 exact 能力仍待确认。 |
| L2 Member/Runtime | 仅通过 SDK 消费安全摘要、状态和 gap；不执行容器或 Runtime。 |
| L4 Observability | 仅诊断支链，低敏 handoff 未闭合时 blocked/deferred。 |
| `L0-bus` | 直接事件边裁剪；formal change/resume 只通过 SDK。 |
| L3 capability/tooling、L4 sandbox、L4 archive、L6 bridges | 不进入 Chat 当前正式主链。 |

### 8.4 禁止依赖红线

Chat 不得直连 owner 私有 API、内部 bus、共享数据库、外部平台正文、Runtime/Tools/Sandbox 执行面或 Observability raw backend；核心语义不得反向依赖 SDK/平台/存储具体实现；本地投影不得反写 owner truth。运行期和事件协作关系不得被改写为 package dependency。

项目详情、群聊关联和成员目录使用同一接入隔离原则，但每个消费面独立验证正式 capability。流程图形库只属于可替换表现层依赖；客户端 store/reducer 的业务状态来源不能绑定库内模拟器、可编辑模型或私有图索引。公司目录 provider 的归属、权限与人类/AI 覆盖未确认时保持 blocked，不自行建立员工服务。

## 9. 数据所有权与一致性策略

> 校准来源：
> - `design-calibration/01_arch_step_08_data_ownership_consistency.md`
>
> 延伸阅读：建议阅读上述中间产物的“数据归属表”“一致性策略表”“逐架构单元数据所有权停审”和“跨数据边界审计”。

### 9.1 Chat-owned truth

Chat-owned truth 只包含客户端局部产品事实：route/context、selection/focus、draft、local intent/attempt、局部展示姿态、recovery context、可访问性/平台体验状态和本地安全清理状态。它们只能影响 Chat-local 页面和恢复，不能被解释为任何 owner 的业务状态。

项目详情标签、整体/阶段/节点选择、画布缩放/平移、展开项和返回群聊来源也属于局部状态。它们不证明正式绑定、阶段归属、节点关系、成员资格或可操作性；重启/跨端恢复前需重新验证目标。

### 9.2 外部 owner truth 与本地消费材料

Conversation、Turn、Participant、scope/visibility/change identity；GlobalMember/actor/identity lifecycle；Project、ProjectMember、WorkItem/Iteration；Gate、Decision、Policy、Approval；Artifact、Evidence、Baseline、版本与血缘；Workspace projection、attention、freshness、export；Member presence/interaction；Runtime run/decision/checkpoint/outcome/handoff；Observability audit/evidence/report/backend 均由对应 owner 拥有。Chat 只消费经 SDK 提供的 safe view/ref/summary/preview/receipt/result/change。

本地展示缓存、view model、恢复快照、source/version/visibility/freshness metadata、SDK consumer resume metadata 和页面降级姿态属于快照/投影；Conversation/Turn、Gate/Decision、Artifact、Workspace、Project/Member/Runtime 和诊断 correlation/ref 属于引用关系数据。它们支持回链、预览、恢复和解释，但不改变正式 owner 的真相、权限或生命周期。

ProcessInstance、Activity、Token/Gateway 与过程推进/汇聚归 L1-process；整体/阶段流程只读投影、节点关联和项目/群聊绑定属于正式外部材料，不是 Chat 关系 truth。公司目录按正式 provider 提供 safe summary，项目成员和群聊参与者各由 owner 返回；公司人员覆盖不从 GlobalMember 名称或 Runtime 在场推定。

### 9.3 数据归属表

| 数据项 | 归属类别 | 处理口径 |
|---|---|---|
| route/context、入口来源、回退位置 | Chat-owned truth | 只说明产品位置，不等于 owner scope 或对象存在性。 |
| selection/focus、展开/折叠、局部阅读位置 | Chat-owned truth | 不改写 Conversation read receipt、Workspace attention 或 owner state。 |
| 未提交 draft、回复目标、本地编辑状态 | Chat-owned truth | draft 不等于 Turn、Decision、Artifact 或审批提交。 |
| local intent/attempt、客户端结果姿态 | Chat-owned truth | confirmed 只能由正式 receipt/result/change 支持。 |
| recovery context、重连/缺口/恢复阶段姿态 | Chat-owned truth | 不等于 owner repair、bus replay 或副作用完成。 |
| 可访问性、平台能力和本地清理状态 | Chat-owned truth | 不改变业务权限、owner result 或跨端语义。 |
| owner safe view/summary/preview/result/change | 快照 / 投影 | 最小消费形态，必须保留来源、visibility、版本/水位和 freshness。 |
| view model、展示缓存、恢复快照 | 快照 / 投影 | 不能作为授权、当前 fresh truth 或业务提交凭证。 |
| SDK consumer resume/gap metadata | 快照 / 投影 | 不等于 owner change cursor、bus offset、版本或 replay truth。 |
| Conversation/Turn/Gate/Decision/Artifact/Workspace/Runtime refs | 引用关系 | 只用于回链、预览或受控入口；不带正文、权限或生命周期。 |
| 低敏 correlation/ref、错误类别 | 引用关系 | 仅用于支持/诊断交接，不是 audit/evidence。 |
| 外部正文、credential/token/secret、raw log、provider/tool/runtime/bridge body | 明确不拥有 | 不进入持有、缓存、诊断、导出、通知或 handoff 生命周期。 |

### 9.4 一致性层次

- `安全强约束`：scope/visibility/actor 与展示/操作资格必须同向；无法验证即收紧。
- `客户端局部一致`：route、selection、draft、focus、local intent/attempt 和 recovery context 在 Chat-local 语境内可解释。
- `owner 结果门控一致`：confirmed/rejected/failed 只能根据正式 receipt/result/change 映射。
- `来源标记的最终一致`：safe view、summary、preview、change、cache 和页面展示允许暂时落后，但必须标注 freshness/partial/stale/unknown，并可经正式 SDK requery/resume 收敛。
- `尽力而为诊断一致`：低敏诊断可延迟或丢失，不影响业务、授权、清理和恢复上限。

不一致不得被压缩成单一成功/失败；根据来源和影响使用 `restricted`、`redacted`、`stale`、`partial`、`unavailable`、`blocked`、`pending`、`unknown`、`reconnecting` 或 `needs-action`。未有正式结果前不显示 confirmed，无法验证 visibility 时不继续展示受保护内容。

### 9.5 关键一致性策略

| 场景 | 一致性口径 | 失败处理 |
|---|---|---|
| actor/scope/visibility 与可见/可操作姿态 | 安全强约束 | restricted/blocked，遮蔽或清理投影。 |
| route/selection/focus/draft | Chat-local 一致 | 保留最小安全状态，提示恢复受限。 |
| draft/attempt 与正式结果 | 结果门控 | submitted/pending/unknown；查询或决定前不盲重放。 |
| safe view 与页面展示 | 来源标记最终一致 | stale/partial/unavailable，不从别的 owner 摘要补齐。 |
| formal change/resume 与缓存 | 来源标记最终一致 | duplicate/乱序/gap/expired/revoked 时暂停或重查。 |
| receipt/result/change 与 confirmed | 结果门控 | 无正式结果时 pending/unknown/read-only。 |
| Artifact ref/preview | 来源标记最终一致 | preview unavailable/visibility unknown 时只显示 ref 或原因。 |
| Workspace view/export | 来源标记最终一致 | stale/partial/blocked；不重建 attention/freshness/export。 |
| logout/revoke/scope change | 安全强约束 | 收紧/清理受影响材料，不因离线/重启继续展示。 |
| 多端/重启恢复 | 设备范围局部一致；正式同步时最终一致 | 无正式同步能力则 unavailable/needs-action。 |
| 低敏诊断 | 尽力而为 | sink 失败只保留本地安全提示。 |
| 整体流程、阶段、分支与 Gateway | 来源标记最终一致，过程结论由 Process 提供 | 缺拓扑/状态/关系合同即 blocked；gap 重查，不按 WorkItem 或 Runtime 补图。 |
| Process 汇聚与 Governance Gate | 分立正式来源，无跨 owner 原子快照保证 | 分别标记版本/新鲜度；分支全部完成的视觉表现不等于汇聚确认或批准。 |
| 项目/群聊绑定与节点关联 | 正式关系投影最终一致；入口访问为安全强约束 | 撤销/解除后失效相关入口和返回选择，重新查询关系；不能解析 ref 或沿缓存访问。 |
| 公司/项目/群聊成员集合 | 每个正式来源独立分页、状态和撤销 | 不能用一集合补另一集合；未知访问权时 restricted，不泄露不可见对象。 |

各来源版本/cursor 不构成可比较的全局水位。安全强约束表示访问与结果门控必须满足，不表示 Chat 对 owner 执行跨域事务。只在 owner 允许离线保留展示且授权语境可验证时使用 stale 缓存；否则遮蔽/清理。正式 safe preview 的临时消费不构成原始正文持久化许可。

## 10. 关键交互与通信方式

> 校准来源：
> - `design-calibration/01_arch_step_09_key_interactions_communication.md`
>
> 延伸阅读：建议阅读上述中间产物的“关键交互场景表”“通信方式判断表”“按架构单元的交互方式停审”和“失败降级与挂起结论”。

### 10.1 通信类别

| 通信类别 | 适用场景 | 正式边界 | 失败姿态 |
|---|---|---|---|
| 同步请求 / 响应 | 安全语境判断、safe view 读取、本地动作和正式意图接收 | `L0-sdk` query/command/ref 边界，或 Chat-local 状态承载 | restricted/blocked/stale/pending/failed/unknown；不把接收判断当最终业务结果。 |
| 异步事件 / 回调 | owner formal change、receipt/result、撤销、可见性/版本变化 | `L0-sdk` formal change/resume/result 边界 | stale/gap/reconnecting/unknown；不直订内部 bus。 |
| 后台任务 / 延后承接 | 缺口恢复、unknown probe、重查、重启恢复、过期清理和非关键诊断 | SDK 正式 probe/requery/resume、平台/本地承载和可选 handoff | unavailable/needs-action/blocked；不盲重放副作用。 |

同步只表示当前边界判断或意图接收，不表示 owner 生命周期已在同一交互内完成；异步只传播正式事实和结果；后台只承担连续性收敛。

### 10.2 关键交互场景

| 场景 | 交互目的 | 通信选择 | 边界说明 |
|---|---|---|---|
| 安全语境进入与切换 | 判断 actor/scope/visibility 下入口是否可见、可读或可操作 | 同步 | Chat 不裁决权限；无法验证时 fail-closed。 |
| 当前协作 safe view 读取 | 获取对话、项目、成员、治理、Artifact、Workspace 或 Runtime 材料 | 同步 | 消费边界，不转移 owner truth。 |
| 本地草稿与选择 | 维护未提交草稿、回复目标、选择和焦点 | Chat-local 同步 | 不穿透 owner 或远端事件面。 |
| 普通发送意图 | 表达发送意图并得到接收、等待、拒绝或失败姿态 | 同步接收 + 异步结果 | 意图与 Turn 正式写入分离。 |
| 受控治理意图 | 在正式授权语境下发起 Gate/Decision 相关动作 | 同步入口 + 异步结果 | GateCard 不生成 Decision。 |
| owner 状态变化 | 传播 Turn、Decision、Artifact、Workspace、Member 或 Runtime 正式变化 | 异步 | 事实传播，不是同步轮询闭环。 |
| receipt/result 回送 | 更新正式接收、确认、拒绝或失败姿态 | 异步 / 受控查询 | 页面刷新和 ACK 不能替代正式结果。 |
| 缺口与 cursor/resume | 恢复缺失、过期或撤销后的页面连续性 | 后台 | 不暴露 broker offset/replay。 |
| unknown 副作用探测 | 判断尝试是否成立，避免重复副作用 | 后台 | 探测不是自动重放。 |
| 重启/断线本地恢复 | 恢复草稿、选择、最小安全展示和下一步提示 | 后台 | 缓存不是当前 truth。 |
| Artifact safe preview | 获取安全预览、摘要或不可预览原因 | 同步，后续可异步更新 | 正文和版本链归 Artifact。 |
| Workspace safe view/export | 显示正式跨项目视图 | 同步 + 异步变化 | 不重建 projection/attention。 |
| 项目详情与整体/阶段/节点下钻 | 获取分层流程与获准关联材料 | 同步 query + Chat-local 选择 | 只读 Process projection；图形点击不推进 Activity，节点关联由正式 ref 提供。 |
| 项目与群聊往返 | 读取绑定/关联群聊并验证目标访问 | 同步 query + 本地导航 | 正式关系与每个 Conversation 的 visibility 独立；撤销后阻断旧入口。 |
| 公司目录、成员详情与 DM 入口 | 分别获取目录摘要和正式可用对话入口 | 同步 query + 本地选择/受控意图 | 目录、ProjectMember、Participant、Member 在场分立；目录可见不代表可创建 DM。 |
| 低敏诊断交接 | 交接连接、缓存、恢复和错误类别 | 异步 / 后台 | 诊断不参与业务结果和授权。 |

### 10.3 关键状态与失败规则

Chat 的客户端结果姿态至少区分 `draft`、`submitted`、`pending`、`confirmed`、`rejected`、`failed` 和 `unknown`；变化/恢复姿态至少区分 `fresh`、`stale`、`gap`、`reconnecting`、`restricted`、`unavailable`、`blocked` 和 `needs-action`。`confirmed` 只有在正式 owner receipt/result/change 满足门控后出现；`unknown` 必须进入查询、等待或用户决定，不能因网络恢复、缓存命中、按钮点击、toast、通知或 transport ACK 自动晋级或重放。

`optimistic` 是 local intent 的可撤销表现，不是 Process/Work/Governance 已提交事实。receipt 只有在 owner 正式合同明确表示业务确认时才可支持 confirmed，接收/排队 receipt 不够。重试与幂等结果读取使用 SDK 已确认能力；缺失时保持 waiting/needs-action。adapter/reducer 必须区分当前 actor/scope/project/source 的消费语境，迟到查询、旧订阅变化不得覆盖新语境或复活撤销材料；gap 重查受影响来源，不能以其他 owner 事件替代正式恢复。

### 10.4 交互示意图

```text
       +----------------------+          +----------------------+
       | Chat 用户 / 平台输入 |          | owner 正式变化        |
       +----------+-----------+          +----------+-----------+
                  | 同步请求 / 响应                    | 异步事件 / 回调
                  v                                    v
       +----------+------------------------------------+----------+
       |                 L0-sdk 正式边界                           |
       +----------+----------------------+-------------------------+
                  |                      |
                  | 同步结果 / 意图      | formal change / resume
                  v                      v
       +----------+-----------+  +-------+----------------+
       | Chat 体验与意图     |  | 连续性 / 恢复承接      |
       +----------+-----------+  +-------+----------------+
                  |                      |
                  +----------+-----------+
                             | 后台延后承接
                             v
                  +----------+-----------+
                  | 本地受限状态 / 提示 |
                  +----------------------+
```

图不表示具体协议、事件名、API、时序或实现模块；SDK 是唯一业务边界，本地承接不是 owner 执行者。

- 图中 SDK 路径只适用于外部业务 query/command/change；本地标签、阶段、节点选择、布局和草稿直接在 Chat-local 边界处理。
- 恢复后必须分别重新验证关系、权限与正式来源；连接恢复不代表业务提交或完整历史恢复。

## 11. 关键技术选型

> 校准来源：
> - `design-calibration/01_arch_step_10_key_technology_selection.md`
>
> 延伸阅读：建议阅读上述中间产物的“关键技术机制表”“采用 / 候选 / 不采用边界”“机制与架构单元覆盖”和“Authority 与风险审计”。

### 11.1 正式采用的架构机制

| 机制 | 解决的问题 | 主要代价 / 约束 |
|---|---|---|
| 外部语义隔离与 SDK-only 正式接入 | 防止页面、核心语义或本地状态吸收 owner truth、私有 API 或内部 bus。 | 增加接缝和合同维护；surface 未闭合时能力必须 blocked/deferred。 |
| 来源感知的只读安全投影 | 防止 safe view/ref/summary/preview/result 被误读为正文、权限或生命周期。 | 产生 stale/partial/unavailable，需要解释来源和降级。 |
| 多轴客户端状态与正式结果门控 | 分离 draft、submitted/pending、confirmed/rejected/failed/unknown 及 stale/gap/revoked。 | 状态组合更复杂，后续 view model/组件不得跨轴晋级。 |
| formal change/resume 连续性承接 | 处理重复、乱序、缺口、cursor 失效和连接恢复。 | 需要 gap/unknown/requery/reconnect 语义，受上游合同约束。 |
| 受限本地持久化与安全清理 | 支持 Desktop 重启、草稿恢复和离线展示，同时限制敏感持有面。 | 需要最小化、redaction、过期、logout/revoke 清理和设备范围限制。 |
| 共享客户端语义与平台 shell 分离 | 保持 Desktop/Web/Mobile 的业务状态、授权和结果解释一致。 | 需要宿主能力矩阵、等价可访问路径和跨端兼容审查。 |
| fail-closed 的可见性与能力闸门 | 防止 URL、缓存、空列表、连接状态或平台登录绕过正式语境。 | 上游短暂失败会减少可见性和可操作性，需要可理解的恢复提示。 |
| 共享语义层内建可访问状态表达 | 让键盘、辅助技术、焦点、等待、撤销和恢复状态在各宿主等价可理解。 | 增加语义约束和跨端审查成本；具体 AT 矩阵待确认。 |
| 正式流程材料的只读渲染与等价列表 | 表达整体/阶段拓扑、并行分支/汇聚与独立 Gate，并支持下钻、缩放和焦点。 | 只依正式拓扑/关联来源；图库不执行/编辑流程，受限节点不泄露名称或关联。 |
| 来源与当前语境隔离的 reducer/失效机制 | 防止多源版本混合、迟到响应污染、撤销后复活以及陈旧返回位置越权。 | 需要明确 source/version/visibility 与当前消费语境；缺 SDK 正式 change/resume 时重查或 blocked，不私造事件。 |

这些机制是架构层决定，不等于某个框架、库、运行时产品、传输协议或代码目录。

### 11.2 采用、候选与不采用边界

| 类别 | 当前结论 |
|---|---|
| 正式采用 | SDK-only、外部语义隔离、来源感知只读投影、多轴状态/结果门控、formal change/resume、受限本地持久化、shell 分离、fail-closed、共享可访问语义。 |
| 候选载体 | React/TypeScript shared UI/core、Tauri Desktop、Web shared UI、Capacitor 类 Mobile shell，以及具体状态/存储/窗口/通知/传输库。 |
| 明确不采用 | Chat 直连 owner/bus/共享数据库、raw body cache、离线审批或 unknown 自动重放、Chat 自建跨域聚合/Runtime/Artifact 正文/Observability backend。 |

### 11.3 技术机制与架构单元覆盖

| 架构单元 | 主要机制 | 当前限制 |
|---|---|---|
| 协作体验语境 | safe projection、多轴状态、fail-closed、可访问语义 | owner view/visibility/freshness contract 待确认。 |
| 受控协作意图 | SDK-only、结果门控、多轴状态、formal result/change | Governance/Conversation receipt/idempotency surface 未闭合。 |
| 安全语境与导航 | SDK-only、fail-closed、shell 分离、受限持久化 | 认证/会话/平台能力矩阵待确认。 |
| 变化与恢复连续性 | formal change/resume、显式状态、受限持久化 | cursor/resume exact contract 未闭合。 |
| 平台体验与可访问性 | shell 分离、共享可访问语义、fail-closed | Desktop host 与辅助技术 authority 未完全闭合。 |
| owner-safe 材料镜像 | safe projection、SDK-only、最小披露 | Artifact/Workspace/Observability safe surface 有 blocker。 |
| 本地展示与恢复投影 | 受限持久化、清理、显式恢复状态 | 持久化上限、跨端恢复和诊断 envelope 待确认。 |

### 11.4 载体和 authority 口径

React/TypeScript、Tauri、Capacitor 类 Mobile shell、具体 SDK transport、状态库、持久化引擎、窗口/通知库、测试框架和日志库均未在架构层固化。`CHAT-UP-001~007`、`WS-UP-001~008`、`CHAT-NF-Q-*`、`CHAT-AC-Q-*` 和 `OPEN-CHAT-*` 继续限制 exact surface、性能数字、兼容矩阵、持久化上限和诊断 envelope；不能用历史材料或偏好升级为实现事实。

上述 Desktop-first、React/TypeScript shared UI/core 与 Tauri Desktop 是已认可的 draft 方向，保持候选载体待正式平台/安全兼容校准；不是未讨论，也不是已实现。流程渲染优先采用成熟只读库：正式输入若提供获准 BPMN 文档可评估 bpmn-js viewer，若提供结构化节点/边则评估通用图库。正式输入格式、许可证、兼容性、可访问列表、性能预算及受限材料过滤均须在启用前核对；本轮未完成产品库选型或验证。禁止从 opaque ref、WorkItem、Runtime 日志或原型坐标自行制造流程模型。

## 12. 备选方案与取舍

> 校准来源：
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读：建议阅读上述中间产物的“方案路径比较表”“取舍对照”“自研与开源的边界”和“当前选择结论”。

### 12.1 结构性路径比较

| 路径 | 当前结论 | 取舍理由 |
|---|---|---|
| 直接连接各 owner，自行组合协议 | 不采用 | 绕过 SDK 的授权、redaction、错误、幂等和恢复边界，扩散 owner DTO/协议。 |
| 经 `L0-sdk` 消费 safe view/ref/result/change | 采用 | 集中跨域接入，保持 owner truth 单一来源，允许统一错误、redaction、resume 和 unknown。 |
| 直接暴露 owner truth | 不采用 | 客户端绑定内部生命周期、正文、权限和版本链，容易形成第二真相或反写。 |
| owner-safe 只读材料 + provenance/freshness + 受控入口 | 采用 | 支持跨域显示和预览，同时保持来源、可见性、新鲜度和降级可解释。 |
| 单一平台专用客户端语义 | 不采用 | Web/Mobile 后续需要重写状态、授权、恢复和可访问性，造成语义分叉。 |
| 共享客户端语义 core + 平台 shell | 采用 | 平台差异被限制在宿主层，V1 Desktop-first 仍保留扩展面。 |
| 自研完整渲染、窗口、存储和跨端基础设施 | 不采用 | 把非核心基础设施风险集中到 Chat，延迟验证协作体验。 |
| 共享语义 core + 成熟开源承载载体 | 采用 | 将资源集中到 Chat 语义、状态、SDK 边界和安全体验；具体项目仍待确认。 |
| 全部跨边界状态同步闭环 | 不采用 | 把事实传播、结果回送和恢复压进同步边界，导致高耦合和伪一致。 |
| 同步请求 + 异步事实传播 + 后台恢复/探测 | 采用 | 与 ownership、一致性和失败姿态匹配。 |
| 离线副作用队列和自动重放 | 不采用 | 无法安全判断授权、版本和副作用是否成立，可能重复发送或治理。 |
| 离线展示/草稿/恢复，副作用保持 pending/unknown | 采用 | 支持连续性而不伪造 owner 成功。 |
| 项目与项目进度独立顶层入口 | 不采用 | 多层流程与关联群聊切换会丢失项目语境、返回位置和各来源状态解释。 |
| 同一项目详情中的五标签与流程下钻 | 采用 | 符合冻结原型及 F-CHAT-018/019，保持整体→阶段→节点与项目↔群聊往返；仍须逐目标授权。 |
| 完全自绘流程布局、命中、缩放及焦点基础设施 | 当前不采用 | 有表现自由度，但布局与可访问性维护成本高；正式输入/库限制明确后可重新评估。 |
| 成熟只读图形载体 + Chat 语义与等价列表 | 采用机制，具体库待选 | 复用绘制/布局能力，Chat 保持来源、状态、受控交互与访问边界；禁止执行器/编辑器接管流程。 |

### 12.2 主线选择

采用共享客户端语义 core、平台 shell 适配、`L0-sdk` 唯一业务接入、owner-safe 只读材料、同步/异步/后台混合承接、结果门控和受限离线恢复。V1 以 Desktop-first 验证协作入口、草稿、发送/重试、GateCard、Artifact 引用/预览、变化消费和恢复连续性；Web/Mobile 只保留共享语义扩展面。

Desktop 主线同时覆盖项目详情、整体/阶段流程、并行结构、节点关联、项目/群聊双向入口及公司成员目录。未提供正式 projection/provider 的区域保持 blocked/unavailable，不用原型硬编码图或演示名单充当生产来源。代价是等待合同与提供等价列表，获得的是项目语境连续、来源可回链和不制造第二真相。

### 12.3 自研与开源的边界

Chat 自研产品语义、页面体验、状态模型、reducer、view model、SDK adapter 边界和安全/可访问语义；客户端窗口、渲染宿主、系统通知、分发和平台适配优先采用成熟开源承载路径。该结论不指定具体项目，也不宣称已有实现或 readiness。

流程绘制/布局同样优先复用成熟只读库，Chat 自研页面组合、下钻/返回、局部选择、状态显化和授权过滤；SDK 完成正式 query/auth/command/change/retry/error/trace/redaction 接入。自研展示语义不意味着自研 SDK、BPMN 引擎、Tools 执行或公司人员后端。

### 12.4 主动放弃与延后

主线主动放弃了页面直连、任意 owner DTO、平台独立业务语义、完整客户端基础设施自研、全同步闭环、离线审批和自动重放。换取的是单一真相、可解释降级、可恢复连续性和后续演进空间；具体框架、shell、状态库、存储库、传输协议和精确性能/兼容指标后置。

### 13.1 横切约束表

| 横切关注点 | 约束要求 | 保护目标 |
|---|---|---|
| 安全边界与可访问状态 | 正式 SDK 边界；actor/scope/visibility 无法验证时 fail-closed；restricted/unknown/revoked 等状态以等价可访问语义表达；不保存 forbidden body/secret。 | owner truth、隐私、授权边界和安全降级的可理解性。 |
| 审计与可追溯 | 入口、intent/attempt、receipt/result/change、requery/resume、撤销、清理和降级保留低敏来源、阶段、版本/水位、结果类别或安全 ref。 | 争议复盘、结果解释、治理回链和不确定性边界。 |

| 性能 / 容量 | 禁止全量正文复制、跨域本地聚合、强行同步闭环和无界缓存；允许局部、按需、分页、延后承接。 | 规模和变化压力下核心入口仍可成立。 |
| 配置与变更控制 | 配置不得绕过 SDK-only、fail-closed、结果门控、forbidden body、owner ownership、unknown 安全、重放和留存边界。 | 防止运行配置或平台差异偷偷改写主线。 |

### 14.2 可接受与不可接受债务

| 债务 | 当前判断 | 处理 |
|---|---|---|
| SDK exact surface、owner visibility/cursor/resume、精确 NFR、Web/Mobile/AT 矩阵、诊断 envelope 未闭合 | 可接受但可能阻塞正向能力 | 显式保持 pending/blocked/deferred；合同闭合后更新接缝和承接。 |
| 搜索、复杂附件、增强通知、移动后台和跨设备恢复未进入主线 | 可接受 | 只有正式 owner/平台能力和范围确认后触发。 |

| 本地 projection 反写 owner truth、unknown 自动重放 | 不可接受 | 删除越界路径，保持 unknown 并等待正式 probe/result。 |
| visibility 不明仍展示敏感材料 | 不可接受 | fail-closed、遮蔽/清理并等待正式验证。 |

### 14.3 演进优先顺序

演进先发生在外部接缝和 owner-safe materialization，再发生在变化/恢复连续性和平台 shell；核心语义、owner truth 排除、结果门控、最小披露和不直连边界保持稳定。演进由正式能力、平台范围、规模压力和诊断需求触发，不由版本愿望或排期推动。

F-CHAT-018～021 是当前核心展示目标，其可用性由正式消费合同决定，不因 SDK 缺口被降格为外围增强。完整 BPMN 执行语义、建模编辑、人类/AI 全员目录覆盖和跨设备同步仍不被假定已具备。当前只完成架构设计；02～07 需逐文档授权校准，完成正式 07 后才建立 planned implementation ledger 与 boundary skeleton，不以架构阶段表宣称实现或 readiness。

### 15.3 风险与待确认的状态规则

- 风险有保守降级姿态，不代表上游合同已闭合；`pending/unknown/read-only` 不能升级为 receipt/idempotency 已成立。
- 待确认的 shell、存储引擎、诊断 envelope 和兼容矩阵在缺 authority 时保持挂起，不用偏好写成选型事实。
- `阻塞` 表示继续会要求伪造 owner truth、直连禁止边界、保存 forbidden body 或确认未知副作用；`有条件阻塞` 表示边界级架构可保守推进，但正向能力或实现级设计不能进入下一层；`不阻塞` 表示已有安全降级可隔离影响，但不表示 ready。

### 15.4 当前处理口径

在上述确认形成前，Chat 只保留能力级架构边界，不复制 owner contract、不锁定具体载体、不宣称实现、测试、验收或 readiness。`CHAT-UP-*`、`WS-UP-*`、`CHAT-NF-Q-*`、`CHAT-AC-Q-*` 和 `OPEN-CHAT-*` 继续作为外部 blocker 或待确认入口留存。

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L5-chat` 不是 `conversation` 的真相仓,也不是 runtime 执行仓,更不是简单的聊天页面集合。它是 **“面向用户的对话交互产品层 / chat experience 层”**。

你可以把它理解成:
- 用户怎样进入正式聊天入口
- 一次 chat 体验里,输入、回复、附件、建议、状态、引用、错误、等待、流式输出怎样被组织
- platform 内部的 conversation、member、runtime、artifact、observability 能力怎样被包装成用户可理解、可操作、可反馈的交互面
- 用户怎样从 chat 里发起、理解、继续、打断和复盘一次 AI 协作过程

这些事情,都由 `L5-chat` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L5-chat`,这些对话体验事实就会散落在:
- `conversation` 各自暴露的原始会话数据里
- `runtime` 自己的状态与执行输出里
- `artifact` 各自的文件/结果预览里
- `observability` 提供的诊断摘要里
- UI 各页面临时拼接的输入框、消息列表、建议条和附件卡片里

结果就会出现:
- 用户看到的是多套拼接过的体验,而不是统一聊天主线
- thread、message、attachment、status、suggestion、diagnostic 各自一套口径
- runtime 的执行结果、人类的输入意图、artifact 的产物预览很难形成统一交互流
- chat 页面只能展示数据,却不能把平台能力稳定组织成“可理解、可继续、可反馈”的产品体验

所以 `L5-chat` 必须独立存在,作为:
> **把 conversation、member、runtime、artifact、observability 等多个系统的结果组织成统一可理解、可操作、可反馈的对话产品体验层。**

### 1.3 新人最容易混淆的几个词

#### ChatThread
就是:
> 用户在 chat 里看到并操作的一条线程体验载体。

它不是 `conversation` 的正式真相本体。

#### ChatReplyState
就是:
> 用户界面里看到的“思考中 / 生成中 / 执行中 / 等待中 / 已完成 / 失败”等回复状态。

它不是 runtime 的正式执行状态机。

#### VisibleMemberCard
就是:
> 聊天里展示给用户看的成员卡片、头像、名称、简介摘要。

它不是 `member` 的主体真相本体。

#### AttachmentCard / ArtifactPreview
就是:
> 聊天里可见的文件卡片、结果卡片、产物预览。

它不是 artifact truth 本体。

#### DiagnosticHint
就是:
> 面向用户展示的状态解释、错误提示、建议动作或健康提示。

它不是 observability truth 本体。

#### InputDraft / SuggestionState
就是:
> 输入框里的草稿、建议、slash/shortcut 状态和临时交互态。

它不是 persisted domain state。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L5-chat/02` 时,先收稳以下前提:
- `L5-chat` 不应按输入框 / 消息列表 / 文件卡片 / 侧边栏等纯组件树平铺理解,而应按对话产品体验主链责任拆
- chat 至少应拆成“会话入口与线程体验 / 消息呈现与回复体验 / 输入、建议与交互编排 / 附件、产物与上下文消费 / 诊断、反馈与状态辅助”五个主要部分
- chat 自己拥有的真相不是 conversation truth、member truth、runtime execution truth、artifact truth 或 observability truth,而是 thread UX、reply UX、input UX、attachment UX、feedback UX 这类产品层真相
- `L5-chat` 只能为用户和操作者提供产品交互面,不能反过来替这些 source systems 持有正式领域真相
- 02 的重点不是“列有哪些页面组件”,而是先把“chat 体验层在平台里到底是什么、和 conversation/member/runtime/artifact/observability 怎么分层”讲清楚
- thread switch、stream render、suggestion、artifact preview、diagnostic hint、feedback 这些不是零散小功能,而是 chat 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的对话产品体验心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,用户面对的不是一堆内部仓,而是一段对话体验。用户真正需要的不是“能看到 message JSON”,而是:
- 进入一个 thread 时能理解当前上下文和当前成员
- 当 runtime 正在思考、执行、等待、失败、完成时,能看到符合人类心智的状态表达
- 文件、产物、引用、建议、下一步动作都能在同一对话面里被组织起来
- 错误、阻断、诊断、重试、继续都能在 chat 面里被解释和引导
- 不需要理解内部 conversation / runtime / artifact / observability 的边界,也能顺畅完成协作

如果把这些逻辑分别散落到:
- conversation 原始接口返回
- runtime 自己的状态输出
- artifact 的文件预览
- observability 的诊断面
- 多个 UI 页面和组件树的局部组合里

系统会快速退化成:
- 用户看到的只是多个系统结果的拼盘
- thread、reply、input、attachment、hint 各自独立,缺少统一交互主线
- 出现异常时,用户不知道现在到底该等、该输、该重试还是该放弃
- 平台能力虽强,但产品体验不连贯

因此,本概要设计的任务就是:
> **把 `L5-chat` 写成一个新人也能看懂的“对话交互产品层”,而不是把会话、执行、文件和提示分别摆在页面上。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 线程与消息统一体验 | 多源拼装风险高 | 单一 chat 主线 | 需正式收敛 |
| 流式回复与状态表达 | 容易割裂 | 统一 reply state 主线 | 需形成产品心智 |
| 附件与产物消费 | 依赖 source 页面 | chat 内统一上下文消费 | 需正式组织 |
| 输入与建议编排 | 临时态易漂移 | suggestion / action 主线稳定 | 需明确交互边界 |
| 诊断与反馈 | source 提示零散 | 统一 status/help/feedback 面 | 需正式收口 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把 platform 内部多个系统的状态和结果组织成统一、连贯、可理解、可继续的聊天协作体验
- **技术问题**:ChatThread、ChatReplyState、VisibleMemberCard、AttachmentCard、SuggestionState、DiagnosticHint 与 conversation / member / runtime / artifact / observability 之间的边界如何稳定建模,并形成统一 chat 主链

## 4. 约束条件

### 4.1 技术约束

- thread / reply / input / attachment / hint 必须始终能回指 source refs
- chat 的临时交互态不能冒充 persisted domain state
- 流式输出、等待态、错误态、继续态必须有统一状态模型
- artifact / diagnostic / member display 只能消费上游只读结果,不能反写源仓
- chat 交互编排不能替代 runtime/process 的业务编排真相

### 4.2 资源约束

- 单会话消息量、附件量、状态更新频率会持续增长,渲染与缓存复杂度必须受控
- 流式回复和 suggestion 体验必须高频实时,但不能拖垮 source systems
- chat 导出的只读视图和上下文片段不能无限膨胀

### 4.3 时间约束

- 当前阶段先收稳 chat 主体验主线,而不是先做复杂社交化、多人态、超长历史分析等扩展
- thread、reply、input、attachment、hint 五条基础链必须优先稳定,否则后续产品体验会长期割裂

### 4.4 合规约束

- UI 层不得擅自改写 source truth
- 诊断提示不得冒充正式治理或执行裁决
- 用户可见附件和摘要必须受权限与上游可见性约束
- 对话导出、分享视图不得替代 archive 正式沉淀本体

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| thread length | 高 | 长周期协作对话 |
| stream updates/sec | 高频 | 流式体验要求 |
| attachment cards/thread | 中高 | 文件与产物消费需求 |
| suggestion states | 高频 | 交互编排需求 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ conversation / member       │
                    │ runtime / artifact / obs    │
                    │ - thread / member / state   │
                    │ - outputs / hints / refs    │
                    └────────────┬───────────────┘
                                 │ chat experience input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-chat                    │
                    │ - thread / reply / input   │
                    │ - attachment / hint / UX   │
                    └────────────┬───────────────┘
                                 │ visible interaction output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ end users / operators      │   │ console / UI shell         │   │ feedback / analytics       │
│ - interact / continue      │   │ - render / layout          │   │ - behavior summaries       │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L5-chat` 自己负责会话入口、回复呈现、输入交互、附件消费、提示与反馈等产品体验主线
- `conversation`、`member`、`runtime`、`artifact`、`observability` 是 source truth 或 source result 的提供方,但 chat 不拥有它们的源真相
- 用户和 operators 通过 chat 消费统一交互面,而不是直接理解底层仓结构
- console / UI shell 负责容器和布局,但 chat 负责产品交互语义

所以 `L5-chat` 在全局里的角色是:
> **把 conversation、member、runtime、artifact、observability 等多个系统的结果组织成统一、连贯、可理解、可操作的对话产品体验层。**

### 5.3 系统边界

**做什么**:
- 管理 thread 入口与 thread 体验
- 呈现回复、流式输出、引用、状态和可见成员信息
- 管理输入、建议、快捷动作、继续/重试/取消等交互体验
- 管理附件、产物、上下文引用、诊断提示和反馈交互

**不做什么**:
- 不持有 conversation truth
- 不持有 runtime execution truth
- 不持有 artifact / observability / member 的源真相
- 不替代 UI 组件库或 analytics 本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| conversation | 99.9% | thread 无法刷新时保留本地只读快照并标记 stale |
| runtime | 99.9% | 运行态延迟时展示 waiting / retry hint,不伪造完成态 |
| artifact | 99.9% | 预览延迟时保留附件卡片和 refs,不伪造内容 |
| observability | 99.9% | 诊断提示缺失时降级为基础错误提示 |
| member / member-images | 99.9% | 成员卡缺失时保留最小身份占位,不伪造成员真相 |

### 5.5 关键依赖风险

- chat 视图和 source truth 漂移会直接造成用户误解
- 流式输出与执行状态若不同步,用户会看到割裂体验
- attachment preview 若和 artifact truth 混层,会造成错误文件语义
- hint / status / diagnostic 若冒充 source truth,会让用户做错操作
- 输入临时态若被错误持久化,会污染正式领域状态

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把输入框、消息列表、文件卡片、侧边栏等组件横向平铺。  
> 它按 **对话产品体验主链职责 + 线程 / 回复 / 输入 / 上下文 / 提示差异** 来拆分。  
> 因此下面每一部分都可能包含多个交互对象和机制,共同支撑同一段 chat 体验主链。

#### 会话入口与线程体验部分

- **它是什么**: 这是 `L5-chat` 的主交互入口层,一起回答“用户怎样进入并继续一个正式线程”
- **为什么单独有它**: 如果没有独立 thread 体验层,thread list、resume、switch、resume state 会和 message 呈现、输入行为混成一层
- **负责什么**:
  - 提供 thread list / open / switch / resume 体验
  - 组织 recent threads / visible thread state
  - 维护用户进入 chat 的主锚点
- **不负责什么 / 容易混淆点**:
  - 不持有 conversation truth 本体
  - 不替代 source 会话状态机
  - 不直接决定 runtime 流程推进
  - 最容易和 Conversation truth、UI shell 路由、source persisted thread state 混淆
- **与其他部分交互**:
  - 下游: 消息呈现与回复体验、输入交互、附件消费、状态辅助
  - 外部: conversation / member / runtime
  - 交互类型: entry 型 + visible thread state 型
- **后续详细设计展开点**:
  - ChatThread / ThreadResume contract
  - thread list / switch / resume 主线

#### 消息呈现与回复体验部分

- **它是什么**: 这是 chat 的核心阅读层,一起回答“用户到底看到了什么回复与状态”
- **为什么单独有它**: reply、stream、citation、visible member card 是用户最直接感知到的体验层,但它们不等于 conversation/runtime/member 真相
- **负责什么**:
  - 渲染 message bubble / reply block / stream rendering
  - 渲染 citation / reference / step summary
  - 渲染 visible member / assistant card
- **不负责什么 / 容易混淆点**:
  - 不持有 runtime execution truth
  - 不持有 member truth 本体
  - 不直接生成 conversation truth
  - 最容易和 runtime 状态机、member 主体资料、conversation persisted reply 混淆
- **与其他部分交互**:
  - 上游: 会话入口与线程体验部分
  - 下游: 诊断、反馈与状态辅助部分
  - 外部: conversation / member / runtime
  - 交互类型: reply render 型 + visible member 型
- **后续详细设计展开点**:
  - ChatReplyState / stream rendering / reference card 模型

#### 输入、建议与交互编排部分

- **它是什么**: 这是 chat 的交互驱动层,一起回答“用户怎样发起下一步动作”
- **为什么单独有它**: 输入行为和阅读行为不是一回事,这里最容易把 UX 编排和业务编排混在一起
- **负责什么**:
  - 管理 input draft / slash / suggestions / quick actions
  - 管理 submit / cancel / regenerate / branch UX
  - 管理 mention / attach / command entry 等短暂态
- **不负责什么 / 容易混淆点**:
  - 不持有 persisted domain state
  - 不替代 runtime/process 的业务编排
  - 不持有 artifact 或 conversation 真相
  - 最容易和 source persisted input、business orchestration、runtime actions 混淆
- **与其他部分交互**:
  - 上游: 会话入口与线程体验部分
  - 下游: 消息呈现与回复体验、附件消费、状态辅助
  - 外部: conversation / runtime / artifact
  - 交互类型: input draft 型 + UX orchestration 型
- **后续详细设计展开点**:
  - suggestion state / quick action / submit flow 模型

#### 附件、产物与上下文消费部分

- **它是什么**: 这是 chat 的上下文与产物承接层,一起回答“聊天里怎样带入和展示上下文材料”
- **为什么单独有它**: 文件、产物、证据和上下文材料是对话体验的重要组成,但它们不是 artifact / archive / source truth 本体
- **负责什么**:
  - 渲染 attachment card / artifact preview / refs
  - 组织 context chips / evidence / output references
  - 支撑 share/export preview 等只读消费面
- **不负责什么 / 容易混淆点**:
  - 不持有 artifact truth
  - 不持有 archive truth
  - 不负责文件物化或结果入库
  - 最容易和 artifact 真相、archive 导出、source 引用本体混淆
- **与其他部分交互**:
  - 上游: 消息呈现与回复体验部分、输入交互部分
  - 下游: 诊断、反馈与状态辅助部分
  - 外部: artifact / archive / observability / conversation
  - 交互类型: attachment consume 型 + context render 型
- **后续详细设计展开点**:
  - attachment / preview / context ref 模型

#### 诊断、反馈与状态辅助部分

- **它是什么**: 这是 chat 的解释与辅助层,一起回答“系统忙、错、阻断时怎样帮助用户”
- **为什么单独有它**: 真正影响体验质量的很多都在非 happy path,如果不单列,这些内容会散在 reply 和 input 层里
- **负责什么**:
  - 管理 loading / waiting / blocked / failed / recovered state hints
  - 管理 diagnostic hint / health hint / cost/latency hint
  - 管理 user feedback / thumbs / correction entry / explain-why surfaces
- **不负责什么 / 容易混淆点**:
  - 不持有 observability truth 本体
  - 不替代 runtime/governance 的真实状态裁决
  - 不直接触发控制命令
  - 最容易和 observability 诊断真相、governance decision、runtime state 机混淆
- **与其他部分交互**:
  - 上游: 消息呈现与回复体验部分、附件消费、runtime/observability 输入
  - 下游: feedback / analytics / user action
  - 交互类型: status helper 型 + diagnostic/feedback 型
- **后续详细设计展开点**:
  - status helper / diagnostic hint / feedback contract

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ conversation / member       │
                    │ runtime / artifact / obs    │
                    │ - thread / member / state   │
                    │ - outputs / hints / refs    │
                    └────────────┬───────────────┘
                                 │ chat experience input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-chat                    │
                    │ - thread / reply / input   │
                    │ - attachment / hint / UX   │
                    └────────────┬───────────────┘
                                 │ visible interaction output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ end users / operators      │   │ console / UI shell         │   │ feedback / analytics       │
│ - interact / continue      │   │ - render / layout          │   │ - behavior summaries       │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L5-chat` 自己负责“组织 thread 体验”“组织 reply/stream 体验”“组织输入和建议交互”“消费附件与上下文材料”“提供状态解释和反馈入口”
- `conversation` / `member` / `runtime` 的交互主要落在 **会话入口与线程体验部分** 与 **消息呈现与回复体验部分**,为 chat 提供 thread、reply、member 和执行状态输入
- `artifact` / `archive` 的交互主要落在 **附件、产物与上下文消费部分**,为 chat 提供文件、结果、证据和导出预览输入
- `observability` 的交互主要落在 **诊断、反馈与状态辅助部分**,为 chat 提供诊断提示、健康补充和解释材料
- console / UI shell / 用户 / operators 消费的是 chat 提供的产品体验结果,而不是 source truth 本体

### 7.3 分模块交互说明(逐个写)

#### 与 `conversation` 的交互

```text
┌────────────────────────────┐
│ conversation               │
│ - threads / turns / msgs   │
└────────────┬───────────────┘
             │ thread/reply input
             ▼
┌────────────────────────────┐
│ chat                       │
│ - ChatThread               │
│ - reply render             │
└────────────────────────────┘
```

- `conversation` 是 **thread 与 message 来源方**
- **交互类型**: thread/reply 输入型交互
- **主流程位置**: open thread、switch thread、resume、render replies 时进入主流程
- **交互解释**:
  - chat 消费 thread/message 真相
  - chat 把它们组织成可见交互体验
  - chat 不持有 conversation truth 本体
- **高风险异常流**:
  - chat thread 视图漂移后被误当 conversation truth
- 后续 `03-详细设计.md` 继续展开:
  - ChatThread contract
  - thread/resume 主线

#### 与 `member / member-images` 的交互

```text
┌────────────────────────────┐
│ member / member-images     │
│ - member identity          │
│ - image summary            │
└────────────┬───────────────┘
             │ visible member input
             ▼
┌────────────────────────────┐
│ chat                       │
│ - member card / persona UI │
└────────────────────────────┘
```

- 这些系统是 **成员展示来源方**
- **交互类型**: visible member 输入型交互
- **主流程位置**: reply render、thread header、member switch、persona display 时进入主流程
- **交互解释**:
  - chat 只消费 member 与 image 的展示摘要
  - visible member card 不持有主体真相
- **高风险异常流**:
  - image/persona 摘要被误当 live member truth
- 后续 `03-详细设计.md` 继续展开:
  - VisibleMemberCard contract
  - identity/image display 主线

#### 与 `runtime` 的交互

```text
┌────────────────────────────┐
│ runtime                    │
│ - stream / execution state │
│ - wait / fail / result     │
└────────────┬───────────────┘
             │ reply/state input
             ▼
┌────────────────────────────┐
│ chat                       │
│ - reply state / progress   │
└────────────────────────────┘
```

- `runtime` 是 **执行状态与流式回复来源方**
- **交互类型**: stream/state 输入型交互
- **主流程位置**: generating、running、waiting、blocked、failed、completed 时进入主流程
- **交互解释**:
  - chat 把 runtime 状态翻译成用户可理解的 reply state
  - chat 不替代 runtime execution truth
- **高风险异常流**:
  - ChatReplyState 与 runtime execution truth 漂移
- 后续 `03-详细设计.md` 继续展开:
  - reply state model
  - stream / wait / fail 主线

#### 与 `artifact / archive` 的交互

```text
┌────────────────────────────┐
│ artifact / archive         │
│ - files / outputs / refs   │
│ - export / evidence view   │
└────────────┬───────────────┘
             │ attachment/context input
             ▼
┌────────────────────────────┐
│ chat                       │
│ - attachment card          │
│ - artifact preview         │
└────────────────────────────┘
```

- `artifact / archive` 是 **上下文材料来源方**
- **交互类型**: attachment / context 输入型交互
- **主流程位置**: file attach、artifact preview、export preview、evidence reference 时进入主流程
- **交互解释**:
  - chat 只读消费文件、产物、历史材料摘要
  - 不反向持有 artifact/ archive 真相
- **高风险异常流**:
  - 附件卡片或导出视图被误当 source truth
- 后续 `03-详细设计.md` 继续展开:
  - attachment / preview / context chip 主线

#### 与 `observability` 的交互

```text
┌────────────────────────────┐
│ observability              │
│ - health / diagnostic      │

└────────────┬───────────────┘
             │ hint input
             ▼
┌────────────────────────────┐
│ chat                       │
│ - diagnostic hint          │
│ - status helper            │
└────────────────────────────┘
```

- `observability` 是 **诊断和状态辅助来源方**
- **交互类型**: hint / health 输入型交互
- **主流程位置**: wait、blocked、failed、degraded、slow、recovered 时进入主流程
- **交互解释**:
  - chat 只翻译和展示诊断提示
  - 不替代 observability source truth
  - status helper 是解释层,不是决策层
- **高风险异常流**:
  - diagnostic hint 被误当 observability 权威结论
- 后续 `03-详细设计.md` 继续展开:
  - hint contract
  - explain / feedback 主线

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是 chat 体验层、哪个模块是只读消费方、哪个模块是用户动作面

本节**不**展开:
- 具体组件树
- 流式渲染和虚拟列表实现细节
- suggestion / slash 求值算法
- 文件预览和分享的底层实现
- 反馈统计与埋点细节

这些内容留到 `03-详细设计.md` 中继续展开。

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 ChatThread / ChatReplyState / VisibleMemberCard / InputDraft / SuggestionState / AttachmentCard / DiagnosticHint / FeedbackEntry 等 chat 体验层真相
- 把 conversation、member、runtime、artifact、observability、archive 的结果组织成统一的 thread、reply、input、attachment、hint、feedback 产品体验主线
- 管理 stream render、wait/fail/recovered state、suggestion/quick action、artifact preview 和 diagnostic hint 的用户可见表现
- 向用户、operators、console、analytics 提供统一的 chat 只读结果与交互事件面

**本模块不做什么**:
- 不持有 conversation truth、member truth、runtime execution truth、artifact truth、observability truth
- 不替代 UI 组件库本体、analytics 系统或控制命令执行层
- 不直接推进 business orchestration 或 runtime/process 状态机

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 chat“为什么存在”,而是让开发者可以直接开始实现:
- thread / recent threads / resume 主线怎样组织 conversation 输入
- reply / stream / references / member cards 怎样形成统一阅读体验
- input draft / slash / suggestion / quick actions 怎样组织用户动作
- attachment / artifact preview / context refs 怎样进入统一上下文消费面
- diagnostic hint / wait / fail / blocked / feedback 怎样帮助用户理解当前状态

如果不先把这些内容采集清楚,03 很容易退化成:
- 页面组件树说明书

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `ChatThread / ChatReplyState / AttachmentCard / FeedbackEntry` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 chat 产品体验主链,`03` 却退化成组件树与前端状态清单
- 实现者知道有 stream render,却不知道它如何和 thread、attachment、hint、feedback 形成一条统一用户心智主线
- 输入、回复、上下文、提示各写一套,彼此断裂

#### 5.2.4 关键函数代码片段

```rust
/// 根据 conversation 输入打开一个正式的 ChatThread 体验对象。
fn open_chat_thread(
    thread_repo: &dyn ChatThreadRepo,
    input: OpenThreadInput,
) {
    // [input.校验 thread 输入边界]
    // 先确认这是对 conversation truth 的消费,而不是本仓自己生成的新真相。
    input.validate_thread_source_boundary();

    // [ChatThread::从输入创建]
    // 再把来源 thread 输入收束成正式 ChatThread 体验对象。
    let thread = ChatThread::from_input(input);

    // [thread_repo.保存 thread 体验状态]
    // 最后把可见 thread 状态写入 chat 层,供 reply/input/context 主线消费。
    thread_repo.save_thread_view(thread);
}
```

这段实现守住的边界是:
- chat thread 只消费 conversation refs,不替代 conversation truth
- open/switch/resume 主线必须围绕可见体验展开,而不是改写上游状态
- thread view 要保持对 source refs 的稳定回指

#### 5.2.5 该部分的边界与非职责
- 不持有 conversation truth 本体
- 不推进 runtime 执行状态
- 不负责附件/诊断真相本体
- 不等于 UI shell 路由本体

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `消息呈现与回复体验部分` 提供 thread 视图输入
- 向 `输入、建议与交互编排部分` 提供 active thread 锚点
- 向 `附件、产物与上下文消费部分` 提供 thread context 锚点

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `ChatThread ≠ Conversation truth` 必须写死
- `visible thread state ≠ persisted source state` 必须写死
- resume token 若不稳定,用户会进入错误线程上下文

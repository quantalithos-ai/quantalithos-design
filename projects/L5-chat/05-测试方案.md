### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 chat“能显示消息”,而是系统验证 `L5-chat` 是否真正满足“面向用户的对话交互产品层 / chat experience 层”的设计要求,尤其要证明以下几点成立:
- ChatThread / ChatReplyState / InputDraft / AttachmentCard / DiagnosticHint 构成正式 chat 体验层真相
- `ChatThread ≠ Conversation truth`、`ChatReplyState ≠ runtime execution truth`、`VisibleMemberCard ≠ Member truth` 等核心边界成立
- thread / reply / stream / input / attachment / hint 五条体验主线可以统一组织,并且 source refs 持续可追溯
- input draft / suggestion / quick actions 只表达 UX 临时态,不污染 persisted domain state
- attachment/artifact preview、diagnostic hint、health hint 都只能消费 source 结果,不反写真相
- wait / fail / blocked / recovered 等非 happy path 体验有统一解释层,且用户可理解下一步动作

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 会话入口与线程体验部分 | thread UX 对象 | P0 | ChatThread、ThreadResumeToken、ThreadListItem、VisibleThreadState |
| 消息呈现与回复体验部分 | reply UX 对象 | P0 | ChatReplyState、StreamChunk、ReferenceCard、VisibleMemberCard、ReplySegment |
| 输入、建议与交互编排部分 | input UX 对象 | P0 | InputDraft、SuggestionState、SlashAction、QuickActionEntry、SubmissionIntent |
| 附件、产物与上下文消费部分 | attachment/context UX 对象 | P0 | AttachmentCard、ArtifactPreviewCard、ContextChip、EvidenceRefCard、SharePreviewCard |
| 诊断、反馈与状态辅助部分 | helper/feedback UX 对象 | P0 | DiagnosticHint、HealthHint、ErrorAssistState、FeedbackEntry、ExplainSurface |
| conversation / member / runtime / artifact / observability 真相本体 | 非范围 | P2 | 只验 chat 如何消费其结果并组织产品体验,不验 source truth 全部实现 |
| UI 组件库本体与视觉像素级实现 | 非范围 | P2 | 只验交互语义和状态组织,不验具体组件风格 |
| analytics / growth 深度分析逻辑 | 非范围 | P2 | 只验反馈/交互信号输出,不验 analytics 全链条 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数与局部不变量 | domain / product owner | `input.validate_thread_source_boundary`、`input.validate_reply_source_boundary`、`draft.validate_input_draft_boundary`、`input.validate_context_source_boundary`、`input.validate_hint_source_boundary` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + render + projection + publisher 联动 | backend / product owner | `OpenThread`、`RenderReply`、`RenderStream`、`UpdateDraft`、`ResolveSuggestions`、`BuildAttachmentCard`、`BuildDiagnosticHint`、`SubmitFeedback` | thread、reply、input、context、assist 五条主线同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | conversation → thread/reply、member-images → visible member、runtime → reply state、artifact/archive → previews、observability → hints | 输入输出语义一致 |
| 恢复专项测试 | 验证 stream 断裂、runtime 状态漂移、artifact 引用失效、hint 失真、draft 误持久化等异常链 | architecture / QA | thread stale、reply mismatch、preview stale、diagnostic conflict、draft pollution | 体验不误导、错误被正确阻断或标记 |
| 投影一致性测试 | 验证 thread/reply/summary/preview/hint 视图与 source refs 一致 | backend / QA | thread view rebuild、reply view rebuild、attachment preview rebuild、hint view rebuild | 投影只读且与 source input 一致 |
| 端到端主线测试 | 验证最小对话体验闭环 | QA / owner | open thread → stream reply → attach/preview → hint/feedback | chat 体验闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| `ChatThread ≠ Conversation truth` | thread 只消费 conversation refs,不反写 source truth | 单元 + 集成测试 | 是 | thread/source compare |
| `ChatReplyState ≠ runtime execution truth` | reply 状态只翻译 runtime 结果,不冒充执行真相 | 单元 + 事件链测试 | 是 | reply/runtime compare |
| `VisibleMemberCard ≠ Member truth` | 成员卡片只展示摘要,不等于 member 主体真相 | 单元 + 集成测试 | 是 | visible member compare |
| `input draft/suggestion state ≠ persisted domain state` | 输入草稿和建议态不得持久化成正式领域状态 | 单元 + 恢复测试 | 是 | draft state / negative flow |
| `attachment/artifact preview ≠ artifact truth` | 产物和附件卡片只能读 source refs,不冒充 artifact 真相 | 单元 + 事件链测试 | 是 | preview/source compare |
| `Diagnostic hint ≠ observability truth` | 诊断提示只是解释层,不替代观测真相 | 单元 + 集成测试 | 是 | hint/source compare |
| `status helper ≠ runtime/governance true state` | blocked/failed/waiting 帮助态只解释,不替代裁决真相 | 单元 + 集成测试 | 是 | status helper diff |
| stream / reply / refs 一致 | 流式分片和最终回复可对账 | 集成 + 恢复专项测试 | 是 | chunk/reply compare |
| attachment / export preview / context 可回指 | 预览与上下文引用都能回指 source refs | 集成 + 投影一致性测试 | 是 | refs compare |

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 thread / resume / switch,都必须回归 thread UX 与 source refs 主线
- 每次改动 reply / stream / visible member card,都必须回归 reply 对账与可见状态主线
- 每次改动 draft / suggestions / quick actions,都必须回归 UX 临时态与 persisted state 边界主线
- 每次改动 attachment / preview / evidence refs,都必须回归上下文消费与 source refs 主线
- 每次改动 hints / status / feedback,都必须回归 explain 层与 source truth 分离主线

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| 多人态 / 多会话并发 UX 后续细化 | 验收矩阵需扩充 | TL / 架构 |
| artifact / archive 预览能力继续演进 | context/preview 验收需增加更多样本 | chat / artifact / archive |
| analytics / feedback 需求增长 | feedback 与行为分析验收需扩充 | product / analytics |

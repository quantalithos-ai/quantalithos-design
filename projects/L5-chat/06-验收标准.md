### 读前说明 · 验收标准标准生产流程

`06-验收标准` 不是从“我想验什么”开始写,而是从 `02/03/05` 已明确的目标、边界、红线、主流程结果和测试门禁反推验收门禁。

建议按以下流程产出:
1. **先收输入**
   - 读取 `02-概要设计.md`、`03-详细设计.md`、`05-测试方案.md`
   - 抽取: 目标/非目标、主要部分边界、主流程关键结果、实现红线、高风险验收点、最小可运行闭环、05 中的强测试门禁
2. **再识别验收对象**
   - 分清功能结果、边界结果、状态结果、对外交互结果、恢复结果、投影结果
3. **按主要部分分组**
   - 每个主要部分分别列: 必须满足什么 / 绝不能出现什么 / 哪些是一票否决
4. **明确通过/不通过条件**
   - 每条验收项必须写清通过条件、失败条件、失败意味着哪条边界被破坏
5. **最后形成门禁清单**
   - 单列一票否决项、可延期优化项、风险接受项与接受人

> 先按“主要部分 + 不可破坏边界”组织,再落成功能门禁和非功能门禁,不要只写口号式验收条目。

## 1. 验收背景与范围

### 1.1 验收背景

本次验收针对 `L5-chat` 的第一批核心设计主线展开。当前 `02-概要设计.md`、`03-详细设计.md` 与 `05-测试方案.md` 已经明确:
- `L5-chat` 是面向用户的对话交互产品层 / chat experience 层,不是 conversation truth 仓、runtime 执行仓或 artifact 真相仓
- ChatThread / ChatReplyState / InputDraft / AttachmentCard / DiagnosticHint 构成正式 chat 体验层真相
- `ChatThread ≠ Conversation truth`、`ChatReplyState ≠ runtime execution truth`、`VisibleMemberCard ≠ Member truth` 等核心边界必须成立
- thread / reply / stream / input / attachment / hint 五条体验主线必须能统一组织,且 source refs 持续可追溯
- input draft / suggestion / quick actions 只表达 UX 临时态,不得污染 persisted domain state
- attachment/artifact preview、diagnostic hint、health hint 都只能消费 source 结果,不得反写真相
- wait / fail / blocked / recovered 等非 happy path 体验必须有统一解释层,并让用户理解下一步动作

因此,本次验收的目的不是笼统判断“能不能发消息和显示卡片”,而是判断 chat 的 thread 主线、reply/stream 主线、input/suggestion 主线、attachment/context 主线与 hint/feedback 主线是否真的成立,是否可作为后续阶段的稳定基线。

### 1.2 验收范围 / 非范围

| 项 | 是否纳入 | 说明 |
|---|---|---|
| 会话入口与线程体验部分 | 是 | ChatThread、ThreadResumeToken、ThreadListItem、VisibleThreadState |
| 消息呈现与回复体验部分 | 是 | ChatReplyState、StreamChunk、ReferenceCard、VisibleMemberCard、ReplySegment |
| 输入、建议与交互编排部分 | 是 | InputDraft、SuggestionState、SlashAction、QuickActionEntry、SubmissionIntent |
| 附件、产物与上下文消费部分 | 是 | AttachmentCard、ArtifactPreviewCard、ContextChip、EvidenceRefCard、SharePreviewCard |
| 诊断、反馈与状态辅助部分 | 是 | DiagnosticHint、HealthHint、ErrorAssistState、FeedbackEntry、ExplainSurface |
| conversation / member / runtime / artifact / observability 真相本体 | 否 | 只验 chat 如何消费其结果并组织产品体验,不验 source truth 全部实现 |
| UI 组件库本体与视觉像素级实现 | 否 | 只验交互语义和状态组织,不验具体组件风格 |
| analytics / growth 深度分析逻辑 | 否 | 只验反馈/交互信号输出,不验 analytics 全链条 |

## 8. 缺陷分级与放行规则

| 缺陷级别 | 是否允许放行 | 说明 |
|---|---|---|
| S | 否 | chat 视图反写真相 / runtime 状态被错误翻译 / artifact preview 冒充 source truth / input 临时态污染领域状态 |
| A | 视情况 | 主线可跑但 stream 对账、hint/source 对账、catalog/summary 一致性不稳 |
| B | 可带着走 | 非关键展示、低优先级 style / preview / summary 细节异常 |

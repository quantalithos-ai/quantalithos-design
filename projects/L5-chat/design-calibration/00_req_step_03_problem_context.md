### 3. SOP 问题回答

#### 3.1 当前业务背景是什么？

Quantalithos 的用户需要在同一个协作入口中阅读对话、理解项目进度、看到成员和运行状态、查看产物引用，并在关键治理节点发起受控审批。正式真相分布在多个 owner 仓中，跨端产品需要把这些安全、可见且有来源的能力组合成连续体验。Chat 因此承担“把平台能力交给人使用”的入口职责。

#### 3.2 当前主要痛点或机会点是什么？

| 问题 | 当前表现 | 影响 |
|---|---|---|
| 多域真相缺少统一入口 | 用户需要在对话、项目、治理、产物和运行语境之间切换，且不同 owner 的读取 / 变化语义不同 | 用户难以判断当前看到的是事实、快照、等待状态还是客户端提示 |
| 客户端命令结果容易被误读 | 发送、重试、审批和恢复都有 transport、command、event 和 owner result 多层状态 | 点击或 ACK 被误认为业务成功，产生错误信任和重复操作 |
| 实时变化与跨端状态复杂 | 变化可能重复、乱序、迟到、缺口或失去 cursor；不同端还需要共享体验语义 | 时间线、GateCard、进度和成员状态出现漂移 |
| 上游合同尚未完全统一 | 各 owner 的 safe view、cursor、visibility、error 和 SDK surface 仍有开放项 | Chat 不能安全地把未闭合合同写成“已接通” |
| 弱网与离线展示边界不清 | 本地可以保留展示缓存，但业务命令的提交状态可能未知 | 离线缓存容易冒充当前真相，恢复时产生重复副作用 |
| 可访问性和安全必须跨端一致 | 卡片、流式状态、错误和权限提示在不同壳层容易漂移 | 关键审批和阅读路径可能不可用或泄漏不可见信息 |

#### 3.3 哪些问题可以量化？

当前只能量化“是否有可判定状态和证据切口”，不能从历史 README 或上游候选数字直接锁定 P95、可用率、群规模或端到端延迟。原因是：

- `L5-chat` 当前没有实现仓、真实环境、workload、运行记录或 measurement authority；
- 上游性能候选只描述各自能力，不自动成为客户端可感知基线；
- SDK surface、event cursor、preview 和 workspace contract 尚未全部闭合。

因此，Step 3 只定义问题和可验证方向；响应性、恢复时间、容量和可访问性门禁在 Step 13~14 以正式测试 / 验收输入为准，不静态伪造数值。

#### 3.4 哪些是业务问题，哪些是技术问题？

| 类型 | 问题定义 |
|---|---|
| 业务问题 | 用户需要一个可信、连续、可访问的协作入口，能够理解对话、项目、成员、运行、产物和治理状态，并在授权范围内采取行动。 |
| 技术问题 | 客户端必须在不拥有业务 truth 的前提下，组合多 owner 的 query / command / event / safe view，处理可见性、cursor、重复、乱序、未知结果、缓存和跨平台状态。 |
| 安全问题 | Chat 不能通过页面、缓存、错误文本、预览或本地状态绕过 owner visibility、redaction、授权或审计边界。 |
| 可靠性问题 | Chat 不能把 transport 断线、ACK、缓存命中或本地 optimistic state 当作 owner 已提交事实；失败、未知和恢复中必须可见。 |

### 逐章修复结构化结果（2026-10-01）

以下为本 Step 已复核的当前需求级结果，替代前轮回填草稿中对应范围；保留旧轮记录用于差异审计，不代表实现或验收通过。

Quantalithos 的正式协作能力分布于对话、身份、工作、治理、制品、工作区、成员与运行等多个 owner。用户需要一个统一入口，在被授权的语境里阅读对话变化、理解项目和成员上下文、查看 Artifact 引用、处理 Gate 相关意图，并在断线或跨端切换后继续工作。Chat 要解决的问题是：如何把分散的正式 safe view、query、command 和 change 组织成可信、连续、可恢复的客户端体验，同时维持 owner truth 边界。

当前难点包括公共 SDK surface 与 owner visibility/cursor/error 语义尚未完全统一；变化可能重复、乱序、缺口或过期；命令 ACK 不等于业务提交；缓存不等于当前 truth；弱网、重启、撤销和多端状态需要明确恢复上限；预览、治理、成员与诊断信息必须满足最小披露和可访问性。当前没有足够的正式测量 authority 将旧文档的性能数字、事件集合、框架候选或可用率承诺作为本需求目标。

原型评审进一步确认：用户还需要在同一项目上下文中理解整体流程、阶段子流程、并行分支、汇聚等待、治理 Gate、关联群聊和交付证据，并在公司成员、项目成员与当前群聊参与者之间保持清晰边界。该问题仍属于跨 owner 协作信息的安全显化与连续性，不要求 Chat 成为项目流程或成员关系的真相源。

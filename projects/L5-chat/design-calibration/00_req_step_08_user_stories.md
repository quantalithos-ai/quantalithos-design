## 3. SOP 问题回答

### 3.1 当前正在讨论哪些核心能力节点？

按 Step 7 的顺序讨论四个节点：

1. **N1 安全协作语境进入与保持**：用户能进入正确的协作范围，并在刷新、重启、深链或撤销后保持安全语境；
2. **N2 正式协作事实安全显化**：用户能理解正式 owner 提供的对话、成员、项目、Gate、Artifact、Workspace 和 Runtime 摘要；
3. **N3 用户意图受控发起与结果反馈**：用户能编辑、发送、重试或发起受控治理意图，并知道结果是否已确认；
4. **N4 变化、失败、离线与恢复下的展示连续性**：用户能在断线、重复、缺口、过期、重启和多端变化后理解当前状态。

### 3.2 哪些角色目标支撑核心闭环？

- 协作者希望进入正确对话、理解 Turn、编辑草稿并知道消息结果；
- 项目负责人希望在项目语境中理解成员/项目/运行摘要，发起必要协作意图并在恢复后继续工作；
- Gate 审批者希望看到治理语境和 Artifact 引用，提交受控审批意图并区分 pending、confirmed、rejected 和 unknown；
- 旁观者/审计查看者希望在授权范围内阅读历史、来源和降级状态，避免把缓存或 UI 提示误读为正式结论；
- 客户端支持人员希望查看低敏连接、缓存、恢复和错误姿态，以便指导用户下一步，而不读取内部日志或原始正文。

### 3.3 哪些角色目标只是外围增强？

以下目标不决定最小闭环：

- 用户希望使用全局搜索、复杂过滤、富文本增强和个性化布局；
- 用户希望收到桌面托盘徽标、细粒度通知、系统分享和多窗口联动；
- 移动端用户希望使用后台推送、手势、系统返回和原生分享；
- 支持人员希望获得更丰富的诊断面板和趋势视图。

这些故事可以记录为外围增强，但不能压过 N1～N4 的核心故事，也不能在没有 owner/SDK 合同的情况下进入正式功能表。

### 3.4 哪些看起来像故事，但不应进入 Chat？

以下句子不是 Chat 用户故事：

- “作为 Chat，我希望创建一个 Conversation/Turn。”这是 owner truth，不是客户端角色目标；
- “作为 Chat，我希望批准一个 Gate。”正式 Decision 归 Governance；客户端只能表达被授权用户的提交意图和结果反馈；
- “作为 Chat，我希望计算成员权限或项目进度。”授权和业务状态归 Identity/Work/Member/Runtime；
- “作为 Chat，我希望订阅内部 bus topic。”这是实现接缝，不是用户价值；应由 SDK formal event capability 承接；
- “作为 Chat，我希望把 transport ACK 视为成功。”这是错误的状态推断，不得进入故事表。

## 4. 核心闭环用户故事

### 4.1 N1：安全协作语境进入与保持

| 用户故事 | 目标类型 | 业务价值 | 与核心能力闭环的关系 |
|---|---|---|---|
| `US-CHAT-001` 作为协作者，我希望进入当前被授权的对话或线程语境，以便我能在正确的协作范围内阅读和参与讨论。 | 核心闭环 | 防止用户在错误 scope、过期链接或未授权入口中协作。 | 支撑 N1“安全协作语境进入与保持”。 |
| `US-CHAT-002` 作为项目负责人，我希望从项目协作入口回到上次仍然有效的讨论语境，以便我能继续处理项目相关协作，而不必依赖不明来源的缓存。 | 核心闭环 | 保持跨次访问连续性，同时要求恢复前重新验证语境。 | 支撑 N1。 |
| `US-CHAT-003` 作为旁观者或审计查看者，我希望知道当前入口是可见、只读、过期、受限还是暂不可用，以便我不会把空白页面或缓存内容误认为正式事实。 | 核心闭环 | 让权限和可用性差异变成可理解的用户状态。 | 支撑 N1。 |
| `US-CHAT-004` 作为客户端支持人员，我希望在用户登出、scope 改变或可见性撤销后能安全结束旧语境，以便敏感内容不会继续留在页面或本地展示状态中。 | 核心闭环 | 降低旧语境残留和错误展示风险。 | 支撑 N1。 |

#### N1 故事停审

- 没有把 route、deep link、selection 或 cache 写成 Conversation/Project truth；
- 故事描述的是“安全进入和继续使用”的角色目标，而不是 SDK query 或路由实现；
- 可见、只读、过期、受限和不可用的目标均有故事承接；
- 没有孤儿故事或把 N2/N3 的业务动作提前写入 N1；
- 允许进入 N2 故事讨论。

#### N2 故事停审

- 每条故事都描述理解 owner 事实的角色目标，而不是渲染组件或 DTO；
- Turn、Gate、Artifact、成员、项目和运行摘要均保留 owner 真相边界；
- safe view、来源、可见性、freshness 和 degraded 语义都有角色价值承接；
- 没有把“显示成功”写成“业务已完成”；
- 允许进入 N3 故事讨论。

#### N3 故事停审

- 故事主体是协作者、审批者或负责人，未把 Chat/SDK 当人类角色；
- 草稿、提交意图、正式结果和 unknown outcome 被区分；
- 发送、重试、Gate 操作描述为角色目标，不写 command method、receipt schema 或接口时序；
- 没有任何故事把 transport ACK、toast 或按钮点击当业务成功；
- 允许进入 N4 故事讨论。

### 4.4 N4：变化、失败、离线与恢复下的展示连续性

| 用户故事 | 目标类型 | 业务价值 | 与核心能力闭环的关系 |
|---|---|---|---|
| `US-CHAT-014` 作为协作者，我希望在新的对话变化到达时看到不会重复、乱序或越过当前可见范围的内容，以便我能继续信任当前讨论。 | 核心闭环 | 保持实时/变化展示的可解释性和可见性边界。 | 支撑 N4“变化、失败、离线与恢复下的展示连续性”。 |
| `US-CHAT-015` 作为项目负责人，我希望在断线、桌面应用重启或 cursor 失效后恢复到带有过期/缺口说明的语境，以便我能继续工作而不会把旧缓存当作最新事实。 | 核心闭环 | 支持 V1 Desktop-first 的恢复主路径。 | 支撑 N4。 |
| `US-CHAT-016` 作为 Gate 审批者，我希望在提交结果未知或治理变化尚未恢复时看到明确的等待和查询提示，以便我不会重复发起可能有副作用的审批。 | 核心闭环 | 保护治理意图的幂等和责任边界。 | 支撑 N4，并承接 N3。 |
| `US-CHAT-017` 作为旁观者或审计查看者，我希望在内容过期、局部不可用或权限撤销时看到相应说明，以便我不会把不完整视图当作完整历史。 | 核心闭环 | 防止 degraded view 被误当正式完整结果。 | 支撑 N4。 |
| `US-CHAT-018` 作为客户端支持人员，我希望查看低敏的连接、缓存和恢复状态，以便我能指导用户重连或重新查询，而不需要访问内部 bus、原始日志或业务正文。 | 核心闭环 | 提供安全的客户端排障入口。 | 支撑 N4。 |

#### N4 故事停审

- 故事覆盖变化、重复/乱序/缺口、断线、重启、过期、撤销和 unknown；
- 故事仍描述用户目标，不把 cursor、event reducer 或 cache schema 写成目标；
- 支持人员故事限定为低敏客户端状态，不开放 Observability backend；
- 没有把网络重新连接或缓存恢复写成业务提交成功；
- 允许进入跨能力故事审计。

## 8. 跨能力故事审计

| 检查项 | 结论 |
|---|---|
| 是否存在没有能力节点映射的核心故事？ | 否；每条 `US-CHAT-001~018` 均映射到 N1～N4。 |
| 是否把同一角色目标重复拆到多个节点？ | 已控制；N3 的“提交并看结果”与 N4 的“恢复未知/变化”分别承担提交语境和恢复连续性。 |
| 是否把 N1 的入口故事误写成 N2 的事实展示？ | 否；N1 只处理进入/保持/撤销，N2 处理理解 owner safe view。 |
| 是否把 N2 的展示故事误写成 N3 的业务完成？ | 否；GateCard/Artifact 语境和受控动作分开。 |
| 是否把 N3 的 command 结果误写成 N4 的实时变化？ | 否；N3 关注用户意图反馈，N4 关注变化消费和恢复。 |
| 是否存在孤儿外围故事？ | 否；`US-CHAT-E01~E04` 均标记外围增强并给出能力归属。 |
| 是否有边界外故事进入正式故事表？ | 否；边界外候选单独审计，不进入核心/外围故事表。 |

## 9. 复杂度判断与设计取舍

| 复杂度来源 | 判断 | 控制方式 |
|---|---|---|
| 角色与 owner 授权交叉 | 高 | 故事只写角色目标；可见/可操作结论留给 owner，Chat 只显示结果。 |
| N2 跨域展示 | 中高 | 按安全摘要、引用、来源和降级状态写故事，不把跨域聚合写成 Chat 真相。 |
| N3 副作用与 unknown | 高 | 将“想做什么”和“是否已完成”分开叙述，后续功能必须保留 unknown/拒绝/失败。 |
| N4 多端恢复 | 高 | Desktop-first 先覆盖重启/断线/过期，Mobile 仅作为外围增强故事。 |
| 故事数量 | 中 | 18 条核心故事覆盖四节点，4 条外围增强保留但不扩张核心范围。 |

取舍结论：采用“按能力节点组织的少量目标故事”，不采用按页面、组件、接口或平台罗列的大故事清单；Desktop-first 作为场景约束进入 N4 和外围增强，不单独生成平台业务故事。

## 10. 正式文档回填草稿

正式 `00-需求文档.md` §8 可回填为：

> L5-chat 的核心用户故事按四个能力节点组织。围绕 N1，协作者、项目负责人、旁观者/审计者和支持人员需要进入并保持正确的协作语境，理解可见、只读、过期、受限和不可用状态。围绕 N2，协作者、项目负责人、审批者和审计查看者需要理解 Turn、成员/项目/运行摘要、Gate/Decision 语境、Artifact 引用以及来源、新鲜度和不可用提示。围绕 N3，协作者和审批者需要保存草稿、发起发送/重试或受控治理意图，并区分提交中、已确认、拒绝、失败和未知结果。围绕 N4，所有主要角色需要在变化、断线、重复、缺口、过期、权限撤销和 Desktop 重启后继续获得可解释的展示状态。
>
> 搜索、过滤、富文本增强、通知/托盘、多窗口、Mobile 推送和高级诊断属于外围增强。创建或修改 owner truth、计算授权、直接订阅内部 bus、把 ACK 当业务成功、执行 Runtime/Tools 或建设 Observability backend 不属于 Chat 用户故事。

## 11. Step 8 自检与门禁

### 11.1 进入 Step 9 条件

- 核心故事已按 N1～N4 完成，并有目标类型、业务价值和闭环映射；
- 外围增强故事已独立标记，不压过核心闭环；
- 边界外故事和错误状态推断已排除；
- 每个能力节点完成故事停审，跨能力重复、孤儿和串线已审计；
- 允许创建并完成 `00_req_step_09_functional_requirements.md`，按能力节点将故事归并为功能需求。

## 12. 本步结论

Step 8 将用户故事从角色清单收敛为四组能力目标：进入正确语境、理解正式事实、受控发起意图、在变化和恢复中保持连续性。故事不拥有 owner truth，也不把 SDK、事件、组件或平台动作当成用户价值。核心故事已经足以进入 Step 9 的功能需求小循环，外围增强和边界外能力保持隔离。
## 13. 原型修复回写

新增故事已按场景而非界面控件表达：用户从项目或群聊进入同一项目上下文，查看整体/阶段流程并下钻节点，识别并行与 Gate 状态，访问关联群聊和成员目录，并在跨端或恢复后继续阅读可信状态。

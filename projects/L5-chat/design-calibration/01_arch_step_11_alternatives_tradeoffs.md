## 2. SOP 问题回答

### 2.1 当前架构主线方案是什么？

当前主线是“共享客户端语义 core + 平台 shell 适配 + `L0-sdk` 唯一业务接入 + owner-safe 只读材料 + 显式结果/恢复状态”。V1 先以 Desktop 作为主要验证承载，Web/Mobile 复用语义边界并作为后续扩展面；客户端只拥有局部体验事实、草稿、选择、恢复和展示缓存，不拥有任何领域 truth。

### 2.2 哪些相邻替代路径值得比较？

本 Step 比较六条会改变主线结构的路径：

1. 直接连接各 owner 与经 SDK 正式接入。
2. 直接暴露 owner truth 与 owner-safe 只读材料。
3. 单一平台专用客户端与共享语义 core + shell 分离。
4. 自研完整客户端基础设施与共享语义 core + 成熟开源承载载体。
5. 全部同步闭环与同步/异步/后台混合承接。
6. 离线可执行业务与离线展示/草稿/恢复限定。

这些都是路径级替代，不是 React 与其他 UI 库、某个状态库与另一个状态库、某个协议与另一个协议的局部比较。

### 2.3 当前选择牺牲了什么，换来了什么？

主线牺牲了初期“直接接入、立即显示、离线可操作、平台特化和一步到位”的表面速度，换来 owner truth 不被复制、SDK 合同集中、跨端语义一致、失败可解释、unknown 不误重放和后续演进可控。它也接受更多映射、状态轴、恢复、清理和可访问性维护成本。

## 3. 历史材料与边界污染诊断

| 历史表达 | 污染风险 | 本 Step 处理 |
|---|---|---|
| “最快方式是各页面直连六域 API” | 把短期接入速度放在 truth/授权边界之前。 | 不采用直连，选择 SDK-only 正式接入。 |
| “把 owner DTO 直接作为前端模型” | 下游反向绑定 owner 内部结构，客户端形成第二真相。 | 采用 safe view/ref/summary/preview 的只读消费面。 |
| “Desktop/Web/Mobile 各做一套” | 平台分叉造成状态、授权和结果语义漂移。 | 采用共享语义 core + shell 分离，Desktop-first 交付范围。 |
| “为控制依赖自研窗口、渲染和协议全栈” | 将产品核心资源消耗在非 Chat 业务差异，延迟可落地验证。 | 采用自有语义 core，基础承载优先使用成熟开源载体；具体载体后置。 |
| “所有状态都同步返回” | 把正式事实传播和延后结果强压进入口，制造伪一致。 | 采用同步/异步/后台混合承接。 |
| “离线也允许审批和重试” | unknown 下重复副作用，缓存延长授权。 | 只采用离线展示、草稿和恢复，业务副作用在线且需正式结果。 |

## 4. 方案路径比较表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 直接连接各 owner，客户端自行组合协议 | 缩短初期接入路径，让页面快速获得各域数据和动作。 | 早期样例接入快，局部页面可少一层映射。 | 绕过 SDK 的授权、redaction、错误、幂等和恢复边界；owner DTO/协议扩散到核心，容易形成私有 API 和多份 truth。 | 不采用 | 该路径与 SDK-only 和全局依赖规则冲突，短期速度不足以抵消长期边界失稳。 |
| 经 `L0-sdk` 的正式接入，Chat 只消费 safe view/ref/result/change | 集中跨域接入、授权、错误和变化恢复边界。 | owner truth 不被复制；SDK 可统一 redaction、retry、resume、receipt 和 unknown；后续 owner 演进对 Chat 影响较小。 | 增加 SDK 合同等待、接缝映射和 blocker；exact surface 未闭合时正向能力不能宣称 ready。 | 采用 | 这是当前唯一与 Chat 职责、全局依赖和安全边界同时一致的主线。 |
| 直接暴露 owner truth 给客户端 | 减少 view/ref 承接层，让客户端直接使用正式对象。 | 初期模型简单，读取路径表面扁平。 | 客户端绑定内部生命周期、正文、权限和版本链；容易反写或形成第二真相，跨 owner 组合会失去清晰归属。 | 不采用 | Chat 需要产品显化而非领域真相暴露；只读 safe projection/ref 更符合数据和演进边界。 |
| owner-safe 只读材料 + provenance/freshness + 受控入口 | 在不转移 truth 的情况下支持跨域显示、预览和动作入口。 | 来源、visibility、新鲜度和降级可解释；Artifact/治理/Workspace 等边界保持独立；适合最终一致。 | 需要处理 stale/partial/unavailable/blocked；跨域卡片不能只靠本地推断完整生命周期。 | 采用 | 这是当前主线的消费面结构，牺牲部分“看起来总是完整”的体验换取可审计和可恢复。 |
| 单一平台专用客户端语义 | 先把一个平台做到高度特化，减少跨端抽象。 | 可利用平台原生能力，早期交互路径可能更短。 | Web/Mobile 后续需要重写语义；状态、授权、恢复和可访问性容易平台分叉；Desktop 选择会锁定产品模型。 | 不采用 | V1 Desktop-first 是范围顺序，不是业务语义专属；共享 core + shell 分离保留后续扩展。 |
| 共享客户端语义 core + 平台 shell 适配 | 在不同宿主保持同一业务状态、授权和结果解释。 | 可复用 view model/store/reducer/安全规则；平台能力差异被限制在 shell；Desktop 可先验证。 | 需要定义宿主能力边界、等价可访问路径和跨端兼容矩阵；某些平台特性不能直接复用。 | 采用 | 主线接受跨端抽象成本，换取业务语义不漂移；具体 shell 载体仍待后续确认。 |
| 自研完整渲染、窗口、存储和跨端基础设施 | 最大化平台控制和定制能力，减少对外部载体约束。 | 可从底层统一所有宿主行为，长期理论控制面较大。 | 研发面远超 Chat 业务差异；安全、可访问、分发、恢复和平台兼容风险集中到本项目；延迟验证核心协作体验。 | 不采用 | 本项目自研的是 Chat 语义和边界，不自研整个客户端基础设施；承载技术优先使用成熟开源路径。 |
| 共享语义 core + 成熟开源承载载体 | 把资源集中到客户端体验、状态和 SDK 边界，利用已有宿主能力。 | 更快验证 Desktop-first 主线，减少窗口/输入/分发等非核心工作；保留替换 shell 的可能。 | 引入开源项目生命周期、平台限制和安全审查成本；需要明确不让载体改写业务语义。 | 采用 | 这是对“自研还是开源”的架构级回答；具体项目选择进入后续技术/方案确认，不在本 Step 锁定。 |
| 全部跨边界状态同步闭环 | 让每次变化都在当前入口立即返回，追求即时完整感。 | 页面反馈直接，部分简单场景容易理解。 | 把事实传播、结果回送、恢复和延后任务压入同步边界；高耦合、长等待、伪一致和失败恢复复杂。 | 不采用 | 仅安全判断、当前 view 读取和意图接收需要同步；正式变化采用异步，恢复采用后台承接。 |
| 同步请求 + 异步事实传播 + 后台恢复/探测 | 按交互性质分别承接即时判断、正式变化和延后收敛。 | 与数据 ownership、一致性和失败姿态匹配；支持 unknown、gap、reconnect 和局部降级。 | 需要多轴状态、关联正式结果、恢复逻辑和用户解释；测试切口更多。 | 采用 | 这是当前通信主线，避免把 transport 成功当业务成功。 |
| 离线允许业务副作用并自动重放 | 在断网时继续发送、审批或推进工作，追求离线完整性。 | 离线体验表面连续，网络恢复后可能减少用户等待。 | 无法安全判断授权、版本和副作用是否已成立；unknown 重放可能重复发送/治理，缓存可能延长可见性。 | 不采用 | V1 只允许离线展示、草稿和恢复；业务副作用需正式在线边界和结果。 |
| 离线展示/草稿/恢复，副作用保持 pending/unknown | 支持断线和重启的用户连续性，同时不伪造 owner 成功。 | 安全边界清楚；可解释地恢复或等待；不把本地状态变成业务 truth。 | 离线期间不能提供完整业务操作；用户需要接受 pending/needs-action/unknown。 | 采用 | 与 Chat-owned 数据范围、fail-closed 和结果门控一致。 |

## 5. 取舍对照

| 当前主线得到的能力 | 主线主动放弃或延后 | 取舍原因 |
|---|---|---|
| owner truth 单一来源、SDK 合同集中、safe projection 可回链 | 页面直连和任意 owner DTO 的短期便利 | 防止客户端成为跨域第二真相。 |
| Desktop-first 快速验证共享协作体验 | 为单个平台深度特化全部业务语义 | 保留 Web/Mobile 的语义扩展路径。 |
| 开源承载载体可替换、产品核心自有 | 自研完整窗口/渲染/分发基础设施 | 将复杂度集中在 Chat 独有价值上。 |
| 同步/异步/后台各司其职 | 所有结果在一次同步交互内收口 | 避免伪一致和长同步边界。 |
| 离线展示、草稿和恢复安全可解释 | 离线审批、自动重放和离线业务完成 | 保护授权、幂等和副作用边界。 |

## 6. 方案边界说明

本章比较的是会改变 Chat 主线边界、数据 ownership、通信承接或跨端演进的路径；具体 React 与其他 UI 库、Tauri 与其他 shell、状态库、存储引擎和传输协议属于后续技术载体或实现选择，不构成独立架构路径。认证实现、Runtime/Tools 执行、外部平台桥接和 Observability backend 已由前文边界明确排除，不再包装成“被放弃方案”。性能数字、兼容矩阵、SDK exact surface 和持久化上限缺少 authority，继续作为 blocker，不通过方案偏好补齐。

## 7. 当前选择结论

### 7.1 主线架构

采用共享客户端语义 core、平台 shell 适配、`L0-sdk` 唯一业务接入、owner-safe 只读材料、同步/异步/后台混合承接、结果门控和受限离线恢复。V1 以 Desktop-first 验证完整协作入口、草稿、发送/重试、GateCard、Artifact 引用/预览、变化消费和恢复连续性；Web/Mobile 只保留共享语义扩展面。

### 7.2 自研与开源的边界

Chat 自研产品语义、页面体验、状态模型、reducer、view model、SDK adapter 边界和安全/可访问语义；客户端窗口、渲染宿主、系统通知、分发和平台适配优先采用成熟开源承载路径。该结论不指定具体项目，也不宣称已有实现或 readiness；载体选择需在后续技术与风险审查中确认。

### 7.3 明确放弃的路径

不采用 owner 直连、核心 truth 直曝、每平台独立业务语义、自研整套基础设施、全同步闭环、离线副作用自动重放、Chat 聚合后端、内部 bus 直订和客户端持有外部正文等路径。

## 9. 正式回填草稿

### 9.1 §12 备选方案与取舍

`L5-chat` 采用共享客户端语义 core、平台 shell 适配和 `L0-sdk` 唯一业务接入的主线。它通过 owner-safe 只读材料、来源/新鲜度标记、结果门控和同步/异步/后台混合承接，把客户端体验与外部 owner truth 分开；V1 Desktop-first 只是交付顺序，不建立平台专属业务语义。具体承载优先采用成熟开源路径，自研集中在 Chat 独有的产品语义、状态、边界和安全/可访问体验。

相邻路径中，直接连接 owner、直接暴露 truth、每平台独立语义、自研完整基础设施、全同步闭环和离线副作用自动重放均不采用，因为它们会破坏 SDK-only、数据 ownership、结果门控、跨端一致和 unknown 安全边界。主线牺牲了直接接入、离线完整操作和平台特化速度，换取单一真相、可解释降级、可恢复连续性和后续演进空间。具体 React/Tauri/Capacitor、状态库、存储库和传输协议仍不是本 Step 的正式结论。

### 问题回答与旧材料诊断

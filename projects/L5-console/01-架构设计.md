## 1. 业务背景与驱动力

### 1.1 业务背景

Console 是 Quantalithos 的组织级治理前台。它不是 Chat 的放大版,也不是简化版 BI 仪表盘,而是把 identity、work、governance、observability、method-library、capability-hub 等多域能力编织成**管理者、合规官、方法论制定者与审计角色的共同操作台**。如果 Chat 负责让用户“跟 AI 团队一起做事”,那 Console 负责让组织“看清楚这支 AI 团队是怎么被配置、被约束、被衡量、被审计的”。

### 1.2 业务驱动力

**业务驱动力**:
- 企业与组织级用户需要一个明确的治理入口,而不是在聊天流里完成所有管理操作
- 42001 管理评审、SoA/AIIA 维护、审计回放、能力池管理都需要高密度、结构化、可导出的界面
- 管理者需要跨项目、跨员工、跨方法资产看到系统整体健康度与风险分布

**技术驱动力**:
- 需要整合多域查询与 drill-down,但不能在前端复制业务真相
- 需要围绕 observability 与 governance 提供可追钻、可过滤、可导出的高密度界面
- 需要把能力池、方法库、治理资产统一组织成明确的信息架构,而不是零散页面堆叠

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 响应性 | 主列表/主看板首屏 | < 2s | RUM / Web Vitals |
| 响应性 | 审计过滤查询 P95 | < 500ms | benchmark |
| 可用性 | Console 关键路径可用率 | ≥ 99.9% | 监控 |
| 交互 | SoA 38 控制项视图完整度 | 100% | E2E |
| 审计 | 管理操作留痕覆盖率 | 100% | 回归测试 |
| 可视化 | DORA / EBM 核心指标可见 | 8 个指标 | dashboard test |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| Console 是治理视角,不能承担日常协作主入口 | `产品矩阵.md` §4.1 | 信息架构必须与 Chat 明确分工 |
| SoA 页面必须覆盖 38 控制项 | governance 仓 + README | 控制项矩阵是硬性模块 |
| 所有管理操作必须留痕 | README + 三红线 | 前端操作流必须连接审计链 |
| 哈希链完整性必须可验证且可导出 | observability 仓 | 审计页必须支持验证与报告 |
| 端侧产品必须经 SDK 访问服务 | sdk-draft / 产品矩阵 | 页面层不能直连私有接口 |
| 权限模型必须显式 | README | 不允许靠“按钮消失”模糊权限边界 |

### 2.2 可变约束

| 约束 | 当前值 | 可调整空间 |
|---|---|---|
| 前端框架 | React / Svelte 候选 | 最终按 L5 统一栈确定 |
| 图表库 | ECharts / D3 候选 | 可按指标复杂度调整 |
| 多租户切换 | 预留,不一定首批完整实现 | 企业版可增强 |
| RBAC 页范围 | 首批可先可视化后编辑 | 后续增强 |
| 导出包形式 | 报告 / JSON / zip 候选 | 可按审计需求扩展 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| 审计查询延迟 | < 500ms | observability 目标 |
| SoA 控制项 | 38 | 42001 Annex A |
| dashboard 核心指标 | 8+ | DORA / EBM / README |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 治理面板种类增加 | 中高 | 页面模块化 + domain-oriented feature slices |
| 指标/图表需求变化 | 高 | dashboard widget registry |
| 多域 drill-down 路径变化 | 中 | query adapters + navigation contracts |
| 多租户/组织能力演进 | 中 | org scope / tenant scope 预留 |
| 权限模型变化 | 中高 | policy-aware front-end guards |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **domain-oriented admin console + shared governance core**(当前) | 贴合多域治理、利于扩展 drill-down 与审计流 | 初期模块较多 | ✅ |
| 单页大表单/大看板系统 | 起步快 | 模块边界混乱、权限难控 | ❌ |
| 每个治理面板独立小应用 | 团队并行性高 | 体验割裂、导航割裂 | ❌ |
| 纯报表中心 | 实现轻 | 无法承载操作与治理闭环 | ❌ |

**最终选择**:**按治理能力分区的单一 Console + 共享状态/权限/审计核心**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 按域/能力分区组织界面 | 用户心智清晰,便于 drill-down | 首页信息架构设计更重 |
| 共享治理核心(权限/审计/导航) | 操作行为一致、避免权限漂移 | 抽象层增加 |
| dashboard/widget 可注册化 | 指标面板可扩展 | 首期实现比写死页面更复杂 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```text
管理者 / 合规官 / 方法制定者 / SRE / Auditor
                        │
                        ▼
               ★ quantalithos-console ★
               - members / projects / governance
               - audit / metrics / capability-hub
               - method-library / management review
                 │         │           │
                 │         │           └────────▶ observability(queries / verify / metrics)
                 │         └────────────────────▶ governance / capability-hub / method-library
                 └──────────────────────────────▶ sdk(core auth + queries)
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 提供组织级管理与治理入口
- ✅ 聚合多域状态,做 drill-down、过滤、对比和导出
- ✅ 承载 SoA/AIIA/Nonconformity/Policy/Gate 的管理视图
- ✅ 提供审计回放、哈希链验证、指标看板与能力池管理

**不做什么**:
- ❌ 不承载日常项目协作与对话主流
- ❌ 不持有业务真相,不在前端复制后端规则引擎
- ❌ 不做代码编辑、部署执行或工具调用
- ❌ 不替代外部 GRC/BI 平台的全部能力

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| governance APIs | 99.9% | SoA/AIIA/Gate 面板不完整 | 只读回退 / skeleton |
| observability APIs | 99.95% | 审计/指标/哈希页不可用 | 局部禁用 + stale summary |
| identity/work/process APIs | 99.9% | 成员与项目大盘不完整 | 局部降级 |
| capability-hub APIs | 99.9% | 能力池页缺数据 | 只读摘要 |
| artifact refs | 99.9% | 证据 drill-down 不完整 | metadata 占位 |

### 4.4 关键依赖风险

- 多域查询结果若缺乏统一导航与 drill-down 规则,Console 会变成页面堆砌而非治理中枢
- 权限模型若在前端被局部特判,会产生“看得到但不该看”或“看不到但该看”的治理风险
- 审计与指标页若只给高层数字而无法追钻原始证据,管理评审会退化成静态报表

- method-library / capability-hub → Method Administration / Capability: **Conformist + Projection**
- artifact → ExecutionTrace / Governance / Audit: **Evidence Projection**，Console 只读展示 implementation-plan、evidence 与 lineage

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```text
browser SPA
    │
    ▼
console shell
  ├─ shared app core
  ├─ feature slices(members/projects/governance/audit/metrics/capability)
  ├─ sdk adapters
  └─ export/report helpers
        │
        ▼
   Quantalithos SDK
        │
        ▼
identity / work / process / governance / observability / capability-hub / artifact
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| console shell | 路由、认证、导航、会话壳层 | TypeScript + React/Svelte SPA | 浏览器主壳 |
| shared governance core | 权限、导航、审计与导出共用逻辑 | TypeScript | 共享逻辑 |
| feature slices | members/projects/governance/audit/metrics/capability 页面群 | TypeScript | 按域拆分 |
| sdk adapters | 与各域服务交互 | TypeScript SDK | 统一契约层 |
| export helpers | 报告/导出辅助 | TypeScript | 辅助能力 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 常规治理查询 | SDK RPC / HTTP | 页面直连服务 | 统一契约、统一 auth |
| 审计/指标 drill-down | query APIs + 分页/过滤 | 拉全量前端过滤 | 控制体量与权限 |
| 导出报告 | 受控后端导出 + 前端触发 | 前端全量拼装 | 降低敏感数据暴露 |
| 跨面板共享状态 | shared store / app core | 每页独立状态 | 保证权限和导航一致 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| 组织治理真相 | 各后端服务 | console |
| 本地布局/筛选状态 | console client | console client |
| 导出任务状态 | 后端服务 / export backend | console |
| 权限可见性视图 | governance/auth backend | console |

### 6.5 部署拓扑

- Console 作为单独 Web SPA 部署
- 不自带专属后端中间层,通过 SDK 直连 Server
- 若后续企业版需要,可增加专门 export/report adapter 层,但不作为首期前置

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```text
router / shell
     │
     ▼
shared governance core
     │
     ├─▶ feature slices
     └─▶ sdk adapters
             │
             ▼
        server truth
```

### 7.2 层间约束规则

- feature slices 只消费 shared governance core 与 SDK adapters,不直接访问原始 transport
- 审计页不自行推断治理语义,只基于 observability / governance 返回的结构化对象
- 方法库与能力池面板不复制后端校验逻辑,只展示与触发操作
- 权限判断必须集中,不能散落在任意组件内硬编码
- 导出能力必须走受控路径,不能靠前端拼出敏感全量数据

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| GovernanceDataAdapter | shared core | SDK-backed governance adapter |
| AuditQueryAdapter | shared core | observability SDK adapter |
| CapabilityAdminAdapter | shared core | capability-hub SDK adapter |
| ExportAdapter | shared core | export/report adapter |
| PermissionResolver | shared core | auth/governance-backed adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 高(治理主入口) |
| 传出耦合 | 高(identity/work/process/governance/observability/cap-hub/artifact) |
| 不稳定性 | 中 |
| 抽象度 | 中高(shared governance core 统一约束) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Member lifecycle truth | identity | members UI | 最终一致 | stale profile view |
| Governance truth | governance | governance UI | 最终一致 | 错误缓存 |
| Audit / metrics truth | observability | audit/metrics UI | 最终一致 | 延迟回放 |
| Capability truth | capability-hub | capability UI | 最终一致 | 状态漂移 |
| 本地视图状态 | console client | console client | 本地强一致 | 可重建 |

### 8.2 一致性层次

- 后端领域对象真相全部来自 L1/L3/L4 服务,Console 只做最终一致投影
- 页面局部筛选、导航、布局状态由客户端本地强一致维护
- 导出/验证动作属于“触发后等待后端结果”的异步一致模型

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| 审计过滤查询失败 | 下游不可用 | 返回可恢复错误 + 保留当前筛选条件 | `query_id` |
| SoA/AIIA drill-down 失败 | artifact/observability 局部异常 | 显示受限/缺失状态并允许重试 | `soa_id` / `aiia_id` |
| 管理操作提交成功但列表未刷新 | 最终一致延迟 | optimistic state + refresh/poll | `operation_id` |
| 导出任务失败 | 后端导出异常 | 失败状态回写 + 可重试 | `export_job_id` |

| 维度 | 内容 |

| 选择理由 | 契约、权限、认证、重试语义都应统一 |
| 演进路径 | SDK 可扩治理/观测 helpers |
| 不可逆程度 | 高 |

### 9.3 dashboard widget registry

| 维度 | 内容 |
|---|---|

| 不可逆程度 | 中 |

### 9.4 drill-down first 信息架构

| 维度 | 内容 |
|---|---|
| 当前选择 | 概览页 + drill-down 到原始证据 |

| 不可逆程度 | 中 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:单一 Console + 共享治理核心(当前) | 方案 B:多独立后台 | 方案 C:报表中心 |
|---|---|---|---|
| 治理连贯性 | 高 | 中低 | 低 |
| 审计可追钻 | 高 | 中 | 中 |
| 实施复杂度 | 中 | 中高 | 低 |
| 用户心智 | 高 | 低 | 中 |
| 长期扩展性 | 高 | 中 | 低 |

### 10.2 最终选择与理由

选择 A,因为 Console 的核心不是“展示多个后台模块”,而是为组织提供一个统一的治理与证据入口。B 会造成导航和权限割裂；C 则只剩“看图”,不能真正承担管理与审计操作。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 重试 | 查询/导出/验证失败时支持显式重试 |
| 降级 | 某域不可用时局部降级,不拖垮全台 |
| 隔离 | 成员、治理、审计、能力池、指标等 feature slice 隔离 |
| 恢复 | 用户刷新后恢复关键筛选与导航状态 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | 管理操作、审计查询、hash verify、导出动作 |
| 指标 | 首屏耗时、查询耗时、导出成功率、权限拒绝率 |
| trace | 前端操作 → SDK → governance/observability 等后端链路可关联 |
| 健康检查 | 关注各主要面板依赖的 error budget |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| 认证 | 统一 SDK auth |
| 授权 | 权限矩阵显式显示与集中校验 |
| 审计 | 所有敏感管理动作进入审计链 |
| 数据最小暴露 | 前端不缓存超出权限范围的敏感全量数据 |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | feature enable、dashboard presets、export strategies 外部化 |
| 环境隔离 | staging/prod/tenant scope 可切换配置 |
| 动态更新 | 指标 widget、实验性治理面板可灰度 |
| 配置五要素 | type / default / source / scope / constraints 明确 |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| 主列表/主看板首屏 | < 2s | RUM / Web Vitals | 管理效率主路径 |
| 审计过滤查询 | < 500ms | benchmark | observability lineage 目标 |
| 哈希链验证反馈 | 用户可等待且结果明确 | E2E | 审计主路径 |
| SoA 控制项视图 | 38 控制项完整可见 | E2E | governance 约束 |

**端到端交付分解**(管理者打开治理面板并 drill-down 到证据):

```text
概览页进入
 + 过滤/定位目标对象
 + 查看治理状态
 + drill-down 到原始证据
 + 可导出/验证结果
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| 多租户切换能力未定 | 企业版范围 | P1 |
| 管理评审自动化程度未定 | 42001 工作流体验 | P1 |
| RBAC 页面是否首批可编辑未定 | 权限治理深度 | P1 |
| 导出包格式未定 | 审计对外交付体验 | P2 |

### 12.2 触发条件(可量化)

| 指标 | 阈值 | 动作 |
|---|---|---|
| 首屏 > 2s | 持续 1 周 | 做更细粒度按域分包/缓存 |
| 审计查询 > 500ms | 持续 1 周 | 强化 query projection / cache |
| 权限误配置或拒绝异常 | > 阈值 | 收紧 PermissionResolver 与 UI guards |
| dashboard 需求持续增长 | > 2 个 Sprint | 增强 widget registry / 自定义组合 |

### 12.3 演进步骤

```text
阶段 1: 员工/项目/治理/审计四主面板跑通
   └─ 可停止点:管理与合规核心路径可用

阶段 2: 指标大盘 / 能力池 / 导出与管理评审增强
   └─ 可停止点:组织级治理闭环成立

阶段 3: 多租户、权限编辑、高级报表与企业增强
   └─ 可停止点:企业版治理面板成熟
```

### 12.4 目标架构

Console 的目标架构不是“后台管理页集合”,而是 **组织级 AI 治理操作系统前台**:用户在这里管理员工、方法、风险、能力与证据,并始终能 drill-down 到真实责任链。未来再扩功能,也必须围绕“治理视角 + 审计证据 + 管理效率”三条主线,不能变成另一个聊天产品或松散报表站。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 信息架构过重导致上手困难 | 中 | 高 | 以管理评审与高频任务为主导航 |
| 权限边界出错 | 低 | 极高 | 集中权限解析 + 回归测试 |
| 审计/指标页仅给摘要不给证据 | 中 | 高 | drill-down first 设计 |
| 多域查询延迟高 | 中 | 高 | projection / cache / 局部懒加载 |

### 13.2 边缘风险

- 多租户/多组织切换引入额外权限与过滤复杂度
- 导出审计包包含过多敏感信息,对外交付风险上升
- 能力池与方法库交叉过深,造成治理模型被误解

### 13.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 多租户/组织切换是否进入首批 | 批次 6 内 | Console + Product |
| 管理评审自动化程度 | 批次 6 内 | Console + Governance |
| 审计导出包格式与颗粒度 | 批次 6 内 | Console + Audit |
| RBAC 首批是否只读可视化 | 批次 6 内 | Console + Governance |

## 14. 上线策略

### 14.1 灰度方案

```text
阶段 1: members / projects / governance / audit 四大面板先上线
阶段 2: SoA/AIIA/指标与能力池页接入
阶段 3: 管理评审与导出能力增强
阶段 4: 视企业需求扩多租户与高级权限页
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| 权限错误暴露敏感数据 | S 级 | 立即关闭相关面板或功能入口 |
| 审计回放/哈希校验结果错误 | S 级 | 停止该功能展示,回退到只读摘要 |
| 主管理路径不可用 | A 级 | 回退相关 feature slice 版本 |
| dashboard 误导性指标展示 | B 级 | 暂停对应 widget,保留其他能力 |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| 主看板首屏 | > 2s | warning |
| 审计过滤查询 | > 500ms | major |
| hash verify 失败率 | > 阈值 | critical |
| 权限拒绝异常 | > 阈值 | security |
| 导出失败率 | > 阈值 | warning |

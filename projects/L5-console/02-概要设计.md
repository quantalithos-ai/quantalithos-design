## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L5-console` 不是 source truth 仓,也不是单一功能页面仓,更不是纯组件集合。它是 **“平台控制台 / 工作台产品层”**。

你可以把它理解成:
- 用户、owner、operator、TL 怎样进入统一工作台
- chat、member、runtime、artifact、observability、capability、archive 等多个能力面怎样被组织成统一控制台体验
- 导航、面板、视图切换、上下文联动、操作入口、状态提示怎样协调
- 平台多个产品面怎样在 console 中形成统一的“工作台心智”,而不是若干孤立页面拼接

这些事情,都由 `L5-console` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L5-console`,这些工作台事实就会散落在:
- `chat` 各自的 thread/entry 页面里
- `runtime` 各自的状态与任务页里
- `artifact` 各自的结果页和列表页里
- `observability` 的 dashboard 与诊断页里
- `archive` 的冷查询与复盘页里
- 各种 panel、tab、breadcrumb、jump 行为和工作流快捷入口里

结果就会出现:
- 平台对用户来说只是多个页面拼盘,而不是统一工作台
- 同一上下文在不同面板之间无法稳定联动
- 用户必须理解底层系统边界才能完成操作
- panel state、quick action、summary view 各自一套口径
- 控制台看起来很全,但不能稳定承接真实工作流

所以 `L5-console` 必须独立存在,作为:
> **把 chat、runtime、artifact、observability、archive、capability 等多个产品面组织成统一、可导航、可切换、可协同的控制台工作台层。**

### 1.3 新人最容易混淆的几个词

#### ConsoleWorkspace
就是:
> 用户在平台中看到并操作的一段统一工作台上下文。

它不是任何一个业务域的正式真相本体。

#### PanelState
就是:
> 某个面板当前的展开、切换、过滤、选中或聚焦状态。

它不是业务状态真相。

#### CrossPanelContext
就是:
> 多面板之间共享的上下文联动信息,如当前 thread、当前 artifact、当前 execution。

它不是多个源系统共享的一份真相状态。

#### ConsoleActionEntry
就是:
> 用户在工作台里看到的快捷操作入口或命令入口。

它不是动作真正执行成功的真相。

#### UnifiedDashboard
就是:
> 工作台中统一展示的多域观察面。

它不是 unified source model,也不意味着底层多个真相已经合一。

#### PermissionHint
就是:
> 控制台给用户的可见性、只读、无权限、受限等提示。

它不是 authorization truth 本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L5-console/02` 时,先收稳以下前提:
- `L5-console` 不应按左侧导航、顶栏、表格、面板等纯布局组件平铺理解,而应按统一工作台体验主链责任拆
- console 至少应拆成“工作台入口与全局导航 / 多面板组织与上下文联动 / 操作入口与工作流辅助 / 统一视图消费与摘要呈现 / 状态提示、权限反馈与个性化工作台”五个主要部分
- console 自己拥有的真相不是 chat truth、runtime truth、artifact truth、observability truth 或 archive truth,而是 workspace UX、panel orchestration、action entry、unified view、permission/feedback/workspace preference 这类工作台层真相
- `L5-console` 只能为用户和操作者提供统一工作台,不能反过来替 source systems 持有正式领域真相
- 02 的重点不是“列有哪些页面和面板”,而是先把“console 工作台层在平台里到底是什么、和 chat/member/runtime/artifact/observability/archive/capability-hub 怎么分层”讲清楚
- global nav、cross-panel context、quick actions、dashboard cards、permission hint、workspace preference 这些不是零散交互点,而是 console 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的统一工作台心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,用户面对的不应是一堆独立页面。用户真正需要的不是“知道去哪个仓看什么”,而是:
- 在同一个工作台中进入 chat、runtime、artifact、observability、archive、capability 等多个能力面
- 在一个 panel 中选中的对象能带动其他 panel 合理切换
- 面板切换、快捷操作、上下文跳转、诊断提示、历史查看都围绕同一工作流展开
- 不需要理解 source systems 的内部边界,也能完成多域协作和运维动作

如果把这些逻辑分别散落到:
- chat 独立入口
- runtime 独立页面
- artifact 独立列表与详情
- observability 独立 dashboard
- archive 独立 query 页面
- 各种手工拼出来的跳转、tab、面板联动逻辑

系统会快速退化成:
- 平台体验像多个工具集合,不是工作台
- 同一任务在多个页面之间割裂
- 用户必须自己在脑中完成跨系统关联
- panel state、上下文联动和操作入口极易漂移

因此,本概要设计的任务就是:
> **把 `L5-console` 写成一个新人也能看懂的“统一控制台 / 工作台产品层”,而不是把多个页面拼到同一个外壳里。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 工作台统一入口 | 多页面入口分散 | 单一 workspace entry | 需正式收敛 |
| 跨面板上下文联动 | 易漂移 | 统一 cross-panel context 主线 | 需明确共享边界 |
| 多域操作可理解性 | 依赖用户理解系统边界 | 控制台内可完成主要工作流 | 需形成统一工作台心智 |
| 状态提示与权限解释 | 来源分散 | 统一 status / permission explain 层 | 需正式收口 |
| 个性化工作台 | 缺少正式模型 | workspace preference / saved layouts | 需成为正式能力 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把多个平台能力面组织成统一、连贯、可切换、可操作的控制台体验,而不是让用户自己在多个子系统之间穿梭
- **技术问题**:ConsoleWorkspace、PanelState、CrossPanelContext、ConsoleActionEntry、UnifiedDashboard、PermissionHint 与 chat / runtime / artifact / observability / archive / capability-hub 之间的边界如何稳定建模,并形成统一工作台主链

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 console 的工作台职责 | workspace / panel / action / summary / permission 职责无歧义 | 文档评审 |
| 明确与 chat / runtime / artifact / observability / archive 边界 | workspace state 与 source truth 分离 | 文档评审 + 后续测试 |
| 明确统一工作流主线 | 入口、联动、操作、摘要、反馈在同一心智下成立 | 设计评审 + 集成测试 |
| 支撑后续详细设计与测试 | 本文足以承接 `03-详细设计.md` 的 workspace UX、panel orchestration、action UX 设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文替代 chat / runtime / artifact / observability / archive 的 source truth
- 不在本文实现共享 UI 组件库本体
- 不在本文替代 authorization 真相或 source policy 真相
- 不在本文定义全部 analytics / growth / BI 能力
- 不在本文实现所有自动化运维命令本体

## 4. 约束条件

### 4.1 技术约束

- workspace、panel、quick action、summary、permission hint 必须始终能回指 source refs
- panel state 与 selection context 只能表达 UX 层状态,不能冒充业务真相
- unified dashboard 只能消费 source 视图,不能反写源仓
- console action entry 只能发起入口,不能冒充执行成功真相
- 个性化布局和偏好不能污染正式领域状态

### 4.2 资源约束

- 多 panel 并发、跨面板联动、频繁上下文切换会持续增长,渲染与缓存复杂度必须受控
- 高频摘要与 dashboard 不能拖垮 source systems
- workspace preference、saved layouts、recent/pinned 状态不能无限膨胀

### 4.3 时间约束

- 当前阶段先收稳统一工作台主链,而不是先做复杂多租户协作空间、低代码编排或高级运营分析
- entry、panel orchestration、action entry、summary、permission/feedback 五条基础链必须优先稳定,否则后续控制台会长期碎裂

### 4.4 合规约束

- UI 层不得擅自改写 source truth
- permission hint 不能替代 authorization truth 本体
- dashboard / summary 不得冒充正式治理、执行、财务真相
- 导出/分享视图不得替代 archive 正式沉淀本体

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| open panels / workspace | 中高 | 多面板工作流需求 |
| cross-panel context updates | 高频 | 工作台联动要求 |
| dashboard cards / summary blocks | 高频 | owner/operator 工作台要求 |
| workspace preferences | 高 | 个性化工作台需求 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ chat / member / runtime     │
                    │ artifact / obs / archive    │
                    │ capability / summaries      │
                    └────────────┬───────────────┘
                                 │ console workspace input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-console                 │
                    │ - workspace / panels       │
                    │ - actions / summaries      │
                    │ - context / permissions    │
                    └────────────┬───────────────┘
                                 │ visible workspace output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ end users / operators      │   │ UI shell / navigation      │   │ feedback / analytics       │
│ - work / inspect / act     │   │ - container / layout       │   │ - usage summaries          │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L5-console` 自己负责统一工作台入口、面板组织、上下文联动、操作入口、状态/权限解释与个性化工作台主线
- `chat`、`member`、`runtime`、`artifact`、`observability`、`archive`、`capability-hub` 是 source truth 或 source result 提供方,但 console 不拥有它们的源真相
- 用户、owner、operator、TL 通过 console 消费统一工作台体验,而不是直接在多个系统页面之间跳转
- UI shell 负责容器与布局壳,但 console 负责工作台产品语义

所以 `L5-console` 在全局里的角色是:
> **把 chat、runtime、artifact、observability、archive、capability 等多个产品面组织成统一、可导航、可切换、可协同的控制台工作台层。**

### 5.3 系统边界

**做什么**:
- 管理 workspace entry / global nav / section switch
- 管理 panels / tabs / split views / context link
- 管理 quick actions / command palette / action entry
- 管理 unified summaries / dashboard cards / preview views
- 管理 permission hints / stale warnings / saved layouts / workspace preferences

**不做什么**:
- 不持有 chat / runtime / artifact / observability / archive 的 source truth
- 不直接执行 source actions 的成功状态推进
- 不替代 authorization 真相、source policy 真相或 analytics 本体
- 不替代共享 UI 组件库本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| chat | 99.9% | thread 面板失联时保留其他 panel 和 stale 标记 |
| runtime / artifact / obs / archive | 99.9% | 单个 panel 失联时保留工作台壳和跨面板上下文,不伪造数据 |
| capability-hub / member | 99.9% | 能力/成员面缺失时显示只读占位与权限说明 |
| UI shell | 99.9% | 壳存在即可保留 workspace state,子面可独立降级 |
| analytics sink | 99.9% | 行为统计延迟不影响工作台主流程 |

### 5.5 关键依赖风险

- workspace state 与 source truth 漂移会直接误导用户操作
- panel 联动若无稳定上下文,跨系统协作会断裂
- summary / dashboard 若被误当 source truth,会导致错误决策
- permission hint 若和真实授权不一致,会造成越权预期或错误阻断
- quick action 若被误当执行成功,会造成用户操作心智错位

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把导航、顶栏、表格、详情页等组件横向平铺。  
> 它按 **统一工作台体验主链职责 + 入口 / 联动 / 操作 / 摘要 / 权限差异** 来拆分。  
> 因此下面每一部分都可能包含多个交互对象和机制,共同支撑同一段 console 工作台主链。

#### 工作台入口与全局导航部分

- **它是什么**: 这是 `L5-console` 的主入口层,一起回答“用户怎样进入统一工作台”
- **为什么单独有它**: 没有统一 entry / nav,console 就会退化成多个页面集合
- **负责什么**:
  - 提供 workspace entry / global nav / app switch / section switch
  - 管理 recent/pinned/favorites 等工作台入口体验
  - 提供统一 global context shell
- **不负责什么 / 容易混淆点**:
  - 不持有 domain source truth
  - 不持有 authorization truth
  - 不负责 panel 内部具体业务逻辑
  - 最容易和路由、权限、业务对象真相混淆
- **与其他部分交互**:
  - 下游: 多面板组织、操作入口、统一视图、权限反馈
  - 外部: chat / member / runtime / artifact / observability / archive
  - 交互类型: entry 型 + global navigation 型
- **后续详细设计展开点**:
  - ConsoleWorkspace / global nav contract
  - recent/pinned/favorites 主线

#### 多面板组织与上下文联动部分

- **它是什么**: 这是 console 的工作台编排层,一起回答“多个能力面怎样在同一工作台联动”
- **为什么单独有它**: 这是 console 区别于普通页面集的核心能力,但又最容易和业务编排真相混层
- **负责什么**:
  - 管理 panels / tabs / split views
  - 管理 selection context / contextual drilldown / cross-panel linking
  - 管理 shared shell state
- **不负责什么 / 容易混淆点**:
  - 不持有业务状态真相
  - 不等于 runtime/process orchestration
  - 不负责 source object 状态推进
  - 最容易和 shared source state、business orchestration、domain lifecycle 混淆
- **与其他部分交互**:
  - 上游: 工作台入口与全局导航部分
  - 下游: 统一视图消费与摘要呈现、状态提示与权限反馈
  - 外部: chat / runtime / artifact / observability / archive
  - 交互类型: panel orchestration 型 + cross-context 型
- **后续详细设计展开点**:
  - PanelState / CrossPanelContext 模型
  - split view / drilldown 主线

#### 操作入口与工作流辅助部分

- **它是什么**: 这是 console 的操作驱动层,一起回答“用户怎样从工作台发起下一步动作”
- **为什么单独有它**: 工作台不仅是观察面,还是操作入口,但操作入口不等于动作本体成功完成
- **负责什么**:
  - 管理 command palette / quick actions / bulk actions / jump / handoff
  - 管理 create/open/inspect entry
  - 组织 workspace-level action UX
- **不负责什么 / 容易混淆点**:
  - 不等于 execution truth
  - 不替代 runtime/process orchestration
  - 不直接保证 source action 已成功
  - 最容易和 command execution、domain command、business workflow 混淆
- **与其他部分交互**:
  - 上游: 工作台入口与全局导航部分、多面板组织部分
  - 下游: 统一视图消费与摘要呈现、状态提示与反馈
  - 外部: chat / runtime / artifact / archive / operators
  - 交互类型: action entry 型 + workflow assist 型
- **后续详细设计展开点**:
  - ConsoleActionEntry / command palette / quick action 主线

#### 统一视图消费与摘要呈现部分

- **它是什么**: 这是 console 的多域结果消费层,一起回答“多域结果怎样被统一呈现”
- **为什么单独有它**: console 的价值在于统一工作台视图,但这里又最容易把 summary/dashboard 当成 source truth
- **负责什么**:
  - 渲染 cards / list / table / detail summaries
  - 渲染 health summary、artifact preview、archive/history、cost/capability snapshots
  - 组织 unified dashboard 和只读多域视图
- **不负责什么 / 容易混淆点**:
  - 不持有 source truth 本体
  - 不替代 chat / runtime / artifact / observability / archive 的正式真相
  - 不负责执行动作结果推进
  - 最容易和 unified source model、source summary truth、BI 层混淆
- **与其他部分交互**:
  - 上游: 多面板组织与上下文联动部分、source systems 输入
  - 下游: 状态提示、权限反馈与个性化工作台
  - 外部: users / owners / operators / console shell
  - 交互类型: unified read model 型 + summary render 型
- **后续详细设计展开点**:
  - dashboard card / summary view / preview contract

#### 状态提示、权限反馈与个性化工作台部分

- **它是什么**: 这是 console 的解释与个性化层,一起回答“系统怎样解释状态并支持个性化”
- **为什么单独有它**: 这决定 console 是否真正可用,但也最容易把可见性/个性化写成权限/真相/业务规则本身
- **负责什么**:
  - 管理 permission hint / readonly banner / stale warning
  - 管理 saved layouts / personalized panels / workspace preferences
  - 管理状态解释与反馈 surfaces
- **不负责什么 / 容易混淆点**:
  - 不等于 authorization truth
  - 不替代业务状态判断真相
  - 不替代 analytics 本体
  - 最容易和 auth policy、source health truth、user profile 真相混淆
- **与其他部分交互**:
  - 上游: 前四个主要部分
  - 下游: users / operators / analytics / personalization
  - 交互类型: permission explain 型 + personalization 型
- **后续详细设计展开点**:
  - permission hint / stale warning / saved layout 主线

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ chat / member / runtime     │
                    │ artifact / obs / archive    │
                    │ capability / summaries      │
                    └────────────┬───────────────┘
                                 │ console workspace input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-console                 │
                    │ - workspace / panels       │
                    │ - actions / summaries      │
                    │ - context / permissions    │
                    └────────────┬───────────────┘
                                 │ visible workspace output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ end users / operators      │   │ UI shell / navigation      │   │ feedback / analytics       │
│ - work / inspect / act     │   │ - container / layout       │   │ - usage summaries          │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L5-console` 自己负责“统一工作台入口”“多面板组织与上下文联动”“操作入口与工作流辅助”“多域摘要呈现”“权限/状态解释与个性化工作台”
- `chat`、`runtime`、`artifact`、`observability`、`archive`、`capability-hub` 的交互主要落在 **多面板组织与上下文联动部分** 与 **统一视图消费与摘要呈现部分**,为 console 提供多域只读视图输入
- `chat` / `runtime` / `artifact` / `archive` 的交互也会落在 **操作入口与工作流辅助部分**,为 console 提供 action entry 目标
- UI shell 是容器与布局承载方,而 console 负责产品语义和工作台编排
- 用户、owner、operator 通过 console 消费统一工作台体验和只读工作流组织面

### 7.3 分模块交互说明(逐个写)

#### 与 `chat` 的交互

```text
┌────────────────────────────┐
│ chat                       │
│ - thread / reply / hints   │
└────────────┬───────────────┘
             │ panel input
             ▼
┌────────────────────────────┐
│ console                    │
│ - chat panel / workspace   │
└────────────────────────────┘
```

- `chat` 是 **对话体验来源方**
- **交互类型**: panel input / summary input 型交互
- **主流程位置**: thread 选择、chat 面板切换、recent thread drilldown 时进入主流程
- **交互解释**:
  - console 组织 chat 面板和其摘要
  - 不持有 chat truth 本体
- **高风险异常流**:
  - console chat 面板状态漂移后被误当 chat source state
- 后续 `03-详细设计.md` 继续展开:
  - panel shell / thread context 主线

#### 与 `runtime / artifact / archive / observability` 的交互

```text
┌────────────────────────────┐
│ runtime / artifact / obs   │
│ archive / capability       │
│ - summaries / previews     │
│ - status / diagnostics     │
└────────────┬───────────────┘
             │ workspace input
             ▼
┌────────────────────────────┐
│ console                    │
│ - dashboard / detail views │
│ - contextual drilldown     │
└────────────────────────────┘
```

- 这些系统是 **多域工作台来源方**
- **交互类型**: summary / preview / diagnostic 输入型交互
- **主流程位置**: dashboard、detail、history、health、preview drilldown 时进入主流程
- **交互解释**:
  - console 汇总这些系统的只读视图
  - console 不反写其 source truth
- **高风险异常流**:
  - unified view 被误当 unified source model
- 后续 `03-详细设计.md` 继续展开:
  - cross-panel context
  - unified summary 主线

#### 与 `users / operators / owners` 的交互

```text
┌────────────────────────────┐
│ console                    │
│ - workspace / actions      │
│ - status / permission      │
└────────────┬───────────────┘
             │ workspace output
             ▼
┌────────────────────────────┐
│ users / operators / owners │
│ - inspect / act / navigate │
└────────────────────────────┘
```

- 这些系统和角色是 **工作台消费方**
- **交互类型**: workspace consume 型 + action entry 型交互
- **主流程位置**: nav、select、quick action、layout switch、context review 时进入主流程
- **交互解释**:
  - console 给出统一工作台和操作入口
  - 用户据此决定下一步
  - action entry 不等于动作已经执行成功
- **高风险异常流**:
  - quick action 状态被误认为 source action 已完成
- 后续 `03-详细设计.md` 继续展开:
  - action entry contract
  - status/permission explain 主线

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是工作台层、哪个模块是只读消费方、哪个模块是操作入口层

本节**不**展开:
- 具体 panel 布局和响应式细节
- command palette 求值算法
- saved layout 的前端状态管理细节
- dashboard 渲染引擎细节
- analytics 埋点细节

这些内容留到 `03-详细设计.md` 中继续展开。

## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收目标”“验收范围表”“Conditional positive 规则”“下游只验接缝”和“非范围与结论影响”，了解 P0 safety 与 positive integration 的分离方式。

### 2.1 验收目标

| 目标 | 裁决目标 |
|---|---|
| `AGO-CON-01` 可信语境与权限收紧 | protected view/intent 只受 current formal context、visibility 与 qualification 支配；本地只能收紧 |
| `AGO-CON-02` owner-safe 只读消费 | 16 Query 保留 owner/source/状态轴、严格空值语义且 write=0 |
| `AGO-CON-03` 受控意图 | draft/request/result phase 分层；唯一 owner write 有正式前置；ambiguous→`unknown` 且不 replay |
| `AGO-CON-04` 八管理主题安全组织 | owner partition、canonical composition、局部降级；不合成 approval/compliance/audit/readiness |
| `AGO-CON-05` 恢复与可访问等价 | subject-specific one-action recovery；视觉/键盘/辅助技术同 guard/input/outcome/ceiling |
| `AGO-CON-06` 架构、配置与证据真实性 | SDK-only、四配置/三 profile、固定 run、pair/digest/review 与 no-static-evidence 均成立 |

### 2.2 范围与优先级

| 范围项 | 类型 | 当前优先级 / 上限 | 裁决重点 |
|---|---|---|---|
| context/session/navigation/access | core client | P0 | fail-closed、旧 scope 清理、route/menu 不授权 |
| owner-safe views + 16 Query | read boundary | P0 | safe mapping、五轴保真、strict empty、zero-write |
| drafts + 5 Command | intent boundary | P0 safety；positive conditional | phase、single-flight、no replay；enabled 后 exact positive |
| eight management topics | composition | P0 safety；per-owner positive conditional | canonical partitions、partial isolation、诚实姿态 |
| recovery + semantic a11y | resilience | P0 | typed recovery ceiling、同 semantic action；具体兼容矩阵 selected |
| adapters / formal seams | runtime boundary | P0 safety；P1 positive | narrow Port、typed error、safe mapper；exact binding conditional |
| client state carrier | client state | P0 session | exact scope、whole record、single writer；当前 session-volatile |
| invalidation consumer | optional event seam | P0 disabled；P1 observed | disabled zero-write；enabled 后只单调收紧 |
| diagnostics | optional side path | P0 disabled/fake safety | whitelist、redaction、isolation；production sink conditional |
| config/profile | control plane | P0 | 恰好四项、三个 profile、strict/startup-only；profile≠readiness |
| architecture/absence | static | P0 | 十模块、5+16+1、0 Event/Job、唯一 owner write；无 service-side units |
| evidence integrity | adjudication support | P0 | fixed-run artifact/report pair、digest、review、no static pass |
| quantitative/browser/AT/production | selected | P2 / authority-required | authority 与 baseline 同时选择后才升级为门禁 |
| peripheral E01～E03 / L5/L6 links | future | P2 | 正式合同与双方停审后逐项启用；当前不进主链 |

### 2.3 Conditional positive 裁决

| Baseline 声明 | 必需安全姿态 | Positive evidence | 裁决上限 |
|---|---|---|---|
| facet 未启用或合同未闭口 | `disabled/read-only/partial/blocked`，且 no-call/no-fake | 不要求，也不得伪造 | 可满足当前 safety，不证明已集成或 ready |
| facet enabled 且 exact contract 固定 | 仍必须满足全部安全门禁 | contract-derived TC/EV instance 必需 | 缺失或失败即对应门禁失败 |
| facet enabled 但合同/证据缺失 | fail-closed / no call | 无合格 positive | 不得进入或不得通过 |
| controlled fake safety 通过 | 只证明客户端不变量 | 不替代 formal positive | 不产生 integration 或 production readiness |

### 2.4 非范围及对结论的影响

| 非范围 | 裁决处理 |
|---|---|
| owner 内部数据库、规则、projection、执行与完整 UI | 不验其内部实现；若 Console 依赖私有边界则触发 VETO/S |
| 尚未闭口的 exact owner/SDK positive surface | baseline 未启用时保持 conditional/residual；启用后缺失即失败 |
| 当前不存在的实现仓、CI、runner、environment | 阻断实际进入验收，不阻断本文合同停审 |
| 无 authority 的量化、具体 browser/AT、production diagnostics | 不给数值/兼容/生产 verdict；可作为候选 residual |
| 未停审 L5/L6 link | 保持 pending/disabled；不作主链、P0 positive 或 evidence |

任何 P0 safety、negative、semantic、static 或 evidence-integrity 红线失败，都不能由 selected/pending/future 状态、其他 owner 成功或外围体验抵消。

## 3. 验收基线

> 校准来源：
> - `design-calibration/06_acceptance_step_03_baseline.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收基线表”“Baseline manifest 最小字段”“证据入口基线”“Profile / 配置 / facet 基线”和“基线变更/失效规则”，了解一次送验如何固定。

### 3.1 必须固定的基线

| 基线 | 必须固定的内容 | 当前状态 | 未固定影响 |
|---|---|---|---|
| design | 正式 00～06 的 immutable source ref/digest/清单 | 文档存在；无 immutable delivery ref | 阻断实际进入 |
| test | 正式 05 ref、96 TC 与 suite/check manifest | 文档存在；runner/suite 未实现 | 阻断执行/进入 |
| implementation/delivery | implementation commit、build/image/package ref 与 digest（按适用） | `not_created / not_fixed` | 阻断进入 |
| environment/dependency | environment、host/browser/runner/tool、SDK/owner/host refs | `not_fixed` | 阻断进入 |
| config | 一个 profile、完整 strict document、source ref 与 digest | `not_fixed` | 阻断进入 |
| facet | owner/host/invalidation/diagnostic/browser/AT/quantitative 的 posture 与 authority | `not_fixed` | positive required 集合不可判定 |
| data | fixture/corpus/scheduler seed 与 manifest | `not_created / not_fixed` | 阻断相关 suite |
| execution | immutable `run_id`、timestamps、tool versions、suite manifest | `not_created` | 无 evidence 资格 |
| review | defect snapshot、handoff/VETO/risk/open-issues review version | `not_created` | 无最终裁决 |

### 3.2 Baseline manifest 最小字段

| 字段 | 要求 |
|---|---|
| `design_source_ref` / `implementation_source_ref` | 分别绑定正式设计与目标实现的不可变 source ref |
| `delivery_ref` | build/image/package 等实际送验标识；不适用项必须有理由 |
| `run_id` | 显式且不可变；禁止 `latest` |
| `environment_ref` / `dependency_refs` | 可定位执行环境、SDK/owner/host/runner 版本或 authority |
| `runtime_profile` | 仅 `local-fake / integration-pending / production-pending` 之一；名称不表示 readiness |
| `config_path` / `config_digest` | 指向同一份已严格校验的 whole document |
| `facet_manifest` | 每个 facet 的 `enabled/disabled/blocked`、required 级别和 authority ref |
| `data_refs` | fixture、synthetic leak corpus、schedule/seed manifest |
| `suite_manifest` | P0/release/selected suites 与 blocking classification |
| `acceptance_review_version` | handoff、VETO、risk、defect/open-issues 使用同一 review version |

### 3.3 固定证据入口

| 对象 | 固定路径 | 当前状态 |
|---|---|---|
| raw artifact | `artifacts/test/<run_id>/...` | 不存在 |
| run summary / gate | `reports/runs/<run_id>/summary.md`、`gate-results.md` | 不存在 |
| EV index / detail | `reports/runs/<run_id>/evidence-index.md`、`evidence/EV-<TYPE>-<NNN>.md` | 不存在 |
| redaction / pairing | `reports/runs/<run_id>/redaction-check.md`、`report-pairing.md` | 不存在 |
| handoff / VETO / risk / open issues | `reports/acceptance/handoff.md`、`veto-checklist.md`、`risk-acceptance.md`、`open-issues.md` | 不存在 |
| review notes | `reports/review/reviewer-notes.md`、`agent-review.md` | 不存在 |

禁止项目重复层级路径、无 run 正式报告、移动别名、跨 run 无声明拼接、静态 Markdown/JSON 宣称 EV/VETO passed，以及用 profile、flag、toast、diagnostic receipt、测试计数或截图替代交付/owner/readiness 证据。

### 3.4 配置、profile 与 facet 基线

- 配置恰好四项：required/no-default `runtime.profile`、default `[]` 的 binding array、两个 default `false` switch；全部 startup-only。
- invalidation 默认 disabled；enabled 后 exact envelope/order/dedup/scope 与 positive evidence 必需。
- diagnostics disabled 合法；enabled 后 approved body-free envelope/sink 与 isolation evidence 必需。
- owner facet 未启用时可保持 read-only/partial/blocked；enabled 后 exact contract/adapter/ref/safe-field evidence 必需。
- browser/AT/quantitative 只有 authority 与 baseline selection 同时存在才成为本轮 release gate。

### 3.5 变更与失效

P0 需求/设计/配置/协议/状态/evidence schema 变化使旧 verdict 失效，必须重开相应设计/测试 Step、执行全量 P0 并创建新 run。implementation/dependency/facet set 变化需影响分析和新 run；复验不得覆盖失败 run。仅 review 解释变化可创建新 review version，但不得修改 raw/report outcome。artifact/report digest 或 pairing 改变会使 evidence 资格失效。

当前基线结论：所有执行基线均缺失，实际验收只能是 `not_entered / blocked_by_missing_baseline`。这不是“不通过” verdict，更不是通过或有条件通过。

## 4. 进入条件与退出条件

> 校准来源：
> - `design-calibration/06_acceptance_step_04_entry_exit.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“验收生命周期”“进入条件”“暂停 / 送验无效条件”“退出条件”和“进入/退出来源追溯”，了解生命周期与三值 verdict 的分离。

### 4.1 验收生命周期

```text
not_entered
  -- all entry conditions satisfied --> entered
entered
  -- gates/evidence review complete --> decision_pending
entered / decision_pending
  -- baseline/evidence invalid --> suspended
decision_pending
  -- three-value verdict + required signoff --> decided
```

`formal_stop_review` 是文档状态，不属于该生命周期。`not_entered / entered / decision_pending` 不是 verdict；`decided` 才能保存“通过 / 有条件通过 / 不通过”。新 baseline 或复验 run 可使既有决定失效并开启新验收实例。

### 4.2 进入条件

- [ ] 正式 00～06 的 immutable design source ref 和适用范围已固定。
- [ ] implementation commit 与适用 delivery build/image/package digest 已固定。
- [ ] environment、runner/tool、SDK/host/owner dependency refs 可定位。
- [ ] 一个 profile、完整 strict config document 和 config digest 已固定。
- [ ] facet manifest 逐项声明 posture；enabled facet 有 exact authority/contract。
- [ ] fixture/data/synthetic corpus/scheduler manifest 可复现且无真实敏感正文。
- [ ] fixed `run_id`、P0/release/selected suite manifest 与 blocking classification 已固定。
- [ ] 全部 P0 blocking suites/checks 产生同 run raw artifacts 与 reports；failed/blocked 也保真归档。
- [ ] evidence index、pairing、redaction、no-static-evidence、architecture/dependency 结果存在且可读。
- [ ] handoff、七项 VETO checklist、open issues 已生成并审查；有 residual 时 risk-acceptance 文件存在。
- [ ] 无未关闭 S、未复验 VETO 修复、run mismatch、缺 pair/digest、静态证据或伪 signoff。

当前上述条件均未实际满足，因此不勾选任何一项，实际状态保持 `not_entered / blocked_by_missing_baseline`。

### 4.3 暂停与送验无效

| 触发 | 生命周期处理 | 后续动作 |
|---|---|---|
| baseline 缺失、矛盾或 design/delivery/config/dependency 漂移 | 不进入 / 暂停；当前 run 失效 | 固定新 baseline、影响分析、新 run |
| P0 runner/suite/check 不可执行 | 不进入 / 暂停 | 修复 harness；不得 skip-pass |
| artifact/report 缺失、run mismatch、digest/pairing 失败 | 送验无效；S | 修复生成链并新 run |
| redaction/forbidden material/private dependency 失败 | 暂停；S/VETO 候选 | 修复并全量 P0 |
| enabled facet 缺 exact contract/positive evidence | 对应范围失败或不可进入 | fail-closed，补 authority/证据 |
| selected facet unavailable 且非 release-required | 不暂停 P0 | 记录 residual；不得生成 positive EV |
| VETO 命中或开放 S | 不得进入决定或准出 | 修复并全量复验 |

### 4.4 退出条件

- [ ] 所有 in-scope P0 item 有真实 `passed/failed/not-applicable-with-authority` 结果；`blocked` 只按 baseline 规则解释。
- [ ] `AC-CON-001～007`、`AC-FR-001～012` 与适用 `AC-FR-013` 均闭环到正式设计、TC、EV instance、固定 report 和裁决影响。
- [ ] `AC-BR-001～007`、`AC-DR-001～005`、`AC-NFR-001～007` 均有适用门禁和证据结论。
- [ ] `VETO-CON-001～007` 均由真实 evidence 检查且未命中；不得静态默认 passed。
- [ ] enabled conditional facets 有 contract-derived positive evidence；未启用姿态保持诚实。
- [ ] P0 raw artifact/report/EV/digest/pairing/redaction/no-static-evidence 完整，无 orphan TC/EV。
- [ ] 无开放 S；A 已修复或满足严格逐项接受；B/R 已记录并按需接受。
- [ ] 复验使用新 run、保留失败 run，baseline 变化已触发所需回归。
- [ ] 风险接受具有 evidence、owner、acceptor、reason、deadline/trigger 与真实 follow-up ref。
- [ ] 最终结论只使用三值，并与 handoff、VETO、risk/defect review version 和所有 required signoff 一致。
- [ ] 没有由 verdict、profile 或 release report 推导 production readiness。

## 5. 功能验收门禁

### 5.1 共同证据与裁决规则

下表中 `EV-<TYPE>-001` 必须是绑定同一 fixed run、正式 TC、suite、raw artifact/report path 与 digest 的合格 instance；共同索引为 `reports/runs/<run_id>/evidence-index.md`。suite 名指 `reports/runs/<run_id>/suites/<suite>.md`，raw 由 index 回指 `artifacts/test/<run_id>/...`。当前 instance 数为 0，所有 item result 均为 `not_evaluated`。

### 5.2 功能验收闭环

## 10. 可观测性、审计与证据门禁

> 校准来源：

>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“四类观测/审计/证据主语”“八个 Evidence family 门禁”“P0 Evidence 追溯”“Report 完整性与 handoff 检查”和“跨证据裁决审计”，了解 evidence instance 的资格和证明上限。

### 10.1 四类主语

| 主语 | 可证明 | 不可证明 |
|---|---|---|
| client diagnostic | 客户端 phase、safe outcome、owner/topic key、body-free correlation 与 sink posture | owner audit/evidence、业务完成、合规或 readiness |
| owner audit/evidence/report ref | 相应 owner 安全引用存在及当前可见关系 | Console 自有证明、正文正确性或客户端 verdict |
| test artifact/report/EV | 固定实现/baseline/run 下的测试事实和门禁结果 | owner truth、risk acceptance、signoff 或 production readiness |
| acceptance handoff/verdict/signoff | 授权角色对固定范围、证据、缺陷与风险的裁决 | 未列范围、future facet 或生产 authority 自动成立 |

### 10.2 八个 Evidence family

每个 instance 必须包含 `schema_version/run_id/evidence_id/suite/tc_refs/status/artifact_path/artifact_digest/report_path/report_digest/config_profile/source_refs/ac_refs/veto_refs/blocker_refs/redaction_status/pairing_status/review_status`，且路径、TC、source refs 与 baseline 同 run 一致。

| Evidence ID | 必需来源 / 证明上限 | 合格条件 | 缺失或失败影响 |
|---|---|---|---|
| `EV-UNIT-001` | pure-contract/config/state/diagnostic unit assertions | in-scope UNIT TC 全有 raw/report/digest；failed/blocked 保真 | unit-backed P0 不可裁决；阻断 |
| `EV-FLOW-001` | module-flow/recovery；client flow、Query no-write、recovery phase | FLOW TC 与 call ledger/report 真实配对 | 功能/协议/recovery P0 不可通过 |
| `EV-CONTRACT-001` | port-adapter/config/state；narrow Port/adapter/config/state parity | formal/fake source 明示；conditional posture 保真 | safety contract 缺失阻断；fake 不证明 formal positive |
| `EV-INTEGRATION-001` | controlled-composition/concurrency；partial/race behavior | deterministic scheduler/ledger、partition/correlation 与 reports 配对 | isolation/concurrency P0 不可通过 |
| `EV-ACCESSIBILITY-001` | semantic-a11y + required selected matrix | core semantic TC 全合格；selected 只覆盖 baseline 声明 matrix | semantic 失败→VETO-006；非required selected 只 residual |
| `EV-SECURITY-001` | redaction/module/release security negatives | synthetic corpus、no echo、minimum disclosure、scan 全合格 | S/VETO 候选；总体不通过 |
| `EV-ARCH-001` | architecture-static/release-dependency；SDK-only、5+16+1/0/0、write inventory | generated graph/registry/call ledger 与 delivery ref 一致 | S/VETO-001/004 候选 |
| `EV-RELEASE-001` | release safety/config/redaction/dependency/report completeness | required release gates 有真实 source/pair/digest，no-static-evidence 合格 | 送验无效/阻断；不等 verdict/signoff/readiness |

### 10.3 Report、handoff 与真实性

| 检查 | 固定入口 | 通过条件 | 失败影响 |
|---|---|---|---|
| raw / summary / gate | `artifacts/test/<run_id>/`、`reports/runs/<run_id>/summary.md`、`gate-results.md` | meta、suite/case、failed/blocked/residual、blocking status 与 digest 保真 | 送验无效或阻断 review |
| evidence index/detail | `reports/runs/<run_id>/evidence-index.md`、`evidence/EV-<TYPE>-<NNN>.md` | 适用 EV 无 orphan，逐 TC/AC/VETO 回指 raw/report/digest | 不可裁决或对应 EV 无资格 |
| redaction / pairing | `redaction-check.md`、`report-pairing.md` | 无 forbidden material，不回显命中值；无 mismatch/orphan/missing digest | S/VETO-004 候选或送验无效 |
| handoff | `reports/acceptance/handoff.md` | baseline、范围、enabled facets、failed/blocked/residual 与 review version 完整并审查 | 不得进入最终裁决 |
| VETO checklist | `reports/acceptance/veto-checklist.md` | 七项逐项有 evidence/结论；无静态默认 pass | 不得通过 |
| risk / open issues | `reports/acceptance/risk-acceptance.md`、`open-issues.md` | residual/defect/owner/trigger/evidence 一致；有条件通过时逐项签署 | 缺失则不得有条件通过 |
| review notes | `reports/review/reviewer-notes.md`、`agent-review.md` | 记录完整性、争议和审查，不改 raw outcome | 未审查 draft 不得签署 |

candidate/family/instance 必须分离；blocked/not_run 不贡献 positive；失败 run 不得被“latest success”覆盖；不能手工补缺失 EV。当前八个 family 只是 future contract，evidence instance=0，所有路径文件均不存在。

| `VETO-CON-005` | UI、固定 control/metric 数量、客户端阈值/flag/cache/partial result 生成 approval/compliance/audit/capability/archive/runtime/readiness 结论 | VIEW/TOPIC/STATE/SEC/CONFIG；`EV-UNIT-001`,`EV-FLOW-001`,`EV-INTEGRATION-001`,`EV-SECURITY-001` | composition、redaction、config、release-safety | 总体“不通过”；S；不可风险接受 |

## 12. 缺陷分级、复验与放行规则

> 校准来源：
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“缺陷分级表”“S 级与强制阻断判定”“修复后复验矩阵”“Future 缺陷关闭证据”“放行规则”和“缺陷与复验停审记录”，了解缺陷如何影响 verdict。

当前没有 defect tracker、`BUG-*`、失败/fixed run 或关闭记录；“无可引用缺陷记录”不等于 S/A/B 为 0。

### 12.1 缺陷分级

| 级别 | 定义 | 对结论的影响 | 复验与关闭要求 |
|---|---|---|---|
| S | VETO；P0 truth/access/phase/body/inference/a11y/isolation；redaction、dependency、strict config 或 evidence integrity 红线破坏 | 未进入时阻断准入；进入后只能“不通过”；不可接受 | 新 run 复跑原 TC、same family、受影响 suite/check 和全量 P0；保留失败 run；完整 closing evidence/reviewer conclusion |
| A | 未命中 S，但适用 P0 flow、blocking suite、主要交付语义或其稳定证明失败 | 原则上不得“通过”；未接受时阻断；只有全部适用 P0 已由独立合格证据证明且不触碰硬门禁时，才可逐项候选“有条件通过” | 原 TC、same family、相关 suite/check/report audit；接受时必须有 alternative evidence、owner、acceptor、deadline/trigger |
| B | 不破坏 P0 的非阻断功能、selected matrix、可读性或维护性问题 | 不贡献 P0 pass；可逐项支持“有条件通过” | 视影响复跑 selected/affected suite 或补 review；记录 follow-up/trigger |
| R | 范围外、future、等待 authority/合同/环境的 residual；不表示已执行失败 | 不影响既定 P0 safety，但不能计为 positive capability/readiness；入 scope 后重定级 | 固定 blocker/authority/owner/trigger；升级后重新 baseline 并测试 |

### 12.2 强制复验规则

所有修复至少复跑原失败 TC、same family 的正/负/边界代表、受影响 suite，以及相邻 redaction/dependency/pairing/no-static-evidence check。以下映射为最小边界：

| 缺陷面 | 必跑 TC / suite / check | 必需 closing evidence |
|---|---|---|
| context/access/navigation | CTX/NAV/SEC；pure-contract、module-flow、semantic-a11y；redaction | fixed-run UNIT/FLOW/SECURITY/ACCESSIBILITY EV |
| views/16 Query/no-write | VIEW/ADAPTER/ARCH；module-flow、port-adapter、architecture-static；redaction/dependency | FLOW/CONTRACT/SECURITY/ARCH EV |
| 5 Command/result/reconcile | INTENT/CONSISTENCY；module-flow、port-adapter、concurrency、release-safety；pairing/no-static | FLOW/CONTRACT/INTEGRATION/RELEASE EV |
| topics/partition/activation | TOPIC/RECOVERY/SEC；composition、recovery、release-safety；redaction/pairing | FLOW/INTEGRATION/SECURITY EV |
| state/carrier/consistency | STATE/CONSISTENCY；pure-contract、concurrency、composition；report audit | UNIT/FLOW/CONTRACT/INTEGRATION EV |
| recovery/a11y | RECOVERY/A11Y；recovery-matrix、semantic-a11y、module-flow；redaction | FLOW/INTEGRATION/ACCESSIBILITY EV |
| config/binding | CONFIG/ADAPTER；config-redline、architecture、release-config；dependency/redaction/report | CONTRACT/SECURITY/RELEASE EV |
| diagnostic/forbidden material | DIAG/SEC；redaction-boundary、release-redaction、source suite；redaction/pairing/no-static | SECURITY/RELEASE EV |
| architecture/protocol/dependency | ARCH + affected protocol；architecture-static、port-adapter、release-dependency | ARCH/RELEASE EV + generated graph/call ledger |
| gate/report/EV tooling | affected formal TC + source suites；pairing/no-static/release-report-audit | RELEASE EV + all affected source EV |

任一 S、协议 inventory、状态/phase、四配置、redaction/dependency/evidence schema 或 release blocking topology 变化都触发正式 05 §14.2 的全量 P0 集合。Conditional positive 仅在新 baseline 声明 enabled 后进入必跑范围。

### 12.3 缺陷关闭与放行

每条关闭记录必须包含 defect ref/级别/发现 run/原 TC/suite/影响面、不可变 failed artifact/report refs/digests、修复 delivery 与设计/测试回写、新 fixed run 与复验集合、source EV/index/pairing/redaction refs、防回归决定、owner/reviewer/日期和关闭结论。S 禁止 risk acceptance；A 只有严格条件下可逐项接受；B/R 放行时必须有风险接受。路径只允许 fixed run roots，禁止 `latest`，失败 run 不得覆盖。

| 条件 | 生命周期 / verdict | 是否放行 |
|---|---|---|
| baseline/runner/environment/evidence 未固定 | `not_entered`，无 verdict | 否；当前实际状态 |
| 任一 VETO 或开放 S | entered 后“不通过” | 否 |
| 适用 P0 failed/blocked 或证据不合格 | entered 后“不通过”或暂停补证 | 否 |
| 开放 A 且无严格接受 | `decision_pending` 或“不通过” | 否 |
| A 严格接受且全部适用 P0 独立证明通过 | 候选“有条件通过” | 有条件 |
| 仅 B/R 且逐项被接受 | 候选“有条件通过” | 有条件；不表示相应 positive/readiness 完成 |
| 适用 P0 全过、VETO 未命中、S/A=0、证据/签署完整 | 候选“通过” | 是；仍须 §14 正式裁决 |
| rerun passed 但 defect/risk/signoff review 未完成 | `decision_pending` | 否 |

## 13. 风险接受与遗留项

> 校准来源：
> - `design-calibration/06_acceptance_step_13_risk_acceptance.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“风险资格分层”“Console residual candidate 登记表”“不可作为风险接受的 blocker / 红线”“风险接受记录字段合同”“后续同步规则”和“风险接受停审记录”，了解有条件通过的严格边界。

### 13.1 资格规则

只有 baseline 明确 excluded/conditional、不会影响适用 P0 safety/truth/evidence、已有合格 evidence 证明安全姿态，且 owner/acceptor/action/deadline/follow-up 全部真实齐备的 residual，才能从 `candidate` 变为 `accepted`。implementation/delivery/environment/fixed run 缺失是 baseline blocker，不能通过风险接受把 `not_entered` 提升为 verdict。VETO/S/required P0 failure/evidence fraud 永不接受。

### 13.2 Residual candidates

### 13.3 不可接受项与记录合同

不可接受：baseline/implementation/fixed run 缺失；enabled/required facet 缺合同或 positive evidence；七项 VETO/S；private boundary/第二 truth/Query write/Policy-Gate 绕过；伪完成/replay；forbidden material；客户端推导 verdict/readiness；核心 a11y 或 partition isolation 失败；config silent fallback；static evidence、mismatch、缺 pair/digest、删除失败 run或伪 signoff。

`reports/acceptance/risk-acceptance.md` 每项必须包含稳定 `risk_id`、`review_version`、baseline/scope/facet posture、impact/reason、fixed-run evidence refs、具名 owner/acceptor、真实 follow-up action/ref、absolute date 或可判定 trigger、status/decision date 和逐项 signatures。仅角色占位不构成接受。baseline/scope/facet 变化、deadline/trigger 到达、evidence/defect 失效、新 VETO/S 或签署撤回会使接受失效并重开裁决。

当前 risk acceptance instance=0；没有具名接受人、日期、证据或 07/运维/issue follow-up ref，因此不存在任何可支持“有条件通过”的已接受风险。

## 14. 最终结论与签署

> 校准来源：
> - `design-calibration/06_acceptance_step_14_final_decision_signoff.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“生命周期到裁决门禁”“五维最终结论表合同”“总体三值判定矩阵”“签署责任表”“签署、风险接受与 readiness 边界”和“决定失效与重开规则”，了解最终裁决如何形成。

### 14.1 当前状态与三值规则

当前生命周期是 `not_entered / blocked_by_missing_baseline`，所以 verdict 与 signoff 均为 `none`。这不是第四种 verdict；实际验收只有在进入、审查完毕并到达 `decided` 后，才允许使用“通过 / 有条件通过 / 不通过”。禁止“基本通过”“原则上通过”“大体没问题”“后补”。

### 14.2 五维结论合同

| 维度 | “通过” | “有条件通过” | “不通过” |
|---|---|---|---|
| 功能验收 | 适用 `AC-CON/AC-FR`、接口/状态/红线 P0 全部 passed；enabled positive 有 contract-derived evidence | P0 全过，仅有逐项 accepted 的非 P0/A-limited/B/R residual | 任一适用 P0 fail/blocked、VETO 或 S |
| 非功能验收 | `AC-NFR-001～007` 适用 required 项 passed；selected 未要求或已通过 | semantic/structural P0 全过，仅 selected/量化/production residual accepted | 任一 P0 NFR、核心 a11y/security/evidence integrity 失败 |
| 发布准备 | release-required suites/checks/evidence/handoff/defect/risk 完整，scope authority 明确 | 所有硬门禁通过，仅不影响发布安全的 residual accepted | delivery/run/report 缺失，release gate/配置/依赖/evidence 失败或 scope 未固定 |
| 总体结论 | 前三维通过；VETO 未命中；S/A=0；风险/签署完整 | 全部适用 P0 passed；VETO/S=0；仅逐项 accepted residual | 任一维度不通过、VETO/S、未接受 A 或证据不可裁决 |
| 是否允许进入下一阶段 | 是 | 有条件；严格受 action/deadline/trigger 约束 | 否；尚未 `decided` 也为否 |

发布准备结论不等 deployment approval 或 production readiness。`production-pending` profile、UI、diagnostic、测试计数、`EV-RELEASE-001`、release report、验收 verdict 或文档 `formal_stop_review` 均不能自动推导生产就绪。

### 14.3 签署责任

实际记录必须绑定 `acceptance_instance_id/review_version/baseline_ref/run_id`、五维结论与理由、evidence/handoff/VETO/risk/defect refs，并由以下责任栏逐项确认：

| 角色 | 必须确认 | 不表示 |
|---|---|---|
| 产品 / 业务验收负责人 | 范围、enabled/excluded facets、管理者主线和业务 residual | 授权、owner truth 或未列功能 ready |
| Console 架构负责人 | SDK-only、ownership、5+16+1/0/0、依赖/状态/配置红线和 VETO | 测试已执行 |
| 测试 / 证据负责人 | 96 TC 适用集、suite/check、EV、pair/digest、缺陷和复验 | 自动产生业务 verdict |
| 实施 / 交付负责人 | implementation/delivery refs、实现范围、配置与依赖 baseline | deployment/production ready |
| 安全 / 合规负责人 | access/minimum disclosure、redaction、evidence integrity、核心 a11y 与合规 residual | 接受未列风险 |
| 运维 / 发布负责人 | environment/profile、release gate、diagnostic/retention residual 与 handoff | profile 即 readiness |
| 最终验收裁决负责人 | 五维结论、VETO、defect、risk review version 与全部签署一致 | 覆盖角色异议或缺失证据 |

同一具名人员可兼任，但每个责任栏必须独立给出身份、结论、日期与签名。总体签署不自动接受风险；risk acceptance 必须由每项 acceptor 独立签署。自动报告只能生成 draft/facts，不能写 verdict、signoff 或 readiness。

### 14.4 决定失效与重开

design/delivery/config/dependency/facet baseline 变化、新 VETO/S、accepted risk 到期或 trigger 到达、evidence digest/pairing/review 失效、关键 owner/SDK contract 改变、签署撤回或角色冲突，都会使既有结论失效。必须创建新 review version，按影响决定新 run/复验，并重新进入 `entered` 或 `decision_pending`；旧决定和失败证据必须保留。

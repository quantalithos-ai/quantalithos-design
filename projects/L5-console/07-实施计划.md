## 2. 实施目标与范围

> 校准来源：
> - `design-calibration/07_implementation_plan_step_02_scope.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“实施目标表”“实施范围表”“非范围表”和“P0/P1/P2 防膨胀规则”小节。

### 2.1 本轮最小可交付结果

本轮目标是形成一个可编译、可测试、可审查的 TypeScript/ESM browser-client 实施增量，覆盖安全访问壳、safe view/query、受控 intent/command、八主题 owner partition、恢复与可访问交互、窄 adapter 和 release evidence 生成链。正向 owner 能力只有在正式合同、目标仓和 baseline 到达后才可解锁；没有合同时交付安全的 no-call、disabled、restricted 或 blocked posture。

### 2.2 P0 实施范围

| 范围族 | P0 计划内容 | 完成判定（未来执行期） |
|---|---|---|
| 客户端模块 | `entry`、`access`、`navigation`、`views`、`intent`、`features`、`recovery`、`adapters`、`state`、`diagnostics` | 按 boundary 有可编译增量和对应门禁；当前均 `not_created` |
| 协议 surface | 5 Command、8 Core Query、8 Topic Query、1 conditional consumer | protocol inventory、side-effect ledger 和测试切口与正式 `03/05/06` 一致 |
| 安全规则 | SDK/formal-boundary-only、Query zero-write、唯一潜在 owner write=`OwnerCommandPort.submit`、unknown 不 replay、forbidden-body/redaction | architecture/no-write/redaction/evidence gate 真实通过 |
| 配置 | `runtime.profile`、`bindings.adapterBindings`、`invalidation.enableSdkInvalidation`、`diagnostics.enableDiagnostics`；三个 profile | strict whole-document、startup-only、fail-closed/zero-secret 真实可验证 |
| 主题组合 | member、project/workspace、method、governance、observability、capability、archive、sandbox 八个独立 partition | canonical order、局部失败隔离、strict empty 和 activation ceiling 有证据 |
| 交付证据 | gate/check/report/evidence/handoff 生成路径 | 只在真实 fixed run 后生成 paired raw/report；当前不存在 |

### 2.3 非范围与禁止误入

| 非范围 | 处理 |
|---|---|
| owner truth、DB、repository/UoW、projection、outbox、worker、job、BFF、private bus | 禁止；出现即 architecture blocker/VETO 方向 |
| Outbound Event、Operations Job | 本项目正式 surface 为 0/0；不得“补实现” |
| 具体框架/router/bundler/package manager/host lifecycle | authority 未固定前保持 pending；不得从历史材料猜选型 |
| owner exact DTO、scope/qualification/safe-field、reconcile/idempotency、invalidation envelope | 合同未闭合时仅 no-call/disabled/blocked；回写 03/05/06 |
| durable、cross-tab、CAS、online LKG、production sink、selected browser/AT、量化阈值 | residual/future；不贡献 P0 positive/readiness |
| 真实 run、artifact/report/evidence、defect、risk acceptance、verdict/signoff/readiness | 只定义 future path，不伪造事实 |

P1/P2 事项不得污染 P0：仅当正式启用 facet、authority、baseline 和证据齐备时才进入适用范围；不可用时记录 residual/blocked，不得写成“基本完成”。

### 6.1 每个 phase 的统一编写顺序

```text
读取项目级 ledger 与当前 boundary ledger
  -> 阅读正式章节与 calibration
  -> 确认 public contract、字段/状态/证据边界
  -> 更新 Design Gate / Scope Gate
  -> 先建立当前测试切口和数据隔离
  -> 实现核心 local safety / mapping
  -> 接入 formal Port / adapter（合同允许时）
  -> 接入 entry/presentation seam
  -> 补齐错误、恢复、redaction、race 和诊断边界
  -> 跑当前 boundary gate 并回写 raw/report 证据
  -> Commit Gate -> 一 boundary 一提交 -> Handoff Gate
```

### 6.4 Boundary Gate / Handoff 规则

每个 boundary 的台账必须包含 `design_gate`、`scope_gate`、`worktree_gate`、`build_gate`、`test_gate`、`evidence_gate`、`commit_gate`、`handoff_gate`。gate 值仅允许 `pending/pass/blocked/not_applicable`；任何 `pass` 必须引用真实 evidence。`blocked` 时只能 `wait_design`、`fix_gate_failure` 或 `handoff`，不得继续实现。

Commit Gate 需要 staged scope 精确对应一个 boundary、无无关用户改动、真实 required checks、whitespace/diff 检查和用户提交授权。Handoff Gate 需要真实 hash/message、未关闭 blocker、未执行检查、下一 boundary 和用户改动保护；没有 hash/run 时保持 pending。

### 6.5 设计者经验复核责任

设计者在移交前、每个 boundary 开工前和设计修复后，必须按 `设计真相源闭环与可落码性标准.md` §九做适用性复核。实现者不承担补洞责任；发现不闭环必须报告具体文件/行号、影响范围和建议回写点。

### 8.3 Fake / controlled / disabled 边界

Fake 只能模拟正式边界的输入/输出和失败姿态，不能模拟未确认的 owner schema、数据库或第二 truth。controlled fake 可用于 no-write、race、partial、redaction 和 semantic tests；disabled branch 只能证明“未调用/不写入/保守降级”，不能证明 owner 正向能力。

### 11.1 提交规则

- 一笔提交只对应一个 Step 6 boundary；不得按单文件碎片化，也不得跨 phase 合并。
- 实现仓 title/body 默认英文，格式为 `<type>(<scope>): <subject>`；type 使用 `feat/fix/refactor/docs/test/chore/perf/ci/style`，scope 必须能回指 boundary，禁止 `misc/tmp`。
- body 第一段写 boundary 目标，后续按协作子功能分组列文件名和改动量；不能把完整路径、日志或字面 `\n` 当作 message 内容。
- 只有真实 raw/report/evidence 才可被引用；当前没有 hash、run、report 或 review，所有字段保持 pending。
- 设计仓文档语言和实现仓英文规则分离；本轮不提交 design commit。

### 11.2 评审与 handoff

Reviewer 必须能从 title/body 回指一个 boundary，并检查 design closure、scope、required checks、证据 pairing、redaction/no-static、用户改动保护和失败材料保留。`reports/acceptance/*` 由脚本生成 draft 后必须人/Agent 审查；未经审查不得交付、风险接受、verdict、signoff 或 readiness。

项目级实施台账和 boundary 台账是实现 agent 每次继续的第一读取入口。缺少台账、当前 boundary 不唯一、gate blocked 或 baseline 不一致时，`next_allowed_action` 不得为 `implement` 或 `commit`。

## 12. 实施完成判定

> 校准来源：
> - `design-calibration/07_implementation_plan_step_12_completion_criteria.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“实施完成判定表”“闭环项完成标准”“交付实现前可落码闭环审计”“交付证据项”“未完成项处理表”和“完成结果矩阵”。

### 12.1 四类执行期结果

| 结果 | 必须满足 | 允许表达 |
|---|---|---|
| `完成 / 可送验` | P0 scope/交付物完成；适用 P0 gate 全过；VETO 未命中；S=0；raw/report/evidence/review 完整；设计闭环无 blocker | 可进入 06 正式验收生命周期；不自动等 production readiness |
| `有条件完成 / 可送验带 residual` | 适用 P0 成立；VETO/S=0；仅已接受且不影响硬门禁的 residual | 必须具名 owner/acceptor/trigger/deadline；不贡献 readiness |
| `不完成 / 不可送验` | 任一 P0 blocked/failed、VETO/S、证据不可裁决、设计闭环 blocker、handoff 未审查 | pause/fix/retest；不得提交或移交 |
| `not_entered` | baseline、implementation、run、review 尚未固定 | 当前事实；不是 verdict |

当前项目只能写：`not_entered / blocked_by_missing_implementation_repo_and_baseline`。没有实现仓、baseline、run、artifact/report/evidence、commit、review 或 06 裁决，不得使用前三类结果。

### 12.2 交付实现前可落码闭环审计

| Phase / boundary | 交付前必须复核 | 当前设计上限 |
|---|---|---|
| PH-01 / `commit-01-a/b` | package/toolchain、四 config、roots、依赖 absence、static paths | target repo/runner/baseline 缺失，`pass with blockers` |
| PH-02 / `commit-02-a/b` | context/visibility/qualification、selection cleanup、semantic route | host authority pending，positive blocked |
| PH-03 / `commit-03-a/b/c` | safe-field/source axes、16 Query zero-write、safe link/reconcile | exact query surface pending，positive blocked |
| PH-04 / `commit-04-a/b/c` | draft/request/result、sole owner write、unknown/no-replay、carrier/race | owner/reconcile/carrier pending，submit positive blocked |
| PH-05 / `commit-05-a/b/c` | eight partition、canonical order、strict empty、failure isolation | owner facet/browser authority pending |
| PH-06 / `commit-06-a/b/c` | typed recovery、semantic equivalence、body-free diagnostics/redaction | sink/AT pending |
| PH-07 / `commit-07-a/b/c` | narrow registry、fake/formal parity、disabled invalidation | exact SDK/invalidation contract pending；positive blocked |
| PH-08 / `commit-08-a/b/c` | fixed run、reports、EV/VETO/handoff/review、no-static | baseline/run/review absent；`blocked` |

### 12.3 未完成项处理

目标仓、baseline、required contract、P0 gate、Query no-write、redaction、dependency、pairing/no-static、VETO/S 或设计闭环 blocker 均不可风险接受；必须修复/回写后以新 evidence 重验。A/B/R/P1/P2 只有在 06 允许且具名接受时才可作为 residual，不能贡献 P0 positive/readiness。没有真实 evidence 不等于“没有问题”。

### 12.4 07 与 06 的权责边界

07 只判断实施资料是否达到“可送验”条件并定义交付路径；06 仍拥有验收 verdict、risk acceptance、signoff 和 readiness。PH-08 可以生成 handoff/VETO/risk/open-issues 草稿，但不能自动写 `passed`、`accepted`、`signed` 或 `ready`。

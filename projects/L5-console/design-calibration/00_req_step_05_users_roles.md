## 4. SOP 问题回答

| 问题 | 回答 |
|---|---|
| 本仓有哪些主要角色？ | 组织管理者、合规/审计角色、方法资产管理员、平台运营者，以及受限查看者；它们是产品意图角色，不等于服务端固定 RBAC 名称。 |
| 哪些是人类角色，哪些是系统角色？ | 上述五类为人类角色；可信会话/身份提供方、正式 owner 服务/SDK、异步结果/状态提供方、辅助技术消费者为系统角色。 |
| 分别在什么场景接触？ | 人类通过管理页面查看安全摘要、比较状态、编辑草稿、请求管理动作或审阅证据；系统角色提供 actor/scope/visibility、query/command result 和状态更新，或消费安全链接/客户端诊断。 |
| 是否存在管理、审计或维护角色？ | 有：组织管理者、方法资产管理员、合规/审计角色和平台运营者。Console 自身不设置它们的正式资格。 |
| 是否需要权限矩阵？ | 需要能力级矩阵，用于说明不同意图角色通常需要的只读/请求范围；矩阵只表达产品需求差异，最终可见性和动作资格逐请求由正式 owner 决定。 |

## 6. 改动前后对比与设计取舍

### 6.1 改动前后对比

| 主题 | 旧口径 | 当前结论 |
|---|---|---|
| 角色模型 | 固定产品内 RBAC 名称 | 基于使用意图的角色，不声明身份系统角色名 |
| 权限来源 | 表格内直接 ✅/❌ | 正式 owner 每次决定，矩阵只说明需求差异 |
| 系统角色 | 仅“系统”一列 | 分为可信上下文、owner/SDK、异步结果和安全诊断消费者 |
| 未闭合动作 | 当作已授权功能 | 只描述“若正式暴露则可请求”，保持 pending |

### 6.2 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 沿用旧固定 RBAC 名称和勾选矩阵 | 直观 | 复制授权规则，无法适应 owner/scope/对象级差异 | 不采用 |
| B. 完全不写权限差异 | 避免越界 | 无法表达审计、管理、方法和只读角色的不同需求 | 不采用 |
| C. 使用产品意图角色 + 能力级差异 + 正式决定兜底 | 能表达用户需求且不夺取授权真相 | 后续需绑定正式 visibility contract | 采用 |

## 7. 结构化中间产物

### 7.1 角色说明表

| 角色 | 类型 | 使用场景 |
|---|---|---|
| 组织管理者 | 人类角色 | 查看组织成员、项目/workspace、过程与总体治理状态，并发起正式开放的成员或组织管理请求。 |
| 合规 / 审计角色 | 人类角色 | 审阅 Governance/SoA/AIIA/Control/Gate、审计、lineage、指标、报告和证据引用的正式可见结果。 |
| 方法资产管理员 | 人类角色 | 浏览方法资产及版本，编辑客户端草稿，并在资格允许时提交方法资产管理请求。 |
| 平台运营者 | 人类角色 | 查看能力注册/暴露、服务退化、Archive/Sandbox 状态和平台诊断入口，并发起正式开放的运维管理请求。 |
| 受限查看者 | 人类角色 | 查看其正式 scope 内的安全摘要、受限原因和可达 drill-down，不接触未获授权的管理操作或敏感正文。 |
| 可信会话与身份上下文提供方 | 系统角色 | 向 Console 提供当前 actor/session/scope 语境或失效姿态；Console 不签发或推导这些事实。 |
| SDK 与正式 owner 服务 | 系统角色 | 提供查询、可见性/资格、命令 receipt/result 和安全引用；各自保有业务 truth。 |
| 异步结果与状态提供方 | 系统角色 | 在正式边界允许时提供 owner 状态变化或结果回查输入，不由 Console 直接订阅内部事件主干。 |
| 安全诊断消费者 | 系统角色 | 接收经过裁剪的客户端错误、性能和交互诊断；其输出不等于业务审计或 evidence。 |

### 7.2 能力级权限差异矩阵

`正式决定` 表示 Console 不能预先授予；实际结果由 actor/scope/visibility/Policy/Gate 与 owner 能力共同决定。

| 操作类型 | 组织管理者 | 合规/审计 | 方法资产管理员 | 平台运营者 | 受限查看者 |
|---|---|---|---|---|---|
| 查看 scope 内安全摘要 | 正式决定 | 正式决定 | 正式决定 | 正式决定 | 正式决定 / 受限 |
| 发起成员/项目相关管理请求 | 意图相关 / 正式决定 | 通常只读 | 不适用 | 受限 / 正式决定 | 不适用 |
| 编辑并提交方法资产草稿 | 受限 / 正式决定 | 通常只读 | 意图相关 / 正式决定 | 不适用 | 不适用 |
| 查看治理、审计、指标和证据引用 | 正式决定 | 意图相关 / 正式决定 | 受限 / 正式决定 | 正式决定 | 受限 / 正式决定 |
| 发起能力、Archive 或平台运维请求 | 受限 / 正式决定 | 通常只读 | 不适用 | 意图相关 / 正式决定 | 不适用 |
| 查看受限/过期/部分/未知原因 | 必须可理解 | 必须可理解 | 必须可理解 | 必须可理解 | 必须按安全合同可理解 |

### 7.3 角色边界

- 角色名不是认证主体、credential、固定 role enum 或授权证明。
- “组织管理者”不自动拥有全组织数据；“审计角色”不自动拥有全部审计正文。
- 系统角色是交互方分类，不表示 Console 依赖其源代码或可绕过 SDK。
- 无正式资格或资格未知时，敏感内容和危险操作均不得放行；受限说明也不能泄露对象存在性。

## 8. 复杂度判断

九类角色已覆盖人类意图和系统交互，但正式文档无需继续细分组织职位。字段级 visibility、对象级权限、角色继承与策略表达都属于 owner 合同或后续设计，不在需求角色章节展开。

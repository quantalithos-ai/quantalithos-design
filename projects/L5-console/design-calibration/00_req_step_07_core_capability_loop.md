## 4. SOP 问题回答

| 问题 | 回答 |
|---|---|
| 没有这个仓，系统缺什么不可替代能力？ | 缺少一个把多 owner 正式管理能力转为统一、可解释、安全且可访问的人类管理体验的产品边界；用户只能直接面对分散服务或由各产品重复实现权限/状态解释。 |
| 仓成立必须共同具备哪些能力？ | 可信访问语境、入口/动作资格呈现、owner-safe 读取与来源保真、受控意图与 owner 结果确认、管理主题视图与回链、降级/错误/过期/可访问性收束。 |
| 哪些缺一个就不成立？ | 六个均不可缺。只有导航没有安全读取是空壳；只有只读 dashboard 无法承接管理操作；只有表单没有 owner 确认会伪造成功；没有降级/a11y 会在失败时误导或不可操作。 |
| 哪些只是外围增强？ | 可配置 dashboard、跨期趋势、批量操作、管理评审模板、个性化首页、跨产品快捷入口等，不决定基本可信管理闭环。 |
| 哪些根本不属于本仓？ | 任何 owner truth、授权/Policy/Gate/合规/readiness 决定、审计/证据/报告生成本体、archive/sandbox 执行、Chat/Runner/Sync/Marketplace 主流程。 |
| 现有功能如何支撑闭环？ | 会话/语境支撑 C1；导航/权限支撑 C2；各页面查询和 filter/drill-down 支撑 C3/C5；表单/命令支撑 C4；治理/审计/能力/Archive 页面支撑 C5；错误/a11y 支撑 C6。 |
| 节点按什么顺序讨论？ | C1 → C2 → C3 → C4 → C5 → C6。这是能力成立的逻辑依赖，不是运行时调用、页面导航或实施顺序。 |
| 每个节点停审必须证明什么？ | 至少证明故事、功能、规则、数据归属、接口/依赖、质量和验收均能回指该节点，且没有越过 owner truth、没有把 pending 写 ready。 |

## 6. 改动前后对比与设计取舍

### 6.1 改动前后对比

| 主题 | 旧结构 | 当前结构 |
|---|---|---|
| 主轴 | 页面清单 / 管理对象 | 人类可信管理交互的能力成立链 |
| 节点 | 员工、方法、治理、审计等领域面 | 访问、资格、读取、意图/结果、主题呈现、韧性 |
| 成功 | 页面可用/绿色 | 来源、资格、结果和失败姿态可判别且不制造 truth |
| 页面范围 | 直接等于核心能力 | 管理主题是 C5 下可裁剪的具体消费面 |

### 6.2 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 按八个页面族各设核心节点 | 页面映射直观 | 重复会话/权限/错误逻辑，无法证明产品共同闭环 | 不采用 |
| B. 完全按请求生命周期设节点 | 跨页面一致 | 容易忽略管理主题范围和回链价值 | 不单独采用 |
| C. 六个横向能力节点，管理主题作为 C5 的纵向消费面 | 同时保留共同闭环和页面范围，可逐节点追溯 | Step 8~14 需严格按节点映射 | 采用 |
| D. 将降级/a11y 仅作为 NFR | 核心节点更少 | 失败场景是产品语义的一部分，缺失会误导管理决策 | 不采用 |

## 7. 结构化中间产物

### 7.1 仓存在必要性

Console 的不可替代性不是拥有更多业务事实，而是把多个正式 owner 的管理能力安全地转译成人类可使用的组织操作台：用户能确认当前语境、理解可见/可操作范围、读取带来源和状态的数据、形成受控意图、区分请求与正式结果，并在权限撤销、部分/过期/冲突/未知时获得保守且可访问的反馈。

### 7.2 核心能力节点

| 节点 | 能力成立描述 | 进入条件 | 退出结果 | 缺失后果 |
|---|---|---|---|---|
| `C-CON-1` 可信会话与访问语境 | Console 能承接当前客户端会话以及正式 actor/scope 引用，并对过期、撤销或不可验证作安全响应 | 产品壳可启动；正式上下文来源存在或明确不可用 | 当前访问语境可判别；不可验证时不暴露受保护内容 | 后续所有读取/操作失去可信主体，必须整体 fail-closed |
| `C-CON-2` 导航、可见性与动作资格呈现 | 页面入口和动作依据正式 visibility/资格结果呈现 visible/restricted/disabled/unknown，不本地授权 | C1 语境存在 | 用户知道哪些入口/动作可请求及依据/限制 | 隐藏按钮、route 或 feature flag 可能被误当权限决定 |
| `C-CON-3` Owner-safe 查询与视图解释 | 经 SDK/正式边界读取安全结果，保留 owner/source、freshness、coverage、availability、consistency，并区分空与缺失 | C1/C2；至少一个正式 read surface | 可理解且不反写的页面视图；局部源可独立降级 | 页面可能伪造完整性、当前性或跨域强一致 truth |
| `C-CON-4` 受控意图提交与正式结果确认 | 本地草稿、格式校验、危险确认、提交、receipt、pending/confirmed/rejected/unknown 分层，副作用只由 owner 决定 | C1/C2；正式 command（若该能力开放） | 用户知道意图是否仅已提交、待确认或已由 owner 正式完成 | toast/HTTP/optimistic state 会冒充业务成功或导致重复副作用 |
| `C-CON-5` 管理主题视图、回链与受控入口 | 员工、项目/workspace、方法、Governance、审计/指标、Capability、Archive/Sandbox 等主题通过 C1~C4 形成可裁剪页面范围与正式回链 | 对应 owner read/command/ref 合同；未闭口可保持 blocked/只读 | 授权用户可在统一信息架构中理解正式状态和到达 owner 结果 | 产品只剩通用壳，无法兑现组织治理与管理入口价值 |
| `C-CON-6` 保守降级、恢复与可访问交互 | partial/stale/missing/unavailable/conflict/unknown 有文本语义、安全遮蔽、重试/回查/退出与键盘/读屏路径 | C1~C5 任一状态，包括失败 | happy/non-happy path 均可理解、可恢复、不误导 | 失败时可能泄露数据、误放行操作或让辅助技术用户无法完成任务 |

### 7.3 核心能力闭环图

```text
[C1 trusted session / actor-scope context]
                     |
                     v
[C2 navigation / visibility / action posture]
                     |
                     v
[C3 owner-safe query / source-preserving view]
                     |
                     v
[C4 controlled intent / owner result confirmation]
                     |
                     v
[C5 management surfaces / traceable drill-down]
                     |
                     v
[C6 degraded / recovery / accessible interaction]
                     |
                     +---- revalidate / requery ----> C1/C2/C3
```

箭头表示能力成立的逻辑依赖与反馈闭合，不表示运行时调用顺序、路由时序、事件传播或开发计划。只读页面可由 C1→C2→C3→C5→C6 成立；未开放 command 的页面不因缺 C4 正向能力而伪装为可写。

### 7.4 能力层级划分

| 能力层级 | 内容 |
|---|---|
| 核心闭环 | `C-CON-1~6` 全部共同成立；具体页面可以按 owner 合同裁剪，但每个启用页面必须经过适用节点 |
| 外围增强 | 可配置 dashboard、跨期趋势/比较、批量操作/导出、管理评审模板、个性化首页、跨产品快捷入口 |
| 边界外 | owner truth、授权/治理/合规/readiness 裁决、服务端聚合/数据库、执行/归档/证据本体、其他产品主流程 |

### 7.5 能力节点讨论与停审顺序

| 顺序 | 节点 | Step 8~14 小循环停审必须证明 |
|---:|---|---|
| 1 | C1 | 会话/上下文故事、功能、外部身份引用、失效规则和验收闭合；不签发 credential |
| 2 | C2 | 入口/动作资格故事、功能、正式 visibility 依赖、unknown/撤销规则和验收闭合；不本地 RBAC |
| 3 | C3 | query/view 故事、功能、来源/状态数据、owner query 依赖和验收闭合；query no-write |
| 4 | C4 | 草稿/命令故事、功能、结果状态、owner command 依赖和验收闭合；accepted≠confirmed、unknown 不自动重放 |
| 5 | C5 | 每个管理主题均有 owner、故事/功能/入口/结果边界；blocked 主题不声称 ready |
| 6 | C6 | 降级/错误/恢复/a11y 故事、规则、状态数据、质量和验收覆盖所有前序节点 |

### 7.6 C5 管理主题范围

| 主题 | 正式 owner | 当前范围上限 |
|---|---|---|
| 员工管理 | identity、member-service | 安全查询与正式开放的生命周期/宿主请求入口 |
| 项目与 Workspace 监控 | work、process、workspace | 项目/工作/过程/跨域安全视图；不拥有进度 truth |
| 方法资产 | method-library | 浏览、客户端草稿和正式开放的提交/发布请求 |
| Governance / SoA / AIIA / Control / Gate | governance、artifact | 正式状态、决定和 evidence refs；不产生 verdict |
| 审计与指标 | observability | 只读查询、过滤、drill-down 及正式开放的验证/报告请求 |
| Capability Hub | capability-hub | 注册/暴露/适配/access-review 状态和正式开放的管理请求 |
| Archive | archive | 请求、材料、完整性/兼容性、恢复/handoff 多轴状态与正式开放入口 |
| Sandbox 状态 | sandbox | 只读隔离/运行/清理状态或正式开放入口；不推导 readiness |

## 8. 复杂度判断

六个节点已形成稳定横向骨架；C5 内含八类管理主题，是后续最复杂节点。Step 8~14 必须按 `C1→C6` 顺序逐节点自检，C5 内再按 owner 主题逐项核对，不能一次生成无归属的大表。由于本 Step 只定义能力结构，单文件足够，无需附录。

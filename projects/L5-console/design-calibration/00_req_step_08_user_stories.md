## 6. 改动前后对比与设计取舍

### 6.1 改动前后对比

| 主题 | 旧口径 | 当前口径 |
|---|---|---|
| 故事组织 | 按页面族平铺 | 先按六个闭环节点，再在 C5 展开管理主题 |
| 角色与权限 | 固定职位拥有固定动作 | 产品意图角色提出目标，实际资格由正式 owner 决定 |
| 成功语义 | 页面响应或操作 toast | 用户能区分草稿、提交、receipt、pending 与 owner 正式结果 |
| 异常语义 | 统一错误或空页面 | partial/stale/missing/unavailable/conflict/unknown 可辨且保守 |
| 待建能力 | 作为现成功能叙述 | 使用“正式开放时”或 blocked/read-only 上限，保持 pending |

### 6.2 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 每个页面写完整会话、权限、查询、错误故事 | 页面自包含 | 横向目标重复，追溯矩阵膨胀且容易语义漂移 | 不采用 |
| B. 只写六条抽象故事 | 简洁 | C5 八个管理主题与不同角色价值无法审查 | 不采用 |
| C. C1~C4/C6 写横向目标，C5 按八主题写纵向目标 | 兼顾共同闭环与产品范围，故事主归属唯一 | 后续功能需显式组合横向节点与主题 | 采用 |
| D. 将所有待开放 command 写成核心故事 | 表面完整 | 把上游 pending 伪造成 ready | 不采用；仅保留条件化请求目标 |

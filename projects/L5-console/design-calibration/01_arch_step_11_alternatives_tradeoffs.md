## 3. SOP 问题回答

| 问题 | 回答 |
|---|---|
| 这个仓有哪些主要可选架构方案？ | 当前主线是“单一可信管理交互客户端 + owner 分区视图组合 + 公共交互不变量 + 正式合同门控渐进激活”。有效相邻替代包括：owner 对齐的联邦管理前台、单一客户端但页面局部自主管理交互语义、等待全部 owner 合同闭口后整面激活、以 SDK 强制推送失效为主路径、以及要求所有 owner 同时成功才展示联合视图。 |
| 为什么当前选择主线？ | 它在不拥有跨域 truth 的前提下提供一致导航、安全、状态解释、命令结果、恢复和可访问语义；同时允许不同 owner 按正式合同独立开放并局部降级。 |
| 被放弃方案的主要优点是什么？ | 联邦前台有更强 owner 自主性；页面局部自治初期抽象少；整面激活能形成一致覆盖印象；强制推送可提高失效感知；全源同时成功能降低用户面对 partial 的解释负担。 |
| 为什么即便有这些优点仍不采用？ | 这些收益分别以体验/安全语义分裂、跨页漂移、被最慢合同阻塞、依赖未闭口通知合同、或扩大故障域为代价，不符合当前多 owner 成熟度和局部可用的现实约束。 |
| 当前选择牺牲了什么，换来了什么？ | 牺牲统一时点、表面完整性、页面局部自由度和“永远最新”的错觉，换来 owner truth 唯一、正式结果可解释、故障局部化、合同诚实、公共安全/a11y 语义一致以及可渐进演进。 |
| 哪些方案不配进入本章？ | 数据库/内部 API 直连、本地权限裁决、Console 自有跨域投影/BFF/worker、raw payload 缓存、客户端报告/证据生成等已被前文边界禁止，不是有效候选；框架、图库、协议、缓存介质和重试参数属于后续局部选择。 |

## 5. 有效替代路径判定

| 候选方向 | 是否构成相邻架构替代 | 判定 |
|---|---|---|
| 单一可信管理客户端 vs owner 对齐联邦前台 | yes | 均可经正式服务边界消费且不拥有 owner truth，但会改变运行边界、公共语义和演进责任。 |
| 公共交互不变量 vs 页面局部自治 | yes | 均可维持单一客户端，但会改变安全、结果、故障和 a11y 语义的集中约束程度。 |
| 合同门控渐进激活 vs 全 owner 同步激活 | yes | 均可保持事实诚实，但会改变依赖耦合、能力可用边界和故障范围。 |
| 显式 query/revalidation 基线 vs SDK 推送必要前置 | yes | 均可保持 owner truth，只改变失效感知的必需依赖和恢复主链。 |
| 分 owner 局部视图 vs 全源同时成功的联合视图 | yes | 均不必创造新 truth，但会改变可用性、状态解释和故障传播。 |
| Console 自有跨域投影/BFF/数据库 | no | 已违反职责、数据和运行非目标，不得作为正式候选。 |
| 本地 RBAC / Policy / Gate 或 receipt 即完成 | no | 已违反不可变安全与结果边界。 |
| React vs Svelte、HTTP vs RPC、缓存或图表产品 | no | 点级实现选择，不构成主线路径替代。 |

## 6. 结构化中间产物

### 6.1 方案路径比较表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 单一可信管理交互客户端，以公共交互不变量组织 owner 分区能力 | 在多个正式 owner 之上提供一致入口，同时不建立跨域业务 truth。 | 导航、语境重验、来源状态、命令结果、恢复和 a11y 可共享同一安全语义；跨主题下钻有一致产品边界。 | 中央客户端承担较高的组合与解释复杂度；必须持续防止公共语义膨胀为治理或业务 core。 | 采用 | 这是当前主线的运行与语义结构，公共部分只拥有交互不变量。 |
| owner 对齐的联邦管理前台，在共同入口下由各 owner 独立承载页面 | 让不同领域独立演进管理体验，同时维持各自 truth。 | owner 自主性强，正向能力可随服务独立演进，中央客户端更薄。 | 会重复语境、状态、命令恢复和 a11y 语义，跨主题导航/草稿连续性碎片化；运行和发布边界显著增加。 | 不采用 | 它是合法相邻路径，但当前没有多独立前台的组织或运行 authority，且会削弱 Console 的统一交互价值。 |
| 单一客户端内由公共可信交互语义约束所有页面 | 防止每个页面自行解释权限、partial、unknown、确认和完成。 | 跨页面行为可预测，安全与结果不变量容易审计；owner 差异仍可在分区内保留。 | 需要前置抽象和治理；公共语义必须保持窄而稳定，不能吸收 owner 领域规则。 | 采用 | 该路径与首行共同构成主线，但强调内部约束方式而非运行数量。 |
| 单一客户端内页面局部自治，仅共享导航外壳 | 以较少公共抽象快速承接差异化 owner 页面。 | 单页实现直接，局部变化隔离，早期协调成本较低。 | visibility、状态轴、结果、恢复和 a11y 易逐页漂移，无法证明全局客户端只收紧且不误报完成。 | 不采用 | 它仍可遵守 SDK-only，但不能可靠守住跨页面核心不变量。 |
| 按正式 owner 合同独立门控、渐进激活管理能力 | 在各 owner 合同成熟度不同的情况下交付诚实且可用的子集。 | 未闭口能力可保持 hidden/read-only/partial/blocked，已闭口能力不被最慢依赖拖住；故障与变更按 owner 隔离。 | 用户会看到能力不齐与不同状态，需要清楚说明来源、覆盖和激活条件；维护门控关系有成本。 | 采用 | 这是结构性能力边界，不是版本排期或 feature flag 产品选择。 |
| 等待所有目标 owner 合同闭口后一次性整面激活 | 以统一时点提供覆盖更整齐的管理面。 | 首次公开时能力集合更容易说明，跨主题体验表面一致。 | 所有能力被最慢 owner 耦合，无法利用已闭口只读价值；任何单一合同变化扩大整面阻塞。 | 不采用 | 该路径不违反 truth 边界，但不适合当前合同成熟度不一致的事实。 |
| 显式 query/revalidation 为成立基线，SDK 失效提示仅作可选增强 | 在没有可靠推送合同的前提下保持安全和可恢复的读取主链。 | 主路径不依赖事件送达；提示缺失可通过显式重查恢复，且无需本地 cursor/projection。 | 新鲜度感知可能较慢；用户会看到重验/重查，具体请求预算仍需后续约束。 | 采用 | 这不排斥未来正式提示，只拒绝把它变成当前成立前提。 |
| 正式 SDK 推送失效作为所有管理视图的必要前置 | 更快发现 owner 状态变化，并统一触发刷新。 | 在提示完整可靠时可减少旧影子停留并改善即时感。 | 强耦合未闭口的提示覆盖、连接恢复和失效语义；提示缺失可能被误解为无变化，且仍不能替代正式查询。 | 不采用 | 可在合同成熟后作为增强演进，但当前不能成为安全或正确性前提。 |
| owner 独立有界读取、分区展示并局部降级 | 在不承诺跨域事务的前提下提供联合管理入口。 | 一个 owner 失败不阻断其他区域；来源、覆盖和一致性差异保持可见。 | 页面必须解释 partial/stale/unavailable，用户需理解不同步；不提供单一“当前”结论。 | 采用 | 与 owner truth 分治和区域化故障隔离一致。 |
| 只有所有 owner 同时成功且状态可比较时才展示联合视图 | 避免用户直接面对部分数据和不同步状态。 | 可展示时语境更整齐，页面分支较少。 | 最弱依赖决定整体可用性；无法利用安全的局部数据，且“同时成功”仍不等于跨域原子一致。 | 不采用 | 它合法但扩大故障域，也容易制造虚假的整体一致感。 |

### 6.2 方案边界说明

本章只比较仍服从正式 owner、SDK-only、客户端只收紧和 forbidden-body 边界的相邻路径。数据库直连、本地治理裁决、跨域第二真相、Console BFF/worker 等已被前文排除，不能通过“备选方案”重新打开。框架、协议、存储、刷新参数和组件结构属于后续局部实现，不构成主线替代。安全、诊断、审计和性能的持续约束将在 Step 12 讨论，不在此扩成另一套方案。

### 6.3 当前取舍收束

| 当前主线主要得到什么 | 当前主线明确失去或承担什么 |
|---|---|
| 单一且可审计的客户端交互边界 | 公共交互语义的设计与维护成本 |
| owner truth 独立、来源和状态可解释 | 不提供跨域原子快照或统一 readiness |
| 已闭口能力可渐进开放 | 页面可能呈现 hidden/read-only/partial/blocked 的不齐状态 |
| 单一 owner 故障局部化 | 需要区域级错误、恢复和 a11y 设计 |
| 不依赖事件提示即可成立 | 可能牺牲即时新鲜感并增加显式重查 |
| owner 正式结果和 unknown 安全恢复 | 不能用乐观完成隐藏延迟或不确定性 |
| 后续技术载体可替换 | 当前不能提前锁定框架、协议或缓存便利性 |

## 7. 复杂度判断

五组路径已经覆盖当前真正可能改变架构主线的选择：运行/组织边界、内部公共语义、合同激活、失效协作和多 owner 可用性。更多“候选”要么已违反不可变边界，要么只是框架、协议或组件实现变体。单文件足以完成路径级比较；无需生成产品横评或未来愿望附录。

| 量化性能和支持矩阵 | 不改变 owner 分区与局部降级路径；进入 Step 12 风险和后续设计。 | `open / blocks numeric budgets` |

本步未发现新的上游 blocker，也不要求外部 owner 立即做出技术选择。pending 仅决定主线内各能力的具体激活与参数，不重新打开已收敛路径。

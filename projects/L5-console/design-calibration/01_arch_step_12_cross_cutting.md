## 3. SOP 问题回答

| 问题 | 回答 |
|---|---|
| 安全边界如何处理？ | 所有业务能力经 `L0-sdk` 或正式服务边界；受保护披露和提交前即时重验 actor/scope/visibility/资格；客户端只能收紧；forbidden body 不进入状态、缓存、错误、诊断或导出；直接入口与已打开页面适用同一约束。 |
| 可观测性需要覆盖哪些正式对象和关键链路？ | 需要安全地区分当前语境、owner、query、submit、receipt、reconciliation、degradation 与 recovery 的客户端阶段和正式安全引用；必须能定位来源/阶段而不记录业务正文。诊断 sink 是条件化旁路，失败不改变权限、结果或恢复。 |
| 可用性和韧性需要守住什么底线？ | 语境不可验证时 fail-closed；单一 owner 故障只影响依赖区域；partial/stale/unavailable/conflict/unknown 不被压平；草稿可按安全上限保留；unknown 无正式依据不重放；诊断与提示缺失不能阻断显式重验/重查。 |
| 性能预算是否需要给出口径？ | 需要结构性口径：本地交互不等待无关 owner，owner 查询/回查必须有界且可归因，不做无界 fan-out、重复自动查询或 unknown 重放，慢来源不得造成无说明的全页等待。当前没有数值 authority，不写首屏、P95、SLA、并发或超时数字。 |
| 配置如何管理，哪些配置不应散落？ | 能改变能力可见性、owner 接入、scope、safe-field、结果解释、失效/重查、诊断边界或 a11y 支持的变更必须经过正式合同与统一边界约束；客户端偏好只改变呈现。feature flag、route、菜单和本地配置不得授予资格、启用未闭口合同或改变 owner truth。 |
| 审计与可追溯如何保证？ | 业务/治理/运行声明回指 owner/source/version/result/ref；草稿、提交经历、receipt、pending 与正式结果分层；Console 只保留获准引用和本客户端经历。正式 audit/evidence 归 owner，客户端日志/诊断不能替代。 |
| 哪些横切项与本仓无关，不应机械照抄？ | 服务端密钥轮换、数据库备份/事务恢复、消息队列死信、worker 调度、集群扩缩容、owner 内部审计留存和 SRE 值班均不属于当前客户端运行边界；不为模板完整性写入。 |
| 每个架构单元适用哪些约束？ | §6.3 对九个架构单元逐一标明主要适用横切项与不适用/外部归属；安全、追溯和 a11y 的具体强度依单元职责不同，不用“全局适用”代替判断。 |
| 每个横切项是否通过停审？ | §6.4 七项均已验证作用范围、判断口径、保护目标和未下沉实现。 |
| 跨横切是否存在空话、遗漏或数据/通信冲突？ | §6.5 未发现 unresolved 冲突；诊断最小化与可定位性、性能与安全重验、可用性与 fail-closed 的张力均通过明确优先级收敛。 |

## 4. 当前材料与旧文档问题诊断

| 历史材料 | 问题 | 本步处置 |
|---|---|---|
| 固定 `<2s`、`P95 <500ms`、`99.9%/99.95%` | 缺少场景、环境、窗口、owner 与证据 authority，无法成为当前架构事实。 | 改为有界、可归因、局部隔离和无界放大禁止；数值保持 pending。 |
| “所有管理操作必须由前端留痕” | 可能把客户端日志升级为正式业务 audit/evidence，并复制敏感正文。 | 只保留请求经历和正式 receipt/result/audit/evidence 安全引用；owner 保持正式追溯 truth。 |
| 哈希验证、审计回放、报告导出由 Console 执行 | 将 Observability/Artifact/Archive 的正式能力和正文迁入客户端。 | Console 只呈现 owner 正式结果/ref；无正式 surface 时 read-only/blocked。 |
| 统一日志字段、监控工具与告警阈值 | 属于实现/运维方案，且可能泄露 forbidden body。 | 只定义可定位的最小安全语义和诊断旁路隔离；exact envelope 后移。 |
| 前端权限配置、route guard、角色表和 feature flag | 配置可绕过正式 visibility/资格或误启用未闭口能力。 | 配置只能收紧和组织呈现；正向激活由正式合同与资格决定。 |
| 全局错误页、统一绿色/健康状态 | 扩大 owner 故障并压平 partial/stale/unknown。 | 采用按 owner 区域化故障与多轴状态；只有语境失效等共享前置才影响全局受保护面。 |
| 可访问性留给组件库 | 无法保证资格、结果、危险确认和恢复在非视觉路径语义等价。 | 将 a11y 等价作为跨 C1~C6 的结构约束，具体组件技术后移。 |

## 5. 横切项适用性与边界

| 横切候选 | 是否进入本章 | 判断 |
|---|---|---|
| 安全边界与数据最小化 | yes | 横跨入口、接缝、状态、查询、命令、错误和诊断，直接保护 owner/Policy/Gate 与 forbidden-body 边界。 |
| 审计与可追溯 | yes | 横跨来源状态、请求结果、治理/证据回链和诊断区分；但不授予 Console 正式审计所有权。 |
| 可观测性 | yes | 横跨所有 owner 依赖与客户端阶段，需要可归因失败，同时受数据最小化限制。 |
| 韧性 / 恢复能力 | yes | 横跨语境失效、owner 部分失败、unknown、提示/诊断缺失和草稿连续性。 |
| 性能 / 容量约束 | yes | 多 owner 查询与回查容易产生 fan-out、等待与重放放大，需结构性上限。 |
| 配置与变更控制 | yes | capability activation、可见性、依赖与状态语义不能被前端配置绕开。 |
| 可访问等价性 | yes，项目特定 | 正式 `00` 要求 C1~C6 在辅助技术路径具备相同目标、状态和安全上限。 |
| 服务端备份、密钥轮换、队列恢复、集群扩缩容 | no | 属于外部 owner / 基础设施或未存在的 Console 服务端运行单元。 |
| 审计留存年限、告警规则、压测脚本、浏览器清单 | no，后移或外部 | 属于制度、配置、测试或 owner 合同，不是本步架构约束；确切 authority 仍 pending。 |

## 6. 结构化中间产物

### 6.1 横切关注点约束表

| 横切关注点 | 作用范围 | 约束要求 | 保护目标 | 说明 |
|---|---|---|---|---|
| 正式访问与最小披露安全边界 | 入口/路由、外部正式接缝、受保护视图、受控意图、直接链接、客户端状态 | 业务访问只经正式边界；每次披露/提交受当前 actor/scope/visibility/资格约束，无法验证即 fail-closed；客户端状态和配置只能收紧。 | 保护身份/授权/Policy/Gate owner，不让旧 session、菜单、URL、缓存或页面开关形成旁路。 | 该约束持续作用于所有页面和两类关键交互，不能由单个 route guard 代替。 |
| Forbidden-body 与外围输出最小化 | owner-safe 结果、状态承载、草稿、错误、日志、诊断、链接、导出入口 | 只允许任务所需安全摘要/ref；credential、授权依据、raw/hidden payload 和业务/治理/证明/执行正文不得进入 Console 生命周期；无法证明安全即裁剪或拒绝。 | 保护外部正文单一归属与最小披露，阻断错误/诊断/导出旁路。 | 它跨越正常与失败路径，不是某个序列化器或日志过滤器的局部规则。 |
| 正式结果与来源可追溯 | owner-safe 读取、多 owner 组合、意图提交、结果回查、Governance/Artifact/Observability 等审阅入口 | 可被解释为业务/治理/运行状态的声明必须保留 owner/source/version/freshness/coverage 或正式 result/ref；草稿、请求经历和正式结果分层；无引用时标 missing/unknown。 | 保护读者能够区分来源事实、客户端经历和正式结果，避免客户端诊断冒充 audit/evidence。 | 这是跨数据、交互和主题的追溯边界，不要求 Console 生成或保存正式审计正文。 |
| 最小安全可观测性 | 客户端语境、owner 依赖、query、submit、receipt、reconciliation、degradation、recovery 与诊断外围 | 用户与维护者应能在不暴露正文的情况下判别 owner、客户端阶段、已知状态和安全关联引用；诊断 sink 缺失/失败不改变业务语义。 | 保护故障可定位性以及诊断与业务、审计之间的语义隔离。 | 本项规定“必须可见什么”，不规定监控产品、字段 schema、采样、告警或保留策略。 |
| 局部故障隔离与保守恢复 | 语境前置、各 owner 查询区、命令结果、可选提示、诊断旁路、本地草稿和安全影子 | 共享安全前置失败时收紧；owner 失败按依赖区域隔离；状态不压平；恢复使用重验、重查、正式 reconciliation、退出或安全保留草稿；unknown 无依据不重放。 | 保护故障不会扩大、被掩盖或导致重复副作用，并保持可恢复的交互连续性。 | 横跨运行承载、数据一致性和通信主链，不是重试脚本或 on-call 手册。 |
| 有界且可归因的交互负载 | 本地交互、多 owner 查询/分页/下钻、资格重验、结果回查、失效提示后的刷新 | 本地状态不等待无关 owner；外部请求按必要 owner 有界发起；慢源不得无说明阻塞全页；禁止无界 fan-out、重复自动刷新和 unknown 命令重放。 | 保护多 owner 管理面在规模增长时不发生请求放大、尾部依赖扩散或安全重验被性能优化绕过。 | 当前约束结构和判断口径，不伪造延迟、并发、频率、TTL 或 SLA 数值。 |
| 正式合同约束下的配置与变更控制 | owner 接入、能力激活、入口/动作姿态、safe-field、状态语义、失效/诊断边界、客户端偏好 | 影响正向能力与安全语义的变更必须以正式合同/资格为上限；route、菜单、feature flag、本地配置和偏好不得授权、补合同、改变结果或 truth；未知配置采用更保守姿态。 | 保护已收敛边界不被运行配置或产品开关偷偷改写，并让未闭口能力保持诚实。 | 本项约束配置能改变什么，不定义配置中心、文件格式、键名或发布流程。 |
| 可访问等价的正式交互语义 | C1~C6 的语境/导航、资格、读取、草稿/确认、结果、错误与恢复 | 键盘和受支持辅助技术必须可理解并完成与视觉路径相同的获准目标；状态不只靠颜色/位置/动画；焦点、播报与恢复不能放宽或缩窄正式语义。 | 保护不同交互方式具有同一安全边界、状态解释、结果判断和恢复能力。 | 它横切所有核心目标，不能等到视觉实现完成后作为样式修补。 |

### 6.2 横切主线映射

| 横切关注点 | 主要作用的既有主线 / 章节 | 主要判断口径 |
|---|---|---|
| 正式访问与最小披露 | 职责、系统上下文、依赖、数据、关键交互 | 无正式语境/资格不披露不提交；无旁路。 |
| Forbidden-body 最小化 | 数据所有权、外部接缝、错误/诊断/导出外围 | 禁止正文零进入；无法证明安全即裁剪。 |
| 正式结果与来源可追溯 | 数据一致性、查询/命令、管理主题 | 所有正式声明可回指 owner/ref；客户端不补造。 |
| 最小安全可观测性 | 运行承载、外部交互、失败/恢复 | 可定位 owner 与阶段；诊断失败不改业务语义。 |
| 局部隔离与恢复 | 容器、数据、交互、方案主线 | 故障不扩散/掩盖；unknown 不重放。 |
| 有界交互负载 | 多 owner 组合、查询/重验/回查 | 无界 fan-out、无关等待和副作用重放均不成立。 |
| 配置与变更控制 | 依赖、技术机制、合同门控演进 | 配置只能在正式合同内组织或收紧。 |
| 可访问等价性 | 所有 C1~C6 支撑语义 | 同一目标、状态、安全上限与恢复。 |

| 正式语境与资格引用 | 安全、追溯、韧性、配置 | 引用最小且可失效，使用时确认当前有效；撤销/过期/冲突即收紧；配置不能延长授权。 | 可观测正文、身份凭证和授权证明不得落入本影子。 | `pass` |
| owner-safe 视图影子 | 安全、追溯、观测、韧性、性能、配置 | 影子按 owner 分区、带来源状态、可失效/撤除；刷新有界；safe-field/生命周期未闭口取更小上限。 | 不做 cursor/replay/rebuild、持久业务缓存或 owner 内部遥测。 | `pass` |
| 正式请求与结果引用 | 安全、追溯、观测、韧性、配置 | 引用仅来自正式 surface，关联请求经历但不等同业务正文；失效时 unknown/blocked；不得由配置或 toast 合成完成。 | 正式结果生命周期、audit/evidence 正文和幂等事实归 owner。 | `pass` |

逐单元结论：九个架构单元均有与自身职责匹配的横切约束，没有以“全局适用”省略判断。服务端密钥、数据库、队列、集群、正式审计留存和 owner 内部监控均未被机械分配给客户端单元。

## 7. 复杂度判断

本步包含八项正式横切约束并作用于九个架构单元，复杂度来自安全与可用、可定位与最小化、性能与即时重验三组张力。通过作用范围、判断口径和优先级即可在架构层闭合，无需编造数值或实施方案。单文件足以完成逐项停审与跨项审计；exact 配置、诊断 envelope、测量预算和辅助技术矩阵应后移到相应后续文档。

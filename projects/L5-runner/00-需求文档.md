## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的价值不止于“让 AI 团队产出代码”,还在于让用户**真正把产出跑起来并使用**。很多非开发者用户即使拿到了代码、文档、发布包,也不知道如何安装、配置、启动、诊断失败。Runner 因此必须把“交付物”变成“可运行的软件实例”:用户登录后看到自己项目的 Release 列表,选择某个版本,由系统拉取 Release 包,在受控沙箱中启动,并提供一键停止、查看日志与资源情况的能力。没有 Runner,平台会停留在“产出交付物”而不是“交付可用软件”的阶段。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 3 当前) | 痛点 |
|---|---|---|
| 仓文档 | 只有 README 骨架 | 端侧产品型第三批样板尚未建立 |
| Release 真相源 | `L1-artifact` 已有完整 00 需求样板 | 端侧如何消费 release/baseline 尚未仓级化 |
| 沙箱底座 | `L4-sandbox` 已完成 00/01 | Runner 如何复用 sandbox 接口还未写成产品需求 |
| SDK 草案 | 已明确所有端侧产品经 SDK 连 Server | Runner 的客户端接入边界未正式落地 |
| 运行体验 | README 已给出冷/热启动目标 | 主路径、失败路径与资源管理口径未成文 |

### 2.3 为什么要做(量化依据)

- `product/产品矩阵.md` 明确 Runner 是 **② 独立产品**，不是 Chat/Console 的附属功能
- README 已提出核心性能目标：**冷启动 < 30s、热启动 < 5s、多项目并发 ≥ 10**
- `L4-sandbox` 已把“Runner 与 Runtime 共用接口”列为硬约束,Runner 是这条约束的主要消费者之一
- 若没有 Runner,AI 团队的交付对非开发者仍停留在“拿到代码不会用”

### 2.4 业务问题 vs 技术问题

- **业务问题**:非开发者用户如何低门槛地试用、运行、停止和观察 AI 产出的软件
- **技术问题**:Release 包获取、版本选择、沙箱启动、多实例资源管理、日志采集、显式版本 pin、失败恢复、主机安全隔离

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 用户打开 Runner,查看自己项目的 Release 列表
2. 用户选择一个 Release,在本地受控环境中启动
3. 用户查看运行状态、资源用量与日志
4. 用户一键停止、删除实例并清理本地资源
5. 用户在已有缓存情况下快速重启某个版本

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **非开发者管理者**,我想要 **选择一个 Release 并一键运行**,以便 **不用懂部署也能试用 AI 团队产出的软件** |
| 优先级 | P0 |
| 验收条件 | **Given** 有一个 approved Release **When** 用户点击 Run **Then** Runner 拉取并在沙箱中成功启动,返回本地访问入口 |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **用户**,我想要 **看到当前运行实例的状态和日志**,以便 **在启动失败或运行异常时知道发生了什么** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个运行中的实例 **When** 用户打开详情面板 **Then** 能看到状态、日志和基础资源信息 |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **用户**,我想要 **一键停止并清理运行实例**,以便 **不留下无用进程和资源占用** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个运行中的实例 **When** 用户点击 Stop/Clean **Then** 实例停止且临时资源被清理 |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **平台**,我想要 **确保 Runner 只运行 approved/baselined Release**,以便 **用户不会误运行不可信或未验收产物** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个未 approved 的 Release **When** 用户尝试运行 **Then** Runner 拒绝启动并显示原因 |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **演示者**,我想要 **在本地已有缓存时快速热启动 Release**,以便 **演示时不被冷启动拖慢** |
| 优先级 | P1 |
| 验收条件 | **Given** 本地已有完整缓存 **When** 用户再次运行同版本 **Then** 启动时间 < 5s |

### 5.3 替代流程

- Release 下载失败 → 显示失败原因并允许重试
- 沙箱启动失败 → 展示错误摘要与日志,不落成半启动实例
- 本地资源不足 → 拒绝启动并给出可理解提示
- 用户切换版本 → 必须显式选择版本,不允许默认 latest

## 6. 功能需求

### 6.1 功能清单与优先级

| ID | 功能名称 | 优先级 | 依赖 | 描述 |
|---|---|---|---|---|

| F-005 | 一键停止 / 清理 | P0 | sandbox | 停止实例并清资源 |
| F-006 | approved / baselined 校验 | P0 | artifact / governance | 非合格 Release 拒绝运行 |

### 6.2 业务规则表

| 规则 ID | 条件 | 结果 |
|---|---|---|
| BR-001 | Release 非 approved / baselined | 拒绝运行 |
| BR-002 | 版本未显式选择 | 不自动使用 `latest` |
| BR-003 | 用户无项目权限 | 不显示或不可启动该 Release |
| BR-004 | Stop/Clean 成功 | 运行实例与临时资源必须一起清理 |
| BR-005 | 沙箱启动失败 | 不得留下残余半启动状态 |
| BR-006 | 多实例并发 | 端口冲突必须显式处理,不能静默覆盖 |

## 9. 数据需求

### 9.1 核心业务实体

| 实体 | 归属域 | 聚合根 | 生命周期 |
|---|---|---|---|
| Artifact(kind=release) | artifact | Artifact | initiated → approved / published / archived |
| Project | work | Project | draft → active → archived / dissolved |
| SandboxExecution | sandbox | SandboxExecution | created → running → exited / killed |
| LocalRunSession | Runner 本地视图对象 | 本地 | launching → running → stopped / failed |

### 9.2 数据关系图

```text
Runner
  ├─ Project -> Release list
  ├─ selected Release -> local cache
  ├─ cached Release -> sandbox execution
  └─ sandbox execution -> status/logs/resources
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| 本地 Release 缓存 | 中短期 | 本地缓存可重建 | 手动或自动清理 |
| 运行会话状态 | 会话级 | 仅本地短保留 + 可上报摘要 | 自动淘汰 |
| 错误日志摘要 | 短期 | 可选上传 observability/chat | 自动清理 |
| 访问历史 | 短期 | 本地偏好 | 可清除 |

### 9.4 隐私与合规要求

| 数据字段 | 敏感级别 | 保护措施 | 合规依据 |
|---|---|---|---|
| 本地运行日志 | 中高 | 仅用户本地可见,上传需显式授权 | 最小暴露原则 |
| Release 元数据 | 中 | 按项目权限控制 | 项目权限边界 |
| 本地缓存路径 | 中 | 不跨用户泄漏 | 本地安全基线 |

## 12. 风险与待确认事项

### 12.1 已知风险(分常见 / 边缘)

**常见风险**:

| ID | 风险 | 影响 | 缓解策略 |

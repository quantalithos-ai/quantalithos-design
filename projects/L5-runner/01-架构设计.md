## 2. 业务背景与驱动力

> 校准来源：
> - `design-calibration/01_arch_step_01_requirements_baseline.md`
> - `design-calibration/01_arch_step_02_goals_constraints.md`
>
> 延伸阅读：建议继续阅读上述文件的“架构基线卡”“业务驱动力”“架构目标表”和“当前阶段可接受取舍”。

Runner 的核心问题不是“在本机拉起一个进程”，而是让用户在端侧明确知道：选择了哪个不可变版本、正式 authority 是否适用、本地材料是否完整、请求是否仅被接收还是已经运行、是否可以安全停止和清理，以及失败时哪些结论来自哪个 owner。若本地 cache、PID、端口、ACK 或日志被当作正式事实，Runner 就会成为第二个 Release、Runtime、Sandbox 或 Observability 真相中心。

| 架构目标 | 说明 |
|---|---|
| 承载端侧选择与运行意图的独立真相 | 用户选择、请求关联、控制意图和恢复姿态需要独立于上游执行真相，否则无法表达 pending/unknown。 |
| 守住正式 authority 到本地资格的单向承接 | 只有正式 Release/Governance 结果才能形成可取得/可运行资格，本地状态不能反向批准。 |
| 让取得、验证、请求、执行、清理和预览保持多轴语义 | 单一 RunnerRun 状态会掩盖 owner 差异和未知副作用，破坏安全验收。 |
| 支撑跨平台本地观察而不拥有全局资源调度 | 端口、路径、容量和平台能力需要可解释，但不能被本地 probe 伪装成 Sandbox allocation 或 lease truth。 |
| 让恢复路径以保护和对账为中心 | 断线、休眠、重启和 lease 变化必须能冻结副作用并进入 reconcile/manual-review，而非盲目重放。 |
| 以安全摘要连接预览、诊断和正式交接 | 用户需要可理解反馈，但 raw body、secret、evidence 和 verdict 必须留在 owner 边界。 |
| 保持入口形态和外部技术可替换 | GUI、CLI、平台壳、下载 transport 和 Sandbox backend 不应决定核心语义或形成私有依赖。 |

## 3. 约束条件

> 校准来源：
> - `design-calibration/01_arch_step_01_requirements_baseline.md`
> - `design-calibration/01_arch_step_02_goals_constraints.md`
> - `design-calibration/01_arch_step_14_risks_open_questions.md`
>
> 延伸阅读：建议继续阅读上述文件的“架构硬约束”“不可变约束表”“架构非目标表”和“风险表”。

### 3.1 不可变约束

| 约束 | 说明 |
|---|---|
| 不拥有上游 truth | Runner 不定义 Release、approval、execution、boundary、lease、cleanup、evidence 或 archive 的正式生命周期。 |
| 不允许隐式版本 | `latest`、默认分支、目录排序和历史选择不能成为副作用输入。 |
| 不允许 owner seam 旁路 | 外部能力必须经 L0-sdk 或正式公开 API/adapter；不得读取相邻源码、共享内部存储或调用私有 backend。 |
| 不把局部观察升级为正式状态 | PID、端口、cache、HTTP 200、ACK、toast、stdout/stderr 只能作为局部观察或提示。 |
| 未知状态保护副作用 | unknown、stale、conflict、reconcile_required 时，危险控制和清理必须挂起。 |
| 保护材料优先于本地便利 | lease/capture/handoff/retention/orphan 保护未解除时不得删除或淘汰。 |
| 诊断最小暴露 | preview、diagnostic、handoff 只允许 redacted、bounded、带来源和 freshness 的安全材料。 |
| 读路径不修复事实 | 查询、刷新、重连、渲染和投影重建不得暗中批准、修复、重放或清理上游 truth。 |

### 3.2 当前阶段可接受取舍

| 取舍 | 当前口径 |
|---|---|
| 精确下载/签名/撤销协议 | 当前只定义 authority/integrity seam 和 fail-closed 语义，等待 `RUN-UP-001/002`。 |
| 精确 Sandbox/Runtime 控制合同 | 当前只定义 request、lease、lifecycle、cleanup 和 reconcile 边界，等待 `RUN-UP-003/004`。 |
| 平台资源容量和恢复时限 | 当前保留冲突可见、保护和人工复核口径，不给无来源数字，等待 `RUN-UP-007`。 |
| Archive 浏览和恢复 | 当前作为外围引用边界，不进入启动、运行或清理主链，等待 `RUN-UP-006`。 |
| Observability 正式交接 | 当前只承载安全诊断摘要和 handoff posture，等待 `RUN-UP-005`。 |
| GUI/CLI/桌面框架 | 当前只要求入口形态可替换和共享语义，不锁定框架或进程模型。 |

### 3.3 架构非目标

| 非目标 | 不展开原因 |
|---|---|
| 不设计 Release/Artifact 服务架构 | 版本、manifest、digest 和生命周期属于 Artifact owner。 |
| 不设计 Governance 决策架构 | approval、policy、gate 和 revoke 属于 Governance owner。 |
| 不设计 Runtime loop 或 Sandbox backend | 执行和隔离真相属于相邻 owner；Runner 只定义公开接缝。 |
| 不设计 Observability evidence/report pipeline | 本地诊断不拥有正式证据链。 |
| 不设计生产部署、集群调度或公网分享 | 这些事项与端侧受控试用入口的架构主线不同。 |
| 不设计数据库表、DTO、API 路径、函数或源码目录 | 这些属于后续概要/详细设计，且必须等待上游合同。 |

批量预取、多运行比较和 Archive 浏览保持外围增强；具体 GUI/CLI、桌面框架、语言、进程模型、数据库和容器 backend 均未定稿。

## 4. 职责边界

> 校准来源：
> - `design-calibration/01_arch_step_03_responsibility_boundary.md`
>
> 延伸阅读：建议继续阅读上述文件的“职责边界表”“边界红线”和“单元级职责停审前提”。

### 4.1 职责边界表

| 职责项 | 类型 | 说明 |
|---|---|---|
| 可信语境与显式 Release/version 选择 | 做 | Runner 拥有用户选择及其 generation，不改变 Release truth。 |
| Authority、取得和完整性资格的本地承接 | 做 | 组合 owner 结果与本地材料姿态，形成本地是否可继续的安全 view。 |
| 正式 Sandbox/Runtime 请求与生命周期展示 | 做 | 表达用户意图、关联和 owner status，不拥有 execution truth。 |
| 端侧资源冲突与平台能力观察 | 做 | 展示 local probe 和影响，不拥有全局 allocation/scheduler。 |
| 停止、清理、保护与断线恢复姿态 | 做 | 组织意图、保护和 reconcile；完成结论来自 owner。 |
| 安全预览、失败诊断与 handoff 姿态 | 做 | 提供 bounded/redacted 用户解释，不生成 evidence/report/verdict。 |
| Release/Artifact 创建、修改、发布、撤销和 baseline truth | 不做 | 版本和产物生命周期属于 Artifact owner。 |
| Governance Policy/Gate/Decision/Approval/Control | 不做 | 批准和治理决定属于 Governance owner。 |
| Project/ProjectMember/Work truth | 不做 | Runner 只消费项目语境和可见性，不伪造成员资格。 |
| Runtime loop、checkpoint、outcome、scheduler | 不做 | 执行真相属于 Runtime owner。 |
| Sandbox boundary、policy、lease、reaper、cleanup guard、私有 backend | 不做 | 隔离和清理真相属于 Sandbox owner。 |
| Observability audit/evidence/report/verdict/signoff | 不做 | 本地诊断只能交接安全摘要，不能升格为审计结论。 |
| Archive package/restore truth | 不做 | Archive 只作为条件性历史引用，不参与运行成功判定。 |
| 本地 PID/端口/cache 作为运行或清理成功 | 易混淆职责 | 它们是观察或材料状态，不是 owner truth。 |
| Sandbox accepted 作为 running | 易混淆职责 | accepted 只表示请求被接收，running 必须有正式状态来源。 |
| 本地日志/telemetry 作为正式 evidence | 易混淆职责 | 本地材料须 redaction 并经过正式 handoff，仍不等于 evidence。 |
| SDK/Bus/适配器实现 | 易混淆职责 | Runner 消费公开 seam，不拥有 SDK、Bus 或相邻仓私有实现。 |

### 4.2 边界红线

- RunnerRun 或等价本地记录只能表达选择、意图、请求关联、观察与展示姿态，不得成为 Runtime/Sandbox execution truth。
- 本地 authority cache 必须在启动前重新验证，不得绕过当前适用性、撤销、过期或 source binding。
- 查询、刷新和恢复必须 no-write，不得隐式批准、修复、重放或清理上游 truth。
- Active lease、capture、handoff、retention 或 orphan 保护未解除时，清理不得删除或淘汰材料。
- 预览、诊断与 handoff 不得穿透 secret/raw body，也不得生成 evidence/report/verdict/signoff。
- 跨域协作只经 SDK/API/adapter/reference，不得共享内部事务、存储或源码路径。

### 9.1 数据归属

| 数据项 | 数据类型 | 归属说明 | 边界说明 |
|---|---|---|---|
| 显式选择、selection generation、失效姿态 | 正式真相数据 | Runner 拥有用户在本地选了什么及其生命周期。 | 不拥有所选 Release/version 本身。 |
| 运行/控制/清理意图、请求关联、reconcile posture | 正式真相数据 | Runner 拥有用户意图和本地处理姿态。 | accepted/running/terminal/cleanup result 仍来自 owner。 |
| 取得进度、cache/quarantine/protection、完整性验证姿态 | 正式真相数据 | Runner 拥有本地材料和验证过程的状态。 | locator、manifest、签名 authority 和 Release 正文不归 Runner。 |
| 端侧资源观察、连接、cursor、generation、恢复标记 | 正式真相数据 | Runner 拥有带 freshness 的本地观察和恢复进度。 | 不拥有全局 allocation、lease、scheduler 或 owner cursor。 |
| 安全展示组合、预览裁剪和本地失败分类 | 正式真相数据 | Runner 拥有展示组合与解释姿态。 | 不拥有 raw output、diagnostic source、evidence 或 verdict。 |
| Release/baseline/approval applicability、revoke/expiry/visibility | 快照 / 投影数据 | 来自 Artifact/Governance，只为当前选择与资格消费。 | snapshot 存在不等于当前 authority；不得反写。 |
| Sandbox request/boundary/lease/execution/cleanup、Runtime result | 快照 / 投影数据 | 来自 Sandbox/Runtime 的 owner-safe view。 | ACK、PID、端口和本地日志不得升级快照。 |
| Observability diagnostic/handoff、Archive restore/archive posture | 快照 / 投影数据 | 条件性消费安全摘要与状态。 | receipt 不等 evidence；archive 不等运行或清理成功。 |
| Release、ArtifactVersion、Baseline、Decision、Request、Boundary、Lease、Run、Output、Diagnostic、Handoff、Archive refs | 引用关系数据 | Runner 只保存安全关联和 source/correlation。 | ref 存在不代表正文可见、状态有效或结果成功。 |
| actor/session/project、platform capability、source version/digest/cursor refs | 引用关系数据 | 用于绑定语境、平台和来源版本。 | scope/version 变化时必须失效或重新验证。 |
| Release/Artifact/manifest/policy/approval 正文、签名私钥、locator secret | 明确不拥有的正文 / 真相 | 属于 Artifact/Governance/安全 owner。 | 不进入 metadata、日志、preview、telemetry 或 handoff 正文。 |
| Runtime context/memory、Sandbox raw stdout/stderr/capture、Observability audit/evidence/report、Archive bundle、Project/Work 正文 | 明确不拥有的正文 / 真相 | 属于对应 owner。 | Runner 只消费允许的 summary/ref。 |
| token、secret、credential、private key | 明确不拥有的正文 / 真相 | Runner 不拥有其生命周期。 | 仅在正式安全边界短暂使用，不得进入普通持久化。 |

### 9.2 一致性策略

| 数据关系 / 场景 | 关联数据类型 | 一致性口径 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 选择与 selection generation 变化 | 正式真相数据 ↔ 正式真相数据 | 本地强一致 | 不生成部分选择；旧 generation 显式 invalidated | 防止已发请求被静默改写。 |
| 意图、请求关联与本地保护状态变化 | 正式真相数据 ↔ 正式真相数据 | 本地强一致 | 保持 pending/unknown，不回填为成功 | 本地安全门禁必须原子地表达当前姿态。 |
| source authority 到本地资格 | 快照 / 投影数据 ↔ 正式真相数据 | 来源版本一致 + 启动前重新验证 | stale/conflict/revoked 时资格失效并 blocked | 本地资格不能超越 owner freshness。 |
| 下载材料与 manifest/digest/source binding | 正式真相数据 ↔ 引用关系数据 | 内容绑定一致 | quarantine/invalid，不修改材料或 source | 传输完成不能替代完整性成立。 |
| Sandbox/Runtime owner status 到本地展示 | 快照 / 投影数据 ↔ 正式真相数据 | 最终一致 + source attribution | 显示 stale/unknown/unavailable，不用 PID 补齐 | 允许展示延迟，不允许语义升级。 |
| control/cleanup unknown 与恢复 | 正式真相数据 ↔ 快照 / 投影数据 | 对账一致 | 冻结自动重放，进入 reconcile/manual-review | 防止重复副作用和误删。 |
| 平台 probe 与 owner allocation/lease | 正式真相数据 ↔ 快照 / 投影数据 | 冲突显式一致 | 显示 conflict，以 owner 资格为准 | 本地观察只说明端侧现状。 |
| preview/diagnostic/handoff | 正式真相数据 ↔ 引用关系数据/明确不拥有的正文 | 来源/可见性/redaction 一致 | partial/restricted/blocked，禁止拉取或保存正文补齐 | 保护敏感内容与审计边界。 |
| 本地状态重建 | 正式真相数据 ↔ 正式存储承载 | generation/cursor 一致 | 无法确认则 unknown/manual-review | 重建恢复姿态，不推进 owner cursor。 |

本地强一致只适用于 Runner-owned 状态；跨 owner 不声明分布式强一致。最终一致视图仍必须暴露 source、freshness 和缺口，不能乐观升级。任何 snapshot/ref 反写、共享事务、正文复制或未知副作用自动重放都被禁止。

## 10. 关键交互与通信方式

> 校准来源：

>
> 延伸阅读：建议继续阅读上述文件的“关键交互场景表”“通信方式判断表”“按架构单元的交互方式与停审”和“跨交互边界审计”。

| 交互场景 | 交互边界 | 交互目的 | 边界说明 |
|---|---|---|---|
| 可信语境与显式选择确认 | 入口 ↔ 选择/资格 ↔ context/Artifact/Governance 接缝 | 确认 actor/scope、immutable version、visibility 和 authority posture | 选择是 Runner-owned；Release 与批准仍由 owner 裁决。 |
| 取得、完整性与平台资格推进 | 后台取得 ↔ Artifact 接缝 ↔ 本地材料/平台 | 形成 transfer、quarantine、integrity、compatibility 姿态 | 传输完成不等 qualified；策略与 manifest 不由 Runner 创建。 |
| 正式运行请求提交 | 本地意图 ↔ Sandbox/Runtime 接缝 | 提交绑定 generation、qualified refs 的受控请求 | 接收不等运行；`accepted ≠ running`。 |
| 执行与控制状态送达 | Sandbox/Runtime owner ↔ 生命周期展示 | 送达 boundary、lease、running、terminal 和控制结果 | PID、端口、连接或 toast 不补齐 owner 状态。 |
| 端侧资源冲突判断 | 资源保护 ↔ 平台边界 ↔ owner allocation/lease view | 解释 probe 与 owner 资格冲突 | probe 是观察，不是抢占、分配或清理真相。 |
| 停止与清理意图及确认 | 本地意图/资源保护 ↔ Sandbox 接缝 | 分离 intent、receipt、control result 和 released | active protection 未解除时不得将本地删除当清理完成。 |
| 断线、重启与未知副作用对账 | 后台恢复 ↔ owner-safe status/ref ↔ 本地状态 | 重验语境、generation、lease 和未决意图 | unknown 不自动重放，无法确认时进入 manual-review。 |
| 输出预览与失败诊断读取 | 诊断/预览 ↔ Runtime/Sandbox/Observability safe view | 提供 bounded/redacted 用户解释 | 不取得或常驻 raw body，不生成 evidence/report/verdict。 |
| 安全诊断交接 | 诊断承载 ↔ Observability handoff | 交接允许的摘要与 refs，展示交接姿态 | receipt 只证明交接状态，不证明 evidence/verdict/signoff。 |

| 交互场景 | 推荐通信方式 | 不宜采用的方式 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 可信语境与显式选择确认 | 同步请求 / 响应 | 异步推送或旧 cache 代替当前选择与 authority 判断 | not-visible、stale、conflict、revoked、expired、blocked 或明确失败 | 用户副作用前必须获得当前可解释结论。 |
| 取得、完整性与平台资格推进 | 后台任务 / 延后承接；关键 source/authority 判断同步收口 | 长时传输阻塞入口，或后台默认为 qualified | pending、paused、incomplete、quarantine、invalid 或 blocked | 本地长任务可延后，资格门禁仍须显式成立。 |
| 正式运行请求提交 | 同步请求 / 响应 | 先显示 running 再后台补正式请求 | not-sent、accepted、pending、rejected、unknown；unknown 冻结重放 | 同步边界只收口请求是否被正式承接。 |
| 执行与控制状态送达 | 异步事件 / 回调 + 同步只读查询 | 持续同步轮询或只信事件缓存 | stale、unknown、unavailable；必要时只读查询对账 | 事实由 owner 成立，事件与查询共同服务消费。 |
| 端侧资源冲突判断 | 同步请求 / 响应 | 无约束后台抢占或以 probe 替代 lease | conflict、stale、unknown 或 blocked，不静默覆盖 | 用户提交前需即时理解冲突，owner 资格优先。 |
| 停止与清理意图及确认 | 同步提交意图 + 异步结果送达 | 将提交 ACK 当控制或清理完成 | requested、accepted、protected、pending、unknown 或 blocked | 意图接收和最终副作用分属不同边界。 |
| 断线、重启与未知副作用对账 | 后台对账 + 同步只读查询 | 以重连成功触发自动 replay | reconcile、manual-review、stale 或 unavailable | 任何新副作用前必须重新收口。 |
| 输出预览与失败诊断读取 | 同步安全查询；派生刷新可后台承接 | 原始持续流作为 Runner 正式 truth | partial、restricted、stale、blocked 或 unavailable | 派生延迟不得被隐藏。 |
| 安全诊断交接 | 同步提交意图 + 异步结果/后台延后承接 | 阻塞运行终态或把 ACK 当正式证据 | pending、accepted、blocked、failed 或 delivered | 交接独立于运行和审计结论，可延后但可追踪。 |

同步成功只表示该同步边界内的判断或意图接收成立，不表示执行或清理完成。异步送达不使本地投影成为 owner truth；后台任务不得修复上游 truth 或盲目补偿未知副作用。具体 API、事件名、topic、DTO、重试算法和时序后置。

## 11. 关键技术选型

> 校准来源：
> - `design-calibration/01_arch_step_10_technology_selection.md`
>
> 延伸阅读：建议继续阅读上述文件的“关键技术机制表”“当前不采用或后置的选择”和“技术边界说明”。

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 | 说明 |
|---|---|---|---|---|
| 正式 SDK/API/adapter 接缝隔离 | 防止入口穿透 owner truth 和私有实现 | 符合 owner 边界与 L5 依赖规则 | 适配/版本/错误/可见性复杂；上游缺口形成 blocker | 接缝决定跨域依赖结构，属于架构机制。 |
| Local truth、external snapshot/ref、forbidden body 分离 | 防止本地状态成为第二 truth | 支撑恢复体验且不复制正文 | 必须处理 source/freshness/visibility 与 stale/partial/unknown | 同时约束存储、交互和展示。 |
| 多轴资格与生命周期状态 | 防止单一 success 压平不同 owner/成功条件 | 守住 `accepted ≠ running` 等红线 | 状态组合、展示和后续合法迁移更复杂 | 长期决定核心语义。 |
| Selection generation 与内容绑定 | 防止选择切换后旧请求/cache 被静默复用 | 每个副作用可追溯到 immutable source | 选择变化会使旧资格失效并触发重验 | 影响一致性、幂等和恢复主链。 |
| Quarantine→qualified 受保护晋级 | 防止传输完成替代完整性 | 只有正式内容绑定和平台资格可放行 | 引入中间姿态、保护元数据和淘汰约束 | 是下载与运行边界之间的保护手段。 |
| 同步/异步/后台三路径分离 | 分离即时判断、owner 事实送达和长时本地工作 | 保持入口可解释且后台不创造成功 | 增加 pending/stale/failed/reconcile 的追踪成本 | 直接影响运行承载和一致性。 |
| Unknown 冻结与查询优先对账 | 防止重连/超时后重复副作用 | 安全性优先于自动恢复速度 | 可能进入 manual-review，依赖 owner read surface | 是跨故障边界的副作用保护。 |
| Redaction-first、body-bounded 预览/交接 | 防止 raw output/secret 冒充 evidence | Runner 只需解释和交接安全线索 | 信息可能 partial/restricted，需要真实性提示 | 同时约束数据、展示、诊断和 handoff。 |
| Local probe 与 owner allocation/lease 双视图 | 防止本地观察升级为调度/清理真相 | 同时满足跨平台体验和 owner 权威 | 观察冲突/滞后时必须保守阻塞 | 影响跨平台资源与清理边界。 |

当前不锁定 Tauri/Electron、Rust/TypeScript/Go、本地数据库、HTTP/RPC/MQ 产品、重试参数或性能数字。Docker、gVisor、Firecracker 和本机进程直管不是 Runner 的直接选型，只能位于 Sandbox owner 的实现边界。

## 12. 备选方案与取舍

> 校准来源：
> - `design-calibration/01_arch_step_11_alternatives_tradeoffs.md`
>
> 延伸阅读：建议继续阅读上述文件的“方案路径比较表”“当前取舍摘要”和“方案边界说明”。

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|
| 同一端侧产品内逻辑分离入口、编排、后台和本地状态 | 在保持边界清晰的同时控制初期运行承载复杂度 | 共享一致语义，控制早期分布式复杂度，保留拆分点 | 必须防止同部署退化为职责混合 | 采用 | 与 Step 6 的逻辑承载角色一致，不预判进程模型。 |
| 初始即物理拆分入口与后台 | 隔离长时取得、恢复与诊断负载 | 故障/资源隔离更强，可独立伸缩 | 引入跨进程状态、部署、版本和恢复协调，缺 workload 依据 | 不采用 | 有效但当前缺少触发其复杂度的事实。 |
| Owner 事实异步送达 + 同步只读查询对账 | 平衡状态及时性、可恢复性与 owner truth 权威 | 兼顾及时性、可恢复性和 owner 权威 | 需要 cursor、freshness、重复/乱序与双路径一致性 | 采用 | 两条路径都只读消费 owner truth，不形成双真相。 |
| 仅同步查询或仅异步本地投影 | 在单一通信路径与当前性之间取舍 | 单一路径更直观或推送更及时 | 前者放大依赖且恢复弱；后者难证明当前性 | 不采用主线 | 可作为降级能力，但不是完整主线。 |
| 受保护 cache + quarantine + qualified 晋级 | 支持可恢复下载、完整性检查和跨请求复用 | 可恢复、复用、区分传输/验证并保护活动材料 | 引入空间、淘汰、stale 和 protection 语义 | 采用 | 与下载/cache 职责及完整性门禁一致。 |
| 每次纯流式取得、不复用 verified cache | 降低长期本地材料管理复杂度 | 减少长期材料管理 | 恢复/复用弱，仍不能免除完整性门禁 | 不采用主线 | 可用于特殊 transport，但不作为端侧主线。 |
| 最小持久 Runner truth + 可重建 owner snapshot/ref | 支撑重启恢复，同时避免复制相邻仓正文和生命周期 | 边界清楚，失效可解释，本地损坏可重建 | 离线展示受限，恢复依赖 owner 可用性 | 采用 | 持久化选择、意图、保护、cursor 与安全 refs，而非外部正文。 |
| 保存丰富 owner 快照以优先离线体验 | 在 owner 不可用时提供更多历史展示 | 离线信息更丰富 | stale/visibility/revoke 复杂，本地副本易冒充 authority | 不采用 | 只有未来明确离线需求和 owner 合同时才可重新评估。 |
| 只读对账后自动收敛；不能确认则人工复核 | 恢复断线、重启与未决状态且避免重复副作用 | 可安全恢复可证明状态，unknown 保守 | 某些场景需 manual-review | 采用 | 对账不等于重放或修复上游。 |
| 全部恢复要求人工复核 | 最大限度避免自动误操作 | 极度保守 | 可证明状态也停滞，用户负担显著 | 不采用 | manual-review 是 unknown 终点，不应成为所有恢复的默认入口。 |

当前得到 owner truth 与本地体验状态分离、安全恢复和可替换承载；相应牺牲是更复杂的状态解释、保护元数据和部分自动化/离线体验。产品/框架横评与已违反 owner 边界的方案不进入正式比较。

## 14. 演进路线

> 校准来源：
> - `design-calibration/01_arch_step_13_evolution.md`
>
> 延伸阅读：建议继续阅读上述文件的“演进路线表”“触发条件与优先改变面”和“阶段边界说明”。

| 阶段 | 当前目标 / 范围 | 可接受债务 | 后续演进项 | 触发条件 | 说明 |
|---|---|---|---|---|---|
| 当前架构基线 | 让边界、承载、依赖、数据、交互、多轴状态和横切约束成立 | UI 壳、语言、进程、存储、协议和量化预算未定；上游合同 blocked/pending | 无；先停审本轮架构 | 用户确认并授权 02，后续继续保留 blocker | 本阶段产物是设计真相源，不是实现 readiness。 |
| 最小正向闭环 | 正式合同成立后承接单一显式 Release 的选择、取得/验证、受控请求、状态、停止/清理和安全诊断 | 可逻辑同部署、有限投影、保守 manual-review | Owner-safe 事件、受保护 cache 和恢复对账细化 | `RUN-UP-001~005/007/008` 主链 surface 闭合并可建立真实集成边界 | 先证明边界正确，不以 mock/fake 代替真实闭环。 |

| 承载拆分与容量演进 | 长时取得/恢复/诊断负载影响入口或隔离时拆分后台 | 短期逻辑同部署可接受 | 独立后台承载、跨承载协调和观测边界 | 有来源 workload/故障数据证明需要拆分 | 最先改变运行承载和通信，不改变核心语义与 owner seam。 |
| 外围消费增强 | 核心稳定后提供预取、比较、Archive 引用或历史视图 | 外围能力可长期缺席 | 受权限/容量约束的外围只读消费 | 核心闭环稳定、对应 owner 合同闭合且有明确需求 | 不把外围增强升级为 Release/Archive/Runtime truth。 |

演进首先改变接缝、恢复保护或运行承载，不改变 truth ownership、SDK-first、多轴状态和 fail-closed 红线。本文不提供时间表、版本路线图或任务拆单。

| 批量预取、多运行比较、Archive 浏览是否进入主线 | 演进路线与外围能力范围 | 明确用户需求、权限/容量约束和 owner 合同 | 保持外围，不进入核心验收 | 尚未形成“必须进入主线”的定论。 |

## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L5-runner` 不是 runtime 真相仓,也不是 sandbox 执行仓,更不是简单的任务列表页面。它是 **“面向任务与执行入口的运行承载产品层 / runner experience 层”**。

你可以把它理解成:
- 用户或系统怎样正式发起一次 run
- run queue、run card、run detail、run controls、run outputs 怎样被组织成产品体验
- 排队、启动、运行、等待、失败、完成、重放这些状态怎样被统一表达
- runtime、sandbox、artifact、observability、capability-hub 的结果怎样被包装成可操作、可监控、可复查的运行面

这些事情,都由 `L5-runner` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L5-runner`,这些运行体验事实就会散落在:
- runtime 自己的执行状态接口里
- sandbox 的会话与 stdout/stderr 回收结果里
- artifact 的结果卡片和文件页里
- observability 的告警、失败、健康视图里
- capability-hub 的 allow/deny 与 provider 可见性摘要里
- 各种 run 列表、详情页、重试按钮和状态提示的临时拼装逻辑里

结果就会出现:
- 用户看到的 run 体验只是多个 source system 结果的拼盘
- run queue、run detail、run output、run control、run hint 各自一套口径
- 发起执行、观察执行、干预执行和查看结果之间缺少统一心智
- runtime 的真相、sandbox 的证据、artifact 的输出、observability 的提示很难形成一个连贯产品面

所以 `L5-runner` 必须独立存在,作为:
> **把 runtime、sandbox、artifact、observability、capability-hub 的运行相关结果组织成统一可发起、可观察、可干预、可复查的执行产品层。**

### 1.3 新人最容易混淆的几个词

#### RunnerRun
就是:
> 用户在 runner 里看到并操作的一个运行单元体验对象。

它不是 runtime 的正式执行真相本体。

#### RunControlEntry
就是:
> 用户在 runner 里看到的 retry / replay / cancel / kill / rerun / continue 等动作入口。

它不是动作已经成功执行的真相。

#### RunOutputPreview
就是:
> 用户在 runner 里看到的输出预览、产物卡、日志摘录、文件摘要。

它不是 artifact 真相本体。

#### RunHealthHint
就是:
> 面向用户显示的延迟、失败、阻断、容量、健康提示。

它不是 observability truth 本体。

#### VisibleCapabilityState
就是:
> runner 里对当前可用能力/受限能力的用户可见状态表达。

它不是 capability-hub 的 capability contract truth。

#### QueueCard / SlotView
就是:
> 用户在 runner 里看到的排队、槽位、资源占用、等待状态的产品层表达。

它不是 scheduler/source queue truth。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L5-runner/02` 时,先收稳以下前提:
- `L5-runner` 不应按列表页 / 详情页 / 日志页 / 按钮栏等页面构件平铺理解,而应按运行承载体验主链责任拆
- runner 至少应拆成“运行入口与运行单元 / 运行状态与执行进度呈现 / 控制动作与恢复交互 / 结果、产物与上下文消费 / 状态提示、能力提示与运行辅助”五个主要部分
- runner 自己拥有的真相不是 runtime execution、sandbox execution、artifact truth、observability truth 或 capability contract,而是 run UX、run state UX、control entry、output preview、status/helper 这类产品层真相
- `L5-runner` 只能为用户和操作者提供统一运行体验面,不能反过来替 source systems 持有正式领域真相
- 02 的重点不是“列有哪些卡片和按钮”,而是先把“runner 产品层在平台里到底是什么、和 runtime/sandbox/artifact/observability/capability-hub 怎么分层”讲清楚
- queue card、run card、output preview、replay UI、health hint、capability hint 这些不是零散交互点,而是 runner 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的运行承载产品心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,用户面对的不是 runtime 内部状态机,而是一次 run 的体验。用户真正需要的不是“能看到 execution_id”,而是:
- 什么时候可以发起 run
- run 现在排队、运行、等待、失败还是已经完成
- 如果失败了,到底该等、重试、重放、取消还是看输出
- run 过程中产物、日志、提示和能力限制怎样被统一组织
- operators 和 owner 怎样在一个可理解的界面里观察并介入

如果把这些逻辑分别散落到:
- runtime 的状态页
- sandbox 的会话页
- artifact 的结果页
- observability 的健康/告警页
- capability-hub 的 allow/deny 视图
- 各种临时拼出来的 run list / retry 按钮 / 输出卡片页面里

系统会快速退化成:
- 用户必须自己在脑中完成“同一个 run”的多系统拼接
- 队列、状态、控制、输出、提示彼此割裂
- run 失败后用户不知道下一步该做什么
- 产品虽然能展示很多信息,但没有统一执行体验主线

因此,本概要设计的任务就是:
> **把 `L5-runner` 写成一个新人也能看懂的“运行承载产品层”,而不是把队列、状态、输出和控制入口分别摆在不同页面上。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| run 入口统一性 | 多源拼装风险高 | 单一 run 主线 | 需正式收敛 |
| run 状态理解成本 | 执行状态分散 | 统一 run state UX | 需形成产品心智 |
| 输出/结果消费 | 依赖 source 页跳转 | runner 内统一消费面 | 需正式组织 |
| retry/replay/cancel 入口 | 容易误导 | 控制入口与结果真相明确分层 | 需正式收口 |
| 能力/健康提示 | 零散 | 统一 hint 与 next-step 面 | 需形成稳定体验链 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把底层执行、隔离、产物、诊断和能力限制组织成统一的运行产品体验,让用户和操作者能正确理解和干预一次 run
- **技术问题**:RunnerRun、RunControlEntry、RunOutputPreview、RunHealthHint、VisibleCapabilityState、QueueCard 与 runtime / sandbox / artifact / observability / capability-hub 之间的边界如何稳定建模,并形成统一 runner 主链

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 runner 的运行承载职责 | run / state / control / output / hint 职责无歧义 | 文档评审 |
| 明确与 runtime / sandbox / artifact / observability / capability-hub 边界 | UX state 与 source truth 分离 | 文档评审 + 后续测试 |
| 明确用户可理解的 run 主线 | 入口、状态、干预、结果、提示在同一心智下成立 | 设计评审 + 集成测试 |
| 支撑后续详细设计与测试 | 本文足以承接 `03-详细设计.md` 的 run UX、control UX、result UX 设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文替代 runtime 正式执行真相
- 不在本文替代 sandbox 执行与隔离真相
- 不在本文替代 artifact 真相或 observability 真相
- 不在本文替代 capability-hub capability contract truth
- 不在本文实现底层 scheduler 或 host runtime 本体

## 4. 约束条件

### 4.1 技术约束

- run card、run detail、queue view、output preview、hint 必须始终能回指 source refs
- runner 的可见状态不能冒充 runtime/sandbox 的正式执行真相
- output preview 只能消费 artifact / sandbox 输出材料,不能反写 source truth
- replay/retry/cancel/kill 等控制入口必须和真实结果真相分层显示
- capability / quota / health / queue 相关提示只能消费 source results,不能自造权威裁决

### 4.2 资源约束

- 并发 run 数、状态更新频率、流式日志片段和输出预览量会持续增长,渲染与缓存复杂度必须受控
- 高频状态与提示刷新不能拖垮 source systems
- result cards、evidence previews、replay traces 不能无限膨胀

### 4.3 时间约束

- 当前阶段先收稳 runner 主体验主线,而不是先做复杂多租户调度、自动诊断闭环或高级容量分析
- run entry、run state、control entry、output preview、hint 五条基础链必须优先稳定,否则运行产品体验会长期割裂

### 4.4 合规约束

- UI 层不得擅自改写 source truth
- run control entry 不得冒充控制动作成功完成
- 用户可见输出、能力状态和诊断提示必须受 source 权限与上游可见性约束
- replay/restore/export 相关提示不得替代 archive / observability / runtime 的正式真相本体

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| run cards / queue entries | 高频 | 执行入口与批量 run 需求 |
| stream/log preview updates | 高频 | 运行反馈需求 |
| artifact/output previews | 中高 | 结果物消费需求 |
| control actions / confirmations | 中高 | operator 干预需求 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ runtime / sandbox / artifact│
                    │ observability / hub / member│
                    │ - run / output / hints      │
                    └────────────┬───────────────┘
                                 │ runner experience input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-runner                  │
                    │ - run / state / control    │
                    │ - output / hint / queue    │
                    └────────────┬───────────────┘
                                 │ visible run output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ end users / operators      │   │ console / UI shell         │   │ feedback / analytics       │
│ - run / inspect / intervene│   │ - layout / embedding       │   │ - usage summaries          │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L5-runner` 自己负责运行入口、运行状态呈现、控制动作入口、结果预览和状态提示等产品体验主线
- `runtime`、`sandbox`、`artifact`、`observability`、`capability-hub`、`member` 是 source truth 或 source result 的提供方,但 runner 不拥有它们的源真相
- 用户和 operators 通过 runner 消费统一运行体验面,而不是直接理解底层仓结构
- console/UI shell 负责工作台容器和布局,但 runner 负责 run 产品语义

所以 `L5-runner` 在全局里的角色是:
> **把 runtime、sandbox、artifact、observability、capability-hub 的运行相关结果组织成统一可发起、可观察、可干预、可复查的执行产品层。**

### 5.3 系统边界

**做什么**:
- 管理 run entry / queue / run card / run detail
- 呈现 run progress / phase / stream / output / hints
- 管理 retry / replay / cancel / kill / rerun / continue 等控制入口
- 管理 artifact/output previews、diagnostic/health/capability hints

**不做什么**:
- 不持有 runtime execution truth
- 不持有 sandbox session truth
- 不持有 artifact / observability / capability-hub 的 source truth
- 不替代 scheduler、sandbox host 或 analytics 本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| runtime | 99.9% | 运行态延迟时展示 waiting/stale hint,不伪造完成态 |
| sandbox | 99.9% | 输出和会话延迟时显示 partial output / stale 标记 |
| artifact | 99.9% | preview 缺失时保留引用卡片和占位,不伪造内容 |
| observability | 99.9% | 诊断提示缺失时降级为基础错误/等待提示 |
| capability-hub | 99.9% | 可见能力缺失时显示 unavailable/denied hint,不伪造 allow 状态 |

### 5.5 关键依赖风险

- runner 视图和 source truth 漂移会直接造成用户误判 run 状态
- queue / progress / output / hint 之间不同步会造成割裂体验
- 控制入口若误导为“已成功执行”,会导致错误操作预期
- output preview 若和 artifact truth 混层,会造成结果误读
- capability/health hints 若冒充 source truth,会让用户做错干预决策

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把列表、详情、日志、按钮等页面元素横向平铺。  
> 它按 **运行承载体验主链职责 + 入口 / 状态 / 控制 / 结果 / 提示差异** 来拆分。  
> 因此下面每一部分都可能包含多个交互对象和机制,共同支撑同一段 runner 体验主链。

#### 运行入口与运行单元部分

- **它是什么**: 这是 `L5-runner` 的主入口层,一起回答“用户怎样正式发起并看到一个 run”
- **为什么单独有它**: 这是 run 产品体验的锚点,如果不单列,run request、run card、queue entry 和执行详情会混成一层
- **负责什么**:
  - 提供 run request、run card、run list/queue entry、execution target 摘要
  - 维护 visible run identity
  - 提供 run 进入工作流的入口体验
- **不负责什么 / 容易混淆点**:
  - 不持有 runtime execution truth
  - 不持有 scheduler/source queue truth
  - 不直接推进执行成功状态
  - 最容易和 runtime execution、queue truth、source run identity 混淆
- **与其他部分交互**:
  - 下游: 状态呈现、控制交互、结果消费、提示辅助
  - 外部: runtime / member / console
  - 交互类型: run entry 型 + visible run identity 型
- **后续详细设计展开点**:
  - RunnerRun / RunQueueEntry / RunCard 主线

#### 运行状态与执行进度呈现部分

- **它是什么**: 这是 runner 的核心观察层,一起回答“run 现在跑到哪里、卡在哪里”
- **为什么单独有它**: progress/phase/wait/fail/stream 是用户理解执行的核心,但它们不等于 runtime/sandbox 真相本体
- **负责什么**:
  - 渲染 progress / phase / wait / blocked / failed / completed 状态
  - 渲染 stream/log excerpts / resource usage summaries
  - 形成统一运行状态观察面
- **不负责什么 / 容易混淆点**:
  - 不持有 runtime execution truth
  - 不持有 sandbox output truth 本体
  - 不直接发起控制动作
  - 最容易和 runtime 状态机、sandbox output、本地 log 真相混淆
- **与其他部分交互**:
  - 上游: 运行入口与运行单元部分
  - 下游: 控制动作、结果消费、提示辅助
  - 外部: runtime / sandbox / observability
  - 交互类型: run state render 型 + stream/status 型
- **后续详细设计展开点**:
  - RunnerRunState / phase model / stream excerpts

#### 控制动作与恢复交互部分

- **它是什么**: 这是 runner 的干预层,一起回答“用户怎样对 run 做受控干预”
- **为什么单独有它**: retry、replay、cancel、kill、rerun 不只是按钮,而是运行干预主线,但又不能与 source control truth 混层
- **负责什么**:
  - 提供 retry / replay / cancel / kill / rerun / continue / inspect 入口
  - 提供控制确认与执行中提示
  - 将控制动作组织成用户可理解的交互流程
- **不负责什么 / 容易混淆点**:
  - 不等于控制动作已经成功执行
  - 不替代 runtime/sandbox 正式控制记录真相
  - 不直接重做业务裁决
  - 最容易和 execution truth、business decision、source control result 混淆
- **与其他部分交互**:
  - 上游: 运行状态与执行进度呈现部分
  - 下游: 结果消费、状态提示
  - 外部: runtime / sandbox / operators
  - 交互类型: control entry 型 + recovery UX 型
- **后续详细设计展开点**:
  - RunControlEntry / replay/retry/cancel UX 主线

#### 结果、产物与上下文消费部分

- **它是什么**: 这是 runner 的结果承接层,一起回答“run 执行后用户到底看到了什么”
- **为什么单独有它**: 结果卡、输出预览、文件引用、证据材料都属于 run 结果消费面,但不能和 artifact/observability/source truth 混层
- **负责什么**:
  - 渲染 run output preview / artifact result card / file refs
  - 组织 execution summary / evidence/log previews
  - 提供结果和上下文的只读消费面
- **不负责什么 / 容易混淆点**:
  - 不持有 artifact truth
  - 不持有 observability source truth
  - 不负责结果真正入库和导出执行
  - 最容易和 artifact 真相、archive 导出、sandbox 原始输出混淆
- **与其他部分交互**:
  - 上游: 运行状态与执行进度呈现部分
  - 下游: 状态提示与运行辅助部分
  - 外部: artifact / archive / sandbox / observability
  - 交互类型: result preview 型 + context consume 型
- **后续详细设计展开点**:
  - RunOutputPreview / artifact result card / evidence ref 模型

#### 状态提示、能力提示与运行辅助部分

- **它是什么**: 这是 runner 的解释与辅助层,一起回答“系统怎样帮助用户理解当前 run 状态”
- **为什么单独有它**: 真正影响运行产品体验的很多都在非 happy path,这里最容易把 capability/observability/scheduler 真相混成 UI 提示
- **负责什么**:
  - 管理 capability availability hint / queue wait hint / health hint / quota hint
  - 管理 next-step suggestions / diagnostics summary / explain surfaces
  - 帮助用户理解等待、失败、受限和下一步动作
- **不负责什么 / 容易混淆点**:
  - 不持有 capability contract truth
  - 不持有 observability truth 本体
  - 不替代 scheduler/source queue 真相
  - 最容易和 capability decision、observability 结论、runtime 状态裁决混淆
- **与其他部分交互**:
  - 上游: 运行状态与执行进度呈现部分、结果消费、runtime/obs/hub 输入
  - 下游: users / operators / console / analytics
  - 交互类型: hint/explain 型 + next-step guidance 型
- **后续详细设计展开点**:
  - RunHealthHint / capability hint / queue hint 主线

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ runtime / sandbox / artifact│
                    │ observability / hub / member│
                    │ - run / output / hints      │
                    └────────────┬───────────────┘
                                 │ runner experience input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-runner                  │
                    │ - run / state / control    │
                    │ - output / hint / queue    │
                    └────────────┬───────────────┘
                                 │ visible run output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ end users / operators      │   │ console / UI shell         │   │ feedback / analytics       │
│ - run / inspect / intervene│   │ - layout / embedding       │   │ - usage summaries          │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L5-runner` 自己负责“组织 run 入口”“组织 queue/state/output/control 体验”“消费 capability/health hints”“输出统一运行产品面”
- `runtime` / `sandbox` 的交互主要落在 **运行入口与运行单元部分** 与 **运行状态与执行进度呈现部分**,为 runner 提供 run、phase、stream、retry/replay、session 结果输入
- `artifact` / `archive` 的交互主要落在 **结果、产物与上下文消费部分**,为 runner 提供输出、文件、证据和历史材料预览输入
- `observability` / `capability-hub` 的交互主要落在 **状态提示、能力提示与运行辅助部分**,为 runner 提供 health/capability/queue/deny/latency 提示
- console/UI shell 负责容器与嵌入,而 runner 负责运行产品语义
- 用户、operators 通过 runner 消费统一运行体验面,而不是直接拼接底层系统输出

### 7.3 分模块交互说明(逐个写)

#### 与 `runtime` 的交互

```text
┌────────────────────────────┐
│ runtime                    │
│ - run / execution state    │
│ - queue / result / retry   │
└────────────┬───────────────┘
             │ run/state input
             ▼
┌────────────────────────────┐
│ runner                     │
│ - run card / state view    │
└────────────────────────────┘
```

- `runtime` 是 **run 状态与结果来源方**
- **交互类型**: run/state 输入型交互
- **主流程位置**: run created、queued、running、waiting、failed、completed 时进入主流程
- **交互解释**:
  - runner 只消费并翻译 runtime 真相
  - 不替代 execution truth 本体
- **高风险异常流**:
  - RunnerRun 状态漂移后被误当 runtime source state
- 后续 `03-详细设计.md` 继续展开:
  - RunnerRun contract
  - run state mapping 主线

#### 与 `sandbox` 的交互

```text
┌────────────────────────────┐
│ sandbox                    │
│ - stream / output / usage  │
│ - kill/replay/cleanup      │
└────────────┬───────────────┘
             │ execution detail input
             ▼
┌────────────────────────────┐
│ runner                     │
│ - output / control hints   │
└────────────────────────────┘
```

- `sandbox` 是 **执行细节与输出来源方**
- **交互类型**: execution detail / output 输入型交互
- **主流程位置**: stream、usage、timeout、kill、replay、cleanup 时进入主流程
- **交互解释**:
  - runner 将 sandbox 结果翻译成产品层 run 体验
  - 不替代 sandbox execution truth
- **高风险异常流**:
  - stdout excerpt 被误当 sandbox output truth 本体
- 后续 `03-详细设计.md` 继续展开:
  - run output preview
  - control hint 主线

#### 与 `artifact / archive` 的交互

```text
┌────────────────────────────┐
│ artifact / archive         │
│ - files / outputs / refs   │
│ - historical materials     │
└────────────┬───────────────┘
             │ result/context input
             ▼
┌────────────────────────────┐
│ runner                     │
│ - output preview / refs    │
└────────────────────────────┘
```

- `artifact / archive` 是 **结果和历史材料来源方**
- **交互类型**: output/context 输入型交互
- **主流程位置**: result view、file preview、evidence reference、history preview 时进入主流程
- **交互解释**:
  - runner 只读消费这些结果和历史材料摘要
  - 不反向持有 artifact/archive 真相
- **高风险异常流**:
  - output preview 被误当 source truth
- 后续 `03-详细设计.md` 继续展开:
  - result card / evidence ref 主线

#### 与 `observability / capability-hub` 的交互

```text
┌────────────────────────────┐
│ observability / hub        │
│ - health / latency / deny  │
│ - capability availability  │
└────────────┬───────────────┘
             │ hint input
             ▼
┌────────────────────────────┐
│ runner                     │
│ - health/capability hints  │
└────────────────────────────┘
```

- 这些系统是 **状态与能力提示来源方**
- **交互类型**: hint / capability 输入型交互
- **主流程位置**: wait、blocked、degraded、capability unavailable、quota/deny 时进入主流程
- **交互解释**:
  - runner 只翻译和展示提示
  - 不替代 observability truth 或 capability contract truth
- **高风险异常流**:
  - capability hint 被误当 contract truth
- 后续 `03-详细设计.md` 继续展开:
  - hint contract
  - queue/capability/status 主线

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是 runner 体验层、哪个模块是只读消费方、哪个模块是控制入口层

本节**不**展开:
- 具体 run 列表/详情页布局
- stream 渲染和日志分页实现细节
- queue 预测与调度算法细节
- action confirmation 组件细节
- 反馈统计与埋点细节

这些内容留到 `03-详细设计.md` 中继续展开。

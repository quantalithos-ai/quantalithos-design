## 1. 模块职责描述

**本模块做什么**:
- 持有正式 RunnerRun / RunQueueEntry / RunCard / RunnerRunState / RunControlEntry / RunOutputPreview / RunHealthHint / VisibleCapabilityState 等 runner 体验层真相
- 把 runtime、sandbox、artifact、observability、capability-hub 的运行相关结果组织成统一 run 入口、运行状态、控制动作、结果预览与提示体验
- 管理 queue/slot 视图、stream/log excerpts、retry/replay/cancel/kill 入口、artifact/output preview、health/capability/queue hints
- 向用户、operators、console、analytics 提供统一的 run 只读结果与交互事件面

**本模块不做什么**:
- 不持有 runtime execution truth、sandbox session truth、artifact truth、observability truth 或 capability contract truth
- 不替代 scheduler/source queue 本体、sandbox host 本体或 analytics 本体
- 不直接推进 source action 的成功状态或业务编排真相

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 runner“为什么存在”,而是让开发者可以直接开始实现:
- run request 如何进入正式 RunnerRun / RunQueueEntry 主线
- phase/progress/stream/log/usage 怎样统一为用户可理解的运行状态体验
- retry/replay/cancel/kill/rerun 怎样作为受控动作入口组织起来
- artifact output、archive evidence、sandbox output 摘要怎样进入统一结果消费面
- health/capability/queue hints 怎样在不冒充 source truth 的前提下帮助用户做下一步动作判断

如果不先把这些内容采集清楚,03 很容易退化成:
- run 列表/详情页字段说明
- stream 日志分页或按钮行为笔记
- retry/replay/cancel 入口清单
- output / hint / queue / capability 各写一套没有统一主线的体验说明

- **异步最终一致**主要是: stream patch、preview refresh、hint rebuild、analytics summaries、部分 replay result 重建

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `RunnerRun / RunnerRunState / RunControlEntry / RunOutputPreview / RunHealthHint` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是统一 run 产品主链,`03` 却退化成 run 列表、日志、按钮、卡片的页面说明
- 实现者知道有 retry/replay/cancel,却不知道它们如何和 queue/state/output/hint 形成同一条体验主线
- 入口、状态、控制、输出、提示各写一套,彼此断裂

#### 5.2.4 关键函数代码片段

```rust
/// 根据来源 run 输入创建正式 RunnerRun 和队列视图入口。
fn create_runner_run(
    run_repo: &dyn RunnerRunRepo,
    input: CreateRunInput,
) {
    // [input.校验 run 输入边界]
    // 先确认 run 入口只是消费 runtime/member 的 source refs,而不是 runner 自己发明执行真相。
    input.validate_runner_run_boundary();

    // [RunnerRun::从输入创建]
    // 再把目标、队列和 run 摘要收束成正式运行单元。
    let run = RunnerRun::from_input(input);

    // [run_repo.保存 run 与队列入口]
    // 最后把 run/queue/card 写入 runner 层,供 state/control/result 主线消费。
    run_repo.save_runner_run(run);
}
```

这段实现守住的边界是:
- runner 只承接可见运行单元,不替代 runtime execution truth
- queue 入口只是产品层视图,不替代调度真相
- run 主体必须稳定回指 source refs

#### 5.2.5 该部分的边界与非职责
- 不持有 runtime execution truth
- 不持有 scheduler/source queue 真相
- 不负责 run 完成状态推进
- 不负责 output/hint 真相本体

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `运行状态与执行进度呈现部分` 提供 run 锚点输入
- 向 `控制动作与恢复交互部分` 提供 action target 输入
- 向 `结果、产物与上下文消费部分` 提供 visible run context

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `RunnerRun ≠ Runtime execution truth` 必须写死
- `queue/slot view ≠ scheduler truth` 必须写死
- queue position 若与 source truth 不一致,用户会直接误判任务状态

```rust
/// 根据 runtime/sandbox 输入渲染统一的 run 状态与进度视图。
fn build_run_state_view(
    state_repo: &dyn RunnerStateRepo,
    input: BuildRunStateInput,
) {
    // [input.校验状态来源边界]
    // 先确认当前状态只消费 runtime/sandbox source refs,不替代其真相本体。
    input.validate_run_state_source_boundary();

    // 再把 phase、stream、usage、wait/fail 摘要收束成可见 run state。

    // 最后把可见状态写入 runner 层,供结果和提示主线消费。

}
```

这段实现守住的边界是:
- runner state 只翻译运行状态,不替代 runtime/sandbox 真相
- stream excerpt 只是摘要,不能冒充原始输出真相
- phase/progress 成立后,控制与提示才能给出一致体验

#### 5.3.5 该部分的边界与非职责
- 不持有 runtime execution truth
- 不持有 sandbox 原始输出真相
- 不直接发起控制命令

- control / output / hint 的分歧必须回收到 action history、state transitions 与 source refs 对账主线

### 7.4 API / 命令签名

#### `CreateRun`


### 7.5 关键函数/命令级伪代码

#### `BuildRunOutputPreview`

```text
function BuildRunOutputPreview(input):
    1. 校验 output/artifact/archive 来源 refs 完整
    2. 确认预览只读消费边界
    3. 生成 RunOutputPreview / ArtifactResultCard / EvidenceRefCard

    5. 写入 result projection
    6. 返回 preview ids
```

```text
function BuildCapabilityHint(input):

    5. 写入 assist view
    6. 返回 hint ids
```

### 8.1 场景 A · 用户发起 run 并看到其进入统一 run 主线

```text
   ▼
```

**开发者关注点**:

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| run target 非法 | 拒绝创建 run |
| queue / state 来源不一致 | 阻断状态更新并标 mismatch |
| control action dispatch 失败 | 记录 history 并标 pending/failed |
| output preview refs 缺失 | 标记 stale/partial preview |
| hint 来源冲突 | 标记 hint conflict 并回退到基础提示 |

### 11.1 重试 / 降级 / 熔断 / 补偿
- stream / preview 延迟时可展示 partial/stale,但不得伪造完整结果
- control dispatch 失败时可重试,但必须保留已触发历史和状态分层
- source hints 缺失时可降级为基础提示,但不伪造 capability/health 真相

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 运行入口与运行单元部分 | run entry 漂移 / queue 视图错位 | runner run boundary validate | 阻断 run 创建或列表更新 | 刷新 source refs 后重试 |
| 运行状态与执行进度呈现部分 | phase/stream/output 不同步 | run state source boundary validate | 标记 mismatch/stale | 重建 state projection |
| 控制动作与恢复交互部分 | action 已触发但 source dispatch 失败 | control entry boundary validate | 标记 pending/failed | 重试 dispatch |
| 结果、产物与上下文消费部分 | preview 缺 refs / artifact 卡片错位 | output source boundary validate | 标记 partial/stale | 重建 preview |
| 状态提示、能力提示与运行辅助部分 | hint 与 source 结论冲突 | hint source boundary validate | 回退基础提示 | 重拉 source hints |

## 12. 实现红线 / 开发禁止事项

- 不允许 RunnerRun / RunnerRunState 反向替代 runtime execution truth
- 不允许 RunControlEntry 冒充控制动作已成功完成
- 不允许 RunOutputPreview / ArtifactResultCard 反向替代 artifact truth

- 不允许 queue/slot view 冒充 scheduler/source queue truth
- 不允许 replay/retry UI 被误当 replay 已完成或业务裁决已重做

## 14. 最小可运行闭环

- 用户或系统发起一次正式 run,RunnerRun 与 RunQueueEntry 成功建立并被列表面展示
- runtime / sandbox / artifact 至少各提供一类输入,runner 成功渲染统一的 run state、output preview 和 hints
- 用户通过一个 control entry 发起 retry/replay/cancel 之一后,runner 能清楚区分“已触发”和“已完成”,并让结果、提示和 source refs 保持一致可追溯

## 15. 结论

本详细设计的核心结论是：
- `L5-runner` 的实现主轴必须按 run / state / control / result / hint 五个主要部分组织,而不是按列表、详情、日志、按钮平铺
- runner 真相层只持有运行入口、运行状态体验、控制入口、结果预览和辅助提示,不接管 runtime、sandbox、artifact、observability、capability-hub 的 source truth
- 所有 run cards、queue views、control entries、output previews、health/capability hints 都必须建立在稳定 source refs、只读消费和 append-only 行为证据之上

后续测试与验收文档,应直接围绕这套统一运行体验主链、控制入口分层、结果消费边界和提示层边界展开.

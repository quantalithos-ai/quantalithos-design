## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
>
> 延伸阅读：请继续阅读该文件的“结构化中间产物”“回填草稿”和“待确认事项”，了解 P0 分母、target tier 和 conditional positive 的收口过程。

### 2.1 验收目标

本轮验收裁决以下 Runner-owned semantic safety 与经 baseline 启用的真实协作接缝：

1. 显式版本选择、authority/qualification、下载与完整性验证。
2. Sandbox 正式请求、启动/停止/清理意图及 owner 状态投影。
3. 资源冲突、保护材料、lease/generation 和清理一致性。
4. 断线、休眠、重启、过期、Unknown 与 RecoveryCase。
5. bounded preview、失败诊断、安全 redaction 和 handoff posture。
6. SDK/API/public adapter 边界、Query no-write、Consumer header-first、Job local-only 与 outbound event=0。
7. 可观测性、证据真实性、缺陷复验、风险和最终裁决边界。

### 2.2 范围与非范围

| 范围项 | 优先级 | 裁决方式 | 非范围/限制 |
|---|---|---|---|
| 显式 selection、authority、material acquisition/integrity | P0 | `AC-RUN-001~004` 与 CTX/MAT/CON/CUT | 不验 Artifact/Governance 内部实现 |
| request、owner status、control、cleanup | P0 | `AC-RUN-005~008` 与 REQ/CTL/OWN/RES | 不把 Runner intent 当 Sandbox/Runtime truth |
| disconnect、Unknown、recovery、idempotency/UoW | P0 | `AC-RUN-009` 与 REC/IDM/UOW/JOB | 无真实 durable/owner seam 时保持 blocked |
| preview、diagnosis、handoff、redaction | P0 | `AC-RUN-010` 与 PRE/OBS/QRY | local record 不等 L4 audit/evidence |
| 跨仓 public seam、协议角色和边界 | P0 | `AC-RUN-011` 与 CON/ENT/CNS/BND | 不编译或复用 Sandbox 私有实现 |
| NFR 安全、可用性、一致性、追溯、观测、平台/资源 | P0 | `NFA-RUN-001~007` | selected platform/positive 由 baseline 决定 |
| 性能、容量、SLO | conditional | `NFA-RUN-008` measurement/residual | 无 authority 不设 hard threshold |
| 失败体验与可理解性 | P1 | `NFA-RUN-009` | baseline 可将其升为 required |
| `FR-RUN-014~016` 外围能力 | P1/P2 | future scope | 不进入当前 P0 pass 分母 |

### 2.3 Target tier

| Tier | 可裁决内容 | 不允许升级 |
|---|---|---|
| `T1-SEMANTIC-P0` | Runner-owned 语义安全、负向、零副作用和边界 | 不代表真实 owner integration、产品或发布 readiness |
| `T2-CONTROLLED-INTEGRATION` | baseline 启用 slot 的真实 public contract、正/负/Unknown/recovery | 未启用 slot 或 fake 不贡献 positive |
| `T3-PRODUCT-REHEARSAL` | 产品式环境、selected platform、主链、cleanup、redaction 与必要 UX | 局部成功、PID/port、profile 名不等 readiness |
| `T4-RELEASE/ACCEPTANCE` | release evidence、VETO、风险、GRC 与 required signoff | verdict 不自动等生产上线 |

只有相应 upstream slot、正式 public contract、真实环境和 target-tier baseline 明确启用时，positive integration 才是 required；否则必须保留 `blocked/conditional`。

## 4. 进入条件与退出条件

> 校准来源：
> - `design-calibration/06_acceptance_step_04_entry_exit.md`
>
> 延伸阅读：请继续阅读该文件的“验收生命周期”“进入 checklist”“暂停/送验无效表”和“退出 checklist”。

### 4.1 生命周期

```text
not_entered -> entered -> decision_pending -> decided
                    \-> suspended -> decision_pending
```

`not_entered`、`entered`、`decision_pending`、`suspended` 不是 verdict。当前为 `not_entered / blocked_by_missing_baseline`。

### 4.2 进入条件

- [ ] 需求/设计/测试 revision、scope、target tier 和 decision authority 已固定。
- [ ] release/artifact、authority、integrity、environment/platform、config、dependency 和 dataset manifest 可定位。
- [ ] fixed `<run_id>`、source revisions、artifact/report roots 和 evidence generation contract 一致。
- [ ] target-tier required suite、TC、slot、checks 和 selected platform 已明确；未启用 positive 显式标为 conditional/blocked。
- [ ] Runner、store/cache、harness、public seam 和审查角色真实可用；不可用必须停在 entry blocker。
- [ ] handoff、veto、open-issues 和 review 入口已准备，未执行项不会被隐藏。

缺任一项不得进入；不得用文档完成、profile、ACK、PID、端口、本地日志或 planned TC 数量替代。

### 4.3 暂停与送验无效

| 情况 | 状态与处理 |
|---|---|
| implementation/baseline/run 不存在 | `not_entered`；不生成不通过 verdict |
| required harness/suite/check unavailable | `blocked/not_run`；修复后新 run |
| redaction/dependency/link/pairing/no-static finding/unavailable | 暂停；进入 VETO/S 候选（若已进入验收） |
| run/source/config/digest mismatch、跨 run 或 `latest` | 送验无效；保留材料并重建 baseline |
| 新安全事件、owner revoke、VETO 或风险 trigger | `suspended`；停止依赖旧 package 的推进 |

### 4.4 退出条件

- [ ] target-tier required `AC-RUN-*`、NFR、协议/状态/事务和 evidence gate 有真实结果。
- [ ] 18 slot/EV、suite/report/check、handoff、VETO、open issues 和 review 可追溯。
- [ ] 无开放 S/VETO；A 已关闭或满足合法风险接受；B/R 透明登记。
- [ ] 复验、争议、风险期限/trigger 和 required signoff 已完成。
- [ ] 三值 verdict 与 scope/tier/decision package 一致。

## 6. 数据边界与架构红线验收

### 6.1 数据与 owner 边界

Runner 可拥有 local selection、acquisition/cache/integrity posture、run/control intent、RecoveryCase、safe projection、diagnosis/handoff posture、幂等和 Job 技术记录；不得保存或修改 Release/Artifact 正文、Governance approval/policy 正文、Runtime loop/result body、Sandbox 私有 state/raw capture、Observability evidence/report、Archive bundle、Project 正文或 secret/token/credential。

Owner projection/ref 必须带 source、scope、visibility、freshness、version/generation、limitation。cache、cursor、receipt、PID/port/probe、profile/readiness marker、local log、handoff posture 均不得升级或反写 owner truth。

## 7. 接口、事件与跨仓同步验收

### 7.1 协议分母

## 8. 状态机、事务与一致性验收

### 8.1 状态主语与不等式

21 个正式状态主语必须按 03 的 enum/variant 和 owner scope 裁决；不得将不同主语压成一个 `RunnerRun` 状态。核心不等式固定为：

## 12. 缺陷分级、复验与放行规则

> 校准来源：
> - `design-calibration/06_acceptance_step_12_defects_retest_release.md`
>
> 延伸阅读：请继续阅读该文件的“缺陷等级与裁决影响”“缺陷生命周期与不可变证据”“复验选择与强制全量规则”和“放行规则”。

### 12.1 S/A/B/R

| 级别 | 含义 | 处理与裁决 |
|---|---|---|
| `S` | VETO、安全/真相/证据完整性破坏 | 暂停、修复、新 run、全量 P0；不可接受；开放即不通过 |
| `A` | target-tier P0 gate/AC/NFR 失败但未命中 VETO | 默认阻断；极窄且不触 P0/VETO 时才可进入 Step 13 候选 |
| `B` | 非 P0、局部 UX/可读性/维护性问题且无安全误导 | 登记、排期或合法接受；不改变 P0 分母 |
| `R` | 范围外、等待 authority、无 hard threshold measurement、未启用 positive slot | 保持 residual/blocked；不计通过，不能绕 required target |

### 12.2 复验

修复后必须建立新 fixed run，保留原失败 run；至少执行原失败 TC、同 family 正/负/边界/Unknown、受影响 suite/check 和 evidence/report pairing。truth owner、协议/状态/UoW/idempotency/recovery、config/readiness、redaction/dependency/evidence schema、SDK adapter、durable store、平台 cleanup 或 report generator 变化时，强制全量 P0（全部适用 suite、108 planned TC 分母、18 slot、四项完整性 check 与 review）。`blocked/not_run/incomplete` 不能关闭 required defect。

### 12.3 放行

| 结果 | 条件 |
|---|---|
| 继续验收执行 | 无开放 S；harness/check 可执行；baseline/run identity 有效 |
| 进入 final decision | S=0；A 已关闭或有合法候选接受；required gate/evidence/VETO 已裁决；争议有 review |
| `通过` | S=0、A=0；全部 target-tier P0 passed；无未接受 required residual；证据和签署完整 |
| `有条件通过` | S=0；P0 主线成立；仅合法 accepted A/B/R；Step 13 全字段、有权 acceptor、期限/trigger/action 完整 |
| `不通过` | 任一 VETO/open S、required P0 failed、或进入裁决后无法满足退出门禁 |

不得用多数通过、提交修复、profile、文档完成、本地成功或签字替代复验和证据。

## 14. 最终结论与签署

> 校准来源：
> - `design-calibration/06_acceptance_step_14_final_decision_signoff.md`
>
> 延伸阅读：请继续阅读该文件的“生命周期与 verdict 分离”“三值 verdict 判定矩阵”“Target-tier 裁决上限”“签署角色、责任与权限边界”和“当前签署模板状态”。

### 14.1 生命周期与三值分离

生命周期只允许：`not_entered`、`entered`、`decision_pending`、`suspended`、`decided`；前三者不是 verdict。实际 verdict 只允许：`通过`、`有条件通过`、`不通过`。当前 lifecycle 为 `not_entered / blocked_by_missing_baseline`，actual verdict 为 `none`。

### 14.2 Decision package

最终 decision 必须绑定 `decision_version`、target tier/scope、baseline/source revisions、fixed run/evidence index digest、gate/VETO/defect/risk/handoff/review versions、required signer set 和 decision time。source superseded/invalidated、风险过期/撤销、scope/tier/platform/release candidate 改变时，旧 package/verdict 不自动延续。

### 14.3 Verdict 矩阵

| 维度 | 通过 | 有条件通过 | 不通过 |
|---|---|---|---|
| Required gates | 全部 target-tier P0 passed | P0 主线 passed，只有合法 residual | required failed，或进入裁决后 required blocked/not_run/incomplete |
| VETO | 12/12 clear | 12/12 clear | 任一 hit/disputed/not clear |
| 缺陷 | S=0、A=0 | S=0、合法 accepted A/B/R | open S、未接受 A、未复验/争议 |
| Evidence/reports | fixed-run pair/check/index/detail/handoff/review 完整 | 同左且风险同版本 | static/cross-run/missing pair/check failed/unavailable/unreviewed |
| Signoff | required signer set 完整同意 | required signer set 完整同意条件 | 缺失/拒绝/权限或 scope/version 不一致 |

T1/T2/T3 不自动授权 T4 或 production readiness；T4 还需 release evidence、GRC/authority-defined conditions 和 required signoff。

### 14.4 签署角色

future package 至少按适用性包含：acceptance authority、product/scope、architecture/security、test/evidence、operations/release、以及启用 slot 对应的 dependency/owner authority。签署确认 package/version/scope/tier 和引用完整，不自动接受未列风险，也不反写任何 owner truth。当前不填写姓名、日期、decision digest 或签署。

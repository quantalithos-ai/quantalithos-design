# 00 需求 Step 3 · 背景与问题定义

> 状态：`completed`

## 1. 本步目标

说明 Runner 为什么在当前产品体系中值得单独收束，列出现状问题及其后果，并区分业务问题与技术问题；本步不提前写目标、功能、接口或实现方案。

## 2. 输入与诊断

- 产品矩阵中 Runner 作为独立 App、面向用户运行产物的叙事。
- 产品最终目的中“最终产出可运行交付物”和“过程可观察”的产品语境。
- Step 2 已收敛的 Runner 边界。
- `L1-artifact` 的 Artifact/version/baseline owner 结论。
- `L4-sandbox` 的 controlled execution、lease、cleanup、capture 与 handoff 边界。
- 旧 Runner 文档中的 `latest`、直接 SandboxService、固定冷/热启动、并发和本地日志等历史材料。

## 3. 业务背景

Quantalithos 不仅要产出代码和交付物，还要让用户能够在端侧使用一个明确版本的软件产物。Runner 位于产品产出与用户实际运行之间，面对的是不应被要求理解部署、依赖、端口、隔离和恢复细节的运行用户。当前需求讨论的必要性在于：把“交付了一个可消费产物”和“端侧是否能安全、可解释地运行”分成清晰的产品与真相边界。

## 4. 现状与问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 端侧运行入口与上游真相边界未形成新版需求基线 | 旧 Runner 材料同时混入 Artifact 下载、Runtime 控制、Sandbox 实现、队列、能力提示和本地日志，RunnerRun 等产品对象被写成持久化运行真相。 | 后续架构和实现可能重复拥有 Release、Runtime、Sandbox 或 Observability 语义，造成跨仓多真相和错误验收。 |
| 已批准版本的消费链路不完整 | 当前上游已明确 Artifact 与 Governance 的 owner 边界，但 Release locator、integrity manifest、digest/signature、authority chain 和 revoke/expire 的 Runner-facing 合同仍未完全闭合。 | 不能证明用户下载、缓存或启动的是可消费且仍获授权的不可变版本；本地 cache 可能掩盖撤销、过期或内容漂移。 |
| 运行请求、真实执行、清理和恢复容易被压平 | `Sandbox accepted`、进程存在、端口开放、UI toast、本地 stdout/stderr 和 handoff ACK 都可能被误读为 running、success、audit 或 signoff。 | 失败诊断、资源释放、断线恢复和安全处置无法可靠判断；未知副作用可能被重复启动或错误清理。 |
| 跨平台和资源冲突问题尚未形成产品层口径 | 端口、文件、磁盘、休眠、网络切换、应用重启和平台能力差异缺少统一的端侧需求表达。 | 用户遇到冲突、断线或恢复时无法理解下一步；不同平台可能出现越权抢占、孤儿资源或不一致的控制体验。 |

这些问题描述当前缺口，不等于已经选择某个桌面框架、容器后端、下载协议、数据库或性能阈值。

## 5. 业务问题 vs 技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | 用户拿到软件产物后，缺少一个能让其明确选择、验证、运行、停止、清理和理解失败的端侧入口；平台因此难以把“产出”稳定转化为“可用软件体验”。 |
| 技术问题 | Runner 与 Artifact/Governance/Runtime/Sandbox/Observability/Archive 的 truth、authority、lease、cleanup、诊断和恢复边界尚未形成统一需求合同；旧材料还把实现选择、固定指标和本地日志混入需求。 |

## 6. 量化与历史数字处理口径

当前没有来源已闭合的 Runner 端到端启动时延、并发量、成功率、带宽、资源上限或清理时限基线。旧材料中的冷启动 `<30s`、热启动 `<5s`、并发 `≥10` 和 `99.9%` 启停成功率只作为 `historical_candidate / pending_nfr`，不作为本轮问题量化或正式需求指标。

## 7. 取舍与未采用方案

- 采用“用户无法可靠完成安全运行闭环”作为业务问题，不采用“缺少 Tauri/Docker”等方案语言作为问题定义。
- 采用“authority、执行、清理、恢复语义未闭合”作为技术问题，不采用旧文档的组件缺失清单作为现状真相。
- 不把问题表直接写成目标或功能；下载、校验、Sandbox 请求和诊断能力留到后续 Step。

> 前置参考：`draft/01_项目作用与交互对象.md`、`projects/L1-workspace/draft/01~03`、已读取的 L0/L1/L2/L4 当前正式文档。
> 本文回答：Runner 需要形成什么产品能力闭环、哪些功能属于核心范围、查询/控制/本地状态/上游真相如何分层，以及依赖失效时如何表达。

## 1. 核心能力闭环（候选）

Runner 的核心不是“启动一个本地进程”，而是让用户从一个明确、可验证的版本选择出发，安全地完成端侧准备、正式 Sandbox 请求、运行控制、观察、清理和恢复：

```text
[R-RUN-1 语境与设备检查]
                |
                v
[R-RUN-2 显式 Release 选择与 authority 校验]
                |
                v
[R-RUN-3 下载 / cache / 完整性验证]
                |
                v
[R-RUN-4 正式 Sandbox 请求与资源预检]
                |
                v
[R-RUN-5 启动、运行、停止、清理控制]
                |
                v
[R-RUN-6 输出预览、失败诊断与 handoff]
                |
                v
[R-RUN-7 断线恢复、lease/orphan 处理与本地重建]
                ^                                      |
                +----------重新查询 / 用户确认 --------+
```

| 能力节点 | 能力成立描述 | Runner 可拥有 | 外部 owner / 前置 | 缺失时的安全结果 |
|---|---|---|---|---|
| `R-RUN-1` | 建立 actor/session/project context、平台、版本选择语境和本机资源探针。 | 本地设备语境、用户选择、probe 摘要。 | SDK actor/context、Work/Workspace safe ref、OS capability。 | 未建立可信语境时不显示敏感 Release，不发起副作用。 |
| `R-RUN-2` | 用户明确选择不可变 Release/version，并验证 Artifact、baseline 和 Governance authority chain。 | 选择记录、确认页、校验姿态。 | Artifact Release/reference、Governance Decision/Approval。 | `not_selected`、`not_visible`、`pending`、`blocked`、`conflict` 或 `expired`。 |
| `R-RUN-3` | 取得正式 locator/manifest 后下载、断点恢复、缓存复用和完整性/签名验证。 | DownloadTask、CacheEntry、验证结果、淘汰意图。 | locator、manifest、digest/signature authority。 | 不完整/不匹配材料不得进入 Sandbox；保留失败诊断。 |
| `R-RUN-4` | 以已验证材料和资源预检结果发起正式 Sandbox request，并等待明确的 request/boundary/lease 状态。 | request correlation、用户可见控制状态。 | Sandbox context、boundary、policy、lease、resource allocation。 | `accepted` 仅表示接收；guard/lease 未成立则 `blocked/pending`。 |
| `R-RUN-5` | 展示并发起启动、停止、取消、清理等用户意图，区分 accepted、running、terminal、cleanup。 | RunnerRun、ControlIntent、local lifecycle view。 | Runtime/Sandbox control/result truth。 | 未知副作用禁止自动重放；终态和清理未确认时保持 `unknown`。 |
| `R-RUN-6` | 展示安全 output preview、failure classification、下一步建议，并把允许的摘要交给 Observability。 | 摘录、引用卡片、诊断摘要和 handoff intent。 | Capture/Runtime result/Observability diagnostic/handoff。 | 本地信息不足时显示 `partial/unavailable`，不生成 evidence/verdict。 |
| `R-RUN-7` | 断线、重启或 lease 变化后，以 cursor/status/reconcile 重新建立本地状态。 | local cursor、recovery posture、orphan reminder、cache revalidation。 | SDK status、Sandbox lease/reconcile、Runtime state。 | 无法确认时停止危险动作，等待用户或 owner reconcile。 |

闭环的“成功”只能分层描述：本地准备成功、正式请求已接收、Sandbox boundary 已建立、Runtime 运行中、Runtime terminal result、资源已清理。这些阶段不能压平为单一 `success`。

## 2. 核心能力范围推演

### 2.1 `R-RUN-1` 运行语境、平台与资源预检

| 入口行为 | Runner 行为 | 明确边界 |
|---|---|---|
| 用户打开 Runner | 建立客户端 session 壳、读取可用平台/本机资源安全摘要。 | 不签发 credential，不把 OS 探针当作治理或全局容量。 |
| 用户选择项目/工作语境 | 保存安全 `project_ref` / context ref，并重新请求 Release/visibility。 | 不从 URL、历史 cache 或 ProjectWorkspace 推断 ProjectMember。 |
| 平台能力不可用 | 显示 `unsupported/unavailable/degraded` 和原因。 | 不自动切换到未经批准的执行后端。 |
| 端口或资源冲突 | 在发起正式 Sandbox 请求前显示冲突、占用来源和解决入口。 | 不强制抢占、修改他人进程或绕过 Sandbox allocation。 |

### 2.2 `R-RUN-2` 显式版本选择与 authority 校验

选择页至少要让用户看见：Release/version 标识、来源、baseline/approval 摘要（若正式可见）、平台/入口元数据、digest/signature 状态、有效期/撤销姿态和下一步限制。具体字段和 query 名称留待上游闭合。

必须满足：

1. 版本选择是用户显式行为或来自一个可回溯的正式选择 ref；`latest`、默认分支、目录排序和“最近使用”只能作为非权威的候选提示，不能直接运行。
2. 选择的 version 必须不可变，且能回指 Artifact/Release 与 Governance authority chain；无法验证 scope、expiry、revocation 或 conflict 时 fail-closed。
3. Runner 不下载或修改未完成 authority 校验的材料；本地管理员角色不能替代上游 approval。
4. 版本被撤销、过期、替换或 baseline 不再适用时，已存在 cache 也必须重新验证，不得继续启动。

### 2.3 `R-RUN-3` 下载、cache 与完整性验证

下载子闭环候选如下：

```text
resolve formal locator
  -> create bounded download task
  -> stream to quarantine/incomplete area
  -> verify size/manifest/digest/signature according to owner policy
  -> atomically promote to cache entry
  -> bind cache entry to immutable release/version ref
  -> evict only when no active run/lease/reference protects it
```

| 状态轴 | 候选值 | 关键不变量 |
|---|---|---|
| Download | `not_started / resolving / transferring / paused / failed / completed` | `completed` 仅表示传输完成，不表示 integrity 或 approval。 |
| Cache | `absent / incomplete / quarantined / verified / stale / invalid / evicted` | 只有 `verified` 且 source authority 仍有效的 entry 可供启动。 |
| Integrity | `unknown / pending / passed / failed / unverifiable` | `failed/unverifiable` 必须阻止 Sandbox request；不得以重命名或重新 hash 通过。 |
| Authority freshness | `unknown / current / stale / revoked / expired / conflict` | 非 `current` 的 Release authority 不得被本地缓存掩盖。 |

断点续传、并发下载、代理、离线 cache 和淘汰策略只能在正式 `04` 中按配置和安全边界收口；当前不承诺任何固定 transport、算法、TTL 或磁盘布局。

### 2.4 `R-RUN-4` Sandbox 正式请求与资源冲突

Runner 的 Sandbox adapter 只负责把已验证的 source refs、平台/资源语境和用户意图送入正式边界，并解释返回状态：

```text
validate local preconditions
  -> submit formal sandbox request (idempotent correlation)
  -> receive accepted / rejected / pending / unknown
  -> query boundary / lease / controlled-run status
  -> expose running only from formal owner status
```

`accepted` 只代表 Sandbox 接收请求；`running` 必须来自正式 controlled execution status；`success` 必须来自相应 Runtime/Sandbox owner 的结果语义。Runner 不执行 guard、policy、lease 或 cleanup 的第二套逻辑，只能在本地做重复提交门禁和安全显示。

### 2.5 `R-RUN-5` 启动、停止、取消、清理和资源一致性

用户可看到的控制入口候选：`start`、`stop`、`cancel_request`、`retry_download`、`retry_after_reconcile`、`cleanup`。每个入口都必须拥有：用户意图、请求关联、预计影响、当前 source posture、accepted/pending/confirmed/rejected/unknown 结果和下一步动作。

Runner 本地运行状态建议采用多轴，而不是一个可写的“真相状态”：

| 状态轴 | 候选值 | 说明 |
|---|---|---|
| Selection | `none / selected / invalidated` | 只表示用户选择，不表示批准。 |
| Preparation | `unresolved / authority_pending / downloading / verifying / ready / blocked` | `ready` 仅表示本地准备和 authority 门禁均满足。 |
| Sandbox request | `not_sent / accepted / rejected / pending / unknown` | `accepted` 不等于 boundary/running。 |
| Execution display | `not_started / starting / running / stopping / terminal / unknown` | 只承接 Runtime/Sandbox 正式状态或明确的本地观察姿态。 |
| Cleanup | `not_required / requested / pending / confirmed / blocked / unknown` | 未确认 cleanup 时不得删除仍可能被使用的材料。 |
| Connectivity | `online / degraded / offline / reconnecting` | 影响查询和控制可用性，不覆盖 source truth。 |

资源一致性规则：

- 端口 probe 只是当前本地观察；正式 allocation/lease 结果优先于 probe。
- start、stop、cleanup 的未知结果不得由进程消失、socket 关闭或 UI 刷新自动改成成功。
- active lease、capture、handoff、retention 或 orphan 保护存在时，不得本地删除 cache、运行目录或输出材料。
- 清理动作必须区分“用户请求已提交”“Sandbox cleanup guard 通过”“资源已释放”“本地材料可淘汰”。

### 2.6 `R-RUN-6` 输出预览、失败诊断与 Observability handoff

Runner 可以提供低风险的即时预览：阶段、有限 stdout/stderr 摘录、退出摘要、资源提示、source refs、freshness 和下一步建议。预览必须默认 redaction-first、body-bounded、不可作为正式证据。

失败诊断至少区分：

| 类别 | 示例语义 | Runner 行为 |
|---|---|---|
| Selection/authority | 未选择、不可见、approval 缺失、已撤销、版本冲突 | 阻止下载/启动，显示 source ref 和修复入口。 |
| Transfer/integrity | locator 不可用、下载中断、digest/signature 不匹配 | cache 保持 quarantine/invalid，不进入 Sandbox。 |
| Sandbox admission | policy/boundary/lease/resource guard 不满足 | 显示 blocked/rejected/pending，不宣称运行失败或成功。 |
| Execution | Runtime/Sandbox 正式报告 failed/cancelled/unknown | 保真展示 source outcome，不自行重试副作用。 |
| Cleanup/recovery | lease 丢失、orphan、cleanup guard 未通过、断线未知 | 停止危险操作，转入 reconcile/人工确认。 |
| Observation/handoff | diagnostic unavailable、handoff blocked/accepted/delivered | 仅显示 handoff 状态，不生成 verdict/signoff。 |

本地诊断到 Observability 的 handoff 只交安全摘要、source refs、关联 ID、错误分类和 redaction 结果；不交 raw secret、完整日志、evidence body 或未经裁剪的 runtime body。

### 2.7 `R-RUN-7` 断线恢复与跨平台体验

恢复流程候选：

```text
detect disconnect / restart
  -> freeze side-effect controls
  -> persist only safe local cursor/request posture
  -> reconnect SDK and revalidate actor/scope/source authority
  -> query formal sandbox/runtime status and lease
  -> reconcile local RunnerRun view
  -> expose confirmed / unknown / blocked next action
```

跨平台要求不是先选 Tauri、Electron 或容器，而是保证同一组语义在不同平台上成立：路径和权限差异不改变 source refs；端口/资源冲突可解释；休眠/唤醒、网络切换、用户注销和应用重启不会自动重放未知副作用；平台专属能力缺失时显式显示 `unsupported`。

## 4. 失败与降级统一口径（候选）

| 失败姿态 | 允许展示 | 允许操作 | 禁止误导 |
|---|---|---|---|
| `not_selected` | 选择入口与所需语境 | 选择正式 version | 显示默认/最新可运行。 |
| `not_visible` | 安全的不可见提示 | 返回上一级或重新认证 | 泄露对象存在性、digest 或审批细节。 |
| `pending` | 正在等待的步骤、关联 ref、预计下一动作（若有正式信息） | 查询、取消可取消请求 | 显示 ready/running/succeeded。 |
| `blocked` | 阻塞 owner、缺失前置和修复入口 | 在允许时重试查询或等待 owner | 本地绕过 guard、切换未经批准后端。 |
| `stale` | 旧值标记、来源时间和重新验证入口 | 重新查询/重新验证 | 把缓存当当前 authority。 |
| `unknown` | 未知原因、保护措施和 reconcile 入口 | 查询/人工确认；不自动重放副作用 | 猜测成功、失败或已清理。 |
| `degraded` | 可用子集、缺失范围和安全提示 | 只执行不依赖缺失部分的读操作 | 把 partial preview 当完整证据。 |
| `unavailable` | 服务/平台不可用和离线姿态 | 保存安全本地意图（如允许） | 离线启动新副作用或伪造正式结果。 |

## 5. 非目标

- 不拥有 Release/Artifact 正文、版本、baseline、digest authority 或 Governance approval。
- 不实现 Runtime loop、checkpoint、outcome、Sandbox backend、isolation policy、lease/reaper 或 archive restore。
- 不把本地 RunnerRun、download cache、PID、端口、stdout/stderr 或 telemetry 写回任何上游 truth。
- 不把 `latest`、默认版本、安装目录最新文件或网络响应状态当作正式选择。
- 不为旧技术选择（Tauri、Electron、Docker、gVisor、Firecracker）提前锁定架构。
- 不承诺未经 authority 支撑的 SLA、启动时延、并发数、成功率、带宽、磁盘或清理时限。

## 6. 待确认问题与 blocker（正式校准时逐项收口）

| 问题 | 影响的功能 | 当前处理 |
|---|---|---|
| Release 是 Artifact 的正式对象、还是由另一个 owner 提供可消费 release view？ | `FR-RUN-001~003` | 不本地命名 owner；等待 Artifact/治理消费合同。 |
| approved/baselined 的最小可验证 authority chain 是什么？ | `FR-RUN-002` | 只保留 authority chain 概念，未知即 blocked。 |
| locator、manifest、digest/signature 的来源和生命周期是什么？ | `FR-RUN-003` | 不锁 transport、算法、缓存布局。 |
| Sandbox request 的 runner-facing DTO、幂等 key、lease 和 reconcile API 是什么？ | `FR-RUN-005~007/011` | 只承接 Sandbox 已确认的 guard/lease/cleanup 原则。 |
| Runtime 是否提供端侧状态/结果安全 read surface？ | `FR-RUN-006~009` | 不复制 Runtime control 或 outcome；保持 adapter pending。 |
| Observability handoff 是否允许 Runner 提交安全摘要？ | `FR-RUN-009/010/013` | 只保留候选 seam，不宣称 receipt/报告存在。 |
| 平台资源探针与 Sandbox allocation 的冲突谁拥有最终裁决？ | `FR-RUN-004/011/012` | 本地 probe 只能提示，正式 allocation 优先。 |
| 断线时哪些请求可安全取消、哪些必须人工 reconcile？ | `FR-RUN-006/007` | 未知副作用冻结，等待正式恢复合同。 |

## 7. 本篇结论

Runner 的最小产品闭环是：**显式且可验证的 Release 选择 → 下载/cache/完整性门禁 → 正式 Sandbox 请求 → 分层的启动/运行/停止/清理状态 → 安全输出预览与诊断 → Observability handoff → 断线/lease/orphan 恢复**。其中所有跨域正向结果都必须回指 owner；本地状态只表达用户意图、取得过程和展示姿态。下一篇将把这一闭环分解为可落码前的模块、对象类别、adapter seam、状态组和切分顺序，仍不锁具体技术或实现事实。

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 的默认叙事是“用户是管理者,不直接写代码”,但仍然存在一类关键用户:他们需要把 AI 阶段性产出的代码同步到本地 IDE 里查看、接手、补充修改,然后再把这些修改以**可审计、可受控、不过主分支直通**的方式推回平台。普通 Git 工具只能同步文件,却不知道项目权限、Review Gate、Artifact 血缘与平台审计语义；而纯平台 UI 又无法满足本地 IDE、LSP、调试器等开发者工作流。L5-sync 因此承担的是“平台代码真相与本地工作区之间的受控同步桥”。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 3 当前) | 痛点 |
|---|---|---|
| 仓文档 | 只有 README 骨架 | 端侧产品型第四份样板尚未建立 |
| code Artifact 真相源 | `L1-artifact` 已有完整 00 需求样板 | Sync 如何消费 code kind 尚未仓级化 |
| review Gate 真相源 | `L1-governance` 已完成 00/01 | 本地 push-back 走 review Gate 的链路未产品化 |
| SDK 草案 | 已明确 SDK 是统一接入层 | CLI/本地工具接入边界还未正式落地 |
| 本地元数据 | README 已提出 `.qs-sync/metadata.json` 永久保留 | 元数据结构、作用与不可删除语义未写成正式需求 |

### 2.3 为什么要做(量化依据)

- `product/产品矩阵.md` 已把 Sync 定义为 **③ 独立产品**，服务于本地工作区同步场景
- README 已明确 `push-review` 必须进 review Gate、冲突不自动合并、`.qs-sync/metadata.json` 不可删,说明这不是普通 Git wrapper
- 若没有 Sync,开发者旁观者与项目接手人只能绕过平台自己 clone/改代码,平台将失去 review Gate、溯源和审计链
- `product/最终目的.md` 中“可观察与可审计”的承诺要求本地改动回流也要被纳入责任链

### 2.4 业务问题 vs 技术问题

- **业务问题**:开发者如何在不破坏平台治理结构的前提下,把代码同步到本地、修改后再受控推回
- **技术问题**:本地 clone/pull、双向同步、review Gate、Git 共存、冲突处理、元数据溯源、权限验证、大仓库性能与多用户协作策略

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 开发者 clone 一个自己有权限的项目到本地
2. 开发者 pull AI 团队最新代码变更
3. 开发者在本地修改代码后执行 `push-review`,进入平台 review Gate
4. 开发者遇到冲突时手动处理,而不是被工具静默合并
5. 审计者查看某次本地修改从 clone 到 push-review 的溯源链

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **开发者旁观者**,我想要 **把某个项目代码 clone 到本地 IDE**,以便 **在熟悉的开发环境里查看和理解 AI 产出** |
| 优先级 | P0 |
| 验收条件 | **Given** 用户拥有项目权限 **When** 执行 `qs-sync clone <project>` **Then** 本地工作区建立且生成 `.qs-sync/metadata.json` |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **项目接手人**,我想要 **pull AI 团队的最新代码**,以便 **在本地继续迭代而不脱离平台上下文** |
| 优先级 | P0 |
| 验收条件 | **Given** 本地已有同步工作区 **When** 执行 `qs-sync pull` **Then** 拉取最新可见代码并更新同步元数据 |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **开发者**,我想要 **把本地修改 push-review 回平台**,以便 **仍然进入平台的 review Gate 与审计链** |
| 优先级 | P0 |
| 验收条件 | **Given** 本地有修改 **When** 执行 `qs-sync push-review` **Then** 不直进主分支,而是创建 review 流并留下溯源记录 |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **平台**,我想要 **在出现冲突时拒绝自动合并**,以便 **关键代码整合仍由人类负责** |
| 优先级 | P0 |
| 验收条件 | **Given** 本地与远端存在冲突 **When** 执行同步 **Then** Sync 明确报冲突并要求人类处理 |

| 字段 | 内容 |
|---|---|
| ID | US-005 |
| 用户故事 | 作为 **审计者**,我想要 **查看某次本地修改的溯源元数据**,以便 **知道是谁、基于哪个项目、哪次同步上下文做出的改动** |
| 优先级 | P1 |
| 验收条件 | **Given** 一个 sync 工作区 **When** 查询 `.qs-sync/metadata.json` 与相关记录 **Then** 能看到项目、用户、基线、同步时间等元数据 |

### 5.3 替代流程

- 用户无项目权限 → clone/pull/push-review 被拒绝
- 本地 metadata 丢失或损坏 → 进入修复/重新绑定流程,不静默继续
- pull 发现冲突 → 进入显式冲突处理,不自动合并
- push-review 网络失败 → 保留本地状态并允许重试

## 8. 交互与界面需求

### 8.1 核心页面 / 流程

首期以 CLI 为主,核心流程是:

| 命令 / 流程 | 说明 |
|---|---|
| `qs-sync clone <project>` | 初始化本地工作区与 metadata |
| `qs-sync pull` | 拉取最新代码与同步上下文 |
| `qs-sync push-review` | 受控回推本地修改 |
| `qs-sync status` | 查看本地工作区与平台状态差异(建议预留) |
| 冲突提示流 | 当不能继续同步时给出明确指引 |

### 8.2 关键 UX 约束

| 约束 | 说明 |
|---|---|
| 不替代 Git 心智模型 | 开发者应理解这是“受控同步层”,不是新 VCS |
| 错误明确 | 权限/冲突/元数据损坏要能明确说明原因 |
| 不静默修复 | 元数据问题、冲突、权限错误都不能悄悄绕过 |
| 命令意图清晰 | `push-review` 必须显式表达“不是直推” |

### 9.1 核心业务实体

### 9.2 数据关系图

```text
Local workspace
  ├─ git repository
  ├─ .qs-sync/metadata.json
  ├─ bound project
  └─ latest synchronized artifact/code baseline
```

### 9.3 数据生命周期与归档

| 数据类型 | 保留期 | 归档策略 | 删除策略 |
|---|---|---|---|
| `.qs-sync/metadata.json` | 工作区全生命周期 | 本地持久保留 | 不允许删除 |
| 本地同步状态 | 会话/工作区级 | 本地更新 | 可通过 repair 重建 |
| push-review 结果摘要 | 短中期 | 本地日志/可选上报 | 自动轮转 |
| 绑定关系 | 工作区级 | metadata 持久化 | 解绑需显式操作 |

### 9.4 隐私与合规要求

| 数据字段 | 敏感级别 | 保护措施 | 合规依据 |
|---|---|---|---|
| 本地路径与用户信息 | 中 | 仅本地存储,不无授权上传 | 最小暴露原则 |
| 项目绑定信息 | 中 | 受权限校验保护 | 项目权限边界 |
| review 回推摘要 | 中高 | 仅显式上传或平台留痕 | 审计基线 |

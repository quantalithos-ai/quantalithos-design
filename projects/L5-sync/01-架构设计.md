## 1. 业务背景与驱动力

### 1.1 业务背景

Sync 不是 Git 的替代品,而是 Quantalithos 平台与本地开发工作区之间的**受控桥梁**。它服务于一个刻意保留的场景：当开发者旁观者、项目接手人或评审者需要把 AI 产出的代码带到本地 IDE 里理解、补充、修复时,平台必须给出一条既符合开发者习惯、又不绕过治理和审计的路径。Sync 因此既要尊重 Git 与本地文件系统的事实标准,又要把 `push-review`、项目权限、代码溯源和 review Gate 留在平台语义里。

### 1.2 业务驱动力

**业务驱动力**:
- 用户需要在本地 IDE 中处理代码,否则 AI 与人工协作会断裂成两套世界
- 平台必须允许“人类接手”而不丢失责任链、审批链和项目上下文
- 企业与团队需要证明本地修改回流后仍然经过平台治理,而不是形成平台外暗流

**技术驱动力**:
- 需要让 clone/pull/push-review 都通过 SDK 与平台服务达成一致契约
- 需要把本地元数据、项目绑定、review Gate 和 Git 共存策略统一到一套同步引擎中
- 需要将冲突处理、权限校验和审计可追溯做成硬边界而不是约定俗成

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 兼容性 | 与 Git 共存 | 100% 样本仓 | E2E / 手测 |
| 安全 | 无权限同步拦截率 | 100% | 安全测试 |
| 溯源 | metadata 覆盖率 | 100% | 回归测试 |
| 可靠性 | 自动合并次数 | 0 | 冲突测试 |
| 可恢复性 | 网络失败后重试成功率 | 100% 样本流 | E2E |
| 治理 | push-review 命中 review Gate | 100% | 集成测试 |

## 2. 约束条件

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| Sync 不替代 Git,Git 仍是底层真相载体 | README | 同步引擎必须建立在 Git 之上而不是重造 VCS |
| `push-review` 必须进入 review Gate | README + governance 约束 | 不允许直推主分支 |
| 冲突不自动合并 | README | 冲突路径必须中止并交给人类 |

| metadata 结构 | 首期最小闭包 | 可扩更多审计字段 |
| 辅助命令 | status / repair / rebind 未定 | 可按使用反馈增强 |

### 2.3 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 本地工作流差异 | 中高 | git facade + local workspace model |
| metadata 演进 | 中高 | versioned sync metadata schema |
| 平台 review 流程变化 | 中 | push-review adapter 隔离 |
| 仓规模增长 | 中高 | clone/pull strategy 抽象 |
| GUI 需求 | 中 | CLI core + optional shell |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **CLI-first sync engine + git facade + governance-aware push path**(当前) | 贴合开发者习惯,控制回流边界 | 需要建元数据与同步模型 | ✅ |
| 纯 Git 插件/脚本集合 | 实现快 | 难以稳定约束 review / metadata / 权限 | ❌ |
| 自定义工作区管理系统 | 理论统一 | 偏离开发者习惯,成本极高 | ❌ |
| 纯 GUI 同步器 | 面向非 CLI 用户友好 | 脱离开发者主工作流 | ❌ |

**最终选择**:**CLI-first 同步引擎 + Git facade + SDK 驱动的平台适配层**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 不替代 Git | 学习成本低、开发者信任高 | 需与多种 Git 状态兼容 |
| 元数据强绑定工作区 | 溯源与权限清晰 | 用户误删/损坏时需要修复流 |
| push-review 单独命令 | 明确治理边界 | 操作路径较 Git push 更严格 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```text
开发者旁观者 / 项目接手人 / 代码评审者
                    │
                    ▼
             ★ quantalithos-sync ★
             - clone / pull / push-review
             - local metadata & workspace binding
             - git coexistence
               │          │
               │          └────────▶ local git workspace
               └──────────────────▶ sdk -> artifact/work/governance
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 初始化本地工作区并绑定平台项目
- ✅ 拉取最新平台代码产物到本地
- ✅ 将本地修改以 `push-review` 方式送回平台 review 流
- ✅ 维护本地 metadata 与溯源状态

**不做什么**:
- ❌ 不替代 Git 的提交、分支、diff 等底层能力
- ❌ 不自动决定冲突或合并结果
- ❌ 不持有平台代码真相与项目真相
- ❌ 不直接绕过 review Gate 把修改推进主路径

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| Rust SDK | 100%(编译期) | 客户端契约漂移 | 版本锁 |
| artifact service | 99.9% | 无法拉取最新代码 | 重试 / 本地保留现状 |
| work/auth services | 99.9% | 项目权限判定失败 | 阻断操作 |
| governance review APIs | 99.9% | push-review 无法入 Gate | 显式失败并允许重试 |
| local git / fs | 环境依赖 | 环境不满足、权限异常 | 明确报错 |

### 4.4 关键依赖风险

- metadata 机制若不稳定,Sync 会丢失“这个工作区是谁、属于哪个项目、基于哪次同步”的关键上下文
- push-review 若与治理服务耦合过浅,可能出现“看似推回成功,实际未进入 Gate”的假阳性体验
- Git facade 若试图替开发者做过多自动化,会直接削弱可审计性与开发者信任

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Workspace Binding | 核心域 | 项目与本地工作区绑定真相 |
| Sync Engine | 核心域 | clone / pull / push-review 同步流程 |
| Governance Return Path | 核心域 | review Gate 回流路径 |
| Git Facade | 支撑子域 | 与 Git 共存的包装层 |
| Metadata & Provenance | 支撑子域 | `.qs-sync/metadata.json` 与审计字段 |
| Diagnostics | 支撑子域 | 冲突、权限、网络、元数据异常提示 |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Binding | 工作区与项目绑定 | WorkspaceBinding |
| Sync | clone/pull/push-review 生命周期 | SyncOperation |
| Metadata | 本地元数据读写与迁移 | SyncMetadata |
| Review Return | 本地改动回流到 review Gate | ReviewSubmission |
| Git Layer | Git 命令包装与状态检测 | GitWorkspaceState |
| Diagnostics | 错误与修复建议 | SyncDiagnostic |

### 5.3 上下文映射关系

- work → Binding: **Customer-Supplier**，Sync 需要平台给出项目权限与身份上下文
- artifact → Sync: **Conformist**，本地代码基于平台 artifact 真相同步
- governance → Review Return: **Open Host Service**，本地修改回流必须进入 Gate
- Git Layer ↔ Metadata: **Shared local context**,Git 状态变化影响 metadata 更新,但 metadata 不是 Git 真相

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| WorkspaceBinding | 某个本地目录与平台项目的绑定关系 | Binding |
| SyncMetadata | `.qs-sync/metadata.json` 中记录的本地溯源元数据 | Metadata |
| ReviewSubmission | 一次 push-review 形成的平台回流对象 | Governance Return |
| GitWorkspaceState | 本地 Git 工作区当前状态投影 | Git Layer |
| SyncDiagnostic | 人类可读的同步失败/冲突/权限提示 | Diagnostics |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```text
developer terminal / optional gui
            │
            ▼
        sync shell
           │
           ▼
      shared sync core
      ├─ binding / metadata
      ├─ git facade
      ├─ sync engine
      └─ review return adapter
           │         │
           │         └────────▶ local git workspace
           └──────────────────▶ sdk -> artifact/work/governance
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| CLI shell | 命令入口与参数解析 | Rust CLI | 主入口 |
| optional GUI shell | 轻量图形工作区入口 | Rust + Tauri(可选) | 可选壳层 |
| shared sync core | 绑定、同步、回推、诊断共用逻辑 | Rust | 核心逻辑 |
| git facade | Git 状态检测与命令封装 | Rust + git invocation/lib | 本地适配 |
| metadata store | 元数据持久化 | local fs/json | 工作区级 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| Sync → Server | Rust SDK | 手写 RPC/HTTP | 统一契约与认证 |
| Sync → Git | facade / command wrapper | 自造 VCS | 保持开发者习惯 |
| CLI/GUI 共用逻辑 | shared sync core | 双实现 | 避免行为漂移 |
| 回推治理 | review adapter + governance call | 直推远端 | 保持 review Gate 边界 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| 平台代码真相 | artifact service | sync |
| 项目权限真相 | work/auth services | sync |
| 本地工作区状态 | git workspace | sync |
| 本地 metadata | sync | sync / user |
| review 回流结果 | governance/platform | sync / user |

### 6.5 部署拓扑

- Sync 首期以本地 CLI 为主,可选小型 GUI 外壳
- 无自建后端,全部通过 Rust SDK 接平台服务
- 所有本地状态以工作区为边界,不做全局隐式跨项目共享

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```text
shell(cli/gui)
    │
    ▼
shared sync core
    ├─▶ binding / metadata
    ├─▶ sync engine
    ├─▶ review return
    └─▶ git facade
            │
            ▼
      sdk truth / local git truth
```

### 7.2 层间约束规则

- shell 只负责交互与命令入口,不直接操作 Git 或平台服务
- Git facade 只包装与检测 Git 状态,不承载平台治理逻辑
- review return 只负责把本地修改送入平台 review 链,不直接推主分支
- metadata 是工作区绑定与溯源的本地真相,但不是代码内容真相
- Sync 遇到权限、冲突、metadata 异常时必须显式中断,不做静默修复

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| ProjectAccessAdapter | sync core | Rust SDK work/auth adapter |
| ArtifactSyncAdapter | sync core | Rust SDK artifact adapter |
| ReviewReturnAdapter | sync core | Rust SDK governance adapter |
| GitWorkspaceAdapter | sync core | git facade implementation |
| MetadataStore | sync core | local JSON/fs store |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(开发者本地入口产品) |
| 传出耦合 | 中高(artifact/work/governance/git/fs/sdk) |
| 不稳定性 | 中 |
| 抽象度 | 中高(sync core + local/platform adapters) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Code artifact truth | artifact | sync | 最终一致 | stale code snapshot |
| Project access truth | work/auth | sync | 最终一致 | 权限延迟 |
| Local Git state | local git workspace | sync / user | 本地强一致 | 工作区损坏 |
| SyncMetadata | sync | sync / user | 本地强一致 | metadata 损坏 |
| Review submission truth | governance/platform | sync / user | 最终一致 | push-review 假成功 |

### 8.2 一致性层次

- 平台代码与权限真相来自 artifact/work/governance,Sync 只做最终一致消费
- 本地工作区与 metadata 由 Sync 在本地强一致维护
- review 回推是异步一致流程,必须把“已提交到 Gate”与“本地命令成功退出”清晰区分

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| pull 过程中网络失败 | artifact 拉取中断 | 保留当前工作区状态并允许重试 | `sync_op_id` |
| push-review 成功上传但 Gate 创建失败 | 平台回流部分失败 | 给出失败状态并允许重试/恢复 | `review_submission_id` |
| metadata 损坏 | 文件缺失/解析失败 | 中断并进入 repair/rebind 路径 | `workspace_id` |
| 冲突检测命中 | git facade 判断冲突 | 中断并提示人工处理 | `sync_op_id` |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:CLI-first + Git facade + review return(当前) | 方案 B:Git 脚本集合 | 方案 C:私有同步系统 |
|---|---|---|---|
| 开发者适配度 | 高 | 中 | 低 |
| 平台治理一致性 | 高 | 中低 | 高 |
| 实施复杂度 | 中 | 低 | 高 |
| 长期信任度 | 高 | 中 | 低 |
| 定位清晰度 | 高 | 中 | 低 |

### 10.2 最终选择与理由

选择 A,因为 Sync 的价值不是“多一个 clone 命令”,而是让本地开发工作流仍然处在平台治理和审计之内。B 太弱,难以承接 metadata 与 review Gate；C 虽统一,却会直接背离开发者对 Git 和本地工作区的心智模型。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 重试 | 网络失败、review 返回失败都支持显式重试 |
| 降级 | observability 不可用不影响本地同步主路径 |
| 隔离 | git、metadata、platform adapters、shell 分层 |
| 恢复 | repair/rebind 预留为异常恢复入口 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | clone/pull/push-review、权限拒绝、metadata 修复、冲突命中 |
| 指标 | clone 成功率、pull 成功率、push-review 成功率、冲突率 |
| trace | 本地操作 → SDK → artifact/work/governance 可关联 |
| 健康检查 | 关注 metadata 完整性与平台回流成功率 |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| 权限校验 | 所有操作前经项目权限检查 |
| 治理回流 | push-review 必过 review Gate |
| 本地元数据 | 不允许静默删除或忽略 |
| 冲突处理 | 不自动裁决,保留人类控制 |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | remote endpoint、clone depth、LFS strategy、log verbosity 外部化 |
| 环境隔离 | dev/staging/prod endpoints 可切换 |
| 动态更新 | helper commands / diagnostics policy 可后续扩展 |
| 配置五要素 | type / default / source / scope / constraints 明确 |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| clone 初始化 | 样本仓可用 | benchmark | 主同步路径 |
| pull 增量同步 | 样本仓可用 | benchmark | 主同步路径 |
| push-review 提交 | 可接受交互延迟 | E2E | 治理回流路径 |
| 冲突检测 | 不额外隐藏长耗时 | E2E | 开发者心智可接受 |

**端到端交付分解**(把本地修改受控推回平台):

```text
clone 绑定工作区
 + pull 获取最新代码
 + 本地修改
 + push-review 触发回流
 + review Gate 接手
 + 平台继续审查链
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| status/repair/rebind 辅助命令未定 | 影响恢复体验 | P1 |
| 大仓浅克隆/LFS 策略未定 | 影响规模化仓使用 | P1 |
| 可选 GUI 外壳未定 | 影响非 CLI 用户体验 | P2 |
| Web IDE 集成未定 | 影响未来扩展 | P2 |

### 12.2 触发条件(可量化)

| 指标 | 阈值 | 动作 |
|---|---|---|
| pull/clone 对大仓失败率上升 | > 阈值 | 引入更强浅克隆/LFS 策略 |
| metadata 损坏问题频发 | > 阈值 | 正式设计 repair/rebind 流 |
| push-review 假成功/误解反馈 | > 阈值 | 强化回流状态模型与文案 |
| GUI 需求持续增长 | > 2 个 Sprint | 设计小型壳层 |

### 12.3 演进步骤

```text
阶段 1: clone / pull / push-review 主路径跑通
   └─ 可停止点:本地接手与受控回流成立

阶段 2: metadata 恢复、冲突体验与大仓优化增强
   └─ 可停止点:实际开发者可持续使用

阶段 3: 可选 GUI / Web IDE 集成 / 多用户高级场景
   └─ 可停止点:Sync 成为稳定的本地桥接产品
```

### 12.4 目标架构

Sync 的目标架构不是“帮你方便一点用 Git”,而是 **平台代码真相与本地开发真相之间的治理桥**:开发者能用熟悉的本地工作流工作,平台仍能知道发生了什么、谁做了什么、哪些修改进入了正式 review 链。未来扩展也必须围绕“Git 共存、受控回流、溯源可查、人类裁决”四条主线。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| metadata 损坏导致工作区失联 | 中 | 高 | repair/rebind 设计 |
| push-review 状态反馈不清 | 中 | 高 | review submission 状态显式化 |
| 大仓同步性能差 | 中 | 中 | 浅克隆/LFS/增量策略 |
| 开发者误用为直推工具 | 中 | 中 | 命令与文案边界清晰 |

### 13.2 边缘风险

- 多用户共享同一工作区导致元数据与 Git 状态冲突
- 绕过 Sync 的 Git push 形成平台外暗流
- 后续 Web IDE 集成把 CLI-first 简洁模型拖复杂

### 13.3 待确认问题

| 问题 | 截止 | 负责人 |
|---|---|---|
| 是否首批提供 status/repair/rebind 命令 | 批次 7 内 | Sync |
| 大仓是否首批支持浅克隆/LFS | 批次 7 内 | Sync + Artifact |
| 可选 GUI 壳层是否纳入后续 | 批次 7 后 | Sync + Product |
| 多用户协作同项目的本地同步策略 | 批次 7 后 | Sync + Governance |

## 14. 上线策略

### 14.1 灰度方案

```text
阶段 1: 样本小仓 clone/pull/push-review 主路径
阶段 2: 冲突路径与权限拒绝路径验证
阶段 3: 大仓样本与增量同步增强
阶段 4: 可选 GUI / 高级辅助命令
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| push-review 绕过 review Gate | S 级 | 立即停用回推入口并修复治理链 |
| metadata 模型错误导致大面积工作区异常 | S 级 | 回滚 metadata schema 版本 / 提供修复脚本 |
| clone/pull 广泛失败 | A 级 | 回滚同步引擎或特定优化策略 |
| 大仓性能异常 | B 级 | 暂停相应优化策略,退回基础模式 |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| clone/pull 成功率 | < 阈值 | warning |
| push-review 失败率 | > 阈值 | major |
| review Gate 命中异常 | > 0 | security |
| metadata 损坏率 | > 阈值 | warning |
| 冲突率异常 | > 阈值 | warning |

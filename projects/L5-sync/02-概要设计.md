## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L5-sync` 不是 source truth 仓,也不是底层消息总线仓,更不是重试脚本目录。它是 **“系统间状态同步与跨端一致性产品层 / sync experience 层”**。

你可以把它理解成:
- 哪些对象、状态、列表、摘要需要在多个端、多个工作台、多个消费面之间保持同步
- 同步任务、同步状态、冲突、重试、回放、补偿怎样被组织成可见、可操作、可诊断的产品层能力
- chat、console、runner 等不同消费面怎样看到“正在同步 / 已同步 / 失败 / 冲突 / 回放中”
- bus、runtime、artifact、archive、member、conversation 等多个系统的变化怎样被组织成统一的一致性体验

这些事情,都由 `L5-sync` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L5-sync`,这些跨端和跨面的一致性事实就会散落在:
- `chat` 自己的 thread 刷新逻辑里
- `console` 自己的 panel/context 联动逻辑里
- `runner` 各自的状态刷新与结果回补逻辑里
- `artifact` / `archive` 各自的增量视图刷新逻辑里
- 各种本地 polling、重试、手工刷新和补偿脚本里

结果就会出现:
- 哪些变化需要同步没有统一主线
- 同步状态、冲突、过期、回放彼此没有统一语义
- 多端看起来都“差不多”,但其实并不一致
- 同步失败时用户和操作者看不到统一的状态与修复入口
- sync 逻辑长期分散在各个产品面里,不可维护

所以 `L5-sync` 必须独立存在,作为:
> **把多源系统变化组织成可见、可诊断、可重试、可冲突处理的跨端一致性产品层。**

### 1.3 新人最容易混淆的几个词

#### SyncTask
就是:
> 一条正式需要被同步的任务记录。

它不是 source domain truth 本体。

#### SyncStatus
就是:
> 一条同步任务当前的过程状态,如 queued / syncing / synced / failed / replaying。

它不是源对象本体状态。

#### SyncProjection
就是:
> 为了把某个 source result 分发到多个消费面而构建的同步层投影。

它不是 source projection truth 本体。

#### ConflictView
就是:
> 系统为用户或操作者展示的不一致解释和修复入口。

它不是源系统正式冲突模型本体。

#### Replay / Resync
就是:
> 对同步过程的重放、重试或补偿。

它不是业务裁决重做。

#### Cross-device consistency
就是:
> 不同端、不同工作台、不同产品面对同一 source 结果保持统一可见性。

它不等于这些端都共享同一份真相所有权。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L5-sync/02` 时,先收稳以下前提:
- `L5-sync` 不应按任务列表、冲突页、重试按钮、事件流横向平铺理解,而应按同步体验主链责任拆
- sync 至少应拆成“同步对象识别与任务入口 / 同步编排与状态推进 / 冲突检测与一致性修复 / 跨端分发与消费体验 / 重试、回放与运维干预”五个主要部分
- sync 自己拥有的真相不是 bus truth、source truth、runtime truth 或 artifact truth,而是 sync task / sync status / conflict / delivery / replay 这类一致性产品层真相
- `L5-sync` 只能为多个消费面提供一致性体验层,不能反过来替 source systems 持有正式领域真相
- 02 的重点不是“列有哪些同步接口和任务状态”,而是先把“sync 层在平台里到底是什么、和 bus/chat/console/runner/runtime/artifact/archive/observability 怎么分层”讲清楚
- sync scope、conflict resolution、cross-device view、replay/resync、lag/backlog 这些不是零散机制,而是 sync 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的跨端一致性与同步体验心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,用户看到的不是单个系统,而是跨多个产品面的结果。用户真正需要的不是“最终能刷新出来”,而是:
- 哪些变化需要从 source systems 传播到 chat、console、runner 等消费面
- 同步现在在排队、进行、失败还是冲突
- 同步失败后要不要重试、是不是 stale、需不需要人工介入
- 多端看到的 thread、summary、result、hint 是否仍然是一致的
- operators 是否能从统一 sync 面理解并修复一致性问题

如果把这些逻辑分别散落到:
- 各个产品面的本地刷新逻辑
- 各种 polling / retry / invalidate 脚本
- source systems 自己维护的局部投影刷新逻辑
- 手工 resync / replay 操作里

系统会快速退化成:
- 用户侧体验虽然能跑,但一致性不可解释
- 哪些状态是“源变了”还是“同步没跟上”无法分清
- 冲突和 stale 只能靠人工猜测
- 不同前端和工作台会对同一对象呈现不同状态
- 同步问题难以产品化治理

因此,本概要设计的任务就是:
> **把 `L5-sync` 写成一个新人也能看懂的“系统间状态同步与跨端一致性产品层”,而不是把同步逻辑散在每个产品面里。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 同步主线统一性 | 多处本地刷新逻辑 | 单一 sync 主线 | 需正式收敛 |
| stale/conflict 可解释性 | 局部且不统一 | 统一可见状态与修复入口 | 需形成产品心智 |
| 跨端一致率 | 依赖实现细节 | 多端一致率 100% 样本链 | 需正式主线 |
| replay/resync 治理 | 手工/脚本化风险高 | 正式 replay/resync 主线 | 需收稳控制链 |
| sync 诊断能力 | 分散 | 可观测、可回放、可审计 | 需形成统一出口 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让平台多个消费面在源系统变化后保持一致可见,并在不一致时给用户和操作者清晰、可操作的同步体验
- **技术问题**:SyncTask、SyncStatus、ConflictView、SyncProjection、Replay/Resync、Cross-device consistency 与 bus / chat / console / runner / runtime / artifact / archive / observability 之间的边界如何稳定建模,并形成统一 sync 主链

## 4. 约束条件

### 4.1 技术约束

- 所有进入 sync 层的变化都必须通过正式 SyncTask 主线进入
- sync status、sync projection、conflict view 必须始终可回指 source refs
- replay/resync 只能重做同步过程,不能重做业务裁决
- 跨端一致性只能消费 source truth 和 bus 传播结果,不能各端私自定义真相
- stale / conflict / replay / backlog 必须统一建模,不能散落在各产品面临时逻辑里

### 4.2 资源约束

- 同步任务数、重试次数、冲突记录和 replay 历史会持续增长,存储与索引复杂度必须受控
- 多端同步刷新不能拖垮 source systems
- conflict compare 和 resync 不能无限放大重放成本

### 4.3 时间约束

- 当前阶段先收稳统一 sync 主线,而不是先做复杂离线合并、跨租户同步或高级一致性分析
- task、status、conflict、delivery、replay 五条基础链必须优先稳定,否则后续所有产品面的一致性都不可解释

### 4.4 合规约束

- sync 层不得反写 source truth 本体
- replay / resync 必须留审计证据链
- conflict 处理与手工修复入口必须可追溯
- stale / unavailable 提示不能伪装成 source truth 本体状态

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| sync tasks/day | 高频 | 多源系统变化和多端消费需求 |
| conflict records | 中高 | 长周期跨端一致性治理 |
| replay / resync jobs | 中高 | 失败与补偿需求 |
| sync-ready projections | 高频 | 多端工作台与产品面消费 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ bus / source systems        │
                    │ chat / runner / console     │
                    │ runtime / artifact / archive│
                    └────────────┬───────────────┘
                                 │ sync source input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-sync                    │
                    │ - task / status / conflict │
                    │ - replay / delivery views  │
                    └────────────┬───────────────┘
                                 │ sync experience output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ product surfaces           │   │ operators / owners         │   │ observability              │
│ - chat / console / runner  │   │ - repair / inspect         │   │ - sync diagnostics         │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L5-sync` 自己负责同步对象识别、同步任务状态、冲突可见化、跨端分发、重试/回放/运维干预等产品体验主线
- `L0-bus` 和各 source systems 提供变化传播与 source refs,但 sync 不拥有 transport truth 或 source truth 本体
- chat、console、runner 等产品面是同步结果消费方,而不是各自重新发明一套同步模型
- operators / owners 通过 sync 层理解并修复不一致,而不是直接在每个产品面里手工补丁式处理

所以 `L5-sync` 在全局里的角色是:
> **把多源系统变化组织成可见、可诊断、可重试、可冲突处理的跨端一致性产品层。**

### 5.3 系统边界

**做什么**:
- 定义 SyncTask / SyncStatus / SyncProjection / ConflictView / ReplayRequest
- 管理 queued/syncing/synced/failed/replaying 等状态
- 管理冲突检测、stale、重放、重试与人工修复入口
- 提供 per-surface sync views 与统一同步诊断面

**不做什么**:
- 不持有 source truth 本体
- 不替代 L0-bus transport truth
- 不重做业务裁决真相
- 不替代 observability / archive 真相本体
- 不替代底层队列、CDC、复制系统本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| bus / source event stream | 99.95% | backlog / replay,不静默丢失 sync task |
| source systems | 99.9% | 单源短暂失联时保留 stale/conflict 视图并阻断误同步 |
| product surfaces | 99.9% | 个别消费面不可用不影响 sync truth,但需标 target lag |
| operators / repair API | 99.9% | repair 入口不可用时保留 conflict 可见性与 ticket |
| observability | 99.9% | hint/diagnostic 缺失时保留基础 sync status 与 backlog |

### 5.5 关键依赖风险

- sync status 与 source truth 漂移会直接误导用户判断系统一致性
- replay/resync 若无证据链,会让 operators 无法区分“已同步”与“假恢复”
- conflict 视图若和 source 冲突真相混层,会导致错误修复
- 不同消费面若各自处理同步状态,将重新回到分散实现
- stale / lag 若不被统一表达,多端体验会持续碎裂

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把任务列表、状态页、冲突页、重试按钮等页面元素横向平铺。  
> 它按 **同步体验主链职责 + 任务 / 状态 / 冲突 / 分发 / 恢复差异** 来拆分。  
> 因此下面每一部分都可能包含多个交互对象和机制,共同支撑同一段 sync 体验主链。

#### 同步对象识别与任务入口部分

- **它是什么**: 这是 `L5-sync` 的主入口层,一起回答“什么需要同步、怎样形成正式任务”
- **为什么单独有它**: 如果没有独立 sync task 入口层,变化识别和状态推进会直接混到一起,后续冲突和修复也会失去共同锚点
- **负责什么**:
  - 接收 source change intake
  - 识别 sync target / scope / target surfaces
  - 创建正式 SyncTask
- **不负责什么 / 容易混淆点**:
  - 不持有 source truth 本体
  - 不直接推进 sync 状态结果
  - 不等于 bus transport truth
  - 最容易和 domain source event、业务对象状态变更、底层队列消息本体混淆
- **与其他部分交互**:
  - 下游: 状态推进、冲突修复、分发与恢复
  - 外部: bus / source systems / product surfaces
  - 交互类型: intake 型 + task entry 型
- **后续详细设计展开点**:
  - SyncTask / SyncScope / target surface 模型

#### 同步编排与状态推进部分

- **它是什么**: 这是 sync 的过程主线层,一起回答“一个同步任务怎样向前推进”
- **为什么单独有它**: 状态机本身就是同步体验的核心可见结构,不单列就会和冲突/重试/消费面缠在一起
- **负责什么**:
  - 管理 queued / syncing / synced / failed / stale / replaying 状态
  - 管理 sequencing / checkpoint / lag tracking / ack
  - 形成统一 sync progress 视图
- **不负责什么 / 容易混淆点**:
  - 不等于 source object state
  - 不等于 bus transport truth
  - 不负责 conflict 内容本体
  - 最容易和 source lifecycle、queue 真相、CDC 进度真相混淆
- **与其他部分交互**:
  - 上游: 同步对象识别与任务入口部分
  - 下游: 冲突修复、分发体验、恢复干预
  - 交互类型: status machine 型 + lag/checkpoint 型
- **后续详细设计展开点**:
  - SyncStatus 模型
  - ack/checkpoint/lag 主线

#### 冲突检测与一致性修复部分

- **它是什么**: 这是 sync 的异常一致性层,一起回答“不一致时怎样识别和修复”
- **为什么单独有它**: 冲突与 stale 不是普通错误,如果不单列,会退化成若干零散重试和手工修补逻辑
- **负责什么**:
  - 检测 divergence / stale / missing update
  - 生成 conflict view / merge hint / resolution proposal
  - 提供 manual resolve entry
- **不负责什么 / 容易混淆点**:
  - 不持有 source conflict truth 本体
  - 不替代 source business decision
  - 不负责跨端分发本体
  - 最容易和源仓冲突模型、业务裁决、最终状态本体混淆
- **与其他部分交互**:
  - 上游: 状态推进部分 / source compare inputs
  - 下游: 分发体验 / 恢复干预 / operators
  - 交互类型: conflict detect 型 + repair entry 型
- **后续详细设计展开点**:
  - ConflictView / stale markers / resolution proposal 模型

#### 跨端分发与消费体验部分

- **它是什么**: 这是 sync 的多端传播层,一起回答“变化怎样被送到多个消费面”
- **为什么单独有它**: sync 的存在价值不是只维护状态机,而是要真正让 chat、console、runner 等消费面感知一致结果
- **负责什么**:
  - 构建 per-surface sync view
  - 管理 fanout / delivery / visibility filtering
  - 管理 cross-device / cross-workspace consistency view
- **不负责什么 / 容易混淆点**:
  - 不等于 source projection truth
  - 不替代 source systems 的正式只读真相
  - 不负责 conflict 修复裁决本体
  - 最容易和 source projection、UI local state、bus fanout 真相混淆
- **与其他部分交互**:
  - 上游: 任务入口、状态推进、冲突检测
  - 下游: chat / console / runner / users
  - 交互类型: fanout 型 + sync-ready projection 型
- **后续详细设计展开点**:
  - per-surface sync views
  - delivery / visibility 主线

#### 重试、回放与运维干预部分

- **它是什么**: 这是 sync 的恢复与操作层,一起回答“卡住、失败、冲突时怎样恢复”
- **为什么单独有它**: 同步稳定性很大程度取决于 replay / retry / resync / manual repair 能力,如果不单列会散成大量脚本式操作
- **负责什么**:
  - 提供 retry / replay / resync / manual trigger
  - 提供 backlog inspect / operator intervention
  - 保留恢复过程证据链
- **不负责什么 / 容易混淆点**:
  - 不重做业务裁决真相
  - 不直接改写 source domain truth
  - 不替代 observability / archive 证据链本体
  - 最容易和 source rollback、业务重做、总线补偿逻辑混淆
- **与其他部分交互**:
  - 上游: 状态推进、冲突修复、source gap
  - 下游: operators / product surfaces / observability
  - 交互类型: recovery control 型 + operator assist 型
- **后续详细设计展开点**:
  - ReplayRequest / ResyncTicket / RepairEntry 模型

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ bus / source systems        │
                    │ chat / runner / console     │
                    │ runtime / artifact / archive│
                    └────────────┬───────────────┘
                                 │ sync source input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-sync                    │
                    │ - task / status / conflict │
                    │ - replay / delivery views  │
                    └────────────┬───────────────┘
                                 │ sync experience output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ product surfaces           │   │ operators / owners         │   │ observability              │
│ - chat / console / runner  │   │ - repair / inspect         │   │ - sync diagnostics         │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L5-sync` 自己负责“识别哪些变化要同步”“管理 sync task 生命周期”“识别并展示冲突/过期”“分发一致性视图”“提供 replay/resync/repair 干预能力”
- `L0-bus` 和 source systems 的交互主要落在 **同步对象识别与任务入口部分** 与 **同步编排与状态推进部分**,为 sync 提供变化事件和 source refs 输入
- `chat` / `console` / `runner` 的交互主要落在 **跨端分发与消费体验部分**,消费 per-surface sync views 与状态摘要
- `observability` 的交互主要落在 **重试、回放与运维干预部分** 与 **冲突检测与一致性修复部分**,为 sync 提供诊断与 backlog 观察面补充
- operators / owners 消费的是 sync 提供的任务、状态、冲突、repair 体验层,而不是直接依赖底层脚本与 source logs

### 7.3 分模块交互说明(逐个写)

#### 与 `L0-bus / source systems` 的交互

```text
┌────────────────────────────┐
│ bus / source systems       │
│ - source changes / refs    │
└────────────┬───────────────┘
             │ task intake input
             ▼
┌────────────────────────────┐
│ sync                       │
│ - SyncTask                 │
│ - SyncStatus               │
└────────────────────────────┘
```

- 这些系统是 **同步来源方**
- **交互类型**: source change / sync intake 输入型交互
- **主流程位置**: source updated、event emitted、replay needed 时进入主流程
- **交互解释**:
  - sync 只消费变化与 refs
  - 不替代 bus truth 和 source truth
- **高风险异常流**:
  - sync pipeline 被误当 transport/source truth 本体
- 后续 `03-详细设计.md` 继续展开:
  - SyncTask intake contract
  - checkpoint / lag 主线

#### 与 `chat / console / runner` 的交互

```text
┌────────────────────────────┐
│ sync                       │
│ - per-surface sync views   │
│ - stale / conflict status  │
└────────────┬───────────────┘
             │ sync delivery output
             ▼
┌────────────────────────────┐
│ chat / console / runner    │
│ - refresh / stale / sync UX│
└────────────────────────────┘
```

- 这些系统是 **同步消费方**
- **交互类型**: sync-ready projection 输出型交互
- **主流程位置**: delivery ready、state changed、conflict detected、resync completed 时进入主流程
- **交互解释**:
  - sync 提供统一的状态/一致性消费面
  - 各产品面不应各自再发明同步状态模型
- **高风险异常流**:
  - 不同消费面对同一 sync task 显示不同状态
- 后续 `03-详细设计.md` 继续展开:
  - per-surface sync views
  - delivery / visibility 主线

#### 与 `operators / owners` 的交互

```text
┌────────────────────────────┐
│ sync                       │
│ - task / conflict / replay │
└────────────┬───────────────┘
             │ repair/inspect output
             ▼
┌────────────────────────────┐
│ operators / owners         │
│ - inspect / replay / fix   │
└────────────────────────────┘
```

- 这些系统和角色是 **同步修复与观察消费方**
- **交互类型**: repair/inspect consume 型交互
- **主流程位置**: failed/stale/conflict/replay 时进入主流程
- **交互解释**:
  - sync 提供统一的 repair / inspect / replay 入口和状态
  - 不替代 source business decision 本体
- **高风险异常流**:
  - replay/resync 被误认为 source truth 已完全恢复
- 后续 `03-详细设计.md` 继续展开:
  - conflict / repair / replay contract

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是 sync 体验层、哪个模块是分发消费方、哪个模块是 repair/inspect 消费方

本节**不**展开:
- queue / retry / replay 的底层实现细节
- CDC / 事件存储算法细节
- per-surface refresh 的缓存实现
- 冲突合并算法细节
- 自动化修复脚本细节

这些内容留到 `03-详细设计.md` 中继续展开。

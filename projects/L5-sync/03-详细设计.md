## 1. 模块职责描述

**本模块做什么**:
- 持有正式 SyncTask / SyncStatus / SyncProjection / ConflictView / ReplayRequest / ResyncTicket / RepairEntry 等 sync 体验层真相
- 把 bus 和多源系统变化收束成统一的同步任务、状态、冲突、分发和恢复主线
- 为 chat / console / runner 等消费面提供 per-surface sync views,并为 operators/owners 提供 repair/replay/resync 入口
- 管理 lag/checkpoint、stale、conflict、manual resolve、replay/resync 的产品层规则与证据链

**本模块不做什么**:
- 不持有 source truth 本体
- 不替代 L0-bus transport truth
- 不重做业务裁决真相或底层队列/CDC/复制系统本体
- 不替代 observability / archive 的真相本体

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 sync“为什么存在”,而是让开发者可以直接开始实现:
- source changes 如何被识别为正式 SyncTask 并进入统一状态机
- queued/syncing/synced/failed/stale/replaying 怎样形成统一可见生命周期
- conflict / stale / divergence 怎样被检测、解释、修复和回放
- per-surface sync views 怎样稳定分发给 chat / console / runner
- operators 怎样通过 replay/resync/manual repair 恢复一致性且保留证据链

如果不先把这些内容采集清楚,03 很容易退化成:
- 任务状态表和错误码清单
- 重试与 replay 脚本说明
- 各产品面各自的刷新状态说明
- bus / CDC / cache / UI 更新逻辑彼此脱节

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `SyncTask / SyncStatus / ConflictView / SurfaceSyncView / ReplayRequest` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是同步体验主链,`03` 却退化成队列、重试、冲突和缓存逻辑清单
- 实现者知道有 stale/conflict/replay,却不知道它们如何和 per-surface sync views、operators 修复面构成一条统一产品主线
- task、status、delivery、repair 各写一套,彼此断裂

#### 5.2.4 关键函数代码片段

```rust
/// 根据来源变化创建正式 SyncTask。
fn create_sync_task(
    intake_repo: &dyn SyncIntakeRepo,
    intake: SourceChangeIntake,
) {
    // [intake.校验来源变化边界]
    // 先确认同步层只消费变化输入,不替代 source object 本体。
    intake.validate_sync_intake_boundary();

    // [SyncTask::从来源变化创建]
    // 再把 source change 与 target/scope 收束成正式同步任务。
    let task = SyncTask::from_intake(intake);

    // [intake_repo.保存同步任务]
    // 最后把同步任务写入 sync 层,供状态、冲突和分发主线消费。
    intake_repo.save_sync_task(task);
}
```

这段实现守住的边界是:
- SyncTask 只承载同步过程,不替代 source truth
- source 变化必须先进入统一任务层,后续状态/分发/repair 才有共同锚点
- sync scope 只描述传播范围,不描述 source ownership

#### 5.2.5 该部分的边界与非职责
- 不推进 sync 状态机结果
- 不承担冲突修复逻辑
- 不直接做分发投影
- 不替代 bus/source truth 本体

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `同步编排与状态推进部分` 提供 sync task 输入
- 向 `冲突检测与一致性修复部分` 提供 source refs 与 intake 基线
- 向 `跨端分发与消费体验部分` 提供 target surfaces 基线

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `SyncTask ≠ source domain truth` 必须写死
- `sync scope ≠ source ownership` 必须写死
- 若 source change 未进入正式 SyncTask,后续所有 sync 状态都会失锚

```rust
/// 根据同步任务推进状态并记录 checkpoint 与 lag。
fn advance_sync_status(
    status_repo: &dyn SyncStatusRepo,
    task: SyncTask,
) {
    // [task.校验状态推进边界]
    // 先确认这次推进的是同步层状态,而不是 source object 本体状态。
    task.validate_sync_status_boundary();
```

- checkpoint/lag 是同步层证据,不替代 bus transport 真相

- 不持有 source object lifecycle truth
- 不替代 bus transport truth
- 不负责 conflict 合并本体
- 不直接做 per-surface projection

```text
   ▼
persistence / delivery / repair evidence
```

#### 读路径

```text
surface sync / backlog / conflict / history query
   │
   ▼
projection / query adapter
   │
   ▼
sync task views / conflict views / surface views / backlog views
```

#### 关键说明

- SyncTask、SyncStatus、ConflictView、SurfaceSyncView、ReplayRequest 属于强一致写路径
- sync task/surface/conflict/backlog/health 视图属于可最终一致读路径
- sync_task_view / sync_surface_view / sync_conflict_view 绝不能反向成为 source truth 或 bus truth 写源
- replay / repair / delivery 的分歧必须回收到 checkpoint、lag、history 与 source refs 对账主线

### 7.5 关键函数/命令级伪代码

#### `BuildSurfaceSyncView`

```text
function BuildSurfaceSyncView(input):
    1. 校验 target surface 合法
    2. 校验 sync-ready projection 只消费 source results
    3. 生成 SurfaceSyncView / DeliveryEnvelope
    4. 应用 VisibilityFilter
    5. 写入 per-surface view
    6. 返回 view id
```

#### `DetectConflict`

```text
function DetectConflict(input):
    1. 读取 SyncStatus / Checkpoint / Lag / source refs
    2. 比较 source 与 target 结果是否一致
    3. 标记 stale / divergence / missing update
    4. 构建 ConflictView / ResolutionProposal
    5. 写入 conflict history
    6. 返回 conflict id
```

### 7.10 错误码定义

| 错误码 | 含义 | HTTP / RPC 映射 | 恢复策略 |
|---|---|---|---|
| `SOURCE_REF_INVALID` | 来源引用非法 | 400 / INVALID_ARGUMENT | 修正 source refs |
| `SYNC_TASK_NOT_FOUND` | 同步任务不存在 | 404 / NOT_FOUND | 重新创建或刷新任务 |
| `SYNC_CHECKPOINT_MISMATCH` | checkpoint 与 source 结果不一致 | 409 / FAILED_PRECONDITION | 重建 checkpoint / replay |
| `SYNC_SURFACE_STALE` | 某消费面仍然过期 | 409 / FAILED_PRECONDITION | 重试 delivery / resync |

### 7.11 返回值语义分类

| 类别 | 语义 | 处理建议 |

## 8. 运行期主线场景

### 8.1 场景 A · 多源变化进入正式 SyncTask 主线

```text
Source change emitted
   │
   ▼
SyncTask created
   │
   ▼
SyncStatus enters queued/syncing
   │
   ▼
Checkpoint / lag established
```

**开发者关注点**:
- source change 是否都进入正式 SyncTask
- task 与 source refs 是否稳定绑定
- lag/checkpoint 是否可回放与对账

### 8.2 场景 B · 同步结果被稳定分发到 chat / console / runner

```text
SyncStatus updated
   │
   ▼
SurfaceSyncView built
   │
   ▼
chat / console / runner refreshed
   │
   ▼
users see consistent state
```

**开发者关注点**:
- 不同消费面是否看到一致状态
- stale/lag 是否被准确标记
- sync-ready projection 是否仍保持只读边界

### 8.3 场景 C · 冲突、过期和失败进入 replay/resync/repair 主线

```text
Conflict/Stale/Failed detected
          │
          ▼
ConflictView + ResolutionProposal built
          │
          ▼
ReplayRequest / ResyncTicket created
          │
          ▼
operators inspect and repair with evidence
```

**开发者关注点**:
- conflict 是否只是解释层而不冒充 source truth
- replay/resync 是否始终有 ticket 与证据链
- recovery 之后是否仍需重新校验 per-surface 一致性

### 8.4 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| bus / source systems | CreateSyncTask / BindSourceChange | 同步对象识别与任务入口部分 | 形成正式 SyncTask |
| SyncTask + source acks | AdvanceSyncStatus / RecordCheckpoint | 同步编排与状态推进部分 | 形成 SyncStatus / checkpoint / lag |
| stale/divergence/failure | DetectConflict / BuildConflictView | 冲突检测与一致性修复部分 | 形成冲突视图与修复入口 |
| sync delivery targets | BuildSurfaceSyncView / DeliverSurfaceProjection | 跨端分发与消费体验部分 | 形成 per-surface sync views |
| operators / repair requests | TriggerReplay / TriggerResync / CreateRepairEntry | 重试、回放与运维干预部分 | 形成 replay/resync/repair 主线 |

### 10.2 关键读模型说明

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| source refs 缺失 | 拒绝建任务 |
| checkpoint 与 source 结果不一致 | 标记 stale/conflict 并阻断 synced |
| 某消费面 delivery 失败 | 标记 target lag / stale |
| replay/resync 失败 | 保留 recovery record 并允许重试 |
| visibility 规则错误 | 阻断 surface view 输出 |

### 11.1 重试 / 降级 / 熔断 / 补偿
- source event 暂不可得时可 backlog + retry,但不得伪造 SyncTask 完成
- per-surface delivery 失败时可局部重试,但必须显式标记 target lag
- conflict 视图构建失败时可降级为 stale view,但不得宣称已同步

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 同步对象识别与任务入口部分 | source change 丢失 / target surface 非法 | sync intake boundary validate | 拒绝建任务 | 补 source 事件后重试 |
| 同步编排与状态推进部分 | 状态推进与 source ack 错配 | sync status boundary validate | 标记 stale/failed | 重算 checkpoint / replay |
| 冲突检测与一致性修复部分 | conflict 误报 / stale 漏报 | conflict source boundary validate | 重新对账并重建冲突视图 | repair / replay |
| 跨端分发与消费体验部分 | 某消费面显示错误状态或仍 stale | delivery boundary validate | 标记 target lag / 重建视图 | 局部 resync |
| 重试、回放与运维干预部分 | replay/resync 无法追踪或无票据 | replay boundary validate | 阻断恢复动作 | 重建 recovery record |

## 14. 最小可运行闭环

- 一条 source change 被正式识别为 SyncTask,并进入 queued/syncing/synced 主线
- chat、console、runner 至少两个以上消费面看到同一 sync state,且 source refs 可回溯
- 当任务进入 stale/conflict 后,operators 能通过 replay/resync/repair 入口发起修复,同时保留正式 recovery 证据链

## 15. 结论

本详细设计的核心结论是：
- `L5-sync` 的实现主轴必须按 task / status / conflict / delivery / recovery 五个主要部分组织,而不是按重试、冲突页、列表、队列脚本平铺
- sync 真相层只持有同步任务、同步状态、冲突解释、分发视图与恢复票据,不接管 source truth 或 bus truth 本体
- 所有 sync task views、surface views、conflict views、replay/resync/repair 结果都必须建立在稳定 source refs、checkpoint/lag 和 append-only 证据链之上

后续测试与验收文档,应直接围绕这套统一同步体验主链、跨端分发边界、冲突修复与恢复干预主线展开.

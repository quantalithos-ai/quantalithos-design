### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 sync“能跑一个同步任务”,而是系统验证 `L5-sync` 是否真正满足“系统间状态同步与跨端一致性产品层 / sync experience 层”的设计要求,尤其要证明以下几点成立:
- SyncTask / SyncStatus / ConflictView / SurfaceSyncView / ReplayRequest 构成正式同步体验层真相
- `SyncTask ≠ source domain truth`、`SyncStatus ≠ source object state`、`sync pipeline ≠ bus truth`、`ConflictView ≠ source conflict truth` 等核心边界成立
- source change → sync task → status → delivery → recovery 五条同步体验主线可以统一组织,并且 source refs 持续可追溯
- stale / conflict / lag / replay / resync 都有统一状态与修复入口,不会让用户和 operators 误解“已同步/已恢复”
- per-surface sync views 只消费 source results,不反写源真相,并且 chat / console / runner 能看到一致状态
- replay / resync / repair 只重做同步过程,不重做业务裁决或改写 source truth

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 同步对象识别与任务入口部分 | sync intake 对象 | P0 | SyncTask、SyncTarget、SyncScope、SyncAudience、SourceChangeIntake |
| 同步编排与状态推进部分 | sync state 对象 | P0 | SyncStatus、SyncCheckpoint、SyncLagSnapshot、SyncAckRecord、SyncProgressView |
| 冲突检测与一致性修复部分 | conflict/repair 对象 | P0 | ConflictView、DivergenceRecord、StaleMarker、ResolutionProposal、ManualResolveEntry |
| 跨端分发与消费体验部分 | delivery/projection 对象 | P0 | SurfaceSyncView、DeliveryEnvelope、VisibilityFilter、SurfaceSyncSummary |
| 重试、回放与运维干预部分 | replay/recovery 对象 | P0 | ReplayRequest、ResyncTicket、RepairEntry、BacklogInspection、SyncRecoveryRecord |
| source truth 仓、L0-bus transport truth、底层队列/CDC/复制系统本体 | 非范围 | P2 | 只验 sync 如何消费 source changes 并组织一致性体验,不验底层真相和基础设施全部实现 |
| 自动化修复脚本和 source-side 真正业务修复逻辑 | 非范围 | P2 | 只验 sync repair/replay 入口与状态链,不验底层修复脚本全部实现 |
| observability / archive 真相本体 | 非范围 | P2 | 只验 sync 如何输出诊断和恢复证据,不验其他仓全部实现 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数与局部不变量 | domain / product owner | `intake.validate_sync_intake_boundary`、`task.validate_sync_status_boundary`、`input.validate_conflict_source_boundary`、`target.validate_delivery_boundary`、`request.validate_replay_boundary` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + queue + projection + publisher 联动 | backend / product owner | `CreateSyncTask`、`AdvanceSyncStatus`、`DetectConflict`、`BuildSurfaceSyncView`、`TriggerReplay`、`TriggerResync` | task、status、conflict、delivery、recovery 五条主线同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | bus/source → sync task、sync → chat/console/runner、sync → operators / observability | 输入输出语义一致 |
| 恢复专项测试 | 验证 source refs 缺失、lag/stale、delivery fail、conflict 误判、replay 无票据等异常链 | architecture / QA | source gap、checkpoint mismatch、delivery stale、repair fail、resync backlog | 一致性不误导、错误被正确阻断或留证 |
| 投影一致性测试 | 验证 sync task/surface/conflict/backlog 视图与主任务链一致 | backend / QA | task view rebuild、surface view rebuild、conflict view rebuild、backlog view rebuild | 投影只读且与主线一致 |
| 端到端主线测试 | 验证最小同步体验闭环 | QA / owner | source change → task → delivery → stale/conflict → replay/resync | sync 体验闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| `SyncTask ≠ source domain truth` | SyncTask 只表达同步任务,不替代源对象真相 | 单元 + 集成测试 | 是 | task/source compare |
| `SyncStatus ≠ source object state` | 同步状态机只表达同步过程,不等于源状态 | 单元 + 集成测试 | 是 | status/source compare |
| `sync pipeline ≠ bus truth` | sync 只能消费 bus 变化,不替代传递契约层 | 单元 + 事件链测试 | 是 | pipeline/bus compare |
| `ConflictView ≠ source conflict truth` | 冲突视图只做解释与修复入口,不替代源冲突真相 | 单元 + 集成测试 | 是 | conflict/source compare |
| `replay/resync ≠ replay business decision` | replay/resync 只重做同步过程,不重做业务裁决 | 单元 + 恢复测试 | 是 | replay/decision separation |
| `cross-device consistency ≠ single source ownership` | 多端看到同一状态,不代表多端可拥有同一真相 | 单元 + 事件链测试 | 是 | surface/source ownership compare |
| per-surface sync views 一致 | chat/console/runner 同步结果一致可解释 | 集成 + 事件链测试 | 是 | cross-surface compare |
| stale/conflict/lag 可解释 | stale、冲突、滞后原因可被展示和追踪 | 集成 + 恢复测试 | 是 | conflict/lag logs |
| replay/resync/repair 可追溯 | 恢复与修复主线有正式 ticket/history | 集成 + 恢复测试 | 是 | replay/resync/repair history |

## 4. 环境与配置矩阵

| 环境 | 用途 | 依赖 | 关键配置 | 风险 |
|---|---|---|---|---|
| dev | 本地主线验证 | local sync store / fake bus / fake source changes / fake chat-console-runner consumers | debug sync state / stale markers visible / replay enabled | 容易只测 happy path |
| test | CI / 集成测试 | deterministic source events / fake delivery adapters / fake repair queue / fake observability | isolated sync tables / fixed source refs / replay tickets enabled | 多消费面一致性样本不足 |
| staging | 端到端演练 | real-like source refs / sync queue / chat-console-runner surface consumers / operators dry-run | stale/conflict/lag/recovery evidence enabled | 高并发 sync 与多面分发时序差异放大 |

## 6. 核心测试场景

| 场景 ID | 场景 | 前置条件 | 步骤摘要 | 预期结果 |
|---|---|---|---|---|
| TC-001 | CreateSyncTask 成功创建正式同步任务 | source refs / target surfaces / scope 合法 | CreateSyncTask | SyncTask 创建成功 |
| TC-002 | source refs 缺失时阻断 sync task 创建 | source_ref 缺失或非法 | CreateSyncTask | 返回 `SOURCE_REF_INVALID` |
| TC-003 | AdvanceSyncStatus 成功推进同步状态并记录 checkpoint/lag | sync task 已存在 | AdvanceSyncStatus | SyncStatus / SyncCheckpoint / SyncLagSnapshot 创建成功 |
| TC-004 | SyncStatus 不得冒充源对象状态 | source object state 存在 | negative flow | 仅更新 sync status,不改 source truth |
| TC-005 | DetectConflict 成功构建 conflict / stale 视图 | lag / compare 数据存在 | DetectConflict / BuildConflictView | ConflictView / DivergenceRecord / StaleMarker 创建成功 |
| TC-006 | 冲突视图不得替代源冲突真相 | source conflict 存在 | negative flow | 只显示解释层与修复入口 |
| TC-007 | BuildSurfaceSyncView 成功向 chat/console/runner 生成 per-surface sync 视图 | sync task synced or replayed | BuildSurfaceSyncView | SurfaceSyncView 创建成功 |
| TC-008 | 不同消费面必须看到一致且可解释的同步状态 | chat/console/runner 同时消费 | BuildSurfaceSyncView + compare | cross-surface 一致 |
| TC-009 | 某消费面 delivery 失败时正确标记 stale/lag | target surface fail | DeliverSurfaceProjection | 标记 stale / lag,不宣告 synced |
| TC-010 | TriggerReplay / TriggerResync 成功创建恢复入口和票据 | sync task failed/stale/conflict | TriggerReplay / TriggerResync | ReplayRequest / ResyncTicket / RecoveryRecord 创建成功 |
| TC-011 | replay/resync 不得重做业务裁决 | source business decision 存在 | negative flow | 仅重做同步过程 |
| TC-012 | CreateRepairEntry 成功创建人工修复入口 | conflict 存在 | CreateRepairEntry | RepairEntry 创建成功 |
| TC-013 | backlog inspect 成功显示积压与恢复证据 | replay backlog 存在 | InspectBacklog | BacklogInspection 创建成功 |
| TC-014 | replay/resync 失败时保留 recovery history 并允许后续重试 | dispatch fail | TriggerReplay / retry | recovery history 完整且可再次触发 |

## 10. 缺陷管理与异常升级

| 严重级别 | 定义 | 处理要求 |
|---|---|---|
| S | sync 任务或状态反写真相 / conflict 误导为 source truth / per-surface 仍 stale 却整体显示 synced / replay/resync 越权改写真相 |
| A | 主线可跑但 stale/lag、repair 票据、delivery 一致性或 backlog 诊断不稳 |
| B | 非关键视图、低优先级 backlog 展示或趋势异常 |

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 SyncTask / SyncScope / target surfaces,都必须回归任务入口与 source refs 主线
- 每次改动 SyncStatus / checkpoint / lag,都必须回归状态推进与 checkpoint 主线
- 每次改动 conflict/stale/resolution,都必须回归冲突解释与修复入口主线
- 每次改动 per-surface sync views,都必须回归 chat/console/runner 一致性主线
- 每次改动 replay/resync/repair,都必须回归恢复票据、证据链与 source truth 分层主线

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| 多消费面/多租户同步策略后续细化 | 验收矩阵需扩充 | TL / 架构 |
| 冲突合并与人工修复能力继续演进 | conflict/repair 验收需增加更多样本 | sync / ops |
| backlog 与 replay 历史增长 | history/backlog 验收需扩充 | platform / observability |

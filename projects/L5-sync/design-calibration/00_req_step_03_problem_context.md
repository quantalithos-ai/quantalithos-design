## 1. 本步目标

说明为什么平台需要一个受控本地同步入口，区分业务层的治理/协作问题与技术层的状态/边界问题，并把历史材料中的伪量化和方案假设隔离出去。

## 2. 应问的问题与回答

### 2.1 业务背景

Quantalithos 的平台事实和治理流程主要存在于服务侧，但开发者、项目接手人和评审者仍需要在本地 IDE、Git 和文件系统中检查、补充和验证代码类产出。这个本地工作流必须继续服从显式项目/版本选择、权限和 Review Gate，而不能退化为一个脱离平台上下文的普通 Git 目录。

### 2.2 当前主要痛点

1. 用户可能从目录、默认分支、Git remote 或旧缓存猜测项目和版本，导致本地内容与正式 Artifact/Workspace 来源无法解释地绑定。
2. 本地工作树存在未提交修改时，普通拉取/覆盖动作可能破坏用户工作；平台来源变化、路径映射和 metadata 漂移也缺少统一的冲突语义。
3. 本地 Git commit、上传成功或 HTTP/transport ACK 容易被误读为 Artifact/Baseline 已建立或 Review 已接受，造成治理链断裂。
4. 网络中断、进程退出、版本比较缺口和外部结果不确定时，盲目重试可能重复副作用或伪造完成状态。
5. 归档项目、权限撤销、来源失效和 provenance 缺口需要安全停止；本地工具不能凭旧缓存继续执行危险操作。

### 2.3 业务问题与技术问题

| 分类 | 问题定义 | 不在本步解决 |
|---|---|---|
| 业务问题 | 用户需要在平台治理和本地开发效率之间建立可解释的受控桥；本地修改回流必须仍进入正式 Review Gate。 | 不在需求阶段决定具体 Gate 协议或批准规则。 |
| 业务问题 | 项目/版本/来源选择必须由用户显式确认，且权限、归档姿态和 provenance 不能被本地工具猜测。 | 不由 Sync 创建 Project、Artifact 或授权结论。 |
| 技术问题 | 平台 source cursor、local applied cursor、Git HEAD/working tree、handoff ACK 和 Review decision 需要分层表示。 | 不在本步定义 schema、状态枚举或数据库。 |
| 技术问题 | 增量更新、映射、冲突、断点恢复和 unknown outcome 需要可重入且不覆盖 dirty worktree 的行为边界。 | 不在本步选择 Git 库、文件格式或重试算法。 |
| 技术问题 | SDK、Artifact/Workspace、Governance、Archive 与 Git/filesystem 的 seam 尚未完全闭合。 | 具体接口后置到 01~04，未闭合项保留 blocker。 |

## 4. 结构化问题结论

L5-sync 要解决的核心问题不是“重新实现 Git”，而是让本地工作区操作具有可验证的项目/版本/来源语境、权限门禁、用户修改保护、可分层的同步结果和 Review handoff 溯源。所有无法由当前 owner 合同证明的内容必须进入 blocked/pending，不得通过缓存、fake、日志或 ACK 补齐。

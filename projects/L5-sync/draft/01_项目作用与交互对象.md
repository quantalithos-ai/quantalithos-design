# 01 · L5-sync 项目作用与交互对象（draft）

> 状态：`draft / pre-calibration`，非正式设计真相源
> 本文不是 `00~07` 正式文档、协议、实现、测试或 readiness 证据。旧 README 与旧正式文档仅作为 `historical_material`。
> 本文目的：在进入正式校准前，先固定 L5-sync 的责任边界、交互对象和待核验问题；任何未有当前上游合同支持的名称、字段和协议均保持候选状态。

## 1. 一句话定位

`L5-sync` 是平台与本地开发工作区之间的**受控同步入口**：它把经过身份、项目/版本、来源和权限校验的本地 working copy 操作，连接到平台 Artifact/Workspace 的正式读取面和 Review handoff 面，并维护一次同步操作所需的本地 session、游标、映射、冲突、恢复和 provenance 关联状态。

它回答的是：“这个 principal 在明确选择的 project/version/source 下，能否安全地把本地工作副本初始化、更新、检查并准备交给正式 Review Gate？”它不回答项目事实、Artifact 事实、基线事实、治理决定、Workspace projection、归档状态或 Git remote 的真相。

### 1.1 为什么必须单独存在

| 易混淆对象 | L5-sync 的边界结论 |
|---|---|
| `L0-sdk` | SDK 是正式平台访问入口和客户端封装；Sync 可以依赖其已闭合的访问面，但不能重定义 SDK 服务合同、错误语义或 owner。 |
| `L1-identity` | identity 提供 principal、认证和身份生命周期；Sync 只消费调用语境与授权输入，不拥有身份或 credential truth。 |
| `L1-work` | work 拥有 `Project`、`ProjectMember`、项目姿态和工作事实；Sync 只读取显式项目选择及允许操作的语境，不创建、修改或复制项目事实。 |
| `L1-governance` | governance 拥有 Review Gate、Decision、Policy 和审批/拒绝结论；Sync 只能准备并提交 review handoff，不能批准、接受、绕过或解释 Gate。 |
| `L1-artifact` | artifact 拥有 Artifact 正文、版本、血缘和 Baseline；Sync 读取可消费的来源绑定并提交候选材料，不能把本地文件或 Git commit提升为 Artifact/Baseline。 |
| `L1-workspace` | workspace 提供经过授权的 Workspace projection/read binding（若正式合同允许）；Sync 的本地 working copy、cursor 和 metadata 不是 Workspace projection。 |
| `L4-archive` | archive 拥有归档/恢复事实；Sync 只读取归档项目姿态和允许的来源/操作提示，不能归档、恢复或拥有 archive truth。 |
| `L4-observability` | observability 提供关联、诊断和安全审计输入；Sync 的命令结果不能仅凭日志或 trace 推导业务成功、Review accepted 或 signoff。 |
| Git CLI/library 与 filesystem | 提供本地工作树、索引、HEAD、文件状态和工具适配 seam；Git remote、远端分支和平台事实不归 Sync。 |
| `L5-chat` / `L5-console` / 其他产品 | 可能消费同步状态或 handoff 结果，但 Sync 不维护跨产品投影、不接管 bus delivery/replay，也不成为统一跨端一致性中心。 |

### 1.2 明确否定的扩张定位

历史材料曾把 sync 叙述成跨 chat、console、runner 的系统间状态同步器，或拥有统一 `SyncTask`、全平台 replay/resync 和跨端一致性 truth。这些说法不属于当前 draft 结论：

- 一次 `sync session/status/conflict` 只描述本地受控同步操作，不是平台业务生命周期。
- Sync 不维护 Workspace read model，不编排 L0-bus delivery/replay，不替代任何来源域的投影 owner。
- Sync 不把本地 commit、上传 ACK 或命令退出码解释成 Artifact、Baseline、Review decision 或 acceptance。

## 2. 本仓拥有 / 只消费 / 禁止拥有（候选）

| 主题 | L5-sync 可拥有的局部状态 | 只消费/回链 | 明确禁止拥有 |
|---|---|---|---|
| 同步会话 | 本地 `sync session` 的尝试、阶段、幂等键、恢复点和安全诊断关联。 | 平台请求/响应的 correlation 与 source ref。 | Project、Artifact、Review 或平台全局任务生命周期。 |
| working copy | 本地目标路径绑定、已识别的 Git/filesystem 状态、受控 materialization 记录。 | Artifact/Workspace 提供的正式来源引用和版本语境。 | Workspace projection、Artifact 正文版本链或 Git remote truth。 |
| 游标与映射 | source cursor、local applied cursor、source-to-local mapping、generation/coverage 关联。 | owner 给出的版本、来源水位和可重取提示。 | 全局事件 delivery cursor、Artifact/Baseline version authority。 |
| 冲突与恢复 | 未提交修改保护结果、冲突记录、恢复 checkpoint、unknown outcome probe 记录。 | Git/filesystem 观察结果和外部调用的可探测状态。 | 自动 merge/rebase/push、强行覆盖用户改动、伪造恢复完成。 |
| provenance | 来源、版本、调用、materialization 和 handoff 的本地关联元数据。 | identity/project/artifact/workspace/review 的正式 ref。 | 删除、篡改或伪造上游 provenance；把本地 metadata 当平台 provenance owner。 |
| review handoff | 待提交候选的本地冻结/准备状态、提交尝试与返回的外部 ref。 | Governance/Review Gate 的正式创建、接收和决定。 | Review verdict、accepted、signoff、Baseline 或“上传即通过”。 |
| 归档姿态 | 对当前项目/来源可执行性的本地缓存状态（须可回查）。 | `L4-archive` 的归档、恢复、dissolved/retired posture。 | Archive record、恢复操作或归档生命周期。 |

本表中的“拥有”只表示 Sync-local truth；它不转移任何上游 authority，也不预先决定最终对象名、数据库形态或协议。

## 4. 交互对象与允许方向

### 4.1 平台真相域

| 对象 | Sync 允许做什么 | Sync 不得做什么 |
|---|---|---|
| principal / identity | 传递请求主体、检查认证上下文和关联信息；在失败时安全停止。 | 自己认证、发 token、创建成员、解释授权默认值。 |
| Project / ProjectMember | 要求用户显式选择项目并读取正式项目/成员姿态与操作许可。 | 猜测默认项目、创建/修改成员、以 local metadata 伪造项目归属。 |
| Artifact / version / Baseline | 读取可 materialize 的来源与版本绑定；提交候选的来源回链。 | 上传本地文件即创建 Artifact；本地 commit 即 Baseline；复制/改写版本链。 |
| Review Gate / Decision | 发起正式 handoff、查询外部接收/决定状态并回链 ref。 | 自动接受、批准、关闭、绕过 Gate；把 ACK/HTTP 200 当 verdict。 |
| Workspace projection | 在正式绑定允许时读取可消费的投影/来源摘要。 | 把本地 working copy 当 Workspace projection；写回 projection 或接管其 owner。 |
| Archive posture | 查询 archived/retired/dissolved 等姿态及允许动作。 | 归档、恢复、伪造未归档状态或继续执行被禁止的写入。 |

### 4.2 本地事实 seam

| seam | 可观察内容 | 安全纪律 |
|---|---|---|
| Git adapter | HEAD、index、working tree dirty 状态、分支/对象存在性、工具版本和受支持命令结果。 | 不自动 merge/rebase/push；不把 commit hash当 Artifact/Baseline。 |
| filesystem adapter | 目标路径、文件指纹、`.qs-sync` 受控 metadata、锁和原子写入能力。 | 先检查路径、权限、未提交修改和 provenance，再 materialize；不覆盖用户修改。 |
| platform SDK adapter | 正式 query、source fetch、handoff、status/probe 的返回和错误。 | 未闭合的接口保持 blocked；不在 adapter 内补造 owner 事实。 |
| observability adapter | trace/correlation、安全诊断和操作审计材料。 | 诊断记录不能改变业务状态或证明 review accepted。 |

## 5. 核心操作闭环（讨论方向）

以下闭环只描述能力方向，具体命令、参数和状态码留给正式 Step 5 以后：

1. **显式选择**：用户明确给出 project、version/source 和本地目标；Sync 通过 identity/work/来源 seam 校验 principal、项目姿态和访问权限。
2. **绑定与初始化**：建立本地 working-copy binding，写入受控 provenance metadata，并记录平台来源 cursor/version；初始化不得静默覆盖既有目录。
3. **观察与增量拉取**：`status` 只观察；`pull` 先检查 dirty/untracked/metadata 完整性，再按可验证 cursor 增量 materialize。无安全边界时停在 blocked/needs-action。
4. **冲突与恢复**：冲突由本地状态与来源变化的可解释比较产生；用户做决定。Sync 可保存 checkpoint、重试安全步骤和 probe unknown outcome，但不自动 merge/rebase。
5. **review handoff**：`push-review` 只准备、冻结并交给正式 Review Gate；上传/提交 ACK、远端对象存在或 transport 成功均不等于 accepted。
6. **归档与溯源**：归档姿态变化必须重新查询并限制操作；每个 materialization/handoff 都保留可回链 provenance，不得静默删除或伪造。

## 6. 本地 Git、平台来源与 provenance 分界

```text
platform source/version ----(formal binding)----> sync local metadata
          |                                           |
          |                                           +--> working copy / cursor / mapping
          |                                           +--> conflict / recovery / handoff attempt
          v
 Artifact / Workspace / Review Gate truth       Git HEAD/index/tree
          |                                           |
          +---------- no authority transfer ----------+
```

需要同时记录、但不得混为一谈的状态至少包括：platform source cursor、local applied cursor、Git HEAD/commit、working-tree clean/dirty、handoff attempt、transport acknowledgement、Review Gate decision。任何状态缺失或来源不明都应降低结果等级，而不是默认成功。

## 7. 历史材料污染审计（候选）

| 历史说法/选择 | 当前 draft 处置 |
|---|---|
| 跨 chat/console/runner 的统一同步器、`SyncTask` 和全平台 replay/resync | 降为 `historical_material`；不作为 L5-sync 主责或正式边界。 |
| 固定 `.qs-sync/metadata.json` 单文件形态 | 仅保留“受控 `.qs-sync` metadata”方向；目录、分片、schema、迁移和完整性待正式校准。 |
| Rust CLI + Tauri GUI | 不确认当前实现或产品授权；CLI/GUI 形态留待需求与实现边界核验。 |
| Git LFS、浅克隆 | 历史候选；是否支持、限制和失败姿态须按当前 Artifact/Git 上游合同重核。 |
| 99.9% 可用性、固定吞吐/延迟数字 | 删除为当前承诺；待正式需求、证据和运行边界支持。 |
| ArtifactService/WorkService/GovernanceService 固定旧 RPC 名称 | 仅作历史线索；不得假定当前 SDK 接口存在。 |
| “永久不可删除 metadata”绝对表述 | 收敛为 provenance 不得被静默删除或伪造；合法迁移、失效和保留策略待正式合同。 |
| 自动 merge/rebase/push 或上传即 review accepted | 明确禁止。 |

## 8. 上游 pending / blocker 候选

以下编号是草稿候选，不是正式 blocker ID：

| 候选 | 未闭合边界 | 当前上限 |
|---|---|---|
| `SYNC-UP-001` | L0-sdk 是否提供精确的 project/version/source/artifact/workspace/review-handoff query 与错误语义。 | 只能定义 adapter 方向，不能锁 RPC/API。 |
| `SYNC-UP-002` | Artifact 与 Workspace 哪一方提供 clone/pull materialization 输入、绑定优先级与版本比较。 | 不能假定来源或全局快照。 |
| `SYNC-UP-003` | Project archived/dissolved/retired posture、权限检查和允许操作矩阵。 | 归档姿态只能 fail-closed。 |
| `SYNC-UP-004` | Review Gate 创建、候选上传、接收 ACK、状态查询和 decision ref 的精确协议。 | handoff 与 accepted 必须分离。 |
| `SYNC-UP-005` | unknown outcome 的 probe、幂等键、重试与终态合同。 | 不得重复副作用或伪造完成。 |
| `SYNC-UP-006` | `.qs-sync` metadata 目录/schema/迁移/完整性/恢复和 provenance 保留规则。 | 只保留受控 metadata 方向。 |
| `SYNC-UP-007` | Git remote、平台 material source、分支/对象存在性的关系与适配边界。 | 不把 remote truth 纳入 Sync。 |
| `SYNC-UP-008` | 增量 cursor、版本 comparator、gap/replay 和跨版本兼容。 | 无可验证 comparator 时 blocked。 |
| `SYNC-UP-009` | Git LFS、浅克隆、GUI 等历史选择的当前支持矩阵。 | 均 pending，不作方案承诺。 |
| `SYNC-UP-010` | 用户未提交修改检测、路径保护、非覆盖和人工冲突决策合同。 | 任何不确定均停止 materialize。 |

## 9. 本篇结论

本 draft 将 L5-sync 收敛为“平台来源与本地 working copy 之间的受控同步入口”，并把 session、metadata、cursor、mapping、conflict、recovery、handoff 和 provenance 限定为 Sync-local 责任。Project、Artifact、Baseline、Review Gate、Workspace projection、Archive、Git remote 和身份授权均保持外部 owner。下一步只有在用户明确要求后，才进入正式 `00` 的需求校准；本篇不表示实现、测试、集成、review verdict 或 readiness 已存在。

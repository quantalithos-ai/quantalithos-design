# 02 · L5-sync 功能推演（draft）

> 状态：`draft / pre-calibration`，非正式设计真相源
> 前置：`draft/01_项目作用与交互对象.md`。本文只推演能力闭环，不替代正式 `00~07`，不锁定 CLI 参数、RPC、事件、schema、模块名、性能数字或实现结果。

## 1. 功能边界原则

L5-sync 的每个能力都必须同时满足四个条件：

1. 有明确的 principal、project、version/source 和本地目标语境；
2. 只操作 Sync-owned local state，或通过正式 seam 请求 owner 能力；
3. 能区分来源版本、Git/文件系统状态、传输 ACK 和 Review decision；
4. 在权限、来源、metadata、冲突或结果不确定时安全停止，而不是猜测或覆盖。

`clone`、`pull`、`status`、`push-review` 是用户可见操作方向；其精确命令合同留待正式 Step 5 以后。

## 2. 候选能力闭环

### C-SYNC-1：显式选择、权限与来源绑定

**意图**：让一次同步操作有可验证的 project/version/source 选择，而不是从目录、分支或缓存猜测上下文。

**候选流程**：

1. 接收 principal、明确 project ref、version/source ref、本地目标路径和操作意图。
2. 经 L0-sdk/identity/work seam 检查认证、项目成员/权限、项目姿态和允许动作。
3. 经 Artifact/Workspace seam 确认 material source、版本语境和来源优先级。
4. 创建 Sync-local session/binding，记录来源与 provenance；任何缺失或冲突均返回 blocked/needs-action。

**禁止**：自动选项目或版本、把 Git remote 默认分支当平台 source、绕过权限、以旧 metadata 继续执行已失效绑定。

### C-SYNC-2：working copy 初始化与 `.qs-sync` 受控 metadata

**意图**：把平台来源安全地绑定到本地目录，并可在后续 status/pull/recovery 中解释。

**候选内容**：目标路径 identity、source/project/version ref、metadata generation、applied cursor、mapping、provenance、工具能力和恢复关联。

**安全规则**：

- 先检测目标路径、锁、Git/filesystem 能力、未提交/未跟踪修改和现有 metadata；不能静默初始化或覆盖。
- metadata 的具体目录布局、文件拆分、schema、迁移、完整性和保留规则均 pending。
- provenance metadata 不得被静默删除、伪造或与另一 source 重绑定；合法迁移必须有可解释记录。

### C-SYNC-3：只读 status 与增量 pull

**status** 只观察并报告：来源绑定、平台/本地 cursor、Git HEAD/index/tree、dirty/untracked 状态、metadata 健康、冲突、恢复和 handoff 状态。它不得隐式 refresh、推进 cursor、写入业务状态或修复冲突。

**pull** 的候选顺序：读取并验证 binding → 观察本地改动 → 获取可验证增量/来源版本 → 比较 cursor 与 mapping → 预览/阻止冲突 → 原子 materialize → 记录新 cursor、provenance 和结果。

若目标目录有用户未提交修改、来源 comparator 未闭合、metadata 损坏或外部结果不明，必须停止或要求明确人工动作；不得覆盖、自动 stash、自动 merge/rebase。

### C-SYNC-4：冲突检测与人工决策

冲突至少包括：来源版本与本地 applied cursor 分叉、同一映射目标的本地修改与来源更新、删除/重命名碰撞、metadata/provenance 不一致、权限/归档姿态变化和外部 handoff 状态不明。

Sync 可以：保存冲突快照/摘要、标识受影响路径和 source ref、提供恢复点、等待用户决策、在决策后重新验证。Sync 不可以：自动 merge、自动 rebase、自动 push、覆盖 dirty 文件、删除冲突证据或把“无冲突”推断成 review accepted。

### C-SYNC-5：`push-review` 与 Review handoff

**意图**：把用户明确准备的本地候选交给正式 Review Gate，而不是把本地 Git 工作流变成平台接受流程。

候选阶段：检查来源/权限/归档姿态 → 确认工作树与 metadata 状态 → 形成可回链的候选快照或上传材料 → 调用正式 handoff → 持久化外部 handoff ref、transport outcome 和下一步查询提示。

必须区分：

| 状态 | 含义 | 不能推导 |
|---|---|---|
| 本地准备/冻结 | 本地候选在某个 revision 下被记录 | Artifact/Baseline 已创建 |
| 上传/提交 ACK | transport 或接收端确认收到请求/材料 | Review accepted、批准、signoff |
| remote/object 可探测 | 某个外部对象或请求可被查询 | Gate decision 已完成 |
| Review decision | Governance owner 的正式决定/ref | 本地工作树必然更新或可自动推送 |

任何自动 push、自动批准、ACK-as-accept 或绕过 Gate 都是硬禁止。

### C-SYNC-6：断点恢复、幂等与 unknown outcome

每个可能产生外部副作用的阶段都应有本地 attempt/idempotency/probe 关联（精确 schema pending）：prepare → call → probe/finalize。网络中断、进程退出或响应丢失时先 probe 外部状态，再决定 retry；不能盲目重放可能有副作用的请求。

恢复必须保持 source binding、provenance、用户改动保护和 cursor 分离。相同输入重试应产生可解释的幂等结果；无法证明等价时升级为 blocked/needs-action。

## 3. 候选功能需求族（非正式编号）

| 候选族 | 能力 | 主要边界 |
|---|---|---|
| `FR-SYNC-SEL` | 显式 project/version/source 选择与权限/姿态检查 | 不猜测上下文、不本地授权 |
| `FR-SYNC-INIT` | working copy 绑定、metadata 初始化/迁移、provenance 记录 | 不覆盖用户改动、不伪造来源 |
| `FR-SYNC-OBS` | status、Git/filesystem 观察、metadata 健康和安全诊断 | query/status 不推进状态 |
| `FR-SYNC-PULL` | 可验证的增量获取、映射、materialize 与 cursor 记录 | 不自动 merge/rebase，不绕过冲突 |
| `FR-SYNC-CONFLICT` | 冲突检测、分类、快照、人工决策等待和恢复点 | 不自动解决、不删除证据 |
| `FR-SYNC-HANDOFF` | push-review 准备、冻结、上传/提交和外部状态回链 | ACK 不等于 accepted，不拥有 Gate |
| `FR-SYNC-RECOVERY` | checkpoint、幂等、probe、重试和中断恢复 | unknown outcome 不盲重放 |
| `FR-SYNC-PROV` | source/version/path/tool/handoff 的 provenance 关联 | 不删除/伪造上游 provenance |
| `FR-SYNC-ARCHIVE` | 归档项目姿态读取、操作裁剪和失效处理 | 不拥有 archive truth |

这些编号只用于本 draft 讨论，正式需求编号须在 Step 00/01 重新生成。

## 4. 状态与结果分离（候选）

```text
source binding      ──> local applied cursor ──> materialization result
       │                         │                         │
       v                         v                         v
permission/posture   Git HEAD/index/tree          local provenance/revision
       │                         │                         │
       +-------------------------+-------------------------+
                                 v
                         review handoff attempt
                                 │
             transport ACK ------+------ Review decision (external)
```

建议后续正式设计显式区分下列状态组：

| 状态组 | 示例语义 | 所属 |
|---|---|---|
| selection/access | unresolved / verified / denied / archived / stale | Sync-local 对外部结论的绑定 |
| materialization | absent / preparing / applied / partial / blocked | Sync-local working-copy 操作 |
| local change | clean / dirty / untracked / conflicted / unknown | Git/filesystem observation |
| source cursor | unset / advancing / gap / applied / invalid | Sync-local source application |
| handoff | not-prepared / prepared / submitted / transport-unknown / probe-required | Sync-local attempt |
| review | not-known / pending-external / accepted / rejected（仅外部 ref 的读取） | Governance owner；Sync 不产生 verdict |
| archive posture | active / archived / dissolved / unknown | Archive/work owner；Sync 只消费 |

具体状态枚举、转换和持久化字段必须在正式 Step 5+ 以当前上游合同为依据，不由本 draft 锁定。

## 5. 配置与工具适配方向（候选）

可能需要配置的主题：平台 endpoint/profile、principal 认证来源、默认禁止项、目标路径与锁策略、source/version 选择策略、metadata 目录策略、Git/filesystem 工具探测、增量/恢复重试、日志关联、LFS/shallow/GUI 能力开关。

当前只确认：配置不能默认启用自动 merge/rebase/push；不能把旧的 LFS、浅克隆或 GUI 选择写成当前承诺；敏感 credential 不得进入 `.qs-sync` provenance。精确 key、默认值、优先级和错误处理后置到正式设计。

## 6. 测试切口和证据边界（候选）

后续正式设计应分别覆盖：

- 显式选择、权限拒绝、项目归档姿态和来源绑定失败；
- 目标路径 dirty/untracked、metadata 缺失/损坏/迁移、provenance 完整性；
- 增量 cursor、重复/乱序/缺口、映射和原子 materialization；
- 冲突分类、人工决策、不得覆盖和恢复 checkpoint；
- Git adapter 的命令白名单与 merge/rebase/push 禁止；
- handoff ACK、unknown outcome、probe、幂等重试与 Review decision 分离；
- LFS、浅克隆、GUI 等待核验项的显式 blocked/unsupported 姿态；
- 归档/撤销/权限变化后的 fail-closed 与 provenance 保全。

测试 double、模拟 ACK 或 fake SDK 只能证明 Sync-local 行为；不能证明真实 Artifact、Review Gate、Git remote、archive 或上游集成已完成。

## 7. 上游 pending / blocker 候选

| 候选 | 需要核验的功能合同 | 未闭合时的功能上限 |
|---|---|---|
| `SYNC-FN-UP-001` | project/version/artifact/workspace source 的选择与比较 | 只能记录候选绑定，不能安全 pull/clone |
| `SYNC-FN-UP-002` | 权限、归档 posture 和允许操作矩阵 | fail-closed，不得继续写入 |
| `SYNC-FN-UP-003` | handoff/upload/probe/idempotency 协议 | 只能准备本地材料，不得宣称提交完成 |
| `SYNC-FN-UP-004` | source cursor、增量、replay/gap 与版本兼容 | 只能 full-stop 或人工重建 |
| `SYNC-FN-UP-005` | metadata schema/迁移/完整性与 provenance 规则 | 不能初始化或修复不明 metadata |
| `SYNC-FN-UP-006` | Git/filesystem 支持矩阵（含 LFS/浅克隆/GUI） | 标记 unsupported/pending，不自动降级 |

## 8. 本篇结论

功能推演形成了从显式选择到初始化、status/pull、冲突、push-review、恢复和溯源的闭环，但所有跨域协议与精确接口仍待正式校准。Sync 的成功必须是分层、可回链、可探测的局部结果；任何外部真相和 Review verdict 都不能由本地命令推导。

## 2. 背景与问题定义

### 2.1 业务背景

Quantalithos 需要一个完全独立于运行时系统的对外入口,让外部访客在不登录、不接入 Server 的情况下理解“这是什么产品、适合谁、和现有 AI 编程工具有什么不同、怎么开始用”。同时,随着 SDK、产品说明、迁移指南、FAQ、博客与版本更新不断增长,平台还需要一个可控的公开文档站与品牌站来承接搜索流量、注册导流与版本化公开文档。L5-website 因此既是**营销站**,也是**公开文档站**,但它不是应用本体,必须与 Chat/Console 等登录后产品明确分工。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 3 当前) | 痛点 |
|---|---|---|
| 仓文档 | 只有 README 骨架 | 段 3 最后一批端侧收口样板尚未建立 |
| 产品叙事 | `product/最终目的.md` 与 `产品矩阵.md` 已完整 | 对外站点如何结构化呈现尚未仓级化 |
| 公共文档 | design 仓与 sdk 草案已存在大量公开内容 | 文档同步、版本对应与公开边界未正式化 |
| 站点定位 | README 已明确静态站点、完全独立部署 | 信息架构、引流边界与“刻意不做”口径未落需求 |
| SEO/多语言 | README 已列开放问题 | 还未形成产品级约束 |

### 2.3 为什么要做(量化依据)

- `product/产品矩阵.md` 已把 Website 定义为 **④ 独立产品**
- README 已明确 `WB1~WB5` 维护纪律,包括 WCAG、GDPR、文档版本对应与每个产品页“刻意不做”段落
- 若没有 Website,外部访客只能直接面对 Chat/Console 等应用入口,难以完成品牌认知、产品理解与自助上手
- SDK、FAQ、迁移指南、Release Notes 等公开内容需要统一对外分发面,否则文档会散落在 design 仓与内部说明中

### 2.4 业务问题 vs 技术问题

- **业务问题**:外部访客如何快速理解 Quantalithos 是什么、适合谁、如何开始、哪些事情它刻意不做
- **技术问题**:静态站点生成、公开文档同步、Server/SDK 版本对应、SEO、无障碍、Cookie/追踪同意、多语言与搜索索引

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 外部访客打开首页理解产品定位并选择下一步
2. 访客进入产品页了解 10 产品及其“刻意不做”
3. 用户进入 docs 查 quickstart / API / FAQ / migration guides
4. 用户通过登录/注册入口跳转到应用产品
5. 内容维护者同步 design 仓公开文档与 SDK API reference

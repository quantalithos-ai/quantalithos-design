## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L5-website` 不是 `console` 工作台仓,也不是 `chat` 交互仓,更不是文档源仓。它是 **“平台外部门户 / 品牌与公开入口产品层”**。

你可以把它理解成:
- 外部访问者第一次接触 Quantalithos 时看到什么
- 产品介绍、能力概览、方法论入口、案例、文档入口、试用入口怎样被统一组织
- website 怎样承载品牌、平台定位、公开资源和转化路径
- 哪些公开内容只是摘要、哪些只是入口、哪些会把访问者继续引导到 console、chat、marketplace 或文档面

这些事情,都由 `L5-website` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L5-website`,这些对外门户事实就会散落在:
- `console` / `chat` 直接暴露出来的内部入口里
- `marketplace` 的局部 listing 页面里
- `method-library` / `capability-hub` 的内部文档或 JSON 输出里
- 各种 landing、FAQ、文档首页、案例页、活动页和跳转页里
- 运营、产品、增长团队各自写的临时页面和脚本里

结果就会出现:
- 平台对外第一印象不统一
- 公共能力介绍、方法体系概览、生态入口和登录入口彼此割裂
- 官网看起来像多个孤立页面,而不是一个统一门户
- 转化漏斗、试用入口、文档导览、marketplace teaser 各自一套口径
- 用户在正式进入产品前,无法建立稳定的“平台是什么”心智

所以 `L5-website` 必须独立存在,作为:
> **把平台品牌、公开能力、方法概览、生态入口和产品转化路径组织成统一对外门户的产品层。**

### 1.3 新人最容易混淆的几个词

#### WebsitePage
就是:
> 对外公开可访问的一类页面或页面视图。

它不是任何 source system 的正式真相本体。

#### PublicCapabilitySummary
就是:
> 对某类能力的公开摘要说明。

它不是 capability-hub 的 capability contract truth。

#### MethodOverview
就是:
> 对方法体系的公开概览、说明和入口。

它不是 method-library 的权威定义真相。

#### CTA
就是:
> 试用、注册、登录、查看演示、继续阅读等转化或导流入口。

它不是 member/account truth,也不等于用户已经真正进入产品。

#### MarketplaceTeaser
就是:
> 官网上对插件、资产、生态的公开摘要展示。

它不是 marketplace 的交易真相本体。

#### PublicDocsNavigation
就是:
> 官网中对文档、指南、FAQ、release notes 的统一导览入口。

它不是 docs source truth 本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L5-website/02` 时,先收稳以下前提:
- `L5-website` 不应按首页 / 产品页 / 定价页 / 文档页等页面导航树平铺理解,而应按对外门户产品主链责任拆
- website 至少应拆成“门户入口与品牌表达 / 产品能力与方法概览展示 / 转化入口与产品导流 / 生态、案例与公开资源 / 反馈、增长分析与站点运营”五个主要部分
- website 自己拥有的真相不是 console/chat/marketplace/method-library/capability-hub 的源真相,而是 page UX、public summaries、CTA、resource navigation、growth surface 这类门户层真相
- `L5-website` 只能为外部访问者提供公开认知与转化入口,不能反过来替内部系统持有正式领域真相
- 02 的重点不是“列有哪些页面路由”,而是先把“website 门户层在平台里到底是什么、和 console/chat/marketplace/method-library/capability-hub 怎么分层”讲清楚
- hero、product pillars、docs navigation、teasers、trial CTA、campaign surfaces 这些不是零散内容块,而是公开门户主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的对外门户与品牌入口心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,用户第一次接触平台时看到的不是内部系统,而是官网和公开入口。用户真正需要的不是“知道系统里有什么仓”,而是:
- 快速理解 Quantalithos 是什么、能做什么、适合谁
- 看到平台能力、方法体系、生态入口和案例材料的统一说明
- 明确下一步是去试用、注册、登录、读文档还是看生态
- 在进入 console/chat/marketplace 前建立清晰的产品心智

如果把这些逻辑分别散落到:
- 内部工作台入口
- marketplace listing 页面
- method-library / capability-hub 的内部定义输出
- 各种临时 landing、FAQ、活动页和营销页

系统会快速退化成:
- 对外品牌和产品定位不一致
- 官网是多个页面集合,不是统一门户
- 公共能力说明、文档导览、转化入口和生态展示彼此脱节
- 访客不知道应该从哪里进入平台,或为什么进入平台

因此,本概要设计的任务就是:
> **把 `L5-website` 写成一个新人也能看懂的“平台外部门户 / 品牌与公开入口产品层”,而不是把若干公开页面放在同一个域名下。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 对外认知统一性 | 多处页面和文案易分散 | 单一门户主线 | 需正式收敛 |
| 能力/方法概览清晰度 | 依赖内部材料改写 | 统一 public summaries | 需建立公开认知面 |
| 转化路径清晰度 | 入口易分散 | 明确 CTA 漏斗 | 需形成导流主线 |
| 生态/资源展示 | 分散 | 统一公开资源面 | 需正式组织 |
| 站点运营可观测性 | 各页面各自处理 | 统一 growth surface | 需收稳运营主线 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把品牌、产品认知、公开能力、方法概览、资源导览和转化入口组织成统一对外门户,让访问者顺畅理解并进入平台
- **技术问题**:WebsitePage、PublicCapabilitySummary、MethodOverview、CTA、MarketplaceTeaser、PublicDocsNavigation 与 console / chat / marketplace / method-library / capability-hub 之间的边界如何稳定建模,并形成统一门户主链

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 website 的门户职责 | brand / summary / CTA / resource / growth 职责无歧义 | 文档评审 |
| 明确与 console / chat / marketplace / method-library / capability-hub 边界 | public page 与 source truth 分离 | 文档评审 + 后续测试 |
| 明确访客可理解的公开主线 | 认知、导流、资源、生态在同一心智下成立 | 设计评审 + 集成测试 |
| 支撑后续详细设计与测试 | 本文足以承接 `03-详细设计.md` 的 public UX、CTA、resource navigation 设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文替代 console / chat / marketplace 的 source truth
- 不在本文替代 method-library / capability-hub 的权威定义真相
- 不在本文替代 docs source truth 或知识仓本体
- 不在本文替代 account/member 真相或试用系统本体
- 不在本文定义全部增长分析和广告投放逻辑

## 4. 约束条件

### 4.1 技术约束

- 所有 public summaries、teasers、CTA、docs 导览都必须能回指 source refs
- website 只能消费 source systems 的公开摘要,不能反写源真相
- CTA 入口不能伪装成用户已经进入产品
- docs / learn / FAQ 的导览只能做入口层,不能冒充 docs source truth
- campaign / growth surfaces 必须和产品/品牌真相分层表达

### 4.2 资源约束

- 多页面/多 campaign/多入口会持续增长,导航和内容结构复杂度必须受控
- public summaries 与 teaser 渲染不能拖垮 source systems
- 公开资源卡、案例卡、FAQ 卡和 CTA 入口不能无限长胖

### 4.3 时间约束

- 当前阶段先收稳门户主线,而不是先做复杂 CMS、自助运营平台或高级增长实验系统
- brand、capability/method overview、CTA、resource navigation、growth surface 五条基础链必须优先稳定,否则官网会长期碎裂

### 4.4 合规约束

- public page 不得泄露未授权内部信息
- CTA 不得误导用户进入不存在或未开放的入口
- marketplace teaser 不得冒充正式交易与 listing 真相
- docs 导览不得覆盖或篡改正式文档来源

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| public pages | 中高 | 官网、案例、FAQ、活动、入口页 |
| CTA / conversion entries | 高频 | 试用/登录/导流需求 |
| public summaries / teasers | 高频 | 能力与生态展示需求 |
| campaign surfaces | 中高 | 运营增长活动需求 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ method / hub / marketplace │
                    │ console / chat / docs       │
                    │ - public summaries / refs   │
                    └────────────┬───────────────┘
                                 │ website input
                                 ▼
                    ┌────────────────────────────┐
                    │ L5-website                 │
                    │ - landing / public overview│
                    │ - CTA / teaser / docs nav  │
                    └────────────┬───────────────┘
                                 │ public portal output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ visitors / prospects       │   │ growth / campaign surface  │   │ product entry points       │
│ - understand / enter       │   │ - funnel / analytics       │   │ - console/chat/marketplace │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L5-website` 自己负责门户入口、品牌表达、能力和方法概览、资源导览、CTA 和增长运营面
- `method-library`、`capability-hub`、`marketplace`、`console`、`chat` 提供对外可消费的摘要和入口引用,但 website 不拥有它们的源真相
- 访客、潜在用户和运营面通过 website 消费统一公开门户体验,而不是直接理解内部系统结构
- website 的角色不是“平台内部工作台”,而是“平台对外认知和转化入口”

所以 `L5-website` 在全局里的角色是:
> **把品牌、公开能力、方法概览、生态入口和产品转化路径统一组织成平台对外门户。**

### 5.3 系统边界

**做什么**:
- 管理 landing / product overview / public navigation
- 管理 capability summary / method overview / use case / architecture highlight 展示
- 管理 CTA / login / signup / demo / get-started 导流入口
- 管理 teaser / case studies / FAQ / docs/learn/blog 导览
- 管理 feedback / campaign / conversion surface

**不做什么**:
- 不持有 console / chat / marketplace 的 source truth
- 不持有 method-library / capability-hub 的权威定义真相
- 不替代 docs source truth、本地 CMS、本地 analytics 平台或成员/账号真相

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| method-library / capability-hub / marketplace public summaries | 99.9% | 摘要缺失时展示降级占位和静态说明,不伪造内容 |
| console / chat / signup / login entries | 99.9% | 入口不可用时禁用 CTA 并提供 fallback 文案 |
| docs / learn / FAQ sources | 99.9% | docs 导览缺失时保留导航壳和 stale 标记 |
| analytics / campaign sink | 99.9% | 统计延迟不影响门户主流程 |
| asset/CDN | 99.9% | 静态素材降级但不影响结构化入口与 CTA 可见性 |

### 5.5 关键依赖风险

- public summaries 与 source truth 漂移会直接误导外部访客
- CTA 若指向错误或未开放入口,会伤害转化信任
- docs / resource 导览若无统一组织,官网会退化成内容拼盘
- campaign surface 若侵入产品真相表达,会长期污染品牌认知
- marketplace teaser 若冒充交易/能力真相,会放大错误预期

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把首页、产品页、FAQ、docs 页等导航路由横向平铺。  
> 它按 **对外门户产品主链职责 + 品牌 / 认知 / 转化 / 资源 / 运营差异** 来拆分。  
> 因此下面每一部分都可能包含多个公开对象和机制,共同支撑同一段 website 门户主链。

#### 门户入口与品牌表达部分

- **它是什么**: 这是 `L5-website` 的主入口层,一起回答“外部访问者第一次看到什么”
- **为什么单独有它**: 这是外部第一触点,如果不单列,品牌表达会和能力概览、CTA、资源导览混成一层
- **负责什么**:
  - 组织 landing、hero、product positioning、brand surfaces
  - 组织 public navigation 和 first-touch 心智
- **不负责什么 / 容易混淆点**:
  - 不持有 source truth 本体
  - 不负责登录后的内部工作台状态
  - 不负责 marketplace 真相本体
  - 最容易和 product truth、内部入口、营销活动文案混淆
- **与其他部分交互**:
  - 下游: 产品能力概览、CTA、资源导览、增长面
  - 外部: visitors / prospects / brand materials
  - 交互类型: landing 型 + brand surface 型
- **后续详细设计展开点**:
  - WebsitePage / brand block / nav contract

#### 产品能力与方法概览展示部分

- **它是什么**: 这是 website 的认知建立层,一起回答“平台能做什么、方法体系是什么”
- **为什么单独有它**: 官网的核心任务之一是帮助访问者建立理解,但展示永远只是摘要,不能替代 source truth
- **负责什么**:
  - 渲染 public capability summary
  - 渲染 method overview / use cases / product pillars / architecture highlights
- **不负责什么 / 容易混淆点**:
  - 不持有 capability contract truth
  - 不持有 method-library 真相本体
  - 不替代 docs 正式内容源
  - 最容易和 capability-hub / method-library / internal docs 真相混淆
- **与其他部分交互**:
  - 上游: capability-hub / method-library public summaries
  - 下游: CTA / resources / visitors
  - 交互类型: public summary 型 + cognitive overview 型
- **后续详细设计展开点**:
  - capability summary card / method overview block

#### 转化入口与产品导流部分

- **它是什么**: 这是 website 的转化层,一起回答“访客怎样进入产品”
- **为什么单独有它**: 官网的业务目标之一是导流和转化,但 CTA 只是入口,不等于 account/member truth
- **负责什么**:
  - 管理 signup / login / trial / demo / get-started CTA
  - 组织跳转到 console/chat/marketplace/docs 的入口逻辑
  - 形成 funnel 主线
- **不负责什么 / 容易混淆点**:
  - 不持有 member/account truth
  - 不替代 console workspace
  - 不保证进入后 source action 已成功
  - 最容易和 auth truth、product activation 真相混淆
- **与其他部分交互**:
  - 上游: 门户入口与品牌表达部分、产品概览展示部分
  - 下游: console / chat / marketplace / auth entry
  - 交互类型: CTA 型 + conversion funnel 型
- **后续详细设计展开点**:
  - CTA contract / entry gating / trial flow

#### 生态、案例与公开资源部分

- **它是什么**: 这是 website 的外部扩展层,一起回答“平台有哪些生态入口和公共资源”
- **为什么单独有它**: 官网不只是介绍产品,还要承接生态、案例和资源导览。但这些都只是公开消费面,不应混成 source truth
- **负责什么**:
  - 管理 marketplace teaser / partner/ecosystem / case studies
  - 管理 docs / learn / FAQ / blog / release notes 导览
  - 管理 public asset gallery / public resource cards
- **不负责什么 / 容易混淆点**:
  - 不持有 marketplace transaction truth
  - 不持有 docs source truth 本体
  - 不替代 archive / release 真相本体
  - 最容易和 docs 仓、marketplace listing 真相、内部 release 文档混淆
- **与其他部分交互**:
  - 上游: marketplace / docs / release / ecosystem refs
  - 下游: visitors / CTA / SEO / growth
  - 交互类型: teaser 型 + public navigation 型
- **后续详细设计展开点**:
  - teaser cards / docs navigation / case study views

#### 反馈、增长分析与站点运营部分

  - 不直接定义内部产品策略

| teaser 直接冒充 marketplace transaction truth | ❌ | teaser 只是入口和摘要 |
| docs navigation 冒充 docs source truth | ❌ | 导览不等于文档真相 |

### 7.8 事件发布点与跨仓协作清单

| 动作 | 事件/调用 | 消费方 | 一致性语义 |
|---|---|---|---|
| 公开页构建 | `website.page.published` | visitors / SEO / shell | 强一致写入 + 最终一致消费 |
| CTA 触发 | `website.cta.triggered` | analytics / auth / product entries | 强一致写入 + 最终一致消费 |
| teaser/docs 导览更新 | `website.resources.updated` | visitors / SEO / docs nav | 最终一致 |
| feedback 提交 | `website.feedback.submitted` | analytics / ops | append-only 输出 |
| campaign 曝光 | `website.campaign.exposed` | analytics / growth | append-only 输出 |

### 7.9 消息格式(MQ Topic / Event Schema)

本仓不定义业务执行事件正文,但要正式发布 website 层门户与转化事件:

| 事件 | 关键字段 | 说明 |
|---|---|---|
| `website.page.published` | `website_page_id` / `page_name` | 公开页可见 |
| `website.cta.triggered` | `cta_entry_id` / `target_ref` | CTA 被触发 |
| `website.resource.updated` | `resource_id` / `resource_kind` | docs/teaser/resource 更新 |
| `website.feedback.submitted` | `feedback_id` / `page_ref` | 站点反馈提交 |
| `website.conversion.recorded` | `conversion_event_id` / `cta_entry_id` | 转化事件记录 |

### 7.10 错误码定义

| 错误码 | 含义 | HTTP / RPC 映射 | 恢复策略 |
|---|---|---|---|
| `PUBLIC_SUMMARY_REF_MISSING` | 公开摘要来源缺失 | 409 / FAILED_PRECONDITION | 修正 source refs |
| `CTA_TARGET_UNAVAILABLE` | CTA 目标不可达或未开放 | 409 / FAILED_PRECONDITION | 修正 target 或隐藏 CTA |
| `MARKETPLACE_TEASER_INVALID` | teaser 引用或公开范围非法 | 409 / FAILED_PRECONDITION | 修正 teaser refs |
| `DOCS_NAV_STALE` | docs 导览引用已过期 | 409 / FAILED_PRECONDITION | 刷新 docs refs |
| `WEBSITE_FEEDBACK_CONTEXT_INVALID` | feedback 缺 page/CTA 上下文 | 400 / INVALID_ARGUMENT | 补齐上下文后重试 |

### 7.11 返回值语义分类

| 类别 | 语义 | 处理建议 |
|---|---|---|
| 正常 | page / summary / CTA / teaser / feedback 正式建立成功 | 继续主线 |
| 可恢复异常 | source refs 延迟、teaser 缺失、CTA 暂不可达、docs stale | 重试或降级展示 |
| 不可恢复异常 | public page 反写真相、CTA 越权导流、marketplace teaser 冒充交易真相 | 阻断并人工介入 |

### 8.1 场景 A · 访客进入官网并建立平台认知

```text
   │
   ▼
```

```text
Visitor chooses CTA
```

**开发者关注点**:

```text
Docs/teaser/campaign updated
```

**开发者关注点**:

## 10. 读模型与投影设计

### 10.1 总体结构

```text
public page / CTA / resource truth
   │
   ▼
projection builders
   │
   ├─▶ landing / public summary views
   ├─▶ teaser / docs navigation views
   └─▶ funnel / conversion summaries
```

### 10.2 关键读模型说明

| 读模型 | 输入 | 输出 |
|---|---|---|
| `landing_view` | WebsitePage / HeroBlock / BrandSurface | 对外首页视图 |

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| public summary 来源缺失 | 阻断页面构建或降级占位 |
| CTA target 不可达 | 隐藏/禁用 CTA 并保留记录 |
| teaser/docs refs 过期 | 标记 stale / fallback 到基础导航 |
| feedback 缺 page/CTA context | 拒绝提交反馈 |
| analytics sink 失败 | backlog + retry,不影响页面主流程 |

### 11.1 重试 / 降级 / 熔断 / 补偿
- teaser/docs 来源缺失时可降级展示占位,但不得伪造内容
- CTA 目标暂不可达时可回退到更安全的入口层文案,但不得宣称已进入产品
- analytics / campaign 失败时可 backlog + retry,但不得丢失 conversion/feedback 证据

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 门户入口与品牌表达部分 | page 摘要与公开 source refs 不一致 | public summary boundary validate | 阻断发布或降级占位 | 修正 refs 后重建 |
| 产品能力与方法概览展示部分 | capability/method 摘要越界污染 source truth | public overview boundary validate | 拒绝渲染或降级摘要 | 刷新 public refs |
| 转化入口与产品导流部分 | CTA 指向失效 / 未开放入口 | CTA target validate | 禁用/替换 CTA | 目标恢复后重放 CTA 配置 |
| 生态、案例与公开资源部分 | teaser/docs 导览引用过期 | resource nav validate | 标记 stale 或 fallback | 重建 teaser/docs view |
| 反馈、增长分析与站点运营部分 | funnel/feedback 失 context / campaign 指标漂移 | growth boundary validate | 拒绝写入或 backlog | 重试 analytics / rebuild funnel |

## 14. 最小可运行闭环

- 外部访问者打开官网后能看到统一 landing、能力概览和方法概览,且这些公开摘要都能回指正式 source refs
- 访问者通过一个 CTA 成功进入 login/trial/console/chat/marketplace 等下一步路径,而 website 只记录转化事件不冒充激活真相
- docs/teaser/feedback/campaign 至少各有一类入口或事件被统一组织进公开门户主线,并能被 owners/growth 观察与优化

## 15. 结论

本详细设计的核心结论是：
- `L5-website` 的实现主轴必须按 brand / summary / CTA / resources / growth 五个主要部分组织,而不是按首页、产品页、FAQ、文档页等导航树平铺
- website 真相层只持有公开页面、摘要、CTA、teaser、docs 导览和 feedback/funnel 事件,不接管 console/chat/marketplace/method-library/capability-hub 的 source truth
- 所有 landing、public summaries、CTA、resource navigation、feedback/conversion 结果都必须建立在稳定 source refs、只读消费和 append-only 行为证据之上

后续测试与验收文档,应直接围绕这套公开门户主链、转化入口分层、资源导览边界和运营面边界展开.

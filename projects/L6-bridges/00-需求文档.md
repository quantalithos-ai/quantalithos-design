## 2. 背景与问题定义

### 2.1 业务背景

很多团队已经深度依赖 Mattermost、Slack、Telegram、Discord 等既有协作平台,不愿意为了 AI 团队协作再切换到另一个全新工作界面。Quantalithos 因此需要 Bridges,把 Conversation、Turn、Mention、GateCard、Artifact 预览等核心协作语义桥接到外部平台里,让用户可以在熟悉的渠道中与 AI 员工互动。但这种桥接不能牺牲治理与审计：外部平台的按钮、回复、@mention 都必须仍然服从 Policy、Gate、身份映射与审计链要求。

### 2.2 现状与痛点(量化)

| 维度 | 当前状态(段 3 当前) | 痛点 |
|---|---|---|
| 仓文档 | 只有 README 骨架 | 段 3 收尾前的生态层样板尚未建立 |
| Conversation 真相源 | `L1-conversation` 已完成 00/01 | 外部平台如何消费 Turn/Conversation 尚未仓级化 |
| 身份映射 | README 已提出 `external_id ↔ GlobalMember` | 映射授权、持久化与生命周期未正式落需求 |
| Gate 外部展示 | 已要求敏感 Gate 不完整渲染 | 简化 GateCard 的边界与验收口径未成文 |
| 外部密钥治理 | README 已提出 KMS/OAuth 基线 | 第三方平台接入的安全模型尚未仓级化 |

### 2.3 为什么要做(量化依据)

- `product/产品矩阵.md` 已把 Bridges 定义为 **⑧ 独立生态产品**
- `L1-conversation` 的领域模型已明确 Bridges 只应通过桥接投影消费 Conversation/Turn,不能直接篡改对话真相
- README 已给出 Mattermost / Telegram / Slack / Discord 四类平台适配目标,说明这是跨平台桥接而不是单一 Bot
- 若没有 Bridges,很多用户必须离开既有协作平台才能使用 AI 员工,产品渗透门槛会显著升高

### 2.4 业务问题 vs 技术问题

- **业务问题**:用户如何在既有协作平台中低摩擦地使用 AI 员工,又不失去平台治理与审计边界
- **技术问题**:Conversation/Turn 映射、Gate 简化渲染、external_id ↔ GlobalMember 映射、平台 SDK 适配、限流、密钥管理、敏感事件裁剪与 observability 留痕

## 5. 核心用例与用户故事

### 5.1 核心用例

1. 用户在外部平台 @ 某个 AI 员工并触发桥接消息
2. 桥接层把外部消息映射为平台 Turn 并回写结果
3. 低敏感 Gate 在外部平台以简化卡片形式呈现并可操作
4. 高敏感 Gate 只提示“打开 Chat 审批”
5. 管理员配置 external_id ↔ GlobalMember 映射与平台凭证

### 5.2 用户故事卡片

| 字段 | 内容 |
|---|---|
| ID | US-001 |
| 用户故事 | 作为 **外部平台用户**,我想要 **在 Slack/Mattermost/Telegram/Discord 中 @ AI 员工并获得回复**,以便 **不离开既有协作平台也能继续协作** |
| 优先级 | P0 |
| 验收条件 | **Given** 已建立 external_id 映射 **When** 用户发送桥接消息 **Then** 平台生成对应 Turn 并回写回复 |

| 字段 | 内容 |
|---|---|
| ID | US-002 |
| 用户故事 | 作为 **平台管理员**,我想要 **显式配置 external_id 与 GlobalMember 的映射**,以便 **外部身份不会绕过组织授权直接进入平台** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个外部账号 **When** 管理员完成映射 **Then** 该账号才能桥接发言 |

| 字段 | 内容 |
|---|---|
| ID | US-003 |
| 用户故事 | 作为 **审批者**,我想要 **在外部平台处理低敏感 Gate 或收到敏感 Gate 回平台提示**,以便 **在便利性与治理之间取得平衡** |
| 优先级 | P0 |
| 验收条件 | **Given** 一个低敏感 Gate **When** 推送到外部平台 **Then** 可简化审批; 若为高敏感 Gate 则只提示回 Chat 审批 |

| 字段 | 内容 |
|---|---|
| ID | US-004 |
| 用户故事 | 作为 **Auditor**,我想要 **知道一条 bridged Turn 来自哪个外部平台和哪个外部账号**,以便 **保留跨平台可追溯性** |
| 优先级 | P1 |
| 验收条件 | **Given** 一条桥接消息 **When** 查询审计链 **Then** 能看到 bridged_from、external_id、member_id 与平台类型 |

### 5.3 替代流程

- 外部平台 API 不可用 → 平台保留内部 Turn 真相并延后回写
- 映射不存在 → 拒绝桥接并提示管理员配置
- 命中敏感 Gate → 不在外部完整渲染,只返回跳转提示
- 平台速率限制触发 → 排队、节流或丢弃低优先级通知并留痕

## 8. 交互与界面需求

### 8.1 核心页面 / 流程

Bridges 首期主要是平台适配体验而非单独前端页面,核心流程是:

| 场景 | 说明 |
|---|---|
| 外部消息进入 | 用户在外部平台发送/提及 -> 桥接层同步到平台 |
| 外部回复返回 | AI / 平台消息从平台回写到外部平台 |
| Gate 提示 | 低敏感 Gate 简化卡片 / 高敏感 Gate 跳转提示 |
| 管理配置 | 管理员配置映射、平台凭证和授权策略 |

### 8.2 关键 UX 约束

| 约束 | 说明 |
|---|---|
| 外部体验不应伪装成全功能 Chat | 用户要知道这是桥接视图 |
| 敏感操作边界清晰 | 平台外能做什么、不能做什么必须明确 |
| 身份映射透明 | 桥接身份必须能追溯回真实 GlobalMember |
| 失败可感知 | 外部平台失败、限流、回退必须有可理解提示 |

## 2. 业务背景与驱动力

> 校准来源：
> - [01 Step 1 需求基线](design-calibration/01_arch_step_01_requirements_baseline.md)
> - [01 Step 2 目标与约束](design-calibration/01_arch_step_02_goals_constraints.md)
>
> 延伸阅读：
> - 建议继续阅读两份中间产物的“架构需求基线”“背景、驱动力与目标”“当前材料诊断”和“回填草稿”小节。

Quantalithos 需要把受控的协作触达延伸到既有外部协作平台。Bridges 的价值不是复制一个聊天产品，而是把外部平台的来源、位置、消息变化、交互和投递效果转换为可解释的局部桥接状态，并在必要时把获准的内部材料安全地表达出去。平台差异、授权撤销、外部未知效果和敏感材料最小暴露，使这项职责不能由需求文档中的单一“消息转发”描述替代。

架构目标如下：

| 架构目标 | 说明 |
|---|---|
| 承载独立桥接局部状态 | 绑定、映射、游标、去重、效果和交接记录不能退化为内部或平台的第二真相。 |
| 守住受权关系与业务责任边界 | 平台认证、来源可信和安装资格不能自动替代内部主体、授权或 owner 责任。 |
| 支撑独立阶段和单一逻辑效果 | 入口ACK、owner接纳、内部Turn、平台receipt和consumer结果必须可分别解释。 |
| 允许平台差异独立演进 | 线程、编辑/删除、附件、回调、限流和版本差异不能穿透共享保护。 |
| 支撑有界安全恢复与只读追溯 | unknown、gap、blocked和manual应保留为正式结果，而不是靠正文缓存或盲重试伪造完整性。 |

业务驱动力是降低团队在既有协作平台中的切换成本，同时保持治理、责任和审计主权；技术驱动力是隔离多平台协议变化、显式管理映射生命周期、表达外部效果的不确定性，并使所有安全交接只携带最小可用引用。

## 3. 约束条件

> 校准来源：
> - [01 Step 1 需求基线](design-calibration/01_arch_step_01_requirements_baseline.md)
> - [01 Step 2 目标与约束](design-calibration/01_arch_step_02_goals_constraints.md)
> - [01 Step 14 风险与挂起](design-calibration/01_arch_step_14_risks_pending.md)
>
> 延伸阅读：
> - 建议继续阅读上述文件的“硬约束与未关闭风险”“不可变约束”“当前可接受取舍”和“架构非目标”小节。

### 3.1 不可变约束

| 约束 | 说明 |
|---|---|
| 不拥有内部或平台 truth | Bridges 只拥有局部配置、relation/mapping、阶段/效果/连续性状态，不拥有 Conversation/Turn、Identity、Gate/Decision、Artifact、Workspace或平台实体真相。 |
| 不把 `external_id` 视为 GlobalMember 或授权 | 主体 kind、内部责任、当前 binding basis 和有效期必须分别成立。 |
| 不绕过适用 Policy / Gate | 外显、入口和 owner action 分别获得当前依据；低敏感不自动等于可审批。 |
| 不把阶段结果互作证明 | ACK、owner accepted、内部 Turn、平台 receipt 和 consumer disposition 只证明自己的阶段。 |
| 不保存或观测禁止材料 | 消息/附件正文、敏感 Gate、secret/token、私有 callback 材料和可还原派生不进入 durable、日志、trace、handoff或证据。 |
| 不将 unknown 当作无效果 | timeout、崩溃、lease失效或版本不可比时保留 indeterminate/gap/manual，不换 target 或新建 effect。 |
| 不通过 query 维护或修复 truth | 读取、probe和safe view不刷新来源、推进游标、改变映射、重放或执行动作。 |
| 不让未选载体改变不变量 | SDK、OAuth/API Key、KMS、Bus、数据库、缓存、路由和部署产品都必须服从上述边界。 |
| 不用设计资产伪造运行资格 | 静态自检、公开资料、台账、planned状态或上游commit不等于账号、token、run、receipt、test、evidence、verdict、signoff或ready。 |

### 3.2 当前阶段可接受取舍

| 取舍 | 当前口径 |
|---|---|
| 平台原生表达非等价 | 按 installation 和 capability 表达 `supported / degraded / unsupported / waiting`，不承诺平台行为等价。 |
| 自动恢复受能力限制 | 无权威来源、probe、comparator、窗口或无副作用依据时保持 `indeterminate / manual`。 |
| 发现、卡片美化和批量配置 | 作为外围增强，不进入当前核心闭环，也不新增正向前置。 |
| Workspace 语境消费 | 仅在具体路径需要且有独立 owner 依据时采用；Workspace 不替代授权或频道 owner。 |

### 3.3 架构非目标

| 非目标 | 不展开原因 |
|---|---|
| 内部领域或平台 truth 系统 | Conversation、Identity、Governance、Artifact、Workspace和平台分别拥有其真相。 |
| 统一 human 认证/权限中心 | 安全入口和 owner 链负责，Bridges 只消费显式 basis 和责任引用。 |
| Chat/Console 产品或跨平台广播 | 并行产品未停审；广播也会扩大当前受众和 target 边界。 |
| 平台正文备份、审批正文存储 | 与 body-free、最小引用和敏感材料边界冲突。 |
| Runtime/Tools 执行或 evidence 裁决 | 执行、治理和观察结果分别归相应 owner。 |

当前没有来源支持的吞吐、延迟、SLA、容量或“四个平台4/4成功率”数字，因此本架构不编造量化承诺。

## 4. 职责边界

> 校准来源：
> - [01 Step 3 职责边界](design-calibration/01_arch_step_03_responsibility_boundary.md)
> - [01 Step 5 语义单元](design-calibration/01_arch_step_05_bounded_contexts.md)
>
> 延伸阅读：
> - 建议继续阅读上述文件的“结构化中间产物”“逐单元语义卡”和“边界红线”小节，了解职责如何与六个语义单元分离。

| 职责项 | 类型 | 说明 |
|---|---|---|
| 桥接配置与受权 `external-binding relation` | 做 | 本仓拥有接入局部关系和生命周期，不拥有授权 basis。 |
| 平台协议转换与来源定位 | 做 | 通过适配边界隔离平台语义，不迁移平台 truth。 |
| 外部 identity/channel/message/thread 的 typed mapping | 做 | 只承载获准引用关系，不创建两端实体。 |
| 受权 owner 交接与安全外显 | 做 | 只转换已获准材料并回链正式 owner 结果。 |
| 投递、callback、去重、位置与恢复局部记录 | 做 | 记录局部处理和效果，不替代内部提交或平台 truth。 |
| body-free 安全追溯交接 | 做 | 输出安全引用、阶段和有限原因，不拥有真实证据或报告。 |
| 内部 Conversation / Turn 及 AI 身份 | 不做 | 分别归 Conversation 与 Identity。 |
| Gate / Decision 与全域认证授权 | 不做 | Governance 和正式入口负责，Bridges 不自建。 |
| Artifact 正文及 Workspace 真相 | 不做 | 只消费授权附件引用和条件只读语境。 |
| 外部实体 truth、正文备份与直接工具执行 | 不做 | 外部平台及执行 owner 负责。 |
| 安装认证与内部显式 binding | 易混淆职责 | 安装 scope/验签不替代内部主体、目标或 action 授权。 |
| Integration 来源与 human 责任 | 易混淆职责 | 可信来源不自动授予 human 参与或审批资格。 |
| mapping 与实体、renderer 与裁决 | 易混淆职责 | 关系和表达不产生业务事实或审批。 |
| ACK、owner 接纳、Turn 与平台 receipt | 易混淆职责 | 各阶段独立，平台接受不证明已读。 |
| 审计 handoff 与 consumer 接受/证据 | 易混淆职责 | 本地交接不形成外部接受、evidence或signoff。 |

边界红线是：不得隐式建身份/对话/权限；不得低敏感默认 action；不得形成 owner/platform 第二 truth；不得把禁止材料写入 durable 或观察出口；不得在未知时盲 retry、换 effect 或换 target；不得让 query 维护；不得让 adapter 直接裁决或执行。

### 5.3 失效与边界说明

| 失效面 | 当前姿态 |
|---|---|
| 身份、责任、visibility、Policy 或 Gate 依据失效 | fail-closed；禁止默认授权、切换目标或继续 action。 |
| 必要 source/material/Artifact ref 缺失 | `blocked / missing_source`；禁止用 durable body 补恢复。 |
| 平台、secret 或能力版本不可用 | 对应 installation 暂停或 blocked；已发效果未知则保留 `indeterminate`。 |
| Workspace 条件消费不可用 | 只限制该分支；有独立 owner 依据的路径不强制经 Workspace。 |
| 观察 consumer 或 producer 准入不足 | 只允许获准的安全有限 handoff；不能报告 evidence 或 ready。 |

本仓位于 Layer 5 的外部协议适配边界。主图的收缩只减少画面，不减少正式依赖或安全约束；未停审的 L5-chat 不在本上下文图中。

## 6. 限界上下文与子域划分

> 校准来源：
> - [01 Step 5 语义单元](design-calibration/01_arch_step_05_bounded_contexts.md)
> - [01 Step 8 数据与一致性](design-calibration/01_arch_step_08_data_consistency.md)
>
> 延伸阅读：
> - 建议继续阅读 Step 5 的“逐单元语义卡”和 Step 8 的“逐单元数据所有权卡”，理解单一局部 BC 内不同状态主语为何不能合并。

Bridges 采用一个外部协议适配限界上下文，内部按状态主语划分六个语义单元。六个单元不是六个业务真相服务，也不是六个部署进程；它们共享本仓的边界、局部版本和结果分层语言，但不能共用一个笼统的“成功”状态。

### 6.1 子域 / 上下文划分

| 名称 | 类型 | 作用 | 与其他部分的关系 |
|---|---|---|---|
| U1 受权绑定与映射 | 核心子域 | 承载 installation、binding generation、受权 relation 和 typed mapping 的局部语义。 | 约束 U2~U4 的受众、目标、来源和 action 定位。 |
| U2 入站交接 | 核心子域 | 承载平台来源验证、入口阶段和 owner handoff 的局部语义。 | 依附 U1 的当前关系，向 Conversation 交出安全引用。 |
| U3 安全外显与交付 | 核心子域 | 承载外显资格、stable effect、attempt 和已知平台结果的局部语义。 | 消费 U1 当前映射和 owner/Governance/Artifact 依据。 |
| U4 交互责任 | 核心子域 | 承载 callback verification、replay/expiry 和 owner action handoff 的局部语义。 | 围绕 U1 的 actor/target 定位，交给 Governance 或其他 owner。 |
| U5 连续性与恢复支撑 | 支撑子域 | 承载 dedup、cursor、epoch、comparator、gap、限流和恢复 disposition。 | 支撑 U1~U4 的连续性，不拥有它们的业务 truth。 |
| U6 安全读取与追溯支撑 | 支撑子域 | 承载 safe view、body-free handoff、局部 trace 和 consumer disposition 引用。 | 消费各单元的安全状态，不能把本地记录升级为 evidence。 |
| owner/basis/material/capability 引用 | 本地索引 / 投影 / 引用 | 为稳定消费外部正式语义保留最小 ref、版本或安全摘要。 | 只引用 Conversation、Identity、Governance、Artifact、Workspace、平台和Observability，不拥有正文。 |

### 6.3 统一语言

| 术语 | 定义 | 使用场景 |
|---|---|---|
| `installation` | 一个外部平台接入实例及其能力/版本范围 | U1、平台资格和配置 |

| `owner handoff` | 向正式 owner 交出安全引用和责任语义的阶段 | U2、U4 |

| `attempt` | 对同一 stable effect 的一次投递尝试 | U3、U5连续性 |
| `delivery receipt` | 本仓对平台已知业务结果的安全记录 | U3；owner result ref另行保留，二者不等同 |
| `gap` | stream/epoch/comparator 不足或变化缺失的局部结果 | U2、U5 |
| `safe view` | 只读、body-free、可降级的局部视图 | U6 |

### 7.3 部署与扩缩边界

平台 adapter 可以按 installation 或平台独立承载，也可以与共享承接角色合并；架构不要求具体进程数量。无论如何部署，平台故障必须隔离到对应 installation/lane，局部状态和后台任务必须按 binding/effect/namespace 保持可解释；不得用共享队列或共享存储跨越 owner 边界。

具体 SDK、OAuth、API Key、KMS、Bus、数据库、缓存、路由和部署产品均保持未选，待 §11 的 seam 资格和 §15 的待确认事项满足后再核验。

### 9.1 数据所有权矩阵

Bridges 的正式 truth 只覆盖局部桥接状态。下表将数据分为正式真相、快照/投影、引用关系和明确不拥有四类；“引用”不等于把目标对象迁移到本仓。

| 数据项 | 数据类型 | 拥有者 | 消费者 | 一致性口径 | 边界 |
|---|---|---|---|---|---|
| configuration revision、binding generation | 正式真相 | Bridges | U1~U6 | 局部强一致 | 不证明安装、basis或平台能力有效。 |
| external-binding relation、typed mapping | 正式真相 | Bridges | 入站、外显、交互 | 局部强一致 | basis/owner授权仍由外部提供。 |
| verification、ACK、owner-handoff disposition | 正式真相 | Bridges | U2、U6 | 局部强一致 | 不等Conversation接纳或Turn提交。 |
| delivery intent、stable effect、attempt、known receipt | 正式真相 | Bridges | U3、U5、观察交接 | 局部强一致 | 不拥有平台message/read receipt。 |
| callback verification、one-use/replay disposition | 正式真相 | Bridges | U4、U5 | 局部强一致 | 不拥有Gate/Decision或审批正文。 |
| cursor、epoch、comparator、dedup、gap、recovery disposition | 正式真相 | Bridges | U2/U3/U5/U6 | 局部强一致 | 不拥有平台或Bus完整性水位。 |
| capability / provider / rate-limit安全摘要 | 快照/投影 | Bridges（受限） | U1~U5 | 来源/版本约束下最终一致 | stale不默认升级为supported。 |
| owner、basis、source、material、visibility、action、consumer ref | 引用关系 | 对应owner/消费者 | Bridges | 引用有效性约束下最终一致 | 只保存typed ref、版本和有限 reason。 |
| safe view / diagnostic summary | 快照/投影 | Bridges | U6安全读取 | 可stale、可重建 | query不反写truth。 |
| Conversation / Turn、Identity、Gate / Decision | 明确不拥有 | 相应内部 owner | Bridges只消费 | owner主导 | 不在本地复制正文或裁决。 |
| Artifact正文、Workspace正文/权限、平台账号/频道/消息/附件 | 明确不拥有 | Artifact、Workspace和平台 | Bridges只消费 | 外部主导 | mapping不迁移实体。 |
| 消息/附件正文、敏感Gate、token、secret、私有callback材料 | 明确不拥有 | owner或私有seam | 仅瞬时转换 | 不进入持久化 | durable、日志、trace、handoff和证据均无例外。 |

### 9.2 一致性层次

| 层次 | 适用范围 | 一致性口径 | 失败口径 |
|---|---|---|---|
| 局部状态一致性 | relation、mapping、generation、effect、attempt、cursor、dedup和局部disposition | 同一局部变更内强一致；历史effect不被新generation改写 | 冲突、撤销和CAS失败进入 blocked/quarantine，不静默覆盖。 |
| owner/平台消费一致性 | Conversation、Identity、Governance、Artifact、Workspace、平台效果 | 外部结果最终一致，需带来源、版本、资格和引用有效性 | pending/unknown/stale保持可见，不以空值或本地摘要补齐。 |
| 跨边界恢复一致性 | gap、未知投递、owner结果和观察handoff | 只按同一 operation/effect 与权威 basis 对账 | 无 comparator、probe、coverage或窗口时保持 gap/indeterminate/manual。 |

### 9.3 数据关系与禁止反写

#### 简化关系示意图: 局部truth与外部引用

```text
+---------------------------+       +----------------------------+
| Bridges local truth       |------>| owner/platform safe refs   |
| relation, effect, cursor  |       | basis, material, result    |
+-------------+-------------+       +--------------+-------------+
              |                                     |
              | no body / no truth migration       | validity required
              v                                     v
      +-------+-------------------------------------+-------+
      | forbidden: platform body, Conversation/Turn,        |
      | Identity, Gate/Decision, Artifact, Workspace,       |
      | secret, private callback, evidence/report bodies    |
      +-----------------------------------------------------+
```

图后说明：

- 局部 truth 可以强一致，但引用目标仍由 owner 或平台决定；引用存在不迁移正文。
- `unknown`、`stale`、`blocked` 和 `gap` 是正式可见结果，不被空值或缓存改写。
- safe view 和 query 只能读取已有局部状态，不能触发 repair、replay、外显、Decision或Runtime/Tools。

### 9.4 补偿原则

补偿对象只能是本仓的 relation、attempt、cursor、gap、handoff 或局部 disposition。补偿必须绑定原 operation/effect、当前 binding generation 和权威依据；不能换 target、生成新 effect、恢复正文、修改 owner truth 或以 lease 失效推断“无效果”。

### 9.5 mapping与连续性语义结构下限

下表是Step5已确认的语义维度与来源边界，不是DDL或公开DTO定义。字段形态、编码、可选性、exact typed-ref、状态枚举及callable surface必须在02~04闭合；未闭合不能交给实现者猜测或用通用字符串代替。

| 局部对象 / 关系 | 必须保持的语义维度 | 权威来源与失败边界 |
|---|---|---|
| adapter configuration | platform、server/环境、installation scope、capability/schema revision、direction/action、route约束、opaque secret ref/version | 受权配置与provider binding；配置版本、binding generation及能力版本不互替。 |
| external-binding relation | installation namespace、external主体/位置、internal typed target、basis/ref/version、方向/action、有效期及撤销generation | 正式授权链提供basis，本仓只保存relation；安装scope不自动成为内部授权。 |
| identity mapping | account locator、human/AI/Integration kind、正式internal actor或AI GlobalMember ref、generation/basis | human责任owner仍待确认；AI引用不替human或participant资格，不建GlobalMember。 |
| channel/DM/topic/thread mapping | platform/installation及位置kind、父子/线程关系、内部Conversation/scope ref、受权generation | 两端位置/目标各由owner确认，显示名、mention或默认频道不能补定位。 |
| message/change mapping | 原external locator、create/edit/delete kind、source ref/version、owner accepted fact/manifestation ref、generation、方向及可信来源标记 | 显式管理或已知owner/平台结果建立；缺原关系则quarantine/gap，不能猜消息或改其他对象。 |
| delivery intent/attempt/receipt | source/version、target/generation、allowed projection/version、operation kind、stable effect；attempt identity及claim/fence；已知结果类别和safe external locator | intent关联不静默改义；attempt不产生新effect；平台message/read truth仍外部。 |
| callback verification | installation、source message/intent、actor责任ref、bound target/action、owner版本、expiry/one-use及operation | 私有token/context只瞬时验证；缺任一必要依据拒绝或blocked。 |
| dedup / effect continuity | management/inbound/callback/outbound/recovery-handoff各namespace、installation/获准scope、稳定operation identity、语义版本及原result关联 | 同义复用当前获准读取的原结果，变义conflict/quarantine；窗口过期不自动再执行。 |
| cursor / gap | source namespace、stream、session/epoch、opaque position、正式comparator/coverage；protocol/owner/effect位置分开 | 无比较器即不可比，不能用key、source version或timestamp代cursor；gap仅权威覆盖可关闭。 |

本仓强一致保护的是上述局部关联和变更，不保证跨owner/平台的总事务。只有获准scope与可比stream中的位置可以推进；ACK、业务处理和delivery位置既不互替，也不能以一个全局offset抹去gap。去重、审计和回放窗口均须有真实范围/保留依据，预算或记录失效后限制自动操作。

> 延伸阅读：

本章只选择通信类别，不锁定 HTTP、SDK、Bus、队列或平台产品。P0 主线是：同步用于当前资格/验证/安全读取，异步用于外部来源和正式事实/效果传播，后台任务用于限流、延后投递、gap对账和局部恢复。

### 10.1 通信类别与阶段结果

| 场景 | 推荐通信方式 | 当前交互可证明 | 不可证明 | 失败姿态 |
|---|---|---|---|---|
| U1 绑定管理与资格 | 同步请求/响应 | 当前局部配置、安装、basis、secret ref和目标资格 | 平台永久可用或内部授权已成立 | 明确拒绝或 waiting/blocked。 |
| U1 变化、撤销和能力传播 | 异步事实/回调 + 后台承接 | 某 installation/binding 的已知变化 | 旧代际可继续或新 target 已授权 | stale/gap；阻止旧排队操作。 |
| U2 平台来源与入口确认 | 异步来源，在入口边界同步返回阶段结果 | 来源验证和入口阶段 | owner接纳、内部Turn或平台业务完成 | 验证失败拒绝；缺安全ref则隔离或 indeterminate。 |
| U2 owner 事实交接 | 同步请求/响应或异步结果 | owner返回的 accepted/rejected/pending/unknown | 平台ACK或本地disposition等于owner结果 | 按原operation保留pending/unknown。 |
| U3 外显资格预检 | 同步请求/响应 | 当前source、target、visibility、Policy/Gate、material和能力资格 | 平台送达、已读或consumer接受 | 缺任何必要依据则 blocked。 |
| U3 外部效果与receipt | 异步结果/回调 | 平台已知业务结果和安全 locator | 内部提交、用户已读或观察消费者接受 | known rejection 与 indeterminate 分开；未知不盲重发。 |
| U3 限流、延后和对账 | 后台任务 | 原intent仍被受控承接 | 排队等于完成 | 按lane/预算等待，超界转 manual。 |
| U4 callback验证 | 同步验证 | installation、签名、actor、target、action、expiry和one-use边界结果 | Gate/Decision已批准或执行已发生 | 过期、重放、跨主体和撤销 fail-closed。 |
| U4 owner action结果 | 异步结果/正式交接 | owner的独立动作结果引用 | callback ACK或按钮状态等于Decision | pending/unknown独立对账。 |
| U5 cursor/gap/recovery | 后台任务 + 权威查询 | 局部位置、去重和恢复结果 | 平台/Bus全局完整性或无效果 | 无 comparator/probe/coverage 保 gap/manual。 |
| U6 safe view / handoff | 同步只读 + 异步consumer结果 | 本地安全视图和已提交handoff | consumer接受、evidence、report或verdict | denied/unavailable/unknown，不由读取触发维护。 |

### 10.3 关键交互不变量

1. 平台 ACK、owner accepted、内部 Turn、平台 receipt 和 consumer disposition 不互相证明。
2. callback 的签名、按钮、管理员身份或低敏感标签不能单独授予 action；owner 必须二次核验。
3. intent 固定 stable effect，attempt 只追加尝试；未知结果不创建新 effect。
4. edit/delete/thread 只作用于原 mapping 和明确能力；不默换频道、target或正文。
5. 查询和观察是 no-write；修复、重放和外显必须由显式维护/命令边界承接。

### 10.4 协议阶段与guard下限

这些是已确认的阶段主语和成立条件，不是最终enum、handler流程或平台响应码；具体协议与状态机由02/03在同一来源链上展开。最终设计必须保持每种缺口结果，不能自创一个统一success来合并阶段。

| 阶段主语 | 成立条件 | 未满足或未知时的姿态 | 禁止推论 |
|---|---|---|---|
| binding configured / active | config、installation、当前basis、typed target及secret资格分别有效 | waiting/blocked；suspended/revoked阻新派发和旧排队 | configured/active不证明平台可用或任何业务提交。 |
| inbound verified / authorized | 平台来源认证、当前relation/generation、operation/change kind、原mapping及source版本可解释；source marker/回环只据验证来源与本仓mapping/发送关系 | invalid拒绝；伪造、回环或冲突隔离，缺关系quarantine/gap | 不信用户自报bridged marker；不以显示名识别回环。 |
| 入口ACK | 返回该平台规定的入口阶段结果；可靠接管另需safe可恢复ref或owner已接纳 | 无安全接管不承诺无损回放，不存raw inbox补偿 | ACK不等owner accepted、Turn提交或用户动作完成。 |
| inbound owner_handoff | target mode、actor/kind、required digest及safe material/ref符合已有Conversation正式合同 | 缺材料/责任blocked；不新造泛用submitTurn | Integration来源例外不取消owner的active/visibility等gate。 |
| owner accepted / rejected / pending | 由owner正式结果和可读取result ref成立 | unknown为indeterminate，按原operation对账 | accepted fact/manifestation不自动等Turn。 |
| edit/delete/thread差异 | 回链原message/thread mapping、版本和逐安装能力 | unsupported，或经owner明确允许degraded；不可比为gap | 外部delete不物理删除内部truth，不伪装新发言或默换target。 |
| outbound prepared | committed source、current binding、visibility、适用Policy/Gate、安全projection及附件资格 | 缺任何必要条件blocked/missing_source | 已提交source不证明外显获准或外部送达。 |
| outbound dispatching | 派发时重核当前依据、secret版本、能力、lane和预算；source/target/projection/effect不改义 | 撤销/失效阻止派发，等待下界和预算受平台合同限制 | 队列/lease/claim不表示平台已接受。 |
| platform_accepted / known_rejected | adapter返回权威业务结果，必要locator可解释且body-free | 无可核验结果为indeterminate | HTTP成功不直接升级业务结果；accepted不等送达/已读。 |
| retry_wait | 已知无副作用的retryable结果、当前授权、原effect、lane及等待下界/预算同时成立 | 不满足时indeterminate/manual/blocked | timeout、lease失效或SDK默认retry不构成无效果依据。 |
| callback verified / owner_handoff | 平台认证、source/action映射、actor责任、当前owner状态、expiry和one-use共同有效 | tampered/expired/replayed/cross-target/revoked拒绝；缺basis blocked | 只交接owner action，不直接批准Gate/Decision或执行工具。 |
| callback owner result | owner二次核验并返回正式action result ref | pending/unknown按原owner operation对账；重复只在当前可见时回显原结果 | callback ACK/deferred和按钮变化不等Decision。 |
| recovery / reconcile | 原source/effect/basis、scope、权威query/probe/coverage和窗口有效 | gap/blocked/missing_source/indeterminate/manual保留 | known success只finalize局部，不再外呼；不修owner/platform truth。 |
| safe handoff / read | mutation材料body-free且准入成立，读取具当前scope/visibility | consumer unknown独立；denied/unavailable不当空 | query/probe不维护；local trace/attempt不形成consumer accepted/evidence。 |

敏感Gate的正文始终不进入外部payload；存在性、提示、受控入口和action各自需要依据。没有正式入口合同时不造URL或按钮，只有获准无动作提示或blocked。附件必要性和省略资格由owner明确，读取/传播ref失效不得用文件缓存或永久公开链接替代；source/projection新版本必须重新受权形成新的intent，不能在原effect内换内容掩盖未知。

本章记录架构机制选择，不把未核验产品写成已选技术。所有具体产品必须在真实版本、scope、安装、secret、限流、结果语义和失败合同核验后，沿既有 seam 接入。

| 技术机制 | 解决的问题 | 采用理由 | 代价 / 约束 |
|---|---|---|---|
| typed per-platform adapter | Slack、Mattermost、Telegram、Discord的线程、编辑/删除、附件、callback和限流差异 | 防止平台私有语义穿透核心；每个installation可独立声明能力 | 需要维护能力矩阵和逐平台资格；不承诺四平台等价。 |
| capability / version / installation gate | 公开协议与具体安装能力不一致 | 将版本、scope、入口、方法、方向和材料资格绑定到具体installation | 未核验能力保持 waiting/unsupported/degraded。 |
| explicit binding generation + typed mapping | 裸external ID、显示名或默认频道串绑 | 保持主体kind、位置kind、target、方向、action和撤销代际可解释 | 映射维护更重；不允许自动发现即绑定。 |
| owner handoff port | 防止Bridges复制内部事实或直接写owner表 | 通过正式边界交出source/target/actor/kind/digest/ref语义 | 上游合同缺失时正向交接保持 blocked。 |
| stable effect + attempt + receipt | 防止超时和重试产生重复外部效果 | 逻辑效果、尝试、平台已知结果三者分离 | unknown需要对账和人工出口，不能用默认retry库替代。 |
| stream/epoch/comparator cursor | 防止跨session、裸ID或时间戳误报位置 | 只有可比位置推进，缺口显式保留 | 需要平台/owner提供可核验比较依据。 |
| body-free safe ref + opaque secret ref | 防止正文、附件、敏感Gate和凭证泄露 | durable、日志、trace、handoff和观察均可共用最小材料边界 | 可诊断信息更少，必须依赖owner安全读取。 |
| query no-write safe view | 防止读取副作用和本地trace冒充证据 | 只读视图、degraded/denied/unknown显式表达 | 修复/重放必须另设维护边界。 |
| sync qualification + async fact + background recovery | 同时满足即时安全拒绝和外部最终一致 | 使通信类别与阶段owner相符 | 运行状态和失败解释比全同步更复杂。 |

### 11.1 配置与 secret seam

配置必须显式携带 platform/installation、capability revision、方向、action、route约束、有效期、binding generation、预算和 opaque secret ref。配置接受不等于安装可用或运行激活；缺 basis、scope、rotation、revoke、解析和失败语义时保持 waiting/blocked。secret 只能通过私有 seam 瞬时解析，raw secret/token/私有 callback 不进入局部 truth、日志或证据。

### 11.2 尚未选定的产品载体

当前未选定具体平台 SDK、OAuth/API Key 供应方式、KMS、消息总线、数据库、缓存、路由产品或部署拓扑；不沿用旧01中的Python/TS组合。载体选择受§15的`BR-UP-007/008/009`和后续合同约束；任何选择都不能削弱typed adapter、body-free、stable effect、cursor/gap和query no-write不变量。

### 11.3 四平台adapter差异边界

| adapter | locator与mapping范围 | inbound/callback验证与阶段 | outbound/变化/附件 | cursor、顺序、限流与恢复 |
|---|---|---|---|---|
| Slack | installation/workspace、account、channel/message/thread；外部workspace不等内部Workspace | raw body仅瞬时验签；时间有效性和当前scope独立；Events ACK单列 | edit/delete/thread、文件读取与传播逐scope/pin核验，不复制正文 | event_id用于来源去重，不作业务commit cursor；ts非全局水位；method/workspace/channel及history/replies发行类别分别核验。 |
| Mattermost | server instance、installation、team/user/channel/post/root | 可信server/plugin或context认证合同；不假设Slack签名头；PAT权限不等内部actor | Blocks/legacy及附件资格按部署版本，不由最新文档推实例能力 | session/event ID和续接按部署核验；限流按实例配置/响应，不承诺完整恢复。 |
| Telegram | bot installation、account/chat/message及可选forum topic | polling/webhook仅一个有效入口；webhook secret私有验证；callback ACK不等owner action | 编辑/删除权限、窗口、thread/topic和附件有效性待服务合同核验，不假设所有chat支持topic或普通删除通知完整 | per-bot update/offset隔离；retry_after与cloud配额/留存/TTL仍待官网核验，不由源码master推固定cloud能力。 |
| Discord | application installation、guild或DM、channel/user/message及thread channel | HTTP/Gateway交互入口互斥，分别核验Ed25519或Gateway认证；interaction token是secret，响应/expiry限时独立 | message content受intent与权限约束，变化/附件按pin核验 | session/sequence只在resume资格内比较，invalid session保gap；Snowflake非跨流水位；bucket/major resource/global动态限流。 |

这是已读官方资料范围的约束矩阵，不是已安装支持矩阵；Telegram官网服务合同缺口仍开放。平台能力必须逐installation、版本、方向、方法和受众核验；SDK包装、直接API、plugin、HTTP/Gateway等仍是候选seam，不预选某种接入。lane只保证获准mapping内的顺序，edit/delete依赖已确认create locator；等待下界不缩短，无副作用证明和预算不成立则不自动retry。

### 11.4 seam最低资格

| seam | 必须可证明 | 缺口姿态 |
|---|---|---|
| adapter | installation/kind、来源验证、mapping、变化/线程、业务结果及限流语义可版本化 | unsupported/degraded/blocked，不用默认兼容。 |
| config | generation、direction/action、route policy、capability revision、scope、expiry/revoke及稳定引用可审计 | 配置接受不等激活，缺依据waiting。 |
| secret | opaque ref、provider/version、scope、轮换/撤销、private读取authority及失败合同 | raw值不出private seam；引用未知/解析失败停止受影响操作。 |
| recovery | 原operation/effect、comparator/coverage、权威probe、预算、窗口及人工出口 | 保unknown/gap/manual，claim/fence不消除外部未知。 |
| evidence handoff | 安全ref/version/阶段/有限reason/位置摘要及真实handoff状态 | 不保存body、原始正文digest、secret、敏感Gate或私有URL，不生成evidence/verdict。 |

### 12.1 路径级方案比较

| 方案 | 主要收益 | 主要代价 / 风险 | 结论 |
|---|---|---|---|
| P0：单一局部 BC + typed adapters + 混合通信 | 共同保护授权、阶段、effect、cursor和body-free；平台差异可独立降级 | 共享抽象和审查维护较重，需要后台和人工对账 | **采用** |
| P1：每个平台独立业务实现 | 平台自由度高，初期局部直观 | P0不变量复制多份，行为漂移、审计难统一 | 不采用 |
| P2：通用跨平台消息/动作模型 | 接入表面较小 | 压平线程、安装、scope、callback、限流和能力版本差异，unsupported难诚实表达 | 不采用 |
| P3：无状态直通代理 | 初期存储和部署简单 | 无法保存generation、dedup、effect和gap，崩溃后无法解释和恢复 | 不采用 |
| P4：全同步边界编排 | 表面即时、调用方易理解 | 把平台时限、限流和最终一致强压入口，易把超时/ACK误报完成 | 不采用为主线 |
| P5：全异步事件优先 | 解耦和延后恢复较强 | 无法即时拒绝未授权请求或返回当前visibility/资格 | 不采用为主线 |

### 12.2 取舍结论

P0 牺牲了短期的原生体验、全平台等价和全同步即时成功，换取 owner/platform truth 不迁移、差异可解释、未知可保留和局部状态可追溯。P4 和 P5 只作为局部场景的通信类别参考：资格/验证/读取需要同步，事实/效果需要异步，延迟/恢复需要后台；不能将任一单类通信扩大为全系统风格。

不纳入比较的方向包括：把外部平台设为内部或平台统一 truth、自动由 external ID 创建 GlobalMember、复制消息/附件正文来保证回放、以日志/静态设计产生 evidence 或 readiness。这些方向违反稳定边界，不是可重新选择的实现方案。

| 平台版本、scope、入口或能力变更 | adapter、capability、mapping、cursor与receipt | 默认兼容、继续使用旧generation。 |

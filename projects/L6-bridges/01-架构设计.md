## 1. 业务背景与驱动力

### 1.1 业务背景

Bridges 的目标不是把 Quantalithos 克隆成另一个 Slack/Telegram 机器人,而是把平台中的**对话、提醒、低敏感审批与 AI 员工互动**安全地延伸到既有协作平台。它必须同时满足两个看似冲突的目标：一方面降低用户切换工具的摩擦,另一方面绝不让外部平台成为绕过平台治理与审计的旁门。换句话说,Bridges 既是“触达层”,也是“边界层”。

### 1.2 业务驱动力

**业务驱动力**:
- 团队已经有既有协作平台,需要低迁移成本地接入 AI 员工
- 个人用户尤其在移动场景下,希望用 Telegram/Slack 等快速收到提醒或做轻量审批
- 产品需要扩展触达面,但不能牺牲管理者、审计者与组织级治理的基本控制

**技术驱动力**:
- conversation 的 Turn/Conversation 与外部平台 Message/Channel/DM 需要可逆映射
- governance 的 Gate 需要按敏感级别裁剪显示,低敏感可在外部处理,高敏感必须回平台
- identity 的 `external_id ↔ GlobalMember` 映射、外部密钥管理、平台限流与 observability 留痕必须统一收敛

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 兼容性 | 四平台样本流可用 | 4/4 | E2E |
| 安全 | 未授权桥接拦截率 | 100% | 安全测试 |
| 审计 | bridged 来源覆盖率 | 100% | 回归测试 |
| 安全 | 明文凭证落盘次数 | 0 | 安全测试 |
| 稳定性 | 外部平台短时失败恢复 | 100% 样本流 | 集成测试 |
| 一致性 | 敏感 Gate 裁剪策略命中率 | 100% | 安全/E2E |

### 2.1 不可变约束

| 约束 | 来源 | 影响 |
|---|---|---|
| 外部平台操作不得绕过 Policy 和 Gate | README / BR1 | 所有交互都需回到平台治理模型 |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 外部平台 API 差异 | 高 | per-platform adapter + shared bridge core |
| Gate 渲染能力 | 中高 | gate renderer abstraction |
| 身份映射策略 | 中 | mapping store + auth policy layer |
| 限流/重试策略 | 中高 | per-platform rate-control adapter |
| 平台功能演进 | 中高 | conversation-first canonical model |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **shared bridge core + per-platform adapters**(当前) | 语义统一、适配差异可隔离 | 初期抽象层更重 | ✅ |
| 每个平台独立实现一套业务逻辑 | 平台自由度高 | 行为漂移、审计规则难统一 | ❌ |
| 只做单平台 Bot | 实现快 | 与产品矩阵目标不符 | ❌ |
| 把外部平台当主真相源 | 平台渗透强 | 彻底破坏 Quantalithos 领域真相 | ❌ |

**最终选择**:**Conversation canonical model + shared bridge core + 四平台适配器**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| 平台真相优先于外部平台真相 | 不破坏治理与审计链 | 外部体验不能做到 100% 原生自由 |
| 平台适配器隔离 | 可按平台差异演进 | 需要维护多套 SDK 适配层 |
| 敏感 Gate 裁剪 | 降低外泄风险 | 外部审批体验受限 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```text
external users / bots / admins
            │
            ▼
      ★ quantalithos-bridges ★
      - platform adapters
      - identity mapping
      - bridged turn translation
      - gate renderer / guardrails
          │          │          │
          │          │          └────────▶ observability
          │          └──────────────────▶ identity / governance
          └─────────────────────────────▶ conversation via SDK
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 把外部平台消息、提及、回复映射到 Conversation/Turn
- ✅ 把平台消息和低敏感交互回写到外部平台
- ✅ 管理 external_id ↔ GlobalMember 映射与平台接入凭证
- ✅ 对 Gate 进行平台友好的简化渲染与敏感度裁剪

**不做什么**:
- ❌ 不持有对话真相、治理真相、身份真相
- ❌ 不把外部平台做成全功能 Chat
- ❌ 不自动创建 GlobalMember 或越权映射身份
- ❌ 不在外部平台完整渲染高敏感审批内容

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| ConversationService | 99.9% | 无法同步消息 | 延迟回写 / backlog |
| GovernanceService | 99.9% | Gate 裁剪/状态查询失败 | 回退到“打开平台查看” |
| IdentityService | 99.9% | 映射与成员上下文失败 | 拒绝桥接 |
| 外部平台 API/SDK | 平台依赖 | 限流/失败/策略变化 | 重试 / 排队 / 功能降级 |
| KMS/OAuth | 高 | 凭证不可用 | 阻断相关平台操作 |
| Observability | 99.95% | 审计写入失败 | backlog / 本地暂存 |

### 4.4 关键依赖风险

- 外部平台消息能力差异如果直接泄漏到业务层,会导致跨平台行为严重漂移
- 身份映射错误会直接污染责任链与审计链
- 平台速率限制或交互限制如果没有统一节流模型,会让桥接系统极不稳定

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Message Bridging | 核心域 | Message ↔ Turn 的双向翻译 |
| Identity Mapping | 核心域 | external_id ↔ GlobalMember 绑定与授权 |
| Gate Projection | 核心域 | Gate 在外部平台的简化投影 |
| Platform Adaptation | 支撑子域 | Mattermost/Telegram/Slack/Discord 平台特化 |
| Security & Audit | 支撑子域 | 凭证、裁剪、留痕、限流 |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Bridge Core | 平台无关的桥接语义核心 | BridgedTurn / BridgeEvent |
| Mapping | 身份映射与授权 | ExternalMapping |
| Gate View | Gate 简化渲染与敏感度裁剪 | ExternalGateView |
| Platform Adapter | 各平台 SDK 与格式适配 | PlatformMessage / PlatformAction |
| Audit | 桥接来源与操作留痕 | BridgeAuditRecord |

### 5.3 上下文映射关系

- conversation → Bridge Core: **Conformist**，外部消息必须服从平台对话模型
- identity → Mapping: **Customer-Supplier**，平台身份是真相源
- governance → Gate View: **Open Host Service + Guarded Projection**
- platform adapters ↔ Bridge Core: **Anti-Corruption Layer**，隔离各平台私有语义

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| BridgedTurn | 由桥接层创建或回写的 Turn 投影 | Bridge Core |
| ExternalMapping | 外部账号与平台成员的授权绑定关系 | Mapping |
| ExternalGateView | 某个 Gate 在外部平台上的简化可见视图 | Gate View |
| PlatformAction | 外部平台中的一次交互动作 | Platform Adapter |
| BridgeAuditRecord | 可追溯到平台、账号、成员和事件的桥接记录 | Audit |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```text
platform users / channels
          │
          ▼
   platform-specific adapters
          │
          ▼
      shared bridge core
      ├─ mapping store
      ├─ turn translator
      ├─ gate projection
      └─ audit / rate control
          │         │         │
          │         │         └────────▶ observability
          │         └──────────────────▶ governance / identity
          └────────────────────────────▶ conversation via SDK
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| shared bridge core | 平台无关桥接逻辑、映射、裁剪、审计 | Python(主) | 逻辑核心 |
| Mattermost adapter | plugin/bot 适配 | Python / 平台 SDK | 平台特化 |
| Telegram adapter | bot 与会话适配 | Python | 平台特化 |
| Slack adapter | app 与交互式消息 | TypeScript / Slack SDK | 平台特化 |
| Discord adapter | bot 与 guild/channel 适配 | Python | 平台特化 |
| mapping store | external_id 授权映射持久化 | local DB / service-backed | 受控持久化 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| Bridges → 平台服务 | SDK | 手写 RPC/HTTP | 保持契约、认证、trace 一致 |
| 外部平台 → adapter | 平台原生 SDK/webhook/event API | 通用抽象协议 | 外部平台差异大,需原生适配 |
| Gate 外显 | 简化卡片 / 交互按钮 | 纯文本消息 | 在不泄露敏感内容前提下保留基本可操作性 |
| 平台失败恢复 | 重试 / backlog / 延迟回写 | 静默丢弃 | 保证可追溯与可恢复 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| Conversation / Turn truth | conversation | bridges |
| ExternalMapping | bridges admin flow | bridge core / admins |
| BridgeAuditRecord | bridges | observability / auditors |
| Gate truth | governance | gate projection |

### 6.5 部署拓扑

- 按平台拆 adapter,共享 bridge core 与 mapping/audit 能力
- 可以单平台独立部署,也可以 monorepo 统一发布
- 不依赖端侧 UI 运行,本质上是生态层接入服务

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```text
platform adapters
      │
      ▼
shared bridge core
   ├─▶ mapping / authz
   ├─▶ turn translation
   ├─▶ gate projection
   └─▶ audit / rate control
           │
           ▼
      sdk-backed platform truth
```

### 7.2 层间约束规则

- platform adapters 不直接实现平台治理语义,只做平台协议适配
- bridge core 不直接持有 Conversation/Gate/Identity 真相,全部经 SDK 查询
- gate projection 只生成“可外显”的视图,不得泄漏敏感原文
- mapping store 的授权逻辑集中,不允许各平台各自偷建身份映射规则
- audit / rate control 失败不能静默吞掉关键桥接动作

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| ConversationBridgeAdapter | bridge core | SDK conversation adapter |
| IdentityMappingAdapter | bridge core | SDK identity + local mapping store |
| GateProjectionAdapter | bridge core | governance-backed gate renderer |
| PlatformTransport | platform abstraction | Mattermost/Telegram/Slack/Discord adapters |
| BridgeAuditSink | audit domain | observability adapter |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(多外部平台入口) |
| 传出耦合 | 高(conversation/governance/identity/observability/外部平台 SDK) |
| 不稳定性 | 中高 |
| 抽象度 | 中高(shared bridge core + platform adapters) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Conversation / Turn truth | conversation | bridges | 最终一致 | 外部延迟 |
| Gate truth | governance | bridges | 最终一致 | 裁剪错误 |
| GlobalMember truth | identity | bridges | 最终一致 | 映射陈旧 |
| ExternalMapping | bridges(admin-managed) | bridges | 强一致 | 错绑责任链 |
| BridgeAuditRecord | bridges | observability | append-only | 审计漏记 |

### 8.2 一致性层次

- Conversation/Gate/Identity 真相在平台服务端,Bridges 最终一致消费
- ExternalMapping 在桥接侧或受控配置侧强一致维护
- 外部平台消息回写与平台写入允许短时最终一致,但必须可追踪/可重放

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| 平台写入成功,外部回写失败 | 平台消息/回复未成功发送到外部平台 | backlog + retry + 标记 degraded | `bridge_event_id` |
| 外部消息进入成功,平台写入失败 | SDK/platform service 失败 | 拒绝确认并可重试 | `external_message_id` |
| Gate 渲染策略变化 | 高/低敏感分类切换 | 重新投影卡片,敏感项收紧 | `gate_id + platform` |
| external mapping 撤销 | 管理员 revoke | 后续消息全部拒绝 | `mapping_id` |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:shared core + platform adapters(当前) | 方案 B:每平台独立 Bot | 方案 C:只支持单平台 |
|---|---|---|---|
| 一致性 | 高 | 低 | 中 |
| 扩展性 | 高 | 中 | 低 |
| 实施复杂度 | 中 | 中 | 低 |
| 产品目标契合 | 高 | 中 | 低 |
| 审计/治理统一 | 高 | 低 | 中 |

### 10.2 最终选择与理由

选择 A,因为 Bridges 的价值不在“接了几个 Bot”,而在“把平台协作语义稳定、安全地延伸到外部生态”。B 会导致各平台行为严重漂移；C 又不满足产品矩阵的生态目标。A 是统一语义与平台差异之间的平衡点。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 重试 | 外部平台失败、限流、短时网络问题支持重试/backlog |
| 降级 | 高敏感 Gate 回平台、平台失败时外部提示受限状态 |
| 隔离 | 平台 adapter、mapping、gate view、audit/rate control 分层隔离 |
| 恢复 | 外部平台恢复后可基于 backlog 补发低优先级消息 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|
| 日志 | 外部入站消息、回写失败、限流命中、映射撤销、Gate 裁剪 |
| 指标 | 各平台成功率、延迟、重试次数、拒绝次数 |
| trace | external message → bridge core → SDK → conversation/governance/identity 链路可关联 |
| 健康检查 | 关注各平台 token 有效性、速率限制、adapter 可达性 |

### 11.3 安全

| 维度 | 落地 |
|---|---|
| 身份授权 | external_id 显式授权映射 |
| 凭据管理 | KMS/OAuth,不明文落盘 |
| Gate 裁剪 | 高敏感审批不在外部完整外显 |
| 审计 | 所有桥接动作与来源留痕 |

### 11.4 配置管理

| 维度 | 落地 |
|---|---|
| 外部化 | 平台 token、webhook、adapter enable/disable、sensitivity policy 外部化 |
| 环境隔离 | dev/staging/prod 使用不同平台 app/bot 配置 |
| 动态更新 | 平台接入开关、敏感 Gate 策略可热更新 |
| 配置五要素 | type / default / source / scope / constraints 明确 |

### 11.5 性能预算表

| 环节 | 预算 | 测量方式 | 来源依据 |
|---|---|---|---|
| 外部消息桥接主路径 | 样本流稳定可用 | E2E | 生态接入主路径 |
| 未授权拦截 | 100% | 安全测试 | 第三方治理硬约束 |
| 凭据安全 | 0 明文落盘 | 安全测试 | README |
| 四平台样本流 | 4/4 | E2E | README |

**端到端交付分解**(外部平台消息进入并回写结果):

```text
外部平台发言
 + 身份映射校验
 + 平台 Turn 写入
 + AI/平台处理
 + 外部回写回复
 + observability 留痕
```

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| 各平台限流策略未统一 | 影响稳定性 | P1 |
| bridged conversation lifecycle 同步未定 | 影响长期状态一致性 | P1 |
| 机器翻译是否纳入未定 | 影响跨语种体验 | P2 |
| 多平台运维与凭据轮换工具未展开 | 影响大规模接入效率 | P2 |

### 12.2 触发条件(可量化)

| 指标 | 阈值 | 动作 |
|---|---|---|
| 某平台失败/限流率显著升高 | > 阈值 | 强化该平台适配与退避策略 |
| 审计追溯缺失 | > 0 | 强化 audit sink 与桥接元数据 |
| 高敏感 Gate 错误外显 | > 0 | 收紧裁剪策略并审计回溯 |
| 多语种沟通需求持续增长 | > 2 个 Sprint | 设计受控翻译层 |

### 12.3 演进步骤

```text
阶段 1: Mattermost/Telegram/Slack/Discord 样本流与映射主路径跑通
   └─ 可停止点:外部消息桥接与低敏感审批成立

阶段 2: 限流/重试/审计与配置管理增强
   └─ 可停止点:桥接能力在真实团队中可稳定使用

阶段 3: 生命周期同步、多语种与更复杂平台能力扩展
   └─ 可停止点:Bridges 成熟为生态层稳定接入面
```

### 12.4 目标架构

Bridges 的目标架构不是“Bot 集合”,而是 **Quantalithos 受控触达层**:平台语义在这里被安全翻译到外部协作生态,用户得到低摩擦入口,而平台仍保有身份、治理与审计主权。未来扩展也必须围绕“平台真相优先、外部体验友好、敏感能力收紧、来源可追溯”四条主线。

## 13. 风险与待确认事项

### 13.1 常见风险

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 身份映射错配 | 中 | 高 | 显式授权 + 审计 + revoke |
| 平台适配差异过大 | 中 | 中 | shared core + ACL adapter |
| 外部平台限流/失败频繁 | 中 | 中 | per-platform rate control |
| 高敏感 Gate 泄漏 | 低 | 极高 | 裁剪硬约束 |

### 13.2 边缘风险

- 外部平台政策变化使接入被突然限制
- 多平台同时桥接同一会话造成一致性复杂度过高
- 用户期望 Bridges 承担完整 Chat 功能,导致产品边界被误解

| 高敏感 Gate kind 清单 | 批次 8 内 | Bridges + Governance |

## 14. 上线策略

### 14.1 灰度方案

```text
阶段 1: 单平台样本流(优先 Mattermost/Telegram 之一)
阶段 2: 扩展到四平台样本适配
阶段 3: 开启低敏感 Gate 外部处理
阶段 4: 强化审计、限流与组织级接入工具
```

### 14.2 回滚策略

| 触发条件 | 等级 | 回滚步骤 |
|---|---|---|
| 外部平台绕过 Gate/Policy | S 级 | 立即停用该平台桥接入口 |
| 敏感 Gate 被错误外显 | S 级 | 收紧渲染策略并回滚版本 |
| 身份映射错误广泛发生 | A 级 | 暂停映射写入,保留只读桥接 |
| 单平台适配严重失稳 | B 级 | 关闭单平台 adapter,不影响其他平台 |

### 14.3 监控指标

| 指标 | 阈值 | 告警方式 |
|---|---|---|
| 平台桥接失败率 | > 阈值 | warning |
| 未授权桥接尝试 | > 阈值 | security |
| 高敏感 Gate 裁剪异常 | > 0 | critical |
| 外部凭证异常 | > 阈值 | security |
| 四平台样本流失败 | > 阈值 | major |

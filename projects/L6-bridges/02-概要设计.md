## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L6-bridges` 不是 source truth 仓,也不是 marketplace 仓,更不是一堆第三方 API 适配脚本。它是 **“平台对外桥接层 / protocol-adapter product layer”**。

你可以把它理解成:
- 平台哪些内部对象、事件、产物、状态需要被桥接到外部系统
- 哪些桥接是输入桥、哪些是输出桥、哪些是双向同步桥
- 内部对象怎样被翻译成外部协议,外部协议又怎样被翻译回平台语义
- bridge status、delivery result、error translation、retry/replay 怎样被统一组织
- 外部系统和平台之间怎样形成稳定、可审计、可恢复的桥接关系

这些事情,都由 `L6-bridges` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L6-bridges`,这些对外桥接事实就会散落在:
- 各个 source system 自己写的一层 webhook/API/export 逻辑里
- `artifact` / `archive` 自己导出材料的脚本里
- `sync` 自己处理对外 fanout 的逻辑里
- `capability-hub` 自己对外接入 provider 或第三方系统的局部实现里
- 各种集成脚本、回调处理器和临时 connector 目录里

结果就会出现:
- 什么对象该桥接、桥给谁、按什么协议桥接没有统一主线
- 外部 schema 和内部模型的映射逐渐分叉
- retry/replay/resync、dead-letter-like failure、operator repair 分散实现
- bridge failure、delivery result 和外部回执没有统一证据链
- bridge 配置和 marketplace 生态配置、capability 接入配置混层

所以 `L6-bridges` 必须独立存在,作为:
> **把平台内部对象、事件、产物与状态安全、稳定、可追溯地映射并投送到外部协议和外部系统的桥接层。**

### 1.3 新人最容易混淆的几个词

#### BridgeMapping
就是:
> 某个内部对象与某个外部协议载荷之间的正式映射规则。

它不是源对象真相本体。

#### BridgeDelivery
就是:
> 一次正式桥接投送或桥接接收过程。

它不是 `L0-bus` 的 transport truth 本体。

#### ExternalEndpointStatus
就是:
> 外部系统回执给桥接层的成功/失败/超时/限流等状态。

它不是内部执行真相本体。

#### Resync / Replay
就是:
> 对桥接链路或桥接投送过程做的重放、补发或重新对齐。

它不是业务裁决重做。

#### PartnerConfig
就是:
> 针对某个对外系统或合作方的桥接配置、映射和策略。

它不是 marketplace transaction truth,也不是 source domain truth。

#### BridgeProjection
就是:
> 为外部系统消费或外部系统输入而构建的桥接投影视图。

它不是 source projection truth 本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L6-bridges/02` 时,先收稳以下前提:
- `L6-bridges` 不应按 API / webhook / export / adapter 横向平铺理解,而应按对外桥接主链责任拆
- bridges 至少应拆成“桥接对象识别与接入入口 / 协议映射与载荷转换 / 投送编排与交付结果 / 同步、回放与故障恢复 / 对外可见性与集成运维”五个主要部分
- bridges 自己拥有的真相不是 source truth、bus truth、capability contract truth 或 marketplace truth,而是 bridge mapping / bridge delivery / bridge replay / partner config / bridge diagnostics 这类桥接层真相
- `L6-bridges` 只能把内部对象和状态对外映射、投送和回收,不能替 source systems 持有正式领域真相
- 02 的重点不是“列有哪些第三方接口和协议名”,而是先把“桥接层在平台里到底是什么、和 bus/capability-hub/sync/artifact/archive/observability 怎么分层”讲清楚
- mapping、delivery、failure、replay、external diagnostics 这些不是零散 connector 技术点,而是 bridge 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的对外桥接心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,平台不只是内部自洽运行,还要和外部系统打通。用户真正需要的不是“能发 HTTP 请求”,而是:
- 哪些内部对象、事件、结果、证据应该被桥接出去
- 外部系统发回来的输入怎样被安全翻译回平台语义
- 桥接失败时,怎样知道是协议问题、投送问题、外部系统问题还是 source 侧问题
- operators 怎样 replay / resync / repair 一条对外桥接链路
- 外部集成是否健康、是否限流、是否产生了外部回执错误都能被统一看见

如果把这些逻辑分别散落到:
- 各个 source systems 的局部 adapter
- sync 层的额外分发逻辑
- artifact/archive 的导出脚本
- 运营或客户成功团队自己的对接脚本

系统会快速退化成:
- 桥接逻辑分散,无人能完整解释“为什么这条外部链路坏了”
- 同一种内部对象对不同外部系统的 schema 映射逐渐漂移
- replay / retry / repair 缺少统一证据链
- 外部系统状态和内部系统状态容易混淆
- 生态扩展和对外集成无法产品化

因此,本概要设计的任务就是:
> **把 `L6-bridges` 写成一个新人也能看懂的“平台对外桥接层”,而不是把各类外部协议适配散在各仓的边缘逻辑里。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| bridge 主线统一性 | 各仓局部适配风险高 | 单一桥接主线 | 需正式收敛 |
| schema 映射稳定性 | 多处映射易漂移 | mapping 可追溯率 100% | 需统一建模 |
| replay/resync 治理 | 脚本化风险高 | 正式化恢复主线 | 需形成控制链 |
| 外部投送可观测性 | 回执与失败分散 | delivery/diagnostic 可统一查询 | 需建立观察面 |
| partner/integration 边界 | 易与 marketplace/hub 混层 | 单一桥接层口径 | 需写死边界 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何让平台内部对象、事件和结果能够稳定、安全、可诊断地对接外部系统,同时不破坏平台内部真相边界
- **技术问题**:BridgeMapping、BridgeDelivery、ProtocolAdapter、Replay/Resync、PartnerConfig 与 bus / capability-hub / sync / artifact / archive / observability 之间的边界如何稳定建模,并形成统一桥接主链

## 4. 约束条件

### 4.1 技术约束

- 所有桥接都必须以正式 BridgeRequest / BridgeMapping / BridgeDelivery 主线进入
- 外部 schema 与内部模型必须显式映射,不能依赖隐式字段兼容
- replay / resync 只能重做桥接与投送过程,不能改写 source truth
- partner config / endpoint config 必须和 capability contract / marketplace truth 分层
- outbound / inbound / bidirectional 桥都必须留 delivery 与 error translation 证据

### 4.2 资源约束

- 不同 external systems、协议和 partner config 数量会持续增长,映射复杂度必须受控
- bridge backlog、failure、retry 历史会长期累积,必须接受 append-only 证据链增长
- 协议转换和外部投送不能拖垮 source systems

### 4.3 时间约束

- 当前阶段先收稳统一桥接主线,而不是先做复杂多协议网关编排或高级生态运营
- mapping、delivery、failure、replay、diagnostic 五条基础链必须优先稳定,否则后续 L6 接入会长期失控

### 4.4 合规约束

- 桥接层不得反写 source truth 本体
- replay / resend / resync 必须留审计证据链
- 外部 payload 不得越权获得内部未授权字段
- export/bridge output 不得伪装成 archive/artifact/source truth 本体

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| bridge tasks/day | 高频 | 多 source 多 partner 集成需求 |
| protocol mappings | 中高 | 多系统多版本协议演进 |
| delivery histories | 高频 | 所有外部投送/回执记录 |
| replay/resync jobs | 中高 | 失败和补偿需求 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ bus / source systems        │
                    │ hub / sync / artifact       │
                    │ archive / observability     │
                    └────────────┬───────────────┘
                                 │ bridge source input
                                 ▼
                    ┌────────────────────────────┐
                    │ L6-bridges                 │
                    │ - mapping / delivery       │
                    │ - replay / diagnostics     │
                    └────────────┬───────────────┘
                                 │ bridge output / external result
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ external systems / partners│   │ operators / integration    │   │ observability              │
│ - inbound / outbound       │   │ - repair / inspect         │   │ - bridge health            │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L6-bridges` 自己负责桥接对象识别、协议映射、投送编排、回执处理、恢复与桥接诊断主线
- `L0-bus`、`capability-hub`、`sync`、`artifact`、`archive`、`runtime` 等系统提供 bridge source inputs,但 bridges 不拥有它们的源真相
- external systems / partners 是 bridge 的最终消费方或输入方
- operators / integration owners 通过 bridges 理解桥接状态并处理失败、重放和修复
- 这个仓的角色不是“定义领域真相”,而是“定义平台和外部世界的安全映射与桥接流程”

所以 `L6-bridges` 在全局里的角色是:
> **把平台内部对象、事件、产物与状态安全、稳定、可追溯地映射并投送到外部协议和外部系统的桥接层。**

### 5.3 系统边界

**做什么**:
- 定义桥接入口和桥接目标
- 定义协议映射与载荷转换
- 管理 outbound / inbound / bidirectional bridge delivery
- 管理 replay / resync / repair / diagnostics
- 输出 partner / integration 可见状态与错误解释

**不做什么**:
- 不持有 source truth 本体
- 不替代 L0-bus transport truth
- 不替代 capability contract / marketplace truth
- 不替代第三方系统或底层网关平台本体

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| bus / source refs | 99.95% | backlog / replay,不伪造 bridge delivery 成功 |
| external endpoints | 99.9% | retry / backoff / resync,但不隐藏失败状态 |
| capability-hub / sync / archive | 99.9% | 某项输入缺失时阻断对应桥接,不伪造成功结果 |
| observability | 99.9% | 诊断面延迟时保留 bridge 主线和最小错误提示 |
| operators / integration repair entry | 99.9% | repair 不可用时保留 bridge status 和 replay backlog |

### 5.5 关键依赖风险

- protocol mapping 与 source truth 漂移会导致桥接数据失真
- delivery result 若和 external endpoint 状态混层,会造成错误恢复判断
- replay/resync 若无证据链,operators 无法区分“已补发”与“已修复”
- partner config 若与 marketplace/hub 混层,会污染生态边界
- external failure 若未统一翻译,不同桥会给出矛盾错误语义

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把 API / webhook / export / adapter 技术接口横向平铺。  
> 它按 **对外桥接主链职责 + 入口 / 映射 / 交付 / 恢复 / 诊断差异** 来拆分。  
> 因此下面每一部分都可能包含多个桥接对象和机制,共同支撑同一段 bridges 主链。

#### 桥接对象识别与接入入口部分

- **它是什么**: 这是 `L6-bridges` 的主入口层,一起回答“什么要被桥接、桥到哪”
- **为什么单独有它**: 如果没有统一 bridge task 入口层,source object、target endpoint、direction、adapter 逻辑会直接混成一锅
- **负责什么**:
  - 接收 bridge request / source refs / target refs
  - 区分 inbound / outbound / bidirectional bridge
  - 创建正式桥接任务锚点
- **不负责什么 / 容易混淆点**:
  - 不持有 source truth 本体
  - 不持有 transport truth 本体
  - 不直接执行载荷转换
  - 最容易和 source object truth、消息总线事件、marketplace config 混淆
- **与其他部分交互**:
  - 下游: 协议映射、交付结果、恢复与诊断
  - 外部: bus / source systems / partner configs
  - 交互类型: bridge entry 型 + source/target anchor 型
- **后续详细设计展开点**:
  - BridgeRequest / BridgeTarget / direction 模型

#### 协议映射与载荷转换部分

- **它是什么**: 这是 bridges 的翻译层,一起回答“内部对象怎样变成外部协议”
- **为什么单独有它**: schema mapping 是桥接中最容易和领域模型混层的部分,必须从 dispatch 和 retry 逻辑里拆出来
- **负责什么**:
  - 定义 protocol adapter
  - 定义 schema mapping / field normalization / version compatibility
  - 构建 outbound/inbound payload
- **不负责什么 / 容易混淆点**:
  - 不持有 source domain truth
  - 不替代 partner/external schema 真相本体
  - 不负责投送成功与否
  - 最容易和 domain model、本地 DTO、source projection truth 混淆
- **与其他部分交互**:
  - 上游: bridge entry / source refs
  - 下游: dispatch / diagnostics / replay
  - 交互类型: payload translation 型 + schema compatibility 型
- **后续详细设计展开点**:
  - BridgeMapping / ProtocolAdapter / payload builder 主线

#### 投送编排与交付结果部分

- **它是什么**: 这是桥接的交付主线层,一起回答“桥接怎样被真正送出去和回执回来”
- **为什么单独有它**: 成功/失败/ack/timeout/duplicate 都在这一层发生,如果不单列会与 mapping 或 repair 混层
- **负责什么**:
  - 管理 outbound/inbound dispatch
  - 管理 ack / delivery result / timeout / duplicate detection
  - 形成正式交付结果记录
- **不负责什么 / 容易混淆点**:
  - 不等于 bus truth
  - 不等于 external endpoint 真相本体
  - 不负责 replay/resync 修复本体
  - 最容易和 transport layer、scheduler、source queue 真相混淆
- **与其他部分交互**:
  - 上游: 协议映射与载荷转换部分
  - 下游: 同步/回放与故障恢复、诊断/运维
  - 交互类型: delivery/ack 型 + error translation 型
- **后续详细设计展开点**:
  - delivery result / ack / duplicate / timeout 主线

#### 同步、回放与故障恢复部分

- **它是什么**: 这是 bridges 的恢复层,一起回答“桥接失败、乱序、断链时怎样修复”
- **为什么单独有它**: 外部世界不可靠,如果 replay/resync/reconcile 不被单列,会退化成 connector 脚本和手工修补逻辑
- **负责什么**:
  - 管理 replay / resend / resync / reconcile
  - 管理 bridge backlog / dead-letter-like failures / operator repair
  - 形成统一恢复证据链
- **不负责什么 / 容易混淆点**:
  - 不重做业务裁决真相
  - 不直接改写 source truth 本体
  - 不替代 archive/observability 正式证据真相
  - 最容易和 source rollback、业务重放、sync 本体修复逻辑混淆
- **与其他部分交互**:
  - 上游: delivery results / diagnostics
  - 下游: partner visible state / operators / observability
  - 交互类型: replay/recovery 型 + operator repair 型
- **后续详细设计展开点**:
  - ReplayRequest / ResyncTicket / RepairEntry 模型

#### 对外可见性与集成运维部分

- **它是什么**: 这是 bridges 的消费面层,一起回答“用户和操作者怎样看桥接是否健康”
- **为什么单独有它**: bridge 层不是黑盒,必须能看见 bridge health、error、partner config summary 与恢复状态
- **负责什么**:
  - 提供 integration status / partner config summary / diagnostics / failure reason views
  - 提供 operators repair 入口与 bridge health 面
  - 提供 error translation 和可见恢复状态
- **不负责什么 / 容易混淆点**:
  - 不持有 observability truth 本体
  - 不替代 marketplace partner truth
  - 不直接执行 repair 结果本体
  - 最容易和 partner config 真相、source metrics、本地监控页混淆
- **与其他部分交互**:
  - 上游: delivery / replay / diagnostics
  - 下游: operators / integration owners / observability / external support
  - 交互类型: bridge health 型 + operator diagnostics 型
- **后续详细设计展开点**:
  - integration health / diagnostics / partner config view 主线

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ bus / source systems        │
                    │ hub / sync / artifact       │
                    │ archive / observability     │
                    └────────────┬───────────────┘
                                 │ bridge source input
                                 ▼
                    ┌────────────────────────────┐
                    │ L6-bridges                 │
                    │ - mapping / delivery       │
                    │ - replay / diagnostics     │
                    └────────────┬───────────────┘
                                 │ bridge output / external result
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ external systems / partners│   │ operators / integration    │   │ observability              │
│ - inbound / outbound       │   │ - repair / inspect         │   │ - bridge health            │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L6-bridges` 自己负责“识别桥接对象”“翻译协议”“管理交付结果”“组织 replay/resync/repair”“提供桥接健康和诊断视图”
- `L0-bus` / source systems / capability-hub / sync / artifact / archive 的交互主要落在 **桥接对象识别与接入入口部分** 与 **协议映射与载荷转换部分**,为 bridges 提供 source refs 和桥接输入
- external systems / partners 的交互主要落在 **投送编排与交付结果部分**,接收 outbound bridge 或返回 inbound 回执
- operators / integration owners 的交互主要落在 **同步、回放与故障恢复部分** 与 **对外可见性与集成运维部分**,消费桥接状态、失败原因和修复入口
- observability 消费的是 bridges 产生的 diagnostics 和健康材料,而不是 bridges 的 source truth 本体

### 7.3 分模块交互说明(逐个写)

#### 与 `bus / source systems` 的交互

```text
┌────────────────────────────┐
│ bus / source systems       │
│ - source events / refs     │
└────────────┬───────────────┘
             │ bridge intake input
             ▼
┌────────────────────────────┐
│ bridges                    │
│ - BridgeRequest            │
│ - BridgeMapping            │
└────────────────────────────┘
```

- 这些系统是 **桥接来源方**
- **交互类型**: source change / source ref 输入型交互
- **主流程位置**: source object updated、event emitted、export required、callback received 时进入主流程
- **交互解释**:
  - bridges 只消费 source refs 与 source materials
  - 不替代 source truth 或 bus truth 本体
- **高风险异常流**:
  - 桥接 payload 被误当 source truth 本体
- 后续 `03-详细设计.md` 继续展开:
  - BridgeRequest contract
  - mapping/intake 主线

#### 与 `external systems / partners` 的交互

```text
┌────────────────────────────┐
│ bridges                    │
│ - delivery / replay / ack  │
└────────────┬───────────────┘
             │ bridge output/input
             ▼
┌────────────────────────────┐
│ external systems / partners│
│ - receive / callback / ack │
└────────────────────────────┘
```

- 它们是 **桥接目标方和回执来源方**
- **交互类型**: outbound/inbound delivery 型交互
- **主流程位置**: payload dispatch、ack 返回、error translation、retry/backoff 时进入主流程
- **交互解释**:
  - bridges 负责稳定发送和接收桥接结果
  - 外部回执只是桥接结果,不等于内部执行真相
- **高风险异常流**:
  - 外部 endpoint status 被误当 internal execution truth
- 后续 `03-详细设计.md` 继续展开:
  - delivery result / ack / timeout 主线

#### 与 `operators / integration owners` 的交互

```text
┌────────────────────────────┐
│ bridges                    │
│ - status / conflict / replay│
└────────────┬───────────────┘
             │ repair/inspect output
             ▼
┌────────────────────────────┐
│ operators / owners         │
│ - replay / resync / repair │
└────────────────────────────┘
```

- 这些系统和角色是 **修复与诊断消费方**
- **交互类型**: repair/inspect consume 型交互
- **主流程位置**: failed / timeout / dead-letter-like failure / replay / resync 时进入主流程
- **交互解释**:
  - bridges 给出统一修复入口、恢复记录和桥接健康面
  - 不替代 source systems 的正式修复结果真相
- **高风险异常流**:
  - replay/resync 被误认为 source truth 已被改写
- 后续 `03-详细设计.md` 继续展开:
  - repair entry / recovery record contract

### 7.4 本节与详细设计的边界

本节只定义:
- 模块之间的交互方向
- 每条交互里传递的核心语义
- 哪个模块是真相源、哪个模块是桥接层、哪个模块是外部回执方、哪个模块是修复/诊断消费方

本节**不**展开:
- webhook / API / file export 的底层实现细节
- schema evolution 兼容算法细节
- retry/backoff 调度实现细节
- partner onboarding / marketplace 合作流程细节
- observability dashboard 实现细节

这些内容留到 `03-详细设计.md` 中继续展开。

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 BridgeRequest / BridgeTarget / BridgeMapping / ProtocolAdapter / BridgeDelivery / DeliveryResult / ReplayRequest / ResyncTicket / IntegrationStatus 等桥接层真相
- 把 source systems 的对象、事件、产物和状态安全映射为外部协议载荷,并稳定完成 outbound / inbound / bidirectional delivery
- 统一记录 ack / timeout / duplicate / replay / repair / diagnostics 证据链
- 为 operators / integration owners / observability 提供 bridge status、failure reason、partner config summary 与恢复入口

**本模块不做什么**:
- 不持有 source truth 本体
- 不替代 L0-bus transport truth、capability-hub contract truth、marketplace transaction truth 或第三方系统本体
- 不重做业务裁决真相
- 不把 bridge output 反写为 archive/artifact/source truth 本体

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 bridges“为什么存在”,而是让开发者可以直接开始实现:
- source objects / source events 如何进入正式 BridgeRequest 主线
- internal schema 怎样被稳定翻译为 external payload
- outbound / inbound delivery 怎样记录 delivery result、ack、timeout、duplicate
- replay / resync / repair 怎样在不改写真相的前提下恢复桥接链路
- integration health / diagnostics / partner status 怎样面向 operators 和 external integrations 提供统一解释面

如果不先把这些内容采集清楚,03 很容易退化成:
- webhook / API 接口清单
- payload 字段 mapping 表
- 重试和回调脚本说明
- 每个桥各自一套 delivery / repair 逻辑,彼此不一致

- `L6-bridges` 是平台对外桥接层,不是 source truth 仓、总线仓或 marketplace 仓

- 与 `bus / capability-hub / sync / artifact / archive / observability / external systems` 的真相边界已经清楚

#### 第 1 步:列出要实现的核心对象

本仓 03 先按五组对象理解:
- 桥接入口对象: BridgeRequest / BridgeTarget / BridgeDirection / SourceBridgeRef / ExternalEndpointRef

#### 第 2 步:列出主流程与关键异常流

主流程至少有三条:
- source material → BridgeRequest → protocol mapping 主线
- mapped payload → outbound/inbound delivery → ack/result 主线
- failure/timeout/duplicate → replay/resync/repair → integration diagnostics 主线

关键异常流至少包括:
- source refs 存在但 mapping 版本不匹配
- payload 已映射成功但 delivery 未建立正式记录
- external endpoint 返回 200 但 payload 语义被拒收
- replay 发生后无 delivery history / failure history 对账链
- partner config 修改后旧 endpoint 仍被继续发送
- bridge sync 与 sync 层状态冲突,用户无法判断谁才是权威解释

#### 第 3 步:列出要落库/持久化的对象与关系

必须先分清:
- 哪些是写模型: bridge_requests / bridge_targets / bridge_mappings / bridge_deliveries / delivery_results / bridge_failures / replay_tickets / partner_configs
- 哪些是只读视图: bridge_status_view / partner_config_view / failure_reason_view / delivery_history_view / bridge_health_view
- 哪些是 append-only: ack history / replay history / repair history / timeout history / duplicate history
- 哪些输入只能作为来源引用,不能反向变成 source truth、bus truth 或 marketplace truth 本体

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 bus / source systems / sync / capability-hub / artifact / archive
- 哪些输出给 external systems / operators / observability
- 哪些回执是桥接结果,哪些只是外部系统局部成功信号
- 哪些 repair / replay / resync 只重做桥接过程,不能重写 source truth

#### 第 5 步:列出最小测试输入

必须测:
- BridgeMapping ≠ source truth
- bridge delivery ≠ bus truth
- external endpoint status ≠ internal execution truth
- Protocol translation ≠ domain model truth
- Bridge retry/replay ≠ replay business decision
- partner/integration config ≠ marketplace truth
- intake / mapping / delivery / recovery / diagnostics 五条主链成立

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `BridgeRequest / BridgeMapping / DeliveryResult / ReplayRequest / IntegrationStatus` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是统一桥接主链,`03` 却退化成 webhook/API/export 的接口清单
- 实现者知道有 replay/resync,却不知道它如何与 mapping、delivery、failure、ops 形成同一条恢复主线
- 入口、映射、交付、恢复、诊断各写一套,彼此断裂

```rust
/// 表示一次正式桥接请求。
pub struct BridgeRequest {
    /// 桥接请求标识。
    pub bridge_request_id: BridgeRequestId,
    /// 来源引用。
    pub source_ref: SourceBridgeRef,
    /// 目标桥接对象。
    pub target: BridgeTarget,
    /// 桥接方向。
    pub direction: BridgeDirection,
}

/// 表示桥接目标。
pub struct BridgeTarget {
    /// 目标系统名称。
    pub target_system: String,
    /// 目标 endpoint 摘要。
    pub endpoint_ref: ExternalEndpointRef,
}

/// 表示来源对象引用。
pub struct SourceBridgeRef {
    /// 来源系统名称。
    pub source_system: String,
    /// 来源对象引用。
    pub source_ref: String,
}

/// 表示外部 endpoint 引用。
pub struct ExternalEndpointRef {
    /// endpoint 标识。
    pub endpoint_id: ExternalEndpointId,
    /// endpoint 摘要。
    pub endpoint_summary: String,
}

/// 表示桥接方向。
pub enum BridgeDirection {
    Inbound,
    Outbound,
    Bidirectional,
}
```

这些对象在该部分里分别承担:
- `BridgeRequest` 负责统一桥接任务入口
- `BridgeTarget` 负责表达桥接目标
- `SourceBridgeRef` 负责回指来源对象
- `ExternalEndpointRef` 负责表达对外 endpoint 引用
- `BridgeDirection` 负责统一桥接方向语言

#### 5.2.4 关键函数代码片段

```rust
/// 根据 source refs 和目标 endpoint 创建正式桥接请求。
fn create_bridge_request(
    intake_repo: &dyn BridgeIntakeRepo,
    input: CreateBridgeRequestInput,
) {
    // [input.校验桥接入口边界]
    // 先确认桥接层只消费 source refs 和目标配置,不替代 source truth 本体。
    input.validate_bridge_entry_boundary();

    // [BridgeRequest::从输入创建]
    // 再把来源对象、目标 endpoint 和桥接方向收束成正式桥接请求。
    let request = BridgeRequest::from_input(input);

    // [intake_repo.保存桥接请求]
    // 最后把 bridge request 写入桥接层,供 mapping/delivery/replay 主线消费。
    intake_repo.save_request(request);
}
```

这段实现守住的边界是:
- bridge request 只是桥接过程入口,不替代 source truth
- source refs 和 target refs 必须先稳定,后续映射与交付才有共同锚点
- 桥接方向描述传输关系,不改变对象所有权

#### 5.2.5 该部分的边界与非职责
- 不持有 source truth 本体
- 不直接做 schema/payload 映射
- 不负责 delivery 成功与否
- 不替代 partner config 真相本体

#### 5.2.6 该部分与其他主要部分的接缝
- 向 `协议映射与载荷转换部分` 提供 request / source refs / target refs 输入
- 向 `投送编排与交付结果部分` 提供 bridge request 锚点
- 向 `同步、回放与故障恢复部分` 提供 replay/resync 重建入口基线

#### 5.2.7 该部分的状态 / 约束 / 易错点
- `BridgeMapping ≠ source truth` 必须写死
- `bridge direction ≠ object ownership` 必须写死
- 若 source/target refs 不稳定,后续 mapping 和 replay 都会失锚

#### 5.3.4 关键函数代码片段

```rust
/// 根据 bridge request 和 source refs 构建正式桥接载荷。
fn build_bridge_payload(
    mapping_repo: &dyn BridgeMappingRepo,
    request: BridgeRequest,
) {
    // [request.校验映射来源边界]
    // 先确认 source refs 只是映射输入,不会被协议层反向改写。
    request.validate_mapping_source_boundary();

    // [BridgeMapping::从请求创建]
    // 再把 source refs 和 target protocol 收束成正式映射规则和载荷包络。
    let mapping = BridgeMapping::from_request(request);

    // [mapping_repo.保存映射和载荷]
    // 最后把 mapping/payload 写入桥接层,供 delivery/replay/diagnostics 主线消费。
    mapping_repo.save_mapping(mapping);
}
```

这段实现守住的边界是:
- 映射层只翻译 source refs,不持有 domain model truth
- payload envelope 只是桥接载荷,不等于 source object 本体
- schema version 与 translation rules 必须显式存在,不能靠隐式兼容

#### 5.3.5 该部分的边界与非职责
- 不持有 source domain truth 本体
- 不负责投送成功与失败结果
- 不替代 external schema 真相本体
- 不执行 replay/resync 本体

#### 5.3.6 该部分与其他主要部分的接缝

## 8. 运行期主线场景

### 8.1 场景 A · source 变化被正式桥接到外部协议

```text
Source refs ready
   │
   ▼
BridgeRequest created
   │
   ▼
BridgeMapping + PayloadEnvelope built
   │
   ▼
BridgeDelivery dispatched
```

**开发者关注点**:
- request 和 source refs 是否稳定绑定
- schema/mapping 是否可追溯
- delivery 是否在桥接层内形成正式记录

### 8.2 场景 B · 外部系统回执与桥接状态形成统一交付链

```text
Delivery dispatched
   │
   ├─▶ ACK received
   ├─▶ timeout recorded
   └─▶ duplicate detected
          │
          ▼
DeliveryResult / IntegrationStatus updated
```

**开发者关注点**:
- 外部回执是否只被解释为 bridge delivery 结果
- failure/timeout/duplicate 是否都能进入统一历史链
- partner health 是否可读可诊断

### 8.3 场景 C · 失败桥接进入 replay/resync/repair 主线

```text
Delivery failed
    │
    ▼
BridgeFailureRecord created
    │
    ▼
ReplayRequest / ResyncTicket / RepairEntry created
    │
    ▼
operators recover bridge with evidence
```

**开发者关注点**:
- replay/resync 是否只重做桥接过程
- recovery 是否始终带 ticket 和失败上下文
- 恢复之后 diagnostics 是否能正确刷新

### 8.4 外部交互入口归属

| 外部来源 | 进入入口 | 落到哪个主要部分 | 结果 |
|---|---|---|---|
| bus / source systems / source refs | CreateBridgeRequest / ResolveBridgeTarget | 桥接对象识别与接入入口部分 | 形成正式 bridge request |
| source refs / target protocol | BuildBridgePayload / ResolveProtocolAdapter | 协议映射与载荷转换部分 | 形成正式桥接载荷 |
| external systems / callbacks | DispatchBridge / RecordAck / RecordTimeout | 投送编排与交付结果部分 | 形成 delivery / result / ack 记录 |
| failed / timeout / duplicate | TriggerReplay / TriggerResync / CreateRepairEntry | 同步、回放与故障恢复部分 | 形成 replay/resync/repair 主线 |
| operators / observability | BuildIntegrationStatus / BuildFailureReasonView | 对外可见性与集成运维部分 | 形成 status / diagnostics / health 视图 |

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| source refs 缺失 | 拒绝创建 bridge request |
| schema version 不匹配 | 阻断 payload 构建 |
| delivery timeout / duplicate | 记录 failure 并进入 replay/resync 候选 |
| external ack 缺失 | 标记 timeout / stale 并留历史 |
| replay/resync 缺失败上下文 | 阻断恢复并标 context missing |
| partner config 与实际 endpoint 漂移 | 标记 diagnostics conflict |

### 11.1 重试 / 降级 / 熔断 / 补偿
- external endpoint 短暂失败时可重试/backoff,但不得隐藏失败状态
- partner status 读取失败时可保留上次可见摘要并标 stale
- replay/resync 失败时可重复触发,但必须保留所有 recovery history

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 桥接对象识别与接入入口部分 | source refs 缺失 / target 配置非法 | bridge entry boundary validate | 拒绝建任务 | 修正 refs 后重试 |
| 协议映射与载荷转换部分 | schema 漂移 / 字段翻译失效 | mapping source boundary validate | 阻断 payload 构建 | 升级 mapping/version |
| 投送编排与交付结果部分 | delivery 超时 / duplicate / ack 缺失 | delivery boundary validate | 标记 failure/timeout | replay/resync |
| 同步、回放与故障恢复部分 | replay 无票据 / repair 无证据链 | bridge recovery boundary validate | 阻断恢复 | 重建 recovery context |
| 对外可见性与集成运维部分 | status/health 与真实 delivery 不一致 | ops source boundary validate | 重建投影并告警 | replay diagnostics rebuild |

## 14. 最小可运行闭环

- 一条内部 source change 被正式识别为 BridgeRequest,并通过明确的 ProtocolAdapter 映射为外部 payload
- 一次 outbound delivery 成功或失败后,bridges 能形成正式 DeliveryResult / FailureReasonView,并对 operators 提供可解释状态
- 当桥接失败时,operators 能通过 ReplayRequest / ResyncTicket / RepairEntry 发起恢复,而不会改写 source truth,同时所有恢复动作都有统一证据链

## 15. 结论

本详细设计的核心结论是：
- `L6-bridges` 的实现主轴必须按 intake / mapping / delivery / recovery / diagnostics 五个主要部分组织,而不是按 webhook/API/export 适配器平铺
- bridges 真相层只持有桥接请求、协议映射、交付结果、恢复票据和诊断视图,不接管 source truth、bus truth、marketplace truth 或 capability contract truth
- 所有 BridgeRequest、BridgeDelivery、ReplayRequest、FailureReasonView、IntegrationStatus 都必须建立在稳定 source refs、映射版本和 append-only delivery/recovery 证据链之上

后续测试与验收文档,应直接围绕这套统一桥接主链、协议转换边界、交付结果解释和恢复主线展开.

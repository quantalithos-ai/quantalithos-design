### 读前说明 · 测试方案标准生产流程

`05-测试方案` 不是从“想到哪些 case 就列哪些 case”开始写,而是从 `02/03` 已冻结的结构、状态机、交互边界和高风险接缝反推测试方案。

建议按以下流程产出:
1. **先收输入**
   - 读取 `00-需求文档.md`、`01-架构设计.md`、`02-概要设计.md`、`03-详细设计.md`
   - 抽取:主要部分、主流程、状态机、非法转换、协议、异常流、最小可运行闭环
2. **再识别测试对象**
   - 分清对象级、函数级、流程级、边界级、协议级测试对象
3. **按主要部分分组**
   - 每个主要部分先列: 必测对象 / 必测函数 / 必测状态流 / 必测异常流
4. **再按测试层级细化**
   - 单元测试 / 集成测试 / 事件链测试 / 恢复测试 / 投影一致性测试 / 端到端主线测试
5. **最后补执行方案**
   - 测试数据、环境依赖、串行执行顺序、CI 门禁、证据归档路径

> 先按“主要部分 + 风险边界”组织,再按测试层级展开,不要反过来只按技术类型罗列测试。

## 1. 测试目标与范围

### 1.1 测试目标

本轮测试的目标不是单纯证明 bridges“能发一个 webhook / API 请求”,而是系统验证 `L6-bridges` 是否真正满足“平台对外桥接层 / protocol-adapter product layer”的设计要求,尤其要证明以下几点成立:
- BridgeRequest / BridgeMapping / BridgeDelivery / ReplayRequest / IntegrationStatus 构成正式桥接体验层真相
- `BridgeMapping ≠ source truth`、`bridge delivery ≠ bus truth`、`external endpoint status ≠ internal execution truth`、`Protocol translation ≠ domain model truth` 等核心边界成立
- request → mapping → delivery → replay/recovery → diagnostics 五条桥接主线可以统一组织,并且 source refs 持续可追溯
- outbound / inbound / bidirectional delivery 的成功/失败/ack/timeout/duplicate 都能被一致表达
- replay / resend / resync / repair 只重做桥接过程,不重做业务裁决或改写 source truth
- partner/integration status、config summary、failure reason 始终只是可见诊断层,不会冒充 marketplace 或 observability 真相

### 1.2 测试范围 / 非范围

| 范围项 | 类型 | 优先级 | 说明 |
|---|---|---|---|
| 桥接对象识别与接入入口部分 | bridge entry 对象 | P0 | BridgeRequest、BridgeTarget、BridgeDirection、SourceBridgeRef、ExternalEndpointRef |
| 协议映射与载荷转换部分 | mapping/payload 对象 | P0 | BridgeMapping、ProtocolAdapter、PayloadSchemaVersion、FieldTranslationRule、PayloadEnvelope |
| 投送编排与交付结果部分 | delivery/ack 对象 | P0 | BridgeDelivery、DeliveryResult、DeliveryAck、TimeoutRecord、DuplicateMarker |
| 同步、回放与故障恢复部分 | replay/recovery 对象 | P0 | ReplayRequest、ResyncTicket、RepairEntry、BridgeFailureRecord、DeadLetterLikeBridgeRecord |
| 对外可见性与集成运维部分 | diagnostics/ops 对象 | P0 | IntegrationStatus、PartnerConfigSummary、FailureReasonView、BridgeHealthView、DeliveryHistoryView |
| source truth、L0-bus transport truth、capability-hub contract truth、marketplace truth、第三方系统本体 | 非范围 | P2 | 只验 bridges 如何消费 source inputs 并组织桥接体验,不验底层 source truths 或第三方系统全部实现 |
| 底层网关、scheduler、重试库本体 | 非范围 | P2 | 只验桥接层的 request/mapping/delivery/recovery/diagnostics 语义,不验底层基础设施实现 |
| 业务裁决与业务回滚逻辑 | 非范围 | P2 | 只验 bridges 的 replay/resync 不越界,不验业务决策链本体 |

## 2. 测试策略与分层

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|---|---|---|---|---|
| 单元测试 | 验证对象成员函数与局部不变量 | domain / integration owner | `input.validate_bridge_entry_boundary`、`request.validate_mapping_source_boundary`、`payload.validate_delivery_boundary`、`failure.validate_bridge_recovery_boundary`、`input.validate_ops_source_boundary` | 边界与不变量符合设计 |
| 集成测试 | 验证 service + repo + adapter + projection + publisher 联动 | backend / integration owner | `CreateBridgeRequest`、`BuildBridgePayload`、`DispatchBridge`、`RecordAck`、`RecordTimeout`、`TriggerReplay`、`TriggerResync`、`BuildIntegrationStatus` | intake、mapping、delivery、recovery、diagnostics 五条主线同时成立 |
| 事件链测试 | 验证上下游接缝链 | integration / platform owner | bus/source → bridge request、mapped payload → external endpoints、delivery result → ops/obs、replay/resync → bridge state refresh | 输入输出语义一致 |
| 恢复专项测试 | 验证 source refs 缺失、schema 漂移、delivery timeout、duplicate、replay 缺上下文、partner config 漂移等异常链 | architecture / QA | invalid refs、schema mismatch、timeout/duplicate、context missing、config drift | 桥接不误导、错误被正确阻断或留证 |
| 投影一致性测试 | 验证 bridge status / failure / health / partner view 与交付主链一致 | backend / QA | status view rebuild、failure view rebuild、health view rebuild、partner summary rebuild | 投影只读且与主链一致 |
| 端到端主线测试 | 验证最小桥接体验闭环 | QA / owner | request → mapping → delivery → ack/fail → replay/resync → diagnostics | bridge 体验闭环跑通 |

## 3. 需求追溯与覆盖矩阵

| 需求/规则 | 测试场景 | 测试层级 | 自动化 | 证据 |
|---|---|---|---|---|
| `BridgeMapping ≠ source truth` | 桥接映射只翻译 source refs,不反写源真相 | 单元 + 集成测试 | 是 | mapping/source compare |
| `bridge delivery ≠ bus truth` | 桥接交付只表达外部交付过程,不替代 transport truth | 单元 + 集成测试 | 是 | delivery/bus compare |
| `external endpoint status ≠ internal execution truth` | 外部回执只能解释 bridge 结果,不替代内部执行真相 | 单元 + 事件链测试 | 是 | endpoint/runtime compare |
| `Protocol translation ≠ domain model truth` | schema/field translation 不得反向污染 domain model | 单元 + 集成测试 | 是 | payload/model compare |
| `Bridge retry/replay ≠ replay business decision` | replay/resync 只重做桥接过程,不重做业务裁决 | 单元 + 恢复测试 | 是 | replay/decision separation |
| `partner/integration config ≠ marketplace truth` | partner 摘要只表达集成配置可见层 | 单元 + 集成测试 | 是 | partner summary / marketplace compare |
| ack / timeout / duplicate 可统一表达 | 外部回执结果一致进入桥接交付主线 | 集成 + 事件链测试 | 是 | ack/timeout/duplicate logs |
| replay/resync/repair 可追溯 | 恢复入口始终带 ticket 与 history | 集成 + 恢复测试 | 是 | replay/resync/repair history |
| diagnostics / health 可回指 delivery refs | 运维诊断可回放与对账 | 集成 + 投影一致性测试 | 是 | diagnostics refs compare |

## 4. 环境与配置矩阵

| 环境 | 用途 | 依赖 | 关键配置 | 风险 |

| staging | 端到端演练 | real-like source refs / bridge adapters / partner configs / operator dry-run | replay/resync/repair evidence enabled / stale markers visible | 多 partner、多协议时序差异放大 |

## 6. 核心测试场景

| 场景 ID | 场景 | 前置条件 | 步骤摘要 | 预期结果 |
|---|---|---|---|---|
| TC-001 | CreateBridgeRequest 成功创建正式桥接请求 | source refs / target / direction 合法 | CreateBridgeRequest | BridgeRequest 创建成功 |
| TC-002 | source refs 缺失时阻断桥接请求 | source_ref 缺失或非法 | CreateBridgeRequest | 返回 `BRIDGE_SOURCE_REF_INVALID` |
| TC-003 | BuildBridgePayload 成功构建正式映射载荷 | request 已存在 + schema 兼容 | BuildBridgePayload | BridgeMapping / PayloadEnvelope 创建成功 |
| TC-004 | schema 漂移或字段翻译失效时阻断 payload 构建 | schema version 不匹配 | BuildBridgePayload | 返回 `BRIDGE_MAPPING_SCHEMA_MISMATCH` |
| TC-005 | DispatchBridge 成功执行正式桥接投送 | payload / endpoint 匹配 | DispatchBridge | BridgeDelivery / DeliveryResult 创建成功 |
| TC-006 | ack/timeout/duplicate 都必须正确进入桥接交付主线 | 外部端分别返回 ACK / timeout / duplicate | RecordAck / RecordTimeout / duplicate flow | histories 记录成功 |
| TC-007 | external endpoint status 不得替代 internal execution truth | source execution 存在 | negative flow | 仅更新 bridge delivery 结果 |
| TC-008 | TriggerReplay / TriggerResync 成功创建恢复入口和票据 | delivery failed/timed out | TriggerReplay / TriggerResync | ReplayRequest / ResyncTicket 创建成功 |
| TC-009 | replay/resync 缺失败上下文时必须被拒绝 | failure context 缺失 | TriggerReplay | 返回 `BRIDGE_FAILURE_CONTEXT_MISSING` |
| TC-010 | replay/resync 不得改写 source truth | recovery input 合法 | negative flow | 只重做桥接主线 |
| TC-011 | BuildIntegrationStatus 成功生成 bridge health 与 failure reason 视图 | delivery/recovery 输入齐全 | BuildIntegrationStatus | IntegrationStatus / FailureReasonView 创建成功 |
| TC-012 | partner config summary 不得冒充 marketplace truth | partner config 存在 | negative flow | 仅形成桥接层摘要 |
| TC-013 | failure/health 视图必须可回指 delivery 和 replay history | delivery/replay histories 存在 | BuildIntegrationStatus + compare | refs 对账成功 |
| TC-014 | replay/resync 后 bridges 状态正确刷新 | replay/resync 成功 | TriggerReplay / TriggerResync → refresh | 状态、历史、health 视图一致 |

## 11. 回归策略与残余风险

### 11.1 回归策略
- 每次改动 request / target / direction,都必须回归桥接入口与 source refs 主线
- 每次改动 mapping / schema / field translation,都必须回归 payload 构建与协议映射主线
- 每次改动 delivery / ack / timeout / duplicate,都必须回归桥接交付与回执主线
- 每次改动 replay / resync / repair,都必须回归恢复票据、失败上下文与 source truth 分层主线
- 每次改动 partner/health/failure views,都必须回归 bridge diagnostics 与 operators 观察面主线

### 11.2 残余风险
| 风险 | 影响 | 接受人 |
|---|---|---|
| 多 partner / 多协议演进持续增长 | 验收矩阵需扩充 | TL / 架构 |
| 复杂 inbound/outbound 双向桥接增加 | delivery/replay 验收需增加更多样本 | bridges / ops |
| diagnostics / health 面继续丰富 | 诊断与运维视图验收需扩充 | operators / observability |

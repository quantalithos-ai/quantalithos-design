## 1. 先用人话理解这个仓

`L6-elves` 不是主体框架本体,也不是 chat / console / runtime 的另一个壳。它是 **“主体框架在外部宿主中的驻留 companion 壳”**。

你可以把它理解成:
- 当主机安装了 Quantalithos 主体框架后,系统可以在桌面、手环等宿主里放出一只“精灵”
- 这只精灵不等于主体本身,但能代表主体对用户做低打扰外显
- 它可以持续存在、展示状态、发出提醒、接收简短输入,并在需要时把复杂交互导回主界面

基础版里,它最重要的职责不是“变成另一个完整智能体”,而是:
> **做一个低打扰、可驻留、可提示、可轻交互、可导流回主体界面的 companion 壳。**

基础版宿主范围在本文中固定为:
- 桌面驻留宿主
- 可穿戴设备轻提示宿主(如手环)

除此之外,当前不纳入其他宿主类型,也不展开更复杂的多宿主体验编排。

## 2. 业务背景与问题定义

当前平台虽然已经有主体框架、chat、console、runner 等正式产品面,但这些入口都还是“主动打开”型体验。用户真正会遇到的问题是:

- 不打开主界面时,主体当前在干什么并不可见
- 用户需要一个轻量、持续驻留、不会打断工作流的存在体来承担提醒和陪伴
- 在桌面或可穿戴设备上,用户往往只需要看一眼状态、接一个提醒、回一句短消息、点一个继续入口
- 如果每次都必须完整打开 chat / console,体验会太重

因此,`L6-elves` 要解决的问题不是“如何复制一个新的主体”,而是:

1. 如何把主体框架的状态与存在感外显到外部宿主
2. 如何在不越权、不持有主体真相的前提下,提供低成本互动
3. 如何在桌面 / 手环等环境里建立一种连续存在的精灵式助手体验

如果没有这一层,平台只能提供:
- 主动式产品入口
- 重交互界面
- 缺少常驻陪伴层

这会导致:
- 状态外显不足
- 提醒成本高
- 轻交互缺失
- 陪伴感和持续感不足

## 3. 目标与非目标

### 3.1 目标

基础版本 `L6-elves` 的目标是:

1. **状态外显**
   - 能在桌面或可穿戴宿主中显示主体的最小状态集合
   - 基础版状态集合固定为:
     - `idle`
     - `busy`
     - `waiting`
     - `blocked`
     - `done`
     - `error`

2. **轻提示**
   - 能以低打扰方式向用户发送提醒、等待提示、完成提示、风险提示
   - 基础版宿主范围固定为:
     - 桌面驻留宿主
     - 可穿戴设备轻提示宿主(如手环)
   - 不扩展到其他未定义宿主,也不承诺多宿主复杂协同
   - 必须区分:
     - **被动可见状态**: 用户主动看一眼时可见
     - **主动提醒**: 精灵主动推送给用户

3. **轻交互**
   - 能接收一句短输入、一个确认/取消动作或一个唤醒动作
   - 基础版轻输入范围固定为:
     - 简短文本输入
     - 确认 / 取消 / 忽略
     - 唤醒主体入口
   - 不承接:
     - 长会话
     - 复杂上下文构造
     - 多轮任务编排

4. **导流升级**
   - 当交互超出精灵能力边界时,能把用户导回正式产品面
   - 基础版导流对象固定为:
     - `chat`
     - `console`
     - `runner`
   - 不导流到任意外部应用或未定义入口

5. **保持 companion 壳定位**
   - 作为主体框架的外显存在体,而不是主体真相本身

### 3.2 非目标

基础版本明确不做:

- 不做完整多轮复杂对话主面
- 不做设备侧完整执行主线
- 不做复杂自治决策
- 不做多设备复杂同步编排
- 不做完整商业化分发与商店能力
- 不让精灵替代 chat / console / runtime / member 的正式真相

## 4. 核心概念与边界

### 4.1 核心概念

#### ElfShell
精灵在某个宿主中的外显壳。

#### ElfPresence
精灵当前对用户可见的存在状态。在基础版中,ElfPresence 只允许使用以下最小状态集合:
- `idle`
- `busy`
- `waiting`
- `blocked`
- `done`
- `error`

它是面对用户的外显状态投影,不是 runtime 内部状态机本身。

#### ElfNudge
精灵发给用户的轻量提示,例如提醒、等待提示、完成提示、注意事项。

#### ElfPromptSurface
精灵给用户开放的最小输入面,如一句话输入、确认/取消、快速唤醒。

#### ElfAction
精灵可直接承接的一次轻交互动作,例如点击、确认、忽略、唤醒。

#### ElfDeviceBinding
精灵与宿主设备之间的绑定关系。

### 4.2 核心边界

基础版必须先写死以下边界:

- `Elf ≠ Member`
- `Elf shell ≠ chat truth`
- `Elf presence ≠ runtime truth`
- `Elf device binding ≠ account/member truth`
- `Elf prompt surface ≠ full conversation surface`
- `Elf action ≠ business orchestration`

也就是说:
- 精灵不是主体本身
- 精灵不是完整聊天入口
- 精灵不是执行真相持有者
- 精灵不是设备账户系统
- 精灵只是 companion 壳和轻交互层

## 5. 用户场景

### 5.1 桌面驻留场景

用户在主机上工作时,精灵常驻桌面边缘或状态区:
- 可见主体当前状态
- 接收轻量提醒
- 一键唤起主界面

### 5.2 可穿戴提醒场景

用户不在主机前时,手环等设备上的精灵以极简方式提示:
- 当前是否有需要关注的事
- 是否进入 `waiting` / `blocked` / `done` / `error` 状态
- 是否需要用户确认某个动作

这里的可穿戴宿主只承担轻提示、轻确认和导流入口,不承接完整会话或设备侧执行主线。

### 5.3 主界面导流场景

当交互超出精灵能力边界时,精灵应把用户导回正式产品面:
- chat
- console
- runner

也就是说,精灵负责“轻入口”,主界面负责“重交互”。

## 7. 功能需求

### 7.1 存在与绑定

- F-001：支持创建一个正式 ElfShell
- F-002：支持 ElfShell 与宿主设备建立 ElfDeviceBinding
- F-003：支持展示 ElfPresence 的最小状态集合
- F-004：基础版宿主类型固定为桌面驻留宿主与可穿戴设备轻提示宿主

### 7.2 提示与提醒

- F-004：支持 ElfNudge
- F-005：支持等待、完成、异常、提醒等轻提示类型
- F-006：支持低打扰提示策略

### 7.3 轻交互

- F-007：支持一句短输入
- F-008：支持确认 / 取消 / 忽略类动作
- F-009：支持快速唤醒主体入口

### 7.4 导流升级

- F-010：支持跳回 chat / console / runner
- F-011：支持在复杂交互场景下放弃本地承接,转交正式界面

## 8. 非功能需求与验收口径

### 8.1 非功能需求

- NF-001：低打扰
- NF-002：低延迟
- NF-003：不越权
- NF-004：可恢复
- NF-005：可关闭 / 可静音

### 8.2 基础版验收口径

基础版完成的最低标准是:

1. 能在桌面驻留宿主或可穿戴设备轻提示宿主中实例化一只精灵
2. 能以 `idle / busy / waiting / blocked / done / error` 六态对外显示主体的最小状态
3. 能发出低打扰提醒
4. 能承接一句短输入或一个确认动作
5. 能在复杂场景下只导流回 `chat / console / runner`
6. 不替代主体真相、不替代执行真相、不替代正式对话真相

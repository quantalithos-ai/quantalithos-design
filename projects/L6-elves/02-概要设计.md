## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L6-elves` 不是主体框架本体,也不是 chat 的缩小版,更不是把 runtime 执行主线搬到桌面或手环上。它是 **“主体框架在外部宿主中的 companion projection layer / 外部宿主陪伴层”**。

你可以把它理解成:
- 当用户没有主动打开 chat / console / runner 时,外部宿主里仍然有一个持续可见的陪伴壳
- 这个壳把主体当前最重要的最小状态投影出来
- 它可以在需要时给用户轻量提醒,接收一句短输入或一个确认动作
- 一旦交互超出边界,它会把用户导回正式产品面继续处理

这些事情,都由 `L6-elves` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L6-elves`,这些宿主侧陪伴事实就会散落在:
- chat / console / runner 各自零散的提醒入口里
- 桌面壳自己的托盘、浮层和通知逻辑里
- 可穿戴设备自己的提示脚本或通知通道里
- observability 输出的状态摘要里
- 一些临时的唤起器、外部入口和本地交互脚本里

结果就会出现:
- 哪些状态应该被外显、哪些状态不该被外显没有统一口径
- 同一类提醒在桌面与可穿戴上逐渐漂移成两套体验
- 轻输入、确认、忽略、唤醒入口没有统一边界
- 复杂交互该何时回主界面没有统一主线
- 设备绑定、宿主提示、导流记录与上游真相容易混层

所以 `L6-elves` 必须独立存在,作为:
> **把主体框架的最小状态、轻提示、轻交互和主界面导流统一组织成外部宿主中的陪伴层。**

### 1.3 新人最容易混淆的几个词

#### ElfPresence
就是:
> 用户在外部宿主里看到的最小状态投影。

它不是 runtime 正式状态机本体。

#### ElfNudge
就是:
> 发给用户的一次低打扰轻提示。

它不是 chat/system message truth 本体。

#### ElfPromptSurface
就是:
> 精灵开放给用户的最小输入面。

它不是 full conversation surface。

#### ElfAction
就是:
> 精灵本地可直接承接的一次轻交互动作。

它不是 business orchestration truth。

#### ElfDeviceBinding
就是:
> 精灵与外部宿主设备之间的局部绑定关系。

它不是 account/member truth。

#### Guarded Diversion
就是:
> 当本地轻交互超出精灵边界时,把用户受控导回 `chat / console / runner` 的升级动作。

它不是任意跳转机制。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L6-elves/02` 时,先收稳以下前提:
- `L6-elves` 不应按托盘 / 卡片 / 通知 / 按钮 / 设置页等组件树平铺理解,而应按 companion 主链责任拆
- elves 至少应拆成“状态投影与存在外显 / 轻提示与低打扰投递 / 轻交互承接与最小输入面 / 宿主适配与设备绑定 / 受控导流与外部可见状态”五个主要部分
- elves 自己拥有的真相不是 member truth、runtime truth、chat truth 或 account truth,而是 `ElfPresence`、`ElfNudge`、`ElfPromptSurface`、`ElfAction`、`ElfDeviceBinding`、diversion / audit record 这类宿主侧投影与交互事实
- `L6-elves` 只能提供基础版宿主陪伴层,不能反过来替正式产品面持有复杂交互真相
- 02 的重点不是“列有哪些宿主组件或通知协议”,而是先把“外部宿主 companion 层在全局里到底是什么、和上游投影、chat / console / runner、observability 怎么分层”讲清楚
- `ElfPresence`、`ElfNudge`、`ElfPromptSurface`、guarded diversion 这些不是零散功能点,而是 elves 主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的外部宿主 companion 心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,用户面对的并不总是主界面。用户真正需要的不是“多一个通知入口”,而是:
- 不打开主界面时,仍然能知道主体现在是空闲、忙碌、等待、阻塞、完成还是异常
- 当系统需要用户注意时,可以通过低打扰的方式轻量提醒
- 用户可以在宿主侧做一句短输入、一次确认、一次忽略或一次唤醒
- 当问题变复杂时,系统会把用户平滑导回正式产品面,而不是在设备侧继续叠加复杂交互
- 这些宿主侧状态、提示、交互和导流,都能保持统一边界,而不是每个宿主各自长成一套产品

如果把这些逻辑分别散落到:
- chat / console / runner 的局部入口
- 桌面驻留逻辑
- 可穿戴提示逻辑
- observability 摘要
- 一些临时脚本和壳层代码里

系统会快速退化成:
- 宿主侧陪伴体验没有统一主线
- 状态投影和真实执行状态混淆
- 轻输入和复杂交互边界越来越模糊
- 宿主能力差异反向污染核心语义
- 导流升级没有统一规则,最终变成任意入口跳板

因此,本概要设计的任务就是:
> **把 `L6-elves` 写成一个新人也能看懂的“外部宿主 companion 层”,而不是把状态提示、轻交互和唤起入口零散散落在多个壳层里。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 宿主陪伴主线统一性 | 容易散落在各壳层 | 单一 elves 主线 | 需正式收敛 |
| 状态投影边界 | 易与 runtime truth 混淆 | 六态最小投影 100% 收口 | 需写死 |
| 轻交互边界 | 易滑向迷你 chat | 最小输入面边界稳定 | 需正式定义 |
| 导流升级统一性 | 容易演变成任意跳转 | 仅 `chat / console / runner` | 需统一建模 |
| 宿主差异控制 | 容易桌面/可穿戴各写一套 | shared core 统一语义 | 需正式组织 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把主体框架的最小状态、轻提示、轻交互和升级导流稳定地组织成一个低打扰、可驻留、可理解的外部宿主陪伴层
- **技术问题**:`ElfPresence`、`ElfNudge`、`ElfPromptSurface`、`ElfAction`、`ElfDeviceBinding`、guarded diversion 与 upstream truth projections、desktop / wearable hosts、`chat / console / runner`、observability 之间的边界如何稳定建模,并形成统一 elves 主链

## 4. 约束条件

### 4.1 技术约束

- `ElfPresence` 只允许 `idle / busy / waiting / blocked / done / error` 六态最小集合
- `ElfPromptSurface` 只能承接一句短输入、确认 / 取消 / 忽略、唤醒入口
- guarded diversion 只允许导向 `chat / console / runner`
- 宿主侧所有状态、提示和交互都必须能回指上游投影来源或导流目标
- desktop / wearable 两类宿主必须共享核心语义,不能各写一套独立产品逻辑
- observability 只消费宿主侧行为证据,不得反向冒充业务裁决

### 4.2 资源约束

- 桌面与可穿戴的宿主能力天然不同,但 shared core 语义必须稳定
- 提示和交互记录会持续增长,要接受宿主侧 append-only 行为证据累积
- 状态刷新与提示投递不能拖垮上游投影输入与正式产品面唤起链路

### 4.3 时间约束

- 当前阶段先收稳基础版 companion 主链,而不是先做复杂宿主生态或多设备联动
- 状态投影、轻提示、轻交互、宿主适配、受控导流五条基础链必须优先稳定,否则后续所有宿主接入都会失控

### 4.4 合规约束

- 宿主侧状态不得冒充 member/runtime/chat/account 真相
- 设备绑定不得冒充身份绑定或账户绑定
- 复杂交互不得在宿主侧继续承接为正式业务编排
- 导流、忽略、确认、宿主故障都必须可留痕、可追溯

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| host types | 2 | 基础版宿主边界 |
| presence states | 6 | `00-需求文档.md` 固定范围 |
| diversion targets | 3 | `00-需求文档.md` 固定范围 |
| light interaction classes | 3 类 | 简短文本 / 确认取消忽略 / 唤醒入口 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ upstream truth projections │
                    │ events / sdk / summaries   │
                    └────────────┬───────────────┘
                                 │ elves input
                                 ▼
                    ┌────────────────────────────┐
                    │ L6-elves                   │
                    │ - presence / nudge         │
                    │ - prompt / binding         │
                    │ - diversion / audit        │
                    └────────────┬───────────────┘
                                 │ host-visible output / guarded diversion
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ desktop / wearable hosts   │   │ chat / console / runner    │   │ observability              │
│ - residency / light prompt │   │ - formal interaction       │   │ - evidence / diagnostics   │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L6-elves` 自己负责状态外显、轻提示、轻交互、宿主适配、设备局部绑定、导流升级与宿主侧留痕主线
- upstream truth projections 是状态、上下文摘要和最小来源事实的提供方,但 elves 不拥有它们的真相
- desktop / wearable hosts 是宿主承载方,不是业务真相方
- `chat / console / runner` 是复杂交互升级后的正式承接面,elves 不替代它们
- observability 负责消费和组织 elves 的宿主侧行为证据,但不替代宿主和上游的正式真相

所以 `L6-elves` 在全局里的角色是:
> **把主体框架的最小状态、轻提示、轻交互和主界面导流统一组织成外部宿主中的 companion 层。**

### 5.3 系统边界

`L6-elves` 做什么:
- 承接最小状态投影
- 承接低打扰轻提示
- 承接最小轻输入和轻动作
- 在超界时执行 guarded diversion
- 输出宿主侧行为证据

`L6-elves` 不做什么:
- 不做 member truth
- 不做 runtime truth
- 不做 chat truth
- 不做 account truth
- 不做完整会话主面
- 不做复杂自治编排

### 5.4 外部系统可用性约束与降级

| 外部依赖 | 约束 | 降级 |
|---|---|---|
| upstream truth projections | 状态输入可能延迟或短暂不可用 | 保留最近一次可见状态并标记 stale |
| desktop residency host | 宿主能力可能受限 | 退化为最小状态显示 + 唤起入口 |
| wearable light-prompt host | 宿主能力更弱 | 退化为极简提示与确认入口 |
| `chat / console / runner` | 导流目标可能暂时不可达 | 显示导流失败提示并允许稍后重试 |
| observability | 留痕输出可能延迟 | 本地暂存后补发 |

### 5.5 关键依赖风险

- 把宿主壳能力直接写进共享核心,会导致语义污染
- 把可见状态写成真实执行状态,会破坏真相边界
- 把轻输入不断扩写,会让精灵滑向迷你 chat
- 把导流写成任意跳转,会破坏主产品面边界

## 6. 本仓由哪些主要组成部分构成

### 6.1 总体分层图

```text
┌──────────────────────────────────────────────┐
│ 主要部分 A · 状态投影与存在外显部分          │
│ ElfPresence / stale / visible state          │
│ 作用:把上游状态收束为用户可理解的六态外显    │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 主要部分 B · 轻提示与低打扰投递部分          │
│ ElfNudge / passive visible / active nudge    │
│ 作用:决定哪些状态变化需要被低打扰地送达用户  │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 主要部分 C · 轻交互承接与最小输入面部分      │
│ ElfPromptSurface / ElfAction                 │
│ 作用:承接一句短输入与确认/取消/忽略/唤醒动作 │
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 主要部分 D · 宿主适配与设备绑定部分          │
│ desktop adapter / wearable adapter / binding │
│ 作用:把共享核心语义映射到两类宿主并维持局部绑定│
└──────────────────────────────────────────────┘
                     ↓
┌──────────────────────────────────────────────┐
│ 主要部分 E · 受控导流与外部可见状态部分      │
│ guarded diversion / audit / visible outcome  │
│ 作用:把超界交互升级到正式产品面并留下可见证据│
└──────────────────────────────────────────────┘
```

### 6.2 主要组成部分说明

#### 6.2.1 主要部分 A · 状态投影与存在外显部分

**它是什么**:
- 它是把上游状态收束为 `ElfPresence` 六态最小集合的 companion 投影部分

**为什么单独有它**:
- 因为“可见状态”是整个宿主陪伴层的起点
- 如果不先把状态投影独立出来,提示、轻交互和导流都会失去统一基线

**负责什么**:
- 把上游状态映射为 `idle / busy / waiting / blocked / done / error`
- 维护 stale、去抖和最小解释口径
- 为后续提示和交互提供统一可见状态输入

**不负责什么 / 容易混淆点**:
- 不负责 runtime 真状态机
- 不负责业务执行裁决
- 不负责 member / chat / account 真相

**与其他部分交互**:
- 向 B 提供状态变化输入
- 向 D 提供宿主可渲染的最小状态结果
- 向 E 提供外部可见结果与留痕上下文

**后续详细设计展开点**:
- 六态映射规则
- stale 判定与去抖策略
- 可见状态与来源 ref 的绑定方式

#### 6.2.2 主要部分 B · 轻提示与低打扰投递部分

**它是什么**:
- 它是承接 `ElfNudge` 生成、分类、节流、静音与投递决策的部分

**为什么单独有它**:
- 因为“能不能提醒、该怎么提醒、是否应该安静”是 companion 体验的核心边界
- 如果把提示散在宿主壳里,桌面与可穿戴会很快漂移

**负责什么**:
- 区分被动可见状态与主动提醒
- 根据状态变化形成等待、完成、异常、风险等轻提示
- 处理低打扰、静音、节流、降级口径

**不负责什么 / 容易混淆点**:
- 不负责长文本说明
- 不负责复杂上下文拼装
- 不把提示送达等同于业务已完成或用户已理解

**与其他部分交互**:
- 读取 A 的状态变化
- 通过 D 投递到 desktop / wearable hosts
- 向 E 输出提示结果与证据

**后续详细设计展开点**:
- 提示分类体系
- 节流与静音策略
- 宿主能力不足时的降级路径

#### 6.2.3 主要部分 C · 轻交互承接与最小输入面部分

**它是什么**:
- 它是承接 `ElfPromptSurface` 和 `ElfAction` 的最小交互部分

**为什么单独有它**:
- 因为 companion 层不是只看状态,还需要让用户给出一句短输入或一个最小动作
- 如果不单独收口,轻交互很容易滑向完整会话面

**负责什么**:
- 承接一句短输入
- 承接确认 / 取消 / 忽略
- 承接唤醒主界面入口
- 对“可本地承接”与“必须升级导流”做第一层判断

**不负责什么 / 容易混淆点**:
- 不负责完整多轮对话
- 不负责复杂上下文构造
- 不负责业务 orchestration
- 不把宿主输入记录当作 conversation truth

**与其他部分交互**:
- 接收 D 从宿主回收的最小动作
- 根据 A/B 当前状态与提示上下文做本地承接或升级判断
- 把超界动作交给 E 处理

**后续详细设计展开点**:
- 最小输入面分类
- 本地承接与超界判定规则
- 交互结果回写与忽略路径

#### 6.2.4 主要部分 D · 宿主适配与设备绑定部分

**它是什么**:
- 它是把 shared elf core 语义映射到 desktop residency host 与 wearable light-prompt host 的适配层,同时承接 `ElfDeviceBinding` 局部绑定事实

**为什么单独有它**:
- 因为宿主差异天然存在,但 shared core 语义必须稳定
- 如果不单独隔离,宿主私有能力会反向污染核心口径

**负责什么**:
- 把状态、提示、轻动作映射到桌面宿主能力
- 把状态、提示、轻动作映射到可穿戴宿主能力
- 维护精灵与设备之间的局部绑定事实

**不负责什么 / 容易混淆点**:
- 不负责 account/member identity truth
- 不负责多设备复杂同步编排
- 不负责宿主自治业务逻辑

**与其他部分交互**:
- 从 A/B/C 接收共享语义
- 把宿主动作回传给 C
- 把绑定信息和宿主能力约束交给 E 形成可见结果与留痕

**后续详细设计展开点**:
- desktop adapter 与 wearable adapter 的差异接口
- binding 生命周期
- 宿主能力矩阵与降级规则

#### 6.2.5 主要部分 E · 受控导流与外部可见状态部分

**它是什么**:
- 它是负责 guarded diversion、导流结果可见化与 observability 留痕的收口部分

**为什么单独有它**:
- 因为 companion 层的关键价值之一,就是知道什么时候必须回正式产品面
- 如果导流和留痕散在各部分里,边界会很快失控

**负责什么**:
- 在超界时导向 `chat / console / runner`
- 形成导流原因、导流结果和最小用户解释
- 输出提示、交互、导流、故障等宿主侧证据

**不负责什么 / 容易混淆点**:
- 不负责正式产品面的后续真相承接
- 不负责 observability 权威裁决
- 不负责任意外部跳转

**与其他部分交互**:
- 接收 C 的超界动作
- 调用正式产品面入口
- 向 observability 输出 normalized behavior evidence

**后续详细设计展开点**:
- guarded diversion rules
- visible outcome models
- evidence 分类与 context binding

### 6.3 主要组成部分汇总表

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
upstream truth projections(events/sdk)
                 │
                 ▼
      状态投影与存在外显部分
                 │
                 ▼
      轻提示与低打扰投递部分
                 │
                 ▼
      轻交互承接与最小输入面部分
                 │
        ┌────────┴────────┐
        ▼                 ▼
宿主适配与设备绑定部分   受控导流与外部可见状态部分
        │                 │
        ▼                 ├────────▶ chat / console / runner
desktop / wearable hosts  └────────▶ observability
```

### 7.2 总解释

- `L6-elves` 负责把上游主体最小状态、轻提示和轻交互投影到外部宿主
- desktop / wearable 是宿主承载方,不是业务真相方
- `chat / console / runner` 是复杂交互升级后的正式承接面
- observability 消费的是 elves 的宿主侧行为记录与状态投影事件,不是上游业务真相

### 7.3 分模块交互说明

#### 7.3.1 与 upstream truth projections(events/sdk) 的交互

上游投影输入方负责提供:
- 最小状态来源
- 最小上下文摘要
- 可导流目标的最小入口信息

`L6-elves` 在这里的职责是:
- 把这些输入收束成 companion 可见语义
- 不反向拼装或重建真相
- 不把上游状态当作宿主侧可直接暴露的所有信息

主交互链是:
> upstream projection → `ElfPresence` → `ElfNudge` / `ElfPromptSurface` → guarded diversion 或宿主可见结果

高风险异常流:
- 把 `ElfPresence` 误写成 runtime truth
- 把宿主显示身份误写成 member truth

#### 7.3.2 与 desktop residency host 的交互

desktop host 负责:
- 常驻承载 companion 外显
- 承载被动可见状态与主动轻提示
- 承载最小轻确认、忽略与唤醒入口

`L6-elves` 在这里的职责是:
- 把 shared core 语义映射成桌面可承载体验
- 不让桌面宿主能力反向污染 shared core 口径
- 不让桌面端逐步膨胀成迷你 chat

主交互链是:
> `ElfPresence` / `ElfNudge` → desktop adapter → 用户动作 → `ElfAction` / guarded diversion

高风险异常流:
- 桌面端自增富交互,突破 companion 边界
- 宿主本地状态被误当正式产品面真相

#### 7.3.3 与 wearable light-prompt host 的交互

wearable host 负责:
- 极简外显状态
- waiting / blocked / done / error 等高价值提示
- 确认 / 取消 / 忽略 / 唤醒入口

`L6-elves` 在这里的职责是:
- 把 shared core 语义压缩成可穿戴可承载的极简表达
- 不在可穿戴侧继续承接复杂对话或执行主线
- 在宿主能力不足时优先退化为“提示 + 导流”

主交互链是:
> `ElfNudge` / `ElfPresence` → wearable adapter → 用户最小动作 → 本地承接或导流升级

高风险异常流:
- 可穿戴侧被写成独立自治入口
- 极简提示被扩写成复杂上下文面

#### 7.3.4 与 `chat / console / runner` 的交互

这三个系统负责:
- 承接复杂交互的正式主面
- 承接超出 companion 边界的后续流程

`L6-elves` 在这里的职责是:
- 只在超界时执行 guarded diversion
- 给用户一个最小解释:为什么需要回主界面
- 不替它们继续承接正式交互真相

主交互链是:
> `ElfPromptSurface` / `ElfAction` 判定超界 → guarded diversion → `chat / console / runner`

高风险异常流:
- 导流被写成任意跳转
- elves 被误当作正式产品面的并行前台

#### 7.3.5 与 observability 的交互

observability 负责:
- 接收宿主侧提示、交互、导流、故障证据
- 统一 source tagging、context binding 与可见性组织

`L6-elves` 在这里的职责是:
- 输出 normalized behavior evidence
- 区分本地轻交互成功、被忽略、被阻断、被导流、导流失败等不同结果
- 不把 observability 结果冒充正式业务裁决

主交互链是:
> nudge / prompt / action / diversion / host fault → evidence record → observability

高风险异常流:
- 观测记录被误当 source truth
- 宿主侧行为与上游真相混层

### 7.4 本节与详细设计的边界

本节只回答:
- elves 如何按主链和上下游交互
- 这些交互分别由哪个主要部分承接
- 交互边界为什么这样划

本节不回答:
- 具体协议字段
- 具体本地存储 schema
- 具体重试参数
- 具体宿主壳实现细节

这些内容留给 `03-详细设计.md`。

### 7.5 三条主线说明

1. **状态外显主线**  
   upstream projection → `ElfPresence` → host visible state

2. **轻提示与轻交互主线**  
   状态变化 → `ElfNudge` → 用户最小动作 → `ElfAction`

3. **超界升级主线**  
   本地判断超界 → guarded diversion → `chat / console / runner` → observability 留痕

## 10. 横切关注点

### 10.1 安全
- 不越权持有 member/runtime/chat/account truth
- 不让 `ElfPromptSurface` 扩写成 full conversation surface
- 不让 `ElfAction` 承担 business orchestration

### 10.2 性能
- 状态投影更新必须及时
- 轻提示投递必须轻量
- 导流升级响应不能过慢

### 10.3 可用性
- 宿主离线时允许降级
- 导流失败时允许明确重试
- 宿主能力不足时优先回退到最小可见状态与唤起入口

### 10.4 可观测性
- 提示、忽略、确认、导流、故障都要留痕
- 所有宿主侧行为都要有 source tagging 与 context binding

### 10.5 成本
- 当前不提前引入复杂宿主生态治理成本
- 优先使用 shared core 控制后续多宿主扩展成本

### 10.6 性能预算表

| 环节 | 预算 | 说明 |
|---|---|---|
| 状态投影进入 `ElfPresence` | < 200ms | 保证外显及时 |
| `ElfNudge` 决策与投递准备 | < 100ms | 保证低打扰提醒不过慢 |
| 宿主投递或外显刷新 | < 300ms | 保证用户可感知 |
| guarded diversion 触发 | < 500ms | 保证复杂场景尽快回主界面 |

## 1. 模块职责描述

**本模块做什么**:
- 持有正式 `ElfPresence` / `ElfNudge` / `ElfPromptSurface` / `ElfAction` / `ElfDeviceBinding` / `GuardedDiversion` 等 elves 层真相
- 把上游最小状态投影、轻提示、最小轻交互、宿主适配、导流升级和宿主侧行为证据组织成统一 companion 主线
- 为 desktop residency host、wearable light-prompt host、`chat / console / runner`、observability 提供稳定的宿主侧投影、交互和结果语义
- 管理 stale / suppression / degraded / diverted / failed 等结果分类,并为后续 `05-测试方案.md` / `06-验收标准.md` 提供可验证输入

**本模块不做什么**:
- 不持有 member truth、runtime truth、chat truth 或 account truth
- 不替代完整多轮复杂对话主面、设备侧完整执行主线或业务 orchestration
- 不替代正式 observability truth,只输出宿主侧行为证据
- 不扩展为多设备复杂同步编排中心或任意导流跳板

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 elves“为什么存在”,而是让开发者可以直接开始实现:
- upstream truth projections 如何进入正式 `ElfPresence` 主线
- presence 变化如何形成 `ElfNudge`
- `ElfPromptSurface` / `ElfAction` 如何承接一句短输入、确认 / 取消 / 忽略 / 唤醒动作
- desktop / wearable adapters 如何承接 shared core 语义而不反向污染边界
- guarded diversion 如何把超界交互升级到 `chat / console / runner`
- 宿主侧 evidence 如何进入 observability,同时不冒充上游业务真相

如果不先把这些内容采集清楚,03 很容易退化成:
- 托盘 / 卡片 / 浮层 / 通知组件树说明书
- 本地交互脚本笔记
- 各类状态字段清单
- 宿主协议配置草图
- 一堆“能做什么”的描述,却没有统一的核心对象、命令和异常主线

### 2.2 内容采集流程(先采集,再落文)

#### 第 0 步:确认 `02-概要设计` 已经稳定

先确认:
- `L6-elves` 是外部宿主 companion 层,不是上游 source truth 仓
- 五个主要部分已经稳定
- 与 upstream truth projections、desktop / wearable hosts、`chat / console / runner`、observability 的边界已经清楚
- `02` 中总交互图与分模块交互图已经能回答“谁给谁什么 elves 语义”

#### 第 1 步:列出要实现的核心对象

本仓 03 先按五组对象理解:
- 状态投影对象: `ElfPresence` / `PresenceSourceRef` / `PresenceProjectionRule` / `PresenceFreshnessWindow` / `PresenceTransitionRecord` / `ElfPresenceView`
- 轻提示对象: `ElfNudge` / `NudgeIntent` / `NudgePolicy` / `NudgeDeliveryTicket` / `NudgeOutcome` / `NudgeHistoryView` / `NudgeSuppressionRecord`

#### 第 2 步:列出主流程与关键异常流

主流程至少有四条:
- upstream status → `ProjectElfPresence` → `ElfPresenceView` 主线
- presence transition → `PlanElfNudge` → `DispatchElfNudge` → `RecordNudgeOutcome` 主线
- host minimal action → `OpenPromptSurface` / `HandleElfAction` 主线
- 超界交互 → `EvaluateGuardedDiversion` → `TriggerGuardedDiversion` → `RecordElfVisibleOutcome` 主线

关键异常流至少包括:
- upstream projection 延迟或缺失
- presence 映射冲突或 freshness 失效
- nudge 被 suppression / mute / throttle
- host action 到达时 prompt surface 已过期
- binding 漂移 / 宿主离线 / capability 不足
- diversion target 暂不可达
- observability sink 不可用导致 evidence backlog

#### 第 3 步:列出要落库/持久化的对象与关系

必须先分清:
- 哪些是写模型: `elf_presences` / `elf_nudges` / `prompt_surfaces` / `elf_actions` / `device_bindings` / `guarded_diversions`
- 哪些是只读视图: `elf_presence_view` / `nudge_history_view` / `prompt_surface_view` / `binding_view` / `visible_outcome_view`
- 哪些是 append-only: `presence_transition_history` / `nudge_delivery_history` / `suppression_history` / `action_history` / `diversion_history` / `behavior_evidence_history`
- 哪些输入只能作为来源引用,不能反向变成 member / runtime / chat / account 真相本体

#### 第 4 步:列出事件与外部协作点

要回答:
- 哪些输入来自 upstream truth projections
- 哪些输出给 desktop / wearable hosts
- 哪些动作会导流到 `chat / console / runner`
- 哪些结果会进入 observability
- 哪些 suppression / rejection / failure 只是 elves 层结果,不能冒充业务真相

#### 第 5 步:列出最小测试输入

必须测:
- `ElfPresence ≠ runtime truth`
- `ElfPromptSurface ≠ full conversation surface`
- `PromptInputDraft ≠ conversation truth`
- `ElfDeviceBinding ≠ account/member truth`
- `ElfAction ≠ business orchestration`
- guarded diversion 只允许 `chat / console / runner`
- 五段主链逐条成立
- `suppressed` / `stale` / `degraded` / `diverted` / `failed` 等语义都可验证

## 3. 先按模块组织,再按文件展开

### 3.1 为什么先按模块组织

`03-详细设计` 不能直接从 `ElfPresence` / `ElfNudge` / `PromptInputDraft` / `ElfDeviceBinding` / `ElfVisibleOutcome` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 companion 主链,`03` 却退化成宿主组件清单
- 实现者知道有提示和按钮,却不知道它们如何通过 shared core、guarded diversion 和 evidence 链接起来

### 3.2 模块到概要交互链映射

| 模块 | 承接的概要交互链 / 主流程 | 主要职责 |

- **异步最终一致**主要是: host delivery result refresh、evidence backfill、stale rebuild、部分 visible outcome 更新

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从对象清单开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是 companion 主链,`03` 却退化成通知脚本或宿主 UI 说明
- 实现者只能看到局部功能点,看不到边界与升级主线

### 5.2 状态投影与存在外显部分

**核心对象**:
- `ElfPresence`
- `PresenceSourceRef`
- `PresenceProjectionRule`
- `PresenceFreshnessWindow`
- `PresenceTransitionRecord`
- `ElfPresenceView`

**核心命令**:
- `ProjectElfPresence`
- `RefreshPresence`
- `MarkPresenceStale`

**实现重点**:
- 上游状态必须先进入 `PresenceSourceRef`,再进入 `PresenceProjectionRule`
- `PresenceProjectionRule` 只允许输出六态最小集合
- freshness 与 stale 逻辑必须显式建模,不能隐含在渲染层
- `ElfPresenceView` 只能是读模型,不可反写 `ElfPresence`

**不允许**:
- 直接把 runtime 内部状态机复制到 elves
- 让宿主渲染层自己决定新状态词表

### 5.3 轻提示与低打扰投递部分

**核心对象**:
- `ElfNudge`
- `NudgeIntent`
- `NudgePolicy`
- `NudgeDeliveryTicket`
- `NudgeOutcome`
- `NudgeHistoryView`
- `NudgeSuppressionRecord`

**核心命令**:
- `PlanElfNudge`
- `DispatchElfNudge`
- `RecordNudgeOutcome`

**实现重点**:
- `PlanElfNudge` 先做 should-notify 分类,再决定 suppress / dispatch
- suppression / mute / throttle 不是简单跳过,必须有 `NudgeSuppressionRecord`
- `NudgeOutcome` 必须区分 `delivered / failed / suppressed / degraded`
- `NudgeHistoryView` 用于读模型,不能驱动新一轮业务判断

**不允许**:
- 把通知送达等同于用户已理解
- 把宿主通知回执等同于业务完成

### 5.4 轻交互承接与最小输入面部分

**核心对象**:
- `ElfPromptSurface`
- `PromptSessionRef`
- `PromptInputDraft`
- `PromptConstraint`
- `ElfAction`
- `ElfActionIntent`
- `ElfActionResult`
- `InteractionBoundaryGuard`
- `PromptSurfaceView`

**核心命令**:
- `OpenPromptSurface`
- `SubmitShortInput`
- `HandleElfAction`

**实现重点**:
- `OpenPromptSurface` 必须绑定明确上下文 ref 与可执行最小动作集合
- `PromptInputDraft` 只在本地交互态存在,不可进入 conversation truth
- `InteractionBoundaryGuard` 负责判断 `handled_locally / rejected / diverted / failed`
- short text 仍然只是最小输入,不是长会话入口

**不允许**:
- 把 `ElfPromptSurface` 写成 mini-chat
- 接受附件、多轮上下文或复杂工具调用

### 5.5 宿主适配与设备绑定部分

**核心对象**:
- `HostAdapterPort`
- `DesktopResidencyAdapter`
- `WearableLightPromptAdapter`
- `HostCapabilityProfile`
- `HostRenderPayload`
- `HostActionPayload`
- `ElfDeviceBinding`
- `BindingStatus`
- `HostFaultRecord`
- `BindingView`

**核心命令**:
- `BindElfDevice`
- `RefreshHostCapabilityProfile`
- `RenderToHost`

**实现重点**:
- shared core 只定义语义,adapter 只做 host protocol/render 差异适配
- `HostCapabilityProfile` 明确宿主能做什么、不能做什么
- `ElfDeviceBinding` 只表达宿主侧局部绑定事实
- binding 与 capability 必须支持 degraded / revoked / detached 等状态

**不允许**:
- 让 binding 上升为 account/member truth
- 让 host adapter 发明新的治理/状态语义

### 5.6 受控导流与外部可见状态部分

**核心对象**:
- `GuardedDiversion`
- `DiversionIntent`
- `DiversionTargetRef`
- `DiversionReason`
- `DiversionOutcome`
- `ElfVisibleOutcome`
- `ElfAuditRecord`
- `BehaviorEvidenceRecord`
- `VisibleOutcomeView`

**核心命令**:
- `EvaluateGuardedDiversion`
- `TriggerGuardedDiversion`
- `RecordElfVisibleOutcome`

**实现重点**:
- target enum 固定为 `chat | console | runner`
- `DiversionReason` 明确说明为什么超界
- `ElfVisibleOutcome` 与 `BehaviorEvidenceRecord` 必须分离:前者给用户看,后者给 observability / 审计
- diversion 成功与失败都要被记录,且 failure 不得自动转为本地继续承接复杂交互

**不允许**:
- 任意外部跳转
- 导流失败后在 elves 内继续主业务交互

## 7. 关键流程与伪代码

### 7.1 总流程图

```text
upstream projection
      │
      ▼
ProjectElfPresence
      │
      ▼
PlanElfNudge
      │
      ▼
OpenPromptSurface / HandleElfAction
```

### 7.2 RPC / 外部入口到内部实现的函数全景图

| 外部入口 | 内部函数链 |
|---|---|
| upstream status projection | `ProjectElfPresence -> build_presence_view -> maybe_plan_nudge` |
| host prompt open | `OpenPromptSurface -> build_prompt_surface_view` |
| host action submit | `HandleElfAction -> classify_action -> local_or_divert` |
| device bind request | `BindElfDevice -> refresh_capability_profile -> save_binding` |
| diversion request | `EvaluateGuardedDiversion -> TriggerGuardedDiversion -> RecordElfVisibleOutcome` |

### 7.3 关键读路径 / 写路径

**写路径 A · 状态投影**:
- 读取 `PresenceSourceRef`
- 应用 `PresenceProjectionRule`
- 写入 `ElfPresence`
- 刷新 `ElfPresenceView`
- 追加 `PresenceTransitionRecord`

**写路径 B · 轻提示**:
- 读取 `ElfPresence`
- 计算 `NudgeIntent`
- 应用 `NudgePolicy`
- 写入 `ElfNudge`
- 视结果写入 `NudgeSuppressionRecord` 或 `NudgeDeliveryTicket`

**写路径 C · 轻交互 / 导流**:
- 打开 `ElfPromptSurface`
- 接收 `ElfActionIntent`
- 通过 `InteractionBoundaryGuard`
- 写入 `ElfActionResult`
- 若超界则创建 `GuardedDiversion`
- 写入 `ElfVisibleOutcome` 与 `BehaviorEvidenceRecord`

### 7.4 API / 命令签名

| 命令 | 输入 | 输出 |
|---|---|---|
| `ProjectElfPresence` | `PresenceSourceRef` + source summary | `presence_id` |
| `PlanElfNudge` | `presence_id` + trigger reason | `nudge_id` or suppression result |
| `DispatchElfNudge` | `nudge_id` + host target | `delivery_ticket_id` |
| `OpenPromptSurface` | `presence_ref` + host context | `prompt_surface_id` |
| `SubmitShortInput` | `prompt_surface_id` + short text | `action_result` |
| `HandleElfAction` | `prompt_surface_id` + `ElfActionKind` | `handled_locally / rejected / diverted / failed` |
| `BindElfDevice` | `host_device_ref` + host kind | `binding_id` |
| `EvaluateGuardedDiversion` | action intent + context refs | allow/deny + target + reason |
| `TriggerGuardedDiversion` | target + reason + context refs | `diversion_id` + outcome |

### 7.5 关键函数/命令级伪代码

#### `ProjectElfPresence`

```text
input: source_ref, source_summary
assert source_ref valid
mapped_state = apply_presence_projection_rule(source_summary)
assert mapped_state in {idle,busy,waiting,blocked,done,error}
presence = upsert_elf_presence(source_ref, mapped_state)
refresh_presence_view(presence)
append_presence_transition_record(presence)
if should_plan_nudge(presence):
    emit PlanElfNudge(presence)
return presence.id
```

#### `HandleElfAction`

```text
input: prompt_surface_id, action_kind, optional short_text
surface = load_prompt_surface(prompt_surface_id)
assert surface.status == open
assert action_kind in surface.allowed_actions
binding = load_active_binding(surface.context_ref)
assert binding valid
capability = load_host_capability(binding)
decision = evaluate_interaction_boundary(surface, action_kind, capability)
if decision == handled_locally:
    result = persist_local_action_result(surface, action_kind)
    record_visible_outcome(result)
    append_behavior_evidence(result)
    return handled_locally
if decision == diverted:
    diversion = trigger_guarded_diversion(surface, action_kind)
    record_visible_outcome(diversion)
    append_behavior_evidence(diversion)
    return diverted
if decision == rejected:
    append_ignored_or_rejected_record(surface, action_kind)
    return rejected
return failed
```

#### `TriggerGuardedDiversion`

```text
input: surface_or_action_context
eligibility = evaluate_diversion_target(surface_or_action_context)
assert eligibility.target in {chat,console,runner}
if not eligibility.allowed:
    return rejected
result = invoke_target_handoff(eligibility.target, context)
write_guarded_diversion(result)
write_elf_visible_outcome(result)
append_behavior_evidence(result)
return result
```

### 7.6 命令前置校验清单

- 上游 source ref 合法
- `ElfPresence` 映射结果在六态集合内
- `ElfPromptSurface` 仍处于 open
- `ElfActionKind` 在允许动作集合内
- `ElfDeviceBinding` 处于 active 或 degraded 可承接状态
- `HostCapabilityProfile` 明确支持当前动作
- 导流目标必须属于 `chat / console / runner`

### 7.7 关键状态机 / 非法转换与约束

| 对象 | 合法状态 | 非法状态处理 |
|---|---|---|
| `ElfPromptSurface` | open → acted → closed / open → expired | expired 后动作到达直接拒绝 |
| `ElfNudge` | planned → suppressed / dispatched → delivered|failed|degraded | 不允许从 delivered 回到 planned |
| `ElfDeviceBinding` | active → degraded → revoked/detached | revoked 后不得继续 dispatch |
| `GuardedDiversion` | created → triggered → completed|failed|rejected | failed 不得自动转为本地复杂承接 |

## 8. 运行期主线场景

### 8.1 场景 A · 桌面宿主持续显示六态 presence
- upstream status 到达
- `ProjectElfPresence`
- 生成 `ElfPresenceView`
- desktop adapter 渲染
- evidence 追加

### 8.2 场景 B · `waiting / blocked / error / done` 触发可穿戴轻提示
- presence transition 进入高价值状态
- `PlanElfNudge`
- wearable adapter dispatch
- `RecordNudgeOutcome`
- 若失败则降级为 passive visible state

### 8.3 场景 C · 用户做一次最小本地动作
- `OpenPromptSurface`
- 用户做 confirm / ignore / wake / short text
- `HandleElfAction`
- 若在边界内则 `handled_locally`
- 刷新 `VisibleOutcomeView`

### 8.4 场景 D · 动作超界后导流到正式产品面
- `EvaluateGuardedDiversion`
- 选定 `chat / console / runner`
- `TriggerGuardedDiversion`
- 若成功则记录 completed
- 若失败则显示可重试解释,不得在 elves 内继续复杂交互

### 8.5 场景 E · 宿主能力降级或离线
- `RefreshHostCapabilityProfile`
- binding 标记为 degraded
- active delivery 暂停
- 退化为最小状态显示或唤起入口
- evidence 进入 backlog / 后补

## 10. 读模型与投影设计

### 10.1 读模型清单

| 读模型 | 来源 | 用途 |
|---|---|---|
| `ElfPresenceView` | `ElfPresence` + freshness | 宿主显示 |
| `NudgeHistoryView` | `ElfNudge` + outcome/suppression history | 宿主与审计读取 |
| `PromptSurfaceView` | `ElfPromptSurface` + allowed actions | 宿主最小交互显示 |
| `BindingView` | `ElfDeviceBinding` + capability profile | 宿主与运维读取 |
| `VisibleOutcomeView` | `GuardedDiversion` / local action result | 给用户看最后结果 |
| `ElfBehaviorView` | `BehaviorEvidenceRecord` 聚合 | observability 消费 |

### 10.2 投影规则

- 所有读模型都必须能回指 source ref 或 elves truth ref
- 读模型不可反写正式真相
- stale / degraded / suppressed 必须进入读模型,不能被 UI 层静默吞掉

### 10.3 读写分离边界

- `ElfPresenceView` ≠ `ElfPresence`
- `PromptSurfaceView` ≠ `ElfPromptSurface`
- `VisibleOutcomeView` ≠ `BehaviorEvidenceRecord`
- `BehaviorEvidenceRecord` ≠ observability truth

## 11. 异常与补偿设计

### 11.1 异常分类与处理策略

| 异常 | 处理 |
|---|---|
| upstream projection 延迟/缺失 | 保留最近状态 + `PresenceStaleMarker` |
| presence 映射冲突 | 保留最近有效状态并追加 conflict 标记 |
| nudge suppression | 写 `NudgeSuppressionRecord`,不视为投递失败 |
| nudge delivery failed | 写 `NudgeOutcome=failed`,必要时降级为 passive visible |
| prompt surface expired | 拒绝动作并追加 expired/ignored record |
| binding invalid | 拒绝本地动作与主动投递 |
| host capability unsupported | 降级到最小可见状态或唤起入口 |
| diversion target unavailable | 写 failed outcome + 提供显式重试 |
| observability sink unavailable | 写本地 backlog,后补 evidence |

### 11.2 重试 / 降级 / 补偿

- nudge delivery retry 只发生在投递层,不能重新发明语义
- diversion retry 只重新尝试 handoff,不能在 elves 内继续复杂交互
- degraded host 允许继续被动可见状态,暂停主动轻提示
- evidence backfill 必须保留原始结果语义,不能合并改写

### 11.3 幂等设计

| 路径 | 幂等键建议 |
|---|---|
| presence projection | `source_ref + projection_version` |
| nudge planning | `presence_ref + nudge_kind + policy_window` |
| action handling | `prompt_surface_id + action_kind + action_nonce` |
| diversion trigger | `action_result_ref + target` |
| evidence append | `behavior_ref + evidence_kind + occurred_at` |

## 12. 实现红线 / 开发禁止事项

- 禁止把 `ElfDeviceBinding` 扩成 account/member identity truth
- 禁止把 `PromptInputDraft` 或 short text 变成 conversation truth
- 禁止让 `ElfPresence` 逻辑驱动 upstream runtime 真状态转换
- 禁止 host adapter 自定义新的状态词表
- 禁止 host adapter 增加新的导流目标
- 禁止 `ElfAction` 直接承担 business orchestration
- 禁止把 visible outcome 与 append-only evidence 混成同一个对象
- 禁止把 suppression / boundary rejection / diversion failure 混成同一种错误语义
- 禁止在 diversion 失败后继续在 elves 内承接复杂交互

## 15. 结论

`L6-elves/03-详细设计.md` 的目标不是把宿主 UI 写得更花,而是把基础版 companion 主线落到足以直接编码的粒度。本文把五段主链拆成了正式对象族、命令、读模型、事件、错误、主流程、异常补偿和测试输入,并把六条硬边界翻译成开发红线。后续如果严格按本文实现,开发者应能在不混淆 member/runtime/chat/account 真相边界的前提下,完成一个只覆盖 desktop residency host、wearable light-prompt host、六态最小状态集合和 `chat / console / runner` guarded diversion 的基础版 L6-elves。

## 1. 业务背景与驱动力

### 1.1 业务背景

Marketplace 是 Quantalithos 把“方法论、能力和运行资产”从内部积累推向生态流通的关键层。它既不是单纯的下载页,也不是传统插件商店的直接复制,而是把 MethodPlugin、ProcessTemplate、Role+Member 镜像、MCP Tool、Deployment Package 等资产放进一个**可审核、可安装、可撤销、可审计、可组织内私有化分发**的生态市场中。它的存在决定 Quantalithos 能否从一个产品演化成一个平台。

### 1.2 业务驱动力

**业务驱动力**:
- 组织和第三方需要共享可复用的方法资产与能力资产,而不是重复造轮子
- Quantalithos 需要形成“资产发布者 → 审核 → 安装者 → 复用反馈”的生态飞轮
- 企业用户需要私有/内部市场来管理组织级标准资产

**技术驱动力**:
- 需要对接 method-library、capability-hub、member-images 等真相源,但不复制其真相
- 需要 marketplace-review Gate、签名/扫描、29110 Deployment Package、安装审计链等统一模型
- 需要把资产发布/撤销的生命周期和平台治理、供应链、合规模型接起来

### 1.3 成功标准(可量化)

| 维度 | 指标 | 目标值 | 测量 |
|---|---|---|---|
| 治理 | 上架走审核流覆盖率 | 100% | 回归测试 |
| 合规 | 29110 DP 包合法性 | 100% 合法包 | 集成测试 |
| 安全 | 镜像类扫描前置 | 100% | 安全测试 |
| 审计 | 购买/安装可追踪覆盖率 | 100% | 回归测试 |
| 通知 | 撤销上架通知覆盖率 | 100% | E2E |
| 可用性 | 搜索/浏览主路径可用 | 100% 样本流 | E2E |

## 3. 架构风格与选型

### 3.1 变化维度识别

| 维度 | 变化频率 | 应对策略 |
|---|---|---|
| 资产类型扩展 | 中高 | upstream-aware listing model |
| 审核流策略变化 | 中 | marketplace-review abstraction |
| 商业化模型变化 | 中高 | payment/entitlement adapter 隔离 |
| 组织内/公开市场差异 | 中 | scope-aware catalog model |
| 安装/撤销反馈链 | 中高 | installation record + notification model |

### 3.2 架构风格决策框架

**候选架构风格**:

| 风格 | 优势 | 劣势 | 适用性 |
|---|---|---|---|
| **listing layer + review flow + upstream truth references**(当前) | 保持真相单一、市场能力清晰 | 模型较多 | ✅ |
| 把 Marketplace 做成资产真相源 | 简化展示 | 会破坏 method-library/cap-hub 等边界 | ❌ |
| 只做下载页 | 实现轻 | 无法承接审核、撤销、安装审计 | ❌ |
| 先做计费系统再做市场 | 商业模型完整 | 过度前置复杂性 | ❌ |

**最终选择**:**市场 listing 层 + 审核流层 + 安装/撤销审计层,上游资产真相保持原仓所有权**

### 3.3 架构风格约束-收益分析

| 约束 | 收益 | 成本 |
|---|---|---|
| listing 不复制真相正文 | 上游边界清晰、减少漂移 | 需要更多跨仓引用与同步 |
| 上架必须审核 | 平台治理与第三方风险可控 | 发布流程更重 |
| 安装/撤销都要有审计与通知 | 责任链清晰 | 生命周期实现更复杂 |

## 4. 系统边界与上下文

### 4.1 系统上下文图(C4 Context 级)

```text
publishers / buyers / enterprise admins / reviewers
                    │
                    ▼
           ★ quantalithos-marketplace ★
           - listing catalog
           - marketplace-review flow
           - install / revoke lifecycle
           - package validation & security gates
             │           │           │
             │           │           └────────▶ observability / notifications
             │           └────────────────────▶ governance(review gate)
             └───────────────────────────────▶ method-library / cap-hub / member-images truth
```

### 4.2 职责边界(做什么 / 不做什么)

**做什么**:
- ✅ 接收发布者上架请求并发起 marketplace-review 审核流
- ✅ 展示、搜索、分类、分发资产 listing
- ✅ 记录安装、撤销、通知等生态生命周期行为
- ✅ 对接镜像类资产扫描/签名门禁与发布者身份校验

**不做什么**:
- ❌ 不持有方法资产、能力资产、镜像资产的业务真相
- ❌ 不替代 method-library、capability-hub、identity、member-images
- ❌ 不优先解决复杂计费/分成问题
- ❌ 不把 Marketplace 做成代码片段站、LLM 模型站或人力市场

### 4.3 外部系统可用性约束

| 外部依赖 | SLA | 依赖风险 | 降级策略 |
|---|---|---|---|
| method-library APIs | 99.9% | 资产无法同步/展示完整信息 | 延迟发布 / 只读展示 |
| capability-hub APIs | 99.9% | MCP 资产无法分发 | 延迟发布 / 只读展示 |
| governance review flow | 99.9% | 上架无法审核 | 暂停新上架,保留浏览 |
| security scan/sign tools | 高 | 供应链验证失败 | 阻断发布 |
| observability/notifications | 99.95% | 安装/撤销审计不完整 | backlog / retry |
| 未来 billing | 待定 | 商业化链路失效 | 回退到免费或组织内分发 |

### 4.4 关键依赖风险

- 若 listing 与上游真相脱节,Marketplace 会变成一个高漂移的“假目录”
- 若 marketplace-review 只是形式流程,第三方与镜像资产会成为平台最大供应链风险口
- 若安装/撤销不留痕,资产传播会脱离平台可追溯性承诺

## 5. 限界上下文与子域划分

### 5.1 子域分类

| 子域 | 分类 | 说明 |
|---|---|---|
| Listing Catalog | 核心域 | 市场展示层与资产索引 |
| Review Flow | 核心域 | marketplace-review Gate 及审核状态 |
| Installation Lifecycle | 核心域 | 安装、撤销、通知、审计 |
| Packaging | 支撑子域 | 29110 Deployment Package 打包/解包 |
| Publisher Trust | 支撑子域 | 发布者验证、签名、扫描门禁 |
| Commercialization | 支撑子域 | 计费/分成/订阅(后置) |

### 5.2 限界上下文划分与职责

| 上下文 | 职责 | 核心对象 |
|---|---|---|
| Catalog | listing 搜索、分类、标签、详情页 | MarketplaceListing |
| Review | 审核状态与决策流 | ListingReviewState |
| Install | 安装/撤销/通知与安装审计 | InstallationRecord |
| Package | DP 包验证与提取 | DeploymentPackage |
| Trust | 发布者身份、扫描、签名校验 | PublisherIdentity / SecurityAttestation |

### 5.3 上下文映射关系

- method-library → Catalog: **Conformist**,方法资产真相来自上游仓
- capability-hub → Catalog: **Conformist**,MCP/Provider 资产真相来自上游仓
- governance → Review: **Open Host Service + Gate-driven**
- member-images / identity → Trust/Catalog: 镜像类资产通过签名/扫描与 Role 元数据绑定
- Install ↔ observability/notifications: **append-only audit + lifecycle propagation**

### 5.4 统一语言词汇表

| 术语 | 定义 | 使用场景 |
|---|---|---|
| MarketplaceListing | 面向市场展示和分发的资产条目 | Catalog |
| DeploymentPackage | 符合 29110 的资产包格式 | Package |
| ListingReviewState | 上架审核状态 | Review |
| InstallationRecord | 某用户/组织安装某资产的可审计记录 | Install |
| PublisherIdentity | 已验证的发布者身份 | Trust |
| SecurityAttestation | 资产扫描/签名/校验的安全证明 | Trust |

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```text
web marketplace / publisher cli
          │
          ▼
    marketplace app core
    ├─ catalog / search / filters
    ├─ review-flow integration
    ├─ package validation
    ├─ install / revoke lifecycle
    └─ trust & security gates
          │         │         │
          │         │         └────────▶ observability / notifications
          │         └──────────────────▶ governance(review gate)
          └────────────────────────────▶ method-library / cap-hub / member-images via SDK
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| web marketplace | 市场浏览、上架、审核、安装入口 | TypeScript Web | 主入口 |
| publisher CLI | 发布者打包、提交、查询审核状态 | Python CLI | 辅助入口 |
| mp-core | 目录、审核、安装共用逻辑 | TypeScript core | 共享逻辑 |
| asset-bundle | 29110 DP 打包/解包 | TS/Python tooling | 包处理 |
| review-flow | marketplace-review 集成 | TS core + SDK | 治理接入 |
| trust/security layer | 签名、扫描、发布者验证结果整合 | TS/Python | 上架门禁 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| Marketplace → 上游资产服务 | SDK | 直接写 HTTP/GraphQL | 统一契约与认证 |
| 上架审核 | governance Gate | 自写审核状态机 | 与平台治理一致 |
| 资产包处理 | 29110 DP package tooling | 自定义随意 zip | 生态资产统一格式 |
| 安装/撤销通知 | 事件/通知通道 | 静态状态修改 | 保证已安装用户可感知 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| asset truth | 上游仓 | marketplace |
| listing metadata | marketplace | users / reviewers |
| installation records | marketplace | users / audit / observability |
| security attestations | security gate / marketplace | reviewers / users |
| review state | governance + marketplace projection | reviewers / publishers |

### 6.5 部署拓扑

- Web 与 publisher CLI 分离,共享 package/review 模型
- Marketplace 运行层不应内嵌复杂支付系统,商业化能力按需后置
- 安装审计和通知链与 observability/notifications 结合,不自建孤立审计系统

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```text
web / cli shells
      │
      ▼
 marketplace core
   ├─▶ catalog / search
   ├─▶ review flow
   ├─▶ package handling
   ├─▶ install lifecycle
   └─▶ trust/security gates
           │
           ▼
      sdk-backed upstream truth + governance
```

### 7.2 层间约束规则

- Catalog 只存 listing 元数据,不上移成为资产真相源
- review flow 不绕过 governance,Marketplace 不私建平行审核体系
- package handling 只校验和提取格式,不解释上游业务语义
- Trust/security gates 不得被前端交互绕过
- Installation lifecycle 必须带审计记录,不能只更新下载计数

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| AssetSourceAdapter | marketplace core | method-library / cap-hub / member-images SDK adapters |
| ReviewFlowAdapter | marketplace core | governance Gate adapter |
| PackageValidator | package domain | 29110 DP validator |
| InstallationAuditSink | install domain | observability / audit adapter |
| TrustVerifier | trust domain | publisher auth + security tooling adapters |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(publishers / buyers / reviewers / enterprise admins) |
| 传出耦合 | 高(method-library/cap-hub/governance/member-images/observability) |
| 不稳定性 | 中高 |
| 抽象度 | 中高(listing/review/install/trust 分层清晰) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Asset truth | 上游真相仓 | marketplace | 最终一致 | listing 漂移 |
| MarketplaceListing | marketplace | users/reviewers | 强一致(市场元数据) | 错链资产 |
| Review state | governance + marketplace projection | publishers/reviewers | 最终一致 | 审核状态延迟 |
| InstallationRecord | marketplace | audit/users | append-only | 安装漏记 |
| SecurityAttestation | security tooling / marketplace | reviewers/users | 强一致(发布门禁结果) | 供应链误判 |

### 8.2 一致性层次

- 上游资产正文真相保持在 method-library / cap-hub / identity / member-images
- Marketplace 自己持有 listing、安装、通知与审核投影的局部强一致真相
- Review state、上游资产更新、撤销通知都属于最终一致传播路径

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| 上架提交成功但审核流创建失败 | governance 调用异常 | listing 保持 submitted/error,允许重试 | `listing_id + submission_id` |
| 安装成功但审计写失败 | observability 短时失败 | backlog + retry | `install_id` |
| 撤销上架通知失败 | 通知链异常 | backlog + repeated notify | `listing_id + revoke_epoch` |
| 上游资产被 retire/supersede | upstream drift | 更新 listing 状态 / 提示迁移 | `asset_ref + version` |

## 9. 关键技术选型

### 9.1 listing layer over upstream truth

| 维度 | 内容 |
|---|---|
| 当前选择 | Marketplace listing 层只引用上游真相 |
| 备选方案 | 市场复制并接管资产真相 |
| 选择理由 | 防止资产模型在市场层分叉,保持职责单一 |
| 演进路径 | 可增加 richer metadata,不接管正文真相 |
| 不可逆程度 | 高 |

### 9.2 29110 Deployment Package tooling

| 维度 | 内容 |
|---|---|
| 当前选择 | 统一 DP 包打包/解包 |
| 备选方案 | 任意 zip/tar 包 |
| 选择理由 | 生态资产需要统一、可审核、可装配的格式 |
| 演进路径 | 可按资产种类增强 schema |
| 不可逆程度 | 中 |

### 9.3 governance-backed marketplace-review

| 维度 | 内容 |
|---|---|
| 当前选择 | 走治理域 Gate 进行上架审核 |
| 备选方案 | 市场自带审核状态机 |
| 选择理由 | 保持平台治理一致性,不造并行审核体系 |
| 演进路径 | 可扩内容审/合规审/安全审子视图 |
| 不可逆程度 | 高 |

### 9.4 trust & security attestation before publish

| 维度 | 内容 |
|---|---|
| 当前选择 | 发布前做签名/扫描/发布者验证 |
| 备选方案 | 发布后抽查 |
| 选择理由 | 生态入口是供应链攻击高风险点,必须前置把关 |
| 演进路径 | 可增强 provenance / org trust levels |
| 不可逆程度 | 高 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:listing + review + install audit(当前) | 方案 B:下载页市场 | 方案 C:复制资产真相到市场 |
|---|---|---|---|
| 生态闭环 | 高 | 低 | 中 |
| 治理一致性 | 高 | 中低 | 低 |
| 真相边界 | 高 | 高 | 低 |
| 实施复杂度 | 中高 | 低 | 高 |
| 平台化潜力 | 高 | 低 | 中 |

### 10.2 最终选择与理由

选择 A,因为 Marketplace 的核心价值不是“展示资产”,而是“让资产在治理和审计约束下被可信地流通”。B 太弱,无法承接审核与安装审计；C 会让市场层污染上游领域模型。A 最符合生态飞轮的长期目标。

## 11. 横切关注点

### 11.1 韧性

| 能力 | 策略 |
|---|---|
| 重试 | 审核流、安装审计、通知失败可重试 |
| 降级 | 上游资产服务异常时保留只读浏览,暂停新安装/新上架 |
| 隔离 | catalog、review、package、install、trust 分层隔离 |
| 回退 | 发布失败与撤销通知都可回退到上次稳定 listing 状态 |

### 11.2 可观测性

| 维度 | 落地 |
|---|---|

## 12. 演进路线

### 12.1 当前架构状态与已知债务

| 债务项 | 影响 | 优先级 |
|---|---|---|
| 计费与分成模型未定 | 影响商业化闭环 | P1 |
| 组织内私有市场策略未细化 | 影响企业版适配 | P1 |
| 开源/付费资产展示区分未定 | 影响用户心智 | P1 |
| 资产信任等级与 provenance 未展开 | 影响供应链可解释性 | P2 |

### 12.2 触发条件(可量化)

| 指标 | 阈值 | 动作 |
|---|---|---|
| 上架失败率异常 | > 阈值 | 优化 package/审核/信任流程 |
| 安装审计缺失 | > 0 | 收紧 install lifecycle 和 audit sink |
| 镜像类安全问题频发 | > 阈值 | 增强 scan/sign/provenance 规则 |
| 资产搜索体验差 | > 阈值 | 强化索引、标签与分类模型 |

### 12.3 演进步骤

```text
阶段 1: 上架审核流 + 搜索/浏览 + 安装审计主路径跑通
   └─ 可停止点:Marketplace 能可信发布和安装资产

阶段 2: 撤销通知、组织内市场、分类与信任增强
   └─ 可停止点:企业与社区双路径成立

阶段 3: 商业化、分成、跨境与高级生态能力
   └─ 可停止点:Marketplace 成为生态飞轮核心
```

### 12.4 目标架构

Marketplace 的目标架构不是“资产目录”,而是 **生态流通与治理平台**:资产在这里被审核、被理解、被安装、被撤销、被审计,但始终不脱离上游真相和平台治理。未来扩展也必须围绕“真相不复制、审核前置、安装可追、生态可扩”四条主线。

## 6. 容器/部署架构

### 6.1 容器图(C4 Container 级)

```text
web marketplace / publisher cli
          │
          ▼
    marketplace app core
    ├─ catalog / search / filters
    ├─ review-flow integration
    ├─ package validation
    ├─ install / revoke lifecycle
    └─ trust & security gates
          │         │         │
          │         │         └────────▶ observability / notifications
          │         └──────────────────▶ governance(review gate)
          └────────────────────────────▶ method-library / cap-hub / member-images via SDK
```

### 6.2 每个容器的职责与技术栈

| 容器 / 进程 | 职责 | 技术栈 | 资源要求 |
|---|---|---|---|
| web marketplace | 市场浏览、上架、审核、安装入口 | TypeScript Web | 主入口 |
| publisher CLI | 发布者打包、提交、查询审核状态 | Python CLI | 辅助入口 |
| mp-core | 目录、审核、安装共用逻辑 | TypeScript core | 共享逻辑 |
| asset-bundle | 29110 DP 打包/解包 | TS/Python tooling | 包处理 |
| review-flow | marketplace-review 集成 | TS core + SDK | 治理接入 |
| trust/security layer | 签名、扫描、发布者验证结果整合 | TS/Python | 上架门禁 |

### 6.3 通信方式与选择理由

| 场景 | 选择 | 备选 | 理由 |
|---|---|---|---|
| Marketplace → 上游资产服务 | SDK | 直接写 HTTP/GraphQL | 统一契约与认证 |
| 上架审核 | governance Gate | 自写审核状态机 | 与平台治理一致 |
| 资产包处理 | 29110 DP package tooling | 自定义随意 zip | 生态资产统一格式 |
| 安装/撤销通知 | 事件/通知通道 | 静态状态修改 | 保证已安装用户可感知 |

### 6.4 数据存储归属

| 数据 | 写入方 | 读取方 |
|---|---|---|
| asset truth | 上游仓 | marketplace |
| listing metadata | marketplace | users / reviewers |
| installation records | marketplace | users / audit / observability |
| security attestations | security gate / marketplace | reviewers / users |
| review state | governance + marketplace projection | reviewers / publishers |

### 6.5 部署拓扑

- Web 与 publisher CLI 分离,共享 package/review 模型
- Marketplace 运行层不应内嵌复杂支付系统,商业化能力按需后置
- 安装审计和通知链与 observability/notifications 结合,不自建孤立审计系统

## 7. 依赖方向与层间约束

### 7.1 依赖方向图

```text
web / cli shells
      │
      ▼
 marketplace core
   ├─▶ catalog / search
   ├─▶ review flow
   ├─▶ package handling
   ├─▶ install lifecycle
   └─▶ trust/security gates
           │
           ▼
      sdk-backed upstream truth + governance
```

### 7.2 层间约束规则

- Catalog 只存 listing 元数据,不上移成为资产真相源
- review flow 不绕过 governance,Marketplace 不私建平行审核体系
- package handling 只校验和提取格式,不解释上游业务语义
- Trust/security gates 不得被前端交互绕过
- Installation lifecycle 必须带审计记录,不能只更新下载计数

### 7.3 依赖倒置的接口点

| 接口 | 定义位置 | 实现位置 |
|---|---|---|
| AssetSourceAdapter | marketplace core | method-library / cap-hub / member-images SDK adapters |
| ReviewFlowAdapter | marketplace core | governance Gate adapter |
| PackageValidator | package domain | 29110 DP validator |
| InstallationAuditSink | install domain | observability / audit adapter |
| TrustVerifier | trust domain | publisher auth + security tooling adapters |

### 7.4 依赖健康度评估

| 指标 | 当前预期 |
|---|---|
| 传入耦合 | 中(publishers / buyers / reviewers / enterprise admins) |
| 传出耦合 | 高(method-library/cap-hub/governance/member-images/observability) |
| 不稳定性 | 中高 |
| 抽象度 | 中高(listing/review/install/trust 分层清晰) |

## 8. 数据所有权与一致性策略

### 8.1 数据所有权矩阵

| 数据 | 拥有者 | 消费者 | 一致性策略 | 风险 |
|---|---|---|---|---|
| Asset truth | 上游真相仓 | marketplace | 最终一致 | listing 漂移 |
| MarketplaceListing | marketplace | users/reviewers | 强一致(市场元数据) | 错链资产 |
| Review state | governance + marketplace projection | publishers/reviewers | 最终一致 | 审核状态延迟 |
| InstallationRecord | marketplace | audit/users | append-only | 安装漏记 |
| SecurityAttestation | security tooling / marketplace | reviewers/users | 强一致(发布门禁结果) | 供应链误判 |

### 8.2 一致性层次

- 上游资产正文真相保持在 method-library / cap-hub / identity / member-images
- Marketplace 自己持有 listing、安装、通知与审核投影的局部强一致真相
- Review state、上游资产更新、撤销通知都属于最终一致传播路径

### 8.3 补偿机制设计

| 场景 | 触发 | 补偿动作 | 幂等保证 |
|---|---|---|---|
| 上架提交成功但审核流创建失败 | governance 调用异常 | listing 保持 submitted/error,允许重试 | `listing_id + submission_id` |
| 安装成功但审计写失败 | observability 短时失败 | backlog + retry | `install_id` |
| 撤销上架通知失败 | 通知链异常 | backlog + repeated notify | `listing_id + revoke_epoch` |
| 上游资产被 retire/supersede | upstream drift | 更新 listing 状态 / 提示迁移 | `asset_ref + version` |

## 9. 关键技术选型

### 9.1 listing layer over upstream truth

| 维度 | 内容 |
|---|---|
| 当前选择 | Marketplace listing 层只引用上游真相 |
| 备选方案 | 市场复制并接管资产真相 |
| 选择理由 | 防止资产模型在市场层分叉,保持职责单一 |
| 演进路径 | 可增加 richer metadata,不接管正文真相 |
| 不可逆程度 | 高 |

### 9.2 29110 Deployment Package tooling

| 维度 | 内容 |
|---|---|
| 当前选择 | 统一 DP 包打包/解包 |
| 备选方案 | 任意 zip/tar 包 |
| 选择理由 | 生态资产需要统一、可审核、可装配的格式 |
| 演进路径 | 可按资产种类增强 schema |
| 不可逆程度 | 中 |

### 9.3 governance-backed marketplace-review

| 维度 | 内容 |
|---|---|
| 当前选择 | 走治理域 Gate 进行上架审核 |
| 备选方案 | 市场自带审核状态机 |
| 选择理由 | 保持平台治理一致性,不造并行审核体系 |
| 演进路径 | 可扩内容审/合规审/安全审子视图 |
| 不可逆程度 | 高 |

### 9.4 trust & security attestation before publish

| 维度 | 内容 |
|---|---|
| 当前选择 | 发布前做签名/扫描/发布者验证 |
| 备选方案 | 发布后抽查 |
| 选择理由 | 生态入口是供应链攻击高风险点,必须前置把关 |
| 演进路径 | 可增强 provenance / org trust levels |
| 不可逆程度 | 高 |

## 10. 备选方案与取舍

### 10.1 候选方案对比

| 维度 | 方案 A:listing + review + install audit(当前) | 方案 B:下载页市场 | 方案 C:复制资产真相到市场 |
|---|---|---|---|
| 生态闭环 | 高 | 低 | 中 |
| 治理一致性 | 高 | 中低 | 低 |
| 真相边界 | 高 | 高 | 低 |
| 实施复杂度 | 中高 | 低 | 高 |
| 平台化潜力 | 高 | 低 | 中 |

### 10.2 最终选择与理由

选择 A,因为 Marketplace 的核心价值不是“展示资产”,而是“让资产在治理和审计约束下被可信地流通”。B 太弱,无法承接审核与安装审计；C 会让市场层污染上游领域模型。A 最符合生态飞轮的长期目标。

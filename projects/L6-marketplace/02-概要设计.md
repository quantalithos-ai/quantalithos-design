## 1. 先用人话理解本仓

### 1.1 这个仓是干什么的

`L6-marketplace` 不是方法资产定义仓,也不是 capability 接入真相仓,更不是单纯的“插件商店页面集合”。它是 **“生态分发、上架与交易产品层 / marketplace experience 层”**。

你可以把它理解成:
- 哪些插件、模板、方法包、能力包、桥接包可以被公开展示、发现、安装、订阅或购买
- 上架、版本、兼容性、评分、评价、交易、订阅、分发、安装这些能力怎样被统一组织
- 外部生态用户怎样理解一个资产、判断是否可用、如何获得它
- 平台怎样把内部已定义好的方法、能力和桥接资产,变成对外可消费的生态入口和商业化面

这些事情,都由 `L6-marketplace` 负责。

### 1.2 为什么要单独有这个仓

如果没有 `L6-marketplace`,这些生态分发事实就会散落在:
- `method-library` 自己暴露的 package refs 里
- `capability-hub` 自己的 capability 目录和 provider 摘要里
- `bridges` 各自的 partner/integration 展示页里
- `website` 的 teaser 页面和 CTA 导流里
- 各类手工发布页、资产列表、下载链接和运营脚本里

结果就会出现:
- 哪些资产是“可被发现、可被获取、可被安装”的没有统一主线
- listing、版本、兼容性、订阅、购买和安装彼此断裂
- 对外展示页和真实可分发资产不一致
- 生态资产的评价、趋势、推荐和运维缺少统一产品层
- 商业化与生态化能力无法从方法资产和能力资产中稳定生长出来

所以 `L6-marketplace` 必须独立存在,作为:
> **把方法资产、能力资产和桥接资产组织成可发现、可评估、可安装、可订阅、可交易的生态分发与消费层。**

### 1.3 新人最容易混淆的几个词

#### MarketplaceListing
就是:
> 一个资产在 marketplace 中的正式上架条目。

它不是该资产的权威定义真相本体。

#### PackageRelease
就是:
> 一个资产对外分发的正式版本包或可安装版本。

它不是方法定义、能力定义或桥接定义本体。

#### CompatibilityBadge
就是:
> 针对某个运行环境、宿主、版本或产品面的兼容性声明/验证结果。

它不是 runtime guarantee truth。

#### InstallRecord
就是:
> 某个用户或组织对某个资产执行安装/启用动作后的 marketplace 侧记录。

它不是下游系统已经真正激活完成的真相。

#### Entitlement
就是:
> 某个用户/组织对某类资产当前拥有的可见权益、许可或访问范围。

它不是 finance ledger,也不等于 source authorization truth。

#### Rating / Review
就是:
> 生态用户对某个资产的评分与反馈。

它不是该资产正式质量真相本体。

### 1.4 内容采集结论(本仓当前重写基线)

本次编写 `L6-marketplace/02` 时,先收稳以下前提:
- `L6-marketplace` 不应按列表页 / 详情页 / 订单页 / 评价页等页面树平铺理解,而应按生态分发与交易主链责任拆
- marketplace 至少应拆成“资产上架与目录 / 版本、兼容性与包分发 / 安装、启用与订阅消费 / 交易、权益与结算可见性 / 评价、反馈与生态运营”五个主要部分
- marketplace 自己拥有的真相不是方法定义、capability contract、bridge config、finance ledger 或 source authorization truth,而是 listing、package release、install record、entitlement view、rating/review、teaser/ranking 这类生态消费层真相
- `L6-marketplace` 只能为生态用户和组织管理员提供可发现、可安装、可订阅、可交易的消费面,不能反过来替 source systems 持有正式领域真相
- 02 的重点不是“列有哪些商店页和按钮”,而是先把“marketplace 生态分发层在平台里到底是什么、和 method-library/capability-hub/bridges/website/console 怎么分层”讲清楚
- listing、package、install、entitlement、rating/review、featured/ranking 这些不是零散功能点,而是生态主链的一部分

> **概要设计的目标不是先给出实现细节,而是先让第一次接触这个仓的人建立正确的生态分发与消费心智。**

## 2. 背景与问题定义

### 2.1 业务背景

在 Quantalithos 里,平台不仅要有方法、能力和桥接,还要能把它们变成生态资产。用户真正需要的不是“有些 package refs”,而是:
- 什么资产可以被外部或内部组织发现
- 这些资产适用于哪些场景、版本、运行环境和产品面
- 资产怎样被安装、启用、订阅、购买和升级
- 用户如何通过评分、评论、趋势和推荐判断其价值
- 平台如何把内部资产能力稳定转成生态入口

如果把这些逻辑分别散落到:
- `method-library` 的插件引用里
- `capability-hub` 的 capability 目录里
- `bridges` 的 partner 配置里
- `website` 的 teaser 和 marketing 页面里
- 一堆手工上架、下载、导出和计费脚本里

系统会快速退化成:
- 资产定义和资产消费面长期混层
- 哪些版本可安装、可见、可升级缺乏统一口径
- listing、compatibility、install、rating、entitlement 各自一套状态模型
- 生态面看起来存在,但无法真正稳定服务用户

因此,本概要设计的任务就是:
> **把 `L6-marketplace` 写成一个新人也能看懂的“生态分发、上架与交易产品层”,而不是把 listing、package、安装和计费零散散落在各个系统里。**

### 2.2 问题量化

| 问题维度 | 当前值 | 目标值 | 差距 |
|---|---|---|---|
| 生态资产统一目录 | 分散在多仓/多页 | 单一 listing / catalog 主线 | 需正式收敛 |
| package/version/compatibility 一致性 | 易漂移 | 单一 package release 主线 | 需统一建模 |
| install/enable/subscribe 行为可追踪性 | 局部实现 | 100% 样本链 | 需形成消费主线 |
| rating/review/featured | 分散 | 统一生态运营面 | 需产品化组织 |
| transaction/entitlement 可见性 | 局部 | 统一体验层 | 需和账本真相分层 |

### 2.3 业务问题 vs 技术问题

- **业务问题**:如何把内部方法资产、能力资产和桥接资产稳定转化为可发现、可评估、可安装、可订阅、可交易的生态消费面
- **技术问题**:MarketplaceListing、PackageRelease、CompatibilityBadge、InstallRecord、Entitlement、Rating/Review 与 method-library / capability-hub / bridges / website / console 之间的边界如何稳定建模,并形成统一 marketplace 主链

## 3. 目标与非目标

### 3.1 目标(可验证)

| 目标 | 指标 | 验收方式 |
|---|---|---|
| 明确 marketplace 的生态分发职责 | listing / package / install / entitlement / rating 职责无歧义 | 文档评审 |
| 明确与 method-library / capability-hub / bridges / website 边界 | 资产消费层与 source truth、账本真相、生态导流分离 | 文档评审 + 后续测试 |
| 明确安装与交易可见性主线 | install / subscribe / purchase / upgrade 主线可验证 | 集成测试 |
| 支撑后续详细设计与测试 | 本文足以承接 `03-详细设计.md` 的 listing、package、install、transaction、review 设计 | 设计评审 |

### 3.2 非目标(明确不做)

- 不在本文替代 method-library / capability-hub / bridges 的 source truth
- 不在本文替代 account/member truth、finance ledger truth 或支付系统本体
- 不在本文实现包存储平台本体
- 不在本文替代 console / website 的入口和容器本体
- 不在本文定义所有广告、投放和复杂促销能力

## 4. 约束条件

### 4.1 技术约束

- 所有 marketplace 可见资产都必须通过正式 Listing / Release 主线进入
- listing、compatibility、install、review、entitlement 都必须能回指 source refs
- install/enable 行为只能表达 marketplace 消费结果,不能直接冒充 source system 激活真相
- transaction/subscription 可见性必须和 finance ledger truth 分层
- rating/review/featured/ranking 只能表达生态反馈与运营结果,不能反向覆盖资产真相

### 4.2 资源约束

- 资产数量、版本数量、兼容性矩阵、评价与订阅记录会持续增长,索引复杂度必须受控
- package / artifact 分发不能拖垮 source systems 或 package storage
- 高并发 catalog 查询、搜索和筛选不能直接依赖 source truth 在线查询

### 4.3 时间约束

- 当前阶段先收稳统一 marketplace 主链,而不是先做复杂动态定价、拍卖、跨区域分发或高级推荐算法
- listing、package、install、entitlement、review 五条基础链必须优先稳定,否则生态消费面会长期失控

### 4.4 合规约束

- 未公开或未授权资产不得出现在公开 catalog
- install / subscribe / purchase / uninstall 记录必须留审计证据链
- compatibility 信息不得夸大为绝对运行保证
- transaction / subscription 可见性不得冒充 finance ledger truth

### 4.5 容量规划

| 资源 | 上限 | 量化依据 |
|---|---|---|
| listings | 高 | 生态资产增长需求 |
| package releases | 高频 | 多版本、多渠道发布需求 |
| install / subscription events | 高频 | 用户消费与升级需求 |
| reviews / ratings | 高 | 长期生态反馈需求 |

## 5. 本仓在全局架构中的位置

### 5.1 系统上下文图

```text
                    ┌────────────────────────────┐
                    │ method / hub / bridges      │
                    │ website / docs / console    │
                    │ - source assets / refs      │
                    └────────────┬───────────────┘
                                 │ marketplace source input
                                 ▼
                    ┌────────────────────────────┐
                    │ L6-marketplace            │
                    │ - listing / package / tx   │
                    │ - install / review / usage │
                    └────────────┬───────────────┘
                                 │ marketplace experience output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ ecosystem users / org admins│  │ console / website          │   │ finance / analytics        │
│ - discover / install / rate │  │ - entry / embedding        │   │ - subscription views       │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 5.2 位置解释

- `L6-marketplace` 自己负责资产上架、版本分发、安装/启用/订阅/交易体验、评分反馈与生态运营主线
- `method-library`、`capability-hub`、`bridges` 提供 source assets 和 package refs,但 marketplace 不拥有它们的源真相
- `website` 和 `console` 提供入口与嵌入能力,但 marketplace 负责生态消费语义
- 外部用户、生态开发者、组织管理员是 marketplace 的直接消费方
- finance / analytics 消费的是 transaction/subscription/usage 视图,而不是 marketplace 的 source truth 本体

所以 `L6-marketplace` 在全局里的角色是:
> **把方法资产、能力资产和桥接资产组织成可发现、可评估、可安装、可订阅、可交易的生态分发与消费层。**

### 5.3 系统边界

**做什么**:
- 定义 marketplace listing / catalog / teaser
- 定义 package release / compatibility / install bundle
- 管理 install / enable / disable / subscribe / uninstall / upgrade 体验
- 管理 rating / review / featured / ranking / feedback
- 输出 transaction / subscription / entitlement 的体验层视图

**不做什么**:
- 不持有 method/capability/bridge source truth
- 不替代 finance ledger / account/member truth / package storage truth
- 不替代 website / console 的入口或容器本体
- 不直接保证 runtime 最终激活真相

### 5.4 外部系统可用性约束与降级

| 外部依赖 | SLA | 降级策略 |
|---|---|---|
| method-library / capability-hub / bridges refs | 99.9% | 摘要缺失时隐藏 listing 或降级占位,不伪造资产真相 |
| package storage / release refs | 99.9% | package 不可读时禁止安装并保留 listing 可见性 |
| account / auth / purchase target | 99.9% | 登录/购买不可达时 CTA 降级并标记 unavailable |
| finance / entitlement views | 99.9% | ledger/授权延迟时展示 pending/stale,不伪造已生效 |
| console / website entries | 99.9% | 某入口不可用不影响 catalog 目录可见 |

### 5.5 关键依赖风险

- listing 与 source asset truth 漂移会直接误导生态用户
- compatibility badge 若被误当保证真相,会放大安装失败预期差
- install record 与下游激活真相混层,会造成“看起来装好了其实没生效”
- transaction/subscription 可见性若和 ledger truth 混层,会造成财务/权益误判
- review/ranking 若直接影响 source truth,会污染正式资产评价边界

### 6.2 主要组成部分说明

> 这里的“主要部分”不是把列表页、详情页、订单页、评价页等页面元素横向平铺。  
> 它按 **生态分发与交易主链职责 + 上架 / 分发 / 安装 / 权益 / 运营差异** 来拆分。  
> 因此下面每一部分都可能包含多个市场对象和机制,共同支撑同一段 marketplace 主链。

#### 资产上架与目录部分

- **它是什么**: 这是 `L6-marketplace` 的主入口层,一起回答“哪些资产可以被公开发现”
- **为什么单独有它**: marketplace 的第一步是可见和可发现,如果没有独立 listing/catalog 层,后续版本、安装、交易都会失去锚点
- **负责什么**:
  - 定义 listing / catalog / categories / tags / publisher summary
  - 管理 visibility / publish state / discoverability
  - 组织外部可见的资产目录
- **不负责什么 / 容易混淆点**:
  - 不持有 source asset truth 本体
  - 不持有 package release truth 本体
  - 不直接处理 install/transaction 结果
  - 最容易和 source asset definition、website teaser、marketplace transaction 真相混淆
- **与其他部分交互**:
  - 下游: version/compatibility、install/entitlement、reviews/ranking
  - 外部: method-library / hub / bridges / website / console
  - 交互类型: listing/catelog 型 + public discoverability 型
- **后续详细设计展开点**:
  - MarketplaceListing / catalog / visibility 主线

#### 版本、兼容性与包分发部分

- **它是什么**: 这是 marketplace 的分发层,一起回答“资产版本怎样被可靠分发”
- **为什么单独有它**: 资产被发现之后,必须通过 package release 和 compatibility 进入真正可消费状态,不单列就会与 listing/install 混层
- **负责什么**:
  - 定义 package release / release channel / compatibility matrix / install bundle
  - 组织 delivery artifacts 与 package refs
  - 提供版本分发和兼容性可见性
- **不负责什么 / 容易混淆点**:
  - 不持有 package definition truth 本体
  - 不替代 runtime guarantee truth
  - 不直接决定 install 成功与否
  - 最容易和 package 真相、runtime guarantee、artifact source truth 混淆
- **与其他部分交互**:
  - 上游: listing、source asset refs
  - 下游: install / upgrade / entitlement 消费
  - 交互类型: release/distribution 型 + compatibility 型
- **后续详细设计展开点**:
  - PackageRelease / CompatibilityBadge / install bundle 主线

#### 安装、启用与订阅消费部分

- **它是什么**: 这是 marketplace 的使用落地层,一起回答“用户怎样真正开始使用资产”
- **为什么单独有它**: 发现和分发之后,用户还需要 install/enable/subscribe/upgrade,这条链最容易和 source activation 真相混层
- **负责什么**:
  - 管理 install / enable / disable / uninstall / upgrade
  - 管理 subscribe / follow / auto-update
  - 形成 install records 与消费主线
- **不负责什么 / 容易混淆点**:
  - 不持有 installed system truth 本体
  - 不持有 source package activation truth
  - 不替代 runtime 或 console 的实际激活结果
  - 最容易和下游系统实际启用真相、member/account 权限真相混淆
- **与其他部分交互**:
  - 上游: package releases / compatibility
  - 下游: transaction/entitlement、rating/review、console / website / users
  - 交互类型: install/enable 型 + consumption 型
- **后续详细设计展开点**:
  - InstallRequest / InstallRecord / SubscriptionState 主线

#### 交易、权益与结算可见性部分

- **它是什么**: 这是 marketplace 的商业化层,一起回答“交易与权益怎样被表达”
- **为什么单独有它**: 一旦进入订阅/购买/授权,就必须和 catalog/install 以及 finance ledger 分层,否则会长期混乱
- **负责什么**:
  - 表达 purchase / subscription / entitlement / license / invoice snapshot
  - 给用户和组织管理员提供可见的权益与账单摘要
  - 组织 pending/active/expired 等消费面状态
- **不负责什么 / 容易混淆点**:
  - 不替代 finance ledger truth
  - 不替代 member/account 真相
  - 不替代 source authorization truth
  - 最容易和支付系统真相、账本真相、系统实际授权真相混淆
- **与其他部分交互**:
  - 上游: install/subscribe 行为、payment/auth inputs
  - 下游: reviews、owners、console、website
  - 交互类型: transaction visible 型 + entitlement 型
- **后续详细设计展开点**:
  - transaction views / entitlement / license summary 主线

#### 评价、反馈与生态运营部分

- **它是什么**: 这是 marketplace 的生态运营层,一起回答“生态资产怎样被反馈和持续运营”
- **为什么单独有它**: marketplace 不只是分发和交易,还要支撑评分、评论、排行、推荐和精选。但这些反馈不能反向污染资产真相
- **负责什么**:
  - 管理 rating / review / featured / ranking / editorial picks
  - 管理 download/install trend / abuse/report / moderation hints
  - 提供生态运营反馈面
- **不负责什么 / 容易混淆点**:
  - 不替代 asset quality truth
  - 不替代 moderation/finance 正式真相本体
  - 不直接决定 source package 真相
  - 最容易和质量结论、运营指标、业务惩罚真相混淆
- **与其他部分交互**:
  - 上游: install/subscribe/usage summaries
  - 下游: ecosystem users / owners / growth / moderation
  - 交互类型: feedback/rating 型 + ecosystem operations 型
- **后续详细设计展开点**:
  - rating/review / ranking / moderation 主线

## 7. 本仓如何与其他模块交互

### 7.1 总交互图

```text
                    ┌────────────────────────────┐
                    │ method / hub / bridges      │
                    │ website / docs / console    │
                    │ - source assets / refs      │
                    └────────────┬───────────────┘
                                 │ marketplace source input
                                 ▼
                    ┌────────────────────────────┐
                    │ L6-marketplace            │
                    │ - listing / package / tx   │
                    │ - install / review / usage │
                    └────────────┬───────────────┘
                                 │ marketplace experience output
                                 ▼
┌────────────────────────────┐   ┌────────────────────────────┐   ┌────────────────────────────┐
│ ecosystem users / org admins│  │ console / website          │   │ finance / analytics        │
│ - discover / install / rate │  │ - entry / embedding        │   │ - subscription views       │
└────────────────────────────┘   └────────────────────────────┘   └────────────────────────────┘
```

### 7.2 总解释

- `L6-marketplace` 自己负责“组织 listing 和 catalog”“组织 package release 和 compatibility”“组织 install/subscribe/entitlement 体验”“组织 rating/review/ranking 运营面”
- `method-library` / `capability-hub` / `bridges` 的交互主要落在 **资产上架与目录部分** 与 **版本、兼容性与包分发部分**,为 marketplace 提供 source assets、package refs 和 public summaries 输入
- `website` / `console` 的交互主要落在 **资产上架与目录部分** 与 **转化/消费主线**,为 marketplace 提供入口承载和嵌入消费面
- finance / auth / analytics 的交互主要落在 **交易、权益与结算可见性部分** 与 **评价、反馈与生态运营部分**,为 marketplace 提供授权、支付和运营观察面补充
- 生态用户和组织管理员消费的是 marketplace 提供的 listing/install/review/entitlement 体验层,而不是直接理解 source truth 结构

### 7.3 分模块交互说明(逐个写)

#### 与 `method-library / capability-hub / bridges` 的交互

```text
┌────────────────────────────┐
│ method / hub / bridges     │
│ - source assets / package  │

             │ marketplace asset input
             ▼
┌────────────────────────────┐
│ marketplace                │
│ - listing / releases       │
└────────────────────────────┘
```

- 这些系统是 **资产来源方**
- **交互类型**: asset/package/source refs 输入型交互
- **主流程位置**: listing build、package release、compatibility compute、publish/unpublish 时进入主流程
- **交互解释**:
  - marketplace 只消费 source asset refs
  - 不替代 method/capability/bridge source truth 本体
- **高风险异常流**:
  - listing 摘要漂移后被误当 source truth
- 后续 `03-详细设计.md` 继续展开:
  - MarketplaceListing contract
  - release / compatibility 主线

#### 与 `website / console` 的交互

```text
┌────────────────────────────┐
│ website / console          │
│ - teaser / embedding       │
└────────────┬───────────────┘
             │ marketplace entry output
             ▼
┌────────────────────────────┐
│ marketplace                │
│ - catalog / details / flow │
└────────────────────────────┘
```

- 这些系统是 **入口承载方**
- **交互类型**: entry/embedding 输出型交互
- **主流程位置**: listing browse、details open、install/purchase flow 时进入主流程
- **交互解释**:
  - marketplace 负责生态消费语义
  - website 和 console 负责入口承载
  - 不等于 source truth 本体
- **高风险异常流**:
  - teaser/entry 被误当 listing 真相本体
- 后续 `03-详细设计.md` 继续展开:
  - teaser/detail/embed 主线

#### 与 `finance / auth / analytics` 的交互

```text
┌────────────────────────────┐
│ marketplace                │
│ - install / tx / review    │
└────────────┬───────────────┘
             │ transaction/usage output
             ▼
┌────────────────────────────┐
│ finance / auth / analytics │

└────────────────────────────┘
```

- 这些系统是 **交易、权益与运营消费/补充方**
- **交互类型**: subscription/entitlement/usage 输入输出型交互
- **主流程位置**: install、purchase、subscribe、review、featured/ranking 更新时进入主流程
- **交互解释**:
  - marketplace 只表达交易与权益的体验层可见状态
  - finance/auth/analytics 才持有各自真相本体
- **高风险异常流**:
  - entitlement 可见性被误当 source authorization truth
- 后续 `03-详细设计.md` 继续展开:
  - entitlement / rating / funnel 主线

### 7.4 本节与详细设计的边界

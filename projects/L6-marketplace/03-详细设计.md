## 1. 模块职责描述

**本模块做什么**:
- 持有正式 MarketplaceListing / PackageRelease / CompatibilityBadge / InstallRecord / EntitlementView / RatingReview / RankingView 等生态消费层真相
- 把方法资产、能力资产和桥接资产组织成统一的 listing、release、install、subscribe、transaction、review 主线
- 管理 package/version/channel、compatibility、install/upgrade/uninstall、purchase/entitlement、rating/review/featured/ranking 体验
- 为 ecosystem users、组织管理员、website、console、growth/finance 提供统一的生态消费与运营面

**本模块不做什么**:
- 不持有 method-library / capability-hub / bridges 的 source truth
- 不替代 account/member truth、finance ledger truth、支付系统本体或 package storage 本体
- 不直接保证 runtime/source system 最终激活真相
- 不替代 website / console 入口壳或 analytics 平台本体

## 2. 前置设计前提 / 内容采集提示

### 2.1 为什么在写 03 前要先采集内容

`03-详细设计` 的目标不是再讲 marketplace“为什么存在”,而是让开发者可以直接开始实现:
- source assets / package refs 如何进入正式 MarketplaceListing 主线
- package release / compatibility matrix 怎样形成可分发、可安装的生态版本面
- install / subscribe / purchase / entitlement 怎样形成消费主线而不混入 source truth
- rating/review/featured/ranking 怎样作为运营与反馈面存在而不污染资产真相
- console / website / finance / analytics 怎样消费 marketplace 输出而不反向控制 source truth

如果不先把这些内容采集清楚,03 很容易退化成:
- 商店详情页字段清单
- 订单与支付页面草图
- 兼容性 badge 的展示说明
- listing、install、review、entitlement 各写一套彼此脱节的状态模型

## 5. 按主要部分展开实现要点

### 5.1 为什么要先按主要部分展开

`03-详细设计` 不能直接从 `MarketplaceListing / PackageRelease / InstallRecord / EntitlementView / RatingEntry` 这些对象平铺开始。
更稳的写法是:
- 先承接 `02-概要设计.md` 已确认的五个主要部分
- 再说明每个主要部分分别落到哪些对象、命令/函数、状态约束、存储与对外消费
- 最后再进入横向的对象模型、流程、存储、异常与测试细节

这样可以避免:
- `02` 讲的是生态分发与消费主链,`03` 却退化成列表页、订单页、评价页的页面清单
- 实现者知道有 listing、install、review,却不知道它们如何和 compatibility、entitlement、ranking 构成同一条生态主线
- 目录、分发、安装、交易、运营各写一套,彼此断裂

fn create_marketplace_listing(

- MarketplaceListing、PackageRelease、InstallRecord、EntitlementView、RatingEntry 属于强一致写路径
- catalog/detail/compatibility/install/ranking/featured 视图属于可最终一致读路径
- catalog_view / compatibility_view / ranking_view 绝不能反向成为 source truth、ledger truth 或 package truth 写源
- install / entitlement / ranking 的分歧必须回收到 source refs、install history、purchase history、review history 对账主线

## 11. 异常与补偿设计

| 场景 | 处理 |
|---|---|
| source asset refs 缺失 | 拒绝 listing 或下架 |
| compatibility 计算失败 | 阻断 install 或标记 unknown |
| install 成功记录已写但 source activation 未完成 | 标记 pending/partial |
| entitlement 状态与 payment/auth 不一致 | 标记 conflict / refresh required |
| rating/review 缺 install 上下文 | 拒绝提交 |
| featured/ranking 证据不足 | 阻断运营更新 |

### 11.1 重试 / 降级 / 熔断 / 补偿
- package refs 暂不可用时可保留 listing 可见性但禁止安装
- entitlement 延迟时可显示 pending/stale,但不得伪造 active
- review/ranking 更新失败时可 backlog + retry,但必须保留反馈与使用证据

### 11.2 按主要部分归属的失败模式

| 主要部分 | 典型失败 | 检测点 | 处理策略 | 补偿 / replay |
|---|---|---|---|---|
| 资产上架与目录部分 | listing 与 source refs 漂移 / visibility 错误 | listing source boundary validate | 拒绝上架或下架 | 重新同步 refs |
| 版本、兼容性与包分发部分 | compatibility 漂移 / bundle 缺失 | release source boundary validate | 阻断 install | 重建 compatibility/bundle |
| 安装、启用与订阅消费部分 | install 已记录但真实启用未完成 | install boundary validate | 标记 pending/partial | 重新对账 activation |
| 交易、权益与结算可见性部分 | entitlement 与 ledger 结果冲突 | entitlement boundary validate | 标记 conflict / refresh | 重拉 auth/payment 结果 |
| 评价、反馈与生态运营部分 | rating/review/ranking 无证据链 | ranking boundary validate | 拒绝更新或回滚排名 | 重建 feedback/usage 聚合 |

## 14. 最小可运行闭环

- 一个 source asset 通过 MarketplaceListing 进入公开 catalog,并绑定至少一个 PackageRelease 和 CompatibilityBadge
- 用户能对该 release 发起 InstallRequest,系统形成 InstallRecord 与 EntitlementView,同时清楚地区分“已安装记录”和“已真正激活”
- 用户或生态运营方能基于该资产提交 Rating/Review,系统生成 RankingView/FeaturedSlot,且整个反馈链可回指安装与使用证据

## 15. 结论

本详细设计的核心结论是：
- `L6-marketplace` 的实现主轴必须按 listing / release / install / commerce / ecosystem 五个主要部分组织,而不是按列表、详情、订单、评价页面平铺
- marketplace 真相层只持有 listing、release、install、entitlement、rating/review 等生态消费层真相,不接管 method-library、capability-hub、bridges、finance、account 的 source truth
- 所有 MarketplaceListing、PackageRelease、InstallRecord、EntitlementView、RankingView 都必须建立在稳定 source refs、兼容性结果和 append-only 交易/安装/反馈证据链之上

后续测试与验收文档,应直接围绕这套生态分发主线、安装与权益边界、评价与运营主线展开.

## 2. 验收目标与范围

> 校准来源：
> - `design-calibration/06_acceptance_step_02_scope.md`
> - `design-calibration/06_acceptance_step_05_function_gate.md`
>
> 延伸阅读：
> - 建议继续阅读范围文件的“结构化中间产物”和功能门禁文件的“独立功能验收项审查”，查看五能力、20 AC和三种证明范围的完整边界。

### 2.1 验收目标

验证发布申请、Governance handoff消费、目录/版本上架、受控获取、撤回/影响通知、审计和有限恢复在声明范围内具备可判定的契约、边界、状态、事务、失败恢复和证据闭环。验收不产生Governance approval、publisher认证、owner内容、安装/付款/送达结果或生产readiness。

### 2.2 In Scope

| 范围 | P0验收目标 | 证明边界 |
|---|---|---|
| 来源与责任 | exact owner/type/ref/version/digest/visibility/scope绑定，缺口fail-closed | 不自产publisher、正文、材料或digest |
| 申请与审核 | Draft、Submit冻结、handoff、正式决定匹配、current gate上架 | Governance正式决定由外部消费；rejected不可List |
| 目录/搜索/版本 | listing壳、分类、搜索、版本选择、可见性和稳定分页 | 不复制资产目录、不fallback最新、不由索引授权 |
| 受控获取 | exact版本/consumer/receiver/scope下建立局部分发责任 | Accepted/Confirmed不等安装、支付或交付 |
| 撤回/影响/通知 | 停新准入、固定upper影响、late增量、NoticeIntent | 不承诺全安装覆盖、送达或已读 |
| 审计/恢复/配置/Web | refs-only audit、原结果重放、有限恢复、同源配置和中英文展示 | 运行指标不证明owner接受或外部成功 |

### 2.3 三类证明范围

| scope | 必须验证 | 不得外推 |
|---|---|---|
| `local-contract` | 全98 TC、11主suite、所有required subcase、实际PG/API/Worker/Web和typed fake边界 | formal owner、Governance approval、安装、支付、通知送达、production ready |
| `formal-integration selected` | local全量基线加送验前冻结的exact owner/type/operation/version/scope实际positive接缝 | 未选择的接缝和fake positive |
| `capacity-candidate` | 经批准workload的raw sample/trend，区分owner等待和本地耗时 | 生产SLO、保留策略、验收三值或发布许可 |

scope在run前冻结。scope、实现、设计、配置、测试库存或owner资格变化必须新baseline/new run/new review；不得失败后删除接缝或挑选通过子例缩scope。

### 2.4 Out of Scope

评分、排名、推荐、收藏、安装激活、Entitlement/Package正文、Billing/支付/订阅/收入分成/跨境交易、Archive恢复写入、active Event/outbox以及无正式owner的生产容量/通知SLO不构成本验收主线。若要纳入，必须先受控回到00/01并重新完成后续文档闭环。

未来送验必须固定下列基线；当前所有值均未提供：

### 3.1 固定证据路径

机器产物统一为 `artifacts/test/<run_id>/` 与 `reports/runs/<run_id>/`；EV必须配对：

```text
reports/runs/<run_id>/evidence/<完整EV-ID>.md
artifacts/test/<run_id>/evidence/<完整EV-ID>.json
```

每个EV还必须回同run `evidence-index.md`、主suite的机器/Markdown报告及该TC所有required raw。禁止 `latest`、项目名重复目录、绝对/逃逸路径、跨run引用、静态pass和覆盖旧run。

人工交接固定为三个append-only入口：

```text
reports/acceptance/handoff.md
reports/acceptance/veto-checklist.md
reports/acceptance/risk-acceptance.md
```

每个入口必须指向显式 `reports/acceptance/<run_id>-<review_id>-{handoff|veto-checklist|risk-acceptance}.md` 详情并登记scope、phase、实际raw-byte摘要和supersedes关系；不得自动选最新记录。人工详情不属于05机器RecordRef/DAG，不产生verdict。

### 4.1 合格送验进入条件

- [ ] scope、exclusions、baseline、run_id、review_id和证明层级已冻结。
- [ ] actual实现、构建、依赖lock、环境、配置、DS和必要owner资格可查；原型/planned路径不算交付。
- [ ] 全98主TC、11主suite及全部required subcase按manifest执行，不挑选passed。
- [ ] actual PostgreSQL、多连接、API/Worker/Web/browser及故障窗口满足所需证明层级。
- [ ] artifact/seal两阶段六checks、schema/hash/redaction/coverage、raw/report/JSON/MD配对完整。
- [ ] 98 EV/index、机器draft、handoff/veto/risk三入口和不可变详情均由实际材料生成/审查。
- [ ] 无S、VETO、scope内P0阻断A、缺证据、缺必要positive资格或污染材料；合法expected拒绝不算缺陷。

### 4.2 结束审查条件（不等放行）

- [ ] 本scope每20 AC、17 NFR、专项门禁、49入口、14 carrier/222 pair及所有required EV均有实际裁决。
- [ ] 五VETO逐项以实际证据核查；未核查不能填写“未触发”。
- [ ] 首次失败、fresh复验、flaky/blocked/unavailable、证据失效和开放项责任明确且保留历史。
- [ ] 功能、非功能、发布准备和总体结论均使用三值并回指固定证据。
- [ ] 实际验收authority、角色分权、日期和不可变签署记录完整。

### 4.3 授予通过的条件

全部P0满足、五VETO无实际触发、证据完整、scope内正式positive资格成立且无阻断缺陷时才可“通过”。只有已由真实具权authority接受的非P0残余才可“有条件通过”。缺P0、资格、证据、VETO核查、签署或未接受风险时不得放行；审查可以结束为“不通过”。生产发布另需产品/安全/运维与部署材料。

| A | 主线、状态、字段、分页、原结果、配置、PG、报告工具或locale语义风险 | 本scope P0阻断；只有证明非P0隔离并经正式authority接受才可条件通过 | 原失败+正反/边界/邻接CUT，fresh同baseline；资格缺口不当代码缺陷关闭 |
| B | 不影响gate、数据、状态、权限、语义、追溯的纯展示问题 | 未接受不能放行；真实已接受的非P0才可条件通过 | 明确影响/排期，抽样修复验证；最终送验仍需全量 |

`blocked`、`unavailable`、`not_run`、缺positive资格或manifest遗漏不是P0 pass；expected的安全拒绝、CommitUnknown或ContractBlocked在断言正确时可以是TC pass。当前没有实际 `defect_id`、fix commit、retest或关闭状态。

缺陷生命周期为 `open → triaged → fix_pending → retest_pending → closed`；复验失败为 `reopened`，延期为 `deferred` 而非 closed。记录必须含实际 defect/severity/state、affected TC/CUT/AC/VETO、design/baseline、失败run/raw/report、DS/seed/subcase、expected/actual安全差异、root cause、fix/new run/retest/EV、reviewer/authority和residual risk。缺真实引用不得造值。

首次失败、旧run和污染证据必须保留；实现/设计/owner/schema/config/profile/DS/scope变化使受影响EV失效，必须新baseline/new run/new review，不能跨run拼接或手改旧index。shared契约、S级或多U变更最终执行全11suite/98TC/全部required subcase；smoke/局部复验不替代全量。

### 14.1 三值算法

正式裁决只允许 `通过`、`有条件通过`、`不通过`。`未送验/未裁决`是过程状态，不是三值结论。

| 顺序 | 条件 | 结论/许可 |
|---|---|---|
| 0 | 没有实际run、审查、authority或scope/baseline未冻结 | 保持未送验/未裁决；不填三值 |
| 1 | 任一VETO/S实际触发 | 不通过；不能风险接受/签署抵消 |
| 2 | 任一P0、required证据、正式positive资格、mandatory check未满足 | 不通过候选；不能用negative pass或缩scope补齐 |
| 3 | P0成立但有未接受/过期/缺七字段残余 | 不通过；无接受人不能条件通过 |
| 4 | 全部P0/VETO/证据/资格成立，只有真实authority接受的非P0残余 | 有条件通过，许可限于明确scope/动作/期限 |
| 5 | 全部P0/VETO/证据/资格成立且残余关闭，签署完整 | 通过；仍不等production-ready或外部owner approval |

维度不平均、不以百分比抵消；未核查VETO不默认无触发。功能、非功能、发布准备、总体结论分别记录三值，并明确local或formal-selected证明范围。capacity-candidate只能提供样本/趋势，不能填写业务三值。

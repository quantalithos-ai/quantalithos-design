## 3. SOP 问题回答

1. 结束后成立什么？市场事实与 owner 真相分离；可信上架门槛可判定；可见发现与版本选择可说明；分发/撤回/通知与失败责任可追溯。
2. 如何验证？逐项正负向情景及跨章追溯，未来测试不能用原型或文档检查代替实际集成。
3. 不纳入什么？外部正文、approval、认证与组织资质真相、安装激活、财务交易、无 owner 的可执行包。
4. 谁处理？对应资产 owner、Governance、认证/授权 owner、正式接收系统；无正式 owner 的保留 future/blocker。

## 4. 当前文档问题诊断

旧 00 §3 G-2 包打包/解包越过资产包 owner，G-3 身份验证没有正式认证来源，G-4 将审计视为安装证明。旧 NG-5 只排除“复杂”计费，会留下私造简单账本的漏洞。

## 5. 改动前后对比

| 项 | 改前 | 改后 | 原因 |
|---|---|---|---|
| 目标 | 功能名+100% | 能成立的边界/结果+验证方式 | 不混功能与证据 |
| 商业范围 | 不做复杂计费 | 无 owner 不做任何财务 truth | 简单支付也需正式 authority |

## 6. 设计取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 完整市场闭环需求+条件正向门槛 | 可以先约束可信边界 | 实现不能立即全部放行 | 采用 |
| 只做目录或默认免费绕过前置 | 快速展示 | 无可信分发/撤回，免费也不替代授权 | 不采用 |

## 7. 结构化中间产物

| 目标 | 说明 | 验证方式 |
|---|---|---|
| G-MP-1 市场责任唯一 | 市场局部事实不替代任何外部真相 | 数据/规则边界与负向案例审查 |
| G-MP-2 可信上架 | publisher、owner 引用、材料及正式治理决定共同限定上架 | 缺失、过期、错版本和有效绑定情景 |
| G-MP-3 可见发现与版本选择 | 用户可区分五类候选资产、市场版本与来源版本 | 可见/不可见/撤回/无可用版本情景 |
| G-MP-4 受控分发 | 获取关系与接收结果清楚，不虚构安装/支付 | 重复、失败、未知和确认情景 |
| G-MP-5 撤回责任与恢复 | 阻止新分发、识别已知影响、通知及审计失败可追溯 | 并发撤回、重试、未知接收与恢复情景 |

| 非目标 | 不做原因 |
|---|---|
| NG-MP-1 资产正文/版本链/Registry | 对应资产与 Artifact owner 拥有 |
| NG-MP-2 审核批准与认证/授权真相 | Governance 与正式安全 owner 拥有；publisher 验证 owner 尚缺 |
| NG-MP-3 安装/成员创建/运行激活 | 接收系统拥有，分发 ACK 不证明激活 |
| NG-MP-4 Billing、支付、订阅、分成、跨境交易 | 无正式 owner；全部 future/blocker，不建局部账本冒充 truth |
| NG-MP-5 无合同的 Deployment Package 执行/打包 | 包 owner、29110 适用范围、安装回退合同未闭合 |
| NG-MP-6 评分评论、推荐、持久收藏及高级统计 | 外围增强，不是核心可信发布分发前提 |

复杂度：两表足够；资产包格式要求本身不废弃，适用与 owner 缺口放 §15，不能宣称合规通过。

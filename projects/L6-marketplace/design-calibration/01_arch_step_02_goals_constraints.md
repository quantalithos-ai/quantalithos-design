## 2. SOP问题回答

必须成立的是：市场独立事实、跨owner来源不污染、市场生命周期与审核/接收分层、可见性贯穿读取和写入、撤回与并发分发守同一边界、恢复有来源。不可变红线是无外部正文/approval/auth/install/finance truth；可接受收缩为外围推荐/评论/归档候选不进入核心。可以结构性判定同意图结果唯一、撤回后无新分发、查询零业务写；容量数字没有依据。人类认证系统、receiver执行与Billing不是本仓要设计的系统。

## 3. 输入诊断

旧01§1“100%合法包/全安装通知”把愿景和测量混合；00§13稳定的是有界/可判别而非具体SLO。不能以技术栈熟悉度充当目标，也不能把缺owner写成“当前不做深认证”。

## 4. 设计取舍

采用结构目标+红线+范围收缩+非目标四类；不采用功能清单当目标，因其不能约束后续责任划分。未qualified集成保持条件，不阻止负向边界完整设计。思考done，允许结构化。

## 5. 结构化中间产物

### 正式§2架构目标

| 架构目标 | 说明 |
|---|---|
| AG-MP-1 承载唯一市场事实 | 否则listing、市场版本与分发责任散落owner/UI。 |
| AG-MP-2 守住来源、审核、市场状态三重边界 | 否则摘要/扫描可能成为第二approval或资产truth。 |
| AG-MP-3 支撑全读取与写入的同scope判断 | 否则搜索总数或后台成为泄漏/绕权路径。 |
| AG-MP-4 支撑分发与撤回竞争的可判别结果 | 否则用户无法区分新获取、既有交接及unknown。 |
| AG-MP-5 允许有来源的延后收敛与恢复 | 否则通知/audit故障会阻塞撤回或伪造成功。 |

### 正式§3约束、取舍、非目标

| 约束 | 说明 |
|---|---|
| 不拥有/复制外部正文及asset truth | owner不可变引用/version/digest/visibility必须来自owner。 |
| 不产生审核批准、身份授权、安装或财务truth | 自有状态仅限市场process，ACK/scan/签名非批准。 |
| 不静默换版本、不凭索引授权 | exact绑定及当前资格须贯穿获取。 |
| 不在外部commit未知时盲重试 | 未知独立、原意图对账，不创造第二结果。 |
| 不从配置或恢复绕gate | 来源失效/撤回不因backlog恢复而复活。 |
| 不越全局依赖/技术约束 | Core/SDK compile与owner runtime分开；draft不可覆盖全局。 |

| 取舍 | 当前口径 |
|---|---|
| 评分/推荐/收藏/高级统计 | 外围增强，不当前核心。 |
| CLI入口 | 可选薄客户端，Web/API/Worker为当前运行主线。 |
| 更强搜索及更细运行拆分 | 先有界局部投影，测量后按结构压力重审。 |
| 市场Archive接缝 | 候选未qualified，不开放export/restore。 |

| 非目标 | 不展开原因 |
|---|---|
| 资产定义/Registry/镜像构建/Artifact正文架构 | 专项owner拥有。 |
| Approval及人类认证/组织资质裁决架构 | Governance及正式security owner拥有。 |
| receiver安装/Member创建/激活架构 | 本仓仅关系与反馈映射。 |
| Billing/订阅/结算/跨境架构 | 无owner，future/blocker；不是可采用的市场方案。 |
| 自建29110可执行包truth | 规范适用和包owner未闭合，保留合规要求而不假造。 |

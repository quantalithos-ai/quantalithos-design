## 1. 总体技术形态

`L6-marketplace` 保持一个设计项目，但内部拆分前端、API、Worker 和共享包；前端只负责展示和输入，Marketplace-owned 业务规则只存在于后端领域/应用层。

```text
                           +----------------------+
                           | marketplace-web      |
                           | Next.js / React      |
                           +----------+-----------+
                                      |
                                      v
                           +----------------------+
                           | marketplace-api     |
                           | Fastify / Node.js   |
                           +-----+----------+-----+
                                 |          |
                     domain/app |          | adapters
                                 v          v
                      +----------+--+   +---+----------------+
                      | shared       |   | marketplace-       |
                      | contracts    |   | adapters           |
                      | domain       |   | L0-sdk / owners    |
                      +------+-------+   +--------------------+
                             |
                             v
                      +------+-------+
                      | PostgreSQL   |
                      | truth +      |
                      | projections  |
                      +------+-------+
                             ^
                             |
                    +--------+---------+
                    | marketplace-    |
                    | worker          |
                    | jobs/outbox/    |
                    | retry/rebuild   |
                    +-----------------+
```

运行单元可以独立部署，但共用同一套 Marketplace domain/application/contracts；它们不形成新的正式项目仓，也不复制领域真相。

## 3. 运行单元与职责

### 3.1 `marketplace-web`

负责：

- 消费者目录、搜索、Listing 详情和版本选择
- Publisher Portal 的发布申请、审核状态和版本管理
- Marketplace Admin 的 listing、可见性、撤回、通知与恢复视图
- loading、empty、stale、blocked、unknown、withdrawn 等状态展示
- 通过 API 发送 command/query

不负责：

- 直接访问数据库或上游仓库
- 自行决定 Governance approval、publisher 验证或公开可见性
- 将获取请求显示为安装激活成功
- 在浏览器内持有资产正文或外部 owner 真相

### 3.2 `marketplace-api`

负责：

- HTTP/API 边界、认证上下文和输入校验
- command/query application service 调用
- 事务、幂等和错误映射
- listing、release、review handoff、distribution、withdrawal 和 catalog read API
- 输出明确的 `pending / blocked / unknown / failed / partial` 结果

不负责：

- 在 route handler 中直接实现领域规则
- 直接调用其他项目数据库
- 用管理员操作或材料状态替代 Governance decision
- 把外部 `commit_unknown` 改写为 succeeded

### 3.3 `marketplace-worker`

负责：

- Governance decision/ref 消费
- owner ref 复核和失效检查
- catalog/search projection 更新和重建
- 撤回影响计算
- notification 发送、重试和结果对账
- distribution unknown 恢复
- outbox/inbox 处理
- Observability/Archive handoff

不负责：

- 修复或反写 owner truth
- 自动生成 approval、identity、payment 或 activation 结果
- 绕过 visibility、撤回或幂等规则

### 3.4 共享包

| 包 | 职责 | 依赖纪律 |
|---|---|---|
| `marketplace-contracts` | request/response、status、error、pagination、provenance 和 degraded view schema | 不含数据库实现或 owner 正文 |
| `marketplace-domain` | Marketplace aggregate、value object、状态转换和不变量 | 纯 TypeScript；不依赖 Web、HTTP、DB、SDK |
| `marketplace-application` | command/query orchestration、UoW、ports、幂等和事务编排 | 依赖 domain 与 ports，不依赖 UI |
| `marketplace-persistence` | PostgreSQL schema、query、migration、事务和 projection repository | 不共享其他项目表，不保存外部正文 |
| `marketplace-search` | catalog/search projection、索引更新和重建 | 索引不是授权或资产真相 |
| `marketplace-adapters` | L0-sdk、owner、Governance、delivery、notification、Observability、Archive 适配 | 外部 unknown 必须保留；fake 只用于测试 |

## 4. 数据与基础设施技术边界

```text
Marketplace-owned PostgreSQL
  listings / releases / review_handoffs
  publisher_relations / distributions
  withdrawals / notification_attempts
  provenance / idempotency / outbox / inbox
  catalog projections / search metadata
```

PostgreSQL 首期同时承担业务事实、局部投影和可靠性记录；不共享其他项目数据库，不把搜索索引当 source truth。

首期搜索建议使用：

```text
PostgreSQL full-text search
+ GIN index
+ pg_trgm fuzzy matching
```

除非正式规模、相关性、多语言分词或性能验证证明不足，否则不提前引入 Elasticsearch/OpenSearch。

后台任务首期建议使用 PostgreSQL-backed queue，使业务事务、outbox 和 job 创建可以形成清晰的本地一致性边界；具体队列库在 `02/03` 校准时再根据仓库标准选择。

Redis、Kafka、新消息总线和独立工作流引擎不是当前前置技术。

## 5. 跨仓适配器方向

```text
Marketplace adapter
       |
       v
     L0-sdk / formal owner boundary
       +-- Identity
       +-- Governance
       +-- Artifact
       +-- Method Library
       +-- Capability Hub
       +-- Member Images
       +-- Delivery receiver
       +-- Notification channel
       +-- Observability
       +-- Archive
       +-- Billing (future/blocker)
```

适配器必须：

- 只调用正式 query/command/event/hand-off 边界
- 区分 rejected、blocked、timeout、partial 和 `commit_unknown`
- 原样保留外部版本、摘要、可见性和 decision/ref provenance
- 不把 fake 结果当真实集成证据
- 不把签名/扫描/ACK 自动转成 approval

签名、扫描、SBOM、OCI registry、cosign、Trivy、Grype、SPDX/CycloneDX 等只可作为后续 adapter 候选；在没有正式 owner 和消费契约前，不锁定为 Marketplace 核心技术栈。

## 6. CLI 与部署形态

Publisher CLI 为可选能力，推荐排在 Web Publisher Portal 和稳定 API 之后：

```text
P0  Web Publisher Portal
P1  versioned API / SDK integration
P2  thin TypeScript/Node.js Publisher CLI
```

CLI 只调用版本化 API，不直接访问数据库或实现领域规则。

首期部署单元建议：

```text
marketplace-web
marketplace-api
marketplace-worker
postgresql
otel-collector（按平台需要）
```

这些是运行部署单元，不代表必须拆成多个设计项目或多个 source-truth 仓。

## 7. 暂不锁定的技术决策

以下内容必须留到正式校准和平台核对：

- Next.js 与组织现有 Web shell 的具体集成方式
- UI 组件库和 CSS 设计系统版本
- Drizzle 或组织既有数据访问标准
- job queue 具体库
- CI/CD、Ingress、容器编排和 secret manager
- 认证 provider 与 token 传递方式
- 专用搜索引擎
- 对象存储、扫描、签名和包仓库
- billing/payment/entitlement provider

## 8. 本篇讨论结论

推荐基线为：

```text
TypeScript
+ Next.js / React
+ Fastify / Node.js LTS
+ PostgreSQL
+ PostgreSQL FTS / pg_trgm
+ PostgreSQL-backed jobs
+ Outbox / Inbox
+ L0-sdk adapters
+ OpenTelemetry
+ Vitest / Testing Library / Playwright
+ Docker/OCI
```

当前技术形态是“一个 Marketplace 项目、前端/API/Worker 分开运行、共享领域和契约包”。技术栈仍是 draft 推荐，不得在正式文档中伪装成已批准的实现选型；具体库、部署平台和外部服务要等正式校准、平台标准与上游合同闭合后再定。

### 2.3 需求文档的三种来源分类

虽然 26 仓都要求撰写 `00-需求文档.md`,但**需求来源并不相同**。写法必须按来源调整,不要机械套模板。

| 类型 | 说明 | 典型仓 | 写法重点 |
|---|---|---|---|
| **产品叙事直推型** | `product/` 层已经有明确产品叙事,仓级需求是在此基础上细化 | L5-chat / L5-console / L5-runner / L5-sync / L6-bridges / L6-marketplace | 强调用户故事、交互、验收标准、非功能指标 |
| **架构反推型** | `product/` 层无直接业务叙事,需求主要来自架构边界和下游 25 仓的共同需要 | L0-core / L0-bus / L4-observability / L4-archive / L4-sandbox | 强调"为什么这个基础设施仓必须存在"、契约职责、下游消费者 |
| **运行时能力型** | 需求来自平台能力与技术流程,既非纯产品也非纯契约 | L2-member / L2-runtime / L2-tools / L3-capability-hub / L3-method-library | 强调操作语义、运行时行为、接口/事件能力边界 |

**写作原则**:
- 产品叙事直推型 → 问题定义主要引用 `product/` 文档,仓级需求做细化
- 架构反推型 → 允许从 `architecture/` 和下游仓需要反推需求,但必须解释"为什么这个仓不得不存在"
- 运行时能力型 → 重点写"这个能力如何被上下游使用",用户故事里的"角色"可能是开发者、运维或 AI Member
- **需求文档讲“问题与目标”,架构设计讲“架构压力与决策”**。若一段内容两边都能写,优先放在 `00-需求文档`; `01-架构设计` 只保留与变化维度、依赖方向、边界、不可逆决策相关的部分


### 2.4 仓类型分类法(决定写法)

虽然所有 26 仓都使用同一套五件套模板,但**不同类型的仓,同一章节的写法和重心不同**。先判断自己属于哪类仓,再落笔。

| 仓类型 | 典型仓 | 需求文档写法重心 | 架构设计写法重心 |
|---|---|---|---|
| **基础设施契约型** | L0-core / L0-bus / L0-sdk / 部分 L4 | 为什么这个基础设施不得不存在;下游共同需要;契约 / 稳定性 / 兼容性 | 依赖方向、契约边界、构建期/运行期容器、演进与版本策略 |
| **业务域型** | L1 六域 | 直接细化 `product/` 叙事;用户故事、功能清单、验收标准最重要 | 边界、上下文、数据所有权、聚合关系、事件编织 |
| **运行时能力型** | L2-member / L2-runtime / L2-tools / 部分 L3 | 能力如何被上下游使用;角色可能是开发者 / 运维 / AI 成员 | 运行时流程、并发、资源管理、恢复路径、容器协作 |
| **端侧产品型** | L5-chat / L5-console / L5-runner / L5-sync / L6-bridges / L6-marketplace / L5-website | 终端用户体验、交互、验收、非功能(尤其 Learnability / Responsiveness) | 上下文图、容器图、外部依赖、网关/UI 边界 |

**使用原则**:
- 先定仓类型,再决定每节重点
- 不同仓可以用同一模板,但不应该写出同一种语气
- 若一仓兼具两种属性(如 method-library 既是能力层又受 Console 管理),在文档头部明确主类型 + 次类型

### 2.5 章节轻重规则

模板**不允许删节**,但不同仓的章节可以按"完整写 / 轻写 / 不适用 + 理由"三档处理。

| 章节 | 完整写 | 轻写 | 不适用 + 理由 |
|---|---|---|---|
| `00-需求文档` §4 用户与角色 | 业务域型 / 端侧产品型 | 基础设施契约型(以维护者 / 下游开发者为主) | 极少见 |
| `00-需求文档` §8 交互与界面需求 | 端侧产品型 | 业务域型(只写关键 UI 约束) | 基础设施契约型 / 纯后端仓常见 |
| `01-架构设计` §5 限界上下文与子域划分 | 业务域型完整按 DDD 语义写 | 基础设施仓按能力上下文写 | 几乎不适用“空缺”,至少要写模块边界 |
| `01-架构设计` §6 容器/部署架构 | 有运行时进程的仓完整写 | L0-core / L0-sdk 这类 CI/发布型仓可写"构建期 / 发布期容器图" | 不适用很少见 |
| `01-架构设计` §14 上线策略 | 业务域 / 端侧产品型写灰度 / 回滚 | L0 仓写发版 / prerelease / registry rollback | 不适用很少见 |

**铁律**:
- 章节不删,只允许标注"本项目不适用 + 理由"
- 对 L0/L4 基础设施仓,允许把 DDD 上下文解释为**能力上下文 / 契约上下文 / 模块边界**
- 对 L0-core / L0-sdk 这类非线上常驻仓,`容器/部署`章节写**构建期 / 发布期 / CI 进程**,不是硬凑线上 Pod

### 4.3 架构设计 10 节评审清单

来自 `架构设计书写规范.md` §五,架构设计交付前必过:

- [ ] **5.1 业务对齐** · 成功标准可量化、无过度设计
- [ ] **5.2 边界划分** · 子域分类合理、统一语言词汇表、数据所有权清晰
- [ ] **5.3 依赖方向** · 稳定性方向一致、无循环依赖
- [ ] **5.4 一致性策略** · 聚合内强一致 / 聚合间最终一致 / Saga / Outbox
- [ ] **5.5 技术选型** · 决策四元组、2-3 备选、不可逆程度评估
- [ ] **5.6 横切能力** · 韧性 + 可观测 + 安全 + 配置 + 性能预算表
- [ ] **5.7 演进能力** · 触发条件可量化
- [ ] **5.8 决策记录** · ADR 索引完整
- [ ] **5.9 反模式自查** · 无简历驱动、无分布式单体、团队对齐
- [ ] **5.10 上线风险** · 灰度 + 回滚 + 异常分常见/边缘

**L0/L4 基础设施仓的解释规则**:
- `§5 限界上下文与子域划分` 可以按**能力上下文 / 模块边界**解释,不强求业务 DDD 语义
- 例如 L0-core 的 `Common Types / Identity Service proto / Work Service proto` 这些上下文,本质是**契约上下文**而非业务限界上下文
- 例如 L4-observability 的 `metrics / traces / audit-log / replay` 这些上下文,本质是**观测能力上下文**
- 评审时重点看:模块边界是否清晰、依赖方向是否合理、数据所有权是否单一,而不是强行追求业务语义命名

### 4.5 详细设计自审(来自 `详细设计书写规范.md`)

**终极检验标准**:一个没参与过的开发者,仅凭概要 + 详细设计,能否直接编写出与设计意图一致的代码?

## 五、写作原则(通则复述)

来自 `设计文档编写通则.md` §三,11 条写作原则:

| 原则 | 说明 |
|---|---|
| **先问题后方案** | 先讲"为什么要做",再讲"怎么做" |
| **非目标必写** | 明确不做什么比目标更重要 |
| **方案要对比** | 至少 2-3 个备选,只给一个等于没设计 |
| **写权衡不写事实** | "选 Kafka 因为吞吐高"是事实;"选 Kafka 而非 RabbitMQ 因为场景吞吐优先于路由灵活"是权衡 |
| **图胜于表,表胜于文** | 能用图不用表,能用表不用段落 |
| **文档要活** | 实现偏差要更新文档,否则文档变"考古材料" |
| **适度即可** | 过度文档化不如不写 |
| **决策有演进** | 每个技术决策不仅写当前选择,还要写备选和演进路径 |
| **约束即防线** | 分层约束、接口契约、前置/后置条件——写在文档里的约束就是防线 |
| **可验证即可信** | 验收准则用可执行命令/指标/断言表达 |
| **详细设计即代码骨架** | 应达到"照着写就能编码"的粒度 |

**10 个致命误区**(避免):

1. 把设计文档写成开发任务说明书
2. 只有方案,没有目标和边界
3. 没有备选方案
4. 只写功能,不写非功能
5. 没有灰度和回滚方案
6. 没有验收指标
7. 上线后不维护
8. 架构图只画分层,不写约束
9. 状态机只画合法转换,不写非法转换处理
10. 非功能指标给数字不给来源

## 六、ASCII 图 9 类速查

来自 `设计文档编写通则.md` §二,每类图"画到什么程度"是规范,非选用问题。

| 图类 | 用途 | 概要/详细 |
|---|---|---|
| 系统上下文图(C4 Context)| 系统和谁交互 | 概要 + 架构 |
| 容器图(C4 Container)| 部署了几个进程 | 概要 + 架构 |
| 组件图(C4 Component)| 模块怎么划分、怎么依赖 | 架构 + 详细 |
| 流程图 | 处理步骤先后、分支逻辑 | 详细(异常路径必画)|
| 时序图 | 多方协作的消息时序 | 详细 |
| 状态机图 + 转换矩阵 | 业务对象的状态变迁 | 详细(含非法转换处理)|
| 数据流图 + 所有权矩阵 | 数据所有权、流转 | 架构 + 详细 |
| 信号传播路径图 | 背压 / 限流的信号 | 详细(反应式系统) |
| 数据结构生命周期图 | 异步资源生命周期 | 详细(必须标注)|

**典型组合**:
- 概要设计:上下文图 + 容器图 + 数据流图
- 详细设计:组件图 + 时序图 + 状态机图 + 流程图
- 分布式事务:时序图 + 状态机图 + 数据流图
- 反应式系统:信号传播路径图 + 数据结构生命周期图

**原则**:**每张图只回答一个问题**。一张图试图回答多个问题,说明图该拆了。

## 八、维护纪律

### 8.1 文档同步

- 实现偏离设计 → **立即更新对应文档**,不允许"代码先于文档"
- 新增决策 → **先写 ADR** 再改文档
- 破坏性变更 → **breaking-change Gate + 公告 + 3 周 deprecation**

### 8.2 提交规范

- 文档变更与代码变更同一 commit(不让文档滞后)
- Commit 信息格式:type 英文,主题正文中文
- Co-Authored-By 固定

### 8.3 评审频率

- **每 N 节点末**:五件套回顾,识别 drift,更新
- **每 Proposed ADR 转 Accepted 时**:受影响文档同步更新
- **每 N 节点前**:本节点仓的 02-概要 / 03-详细 / 04-实施 完成度审查

## 一、项目定位

### 1.1 核心职责

quantalithos-chat 是用户与 AI Agent 团队交互的唯一入口。

```
用户的日常操作：
  1. 和 Assistant 聊天发起新项目
  2. 在项目群聊里看 Agent 讨论、参与对话
  3. 审批门禁卡片（确认 PRD、验收功能）
  4. 查看项目进度、工单看板、产物文档
  5. 管理 Agent 配置和项目设置
```

**不做的事：**
- 不做业务逻辑 — 全部在 sdk-wasm / platform / flow 里
- 不直接调用 platform API — 通过 sdk-wasm 间接调用
- 不做数据持久化 — 数据在 platform，chat 只做渲染和缓存

```

│ 🔍 搜索   │  搜索会话
│──────────│
```

## 六、数据流

### 6.1 消息收发

```
发送消息：
  用户输入 → ChatInput.vue
    → chatStore.sendMessage()
    → sdk.client.sendMessage(roomId, content)
    → sdk-wasm → WebSocket → gate → flow → runtime → Agent

接收消息：
  Agent 回复 → runtime → flow → gate → WebSocket → sdk-wasm
    → sdk events.onMessage()
    → chatStore.addMessage()
    → MessageList.vue 自动更新
```

### 6.2 门禁审批

```
收到审批请求：
  flow 发送 GateCard → gate → WebSocket → sdk-wasm
    → gateStore.addPendingGate()
    → GateCard.vue 渲染在消息流中
    → 会话列表显示 🔔 提醒

用户操作：
  点击"确认通过" → GateCard.vue
    → gateStore.respondGate(gateId, "approve")
    → sdk.client.respondGate(gateId, "approve")
    → sdk-wasm → HTTP → gate → flow
    → flow 推进到下一阶段
    → 消息流中 GateCard 状态更新为"已确认"
```

### 6.3 看板数据

```
加载看板：
  用户点击 📊 → KanbanView.vue
    → kanbanStore.loadKanban(projectId)
    → sdk.client.getProjectWorkitems(projectId)
    → sdk-wasm → HTTP → gate → platform
    → 返回工单列表 → 按 status 分栏渲染
```

### 6.4 进度数据

```
加载进度：
  用户点击 📈 → ProgressView.vue
    → progressStore.loadProgress(projectId)
    → sdk.client.getProjectProgress(projectId)
    → sdk-wasm → HTTP → gate → platform
    → 返回 ProgressView（pipeline 节点状态 + 当前阶段任务列表）
    → PipelineProgress.vue 渲染进度条
    → StageDetail.vue 渲染任务流水线
```

## 七、Phase 分期

### Phase 1

| 功能 | 说明 |
|------|------|
| 三栏布局 | 导航 + 会话列表 + 主内容 |
| Assistant 私聊 | 发起新项目 |
| 项目群聊 | 消息收发、Agent 消息展示 |
| 内嵌卡片 | 工单卡片、进度条、任务状态组 |
| 门禁审批 | GateCard 渲染和操作 |
| 工单看板 | 基础看板（按状态分栏） |
| 项目进度 | Pipeline 进度条 + 阶段任务列表 |

Phase 1 不实现 WebSocket（用轮询），不实现虚拟滚动，不实现拖拽。

### Phase 2

| 功能 | 说明 |
|------|------|

## 十、约束条件

### 10.1 技术约束

| 约束 | 说明 |
|------|------|
| 框架 | Vue 3 + Composition API + TypeScript，不使用 Options API |
| 构建 | Vite，不使用 Webpack |
| 数据获取 | 全部通过 sdk-wasm，不直接调用 platform/gate API |
| 状态管理 | Pinia，不使用 Vuex |
| 样式 | CSS Variables + Scoped CSS，不使用 Tailwind（与 Naive UI 冲突） |
| 无服务端渲染 | 纯 SPA，Nginx 静态托管；Phase 2 Tauri 桌面端 |

### 10.2 容量规划

| 指标 | Phase 1 目标 | Phase 2 目标 |
|------|-------------|-------------|
| 首屏加载（gzip） | < 500KB（不含 WASM） | < 800KB（含 WASM） |
| WASM 初始化 | < 200ms | < 200ms |
| 消息列表渲染（100 条） | < 100ms | < 100ms |
| 看板渲染（50 工单） | < 200ms | < 200ms |
| 内存占用 | < 100MB | < 200MB |

### 10.3 层间约束

| 约束 | 说明 |
|------|------|
| views/ 不直接调用 sdk-wasm | views 通过 stores/ 获取数据，不直接 import sdk |
| stores/ 是唯一的数据源 | 所有组件从 Pinia store 读取数据 |
| components/ 不依赖 stores/ | 通用组件通过 props 接收数据，不直接读取 store |
| sdk/ 是唯一的网络层 | 所有 HTTP/WS 调用封装在 sdk/ 目录 |
| types/ 对齐 sdk-models | TS 类型定义与 Rust sdk-models 保持一致 |

```
依赖方向（单向）：

  views/（页面）
    │
    ├──> stores/（Pinia 状态管理）
    │       │
    │       └──> sdk/（SDK 薄封装）
    │              │
    │              └──> @quantalithos/sdk-wasm（WASM 模块）
    │
    └──> components/（通用组件，通过 props 接收数据）
```

## 十一、技术选型（决策四元组）

### 11.1 前端框架

| 维度 | 当前选择 |
|------|---------|
| 方案 | Vue 3 + Composition API |
| 备选 | ① React 18　② Svelte 5　③ Solid.js |
| 理由 | Vue 3 响应式系统与 Pinia 状态管理天然契合；Naive UI 是 Vue 3 原生组件库，质量高；团队 Vue 经验丰富；React 需要额外选择状态管理方案 |
| 演进路径 | 长期使用 Vue 3；Phase 2 Tauri 桌面端复用同一套 Vue 代码 |

### 11.2 UI 组件库

| 维度 | 当前选择 |
|------|---------|
| 方案 | Naive UI |
| 备选 | ① Element Plus　② Ant Design Vue　③ 自研组件 |
| 理由 | Naive UI 完全 TypeScript 编写，tree-shaking 友好，主题定制灵活（CSS Variables）；Element Plus 体积较大；自研成本高 |
| 演进路径 | 长期使用；Phase 2 如需深度定制，可 fork 部分组件 |

### 11.3 桌面端方案（Phase 2）

| 维度 | 当前选择 |
|------|---------|
| 方案 | Tauri（Rust + WebView） |
| 备选 | ① Electron　② Flutter Desktop |
| 理由 | Tauri 可直接调用 sdk Rust 代码（不经过 WASM），包体积小（~10MB vs Electron ~150MB）；与项目 Rust 技术栈一致 |
| 演进路径 | Phase 2 实现 Tauri 桌面端；Phase 3 评估移动端（Tauri Mobile） |

## 十二、横切关注点

### 12.1 安全

| 关注点 | 方案 |
|--------|------|
| XSS 防护 | Vue 3 默认转义模板输出；不使用 v-html（除 Markdown 渲染，用 DOMPurify 过滤） |
| Token 存储 | sdk-wasm 内存中持有，不写入 localStorage |
| CSRF | SPA 不使用 cookie 认证，JWT 在 Authorization header，无 CSRF 风险 |
| 内容安全策略 | Phase 2 配置 CSP header（Nginx） |

### 12.2 性能

| 关注点 | 方案 |
|--------|------|
| 首屏加载 | WASM 异步加载（不阻塞首屏）；路由懒加载（动态 import） |
| 消息列表 | 虚拟滚动（vue-virtual-scroller），只渲染可见区域 |
| 看板渲染 | 分页加载工单（每页 50 条） |
| 图片/产物 | 懒加载 + 缩略图 |

### 12.3 可用性

| 关注点 | 方案 |
|--------|------|
| 离线状态 | 检测网络断开 → 显示离线提示条；恢复后自动刷新数据 |
| WASM 加载失败 | 显示降级页面（纯 HTML 提示升级浏览器） |
| 错误边界 | Vue errorHandler 全局捕获 → 显示错误提示 toast |

### 12.4 可观测性

| 维度 | 方案 |
|------|------|
| 错误上报 | Phase 2 接入 Sentry（Vue 插件） |
| 性能指标 | Phase 2 上报 FCP / LCP / WASM init 耗时 |
| 用户行为 | Phase 3 评估匿名使用统计 |

### 12.5 成本

| 关注点 | 方案 |
|--------|------|
| 托管 | Nginx 静态文件托管，零运行时成本 |
| CDN | Phase 2 引入 CDN 加速静态资源 |
| 包体积 | Vite tree-shaking + Naive UI 按需导入 |

## 十三、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | WASM 包体积过大 | 首屏加载慢 | 中 | WASM 异步加载不阻塞首屏；Phase 2 wasm-opt 优化；兜底：sdk-api 用 TS 重写 |
| 2 | 浏览器不支持 WASM | 部分用户无法使用 | 低 | 目标浏览器 Chrome 90+/Firefox 90+/Safari 15+，覆盖 >95%；不支持的显示升级提示 |
| 3 | 消息列表性能（>1000 条） | 页面卡顿 | 中 | 虚拟滚动（只渲染可见区域）；历史消息分页加载 |
| 4 | Naive UI 组件不满足需求 | 需要自定义组件 | 中 | Naive UI 支持主题覆盖和 slot 自定义；极端情况 fork 组件 |
| 5 | Phase 2 Tauri 集成复杂 | 桌面端延期 | 中 | Phase 1 Web 端先行；Tauri 集成独立分支开发 |

## 十四、上线策略

### 14.1 灰度方案

| 阶段 | 范围 | 观察时间 | 推进条件 |
|------|------|---------|---------|
| 内部测试 | 开发团队使用 | 3 天 | 核心流程跑通（登录→聊天→门禁→看板） |
| 小范围 | 邀请 5-10 用户 | 1 周 | 无 P0 bug，性能无退化 |
| 全量 | 所有用户 | 持续 | — |

### 14.2 回滚策略

| 触发条件 | 回滚步骤 |
|---------|---------|
| 白屏率 > 1% | Nginx 切回旧版本静态文件 |
| WASM 加载失败率 > 5% | 回退 sdk-wasm 版本（npm 锁定） |

### 14.3 上线监控指标

| 指标 | 告警阈值 |
|------|---------|
| 白屏率 | > 1% |
| WASM init 成功率 | < 99% |
| FCP（首次内容绘制） | > 3s |
| JS 错误率 | > 0.5% |

# quantalithos-core 概要设计

> 核心共享库 — BPMN 引擎、通信协议、共享数据模型（依赖方：flow + runtime + sdk）

---

## 一、项目定位

### 1.1 核心职责

quantalithos-core 是所有子项目的公共基础，包含：

- **schemas/**：语言无关的协议定义（JSON Schema），Rust 和 Python 项目都从这里对齐数据结构
- **python/**：Python 端共享实现（BPMN 引擎 + 通信协议 + 数据模型），flow 和 runtime 共同依赖
- **rust/**：Rust 端共享数据模型（Phase 2，和 sdk-models 对齐）

```
                    quantalithos-core
                    ┌─────────────────────────────────────┐
                    │                                     │
                    │  schemas/          语言无关定义       │
                    │  (JSON Schema)     所有项目对齐       │
                    │                                     │
                    │  python/           Python 实现        │
                    │  ├── bpmn/         BPMN 引擎         │
                    │  ├── protocol/     通信协议           │
                    │  └── models/       数据模型           │
                    │                                     │
                    │  rust/             Rust 实现(Phase 2) │
                    │  └── models/       数据模型           │
                    │                                     │
                    └──────────┬──────────────────────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
         flow (Python)    runtime (Python)   sdk (Rust)
         依赖 python/     依赖 python/       对齐 schemas/
```

### 1.2 设计目标与非目标

| 设计目标 | 说明 |
|---------|------|
| 单一事实来源 | 所有共享类型只在 core 定义一次，flow/runtime/sdk 不重复定义 |
| 语言无关 | schemas/ 用 JSON Schema，Python 和 Rust 各自生成对应类型 |
| 可独立测试 | core 不依赖 flow/runtime/platform，可以独立 pip install 和单元测试 |
| 向后兼容 | ProcessDefinition 带 version 字段，新版本引擎能读旧版本定义 |
| 可扩展 | 新增 BPMN 节点类型 = 加一个类 + 注册一个策略，不改引擎代码 |

| 非目标 | 说明 |
|--------|------|
| 不做通用 BPMN 引擎 | 只实现 Quantalithos 需要的 11 种 BPMN 元素 |
| 不做 HTTP 服务 | core 是纯库（pip install），不监听端口 |
| 不做持久化 | core 不访问数据库，持久化由 platform 负责 |
| 不做 LLM 调用 | LLM 相关逻辑在 runtime，core 只定义协议 |

### 1.3 与 sdk 的区别

```
core = 定义"是什么"（协议、模型、引擎）
sdk  = 实现"怎么用"（API 客户端、WebSocket、状态管理）

core 的消费者：flow、runtime（Python）+ sdk（对齐 schemas）
sdk 的消费者：chat、console、runner、sync（Rust/WASM）
```

## 三、BPMN 引擎设计

### 3.1 节点继承体系

**设计动机：** 旧设计用 3 个子类（EventNode/ActivityNode/GatewayNode）+ 枚举字符串区分具体类型，导致字段膨胀（gate_config 挂在所有 Activity 上）和 visitor 二次 match。

**设计决策：** 每种 BPMN 对象一个类，每个类只携带自己的字段 + 领域行为。

```
FlowNode（抽象基类，纯数据 + 领域行为）
│
├── EventNode
│   ├── StartEvent          trigger: none|message|timer
│   ├── EndEvent            trigger: none|terminate → is_terminate() 领域行为
│   ├── IntermediateEvent   Phase 2
│   └── BoundaryEvent       Phase 2, attached_to + interrupting
│
├── ActivityNode
│   ├── AbstractTask        actor + action + input_refs + allowed_tools + output_schema
│   │                       → get_tool_set() + validate_output() 领域行为
│   ├── UserTask            gate_config → get_approvers() + is_hard_gate() 领域行为
│   ├── ServiceTask         Phase 2
│   ├── CallActivity        Phase 2, call_process_id
│   └── AdHocSubProcess     ordering + completion_condition + participant_ids + coordinator_id + metadata
│                           → get_participants() + is_coordinator() + is_complete() 领域行为
│
└── GatewayNode
    ├── ExclusiveGateway    default_route → evaluate(edges, outputs) 领域行为（对象自治）
    └── ParallelGateway     Phase 2 → get_fork_targets() + is_join_complete() 领域行为
```

**关键设计点：**

- `node_type` 字段作为 discriminator，用于策略查表和 JSON 反序列化
- `NODE_TYPE_MAP` 注册表：node_type → 具体类，`deserialize_node(dict)` 工厂函数
- 领域行为封装在对象上（ExclusiveGateway 自己评估条件），引擎不包含领域逻辑
- 新增节点类型 = 加一个类 + NODE_TYPE_MAP 注册 + 策略注册，不改任何已有代码

> 完整的类定义和字段表见详细设计第二章。

### 3.2 策略注册表

**设计动机：** 同一个 BPMN 对象在 flow 和 runtime 中行为不同（AbstractTask 在 flow 中构造 FlowMessage，在 runtime 中注入 prompt）。

**方案对比：**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|:---:|
| visitor 模式 | 经典，对象有 accept() | 对象知道 visitor 存在，新增节点改所有 visitor | 废弃 |
| 标准策略模式 | 对象持有 executor | executor 不可序列化，YAML 加载时不知道注入哪个 | 废弃 |
| 策略注册表 | 对象完全不知道策略存在，按 node_type 查表 | 调用链多一层间接 | **采纳** |

**工作方式：**

```
BPMNEngine 遍历到一个节点时：

  1. 检查是否是 Gateway → 对象自治（node.evaluate()），不走策略
  2. 否则 → registry.get(node.node_type) → strategy.execute(node, ctx)

flow 启动时注册：
  registry.register("abstract_task", FlowTaskStrategy())      → 构造 FlowMessage
  registry.register("user_task", FlowUserTaskStrategy())       → 创建 GateCard
  registry.register("ad_hoc_sub_process", FlowAdHocStrategy()) → 构造 FlowMessage
  registry.register("end_event", FlowEndEventStrategy())       → 推进阶段

runtime 启动时注册：
  registry.register("abstract_task", AgentTaskStrategy())      → 注入 prompt + think→act
  registry.register("ad_hoc_sub_process", AgentAdHocStrategy())→ 启动协作活动
```

**ExecutionContext：** 策略执行时需要的运行时依赖（agent / tools / runtime_client 等），不存在对象上，作为参数传入。FlowExecutionContext 和 AgentExecutionContext 各自携带不同的依赖。

> 完整的策略接口、注册表、ExecutionContext 定义见详细设计第五章。

### 3.3 Token 模型

**设计动机：** 旧设计用单指针 `current_node` 遍历，ParallelGateway 需要同时跟踪多条执行路径，单指针无法表达。

**设计决策：** Token 模型。每个 Token 是一个独立的执行指针。

```
Token 的生命周期：

  创建：BPMNEngine.run() 在 StartEvent 创建初始 Token
  推进：每轮循环处理所有 active Token
  分裂：ParallelGateway(diverging) → 1 个 Token 变 N 个
  合并：ParallelGateway(converging) → N 个 Token 变 1 个
  消亡：EndEvent → Token completed

  线性流程退化为始终只有 1 个 active Token，无额外开销。
```

**Token 状态机：**

```
  active ──→ completed    （正常完成 / fork 后消亡）
  active ──→ waiting      （到达 join 节点等待其他分支）
  waiting ──→ completed   （所有分支到达，合并后消亡）
  completed → (终态)       （不可再转换，transition_to() Fail Fast）
```

**关键设计点：**

- `transition_to()` 方法强制状态机约束，非法转换立即报错
- `history` 列表记录所有状态变更（可观测性）
- 已 completed 的 Token 跳过处理（幂等性）
- join 时用 `node_id` 匹配（所有到达同一 join 节点的 Token），比 parent_token_id 更可靠

> 完整的 Token 定义和 BPMNEngine 实现见详细设计第二、五章。

### 3.4 ProcessDefinition 校验

**设计动机：** 从 YAML 加载的 ProcessDefinition 可能有结构错误（缺少 StartEvent、edge 指向不存在的节点），不校验会导致引擎运行时崩溃。

**契约设计：** BPMNEngine.run() 的前置条件 — 只接受结构合法的 ProcessDefinition。

**8 条校验规则：**

1. 有且只有一个 StartEvent
2. 至少一个 EndEvent
3. 所有 edge 的 source/target 必须存在
4. StartEvent 不能有入口 edge
5. EndEvent 不能有出口 edge
6. ExclusiveGateway(diverging) 至少有一个出口
7. ParallelGateway(diverging) 至少有 2 个出口
8. 非 EndEvent 节点至少有一个出口

**工厂方法：** `ProcessDefinition.from_dict(data)` 反序列化 + 校验一步完成，校验失败立即 raise。

> 完整的校验实现和 ProcessDefinition/ProcessInstance 定义见详细设计第二章。

### 3.5 ProcessInstance 归属

**设计动机：** flow 需要额外的追踪字段（edge_history / gate_history），但 core 的 BPMNEngine 不应该知道这些。

**设计决策：** core 提供基础版 ProcessInstance（tokens + node_outputs + status），flow 继承扩展为 FlowProcessInstance。runtime 直接用基础版。BPMNEngine 只依赖基础版。

## 四、通信协议

### 4.1 消息类型设计

**设计动机：** 旧设计有 10 种消息类型（task_assign / session_start / session_end 等），每种 BPMN 节点类型对应一种自造的消息类型。session_start 是 BPMN 中不存在的概念，引发歧义。

**设计决策：** 6 种消息类型，节点执行统一为 node_execute。

```
生命周期（runtime 自有）：
  agent_create / agent_destroy / agent_suspend / agent_resume

节点执行（和 BPMN 对齐）：
  node_execute    payload 带序列化的 FlowNode + 完整 ProcessDefinition
  node_cancel     取消正在执行的节点

消息路由：
  chat_message    群聊/私聊/ask_reply 统一（reply_to 字段区分）
```

**关键设计点：**

- FlowMessage 传输层保持 `payload: dict`（JSON 兼容），接收方调用 `parse_payload()` 解析为具体 Payload 类型
- 每种消息类型一个 Payload 类（Pydantic BaseModel），字段缺失/类型错误立即报错（Fail Fast）
- node_execute 传完整 ProcessDefinition（不是 ID），避免 runtime 再次请求 platform，保证版本一致性

> 完整的 Payload 类定义和 FlowMessage/NodeResult 字段表见详细设计第三章。

### 4.2 SandboxProvider 接口

**设计动机：** runtime 的工具（file_write / code_execute / git_commit）需要在 sandbox 容器内执行，但 runtime 不应该直接依赖 Docker API。

**设计决策：** core 定义 SandboxProvider 抽象接口，sandbox 实现该接口。runtime 通过接口调用，不知道底层是 Docker 还是宿主机。

```
SandboxProvider 接口：
  exec(agent_id, command) → ExecResult
  write_file(agent_id, path, content) → Ok
  read_file(agent_id, path) → content
  git_commit(agent_id, message) → Ok
  git_push(agent_id) → Ok
  get_service_url(service_name) → url
```

> 完整的接口定义见详细设计第五章。

## 五、错误处理策略

### 5.1 错误分类

| 类别 | 触发场景 | 恢复策略 |
|------|---------|---------|
| 结构错误 | ProcessDefinition 校验失败（缺 StartEvent、edge 断裂） | Fail Fast，拒绝执行，上报给调用方 |
| 状态错误 | Token 非法状态转换（completed → active） | Fail Fast，raise ValueError |
| 路由错误 | ExclusiveGateway 所有条件不满足且无 default_route | Fail Fast，raise RuntimeError |
| 推进错误 | 非 EndEvent 节点没有出口 edge | Fail Fast，raise RuntimeError |
| 反序列化错误 | node_type 未注册、字段缺失 | Fail Fast，raise ValueError |
| 策略缺失 | registry.get() 找不到对应策略 | Fail Fast，raise ValueError |
| Payload 错误 | FlowMessage.parse_payload() 字段类型不匹配 | Fail Fast，Pydantic ValidationError |

### 5.2 错误传播路径

```
core 内部错误 → 调用方（flow / runtime）→ 上层处理

  ProcessDefinition.validate_structure() 失败
    → BPMNEngine.run() 不执行
    → flow/runtime 收到 ValueError
    → 上报 NodeResult(failed, reason="ProcessDefinition 校验失败: ...")

  Token.transition_to() 非法转换
    → BPMNEngine.advance_token() 中断
    → flow/runtime 收到 ValueError
    → 上报 NodeResult(failed)

  ExclusiveGateway.evaluate() 无匹配
    → BPMNEngine.advance_token() 中断
    → flow/runtime 收到 RuntimeError
    → 上报 NodeResult(failed, reason="Gateway 无匹配条件")

  strategy.execute() 内部异常
    → BPMNEngine 不捕获（由策略实现者处理）
    → flow/runtime 的策略实现自行决定重试或上报
```

### 5.3 设计原则

- **core 只 Fail Fast，不做恢复**：core 是纯库，不知道上层的恢复策略
- **错误信息必须包含上下文**：node_id / token_id / process_id，方便定位
- **不静默忽略**：任何异常状态都立即报错，不允许带病运行

## 六、性能边界与扩展点

### 6.1 性能边界

| 维度 | Phase 1 设计约束 | 瓶颈分析 |
|------|-----------------|---------|
| 节点数量 | 单个 ProcessDefinition 最多 ~100 个节点 | validate_structure() 是 O(n²)（edge 校验），100 节点内可忽略 |
| Token 数量 | 并行分支最多 ~10 个 Token | get_active_tokens() 遍历全部 Token，10 个内无性能问题 |
| 嵌套深度 | 不支持嵌套 ParallelGateway（Phase 2） | Phase 1 只有线性 + exclusive 分支 |
| 序列化 | ProcessDefinition JSON 最大 ~100KB | 放入 FlowMessage payload，HTTP 传输无压力 |
| 引擎循环 | 单次 run() 最多 ~1000 轮（防止死循环） | 超过上限强制终止，上报 failed |

### 6.2 扩展点

| 扩展点 | 机制 | 说明 |
|--------|------|------|
| 新增 BPMN 节点类型 | 加一个 FlowNode 子类 + NODE_TYPE_MAP 注册 | 不改 BPMNEngine |
| 新增执行策略 | 实现 NodeStrategy + registry.register() | 不改已有策略 |
| 新增 ExecutionContext | 继承 ExecutionContext 基类 | 不改 BPMNEngine |
| 新增 Payload 类型 | 加一个 BaseModel + PAYLOAD_TYPE_MAP 注册 | 不改 FlowMessage |
| 条件表达式扩展 | 修改 ExclusiveGateway._match_condition() | Phase 2 引入表达式引擎 |
| 新增 SandboxProvider 实现 | 实现接口（Docker / K8s / 宿主机） | runtime 不感知 |
| ProcessDefinition 校验规则扩展 | 在 validate_structure() 中加规则 | 不影响已有规则 |

### 6.3 不可扩展的部分（有意为之）

| 不可扩展 | 原因 |
|---------|------|
| Token 状态机 | 只有 3 种状态（active/waiting/completed），BPMN 标准定义，不应该扩展 |
| FlowMessage.type | 只有 6 种，新增消息类型需要慎重评估（影响 runtime 的 dispatch） |
| BPMNEngine 主循环 | Token 驱动的 while 循环是核心不变量，不应该被覆盖 |

## 七、Phase 分期

### Phase 1

| 模块 | 范围 |
|------|------|
| bpmn/models | StartEvent + EndEvent + AbstractTask + UserTask + AdHocSubProcess + ExclusiveGateway + FlowEdge |
| bpmn/token | Token 模型 |
| bpmn/engine | Token 驱动引擎（线性 + exclusive 分支，退化为单 Token） |
| bpmn/strategy | NodeStrategy 接口 + StrategyRegistry |
| bpmn/context | ExecutionContext / FlowExecutionContext / AgentExecutionContext |
| protocol | FlowMessage（6 种）+ 类型化 Payload + NodeResult |
| models | RoleDefinition + SharedRule + WorkItem |

### Phase 2

| 模块 | 范围 |
|------|------|
| bpmn/models | IntermediateEvent + BoundaryEvent + ServiceTask + CallActivity + ParallelGateway |
| bpmn/engine | ParallelGateway Token 分裂/合并 + CallActivity 子流程 + BoundaryEvent |
| bpmn/models | ExclusiveGateway 条件表达式扩展（>, <, in） |
| rust/models | 和 schemas/ 对齐的 Rust struct |

### 不实现的 BPMN 元素

> 完整的落地决策表见 `docs/design/流程图模型与节点原语设计.md` 第十章。

| 类别 | 不实现的元素 | 原因 |
|------|------------|------|
| 网关 | Inclusive / Event-based / Complex | 无场景，Exclusive + Parallel 已覆盖 |
| 活动 | Script / Send / Receive / Business Rule / Manual | Agent 本身能执行脚本，消息用 FlowMessage |
| 事件 | Compensation / Escalation / Cancel / Signal | 无事务回滚需求，用 NodeResult(blocked/failed) 替代 |
| 连接 | Message Flow | 单系统内部，不跨组织 |
| 泳道 | Pool | 同上 |
| 数据 | Data Object / Data Store | 用 Artifact + platform 数据库替代 |

### 1.2 设计原则

- **零业务逻辑**：core 不知道 TDD、不知道博客项目、不知道 Agent 池。它只定义数据结构和引擎接口
- **语言无关**：schemas/ 是 Python 和 Rust 的共同基准，Python Pydantic 模型是权威实现
- **向后兼容**：ProcessDefinition 带 version 字段，消费者可按版本加载
- **策略注册表**：BPMNEngine 不包含任何节点处理逻辑，按 node_type 查表调用策略

## 二、数据结构 — bpmn 模块

### 2.1 FlowNode 基类

```python
# bpmn/models.py
#
# 本模块定义 BPMN 2.0 节点的继承体系。
# 设计目标：用 Python 类型系统表达 BPMN 标准中的节点分类（Event / Activity / Gateway），
# 同时保持"纯数据 + 领域行为"的风格 — 节点对象知道自己的语义，但不知道谁在驱动它。
#
# 为什么用继承而非组合：
#   BPMN 节点天然是 IS-A 关系（StartEvent IS-A FlowNode），
#   且每种节点有独特的字段和行为，继承比 type 字段 + if-else 更类型安全。
#
# 为什么不用 Pydantic discriminated union：
#   discriminated union 要求所有子类在同一个文件中声明 Union[...]，
#   不利于 Phase 2 扩展新节点类型。注册表模式（NODE_TYPE_MAP）更灵活。

class FlowNode(BaseModel):
    """BPMN 节点抽象基类 — 纯数据 + 领域行为，不知道策略的存在
    
    设计职责：
      - 承载节点的静态定义数据（从 YAML/JSON 反序列化而来）
      - 提供领域行为方法（如 ExclusiveGateway.evaluate）
      - 不包含执行逻辑（执行由 NodeStrategy 负责）
      - 不持有运行时状态（运行时状态在 ProcessInstance 中）
    
    协作关系：
      - BPMNEngine 读取 node_type 查找对应的 NodeStrategy
      - ProcessDefinition 持有 FlowNode 列表
      - deserialize_node() 根据 node_type 实例化具体子类
    """
    id: str                           # 节点唯一标识，在同一个 ProcessDefinition 内唯一
    name: str = ""                    # 人类可读名称，用于日志、通知和前端展示
    status: str = "pending"           # 节点在流程实例中的状态（由 ProcessInstance.node_states 管理，此处为默认值）
    node_type: str                    # 类型标识符（discriminator），三个用途：
                                      #   1. StrategyRegistry 按此字段查找执行策略
                                      #   2. deserialize_node() 按此字段选择具体子类
                                      #   3. JSON Schema 中作为 discriminator 属性

    class Config:
        extra = "allow"               # 允许子类扩展字段 — 这样 Phase 2 新增的节点属性
                                      # 不会导致已有的反序列化代码报错（向后兼容）
```

### 2.2 事件节点

```python
class StartEvent(FlowNode):
    """开始事件 — 流程的唯一入口点
    
    设计约束：
      - 一个 ProcessDefinition 有且只有一个 StartEvent（validate_structure 校验）
      - 不能有入口 edge（没有节点可以"跳转到"开始事件）
      - BPMNEngine 启动时创建初始 Token 放在 StartEvent 上
    
    trigger 字段（Phase 2 扩展）：
      - none：手动启动（Phase 1 唯一支持的方式）
      - message：收到特定消息时自动启动
      - timer：定时启动（如每日构建）
      - signal：收到全局信号时启动
    """
    node_type: str = "start_event"
    trigger: str = "none"             # 触发方式 — Phase 1 只支持 none（由 flow daemon 手动启动）

class EndEvent(FlowNode):
    """结束事件 — 流程的出口点，Token 到达此处即消亡
    
    设计约束：
      - 一个 ProcessDefinition 至少有一个 EndEvent
      - 不能有出口 edge（流程到此结束）
      - 可以有多个 EndEvent（如正常结束 + 异常终止）
    
    trigger 字段：
      - none：正常结束 — 只消亡当前 Token，其他并行分支继续
      - terminate：强制终止 — 消亡所有 active Token，整个流程立即结束
        使用场景：用户"驳回"时走 terminate EndEvent，终止整个项目流程
    """
    node_type: str = "end_event"
    trigger: str = "none"             # none = 正常结束 | terminate = 强制终止所有分支

    # 领域行为
    def is_terminate(self) -> bool:
        """是否终止所有分支（terminate 类型终止整个流程）
        
        BPMNEngine.advance_token() 中调用：
          如果 is_terminate() == True，引擎会遍历所有 active Token 并 completed
        """
        return self.trigger == "terminate"

class IntermediateEvent(FlowNode):    # Phase 2
    """中间事件 — 流程执行过程中的等待点或触发点
    
    BPMN 标准中的中间事件分为两类：
      - catch（捕获）：流程暂停，等待外部事件到达后继续
        场景：等待用户回复、等待定时器到期、等待外部系统回调
      - throw（抛出）：流程主动发出信号，然后继续执行
        场景：通知其他流程、发送消息、触发全局事件
    
    Phase 2 实现，Phase 1 不使用。
    """
    node_type: str = "intermediate_event"
    direction: str = "catch"          # catch = 等待外部事件 | throw = 主动发出事件
    trigger: str = "timer"            # 事件类型：message（消息）| timer（定时）| signal（信号）

class BoundaryEvent(FlowNode):        # Phase 2
    """边界事件 — 附着在活动节点上的超时/异常处理器
    
    设计意图：
      为长时间运行的活动节点提供超时保护和异常处理。
      当 BoundaryEvent 触发时，根据 interrupting 决定是否中断宿主活动。
    
    使用场景：
      - timer + interrupting=True：Agent 执行超时 → 中断任务，走超时分支
      - timer + interrupting=False：执行超过阈值 → 发通知但不中断
      - error + interrupting=True：Agent 报错 → 中断任务，走错误处理分支
    
    Phase 2 实现，Phase 1 不使用。
    """
    node_type: str = "boundary_event"
    attached_to: str                  # 宿主活动节点的 ID — 此事件"附着"在哪个节点上
    trigger: str = "timer"            # 触发类型：timer（超时触发）| error（错误触发）
    interrupting: bool = True         # True = 触发时中断宿主活动（Token 从宿主移走）
                                      # False = 触发时不中断（创建新 Token 走边界分支，宿主继续）
    timeout: Optional[int] = None     # 超时秒数（仅 trigger="timer" 时有效）
```

### 2.3 活动节点

```python
class AbstractTask(FlowNode):
    """抽象任务 — Agent 执行的基础任务节点
    
    设计职责：
      这是系统中最常用的节点类型。代表一个需要 AI Agent 执行的工作单元。
      flow 侧：FlowTaskStrategy 将其转为 FlowMessage 发给 runtime
      runtime 侧：AgentTaskStrategy 注入 prompt，驱动 Agent think→act 循环
    
    为什么叫 AbstractTask 而非 Task：
      BPMN 2.0 标准中 Task 有多个子类型（UserTask/ServiceTask/ScriptTask 等），
      AbstractTask 表示"由 Agent 自主决定如何完成"的通用任务，
      区别于 UserTask（需要人类操作）和 ServiceTask（系统自动调用）。
    
    协作关系：
      - flow 构造此节点 → 序列化为 dict → 放入 FlowMessage.payload.node
      - runtime 收到后 deserialize_node() → 还原为 AbstractTask 实例
      - AgentTaskStrategy 读取 action/allowed_tools/output_schema 驱动执行
    """
    node_type: str = "abstract_task"
    actor: Optional[str] = None       # 执行者的角色 ID（如 "backend_dev"）
                                      # flow 通过 ctx.resolve_actor() 将角色 ID 映射为具体 agent_id
    action: Optional[str] = None      # 自然语言描述的任务内容 — 注入 Agent prompt 的第四层（任务上下文）
                                      # 示例："实现 TASK-003：文章标签系统"
    input_refs: List[str] = []        # 输入引用列表 — Agent 执行前需要读取的上下文
                                      # 可以是工单 ID（"TASK-003"）或产物 ID（"artifact-001"）
                                      # runtime 会调用 platform API 解析为实际内容注入 prompt
    allowed_tools: List[str] = []     # 节点级工具白名单 — 三层权限的第三层
                                      # 空列表 = 不限制（使用角色级工具集）
                                      # 非空 = 只允许列表中的工具（与角色级取交集）
    output_schema: Optional[dict] = None  # 输出结构定义（JSON Schema 格式）
                                          # Agent 调用 submit_step_result 时校验输出是否符合此 schema
                                          # None = 不校验（自由输出）

    # 领域行为
    def get_tool_set(self) -> List[str]:
        """返回节点级允许的工具集
        
        ToolExecutor 在三层权限校验的第三层使用此方法。
        空列表表示"不限制"，由上层（角色级）决定。
        """
        return self.allowed_tools

    def validate_output(self, output: dict) -> bool:
        """校验 Agent 提交的输出是否符合 schema
        
        调用时机：Agent 调用 submit_step_result 工具时，
        runtime 用此方法校验输出格式是否正确。
        
        Phase 1 实现：简单的必填字段存在性检查（不校验类型）
        Phase 2 扩展：引入 jsonschema 库做完整校验
        """
        if self.output_schema is None:
            return True
        # Phase 1：简单字段存在性检查
        required = self.output_schema.get("required", [])
        return all(k in output for k in required)

class UserTask(FlowNode):
    """用户任务 — 门禁审批节点，流程暂停等待人类操作
    
    设计职责：
      代表需要人类用户介入的决策点。flow 侧创建 GateCard 推送给用户，
      流程暂停直到用户做出操作（approve/reject/request_changes）。
    
    与 AbstractTask 的区别：
      - AbstractTask：AI Agent 自主执行，无需人类介入
      - UserTask：必须等待人类操作，AI 不能代替决策
    
    使用场景：
      - 需求确认（用户确认 PRD）
      - 验收确认（用户验收最终产物）
      - 阶段推进审批（从开发进入测试）
    
    gate_config 结构：
      {
        "gate_type": "hard" | "soft",     # hard = 必须人工确认 | soft = 可自动通过
        "approvers": ["user"],            # 审批人列表
        "timeout": 4320,                  # 超时分钟数（超时后 gate 状态变为 expired）
        "auto_approve_condition": null    # Phase 2：自动通过条件表达式
      }
    """
    node_type: str = "user_task"
    actor: Optional[str] = None       # 审批人角色（通常是 "user"）
    action: Optional[str] = None      # 审批说明（展示在 GateCard 上）
    gate_config: dict = {}            # 门禁配置 — 决定审批行为和超时策略

    # 领域行为
    def get_approvers(self) -> List[str]:
        """获取审批人列表 — GateController 用于确定推送目标"""
        return self.gate_config.get("approvers", [])

    def get_timeout(self) -> Optional[int]:
        """获取超时时间（分钟）— GateController 用于设置超时定时器"""
        return self.gate_config.get("timeout")

    def is_hard_gate(self) -> bool:
        """是否为硬门禁 — 硬门禁必须人工确认，软门禁可配置自动通过"""
        return self.gate_config.get("gate_type") == "hard"

class ServiceTask(FlowNode):          # Phase 2
    """服务任务 — 系统自动执行的外部服务调用
    
    设计意图：
      代表不需要 AI Agent 参与的自动化操作，如：
      - 调用 CI/CD 触发构建
      - 调用通知服务发送邮件
      - 调用外部 API 获取数据
    
    与 AbstractTask 的区别：
      - AbstractTask：需要 AI 思考和决策
      - ServiceTask：确定性的 API 调用，无需 AI 参与
    
    Phase 2 实现，Phase 1 不使用。
    """
    node_type: str = "service_task"
    service_ref: str = ""             # 外部服务标识（如 "ci_trigger" / "email_sender"）
    service_config: dict = {}         # 服务调用配置（URL、参数模板等）

class CallActivity(FlowNode):         # Phase 2
    """调用活动 — 启动子流程，等待子流程完成后继续
    
    设计意图：
      实现流程的层次化组合。Pipeline 的每个阶段就是一个 CallActivity，
      引用一个阶段级 ProcessDefinition 作为子流程。
    
    三层流程层次：
      项目流程（Pipeline）→ CallActivity 引用 → 阶段流程（Workflow）
      阶段流程 → CallActivity 引用 → Agent 流程（Procedure）
    
    执行语义：
      flow 侧：FlowEngine.start_sub_process() 加载子流程定义并实例化
      Token 在 CallActivity 上等待，直到子流程的 EndEvent 触发
      子流程完成后，父流程的 Token 继续推进
    """
    node_type: str = "call_activity"
    actor: Optional[str] = None       # 子流程的主执行者（可选，子流程内部可能有多个角色）
    call_process_id: str = ""         # 子流程的 ProcessDefinition ID
                                      # flow 通过 platform_client.get_process(call_process_id) 加载

    # 领域行为
    def get_sub_process_id(self) -> str:
        """获取子流程 ID — FlowEngine.start_sub_process() 用于加载子流程定义"""
        return self.call_process_id

class AdHocSubProcess(FlowNode):
    """Ad-Hoc 子流程 — 通用的无序多人协作活动
    
    设计意图：
      BPMN 标准中的 Ad-Hoc Sub-Process 表示"内部活动没有固定顺序"的容器。
      在 Quantalithos 中用于多 Agent 协作场景：
      - 头脑风暴（多人讨论，协调者总结）
      - PRD 评审（多人评审，协调者提交结论）
      - 技术方案讨论（多人发言，TL 拍板）
    
    为什么不用多个 AbstractTask 串联：
      协作活动的特点是"无序"— 参与者可以任意顺序发言，
      不是 A 做完 B 再做的线性流程。AdHocSubProcess 表达了这种语义。
    
    完成条件（completion_condition）：
      - "coordinator_submit"：协调者调用 submit 工具 → 活动结束
      - "all_done"：所有内部活动都完成 → 活动结束
    
    协作关系：
      flow 侧：FlowAdHocStrategy 发 FlowMessage 给协调者
      runtime 侧：AgentAdHocStrategy 将所有参与者推入 EXECUTING 状态
      参与者通过 send_chat_message 在群聊中讨论
      协调者调用 submit_step_result 提交结论 → 活动结束
    """
    node_type: str = "ad_hoc_sub_process"

    # BPMN 标准字段
    ordering: str = "parallel"                    # parallel = 参与者可并行活动 | sequential = 依次执行
    completion_condition: str = "coordinator_submit"  # 完成条件判断方式
    cancel_remaining: bool = True                 # 完成时是否取消未完成的内部活动
                                                  # True = 协调者提交后，其他人的活动自动结束

    # 通用扩展字段
    participant_ids: List[str] = []               # 参与者 agent_id 列表（所有需要参与讨论的 Agent）
    coordinator_id: Optional[str] = None          # 协调者 agent_id — 有权提交最终结论的人
    inner_activities: List[dict] = []             # 内部可执行活动定义（Phase 2 扩展用）

    # 场景配置（不污染类定义，用 metadata 承载场景特有数据）
    metadata: dict = {}                           # 场景相关的额外数据
                                                  # 讨论场景：{"agenda": "...", "topic": "..."}
                                                  # 评审场景：{"checklist": [...], "artifacts": [...]}

    # 领域行为
    def get_participants(self) -> List[str]:
        """获取所有参与者 — runtime 用于将参与者推入协作状态"""
        return self.participant_ids

    def is_coordinator(self, agent_id: str) -> bool:
        """判断是否为协调者 — 只有协调者可以提交最终结论"""
        return agent_id == self.coordinator_id

    def is_complete(self, context: dict) -> bool:
        """评估完成条件 — BPMNEngine 在每轮循环中调用
        
        为什么用 match 而非 if-else：
          Python 3.10+ 的 match 语义更清晰，且便于 Phase 2 扩展新的完成条件。
        """
        match self.completion_condition:
            case "coordinator_submit":
                return context.get("coordinator_submitted", False)
            case "all_done":
                completed = context.get("completed_activities", [])
                return len(completed) >= len(self.inner_activities)
            case _:
                return False

    def get_metadata(self, key: str, default=None):
        """获取场景配置 — 避免直接访问 metadata dict，提供统一入口"""
        return self.metadata.get(key, default)
```

### 2.4 网关节点

```python
class ExclusiveGateway(FlowNode):
    """排他网关 — 条件分支，从多条出口中选择唯一一条
    
    BPMN 语义：
      排他网关（XOR Gateway）按条件评估选择一条且仅一条出口路径。
      如果多个条件同时满足，选择第一个匹配的（按 edges 列表顺序）。
      如果所有条件都不满足，走 default_route。
      如果连 default_route 都没有 → Fail Fast 抛异常。
    
    direction 字段：
      - diverging（发散）：一个入口，多个出口 — 做条件判断
      - converging（汇聚）：多个入口，一个出口 — 合并分支（不等待，先到先过）
    
    为什么条件评估放在对象内部（对象自治）而非 BPMNEngine：
      1. Gateway 的条件评估是 BPMN 标准语义，在 flow 和 runtime 中完全一样
      2. 不需要按环境区分行为（不像 AbstractTask 在 flow/runtime 中行为不同）
      3. 评估逻辑和 Gateway 的字段（default_route、outgoing_edges）紧密耦合
      4. 放在对象内部更符合"告诉，不要问"原则
    """
    node_type: str = "exclusive_gateway"
    direction: str = "diverging"      # diverging = 条件分支 | converging = 合并（先到先过）
    default_route: Optional[str] = None  # 默认出口节点 ID — 所有条件都不满足时的兜底路径

    # 领域行为：对象自治，不依赖外部
    def evaluate(self, outgoing_edges: List["FlowEdge"], node_outputs: dict) -> str:
        """评估条件，返回应该走的目标 node_id
        
        算法：
          1. 遍历所有 conditional 类型的出口边
          2. 对每条边的 condition 表达式求值
          3. 第一个匹配的 → 返回其 target
          4. 都不匹配 → 走 default_route
          5. 连 default_route 都没有 → Fail Fast 抛异常
        
        为什么 Fail Fast 而非返回 None：
          条件都不满足说明流程定义有缺陷（遗漏了某种情况），
          这是设计错误而非运行时异常，应该立即暴露而非静默跳过。
        
        node_outputs 参数：
          ProcessInstance.node_outputs 的合并结果 — 所有已完成节点的输出。
          条件表达式中的 field 从这里取值。
        """
        for edge in outgoing_edges:
            if edge.flow_type == "conditional" and edge.condition:
                if self._match_condition(edge.condition, node_outputs):
                    return edge.target

        if self.default_route:
            return self.default_route

        raise RuntimeError(
            f"ExclusiveGateway '{self.id}' 所有条件都不满足且没有 default_route"
        )

    def _match_condition(self, condition: str, outputs: dict) -> bool:
        """条件表达式求值
        
        Phase 1 实现：简单字段匹配
          支持：field == value / field != value
          值比较：统一转为字符串比较（str(outputs.get(field)) == value）
          引号处理：自动去除 value 两端的单引号或双引号
        
        Phase 2 扩展：引入 simpleeval 库支持 >, <, in, contains 等操作符
        
        为什么不用 Python eval：
          eval 有代码注入风险 — condition 来自 YAML 定义文件，
          虽然不是用户输入，但防御性编程要求不使用 eval。
        """
        if "==" in condition:
            field, value = [s.strip().strip("'\"") for s in condition.split("==")]
            return str(outputs.get(field)) == value
        if "!=" in condition:
            field, value = [s.strip().strip("'\"") for s in condition.split("!=")]
            return str(outputs.get(field)) != value
        return False

class ParallelGateway(FlowNode):      # Phase 2
    """并行网关 — Token 分裂与合并，实现并行执行
    
    BPMN 语义：
      并行网关（AND Gateway）在发散时将一个 Token 分裂为多个，
      在汇聚时等待所有分支的 Token 都到达后合并为一个继续。
    
    direction 字段：
      - diverging（fork）：一个 Token 进入 → 分裂为 N 个子 Token（N = 出口边数量）
        每个子 Token 独立推进各自的分支
      - converging（join）：等待所有入口边的 Token 都到达 → 合并为一个新 Token 继续
        未到齐时，先到的 Token 状态变为 waiting
    
    与 ExclusiveGateway 的区别：
      - Exclusive：选一条路走（OR）
      - Parallel：所有路都走（AND）
    
    Token 生命周期（fork）：
      父 Token → completed（消亡）
      → 创建 N 个子 Token（parent_token_id = 父 Token ID）
    
    Token 生命周期（join）：
      子 Token 到达 → waiting
      所有子 Token 都 waiting → 全部 completed → 创建一个新的合并 Token
    
    Phase 1 实现基础版（固定分支数量），Phase 2 支持动态分支。
    """
    node_type: str = "parallel_gateway"
    direction: str = "diverging"      # diverging = fork（分裂）| converging = join（合并）

    # 领域行为
    def get_fork_targets(self, outgoing_edges: List["FlowEdge"]) -> List[str]:
        """fork 时返回所有出口目标节点 ID
        
        BPMNEngine.advance_token() 中调用：
          为每个 target 创建一个子 Token，父 Token 消亡。
        """
        return [e.target for e in outgoing_edges]

    def is_join_complete(self, waiting_count: int, expected_count: int) -> bool:
        """join 时判断是否所有分支都已到达
        
        BPMNEngine.advance_token() 中调用：
          waiting_count = 当前在此节点上 status=waiting 的 Token 数量
          expected_count = 此节点的入口边数量（= fork 时分裂出的分支数）
          
        当 waiting_count >= expected_count 时，所有分支都到齐，可以合并。
        """
        return waiting_count >= expected_count
```

```python
class FlowEdge(BaseModel):
    """BPMN 连接（Sequence Flow）— 节点间的有向边
    
    设计职责：
      定义节点之间的连接关系和流转条件。
      BPMNEngine 通过 ProcessDefinition.get_outgoing_edges() 获取某节点的所有出口边，
      然后根据 flow_type 决定如何选择下一个节点。
    
    flow_type 三种值的使用场景：
      - sequence：无条件顺序流 — 直接走（线性流程中最常见）
      - conditional：条件流 — 只在条件满足时走（ExclusiveGateway 的出口边）
      - default：默认流 — 所有 conditional 都不满足时的兜底（ExclusiveGateway.default_route 的边）
    
    condition 字段：
      仅 flow_type="conditional" 时有效。
      Phase 1 格式："field == value" 或 "field != value"
      Phase 2 扩展：支持 >, <, in, contains 等操作符
      求值上下文：ProcessInstance.node_outputs 中已完成节点的输出合并
    """
    id: str                           # 边的唯一标识（在同一个 ProcessDefinition 内唯一）
    source: str                       # 源节点 ID — 边从哪个节点出发
    target: str                       # 目标节点 ID — 边指向哪个节点
    flow_type: str = "sequence"       # 边的类型：sequence（无条件）| conditional（有条件）| default（兜底）
    condition: Optional[str] = None   # 条件表达式 — 仅 conditional 时有效
                                      # ExclusiveGateway.evaluate() 会逐条评估这些条件
    label: Optional[str] = None       # 显示标签 — 用于前端 BPMN 图上的边标注
                                      # 如 "approved"、"needs_revision"、"pass"
```

```python
# bpmn/models.py
#
# 反序列化注册表 — 将 dict 数据还原为具体的 FlowNode 子类实例。
# 
# 为什么用注册表模式（NODE_TYPE_MAP）而非 Pydantic discriminated union：
#   1. discriminated union 要求在一个地方声明所有子类的 Union 类型，
#      Phase 2 新增节点类型时需要修改 Union 定义（不符合开闭原则）
#   2. 注册表模式只需在 NODE_TYPE_MAP 中添加一行映射
#   3. 与 StrategyRegistry 的设计风格一致（都是按 node_type 查表）
#
# 数据流：
#   YAML/JSON → dict → deserialize_node(dict) → 具体 FlowNode 子类实例
#   ProcessDefinition.from_dict() 内部对每个 node dict 调用此函数

NODE_TYPE_MAP = {
    "start_event": StartEvent,
    "end_event": EndEvent,
    "intermediate_event": IntermediateEvent,
    "boundary_event": BoundaryEvent,
    "abstract_task": AbstractTask,
    "user_task": UserTask,
    "service_task": ServiceTask,
    "call_activity": CallActivity,
    "ad_hoc_sub_process": AdHocSubProcess,
    "exclusive_gateway": ExclusiveGateway,
    "parallel_gateway": ParallelGateway,
}

def deserialize_node(data: dict) -> FlowNode:
    """根据 node_type 字段反序列化为具体类型
    
    Fail Fast 设计：
      未知的 node_type 立即抛异常，而非返回基类 FlowNode。
      原因：如果返回基类，后续策略查找会静默失败或行为异常，
      不如在入口处就暴露问题（可能是 YAML 拼写错误或版本不兼容）。
    
    调用者：
      - ProcessDefinition.from_dict()：加载流程定义时
      - MainLoop.handle_node_execute()：runtime 收到 FlowMessage 时还原节点
    """
    node_type = data.get("node_type")
    cls = NODE_TYPE_MAP.get(node_type)
    if cls is None:
        raise ValueError(f"Unknown node_type: {node_type}")
    return cls(**data)
```

### 2.7 Token 模型

```python
# bpmn/token.py

class Token(BaseModel):
    """BPMN Token — 流程中的执行指针
    
    Token 是 BPMNEngine 的核心概念，代表一个独立的执行路径。
    线性流程只有 1 个 Token，ParallelGateway 会分裂出多个。
    Token 到达 EndEvent 时消亡（status=completed）。
    
    为什么需要 Token 而不是单指针：
      单指针（current_node_id）无法表达并行执行。
      ParallelGateway fork 时需要同时跟踪多条路径，
      每条路径是一个独立的 Token。
    """
    token_id: str                      # 唯一标识，用于日志追踪和崩溃恢复时匹配
    node_id: str                       # 当前所在节点 ID，引擎每轮循环读取此字段决定处理哪个节点
    parent_token_id: Optional[str] = None  # fork 时记录父 Token ID，join 时用于匹配同一组分支
    status: str = "active"             # active（可执行）| waiting（等待 join）| completed（已消亡）
    history: List[dict] = []           # 状态变更历史，用于调试和审计（谁在什么时候从哪个节点改了状态）

    # 状态机约束 — 为什么只有 3 种状态：
    # BPMN 标准中 Token 只有这三种生命周期状态。
    # active = 正在被引擎处理
    # waiting = 到达 join 节点，等待其他分支的 Token 也到达
    # completed = 生命周期结束（到达 EndEvent / fork 后消亡 / join 合并后消亡）
    VALID_TRANSITIONS = {
        "active": {"completed", "waiting"},
        "waiting": {"completed"},
        # completed 是终态，不可再转换
    }

    def transition_to(self, new_status: str):
        """状态转换 — Fail Fast，非法转换立即报错
        
        为什么用方法而不是直接赋值 self.status = new_status：
          1. 强制状态机约束（completed → active 是非法的）
          2. 自动记录 history（可观测性）
          3. 集中一个入口，方便加日志和事件回调
        """
        allowed = self.VALID_TRANSITIONS.get(self.status, set())
        if new_status not in allowed:
            raise ValueError(
                f"Token '{self.token_id}' 非法状态转换: {self.status} → {new_status}，"
                f"允许: {self.status} → {allowed or '(终态)'}"
            )
        self.history.append({
            "from": self.status,
            "to": new_status,
            "node_id": self.node_id,
            "timestamp": datetime.now().isoformat(),
        })
        self.status = new_status
```

### 2.8 ProcessDefinition

```python
# bpmn/process.py
#
# 流程定义与流程实例 — BPMN 的静态定义和运行时状态分离。
# ProcessDefinition = 静态蓝图（从 YAML/JSON 加载，不可变）
# ProcessInstance = 运行时状态（Token 位置、节点输出、执行状态）

class ProcessDefinition(BaseModel):
    """BPMN 流程定义 — 从 YAML/JSON 加载的静态蓝图
    
    设计职责：
      承载一个完整流程的节点和边定义。是纯数据对象，不持有运行时状态。
      同一个 ProcessDefinition 可以被多次实例化为不同的 ProcessInstance。
    
    三层流程层次中的角色：
      - 项目流程（Pipeline）：process_id="standard_pipeline"
      - 阶段流程（Workflow）：process_id="requirement_analysis"
      - Agent 流程（Procedure）：process_id="tdd_workflow"
      三层格式完全一致，区别只在于谁驱动执行。
    
    version 字段的用途：
      向后兼容 — 消费者可以按版本加载不同的流程定义。
      Phase 2 支持版本迁移（旧版本实例在新版本定义上继续执行）。
    
    不可变性：
      加载后不应修改。如需修改流程定义，应创建新版本。
      运行时状态变更记录在 ProcessInstance 中。
    """
    process_id: str                   # 流程定义的唯一标识（如 "tdd_workflow"）
    name: str = ""                    # 人类可读名称（如 "TDD 工作流"）
    description: str = ""             # 流程描述（用于文档和前端展示）
    version: str = "1.0"              # 版本号 — 支持同一流程的多版本共存
    nodes: List[FlowNode]             # 节点列表 — 流程中所有的 BPMN 节点
    edges: List[FlowEdge]             # 边列表 — 节点之间的连接关系

    @classmethod
    def from_dict(cls, data: dict) -> "ProcessDefinition":
        """工厂方法：从 dict（YAML/JSON 解析后）构造并校验
        
        为什么用工厂方法而非 __init__：
          1. 需要对 nodes 做多态反序列化（deserialize_node）
          2. 需要在构造后立即校验结构完整性
          3. 校验失败时提供清晰的错误信息（包含 process_id）
        
        数据流：
          YAML 文件 → yaml.safe_load() → dict → from_dict() → ProcessDefinition
          platform API → JSON → dict → from_dict() → ProcessDefinition
        """
        nodes = [deserialize_node(n) for n in data.get("nodes", [])]
        edges = [FlowEdge(**e) for e in data.get("edges", [])]
        instance = cls(
            process_id=data["process_id"],
            name=data.get("name", ""),
            description=data.get("description", ""),
            version=data.get("version", "1.0"),
            nodes=nodes,
            edges=edges,
        )
        errors = instance.validate_structure()
        if errors:
            raise ValueError(f"ProcessDefinition '{data['process_id']}' 校验失败: {errors}")
        return instance

    def validate_structure(self) -> List[str]:
        """校验流程定义的结构完整性 — 契约设计前置条件
        
        设计理由：
          这 8 条规则确保流程定义在结构上是合法的 BPMN 图。
          在加载时就校验（而非执行时），遵循 Fail Fast 原则。
          校验失败意味着流程定义有设计缺陷，应该修复 YAML 而非运行时容错。
        
        8 条校验规则：
          1. 有且只有一个 StartEvent — BPMN 标准要求
          2. 至少一个 EndEvent — 流程必须有出口
          3. 所有 edge 的 source/target 必须存在 — 防止悬空引用
          4. StartEvent 不能有入口 edge — 语义约束
          5. EndEvent 不能有出口 edge — 语义约束
          6. ExclusiveGateway(diverging) 至少有一个出口 — 否则流程卡死
          7. ParallelGateway(diverging) 至少有 2 个出口 — 否则不需要并行
          8. 非 EndEvent 节点至少有一个出口 — 防止流程卡死
        """
        errors = []
        node_ids = {n.id for n in self.nodes}

        # 1. 有且只有一个 StartEvent
        starts = [n for n in self.nodes if isinstance(n, StartEvent)]
        if len(starts) != 1:
            errors.append(f"必须有且只有一个 StartEvent，发现 {len(starts)} 个")

        # 2. 至少一个 EndEvent
        ends = [n for n in self.nodes if isinstance(n, EndEvent)]
        if len(ends) == 0:
            errors.append("必须至少有一个 EndEvent")

        # 3. 所有 edge 的 source/target 必须存在
        for edge in self.edges:
            if edge.source not in node_ids:
                errors.append(f"Edge '{edge.id}' source '{edge.source}' 不存在")
            if edge.target not in node_ids:
                errors.append(f"Edge '{edge.id}' target '{edge.target}' 不存在")

        # 4. StartEvent 不能有入口 edge
        if starts:
            for edge in self.edges:
                if edge.target == starts[0].id:
                    errors.append("StartEvent 不能有入口 edge")

        # 5. EndEvent 不能有出口 edge
        end_ids = {n.id for n in ends}
        for edge in self.edges:
            if edge.source in end_ids:
                errors.append(f"EndEvent '{edge.source}' 不能有出口 edge")

        # 6. ExclusiveGateway(diverging) 至少有一个出口
        for node in self.nodes:
            if isinstance(node, ExclusiveGateway) and node.direction == "diverging":
                if not self.get_outgoing_edges(node.id):
                    errors.append(f"ExclusiveGateway '{node.id}' 没有出口 edge")

        # 7. ParallelGateway(diverging) 至少有 2 个出口
        for node in self.nodes:
            if isinstance(node, ParallelGateway) and node.direction == "diverging":
                if len(self.get_outgoing_edges(node.id)) < 2:
                    errors.append(f"ParallelGateway '{node.id}' fork 至少需要 2 个出口")

        # 8. 非 EndEvent 节点至少有一个出口
        for node in self.nodes:
            if not isinstance(node, EndEvent) and not self.get_outgoing_edges(node.id):
                errors.append(f"节点 '{node.id}' 没有出口 edge")

        return errors

    def get_node(self, node_id: str) -> FlowNode:
        """按 ID 获取节点
        
        Fail Fast：节点不存在时立即抛异常。
        调用者应确保 node_id 来自合法来源（如 Token.node_id 或 edge.target）。
        """
        for n in self.nodes:
            if n.id == node_id:
                return n
        raise ValueError(f"Node '{node_id}' not found in '{self.process_id}'")

    def get_start_event(self) -> StartEvent:
        """获取唯一的 StartEvent — BPMNEngine.run() 启动时调用"""
        for n in self.nodes:
            if isinstance(n, StartEvent):
                return n
        raise ValueError(f"ProcessDefinition '{self.process_id}' 没有 StartEvent")

    def get_outgoing_edges(self, node_id: str) -> List[FlowEdge]:
        """获取指定节点的所有出口边 — BPMNEngine.advance_token() 中使用"""
        return [e for e in self.edges if e.source == node_id]

    def get_incoming_edges(self, node_id: str) -> List[FlowEdge]:
        """获取指定节点的所有入口边 — ParallelGateway join 时计算 expected_count"""
        return [e for e in self.edges if e.target == node_id]
```

### 3.1 消息类型（6 种）

```python
# protocol/flow_message.py
#
# 消息类型枚举 — 定义 flow 和 runtime 之间通信的所有消息种类。
#
# 设计分组：
#   消息分为两组，对应 Agent 的两种关注点：
#   1. 生命周期组（agent_*）：管理 Agent 实例的创建/销毁/挂起/恢复
#      这些消息改变 Agent 的存在状态，不涉及具体任务执行
#   2. 节点执行组（node_*）：驱动 Agent 执行 BPMN 节点
#      这些消息触发 Agent 的 think→act 循环
#   3. 消息路由（chat_message）：群聊/私聊/ask_reply 统一
#
# 为什么用 str Enum 而非纯字符串：
#   1. IDE 自动补全和类型检查
#   2. 防止拼写错误（"node_excute" 这种 typo 会被 IDE 标红）
#   3. 枚举值可以遍历（用于校验和文档生成）

class FlowMessageType(str, Enum):
    """消息类型 — 和 BPMN 生命周期对齐"""
    # ── 生命周期组（runtime 自有，不对应 BPMN 节点）──
    AGENT_CREATE = "agent_create"     # 创建 Agent 实例（必须先创建才能发任务）
    AGENT_DESTROY = "agent_destroy"   # 销毁 Agent 实例（释放资源）
    AGENT_SUSPEND = "agent_suspend"   # 挂起 Agent（保存状态栈 + 对话历史到快照）
    AGENT_RESUME = "agent_resume"     # 恢复 Agent（从快照重建实例）
    # ── 节点执行组（和 BPMN 节点执行对齐）──
    NODE_EXECUTE = "node_execute"     # 执行 BPMN 节点（payload 带序列化的 FlowNode）
    NODE_CANCEL = "node_cancel"       # 取消正在执行的节点（如超时或用户手动取消）
    # ── 消息路由 ──
    CHAT_MESSAGE = "chat_message"     # 聊天消息（群聊/私聊/ask_reply 统一入口）
```

### 3.2 类型化 Payload

```python
# protocol/payloads.py
#
# 类型化 Payload — 每种 FlowMessage 类型对应一个具体的 Payload 类。
#
# 设计意图：
#   FlowMessage.payload 在传输层保持 dict（JSON 兼容），
#   但消费者通过 parse_payload() 可以获得类型安全的 Pydantic 对象。
#   这样既保证了序列化的简单性，又提供了消费端的类型校验。
#
# 为什么不直接在 FlowMessage 中用 Union[Payload1, Payload2, ...]：
#   1. FlowMessage 需要跨网络传输（JSON），Union 类型的序列化/反序列化复杂
#   2. 不同消费者可能只关心部分字段，dict 更灵活
#   3. 新增消息类型时不需要修改 FlowMessage 的类型定义

class NodeExecutePayload(BaseModel):
    """节点执行 Payload — flow 告诉 runtime "执行这个节点"
    
    这是最核心的 Payload 类型，承载了 Agent 执行任务所需的全部信息。
    
    数据流：
      flow 构造 → 序列化为 dict → 放入 FlowMessage.payload → HTTP 传输
      → runtime 收到 → parse_payload() → NodeExecutePayload 实例
      → MainLoop.handle_node_execute() 消费各字段
    """
    process_instance_id: str          # 所属的流程实例 ID — 用于上报 NodeResult 时关联
    node: dict                        # 序列化的 FlowNode — runtime 用 deserialize_node() 还原
                                      # 为什么传 dict 而非具体类型：跨网络传输需要 JSON 兼容
    control_level: str = "free"       # 三级控制：free（自由）| guided（引导）| enforced（强制）
                                      # free：Agent 自主决定如何完成
                                      # guided：prompt 中包含步骤建议，但 Agent 可以偏离
                                      # enforced：BPMNEngine 强制按工作流步骤执行
    process_definition: Optional[dict] = None  # enforced 时必填：完整的 ProcessDefinition
                                               # runtime 的 WorkflowEngine 需要加载工作流定义
                                               # 由 flow 加载后传入，runtime 不再请求 platform
    input_refs: List[str] = []        # 输入引用列表 — runtime 解析为实际内容注入 prompt
    allowed_tools: List[str] = []     # 节点级工具白名单 — 三层权限的第三层
    output_schema: Optional[dict] = None  # 输出结构定义 — 动态生成 submit_step_result 工具的参数
    suspicion_hints: List[str] = []   # 怀疑机制提示 — 注入 prompt 第四层，提醒 Agent 独立验证
                                      # 场景：代码审查时提醒"前序代码可能有错"
                                      # 由 flow 的 get_suspicion_hints() 根据节点类型生成

class NodeCancelPayload(BaseModel):
    """取消节点执行 — flow 告诉 runtime "停止这个任务"
    
    使用场景：
      - 用户手动取消任务
      - 门禁超时导致流程回退
      - BoundaryEvent 触发中断（Phase 2）
    """
    process_instance_id: str          # 所属流程实例
    node_id: str                      # 要取消的节点 ID
    reason: str = ""                  # 取消原因（记录到日志和通知）

class ChatMessagePayload(BaseModel):
    """聊天消息 Payload — 群聊/私聊/ask_reply 统一格式
    
    设计意图：
      三种聊天场景用同一个 Payload 类型，通过字段组合区分：
      - 普通群聊：sender_id + content + mentions（可选）
      - 私聊/被 @：sender_id + content + mentions 包含目标 agent_id
      - ask_reply（回复提问）：sender_id + content + reply_to（非空）
    
    为什么统一而非分三个 Payload：
      runtime 的 MainLoop.handle_chat_message() 处理逻辑是统一的，
      都是"注入消息到对话历史 → 判断是否需要回复 → 执行回复"。
      分三个类型只会增加 match 分支而不减少逻辑复杂度。
    """
    sender_id: str                    # 发送者：Agent ID（如 "frontend-dev-1"）或 "user"
    content: str                      # 消息内容（纯文本）
    mentions: List[str] = []          # 被 @ 的 Agent ID 列表 — 决定哪些 Agent 需要回复
    reply_to: Optional[dict] = None   # ask_reply 时填入：{ask_id: str, responder_id: str}
                                      # ask_id = 原始 ask_teammate 工具调用的 tool_call_id
                                      # responder_id = 回复者的 agent_id
                                      # MainLoop 收到后通过 ask_id 匹配等待中的 asyncio.Event

class AgentCreatePayload(BaseModel):
    """创建 Agent — flow 告诉 runtime "创建一个新的 Agent 实例"
    
    runtime 收到后：
      1. 通过 role_id 从 platform 加载角色定义
      2. 加载角色引用的共享规则
      3. 创建 Agent 实例（初始状态栈 = [IDLE]）
      4. 组装初始 system prompt
      5. 加入 Agent 池
    """
    role_id: str                      # 角色 ID（如 "backend_dev"）— 决定 Agent 的身份和能力
    project_id: str                   # 项目 ID — 决定加载哪个项目的配置覆盖

class AgentDestroyPayload(BaseModel):
    """销毁 Agent — flow 告诉 runtime "释放这个 Agent"
    
    使用场景：
      - 项目完成，所有 Agent 销毁
      - 阶段切换，不再需要某个角色
      - 资源回收（长时间 idle 的 Agent）
    """
    reason: str = ""                  # 销毁原因（记录到日志）

# Payload 类型映射表 — parse_payload() 根据 message type 查找对应的 Payload 类
# None 表示该消息类型没有结构化 payload（suspend/resume 只需要 agent_id）
PAYLOAD_TYPE_MAP = {
    "agent_create": AgentCreatePayload,
    "agent_destroy": AgentDestroyPayload,
    "agent_suspend": None,            # suspend 不需要额外参数，agent_id 在 FlowMessage 层
    "agent_resume": None,             # resume 不需要额外参数，从快照恢复
    "node_execute": NodeExecutePayload,
    "node_cancel": NodeCancelPayload,
    "chat_message": ChatMessagePayload,
}
```

### 3.3 FlowMessage

```python
# protocol/flow_message.py

class FlowMessage(BaseModel):
    """flow → runtime 统一消息 — 所有通信的唯一载体
    
    设计职责：
      这是 flow 和 runtime 之间通信的唯一消息格式。
      无论是创建 Agent、执行节点还是转发聊天消息，都用这一个结构。
    
    为什么统一而非按类型分多个消息类：
      1. runtime 只有一个入口（POST /messages），统一格式简化路由
      2. 序列化/反序列化只需处理一种格式
      3. 日志和监控只需关注一种消息结构
      4. 新增消息类型不需要新增 API 端点
    
    payload 为什么保持 dict 而非直接用 Pydantic 子类：
      1. JSON 传输层天然是 dict，避免序列化/反序列化的额外开销
      2. 消费者按需调用 parse_payload() 获得类型安全的对象
      3. 中间件（如日志、监控）可以直接读 dict 而不需要知道具体类型
      4. 向后兼容 — 新版本的 payload 字段不会导致旧版本反序列化失败
    """
    message_id: str                   # 消息唯一标识（UUID）— 用于：
                                      #   1. NodeResult 回溯（result.message_id 对应哪个请求）
                                      #   2. 幂等性保证（重复消息可以去重）
                                      #   3. 日志追踪（从请求到响应的完整链路）
    type: str                         # 消息类型 — FlowMessageType 枚举值
    agent_id: str                     # 目标 Agent ID — runtime 据此路由到具体 Agent 实例
    project_id: str                   # 项目 ID — 用于多项目隔离和配置加载
    payload: dict                     # 类型化负载 — 传输层保持 dict，消费端按需 parse
    created_at: datetime              # 创建时间 — 用于超时检测和审计

    def parse_payload(self) -> Optional[BaseModel]:
        """根据 type 解析 payload 为具体的 Pydantic 类型
        
        Fail Fast 设计：
          - 未知的 type → 立即抛异常（可能是版本不兼容）
          - type 在 MAP 中但值为 None → 返回 None（该类型无结构化 payload）
          - type 在 MAP 中且有类 → Pydantic 构造并校验（字段缺失会抛 ValidationError）
        
        调用者：
          MainLoop.dispatch() 中各 handler 的第一步都是 parse_payload()
        """
        cls = PAYLOAD_TYPE_MAP.get(self.type)
        if cls is None and self.type not in PAYLOAD_TYPE_MAP:
            raise ValueError(f"Unknown message type: {self.type}")
        if cls is None:
            return None               # 该类型无 payload（suspend/resume）
        return cls(**self.payload)     # Pydantic 校验 — 字段缺失或类型错误会抛异常
```

### 3.4 NodeResult

```python
# protocol/node_result.py
#
# NodeResult 是 runtime → flow 的执行结果上报。
# 每个 FlowMessage(type=node_execute) 最终对应一个 NodeResult 回传。
# flow 根据 result_type 决定流程如何推进（继续/重试/回退/卡住）。

class NodeResultType(str, Enum):
    """执行结果类型 — 三种可能的结局"""
    COMPLETED = "completed"           # 成功完成 — flow 推进到下一个节点
    BLOCKED = "blocked"               # 被阻塞 — Agent 无法继续（缺少信息/权限不足）
                                      # flow 通知用户或尝试其他路径
    FAILED = "failed"                 # 执行失败 — Agent 出错（超时/异常/超过最大轮次）
                                      # flow 根据重试策略决定重试或走 on_fail 边

class NodeResult(BaseModel):
    """runtime → flow 执行结果 — Agent 完成（或失败）一个节点后上报
    
    设计职责：
      1. 告诉 flow 执行结果（成功/阻塞/失败）
      2. 携带执行产出（output）供后续节点使用
      3. 提供可观测性数据（duration/tokens/tool_calls）供监控和成本分析
      4. 提供推理链摘要（reasoning_trace）供审计和调试
    
    消费者：
      - flow EventLoop.handle_node_result()：根据 result_type 推进流程
      - flow GateController：将 output 中的产物展示在审批卡片上
      - console 详情面板：展示执行统计和推理链
      - 成本分析系统：按 Agent/任务/项目统计 token 消耗
    """
    message_id: str                   # 对应的 FlowMessage.message_id — 用于回溯是哪个请求的结果
    agent_id: str                     # 执行者 Agent ID
    result_type: str                  # 结果类型：completed | blocked | failed
    output: Optional[dict] = None     # 执行产出 — completed 时必填
                                      # 内容由 output_schema 定义（如 {test_file: "...", passed: true}）
                                      # 存入 ProcessInstance.node_outputs，供后续 Gateway 条件求值
    reason: Optional[str] = None      # 原因说明 — blocked/failed 时必填
                                      # blocked："缺少数据库连接信息，需要 DevOps 提供"
                                      # failed："超过最大轮次（20 轮）"
    reasoning_trace: Optional[str] = None  # 推理链摘要 — Agent 执行过程的自然语言总结
                                           # 用途：审计追溯（"按 TDD 流程实现，12 测试通过"）
                                           # 不是完整的对话历史，而是 Agent 自己总结的执行过程
    # ── 可观测性统计字段 ──
    duration_ms: int = 0              # 总执行时长（毫秒）— 从收到 FlowMessage 到上报 NodeResult
    tool_call_count: int = 0          # 工具调用总次数 — 衡量任务复杂度
    llm_call_count: int = 0           # LLM 调用总次数 — 衡量 think→act 循环轮数
    total_tokens: int = 0             # Token 总消耗 — 成本分析的核心指标
    created_at: datetime              # 上报时间
```

## 四、数据结构 — models 模块

### 4.1 RoleDefinition + PermissionConfig

```python
# models/role.py
#
# 角色定义和权限配置 — 决定 Agent "是谁"和"能做什么"。
# 从 platform API 加载（支持三级覆盖：system → company → project）。

class PermissionConfig(BaseModel):
    """路径权限配置 — 控制 Agent 对文件系统的访问范围
    
    设计意图：
      Agent 在沙箱中执行文件操作时，ToolExecutor 根据此配置校验路径合法性。
      forbidden_paths 优先级最高 — 即使 read_paths 包含了某路径，
      如果 forbidden_paths 也包含它，则拒绝访问。
    
    路径格式：
      支持 glob 模式（如 "workspace/src/**"）。
      路径相对于沙箱的 /workspace/ 目录。
    
    三层权限中的位置：
      PermissionConfig 是角色级权限的一部分（第二层），
      与状态级（第一层）和节点级（第三层）共同决定最终权限。
    """
    read_paths: List[str] = []        # 可读路径列表 — Agent 可以读取这些路径下的文件
    write_paths: List[str] = []       # 可写路径列表 — Agent 可以创建/修改这些路径下的文件
    forbidden_paths: List[str] = []   # 禁止访问路径 — 优先级最高，覆盖 read/write
                                      # 典型用途：禁止访问 .env、secrets/、deploy/ 等敏感路径


class RoleDefinition(BaseModel):
    """角色定义 — 决定 Agent 的身份、能力和约束
    
    设计职责：
      这是 Agent 的"人格定义"。从 YAML 文件加载，存储在 platform 数据库中。
      runtime 创建 Agent 时加载角色定义，用于：
      1. PromptBuilder 组装 system prompt（identity + constraints）
      2. ToolExecutor 校验工具权限（tools 列表）
      3. ToolExecutor 校验路径权限（permissions）
    
    三级覆盖机制：
      platform API 自动处理覆盖合并：
      system 级（预装默认）→ company 级（公司统一）→ project 级（项目特化）
      runtime 收到的是合并后的最终结果，不需要自己做合并。
    
    extends 字段（Phase 2）：
      角色继承 — 如 backend_dev extends base_dev。
      子角色继承父角色的 tools/permissions/constraints，可以覆盖或追加。
    """
    role_id: str                      # 角色唯一标识（如 "tech_lead"）— 格式：小写字母+数字+下划线
    role_name: str                    # 人类可读名称（如 "项目负责人"）— 用于前端展示和通知
    description: str = ""             # 角色描述 — 用于文档和管理后台
    extends: Optional[str] = None     # 继承自哪个角色（Phase 2）— 如 "base_dev"

    # ── 共享规则引用 ──
    shared_rules_include: List[str] = []  # 引用的共享规则 ID 列表 — runtime 加载这些规则注入 prompt
    shared_rules_exclude: List[str] = []  # 排除的共享规则 — 继承时用于去掉父角色的某些规则

    # ── 身份与约束（注入 prompt 第二层）──
    identity: str                     # 自然语言身份描述 — 告诉 LLM "你是谁"
                                      # 示例："你是项目负责人，负责需求分析、技术方案设计..."
    constraints: List[str] = []       # 行为约束列表 — 告诉 LLM "你不能做什么"
                                      # 示例：["不直接实现代码", "不跳过需求分析直接进入开发"]

    # ── 能力定义 ──
    tools: List[str] = []             # 角色级工具白名单 — 三层权限的第二层
                                      # 只有在此列表中的工具，Agent 才能调用
    skills: List[str] = []            # 技能列表（Phase 3）— 可安装的技能包
    workflows: List[str] = []         # 可安装的工作流 ID 列表 — Level 3 Enforced 时使用
                                      # 如 tech_lead 可以安装 review_workflow

    # ── 权限 ──
    permissions: PermissionConfig = Field(default_factory=PermissionConfig)

    # ── 元信息 ──
    version: str = "1.0.0"            # 版本号 — 角色定义的版本管理
    created_by: str = "system"        # 创建者 — system（预装）/ admin（管理员自定义）

    @validator("role_id")
    def validate_role_id(cls, v):
        """校验 role_id 格式 — 只允许小写字母开头 + 小写字母/数字/下划线
        
        为什么限制格式：
          role_id 会出现在 agent_id 中（如 "backend-dev-1" 对应 role_id="backend_dev"），
          统一格式避免命名混乱和解析歧义。
        """
        if not re.match(r'^[a-z][a-z0-9_]*$', v):
            raise ValueError(f"role_id 格式无效: {v}")
        return v
```

### 4.2 SharedRule

```python
# models/rule.py
#
# 共享规则 — 跨角色的行为规范，注入 Agent 的 prompt 中。
# 规则有两种消费方式（双层消费机制），由 schema_def 字段是否存在决定。

class SharedRule(BaseModel):
    """共享规则 — 定义 Agent 的行为规范
    
    设计职责：
      共享规则是跨角色的通用行为约束。不同于角色定义（每个角色独有），
      共享规则可以被多个角色引用（通过 shared_rules_include）。
    
    双层消费机制（核心设计）：
      1. 有 schema_def → 注入 prompt 第一层（系统硬约束）
         runtime 框架层会校验 Agent 的输出是否符合 schema_def 定义的格式。
         违反硬约束 = 框架层拒绝（不是靠 LLM 自觉）。
         示例：communication 规则要求回复必须是 result/blocked/clarification 之一。
      
      2. 无 schema_def → 注入 prompt 第三层（软性指引）
         只是 prompt 中的文字建议，靠 LLM 自觉遵守。
         违反软指引 = LLM 可能不遵守（但不会被框架拦截）。
         示例：tdd 规则建议按红-绿-重构循环开发。
    
    为什么不全部做成硬约束：
      有些规则无法用 schema 表达（如"系统化调试"），
      且过度硬约束会限制 LLM 的灵活性。
    
    三级覆盖：
      项目级可以 enabled: false 关闭某条规则（如博客项目关闭 TDD）。
      platform API 自动处理覆盖，runtime 收到的是最终结果。
    """
    rule_id: str                      # 规则唯一标识（如 "communication"）
    name: str                         # 人类可读名称（如 "沟通规则"）
    description: str = ""             # 规则描述
    enabled: bool = True              # 是否启用 — 项目级可覆盖为 false 来关闭此规则

    # ── 双层消费 ──
    schema_def: Optional[dict] = None # 有值 → 硬约束（runtime 框架层校验）
                                      # 无值 → 软指引（只注入 prompt，不做框架校验）
    content: str                      # 规则内容（Markdown 格式）— 注入 prompt 供 LLM 阅读
                                      # 无论是硬约束还是软指引，content 都会注入 prompt
```

### 5.1 NodeStrategy 接口 + StrategyRegistry

```python
# bpmn/strategy.py
#
# 策略模式 — 将节点的"具体行为"从引擎中解耦。
#
# 核心设计思想：
#   BPMNEngine 只负责 Token 管理和节点遍历（"怎么走"），
#   节点到达后"做什么"由策略决定。
#   flow 和 runtime 各自注册不同的策略实现：
#     flow 侧：FlowTaskStrategy 构造 FlowMessage 发给 runtime
#     runtime 侧：AgentTaskStrategy 注入 prompt 驱动 Agent 执行
#
# 为什么用策略模式而非 Visitor 模式：
#   1. Visitor 要求对象知道 visitor 的存在（accept 方法），违反"纯数据"原则
#   2. 策略模式中对象完全不知道策略的存在 — FlowNode 没有任何策略相关代码
#   3. 注册表模式支持运行时动态注册/替换策略（测试时 mock 更方便）
#
# 线程安全：
#   StrategyRegistry 在初始化时注册所有策略，之后只读。
#   策略实例本身是无状态的（所有状态通过 ExecutionContext 传入）。

class NodeStrategy(ABC):
    """节点执行策略接口 — flow 和 runtime 各自实现
    
    实现者必须提供 execute() 方法。
    execute() 的返回值语义：
      - 返回 dict → 同步完成，结果存入 ProcessInstance.node_outputs
      - 返回 None → 异步等待回调（如 flow 发消息给 runtime 后等待 NodeResult）
    """

    @abstractmethod
    async def execute(self, node: FlowNode, ctx: "ExecutionContext") -> Optional[dict]:
        """执行节点，返回结果
        
        参数：
          node: 当前要执行的 FlowNode 实例（具体子类型）
          ctx: 执行上下文 — 提供运行时依赖（HTTP 客户端、Agent 实例等）
        
        返回：
          dict → 执行结果（同步完成）
          None → 异步等待（flow 等 NodeResult 回调，runtime 等 step_complete）
        
        异常：
          策略内部的异常应该被捕获并转为 NodeResult(failed)，
          不应该让异常穿透到 BPMNEngine（会导致整个流程崩溃）。
        """
        ...


class StrategyRegistry:
    """策略注册表 — 按 node_type 查找对应的执行策略
    
    设计职责：
      维护 node_type → NodeStrategy 的映射关系。
      BPMNEngine 在处理每个节点时，通过 registry.get(node.node_type) 获取策略。
    
    使用方式：
      registry = StrategyRegistry()
      registry.register("abstract_task", FlowTaskStrategy())
      registry.register("user_task", FlowUserTaskStrategy())
      engine = BPMNEngine(registry)
    
    未注册的 node_type：
      has() 返回 False → BPMNEngine 跳过策略执行，直接 advance_token。
      这是正常情况 — StartEvent 和 Gateway 不需要策略（引擎自己处理）。
      但如果一个 AbstractTask 没有注册策略 → get() 会抛异常（Fail Fast）。
    """

    def __init__(self):
        self._strategies: Dict[str, NodeStrategy] = {}

    def register(self, node_type: str, strategy: NodeStrategy):
        """注册策略 — 通常在应用启动时调用一次"""
        self._strategies[node_type] = strategy

    def get(self, node_type: str) -> NodeStrategy:
        """获取策略 — Fail Fast，未注册时立即抛异常
        
        调用者应先用 has() 检查是否注册。
        直接调用 get() 而不检查 = 断言"这个 node_type 必须有策略"。
        """
        strategy = self._strategies.get(node_type)
        if strategy is None:
            raise ValueError(f"No strategy registered for node_type '{node_type}'")
        return strategy

    def has(self, node_type: str) -> bool:
        """检查是否有注册策略 — BPMNEngine 用于判断是否需要执行策略"""
        return node_type in self._strategies
```

### 5.2 ExecutionContext

```python
# bpmn/context.py
#
# 执行上下文 — 策略执行时需要的运行时依赖注入容器。
#
# 设计意图：
#   NodeStrategy.execute() 需要访问外部资源（HTTP 客户端、Agent 实例等），
#   但策略本身应该是无状态的。ExecutionContext 作为参数传入，
#   提供策略执行所需的一切运行时依赖。
#
# 三层继承：
#   ExecutionContext（基类）— 共享字段（process_instance_id、control_level 等）
#   ├── FlowExecutionContext — flow 侧策略使用（有 runtime_client、gate_controller）
#   └── AgentExecutionContext — runtime 侧策略使用（有 agent、tools、executor）
#
# 为什么分三层而非一个大类：
#   flow 和 runtime 的依赖完全不同：
#   - flow 需要 HTTP 客户端（发消息给 runtime）和门禁控制器
#   - runtime 需要 Agent 实例和工具列表
#   合并为一个类会导致大量 Optional 字段和类型不安全。

class ExecutionContext(BaseModel):
    """执行上下文基类 — 策略执行时的共享参数
    
    所有策略都需要知道的信息：
      - 当前在哪个流程实例中执行（process_instance_id）
      - 对应哪个消息（message_id）
      - 控制级别是什么（control_level）
      - 输入引用和输出约束
    """
    process_instance_id: str          # 当前流程实例 ID — 用于上报 NodeResult 时关联
    message_id: str = ""              # 触发此次执行的 FlowMessage ID
    input_refs: List[str] = []        # 输入引用 — 策略可能需要解析为实际内容
    control_level: str = "free"       # 控制级别 — 策略据此决定执行方式
    output_schema: Optional[dict] = None  # 输出约束 — 策略据此校验执行结果

    class Config:
        arbitrary_types_allowed = True  # 允许非 Pydantic 类型的字段（如 HTTP 客户端实例）


class FlowExecutionContext(ExecutionContext):
    """flow 侧的执行上下文 — FlowTaskStrategy 等策略使用
    
    提供 flow 策略执行所需的外部依赖：
      - runtime_client：向 runtime 发送 FlowMessage
      - gate_controller：创建门禁审批卡片
      - platform_client：读取工单/产物等数据
    
    为什么用 Any 而非具体类型：
      避免 core 对 flow 的具体实现产生依赖（core 是共享库）。
      实际类型在 flow 项目中确定（如 RuntimeClient、GateController）。
    """
    runtime_client: Any               # HTTP 客户端 — 向 runtime POST /messages
    gate_controller: Any              # 门禁控制器 — 创建 GateCard 推送给用户
    platform_client: Any              # platform API 客户端 — 读取工单/产物/配置
    project_id: str = ""              # 项目 ID — 构造 FlowMessage 时需要

    def resolve_actor(self, actor: Optional[str]) -> str:
        """解析角色 ID 为具体的 agent_id
        
        Phase 1 实现：直接返回（角色 ID = agent_id，一对一映射）
        Phase 2 扩展：支持角色池（一个角色多个 Agent，按负载选择）
        """
        return actor or ""

    async def on_process_completed(self):
        """流程完成回调 — FlowEndEventStrategy 调用
        
        通知 FlowEngine 当前流程实例已完成，
        FlowEngine 据此推进父流程（如阶段完成后推进 Pipeline）。
        """
        ...


class AgentExecutionContext(ExecutionContext):
    """runtime 侧的执行上下文 — AgentTaskStrategy 等策略使用
    
    提供 runtime 策略执行所需的运行时依赖：
      - agent：当前 Agent 实例（含状态栈、对话历史、角色定义）
```

### 5.3 flow 侧策略

```python
# flow 项目中定义
#
# flow 侧策略实现 — 每种节点类型在 flow 中的具体行为。
# flow 的策略核心职责：构造 FlowMessage 发给 runtime，然后等待回调。
# 所有 flow 策略都返回 None（异步等待 NodeResult 回调）。

class FlowTaskStrategy(NodeStrategy):
    """flow: AbstractTask → 构造 node_execute 消息发给 runtime
    
    执行逻辑：
      1. 通过 ctx.resolve_actor() 将角色 ID 映射为 agent_id
      2. 将 FlowNode 序列化为 dict 放入 payload
      3. 构造 FlowMessage 发送给 runtime
      4. 返回 None — 流程暂停，等待 runtime 上报 NodeResult
    
    返回 None 的语义：
      BPMNEngine 收到 None 后不会立即 advance_token，
      而是等待外部事件（NodeResult）触发后再继续推进。
      这实现了"异步等待"的语义 — flow 发出指令后不阻塞。
    """
    async def execute(self, node: AbstractTask, ctx: FlowExecutionContext) -> Optional[dict]:
        msg = FlowMessage(
            message_id=generate_id(),
            type="node_execute",
            agent_id=ctx.resolve_actor(node.actor),
            project_id=ctx.project_id,
            payload=NodeExecutePayload(
                process_instance_id=ctx.process_instance_id,
                node=node.dict(),
                control_level="free",
                input_refs=node.input_refs,
                allowed_tools=node.allowed_tools,
                output_schema=node.output_schema,
            ).dict(),
            created_at=datetime.now(),
        )
        await ctx.runtime_client.send(msg)
        return None  # 异步等待 NodeResult 回调

class FlowUserTaskStrategy(NodeStrategy):
    """flow: UserTask → 创建门禁卡片，等待用户操作
    
    执行逻辑：
      调用 gate_controller.create_gate() 创建 GateCard，
      通过 gate → chat 推送给用户。
      流程暂停，等待用户点击 approve/reject/request_changes。
    
    与 FlowTaskStrategy 的区别：
      FlowTaskStrategy 等待 Agent（机器）完成
      FlowUserTaskStrategy 等待用户（人类）操作
    """
    async def execute(self, node: UserTask, ctx: FlowExecutionContext) -> Optional[dict]:
        await ctx.gate_controller.create_gate(node)
        return None  # 异步等待用户审批操作

class FlowAdHocStrategy(NodeStrategy):
    """flow: AdHocSubProcess → 构造 node_execute 消息发给协调者
    
    执行逻辑：
      将 AdHocSubProcess 节点发给协调者（coordinator_id）。
      如果没有指定协调者，发给参与者列表的第一个。
      runtime 收到后由 AgentAdHocStrategy 将所有参与者推入协作状态。
    
    为什么发给协调者而非所有参与者：
      FlowMessage 是一对一的（一个 agent_id），不支持广播。
      runtime 的 AgentAdHocStrategy 负责将消息"扩散"给所有参与者。
    """
    async def execute(self, node: AdHocSubProcess, ctx: FlowExecutionContext) -> Optional[dict]:
        msg = FlowMessage(
            message_id=generate_id(),
            type="node_execute",
            agent_id=node.coordinator_id or node.participant_ids[0],
            project_id=ctx.project_id,
            payload=NodeExecutePayload(
                process_instance_id=ctx.process_instance_id,
                node=node.dict(),
                control_level="free",
            ).dict(),
            created_at=datetime.now(),
        )
        await ctx.runtime_client.send(msg)
        return None  # 异步等待协调者提交结论

class FlowEndEventStrategy(NodeStrategy):
    """flow: EndEvent → 通知流程完成，触发阶段推进
    
    执行逻辑：
      调用 ctx.on_process_completed() 通知 FlowEngine 当前流程实例完成。
      FlowEngine 据此推进父流程：
      - 如果是阶段流程完成 → 推进 Pipeline 到下一个阶段
      - 如果是 Pipeline 完成 → 项目完成
    
    为什么 EndEvent 需要策略而 StartEvent 不需要：
      StartEvent 只是 Token 的起点，不需要"做什么"。
      EndEvent 需要触发"流程完成"的副作用（推进父流程、发通知等）。
    """
    async def execute(self, node: EndEvent, ctx: FlowExecutionContext) -> Optional[dict]:
        await ctx.on_process_completed()
        return None

def create_flow_registry() -> StrategyRegistry:
    """构造 flow 侧的策略注册表 — FlowEngine 初始化时调用
    
    注册了 4 种节点类型的策略：
      - abstract_task → FlowTaskStrategy（发消息给 runtime）
      - user_task → FlowUserTaskStrategy（创建门禁卡片）
      - ad_hoc_sub_process → FlowAdHocStrategy（发消息给协调者）
      - end_event → FlowEndEventStrategy（触发流程完成）
    
    未注册的节点类型（由 BPMNEngine 自己处理）：
      - start_event：引擎创建初始 Token，无需策略
      - exclusive_gateway：引擎调用 node.evaluate()，无需策略
      - parallel_gateway：引擎处理 Token 分裂/合并，无需策略
    """
    registry = StrategyRegistry()
    registry.register("abstract_task", FlowTaskStrategy())
    registry.register("user_task", FlowUserTaskStrategy())
    registry.register("ad_hoc_sub_process", FlowAdHocStrategy())
    registry.register("end_event", FlowEndEventStrategy())
    return registry
```

### 5.4 runtime 侧策略

```python
# runtime 项目中定义
#
# runtime 侧策略实现 — 每种节点类型在 runtime 中的具体行为。
# runtime 的策略核心职责：注入 prompt + 驱动 Agent think→act 循环。
# 与 flow 侧策略的区别：flow 只"发指令"，runtime 真正"执行任务"。

class AgentTaskStrategy(NodeStrategy):
    """runtime: AbstractTask → 注入步骤 prompt，驱动 Agent think→act 循环
    
    执行逻辑：
      1. 将节点的 name 和 action 组装为步骤 prompt，注入 Agent 对话历史
      2. 在当前工具集基础上追加 step_complete 工具（Agent 完成后调用此工具提交结果）
      3. 调用 AgentExecutor.run() 启动 think→act 循环
      4. Agent 调用 step_complete 时循环结束，返回执行结果
    
    step_complete 工具的作用：
      这是 Agent 表达"我完成了"的唯一方式。
      工具的参数由 node.output_schema 动态生成，确保输出格式符合预期。
      没有 step_complete，Agent 会无限循环（不知道什么时候该停）。
    
    返回值：
      Agent 调用 step_complete 时传入的参数 dict — 作为节点的执行输出。
      存入 ProcessInstance.node_outputs，供后续 Gateway 条件求值。
    """
    async def execute(self, node: AbstractTask, ctx: AgentExecutionContext) -> Optional[dict]:
        # 注入步骤 prompt — 告诉 Agent 当前要做什么
        step_prompt = f"【当前步骤：{node.name}】\n{node.action or ''}"
        ctx.agent.conversation.append(Message(role="system", content=step_prompt))
        # 追加 step_complete 工具 — Agent 完成后必须调用此工具提交结果
        step_tools = ctx.tools + [create_step_complete_tool(node.output_schema)]
        # 启动 think→act 循环 — 直到 Agent 调用 step_complete 或超过最大轮次
        result = await ctx.executor.run(ctx.agent, step_tools)
        return result

class AgentAdHocStrategy(NodeStrategy):
    """runtime: AdHocSubProcess → 将所有参与者推入协作状态
    
    执行逻辑：
      1. 从 metadata 获取议程（agenda）
      2. 遍历所有参与者，将每个 Agent 推入 EXECUTING 状态
      3. 注入协作活动的 system prompt（议程、协调者信息）
      4. 返回 None — 协作活动通过群聊进行，协调者提交结论时结束
    
    与 AgentTaskStrategy 的区别：
      - AgentTaskStrategy：单个 Agent 独立执行
      - AgentAdHocStrategy：多个 Agent 协作，通过群聊交互
    
    协作活动的结束方式：
      协调者调用 submit_step_result → runtime 上报 NodeResult(completed)
      → flow 收到后推进流程
    """
    async def execute(self, node: AdHocSubProcess, ctx: AgentExecutionContext) -> Optional[dict]:
        agenda = node.get_metadata("agenda", node.name)
        # 将所有参与者推入协作状态
        for agent in ctx.get_agents(node.get_participants()):
            agent.state_stack.append(StackEntry(
                state=StackState.EXECUTING,
                context={
                    "node_type": "ad_hoc_sub_process",
                    "node_id": node.id,
                    "coordinator_id": node.coordinator_id,
                    "participant_ids": node.participant_ids,
                }
            ))
            # 注入协作活动 prompt — 告诉每个参与者当前在做什么
            agent.conversation.append(Message(
                role="system",
                content=f"【协作活动开始】\n议程：{agenda}\n协调者：{node.coordinator_id}"
            ))
        return None  # 协作通过群聊进行，协调者提交结论时结束

def create_agent_registry() -> StrategyRegistry:
    """构造 runtime 侧的策略注册表 — WorkflowEngine 初始化时调用
    
    注册了 2 种节点类型的策略：
      - abstract_task → AgentTaskStrategy（注入 prompt + think→act）
      - ad_hoc_sub_process → AgentAdHocStrategy（多人协作）
    
    runtime 不需要处理的节点类型：
      - start_event / end_event / gateway：由 BPMNEngine 自己处理
      - user_task：runtime 不处理门禁（门禁由 flow 管理）
    """
    registry = StrategyRegistry()
    registry.register("abstract_task", AgentTaskStrategy())
    registry.register("ad_hoc_sub_process", AgentAdHocStrategy())
    return registry
```

### 5.5 BPMNEngine

```python
# bpmn/engine.py

class BPMNEngine:
    """BPMN 流程引擎 — Token 驱动 + 策略注册表
    
    这是整个系统的核心引擎，flow 和 runtime 都通过它驱动流程执行。
    
    设计原则：
      - 引擎只负责 Token 管理和节点遍历（"怎么走"）
      - 节点的具体行为由策略决定（"到了这里做什么"）
      - Gateway 的条件评估由对象自己完成（对象自治）
      - 引擎不包含任何业务逻辑
    
    为什么 Gateway 不走策略：
      Gateway 的行为（条件评估 / Token 分裂合并）是 BPMN 标准语义，
      在 flow 和 runtime 中完全一样，不需要按环境区分。
      而且 Gateway 的行为和 Token 管理紧密耦合（分裂/合并），
      放在引擎内部比委托给外部策略更自然。
    """

    def __init__(self, registry: StrategyRegistry, on_event=None):
        self.registry = registry
        # on_event 回调用于可观测性：引擎每个关键动作都会通知外部
        # flow 用它记录 edge_history，runtime 用它发送 AG-UI 事件给前端
        self.on_event = on_event or (lambda e: None)

    async def run(self, process_def: ProcessDefinition, instance: ProcessInstance, ctx: ExecutionContext):
        """Token 驱动的流程执行
        
        为什么是 async：
          策略的 execute() 可能涉及网络调用（flow 发 HTTP 给 runtime，
          runtime 调用 LLM），必须是异步的。
        """

        # 0. 校验 — 契约设计的前置条件
        # 为什么在 run() 里校验而不是在 from_dict() 里：
        #   from_dict() 已经校验了，但 ProcessDefinition 可能被手动构造（测试场景），
        #   所以 run() 再校验一次作为防御性编程。
        errors = process_def.validate_structure()
        if errors:
            raise ValueError(f"ProcessDefinition 校验失败: {errors}")

        # 1. 创建初始 Token — 流程从 StartEvent 开始
        start_node = process_def.get_start_event()
        initial_token = Token(token_id=generate_id(), node_id=start_node.id)
        instance.tokens = [initial_token]
        self.on_event({"type": "engine_started", "process_id": process_def.process_id})

        # 2. 主循环：每轮处理所有 active Token
        # 为什么是 while + for 而不是递归：
        #   递归在深层流程中会栈溢出（100 个节点 = 100 层递归）。
        #   while 循环 + Token 列表是迭代式的，无栈深度限制。
        while self.has_active_tokens(instance):
            for token in self.get_active_tokens(instance):
                node = process_def.get_node(token.node_id)
                self.on_event({"type": "node_enter", "node_id": node.id, "token_id": token.token_id})

                # Gateway 对象自治（条件评估 / Token 分裂合并）
                # Activity/Event 走策略注册表（由 flow/runtime 各自实现）
                # 为什么用 isinstance 而不是 node_type 字符串：
                #   isinstance 是类型安全的，IDE 能提示方法；
                #   而且 Gateway 的处理逻辑在 advance_token 中，不在这里。
                if not isinstance(node, (ExclusiveGateway, ParallelGateway)):
                    if self.registry.has(node.node_type):
                        strategy = self.registry.get(node.node_type)
                        result = await strategy.execute(node, ctx)
                        if result:
                            instance.node_outputs[node.id] = result

                await self.advance_token(token, node, process_def, instance)

        self.on_event({"type": "engine_completed", "process_id": process_def.process_id})

    async def advance_token(self, token, node, process_def, instance):
        """推进 token（幂等：已 completed 跳过）"""

        if token.status == "completed":
            return

        if isinstance(node, EndEvent):
            token.transition_to("completed")
            if node.is_terminate():
                for t in instance.tokens:
                    if t.status == "active":
                        t.transition_to("completed")
            self.on_event({"type": "token_end", "token_id": token.token_id})
            return

        if isinstance(node, ParallelGateway) and node.direction == "diverging":
            token.transition_to("completed")
            targets = node.get_fork_targets(process_def.get_outgoing_edges(node.id))
            for target_id in targets:
                child = Token(token_id=generate_id(), node_id=target_id, parent_token_id=token.token_id)
                instance.tokens.append(child)
            self.on_event({"type": "token_fork", "parent": token.token_id, "children": len(targets)})
            return

        if isinstance(node, ParallelGateway) and node.direction == "converging":
            token.transition_to("waiting")
            waiting = [t for t in instance.tokens if t.node_id == node.id and t.status == "waiting"]
            expected = len(process_def.get_incoming_edges(node.id))
            if node.is_join_complete(len(waiting), expected):
                for t in waiting:
                    t.transition_to("completed")
                outgoing = process_def.get_outgoing_edges(node.id)
                if outgoing:
                    merged = Token(token_id=generate_id(), node_id=outgoing[0].target)
                    instance.tokens.append(merged)
                self.on_event({"type": "token_join", "node_id": node.id})
            return

        if isinstance(node, ExclusiveGateway):
            outgoing = process_def.get_outgoing_edges(node.id)
            target = node.evaluate(outgoing, instance.node_outputs)
            token.node_id = target
            return

        # 普通节点：沿 sequence flow 推进
        outgoing = process_def.get_outgoing_edges(node.id)
        if outgoing:
            token.node_id = outgoing[0].target
        else:
            raise RuntimeError(f"节点 '{node.id}' 没有出口 edge")

    def has_active_tokens(self, instance) -> bool:
        """检查是否还有活跃的 Token（包括 waiting 状态）
        
        BPMNEngine.run() 的主循环终止条件：has_active_tokens() == False。
        
        为什么包含 waiting 状态：
          waiting 的 Token 是 ParallelGateway join 时先到的分支，
          它们还在等待其他分支到齐。如果不计入 active，
          引擎会在所有分支到齐前提前退出（误判为流程结束）。
        """
        return any(t.status in ("active", "waiting") for t in instance.tokens)

    def get_active_tokens(self, instance) -> List[Token]:
        """获取所有需要推进的 Token（不包括 waiting）
        
        与 has_active_tokens 的不对称设计：
          has_active_tokens 包含 waiting（判断"流程是否还在运行"）
          get_active_tokens 不包含 waiting（判断"哪些 Token 需要被处理"）
          
        waiting 的 Token 不需要被"推进" — 它们在等待其他分支，
        只有当 is_join_complete() 返回 True 时才会被合并处理。
        """
        return [t for t in instance.tokens if t.status == "active"]
```

```python
支持的操作符：
```

## 八、错误类型

```python
# bpmn/errors.py
#
# core 模块的异常体系 — 所有异常继承自 CoreError。
#
# 设计原则：
#   1. 每种异常对应一类明确的错误场景（不用通用 Exception）
#   2. 异常消息包含足够的上下文信息（哪个节点、哪个字段出错）
#   3. 调用者可以按异常类型做不同处理（如 flow 对 NoMatchingCondition 走 default 分支）
#
# 恢复建议：
#   - ProcessDefinitionError → 修复 YAML 定义文件（设计时错误，非运行时错误）
#   - NoMatchingCondition → 检查 Gateway 的条件覆盖是否完整，或添加 default_route
#   - UnsupportedGatewayType → 确认 Phase 版本是否支持该网关类型
#   - InvalidCondition → 检查条件表达式格式是否符合 "field op value"
#   - InvalidFlowMessage → 检查消息构造方是否使用了正确的 type 和 payload 格式

class CoreError(Exception):
    """core 错误基类 — 所有 core 模块的异常都继承此类
    
    消费者可以 catch CoreError 统一处理所有 core 相关错误，
    也可以 catch 具体子类做精细化处理。
    """

class ProcessDefinitionError(CoreError):
    """流程定义错误 — 流程定义的结构不合法
    
    触发场景：
      - 没有 StartEvent 节点
      - 有多个 StartEvent 节点
      - 节点 ID 重复
      - 边引用不存在的节点（source 或 target 不在 node_ids 中）
      - nodes 列表为空
    
    恢复方式：
      这是设计时错误 — 修复 YAML/JSON 流程定义文件。
      validate_structure() 会返回所有错误的列表，一次性修复。
    """

class NoMatchingCondition(CoreError):
    """排他网关无匹配条件 — 所有条件都不满足且没有兜底路径
    
    触发场景：
      ExclusiveGateway.evaluate() 中：
      - 所有 conditional 边的条件都不匹配
      - 且没有 default_route 配置
    
    恢复方式：
      1. 检查条件表达式是否覆盖了所有可能的输出值
      2. 添加 default_route 作为兜底（推荐）
      3. 检查上游节点的 output 是否符合预期
    """

class UnsupportedGatewayType(CoreError):
    """不支持的网关类型 — 当前 Phase 不支持该网关
    
    触发场景：
      - Phase 1 中使用了 ParallelGateway（已调整为 Phase 1 支持）
      - 使用了 InclusiveGateway（Phase 3 才支持）
    
    恢复方式：
      检查流程定义中使用的网关类型是否在当前版本支持范围内。
    """

class InvalidCondition(CoreError):
    """条件表达式格式错误 — 无法解析条件字符串
    
    触发场景：
      ExclusiveGateway._match_condition() 中：
      - 条件字符串不包含 == 或 != 操作符
      - 条件字符串格式不符合 "field op value"
    
    恢复方式：
      检查 FlowEdge.condition 的格式。
      Phase 1 只支持 "field == value" 和 "field != value"。
    """

class InvalidFlowMessage(CoreError):
    """FlowMessage 格式错误 — 消息类型或 payload 不合法
    
    触发场景：
      FlowMessage.parse_payload() 中：
      - type 不在 PAYLOAD_TYPE_MAP 中（未知消息类型）
      - payload 缺少必填字段（Pydantic ValidationError）
    
    恢复方式：
      检查消息构造方（通常是 flow）是否使用了正确的 type 值和 payload 结构。
      可能是版本不兼容（flow 和 runtime 版本不一致）。
    """
```

ProcessDefinition 加载时的校验（在 `__init__` 或 validator 中）：

```python
@validator("nodes")
def validate_nodes(cls, v):
    ids = [n.id for n in v]
    if len(ids) != len(set(ids)):
        raise ProcessDefinitionError("节点 ID 重复")
    starts = [n for n in v if isinstance(n, StartEvent)]
    if len(starts) == 0:
        raise ProcessDefinitionError("缺少 start 节点")
    if len(starts) > 1:
        raise ProcessDefinitionError("多个 start 节点")
    return v

@validator("edges")
def validate_edges(cls, v, values):
    node_ids = {n.id for n in values.get("nodes", [])}
    for edge in v:
        if edge.source not in node_ids:
            raise ProcessDefinitionError(f"边 {edge.id} 的 source '{edge.source}' 不存在")
        if edge.target not in node_ids:
            raise ProcessDefinitionError(f"边 {edge.id} 的 target '{edge.target}' 不存在")
    return v
```

```yaml
# TDD 工作流 — Agent 级 ProcessDefinition
#
# 设计意图：
#   这是 runtime 的 WorkflowEngine 在 Level 3 (Enforced) 模式下驱动的工作流。
#   强制 Agent 按"红-绿-重构"循环执行，不允许跳过步骤。
#
# 流程路径：
#   start → write_test → run_red → write_code → run_green → check_result
#   check_result 网关：
#     passed == True → end（测试通过，任务完成）
#     default → write_code（测试失败，回到写代码步骤重试）
#
# 为什么用 ExclusiveGateway 而非让 Agent 自己判断：
#   Level 3 Enforced 的核心是"框架强制控制"，不依赖 LLM 的自觉。
#   Gateway 的条件评估是确定性的（读 output.passed 字段），
#   不会因为 LLM 的"幻觉"而跳过失败的测试。
#
# allowed_tools 的设计：
#   每个步骤只开放必要的工具，防止 Agent 在"写测试"步骤直接写实现代码。
#   这是三层权限的第三层（节点级）在实际流程中的体现。

process_id: tdd_workflow
name: TDD 工作流
version: "1.0"

nodes:
  # 流程入口
  - id: start
    node_type: start_event

  # 步骤 1：写失败测试（红灯）
  # Agent 只能读文件和写文件，不能执行代码（防止提前验证）
  - id: write_test
    node_type: abstract_task
    name: "写失败测试"
    action: "为当前任务编写单元测试，测试应该失败（红灯）"
    allowed_tools: [file_read, file_write]
    output_schema:
      type: object
      properties:
        test_file: { type: string }   # Agent 必须告诉我们测试文件路径
      required: [test_file]

  # 步骤 2：运行测试确认失败
  # Agent 只能执行代码（运行测试），不能修改文件
  - id: run_red
    node_type: abstract_task
    name: "运行测试（确认红灯）"
    action: "运行测试，确认新写的测试失败"
    allowed_tools: [code_execute]
    output_schema:
      type: object
      properties:
        passed: { type: boolean }     # 期望为 false（红灯）
        output: { type: string }      # 测试输出（作为证据）
      required: [passed]

  # 步骤 3：写最少的实现代码
  # Agent 可以读写文件，实现让测试通过的最少代码
  - id: write_code
    node_type: abstract_task
    name: "写代码"
    action: "编写最少的代码让测试通过"
    allowed_tools: [file_read, file_write]

  # 步骤 4：运行测试确认通过
  # Agent 只能执行代码，不能修改文件（防止偷偷改测试）
  - id: run_green
    node_type: abstract_task
    name: "运行测试（确认绿灯）"
    action: "运行测试，确认所有测试通过"
    allowed_tools: [code_execute]
    output_schema:
      type: object
      properties:
        passed: { type: boolean }     # 期望为 true（绿灯）
        total: { type: integer }      # 总测试数
        failed: { type: integer }     # 失败测试数
      required: [passed]

  # 条件网关：检查测试结果
  # passed == True → 结束 | 否则 → 回到 write_code 重试
  - id: check_result
    node_type: exclusive_gateway
    direction: diverging
    default_route: write_code         # 默认回到写代码（测试失败时的兜底路径）

  # 流程出口
  - id: end
    node_type: end_event

edges:
  # 线性流程：start → write_test → run_red → write_code → run_green → check_result
  - id: e1
    source: start
    target: write_test
    flow_type: sequence

  - id: e2
    source: write_test
    target: run_red
    flow_type: sequence

  - id: e3
    source: run_red
    target: write_code
    flow_type: sequence

  - id: e4
    source: write_code
    target: run_green
    flow_type: sequence

  - id: e5
    source: run_green
    target: check_result
    flow_type: sequence

  # 条件分支：测试通过 → 结束
  - id: e6
    source: check_result
    target: end
    flow_type: conditional
    condition: "passed == True"        # 从 run_green 的 output.passed 取值
    label: "pass"

  # 默认分支：测试失败 → 回到写代码（形成循环）
  - id: e7
    source: check_result
    target: write_code
    flow_type: default
    label: "fail → retry"             # 前端 BPMN 图上显示的标签
```

## 十一、SandboxProvider 完整接口

```python
# bpmn/sandbox.py

from abc import ABC, abstractmethod
from typing import Optional
from pydantic import BaseModel


class ExecResult(BaseModel):
    """命令执行结果 — SandboxProvider.exec() 的返回值
    
    设计职责：
      封装容器内命令执行的完整结果。ToolExecutor 据此构造 ToolResult 返回给 LLM。
      success property 是便捷判断（exit_code == 0），避免调用者每次手动比较。
    
    duration_ms 计算方式：
      从 exec 请求发出到收到完整 stdout/stderr 的时间（包含网络延迟）。
      用于 ExecutionTrace 记录和性能分析。
    """
    exit_code: int                    # 命令退出码 — 0=成功，非0=失败
    stdout: str                       # 标准输出 — 返回给 LLM 阅读
    stderr: str                       # 标准错误 — 失败时包含错误信息
    duration_ms: int                  # 执行耗时（毫秒）— 从请求发出到结果返回

    @property
    def success(self) -> bool:
        """是否执行成功 — ToolExecutor 据此设置 ToolResult.success"""
        return self.exit_code == 0


class FileInfo(BaseModel):
    """文件信息 — SandboxProvider.read_file() / stat() 的返回值
    
    path 格式：相对于容器内 /workspace/ 目录的路径（如 "src/main.rs"）。
    exists=False 时 size=0（文件不存在时 size 无意义）。
    """
    path: str                         # 文件路径（相对于 /workspace/）
    size: int                         # 文件大小（字节）— exists=False 时为 0
    exists: bool                      # 文件是否存在


class SandboxProvider(ABC):
    """沙箱环境抽象接口 — runtime 工具通过此接口在容器内执行操作

    实现者：
      - DockerSandboxProvider（Phase 1：调用 sandbox-manager API）
      - HostSandboxProvider（测试用：直接在宿主机执行）
      - MockSandboxProvider（单元测试用）
    """

    @abstractmethod
    async def exec(self, agent_id: str, command: str, timeout: int = 300) -> ExecResult:
        """在指定 Agent 的容器内执行命令

        Args:
            agent_id: Agent 标识（决定在哪个容器执行）
            command: shell 命令（如 "cargo test"）
            timeout: 超时秒数（默认 300s）

        Returns:
            ExecResult: 包含 exit_code / stdout / stderr / duration_ms

        Raises:
            SandboxNotAvailable: 容器未启动或不可达
            SandboxTimeout: 命令执行超时
        """
        ...

    @abstractmethod
    async def write_file(self, agent_id: str, path: str, content: str) -> None:
        """写文件到指定 Agent 的容器内

        Args:
            agent_id: Agent 标识
            path: 容器内路径（相对于 /workspace/，如 "src/models/tag.py"）
            content: 文件内容

        Raises:
            SandboxNotAvailable: 容器未启动
            SandboxPermissionError: 路径不在 /workspace/ 内（安全限制）
        """
        ...

    @abstractmethod
    async def read_file(self, agent_id: str, path: str) -> str:
        """读取指定 Agent 容器内的文件

        Args:
            agent_id: Agent 标识
            path: 容器内路径

        Returns:
            文件内容字符串

        Raises:
            SandboxNotAvailable: 容器未启动
            FileNotFoundError: 文件不存在
        """
        ...

    @abstractmethod
    async def list_files(self, agent_id: str, path: str = ".") -> list[FileInfo]:
        """列出目录内容

        Args:
            agent_id: Agent 标识
            path: 目录路径（相对于 /workspace/）

        Returns:
            FileInfo 列表
        """
        ...

    @abstractmethod
    async def git_commit(self, agent_id: str, message: str, files: list[str] = None) -> str:
        """在容器内执行 git add + git commit

        Args:
            agent_id: Agent 标识
            message: commit message
            files: 要 stage 的文件列表（None = git add -A）

        Returns:
            commit hash

        Raises:
            SandboxNotAvailable: 容器未启动
            GitError: git 操作失败（如没有变更）
        """
        ...

    @abstractmethod
    async def git_push(self, agent_id: str) -> None:
        """在容器内执行 git push

        Raises:
            SandboxNotAvailable: 容器未启动
            GitError: push 失败（如远程拒绝）
        """
        ...

    @abstractmethod
    async def get_service_url(self, service_name: str) -> str:
        """获取共享服务的内部 URL

        Args:
            service_name: 服务名（"postgres" / "redis" / "gitea"）

        Returns:
            内部 URL（如 "postgres://user:pass@blog-postgres:5432/blog"）
        """
        ...

    @abstractmethod
    async def get_status(self, agent_id: str) -> dict:
        """获取 Agent 容器的状态

        Returns:
            {"status": "running", "cpu_percent": 45, "memory_mb": 512}
        """
        ...


# 异常类型
#
# 沙箱相关异常 — 与 §八 的 CoreError 体系独立。
# 原因：沙箱异常属于基础设施层（I/O 错误），不属于 BPMN 业务逻辑层。
# CoreError 是 BPMN 引擎的业务异常（流程定义错误、条件不匹配等），
# Sandbox 异常是运行时环境异常（容器挂了、超时了、权限不够）。
#
# 可重试性标注：
#   SandboxNotAvailable — 可重试（容器可能正在启动中，等几秒再试）
#   SandboxTimeout — 不重试（命令本身太慢，重试也会超时）
#   SandboxPermissionError — 不重试（路径非法，重试也会被拒绝）
#   GitError — 视情况（网络问题可重试，冲突不可重试）

class SandboxNotAvailable(Exception):
    """沙箱环境不可用 — 容器未启动 / Docker daemon 不可达 / 网络不通
    
    触发场景：ToolExecutor 调用 SandboxProvider 时容器不存在或无法连接。
    恢复方式：等待容器启动完成后重试（通常 5-10 秒）。
    """
    pass

class SandboxTimeout(Exception):
    """命令执行超时 — 命令在指定时间内未完成
    
    触发场景：exec() 的 timeout 参数到期（默认 300s）。
    恢复方式：不重试。错误信息返回给 LLM，LLM 自己决定（缩短命令/拆分任务）。
    """
    pass

class SandboxPermissionError(Exception):
    """权限错误 — 试图访问容器内 /workspace/ 之外的路径
    
    触发场景：write_file/read_file 的 path 参数包含 "../" 或绝对路径。
    恢复方式：不重试。错误信息返回给 LLM，LLM 应该修正路径。
    """
    pass

class GitError(Exception):
    """Git 操作失败 — commit/push/clone 等操作异常
    
    触发场景：git_commit 时工作区无变更、push 时远程拒绝、clone 时仓库不存在。
    恢复方式：错误信息返回给 LLM，LLM 自己决定下一步。
    """
    pass
```

### 11.6 ModelProvider 接口（Phase 2）

```python
# model/provider.py
#
# ModelProvider — runtime 多模型工具通过此接口调用各种 AI 模型。
# 与 SandboxProvider / TestbedProvider 同级的外部服务抽象。

# 设计意图：

# 实现者：
#   - HttpModelProvider（生产环境：调用 OpenAI/Anthropic/DeepL 等外部 API）
#   - MockModelProvider（测试用：返回固定结果）

from abc import ABC, abstractmethod
from typing import Optional


class ModelProvider(ABC):
    """多模型调用抽象接口 — runtime 的 model_ops 工具通过此接口调用"""

    @abstractmethod
    async def generate_image(self, prompt: str, style: str = "diagram", size: str = "1024x1024") -> str:
        """生成图片
        
        Args:
            prompt: 图片描述（英文效果更好）
            style: 风格（diagram/ui_mockup/illustration/photo）
            size: 尺寸
        
        Returns:
            生成的图片保存路径（相对于 /workspace/）
        """
        ...

    @abstractmethod
    async def analyze_image(self, image_path: str, question: str) -> str:
        """分析图片内容
        
        Args:
            image_path: 图片文件路径
            question: 关于图片的问题
        
        Returns:
            分析结果文本
        """
        ...

    @abstractmethod
    async def translate(self, text: str, target_lang: str, source_lang: Optional[str] = None) -> str:
        """翻译文本
        
        Args:
            text: 要翻译的文本
            target_lang: 目标语言代码（en/zh/ja/ko/fr/de）
            source_lang: 源语言（可选，自动检测）
        
        Returns:
            翻译结果
        """
        ...

    @abstractmethod
    async def invoke(self, model_id: str, prompt: str, **kwargs) -> str:
        """通用模型调用（兜底方法）
        
        当预定义的方法不满足需求时，直接指定模型 ID 调用。
        
        Args:
            model_id: 模型标识（从 platform model_registry 查找）
            prompt: 给模型的 prompt
            **kwargs: 模型特定参数
        
        Returns:
            模型输出（文本或文件路径）
        """
        ...


class HttpModelProvider(ModelProvider):
    """通过 HTTP 调用各模型 API 的实现
    
    内部流程：
      1. 从 platform model_registry 查找 model_id 对应的 provider + API key
      2. 根据 provider 选择对应的 SDK（openai / anthropic / deepl）
      3. 调用 API，获取结果
      4. 图片类结果保存到 sandbox 文件系统，返回路径
    """

    def __init__(self, platform_client, sandbox_provider):
        self.platform_client = platform_client  # 查询 model_registry
        self.sandbox_provider = sandbox_provider  # 保存图片到容器

    async def generate_image(self, prompt: str, style: str = "diagram", size: str = "1024x1024") -> str:
        # 1. 查找图像生成模型（capability="image_generation"）
        model = await self.platform_client.get_model_by_capability("image_generation")
        # 2. 调用对应 API（如 OpenAI DALL-E）
        image_bytes = await self._call_image_api(model, prompt, size)
        # 3. 保存到 sandbox
        path = f"generated/{uuid4()}.png"
        await self.sandbox_provider.write_file_bytes(path, image_bytes)
        return path

    # ... 其他方法类似
```

# quantalithos-flow 概要设计

> 流程编排引擎 — BPMN 2.0 流程编排、门禁控制、任务调度、消息路由（依赖 quantalithos-core）

---

## 一、项目定位

### 1.1 核心职责

quantalithos-flow 是整个平台的**编排中枢（daemon）**，负责宏观流程控制：

- **阶段状态机**：管理项目在 6 个阶段之间的流转、门禁、回退
- **工作流模板**：定义阶段内部的 step 顺序、触发条件、完成判定
- **任务状态机**：驱动任务卡在 created→assigned→in_development→...→completed 之间流转
- **step 调度**：决定当前节点由哪个 Agent 执行，通过 BPMNEngine + 策略注册表驱动
- **消息路由**：控制消息分发、@提及路由、参与度控制
- **门禁控制**：硬门禁（用户必须确认）、软门禁（默认自动通过）
- **交接包管理**：阶段间的正式交接对象（entry_packet → exit_packet）

### 1.2 设计目标与非目标

| 设计目标 | 说明 |
|---------|------|
| daemon 长驻进程 | flow 是一个持续运行的服务，监听事件并驱动流程 |
| 事件驱动 | 以事件编排为核心，当前通过 platform `/api/events` 轮询兼容接入 |
| BPMN 对齐 | 所有流程用 ProcessDefinition 描述，BPMNEngine + Token 驱动 |
| 门禁控制 | 关键节点暂停等待人类确认，硬门禁不可跳过 |
| 持久执行 | 每步持久化状态，崩溃后可从断点恢复 |

| 非目标 | 说明 |
|--------|------|
| 不做 Agent 执行 | "怎么做"由 runtime 负责，flow 只负责"谁做什么" |
| 不做数据存储 | 数据在 platform，flow 通过 API 读写 |
| 不做任务调度 | 依赖图和波次调度由 platform TaskScheduler 负责 |
| 不做消息渲染 | 消息展示由 chat 负责 |

### 1.3 与 quantalithos-core 的关系

flow 依赖 core（建议本地依赖 `quantalithos-core @ file:///home/aris/WorkProject/quantalithos-core/python`）获取：

- **BPMN 引擎**：`BPMNEngine` + `StrategyRegistry` — flow 注册 `FlowTaskStrategy` / `FlowUserTaskStrategy` / `FlowAdHocStrategy`
- **BPMN 节点模型**：`StartEvent`、`EndEvent`、`AbstractTask`、`UserTask`、`AdHocSubProcess`、`ExclusiveGateway`、`ParallelGateway`
- **通信协议**：`FlowMessage`、`NodeResult`、`FlowExecutionContext` 及各类 payload 模型
- **数据模型**：`ProcessDefinition`、`ProcessInstance`、`RoleDefinition`、`SharedRule`、`WorkItem`


### 1.4 与 quantalithos-runtime 的分工

| 维度 | flow | runtime |
|------|------|---------|
| 职责 | "谁做什么、什么顺序" | "怎么做" |
| 粒度 | 项目级 / 阶段级 | Agent 级 |
| 驱动方式 | BPMNEngine + FlowTaskStrategy 等 | BPMNEngine + AgentTaskStrategy 等 |
| 消息 | 构造 FlowMessage(node_execute) | 接收并执行 |
| 门禁 | FlowUserTaskStrategy 创建 GateCard | 不参与 |
| 状态 | core `ProcessInstance` + flow 辅助索引 | core `ProcessInstance`（执行侧） |

## 二、核心概念

| 概念 | 说明 |
|------|------|
| ProcessDefinition | BPMN 流程定义（YAML → 节点 + 边），三种 scope：pipeline / stage / agent |
| ProcessInstance | 运行时流程实例，统一复用 quantalithos-core 模型 |
| Token | 执行指针，由 BPMNEngine 管理（分裂/合并/推进） |
| FlowMessage | flow → runtime 的统一消息（type=node_execute / chat_message / agent_create 等） |
| NodeResult | runtime → flow 的执行结果（completed / blocked / failed） |
| GateCard | 门禁审批卡片，发给 chat 展示，等待用户操作 |
| FlowState | daemon 快照；嵌入 core `ProcessInstance`，并补充门禁、消息、边历史等编排元数据 |

## 五、flow 需要实现的 BPMN 元素清单

> 完整的落地决策表见 `docs/design/流程图模型与节点原语设计.md` 第十章。

### Phase 1（10 种）

| BPMN 元素 | flow 的处理方式 |
|-----------|---------------|
| StartEvent (none) | 不注册策略，BPMNEngine 自动跳过 |
| EndEvent (none) | FlowEndEventStrategy → 流程完成，推进阶段 |
| EndEvent (terminate) | EndEvent.is_terminate() → BPMNEngine 终止所有 token |
| Abstract Task | FlowTaskStrategy → 构造 FlowMessage(node_execute) 发给 runtime |
| User Task | FlowUserTaskStrategy → 创建 GateCard，等待用户操作 |
| Ad-Hoc SubProcess | FlowAdHocStrategy → 构造 FlowMessage(node_execute) 发给 runtime |
| Exclusive Gateway (XOR) | 不注册策略，ExclusiveGateway.evaluate() 对象自治 |
| Sequence Flow | BPMNEngine.advance_token → 沿边推进 |
| Conditional Flow | ExclusiveGateway.evaluate() 评估 edge.condition |
| Default Flow | ExclusiveGateway.default_route 兜底 |

### Phase 2 新增（4 种）

| BPMN 元素 | flow 的处理方式 |
|-----------|---------------|
| Parallel Gateway (AND) | Token 分裂/合并（BPMNEngine 处理） |
| Call Activity | 启动子流程 ProcessInstance |
| Boundary Event (timer) | 超时后走超时分支 |
| Boundary Event (error) | NodeResult(failed) 后走错误分支 |

## 六、错误处理策略

### 6.1 错误分类与恢复矩阵

| 错误类别 | 触发场景 | 恢复策略 | 说明 |
|---------|---------|---------|------|
| NodeResult(failed) | Agent 执行失败（LLM 错误 / 工具错误） | 重试 2 次 → 走 on_fail 边 → 无 on_fail 则通知用户 | flow 的核心错误处理 |
| NodeResult(blocked) | Agent 被阻塞（等待外部输入 / 权限不足） | 通知 TL 介入 | 不自动重试 |
| runtime 不可达 | HTTP 连接失败 | 指数退避重试 3 次 → 暂停流程 → 通知用户 | 基础设施问题 |
| platform 不可达 | HTTP 连接失败 | 指数退避重试 3 次 → 暂停流程 | 基础设施问题 |
| ProcessDefinition 加载失败 | platform 返回 404 / 格式错误 | 不重试，流程终止 | 配置错误 |
| 门禁超时 | 用户 7 天未操作 | Phase 1 不处理 / Phase 2 自动通过或通知 | 可配置 |
| Token 卡死 | Gateway 无匹配 + 无 default | core Fail Fast → flow 收到异常 → 通知用户 | 配置错误 |
| daemon 崩溃 | 进程异常退出 | 从 snapshot 恢复（current.yaml） | 持久执行 |

### 6.2 重试与回退机制

```
Agent 执行失败时的处理流程：

  NodeResult(failed) 到达
       │
       ├── 检查重试次数 < max_retries (2)
       │   ├── 是 → 重新发 FlowMessage → Agent 重新执行
       │   └── 否 → 检查 on_fail 边
       │            ├── 有 → 走 on_fail 分支（回退到指定节点）
       │            └── 无 → 流程卡住 → 通知用户 → 等待人工干预
```

### 6.3 设计原则

- **flow 不做 LLM 级重试**：那是 runtime 的事（已重试 3 次后才上报 failed）
- **flow 做节点级重试**：同一个节点重新执行（最多 2 次）
- **不可恢复时通知用户**：不静默卡死，在 chat 中显示错误信息
- **daemon 崩溃可恢复**：每步持久化，重启后从断点继续

## 七、性能边界与扩展点

### 7.1 性能边界

| 维度 | Phase 1 设计约束 | 说明 |
|------|-----------------|------|
| 并发项目数 | 单 flow 进程最多 ~10 个项目同时运行 | 每个项目一个 ProcessInstance |
| 并发 Token | 单项目最多 ~10 个 active Token（Phase 2 并行） | Phase 1 只有 1 个 |
| 事件处理延迟 | platform 事件到 flow 处理 < 1s | 当前默认 `event_poll_interval_ms=1000`，由轮询周期主导 |
| 持久化频率 | 每步写入 current.yaml | 文件 I/O，~1ms |
| FlowMessage 发送 | HTTP POST 到 runtime，~50ms | 网络延迟 |

### 7.2 扩展点

| 扩展点 | 机制 | 说明 |
|--------|------|------|
| 新增节点策略 | 实现 NodeStrategy + registry.register() | 不改 FlowEngine |
| 新增门禁类型 | GateController 扩展 | 不改流程引擎 |
| 新增事件监听 | PlatformListener 加新事件处理 | 不改已有事件 |
| 持久化策略 | 替换 StatePersister 实现（文件 → Event Sourcing） | 不改引擎 |
| 事件总线 | 替换 broadcast 实现（进程内 → Redis Pub/Sub） | 不改业务逻辑 |

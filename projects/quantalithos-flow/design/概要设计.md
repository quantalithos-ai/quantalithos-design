# quantalithos-flow 概要设计

> 流程编排引擎 — 阶段状态机、工作流模板、门禁控制、任务调度、消息路由

---

## 一、项目定位

### 1.1 核心职责

quantalithos-flow 是整个平台的**编排中枢（daemon）**，负责宏观流程控制：

- **阶段状态机**：管理项目在 6 个阶段之间的流转、门禁、回退
- **工作流模板**：定义阶段内部的 step 顺序、触发条件、完成判定
- **任务状态机**：驱动任务卡在 created→assigned→in_development→...→completed 之间流转
- **step 调度**：决定当前 step 由哪个 Agent 执行，向 quantalithos-runtime 下发 StepAssignment
- **消息路由**：控制消息分发、@提及路由、参与度控制
- **门禁控制**：硬门禁（用户必须确认）、软门禁（默认自动通过）、done_when / output_schema 校验
- **交接包管理**：阶段间的正式交接对象（entry_packet → exit_packet）

### 1.2 在整体架构中的位置

```
quantalithos-chat (聊天前端)
      │
      │ HTTP/WebSocket
      ▼
quantalithos-gate (API 网关)
      │
      ├──────────────────┬──────────────────┐
      │                  │                  │
      ▼                  ▼                  ▼
╔═══════════════╗  quantalithos-vault  quantalithos-runtime
║ quantalithos- ║  (产物服务)          (Agent 运行时)
║ flow (daemon) ║        │                  │
╚═══════╤═══════╝        │                  │
        │                │                  │
        └────────────────┴──────────────────┘
                         │
                ┌────────┴────────┐
                │                 │
                ▼                 ▼
         quantalithos-sync  quantalithos-infra
         (工作区同步)        (基础设施)
```

### 1.3 与 quantalithos-runtime 的分工

| 职责 | quantalithos-flow | quantalithos-runtime |
|------|-------------------|----------------------|
| 阶段流转（6 阶段） | ✅ 控制 | 不参与 |
| 工作流 step 推进 | ✅ 调度 | 接收 StepAssignment 执行 |
| 任务状态流转 | ✅ 驱动 | 只读消费 + 事件上报 |
| Agent 实例化/销毁 | 发出指令 | ✅ 执行 |
| Agent think→act 循环 | 不参与 | ✅ 执行 |
| 消息路由与参与度控制 | ✅ 控制 | 不参与 |
| 工具权限（step 级动态） | ✅ 下发 allowed_tools | 校验（取交集） |
| 门禁与审批 | ✅ 控制 | 不参与 |
| LLM 调用 | 不参与 | ✅ 执行 |

一句话：**flow 决定"谁在什么时候做什么"，runtime 负责"怎么做"。**

## 二、核心概念

### 2.1 三层编排模型

```
第一层：阶段流转    — 项目现在在哪个阶段？    → 阶段状态机控制
第二层：阶段内编排  — 这个阶段内谁先做谁后做？ → 工作流模板驱动
第三层：即时交互    — 两个 Agent 之间怎么对话？ → 消息路由控制
```

### 2.2 核心对象关系

```
Project
  └── StageMachine（6 阶段状态机）
        └── WorkflowInstance（当前阶段的工作流实例）
              └── Step（当前正在执行的步骤）
                    └── StepAssignment（下发给 Agent 的执行指令）
```

## 三、阶段状态机

### 3.1 阶段定义与 Assistant 的关系

Assistant 的启动流程（7 步状态机）在私聊空间执行，由 runtime 驱动，不属于 flow。flow 实例在 Assistant 完成启动、创建项目群聊后才创建。

```
Assistant 启动流程（runtime 管理，私聊空间）
        │
        │ 产出 assistant_startup_handoff
        │ 创建项目群聊 + Tech Lead
        │
        ▼
flow 实例创建 ← 从这里开始才是 flow 的管辖范围
        │
        ▼
stage_0：Tech Lead 目标校准（flow 的第一个阶段）
        │
        ▼
stage_1 → stage_2 → stage_3 → stage_4 → stage_5 → completed
```

六阶段定义：

```
阶段 0  目标校准（Tech Lead 接手，校准目标并路由）
阶段 1  需求理解（硬门禁：用户确认 PRD）
阶段 2  方案拆解与实施准备（软门禁）
阶段 3  迭代开发与测试（任务级流水线）
阶段 4  验收、发布准备与最终确认（硬门禁）
阶段 5  发布执行、发布后观察与回退控制
```

### 3.2 daemon 启动流程

```
Assistant 完成启动，创建项目群聊
                │
                ▼
┌─────────────────────────────────┐
│         daemon 启动              │
│                                 │
│  1. 读取 manifest.yaml          │
│  2. 检查 snapshots/workflow/    │
│     ├── 有快照 → 断点续跑       │
│     └── 无快照 → 新项目         │
│  3. 初始化阶段 = stage_0        │
│  4. 加载 stage_0 工作流模板     │
│  5. 进入事件循环                │
└─────────────────────────────────┘
                │
                ▼
        ┌──────────────┐
        │   stage_0    │
        │  目标校准     │
        └──────────────┘
```

### 3.3 事件驱动机制

阶段流转不是定时轮询，而是事件驱动。触发阶段流转的事件来源：

| 事件来源 | 示例 |
|----------|------|
| StepEvent（runtime 上报） | Agent 完成了最后一个 step |
| 用户操作（chat 转发） | 用户点击"确认 PRD"、"批准发布" |
| 系统判断（flow 内部） | 检测到所有前置条件满足 |

阶段流转的完整判断流程：

```
收到事件
    │
    ▼
┌───────────────────────┐
│  检查 exit_conditions │
│  是否全部满足          │
└───────────┬───────────┘
            │
     ┌──────┴──────┐
     │             │
  未满足         全部满足
     │             │
     ▼             ▼
  忽略，      ┌───────────────────────┐
  继续等待    │  检查 gate_type       │
              └───────────┬───────────┘
                          │
               ┌──────────┼──────────┐
               │          │          │
            hard        soft       none
               │          │          │
               ▼          ▼          ▼
          发送审批    检查项目配置  直接通过
          卡片给用户  是否要求确认      │
               │     ┌────┴────┐      │
               │   要求     不要求     │
               │     │        │       │
               ▼     ▼        ▼       │
          等待用户  同hard   自动通过   │
          确认                  │      │
               │               │      │
               └───────┬───────┘      │
                       │              │
                       ▼              │
              ┌────────────────┐      │
              │  门禁通过       │ <────┘
              │                │
              │  1. 保存快照   │
              │  2. 更新阶段   │
              │  3. 写 current │
              │  4. 加载模板   │
              │  5. 触发 step  │
              └────────────────┘
```

### 3.4 阶段状态机定义

```python
class ProjectStage(str, Enum):
    STAGE_0_ALIGNMENT = "stage_0"     # Tech Lead 目标校准
    STAGE_1_REQUIREMENT = "stage_1"
    STAGE_2_DESIGN = "stage_2"
    STAGE_3_DEVELOPMENT = "stage_3"
    STAGE_4_ACCEPTANCE = "stage_4"
    STAGE_5_RELEASE = "stage_5"
    COMPLETED = "completed"
    SUSPENDED = "suspended"


class StageTransition(BaseModel):
    """阶段流转规则"""
    from_stage: ProjectStage
    to_stage: ProjectStage
    gate_type: str                    # "hard" | "soft" | "none"
    exit_conditions: List[str]        # 离开当前阶段的前置条件
    entry_requirements: List[str]     # 进入下一阶段的必要产物/状态
    gate_checker: Optional[str]       # 门禁校验逻辑标识
```

### 3.5 各阶段 exit_conditions 与 entry_requirements

以博客项目为例说明每个阶段的具体条件：

**stage_0 → stage_1（目标校准 → 需求理解）：**

```yaml
exit_conditions:
  - assistant_startup_handoff.handoff_status == "accepted"
  - goal_alignment_brief.alignment_status == "passed"
  - goal_alignment_brief.recommended_route == "stage1_requirement_analysis"
gate_type: none
entry_requirements:
  - tech_lead 已实例化
  - 项目群聊已创建
```

```
例：Tech Lead 读完交接包，确认"这是一个新项目，需要完整需求分析"
    → goal_alignment_brief.status = "passed"
    → daemon 检查 exit_conditions 全部满足
    → gate_type = none，直接通过
    → 进入 stage_1
```

**stage_1 → stage_2（需求理解 → 设计与规划）：**

```yaml
exit_conditions:
  - prd 文档已生成（docs/prd/ 下存在文件）
  - 需求评审已完成（全员审查）
  - 用户已确认 PRD
gate_type: hard                      # 必须用户确认
entry_requirements:
  - prd_final 存在于 docs/prd/
```

```
例：TL 整理完 PRD，全员评审通过
    → daemon 检查 exit_conditions
    → ✅ PRD 已生成
    → ✅ 评审已完成
    → ❌ 用户未确认
    → 向用户发送审批卡片
    → 用户点击 [确认]
    → 重新检查：全部满足
    → 进入 stage_2
```

**stage_2 → stage_3（设计与规划 → 迭代开发）：**

```yaml
exit_conditions:
  - 设计文档集已完成（UI设计/接口文档/技术方案）
  - 任务列表已拆解（至少 1 个任务卡 status == "created"）
  - 汇总评审已完成
gate_type: soft                      # 默认自动通过
entry_requirements:
  - 至少 1 个任务卡 status == "created"
  - CI/CD 已就绪（DevOps 并行产出）
  - 分支策略已建立（main → dev → task/*）
```

**stage_3 → stage_4（迭代开发 → 验收）：**

```yaml
exit_conditions:
  - 所有任务卡 status == "completed"
  - 集成测试通过
gate_type: none                      # 系统自动判断
entry_requirements:
  - 集成测试报告存在
  - dev 分支构建通过
```

```
例：最后一个任务 TASK-004 测试通过
    → runtime 上报 StepEvent: completed
    → daemon 检查：所有任务都 completed？是
    → daemon 触发集成测试
    → 集成测试通过
    → exit_conditions 全部满足
    → gate_type = none，直接通过
    → 进入 stage_4
```

**stage_4 → stage_5（验收 → 发布）：**

```yaml
exit_conditions:
  - 用户验收通过
  - 分支收尾完成（dev → main 合并）
gate_type: hard                      # 必须用户最终确认
entry_requirements:
  - main 分支构建通过
  - release_readiness_report 存在
```

**stage_5 → completed：**

```yaml
exit_conditions:
  - 发布执行完成
  - 观察窗通过（无异常）
  - release_outcome_report 存在
gate_type: none
```

### 3.6 回退规则

```
正常流转：
stage_0 → stage_1 → stage_2 → stage_3 → stage_4 → stage_5 → completed

允许的回退：
stage_4 ──→ stage_3    用户提修改意见（创建新任务卡）
stage_4 ──→ stage_1    需求变更（PRD 需重新确认）
stage_5 ──→ stage_3    发布失败（创建修复任务卡，走 bugfix 流程）
```

```python
class AllowedRollback(BaseModel):
    """允许的回退规则"""
    from_stage: ProjectStage
    to_stage: ProjectStage
    trigger: str                      # 触发回退的事件类型
    action: str                       # 回退时执行的动作
```

回退时的处理流程：

```
用户在 stage_4 说："标签筛选页面加载太慢，需要优化"
    │
    ▼
┌───────────────────────────────────┐
│  daemon 收到 request_changes      │
│                                   │
│  1. 保存 stage_4 快照（审计用）   │
│  2. 检查回退规则：                │
│     stage_4 → stage_3 ✅ 允许     │
│  3. 创建新任务卡：                │
│     TASK-005: 优化标签筛选性能    │
│     type: fix                     │
│     status: created               │
│  4. 状态 → stage_3               │
│  5. 加载 iterative_development   │
│  6. 新任务进入开发流水线          │
└───────────────────────────────────┘
```

注意：回退到 stage_3 时，已完成的任务不会被重置。只是创建新任务卡，走正常的开发流水线。

### 3.7 阶段状态持久化

daemon 崩溃恢复后需要知道当前在哪个阶段。两层保障：

**实时状态文件：**

```yaml
# snapshots/workflow/current.yaml
project_id: blog-project
current_stage: stage_3
entered_at: 2026-04-20T10:00:00Z
workflow_id: iterative_development
current_step: code_review
active_assignment_id: assign-00042
```

每次阶段变更或 step 推进时更新。daemon 重启时先读此文件恢复状态。

**门禁历史（审计用）：**

```yaml
# snapshots/workflow/gate_history.yaml
gates:
  - stage: stage_0
    gate_type: none
    passed_at: 2026-04-18T09:00:00Z
    
  - stage: stage_1
    gate_type: hard
    passed_at: 2026-04-18T14:00:00Z
    approved_by: user
    artifact: docs/prd/blog-prd-v1.md
    
  - stage: stage_2
    gate_type: soft
    passed_at: 2026-04-19T10:00:00Z
    auto_approved: true
```

门禁历史只追加不修改，用于审计和回溯。

## 四、工作流模板

### 4.1 两层工作流模型

工作流模板分为两层，使用同一套格式，区别在于作用域和驱动者：

```
┌─────────────────────────────────────────────────────────────────┐
│  项目级工作流（flow 驱动，多 Agent 协作）                        │
│                                                                 │
│  iterative_development.yaml                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐                  │
│  │implement │───>│code_review│───>│ testing  │                  │
│  │developer │    │tech_lead  │    │ tester   │                  │
│  │          │    │          │    │          │                  │
│  │ workflow:│    │ workflow:│    │ workflow:│                  │
│  │ tdd_wf   │    │ review_wf│    │ null     │                  │
│  └────┬─────┘    └──────────┘    └──────────┘                  │
│       │                                                         │
│       │ 引用 Agent 级工作流                                      │
│       ▼                                                         │
│  ┌─────────────────────────────────────────────────────┐       │
│  │  Agent 级工作流（runtime 驱动，单 Agent 内部）        │       │
│  │                                                     │       │
│  │  tdd_workflow.yaml                                  │       │
│  │  ┌─────────┐  ┌──────────┐  ┌─────────┐           │       │
│  │  │read_task│─>│write_test│─>│run_red  │           │       │
│  │  └─────────┘  └──────────┘  └────┬────┘           │       │
│  │                                   │                │       │
│  │  ┌──────────┐  ┌──────────┐  ┌───▼─────┐         │       │
│  │  │ submit   │<─│ verify   │<─│write_code│         │       │
│  │  └──────────┘  └──────────┘  └─────────┘         │       │
│  └─────────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────────┘
```

| | 项目级工作流 | Agent 级工作流 |
|---|-------------|---------------|
| 驱动者 | flow (daemon) | runtime |
| 参与者 | 多个 Agent | 单个 Agent |
| step 的 actor | 不同角色 | 固定为当前 Agent（self） |
| 嵌套 | 可以引用 Agent 级工作流 | 不再嵌套（叶子节点） |
| 安装方式 | 项目配置 / 阶段关联 | 角色定义的 workflows 字段 |

### 4.2 模板格式规范

项目级和 Agent 级使用同一套字段格式：

```yaml
# 模板公共字段
workflow_id: string               # 唯一标识
name: string                      # 显示名称
scope: "project" | "agent"        # 项目级 or Agent 级
stage: string                     # 关联阶段（项目级必填，Agent 级可选）
description: string

steps:
  - id: string
    name: string
    actor: string                 # 项目级：角色类型；Agent 级：固定为 "self"
    trigger: string               # 触发条件
    input: [string]               # 输入引用
    output: [string]              # 输出产物
    allowed_tools: [string]       # step 级工具权限
    workflow: string | null       # 引用 Agent 级工作流（项目级 step 可选）
    done_when: [string]           # 完成条件
    next: string | null           # 下一个 step
    on_fail: string               # 失败后跳转
```

### 4.3 项目级模板示例

**阶段 3 迭代开发（引用 Agent 级工作流）：**

```yaml
# workflow_templates/project/iterative_development.yaml

workflow_id: iterative_development
name: "迭代开发与测试"
scope: project
stage: stage_3
description: "单个任务的开发流水线：编码→审查→测试"

steps:
  - id: implement
    name: "编码实现"
    actor: developer
    trigger: task_assigned
    input: [task_card]
    output: [code_patch, verification_report]
    allowed_tools: [file_read, file_write, code_execute, git_commit]
    workflow: tdd_workflow          # ← 引用 Agent 级工作流
    done_when:
      - tests_passed
      - deliverable_submitted
    next: code_review
    on_fail: implement

  - id: code_review
    name: "代码审查"
    actor: tech_lead
    trigger: implement.completed
    input: [code_patch]
    output: [review_result]
    allowed_tools: [file_read, git_diff]
    workflow: review_workflow       # ← 引用 Agent 级工作流
    done_when:
      - review_submitted
    next: testing
    on_fail: implement

  - id: testing
    name: "任务测试"
    actor: tester
    trigger: code_review.completed
    input: [code_patch, review_result]
    output: [test_report]
    allowed_tools: [file_read, code_execute]
    workflow: null                  # ← 无子流程，自由执行
    done_when:
      - all_tests_passed
    next: null
    on_fail: implement
```

### 4.4 Agent 级模板示例

**TDD 工作流（安装在开发角色上）：**

```yaml
# workflow_templates/agent/tdd_workflow.yaml

workflow_id: tdd_workflow
name: "TDD 红-绿-重构循环"
scope: agent
description: "测试驱动开发流程"

steps:
  - id: read_task
    name: "读取工单"
    actor: self
    done_when: [task_understood]
    next: write_failing_test

  - id: write_failing_test
    name: "写失败测试"
    actor: self
    done_when: [test_file_created]
    next: run_test_red

  - id: run_test_red
    name: "确认测试失败"
    actor: self
    done_when: [test_failed]
    next: write_code
    on_fail: write_failing_test

  - id: write_code
    name: "编写实现代码"
    actor: self
    done_when: [code_written]
    next: run_test_green

  - id: run_test_green
    name: "确认测试通过"
    actor: self
    done_when: [test_passed]
    next: refactor
    on_fail: write_code

  - id: refactor
    name: "重构"
    actor: self
    done_when: [test_still_passed]
    next: verify

  - id: verify
    name: "运行 verification_command"
    actor: self
    done_when: [verification_passed]
    next: submit
    on_fail: write_code

  - id: submit
    name: "提交交付物"
    actor: self
    done_when: [deliverable_submitted]
    next: null
```

**Assistant 启动流程（安装在 Assistant 角色上）：**

```yaml

steps:
  - id: identify_intent

    done_when: [intent_identified]
    next: collect_context

  - id: collect_context
    name: "收集信息"
    actor: self
    action: "补齐项目名称、类型、目标、规模等最小必要信息"
    done_when: [context_collected]

  - id: create_workspace
```

### 5.1 flow 下发给 runtime 的执行指令

```python
class StepAssignment(BaseModel):
```

### 7.1 职责

- 这条消息该不该转发给某个 Agent
- @提及如何路由
- 群聊讨论时谁能发言

### 7.2 参与度控制

```python
class ParticipationMode(str, Enum):
    MENTION_ONLY = "mention_only"     # 被 @才能回复
    FREE = "free"                     # 自由发言
    ROUND_ROBIN = "round_robin"       # 轮流发言
    MUTED = "muted"                   # 静默
```

参与度模式可以在 step 级别覆盖：

```yaml
# 头脑风暴 step：全员自由发言
- id: brainstorm
  actor: all
  participation_mode: free

- id: implement
  actor: developer
  participation_mode: mention_only
```

## 八、门禁系统

### 8.1 门禁类型

| 类型 | 说明 | 示例 |
|------|------|------|
| hard | 必须用户操作确认 | 阶段 1→2 用户确认 PRD，阶段 4→5 用户最终确认 |
| soft | 默认自动通过，可配置为需要确认 | 阶段 2→3 设计评审 |
| done_when | 系统自动校验完成条件 | tests_passed, deliverable_submitted |
| output_schema | 系统校验输出格式 | DELIVERABLE 必须包含 summary + changed_files |

```
         ▼          ▼          ▼
      记录门禁   回退到      项目状态
      通过历史   stage_1     → suspended
      进入       相关 step
      stage_2
```

### 9.1 flow 负责的快照

flow 负责项目级编排状态的快照，存储在 `snapshots/workflow/`：

**实时状态（current.yaml）：**

```yaml
# snapshots/workflow/current.yaml
project_id: blog-project
current_stage: stage_3
entered_at: 2026-04-20T10:00:00Z
workflow_id: iterative_development
current_step: code_review
active_assignment_id: assign-00042
active_agents: [tech-lead, backend-dev-1, frontend-dev-1]
```

**阶段快照（阶段切换时生成）：**

```yaml
# snapshots/workflow/stage3_20260420.yaml
project_id: blog-project

current_step: code_review
```

## 十一、与其他子项目的接口

| 对接方 | 接口方式 | 说明 |
|--------|----------|------|
| quantalithos-runtime | StepAssignment / StepEvent | flow 下发执行指令，runtime 上报结果 |
| quantalithos-chat | WebSocket / API | 门禁审批卡片、状态更新推送 |
| quantalithos-vault | API | 读写产物（PRD、设计文档、测试报告） |
| quantalithos-sync | CLI 调用 | 项目启动时 restore，变更时 push |
| 研发协作平台 | API | 任务 CRUD、需求查询、BUG 管理 |

# quantalithos-flow 概要设计

> 流程编排引擎 — 阶段状态机、工作流模板、门禁控制、任务调度、消息路由

---

## 一、项目定位

### 1.1 核心职责

quantalithos-flow 是整个平台的**编排中枢（daemon）**，负责宏观流程控制：

- **阶段状态机**：管理项目在 6 个阶段之间的流转、门禁、回退
- **工作流模板**：定义阶段内部的 step 顺序、触发条件、完成判定
- **任务状态机**：驱动任务卡在 created→assigned→in_development→...→completed 之间流转
- **step 调度**：决定当前 step 由哪个 Agent 执行，向 quantalithos-runtime 下发 StepAssignment
- **消息路由**：控制消息分发、@提及路由、参与度控制
- **门禁控制**：硬门禁（用户必须确认）、软门禁（默认自动通过）、done_when / output_schema 校验
- **交接包管理**：阶段间的正式交接对象（entry_packet → exit_packet）

### 1.2 在整体架构中的位置

```
quantalithos-chat (聊天前端)
      │
      │ HTTP/WebSocket
      ▼
quantalithos-gate (API 网关)
      │
      ├──────────────────┬──────────────────┐
      │                  │                  │
      ▼                  ▼                  ▼
╔═══════════════╗  quantalithos-vault  quantalithos-runtime
║ quantalithos- ║  (产物服务)          (Agent 运行时)
║ flow (daemon) ║        │                  │
╚═══════╤═══════╝        │                  │
        │                │                  │
        └────────────────┴──────────────────┘
                         │
                ┌────────┴────────┐
                │                 │
                ▼                 ▼
         quantalithos-sync  quantalithos-infra
         (工作区同步)        (基础设施)
```

### 1.3 与 quantalithos-runtime 的分工

| 职责 | quantalithos-flow | quantalithos-runtime |
|------|-------------------|----------------------|
| 阶段流转（6 阶段） | ✅ 控制 | 不参与 |
| 工作流 step 推进 | ✅ 调度 | 接收 StepAssignment 执行 |
| 任务状态流转 | ✅ 驱动 | 只读消费 + 事件上报 |
| Agent 实例化/销毁 | 发出指令 | ✅ 执行 |
| Agent think→act 循环 | 不参与 | ✅ 执行 |
| 消息路由与参与度控制 | ✅ 控制 | 不参与 |
| 工具权限（step 级动态） | ✅ 下发 allowed_tools | 校验（取交集） |
| 门禁与审批 | ✅ 控制 | 不参与 |
| LLM 调用 | 不参与 | ✅ 执行 |

一句话：**flow 决定"谁在什么时候做什么"，runtime 负责"怎么做"。**

## 二、核心概念

### 2.1 三层编排模型

```
第一层：阶段流转    — 项目现在在哪个阶段？    → 阶段状态机控制
第二层：阶段内编排  — 这个阶段内谁先做谁后做？ → 工作流模板驱动
第三层：即时交互    — 两个 Agent 之间怎么对话？ → 消息路由控制
```

### 2.2 核心对象关系

```
Project
  └── StageMachine（6 阶段状态机）
        └── WorkflowInstance（当前阶段的工作流实例）
              └── Step（当前正在执行的步骤）
                    └── StepAssignment（下发给 Agent 的执行指令）
```

## 三、阶段状态机

### 3.1 两层分离：Pipeline Template + Workflow Template

阶段和工作流是两层独立概念，参考禅道、Jira、CodeArts 等主流产品的设计模式：

```
┌─────────────────────────────────────────────────────────────┐
│  Pipeline Template（阶段模板）                               │
│  定义项目经过哪些阶段、什么门禁、什么顺序                     │
│  面向：管理者和用户（宏观进度）                               │
│                                                             │
│  standard.yaml:                                             │
│    alignment → requirement → design → dev → accept → release│
│                                                             │
│  hotfix.yaml:                                               │
│    fix → verify → release                                   │
│                                                             │
│  enhancement.yaml:                                          │
│    requirement → design → dev → accept → release            │
└──────────────────────┬──────────────────────────────────────┘
                       │ 每个阶段引用
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Workflow Template（工作流模板）                              │
│  定义阶段内部怎么一步步做                                    │
│  面向：执行者 / Agent（微观执行）                             │
│                                                             │
│  requirement_analysis.yaml:                                 │
│    collect → brainstorm → write_prd → review                │
│                                                             │
│  iterative_development.yaml:                                │
│    implement → code_review → testing                        │
│                                                             │
│  bugfix.yaml:                                               │
│    reproduce → locate → fix → verify                        │
└─────────────────────────────────────────────────────────────┘
```

两层分离的好处：
- 同一个工作流模板可以被不同阶段模板复用（如 acceptance_review 同时被 standard 和 hotfix 引用）
- 裁剪阶段不影响工作流模板本身
- 前端直接从阶段模板渲染进度条，不需要遍历工作流链

> **设计决策记录：移除 ProjectStage 枚举和 StageTransition**
>
> 原设计中阶段是硬编码的 Python 枚举（STAGE_0_ALIGNMENT、STAGE_1_REQUIREMENT 等），
> 阶段流转通过 StageTransition 数据结构定义。经讨论后改为配置驱动的 Pipeline Template，原因：
>
> - 硬编码枚举无法支持不同项目类型使用不同阶段（hotfix 只需 3 个阶段，standard 需要 6 个）
> - 无法加减阶段（如某公司想加"安全评审"阶段）
> - 与"流程模板可配置、可裁剪"的框架设计原则矛盾
> - 每次改阶段都要改代码，不符合配置驱动架构

### 3.2 阶段定义与 Assistant 的关系

Assistant 的启动流程在私聊空间执行，由 runtime 驱动 Agent 级工作流，不属于 flow。flow 实例在 Assistant 完成启动、创建项目群聊后才创建。

```
Assistant 启动流程（runtime 管理，私聊空间）
        │
        │ 产出 assistant_startup_handoff
        │ 创建项目群聊 + Tech Lead
        │
        ▼
flow 实例创建 ← 从这里开始才是 flow 的管辖范围
        │
        │ 加载 Pipeline Template（如 standard.yaml）
        │
        ▼
alignment → requirement → design → development → acceptance → release
                                                                  │
                                                                  ▼
                                                              completed
```

### 3.4 数据结构

```python
class GateType(str, Enum):
    HARD = "hard"                     # 必须用户确认
    SOFT = "soft"                     # 默认自动通过，可配置为需要确认
    NONE = "none"                     # 直接通过


class StageDefinition(BaseModel):
    """阶段定义 — 从 Pipeline Template 加载"""
    id: str                           # 阶段标识（如 "requirement"）
    name: str                         # 显示名称（如 "需求理解"）
    workflow_id: str                  # 关联的工作流模板
    gate_type: GateType              # 进入下一阶段前的门禁类型


class RollbackRule(BaseModel):
    """回退规则"""
    from_stage: str                   # 从哪个阶段
    to_stage: str                     # 回退到哪个阶段
    trigger: str                      # 触发回退的事件类型
    action: str                       # 回退时执行的动作描述


class PipelineTemplate(BaseModel):
    """阶段模板 — 定义项目经过哪些阶段"""
    pipeline_id: str
    name: str
    description: str
    stages: List[StageDefinition]
    rollbacks: List[RollbackRule] = []


class PipelineInstance(BaseModel):
    """阶段实例 — 运行时状态"""
    instance_id: str
    pipeline_id: str                  # 来自哪个模板
    project_id: str
    current_stage_id: str             # 当前阶段
    stage_states: Dict[str, str]      # {stage_id: "pending"|"active"|"completed"}
    created_at: datetime
```

### 3.6 事件驱动与阶段流转

阶段流转不是定时轮询，而是事件驱动。触发阶段流转的事件来源：

| 事件来源 | 示例 |
|----------|------|
| StepEvent（runtime 上报） | Agent 完成了最后一个 step |
| 用户操作（chat 转发） | 用户点击"确认 PRD"、"批准发布" |

流转判断流程：

```
收到事件（StepEvent / 用户操作）
    │
    ▼
┌──────────────────────────┐
│  当前阶段工作流           │
│  所有 step completed?    │
└───────────┬──────────────┘
            │
     ┌──────┴──────┐
     │             │
    否            是
     │             │
     ▼             ▼
  忽略，      ┌───────────────────────┐
  继续等待    │  检查 gate_type       │
              └───────────┬───────────┘
                          │
               ┌──────────┼──────────┐
               │          │          │
            hard        soft       none
               │          │          │
               ▼          ▼          ▼
          发送审批    检查项目配置  直接通过
          卡片给用户  是否要求确认      │
               │     ┌────┴────┐      │
               │   要求     不要求     │
               │     │        │       │
               ▼     ▼        ▼       │
          等待用户  同hard   自动通过   │
          确认                  │      │
               │               │      │
               └───────┬───────┘      │
                       │              │
                       ▼              │
              ┌────────────────┐      │
              │  门禁通过       │ <────┘
              │                │
              │  1. 保存快照   │
              │  2. 更新阶段   │
              │  3. 写 current │
              │  4. 加载模板   │
              │  5. 触发 step  │
              └────────────────┘
```

以博客项目 requirement → design 为例：

```
requirement 阶段工作流定义了 4 个 step：
  collect → brainstorm → write_prd → review_prd

每个 step 有自己的 done_when：
  collect:     summary_submitted
  brainstorm:  notes_submitted
  write_prd:   prd_generated
  review_prd:  review_approved

当 review_prd completed 时：
    │
    ▼
  daemon 检查：requirement 阶段所有 step completed？
    │
    ├── 否 → 继续等待
    │
    └── 是 → 检查 gate_type
              │
              └── hard → 发送审批卡片给用户
                         │
                         ├── 用户确认 → 进入 design 阶段
                         └── 用户拒绝 → 回退（见 3.7）
```

不需要额外的 exit_conditions 检查 — "PRD 已生成"由 write_prd step 保证，"评审已完成"由 review_prd step 保证，"用户已确认"由 gate_type: hard 保证。

### 3.7 回退规则

回退规则定义在 Pipeline Template 的 `rollbacks` 字段中：

```
标准流程正常流转：
alignment → requirement → design → development → acceptance → release → completed

允许的回退（定义在 standard.yaml 的 rollbacks 中）：
acceptance ──→ development    用户提修改意见（创建新任务卡）
acceptance ──→ requirement    需求变更（PRD 需重新确认）
release    ──→ development    发布失败（创建修复任务卡，走 bugfix 流程）
```

回退时的处理流程：

```
用户在 acceptance 阶段说："标签筛选页面加载太慢，需要优化"
    │
    ▼
┌───────────────────────────────────┐
│  daemon 收到 request_changes      │
│                                   │
│  1. 保存 acceptance 快照（审计用）│
│  2. 检查回退规则：                │
│     acceptance → development      │
│     ✅ 在 rollbacks 中允许        │
│  3. 创建新任务卡：                │
│     TASK-005: 优化标签筛选性能    │
│     type: fix                     │
│     status: created               │
│  4. 状态 → development           │
│  5. 加载 iterative_development   │
│  6. 新任务进入开发流水线          │
└───────────────────────────────────┘
```

注意：回退到 development 时，已完成的任务不会被重置。只是创建新任务卡，走正常的开发流水线。

### 3.8 阶段状态持久化

daemon 崩溃恢复后需要知道当前在哪个阶段。两层保障：

**实时状态文件：**

```yaml
# snapshots/workflow/current.yaml
project_id: blog-project
pipeline_id: standard
current_stage_id: development
entered_at: 2026-04-20T10:00:00Z
workflow_id: iterative_development
current_step: code_review
active_assignment_id: assign-00042
```

每次阶段变更或 step 推进时更新。daemon 重启时先读此文件恢复状态。

**门禁历史（审计用）：**

```yaml
# snapshots/workflow/gate_history.yaml
gates:
  - stage_id: alignment
    gate_type: none
    passed_at: 2026-04-18T09:00:00Z
    
  - stage_id: requirement
    gate_type: hard
    passed_at: 2026-04-18T14:00:00Z
    approved_by: user
    artifact: docs/prd/blog-prd-v1.md
    
  - stage_id: design
    gate_type: soft
    passed_at: 2026-04-19T10:00:00Z
    auto_approved: true
```

门禁历史只追加不修改，用于审计和回溯。

## 四、工作流模板

### 4.1 两层工作流模型

工作流模板分为两层，使用同一套格式，区别在于作用域和驱动者：

```
┌─────────────────────────────────────────────────────────────────┐
│  项目级工作流（flow 驱动，多 Agent 协作）                        │
│                                                                 │
│  iterative_development.yaml                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐                  │
│  │implement │───>│code_review│───>│ testing  │                  │
│  │developer │    │tech_lead  │    │ tester   │                  │
│  │          │    │          │    │          │                  │
│  │ workflow:│    │ workflow:│    │ workflow:│                  │
│  │ tdd_wf   │    │ review_wf│    │ null     │                  │
│  └────┬─────┘    └──────────┘    └──────────┘                  │
│       │                                                         │
│       │ 引用 Agent 级工作流                                      │
│       ▼                                                         │
│  ┌─────────────────────────────────────────────────────┐       │
│  │  Agent 级工作流（runtime 驱动，单 Agent 内部）        │       │
│  │                                                     │       │
│  │  tdd_workflow.yaml                                  │       │
│  │  ┌─────────┐  ┌──────────┐  ┌─────────┐           │       │
│  │  │read_task│─>│write_test│─>│run_red  │           │       │
│  │  └─────────┘  └──────────┘  └────┬────┘           │       │
│  │                                   │                │       │
│  │  ┌──────────┐  ┌──────────┐  ┌───▼─────┐         │       │
│  │  │ submit   │<─│ verify   │<─│write_code│         │       │
│  │  └──────────┘  └──────────┘  └─────────┘         │       │
│  └─────────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────────┘
```

| | 项目级工作流 | Agent 级工作流 |
|---|-------------|---------------|
| 驱动者 | flow (daemon) | runtime |
| 参与者 | 多个 Agent | 单个 Agent |
| step 的 actor | 不同角色 | 固定为当前 Agent（self） |
| 嵌套 | 可以引用 Agent 级工作流 | 不再嵌套（叶子节点） |
| 安装方式 | 项目配置 / 阶段关联 | 角色定义的 workflows 字段 |

### 4.2 模板格式规范

> **设计决策记录：从 steps 列表改为 nodes + edges + annotations 三层结构**
>
> 原设计中工作流模板只有一个 `steps` 列表，连接关系（next/on_fail/routes）混在节点里。
> 经讨论后改为节点、边、标注分离，各管各的：
> - 节点只描述"自己是什么"
> - 边只描述"谁连谁"
> - 标注只描述"补充说明"
>
> 原因：节点里的 next/on_fail 和独立的 Edge 表达同一件事，分散在两处容易不一致。
> 分离后，可视化渲染时直接遍历 nodes 画图形、遍历 edges 画线，不需要从节点里反向提取连接关系。
>
> 详细讨论过程见 `docs/design/流程图模型与节点原语设计.md`。

```yaml
# 模板结构
workflow_id: string               # 唯一标识
name: string                      # 显示名称
scope: "project" | "agent"        # 项目级 or Agent 级
description: string

nodes:                            # 节点列表 — 流程中的"点"
  - id: string
    type: string                  # start | end | task | sub_process | decision | parallel | event
    name: string
    # ... 各类型专属字段（见下方）

edges:                            # 边列表 — 节点之间的"线"
  - id: string
    type: string                  # sequence | conditional | on_fail | on_approve | on_reject | fork_branch
    source: string                # 起始节点 ID
    target: string                # 目标节点 ID
```

> **设计决策记录：用 output_schema + submit_step_result 工具替代 done_when**
>
> 原设计中 step 完成条件用 `done_when` 字符串列表表示（如 `tests_passed`、`deliverable_submitted`），
> daemon 无法用代码校验这些字符串。经讨论后改为：
>
> - `output_schema`：定义 step 输出的 JSON Schema
> - runtime 为每个有 output_schema 的 step 动态注册 `submit_step_result` 工具
> - Agent 通过 LLM function calling 调用该工具提交结果，格式由 LLM 原生保证
> - daemon 收到 StepEvent 后不需要额外校验 — function calling 已保证格式正确
>
> 这与 OpenAI Function Calling、LangChain Structured Output、CrewAI output_pydantic 的做法一致。
> Agent 级工作流（scope: agent）仍保留 done_when，因为 Agent 级 step 由 runtime 内部驱动，
> 不经过 submit_step_result 工具。

#### 4.3.2 requirement_analysis — 需求理解

> design 侧（阶段1-需求理解.md）定义了 9 步 + 3 条回环。Phase 1 用 next/on_fail 近似表达回环，
> Phase 2 引入 decision gateway 后可精确建模条件分支。

```yaml
# workflow_templates/project/requirement_analysis.yaml

workflow_id: requirement_analysis
name: "需求理解"
scope: project
description: "收集需求、团队讨论、范围收敛、PRD 撰写、评审确认"

steps:
  # ── 1. TL 接管与入口校验 ──
  - id: tl_takeover
    mode: task
    actor: tech_lead
    trigger: stage_entered
    action: |
      阅读阶段 0 交接包和目标校准结果，验证入口条件。
      确认 handoff_status=accepted, alignment_status=passed。
      向用户说明接下来先做需求理解和范围收敛。
    input_refs: [assistant_startup_handoff, goal_alignment_brief]
    allowed_tools: [file_read, ask_teammate]
    output_schema:
      type: takeover_result
      properties:
        entry_validated: { type: boolean }
        requirement_context: { type: string, description: "需求背景摘要" }
      required: [entry_validated, requirement_context]
    next: collect_requirements

  # ── 2. 初始需求收集（TL↔用户一对一）──
  - id: collect_requirements
    mode: task
    actor: tech_lead
    action: |
      与用户沟通，收集需求细节。关注：用户角色、核心目标、
      功能范围、约束条件、参考产品。整理为结构化需求摘要。
      信息不足时通过 ask_teammate 向用户补问。
    allowed_tools: [file_read, file_write, search_docs, ask_teammate]
    output_schema:
      type: requirement_summary
      properties:
        functional_requirements:
          type: array
          items: { type: string }
        non_functional_requirements:
          type: array
          items: { type: string }
        constraints:
          type: array
          items: { type: string }
        open_questions:
          type: array
          items: { type: string }
      required: [functional_requirements]
    next: brainstorm
    on_fail: collect_requirements    # 回环 1：信息不足时重新收集

  # ── 3. 团队头脑风暴（全员讨论）──
  - id: brainstorm
    mode: session
    session:
      moderator: tech_lead
      participants: [tech_lead, backend_dev, frontend_dev, tester]
      agenda: |
        从各自角色角度讨论需求的可行性、风险和建议。
        后端关注领域模型和业务规则，前端关注页面流和交互，
        测试关注可测性和验收标准，DevOps 关注部署和环境。
    input_refs: [collect_requirements.output]
    allowed_tools: [file_read, search_docs]
    output_schema:
      type: brainstorm_notes
      properties:
        suggestions:
          type: array
          items: { type: string }
        risks:
          type: array
          items: { type: string }
        decisions:
          type: array
          items: { type: string }
        open_questions:
          type: array
          items: { type: string }
      required: [suggestions, decisions]
    next: scope_convergence

  # ── 4. 版本范围与 MVP 收敛 ──
  - id: scope_convergence
    mode: task
    actor: tech_lead
    action: |
      基于需求摘要和头脑风暴结果，收敛版本范围。
      明确 in_scope / out_of_scope / deferred 条目。
      产出 version_scope_brief。
      如果范围无法收敛，通过 ask_teammate 向用户补问。
    input_refs: [collect_requirements.output, brainstorm.output]
    allowed_tools: [file_read, file_write, ask_teammate]
    output_schema:
      type: version_scope_brief
      properties:
        scope_status:
          type: string
          enum: [converged, needs_clarification, blocked]
        mvp_goal: { type: string }
        in_scope_items:
          type: array
          items: { type: string }
        out_of_scope_items:
          type: array
          items: { type: string }
        deferred_items:
          type: array
          items: { type: string }
      required: [scope_status, mvp_goal, in_scope_items]
    next: write_prd
    on_fail: brainstorm              # 回环 2：范围不稳定时回退到讨论

  # ── 5. 撰写 PRD ──
  - id: write_prd
    mode: task
    actor: tech_lead
    action: |
      基于需求摘要、头脑风暴结果和版本范围，撰写正式 PRD 文档。
      包含功能需求、非功能需求、验收标准、约束条件。
    input_refs: [collect_requirements.output, brainstorm.output, scope_convergence.output]
    allowed_tools: [file_read, file_write]
    output_schema:
      type: prd_document
      properties:
        prd_path: { type: string, description: "PRD 文件路径" }
        summary: { type: string, description: "PRD 摘要" }
      required: [prd_path, summary]
    next: review_prd

  # ── 6. PRD 评审（全员）──
  - id: review_prd
    mode: session
    session:
      moderator: tech_lead
      participants: [tech_lead, backend_dev, frontend_dev, tester]
      agenda: "评审 PRD 文档，提出修改意见或确认通过。"
    input_refs: [write_prd.output]
    allowed_tools: [file_read]
    output_schema:
      type: review_result
      properties:
        verdict:
          type: string
          enum: [approved, needs_revision]
        comments:
          type: array
          items: { type: string }
      required: [verdict]
    next: null                       # 评审通过 → 阶段完成 → 触发门禁
    on_fail: write_prd               # 回环 3：评审不通过 → 修改 PRD
```


```yaml
          type: array
          items:
            type: object
            properties:
              level: { type: string, enum: [blocker, major, suggestion] }
              description: { type: string }
      required: [verdict]
    next: testing
    on_fail: implement               # 审查不通过 → 打回开发

  - id: testing
    name: "任务测试"
    mode: task
    actor: tester
    trigger: code_review.completed
    action: "执行功能测试和回归测试，验证实现是否符合验收标准。"
    input_refs: [task_card, implement.output]
    allowed_tools: [file_read, code_execute]
    workflow: null                    # 无子流程，自由执行
    output_schema:
      type: test_report
      properties:
        total_tests: { type: integer }
        passed: { type: integer }
        failed: { type: integer }
        verdict:
          type: string
          enum: [passed, failed]
      required: [total_tests, passed, failed, verdict]
    next: null
    on_fail: implement               # 测试失败 → 打回开发
```

#### 4.3.5 acceptance_review — 验收与最终确认

> design 侧（阶段4-验收、发布准备与最终确认.md）定义了完整的验收闭环：
> 场景准备→演示/验证→异议记录→结论判定→驳回/通过，以及三层输入模型
> （completion_report / entry_packet / entry_contract）。
> Phase 1 简化为 3 步线性流程。

```yaml
# workflow_templates/project/acceptance_review.yaml

workflow_id: acceptance_review
name: "验收与最终确认"
scope: project
description: "集成测试、用户验收、分支收尾"

steps:
  # ── 1. 集成测试 ──
  - id: integration_test
    mode: task
    actor: tester
    trigger: stage_entered
    action: |
      在 dev 分支上执行全量集成测试，验证所有功能协同工作。
      确认核心链路（文章 CRUD → 标签关联 → 评论提交）端到端通过。
    allowed_tools: [file_read, code_execute, terminal_execute]
    output_schema:
      type: integration_test_report
      properties:
        total_tests: { type: integer }
        passed: { type: integer }
        failed: { type: integer }
        coverage: { type: string, description: "测试覆盖率" }
        verdict:
          type: string
          enum: [passed, failed]
      required: [total_tests, passed, failed, verdict]
    next: user_acceptance
    on_fail: null                    # 集成测试失败 → 回退到 development 阶段

  # ── 2. 用户验收 ──
  - id: user_acceptance
    mode: session
    session:
      moderator: tech_lead
      participants: [tech_lead, tester, user]
      agenda: |
        向用户展示功能演示，逐项对照验收标准。
        收集用户反馈，记录异议和修改意见。
    input_refs: [integration_test.output]
    allowed_tools: [file_read, search_docs]
    output_schema:
      type: acceptance_result
      properties:
        verdict:
          type: string
          enum: [accepted, needs_changes, rejected]
        feedback:
          type: array
          items: { type: string }
        accepted_items:
          type: array
          items: { type: string }
        rejected_items:
          type: array
          items: { type: string }
      required: [verdict]
    next: branch_finalize
    on_fail: null                    # needs_changes → 回退到 development 阶段创建修复任务

  # ── 3. 分支收尾 ──
  - id: branch_finalize
    mode: task
    actor: devops
    trigger: user_acceptance.completed
    action: |
      将 dev 分支合并到 main，清理 task 分支，
      确认 main 分支构建通过，准备发布。
    allowed_tools: [file_read, git_commit, terminal_execute]
    output_schema:
      type: branch_status
      properties:
        merged_to_main: { type: boolean }
        main_build_passed: { type: boolean }
        cleaned_branches:
          type: array
          items: { type: string }
      required: [merged_to_main, main_build_passed]
    next: null
```

```
例：博客项目

integration_test:
    测试工程师在 dev 分支跑全量测试
    → 42 tests, 42 passed, 0 failed, coverage 85%
    → verdict: passed

user_acceptance（TL 主持，用户参与）:
    TL："请看文章发布功能..."
    用户："文章发布没问题"
    TL："标签筛选..."
    用户："标签筛选页面加载有点慢，其他都可以"
    TL 总结 → submit_step_result({
        verdict: "accepted",
        feedback: ["标签筛选性能可优化，不阻塞发布"],
        accepted_items: ["文章 CRUD", "评论", "标签"],
        rejected_items: []
    })

branch_finalize:
    DevOps 合并 dev → main，清理 task/* 分支
    → merged_to_main: true, main_build_passed: true

→ gate_type: hard → 发送审批卡片给用户 → 用户最终确认 → 进入 release 阶段
```

> **Phase 2 待补充：**
> - 三层输入模型：stage3_completion_report → acceptance_entry_packet → stage4_entry_contract
> - 验收项级别的状态管理（每个验收项有独立的链路：准备→执行→异议→判定）
> - 发布准备门禁（环境/配置/依赖/回滚预案是否就绪）
> - 最终确认责任链（谁确认功能验收、谁确认 NFR、谁签发进入发布）
> - 遗留问题分类处理（可接受遗留 / 必须修复 / 必须回退阶段 3 / 不属于本次范围）
> - reject route / rollback route / reopen stage3 route 的完整处理


#### 4.3.6 release_execution — 发布执行与观察

> design 侧（阶段5-发布执行、发布后观察与回退控制.md）定义了完整的发布闭环：
> precheck→执行→smoke check→灰度观察→放量→结案，以及独立的回滚子流程。
> Phase 1 简化为 5 步线性流程 + on_fail 回滚。

```yaml
# workflow_templates/project/release_execution.yaml

workflow_id: release_execution
name: "发布执行与观察"
scope: project
description: "发布前检查、执行部署、冒烟测试、观察、结案"

steps:
  # ── 1. 发布前最终检查 ──
  - id: precheck
    mode: task
    actor: devops
    trigger: stage_entered
    action: |
      执行发布前最终检查：环境就绪、配置正确、依赖可用、
      回滚方案已确认、发布窗口已确认。
    allowed_tools: [file_read, terminal_execute]
    output_schema:
      type: precheck_result
      properties:
        env_ready: { type: boolean }
        config_verified: { type: boolean }
        deps_healthy: { type: boolean }
        rollback_plan_confirmed: { type: boolean }
        verdict:
          type: string
          enum: [pass, fail]
      required: [verdict]
    next: execute_deploy
    on_fail: precheck                # 检查不通过 → 修复后重新检查

  # ── 2. 执行部署 ──
  - id: execute_deploy
    mode: task
    actor: devops
    action: |
      按发布计划执行部署。记录部署版本、时间、目标环境。
    input_refs: [precheck.output]
    allowed_tools: [file_read, terminal_execute]
    output_schema:
      type: deploy_result
      properties:
        deployed: { type: boolean }
        deploy_version: { type: string }
        deploy_time: { type: string }
        target_env: { type: string }
      required: [deployed, deploy_version]
    next: smoke_test
    on_fail: rollback                # 部署失败 → 回滚

  # ── 3. 冒烟测试 ──
  - id: smoke_test
    mode: task
    actor: tester
    action: |
      执行冒烟测试，验证核心链路在生产环境正常工作。
      至少覆盖：用户登录、核心业务流程、关键 API 响应。
    input_refs: [execute_deploy.output]
    allowed_tools: [file_read, code_execute, terminal_execute]
    output_schema:
      type: smoke_result
      properties:
        total_checks: { type: integer }
        passed: { type: integer }
        failed: { type: integer }
        verdict:
          type: string
          enum: [passed, failed]
      required: [verdict]
    next: observe
    on_fail: rollback                # 冒烟失败 → 回滚

  # ── 4. 发布后观察 ──
  - id: observe
    mode: task
    actor: devops
    action: |
      监控发布后的系统指标，持续观察一段时间。
      关注：错误率、延迟 P99、CPU/内存、关键业务指标。
      如果指标异常，立即触发回滚。
    input_refs: [execute_deploy.output, smoke_test.output]
    allowed_tools: [file_read, terminal_execute, search_docs]
    output_schema:
      type: observation_report
      properties:
        duration_minutes: { type: integer, description: "观察时长（分钟）" }
        error_rate: { type: string }
        latency_p99: { type: string }
        verdict:
          type: string
          enum: [healthy, degraded, rollback_needed]
      required: [verdict]
    next: release_conclusion
    on_fail: rollback                # 观察异常 → 回滚

  # ── 5. 发布结论 ──
  - id: release_conclusion
    mode: task
    actor: tech_lead
    action: |
      总结发布结果，产出发布报告。
      包含：发布状态、关键指标、遗留问题、经验教训。
    input_refs: [execute_deploy.output, smoke_test.output, observe.output]
    allowed_tools: [file_read, file_write]
    output_schema:
      type: release_outcome_report
      properties:
        release_status:
          type: string
          enum: [success, partial, rolled_back]
        summary: { type: string }
        key_metrics:
          type: object
          properties:
            error_rate: { type: string }
            latency_p99: { type: string }
        lessons_learned:
          type: array
          items: { type: string }
      required: [release_status, summary]
    next: null

  # ── R. 回滚（任何 step 的 on_fail 指向此处）──
  - id: rollback
    mode: task
    actor: devops
    action: |
      执行回滚操作，恢复到上一个稳定版本。
      回滚后执行验证，确认系统恢复正常。
    allowed_tools: [file_read, terminal_execute]
    output_schema:
      type: rollback_result
      properties:
        rolled_back: { type: boolean }
        rollback_version: { type: string }
        verification_passed: { type: boolean }
        reason: { type: string, description: "回滚原因" }
      required: [rolled_back, reason]
    next: release_conclusion         # 回滚后也要产出发布结论
```

```
例：博客项目

precheck:
    DevOps 检查 → env_ready: true, config_verified: true,
    deps_healthy: true, rollback_plan_confirmed: true
    → verdict: pass

execute_deploy:
    DevOps 执行部署 → deployed: true, version: v1.0.0,
    target_env: production

smoke_test:
    测试工程师执行冒烟测试 → 10 checks, 10 passed
    → verdict: passed

observe:
    DevOps 监控 30 分钟 → error_rate: 0.1%, latency_p99: 180ms
    → verdict: healthy

release_conclusion:
    TL 总结 → release_status: success,
    summary: "博客系统 v1.0.0 发布成功，指标正常"

→ gate_type: none → 项目 completed
```

```
例：博客项目（回滚场景）

precheck → pass
execute_deploy → deployed: true, version: v1.0.0
smoke_test → 10 checks, 8 passed, 2 failed → verdict: failed
    → on_fail → rollback

rollback:
    DevOps 回滚到 v0.9.0 → rolled_back: true,
    verification_passed: true,
    reason: "冒烟测试失败：评论提交接口 500"

release_conclusion:
    TL 总结 → release_status: rolled_back,
    summary: "v1.0.0 发布回滚，评论接口异常",
    lessons_learned: ["评论接口需要增加集成测试覆盖"]

→ 回退到 development 阶段，创建修复任务
```

> **Phase 2 待补充：**
> - 三层输入模型：stage4_exit_packet → release_entry_packet → stage5_entry_contract
> - 灰度发布与分批放量（canary → 10% → 50% → 100%，每批观察后决策）
> - 发布中的动态决策机制（继续/暂停/回滚的实时判断，基于指标阈值）
> - 回滚子流程独立建模（回滚验证、回滚后影响评估、回滚后通知）
> - 发布后跟踪期（发布成功后持续观察 N 天，期间发现问题走 hotfix 流程）
> - release_outcome_report 作为项目归档的正式结案文档

## 六、任务调度与状态机

### 6.1 任务对象模型

任务在不同阶段有不同的形态：

```
阶段 2（设计态）                    阶段 3（运行态）
                                   
平台工单                            TaskInstance
┌──────────────────┐               ┌──────────────────────────────┐
│ TASK-003          │               │ taski-003                     │
│ title: 标签系统   │  ──投影──>    │                               │
│ type: feature     │               │ source_ref: "TASK-003"        │
│ depends_on: [002] │               │ status: ready                 │
│ priority: high    │               │ owner_id: backend-dev-1       │
│                   │               │ reviewer_id: tech-lead        │
│ "应该做什么"      │               │ dependencies:                 │
│                   │               │   upstream: [taski-002]       │
└──────────────────┘               │   external: []                │
                                   │ scope_in: [标签CRUD, 按标签筛选]│
                                   │ scope_out: [标签推荐算法]      │
                                   │ blocker_conditions: []         │
                                   │ wave: 2                        │
                                   │ priority: high                 │
                                   │ reopen_count: 0                │
                                   │                               │
                                   │ "能不能做、谁来做、什么条件"    │
                                   └──────────────────────────────┘
```

**为什么需要 TaskInstance 而不是直接用平台工单？**

平台工单是"应该做什么"，TaskInstance 是"现在能不能做"。同一个工单在不同项目、不同波次、不同团队配置下，调度行为完全不同。TaskInstance 承载的是运行时调度决策所需的全部信息。

### 6.2 TaskInstance 数据结构

```python
class TaskInstance(BaseModel):
    """阶段 3 的核心调度对象"""

    # 标识
    instance_id: str                  # taski-003
    source_ref: str                   # 平台工单 ID（TASK-003）
    task_type: str                    # feature | bugfix | refactor | integration

    # 状态
    status: TaskInstanceStatus
    reopen_count: int = 0             # 区分一次完成和多轮返工

    # 人员
    owner_id: str                     # 主执行者
    reviewer_id: str                  # 主审查者

    # 依赖
    dependencies: TaskDependencies

    # 约束（从阶段 2 继承）
    scope_in: List[str]               # 明确要做什么
    scope_out: List[str]              # 明确不做什么
    blocker_conditions: List[str]     # 满足前不得推进

    # 调度
    wave: int                         # 波次（第几批启动）
    priority: str                     # critical | high | medium | low

    # 工作流
    workflow_instance_id: Optional[str]  # 绑定的 WorkflowInstance


class TaskInstanceStatus(str, Enum):
    DRAFT = "draft"                   # 刚从阶段 2 投影，未就绪
    READY = "ready"                   # 依赖满足，可以启动
    IN_PROGRESS = "in_progress"       # 开发中
    IN_REVIEW = "in_review"           # 审查中
    IN_FIX = "in_fix"                # 审查不通过，修复中（不新建任务）
    IN_VERIFICATION = "in_verification"  # 测试中
    BLOCKED = "blocked"               # 被阻塞（外部依赖等）
    DONE = "done"                     # 完成
    CANCELLED = "cancelled"           # 取消


class TaskDependencies(BaseModel):
    upstream: List[str] = []          # 依赖的其他 TaskInstance ID
    external: List[ExternalDep] = []  # 外部依赖


class ExternalDep(BaseModel):
    dep_id: str                       # 如 "notify-account-ready"
    description: str                  # "正式通知账号开通"
    satisfied: bool = False           # 是否已满足
```

### 6.3 任务状态流转

```
                    ┌──────────────────────────────────────────────────────┐
                    │                                                      │
                    │  ┌───────┐                                           │
                    │  │ draft │  阶段 3 初始化时从平台工单投影              │
                    │  └───┬───┘                                           │
                    │      │ 依赖检查                                      │
                    │      ├── 依赖未满足 ──→ draft（等待）                 │
                    │      ├── 外部依赖未满足 ──→ blocked                   │
                    │      └── 全部满足 ──→ ready                          │
                    │                                                      │
                    │  ┌───────┐                                           │
                    │  │ ready │  可以启动，等待 Agent 空闲                  │
                    │  └───┬───┘                                           │
                    │      │ daemon 分配 TaskAssignment                    │
                    │      ▼                                               │
                    │  ┌─────────────┐                                     │
                    │  │ in_progress │  Agent 执行 implement step          │
                    │  └──────┬──────┘                                     │
                    │         │ Agent submit_step_result                   │
                    │         ▼                                            │
                    │  ┌───────────┐                                       │
                    │  │ in_review │  TL 执行 code_review step             │
                    │  └─────┬─────┘                                       │
                    │        │                                             │
                    │   ┌────┴────┐                                        │
                    │   │         │                                        │
                    │   ▼         ▼                                        │
                    │ 通过      不通过                                      │
                    │   │         │                                        │
                    │   ▼         ▼                                        │
                    │ ┌──────────────────┐  ┌────────┐                    │
                    │ │ in_verification  │  │ in_fix │ reopen_count++     │
                    │ └────────┬─────────┘  └───┬────┘                    │
                    │          │                 │ 修复完成                 │
                    │     ┌────┴────┐            │ 重新进入 in_review      │
                    │     │         │            └──→ in_review            │
                    │     ▼         ▼                                      │
                    │   通过      发现 Bug                                  │
                    │     │         │                                      │
                    │     ▼         └──→ in_fix（同上）                    │
                    │  ┌──────┐                                            │
                    │  │ done │                                            │
                    │  └──────┘                                            │
                    │                                                      │
                    │  任何状态 ──→ cancelled（用户取消）                    │
                    │  任何状态 ──→ blocked（外部依赖突然不满足）            │
                    └──────────────────────────────────────────────────────┘
```

**与旧设计的区别：**

| 旧设计 | 新设计 | 变化原因 |
|--------|--------|---------|
| created → assigned | draft → ready | draft 表示"还不能做"，ready 表示"可以做了" |
| review_rejected | in_fix | 不是新状态，是同一个任务的修复阶段，reopen_count 追踪返工次数 |
| bug_found | in_fix | 同上，测试发现 Bug 也走 in_fix |
| 无 | blocked | 外部依赖不满足时的状态 |
| 无 | in_verification | 区分"审查中"和"测试中" |
| 无 | draft | 区分"刚投影"和"可以启动" |

#### 6.5.3 依赖图构建

```python
class DependencyGraph:
    """任务依赖图"""

    def __init__(self, instances: List[TaskInstance]):
        self.graph: Dict[str, List[str]] = {}    # task_id → [downstream_ids]
        self.in_degree: Dict[str, int] = {}      # task_id → 未满足的依赖数
        self._build(instances)

    def _build(self, instances: List[TaskInstance]):
        """从 TaskInstance 列表构建依赖图"""
        for inst in instances:
            self.in_degree[inst.instance_id] = len(inst.dependencies.upstream)
            for dep in inst.dependencies.upstream:
                self.graph.setdefault(dep, []).append(inst.instance_id)

    def get_ready_tasks(self) -> List[str]:
        """返回所有依赖已满足（in_degree == 0）且状态为 draft 的任务"""
        return [tid for tid, deg in self.in_degree.items() if deg == 0]

    def on_task_completed(self, task_id: str) -> List[str]:
        """任务完成后，更新下游依赖，返回新变为 ready 的任务"""
        newly_ready = []
        for downstream in self.graph.get(task_id, []):
            self.in_degree[downstream] -= 1
            if self.in_degree[downstream] == 0:
                newly_ready.append(downstream)
        return newly_ready
```

#### 6.5.4 调度器核心逻辑

```python
class TaskScheduler:
    """任务调度器 — 事件驱动"""

    def __init__(self, instances: List[TaskInstance], config: ParallelConfig):
        self.dep_graph = DependencyGraph(instances)
        self.config = config
        self.instances = {i.instance_id: i for i in instances}
        self.running_count = 0

    async def initialize(self):
        """阶段 3 初始化：将所有 ready 任务启动"""
        for task_id in self.dep_graph.get_ready_tasks():
            self.instances[task_id].status = TaskInstanceStatus.READY
        await self.dispatch_ready_tasks()

    async def on_event(self, event: StepEvent):
        """每次收到 StepEvent 重新评估调度"""

        # 1. 更新当前任务状态
        instance = self.get_instance(event.assignment_id)
        self.update_status(instance, event)

        # 2. 如果任务完成，检查下游依赖
        if event.event_type == "completed":
            self.running_count -= 1
            newly_ready = self.dep_graph.on_task_completed(instance.instance_id)
            for task_id in newly_ready:
                self.instances[task_id].status = TaskInstanceStatus.READY

        # 3. 如果任务失败，检查是否阻塞下游
        if event.event_type == "failed":
            self.running_count -= 1
            self.mark_downstream_blocked(instance)

        # 4. 调度所有 ready 的任务
        await self.dispatch_ready_tasks()

    async def dispatch_ready_tasks(self):
        """调度所有 ready 且有空闲 Agent 的任务"""
        for task in self.get_ready_tasks():
            if self.running_count >= self.config.max_parallel_tasks:
                break
            agent = self.find_available_agent(task)
            if agent:
                task.status = TaskInstanceStatus.IN_PROGRESS
                self.running_count += 1
                await self.dispatch(task, agent)
```

```python
class TaskProvider(ABC):
    @abstractmethod
    async def create(self, task: TaskCreate) -> str:
        """创建任务，返回任务 ID"""

    @abstractmethod
    async def read(self, task_id: str) -> TaskDetail:
        """读取任务详情"""

    @abstractmethod
    async def update(self, task_id: str, changes: TaskUpdate) -> None:
        """更新任务（状态、assignee、交付物等）"""

    @abstractmethod
    async def query(self, filters: TaskQuery) -> List[TaskSummary]:
        """查询任务列表"""

    @abstractmethod
    async def on_change(self, callback: Callable) -> None:
        """监听任务变更事件（状态流转时通知 flow）"""
```

## 七、三种交互模式

现实开发中，团队协作有三种本质不同的活动。我们的架构需要分别建模，而不是用统一的"消息路由"混在一起。

### 7.1 三种模式总览

```
┌─────────────────────────────────────────────────────────────┐
│  模式 1：任务执行（Task Execution）                          │
│                                                             │
│  flow 分配任务 → Agent 独立执行 → 上报结果                   │
│                                                             │
│  现实类比：开发者在工位上写代码                               │
│  特征：一对一、异步、结构化输入输出                           │
├─────────────────────────────────────────────────────────────┤
│  模式 2：协作会议（Collaboration Session）                    │
│                                                             │
│  daemon 发起会议 → 多人参与讨论 → 主持人总结结论              │
│                                                             │
│  现实类比：需求评审会、设计评审会                             │
│  特征：多对多、同步、有主持人和议程、有明确结论               │
├─────────────────────────────────────────────────────────────┤
│  模式 3：即时沟通（Instant Messaging）                       │
│                                                             │
│  Agent 执行任务时遇到问题 → @某人问一句 → 得到回答 → 继续    │
│                                                             │
│  现实类比：Slack 里 @同事问一个问题                          │
│  特征：一对一、异步、非结构化、无明确结束                     │
└─────────────────────────────────────────────────────────────┘
```

| | 任务执行 | 协作会议 | 即时沟通 |
|---|---------|---------|---------|
| 参与者 | 1 个 Agent | 多个 Agent + 用户 | 2 个 Agent |
| 触发 | flow 分配 step | flow 发起 session step | Agent 调用工具 |
| 结束 | Agent submit_step_result | 主持人 submit_step_result | 对方回复 |
| 产出 | 结构化（output_schema） | 结构化（会议结论） | 非结构化（自然语言） |
| 归属 | flow 调度 + runtime 执行 | flow 管理 + runtime 执行 | runtime 工具 + flow 路由 |
| 是否是 step | 是 | 是 | 不是 |


**即时沟通与协作会议的区别：**

| | 协作会议 | 即时沟通 |
|---|---------|---------|
| 触发 | flow 发起 SessionAssignment | Agent 调用 ask_teammate 工具 |
| 参与者 | 预定义的参与者列表 | 调用者指定一个目标 |
| 上下文 | 所有人共享同一个讨论上下文 | 一问一答，不影响其他人 |
| 结束 | 主持人 submit_step_result | 对方回复即结束 |
| 是否阻塞 step | 是（整个 step 就是讨论） | 是（等待回复，但 step 继续） |
| 记录 | 群聊历史 | Agent 对话历史中的工具调用记录 |

## 八、门禁系统

### 8.1 门禁出现的位置

门禁出现在两个地方，机制相同：

| 位置 | 说明 | 示例 |
|------|------|------|
| 阶段边界 | 从一个阶段进入下一个阶段时 | requirement → design：用户确认 PRD |
| step 内部 | 某些 step 的结果需要用户确认 | user_acceptance：用户验收功能 |

### 8.2 门禁类型

| 类型 | 说明 | 示例 |
|------|------|------|
| hard | 必须用户操作确认 | 阶段 1→2 用户确认 PRD，阶段 4→5 用户最终确认 |
| soft | 默认自动通过，可配置为需要确认 | 阶段 2→3 设计评审 |

> **设计决策记录：去掉 done_when 和 output_schema 作为门禁类型**
>
> 原设计中 done_when 和 output_schema 也列为门禁类型。经讨论后：
> - done_when 已被 output_schema + submit_step_result 工具替代（见第四章）
> - output_schema 的校验由 LLM function calling 在工具调用时保证，不是门禁
> - 门禁只指"需要人类操作确认"的环节，系统自动校验不算门禁

### 8.3 数据结构

```python
class GateRequest(BaseModel):

    project_id: str

    trigger_point: str                # "stage_transition" | "step_completion"

                                      # | "changes_requested" | "expired"
```

### 8.6 审批流程

```
某个条件触发审批（阶段完成 / step 需要确认）
    │
    ▼
flow 生成 GateRequest
    │
    ├── gate_type == soft？
    │   ├── 项目配置要求确认？
    │   │   ├── 不要求 → 自动 approve，记录历史，继续
    │   │   └── 要求 → 同 hard
    │   └──
    │
    ├── gate_type == hard
    │   │
    │   ▼
    │   生成 GateCard，通过 chat API 发送给用户
    │   │
    │   ▼
    │   等待用户操作...
    │   │
    │   ├── approve（确认通过）
    │   │   → 记录门禁通过历史
    │   │   → 推进到下一阶段 / 下一 step
    │   │
    │   ├── request_changes（需要修改）
    │   │   → 记录用户意见
    │   │   → 回退到指定 step（如 write_prd）
    │   │   → 用户意见作为新的输入注入 Agent prompt
    │   │
    │   ├── reject（驳回）
    │   │   → 记录驳回原因
    │   │   → 回退到更早的阶段（如 requirement → 重新收集需求）
    │   │
    │   └── 超时（timeout_minutes 到期）
    │       → status = expired
    │       → 通知用户"审批已过期"
    │       → 项目状态 → suspended
    │       → 用户下次回来时可重新触发审批
    │
    ▼
记录到 gate_history.yaml（审计用）
```

### 8.7 用户操作后的处理

**approve — 确认通过：**

```
用户点击"确认通过"
    │
    ▼
flow 更新 GateRequest.status = "approved"
    │
    ▼
记录到 gate_history.yaml:
    gate_id: gate-00012
    gate_type: hard
    trigger_point: stage_transition
    from_stage: requirement
    to_stage: design
    status: approved
    responded_by: user
    responded_at: 2026-04-18T14:00:00Z
    │
    ▼
推进到 design 阶段
    加载 design_and_planning 工作流模板
    触发第一个 step
```

**request_changes — 需要修改：**

```
用户点击"需要修改"，填写意见：
    "评论功能不需要 WebSocket，用轮询就行"
    │
    ▼
flow 更新 GateRequest.status = "changes_requested"
    │
    ▼
flow 决定回退目标：
    阶段边界审批 → 回退到当前阶段的指定 step
    step 内审批 → 回退到当前 step 的 on_fail
    │
    ▼
重新下发 TaskAssignment / SessionAssignment：
    action 中追加用户意见：
    "用户反馈：评论功能不需要 WebSocket，用轮询就行。
     请根据此反馈修改 PRD。"
    │
    ▼
Agent 根据用户意见修改产出
    │
    ▼
修改完成后重新触发审批
```

**reject — 驳回：**

```
用户点击"驳回"，填写原因：
    "这个方向不对，我不想做博客了，想做电商"
    │
    ▼
flow 更新 GateRequest.status = "rejected"
    │
    ▼
flow 根据 pipeline 回退规则决定回退到哪个阶段
    （通常回退到更早的阶段，如 requirement 甚至 alignment）
    │
    ▼
保存当前阶段快照（审计用）
清理当前阶段的临时状态
加载目标阶段的工作流模板
```

**expired — 超时：**

```
timeout_minutes 到期，用户未操作
    │
    ▼
flow 更新 GateRequest.status = "expired"
    │
    ▼
通过 chat 发送提醒：
    "📋 需求评审确认已过期（72 小时未操作）。
     项目已暂停，回复 /resume 可重新触发审批。"
    │
    ▼
项目状态 → suspended
    │
    ▼
用户下次回来：
    /resume → flow 重新生成 GateRequest → 发送新的审批卡片
```

## 十三、设计决策记录

### 13.1 Agent 级工作流命名讨论

> **状态：待定，暂不修改**
>
> 当前 Agent 级工作流使用 `scope: "agent"`，存放在 `workflow_templates/agent/` 目录下，项目级 step 通过 `workflow` 字段引用。
>
> 讨论中提出：项目级和 Agent 级都叫 workflow 看起来混淆。现实开发中两者的叫法不同：
>
> - 项目级：流程（Process / Workflow）— 多人协作，关注谁做什么、什么顺序、什么门禁
> - Agent 级：规程（Procedure / Practice）— 单人执行，关注怎么做、什么步骤、什么规范
>
> 如果采纳，变更范围：
>
> ```
> scope: "agent"              → scope: "procedure"
> workflow_templates/agent/   → procedure_templates/
> step.workflow: tdd_workflow  → step.procedure: tdd
> ```
>
> 暂不修改的原因：当前格式统一（同一套 YAML 结构），改名涉及 flow 和 runtime 两侧文档同步更新，等核心设计稳定后再评估。

### 13.2 移除 exit_conditions / entry_requirements

> **状态：已采纳**
>
> 原设计中 StageTransition 包含 `exit_conditions` 和 `entry_requirements` 字段。移除原因：
> - 与工作流模板中 step 的 done_when 重复检查
> - 自然语言字符串，系统无法自动校验
> - "用户已确认"是 gate_type: hard 的职责
>
> 简化后：所有 step completed + gate passed = 进入下一阶段。

### 13.3 移除 ProjectStage 硬编码枚举

> **状态：已采纳**
>
> 原设计中阶段是 Python 枚举（STAGE_0 ~ STAGE_5）。改为配置驱动的 PipelineTemplate，原因：
> - 不同项目类型需要不同阶段数量（standard 6 个，hotfix 3 个）
> - 无法加减阶段
> - 与"流程模板可配置、可裁剪"的设计原则矛盾

## 十四、流程引擎抽象层设计

### 14.1 设计目标

Phase 1 先实现 BPMN 2.0 Level 1（描述性建模）子集，保留抽象层方便 Phase 2 扩展到 Level 2/3。

核心原则：
- 引擎只依赖抽象接口，不依赖具体节点类型
- 新增节点类型只需实现接口 + 注册，不改引擎代码
- ISO 5807 的符号是 BPMN 2.0 的子集，不需要单独适配

### 14.2 抽象层架构

```python
# ── 抽象基类 ──

class FlowNode(BaseModel):
    """流程图节点 — 抽象基类"""
    id: str
    type: NodeType
    name: str = ""
    description: str = ""
    status: NodeStatus = NodeStatus.PENDING

    # 连接关系（Phase 1 用 next/on_fail，Phase 2 扩展为 edges）
    next: Optional[str] = None
    on_fail: Optional[str] = None

    def accept(self, visitor: "NodeVisitor"):
        """访问者模式 — 引擎通过 visitor 处理不同类型的节点"""
        return visitor.visit(self)

    def validate(self) -> List[str]:
        """校验节点定义是否合法，返回错误列表"""
        return []

class TaskNode(FlowNode):
    """任务节点 — 一个 Agent 执行"""
    type: NodeType = NodeType.TASK

    action: str = ""                  # 任务描述（注入 prompt）
    input_refs: List[str] = []
    allowed_tools: List[str] = []
    workflow: Optional[str] = None    # Agent 级工作流引用
    output_schema: Optional[dict] = None

        if not self.actor:

    """协作会议节点 — 多人讨论"""
    type: NodeType = NodeType.SESSION
    moderator: str                    # 主持人
    participants: List[str] = []      # 参与者
    agenda: str = ""                  # 议程
    allowed_tools: List[str] = []
    output_schema: Optional[dict] = None

            errors.append(f"SessionNode '{self.id}' 缺少 moderator")
        if not self.participants:
            errors.append(f"SessionNode '{self.id}' 缺少 participants")
```

### 14.6 引擎核心：NodeVisitor + NodeExecutor

```python
class NodeVisitor(ABC):
    """访问者接口 — 引擎通过此接口处理不同类型的节点"""

    @abstractmethod
    async def visit_task(self, node: TaskNode) -> NodeStatus:
        """处理任务节点：下发 TaskAssignment，等待 StepEvent"""

    @abstractmethod
    async def visit_session(self, node: SessionNode) -> NodeStatus:
        """处理会议节点：下发 SessionAssignment，等待主持人提交"""

    @abstractmethod
    async def visit_decision(self, node: DecisionNode) -> str:
        """处理判断节点：评估条件，返回目标节点 ID"""

    @abstractmethod
    async def visit_gate(self, node: DecisionNode) -> str:
        """处理门禁节点：发送审批卡片，等待用户操作，返回目标节点 ID"""

    @abstractmethod
    async def visit_fork(self, node: ParallelNode) -> List[str]:
        """处理并行分支：返回所有分支的起始节点 ID"""

    @abstractmethod
    async def visit_join(self, node: ParallelNode) -> NodeStatus:
        """处理并行合并：等待所有/任一分支完成"""

    @abstractmethod
    async def visit_event(self, node: EventNode) -> NodeStatus:
        """处理事件节点：等待事件触发或超时"""


class FlowEngine:
    """流程引擎 — 只依赖抽象接口"""

    def __init__(self, visitor: NodeVisitor):
        self.visitor = visitor

    async def execute(self, workflow: WorkflowInstance):
        """执行工作流实例"""
        current = self.get_start_node(workflow)

        while current:
            current.status = NodeStatus.RUNNING

            # 通过访问者模式分派到具体处理逻辑
            result = await current.accept(self.visitor)

            if isinstance(result, NodeStatus):
                current.status = result
                if result == NodeStatus.COMPLETED:
                    current = self.get_next_node(workflow, current)
                elif result == NodeStatus.FAILED:
                    current = self.get_fail_node(workflow, current)
                else:
                    break  # BLOCKED, CANCELLED 等
            elif isinstance(result, str):
                # decision/gate 返回目标节点 ID
                current.status = NodeStatus.COMPLETED
                current = self.get_node_by_id(workflow, result)
            elif isinstance(result, list):
                # fork 返回分支列表，并行执行
                current.status = NodeStatus.COMPLETED
                await self.execute_parallel(workflow, result)
                current = self.get_next_node(workflow, current)
```

### 14.7 Phase 1 实现范围

Phase 1 只实现 `TaskNodeExecutor` 和 `SessionNodeExecutor`：

```python
class Phase1Visitor(NodeVisitor):
    """Phase 1 实现 — 只处理 task 和 session"""

    async def visit_task(self, node: TaskNode) -> NodeStatus:
        # 构造 TaskAssignment，下发给 runtime
        assignment = TaskAssignment(
            step_id=node.id,
            agent_id=self.resolve_actor(node.actor),
            action=node.action,
            input_refs=node.input_refs,
            allowed_tools=node.allowed_tools,
            workflow=node.workflow,
            output_schema=node.output_schema,
        )
        event = await self.runtime_client.send_assignment(assignment)
        if event.event_type == "completed":
            return NodeStatus.COMPLETED
        elif event.event_type == "blocked":
            return NodeStatus.BLOCKED
        else:
            return NodeStatus.FAILED

    async def visit_session(self, node: SessionNode) -> NodeStatus:
        # 构造 SessionAssignment，下发给 runtime
        assignment = SessionAssignment(
            step_id=node.id,
            moderator_id=self.resolve_actor(node.moderator),
            participant_ids=[self.resolve_actor(p) for p in node.participants],
            agenda=node.agenda,
            allowed_tools=node.allowed_tools,
            output_schema=node.output_schema,
        )
        event = await self.runtime_client.send_assignment(assignment)
        if event.event_type == "completed":
            return NodeStatus.COMPLETED
        else:
            return NodeStatus.FAILED

    # Phase 2 才实现的方法，Phase 1 抛出 NotImplementedError
    async def visit_decision(self, node): raise NotImplementedError("Phase 2")
    async def visit_gate(self, node): raise NotImplementedError("Phase 2")
    async def visit_fork(self, node): raise NotImplementedError("Phase 2")
    async def visit_join(self, node): raise NotImplementedError("Phase 2")
    async def visit_event(self, node): raise NotImplementedError("Phase 2")
```

Phase 2 扩展时，只需实现新的 visitor 方法，不改 FlowEngine 代码：

```
Phase 1 → Phase 2 扩展路径：

1. 实现 visit_decision → 支持条件分支
2. 实现 visit_gate → 支持 step 间门禁
3. 实现 visit_fork / visit_join → 支持并行
4. 实现 visit_event → 支持等待外部事件

FlowEngine.execute() 不需要任何修改。
```

### 14.4 演进规划

不需要现在实现完整的流程原语体系。分阶段演进：

**Phase 1（当前）：线性 step 链**

```
A ──→ B ──→ C
      │
      └── on_fail ──→ A
```

能力：顺序执行、失败回退、子流程引用、门禁。
覆盖场景：标准六阶段流程、hotfix 流程。

**Phase 2：加入并行和条件分支**

```
      ┌──→ B ──┐
A ──◆─┤        ├─◆──→ D
      └──→ C ──┘

A ──◇── 条件1 ──→ B
    │
    └── 条件2 ──→ C
```

新增：fork/join（并行网关）、decision（排他网关）、blocked/cancelled 状态。
覆盖场景：前后端并行开发、条件性跳过某些 step。

**Phase 3：完整流程引擎**

新增：event_wait（中间事件）、inclusive gateway（包容网关）、loop（循环）、skip_with_reason。
覆盖场景：等待外部事件、复杂的动态编排。

**Phase 1 到 Phase 2 的迁移路径：**

```
Phase 1 的 step 定义：
  - id: implement
    next: code_review
    on_fail: implement

Phase 2 扩展后：
  - id: implement_fork
    type: parallel_gateway          # 新增字段
    branches:
      - [backend_implement, backend_test]
      - [frontend_implement, frontend_test]
    join: integration_test

  - id: review_decision
    type: exclusive_gateway          # 新增字段
    conditions:
      - condition: "review_result == 'approved'"
        next: testing
      - condition: "review_result == 'rejected'"
        next: implement
    default: implement
```

Phase 1 的 step 定义在 Phase 2 中仍然有效（type 默认为 task，next/on_fail 仍然工作），向后兼容。

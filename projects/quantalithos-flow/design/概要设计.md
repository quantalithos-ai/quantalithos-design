# quantalithos-flow 概要设计

> 流程编排引擎 — 阶段状态机、工作流模板、门禁控制、任务调度、消息路由

---

## 一、项目定位

### 1.1 核心职责

quantalithos-flow 是整个平台的**编排中枢（daemon）**，负责宏观流程控制：

- **阶段状态机**：管理项目在 6 个阶段之间的流转、门禁、回退
- **工作流模板**：定义阶段内部的 step 顺序、触发条件、完成判定
- **任务状态机**：驱动任务卡在 created→assigned→in_development→...→completed 之间流转
- **step 调度**：决定当前节点由哪个 Agent 执行，向 quantalithos-runtime 下发 NodeAssignment
- **消息路由**：控制消息分发、@提及路由、参与度控制
- **门禁控制**：硬门禁（用户必须确认）、软门禁（默认自动通过）
- **交接包管理**：阶段间的正式交接对象（entry_packet → exit_packet）

### 1.2 在整体架构中的位置

```
quantalithos-chat (聊天前端)
      │
      │ HTTP/WebSocket
      ▼
quantalithos-gate (API 网关)
      │
      ├──────────────────┬──────────────────┐
      │                  │                  │
      ▼                  ▼                  ▼
╔═══════════════╗  quantalithos-platform  quantalithos-runtime
║ quantalithos- ║  (平台数据服务)          (Agent 运行时)
║ flow (daemon) ║        │                  │
╚═══════╤═══════╝        │                  │
        │                │                  │
        └────────────────┴──────────────────┘
                         │
                ┌────────┴────────┐
                │                 │
                ▼                 ▼
         quantalithos-sync  quantalithos-infra
         (工作区同步)        (基础设施)
```

### 1.3 与 quantalithos-runtime 的分工

| 职责 | quantalithos-flow | quantalithos-runtime |
|------|-------------------|----------------------|
| 阶段流转（6 阶段） | ✅ 控制 | 不参与 |
| 工作流 step 推进 | ✅ 调度 | 接收 NodeAssignment 执行 |
| 任务状态流转 | ✅ 驱动 | 只读消费 + 事件上报 |
| Agent 实例化/销毁 | 发出指令 | ✅ 执行 |
| Agent think→act 循环 | 不参与 | ✅ 执行 |
| 消息路由与参与度控制 | ✅ 控制 | 不参与 |
| 工具权限（step 级动态） | ✅ 下发 allowed_tools | 校验（取交集） |
| 门禁与审批 | ✅ 控制 | 不参与 |
| LLM 调用 | 不参与 | ✅ 执行 |

一句话：**flow 决定"谁在什么时候做什么"，runtime 负责"怎么做"。**

## 二、核心概念

### 2.1 统一的流程模型

所有层次的流程都用同一套 BPMN 2.0 格式（ProcessDefinition = nodes + edges）表达：

```
第一层：项目流程    — 项目经过哪些阶段？    → ProcessDefinition（每个阶段是 Call Activity）
第二层：阶段流程    — 这个阶段内怎么做？    → ProcessDefinition（每个 step 是 Activity/Gateway/Event）
第三层：Agent 流程  — 单个 Agent 怎么做？   → ProcessDefinition（如 TDD 循环）
```

### 2.2 核心对象关系

```
Project
  └── ProcessInstance（项目流程实例，从项目级 ProcessDefinition 加载）
        └── ProcessInstance（当前阶段的流程实例，由 Call Activity 触发）
              └── FlowNode（当前正在执行的节点）
                    └── NodeAssignment（下发给 Agent 的执行指令）
```

## 三、项目流程（Pipeline as ProcessDefinition）

> **设计决策：Pipeline 也是 ProcessDefinition**
>
> 原设计中 Pipeline 是独立的概念（PipelineTemplate + stages 列表），不属于 BPMN。
> 经讨论后统一为 BPMN 2.0：Pipeline 本身就是一个 ProcessDefinition，
> 每个"阶段"是一个 Call Activity 节点，门禁是 Exclusive Gateway 节点。
>
> 这样整个系统只有一种流程定义格式（ProcessDefinition），
> 从项目级到阶段级到 Agent 级，全部用同一套 nodes + edges 表达。

### 3.1 统一的流程层次

```
┌─────────────────────────────────────────────────────────────┐
│  项目流程（Pipeline）                                        │
│  = ProcessDefinition，每个阶段是 Call Activity              │
│                                                             │
│  standard_pipeline:                                         │
│  ○→ [alignment] → ◇gate → [requirement] → ◇gate →          │
│     [design] → ◇gate → [development] → ◇gate →             │
│     [acceptance] → ◇gate → [release] → ⊕                   │
│                                                             │
│  每个 [...] 是 Call Activity，引用阶段级流程                 │
└──────────────────────┬──────────────────────────────────────┘
                       │ call_process_id
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  阶段流程（Workflow）                                        │
│  = ProcessDefinition，每个 step 是 Activity / Gateway       │
│                                                             │
│  requirement_analysis:                                      │
│  ○→ collect → brainstorm → write_prd → review → ◇ → ⊕     │
│                                                             │
│  step 可以引用 Agent 级流程                                  │
└──────────────────────┬──────────────────────────────────────┘
                       │ call_process_id
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Agent 级流程（Procedure）                                   │
│  = ProcessDefinition，由 runtime 驱动                       │
│                                                             │
│  tdd_workflow:                                              │
│  ○→ read_task → write_test → run_red → write_code →        │
│     run_green → refactor → verify → submit → ⊕             │
└─────────────────────────────────────────────────────────────┘

三层都是 ProcessDefinition，格式完全一致。
区别只在于谁驱动执行：
  项目流程 → flow daemon
  阶段流程 → flow daemon
  Agent 流程 → runtime AgentWorkflowEngine
```

### 3.2 阶段定义与 Assistant 的关系

Assistant 的启动流程在私聊空间执行，由 runtime 驱动 Agent 级工作流，不属于 flow。flow 实例在 Assistant 完成启动、创建项目群聊后才创建。

```
Assistant 启动流程（runtime 管理，私聊空间）
        │
        │ 产出 assistant_startup_handoff
        │ 创建项目群聊 + Tech Lead
        │
        ▼
flow 加载项目流程 ProcessDefinition（如 standard_pipeline）
        │
        │ 从 start 事件开始执行
        │
        ▼
○→ [alignment] → ◇ → [requirement] → ◇ → ... → ⊕
```

### 3.4 数据结构（更新）

```python
# Pipeline 不再有独立的数据结构
# 它就是一个 ProcessDefinition，和阶段流程、Agent 流程用同一个类

class ProcessDefinition(BaseModel):
    """BPMN 2.0 流程定义 — 统一表达项目流程/阶段流程/Agent 流程"""
    process_id: str
    name: str
    description: str = ""
    scope: str = "pipeline"           # "pipeline" | "stage" | "agent"

    # 流对象
    nodes: List[FlowNode]             # EventNode | ActivityNode | GatewayNode
    edges: List[FlowEdge]

    # 泳道（可选）
    pool: Optional[Pool] = None

    # 数据（可选）
    data_objects: List[DataObject] = []

    # 制品（可选）
    artifacts: List[FlowArtifact] = []


class ProcessInstance(BaseModel):
    """流程实例 — 运行时状态"""
    instance_id: str
    process_id: str                   # 来自哪个 ProcessDefinition
    project_id: str
    scope: str                        # "pipeline" | "stage" | "agent"
    current_node_id: Optional[str]    # 当前正在执行的节点
    node_states: Dict[str, str]       # {node_id: "pending"|"active"|"completed"|"failed"|"skipped"}
    created_at: datetime
```

> **设计决策记录：去掉 PipelineTemplate / PipelineInstance / StageDefinition**
>
> 原设计中 Pipeline 有独立的数据结构（PipelineTemplate、PipelineInstance、StageDefinition、RollbackRule）。
> 经讨论后统一为 ProcessDefinition：
> - PipelineTemplate → ProcessDefinition(scope="pipeline")
> - StageDefinition → ActivityNode(sub_process_type=CALL_ACTIVITY)
> - gate_type → GatewayNode(gate_config={...})
> - RollbackRule → FlowEdge(flow_type=conditional, label="request_changes")
> - PipelineInstance → ProcessInstance(scope="pipeline")
>
> 好处：整个系统只有一种流程定义格式，从项目级到 Agent 级完全统一。

### 3.7 回退规则

回退不再是独立的 RollbackRule 数据结构，而是 ProcessDefinition 中的 conditional edge：

```
例：acceptance 阶段用户要求修改

gate_after_acceptance 网关有三条出口 edge：
  e13: approve → release
  e14: request_changes → development（回退）

回退时的处理：
  1. 保存当前阶段快照（审计用）
  2. 沿 e14 edge 回到 development 节点
  3. 重新加载 iterative_development ProcessDefinition
  4. 用户意见注入新的 NodeAssignment.action
```

```
例：博客项目验收阶段

用户："标签筛选页面加载太慢，需要优化"
    │
    ▼
gate_after_acceptance
    │ request_changes edge (e14)
    ▼
development（重新激活）
    │
    ▼
flow 创建新任务：TASK-005 优化标签筛选性能
    │
    ▼
iterative_development 流程重新执行
    implement → code_review → testing
```

## 四、阶段级与 Agent 级流程定义

### 4.1 三层流程模型

所有层次都是 ProcessDefinition（nodes + edges），区别在于作用域和驱动者：

```
┌─────────────────────────────────────────────────────────────────┐
│  阶段级流程（flow 驱动，多 Agent 协作）                          │
│                                                                 │
│  iterative_development                                          │

### 4.2 模板格式规范

> **设计决策记录：统一使用 BPMN 2.0 ProcessDefinition 格式**
>
> 所有层次的流程（项目级、阶段级、Agent 级）都使用同一套格式：
> - nodes：节点列表（EventNode / ActivityNode / GatewayNode）
> - edges：边列表（FlowEdge）
> - data_objects：数据对象（可选）
> - artifacts：制品/注释（可选）
> - pool：泳道（可选）
>
> 详细的数据结构定义见第十四章 14.10 BPMN 2.0 完整建模。

```yaml
# ProcessDefinition 统一格式
process_id: string                # 唯一标识
name: string                      # 显示名称
description: string

nodes:                            # 节点列表 — BPMN 三大类
  - id: string
    category: string              # event | activity | gateway
    # event 专属：event_position, event_trigger, ...
    # activity 专属：task_type, actor, action, output_schema, ...
    # gateway 专属：gateway_type, direction, condition_field, routes, ...

edges:                            # 边列表 — 连接线
  - id: string
    flow_type: string             # sequence | conditional | default | message | association
    source: string                # 起始节点 ID
    target: string                # 目标节点 ID
    label: string                 # 线上文字（如 "approved"）
    condition: string             # 条件表达式（conditional 类型时）

data_objects:                     # 数据对象（可选）
  - id: string
    data_type: string             # data_object | data_input | data_output | data_store
    name: string
    attached_to: string           # 关联的节点 ID

artifacts:                        # 制品/注释（可选）
  - id: string
    artifact_type: string         # annotation | group
    text: string
    attached_to: string

pool:                             # 泳道（可选）
  id: string
  name: string
  lanes:
    - id: string
      name: string
      role_id: string
      node_ids: [string]
```

> 完成条件：
> - 阶段级/项目级节点：通过 `output_schema` + `submit_step_result` 工具（LLM function calling 保证格式）
> - Agent 级节点：保留 `done_when`（由 AgentWorkflowEngine 在 runtime 内部判断）
> - 门禁：通过 Gateway + `gate_config`（User Task 等待用户操作）

### 4.4 Agent 级工作流模板（BPMN 2.0 格式）

Agent 级工作流由 runtime 驱动，内部 step 仍保留 done_when（由 AgentWorkflowEngine 判断），但整体结构改为 nodes + edges 格式。

    actor: self
    done_when: [code_written]

    category: activity
    task_type: abstract
    name: "确认测试通过"
    actor: self
    done_when: [test_passed]

    category: activity
    task_type: abstract
    name: "重构"
    actor: self
    done_when: [test_still_passed]

  - id: verify
    category: activity
    task_type: abstract

    actor: self
    done_when: [verification_passed]

    category: activity
    task_type: abstract
    name: "提交交付物"

## 五、flow 与 runtime 的接口

### 5.1 两种 Assignment

flow 下发统一的 NodeAssignment，通过 `mode` 字段区分单人执行和多人协作：

```python
class NodeAssignment(BaseModel):
    """flow → runtime：节点执行分配"""
    assignment_id: str                # 本次分配的唯一 ID
    project_id: str
    process_instance_id: str          # 当前流程实例 ID
    node_id: str                      # 当前节点 ID（ProcessDefinition 中的 node.id）
    mode: str                         # "solo" | "collaboration"

    # ── solo 模式（单人执行）──
    agent_id: Optional[str] = None    # 执行者
    action: Optional[str] = None      # 任务描述（注入 prompt）
    call_process_id: Optional[str] = None  # Agent 级流程 ID（如 tdd_workflow）

    # ── collaboration 模式（多人协作）──
    moderator_id: Optional[str] = None     # 主持人（负责提交结论）
    participant_ids: List[str] = []        # 所有参与者（含主持人）
    agenda: Optional[str] = None           # 议程（注入所有参与者的 prompt）

    # ── 共享字段 ──
    input_refs: List[str] = []        # 输入引用（平台工单 ID、上一步 output 等）
    allowed_tools: List[str] = []     # 节点级工具权限
    output_schema: Optional[dict] = None   # 输出格式（用于 submit_step_result 工具）
    created_at: datetime
```

> **设计决策：统一为一种 NodeAssignment**
>
> 原设计中有 TaskAssignment 和 SessionAssignment 两种结构。经讨论后合并为一种 NodeAssignment，
> 用 `mode` 字段区分。原因：
> - 两种 Assignment 对应的都是 ActivityNode，区别只是执行模式
> - 统一后 runtime 只需要处理一种 Assignment 类型
> - solo 和 collaboration 的共享字段（input_refs、allowed_tools、output_schema）不需要重复定义

### 5.2 统一的 NodeResult

## 六、任务调度与状态机

### 6.1 任务对象模型

任务在不同阶段有不同的形态：

```
阶段 2（设计态）                    阶段 3（运行态）
                                   
平台工单                            TaskInstance
┌──────────────────┐               ┌──────────────────────────────┐
│ TASK-003          │               │ taski-003                     │
│ title: 标签系统   │  ──投影──>    │                               │
│ type: feature     │               │ source_ref: "TASK-003"        │
│ depends_on: [002] │               │ status: ready                 │
│ priority: high    │               │ owner_id: backend-dev-1       │
│                   │               │ reviewer_id: tech-lead        │
│ "应该做什么"      │               │ dependencies:                 │
│                   │               │   upstream: [taski-002]       │
└──────────────────┘               │   external: []                │
                                   │ scope_in: [标签CRUD, 按标签筛选]│
                                   │ scope_out: [标签推荐算法]      │
                                   │ blocker_conditions: []         │
                                   │ wave: 2                        │
                                   │ priority: high                 │
                                   │ reopen_count: 0                │
                                   │                               │
                                   │ "能不能做、谁来做、什么条件"    │
                                   └──────────────────────────────┘
```

**为什么需要 TaskInstance 而不是直接用平台工单？**

平台工单是"应该做什么"，TaskInstance 是"现在能不能做"。同一个工单在不同项目、不同波次、不同团队配置下，调度行为完全不同。TaskInstance 承载的是运行时调度决策所需的全部信息。

### 6.2 TaskInstance 数据结构

```python
class TaskInstance(BaseModel):
    """阶段 3 的核心调度对象"""

    # 标识
    instance_id: str                  # taski-003
    source_ref: str                   # 平台工单 ID（TASK-003）
    task_type: str                    # feature | bugfix | refactor | integration

    # 状态
    status: TaskInstanceStatus
    reopen_count: int = 0             # 区分一次完成和多轮返工

    # 人员
    owner_id: str                     # 主执行者
    reviewer_id: str                  # 主审查者

    # 依赖
    dependencies: TaskDependencies

    # 约束（从阶段 2 继承）
    scope_in: List[str]               # 明确要做什么
    scope_out: List[str]              # 明确不做什么
    blocker_conditions: List[str]     # 满足前不得推进

    # 调度
    wave: int                         # 波次（第几批启动）
    priority: str                     # critical | high | medium | low

    # 工作流
    workflow_instance_id: Optional[str]  # 绑定的 WorkflowInstance


class TaskInstanceStatus(str, Enum):
    DRAFT = "draft"                   # 刚从阶段 2 投影，未就绪
    READY = "ready"                   # 依赖满足，可以启动
    IN_PROGRESS = "in_progress"       # 开发中
    IN_REVIEW = "in_review"           # 审查中
    IN_FIX = "in_fix"                # 审查不通过，修复中（不新建任务）
    IN_VERIFICATION = "in_verification"  # 测试中
    BLOCKED = "blocked"               # 被阻塞（外部依赖等）
    DONE = "done"                     # 完成
    CANCELLED = "cancelled"           # 取消


class TaskDependencies(BaseModel):
    upstream: List[str] = []          # 依赖的其他 TaskInstance ID
    external: List[ExternalDep] = []  # 外部依赖


class ExternalDep(BaseModel):
    dep_id: str                       # 如 "notify-account-ready"
    description: str                  # "正式通知账号开通"
    satisfied: bool = False           # 是否已满足
```

### 6.3 任务状态流转

```
                    ┌──────────────────────────────────────────────────────┐
                    │                                                      │
                    │  ┌───────┐                                           │
                    │  │ draft │  阶段 3 初始化时从平台工单投影              │
                    │  └───┬───┘                                           │
                    │      │ 依赖检查                                      │
                    │      ├── 依赖未满足 ──→ draft（等待）                 │
                    │      ├── 外部依赖未满足 ──→ blocked                   │
                    │      └── 全部满足 ──→ ready                          │
                    │                                                      │
                    │  ┌───────┐                                           │
                    │  │ ready │  可以启动，等待 Agent 空闲                  │
                    │  └───┬───┘                                           │
                    │      │ daemon 分配 NodeAssignment                    │
                    │      ▼                                               │
                    │  ┌─────────────┐                                     │
                    │  │ in_progress │  Agent 执行 implement step          │
                    │  └──────┬──────┘                                     │
                    │         │ Agent submit_step_result                   │
                    │         ▼                                            │
                    │  ┌───────────┐                                       │
                    │  │ in_review │  TL 执行 code_review step             │
                    │  └─────┬─────┘                                       │
                    │        │                                             │
                    │   ┌────┴────┐                                        │
                    │   │         │                                        │
                    │   ▼         ▼                                        │
                    │ 通过      不通过                                      │
                    │   │         │                                        │
                    │   ▼         ▼                                        │
                    │ ┌──────────────────┐  ┌────────┐                    │
                    │ │ in_verification  │  │ in_fix │ reopen_count++     │
                    │ └────────┬─────────┘  └───┬────┘                    │
                    │          │                 │ 修复完成                 │
                    │     ┌────┴────┐            │ 重新进入 in_review      │
                    │     │         │            └──→ in_review            │
                    │     ▼         ▼                                      │
                    │   通过      发现 Bug                                  │
                    │     │         │                                      │
                    │     ▼         └──→ in_fix（同上）                    │
                    │  ┌──────┐                                            │
                    │  │ done │                                            │
                    │  └──────┘                                            │
                    │                                                      │
                    │  任何状态 ──→ cancelled（用户取消）                    │
                    │  任何状态 ──→ blocked（外部依赖突然不满足）            │
                    └──────────────────────────────────────────────────────┘
```

**与旧设计的区别：**

| 旧设计 | 新设计 | 变化原因 |
|--------|--------|---------|
| created → assigned | draft → ready | draft 表示"还不能做"，ready 表示"可以做了" |
| review_rejected | in_fix | 不是新状态，是同一个任务的修复阶段，reopen_count 追踪返工次数 |
| bug_found | in_fix | 同上，测试发现 Bug 也走 in_fix |
| 无 | blocked | 外部依赖不满足时的状态 |
| 无 | in_verification | 区分"审查中"和"测试中" |
| 无 | draft | 区分"刚投影"和"可以启动" |

#### 6.5.3 依赖图构建

```python
class DependencyGraph:
    """任务依赖图"""

    def __init__(self, instances: List[TaskInstance]):
        self.graph: Dict[str, List[str]] = {}    # task_id → [downstream_ids]
        self.in_degree: Dict[str, int] = {}      # task_id → 未满足的依赖数
        self._build(instances)

    def _build(self, instances: List[TaskInstance]):
        """从 TaskInstance 列表构建依赖图"""
        for inst in instances:
            self.in_degree[inst.instance_id] = len(inst.dependencies.upstream)
            for dep in inst.dependencies.upstream:
                self.graph.setdefault(dep, []).append(inst.instance_id)

    def get_ready_tasks(self) -> List[str]:
        """返回所有依赖已满足（in_degree == 0）且状态为 draft 的任务"""
        return [tid for tid, deg in self.in_degree.items() if deg == 0]

    def on_task_completed(self, task_id: str) -> List[str]:
        """任务完成后，更新下游依赖，返回新变为 ready 的任务"""
        newly_ready = []
        for downstream in self.graph.get(task_id, []):
            self.in_degree[downstream] -= 1
            if self.in_degree[downstream] == 0:
                newly_ready.append(downstream)
        return newly_ready
```

#### 6.5.4 调度器核心逻辑

```python
class TaskScheduler:
    """任务调度器 — 事件驱动"""

    def __init__(self, instances: List[TaskInstance], config: ParallelConfig):
        self.dep_graph = DependencyGraph(instances)
        self.config = config
        self.instances = {i.instance_id: i for i in instances}
        self.running_count = 0

    async def initialize(self):
        """阶段 3 初始化：将所有 ready 任务启动"""
        for task_id in self.dep_graph.get_ready_tasks():
            self.instances[task_id].status = TaskInstanceStatus.READY
        await self.dispatch_ready_tasks()

    async def on_event(self, event: NodeResult):
        """每次收到 NodeResult 重新评估调度"""

        # 1. 更新当前任务状态
        instance = self.get_instance(event.assignment_id)
        self.update_status(instance, event)

        # 2. 如果任务完成，检查下游依赖
        if event.result_type == "completed":
            self.running_count -= 1
            newly_ready = self.dep_graph.on_task_completed(instance.instance_id)
            for task_id in newly_ready:
                self.instances[task_id].status = TaskInstanceStatus.READY

        # 3. 如果任务失败，检查是否阻塞下游
        if event.result_type == "failed":
            self.running_count -= 1
            self.mark_downstream_blocked(instance)

        # 4. 调度所有 ready 的任务
        await self.dispatch_ready_tasks()

    async def dispatch_ready_tasks(self):
        """调度所有 ready 且有空闲 Agent 的任务"""
        for task in self.get_ready_tasks():
            if self.running_count >= self.config.max_parallel_tasks:
                break
            agent = self.find_available_agent(task)
            if agent:
                task.status = TaskInstanceStatus.IN_PROGRESS
                self.running_count += 1
                await self.dispatch(task, agent)
```

class TaskProvider(ABC):
    @abstractmethod
    async def create(self, task: TaskCreate) -> str:
        """创建任务，返回任务 ID"""

    @abstractmethod
    async def read(self, task_id: str) -> TaskDetail:
        """读取任务详情"""

    @abstractmethod
    async def update(self, task_id: str, changes: TaskUpdate) -> None:
        """更新任务（状态、assignee、交付物等）"""

    @abstractmethod
    async def query(self, filters: TaskQuery) -> List[TaskSummary]:
        """查询任务列表"""

    @abstractmethod
    async def on_change(self, callback: Callable) -> None:
        """监听任务变更事件（状态流转时通知 flow）"""
```

## 七、三种交互模式

现实开发中，团队协作有三种本质不同的活动。我们的架构需要分别建模，而不是用统一的"消息路由"混在一起。

### 7.1 三种模式总览

```
┌─────────────────────────────────────────────────────────────┐
│  模式 1：任务执行（Task Execution）                          │
│                                                             │
│  flow 分配任务 → Agent 独立执行 → 上报结果                   │
│                                                             │
│  现实类比：开发者在工位上写代码                               │
│  特征：一对一、异步、结构化输入输出                           │
├─────────────────────────────────────────────────────────────┤
│  模式 2：协作会议（Collaboration Session）                    │
│                                                             │
│  daemon 发起会议 → 多人参与讨论 → 主持人总结结论              │
│                                                             │
│  现实类比：需求评审会、设计评审会                             │
│  特征：多对多、同步、有主持人和议程、有明确结论               │
├─────────────────────────────────────────────────────────────┤
│  模式 3：即时沟通（Instant Messaging）                       │
│                                                             │
│  Agent 执行任务时遇到问题 → @某人问一句 → 得到回答 → 继续    │
│                                                             │
│  现实类比：Slack 里 @同事问一个问题                          │
│  特征：一对一、异步、非结构化、无明确结束                     │
└─────────────────────────────────────────────────────────────┘
```

| | 任务执行 | 协作会议 | 即时沟通 |
|---|---------|---------|---------|
| 参与者 | 1 个 Agent | 多个 Agent + 用户 | 2 个 Agent |
| 触发 | flow 分配 step | flow 发起 session step | Agent 调用工具 |
| 结束 | Agent submit_step_result | 主持人 submit_step_result | 对方回复 |
| 产出 | 结构化（output_schema） | 结构化（会议结论） | 非结构化（自然语言） |
| 归属 | flow 调度 + runtime 执行 | flow 管理 + runtime 执行 | runtime 工具 + flow 路由 |
| 是否是 step | 是 | 是 | 不是 |

|------|------|------|
| 阶段边界 | 从一个阶段进入下一个阶段时 | requirement → design：用户确认 PRD |
| step 内部 | 某些 step 的结果需要用户确认 | user_acceptance：用户验收功能 |

### 8.2 门禁类型

| 类型 | 说明 | 示例 |
|------|------|------|
| hard | 必须用户操作确认 | 阶段 1→2 用户确认 PRD，阶段 4→5 用户最终确认 |
| soft | 默认自动通过，可配置为需要确认 | 阶段 2→3 设计评审 |

> **设计决策记录：去掉 done_when 和 output_schema 作为门禁类型**
>
> 原设计中 done_when 和 output_schema 也列为门禁类型。经讨论后：
> - done_when 已被 output_schema + submit_step_result 工具替代（见第四章）
> - output_schema 的校验由 LLM function calling 在工具调用时保证，不是门禁
> - 门禁只指"需要人类操作确认"的环节，系统自动校验不算门禁

### 8.3 数据结构

```python
class GateRequest(BaseModel):
    """审批请求"""
    gate_id: str                      # 唯一 ID
    project_id: str
    gate_type: str                    # "hard" | "soft"
    trigger_point: str                # "stage_transition" | "step_completion"

    # 审批上下文
    title: str                        # "需求评审确认" / "用户验收"
    description: str                  # 审批说明
    artifacts: List[GateArtifact]     # 需要审阅的产物列表

    # 来源信息
    from_stage: Optional[str]         # 阶段边界时：当前阶段
    to_stage: Optional[str]           # 阶段边界时：目标阶段
    node_id: Optional[str]            # 节点内审批时：哪个节点
    step_output: Optional[dict]       # step 内审批时：step 的输出

    # 状态
    status: str                       # "pending" | "approved" | "rejected"
                                      # | "changes_requested" | "expired"
    requested_at: datetime
    responded_at: Optional[datetime]
    timeout_minutes: Optional[int]    # 超时时间（分钟），null 表示不超时
    responded_by: Optional[str]       # 审批人
    comment: Optional[str]            # 审批意见（驳回/修改时必填）


class GateArtifact(BaseModel):
    """审批产物 — 用户需要审阅的内容"""
    name: str                         # "PRD 文档" / "集成测试报告"
    type: str                         # "document" | "test_report" | "demo" | "code_diff"
    ref: str                          # 引用（platform ID、平台工单 ID、URL 等）
    summary: Optional[str]            # 摘要（方便用户快速了解）
```

### 8.6 审批流程

```
某个条件触发审批（阶段完成 / step 需要确认）
    │
    ▼
flow 生成 GateRequest
    │
    ├── gate_type == soft？
    │   ├── 项目配置要求确认？
    │   │   ├── 不要求 → 自动 approve，记录历史，继续
    │   │   └── 要求 → 同 hard
    │   └──
    │
    ├── gate_type == hard
    │   │
    │   ▼
    │   生成 GateCard，通过 chat API 发送给用户
    │   │
    │   ▼
    │   等待用户操作...
    │   │
    │   ├── approve（确认通过）
    │   │   → 记录门禁通过历史
    │   │   → 推进到下一阶段 / 下一 step
    │   │
    │   ├── request_changes（需要修改）
    │   │   → 记录用户意见
    │   │   → 回退到指定 step（如 write_prd）
    │   │   → 用户意见作为新的输入注入 Agent prompt
    │   │
    │   ├── reject（驳回）
    │   │   → 记录驳回原因
    │   │   → 回退到更早的阶段（如 requirement → 重新收集需求）
    │   │
    │   └── 超时（timeout_minutes 到期）
    │       → status = expired
    │       → 通知用户"审批已过期"
    │       → 项目状态 → suspended
    │       → 用户下次回来时可重新触发审批
    │
    ▼
记录到 gate_history.yaml（审计用）
```

### 8.7 用户操作后的处理

**approve — 确认通过：**

```
用户点击"确认通过"
    │
    ▼
flow 更新 GateRequest.status = "approved"
    │
    ▼
记录到 gate_history.yaml:
    gate_id: gate-00012
    gate_type: hard
    trigger_point: stage_transition
    from_stage: requirement
    to_stage: design
    status: approved
    responded_by: user
    responded_at: 2026-04-18T14:00:00Z
    │
    ▼
推进到 design 阶段
    加载 design_and_planning 工作流模板
    触发第一个 step
```

**request_changes — 需要修改：**

```
用户点击"需要修改"，填写意见：
    "评论功能不需要 WebSocket，用轮询就行"
    │
    ▼
flow 更新 GateRequest.status = "changes_requested"
    │
    ▼
flow 决定回退目标：
    阶段边界审批 → 回退到当前阶段的指定 step
    step 内审批 → 回退到当前 step 的 on_fail
    │
    ▼
重新下发 NodeAssignment：
    action 中追加用户意见：
    "用户反馈：评论功能不需要 WebSocket，用轮询就行。
     请根据此反馈修改 PRD。"
    │
    ▼
Agent 根据用户意见修改产出
    │
    ▼
修改完成后重新触发审批
```

**reject — 驳回：**

```
用户点击"驳回"，填写原因：
    "这个方向不对，我不想做博客了，想做电商"
    │
    ▼
flow 更新 GateRequest.status = "rejected"
    │
    ▼
flow 根据 pipeline 回退规则决定回退到哪个阶段
    （通常回退到更早的阶段，如 requirement 甚至 alignment）
    │
    ▼
保存当前阶段快照（审计用）
清理当前阶段的临时状态
加载目标阶段的工作流模板
```

**expired — 超时：**

```
timeout_minutes 到期，用户未操作
    │
    ▼
flow 更新 GateRequest.status = "expired"
    │
    ▼
通过 chat 发送提醒：
    "📋 需求评审确认已过期（72 小时未操作）。
     项目已暂停，回复 /resume 可重新触发审批。"
    │
    ▼
项目状态 → suspended
    │
    ▼
用户下次回来：
    /resume → flow 重新生成 GateRequest → 发送新的审批卡片
```

### 8.8 各阶段的门禁配置

定义在 Pipeline Template 中：

```yaml

## 十三、设计决策记录

### 13.1 Agent 级工作流命名讨论

> **状态：待定，暂不修改**
>
> 当前 Agent 级工作流使用 `scope: "agent"`，存放在 `workflow_templates/agent/` 目录下，项目级 step 通过 `workflow` 字段引用。
>
> 讨论中提出：项目级和 Agent 级都叫 workflow 看起来混淆。现实开发中两者的叫法不同：
>
> - 项目级：流程（Process / Workflow）— 多人协作，关注谁做什么、什么顺序、什么门禁
> - Agent 级：规程（Procedure / Practice）— 单人执行，关注怎么做、什么步骤、什么规范
>
> 如果采纳，变更范围：
>
> ```
> scope: "agent"              → scope: "procedure"
> workflow_templates/agent/   → procedure_templates/
> step.workflow: tdd_workflow  → step.procedure: tdd
> ```
>
> 暂不修改的原因：当前格式统一（同一套 YAML 结构），改名涉及 flow 和 runtime 两侧文档同步更新，等核心设计稳定后再评估。

### 13.2 移除 exit_conditions / entry_requirements

> **状态：已采纳**
>
> 原设计中 StageTransition 包含 `exit_conditions` 和 `entry_requirements` 字段。移除原因：
> - 与工作流模板中 step 的 done_when 重复检查
> - 自然语言字符串，系统无法自动校验
> - "用户已确认"是 gate_type: hard 的职责
>
> 简化后：所有 step completed + gate passed = 进入下一阶段。

### 13.3 移除 ProjectStage 硬编码枚举

> **状态：已采纳**
>
> 原设计中阶段是 Python 枚举（STAGE_0 ~ STAGE_5）。改为配置驱动的 PipelineTemplate，原因：
> - 不同项目类型需要不同阶段数量（standard 6 个，hotfix 3 个）
> - 无法加减阶段
> - 与"流程模板可配置、可裁剪"的设计原则矛盾

## 十四、流程引擎抽象层设计

### 14.1 设计目标

Phase 1 先实现 BPMN 2.0 Level 1（描述性建模）子集，保留抽象层方便 Phase 2 扩展到 Level 2/3。

核心原则：
- 引擎只依赖抽象接口，不依赖具体节点类型
- 新增节点类型只需实现接口 + 注册，不改引擎代码
- ISO 5807 的符号是 BPMN 2.0 的子集，不需要单独适配

### 14.2 抽象层架构

```
                    ┌─────────────────────────┐
                    │   FlowNode (抽象基类)    │
                    │                         │
                    │   id: str               │
                    │   type: NodeType        │
                    │   name: str             │
                    │   status: NodeStatus    │
                    │                         │
                    │   accept(visitor)       │  ← 访问者模式
                    │   validate()            │  ← 校验自身合法性

### 14.6 引擎核心：NodeVisitor + NodeExecutor

```python
class NodeVisitor(ABC):
    """访问者接口 — 引擎通过此接口处理不同类型的节点"""

    @abstractmethod
    async def visit_task(self, node: TaskNode) -> NodeStatus:
        """处理任务节点：下发 NodeAssignment，等待 NodeResult"""

    @abstractmethod
    async def visit_session(self, node: SessionNode) -> NodeStatus:
        """处理会议节点：下发 NodeAssignment，等待主持人提交"""

    @abstractmethod
    async def visit_decision(self, node: DecisionNode) -> str:
        """处理判断节点：评估条件，返回目标节点 ID"""

    @abstractmethod
    async def visit_gate(self, node: DecisionNode) -> str:
        """处理门禁节点：发送审批卡片，等待用户操作，返回目标节点 ID"""

    @abstractmethod
    async def visit_fork(self, node: ParallelNode) -> List[str]:
        """处理并行分支：返回所有分支的起始节点 ID"""

    @abstractmethod
    async def visit_join(self, node: ParallelNode) -> NodeStatus:
        """处理并行合并：等待所有/任一分支完成"""

    @abstractmethod
    async def visit_event(self, node: EventNode) -> NodeStatus:
        """处理事件节点：等待事件触发或超时"""


class FlowEngine:
    """流程引擎 — 只依赖抽象接口"""

    def __init__(self, visitor: NodeVisitor):
        self.visitor = visitor

    async def execute(self, workflow: WorkflowInstance):
        """执行工作流实例"""
        current = self.get_start_node(workflow)

        while current:
            current.status = NodeStatus.RUNNING

            # 通过访问者模式分派到具体处理逻辑
            result = await current.accept(self.visitor)

            if isinstance(result, NodeStatus):
                current.status = result
                if result == NodeStatus.COMPLETED:
                    current = self.get_next_node(workflow, current)
                elif result == NodeStatus.FAILED:
                    current = self.get_fail_node(workflow, current)
                else:
                    break  # BLOCKED, CANCELLED 等
            elif isinstance(result, str):
                # decision/gate 返回目标节点 ID
                current.status = NodeStatus.COMPLETED
                current = self.get_node_by_id(workflow, result)
            elif isinstance(result, list):
                # fork 返回分支列表，并行执行
                current.status = NodeStatus.COMPLETED
                await self.execute_parallel(workflow, result)
                current = self.get_next_node(workflow, current)
```

### 14.7 Phase 1 实现范围

Phase 1 只实现 `TaskNodeExecutor` 和 `SessionNodeExecutor`：

```python
class Phase1Visitor(NodeVisitor):
    """Phase 1 实现 — 只处理 task 和 session"""

    async def visit_task(self, node: TaskNode) -> NodeStatus:
        # 构造 NodeAssignment，下发给 runtime
        assignment = NodeAssignment(
            node_id=node.id,
            agent_id=self.resolve_actor(node.actor),
            action=node.action,
            input_refs=node.input_refs,
            allowed_tools=node.allowed_tools,
            workflow=node.workflow,
            output_schema=node.output_schema,
        )
        event = await self.runtime_client.send_assignment(assignment)
        if event.result_type == "completed":
            return NodeStatus.COMPLETED
        elif event.result_type == "blocked":
            return NodeStatus.BLOCKED
        else:
            return NodeStatus.FAILED

    async def visit_session(self, node: SessionNode) -> NodeStatus:
        # 构造 NodeAssignment，下发给 runtime
        assignment = NodeAssignment(
            node_id=node.id,
            moderator_id=self.resolve_actor(node.moderator),
            participant_ids=[self.resolve_actor(p) for p in node.participants],
            agenda=node.agenda,
            allowed_tools=node.allowed_tools,
            output_schema=node.output_schema,
        )
        event = await self.runtime_client.send_assignment(assignment)
        if event.result_type == "completed":
            return NodeStatus.COMPLETED
        else:
            return NodeStatus.FAILED

    # Phase 2 才实现的方法，Phase 1 抛出 NotImplementedError
    async def visit_decision(self, node): raise NotImplementedError("Phase 2")
    async def visit_gate(self, node): raise NotImplementedError("Phase 2")
    async def visit_fork(self, node): raise NotImplementedError("Phase 2")
    async def visit_join(self, node): raise NotImplementedError("Phase 2")
    async def visit_event(self, node): raise NotImplementedError("Phase 2")
```

Phase 2 扩展时，只需实现新的 visitor 方法，不改 FlowEngine 代码：

```
Phase 1 → Phase 2 扩展路径：

1. 实现 visit_decision → 支持条件分支
2. 实现 visit_gate → 支持 step 间门禁
3. 实现 visit_fork / visit_join → 支持并行
4. 实现 visit_event → 支持等待外部事件

FlowEngine.execute() 不需要任何修改。
```

### 14.10 BPMN 2.0 完整建模

> **设计决策：全部转为 BPMN 2.0 建模**
>
> 原设计中 NodeType 混合了 ISO 5807 和 BPMN 2.0 两套标准的符号。
> 经讨论后决定全部转为 BPMN 2.0，原因：
> - ISO 5807 的符号是 BPMN 2.0 的子集，不需要单独保留
> - BPMN 2.0 有更丰富的事件、网关、任务类型，覆盖我们的全部场景
> - BPMN 2.0 有三层建模体系（描述/分析/可执行），天然支持 Phase 分期
>
> 去掉的 ISO 5807 独有类型：PREPARATION、IO、DOCUMENT、MULTI_DOCUMENT、DATA_STORE、CONNECTOR、MANUAL
> 这些在 BPMN 2.0 中有更好的替代（Task 子类型、Data Object、Link Event 等）

class GatewayNode(FlowNode):

```

**与原设计的映射：**

| 原 NodeType | BPMN 2.0 对应 | 新的表达方式 |
|-------------|---------------|-------------|
| DECISION | Exclusive Gateway | GatewayNode(gateway_type=EXCLUSIVE) |
| GATE | Exclusive Gateway + gate_config | GatewayNode(gateway_type=EXCLUSIVE, gate_config={...}) |
| FORK | Parallel Gateway (diverging) | GatewayNode(gateway_type=PARALLEL, direction=DIVERGING) |
| JOIN | Parallel Gateway (converging) | GatewayNode(gateway_type=PARALLEL, direction=CONVERGING) |

**Phase 分期：**

| 网关 | Phase | 说明 |
|------|-------|------|
| Exclusive (XOR) | Phase 1 | 条件分支 + 门禁 |
| Parallel (AND) | Phase 2 | 多任务并行 |
| Inclusive (OR) | Phase 3 | 多条件并行选择 |
| Event-based | Phase 3 | 等待事件决定走哪条路 |
| Complex | Phase 3 | 自定义逻辑 |

**博客项目例子 — 三种网关对比：**

```
排他网关 (XOR) — 代码审查结果：

                    ◇ XOR
                   ╱ ╲
        approved  ╱   ╲  needs_revision
                ╱     ╲
               ▼       ▼
           testing   implement（打回修改）


并行网关 (AND) — 多任务并行开发：

            ◇+ AND (diverging)
           ╱  │  ╲
          ╱   │   ╲
         ▼    ▼    ▼
      TASK  TASK  TASK
      001   002   004
         ╲    │   ╱
          ╲   │  ╱
           ▼  ▼ ▼
           ◇+ AND (converging)
              │
              ▼
        集成测试


包含网关 (OR) — 根据项目类型决定需要哪些角色（Phase 3）：

                    ◇○ OR (diverging)
                   ╱  │  ╲
     has_frontend ╱   │   ╲ has_mobile
                ╱    │    ╲
               ▼     │     ▼
          拉前端开发  │  拉移动开发
               ╲     │    ╱
                ╲    │   ╱
                 ▼   ▼  ▼
                ◇○ OR (converging)
                    │
                    ▼
               继续流程

  如果 has_frontend 且 has_mobile，两条路都走
  如果只有 has_frontend，只走一条
```

#### 14.10.4 连接对象（Connecting Objects）

```python
class FlowType(str, Enum):
    """连接线类型 — 对应 BPMN 2.0 三种连接线"""
    SEQUENCE = "sequence"             # ──────>  顺序流（实线箭头）
    CONDITIONAL = "conditional"       # ──◇───>  条件顺序流（实线+菱形）
    DEFAULT = "default"               # ──/───>  默认顺序流（实线+斜线）
    MESSAGE = "message"               # ─ ─ ─>   消息流（虚线空心箭头）
    ASSOCIATION = "association"        # ·····>   关联（点线）
    DATA_ASSOCIATION = "data_assoc"   # ····<>   数据关联（点线双向）


class FlowEdge(BaseModel):
    """连接线"""
    id: str
    flow_type: FlowType
    source: str                       # 起始节点 ID
    target: str                       # 目标节点 ID
    label: Optional[str] = None       # 线上的文字
    condition: Optional[str] = None   # 条件表达式（CONDITIONAL 类型时）
```

**与原设计的映射：**

| 原 EdgeType | BPMN 2.0 对应 | 说明 |
|-------------|---------------|------|
| SEQUENCE | Sequence Flow | 不变 |
| CONDITIONAL | Conditional Sequence Flow | 不变 |
| ON_FAIL | Conditional Sequence Flow (label="fail") | 合并为条件流 |
| ON_APPROVE | Conditional Sequence Flow (label="approve") | 合并为条件流 |
| ON_REJECT | Conditional Sequence Flow (label="reject") | 合并为条件流 |
| FORK_BRANCH | Sequence Flow (from Parallel GW) | 不需要独立类型 |
| JOIN_BRANCH | Sequence Flow (to Parallel GW) | 不需要独立类型 |
| — | Default Sequence Flow | 新增 |
| — | Message Flow | 新增（Phase 3） |
| — | Association | 新增（注释连接） |
| — | Data Association | 新增（数据关联） |

#### 14.10.10 原 NodeType 到 BPMN 2.0 的完整迁移表

| 原 NodeType | BPMN 2.0 表达 | 类别 | Phase |
|-------------|---------------|------|-------|
| START | EventNode(position=START, trigger=NONE) | Event | Phase 1 |
| END | EventNode(position=END, trigger=NONE) | Event | Phase 1 |
| TASK | ActivityNode(task_type=ABSTRACT) | Activity | Phase 1 |
| SESSION | ActivityNode(sub_process_type=AD_HOC, session={...}) | Activity | Phase 1 |
| SUB_PROCESS | ActivityNode(sub_process_type=CALL_ACTIVITY) | Activity | Phase 2 |
| DECISION | GatewayNode(gateway_type=EXCLUSIVE) | Gateway | Phase 1 |
| GATE | GatewayNode(gateway_type=EXCLUSIVE, gate_config={...}) | Gateway | Phase 1 |
| FORK | GatewayNode(gateway_type=PARALLEL, direction=DIVERGING) | Gateway | Phase 2 |
| JOIN | GatewayNode(gateway_type=PARALLEL, direction=CONVERGING) | Gateway | Phase 2 |
| EVENT | EventNode(position=INTERMEDIATE, trigger=...) | Event | Phase 2/3 |
| PREPARATION | ActivityNode(task_type=ABSTRACT, tag="preparation") | Activity | 去掉 |
| IO | DataObject(data_type=DATA_OBJECT) | Data | 去掉 |
| DOCUMENT | DataObject(data_type=DATA_OBJECT) | Data | 去掉 |
| MULTI_DOCUMENT | DataObject(data_type=DATA_COLLECTION) | Data | 去掉 |
| DATA_STORE | DataObject(data_type=DATA_STORE) | Data | 去掉 |
| CONNECTOR | EventNode(trigger=LINK) | Event | 去掉 |
| MANUAL | ActivityNode(task_type=MANUAL) | Activity | 去掉 |

> "去掉"指不再作为独立 NodeType，而是用 BPMN 2.0 的标准方式表达。
> 可视化时仍然可以根据 task_type / data_type 渲染对应的 ISO 5807 图形。

# 并行多实例 — 同时创建多个实例（Phase 2）
- id: parallel_tasks

#### 14.10.12 BPMN 2.0 YAML 配置格式 — 网关（Gateways）

##### Exclusive Gateway — 排他网关 XOR（Phase 1）

只走一条分支，评估条件，走第一个为真的。

```yaml
- id: review_decision
  category: gateway
  gateway_type: exclusive           # ◇ XOR
  direction: diverging              # 分支
  name: "代码审查结果判断"
  condition_field: code_review.output.verdict
  routes:
    approved: testing
    needs_revision: implement
  default: implement                # 所有条件都不满足时
```

```yaml
# 合并用法（多条分支汇入一个点）
- id: review_merge
  category: gateway
  gateway_type: exclusive
  direction: converging             # 合并
  name: "审查结果汇合"
```

```
例：博客项目 — 代码审查后

  ┌──────────────┐
  │ code_review  │
  └──────┬───────┘
         │ output.verdict
         ▼
         ◇ XOR (review_decision)
        ╱ ╲
approved╱   ╲needs_revision
      ╱     ╲
     ▼       ▼
  testing   implement（打回修改）
```

##### Exclusive Gateway + gate_config — 门禁（Phase 1）

门禁是排他网关的特例：条件来源不是上一步的 output，而是用户的操作。

```yaml
- id: prd_approval
  category: gateway
  gateway_type: exclusive
  direction: diverging
  name: "PRD 审批"
  gate_config:                      # 非空 = 这是门禁型网关
    title: "需求评审确认"
    gate_type: hard
    timeout_minutes: 4320
    artifacts_from: [write_prd]
    actions:
      - { action_type: approve, label: "确认通过" }
      - { action_type: request_changes, label: "需要修改" }
      - { action_type: reject, label: "驳回" }
  routes:
    approve: design_stage
    request_changes: write_prd
    reject: end_rejected
```

```
例：博客项目 — 用户确认 PRD

  ┌──────────────┐
  │ write_prd    │
  └──────┬───────┘
         │
         ▼
         ◇👤 XOR + gate (prd_approval)
        ╱ │ ╲
approve╱  │  ╲reject
      ╱   │   ╲
     ▼    ▼    ▼
  design  write  end
  stage   _prd   rejected
       (request
        changes)
```

##### Parallel Gateway — 并行网关 AND（Phase 2）

所有分支同时执行，等全部完成后合并。

```yaml
# 分支
- id: parallel_dev_start
  category: gateway
  gateway_type: parallel            # ◇+ AND
  direction: diverging
  name: "多任务并行开发"
  branches: [task_001, task_002, task_004]

# 合并
- id: parallel_dev_end
  category: gateway
  gateway_type: parallel
  direction: converging
  name: "等待所有任务完成"
  join_policy: all                  # all = 等全部完成
```

```
例：博客项目 — 多任务并行

         ◇+ AND (diverging)
        ╱  │  ╲
       ╱   │   ╲
      ▼    ▼    ▼
   TASK  TASK  TASK
   001   002   004
      ╲    │   ╱
       ╲   │  ╱
        ▼  ▼ ▼
        ◇+ AND (converging)
           │
           ▼
     integration_test
```

##### Inclusive Gateway — 包含网关 OR（Phase 3）

走一条或多条分支，评估所有条件，走所有为真的。

```yaml
# 分支
- id: role_expansion
  category: gateway
  gateway_type: inclusive           # ◇○ OR
  direction: diverging
  name: "根据项目类型扩展角色"
  conditions:
    - condition: "project.has_frontend == true"
      target: add_frontend_dev
    - condition: "project.has_mobile == true"
      target: add_mobile_dev
    - condition: "project.needs_devops == true"
      target: add_devops
  default: skip_expansion

# 合并
- id: role_expansion_end
  category: gateway
  gateway_type: inclusive
  direction: converging
  name: "角色扩展完成"
```

```
例：博客项目（has_frontend=true, has_mobile=false）

         ◇○ OR (diverging)
        ╱  │  ╲
  前端 ╱   │   ╲ 移动端
  true╱    │    ╲false
     ▼     │     ╳ (不走)
  拉前端   │
  开发     │ DevOps
           │ true
           ▼
        拉 DevOps
     ╲     │
      ╲    │
       ▼   ▼
       ◇○ OR (converging)
          │
          ▼
       继续流程
```

##### Event-based Gateway — 事件网关（Phase 3）

等待事件，第一个到达的事件决定走哪条路。

```yaml
- id: wait_response
  category: gateway
  gateway_type: event_based         # ◇⚡ 事件网关
  direction: diverging
  name: "等待用户回复或超时"
  event_routes:
    - event_type: message
      message_ref: user_reply
      target: process_reply
    - event_type: timer
      timer_duration: "PT72H"       # 72 小时
      target: timeout_handler
```

```
例：博客项目 — 等待用户确认或超时

         ◇⚡ Event-based
        ╱     ╲
  用户回复╱     ╲72h 超时
        ╱       ╲
       ▼         ▼
  处理回复    超时处理
             (项目暂停)
```

##### Complex Gateway — 复杂网关（Phase 3）

自定义分支/合并逻辑，用于上述网关都无法表达的场景。

```yaml
- id: complex_merge
  category: gateway
  gateway_type: complex             # ◇* 复杂网关
  direction: converging
  name: "自定义合并逻辑"
  complex_condition: "任意 2 个分支完成即可继续"
  # 具体表达式语法待 Phase 3 定义
```

```
记录：Phase 3 评估是否需要。
大多数场景可以用 Exclusive + Parallel + Inclusive 组合表达。
```

##### 网关类型汇总

| 网关类型 | YAML gateway_type | Phase | 我们的场景 |
|---------|-------------------|-------|-----------|
| Exclusive (XOR) | exclusive | Phase 1 | 条件分支（审查通过/不通过） |
| Exclusive + gate_config | exclusive + gate_config | Phase 1 | 门禁（用户审批） |
| Parallel (AND) | parallel | Phase 2 | 多任务并行开发 |
| Inclusive (OR) | inclusive | Phase 3 | 根据条件走多条路（角色扩展） |
| Event-based | event_based | Phase 3 | 等待事件决定走哪条路 |
| Complex | complex | Phase 3 | 自定义逻辑 |

#### 14.10.14 BPMN 2.0 YAML 配置格式 — 连接对象（Connecting Objects）

##### Sequence Flow — 顺序流（Phase 1）

```yaml
edges:
  # 普通顺序流
  - id: e1
    flow_type: sequence             # ──────> 实线箭头
    source: collect
    target: brainstorm

  # 条件顺序流
  - id: e2
    flow_type: conditional          # ──◇───> 实线+菱形
    source: review_decision
    target: testing
    label: "approved"
    condition: "verdict == 'approved'"

  # 默认顺序流
  - id: e3
    flow_type: default              # ──/───> 实线+斜线
    source: review_decision
    target: implement
    label: "default"
```

例：博客项目 — 代码审查后的三条线

  ┌──────────────┐

         ▼
         ◇ review_decision
        ╱ ╲
  ──◇──╱   ╲──◇──     条件顺序流（有菱形标记）
approved╱     ╲needs_revision
      ╱       ╲
     ▼    ──/──▼        默认顺序流（有斜线标记）
  testing   implement

```yaml

#### 14.10.17 我们对 BPMN 2.0 的扩展

BPMN 2.0 标准允许扩展（Extension Elements），以下是我们需要的三个扩展点。

##### 扩展 1：session（协作会议）— Ad-Hoc Sub-Process 的扩展

**为什么需要扩展：**

BPMN 的 Ad-Hoc Sub-Process 内部是预定义的独立活动，执行者选择做哪些、做几次。
我们的 session 是多人共享上下文的实时对话，参与者能看到彼此说了什么并回应。

```
BPMN Ad-Hoc 的执行方式（独立活动，互相看不到）：

  ┌─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
  │ brainstorm                                 ~  │
  │                                               │
  │  ┌─👤────────┐  ┌─👤────────┐  ┌─👤────────┐│
  │  │ BE 发言   │  │ FE 发言   │  │ QA 发言   ││
  │  │ (独立)    │  │ (独立)    │  │ (独立)    ││
  │  │ 看不到    │  │ 看不到    │  │ 看不到    ││
  │  │ 别人说的  │  │ 别人说的  │  │ 别人说的  ││
  │  └──────────┘  └──────────┘  └──────────┘ │
  └─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘

  BE 不知道 FE 说了什么，FE 不知道 QA 说了什么。


我们的 session 的执行方式（共享上下文的实时对话）：

  ┌─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐
  │ brainstorm                                 ~  │
  │                                               │
  │  BE: "标签建议用多对多关联表"                   │
  │  FE: "同意，评论建议用 WebSocket"  ← 看到 BE  │
  │  QA: "WebSocket 要考虑 XSS"       ← 看到 FE  │
  │  BE: "好的，我加个 sanitize"       ← 回应 QA  │
  │  TL: "总结一下..."                ← 看到全部  │
  └─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘

  所有人共享同一个对话上下文。
```

**实现方式：Ad-Hoc Sub-Process + session 扩展属性**

在 BPMN 的 Ad-Hoc Sub-Process 基础上，增加 `session` 扩展属性：

```yaml
- id: brainstorm
  category: activity
  sub_process_type: ad_hoc
  name: "团队头脑风暴"
  # BPMN 标准属性
  ordering: parallel
  completion_condition: "moderator_submitted == true"
  # 我们的扩展属性
  session:
    moderator: tech_lead
    participants: [tech_lead, backend_dev, frontend_dev, tester]
    agenda: "讨论需求的可行性、风险和建议"
    interaction_mode: shared_context    # 共享上下文（区别于 BPMN 的独立活动）
  output_schema:
    type: object
    properties:
      suggestions: { type: array, items: { type: string } }
      risks: { type: array, items: { type: string } }
      decisions: { type: array, items: { type: string } }
    required: [suggestions, decisions]
```

**引擎处理逻辑：**

```
引擎遇到 Ad-Hoc Sub-Process 节点
    │
    ├── 有 session 扩展属性？
    │   │
    │   ├── 是 → 走 session 模式
    │   │       生成 NodeAssignment
    │   │       激活所有 participants
    │   │       开启共享上下文对话
    │   │       moderator 调用 submit_step_result 结束
    │   │
    │   └── 否 → 走标准 BPMN Ad-Hoc 模式
    │           内部活动独立执行
    │           completionCondition 满足时结束
```

**与标准 BPMN 的兼容性：**

| 维度 | 标准 BPMN Ad-Hoc | 我们的 session |
|------|-----------------|---------------|
| 容器类型 | Ad-Hoc Sub-Process | 同（sub_process_type: ad_hoc） |
| ordering | parallel / sequential | parallel（固定） |
| completionCondition | 表达式 | moderator_submitted == true |
| 内部活动 | 预定义的 Task 列表 | 无（自由对话） |
| 扩展属性 | 无 | session: {moderator, participants, agenda, interaction_mode} |
| 可视化 | 标准 Ad-Hoc 图形（波浪底线） | 同 + 参与者头像标注 |

如果导出为标准 BPMN XML，session 属性放在 `<extensionElements>` 里，
不影响标准 BPMN 工具的解析（会忽略扩展属性，显示为普通 Ad-Hoc Sub-Process）。

##### 扩展 2：NodeAssignment — 引擎到执行者的通信协议

**为什么需要扩展：**

BPMN 2.0 定义了流程的建模语义，但没有定义引擎和执行者之间的通信协议。
标准 BPMN 引擎（如 Camunda、Activiti）通过 Java API 或 REST API 分配任务，
但具体的 payload 格式是引擎实现自定义的，不在 BPMN 标准范围内。

```
标准 BPMN 引擎（如 Camunda）：

  引擎                              执行者
    │                                  │
    │  Camunda REST API                │
    │  POST /task/{id}/complete        │
    │  body: { variables: {...} }      │
    │ ──────────────────────────────>  │
    │                                  │
    │  自定义的 payload 格式            │
    │  不在 BPMN 标准里                │


我们的系统：

  flow                              runtime
    │                                  │
    │  NodeAssignment
    │  { assignment_id, node_id,       │
    │    agent_id, action,             │
    │    allowed_tools, output_schema } │
    │ ──────────────────────────────>  │
    │                                  │
    │  NodeResult                       │
    │  { result_type, output }          │
    │ <──────────────────────────────  │
```

**这不是对 BPMN 的"违反"，而是 BPMN 标准本身不覆盖的领域。**
所有 BPMN 引擎都有自己的任务分配协议，我们的 NodeAssignment/NodeAssignment 就是我们的协议。

##### 扩展 3：submit_step_result — 动态注册的完成工具

**为什么需要扩展：**

标准 BPMN 引擎中，任务完成是通过 API 调用（如 `completeTask(taskId, variables)`）。
我们的执行者是 LLM Agent，不能调 API，只能调工具（function calling）。

```
标准 BPMN 引擎：

  人类用户在表单里填写数据 → 点击"提交" → 调用 completeTask API


我们的系统：

  LLM Agent 执行 think→act 循环
    → LLM 决定调用 submit_step_result 工具
    → function calling 保证参数格式符合 output_schema
    → runtime 收到工具调用，构造 NodeResult 上报给 flow
```

**submit_step_result 本质上就是 BPMN 的 completeTask，只是调用方式不同：**

| | 标准 BPMN | 我们的系统 |
|---|-----------|----------|
| 调用者 | 人类（通过表单/API） | LLM Agent（通过 function calling） |
| 格式保证 | 表单校验 | JSON Schema + function calling |
| 调用方式 | REST API | LLM 工具调用 |
| 本质 | completeTask(taskId, variables) | submit_step_result(output) |

##### 扩展总结

| 扩展 | BPMN 基础 | 扩展内容 | 兼容性 |
|------|----------|---------|--------|
| session | Ad-Hoc Sub-Process | 增加 session 属性（moderator/participants/agenda/interaction_mode） | 导出 BPMN XML 时放在 extensionElements，标准工具可忽略 |
| NodeAssignment | BPMN 不覆盖此领域 | 引擎→执行者的通信协议 | 不影响 BPMN 模型层，是运行时实现 |
| submit_step_result | completeTask 的变体 | LLM function calling 替代 API 调用 | 不影响 BPMN 模型层，是执行层实现 |

三个扩展都不违反 BPMN 2.0 标准，而是在标准允许的扩展机制内实现。

### 14.9 设计决策：从 ISO 5807 混合模型转为纯 BPMN 2.0

> **状态：已采纳**
>
> 原设计中 NodeType 混合了 ISO 5807 和 BPMN 2.0 两套标准的符号（PREPARATION、IO、DOCUMENT、
> MULTI_DOCUMENT、DATA_STORE、CONNECTOR、MANUAL 来自 ISO 5807）。
>
> 经讨论后决定全部转为 BPMN 2.0，原因：
> - ISO 5807 的符号是 BPMN 2.0 的子集，不需要单独保留
> - BPMN 2.0 有更丰富的事件、网关、任务类型，覆盖我们的全部场景
> - BPMN 2.0 有三层建模体系（描述/分析/可执行），天然支持 Phase 分期
> - session（多人协作讨论）是我们独有的扩展，映射为 BPMN 的 Ad-Hoc Sub-Process
>
> 去掉的 ISO 5807 独有类型及其 BPMN 替代：
>
> | 去掉的类型 | BPMN 替代 |
> |-----------|----------|
> | PREPARATION | ActivityNode(task_type=ABSTRACT, tag="preparation") |
> | IO | DataObject(data_type=DATA_OBJECT) |
> | DOCUMENT | DataObject(data_type=DATA_OBJECT) |
> | MULTI_DOCUMENT | DataObject(data_type=DATA_COLLECTION) |
> | DATA_STORE | DataObject(data_type=DATA_STORE) |
> | CONNECTOR | EventNode(trigger=LINK) |
> | MANUAL | ActivityNode(task_type=MANUAL) |
>
> 详见第十四章 14.10 BPMN 2.0 完整建模。
> ISO 5807 和 BPMN 2.0 的完整描述见 `docs/design/流程图标准-ISO5807.md` 和 `docs/design/流程图标准-BPMN2.md`。

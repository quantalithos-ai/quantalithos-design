## 二、数据结构

### 2.1 ProcessDefinition / ProcessInstance / FlowMessage / NodeResult（来自 quantalithos-core）

flow 将流程定义、流程实例、执行上下文和消息协议都视为 core 的权威来源。所有流程 YAML/JSON 在落库或执行前都先由 `ProcessManager` 交给 core 模型校验，所有发往 runtime 的消息也统一使用 core 的 `FlowMessage` 及 payload 模型序列化。

```python
from quantalithos_core import FlowExecutionContext
from quantalithos_core import FlowMessage
from quantalithos_core import NodeExecutePayload
from quantalithos_core import NodeResult
from quantalithos_core import ProcessDefinition
from quantalithos_core import ProcessInstance
```

当前实现中，flow **不会**在项目内重新声明一套 `ProcessInstance`。daemon 直接把 core `ProcessInstance` 嵌入 `FlowState`，并用 flow 侧的辅助索引补充编排语义：

```python
# Core-owned runtime instances embedded in the daemon snapshot.
pipeline_instance: ProcessInstance
stage_instance: ProcessInstance | None
sub_instances: dict[str, ProcessInstance]

# Flow-owned companion indexes keyed by instance_id.
instance_parents: dict[str, str | None]
instance_callers: dict[str, str]
instance_current_nodes: dict[str, str | None]
instance_node_states: dict[str, dict[str, str]]
instance_feedback: dict[str, dict[str, str]]
```

这样做的结果是：

- BPMN token、节点输出、流程状态由 core `ProcessInstance` 负责。
- 回退、门禁、消息关联、边历史等编排元数据由 flow 快照负责。
- runtime 与 flow 在消息和实例字段上天然对齐，避免双份模型漂移。

### 2.4 WorkItemExecution（工单执行实例）

```python
class WorkItemExecution(BaseModel):
    """工单执行实例 — 阶段 3（迭代开发）的核心调度对象
    
    设计意图：
      WorkItemExecution 是 flow 对 platform WorkItem 的"执行视图"。
      platform 管理工单的数据（标题、描述、状态），
      flow 管理工单的执行（依赖调度、波次分配、工作流绑定）。
    
    与 platform WorkItem 的关系：
      source_ref 关联 platform 的 workitem_id。
      flow 不复制 WorkItem 的全部数据，只维护执行相关的状态。
      工单的详细信息通过 platform API 按需获取。
    
    波次调度（wave）：
      依赖图中无依赖的任务为第 1 波，依赖第 1 波的为第 2 波，以此类推。
      同一波次内的任务可以并行执行（分配给不同 Agent）。
      波次由 DependencyGraph 在初始化时计算。
    """
    instance_id: str                  # 执行实例 ID（如 "wie-003"）— flow 内部标识
    source_ref: str                   # 平台工单 ID（如 "TASK-003"）— 关联 platform 数据
    item_type: str                    # 工单类型：feature | bugfix | refactor
    status: str                       # 执行状态：draft | ready | in_progress | in_review | completed | blocked
    owner_id: str                     # 主执行者 agent_id — 谁在做这个任务
    reviewer_id: str                  # 审查者 agent_id — 谁来审查
    dependencies: List[str] = []      # 依赖的 WorkItemExecution.instance_id 列表
    wave: int = 1                     # 波次编号 — 同波次可并行，跨波次必须串行
    priority: str = "medium"          # 优先级 — 同波次内高优先级先执行
    workflow_instance_id: Optional[str] = None  # 绑定的 ProcessInstance ID
                                                # 如 TDD 工作流实例（Level 3 Enforced 时）


class DependencyGraph:
    """工单依赖图 — 管理任务间的依赖关系和调度顺序
    
    设计意图：
      TL 拆解任务时定义依赖关系（如"标签系统"依赖"文章模型"），
      DependencyGraph 据此计算波次和调度顺序。
    
    调度算法：
      1. 拓扑排序确定波次（无依赖 = wave 1，依赖 wave 1 的 = wave 2...）
      2. 同波次内按 priority 排序
      3. get_ready_items() 返回当前可执行的任务（依赖都 completed 且自身 ready）
      4. on_item_completed() 检查下游任务是否变为 ready
    
    并行度控制（Phase 2）：
      Phase 1 不限制并行度（有多少 ready 就执行多少）。
      Phase 2 引入 max_concurrency 参数控制同时执行的任务数。
    """
    items: Dict[str, WorkItemExecution]  # 所有工单执行实例 { instance_id: WIE }
    edges: List[Tuple[str, str]]      # 依赖边 (from_id, to_id) = from 完成后 to 才能开始

    def get_ready_items(self) -> List[WorkItemExecution]:
        """返回所有依赖已满足且状态为 ready 的任务
        
        调用时机：
          1. 初始化时 — 找出第一波可执行的任务
          2. on_item_completed() 后 — 检查新解锁的任务
        """

    def on_item_completed(self, item_id: str) -> List[WorkItemExecution]:
        """任务完成后，检查哪些下游任务变为 ready
        
        算法：
          1. 找到所有以 item_id 为 from 的边
          2. 对每个 to_id，检查其所有依赖是否都 completed
          3. 如果是 → 将 to_id 的状态改为 ready，加入返回列表
        """
```

### 2.5 GateRequest（门禁审批）

```python
class GateRequest(BaseModel):
    """门禁审批请求 — 流程暂停等待用户决策
    
    设计意图：
      门禁是用户参与流程控制的唯一方式。
      当流程到达 UserTask 节点时，GateController 创建 GateRequest，
      通过 gate → chat 推送给用户。用户操作后，flow 据此推进流程。
    
    gate_type 两种类型：
      - hard：硬门禁 — 必须人工确认，不能自动通过
        场景：需求确认、最终验收（用户必须看过产物才能继续）
      - soft：软门禁 — 可配置自动通过条件
        场景：设计阶段完成后的确认（如果用户 24h 不操作则自动通过）
    
    trigger_point 两种触发点：
      - stage_transition：阶段间推进时触发（Pipeline 级别的门禁）
      - step_completion：阶段内步骤完成时触发（Workflow 级别的门禁）
    
    status 状态流转：
      pending → approved（用户批准）
      pending → rejected（用户驳回）
      pending → changes_requested（用户要求修改）
      pending → expired（超时未操作）
    
    超时处理（Phase 2）：
      timeout_minutes 到期后：
      - hard 门禁 → status=expired，通知用户
      - soft 门禁 → status=approved，自动通过
    """
    gate_id: str                      # 门禁唯一标识（UUID）
    project_id: str                   # 所属项目 ID
    gate_type: str                    # 门禁类型：hard（必须人工）| soft（可自动通过）
    trigger_point: str                # 触发点：stage_transition | step_completion
    title: str                        # 门禁标题（展示在 GateCard 上）
    description: str                  # 门禁描述（告诉用户需要确认什么）
    artifacts: List[dict]             # 需要审阅的产物列表（展示在 GateCard 上供用户查看）
    status: str = "pending"           # 当前状态：pending | approved | rejected | changes_requested | expired
    timeout_minutes: Optional[int] = None  # 超时时间（分钟）— None 表示不超时
    requested_at: datetime            # 创建时间
    responded_at: Optional[datetime] = None  # 用户操作时间
    comment: Optional[str] = None     # 用户的审批意见（reject/changes_requested 时必填）
```

### 2.6 持久化状态

```python
class FlowState(BaseModel):
    """flow daemon 的完整状态 — 每步持久化，崩溃后可恢复
    
    设计意图：
      FlowState 是 flow daemon 的"大脑" — 记录项目流程的完整执行状态。
      每次状态变更后立即持久化（Phase 1 写文件，Phase 2 事件日志），
      daemon 崩溃重启后从快照恢复，实现断点续跑。
    
    为什么是一个大对象而非分散存储：
      1. 持久化时一次性写入，保证一致性（不会出现"Pipeline 推进了但阶段没更新"）
      2. 恢复时一次性加载，不需要从多个来源拼凑状态
      3. 调试时可以直接查看 current.yaml 了解完整状态
    
    pending_messages 的用途：
      跟踪已发送但未收到回复的 FlowMessage。
      如果 daemon 重启后发现有 pending 消息，可以决定是否重发。
    
    message_to_node 的回溯机制：
      收到 NodeResult 时，通过 result.message_id 查找对应的 (instance_id, node_id)，
      从而知道"这个结果属于哪个流程实例的哪个节点"。
    """
    project_id: str                   # 项目 ID — 一个 daemon 管理一个项目

    # ── core 流程实例 ──
    pipeline_instance: ProcessInstance  # 项目级 pipeline 实例
    stage_instance: Optional[ProcessInstance] = None  # 当前活跃阶段实例
    stage_instance_map: Dict[str, str] = Field(default_factory=dict)  # pipeline 阶段节点 ID -> 子流程实例 ID
    sub_instances: Dict[str, ProcessInstance] = Field(default_factory=dict)  # 所有已注册子流程实例

    # ── flow 辅助索引 ──
    instance_parents: Dict[str, Optional[str]] = Field(default_factory=dict)  # instance_id -> parent_instance_id
    instance_callers: Dict[str, str] = Field(default_factory=dict)  # instance_id -> caller node id
    instance_current_nodes: Dict[str, Optional[str]] = Field(default_factory=dict)  # instance_id -> 当前逻辑节点
    instance_node_states: Dict[str, Dict[str, str]] = Field(default_factory=dict)  # instance_id -> node_id -> state
    instance_feedback: Dict[str, Dict[str, str]] = Field(default_factory=dict)  # instance_id -> node_id -> rollback feedback

    # ── 任务调度 ──
    work_item_executions: List[WorkItemExecution] = Field(default_factory=list)  # 工单执行视图
    dependency_graph: Optional[dict] = None  # 依赖图快照

    # ── 消息追踪 ──
    pending_messages: Dict[str, str] = Field(default_factory=dict)  # message_id -> dispatched/completed/failed/blocked
    message_to_node: Dict[str, Tuple[str, str]] = Field(default_factory=dict)  # message_id -> (instance_id, node_id)

    # ── platform 游标 / 门禁 / 审计 ──
    last_platform_event_id: Optional[str] = None  # 上次处理到的 platform event id
    pending_gates: List[GateRequest] = Field(default_factory=list)  # 等待用户操作的门禁
    gate_history: List[dict] = Field(default_factory=list)  # 门禁历史
    active_agents: List[str] = Field(default_factory=list)  # 当前活跃 Agent
    edge_history: List[EdgeTraversal] = Field(default_factory=list)  # 边遍历历史，用于回退与可视化

    # ── 元数据 ──
    updated_at: datetime              # 最后更新时间
```

## 三、核心执行流程

### 3.1 daemon 事件循环

```python
# daemon/event_loop.py
#
# flow daemon 的主事件循环 — 项目流程的"心脏"。
#
# 设计意图：
#   flow daemon 是一个长驻进程，每个项目一个 daemon 实例。
#   它以事件编排为核心，但当前 platform 输入通路仍通过 HTTP 轮询兼容接入：
#   拉取 platform 事件 → 串行处理 → 持久化状态 → 空闲时短暂 sleep。
#
# 事件来源：
#   - node_result：runtime `/messages` 同步返回或未来异步回调的 NodeResult
#   - gate_response：用户的门禁审批操作
#   - chat_message：用户群聊消息（转发给 runtime）
#   - platform_event：通过 `/api/events` 轮询得到的工单事件
#
# 持久化策略：
#   每次事件处理后立即持久化 — 确保崩溃后不丢失状态。
#   Phase 1 写 YAML 文件（简单可靠），Phase 2 改为事件日志（Event Sourcing）。

class EventLoop:
    """flow daemon 的主事件循环 — 串行处理事件并每步持久化"""

    def __post_init__(self) -> None:
        # runtime 同步返回的 NodeResult 会直接复用这里的标准处理通路。
        self.flow_engine.node_result_handler = self.handle_node_result

    async def run(self) -> None:
        self._install_signal_handlers()
        self.state = await self.state_persister.load(self.project_id)
        if self.state is None:
            self.state = await self.initialize_project(self.project_id)

        while not self._stop_event.is_set():
            await self.wait_for_event()

    async def wait_for_event(self) -> None:
        if self.state is None:
            raise RuntimeError("EventLoop state is not initialized.")

        platform_events = await self.platform_listener.poll_events(self.state)
        if not platform_events:
            await asyncio.sleep(self.idle_sleep_secs)
            return

        for event in platform_events:
            await self.handle_platform_event(event)

    async def initialize_project(self, project_id: str) -> FlowState:
        project = await self.platform_client.get_project(project_id)
        pipeline_process_id = project["pipeline_process_id"]
        pipeline_definition = await self.flow_engine.load_process_definition(
            pipeline_process_id,
            project_id=project_id,
        )

        state = FlowState.create_empty(project_id=project_id)
        # 先挂到 self.state，再启动 pipeline；这样 runtime 若同步返回结果，
        # EventLoop.handle_node_result() 可以安全回流到同一状态对象。
        self.state = state

        for agent_id in project.get("active_agents", []):
            if self.agent_lifecycle_manager is not None:
                await self.agent_lifecycle_manager.create_agent(state, agent_id)

        await self.flow_engine.start_process(
            state=state,
            process_definition=pipeline_definition,
            scope="pipeline",
            parent_instance_id=None,
            caller_node_id=None,
            instance_id=state.pipeline_instance.instance_id,
        )
        await self.state_persister.save(state)
        return state
```

### 3.2 节点执行策略

> **设计决策记录：NodeDispatcher → FlowNodeVisitor → 策略注册表**
>
> 第一版：NodeDispatcher 自己实现遍历循环、dict 访问节点、字符串比较 category。
> 第二版：FlowNodeVisitor 实现 core 的 NodeVisitor 接口，但对象知道 visitor 的存在。
> 最终版：策略注册表。对象完全不知道策略的存在，BPMNEngine 按 node_type 查表调用。

```python
# engine/strategies.py
#
# flow 侧策略实现（flow 项目内部版本）。
# 与 core 详细设计 §5.3 中的策略定义一致，此处是 flow 项目中的实际代码位置。
# 详细注释见 core 详细设计 §5.3。

from quantalithos_core.bpmn import NodeStrategy, FlowExecutionContext
from quantalithos_core.bpmn import AbstractTask, UserTask, AdHocSubProcess, EndEvent
from quantalithos_core.protocol import FlowMessage, NodeExecutePayload

class FlowTaskStrategy(NodeStrategy):
    """flow: AbstractTask → 构造 node_execute 消息发给 runtime
    
    核心职责：将 BPMN 节点转为 FlowMessage 发给 runtime。
    返回 None 表示异步等待 — 流程暂停直到收到 NodeResult 回调。
    """
    async def execute(self, node: AbstractTask, ctx: FlowExecutionContext) -> Optional[dict]:
        msg = FlowMessage(
            message_id=generate_id(),
            type="node_execute",
            agent_id=ctx.resolve_actor(node.actor),
            project_id=ctx.project_id,
            payload=NodeExecutePayload(
                process_instance_id=ctx.process_instance_id,
                node=node.dict(),
                control_level="free",
                input_refs=node.input_refs,
                allowed_tools=node.allowed_tools,
                output_schema=node.output_schema,
            ).dict(),
            created_at=datetime.now(),
        )
        await ctx.runtime_client.send(msg)
        return None  # 异步等待 NodeResult 回调

class FlowUserTaskStrategy(NodeStrategy):
    """flow: UserTask → 创建门禁卡片，等待用户操作
    
    执行逻辑：
      调用 gate_controller.create_gate() 创建 GateCard 推送给用户。
      流程暂停，等待用户点击 approve/reject/request_changes。
      与 FlowTaskStrategy 的区别：等待人类操作而非 Agent 执行。
    """
    async def execute(self, node: UserTask, ctx: FlowExecutionContext) -> Optional[dict]:
        await ctx.gate_controller.create_gate(node)
        return None

class FlowAdHocStrategy(NodeStrategy):
    """flow: AdHocSubProcess → 构造 node_execute 消息发给协调者
    
    执行逻辑：
      将 AdHocSubProcess 节点发给协调者（moderator_id）。
      runtime 收到后由 AgentAdHocStrategy 将所有参与者推入协作状态。
      为什么 control_level 固定为 "free"：
        协作活动本质是"讨论"，不需要强制步骤控制。
        协调者自主决定何时提交结论。
    """
    async def execute(self, node: AdHocSubProcess, ctx: FlowExecutionContext) -> Optional[dict]:
        msg = FlowMessage(
            message_id=generate_id(),
            type="node_execute",
            agent_id=node.moderator_id,
            project_id=ctx.project_id,
            payload=NodeExecutePayload(
                process_instance_id=ctx.process_instance_id,
                node=node.dict(),
                control_level="free",
            ).dict(),
            created_at=datetime.now(),
        )
        await ctx.runtime_client.send(msg)
        return None

class FlowEndEventStrategy(NodeStrategy):
    """flow: EndEvent → 流程完成，触发阶段推进
    
    执行逻辑：
      调用 ctx.on_process_completed() 通知 FlowEngine 当前流程实例完成。
      FlowEngine 据此推进父流程（阶段完成 → Pipeline 推进到下一阶段）。
    """
    async def execute(self, node: EndEvent, ctx: FlowExecutionContext) -> Optional[dict]:
        await ctx.on_process_completed()
        return None

```python
# engine/flow_engine.py
#
# FlowEngine — flow 项目对 core.BPMNEngine 的封装。
# 负责构造策略注册表、执行上下文，管理流程实例生命周期。
#
# 与 core.BPMNEngine 的关系：
#   BPMNEngine 是通用的 Token 驱动引擎（不知道 flow/runtime 的区别）。
#   FlowEngine 通过策略注册表告诉 BPMNEngine "到了某个节点该做什么"。
#   BPMNEngine 负责"怎么走"，FlowEngine 负责"做什么"。

from quantalithos_core.bpmn import BPMNEngine, StrategyRegistry, FlowExecutionContext

class FlowEngine:
    """flow 的流程引擎 — 委托 core.BPMNEngine + 策略注册表驱动
    
    设计职责：
      1. 构造 flow 侧的策略注册表（注册 FlowTaskStrategy 等）
      2. 构造 FlowExecutionContext（注入 runtime_client 等依赖）
      3. 管理流程实例的生命周期（启动、完成、推进父流程）
    """

    def __init__(self, runtime_client, gate_controller, platform_client):
        self.runtime_client = runtime_client      # 向 runtime 发送 FlowMessage
        self.gate_controller = gate_controller    # 创建门禁审批卡片
        self.platform_client = platform_client    # 读取工单/产物/流程定义

    def create_registry(self) -> StrategyRegistry:
        """构造 flow 侧的策略注册表"""
        registry = StrategyRegistry()
        registry.register("abstract_task", FlowTaskStrategy())
        registry.register("user_task", FlowUserTaskStrategy())
        registry.register("ad_hoc_sub_process", FlowAdHocStrategy())
        registry.register("end_event", FlowEndEventStrategy())
        # start_event / exclusive_gateway / parallel_gateway → 不注册，引擎自动处理
        return registry

    async def start_process(
        self,
        state: FlowState,
        process_definition: ProcessDefinition,
        *,
        scope: str,
        parent_instance_id: str | None = None,
        caller_node_id: str | None = None,
        instance_id: str | None = None,
    ) -> ProcessInstance:
        """启动一个流程并交给 core BPMNEngine 推进。"""
        instance = self.create_process_instance(
            process_definition=process_definition,
            project_id=state.project_id,
            scope=scope,
            instance_id=instance_id,
        )
        self._register_process_definition(
            process_definition,
            project_id=state.project_id,
        )
        self._register_instance(
            state=state,
            process_definition=process_definition,
            instance=instance,
            parent_instance_id=parent_instance_id,
            caller_node_id=caller_node_id,
        )
        await self.drive_process(
            state=state,
            process_definition=process_definition,
            process_instance=instance,
        )
        if instance.status == "completed":
            await self.handle_completed_process(state=state, instance=instance)
        return instance

    async def handle_completed_process(
        self,
        state: FlowState,
        instance: ProcessInstance,
    ) -> None:
        """子流程完成后推进父流程；阶段完成时可继续推进 pipeline。"""
        state.instance_current_nodes[instance.instance_id] = None
        parent_instance_id = state.instance_parents.get(instance.instance_id)
        caller_node_id = state.instance_callers.get(instance.instance_id)
        if parent_instance_id is None or caller_node_id is None:
            return

        parent_instance = self.get_instance(state, parent_instance_id)
        parent_definition = await self.load_process_definition(
            parent_instance.process_id,
            project_id=parent_instance.project_id,
        )
        parent_instance.node_outputs[caller_node_id] = {
            "sub_process_instance_id": instance.instance_id,
            "sub_process_id": instance.process_id,
            "status": "completed",
        }
        self._mark_node_completed(
            state=state,
            instance_id=parent_instance.instance_id,
            node_id=caller_node_id,
        )
        self._advance_completed_tokens(
            process_definition=parent_definition,
            process_instance=parent_instance,
            node_id=caller_node_id,
            state=state,
        )
        await self.drive_process(
            state=state,
            process_definition=parent_definition,
            process_instance=parent_instance,
        )

    async def start_sub_process(
        self,
        state: FlowState,
        parent_instance: ProcessInstance,
        node: CallActivity,
    ) -> ProcessInstance:
        """CallActivity 到达时加载并启动子流程。"""
        process_definition = await self.load_process_definition(
            node.call_process_id,
            project_id=state.project_id,
        )
        scope = "stage" if parent_instance.scope == "pipeline" else "sub_process"
        return await self.start_process(
            state=state,
            process_definition=process_definition,
            scope=scope,
            parent_instance_id=parent_instance.instance_id,
            caller_node_id=node.id,
        )


    def get_suspicion_hints(self, node: dict) -> List[str]:
        """根据节点类型生成怀疑机制提示 — 注入 Agent prompt 第四层
        
        设计意图：
          "怀疑机制"是防止 Agent 盲目信任前序产出的安全措施。
          代码审查时提醒"前序代码可能有 BUG"，
          测试时提醒"实现代码可能有问题"。
          这样 Agent 会独立验证而非假设前序工作是正确的。
        
        为什么由 flow 生成而非 runtime：
          flow 知道流程上下文（当前是审查节点还是测试节点），
          runtime 只知道"执行一个 AbstractTask"，不知道流程语义。
        """
        hints = []
        node_name = node.get("name", "")
        node_id = node.get("id", "")

        # 代码审查节点
        if "review" in node_id or "review" in node_name.lower():
            hints.append("前序产出（PRD、设计文档）可能有遗漏或错误，请独立验证代码是否满足实际需求。")

        # 测试节点
        if "test" in node_id or "test" in node_name.lower():
            hints.append("实现代码可能有 BUG，PRD 可能有遗漏，请从用户视角独立设计测试用例。")

        # 修复节点（审查打回后）
        if "fix" in node_id:
            hints.append("前序产出可能有其他遗漏，请独立验证，不要只修复指出的问题。")

        return hints


    async def advance_to_next(self, state, instance, current_node_id, next_node_id, edge):
        """推进到下一个节点，记录 edge_history + 持久化
        
        设计意图：
          每次 Token 推进时记录走过的边（edge_history），用于：
          1. 前端 BPMN 图标注走过的路径（绿色）
          2. 打回路径标注（count > 1 时红色）
          3. 审计追溯（流程走了哪条路）
        
        existing.count += 1 的含义：
          同一条边被走过多次 = 打回后重新执行。
          如 review → implement 的边 count=2 表示被打回过一次。
        """

        # 记录 edge_history — 检查是否已走过此边（打回场景）
        existing = next((e for e in instance.edge_history if e.edge_id == edge["id"]), None)
        if existing:
            existing.count += 1             # 打回计数 +1
            existing.traversed_at = datetime.now()
        else:
            instance.edge_history.append(EdgeTraversal(
                edge_id=edge["id"],
                source_node_id=current_node_id,
                target_node_id=next_node_id,
                label=edge.get("label"),
                traversed_at=datetime.now(),
            ))

        # 持久化（关键步骤）
        await self.state_persister.save(state)

        # 推进
        instance.current_node_id = next_node_id
        next_node = self.get_node(instance, next_node_id)
        await self.dispatch(state, instance, next_node)
```

### 3.3 NodeResult 处理

```python
# daemon/event_loop.py (续)
#
# NodeResult 处理 — flow 收到 runtime 执行结果后的核心逻辑。
# 结果来源可以是 runtime `/messages` 的同步响应，也可以是未来的异步回调；
# 两种来源都统一走 EventLoop.handle_node_result()。

class EventLoop:
    async def handle_node_result(self, result: NodeResult):
        self._node_result_queue.append(result)
        if self._draining_node_results:
            return

        self._draining_node_results = True
        try:
            while self._node_result_queue:
                current = self._node_result_queue.popleft()
                await self._handle_node_result_once(current)
        finally:
            self._draining_node_results = False

    async def _handle_node_result_once(self, result: NodeResult) -> None:
        if self.state is None:
            raise RuntimeError("EventLoop state is not initialized.")

        current_status = self.state.pending_messages.get(result.message_id)
        if current_status != "dispatched":
            return

        self.state.pending_messages[result.message_id] = result.result_type
        mapping = self.state.message_to_node.get(result.message_id)
        if mapping is None:
            await self.state_persister.save(self.state)
            return
        instance_id, node_id = mapping
        instance = self.flow_engine.get_instance(self.state, instance_id)
        node_states = self.state.instance_node_states.setdefault(instance_id, {})

        match result.result_type:
            case "completed":
                await self.flow_engine.resume_after_node_result(
                    state=self.state,
                    instance=instance,
                    node_id=node_id,
                    output=result.output or {},
                )
            case "blocked":
                node_states[node_id] = "blocked"
            case "failed":
                await self._handle_failed_result(
                    instance=instance,
                    node_id=node_id,
                    reason=result.reason or "",
                )
            case _:
                raise ValueError(f"Unsupported node result type: {result.result_type}")

        await self.state_persister.save(self.state)
```

### 3.5 门禁控制（GateController）

```python
# business/gate_controller.py
#
# 门禁审批管理 — 用户参与流程控制的唯一入口。
#
# 设计意图：
#   门禁是"人在回路"（Human-in-the-Loop）的实现。
#   AI Agent 自动执行任务，但关键决策点需要人类确认。
#   GateController 负责创建审批请求、处理用户操作、推进流程。
#
# 数据流：
#   flow 到达 UserTask → GateController.create_gate() → 创建 GateRequest
#   → 通过 gate API 推送给 chat 前端 → 用户看到 GateCard
#   → 用户操作（approve/reject/changes_requested）
#   → gate API 回调 → EventLoop.handle_gate_response()
#   → GateController.handle_response() → 推进或回退流程

class GateController:
    """门禁审批管理 — 创建审批请求、处理用户操作"""

    async def create_gate(self, state: FlowState, instance: ProcessInstance, node: dict):
        """创建门禁审批请求 — 流程暂停等待用户决策
        
        调用时机：
          FlowUserTaskStrategy.execute() 中调用。
          流程到达 UserTask 节点时触发。
        """
        gate_config = node.get("gate_config", {})

        gate = GateRequest(
            gate_id=generate_id(),
            project_id=state.project_id,
            gate_type=gate_config.get("gate_type", "hard"),
            trigger_point="step_completion",
            title=gate_config.get("title", node.get("name", "")),
            description=gate_config.get("description", ""),
            artifacts=await self.collect_artifacts(state, gate_config),
            timeout_minutes=gate_config.get("timeout_minutes"),
            requested_at=datetime.now(),
        )

        # soft gate 且项目配置不要求确认 → 自动通过
        if gate.gate_type == "soft" and not self.project_requires_confirmation(state):
            gate.status = "approved"
            gate.responded_at = datetime.now()
            state.gate_history.append(gate.dict())
            # 推进到下一个节点
            instance.node_states[node["id"]] = "completed"
            next_node = self.find_next_node(instance, node["id"])
            if next_node:
                # 由 BPMNEngine 推进 token（soft gate 自动通过后继续执行）
                await self.flow_engine.resume_token(state, instance, next_node)
            return

        # hard gate → 发送审批卡片给用户
        state.pending_gates.append(gate)
        await self.send_gate_card(state, gate)


    async def handle_gate_response(self, state: FlowState, gate_id: str, action: str, comment: str = ""):
        """处理用户的审批操作 — 根据用户决策推进或回退流程
        
        三种操作：
          approve → 流程继续前进（推进到下一个节点）
          request_changes → 回退到前一个活动节点，注入用户意见重新执行
          reject → 终止流程或回退到更早的阶段
        
        回退机制（request_changes）：
          1. 找到回退目标节点（on_request_changes 配置 或 前一个 Activity）
          2. 将用户的 comment 注入到下一次任务的 action 中
          3. 重新执行目标节点（Agent 会看到用户的修改意见）
          edge_history 中 count > 1 表示被打回过（前端用红色标注）
        """
        gate = self.find_pending_gate(state, gate_id)
        if not gate:
            return

        gate.responded_at = datetime.now()
        gate.comment = comment

        match action:
            case "approve":
                gate.status = "approved"
                state.gate_history.append(gate.dict())
                state.pending_gates.remove(gate)
                # 推进流程
                instance, node = self.find_gate_context(state, gate)
                instance.node_states[node["id"]] = "completed"
                next_node = self.find_next_node(instance, node["id"])
                if next_node:
                    # 由 BPMNEngine 推进 token（审批通过后继续执行）
                    await self.flow_engine.resume_token(state, instance, next_node)

            case "request_changes":
                gate.status = "changes_requested"
                state.pending_gates.remove(gate)
                # 回退到指定节点
                instance, node = self.find_gate_context(state, gate)
                rollback_target = node.get("on_request_changes") or self.find_previous_activity(instance, node["id"])
                if rollback_target:
                    # 注入用户意见到下一次任务的 action
                    await self.rollback_with_feedback(state, instance, rollback_target, comment)

            case "reject":
                gate.status = "rejected"
                state.gate_history.append(gate.dict())
                state.pending_gates.remove(gate)
                # 回退到更早的阶段或终止
                await self.handle_rejection(state, gate)
```

### 3.6 任务调度（TaskScheduler）

```python
# business/platform_listener.py
#
# PlatformListener — 监听 platform 事件，将工单状态变更转为 Agent 执行指令。
#
# 设计意图：
#   platform 管理工单的"数据状态"（created → assigned → in_progress...），
#   flow 管理工单的"执行编排"（告诉 Agent 怎么做、用什么工具、什么控制级别）。
#   PlatformListener 是两者之间的桥梁。
#
# 职责分离（设计更新）：
#   任务调度（依赖图、波次、并行分发）已移到 platform。
#   flow 不再管"谁先做谁后做"，只管"Agent 需要执行时告诉它怎么做"。
#   这样 flow 更专注于流程编排，platform 更专注于数据管理。
#
# STATUS_CONFIGS 的设计：
#   每种工单状态对应不同的执行配置：
#   - in_progress：开发阶段 → enforced + TDD 工作流（强制按步骤来）
#   - in_review：审查阶段 → free + 怀疑机制（独立验证）
#   - in_testing：测试阶段 → free + 怀疑机制（独立设计测试用例）
#   这些配置决定了 FlowMessage 中的 control_level 和 allowed_tools。

class PlatformListener:
    """监听 platform 事件，构造 FlowMessage 发给 runtime
    
    设计更新：任务调度（依赖图、波次、并行分发）已移到 platform。
    flow 不再管"谁先做谁后做"，只管"Agent 需要执行时告诉它怎么做"。
    """

    # 每种工单状态对应的 FlowMessage 配置
    # 决定 Agent 执行时的控制级别、可用工具、怀疑提示
    STATUS_CONFIGS = {
        "in_progress": {
            # 开发阶段：强制 TDD 工作流（Level 3 Enforced）
            "control_level": "enforced",
            "process_id": "tdd_workflow",       # 强制使用的工作流 ProcessDefinition
            "allowed_tools": ["file_read", "file_write", "code_execute", "git_commit",
                              "workitem_transition", "task_read", "search_docs",
                              "ask_teammate", "send_chat_message"],
        },
        "in_review": {
            # 审查阶段：自由执行 + 怀疑机制
            "control_level": "free",
            "allowed_tools": ["file_read", "git_diff", "search_docs",
                              "workitem_transition", "workitem_assign",
                              "ask_teammate", "send_chat_message"],
            "suspicion_hints": ["前序代码可能有错，请独立验证，不要只对照任务卡检查"],
        },
        "in_testing": {
            # 测试阶段：自由执行 + 怀疑机制
            "control_level": "free",
            "allowed_tools": ["file_read", "code_execute", "search_docs",
                              "workitem_transition", "workitem_assign", "task_create",
                              "ask_teammate", "send_chat_message",
                              # Phase 3：真机测试工具（testbed）
                              "device_list", "device_deploy", "device_run_test",
                              "device_screenshot", "device_logs", "device_performance"],
            "suspicion_hints": ["实现代码可能有 BUG，请从用户视角独立设计测试用例"],
        },
    }

    async def on_workitem_assigned(self, event: dict):
        """platform 事件：工单被指派给某个 Agent
        
        这是 flow 响应 platform 事件的核心方法。
        当 platform 将工单指派给某个 Agent 时（自动调度或手动指派），
        flow 根据工单状态构造 FlowMessage 告诉 Agent 怎么做。
        
        流程：
          1. 读取工单详情（获取状态、标题等）
          2. 确保目标 Agent 已创建（如果不存在则创建）
          3. 根据工单状态查找 STATUS_CONFIGS
          4. 构造 AbstractTask 节点 + FlowMessage
          5. 发送给 runtime
        """
        workitem_id = event["workitem_id"]
        agent_id = event["new_assignee"]
        reason = event.get("reason", "")

        # 读取工单详情
        workitem = await self.platform_client.get_workitem(workitem_id)
        status = workitem["status"]

        # 确保 Agent 已创建
        if agent_id not in self.state.active_agents:
            await self.agent_lifecycle.create_agent(self.state, agent_id)

        # 根据工单状态查找 FlowMessage 配置
        config = self.STATUS_CONFIGS.get(status)
        if not config:
            return  # 不需要 Agent 执行的状态（如 created）

        # 构造 FlowMessage（node_execute）
        node = AbstractTask(
            id=workitem_id,
            name=self.build_action(workitem, status),
            action=self.build_action(workitem, status),
            actor=agent_id,
            allowed_tools=config.get("allowed_tools", []),
            output_schema=self.get_output_schema(status),
        )
        msg = FlowMessage(
            message_id=generate_id(),
            type="node_execute",
            agent_id=agent_id,
            project_id=self.state.project_id,
            payload=NodeExecutePayload(
                process_instance_id=self.state.current_instance_id,
                node=node.dict(),
                control_level=config.get("control_level", "free"),
                process_id=config.get("process_id"),
                input_refs=[workitem_id],
                output_schema=self.get_output_schema(status),
                suspicion_hints=config.get("suspicion_hints", []),
            ).dict(),
            created_at=datetime.now(),
        )
        await self.runtime_client.send(msg)
        self.state.pending_messages[msg.message_id] = "dispatched"

    def build_action(self, workitem: dict, status: str) -> str:
        """根据工单和状态构造自然语言任务描述"""
        title = workitem["title"]
        match status:
            case "in_progress":
                return f"实现 {workitem['id']}：{title}"
            case "in_review":
                return f"审查 {workitem['id']}：{title} 的代码变更"
            case "in_testing":
                return f"测试 {workitem['id']}：{title} 的功能实现"
            case _:
                return f"处理 {workitem['id']}：{title}"

    async def on_workitem_status_changed(self, event: dict):
        """platform 事件：工单状态变更"""
        # 大部分状态变更由 platform 自动处理（指派 + 通知）
        # flow 只关心特殊情况
        if event["to_status"] == "completed":
            # 通知群聊
            await self.notify_chat(
                f"✅ {event['workitem_id']} 已完成"
            )

    async def on_all_tasks_completed(self, event: dict):
        """platform 事件：项目所有任务完成"""
        # 推进到下一阶段（验收）
        await self.advance_stage(self.state)
```

### 3.7 Agent 生命周期管理

```python
# business/agent_lifecycle.py
#
# Agent 生命周期管理 — flow 通过此组件控制 Agent 的创建/销毁/挂起/恢复。
#
# 设计意图：
#   flow 不直接操作 Agent（Agent 在 runtime 中），
#   而是通过发送 FlowMessage 来间接管理 Agent 的生命周期。
#   AgentLifecycleManager 封装了这些 FlowMessage 的构造逻辑。
#
# agent_id 命名约定：
#   {role_id_kebab}-{序号}，如 "backend-dev-1"、"tech-lead"
#   resolve_role_id() 从 agent_id 反推 role_id（去掉序号，kebab → snake）

class AgentLifecycleManager:
    """向 runtime 发送 Agent 生命周期指令"""

    async def create_agent(self, state: FlowState, agent_id: str):
        """创建 Agent — 项目启动或新阶段需要新角色时调用
        
        调用时机：
          1. 项目初始化时创建 TL 和 Assistant
          2. 进入开发阶段时创建 BE/FE/Tester
          3. on_workitem_assigned 时发现目标 Agent 不存在
        """
        # 从 agent_id 推断 role_id（如 "backend-dev-1" → "backend_dev"）
        role_id = self.resolve_role_id(agent_id)

        msg = FlowMessage(
            message_id=generate_id(),
            type="agent_create",
            agent_id=agent_id,
            project_id=state.project_id,
            payload={"role_id": role_id},
            created_at=datetime.now(),
        )
        await self.runtime_client.send(msg)
        state.active_agents.append(agent_id)

    async def destroy_agent(self, state: FlowState, agent_id: str):
        """销毁 Agent — 项目完成或阶段切换时不再需要某角色
        
        调用时机：
          1. 项目完成时销毁所有 Agent
          2. 阶段切换时不再需要某角色（如需求阶段结束后不再需要 Assistant）
        """
        msg = FlowMessage(
            message_id=generate_id(),
            type="agent_destroy",
            agent_id=agent_id,
            project_id=state.project_id,
            payload={},
            created_at=datetime.now(),
        )
        await self.runtime_client.send(msg)
        state.active_agents.remove(agent_id)

    async def suspend_all(self, state: FlowState):
        """挂起所有 Agent — 用户下线或项目暂停时调用
        
        为什么用 list(state.active_agents) 而非直接遍历：
          循环体内 runtime_client.send() 是异步的，如果发送失败需要从列表中移除。
          直接遍历时修改列表会导致 RuntimeError。
          list() 创建副本，遍历副本、修改原列表。
        
        state.active_agents.clear() 的时机：
          所有 suspend 消息发出后才 clear — 确保即使部分发送失败，
          下次重试时还能找到未成功挂起的 Agent。
          （Phase 1 简化：假设全部成功，直接 clear）
        """
        for agent_id in list(state.active_agents):
            msg = FlowMessage(
                message_id=generate_id(),
                type="agent_suspend",
                agent_id=agent_id,
                project_id=state.project_id,
                payload={},
                created_at=datetime.now(),
            )
            await self.runtime_client.send(msg)
        state.active_agents.clear()
```

### 3.8 持久化（StatePersister）

```python
# infra/state_persister.py
#
# 状态持久化 — 确保 daemon 崩溃后可以断点续跑。
#
# Phase 1 策略：每步写文件
#   简单可靠，适合单机部署。
#   缺点：无法回溯历史状态（只有最新快照）。
#
# Phase 2 策略：事件日志（Event Sourcing）
#   每次状态变更记录为一个事件，状态可以从事件序列重建。
#   优点：完整的审计追溯、可以回放到任意时间点。
#   缺点：实现复杂度高，需要事件存储基础设施。
#
# 为什么 Phase 1 选择文件而非数据库：
#   1. 减少外部依赖（不需要 Redis/PostgreSQL）
#   2. YAML 格式人类可读（调试时直接查看 current.yaml）
#   3. 单机部署足够（Phase 1 不需要分布式）

class StatePersister:
    """每步持久化 — Phase 1 文件，Phase 2 事件日志"""

    async def save(self, state: FlowState):
        """保存状态到文件 — 每次事件处理后调用
        
        为什么是 async：
          Phase 2 改为写数据库时需要 async。
          Phase 1 虽然是文件 IO，但保持接口一致。
        """
        state.updated_at = datetime.now()
        path = f"snapshots/workflow/current.yaml"
        with open(path, 'w') as f:
            yaml.dump(state.dict(), f)

    async def load(self, project_id: str) -> Optional[FlowState]:
        """从文件恢复状态 — daemon 启动时调用
        
        返回 None 表示没有已有快照（新项目）。
        返回 FlowState 表示有快照（断点续跑）。
        """
        path = f"snapshots/workflow/current.yaml"
        if not os.path.exists(path):
            return None
        with open(path, 'r') as f:
            data = yaml.safe_load(f)
        return FlowState(**data)

    async def append_event(self, event: dict):
        """Phase 2：追加事件到事件日志"""
        path = f"snapshots/workflow/events.jsonl"
        with open(path, 'a') as f:
            f.write(json.dumps(event) + '\n')
```

### 4.1 当前已实现接口

当前 `quantalithos-flow` 既是后台 daemon，也是一个内嵌 HTTP ingress 进程。已经落地的接口分为两类：

```
Inbound -> flow daemon
GET /health
  - response: HealthResponse

POST /chat/messages
  - request: ChatMessageRequest
  - response: ChatDispatchResponse

POST /gate/{gate_id}/respond
  - request: GateResponseRequest
  - response: AcceptedResponse

POST /internal/node-results
  - request: core NodeResult
  - response: AcceptedResponse

Outbound -> runtime
POST /messages
  - request: core FlowMessage
  - response(node_execute): core NodeResult
  - response(other): RuntimeStatusResponse

Outbound -> platform
GET /api/projects/{project_id}
GET /api/projects/{project_id}/members
GET /api/agent-config/processes/{process_id}?project_id=...
GET /api/workitems/{workitem_id}
GET /api/projects/{project_id}/workitems           # direct lookup 缺失时回退
GET /api/workitems/{workitem_id}/dependencies
GET /api/events?since_event_id=...&project_id=...

Inbound -> daemon internal hooks
EventLoop.handle_node_result(...)
EventLoop.handle_gate_response(...)
EventLoop.handle_chat_message(...)
EventLoop.handle_platform_event(...)
```

兼容性约束：

- `POST /internal/node-results` 当前定位为 runtime/集成侧内部入口，主价值是把外部结果重新接入 `EventLoop.handle_node_result()` 的标准通路。
- runtime 侧统一走 `POST /messages`，不再维护单独的 `/results` 回调主通路。
- platform 若尚未提供 `/api/events`，`PlatformClient.list_events()` 将远端 `404` 视为“暂无事件”。
- platform 若尚未提供 `/api/workitems/{id}`，`PlatformClient.get_workitem()` 会扫描 `/api/projects/{project_id}/workitems` 作为兼容回退。

async def notify_chat(self, state: FlowState, text: str, link_type: str = None, link_id: str = None):
    """发送轻量通知到群聊"""
    # 通知发给所有活跃 Agent（它们会在群聊里看到）
    # 同时通过 gate WebSocket 推送给用户的 chat 前端

        }
    })

### 4.6 edge_history 数据结构

记录哪些边被走过，用于前端标注走过的路径和打回路径。

```python
class EdgeTraversal(BaseModel):
    """边的遍历记录 — 记录流程走过的路径
    
    设计意图：
      前端 BPMN 图需要知道哪些边被走过（标绿色），
      哪些边被走过多次（标红色 = 打回路径）。
      EdgeTraversal 记录每条边的遍历历史。
    
    count 字段的含义：
      count == 1：正常走过一次（绿色）
      count > 1：被打回过（红色 + 显示打回次数）
      前端据此给边标注不同颜色和数字。
    """
    edge_id: str                      # 边的 ID — 对应 FlowEdge.id
    source_node_id: str               # 源节点 ID — 从哪里出发
    target_node_id: str               # 目标节点 ID — 走向哪里
    label: Optional[str] = None       # 条件标签（如 "approved"、"needs_revision"）— 前端展示
    traversed_at: datetime            # 最后一次遍历时间
    count: int = 1                    # 这条边被走过几次（打回会 >1）
```

在 ProcessInstance 中新增（flow 自有扩展，不在 core 中）：

```python
# ProcessInstance 扩展字段
edge_history: List[EdgeTraversal] = []  # 边遍历历史
```

BPMNEngine 每次推进 token 时，通过 on_event 回调记录边遍历：

```python
async def advance_to_next(self, instance, current_node_id, next_node_id, edge):
    """推进到下一个节点，记录边遍历"""
    # 记录 edge_history
    existing = next((e for e in instance.edge_history if e.edge_id == edge["id"]), None)
    if existing:
        existing.count += 1
        existing.traversed_at = datetime.now()
    else:
        instance.edge_history.append(EdgeTraversal(
            edge_id=edge["id"],
            source_node_id=current_node_id,
            target_node_id=next_node_id,
            label=edge.get("label"),
            traversed_at=datetime.now(),
        ))
    
    # 推进
    instance.current_node_id = next_node_id
    await self.dispatch(state, instance, self.get_node(instance, next_node_id))
```

## 三、项目流程（Pipeline as ProcessDefinition）

> **设计决策：Pipeline 也是 ProcessDefinition**
>
> 原设计中 Pipeline 是独立的概念（PipelineTemplate + stages 列表），不属于 BPMN。
> 经讨论后统一为 BPMN 2.0：Pipeline 本身就是一个 ProcessDefinition，
> 每个"阶段"是一个 Call Activity 节点，门禁是 Exclusive Gateway 节点。
>
> 这样整个系统只有一种流程定义格式（ProcessDefinition），
> 从项目级到阶段级到 Agent 级，全部用同一套 nodes + edges 表达。

### 3.4 数据结构（更新）

```python
# ProcessDefinition 和 ProcessInstance 来自 quantalithos-core
from quantalithos_core.bpmn import ProcessDefinition, FlowNode, FlowEdge
from quantalithos_core.bpmn import EventNode, ActivityNode, GatewayNode

# ProcessInstance 是 flow 自有的运行时状态
# 注意：此处是 §三 中 flow 内部使用的简化版 ProcessInstance，
# 与 §2.3 中的完整版（含 edge_history/gate_history）是同一个类型的不同展示角度。
# 编码时以 §2.3 的完整版为准。
class ProcessInstance(BaseModel):
    """流程实例 — 运行时状态（简化展示，完整定义见 §2.3）"""
    instance_id: str
    process_id: str                   # 来自哪个 ProcessDefinition
    project_id: str
    scope: str                        # "pipeline" | "stage" | "agent"
    current_node_id: Optional[str]    # 当前正在执行的节点
    node_states: Dict[str, str]       # {node_id: "pending"|"active"|"completed"|"failed"|"skipped"}
    created_at: datetime
```

> **设计决策记录：去掉 PipelineTemplate / PipelineInstance / StageDefinition**
>
> 原设计中 Pipeline 有独立的数据结构（PipelineTemplate、PipelineInstance、StageDefinition、RollbackRule）。
> 经讨论后统一为 ProcessDefinition：
> - PipelineTemplate → ProcessDefinition(scope="pipeline")
> - StageDefinition → ActivityNode(sub_process_type=CALL_ACTIVITY)
> - gate_type → GatewayNode(gate_config={...})
> - RollbackRule → FlowEdge(flow_type=conditional, label="request_changes")
> - PipelineInstance → ProcessInstance(scope="pipeline")
>
> 好处：整个系统只有一种流程定义格式，从项目级到 Agent 级完全统一。

## 四、阶段级与 Agent 级流程定义

### 4.1 三层流程模型

所有层次都是 ProcessDefinition（nodes + edges），区别在于作用域和驱动者：

```
┌─────────────────────────────────────────────────────────────────┐
│  阶段级流程（flow 驱动，多 Agent 协作）                          │
│                                                                 │
│  iterative_development                                          │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐                  │
│  │implement │───>│code_review│───>│ testing  │                  │
│  │developer │    │tech_lead  │    │ tester   │                  │
│  │          │    │          │    │          │                  │
│  │call:     │    │call:     │    │          │                  │
│  │ tdd_wf   │    │ review_wf│    │          │                  │
│  └────┬─────┘    └──────────┘    └──────────┘                  │
│       │                                                         │
│       │ call_process_id 引用 Agent 级流程                        │
│       ▼                                                         │
│  ┌─────────────────────────────────────────────────────┐       │
│  │  Agent 级流程（runtime 驱动，单 Agent 内部）          │       │
│  │                                                     │       │
│  │  tdd_workflow                                       │       │
│  │  ┌─────────┐  ┌──────────┐  ┌─────────┐           │       │
│  │  │read_task│─>│write_test│─>│run_red  │           │       │
│  │  └─────────┘  └──────────┘  └────┬────┘           │       │
│  │                                   │                │       │
│  │  ┌──────────┐  ┌──────────┐  ┌───▼─────┐         │       │
│  │  │ submit   │<─│ verify   │<─│write_code│         │       │
│  │  └──────────┘  └──────────┘  └─────────┘         │       │
│  └─────────────────────────────────────────────────────┘       │
└─────────────────────────────────────────────────────────────────┘
```

| | 阶段级流程 | Agent 级流程 |
|---|-------------|---------------|
| 驱动者 | flow (daemon) | runtime |
| 参与者 | 多个 Agent | 单个 Agent |
| 节点的 actor | 不同角色 | 固定为当前 Agent（self） |
| 嵌套 | 可以通过 Call Activity 引用 Agent 级流程 | 不再嵌套（叶子节点） |
| 安装方式 | 项目配置 / 阶段关联 | 角色定义的 workflows 字段 |

### 4.2 模板格式规范

> **设计决策记录：统一使用 BPMN 2.0 ProcessDefinition 格式**
>
> 所有层次的流程（项目级、阶段级、Agent 级）都使用同一套格式：
> - nodes：节点列表（EventNode / ActivityNode / GatewayNode）
> - edges：边列表（FlowEdge）
> - data_objects：数据对象（可选）
> - artifacts：制品/注释（可选）
> - pool：泳道（可选）
>
> 详细的数据结构定义见第十四章 14.10 BPMN 2.0 完整建模。

```yaml
# ProcessDefinition 统一格式
process_id: string                # 唯一标识
name: string                      # 显示名称
description: string

nodes:                            # 节点列表 — BPMN 三大类
  - id: string
    category: string              # event | activity | gateway
    # event 专属：event_position, event_trigger, ...
    # activity 专属：task_type, actor, action, output_schema, ...
    # gateway 专属：gateway_type, direction, condition_field, routes, ...

edges:                            # 边列表 — 连接线
  - id: string
    flow_type: string             # sequence | conditional | default | message | association
    source: string                # 起始节点 ID
    target: string                # 目标节点 ID
    label: string                 # 线上文字（如 "approved"）
    condition: string             # 条件表达式（conditional 类型时）

data_objects:                     # 数据对象（可选）
  - id: string
    data_type: string             # data_object | data_input | data_output | data_store
    name: string
    attached_to: string           # 关联的节点 ID

artifacts:                        # 制品/注释（可选）
  - id: string
    artifact_type: string         # annotation | group
    text: string
    attached_to: string

pool:                             # 泳道（可选）
  id: string
  name: string
  lanes:
    - id: string
      name: string
      role_id: string
      node_ids: [string]
```

> 完成条件：
> - 阶段级/项目级节点：通过 `output_schema` + `submit_step_result` 工具（LLM function calling 保证格式）
> - Agent 级节点：保留 `done_when`（由 AgentWorkflowEngine 在 runtime 内部判断）
> - 门禁：通过 Gateway + `gate_config`（User Task 等待用户操作）

#### 4.3.2 requirement_analysis — 需求理解

```yaml
# requirement_analysis — 需求理解阶段流程定义
#
# 设计意图：
#   这是六阶段中的第一个实质阶段（阶段 0 只是启动）。
#   目标是从用户的模糊想法中提炼出结构化的需求文档（PRD）。
#   流程设计为"收集→讨论→撰写→评审→确认"五步，
#   其中讨论和评审是 AdHocSubProcess（多人自由发言），
#   最后的用户确认是 UserTask（硬门禁，必须人类操作）。
#
# 为什么用 AdHocSubProcess 而不是多个 AbstractTask：
#   讨论没有固定顺序，参与者自由发言，不适合用线性流程表达。
#   AdHocSubProcess 的语义就是"内部活动无固定顺序"。
#
# 为什么最后有 UserTask：
#   需求确认是不可逆的决策点（进入方案拆解后再改需求代价很大），
#   必须由人类用户明确确认，不能由 AI 自动通过。

process_id: requirement_analysis
name: "需求理解"
description: "收集需求、团队讨论、撰写 PRD、评审确认"

nodes:
  - id: start
    category: event
    event_position: start
    event_trigger: none

  - id: collect
    category: activity
    task_type: abstract
    name: "收集需求信息"
    actor: tech_lead
    action: "与用户沟通，收集需求细节，整理需求要点。"
    allowed_tools: [file_read, file_write, search_docs, ask_teammate]
    output_schema:
      type: object
      properties:
        functional_requirements: { type: array, items: { type: string } }
        non_functional_requirements: { type: array, items: { type: string } }
        constraints: { type: array, items: { type: string } }
        open_questions: { type: array, items: { type: string } }
      required: [functional_requirements]

  - id: brainstorm
    node_type: ad_hoc_sub_process
    name: "团队头脑风暴"
    ordering: parallel
    completion_condition: coordinator_submit
    participant_ids: [tech_lead, backend_dev, frontend_dev, tester]
    coordinator_id: tech_lead
    metadata:
      agenda: "从各自角色角度讨论需求的可行性、风险和建议"
    allowed_tools: [file_read, search_docs]
    output_schema:
      type: object
      properties:
        suggestions: { type: array, items: { type: string } }
        risks: { type: array, items: { type: string } }
        decisions: { type: array, items: { type: string } }
      required: [suggestions, decisions]

  - id: write_prd
    category: activity
    task_type: abstract
    name: "撰写 PRD"
    actor: tech_lead
    action: "基于需求收集和头脑风暴结果，撰写正式 PRD 文档。"
    input_refs: [collect.output, brainstorm.output]
    allowed_tools: [file_read, file_write]
    output_schema:
      type: object
      properties:
        prd_path: { type: string }
        summary: { type: string }
      required: [prd_path, summary]

  - id: review_prd
    node_type: ad_hoc_sub_process
    name: "PRD 评审"
    ordering: parallel
    completion_condition: coordinator_submit
    participant_ids: [tech_lead, backend_dev, frontend_dev, tester]
    coordinator_id: tech_lead
    metadata:
      agenda: "评审 PRD 文档，提出修改意见或确认通过"
    input_refs: [write_prd.output]
    allowed_tools: [file_read]
    output_schema:
      type: object
      properties:
        verdict: { type: string, enum: [approved, needs_revision] }
        comments: { type: array, items: { type: string } }
      required: [verdict]

  - id: review_decision
    category: gateway
    gateway_type: exclusive
    direction: diverging
    name: "评审结果判断"
    condition_field: review_prd.output.verdict
    default: write_prd

  - id: end
    category: event
    event_position: end
    event_trigger: none

edges:
  - { id: e1, flow_type: sequence, source: start, target: collect }
  - { id: e2, flow_type: sequence, source: collect, target: brainstorm }
  - { id: e3, flow_type: sequence, source: brainstorm, target: write_prd }
  - { id: e4, flow_type: sequence, source: write_prd, target: review_prd }
  - { id: e5, flow_type: sequence, source: review_prd, target: review_decision }
  - { id: e6, flow_type: conditional, source: review_decision, target: end, label: "approved", condition: "verdict == 'approved'" }

#### 4.3.3 design_and_planning — 方案拆解与实施准备

```yaml
# design_and_planning — 方案拆解阶段流程定义
#

#### 4.3.4 iterative_development — 迭代开发与测试

```yaml
# iterative_development — 迭代开发阶段流程定义（任务级）
#
# 设计意图：
#   这是单个任务（如 TASK-003 标签系统）的开发流水线。
#   每个任务走"编码→审查→测试"三步，审查有通过/打回分支。
#   如果 TL 指定了 control_level=enforced + process_id=tdd_workflow，
#   则编码步骤内部还会走 TDD 工作流（由 runtime 的 WorkflowEngine 驱动）。
#
# 为什么审查后有 ExclusiveGateway：
#   代码审查只有两种结果：通过或打回。
#   通过 → 进入测试；打回 → 回到编码（Agent 根据审查意见修改）。
#   这是 BPMN 的标准模式：Activity → Gateway → 条件分支。
#
# 为什么编码节点用 CallActivity 引用 tdd_workflow：
#   TDD 工作流是 Agent 级的（写测试→运行红灯→写代码→运行绿灯→检查），
#   由 runtime 的 BPMNEngine 驱动，不是 flow 驱动。
#   flow 只知道"编码"这一步，不知道内部有几个子步骤。

#### 4.3.7 bugfix — 修复流程

> **设计更新：对齐 BUG 完整生命周期（指派→确认→修复→指派验证人→验证→关闭）**
>
> 原设计只有 reproduce→locate→fix→verify 四步。
> 更新后体现完整的指派流转：
> - BUG 创建时指定 reporter + assignee
> - 修复完成后自动指派给验证人（通常是 reporter）
> - 验证不通过时重新指派给处理人

```yaml

      验证修复是否解决了问题，执行回归测试。
      注意：不要只验证报告的问题，也检查相关功能是否受影响。
      验证通过 → workitem_transition(status='closed')
      验证不通过 → workitem_transition(status='reopen') + workitem_assign(assignee=developer)
    input_refs: [reproduce.output, fix.output]
    allowed_tools: [file_read, code_execute, workitem_transition, workitem_assign]
    output_schema:
      type: object
      properties:
        bug_fixed: { type: boolean }
        regression_passed: { type: boolean }
        verdict: { type: string, enum: [passed, failed] }
        comments: { type: string }
      required: [bug_fixed, regression_passed, verdict]

  - id: verify_decision
    category: gateway
    gateway_type: exclusive
    direction: diverging
    name: "验证结果判断"
    condition_field: verify.output.verdict
    default: fix

  - id: end
    category: event
    event_position: end
    event_trigger: none

  - id: end_rejected
    category: event
    event_position: end
    event_trigger: none
    name: "BUG 被拒绝/无法复现"

edges:
  - { id: e1, flow_type: sequence, source: start, target: confirm }
  - { id: e2, flow_type: sequence, source: confirm, target: confirm_decision }
  - { id: e3, flow_type: conditional, source: confirm_decision, target: reproduce, label: "is_bug=true", condition: "is_bug == true" }
  - { id: e4, flow_type: default, source: confirm_decision, target: end_rejected, label: "not a bug" }
  - { id: e5, flow_type: sequence, source: reproduce, target: locate }
  - { id: e6, flow_type: sequence, source: locate, target: fix }
  - { id: e7, flow_type: sequence, source: fix, target: verify }
  - { id: e8, flow_type: sequence, source: verify, target: verify_decision }
  - { id: e9, flow_type: conditional, source: verify_decision, target: end, label: "passed", condition: "verdict == 'passed'" }
  - { id: e10, flow_type: default, source: verify_decision, target: fix, label: "failed (reopen)" }
```

## 五、flow 与 runtime 的接口

### 5.1 统一消息接口

> **设计决策：从 NodeAssignment 特殊对象改为统一消息**
>
> 原设计中 flow 通过 NodeAssignment 这个特殊对象下发任务。
> 经讨论后改为统一消息格式，和群聊消息、用户消息走同一个入口。
> 详见 `docs/design/Agent统一模型与三级控制设计.md`。

flow → runtime 的所有通信都是"消息"（FlowMessage 来自 quantalithos-core）：

```python
from quantalithos_core.protocol import FlowMessage

# 消息类型（6 种，和 BPMN 对齐）：
# "agent_create"     — 创建 Agent 实例
# "agent_destroy"    — 销毁 Agent 实例
# "agent_suspend"    — 挂起 Agent
# "agent_resume"     — 恢复 Agent
# "node_execute"     — 执行 BPMN 节点（payload 带序列化的 FlowNode）
# "node_cancel"      — 取消正在执行的节点
# "chat_message"     — 聊天消息（群聊/私聊/ask_reply 统一）
```

**node_execute 的 payload（NodeExecutePayload）：**

```python
{
    "process_instance_id": "pi-001",
    "node": {                              # 序列化的 FlowNode
        "node_type": "abstract_task",
        "id": "implement",
        "name": "编码实现",
        "action": "实现文章标签系统",
        "actor": "backend-dev-1",
        "allowed_tools": ["file_read", "file_write", "code_execute", "git_commit"],
        "output_schema": { ... }
    },
    "control_level": "enforced",
    "process_id": "tdd_workflow",
    "input_refs": ["TASK-003"],
    "suspicion_hints": ["前序产出可能有遗漏，请独立验证"]
}
```

> **设计决策记录：消息类型从 10 种精简为 6 种**
>
> 旧设计：task_assign / session_start / session_end / ask_reply / task_cancel 等自造概念。
> 新设计：节点执行统一为 node_execute，payload 带序列化的 FlowNode。
> runtime 收到后反序列化为具体类型，BPMNEngine 按 node_type 查表调用策略。
> 详见 core 概要设计第四章。

### 5.2 统一的 NodeResult

NodeResult 来自 quantalithos-core（`from quantalithos_core.protocol import NodeResult`）。

> **新增字段：reasoning_trace**
>
> 来源：可追溯性论文（arxiv 2510.07614）。
> Agent 提交结果时附带推理链摘要，记录"为什么这么做"。
> 用于审计和错误追溯。Phase 1 可选，Phase 2 必填。

### 5.3 持久执行

> **来源：持久执行调研（docs/research/study-durable-execution.md）**
>
> Checkpoint ≠ 持久执行。flow daemon 需要从"手动快照"升级为"每步自动持久化"。

**Phase 1：每步写入状态文件**

```
daemon 发送 node_execute 消息：
  → 写入 snapshots/workflow/current.yaml
  → 记录 message_id + 状态 = "dispatched"

daemon 收到 NodeResult：
  → 更新 current.yaml
  → 记录 message_id + 状态 = "completed"

daemon 崩溃重启：
  → 读取 current.yaml
  → 检查每个消息的状态
  → dispatched 但没有 completed → 查询 runtime 确认状态
  → 从精确位置继续
```

## 六、任务调度（platform 驱动 + flow 监听）

> **设计更新：任务调度从 flow 移到 platform**
>
> 原设计中 flow 有 TaskScheduler / TaskInstance / DependencyGraph，负责任务调度。
> 经讨论后改为：
> - 任务依赖图、状态流转、自动指派 → platform 驱动
> - flow 监听 platform 事件，在 Agent 需要执行时发 FlowMessage 告诉 Agent 怎么做
>
> 原因：任务调度本质上是"工单状态流转 + 依赖检查"，和 CodeArts/Jira 一样属于平台职责。
> flow 的核心职责收窄为：阶段内流程编排 + 阶段间推进 + 门禁 + AdHocSubProcess + Agent 指令。

### 6.1 三层职责划分

```
platform 管"东西"的状态：
  工单生命周期（created → in_progress → in_review → completed）
  自动指派（状态变更时切换 assignee）
  任务依赖图（TL 触发 start_execution 后自动调度）
  通知推送（WorkItemAssigned 事件）

flow 管"活动"的编排：
  阶段内流程（collect → brainstorm → write_prd → review → 门禁）
  阶段间推进（需求完成 → 设计开始）
  监听 platform 事件 → 向 runtime 发 FlowMessage
  AdHocSubProcess 发起（头脑风暴、设计评审）
  Agent 生命周期指令

runtime 管 Agent 的"大脑"：
  接收 FlowMessage → Agent 执行 → 上报结果
```

### 6.2 flow 如何响应 platform 的任务事件

```
platform 发布事件                flow 监听并处理
──────────────────────────────────────────────────────────────

WorkItemAssigned                flow 收到事件：
  { workitem_id: "TASK-003",     "TASK-003 被指派给 backend-dev-1"
    new_assignee: "be-1",
    reason: "dependency_met" }   flow 判断：
                                   Agent be-1 是否已创建？
                                   ├── 没有 → 先发 agent_create
                                   └── 已有 → 直接发任务

                                 flow 构造 FlowMessage：
                                   type: "node_execute"
                                   agent_id: "backend-dev-1"
                                   payload: {
                                     action: "实现标签系统"
                                     control_level: "enforced"
                                     process_id: "tdd_workflow"
                                     allowed_tools: [...]
                                     output_schema: {...}
                                     suspicion_hints: [...]
                                   }
                                 → 发送给 runtime

WorkItemStatusChanged           flow 收到事件：
  { workitem_id: "TASK-003",     "TASK-003 状态变为 in_review"
    from: "in_progress",
    to: "in_review" }            flow 判断：
                                   in_review 意味着需要 TL 审查
                                   → 构造 FlowMessage 给 TL
                                   → 注入审查相关的工具和提示

AllTasksCompleted               flow 收到事件：
  { project_id: "blog" }         "博客项目所有任务完成"
                                 → 推进到下一阶段（验收）
```

### 6.3 flow 不再管的事

```
以下职责已移到 platform：

  ❌ TaskInstance 数据结构 → platform 的 workitems 表
  ❌ DependencyGraph → platform 的 workitem_dependencies 表
  ❌ dispatch_ready_tasks → platform 的 start_execution + 自动调度
  ❌ on_task_completed 检查下游 → platform 自动检查
  ❌ 波次计算 → platform 根据依赖图自动确定
  ❌ TaskProvider 抽象 → 不需要了，platform 就是唯一数据源
```

### 6.4 iterative_development 工作流的变化

```
原设计：
  iterative_development.yaml 定义了 implement → code_review → testing
  flow 按这个工作流调度三个 Agent

新设计：
  implement → code_review → testing 不再是独立的工作流
  而是工单状态机的自然流转：
    in_progress（开发）→ in_review（审查）→ in_testing（测试）→ completed

  platform 驱动状态流转 + 自动指派
  flow 监听状态变更事件 → 向对应 Agent 发 FlowMessage

  iterative_development.yaml 仍然保留，但用途变了：
    不再用于"调度三个 Agent 的顺序"
    而是用于"告诉 flow 每个状态对应什么 FlowMessage 配置"

  例：
    in_progress 状态 → FlowMessage 配置：
      control_level: "enforced"
      process_id: "tdd_workflow"
      allowed_tools: [file_read, file_write, code_execute, git_commit]

    in_review 状态 → FlowMessage 配置：
      control_level: "free"
      allowed_tools: [file_read, git_diff]
      suspicion_hints: ["前序代码可能有错，请独立验证"]

    in_testing 状态 → FlowMessage 配置：
      control_level: "free"
      allowed_tools: [file_read, code_execute]
      suspicion_hints: ["实现代码可能有 BUG，请从用户视角独立测试"]
```

## 七、三种交互模式

现实开发中，团队协作有三种本质不同的活动。我们的架构需要分别建模，而不是用统一的"消息路由"混在一起。

### 7.1 三种模式总览

```
┌─────────────────────────────────────────────────────────────┐
│  模式 1：任务执行（Task Execution）                          │
│                                                             │
│  flow 分配任务 → Agent 独立执行 → 上报结果                   │
│                                                             │
│  现实类比：开发者在工位上写代码                               │
│  特征：一对一、异步、结构化输入输出                           │
├─────────────────────────────────────────────────────────────┤
│  模式 2：协作活动（AdHocSubProcess）                          │
│                                                             │
│  daemon 发起会议 → 多人参与讨论 → 主持人总结结论              │
│                                                             │
│  现实类比：需求评审会、设计评审会                             │
│  特征：多对多、同步、有主持人和议程、有明确结论               │
├─────────────────────────────────────────────────────────────┤
│  模式 3：即时沟通（Instant Messaging）                       │
│                                                             │
│  Agent 执行任务时遇到问题 → @某人问一句 → 得到回答 → 继续    │
│                                                             │
│  现实类比：Slack 里 @同事问一个问题                          │
│  特征：一对一、异步、非结构化、无明确结束                     │
└─────────────────────────────────────────────────────────────┘
```

| | 任务执行 | 协作会议 | 即时沟通 |
|---|---------|---------|---------|
| 参与者 | 1 个 Agent | 多个 Agent + 用户 | 2 个 Agent |
| 触发 | flow 分配 step | flow 发起 AdHocSubProcess | Agent 调用工具 |
| 结束 | Agent submit_step_result | 主持人 submit_step_result | 对方回复 |
| 产出 | 结构化（output_schema） | 结构化（会议结论） | 非结构化（自然语言） |
| 归属 | flow 调度 + runtime 执行 | flow 管理 + runtime 执行 | runtime 工具 + flow 路由 |
| 是否是 step | 是 | 是 | 不是 |

### 7.2 Assignment 与 NodeResult

| 模式 | FlowMessage.type | 关键字段 |
|------|-------------------|---------|
| 任务执行 | solo | agent_id, action, call_process_id |
| 协作会议 | collaboration | moderator_id, participant_ids, agenda |
| 即时沟通 | — | 不使用 FlowMessage，是 Agent 的 ask_teammate 工具调用 |

### 7.6 模式 3：即时沟通（Instant Messaging）

即时沟通不是 step，是 Agent 在执行任务时可以使用的一个工具：

```python
# runtime 内置工具
class AskTeammateTool(Tool):
    name = "ask_teammate"
    description = "向团队成员提问，等待回复"

    async def execute(self, target: str, question: str) -> str:
        """
        1. runtime 将问题发送给 flow
        2. flow 路由消息给目标 Agent
        3. 目标 Agent 回复
        4. flow 将回复路由回来
        5. 作为工具结果返回给调用者
        """
```

```
例：后端开发在实现标签系统时遇到问题

backend-dev-1 执行 implement step
    │
    │ think: 标签表 name 字段要不要加唯一索引？不确定，问一下 TL
    │ act:   ask_teammate(target="tech-lead", question="标签表 name 要加唯一索引吗？")
    │
    ▼
runtime → flow（路由消息给 tech-lead）
    │
    ▼
tech-lead 收到问题，回复："加，防止重复标签"
    │
    ▼
flow → runtime（路由回复给 backend-dev-1）
    │
    ▼
ask_teammate 工具返回："加，防止重复标签"
    │
    ▼
backend-dev-1 继续执行 think→act 循环
    │ think: 好的，加唯一索引
    │ act:   file_write(tag.rs)  # 加上唯一索引
```

**即时沟通与协作会议的区别：**

| | 协作会议 | 即时沟通 |
|---|---------|---------|
| 触发 | flow 发起 FlowMessage | Agent 调用 ask_teammate 工具 |
| 参与者 | 预定义的参与者列表 | 调用者指定一个目标 |
| 上下文 | 所有人共享同一个讨论上下文 | 一问一答，不影响其他人 |
| 结束 | 主持人 submit_step_result | 对方回复即结束 |
| 是否阻塞 step | 是（整个 step 就是讨论） | 是（等待回复，但 step 继续） |
| 记录 | 群聊历史 | Agent 对话历史中的工具调用记录 |

## 八、门禁系统

### 8.1 门禁出现的位置

门禁出现在两个地方，机制相同：

| 位置 | 说明 | 示例 |
|------|------|------|
| 阶段边界 | 从一个阶段进入下一个阶段时 | requirement → design：用户确认 PRD |
| step 内部 | 某些 step 的结果需要用户确认 | user_acceptance：用户验收功能 |

### 8.2 门禁类型

| 类型 | 说明 | 示例 |
|------|------|------|
| hard | 必须用户操作确认 | 阶段 1→2 用户确认 PRD，阶段 4→5 用户最终确认 |
| soft | 默认自动通过，可配置为需要确认 | 阶段 2→3 设计评审 |

> **设计决策记录：去掉 done_when 和 output_schema 作为门禁类型**
>
> 原设计中 done_when 和 output_schema 也列为门禁类型。经讨论后：
> - done_when 已被 output_schema + submit_step_result 工具替代（见第四章）
> - output_schema 的校验由 LLM function calling 在工具调用时保证，不是门禁
> - 门禁只指"需要人类操作确认"的环节，系统自动校验不算门禁

    │   │
    │   ▼

    │   │

    ▼

```

**expired — 超时：**

    │

## 十三、设计决策记录

### 13.1 Agent 级工作流命名讨论

> **状态：待定，暂不修改**
>
> 当前 Agent 级工作流使用 `scope: "agent"`，存放在 `workflow_templates/agent/` 目录下，项目级 step 通过 `workflow` 字段引用。
>
> 讨论中提出：项目级和 Agent 级都叫 workflow 看起来混淆。现实开发中两者的叫法不同：
>
> - 项目级：流程（Process / Workflow）— 多人协作，关注谁做什么、什么顺序、什么门禁
> - Agent 级：规程（Procedure / Practice）— 单人执行，关注怎么做、什么步骤、什么规范
>
> 如果采纳，变更范围：
>
> ```
> scope: "agent"              → scope: "procedure"
> workflow_templates/agent/   → procedure_templates/
> step.workflow: tdd_workflow  → step.procedure: tdd
> ```
>
> 暂不修改的原因：当前格式统一（同一套 YAML 结构），改名涉及 flow 和 runtime 两侧文档同步更新，等核心设计稳定后再评估。

### 13.2 移除 exit_conditions / entry_requirements

> **状态：已采纳**
>
> 原设计中 StageTransition 包含 `exit_conditions` 和 `entry_requirements` 字段。移除原因：
> - 与工作流模板中 step 的 done_when 重复检查
> - 自然语言字符串，系统无法自动校验
> - "用户已确认"是 gate_type: hard 的职责
>
> 简化后：所有 step completed + gate passed = 进入下一阶段。

### 13.3 移除 ProjectStage 硬编码枚举

> **状态：已采纳**
>
> 原设计中阶段是 Python 枚举（STAGE_0 ~ STAGE_5）。改为配置驱动的 PipelineTemplate，原因：
> - 不同项目类型需要不同阶段数量（standard 6 个，hotfix 3 个）
> - 无法加减阶段
> - 与"流程模板可配置、可裁剪"的设计原则矛盾

### 7.2 持久化时机

```python
# infra/state_persister.py

class StatePersister:
    """每步持久化 — Phase 1 文件写入"""

    def __init__(self, snapshot_dir: str = "snapshots/workflow"):
        self.snapshot_dir = snapshot_dir
        self.current_path = f"{snapshot_dir}/current.yaml"

    async def save(self, state: FlowState):
        """写入 current.yaml（原子写入：先写 tmp 再 rename）"""
        data = {
            "project_id": state.project_id,
            "pipeline_instance": state.pipeline_instance.dict() if state.pipeline_instance else None,
            "stage_instance": state.stage_instance.dict() if state.stage_instance else None,
            "pending_messages": state.pending_messages,
            "gate_history": state.gate_history,
            "last_updated": datetime.now().isoformat(),
        }
        tmp_path = f"{self.current_path}.tmp"
        with open(tmp_path, 'w') as f:
            yaml.dump(data, f, allow_unicode=True)
        os.rename(tmp_path, self.current_path)  # 原子操作

    async def load(self) -> Optional[FlowState]:
        """从 current.yaml 恢复状态"""
        if not os.path.exists(self.current_path):
            return None
        with open(self.current_path) as f:
            data = yaml.safe_load(f)
        return FlowState.from_snapshot(data)
```

### 7.3 崩溃恢复流程

```
daemon 启动时：
  1. state_persister.load() → 读取 current.yaml
  2. 如果有 pending_messages（status=dispatched 但没有 completed）：
     → 查询 runtime：GET /agents/{agent_id}/status
     → 如果 Agent 还在执行 → 等待 NodeResult
     → 如果 Agent 已完成但 flow 没收到 → 重新请求结果
     → 如果 Agent 不存在 → 重新发 FlowMessage
  3. 恢复 BPMNEngine 状态 → 继续执行
```

## 八、PlatformListener 完整实现

```python
# business/platform_listener.py

class PlatformListener:
    """监听 platform 事件，触发流程推进"""

    def __init__(self, event_bus, flow_engine: FlowEngine, state: FlowState):
        self.event_bus = event_bus
        self.flow_engine = flow_engine
        self.state = state

    async def start(self):
        """订阅 platform 事件总线"""
        receiver = self.event_bus.subscribe()
        while True:
            event = await receiver.recv()
            await self.handle_event(event)

    async def handle_event(self, event: PlatformEvent):
        """根据事件类型分发处理"""
        match event.event_type:
            case "WorkItemAssigned":
                await self.on_workitem_assigned(event)
            case "TaskBecameReady":
                await self.on_task_became_ready(event)
            case "AllTasksCompleted":
                await self.on_all_tasks_completed(event)
            case "WorkItemStatusChanged":
                await self.on_status_changed(event)

    async def on_workitem_assigned(self, event: PlatformEvent):
        """工单被指派 → 构造 FlowMessage 发给 runtime"""
        data = event.data
        workitem_id = data["workitem_id"]
        assignee_id = data["assignee_id"]

        # 从 platform 读取工单详情（含 workflow_config）
        workitem = await self.platform_client.get_workitem(workitem_id)
        workflow_config = workitem.get("metadata", {}).get("workflow_config", {})

        # 确定控制级别和工作流
        control_level = workflow_config.get("control_level", "free")
        process_definition = None
        if control_level == "enforced":
            process_id = workflow_config.get("process_id")
            if process_id:
                template = await self.platform_client.get_process(process_id)
                process_definition = template.get("definition")

        # 构造 AbstractTask 节点
        node = AbstractTask(
            id=workitem_id,
            node_type="abstract_task",
            name=workitem["title"],
            action=workitem.get("description", ""),
            actor=assignee_id,
            allowed_tools=workflow_config.get("allowed_tools", []),
            output_schema=workflow_config.get("output_schema"),
        )

        # 构造 FlowMessage
        msg = FlowMessage(
            message_id=generate_id(),
            type="node_execute",
            agent_id=assignee_id,
            project_id=event.project_id,
            payload=NodeExecutePayload(
                process_instance_id=self.state.stage_instance.instance_id,
                node=node.dict(),
                control_level=control_level,
                process_definition=process_definition,
                input_refs=[workitem_id],
                allowed_tools=node.allowed_tools,
                output_schema=node.output_schema,
            ).dict(),
            created_at=datetime.now(),
        )

        await self.runtime_client.send(msg)
        self.state.pending_messages[msg.message_id] = {
            "status": "dispatched",
            "agent_id": assignee_id,
            "node_id": workitem_id,
            "sent_at": datetime.now().isoformat(),
        }
        await self.state_persister.save(self.state)

    async def on_task_became_ready(self, event: PlatformEvent):
        """依赖满足的任务就绪 → 和 on_workitem_assigned 相同处理"""
        await self.on_workitem_assigned(event)

    async def on_all_tasks_completed(self, event: PlatformEvent):
        """所有任务完成 → 推进阶段"""
        # 当前阶段的 EndEvent 被触发
        # BPMNEngine 会自动处理（FlowEndEventStrategy）
        pass

    async def on_status_changed(self, event: PlatformEvent):
        """工单状态变更 → 通知 chat 更新看板"""
        # 通过 gate WebSocket 推送给前端
        pass
```

## 十二、幂等设计

### 12.1 重复事件场景

```
场景 1：NodeResult 重复上报
  runtime 上报 NodeResult → 网络超时 → runtime 重试 → flow 收到两次

场景 2：gate_response 重复操作
  用户点击"批准" → 网络慢 → 用户再点一次 → flow 收到两次

场景 3：platform 事件重复投递
  Phase 2 Redis Pub/Sub 的 at-least-once 语义
```

### 12.2 幂等方案

```
NodeResult 幂等：
  幂等键：result.message_id（对应 FlowMessage.message_id）
  幂等窗口：pending_messages 字典（已发送的消息 ID）
  实现方式：

  async def handle_node_result(self, result: NodeResult):
      # 幂等检查：该 message_id 是否已处理
      current = self.state.pending_messages.get(result.message_id)
      if current != "dispatched":
          # 已处理过（completed/failed/blocked）→ 静默忽略
          logger.info("duplicate_result", message_id=result.message_id)
          return
      
      # 标记为已处理
      self.state.pending_messages[result.message_id] = result.result_type
      # ... 正常处理

gate_response 幂等：
  幂等键：gate_id
  幂等窗口：pending_gates 列表
  实现方式：

  async def handle_gate_response(self, gate_id, action, comment):
      gate = self.find_pending_gate(gate_id)
      if gate is None:
          # 已处理过（不在 pending 列表中）→ 静默忽略
          return
      # ... 正常处理（处理后从 pending_gates 移除）
```

### 12.3 各事件类型的幂等行为

| 事件类型 | 幂等键 | 幂等行为 |
|---------|--------|---------|
| NodeResult | message_id | pending_messages 状态检查 |
| gate_response | gate_id | pending_gates 存在性检查 |
| platform WorkItemAssigned | workitem_id + status | 检查是否已为该工单发过 FlowMessage |
| platform AllTasksCompleted | project_id | 检查 Pipeline 是否已推进到验收阶段 |

## 十三、node_states 转换矩阵

### 13.1 节点状态定义

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| pending | 未开始（初始状态） | 否 |
| running | 正在执行（已发 FlowMessage，等待 NodeResult） | 否 |
| completed | 已完成 | 是 |
| failed | 执行失败（超过重试次数） | 是 |
| skipped | 被跳过（条件分支中未走到的路径） | 是 |

### 13.2 转换矩阵

| 从 \ 到 | pending | running | completed | failed | skipped |
|---------|---------|---------|-----------|--------|---------|
| pending | — | ✅ 发送 FlowMessage | ❌ | ❌ | ✅ 条件分支未走到 |
| running | ✅ 重试（重置为 pending 再重新执行） | — | ✅ NodeResult(completed) | ✅ NodeResult(failed) 且超过重试 | ❌ |
| completed | ❌ 终态 | ❌ | — | ❌ | ❌ |
| failed | ❌ 终态 | ❌ | ❌ | — | ❌ |
| skipped | ❌ 终态 | ❌ | ❌ | ❌ | — |

### 13.3 非法转换处理

| 非法转换 | 触发场景 | 处理策略 |
|---------|---------|---------|
| completed → running | 已完成的节点收到重复的 NodeResult | 静默忽略（幂等） |
| failed → running | 已失败的节点收到迟到的 NodeResult | 静默忽略 |
| pending → completed | 跳过执行直接完成 | 不允许 — 必须经过 running |
| running → skipped | 正在执行的节点被跳过 | 先 cancel（发 node_cancel），再标记 skipped |

    config_path: pathlib.Path,
    project_id: str | None = None,
) -> DaemonDependencies:
    flow_config = FlowConfig.from_yaml(config_path)
    if project_id:
        flow_config = dataclasses.replace(flow_config, project_id=project_id)

    runtime = RuntimeClient(
        base_url=flow_config.runtime.base_url,
        timeout_secs=flow_config.runtime.timeout_secs,
    )
    platform = PlatformClient(

    )
    persister = StatePersister(snapshot_path=pathlib.Path(flow_config.persistence.path))
    persister.ensure_parent_dir()

    gate = GateController(platform_client=platform)
    lifecycle = AgentLifecycleManager(runtime_client=runtime)
    engine = FlowEngine(
        process_manager=ProcessManager(),
        runtime_client=runtime,
        platform_client=platform,
        gate_controller=gate,
        agent_lifecycle_manager=lifecycle,
    )
    listener = PlatformListener(
        platform_client=platform,
        flow_engine=engine,
        agent_lifecycle_manager=lifecycle,
    )
    daemon = EventLoop(
        project_id=flow_config.project_id,
        idle_sleep_secs=flow_config.daemon.idle_sleep_secs,
        state_persister=persister,
        flow_engine=engine,
        platform_listener=listener,
        platform_client=platform,
        agent_lifecycle_manager=lifecycle,
    )
    return DaemonDependencies(config=flow_config, daemon=daemon, flow_engine=engine)

`run_daemon()` 在 `config.api.enabled=true` 时会并发运行两条主通路：一条是 `EventLoop.run()` 的后台编排循环，另一条是 `uvicorn` 托管的 `daemon/http_api.py` ingress；任一侧退出时，另一侧会收到协同停机信号。

### 14.3 EventLoop 骨架

```python
@dataclasses.dataclass(slots=True)
class EventLoop:
    project_id: str
    idle_sleep_secs: float
    state_persister: StatePersister
    flow_engine: FlowEngine
    platform_listener: PlatformListener
    platform_client: PlatformClient
    agent_lifecycle_manager: AgentLifecycleManager | None = None
    state: FlowState | None = None
    _stop_event: asyncio.Event = dataclasses.field(default_factory=asyncio.Event)
    _node_result_queue: collections.deque[NodeResult] = dataclasses.field(
        default_factory=collections.deque
    )

    def __post_init__(self) -> None:
        self.flow_engine.node_result_handler = self.handle_node_result

    async def run(self) -> None:
        self.state = await self.state_persister.load(self.project_id)
        if self.state is None:
            self.state = await self.initialize_project(self.project_id)
        while not self._stop_event.is_set():
            await self.wait_for_event()
```

## 十五、EventLoop 并发分析

### 15.1 并发模型

flow daemon 基于 Python asyncio 单线程事件循环。
EventLoop.run() 是一个 while 循环；每轮从 platform 拉取一批新事件，没有事件时短暂 sleep。

```
asyncio 事件循环（单线程）
  │
  └── EventLoop.run()
      └── while not stop_event:
          await wait_for_event()
            ├─ poll platform events
            ├─ for event in events: await handle_platform_event(event)
            └─ no events -> asyncio.sleep(idle_sleep_secs)

关键保证：
  ✅ 事件严格串行处理（不会并发处理两个事件）
  ✅ 每个事件处理完后立即持久化（崩溃恢复不丢事件）
  ❌ 但 handle_* 内部的 await 点可能导致事件积压
```

### 15.2 潜在问题

| # | 场景 | 风险 | 应对 |
|---|------|------|------|
| 1 | handle_node_result 中 await runtime_client.send() 很慢 | 后续事件积压 | 设置超时（10s），超时后记录日志继续 |
| 2 | 多个 NodeResult 同时到达 | 不会并发处理（串行队列） | 无风险，但处理延迟可能增加 |
| 3 | gate_response 和 NodeResult 同时到达 | 串行处理，先到先处理 | 无竞态风险 |
| 4 | state_persister.save() 失败 | 状态未持久化，崩溃后丢失 | 重试 3 次，仍失败则记录错误日志 |

### 15.3 事务边界

```
每个事件处理的事务边界：

  await wait_for_event()
  → 解析出一条待处理输入（platform event / node_result / gate_response）
  
  ┌─ 事务开始 ─────────────────────────────────────┐
  │  1. 幂等检查（内存操作，快）                      │
  │  2. 状态更新（修改 self.state，内存操作）          │
  │  3. 发送 FlowMessage（await，可能慢）             │
  │  4. 通知群聊（await，可能慢）                     │
  └─ 事务结束 ─────────────────────────────────────┘
  
  await state_persister.save(self.state)  ← 持久化（事务外）
  
  如果步骤 3 失败：
    状态已更新但 FlowMessage 未发送
    → 崩溃恢复后：状态显示"已处理"但 Agent 未收到任务
    → 解决：pending_messages 记录发送状态，恢复后重发未确认的消息
```

## 十八、数据生命周期

### FlowState 生命周期

```
创建（initialize_project）
  └─ 空的 FlowState（pipeline_instance + 空的 sub_instances）

活跃（EventLoop 运行中）
  └─ 每个事件处理后更新
  └─ 每步持久化到 YAML 文件

阶段切换
  └─ 旧阶段的 ProcessInstance 保留在 sub_instances 中（历史）
  └─ 新阶段的 ProcessInstance 创建

项目完成
  └─ Pipeline 所有阶段 completed
  └─ FlowState 最终持久化
  └─ daemon 退出

崩溃恢复
  └─ 从 YAML 文件加载最后一次持久化的 FlowState
  └─ 检查 pending_messages，重发未确认的 FlowMessage
```

### GateRequest 生命周期

```
创建（UserTask 节点到达时）
  └─ status = "pending"
  └─ 加入 state.pending_gates

等待（用户未操作）
  └─ 通过 gate → chat 推送 GateCard 给用户
  └─ 定时检查超时

操作（用户点击）
  └─ approve → status = "approved" → 从 pending_gates 移除 → 加入 gate_history
  └─ reject → status = "rejected" → 从 pending_gates 移除 → 加入 gate_history
  └─ changes_requested → 从 pending_gates 移除 → 回退到前一个节点

超时
  └─ hard gate → status = "expired" → 通知用户
  └─ soft gate → status = "auto_approved" → 自动通过
```

## 十九、异常处理补偿逻辑

### EventLoop 各 handler 的补偿矩阵

| handler | 步骤 | 失败场景 | 补偿动作 |
|---------|------|---------|----------|
| handle_node_result | 更新 node_states | — | 不会失败（内存操作） |
| handle_node_result | 发送 FlowMessage（推进下一节点） | runtime 不可达 | 重试 3 次，仍失败则标记 pending_messages 为 "send_failed"，恢复后重发 |
| handle_node_result | 通知群聊 | gate 不可达 | 降级：跳过通知，不影响流程推进 |
| handle_gate_response | 推进流程 | runtime 不可达 | 同上 |
| handle_gate_response | 回退流程 | 目标节点不存在 | Fail Fast — 流程定义错误 |
| handle_platform_event | 发送 FlowMessage | runtime 不可达 | 重试 3 次，记录到 pending_messages |
| state_persister.save | 写入文件 | 磁盘满/权限 | 重试 3 次，仍失败则记录错误日志（下次事件处理时再尝试） |

### 关键补偿原则

```
1. 状态更新和消息发送不在同一个事务中
   → 可能出现"状态已更新但消息未发送"
   → 通过 pending_messages 记录发送状态，恢复后重发

2. 通知是可降级的
   → 群聊通知失败不影响流程推进
   → 用户可以通过 console 查看进度（不依赖通知）

3. 持久化失败不终止 daemon
   → 记录错误日志，下次事件处理时重试
   → 最坏情况：崩溃后丢失最后一个事件的状态变更
   → Phase 2 改为 WAL（Write-Ahead Log）保证不丢
```

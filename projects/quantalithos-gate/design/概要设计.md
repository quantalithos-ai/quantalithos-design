## 一、项目定位

### 1.1 核心职责

quantalithos-gate 是所有外部请求的唯一入口。客户端（chat/sdk）不直接访问后端服务，全部通过 gate 转发。

```
用户浏览器 / Tauri / Mobile
         │
         │ HTTP + WebSocket
         ▼
╔═════════════════════════════════════════╗
║         quantalithos-gate               ║
║                                         ║
║  ┌──────────┐  ┌──────────┐  ┌───────┐ ║
║  │ 认证授权  │  │ 请求路由  │  │ WS 管 │ ║
║  │ Auth     │  │ Router   │  │ 理    │ ║
║  └────┬─────┘  └────┬─────┘  └───┬───┘ ║
║       │             │            │      ║
╚═══════╪═════════════╪════════════╪══════╝
        │             │            │
        ▼             ▼            ▼
   ┌─────────┐  ┌──────────┐  ┌──────────┐
   │platform │  │  flow    │  │ runtime  │
   │ :8001   │  │  :8002   │  │  :8003   │
   └─────────┘  └──────────┘  └──────────┘
```

**不做的事：**
- 不做业务逻辑 — 纯转发，不修改请求/响应内容
- 不做数据持久化 — 无数据库（JWT 无状态）
- 不做服务发现 — Phase 1 静态配置后端地址

### 1.2 设计目标与非目标

| 设计目标 | 说明 |
|---------|------|
| 唯一外部入口 | 所有客户端请求都经过 gate，后端服务不直接暴露 |
| 无状态 | JWT 认证，gate 不存储会话，可水平扩展 |
| 纯转发 | 不修改请求/响应内容，不包含业务逻辑 |
| WebSocket 管理 | 统一管理客户端 WS 连接，后端事件广播给订阅者 |
| 限流保护 | Token Bucket 限流，防止滥用 |

| 非目标 | 说明 |
|--------|------|
| 不做业务逻辑 | 业务在 platform/flow/runtime |
| 不做数据持久化 | 无数据库 |
| 不做服务发现 | Phase 1 静态配置，Phase 3 考虑 Consul/etcd |
| 不做负载均衡 | Phase 1 单实例后端，Phase 3 考虑多实例 |

### 1.3 错误处理矩阵

| 错误场景 | 处理方式 | HTTP 状态码 |
|---------|---------|:---:|
| JWT 缺失或无效 | 返回错误，不转发 | 401 |
| JWT 过期 | 返回错误，客户端用 refresh token 续期 | 401 |
| 路由不匹配 | 返回 404 | 404 |
| 后端服务不可用 | 返回 502 Bad Gateway | 502 |
| 后端响应超时（30s） | 返回 504 Gateway Timeout | 504 |
| 请求体过大（>10MB） | 返回 413 | 413 |
| 限流触发 | 返回 429 Too Many Requests | 429 |
| WS 连接数超限（>5/user） | 拒绝新连接 | 403 |

### 1.4 在整体架构中的位置

| 消费者 | 通过 gate 访问 |
|--------|---------------|
| quantalithos-chat (web) | 通过 sdk-wasm → gate → platform/flow |
| quantalithos-chat (Tauri) | 通过 sdk → gate → platform/flow |
| quantalithos-sync | 直接访问 platform（不经过 gate，CLI 工具用 API Token） |
| quantalithos-flow | 直接访问 platform/runtime（内部服务间通信，不经过 gate） |
| quantalithos-runtime | 直接访问 platform（内部服务间通信） |

> gate 只面向外部客户端。内部服务间通信不经过 gate。

## 二、核心模块

### 2.1 认证授权（Auth）

```
登录流程：

用户                    gate                     platform
  │                      │                          │
  │  POST /auth/login    │                          │
  │  { email, password } │                          │
  │ ──────────────────>  │                          │
  │                      │  验证用户凭据              │
  │                      │ ──────────────────────>  │
  │                      │                          │
  │                      │  用户信息                  │
  │                      │ <──────────────────────  │
  │                      │                          │
  │  { token: "jwt..." } │  签发 JWT                 │
  │ <──────────────────  │                          │


请求校验：

客户端                   gate                     后端服务
  │                      │                          │
  │  GET /api/projects   │                          │
  │  Authorization:      │                          │
  │    Bearer jwt...     │                          │
  │ ──────────────────>  │                          │
  │                      │                          │
  │                      │  1. 校验 JWT 签名         │
  │                      │  2. 检查是否过期           │
  │                      │  3. 提取 user_id          │
  │                      │  4. 注入 X-User-Id 头     │
  │                      │                          │
  │                      │  转发请求                  │
  │                      │ ──────────────────────>  │
  │                      │                          │
  │  响应                 │  响应                     │
  │ <──────────────────  │ <──────────────────────  │
```

```rust
// JWT 配置
struct AuthConfig {
    jwt_secret: String,           // JWT 签名密钥
    token_expiry: Duration,       // Token 有效期（如 24h）
    refresh_expiry: Duration,     // Refresh Token 有效期（如 7d）
}

// JWT Claims
struct Claims {
    sub: String,                  // user_id
    exp: usize,                   // 过期时间
    iat: usize,                   // 签发时间
}
```

**Auth API：**

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /auth/login | 登录，返回 JWT |
| POST | /auth/refresh | 刷新 Token |
| POST | /auth/logout | 登出（可选，JWT 无状态） |
| GET | /auth/me | 获取当前用户信息 |

### 2.2 请求路由（Router）

```rust
// 路由配置（Phase 1 静态配置）
struct RouteConfig {
    routes: Vec<RouteRule>,
}

struct RouteRule {
    prefix: String,               // 路径前缀
    target: String,               // 后端服务地址
    strip_prefix: bool,           // 是否去掉前缀
    auth_required: bool,          // 是否需要认证
}
```

**路由表：**

| 路径前缀 | 目标服务 | 认证 | 说明 |
|---------|---------|------|------|
| /auth/** | gate 自身处理 | ❌ | 登录/刷新不需要认证 |
| /api/projects/** | platform:8001 | ✅ | 项目管理 |
| /api/workitems/** | platform:8001 | ✅ | 工单管理 |
| /api/artifacts/** | platform:8001 | ✅ | 产物管理 |
| /api/agent-config/** | platform:8001 | ✅ | Agent 配置 |
| /api/snapshots/** | platform:8001 | ✅ | 快照管理 |
| /api/flow/** | flow:8002 | ✅ | 流程引擎（门禁操作等） |
| /ws | gate 自身处理 | ✅ | WebSocket 连接 |

```
请求转发流程：

客户端请求：GET /api/projects/blog/views/ai
    │
    ▼
gate 收到请求
    │
    ├── 1. 匹配路由规则：/api/projects/** → platform:8001
    ├── 2. 认证中间件：校验 JWT → 提取 user_id
    ├── 3. 注入头：X-User-Id: user-001
    ├── 4. 限流检查：未超限
    ├── 5. 转发：GET http://platform:8001/api/projects/blog/views/ai
    │         Headers: X-User-Id: user-001
    ├── 6. 收到响应
    └── 7. 返回给客户端
```

### 2.3 WebSocket 管理（WS Manager）

```
WebSocket 连接流程：

客户端                   gate                     flow / platform
  │                      │                          │
  │  WS /ws?token=jwt    │                          │
  │ ──────────────────>  │                          │
  │                      │  校验 JWT                 │
  │                      │  创建 WsSession           │
  │  连接建立             │                          │
  │ <──────────────────  │                          │
  │                      │                          │
  │  subscribe:          │                          │
  │  { project: "blog" } │                          │
  │ ──────────────────>  │                          │
  │                      │  注册订阅                  │
  │                      │  blog 项目的事件 → 此连接  │
  │                      │                          │
  │                      │  事件：TASK-003 completed  │
  │                      │ <──────────────────────  │
  │                      │                          │
  │  event:              │  检查订阅：               │
  │  { type: "workitem", │  此连接订阅了 blog 项目    │
  │    data: {...} }     │  → 转发                   │
  │ <──────────────────  │                          │
```

```rust
// WebSocket 会话
struct WsSession {
    user_id: String,
    subscriptions: HashSet<String>,   // 订阅的 topic（如 "project:blog"）
    tx: mpsc::Sender<WsMessage>,      // 发送通道
}

// WebSocket 消息类型
// 参考 AG-UI 协议（docs/research/protocol-ag-ui.md）的 17 种事件类型
enum WsMessage {
    // 客户端 → gate
    Subscribe { topic: String },
    Unsubscribe { topic: String },
    ChatMessage { room_id: String, content: String },

    // gate → 客户端（对齐 AG-UI 事件模型）
    // 生命周期事件
    RunStarted { agent_id: String, node_id: String },           // Agent 开始执行
    RunFinished { agent_id: String, result_type: String },      // Agent 执行完成
    RunError { agent_id: String, error: String },               // Agent 执行出错
    StepStarted { agent_id: String, step_id: String },          // 工作流步骤开始
    StepFinished { agent_id: String, step_id: String },         // 工作流步骤完成

    // 消息流事件
    TextMessageStart { agent_id: String },                      // Agent 开始回复（流式）
    TextMessageContent { agent_id: String, content: String },   // 回复内容片段
    TextMessageEnd { agent_id: String },                        // 回复结束

    // 工具调用事件
    ToolCallStart { agent_id: String, tool: String },           // Agent 调用工具
    ToolCallEnd { agent_id: String, tool: String, result: String }, // 工具执行完成

    // 状态事件
    StateSnapshot { project_id: String, data: Value },          // 完整状态快照
    StateDelta { project_id: String, patch: Value },            // 状态增量更新

    // 自定义事件
    GateCard { gate: GateCard },                                // 门禁审批卡片
    ChatIncoming { message: ChatMessage },                      // 群聊消息
    Notification { title: String, body: String },               // 通知
}
```

**事件来源与转发：**

| 事件来源 | 事件类型 | 转发给谁 | 说明 |
|---------|---------|---------|------|
| platform | WorkItemCreated | 订阅了该项目的所有连接 | 新工单创建通知 |
| platform | WorkItemAssigned | 被指派的 Agent 对应的连接 | "你有一个新 BUG 待处理" |
| platform | WorkItemStatusChanged | 订阅了该项目的所有连接 | 工单状态变更（看板自动更新） |
| platform | WorkItemVerified | 相关 Agent 的连接 | 验证结果通知 |
| platform | WorkItemClosed | 订阅了该项目的所有连接 | 工单关闭通知 |
| platform | WorkItemCommented | 工单相关人的连接 | 新评论通知 |
| platform | ArtifactCreated | 订阅了该项目的所有连接 | 新产物创建 |
| flow | StageChanged | 订阅了该项目的所有连接 | 阶段推进通知 |
| flow | GateRequested | 该项目的用户连接 | 门禁审批卡片 |
| flow | ChatMessage | 订阅了该群聊的所有连接 | 群聊消息路由 |
| runtime | AgentMessage | 订阅了该群聊的所有连接 | Agent 发言 |
| runtime | RunStarted | 订阅了该项目的所有连接 | Agent 开始执行任务 |
| runtime | RunFinished | 订阅了该项目的所有连接 | Agent 完成任务 |

### 2.4 限流与保护

```rust
struct RateLimitConfig {
    requests_per_second: u32,     // 每秒请求数（如 100）
    burst_size: u32,              // 突发容量（如 200）
    ws_connections_per_user: u32, // 每用户最大 WS 连接数（如 5）
}
```

| 保护措施 | 配置 | 说明 |
|---------|------|------|
| 请求限流 | 100 req/s per user | Token Bucket 算法 |
| 请求体大小 | 10MB | 防止大文件攻击 |
| 请求超时 | 30s | 后端无响应时断开 |
| WS 连接数 | 5 per user | 防止连接泄漏 |
| WS 心跳 | 30s | 检测死连接 |

### 3.1 层间约束规则

| 约束 | 说明 |
|------|------|
| auth/ 不依赖 router/ 和 ws/ | 认证是独立关注点，通过 axum middleware 注入，不直接调用路由或 WebSocket 模块 |
| router/ 不依赖 ws/ | HTTP 反向代理和 WebSocket 管理是两条独立链路，互不引用 |
| ws/ 不依赖 router/ | WebSocket 连接由 main.rs 独立注册路由，不经过 HTTP 反向代理 |
| ratelimit/ 不依赖任何业务模块 | 限流是纯基础设施，通过 middleware 注入，不感知业务语义 |
| logging/ 不依赖任何业务模块 | 日志中间件只读取请求/响应元数据，不解析业务内容 |
| config.rs 被所有模块依赖 | 全局配置是唯一的共享依赖，所有模块通过 config 读取自己的配置段 |

```
依赖方向（单向，禁止反向依赖）：

  main.rs（组装层）
    │
    ├──> auth/          认证中间件
    ├──> router/        HTTP 反向代理
    ├──> ws/            WebSocket 管理
    ├──> ratelimit/     限流中间件
    └──> logging/       日志中间件
           │
           └──> config.rs（全局配置，所有模块共享）
```

## 四、技术选型（决策四元组）

| 类别 | 选型 | 说明 |
|------|------|------|
| 语言 | Rust | 和 platform/sync/sdk 一致 |
| HTTP 框架 | axum | 和 platform 一致，高性能 |
| JWT | jsonwebtoken | Rust JWT 库 |
| HTTP 客户端 | reqwest | 转发请求到后端 |
| WebSocket | axum + tokio-tungstenite | 原生支持 |
| 限流 | governor | Rust 限流库（Token Bucket） |
| 日志 | tracing + tracing-subscriber | 结构化日志 |
| 配置 | serde_yaml | YAML 配置文件 |

### 4.1 网关方案选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | Rust + axum 自研网关 |
| 备选 | ① Nginx + Lua (OpenResty)　② Envoy + WASM Filter　③ Go + gin 自研 |
| 理由 | 项目全栈 Rust，自研可深度集成 WebSocket 订阅管理和 AG-UI 事件转发；Nginx/Envoy 做反向代理成熟但 WebSocket 订阅路由需要额外开发，且引入异构技术栈增加运维成本 |
| 演进路径 | Phase 3 流量增长后，可在 gate 前加 Envoy 做 L4 负载均衡，gate 退化为应用层网关 |

### 4.2 认证方案选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | JWT（无状态 Token） |
| 备选 | ① Session + Redis　② OAuth 2.0 + OIDC |
| 理由 | gate 设计为无状态可水平扩展，JWT 不需要共享存储；Session 方案需要 Redis 集中存储，增加依赖；OAuth Phase 2 作为补充（GitHub/Google 登录），不替代 JWT |
| 演进路径 | Phase 2 增加 OAuth 作为登录入口，登录后仍签发 JWT；Phase 3 如需 Token 吊销，引入短 TTL + Redis 黑名单 |

### 4.3 事件通道选型（gate ↔ 后端）

| 维度 | 当前选择 |
|------|---------|
| 方案 | SSE 轮询（后端 → gate） |
| 备选 | ① Redis Pub/Sub　② NATS　③ gRPC 双向流 |
| 理由 | Phase 1 后端服务单实例，SSE 最简单且无额外依赖；Redis/NATS 在多实例场景才有价值 |
| 演进路径 | Phase 2 切换为 Redis Pub/Sub（和 platform 事件总线对齐）；Phase 3 评估 NATS |

## 五、配置示例

```yaml
# config/gate.yaml

server:
  host: "0.0.0.0"
  port: 8000
  request_timeout_secs: 30
  max_body_size_mb: 10

auth:
  jwt_secret: "your-secret-key"
  token_expiry_hours: 24
  refresh_expiry_days: 7

# 后端服务池（借鉴 Nginx upstream）
upstreams:
  platform:
    servers:
      - "http://localhost:8001"
    # 未来多实例：
    # - "http://platform-1:8001"
    # - "http://platform-2:8001"
    # load_balance: round_robin

  flow:
    servers:
      - "http://localhost:8002"

  runtime:
    servers:
      - "http://localhost:8003"

# HTTP 路由规则
routes:
  # platform 模块（按模块粒度配置，未来拆分只改 upstream）
  - prefix: "/api/projects"
    upstream: platform
    auth_required: true

  - prefix: "/api/workitems"
    upstream: platform
    auth_required: true

  - prefix: "/api/artifacts"
    upstream: platform
    auth_required: true

  - prefix: "/api/agent-config"
    upstream: platform
    auth_required: true

  - prefix: "/api/snapshots"
    upstream: platform
    auth_required: true

  - prefix: "/api/knowledge"
    upstream: platform
    auth_required: true

  # flow 模块
  - prefix: "/api/flow"
    upstream: flow
    auth_required: true

  # auth 端点（gate 自身处理，不转发）
  - prefix: "/auth"
    handler: internal
    auth_required: false

# WebSocket 配置
websocket:
  # 外层：客户端 ←→ gate
  client:
    path: "/ws"
    auth_required: true
    heartbeat_interval_secs: 30
    max_connections_per_user: 5
    message_max_size_kb: 64

  # 内层：gate ←→ 后端事件通道
  backend:
    # Phase 1：SSE 轮询
    mode: sse
    sources:
      - name: platform_events
        url: "http://localhost:8001/internal/events/stream"
      - name: flow_events
        url: "http://localhost:8002/internal/events/stream"

    # Phase 2：Redis Pub/Sub
    # mode: redis
    # redis_url: "redis://localhost:6379"
    # channels:
    #   - "platform:events"
    #   - "flow:events"

    # Phase 3：NATS
    # mode: nats
    # nats_url: "nats://localhost:4222"

# 限流
ratelimit:
  requests_per_second: 100
  burst_size: 200
```

## 八、约束条件

### 8.1 技术约束

| 约束 | 说明 |
|------|------|
| 语言 | Rust（axum），与 platform/sandbox/sdk 统一技术栈 |
| 无状态 | gate 不持有任何持久化数据，不连接数据库；JWT 无状态认证 |
| 纯转发 | 不修改请求/响应 body，不包含业务逻辑；仅注入/读取 HTTP 头 |
| 配置驱动 | 路由表、限流参数、后端地址全部通过 YAML 配置，不硬编码 |
| 单进程 | Phase 1 单实例部署；Phase 3 多实例 + 外部负载均衡 |

### 8.2 容量规划

| 指标 | Phase 1 目标 | Phase 2 目标 |
|------|-------------|-------------|
| HTTP QPS（单实例） | 1,000 | 5,000 |
| 并发 WebSocket 连接 | — | 500 |
| 每用户 WS 连接上限 | — | 5 |
| HTTP 请求 P95 延迟（转发开销） | < 5ms | < 5ms |
| 内存占用 | < 64MB | < 256MB |
| 后端转发超时 | 30s | 30s |
| 请求体大小上限 | 10MB | 10MB |

### 8.3 合规约束

- JWT secret 不得出现在日志、错误响应、配置文件版本控制中
- 所有转发请求注入 `X-Request-Id`，贯穿全链路（W3C Trace Context）
- 不在响应头中泄露后端服务地址（移除 `Server`、`X-Powered-By` 等头）
- CORS 白名单严格限制，不使用 `*`

## 九、横切关注点

### 9.1 安全

| 关注点 | 方案 |
|--------|------|
| 认证 | JWT（HS256），Phase 2 增加 OAuth 2.0 登录入口 |
| Token 吊销 | Phase 1 不支持（短 TTL + refresh 机制）；Phase 3 引入 Redis 黑名单 |
| 传输安全 | Phase 1 开发环境 HTTP；生产环境 TLS 终止在 gate 前的反向代理（Nginx/Caddy） |
| 请求头注入 | gate 注入 `X-User-Id` / `X-Request-Id`，后端服务信任这些头 |
| 请求体校验 | gate 不校验 body 内容（纯转发），body 校验由后端服务负责 |
| WebSocket 认证 | WS 握手时通过 query param `?token=jwt` 校验，连接建立后不再校验 |
| Prompt Injection | gate 层不涉及 LLM 调用，但需确保用户输入不被注入到内部服务头中 |

### 9.2 性能

**端到端延迟预算表（HTTP 请求转发）：**

| 环节 | 预估延迟 | 依据 |
|------|---------|------|
| gate 接收请求 + 路由匹配 | < 0.1ms | axum 路由匹配 O(1) |
| JWT 校验 | < 0.5ms | HS256 纯 CPU 计算 |
| 限流检查 | < 0.1ms | 内存 Token Bucket |
| 请求头注入 | < 0.1ms | 字符串操作 |
| reqwest 转发（不含后端处理） | < 2ms | 本地网络 + 连接池复用 |
| **gate 总开销** | **< 3ms** | 不含后端服务处理时间 |

> gate 的设计目标是转发开销 < 5ms（P95），不成为请求链路的瓶颈。

### 9.3 可用性

| 关注点 | 方案 |
|--------|------|
| 单点故障 | Phase 1 单实例可接受（开发阶段）；Phase 3 多实例 + 健康检查 |
| 后端不可用 | 返回 502 Bad Gateway，不缓存错误响应 |
| 后端超时 | 30s 超时后返回 504，释放连接 |
| 优雅关闭 | SIGTERM 后停止接受新连接，等待已有请求完成（最长 10s） |
| WS 连接断开 | 客户端自动重连（指数退避），gate 清理 session |

### 9.4 可观测性

| 维度 | 方案 |
|------|------|
| 日志 | tracing + tracing-subscriber，JSON 结构化，每请求记录 method/path/status/duration/user_id/request_id |
| 追踪 | X-Request-Id 贯穿 gate → 后端，Phase 2 对齐 W3C Trace Context（traceparent 头） |
| 指标 | Phase 2 引入 metrics crate + /metrics 端点（Prometheus 格式） |
| 关键指标 | http_requests_total（按 status/method/path）、http_request_duration_seconds、ws_connections_active、ws_messages_total |

### 9.5 成本

| 关注点 | 方案 |
|--------|------|
| 资源占用 | Rust 单二进制，内存 < 64MB（Phase 1），无 GC 停顿 |
| 外部依赖 | Phase 1 零外部依赖（无 Redis/MQ）；Phase 2 引入 Redis（事件通道） |
| 运维成本 | 单二进制部署，配置文件驱动，无数据库迁移 |

## 十、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | JWT 密钥泄露 | 攻击者可伪造任意用户 Token | 低 | 密钥从环境变量注入，不进版本控制；Phase 3 支持密钥轮换（双密钥过渡期） |
| 2 | WebSocket 连接风暴 | 大量连接耗尽内存/文件描述符 | 中 | 每用户最多 5 连接 + 全局连接数上限（Phase 2: 500）；超限拒绝新连接 |
| 3 | 后端服务全部不可用 | 所有 API 返回 502 | 低 | Phase 1 可接受（开发阶段）；Phase 3 引入熔断器（circuit breaker），快速失败 + 降级响应 |
| 4 | 慢后端拖垮 gate | 转发线程被慢请求占满，新请求排队 | 中 | 30s 硬超时 + reqwest 连接池上限（每后端 32 连接）；超时后立即释放 |
| 5 | 限流配置不当 | 正常用户被误限 / 恶意用户未被限 | 中 | Phase 1 保守配置（100 req/s/user）；Phase 2 增加 IP 级限流 + 动态调整 |
| 6 | SSE 事件通道断开（Phase 1） | gate 收不到后端事件，WS 客户端无推送 | 中 | 自动重连（5s 间隔）+ 重连后请求全量状态快照；Phase 2 切换为 Redis Pub/Sub |

### 常见异常场景

| 场景 | 处理方式 |
|------|---------|
| JWT 过期 | 返回 401，客户端用 refresh token 续期 |
| 路由不匹配 | 返回 404 Not Found |
| 后端 5xx | 透传后端状态码，不重试（Phase 1）；Phase 2 可配置重试 |
| 请求体过大 | 返回 413 Payload Too Large |
| 限流触发 | 返回 429 Too Many Requests，响应头含 Retry-After |

### 边缘异常场景

| 场景 | 处理方式 |
|------|---------|
| JWT 签名算法被篡改（alg: none 攻击） | jsonwebtoken 库默认拒绝 none 算法；配置中显式指定 HS256 |
| WebSocket 消息体超大 | 单消息上限 64KB，超限断开连接 |
| 后端返回非法 HTTP 响应 | gate 返回 502，日志记录原始错误 |
| 并发 refresh token 请求 | JWT 无状态，多次 refresh 各自签发新 token，旧 token 在 TTL 内仍有效 |

## 十一、上线策略

### 11.1 灰度方案

| 阶段 | 流量比例 | 观察时间 | 推进条件 |
|------|---------|---------|---------|
| 金丝雀 | 5% 流量经过新版 gate | 30 min | 错误率 < 0.1%，P95 延迟无退化 |
| 小流量 | 30% | 2h | 同上 |
| 全量 | 100% | 持续观察 | — |

### 11.2 回滚策略

| 触发条件 | 回滚步骤 |
|---------|---------|
| 错误率 > 1% | 立即切回旧版（Nginx upstream 切换） |
| P95 延迟退化 > 50% | 立即切回旧版 |
| WebSocket 大面积断连 | 切回旧版，客户端自动重连 |

> 回滚安全性：gate 无状态、无数据库，切换版本不涉及数据迁移，可秒级回滚。

### 11.3 上线监控指标

| 指标 | 告警阈值 |
|------|---------|
| HTTP 5xx 比例 | > 1% 持续 1 分钟 |
| HTTP P95 延迟 | > 100ms（含后端处理） |
| WS 活跃连接数 | > 400（接近上限 500） |
| 进程内存 | > 200MB |

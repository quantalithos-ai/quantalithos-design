## 一、项目定位

### 1.1 核心职责

quantalithos-infra 不是运行时服务，是一组部署配置和运维工具，管理所有子项目的运行环境。

```
┌─────────────────────────────────────────────────────────────┐
│  quantalithos-infra 管理的范围                               │
│                                                             │
│  ┌─────────┐  ┌─────────┐  ┌──────────┐  ┌─────────┐     │
│  │  gate   │  │platform │  │  flow    │  │ runtime │     │
│  │  :8000  │  │  :8001  │  │  :8002   │  │  :8003  │     │
│  └────┬────┘  └────┬────┘  └────┬─────┘  └────┬────┘     │
│       │            │            │              │           │
│  ┌────┴────────────┴────────────┴──────────────┴────┐     │
│  │              Docker Compose / K8s                 │     │
│  └──────────────────────┬───────────────────────────┘     │
│                         │                                  │
│  ┌──────────────────────┴───────────────────────────┐     │
│  │              基础设施层                            │     │
│  │  PostgreSQL  Redis  MinIO/S3  NATS(Phase 2)      │     │
│  └──────────────────────────────────────────────────┘     │
│                                                             │
│  ┌──────────────────────────────────────────────────┐     │
│  │              CI/CD                                │     │
│  │  GitHub Actions / GitLab CI                       │     │
│  └──────────────────────────────────────────────────┘     │
│                                                             │
│  ┌──────────────────────────────────────────────────┐     │
│  │              监控告警                              │     │
│  │  Prometheus + Grafana + Loki                      │     │
│  └──────────────────────────────────────────────────┘     │
└─────────────────────────────────────────────────────────────┘
```

**不做的事：**
- 不包含业务代码 — 只有配置文件和脚本
- 不做应用层逻辑 — 应用配置在各子项目自己的 config/ 里

### 1.2 与其他子项目的关系

| 子项目 | infra 提供什么 |
|--------|---------------|
| gate (Rust) | Dockerfile、K8s Deployment、健康检查 |
| platform (Rust) | Dockerfile、数据库迁移、MinIO 配置 |
| flow (Python) | Dockerfile、Python 依赖管理 |
| runtime (Python) | Dockerfile、沙箱配置 |
| chat (Vue 3) | Dockerfile（Nginx 静态托管）、构建配置 |
| sdk (Rust) | CI 构建（WASM 编译）、npm 发布 |
| sync (Rust) | CI 构建、跨平台二进制发布 |

### 2.1 层间约束规则

| 约束 | 说明 |
|------|------|
| docker/ 不包含业务代码 | 只有 Dockerfile 和 compose 配置，不含应用逻辑 |
| db/ 只包含 DDL 和 seeds | 不含应用层查询逻辑，查询在各服务的 Repo 层 |
| ci/ 不依赖本地环境 | CI 脚本在容器内运行，不假设宿主机安装了特定工具 |
| scripts/ 是开发辅助 | 不在生产环境运行，不包含生产部署逻辑 |
| envs/ 不进版本控制 | .env.example 进版本控制，.env.dev/.staging/.prod 通过 .gitignore 排除 |
| monitoring/ 不依赖应用代码 | 通过 /metrics 端点和日志采集，不侵入应用 |

```
依赖方向：

  docker/compose → 引用各子项目的 Dockerfile
  db/migrations  → 被 platform 的 sqlx 消费
  ci/            → 调用 docker/ 和 scripts/
  monitoring/    → 采集各服务的 /metrics 和日志
  scripts/       → 调用 docker/ 和 db/
  envs/          → 被 docker/compose 和各服务读取
```

## 三、核心配置

### 3.1 Docker Compose（本地开发）

```yaml
# docker/docker-compose.yaml

version: "3.8"

services:
  # ── 基础设施 ──
  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: quantalithos
      POSTGRES_PASSWORD: dev_password
      POSTGRES_DB: quantalithos
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./db/migrations:/docker-entrypoint-initdb.d

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"

  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: quantalithos
      MINIO_ROOT_PASSWORD: dev_password
    ports:
      - "9000:9000"
      - "9001:9001"
    volumes:
      - minio_data:/data

  # ── 应用服务 ──
  gate:
    build:
      context: ../projects/quantalithos-gate
      dockerfile: ../infra/docker/gate/Dockerfile
    ports:
      - "8000:8000"
    environment:
      - CONFIG_PATH=/app/config/gate.yaml
    depends_on:
      - platform
      - flow

  platform:
    build:
      context: ../projects/quantalithos-platform
      dockerfile: ../infra/docker/platform/Dockerfile
    ports:
      - "8001:8001"
    environment:
      - DATABASE_URL=postgres://quantalithos:dev_password@postgres:5432/quantalithos
      - MINIO_ENDPOINT=http://minio:9000
    depends_on:
      - postgres
      - redis
      - minio

  flow:
    build:
      context: ../projects/quantalithos-flow
      dockerfile: ../infra/docker/flow/Dockerfile
    ports:
      - "8002:8002"
    environment:
      - PLATFORM_URL=http://platform:8001
      - RUNTIME_URL=http://runtime:8003
    depends_on:
      - platform

  runtime:
    build:
      context: ../projects/quantalithos-runtime
      dockerfile: ../infra/docker/runtime/Dockerfile
    ports:
      - "8003:8003"
    environment:
      - PLATFORM_URL=http://platform:8001
      - FLOW_URL=http://flow:8002
      - LLM_API_KEY=${LLM_API_KEY}
    depends_on:
      - platform
      - flow

  chat:
    build:
      context: ../projects/quantalithos-chat
      dockerfile: ../infra/docker/chat/Dockerfile
    ports:
      - "3000:80"
    depends_on:
      - gate

volumes:
  postgres_data:
  minio_data:
```

### 3.3 开发环境一键搭建

```bash
#!/bin/bash
# scripts/setup-dev.sh

echo "=== Quantalithos 开发环境搭建 ==="

# 1. 检查依赖
echo "检查依赖..."
command -v docker >/dev/null 2>&1 || { echo "需要安装 Docker"; exit 1; }
command -v rustup >/dev/null 2>&1 || { echo "需要安装 Rust"; exit 1; }
command -v python3 >/dev/null 2>&1 || { echo "需要安装 Python 3"; exit 1; }
command -v node >/dev/null 2>&1 || { echo "需要安装 Node.js"; exit 1; }

# 2. 启动基础设施
echo "启动 PostgreSQL + Redis + MinIO..."
docker compose -f docker/docker-compose.yaml up -d postgres redis minio

# 3. 等待数据库就绪
echo "等待数据库就绪..."
until docker compose exec postgres pg_isready; do sleep 1; done

# 4. 执行数据库迁移
echo "执行数据库迁移..."
bash db/migrate.sh

# 5. 导入初始数据
echo "导入初始数据..."
docker compose exec -T postgres psql -U quantalithos < db/seeds/system_roles.sql
docker compose exec -T postgres psql -U quantalithos < db/seeds/shared_rules.sql
docker compose exec -T postgres psql -U quantalithos < db/seeds/pipeline_templates.sql

# 6. 编译 sdk-wasm
echo "编译 sdk-wasm..."
cd ../projects/quantalithos-sdk
wasm-pack build crates/sdk-wasm --target web

# 7. 安装 chat 依赖
echo "安装 chat 依赖..."
cd ../quantalithos-chat
npm install

echo "=== 开发环境就绪 ==="
echo "启动服务："
echo "  platform:  cd projects/quantalithos-platform && cargo run"
echo "  flow:      cd projects/quantalithos-flow && python -m quantalithos_flow"
echo "  runtime:   cd projects/quantalithos-runtime && python -m quantalithos_runtime"
echo "  gate:      cd projects/quantalithos-gate && cargo run"
echo "  chat:      cd projects/quantalithos-chat && npm run dev"
```

## 六、技术选型（决策四元组）

### 6.1 容器编排

| 维度 | 当前选择 |
|------|---------|
| 方案 | Docker Compose（本地开发 + Phase 1 部署） |
| 备选 | ① Kubernetes（K8s）　② Podman Compose　③ Nomad |
| 理由 | Phase 1 单机部署，Docker Compose 最简单；K8s 在单机场景过重（etcd + API Server + kubelet）；Podman 生态不如 Docker 成熟 |
| 演进路径 | Phase 2 引入 K8s（多节点部署）；Phase 3 Helm Chart 包管理 |

### 6.2 数据库

| 维度 | 当前选择 |
|------|---------|
| 方案 | PostgreSQL 16 |
| 备选 | ① MySQL 8　② CockroachDB　③ SQLite |
| 理由 | JSONB 原生支持（Agent 配置存储）；sqlx 编译时 SQL 校验；丰富的索引类型（GIN/GiST）；CockroachDB 分布式但运维复杂；SQLite 不支持并发写 |
| 演进路径 | 长期使用 PostgreSQL；Phase 3 如需分库可用 Citus 扩展 |

### 6.3 对象存储

| 维度 | 当前选择 |
|------|---------|
| 方案 | MinIO（S3 兼容） |
| 备选 | ① 本地文件系统　② AWS S3　③ SeaweedFS |
| 理由 | S3 API 兼容，开发环境自托管零成本；生产环境可无缝切换到 AWS S3；本地文件系统不支持多实例共享 |
| 演进路径 | 生产环境直接切换为 AWS S3 / 阿里云 OSS（只改 endpoint 配置） |

### 6.4 CI/CD

| 维度 | 当前选择 |
|------|---------|
| 方案 | GitHub Actions |
| 备选 | ① GitLab CI　② Gitea Actions　③ Jenkins |
| 理由 | 项目托管在 GitHub，Actions 原生集成零配置；GitLab CI 需要自建 Runner；Jenkins 运维成本高 |
| 演进路径 | 如迁移到自托管 Gitea，切换为 Gitea Actions（语法兼容 GitHub Actions） |

### 6.5 监控

| 维度 | 当前选择 |
|------|---------|
| 方案 | Prometheus + Grafana + Loki |
| 备选 | ① Datadog　② ELK Stack　③ VictoriaMetrics |
| 理由 | 开源免费，社区生态成熟；Prometheus 是 CNCF 标准；Grafana 支持多数据源；Datadog 按量计费成本高 |
| 演进路径 | 长期使用；Phase 3 如指标量大可换 VictoriaMetrics（Prometheus 兼容，存储效率更高） |

## 七、约束条件

### 7.1 技术约束

| 约束 | 说明 |
|------|------|
| 不含业务代码 | infra 只有配置文件、脚本、Dockerfile，不含任何应用逻辑 |
| 环境变量驱动 | 所有敏感配置（密码、API Key）通过环境变量注入，不硬编码 |
| 幂等脚本 | setup-dev.sh / migrate.sh 可重复执行，不会破坏已有数据 |
| 单机优先 | Phase 1 所有服务在单机 Docker Compose 运行；Phase 2 才引入 K8s |

### 7.2 容量规划

| 指标 | Phase 1 目标 | Phase 2 目标 |
|------|-------------|-------------|
| 服务数量 | 5（gate/platform/flow/runtime/chat） | 8（+console/sandbox/gitea） |
| PostgreSQL 存储 | < 1GB | < 10GB |
| MinIO 存储 | < 5GB | < 50GB |
| 宿主机内存 | 8GB 足够 | 16GB 推荐 |
| 宿主机磁盘 | 20GB（含 Docker 镜像） | 50GB |

### 7.3 合规约束

- .env 文件不进版本控制（.gitignore 排除）
- Docker 镜像不包含密钥（运行时通过环境变量注入）
- 数据库备份加密存储（Phase 2）
- CI/CD 密钥通过 GitHub Secrets 管理，不写入配置文件

## 八、横切关注点

### 8.1 安全

| 关注点 | 方案 |
|--------|------|
| 密钥管理 | 环境变量注入；GitHub Secrets（CI）；Phase 3 评估 Vault |
| 网络隔离 | Docker Compose 默认网络隔离；Phase 2 K8s NetworkPolicy |
| 镜像安全 | Phase 2 引入 Trivy 镜像漏洞扫描 |
| 数据库访问 | 只有 platform 直连 PostgreSQL，其他服务通过 platform API |

### 8.2 可用性

| 关注点 | 方案 |
|--------|------|
| 服务启动顺序 | Docker Compose depends_on 保证依赖顺序 |
| 健康检查 | 每个服务暴露 /health 端点；Phase 2 K8s livenessProbe + readinessProbe |
| 数据持久化 | Docker volume 持久化 PostgreSQL/MinIO/Gitea 数据 |
| 备份恢复 | Phase 2 引入 pg_dump 定时备份 + MinIO 版本控制 |

### 8.3 可观测性

| 维度 | 方案 |
|------|------|
| 日志 | Phase 1：docker logs 查看；Phase 2：Loki 集中采集 |
| 指标 | Phase 2：Prometheus 采集各服务 /metrics；Grafana 面板 |
| 追踪 | Phase 2：各服务注入 X-Request-Id；Phase 3：Jaeger 分布式追踪 |

### 8.4 成本

| 关注点 | 方案 |
|--------|------|
| 开发环境 | 全部自托管（Docker Compose），零云服务成本 |
| 生产环境 | Phase 1 单机 VPS（~$20/月）；Phase 2 K8s 集群（~$100/月） |
| 存储成本 | MinIO 自托管零成本；生产切 S3 按量计费 |

## 九、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | Docker daemon 崩溃 | 所有服务不可用 | 低 | Phase 1 可接受（开发阶段）；Phase 2 K8s 多节点容灾 |
| 2 | PostgreSQL 数据丢失 | 全平台数据丢失 | 低 | Docker volume 持久化；Phase 2 定时 pg_dump 备份（每 6h） |
| 3 | 迁移脚本执行失败 | 数据库 schema 不一致 | 中 | 迁移脚本幂等（IF NOT EXISTS）；失败时回滚到上一版本 |
| 4 | 环境变量泄露 | 密钥暴露 | 低 | .env 不进版本控制；CI 用 GitHub Secrets；日志中不打印环境变量 |
| 5 | Docker 镜像构建缓慢 | 开发效率低 | 中 | 多阶段构建（builder + runtime）；利用 Docker layer cache |
| 6 | 端口冲突 | 服务启动失败 | 低 | 端口规划表统一管理；setup-dev.sh 启动前检查端口占用 |

### 常见异常场景

| 场景 | 处理方式 |
|------|---------|
| docker compose up 部分服务启动失败 | docker compose logs 查看失败原因；depends_on 保证依赖顺序 |
| 数据库迁移冲突 | 回滚到上一版本迁移；修复 SQL 后重新执行 |
| MinIO 磁盘满 | 清理旧版本产物；扩容 volume |
| CI 构建超时 | 检查 Docker cache 是否命中；优化 Dockerfile 层顺序 |

## 十、上线策略

### 10.1 灰度方案

| 阶段 | 范围 | 观察时间 | 推进条件 |
|------|------|---------|---------|
| 本地验证 | docker compose up 全部服务 | 1 天 | 所有服务 /health 返回 200 |
| staging | 部署到 staging 环境 | 3 天 | 端到端流程跑通（创建项目→Agent 执行→产物提交） |
| production | 部署到生产环境 | 持续 | — |

### 10.2 回滚策略

| 触发条件 | 回滚步骤 |
|---------|---------|
| 服务启动失败 | docker compose down → 切回旧镜像 tag → docker compose up |
| 数据库迁移失败 | 执行回滚 SQL（每个迁移文件附带 down.sql）；Phase 2 用 sqlx migrate revert |
| 配置错误 | 修改 .env / config 文件 → docker compose restart |

### 10.3 上线监控指标

| 指标 | 告警阈值 |
|------|---------|
| 服务 /health 状态 | 任一服务返回非 200 持续 1 分钟 |
| PostgreSQL 连接数 | > 80%（max_connections 默认 100） |
| 磁盘使用率 | > 80% |
| Docker 容器重启次数 | > 3 次/小时 |

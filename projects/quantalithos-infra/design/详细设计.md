## 三、启动脚本

```bash
#!/bin/bash
# scripts/setup-dev.sh — 一键启动开发环境

set -e

echo "🚀 Quantalithos AI 开发环境启动"

# 1. 检查依赖
command -v docker >/dev/null 2>&1 || { echo "❌ 需要安装 Docker"; exit 1; }
command -v docker-compose >/dev/null 2>&1 || { echo "❌ 需要安装 Docker Compose"; exit 1; }

# 2. 复制环境变量
if [ ! -f .env ]; then
    cp config/.env.example .env
    echo "📝 已创建 .env，请填入 LLM_API_KEY"
fi

# 3. 启动基础设施
echo "📦 启动 PostgreSQL + Redis + MinIO..."
docker-compose -f docker/docker-compose.yml up -d postgres redis minio

# 4. 等待数据库就绪
echo "⏳ 等待数据库就绪..."
until docker-compose exec postgres pg_isready -U quantalithos; do
    sleep 1
done

# 5. 运行迁移
echo "🔧 运行数据库迁移..."
bash scripts/migrate.sh

# 6. 导入初始数据
echo "🌱 导入初始数据..."
bash scripts/seed.sh

# 7. 启动应用服务
echo "🚀 启动应用服务..."
docker-compose -f docker/docker-compose.yml up -d platform flow runtime gate chat

echo ""
echo "✅ 开发环境已就绪"
echo "   gate:     http://localhost:8000"
echo "   chat:     http://localhost:3000"
echo "   platform: http://localhost:8001"
echo "   flow:     http://localhost:8002"
echo "   runtime:  http://localhost:8003"
echo "   MinIO:    http://localhost:9001"
```

## 七、并发与一致性

infra 本身不是运行时服务，并发问题主要出现在脚本执行和数据库迁移场景。

### 7.1 竞态场景分析

| 竞态场景 | 共享资源 | 控制策略 |
|---------|---------|---------|
| 两人同时执行 migrate.sh | PostgreSQL schema | sqlx migrate 内置 advisory lock（pg_advisory_lock），同一时刻只有一个迁移进程执行 |
| docker compose up 并发启动 | Docker daemon | Docker Compose 内部串行化容器创建；depends_on 保证依赖顺序 |
| CI 并发构建同一分支 | Docker layer cache | GitHub Actions concurrency group 限制同一分支只有一个 CI 运行 |
| 多服务同时连接 PostgreSQL | 连接池 | PostgreSQL max_connections=100；每个服务连接池上限 20 |

### 7.2 数据库迁移一致性

```
迁移执行保证：

  1. sqlx migrate run 获取 advisory lock
  2. 读取 _sqlx_migrations 表，确定已执行的版本
  3. 按版本号顺序执行未执行的迁移
  4. 每个迁移在独立事务中执行（失败自动回滚）
  5. 释放 advisory lock

  → 保证：多实例同时启动时，迁移只执行一次
```

## 八、性能设计

### 8.1 Docker 镜像构建优化

| 优化项 | 方案 | 效果 |
|--------|------|------|
| 多阶段构建 | builder 阶段编译 → runtime 阶段只复制二进制 | Rust 镜像从 ~2GB 降到 ~100MB |
| 依赖缓存 | 先 COPY Cargo.toml → cargo build（缓存依赖）→ 再 COPY src/ | 代码变更时只重编译业务代码，不重编译依赖 |
| .dockerignore | 排除 target/、node_modules/、.git/ | 减少构建上下文传输时间 |
| 基础镜像 | Rust 服务用 debian:bookworm-slim；Python 用 python:3.12-slim | 最小化镜像体积 |

### 8.2 数据库性能

| 配置项 | Phase 1 | Phase 2 | 说明 |
|--------|---------|---------|------|
| max_connections | 100 | 200 | 5 个服务 × 20 连接池 = 100 |
| shared_buffers | 256MB | 1GB | PostgreSQL 推荐为总内存的 25% |
| work_mem | 4MB | 16MB | 排序/哈希操作内存 |
| wal_level | replica | replica | 支持 Phase 2 流复制 |

### 8.3 服务启动时间

| 服务 | 冷启动 | 热启动（镜像已缓存） |
|------|--------|---------------------|
| PostgreSQL | ~5s | ~2s |
| Redis | ~1s | ~1s |
| MinIO | ~3s | ~2s |
| platform (Rust) | ~2s | ~1s |
| gate (Rust) | ~1s | ~1s |
| flow (Python) | ~3s | ~2s |
| runtime (Python) | ~3s | ~2s |
| chat (Nginx) | ~1s | ~1s |
| **全部服务** | **~30s** | **~15s** |

## 九、测试设计

### 9.1 核心测试场景

| # | 场景 | 类型 | 验收准则 |
|---|------|------|---------|
| 1 | setup-dev.sh 一键启动 | 集成 | 执行脚本 → 所有服务 /health 返回 200 |
| 2 | migrate.sh 幂等执行 | 集成 | 执行两次 → 第二次无报错，表结构不变 |
| 3 | seed.sh 幂等执行 | 集成 | 执行两次 → 第二次无报错，数据不重复（ON CONFLICT DO NOTHING） |
| 4 | reset-db.sh 重置 | 集成 | 执行 → 数据库清空 → migrate + seed → 数据恢复 |
| 5 | Docker 镜像构建 | 集成 | docker compose build → 5 个镜像构建成功 |
| 6 | 服务依赖顺序 | 集成 | docker compose up → platform 等待 postgres 就绪后启动 |
| 7 | 环境变量注入 | 集成 | 修改 .env 中的 DB_PASSWORD → platform 使用新密码连接成功 |
| 8 | 端口不冲突 | 集成 | 所有服务同时启动 → 无端口冲突报错 |
| 9 | 数据持久化 | 集成 | docker compose down → docker compose up → PostgreSQL 数据仍在 |
| 10 | health-check.sh | 集成 | 所有服务运行时返回 OK；停止 platform → 报告 platform 不可达 |

### 9.2 测试方式

infra 的测试主要是脚本级集成测试，不使用单元测试框架：

- 在 CI 中启动 Docker Compose → 执行各脚本 → 验证结果 → 清理
- 使用 `curl` 验证 /health 端点
- 使用 `docker compose exec postgres psql` 验证数据库状态

## 十一、跨模块调用链

### 11.1 开发环境启动

```
开发者执行 setup-dev.sh
  → docker compose up -d postgres redis minio
    → 等待 postgres pg_isready
  → migrate.sh
    → sqlx migrate run（获取 advisory lock → 执行 DDL → 释放）
  → seed.sh
    → psql < system_roles.sql（ON CONFLICT DO NOTHING）
    → psql < shared_rules.sql
    → psql < pipeline_templates.sql
  → docker compose up -d platform flow runtime gate chat
    → platform 启动 → 连接 postgres + redis → /health 200
    → flow 启动 → 连接 platform → /health 200
    → runtime 启动 → 连接 platform → /health 200
    → gate 启动 → 连接 platform + flow + runtime → /health 200
    → chat 启动 → Nginx 静态托管 → /health 200
  → 输出所有服务 URL
```

### 11.2 CI 构建流水线

```
开发者 push 代码到 GitHub
  → GitHub Actions 触发
    → rust-build.yaml
      → cargo build --workspace（gate/platform/sdk/sync）
      → cargo test --workspace
      → cargo clippy --workspace
    → python-build.yaml（并行）
      → pip install -r requirements.txt（flow/runtime）
      → pytest
      → ruff check
    → chat-build.yaml（并行）
      → npm install
      → wasm-pack build（sdk-wasm）
      → npm run build
      → npm run test
    → 全部通过 → docker compose build → 推送镜像到 registry
```

### 11.3 数据库迁移（生产环境）

```
运维执行 migrate.sh（或 CI 自动执行）
  → sqlx migrate run --database-url $DATABASE_URL
    → 获取 pg_advisory_lock(hash('sqlx_migrate'))
    → SELECT * FROM _sqlx_migrations → 已执行到 003
    → 执行 004_create_agent_config.sql（事务内）
      → 成功 → INSERT INTO _sqlx_migrations
    → 执行 005_create_snapshots.sql（事务内）
      → 成功 → INSERT INTO _sqlx_migrations
    → 释放 advisory lock
  → 输出 "Applied 2 migrations"
```

| 文档 | 阅读目的 |

### 1.2 编码约束

- 语言：Rust，代码全英文
- 框架：axum 0.7 + sqlx 0.7 + tokio 1.0 + serde 1.0
- 数据库：PostgreSQL 16
- 不直接依赖 runtime/flow（通过事件解耦）
- 所有数据访问通过 Repo trait 抽象（便于 mock 测试）
- 不使用 unwrap()/expect()（除初始化阶段的不可恢复错误）
- Commit scope：project | workitem | artifact | agent-config | snapshot | event | api | common

### 1.3 提交规范

遵循 `docs/design/实施计划书写规范.md` §前置条件 3 的 commit 格式。

## 二、技术风险评估

**需要 Spike：sqlx 编译时 SQL 校验**

| 风险 | 验证方式 | 通过标准 |
|------|---------|---------|
| sqlx 编译时校验是否需要运行中的 PostgreSQL | 写最简 CRUD 验证 sqlx::query! 宏 | 编译通过 + 运行时查询正确 |
| JSONB 字段的 sqlx 映射 | 测试 serde_json::Value 与 JSONB 的读写 | 写入 JSON → 读出 → 结构一致 |
| broadcast channel 的背压行为 | 模拟 1024+ 事件堆积 | 确认旧事件被丢弃（lagged），不阻塞发送方 |

Spike 代码位置：`spike/sqlx_jsonb_test/`（不合并主干）

## 五、回退规则

| 阶段 | 回退触发条件 | 回退目标 |
|------|------------|---------|
| 阶段 0 | sqlx 编译时校验对开发流程影响过大 | 概要设计，评估换 sea-orm 或 diesel |
| 阶段 2 | JSONB 字段的 sqlx 映射有性能问题 | 详细设计，评估将 JSONB 拆为独立列 |
| 阶段 3 | transition 的 7 步流程事务边界不清晰 | 详细设计 §十五点五，重新划分事务边界 |
| 阶段 4 | broadcast channel 在高并发下丢事件严重 | 概要设计，提前引入 Redis Pub/Sub |
| 阶段 5 | 三级覆盖的合并逻辑比预期复杂 | 详细设计，Phase 1 只做替换不做字段级合并 |

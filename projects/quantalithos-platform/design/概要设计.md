# quantalithos-platform 概要设计

> 平台数据服务 — 事件驱动架构，承载研发协作、产物管理、AI 配置、知识沉淀

---

## 一、项目定位

### 1.1 核心职责

quantalithos-platform 是整个平台的**数据中枢**，所有持久化数据都在这里。其他子项目（flow、runtime、chat、sync）都是它的消费者。

> **设计决策：从 quantalithos-vault（产物服务）升级为 quantalithos-platform（平台数据服务）**
>
> 原 vault 只负责产物存储。经讨论后发现平台需要承载项目管理、工单管理、
> 团队配置、AI Agent 配置、知识库等多个领域，远超"产物存储"的范畴。
> 参考禅道（一体化研发管理）+ CodeArts（产物管理）+ AI 配置管理的综合需求，
> 升级为平台数据服务。

## 二、架构设计：事件驱动

### 2.1 为什么选择事件驱动

```
对比三种架构：

单体服务（禅道模式）：
  ✅ 部署简单
  ❌ 模块共享数据库 → 表之间 JOIN 耦合 → 未来拆分成本极高
  ❌ 一个模块的 bug 可能影响全部

模块化单体（Rust workspace 模式）：
  ✅ 部署简单（单一二进制）
  ⚠️ 模块通过 trait 接口通信，但仍共享数据库
  ❌ 拆分时需要拆数据库

事件驱动（推荐）：
  ✅ 每个领域模块独立数据库 → 从第一天就是分的
  ✅ 模块之间通过事件异步通信 → 天然解耦
  ✅ 未来拆分零成本 → 每个模块已经是独立的
  ✅ Rust 实现 → 单一二进制部署（Phase 1 嵌入式事件总线）
  ⚠️ 需要设计好事件契约
```

### 2.3 事件驱动的工作方式

```
例：TL 在阶段 2 创建任务

flow 调用 platform API：
  POST /api/workitems/tasks
  { title: "标签系统", type: "feature", project_id: "blog" }
      │
      ▼
workitem 模块处理：
  1. 写入 workitem 数据库 → TASK-003
  2. 发布事件到事件总线：
     TaskCreated { task_id: "TASK-003", project_id: "blog", ... }
      │
      ▼
事件总线广播：
      │
      ├──> project 模块消费：
      │    更新项目的 task_count + 1
      │
      ├──> chat 模块消费（通过 WebSocket 推送）：
      │    通知前端刷新看板
      │
      └──> snapshot 模块消费：
           记录变更日志


例：Agent 完成编码，提交产物

runtime 调用 platform API：
  POST /api/artifacts
  { type: "code_patch", project_id: "blog", task_ref: "TASK-003",
    files: [...], test_result: "passed" }
      │
      ▼
artifact 模块处理：
  1. 存储产物元数据 → art-00042
  2. 存储文件到 S3/本地
  3. 发布事件：
     ArtifactCreated { artifact_id: "art-00042", task_ref: "TASK-003", ... }
      │
      ▼
事件总线广播：
      │
      ├──> workitem 模块消费：
      │    更新 TASK-003 的 deliverables 列表
      │
      └──> project 模块消费：
           更新项目的产物统计
```

### 3.2 workitem — 工单管理

```rust
// 工单基类 — 需求、任务、BUG 共用
struct WorkItem {
    id: String,                       // "TASK-003" / "REQ-001" / "BUG-002"
    project_id: String,
    item_type: WorkItemType,          // requirement | task | bug
    title: String,
    description: String,
    status: String,                   // 状态机由 item_type 决定
    priority: Priority,               // critical | high | medium | low
    assignee_id: Option<String>,      // 负责人
    reporter_id: String,              // 创建者
    parent_id: Option<String>,        // 父工单（需求 → 任务的关联）
    dependencies: Vec<String>,        // 依赖的工单 ID 列表
    labels: Vec<String>,              // 标签
    comments: Vec<Comment>,           // 评论
    attachments: Vec<String>,         // 关联的产物 ID
    created_at: DateTime,
    updated_at: DateTime,
}

enum WorkItemType {
    Requirement,                      // 需求（关联 PRD）
    Task,                             // 任务（开发任务）
    Bug,                              // 缺陷
}

enum Priority {
    Critical,
    High,
    Medium,
    Low,
}

struct Comment {
    id: String,
    author_id: String,                // Agent ID 或 "user"
    content: String,
    created_at: DateTime,
}
```

**任务状态机（task 类型）：**

```
created → assigned → in_progress → in_review → in_testing → completed
                         ↑              │            │
                         │              ▼            ▼
                         ├──── review_rejected   bug_found
                         │              │            │
                         └──────────────┴────────────┘

状态流转规则：
  created → assigned        指派处理人时自动流转
  assigned → in_progress    处理人开始工作时
  in_progress → in_review   处理人提交代码后
  in_review → in_testing    审查通过后，自动指派给测试人
  in_review → review_rejected  审查不通过，重新指派给处理人
  in_testing → completed    测试通过
  in_testing → bug_found    测试发现问题，重新指派给处理人
  review_rejected → in_progress  处理人重新修改
  bug_found → in_progress   处理人重新修复
```

**需求状态机（requirement 类型）：**

```
draft → reviewing → approved → in_progress → implemented → verified → closed
          │                                       │
          ▼                                       ▼
       needs_revision → reviewing            verify_failed → in_progress

状态流转规则：
  draft → reviewing         提交评审，指派给 TL
  reviewing → approved      TL 评审通过
  reviewing → needs_revision  TL 要求修改，重新指派给提出人
  needs_revision → reviewing  修改后重新提交
  approved → in_progress    TL 拆解为任务，开始实现
  in_progress → implemented  所有关联任务完成
  implemented → verified    验收通过（用户确认）
  implemented → verify_failed  验收不通过，重新指派给 TL
  verify_failed → in_progress  TL 创建修复任务
  verified → closed         需求关闭
```

**BUG 状态机（bug 类型）：**

```
open → confirmed → fixing → fixed → verifying → closed
 │        │          │                   │
 │        ▼          ▼                   ▼
 │     rejected    blocked          reopen → confirmed
 │
 └── cannot_reproduce

状态流转规则：
  open → confirmed          处理人确认是 BUG
  open → rejected           处理人拒绝（不是 BUG），指派回提出人
  open → cannot_reproduce   处理人无法复现，指派回提出人补充信息
  confirmed → fixing        处理人开始修复
  fixing → fixed            修复完成，指派给验证人（通常是提出人）
  fixing → blocked          被阻塞（依赖其他修复）
  blocked → fixing          阻塞解除
  fixed → verifying         验证人开始验证
  verifying → closed        验证通过，BUG 关闭
  verifying → reopen        验证不通过，重新指派给处理人
  reopen → confirmed        处理人重新确认
```

**指派机制：**

每个工单有三个角色字段：

```python
struct WorkItem {
    # ... 其他字段 ...
    reporter_id: String,              # 提出人（创建时指定，不变）
    assignee_id: Option<String>,      # 当前处理人（随状态流转变化）
    verifier_id: Option<String>,      # 验证人（修复完成时指定）
}
```

状态流转时自动变更指派：

```
BUG 场景：
  测试-1 创建 BUG → reporter=测试-1, assignee=后端开发-1
  后端开发-1 修复 → 状态=fixed, assignee=测试-1（自动指派回提出人验证）
  测试-1 验证通过 → 状态=closed

需求场景：
  用户创建需求 → reporter=user, assignee=TL（评审）
  TL 评审通过 → 拆解为任务，每个任务 assignee=对应开发
  所有任务完成 → 需求状态=implemented, assignee=user（验收）
  用户验收通过 → 状态=closed

任务场景：
  TL 创建任务 → reporter=TL, assignee=后端开发-1
  后端开发-1 提交审查 → 状态=in_review, assignee=TL（审查）
  TL 审查通过 → 状态=in_testing, assignee=测试-1
  测试-1 通过 → 状态=completed
```

> **设计更新：任务调度由 platform 驱动**
>
> 原设计中任务调度（依赖图、波次、并行分发）由 flow 的 TaskScheduler 负责。
> 经讨论后改为 platform 驱动：
> - 任务依赖关系存在 platform 数据库（workitem_dependencies 表）
> - TL 拆完所有任务后调用 start_execution 触发调度
> - platform 检查依赖图，将无依赖的任务状态改为 assigned + 自动指派
> - 任务完成时 platform 自动检查下游任务是否就绪
> - platform 不直接和 runtime 通信，通过事件通知 flow，flow 向 runtime 发 FlowMessage
>
> 原因：任务调度本质上是"工单状态流转 + 依赖检查"，属于 platform 的职责。
> flow 只需要监听 platform 事件，在 Agent 需要执行时发送 FlowMessage 告诉 Agent 怎么做。

**任务调度 API：**

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/projects/{pid}/workitems/start-execution | TL 触发任务调度（检查依赖图，启动无依赖任务） |
| GET | /api/projects/{pid}/workitems/dependency-graph | 获取任务依赖图（前端进度页用） |

**start_execution 处理逻辑：**

```
TL 调用 start_execution
    │
    ▼
platform 读取项目下所有 workitems + dependencies
    │
    ▼
构建依赖图，找出无依赖的任务
    │
    ▼
将无依赖任务状态改为 assigned + 指派给 assignee
    │
    ▼
发布 WorkItemAssigned 事件（每个被启动的任务一个）
    │
    ▼
flow 监听到事件 → 向 runtime 发 FlowMessage 告诉 Agent 怎么做
```

**任务完成时的自动调度：**

```
Agent 完成 TASK-002 → platform 状态变为 completed
    │
    ▼
platform 检查：谁依赖 TASK-002？
    → TASK-003（依赖 [TASK-002]）→ 依赖满足 → assigned + 指派
    → TASK-004（依赖 [TASK-002]）→ 依赖满足 → assigned + 指派
    → TASK-005（依赖 [TASK-003, TASK-004]）→ 依赖未满足 → 不动
    │
    ▼
发布 WorkItemAssigned 事件
    │
    ▼
```

## 三点五、API 设计：多视图模式

### 3.5.1 设计原则

> **借鉴 Tavily 的 AI-native 设计哲学**
>
> 参考 `docs/design/Tavily-为什么更适合AI及可借鉴点.md` 的核心思路：
> - 返回结果不应只是原始数据，而应是"可继续推理的决策材料"
> - 不同消费者需要不同的数据表示
> - 分数化、状态化、证据化
> - 事实/判断/建议分层返回

platform 的每个资源都支持多种视图，通过 RESTful 子资源路由访问：

```
GET /api/{resource}/{id}                 完整数据（web 页面用）
GET /api/{resource}/{id}/views/ai        AI 决策视图（flow/runtime 用）
GET /api/{resource}/{id}/views/card      卡片摘要（chat 嵌入用）
GET /api/{resource}/{id}/views/{custom}  自定义视图（按需扩展）
```

三种消费者，三种视图：

```
┌─────────────────────────────────────────────────────────────────┐

│                                                                 │

│       │                                                         │
│       ├── /views/ai  → AI 决策视图  → flow/runtime 消费          │
│       │                 facts + checks + scores + actions        │

│       └── /views/card → 卡片摘要   → chat 聊天窗口嵌入           │
```

### 3.5.3 AI 视图格式规范

所有资源的 `/views/ai` 都遵循统一的三层结构：

```json
{
  "id": "TASK-003",
  "resource_type": "workitem",

  "facts": {
    "status": "in_review",
    "type": "task",
    "priority": "high",
    "assignee": "backend-dev-1",
    "reviewer": "tech-lead",

    "created_at": "2026-04-20T10:00:00Z",

  },

  "checks": {
    "review_status": "pending",
    "blocking_issues": [],
    "missing_items": [],
    "risk_flags": [],
    "compliance_status": "ready"
  },

  "scores": {
    "readiness": 0.8,
    "risk": 0.1,
    "evidence_completeness": 0.9
  },

  "actions": {
    "allowed": ["approve_review", "reject_review", "add_comment"],
    "blocked": [],
    "recommended_next": "approve_review"
  },

    "source_of_record": "workitem",
```

**三层含义：**

| 层 | 字段 | 含义 | 谁产出 |
|---|------|------|--------|
| facts | 客观事实 | 当前状态、关联关系、时间 | 数据库直接查询 |
| checks | 系统判断 | 是否达标、缺失项、风险 | platform 业务逻辑计算 |
| scores | 量化分数 | 就绪度、风险度、完整度 | platform 规则引擎计算 |
| actions | 推荐动作 | 允许做什么、建议做什么 | platform 状态机推导 |
| evidence_refs | 证据引用 | 支撑判断的产物/记录 | 关联查询 |
| trace | 追溯信息 | 来源、请求 ID、新鲜度 | 自动附加 |

```
例：flow 收到 TASK-003 的 AI 视图后的决策过程

flow 调用：GET /api/workitems/TASK-003/views/ai

flow 读取：
  checks.review_status == "pending"     → 还在审查中，不推进
  checks.blocking_issues == []          → 没有阻塞
  actions.allowed 包含 "approve_review" → 可以审批

  → flow 等待 TL 的 code_review 节点完成
  → TL 提交 NodeResult(result_type="completed", output={verdict: "approved"})
  → flow 再次查询 AI 视图
  → checks.review_status == "approved"
  → actions.recommended_next == "start_testing"
  → flow 推进到 testing 节点
```

### 4.4 前端架构

> **设计决策：chat + 独立 web（Phase 2 如果需要）**
>
> - Phase 1：quantalithos-chat 承载所有前端功能（聊天 + 看板 + 进度 + 产物查看）
> - Phase 2：如果需要独立的管理后台（不依赖聊天入口），再拆出独立 web 应用
> - 两者共享同一套 platform API，不需要额外的 BFF 层

**前端技术选型：Vue 3**

| 维度 | 说明 |
|------|------|
| 框架 | Vue 3 + Composition API |
| 构建 | Vite |
| UI 库 | Naive UI 或 Element Plus |
| 状态管理 | Pinia |
| 路由 | Vue Router |
| HTTP | Axios |
| 图表/流程图 | AntV X6（流程图渲染）或 Vue Flow |
| WebSocket | 原生 WebSocket + 自动重连 |

**选 Vue 3 的原因：**
- 学习曲线最低，单文件组件直观
- Composition API 和 React Hooks 能力对等
- 中文生态最好（文档、社区、UI 库）
- Vite 构建速度快
- 和 Rust 后端配合良好（都是编译型思维）

**chat 和 web 的关系：**

```
Phase 1：
  quantalithos-chat (Vue 3)
    ├── /chat          聊天界面（私聊/群聊）
    ├── /chat/cards    嵌入式卡片（调用 /views/card API）
    ├── /projects      项目列表和进度（调用 /views/progress API）
    ├── /workitems     看板视图（调用工单 API）
    └── /artifacts     产物查看（调用产物 API）

Phase 2（如果需要）：
  quantalithos-web (Vue 3，独立应用)
    ├── /dashboard     管理仪表盘
    ├── /projects      项目管理（完整 CRUD）
    ├── /workitems     工单管理（完整看板 + 列表 + 详情）
    ├── /artifacts     产物管理（搜索 + 版本历史）
    ├── /agents        Agent 配置管理
    └── /settings      系统设置

  两个前端共享：
    - 同一套 platform API
    - 同一套 UI 组件库（抽成 npm 包）
    - 同一套类型定义
```

## 七、待细化

- 认证与权限：API 认证方式（JWT / API Key）、模块级权限控制
- 多租户：是否需要支持多个组织/公司

- API 版本管理：/api/v1/ 前缀

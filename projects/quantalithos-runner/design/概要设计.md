# quantalithos-runner 概要设计

> 跨平台运行器 — 用户体验 AI 开发的应用（WebView + 原生桥接）

---

## 一、项目定位

### 1.1 核心职责

quantalithos-runner 是一个跨平台 App，用户安装后，AI 开发的任何项目都能在里面运行和体验。

```
类比：
  微信 → 小程序
  Steam → 游戏
  Quantalithos Runner → AI 开发的应用
```

### 1.2 和其他项目的区别

```
chat     = 和 AI 团队协作（聊天、审批、看进度）
console  = 管理配置（项目设置、Agent 配置、监控）
runner   = 体验产品（运行 AI 开发的应用）
sandbox  = 开发环境（Agent 在里面编码、测试）
```

### 1.3 在整体架构中的位置

```
sandbox（开发环境）
  │
  │ build 模式 → 打包产物
  │
  ▼
platform（存储构建产物）
  │
  │ runner 下载产物
  │
  ▼
runner（用户设备）
  │
  │ 运行应用
  │
  ▼
用户体验
```

```
┌─────────────────────────────────────┐

│  ┌──────────┐                      │

│  └──────────┘                      │
└─────────────────────────────────────┘

数据来源：platform API
  GET /api/projects → 项目列表
  GET /api/projects/:pid/builds → 构建产物列表
```

### 2.2 运行时引擎

```
应用类型 → 运行方式：

  Web 应用（Vue / React）     → WebView 直接加载
  桌面应用（Electron / Tauri） → Web 模式运行
  Flutter 应用                → flutter build web → WebView
  React Native 应用           → react-native-web → WebView
  游戏（Unity / Godot）       → WebGL 导出 → WebView
  CLI 工具                    → xterm.js Web 终端

  统一入口：WebView 容器
```

### 2.3 应用沙箱

```
每个应用独立的：
  ├── 存储空间（localStorage / IndexedDB）
  ├── 网络权限（只能访问自己的后端 API）
  ├── 原生权限（相机 / GPS / 存储 → 按需授权）
  └── 生命周期（启动 / 暂停 / 恢复 / 关闭）
```

### 2.4 版本管理

```
应用更新流程：

  sandbox build 模式 → 打包新版本
       │
       │ POST /api/projects/:pid/builds
       ▼
  platform 存储构建产物
       │
       │ runner 检查更新
       │ GET /api/projects/:pid/builds?latest=true
       ▼
  runner 下载 + 安装
       │
       │ 替换本地应用包
       ▼
  用户看到新版本
```

## 三、技术栈

| 平台 | 技术 | 说明 |
|------|------|------|
| iOS | Swift + WKWebView | 原生 App + WebView 容器 |
| Android | Kotlin + WebView | 原生 App + WebView 容器 |
| Desktop | Tauri | Rust + WebView（和 chat 共用 Tauri） |
| Web | 浏览器 | PWA 模式，直接在浏览器运行 |

跨平台共享层：
| 层 | 技术 | 说明 |
|---|------|------|
| SDK | quantalithos-sdk（UniFFI 绑定） | API 调用、版本管理 |
| UI 框架 | Vue 3（WebView 内） | 应用列表、设置页面 |
| 原生桥接 | Capacitor 或自定义 bridge | WebView ↔ 原生能力 |

## 六、约束条件

### 6.1 技术约束

| 约束 | 说明 |
|------|------|
| 桌面端框架 | Tauri 2.x（Rust + WebView），与 chat 共用 Tauri 基础设施 |
| 移动端 | iOS: Swift + WKWebView；Android: Kotlin + WebView（Phase 3） |
| Web 端 | PWA 模式，浏览器直接访问（Phase 2 首发平台） |
| Shell UI | Vue 3（WebView 内渲染），所有平台共用同一套 UI |
| 原生桥接 | Capacitor 或自定义 bridge（JS ↔ Native），Phase 2 仅桌面端 |
| 数据持久化 | 本地 JSON 文件（registry.json），不使用本地数据库 |
| 网络通信 | 通过 gate 访问 platform API，不直接连数据库 |
| 应用包格式 | ZIP 压缩 + SHA256 校验，内含 manifest.json |

### 6.2 容量规划

| 指标 | Phase 2 目标 | Phase 3 目标 |
|------|-------------|-------------|
| 已安装应用数 | 1–10 | 50–100 |
| 单应用包大小 | < 50MB | < 200MB |
| WebView 并发实例 | 1（单应用运行） | 3–5（多应用切换） |
| 应用启动时间 | < 3s（本地加载） | < 2s |
| 本地存储总量 | < 500MB | < 2GB |
| 内存占用（Runner 本体） | < 128MB | < 256MB |
| 内存占用（单 WebView） | < 256MB | < 512MB |

### 6.3 合规约束

- 应用沙箱隔离：每个应用的存储、网络、权限互相不可见
- 权限授权：原生能力（相机/GPS/通知等）需用户明确授权
- 下载校验：所有应用包下载后必须 SHA256 校验，防止篡改
- 网络白名单：WebView 内应用只能访问声明的域名

## 七、层间约束

```
层间依赖规则（防退化）：

  Shell UI（Vue 3）
      │
      │ 只能调用 sdk 封装层
      │ 不能直接调用 Rust engine
      ▼
  sdk 封装层（TypeScript）
      │
      │ 只能调用 engine 暴露的 Tauri commands / bridge API
      │ 不能直接操作文件系统
      ▼
  engine 层（Rust）
      │
      │ 只能通过 PlatformClient 访问 platform
      │ 不能直接构造 HTTP 请求
      ▼
  platform（远程服务）

禁止的依赖方向：
  ✗ engine → Shell UI（engine 不知道 UI 的存在）
  ✗ Shell UI → 文件系统（必须通过 engine）
  ✗ WebView 应用 → Runner Shell 数据（沙箱隔离）
  ✗ WebView 应用 A → WebView 应用 B 的存储（沙箱隔离）
```

## 八、横切关注点

### 8.1 安全

| 关注点 | 方案 |
|--------|------|
| 应用沙箱 | 每个应用独立 WebView 实例，存储/网络/权限隔离 |
| 权限控制 | 原生能力按需授权，用户可随时撤销 |
| 下载完整性 | SHA256 校验，校验失败拒绝安装 |
| 网络隔离 | WebView 内应用只能访问 manifest 声明的域名白名单 |
| 代码注入防护 | 禁止 WebView 加载外部脚本（CSP 策略） |
| 认证 | Runner 通过 gate 认证（JWT），应用内不暴露 token |

### 8.2 性能

| 关注点 | 方案 |
|--------|------|
| 应用启动 | 本地文件加载（file:// 协议），避免网络延迟 |
| 下载优化 | 断点续传 + 进度展示；Phase 3 增量更新（diff patch） |
| WebView 内存 | 单应用运行模式（Phase 2）；多应用时后台应用冻结（Phase 3） |
| 缓存策略 | 应用列表缓存 60s；应用包永久缓存（版本号变化时才重新下载） |

### 8.3 可用性

| 关注点 | 方案 |
|--------|------|
| 离线运行 | 已安装应用可离线运行（Phase 3 完整支持） |
| 安装失败恢复 | 下载到临时目录，校验通过后才替换；失败不影响已安装版本 |
| 版本回滚 | 保留最近 2 个备份版本，一键回滚 |
| 错误提示 | 用户可理解的错误信息（非技术术语） |

### 8.4 可观测性

| 维度 | 方案 |
|------|------|
| 日志 | Rust: tracing；Shell UI: console.log 收集 |
| 崩溃报告 | WebView 崩溃捕获 + 上报（Phase 3） |
| 性能指标 | 应用启动时间、下载速度、WebView 内存占用 |

### 8.5 成本

| 关注点 | 方案 |
|--------|------|
| 存储成本 | 本地存储配额限制（默认 100MB/应用） |
| 带宽成本 | 应用包压缩（ZIP）；Phase 3 增量更新减少下载量 |
| 开发成本 | Phase 2 先做 Web/PWA + Tauri 桌面端，Phase 3 再做移动端 |

## 九、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | WebView 跨平台行为不一致（Safari/Chromium/WebKitGTK） | 应用在不同平台表现不同 | 高 | Phase 2 先做 PWA + Tauri（Chromium 内核为主）；建立跨平台兼容性测试矩阵 |
| 2 | 应用沙箱隔离不完整（WebView 存储泄漏） | 应用间数据互相可见 | 中 | 每个应用使用独立 WebView 实例 + 独立 data partition；Phase 2 编写沙箱隔离测试 |
| 3 | 大型应用包下载失败（网络不稳定） | 用户安装体验差 | 中 | 断点续传 + 重试机制；下载到临时目录，失败不影响已安装版本 |
| 4 | WebView 内存泄漏（长时间运行应用） | Runner 整体卡顿或崩溃 | 中 | Phase 2 单应用运行模式；监控 WebView 内存，超阈值提示用户重启应用 |
| 5 | Tauri 版本升级导致 API 不兼容 | 桌面端构建失败 | 低 | 锁定 Tauri 2.x 版本；关注 Tauri 发布日志，提前评估升级影响 |
| 6 | 移动端 WebView 性能不足（低端设备） | 应用运行卡顿 | 中 | Phase 3 移动端实现时做性能基准测试；提供"轻量模式"（禁用动画/降低分辨率） |

## 十、上线策略

### 10.1 发布顺序

```
Phase 2 发布顺序：

  ① Web/PWA 版（浏览器直接访问）
     │
     │ 验证核心流程：应用列表 → 安装 → 运行
     │ 收集用户反馈
     ▼
  ② Tauri 桌面端（macOS → Windows → Linux）
     │
     │ 验证原生能力：本地存储、文件系统
     │ 验证 WebView 容器隔离
     ▼
  ③ 全平台发布
```

### 10.2 灰度方案

| 阶段 | 范围 | 持续时间 | 观察指标 |
|------|------|---------|---------|
| 内部测试 | 开发团队 | 1 周 | 功能完整性、崩溃率 |
| 小范围灰度 | 10% 用户 | 1 周 | 应用安装成功率、启动时间、内存占用 |
| 全量发布 | 100% 用户 | — | 同上 + 用户留存率 |

### 10.3 回滚策略

- Web/PWA：回滚 CDN 部署版本（秒级）
- Tauri 桌面端：发布旧版本安装包 + 应用内提示更新
- 应用级回滚：用户可在 Runner 内回滚单个应用到上一版本

### 10.4 监控指标

| 指标 | 告警阈值 |
|------|---------|
| 应用安装成功率 | < 95% |
| 应用启动成功率 | < 98% |
| WebView 崩溃率 | > 1% |
| 平均启动时间 | > 5s |
| 下载失败率 | > 10% |

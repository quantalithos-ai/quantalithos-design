# Agent Runtime 技术选型

> 本文档记录 quantalithos-runtime 项目的技术选型决策过程和最终结论。

---

## 一、选型背景

### 1.1 项目定位

quantalithos-runtime 是 AI 驱动研发协作平台的核心引擎，负责：

- Agent 生命周期管理
- LLM 调用封装
- 多 Agent 协作
- 状态机管理
- 工具调用系统

### 1.2 选型目标

- 快速开发：能够在 3 个月内完成核心功能
- 生产可用：支撑多用户、多项目并发
- 生态成熟：能够复用现有 AI 生态
- 可维护性：代码清晰、易于迭代

## 二、候选语言分析

### 2.1 Python

| 维度 | 评估 |
|------|------|
| **AI 生态** | ⭐⭐⭐⭐⭐ 最成熟 |
| **LLM SDK** | ⭐⭐⭐⭐⭐ OpenAI 官方优先支持 |
| **Agent 框架** | ⭐⭐⭐⭐⭐ LangChain、LlamaIndex |
| **开发效率** | ⭐⭐⭐⭐⭐ 快速迭代 |
| **类型安全** | ⭐⭐⭐ Pydantic 补强 |
| **性能** | ⭐⭐⭐ 异步可接受 |
| **并发模型** | ⭐⭐⭐⭐ asyncio 成熟 |

**核心优势：**

```
AI 生态完整
─────────────────────────────────────────
OpenAI SDK      ✅ 官方优先支持
LangChain       ✅ 最成熟的 Agent 框架
LlamaIndex      ✅ 知识库/RAG 首选
Pydantic        ✅ 类型安全 + 数据验证
FastAPI         ✅ 高性能异步 API
Chroma/Pinecone ✅ 向量存储原生支持
```

### 2.2 TypeScript

| 维度 | 评估 |
|------|------|
| **类型安全** | ⭐⭐⭐⭐⭐ 编译时检查 |
| **前后端统一** | ⭐⭐⭐⭐⭐ 代码复用 |
| **异步支持** | ⭐⭐⭐⭐⭐ 原生 Promise/async |
| **AI 生态** | ⭐⭐⭐ 不如 Python 成熟 |
| **LLM SDK** | ⭐⭐⭐ 有但非官方优先 |
| **Agent 框架** | ⭐⭐⭐ 选择较少 |

**核心优势：**

```
前后端技术栈统一
─────────────────────────────────────────
chat-frontend (TypeScript)
       │
       └──→ agent-runtime (TypeScript)
            - 类型定义共享
            - 代码复用
            - 团队技能统一
```

### 2.3 Rust

| 维度 | 评估 |
|------|------|
| **性能** | ⭐⭐⭐⭐⭐ 极致性能 |
| **内存安全** | ⭐⭐⭐⭐⭐ 无 GC |
| **并发模型** | ⭐⭐⭐⭐⭐ 无数据竞争 |
| **跨平台分发** | ⭐⭐⭐⭐⭐ 单一二进制 |
| **AI 生态** | ⭐⭐ 不成熟 |
| **LLM SDK** | ⭐⭐ 选择极少 |
| **开发效率** | ⭐⭐ 周期长 |

**适用场景：**

```
✅ 本地工具（如 Codex CLI）
✅ 性能关键模块
✅ 安全隔离沙箱
✅ 高并发路由

❌ 复杂业务逻辑
❌ AI 框架集成
❌ 快速迭代阶段
```

### 2.4 Go

| 维度 | 评估 |
|------|------|
| **并发模型** | ⭐⭐⭐⭐⭐ goroutine |
| **部署简单** | ⭐⭐⭐⭐⭐ 单一二进制 |
| **开发效率** | ⭐⭐⭐⭐ 中等 |
| **AI 生态** | ⭐⭐ 较弱 |
| **类型系统** | ⭐⭐⭐ 泛型支持一般 |

## 四、决策结论

### 4.1 最终选择：两阶段策略

**Phase 1（当前）：纯 Python 实现**

快速验证设计、跑通核心闭环。性能瓶颈在 LLM API 调用（网络 IO），本地计算不是瓶颈。

**Phase 2（设计验证完成后）：Rust 框架骨架 + Python 业务模块**

识别真实瓶颈后，逐步将框架骨架下沉到 Rust，Python 保留业务模块。

```
Phase 1: 纯 Python（当前阶段）
─────────────────────────────────────────────────────
quantalithos-runtime 全部用 Python 实现
  - asyncio 做并发
  - Docker/subprocess 做沙箱
  - Python 层做权限校验
  - 目标：验证设计、跑通闭环

Phase 2: Rust 框架骨架 + Python 业务模块（设计验证后）
─────────────────────────────────────────────────────
Rust 层（框架骨架）— 稳定、性能敏感、安全关键
  - 进程管理、事件循环 (tokio)
  - 消息总线、路由
  - 权限校验引擎（硬拦截）
  - 沙箱执行环境
  - 配置加载、schema 校验
  - Agent 生命周期管理

Python 层（业务模块）— 频繁迭代、依赖 AI 生态
  - LLM 调用（官方 SDK）
  - Prompt 组装
  - 角色定义加载
  - 记忆系统
  - 工具实现
  - 技能编排

交互方式: PyO3 (Rust 编译为 Python 可导入的 .so)
构建工具: maturin (pip install 体验与纯 Python 包一致)
```

### 4.2 各子项目语言定位

| 子项目 | Phase 1 | Phase 2 | 说明 |
|--------|---------|---------|------|
| quantalithos-runtime | Python | Rust 骨架 + Python 模块 | 核心引擎，Phase 2 框架下沉 |
| quantalithos-flow | Python | Python（可选 Rust 热点） | 编排逻辑复杂，Python 迭代快 |
| quantalithos-sync | Rust | Rust | CLI 工具，从一开始就用 Rust |
| quantalithos-chat | TypeScript | TypeScript | 前端，标准 Web 技术栈 |
| quantalithos-vault | Python | Python | 产物管理，CRUD 为主 |
| quantalithos-gate | Python (FastAPI) | Go 或 Rust | API 网关，后期按并发需求升级 |
| quantalithos-infra | YAML/Shell | YAML/Shell | 基础设施配置 |

### 4.3 Phase 2 Rust 框架骨架的项目结构（预览）

> 以下结构仅作为 Phase 2 的设计参考，Phase 1 不实现。

```
quantalithos-runtime/
├── Cargo.toml                    # Rust workspace
├── crates/
│   ├── runtime-core/             # 进程管理、事件循环、Agent 生命周期
│   ├── message-bus/              # 消息总线、路由
│   ├── permission-engine/        # 权限校验、硬拦截
│   ├── sandbox/                  # 沙箱执行环境
│   ├── config-loader/            # YAML 配置加载、schema 校验
│   └── py-bridge/                # PyO3 桥接层
│
├── pyproject.toml                # Python 包定义
├── python/
│   └── quantalithos_runtime/     # Python 业务模块
│       ├── llm/                  # LLM 调用
│       ├── memory/               # 记忆系统
│       ├── roles/                # 角色加载与 prompt 组装
│       ├── tools/                # 工具实现
│       └── skills/               # 技能编排
│
├── shared_rules/                 # YAML 共享规则
├── role_store/                   # YAML 角色定义
└── skill_store/                  # YAML 技能定义
```

### 4.4 Phase 2 划分原则

| 判断标准 | → Rust | → Python |
|----------|--------|----------|
| 变化频率低（框架稳定后很少改） | ✅ | |
| 性能要求高（并发、消息路由、沙箱） | ✅ | |
| 安全要求高（权限拦截不能被绕过） | ✅ | |
| AI 生态依赖强（LLM SDK、向量库） | | ✅ |
| 频繁迭代（prompt、角色、工具） | | ✅ |

## 五、技术栈确定

### 5.1 Python 部分

| 组件 | 选型 | 版本 |
|------|------|------|
| 语言 | Python | 3.11+ |
| 异步框架 | asyncio + anyio | - |
| LLM 调用 | openai / litellm | 最新 |
| Agent 框架 | LangChain (可选) | 0.1+ |
| 类型系统 | Pydantic | v2 |
| API 框架 | FastAPI | 0.100+ |
| 数据库 | PostgreSQL + SQLAlchemy 2.0 | 异步 |
| 缓存 | Redis | - |
| 向量存储 | Chroma (开发) / Pinecone (生产) | - |
| 测试 | pytest + pytest-asyncio | - |

### 5.2 Rust 部分

| 组件 | 选型 | 说明 |
|------|------|------|
| Python 绑定 | PyO3 | Python ↔ Rust 交互 |
| 异步运行时 | tokio | 高并发 |
| 序列化 | serde | JSON/MessagePack |
| 沙箱 | firecracker / container | 安全隔离 |

## 六、风险与应对

### 6.1 Python 性能风险

| 风险 | 应对策略 |
|------|----------|
| GIL 限制 | 异步 IO、多进程 |
| 高并发瓶颈 | Rust 路由模块 |
| 内存占用 | 定期 GC、连接池 |

### 6.2 Rust 集成风险

| 风险 | 应对策略 |
|------|----------|
| PyO3 学习曲线 | 先纯 Python，后引入 Rust |
| 编译复杂度 | 独立模块，可选安装 |
| 调试困难 | 完善日志、单元测试 |

---

## 七、演进路线

```
Phase 1: 纯 Python 实现（验证设计）
─────────────────────────────────────────
- 全部用 Python 实现 quantalithos-runtime
- 跑通阶段 0 → 1 → 2 → 3 核心闭环
- asyncio 并发、Docker/subprocess 沙箱
- 验证角色系统、记忆系统、工具系统的设计

Phase 2: Rust 框架骨架引入（设计验证完成后）
─────────────────────────────────────────
- 识别真实性能瓶颈和安全需求
- 逐步将框架骨架下沉到 Rust（进程管理、消息总线、权限引擎、沙箱）
- Python 保留业务模块（LLM、prompt、记忆、工具、技能）
- 通过 PyO3 + maturin 构建，对外仍是 pip install 体验

Phase 3: 生产就绪（持续）
─────────────────────────────────────────
- 监控告警
- 日志审计
- 文档完善
- 性能调优
```

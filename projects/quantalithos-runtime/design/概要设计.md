## 一、项目定位

### 1.1 核心职责

Agent Runtime 是整个 AI 研发协作平台的**核心引擎**，负责：

- **Agent 生命周期管理**：实例化、销毁、持久化
- **Agent 角色定义**：Prompt 管理、工具权限、行为约束
- **LLM 调用封装**：统一接口、流式输出、成本追踪
- **工具调用系统**：工具注册、执行、沙箱隔离
- **多 Agent 协作**：消息路由、群聊管理
- **状态机管理**：状态转换、事件驱动

**技术选型：** 当前阶段（Phase 1）使用纯 Python 实现，快速验证设计。设计验证完成后（Phase 2）逐步将框架骨架（进程管理、消息总线、权限引擎、沙箱）下沉到 Rust，Python 保留业务模块（LLM 调用、prompt 组装、记忆、工具、技能）。详见 `技术选型.md`。

### 1.3 与 quantalithos-flow 的分工

quantalithos-runtime 负责 step 内部的 think → act 循环（Agent 执行层），宏观编排由 quantalithos-flow（daemon）控制：

- **quantalithos-flow（daemon）**：阶段状态机、工作流模板解析、step 调度、门禁校验、交接包管理
- **quantalithos-runtime**：Agent 生命周期、LLM 调用、工具执行、记忆管理、角色定义

Agent 不需要理解完整工作流，daemon 在每个 step 触发时注入最小必要上下文（当前任务、完成条件、完成后动作）。

### 1.4 与 quantalithos-sync 的衔接

quantalithos-sync 是 Rust 实现的 CLI 工具，负责项目工作区的初始化、恢复与双向同步。quantalithos-runtime 不直接管理配置文件的跨机器同步，而是从 quantalithos-sync 拉取到本地的目录结构中读取配置。

**衔接关系：**

- quantalithos-sync 负责将角色定义、共享规则、快照、任务卡、文档等从云端同步到本地项目目录
- quantalithos-runtime 从本地目录加载配置，不关心配置来源是本地编辑还是 quantalithos-sync 拉取
- quantalithos-flow (daemon) 在项目启动时调用 quantalithos-sync restore，确保本地工作区就绪后再启动 Agent

**本地项目目录结构（由 quantalithos-sync 管理）：**

**目录与云端库的映射及同步策略：**

- `agents/`：角色模板、规则、配置 — 项目创建时确定，偶尔修改，用于实例化 Agent

## 三、核心模块详细设计

### 3.1 core - 核心抽象层

#### 3.1.1 Agent 基类

```python
class Agent(ABC):
    """Agent 基类，所有角色继承此类"""
    
    # 核心属性
    agent_id: str              # 唯一标识
    role_id: str               # 角色定义 ID
    state: AgentState          # 当前状态
    config: AgentConfig        # 配置信息
    
    # 组件
    memory: Memory             # 记忆系统
    tools: List[Tool]          # 可用工具
    llm_client: LLMClient      # LLM 客户端
    
    # 核心方法
    async def process_message(message: Message) -> Message
    async def think() -> Optional[ToolCall]
    async def act(tool_call: ToolCall) -> ToolResult
```

#### 3.1.2 状态机

quantalithos-runtime 只维护 Agent 执行级别的状态机（think→act 循环）。项目级阶段状态机和任务级状态机由 quantalithos-flow (daemon) 负责。

**三层状态机归属：**

| 状态机 | 归属 | 说明 |
|--------|------|------|
| 项目级阶段状态机（6 阶段） | quantalithos-flow | daemon 控制阶段流转、门禁、回退 |
| 任务级状态机 | quantalithos-flow | daemon 驱动任务状态流转（created→assigned→in_development→...） |
| Agent 执行状态机 | quantalithos-runtime | Agent 内部 think→act 循环 |

quantalithos-runtime 对任务状态的关系是**只读消费 + 事件上报**：
- 读取：从任务卡文件读取当前任务状态，作为执行上下文的一部分
- 上报：Agent 完成 step 后向 quantalithos-flow 发送事件（如 `DELIVERABLE`、`BLOCKED`），由 quantalithos-flow 决定是否推进任务状态

**Agent 执行状态机：**

```
         ┌─────────┐
         │  idle   │ ← 初始状态
         └────┬────┘
              │ 接收消息
              ▼
         ┌─────────┐
         │ thinking│ ← 调用 LLM 思考
         └────┬────┘
              │ 决定行动
              ▼
         ┌─────────┐
         │ acting  │ ← 执行工具/发送消息
         └────┬────┘
              │ 需要等待
              ▼
         ┌─────────┐
         │ waiting │ ← 等待用户/其他Agent响应
         └────┬────┘
              │ 收到响应
              ├──────────────┐
              │              │
              ▼              ▼
         ┌─────────┐   ┌─────────┐
         │ thinking│   │completed│
         └─────────┘   └─────────┘
```

#### 3.1.3 消息结构

```python
class MessageType(str, Enum):
    """结构化消息类型"""
    TASK_ASSIGN = "TASK_ASSIGN"           # 任务分配
    QUESTION = "QUESTION"                 # 提问/澄清
    DELIVERABLE = "DELIVERABLE"           # 交付物提交
    REVIEW_RESULT = "REVIEW_RESULT"       # 代码审查结果
    BUG_REPORT = "BUG_REPORT"             # 缺陷报告
    STATUS_UPDATE = "STATUS_UPDATE"       # 状态更新
    GENERAL = "GENERAL"                   # 普通消息（群聊讨论等）


class ReplyType(str, Enum):
    """回复类型（Agent 产出消息时必须指定）"""
    RESULT = "result"                     # 完成，附带产出和验证证据
    BLOCKED = "blocked"                   # 被卡住，附带原因和需要的帮助
    CLARIFICATION = "clarification"       # 需要更多信息，附带具体问题


class Message(BaseModel):
    """消息结构"""
    message_id: str                       # 消息 ID
    message_type: MessageType             # 结构化消息类型
    reply_type: Optional[ReplyType]       # Agent 回复时必填
    role: str                             # "user" | "assistant" | "system" | "tool"
    content: str                          # 消息正文
    sender_agent_id: Optional[str]        # 发送者 Agent ID
    target_agent_id: Optional[str]        # 目标 Agent ID（@提及）
    mentions: List[str] = []              # 被 @提及的角色 ID 列表
    task_id: Optional[str]                # 关联任务 ID
    metadata: dict = {}                   # 扩展元数据
    created_at: datetime                  # 时间戳

    # reply_type 为 result 时必填
    output: Optional[dict] = None         # 产出内容
    verification: Optional[dict] = None   # 验证证据

    # reply_type 为 blocked 时必填
    reason: Optional[str] = None          # 阻塞原因
    help_needed: Optional[str] = None     # 需要的帮助

    # reply_type 为 clarification 时必填
    question: Optional[str] = None        # 具体问题
```

**消息校验由 runtime 框架层执行**（对应 shared_rules/communication.yaml 的 schema）：
- Agent 产出消息时，runtime 校验 reply_type 是否合法、必填字段是否齐全
- 消息路由、@提及路由、参与度控制由 quantalithos-flow (daemon) 负责，不在 runtime 层

### 3.3 memory - 记忆系统

#### 3.3.1 记忆架构

记忆系统分为两层，分阶段实现：

```
┌─────────────────────────────────────────────────────────┐
│                      记忆系统                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  ┌─────────────────────────────────────────────────┐   │
│  │ 对话记忆 (Conversation Memory)                   │   │
│  │ - 完整对话历史（含 daemon 注入的 step 上下文）    │   │
│  │ - 按会话/项目组织                                 │   │
│  │ - Phase 1：内存                                   │   │
│  │ - Phase 2：持久化到数据库（PostgreSQL）            │   │
│  └─────────────────────────────────────────────────┘   │
│                         │                               │
│                         ▼                               │
│  ┌─────────────────────────────────────────────────┐   │
│  │ 长期记忆 (Long-term Memory)          [Phase 3]   │   │
│  │ - 向量存储（Chroma / Pinecone）                   │   │
│  │ - 语义检索：用当前任务描述检索历史经验             │   │
│  │ - 来源：从历史项目的对话记忆中提取沉淀             │   │
│  └─────────────────────────────────────────────────┘   │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**设计决策：**

- 不设独立的"工作记忆"概念。daemon 注入的 step 上下文（当前任务、输入、完成条件）作为系统消息插入对话历史，LLM 自然理解"现在换任务了"。这与 Claude Code、Cursor、Superpowers 等主流工具的做法一致。
- 对话记忆是 Agent 的核心记忆，记录所有交互历史。Phase 1 在内存中，会话结束即丢失；Phase 2 持久化到数据库，支持 Agent 挂起/恢复。
- 长期记忆是跨项目经验积累，Phase 3 实现。从历史对话中提取经验片段，向量化后存入向量库，新任务开始时语义检索相关经验注入上下文。

**与快照系统的关系：**

```
Agent 被挂起时：
  对话记忆 ──→ 持久化到数据库（Phase 2）
  长期记忆 ──→ 已在向量库中（Phase 3）
  快照元数据 ──→ 写入 snapshots/agents/ 目录（YAML 文件）
                 记录 agent_id、role_id、state、conversation_ref、memory_ref

Agent 被恢复时：
  读取快照元数据 ──→ 从数据库恢复对话记忆
                     从向量库恢复长期记忆
                     daemon 重新注入当前 step 上下文
```

快照元数据是恢复的索引，不是记忆本身。它存在本地 `snapshots/` 目录，由 quantalithos-sync 同步到云端 AI 编排与知识平台的快照库。

**分阶段实现计划：**

| 阶段 | 内容 | 存储 |
|------|------|------|
| Phase 1（MVP） | 对话记忆（会话内） | 内存，会话结束丢失 |
| Phase 2 | 对话记忆持久化 + Agent 快照恢复 | PostgreSQL + snapshots/ YAML |
| Phase 3 | 长期记忆（跨项目经验） | 向量库（Chroma/Pinecone） |

#### 3.3.2 记忆压缩

当对话历史过长时，需要进行压缩：

```
原始对话（100条消息）
       │
       ▼
摘要压缩
       │
       ▼

```

### 3.4 tools - 工具系统

#### 3.4.0 工具与技能的区别

**工具（Tool）**：原子操作能力，单一职责
- 例如：`file_read`、`git_commit`、`terminal_execute`
- 运行时注册，全局可用
- 权限控制：角色定义中的 `tools` 列表

**技能（Skill）**：工具组合 + 执行流程 + 领域知识
- 例如：`代码审查`、`故障诊断`、`部署流程`
- 可由助手动态创建（参考 Hermes 自进化）
- 权限控制：角色定义中的 `skills` 列表

```
工具层级结构：

┌─────────────────────────────────────────────────────────┐
│                        技能层                            │
│  code_review_skill = [git_diff, file_read, lint_check]  │
│  deploy_skill = [build, test, deploy, notify]           │
└─────────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────┐
│                        巀具层                            │
│  file_read | git_commit | terminal_execute | ...       │
└─────────────────────────────────────────────────────────┘
```

**技能示例：**


#### 3.4.1 工具基类

```python
class Tool(ABC):
    """工具基类"""
    
    tool_name: str             # 工具名称
    description: str           # 工具描述
    parameters: dict           # JSON Schema 参数定义
    
    async def execute(**kwargs) -> ToolResult:
        """执行工具"""
        pass
    
    def validate_parameters(**kwargs) -> bool:
        """校验参数"""
        pass
```

#### 3.4.2 工具权限控制

工具权限采用**两层控制**：角色级静态权限 + step 级动态权限，两者取交集。

**第一层：角色级静态权限**

由角色定义中的 `tools` 字段控制，定义该角色能力的最大边界：

```python
role_def = RoleDefinition(
    role_id="tech_lead",
    role_name="Tech Lead",
    tools=[
        "file_read",
        "file_write",
        "git_status",
        "git_commit",
        "search_docs",
        "create_task",
        "assign_task",
        "create_role"
    ]
)
```

**第二层：step 级动态权限**

由 quantalithos-flow (daemon) 在分配 step 时注入 `allowed_tools`，将角色能力收缩到当前 step 所需的最小集：

```python
# daemon 注入的 step 上下文
step_context = {
    "step_id": "brainstorm",
    "action": "从各自角度讨论方案和风险",
    "allowed_tools": ["file_read", "search_docs"],  # 讨论阶段只允许读取
}
```

**运行时校验逻辑：**

```python
class ToolExecutor:
    def can_execute(self, agent: Agent, tool_name: str, step_context: Optional[dict] = None) -> bool:
        """两层权限取交集"""
        # 第一层：角色级静态权限
        role_def = role_store.get(agent.role_id)
        if tool_name not in role_def.tools:
            return False
        
        # 第二层：step 级动态权限（如果 daemon 注入了 allowed_tools）
        if step_context and "allowed_tools" in step_context:
            if tool_name not in step_context["allowed_tools"]:
                return False
        
        return True
```

**两层权限的关系：**

```
最终可用工具 = 角色定义的 tools ∩ daemon 下发的 step.allowed_tools
```

- 角色级权限定义能力上限（后端开发永远不能 deploy）
- step 级权限收缩当前场景（编码阶段不能合并分支）
- 如果 daemon 未注入 allowed_tools，则退化为仅角色级权限
- step 级权限不能超出角色级权限（交集，不是并集）

```python
class CreateRoleTool(Tool):
    """让助手可以动态创建新角色"""
    
    tool_name = "create_role"
    description = "创建一个新的角色定义"
    parameters = {
        "type": "object",
        "properties": {
            "role_name": {
                "type": "string",
                "description": "角色显示名称"
            },
            "identity": {
                "type": "string",
                "description": "角色身份描述（自然语言）"
            },
            "constraints": {
                "type": "array",
                "items": {"type": "string"},
                "description": "行为约束列表"
            },
            "tools": {
                "type": "array",
                "items": {"type": "string"},
                "description": "可用工具列表"
            },
            "read_paths": {
                "type": "array",
                "items": {"type": "string"},
                "description": "可读路径"
            },
            "write_paths": {
                "type": "array",
                "items": {"type": "string"},
                "description": "可写路径"
            },
            "forbidden_paths": {
                "type": "array",
                "items": {"type": "string"},
                "description": "禁止访问路径"
            },
            "extends": {
                "type": "string",
                "description": "继承自哪个角色（可选）"
            }
        },
        "required": ["role_name", "identity", "tools"]
    }
    
    async def execute(self, **kwargs) -> ToolResult:
        """执行角色创建"""
        
        # 1. 创建角色定义
        role_def = RoleDefinition(
            role_id=generate_role_id(kwargs["role_name"]),
            role_name=kwargs["role_name"],
            identity=kwargs["identity"],
            constraints=kwargs.get("constraints", []),
            tools=kwargs["tools"],
            permissions=PermissionConfig(
                read_paths=kwargs.get("read_paths", []),
                write_paths=kwargs.get("write_paths", []),
                forbidden_paths=kwargs.get("forbidden_paths", [])
            ),
            created_by="assistant",
            extends=kwargs.get("extends")
        )
        
        # 2. 验证角色定义
        validation_result = self.validate_role_definition(role_def)
        if not validation_result.is_valid:
            return ToolResult(
                success=False,
                error=f"角色定义验证失败: {validation_result.error}"
            )
        
        # 3. 存储到角色库
        role_store.save(role_def)
        
        # 4. 注册到运行时
        agent_runtime.register_role(role_def)
        
        return ToolResult(
            success=True,
            data={
                "role_id": role_def.role_id,
                "message": f"角色 {role_def.role_name} 创建成功"
            }
        )
    
    def validate_role_definition(self, role_def: RoleDefinition) -> ValidationResult:
        """验证角色定义的合法性"""
        
        # 检查 role_id 是否已存在
        if role_store.exists(role_def.role_id):
            return ValidationResult(
                is_valid=False,
                error=f"角色 {role_def.role_id} 已存在"
            )
        
        # 检查继承的角色是否存在
        if role_def.extends and not role_store.exists(role_def.extends):
            return ValidationResult(
                is_valid=False,
                error=f"继承的目标角色 {role_def.extends} 不存在"
            )
        
        # 检查工具是否都可用
        available_tools = tool_registry.list_tools()
        for tool_name in role_def.tools:
            if tool_name not in available_tools:
                return ValidationResult(
                    is_valid=False,
                    error=f"工具 {tool_name} 不存在"
                )
        
        return ValidationResult(is_valid=True)
```

### 3.5 roles - 角色定义

#### 3.5.1 设计理念

**核心原则：角色定义数据化，而非代码化。**

传统做法是将角色写死在代码中，每次新增角色都需要修改代码并重新部署。本系统采用数据化的角色定义：

- 角色定义是数据对象，存储在 `role_store` 中
- 助手可以通过工具动态创建新角色
- 运行时动态加载和注册角色
- 支持角色继承与组合

#### 3.5.1.1 Assistant（私人助理）角色设计

Assistant 是用户进入系统后的入口角色。它不属于任何单一项目，而是面向用户本人提供工作台级服务。

**生命周期：** 临时 Agent — 用户在线时存活，离线后释放。用户偏好和项目列表持久化在 `user_profile` 中。

**职责：**

| 职责 | 说明 |
|------|------|
| 发起新项目 | 协助用户整理项目申请表 → 创建群聊与 Tech Lead → 完成上下文转交 |
| 进入已有项目 | 查找用户项目列表 → 从快照恢复项目群组和 Agent 团队 |
| 管理项目列表 | 维护用户的项目列表（存在 user_profile 中） |
| 文档与知识服务 | 帮用户查阅文档、汇总上下文、做项目导航 |

**不做的事：** 不深度参与项目内讨论、不主导需求分析、不做技术决策、不做任务拆解（这些由项目 Tech Lead 负责）。

**启动状态机：**

```
idle
  → identifying_intent        判断是新项目、已有项目还是仅咨询
  → collecting_context         补齐最小必要信息
  → drafting_application       生成 project_application 草案
  → waiting_user_confirmation  用户确认或修正
  → provisioning_project       创建群聊、文件空间、实例化 Tech Lead
  → building_handoff           生成 assistant_startup_handoff 交接包
  → handoff_completed          通知用户项目已启动
  → exited                     退出启动主导流程
```

阻断规则：
- 未确认的 `project_application` 不能进入 `provisioning_project`
- 未完成建场的项目不能进入 `building_handoff`
- 未成功生成 `assistant_startup_handoff` 不能标记为 `handoff_completed`

**交接包：`assistant_startup_handoff`**

```yaml
assistant_startup_handoff:
  startup_id: string                    # 一次启动流程的唯一标识
  source: assistant                     # 固定为 assistant
  handoff_status: draft | ready_for_tech_lead | accepted
  user_request_summary: string          # 用户原始诉求摘要

  project_application:                  # 结构化申请表
    name: string
    type: new_project | enhancement | bugfix | ops
    description: string
    scope: small | medium | large
    feature_count: int
    has_frontend: bool
    has_mobile: bool
    priority: urgent | normal | low
    reference: string
    constraints: string

  startup_context:
    entry_mode: form | dialogue         # 启动入口类型
    user_confirmed: bool                # 用户是否确认申请口径
    known_constraints: string[]         # 已知约束
    open_questions: string[]            # 尚未澄清的问题
    assumptions: string[]               # 启动阶段默认假设

  routing_hint:
    suggested_owner: tech_lead          # 建议接手者
    suggested_next_step: goal_alignment # 建议下一动作
    candidate_route: stage1_requirement_analysis | bugfix_flow | ops_flow | exploration_flow
    urgency: low | normal | urgent
```

写入与消费责任：
- **Assistant** 负责创建、补齐、确认并投递交接包
- **Tech Lead** 负责读取、接受、基于其进入目标校准
- **系统/编排层** 负责保证交接包与项目现场、群聊、Tech Lead 实例之间的关联完整性

更新规则：
- `user_request_summary` 和用户确认后的 `project_application` 不应被无痕重写
- `known_constraints`、`open_questions`、`assumptions` 允许增补
- 一旦 `handoff_status = accepted`，项目主导责任从 Assistant 转移到 Tech Lead

**目标校准：`goal_alignment_brief`**

Tech Lead 接手后执行目标校准，产出结构化校准结果：

```yaml
goal_alignment_brief:
  source_startup_id: string             # 关联本次启动交接
  aligned_by: tech_lead                 # 固定为 tech_lead
  alignment_status: passed | needs_clarification | reroute

  work_item_type: new_project | enhancement | bugfix | optimization | exploration | ops
  core_problem: string                  # 核心要解决的问题
  target_outcome: string                # 本轮希望达成的结果
  target_users_or_scope: string         # 面向谁、影响范围
  priority_reason: string               # 为什么现在做
  success_signal: string[]              # 什么现象代表值得继续

  uncertainty_level: low | medium | high
  recommended_route: stage1_requirement_analysis | bugfix_flow | ops_flow | exploration_flow
  followup_questions: string[]          # needs_clarification 时的待补问项
  blocking_issue: string                # reroute 或阻断时的主因
```

通过条件：能判断类型、能写出问题、能给出目标、能定义成功信号、能确定路由。不要求信息完整，只要求足以支撑流程路由。

**阶段 1 入口规则：**

```
assistant_startup_handoff accepted
  → Tech Lead goal alignment
  → goal_alignment_brief passed
  → recommended_route = stage1_requirement_analysis
  → Stage 1 entry
```

#### 3.5.2 角色定义结构

**设计原则：优先使用 YAML/JSON，而非 Markdown**

原因：
- ✅ 结构化：YAML/JSON 天然支持嵌套、数组、对象
- ✅ 可验证：可通过 JSON Schema 校验格式
- ✅ 可编程：易于序列化/反序列化，无需解析 Markdown
- ✅ 可继承：YAML 支持锚点和合并，便于角色继承

```python
class RoleDefinition(BaseModel):
    """角色定义 - 数据对象"""
    
    # 基本信息
    role_id: str                      # 唯一标识
    role_name: str                    # 显示名称
    description: str                  # 简短描述
    
    # 共享规则引用
    shared_rules: SharedRulesConfig   # 声明加载哪些共享规则
    
    # 身份与约束
    identity: str                     # 身份描述（自然语言）
    constraints: List[str]            # 行为约束
    
    # 能力配置
    tools: List[str]                  # 可用工具列表
    skills: List[str]                 # 可用技能列表（技能是工具的组合）
    
    # 记忆配置
    memory_config: MemoryConfig       # 记忆策略配置
    
    # 权限配置
    permissions: PermissionConfig     # 路径权限
    
    # 自进化配置
    evolution_config: EvolutionConfig # 技能自迭代配置
    
    # 元信息
    created_by: str                   # "system" | "assistant" | "user"
    created_at: datetime
    version: str
    
    # 可选：继承
    extends: Optional[str] = None     # 继承自哪个角色
    overrides: Optional[dict] = None  # 覆盖配置


class SharedRulesConfig(BaseModel):
    """共享规则引用配置"""
    include: List[str]                # 要加载的共享规则 rule_id 列表
    exclude: List[str] = []           # 要排除的共享规则（项目级可用此字段关闭某些规则）


class MemoryConfig(BaseModel):
    """记忆策略配置"""
    enable_long_term: bool            # 是否启用长期记忆
    compression_threshold: int        # 压缩阈值（消息数）
    retention_days: int               # 记忆保留天数
    enable_user_profile: bool         # 是否学习用户偏好


class EvolutionConfig(BaseModel):
    """自进化配置（参考 Hermes）"""
    enable_auto_skill: bool           # 是否自动生成技能
    skill_improvement: bool           # 是否在使用中迭代技能
    frozen_snapshot: bool             # 是否启用冻结快照（降低 Token）


class PermissionConfig(BaseModel):
    """权限配置"""
    read_paths: List[str]             # 可读路径
    write_paths: List[str]            # 可写路径
    forbidden_paths: List[str]        # 禁止访问路径
    
    # 工具级权限细化（参考 OpenClaw）
    tool_restrictions: Dict[str, Any] # 工具限制条件
    # 例如：{"code_execute": {"max_timeout": 30, "sandbox": true}}
```

#### 3.5.2.1 YAML 角色定义规范

**完整示例：Tech Lead 角色**

```yaml
# role_store/tech_lead.yaml

# 基本信息
role_id: tech_lead
role_name: "项目负责人"
description: "负责需求分析、技术方案设计、任务拆解和工作分配"

# 共享规则引用
shared_rules:
  include:
    - communication
    - verification
    - review
  exclude: []              # 项目级可在此排除，如 exclude: [tdd]

# 身份定义
identity: |
  你是项目负责人，负责需求分析、技术方案设计、任务拆解和工作分配。
  你需要主导项目从需求到交付的全流程，但不直接实现代码。

# 行为约束
```

#### 3.5.2.3 共享规则（YAML 格式）

共享规则是所有角色通用的行为规范。每条规则是一个独立 YAML 文件，存储在 `shared_rules/` 目录下。

**设计原则：**
- 共享规则不是硬编码的固定列表，而是可扩展的规则库
- 用户/公司可以新增自己的共享规则（如"安全编码规范"、"国际化规范"）
- 项目级别可以覆盖或禁用某些规则
- 角色定义中通过 `shared_rules.include/exclude` 显式声明加载哪些规则

**共享规则文件结构：**

共享规则分为两部分：
- `schema`：给 runtime 框架层消费，做硬控制（校验、拦截、报错）
- `content`：给 LLM 消费，注入 system prompt 做风格指引

设计原则：**schema 管"能不能"，content 管"好不好"。** 凡是能在框架层控制的，不交给 prompt。

> 注意：消息路由、发言权控制（participation）、@提及路由、消息类型分发等属于编排层职责，由 quantalithos-flow (daemon) 在工作流模板或阶段配置中定义，不在 quantalithos-runtime 的共享规则中。quantalithos-runtime 的共享规则只管 Agent 产出消息后的格式校验和 prompt 层行为指引。

```yaml
# shared_rules/communication.yaml

rule_id: communication
name: "沟通规则"
description: "Agent 回复格式与沟通风格规范"
version: "1.0.0"
enabled: true                    # 全局开关

# runtime 框架层消费 — 硬控制
schema:
  # 回复类型约束
  reply_types:
    allowed: [result, blocked, clarification]
    required_fields:
      result: [output, verification]
      blocked: [reason, help_needed]
      clarification: [question]
    forbidden_patterns:
      - action: reject           # reject | warn | log
        patterns:
          - "收到，我来处理"
          - "正在进行中"
          - "好的，我了解了"

# LLM prompt 层消费 — 风格指引
content: |
  ## 沟通风格
  - 回复时直接给出结论和产出，不做寒暄
  - result 类型必须附带实际运行证据，不能只说"我做完了"
  - blocked 时必须说清楚卡在哪里、需要谁提供什么
  - clarification 时问题要具体，不能问"还有什么要求吗"

# 元信息
created_by: system               # system | company | user
applicable_roles: all            # all | [role_id_list]
tags: [communication, protocol]
```

#### 3.5.2.5 YAML vs Markdown 对比

| 维度 | YAML | Markdown | 结论 |
|------|------|----------|------|
| **结构化** | ✅ 原生支持嵌套、数组 | ❌ 需手动解析 | **YAML 胜** |
| **可验证** | ✅ JSON Schema 校验 | ❌ 无标准校验 | **YAML 胜** |
| **可读性** | ⚠️ 略低（需熟悉语法） | ✅ 高（人类友好） | **Markdown 胜** |
| **可维护** | ✅ 工具支持完善 | ⚠️ 易出现格式混乱 | **YAML 胜** |
| **可继承** | ✅ 锚点/合并机制 | ❌ 不支持 | **YAML 胜** |
| **跨语言** | ✅ 通用序列化格式 | ⚠️ 需解析库 | **YAML 胜** |

**最终决策：全部使用 YAML**
- 角色定义：✅ YAML（`role_store/*.yaml`）
- 技能定义：✅ YAML（`skill_store/*.yaml`）
- 共享规则：✅ YAML（`shared_rules/*.yaml`），规则正文放在 `content` 字段中
- Prompt 组装：在代码中按角色的 `shared_rules.include/exclude` 加载规则，拼接 `content` 字段

> 注：design 侧原方案中共享规则和角色身份使用 Markdown 文件，经讨论后统一改为 YAML。三层分离的概念模型（共享规则 / 角色定义 / 角色权限）保留，但不再体现为不同文件格式。

#### 3.5.2.6 Prompt 组装逻辑（从 YAML 到自然语言）

```python
def build_system_prompt(
    role_def: dict,
    shared_rules_dir: str,
    project_root: Optional[str] = None
) -> str:
    """从 YAML 角色定义组装系统 Prompt"""
    
    # 1. 加载角色声明的共享规则
    rule_ids = role_def['shared_rules']['include']
    excludes = role_def['shared_rules'].get('exclude', [])
    
    rules_content = []
    for rule_id in rule_ids:
        if rule_id in excludes:
            continue
        rule = resolve_shared_rule(rule_id, shared_rules_dir, project_root)
        if rule and rule.get('enabled', True):
            rules_content.append(rule['content'])
    
    # 2. 组装 prompt：共享规则 + 角色身份 + 行为约束
    prompt = "\n\n".join(rules_content)
    prompt += f"\n\n# 角色身份\n{role_def['identity']}"
    prompt += f"\n\n# 行为约束\n"
    prompt += "\n".join(f"- {c}" for c in role_def['constraints'])
    
    # 3. 阶段规则和任务上下文由 quantalithos-flow (daemon) 在运行时注入
    return prompt


def resolve_shared_rule(
    rule_id: str,
    shared_rules_dir: str,
    project_root: Optional[str] = None
) -> Optional[dict]:
    """按三级优先级查找共享规则"""
    
    search_paths = []
    
    # 项目级（最高优先级）
    if project_root:
        search_paths.append(f"{project_root}/agents/shared_rules/{rule_id}.yaml")
    
    # 公司级
    search_paths.append(f"company_templates/shared_rules/{rule_id}.yaml")
    
    # 系统级
    search_paths.append(f"{shared_rules_dir}/{rule_id}.yaml")
    
    for path in search_paths:
        if os.path.exists(path):
            return load_yaml(path)
    
    return None
```

**prompt 组装顺序：**

```
最终 system_prompt =
    shared_rules（按 include/exclude 加载的共享规则 content）
  + identity（角色身份描述）
  + constraints（行为约束）
  + 当前阶段规则（由 quantalithos-flow daemon 注入）
  + 当前任务上下文（工单内容，如果在阶段 3）
```

permissions 不注入 prompt，而是由运行时在工具调用时做权限校验。

#### 3.5.3 项目级角色团队

**核心问题：如何为每个项目独立创建不同的角色团队？**

##### 3.5.3.1 当前设计的不足

当前设计存在的问题：
- ❌ 角色定义存储在全局 `role_store/`，所有项目共享
- ❌ 项目无法自定义角色（如修改权限、添加技能）
- ❌ 同一角色在不同项目中可能有不同的权限需求
- ❌ 无法为特定项目创建专属角色

##### 3.5.3.2 解决方案：三级角色定义体系

```
角色定义优先级（从高到低）：

① project_roles/           项目级角色定义（优先级最高）
   └── {project_id}/
       ├── tech_lead.yaml      # 覆盖全局角色定义
       ├── backend_dev.yaml
       └── custom_role.yaml    # 项目专属角色

② company_templates/       公司级角色模板
   ├── mobile-developer/
   ├── ml-engineer/
   └── payment-specialist/

③ system_templates/        系统预置模板
   ├── assistant/
   ├── tech-lead/
   ├── backend-developer/
   └── frontend-developer/
```

**查找顺序：**
```
项目启动时查找角色定义：
project_roles/{project_id}/{role_id}.yaml
  ↓ 不存在
company_templates/{role_id}/
  ↓ 不存在
system_templates/{role_id}/
  ↓ 不存在
```

##### 3.5.3.7 运行时权限隔离

```python
class ProjectAwarePermissionChecker:
    """项目感知的权限检查器"""
    
    def check_permission(
        self,
        agent: Agent,
        action: str,
        target_path: str
    ) -> bool:
        """检查 Agent 在项目中的权限"""
        
        # 1. 获取项目 ID
        project_id = agent.project_id
        
        # 2. 加载项目级角色定义
        role_def = self.load_project_role(
            project_id=project_id,
            role_id=agent.role_id
        )
        
        # 3. 检查路径前缀
        project_base = f"projects/{project_id}/"
        if not target_path.startswith(project_base):
            # 不允许访问其他项目的文件
            return False
        
        # 4. 检查项目级权限
        relative_path = target_path[len(project_base):]
        permissions = role_def['permissions']
        
        # 检查禁止访问
        if self.match_paths(relative_path, permissions['forbidden_paths']):
            return False
        
        # 检查写权限
        if action == 'write':
            return self.match_paths(relative_path, permissions['write_paths'])
        
        # 检查读权限
        if action == 'read':
            return self.match_paths(relative_path, permissions['read_paths'])
        
        return False
```

###### 推荐方案：混合模式

**核心思路：**
- **系统级/公司级角色** → 存储在 `agent-runtime` 内
- **项目级角色** → 存储在项目的 `agents/` 目录

```
角色定义查找顺序：

1. 项目仓库：{project_root}/agents/roles/{role_id}.yaml
   ↓ 不存在
   
2. 公司模板：agent-runtime/company_templates/{role_id}/
   ↓ 不存在
   
3. 系统模板：agent-runtime/system_templates/{role_id}/
   ↓ 不存在
   
4. AI 辅助创建 → 保存到项目 agents/roles/
```

**代码实现：**

```python
class RoleDefinitionResolver:
    """角色定义解析器"""
    
    def resolve_role_definition(
        self,
        role_id: str,
        project_root: str
    ) -> RoleDefinition:
        """按优先级查找角色定义"""
        
        # 1. 项目仓库中的角色定义（最高优先级）
        project_role_path = f"{project_root}/agents/roles/{role_id}.yaml"
        if os.path.exists(project_role_path):
            return self.load_yaml(project_role_path)
        
        # 2. 公司级模板
        company_role_path = f"company_templates/{role_id}/definition.yaml"
        if os.path.exists(company_role_path):
            return self.load_yaml(company_role_path)
        
        # 3. 系统级模板
        system_role_path = f"system_templates/{role_id}/definition.yaml"
        if os.path.exists(system_role_path):
            return self.load_yaml(system_role_path)
        
        # 4. 角色不存在，返回 None
        return None
    
    async def create_role_if_missing(
        self,
        role_id: str,
        project_root: str,
        project_context: dict
    ) -> RoleDefinition:
        """如果角色缺失，AI 辅助创建并保存到项目仓库"""
        
        role_def = self.resolve_role_definition(role_id, project_root)
        if role_def:
            return role_def
        
        # AI 辅助创建
        role_def = await self.ai_create_role(
            role_id=role_id,
            context=project_context
        )
        
        # 保存到项目仓库
        save_path = f"{project_root}/agents/roles/{role_id}.yaml"
        self.save_yaml(role_def, save_path)
        
        return role_def
```

**项目启动流程：**

```python
async def bootstrap_project(project_root: str):
    """项目启动流程"""
    
    # 1. 加载团队配置
    team_config = load_yaml(f"{project_root}/agents/team.yaml")
    
    # 2. 解析所有角色定义
    resolver = RoleDefinitionResolver()
    
    for role_config in team_config['team']:
        role_id = role_config['role_id']
        
        # 从项目仓库 → 公司模板 → 系统模板查找
        role_def = resolver.resolve_role_definition(
            role_id=role_id,
            project_root=project_root
        )
        
        # 如果缺失，AI 创建并保存到项目仓库
        if not role_def:
            role_def = await resolver.create_role_if_missing(
                role_id=role_id,
                project_root=project_root,
                project_context=team_config
            )
        
        # 实例化 Agent
        await instantiate_agent(role_def, project_root)
```

```python
def build_system_prompt(role_id: str) -> str:
    """从 YAML 角色定义组装系统 Prompt"""
    
    # 第一层：加载共享规则（YAML）
    shared_rules = load_shared_rules_from_yaml()
    # communication.yaml + tdd.yaml + debugging.yaml + ...
    
    # 第二层：加载角色定义（YAML）
    role_def = role_store.load_yaml(role_id)
    # 从 role_store/role_id.yaml 读取角色定义数据
    
    # 第三层：转换为 Prompt 文本
    role_prompt = format_role_prompt(role_def)
    # 将 role_def['identity'], role_def['constraints'],
    # role_def['permissions'] 转换为自然语言描述
    
    # 组装
    system_prompt = f"""
{format_shared_rules(shared_rules)}

{role_prompt}
"""
    return system_prompt


def format_role_prompt(role_def: dict) -> str:
    """将 YAML 角色定义转换为 Prompt 文本"""
    
    constraints_text = '\n'.join(f'- {c}' for c in role_def['constraints'])
    
    prompt = f"""
# 角色身份
{role_def['identity']}

# 行为约束
{constraints_text}

# 权限说明
可访问路径：{', '.join(role_def['permissions']['read_paths'])}
可修改路径：{', '.join(role_def['permissions']['write_paths'])}
禁止访问：{', '.join(role_def['permissions']['forbidden_paths'])}
"""
    return prompt


def load_shared_rules_from_yaml() -> dict:
    """从 YAML 文件加载共享规则"""
    
    import yaml
    from pathlib import Path
    
    rules = {}
    shared_dir = Path('prompts/shared/')
    
    for yaml_file in shared_dir.glob('*.yaml'):
        with open(yaml_file, 'r', encoding='utf-8') as f:
            rule = yaml.safe_load(f)
            rules[rule['rule_id']] = rule
    
    return rules
```

```python
class AgentExecutor:
    """Agent 执行器"""
    
    async def run(self, agent: Agent, message: Message):
        """运行 Agent 处理消息"""
        
        while True:
            # 1. 更新状态
            agent.state = AgentState.THINKING
            
            # 2. 思考
            tool_call = await agent.think()
            
            if tool_call:
                # 3. 执行工具
                agent.state = AgentState.ACTING
                result = await agent.act(tool_call)
                
                # 将结果加入记忆，继续思考
                agent.memory.add_tool_result(result)
                continue
            
            # 4. 生成响应
            response = await agent.generate_response()
            
            # 5. 发送消息
            await self.send_message(response)
            
            # 6. 更新状态
            agent.state = AgentState.WAITING
            break
```

## 七、角色能力维度总览

基于 OpenClaw 和 Hermes 的设计，角色定义应包含以下能力维度：

### 7.1 核心能力维度

| 维度 | 说明 | 数据字段 |
|------|------|----------|
| **身份定义** | 角色身份描述、职责 | `identity`, `constraints` |
| **工具能力** | 可用的原子操作工具 | `tools` |
| **技能能力** | 可用的工具组合技能 | `skills` |
| **权限边界** | 文件/路径访问权限 | `permissions` |
| **记忆策略** | 记忆存储和检索策略 | `memory_config` |
| **自进化** | 技能自动生成和迭代 | `evolution_config` |

### 7.2 OpenClaw vs Hermes 对比参考

| 能力维度 | OpenClaw | Hermes | 我们的方案 |
|----------|----------|--------|------------|
| **角色定义** | Workspace 文件系统 | 单体 Agent | `RoleDefinition` 数据对象 |
| **技能创建** | 手动创建 | **自动生成** | 支持两种方式 |
| **技能迭代** | 手动编辑 | **自动优化** | 可选开启（`evolution_config`） |
| **记忆系统** | Markdown 文件 | SQLite + FTS5 | 分层记忆 + 可选 SQLite |
| **用户画像** | USER.md 手动维护 | **Honcho 自动学习** | 可选开启（`memory_config`） |
| **权限控制** | Agent 级 Skills 白名单 | 最小权限原则 | `PermissionConfig` + 工具级限制 |
| **MCP 支持** | 非原生 | **原生支持** | 规划中 |

### 7.3 技能系统设计要点

#### 7.3.1 技能定义结构

```python
class SkillDefinition(BaseModel):
    """技能定义"""
    
    skill_id: str                     # 唯一标识
    skill_name: str                   # 显示名称
    description: str                  # 描述
    
    # 技能组成
    tools: List[str]                  # 依赖的工具列表
    steps: List[SkillStep]            # 执行步骤
    validation: List[str]             # 验证条件
    on_failure: List[str]             # 失败处理
    
    # 元信息
    created_by: str                   # "system" | "assistant" | "evolution"
    auto_generated: bool              # 是否自动生成
    version: str
    usage_count: int                  # 使用次数（用于迭代优化）


class SkillStep(BaseModel):
    """技能执行步骤"""
    tool: str                         # 工具名称
    params: Dict[str, Any]            # 参数（支持模板变量）
    condition: Optional[str]          # 执行条件
```

#### 7.3.2 技能自动生成（参考 Hermes）

```
任务完成流程：

1. Agent 完成复杂任务
   │
   ▼
2. 分析执行轨迹
   - 哪些工具被组合使用
   - 参数传递模式
   - 验证逻辑
   │
   ▼
3. 生成技能定义
   skill_manager.create_skill_from_trace(
       task_trace=execution_trace,
       skill_name="数据迁移流程",
       min_reuse_potential=0.7
   )
   │
   ▼
4. 存储到技能库
   skill_store.save(skill_def)
   │
   ▼
5. 后续自动复用
   当识别到相似任务时，自动推荐使用该技能
```

#### 7.3.3 技能迭代优化

```python
class SkillEvolutionEngine:
    """技能自进化引擎"""
    
    async def improve_skill(
        self,
        skill_id: str,
        usage_feedback: UsageFeedback
    ) -> SkillDefinition:
        """根据使用反馈迭代技能"""
        
        # 1. 分析反馈
        # - 成功率、失败原因、用户修正
        
        # 2. 识别改进点
        # - 参数默认值优化
        # - 步骤顺序调整
        # - 验证条件补充
        
        # 3. 生成新版本
        new_skill = self.generate_improved_skill(
            current_skill=skill_store.get(skill_id),
            feedback=usage_feedback
        )
        
        # 4. 保存新版本
        skill_store.save(new_skill)
        
        return new_skill
```

#### 7.4.2 冻结快照模式（参考 Hermes）

```python
class FrozenSnapshot:
    """冻结快照 - 降低 Token 消耗"""
    
    def create_snapshot(self, messages: List[Message]):
        """创建不可变的对话快照"""
        # 1. 计算快照 Hash
        snapshot_hash = self.compute_hash(messages)
        
        # 2. 存储快照
        self.snapshot_store.save(
            hash=snapshot_hash,
            content=messages,
            created_at=datetime.now()
        )
        
        # 3. 后续请求复用快照
        # 只发送快照 Hash + 新消息
        # LLM 服务端可根据 Hash 恢复上下文
        return snapshot_hash
```

**优势：**
- 显著降低 API Token 消耗
- 支持 Prompt Cache（Anthropic 原生优化）
- 避免重复发送相同上下文

### 7.5 权限控制设计要点

#### 7.5.1 多层权限控制

```
权限检查流程：

Agent 请求操作
       │
       ├─ 第1层：角色级工具权限
       │    工具是否在 role_def.tools 中？
       │
       ├─ 第2层：角色级技能权限
       │    技能是否在 role_def.skills 中？
       │
       ├─ 第3层：路径权限
       │    路径是否在 permissions.read/write_paths 中？
       │
       ├─ 第4层：工具级限制
       │    是否满足 permissions.tool_restrictions？
       │    例如：code_execute 的 max_timeout
       │
       └─ 第5层：运行时安全检查
            沙箱隔离、敏感操作审计
```

#### 7.5.2 工具级限制示例

```python
# Tech Lead 角色定义
role_def = RoleDefinition(
    role_id="tech_lead",
    tools=["code_execute", "git_commit", ...],
    permissions=PermissionConfig(
        read_paths=["src/", "docs/", "tests/"],
        write_paths=["docs/", "tasks/"],
        forbidden_paths=["deploy/", "secrets/"],
        tool_restrictions={
            "code_execute": {
                "max_timeout": 30,           # 最多执行 30 秒
                "sandbox": True,              # 必须在沙箱中执行
                "forbidden_commands": ["rm -rf"]
            },
            "git_commit": {
                "require_review": True,       # 需要代码审查
                "protected_branches": ["main", "master"]
            }
        }
    )
)
```

## 一、项目定位

### 1.1 核心职责

quantalithos-sandbox 为每个项目提供隔离的运行环境，支持三种模式：

```
┌─────────────────────────────────────────────────────────────┐
│  quantalithos-sandbox                                        │
│                                                             │
│  模式 1：dev（开发）                                         │
│  ├── 每个 Agent 独立容器                                     │
│  ├── Agent 在容器内编码、编译、测试                           │
│  ├── 热重载、调试端口                                        │
│  └── 共享服务（数据库 / Redis / Gitea）                      │
│                                                             │
│  模式 2：preview（预览）                                     │
│  ├── 前后端打包部署到统一容器                                 │
│  ├── 注入测试数据                                            │
│  ├── 通过 gate 暴露公开 URL                                  │
│  └── 用户在浏览器中体验产品                                   │
│                                                             │
│  模式 3：build（构建）                                       │
│  ├── 编译生产版本                                            │
│  ├── 打包产物（Docker 镜像 / 静态文件 / 安装包）             │
│  ├── 运行集成测试                                            │
│  └── 上传产物到 platform → runner 可下载                     │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 设计目标与非目标

| 设计目标 | 说明 |
|---------|------|
| 项目隔离 | 每个项目独立的容器组，互不影响 |
| Agent 隔离 | 每个 Agent 独立容器，编译/测试不互相干扰 |
| 跨语言支持 | 根据项目技术栈动态选择基础镜像（Rust/Node/Python/Go） |
| 三种模式 | dev（开发）/ preview（预览）/ build（构建），按需切换 |
| 代码持久化 | 容器内代码通过 Gitea 持久化，容器销毁不丢失 |
| 可观测 | 容器状态、资源占用、日志实时上报 |

| 非目标 | 说明 |
|--------|------|
| 不做代码编辑器 | 代码编辑由 Agent 的 file_write 工具完成 |
| 不做 CI/CD | 构建流水线由 build 模式触发，不是独立的 CI 系统 |
| 不做多机调度 | Phase 1 单机 Docker，Phase 3 考虑 K8s |
| 不做资源计费 | Phase 1 不限制资源，Phase 3 考虑配额 |

### 1.3 错误处理矩阵

| 错误场景 | 处理方式 | 影响范围 |
|---------|---------|---------|
| Docker daemon 不可用 | sandbox_create 返回错误，Agent 无法执行 | 整个项目 |
| 容器创建失败（镜像拉取超时） | 重试 2 次，仍失败则上报 platform | 单个 Agent |
| 容器 OOM（内存不足） | 容器被 kill，上报错误，Agent 重新执行 | 单个 Agent |
| 磁盘满 | 拒绝 file_write，返回错误给 Agent | 单个 Agent |
| 端口冲突 | port_allocator 自动选择下一个可用端口 | 无影响 |
| Gitea 不可用 | git_push 失败，代码保留在容器内，稍后重试 | 不影响开发 |
| 容器内进程崩溃 | 自动重启（restart: unless-stopped） | 短暂中断 |
| compose up 超时 | 返回部分成功状态，已启动的容器保留 | 部分 Agent |

### 1.4 在整体架构中的位置

```
                    quantalithos-platform（云端数据中枢）
                         │
                         │ 项目配置 / 状态上报 / 构建产物
                         │
                    quantalithos-sandbox（沙箱环境管理）
                         │
              ┌──────────┼──────────────────┐
              │          │                  │
              ▼          ▼                  ▼
         sandbox-manager  Docker API       Gitea
         （Rust 服务）    （容器生命周期）   （Git 仓库）
              │
    ┌─────────┼─────────────────┐
    │         │                 │
    ▼         ▼                 ▼
  dev 模式   preview 模式     build 模式
  Agent 容器  统一部署容器     构建容器

  runtime 的工具（code_execute / file_write / git_commit）
  通过 SandboxProvider 接口调用 sandbox-manager API
```

### 1.3 与其他子项目的关系

| 子项目 | 关系 | 说明 |
|--------|------|------|
| platform | sandbox → platform API | 读取项目配置，上报状态，上传构建产物 |
| runtime | runtime → sandbox API | Agent 工具通过 SandboxProvider 在容器内执行 |
| core | core 定义 SandboxProvider 接口 | sandbox 实现该接口 |
| flow | flow 不直接调用 sandbox | TL Agent 通过 runtime 工具间接调用 |
| gate | gate 反向代理 preview URL | preview 模式下用户通过 gate 访问 |
| infra | infra 部署 sandbox-manager + Gitea | Docker Compose 配置 |
| console | console 展示 sandbox 状态 | 调用 platform API 获取 |
| runner | runner 下载 build 产物 | 从 platform 下载 |

## 三、sandbox-manager 服务

### 3.1 架构

```
sandbox-manager（Rust 服务，:8004）
│
├── api/
│   ├── POST /sandbox/create          创建沙箱环境
│   ├── POST /sandbox/:id/destroy     销毁
│   ├── POST /sandbox/:id/pause       暂停（docker-compose stop）
│   ├── POST /sandbox/:id/resume      恢复（docker-compose start）
│   ├── POST /sandbox/:id/switch      切换模式（dev→preview→build）
│   ├── GET  /sandbox/:id/status      状态查询
│   ├── POST /sandbox/:id/exec        在指定容器内执行命令
│   ├── POST /sandbox/:id/write-file  写文件到指定容器
│   ├── GET  /sandbox/:id/read-file   读文件
│   └── GET  /sandbox/:id/logs        容器日志
│
├── docker/
│   ├── compose_generator.rs          根据配置生成 docker-compose.yml
│   ├── container_manager.rs          调用 Docker API（bollard）
│   └── port_allocator.rs             端口分配（避免冲突）
│
├── templates/
│   ├── dev/                          dev 模式模板
│   │   ├── rust.yml                  Rust 开发容器模板
│   │   ├── node.yml                  Node.js 开发容器模板
│   │   ├── python.yml                Python 开发容器模板
│   │   └── shared_services.yml       共享服务模板
│   ├── preview/
│   │   └── unified.yml               统一部署模板
│   └── build/
│       └── builder.yml               构建容器模板
│
└── config.rs                         全局配置
```

### 3.2 目录结构

```
quantalithos-sandbox/
├── Cargo.toml
│
├── src/
│   ├── main.rs                      # axum server :8004
│   ├── api/

│   │   ├── create.rs                # 创建沙箱
│   │   ├── lifecycle.rs             # 暂停/恢复/销毁/切换
│   │   ├── exec.rs                  # 容器内执行命令
│   │   ├── files.rs                 # 文件读写
│   │   └── status.rs                # 状态查询
│   │
│   ├── docker/
│   │   ├── mod.rs
│   │   ├── compose_generator.rs     # 生成 docker-compose.yml
│   │   ├── container_manager.rs     # bollard Docker API
│   │   └── port_allocator.rs        # 端口分配
│   │
│   ├── gitea/
│   │   ├── mod.rs
│   │   └── client.rs                # Gitea API 客户端
│   │
│   └── config.rs
│
├── templates/                       # 容器模板
│   ├── dev/
│   ├── preview/
│   └── build/
│
└── config/
    └── sandbox.yaml
```

### 3.3 层间约束规则

| 约束 | 说明 |
|------|------|
| api/ 不直接调用 Docker API | api 层通过 docker/ 模块间接操作容器，不直接 import bollard |
| api/ 不直接调用 Gitea API | api 层通过 gitea/ 模块间接操作 Git，不直接发 HTTP 请求 |
| docker/ 不依赖 api/ 和 gitea/ | 容器管理是纯基础设施，不感知 HTTP 路由和 Git 逻辑 |
| gitea/ 不依赖 api/ 和 docker/ | Git 操作独立于容器管理和 HTTP 路由 |
| templates/ 是纯数据 | YAML 模板文件不含代码逻辑，由 docker/compose_generator.rs 读取和渲染 |
| config.rs 被所有模块依赖 | 全局配置是唯一的共享依赖 |

```
依赖方向（单向，禁止反向依赖）：

  main.rs（组装层）
    │
    └──> api/（HTTP 路由层）
           │
           ├──> docker/（容器管理层）
           │       │
           │       └──> templates/（YAML 模板，纯数据）
           │
           └──> gitea/（Git 服务层）
                  │
                  └──> config.rs（全局配置）
```

## 四、技术选型（决策四元组）

| 类别 | 选型 | 说明 |
|------|------|------|
| 语言 | Rust | 和 platform/gate 一致 |
| HTTP 框架 | axum | 和 platform/gate 一致 |
| Docker API | bollard | Rust Docker 客户端 |
| Git 服务 | Gitea | 轻量自托管 Git（Go 单二进制） |
| 配置 | serde_yaml | 模板 + 项目配置 |

### 4.1 容器化方案选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | Docker Compose（bollard 调用 Docker Engine API） |
| 备选 | ① Kubernetes + Pod　② Firecracker microVM　③ Podman（rootless） |
| 理由 | Phase 1 单机部署，Docker Compose 最简单且生态成熟；K8s 在单机场景过重；Firecracker 安全性更高但开发复杂度大幅增加；Podman rootless 安全性好但 compose 兼容性不如 Docker |
| 演进路径 | Phase 3 迁移到 K8s（每个沙箱 = 一个 Namespace + 多个 Pod）；安全敏感场景评估 gVisor 作为 OCI runtime |

### 4.2 Git 服务选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | Gitea（自托管 Git 服务） |
| 备选 | ① GitLab CE　② Forgejo　③ 裸 Git + SSH |
| 理由 | Gitea 单二进制部署、资源占用低（~100MB 内存）、API 完善；GitLab CE 功能丰富但资源占用高（>2GB）；裸 Git 缺少 Web UI 和 API |
| 演进路径 | Gitea 长期使用，Phase 3 如需 CI/CD 集成可评估 Gitea Actions |

### 4.3 容器镜像策略

| 维度 | 当前选择 |
|------|---------|
| 方案 | 预构建基础镜像（quantalithos/dev-rust、quantalithos/dev-node 等） |
| 备选 | ① 每次从官方镜像 + Dockerfile 构建　② Nix 构建环境 |
| 理由 | 预构建镜像启动快（秒级），避免每次 create 时安装工具链；Dockerfile 构建每次耗时数分钟；Nix 可复现但学习曲线陡 |
| 演进路径 | Phase 2 引入镜像版本管理 + 自动构建流水线（Gitea Actions） |

## 五、Phase 分期

### Phase 1

| 模块 | 范围 |
|------|------|

## 七、约束条件

### 7.1 技术约束

| 约束 | 说明 |
|------|------|
| 语言 | Rust（axum），与 platform/gate 统一技术栈 |
| 容器运行时 | Docker Engine（bollard 调用 Docker API），不直接调用 containerd |
| 网络模型 | 每个项目一个 Docker bridge 网络，项目间网络隔离 |
| 存储 | 容器内代码通过 Docker volume 持久化；Phase 2 通过 Gitea 持久化 |
| 部署 | Phase 1 单机 Docker；Phase 3 K8s |
| 内部服务 | sandbox-manager 是内部服务，不经过 gate，由 runtime 通过 SandboxProvider 接口直接调用 |

### 7.2 容量规划

| 指标 | Phase 1 目标 | Phase 2 目标 |
|------|-------------|-------------|
| 并发项目数 | 1–3 | 10–20 |
| 每项目 Agent 容器数 | 2–5 | 5–10 |
| 单机最大容器数 | 15 | 50 |
| 单容器内存上限 | 2GB（不限制） | 2GB（cgroup 硬限制） |
| 单容器 CPU 上限 | 不限制 | 2 核（cgroup 硬限制） |
| 单容器磁盘上限 | 不限制 | 10GB（Phase 3） |
| sandbox_create 响应时间 | < 30s（含镜像拉取缓存命中） | < 15s |
| exec 命令响应时间 | < 60s（编译类命令除外） | 同左 |
| sandbox-manager 内存占用 | < 128MB | < 256MB |

### 7.3 合规约束

- 容器内进程以非 root 用户运行（Phase 2 加固）
- 容器不挂载宿主机敏感目录（/etc、/var/run/docker.sock 只读挂载给 manager）
- Agent 执行的命令通过白名单校验（Phase 2），Phase 1 信任 runtime 传入的命令
- 构建产物上传前进行病毒扫描（Phase 3）

## 八、横切关注点

### 8.1 安全

| 关注点 | 方案 |
|--------|------|
| 容器逃逸 | Phase 1：Docker 默认隔离 + 禁用 `--privileged`；Phase 2：评估 gVisor 作为 OCI runtime；Phase 3：Firecracker microVM |
| 网络隔离 | 每个项目独立 Docker bridge 网络，项目间不可互访；容器只能访问共享服务和外网（可配置） |
| 文件系统隔离 | 每个 Agent 容器独立 volume，不共享文件系统；共享服务（DB/Redis）通过网络访问 |
| 命令注入 | exec API 接收结构化命令（command + args 数组），不拼接 shell 字符串 |
| 镜像安全 | 只使用预构建的 quantalithos/* 基础镜像，不允许 Agent 指定任意镜像 |
| Prompt Injection → 沙箱 | Agent 可能被 prompt injection 诱导执行恶意命令；Phase 1 依赖 runtime 层过滤；Phase 2 sandbox 层增加命令白名单 |

### 8.2 性能

**端到端延迟预算表（sandbox_create dev 模式）：**

| 环节 | 预估延迟 | 依据 |
|------|---------|------|
| 读取项目配置（platform API） | < 100ms | HTTP 调用 |
| 生成 docker-compose.yml | < 50ms | 模板渲染 |
| docker-compose up（镜像已缓存） | 5–15s | 容器启动 + 共享服务就绪 |
| git clone 到容器内 | 2–10s | 取决于仓库大小 |
| **总计** | **< 30s** | 首次创建；后续 resume < 3s |

### 8.3 可用性

| 关注点 | 方案 |
|--------|------|
| Docker daemon 不可用 | sandbox_create 返回错误，runtime 上报 platform；不自动重试（需人工排查） |
| 容器 OOM | Docker 自动 kill，sandbox-manager 检测到后上报状态；runtime 可选择重新 exec |
| 磁盘满 | file_write 返回错误，Agent 收到错误后可清理或上报 |
| sandbox-manager 崩溃 | 已创建的容器继续运行（Docker 管理）；manager 重启后通过 docker ps 恢复状态 |

### 8.4 可观测性

| 维度 | 方案 |
|------|------|
| 日志 | tracing + tracing-subscriber，JSON 结构化；每个 API 调用记录 sandbox_id/project_id/action/duration |
| 容器日志 | 通过 Docker logs API 采集，GET /sandbox/:id/logs 暴露给调用方 |
| 指标 | Phase 2 引入 /metrics 端点：sandbox_create_duration、containers_active、exec_duration、disk_usage_bytes |
| 追踪 | 接收 runtime 传入的 X-Request-Id，贯穿 sandbox 操作日志 |

### 8.5 成本

| 关注点 | 方案 |
|--------|------|
| 容器资源 | Phase 1 不限制（开发阶段）；Phase 2 cgroup 限制（2GB 内存 / 2 核 CPU） |
| 闲置容器 | Phase 2 引入自动暂停（idle > 30min → docker-compose stop）；resume < 3s |
| 磁盘清理 | Phase 2 引入定时清理（已销毁沙箱的 volume 保留 7 天后删除） |
| 镜像存储 | 预构建镜像约 2–5GB/语言；定期清理未使用的旧版本镜像 |

## 九、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | Docker daemon 崩溃 | 所有沙箱不可用，Agent 无法执行 | 低 | Phase 1 可接受（开发阶段）；Phase 3 K8s 多节点，单节点故障不影响全局 |
| 2 | 容器逃逸（LLM 诱导恶意命令） | 攻击者获取宿主机权限 | 中 | Phase 1：禁用 --privileged + 非 root 用户；Phase 2：gVisor；Phase 3：Firecracker |
| 3 | 资源耗尽（内存/CPU/磁盘） | 宿主机不稳定，影响所有项目 | 中 | Phase 1：单机 3 项目上限；Phase 2：cgroup 硬限制 + 磁盘配额 + 自动暂停闲置容器 |
| 4 | 端口冲突 | 容器启动失败 | 低 | port_allocator 维护已分配端口集合，自动选择下一个可用端口（范围 10000–60000） |
| 5 | Gitea 不可用（Phase 2） | git push 失败，代码只在容器内 | 中 | 代码保留在容器 volume 中不丢失；Gitea 恢复后自动重试 push |
| 6 | 基础镜像过时 | 容器内工具链版本落后，编译失败 | 低 | Phase 2 引入镜像自动构建流水线，每周更新基础镜像 |

### 常见异常场景

| 场景 | 处理方式 |
|------|---------|
| 镜像拉取超时 | 重试 2 次（间隔 5s），仍失败返回错误给 runtime |
| 容器启动失败（端口占用） | port_allocator 重新分配端口，重试 1 次 |
| exec 命令超时（如编译卡死） | 60s 超时后 kill 进程，返回 timeout 错误 |
| 容器内磁盘满 | file_write 返回 disk_full 错误，Agent 可执行清理命令 |

### 边缘异常场景

| 场景 | 处理方式 |
|------|---------|
| docker-compose up 部分成功 | 返回 partial_success 状态，已启动的容器保留，未启动的记录错误原因 |
| 容器内进程僵死（zombie） | Phase 2 引入健康检查（每 30s），连续 3 次失败则重启容器 |
| 宿主机重启后容器状态丢失 | sandbox-manager 启动时扫描 docker ps，重建内存状态；标记为 unknown 的沙箱需要用户确认 |
| 两个项目同时 create 竞争资源 | sandbox_create 内部加互斥锁（tokio Mutex），串行化容器创建 |

## 十、上线策略

### 10.1 灰度方案

| 阶段 | 范围 | 观察时间 | 推进条件 |
|------|------|---------|---------|
| 内部测试 | 1 个测试项目 | 1 天 | create/exec/destroy 全流程无错误 |
| 小范围 | 3 个项目 | 3 天 | 容器稳定运行，无 OOM/崩溃 |
| 全量 | 所有项目 | 持续观察 | — |

### 10.2 回滚策略

| 触发条件 | 回滚步骤 |
|---------|---------|
| sandbox-manager 崩溃率 > 0 | 回退到旧版二进制，已有容器不受影响 |
| 容器创建成功率 < 90% | 回退到旧版，排查 Docker/镜像问题 |
| 宿主机资源告警 | 暂停新建沙箱，清理闲置容器 |

> 回滚安全性：sandbox-manager 无状态数据库，容器由 Docker 管理；回退版本后通过 docker ps 恢复状态。

### 10.3 上线监控指标

| 指标 | 告警阈值 |
|------|---------|
| sandbox_create 成功率 | < 95% 持续 5 分钟 |
| 活跃容器数 | > 单机上限的 80% |
| 宿主机内存使用率 | > 85% |
| 宿主机磁盘使用率 | > 80% |
| exec 超时率 | > 5% |

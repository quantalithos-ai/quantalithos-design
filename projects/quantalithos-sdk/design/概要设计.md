## 一、项目定位

### 1.1 核心职责

quantalithos-sdk 是所有客户端（web、desktop、mobile）与 quantalithos-platform 交互的统一基础库。

```
                    quantalithos-platform (API)
                           │
                           │ HTTP + WebSocket
                           │
                    ╔══════╧══════════╗
                    ║ quantalithos-   ║
                    ║   sdk (Rust)    ║
                    ╚══════╤══════════╝
                           │
              ┌────────────┼────────────────────┐
              │            │                    │
              ▼            ▼                    ▼
         sdk-wasm     Tauri 直接调用      UniFFI 绑定
         (浏览器)     (桌面端)            (iOS/Android/Flutter)
              │            │                    │
              ▼            ▼                    ▼
         quantalithos  quantalithos        quantalithos
           -chat         -chat               -mobile
         (Vue 3 web)   (Tauri desktop)     (Phase 3)
```

**不做的事：**
- 不做 UI 渲染 — 那是各端的事
- 不做平台特性（通知、托盘）— 那是各端的事
- 不做业务编排 — 那是 flow 的事

### 1.2 谁消费 SDK

| 消费者 | 使用的 crate | 绑定方式 |
|--------|-------------|---------|
| quantalithos-chat (Vue 3 web) | sdk-models + sdk-api + sdk-ws + sdk-store → sdk-wasm | WASM + TS 薄封装 |
| quantalithos-chat (Tauri desktop) | sdk-models + sdk-api + sdk-ws + sdk-store | Rust 直接调用 |
| quantalithos-sync | sdk-models + sdk-api | Rust 直接调用 |
| quantalithos-mobile (Phase 3) | sdk-models + sdk-api + sdk-ws + sdk-store | UniFFI → Swift/Kotlin |

### 1.3 与 quantalithos-sync 的关系

sync 当前自己实现了 platform API 客户端（client/ 模块）。SDK 完成后，sync 应该迁移到使用 sdk-api：

```
当前：
  quantalithos-sync/src/client/     # 自己实现的 API 客户端
    ├── project.rs
    ├── workitem.rs
    └── artifact.rs

迁移后：
  quantalithos-sync
    └── 依赖 sdk-models + sdk-api   # 复用 SDK 的 API 客户端
```

### 2.1 依赖关系

```
sdk-models（零依赖，纯数据结构）
    │
    ├──> sdk-api（HTTP 客户端）
    │       │
    ├──> sdk-ws（WebSocket）
    │       │
    └───────┴──> sdk-store（状态管理，依赖 api + ws）
                     │
                     └──> sdk-wasm（WASM 绑定，依赖 store）

消费者按需引用：
  sync    → sdk-models + sdk-api          （最轻量）
  Tauri   → sdk-models + sdk-api + sdk-ws + sdk-store（完整，Rust 直接调用）
  web     → sdk-wasm                      （WASM 包，内含全部）
  mobile  → UniFFI 绑定 sdk-store         （Phase 3）
```

### 2.2 层间约束规则

| 约束 | 说明 |
|------|------|
| sdk-models 零外部依赖 | 只依赖 serde/chrono，不依赖任何网络库或其他 crate；所有 crate 都依赖它 |
| sdk-api 不依赖 sdk-ws / sdk-store / sdk-wasm | API 客户端是纯 HTTP 层，不感知 WebSocket 和状态管理 |
| sdk-ws 不依赖 sdk-api / sdk-store / sdk-wasm | WebSocket 层独立于 HTTP 和状态管理 |
| sdk-store 不依赖 sdk-wasm | 状态管理层是纯 Rust 逻辑，不感知 WASM 绑定细节 |
| sdk-wasm 是最外层 | 只做 Rust↔JS 类型转换和桥接，不含业务逻辑 |
| 依赖方向严格单向 | models → api/ws → store → wasm，禁止反向依赖 |

```
依赖方向（严格单向，禁止反向）：

  sdk-models（纯数据，零依赖）
       │
       ├──> sdk-api（HTTP 客户端，依赖 models）
       │
       ├──> sdk-ws（WebSocket，依赖 models）
       │
       └──> sdk-store（状态管理，依赖 models + api + ws）
                │
                └──> sdk-wasm（WASM 桥接，依赖 store，最外层）
```

## 三、核心模块设计

### 3.1 sdk-models — 数据模型

纯数据结构，零外部依赖（只依赖 serde），所有其他 crate 和消费者都依赖它。

| 模块 | 包含的类型 | 说明 |
|------|-----------|------|
| project.rs | Project, ProjectStatus, TeamMember | 项目和团队 |
| workitem.rs | WorkItem, WorkItemType, Priority, WorkItemTransition, WorkItemComment | 工单和状态变更 |
| artifact.rs | Artifact, ArtifactVersion | 产物和版本 |
| role.rs | RoleDefinition, SharedRule, ProcessTemplate | Agent 配置 |
| llm.rs | ModelInfo, ProjectLlmConfig | LLM 模型配置 |
| message.rs | FlowMessage, FlowMessageType, NodeResult, NodeResultType | flow↔runtime 通信协议 |
| payload.rs | NodeExecutePayload, ChatMessagePayload, AgentCreatePayload, ReplyTo | 消息负载类型 |
| bpmn.rs | FlowNode（tagged enum）, FlowEdge | BPMN 节点（前端渲染用） |
| views.rs | AiView, CardView, ProgressView, PipelineProgress, StageProgress, TaskSummary | 多视图模型 |

> 完整的 struct 定义见详细设计 §二。

### 3.2 sdk-api — platform API 客户端

封装所有 platform HTTP API 调用，提供类型安全的 Rust 接口。

| API 模块 | 核心方法 | 对应 platform 端点 |
|---------|---------|-------------------|
| ProjectApi | create / get / list / get_progress / list_members | /api/projects/* |
| WorkItemApi | create / get / list / transition / assign / get_ai_view / get_card_view | /api/workitems/* |
| ArtifactApi | create / get / list / get_content / list_versions | /api/artifacts/* |
| AgentConfigApi | get_role / list_rules / get_process / get_process_graph / fork_process | /api/agent-config/* |
| SnapshotApi | save_agent / get_agent / save_workflow / get_latest_workflow | /api/snapshots/* |
| LlmApi | list_models / get_model / get_project_config / update_project_config | /api/system/models/* |

> 完整的方法签名和实现见详细设计 §三。

### 3.3 sdk-ws — WebSocket 连接管理（Phase 2）

| 组件 | 职责 |
|------|------|
| WsConnection | 连接管理（连接/断开/自动重连/心跳） |
| Subscription | 订阅管理（按 topic 订阅/取消订阅） |

核心方法签名：

| 方法 | 说明 |
|------|------|
| connect() | 建立 WebSocket 连接（携带 JWT token） |
| disconnect() | 断开连接 |
| on_message(callback) | 注册消息回调（收到 PlatformEvent 时触发） |
| subscribe_project(pid) | 订阅项目级事件（工单变更、阶段推进等） |
| unsubscribe(topic) | 取消订阅 |

> Phase 2 实现。完整定义见详细设计 §3.5（待补充）。

### 3.4 sdk-store — 状态管理（Phase 2）

| 组件 | 职责 |
|------|------|
| ChatStore | 聊天状态（消息列表、群聊、门禁） |
| ProjectStore | 项目状态（阶段进度、团队） |
| WorkItemStore | 工单状态（看板、列表） |

核心方法签名：

| 方法 | 说明 |
|------|------|
| load_project(pid) | 加载项目的聊天室列表和进度 |
| send_message(room_id, content) | 发送聊天消息 |
| respond_gate(gate_id, action, comment) | 处理门禁审批 |
| get_kanban(pid) | 获取工单看板数据 |
| get_progress(pid) | 获取项目进度（流程图数据） |

> Phase 2 实现。完整定义见详细设计 §3.6（待补充）。

### 3.5 sdk-wasm — WASM 绑定

Phase 1 采用全局 PlatformClient + 独立函数的方式（无状态），Phase 2 引入 sdk-store 后升级为有状态的 QuantalithosClient。

> Phase 1 的 WASM 绑定实现见详细设计 §四。

**Vue 3 中使用（TS 薄封装）：**

```typescript
// quantalithos-chat/src/sdk.ts — TS 薄封装
import init, { QuantalithosClient } from '@quantalithos/sdk-wasm'

let client: QuantalithosClient

export async function initSDK(platformUrl: string, token: string) {
  await init()  // 初始化 WASM
  client = new QuantalithosClient(platformUrl, token)
  await client.connect()
}

export async function loadProject(projectId: string) {
  return JSON.parse(await client.load_project(projectId))
}

export async function getWorkitemCard(id: string): Promise<CardView> {
  return JSON.parse(await client.get_workitem_card(id))
}

export async function respondGate(gateId: string, action: string) {
  await client.respond_gate(gateId, action)
}
```

<!-- quantalithos-chat/src/components/WorkitemCard.vue -->
<template>

## 四、技术选型（决策四元组）

| crate | 依赖 | 说明 |
|-------|------|------|
| sdk-models | serde, chrono | 纯数据结构，零网络依赖 |
| sdk-api | sdk-models, reqwest | HTTP 客户端 |
| sdk-ws | sdk-models, tokio-tungstenite | WebSocket |
| sdk-store | sdk-models, sdk-api, sdk-ws | 状态管理 |
| sdk-wasm | sdk-store, wasm-bindgen, js-sys | WASM 绑定 |

### 4.1 SDK 架构选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | Rust 核心 + WASM/UniFFI 多平台绑定 |
| 备选 | ① TypeScript 原生 SDK（web 优先）　② Flutter + Dart SDK　③ 各端独立实现 |
| 理由 | 一套核心代码覆盖 web（WASM）、desktop（Tauri 直接调用）、mobile（UniFFI），避免多端重复实现；TypeScript SDK 只能覆盖 web，desktop/mobile 需要额外实现；Flutter SDK 绑定 Dart 生态，与现有 Vue 3 前端不兼容 |
| 演进路径 | 如果 WASM 包体积成为瓶颈（>1MB gzip），可将 sdk-models 用 tsify 自动生成 TS 类型，sdk-api 用 TS 重写（仅 web 端），Tauri/mobile 端继续用 Rust |

### 4.2 WASM 绑定方案选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | wasm-bindgen + js-sys + web-sys |
| 备选 | ① wasm-pack + wasm-opt　② Emscripten　③ AssemblyScript |
| 理由 | wasm-bindgen 是 Rust→WASM 的标准工具链，与 Cargo 生态无缝集成；Emscripten 面向 C/C++；AssemblyScript 是独立语言，无法复用 Rust 代码 |
| 演进路径 | Phase 2 引入 wasm-opt 优化包体积；Phase 3 评估 component model（WASI Preview 2）实现更细粒度的模块加载 |

### 4.3 HTTP 客户端选型

| 维度 | 当前选择 |
|------|---------|
| 方案 | reqwest（WASM 模式下自动切换为 fetch API） |
| 备选 | ① surf　② ureq（同步）　③ 手写 fetch 封装 |
| 理由 | reqwest 同时支持 native 和 WASM target，一套代码两端运行；surf 生态较小；ureq 不支持异步和 WASM |
| 演进路径 | reqwest 长期使用，无需迁移 |

## 八、约束条件

### 8.1 技术约束

| 约束 | 说明 |
|------|------|
| 语言 | Rust（Cargo workspace），与 platform/gate/sandbox 统一技术栈 |
| WASM 目标 | wasm32-unknown-unknown，通过 wasm-bindgen 桥接 JS |
| 浏览器兼容 | 支持 Chrome 90+ / Firefox 90+ / Safari 15+（WASM + BigInt 支持） |
| 无运行时依赖 | sdk-models 零外部依赖；sdk-api 仅依赖 reqwest + serde |
| 不含业务逻辑 | SDK 只做数据传输和状态缓存，不包含流程编排、Agent 执行等业务逻辑 |
| 对齐 core schemas | sdk-models 的数据结构必须与 core 定义的 JSON Schema 一致 |

### 8.2 容量规划

| 指标 | Phase 1 目标 | Phase 2 目标 |
|------|-------------|-------------|
| WASM 包体积（gzip） | < 500KB | < 800KB（含 ws + store） |
| sdk-api 请求 P95 延迟（不含网络） | < 5ms（序列化/反序列化开销） | 同左 |
| sdk-store 内存占用（浏览器） | — | < 20MB（100 个工单 + 1000 条消息） |
| WebSocket 重连间隔 | — | 指数退避 1s→2s→4s→...→30s（上限） |
| 并发 API 请求数 | 不限制 | 同一 endpoint 最多 3 并发（防抖） |

### 8.3 合规约束

- JWT token 存储在内存中（sdk-store），不写入 localStorage（防 XSS 窃取）
- WASM 模块不访问 DOM（通过 js-sys 回调通知 JS 层）
- 不在 SDK 层记录用户敏感数据（密码、token 值不出现在日志/错误信息中）

## 九、横切关注点

### 9.1 安全

| 关注点 | 方案 |
|--------|------|
| Token 存储 | 内存中持有（sdk-store），不写入 localStorage/sessionStorage；页面刷新后需重新登录或从 Tauri secure store 恢复 |
| XSS 防护 | SDK 不操作 DOM，不拼接 HTML；所有数据通过 JSON 序列化传递给 JS 层 |
| 请求伪造 | 所有 API 请求携带 Authorization: Bearer JWT，由 gate 校验 |
| WASM 沙箱 | WASM 模块运行在浏览器沙箱中，无文件系统/网络直接访问权限，通过 web-sys 调用浏览器 API |
| 错误信息泄露 | SDK 错误类型只暴露错误码和用户友好消息，不暴露内部堆栈或服务端详情 |

### 9.2 性能

**端到端延迟预算表（SDK API 调用，web 端）：**

| 环节 | 预估延迟 | 依据 |
|------|---------|------|
| JS → WASM 调用开销 | < 0.1ms | wasm-bindgen 零拷贝桥接 |
| Rust 序列化请求体 | < 1ms | serde_json，典型 payload < 10KB |
| fetch API 发送（不含网络） | < 0.5ms | 浏览器原生 |
| 网络往返（本地开发） | 5–20ms | localhost |
| Rust 反序列化响应体 | < 1ms | serde_json |
| WASM → JS 返回 | < 0.1ms | wasm-bindgen |
| **SDK 总开销（不含网络）** | **< 3ms** | |

**WASM 包体积预算：**

| 组件 | 预估体积（gzip） | 说明 |
|------|-----------------|------|
| sdk-models | ~50KB | 纯数据结构 + serde |
| sdk-api | ~100KB | reqwest WASM target + 路由定义 |
| sdk-ws | ~80KB | tokio-tungstenite WASM |
| sdk-store | ~50KB | 纯 Rust 逻辑 |
| wasm-bindgen 运行时 | ~30KB | 桥接层 |
| **Phase 1 总计** | **~200KB** | 仅 models + api + wasm |
| **Phase 2 总计** | **~400KB** | 含 ws + store |

### 9.3 可用性

| 关注点 | 方案 |
|--------|------|
| 网络断开 | sdk-api 请求失败返回 NetworkError，由 JS 层决定重试或提示用户 |
| WebSocket 断连 | sdk-ws 自动重连（指数退避 1s→30s），重连后重新订阅所有 topic |
| API 超时 | 默认 30s 超时，可通过 PlatformClient 配置覆盖 |
| WASM 加载失败 | JS 层 init() 返回错误，前端显示降级页面 |

### 9.4 可观测性

| 维度 | 方案 |
|------|------|
| 日志 | Phase 1：console.log/warn/error（通过 web-sys）；Phase 2：结构化日志 + 可配置日志级别 |
| 错误上报 | SDK 错误通过回调通知 JS 层，由前端决定是否上报（Sentry 等） |
| 性能指标 | Phase 2：API 调用耗时、WebSocket 重连次数、消息延迟，通过回调暴露给前端 |

### 9.5 成本

| 关注点 | 方案 |
|--------|------|
| 包体积 | Phase 1 目标 < 500KB gzip；Phase 2 引入 wasm-opt -Oz 优化 |
| 内存占用 | sdk-store 使用 Rust 内存管理，无 GC 开销；大列表分页加载，不全量缓存 |
| 维护成本 | 一套 Rust 代码覆盖 web/desktop/mobile，避免多端重复实现 |

## 十、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | WASM 包体积膨胀 | 首屏加载慢，用户体验差 | 中 | Phase 1 严格控制依赖（reqwest 用 WASM feature flag 裁剪）；Phase 2 引入 wasm-opt + tree-shaking；兜底方案：sdk-api 用 TS 重写（仅 web 端） |
| 2 | 浏览器 WASM 兼容性 | 部分旧浏览器无法使用 | 低 | 目标浏览器 Chrome 90+ / Firefox 90+ / Safari 15+，覆盖 >95% 用户；不支持的浏览器显示升级提示 |
| 3 | Rust↔JS 类型转换错误 | 运行时 panic 或数据丢失 | 中 | sdk-wasm 层统一 try-catch，Rust panic 转为 JS Error；所有跨边界类型用 serde_json 序列化（不依赖 wasm-bindgen 自动转换复杂类型） |
| 4 | reqwest WASM target 功能缺失 | 部分 HTTP 功能不可用（如 cookie、代理） | 低 | SDK 不需要 cookie（JWT 在 header）和代理；如遇功能缺失，可降级为手写 fetch 封装 |
| 5 | UniFFI 绑定维护成本（Phase 3） | 每次 SDK 接口变更需同步更新 Swift/Kotlin 绑定 | 中 | UniFFI 从 .udl 文件自动生成绑定代码，接口变更只需更新 .udl；Phase 3 引入 CI 自动化 |
| 6 | sdk-models 与 core schemas 不一致 | 序列化/反序列化失败 | 中 | Phase 2 引入 JSON Schema 校验（CI 中对比 sdk-models 和 core schemas）；Phase 1 人工对齐 |

### 常见异常场景

| 场景 | 处理方式 |
|------|---------|
| API 返回 401 | sdk-api 抛出 AuthError，JS 层跳转登录页 |
| API 返回 5xx | sdk-api 抛出 ServerError，JS 层显示错误提示 |
| 网络不可达 | sdk-api 抛出 NetworkError，JS 层显示离线提示 |
| WebSocket 断连 | sdk-ws 自动重连，重连期间 JS 层显示连接中状态 |
| WASM 初始化失败 | init() 返回错误，前端显示降级页面（纯 HTML 提示） |

### 边缘异常场景

| 场景 | 处理方式 |
|------|---------|
| 响应体 JSON 解析失败 | sdk-api 返回 ParseError（含原始响应片段），不 panic |
| WebSocket 消息格式异常 | sdk-ws 记录 warn 日志，丢弃该消息，不断开连接 |
| 并发调用同一 API | Phase 2 sdk-store 层去重（相同请求 3s 内只发一次） |
| 浏览器标签页切到后台 | WebSocket 可能被浏览器节流；恢复前台时发送 ping 检测连接状态 |

## 十一、上线策略

### 11.1 灰度方案

| 阶段 | 范围 | 观察时间 | 推进条件 |
|------|------|---------|---------|
| 内部测试 | 开发团队使用 | 3 天 | API 调用成功率 > 99%，WASM 加载无报错 |
| npm canary | 发布 @quantalithos/sdk-wasm@canary | 1 周 | 无 P0 bug |
| npm latest | 发布 @quantalithos/sdk-wasm@latest | 持续 | — |

### 11.2 回滚策略

| 触发条件 | 回滚步骤 |
|---------|---------|
| WASM 加载失败率 > 1% | npm unpublish canary，前端锁定上一版本 |
| API 调用成功率 < 95% | 排查是 SDK 问题还是后端问题；SDK 问题则回退版本 |
| 包体积超过 1MB gzip | 阻止发布，排查新增依赖 |

> 回滚安全性：SDK 是客户端库，通过 npm 版本管理；前端 package.json 锁定版本号即可回退。

### 11.3 发布监控指标

| 指标 | 告警阈值 |
|------|---------|
| WASM init() 成功率 | < 99% |
| API 调用 P95 延迟（含网络） | > 2s |
| WebSocket 重连频率 | > 5 次/分钟（单用户） |
| npm 包体积（gzip） | > Phase 目标的 120% |

| 文档 | 阅读目的 |

### 1.2 编码约束

- 语言：Rust，代码全英文
- 框架：clap 4 + reqwest 0.12 + tokio 1.0 + serde 1.0 + serde_yaml 0.9
- 不直接访问 platform 数据库（通过 HTTP API）
- 所有 HTTP 请求通过 client/ 模块封装（便于 mock 测试）
- 不使用 unwrap()/expect()（除 main 入口的不可恢复错误）
- Commit scope：cli | manifest | client | sync-engine | workspace | common

### 1.3 提交规范

遵循 `docs/design/实施计划书写规范.md` §前置条件 3 的 commit 格式。

## 二、技术风险评估

**需要 Spike：reqwest + serde_yaml 序列化往返**

| 风险 | 验证方式 | 通过标准 |
|------|---------|---------|
| platform API JSON 响应能否正确反序列化为 Rust struct | 写最简 client 调用 platform /health 和 /api/projects | 编译通过 + 运行时反序列化正确 |
| serde_yaml 序列化/反序列化往返一致性 | Rust struct → YAML 文件 → 读回 → 比较 | 往返数据一致，中文字段不乱码 |
| fs2 文件锁跨平台行为 | Linux + macOS 上测试 flock 排他锁 | 两个进程同时获取锁，一个成功一个等待 |

Spike 代码位置：`spike/sync_reqwest_test/`（不合并主干）

## 五、回退规则

| 阶段 | 回退触发条件 | 回退目标 |
|------|------------|---------|
| 阶段 0 | reqwest 异步模型与 clap 集成有兼容问题 | 概要设计，评估换 ureq（同步 HTTP）简化架构 |
| 阶段 2 | platform API 响应格式与预期不一致 | 详细设计，与 platform 团队对齐 API 契约后重新实现 client |
| 阶段 2 | file_mapper 的 YAML/JSON 序列化丢失字段 | 详细设计 §二，检查 serde 属性标注（#[serde(flatten)] 等） |
| 阶段 3 | fs2 文件锁在某些文件系统（NFS）上不可靠 | 详细设计 §六，改用 PID 文件 + advisory lock 方案 |
| 阶段 4 | 冲突检测基于时间戳不够精确（时钟偏移） | 概要设计 §五，Phase 3 引入内容 hash 比较替代时间戳 |

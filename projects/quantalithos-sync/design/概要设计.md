# quantalithos-sync 概要设计

> 工作区同步工具 — Rust CLI，项目工作区的初始化、恢复、双向同步

---

## 一、项目定位

### 1.1 核心职责

quantalithos-sync 是一个 Rust 实现的 CLI 工具，负责将 quantalithos-platform 云端数据同步到本地项目工作区，以及将本地变更推送回云端。

```
云端（quantalithos-platform）          本地（项目工作区）
┌─────────────────────────┐           ┌─────────────────────────┐
│ project API              │           │ agents/                  │
│ workitem API             │  ←sync→  │ docs/                    │
│ artifact API             │           │ tasks/                   │
│ agent-config API         │           │ snapshots/               │
│ snapshot API             │           │ workspace/ (Git)         │
└─────────────────────────┘           │ manifest.yaml            │
                                      └─────────────────────────┘
```

**不做的事：**
- 不管代码仓库的同步 — workspace/ 由 Git 直接管理
- 不管 Agent 运行时 — 那是 runtime 的事
- 不管流程编排 — 那是 flow 的事
- 不做持续监听 — 是命令行工具，调用一次执行一次

### 1.2 在整体架构中的位置

```
quantalithos-flow (daemon)
      │
      │ 项目启动时调用
      │ sync restore --project blog
      │
      ▼
╔═══════════════════════╗          quantalithos-platform
║ quantalithos-sync     ║ -------> (平台数据服务 API)
║ (Rust CLI)            ║ <-------
╚═══════════╤═══════════╝
            │
            │ 读写本地文件系统
            ▼
┌───────────────────────────────────────────┐
│ project_files/{project}/                  │
│ ├── agents/          ← agent-config API   │
│ ├── docs/            ← artifact API       │
│ ├── tasks/           ← workitem API       │
│ ├── snapshots/       ← snapshot API       │
│ ├── workspace/       ← Git clone/pull     │
│ └── manifest.yaml    ← project API        │
└───────────────────────────────────────────┘
```

### 1.3 使用场景

```
场景 1：新项目初始化
  用户创建项目 → Assistant 完成启动 → daemon 调用 sync init
  → 创建本地目录结构 + manifest.yaml

场景 2：项目恢复（用户隔天回来）
  用户回来 → daemon 调用 sync restore --project blog
  → 从 platform 拉取全部数据 → 本地工作区就绪 → 继续工作

场景 3：开发过程中增量同步
  Agent 产出新产物 → runtime 写入 platform API
  → daemon 调用 sync pull → 本地 docs/ 更新

场景 4：本地修改推送
  用户手动编辑了 agents/role_store/backend_dev.yaml
  → sync push → 推送到 platform agent-config API

场景 5：查看同步状态
  sync status --project blog
  → 显示本地和云端的差异
```

## 二、CLI 命令设计

```
quantalithos-sync <command> [options]

命令：
  init      初始化新项目工作区
  restore   从云端恢复完整工作区
  pull      从云端拉取变更到本地
  push      将本地变更推送到云端
  status    查看本地与云端的差异
  clean     清理本地工作区

全局选项：
  --project <id>        项目 ID（必填）
  --platform-url <url>  platform API 地址（默认从环境变量）
  --token <token>       认证 token（默认从环境变量）
  --verbose             详细输出
  --dry-run             只显示将要执行的操作，不实际执行
```

### 2.1 init — 初始化

```bash
quantalithos-sync init --project blog --pipeline standard

执行过程：
  1. 调用 POST /api/projects 创建项目（如果云端不存在）
  2. 创建本地目录结构：
     project_files/blog/
     ├── agents/
     │   ├── shared_rules/
     │   ├── role_store/
     │   └── manifest.yaml
     ├── docs/
     ├── tasks/
     ├── snapshots/
     └── workspace/
  3. 生成 manifest.yaml
  4. 从 platform 拉取系统级 agent-config（角色模板、共享规则、流程模板）
  5. git init workspace/（如果需要）

输出：
  ✅ 项目 blog 初始化完成
  📁 project_files/blog/
  📄 manifest.yaml 已生成
  🔧 系统级配置已拉取（5 个角色、4 条共享规则、8 个流程模板）
```

### 2.2 restore — 恢复

```bash
quantalithos-sync restore --project blog

执行过程：
  1. 读取 manifest.yaml 获取项目配置
  2. 并行拉取各模块数据：
     ├── agents/     ← GET /api/projects/blog/agent-config/roles
     │                  GET /api/agent-config/shared-rules
     ├── docs/       ← GET /api/projects/blog/artifacts?type=document
     ├── tasks/      ← GET /api/projects/blog/workitems
     ├── snapshots/  ← GET /api/projects/blog/snapshots/workflow
     │                  GET /api/projects/blog/snapshots/agents
     └── workspace/  ← git clone / git pull

  3. 写入本地文件
  4. 更新 manifest.yaml 的 last_sync 时间戳

输出：
  ✅ 项目 blog 恢复完成
  📥 agents/: 3 个角色定义, 4 条共享规则
  📥 docs/: 5 个文档
  📥 tasks/: 8 个工单
  📥 snapshots/: 1 个流程快照, 3 个 Agent 快照
  📥 workspace/: git pull (3 commits behind)
  ⏱ 耗时 2.3s
```

### 2.3 pull — 增量拉取

```bash
quantalithos-sync pull --project blog
quantalithos-sync pull --project blog --module agents    # 只拉取 agents
quantalithos-sync pull --project blog --module tasks     # 只拉取 tasks

执行过程：
  1. 读取 manifest.yaml 的 last_sync 时间戳
  2. 调用 platform API 查询 since=last_sync 的变更
  3. 下载变更的文件，覆盖本地
  4. 如果本地也有修改 → 冲突检测 → 提示用户
  5. 更新 last_sync

输出：
  📥 pull 完成（since 2026-04-20T14:00:00Z）
  📄 tasks/TASK-003.md 更新（status: in_review → completed）
  📄 docs/prd/blog-prd-v1.md 无变化
  📄 snapshots/workflow/current.yaml 更新
  ⏱ 耗时 0.8s
```

### 2.4 push — 推送

```bash
quantalithos-sync push --project blog
quantalithos-sync push --project blog --module agents    # 只推送 agents

执行过程：
  1. 扫描本地文件的修改时间 vs manifest.yaml 的 last_sync
  2. 找出本地变更的文件
  3. 调用 platform API 推送变更：
     ├── agents/ 变更 → PUT /api/projects/blog/agent-config/roles/{id}
     ├── docs/ 变更   → PUT /api/artifacts/{id}
     └── tasks/ 变更  → PUT /api/workitems/{id}
  4. 更新 last_sync

输出：
  📤 push 完成
  📄 agents/role_store/backend_dev.yaml → 已推送
  ⏱ 耗时 0.5s
```

### 2.5 status — 状态

```bash
quantalithos-sync status --project blog

输出：
  📊 项目 blog 同步状态
  
  上次同步：2026-04-20T14:00:00Z（2 小时前）
  
  本地变更（未推送）：
    M agents/role_store/backend_dev.yaml
  
  云端变更（未拉取）：
    M tasks/TASK-003.md (status: completed)
    A tasks/TASK-006.md (新工单)
    M snapshots/workflow/current.yaml
  
  workspace/ (Git):
    本地：main (3 commits ahead)
    远程：main (up to date)
```

## 三、manifest.yaml

manifest 是 sync 的驱动文件，描述项目的同步配置：

```yaml
# project_files/blog/manifest.yaml

project_id: blog
project_name: "个人博客系统"
platform_url: "http://localhost:8080"

# 同步配置
sync:
  last_sync: "2026-04-20T14:00:00Z"
  auto_pull_on_restore: true        # restore 时自动 pull 全部
  
  # 各模块的同步策略
  modules:
    agents:
      enabled: true
      direction: bidirectional       # 双向同步
      source: agent-config           # platform API 模块
    docs:
      enabled: true
      direction: bidirectional
      source: artifact
      filter:
        types: [document, prd_document, tech_design]
    tasks:
      enabled: true
      direction: pull_only           # 只拉取，不推送（主数据在 platform）
      source: workitem
    snapshots:
      enabled: true
      direction: pull_only
      source: snapshot
    workspace:
      enabled: true
      direction: git                 # Git 管理，不走 platform API
      git_remote: "git@github.com:user/blog.git"
      default_branch: main

# 项目流程配置
pipeline_process_id: standard_pipeline

# 团队配置引用
team_config_ref: "project/blog/team"
```

## 五、同步引擎设计

### 5.1 数据流向

```
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  platform API                sync engine              本地文件   │
│                                                                 │
│  GET /api/projects/          ┌──────────┐                       │
│    blog/agent-config/  ───>  │          │  ───>  agents/*.yaml  │
│    roles                     │          │                       │
│                              │  file    │                       │
│  GET /api/projects/          │  mapper  │                       │
│    blog/workitems      ───>  │          │  ───>  tasks/*.md     │
│                              │          │                       │
│  GET /api/projects/          │          │                       │
│    blog/artifacts      ───>  │          │  ───>  docs/*         │
│                              └──────────┘                       │
│                                                                 │
│  反向（push）：                                                  │
│                                                                 │
│  agents/*.yaml         ───>  file_mapper  ───>  PUT /api/...   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 5.2 file_mapper — API 数据与本地文件的映射

```
platform API 数据                    本地文件
─────────────────────────────────────────────────────

角色定义 JSON                        agents/role_store/{role_id}.yaml
  GET /api/agent-config/roles/{id}   → YAML 序列化写入

共享规则 JSON                        agents/shared_rules/{rule_id}.yaml
  GET /api/agent-config/             → YAML 序列化写入
    shared-rules/{id}

工单 JSON                            tasks/{id}.md
  GET /api/workitems/{id}            → Markdown + YAML frontmatter

产物（结构化）JSON                   docs/{type}/{name}.json
  GET /api/artifacts/{id}/content    → JSON 写入

产物（文件）二进制                   docs/{type}/{filename}
  GET /api/artifacts/{id}/content    → 二进制写入

流程快照 JSON                        snapshots/workflow/current.yaml
  GET /api/projects/{pid}/           → YAML 序列化写入
    snapshots/workflow

Agent 快照 JSON                      snapshots/agents/{agent_id}.yaml
  GET /api/projects/{pid}/           → YAML 序列化写入
    snapshots/agents/{agent_id}
```

### 5.3 冲突检测

```
pull 时发现本地和云端都有修改：

  本地 agents/role_store/backend_dev.yaml
    modified_at: 2026-04-20T15:00:00Z（本地修改）

  云端 GET /api/agent-config/roles/backend_dev
    updated_at: 2026-04-20T15:30:00Z（云端也修改了）

  → 冲突！

处理策略：
  1. 默认：提示用户选择
     ⚠️ 冲突：agents/role_store/backend_dev.yaml
     本地修改时间：15:00  云端修改时间：15:30
     [L] 保留本地  [R] 使用云端  [M] 手动合并  [S] 跳过

  2. --force-local：强制使用本地版本
  3. --force-remote：强制使用云端版本
  4. tasks/ 模块：永远以云端为准（pull_only）
```

## 七、与 daemon 的集成

```
daemon 启动流程中调用 sync：

daemon 进程启动
    │
    ▼
读取项目配置
    │
    ▼
调用 sync restore --project blog
    │
    ├── 成功 → 本地工作区就绪
    │          │
    │          ▼
    │       读取 snapshots/workflow/current.yaml
    │       恢复流程状态
    │       继续执行
    │
    └── 失败 → 报错，daemon 不启动
               通知用户检查网络/配置

daemon 运行过程中：
    Agent 产出产物 → runtime 写入 platform API
                   → daemon 定期调用 sync pull 更新本地
                   （或由 platform 事件触发）
```

## 八、Phase 分期

### Phase 1

| 功能 | 说明 |
|------|------|
| init | 创建目录结构 + manifest.yaml |
| restore | 全量拉取（不做增量） |
| status | 显示本地文件列表 |
| pull | 全量覆盖（不做 diff） |
| workspace | git clone / git pull |

Phase 1 不做增量同步和冲突检测，每次 restore/pull 都是全量覆盖。

### Phase 2

| 功能 | 说明 |
|------|------|
| 增量 pull | 基于 last_sync 时间戳，只拉取变更 |
| push | 本地变更推送到云端 |
| 冲突检测 | 本地和云端同时修改时提示 |
| status | 对比本地和云端的差异 |
| clean | 清理本地工作区 |

### Phase 3

| 功能 | 说明 |
|------|------|
| 文件监听 | 监听本地文件变更，自动 push |
| WebSocket | 监听 platform 事件，自动 pull |
| 选择性同步 | 只同步指定模块/文件 |
| 离线模式 | 网络断开时缓存操作，恢复后批量同步 |

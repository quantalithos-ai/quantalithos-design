## 二、Manifest 格式

```yaml
# .quantalithos.yaml — 项目工作区 manifest

project_id: "blog"
platform_url: "http://localhost:8001"

sync:
  # 同步哪些内容到本地
  roles: true                    # 角色定义 → .quantalithos/roles/
  shared_rules: true             # 共享规则 → .quantalithos/rules/
  artifacts: true                # 产物 → .quantalithos/artifacts/
  workitems: true                # 工单 → .quantalithos/tasks/

  roles: ".quantalithos/roles"
  rules: ".quantalithos/rules"
  artifacts: ".quantalithos/artifacts"
  tasks: ".quantalithos/tasks"
```

## 三、子命令实现

### 3.1 sync init

```rust
// commands/init.rs
//
// 初始化命令 — 在当前目录创建 .quantalithos/ 工作区并首次同步。
//
// 使用场景：
//   用户在本地 IDE 中想查看项目的角色定义、工单、产物等信息。
//   运行 `sync init blog http://localhost:8001` 后，
//   本地会出现 .quantalithos/ 目录，包含从 platform 拉取的所有配置文件。
//
// 与 git clone 的区别：
//   git clone 拉取代码仓库（Agent 在 sandbox 中写的代码）
//   sync init 拉取项目配置（角色定义/共享规则/工单/产物元数据）
//   两者互补，不冲突。

pub async fn init(project_id: &str, platform_url: &str) -> Result<()> {
    // 1. 创建 .quantalithos/ 目录
    fs::create_dir_all(".quantalithos/roles")?;
    fs::create_dir_all(".quantalithos/rules")?;
    fs::create_dir_all(".quantalithos/artifacts")?;
    fs::create_dir_all(".quantalithos/tasks")?;

    // 2. 生成 manifest
    let manifest = Manifest {
        project_id: project_id.to_string(),
        platform_url: platform_url.to_string(),
        ..Default::default()
    };
    fs::write(".quantalithos.yaml", serde_yaml::to_string(&manifest)?)?;

    // 3. 首次 restore
    restore(&manifest).await?;

    println!("✅ 项目 {} 初始化完成", project_id);
    Ok(())
}
```

### 3.2 sync restore

```rust
// commands/restore.rs
//
// 恢复命令 — 从 platform 拉取最新数据覆盖本地文件。
//
// 设计意图：
//   将 platform 上的项目配置同步到本地 .quantalithos/ 目录。
//   用户可以用本地 IDE 查看/编辑角色定义、共享规则等 YAML 文件。
//
// 并行拉取（tokio::join!）：
//   四种资源独立拉取，互不阻塞。某一种失败不影响其他。
//   这样即使 platform 的某个 API 暂时不可用，其他资源仍能同步。
//
// structured_data 过滤：
//   只同步 storage_type="structured" 的产物（JSON 数据）。
//   文件类产物（代码/图片）通过 git clone 获取，不走 sync。

pub async fn restore(manifest: &Manifest) -> Result<()> {
    let client = PlatformClient::new(&manifest.platform_url, &get_token()?);

    // 并行拉取所有资源（独立错误处理，部分失败不影响其他）
    let (roles_result, rules_result, artifacts_result, workitems_result) = tokio::join!(
        client.agent_config().list_project_roles(&manifest.project_id),
        client.agent_config().list_project_rules(&manifest.project_id),
        client.artifacts().list(&manifest.project_id),
        client.workitems().list(&manifest.project_id),
    );

    let mut errors: Vec<String> = vec![];

    // 写入本地文件（每种资源独立处理，一个失败不影响其他）
    if manifest.sync.roles {
        match roles_result {
            Ok(roles) => {
                for role in roles {
                    let path = format!("{}/{}.yaml", manifest.local_dirs.roles, role.role_id);
                    fs::write(&path, serde_yaml::to_string(&role)?)?;
                }
            },
            Err(e) => errors.push(format!("roles: {}", e)),
        }
    }

    if manifest.sync.artifacts {
        match artifacts_result {
            Ok(artifacts) => {
                for artifact in artifacts {
                    if artifact.storage_type == "structured" {
                        let path = format!("{}/{}.json", manifest.local_dirs.artifacts, artifact.id);
                        fs::write(&path, serde_json::to_string_pretty(&artifact.structured_data)?)?;
                    }
                }
            },
            Err(e) => errors.push(format!("artifacts: {}", e)),
        }
    }

    if manifest.sync.workitems {
        match workitems_result {
            Ok(items) => {
                for item in items {
                    let path = format!("{}/{}.yaml", manifest.local_dirs.tasks, item.id);
                    fs::write(&path, serde_yaml::to_string(&item)?)?;
                }
            },
            Err(e) => errors.push(format!("workitems: {}", e)),
        }
    }

    if errors.is_empty() {
        println!("✅ restore 完成");
    } else {
        println!("⚠️ restore 部分完成，以下资源拉取失败：");
        for e in &errors {
            println!("  - {}", e);
        }
    }
    Ok(())
}
```

### 3.3 sync status

```rust
// commands/status.rs
//
// 状态命令 — 比较本地 .quantalithos/ 和 platform 远程的差异。
//
// 设计意图：
//   类似 git status — 告诉用户"本地和远程有什么不同"。
//   用户据此决定是 restore（拉取远程覆盖本地）还是 push（推送本地到远程）。
//
// compute_diff 的比较算法：
//   按 ID 匹配（workitem_id / role_id / rule_id），比较 updated_at 时间戳。
//   远程有本地没有 → Added（远程新增）
//   两者都有但 updated_at 不同 → Modified（已修改）
//   本地有远程没有 → Deleted（远程已删除）

pub async fn status(manifest: &Manifest) -> Result<()> {
    let client = PlatformClient::new(&manifest.platform_url, &get_token()?);

    // 比较本地 vs 远程
    let remote_items = client.workitems().list(&manifest.project_id).await?;
    let local_items = load_local_workitems(&manifest.local_dirs.tasks)?;

    let diff = compute_diff(&local_items, &remote_items);

    if diff.is_empty() {
        println!("✅ 本地和远程一致");
    } else {
        for d in &diff {
            match d {
                DiffEntry::Added(id) => println!("  + {} (远程新增)", id),
                DiffEntry::Modified(id) => println!("  ~ {} (已修改)", id),
                DiffEntry::Deleted(id) => println!("  - {} (远程已删除)", id),
            }
        }
    }
    Ok(())
}
```

## 六、并发与一致性

### 6.1 并发模型

quantalithos-sync 是 CLI 工具，单次调用执行一次同步操作。并发场景来自：
- 同一项目多个 sync 进程同时运行（用户手动 + daemon 自动）
- restore/pull 内部多模块并行拉取（tokio::join!）

```
场景 1：两个 sync 进程同时 restore 同一项目

  进程 A: sync restore --project blog
  进程 B: sync restore --project blog（daemon 触发）

  风险：两个进程同时写入 .quantalithos/ 目录，文件内容交错损坏

  控制策略：文件锁（flock）
  ┌──────────────────────────────────────────────┐
  │  进程 A                                       │
  │  1. 获取 .quantalithos/.lock 排他锁           │
  │  2. 执行 restore                              │
  │  3. 释放锁                                    │
  │                                               │
  │  进程 B                                       │
  │  1. 尝试获取 .quantalithos/.lock              │
  │  2. 锁被占用 → 等待（超时 60s）               │
  │  3. 获取锁 → 执行 restore                     │
  │  4. 释放锁                                    │
  └──────────────────────────────────────────────┘
```

### 6.2 文件锁实现

```rust
// sync_engine/lock.rs
//
// 使用 flock 排他锁防止多个 sync 进程同时操作同一工作区。
// 锁文件位于 .quantalithos/.lock，进程退出时自动释放。

use std::fs::{File, OpenOptions};
use fs2::FileExt;  // flock 跨平台封装

pub struct WorkspaceLock {
    file: File,
}

impl WorkspaceLock {
    /// 获取工作区排他锁，超时 60 秒
    pub fn acquire(workspace_dir: &Path) -> Result<Self> {
        let lock_path = workspace_dir.join(".lock");
        let file = OpenOptions::new()
            .create(true)
            .write(true)
            .open(&lock_path)?;

        // 尝试获取排他锁（非阻塞）
        match file.try_lock_exclusive() {
            Ok(()) => Ok(Self { file }),
            Err(_) => {
                eprintln!("⏳ 另一个 sync 进程正在运行，等待中...");
                // 阻塞等待（超时由调用方控制）
                file.lock_exclusive()?;
                Ok(Self { file })
            }
        }
    }
}

impl Drop for WorkspaceLock {
    fn drop(&mut self) {
        let _ = self.file.unlock();
    }
}
```

### 6.3 内部并行拉取的一致性

```
restore 内部并行拉取各模块：

  tokio::join!(
      pull_roles(),        ← 独立 HTTP 请求
      pull_rules(),        ← 独立 HTTP 请求
      pull_artifacts(),    ← 独立 HTTP 请求
      pull_workitems(),    ← 独立 HTTP 请求
  )

  一致性问题：
    四个请求在不同时刻到达 platform，可能拿到不一致的快照。
    例如：roles 拿到 T1 时刻的数据，workitems 拿到 T2 时刻的数据。

  Phase 1 接受方案：
    中小项目数据变更频率低，时间窗口内不一致可接受。
    manifest.yaml 记录 last_sync 为最后一个请求完成的时间。

  Phase 2 改进方案：
    platform 提供 snapshot API — 一次请求返回某时刻的全量快照。
    sync 调用 GET /api/projects/blog/snapshot?at=<timestamp>
```

## 七、性能设计

### 7.1 Phase 1 性能目标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| restore 耗时（中小项目） | < 5s | 5–20 个工单 + 10–30 个产物 |
| pull 耗时（增量） | < 2s | 通常只有几个文件变更 |
| push 耗时 | < 2s | 通常只推送 1–3 个文件 |
| 内存占用 | < 50MB | 全量数据在内存中序列化/反序列化 |
| 二进制大小 | < 20MB | Rust release 编译 + strip |

### 7.2 大文件处理

```
文件类型与处理策略：

  结构化数据（YAML/JSON）：
    大小：通常 < 100KB
    处理：全量加载到内存，serde 序列化/反序列化
    无需特殊处理

  产物文件（文档/报告）：
    大小：通常 < 1MB，偶尔 10MB+
    处理：reqwest 流式下载，直接写入文件，不全量加载到内存

  快照文件：
    大小：可能 > 10MB（包含完整 Agent 上下文）
    处理：默认不同步（manifest.sync.snapshots = false）
    需要时流式下载
```

```rust
// client/download.rs
//
// 大文件流式下载 — 不将整个响应体加载到内存。
// 适用于产物文件和快照文件。

pub async fn download_to_file(
    client: &reqwest::Client,
    url: &str,
    dest: &Path,
) -> Result<u64> {
    let response = client.get(url).send().await?.error_for_status()?;
    let total_size = response.content_length().unwrap_or(0);

    let mut file = tokio::fs::File::create(dest).await?;
    let mut stream = response.bytes_stream();
    let mut downloaded: u64 = 0;

    while let Some(chunk) = stream.try_next().await? {
        file.write_all(&chunk).await?;
        downloaded += chunk.len() as u64;
    }

    Ok(downloaded)
}
```

### 7.3 增量同步设计（Phase 2）

```
增量同步基于 last_sync 时间戳：

  1. 读取 manifest.yaml 的 last_sync
  2. 调用 platform API：
     GET /api/projects/blog/workitems?updated_since=2026-04-20T14:00:00Z
  3. 只下载 updated_since 之后变更的资源
  4. 更新 last_sync 为当前时间

  优化：ETag 缓存
  ┌──────────────────────────────────────────────┐
  │  首次请求：                                    │
  │  GET /api/workitems/TASK-003                  │
  │  → 200 OK, ETag: "abc123"                    │
  │  → 保存 ETag 到 .quantalithos/.etags         │
  │                                               │
  │  后续请求：                                    │
  │  GET /api/workitems/TASK-003                  │
  │  If-None-Match: "abc123"                      │
  │  → 304 Not Modified（无需下载）               │
  │  → 或 200 OK, ETag: "def456"（有变更）       │
  └──────────────────────────────────────────────┘
```

## 九、部署与运维

### 9.1 配置项五要素

| 配置项 | 类型 | 默认值 | 有效范围 | 依赖 | 排查 |
|--------|------|--------|---------|------|------|
| QUANTALITHOS_TOKEN | string | — | 非空字符串 | platform 签发的有效 token | `curl -H "Authorization: Bearer $TOKEN" $URL/health` |
| QUANTALITHOS_PLATFORM_URL | string | http://localhost:8001 | 合法 HTTP(S) URL | platform 服务必须可达 | `curl $URL/health` |
| --project | string | — | 合法 project_id | platform 中已存在的项目 | `curl $URL/api/projects/$ID` |
| --verbose | bool | false | true/false | — | 开启后输出 DEBUG 日志 |
| --dry-run | bool | false | true/false | — | 开启后只显示操作不执行 |
| --timeout | int | 30 | 5–300（秒） | 网络环境 | 慢网络环境适当增大 |

### 9.2 配置优先级

```
配置来源（优先级从高到低）：

  1. 命令行参数        --platform-url http://...
  2. 环境变量          QUANTALITHOS_PLATFORM_URL=http://...
  3. 项目 manifest     .quantalithos.yaml 中的 platform_url
  4. 全局配置          ~/.quantalithos/config.yaml
  5. 内置默认值        http://localhost:8001
```

### 9.3 错误码与排查

| 错误码 | 含义 | 排查步骤 |
|--------|------|---------|
| SYNC_E001 | platform 不可达 | 检查 platform_url 是否正确，platform 服务是否启动 |
| SYNC_E002 | 认证失败（401） | 检查 token 是否过期，重新获取 token |
| SYNC_E003 | 项目不存在（404） | 检查 project_id 是否正确 |
| SYNC_E004 | manifest 解析失败 | 检查 .quantalithos.yaml 格式是否正确 |
| SYNC_E005 | 文件写入失败 | 检查磁盘空间和目录权限 |
| SYNC_E006 | 工作区被锁定 | 等待其他 sync 进程完成，或删除 .quantalithos/.lock |

## 十、幂等设计

### 10.1 restore 幂等性

```
restore 是天然幂等的 — 多次执行结果相同：

  第一次 restore：
    .quantalithos/ 为空
    → 从 platform 拉取全部数据
    → 写入文件
    → 更新 last_sync

  第二次 restore（数据未变）：
    .quantalithos/ 已有数据
    → 从 platform 拉取全部数据
    → 覆盖写入（内容相同，文件不变）
    → 更新 last_sync

  第二次 restore（数据有变）：
    → 从 platform 拉取全部数据
    → 覆盖写入（新内容替换旧内容）
    → 更新 last_sync

  关键：restore 始终以 platform 为准，全量覆盖本地。
  不存在"执行两次结果不同"的情况。
```

### 10.2 push 幂等性（Phase 2）

```
push 的幂等性通过 updated_at 时间戳保证：

  第一次 push：
    本地 backend_dev.yaml 修改时间 > last_sync
    → 推送到 platform（PUT /api/agent-config/roles/backend_dev）
    → platform 返回新的 updated_at
    → 更新本地 last_sync

  第二次 push（未再修改）：
    本地 backend_dev.yaml 修改时间 < last_sync
    → 无变更，跳过推送
    → 输出 "无变更需要推送"

  并发 push 冲突：
    进程 A push backend_dev.yaml → platform 更新 updated_at = T2
    进程 B push backend_dev.yaml → platform 检测到 updated_at 已变
    → 409 Conflict → 提示用户先 pull 再 push
```

### 10.3 init 幂等性

```
init 对已存在的工作区是安全的：

  第一次 init：
    .quantalithos/ 不存在
    → 创建目录结构 + manifest.yaml
    → 执行首次 restore

  第二次 init（工作区已存在）：
    .quantalithos/ 已存在
    → 检测到已初始化
    → 提示 "工作区已存在，使用 sync restore 更新"
    → 不覆盖现有 manifest（防止用户自定义配置丢失）
```

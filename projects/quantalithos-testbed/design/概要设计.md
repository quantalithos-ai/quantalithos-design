# quantalithos-testbed 概要设计

> 跨平台真机测试服务 — AI Agent 驱动的远程设备部署、UI 自动化、结果收集

---

## 一、项目定位

### 1.1 核心职责

quantalithos-testbed 是 AI Agent 的"远程手臂" — 让 Tester Agent 能够在真实设备上部署应用、执行 UI 自动化测试、收集结果。

```
sandbox  → Agent 写代码的地方（Linux Docker 容器）
testbed  → Agent 验证代码的地方（真实设备 / 模拟器）
runner   → 用户体验产品的地方（最终交付）

三者形成生命周期链：sandbox（开发）→ testbed（测试）→ runner（交付）
```

**做的事：**
- 管理远程测试设备（注册/状态监控/排队调度）
- 部署应用到目标设备（.apk / .ipa / .dmg / .exe）
- 执行 UI 自动化测试脚本（基于 Appium）
- 收集测试结果（截图/日志/crash report/性能数据）
- 上报结果到 platform（作为 Artifact 存储）

**不做的事：**
- 不做应用构建（那是 sandbox build 模式的事）
- 不做测试脚本编写（那是 Tester Agent 在 sandbox 中写的）
- 不做测试结果分析（那是 Tester Agent 的 think 过程）
- 不做设备采购/维护（物理设备由运维管理）

### 1.3 与其他子项目的关系

| 子项目 | 关系 |
|--------|------|
| sandbox | sandbox build 产出构建产物 → testbed 部署到设备 |

## 二、核心概念

### 2.1 设备（Device）

| 字段 | 说明 |
|------|------|
| id | 设备标识（如 "iphone-14-lab1"） |
| platform | ios / android / macos / windows / linux |
| model | 设备型号（如 "iPhone 14 Pro"） |
| os_version | 系统版本（如 "iOS 17.2"） |
| connection | 连接方式：usb / adb_wifi / ssh / cloud |
| status | available / busy / offline / maintenance |
| capabilities | 设备能力（camera / gps / nfc 等） |

### 2.2 测试任务（TestJob）

| 字段 | 说明 |
|------|------|
| job_id | 任务唯一标识 |
| device_id | 目标设备 |
| artifact_id | 要部署的应用（platform artifact） |
| test_script | UI 自动化脚本（YAML） |
| status | queued / deploying / running / completed / failed |
| requested_by | 请求者（Agent ID） |

### 2.3 测试脚本（TestScript）

声明式 YAML 格式，Tester Agent 编写：

```yaml
# 示例：测试相机功能
name: "camera_capture_test"
timeout: 60s

steps:
  - action: launch_app
    package: "com.quantalithos.diary"

  - action: tap
    element: { accessibility_id: "new_diary_button" }

  - action: tap
    element: { accessibility_id: "add_cover_button" }

  - action: assert_visible
    element: { accessibility_id: "permission_dialog" }
    screenshot: "step_permission"

  - action: tap
    element: { text: "允许" }

  - action: wait
    duration: 3s

  - action: assert_visible
    element: { accessibility_id: "cover_preview" }
    screenshot: "step_cover_ok"

  - action: check_performance
    metrics: [memory, cpu]
    threshold:
      memory_mb: 200
      cpu_percent: 80
```

### 2.4 测试结果（TestResult）

| 字段 | 说明 |
|------|------|
| job_id | 关联的测试任务 |
| device_id | 执行设备 |
| status | passed / failed / error / timeout |
| steps_total | 总步骤数 |
| steps_passed | 通过步骤数 |
| screenshots | 截图列表（每步一张） |
| device_logs | 设备日志 |
| crash_report | 崩溃报告（如果有） |
| performance | 性能数据（CPU/内存/帧率） |
| duration_ms | 总执行时长 |

## 三、API 设计

### 3.1 设备管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /devices | 列出所有设备（含状态） |
| GET | /devices/:id | 获取设备详情 |
| POST | /devices | 注册新设备 |
| PUT | /devices/:id/status | 更新设备状态 |
| DELETE | /devices/:id | 移除设备 |

### 3.2 测试任务

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /jobs | 创建测试任务（部署 + 执行） |
| GET | /jobs/:id | 获取任务状态和结果 |
| GET | /jobs/:id/logs | 获取实时日志流 |
| POST | /jobs/:id/cancel | 取消任务 |
| GET | /jobs?device_id=&status= | 查询任务列表 |

### 3.3 即时操作（Agent 工具直接调用）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /devices/:id/deploy | 部署应用到设备 |
| POST | /devices/:id/screenshot | 截取当前屏幕 |
| POST | /devices/:id/logs | 获取设备日志 |
| POST | /devices/:id/performance | 获取性能数据 |
| POST | /devices/:id/exec | 执行单条 Appium 命令 |

## 四、技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 语言 | Rust | 与其他后端服务一致 |
| HTTP 框架 | axum | 统一技术栈 |
| UI 自动化 | Appium 2.0 | 跨平台统一 API |
| iOS 驱动 | XCUITest driver | Apple 官方 UI 测试框架 |
| Android 驱动 | UiAutomator2 driver | Google 官方 UI 测试框架 |
| macOS 驱动 | Mac2 driver | Appium macOS 支持 |
| Windows 驱动 | WinAppDriver | Microsoft 官方 |
| 设备连接 | ADB (Android) + libimobiledevice (iOS) + SSH (桌面) | 标准工具链 |
| 模拟器 | Android Emulator + iOS Simulator | 无真机时的替代方案 |

### 4.1 为什么选 Appium

- 跨平台统一 API（一套脚本格式适配所有平台）
- 不需要修改被测应用（黑盒测试）
- 支持 accessibility id 定位（与 Flutter/RN 的无障碍标签对齐）
- 社区成熟，文档完善
- 支持并行测试（多设备同时执行）

## 六、与 runtime 的集成

Tester Agent 通过以下工具调用 testbed：

| 工具名 | 说明 | 参数 |
|--------|------|------|
| device_list | 列出可用设备 | platform (可选过滤) |
| device_deploy | 部署应用到设备 | device_id, artifact_id |
| device_run_test | 执行 UI 自动化测试 | device_id, test_script (YAML) |
| device_screenshot | 截取设备屏幕 | device_id |
| device_logs | 获取设备日志 | device_id, since, filter |
| device_performance | 获取性能数据 | device_id, duration_secs |

这些工具在 runtime 中注册为 ToolDefinition，通过 HTTP 调用 testbed API。

## 七、待细化

- 设备排队策略（多个 Agent 同时请求同一设备时如何调度）

## 八、横切关注点

### 8.1 安全

| 关注点 | 方案 |
|--------|------|
| 认证 | 由 gate 层处理（JWT），testbed 信任 X-User-Id / X-Agent-Id 请求头 |
| 授权 | Phase 3 不做细粒度授权；Phase 4 按项目隔离设备访问 |
| 输入校验 | serde 反序列化 + 自定义 validator（设备 ID 格式、脚本 action 白名单） |
| 脚本安全 | 声明式 YAML 只允许预定义 action，不执行任意代码 |
| 设备隔离 | 每个 Appium session 独占设备，session 结束后清理应用数据 |
| 敏感数据 | 设备连接凭证（SSH key / UDID）不在 API 响应中暴露，日志中脱敏 |

### 8.2 性能

| 关注点 | 方案 |
|--------|------|
| 大文件传输 | APK/IPA 从 platform 下载到本地缓存，相同 artifact_id 不重复下载 |
| Appium session 复用 | 同一设备连续执行多个测试时复用 session，减少启动开销（~5s/次） |
| 并发任务 | Phase 3 单设备串行；Phase 4 多设备并行（max_concurrent_jobs 控制） |
| 截图压缩 | PNG 截图压缩后上传 platform，减少网络传输（~2MB → ~500KB） |

### 8.3 可用性

| 关注点 | 方案 |
|--------|------|
| 设备离线 | 健康检查（30s 间隔），连续 3 次失败标记 offline，恢复后自动标记 available |
| 任务超时 | 整体超时（默认 120s）+ 单步超时（默认 30s），超时自动终止并回收设备 |
| 排队超时 | 排队超过 5 分钟自动失败，防止 Agent 无限等待 |
| 进程重启 | 内存中的任务队列丢失可接受（Phase 3），Agent 可重新提交；Phase 4 持久化队列 |

### 8.4 可观测性

| 维度 | 方案 |
|------|------|
| 日志 | tracing + tracing-subscriber（结构化 JSON），每个测试步骤独立 span |
| 追踪 | X-Request-Id 贯穿 Agent → testbed → Appium，关联设备日志 |
| 指标 | 设备利用率、任务排队时长、测试通过率、Appium session 创建耗时 |
| 告警 | 设备全部 offline 时告警（Phase 4） |

### 8.5 成本

| 关注点 | 方案 |
|--------|------|
| 设备采购 | Phase 3 用模拟器 + 1-2 台真机验证；Phase 4 按需扩展 |
| 云设备农场 | Phase 4 按需调用 AWS Device Farm / Firebase Test Lab，按分钟计费 |
| 存储 | 截图/日志保留 30 天自动清理（retention_days 配置） |

## 九、风险与缓解策略

| # | 风险 | 影响 | 概率 | 缓解策略 |
|---|------|------|------|---------|
| 1 | 设备物理故障（USB 断开/电池耗尽/系统崩溃） | 测试任务失败，设备不可用 | 中 | 健康检查自动标记 offline + 任务自动 fail + Agent 可选择其他设备重试 |
| 2 | Appium session 不稳定（创建失败/中途断开） | 测试执行中断 | 中 | session 创建重试 3 次（指数退避）；session 断开时自动 fail 任务并回收设备 |
| 3 | Appium 元素定位失败（UI 变更/加载慢） | 测试步骤误报失败 | 高 | 单步超时可配置（默认 30s）；推荐 accessibility_id 定位（最稳定）；失败时自动截图辅助排查 |
| 4 | 大文件传输超时（APK > 200MB） | 部署阶段超时 | 低 | 本地缓存已下载的 artifact；分块下载 + 断点续传（Phase 4） |
| 5 | 多 Agent 竞争同一设备导致长时间排队 | Agent 等待时间过长 | 中 | 排队超时 5 分钟自动失败；Phase 4 引入设备池 + 负载均衡 |
| 6 | 模拟器性能不足（帧率低/响应慢） | 性能测试数据不准确 | 中 | 性能测试仅在真机上执行；模拟器仅用于功能测试 |

## 十、上线策略

### Phase 3 上线

| 阶段 | 内容 |
|------|------|
| 开发环境 | 本地 Android Emulator + Appium，开发者自测 |
| 集成测试 | 1 台 Android 真机（Pixel 7）+ testbed 服务，验证完整流程 |
| 内部验收 | Tester Agent 通过 runtime 工具执行 3 个标准测试用例（启动/点击/断言） |
| 上线标准 | 3 个标准用例在模拟器和真机上均通过；设备健康检查正常运行；结果成功上报 platform |

### Phase 4 上线

| 阶段 | 内容 |
|------|------|
| iOS 验证 | macOS 构建机 + iPhone 真机，验证 XCUITest driver |
| 云设备验证 | AWS Device Farm 适配器，验证远程设备调用 |
| 并行验证 | 3 台设备同时执行不同测试，验证调度和隔离 |
| 上线标准 | iOS + Android 双平台通过；云设备按需调用成功；并行任务互不干扰 |

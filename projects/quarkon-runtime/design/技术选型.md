# Agent Runtime 技术选型

> 本文档记录 agent-runtime 项目的技术选型决策过程和最终结论。

---

## 一、选型背景

### 1.1 项目定位

agent-runtime 是 AI 驱动研发协作平台的核心引擎，负责：

- Agent 生命周期管理
- LLM 调用封装
- 多 Agent 协作
- 状态机管理
- 工具调用系统

### 1.2 选型目标

- 快速开发：能够在 3 个月内完成核心功能
- 生产可用：支撑多用户、多项目并发
- 生态成熟：能够复用现有 AI 生态
- 可维护性：代码清晰、易于迭代

## 二、候选语言分析

### 2.1 Python

| 维度 | 评估 |
|------|------|
| **AI 生态** | ⭐⭐⭐⭐⭐ 最成熟 |
| **LLM SDK** | ⭐⭐⭐⭐⭐ OpenAI 官方优先支持 |
| **Agent 框架** | ⭐⭐⭐⭐⭐ LangChain、LlamaIndex |
| **开发效率** | ⭐⭐⭐⭐⭐ 快速迭代 |
| **类型安全** | ⭐⭐⭐ Pydantic 补强 |
| **性能** | ⭐⭐⭐ 异步可接受 |
| **并发模型** | ⭐⭐⭐⭐ asyncio 成熟 |

**核心优势：**

```
AI 生态完整
─────────────────────────────────────────
OpenAI SDK      ✅ 官方优先支持
LangChain       ✅ 最成熟的 Agent 框架
LlamaIndex      ✅ 知识库/RAG 首选
Pydantic        ✅ 类型安全 + 数据验证
FastAPI         ✅ 高性能异步 API
Chroma/Pinecone ✅ 向量存储原生支持
```

### 2.2 TypeScript

| 维度 | 评估 |
|------|------|
| **类型安全** | ⭐⭐⭐⭐⭐ 编译时检查 |
| **前后端统一** | ⭐⭐⭐⭐⭐ 代码复用 |
| **异步支持** | ⭐⭐⭐⭐⭐ 原生 Promise/async |
| **AI 生态** | ⭐⭐⭐ 不如 Python 成熟 |
| **LLM SDK** | ⭐⭐⭐ 有但非官方优先 |
| **Agent 框架** | ⭐⭐⭐ 选择较少 |

**核心优势：**

```
前后端技术栈统一
─────────────────────────────────────────
chat-frontend (TypeScript)
       │
       └──→ agent-runtime (TypeScript)
            - 类型定义共享
            - 代码复用
            - 团队技能统一
```

### 2.3 Rust

| 维度 | 评估 |
|------|------|
| **性能** | ⭐⭐⭐⭐⭐ 极致性能 |
| **内存安全** | ⭐⭐⭐⭐⭐ 无 GC |
| **并发模型** | ⭐⭐⭐⭐⭐ 无数据竞争 |
| **跨平台分发** | ⭐⭐⭐⭐⭐ 单一二进制 |
| **AI 生态** | ⭐⭐ 不成熟 |
| **LLM SDK** | ⭐⭐ 选择极少 |
| **开发效率** | ⭐⭐ 周期长 |

**适用场景：**

```
✅ 本地工具（如 Codex CLI）
✅ 性能关键模块
✅ 安全隔离沙箱
✅ 高并发路由

❌ 复杂业务逻辑
❌ AI 框架集成
❌ 快速迭代阶段
```

### 2.4 Go

| 维度 | 评估 |
|------|------|
| **并发模型** | ⭐⭐⭐⭐⭐ goroutine |
| **部署简单** | ⭐⭐⭐⭐⭐ 单一二进制 |
| **开发效率** | ⭐⭐⭐⭐ 中等 |
| **AI 生态** | ⭐⭐ 较弱 |
| **类型系统** | ⭐⭐⭐ 泛型支持一般 |

## 三、需求对比分析

### 3.1 项目需求 vs 语言特性

| 需求 | Python | TypeScript | Rust | Go |
|------|--------|------------|------|-----|
| LLM 调用 | ✅ 最优 | ✅ 良好 | ⚠️ 需封装 | ⚠️ 需封装 |
| Agent 框架集成 | ✅ LangChain | ⚠️ 选择少 | ❌ 无成熟方案 | ❌ 无成熟方案 |
| 向量存储集成 | ✅ 原生支持 | ✅ 有 SDK | ⚠️ 需封装 | ⚠️ 需封装 |
| 多用户并发 | ✅ asyncio | ✅ Promise | ✅ tokio | ✅ goroutine |
| 快速迭代 | ✅ 最优 | ✅ 良好 | ⚠️ 较慢 | ✅ 良好 |
| 生产部署 | ✅ 成熟 | ✅ 成熟 | ✅ 优秀 | ✅ 优秀 |

### 3.2 开发周期估算

| 语言 | MVP 周期 | 完整功能周期 |
|------|----------|-------------|
| Python | 1 个月 | 3 个月 |
| TypeScript | 1.5 个月 | 4 个月 |
| Rust | 3 个月 | 6+ 个月 |
| Go | 2 个月 | 4 个月 |

### 4.2 选择理由

```
Python 为主
─────────────────────────────────────────
1. AI 生态最成熟
   - OpenAI SDK 官方优先支持
   - LangChain/LlamaIndex 开箱即用
   - 向量存储原生集成

2. 开发效率最高
   - 快速迭代验证
   - 代码简洁易读
   - 社区资源丰富

3. 团队适配
   - 后端经验可迁移
   - 学习成本低
   - 招聘容易

Rust 关键模块
─────────────────────────────────────────
1. 性能热点优化
   - 消息路由高并发
   - 向量计算加速

2. 安全隔离
   - 沙箱代码执行
   - 资源限制控制

3. 渐进式引入
   - 先用 Python 跑通
   - 后用 Rust 优化热点
   - 降低初期风险
```

## 五、技术栈确定

### 5.1 Python 部分

| 组件 | 选型 | 版本 |
|------|------|------|
| 语言 | Python | 3.11+ |
| 异步框架 | asyncio + anyio | - |
| LLM 调用 | openai / litellm | 最新 |
| Agent 框架 | LangChain (可选) | 0.1+ |
| 类型系统 | Pydantic | v2 |
| API 框架 | FastAPI | 0.100+ |
| 数据库 | PostgreSQL + SQLAlchemy 2.0 | 异步 |
| 缓存 | Redis | - |
| 向量存储 | Chroma (开发) / Pinecone (生产) | - |
| 测试 | pytest + pytest-asyncio | - |

### 5.2 Rust 部分

| 组件 | 选型 | 说明 |
|------|------|------|
| Python 绑定 | PyO3 | Python ↔ Rust 交互 |
| 异步运行时 | tokio | 高并发 |
| 序列化 | serde | JSON/MessagePack |
| 沙箱 | firecracker / container | 安全隔离 |

## 六、风险与应对

### 6.1 Python 性能风险

| 风险 | 应对策略 |
|------|----------|
| GIL 限制 | 异步 IO、多进程 |
| 高并发瓶颈 | Rust 路由模块 |
| 内存占用 | 定期 GC、连接池 |

### 6.2 Rust 集成风险

| 风险 | 应对策略 |
|------|----------|
| PyO3 学习曲线 | 先纯 Python，后引入 Rust |
| 编译复杂度 | 独立模块，可选安装 |
| 调试困难 | 完善日志、单元测试 |

## 七、演进路线

```
Phase 1: 纯 Python MVP (1 个月)
─────────────────────────────────────────
- Agent 基类
- LLM 调用
- 简单记忆
- 两个角色（Assistant, Tech Lead）

Phase 2: 完整功能 (2 个月)
─────────────────────────────────────────
- 所有角色
- 完整记忆系统
- 工具系统
- 群聊管理

Phase 3: 性能优化 (1 个月)
─────────────────────────────────────────
- 引入 Rust 路由模块
- 沙箱执行引擎
- 性能测试与优化

Phase 4: 生产就绪 (持续)
─────────────────────────────────────────
- 监控告警
- 日志审计
- 文档完善
```

# review — 代码审查

> **目录定位**:Quantalithos 的**代码审查要求和报告**。A 方案下,代码审查要求沉淀为规范,审查报告按迭代归档。

---

## 一、目录构成

```
代码审查要求.md          审查总则(通用,跨 Phase)
phase-1/                 Phase 1 的审查归档
├── 审查计划.md          Phase 1 审查计划
└── reports/             Phase 1 各轮审查报告
```

---

## 二、A 方案下的定位

### 2.1 `代码审查要求.md`(保留)

作为**跨阶段通用的总则**保留。A 方案下具体的审查清单以 `standards/子项目遵循规范清单.md` §九 PR 审查模板为准,本文与之互补。

### 2.2 `phase-1/`(归档,不删)

Phase 1 的审查记录作为**历史证据**保留,支撑可审计性(红线 1)。**不可删除**。

### 2.3 未来结构

A 方案启动后,按迭代归档:

```
review/
├── README.md
├── 代码审查要求.md       (通用总则)
├── phase-1/              (历史)
├── iteration-01/         (A 方案第一次迭代)
│   ├── 审查计划.md
│   └── reports/
├── iteration-02/
│   └── ...
```

---

## 三、审查实施位置

**PR 层审查** → 按 `standards/子项目遵循规范清单.md` §九 模板过,通过 Gate。
**阶段性审查** → 以"迭代"为单位做综合审查,产出归入 `iteration-NN/reports/`。
**合规审查** → 作为 42001 §9.2 Internal Audit 的一部分,由 Auditor Role 执行,产出归入 `governance.ComplianceDeclaration`。

---

## 四、与其他目录的分工

| 目录 | 作用 |
|---|---|
| **review/** (本目录) | 审查要求 + 审查报告归档 |
| `standards/` | 审查的必守清单 |
| `acceptance/` | 最终验收(不是代码审查,是产品验收) |
| `governance` 域(实现) | 审计事件的运行时载体 |

---

## 五、修订纪律

- `代码审查要求.md` 变更走 ADR
- Phase 1 归档不可修改
- 新迭代开始时按模板创建 `iteration-NN/`

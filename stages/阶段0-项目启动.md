# 阶段 0：项目入口与启动（Assistant -> Tech Lead）

> 本文档细化阶段 0 的完整设计，用于逐项讨论和确认。

---

## 一、Assistant 角色定义

Assistant（私人助理）是用户进入系统后的入口。它不属于任何单一项目，而是面向用户本人提供工作台级服务。Assistant 本身也是临时 Agent（用户在线时存活，离线后释放，用户偏好和项目列表存在 `user_profile` 文件中）。

| 职责 | 说明 |
|------|------|
| 发起新项目 | 协助用户整理项目申请表 → 创建群聊与 `Tech Lead` → 完成上下文转交 |
| 进入已有项目 | 查找用户项目列表 → 从快照恢复项目群组和 Agent 团队 |
| 管理项目列表 | 维护用户的项目列表（存在 user_profile 文件中） |
| 文档与知识服务 | 帮用户查阅内部/外部技术文档、汇总上下文、做项目导航 |

Assistant **不做**的事：不深度参与项目内讨论、不主导长期需求分析、不做技术决策、不负责项目内的需求/缺陷推进、不做任务拆解和项目编排（这些由项目 `Tech Lead` 负责）。

但 Assistant 需要遵守一段固定的**项目启动流程**：

- 整理用户的新项目申请
- 完成轻量确认
- 创建项目群聊
- 实例化项目 `Tech Lead`
- 将申请信息与入口上下文转交给 `Tech Lead`

也就是说，项目启动不是独立角色，而是 Assistant 必须遵守的一段标准流程。

### Assistant 与项目 Tech Lead 的职责划分

| 职责 | Assistant | 项目 Tech Lead |
|------|-----------|----------------|
| 整理用户新想法 / 新项目申请 | ✅ | ❌ |
| 执行项目启动流程 | ✅ | ❌ |
| 创建项目群聊并实例化 `Tech Lead` | ✅ | ❌ |
| 引导用户进入已有项目 | ✅ | ❌ |
| 目标校准与流程路由 | ❌ | ✅ |
| 项目内需求/缺陷分类 | ❌ | ✅ |
| 项目内任务拆解和分配 | ❌ | ✅ |
| 项目内加人/减人 | ❌ | ✅（可请求 daemon 实例化新角色） |

### 用户档案（user_profile）

```yaml
# user_profiles/<user_id>.yaml
user:
  id: user-001
  preferences:
    default_backend: "Rust"
    preferred_style: "简洁"
  projects:
    - name: "个人博客系统"
      file_space: "project_files/personal-blog/"
      status: idle
      last_active: 2026-04-10
    - name: "电商平台"
      file_space: "project_files/ecommerce/"
      status: active
      last_active: 2026-04-12
```

## 二、项目申请表

无论通过哪种入口，最终都产出一份**结构化的项目申请表**。Assistant 负责帮助用户整理和确认这张表，并按项目启动流程创建群聊与 `Tech Lead`，再将申请信息转交给后者。

### 申请表字段

```yaml
project_application:
  # 基本信息
  name: "个人博客系统"
  type: new_project              # new_project / enhancement / bugfix / ops
  description: "做一个类似 Medium 风格的个人博客"

  # 规模判断依据
  scope: medium                  # small / medium / large（Tech Lead 建议，用户确认）
  feature_count: 5               # 大概几个功能模块
  has_frontend: true             # 是否有前端界面
  has_mobile: false              # 是否有移动端

  # 优先级
  priority: normal               # urgent / normal / low

  # 补充信息（可选）
  reference: "参考 Medium"        # 参考产品
  existing_project: ""           # 如果是 enhancement/bugfix，关联哪个已有项目
  constraints: "希望用 Rust 后端" # 技术约束
```

### 申请表的生成方式

| 入口 | 适合谁 | 流程 |
|------|--------|------|
| **入口 A：直接填表** | 老手用户 | 用户在前端填写申请表 → 提交 → Assistant 记录并确认 |
| **入口 B：对话生成** | 新手用户 | 用户跟 Assistant 聊天 → Assistant 引导提问并生成申请表 → 用户确认 |

### Assistant 的项目启动流程

`project_application` 只是原始申请输入，还不足以直接作为进入 `阶段1` 的稳定入口。

因此在正式进入需求理解之前，Assistant 需要先执行一段标准项目启动流程：整理申请信息、创建项目群聊、实例化 `Tech Lead`，并将入口上下文转交给后者，由 `Tech Lead` 执行轻量的 `目标校准` 步骤。

#### 标准启动流程（7 步）

建议把 Assistant 的启动协议固定为下面 7 步：

1. `识别（identify_intent）`：判断用户当前是在发起新项目、进入已有项目，还是仅在做信息咨询
2. `收集（collect_context）`：围绕项目名称、类型、目标、规模、约束等最小必要信息补齐上下文
3. `生成申请表（draft_application）`：整理出结构化的 `project_application`
4. `确认申请（confirm_application）`：请用户确认申请口径，必要时做最后一轮修正
5. `创建现场（create_workspace）`：创建项目群聊、项目文件空间，并实例化项目 `Tech Lead`
6. `生成交接包（build_handoff）`：生成 `assistant_startup_handoff`，把申请信息、入口上下文和启动判断转交给 `Tech Lead`
7. `退出启动流程（exit_startup）`：向用户说明“项目已建立，Tech Lead 已接手”，Assistant 退出该项目的主导流程

这 7 步的含义是：Assistant 负责把项目送上轨道，但不继续主导项目内的分析、设计和执行。

#### 启动交接包：`assistant_startup_handoff`

Assistant 交给 `Tech Lead` 的不应只是申请表本身，而应是一个完整的启动交接包。这样 `Tech Lead` 接手时能同时看到：

- 用户原始意图
- Assistant 已完成的整理结果
- 当前仍未解决的不确定项
- 进入阶段 0 后续动作所需的最小上下文

建议首版结构如下：

```yaml
assistant_startup_handoff:
  startup_id: startup-20260418-001
  source: assistant
  handoff_status: ready_for_tech_lead

  user_request_summary: "用户想启动一个个人博客系统，风格参考 Medium"

  project_application:
    name: "个人博客系统"
    type: new_project
    description: "做一个类似 Medium 风格的个人博客"
    scope: medium
    feature_count: 5
    has_frontend: true
    has_mobile: false
    priority: normal
    reference: "参考 Medium"
    existing_project: ""
    constraints: "希望用 Rust 后端"

  startup_context:
    entry_mode: dialogue
    user_confirmed: true
    known_constraints:
      - "希望使用 Rust 后端"
    open_questions:
      - "评论是否需要审核机制"
      - "是否需要后台管理端"
    assumptions:
      - "首期默认只覆盖 Web 端"

  routing_hint:
    suggested_owner: tech_lead
    suggested_next_step: goal_alignment
    candidate_route: stage1_requirement_analysis
    urgency: normal
```

其中建议分层理解为：

- `project_application` 保存结构化申请输入
- `startup_context` 保存 Assistant 在启动过程中已经观察到的上下文
- `routing_hint` 只是启动建议，不替代 `Tech Lead` 的正式判断

建议首版字段约束进一步明确为：

| 字段 | 含义 | 是否必填 | 说明 |
|------|------|----------|------|
| `startup_id` | 一次启动流程的唯一标识 | 是 | 用于追踪同一次启动中的确认、建场和交接动作 |
| `source` | 交接来源 | 是 | 首版固定为 `assistant` |
| `handoff_status` | 当前交接状态 | 是 | 建议先收敛为 `draft` / `ready_for_tech_lead` / `accepted` |
| `user_request_summary` | 用户原始诉求摘要 | 是 | 保留用户为什么发起该项目的自然语言语义 |
| `project_application` | 结构化申请表 | 是 | 作为后续目标校准与路由判断的基础输入 |
| `startup_context.entry_mode` | 启动入口类型 | 是 | 例如 `form` / `dialogue` |
| `startup_context.user_confirmed` | 用户是否确认申请口径 | 是 | 未确认时不应进入正式建场与交接 |
| `startup_context.known_constraints` | 已知约束 | 否 | 用于帮助 `Tech Lead` 快速识别边界条件 |
| `startup_context.open_questions` | 尚未澄清的问题 | 否 | 显式告诉 `Tech Lead` 接手后优先补问什么 |
| `startup_context.assumptions` | 启动阶段默认假设 | 否 | 需要与事实区分，避免被误当成已确认需求 |
| `routing_hint.suggested_owner` | 建议接手者 | 是 | 首版一般为 `tech_lead` |
| `routing_hint.suggested_next_step` | 建议下一动作 | 是 | 首版建议固定为 `goal_alignment` |
| `routing_hint.candidate_route` | 候选流程 | 否 | 只是建议，不具有最终决定权 |
| `routing_hint.urgency` | 当前紧急度 | 否 | 帮助 `Tech Lead` 判断接手优先级 |

建议再补两条边界规则：

- `assistant_startup_handoff` 只记录启动阶段已知事实、未决问题和临时判断，不写入详细需求、方案设计或任务拆解
- 任何未获用户确认的内容都应优先放在 `assumptions` 或 `open_questions`，而不是伪装成已确认事实

#### 正式字段规范（建议首版）

如果要把 `assistant_startup_handoff` 继续推进到可实现接口层，我建议把字段规范再收敛一层：除了“有没有这个字段”，还要定义它的允许值、谁负责写入、谁负责消费，以及后续是否允许更新。

```yaml
assistant_startup_handoff:
  startup_id: string
  source: assistant
  handoff_status: draft | ready_for_tech_lead | accepted
  user_request_summary: string

  project_application: object
  startup_context:
    entry_mode: form | dialogue
    user_confirmed: boolean
    known_constraints: string[]
    open_questions: string[]
    assumptions: string[]

  routing_hint:
    suggested_owner: tech_lead
    suggested_next_step: goal_alignment
    candidate_route: stage1_requirement_analysis | bugfix_flow | ops_flow | exploration_flow
    urgency: low | normal | urgent
```

建议首版字段语义进一步固定为：

| 字段 | 类型 / 允许值 | 写入方 | 主要消费方 | 更新规则 |
|------|----------------|--------|------------|----------|
| `startup_id` | `string` | Assistant | Assistant / `Tech Lead` / 系统追踪 | 创建后只读 |
| `source` | 固定 `assistant` | Assistant | `Tech Lead` / 审计链路 | 创建后只读 |
| `handoff_status` | `draft` / `ready_for_tech_lead` / `accepted` | Assistant，`Tech Lead` 可更新为 `accepted` | Assistant / `Tech Lead` | 允许按状态机单向推进 |
| `user_request_summary` | `string` | Assistant | `Tech Lead` | 交接后原则上只追加修订说明，不覆盖原摘要 |
| `project_application` | `object` | Assistant | `Tech Lead` | 用户确认前可改；确认后仅允许更正明显录入错误 |
| `startup_context.entry_mode` | `form` / `dialogue` | Assistant | `Tech Lead` | 创建后只读 |
| `startup_context.user_confirmed` | `boolean` | Assistant | Assistant / `Tech Lead` | 只允许从 `false` 变 `true` |
| `startup_context.known_constraints` | `string[]` | Assistant | `Tech Lead` | 可补充，不应无痕覆盖 |
| `startup_context.open_questions` | `string[]` | Assistant | `Tech Lead` | 可在接手后逐项关闭或迁移 |
| `startup_context.assumptions` | `string[]` | Assistant | `Tech Lead` | 接手后应被确认、修正或移除 |
| `routing_hint.suggested_owner` | 固定 `tech_lead` | Assistant | 调度层 / `Tech Lead` | 首版只读 |
| `routing_hint.suggested_next_step` | 固定 `goal_alignment` | Assistant | `Tech Lead` | 首版只读 |
| `routing_hint.candidate_route` | 枚举值 | Assistant | `Tech Lead` | 仅为建议，可被 `Tech Lead` 覆写判断 |
| `routing_hint.urgency` | `low` / `normal` / `urgent` | Assistant | `Tech Lead` | 允许按上下文补充更新 |

建议再把字段分成三层职责：

- `Assistant` 必写层：`startup_id`、`source`、`handoff_status`、`user_request_summary`、`project_application`、`startup_context.entry_mode`、`startup_context.user_confirmed`
- `Assistant` 建议写层：`known_constraints`、`open_questions`、`assumptions`、`candidate_route`、`urgency`
- `Tech Lead` 接手消费层：优先消费 `project_application`、`open_questions`、`assumptions`，然后进入 `goal_alignment`

#### 写入与消费责任

为了避免后续角色边界再次混淆，我建议把 `assistant_startup_handoff` 的责任边界写清楚：

| 角色 | 对 `assistant_startup_handoff` 的责任 |
|------|-------------------------------------|
| `Assistant` | 负责创建、补齐、确认并投递交接包 |
| `Tech Lead` | 负责读取、接受、基于其进入 `目标校准`，但不回头要求 Assistant 继续主导项目 |
| 系统 / 编排层 | 负责保证交接包与项目现场、群聊、`Tech Lead` 实例之间的关联完整性 |

建议按下面规则执行：

- `Assistant` 对“启动信息是否被正确整理”负责，但不对“项目后续目标是否最终收敛”负责
- `Tech Lead` 从 `accepted` 开始对后续目标校准、需求理解和项目推进负责
- 如果 `Tech Lead` 发现交接包信息不足，应在项目上下文内补问，而不是把项目重新退回给 Assistant 重启一遍

#### 更新与追加规则

建议首版再明确三条更新原则：

- 保留原始性：`user_request_summary` 和用户确认后的 `project_application` 不应被无痕重写
- 允许追加性：`known_constraints`、`open_questions`、`assumptions` 允许增补，但应保留修改痕迹或状态语义
- 保持单向交接：一旦 `handoff_status = accepted`，项目主导责任即从 Assistant 转移到 `Tech Lead`

这样定义之后，`assistant_startup_handoff` 就不再只是一个“消息对象”，而是一个真正的启动交接契约。

#### Assistant 启动状态机（首版）

建议把 Assistant 启动流程定义成一个轻量状态机，而不是一段松散对话。首版可先收敛为：

```text
idle
  -> identifying_intent
  -> collecting_context
  -> drafting_application
  -> waiting_user_confirmation
  -> provisioning_project
  -> building_handoff
  -> handoff_completed
  -> exited
```

建议各状态的系统行为如下：

| 状态 | 系统行为 | 退出条件 |
|------|----------|----------|
| `identifying_intent` | 判断是新项目、已有项目还是仅咨询 | 已识别出项目启动意图 |
| `collecting_context` | 补齐最小必要信息 | 足以生成申请表 |
| `drafting_application` | 生成 `project_application` 草案 | 申请表草案已形成 |
| `waiting_user_confirmation` | 请求用户确认或修正 | 用户明确确认 |
| `provisioning_project` | 创建群聊、文件空间、实例化 `Tech Lead` | 项目现场已建立 |
| `building_handoff` | 生成 `assistant_startup_handoff` 并投递 | `Tech Lead` 已可接手 |
| `handoff_completed` | 通知用户项目已启动 | 用户已收到接手提示 |
| `exited` | Assistant 退出该次启动主导流程 | 启动流程结束 |

建议首版异常分流先只处理三类：

- 用户取消：进入 `exited`
- 信息不足：回退到 `collecting_context`
- 建场失败或 `Tech Lead` 实例化失败：停留在 `provisioning_project` 并触发重试 / 告警

建议把核心迁移规则也明确下来：

| 当前状态 | 触发条件 | 下一状态 | 说明 |
|------|----------|----------|------|
| `idle` | 用户提出新项目意图 | `identifying_intent` | 启动流程开始 |
| `identifying_intent` | 确认为新项目启动 | `collecting_context` | 若只是咨询则不进入项目启动 |
| `collecting_context` | 信息达到最小集 | `drafting_application` | 最小集不足时继续补问 |
| `drafting_application` | 申请表草案生成完成 | `waiting_user_confirmation` | 进入正式确认环节 |
| `waiting_user_confirmation` | 用户确认 | `provisioning_project` | 用户修改则回到 `collecting_context` 或 `drafting_application` |
| `provisioning_project` | 群聊、文件空间、`Tech Lead` 均已准备完成 | `building_handoff` | 任一资源失败则停留当前状态 |
| `building_handoff` | 交接包生成并发送成功 | `handoff_completed` | `Tech Lead` 可以开始执行 `目标校准` |
| `handoff_completed` | 已向用户提示接手完成 | `exited` | Assistant 退出主导流程 |

建议首版阻断规则如下：

- 未确认的 `project_application` 不能进入 `provisioning_project`
- 未完成建场的项目不能进入 `building_handoff`
- 未成功生成 `assistant_startup_handoff` 不能标记为 `handoff_completed`

建议首版恢复规则如下：

- `collecting_context` 和 `drafting_application` 允许来回往返，直到申请口径稳定
- `provisioning_project` 失败后允许重试，但不应回退并覆盖已确认的申请内容
- `handoff_completed` 之后如需修改项目启动口径，应由 `Tech Lead` 在项目上下文内继续处理，而不是让 Assistant 重新主导同一次启动

这一步只回答：

- 这次工作属于什么类型
- 当前到底为什么要启动
- 这一轮想达成什么结果
- 什么现象可以说明这轮启动是值得的
- 后续应该进入哪条正式流程

这一步**不**回答：

- 详细需求怎么定义
- 方案怎么设计
- 技术怎么实现
- 任务如何拆解

换句话说，`目标校准` 是 `阶段0` 的轻门禁，而不是提前展开 `阶段1`。

建议最小字段先控制为：

- `work_item_type`
- `core_problem`
- `target_outcome`
- `target_users_or_scope`
- `priority_reason`
- `success_signal`

同时建议由系统补充两个辅助字段：

- `uncertainty_level`
- `recommended_route`

建议产出一个轻量对象：

```yaml
goal_alignment_brief:
  work_item_type: enhancement
  core_problem: "现有博客系统缺少评论能力，用户无法形成互动"
  target_outcome: "交付可用的评论 MVP，并可进入后续验收"
  target_users_or_scope: "博客访客与文章作者"
  priority_reason: "评论能力是内容互动闭环的缺失项"
  success_signal:
    - "访客可提交评论"
    - "作者可查看评论"
    - "核心评论流程可演示"
  uncertainty_level: medium
  recommended_route: stage1_requirement_analysis
```

#### `goal_alignment_brief` 正式规范（建议首版）

如果要把 `目标校准` 继续推进到正式实现层，我建议把它定义成一个由 `Tech Lead` 产出的结构化对象，而不是一段散落在对话里的结论。

建议首版输入来源固定为：

- `assistant_startup_handoff.project_application`
- `assistant_startup_handoff.user_request_summary`
- `assistant_startup_handoff.startup_context`
- `Tech Lead` 接手后补问得到的最少必要信息

建议首版输出对象抽象为：

```yaml
goal_alignment_brief:
  source_startup_id: startup-20260418-001
  aligned_by: tech_lead
  alignment_status: passed

  work_item_type: enhancement
  core_problem: "现有博客系统缺少评论能力，用户无法形成互动"
  target_outcome: "交付可用的评论 MVP，并可进入后续验收"
  target_users_or_scope: "博客访客与文章作者"
  priority_reason: "评论能力是内容互动闭环的缺失项"
  success_signal:
    - "访客可提交评论"
    - "作者可查看评论"
    - "核心评论流程可演示"

  uncertainty_level: medium
  recommended_route: stage1_requirement_analysis
  followup_questions: []
  blocking_issue: ""
```

建议首版字段语义进一步固定为：

| 字段 | 类型 / 允许值 | 写入方 | 主要消费方 | 说明 |
|------|----------------|--------|------------|------|
| `source_startup_id` | `string` | `Tech Lead` | 系统 / `Tech Lead` | 关联本次启动交接 |
| `aligned_by` | 固定 `tech_lead` | `Tech Lead` | 审计链路 / 后续阶段 | 明确由谁完成校准 |
| `alignment_status` | `passed` / `needs_clarification` / `reroute` | `Tech Lead` | 流程编排层 / `Tech Lead` | 表示校准结果状态 |
| `work_item_type` | `new_project` / `enhancement` / `bugfix` / `optimization` / `exploration` / `ops` | `Tech Lead` | 阶段路由层 | 决定后续走哪条流程 |
| `core_problem` | `string` | `Tech Lead` | `阶段1` / 其他流程 | 说明为什么这次要启动 |
| `target_outcome` | `string` | `Tech Lead` | `阶段1` / 交付规划 | 说明本轮想达成什么结果 |
| `target_users_or_scope` | `string` | `Tech Lead` | `阶段1` | 说明影响对象或范围 |
| `priority_reason` | `string` | `Tech Lead` | 排期 / 决策层 | 说明为什么现在做 |
| `success_signal` | `string[]` | `Tech Lead` | `阶段1` / 验收定义 | 说明什么现象代表值得继续 |
| `uncertainty_level` | `low` / `medium` / `high` | `Tech Lead` | 提问策略 / 路由层 | 影响后续提问强度和是否插入额外步骤 |
| `recommended_route` | `stage1_requirement_analysis` / `bugfix_flow` / `ops_flow` / `exploration_flow` | `Tech Lead` | 流程编排层 | 给出建议后续流程 |
| `followup_questions` | `string[]` | `Tech Lead` | `Tech Lead` / 用户 | 在 `needs_clarification` 时列出待补问项 |
| `blocking_issue` | `string` | `Tech Lead` | 流程编排层 / 用户 | 在 `reroute` 或阻断时记录主因 |

建议再把它和 `assistant_startup_handoff` 的边界写清楚：

- `assistant_startup_handoff` 负责保存启动输入和入口上下文
- `goal_alignment_brief` 负责保存 `Tech Lead` 接手后的意图校准结果
- 前者偏“原始输入 + 交接事实”，后者偏“正式判断 + 流程路由”

#### 通过条件与门禁规则

建议把 `目标校准` 的通过条件定义为：

- 能判断 `work_item_type`
- 能写出明确的 `core_problem`
- 能写出本轮 `target_outcome`
- 能说明 `priority_reason`
- 能给出最小可验证的 `success_signal`
- 能确定 `recommended_route`

这一步不要求：

- 所有需求细节都清楚
- 所有边界条件都清楚
- 所有设计问题都清楚
- 所有实施任务都已经拆解

因此它的通过标准不是“信息完整”，而是“信息已经足以支撑类型判断、目标确认和流程路由”。

建议首版门禁规则进一步固定为：

| 条件 | 结果 | 是否允许进入 `阶段1` |
|------|------|-----------------------|
| `alignment_status = passed` 且 `recommended_route = stage1_requirement_analysis` | 通过 | 是 |
| `alignment_status = passed` 但 `recommended_route != stage1_requirement_analysis` | 改走其他流程 | 否 |
| `alignment_status = needs_clarification` | 留在 `阶段0` 补问 | 否 |
| `alignment_status = reroute` | 直接分流 | 否 |

#### 失败时的处理方式

如果 `目标校准` 未通过，建议不要直接进入 `阶段1`，而是按原因分流：

- 信息不足：`Tech Lead` 产出 `followup_questions`，并补问 1~3 个关键问题
- 目标冲突：记录冲突点，先让用户完成目标层取舍
- 类型不清：先稳定 `work_item_type`，再决定进入哪条流程
- 明显不适合走需求流程：将 `alignment_status` 设为 `reroute`，并给出 `blocking_issue`

建议首版恢复规则如下：

- `needs_clarification` 可以在补问后重新评估，并更新为 `passed` 或 `reroute`
- 一旦 `recommended_route` 已明确为非 `stage1_requirement_analysis`，就不应再强行进入 `阶段1`
- `goal_alignment_brief` 应保留最新正式判断，但不应覆盖 `assistant_startup_handoff` 中的原始启动输入

#### 与 `阶段1` 的衔接规则

建议把 `阶段1` 的正式入口定义为：

```text
assistant_startup_handoff accepted
  -> Tech Lead goal alignment
  -> goal_alignment_brief passed
  -> recommended_route = stage1_requirement_analysis
  -> Stage 1 entry
```

这意味着：

- `阶段1` 的输入不再只是 `project_application`
- 而是 `assistant_startup_handoff + goal_alignment_brief`
- `goal_alignment_brief` 负责告诉 `阶段1`：为什么做、做到什么算有效、当前该走哪条流程

## 三、启动交互流程

### 入口 B 完整流程（Assistant 启动项目并移交 Tech Lead）

```
用户                 Assistant（私人助理）               项目群组 / Tech Lead
 │                        │                                │
 │  "我想做一个博客"     │                                │
 │ ────────────────────> │                                │
 │                        │ 引导提问、整理申请表            │
 │  <── "新项目还是改已有？"│                               │
 │  "新项目" ─────────>   │                               │
 │  <── "大概哪些功能？"   │                               │
 │  "文章、标签、评论..."→ │                               │
 │                        │ 生成 `project_application`     │
 │  <── "我先帮您整理申请" │                               │
 │  "确认" ───────────>   │                               │
 │                        │ 创建项目群聊                    │
 │                        │ 实例化 `Tech Lead`             │
 │                        │ 转交申请与入口上下文──────────> │
 │  <── "项目已创建，      │                               │
 │      Tech Lead 已接手" │                               │
 │                        │                                │
 │                        │                      `Tech Lead` 继续追问、
 │                        │                      目标校准、组队与后续推进
```

### 评估逻辑

`Tech Lead` 不再用硬编码的关键词规则。评估不只基于 `project_application`，还应结合 `goal_alignment_brief` 的结果：

| 字段组合 | 判断结果 | 团队组成 |
|----------|----------|----------|
| type=bugfix, feature_count=1 | hotfix | Tech Lead + 开发 + 测试 |
| type=new_project/enhancement, feature_count≤2, has_frontend=false | small | Tech Lead + 开发 + 测试 |
| type=new_project/enhancement, feature_count 3-6 | medium | Tech Lead + 开发 + 测试 + DevOps（+UI/前端按需） |
| type=new_project, feature_count>6 | large | Tech Lead + 开发 x N + 测试 + DevOps（+UI/前端/移动端按需） |

`Tech Lead` 作为 LLM Agent，可以综合理解申请表内容做判断，上表只是参考指南（写入 `tech-lead` 的 identity.md），不是硬编码 if-else。

## 四、项目 vs 需求条目

**申请表只用于创建新项目。** 项目创建后，所有后续工作（加功能、修 Bug、优化等）在项目群组内直接提出，由 Tech Lead 处理。

| 概念 | 创建方式 | 频率 |
|------|----------|------|
| **项目** | 申请表 → Assistant 整理 → Assistant 启动项目并移交 `Tech Lead` | 偶尔（一个博客系统只创建一次） |
| **需求/缺陷/优化** | 在项目群组内直接对 Tech Lead 说 | 频繁（每天都可能） |

### 项目长期存在

项目不再是"做完就结束"，而是持续运行的：

```
项目创建 → 首批需求开发 → 交付 → 日常维护（加功能、修 Bug）→ ... → 归档
```

群组也长期存在。Agent 在项目 idle 时释放，需要时从快照恢复。

### 项目内的工作流

用户在群组内直接发起新工作，不需要再走 Assistant：

```
用户在群组内:
  │
  ├─ "加一个评论功能"  → Tech Lead 判断为需求 → 走阶段 1-5 流程
  ├─ "登录有 Bug"      → Tech Lead 判断为缺陷 → 走 Bug 修复流程
  ├─ "首页加载太慢"    → Tech Lead 判断为优化 → 走对应流程
  └─ "部署到新服务器"   → Tech Lead 判断为运维 → DevOps 主导
```

### 需求条目与任务卡的关系

```
project_files/<project>/
  ├── requirements/              # 需求/缺陷/优化条目（Tech Lead 创建）
  │     ├── REQ-001.md           # 需求：评论功能
  │     ├── BUG-001.md           # 缺陷：登录报 500
  │     └── OPT-001.md           # 优化：首页加载慢
  │
  └── tasks/                     # 任务卡（从需求条目拆出）
        ├── TASK-013.md          # parent: REQ-001
        ├── TASK-014.md          # parent: REQ-001
        └── TASK-015.md          # parent: BUG-001
```

任务卡增加 `parent` 字段关联需求条目。

### 两种启动方式

- **新项目**：申请表（填表或对话生成）→ Assistant 整理 → Assistant 启动项目并移交 `Tech Lead`
- **已有项目**：用户告诉 Assistant "回到 XX 项目" → 从快照恢复群组和 Agent → 用户在群内直接提需求

## 五、Agent 生命周期

### 核心策略：持久化"现场"而非"人"

所有 Agent（包括 Assistant 和项目 `Tech Lead`）都是临时的。持久化的是**项目现场快照**和**用户档案**，不是 Agent 进程。

```
Agent 销毁前 → 保存现场快照到文件
Agent 需要时 → 读快照 → 实例化 → 注入快照 → 继续工作
```

| 维度 | 持久化 Agent | 持久化现场 |
|------|-------------|-----------|
| 资源占用 | 项目 idle 也占资源 | 只占文件存储 |
| 信息完整度 | Agent 记忆可能遗漏 | 文件是精确记录，不会遗忘 |
| 并发问题 | 持久 TL 被多项目抢 | 每个项目独立实例化 |
| 可迁移/审计 | 绑定在进程上 | 文件可备份、版本控制、查阅 |

### Agent 生命周期

```
Assistant: 用户在线时存活 → 离线后释放
           （用户偏好和项目列表存在 user_profile 文件中）

项目 Tech Lead 与其他项目 Agent: 项目 active 时存活 → idle 时释放 → 被唤醒时从快照恢复
```

### 项目现场快照

快照保存在项目文件空间中，daemon 在关键时刻自动保存：

```
project_files/<project>/
  └── .snapshot/
        ├── team.yaml              # 团队成员 + 角色模板来源
        ├── agents/                # 每个 Agent 的运行时状态
        │     ├── tech-lead-001.yaml
        │     ├── backend-dev-001.yaml
        │     └── test-eng-001.yaml
        └── project-state.yaml    # 项目阶段、活跃需求、Git 状态
```

**team.yaml — 团队快照：**

```yaml
team:
  - id: tech-lead-001
    role_template: system_templates/tech-lead
    joined_at: 2026-04-01
  - id: backend-dev-001
    role_template: company_templates/backend-developer
    joined_at: 2026-04-01
  - id: test-eng-001
    role_template: system_templates/test-engineer
    joined_at: 2026-04-02
```

**agent 快照 — 项目内积累的知识：**

```yaml
# agents/backend-dev-001.yaml
agent:
  id: backend-dev-001
  role_template: company_templates/backend-developer
  project_notes: |
    - 本项目后端用 Rust + Actix-web
    - 数据库用 PostgreSQL，ORM 用 diesel
    - 文章表和标签表已建好，评论表待建
    - 代码规范：函数命名 snake_case，错误处理统一 Result<T, AppError>
  current_task: TASK-014
  completed_tasks: [TASK-013, TASK-015]
```

**project-state.yaml — 项目状态：**

```yaml
project:
  name: "个人博客系统"
  status: idle                # active / idle / archived
  current_stage: ITERATIVE_DEV
  last_active: 2026-04-10
  active_requirements:
    - REQ-001: "评论功能（进行中）"
    - BUG-001: "登录报 500（已关闭）"
  git:
    branch: dev
    last_commit: "feat: add tag CRUD API"
```

**快照保存时机：**

| 时机 | 触发方式 |
|------|----------|
| 每个任务完成时 | daemon 自动保存 |
| 每个阶段切换时 | daemon 自动保存 |
| 项目进入 idle 前 | daemon 保存完整快照并释放 Agent |
| 用户手动触发 | 用户在群聊中说"保存当前进度" |

### 恢复流程

用户三个月后回来：

```
用户 → Assistant: "回到我的博客项目"
  → Assistant 读取 .snapshot/project-state.yaml → 状态 idle
  → 读取 .snapshot/team.yaml → 原团队配置
  → 从模板重新实例化同样的角色
  → 给每个 Agent 加载对应的 agent 快照（project_notes）
  → 重建群组，拉入用户和 Agent
  → Tech Lead 接手："我已回顾项目状态，博客已完成文章和标签，
     评论功能进行到一半。您想继续还是做其他的？"
```

### 角色决策：怎么决定创建哪些角色

三层叠加决策：

| 层级 | 输入 | 示例 |
|------|------|------|
| 申请表字段 | has_frontend=true → 需要前端开发 | 基础判断 |
| LLM 理解 | description 提到"推荐算法" → 需要 ML 工程师 | 补充判断 |
| 用户确认 | 用户："后端要两个，一个做 API 一个做推荐" | 最终调整 |

### 模板来源与查找优先级

角色模板有三个来源，按优先级查找：

```
① company_templates/       用户自定义（公司内共享，优先级最高）
    ├── mobile-developer/
    ├── ml-engineer/
    └── payment-specialist/

② system_templates/        系统预装（开箱即用）
    ├── assistant/
    ├── tech-lead/
    ├── backend-developer/
    ├── frontend-developer/
    ├── test-engineer/
    ├── devops/
    └── ui-designer/

③ 运行时生成               AI 辅助创建临时模板，用户确认后可保存到 company_templates
```

公司模板优先于系统模板——用户可能自定义了"后端开发"覆盖系统默认的（如公司所有后端都用 Go）。

### 完整的角色创建流程

```
Assistant 协助用户确认申请表
  → Assistant 创建项目群聊并实例化 `Tech Lead`
  → `Tech Lead` 从申请表 + LLM 理解确定需要哪些角色
  → 逐个角色查找模板：company_templates → system_templates → 不存在
  → 都有 → 展示团队列表给用户确认
  → 有缺失 → 提示用户："缺少 XX 角色模板，是否要我生成一个？"
     → AI 辅助生成模板草稿（identity.md + permissions.yaml）
     → 用户确认 → 可选保存到 company_templates 供以后复用
  → 用户最终确认团队
  → daemon 从模板实例化 Agent（生成唯一 ID，加载三层 prompt）
  → 拉入群组
```

## 六、数据分层架构

用户通过前端 App 操作，Agent 在文件系统中工作，daemon 负责两侧同步。

```
┌─────────────────────┐     ┌──────────────────────┐
│   前端 App (UI)     │     │   AI Agent 工作区     │
│                     │     │                       │
│  项目列表           │     │  project_files/       │
│  看板视图           │     │    ├── src/            │
│  任务详情           │     │    ├── tests/          │
│  聊天记录           │     │    ├── docs/           │
│  审批/门禁          │     │    └── .snapshot/      │
│  项目申请表         │     │                       │
└────────┬────────────┘     └───────────┬───────────┘
         │                              │
         │         ┌──────────┐         │
         └────────>│  daemon  │<────────┘
                   │  (Rust)  │
                   │  + DB    │
                   └──────────┘
```

**核心原则：用户看到的走数据库（快、可查询、实时推送），Agent 工作的走文件系统（可读写、可 Git 管理）。daemon 负责两者同步。**

### 存数据库（前端展示、查询、实时推送）

| 数据 | 原因 |
|------|------|
| 项目列表、项目状态 | 快速查询、列表展示 |
| 项目申请表 | 结构化表单，前端提交 |
| 需求/缺陷条目 | 筛选、排序、看板展示 |
| 任务卡元数据 | 状态、负责人、优先级等需要实时查询 |
| 聊天记录 | 分页加载、搜索 |
| 用户档案、偏好 | 多用户管理 |
| 团队快照元数据 | 项目恢复时快速加载 |
| Agent 状态 | 实时展示给用户 |

### 存文件系统（Agent 工作区、Git 管理）

| 数据 | 原因 |
|------|------|
| 源代码 | Git 版本控制 |
| 设计文档、PRD | Agent 直接读写，需要 Git 管理 |
| 测试报告 | Agent 生成的产出物 |
| Agent 的 project_notes | Agent 读取恢复上下文 |
| 共享规则、角色模板 | Agent 加载用 |

### 同步机制

```
Agent → 文件系统:
  Agent 完成任务 → 更新代码和文档 → 发送 DELIVERABLE 消息
  → daemon 更新数据库中的任务状态
  → daemon 推送更新到前端（WebSocket）
  → 用户在 App 上实时看到看板变化

用户 → 数据库:
  用户在 App 创建需求条目 → 前端提交到 daemon API
  → daemon 存入数据库 → 在群聊中通知 Tech Lead
```

## 八、团队规模裁剪（修正）

Tech Lead 是**所有项目的标配**，因为代码审查不能跳过。Hotfix 只裁剪流程，不裁剪审查角色。

| 规模 | 团队 | 流程 |
|------|------|------|
| **hotfix** | Tech Lead + 开发 + 测试 | 定位→修复→审查→测试→部署 |
| **small** | Tech Lead + 开发 + 测试 | 简要设计→开发→测试→交付 |
| **medium** | Tech Lead + 开发 + 测试 + DevOps（+按需） | 完整 6 阶段 |
| **large** | Tech Lead + 开发 x N + 测试 + DevOps（+按需） | 完整 6 阶段，多轮迭代 |

## 九、缺失项清单（全部解决）

| # | 缺失项 | 解决方案 | 状态 |
|---|--------|----------|------|
| 1 | 评估逻辑太粗糙 | 表单驱动 + LLM 判断 | ✅ |

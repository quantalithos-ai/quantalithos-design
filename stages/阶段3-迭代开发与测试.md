# 阶段 3：迭代开发与测试（任务级流水线）

> 本文档作为阶段 3 的独立讨论入口，用于定义任务级实施执行的目标、边界、核心议题与运行骨架。

---

## 一、阶段 3 的建议命名

结合前面的全景图、阶段 1 文档和早期设计方案(已归入 `architecture/legacy/设计优化方案.md`),我建议把下一阶段统一命名为：

> **阶段 3：迭代开发与测试（任务级流水线）**

这个命名比“实施执行”更好的一点在于：

- 它保留了“执行阶段”的含义
- 但更准确地强调了：
  - 不是整批开发
  - 而是任务级流转
  - 开发与测试不是尾部串行，而是任务内耦合推进

所以如果后面需要同时保留一个抽象名和一个业务名，我建议这样对应：

- 阶段抽象名：`阶段 3：实施执行`
- 阶段工作名：`阶段 3：迭代开发与测试（任务级流水线）`

在后续文档里，优先用第二个名字会更清晰。

## 二、阶段 3 的本质

我建议把阶段 3 的本质先收敛成一句话：

> **阶段 3 不是“把设计交给开发去做”这么简单，而是把阶段 2 形成的结构化执行输入，转成一条受控的、多任务并行的、可验证的任务级交付流水线。**

换句话说，阶段 2 解决的是：

- 做什么
- 谁负责
- 边界是什么
- 按什么节奏推进
- 是否可以进入实施

而阶段 3 解决的是：

- 一个个任务如何被真正执行
- 开发、测试、评审、修复如何围绕同一任务状态机运转
- 多任务如何并行而不失控
- blocker、bug、返工、重审如何被结构化处理
- 阶段完成如何从任务完成中被汇总出来

## 三、阶段 3 的目标

我建议先把阶段 3 的目标定成下面五类：

### 1. 把阶段 2 的 handoff 转成真实可执行任务流

也就是：
- `stage2_handoff_package` 不只是交接文档
- 它要被 runtime 投影为阶段 3 的任务级执行图

### 2. 管理单任务生命周期

也就是每个任务要有完整流转链：

- 开发
- 自测 / 单测
- 代码审查
- 任务测试
- 缺陷修复
- 完成验证

### 3. 管理多任务并行

也就是：
- 哪些任务可并行
- 哪些任务必须等待依赖解除
- 哪些任务失败会阻塞其它任务

### 4. 管理执行期异常

也就是：
- bug report
- review reject
- verification fail
- unblock request
- change request

都要有正式路由，不是临时聊天处理。

### 5. 形成阶段 4 可消费的完成态产物

也就是最终至少要形成：

- 已完成任务集合
- 测试与验证证据
- 集成测试输入
- 阶段 4 的验收准备输入

## 四、阶段 3 不解决什么

为了避免阶段 3 再次边界漂移，我建议也先明确它不解决什么：

### 1. 不重新做阶段 2 的主拆解

也就是：
- 不回头重新讨论大的 workstream 结构
- 不把阶段 3 当成“边做边重新设计阶段 2”

当然，执行期会发现设计缺口，但那应通过：
- change route
- rollback route
- escalation route

处理，而不是默认重开全部阶段 2。

### 2. 不承担最终用户验收

用户正式确认属于阶段 4，而不是阶段 3。

阶段 3 可以有：
- 增量预览
- 中间展示
- 提前纠偏

但这不等于正式验收通过。

### 3. 不承担生产部署

生产部署属于阶段 5。

阶段 3 最多做到：
- 本地 / CI 验证
- 预览环境联调
- 集成测试准备

### 4. 不默认吸收需求级变更

执行期如果出现“其实需求不是这样”的情况，不能直接当普通 bug 修。

必须区分：
- 实现缺陷
- 设计缺口
- 需求变更

否则阶段 3 会无限膨胀。

## 五、阶段 2 到阶段 3 的交接关系

这是进入下一阶段时最关键的一层。

我建议明确：

> **阶段 3 不是从零开始，而是以阶段 2 的 `stage2_handoff_package` 作为正式输入，以 `implementation_entry_packet` 作为 runtime 启动输入。**

可先抽象成：

```text
stage2_handoff_package
   -> implementation_entry_packet
   -> Stage3 Runtime Initialization
   -> task-level execution graph
   -> iterative delivery pipeline
```

## 六、阶段 3 的关键输入

我建议把阶段 3 的输入分成三层，而不是把所有 artifacts 当成同一层资料：

- `stage2_handoff_package`：阶段级聚合交接包，负责保留方案背景、范围基线与主 artifacts 汇总
- `implementation_entry_packet`：实施进入 gate 通过后的正式启动包，负责声明“允许进入阶段 3 时，究竟带着哪些对象与约束进入”
- `stage3_entry_contract`：阶段 3 的消费契约，负责把进入包进一步翻译为 runtime 可执行的启动规则、继承约束和持续跟踪项

换句话说：

> `stage2_handoff_package` 解决“交什么”，`implementation_entry_packet` 解决“能不能进”，`stage3_entry_contract` 解决“进来之后怎么消费”。

### 1. 阶段 3 必须直接消费的进入对象

我建议阶段 3 不要把 `implementation_entry_packet` 当成一个只读外壳，而应把其中对象分成“直接启动输入”和“引用型背景输入”两层。

**直接启动输入**：进入 runtime 初始化后立即生效，用于任务实例化、调度和校验。

- `task_tree`：生成 `task_instance`、依赖边和最小执行单元
- `ownership_map`：绑定 owner、主评审、必需会签与升级路径
- `interface_contracts`：形成实现边界、联调边界与验证边界
- `implementation_plan`：形成任务波次、前置条件、执行顺序与验证切口
- `risk_register`：形成高风险任务标记、blocker 监控与风险驱动的验证要求
- `dependency_readiness_packet`：形成外部依赖可用性基线、回退方案与不可启动条件
- `readiness_report`：形成阶段 3 启动判断基线、环境/数据/权限前提与首轮 can_start 条件
- `carry_over_risks`：转译为阶段 3 的持续风险项或初始 blocker
- `stage3_entry_constraints`：转译为启动门槛、任务禁止条件和迭代内强约束

**引用型背景输入**：不直接驱动调度，但必须保留，用于审计、回退和边界判定。

- `approved_scope_version`：作为阶段 3 执行范围基线，防止执行期偷偷漂移
- `solution_summary`：作为设计缺口、异常升级与是否回退阶段 2 的判定背景
- `milestone_plan`：作为阶段级节奏参考，不直接替代任务级调度规则
- `source_gate_evaluation_id`：回溯 gate 结论、条件项与回退路由
- `approvers`：作为正式进入责任链，而不是 runtime 审批流本身

进一步约束为：

- 阶段 3 的主调度器应优先消费 `implementation_entry_packet` 中已批准的对象引用，而不是跳回阶段 2 自行挑选 artifacts
- 若某对象未出现在 `included_artifacts`，默认不应被当成阶段 3 的正式输入
- `solution_summary` 可以被阶段 3 参考，但不应在执行期替代 `task_tree` 和 `implementation_plan` 成为主调度依据

### 2. `readiness_report`、`stage2_gate_evaluation` 与 NFR 映射结果如何在阶段 3 生效

这三类对象都不应在阶段 3 被重新“评一次”，而应转化为不同类型的 runtime 约束。

#### `readiness_report` 的生效方式

`readiness_report` 进入阶段 3 后，不再只是“是否 ready”的说明，而应成为：

- 首轮任务启动前的 readiness 基线
- 环境、权限、测试数据、日志最小项等前置条件的来源
- 哪些任务可立即进入开发、哪些任务必须等待依赖解除的判断依据
- 执行期如果 readiness 前提被破坏时的 blocker 触发源

因此：

- `readiness_report` 不重做 gate 判定
- 但会转译成 `can_start` 规则、`blocked_reason` 和启动前检查项

#### `stage2_gate_evaluation` 的生效方式

`stage2_gate_evaluation` 在阶段 3 中的角色，不是继续参与调度细节，而是提供正式的进入依据和回退框架。

我建议阶段 3 至少继承它的以下语义：

- `decision_status`：决定当前入口是标准启动，还是带条件启动
- `decision_reasons`：作为阶段 3 初始上下文的一部分，说明为什么现在允许开工
- `required_followups`：转译为阶段 3 的启动义务项或早期迭代必跟踪项
- `blocking_items`：若仍存在，则必须转译为显式 blocker，而不是在阶段 3 中消失
- `fallback_route`：一旦执行期发现前提失效，用于决定回退到阶段 2 的哪个主线步骤

进一步约束为：

- 阶段 3 不应重新改写 gate 结论
- 但必须显式继承 gate 留下的条件项和回退路由
- `conditional_pass` 进入阶段 3 后，必须表现为“带约束启动”，不能表现为普通 `pass`

#### `nfr_design_mapping` / `constraint_to_design_map` 的生效方式

NFR 映射结果在阶段 3 中至少应通过三条通道生效：

- **硬约束继承**：已经落到 `interface_contracts`、`readiness_report`、`stage3_entry_constraints` 的安全、合规、运行前提，必须在任务启动前继承
- **执行动作继承**：已经落到 `task_tree`、`implementation_plan` 的设计动作，应转成正式任务、验证任务或前置步骤
- **持续风险继承**：`constraint_to_design_map.carry_forward_risks` 这类未在阶段 2 关闭的项，应转成阶段 3 持续跟踪项，而不是留在文档注释里

这意味着：

- NFR 映射结果不能只在阶段 2 文档里“存在过”
- 只要它影响实现边界、验证切口、依赖前提或 gate 条件，就必须投影到阶段 3 runtime

### 3. 哪些约束必须启动前继承，哪些要在迭代中持续跟踪

我建议把阶段 3 的继承约束固定分成两层：

**启动前必须继承的约束**：未满足前，不应进入正式任务执行。

- `approved_scope_version` 对应的范围边界
- `stage3_entry_constraints` 中声明为启动前提的条件
- `readiness_report` 中涉及环境、权限、测试数据、日志最小项的 readiness 前提
- `interface_contracts` 中影响输入输出、安全、合规和协作边界的硬约束
- `dependency_readiness_packet` 中仍要求先满足的外部依赖前提
- `stage2_gate_evaluation.required_followups` 中被标记为开工前必须补齐的项

**迭代中持续跟踪的约束**：允许启动，但必须挂在任务流、风险流或 blocker 流里持续检查。

- `carry_over_risks` 中尚未关闭但已接受带入阶段 3 的风险
- `risk_register` 中会影响顺序、质量或里程碑的高风险项
- NFR 映射中 `monitor` / `review_required` 级别的约束
- `constraint_to_design_map.carry_forward_risks` 中需要在首轮迭代继续验证的项
- `milestone_plan` 与 `implementation_plan` 中需要滚动校准的节奏和资源约束
- `conditional_pass` 场景下被允许后补、但必须持续回填状态的条件项

进一步约束为：

- 启动前约束解决的是“是否能开始”
- 持续跟踪约束解决的是“开始后如何不失控”
- 同一个约束可以先作为启动前提，进入阶段 3 后再降级为持续监控项，但不能反过来偷降级

### 4. 建议补的正式对象：`stage3_entry_contract`

我建议阶段 3 至少补一个新的正式对象：`stage3_entry_contract`。

它不是替代 `implementation_entry_packet`，而是把“通过 gate 后允许进入阶段 3”这件事，进一步 formalize 为“阶段 3 到底消费什么、按什么规则消费、出现问题时回到哪里”。

建议首版对象抽象为：

```yaml
stage3_entry_contract:
  source_implementation_entry_id: entry-001
  source_stage2_handoff_id: stage2-handoff-001
  contract_status: draft | review_ready | active | blocked
  startup_required_artifacts:
    - task_tree
    - ownership_map
    - interface_contracts
    - implementation_plan
    - risk_register
    - dependency_readiness_packet
    - readiness_report
  startup_required_constraints:
    - "正式账号未开通前，不得启动依赖正式账号的任务"
    - "日志与最小监控未就绪前，不得进入联调验证"
  carried_followups:
    - source: stage2_gate_evaluation.required_followups
      enforcement: block_stage_start | block_task_start | monitor_until_closed
  carried_runtime_rules:
    - source: stage3_entry_constraints
      rule_type: hard_constraint | start_condition | monitor_rule
    - source: constraint_to_design_map.carry_forward_risks
      rule_type: risk_monitor
  reference_inputs:
    - approved_scope_version
    - solution_summary
    - milestone_plan
    - source_gate_evaluation_id
  rollback_routes:
    design_gap: return_to_solution_alignment
    dependency_gap: return_to_dependency_readiness
    scope_conflict: return_to_stage1
  next_action: initialize_stage3_runtime | hold_stage3 | request_stage2_followup
```

建议职责边界固定为：

- `implementation_entry_packet`：负责声明“允许进入阶段 3 的正式进入状态”
- `stage3_entry_contract`：负责声明“阶段 3 如何消费这个进入状态”
- `stage3 runtime`：负责把 contract 转成任务实例、调度规则和 blocker 规则

如果后续 runtime 需要一个持久化启动快照，再额外补一个 `stage3_execution_context` 也合理；但从当前 formalization 进度看，最小必要新增对象先固定为 `stage3_entry_contract` 即可。

### 5. 一张简化衔接图

```text
stage2_handoff_package
  -> implementation_entry_packet
  -> stage3_entry_contract
  -> Stage3 Runtime Initialization
  -> task_instance / blocker_rule / verification_rule
```

这些输入进入阶段 3 后，不应只是“可读资料”，而应被 runtime 继续转译成：

- 任务实例
- 依赖约束
- review 要求
- verification 要求
- blocker 监控规则

## 七、阶段 3 的阶段出口

如果先给阶段 3 定一个出口，我建议它至少要回答：

- 哪些任务已完成并通过验证
- 哪些 blocker 已关闭
- 哪些 bug 仍未关闭
- 是否已达到集成测试与阶段 4 验收前置条件

因此阶段 3 的出口对象大致可以先理解成：

- `task_delivery_summary`
- `verification_evidence_bundle`
- `integration_report`
- `stage3_completion_report`
- `acceptance_entry_packet`

换句话说：

> **阶段 2 的出口是“可开工”，阶段 3 的出口是“已完成到足以进入验收”。**

## 八、阶段 3 的主流程骨架

基于当前已有定义，我建议阶段 3 的主流程骨架先理解成：

```text
(Stage 3 Start)
   |
   v
[1. 阶段3运行初始化]
   |
   v
[2. 任务实例化与调度]
   |
   v
[3. 单任务开发/测试/审查流水线]
   |
   v
[4. 多任务并行收敛]
   |
   v
[5. 集成测试与阶段完成判断]
   |
   v
<是否达到阶段3完成条件?>
   |否                     |是
   v                       v
继续任务流转 / 处理异常     [6. 输出阶段3完成包]
                            |
                            v
                       (Stage 3 End)
```

## 九、我建议阶段 3 先拆成哪些核心议题

和阶段 2 一样，阶段 3 也不应该一开始就只看成一个大阶段，而更适合先拆成几个可讨论的核心议题。

我建议第一版先拆成下面六个议题：

### 议题 1：阶段 3 的目标、边界与任务级本质

回答：
- 阶段 3 到底负责什么
- 任务级流水线和阶段 2 的区别是什么
- 什么属于实现问题，什么属于需求 / 设计变更

### 议题 2：任务实例化与任务状态机

回答：
- 阶段 2 的 `task_tree` 如何投影为阶段 3 的 task instance
- 一个任务的状态机应该怎么定义
- review、bug、reopen 如何挂接在任务状态机上

### 议题 3：单任务流水线设计

回答：
- 单任务内的开发、测试、审查、修复、完成验证如何流转
- TDD 在 runtime 里如何表达为可选 / 默认策略
- “无新鲜证据不宣称成功”如何进入状态机

### 议题 4：多任务并行与依赖调度

回答：
- runtime 如何决定哪些任务可以并行
- 哪些任务是 blocker
- 哪些失败会导致级联阻塞或调度重排

### 议题 5：执行期异常、bug、变更与回退

回答：
- bug report 如何进入主线
- review reject、verification fail 如何重开任务
- 设计缺口和需求变更何时回退到阶段 2 / 阶段 1

### 议题 6：阶段 3 完成条件与阶段 4 交接

回答：
- 什么叫阶段 3 已完成
- 集成测试在阶段 3 的位置是什么
- 阶段 4 的 `acceptance_entry_packet` 应该长什么样

## 十、阶段 3 运行时可能需要的新核心对象

进入阶段 3 之后，核心对象会和阶段 2 不同。

我建议至少会出现下面这些新对象：

- `task_instance`
- `task_state`
- `code_patch`
- `verification_result`
- `review_result`
- `bug_report`
- `blocker_record`
- `change_request`
- `rollback_decision`
- `integration_report`
- `task_delivery_summary`
- `stage3_completion_report`
- `acceptance_entry_packet`

这意味着：

- 阶段 2 偏设计 artifacts
- 阶段 3 偏执行 artifacts + 证据 artifacts

## 十一、阶段 3 最值得优先讨论的难点

如果要判断从哪里开始深化，我认为阶段 3 最难的不是“开发要写代码”这件事，而是下面四件事：

### 1. 任务状态机怎么定义才不会失控

这是阶段 3 的核心。

### 2. review / bug / verification 三条链如何挂到同一任务上

否则系统会分裂成三套状态。

### 3. 多任务并行调度如何和依赖图联动

否则只会变成“大家同时做事”，但 runtime 没有真正调度能力。

### 4. 何时应该回退到阶段 2，而不是继续硬修

这是避免执行期吞掉设计期问题的关键。

## 十二、当前最合理的下一步

如果我们确认正式进入阶段 3，我建议最自然的推进顺序是：

1. 先完整展开 `议题 1：阶段 3 的目标、边界与任务级本质`
2. 再展开 `议题 2：任务实例化与任务状态机`
3. 然后再进入单任务流水线、多任务并行和异常回退

原因很简单：

- 阶段 3 一旦没有先定稳任务状态机，后面所有流水线讨论都会漂

## 十三、议题 2：任务实例化与任务状态机

在阶段 3 里，真正进入 runtime 的，不应再是阶段 2 的静态 `task_tree`，而应是带约束、带责任、带验证要求的 `task_instance`。

换句话说：

> **阶段 2 定义“任务应该怎样被做”，阶段 3 定义“这个任务实例现在是否能启动、正在经历什么、何时算真正完成”。**

### 1. 任务实例化要解决什么问题

我建议先把 `任务实例化` 要解决的问题收敛为下面五类：

- `task_tree` 是设计态结构，不能直接等同于 runtime 中的可执行对象
- 阶段 2 已定义的 owner、依赖、接口、计划、风险，在进入阶段 3 后必须落到单任务
- 不是所有任务在阶段 3 启动时都可立即开工，需要按约束决定 `ready` 还是 `blocked`
- review、verification、bug、reopen 不应各自形成独立主状态，而应挂接到同一任务生命周期
- 执行期需要区分“任务定义本身”与“任务当前这次运行状态”

因此我建议把阶段 3 的最小运行时对象固定为下面三层：

- `task_definition_ref`：引用阶段 2 中的原始任务定义节点
- `task_instance`：阶段 3 中真正可执行、可调度、可追踪的任务对象
- `task_state`：这个实例当前处于什么运行状态

### 2. `task_tree` 如何投影为 `task_instance`

我建议默认采用：

> **一个已批准的 `task_tree` 叶子任务节点，在阶段 3 初始化后默认投影为一个 `task_instance`；reopen 不新建实例，split / replan 才新建实例。**

这样做的原因是：

- 如果每次 review reject 或 verification fail 都新建实例，会导致状态和责任链断裂
- 如果完全不允许新实例，又无法表达任务拆分、返工重规划和补充子任务

因此首版建议固定下面三条规则：

- **默认一对一投影**：一个可执行叶子节点 -> 一个 `task_instance`
- **失败后优先 reopen**：review reject / verification fail / defect reopen 默认回到原实例继续推进
- **结构变更才新建实例**：只有任务被拆分、替换、合并、重新规划时，才生成新的实例或补充实例

### 3. `task_instance` 应继承哪些输入

我建议 `task_instance` 至少从下面几类正式对象中编译得到：

- `task_tree`：提供任务标识、任务边界、依赖关系、拆解层级、任务类型
- `ownership_map`：提供 owner、协作角色、默认主评审与升级责任链
- `interface_contracts`：提供实现边界、接口变更影响面、联调前置条件
- `implementation_plan`：提供波次、顺序、前置任务、阶段内里程碑约束
- `risk_register`：提供高风险标记、风险备注、额外验证要求
- `readiness_report`：提供环境、权限、测试数据、最小 readiness 前提
- `dependency_readiness_packet`：提供外部依赖可用性与不可启动条件
- `stage3_entry_contract`：提供启动规则、必须继承的约束和运行时 followup

进一步约束为：

- `task_tree` 决定“这是什么任务”
- `ownership_map` 决定“谁主做、谁必须评、谁要被通知”
- `implementation_plan` 决定“何时可以排入执行波次”
- `stage3_entry_contract` 决定“能否启动、启动后必须持续满足什么条件”

### 4. 建议补的正式对象：`task_instance`

我建议把 `task_instance` 正式抽象为：

```yaml
task_instance:
  task_instance_id: taski-001
  source_task_node_id: task-node-001
  instance_status: draft | ready | in_progress | in_review | in_fix | in_verification | blocked | done | cancelled
  task_type: feature | bugfix | integration | test_support | env_setup | refactor | research_spike
  scope_in:
    - "评论提交接口实现"
  scope_out:
    - "评论列表分页优化"
  owner: backend-dev
  collaborators:
    - frontend-dev
  reviewer_config:
    primary_reviewer: tech-lead
    required_reviewers:
      - frontend-dev
    optional_reviewers: []
    notified_roles:
      - tester
    approval_policy: all_required
  dependencies:
    upstream_task_instance_ids: []
    external_dependencies:
      - notify-account-ready
  implementation_requirements:
    - "必须遵守评论提交接口输入校验约束"
  verification_requirements:
    - "提交接口通过任务级验证"
    - "关键日志字段可观测"
  blocker_conditions:
    - "正式通知账号未开通时不得进入联调"
  risk_flags:
    - performance_risk
  milestone_ref: M1
  reopen_count: 0
  current_state_ref: task-state-001
  next_action: wait_for_dependency | start_dev | request_review | enter_verification | close_task
```

建议首版字段语义固定为：

- `instance_status`：只表达任务主生命周期，不直接承载所有辅助判断
- `reviewer_config`：由 `ownership_map`、`interface_contracts`、`task_type` 等共同推导
- `implementation_requirements`：承接接口、NFR、readiness 等硬约束
- `verification_requirements`：承接测试、可观测性、验收切口等验证要求
- `blocker_conditions`：表达“满足前不得推进”的条件，而不是普通备注
- `reopen_count`：用于区分一次完成和多轮返工，不重新生成新实例

### 5. 任务实例化规则

我建议阶段 3 初始化时，至少按下面顺序完成实例化：

1. 读取 `stage3_entry_contract.startup_required_artifacts`
2. 选择 `implementation_entry_packet.included_artifacts` 中允许进入 runtime 的任务相关对象
3. 从 `task_tree` 中筛出可执行叶子节点
4. 根据 `ownership_map` 绑定 owner 与评审责任
5. 根据 `implementation_plan` 计算波次、优先级和前置顺序
6. 根据 `interface_contracts`、`readiness_report`、`dependency_readiness_packet` 注入约束
7. 根据 `risk_register`、`carry_over_risks` 注入风险标记和附加验证要求
8. 输出 `task_instance` 与初始 `task_state`

进一步约束为：

- 依赖未满足的任务可以被实例化，但初始状态应为 `blocked` 或 `draft`，而不是假装 `ready`
- 缺 owner、缺 scope 边界、缺验证要求的任务，不应进入 `ready`
- 任务实例化是受控编译过程，不是简单把 `task_tree` 平铺成列表

### 6. 建议补的正式对象：`task_state`

我建议把 `task_state` 视为 `task_instance` 的独立运行时快照，而不是直接复用 `instance_status` 一列文本。

建议首版对象抽象为：

```yaml
task_state:
  task_state_id: task-state-001
  task_instance_id: taski-001
  state_type: draft | ready | in_progress | awaiting_review | review_rejected | in_fix | awaiting_verification | verification_failed | blocked | done | cancelled
  entered_at: 2026-04-19T10:00:00Z
  entered_reason: runtime_initialized
  evidence_refs: []
  active_blockers: []
  pending_actions:
    - assign_dev_work
  retry_from_state: null
  next_state_candidates:
    - in_progress
    - blocked
```

建议边界固定为：

- `task_instance` 负责保存稳定的执行上下文
- `task_state` 负责记录“当前这一步是什么状态、为何进入、接下来可去哪”
- `review_result`、`verification_result`、`bug_report`、`blocker_record` 都是挂接对象，不替代主状态机

### 7. 任务主状态机建议

我建议阶段 3 的首版任务主状态机固定为下面这条主链：

```text
draft
-> ready
-> in_progress
-> awaiting_review
-> awaiting_verification
-> done
```

并允许挂接下面三类受控回退：

```text
ready / in_progress / awaiting_review / awaiting_verification
-> blocked

awaiting_review
-> review_rejected
-> in_fix
-> awaiting_review

awaiting_verification
-> verification_failed
-> in_fix
-> awaiting_verification
```

进一步约束为：

- `blocked` 是暂停推进，不等于失败关闭
- `review_rejected` 和 `verification_failed` 是有原因的回退态，不应直接吞并成普通 `in_fix`
- `done` 必须建立在最新一轮 review / verification 证据成立的前提上
- `cancelled` 只用于任务被上游撤销、并入其他任务或 scope 被正式移出，不应用来假装“做不下去”

### 8. review、verification、bug、reopen 如何挂到状态机上

这是议题 2 的关键。

我建议首版按下面方式挂接：

#### `review_result`

- 当任务从 `in_progress` 提交审查时，进入 `awaiting_review`
- 若主评审与必审人按 `approval_policy` 通过，则进入 `awaiting_verification`
- 若被拒绝，则生成 `review_result = rejected`，主状态进入 `review_rejected`，随后转 `in_fix`

#### `verification_result`

- 当任务完成开发并满足送测条件后，进入 `awaiting_verification`
- 若验证通过，则进入 `done`
- 若验证失败，则生成 `verification_result = failed`，主状态进入 `verification_failed`，随后转 `in_fix`

#### `bug_report`

- `bug_report` 不直接等于任务状态
- 它应作为挂接对象，记录 defect 来源、严重级别、是否阻断、是否要求 reopen
- 若 bug 证明任务完成态失效，则任务从 `done` 或 `awaiting_verification` 被 reopen 到 `in_fix`

#### `blocker_record`

- blocker 可发生在任意未完成态
- blocker 打开时，任务进入或保持 `blocked`
- blocker 关闭后，任务回到 `retry_from_state` 指向的上一个推进态，而不是强制从头开始

#### `reopen`

- reopen 是事件，不是长期状态
- reopen 的作用是把任务从 `done`、`awaiting_review` 或 `awaiting_verification` 等状态重新送回 `in_fix` 或 `in_progress`
- 每次 reopen 都应增加 `reopen_count`，并写明触发原因：`review_reject` / `verification_fail` / `bug_confirmed` / `scope_adjusted`

### 9. 建议补的关键事件

我建议首版至少固定下面这些任务事件：

- `task_instantiated`
- `task_ready`
- `task_started`
- `review_requested`
- `review_passed`
- `review_rejected`
- `verification_requested`
- `verification_passed`
- `verification_failed`
- `bug_linked`
- `task_reopened`
- `blocker_opened`
- `blocker_cleared`
- `task_completed`
- `task_cancelled`

这样运行时表达会更清晰：

- 状态回答“现在处于哪里”
- 事件回答“为什么发生变化”
- 挂接对象回答“变化的证据和上下文是什么”

### 10. 我建议先固定的最小结论

基于当前阶段 2 已完成的 formalization，我建议把议题 2 先收敛成下面这版：

- `task_tree` 不能直接当 runtime 任务列表，必须投影为 `task_instance`
- `task_instance` 至少要继承 owner、依赖、评审要求、接口约束、验证要求、blocker 条件和风险标记
- `task_state` 应作为独立运行时对象存在，而不是只靠一个字符串字段表达全过程
- review / verification / bug / blocker 都应挂到同一任务生命周期，而不是裂变成多套平行状态机
- reopen 默认不新建任务实例，只有 split / replan / replace 才创建新实例
- 议题 2 收稳后，下一步再进入 `议题 3：单任务流水线设计`

## 十四、议题 3：单任务流水线设计

在议题 2 里，我们已经把“任务如何进入 runtime”收稳了；议题 3 要回答的则是：

> **一个 `task_instance` 从开始执行到最终完成，中间到底要经过哪些受控步骤，哪些证据是必需的，失败后怎样回到修复回路，而不是凭口头说“已经做完”。**

换句话说：

- 议题 2 解决“任务是什么、现在处于什么状态”
- 议题 3 解决“任务在一次完整交付回路中怎样流转”

### 1. 单任务流水线要解决什么问题

我建议先把议题 3 的目标收敛成下面六类：

- 开发、自测、审查、验证、修复不能只靠习惯推进，必须有正式顺序
- 不是代码提交了就算任务完成，必须有可核验的交付证据
- review 与 verification 都应成为任务主流水线中的正式节点，而不是附带动作
- `TDD` 应作为可配置执行策略进入 runtime，而不是留在口头要求里
- verification fail、review reject、bug reopen 需要回到统一修复回路
- “无新鲜证据不宣称成功”必须成为阶段 3 的系统规则，而不是个人自觉

### 2. 单任务流水线的建议主链

我建议阶段 3 的首版单任务流水线固定为下面这条主链：

```text
ready
-> in_progress
-> self_check
-> awaiting_review
-> awaiting_verification
-> delivery_ready
-> done
```

各节点语义建议固定为：

- `ready`：任务已具备启动条件，但尚未开始实际执行
- `in_progress`：进入实现、改动、补测试、准备交付物的主执行阶段
- `self_check`：owner 完成自检，确认最小证据已产生，准备提交评审
- `awaiting_review`：等待主评审和必审人给出正式结论
- `awaiting_verification`：等待任务级验证结论，包括测试、联调、验证命令或结构化检查
- `delivery_ready`：review 与 verification 已通过，正在收拢交付摘要与最终证据
- `done`：交付物、证据、状态都已闭环，任务可计入阶段完成集合

进一步约束为：

- `done` 之前必须经过 `delivery_ready`，避免“通过了但没沉淀交付物”
- `self_check` 不等于 review，它是 owner 对自己提交质量的门槛
- `awaiting_review` 和 `awaiting_verification` 都是正式等待态，不能用一句“测过了”替代

#### 一张简化单任务流水线图

```text
ready
  |
  v
in_progress
  |
  v
self_check
  |
  v
awaiting_review ----reject----> review_rejected
  |                               |
  | pass                          v
  v                            in_fix
awaiting_verification             |
  |                               |
  | pass                          +----> self_check
  v
delivery_ready
  |
  v
done

awaiting_verification --fail--> verification_failed --+ 
                                                       |
                                                       v
                                                     in_fix
```

### 3. 每个步骤至少应产出什么证据

我建议把“单任务完成”建立在最小证据集合上，而不是只看状态流转。

建议首版先固定下面这组证据要求：

- `in_progress`：至少形成可追踪的改动上下文，如 `code_patch`、配置修改、文档变更或实现说明
- `self_check`：至少形成 `self_check_report`，说明自测范围、通过结果、未覆盖项和已知限制
- `awaiting_review`：至少形成 `review_submission`，包含变更摘要、影响范围、风险提醒、请求评审对象
- `awaiting_verification`：至少形成 `verification_request`，明确验证命令、验证环境、验证对象、通过标准
- `delivery_ready`：至少形成 `task_delivery_candidate`，包含 summary、changed_files、verification evidence、open issues
- `done`：至少形成最终 `task_delivery_record`，并绑定最新 `review_result` 与 `verification_result`

进一步约束为：

- 没有新证据，不允许从 `in_fix` 直接重新宣称完成
- 没有结构化交付记录，不允许从 `awaiting_verification` 直接跳到 `done`
- “我本地看过没问题”只能作为 `self_check_report` 的一部分，不能替代正式验证证据

### 4. 建议补的正式对象：`task_delivery_record`

我建议在阶段 3 补一个正式的任务级交付对象：`task_delivery_record`。

它的作用不是重复 `task_instance`，而是回答：

- 这次交付到底改了什么
- 证据在哪里
- 当前这一轮为何能声称完成
- 还留了哪些已知问题

建议首版对象抽象为：

```yaml
task_delivery_record:
  delivery_record_id: tdr-001
  task_instance_id: taski-001
  delivery_status: draft | review_pending | verification_pending | ready_to_close | closed
  change_summary:
    - "完成评论提交接口实现与输入校验"
  changed_artifacts:
    - backend/comment_controller.py
    - tests/test_comment_submit.py
  self_check_evidence:
    - self-check-001
  review_evidence:
    - review-result-001
  verification_evidence:
    - verification-result-001
  open_issues: []
  known_limits:
    - "压测基线仍待阶段级集成测试补足"
  close_statement: "当前任务范围内目标已完成并具备最新证据"
  next_action: close_task | reopen_for_fix | hold_for_followup
```

建议边界固定为：

- `task_instance` 负责任务运行上下文
- `task_state` 负责当前状态快照
- `task_delivery_record` 负责本轮交付证据和关闭声明

### 5. “无新鲜证据不宣称成功”如何进入流水线

这是议题 3 最关键的一条规则。

我建议首版直接固定为下面这条执行原则：

> **任何任务只有在最新一轮修复之后重新提交了新的 review / verification 证据，才允许重新进入 `delivery_ready` 或 `done`。**

因此建议增加下面三条硬规则：

- 从 `in_fix` 回到 `awaiting_review` 前，必须提交新的 `review_submission`
- 从 `in_fix` 回到 `awaiting_verification` 前，必须提交新的 `verification_request` 或新的验证证据引用
- 若最新变更影响了原有通过结论，旧的 `review_result` / `verification_result` 自动失效，不得复用为完成依据

这样做的原因是：

- 避免“上次通过过，所以这次也算通过”的伪完成
- 避免 fix 后没有重新验证就直接关闭任务
- 让 reopen、修复、重测在系统里形成真正闭环

### 6. `TDD` 在单任务流水线中的位置

我建议不要把 `TDD` 强行做成所有任务都必须经过的一条独立主状态机，而更适合把它建成：

- `task_execution_strategy` 的一种可配置策略
- 在 `in_progress -> self_check` 之间要求额外证据的执行约束

也就是说：

- 对适合 `TDD` 的任务，runtime 应要求先有失败测试或先有测试用例，再进入主要实现
- 对环境配置、纯运维协作、资料整理等不适合 `TDD` 的任务，不应强行套用

我建议首版支持三类策略：

- `tdd_required`
- `tdd_preferred`
- `direct_implementation`

建议最小语义为：

- `tdd_required`：没有测试先行证据，不得进入 `self_check`
- `tdd_preferred`：默认推荐测试先行，但允许给出理由后按直接实现推进
- `direct_implementation`：任务按普通实现流水线推进，不强制测试先行

### 7. 建议补的正式对象：`task_execution_strategy`

为了避免 `TDD` 只停留在口头层，我建议补一个轻量对象：`task_execution_strategy`。

```yaml
task_execution_strategy:
  task_instance_id: taski-001
  strategy_type: tdd_required | tdd_preferred | direct_implementation
  required_preconditions:
    - "若为 tdd_required，需先提交 failing test evidence"
  self_check_minimums:
    - "提供本轮自测结论"
    - "提供关键 verification command 结果"
  review_entry_requirements:
    - "提供变更摘要与影响范围"
  verification_entry_requirements:
    - "提供验证命令、验证环境与预期结果"
  bypass_reason: null
  next_action: continue_execution | request_exception | revise_strategy
```

建议职责边界固定为：

- `task_instance` 回答“任务是什么”
- `task_execution_strategy` 回答“这个任务按什么执行策略推进”
- `task_delivery_record` 回答“这轮交付凭什么可以关闭”

### 8. review / verification / fix 回路怎样串起来

我建议单任务流水线至少支持下面两条标准修复回路：

#### review 修复回路

```text
awaiting_review
-> review_rejected
-> in_fix
-> self_check
-> awaiting_review
```

语义是：

- 被拒绝后先回到修复态
- 修复完成后必须重新自检
- 自检后再重新提交评审

#### verification 修复回路

```text
awaiting_verification
-> verification_failed
-> in_fix
-> self_check
-> awaiting_verification
```

语义是：

- 验证失败后不允许跳过自检直接回测
- fix 后先由 owner 对修复结果负责
- 自检通过后再重新进入验证

进一步约束为：

- `in_fix` 是统一修复态，但进入原因必须可追踪
- 修复回路结束后，必须带着新证据重返 review 或 verification
- 一个任务可以多轮循环，但每一轮都要有新的交付记录和证据链

### 9. 单任务完成判定

我建议首版把任务完成条件固定为最小四件套：

- 主状态达到 `delivery_ready`
- 最新一轮 `review_result` 为通过
- 最新一轮 `verification_result` 为通过
- `task_delivery_record.delivery_status = closed`

进一步补一条否定规则：

- 只要存在未关闭 blocker、失效证据、必审人缺席或验证结果过期，任务都不得进入 `done`

### 10. 我建议先固定的最小结论

基于当前阶段 3 的 formalization 进度，我建议把议题 3 先收敛成下面这版：

- 单任务流水线必须显式包含 `self_check`、`review`、`verification`、`delivery` 四类关键节点
- `done` 不能只由状态推进得到，必须由最新证据和交付记录共同支撑
- “无新鲜证据不宣称成功”应成为 fix / reopen 后的硬规则
- `TDD` 更适合作为任务执行策略，而不是强制所有任务共享的一条固定主链
- review reject 和 verification fail 都应回到统一的 `in_fix -> self_check` 修复回路
- 议题 3 收稳后，下一步再进入 `议题 4：多任务并行与依赖调度`

## 十五、议题 4：多任务并行与依赖调度

当议题 2 和议题 3 收稳后，阶段 3 的下一个核心问题就不再是“一个任务怎么做”，而是：

> **多个 `task_instance` 在同一阶段里如何并行推进、何时必须等待、谁会阻塞谁、哪些失败会引发局部重排或级联阻塞。**

换句话说：

- 议题 3 解决单任务闭环
- 议题 4 解决多任务之间如何不失控地一起跑

### 1. 多任务并行调度要解决什么问题

我建议先把议题 4 要解决的问题收敛成下面六类：

- `task_instance` 已经存在，但还没有正式的调度语义
- 不是所有任务都能一拿到就开工，必须区分可并行、需串行、待依赖解除
- 阶段 2 的 `task_tree`、`ownership_map`、`implementation_plan`、`milestone_plan`、`risk_register` 中已经包含调度线索，阶段 3 不能丢掉
- `blocked` 不只是单任务问题，还会影响下游任务、汇合点和阶段级完成判断
- 多任务不能只靠“大家自己记得先后顺序”，需要 runtime 给出正式可执行顺序
- 并行调度必须允许局部重排，而不是一个任务卡住就把整个阶段冻结

### 2. 调度的最小判断单位

我建议阶段 3 的调度不要直接以“角色”或“workstream”作为最小单位，而应固定为：

- **最小执行单位**：`task_instance`
- **最小依赖单位**：`task_dependency_edge`
- **最小阻塞单位**：`blocker_record`
- **最小汇合单位**：`join_condition`

这样做的原因是：

- 角色会变，但任务实例是 runtime 真正推进的对象
- 阻塞有时来自任务，有时来自外部依赖，不能全塞进任务状态字符串
- 多任务汇合不能只靠肉眼判断，需要显式 join 规则

### 3. 哪些任务可以并行，哪些必须等待

我建议首版把任务关系先分成下面四类：

#### `hard_dependency`

上游未完成，下游不得启动。

例如：

- 后端接口未就绪，前端联调任务不得进入验证
- 环境账号未开通，依赖该账号的接入任务不得启动

#### `soft_dependency`

上游未完成不一定阻断启动，但会影响质量、效率或后续验证。

例如：

- 测试数据准备未完善，开发可以继续编码，但验证任务会受影响
- 可观测性面板未完成，不阻断业务实现，但会阻断完成态关闭

#### `review_dependency`

某任务是否可继续，不取决于上游代码完成，而取决于指定评审结论。

例如：

- 跨接口任务需要前端 / TL 会签后，相关下游任务才能进入联调

#### `join_dependency`

若干并行任务各自可推进，但只有全部达到指定条件后，才能进入汇合节点。

例如：

- 前后端并行开发可以同时进行
- 但“集成测试准备完成”必须等待 FE / BE / 测试准备三个分支都满足 join 条件

进一步约束为：

- 只有 `hard_dependency` 直接决定“能否启动”
- `soft_dependency` 更适合作为风险提醒或阶段内弱约束
- `review_dependency` 强调的是人和结论，不只是代码依赖
- `join_dependency` 解决“并行结束后何时允许汇合”

### 4. 建议补的正式对象：`task_dependency_edge`

我建议把多任务调度里最关键的依赖边显式建模，而不是让依赖只留在 `task_tree` 注释里。

建议首版对象抽象为：

```yaml
task_dependency_edge:
  dependency_edge_id: dep-001
  upstream_task_instance_id: taski-be-001
  downstream_task_instance_id: taski-fe-002
  dependency_type: hard_dependency | soft_dependency | review_dependency | join_dependency
  dependency_reason: "前端联调依赖后端接口稳定"
  satisfaction_rule: upstream_done | upstream_delivery_ready | review_passed | join_group_completed
  impact_if_unsatisfied: block_start | allow_with_risk | block_verification | hold_join
  fallback_route: requeue_downstream | reopen_upstream | raise_blocker | request_replan
  current_status: pending | satisfied | waived | invalidated
```

建议字段边界固定为：

- `dependency_type`：说明依赖是什么性质
- `satisfaction_rule`：说明怎样才算依赖满足
- `impact_if_unsatisfied`：说明不满足时具体影响什么
- `current_status`：说明当前是否已经解除依赖

### 5. 调度器的首版规则

我建议阶段 3 的首版调度器至少按下面顺序工作：

1. 收集所有 `task_instance`
2. 读取 `task_dependency_edge`
3. 读取 `blocker_record` 与 `task_state`
4. 过滤掉 `cancelled` / `done` 任务
5. 判断每个任务当前是否满足启动条件
6. 将任务分成 `ready_now`、`blocked_now`、`waiting_join`、`waiting_review_dependency`
7. 对 `ready_now` 任务再按优先级、波次、owner 负载和里程碑窗口排序
8. 输出当前调度批次和等待原因清单

进一步约束为：

- 调度器不决定任务怎么做，只决定当前允许哪些任务进入推进态
- `ready` 不是全局一次性标签，而是每一轮调度的动态结果
- 调度输出不应只是一个顺序列表，还应显式说明“为什么没被调度”

### 6. 并行批次与汇合规则

我建议阶段 3 显式支持 `fork / join` 语义，而不是只有“谁先谁后”的单链路思维。

建议首版先固定两类并行批次：

- `execution_batch`：当前可以并行推进的一组任务
- `join_group`：必须在某个汇合条件满足后才能继续下游的任务集合

建议语义为：

- 一个 `execution_batch` 内的任务彼此没有 `hard_dependency`
- 一个 `join_group` 内的任务可以异步完成，但其下游汇合任务必须等待 join 条件成立
- join 默认不要求所有任务 `done`，而要求满足预设 `join_condition`

例如：

- FE 开发任务达到 `delivery_ready`
- BE 开发任务达到 `delivery_ready`
- 测试准备任务达到 `ready`

这时就可以放行“集成验证任务”，而不必等所有分支都完全 `done`

#### 一张简化并行 / 汇合图

```text
                 [调度器]
                     |
         +-----------+-----------+
         |                       |
         v                       v
   execution_batch_A       execution_batch_B
   (FE 开发任务)           (BE 开发任务)
         |                       |
         v                       v
   FE.delivery_ready       BE.delivery_ready
         \                       /
          \                     /
           +------ join -------+
                   |
                   v
        测试准备.ready 已满足?
              |否        |是
              v          v
         waiting_join   release
                           |
                           v
                 集成验证 task_instance
```

### 7. 建议补的正式对象：`join_condition`

为了避免并行汇合只靠口头理解，我建议补一个轻量对象：`join_condition`。

```yaml
join_condition:
  join_condition_id: join-001
  join_group_id: integ-join-001
  required_inputs:
    - taski-fe-001: delivery_ready
    - taski-be-001: delivery_ready
    - taski-test-001: ready
  release_task_instance_ids:
    - taski-integration-001
  unmet_behavior: keep_waiting | escalate_blocker | request_replan
  current_status: pending | satisfied | escalated
```

这样阶段 3 就能表达：

- 哪些并行分支可以同时跑
- 何时允许合流
- 合流失败时该继续等、升级 blocker 还是重编排

### 8. blocker 与级联阻塞怎么处理

这是议题 4 的第二个核心。

我建议把 blocker 的影响范围固定分成三层：

- **task_local**：只阻塞当前任务，不影响其他任务
- **dependency_scoped**：阻塞所有直接依赖该任务或该外部条件的下游任务
- **stage_scoped**：影响阶段级关键路径，导致大量任务等待或暂停

例如：

- 某个单测不稳定，可能只是 `task_local`
- 后端接口契约未稳定，可能是 `dependency_scoped`
- 测试环境整体不可用，可能是 `stage_scoped`

我建议进一步固定下面三条规则：

- `blocker_record` 必须显式带 `scope`
- `scope = dependency_scoped` 时，调度器必须自动重算下游可启动集合
- `scope = stage_scoped` 时，不代表全阶段立即停止，而是必须触发一次调度重评估或升级流程

#### 一张简化级联阻塞图

```text
[共享依赖: test-env]
          |
          v
   blocker_record(scope=stage_scoped)
          |
   +------+------+----------------+
   |             |                |
   v             v                v
taski-integ   taski-e2e      taski-release-check
 blocked        blocked            blocked
   |
   +----> 调度器重算 ready_now / waiting_join / blocked_now
```

### 9. 建议补的正式对象：`scheduling_snapshot`

为了让并行调度不是黑盒，我建议补一个运行时快照对象：`scheduling_snapshot`。

```yaml
scheduling_snapshot:
  snapshot_id: sched-001
  generated_at: 2026-04-19T11:00:00Z
  ready_now:
    - taski-fe-001
    - taski-be-001
  blocked_now:
    - taski-integration-001
  waiting_join:
    - taski-integration-001
  waiting_review_dependency: []
  active_blockers:
    - blocker-env-001
  cascade_impacts:
    - blocker-env-001 -> [taski-integration-001, taski-e2e-001]
  scheduling_notes:
    - "前后端开发可并行，集成验证需等待 join 条件满足"
  next_action: dispatch_ready_batch | hold_and_wait | escalate_blocker
```

它的作用是：

- 给 runtime 一个当前调度面的正式快照
- 让用户或 TL 看到“哪些任务能跑、哪些任务在等、为什么在等”
- 为后续调度重排提供可追溯依据

### 10. 哪些失败会导致级联阻塞或调度重排

我建议首版先固定下面三类高影响事件：

- `critical_upstream_failed`：关键上游任务失败，导致多个下游任务从 `ready` 转为等待
- `shared_dependency_blocked`：共享环境、账号、接口或数据依赖失效，导致一组任务同步受阻
- `join_condition_timeout`：并行分支长期无法汇合，必须升级为 blocker 或请求重排

对应调度动作建议为：

- **局部重排**：只调整受影响 workstream 的任务顺序
- **冻结下游**：保持无关任务继续推进，但冻结被影响的依赖链
- **升级处理**：当阻塞达到阶段级关键路径时，转入议题 5 的异常 / 变更 / 回退机制

### 11. 我建议先固定的最小结论

基于当前阶段 3 的 formalization 进度，我建议把议题 4 先收敛成下面这版：

- 多任务调度的最小执行单位应是 `task_instance`，不是角色或文档块
- 阶段 3 需要显式建模 `task_dependency_edge`，否则并行与等待无法 formalize
- 并行调度至少应支持 `execution_batch`、`join_group`、`join_condition` 三层语义
- `blocked` 必须支持作用域区分，否则无法表达级联阻塞
- 调度器每一轮都应输出 `scheduling_snapshot`，说明谁能跑、谁在等、为什么在等
- 议题 4 收稳后，下一步再进入 `议题 5：执行期异常、bug、变更与回退`

## 十六、议题 5：执行期异常、bug、变更与回退

当议题 2、议题 3、议题 4 收稳后，阶段 3 的下一个核心问题就不再是“任务能不能推进”，而是：

> **执行过程中出现异常时，runtime 如何判断这是普通修复、局部阻塞、设计缺口、需求变更，还是需要正式回退到前置阶段。**

换句话说：

- 议题 3 解决单任务闭环
- 议题 4 解决多任务调度闭环
- 议题 5 解决执行异常如何不把阶段边界冲垮

### 1. 议题 5 要解决什么问题

我建议先把议题 5 要解决的问题收敛成下面六类：

- bug 可能在 `self_check`、`review`、`verification`、`integration` 多个入口被发现，不能每次都临时判断
- `review_rejected`、`verification_failed`、`bug_report.confirmed` 都会导致 reopen，但 reopen 的责任边界和证据失效规则必须统一
- 不是所有异常都属于实现缺陷，有些其实是环境阻塞、设计缺口或需求变更
- 阶段 3 必须能区分“继续在当前任务修”与“必须回退到阶段 2 / 阶段 1”
- 回退不应只理解为代码回滚，还包括调度回退、证据失效、阶段级重开
- 一旦异常影响已通过结论，下游任务、join 条件和阶段出口判断都必须同步重算

### 2. 执行期异常的最小分类

我建议阶段 3 首版先把异常分成下面五类。

#### `implementation_defect`

在已批准范围、已批准方案、已批准接口约束内，当前实现没有满足预期。

例如：

- 代码逻辑错误
- 配置错误
- 边界条件漏处理
- 回归缺陷

默认路由：留在阶段 3，通过 `reopen -> in_fix` 修复。

#### `execution_blocker`

任务不是因为实现错误失败，而是因为环境、账号、数据、依赖或外部协作条件暂时不可用。

例如：

- 测试环境异常
- 外部接口不可用
- 联调账号未开通
- 关键依赖任务长时间未满足 join 条件

默认路由：生成或升级 `blocker_record`，由调度器重算影响面，而不是假装这是普通 bug。

#### `design_gap`

执行时发现当前 `solution_summary`、`interface_contracts`、`implementation_plan` 或 `nfr_design_mapping` 不能支撑继续实现。

例如：

- 接口契约缺字段，无法完成联调
- 原方案遗漏关键容错链路
- 当前设计无法满足既定 NFR 目标
- 任务拆解方式已无法覆盖真实实施路径

默认路由：升级为 `change_request`，并回退到阶段 2 的对应主线。

#### `requirement_change`

执行期发现“要做什么”本身变了，而不是“怎么做”出了问题。

例如：

- 验收口径变化
- MVP 边界变化
- 关键角色新增或删除能力点
- NFR 目标被正式改写

默认路由：升级为 `change_request`，并回退到阶段 1 的范围 / 验收 / 需求口径主线。

#### `evidence_invalidation`

最新变更、重开或回退动作使旧的通过证据失效。

例如：

- fix 之后旧的 `review_result` 已不再覆盖最新改动
- join 上游回退导致下游原验证结论不再成立
- 已关闭任务被 reopen，原 `task_delivery_record` 不再可直接复用

默认路由：标记旧证据失效，相关任务重新进入 review / verification 闭环。

我建议进一步固定下面五条分类原则：

- “能否继续在原范围内修掉”是区分 `implementation_defect` 与 `design_gap` 的第一标准
- “是不是条件暂时不可用”是区分 `execution_blocker` 与其他类型的第一标准
- “是不是连范围 / 验收口径都变了”是区分 `requirement_change` 与 `design_gap` 的第一标准
- “旧证据是否还有效”必须单独判断，不能因为问题修好了就默认证据仍然有效
- 异常分类一旦变化，原路由决定也必须允许被更新

### 3. `bug_report` 如何进入主线

`bug_report` 在阶段 3 里不应只是一个问题登记条目，而应是可以驱动 reopen、阻塞升级和回退判断的正式入口对象。

我建议它至少支持下面这些来源：

- `self_check` 中发现的实现缺陷
- `review` 中指出的错误实现或遗漏影响
- `verification` 中暴露的失败结果
- `integration` 或回归验证中发现的跨任务问题

建议首版对象抽象为：

```yaml
bug_report:
  bug_report_id: bug-001
  source_task_instance_id: taski-fe-001
  discovered_in: self_check | review | verification | integration | regression
  symptom_summary: "登录页调用接口返回 500"
  suspected_category: implementation_defect | environment_issue | contract_mismatch | unknown
  severity: low | medium | high | critical
  impact_scope: current_task | dependency_chain | stage_exit
  triage_status: pending | confirmed | rejected | duplicate | deferred
  route_action: reopen_current_task | create_fix_task | raise_blocker | request_stage2_replan
  linked_evidence:
    - verification_result: verify-009
  owner: fe_owner
```

建议路由规则固定为：

- 所有 `bug_report` 先经过 triage，再决定是 reopen、raise blocker 还是 request replan
- `triage_status = confirmed` 且根因属于实现缺陷时，默认 `route_action = reopen_current_task`
- 若问题影响多个已交付任务，可新建 fix task，但必须保留与原 `task_instance`、`task_delivery_record` 的关联
- 若根因属于环境或共享依赖，不应用 bug closure 掩盖，而应转为 `blocker_record`
- 若 triage 发现本质是设计缺口或需求变化，应升级为 `change_request`，而不是继续在 bug 流里打转

### 4. review reject、verification fail、bug confirm 如何重开任务

我建议阶段 3 把下面三类事件都统一收敛为受控的 `reopen` 动作：

- `review_result = rejected`
- `verification_result = failed`
- `bug_report.triage_status = confirmed`

默认主链可以简化为：

```text
review_rejected ---------> reopen(reason=review_rejected)
verification_failed -----> reopen(reason=verification_failed)
bug_report.confirmed ----> reopen(reason=confirmed_bug)
                                   |
                                   v
                                 in_fix
                                   |
                                   v
                               self_check
                                   |
                    +--------------+--------------+
                    |                             |
                    v                             v
             awaiting_review              awaiting_verification
```

我建议进一步固定下面六条规则：

- 默认先 reopen 原 `task_instance`，而不是一发现问题就新建任务
- 只有任务边界被正式拆分、替换、合并或重排时，才允许改为新建 fix task
- `done` 状态的任务一旦 reopen，相关 `task_delivery_record` 立即降级为非关闭态
- `reopen` 必须带原因、触发来源、影响范围和失效证据列表，不能只改一个状态值
- `reopen` 之后若影响下游依赖，调度器必须同步重算 `task_dependency_edge`、`join_condition`、`scheduling_snapshot`
- reopen 后重新关闭任务时，必须遵守“无新鲜证据不宣称成功”规则

### 5. 建议补的正式对象：`change_request`

当问题已经不是普通实现缺陷，而是执行中发现设计缺口、依赖条件变化或需求口径变化时，我建议补一个正式对象：`change_request`。

```yaml
change_request:
  change_request_id: cr-001
  source_task_instance_id: taski-integration-001
  trigger_source: bug_report | review_result | verification_result | blocker_record | manual_raise
  change_type: design_gap | requirement_change | dependency_change | risk_escalation
  summary: "现有接口契约缺少批量查询字段，无法完成联调"
  affected_baselines:
    - interface_contracts
    - solution_summary
    - implementation_plan
  impact_scope: current_task | dependency_chain | stage_scope
  recommended_route: continue_in_stage3 | return_to_stage2 | return_to_stage1 | rollback_then_replan
  suspend_task_instance_ids:
    - taski-fe-001
    - taski-integration-001
  decision_owner: tl_or_pm
  decision_status: draft | triaging | approved | rejected | routed
```

建议字段职责固定为：

- `change_type`：说明变更本质是什么
- `affected_baselines`：说明打穿了哪些既有基线
- `recommended_route`：说明建议继续修、回阶段 2、回阶段 1，还是先 rollback 再重排
- `suspend_task_instance_ids`：说明哪些任务应先冻结，防止错误继续扩散

### 6. 什么时候继续在阶段 3 修，什么时候回退

我建议阶段 3 首版至少固定下面这组判定边界。

继续留在阶段 3 修的典型条件：

- 范围基线没有变
- 验收口径没有变
- 方案和接口主约束没有变
- 只需要修改代码、配置、测试或局部执行顺序
- 现有 `task_instance` 结构仍足以承载修复

应回退到阶段 2 的典型条件：

- `solution_summary` 已不足以解释怎么做
- `interface_contracts` 需要重新定义或扩大影响面
- `implementation_plan` / `task_tree` / 依赖图需要重拆或重排
- `nfr_design_mapping` / `constraint_to_design_map` 显示当前设计无法满足既定 NFR
- 阶段 2 gate 的条件项或依赖 readiness 前提已被证明失效

应回退到阶段 1 的典型条件：

- `approved_scope_version` 发生正式变化
- MVP / 非 MVP 边界改变
- 验收标准、业务规则或目标用户理解发生变化
- NFR 目标本身被改写，而不只是实现不达标

这里我建议加一条硬边界：

> **阶段 3 可以修实现，但不能擅自改范围；可以修方案落地细节，但不能偷偷改写阶段 2 已批准的设计基线。**

### 7. 建议补的正式对象：`rollback_decision`

为了避免“回退”只有口头语义，我建议再补一个轻量对象：`rollback_decision`。

```yaml
rollback_decision:
  rollback_decision_id: rb-001
  trigger_source_type: bug_report | change_request | blocker_record | gate_revalidation
  trigger_source_id: cr-001
  rollback_scope: current_task | dependency_chain | execution_batch | return_to_stage2 | return_to_stage1
  rollback_reason: implementation_defect | design_gap | requirement_change | dependency_failure | evidence_invalidated
  affected_task_instance_ids:
    - taski-fe-001
    - taski-integration-001
  required_resets:
    - invalidate_review_result
    - invalidate_verification_result
    - freeze_downstream_tasks
  reentry_condition:
    - "阶段 2 更新 interface_contracts 后重新实例化受影响任务"
  decision_owner: tl_or_pm
  decision_status: draft | approved | executing | completed | cancelled
```

它要回答的不是“要不要 git revert”这么窄的问题，而是：

- 回退影响哪些任务或依赖链
- 哪些通过证据必须作废
- 哪些任务需要冻结或重排
- 何时允许重新进入阶段 3 主线

### 8. 回退动作应落到哪几层

我建议把 rollback 的作用层次固定分成三层：

- **任务级回退**：当前任务从 `done` / `delivery_ready` / `awaiting_verification` 回到 `in_fix` 或 `ready`
- **调度级回退**：冻结一组下游任务、撤销 join 放行、重算 `scheduling_snapshot`
- **阶段级回退**：正式返回阶段 2 或阶段 1，等待基线更新后再重新进入阶段 3

进一步约束为：

- rollback 既可能伴随代码回滚，也可能只是状态、证据和调度权限回退
- 只要 rollback 影响了已满足的依赖边，相关 `task_dependency_edge.current_status` 就不得继续保留为 `satisfied`
- 只要 rollback 影响了 join 输入，相关 `join_condition.current_status` 就必须重新计算
- 阶段级回退期间，受影响任务不得假装继续推进，只能保持冻结、blocked 或 routed 状态

                    |
                    v
            issue_detected / signal_raised
                    |
                    v
              [triage / classify]
   +----------------+----------------+----------------+----------------+
   |                |                |                |                |
   v                v                v                v                v
implementation  execution_blocker   design_gap   requirement_change  evidence_invalid
   defect             |                |                |                |

   |                  |                |                |            pass evidence

### 10. 我建议先固定的最小结论

基于当前阶段 3 的 formalization 进度，我建议把议题 5 先收敛成下面这版：

- `bug_report`、`blocker_record`、`change_request`、`rollback_decision` 应分别承担缺陷、阻塞、变更、回退四类不同职责
- `review_rejected`、`verification_failed`、`bug_report.confirmed` 都应通过统一 `reopen` 动作回到受控修复链
- `implementation_defect` 默认留在阶段 3 修，`design_gap` 默认回阶段 2，`requirement_change` 默认回阶段 1
- rollback 不只是代码回滚，还包括证据失效、依赖撤销、下游冻结和阶段级重开
- 任何会影响既有通过结论的变更，都必须触发 `evidence_invalidation` 判断
- 议题 5 收稳后，下一步再进入 `议题 6：阶段 3 完成条件与阶段 4 交接`

## 十七、议题 6：阶段 3 完成条件与阶段 4 交接

当议题 2 到议题 5 都已经有了首版 runtime 语义后，阶段 3 的最后一个核心问题就不再是“任务怎么跑”，而是：

> **什么情况下才能正式说阶段 3 已完成，并把执行产物、验证证据和未决风险交给阶段 4 消费。**

换句话说：

- 议题 3 解决单任务完成
- 议题 4 解决多任务收敛
- 议题 5 解决异常与回退
- 议题 6 解决阶段出口与验收入口

### 1. 议题 6 要解决什么问题

我建议先把议题 6 要解决的问题收敛成下面六类：

- 单个 `task_instance.done` 不等于整个阶段已经可进入验收
- 阶段 3 需要把“实现完成”“集成通过”“可进入阶段 4 验收”三层语义拆开
- 不能只统计完成任务数量，还要显式判断 blocker、bug、NFR 证据和例外项
- 集成测试要有正式位置，否则阶段出口会变成“大家都说差不多好了”
- 阶段 4 不应重新从零拼装阶段 3 的结果，必须接收正式 handoff 包
- 即使存在 carry-over issue，也必须明确哪些允许带入阶段 4，哪些绝对不允许

### 2. 阶段 3 完成，不等于所有任务都 done

我建议把阶段 3 的完成语义固定分成三层：

#### 任务完成

说明单个 `task_instance` 已完成自身的 review、verification、delivery 闭环。

#### 集成完成

说明关键 join 路径上的多个任务已经满足集成条件，并形成了正式的 `integration_report`。

#### 阶段完成

说明当前版本范围内要求进入验收的内容，已经达到“足以进入阶段 4”的状态。

这三层的关系不是并列的，而是：

```text
task done / delivery_ready
          |
          v
   integration passed
          |
          v
stage3 completion ready
          |
          v
 acceptance_entry_packet
```

我建议进一步固定下面四条边界：

- 任务 `done` 是阶段完成的必要条件之一，但不是充分条件
- 集成通过是阶段完成的重要前提，但仍不等于正式用户验收通过
- 阶段 3 可以为阶段 4 做好验收准备，但不替代阶段 4 的业务确认
- 任何关键 blocker、关键 bug、未完成的回退动作，都会阻断阶段完成判定

### 3. 集成测试在阶段 3 的位置

我建议把集成测试正式放在阶段 3 的后段，而不是阶段 4。

原因是：

- 集成测试验证的是“设计出来的多块东西能不能一起工作”
- 阶段 4 验收验证的是“交付结果是否满足业务目标与验收口径”
- 如果把集成问题拖到阶段 4 才暴露，阶段边界会失真

因此建议把集成测试的角色固定为：

- 承接 `join_condition` 释放后的跨任务验证
- 覆盖关键主链路、关键依赖链路、关键回归链路
- 输出阶段级通过 / 不通过 / 带风险通过结论
- 为 `stage3_completion_report` 提供关键输入

进一步约束为：

- 没有完成关键 join 的任务集合，不得宣称已完成集成测试
- 集成测试失败默认留在阶段 3 处理，不得直接丢给阶段 4 验收兜底
- 集成测试结论若依赖特定环境、数据或 mock 条件，必须显式记录在报告里

### 4. 建议补的正式对象：`integration_report`

为了避免集成测试只留在口头层，我建议把它 formalize 成 `integration_report`。

```yaml
integration_report:
  integration_report_id: integ-001
  source_join_group_id: integ-join-001
  covered_task_instance_ids:
    - taski-fe-001
    - taski-be-001
    - taski-test-001
  execution_environment: test_env_a
  executed_scenarios:
    - "用户登录主链路"
    - "异常重试链路"
  result_status: passed | failed | passed_with_risk | blocked
  blocking_findings:
    - "支付回调在超时场景下未闭环"
  linked_bug_reports:
    - bug-201
  nfr_observations:
    - "P95 延迟接近阈值，建议阶段 4 验收重点观察"
  recommended_action: proceed_to_completion_check | reopen_tasks | request_replan
```

建议字段职责固定为：

- `covered_task_instance_ids`：说明这轮集成验证覆盖了哪些任务输出
- `executed_scenarios`：说明验证了哪些关键路径，而不是模糊地说“联调通过”
- `result_status`：说明是通过、失败、带风险通过还是被阻断
- `recommended_action`：说明下一步是进入完成判断、回开任务还是请求重排

### 5. 建议补的正式对象：`task_delivery_summary`

单任务里我们已经有 `task_delivery_record`，但到了阶段出口，我建议再补一个汇总层对象：`task_delivery_summary`。

```yaml
task_delivery_summary:
  summary_id: tds-001
  scope_version: scope-v3
  included_task_instance_ids:
    - taski-fe-001
    - taski-be-001
    - taski-test-001
  completed_tasks:
    - taski-fe-001
    - taski-be-001
  cancelled_tasks:
    - taski-spike-009
  blocked_tasks: []
  deferred_items:
    - "监控看板优化留到后续版本"
  unresolved_bug_refs: []
  evidence_refs:
    - task_delivery_record: tdr-001
    - verification_result: verify-018
  summary_status: draft | review_ready | accepted
```

它回答的不是单任务“做完没”，而是：

- 当前范围内哪些任务已交付
- 哪些任务被正式取消或移出
- 哪些事项被明确延期
- 阶段出口引用的是哪些完成证据

### 6. 阶段 3 的最小完成条件

我建议首版把阶段 3 的完成条件固定成下面这组六项。

#### 必须满足的硬条件

- `approved_scope_version` 内要求进入验收的任务，已 `done`、已正式 `cancelled`，或被正式移出本次范围
- 不存在未关闭的 `stage_scoped blocker`
- 不存在会直接破坏验收主链路的 `critical` / `high` 级未决 bug
- 关键 join 路径已完成集成验证，并形成 `integration_report.result_status = passed | passed_with_risk`
- 所有受影响任务的最新 `review_result`、`verification_result` 仍然有效
- 所有已批准的 `change_request`、`rollback_decision` 都已执行到可重新稳定判断的状态

#### 允许带入阶段 4，但必须显式声明的事项

- 不影响核心验收链路的低优先级 bug
- 已知但已接受的 monitor 类 NFR 风险
- 不属于本次 MVP 验收范围的 deferred item
- 已记录 workaround 且不会扭曲验收结论的环境限制

这里我建议加一条硬规则：

> **阶段 3 完成判定必须是“可解释的完成”，而不是“看起来差不多都做了”。**

### 7. 建议补的正式对象：`stage3_completion_report`

为了把完成判定本身 formalize，我建议补一个阶段级对象：`stage3_completion_report`。

```yaml
stage3_completion_report:
  completion_report_id: s3c-001
  scope_version: scope-v3
  completion_status: draft | blocked | ready_for_acceptance | conditionally_ready | rolled_back
  task_delivery_summary_ref: tds-001
  integration_report_refs:
    - integ-001
  open_blockers: []
  open_bug_summary:
    critical: 0
    high: 0
    medium: 1
  nfr_completion_view:
    mandatory_checks_passed:
      - security_baseline
      - logging_baseline
    carry_over_observations:
      - "容量压测仅完成首轮"
  deferred_items:
    - "监控大盘优化不纳入本次验收"
  stage4_readiness:
    can_enter: true
    required_attention:
      - "阶段 4 需重点关注高并发下的响应波动"
  recommended_action: generate_acceptance_entry_packet | hold_stage3 | reopen_execution
```

建议字段职责固定为：

- `completion_status`：说明阶段 3 当前是 blocked、可进入验收，还是只能带条件进入
- `open_bug_summary`：说明仍带着哪些遗留问题进入判断
- `nfr_completion_view`：说明 NFR 是已满足、部分满足还是带观察项进入阶段 4
- `stage4_readiness`：说明阶段 4 是否可启动，以及需要重点关注什么

### 8. 建议补的正式对象：`acceptance_entry_packet`

阶段 4 不应该自己去翻散落的任务记录，我建议阶段 3 在出口处生成正式的 `acceptance_entry_packet`。

```yaml
acceptance_entry_packet:
  acceptance_entry_id: aep-001
  source_stage3_completion_report_id: s3c-001

    - "失败回退链路"

  excluded_from_acceptance:
    - "后续版本的看板美化"
  demo_or_validation_scenarios:
    - "正常下单"
    - "库存不足"
  recommendation: enter_stage4 | hold_for_fix
```

我建议阶段 4 至少直接消费它里面的这些信息：

- 当前验收针对的正式范围版本
- 阶段 3 已完成的任务与集成结论
- 关键验证证据与演示 / 验收场景
- 已知问题、延期项、非验收项
- 对阶段 4 的重点关注提醒

### 10. 我建议先固定的最小结论

基于当前阶段 3 的 formalization 进度，我建议把议题 6 先收敛成下面这版：

- 阶段 3 完成必须区分任务完成、集成完成、阶段完成三层语义
- 集成测试属于阶段 3 后段的正式工作，不应外溢到阶段 4 去兜底
- `integration_report`、`task_delivery_summary`、`stage3_completion_report`、`acceptance_entry_packet` 应构成阶段出口的最小对象链
- 阶段完成判定必须同时检查 blocker、bug、NFR、回退状态和范围覆盖，而不只是看任务 done 数量
- 阶段 4 应消费正式的 `acceptance_entry_packet`，而不是自己回头拼接阶段 3 证据

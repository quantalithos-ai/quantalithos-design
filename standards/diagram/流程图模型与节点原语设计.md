# 流程图模型与节点原语设计

> 讨论如何将标准流程图（ISO 5807 / BPMN 2.0）的图形元素映射到 quantalithos-flow 的工作流模板，
> 使工作流模板能够完整表达流程图，支持可视化渲染。

---

## 一、问题背景

当前 flow 概要设计的工作流模板只有两种节点类型（task / session），只能表达线性流程 + 失败回退。
无法表达项目管理中常见的流程图元素：条件分支、并行分支、人工审批点、循环等。

如果要实现"用户在前端看到完整的项目流程图，并实时看到当前走到哪一步"，
工作流模板必须能完整表达标准流程图的所有图形元素。

---

## 二、标准参考文档

两份标准的完整描述见独立文档：

- [ISO 5807:1985 流程图标准](流程图标准-ISO5807.md) — 16 种基础符号，面向程序逻辑
- [BPMN 2.0 业务流程建模标准](流程图标准-BPMN2.md) — ~50 种符号，面向业务流程

## 三、ISO 5807 与 BPMN 2.0 对比

### 3.1 定位差异

```
ISO 5807 (1985)                         BPMN 2.0 (2013)
────────────────────────────────────────────────────────────────

面向：程序逻辑、数据处理               面向：业务流程、组织协作
年代：1985                              年代：2011 发布，2013 成为 ISO
符号：~16 种                            符号：~50 种
层次：单层                              层次：三层（描述/分析/可执行）
执行：不可执行                          执行：BPMN XML 可被引擎执行
组织：ISO                               组织：OMG → ISO/IEC 19510

一句话区别：
  ISO 5807 回答"程序怎么跑"
  BPMN 2.0 回答"业务怎么跑"
```

### 3.2 符号逐项对比

### 3.3 总结

```
ISO 5807 有但 BPMN 没有的（3 个）：
  - 准备符（Preparation）→ BPMN 用 Task 替代
  - 显示符（Display）→ BPMN 用 Task 替代
  - 手动输入符（Manual Input）→ BPMN 用 User Task 替代

BPMN 有但 ISO 5807 没有的（核心，15+ 个）：
  - 事件系统（30+ 种事件）
  - 多种网关（5 种）
  - 多种任务类型（8 种）
  - 多种子流程类型（5 种）
  - 泳道（Pool / Lane）
  - 消息流
  - 错误/补偿/升级/取消事件
  - 事务子流程
  - 边界事件
  - 活动标记（循环、多实例）
  - 数据对象状态
  - 分组

两者都有的（核心，8 个）：
  - 开始/结束
  - 处理/任务
  - 判断/排他网关
  - 并行
  - 子流程
  - 数据输入/输出
  - 注释
  - 连接符
```

### 3.4 对我们的启示

```
我们的平台是"AI Agent 协作完成软件研发"：

  ✅ 需要角色/职责划分 → 需要 BPMN 的泳道概念
  ✅ 需要多人协作 → 需要 BPMN 的消息流概念
  ✅ 需要等待用户确认 → 需要 BPMN 的事件概念
  ✅ 需要超时处理 → 需要 BPMN 的定时事件
  ✅ 需要错误处理 → 需要 BPMN 的错误事件
  ✅ 需要并行任务 → 需要 BPMN 的并行网关
  ✅ 需要条件分支 → 需要 BPMN 的排他网关
  ⚠️ 需要多人讨论 → ISO 5807 和 BPMN 都没有（我们的 session）
  ❌ 不需要跨组织协作 → 不需要 BPMN 的 Pool 间消息流
  ❌ 不需要事务回滚 → 不需要 BPMN 的事务子流程（Phase 1）

结论：以 BPMN 2.0 为主要参考，ISO 5807 作为基础图形补充。
     session（多人协作讨论）是我们独有的扩展，两个标准都没有。
```

### 4.1 我们需要哪些元素

基于第三章的分析，结合我们的实际场景（AI Agent 协作完成软件研发），逐项判断：

```
┌──────────────────────┬──────────┬──────────┬──────────────────────────────┐
│ 标准元素             │ 来源     │ 是否需要 │ 说明                          │
├──────────────────────┼──────────┼──────────┼──────────────────────────────┤
│ Start / End          │ 两者都有 │ ✅ 需要  │ 流程入口和出口                │
│ Task (处理)          │ 两者都有 │ ✅ 需要  │ Agent 执行任务                │
```

### 4.2 我们独有的扩展：session

ISO 5807 和 BPMN 2.0 都没有直接对应 session（多人实时协作讨论）的图形。

BPMN 最接近的是 Ad-Hoc Sub-Process（临时子流程，内部活动没有固定顺序），但 Ad-Hoc Sub-Process 的参与者仍然是预定义的活动，不是"多人自由讨论"。

session 是我们的平台独有的扩展，保留为独立类型。

## 五、最终方案：BPMN 2.0 三大类建模

> **设计决策：全面转为 BPMN 2.0，去掉 ISO 5807 独有类型**
>
> 原方案中 StepType 混合了 ISO 5807 和 BPMN 2.0 两套标准（16 种类型）。
> 经讨论后全面转为 BPMN 2.0 三大类（EventNode / ActivityNode / GatewayNode），
> ISO 5807 独有类型（PREPARATION/IO/DOCUMENT/MULTI_DOCUMENT/DATA_STORE/CONNECTOR/MANUAL）
> 用 BPMN 标准方式替代。
>
> 详细的数据结构定义见 flow 概要设计第十四章 14.10。

### 5.1 节点分类

```
BPMN 2.0 三大流对象：

  ○ ◎ ⊕    EventNode        事件：流程中发生的事情
            - position: start | intermediate | end | boundary
            - trigger: none | message | timer | signal | error | ...

  ┌──────┐  ActivityNode     活动：需要执行的工作
  └──────┘  - task_type: abstract | user | service | script | send | receive | manual
            - sub_process_type: embedded | call_activity | transaction | event_sub | ad_hoc

    ◇       GatewayNode      网关：控制流程走向
            - gateway_type: exclusive | parallel | inclusive | event_based | complex
            - direction: diverging | converging
```

### 5.2 连接线

```
BPMN 2.0 连接线：

  ──────────>   sequence        顺序流（默认）
  ──◇──────>    conditional     条件顺序流
  ──/──────>    default         默认顺序流
  ─ ─ ─ ─ ─>   message         消息流（Phase 3）
  ·········>    association      关联（注释连接）
  ····<····>    data_assoc      数据关联
```

### 5.3 数据与制品

```
数据对象（不是流程节点，是附着在活动上的标注）：

  📄    DataObject          数据对象（替代 ISO 5807 的 IO/DOCUMENT）
  📄⇒   DataInput           数据输入
  📄⇐   DataOutput          数据输出
  ═══   DataStore           数据存储（替代 ISO 5807 的 DATA_STORE）
  ≡📄   DataCollection      数据集合（替代 ISO 5807 的 MULTI_DOCUMENT）

制品（不影响执行）：

  ┌╌╌╌┐  TextAnnotation     文本注释
  ┌─ ─┐  Group              分组
```

### 5.4 泳道

```
  Pool    池 — 表示一个参与者（= 项目团队）
  Lane    道 — 池内部的角色划分（= actor 字段）
```

### 5.5 与原 StepType 的迁移对照

| 原 StepType | BPMN 2.0 表达 | 说明 |
|-------------|---------------|------|
| START | EventNode(position=start) | 开始事件 |
| END | EventNode(position=end) | 结束事件 |
| TASK | ActivityNode(task_type=abstract) | 抽象任务 |
| SESSION | ActivityNode(sub_process_type=ad_hoc, session={...}) | 临时子流程 = 多人讨论 |
| SUB_PROCESS | ActivityNode(sub_process_type=call_activity) | 调用活动 |
| DECISION | GatewayNode(gateway_type=exclusive) | 排他网关 |
| GATE | GatewayNode(gateway_type=exclusive, gate_config={...}) | 排他网关 + 门禁配置 |
| FORK | GatewayNode(gateway_type=parallel, direction=diverging) | 并行网关（分支） |
| JOIN | GatewayNode(gateway_type=parallel, direction=converging) | 并行网关（合并） |
| EVENT | EventNode(position=intermediate) | 中间事件 |
| PREPARATION | ActivityNode(task_type=abstract, tag="preparation") | 去掉独立类型 |
| IO | DataObject(data_type=data_object) | 去掉独立类型 |
| DOCUMENT | DataObject(data_type=data_object) | 去掉独立类型 |
| MULTI_DOCUMENT | DataObject(data_type=data_collection) | 去掉独立类型 |
| DATA_STORE | DataObject(data_type=data_store) | 去掉独立类型 |
| CONNECTOR | EventNode(trigger=link) | 去掉独立类型 |
| MANUAL | ActivityNode(task_type=manual) | 去掉独立类型 |

| 原 EdgeType | BPMN 2.0 FlowType | 说明 |
|-------------|-------------------|------|
| SEQUENCE | sequence | 不变 |
| CONDITIONAL | conditional | 不变 |
| ON_FAIL | conditional (label="fail") | 合并为条件流 |
| ON_APPROVE | conditional (label="approve") | 合并为条件流 |
| ON_REJECT | conditional (label="reject") | 合并为条件流 |
| FORK_BRANCH | sequence (from Parallel GW) | 不需要独立类型 |
| — | default | 新增 |
| — | message | 新增（Phase 3） |
| — | association | 新增 |

## 七、Phase 分期

### Phase 1（当前）

实现 BPMN Level 1 子集：

| 元素 | BPMN 类型 | 说明 |
|------|-----------|------|
| EventNode(start/end) | Start/End Event | 流程入口出口 |
| ActivityNode(abstract) | Abstract Task | Agent 执行任务 |
| ActivityNode(user) | User Task | 等待用户审批 |
| ActivityNode(ad_hoc) | Ad-Hoc Sub-Process | 多人讨论（session 扩展） |
| GatewayNode(exclusive) | Exclusive Gateway | 条件分支 + 门禁 |
| FlowEdge(sequence/conditional/default) | Sequence Flow | 节点连接 |

### Phase 2

引入 BPMN Level 2 元素：

| 元素 | BPMN 类型 | 说明 |
|------|-----------|------|
| ActivityNode(service) | Service Task | 系统自动执行（CI、部署） |
| ActivityNode(script) | Script Task | 执行脚本（数据库迁移） |
| ActivityNode(manual) | Manual Task | 用户手动操作 |
| ActivityNode(call_activity) | Call Activity | 引用子流程 |
| GatewayNode(parallel) | Parallel Gateway | 多任务并行 |
| EventNode(timer, boundary) | Timer Boundary Event | 节点超时 |
| EventNode(error, boundary) | Error Boundary Event | 节点失败 |
| ActivityMarker(loop/multi_instance) | Loop / Multi-Instance | 循环、多实例 |
| DataObject / DataStore | Data Object / Store | 数据标注 |
| Pool / Lane | Swimlane | 角色泳道 |

### Phase 3

引入 BPMN Level 3 元素：

| 元素 | BPMN 类型 | 说明 |
|------|-----------|------|
| GatewayNode(inclusive) | Inclusive Gateway | 多条件并行选择 |
| GatewayNode(event_based) | Event-based Gateway | 等待事件决定走哪条路 |
| EventNode(message) | Message Event | 等待/发送消息 |
| EventNode(signal) | Signal Event | 跨流程通知 |
| EventNode(compensation) | Compensation Event | 发布回滚 |
| ActivityNode(transaction) | Transaction Sub-Process | 事务（全部成功或回滚） |
| ActivityNode(event_sub) | Event Sub-Process | 全局错误处理 |
| FlowEdge(message) | Message Flow | 跨组织消息（如果需要） |

### Phase 1 → Phase 2 兼容性

Phase 1 的 ProcessDefinition 在 Phase 2 中仍然有效：
- ActivityNode(abstract) 仍然工作
- GatewayNode(exclusive) 仍然工作
- Phase 2 是增量扩展，不是破坏性变更

## 十、BPMN 2.0 元素落地决策

> 基于项目实际场景，将 BPMN 2.0 约 50 种元素分为三级：应该落地、可以但不急、不应该落地。
> 判断标准：① 当前设计是否已经需要这个语义 ② 能否用已有元素替代 ③ 实现成本 vs 收益

### 10.1 应该落地（有真实场景驱动，不实现跑不通）

| BPMN 元素 | 我们的场景 | Phase | 实现位置 |
|-----------|-----------|-------|---------|
| StartEvent (none) | 每个流程的入口 | 1 | core: EventNode(position=start) |
| EndEvent (none) | 每个流程的出口 | 1 | core: EventNode(position=end) |
| EndEvent (terminate) | 用户取消项目，终止所有并行分支 | 1 | core: EventNode(position=end, trigger=terminate) |
| Abstract Task | Agent 执行任务（编码/审查/测试/写文档） | 1 | core: ActivityNode(task_type=abstract) |
| User Task | 门禁审批（用户确认/驳回） | 1 | core: ActivityNode(task_type=user) + gate_config |
| Ad-Hoc SubProcess | session 多人讨论（头脑风暴/设计评审） | 1 | core: ActivityNode(sub_process_type=ad_hoc) |
| Exclusive Gateway (XOR) | 审查通过/打回、测试通过/失败 | 1 | core: GatewayNode(gateway_type=exclusive) |
| Sequence Flow | 节点间的执行顺序 | 1 | core: FlowEdge(flow_type=sequence) |
| Conditional Sequence Flow | 网关出口条件（verdict=="approved"） | 1 | core: FlowEdge(flow_type=conditional, condition=...) |
| Default Sequence Flow | 网关所有条件都不满足时的兜底路径 | 1 | core: FlowEdge(flow_type=default) |
| Parallel Gateway (AND) | 多任务并行执行（T-003 + T-004 同时开发） | 2 | core: GatewayNode(gateway_type=parallel) |

共 11 种，Phase 1 需要 10 种，Phase 2 新增 1 种。

### 10.2 可以落地但不急（有场景，Phase 1 有替代方案）

| BPMN 元素 | 场景 | Phase 1 替代方案 | 建议 Phase |
|-----------|------|-----------------|-----------|
| Call Activity | 阶段嵌套子流程 | 用 scope 字段区分 pipeline/stage，不需要真正的子流程实例化 | Phase 2 |
| Boundary Event (timer) | 任务执行超时 | runtime 的 LLM 重试 + flow 的 NodeResult(failed) 处理 | Phase 2 |
| Boundary Event (error) | Agent 执行失败 | NodeResult(failed) + flow 的 fallback 逻辑 | Phase 2 |
| Intermediate Event (timer) | 发布后观察窗口 | Phase 1 不需要发布后观察，手动确认即可 | Phase 2 |
| Service Task | CI/CD 自动执行 | Phase 1 没有 CI 集成 | Phase 2 |
| Lane | 泳道可视化（按角色分行） | 用 actor 字段标注角色，前端按角色分组显示 | Phase 2 |
| Loop Marker | TDD 循环标记 | 用 ExclusiveGateway 回退边实现同等效果 | Phase 2 |

共 7 种，全部推迟到 Phase 2。

### 10.3 不应该落地（无场景或有更好替代）

| BPMN 元素 | 排除原因 |
|-----------|---------|
| Inclusive Gateway (OR) | 我们的场景要么全走（Parallel）要么选一条（Exclusive），没有"走部分"的需求。如果未来出现，再评估 |
| Event-based Gateway | 需要同时监听多种外部事件竞争。我们的门禁用 UserTask 就够了，超时用 BoundaryEvent(timer) |
| Complex Gateway | BPMN 规范自己都建议"尽量避免使用"，语义复杂且难以维护 |
| Message Flow | 跨 Pool（跨组织）的消息传递。我们是单系统内部协作，flow→runtime 用 FlowMessage（HTTP） |
| Pool | 表示独立参与者/组织。我们只有一个"项目团队"，不需要多 Pool |
| Script Task | Agent 本身就能执行脚本（code_execute 工具），不需要单独的节点类型 |
| Send Task / Receive Task | BPMN 消息语义。我们用 FlowMessage 通信，不需要在流程图层面建模消息收发 |
| Business Rule Task | 需要规则引擎（如 DMN）。我们的规则用 shared_rules 的 schema 硬校验实现 |
| Manual Task | 所有人类操作都走 UserTask（门禁），不需要区分"手动任务"和"用户任务" |
| Compensation Event | 需要事务回滚语义（"做完 A 后发现要撤销，执行 A 的补偿"）。我们没有这个需求 |
| Escalation Event | 用 NodeResult(blocked) + flow 的升级逻辑替代，不需要 BPMN 的升级事件 |
| Cancel Event | 用 EndEvent(terminate) 替代，不需要区分"取消"和"终止" |
| Transaction SubProcess | 需要"全部成功或全部回滚"语义。我们的阶段不需要事务性 |
| Signal Event | 广播信号给所有监听者。我们用事件总线（platform event bus）替代 |
| Intermediate Event (message) | 等待特定消息。Phase 1/2 用 UserTask 等待用户操作就够了 |
| Data Object / Data Store | BPMN 的数据建模。我们用 Artifact + platform 数据库，不需要在流程图中建模数据 |
| Text Annotation | 流程图注释。前端渲染时可以加，不需要在引擎中实现 |
| Group | 视觉分组。纯前端展示，不影响执行 |
| Multi-Instance (parallel/sequential) | 用 ParallelGateway + 多个 Task 节点替代，语义更清晰 |

共 19 种，全部不实现。

### 10.4 决策总结

```
BPMN 2.0 ~50 种元素
│
├── 应该落地：11 种（Phase 1: 10 + Phase 2: 1）
│   → 覆盖了我们 95% 的流程编排需求
│
├── 可以但不急：7 种（全部 Phase 2）
│   → Phase 1 都有更简单的替代方案
│
└── 不应该落地：19 种
    → 无场景 / 有更好替代 / 复杂度不值得
    → 如果未来出现新需求，回来重新评估
```

> **原则：我们不是在做通用 BPMN 引擎，而是在做 AI Agent 协作平台。只实现有真实场景驱动的 BPMN 元素。**

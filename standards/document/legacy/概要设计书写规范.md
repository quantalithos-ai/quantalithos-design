# 概要设计书写规范

> 概要设计回答 **"为什么这样做、做什么"**。  
> 它是设计文档漏斗的上层——收束方向，定义边界，做出取舍。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)  
> 架构图绘制方法见 → [设计文档编写通则](设计文档编写通则.md) 第二章  

---

## 一、概要设计的目标

概要设计要解决三个核心问题：

1. **系统边界**：这个系统是什么、不是什么、和谁交互
2. **架构方向**：选什么架构风格、怎么拆模块、关键技术选型
3. **取舍依据**：为什么选 A 不选 B，做了哪些权衡

## 四、各模块编写要点

### 4.1 文档元信息与读码导航

文档元信息不仅是"标题+作者+日期"，更重要的附加项是**读码导航**——告诉不同时间预算的读者应该看什么：

| 时间预算 | 阅读路径 |
|---------|---------|
| 30 分钟 | §4~§6（架构与选型） |
| 2 小时  | 本文档全文 + 服务 README |
| 半天    | + 详细设计 + 对应核心代码 |

### 4.2 背景与问题定义

**编写要点**：
- 用 3~5 句话说清"为什么要做"——不要写成 PRD 摘抄
- 问题定义要量化：当前 QPS 是多少、P99 延迟是多少、故障率是多少
- 区分"业务问题"和"技术问题"——解决方案不同

### 4.3 目标与非目标

**编写要点**：
- **非目标比目标更重要**——明确"不做"的范围，防止需求蔓延
- 目标应可验证：用指标表达（如"下单 P99 < 15ms"），而非"提升性能"
- 非目标要具体：不是"不考虑性能"，而是"本次不考虑异地多活"

### 4.4 系统上下文与边界

**编写要点**：
- 系统上下文图的绘制规范见 → [设计文档编写通则](设计文档编写通则.md) §2.1
- 文字说明必须补充：职责边界、外部系统可用性约束、关键依赖风险、数据归属
- **常见错误**：只画图不写文字——图传达不了 SLA、降级策略等语义

### 4.5 总体架构设计

**编写要点**：
- 架构风格要写明（分层 / 六边形 / 微服务 / 事件驱动）及其选择理由
- 模块划分要标注职责（一句话定义每个模块做什么）
- **层间约束必须写明**——这是防止架构退化的核心防线
  - 例："domain 层不直接依赖 infra 层（通过接口倒置）"
  - 例："api 层只做参数校验和响应组装，不含业务逻辑"

**层间约束多语言示例**：

```c
// === C: 层间约束（通过函数指针表实现接口倒置） ===

// domain/order_service.h — domain 层只声明接口，不引用 infra 头文件
typedef struct stock_proxy stock_proxy_t;  // 前向声明，不 #include infra 头文件

struct order_service {
    const stock_proxy_t *stock;   // 依赖接口，不依赖实现
    const order_repo_t  *repo;
};

// infra/stock_proxy_grpc.c — infra 层实现 domain 层声明的接口
static int grpc_batch_deduct(stock_proxy_t *self, const item_list_t *items) {
    // gRPC 调用实现...
}

// 入口处注册实现
stock_proxy_t *stock_proxy = stock_proxy_grpc_create(channel);
order_service_t svc = { .stock = stock_proxy, .repo = repo };
```

```rust
// === Rust: 层间约束（通过 trait 实现接口倒置） ===

// src/domain/mod.rs — domain 层只定义 trait，不引用 infra
pub trait StockProxy: Send + Sync {
    async fn batch_deduct(&self, items: &[OrderItem]) -> Result<BatchDeductResult>;
}

// src/domain/order_service.rs — domain 依赖 trait，不依赖具体实现
pub struct OrderService {
    stock_proxy: Box<dyn StockProxy>,  // 接口倒置
    repo: Box<dyn OrderRepo>,
}

// src/infra/grpc_stock_proxy.rs — infra 层实现 domain 的 trait
pub struct GrpcStockProxy { channel: Channel }

#[async_trait]
impl StockProxy for GrpcStockProxy {
    async fn batch_deduct(&self, items: &[OrderItem]) -> Result<BatchDeductResult> {
        // gRPC 调用实现...
    }
}

// 入口组装
let svc = OrderService::new(
    Box::new(GrpcStockProxy::new(channel)),  // 注入实现
    Box::new(PgOrderRepo::new(pool)),
);
```

```python
# === Python: 层间约束（通过 Protocol/ABC 实现接口倒置） ===

# src/domain/protocols.py — domain 层只定义 Protocol，不引用 infra
from typing import Protocol

class StockProxy(Protocol):
    def batch_deduct(self, items: list[OrderItem]) -> BatchDeductResult: ...

class OrderRepo(Protocol):
    def save(self, order: Order) -> None: ...
    def find_by_id(self, order_id: str) -> Order | None: ...

# src/domain/order_service.py — domain 依赖 Protocol，不依赖具体实现
class OrderService:
    def __init__(self, stock_proxy: StockProxy, repo: OrderRepo):
        self._stock_proxy = stock_proxy  # 接口倒置
        self._repo = repo

# src/infra/grpc_stock_proxy.py — infra 层实现 domain 的 Protocol（鸭子类型）
class GrpcStockProxy:
    """无需显式继承 Protocol，只要方法签名匹配即可"""
    def batch_deduct(self, items: list[OrderItem]) -> BatchDeductResult:
        # gRPC 调用实现...

# 入口组装
svc = OrderService(
    stock_proxy=GrpcStockProxy(channel),  # 注入实现
    repo=SqlAlchemyOrderRepo(session),
)
```

### 4.6 关键技术选型

**编写要点**：
- 使用**决策四元组**：当前选择 | 备选方案 | 选择理由 | 演进路径
- 选择理由写"权衡"而非"事实"——
  - ✗ "选 Kafka 因为吞吐高"（事实，不是权衡）
  - ✓ "选 Kafka 而非 RabbitMQ 因为我们的场景吞吐优先于路由灵活"（权衡）
- 演进路径让未来维护者知道"还可以怎么做"

**决策四元组多语言示例**：

| 决策项 | 内容 |
|-------|------|
| 当前选择 | Rust + Axum + tonic |
| 备选方案 | Go + Gin + grpc-go / Java + Spring Boot + gRPC / Python + FastAPI + grpcio |
| 选择理由 | 吞吐优先于开发效率：单机 15 万 QPS vs Go 8 万 vs Java 5 万 vs Python 1.5 万；内存占用仅 Go 的 1/5 |
| 演进路径 | 若团队 Rust 招聘困难，可拆分非核心模块为 Go 微服务，核心路径保留 Rust |

| 决策项 | 内容 |
|-------|------|
| 当前选择 | C + libevent + SQLite（嵌入式场景） |
| 备选方案 | Rust + tokio + sled / Go + net/http + bbolt |
| 选择理由 | 目标平台为 ARM Cortex-A，内存 < 64MB；C 可直接操控内存布局，无运行时开销 |
| 演进路径 | 若业务复杂度增长导致内存安全问题频发，迁移到 Rust（FFI 渐进替换） |

### 4.7 备选方案与取舍

**编写要点**：
- 至少 2~3 个备选方案，用对比表格呈现
- 对比维度应覆盖：一致性、吞吐量、复杂度、运维成本、团队熟悉度
- 选择结论要写明理由，不要让读者猜

### 4.8 关键接口与数据流概览

**编写要点**：
- 概要设计只写接口边界（谁调谁、协议是什么），不写入参/出参细节
- 数据流至少有一条路径**精确到函数调用链**——这是概要设计到详细设计的衔接点
  - 例：`OrderController.create → AppService.createOrder → StockProxy.deduct → Domain.create → Repo.save`

**函数级调用链多语言示例**：

```
// C 风格调用链（函数指针表）
order_controller_create(req)
  → order_service_create(svc, cmd, &order_id)
      → stock_proxy->batch_deduct(svc->stock, cmd->items)     // [RPC] 函数指针调用
      → order_create(cmd->user_id, cmd->items, cmd->address_id) // 领域逻辑
      → svc->repo->save(svc->repo, &order)                     // 函数指针调用
      → event_bus->publish(svc->event_bus, "OrderCreated", &order)

// Rust 风格调用链（trait 方法调用）
order_controller::create_order(cmd)
  → order_service.create_order(&cmd)?
      → self.stock_proxy.batch_deduct(&cmd.items)?             // [RPC] trait 方法
      → Order::new(&cmd.user_id, cmd.items, &cmd.address_id)   // 领域逻辑
      → self.repo.save(&order)?                                // trait 方法
      → self.event_bus.publish(OrderCreatedEvent::from(&order))? // [MQ]

// Python 风格调用链（Protocol 方法调用）
order_controller.create_order(cmd)
  → order_service.create_order(cmd)
      → self._stock_proxy.batch_deduct(cmd.items)             # [RPC] Protocol 方法
      → Order(user_id=cmd.user_id, items=cmd.items, ...)      # 领域逻辑
      → self._repo.save(order)                                 # Protocol 方法
      → self._event_bus.publish("OrderCreated", order.to_dict()) # [MQ]
```

### 4.9 横切关注点

**编写要点**：
- 安全、性能、可用性、可观测性、成本——五项不可遗漏
- **性能预算表**是必须项：端到端延迟分解，每环节预估延迟 + 依据
- 非功能指标要标注来源：如"P99 < 15ms ← 非功能需求 ORD-NF01"

### 4.10 风险与待确认事项

**编写要点**：
- 异常场景分两层：「常见」和「边缘」——处理优先级不同
- 每个风险必须有缓解策略，不能只列风险不列方案
- 待确认事项要标注截止时间——过期未确认视为接受风险

### 4.11 上线策略

**编写要点**：
- 灰度方案：流量切换比例、观察时间、推进条件
- 回滚策略：触发条件、回滚步骤、数据兼容性
- 监控指标：关键业务指标 + 系统指标，标注告警阈值

## 五、概要设计评审清单

- [ ] 背景和问题定义是否清晰
- [ ] 目标和非目标是否明确
- [ ] 系统边界是否画清楚
- [ ] 架构选型是否使用决策四元组（选择+备选+理由+演进路径）
- [ ] 备选方案是否至少 2~3 个
- [ ] 分层架构是否写入层间约束规则
- [ ] 核心数据流是否至少有一条路径精确到函数调用链
- [ ] 关键路径是否有端到端时序分析
- [ ] 横切关注点（安全/性能/可用性/可观测/成本）是否覆盖
- [ ] 性能章节是否包含端到端延迟预算表
- [ ] 是否包含容量规划（内存/CPU/连接数）
- [ ] 风险是否识别并有缓解策略，异常场景是否区分「常见」和「边缘」
- [ ] 是否有需求追溯矩阵（需求ID ↔ 设计章节 ↔ 测试场景）
- [ ] 非功能需求指标是否标注来源和依据
- [ ] 灰度和回滚方案是否完备
- [ ] 上下游影响是否评估
- [ ] 文档是否包含版本号和变更记录
- [ ] 评审人是否覆盖架构/开发/测试/运维

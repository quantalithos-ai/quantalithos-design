# 需求文档书写规范

> 需求文档回答 **"要做什么、为什么要做、做成什么样算成功"**。  
> 它是软件工程的源头——需求定义不清，设计、开发、测试全部失焦。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)  
> 概要设计书写规范见 → [概要设计书写规范](概要设计书写规范.md)  

---

## 一、需求文档的目标

需求文档要解决三个核心问题：

1. **问题定义**：当前存在什么问题或机会，为什么值得做
2. **需求范围**：做什么、不做什么、做到什么程度
3. **验收标准**：怎么判断做完了、做对了

```
┌───────────────────────────────────────────────────────────────┐
│                    需求文档在工程链路中的位置                     │
├───────────────────────────────────────────────────────────────┤
│                                                               │
│  业务诉求 → 需求文档 → 概要设计 → 详细设计 → 编码 → 测试      │
│               │           │           │              │         │
│               ▼           ▼           ▼              ▼         │
│           做什么、     为什么这样    具体怎么     代码实现      │
│           为什么做     做、边界      做                         │
│                                                               │
│  需求文档是漏斗的入口——定义问题，收束期望，量化成功。          │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

## 二、需求文档必须包含的模块

```
┌─────────────────────────────────────────────────────────────┐
│                   需求文档结构                                 │

│                                                             │

│                                                             │

│     - 为什么要做（量化）                                      │
│                                                             │
│  3. 目标与非目标                                             │

│                                                             │
│  4. 用户与角色                                               │

│                                                             │
│  5. 核心用例与用户故事                                       │

│                                                             │
│  6. 功能需求                                                 │
│     - 功能清单与优先级（P0/P1/P2）                           │

│                                                             │
│  7. 非功能需求                                               │

│                                                             │
│  8. 交互与界面需求（可选）                                    │
│     - 核心页面/流程的交互说明                                 │
│     - 关键 UX 约束                                           │
│                                                             │
│  9. 数据需求                                                 │
│     - 核心业务实体与关系                                     │
│     - 数据生命周期与归档策略                                  │
│     - 隐私与合规要求                                         │
│                                                             │

│     - 外部系统依赖列表                                       │

│                                                             │
│  11. 验收标准                                               │
│     - 功能验收标准（每个功能的通过条件）                      │

│                                                             │
│  12. 风险与待确认事项                                        │
│     - 已知风险、影响、缓解策略                                │
│     - 待确认问题与截止时间                                   │
│                                                             │
│  13. 需求追溯矩阵                                           │
│     - 需求 ID ↔ 功能 ↔ 测试场景 ↔ 上线指标                  │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 三、需求文档的输入与输出

| 维度 | 输入材料 | 输出内容 |
|------|---------|---------|
| 业务 | 业务方诉求、市场分析、竞品调研 | 背景与问题定义、目标与非目标 |
| 用户 | 用户反馈、客服工单、用户访谈 | 用户与角色、用户故事 |
| 产品 | 产品路线图、PRD 草案 | 功能需求、交互需求、优先级 |
| 技术 | 现有系统架构、技术约束 | 非功能需求、接口与依赖 |
| 合规 | 法律法规、隐私政策、安全规范 | 数据需求、安全需求 |
| 运营 | SLA、监控数据、容量数据 | 非功能验收标准、上线指标 |

### 输入材料清单

| 序号 | 材料名称 | 来源 | 必要性 | 说明 |
|------|---------|------|--------|------|
| 1 | 业务方诉求文档 | 业务团队 | **必须** | 业务目标、期望效果 |
| 2 | 用户反馈 / 工单 | 客服 / 运营 | **必须** | 真实痛点、优先级依据 |
| 3 | 竞品分析报告 | 产品团队 | 推荐 | 功能对标、差异化定位 |
| 4 | 现有系统架构文档 | 架构组 | 推荐 | 技术约束、依赖边界 |
| 5 | 法律法规 / 合规要求 | 法务 / 安全 | 视场景 | 数据隐私、行业合规 |
| 6 | 历史需求与事故库 | SRE / 测试 | 推荐 | 避免重复踩坑 |

### 输出内容清单

| 序号 | 输出物 | 形式 | 受众 |
|------|--------|------|------|
| 1 | 问题定义与目标 | 文字 + 表格 | 全团队 |
| 2 | 角色权限矩阵 | 表格 | 开发 + 测试 |
| 3 | 用户故事卡片 | 表格 | 全团队 |
| 4 | 功能需求清单（含优先级） | 表格 | 开发 + 测试 |
| 5 | 业务规则表 | 表格 | 开发 + 测试 |
| 6 | 非功能需求指标表 | 表格 | 开发 + SRE |
| 7 | 数据实体关系图 | ASCII / 绘图工具 | 开发 |
| 8 | 验收标准表 | 表格 | 测试 + 产品 |
| 9 | 风险清单 | 表格 | 全团队 |
| 10 | 需求追溯矩阵 | 表格 | 全团队 |

## 四、各模块编写要点

### 4.1 文档元信息与阅读导航

文档元信息不仅是"标题+作者+日期"，更重要的附加项是**阅读导航**——告诉不同时间预算的读者应该看什么：

| 时间预算 | 阅读路径 |
|---------|---------|
| 5 分钟  | §4~§6（角色、用例、功能需求） |
| 30 分钟 | 本文档全文 |
| 1 小时  | + 验收标准 + 需求追溯矩阵 |

### 4.2 背景与问题定义

**编写要点**：
- 用 3~5 句话说清"为什么要做"——不要写成流水账
- 问题定义要量化：当前转化率是多少、用户投诉量是多少、人工处理成本是多少
- 区分"业务问题"和"用户问题"——解决方案的视角不同
- 避免把解决方案混入问题定义——问题定义只描述现状和痛点

**示例**：

```
┌──────────────────────────────────────────────────────────────┐
│  ✗ 差的问题定义                                              │
│  ──────────────                                              │
│  "我们需要一个推荐系统，用协同过滤算法给用户推荐商品。"       │
│  → 这不是问题定义，这是解决方案                               │
│                                                              │
│  ✓ 好的问题定义                                              │
│  ──────────────                                              │
│  "搜索转化率仅 2.3%（行业均值 5.1%），用户平均浏览 15 个      │
│  商品才下单。80% 的用户在浏览 8 个商品后离开。核心问题：       │
│  用户找不到想要的商品。"                                     │
│  → 量化现状 + 对标 + 根因分析                                │
└──────────────────────────────────────────────────────────────┘
```

### 4.3 目标与非目标

**编写要点**：
- **非目标比目标更重要**——明确"不做"的范围，防止需求蔓延
- 目标应可验证：用指标表达（如"搜索转化率提升到 4%"），而非"提升搜索体验"
- 非目标要具体：不是"不考虑性能"，而是"本次不考虑离线推荐场景"
- 目标与问题定义要形成因果链：问题 → 目标 → 验收标准

**目标-非目标表示例**：

| 类型 | 内容 | 验证方式 |
|------|------|---------|
| ✅ 目标 | 搜索转化率从 2.3% 提升到 4% | 上线后 A/B 测试 2 周 |
| ✅ 目标 | 用户平均浏览商品数从 15 降到 8 | 埋点数据统计 |
| ❌ 非目标 | 不做离线推荐 | — |
| ❌ 非目标 | 不做个性化首页 | — |
| ❌ 非目标 | 不做跨品类推荐 | — |

### 4.4 用户与角色

**编写要点**：
- 每个角色用一句话定义：谁 + 在什么场景下 + 做什么
- 权限矩阵必须穷举：谁能做什么、谁不能做什么
- 不要遗漏管理角色和系统角色（如定时任务、后台运营）

**角色权限矩阵示例**：

| 操作 | 普通用户 | VIP 用户 | 运营人员 | 系统管理员 |
|------|---------|---------|---------|-----------|
| 浏览商品 | ✅ | ✅ | ✅ | ✅ |
| 下单 | ✅ | ✅ | ❌ | ❌ |
| 退款 | ✅（限自己） | ✅（限自己） | ✅（任意） | ✅（任意） |
| 修改商品价格 | ❌ | ❌ | ✅ | ✅ |
| 审核商品 | ❌ | ❌ | ❌ | ✅ |

### 4.5 核心用例与用户故事

**编写要点**：
- 用户故事遵循格式：**作为 [角色]，我想要 [行为]，以便 [价值]**
- 每个用户故事必须附带验收条件（Given-When-Then）
- 用例按端到端场景组织，不要按页面或按钮罗列
- 区分**主流程**和**替代流程**

**用户故事卡片示例**：

| 字段 | 内容 |
|------|------|
| ID | US-001 |
| 用户故事 | 作为 购物用户，我想要 按条件筛选商品，以便 快速找到我需要的商品 |
| 优先级 | P0 |
| 验收条件 | **Given** 用户在搜索结果页 **When** 选择"价格从低到高"排序 **Then** 商品列表按价格升序重排 |
| 验收条件 | **Given** 用户在搜索结果页 **When** 选择"仅看有货"筛选 **Then** 仅显示库存 > 0 的商品 |
| 替代流程 | 无搜索结果时展示推荐商品，文案"没有找到相关商品，为你推荐" |

### 4.6 功能需求

**编写要点**：
- 功能按**用户场景**组织，不要按技术模块组织
- 每个功能标注优先级（P0 必做 / P1 应做 / P2 可做）
- 业务规则必须用表格穷举，不要用自然语言描述分支逻辑
- 功能之间如有依赖关系，需要标注

**功能清单示例**：

| ID | 功能名称 | 优先级 | 依赖 | 描述 |
|----|---------|--------|------|------|
| F-001 | 商品搜索 | P0 | — | 支持关键词搜索，返回商品列表 |
| F-002 | 搜索结果筛选 | P0 | F-001 | 支持按品类、价格区间、库存状态筛选 |
| F-003 | 搜索结果排序 | P1 | F-001 | 支持按价格、销量、评分排序 |
| F-004 | 搜索建议 | P2 | F-001 | 输入时展示搜索建议词 |

**业务规则表示例**：

| 规则 ID | 条件 | 结果 |
|---------|------|------|
| BR-001 | 商品库存 = 0 | 不在搜索结果中展示 |
| BR-002 | 商品状态 = 下架 | 不在搜索结果中展示 |
| BR-003 | 搜索关键词为空 | 展示热门推荐 |
| BR-004 | 搜索结果 > 1000 条 | 只返回前 1000 条，提示"已筛选最相关结果" |

### 4.7 非功能需求

**编写要点**：
- 性能、可用性、安全、可观测性、兼容性——五项不可遗漏
- **每项指标必须量化**：给数字 + 测量方式 + 来源依据
- 来源依据比数字更重要——"P99 < 200ms"依据是什么？
- 区分**业务指标**和**系统指标**：前者面向业务方，后者面向技术团队

**非功能需求指标表示例**：

| 维度 | 指标 | 目标值 | 测量方式 | 来源依据 |
|------|------|--------|---------|---------|
| 性能 | 搜索响应 P99 | < 200ms | APM 埋点 | 竞品 P99 约 150ms，留 30% 余量 |
| 性能 | 搜索 QPS 峰值 | ≥ 5000 | 压测 | 双十一峰值预估 3000，留 60% 余量 |
| 可用性 | 搜索服务 SLA | 99.95% | 监控 | 业务方要求，影响 GMV |
| 安全 | 搜索接口限流 | 单用户 50 次/分钟 | 网关限流 | 防爬虫，历史攻击数据分析 |
| 可观测性 | 慢查询告警 | > 500ms 告警 | 日志监控 | P99 的 2.5 倍 |
| 兼容性 | 客户端版本 | iOS ≥ 14, Android ≥ 10 | 埋点数据 | 覆盖 95% 以上用户 |

### 4.8 交互与界面需求

**编写要点**：
- 需求文档只描述**交互逻辑和 UX 约束**，不描述视觉设计
- 重点关注：核心流程的交互步骤、异常态的交互处理、关键 UX 约束
- 用流程图或状态机描述多步骤交互，不要用大段文字

**关键交互约束示例**：

| 约束 | 说明 |
|------|------|
| 搜索响应 | 结果 ≤ 200ms 时即时展示；> 200ms 展示骨架屏 |
| 空结果 | 展示推荐商品 + 引导文案，不要空白页 |
| 网络异常 | 展示重试按钮 + 提示文案，不要直接 Toast |
| 加载更多 | 滑动到底部自动加载，不要"点击加载更多"按钮 |

### 4.9 数据需求

**编写要点**：
- 用简单的实体关系图描述核心业务实体及其关系
- 标注每个实体的**数据所有权**：谁创建、谁修改、谁消费
- 数据生命周期：创建 → 使用 → 归档 → 销毁
- 隐私与合规要求单列：涉及哪些敏感字段、合规标准是什么

**数据实体关系示例**：

```
┌──────────┐      1:N      ┌──────────┐      1:N      ┌──────────┐
│   用户    │──────────────►│   订单    │──────────────►│  订单项   │
│ (User)   │              │ (Order)  │              │(Item)    │
└──────────┘              └────┬─────┘              └────┬─────┘
                               │                         │
                          N:1  │                    N:1   │
                               ▼                         ▼
                         ┌──────────┐              ┌──────────┐
                         │  收货地址  │              │   商品    │
                         │(Address) │              │(Product) │
                         └──────────┘              └──────────┘
```

**数据所有权矩阵**：

| 数据 | 拥有者（写入方） | 消费者（读取方） | 敏感等级 | 保留策略 |
|------|----------------|----------------|---------|---------|
| 用户信息 | 用户服务 | 订单服务、搜索服务 | 🔴 高 | 注销后 30 天删除 |
| 订单数据 | 订单服务 | 支付服务、通知服务 | 🟡 中 | 3 年归档 |
| 搜索日志 | 搜索服务 | 推荐服务 | 🟢 低 | 90 天滚动删除 |

### 4.10 接口与依赖

**编写要点**：
- 列出所有外部系统依赖，标注可用性约束
- 上下游接口在需求阶段写**契约意图**（谁调谁、为什么调），不写实现细节
- 标注依赖风险：第三方系统的 SLA、限流、维护窗口

**外部依赖表示例**：

| 依赖系统 | 方向 | 交互意图 | 协议 | SLA | 风险 |
|---------|------|---------|------|-----|------|
| 库存系统 | 下游 | 查询/扣减库存 | gRPC | 99.9% | ⚠ 扣减非幂等，需补偿 |
| 支付平台 | 下游 | 发起支付 | HTTPS | 99.95% | ⚠ 第三方，不可控维护窗口 |
| 消息队列 | 下游 | 发布订单事件 | MQ | 99.99% | — |
| 用户服务 | 上游 | 查询用户信息 | gRPC | 99.95% | — |

### 4.11 验收标准

**编写要点**：
- 功能验收标准：每个功能都有明确的通过条件，用 Given-When-Then 格式
- 非功能验收标准：量化指标 + 测量方式 + 达标判定
- 验收标准是**需求文档最重要的部分**——没有验收标准的需求不算完成
- 避免模糊表述：不说"速度快"，说"P99 < 200ms"

**验收标准表示例**：

| ID | 需求 ID | 类型 | 验收条件 | 测量方式 | 达标判定 |
|----|---------|------|---------|---------|---------|
| AC-001 | F-001 | 功能 | 关键词搜索返回相关商品 | 手动测试 + 自动化 | Top 5 结果相关率 ≥ 80% |
| AC-002 | F-001 | 功能 | 空关键词搜索返回热门推荐 | 手动测试 | 展示 10 条推荐 |
| AC-003 | F-001 | 性能 | 搜索响应 P99 < 200ms | 压测 | 连续 3 天达标 |
| AC-004 | F-002 | 功能 | 筛选后结果符合条件 | 自动化 | 100% 条件命中 |

### 4.12 风险与待确认事项

**编写要点**：
- 每个风险必须有缓解策略，不能只列风险不列方案
- 风险按影响分级：🔴 高影响 / 🟡 中影响 / 🟢 低影响
- 待确认事项要标注截止时间——过期未确认视为接受风险

**风险清单示例**：

| 风险 | 影响 | 概率 | 缓解策略 |
|------|------|------|---------|
| 搜索引擎性能不达标 | 🔴 高 | 中 | 预留 2 周调优时间；备选：降级为数据库查询 |
| 第三方支付接口变更 | 🟡 中 | 低 | 接入层做防腐层，变更影响收束 |
| 商品数据同步延迟 | 🟢 低 | 高 | 搜索结果标注"数据可能有延迟" |

**待确认事项示例**：

| 问题 | 影响范围 | 截止时间 | 负责人 |
|------|---------|---------|--------|
| 搜索是否需要支持拼音搜索？ | F-001 范围 | 2024-03-15 | 产品 @张三 |
| 历史订单是否可搜索？ | 数据需求 | 2024-03-20 | 业务 @李四 |

## 五、需求文档评审清单

- [ ] 背景和问题定义是否量化、是否混淆了解决方案
- [ ] 目标和非目标是否明确、可验证
- [ ] 角色定义是否完整、权限矩阵是否穷举
- [ ] 用户故事是否按端到端场景组织、是否有验收条件
- [ ] 功能需求是否标注优先级（P0/P1/P2）
- [ ] 业务规则是否用表格穷举而非自然语言描述
- [ ] 非功能需求是否五项覆盖（性能/可用性/安全/可观测/兼容）
- [ ] 非功能指标是否量化且标注来源依据
- [ ] 数据需求是否包含实体关系、所有权矩阵、隐私合规
- [ ] 外部依赖是否标注 SLA 和风险
- [ ] 验收标准是否每个功能都有、是否可测量
- [ ] 风险是否有缓解策略、待确认事项是否有截止时间
- [ ] 需求追溯矩阵是否覆盖需求 ID ↔ 功能 ↔ 测试场景
- [ ] 文档是否包含版本号和变更记录
- [ ] 评审人是否覆盖产品 / 开发 / 测试 / 运营

## 六、需求文档与设计文档的衔接

```
┌──────────────────────────────────────────────────────────────┐
│                  文档衔接关系                                   │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  需求文档              概要设计            详细设计            │
│  ─────────           ─────────          ─────────           │
│  问题定义    →→→     系统边界           模块职责              │
│  目标与非目标 →→→    架构方向           代码结构              │
│  功能需求    →→→     模块划分           接口定义 + 伪代码     │
│  非功能需求  →→→     性能预算表         并发/缓存/降级方案     │
│  业务规则    →→→     状态机设计         状态转换实现           │
│  数据需求    →→→     数据流概览         表结构 + 索引设计      │
│  验收标准    →→→     上线策略           测试用例 + 压测方案    │
│                                                              │
│  关键原则：需求文档定义"做什么"，概要设计决定"怎么组织"，     │
│  详细设计展开"怎么实现"。三层文档通过需求追溯矩阵串联。       │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

**衔接检查项**：

| 检查项 | 说明 |
|--------|------|
| 需求 ID 可追溯 | 每个功能需求 ID 在概要设计中都有对应章节 |
| 非功能需求有预算 | 需求文档的 P99 指标在概要设计中有端到端延迟预算分解 |
| 业务规则有状态机 | 需求文档的业务规则在概要设计/详细设计中有状态机图覆盖 |
| 验收标准可执行 | 验收标准的测量方式在测试用例中可落地 |

## 七、常见误区

```
┌───────────────────────────────────────────────────────────┐
│                   需求文档的 10 个致命误区                   │
├───────────────────────────────────────────────────────────┤
│                                                           │
│  ❶ 把解决方案混入问题定义                                  │
│     → 问题定义只描述现状和痛点，不要预设解决方案            │
│                                                           │
│  ❷ 没有量化指标                                          │
│     → "提升用户体验"不可验证，"P99 < 200ms"可验证         │
│                                                           │
│  ❸ 没有非目标                                            │
│     → 不写非目标 = 默认所有相关事情都做，需求无限蔓延      │
│                                                           │
│  ❹ 业务规则用自然语言描述                                 │
│     → "如果用户是 VIP 且订单金额大于 100 元则免运费"      │
│       应写成规则表格，避免歧义和遗漏                       │
│                                                           │
│  ❺ 非功能需求不给来源依据                                 │
│     → "P99 < 200ms"——依据是什么？竞品？压测？业务方要求？  │
│                                                           │
│  ❻ 没有验收标准                                          │
│     → 没有验收标准的需求不算完成，"做完了"≠"做对了"       │
│                                                           │
│  ❼ 遗漏异常场景和边界条件                                 │
│     → 只写正常流程不写异常，开发和测试只能自己猜           │
│                                                           │
│  ❽ 按页面/按钮罗列功能                                   │
│     → 应按用户场景组织，避免只见树木不见森林               │
│                                                           │
│  ❾ 角色和权限定义不完整                                   │
│     → 遗漏管理角色或系统角色，上线后才发现权限漏洞         │
│                                                           │
│  ❿ 需求文档写完就束之高阁                                 │
│     → 需求变更必须更新文档，否则后续文档全部失真           │
│                                                           │
└───────────────────────────────────────────────────────────┘
```

## 八、需求文档模板

```markdown
# [项目名] 需求文档

> 作者 | 日期 | 评审人 | 状态
> 版本 | 最后更新 | 变更记录

## 阅读导航（推荐）

## 1. 背景与问题定义
## 2. 目标与非目标
## 3. 用户与角色（附权限矩阵）
## 4. 核心用例与用户故事（附验收条件）
## 5. 功能需求（附功能清单、业务规则表）
  - 5.1 [功能模块 A]
  - 5.2 [功能模块 B]
  - ...
## 6. 非功能需求（附量化指标表）
  - 6.1 性能
  - 6.2 可用性
  - 6.3 安全
  - 6.4 可观测性
  - 6.5 兼容性
## 7. 交互与界面需求
## 8. 数据需求（附实体关系图、所有权矩阵）
  - 8.1 核心业务实体
  - 8.2 数据生命周期与归档
  - 8.3 隐私与合规
## 9. 接口与依赖（附外部依赖表）
## 10. 验收标准（附验收标准表）
## 11. 风险与待确认事项
## 12. 需求追溯矩阵
```

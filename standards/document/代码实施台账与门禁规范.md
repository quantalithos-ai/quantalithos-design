# 代码实施台账与门禁规范

> 本规范定义“实现 agent 在代码仓落码时，必须如何记录实施台账、执行门禁、处理 blocker、提交代码和交付后续状态”。
> 它适用于所有从设计仓 `07-实施计划.md` / `design-calibration` 转入实现仓的编码任务。
> 本规范不替代 `实施计划书写规范.md`，也不替代具体项目的 `07-实施计划.md`；它规定实现阶段的执行记录和门禁协议。

## 一、定位

代码实施台账不是聊天摘要，也不是自由日志。

代码实施台账也不是普通 checklist。Checklist 只回答“做没做”;实施台账必须同时回答:

```text
现在在哪个 boundary
基于哪个 design baseline
当前 gate 是 pass / pending / blocked / not_applicable
下一步只允许做什么
为什么允许或不允许
证据是什么
```

因此,实施台账的实际产物是一组可恢复、可审计、可阻断的状态文件:

```text
预先定义的步骤
  + 执行状态
  + 门禁判定
  + 证据
  + blocker
  + 下一步允许动作
```

```text
设计仓实施计划
  -> commit boundary
  -> 实现 agent 开工
  -> 实施台账
  -> 代码修改
  -> 门禁验证
  -> commit / blocker / handoff
```

它的作用是：

1. 让实现 agent 在继续、恢复上下文或换 agent 时知道当前做到哪一步。
2. 记录当前代码实现绑定的 design baseline。
3. 明确当前 commit boundary 允许修改和禁止修改的范围。
4. 把“能否继续实现、能否提交、能否进入下一 boundary”变成可审计门禁。
5. 把实现侧发现的设计 blocker 回流到设计仓，而不是由实现端自行补 schema、port、状态、mapper、配置或测试证据。
6. 让 commit message、staged files、测试命令和交付状态都有证据。

禁止做法：

```text
只在最终回复里说“已完成”
只写自由文本总结，不记录 gate_status / next_allowed_action
提交后才补台账
遇到 blocker 后继续实现
把台账当 TODO 清单，勾选但没有证据
```

## 三、强制文件位置

### 3.1 设计仓项目级实施台账

每个进入实现的项目必须在设计仓保留项目级实施台账：

```text
projects/<project>/design-calibration/implementation_execution_ledger.md
```

用途：

- 记录当前实现总体状态。
- 记录当前 design baseline。
- 记录当前实现仓路径。
- 记录当前 boundary、blocker 和下一步动作。
- 作为实现 agent 每次继续前的第一读取入口。

### 3.2 设计仓 boundary 级实施台账

每个 commit boundary 必须有独立台账：

```text
projects/<project>/design-calibration/implementation-boundaries/<boundary_id>.md
```

示例：

```text
projects/L1-identity/design-calibration/implementation-boundaries/commit-03-b.md
```

用途：

- 记录该 boundary 的读取文档、允许范围、禁止范围和必跑检查。
- 记录该 boundary 的 Design Gate、Scope Gate、Build Gate、Commit Gate 和 Handoff Gate。
- 记录 blocker、修复 baseline 和是否可继续。

### 3.2.1 planned boundary 预创建规则

正式 `07-实施计划.md` 已经列入 Boundary Gate Matrix 的 commit boundary,必须在实现移交前预创建对应的 boundary 台账骨架。

预创建不是授权实现。除当前 boundary 外,未来 boundary 台账必须满足:

- `status = planned`。
- `next_allowed_action = wait_until_current`。
- Gate Matrix 的 activation / design gate 必须说明“等待项目级实施台账推进到本 boundary”。
- Allowed Scope、Forbidden Scope、Required Checks、Commit Gate、Handoff Gate 可以先按正式 `07` 填入 planned 口径,但不得把任何 gate 标为 `pass`。
- 项目级实施台账必须只把一个 boundary 标为 current;未来 boundary 只能在 Boundary Ledger 中标为 `planned / wait_until_current`。

缺少未来 boundary 台账骨架时,不得等实现 agent 开到该 boundary 后再临场补文件。设计侧必须先补齐全部 planned skeleton,再移交实现。实现 agent 只能在当前 boundary 缺失或新 boundary 被正式追加时请求设计侧补台账;不能把常规推进变成每个 boundary 一次的设计 blocker。

### 3.3 实现仓本地执行台账

实现仓可保留本地 scratch 台账：

```text
<implementation_repo>/.codex/implementation_ledger.md
```

用途：

- 记录当前工作区本地状态、已触碰文件、未纳入用户改动、已跑命令和下一步。
- 该文件不替代设计仓台账。
- 若实现仓策略禁止提交 `.codex/`，该文件可不提交，但最终交付必须回写设计仓项目级和 boundary 级台账。

## 四、状态和值域

### 4.1 `gate_status`

`gate_status` 只能使用以下值：

| 值 | 含义 | 是否允许继续实现 |
|---|---|---|
| `pending` | 门禁尚未执行或证据未补齐 | 不允许进入下一动作，只能补证据或执行门禁 |
| `pass` | 门禁已通过且有证据 | 允许执行 `next_allowed_action` |
| `blocked` | 存在设计、范围、环境、测试或提交阻塞 | 不允许继续实现，只能修复、回写或等待 |
| `not_applicable` | 当前 boundary 不适用该门禁 | 允许，但必须写明原因 |

禁止使用：

```text
ok
done
maybe
good
用户同意
已处理
```

### 4.2 `next_allowed_action`

`next_allowed_action` 只能使用以下值：

| 值 | 含义 |
|---|---|
| `read_docs` | 先读取台账、设计 baseline 和 boundary 文档 |
| `open_boundary` | 创建或更新当前 boundary 台账 |
| `implement` | 允许按当前 allowed scope 修改代码 |
| `run_gates` | 允许运行格式化、编译、测试、证据或静态检查 |
| `fix_gate_failure` | 只允许修复已失败的门禁 |
| `commit` | 允许提交当前 staged 改动 |
| `wait_design` | 等待设计仓闭口，不允许实现端自行补口 |
| `handoff` | 允许整理交付说明和后续任务 |
| `start_next_boundary` | 允许进入下一个 commit boundary |

若 `gate_status = blocked`，`next_allowed_action` 必须是 `wait_design`、`fix_gate_failure` 或 `handoff` 之一。

项目级台账必须包含固定字段表：

```md
## Current Implementation State

| field | value |
|---|---|
| project | L1-identity |
| design_repo | /home/aris/Projects/quantalithos-design |
| implementation_repo | /home/aris/Projects/quantalithos-identity |
| current_design_baseline | 3bee523 |
| current_boundary | commit-03-b |
| gate_status | blocked |
| gate_reason | MemberSummaryView scoped lookup missing persisted scope source |
| next_allowed_action | wait_design |
| current_recovery_point | commit-03-b / projection fake scoped lookup |
| last_updated_by | implementation agent |
| last_updated_at | 2026-06-15 |
```

必须包含 boundary 汇总表：

```md
## Boundary Ledger
```

```md

|---|---|---|---|---|---|
| BLK-ID-03B-001 | commit-03-b | implementation | resolved | 3bee523 | continue commit-03-b |
```

## 七、固定门禁

### 7.1 Design Gate

目标：确认实现端基于已闭口设计，而不是自行发明设计。

必须检查：

| 检查项 | 证据 |
|---|---|
| 已读取项目级实施台账 | 台账路径和读取时间 |
| 已读取当前 boundary 台账 | boundary 台账路径 |
| design baseline 是明确 commit hash | `git -C <design_repo> rev-parse --short HEAD` 或指定 baseline |
| 当前 boundary 在 `07-实施计划.md` 或 calibration 中存在 | 具体路径 |
| 当前实现没有遇到未闭合 schema / port / state / mapper / config / evidence | blocker 表或 `pass` 说明 |

失败处理：

- `gate_status = blocked`
- `next_allowed_action = wait_design`
- 必须写出 blocker 证据和建议闭口点。

### 7.2 Scope Gate

目标：确认改动只属于当前 commit boundary。

必须检查：

| 检查项 | 证据 |
|---|---|
| allowed files 已列出 | boundary 台账 `Allowed Scope` |
| touched files 未越界 | `git status --short` / `git diff --name-only` |
| 用户已有无关改动未被纳入 | `git status --short` 对比说明 |
| 没有顺手重构或跨 boundary 功能 | diff 说明 |

失败处理：

- 未提交前必须拆分或撤出越界 staged 内容。
- 不得使用 destructive 命令处理用户改动。

### 7.3 Worktree Gate

目标：保护用户已有工作区状态。

必须记录：

```md
## Worktree Gate

| item | status | evidence |
|---|---|---|
| initial_status_recorded | pass | `git status --short` before edits |
| user_unrelated_changes_identified | pass | `.gitignore` not touched |
| destructive_commands_avoided | pass | no reset/checkout of user files |
```

若工作区存在用户改动，实现 agent 必须：

- 只处理与当前任务直接相关的文件。
- 提交前确认 staged files 不包含用户无关改动。
- final / handoff 中说明哪些用户改动未触碰。

### 7.4 Build Gate

目标：确认代码可编译或明确说明为什么不能验证。

常见证据：

```text
cargo fmt --all
cargo check -p <crate>
cargo test -p <crate> <targeted_test>
git diff --check
```

如果命令未运行，不能写 `pass`，必须写：

```text
status = blocked 或 pending
reason = 未运行原因
next_allowed_action = run_gates
```

### 7.5 Test Gate

目标：确认当前 boundary 的行为有最小测试覆盖。

必须记录：

| 检查项 | 证据 |
|---|---|
| targeted tests | 命令和结果 |
| affected crate tests | 命令和结果 |
| negative tests, if required | 测试名 |
| duplicate / replay / idempotency tests, if boundary touches them | 测试名 |

不能用“代码简单”替代测试证据。若设计计划明确测试后置，必须引用具体 boundary 说明。

### 7.6 Evidence Gate

目标：确认测试证据、报告或验收材料按当前项目规则生成。

适用于包含 `scripts/gates`、`artifacts/test/<run_id>`、`reports/runs/<run_id>` 或验收证据的 boundary。

必须记录：

| 检查项 | 证据 |
|---|---|
| raw artifact generated | artifact path |
| report generated | report path |
| evidence index updated | evidence path |
| digest / source commits recorded | artifact metadata |

若当前 boundary 不涉及证据产物，可设为 `not_applicable`，但必须写明原因。

### 7.7 Commit Gate

目标：防止 commit 不规范、混入无关改动或提交未验证代码。

提交前必须记录：

```md
## Commit Gate

| gate | status | evidence |
|---|---|---|
| staged_scope | pass | `git diff --cached --name-only` only includes allowed files |
| unrelated_changes | pass | user `.gitignore` remains unstaged |
| commit_message_format | pass | `feat(identity-infra): add scoped member summary lookup` |
| whitespace | pass | `git diff --cached --check` |
| required_checks | pass | `cargo check -p identity-infra` |
```

commit message 必须遵守当前项目实施计划或标准中的格式。若无项目特殊规定，默认：

```text
type(scope): subject
```

常用 type：

| type | 用途 |
|---|---|
| `feat` | 新功能或新实现切片 |
| `fix` | 修复行为缺陷 |
| `test` | 测试补充 |
| `docs` | 文档改动 |
| `refactor` | 不改变行为的重构 |
| `chore` | 构建、脚本、维护 |

错误示例：

```text
update
fix stuff
wip
继续
commit-03-b
```

提交后必须记录：

```md
| field | value |
|---|---|
| committed_hash | abc1234 |
| committed_message | feat(identity-infra): add scoped member summary lookup |
| post_commit_status | pass |
| next_allowed_action | start_next_boundary |
```

### 7.8 Handoff Gate

目标：确保交付信息足够让用户或下一个 agent 接上。

必须记录：

| 检查项 | 证据 |
|---|---|
| commit hash | hash |
| gates run | 命令清单 |
| tests not run | 原因 |
| remaining blockers | blocker 表 |
| next boundary | boundary id |
| user-owned changes untouched | 文件列表 |

## 八、实现 agent 执行状态机

实现 agent 必须按下面状态推进：

```text
read_docs
  -> open_boundary
  -> implement
  -> run_gates
  -> commit
  -> handoff
  -> start_next_boundary
```

任意阶段遇到未闭合设计问题：

```text
any state
  -> gate_status = blocked
  -> next_allowed_action = wait_design
  -> write blocker
  -> stop implementation
```

任意阶段遇到测试或格式失败：

```text
run_gates
  -> gate_status = blocked
  -> next_allowed_action = fix_gate_failure
  -> fix within current boundary
  -> run_gates
```

禁止跳转：

```text
read_docs -> commit
implement -> start_next_boundary
blocked -> implement
pending -> commit
```

## 九、blocker 记录格式

实现侧 blocker 必须使用结构化格式：

```md
## Blocker BLK-ID-03B-001

| field | value |
|---|---|
| boundary | commit-03-b |
| discovered_in | implementation |
| gate | design_gate |
| status | open |
| blocking_reason | MemberSummaryView lookup requires persisted visibility_scope_ref but design does not define save/index source |
| affected_files | `crates/infra/src/memory_runtime.rs`; `crates/infra/tests/...` |
| design_sources | Step 7 line refs; Step 11 line refs |
| forbidden_workarounds | private fake map; body scan; scope inferred from visibility_result_ref |
| requested_design_closure | add visibility_scope_ref to MemberSummaryView and member_summary_views current index |
| next_allowed_action | wait_design |
```

blocker 关闭后必须补：

```md
| design_fix_baseline | 3bee523 |
| resolution_summary | Step 6/7/8/9/11/16 now define scoped lookup and scope mismatch degraded surface |
| status | resolved |
| next_allowed_action | implement |
```

## 十、正反例

### 10.1 正例：提交前门禁

```md
## Commit Gate

| gate | status | evidence |
|---|---|---|
| staged_scope | pass | `git diff --cached --name-only` only lists `crates/infra/src/memory_runtime.rs` and targeted tests |
| unrelated_changes | pass | `.gitignore` remains unstaged |
| commit_message_format | pass | `feat(identity-infra): add scoped member summary lookup` |
| whitespace | pass | `git diff --cached --check` no output |
| required_checks | pass | `cargo check -p identity-infra`; `cargo test -p identity-infra projection_query_tests` |
```

为什么正确：

- 每个 `pass` 都有证据。
- commit message 是可审查格式。
- 明确用户无关改动未纳入。

### 10.2 反例：自由勾选

```md
- [x] 代码完成
- [x] 测试通过
- [x] commit 规范
- [x] 可以继续
```

为什么错误：

- 没有 design baseline。
- 没有 boundary。
- 没有 touched files。
- 没有命令证据。
- 没有 commit message。
- 无法判断是否越界。

### 10.3 正例：设计 blocker

```md
| field | value |
|---|---|
| gate_status | blocked |
| gate_reason | Step 7 requires stable lookup, but Step 11 store has no matching persisted key |
| next_allowed_action | wait_design |
```

为什么正确：

- 明确阻塞的是设计闭口，不是实现技巧。
- 明确不能继续实现。
- 给出下一动作是等待设计修复。

### 10.4 反例：实现端自行补口

```md
临时在 fake 里加一个 HashMap<(member_ref, scope_ref), view_ref>，先让测试过。
```

为什么错误：

- fake 私有语义没有 durable adapter 等价依据。
- 实现端自行补 schema / persistence index。
- 后续正式实现会与设计真相源分裂。

## 十一、恢复上下文规则

实现 agent 在以下场景必须先读取台账：

- 用户说“继续”。
- 上下文压缩后恢复。
- 切换 agent。
- 进入新 commit boundary。
- 准备提交。
- 遇到 blocker 后用户给出设计修复。

读取顺序固定：

```text
1. projects/<project>/design-calibration/implementation_execution_ledger.md
2. projects/<project>/design-calibration/implementation-boundaries/<current_boundary>.md
3. 当前项目 `07-实施计划.md`
4. 当前 boundary 的 required design Step 文档
5. 实现仓本地 `.codex/implementation_ledger.md`，若存在
```

如果项目级实施台账不存在：

- 不得直接实现。
- 必须先创建项目级台账和当前 boundary 台账。
- `gate_status` 先设为 `pending`。
- `next_allowed_action` 先设为 `read_docs`。

## 十三、机器检查建议

项目可以增加脚本检查台账，例如：

```text
scripts/gates/check_implementation_ledger.sh
```

最小检查项：

| 检查项 | 失败条件 |
|---|---|
| required files | 项目级台账或当前 boundary 台账不存在 |
| planned boundary files | `07-实施计划.md` / Boundary Gate Matrix 已列出的未来 boundary 缺少预创建台账骨架 |
| future boundary activation | 未来 boundary 的 `status` 不是 `planned` 或 `next_allowed_action` 不是 `wait_until_current` |
| field values | `gate_status` / `next_allowed_action` 使用非法值 |
| design baseline | baseline 为空或不是 commit hash |
| boundary id | 当前 boundary 为空 |
| commit gate | `commit` 前缺 staged scope、message、whitespace、required checks 证据 |
| blocked rule | `gate_status=blocked` 但 `next_allowed_action=implement` |
| evidence | `pass` 项没有 evidence |

在脚本存在前，agent 仍必须人工按本规范检查并记录证据。脚本是强化，不是规则来源。

## 十四、完成判定

一个 commit boundary 只有同时满足以下条件，才能判定完成：

1. 当前 boundary 台账存在。
2. Design Gate 通过或明确 `not_applicable`。
3. Scope Gate 通过。
4. Worktree Gate 通过。
5. Build Gate / Test Gate 按实施计划通过，或有正式后置说明。
6. Evidence Gate 按实施计划通过，或为 `not_applicable` 且有原因。
7. Commit Gate 通过。
8. commit hash 已写回台账。
9. Handoff Gate 通过。
10. 项目级实施台账已更新到下一动作。

如果任何必要门禁为 `pending` 或 `blocked`，不得声称 boundary 完成。

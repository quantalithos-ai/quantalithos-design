# 全局项目依赖关系与裁剪规则

> 本规范定义 Quantalithos 27 个正式子项目之间的总依赖基线，以及单个子项目在编写需求、架构、详细设计和实施计划时如何从总依赖关系中裁剪自己的依赖子图。
> 总依赖关系来自 `architecture/仓库拆分方案.md` §十一“仓间依赖矩阵”，本文只做写作与讨论约束。

---

## 1. 适用范围

本文适用于所有子项目的：

- `00-需求文档.md`
- `01-架构设计.md`
- `03-详细设计.md`
- `07-实施计划.md`
- 对应 `design-calibration/` 中间产物

本文不替代具体子项目文档。每个子项目只应从本文裁剪出与本仓有关的依赖关系，不能把总依赖矩阵整表复制进单仓文档。

---

## 2. 依赖类型

| 依赖类型 | 含义 | 是否可写入 `Cargo.toml` / package dependency | 常见表达 |
|---|---|---|---|
| 编译期依赖 | 当前仓代码直接引用另一个仓提供的 crate / package / 类型 / trait / DTO / Error。 | 是 | `path dependency`、private git tag / rev、workspace crate |
| 运行期依赖 | 当前仓运行时通过 HTTP / RPC / SDK / adapter / service boundary 消费另一个仓能力。 | 否 | service endpoint、SDK client、adapter binding |
| 事件协作依赖 | 当前仓通过 `L0-bus` 发布 / 订阅事件与另一个仓协作。 | 否 | event publisher、event subscriber、projection |

关键规则：

- 只有编译期依赖可以落为本地 `path dependency`。
- 运行期依赖和事件协作依赖不得直接写成 Cargo path dependency。
- 单仓文档必须说明某条关系属于哪一种依赖类型。

| `L5-chat` | `L0-core` / `L0-sdk` | Conversation / workspace / governance 经 SDK | 不直接订阅内部事件，除非 SDK 提供 | 用户聊天入口 |
| `L5-runner` | `L0-core` / `L0-sdk` | `L4-sandbox` 经正式边界 | 按需通过 SDK 消费状态 | 一键运行 AI 产物 |

| `L5-sync` | `L0-core` / `L0-sdk` | workspace / archive / artifact 经 SDK | 按需通过 SDK 消费状态 | CLI / 同步库 |
| `L5-website` | `L0-core` / 按需 `L0-sdk` 示例 | 文档与公开示例 | 通常不进入内部事件协作 | 静态站点 / 文档站 |

| `L6-marketplace` | `L0-core` / `L0-sdk` | method / tool / role 发布审核能力 | 按需发布生态资产事件 | 资产市场 |

说明：

- `projects/L6-elves` 当前存在旧草案目录，但不属于 `architecture/仓库拆分方案.md` 的 27 仓权威清单；除非后续 ADR 纳入正式架构，否则单仓依赖矩阵不得把它当成正式依赖节点。
- 表中运行期依赖和事件协作依赖必须在单仓文档中再次裁剪和确认。

### 4.1 系统讨论顺序与并行窗口

系统讨论顺序必须从总依赖关系裁剪而来,不是按项目目录名、层级编号或当前关注度排队。已完成系统校准的项目作为上游输入使用;未完成系统校准的项目按依赖层推进。层间必须串行,层内只有在共同上游已经闭口时才允许并行讨论。

```text
Legend:
  [C] calibrated / 已系统讨论,作为当前上游输入
  [P] pending / 待系统讨论或待重新校准
  ==> strong serial dependency / 强串行依赖
  --> soft dependency or consumption boundary / 软依赖或消费边界
  { ... } parallel window / 可并行讨论窗口

CALIBRATED FOUNDATION

  +----------+    +---------+    +--------+
  | L0-core  |    | L0-bus  |    | L0-sdk |
  |   [C]    |    |   [C]   |    |  [C]   |
  +----------+    +---------+    +--------+

  +--------------+  +---------+  +------------+  +-----------------+  +---------------+
  | L1-identity  |  | L1-work |  | L1-process |  | L1-conversation |  | L1-governance |
  |     [C]      |  |   [C]   |  |    [C]     |  |       [C]       |  |      [C]      |
  +--------------+  +---------+  +------------+  +-----------------+  +---------------+

  +-------------------+
  | L3-method-library |
  |        [C]        |
  +-------------------+
            |
            v

LAYER 1: TRUTH SOURCE / CONTROL CLOSURE

  +---------------+       +-------------------+       +------------------+       +-------------+
  | L1-artifact   |  ==>  | L3-capability-hub |  ==>  | L4-observability |  ==>  | L4-sandbox |
  | evidence      |       | capability access |       | audit / metrics  |       | isolation  |
  | lineage [P]   |       | MCP / A2A / API   |       | evidence [P]     |       | [P]        |
  +---------------+       +-------------------+       +------------------+       +-------------+
          |                         |                           |                       |
          +-------------------------+---------------------------+-----------------------+
                                                v

LAYER 2: RUNTIME / TOOLING CORE

                                      +------------+
                                      | L2-tools   |
                                      | [P]        |
                                      +------------+
                                            |
                                            v
                                      +------------+
                                      | L2-runtime |
                                      | [P]        |
                                      +------------+
                                            |
                                            v

LAYER 3: MEMBER RUNTIME PARALLEL WINDOW

               { L2-member [P] | L2-member-service [P] | L2-member-images [P] }
                                            |
                                            v

LAYER 4: CROSS-DOMAIN MATERIALIZATION

                                      +--------------+
                                      | L1-workspace |
                                      | [P]          |
                                      +--------------+
                                            |
                                            v
                                      +------------+
                                      | L4-archive |
                                      | [P]        |
                                      +------------+
                                            |
                                            v

LAYER 5: PRODUCT / DISTRIBUTION PARALLEL WINDOW

        { L5-console [P] | L5-chat [P] | L5-runner [P] | L5-sync [P]
          L6-marketplace [P] | L6-bridges [P] }
                                            |
                                            v
                              { L5-website [P] | L6-elves [P] }
```

执行规则:

- `CALIBRATED FOUNDATION` 中的项目不重新排队,但作为后续项目讨论的正式上游输入;若其中任何正式文档被回归重写,受影响下游必须记录 pending 或 blocker。
- `LAYER 1` 是当前未系统讨论项目的上游 truth / control 闭口层,默认按 `L1-artifact -> L3-capability-hub -> L4-observability -> L4-sandbox` 串行推进。
- `LAYER 2` 必须在 Layer 1 对应边界闭口后推进;`L2-tools` 先于 `L2-runtime`,因为 runtime loop 依赖工具契约和 capability / sandbox 边界。
- `LAYER 3` 只有在 `L2-runtime` 的运行边界稳定后才进入并行窗口;并行讨论时不得互相反向定义 member runtime truth。
- `LAYER 4` 是跨域视图和归档恢复层;`L1-workspace` 必须先收束跨 L1 视图边界,`L4-archive` 再承接归档 / 恢复语义。
- `LAYER 5` 是产品与生态分发表面层;只有在 runtime、workspace / archive、capability 和 governance / artifact 边界稳定后才允许并行讨论。
- `L6-elves` 仍需先做正式定位审查;除非被新的正式架构或 ADR 纳入,不得把它写成其他仓的正式依赖前置。

并行纪律:

- 不同项目可以由不同 agent 并行讨论,但只能在同一并行窗口内进行,且每个 agent 只能修改自己的 `projects/<target>/...` 和必要的标准文件。
- 同一项目内的正式文档仍必须按 `00 -> 01 -> 02 -> 03 -> 04 -> 05 -> 06 -> 07` 串行推进,不得因项目间并行而跳过单项目文档门禁。
- 并行项目读取同一上游时,只能使用已完成并通过停审的正式文档或已明确标记为可引用的中间产物;未稳定上游必须记录为 blocker / pending,不能私自吸收。
- 若并行讨论发现上游边界缺口,应暂停受影响下游章节,把 blocker 回流到 owning 项目的 `design-calibration` flow / ledger,不得在下游项目中自行补上游真相。

## 5. 单仓裁剪输出格式

每个子项目讨论依赖关系时，必须输出以下表格。

### 5.1 本仓依赖裁剪表

| 关联项目 | 全局关系 | 本仓角色 | 依赖类型 | 是否进入当前文档主链 | 裁剪理由 |
|---|---|---|---|---|---|
| `<repo>` | `<来自总依赖矩阵的关系>` | 依赖方 / 被依赖方 / 协作方 | 编译期 / 运行期 / 事件协作 | 是 / 否 | `<为什么进入或不进入>` |

### 5.2 本仓依赖类型分类表

| 依赖类型 | 关联项目 | 本仓如何使用 / 提供能力 | 后续文档落点 |
|---|---|---|---|
| 编译期依赖 | `<repo>` | `<crate / type / contract>` | 详细设计 / 实施计划 |
| 运行期依赖 | `<repo>` | `<API / SDK / adapter>` | 架构设计 / 详细设计 |
| 事件协作依赖 | `<repo>` | `<publish / subscribe / projection>` | 需求 / 架构 / 测试 |

### 5.3 本仓禁止依赖表

| 禁止依赖 | 禁止原因 | 正确协作方式 |
|---|---|---|
| `<repo A> -> <repo B>` | `<违反层级 / 破坏真相边界 / 形成循环>` | `<event / SDK / query / artifact ref>` |

## 6. 单仓裁剪 ASCII 图格式

依赖裁剪类中间产物和正式章节必须按以下格式画图。

````md
#### 依赖裁剪图: <repo-name>

```text
Global baseline
  |
  | crop only related edges
  v
+---------------------+
| <current repo>      |
+----------+----------+
           |
           | [compile/runtime/event]
           v
     <related repo>
```

图示说明：

- 本图只展示 `<repo-name>` 相关依赖，不展示全 27 仓。
- `[compile]` 表示可进入 package dependency；`[runtime]` 和 `[event]` 不得写成 package dependency。
- 箭头表达依赖 / 消费 / 协作方向，不表达调用顺序。
````

图形约束：

- 必须使用 `text` 代码块。
- 图标题必须写成 `#### 依赖裁剪图: <repo-name>`。
- 图中必须标注依赖类型：`[compile]`、`[runtime]`、`[event]`。
- 图后必须写 2~5 条图示说明。
- 单仓图不得把全 27 仓全部画入；只画与当前仓有关的依赖边。
- 不得用该图表达函数调用链、API 时序、事件传播时序或实施顺序。

## 7. 正反例

### 正例

```text
L1-process
  -> [compile] L0-core
  -> [event]   L0-bus
  -> [runtime] L3-method-library
```

解释：

- `L0-core` 可进入编译期依赖。
- `L0-bus` 是事件协作主干，不等于直接依赖某个业务仓。
- `L3-method-library` 是运行期方法定义来源，不应默认写成直接源码依赖。

### 反例

```toml
[dependencies]
quantalithos-method-library = { path = "../quantalithos-method-library" }
```

错误原因：

```text
仅因为 process 运行期消费 method-library，并不能推出 process 应直接依赖 method-library 源码。
必须先判断它是编译期依赖、运行期依赖，还是事件协作依赖。
```

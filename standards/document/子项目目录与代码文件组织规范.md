# 子项目目录与代码文件组织规范

> 本规范定义 Quantalithos 子项目在设计仓目录、实现仓目录、Rust workspace member、Cargo package、Rust crate、binary 和源码文件上的组织与命名规则。
> 它不替代 `standards/coding/rust.md`。Rust 编码规范负责标识符、注释、格式和语言级实践；本文负责工程目录与代码文件组织。

## 1. 适用范围

本文适用于：

- `projects/Lx-xxx/` 设计文档目录
- `/home/aris/Projects/quantalithos-xxx` 实现代码仓
- Rust 单 crate 模块分层仓
- Rust workspace 多 crate 仓
- 详细设计、实施计划和 `design-calibration/` 中涉及目录与命名的中间产物

本文不定义：

- 需求、架构、概要、详细设计的章节结构
- Rust 类型、函数、变量、注释和格式规则
- 公共 crates.io 发布命名策略
- 非 Rust 项目的框架专属目录结构

## 2. 三层命名原则

目录与命名必须分清三层语义。

```text
设计仓目录
  用 L0 / L1 / L2 表达架构层级导航。

实现仓目录
  用 quantalithos-<project> 表达全局项目身份。

代码仓内部目录
  用 crates/<role> 或 src/<module> 表达仓内职责。
```

核心原则：

- 仓库名负责全局唯一身份。
- 仓内目录名负责职责表达。
- Cargo package / Rust crate 名负责跨 crate 引用身份。
- `L0` / `L1` / `L2` 只存在于设计仓和架构文档，不进入代码命名。
- `quantalithos` 前缀只用于实现仓名，默认不进入内部 package / crate 名。
- 公开发布命名策略由单独发布 ADR 决定，不作为当前默认规则。

## 3. 设计仓目录规则

设计仓目录固定使用：

```text
projects/Lx-<project>/
```

示例：

```text
projects/L0-core/
projects/L1-identity/
projects/L3-method-library/
```

标准结构：

```text
projects/Lx-<project>/
  README.md
  00-需求文档.md
  01-架构设计.md
  02-概要设计.md
  03-详细设计.md
  04-配置设计.md
  05-测试方案.md
  06-验收标准.md
  07-实施计划.md
  design-calibration/
  diagrams/
  legacy/
```

约束：

- `design-calibration/` 只放 SOP 中间产物、流程工作台和回填草稿。
- `diagrams/` 只放图源或导出图。
- `legacy/` 只放被替换的旧版正式文档或旧草案。
- 设计仓子项目目录不得放实现代码、临时脚本、构建产物或真实运行状态目录。

## 4. 实现仓目录规则

实现仓默认位于：

```text
/home/aris/Projects/quantalithos-<project>
```

示例：

```text
/home/aris/Projects/quantalithos-core
/home/aris/Projects/quantalithos-bus
/home/aris/Projects/quantalithos-identity
/home/aris/Projects/quantalithos-method-library
```

命名规则：

| 项 | 规则 | 示例 |
|---|---|---|
| 实现仓目录 | `quantalithos-<project>` | `quantalithos-core` |
| project slug | 使用仓名中的项目部分 | `core`、`identity`、`method-library` |
| 不允许 | `L0-core`、`l0_core`、`quantalithos-l0-core` | 架构层级不得进入代码仓名 |

## 5. Rust Workspace 多 Crate 规则

当详细设计选择 workspace 多 crate 架构时，仓内目录使用短职责名。

推荐结构：

```text
quantalithos-<project>/
  Cargo.toml
  crates/
    contracts/
    domain/
    application/
    infra/
    api/
    worker/
    cli/
    jobs/
    ops/
  tests/
```

并非所有仓都必须拥有上述全部 member。每个仓只能创建详细设计已确认的 member。

命名规则：

| 层级 | 规则 | core 示例 | identity 示例 |
|---|---|---|---|
| member 目录 | `crates/<role>` | `crates/domain` | `crates/domain` |
| Cargo package | `<project>-<role>` | `core-domain` | `identity-domain` |
| Rust lib crate | `<project>_<role>` | `core_domain` | `identity_domain` |
| binary package | `<project>-<role>` | `core-cli` | `identity-api` |
| binary name | `<project>` 或 `<action_name>` | `core`、`outbox_relay` | `identity-api` |

说明：

- member 目录不重复项目名前缀，不写 `crates/core_domain`。
- Cargo package 使用 hyphen。
- Rust lib crate 使用 underscore。
- binary 名按用户入口或动作命名；多个 job binary 可使用具体动作名。

## 6. Rust 单 Crate 模块分层规则

当详细设计选择单 crate 模块分层架构时，使用 `src/<module>` 表达仓内职责。

推荐结构：

```text
quantalithos-<project>/
  Cargo.toml
  src/
    lib.rs
    main.rs
    contracts/
    domain/
    application/
    infra/
    api/
    worker/
    ops/
    config/
    observability/
  tests/
```

命名规则：

| 层级 | 规则 | 示例 |
|---|---|---|
| Cargo package | `<project>` 或 `<project>-service` | `identity` / `identity-service` |
| Rust lib crate | `<project>` 或 `<project>_service` | `identity` / `identity_service` |
| 模块目录 | `src/<module>` | `src/domain` |
| 文件名 | `snake_case.rs` | `global_member.rs` |

约束：

- 单 crate 内部模块不得用 `l1_identity_domain.rs` 这类架构层级命名。
- 如果外部仓需要直接依赖本仓 DTO / Error / Event / Snapshot，优先评估 workspace 多 crate，而不是把所有公共契约塞进单 crate。

## 7. 角色目录最小集合

常见 role 名称如下。项目可以裁剪，但不得随意发明同义词。

| role | 适用形态 | 职责 |
|---|---|---|
| `contracts` | workspace / single crate module | DTO、Command、Query、Event、Job、View、Receipt、Error 等公共契约 |
| `domain` | workspace / single crate module | 领域对象、值对象、状态、策略、不变量 |
| `application` | workspace / single crate module | application service、port trait、用例编排、事务边界 |
| `infra` | workspace / single crate module | repository、adapter、runtime wiring、外部系统适配 |
| `api` | workspace / single crate module | HTTP / RPC / inbound API 入口 |
| `worker` | workspace / single crate module | 常驻 worker、consumer、subscriber |
| `cli` | workspace / single crate module | CLI 入口 |
| `jobs` | workspace / single crate module | 一次性 job、operations job、后台任务 binary |
| `ops` | workspace / single crate module | 运维命令、维护工具、人工操作入口 |
| `config` | single crate module | 配置结构、加载、验证、默认值 |
| `observability` | single crate module | log、metric、trace、audit 切口 |

选择约束：

- 同一个项目内不得同时使用 `infra` 和 `infrastructure` 表达同一层职责。
- 同一个项目内不得同时使用 `worker` 和 `jobs` 表达同一类入口；常驻进程用 `worker`，一次性任务用 `jobs`。
- `utils`、`common`、`helper` 不得作为顶层 role。确需共享逻辑时，应归入明确职责模块。

## 8. 文件命名与拆分规则

Rust 文件命名遵守 `standards/coding/rust.md`，并补充以下工程组织规则。

| 对象 | 命名规则 | 示例 |
|---|---|---|
| 目录 | `snake_case` 或短职责名 | `reference_projection` |
| 文件 | `snake_case.rs` | `global_member.rs` |
| 测试文件 | `<feature>_tests.rs` 或 `<interface>_tests.rs` | `hire_global_member_tests.rs` |
| binary 文件 | `<action_name>.rs` | `outbox_relay.rs` |
| module | `snake_case` | `application_services` |
| Rust type | `UpperCamelCase` | `GlobalMember` |
| Rust function | `snake_case` | `hire_global_member` |

拆分原则：

- application 层按用例 / command / query / job 拆分。
- domain 层按聚合、值对象、状态机、领域策略拆分。
- infra 层按 adapter、store、publisher、resolver、runtime wiring 拆分。
- tests 按功能场景、接口场景或风险切口拆分。
- 文件名必须表达职责，不得只写 `service.rs`、`manager.rs`、`helper.rs`、`utils.rs`。

## 9. 实现仓 artifacts 与 reports 目录规则

实现仓必须区分机器原始证据和人类可读报告。

```text
quantalithos-<project>/
  artifacts/
    test/
      <run_id>/
        meta/
          context.json
        evidence-index.json
        suites/
          <suite>/
            report.json
            stdout.log
            stderr.log
  reports/
    README.md
    runs/
      <run_id>/
        summary.md
        evidence-index.md
        gate-results.md
        redaction-check.md
        suites/
          <suite>.md
        evidence/
          EV-<TYPE>-<NNN>.md
    acceptance/
      handoff.md
      veto-checklist.md
      risk-acceptance.md
      open-issues.md
    review/
      reviewer-notes.md
      agent-review.md
```

### 9.1 `artifacts/test/<run_id>` 规则

`artifacts/test/<run_id>` 是机器生成的原始测试证据包。

| 项 | 规则 |
|---|---|
| 目录层级 | 固定为 `artifacts/test/<run_id>/` |
| 禁止层级 | 不得写成 `artifacts/test/<project>/<run_id>/` |
| 典型来源 | gate script、CI、测试框架、benchmark、redaction scan |
| 典型内容 | JSON report、stdout/stderr log、raw evidence index、context metadata |
| 是否入库 | 默认 gitignored；只有项目明确要求时才保存样例 fixture |
| 正式引用 | 必须引用固定 `<run_id>`，不得引用 `latest` |

`run_id` 推荐格式：

```text
<gate-or-suite>-<UTC timestamp>Z
release-gate-20260529T054911Z
release-gate-20260529T054911Z-1732b7c
```

最小文件要求：

| 文件 | 作用 | 格式 |
|---|---|---|
| `meta/context.json` | 记录运行上下文 | JSON |
| `evidence-index.json` | 记录 EV、TC、suite、artifact 路径索引 | JSON |
| `suites/<suite>/report.json` | 单 suite 结构化结果 | JSON |
| `suites/<suite>/stdout.log` | 标准输出 | text |
| `suites/<suite>/stderr.log` | 标准错误 | text |

即使测试失败，也必须尽量产出 `report.json`、stdout/stderr log 和 failure reason。

### 9.2 `reports/` 规则

`reports/` 是从 raw artifacts 生成、并允许人或 Agent 审查补充的人类可读报告目录。

| 项 | 规则 |
|---|---|
| 目录层级 | 固定为 `reports/` |
| 禁止层级 | 不得写成 `reports/<project>/...` |
| 典型来源 | `scripts/reports/*` 从 `artifacts/test/<run_id>` 生成 |
| 审查方式 | 脚本生成初稿后，人或 Agent 可以补充验收说明、风险接受和审查意见 |
| 是否入库 | 由实施计划或验收计划决定；送验用报告通常可以入库或附在交付包 |
| 正式引用 | 引用 `reports/runs/<run_id>/...` 和 `reports/acceptance/...` |

`reports/README.md` 是人类入口，必须说明当前送验 run、关联 artifact root、主要报告和验收交接文件。

`reports/runs/<run_id>/` 保存某次固定运行的可读摘要，不得使用 `latest` 作为正式验收引用。

`reports/acceptance/` 用于送验交接：

| 文件 | 生成方式 | 作用 |
|---|---|---|
| `handoff.md` | 脚本生成初稿，人 / Agent 审查补充 | 给验收方的交付摘要 |
| `veto-checklist.md` | 脚本生成初稿，人 / Agent 确认 | 一票否决项检查 |
| `risk-acceptance.md` | 人 / Agent 主写 | 风险接受说明 |
| `open-issues.md` | 脚本生成初稿，人 / Agent 补充 | 未关闭问题和后续动作 |

### 9.3 证据 JSON 最小字段

`meta/context.json` 至少包含：

```json
{
  "schema_version": "1",
  "run_id": "release-gate-20260529T054911Z",
  "repository": "quantalithos-core",
  "commit": "<commit-sha>",
  "branch": "<branch>",
  "config_profile": "release-like",
  "started_at": "<iso-8601>",
  "finished_at": "<iso-8601>",
  "generated_by": "scripts/gates/run_release_gate.sh"
}
```

`evidence-index.json` 至少包含：

```json
{
  "schema_version": "1",
  "run_id": "release-gate-20260529T054911Z",
  "commit": "<commit-sha>",
  "result": "passed",
  "evidence": []
}
```

每个 suite `report.json` 至少包含：

```json
{
  "schema_version": "1",
  "report_id": "<report-id>",
  "evidence_id": "EV-UNIT-001",
  "run_id": "release-gate-20260529T054911Z",
  "commit": "<commit-sha>",
  "suite": "unit",
  "case_id": "TC-DOM-001",
  "config_profile": "ci-test",
  "result": "passed",
  "started_at": "<iso-8601>",
  "finished_at": "<iso-8601>",
  "command": "cargo test -p domain",
  "exit_code": 0,
  "stdout": "suites/unit/stdout.log",
  "stderr": "suites/unit/stderr.log"
}
```

路径字段默认使用 artifact root 内相对路径。绝对 artifact root 可以只出现在 `meta/context.json`。

### 9.4 安全与引用规则

- artifact 和 report 都不得包含 raw secret、token、private key、credential value 或完整业务正文。
- 允许保存 `secret_ref`、`redacted_ref`、hash、fingerprint、trace_id 和脱敏摘要。
- release gate 必须包含 redaction / boundary scan。
- `latest` 指针仅允许本地调试使用，正式测试、验收和交付不得引用。

## 10. 实现仓 scripts 与测试工具目录规则

实现仓脚本必须放在 `scripts/` 下，不能放在 `reports/` 下。

```text
quantalithos-<project>/
  scripts/
    gates/
      run_ci_gate.sh
      run_release_gate.sh
      run_e2e_gate.sh
    reports/
      generate_reports.sh
      generate_evidence_index.sh
      generate_acceptance_handoff.sh
    checks/
      check_artifacts.sh
      check_redaction.sh
      check_report_links.sh
    dev/
      <local helper scripts>
  crates/
    xtask/                 # 可选；仅当脚本逻辑复杂或需要 Rust 复用时使用
```

| 目录 | 职责 | 是否可作为验收入口 |
|---|---|---|
| `scripts/gates/` | 执行 CI、release、E2E 等门禁 | 是 |
| `scripts/reports/` | 从 `artifacts/test/<run_id>` 生成 `reports/` | 是 |
| `scripts/checks/` | 检查 artifact 完整性、脱敏和 report 链接 | 是 |
| `scripts/dev/` | 本地开发辅助 | 否 |
| `crates/xtask/` | 可选复杂工具实现 | 视命令是否被 gate script 调用 |

脚本命名使用：

```text
<verb>_<object>.sh
```

正确示例：

```text
run_ci_gate.sh
run_release_gate.sh
generate_reports.sh
check_redaction.sh
```

错误示例：

```text
run.sh
test.sh
ci.sh
final.sh
check.sh
gen.sh
```

Gate script 必须支持以下参数：

```text
--run-id <run_id>
--artifact-root <path>
--config-profile <profile>
```

也可以支持对应环境变量：

```text
RUN_ID
ARTIFACT_ROOT
CONFIG_PROFILE
```

优先级固定为：

```text
CLI args > environment variables > defaults
```

默认 artifact root：

```text
artifacts/test/<run_id>
```

Report script 至少应支持：

```text
scripts/reports/generate_reports.sh \
  --run-id <run_id> \
  --artifact-root artifacts/test/<run_id> \
  --report-root reports
```

约束：

- `scripts/reports/*` 只能从固定 `<run_id>` 的 artifacts 生成报告，不得默认读取 `latest`。
- `scripts/checks/check_report_links.sh` 必须能检查 `reports/runs/<run_id>` 是否能回指 `artifacts/test/<run_id>`。
- `scripts/checks/check_redaction.sh` 必须能扫描 artifact 和 report 中的 raw secret / raw body 风险。
- 如果项目不需要某类脚本，实施计划必须说明原因，而不是留下空目录占位。

## 9. 输出表格式

详细设计和中间产物讨论目录与文件组织时，必须输出以下表格。

### 9.1 目录 / Package / Crate / Binary 映射表

| 实现单元目录 | 类型 | Cargo package | Rust crate / binary | 职责 | 是否对外暴露 |
|---|---|---|---|---|---|
| `crates/contracts` | library crate | `core-contracts` | `core_contracts` | 公共契约 DTO | 是 |

### 9.2 文件职责表

| 文件路径 | 所属实现单元 | 定义内容 | 主要责任 |
|---|---|---|---|
| `crates/contracts/src/commands.rs` | `contracts` | Command DTO | 写入口协议 |

### 9.3 命名检查表

| 检查项 | 通过条件 | 结果 |
|---|---|---|
| 实现仓目录 | `/home/aris/Projects/quantalithos-<project>` | 通过 / 不通过 |
| member 目录 | `crates/<role>`，不含项目名前缀 | 通过 / 不通过 |
| Cargo package | `<project>-<role>` | 通过 / 不通过 |
| Rust crate | `<project>_<role>` | 通过 / 不通过 |
| 架构层级泄漏 | 代码命名中不出现 `L0` / `L1` / `l0_` / `l1_` | 通过 / 不通过 |

## 10. 正反例

### 正例：core workspace

```text
quantalithos-core/
  crates/
    contracts/      package: core-contracts      crate: core_contracts
    domain/         package: core-domain         crate: core_domain
    application/    package: core-application    crate: core_application
    infra/          package: core-infra          crate: core_infra
    cli/            package: core-cli            bin: core
    jobs/           package: core-jobs           bin: validate_contract_change
```

### 正例：identity workspace

```text
quantalithos-identity/
  crates/
    contracts/      package: identity-contracts      crate: identity_contracts
    domain/         package: identity-domain         crate: identity_domain
    application/    package: identity-application    crate: identity_application
    infra/          package: identity-infra          crate: identity_infra
    api/            package: identity-api            bin: identity-api
    worker/         package: identity-worker         bin: identity-worker
```

### 反例

```text
quantalithos-core/
  crates/
    core_contracts/
    core_domain/
    l0_core_application/
```

错误原因：

- 仓内 member 目录重复项目前缀。
- 架构层级 `l0` 泄漏进代码命名。
- 目录职责不再是短语义名。

```toml
[package]
name = "quantalithos-core-contracts"
```

当前阶段不建议这样写。`quantalithos-` 已由实现仓名承载，内部 package 默认使用 `<project>-<role>`。公开发布阶段是否改用更长命名由发布 ADR 决定。

## 11. 评审清单

- [ ] 设计仓目录是否使用 `projects/Lx-<project>`。
- [ ] 实现仓目录是否使用 `/home/aris/Projects/quantalithos-<project>`。
- [ ] 是否没有把 `L0` / `L1` / `L2` 写进 package、crate、module、file、type、function 名称。
- [ ] workspace member 目录是否使用 `crates/<role>` 短职责名。
- [ ] Cargo package 是否使用 `<project>-<role>`。
- [ ] Rust lib crate 是否使用 `<project>_<role>`。
- [ ] binary 名是否表达用户入口或具体动作。
- [ ] 文件名是否使用 `snake_case.rs` 并表达职责。
- [ ] 是否没有使用 `utils`、`common`、`helper` 作为顶层职责目录。
- [ ] 目录 / package / crate / binary 映射表是否完整。

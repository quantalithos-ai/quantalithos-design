# 实施计划书写规范

> 实施计划回答 **"如何把已完成的设计按可验证顺序落地为代码"**。
> 它位于详细设计、测试方案、验收标准之后，负责定义实施前置条件、阅读清单、阶段顺序、任务边界、提交纪律、测试门禁、验收嵌入和完成判定。
> 实施计划不是详细设计的重复，也不是测试方案、验收报告、部署手册或个人日程表。

## 一、实施计划的目标

实施计划要解决的问题包括：

1. 实施者开始编码前必须阅读哪些文档、确认哪些配置、遵循哪些规范。
2. 当前仓的实施对象、交付物和非交付物是什么。
3. 哪些功能能力、模块、接口、事件、持久化和测试必须按什么顺序落地。
4. 每个实施阶段的输入、输出、完成判定和提交边界是什么。
5. 测试方案和验收标准如何嵌入实施过程，而不是最后补做。
6. 哪些风险、Spike、待确认项必须前置处理。
7. 什么时候可以暂停、回退、变更计划或判定实施完成。

实施计划不回答：

```text
重新定义需求目标、用户故事、功能需求或验收标准
重新定义架构边界、模块拆分、对象模型或协议细节
重写详细设计中的 struct / enum / trait / API / DDL / 伪代码
展开部署拓扑、告警阈值、运维处置步骤或环境参数全集
编写每日排期、人员工时排班或个人待办流水账
```

实施计划的完成标准是：

```text
其他 agent 可以按实施计划先读正确文档、确认正确环境、按正确顺序实施、
按阶段提交、按门禁验证，并知道每个阶段做到什么程度才可以进入下一阶段。
```

## 二、与上游 / 下游文档的边界

### 2.1 相对需求文档

实施计划承接需求文档中的用户故事、功能需求、非功能需求和验收方向，但不重写需求。

实施计划中允许写：

- 本轮实施覆盖哪些需求编号。
- 哪些需求暂不实施、延期实施或只做 Spike。
- 每个实施阶段覆盖哪些需求能力。

实施计划中禁止写：

- 新增未在需求文档中出现的用户故事。
- 修改需求优先级。
- 用实施便利性改变需求边界。

### 2.2 相对架构设计

实施计划承接架构设计中的系统位置、依赖方向、通信方式、数据所有权和技术取舍。

实施计划中允许写：

- 阶段顺序如何尊重架构依赖。
- 哪些外部仓、外部服务或事件总线能力是实施前置条件。
- 哪些架构红线必须作为实施门禁。

实施计划中禁止写：

- 重新选择通信方式。
- 重新划分仓边界或模块边界。
- 绕过架构红线先做临时实现。

### 2.3 相对概要设计

实施计划承接概要设计中的主要组成部分、关键对象轮廓、接口骨架、处理流和状态机轮廓。

实施计划中允许写：

- 哪些主要组成部分先落地，哪些后落地。
- 哪些关键对象或接口构成阶段完成判定。
- 哪些处理流要先形成可运行纵切。

实施计划中禁止写：

- 重新组织主要组成部分。
- 把概要设计未确认的对象当作正式实现对象。
- 用对象清单代替功能实施顺序。

### 2.4 相对详细设计

实施计划必须以详细设计为直接输入。

详细设计提供：

- 文件布局、模块实现契约和对象实现契约。
- API / Command / Query / Event / Job 协议契约。
- 逐接口函数级处理流。
- 状态机、持久化、事务、一致性、错误、并发和测试切口。

实施计划继续展开：

- 实施阶段与依赖顺序。
- 阶段任务拆分、编写顺序与提交边界。
- 每阶段需要执行的测试与验收门禁。
- 实施风险、暂停点、回退点和完成判定。

实施计划禁止重写详细设计中的字段、函数、协议、DDL 和伪代码。

### 2.5 相对测试方案与验收标准

实施计划必须引用测试方案和验收标准。

| 下游文档 | 实施计划中允许写 | 实施计划中禁止写 |
|---|---|---|
| 测试方案 | 每个阶段需要执行哪些测试切口、自动化命令和证据归档动作 | 重写完整测试策略、测试用例矩阵或专项测试方案 |
| 验收标准 | 每个阶段对应哪些验收门禁、哪些一票否决项必须提前规避 | 重写完整验收标准或替代验收结论 |

### 2.6 相对部署、运维和配置文档

实施计划可以写实施前必须准备的配置、环境和外部依赖，但不替代部署与运维手册。

## 三、实施计划章节主链

正式文档建议使用以下章节顺序：

```text
1. 与上游文档的关系声明
2. 实施目标与范围
3. 实施前置条件与阅读清单
4. 实施对象与交付物清单
5. 实施阶段与依赖顺序
6. 阶段任务拆分、编写顺序与提交边界
7. 测试与验收门禁嵌入
8. 配置、环境与外部依赖准备
9. Spike、风险与待确认事项
10. 回退、暂停与变更控制
11. 提交、评审与交付纪律
12. 实施完成判定
13. 参考
```

### 3.1 主组织轴

实施计划的主组织轴是 **阶段化的可验证功能增量**。

```text
正确组织方式：
  按功能能力 / 纵切链路 / 可验证阶段展开
  每个阶段有明确输入、输出、提交边界、测试门禁和验收门禁

错误组织方式：
  按对象逐个实现
  按函数逐个实现
  按文件逐个实现
  把所有模块混成一笔大提交
  用个人待办替代阶段计划
```

阶段可以引用模块、对象和接口，但阶段本身不应退化成对象清单。

### 3.2 阶段粒度规则

一个实施阶段必须满足：

- 能形成可检查的代码增量。
- 能执行至少一个明确测试切口。
- 能产生明确提交边界。
- 能说明失败时如何暂停、回退或调整。
- 能对应至少一个需求、设计切口或验收门禁。

一个实施阶段不应过大：

```text
错误：
  Phase 1. 完成全部后端

正确：
  Phase 1. 建立成员创建纵切
    覆盖 command -> domain -> repository -> outbox -> query projection 的最小闭环
```

### 3.3 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式实施计划时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/07_implementation_plan_step_06_tasks_commits.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章实施计划结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的实施阶段、提交边界、门禁或回退口径。

实施计划还必须把这些校准来源转译为实施者可执行的阶段阅读门禁：

- 正式 `00`~`07` 文档是实现基线，`design-calibration` 是决策背景和细节追溯，不替代正式文档。
- 当子项目存在 `design-calibration/` 时，实施计划 §3 必须给出“阶段实施前阅读矩阵”，说明每个阶段或 commit boundary 开工前必须补读哪些校准文件。
- 阶段阅读矩阵必须从正式章节的 `校准来源` 和当前阶段范围推导，不能把整个 `design-calibration/` 目录粗暴列为全局必读。
- 如果正式文档与 `design-calibration` 发生冲突，以正式 `00`~`07` 文档为准；如果正式文档表达不清，先阅读对应校准来源；仍不清楚时必须暂停并回报设计缺口。

## 四、通用输出规则

### 4.1 表 / 图 / 清单使用规则

实施计划线整体采用：

- 表格收稳阶段、任务、依赖、门禁和提交边界。
- ASCII 图表达阶段依赖、外部准备和门禁嵌入。
- 清单表达前置阅读、配置检查和完成判定。
- 短文解释阶段拆分依据、风险和取舍。

其中：

- 表格必须有稳定列名，不能退化成自由 checklist。
- ASCII 图必须使用 `text` 代码块。
- 命令示例必须使用 `bash` 代码块。
- JSON / Proto 示例通常不应出现在实施计划；如确需引用，必须说明来自详细设计或配置设计。
- 不得把详细设计中的完整对象、函数、协议和 DDL 复制到实施计划。

### 4.2 ASCII 图统一格式

所有 ASCII 图必须采用以下结构：

````md
#### <图类型>: <图标题>

```text
<ASCII 图正文>
```

关键说明：
- <图表达了什么实施关系>
- <图没有表达哪些详细设计内容>
- <图中最容易误解的边界是什么>
````

ASCII 图写法约束：

- 只使用稳定文本字符：`+ - | / \ > < v ^ [ ] ( ) : .`
- 不使用 Mermaid、PlantUML、Graphviz 或截图。
- 图中节点名必须与正文中的阶段名、模块名、门禁名或外部依赖名一致。
- 箭头旁必须标注关系类型，例如 `depends_on`、`enables`、`gate`、`read`、`verify`。
- 图后必须有 2~5 条关键说明。
- 图不能承载完整任务表、完整测试用例或完整提交说明。

### 4.3 阶段编号规则

阶段使用 `PH-<两位数字>` 编号。

```text
PH-01 前置准备与仓初始化
PH-02 最小纵切链路
PH-03 查询与投影能力
PH-04 状态机与一致性补强
```

编号规则：

- 编号必须稳定，不因标题微调而变化。
- 阶段之间有依赖时，必须在阶段表中显式写出。
- 不允许用 `第一阶段 / 第二阶段` 替代正式编号。

### 4.4 任务编号规则

阶段内任务使用 `IMPL-<阶段号>-<序号>` 编号。

```text
IMPL-02-01 建立 command handler 骨架
IMPL-02-02 接入 domain aggregate
IMPL-02-03 接入 repository port 与 fake repository test
```

任务规则：

- 任务以功能实施动作命名，不以对象名裸命名。
- 任务必须有完成判定。
- 任务必须归属某个阶段。
- 如果任务大到需要多人协作、独立排期或独立验收，应升级为正式 WorkItem，而不是留在实施计划内部。

### 4.5 门禁编号规则

测试与验收门禁使用 `GATE-<两位数字>` 编号。

```text
GATE-01 编译与格式化通过
GATE-02 核心 command 单元测试通过
GATE-03 最小 API 集成测试通过
GATE-04 验收标准 AC-001~AC-004 可判定
```

门禁规则：

- 门禁必须说明验证方式。
- 门禁必须引用测试方案或验收标准中的编号。
- 门禁必须说明失败后的处理口径。

### 4.6 提交边界规则

实施计划必须提前定义提交边界。

提交边界应按：

```text
可验证功能增量
阶段完成点
风险隔离点
跨模块一致性完成点
```

提交边界不应按：

```text
单个 struct
单个函数
单个文件
当天做了什么
无关改动混合
```

提交前必须确认当前项目的提交规范和项目级 git 用户配置。

提交粒度判断：

| 粒度 | 示例 | 结论 | 原因 |
|---|---|---|---|
| 过细 | 每写一个函数、一个 struct 或一个文件就 commit | 不推荐 | 噪音过多，review 和回退价值低 |
| 适中 | 一个可独立验证的功能增量或阶段边界完成后 commit | 推荐 | 能用一句话描述，能独立验证，便于 review 和回退 |
| 过粗 | 多个无关功能、格式化、测试和文档一次性混入 | 不推荐 | diff 不可审查，失败后难以定位和回退 |

判断规则：

- 这次改动能否用一句话说明。
- 这次改动是否对应一个提交边界。
- 这次改动是否已经通过该边界的测试或验收门禁。
- 这次改动是否混入了无关功能、无关格式化或未确认设计变更。

### 4.7 编写代码顺序规则

实施计划必须说明每个阶段内部的推荐编码顺序。

编码顺序的目标不是规定每一行代码先写什么，而是避免实现者在没有行为边界、测试切口和提交门禁的情况下随意铺代码。

推荐顺序：

```text
1. 阅读本阶段输入
2. 确认本阶段对外契约
3. 建立或更新测试切口
4. 实现核心领域 / 应用逻辑
5. 接入 port / adapter / repository / external client
6. 接入 API / command / query / event / job 入口
7. 补齐错误、状态、事务、幂等、审计和日志
8. 运行本阶段门禁
9. 整理证据和文档同步
10. 按提交边界提交
```

写法要求：

- 编码顺序必须服务于阶段目标，不能变成对象清单。
- 优先锁定外部契约和测试切口，再填内部实现。
- 核心规则、状态转换和事务边界必须早于外围优化。
- 测试、证据和文档同步不能留到所有代码完成之后再补。
- 如果阶段内存在特殊顺序，必须在该阶段小节单独说明。

错误示例：

```text
1. 写所有 struct
2. 写所有 repository
3. 写所有 service
4. 最后写测试
```

问题：

- 这是按对象层堆叠，不是按可验证功能增量推进。
- 直到最后才验证，容易积累大范围返工。
- 无法形成清晰提交边界。

### 4.7.1 代码实现批次规则

实施计划必须约束代码实现批次。代码批次不是 commit 的同义词，而是实现者在一个阶段内实际落地代码的最小可验证工作单元。一个 commit 可以包含一个或少数几个强相关代码批次，但每个代码批次都必须能说明输入、输出、验证方式和是否进入提交边界。

推荐实现方式：

```text
先建立模块 / 文件 / 类型 / trait / 函数签名骨架
再按可验证功能切片补实现
每个批次完成后运行对应门禁
批次通过后再判断是否达到提交边界
```

代码批次应按：

```text
一个 command
一个 query
一个状态迁移
一个 repository 方法组
一个 worker / job 最小闭环
一个错误恢复或一致性切片
```

代码批次不应按：

```text
所有 domain 一次写完
所有 repository 一次写完
所有测试最后补
随手改到哪里算哪里
为了凑提交把无关功能揉在一起
```

批次规模规则：

- 单批新增 / 修改代码以 100~300 行为宜。
- 预计单批超过 300 行时，应拆成多个批次。
- 预计单批超过 500 行时，必须拆分，禁止一次性实现。
- 高风险逻辑即使不足 300 行，也应单独批次实现、单独测试、单独 review。
- 高风险逻辑包括状态机、事务、并发、幂等、权限、安全、审计、错误恢复和跨仓同步。

每个代码批次至少要说明：

| 字段 | 说明 |
|---|---|
| 批次编号 | `BATCH-<阶段号>-<序号>` |
| 目标 | 本批次要形成的可验证代码增量 |
| 输入 | 详细设计章节、测试切口、依赖批次 |
| 输出 | 本批次新增 / 修改的模块、函数、测试或证据 |
| 预计规模 | 预计新增 / 修改行数区间，或说明不适合按行数估算 |
| 验证门禁 | fmt / lint / unit / integration / acceptance 中哪些必须执行 |
| 提交关系 | 本批次是否单独提交，或归入哪个提交边界 |

正确示例：

```text
BATCH-02-01 建立 command handler、DTO 和最小测试骨架，预计 120 行，门禁 GATE-01。
BATCH-02-02 接入 aggregate 状态迁移和失败分支，预计 180 行，门禁 GATE-01 / GATE-02。
BATCH-02-03 接入 repository fake 和幂等测试，预计 220 行，门禁 GATE-02。
commit-02-a 在 BATCH-02-01~03 全部通过后提交。
```

错误示例：

```text
BATCH-02-01 完成整个后端。
BATCH-02-02 写所有测试。
BATCH-02-03 修一修能跑。
```

错误原因：

- 批次不可验证，无法判断何时完成。
- 测试被放到最后，无法及时发现设计偏离。
- 批次和提交边界无法对应，review 和回退成本过高。

### 4.7.2 测试脚本、运行证据和报告生成规则

实施计划必须把测试脚本、运行证据和报告生成纳入阶段门禁，不能只写“运行测试”。

固定目录：

```text
scripts/
  gates/
  reports/
  checks/
  dev/

artifacts/test/<run_id>/

reports/
  README.md
  runs/<run_id>/
  acceptance/
  review/
```

实施计划必须说明：

| 项 | 必须说明的内容 |
|---|---|
| gate scripts | 哪些 `scripts/gates/*.sh` 是 PR、CI、release 或 E2E 门禁入口 |
| report scripts | 哪些 `scripts/reports/*.sh` 从 artifact 生成 reports |
| check scripts | 哪些 `scripts/checks/*.sh` 检查 artifact 完整性、脱敏和 report 链接 |
| artifact root | 默认使用 `artifacts/test/<run_id>` |
| report root | 默认使用 `reports/`，其中运行报告进入 `reports/runs/<run_id>` |
| acceptance reports | `reports/acceptance/handoff.md`、`veto-checklist.md`、`risk-acceptance.md` 的生成和审查责任 |
| review reports | 人 / Agent 审查意见进入 `reports/review/` |

Gate script 必须支持：

```text
--run-id <run_id>
--artifact-root <path>
--config-profile <profile>
```

也可以支持环境变量：

```text
RUN_ID
ARTIFACT_ROOT
CONFIG_PROFILE
```

优先级固定为：

```text
CLI args > environment variables > defaults
```

阶段门禁写法示例：

```text
PH-06 release gate:
1. run scripts/gates/run_release_gate.sh --run-id <run_id> --artifact-root artifacts/test/<run_id> --config-profile release-like
2. run scripts/checks/check_artifacts.sh --run-id <run_id> --artifact-root artifacts/test/<run_id>
3. run scripts/checks/check_redaction.sh --artifact-root artifacts/test/<run_id> --report-root reports
4. run scripts/reports/generate_reports.sh --run-id <run_id> --artifact-root artifacts/test/<run_id> --report-root reports
5. human / Agent review reports/acceptance/handoff.md and reports/acceptance/veto-checklist.md
```

约束：

- 不得使用 `artifacts/test/<project>/<run_id>`。
- 不得使用 `reports/<project>`。
- 生成报告的脚本不得放在 `reports/` 输出目录下。
- 正式交付和验收不得引用 `latest`。
- `reports/acceptance/*` 可以脚本生成初稿，但必须在人 / Agent 审查后才能作为验收交接依据。
- raw secret、token、private key、credential value 或完整业务正文不得进入 artifacts 或 reports。

当 report generator 的脚本能力早于最终送验证据落码时,实施计划必须按 commit boundary 明确区分:

| 成熟度 | 含义 | 允许阶段示例 |
|---|---|---|
| script capability | 参数、path shape、failure summary、redaction 初稿可独立运行 | release scripts boundary |
| minimal evidence index shell | 从 `artifacts/test/<run_id>/evidence-index.json` 渲染最小 `reports/runs/<run_id>/evidence-index.md`,只证明链接形态可解析 | release scripts boundary |
| final EV detail pages | `reports/runs/<run_id>/evidence/EV-*.md` 齐全并被完整 index 引用 | final reports boundary |
| acceptance handoff | `reports/acceptance/*` 生成初稿并经人 / Agent 审查补充 | final handoff boundary |

不得在一个 boundary 中写“交付 report generator”,另一个 boundary 中又笼统写“生成 evidence index”,导致实现者无法判断当前脚本是否必须生成 `evidence-index.md`。若早期 boundary 只允许最小 index 壳,必须明确禁止最终 EV 明细页和验收结论。

### 4.7.3 编码前设计闭环复核规则

实施计划必须要求实现者在每个 phase / commit boundary 开工前完成设计闭环复核。该复核用于确认当前阶段不需要实现者自行补字段、选状态名、改 DTO 或调整 phase scope。

正式设计准备移交给实现 agent 前,实施计划还必须要求按 phase / commit boundary 对正式 `03-详细设计.md`、`05-测试方案.md`、`06-验收标准.md` 和 `07-实施计划.md` 做一次整体可落码闭环审计。标准存在不等于当前项目文档已经符合标准;审计未通过时不得移交实现,必须先回写设计真相源并固定新的 design baseline。

每个 phase / commit boundary 至少输出：

| 复核项 | 检查内容 | 失败处理 |
|---|---|---|
| 字段闭环 | 当前阶段涉及的 Domain 必填字段是否都有 DTO / event / 派生来源 | 暂停并回报设计缺口 |
| DTO 构造闭环 | 当前阶段输入契约是否能构造目标对象 | 暂停并回报设计缺口 |
| 状态闭环 | 当前阶段测试和验收是否使用详细设计正式状态名 | 暂停并回写设计文档 |
| phase boundary | 当前阶段是否依赖后续 phase 才实现的对象、结果或证据 | 暂停并调整实施计划或设计 |
| 证据闭环 | 当前阶段门禁是否能产生测试 / 验收证据 | 补齐测试或验收门禁 |
| 命名一致性 | 字段、函数、状态、测试、证据是否存在旧名或口语名 | 回写设计文档并同步实施计划 |

交付实现前整体审计至少输出：

| 审计项 | 内容 | 失败处理 |
|---|---|---|
| 审计范围 | 按 `07` 的每个 phase / commit boundary 复核正式 `03/05/06/07` | 补审缺失 boundary 或缺失文档 |
| 适用标准项 | 映射 `设计真相源闭环与可落码性标准.md` §九的适用项 | 回到标准逐项复核 |
| blocker | 记录冲突文件、章节、影响 boundary 和建议口径 | 回写设计真相源 |
| baseline | 记录审计通过所依赖的 design baseline / commit | 未固定 baseline 不移交实现 |

正确示例：

```text
commit-04-b 开工前检查:
- CommittedOutboxFactInput 含 core_event_ref、delivery_mode、target_scope。
- core_event_ref 不得由 core_event_envelope_ref 代替。
- PublicationMaterial::from_outbox_fact(...) 可以构造完整 material。
- 缺字段时本阶段返回 rejected，不继续进入 delivery。
```

错误示例：

```text
先实现 commit-04-b，缺字段时在代码里临时加默认值。
core_event_envelope_ref 先当 core_event_ref 用，后面再修。
测试名称继续用 dispatched / completed。
```

错误原因：

- 实现者自行做了设计取舍。
- 代码会偏离正式详细设计。
- 后续测试、验收和提交边界会继续扩大冲突。

### 4.8 提交时机规则

实施计划必须说明 commit 的时机。

推荐提交时机：

```text
阶段前置准备完成且可独立审查
最小纵切链路打通且门禁通过
高风险 Spike 有明确结论
跨模块一致性修改完成且门禁通过
阶段完成且测试 / 验收证据已归档
设计偏离已回写文档并完成复核
```

不应提交的时机：

```text
代码尚不能编译
阶段门禁未跑或失败
只改了半个对象或半个函数
无关格式化、功能、测试、文档混在一起
设计已经偏离但没有回写文档
为了保存进度而提交不可审查的 WIP
```

写法要求：

- 每笔提交必须对应一个提交边界。
- 提交前必须通过该边界声明的门禁。
- 提交 message 必须遵循项目提交规范，并参考历史提交。
- 项目要求固定 footer 时，只保留项目规定的 footer。
- 除非项目明确允许，不提交 `WIP`。

### 4.9 Commit 规范完整规则

实施计划必须完整说明 commit 规则，不能只写“按规范提交”。如果目标实现仓已有更严格的提交规范，本章应引用目标仓规范，并说明与本规则的差异。

除当前 `quantalithos-design` 文档仓有项目级例外外，其他实现代码仓默认采用本节的英文 commit 规范。

#### 4.9.1 提交时机与粒度

提交时机：

每完成一个 `§6` 中定义的 commit boundary，必须进行一次 commit。不要攒一堆不相关的改动一次性提交，也不要一个函数、一个文件或一个子模块一个 commit。

| 粒度 | 判断标准 | 是否合格 | 原因 |
|---|---|---|---|
| 过细 | 每写一个函数、一个 struct 或一个文件就 commit | 不合格 | 噪音太多，git log 不可读，review 价值低 |
| 适中 | 一个可独立验证的功能模块、阶段边界或风险隔离点完成后 commit | 合格 | 能用一句话描述，能独立验证，便于 review 和 revert |
| 过粗 | 一整个大阶段、多个无关功能或格式化 / 测试 / 文档混成一笔 | 不合格 | 无法定位问题，无法回退单个功能 |

判断“该不该 commit”的简单规则：

- 这次改动能用一句话描述吗。能，则可以进入提交判断。
- 这次改动包含两个不相关的功能吗。是，则拆成两个 commit。
- 这次改动的测试和阶段门禁通过了吗。通过，才允许 commit；未通过，不提交半成品。
- 这次改动是否对应 §6 中一个明确提交边界。不能对应，则先调整提交边界。
- 如果一个 commit boundary 内部包含多个协作子功能，仍然保留为一笔提交，不按文件或子模块拆成多笔；但 body 必须按子功能分组说明。
- 如果实施计划要求若干中间步骤最后合并为一笔提交，应在本地整理提交历史，最终只保留那一笔合规提交。

#### 4.9.2 Commit message 基本结构

实现代码仓 commit 必须遵循以下结构：

```text
<type>(<scope>): <subject>

One-sentence summary for this commit boundary:

Sub-feature group A:
- file_a.rs (+12): concise functional summary.
- file_b.rs (~+80/-10): concise functional summary.

Sub-feature group B:
- file_c.rs (+34): concise functional summary.
- file_d.rs (+9): concise functional summary.

Co-Authored-By: Codex <noreply@openai.com>
```

说明：

- 标题格式固定为 `<type>(<scope>): <subject>`，`scope` 必填；目标仓更严格规则只能叠加，不能放宽固定标题要求。
- 提交信息必须使用英文。
- `subject` 要短，直接描述这笔提交的功能边界。
- `body` 必须使用英文。
- `body` 必须先用一句话说明本 commit boundary，再按子功能分组列文件。
- `body` 里的文件条目只写文件名，不写完整路径。
- 每个文件条目必须带大致改动量，例如 `(+3)`、`(-35)`、`(~38)`、`(~+330/-60)`。
- `body` 不能写字面量 `\n`，必须使用真实换行。
- bullet 之间不要插空行。
- `Co-Authored-By: Codex <noreply@openai.com>` 默认保留。
- `Co-Authored-By` 前必须空一行。
- 当需要精确控制格式时，不要依赖多次 `git commit -m` 拼接；应把完整 message 写到文件里，再使用 `git commit -F` 或 `git commit --amend -F`。

Type 列表：

| Type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复 Bug |
| `refactor` | 重构，不改变外部行为 |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 构建、工具、依赖或杂项维护 |
| `perf` | 性能优化 |
| `ci` | CI / CD 变更 |
| `style` | 代码格式，不影响逻辑 |

Scope 列表按项目实际情况调整。可选示例：

```text
project | workitem | artifact | agent-config | snapshot | event | api | common | design | integration | knowledge
```

#### 4.9.3 语言边界

| 场景 | commit message | 文档 / 代码注释 | 说明 |
|---|---|---|---|
| 当前 design 文档仓 | `type` 使用英文，`subject` 和 `body` 使用中文，footer 使用项目固定文本 | 设计文档正文、伪代码说明和示例注释允许中文 | 仅 `quantalithos-design` 属于此类 |
| 其他实现仓 | commit message 必须使用英文，标题格式固定为 `type(scope): subject`；目标仓更严格规则只能叠加，不能放宽英文 commit 和固定标题要求 | 源码标识符、rustdoc、普通注释、测试名默认只使用英文 | 不得继承 design 仓中文 commit 口径 |

实现代码仓如果确需出现中文，只能作为明确的业务数据、协议样例、国际化资源或测试夹具，并应在实施计划中单独说明原因和落点。

#### 4.9.4 Footer 规范

每次 commit 如果有 AI 参与编写，必须在 footer 中标注 `Co-Authored-By`，除非项目明确规定人工独立提交或不使用 AI 注脚。实现代码仓默认保留：

```text
Co-Authored-By: Codex <noreply@openai.com>
```

该 footer 前必须有一个真实空行。

通用注脚格式：

```text
Co-Authored-By: <模型显示名> <邮箱>
```

通用 AI 注脚表：

| AI 模型 | 注脚 |
|---|---|
| Claude (Anthropic) | `Co-Authored-By: Claude <noreply@anthropic.com>` |
| ChatGPT (OpenAI) | `Co-Authored-By: ChatGPT <noreply@openai.com>` |
| Codex (OpenAI) | `Co-Authored-By: Codex <noreply@openai.com>` |
| Gemini (Google) | `Co-Authored-By: Gemini <noreply@google.com>` |
| DeepSeek | `Co-Authored-By: DeepSeek <noreply@deepseek.com>` |
| Kiro (AWS) | `Co-Authored-By: Kiro <noreply@kiro.dev>` |
| 其他模型 | `Co-Authored-By: <模型名> <noreply@<厂商域名>>` |

通用规则：

1. 一次 commit 只标注实际参与的模型。人工独立编写时，可以不加 `Co-Authored-By`。
2. 如果多个模型参与同一次 commit，且项目允许多注脚，每个模型各占一行。
3. 模型名写产品名而非版本号。写 `Claude` 不写 `Claude Opus 4`；写 `Codex` 不写 `Codex 5.4`；写 `ChatGPT` 不写 `GPT-4o`。
4. 同一厂商的不同产品线要区分。ChatGPT 和 Codex 虽然都是 OpenAI，但产品定位不同，应分开标注。
5. 邮箱统一用 `noreply@<厂商域名>`，不要用个人邮箱或虚构邮箱。

项目覆盖规则：

- 如果项目规定固定 footer，则以项目固定 footer 为准，不展开通用多模型注脚。
- 当前 `quantalithos-design` 固定 footer 为：

```text
Co-Authored-By: Codex <noreply@openai.com>
```

其他 footer 场景：

| 场景 | footer 内容 |
|---|---|
| 关联 issue | `Closes #42` 或 `Refs #42` |
| 破坏性变更 | `BREAKING CHANGE: <description>` |

footer 中各项顺序：

```text
Co-Authored-By
Closes / Refs
BREAKING CHANGE
```

#### 4.9.5 Commit Body 格式

body 是 commit message 中最重要的部分。它应让 reviewer 不看 diff 也能理解这次改动做了什么。

核心规则：

```text
按子功能分组，每组一句话总结 + 文件列表。
```

body 的结构：

```text
One-sentence summary for this commit boundary:

<Sub-feature group A>:
- <file_name> (<change-size>): <concise functional summary>.
- <file_name> (<change-size>): <concise functional summary>.

<Sub-feature group B>:
- <file_name> (<change-size>): <concise functional summary>.
```

每一行的格式拆解：

| 部分 | 规则 | 正确示例 | 错误示例 |
|---|---|---|---|
| 文件名 | 只写文件名本身，不带目录路径 | `executor.py` / `实施计划书写规范.md` | `quantalithos_runtime/engine/executor.py` |
| 行数标记 | `+` 表示新增行数，`-` 表示删除行数，`~` 表示修改行数，可组合表达大致变化 | `(+3)` / `(-35)` / `(~38)` / `(~+330/-60)` | `(120 lines)` |
| 文件描述 | 一句话说明这个文件改了什么，用动词开头 | `implement multi-round think-act loop` | `think-act loop` |
| 子功能分组 | 一句完整描述，说明这组改动的目的，末尾加冒号 | `Basic query handlers and HTTP routes:` | `Task scheduling:` |

语言要求：

- 当前 design 文档仓使用中文功能总结和中文文件描述，但 `type` 保持英文。
- 其他实现仓使用英文 subject、英文 summary、英文子功能分组和英文文件描述；目标仓更严格规则只能叠加，不能放宽英文要求。

格式要求：

- 标题后必须空一行再写 body。
- `Co-Authored-By` 前必须空一行。
- bullet 之间不要插空行。
- body 中不得出现字面量 `\n`。
- 需要精确控制格式时，使用 `git commit -F <message-file>` 或 `git commit --amend -F <message-file>`。

功能总结的写法：

#### 4.9.7 Commit 自检清单

每次 commit 前必须对照以下清单检查：

- [ ] subject 是否用一句话概括了这次改动的目的。
- [ ] 实现代码仓标题是否固定为 `<type>(<scope>): <subject>`，且 `scope` 已填写。
- [ ] commit 是否只做了一件事，或一个阶段的完整可验证交付。
- [ ] commit 是否对应 §6 中一个明确的 commit boundary。
- [ ] 如果一个 commit boundary 包含多个协作子功能，是否仍保留为一笔提交，并在 body 中按子功能分组。
- [ ] body 是否先用一句话说明本 commit boundary，再按子功能分组。
- [ ] 每个文件是否只写了文件名，不带目录路径。
- [ ] 每个文件是否标注了增删改行数。
- [ ] 每个文件是否有一句话描述改动内容。
- [ ] 子功能分组是否是完整句子，而不是名词标签。
- [ ] body 中是否没有字面量 `\n`。
- [ ] bullet 之间是否没有插入空行。
- [ ] `Co-Authored-By` 前是否有一个真实空行。
- [ ] 如果提交到当前 design 文档仓，subject 和 body 是否使用中文，`type` 是否使用英文。
- [ ] 如果提交到其他实现仓，subject、body、源码标识符、rustdoc、普通注释和测试名是否使用英文，并符合目标仓更严格规范。
- [ ] 需要精确控制格式时，是否使用完整 message 文件执行 `git commit -F` 或 `git commit --amend -F`。
- [ ] 如果有 AI 参与，是否标注了项目要求的 `Co-Authored-By`。
- [ ] 如果项目要求固定 footer，是否只保留项目规定的 footer。
- [ ] 如果项目允许多模型 footer，是否每个实际参与模型各占一行。
- [ ] 该提交边界要求的 fmt / lint / test / acceptance 是否通过。
- [ ] 设计偏离、接口变化或验收口径变化是否已回写文档。

### 4.10 正式章节必须保留校准来源入口

整理正式实施计划时，每个正式章节开头必须回答：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~13。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/07_implementation_plan_step_06_tasks_commits.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/07_implementation_plan_step_06_tasks_commits.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解阶段任务拆分、编写顺序与提交边界如何从详细设计、测试方案和验收门禁收敛而来。
```

#### Agent 启动与永久记忆种子

本小节定义实现 agent 开工时可以写入项目永久记忆的唯一来源。永久记忆不是 agent 自由总结,而是本小节种子表的机械投影。没有种子表时,实现 agent 不得自行生成项目永久记忆。

永久记忆只保存执行规则和规范索引,不保存详细设计 truth。详细设计字段 schema、状态矩阵、DTO 表、业务规则正文、测试用例全文和临时 blocker 细节不得复制进永久记忆;只能通过来源文档和章节被索引。

| 记忆 ID | 适用范围 | 类别 | 必须写入的记忆文本 | 规范路径来源 | 来源文档 | 来源章节 | 刷新触发 | 失效条件 | 冲突处理 | 禁止改写 |
|---|---|---|---|---|---|---|---|---|---|---|
| MEM-<PROJECT>-001 | project / phase / commit-boundary | 必读规范 | 开始任何代码、配置、脚本或测试改动前,必须读取当前 boundary 所属技术栈的编码规范、项目提交规范和目录组织规范;具体路径以 `07-实施计划.md` §3 阅读清单为准,不得自行猜测。 | `07-实施计划.md` §3 阅读清单 | `07-实施计划.md` | §3.x | 项目首次开工 / 技术栈或规范路径变更 | until superseded | 正式文档优先,暂停并刷新记忆 | 是 |
| MEM-<PROJECT>-002 | commit-boundary | 工作区安全 | 提交前只暂存当前 boundary 相关文件,不得暂存或改写用户已有未提交改动。 | 不适用 | `07-实施计划.md` | §10 | 每次提交前 | until superseded | 暂停并重新核对暂存区 | 是 |
| MEM-<PROJECT>-003 | project / phase / commit-boundary | 交付实现前闭环审计 | 在把项目交给实现 agent 或进入新的实现 baseline 前,必须按 `设计真相源闭环与可落码性标准.md` 对正式 `03/05/06/07` 做一次按 phase / commit boundary 的可落码闭环审计;标准存在不等于当前项目文档已符合标准,未通过时先回写 design repo 并固定新 baseline。 | `07-实施计划.md` §3 阅读清单 / `设计真相源闭环与可落码性标准.md` | `07-实施计划.md` | §3.x / §12 | 实现交付前 / design baseline 变化 / 进入新实现 baseline | until superseded | 暂停移交实现并回写设计真相源 | 是 |

字段要求：

- `记忆 ID` 必须稳定,建议使用 `MEM-<PROJECT>-NNN`,不得复用旧 ID 表达新规则。
- `适用范围` 只能写 `project`、`phase`、`commit-boundary` 或项目正式定义的更小范围。
- `必须写入的记忆文本` 必须是一句可执行规则,不得使用“建议”“尽量”“看情况”等弱约束。
- `规范路径来源` 必须指向阅读清单或写 `不适用`;不得在通用标准中硬编码某一种语言规范。
- `来源文档` 和 `来源章节` 必须能定位到正式 `00`~`07` 或标准文档。
- `刷新触发` 必须说明什么时候重新写入或核对该记忆。
- `失效条件` 必须说明该规则何时失效;长期规则写 `until superseded`。
- `冲突处理` 必须说明永久记忆与正式文档冲突时的处理,默认是正式文档优先并刷新记忆。
- `禁止改写 = 是` 时,agent 只能逐字写入,不得概括、扩写或合并。

生成门禁：

| 检查项 | 通过标准 | 失败处理 |
|---|---|---|
| 种子表存在 | 本小节有固定表,且至少覆盖必读规范、提交纪律、工作区安全和设计缺口暂停规则中的适用项 | 不生成永久记忆,暂停并要求补实施计划 |
| 只写表内内容 | 永久记忆逐条来自 `必须写入的记忆文本` | 删除自由总结内容并回到种子表 |
| 来源完整 | 每条记忆有来源文档、来源章节、刷新触发和冲突处理 | 不写入该条记忆 |
| 交付实现前审计 | 种子表必须包含实现交付前按 phase / commit boundary 审计正式 `03/05/06/07` 的规则 | 不生成永久记忆,暂停并补实施计划 |
| 技术栈不硬编码 | 语言 / 框架 / 目录规范路径来自阅读清单 | 暂停并补阅读清单 |
| 不复制设计 truth | 不写 DTO 字段表、状态矩阵、业务规则正文或测试用例全文 | 删除该内容,改为索引正式文档 |
| 临时规则有失效条件 | owner 临时约束必须标注 `失效条件` | 不写入永久记忆 |

禁止项：

- 禁止让 agent 根据对话或全文阅读结果自由生成永久记忆。
- 禁止把临时对话要求写成永久规则,除非已进入种子表并写明失效条件。
- 禁止把详细设计 schema、状态矩阵、DTO 字段表、测试用例全文复制进永久记忆。
- 禁止把某一种语言规范作为所有项目默认;多语言项目必须按 boundary 指向对应规范。
- 禁止用永久记忆替代正式设计文档;冲突时必须以正式文档为准。

#### 本地多仓依赖前置

| 依赖仓库 | 全局依赖类型 | 本地路径 | 当前引用方式 / 协作方式 | 检查方式 | 不存在时处理 |
|---|---|---|---|---|---|
| `quantalithos-core` | 编译期依赖 | `/home/aris/Projects/quantalithos-core` | 本地 path dependency | 检查目录和 `Cargo.toml` | 暂停依赖真实类型的阶段，或按测试方案使用 fixture / fake |

写法要求：

- 当前阶段不要求发布到公共 crates.io。
- 当前阶段不默认要求通过 GitHub 引用已实现仓库。
- 只有需求 / 架构 / 详细设计中已经确认的编译期依赖，才能写本地 path dependency。
- 运行期依赖和事件协作依赖必须写 API / SDK / adapter / event / projection / fake 等协作方式，不得写成本地 path dependency。
- 中期方案可以记录为 private git dependency，并固定 tag 或 rev。
- 具体 Cargo path 必须以依赖仓真实 crate 布局为准。

#### 开工前设计闭环复核

开工前设计闭环复核必须遵守 `standards/document/设计真相源闭环与可落码性标准.md`。下表是阶段 / commit boundary 的最小承载格式，实际项目不得删减该标准要求的复核项。

| 复核项 | 检查内容 | 失败处理 |
|---|---|---|
| 字段闭环 | <本阶段涉及的 Domain 必填字段来源是否完整> | 暂停并回报设计缺口 |

| artifact materialization 闭环 | <runner 是否能解析 artifact location> | 暂停并回报设计缺口 |
| phase boundary | <是否引用后续 phase 对象 / 结果 / 证据> | 调整阶段或回写设计 |

写法要求：

- 任务必须以实施动作命名。
- 任务必须写明阶段内编写顺序。
- 每个阶段必须说明代码实现批次，批次必须有目标、输入、输出、预计规模、验证门禁和提交关系。
- 每个阶段或 commit boundary 必须说明开工前设计闭环复核，至少覆盖 `设计真相源闭环与可落码性标准.md` §九的所有适用项。
- 单批预计超过 300 行应拆分；超过 500 行必须拆分；高风险逻辑即使不足 300 行也应单独批次实现。
- 提交边界必须说明包含和不包含。
- 提交边界必须说明 commit 时机。
- 不允许把多个无关阶段合成一个提交。
- 不允许把未验证代码作为阶段完成。

| 检查项 | 通过条件 |
|---|---|
| git 配置 | `user.name`、`user.email` 符合项目要求 |

| 提交信息 | subject、body、footer 符合项目提交规范和历史风格 |
| 标题格式 | 实现代码仓使用 `<type>(<scope>): <subject>` |

- 必须要求提交前阅读提交规范和历史提交。

- 必须要求提交时机与 §6 的提交边界一致。
- 必须禁止把格式化、设计变更、功能实现、测试补充混成不可审查的一笔。
- 必须要求一笔提交对应一个 §6 commit boundary；同一 boundary 内的多个协作子功能按 body 分组，不按文件或子模块拆成多笔。
- 提交注脚如项目要求使用固定 footer，必须在本章说明。

## 八、正反例

### 8.1 正确示例

| 阶段编号 | 阶段名称 | 实施目标 | 依赖阶段 | 核心交付物 | 阶段门禁 |
|---|---|---|---|---|---|
| PH-02 | 创建成员最小纵切 | 打通 API -> application -> domain -> repository 的创建闭环 | PH-01 | command handler / aggregate / repo fake / unit tests | GATE-01 / GATE-02 |

说明：

- 阶段按功能纵切命名。
- 阶段有依赖、交付物和门禁。
- 实施者知道本阶段完成后可以提交什么。

### 8.2 错误示例

```text
第一阶段：写 GlobalMember
第二阶段：写 ProjectMember
第三阶段：写 Repository
第四阶段：写测试
```

问题：

- 这是按对象拆分，不是按可验证功能增量拆分。
- 每阶段都缺少输入、输出、门禁和提交边界。
- 测试被放到最后，无法形成阶段验证。
- 无法判断每个阶段是否真的完成。

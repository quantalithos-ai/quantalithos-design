## 一、架构设计的目标

架构设计要回答的问题包括：

1. 这个仓在全局系统中的位置是什么
2. 它和哪些仓或系统交互
3. 它拥有哪些边界与真相
4. 它内部按什么架构风格组织
5. 哪些依赖方向被允许
6. 哪些数据由它拥有，哪些只是引用或快照
7. 哪些关键技术选型被采用，为什么
8. 哪些方案被放弃，为什么
9. 哪些横切关注点需要提前约束
10. 未来如何演进

架构设计不回答：

```text
数据库表结构
Rust 结构体字段
handler 伪代码
repository 函数细节
文件目录树
具体测试用例
迁移脚本
```

这些内容属于概要设计、详细设计、测试方案或实施计划。

## 二、架构设计的章节主链

正式文档建议使用以下章节顺序：

```text
1. 与上游文档的关系声明
2. 业务背景与驱动力
3. 约束条件
4. 职责边界
5. 系统边界与上下文
6. 限界上下文与子域划分
7. 容器 / 部署架构
8. 依赖方向与层间约束
9. 数据所有权与一致性策略
10. 关键交互与通信方式
11. 关键技术选型
12. 备选方案与取舍
13. 横切关注点
14. 演进路线
15. 风险与待确认事项
16. 需求追溯矩阵
17. ADR 索引
18. 参考
```

### 2.1 过程与结果的关系

- `架构设计讨论流程_SOP.md` 负责定义讨论步骤。
- `架构设计书写规范.md` 负责定义最终文档结构。
- 前者收敛结论，后者承接结果。

## 三、总体写作原则

### 3.1 先需求基线，后架构推导

架构设计必须建立在已经收敛的需求基线之上。
如果需求边界和核心能力还不稳定，架构推导就会失真。

### 3.2 先边界，后实现

架构设计首先要讲清：

```text
系统边界
职责边界
依赖方向
数据所有权
一致性层次
```

而不是过早写实现细节。

### 3.3 先系统位置，后组件细节

架构设计先回答“它在全局系统中的位置”，再回答“内部如何组织”。

### 3.4 不确定项不脑补

凡是架构上尚未关闭的问题，必须进入风险与待确认事项，不要用主观判断替代结论。

## 四、章节级规范

### 4.1 与上游文档的关系声明

#### 4.1.1 本章目标

说明本文在架构层承接哪些上游文档结论，明确这篇架构设计不是另起一套定义，而是在当前仓上做结构性细化。

#### 4.1.2 本章输入

- 当前仓对应的需求文档
- 上游产品文档中的相关主题
- 全局架构文档中的仓级定位与边界结论

#### 4.1.3 本章输出

- 上游文档来源表
- 收束说明短文

#### 4.1.4 本章应回答的问题

```text
1. 本文承接哪些上游文档？
2. 承接的是上游哪一部分主题？
3. 本文在当前仓的架构层细化什么内容？
4. 本文不重新定义哪些上游边界或概念？
```

#### 4.1.5 本章不应回答的问题

```text
- 不写架构需求基线清单
- 不写架构目标与约束
- 不写系统上下文图
- 不写职责边界
- 不写容器、数据所有权或技术选型细节
```

#### 4.1.6 推荐表达形式

##### 主表达形式
- 上游文档来源表
- 收束说明短文

##### 固定结构表

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|

#### 4.1.7 粒度要求

- 只写文档来源、承接主题和本文的架构层细化范围
- 不展开为需求基线清单、边界清单或架构约束表
- 不重写上游文档原文

#### 4.1.8 完成标准

- 已明确本文承接的上游文档与主题
- 已说明本文不重新定义什么
- 没有滑入架构约束、系统上下文、职责边界或实现层内容

#### 4.1.9 正反例

**正确示例（identity）：**

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|
| `00-需求文档.md` | `目标与非目标 / 核心能力闭环 / 数据需求与数据归属` | `L1-identity` 已收稳的需求边界、核心能力、数据归属与非功能前提 |
| `product/最终目的.md` | `AI 员工是有身份的个体` | 平台级成员身份主题的产品来源 |
| `product/六域模型.md` | `Identity 域` | Identity 域在架构层的仓级边界与结构来源 |
| `architecture/仓库拆分方案.md` | `L1-identity 仓职责定义` | `L1-identity` 的全局仓级定位来源 |

本文在架构层首先承接 `L1-identity` 已收稳的需求文档结论，再向上追溯到产品叙事、六域模型和全局仓级定位文档。本文不重新定义需求边界，只把这些边界转译为系统结构、依赖和取舍。

**错误示例 A：把需求基线清单写进 4.1**

```text
GlobalMember 为真相，RoleCatalogEntry 为快照，MemoryRef 为引用。
```

错误原因：
```text
这已经进入需求基线或数据所有权层，不属于来源声明。
```

**错误示例 B：把系统上下文图画进 4.1**

```text
L3-method-library -> L1-identity -> L1-work
```

错误原因：
```text
这已经进入系统边界与上下文章节，不属于来源声明。
```

### 4.2 业务背景与驱动力

#### 4.2.1 本章目标

说明为什么值得为这个仓单独做架构设计，明确当前仓在产品 / 系统推进中的结构性驱动力，并给出架构必须确保成立的核心结构目标。

#### 4.2.2 本章输入

- 已收敛的架构需求基线清单
- 当前仓在产品与系统推进中的问题背景
- 当前仓的上游全局架构约束

#### 4.2.3 本章输出

- 业务背景结论
- 驱动力结论
- 架构目标表

#### 4.2.4 本章应回答的问题

```text
1. 当前仓为什么值得单独做架构设计？
2. 当前仓在产品 / 系统推进中的关键驱动力是什么？
3. 哪些结构性问题无法只靠需求文档解决？
4. 架构必须确保什么结构成立？
```

#### 4.2.5 本章不应回答的问题

```text
- 不写不可变约束清单
- 不写当前阶段可接受取舍
- 不写架构非目标
- 不写技术选型
- 不写容器、依赖方向或实现方案
```

#### 4.2.6 推荐表达形式

##### 主表达形式
- 业务背景短文
- 驱动力清单
- 架构目标表

##### 架构目标表固定结构

| 架构目标 | 说明 |
|---|---|

#### 4.2.7 `架构目标` 列写法规则

```text
1. 架构目标必须写成“架构必须确保成立的结构性结果”。
2. 不写抽象品质口号。
3. 不写功能项。
4. 不写技术方案或实现机制。
5. 优先使用“承载 / 支撑 / 守住 / 允许”这一类结构性动词。
6. 每条架构目标都应能回到本仓边界、核心能力结构或数据边界。
```

#### 4.2.8 `说明` 列写法规则（目标表）

```text
1. 说明用于解释该架构目标为什么对当前仓是必要的。
2. 优先回答“如果不满足该目标，会破坏什么结构、语义或边界”。
3. 不重复目标原文。
4. 不写实现方案、技术手段或未来愿景。
5. 建议控制为一句判断句。
```

#### 4.2.9 完成标准

- 已说明当前仓的业务背景与结构性驱动力
- 已说明为什么需要单独做架构设计
- 已明确架构必须确保什么成立
- 没有把约束、取舍或非目标混写进本章

#### 4.2.10 正反例

**正确示例（identity）：**

##### 业务背景与驱动力

Quantalithos 要求 AI 员工作为长期存在、可被平台稳定引用的身份主体，而不是一次性执行器或会话实例。随着平台进入多项目、多成员、跨阶段协作场景，单靠需求层边界已经不足以支撑后续系统结构，因此需要在架构层明确 identity 仓如何承载平台级成员身份真相。

##### 架构目标表

| 架构目标 | 说明 |
|---|---|
| 承载独立的平台级成员身份真相 | 否则成员身份会退化为运行时实例、项目成员或认证主体的附属物。 |
| 支撑下游对成员身份的稳定引用 | 否则下游无法围绕同一成员主体建立稳定协作。 |
| 允许成员生命周期被正式管理 | 否则成员只会成为静态档案，无法支撑正式状态变化。 |
| 守住成员真相与外部正文边界 | 否则本仓会吸收不属于它的外部正文真相。 |

**错误示例 A：把功能项写成架构目标**

```text
支持创建成员
支持查询成员
支持更新生命周期
```

错误原因：
```text
这是功能需求，不是架构目标。
```

**错误示例 B：把约束写进背景**

```text
identity 不做认证、不做授权、不做项目成员分配。
```

错误原因：
```text
这属于约束条件，不属于业务背景与驱动力。
```

### 4.3 约束条件

#### 4.3.1 本章目标

把需求层已经收稳的边界、能力和数据前提收束成架构不可变约束、当前阶段可接受取舍和架构非目标。

#### 4.3.2 本章输入

- 已收敛的架构需求基线清单
- Step 2 已收敛的架构目标
- 当前阶段的现实前提与已知风险

#### 4.3.3 本章输出

- 不可变约束表
- 当前阶段可接受取舍表
- 架构非目标表

#### 4.3.4 本章应回答的问题

```text
1. 哪些边界是不可变的？
2. 哪些内容当前阶段可以接受收缩？
3. 哪些事项明确不属于当前架构主线？
4. 哪些条件若被破坏，会直接打穿本仓边界？
```

#### 4.3.5 本章不应回答的问题

```text
- 不重写业务背景与驱动力
- 不重写系统上下文图
- 不写技术选型
- 不写容器或实现方案
```

#### 4.3.6 推荐表达形式

##### 主表达形式
- 不可变约束表
- 当前阶段可接受取舍表
- 架构非目标表

##### 固定结构

| 约束 | 说明 |
|---|---|

| 取舍 | 当前口径 |
|---|---|

| 非目标 | 不展开原因 |
|---|---|

#### 4.3.7 `约束` 列写法规则

```text
1. 约束必须写成不可变红线，而不是目标、愿景或实现方案。
2. 优先使用“不做 / 不拥有 / 不将……视为 / 不允许”这一类负向约束句式。
3. 约束必须具体到仓级职责边界或对象边界。
4. 不写抽象原则，不写技术选型。
5. 每条约束应能明确指出一条会被保护或被打穿的边界。
```

#### 4.3.8 `取舍` 列写法规则

```text
1. 取舍必须写成“当前阶段有意识接受的架构收缩”，不写成 TODO 或借口。
2. 取舍对象必须属于本仓潜在范围，而不是边界外能力。
3. 取舍不得与“架构非目标”混淆。
4. 当前口径必须明确说明：当前如何处理该项收缩。
5. 推荐使用“当前作为外围增强处理 / 当前不纳入核心闭环 / 当前保留为边界背景 / 当前仅保留最小承接”等句式。
```

#### 4.3.9 `非目标` 列写法规则

```text
1. 非目标用于明确“这篇架构设计不展开什么范围”，不用于表达阶段性延后事项。
2. 非目标优先写成“架构范围排除项”，而不是细小功能排除项。
3. 非目标不得与“当前阶段可接受取舍”混淆。
4. 推荐使用“不设计 / 不承载 / 不纳入”一类句式。
```

#### 4.3.10 `不展开原因` 列写法规则

```text
1. 说明为什么该事项不属于当前架构主线。
2. 优先写边界归因，而不是实施理由。
3. 不写未来 TODO，不写技术方案。
```

#### 4.3.11 完成标准

- 已明确哪些边界不可变
- 已明确当前阶段哪些内容有意识地不做深
- 已明确哪些事项不属于当前架构范围
- 没有把约束、取舍和非目标混写

#### 4.3.12 正反例

**正确示例（identity）：**

##### 不可变约束表

| 约束 | 说明 |
|---|---|
| 不做认证 | 否则成员身份真相会与安全入口职责混淆。 |
| 不做权限裁决 | 否则 identity 会侵入授权 / 治理边界。 |
| 不做项目成员分配 | 否则平台级成员身份与项目级成员关系会被打穿。 |
| 不拥有 `RoleDefinition` 正文 | 否则定义真相会从 method-library 漂移进 identity。 |
| 不拥有 memory / archive / artifact 正文真相 | 否则 identity 会膨胀为外部正文总仓。 |

##### 当前阶段可接受取舍表

| 取舍 | 当前口径 |
|---|---|
| 高风险成员处置增强 | 当前作为外围增强能力处理，不进入核心能力闭环。 |
| richer capability profile | 当前仅保留成员视角摘要，不展开为本仓核心主结构。 |
| 外部正文相关关系 | 当前保留为边界背景，不提升为正式主依赖。 |

##### 架构非目标表

| 非目标 | 不展开原因 |
|---|---|
| 不设计认证架构 | 登录认证属于安全入口层，不属于 identity 仓的架构主线。 |
| 不设计权限系统 | 权限裁决属于授权 / 治理能力，不属于 identity 仓的核心职责。 |
| 不承载项目级成员生命周期 | 项目成员分配与生命周期属于 `L1-work` 范围，不属于平台级成员身份真相。 |
| 不设计外部正文存储架构 | memory / archive / artifact 正文属于外部系统或相邻仓，不属于 identity 的架构范围。 |

**错误示例 A：把抽象品质词写成约束条件**

```text
高性能
高可用
```

错误原因：
```text
这些表述不是边界约束，也不是取舍或非目标。
```

**错误示例 B：把边界外事项写成取舍**

```text
认证当前阶段先不做深。
```

错误原因：
```text
认证不属于 identity 架构范围，应该进入非目标，而不是当前阶段取舍。
```

### 4.4 职责边界

#### 4.4.1 本章目标

明确本仓在全局职责分工中的承担范围，收稳“做什么 / 不做什么 / 易混淆职责 / 边界红线”。

#### 4.4.2 本章输入

- Step 1 已收敛的架构需求基线
- Step 2 已收敛的架构目标与约束
- 已知的仓级职责边界线索

#### 4.4.3 本章输出

- 职责边界表
- 做 / 不做清单
- 边界红线清单

#### 4.4.4 本章应回答的问题

```text
1. 这个仓具体做什么？
2. 这个仓具体不做什么？
3. 哪些能力看起来相关但必须属于其他仓？
4. 哪些行为绝不能隐式发生？
5. 哪些边界如果不写清，后续设计最容易串线？
```

#### 4.4.5 本章不应回答的问题

```text
- 不重画系统上下文图
- 不展开子域 / 限界上下文
- 不展开容器与部署视图
- 不展开数据所有权矩阵
- 不展开接口协议或实现层依赖
```

#### 4.4.6 推荐表达形式

#### 4.7.7 容器 / 部署架构图规则

##### 图的主语


错误原因：
```text
这是运行承载拓扑，关注的是“谁在跑”，更接近 4.7 容器 / 部署架构，而不是允许什么依赖方向。
```

**错误示例 C：写成协议 / 时序图**

```text
POST /members -> validate -> save -> publish event
```

错误原因：
```text
这是协议和步骤链，写的是实际处理流程，已经滑向交互与通信方式，应属于 4.10 或更低层设计。
```

**错误示例 D：写成术语口号图**

```text
adapter
   ↓
application
   ↓
domain
```

错误原因：
```text
这只是架构术语摆放，没有说明允许依赖什么、禁止依赖什么、为什么这样限制，因此不是可审查的约束图。
```

**错误示例 E：写成子域结构图**

```text
核心子域 -> 支撑子域 -> 本地索引 / 投影 / 引用
```

错误原因：
```text
这是 4.6 的语义结构表达，讲的是内部语义层次，不是依赖方向与层间约束。
```

### 4.9 数据所有权与一致性策略

#### 4.9.1 本章目标

说明哪些数据由本仓拥有正式真相，哪些只是快照 / 投影、引用关系或明确不拥有的正文 / 真相，并在这些归属判断成立的前提下，说明相关数据关系应采用什么一致性口径以及失败时的架构层处理原则。

本章中的“数据所有权”，指架构层的数据归属与正式真相边界，不讨论权限归属、法律归属或存储实现归属。

#### 4.9.2 本章输入

- 已收敛的约束条件
- 已收敛的系统边界与上下文
- 已收敛的限界上下文与子域划分
- 已收敛的容器 / 部署架构
- 已收敛的依赖方向与层间约束

#### 4.9.3 本章输出

- 数据归属表
- 一致性策略表
- 按需补充的数据边界说明短文
- 按需补充的简化关系示意图

#### 4.9.4 本章应回答的问题

```text
1. 哪些数据由本仓拥有正式真相？
2. 哪些数据只是快照 / 投影？
3. 哪些数据只是引用关系？
4. 哪些正文 / 真相本仓明确不拥有？
5. 在这些归属判断成立的前提下，不同数据关系应采用什么一致性口径？
6. 当一致性暂时不成立时，架构层应怎样处理？
```

#### 4.9.5 本章不应回答的问题

```text
- 不写数据库设计
- 不写缓存 / 投影 / outbox 的低层实现
- 不写事务机制与技术补偿方案
- 不写协议 / 交互细节
- 不写代码对象模型
- 不重写 4.6 / 4.7 / 4.8
- 不把本章写成“真假快照引用”的口号展示
```

#### 4.9.6 推荐表达形式

##### 主表达形式
1. 数据归属表
2. 一致性策略表

##### 辅表达形式（按需）
3. 数据边界说明短文
4. 简化关系示意图

##### 图表分工
- 数据归属表负责先回答“本仓拥有什么、不拥有什么、为什么这样划边界”。
- 一致性策略表负责在归属判断成立的前提下，回答“这些关系应采用什么一致性口径，以及失败时如何处理”。
- 同一数据项可以出现在归属表；一致性策略表则按“关系 / 场景”逐行展开，而不是按数据项重复列举。
- 图只作为边界感辅助表达，不作为主结构。
- 短文负责收束边界判断与例外，不重写图和表。

#### 4.9.7 数据类型（正式定稿）

| 数据类型 | 含义 |
|---|---|
| 正式真相数据 | 由本仓正式拥有，并由本仓定义状态边界、生命周期口径与架构责任的数据。 |
| 快照 / 投影数据 | 本仓为稳定消费外部语义、支持只读视图或承接运行需要而保留的影子数据，但其正式真相不在本仓。 |
| 引用关系数据 | 本仓只保存指向外部对象、外部正文或外部正式材料的引用关系，而不保存其正文真相。 |
| 明确不拥有的正文 / 真相 | 本仓在架构层明确不得吸收、不应保存、不应主张拥有的数据正文或正式真相。 |

##### 本章讨论顺序（正式定稿）
本章应先回答“谁拥有什么、不拥有什么”，再回答“这些关系应采用什么一致性口径”。一致性策略必须建立在真相归属之上，不应脱离归属边界单独定义。4.6 中的“本地索引 / 投影 / 引用”用于说明内部语义结构位置；本章中的“快照 / 投影 / 引用关系数据”用于说明数据归属边界，两者不等同。

#### 4.9.8 数据归属表

##### 固定结构表

| 数据项 | 数据类型 | 归属说明 | 边界说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 数据项 | 需要判断归属边界的正式数据对象或正式数据类别 | 不写字段名、表名、缓存 key、schema 属性或实现层数据单元 |
| 数据类型 | 当前章节已收稳的正式数据类型枚举之一 | 不写临时类型、技术类型或实现分类词 |
| 归属说明 | 该数据项正式真相的归属判断：由本仓拥有、由外部拥有而本仓仅保留影子或引用，或本仓明确不拥有 | 不写实现存储方式、接口行为或同步机制 |
| 边界说明 | 必要的去歧义判断，解释为什么它不应被误读为其他类型，为什么本地存在不等于拥有真相 | 不写长段实现分析、同步时序、部署细节或数据结构展开 |

#### 4.9.9 一致性策略表

##### 固定结构表

| 数据关系 / 场景 | 关联数据类型 | 一致性口径 | 失败处理口径 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 数据关系 / 场景 | 需要判断一致性口径的正式数据关系或正式状态变化场景 | 不写孤立对象名、实现动作、接口名称、事件名称或数据库操作 |
| 关联数据类型 | 该一致性判断建立在何种正式数据类型组合之上 | 不写实现对象、服务对象或临时分类词 |
| 一致性口径 | 该数据关系在架构上要求的正式一致性层次 | 不写事务机制、事件机制、缓存机制或具体实现方案 |
| 失败处理口径 | 一致性暂时不成立时的架构层处理原则 | 不写低层补偿机制、脚本实现、组件配置、运行补偿流程或交互重试策略 |
| 说明 | 一致性口径成立的边界原因与保护目标 | 不写实现分析、同步链路时序或未来演进讨论 |

#### 4.9.10 数据边界说明（按需）

数据边界说明短文用于解释：
- 为什么某些数据虽然本地存在，但不属于本仓真相
- 为什么某些数据虽然和本仓关系很强，仍然只能作为引用
- 为什么某些正文必须明确排除在本仓之外
- 为什么这里不继续下沉到数据库、事务、投影或缓存实现

约束：
```text
- 共 1 段
- 3~5 句
- 不重写图和表
- 不滑入实现细节
```

#### 4.9.11 简化关系示意图（按需）

简化关系示意图只用于帮助读者快速建立“真相 / 快照 / 引用 / 明确不拥有”之间的大致边界感，不用于表达对象全量结构、存储设计、同步流程或事件流。

#### 4.9.12 完成标准

- 已明确本仓的正式真相数据、快照 / 投影数据、引用关系数据和明确不拥有的正文 / 真相
- 已说明每类数据为什么属于当前归属边界
- 已明确不同数据关系应采用的一致性口径
- 已明确一致性暂时不成立时的架构层处理原则
- 已通过数据归属表与一致性策略表共同建立“归属 → 一致性”的结构心智
- 没有滑入数据库设计、缓存 / 投影 / outbox 实现、事务机制、协议交互或代码对象模型

#### 4.9.13 正反例

**正确示例 A：数据归属表（通用）**

| 数据项 | 数据类型 | 归属说明 | 边界说明 |
|---|---|---|---|
| 本仓核心状态 | 正式真相数据 | 由本仓拥有正式真相，并由本仓定义状态边界与生命周期口径。 | 若该状态真相不由本仓拥有，本仓核心边界将失去成立基础。 |
| 外部语义影子 | 快照 / 投影数据 | 本仓只为稳定消费或只读承接而保留影子结构，不拥有其正式真相。 | 本地保留影子不等于拥有正式真相。 |
| 外部对象关联 | 引用关系数据 | 本仓仅保存对外部对象或外部正文的引用关系，不保存其正文真相。 | 引用关系成立不等于正文归属进入本仓。 |
| 外部正文 / 外部主真相 | 明确不拥有的正文 / 真相 | 本仓在架构层明确不拥有其正文或正式真相。 | 若将其吸收进本仓，会直接打穿仓边界。 |

**正确示例 B：一致性策略表（通用）**

| 数据关系 / 场景 | 关联数据类型 | 一致性口径 | 失败处理口径 | 说明 |
|---|---|---|---|---|
| 核心状态内部变更 | 正式真相数据 ↔ 正式真相数据 | 强一致 | 明确失败，不回填为部分完成状态 | 核心真相内部状态若漂移，本仓边界会直接失真。 |
| 真相到只读承接更新 | 正式真相数据 ↔ 快照 / 投影数据 | 最终一致 | 重试后收敛，必要时保留旧视图 | 只读承接延迟不等于正式真相失效。 |
| 真相到外部引用维护 | 正式真相数据 ↔ 引用关系数据 | 引用有效性一致 | 保持引用失效态，不伪造正文补齐 | 引用成立只要求关系有效，不等于拥有正文。 |
| 本仓与外部正文边界 | 引用关系数据 ↔ 明确不拥有的正文 / 真相 | 边界约束一致 | 不回填为本仓真相，必要时挂起或显式失败 | 外部正文只可被引用，不可被吸收为本仓拥有。 |

正确原因：
```text
示例先用数据归属表回答“谁拥有什么、不拥有什么”，再用一致性策略表回答“这些关系怎样一致、失败时怎样处理”。表中每一行都有边界判断和一致性口径，而不是数据库结构、事务机制或实现细节。
```

**identity 辅助说明：**

```text
在 L1-identity 中，可把平台级成员身份及其正式状态边界理解为正式真相数据，把目录级、摘要级或只读承接影子结构理解为快照 / 投影数据，把对外部对象或外部正文的关联理解为引用关系数据，把虽然强相关但在架构上明确不属于 identity 的外部内容理解为“明确不拥有的正文 / 真相”。下述说明只用于帮助理解数据归属视角，不重新定义 identity 的语义结构。identity 只作为边界理解的辅助说明，不作为模板定义来源。
```

**错误示例 A：写成数据库设计表**

```text
表：members
字段：member_id, status, role_id, profile_json, memory_ref_uri
索引：idx_status, idx_role_id
```

错误原因：
```text
这是存储设计，不是数据归属判断，也不是一致性策略判断，已经滑入概要 / 详细设计或数据库设计层。
```

**错误示例 B：写成对象 / 字段清单**

```text
GlobalMember
RoleCatalogEntry
CapabilityProfile
MemoryRef
ArchiveRef
status
version
updated_at
```

错误原因：
```text
这里只是在列对象和字段，没有说明谁拥有真相、什么只是影子、什么只是引用、什么明确不拥有，也没有一致性口径。
```

**错误示例 C：写成事务 / outbox / projection 实现说明**

```text
写主表后写 outbox，再异步更新 projection，失败后重试三次并写死信。
```

错误原因：
```text
这是实现机制，不是架构层一致性口径，已经下沉到工程实现策略。
```

**错误示例 D：只有分类，没有边界判断**

```text
成员数据 = 真相
角色数据 = 快照
外部正文 = 引用
```

错误原因：
```text
这里只有标签，没有归属说明、边界说明、一致性口径和失败处理原则，不具备规范约束力。
```

**错误示例 E：把引用关系写成正文拥有**

```text
本仓保存外部正文摘要，因此可视为本仓拥有该正文的局部真相。
```

错误原因：
```text
这把“引用 / 影子存在”误写成了“正文归属”，会直接打穿数据边界，是本章最需要防的本质错误之一。
```

**错误示例 F：只写强一致 / 最终一致口号**

```text
核心数据强一致，其他数据最终一致。
```

错误原因：
```text
没有关系对象、没有关联数据类型、没有失败处理口径，也没有边界理由，因此没有架构审查价值。
```

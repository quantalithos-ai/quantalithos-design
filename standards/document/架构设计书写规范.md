## 一、架构设计的目标

架构设计要回答的问题包括：

1. 这个仓在全局系统中的位置是什么
2. 它和哪些仓或系统交互
3. 它拥有哪些边界与真相
4. 它内部按什么架构风格组织
5. 哪些依赖方向被允许
6. 哪些数据由它拥有，哪些只是引用或快照
7. 哪些关键技术选型被采用，为什么
8. 哪些方案被放弃，为什么
9. 哪些横切关注点需要提前约束
10. 未来如何演进

架构设计不回答：

```text
数据库表结构
Rust 结构体字段
handler 伪代码
repository 函数细节
文件目录树
具体测试用例
迁移脚本
```

这些内容属于概要设计、详细设计、测试方案或实施计划。

## 二、架构设计的章节主链

正式文档建议使用以下章节顺序：

```text
1. 与上游文档的关系声明
2. 业务背景与驱动力
3. 约束条件
4. 职责边界
5. 系统边界与上下文
6. 限界上下文与子域划分
7. 容器 / 部署架构
8. 依赖方向与层间约束
9. 数据所有权与一致性策略
10. 关键交互与通信方式
11. 关键技术选型
12. 备选方案与取舍
13. 横切关注点
14. 演进路线
15. 风险与待确认事项
16. 需求追溯矩阵
17. ADR 索引
18. 参考
```

### 2.1 过程与结果的关系

- `架构设计讨论流程_SOP.md` 负责定义讨论步骤。
- `架构设计书写规范.md` 负责定义最终文档结构。
- 前者收敛结论，后者承接结果。

### 2.2 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式架构设计时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/01_arch_step_05_system_context.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章架构结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的架构结论。
- 正式章节正文只承载收口后的架构结论；问题回答、旧材料诊断、方案取舍、差异审计、模块自检和停审记录必须留在 `design-calibration` 中间产物。
- `设计文档讨论中间产物规范.md` 中的 100~300 行规则只约束单次写入 / patch 批次，不限制正式架构文档、章节、模块、表格或附录的最终长度。
- 正式章节写入前必须按 `设计文档讨论中间产物规范.md` 的三层门禁完成写入前检查:项目级台账允许装配当前文档,文档级 flow 允许装配当前 Step / 章节,Step 文件允许正式回填。
- 不得为了满足单批行数而压缩架构完整性；系统上下文、依赖方向、数据归属、技术取舍和 ADR 索引必须按本规范完整收口。

## 三、总体写作原则

### 3.1 先需求基线，后架构推导

架构设计必须建立在已经收敛的需求基线之上。
如果需求边界和核心能力还不稳定，架构推导就会失真。

### 3.2 先边界，后实现

架构设计首先要讲清：

```text
系统边界
职责边界
依赖方向
数据所有权
一致性层次
```

而不是过早写实现细节。

### 3.3 先系统位置，后组件细节

架构设计先回答“它在全局系统中的位置”，再回答“内部如何组织”。

### 3.4 不确定项不脑补

凡是架构上尚未关闭的问题，必须进入风险与待确认事项，不要用主观判断替代结论。

### 3.5 正式章节必须保留校准来源入口

整理正式架构设计时，每个正式章节开头必须回答：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~18。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/01_arch_step_05_system_context.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/01_arch_step_05_system_context.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解系统边界与上下文如何从上游需求和全局架构结论收敛而来。
```

## 四、章节级规范

### 4.1 与上游文档的关系声明

#### 4.1.1 本章目标

说明本文在架构层承接哪些上游文档结论，明确这篇架构设计不是另起一套定义，而是在当前仓上做结构性细化。

#### 4.1.2 本章输入

- 当前仓对应的需求文档
- 上游产品文档中的相关主题
- 全局架构文档中的仓级定位与边界结论

#### 4.1.3 本章输出

- 上游文档来源表
- 收束说明短文

#### 4.1.4 本章应回答的问题

```text
1. 本文承接哪些上游文档？
2. 承接的是上游哪一部分主题？
3. 本文在当前仓的架构层细化什么内容？
4. 本文不重新定义哪些上游边界或概念？
```

#### 4.1.5 本章不应回答的问题

```text
- 不写架构需求基线清单
- 不写架构目标与约束
- 不写系统上下文图
- 不写职责边界
- 不写容器、数据所有权或技术选型细节
```

#### 4.1.6 推荐表达形式

##### 主表达形式
- 上游文档来源表
- 收束说明短文

##### 固定结构表

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|

#### 4.1.7 粒度要求

- 只写文档来源、承接主题和本文的架构层细化范围
- 不展开为需求基线清单、边界清单或架构约束表
- 不重写上游文档原文

#### 4.1.8 完成标准

- 已明确本文承接的上游文档与主题
- 已说明本文不重新定义什么
- 没有滑入架构约束、系统上下文、职责边界或实现层内容

#### 4.1.9 正反例

**正确示例（identity）：**

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|
| `00-需求文档.md` | `目标与非目标 / 核心能力闭环 / 数据需求与数据归属` | `L1-identity` 已收稳的需求边界、核心能力、数据归属与非功能前提 |
| `product/最终目的.md` | `AI 员工是有身份的个体` | 平台级成员身份主题的产品来源 |
| `product/六域模型.md` | `Identity 域` | Identity 域在架构层的仓级边界与结构来源 |
| `architecture/仓库拆分方案.md` | `L1-identity 仓职责定义` | `L1-identity` 的全局仓级定位来源 |

本文在架构层首先承接 `L1-identity` 已收稳的需求文档结论，再向上追溯到产品叙事、六域模型和全局仓级定位文档。本文不重新定义需求边界，只把这些边界转译为系统结构、依赖和取舍。

**错误示例 A：把需求基线清单写进 4.1**

```text
GlobalMember 为真相，RoleCatalogEntry 为快照，MemoryRef 为引用。
```

错误原因：
```text
这已经进入需求基线或数据所有权层，不属于来源声明。
```

**错误示例 B：把系统上下文图画进 4.1**

```text
L3-method-library -> L1-identity -> L1-work
```

错误原因：
```text
这已经进入系统边界与上下文章节，不属于来源声明。
```

### 4.2 业务背景与驱动力

#### 4.2.1 本章目标

说明为什么值得为这个仓单独做架构设计，明确当前仓在产品 / 系统推进中的结构性驱动力，并给出架构必须确保成立的核心结构目标。

#### 4.2.2 本章输入

- 已收敛的架构需求基线清单
- 当前仓在产品与系统推进中的问题背景
- 当前仓的上游全局架构约束

#### 4.2.3 本章输出

- 业务背景结论
- 驱动力结论
- 架构目标表

#### 4.2.4 本章应回答的问题

```text
1. 当前仓为什么值得单独做架构设计？
2. 当前仓在产品 / 系统推进中的关键驱动力是什么？
3. 哪些结构性问题无法只靠需求文档解决？
4. 架构必须确保什么结构成立？
```

#### 4.2.5 本章不应回答的问题

```text
- 不写不可变约束清单
- 不写当前阶段可接受取舍
- 不写架构非目标
- 不写技术选型
- 不写容器、依赖方向或实现方案
```

#### 4.2.6 推荐表达形式

##### 主表达形式
- 业务背景短文
- 驱动力清单
- 架构目标表

##### 架构目标表固定结构

| 架构目标 | 说明 |
|---|---|

#### 4.2.7 `架构目标` 列写法规则

```text
1. 架构目标必须写成“架构必须确保成立的结构性结果”。
2. 不写抽象品质口号。
3. 不写功能项。
4. 不写技术方案或实现机制。
5. 优先使用“承载 / 支撑 / 守住 / 允许”这一类结构性动词。
6. 每条架构目标都应能回到本仓边界、核心能力结构或数据边界。
```

#### 4.2.8 `说明` 列写法规则（目标表）

```text
1. 说明用于解释该架构目标为什么对当前仓是必要的。
2. 优先回答“如果不满足该目标，会破坏什么结构、语义或边界”。
3. 不重复目标原文。
4. 不写实现方案、技术手段或未来愿景。
5. 建议控制为一句判断句。
```

#### 4.2.9 完成标准

- 已说明当前仓的业务背景与结构性驱动力
- 已说明为什么需要单独做架构设计
- 已明确架构必须确保什么成立
- 没有把约束、取舍或非目标混写进本章

#### 4.2.10 正反例

**正确示例（identity）：**

##### 业务背景与驱动力

Quantalithos 要求 AI 员工作为长期存在、可被平台稳定引用的身份主体，而不是一次性执行器或会话实例。随着平台进入多项目、多成员、跨阶段协作场景，单靠需求层边界已经不足以支撑后续系统结构，因此需要在架构层明确 identity 仓如何承载平台级成员身份真相。

##### 架构目标表

| 架构目标 | 说明 |
|---|---|
| 承载独立的平台级成员身份真相 | 否则成员身份会退化为运行时实例、项目成员或认证主体的附属物。 |
| 支撑下游对成员身份的稳定引用 | 否则下游无法围绕同一成员主体建立稳定协作。 |
| 允许成员生命周期被正式管理 | 否则成员只会成为静态档案，无法支撑正式状态变化。 |
| 守住成员真相与外部正文边界 | 否则本仓会吸收不属于它的外部正文真相。 |

**错误示例 A：把功能项写成架构目标**

```text
支持创建成员
支持查询成员
支持更新生命周期
```

错误原因：
```text
这是功能需求，不是架构目标。
```

**错误示例 B：把约束写进背景**

```text
identity 不做认证、不做授权、不做项目成员分配。
```

错误原因：
```text
这属于约束条件，不属于业务背景与驱动力。
```

### 4.3 约束条件

#### 4.3.1 本章目标

把需求层已经收稳的边界、能力和数据前提收束成架构不可变约束、当前阶段可接受取舍和架构非目标。

#### 4.3.2 本章输入

- 已收敛的架构需求基线清单
- Step 2 已收敛的架构目标
- 当前阶段的现实前提与已知风险

#### 4.3.3 本章输出

- 不可变约束表
- 当前阶段可接受取舍表
- 架构非目标表

#### 4.3.4 本章应回答的问题

```text
1. 哪些边界是不可变的？
2. 哪些内容当前阶段可以接受收缩？
3. 哪些事项明确不属于当前架构主线？
4. 哪些条件若被破坏，会直接打穿本仓边界？
```

#### 4.3.5 本章不应回答的问题

```text
- 不重写业务背景与驱动力
- 不重写系统上下文图
- 不写技术选型
- 不写容器或实现方案
```

#### 4.3.6 推荐表达形式

##### 主表达形式
- 不可变约束表
- 当前阶段可接受取舍表
- 架构非目标表

##### 固定结构

| 约束 | 说明 |
|---|---|

| 取舍 | 当前口径 |
|---|---|

| 非目标 | 不展开原因 |
|---|---|

#### 4.3.7 `约束` 列写法规则

```text
1. 约束必须写成不可变红线，而不是目标、愿景或实现方案。
2. 优先使用“不做 / 不拥有 / 不将……视为 / 不允许”这一类负向约束句式。
3. 约束必须具体到仓级职责边界或对象边界。
4. 不写抽象原则，不写技术选型。
5. 每条约束应能明确指出一条会被保护或被打穿的边界。
```

#### 4.3.8 `取舍` 列写法规则

```text
1. 取舍必须写成“当前阶段有意识接受的架构收缩”，不写成 TODO 或借口。
2. 取舍对象必须属于本仓潜在范围，而不是边界外能力。
3. 取舍不得与“架构非目标”混淆。
4. 当前口径必须明确说明：当前如何处理该项收缩。
5. 推荐使用“当前作为外围增强处理 / 当前不纳入核心闭环 / 当前保留为边界背景 / 当前仅保留最小承接”等句式。
```

#### 4.3.9 `非目标` 列写法规则

```text
1. 非目标用于明确“这篇架构设计不展开什么范围”，不用于表达阶段性延后事项。
2. 非目标优先写成“架构范围排除项”，而不是细小功能排除项。
3. 非目标不得与“当前阶段可接受取舍”混淆。
4. 推荐使用“不设计 / 不承载 / 不纳入”一类句式。
```

#### 4.3.10 `不展开原因` 列写法规则

```text
1. 说明为什么该事项不属于当前架构主线。
2. 优先写边界归因，而不是实施理由。
3. 不写未来 TODO，不写技术方案。
```

#### 4.3.11 完成标准

- 已明确哪些边界不可变
- 已明确当前阶段哪些内容有意识地不做深
- 已明确哪些事项不属于当前架构范围
- 没有把约束、取舍和非目标混写

#### 4.3.12 正反例

**正确示例（identity）：**

##### 不可变约束表

| 约束 | 说明 |
|---|---|
| 不做认证 | 否则成员身份真相会与安全入口职责混淆。 |
| 不做权限裁决 | 否则 identity 会侵入授权 / 治理边界。 |
| 不做项目成员分配 | 否则平台级成员身份与项目级成员关系会被打穿。 |
| 不拥有 `RoleDefinition` 正文 | 否则定义真相会从 method-library 漂移进 identity。 |
| 不拥有 memory / archive / artifact 正文真相 | 否则 identity 会膨胀为外部正文总仓。 |

##### 当前阶段可接受取舍表

| 取舍 | 当前口径 |
|---|---|
| 高风险成员处置增强 | 当前作为外围增强能力处理，不进入核心能力闭环。 |
| richer capability profile | 当前仅保留成员视角摘要，不展开为本仓核心主结构。 |
| 外部正文相关关系 | 当前保留为边界背景，不提升为正式主依赖。 |

##### 架构非目标表

| 非目标 | 不展开原因 |
|---|---|
| 不设计认证架构 | 登录认证属于安全入口层，不属于 identity 仓的架构主线。 |
| 不设计权限系统 | 权限裁决属于授权 / 治理能力，不属于 identity 仓的核心职责。 |
| 不承载项目级成员生命周期 | 项目成员分配与生命周期属于 `L1-work` 范围，不属于平台级成员身份真相。 |
| 不设计外部正文存储架构 | memory / archive / artifact 正文属于外部系统或相邻仓，不属于 identity 的架构范围。 |

**错误示例 A：把抽象品质词写成约束条件**

```text
高性能
高可用
```

错误原因：
```text
这些表述不是边界约束，也不是取舍或非目标。
```

**错误示例 B：把边界外事项写成取舍**

```text
认证当前阶段先不做深。
```

错误原因：
```text
认证不属于 identity 架构范围，应该进入非目标，而不是当前阶段取舍。
```

### 4.4 职责边界

#### 4.4.1 本章目标

明确本仓在全局职责分工中的承担范围，收稳“做什么 / 不做什么 / 易混淆职责 / 边界红线”。

#### 4.4.2 本章输入

- Step 1 已收敛的架构需求基线
- Step 2 已收敛的架构目标与约束

#### 4.4.3 本章输出

- 职责边界表
- 做 / 不做清单
- 边界红线清单

#### 4.4.4 本章应回答的问题

```text
1. 这个仓具体做什么？
2. 这个仓具体不做什么？
3. 哪些能力看起来相关但必须属于其他仓？
4. 哪些行为绝不能隐式发生？
5. 哪些边界如果不写清，后续设计最容易串线？
```

#### 4.4.5 本章不应回答的问题

```text
- 不重画系统上下文图
- 不展开子域 / 限界上下文
- 不展开容器与部署视图
- 不展开数据所有权矩阵
- 不展开接口协议或实现层依赖
```

#### 4.4.6 推荐表达形式

##### 主表达形式
- 职责边界表
- 边界红线清单

##### 固定结构表

| 职责项 | 类型 | 说明 |
|---|---|---|

##### 类型（正式定稿）

| 类型 | 含义 |
|---|---|
| 做 | 本仓正式承担的职责 |
| 不做 | 本仓明确排除的职责 |
| 易混淆职责 | 最容易被误判为本仓职责、需额外说明边界的事项 |

#### 4.4.7 `类型` 列写法规则

```text
1. 类型用于标明该职责项在归属层中的类别。
2. 当前默认只允许三类：做 / 不做 / 易混淆职责。
3. 不应继续扩展更多细分类，除非后续体系证明有必要。
```

#### 4.4.8 `说明` 列写法规则

```text
1. 说明用于解释该职责项为什么属于“做 / 不做 / 易混淆职责”中的当前类别。
2. 说明应控制为一句判断句。
3. 优先回答“该职责属于哪里”或“若不这样划分，会打穿哪条边界”。
4. 不重复职责项原文。
5. 不写实现机制、交互方式或长段边界论证。
```

#### 4.4.9 完成标准

- 已清楚说明本仓做什么、不做什么、最易混淆职责是什么
- 已给出边界红线
- 没有把系统上下文、子域划分、数据所有权或接口细节混写进本章

#### 4.4.10 正反例

**正确示例（identity）：**

| 职责项 | 类型 | 说明 |
|---|---|---|
| 平台级成员身份真相承载 | 做 | 这是本仓正式承载的核心职责。 |
| 成员生命周期维护 | 做 | 若不由本仓承载，成员状态将失去独立正式语义。 |
| 认证 | 不做 | 该职责属于安全入口层，不属于 identity 范围。 |
| 权限裁决 | 不做 | 若由本仓承载，会打穿授权 / 治理边界。 |
| 项目成员分配 | 不做 | `ProjectMember` 属于 `L1-work`，不属于 identity。 |
| 成员画像与角色定义边界 | 易混淆职责 | 该职责容易与 `L3-method-library` 混淆，需显式分层。 |
| 平台级成员与项目级成员边界 | 易混淆职责 | 若不显式区分，后续设计容易把 `GlobalMember` 与 `ProjectMember` 混为一体。 |

##### 边界红线

- 不得将 `ProjectMember` 视为平台级成员身份真相。
- 不得在 identity 中保存 `RoleDefinition` 正文。
- 不得在 identity 中保存 memory / archive / artifact 正文。
- 不得让认证 / 授权逻辑侵入 identity 仓。

**错误示例 A：把上下文关系写成职责**

```text
identity 依赖 method-library，identity 对外输出给 work。
```

错误原因：
```text
这是系统边界与上下文关系，属于前一章，不是职责归属。
```

**错误示例 B：把功能项写成职责**

```text
支持创建成员、支持查询成员、支持更新生命周期。
```

错误原因：
```text
这是功能需求层，不是职责边界层。
```

**错误示例 C：说明列写成实现方案**

```text
通过 event bus 同步给下游。
```

错误原因：
```text
这是交互方式或实现机制，不是职责归因说明。
```

### 4.5 系统边界与上下文

#### 4.5.1 本章目标

说明这个仓在全局系统中的位置，明确它有哪些正式上下文对象、输入面、输出面以及外部边界，并建立读者对本仓外部关系的第一层心智。

- 已确认的架构目标与约束
- 已知的上下游仓 / 外部系统 / 外部能力事实

#### 4.5.3 本章输出

- 系统上下文图
- 上下游与输入/输出面表
- 边界说明短文

#### 4.5.4 本章应回答的问题

```text
1. 这个仓在全局系统中的位置是什么？
2. 它有哪些正式上游？
3. 它有哪些正式下游？

```

#### 4.5.5 本章不应回答的问题

```text
- 不展开本仓内部职责划分
- 不展开限界上下文 / 子域内部结构
- 不展开容器与部署细节
```

#### 4.5.6 推荐表达形式

##### 主表达形式
1. 系统上下文图
2. 上下游与输入/输出面表

##### 辅表达形式
3. 边界说明短文

##### 小节结构
```text
4.5.1 系统上下文图
4.5.2 上下游与输入/输出面表
4.5.3 边界说明
```

#### 4.5.7 系统上下文图规则

##### 图对象类型（正式定稿）
系统上下文图中允许出现的对象类型包括：

1. 本仓
2. 内部仓
3. 外部系统
4. 外部能力
5. 入口系统（按需）

除以上对象类型外，不应引入角色、文档来源对象、内部模块、协议对象或实现组件。

##### 图关系类型（正式定稿）
系统上下文图中的关系类型固定为：

| 关系类型 | 含义 |
|---|---|
| 输入 | 本仓从该对象接收正式输入面 |
| 输出 | 本仓向该对象提供正式输出面 |
| 依赖 | 本仓某项能力的成立依赖该对象存在 |

除以上三类外，不应继续细分为查询、变更、事件、同步、异步、发布、订阅等更细语义。

##### 布局规则（正式定稿）
```text
1. 本仓位于图中央。
2. 关键输入 / 关键依赖对象优先放在上方。
3. 关键输出 / 关键消费对象优先放在下方。
4. 次级关系对象可放在左侧或右侧。
5. 图中优先使用横平竖直的直线连接。
6. 尽量避免使用斜线连接。
```

##### 图对象数量约束
```text
- 1 个中心仓
- 关键上下文对象建议 3~7 个
- 超过 7 个应考虑收缩为关键对象，不建议继续单图扩张
```

##### 图后说明
图后必须补一句：

```text
该图仅表达本仓与正式上下文对象之间的边界关系与输入/输出方向，不表达接口、事件、实现组件或运行时顺序。
```

#### 4.5.8 上下游与输入/输出面表

##### 固定结构表

| 对象 | 关系方向 | 关系类型 | 输入/输出面 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 对象 | 本仓正式上下文关系中的对象名 | 不写内部模块、角色、文档来源对象 |
| 关系方向 | 输入 / 输出 | 不写调用顺序 |
| 关系类型 | 来源 / 消费 / 入口 / 治理依赖 | 不继续扩展成协议语义 |
| 输入/输出面 | 本仓与该对象之间的能力面 | 不写接口名、事件名、DTO |
| 说明 | 这条关系为什么重要，当前阶段如何理解 | 不写实现方案 |

#### 4.5.9 边界说明

边界说明短文用于解释：
- 为什么这些对象属于正式上下文对象
- 哪些对象虽然相关但不进入本章主图
- 为什么当前图和表的边界划法成立

约束：
```text
- 1 段
- 3~5 句
- 不重写图和表
- 不展开内部结构
```

#### 4.5.10 完成标准

- 已明确本仓在全局系统中的位置
- 已用正式对象画出系统上下文图
- 已通过配套表格解释图中对象的关系语义
- 已补边界说明，且没有滑入内部结构或协议细节

#### 4.5.11 正反例

**正确示例（identity）：**

```text
                    +----------------------+
                    |  L3-method-library   |
                    |  角色/能力定义来源    |
                    +----------------------+
                              |
                              v

+----------------------+   +----------------------+   +----------------------+
|    L1-governance     |   |     L1-identity      |   |     L5-console       |
| 高风险处置结论引用    |-->| 平台级成员身份真相仓  |<--|   管理/查看入口系统   |
+----------------------+   +----------------------+   +----------------------+

                              |
                              v
                    +----------------------+
                    |       L1-work        |
                    |   项目成员身份锚点    |
                    +----------------------+
```

| 对象 | 关系方向 | 关系类型 | 输入/输出面 | 说明 |
|---|---|---|---|---|
| `L3-method-library` | 输入 | 来源 | 角色/能力定义来源 | identity 依赖其稳定语义锚点来收稳成员身份主题。 |
| `L1-governance` | 输入 | 治理依赖 | 高风险处置结论引用 | 涉及高风险成员处置时，需要外部正式治理结论。 |

**错误示例 A：把文档来源对象画进上下文图**

```text
product/最终目的.md -> L1-identity -> L1-work
```

错误原因：
```text

```

**错误示例 B：把角色画进上下文图**

```text

```

错误原因：
```text
角色属于需求中的用户与角色层，不属于系统上下文对象；应优先画入口系统。
```

**错误示例 C：在图中写接口名 / 事件名**

```text
L3-method-library --RoleDefinitionPublished--> L1-identity
```

错误原因：
```text
系统上下文图不表达接口协议或事件名，只表达正式上下文关系。
```

#### 4.6.8 `与其他部分的关系` 列写法规则

```text
1. 该列用于说明该子域 / 上下文单元与本仓其他部分的内部语义关系。

4. 建议控制为一句判断句。
```

#### 4.6.9 上下文关系图规则

##### 图的目的

```text

```

##### 绘制约束

```text
1. 优先使用直线连接。
2. 尽量避免使用斜线连接。
3. 图中不得出现外部上下文对象、角色、接口名、事件名、数据库表、实现组件或运行顺序。
```

#### 4.6.10 完成标准

- 已明确本仓内部语义结构的层次划分
- 已区分核心子域、支撑子域和本地索引 / 投影 / 引用
- 已通过关系图或关系列解释这些部分如何共同构成整体

### 4.9 数据所有权与一致性策略

#### 4.9.1 本章目标

说明哪些数据由本仓拥有正式真相，哪些只是快照 / 投影、引用关系或明确不拥有的正文 / 真相，并在这些归属判断成立的前提下，说明相关数据关系应采用什么一致性口径以及失败时的架构层处理原则。

本章中的“数据所有权”，指架构层的数据归属与正式真相边界，不讨论权限归属、法律归属或存储实现归属。

#### 4.9.2 本章输入

- 已收敛的约束条件
- 已收敛的系统边界与上下文
- 已收敛的限界上下文与子域划分
- 已收敛的容器 / 部署架构
- 已收敛的依赖方向与层间约束

#### 4.9.3 本章输出

- 数据归属表
- 一致性策略表
- 按需补充的数据边界说明短文
- 按需补充的简化关系示意图

#### 4.9.4 本章应回答的问题

```text
1. 哪些数据由本仓拥有正式真相？
2. 哪些数据只是快照 / 投影？
3. 哪些数据只是引用关系？
4. 哪些正文 / 真相本仓明确不拥有？
5. 在这些归属判断成立的前提下，不同数据关系应采用什么一致性口径？
6. 当一致性暂时不成立时，架构层应怎样处理？
```

#### 4.9.5 本章不应回答的问题

```text
- 不写数据库设计
```

#### 4.9.7 数据类型（正式定稿）

#### 4.10.7 通信方式类型（正式定稿）

| 通信方式类型 | 含义 |
|---|---|
| 同步请求 / 响应类交互 | 需要在一个正式交互边界上即时得到结果、状态判断或明确失败口径的交互。 |

| 后台任务 / 延后承接类交互 | 不要求在当前同步边界内立即收口，而适合通过后台推进、重试、延后补偿或异步承接完成的交互。 |

| 通过正式承接层隔离外部输入与核心语义 | 防止外部入口、外部协作边界或外部能力直接打穿本仓核心边界 | 若外部输入可直接触达核心语义，本仓会迅速吸收不属于自身的外部语义，导致边界失稳 | 增加正式承接层，并要求输入边界与核心语义之间持续保持隔离 | 这项机制改变外部输入如何进入核心边界，属于架构层的结构性技术决定。 |
| 采用只读投影而非直接暴露核心真相对外供给 | 支撑外部稳定消费正式状态、摘要或只读视图，而不让下游直接依赖核心真相结构 | 若直接把核心真相暴露为外部消费面，读写边界会混层，下游会反向绑定核心模型，压缩后续演进空间 | 增加投影承接层、延迟收敛成本与一致性解释负担 | 这项机制同时影响运行承载、数据边界和交互方式，因此应作为关键架构选型显式记录。 |
| 采用事件最终一致承接跨边界状态传播 | 支撑正式状态变化在边界之间传播，而不把所有承接问题强压进同步即时闭环 | 若一律要求同步收口，会把不适合同步完成的问题塞进入口边界，造成伪一致与高耦合 | 增加延迟收敛、追踪、失败恢复与消费侧理解成本 | 这项机制改变跨边界状态传播的主承接方式，属于影响一致性和交互主链的架构层决定。 |

正确原因：
```text
示例中的每一项都不是单纯的产品名或技术清单，而是明确采用的架构层技术机制。每一行都同时说明了解决的问题、采用理由、代价 / 约束，以及为什么它够格进入本章。
```

**identity 辅助说明：**

```text

```

### 4.12 备选方案与取舍

#### 4.12.1 本章目标

说明当前主线方案为什么选择了某条方案路径、放弃了哪些相邻替代路径，以及这种取舍分别换来了什么、牺牲了什么。

本章中的“备选方案”，主要指与当前主线方案构成结构性替代关系的方案路径，不指产品名、框架名、局部实现方式或未来愿望池。

#### 4.12.2 本章输入

- 已收敛的约束条件
- 已收敛的容器 / 部署架构
- 已收敛的依赖方向与层间约束
- 已收敛的数据所有权与一致性策略
- 已收敛的关键交互与通信方式
- 已收敛的关键技术选型

#### 4.12.3 本章输出

- 方案路径比较表
- 按需补充的方案边界说明短文
- 按需补充的轻量取舍对照表

#### 4.12.4 本章应回答的问题

```text
1. 当前架构主线方案是什么？
2. 哪些相邻替代路径值得进入本章比较？
3. 每条路径分别在解决什么问题？
4. 每条路径各自带来什么主要收益与主要代价 / 约束？
5. 为什么当前采用主线方案，而不采用其他路径？
```

#### 4.12.5 本章不应回答的问题

```text
- 不写产品横向对比目录
- 不写局部实现对比
- 不写愿望池 / 脑暴池 / 未来可能性大全
- 不重写 4.11
- 不重写 4.7 / 4.8 / 4.9 / 4.10 的局部判断
- 不写单边方案赞美
- 不把已被前文排除的边界外事项重新包装成“备选方案”
```

#### 4.12.6 推荐表达形式

##### 主表达形式
1. 方案路径比较表

##### 辅表达形式（按需）
2. 方案边界说明短文
3. 轻量取舍对照表

##### 图表分工
- 主表负责把当前主线方案与相邻替代路径放在同一张表中，比较它们各自试图解决什么问题、带来什么收益与代价，以及为什么当前采用或不采用。
- 本章只比较路径级替代关系，不逐项论证单个技术机制是否成立；单项机制的采用理由与代价应优先在 4.11 说明。
- 短文负责收束边界，解释为什么某些看起来相关的方向不配进入本章，以及为什么本章只比较相邻替代路径。
- 轻量对照表只在主表较重时帮助读者快速抓住“当前方案得到什么 / 失去什么”，不替代主表本身。

#### 4.12.7 备选方案判定规则（正式定稿）

只有当某条方案路径同时满足以下条件时，才配进入本章：
- 它与当前主线方案构成结构性替代关系
- 它是路径级替代，而不是点级替代
- 它没有被前文约束条件、非目标或边界判断明确排除

本章中的“相邻替代路径”，指会改变主线结构判断、但不脱离当前已收稳边界前提的替代路径。方案比较必须同时写清“得到什么 / 失去什么”，不得只写当前方案优点，也不得把未来愿望池、探索池或脑暴池混入正式比较。

#### 4.12.8 方案路径比较表

##### 固定结构表

| 方案路径 | 解决的问题 | 主要收益 | 主要代价 / 约束 | 当前结论 | 说明 |
|---|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 方案路径 | 与当前主线形成结构性替代关系的路径级做法 | 不写产品名、框架名、局部实现方式或点级技术替换项 |
| 解决的问题 | 该路径试图解决的架构层问题 | 不写空泛优点或技术口号 |
| 主要收益 | 该路径在边界、依赖、一致性、交互承接或演进可控性上的主要正收益 | 不写抽象赞美词 |
| 主要代价 / 约束 | 该路径引入的复杂度、结构成本或额外约束 | 不写模糊形容词或弱化表述 |
| 当前结论 | 当前主线方案对该路径的正式判断，优先使用“采用 / 不采用”，按需才使用“保留观察” | 不写模糊拖延式状态词 |
| 说明 | 必要的去歧义判断，解释该路径为什么是有效替代路径，以及为什么当前结论成立 | 不写实现细节或愿望池讨论 |

#### 4.12.9 方案边界说明（按需）

- 方案边界说明短文用于解释：
- 为什么某些看起来相关的方向不配进入本章
- 为什么某些已被前文排除的内容不再纳入比较
- 为什么本章只比较相邻替代路径，而不展开所有可能性
- 为什么这里不继续滑入产品横评、局部实现或未来脑暴讨论
- 若某项差异主要体现在横切治理、审计、可观测或韧性约束，而不是主线路径替换，应优先归入 4.13

约束：
```text
- 共 1 段
- 3~5 句
- 不重写主表
- 不滑入大段脑暴或实现细节
```

#### 4.12.10 轻量取舍对照表（按需）

轻量取舍对照表只用于在主表较长时，快速收束“当前方案主要得到什么 / 失去什么”，帮助读者把握当前取舍重心，不替代主表本身。

#### 4.12.11 完成标准

- 已明确当前架构主线方案
- 已明确哪些相邻替代路径值得比较
- 已说明每条路径各自解决什么问题
- 已同时写清主要收益与主要代价 / 约束
- 已给出当前采用 / 不采用的正式结论
- 没有滑入产品横评、局部实现对比、愿望池或前文已排除事项的重新包装

#### 4.12.12 正反例

### 4.13 横切关注点

#### 4.13.1 本章目标

说明哪些横切要求会持续作用于本仓主线、分别作用于哪些结构面、要求架构满足什么，以及它们在保护什么。

- 已收敛的约束条件
- 已收敛的容器 / 部署架构
- 已收敛的依赖方向与层间约束
- 已收敛的数据所有权与一致性策略
- 已收敛的关键交互与通信方式
- 已收敛的关键技术选型
- 已收敛的备选方案与取舍

#### 4.13.3 本章输出

- 横切关注点约束表
- 按需补充的横切影响说明短文
- 按需补充的主线映射小表

#### 4.13.4 本章应回答的问题

```text
1. 哪些横切要求已经上升为本仓长期作用于主线的正式要求？
2. 这些要求分别作用于哪些边界、交互、数据关系或承载结构？
3. 它们要求架构满足什么？

5. 为什么这些要求不能只留到实现层、运维层或制度层再补？
```

#### 4.13.5 本章不应回答的问题

```text
- 不写性能压测与容量实施方案
```

### 4.14 演进路线

#### 4.14.1 本章目标

说明当前架构主线在什么阶段做到哪里算成立、哪些结构债务当前可接受、哪些主线能力后续才进入演进主线，以及什么条件会触发下一阶段演进。

本章中的“阶段”，指架构主线成立与演进的结构阶段，不指项目版本、排期或交付里程碑。

#### 4.14.2 本章输入

- 已收敛的约束条件
- 已收敛的容器 / 部署架构
- 已收敛的依赖方向与层间约束
- 已收敛的数据所有权与一致性策略
- 已收敛的关键交互与通信方式
- 已收敛的关键技术选型
- 已收敛的备选方案与取舍
- 已收敛的横切关注点

#### 4.14.3 本章输出

- 演进路线表
- 按需补充的阶段边界说明短文
- 按需补充的触发条件小表

#### 4.14.4 本章应回答的问题

```text
1. 当前阶段做到哪里算足够支撑主线？

4. 什么条件会触发下一阶段演进？
5. 当前主线演进时，最先改变的结构面是什么？
```

### 4.15 风险与待确认事项

#### 4.15.1 本章目标

显式收纳当前尚未关闭的架构风险和待确认问题，说明它们分别影响什么、当前如何处理，以及哪些会阻塞后续主线推进。

本章中的“风险”，统一指已识别出来、尚未关闭、并会影响主线判断的正式风险，不在本章内再区分额外风险等级。

#### 4.15.2 本章输入

- 前面各章节中尚未完全收稳的结论
- 已显式暴露的边界、依赖、数据、一致性、交互、技术机制或主线路径问题
- 当前阶段边界与可接受债务判断

#### 4.15.3 本章输出

- 风险表
- 待确认事项表
- 按需补充的当前处理口径说明短文

#### 4.15.4 本章应回答的问题

```text
1. 当前有哪些已识别但尚未关闭的正式风险？
2. 这些风险分别影响什么、当前如何约束 / 暂存、是否阻塞后续推进？
3. 当前还有哪些尚未形成定论、但会影响主线判断的待确认事项？
4. 这些待确认事项分别缺什么确认、当前怎样挂起？
5. 为什么这些内容配进入本章，而不是写成任务、TODO 或已定结论？
```

#### 4.15.5 本章不应回答的问题

```text
- 不写任务 backlog
- 不写 TODO / 优化清单
- 不写最终解决方案
- 不写空泛风险页
- 不重写已定结论
- 不把局部实现问题提升成风险或待确认事项
- 不写“假挂起”表述
```

#### 4.15.6 推荐表达形式

##### 主表达形式
1. 风险表
2. 待确认事项表

##### 辅表达形式（按需）
3. 当前处理口径说明短文

##### 图表分工
- 风险表负责收纳已经识别但尚未关闭、且会影响主线判断的问题。
- 待确认事项表负责收纳尚未形成定论、仍需进一步确认且会影响前文成立的问题。
- 可接受债务和后续演进项不自动构成风险或待确认事项；只有当其仍未关闭且会影响主线判断时，才进入本章。
- 短文负责解释为什么某些问题当前被视为风险、而另一些问题当前只能挂起为待确认事项，不重写两张表。

#### 4.15.7 风险与待确认事项判定规则（正式定稿）

- 风险：已经识别出会影响主线成立、边界稳定、依赖方向、数据归属、一致性或关键交互的问题，但当前还没有被关闭。
- 待确认事项：尚未形成确定结论、仍需外部信息、进一步判断或前置澄清的问题；它可能影响前文成立，但当前还不能被写成已知风险。

只有那些仍未关闭，并且会影响主线判断的内容，才配进入本章。普通 TODO、任务、愿望、局部优化项和已定结论都不应进入本章。

#### 4.15.8 风险表

##### 固定结构表

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 风险项 | 已识别出来、尚未关闭、并会影响主线判断的正式风险项 | 不写 TODO 事项、项目任务名、功能愿望或解决动作 |
| 影响范围 | 该风险会影响哪条主线、哪类边界、哪类交互或哪类数据关系 | 不写空泛的“全局受影响”式描述 |
| 当前处理口径 | 风险尚未关闭时的架构层约束、暂存或保守承接方式 | 不写最终修复方案、实施步骤、负责人、时间安排、处置动作或任务拆分 |
| 是否阻塞 | 该风险对后续推进的正式判断，优先使用“阻塞 / 不阻塞”，按需才使用“有条件阻塞” | 不写模糊观察式状态词 |
| 说明 | 必要的去歧义判断，解释该问题为什么已经属于正式风险、为什么当前处理口径合理 | 不写解决方案或实施分析 |

#### 4.15.9 待确认事项表

##### 固定结构表

| 待确认事项 | 影响范围 | 缺失确认 | 当前挂起口径 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 待确认事项 | 尚未形成确定结论、仍需进一步确认且会影响主线判断的问题项 | 不写普通疑问、功能愿望、实施待办或优化事项 |
| 影响范围 | 该事项若定论变化，将影响哪条主线、哪类边界、哪类交互或哪类数据关系 | 不写泛化的“整体相关”类表述 |
| 缺失确认 | 当前还缺什么确认，因此该事项不能被定论 | 不写“还没想好”“后续再看”“继续讨论”等空泛表达 |
| 当前挂起口径 | 尚未定论前的保守挂起方式 | 不写临时方案、感觉性处理、预支结论、处置动作或任务拆分 |
| 说明 | 必要的去歧义判断，解释该事项为什么仍属于待确认事项、为什么当前还不能定论，以及为什么当前挂起口径合理 | 不写方案推演或实施建议 |

#### 4.15.10 当前处理口径说明（按需）

当前处理口径说明短文用于解释：
- 为什么某些问题当前被视为风险，而不是待确认事项
- 为什么某些问题当前只能挂起，而不能装成已知结论
- 为什么这里不继续写最终解决方案

约束：
```text
- 共 1 段
- 3~5 句
- 不重写两张表
- 不滑入实施方案
```

#### 4.15.11 完成标准

- 已明确区分正式风险与待确认事项
- 已写清每项风险的影响范围、当前处理口径与阻塞性
- 已写清每项待确认事项的影响范围、缺失确认与当前挂起口径
- 已说明为什么这些项配进入本章
- 没有滑入任务层、方案层或已定结论回退层
- 没有使用空泛风险词或假挂起表述

#### 4.15.12 正反例

**正确示例 A：风险表（通用）**

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|
| 核心边界尚未完全闭环的风险 | 核心边界判断、对外承接边界 | 当前按更保守边界收口，不提升为正式能力 | 有条件阻塞 | 该问题已明确会影响主线成立，因此属于正式风险，而不是普通待办。 |
| 跨边界传播未完全收稳的风险 | 状态传播主线、外部承接边界 | 当前只允许保守传播口径，不伪装为已稳定闭环 | 不阻塞 | 该问题已被识别，但在当前阶段仍可带约束推进。 |

|---|---|---|---|---|

### 4.16 需求追溯矩阵

#### 4.16.1 本章目标

把前面已经收稳的需求结论 / 约束与架构承接结果显式连接起来，并暴露尚未承接、缺少来源或仍未闭环的追溯缺口。

4.1 负责声明本文承接哪些来源范围；本章负责逐条追踪具体需求结论如何被具体架构结果承接，不重复列来源范围说明。本章只记录追溯状态与映射缺口，不判断风险性质、阻塞性或处理口径；这些应进入 4.15。

#### 4.16.2 本章输入

- 已明确的需求来源与需求结论 / 约束
- 已收稳的 4.1 ~ 4.15 架构章节结果
- 当前仍未闭环的来源—承接关系线索

#### 4.16.3 本章输出

- 需求追溯矩阵
- 漏项检查表
- 按需补充的追溯范围说明短文

#### 4.16.4 本章应回答的问题

```text
1. 哪些需求结论 / 约束已经被哪些架构结果承接？
2. 这些承接关系最终落在哪个架构章节位置？
3. 为什么说这条需求与这条架构结果之间构成正式承接关系？
4. 目前还有哪些需求未被承接、哪些架构判断缺少来源、哪些关系仍未闭环？
5. 这些缺口当前处于什么状态、会影响什么？
```

#### 4.16.5 本章不应回答的问题

```text
- 不写章节摘要
- 不凭主观补写新来源
- 不用笼统映射掩盖缺口
- 不新增架构结论
- 不写项目状态汇报
- 不写补齐实施计划
- 不把已闭环内容重新包装成漏项
```

#### 4.16.6 推荐表达形式

##### 主表达形式
1. 需求追溯矩阵
2. 漏项检查表

##### 辅表达形式（按需）
3. 追溯范围说明短文

##### 图表分工
- 主矩阵负责说明哪些需求结论 / 约束已经被哪些架构结果承接、最终落在哪个架构章节中，以及为什么这种追溯映射关系成立。
- 漏项检查表负责显式暴露尚未被承接的需求、缺少来源的架构判断以及仍未闭环的追溯缺口。
- 主矩阵只写已成立的追溯映射；漏项表只写尚未闭环的追溯缺口。
- 短文只用于收束追溯范围与粒度，不替代两张主表。

#### 4.16.7 需求追溯矩阵

##### 固定结构表

| 需求来源 | 需求结论 / 约束 | 架构承接结果 | 承接位置 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 需求来源 | 该需求结论 / 约束来自哪个正式需求来源单元 | 不写模糊来源、经验判断或主观推断 |
| 需求结论 / 约束 | 被架构承接的具体需求判断 | 不写章节标题本身、不大段复制原文，也不退化成对象清单 |
| 架构承接结果 | 哪个具体架构结果在承接这条需求结论 | 不只写章节号或“已承接”类空表述 |
| 承接位置 | 该架构承接结果最终落在哪个架构章节位置 | 不写模糊位置描述 |
| 说明 | 必要的去歧义判断，解释为什么该需求结论与该架构结果之间构成正式追溯映射关系 | 不写主观总结或状态汇报 |

#### 4.16.8 漏项检查表

##### 固定结构表

| 追溯缺口类型 | 对象 / 缺口 | 影响范围 | 当前状态 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 追溯缺口类型 | 当前追溯体系中缺口的正式类别 | 不写模糊状态词或临时备注词 |
| 对象 / 缺口 | 具体缺的是哪个需求承接、来源指向或追溯闭环 | 不写笼统概述 |
| 影响范围 | 该缺口若不补齐，将影响哪条主线、哪类边界、哪类交互或哪部分架构判断 | 不写泛化的严重性形容词 |
| 当前状态 | 该缺口当前处于何种追溯状态 | 不写项目执行状态或模糊拖延表述 |
| 说明 | 必要的去歧义判断，解释为什么该项确实构成追溯缺口、为什么不能主观补齐，以及为什么当前状态合理 | 不写补齐方案、任务计划或长段总结 |

#### 4.16.9 追溯范围说明（按需）

追溯范围说明短文用于解释：
- 为什么本章采用当前追溯粒度
- 为什么某些内容不进入主矩阵
- 为什么某些缺口当前保留在漏项表中，而不是强行补齐
- 为什么这里不继续滑入状态汇报、补齐计划或主观总结

约束：
```text
- 共 1 段
- 3~5 句
- 不重写两张表
- 不滑入主观总结
```

#### 4.16.10 完成标准

- 已明确需求来源、需求结论 / 约束、架构承接结果与承接位置之间的正式映射
- 已说明每条映射为什么成立
- 已显式暴露尚未承接、缺少来源或仍未闭环的追溯缺口
- 已说明这些缺口的影响范围与当前状态
- 没有用装饰性“已覆盖”矩阵掩盖问题
- 没有滑入项目状态汇报、补齐计划或新结论创造

#### 4.16.11 正反例

**正确示例 A：需求追溯矩阵（通用）**

| 需求来源 | 需求结论 / 约束 | 架构承接结果 | 承接位置 | 说明 |
|---|---|---|---|---|

### 4.17 ADR 索引

#### 4.17.1 本章目标

说明哪些架构决策已经足够关键、足够长期、值得被后续读者单独理解并长期保留为 ADR 索引项，以及这些决策分别在解决什么问题、关联哪类主线判断。

- 已收稳的 4.1 ~ 4.16 架构章节结果
- 当前项目已存在的 ADR 记录（如有）

#### 4.17.3 本章输出

- ADR 索引表
- 按需补充的决策边界说明短文

#### 4.17.4 本章应回答的问题

```text
1. 哪些架构决策已经足够关键并应进入 ADR 索引？
2. 每项决策分别在解决什么架构层问题？
3. 每项决策主要关联哪类主线判断？
4. 为什么这些决策值得被长期单独保留？
5. 为什么它们不是局部实现选择、历史讨论记录或文件清单？
```

#### 4.17.5 本章不应回答的问题

```text
- 不写 ADR 正文内容
- 不写文件目录 / 文件树
- 不写历史讨论年表
- 不写技术栈或机制清单
- 不重写 4.16 的追溯关系
- 不把未收稳事项提前升格为 ADR
- 不把所有事项都升格为 ADR
```

#### 4.17.6 推荐表达形式

##### 主表达形式
1. ADR 索引表

##### 辅表达形式（按需）
2. 决策边界说明短文

##### 图表分工
- 主表负责逐项索引哪些架构决策已经足够关键、足够长期、值得被后续读者单独理解，并说明它们分别在解决什么问题、关联哪类主线判断以及为什么应被长期保留。
- 短文只用于收束边界，解释为什么某些决策配进入索引，以及为什么本章不展开成文件目录、历史年表或 ADR 正文摘要。

#### 4.17.7 ADR 进入标准（正式定稿）

只有满足以下条件的决策，才配进入本章：
- 它是架构层决策，而不是局部实现选择
- 它具有长期稳定性或长期影响
- 它值得被后续读者单独理解

本章主语是架构决策本身，ADR 编号与文件落点只是索引字段，不应取代决策本身成为本章主语。

#### 4.17.8 ADR 索引表

##### 固定结构表

| ADR 编号 | 架构决策 | 解决的问题 | 关联主线 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| ADR 编号 | 已正式纳入索引的 ADR 编号 | 不写草稿标题、讨论纪要名或临时路径名 |
| 架构决策 | 该 ADR 所记录的核心架构决定 | 不写主题词、技术栈名、局部实现动作或会议标题 |
| 解决的问题 | 该决策所针对的架构层问题 | 不写空泛优点、流行性理由或抽象质量描述 |
| 关联主线 | 该决策主要关联的主线判断类别 | 不写泛化的“整体相关”类表述 |
| 说明 | 必要的去歧义判断，解释为什么该决策值得被长期单独索引、为什么它不是局部实现选择，以及为什么后续读者需要单独理解它 | 不写历史过程、实现分析或大段摘要 |

#### 4.17.9 决策边界说明（按需）

- 为什么这里不重复 4.16 的来源—承接映射
- 为什么这里不展开 ADR 正文内容

约束：
```text
- 共 1 段
- 3~5 句
- 不重写主表
- 不滑入 ADR 正文内容
```

#### 4.17.10 完成标准

- 已明确哪些架构决策已经足够关键并应进入 ADR 索引
- 已说明每项决策所解决的架构层问题
- 已说明每项决策主要关联哪类主线判断
- 已说明为什么这些决策值得长期单独保留
- 没有滑入文件目录、历史年表、追溯矩阵或技术清单
- 没有把未收稳事项或局部实现偏好提前写进索引

## 五、图表与表达形式规范

架构设计采用：

- 表为主
- 图按需
- 短文收束边界

其中：
- 表负责收稳边界、上下文、归属、约束、取舍、追溯和风险。
- 图负责建立结构关系心智，但不承载字段、接口、函数、DDL、协议 schema 或实现时序。
- 短文负责解释为什么这样切边界、为什么某些内容不展开，以及如何理解例外。

### 5.1 表格使用规则

每张表必须至少承担以下一种职责：

- 划分边界
- 解释关系
- 固定约束
- 记录取舍
- 暴露缺口
- 建立追溯

表格不应退化成目录、清单或阅读记录。表格中的每一列都应能回答“写什么 / 不写什么 / 为什么需要这一列”。

### 5.2 图的使用规则

架构设计中的图只表达架构层结构关系，包括：

- 系统上下文边界
- 内部语义结构关系
- 运行承载关系
- 架构依赖方向
- 数据归属边界
- 关键交互边界

架构设计中的图不表达：

- API 路径
- event / topic / callback 名称
- DTO / schema / 字段
- Rust struct / trait / 函数签名
- 数据库表、索引和迁移
- 详细时序、处理流程和伪代码
- 部署参数、资源配置和运维脚本

### 5.3 ASCII 图统一格式

架构设计中的 ASCII 图必须使用统一风格，避免不同仓各画各的。

#### 统一输出结构

每一张 ASCII 图必须采用以下结构：

````md
#### <图类型标题>

```text
<ASCII 图正文>
```

图后说明：
- <说明图表达了什么架构关系>
- <说明图没有表达哪些下游设计内容>
- <说明图中最容易误解的边界是什么>
````

其中：
- `图类型标题` 必须使用本规范允许的图类型名称。
- 图正文必须放在 `text` 代码块中。
- `图后说明` 必须有 2~5 条。
- 禁止只有图、没有标题或没有图后说明。

#### 允许的图类型

| 图类型 | 允许出现章节 | 作用 | 主方向 |
|---|---|---|---|
| 系统上下文图 | 4.5 | 说明本仓与正式上下文对象之间的输入、输出、依赖关系 | 中心辐射或上下游 |
| 上下文关系图 | 4.6 | 说明本仓内部核心子域、支撑子域和本地索引 / 投影 / 引用的语义关系 | 自上而下 |
| 容器 / 部署架构图 | 4.7 | 说明本仓运行承载单元、正式存储承载和基础设施依赖 | 自上而下 |
| 依赖方向图 | 4.8 | 说明架构责任层 / 依赖角色之间允许的依赖方向 | 外层到内层或自上而下 |
| 简化关系示意图 | 4.9 按需 | 辅助说明真相、快照 / 投影、引用和明确不拥有之间的边界 | 自上而下 |
| 简化交互示意图 | 4.10 按需 | 辅助说明同步、异步、后台承接在边界上的位置感 | 自上而下 |

禁止在架构设计中新增未定义的图类型；确有必要时，应先修改本规范，再落到具体架构设计文档。

#### 基本字符集

允许使用：

```text
| + - = / \ < > v ^
```

允许在简单图中使用：

```text
->  =>
```

禁止使用：

```text
Mermaid / PlantUML / Graphviz 语法
Emoji
彩色标记
混用多套箭头风格
框图中夹杂 Markdown 表格
```

#### 节点命名规则

- 节点名称必须使用本章已收稳的正式架构主语。
- 系统上下文图使用仓、外部系统、外部能力或入口系统名。
- 上下文关系图使用核心子域、支撑子域、本地索引 / 投影 / 引用名。
- 容器 / 部署架构图使用运行承载角色名，不写代码模块名。
- 依赖方向图使用架构责任层 / 依赖角色名，不写 handler、repository、service 等实现名。
- 同一张图中不得把上下文对象、运行单元、依赖角色、代码对象混成同一级。

#### 方向规则

- 系统上下文图以本仓为中心，关键输入 / 依赖优先在上方，关键输出 / 消费优先在下方。
- 上下文关系图、运行承载图和交互示意图优先自上而下。
- 依赖方向图必须让箭头表达允许依赖或边界接入，不表达调用顺序。
- 同一张图内不要同时大量使用自上而下和自左向右两种主方向。

#### 图后说明规则

每张图后必须有 2~5 条说明，说明：

- 图表达了什么架构关系
- 图没有表达哪些概要设计 / 详细设计内容
- 图中最容易误解的边界是什么

禁止图后无说明直接进入下一节。

### 5.4 短文使用规则

短文只用于边界收束：

- 解释为什么这些对象进入本章
- 解释为什么某些相关对象不进入本章
- 解释图表没有表达的内容
- 解释容易误解的边界

短文不承担新判断，不替代表格和图。建议每段 3~5 句。

## 六、编号与术语规范

### 6.1 章节编号

正式架构设计文档应使用本规范第二章定义的 1~18 主链编号，不得自行增删主章节。

若某章当前不适用，应保留章节并说明“不适用原因”，而不是删除章节。

### 6.2 术语分层

以下术语不得混用：

| 术语 | 所属层 | 说明 |
|---|---|---|
| 系统上下文对象 | 架构设计 | 本仓外部正式上下文中的仓、系统、能力或入口系统 |
| 职责边界 | 架构设计 | 本仓做什么、不做什么、哪些职责易混淆 |
| 限界上下文 / 子域 | 架构设计 | 本仓内部语义结构，不是代码模块 |
| 容器 / 部署架构 | 架构设计 | 运行承载角色，不是源码目录或部署手册 |
| 架构责任层 / 依赖角色 | 架构设计 | 依赖方向中的边界角色，不是代码层名 |
| 代码主体 / 模块 | 概要设计 | 由概要设计继续展开的可实现结构主语 |
| 对象 / struct / 函数 | 概要 / 详细设计 | 不应在架构设计中提前展开 |

### 6.3 表达禁区

架构设计中禁止把以下内容作为正式架构主语：

```text
src 目录
文件名
handler / repository / DTO / schema
数据库表名
API path
event topic
函数调用链
测试用例
部署参数
```

## 七、推荐生成方式

架构设计推荐采用“先讨论，后成文”的方式生成。

### 7.1 推荐顺序

```text
1. 阅读当前仓需求文档和全局架构材料
2. 按 `架构设计讨论流程_SOP.md` 逐步收敛 Step 1 ~ Step 16
3. 每一步先确认输入，再确认输出，再围绕输出反推问题
4. 将已确认结论回填到本规范 1~18 正式章节
5. 最后统一术语、图表格式、追溯、ADR 和参考
```

### 7.2 生成约束

- 不允许一次性脑补完整架构设计。
- 不允许跳过需求基线直接画图。
- 不允许在整理正式文档阶段新增未经讨论的新结论。
- 不允许为了文档完整而把未确认事项润色成定论。
- 不允许把概要设计或详细设计内容提前写入架构设计。

### 7.3 与下游文档的衔接

架构设计完成后，应向概要设计交付：

- 系统边界
- 职责边界
- 限界上下文 / 子域划分
- 容器 / 部署架构
- 依赖方向与层间约束
- 数据所有权与一致性策略
- 关键交互与通信方式
- 关键技术机制与取舍
- 风险、待确认事项、ADR 和追溯结论

概要设计不得重新发明这些架构结论，只能在其基础上继续展开代码主体框架、对象轮廓、接口骨架、关键处理流和状态机。

## 八、评审清单

### 8.1 上游承接检查

- 是否明确承接了当前仓需求文档和全局架构材料？
- 是否没有把来源声明写成资料目录或阅读记录？
- 是否没有重写需求目标、用户故事和验收标准？
- 每个正式章节是否列出对应的 `design-calibration` 中间产物，并引导读者继续阅读？

### 8.2 边界检查

- 职责边界是否清楚说明做什么、不做什么、易混淆职责和边界红线？
- 系统上下文图是否只出现正式上下文对象？
- 是否没有把角色、文档来源对象、接口名或事件名画进系统上下文图？
- 限界上下文 / 子域划分是否表达语义结构，而不是对象清单或代码模块清单？

### 8.3 运行与依赖检查

- 容器 / 部署架构是否表达运行承载关系，而不是源码结构或基础设施部署手册？
- 依赖方向图是否表达允许依赖和边界接入，而不是调用顺序？
- 是否没有把 handler、repository、service 等实现名词当成架构责任层？

### 8.4 数据与交互检查

- 数据归属是否先说明谁拥有真相，再说明一致性策略？
- 是否明确区分正式真相数据、快照 / 投影数据、引用关系数据和明确不拥有的正文 / 真相？
- 关键交互是否先说明场景与边界，再说明通信方式？
- 是否没有写 API 目录、事件目录、DTO、schema 或时序流程？

### 8.5 取舍与演进检查

- 关键技术选型是否说明解决的问题、采用理由和代价 / 约束？
- 备选方案是否是路径级替代，而不是局部实现变体？
- 横切关注点是否有作用范围、约束要求和保护目标？
- 演进路线是否是结构演进，不是项目排期或 TODO 清单？

### 8.6 风险、追溯与参考检查

- 风险和待确认事项是否拆开表达？
- 需求追溯矩阵是否写清来源、需求结论、架构承接结果、承接位置和说明？
- ADR 索引是否索引长期架构决策，而不是文件清单或历史年表？
- 参考材料是否说明材料类别、用途 / 参考价值和入章理由？

### 8.7 图表一致性检查

- 每张 ASCII 图是否有明确图类型标题、`text` 代码块和 2~5 条图后说明？
- 图是否使用本规范允许的图类型？
- 图是否保持统一字符集、统一方向和统一箭头风格？
- 图是否没有混入 Mermaid / PlantUML / Graphviz、Emoji、颜色或 Markdown 表格？
- 表格是否承担结构判断职责，而不是退化成 checklist？

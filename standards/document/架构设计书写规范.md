# 架构设计书写规范

> 架构设计回答 **"约束是什么、边界怎么划、方向朝哪走、变化怎么管、决策为什么"**。  
> 它是设计文档漏斗的最上层——在需求与概要设计之间，识别不可逆决策，选择架构风格，划定系统边界。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)  
> 架构图绘制方法见 → [设计文档编写通则](设计文档编写通则.md) 第二章  
> 架构设计理论基础见 → [架构设计](../../architecture/架构设计.md)  
> 概要设计书写规范见 → [概要设计书写规范](概要设计书写规范.md)

## 一、架构设计的目标

架构设计要解决五个核心问题：

1. **识别约束**：哪些是不能变的，哪些是可以变的
2. **选择边界**：在哪里划分模块/服务/上下文
3. **控制方向**：依赖朝哪走，数据归谁管
4. **管理变化**：哪些维度需要容易修改，哪些需要稳定
5. **记录决策**：为什么这样选，不那样选

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│  架构设计与概要设计的关系：                                    │
│                                                              │
│  架构设计 → 识别不可逆决策、选择架构风格、划定边界            │
│     │                                                        │
│     ▼                                                        │
│  概要设计 → 在架构决策的约束下，定义模块、选型、接口          │
│     │                                                        │
│     ▼                                                        │
│  详细设计 → 具体实现方案（能直接编码）                        │
│                                                              │
│  区别：                                                      │
│  · 架构设计关注"哪些决策一旦做出就难以逆转"                  │
│  · 概要设计关注"在架构约束下做什么、怎么做"                  │
│  · 小项目可合并，大项目必须分离                               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 四、各模块编写要点

### 4.1 文档元信息与读码导航

文档元信息不仅是"标题+作者+日期"，更重要的附加项是**读码导航**——告诉不同时间预算的读者应该看什么：

| 时间预算 | 阅读路径 |
|---------|---------|
| 15 分钟 | §4~§8（架构风格、边界、容器、依赖） |
| 1 小时  | 本文档全文 + ADR 索引 |
| 半天    | + 概要设计 + 对应核心代码 + 架构理论体系 |

### 4.2 业务背景与驱动力

**编写要点**：
- 用 3~5 句话说清"为什么要做"——不要写成 PRD 摘抄
- **驱动力分类**：区分业务驱动力（增长、合规、体验）和技术驱动力（性能、可维护性、成本）
- 问题定义要量化：当前 QPS 是多少、P99 延迟是多少、故障率是多少
- 业务目标要有成功标准：如"支撑日均 500 万订单"，而非"支撑更多订单"

### 4.3 约束条件

**编写要点**：
- 约束必须分类为**不可变约束**和**可变约束**——这决定了后续决策的自由度
  - 不可变约束：监管合规、已有合同、物理限制、不可逆的技术选型
  - 可变约束：人力、时间、预算——这些可以通过协商改变
- 不可变约束是架构决策的**输入**，不是要解决的问题
- 容量规划必须包含量化依据，而非拍脑袋数字

```
┌──────────────────────────────────────────────────────────────┐
│  约束分类示例                                                │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  不可变约束（架构决策必须遵守）：                              │
│  · 用户数据必须存储在国内（合规）                             │
│  · 支付交易必须可审计（监管）                                 │
│  · 必须使用公司统一认证中心（组织约束）                       │
│                                                              │
│  可变约束（可通过协商改变）：                                 │
│  · 首期开发人力 5 人                                         │
│  · 上线截止 3 月底                                           │
│  · 云资源月预算 5 万                                         │
│                                                              │
│  关键判断：                                                   │
│  · 不可变约束 → 架构必须适应                                 │
│  · 可变约束 → 架构应尽量保留调整空间                         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 4.4 架构风格与选型

**编写要点**：
- 架构风格的选择不是"我喜欢"或"别人也这样"，而是**选择一组约束来获得特定收益**
- 必须使用**架构风格决策框架**来论证选型

```
┌──────────────────────────────────────────────────────────────┐
│                    架构风格决策框架                             │
│                                                              │
│  Step 1: 识别系统的主要变化维度                               │
│    · 哪些部分变化最频繁？                                     │
│    · 哪些部分最需要独立演进？                                  │
│    · 哪些部分最需要独立扩展？                                  │
│                                                              │
│  Step 2: 评估约束的收益-成本                                  │
│    · 这个约束是否解决了 Step 1 中识别的真正问题？              │
│    · 这个约束的成本（运维、理解、沟通）是否可接受？            │
│    · 如果去掉这个约束，最坏情况是什么？                        │
│                                                              │
│  Step 3: 选择约束最少的风格                                   │
│    · 优先选约束少的风格（单体 > 模块化单体 > 微服务）          │
│    · 只有当约束的收益明确大于成本时才增加约束                  │
│    · 约束应该是被问题驱动的，而不是被趋势驱动的                │
│                                                              │
│  Step 4: 预留演进路径                                        │
│    · 当前选择不应关闭未来选择的门                              │
│    · 模块化单体应该能按模块拆成微服务                          │
│    · 分层架构应该能演进为六边形架构                            │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

- 常见架构风格的约束-收益分析必须写明：

| 架构风格 | 核心约束 | 核心收益 | 核心代价 | 适用场景 |
|---------|---------|---------|---------|---------|
| 分层架构 | 层间单向依赖 | 关注点分离，易理解 | 层泄漏风险 | 业务逻辑简单的系统 |
| 六边形架构 | 内部不依赖外部 | 业务与技术解耦 | 接口层间接开销 | 核心逻辑需要保护的业务系统 |
| 整洁架构 | 依赖方向由外向内 | 框架无关，可测试 | 层次多时开发效率 | 领域模型复杂的系统 |
| 微服务 | 服务独立部署+独立数据库 | 独立扩展、独立演进 | 分布式复杂性 | 团队>15人、部署冲突频繁 |
| 事件驱动 | 组件通过事件通信 | 时间解耦、空间解耦 | 一致性复杂、调试困难 | 需要异步解耦的流程 |

**核心原则**：**约束必须被问题驱动，而非趋势驱动**。"别人也这样拆"不是选择架构风格的理由。

### 4.5 系统边界与上下文

**编写要点**：
- 系统上下文图的绘制规范见 → [设计文档编写通则](设计文档编写通则.md) §2.1
- 文字说明必须补充：职责边界、外部系统可用性约束、关键依赖风险、数据归属
- **常见错误**：只画图不写文字——图传达不了 SLA、降级策略等语义
- 系统边界定义要明确"做什么 / 不做什么"——防止范围蔓延

### 4.6 限界上下文与子域划分

**编写要点**：
- 子域分类是架构级决策——决定了不同部分的投入策略
  - **核心域**：竞争力所在，值得投入最优秀的建模资源
  - **支撑子域**：必要但不构成壁垒，可外包或用现成方案
  - **通用子域**：可购买/复用现成方案（如认证、通知）
- 限界上下文的划分原则：
  - 围绕业务能力而非技术层
  - 同一术语跨上下文有不同含义时，必须定义限界上下文
  - 上下文间的映射关系必须明确

**统一语言词汇表**（必须附带）：

| 业务术语 | 代码命名 | 语义定义 | 所属上下文 |
|---------|---------|---------|-----------|
| 商品 | Product | SKU + 价格 + 库存 | 商品上下文 |
| 商品 | Product | 重量 + 尺寸 + 包装 | 物流上下文 |
| 订单 | Order | 用户购买记录 | 订单上下文 |

> **关键检验**：如果开会说的词和代码里的词不一样，统一语言就没有真正落地。

**上下文映射关系模式**：

| 关系模式 | 语义 | 适用场景 |
|---------|------|---------|
| 防腐层 (ACL) | 下游隔离上游模型 | 上游不稳定或概念不匹配 |
| 开放主机服务 (OHS) | 上游提供标准协议 | 上游被多个下游依赖 |
| 共享内核 (SK) | 共享稳定模型 | 概念高度重合且变更极少 |
| 客户-供应商 (C/S) | 上游根据下游需求提供 | 下游需求优先级高 |
| 遵奉者 (Conformist) | 下游直接采用上游模型 | 适配成本高于遵从成本 |
| 各走各路 (SW) | 不建立集成 | 集成收益低于成本 |

### 4.7 容器/部署架构

**编写要点**：
- 容器图的绘制规范见 → [设计文档编写通则](设计文档编写通则.md) §2.2
- 每个容器必须标注：技术栈、职责（一句话）、数据存储归属
- 通信方式选择的理由必须写明（为什么这里用同步 HTTP 而非异步 MQ）
- **数据存储归属**：谁写谁读，标注 Single Writer 原则
- 部署拓扑：集群/单机、区域、实例数

### 4.8 依赖方向与层间约束

**编写要点**：
- 依赖方向决定了系统的**变化传播方向**——这是架构设计中最核心的防线
- **层间约束必须写明**——这是防止架构退化的核心防线
  - 例："domain 层不直接依赖 infra 层（通过接口倒置）"
  - 例："api 层只做参数校验和响应组装，不含业务逻辑"
  - 例："跨上下文调用通过 API / 事件，不直接访问内部"
- 依赖方向必须与稳定性方向一致——稳定的模块被依赖，不稳定的模块依赖稳定的模块

**依赖健康度评估**：

| 指标 | 含义 | 健康方向 |
|------|------|---------|
| 传入耦合 | 被多少其他模块依赖 | 核心模块应该高（被依赖） |
| 传出耦合 | 依赖了多少其他模块 | 核心模块应该低（不依赖） |
| 不稳定性 | 传出 / (传入 + 传出) | 核心模块应该接近 0 |
| 抽象度 | 抽象类/接口的比例 | 稳定模块应该高抽象 |

**层间约束多语言示例**：

```c

    const stock_proxy_t *stock;   // 依赖接口，不依赖实现

// infra/stock_proxy_grpc.c — infra 层实现 domain 层声明的接口
static int grpc_batch_deduct(stock_proxy_t *self, const item_list_t *items) {
    // gRPC 调用实现...
}

// 入口处注册实现
stock_proxy_t *stock_proxy = stock_proxy_grpc_create(channel);
order_service_t svc = { .stock = stock_proxy, .repo = repo };
```

### 4.9 数据所有权与一致性策略

**编写要点**：
- **数据所有权矩阵**是架构设计中最重要的表格之一——它决定了服务边界的合理性
- **每份数据有且只有一个写入者**（Single Writer Principle）——违反此原则的地方必须标注风险
- 一致性策略必须分层设计：

```
┌──────────────────────────────────────────────────────────────┐
│                      一致性层次模型                            │
│                                                              │
│  Level 1: 聚合内一致性（强一致）                              │
│  · 通过事务保证聚合的不变式                                   │
│  · 本地事务即可满足                                           │
│                                                              │
│  Level 2: 聚合间一致性（最终一致）                            │
│  · 通过领域事件 + 异步通知实现最终一致性                       │
│  · 需要设计补偿机制处理失败场景                                │
│                                                              │
│  Level 3: 跨服务一致性（Saga 模式）                           │
│  · 每个服务有自己的数据库，无法使用跨库事务                    │
│  · 通过编排或协调的 Saga 模式管理长事务                        │
│  · 每个步骤有对应的补偿操作                                    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

- Saga 模式选择依据：
  - 参与者 ≤ 3 且流程简单 → 编排式（Choreography）
  - 参与者 > 3 或流程复杂 → 协调式（Orchestrator）
- 涉及事件发布时，必须说明是否使用 Transactional Outbox 模式

**数据所有权矩阵模板**：

| 数据 | 拥有者（写入方） | 消费者（读取方） | 一致性策略 | 风险标注 |
|------|----------------|----------------|-----------|---------|
| 订单数据 | 订单服务 | 支付服务、通知服务 | 聚合内强一致 | — |
| 库存数据 | 库存服务 | 订单服务（查询） | 跨服务 Saga | ⚠ 订单服务也写库存（预扣），需区分 |

### 4.10 关键技术选型

**编写要点**：
- 使用**决策四元组**：当前选择 | 备选方案 | 选择理由 | 演进路径
- 选择理由写"权衡"而非"事实"——
  - ✗ "选 Kafka 因为吞吐高"（事实，不是权衡）
  - ✓ "选 Kafka 而非 RabbitMQ 因为我们的场景吞吐优先于路由灵活"（权衡）
- 演进路径让未来维护者知道"还可以怎么做"
- **选型不可逆程度评估**：

```
┌──────────────────────────────────────────────────────────────┐
│  决策的不可逆程度                                             │
│                                                              │
│  高可逆 (随时可改)                                           │
│  · 具体算法实现                                              │
│  · 缓存策略                                                  │
│  · 框架版本                                                  │
│  → 快速决定，边做边调                                        │
│                                                              │
│  中等可逆 (改造成本中等)                                      │
│  · 数据库选型                                                │
│  · 消息队列选型                                              │
│  · 服务间通信协议                                            │
│  → 通过端口/适配器隔离，降低切换成本                          │
│                                                              │
│  低可逆 (改造成本极高)                                        │
│  · 系统边界划分                                              │
│  · 依赖方向                                                  │
│  · 数据所有权                                                │
│  · 统一语言                                                  │
│  → 充分思考，尽早确定，用 ADR 记录                           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 4.11 备选方案与取舍

**编写要点**：
- 至少 2~3 个备选方案，用对比表格呈现
- 对比维度应覆盖：一致性、吞吐量、复杂度、运维成本、团队熟悉度、**不可逆程度**
- 选择结论要写明理由，不要让读者猜
- 每个被否决的方案记录否决原因——这是 ADR 的输入

### 4.12 横切关注点

**编写要点**：
- 韧性、可观测性、安全、配置管理、性能——五项不可遗漏
- **韧性设计**是分布式系统最重要的横切能力：

| 韧性模式 | 架构设计中应明确的内容 |
|---------|---------------------|
| 超时策略 | 各外部调用的超时阈值及理由 |
| 重试策略 | 次数、退避算法、可重试的错误类型 |
| 熔断策略 | 触发条件、恢复机制、降级方案 |
| 限流策略 | 限流维度、阈值、被限流时的响应 |
| 降级策略 | 哪些功能可降级、降级后的替代行为 |
| 隔离策略 | 线程池隔离 / 信号量隔离 / 租户隔离 |

- **性能预算表**是必须项：端到端延迟分解，每环节预估延迟 + 依据
- 非功能指标要标注来源：如"P99 < 15ms ← 非功能需求 ORD-NF01"

### 4.13 演进路线

**编写要点**：
- 架构不是一次性设计，而是持续演进——演进路线是架构设计的重要组成部分
- 演进触发条件必须是**可量化的**，而非主观感受：

```
┌──────────────────────────────────────────────────────────────┐
│  演进触发条件（参考阈值）                                     │
│                                                              │
│  · 团队规模 > 15 人                                         │
│  · 部署冲突频率 > 每周 2 次                                  │
│  · 某个模块的 QPS 与整体差距 > 10 倍                        │
│  · 某个模块的发布频率与整体差距 > 5 倍                      │
│                                                              │
│  注意：这些是参考阈值，不是硬性标准。                        │
│  真正的触发条件应该是"当前架构的痛苦程度"而非数字。           │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

- 演进步骤的核心原则：**每一步之间是松耦合的——可以停在任意一步**
- 推荐演进路线：

```
  Phase 1: 模块化单体
  · 内部按限界上下文分模块
  · 每个模块有自己的 domain / app / infrastructure
  · 模块间通过接口/事件通信
  · 一个部署单元

  Phase 2: 按需拆分
  · 当部署冲突频繁时，拆出变化最频繁的模块
  · 当团队扩大时，按团队边界拆分
  · 当性能瓶颈明确时，拆出需要独立扩展的模块
  · 每次只拆一个模块，不要一次性全拆

  Phase 3: 持续优化
  · 根据实际运行数据调整服务边界
  · 引入 CQRS / ES 只在真正需要的上下文
```

- 目标架构不是固定终点，而是方向

### 4.14 风险与待确认事项

**编写要点**：
- 异常场景分两层：「常见」和「边缘」——处理优先级不同
- 每个风险必须有缓解策略，不能只列风险不列方案
- 待确认事项要标注截止时间——过期未确认视为接受风险
- **反模式自查**：风险清单中应包含对常见反模式的排查

**反模式自查清单**：

| 反模式 | 根因 | 自查问题 |
|--------|------|---------|
| 简历驱动架构 | 用技术时髦度驱动决策 | "如果去掉这个技术，我解决的那个问题是否还存在？" |
| 过早微服务 | 混淆最终形态与起步形态 | "当前的痛点是否必须通过拆服务解决？" |
| 分布式单体 | 拆了服务但共享数据库 | "是否有多个服务写同一个数据库/表？" |
| 全局 CQRS | 没有局部复杂度就全局引入 | "读写差异是否大到必须分离模型？" |
| 忽视康威定律 | 架构与团队不匹配 | "服务边界是否对齐团队边界？" |
| 层泄漏 | 业务逻辑散落在 Controller/DAO | "domain 层是否承载了核心业务规则？" |
| 万能 common 模块 | 什么都往 common 里塞 | "common 模块是否只包含工具类和接口定义？" |

### 4.15 上线策略

**编写要点**：
- 灰度方案：流量切换比例、观察时间、推进条件
- 回滚策略：触发条件、回滚步骤、数据兼容性
- 监控指标：关键业务指标 + 系统指标，标注告警阈值
- **架构变更的上线策略**应比功能上线更保守——架构变更的影响范围更广

## 五、架构设计评审清单

### 5.1 业务对齐

- [ ] 业务背景和驱动力是否清晰
- [ ] 业务目标是否有可量化的成功标准
- [ ] 架构风格是否与业务目标匹配（而非与趋势匹配）
- [ ] 能解释"为什么这样设计"而非"别人也这样设计"
- [ ] 没有为假想未来过度设计

### 5.2 边界划分

- [ ] 边界围绕业务能力而非纯技术分层
- [ ] 子域分类是否合理（核心域/支撑子域/通用子域）
- [ ] 限界上下文划分是否有业务语义支撑
- [ ] 统一语言词汇表是否建立
- [ ] 上下文映射关系是否明确
- [ ] 数据所有权清晰，无共享写入
- [ ] 同一术语跨边界有不同含义时已定义限界上下文
- [ ] 跨边界协作通过 API / 事件 / 消息，而非直接访问内部

### 5.3 依赖方向

- [ ] 依赖方向与稳定性方向一致
- [ ] 核心业务不直接依赖框架 / 数据库 / SDK
- [ ] 通过端口（接口）隔离外部依赖
- [ ] 无循环依赖
- [ ] 层间约束规则是否写入文档

### 5.4 一致性策略

- [ ] 聚合内使用强一致，聚合间使用最终一致
- [ ] 跨服务一致性使用 Saga / Outbox 而非 2PC
- [ ] 补偿机制已设计
- [ ] 事件发布是否使用 Outbox 模式

### 5.5 技术选型

- [ ] 架构风格是否使用决策框架论证
- [ ] 技术选型是否使用决策四元组（选择+备选+理由+演进路径）
- [ ] 选型不可逆程度是否评估
- [ ] 备选方案是否至少 2~3 个

### 5.6 横切能力

- [ ] 韧性：超时、重试、熔断、降级、限流
- [ ] 可观测：日志、指标、追踪、健康检查
- [ ] 安全：认证、授权、审计、密钥管理
- [ ] 配置：外部化配置、环境隔离
- [ ] 性能预算表是否包含端到端延迟分解

### 5.7 演进能力

- [ ] 新增一个业务能力只需改少量模块
- [ ] 替换基础设施时核心业务不受影响
- [ ] 团队扩大后边界仍能支撑协作
- [ ] 演进路线是否有可量化的触发条件
- [ ] 演进步骤是否可以停在任意一步

### 5.8 决策记录

- [ ] 重要架构决策已写 ADR
- [ ] ADR 包含背景、备选方案、取舍、后果
- [ ] 需求追溯矩阵是否完整

### 5.9 反模式自查

- [ ] 是否存在简历驱动架构的迹象
- [ ] 微服务拆分是否由真正痛点驱动
- [ ] 是否存在共享数据库的分布式单体
- [ ] 是否过度使用 CQRS / ES
- [ ] 架构边界是否对齐团队边界
- [ ] 是否存在层泄漏
- [ ] common 模块是否过厚

### 5.10 上线与风险

- [ ] 灰度和回滚方案是否完备
- [ ] 上下游影响是否评估
- [ ] 风险是否有缓解策略
- [ ] 异常场景是否区分「常见」和「边缘」
- [ ] 文档是否包含版本号和变更记录
- [ ] 评审人是否覆盖架构/开发/测试/运维

```
│  · 依赖方向与层间约束          · 关键技术选型（决策四元组）       │
│  · 数据所有权与一致性策略      · 备选方案与取舍                   │
│  · 演进路线                    · 横切关注点                       │
│  · ADR                         · 上线策略                         │
│                                                                  │
│  重叠区域（两者都需要关注）：                                     │
│  · 约束条件、横切关注点、风险与待确认、上线策略                  │
│  · 小项目可合并为一份文档                                        │
│                                                                  │
│  分离原则：                                                      │
│  · 如果架构决策还未稳定，先写架构设计                            │
│  · 如果架构决策已稳定，概要设计直接引用                          │
│  · 架构设计变更影响全局，概要设计变更影响局部                    │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

## 八、反模式与常见错误

### 8.1 架构设计文档的致命错误

```
┌───────────────────────────────────────────────────────────┐
│              架构设计文档的 10 个致命错误                    │
├───────────────────────────────────────────────────────────┤
│                                                           │
│  ❶ 只画架构图，不写层间约束                                │
│     → 后续开发"图方便"跨层调用，架构逐渐退化                │
│                                                           │
│  ❷ 架构选型没有用决策框架论证                              │
│     → "别人也这样"不是理由，约束必须被问题驱动              │
│                                                           │
│  ❸ 没有数据所有权矩阵                                     │
│     → 多服务写同一张表是分布式系统最危险的耦合              │
│                                                           │
│  ❹ 限界上下文按技术层划分而非业务能力                      │
│     → 技术边界比业务边界更不稳定                            │
│                                                           │
│  ❺ 没有演进路线                                           │
│     → 架构成为不可改变的"遗产"，而非可持续演化的资产        │
│                                                           │
│  ❻ 没有区分不可变约束和可变约束                            │
│     → 可变约束被当作不可变约束，限制了架构的调整空间        │
│                                                           │
│  ❺ 一致性策略没有分层设计                                  │
│     → 要么全部强一致（性能差），要么全部最终一致（数据乱）  │
│                                                           │
│  ❽ 没有写 ADR                                             │
│     → 后来者不知道"为什么这样选"，容易重复论证已否决方案    │
│                                                           │
│  ❾ 把架构设计写成详细设计                                  │
│     → 架构设计关注不可逆决策，不是代码实现细节              │
│                                                           │
│  ❿ 没有反模式自查                                        │
│     → 简历驱动、过早微服务、分布式单体等反模式未排查        │
│                                                           │
└───────────────────────────────────────────────────────────┘
```

### 8.2 架构设计核心反模式

| 反模式 | 根因 | 检验方法 |
|--------|------|---------|
| **简历驱动架构** | 用技术时髦度而非问题驱动决策 | "去掉这个技术，我解决的问题是否还在？" |
| **过早微服务** | 混淆最终形态和起步形态 | "当前的痛点是否必须通过拆服务解决？" |
| **分布式单体** | 拆了服务但共享数据库 | "是否有多个服务写同一个数据库/表？" |
| **全局 CQRS** | 没有局部复杂度就全局引入 | "读写差异是否大到必须分离模型？" |
| **忽视康威定律** | 架构与团队协作方式不匹配 | "服务边界是否对齐团队边界？" |
| **层泄漏** | 业务逻辑出现在 Controller/DAO | "domain 层是否承载了核心业务规则？" |
| **万能 common 模块** | 什么都往 common 里塞 | "common 是否只包含工具类和接口定义？" |
| **事件伪装命令** | "请创建订单"伪装成事件 | "这个消息是过去时（事件）还是祈使语气（命令）？" |
| **过度抽象** | 为假想的未来变化建立抽象 | "当前需求是否驱动了这个抽象？" |
| **技术驱动的边界** | 按技术层而非业务划分 | "业务边界是否比技术边界更稳定？" |

> **所有反模式的共性**：将手段当作目的。微服务是手段，业务解耦是目的；DDD 是手段，领域理解是目的；技术选型是手段，解决问题是目的。

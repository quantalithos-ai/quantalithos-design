# 概要设计书写规范

> 概要设计回答 **“在已收稳的需求与架构边界下，系统如何被组织成可实现的主要结构”**。  
> 它位于架构设计与详细设计之间，负责定义系统由哪些主要部分构成、这些部分各自承担什么职责、通过哪些关键接缝协作，以及哪些对象与流程轮廓足以支撑进入详细设计。

## 一、概要设计的目标

概要设计要解决的问题包括：

1. 在已收稳的需求与架构边界下，系统由哪些主要部分构成
2. 这些主要部分各自承担什么职责，通过哪些关键接缝协作
3. 哪些关键对象与主要流程轮廓已经足以支撑进入详细设计

概要设计不回答：

```text
重新定义需求目标、用户故事、验收标准
重新定义系统上下文、子域划分、方案取舍或架构级技术选型
提前展开字段、函数、DDL、时序细节、部署参数和运维细节
```

---

## 二、概要设计与上游 / 下游文档的边界

### 2.1 相对需求文档

概要设计承接已收稳的需求结论，但不再重写：

- 目标与非目标
- 用户故事
- 功能需求
- 验收标准

### 2.2 相对架构设计

概要设计承接已收稳的架构边界与约束，但不再重写：

- 系统上下文与边界
- 限界上下文与子域划分
- 数据所有权原则
- 关键技术选型
- 备选方案与取舍
- ADR 索引
- 需求追溯矩阵

### 2.3 相对详细设计

概要设计停在“可实现结构轮廓”，不提前展开：

- 代码目录结构
- 字段定义
- 函数调用链
- DDL / 索引
- 协议 schema
- 部署与运维细节

### 2.4 术语与表达总规则

#### 核心主术语
概要设计线的核心主术语统一如下：

- `主要组成部分`：概要设计层的正式主要部分，不与架构线的系统边界 / 子域主语，也不与详细设计层的模块 / 类 / 函数主语混用。
- `关键接缝`：主要组成部分之间已足够稳定、需要在概要设计层正式点名的协作接面，不写成协议细节或实现接口。
- `轮廓`：概要设计层对对象、流程、异常与边界场景的表达深度词，用于表示“已进入可实现结构层，但仍未下沉到详细设计”。

除非确有必要，不再并行使用 `正式部分`、`接面`、`承接口径` 等与以上主术语近义但易造成跨章漂移的表达。

#### 图 / 表 / 短文总规则
概要设计线整体采用：

- 表为主
- 图按需
- 短文收束边界

其中：
- 表负责收稳主语、职责、边界、接缝、对象与流程轮廓，不退化成 checklist。
- 图只在纯文字与表格不足以建立结构感时才出现，不承载 API、事件、字段、函数、DDL、详细时序或运维参数。
- 短文只用于解释为什么某章这样切、为什么某些内容不该展开，以及如何理解例外，不承担新判断。

#### `identity` 辅助说明最小规则
`identity` 辅助说明只用于把通用规则映射到真实仓级语境：

- 不新增本章判断标准
- 不替代主规则
- 不充当实现示例
- 不形成第二套样板正文

如果某章的 `identity` 辅助说明只是复述正文，则应缩短到仅保留映射价值。

## 三、概要设计的章节主链

正式文档建议使用以下章节顺序：

```text
1. 与上游文档的关系声明
2. 本次设计目标与范围
3. 约束条件
4. 主要组成部分概览
5. 各部分职责与边界
6. 关键接缝与接口轮廓
7. 关键对象轮廓
8. 主要流程轮廓
9. 异常与边界场景轮廓
10. 设计风险与待确认事项
11. 参考
```

## 四、章节级规范

### 4.1 与上游文档的关系声明

#### 4.1.1 本章目标

说明当前 `02-概要设计.md` 在语义上承接哪些已收稳的需求与架构结论，明确这份概要设计不是重新定义需求与架构，而是在这些前提下继续向“可实现结构”展开。

本章只回答“本文承接自哪里”，不正式收口本次概要设计要讲到哪里；后者应在 4.2 中完成。

#### 4.1.2 本章应回答的问题

```text
1. 本文承接哪些需求文档与架构文档？
2. 承接的是上游哪一部分已经收稳的结论？
3. 本文为什么不是重新定义这些需求与架构主题？
4. 本文只在什么层次继续展开？
```

#### 4.1.3 本章不应回答的问题

```text
- 不重新解释需求目标、用户故事、验收标准
- 不重新解释系统上下文、子域划分、依赖方向、数据归属原则
- 不提前展开主要组成部分、职责、接缝、对象或流程内容
- 不把本章写成上游文档摘要或目录复述
```

#### 4.1.4 推荐表达形式

##### 主表达形式
1. 来源映射表
2. 一段收束说明短文

##### 图表分工
- 表负责说明：承接自哪些文档、哪一部分结论、承接内容是什么。
- 短文负责说明：本文为什么不是重写上游，而是继续向概要设计层展开。

#### 4.1.5 来源映射表

##### 固定结构表

| 来源文档 | 上游章节 / 模块 | 承接内容 |
|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 来源文档 | 当前概要设计正式承接的需求文档或架构文档 | 不写临时笔记、讨论稿、阅读材料 |
| 上游章节 / 模块 | 上游文档中被承接的稳定结论所在位置 | 不写模糊“前文提过”类描述 |
| 承接内容 | 已收稳的边界前提、结构前提、接缝前提或对象前提 | 不写需求目标、功能清单、技术选型或实现细节 |

#### 4.1.6 写法规则

##### 承接内容的粒度
这一列只写：
- 本文继续展开所依赖的上游前提

优先写：
- 主要边界前提
- 主要组成前提
- 关键接缝前提
- 对象与流程轮廓前提

不应写：
- 用户故事
- 功能项
- 接口名
- 模块名
- 结构体名
- 字段级内容

##### 收束说明短文
短文必须回答：

```text
1. 本文继续展开的是哪一层问题
2. 为什么本文不是重新定义需求或架构
3. 本文承接上游后，准备向什么层次展开
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做承接层次说明
- 不提前进入 4.2 ~ 4.10 的具体内容
```

#### 4.1.7 完成标准

- 已明确本文承接哪些正式需求与架构来源
- 已明确承接的是哪些已经收稳的结论
- 已明确本文只继续展开概要设计层问题
- 没有把本章写成需求摘要、架构摘要或新内容正文

#### 4.1.8 正反例

**正确示例（通用）：**

| 来源文档 | 上游章节 / 模块 | 承接内容 |
|---|---|---|
| `00-需求文档.md` | `目标与非目标` / `核心能力主线` | 本次概要设计继续承接的能力边界与范围前提 |
| `01-架构设计.md` | `职责边界` / `主要边界与协作方式` | 本次概要设计展开主要组成部分与关键接缝时必须守住的架构边界 |
| `01-架构设计.md` | `数据所有权与一致性策略` / `关键交互与通信方式` | 本次概要设计定义对象轮廓和流程轮廓时必须承接的数据与交互前提 |

**收束说明短文示例：**

```text
本文在已收稳的需求与架构边界下，继续向“可实现结构”展开。它不重新定义系统边界、数据归属和技术取舍，只承接这些前提，进一步说明系统由哪些主要部分构成、这些部分如何通过关键接缝协作，并收稳进入详细设计所需的结构轮廓。
```

**错误示例 A：写成需求摘要**

```text
本文承接用户故事、功能需求、验收标准，并进一步细化这些需求。
```

错误原因：
```text
这会让概要设计回滑成需求文档第二版，而不是承接需求后继续展开可实现结构。
```

**错误示例 B：写成架构摘要**

```text
本文承接系统上下文、子域划分、技术选型和架构取舍，并重新整理系统整体结构。
```

错误原因：
```text
这会让概要设计变成架构设计第二版，而不是承接架构边界后继续下沉到主要部分与接缝轮廓。
```

**错误示例 C：提前写本章后续正文**

```text
本文承接上游后，将系统划分为入口层、承接层、对象层、执行层，并定义主要流程。
```

错误原因：
```text
这里已经提前进入 4.4 之后的正文内容，不属于 4.1 的职责。
```

#### 4.1.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- `02-概要设计.md` 不是重新定义“身份真相仓”是什么
- 也不是重新论证身份边界、状态传播方式或数据归属原则
- 它只是在这些已收稳前提下，确认后续概要设计可以承接哪些输入边界，并为“本次设计目标与范围”的正式收口建立前提

这段说明只用于帮助理解承接层次，不作为模板定义来源。

### 4.2 本次设计目标与范围

#### 4.2.1 本章目标

明确本次概要设计准备收敛到什么深度、重点把哪些主要结构讲清，以及哪些内容当前不进入概要设计范围，从而为后续“主要组成部分、职责、接缝、对象与流程轮廓”的展开建立稳定边界。

#### 4.2.2 本章应回答的问题

```text
1. 本次概要设计最主要要把哪些结构讲清？
2. 这一轮概要设计应停在什么深度，才算足够支撑进入详细设计？
3. 哪些内容属于本次概要设计范围？
4. 哪些内容虽然相关，但当前不进入概要设计范围？
5. 哪些内容应明确留给详细设计，而不应在概要设计中提前展开？
```

#### 4.2.3 本章不应回答的问题

```text
- 不重写需求目标、用户故事、验收标准
- 不重写系统上下文、子域划分、技术选型和方案取舍
- 不直接拆字段、函数、DDL、时序细节
- 不把“当前范围”写成产品路线图、任务拆单或功能愿望池
- 不把“非范围”写成模糊的“以后再说”
```

#### 4.2.4 推荐表达形式

##### 主表达形式
1. 设计目标表
2. 非范围表

##### 图表分工
- 目标表负责说明：这轮概要设计必须收稳哪些结构轮廓。
- 非范围表负责说明：哪些内容当前明确不进入概要设计范围，以及为什么不进入。

#### 4.2.5 设计目标表

##### 固定结构表

| 设计目标 | 说明 | 验证方式 |
|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 设计目标 | 本次概要设计完成后应成立的主要结构轮廓 | 不写功能项、接口名、技术产品名 |
| 说明 | 该结构轮廓为什么是本次概要设计必须收稳的 | 不写实现步骤或详细设计细节 |
| 验证方式 | 如何判断这一轮概要设计已把该目标讲清 | 不写项目验收或测试计划 |

#### 4.2.6 非范围表

##### 固定结构表

| 非范围 | 不进入原因 |
|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 非范围 | 当前不进入概要设计的内容 | 不写模糊“后续可能有”类愿望项 |
| 不进入原因 | 为什么该内容应保留在上游或下游章节中 | 不写拖延式理由或任务借口 |

#### 4.2.7 写法规则

##### 设计目标的粒度
设计目标应写成：

```text
本次概要设计完成后，应已讲清的主要结构轮廓
```

优先写：
- 主要组成部分的稳定划分
- 各部分职责与边界轮廓
- 关键接缝与接口轮廓
- 关键对象轮廓
- 主要流程轮廓

不应写：
- 用户故事
- 功能需求
- 技术选型
- 方案取舍
- 详细设计对象
- 上线与运维细节

##### 非范围的写法
非范围应明确写成：

```text
当前不进入概要设计范围，原因是……
```

优先写明它属于：
- 需求文档
- 架构设计
- 详细设计
- 运维/实施层

不应写成：
- 以后再看
- 后续优化
- 暂时不做

因为这类表述没有边界判断力。

#### 4.2.8 完成标准

- 已明确本次概要设计要收敛哪些主要结构轮廓
- 已明确概要设计当前停在什么深度
- 已明确哪些内容当前不进入概要设计范围
- 已说明这些非范围项分别属于上游还是下游层次
- 没有把范围写成功能愿望池，也没有把非范围写成拖延借口

#### 4.2.9 正反例

**正确示例（通用）：**

##### 设计目标表

| 设计目标 | 说明 | 验证方式 |
|---|---|---|
| 建立主要组成部分的稳定划分 | 必须让读者知道系统由哪些正式部分构成，而不是停留在抽象架构边界上 | 后续章节能围绕这些部分持续展开且不再随意增删主语 |
| 建立各部分职责与关键接缝轮廓 | 必须先说明各部分做什么、如何接起来，后续详细设计才能有稳定输入 | 后续章节能围绕职责与接缝收稳对象轮廓与流程轮廓 |
| 建立进入详细设计所需的关键对象与主要流程轮廓 | 必须在概要设计层把对象与流程讲到足以进入详细设计的程度 | 后续详细设计可以展开字段、函数与时序，而无需重新发明主结构 |

##### 非范围表

| 非范围 | 不进入原因 |
|---|---|
| 系统上下文与边界重述 | 已由架构设计收稳，不应在概要设计中重新展开 |
| 技术产品选型比较 | 属于架构设计取舍层，不属于概要设计主语 |
| 字段级对象定义与 DDL | 属于详细设计层，不应提前进入概要设计 |
| 上线策略、灰度、回滚与运维细节 | 属于部署与运维实施层，不应进入概要设计主链 |

**错误示例 A：把设计目标写成功能清单**

```text
目标：
- 支持创建对象
- 支持查询对象
- 支持更新对象
```

错误原因：
```text
这已经回滑成需求功能项，而不是概要设计层的结构目标。
```

**错误示例 B：把设计目标写成技术选型**

```text
目标：
- 采用事件驱动
- 引入 Redis
- 使用 PostgreSQL
```

错误原因：
```text
这些是架构设计或技术选型层的问题，不是概要设计层的本次设计目标。
```

**错误示例 C：把非范围写成拖延口号**

```text
非范围：
- 后续再考虑
- 以后优化
- 暂时不做
```

错误原因：
```text
没有说明该项为何不进入概要设计，也没有说明它属于哪一层。
```

#### 4.2.10 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 当前 `02-概要设计.md` 这一轮到底要讲清 identity 的哪些主要结构轮廓
- 哪些内容仍停留在已收稳的架构边界层
- 哪些内容应明确留给详细设计去展开

它不是在重新定义 identity 的目标，也不是提前写 identity 的详细设计，只是在正式收口“这次概要设计讲到哪里、停在什么深度”。

### 4.3 约束条件

#### 4.3.1 本章目标

说明当前概要设计在继续向“可实现结构”展开时，必须持续守住哪些约束，防止本次设计回滑去重写需求、架构，或过早掉进详细设计与运维实施层。

本章不重新定义上游需求与架构约束，而是把这些已收稳前提转译成概要设计继续展开时必须守住的表达边界与结构边界。

#### 4.3.2 本章应回答的问题

```text
1. 当前概要设计必须继续守住哪些上游边界与非目标？
2. 哪些内容在概要设计层绝不能提前下沉到详细设计？
3. 哪些结构展开如果越界，会直接打穿已收稳的需求或架构主线？
4. 哪些约束会直接影响主要组成部分、接缝、对象与流程轮廓的表达深度？
5. 哪些约束如果不先写清，后续各章最容易串层或失真？
```

#### 4.3.3 本章不应回答的问题

```text
- 不重新定义需求约束与架构约束本身
- 不写技术选型理由
- 不写实现层限制清单
- 不写运维与部署细节约束
- 不把“详细设计以后再说”写成空泛提醒
```

#### 4.3.4 推荐表达形式

##### 主表达形式
1. 约束清单表

##### 辅表达形式（按需）
2. 一段约束边界说明短文

##### 图表分工
- 表负责说明：当前概要设计必须持续守住哪些约束、这些约束作用在哪些结构面上、当前要求是什么。
- 短文负责说明：为什么这些约束在概要设计层必须先钉住，而不是留给详细设计再补。

#### 4.3.5 约束清单表

##### 固定结构表

| 约束 | 作用范围 | 当前要求 |
|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 约束 | 本次概要设计必须继续守住的边界约束、层次约束或表达约束 | 不写技术产品、实现机制或运维规则 |
| 作用范围 | 该约束会直接作用于哪些主要结构面 | 不写泛化“整体都要遵守”式表述 |
| 当前要求 | 当前概要设计层必须满足的约束口径 | 不写实施步骤、落地动作或详细设计细节 |

#### 4.3.6 写法规则

##### 约束的类型
本章里的约束优先覆盖下面几类：

- 上游承接约束
- 层次边界约束
- 结构表达约束
- 边界外能力约束

##### 约束的粒度
约束应写成：

```text
概要设计层必须持续守住的表达边界或结构边界
```

优先写：
- 不重写什么
- 不提前展开什么
- 不混入什么
- 当前必须保持什么轮廓深度

不应写：
- 框架限制
- 性能参数
- 表结构约束
- API 细节
- 部署脚本要求

##### 约束边界说明短文
短文必须回答：

```text
1. 为什么这些约束必须在概要设计层先被写清
2. 为什么它们不能等到详细设计再补
3. 这些约束在保护哪种层次边界
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做层次边界说明
- 不提前进入后续章节正文
```

#### 4.3.7 完成标准

- 已明确概要设计层必须继续守住哪些约束
- 已明确这些约束分别作用于哪些结构面
- 已明确当前概要设计层应停在哪个表达深度
- 没有把约束写成技术实现限制或运维清单
- 没有用“以后再说”替代真正的边界约束

#### 4.3.8 正反例

**正确示例（通用）：**

| 约束 | 作用范围 | 当前要求 |
|---|---|---|
| 不重写需求目标与架构边界 | 本次设计目标、组成部分划分、职责边界 | 概要设计只承接已收稳需求与架构结论，不重新定义上游边界 |
| 不提前进入详细设计层 | 接缝轮廓、对象轮廓、流程轮廓 | 当前只写轮廓，不写字段、函数、DDL、时序细节 |
| 不把边界外能力混入本仓主要组成部分 | 主要组成部分概览、各部分职责与边界 | 与本仓职责边界不一致的能力不得作为正式组成部分进入概要设计主链 |
| 不把局部实现结构误写成正式部分 | 组成部分划分、对象轮廓 | 代码目录、类、函数、临时辅助结构不应升级为概要设计主语 |

**约束边界说明短文示例：**

```text
概要设计是在已收稳的需求与架构边界下继续向可实现结构展开，因此必须先守住上游承接边界和下游详细设计边界。若这些约束不先写清，后续组成部分、接缝、对象与流程轮廓就会继续在需求、架构与详细设计之间串层漂移。
```

**错误示例 A：把约束写成技术选型**

```text
约束：
- 使用 PostgreSQL
- 使用 Redis
- 使用 gRPC
```

错误原因：
```text
这些是架构设计或技术选型层判断，不是概要设计层必须持续守住的表达边界约束。
```

**错误示例 B：把约束写成实现限制**

```text
约束：
- 接口必须返回 JSON
- 数据表必须建索引
- 所有函数必须幂等
```

错误原因：
```text
这些已经下沉到协议、数据库或实现层，不属于概要设计阶段的结构约束。
```

**错误示例 C：把约束写成空泛提醒**

```text
约束：
- 不要写得太细
- 不要太复杂
- 先简单一点
```

错误原因：
```text
这类表述没有说明具体保护什么边界，也没有可执行的层次判断力。
```

#### 4.3.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 当前概要设计不能重新去定义 identity 的“身份真相仓”边界
- 不能把架构层已经定好的边界、传播方式、数据归属原则重新展开一遍
- 也不能提前把字段、函数、DDL 或实现链路拉进概要设计

它的作用，是保证后续 identity 的组成部分、职责、接缝、对象与流程轮廓都停留在正确层次上。

### 4.4 主要组成部分概览

#### 4.4.1 本章目标

说明当前系统在概要设计层应被划分为哪些主要组成部分、这些部分为什么需要被单独识别出来，以及它们共同如何构成一个可实现的整体轮廓。

#### 4.4.2 本章应回答的问题

```text
1. 当前概要设计层面，本仓应被划分为哪些主要组成部分？
2. 为什么这些部分需要被单独识别，而不是混成一体？
3. 哪些划分是在承接职责边界，哪些划分是在承接主要接缝或主要数据边界？
4. 哪些看起来像“部分”，但其实只是详细设计层实现，不应进入本章？
5. 哪些内容属于边界外能力，因此即使相关，也不应被纳入本仓主要组成部分？
```

#### 4.4.3 本章不应回答的问题

```text
- 不展开各部分详细职责
- 不展开部分之间的协作接缝
- 不展开对象字段或数据库结构
- 不把系统上下文对象、外部仓、角色或协议对象直接当成本仓内部组成部分
- 不把代码目录、类、函数或实现模块写成本章主语
```

#### 4.4.4 推荐表达形式

##### 主表达形式
1. 主要组成部分概览表

##### 辅表达形式（按需）
2. 极简组成关系示意图

##### 图表分工
- 表负责说明：有哪些主要组成部分、各自的一句话定义、以及为什么独立存在。
- 图只在必要时辅助表达部分之间的大体结构感，不承担职责、接缝和流程细节。

#### 4.4.5 主要组成部分概览表

##### 固定结构表

| 组成部分 | 一句话定义 | 划分依据 |
|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 组成部分 | 概要设计层的正式主要部分名称 | 不写代码目录、类、函数、实现模块名 |
| 一句话定义 | 该部分最短定义，说明它在整体中的存在意义 | 不写详细职责清单或流程细节 |
| 划分依据 | 为什么它应被单独识别出来 | 不写实现方便、团队习惯或随意拆分理由 |

#### 4.4.6 写法规则

##### 组成部分的粒度
组成部分应写成：

```text
概要设计层可独立识别、可单独承接职责与接缝的正式部分
```

优先写：
- 稳定的主要结构单元
- 未来在详细设计中会继续向下展开的正式部分
- 与职责边界、接缝轮廓或关键对象轮廓直接相关的部分

不应写：
- 代码目录
- 类 / 结构体
- 函数
- 中间临时对象
- 单纯为实现方便临时拆出来的模块

##### 一句话定义的写法
一句话定义必须回答：

```text
它在整体里是干什么的
```

不要求解释全部职责，只要求建立：
- 部分存在感
- 结构独立性
- 非详细设计层表达

##### 划分依据的写法
划分依据优先回答：

```text
为什么这个部分必须单独存在
```

可以来自：
- 职责边界
- 关键接缝
- 关键对象轮廓
- 主要流程轮廓需要

不应写成：
- 因为代码好写
- 因为模块多一点更灵活
- 因为团队习惯

#### 4.4.7 完成标准

- 已明确本仓在概要设计层应被划分为哪些主要组成部分
- 每个组成部分都有一句话定义
- 每个组成部分都有清晰划分依据
- 没有把外部对象、代码结构或详细设计对象误写成主要组成部分
- 读者已经能建立系统“主要部分”的第一层结构感

#### 4.4.8 正反例

**正确示例（通用）：**

| 组成部分 | 一句话定义 | 划分依据 |
|---|---|---|
| 正式输入承接部分 | 承接系统正式输入并将其导入内部结构 | 该部分直接对应外部输入边界，若不单独识别，后续接缝与职责会混入核心部分 |
| 核心处理部分 | 承担系统核心处理与核心状态变化组织 | 该部分需要作为后续对象轮廓和流程轮廓的主要展开中心 |
| 结果承接 / 对外供给部分 | 承接对外消费、只读供给或结果输出 | 该部分与核心处理部分的边界必须独立，否则外部消费会反向绑定核心结构 |

**错误示例 A：写成代码目录**

```text
api/
service/
repo/
model/
```

错误原因：
```text
这已经掉进代码组织层，不是概要设计层的主要组成部分。
```

**错误示例 B：写成系统上下文对象**

```text
用户端
外部系统
数据库
消息队列
```

错误原因：
```text
这些对象属于上下文对象、基础设施或外部边界，不是本仓内部主要组成部分本身。
```

**错误示例 C：写成实现模块或函数集合**

```text
创建对象模块
校验模块
发送消息模块
更新数据库模块
```

错误原因：
```text
这类拆法过于贴近执行步骤和实现动作，失去了概要设计层的稳定结构主语。
```

#### 4.4.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 当前概要设计层面，identity 不应只是一个“身份真相仓”的抽象词
- 而应进一步展开为若干主要组成部分
- 这些部分是后续职责、接缝、对象与流程轮廓继续展开的稳定主语

它不是在写 identity 的代码模块，也不是在重画架构边界，而是在建立“概要设计层的正式部分骨架”。

### 4.5 各部分职责与边界

#### 4.5.1 本章目标

在已划分出主要组成部分的前提下，明确每个部分分别承担什么职责、不承担什么职责，以及它们之间通过什么边界彼此分开，从而防止概要设计继续发散成重复架构边界或过早滑入详细设计。

#### 4.5.2 本章应回答的问题

```text
1. 每个主要组成部分分别承担什么职责？
2. 每个主要组成部分明确不承担什么职责？
3. 哪些内容虽然相关，但必须由相邻部分或边界外能力承担？
4. 各部分之间靠什么边界彼此分开？
5. 哪些职责如果不写清，后续最容易让概要设计滑进实现层或让不同部分串线？
```

#### 4.5.3 本章不应回答的问题

```text
- 不重写本仓整体职责边界
- 不展开各部分之间的关键接缝细节
- 不展开字段、函数、表结构或实现流程
- 不把外部对象、系统上下文边界或架构层职责边界混写成部分内部职责
- 不把“怎么实现”写成“是什么职责”
```

#### 4.5.4 推荐表达形式

##### 主表达形式
1. 各部分职责与边界表

##### 辅表达形式（按需）
2. 部分边界说明短文

##### 图表分工
- 表负责说明：每个部分承担什么、不承担什么，以及它与相邻部分如何分界。
- 短文负责解释：为什么这些边界必须在概要设计层先钉住，而不能留给详细设计再补。

#### 4.5.5 各部分职责与边界表

##### 固定结构表

| 组成部分 | 承担什么 | 不承担什么 | 边界说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 组成部分 | 已在 4.4 收稳的正式主要组成部分 | 不写代码目录、类、函数或外部对象 |
| 承担什么 | 该部分在概要设计层承担的正式职责 | 不写实现步骤、接口细节或字段级对象定义 |
| 不承担什么 | 与相邻部分或边界外能力明确切开的非职责项 | 不写含糊“其他内容”类表述 |
| 边界说明 | 该部分与相邻部分彼此分开的依据 | 不写系统上下文重述或大段架构解释 |

#### 4.5.6 写法规则

##### 职责的粒度
职责应写成：

```text
概要设计层正式部分在整体中承担的职责轮廓
```

优先写：
- 该部分负责承接什么
- 该部分不负责什么
- 它为什么不能和相邻部分混层

不应写：
- 函数职责
- 表结构职责
- 接口调用细节
- 中间状态处理细节

##### 边界说明的写法
边界说明优先回答：

```text
为什么这个部分和相邻部分必须分开
```

可以来自：
- 职责边界
- 主要接缝
- 关键对象轮廓
- 主要流程轮廓

不应写成：
- 因为代码拆分方便
- 因为实现上这样更顺手
- 因为习惯这样分层

##### 部分边界说明短文
短文必须回答：

```text
1. 为什么这些部分边界必须在概要设计层先被明确
2. 为什么它们不能等到详细设计再自然浮现
3. 如果边界不清，会导致什么层次串线
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做部分边界说明
- 不提前进入接缝细节或流程细节
```

#### 4.5.7 完成标准

- 已明确每个主要组成部分承担什么职责
- 已明确每个主要组成部分不承担什么职责
- 已说明各部分之间为什么必须分开
- 没有把本仓整体职责边界、系统上下文对象或实现细节混写进本章
- 读者已经能理解各主要部分之间的职责切面

#### 4.5.8 正反例

**正确示例（通用）：**

| 组成部分 | 承担什么 | 不承担什么 | 边界说明 |
|---|---|---|---|
| 正式输入承接部分 | 承接正式输入并把输入导入内部结构 | 不直接承担核心处理与核心状态演化 | 若输入承接与核心处理不分开，外部输入会反向统治内部结构 |
| 核心处理部分 | 承担核心状态变化与核心处理组织 | 不直接作为对外消费面暴露 | 若核心处理直接承担外部消费，读写与演进边界会混层 |
| 结果承接 / 对外供给部分 | 承接对外消费、只读供给或正式结果输出 | 不承担核心状态生成与内部主处理 | 若结果供给和核心处理不分开，下游会直接绑定内部真相结构 |

**错误示例 A：写成实现职责**

```text
service 负责校验，repo 负责存储，handler 负责返回。
```

错误原因：
```text
这已经掉进实现层，不是概要设计层的部分职责与边界表达。
```

**错误示例 B：写成外部边界职责**

```text
用户端负责输入，外部系统负责回调，数据库负责保存。
```

错误原因：
```text
这里混入了外部对象和基础设施对象，不是在说明本仓内部主要部分的职责边界。
```

**错误示例 C：只写“承担什么”，不写“不承担什么”**

```text
核心处理部分负责状态处理。
```

错误原因：
```text
缺少非职责约束，后续最容易导致边界膨胀和部分串线。
```

#### 4.5.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- identity 的主要部分分别承担什么职责
- 哪些职责不能混在一起
- 为什么身份真相相关处理、对外消费承接和输入承接必须保持边界

它不是在写 identity 的代码分层，也不是在重画架构边界，而是在把“主要部分之间如何分责”讲清楚。

### 4.6 关键接缝与接口轮廓

#### 4.6.1 本章目标

在已明确主要组成部分及其职责边界的前提下，收稳这些部分之间通过哪些关键接缝协作、接口轮廓应表达什么层次，以及哪些输入输出已经足以在概要设计层被正式点名。

#### 4.6.2 本章应回答的问题

```text
1. 主要组成部分之间通过哪些关键接缝协作？
2. 哪些接缝在概要设计层已经足以被正式点名？
3. 这些接缝分别在承接什么输入或输出？
4. 哪些看起来像“接口”，但其实已经掉到协议或详细设计层，不应进入本章？
5. 哪些接缝如果不先讲清，后续最容易导致部分之间串线？
```

#### 4.6.3 本章不应回答的问题

```text
- 不写 API 路径
- 不写协议 schema
```

```text
3. 哪些失败不能留到详细设计才发现？
4. 异常与边界场景在概要设计层需要讲到什么程度才足够？
5. 哪些内容仍属于详细设计的异常处理细节，不应在本章展开？
```

#### 4.9.3 本章不应回答的问题

```text
- 不展开完整异常处理机制
- 不写补偿脚本
- 不写恢复流程细节
- 不写错误码、重试参数、异常分支实现细节
- 不把 4.10 设计风险与待确认事项里的未关闭问题全部提前写进本章
- 不把异常与边界场景轮廓写成完整故障手册
```

#### 4.9.4 推荐表达形式

##### 主表达形式
1. 异常与边界场景轮廓表

##### 辅表达形式（按需）
2. 极简异常影响示意图
3. 一段异常轮廓说明短文

##### 图表分工
- 表负责说明：哪些异常与边界场景必须被点名、它们影响哪些部分协作关系、当前应理解到什么轮廓程度。
- 图只在必要时辅助表达异常场景对主流程的大体影响，不承担恢复与补偿细节。
- 短文负责解释为什么这些异常场景必须在概要设计层先出现，而不能完全留给详细设计。

#### 4.9.5 异常与边界场景轮廓表

##### 固定结构表

| 异常 / 边界场景 | 影响哪些部分 / 流程 | 当前轮廓口径 | 说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 异常 / 边界场景 | 概要设计层必须先点名的关键异常路径或边界场景 | 不写错误码、重试参数、脚本名或恢复步骤 |
| 影响哪些部分 / 流程 | 该场景会改写哪些部分协作关系或主流程理解 | 不写详细时序、协议交互或实现顺序 |
| 当前轮廓口径 | 在概要设计层应理解到什么程度 | 不写完整异常处理机制或补偿设计 |
| 说明 | 为什么该场景值得在概要设计层被正式点名 | 不写运维手册或大段故障分析 |

#### 4.9.6 写法规则

##### 场景的粒度
异常与边界场景应写成：

```text
会影响主要流程理解、部分协作关系或边界承接口径的关键异常轮廓
```

优先写：
- 输入边界异常轮廓
- 核心处理未形成结果的轮廓
- 只读 / 对外供给未成立的边界轮廓
- 跨边界传播未收口的场景轮廓

不应写：
- 详细错误码
- 技术重试细节
- 补偿步骤
- 恢复脚本
- 运维处置动作

##### 当前轮廓口径的写法
当前轮廓口径必须回答：

```text
在概要设计层，当前只需要把这类异常理解到什么程度
```

优先写：
- 必须知道它会影响哪类协作关系
- 必须知道它会让主流程在哪一层断开
- 必须知道它当前不能被伪装成已完成

不应写：
- 如何重试
- 如何补偿
- 如何恢复
- 谁来处理

##### 异常轮廓说明短文
短文必须回答：

```text
1. 为什么这些异常与边界场景必须在概要设计层先点名
2. 为什么它们不能完全等到详细设计再出现
3. 如果当前不说明，会导致哪些流程和部分边界失真
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做异常轮廓层次说明
- 不提前进入恢复机制与补偿脚本
```

#### 4.9.7 完成标准

- 已明确哪些关键异常路径与边界场景必须在概要设计层先点名
- 已说明这些场景会影响哪些部分协作关系或主流程理解
- 已明确这些场景当前只需理解到什么轮廓程度
- 没有把异常轮廓写成详细处理机制、补偿脚本或运维流程
- 读者已经知道哪些失败不能在概要设计层被假装忽略

#### 4.9.8 正反例

**正确示例（通用）：**

| 异常 / 边界场景 | 影响哪些部分 / 流程 | 当前轮廓口径 | 说明 |
|---|---|---|---|
| 正式输入未形成有效承接 | 正式输入承接部分 ↔ 核心处理部分 | 当前必须点名“输入未进入主线”这一类异常轮廓 | 若不先说明，主流程看起来会被错误理解为总能顺利进入内部结构 |
| 核心处理未形成正式结果 | 核心处理部分 ↔ 结果承接 / 对外供给部分 | 当前必须点名“结果未形成、不能伪装为已完成” | 该场景直接影响主流程是否真正闭环 |
| 对外供给未成立或传播未收口 | 结果承接部分 ↔ 外部消费或边界传播部分 | 当前必须点名“外部消费 / 传播未成立”的边界轮廓 | 若不点名，后续会把对外供给误看成天然总成立 |

**错误示例 A：写成错误码清单**

```text
E1001
E1002
E1003
```

错误原因：
```text
这是详细设计或协议层内容，不是概要设计层的异常与边界场景轮廓。
```

**错误示例 B：写成恢复脚本说明**

```text
失败后执行重试脚本，连续三次失败后人工回放。
```

错误原因：
```text
这是恢复与运维实施细节，不属于概要设计层轮廓表达。
```

**错误示例 C：只写“异常需要处理”**

```text
异常情况需要进一步处理。
```

错误原因：
```text
没有说明异常场景影响什么，也没有说明当前应理解到什么轮廓程度，无法支撑主流程理解。
```

#### 4.9.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 哪些 identity 相关异常或边界场景必须在概要设计层被先点名
- 它们会如何影响主要部分之间的协作关系
- 哪些失败当前绝不能被伪装成主流程已经自然成立

它不是在写 identity 的错误码、重试脚本或恢复方案，而是在建立“异常轮廓也会影响结构理解”的前提。

### 4.10 设计风险与待确认事项

#### 4.10.1 本章目标

在主要结构、接缝、对象、流程与异常轮廓已收稳的前提下，显式收纳当前概要设计层尚未闭环的设计问题，区分哪些已构成设计风险、哪些仍待确认，并说明它们会如何影响是否进入详细设计。

#### 4.10.2 本章应回答的问题

```text
1. 当前概要设计层已经明确构成风险、但尚未闭环的问题有哪些？
2. 当前还有哪些问题尚未形成定论，只能作为待确认事项挂起？
3. 这些未闭环项分别会影响哪些主要部分、接缝、对象或流程判断？
4. 哪些问题若不先收纳，后续详细设计会被误导？
5. 哪些内容只是任务或优化项，不应被包装成设计风险或待确认事项？
```

#### 4.10.3 本章不应回答的问题

```text
- 不写项目 backlog
- 不写 TODO 清单
- 不写具体实施方案
- 不写空泛风险页
- 不重写已定结论
- 不把局部实现问题提升成设计风险或待确认事项
- 不写“假挂起”表述
```

#### 4.10.4 推荐表达形式

##### 主表达形式
1. 设计风险表
2. 设计待确认事项表

##### 辅表达形式（按需）
3. 当前设计层处理口径说明短文

##### 图表分工
- 风险表负责收纳已经识别但尚未关闭、且会影响概要设计主线判断的问题。
- 待确认事项表负责收纳尚未形成定论、仍需进一步确认且会影响是否进入详细设计的问题。
- 短文负责解释为什么某些问题当前被视为设计风险、而另一些问题当前只能挂起为待确认事项，不重写两张表。

#### 4.10.5 设计风险与待确认事项判定规则（正式定稿）

- 设计风险：已经识别出会影响概要设计主线成立、主要部分协作、关键接缝、关键对象或主要流程理解的问题，但当前还没有被关闭。
- 设计待确认事项：尚未形成确定结论、仍需进一步判断或前置澄清的问题；它可能影响概要设计继续成立，但当前还不能被写成已知风险。

只有那些仍未闭环，并且会影响概要设计主线判断的内容，才配进入本章。普通 TODO、任务、愿望、局部优化项和已定结论都不应进入本章。

#### 4.10.6 设计风险表

##### 固定结构表

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 风险项 | 已识别出来、尚未关闭、并会影响概要设计主线判断的正式设计风险项 | 不写 TODO 事项、项目任务名、功能愿望或解决动作 |
| 影响范围 | 该风险会影响哪条概要设计主线、哪类组成部分、哪类接缝、哪类对象或哪类流程理解 | 不写空泛“整体受影响”式描述 |
| 当前处理口径 | 风险尚未关闭时的设计层约束、暂存或保守承接方式 | 不写最终修复方案、实施步骤、负责人、时间安排、处置动作或任务拆分 |
| 是否阻塞 | 该风险对进入详细设计或继续收稳概要设计主线的正式判断 | 不写模糊观察式状态词 |
| 说明 | 必要的去歧义判断，解释该问题为什么已经属于设计风险、为什么当前处理口径合理 | 不写解决方案或实施分析 |

#### 4.10.7 设计待确认事项表

##### 固定结构表

| 待确认事项 | 影响范围 | 缺失确认 | 当前挂起口径 | 说明 |
|---|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 待确认事项 | 尚未形成确定结论、仍需进一步确认且会影响概要设计主线判断的问题项 | 不写普通疑问、功能愿望、实施待办或优化事项 |
| 影响范围 | 该事项若定论变化，将影响哪条概要设计主线、哪类组成部分、哪类接缝、哪类对象或哪类流程理解 | 不写泛化的“整体相关”类表述 |
| 缺失确认 | 当前还缺什么确认，因此该事项不能被定论 | 不写“还没想好”“后续再看”“继续讨论”等空泛表达 |
| 当前挂起口径 | 尚未定论前的保守挂起方式 | 不写临时方案、感觉性处理、预支结论、处置动作或任务拆分 |
| 说明 | 必要的去歧义判断，解释该事项为什么仍属于待确认事项、为什么当前还不能定论，以及为什么当前挂起口径合理 | 不写方案推演或实施建议 |

#### 4.10.8 当前设计层处理口径说明（按需）

当前设计层处理口径说明短文用于解释：
- 为什么某些问题当前被视为设计风险，而不是待确认事项
- 为什么某些问题当前只能挂起，而不能装成已知结论
- 为什么这里不继续写最终解决方案

约束：
```text
- 共 1 段
- 3~5 句
- 不重写两张表
- 不滑入实施方案
```

#### 4.10.9 完成标准

- 已明确区分设计风险与设计待确认事项
- 已写清每项风险的影响范围、当前处理口径与阻塞性
- 已写清每项待确认事项的影响范围、缺失确认与当前挂起口径
- 已说明为什么这些项配进入本章
- 没有滑入任务层、方案层或已定结论回退层
- 没有使用空泛风险词或假挂起表述

#### 4.10.10 正反例

**正确示例 A：设计风险表（通用）**

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|
| 核心部分边界尚未完全闭环的风险 | 核心部分边界、关键接缝主线 | 当前按更保守边界收口，不提升为正式主结构 | 有条件阻塞 | 该问题已明确会影响概要设计主线成立，因此属于正式设计风险，而不是普通待办。 |
| 关键接缝表达尚未完全收稳的风险 | 接缝轮廓、主要流程理解 | 当前只允许保守接缝口径，不伪装为已稳定闭环 | 不阻塞 | 该问题已被识别，但在当前阶段仍可带约束推进。 |
| 只读承接结果轮廓可能失真的风险 | 对外供给面、只读对象轮廓、主要流程末端 | 当前保留只读承接口径，不回填为核心结构定论 | 不阻塞 | 风险已经明确，当前处理重点是约束其影响，不是假装已经关闭。 |

**正确示例 B：设计待确认事项表（通用）**

| 待确认事项 | 影响范围 | 缺失确认 | 当前挂起口径 | 说明 |
|---|---|---|---|---|
| 某关键部分边界的最终裁决尚未形成 | 部分边界主线、后续职责说明 | 缺最终边界结论确认 | 当前不回填为定论，只作结构背景保留 | 该事项尚未形成定论，因此不能升级为正式设计风险，也不能伪装成已知结论。 |
| 某关键接缝是否进入主线尚待确认 | 接缝主线、后续流程轮廓判断 | 缺主线范围裁决 | 当前不纳入主线，只挂起为未决项 | 该事项会影响后续章节成立，但当前仍缺关键判断依据。 |
| 某异常场景是否足以上升到概要设计层尚待确认 | 异常轮廓主线、进入详细设计条件 | 缺边界严重性确认 | 当前按更保守边界处理，不提前写入正式异常轮廓 | 该事项当前不能被写成已知风险，但必须显式挂起以防误导主线。 |

**错误示例 A：写成任务 backlog**

```text
补对象轮廓
补接缝
补流程
补异常
```

错误原因：
```text
这是任务清单，不是设计层未闭环问题判断，没有影响范围、当前口径或阻塞性判断。
```

**错误示例 B：写成 TODO / 优化清单**

```text
后续优化流程
后续增强对象模型
后续补异常处理
```

错误原因：
```text
只有愿望和方向，没有说明是不是风险、缺什么确认以及当前处理口径，因此不配直接进入本章。
```

**错误示例 C：写成空泛风险页**

```text
存在设计风险
存在对象风险
存在流程风险
```

错误原因：
```text
没有影响范围、当前处理口径、阻塞性，也没有说明为什么它是正式设计风险，这类写法没有规范判断力。
```

**错误示例 D：写成已定结论重复页**

```text
主要组成部分必须清晰，接缝必须稳定，流程必须完整。
```

错误原因：
```text
这些可能是前文已收稳结论，不是新的设计风险或待确认事项，这会让本章变成前文回退区。
```

**错误示例 E：把待确认事项写成已知风险**

```text
某关键接缝是否进入主线尚未确认，因此这是当前最大的正式设计风险。
```

错误原因：
```text
如果“是否进入主线”还没确认，那它更应该先写成待确认事项，不能提前升级成已知设计风险。
```

**错误示例 F：只有“挂起”没有“缺失确认”**

```text
该事项当前挂起，后续再看。
```

错误原因：
```text
没有说明缺什么确认、影响范围以及为什么只能挂起，这样的待确认事项写法太空，不能进入正式规范。
```

#### 4.10.11 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 哪些 identity 相关问题已经明确会影响主要部分、接缝、对象、流程或异常轮廓，因此属于设计风险
- 哪些问题仍未形成稳定结论，只能挂起等待确认
- 当前如何保守约束这些问题，而不让它们污染已收稳的概要设计主线

它不是在写 identity 的整改清单或实施计划，而是在收稳“哪些问题还没闭环”。

```text
- 不重写需求追溯矩阵
- 不重写 ADR 索引
- 不写资料仓 / 链接大全
- 不写主观推荐阅读清单
- 不新增判断
- 不用“仅供参考”掩盖弱材料
```

#### 4.11.4 推荐表达形式

##### 主表达形式
1. 参考材料清单表

##### 辅表达形式（按需）
2. 参考范围说明短文

##### 图表分工
- 主表负责稳定、克制、可导航地列出哪些材料构成当前概要设计文档的正式参考，并说明它们各自属于什么类型、为什么值得被长期保留。
- 短文只用于收束参考范围，解释为什么某些材料进入本章、为什么某些草稿或临时资料不进入本章，以及为什么这里不重复上游承接、追溯关系和决策索引的职责。

#### 4.11.5 参考材料清单表

##### 固定结构表

| 参考材料 | 材料类别 | 用途 / 参考价值 | 说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 参考材料 | 当前概要设计文档正式保留的参考材料名称 | 不写临时讨论稿、含糊来源描述或仅有路径而无材料语义的表述 |
| 材料类别 | 该材料所属的稳定、可复用类别 | 不写过弱的泛化分类词，也不临时创造过细类别 |
| 用途 / 参考价值 | 该材料对当前概要设计文档成立的正式参考意义 | 不写“仅供参考”“看过”“备用资料”之类弱表述 |
| 说明 | 必要的去歧义判断，解释该材料为什么配进入本章、为什么值得长期保留，以及为什么它不是草稿、临时笔记或可省略资料 | 不写来源关系分析、追溯关系说明或 ADR 摘要 |

#### 4.11.6 参考范围说明（按需）

参考范围说明短文用于解释：
- 为什么某些材料进入本章
- 为什么某些草稿、临时笔记或一次性讨论材料不进入本章
- 为什么这里不重复上游承接声明、追溯关系和 ADR 索引职责
- 为什么参考章节应保持克制，而不是变成资料仓或导读页

约束：
```text
- 共 1 段
- 3~5 句
- 不重写主表
- 不滑入主观总结或来源关系分析
```

#### 4.11.7 完成标准

- 已明确哪些材料构成当前概要设计文档的正式参考
- 已说明每份材料属于什么类别
- 已说明每份材料为什么值得被长期保留
- 已排除草稿、临时材料和与前文章节职责重叠的内容
- 清单可导航但不过载
- 没有滑入资料仓、导读页或附录式杂项清单

#### 4.11.8 正反例

**正确示例（通用）：**

| 参考材料 | 材料类别 | 用途 / 参考价值 | 说明 |
|---|---|---|---|
| 当前仓对应的上游需求文档 | 上游需求材料 | 用于理解本次概要设计最终承接的需求边界、能力范围与约束来源 | 该材料不是来源声明的重复，而是后续读者理解本次概要设计时仍需回看的正式上游材料。 |
| 当前仓对应的架构设计文档 | 上游架构材料 | 用于理解当前概要设计所承接的系统边界、主要结构约束与交互前提 | 该材料长期影响主要组成部分、接缝、对象与流程的展开，因此值得被稳定保留为正式参考。 |
| 关键 ADR 或标准性材料 | ADR / 标准材料 | 用于理解本次概要设计所依赖的关键决策依据或方法边界 | 该类材料只有在已经对当前主线产生稳定约束时才配进入本章。 |

**错误示例 A：写成链接清单大全**

```text
- xxx.md
- yyy.md
- zzz.md
- aaa.md
```

错误原因：
```text
这只是链接堆放，没有材料类别、用途说明和筛选门槛，因此会让本章退化成文件堆放区。
```

**错误示例 B：写成来源声明第二版**

```text
本文承接自需求文档、架构文档与相关标准。
```

错误原因：
```text
这只是来源声明，没有列出正式参考材料，也没有说明为什么这些材料值得长期保留，职责已经与 4.1 重叠。
```

**错误示例 C：写成资料仓**

```text
草稿文档
临时笔记
legacy 文档
会议纪要
历史方案
```

错误原因：
```text
没有正式筛选、没有稳定性判断，也没有“为什么现在还值得保留”的理由，这会让本章失去克制性。
```

**错误示例 D：写成阅读指南**

```text
建议新人先看需求文档，再看架构设计，再看 ADR。
```

错误原因：
```text
这是导读页，不是参考材料清单，本章不应承担阅读顺序推荐职责。
```

**错误示例 E：只写“仅供参考”**

```text
某规范文档，仅供参考。
```

错误原因：
```text
没有说明为什么值得保留，“仅供参考”过于弱，不能作为正式入章理由，会让本章变成礼貌性附录。
```

#### 4.11.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者筛出哪些上游需求材料、架构材料、关键 ADR 或规范材料，是真正支撑 identity 概要设计主线理解的正式参考。它不是在重复 identity 的来源声明、追溯关系或决策索引，而是在收口“后续读者还应回看哪些正式材料”。

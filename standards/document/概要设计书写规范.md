# 概要设计书写规范

> 概要设计回答 **“在已收稳的需求与架构边界下，系统如何被组织成可实现的主要结构”**。

## 一、概要设计的目标

概要设计要解决的问题包括：

1. 在已收稳的需求与架构边界下，系统由哪些主要部分构成
2. 这些主要部分各自承担什么职责，通过哪些关键接缝协作
3. 这些主要部分如何落到代码主体框架、接口骨架、关键处理流与状态机骨架
4. 哪些关键对象、正式接口、关键流程与状态流转已经足以支撑进入详细设计
5. 哪些主要部分、接缝、运行形态或外部适配会受到配置影响，并应交给详细设计继续收口配置实现契约

概要设计不回答：

```text
重新定义需求目标、用户故事、验收标准
重新定义系统上下文、子域划分、方案取舍或架构级技术选型
提前展开完整字段模型、函数实现、DDL、详细时序、部署参数和运维细节
```

## 二、概要设计与上游 / 下游文档的边界

### 2.1 相对需求文档

概要设计承接已收稳的需求结论，但不再重写：

- 目标与非目标
- 用户故事
- 功能需求
- 验收标准

### 2.2 相对架构设计

概要设计承接已收稳的架构边界与约束，但不再重写：

- 系统上下文与边界
- 限界上下文与子域划分
- 数据所有权原则
- 关键技术选型
- 备选方案与取舍
- ADR 索引
- 需求追溯矩阵

### 2.3 相对详细设计

概要设计停在“可实现结构骨架”，不提前展开：

- 代码目录结构与文件路径
- 完整字段定义与字段类型全集
- 完整函数签名、函数实现与函数调用链
- DDL / 索引
- 协议 schema
- 部署与运维细节

但概要设计必须允许并鼓励点名以下内容：

- 正式对象名、聚合名、值对象名、投影名、事件记录名
- 正式 API / Command / Query / Event / Operations Job 名称
- 关键字段骨架，必须写明字段类型，但不写完整字段类型全集、数据库列定义和序列化 schema
- 成员函数 / 工厂函数骨架，参数必须写明类型名和参数名，但不写完整 Rust 签名、实现代码和调用链脚本
- 状态集合、状态含义和状态流转方向
- 重要函数数据流的结构骨架，但不写完整伪代码
- 配置影响轮廓，包括哪些主要部分可能受配置影响、哪些边界禁止配置化、哪些内容交给详细设计继续定义配置实现契约

### 2.4 术语与表达总规则

#### 核心主术语
概要设计线的核心主术语统一如下：

- `主要组成部分`：概要设计层的正式主要部分，不与架构线的系统边界 / 子域主语，也不与详细设计层的模块 / 类 / 函数主语混用。
- `关键接缝`：主要组成部分之间已足够稳定、需要在概要设计层正式点名的协作接缝，不写成协议细节或实现接口。
- `轮廓`：概要设计层对对象、流程、异常与边界场景的表达深度词，用于表示“已进入可实现结构层，但仍未下沉到详细设计”。

除非确有必要，不再并行使用 `主要组成部分`、`接缝`、`轮廓口径` 等与以上主术语近义但易造成跨章漂移的表达。

#### 图 / 表 / 短文总规则
概要设计线整体采用：

- 表为主
- 图按需
- 短文收束边界

其中：
- 表负责收稳主语、职责、边界、接缝、对象与流程轮廓，不退化成 checklist。
- 图只在纯文字与表格不足以建立结构感时才出现，不承载 API、事件、字段、函数、DDL、详细时序或运维参数。
- ASCII 图必须统一采用“明确图标题 + `text` 代码块 + 2~5 条关键说明”的结构，不允许各仓自行发明图风格。
- 短文只用于解释为什么某章这样切、为什么某些内容不该展开，以及如何理解例外，不承担新判断。

#### `identity` 辅助说明最小规则
`identity` 辅助说明只用于把通用规则映射到真实仓级语境：

- 不新增本章判断标准
- 不替代主规则
- 不充当实现示例
- 不形成第二套样板正文

如果某章的 `identity` 辅助说明只是复述正文，则应缩短到仅保留映射价值。

## 三、概要设计的章节主链

正式文档建议使用以下章节顺序：

```text
1. 与上游文档的关系声明
2. 本次设计目标与范围
3. 约束条件
4. 代码主体框架总览
5. 主要组成部分、职责与边界
6. 关键对象轮廓
7. API / 接口骨架
8. 关键处理流 / 重要函数数据流
9. 状态定义与状态流转
10. 异常与边界场景轮廓
11. 配置影响轮廓
12. 详细设计承接清单
13. 设计风险与待确认事项
14. 参考
```

### 3.1 新主链与旧主链的对应关系

| 新主链章节 | 旧主链对应内容 | 变化说明 |
|---|---|---|
| 代码主体框架总览 | 主要组成部分概览的一部分 | 新增为独立章节，要求把架构模块映射到代码主体骨架和实现分层视图 |
| 主要组成部分、职责与边界 | 主要组成部分概览 + 各部分职责与边界 | 合并表达，避免组成部分和职责边界分裂成两次重复讨论 |
| 关键对象轮廓 | 关键对象轮廓 | 保留，但允许写关键字段骨架与成员函数骨架 |
| API / 接口骨架 | 关键接缝与接口轮廓的一部分 | 新增为独立章节，要求按 Command / Query / Event / Operations 等类别输出正式接口骨架 |
| 关键处理流 / 重要函数数据流 | 主要流程轮廓 | 强化为可承接详细设计的处理流骨架，允许点名关键函数 / service / domain method 名称 |
| 状态定义与状态流转 | 关键对象 / 主要流程中的状态内容 | 新增为独立章节，避免状态机散落在对象和流程里 |
| 配置影响轮廓 | 原无独立章节 | 新增为轻量收口章节，只识别配置影响、禁止配置化边界和详细设计承接方向，不写配置项清单或 JSON |
| 详细设计承接清单 | 原无独立章节 | 新增为收口门禁，明确哪些主语已收稳、详细设计继续展开什么 |

旧版章节中的“关键接缝”不再作为独立正式章节保留，而应分散吸收到：
- `4. 代码主体框架总览` 的部分交互视图
- `5. 主要组成部分、职责与边界` 的边界说明
- `7. API / 接口骨架` 的正式接口分类
- `8. 关键处理流 / 重要函数数据流` 的流转说明

### 3.2 第 5 章与第 6 章的边界

第 5 章和第 6 章必须保持不同组织轴：

```text
第 5 章：按“主要组成部分”组织
  说明每个主要组成部分承担什么、不承担什么、包含哪些代码主体 / 模块、与其他部分如何接。

第 6 章：按“关键对象”组织
  说明每个关键对象的所属部分、对象类型、主要责任、关键字段骨架、成员函数骨架、工厂函数骨架和禁止事项。
```

因此：
- 第 5 章可以列出某个主要组成部分包含哪些代码主体 / 模块。
- 第 5 章不展开这些对象的字段骨架、成员函数骨架和工厂函数骨架。
- 第 6 章必须独立存在，不能作为第 5 章子节被吸收。
- 第 6 章可以通过“所属部分”字段回指第 5 章，但它的组织方式应以对象为主，而不是按组成部分重复嵌套。

### 3.3 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式概要设计时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/02_hld_step_05_components_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章概要设计结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的概要设计结论。

### 3.4 正式章节必须保留校准来源入口

整理正式概要设计时，每个正式章节开头必须回答：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~13。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/02_hld_step_05_components_boundary.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/02_hld_step_05_components_boundary.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解主要组成部分、职责与边界如何从架构边界收敛到可实现结构。
```

## 四、新增强骨架章节输出约束

> 本节定义新版概要设计主链中新增或强化章节的输出格式。
> 后续“章节级规范”若仍出现旧口径，以本节为新版主链的优先约束。

### 4.1 与上游文档的关系声明

#### 本章目标

说明当前概要设计承接哪些已收稳的需求、架构和全局设计结论，并明确本文继续向哪一层可实现结构展开。

#### 必须输出

1. 上游关系映射表
2. `本文不再回答` 清单
3. `本文必须回答` 清单

#### 上游关系映射表格式

| 来源文档 | 承接内容 | 本文继续展开什么 |
|---|---|---|

#### 表格写法约束

- 本章必须使用上游关系映射表。
- `来源文档` 必须写正式文档路径或稳定文档名，不写临时讨论描述。
- `承接内容` 只写已经收稳的需求、架构或全局设计结论。
- `本文继续展开什么` 必须写本概要设计继续下沉的结构方向。
- 表格不能写成上游文档摘要、目录复述或阅读记录。

#### 图示写法约束

- 本章禁止画图。
- 不画上游依赖图、系统上下文图或文档关系图，避免回滑到架构设计或文档索引。

#### `本文不再回答` 清单格式

```md
本文不再回答：
- <已由需求 / 架构 / 全局设计收稳的问题>
```

#### `本文必须回答` 清单格式

```md
本文必须回答：
- <本概要设计必须继续收稳的结构问题>
```

#### 允许写

- 上游已经收稳的边界、主语、模块、状态、依赖方向和非目标
- 本文继续展开到代码主体、对象、接口、处理流和状态机的方向

#### 禁止写

- 重写需求目标、用户故事或架构取舍
- 把上游文档摘要复制成正文
- 在本章提前展开对象字段、接口表和处理流

### 4.2 本次设计目标与范围

#### 本章目标

明确本次概要设计要收稳哪些结构、交付给详细设计什么输入，以及哪些内容明确不进入本轮概要设计。

#### 必须输出

1. 设计目标表
2. 非范围表

#### 设计目标表格式

| 目标 | 说明 | 交付给详细设计的结果 |
|---|---|---|

#### 非范围表格式

| 非范围 | 留给哪一层 |
|---|---|

#### 表格写法约束

- 本章必须使用设计目标表和非范围表。
- `目标` 必须写本轮概要设计要收稳的结构目标，不写功能需求项。
- `交付给详细设计的结果` 必须写详细设计可继续展开的对象、接口、流程、状态机或边界。
- `非范围` 必须写当前明确不进入概要设计的内容。
- `留给哪一层` 必须写明确层次，例如需求、架构、详细设计、实施计划、相邻仓或运维层。

#### 图示写法约束

- 本章禁止画图。
- 不画路线图、任务拆分图、功能范围图或项目计划图。

#### 允许写

- 本轮必须收稳的代码主体框架、对象骨架、接口骨架、关键处理流和状态机
- 每个目标交付给详细设计继续展开的内容
- 明确属于详细设计、实施计划、相邻仓或上游文档的非范围项

#### 禁止写

- 功能需求清单
- 任务拆分、开发排期和实施步骤
- 把非范围写成“后续优化”“以后再看”

### 4.3 约束条件

#### 本章目标

收稳会直接影响概要设计结构的硬约束，避免后续章节在对象、接口、流程和状态机上越界。

#### 必须输出

1. 约束条件表

#### 约束条件表格式

| 约束 | 说明 |
|---|---|

#### 表格写法约束

- 本章必须使用约束条件表。
- `约束` 必须写可影响后续结构判断的硬约束。
- `说明` 必须解释该约束保护什么边界，或会影响哪些对象、接口、处理流、状态机。
- 不写泛化工程口号、技术偏好、运维规则或数据库实现约束。

#### 图示写法约束

- 本章禁止画图。
- 约束关系如果复杂，也应在后续对应结构章节画图，不在本章画约束网络图。

#### 允许写

- 创建 / 查询 / 写入 / 状态传播等主线必须遵守的设计约束
- 数据归属、跨仓边界、状态边界、只读投影边界和安全边界
- 对后续对象、接口和处理流有直接影响的非功能约束

#### 禁止写

- 上游架构全文复述
- 与本仓概要设计无关的泛化工程原则
- 不能指导后续章节的口号式约束

### 4.4 代码主体框架总览

#### 本章目标

把架构设计中已经收稳的模块 / 边界，转译为后续详细设计可以继续展开的代码主体框架。

#### 必须输出

1. 架构模块到代码主体的映射图
2. 实现分层视图
3. 业务模块与实现分层的关系说明
4. 关键判断小节

#### 推荐格式

##### 架构模块到代码主体映射图

```text
<仓名 / 模块名>
│
├─ 1. <主要组成部分>
│   ├─ <正式入口 / 服务 / 对象骨架>
│   └─ <正式入口 / 服务 / 对象骨架>
│
├─ 2. <主要组成部分>
│   ├─ <Application Service / Domain Object>
│   └─ <Application Service / Domain Object>
│
└─ 3. <主要组成部分>
    ├─ <Projection / Outbox / Port>
    └─ <Projection / Outbox / Port>
```

##### 实现分层视图

#### 本章目标

点名详细设计必须继续承接的核心对象、聚合、值对象、投影、事件记录和上下文对象，并说明每个对象在概要设计层应被理解到什么程度。

#### 表格写法约束

- 本章必须按对象独立成节，不得只用一个对象总览表替代。
- 每个对象至少必须有基本信息表。
- 聚合、实体、值对象、投影、outbox record 等关键对象必须按需补关键字段表。
- 存在状态的对象必须补状态集合表。
- 存在行为的对象必须补成员函数表或工厂函数表。
- 每张表的每一行都必须解释作用，不能只列名称。
- 字段表必须使用 `字段 | 类型 | 作用`。
- 函数表中的函数参数必须使用 `TypeName param_name`。

#### 图示写法约束

- 本章默认不画图。
- 只有对象分布关系复杂、单靠表格无法看清对象属于哪些主要组成部分时，才允许补对象分布图。
- 对象分布图只能表达对象与主要组成部分之间的归属或引用关系。
- 对象分布图禁止表达字段结构、方法调用链、继承树、数据库 ER 图或完整类图。
- 如补对象分布图，必须遵守 `5.3.4 ASCII 图统一格式`。

如果某个对象没有独立状态集合、成员函数或工厂函数，可以省略对应小节，但必须能说明省略原因。

#### 允许写

- 关键字段名骨架
- 关键字段类型骨架
- 每个关键字段的作用
- 状态集合及每个状态的作用
- 成员函数 / 工厂函数名称骨架
- 成员函数 / 工厂函数的参数类型骨架，格式为 `TypeName param_name`
- 每个成员函数 / 工厂函数的作用
- 对象类型和职责
- 对象禁止事项

#### 禁止写

- 完整字段类型全集
- 序列化 schema
- 完整 Rust 函数签名，包括可见性、返回类型、泛型、生命周期、trait 约束和实现体
- 函数实现代码
- 数据库列定义
- 一次性局部变量或临时缓存结构

#### 输出约束

- 不应把所有对象合并成一个总览表作为主要输出。
- 对象总览可以作为辅助索引出现，但不能替代单对象小节。
- 关键字段表必须使用 `字段 / 类型 / 作用` 三列。
- 字段类型必须是概要设计层的类型名，例如 `GlobalMemberId`、`DisplayName`、`LifecycleValue`，不能只写字段名。
- 禁止只写 `global_member_id`；应写成 `global_member_id: GlobalMemberId`，并在表格中拆为字段和类型两列。
- 字段类型不展开到完整 Rust 字段声明、泛型细节、数据库列类型或序列化字段名。
- 成员函数、状态集合、工厂函数必须分别成表，不能压成同一行文本。
- 表中每一项都必须解释作用，不能只列名称。
- 成员函数和工厂函数不写完整 Rust 签名，但参数必须写成 `TypeName param_name`。
- 禁止只写裸参数名，例如 `activate(actor, reason)`；应写成 `activate(ActorContext actor, LifecycleReason reason)`。
- 无参数函数可以保留空参数列表，例如 `is_terminal()`。
- 返回类型只有在影响边界判断时才需要写入概要设计；通常留给详细设计。

#### 与第 5 章的关系

关键对象轮廓必须作为独立章节输出，不应被折叠进“主要组成部分、职责与边界”章节。

```text
第 5 章负责定位：
  核心身份处理部分包含 GlobalMember、GlobalMemberLifecycle、RoleCatalogEntry。

第 6 章负责定义：
  GlobalMember 是什么对象、承担什么责任、有哪些关键字段骨架和成员函数骨架。
```

这样做可以避免两个问题：
- 第 5 章过重，提前变成半个详细设计。
- 跨流程对象的横向关系被主要组成部分切碎。

### 4.3 约束条件

#### 4.3.1 本章目标

说明当前概要设计在继续向“可实现结构”展开时，必须持续守住哪些约束，防止本次设计回滑去重写需求、架构，或过早掉进详细设计与运维实施层。

本章不重新定义上游需求与架构约束，而是把这些已收稳前提转译成概要设计继续展开时必须守住的表达边界与结构边界。

#### 4.3.2 本章应回答的问题

```text
1. 当前概要设计必须继续守住哪些上游边界与非目标？
2. 哪些内容在概要设计层绝不能提前下沉到详细设计？
3. 哪些结构展开如果越界，会直接打穿已收稳的需求或架构主线？
4. 哪些约束会直接影响主要组成部分、接缝、对象与流程轮廓的表达深度？
5. 哪些约束如果不先写清，后续各章最容易串层或失真？
```

#### 4.3.3 本章不应回答的问题

```text
- 不重新定义需求约束与架构约束本身
- 不写技术选型理由
- 不写实现层限制清单
- 不写运维与部署细节约束
- 不把“详细设计以后再说”写成空泛提醒
```

##### 主表达形式
1. 约束清单表

##### 辅表达形式（按需）
2. 一段约束边界说明短文

- 短文负责说明：为什么这些约束在概要设计层必须先钉住，而不是留给详细设计再补。

##### 固定结构表

| 约束 | 作用范围 | 当前要求 |

#### 4.3.6 写法规则

##### 约束的类型
本章里的约束优先覆盖下面几类：

- 上游承接约束
- 层次边界约束
- 结构表达约束
- 边界外能力约束

##### 约束的粒度
约束应写成：

```text
概要设计层必须持续守住的表达边界或结构边界
```

优先写：
- 不重写什么
- 不提前展开什么
- 不混入什么
- 当前必须保持什么轮廓深度

不应写：
- 框架限制
- 性能参数
- 表结构约束
- API 细节
- 部署脚本要求

##### 约束边界说明短文
短文必须回答：

```text
1. 为什么这些约束必须在概要设计层先被写清

3. 这些约束在保护哪种层次边界
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做层次边界说明
- 不提前进入后续章节正文
```

#### 4.3.7 完成标准

- 已明确概要设计层必须继续守住哪些约束
- 已明确这些约束分别作用于哪些结构面

- 没有用“以后再说”替代真正的边界约束

#### 4.3.8 正反例

**正确示例（通用）：**

| 约束 | 作用范围 | 当前要求 |

错误原因：

```text
- 先简单一点
```

### 4.4 主要组成部分概览

#### 4.4.1 本章目标

说明当前系统在概要设计层应被划分为哪些主要组成部分、这些部分为什么需要被单独识别出来，以及它们共同如何构成一个可实现的整体轮廓。

#### 4.4.2 本章应回答的问题

```text
1. 当前概要设计层面，本仓应被划分为哪些主要组成部分？
2. 为什么这些部分需要被单独识别，而不是混成一体？
3. 哪些划分是在承接职责边界，哪些划分是在承接主要接缝或主要数据边界？
4. 哪些看起来像“部分”，但其实只是详细设计层实现，不应进入本章？
5. 哪些内容属于边界外能力，因此即使相关，也不应被纳入本仓主要组成部分？
```

#### 4.4.3 本章不应回答的问题

```text
- 不展开各部分详细职责
- 不展开部分之间的协作接缝
- 不展开对象字段或数据库结构
- 不把系统上下文对象、外部仓、角色或协议对象直接当成本仓内部组成部分
- 不把代码目录、类、函数或实现模块写成本章主语
```

#### 4.4.4 推荐表达形式

##### 主表达形式
1. 主要组成部分概览表

##### 辅表达形式（按需）
2. 极简组成关系示意图

##### 图表分工
- 表负责说明：有哪些主要组成部分、各自的一句话定义、以及为什么独立存在。
- 图只在必要时辅助表达部分之间的大体结构感，不承担职责、接缝和流程细节。

#### 4.4.5 主要组成部分概览表

##### 固定结构表

| 组成部分 | 一句话定义 | 划分依据 |
|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 组成部分 | 概要设计层的正式主要部分名称 | 不写代码目录、类、函数、实现模块名 |
| 一句话定义 | 该部分最短定义，说明它在整体中的存在意义 | 不写详细职责清单或流程细节 |
| 划分依据 | 为什么它应被单独识别出来 | 不写实现方便、团队习惯或随意拆分理由 |

#### 4.4.6 写法规则

##### 组成部分的粒度
组成部分应写成：

```text
概要设计层可独立识别、可单独承接职责与接缝的主要组成部分
```

优先写：
- 稳定的主要结构单元
- 未来在详细设计中会继续向下展开的主要组成部分
- 与职责边界、接缝轮廓或关键对象轮廓直接相关的部分

不应写：
- 代码目录
- 类 / 结构体
- 函数
- 中间临时对象
- 单纯为实现方便临时拆出来的模块

##### 一句话定义的写法
一句话定义必须回答：

```text
它在整体里是干什么的
```

不要求解释全部职责，只要求建立：
- 部分存在感
- 结构独立性
- 非详细设计层表达

##### 划分依据的写法
划分依据优先回答：

```text
为什么这个部分必须单独存在
```

可以来自：
- 职责边界
- 关键接缝
- 关键对象轮廓
- 主要流程轮廓需要

不应写成：
- 因为代码好写
- 因为模块多一点更灵活
- 因为团队习惯

#### 4.4.7 完成标准

- 已明确本仓在概要设计层应被划分为哪些主要组成部分
- 每个组成部分都有一句话定义
- 每个组成部分都有清晰划分依据
- 没有把外部对象、代码结构或详细设计对象误写成主要组成部分
- 读者已经能建立系统“主要部分”的第一层结构感

#### 4.4.8 正反例

**正确示例（通用）：**

| 组成部分 | 一句话定义 | 划分依据 |
|---|---|---|
| 正式输入承接部分 | 承接系统正式输入并将其导入内部结构 | 该部分直接对应外部输入边界，若不单独识别，后续接缝与职责会混入核心部分 |
| 核心处理部分 | 承担系统核心处理与核心状态变化组织 | 该部分需要作为后续对象轮廓和流程轮廓的主要展开中心 |
| 结果承接 / 对外供给部分 | 承接对外消费、只读供给或结果输出 | 该部分与核心处理部分的边界必须独立，否则外部消费会反向绑定核心结构 |

**错误示例 A：写成代码目录**

```text
api/
service/
repo/
model/
```

错误原因：
```text
这已经掉进代码组织层，不是概要设计层的主要组成部分。
```

**错误示例 B：写成系统上下文对象**

```text
用户端
外部系统
数据库
消息队列
```

错误原因：
```text
这些对象属于上下文对象、基础设施或外部边界，不是本仓内部主要组成部分本身。
```

**错误示例 C：写成实现模块或函数集合**

```text
创建对象模块
校验模块
发送消息模块
更新数据库模块
```

错误原因：
```text
这类拆法过于贴近执行步骤和实现动作，失去了概要设计层的稳定结构主语。
```

#### 4.4.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 当前概要设计层面，identity 不应只是一个“身份真相仓”的抽象词
- 而应进一步展开为若干主要组成部分
- 这些部分是后续职责、接缝、对象与流程轮廓继续展开的稳定主语

它不是在写 identity 的代码模块，也不是在重画架构边界，而是在建立“概要设计层的主要组成部分骨架”。

### 4.5 各部分职责与边界

#### 4.5.1 本章目标

在已划分出主要组成部分的前提下，明确每个部分分别承担什么职责、不承担什么职责，以及它们之间通过什么边界彼此分开，从而防止概要设计继续发散成重复架构边界或过早滑入详细设计。

#### 4.5.2 本章应回答的问题

```text
1. 每个主要组成部分分别承担什么职责？
2. 每个主要组成部分明确不承担什么职责？
3. 哪些内容虽然相关，但必须由相邻部分或边界外能力承担？
4. 各部分之间靠什么边界彼此分开？
5. 哪些职责如果不写清，后续最容易让概要设计滑进实现层或让不同部分串线？
```

#### 4.5.3 本章不应回答的问题

```text
- 不重写本仓整体职责边界
- 不展开各部分之间的关键接缝细节
- 不展开字段、函数、表结构或实现流程
- 不把外部对象、系统上下文边界或架构层职责边界混写成部分内部职责
- 不把“怎么实现”写成“是什么职责”
```

#### 4.5.4 推荐表达形式

##### 主表达形式
1. 各部分职责与边界表

##### 辅表达形式（按需）
2. 部分边界说明短文

##### 图表分工
- 表负责说明：每个部分承担什么、不承担什么，以及它与相邻部分如何分界。
- 短文负责解释：为什么这些边界必须在概要设计层先钉住，而不能留给详细设计再补。

#### 4.5.5 各部分职责与边界表

##### 固定结构表

| 组成部分 | 承担什么 | 不承担什么 | 边界说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 组成部分 | 已在 4.4 收稳的正式主要组成部分 | 不写代码目录、类、函数或外部对象 |
| 承担什么 | 该部分在概要设计层承担的正式职责 | 不写实现步骤、接口细节或字段级对象定义 |
| 不承担什么 | 与相邻部分或边界外能力明确切开的非职责项 | 不写含糊“其他内容”类表述 |
| 边界说明 | 该部分与相邻部分彼此分开的依据 | 不写系统上下文重述或大段架构解释 |

#### 4.5.6 写法规则

##### 职责的粒度
职责应写成：

```text
概要设计层主要组成部分在整体中承担的职责轮廓
```

优先写：
- 该部分负责承接什么
- 该部分不负责什么
- 它为什么不能和相邻部分混层

不应写：
- 函数职责
- 表结构职责
- 接口调用细节
- 中间状态处理细节

##### 边界说明的写法
边界说明优先回答：

```text
为什么这个部分和相邻部分必须分开
```

可以来自：
- 职责边界
- 主要接缝
- 关键对象轮廓
- 主要流程轮廓

不应写成：
- 因为代码拆分方便
- 因为实现上这样更顺手
- 因为习惯这样分层

##### 部分边界说明短文
短文必须回答：

```text
1. 为什么这些部分边界必须在概要设计层先被明确
2. 为什么它们不能等到详细设计再自然浮现
3. 如果边界不清，会导致什么层次串线
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做部分边界说明
- 不提前进入接缝细节或流程细节
```

#### 4.5.7 完成标准

- 已明确每个主要组成部分承担什么职责
- 已明确每个主要组成部分不承担什么职责
- 已说明各部分之间为什么必须分开
- 没有把本仓整体职责边界、系统上下文对象或实现细节混写进本章
- 读者已经能理解各主要部分之间的职责切面

#### 4.5.8 正反例

**正确示例（通用）：**

| 组成部分 | 承担什么 | 不承担什么 | 边界说明 |
|---|---|---|---|
| 正式输入承接部分 | 承接正式输入并把输入导入内部结构 | 不直接承担核心处理与核心状态演化 | 若输入承接与核心处理不分开，外部输入会反向统治内部结构 |
| 核心处理部分 | 承担核心状态变化与核心处理组织 | 不直接作为对外消费面暴露 | 若核心处理直接承担外部消费，读写与演进边界会混层 |
| 结果承接 / 对外供给部分 | 承接对外消费、只读供给或正式结果输出 | 不承担核心状态生成与内部主处理 | 若结果供给和核心处理不分开，下游会直接绑定内部真相结构 |

**错误示例 A：写成实现职责**

```text
service 负责校验，repo 负责存储，handler 负责返回。
```

错误原因：
```text
这已经掉进实现层，不是概要设计层的部分职责与边界表达。
```

**错误示例 B：写成外部边界职责**

```text
用户端负责输入，外部系统负责回调，数据库负责保存。
```

错误原因：
```text
这里混入了外部对象和基础设施对象，不是在说明本仓内部主要部分的职责边界。
```

**错误示例 C：只写“承担什么”，不写“不承担什么”**

```text
核心处理部分负责状态处理。
```

错误原因：
```text
缺少非职责约束，后续最容易导致边界膨胀和部分串线。
```

#### 4.5.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- identity 的主要部分分别承担什么职责
- 哪些职责不能混在一起
- 为什么身份真相相关处理、对外消费承接和输入承接必须保持边界

它不是在写 identity 的代码分层，也不是在重画架构边界，而是在把“主要部分之间如何分责”讲清楚。

### 4.6 关键接缝与接口轮廓

#### 4.6.1 本章目标

在已明确主要组成部分及其职责边界的前提下，收稳这些部分之间通过哪些关键接缝协作、接口轮廓应表达什么层次，以及哪些输入输出已经足以在概要设计层被正式点名。

#### 4.6.2 本章应回答的问题

```text
1. 主要组成部分之间通过哪些关键接缝协作？
2. 哪些接缝在概要设计层已经足以被正式点名？
3. 这些接缝分别在承接什么输入或输出？
4. 哪些看起来像“接口”，但其实已经掉到协议或详细设计层，不应进入本章？
5. 哪些接缝如果不先讲清，后续最容易导致部分之间串线？
```

#### 4.6.3 本章不应回答的问题

```text
- 不写 API 路径
- 不写协议 schema
- 不写事件字段与回调参数
- 不写函数签名或调用链
- 不把系统上下文对象关系重写成接缝轮廓
- 不展开详细设计层接口契约
```

#### 4.6.4 推荐表达形式

##### 主表达形式
1. 关键接缝概览表

##### 辅表达形式（按需）
2. 极简接缝关系示意图
3. 一段接缝边界说明短文

##### 图表分工
- 表负责说明：各主要组成部分之间通过哪些关键接缝协作、这些接缝承接什么输入输出、处于什么轮廓层次。
- 图只在必要时辅助表达接缝之间的大体关系，不承担协议、流程或对象细节。
- 短文负责解释为什么这些接缝必须在概要设计层先被点名。

#### 4.6.5 关键接缝概览表

##### 固定结构表

| 接缝 | 连接哪些部分 | 承接什么 | 轮廓说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 接缝 | 概要设计层已足够稳定、应被点名的关键接缝 | 不写 API 名、topic 名、event 名或回调名 |
| 连接哪些部分 | 该接缝连接的主要组成部分 | 不写外部系统上下文对象或实现模块 |
| 承接什么 | 该接缝在概要设计层承接的输入 / 输出轮廓 | 不写协议字段、消息体结构或参数细节 |
| 轮廓说明 | 为什么这条接缝值得在概要设计层被正式点名 | 不写详细接口契约或调用链 |

#### 4.6.6 写法规则

##### 接缝的粒度
接缝应写成：

```text
主要组成部分之间已经足以被正式点名的协作接缝
```

优先写：
- 会持续存在的正式接缝
- 对后续对象轮廓或流程轮廓有直接影响的接缝
- 如果不先讲清，后续部分之间最容易串线的接缝

不应写：
- 协议细节
- 具体 API / 事件 / 回调名字
- 代码级函数接口
- 临时实现通道

##### 承接什么的写法
这里应回答：

```text
这条接缝承接的是什么输入 / 输出轮廓
```

优先写：
- 正式输入
- 正式输出
- 只读供给
- 核心处理结果
- 边界级传播或回送轮廓

不应写：
- 参数清单
- payload 字段
- schema
- 函数调用参数

##### 接缝边界说明短文
短文必须回答：

```text
1. 为什么这些接缝必须在概要设计层先点名
2. 为什么它们不能等到详细设计再自然浮现
3. 如果接缝不清，会导致哪些部分边界串线
```

##### 短文粒度约束
```text
- 共 1 段
- 2~4 句
- 总长度建议 80~160 字
- 只做接缝层次说明
- 不提前进入流程和协议细节
```

#### 4.6.7 完成标准

- 已明确主要组成部分之间通过哪些关键接缝协作
- 已明确这些接缝分别承接什么输入 / 输出轮廓
- 已说明为什么这些接缝值得在概要设计层被正式点名
- 没有把系统上下文关系、协议细节或代码接口误写进本章
- 读者已经能建立“主要部分如何接起来”的第一层理解

#### 4.6.8 正反例

**正确示例（通用）：**

| 接缝 | 连接哪些部分 | 承接什么 | 轮廓说明 |
|---|---|---|---|
| 正式输入承接接缝 | 正式输入承接部分 ↔ 核心处理部分 | 承接系统正式输入进入内部处理 | 该接缝若不先点名，输入边界会直接混入核心处理主语 |
| 核心处理结果接缝 | 核心处理部分 ↔ 结果承接 / 对外供给部分 | 承接核心处理后的结果输出轮廓 | 该接缝决定核心处理与对外消费面如何分开 |
| 只读供给接缝 | 核心处理部分 ↔ 只读承接 / 消费部分 | 承接摘要、只读视图或结果供给轮廓 | 该接缝若不明确，外部消费容易反向绑定核心结构 |

**错误示例 A：写成 API / 事件列表**

```text
POST /items
GET /items/{id}
ItemCreated
ItemUpdated
```

错误原因：
```text
这已经掉进协议与接口目录层，不是概要设计层的关键接缝轮廓。
```

**错误示例 B：写成函数级接口**

```text
createItem(input)
validateItem(input)
persistItem(entity)
```

错误原因：
```text
这是代码级函数接口，不是概要设计层的部分协作接缝。
```

**错误示例 C：写成系统上下文关系重述**

```text
用户端 -> 系统
系统 -> 外部服务
系统 -> 数据库
```

错误原因：
```text
这在重写系统上下文对象关系，而不是说明本仓内部主要部分之间的关键接缝。
```

#### 4.6.9 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- identity 的主要组成部分之间通过哪些正式接缝协作
- 哪些接缝在概要设计层已经足以被点名
- 这些接缝承接的是哪类输入输出轮廓，而不是具体接口或事件协议

它不是在写 identity 的 API 列表，也不是在写 callback / event 目录，而是在收稳“主要部分如何通过正式接缝接起来”。

#### 4.7.8 正反例

### 4.10 设计风险与待确认事项

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 待确认事项 | 尚未形成确定结论、仍需进一步确认且会影响概要设计主线判断的问题项 | 不写普通疑问、功能愿望、实施待办或优化事项 |
| 影响范围 | 该事项若定论变化，将影响哪条概要设计主线、哪类组成部分、哪类接缝、哪类对象或哪类流程理解 | 不写泛化的“整体相关”类表述 |
| 缺失确认 | 当前还缺什么确认，因此该事项不能被定论 | 不写“还没想好”“后续再看”“继续讨论”等空泛表达 |
| 当前挂起口径 | 尚未定论前的保守挂起方式 | 不写临时方案、感觉性处理、预支结论、处置动作或任务拆分 |
| 说明 | 必要的去歧义判断，解释该事项为什么仍属于待确认事项、为什么当前还不能定论，以及为什么当前挂起口径合理 | 不写方案推演或实施建议 |

#### 4.10.8 当前设计层处理口径说明（按需）

当前设计层处理口径说明短文用于解释：
- 为什么某些问题当前被视为设计风险，而不是待确认事项
- 为什么某些问题当前只能挂起，而不能装成已知结论
- 为什么这里不继续写最终解决方案

约束：
```text
- 共 1 段
- 3~5 句
- 不重写两张表
- 不滑入实施方案
```

#### 4.10.9 完成标准

- 已明确区分设计风险与设计待确认事项
- 已写清每项风险的影响范围、当前处理口径与阻塞性
- 已写清每项待确认事项的影响范围、缺失确认与当前挂起口径
- 已说明为什么这些项配进入本章
- 没有滑入任务层、方案层或已定结论回退层
- 没有使用空泛风险词或假挂起表述

#### 4.10.10 正反例

**正确示例 A：设计风险表（通用）**

| 风险项 | 影响范围 | 当前处理口径 | 是否阻塞 | 说明 |
|---|---|---|---|---|
| 核心部分边界尚未完全闭环的风险 | 核心部分边界、关键接缝主线 | 当前按更保守边界收口，不提升为正式主结构 | 有条件阻塞 | 该问题已明确会影响概要设计主线成立，因此属于正式设计风险，而不是普通待办。 |
| 关键接缝表达尚未完全收稳的风险 | 接缝轮廓、主要流程理解 | 当前只允许保守接缝口径，不伪装为已稳定闭环 | 不阻塞 | 该问题已被识别，但在当前阶段仍可带约束推进。 |
| 只读承接结果轮廓可能失真的风险 | 对外供给面、只读对象轮廓、主要流程末端 | 当前保留只读轮廓口径，不回填为核心结构定论 | 不阻塞 | 风险已经明确，当前处理重点是约束其影响，不是假装已经关闭。 |

**正确示例 B：设计待确认事项表（通用）**

| 待确认事项 | 影响范围 | 缺失确认 | 当前挂起口径 | 说明 |
|---|---|---|---|---|
| 某关键部分边界的最终裁决尚未形成 | 部分边界主线、后续职责说明 | 缺最终边界结论确认 | 当前不回填为定论，只作结构背景保留 | 该事项尚未形成定论，因此不能升级为正式设计风险，也不能伪装成已知结论。 |
| 某关键接缝是否进入主线尚待确认 | 接缝主线、后续流程轮廓判断 | 缺主线范围裁决 | 当前不纳入主线，只挂起为未决项 | 该事项会影响后续章节成立，但当前仍缺关键判断依据。 |
| 某异常场景是否足以上升到概要设计层尚待确认 | 异常轮廓主线、进入详细设计条件 | 缺边界严重性确认 | 当前按更保守边界处理，不提前写入正式异常轮廓 | 该事项当前不能被写成已知风险，但必须显式挂起以防误导主线。 |

**错误示例 A：写成任务 backlog**

```text
补对象轮廓
补接缝
补流程
补异常
```

错误原因：
```text
这是任务清单，不是设计层未闭环问题判断，没有影响范围、当前口径或阻塞性判断。
```

**错误示例 B：写成 TODO / 优化清单**

```text
后续优化流程
后续增强对象模型
后续补异常处理
```

错误原因：
```text
只有愿望和方向，没有说明是不是风险、缺什么确认以及当前处理口径，因此不配直接进入本章。
```

**错误示例 C：写成空泛风险页**

```text
存在设计风险
存在对象风险
存在流程风险
```

错误原因：
```text
没有影响范围、当前处理口径、阻塞性，也没有说明为什么它是正式设计风险，这类写法没有规范判断力。
```

**错误示例 D：写成已定结论重复页**

```text
主要组成部分必须清晰，接缝必须稳定，流程必须完整。
```

错误原因：
```text
这些可能是前文已收稳结论，不是新的设计风险或待确认事项，这会让本章变成前文回退区。
```

**错误示例 E：把待确认事项写成已知风险**

```text
某关键接缝是否进入主线尚未确认，因此这是当前最大的正式设计风险。
```

错误原因：
```text
如果“是否进入主线”还没确认，那它更应该先写成待确认事项，不能提前升级成已知设计风险。
```

**错误示例 F：只有“挂起”没有“缺失确认”**

```text
该事项当前挂起，后续再看。
```

错误原因：
```text
没有说明缺什么确认、影响范围以及为什么只能挂起，这样的待确认事项写法太空，不能进入正式规范。
```

#### 4.10.11 identity 辅助说明

如果用 `L1-identity` 帮助理解，本章应帮助读者看清：

- 哪些 identity 相关问题已经明确会影响主要部分、接缝、对象、流程或异常轮廓，因此属于设计风险
- 哪些问题仍未形成稳定结论，只能挂起等待确认
- 当前如何保守约束这些问题，而不让它们污染已收稳的概要设计主线

它不是在写 identity 的整改清单或实施计划，而是在收稳“哪些问题还没闭环”。

### 4.11 参考

#### 4.11.1 本章目标

明确哪些上游需求材料、架构材料、关键决策材料与规范材料仍构成当前概要设计文档的正式参考，并以稳定、克制、可导航的方式列出。

#### 4.11.2 本章应回答的问题

```text
1. 哪些材料构成当前概要设计文档的正式参考？
2. 这些材料分别属于什么类别？
3. 它们为什么值得被长期保留为概要设计参考？
4. 为什么这些材料不与上游承接声明、追溯矩阵或 ADR 索引职责重叠？
5. 为什么某些草稿、临时材料或一次性讨论记录不进入本章？
```

#### 4.11.3 本章不应回答的问题

```text
- 不重写与上游文档的关系声明
- 不重写需求追溯矩阵
- 不重写 ADR 索引
- 不写资料仓 / 链接大全
- 不写主观推荐阅读清单
- 不新增判断
- 不用“仅供参考”掩盖弱材料
```

#### 4.11.4 推荐表达形式

##### 主表达形式
1. 参考材料清单表

##### 辅表达形式（按需）
2. 参考范围说明短文

##### 图表分工
- 主表负责稳定、克制、可导航地列出哪些材料构成当前概要设计文档的正式参考，并说明它们各自属于什么类型、为什么值得被长期保留。
- 短文只用于收束参考范围，解释为什么某些材料进入本章、为什么某些草稿或临时资料不进入本章，以及为什么这里不重复上游承接、追溯关系和决策索引的职责。

#### 4.11.5 参考材料清单表

##### 固定结构表

| 参考材料 | 材料类别 | 用途 / 参考价值 | 说明 |
|---|---|---|---|

##### 字段解释

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 参考材料 | 当前概要设计文档正式保留的参考材料名称 | 不写临时讨论稿、含糊来源描述或仅有路径而无材料语义的表述 |
| 材料类别 | 该材料所属的稳定、可复用类别 | 不写过弱的泛化分类词，也不临时创造过细类别 |
| 用途 / 参考价值 | 该材料对当前概要设计文档成立的正式参考意义 | 不写“仅供参考”“看过”“备用资料”之类弱表述 |
| 说明 | 必要的去歧义判断，解释该材料为什么配进入本章、为什么值得长期保留，以及为什么它不是草稿、临时笔记或可省略资料 | 不写来源关系分析、追溯关系说明或 ADR 摘要 |

#### 4.11.6 参考范围说明（按需）

参考范围说明短文用于解释：
- 为什么某些材料进入本章
- 为什么某些草稿、临时笔记或一次性讨论材料不进入本章
- 为什么这里不重复上游承接声明、追溯关系和 ADR 索引职责
- 为什么参考章节应保持克制，而不是变成资料仓或导读页

约束：
```text
- 共 1 段
- 3~5 句
- 不重写主表
- 不滑入主观总结或来源关系分析
```

#### 4.11.7 完成标准

- 已明确哪些材料构成当前概要设计文档的正式参考
- 已说明每份材料属于什么类别
- 已说明每份材料为什么值得被长期保留
- 已排除草稿、临时材料和与前文章节职责重叠的内容
- 清单可导航但不过载
- 没有滑入资料仓、导读页或附录式杂项清单

#### 4.11.8 正反例

**正确示例（通用）：**

| 参考材料 | 材料类别 | 用途 / 参考价值 | 说明 |
|---|---|---|---|
| 当前仓对应的上游需求文档 | 上游需求材料 | 用于理解本次概要设计最终承接的需求边界、能力范围与约束来源 | 该材料不是来源声明的重复，而是后续读者理解本次概要设计时仍需回看的正式上游材料。 |

| 关键 ADR 或标准性材料 | ADR / 标准材料 | 用于理解本次概要设计所依赖的关键决策依据或方法边界 | 该类材料只有在已经对当前主线产生稳定约束时才配进入本章。 |

**错误示例 A：写成链接清单大全**

```text
- zzz.md
- aaa.md
```

错误原因：
```text
这只是链接堆放，没有材料类别、用途说明和筛选门槛，因此会让本章退化成文件堆放区。
```

**错误示例 B：写成来源声明第二版**

```text
本文承接自需求文档、架构文档与相关标准。
```

错误原因：
```text
这只是来源声明，没有列出正式参考材料，也没有说明为什么这些材料值得长期保留，职责已经与 4.1 重叠。
```

**错误示例 C：写成资料仓**

```text

临时笔记
legacy 文档
会议纪要
历史方案
```

错误原因：
```text
没有正式筛选、没有稳定性判断，也没有“为什么现在还值得保留”的理由，这会让本章失去克制性。
```

**错误示例 D：写成阅读指南**

```text
建议新人先看需求文档，再看架构设计，再看 ADR。
```

错误原因：
```text
这是导读页，不是参考材料清单，本章不应承担阅读顺序推荐职责。
```

**错误示例 E：只写“仅供参考”**

```text
某规范文档，仅供参考。
```

错误原因：
```text
没有说明为什么值得保留，“仅供参考”过于弱，不能作为正式入章理由，会让本章变成礼貌性附录。
```

如果用 `L1-identity` 帮助理解，本章应帮助读者筛出哪些上游需求材料、架构材料、关键 ADR 或规范材料，是真正支撑 identity 概要设计主线理解的正式参考。它不是在重复 identity 的来源声明、追溯关系或决策索引，而是在收口“后续读者还应回看哪些正式材料”。

## 六、图表与表达形式规范

### 5.1 总体原则

概要设计线整体采用：

> 表为主、图按需、短文收束边界。

图、表、短文分别承担不同职责：

- 表：收稳主语、职责、边界、接缝、对象与流程轮廓
- 图：只在必要时补充结构感与关系感
- 短文：只用于说明边界、例外与不展开的原因

概要设计不以“图越多越好”为原则，也不以“纯文字说明”为目标；它的核心是让读者在不过早掉进详细设计的前提下，建立足够稳定的可实现结构心智。

### 5.2 表的使用规则

#### 5.2.1 表是默认主表达形式
大多数概要设计章节应优先使用表格收敛内容，例如：

- 主要组成部分概览表
- 各部分职责与边界表
- 主要组成部分内代码主体表
- 关键对象字段 / 状态 / 函数表
- API / 接口骨架表
- 关键处理流 ASCII 图后的关键设计点
- 状态定义表
- 异常与边界场景轮廓表
- 设计风险表
- 设计待确认事项表
- 参考材料清单表

#### 5.2.2 表必须承担“判断”职责
表格不能退化成：

- checklist
- 名称列表
- 目录抄写
- 大词堆砌

每一张表都应至少承担以下之一：
- 划分主语
- 划清边界
- 收稳轮廓
- 解释关系
- 暴露未闭环项

#### 5.2.3 表格行文应克制
表格中的每一列应回答：
- 写什么
- 不写什么
- 为什么有这一列

不应通过表格把：
- 协议细节
- 字段细节
- 函数细节
- DDL
- 运维参数
提前拉进概要设计。

### 5.3 图的使用规则

#### 5.3.1 图不是默认主结构
概要设计线中，图通常是按需辅助表达，不是默认主结构。

只有在满足以下条件之一时，才建议使用图：
- 单靠表格不足以建立结构感
- 主要组成部分、接缝或流程关系较难用纯表快速看懂
- 如果不画图，读者很难形成整体轮廓

#### 5.3.2 图只表达“轮廓关系”
概要设计图只应表达：
- 主要部分之间的大体结构关系
- 主要组成部分之间的大体连接关系
- 关键处理流的大体流动方向
- 状态流转和状态传播关系
- 异常 / 边界场景对主流程的影响轮廓
- 配置来源、运行装配和受影响概要层结构之间的轮廓关系

图不应表达：
- API 路径
- topic / event 名
- 回调参数
- 字段结构
- 详细时序
- 函数调用链
- DDL / 索引
- 部署与运维参数

#### 5.3.3 图的粒度必须低于详细设计
概要设计图的目标是：

> 建立结构轮廓感，不是替代详细设计图。

因此不应画成：
- 代码模块图
- 时序图
- 协议交互图
- 部署拓扑图
- 实现流程图

#### 5.3.4 ASCII 图统一格式

概要设计中的 ASCII 图必须使用统一风格，避免不同文档各画各的。

##### 统一输出结构

每一张 ASCII 图必须采用以下结构：

````md
#### <图类型标题>

```text
<ASCII 图正文>
```

关键说明：
- <说明图表达了什么结构关系>
- <说明图没有表达哪些详细设计内容>
- <说明图中最容易误解的边界是什么>
````

其中：
- `图类型标题` 必须使用本规范允许的图类型名称。
- 图正文必须放在 `text` 代码块中。
- `关键说明` 必须有 2~5 条。
- 禁止只有图、没有标题或没有图后说明。

##### 允许的图类型

概要设计正式章节只允许使用以下 ASCII 图类型：

| 图类型 | 允许出现章节 | 作用 | 主方向 |
|---|---|---|---|
| 架构模块到代码主体映射图 | §4 | 把架构模块转译为代码主体骨架 | 自上而下树形 |
| 实现分层视图 | §4 | 说明外部入口如何进入实现分层 | 自上而下 |
| 各部分交互总图 | §5 | 说明主要组成部分之间的大体交互 | 自上而下为主，少量横向分支 |
| 局部接缝图 | §5 按需 | 说明复杂组成部分之间的局部接缝 | 自上而下为主 |
| 对象分布图 | §6 按需 | 说明关键对象与主要组成部分的归属关系 | 自上而下树形 |
| 处理流图 | §8 | 说明关键接口如何穿过入口、服务、对象和结果 | 自上而下 |
| 状态流转图 | §9 | 说明状态、触发动作和迁移方向 | 自上而下 |
| 状态传播关系图 | §9 按需 | 说明状态变化如何传播到事件、投影或下游 | 自上而下为主，少量横向分支 |
| 异常影响图 | §10 按需 | 说明异常如何改变主线轮廓或落到哪个部分处理 | 自上而下为主，少量分支 |
| 配置影响轮廓图 | §11 按需 | 说明配置影响哪些主要部分、入口、adapter、job 或接缝 | 自上而下为主，少量横向分支 |

禁止在概要设计中新增未定义的图类型；确有必要时，应先修改本规范，再落到具体概要设计文档。

##### 基本字符集

允许使用：

```text
│ ├─ └─ ┌ ┐ └ ┘ ─ ▼ ►
```

允许在简单图中使用：

```text
->  =>
```

禁止使用：

```text
花哨边框
Emoji
彩色标记
Mermaid / PlantUML / Graphviz 语法
混用多套箭头风格
表情、颜色、特殊图标
框图中夹杂 Markdown 表格
```

##### 图标题规则

每个图前必须有明确标题，标题应说明图的类型：

```md
#### 架构模块到代码主体映射图
#### 实现分层视图
#### 各部分交互总图
#### <接口名> 处理流
#### 状态流转图
#### 状态传播关系图
```

禁止只写：

```md
#### 图
#### 流程
#### 架构图
```

##### 节点命名规则

- 节点名称必须使用本章已收稳的正式主语。
- 业务组成部分使用中文正式名，例如 `核心身份处理部分`。
- 代码主体使用正式对象或服务名，例如 `GlobalMember`、`OutboxPublisher`。
- 实现分层使用稳定英文层名，例如 `Inbound / Operations`、`Application Services`。
- 同一张图中不要把业务组成部分、实现分层、对象、函数混成同一级。

##### 方向规则

- 结构包含关系使用自上而下树形图。
- 层级调用 / 处理流使用自上而下 `▼`。
- 横向发布、分支或旁路使用 `├─` / `└─`。
- 图内不要同时大量使用自上而下和自左向右两种主方向。

##### 箭头规则

- 主路径使用 `│` + `▼`。
- 分支使用 `├─` 和 `└─`。
- 简短横向关系允许使用 `->`，但同一张图内要保持一致。
- 状态迁移清单中允许使用 `<state_a> -> <state_b>`，但状态流转图正文仍优先使用 `│` + `▼`。
- 不用箭头表达完整时序、协议交互或函数调用链。

##### 注释规则

- 图中允许用短注释说明节点作用。
- 注释应放在节点同一行右侧，保持简短。
- 不在图中写长段落、完整字段、完整参数表或错误码。

示例：

```text
核心身份处理部分
  ├─ GlobalMember              平台级成员真相
  └─ GlobalMemberLifecycle     生命周期状态机
```

##### 图后说明规则

每张图后必须有 2~5 条关键说明，说明：

- 图表达了什么结构关系
- 图没有表达哪些详细设计内容
- 图中最容易误解的边界是什么

禁止图后无说明直接进入下一节。

##### 跨文档一致性规则

- 同一类图在不同仓的概要设计中必须使用同一种结构模板。
- 如果 identity、method-library、work、process 等仓都需要画 `实现分层视图`，应沿用同一层名与同一方向。
- 不允许某个仓使用树形图表达处理流、另一个仓使用横向箭头表达同类处理流。
- 如果某仓确实需要偏离模板，必须在图后说明偏离原因，并确保没有表达详细设计内容。

### 5.4 短文的使用规则

#### 5.4.1 短文只做边界收束
短文在概要设计中主要用于：
- 解释为什么这样切章节
- 解释为什么某些内容不展开
- 解释为什么图 / 表这样表达
- 解释关键例外与去歧义判断

#### 5.4.2 短文不承担新判断
短文不应用于：
- 新增章节主结论
- 替代表格主内容
- 提前引入后续章节内容
- 变成散文式结构说明

#### 5.4.3 短文应保持克制
建议：
- 1 段
- 2~4 句
- 总长度以能完成边界说明为准

不要写成长篇“理念段落”。

### 5.5 图 / 表 / 短文的协同关系

#### 5.5.1 表先于图
在概要设计线中，通常先有表，再决定是否补图。也就是说：
- 先收主语
- 再补结构感

#### 5.5.2 图不能替代表
即使画图，仍应有对应表格来说明：
- 图中对象是什么
- 为什么值得被点名
- 为什么边界这样切

#### 5.5.3 短文不能替代图表
短文只负责解释：
- 为什么这样表达
- 为什么不往下展开

不能替代表格和图承担结构表达任务。

### 5.6 `identity` 辅助说明的使用规则

#### 5.6.1 作用
`identity` 辅助说明只用于：
- 把通用规则映射到真实仓级语境

#### 5.6.2 不做什么
`identity` 辅助说明不用于：
- 新增本章判断标准
- 替代主规则
- 充当实现示例
- 形成第二套样板正文

#### 5.6.3 何时写
只有在：
- 当前章节规则较抽象
- 加上 `identity` 后能明显帮助读者理解
时才写。

如果只是复述正文，应删减到最小。

### 5.7 图表充分性要求

一个合格的概要设计，至少应以稳定的主表体系为核心，并按需补充少量帮助建立结构感的示意图。

表格用于收稳：
- 主要组成部分
- 职责边界
- 关键对象
- API / 接口骨架
- 关键处理流
- 状态定义
- 异常轮廓
- 配置影响轮廓
- 未闭环项
- 参考材料

图只在纯表格不足以建立结构感时出现，并且只表达主要结构关系、组成部分交互关系、关键处理流、状态流转或配置影响轮廓，不提前承载协议、字段、函数实现、DDL、时序细节、配置项清单或运维参数。

### 5.8 本节完成标准

- 已明确概要设计线整体采用“表为主、图按需、短文收束边界”的总规则
- 已明确图只表达结构轮廓，不承载实现细节
- 已明确表必须承担判断职责，不能退化成清单
- 已明确短文只做边界收束，不承担新判断
- 已明确 `identity` 辅助说明的最小角色
- 已明确合格概要设计至少应具备的图表充分性要求
- 后续各章节可直接复用本节总规则，而不必反复重申

## 九、评审清单

### 8.1 评审总原则

评审概要设计时，不应先问：

- 这个实现是不是最优
- 这个技术方案是不是最先进
- 这个目录结构是不是顺手

而应先问：

> 这份概要设计有没有把“可实现结构层”的主语讲清。

也就是说，评审顺序应优先是：

1. 承接是否正确
2. 范围是否清楚
3. 约束是否守住
4. 主要结构是否成形
5. 是否越界到上下游层次

### 8.2 评审清单（总表）

#### 8.2.1 上游承接检查
- 是否明确承接了哪些需求与架构结论？
- 是否没有把需求目标、系统上下文、架构取舍重新写一遍？
- 是否没有把来源声明写成上游文档摘要？
- 每个正式章节是否列出对应的 `design-calibration` 中间产物，并引导读者继续阅读？

#### 8.2.2 范围与深度检查
- 是否明确说明这轮概要设计讲到哪里？
- 是否明确哪些内容当前不进入概要设计范围？
- 是否没有把范围写成功能愿望池？
- 是否没有把非范围写成“以后再说”？

#### 8.2.3 约束检查
- 是否写清概要设计层必须继续守住哪些约束？
- 是否明确这些约束在保护什么边界？
- 是否没有把约束写成技术实现限制或运维清单？

#### 8.2.4 主要结构检查
- 是否已经收稳代码主体框架，而不是只停留在架构模块名？
- 架构模块到代码主体的映射是否清楚？
- 主要组成部分、职责与边界是否清楚？
- 关键对象是否已经点名到对象骨架、关键字段骨架和成员函数骨架？
- API / Command / Query / Event / Operations Job 是否已经按类别收稳？
- 关键处理流是否已经说明重要接口如何穿过入口、application service、domain object、repository / outbox / projection？
- 状态定义与状态流转是否已经单独收稳（如适用）？
- 异常与边界场景是否补了必要的轮廓？
- 配置影响轮廓是否已经说明哪些主要部分或接缝受配置影响、哪些边界禁止配置化、哪些配置实现契约交给详细设计？
- 是否已经形成详细设计承接清单？

#### 8.2.5 风险与待确认检查
- 是否已显式说明当前设计层未闭环项？
- 是否区分了风险与待确认事项（如适用）？
- 是否没有把 TODO、任务或实施方案写进来？

#### 8.2.6 层次边界检查
- 是否没有回滑成需求文档？
- 是否没有重写架构设计？
- 是否没有提前写完整详细设计？
- 是否正确区分“概要设计允许的骨架”和“详细设计才写的完整细节”？
- 是否没有混入部署、运维和交付层内容？

#### 8.2.7 图表充分性检查
- 是否已经具备支撑本章主语的主表，而不是只靠文字说明？
- 是否已经至少通过一组稳定主表收稳：代码主体框架、主要组成部分 / 职责边界、关键对象、API / 接口骨架、关键处理流、状态机、配置影响轮廓、详细设计承接清单、设计风险 / 待确认事项、参考材料？
- 图是否只在建立结构感确有必要时出现？
- ASCII 图是否都使用了明确图标题、`text` 代码块和图后 2~5 条关键说明？
- ASCII 图是否遵守统一字符集、统一方向和统一箭头规则，没有混入 Mermaid / PlantUML / Graphviz、表情、颜色或多套箭头风格？
- 同类图在不同章节或不同仓之间是否保持同一种模板和方向？
- 图是否仍停留在概要设计层骨架，而没有提前滑入完整协议图、详细时序图、代码调用链脚本或部署运维图？
- 表格是否承担了结构判断职责，而不是退化成 checklist 或目录清单？

### 8.3 评审时应优先识别的典型错误

#### 错误 1：只有章节名，没有结构主语
例如：
- 看起来章节都齐
- 但没有讲清代码主体框架、关键对象、正式接口、处理流和状态机

#### 错误 2：架构内容回流
例如：
- 系统上下文
- 子域划分
- 关键技术选型
- 方案取舍
又在概要设计里重新展开

#### 错误 3：详细设计内容提前掉落
例如：
- 完整字段类型全集
- 完整函数签名或实现代码
- DDL
- 协议 schema
- 时序细节

注意：关键字段骨架、成员函数骨架、正式 API / Event / Job 名称不属于本错误；它们是新版概要设计应当收稳的骨架内容。

#### 错误 4：风险未收口
例如：
- 未闭环问题没有被显式收纳
- 直接假装主线已经全部成立

### 8.4 评审结论建议分级

#### A. 可继续进入详细设计
满足条件：
- 代码主体框架已经清楚
- 对象、接口、处理流、状态机、配置影响轮廓和详细设计承接清单已经收稳
- 层次边界稳定
- 风险已被显式收口
- 没有写入完整字段模型、完整协议 schema、实现代码或 DDL

#### B. 可继续讨论但不能进入详细设计
满足条件：
- 主结构已有雏形
- 但代码主体框架、关键对象、接口骨架、处理流、状态机或配置影响轮廓仍不稳
- 或设计层未闭环项还未收住

#### C. 需退回重构
满足条件：
- 仍然回滑到需求 / 架构 / 详细设计
- 主语不清
- 边界不清
- 不能支撑后续展开

### 8.5 本节完成标准

- 已给出概要设计评审的总原则
- 已形成覆盖上游承接、范围深度、约束、结构、风险和层次边界的检查清单
- 已补入图表充分性检查
- 已列出典型错误检查方向
- 已给出可执行的评审结论分级
- 后续评审概要设计文档时，可以直接使用本节作为最小检查框架

## 十一、正反例附录

### 10.1 本附录的作用

本附录用于跨章节提示：

- 概要设计层正确表达的共同特征
- 最常见的跨层误写方式
- 人类作者和 Agent 在起稿、评审和收口时可直接复用的判断坐标

本附录不替代各章节内的正反例，
而是为整条概要设计主链提供共性错误与共性正确性标准。

### 10.2 正确写法的共性特征

一份写得正确的概要设计，通常同时具备下面这些特征：

#### 1. 承接上游而不重写上游
它清楚承接：
- 需求边界
- 架构边界
- 架构约束

但不重新定义：
- 用户故事
- 系统上下文
- 子域划分
- 技术选型
- 方案取舍

#### 2. 主语稳定
它真正围绕以下主语展开：
- 主要组成部分
- 各部分职责与边界
- 关键接缝与接口轮廓
- 关键对象轮廓
- 主要流程轮廓
- 异常与边界场景轮廓

而不是在需求主语、架构主语、详细设计主语之间乱切。

#### 3. 停在“轮廓层”
它已经足够具体到：
- 能支撑进入详细设计

但仍然克制到：
- 不提前写字段
- 不提前写函数
- 不提前写 DDL
- 不提前写时序细节
- 不提前写部署与运维细节

#### 4. 表达重心是“结构可实现性”
它讲的是：
- 主要部分怎么构成整体
- 这些部分怎么分责
- 通过什么接缝接起来
- 对象和流程轮廓怎么支撑实现

而不是：
- 功能罗列
- 技术罗列
- 实现细节堆砌

#### 5. 未闭环问题被显式收口
它不会为了“文档完整”而把没想清楚的地方装成定论，
而是会在：
- 设计风险
- 待确认事项
里显式收住未闭环项。

### 10.3 常见跨层错误总表述

#### 错误类型 A：回滑成需求文档
表现：
- 继续写用户故事
- 继续写功能需求
- 继续写验收标准
- 把设计目标写成功能清单

本质问题：
没有从“做什么”下沉到“怎样形成可实现结构”。

#### 错误类型 B：回滑成架构设计
表现：
- 重新讲系统上下文
- 重新讲子域划分
- 重新讲数据所有权原则
- 重新讲技术选型和方案取舍

本质问题：
没有真正承接上游，而是在重写架构设计第二版。

#### 错误类型 C：提前掉进详细设计
表现：
- 字段定义
- DDL
- 函数调用链
- 协议 schema
- 时序脚本
- 恢复脚本
- 部署参数

本质问题：
没有守住概要设计的“轮廓层”。

#### 错误类型 D：只有结构名，没有判断力
表现：
- 列一堆模块名
- 列一堆对象名
- 列一堆流程名
- 但没有说明为什么存在、怎么分界、如何承接

本质问题：
看起来像设计，实际上只是目录和名词堆砌。

#### 错误类型 E：把未闭环项装成已完成
表现：
- 明明还没定，就直接写进正文
- 用“后续再补”掩盖主线未闭环
- 风险和待确认事项收不住

本质问题：
用完整感掩盖不确定性。

### 10.4 正确示例（跨章节通用）

#### 正确示例 A：先承接、后展开
```text
本文承接已收稳的需求与架构边界，在此基础上继续展开主要组成部分、职责、接缝、对象与流程轮廓。
```

为什么正确：
```text
它先把概要设计放回正确层次：不是重写上游，而是在已收稳前提下继续向可实现结构展开。
```

#### 正确示例 B：轮廓足够、细节克制
```text
该部分负责承接正式输入并将其导入内部主线，但本章不展开具体协议字段与函数调用顺序。
```

为什么正确：
```text
它已经说明部分职责与结构作用，但没有提前掉进协议和实现细节。
```

#### 正确示例 C：先结构、后风险
```text
在主要部分、接缝和流程轮廓收稳后，本章再显式收纳当前仍未闭环的设计风险与待确认事项。
```

为什么正确：
```text
它说明未闭环项不是被藏起来，而是在正确位置被收口。
```

### 10.5 错误示例（跨章节通用）

#### 错误示例 A：把概要设计写成需求第二版
```text
本系统支持创建、查询、修改、删除，并满足以下用户故事……
```

错误原因：
```text
这仍然停留在需求主语，没有进入概要设计层的可实现结构主语。
```

#### 错误示例 B：把概要设计写成架构第二版
```text
系统上下文包括 A、B、C，采用事件驱动架构与最终一致模型……
```

错误原因：
```text
这在重写架构设计层，而不是承接架构边界后继续下沉到主要部分与接缝。
```

#### 错误示例 C：把概要设计写成详细设计前稿
```text
对象包含 id、status、version 字段，核心流程由 validate() -> persist() -> publish() 组成。
```

错误原因：
```text
字段、函数调用链和实现时序已经明显下沉到详细设计层。
```

#### 错误示例 D：只有名词，没有结构判断
```text
系统包括输入模块、处理模块、输出模块、对象模块、流程模块。
```

错误原因：
```text
只是名词堆砌，没有说明为什么存在、如何分界、如何协作，因此没有概要设计判断力。
```

#### 错误示例 E：把未闭环问题藏进正文
```text
当前主流程闭环已经成立，后续再逐步完善异常与恢复。
```

错误原因：
```text
如果异常与恢复仍未收稳，就不应直接宣称主流程闭环已经成立。
```

### 10.6 `identity` 辅助说明的附录规则

- 只用于映射通用规则
- 不新增判断标准
- 不代替主规则
- 不形成第二套样板正文

如果某条 `identity` 说明只是把正文再讲一遍，应删减。

# 概要设计讨论流程_SOP

> 目标：定义“概要设计内容如何生成”，用于把已收稳的需求与架构结果转译成可实现的代码主体骨架，并补足 `standards/document/概要设计书写规范.md` 仅定义结果结构、不定义生成流程的空白。
> 适用对象：人类作者、Claude/其他 Agent、多人协作讨论。  
> 与 `概要设计书写规范.md` 的关系：书写规范负责定义最终结果结构；本 SOP 负责定义章节如何被讨论、收敛和回填。

## 1. 适用前提

本 SOP 适用于：

```text
需要为一个仓 / 一个模块 / 一个子系统编写 02-概要设计.md
且希望先通过讨论逐步收敛内容，再落正式文档
```

它不适用于：

```text
重新定义需求目标与用户故事
重新定义架构边界、子域划分与技术取舍
直接展开完整字段模型、函数实现、DDL、部署参数和运维细节
```

---

## 2. 核心原则

### 2.1 先承接，后展开

概要设计不是从零开始，而是在已收稳的需求与架构边界下展开可实现结构。

### 2.2 先主体，后细节

概要设计优先收稳：

```text
代码主体框架
约束条件
主要组成部分、职责与边界
关键对象轮廓
API / 接口骨架
关键处理流 / 重要函数数据流
状态定义与状态流转
详细设计承接清单
```

而不是一上来写完整字段模型、函数实现、表结构和实现细节。

### 2.3 先骨架，后实现

概要设计可以点名正式对象名、API 名、事件名、字段骨架和函数骨架；关键字段必须写明字段类型，函数参数必须写明参数类型；但不写完整协议 schema、完整字段类型全集、函数实现、DDL 和完整调用链。

### 2.4 不重复上游

概要设计不重新发明需求目标、用户故事、系统上下文、子域划分、关键技术选型与方案取舍。

### 2.5 门禁真实生效

如果上游输入边界未收稳、当前范围未收稳、代码主体框架还说不清，就不应强行进入后续章节。

### 2.6 Step 模型统一

本 SOP 沿用已在需求线、架构线验证通过的 8 字段模型：

- 本步目标
- 本步输入
- 本步输出
- 应问的问题
- 期望产出
- 回填位置
- 执行约束
- 进入下一步的条件

### 2.7 ASCII 图输出统一

凡是本 SOP 中要求或允许输出 ASCII 图的 Step，都必须在讨论阶段同时收稳：

```text
图类型
图标题
ASCII 图正文
图后 2~5 条关键说明
```

讨论阶段禁止只说“画一个图”或只输出裸图。所有 ASCII 图必须遵守 `概要设计书写规范` 5.3.4 `ASCII 图统一格式`。

产图 Step 的最小输出结构为：

````md
#### <图类型标题>

```text
<ASCII 图正文>
```

关键说明：
- <图表达了什么结构关系>
- <图没有表达哪些详细设计内容>
- <图中最容易误解的边界是什么>
````

如果某一步按需可画图但本轮不画，必须说明“不画图的原因”，不能留下空图占位。

## 3. Step 模板的字段关系

每个 Step 都由以下字段组成：

| 字段 | 作用 |
|---|---|
| 本步目标 | 定义本步存在的意义，说明这一步要解决什么问题。 |
| 本步输入 | 定义本步开始前必须具备的前提、上游结论或已收敛结果。 |
| 本步输出 | 定义本步必须收敛出的结果类型。 |
| 应问的问题 | 用于把输入收敛成输出的问题集合，不是独立问卷。 |
| 期望产出 | 本步应交付的具体结论项，是对“本步输出”的展开。 |
| 回填位置 | 指明本步产出最终写入的规范章节或正式文档位置。 |
| 执行约束 | 规定本步过程中哪些做法允许，哪些做法禁止。 |
| 进入下一步的条件 | 判断本步是否完成的门槛。 |

### 执行顺序

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 回填位置
  -> 进入下一步的条件
```

## 4. 建议的讨论总流程

```text
Step 1. 确认上游输入边界
Step 2. 明确本仓设计目标与当前范围
Step 3. 收稳约束条件
Step 4. 代码主体框架映射
Step 5. 主要组成部分、职责与边界
Step 6. 关键对象轮廓
Step 7. API / 接口骨架
Step 8. 关键处理流 / 重要函数数据流
Step 9. 状态机与状态流转
Step 10. 异常与边界场景轮廓
Step 11. 详细设计承接清单
Step 12. 设计风险与待确认事项
Step 13. 整理正式概要设计文档
```

## 5. 每一步的讨论目标、输入与产出

> 说明：当前正式正文已补齐 Step 1 ~ Step 13 的 8 字段骨架，可作为概要设计线正式流程骨架使用；后续重点是用真实仓级样本继续校准每一步的输出粒度。

### Step 1. 确认上游输入边界

#### 本步目标
确认当前概要设计依赖的需求结论和架构结论已经收敛到足以支撑“代码主体框架、主要组成部分、对象骨架、接口骨架、关键处理流与状态机”展开的程度，并识别哪些上游边界会直接影响当前概要设计的范围与深度。

#### 本步输入
- 当前仓对应的 `00-需求文档.md`
- 当前仓对应的 `01-架构设计.md`
- 已明确的上游产品 / 全局架构 / 仓拆分相关结论（如有）
- 当前已知的本仓职责边界、主要交互边界、数据边界与非目标结论

#### 本步输出
- 上游关系映射表
- `本文不再回答` 清单
- `本文必须回答` 清单

#### 应问的问题

```text
1. 当前概要设计要承接哪些需求结论？
2. 当前概要设计要承接哪些架构结论？
3. 这些结论里，哪些已经足够稳定，可以直接作为概要设计输入？
4. 哪些结论虽然相关，但仍未收稳，因此当前不能直接往下展开？
5. 哪些边界、非目标和约束会直接决定概要设计当前不该展开到哪里？
```

#### 期望产出

```md
| 来源文档 | 承接内容 | 本文继续展开什么 |
|---|---|---|

本文不再回答：
- <已由需求 / 架构 / 全局设计收稳的问题>

本文必须回答：
- <本概要设计必须继续收稳的结构问题>
```

#### 回填位置
- `概要设计书写规范` 1 与上游文档的关系声明
- `概要设计书写规范` 2 本次设计目标与范围（仅提供前置输入，不在本步正式收口）
- `概要设计书写规范` 3 约束条件（仅识别约束线索，不在本步正式收口）

#### 执行约束
- 本步只确认“概要设计可承接什么”，不重新发明需求与架构结论。
- Step 1 只做输入边界确认，不正式收口本次设计范围与当前深度；这些应在 Step 2 完成。
- 不在本步提前展开代码主体框架、接口骨架、对象轮廓、处理流或状态机。
- 对尚未收稳的上游结论，必须明确列为“暂不进入范围”，不能为了推进概要设计而脑补定论。
- 不把详细设计层内容（完整字段、函数实现、DDL、调用链）提前当作上游输入。

#### 进入下一步的条件

```text
已明确概要设计当前承接哪些需求与架构结论，已明确本文不再回答什么、必须回答什么，且足以支撑进入“本仓设计目标与当前范围”的讨论。
```

---

### Step 2. 明确本仓设计目标与当前范围

#### 本步目标
在已经确认可承接的上游需求与架构输入前提下，明确本次概要设计要收敛到什么深度、重点把哪些代码主体、对象骨架、接口骨架、处理流和状态机讲清，以及哪些内容当前不进入概要设计范围。

#### 本步输入
- Step 1 已收敛的上游关系映射表
- Step 1 已收敛的 `本文不再回答` 清单
- Step 1 已收敛的 `本文必须回答` 清单
- 当前已知的本仓设计目标、架构边界、主要约束与非目标

#### 本步输出
- 设计目标表
- 非范围表
- 当前阶段设计深度口径

#### 应问的问题

```text
1. 本次概要设计最主要要把哪些结构说清？
2. 这一轮概要设计应停在什么深度，才算足够支撑进入详细设计？
3. 哪些内容属于本次概要设计范围？
4. 哪些内容虽然相关，但当前不进入概要设计范围？
5. 哪些内容应留给详细设计，而不应在本章提前展开？
```

#### 期望产出

```md
| 目标 | 说明 | 交付给详细设计的结果 |
|---|---|---|

| 非范围 | 留给哪一层 |
|---|---|

当前阶段设计深度口径：
- <本轮概要设计收敛到什么程度>
```

#### 回填位置
- `概要设计书写规范` 2 本次设计目标与范围

#### 执行约束
- 本步只回答“这轮概要设计要收什么、不收什么”，不提前拆对象和接口细节。
- 不把架构设计已经收稳的边界、上下文、依赖方向、数据归属重新讨论一遍。
- 不把详细设计层内容（完整字段、完整函数签名、DDL、详细时序）提前纳入“本次范围”。
- 范围必须和“当前可承接输入”一致，不能凭愿望扩大范围。
- 非范围项必须写清是“当前不进入概要设计”，而不是含糊写成“以后再看”。

#### 进入下一步的条件

```text
已明确本次概要设计要收敛哪些结构、停在什么深度、哪些内容当前不进入范围，且足以支撑进入“约束条件”的讨论。
```

---

### Step 3. 收稳约束条件

#### 本步目标
从上游输入、设计目标和非范围中提炼会直接影响概要设计结构的硬约束，避免后续对象、接口、处理流和状态机越界。

#### 本步输入
- Step 1 已收敛的上游关系映射表
- Step 1 已收敛的 `本文不再回答` / `本文必须回答` 清单
- Step 2 已收敛的设计目标表
- Step 2 已收敛的非范围表
- 当前已知的数据归属、跨仓边界、安全边界、状态传播边界和只读查询边界

#### 本步输出
- 约束条件表

#### 应问的问题

```text
1. 哪些约束会直接影响本仓对象、接口、处理流或状态机设计？
2. 哪些约束来自需求文档，哪些约束来自架构设计或全局设计？
3. 哪些边界如果不先写清，后续最容易串到相邻仓或详细设计？
4. 哪些约束只是泛化工程原则，不应进入本章？
5. 每条约束是否能指导后续章节的设计判断？
```

#### 期望产出

```md
| 约束 | 说明 |
|---|---|
```

#### 回填位置
- `概要设计书写规范` 3 约束条件

#### 执行约束
- 本步只收稳会影响概要设计结构的硬约束。
- 约束必须能指导后续代码主体、对象、接口、处理流或状态机判断。
- 不把上游架构全文复述为约束。
- 不写与本仓概要设计无关的泛化工程原则。
- 不把详细设计实现策略、数据库约束或部署约束提前写入本步。

#### 进入下一步的条件

```text
已明确后续概要设计必须遵守的结构性约束，且每条约束都能影响后续章节判断，足以支撑进入“代码主体框架映射”的讨论。
```

### Step 4. 代码主体框架映射

#### 本步目标
把架构设计中已经收稳的模块、边界和主线，转译为后续详细设计可以继续展开的代码主体框架，明确业务主要组成部分与实现分层之间的关系。

#### 本步输入
- Step 2 已收敛的本次概要设计目标与范围
- Step 3 已收敛的约束条件
- 架构设计中已经收稳的主要模块、主线闭环和边界
- 当前仓已知的入口类型、核心处理主体、只读供给主体、传播 / 持久化 / 投影主体线索

#### 本步输出
- 架构模块到代码主体映射图
- 实现分层视图
- 业务主要组成部分与实现分层的关系说明
- 关键判断小节

#### 应问的问题

```text
1. 架构层已经收稳的模块，分别应落到哪些代码主体骨架上？
2. 哪些主体属于 Inbound / Operations，哪些属于 Application Services？
3. 哪些主体属于 Domain Model，哪些属于 Ports / Persistence / Projection / Outbox？
4. 哪些名称必须在概要设计层先点名，否则详细设计会重新发明主语？
5. 哪些内容已经是代码目录、文件路径或框架实现，不应在本步展开？
```

#### 期望产出

````md

<按统一 ASCII 图格式输出>
```

关键说明：

- <说明该图不表达目录、文件路径或完整实现定义>

#### 实现分层视图

```text
<按统一 ASCII 图格式输出>
```

关键说明：
- <说明业务主要组成部分和实现分层的关系>
- <说明该图不表达具体框架、目录或部署结构>

业务主要组成部分与实现分层关系说明
关键判断小节：
- 哪些名称是业务主要组成部分
- 哪些名称只是实现分层
- 为什么二者不能混用
````

#### 回填位置
- `概要设计书写规范` 4 代码主体框架总览

#### 执行约束
- 可以点名正式服务、聚合、对象、投影、outbox、port、job。
- 必须区分“业务主要组成部分”和“Inbound / Application / Domain / Ports”等实现分层。
- 本步必须产出两张 ASCII 图：`架构模块到代码主体映射图` 和 `实现分层视图`。
- 两张图都必须使用 `text` 代码块，并在图后写 2~5 条关键说明。
- 两张图必须遵守 `概要设计书写规范` 5.3.4 `ASCII 图统一格式`。
- 不写具体代码目录和文件路径。
- 不写完整 trait / struct 定义。
- 不把外部系统上下文对象当成本仓内部代码主体。

#### 进入下一步的条件

```text
已明确架构模块如何映射为代码主体骨架，已明确业务主要组成部分与实现分层的关系，且没有提前下沉到代码目录、文件路径或完整实现定义，足以支撑进入“主要组成部分、职责与边界”的讨论。
```

### Step 5. 主要组成部分、职责与边界

#### 本步目标
在代码主体框架已经初步明确的前提下，收稳本仓的主要组成部分，说明每个部分承担什么、不承担什么，以及它们之间通过什么边界彼此分开。

#### 本步输入
- Step 4 已收敛的代码主体框架映射
- Step 4 已收敛的实现分层视图
- 架构设计中已收稳的职责边界、主要交互边界和数据边界

#### 本步输出
- 组成部分总表
- 各部分交互总图
- 每个主要组成部分的独立小节
- 每个组成部分的代码主体 / 模块表
- 总体边界说明
- 后续展开一致性检查结论

#### 应问的问题

```text
1. 当前概要设计层面，本仓应被划分为哪些主要组成部分？
2. 每个主要组成部分分别承担什么职责？
3. 每个主要组成部分明确不承担什么职责？
4. 每个主要组成部分包含哪些代码主体 / 模块？
5. 这些代码主体 / 模块在本部分中只需要说明到什么粒度？
6. 哪些内容虽然相关，但必须由相邻部分或边界外能力承担？
7. 哪些职责如果不写清，后续最容易让概要设计滑进实现层或让不同部分串线？
```

#### 期望产出

````md
| 组成部分 | 核心职责 | 主要代码主体 | 不承担什么 |
|---|---|---|---|

#### 各部分交互总图

```text
````

### Step 12. 设计风险与待确认事项

#### 本步目标

```text

4. 哪些问题若不先收纳，后续详细设计会被误导？
```

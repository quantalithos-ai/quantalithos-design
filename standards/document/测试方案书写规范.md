# 测试文档书写规范

> 测试文档回答 **"如何证明它做对了、在哪些条件下算通过、出了问题如何复现与定位"**。  
> 它把需求与设计转成可执行的验证活动，直接指导测试实施、回归和放行决策。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)  
> 设计输入见 → [详细设计书写规范](详细设计书写规范.md)  

---

## 一、测试文档的目标

测试文档的核心目标是**让测试、开发、产品、运维在不依赖口头补充的情况下，对“测什么、怎么测、测到什么程度算通过”形成一致理解**。为此，它至少要解决六个问题：

1. **测试范围**：本次验证哪些功能、流程、风险点，不验证什么
2. **测试策略**：采用哪些测试层级和方法，手工测还是自动测，冒烟/回归/专项如何组织
3. **测试条件**：在哪个环境、什么配置、什么数据下执行，哪些前提必须满足
4. **测试判定**：进入准则、退出准则、通过标准、阻塞标准是什么
5. **问题闭环**：失败后如何记录、分类、升级、回归验证
6. **证据留存**：如何形成测试报告、覆盖矩阵、缺陷记录、自动化报告等可审计证据

> **测试文档的终极检验标准**：一个未参与项目的测试人员，仅凭需求文档 + 设计文档 + 测试文档，能否独立完成测试准备、执行、缺陷上报、结果汇报与放行建议？如果不能，说明测试文档还不够细。

> **与详细设计中的“测试设计”区别**：详细设计里的“测试设计”是站在实现者视角，说明系统应暴露哪些验证切口；本规范关注的是测试团队如何组织测试计划、测试用例、测试执行与测试报告。

## 二、测试文档必须包含的模块

```
┌─────────────────────────────────────────────────────────────┐
│                   测试文档结构                                 │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 文档元信息与文档类型声明                                 │
│     - 标题 / 作者 / 日期 / 状态 / 目标版本 / 目标构建         │
│     - 本文档是测试计划 / 测试用例集 / 测试报告 / 综合文档       │
│     - 数据来源声明（如“接口来自 OpenAPI，状态机来自详细设计”） │
│                                                             │
│  2. 测试对象与范围                                           │
│     - 测试对象（模块 / 服务 / 版本 / 变更点）                 │
│     - 测试范围 / 非范围 / 优先级                             │
│                                                             │
│  3. 测试策略与测试分层                                       │
│     - 单元 / 集成 / API / 端到端 / 探索 / 验收 / 专项         │
│     - 手工 vs 自动化的边界                                   │
│     - 风险驱动策略与测试金字塔                               │
│                                                             │
│  4. 需求追溯与覆盖矩阵                                       │
│     - 需求 ID ↔ 设计章节 ↔ 测试场景 ↔ 测试用例 ↔ 缺陷 ↔ 报告   │
│     - 明确哪些风险已覆盖、哪些风险未覆盖                     │
│                                                             │
│  5. 测试环境与配置矩阵                                       │
│     - 环境拓扑、依赖服务、版本、开关、浏览器/设备矩阵         │
│     - 环境约束、时钟、地域、账号、权限                       │
│                                                             │
│  6. 测试数据设计                                             │
│     - 基础数据、边界数据、异常数据、并发数据、脱敏策略         │
│     - 数据生成、回收、复用、隔离方式                         │
│                                                             │
│  7. 测试用例设计                                             │
│     - 前置条件 / 步骤 / 输入 / 预期结果 / 断言点              │
│     - 优先级 / 自动化候选 / 责任人 / 关联需求                 │
│                                                             │
│  8. 进入准则与退出准则                                       │
│     - 开始测试前必须满足什么                                 │
│     - 何时可以结束测试并给出结论                             │
│                                                             │
│  9. 执行计划与资源安排                                       │
│     - 测试轮次 / Milestone / 套件 / 人员 / 工时 / 日程         │
│     - 配置分配与测试矩阵                                     │
│                                                             │
│  10. 缺陷管理与异常升级                                      │
│     - 严重级别 / 优先级 / 状态流转 / 升级路径 / SLA           │
│     - 区分产品缺陷、环境问题、用例问题、需求缺口             │
│                                                             │
│  11. 自动化与 CI/CD 集成                                     │
│     - 哪些场景自动化、在哪个流水线跑、失败如何处理            │
│     - 报告、覆盖率、Flaky 策略、门禁阈值                     │
│                                                             │
│  12. 专项测试与非功能验证                                    │
│     - 性能 / 安全 / 兼容性 / 可用性 / 可恢复性 / 可观测性      │
│     - 指标、方法、负载模型、阈值、环境、证据                 │
│                                                             │
│  13. 测试报告与证据归档                                      │
│     - 执行结果、通过率、缺陷分布、残余风险、放行建议          │
│     - 截图、日志、自动化报告、覆盖率、录屏、压测结果          │
│                                                             │
│  14. 回归策略与残余风险                                      │
│     - 变更影响分析、最小回归集、全量回归触发条件              │
│     - 已知未关闭风险与风险接受记录                           │
│                                                             │
│  15. 从设计到测试的实施路线图                                │
│     - 从需求/设计输入到测试准备、执行、留证、放行的顺序       │
│                                                             │
└─────────────────────────────────────────────────────────────┘

注意：测试文档不是单一工件。复杂项目至少会拆成三类工件：
- **测试计划/策略**：回答“测什么、怎么组织”
- **测试用例/测试步骤**：回答“具体怎么测”
- **测试报告/测试记录**：回答“测得怎么样、是否建议放行”

注意：测试文档超过 1500 行时，应按测试计划、测试用例集、专项测试方案、测试报告拆分为子文档，每份独立可读。
```

## 三、测试文档的输入与输出

| 维度 | 输入材料 | 输出内容 |
|------|---------|---------|
| 需求 | 需求文档、用户故事、验收标准 | 测试范围、场景清单、覆盖矩阵 |
| 设计 | 概要设计、详细设计、接口文档、状态机 | 测试策略、测试点、接口用例、状态流转用例 |
| 变更 | 变更单、提交记录、PR、发布说明 | 影响分析、回归策略、增量测试集 |
| 环境 | 环境清单、部署配置、测试账号、依赖 SLA | 环境矩阵、数据准备、前置条件 |
| 质量 | 缺陷历史、事故复盘、风险清单 | 高风险回归集、专项测试计划 |
| 自动化 | CI/CD 流程、测试框架、覆盖率工具 | 自动化门禁方案、报告归档规范 |

## 四、各模块编写要点

### 4.1 文档元信息与文档类型声明

**必须先声明文档类型**，否则测试计划、测试用例、测试报告很容易写混。

建议在文档开头明确：
- 本文档是 `测试计划`、`测试用例集`、`测试报告`，还是三者合并的综合文档
- 目标对象是哪个版本、哪个构建、哪个分支、哪个发布批次
- 关联哪些需求、哪些设计文档、哪些接口定义
- 数据来源是什么，并注明“如需求/设计/接口发生变更，本文档须同步更新”

**编写要点**：
- 文档元信息至少包含：标题、作者、评审人、状态、日期、目标版本、目标构建号
- 测试对象必须可定位：如 `order-service v1.6.2 build-314`，而不是“订单模块最新版本”
- 数据来源声明要写到文件级或系统级，如“接口字段来自 `openapi/order.yaml`，状态流转来自 `详细设计书写规范.md` 对应模块”
- 综合文档必须在目录或导航中明确区分“计划、用例、报告”三个部分

**推荐附加项**：

| 时间预算 | 阅读路径 |
|---------|---------|
| 10 分钟 | §2、§3、§8、§13（范围、策略、准则、结论） |
| 30 分钟 | 本文档全文 |
| 2 小时  | + 关联需求 + 详细设计 + 自动化报告 |

### 4.2 测试对象与范围

测试范围不是简单罗列“测登录、测下单、测支付”，而是**把本次验证边界说清楚**。

**编写要点**：
- 明确测试对象：模块、服务、端、版本、发布批次
- 明确测试范围：本次改动覆盖哪些需求、接口、状态转换、权限规则、配置项
- 明确非范围：哪些功能本次不测，为什么不测，风险由谁承担
- 按优先级标记：`P0` 核心路径、`P1` 主要路径、`P2` 次要路径
- 区分“本次不测”与“无法测试”——后者必须写成风险，而不是轻描淡写跳过

**范围表示例**：

| 范围项 | 类型 | 优先级 | 说明 |
|--------|------|--------|------|
| 创建订单主流程 | 功能 | P0 | 用户下单成功、库存预扣、订单入库 |
| 支付回调状态流转 | 状态机 | P0 | `CREATED -> PAID` 及非法重复回调 |
| 库存不足失败路径 | 异常 | P0 | 需验证错误码、回滚、副作用 |
| 优惠券跨店铺核销 | 非范围 | — | 本次需求未改动，不纳入本轮 |
| 海外站多币种结算 | 风险项 | — | 环境缺失，需单列残余风险 |

> **关键原则**：测试范围必须以**需求 ID、接口 ID、状态节点、风险项**为锚点，而不是以“页面感觉差不多”这种模糊描述为锚点。

### 4.3 测试策略与测试分层

好的测试文档不只是列出“有哪些用例”，而是先回答：**为什么这类问题要在这个层级被发现**。

**编写要点**：
- 明确测试分层：单元、组件/模块、接口、集成、端到端、探索、验收、专项
- 明确每一层的目标、责任人、执行时机、门禁作用
- 手工测试与自动化测试要划边界：什么适合自动化，什么保留手工探索
- 采用风险驱动思路：高频、高损失、高耦合路径优先自动化和回归
- 写明测试金字塔，避免“全部靠 UI 回归”或“只有单测没有集成测试”

**测试分层示例**：

| 层级 | 目标 | 责任 | 典型内容 | 通过标准 |
|------|------|------|---------|---------|
| 单元测试 | 约束函数级规则 | 开发 | 纯业务规则、边界值、异常抛出 | 核心模块覆盖率达标 |
| 接口/契约测试 | 约束接口语义 | 开发 + 测试 | 请求校验、错误码、幂等、兼容性 | 接口契约无回归 |
| 集成测试 | 验证模块协作 | 开发 + 测试 | DB、缓存、MQ、第三方依赖交互 | 关键协作路径通过 |
| 端到端测试 | 验证用户主流程 | 测试 | 登录、下单、支付、退款等完整路径 | P0 场景通过 |
| 探索测试 | 发现未知风险 | 测试 | 组合操作、异常时序、体验问题 | 关键疑点有结论 |
| 专项测试 | 验证 NFR | 测试 + SRE + 安全 | 性能、安全、兼容、恢复 | 指标达到阈值 |

**测试金字塔示意**：

```
                 ┌────────────────────┐
                 │   验收 / 探索测试   │  数量少，覆盖关键业务风险
                 └─────────┬──────────┘
                           │
               ┌───────────▼───────────┐
               │     端到端 / 集成测试   │  覆盖关键链路与协作边界
               └───────────┬───────────┘
                           │
             ┌─────────────▼─────────────┐
             │   接口 / 契约 / 组件测试    │  覆盖多数业务规则与协议
             └─────────────┬─────────────┘
                           │
           ┌───────────────▼───────────────┐
           │          单元测试               │  数量最多，反馈最快
           └───────────────────────────────┘
```

> **社区共识**：测试计划是高层策略文档，测试用例是具体执行文档。测试计划负责范围、目标、资源、排期、风险；测试用例负责前置条件、步骤、数据、预期结果。不要把二者混成一篇没有层次的流水账。

### 4.4 需求追溯与覆盖矩阵

覆盖率不是“写了多少条用例”，而是**关键需求和关键风险是否都有验证路径**。

**编写要点**：
- 每个需求必须能追到测试场景和测试用例；每个高风险点必须能追到验证证据
- 覆盖矩阵必须显式展示未覆盖项，而不是只展示已覆盖项
- 缺陷也应能回链到需求或设计点，避免“提了 bug 但不知道影响什么”
- 自动化与手工覆盖要区分标注，防止误判覆盖情况
- 对状态机、并发、权限、兼容性等高风险维度，建议单独建追溯列

**追溯矩阵示例**：

| 需求 ID | 设计输入 | 测试场景 | 用例 ID | 方式 | 结果证据 | 缺陷 | 备注 |
|---------|---------|---------|--------|------|---------|------|------|
| REQ-001 | 订单创建主流程 | 用户成功下单 | TC-ORDER-001 | 自动化 API | `report/api/order.html` | — | 已覆盖 |
| REQ-002 | 订单状态机 | 重复支付回调 | TC-ORDER-017 | 手工 + 自动化 | `logs/pay-callback.log` | BUG-132 | 已修复待回归 |
| REQ-003 | 幂等设计 | 重复提交创建订单 | TC-ORDER-023 | 自动化集成 | `report/idem.json` | — | 已覆盖 |
| RISK-005 | 并发一致性 | 同 SKU 并发下单 | TC-STOCK-004 | 专项压测 | `jmeter/stock.jtl` | — | 已覆盖 |
| REQ-008 | 海外多币种 | 订单金额换算 | — | 未覆盖 | — | — | 环境缺失，转残余风险 |

> **关键原则**：没有追溯，就没有覆盖证明；没有未覆盖项，就说明矩阵在掩盖问题。

### 4.5 测试环境与配置矩阵

同一套用例在不同环境、不同配置下可能得到完全不同的结果。环境不清，是测试文档最常见的失真来源之一。

**编写要点**：
- 写清环境名称、部署版本、依赖服务版本、配置开关、测试账号、权限模型
- 涉及前端时，明确浏览器、操作系统、分辨率、设备类型
- 涉及后端时，明确数据库版本、缓存版本、中间件版本、第三方沙箱环境
- 涉及时序逻辑时，明确时区、系统时间、延迟注入、定时任务触发方式
- 测试环境限制也要写明，如“压测仅允许在 perf 环境进行”

**环境矩阵示例**：

| 环境 | 目标 | 版本/构建 | 关键依赖 | 配置差异 | 使用场景 |
|------|------|-----------|---------|---------|---------|
| `dev` | 开发自测 | 本地最新 | Mock 支付 / 本地 DB | Debug 开关开启 | 开发联调 |
| `test` | 功能测试 | build-314 | 测试库存 / 测试 MQ | Trace 开启、限流关闭 | 主功能回归 |
| `staging` | 预发验证 | build-314-rc1 | 类生产依赖 | 限流、熔断、鉴权开启 | 放行前验证 |
| `perf` | 性能专项 | build-314-perf | 独立压测 DB | 监控采样增强 | 压测 / 容量验证 |

**兼容配置矩阵示例**：

| 维度 | 配置集合 | 是否必须覆盖 |
|------|---------|-------------|
| 浏览器 | Chrome、Firefox、Safari | Web 必须 |
| 移动端 | iOS 17、Android 14 | App/H5 必须 |
| 数据库 | MySQL 8.0、PostgreSQL 15 | 多数据库产品必须 |
| 地域 | 北京、上海、海外节点 | 涉及时区/网络差异时必须 |

### 4.6 测试数据设计

没有测试数据设计，测试用例通常会退化成“理想路径演示”，而不是有效验证。

**编写要点**：
- 按类型设计数据：正常数据、边界数据、非法数据、缺失数据、重复数据、并发数据、权限隔离数据
- 数据要有生命周期：谁创建、谁维护、何时清理、能否复用
- 敏感数据必须脱敏，不能把生产实名数据直接抄进测试环境
- 对幂等、并发、定时任务、状态机等场景，要准备专门数据集
- 数据准备步骤要可重复执行，避免“靠某个人记忆准备”

**测试数据表示例**：

| 数据集 | 用途 | 内容 | 生成方式 | 清理方式 |
|--------|------|------|---------|---------|
| `seed_order_normal` | 主流程 | 正常用户、正常库存、有效地址 | SQL 脚本 | 执行后保留复用 |
| `seed_order_boundary` | 边界值 | 50 个行项、超长地址、金额边界 | 工具脚本 | 当日清理 |
| `seed_order_invalid` | 异常输入 | 缺失 userId、非法 couponId | API 构造 | 无需清理 |
| `seed_order_concurrent` | 并发 | 同一 SKU 低库存、多用户并发下单 | 压测脚本 | 场景后回滚库存 |
| `seed_order_permission` | 权限 | 普通用户、运营、管理员账号 | 账号平台 | 定期重置密码 |

> **关键原则**：测试数据不是附件，而是测试设计的一部分。没有数据设计，就无法稳定复现问题，也无法保证回归结果可信。

### 4.7 测试用例设计

测试用例是测试文档中最容易写成“操作说明书”的部分，但真正好的用例应当表达**验证意图**而不只是操作步骤。

**编写要点**：
- 每条用例必须至少包含：`用例 ID`、`标题`、`优先级`、`前置条件`、`步骤`、`输入/数据`、`预期结果`、`断言点`、`关联需求`、`责任人`
- 预期结果必须落到可观测事实：返回码、数据库状态、事件发送、页面提示、日志、监控指标等
- 设计态用例只写**预期结果**；执行记录再补充**实际结果**、执行状态、证据链接
- 尽量让一条用例只验证一个核心规则或一个失败原因，避免“一条用例断言十件事”导致定位困难
- 必须覆盖：主流程、替代流程、异常分支、边界值、状态机非法转换、权限场景、幂等场景

**推荐用例模板**：

```text
Case ID: TC-ORDER-017
Title: 已支付订单收到重复支付回调时不应重复扣账
Priority: P0
Type: API / 状态机 / 幂等
Preconditions:
  - 订单 O1001 状态为 PAID
  - 支付平台回调签名有效
Test Data:
  - orderId=O1001
  - callbackId=CB20260512001
Steps:
  1. 调用 POST /api/v1/payment/callback，传入已支付订单 O1001 的回调请求
  2. 再次以相同 callbackId 重放相同请求
Expected Results:
  1. 第一次请求返回 200，响应语义为“已处理/幂等成功”
  2. 第二次请求返回 200 或业务幂等码，不得重复扣账
  3. t_order.status 保持 PAID，不发生二次状态跳转
  4. 不新增重复支付流水，不重复发送 OrderPaidEvent
Assertions:
  - 接口响应码与业务码符合约定
  - 数据库支付流水条数不增加
  - MQ 中无重复事件
Related Requirement: REQ-002
Automation Candidate: Yes
Owner: qa.order
```

**常见错误**：
- 只写“点击按钮，页面正常”——没有可判定标准
- 只测正常路径，不测异常与边界
- 预期结果停留在 UI 提示，未检查后端状态与副作用
- 用例标题写成“测试订单功能”——信息量过低

### 4.8 进入准则与退出准则

进入/退出准则是测试文档中的“门禁系统”。没有它，测试开始和结束都只能靠感觉。

**编写要点**：
- 进入准则必须可检查，例如“接口文档冻结”“测试环境可用”“核心依赖可访问”“冒烟通过”
- 退出准则必须可量化，例如“P0/P1 用例通过率 >= 95%”“Blocker/Critical 缺陷为 0”
- 退出准则要说明例外处理：未满足时谁可以接受风险并放行
- 不允许使用“基本稳定”“大体没问题”“先上线再说”等模糊描述

**进入/退出准则示例**：

| 类型 | 条件 | 判定方式 |
|------|------|---------|
| 进入准则 | 需求与设计评审通过 | 有评审记录 |
| 进入准则 | 测试环境、账号、数据已准备完成 | 清单打勾完成 |
| 进入准则 | 构建成功，核心冒烟用例通过 | CI 报告通过 |
| 进入准则 | 外部依赖沙箱可用 | 联调检查通过 |
| 退出准则 | 所有 P0 用例通过 | 报告汇总 |
| 退出准则 | P1 用例通过率 >= 95% | 报告统计 |
| 退出准则 | Blocker/Critical 缺陷 = 0 | 缺陷系统查询 |
| 退出准则 | 未关闭风险已明确记录并被接受 | 风险接受记录 |

> **关键原则**：退出准则不是“没有发现问题”，而是“关键目标已验证、未解决问题已被显式接受”。

### 4.9 执行计划与资源安排

测试文档不仅要告诉测试人员“测什么”，还要告诉团队**什么时候测、谁来测、按什么轮次推进**。

**编写要点**：
- 以 Sprint、Milestone 或发布批次组织测试计划
- 按测试套件或场景分配责任人，而不是笼统写“QA 团队负责”
- 对不同配置矩阵分配测试人员和时间预算
- 对可复用用例采用“引用已有用例 + 新建测试计划”的方式，避免每轮都复制一套分叉用例
- 写明依赖阻塞关系，例如“支付沙箱未就绪前，只能完成本地 Mock 回归”

**执行计划示例**：

| 阶段 | 时间 | 内容 | 责任人 | 检查点 |
|------|------|------|--------|-------|
| 冒烟 | Day 1 | 核心接口、主流程、环境连通性 | QA-A | 冒烟通过 |
| 功能回归 | Day 2-3 | P0/P1 场景、异常路径、权限场景 | QA-A / QA-B | P0 完成 |
| 集成联调 | Day 3 | 支付、库存、MQ 联调 | QA-C | 外部依赖联通 |
| 专项测试 | Day 4 | 性能、兼容性、安全检查 | QA-D / SRE | 指标达标 |
| 放行复核 | Day 5 | 回归缺陷、汇总结论、放行建议 | QA Lead | 测试报告输出 |

**配置分配示例**：

| 套件 | 配置 | 执行人 | 备注 |
|------|------|--------|------|
| Web 主流程 | Chrome / Windows | QA-A | 自动化 + 手工抽检 |
| Web 兼容性 | Safari / macOS | QA-B | 仅核心路径 |
| API 幂等 | test 环境 | QA-C | 自动化 nightly |
| 性能基准 | perf 环境 | QA-D | 禁止与功能测试混跑 |

### 4.10 缺陷管理与异常升级

测试活动不是“发现问题就丢给开发”，而是**把问题结构化描述并推动闭环**。

**编写要点**：
- 必须定义严重级别（Severity）和优先级（Priority），二者不要混用
- 缺陷单至少包含：环境、步骤、输入、预期、实际、日志/截图、复现概率、影响范围、归属判断
- 必须区分四类问题：产品缺陷、环境问题、测试用例问题、需求/设计缺口
- 要定义升级路径：谁可以判定 blocker、谁决定延期、谁接受风险
- 对测试中发现的问题，建议记录“首次发现版本”“修复版本”“回归结论”

**严重级别示例**：

| 严重级别 | 含义 | 例子 |
|---------|------|------|
| Blocker | 阻塞测试或阻塞核心业务 | 服务不可用、数据破坏、无法登录 |
| Critical | 核心功能错误且无替代路径 | 重复扣款、订单状态错乱 |
| Major | 主要功能异常但有替代路径 | 优惠券不可用、部分页面报错 |
| Minor | 局部问题，对主流程影响有限 | 文案错误、样式错位 |
| Trivial | 建议优化 | 对齐、提示词不一致 |

**测试期问题记录至少应包含的信息**（参考问题报告实践）：
- 触发步骤、输入数据、预期结果、实际结果
- 出现问题的具体步骤号
- 环境、时间、版本、构建号
- 是否尝试复现、复现频率、观察者
- 相关日志、截图、录屏、请求响应、监控快照

> **关键原则**：无法复现的问题不等于不存在，但必须把“复现条件未知”写清楚；不能只写一句“偶现”。

### 4.11 自动化与 CI/CD 集成

自动化不是“把手工步骤录一遍”，而是**把高价值、可重复、稳定的验证路径前移成门禁**。

**编写要点**：
- 写清哪些场景自动化，哪些保留手工探索，以及原因
- 明确自动化运行位置：本地、PR 流水线、合并后流水线、夜间回归、发布前回归
- 明确失败处理：真实失败 vs Flaky，谁负责判定和修复
- 指定报告归档方式：HTML 报告、JUnit XML、覆盖率、截图、日志
- 明确门禁阈值：如“PR 必须通过单测和契约测试”“发布前必须通过 P0 自动化回归”

**自动化分层示例**：

| 层级 | 触发时机 | 内容 | 目标 |
|------|---------|------|------|
| PR 门禁 | 每次提交 | 单测、静态检查、轻量接口测试 | 快速拦截明显回归 |
| 合并后 | 每次合并主干 | 核心 API 回归、契约测试、冒烟 | 保证主干可用 |
| Nightly | 每晚 | 扩展回归集、兼容性集、数据校验 | 发现慢性回归 |
| 发布前 | RC 阶段 | P0/P1 全量回归、专项测试 | 支撑放行决策 |

**常见错误**：
- 只写工具名，不写覆盖范围和门禁策略
- 自动化失败后没有归属人，报告长期红着没人管
- 把高波动 UI 录制脚本当作唯一回归手段

### 4.12 专项测试与非功能验证

很多团队的测试文档只写功能用例，但真正导致线上事故的往往是性能、容量、权限、兼容性、恢复能力等非功能问题。

**编写要点**：
- 对每一类专项测试，至少写清：目标、场景、负载模型、数据量、环境、工具、指标阈值、证据输出
- 性能测试必须说明：并发模型、请求比例、压测时长、预热方式、观测指标、瓶颈定位方法
- 安全测试必须说明：鉴权、越权、输入校验、敏感信息暴露、审计日志
- 兼容性测试必须说明：浏览器/设备/操作系统/协议版本矩阵
- 可恢复性测试必须说明：依赖超时、节点重启、消息堆积、回滚恢复等场景

**专项测试表示例**：

| 类型 | 核心问题 | 指标/阈值 | 证据 |
|------|---------|----------|------|
| 性能 | 高峰时下单链路是否满足 SLA | `P99 < 300ms`，错误率 `< 0.1%` | 压测报告 + 仪表盘截图 |
| 安全 | 是否存在越权和敏感信息泄露 | 0 个高危漏洞 | 扫描报告 + 人工验证记录 |
| 兼容 | 核心页面在主流浏览器可用 | Chrome/Firefox/Safari 全通过 | 兼容矩阵 |
| 恢复 | 库存服务超时后能否降级和恢复 | 降级生效，恢复后无数据错乱 | 演练记录 + 日志 |
| 可观测 | 失败时能否定位问题 | Trace、日志、指标完整 | 链路追踪截图 |

> **关键原则**：专项测试要验证“系统在压力和异常下怎么表现”，而不是只验证“系统在理想条件下能工作”。

### 4.13 测试报告与证据归档

测试报告不是流水账，它的核心作用是**传达结论与决策依据**。

**编写要点**：
- 报告必须包含：范围、方法、环境、执行摘要、结果、未关闭问题、残余风险、建议结论
- 报告应说明“如何得到这些结果”，而不是只贴一个通过率
- 报告要显式写出未测试项和未覆盖风险，避免给出虚假的“全部通过”印象
- 证据归档要可检索：报告链接、日志路径、截图、录屏、自动化报告、压测结果、覆盖率结果
- 报告必须服务于决策：建议放行 / 建议有条件放行 / 建议不放行

**测试报告摘要示例**：

| 维度 | 结果 |
|------|------|
| 测试范围 | 覆盖 REQ-001 ~ REQ-008，共 47 条用例 |
| 执行结果 | 通过 43，失败 2，阻塞 2 |
| 缺陷分布 | Blocker 0，Critical 1，Major 2，Minor 3 |
| 未覆盖项 | 海外多币种换算，原因：环境未就绪 |
| 残余风险 | 高并发库存回补仅在 perf 环境验证一次 |
| 建议 | 修复 BUG-132 后回归，完成后可有条件放行 |

**证据清单至少应包含**：
- 自动化测试报告链接
- 缺陷单列表
- 关键日志 / Trace ID
- 截图 / 录屏 / 抓包文件
- 覆盖率或覆盖矩阵
- 压测结果 / 安全扫描结果 / 兼容矩阵

> **标准经验**：报告除了“结果”外，还应该包含“方法、上下文、假设、结论、建议”。没有上下文的结果不具备决策价值。

### 4.14 回归策略与残余风险

回归不是“每次都全量重测一遍”，而是**围绕变更影响和历史风险构建最小可信回归集**。

**编写要点**：
- 每次测试前先做影响分析：改了哪些模块、接口、配置、状态机、依赖
- 明确最小回归集：核心主路径、高风险历史缺陷、关联上下游、配置开关影响路径
- 明确全量回归触发条件：大版本发布、底层框架升级、核心状态机变更、数据库迁移等
- 残余风险必须结构化记录：影响范围、触发条件、缓解措施、接受人

**回归策略示例**：

| 变更类型 | 最小回归集 | 是否全量回归 |
|---------|-----------|-------------|
| 文案 / 样式调整 | 页面展示 + 关键入口冒烟 | 否 |
| 接口字段新增 | 契约测试 + 上下游联调 | 视影响 |
| 状态机逻辑调整 | 主流程 + 异常流 + 非法转换 | 建议 |
| DB 迁移 / 索引调整 | CRUD + 并发 + 性能基准 | 必须 |
| 基础组件升级 | 受影响模块全回归 + 专项验证 | 建议全量 |

**残余风险示例**：

| 风险 | 原因 | 影响 | 缓解措施 | 接受人 |
|------|------|------|---------|-------|
| 海外时区订单取消未覆盖 | 海外环境不可用 | 可能出现时间边界问题 | 上线后灰度观察 + 日志告警 | 产品负责人 |
| Safari 长列表性能未专项验证 | 设备资源不足 | 个别用户体验波动 | 首批灰度仅开放 Chrome/Firefox | 技术负责人 |

### 4.15 从设计到测试：实施路线图

测试文档写完后，应该能直接指导团队从输入到放行结论的执行顺序。建议采用如下路线图：

```
┌──────────────────────────────────────────────────────────────┐
│  从设计到测试的实施路线图                                      │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  第 1 步：定边界（Day 0）                                     │
│  ─────────────────────                                       │
│  输入：需求文档 + 详细设计 + 变更清单                         │
│  动作：                                                       │
│    1. 圈定本次测试对象、测试范围、非范围                      │
│    2. 识别高风险路径、状态机、幂等、并发、权限场景            │
│    3. 建立需求追溯矩阵初稿                                    │
│  检查点：测试范围与高风险场景达成一致                         │
│                                                              │
│  第 2 步：备条件（Day 0-1）                                   │
│  ──────────────────────                                      │
│  输入：环境清单 + 配置 + 测试账号 + 数据需求                  │
│  动作：                                                       │
│    1. 搭建/确认测试环境与配置矩阵                             │
│    2. 准备测试数据与回收脚本                                  │
│    3. 定义进入准则                                            │
│  检查点：环境、账号、数据可重复准备                           │
│                                                              │
│  第 3 步：设计用例（Day 1-2）                                 │
│  ──────────────────────                                      │
│  输入：测试策略 + 追溯矩阵                                    │
│  动作：                                                       │
│    1. 编写 P0/P1 核心用例                                     │
│    2. 补异常、边界、状态机非法转换用例                        │
│    3. 标记自动化候选                                          │
│  检查点：关键需求、关键风险均有对应测试场景                   │
│                                                              │
│  第 4 步：接自动化（Day 2-3）                                 │
│  ──────────────────────                                      │
│  输入：用例集 + CI/CD 流水线                                  │
│  动作：                                                       │
│    1. 将稳定高频场景接入 PR / Nightly / Release 流水线        │
│    2. 配置报告与证据归档                                      │
│    3. 建立失败分诊与 Flaky 处理规则                           │
│  检查点：自动化门禁能稳定产出可读报告                         │
│                                                              │
│  第 5 步：执行与闭环（Day 3-5）                               │
│  ──────────────────────                                      │
│  输入：测试计划 + 缺陷流程                                    │
│  动作：                                                       │
│    1. 按轮次执行冒烟、功能、联调、专项测试                    │
│    2. 提交缺陷并跟踪修复                                      │
│    3. 完成修复回归与最小回归集验证                            │
│  检查点：关键缺陷关闭、回归通过                               │
│                                                              │
│  第 6 步：出结论（Day 5+）                                    │
│  ─────────────────────                                       │
│  输入：测试结果 + 缺陷现状 + 残余风险                          │
│  动作：                                                       │
│    1. 输出测试报告与证据清单                                  │
│    2. 记录未覆盖项和残余风险                                  │
│    3. 给出放行建议或阻塞建议                                  │
│  检查点：测试结论可审计、可追溯、可支撑发布决策               │
│                                                              │
│  原则：                                                       │
│  · 先定范围，再备环境，再写用例，再执行回归                   │
│  · 先解决“能不能测”，再解决“测得够不够深”                     │
│  · 每一步都要留下证据，不接受口头“测过了”                     │
│  · 如果某一步卡住，优先回看需求/设计是否不清                   │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

## 五、测试文档评审清单

- [ ] 是否明确声明了文档类型（测试计划 / 用例集 / 测试报告）
- [ ] 测试对象是否可定位到具体版本、构建、分支或发布批次
- [ ] 是否声明了数据来源以及与需求/设计/接口的同步关系
- [ ] 测试范围与非范围是否清晰，是否避免“默认全测/默认不测”的模糊状态
- [ ] 是否按优先级标记了 P0/P1/P2 场景
- [ ] 是否明确了测试分层与策略，而不是只有一堆用例标题
- [ ] 需求、设计、风险、用例、缺陷、报告之间是否有追溯关系
- [ ] 是否显式列出未覆盖项和未覆盖风险
- [ ] 测试环境、依赖版本、配置开关、账号权限是否写清楚
- [ ] 测试数据是否包含正常、边界、异常、并发、权限等数据集
- [ ] 用例是否包含前置条件、步骤、输入、预期结果、断言点
- [ ] 预期结果是否可观测，而非“系统正常”“页面正确”这类模糊描述
- [ ] 是否覆盖主流程、异常路径、边界场景、状态机非法转换、幂等、权限、并发
- [ ] 是否定义了可检查的进入准则与退出准则
- [ ] 是否有测试轮次、人员、时间安排和配置矩阵分配
- [ ] 缺陷管理是否定义了严重级别、优先级、流转与升级路径
- [ ] 是否区分产品缺陷、环境问题、用例问题、需求缺口
- [ ] 是否定义了自动化测试的范围、运行位置、门禁阈值和失败处理规则
- [ ] 性能、安全、兼容、恢复等专项测试是否按需覆盖
- [ ] 测试报告是否包含范围、方法、结果、残余风险、建议结论
- [ ] 测试证据是否可检索、可审计、可回放
- [ ] 回归策略是否基于变更影响，而不是盲目全量回归
- [ ] 残余风险是否被记录，并明确接受人
- [ ] 仅凭本文档，测试人员是否能够独立完成准备、执行、提单、回归和汇报
- [ ] 测试文档是否超过 1500 行？如超过，是否已按计划/用例/报告拆分

## 附录：参考资料

- ISO/IEC/IEEE 15289:2019，关于 `plan`、`procedure`、`report`、`test procedure`、`test report`、`validation plan`、`verification plan` 等信息项内容要求
- TestRail: `Organize Your Test Plan Documents`，强调测试计划中的前置条件、步骤、预期结果、优先级、工作量估计、里程碑与报告

- PractiTest: `Test Plan vs Test Case`，强调测试计划是高层策略与管理文档，测试用例是低层执行文档

## 一、测试方案的目标

测试方案不是测试报告,也不是测试用例平台的字段说明。

它的目标是把需求、概要设计和详细设计转化为可执行、可追溯、可留证的验证方案,使开发、测试、架构、运维和验收方在以下问题上形成一致理解:

1. 本轮到底测试什么,不测试什么。
2. 哪些设计对象、接口、状态机、事务、一致性、错误恢复和非功能风险必须被验证。
3. 每类测试应该在哪个层级执行,由谁执行,何时执行。
4. 测试数据、环境、配置、依赖和外部服务如何准备。
5. 哪些测试进入 PR 门禁、nightly、staging smoke 或 release gate。
6. 测试结果如何形成可审计证据,并如何交给 `06-验收标准.md` 做裁决。

终极检验标准:

```text
一个未参与项目的测试人员,
仅凭 00/01/02/03/05,
能否独立准备环境、构造数据、执行测试、定位失败、留存证据,
并把结果交给 06 做验收裁决。
```

## 二、与上游 / 下游文档的边界

### 2.1 相对需求文档

测试方案承接需求文档中的:

- 目标与非目标
- 用户故事和核心用例
- 功能需求与业务规则
- 非功能需求
- 数据边界
- 接口与依赖
- 验收方向

测试方案不重新定义需求,只把需求转成测试范围、测试场景和覆盖矩阵。

### 2.2 相对架构设计

测试方案承接架构设计中的:

- 上下游交互边界
- 通信方式
- 数据所有权
- 横切关注点
- 关键风险

测试方案不重新选择架构方案,只验证架构边界是否成立。

### 2.3 相对概要设计

测试方案承接概要设计中的:

- 主要组成部分
- 关键对象轮廓
- API / 接口骨架
- 关键处理流
- 状态定义与状态流转
- 异常与边界场景

测试方案不展开代码实现细节,但必须确保概要设计中的每条主线都有测试切口。

### 2.4 相对详细设计

测试方案强承接详细设计中的:

- 模块实现契约
- 对象字段和函数契约
- Command / Query / Event / Job 协议
- 逐接口函数级处理流
- 状态机与转换矩阵
- 事务、一致性、幂等、并发和恢复
- 错误模型
- 配置、外部依赖、观测和审计
- `测试切口与最小验证清单`

测试方案不替代详细设计中的代码契约,只定义如何验证这些契约。

### 2.5 相对验收标准

测试方案提供证据,验收标准做裁决。

```text
05-测试方案
  - 怎么测
  - 测哪些场景
  - 证据怎么留

06-验收标准
  - 什么结果算通过
  - 什么问题一票否决
  - 残余风险谁接受
```

### 2.6 相对实施计划

测试方案定义验证门禁;实施计划安排何时实现、何时测试、何时提交和何时回退。

测试方案不写开发排期,但必须提供实施计划可引用的测试阶段、自动化门禁和退出准则。

## 三、测试方案章节主链

正式 `05-测试方案.md` 必须使用以下主链。

```text
1. 与上游文档的关系声明
2. 本次测试目标与范围
3. 测试对象与测试切口
4. 测试策略与分层
5. 需求追溯与覆盖矩阵
6. 测试场景与用例设计
7. 测试数据设计
8. 测试环境与配置矩阵
9. 自动化与 CI/CD 门禁
10. 专项测试与非功能验证
11. 缺陷管理与复验规则
12. 进入准则与退出准则
13. 测试报告与证据归档
14. 回归策略与残余风险
15. 参考
```

章节不得随意改名。确需增减章节时,必须在文档元信息中说明原因。

### 3.1 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式测试方案时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/05_test_plan_step_06_cases.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章测试方案结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的测试范围、用例、门禁或证据口径。
- 正式章节正文只承载收口后的测试方案结论；问题回答、旧材料诊断、方案取舍、差异审计、模块自检和停审记录必须留在 `design-calibration` 中间产物。
- `设计文档讨论中间产物规范.md` 中的 100~300 行规则只约束单次写入 / patch 批次，不限制正式测试方案文档、章节、模块、表格或附录的最终长度。
- 正式章节写入前必须按 `设计文档讨论中间产物规范.md` 的写入前检查确认对应 Step / 模块思考记录、写入记录和自检状态已经完成。
- 不得为了满足单批行数而压缩测试完整性；测试范围、用例矩阵、门禁、证据 schema、报告归档和回归策略必须按本规范完整收口。

## 四、通用输出规则

### 4.1 表 / 图 / 清单使用规则

测试方案以表格为主,ASCII 图按需使用,短文用于解释边界和取舍。

| 表达形式 | 适用场景 | 约束 |
|---|---|---|
| 表格 | 范围、矩阵、用例、环境、数据、门禁、证据、风险 | 必须有稳定列名,不得只写散文 |
| ASCII 图 | 测试分层、证据流、自动化流水线、环境拓扑 | 必须有标题和关键说明 |
| 清单 | 进入准则、退出准则、执行检查项 | 每项必须可判定 |
| 短文 | 解释范围、边界和取舍 | 不得替代表格或矩阵 |

### 4.2 ASCII 图统一格式

测试方案中所有 ASCII 图必须使用以下格式。

````md
#### <图类型>: <图标题>

```text
<ASCII 图正文>
```

关键说明:

- <图表达的测试关系>
- <图不表达的实现细节>
- <图中最容易误解的边界>
````

允许的图类型:

| 图类型 | 用途 |
|---|---|
| 测试分层图 | 表达 unit / service / integration / E2E / release gate 关系 |
| 证据流图 | 表达测试执行结果如何进入报告、验收和风险接受 |
| 环境拓扑图 | 表达测试环境、依赖服务和外部系统 |
| 自动化门禁图 | 表达 PR、nightly、staging、release gate 的测试套件 |
| 回归触发图 | 表达变更类型如何触发最小 / 全量回归 |

### 4.3 用例编号规则

测试用例编号必须稳定。

推荐格式:

```text
TC-<模块或主线>-<三位序号>
```

示例:

```text
TC-CMD-001
TC-STATE-003
TC-OUTBOX-002
TC-RECOVERY-004
```

禁止使用:

```text
case1
测试一下发布
临时用例 A
```

### 4.4 证据编号规则

测试证据必须能被验收标准引用。

推荐格式:

```text
EV-<测试层级>-<三位序号>
```

示例:

```text
EV-UNIT-001
EV-API-004
EV-REPLAY-002
```

### 4.5 正式章节必须保留校准来源入口

整理正式测试方案时，每个正式章节开头必须回答：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~15。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/05_test_plan_step_06_cases.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/05_test_plan_step_06_cases.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解测试场景与用例如何从需求、设计契约和风险切口收敛而来。
```

### 4.6 artifacts / reports / scripts 统一口径

测试方案必须承接 `子项目目录与代码文件组织规范.md` 中的实现仓运行证据规则。

固定分工：

```text
scripts/gates/*
  -> 执行测试门禁
  -> 输出 artifacts/test/<run_id>/

scripts/reports/*
  -> 读取 artifacts/test/<run_id>/
  -> 生成 reports/runs/<run_id>/ 和 reports/acceptance/

human / Agent review
  -> 审查 reports/acceptance/*
  -> 补充风险接受、交接说明和复核意见
```

测试方案中必须使用以下路径口径：

| 类型 | 固定路径 | 禁止写法 | 说明 |
|---|---|---|---|
| 原始机器证据 | `artifacts/test/<run_id>/...` | `artifacts/test/<project>/<run_id>/...` | 由 gate / CI / test runner 生成 |
| 人类可读报告 | `reports/runs/<run_id>/...` | `reports/<project>/...` | 由 `scripts/reports/*` 生成 |
| 验收交接报告 | `reports/acceptance/...` | `reports/<project>/acceptance/...` | 脚本生成初稿，人 / Agent 审查补充 |
| 生成脚本 | `scripts/reports/*.sh` | `reports/*.sh` | 脚本不得放在输出目录内 |

测试方案不得把 `latest` 作为正式证据引用。`latest` 只允许本地调试，正式测试、验收和交付必须引用固定 `<run_id>`。

### 4.7 测试与详细设计闭环规则

测试方案必须使用详细设计中的正式对象名、字段名、函数名、协议名、状态名和错误名。测试方案不得把旧口语状态、临时字段名或实现者猜测写成测试断言。

必须完成以下闭环：

| 闭环项 | 要求 | 落点 |
|---|---|---|
| 对象闭环 | 每个 P0 测试对象能回指 `03-详细设计.md` 的模块、对象或协议 | §3 |
| 字段闭环 | 用例断言字段必须来自详细设计字段或协议 schema | §6 / §7 |
| 状态闭环 | 用例预期结果必须使用详细设计正式 enum variant | §6 |
| 负向闭环 | 字段缺失、非法状态、非法迁移、phase 越界必须有对应负向测试 | §6 / §10 |
| 证据闭环 | 证据 ID 能被 `06-验收标准.md` 的 AC 项消费 | §13 |

推荐补充测试闭环表：

| 测试用例 | 设计契约 | 字段 / 状态断言 | 负向条件 | 证据 ID |
|---|---|---|---|---|

正确示例：

```md
| 测试用例 | 设计契约 | 字段 / 状态断言 | 负向条件 | 证据 ID |
|---|---|---|---|---|
| TC-BUS-PUB-002 | 03 §7 AcceptPublicationCommand / §5 PublicationMaterial | missing core_event_ref -> rejected | core_event_ref 不得由 core_event_envelope_ref 代替 | EV-API-002 |
| TC-BUS-DLV-001 | 03 §9 DeliveryStatus | RunDeliveryProgression 成功后为 Delivered | 不断言 Completed | EV-WORKER-001 |
```

错误示例：

```md
| TC | 预期 |
|---|---|
| TC-BUS-DLV-001 | dispatched / completed |
```

错误原因：

- 使用旧口语状态名，未回指详细设计正式 enum。
- 没有说明字段、状态或证据来源。
- 可能把后续 phase 才产生的状态写成本 phase 测试预期。

## 五、章节级规范

### 5.1 与上游文档的关系声明

本章目标:

说明测试方案承接哪些文档,哪些内容作为测试输入,哪些内容不在本文重新讨论。

必须输出:

| 来源文档 | 测试输入 | 本文如何使用 |
|---|---|---|
| `00-需求文档.md` | <需求 / 规则 / 非功能> | <转成测试范围和覆盖矩阵> |
| `01-架构设计.md` | <边界 / 交互 / 风险> | <转成集成和边界测试> |
| `02-概要设计.md` | <主要组成部分 / 流程 / 状态> | <转成测试对象和切口> |
| `03-详细设计.md` | <协议 / 状态机 / 事务 / 错误 / 并发> | <转成接口、状态、恢复和一致性测试> |
| `06-验收标准.md` | <验收门禁> | <测试证据回填给验收> |

写法规则:

- 必须明确测试方案不重新定义需求和设计。
- 必须说明详细设计中哪些章节是测试设计的直接输入。
- 必须说明测试方案与验收标准的边界。

完成标准:

- 读者能知道每类测试依据来自哪里。
- 读者能知道后续文档如何消费测试证据。

### 5.2 本次测试目标与范围

本章目标:

明确本轮验证的目标、范围、非范围、优先级和风险边界。

必须输出范围表:

| 范围项 | 类型 | 优先级 | 验证目标 | 非目标 / 说明 |
|---|---|---|---|---|
| <模块 / 接口 / 状态机 / 风险> | <功能 / 协议 / 状态 / 非功能> | P0/P1/P2 | <要证明什么> | <不测什么> |

写法规则:

- 范围必须绑定需求 ID、设计章节、接口名、状态机或风险项。
- 非范围必须说明原因和风险归属。
- 不得只写“测试全部功能”。

完成标准:

- P0 范围可以直接推导出测试场景和退出准则。
- 非范围不会被误解为遗漏。

### 5.3 测试对象与测试切口

本章目标:

从概要 / 详细设计中抽取必须被验证的对象和切口。

必须输出测试切口总表:

| 测试对象 | 来源章节 | 测试切口 | 风险 | 推荐测试层级 |
|---|---|---|---|---|
| <对象 / 模块 / 接口 / 状态机> | <03 §x> | <验证点> | <若失败的影响> | <unit / service / integration / API / E2E> |

推荐分类:

| 分类 | 示例 |
|---|---|
| 模块切口 | domain、application service、repository、worker、api |
| 对象切口 | aggregate、value object、DTO、event envelope |
| 接口切口 | Command、Query、Event、Job |
| 状态切口 | lifecycle、outbox、idempotency、job |
| 一致性切口 | 事务、outbox、snapshot、projection |
| 恢复切口 | retry、replay、dead-letter、rebuild |
| 非功能切口 | 性能、可观测、安全、审计 |

完成标准:

- 详细设计中的关键实现契约都有测试入口。
- 每个高风险切口都有推荐测试层级。
- P0 测试对象能回指具体详细设计章节，不能只写模块泛名。

### 5.4 测试策略与分层

本章目标:

说明不同问题应该在哪个测试层级被发现,避免所有风险都堆到 E2E。

必须输出测试分层图和分层表。

测试分层图模板:

````md
#### 测试分层图: <项目名> 测试金字塔

```text
[Unit tests]
  - domain / value object / policy / DTO
        |
        v
[Service tests]
  - application service + fake ports
        |
        v
[Integration tests]
  - repository / UnitOfWork / external adapters
        |
        v
[API / Worker contract tests]
  - HTTP / RPC / event / job contract
        |
        v
[E2E / Release gate]
  - 最小业务闭环与跨仓同步样本
```

关键说明:

- 单元测试优先发现领域规则错误。
- service 测试验证编排顺序和事务边界。
- E2E 只覆盖最小闭环和跨仓高风险链路。
````

测试分层表:

| 层级 | 目标 | 典型内容 | 执行时机 | 失败处理 |
|---|---|---|---|---|
| Unit | <局部不变量> | <对象 / policy> | PR | 阻断 |
| Service | <应用编排> | <command / query service> | PR / CI | 阻断 |

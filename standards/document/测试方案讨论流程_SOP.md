# 测试方案讨论流程_SOP

> 目标: 定义 `05-测试方案.md` 如何通过讨论逐步生成。
> 适用对象: 人类作者、Claude/其他 Agent、多人协作讨论。
> 与 `测试方案书写规范.md` 的关系: 书写规范定义最终结果结构;本 SOP 定义内容生成顺序。
> 与 `设计文档讨论中间产物规范.md` 的关系: 本 SOP 定义每一步问什么;中间产物规范定义每一步讨论后留下什么、如何确认、如何回填。

## 1. 适用前提

本 SOP 适用于:

```text
需要为一个仓 / 一个模块 / 一个子系统编写 05-测试方案.md
且希望先通过讨论逐步收敛测试范围、测试切口、用例、数据、环境、门禁和证据
```

它不适用于:

```text
重新定义需求目标
重新定义概要 / 详细设计
替代测试执行报告
替代验收标准
直接安排开发排期
```

## 2. 核心原则

### 2.1 先承接设计,后设计测试

测试方案必须从 `00/01/02/03` 中抽取测试输入,不得凭经验自由罗列用例。

### 2.2 先测试对象,后测试用例

必须先明确要验证哪些对象、接口、状态机、事务、一致性、错误恢复和非功能风险,再设计用例。

### 2.3 先切口,后分层

测试层级服务于风险发现位置。不是先决定“写多少单测 / 集成测试”,而是先确认风险应该在哪一层被发现。

### 2.4 证据面向验收

每个 P0 测试场景都应能形成证据,并被 `06-验收标准.md` 引用。

### 2.5 以测试切口为小循环主轴

测试方案不能先一次性生成全仓用例大表,再事后补数据、自动化和证据。必须按测试切口 / 功能能力逐个小循环展开:

```text
测试对象 / 设计真相源
  -> 测试切口
  -> 正向 / 负向 / 边界场景
  -> 用例和断言
  -> 测试数据
  -> 自动化 / 手工门禁
  -> 证据 ID 和验收引用
  -> 切口停审
```

每个 P0 测试切口完成后必须停审:

- 是否有正式设计来源,字段、状态、接口、错误和 phase 边界是否使用正式名称。
- 是否至少有一个可执行用例或明确风险接受。
- 用例是否有前置数据、断言点、自动化 / 手工执行口径和证据输出。
- 证据是否能被验收标准引用,且 artifact / report 路径固定。

所有测试切口完成后,必须做跨切口覆盖审计,检查孤儿设计契约、重复用例、未覆盖 P0 风险、测试数据冲突、自动化门禁缺口、证据编号冲突和验收引用缺口。

### 2.6 中间产物先于正式文档

不得直接跳到正式 `05-测试方案.md`。

执行链路必须是:

```text
本步输入
  -> 应问的问题
  -> SOP 问题回答
  -> Step 中间产物
  -> 回填草稿
  -> 用户确认 / 门禁通过
  -> 正式测试方案章节
```

Step 中间产物必须放在对应子项目的 `design-calibration/` 目录下，并遵循 `standards/document/设计文档讨论中间产物规范.md`。

每个 Step 的中间产物至少包含：

- Step 状态
- 本步输入
- SOP 问题回答
- 当前文档问题诊断
- 改动前后对比
- 测试设计取舍
- 结构化中间产物
- 回填草稿
- 待确认事项
- 进入下一步条件

推荐命名:

```text
05_test_plan_calibration_flow.md
05_test_plan_step_01_input_boundary.md
05_test_plan_step_02_scope.md
...
```

### 2.7 ASCII 图输出统一

凡是本 SOP 中要求或允许输出 ASCII 图的 Step,必须同时收稳:

```text
图类型
图标题
ASCII 图正文
图后 2~5 条关键说明
```

所有 ASCII 图必须遵守 `测试方案书写规范.md` 4.2。

### 2.8 通用执行纪律

测试方案讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `05-测试方案.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。
- 测试对象、用例矩阵、测试数据、测试环境、自动化门禁和证据归档等 Step 必须分别收敛。

正确示例：

```text
Step 3 单独抽取测试对象与测试切口。
Step 6 单独设计测试场景与用例矩阵。
Step 13 单独定义测试报告与证据归档。
正式 05-测试方案.md 每章标注具体校准来源。
```

错误示例：

```text
把 Step 3~Step 8 合并成“测试方案设计”。
用一张大表同时表达测试对象、测试用例、测试数据和测试环境。
在旧 05-测试方案.md 上追加新版 TC / EV 编号。
一次性写入 800 行用例矩阵。
```

错误原因：

- 测试对象、用例、数据和环境属于不同设计判断，合并后证据链不清。
- 旧测试编号和新版 TC / EV 容易混杂。
- 验收标准无法稳定引用测试证据。

### 2.9 测试用例必须回指设计真相源

测试方案不能自行发明字段、状态、接口、错误或证据口径。每个 P0 用例必须能说明它验证的是哪个详细设计契约。

正确示例：

```text
TC-BUS-PUB-002
  -> 验证 AcceptPublicationCommand 缺少 core_event_ref 时被拒绝
  -> 设计来源为 03 §7 协议契约和 §5 PublicationMaterial 字段闭环
  -> 证据 EV-API-002 交给 AC-SYNC-001 消费
```

错误示例：

```text
TC-BUS-DLV-001
  -> 预期 dispatched / completed
  -> 但详细设计正式状态为 Delivered, Completed 属于后续 feedback 流
```

错误原因：

- 测试继续使用旧口语状态名。
- 测试断言越过当前处理流或当前 phase。
- 验收标准无法判断证据是否验证了正式设计契约。

## 3. Step 模板字段

每个 Step 必须包含以下字段:

| 字段 | 作用 |
|---|---|
| 本步目标 | 说明本步要解决什么测试设计问题 |
| 本步输入 | 说明进入本步前必须具备哪些上游信息 |
| 本步输出 | 说明本步必须产出什么结构化结果 |
| 应问的问题 | 用于把输入收敛成输出的问题集合 |
| 期望产出 | 本步应该沉淀的表、图、矩阵或清单 |
| 回填位置 | 指向 `05-测试方案.md` 的章节 |
| 执行约束 | 说明本步允许和禁止的做法 |
| 进入下一步的条件 | 判断本步是否完成的门禁 |

执行顺序:

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 回填位置
  -> 进入下一步的条件
```

## 4. 建议的讨论总流程

```text
Step 1. 确认测试输入边界
Step 2. 明确测试目标、范围和非范围
Step 3. 抽取测试对象与测试切口
Step 4. 制定测试策略与分层
Step 5. 建立需求追溯与覆盖矩阵
Step 6. 设计测试场景与用例矩阵
Step 7. 设计测试数据
Step 8. 设计测试环境与配置矩阵
Step 9. 设计自动化与 CI/CD 门禁
Step 10. 设计专项测试与非功能验证
Step 11. 定义缺陷管理与复验规则
Step 12. 定义进入准则与退出准则
Step 13. 定义测试报告与证据归档
Step 14. 定义回归策略与残余风险
Step 15. 整理正式测试方案文档
```

---

## 5. 每一步的讨论目标、输入与产出

### Step 1. 确认测试输入边界

#### 本步目标

确认测试方案依赖的需求、架构、概要、详细设计和验收输入是否足够。

#### 本步输入

- `00-需求文档.md`
- `01-架构设计.md`
- `02-概要设计.md`
- `03-详细设计.md`
- `06-验收标准.md` 草案或验收方向

#### 本步输出

- 上游输入映射表
- 不再回答的问题清单
- 测试方案必须回答的问题清单

#### 应问的问题

1. 当前测试方案要承接哪些需求、规则和非功能目标?
2. 哪些概要 / 详细设计章节直接影响测试对象?
3. 哪些验收项需要测试方案提供证据?
4. 哪些内容不应在测试方案中重新定义?
5. 当前上游是否存在会阻塞测试设计的缺口?

#### 期望产出

| 来源文档 | 测试输入 | 回填章节 |
|---|---|---|

#### 回填位置

`05-测试方案.md` §1。

#### 执行约束

- 不得重新发明需求编号。
- 不得替代详细设计补实现契约。
- 上游缺口必须进入待确认事项。

#### 进入下一步的条件

- 输入文档清单明确。
- 测试方案边界明确。

### Step 2. 明确测试目标、范围和非范围

#### 本步目标

定义本轮测试要证明什么、覆盖什么、不覆盖什么。

#### 本步输入

- Step 1 输入映射
- 需求文档目标 / 非目标
- 详细设计 P0/P1/P2 范围

#### 本步输出

- 测试目标
- 范围 / 非范围表
- 优先级口径

#### 应问的问题

1. P0 必须通过哪些测试才能证明主链成立?
2. P1/P2 是否只做边界验证或延后?
3. 哪些下游能力只测接缝,不测对方完整实现?
4. 哪些非范围有残余风险?
5. 哪些范围项是一票否决相关?

#### 期望产出

| 范围项 | 类型 | 优先级 | 验证目标 | 非目标 / 说明 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §2。

#### 执行约束

- P0 必须可测试。
- 非范围必须说明风险归属。

#### 进入下一步的条件

- P0/P1/P2 和非范围已收稳。

### Step 3. 抽取测试对象与测试切口

#### 本步目标

从概要和详细设计中抽取必须验证的测试对象。

#### 本步输入

- 主要组成部分
- 模块实现契约
- 对象 / API / 状态机 / 事务 / 错误 / 并发 / 配置 / 观测章节

#### 本步输出

- 测试对象与测试切口总表
- P0 测试切口停审记录
- 跨切口设计来源审计表

#### 应问的问题

1. 哪些 domain object / value object / policy 必须单测?
2. 哪些 application service 必须做 service test?
3. 哪些 repository / adapter / worker 必须做集成测试?
4. 哪些 Command / Query / Event / Job 必须做协议和流程测试?
5. 哪些状态机、事务、一致性、幂等和恢复行为必须单列切口?
6. 哪些字段缺失、DTO 构造失败或引用混同必须作为负向测试切口?
7. 哪些状态名必须以详细设计正式 enum variant 为准?
8. 每个测试切口回指哪个详细设计对象、协议、flow、状态矩阵、持久化契约或错误模型?
9. 哪些 P0 设计契约还没有测试切口承接?
10. 每个 P0 测试切口完成后是否通过停审?

#### 期望产出

| 测试对象 | 来源章节 | 测试切口 | 风险 | 推荐测试层级 |
|---|---|---|---|---|

| 测试切口 | 设计真相源 | 覆盖字段 / 状态 / 协议 / 错误 | P0/P1/P2 | 后续用例要求 |
|---|---|---|---|---|

#### P0 测试切口停审记录

| 测试切口 | 审查项 | 结论 | 缺口 / 修正 |
|---|---|---|---|

#### 跨切口设计来源审计表

| 审计项 | 结论 | 缺口 / 修正 |
|---|---|---|

#### 回填位置

`05-测试方案.md` §3。

#### 执行约束

- 不得只按技术层级列测试。
- 必须覆盖详细设计 §15 中的最小验证清单。
- 必须优先使用详细设计正式字段名、状态名、协议名和错误名。
- 字段缺失、非法状态、DTO 构造失败等 P0 风险不得只留给人工检查。
- 每个 P0 测试切口必须回指具体设计真相源,不能只写“核心流程”。
- 每个 P0 测试切口完成后必须停审:设计来源是否明确、风险是否具体、推荐层级是否合理、后续用例是否可落地。
- 所有切口完成后必须审计孤儿 P0 设计契约、重复切口、状态 / 字段命名漂移和 phase boundary 越界。

#### 进入下一步的条件

- P0 测试对象都有明确切口。
- 每个 P0 测试切口已停审,跨切口设计来源审计没有 unresolved 冲突。

### Step 4. 制定测试策略与分层

#### 本步目标

决定每类风险应该在哪一层被发现。

#### 本步输入

- Step 3 测试切口
- 详细设计模块边界和处理流

#### 本步输出

- 测试分层图
- 测试分层表

#### 应问的问题

1. 哪些问题必须在 unit 层发现?
2. 哪些问题必须在 service 层验证编排?
3. 哪些问题必须依赖 DB / adapter / worker 集成测试?
4. 哪些问题需要 API / contract test?
5. 哪些场景才需要 E2E 或 release gate?

#### 期望产出

#### 测试分层图: <项目名> 测试金字塔

```text
[Unit]
  -> [Service]
  -> [Integration]
  -> [API / Worker]
  -> [E2E / Release gate]
```

| 层级 | 目标 | 典型内容 | 执行时机 | 失败处理 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §4。

#### 执行约束

- 不得把所有高风险问题都推给 E2E。
- 必须说明失败是否阻断。

#### 进入下一步的条件

- 测试分层可以覆盖 Step 3 全部 P0 切口。

### Step 5. 建立需求追溯与覆盖矩阵

#### 本步目标

建立需求、设计、场景、用例、证据之间的追溯。

#### 本步输入

- 需求 ID / 规则 ID
- Step 3 / Step 4 结果

#### 本步输出

- 覆盖矩阵
- 未覆盖项清单
- 按测试切口组织的需求 / 设计 / 证据映射表
- 覆盖矩阵停审记录
- 跨覆盖项审计表

#### 应问的问题

1. 每个 P0 需求对应哪些设计章节?
2. 每个 P0 需求至少有哪些测试场景?
3. 哪些场景必须自动化?
4. 每个场景的证据如何编号?
5. 哪些需求暂未覆盖,原因是什么?
6. 每个 Step 3 测试切口是否至少映射到一个需求 / 规则 / 设计契约或明确说明只做设计风险覆盖?
7. 每个 P0 需求 / 规则是否至少有一个测试切口、用例候选和证据 ID?
8. 覆盖矩阵完成后是否通过停审?

#### 期望产出

| 需求 / 规则 ID | 设计依据 | 测试场景 | 用例 ID | 自动化 | 证据 ID | 覆盖状态 |
|---|---|---|---|---|---|---|

| 测试切口 | 需求 / 规则 ID | 设计契约 | 场景 | 用例候选 | 证据 ID | 覆盖状态 |
|---|---|---|---|---|---|---|

#### 覆盖矩阵停审记录

| 覆盖项 / 测试切口 | 审查项 | 结论 | 缺口 / 修正 |
|---|---|---|---|

#### 跨覆盖项审计表

| 审计项 | 结论 | 缺口 / 修正 |
|---|---|---|

#### 回填位置

`05-测试方案.md` §5。

#### 执行约束

- 未覆盖项不得静默消失。
- P0 需求不得只写“人工确认”。
- 覆盖矩阵必须同时能从需求 / 规则查到测试切口,也能从测试切口查到需求 / 规则 / 设计契约。
- P0 覆盖项完成后必须停审:需求是否有设计依据、设计是否有用例候选、证据 ID 是否预留、自动化判断是否合理。
- 所有覆盖项完成后必须审计孤儿需求、孤儿设计契约、孤儿测试切口、重复证据 ID 和 P0 自动化缺口。

#### 进入下一步的条件

- P0 覆盖矩阵无空洞,或空洞已进入风险。

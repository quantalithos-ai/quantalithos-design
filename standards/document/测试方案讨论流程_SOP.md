# 测试方案讨论流程_SOP

> 目标: 定义 `05-测试方案.md` 如何通过讨论逐步生成。
> 适用对象: 人类作者、Claude/其他 Agent、多人协作讨论。
> 与 `测试方案书写规范.md` 的关系: 书写规范定义最终结果结构;本 SOP 定义内容生成顺序。
> 与 `设计文档讨论中间产物规范.md` 的关系: 本 SOP 定义每一步问什么;中间产物规范定义每一步讨论后留下什么、如何确认、如何回填。

## 1. 适用前提

本 SOP 适用于:

```text
需要为一个仓 / 一个模块 / 一个子系统编写 05-测试方案.md
且希望先通过讨论逐步收敛测试范围、测试切口、用例、数据、环境、门禁和证据
```

它不适用于:

```text
重新定义需求目标
重新定义概要 / 详细设计
替代测试执行报告
替代验收标准
直接安排开发排期
```

## 2. 核心原则

### 2.1 先承接设计,后设计测试

测试方案必须从 `00/01/02/03` 中抽取测试输入,不得凭经验自由罗列用例。

### 2.2 先测试对象,后测试用例

必须先明确要验证哪些对象、接口、状态机、事务、一致性、错误恢复和非功能风险,再设计用例。

### 2.3 先切口,后分层

测试层级服务于风险发现位置。不是先决定“写多少单测 / 集成测试”,而是先确认风险应该在哪一层被发现。

### 2.4 证据面向验收

每个 P0 测试场景都应能形成证据,并被 `06-验收标准.md` 引用。

### 2.5 中间产物先于正式文档

不得直接跳到正式 `05-测试方案.md`。

执行链路必须是:

```text
本步输入
  -> 应问的问题
  -> SOP 问题回答
  -> Step 中间产物
  -> 回填草稿
  -> 用户确认 / 门禁通过
  -> 正式测试方案章节
```

Step 中间产物必须放在对应子项目的 `design-calibration/` 目录下，并遵循 `standards/document/设计文档讨论中间产物规范.md`。

每个 Step 的中间产物至少包含：

- Step 状态
- 本步输入
- SOP 问题回答
- 当前文档问题诊断
- 改动前后对比
- 测试设计取舍
- 结构化中间产物
- 回填草稿
- 待确认事项
- 进入下一步条件

推荐命名:

```text
05_test_plan_calibration_flow.md
05_test_plan_step_01_input_boundary.md
05_test_plan_step_02_scope.md
...
```

### 2.6 ASCII 图输出统一

凡是本 SOP 中要求或允许输出 ASCII 图的 Step,必须同时收稳:

```text
图类型
图标题
ASCII 图正文
图后 2~5 条关键说明
```

所有 ASCII 图必须遵守 `测试方案书写规范.md` 4.2。

### 2.7 通用执行纪律

测试方案讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `05-测试方案.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。
- 测试对象、用例矩阵、测试数据、测试环境、自动化门禁和证据归档等 Step 必须分别收敛。

正确示例：

```text
Step 3 单独抽取测试对象与测试切口。
Step 6 单独设计测试场景与用例矩阵。
Step 13 单独定义测试报告与证据归档。
正式 05-测试方案.md 每章标注具体校准来源。
```

错误示例：

```text
把 Step 3~Step 8 合并成“测试方案设计”。
用一张大表同时表达测试对象、测试用例、测试数据和测试环境。
在旧 05-测试方案.md 上追加新版 TC / EV 编号。
一次性写入 800 行用例矩阵。
```

错误原因：

- 测试对象、用例、数据和环境属于不同设计判断，合并后证据链不清。
- 旧测试编号和新版 TC / EV 容易混杂。
- 验收标准无法稳定引用测试证据。

## 3. Step 模板字段

每个 Step 必须包含以下字段:

| 字段 | 作用 |
|---|---|
| 本步目标 | 说明本步要解决什么测试设计问题 |
| 本步输入 | 说明进入本步前必须具备哪些上游信息 |
| 本步输出 | 说明本步必须产出什么结构化结果 |
| 应问的问题 | 用于把输入收敛成输出的问题集合 |
| 期望产出 | 本步应该沉淀的表、图、矩阵或清单 |
| 回填位置 | 指向 `05-测试方案.md` 的章节 |
| 执行约束 | 说明本步允许和禁止的做法 |
| 进入下一步的条件 | 判断本步是否完成的门禁 |

执行顺序:

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 回填位置
  -> 进入下一步的条件
```

## 4. 建议的讨论总流程

```text
Step 1. 确认测试输入边界
Step 2. 明确测试目标、范围和非范围
Step 3. 抽取测试对象与测试切口
Step 4. 制定测试策略与分层
Step 5. 建立需求追溯与覆盖矩阵
Step 6. 设计测试场景与用例矩阵
Step 7. 设计测试数据
Step 8. 设计测试环境与配置矩阵
Step 9. 设计自动化与 CI/CD 门禁
Step 10. 设计专项测试与非功能验证
Step 11. 定义缺陷管理与复验规则
Step 12. 定义进入准则与退出准则
Step 13. 定义测试报告与证据归档
Step 14. 定义回归策略与残余风险
Step 15. 整理正式测试方案文档
```

## 5. 每一步的讨论目标、输入与产出

### Step 1. 确认测试输入边界

#### 本步目标

确认测试方案依赖的需求、架构、概要、详细设计和验收输入是否足够。

#### 本步输入

- `00-需求文档.md`
- `01-架构设计.md`
- `02-概要设计.md`
- `03-详细设计.md`
- `06-验收标准.md` 草案或验收方向

#### 本步输出

- 上游输入映射表
- 不再回答的问题清单
- 测试方案必须回答的问题清单

#### 应问的问题

1. 当前测试方案要承接哪些需求、规则和非功能目标?
2. 哪些概要 / 详细设计章节直接影响测试对象?
3. 哪些验收项需要测试方案提供证据?
4. 哪些内容不应在测试方案中重新定义?
5. 当前上游是否存在会阻塞测试设计的缺口?

#### 期望产出

| 来源文档 | 测试输入 | 回填章节 |
|---|---|---|

#### 回填位置

`05-测试方案.md` §1。

#### 执行约束

- 不得重新发明需求编号。
- 不得替代详细设计补实现契约。
- 上游缺口必须进入待确认事项。

#### 进入下一步的条件

- 输入文档清单明确。
- 测试方案边界明确。

### Step 2. 明确测试目标、范围和非范围

#### 本步目标

定义本轮测试要证明什么、覆盖什么、不覆盖什么。

#### 本步输入

- Step 1 输入映射
- 需求文档目标 / 非目标
- 详细设计 P0/P1/P2 范围

#### 本步输出

- 测试目标
- 范围 / 非范围表
- 优先级口径

#### 应问的问题

1. P0 必须通过哪些测试才能证明主链成立?
2. P1/P2 是否只做边界验证或延后?
3. 哪些下游能力只测接缝,不测对方完整实现?
4. 哪些非范围有残余风险?
5. 哪些范围项是一票否决相关?

#### 期望产出

| 范围项 | 类型 | 优先级 | 验证目标 | 非目标 / 说明 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §2。

#### 执行约束

- P0 必须可测试。
- 非范围必须说明风险归属。

#### 进入下一步的条件

- P0/P1/P2 和非范围已收稳。

### Step 3. 抽取测试对象与测试切口

#### 本步目标

从概要和详细设计中抽取必须验证的测试对象。

#### 本步输入

- 主要组成部分
- 模块实现契约
- 对象 / API / 状态机 / 事务 / 错误 / 并发 / 配置 / 观测章节

#### 本步输出

- 测试对象与测试切口总表

#### 应问的问题

1. 哪些 domain object / value object / policy 必须单测?
2. 哪些 application service 必须做 service test?
3. 哪些 repository / adapter / worker 必须做集成测试?
4. 哪些 Command / Query / Event / Job 必须做协议和流程测试?
5. 哪些状态机、事务、一致性、幂等和恢复行为必须单列切口?

#### 期望产出

| 测试对象 | 来源章节 | 测试切口 | 风险 | 推荐测试层级 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §3。

#### 执行约束

- 不得只按技术层级列测试。
- 必须覆盖详细设计 §15 中的最小验证清单。

#### 进入下一步的条件

- P0 测试对象都有明确切口。

### Step 4. 制定测试策略与分层

#### 本步目标

决定每类风险应该在哪一层被发现。

#### 本步输入

- Step 3 测试切口
- 详细设计模块边界和处理流

#### 本步输出

- 测试分层图
- 测试分层表

#### 应问的问题

1. 哪些问题必须在 unit 层发现?
2. 哪些问题必须在 service 层验证编排?
3. 哪些问题必须依赖 DB / adapter / worker 集成测试?
4. 哪些问题需要 API / contract test?
5. 哪些场景才需要 E2E 或 release gate?

#### 期望产出

#### 测试分层图: <项目名> 测试金字塔

```text
[Unit]
  -> [Service]
  -> [Integration]
  -> [API / Worker]
  -> [E2E / Release gate]
```

| 层级 | 目标 | 典型内容 | 执行时机 | 失败处理 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §4。

#### 执行约束

- 不得把所有高风险问题都推给 E2E。
- 必须说明失败是否阻断。

#### 进入下一步的条件

- 测试分层可以覆盖 Step 3 全部 P0 切口。

### Step 5. 建立需求追溯与覆盖矩阵

#### 本步目标

建立需求、设计、场景、用例、证据之间的追溯。

#### 本步输入

- 需求 ID / 规则 ID
- Step 3 / Step 4 结果

#### 本步输出

- 覆盖矩阵
- 未覆盖项清单

#### 应问的问题

1. 每个 P0 需求对应哪些设计章节?
2. 每个 P0 需求至少有哪些测试场景?
3. 哪些场景必须自动化?
4. 每个场景的证据如何编号?
5. 哪些需求暂未覆盖,原因是什么?

#### 期望产出

| 需求 / 规则 ID | 设计依据 | 测试场景 | 用例 ID | 自动化 | 证据 ID | 覆盖状态 |
|---|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §5。

#### 执行约束

- 未覆盖项不得静默消失。
- P0 需求不得只写“人工确认”。

#### 进入下一步的条件

- P0 覆盖矩阵无空洞,或空洞已进入风险。

### Step 6. 设计测试场景与用例矩阵

#### 本步目标

把测试场景落成可执行用例。

#### 本步输入

- Step 5 覆盖矩阵
- 详细设计接口、状态机、错误和处理流

#### 本步输出

- 测试场景表
- 用例矩阵

#### 应问的问题

1. 每个 P0 正向主线怎么执行?
2. 每个关键反向和边界场景如何触发?
3. 每个状态非法迁移如何断言?
4. 每个事务回滚和副作用如何验证?
5. 每个恢复场景如何复现?

#### 期望产出

| 用例 ID | 场景 | 优先级 | 前置条件 | 输入 / 操作 | 预期结果 | 断言点 | 自动化候选 |
|---|---|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §6。

#### 执行约束

- P0 用例必须有断言点。
- 不得只写“执行接口,看是否成功”。

#### 进入下一步的条件

- P0 用例可执行、可断言、可留证。

### Step 7. 设计测试数据

#### 本步目标

定义测试数据如何构造、隔离、复用和清理。

#### 本步输入

- 用例矩阵
- 详细设计 DTO / schema / 状态机 / 持久化契约

#### 本步输出

- 测试数据集表
- fixture / builder / seed 规则

#### 应问的问题

1. 哪些基础数据必须存在?
2. 哪些边界、异常、并发和恢复数据必须构造?
3. 数据如何隔离不同测试运行?
4. 数据如何清理?
5. 哪些外部依赖使用 fake / stub / real-like?

#### 期望产出

| 数据集 | 用途 | 构造方式 | 隔离键 | 清理方式 | 关联用例 |
|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §7。

#### 执行约束

- 测试数据必须可重复生成。
- 不得依赖人工临时造数。

#### 进入下一步的条件

- P0 用例的数据前置条件可满足。

### Step 8. 设计测试环境与配置矩阵

#### 本步目标

定义测试环境、依赖服务和配置开关。

#### 本步输入

- 详细设计配置 / 外部依赖章节
- 用例和数据设计

#### 本步输出

- 环境矩阵
- 配置矩阵
- 必要时输出环境拓扑图

#### 应问的问题

1. local / CI / integration / staging 分别测什么?
2. 每个环境依赖哪些服务?
3. 哪些 feature flag / config 影响测试结果?
4. 哪些依赖需要 mock 或 fake?
5. 环境不可用时如何处理?

#### 期望产出

| 环境 | 用途 | 依赖服务 | 关键配置 / feature flag | 数据策略 | 风险 |
|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §8。

#### 执行约束

- 不得只写“测试环境准备好”。
- 配置必须可定位。

#### 进入下一步的条件

- P0 自动化和人工测试环境均可定位。

### Step 9. 设计自动化与 CI/CD 门禁

#### 本步目标

定义哪些套件自动执行,在哪条流水线执行,失败是否阻断。

#### 本步输入

- 测试分层
- 用例矩阵
- 环境矩阵

#### 本步输出

- 自动化套件表
- CI/CD 门禁图

#### 应问的问题

1. 哪些 suite 必须进 PR?
2. 哪些 suite 进 main CI?
3. 哪些 suite 进 nightly?
4. 哪些 suite 是 staging smoke 或 release gate?
5. flaky、超时和依赖故障如何处理?

#### 期望产出

| 套件 | 覆盖范围 | 执行位置 | 触发条件 | 阻断级别 | 报告 |
|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §9。

#### 执行约束

- P0 主线不得只依赖手工测试。
- 阻断级别必须明确。

#### 进入下一步的条件

- P0 自动化门禁清晰。

### Step 10. 设计专项测试与非功能验证

#### 本步目标

定义性能、安全、一致性、恢复、观测和审计专项。

#### 本步输入

- 非功能需求
- 详细设计事务、错误、并发、配置、观测章节

#### 本步输出

- 专项测试矩阵

#### 应问的问题

1. 哪些性能指标必须验证?
2. 哪些安全和边界红线必须负向测试?
3. 哪些一致性和恢复场景必须故障注入?
4. 哪些日志、指标和审计证据必须存在?
5. 阈值来自哪里?

#### 期望产出

| 专项 | 指标 / 风险 | 方法 | 环境 | 阈值 / 通过条件 | 证据 |
|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §10。

#### 执行约束

- 非功能指标不得无来源。
- 可观测性必须可通过证据验证。

#### 进入下一步的条件

- P0 非功能和红线均有验证方式。

### Step 11. 定义缺陷管理与复验规则

#### 本步目标

定义缺陷分级、升级、修复和复验规则。

#### 本步输入

- 用例矩阵
- 一票否决项
- 验收风险

#### 本步输出

- 缺陷分级表
- 复验规则

#### 应问的问题

1. 哪些缺陷属于 S 级阻断?
2. 哪些缺陷可以风险接受?
3. 修复后必须回归哪些用例?
4. 缺陷关闭需要哪些证据?
5. 是否需要新增自动化防回归?

#### 期望产出

| 级别 | 定义 | 示例 | 处理要求 | 是否阻断 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §11。

#### 执行约束

- 一票否决缺陷不得降级为普通风险。
- 复验必须说明证据要求。

#### 进入下一步的条件

- 缺陷分级和复验规则可执行。

### Step 12. 定义进入准则与退出准则

#### 本步目标

定义测试开始和结束的门禁。

#### 本步输入

- 环境、数据、自动化、缺陷规则

#### 本步输出

- 进入准则
- 退出准则

#### 应问的问题

1. 开始测试前哪些文档必须冻结?
2. 哪些环境和数据必须可用?
3. 哪些自动化必须可运行?
4. 退出时哪些用例必须通过?
5. 哪些缺陷和风险会阻断退出?

#### 期望产出

```md
### 进入准则

- [ ] <可判定条件>

### 退出准则

- [ ] <可判定条件>
```

#### 回填位置

`05-测试方案.md` §12。

#### 执行约束

- 准则必须可判定,不得写“基本完成”。

#### 进入下一步的条件

- 进入 / 退出准则无模糊项。

### Step 13. 定义测试报告与证据归档

#### 本步目标

定义测试执行后的报告和证据结构。

#### 本步输入

- 用例矩阵
- 自动化报告
- 验收证据需求

#### 本步输出

- 证据归档表
- 测试报告结构

#### 应问的问题

1. 每类测试输出什么证据?
2. 证据保存在哪里?
3. 证据如何关联用例和验收项?
4. 哪些日志、trace、DB snapshot 或报告必须保留?
5. 证据保留多久?

#### 期望产出

| 证据 ID | 证据类型 | 来源 | 保存位置 | 关联用例 | 验收引用 |
|---|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §13。

#### 执行约束

- 测试方案只定义证据要求,不填写执行结论。

#### 进入下一步的条件

- P0 用例都有证据归档方式。

### Step 14. 定义回归策略与残余风险

#### 本步目标

定义变更如何触发回归,未覆盖风险如何记录。

#### 本步输入

- 用例矩阵
- 缺陷规则
- 未覆盖项

#### 本步输出

- 回归触发表
- 残余风险表

#### 应问的问题

1. 哪些变更触发最小回归?
2. 哪些变更触发全量回归?
3. 哪些风险暂不覆盖?
4. 谁接受残余风险?
5. 哪些风险必须转入验收标准?

#### 期望产出

| 变更类型 | 最小回归集 | 全量回归触发条件 | 责任人 |
|---|---|---|---|

| 风险 | 未覆盖原因 | 影响 | 缓解方式 | 接受人 |
|---|---|---|---|---|

#### 回填位置

`05-测试方案.md` §14。

#### 执行约束

- 未覆盖风险必须有接受人或待确认项。

#### 进入下一步的条件

- 回归策略和残余风险可被实施计划 / 验收标准引用。

### Step 15. 整理正式测试方案文档

#### 本步目标

把前 14 个 Step 的中间产物整理成正式 `05-测试方案.md`。

#### 本步输入

- Step 1 ~ Step 14 中间产物
- `测试方案书写规范.md`

#### 本步输出

- 完整 `05-测试方案.md`
- 自审结果

#### 应问的问题

1. 正式文档是否按 15 章主链组织?
2. 是否保留了所有 P0 测试对象、场景、数据、环境、门禁和证据?
3. 是否删除了 SOP 问题原文和讨论语气?
4. 是否所有未确认项都进入残余风险?
5. 是否能被 `06-验收标准.md` 直接消费?

#### 期望产出

- 正式测试方案
- 评审清单结果

#### 回填位置

完整 `05-测试方案.md`。

#### 执行约束

- 不得把中间产物原样粘贴为正式文档。
- 不得把执行结果写进测试方案。

#### 进入下一步的条件

- 测试方案可作为验收标准和实施计划输入。

# 设计真相源闭环与可落码性标准

> 本标准用于判断设计文档是否已经达到“实现者可以 1:1 落码”的程度。
> 它不是替代需求、架构、概要、详细、测试、验收或实施计划，而是为这些文档提供统一的闭环复核口径。

## 一、适用范围

本标准适用于：

- `00-需求文档.md`
- `01-架构设计.md`
- `02-概要设计.md`
- `03-详细设计.md`
- `04-配置设计.md`
- `05-测试方案.md`
- `06-验收标准.md`
- `07-实施计划.md`
- `design-calibration/` 中间产物
- 实现 agent 开工前设计复核

本标准重点约束以下问题：

```text
字段从哪里来
对象如何构造
状态由谁推进
引用如何解析
scope 如何获得
校验读取哪个 truth
投影能否重建
artifact 能否 materialize
当前 phase 能否独立实现
```

## 二、核心原则

### 2.1 设计真相源必须唯一

同一个概念只能有一个正式定义来源。其他文档可以引用、展开或映射，但不能重新定义。

必须唯一的内容包括：

- struct / enum / value object 字段
- command / query / event / job DTO schema
- result / receipt / reason / ref 类型
- 状态枚举与状态迁移
- metadata / idempotency / trace / request digest
- artifact root / report root / evidence root
- phase / commit boundary

正确示例：

```text
SDK 复用 core_contracts::CommandMetadata。
SDK 文档只说明本项目如何使用该 metadata，不重新定义字段。
```

错误示例：

```text
03-详细设计定义 CommandMetadata = idempotency_key + trace_context。
Step 8 定义 CommandMetadata = request_id + requested_at。
core-contracts 又定义 CommandMetadata = RequestMetadata + reason。
```

错误原因：

- 实现者无法判断 public DTO surface。
- 下游测试和上游 contracts 会分别引用不同定义。

### 2.2 进入实现边界的类型必须有 schema

任何进入 DTO、domain method、factory、repository、event、test fixture 的类型，都不能只停留在名称级描述。

至少要定义：

- 归属文档和模块
- struct / enum / newtype 形态
- 字段或 variant
- 必填 / 可选
- 与上游 / 下游字段的映射
- validation rule
- 缺失、not_found、conflict 或 reject 行为

正确示例：

```rust
/// 会话事实追加失败原因。
pub enum FactAppendRejectionReason {
    /// 请求试图携带正文，而事实协议只允许 payload 引用。
    InlineBodyForbidden,
    /// payload_ref 类型要求 digest，但请求未提供 payload_digest。
    MissingPayloadDigest,
}
```

错误示例：

```text
FactAppendRejectionReason: fact append rejected 时使用。
```

错误原因：

- 无法生成 enum variant。
- 测试无法断言具体失败分支。

### 2.3 设计必须按闭环链路复核

每个 command / query / event / job 至少要完成以下链路复核：

```text
Request / Event / Job DTO
  -> Metadata / Context
  -> Application flow
  -> Domain factory / method
  -> Repository / Port / Adapter
  -> Outbox / Event / Projection / Artifact
  -> Result / Receipt
  -> State matrix
  -> Test / Acceptance
  -> Implementation phase / commit boundary
```

如果链路中任一节点缺字段、缺类型、缺 truth source 或依赖后续 phase，本项不能交给实现者自行处理。

设计准备移交给实现 agent 前,不得只声明“适用本标准”。必须按 `07-实施计划.md` 的 phase / commit boundary 对正式 `03-详细设计.md`、`05-测试方案.md`、`06-验收标准.md` 和 `07-实施计划.md` 做一次整体可落码闭环审计。审计输出至少记录 boundary、复核范围、适用标准项、结论、blocker、修复后的 design baseline。未通过时先回写设计真相源,不得把问题留给实现阶段逐个暴露。

### 2.4 可选字段必须在 schema 层可选

如果设计语义允许字段缺失后派生，schema 必须显式写成 `Option<T>` 或等价可选形态，并定义派生来源。

正确示例：

```rust
pub struct AppendConversationFactRequest {
    pub visibility_scope_id: Option<VisibilityScopeId>,
}
```

并说明：

```text
缺失时从 committed conversation truth 派生默认 visibility scope。
提供时作为 guard；若与 committed truth 不一致，返回 ApplicationError::NotVisible。
```

错误示例：

```json
{ "visibility_scope_id": "VisibilityScopeId" }
```

同时字段表写：

```text
visibility_scope_id 缺失时 derive default。
```

错误原因：

- Rust DTO 无法同时表达必填和可省略。
- 幂等 request digest 也无法确定规范化输入。

### 2.5 每条校验规则必须有 truth source

凡是设计中出现以下规则，必须同时定义读取来源：

- ref 必须存在
- ref 必须属于某 public surface
- replacement ref 必须可解析
- version 必须大于当前版本
- scope 必须允许 read / append / publish
- artifact digest 必须匹配
- projection freshness 必须可判定

校验规则最小定义：

| 项 | 要求 |
|---|---|
| 输入字段 | 待校验的 DTO / command / query 字段 |
| truth source | domain truth / upstream snapshot / repository / artifact replay source |
| lookup port | 具体 repository / port / adapter 方法 |
| 失败行为 | not_found / reject / conflict / quarantine / error |
| 测试切口 | 对应 TC / AC / unit test |

正确示例：

```text
replacement_api_ref 必须通过 PublicSdkApiRepository.get(api_ref) 解析到 public SDK surface。
缺失返回 ApplicationError::NotFound。
解析到非 public API 返回 ApplicationError::InvalidReplacement。
```

错误示例：

```text
replacement_api_ref 必须属于 public SDK surface。
```

错误原因：

- 没有 port 或 truth source，无法落码。

### 2.6 Actor authority 与 scope policy 必须闭合

凡是设计中出现 actor、consumer、source actor、system actor、integration actor、participant scope、visibility scope 或 trusted source 例外,必须明确以下内容:

- actor 字段来自 command metadata、event payload、consumer context、repository lookup 还是系统生成。
- 该 actor 表示业务参与者、系统执行者、外部集成入口还是来源边界代理。
- 是否要求 actor 存在于 participant / membership / visibility scope 中。
- 如果允许 trusted source actor 例外,必须列出适用 source kind、actor kind、入口协议和不可绕过的 gate。
- 普通 actor path 与 trusted source path 的错误映射必须不同步漂移。

最小定义表:

| 项 | 要求 |
|---|---|
| 输入 actor 字段 | `ActorRef` / `SystemActorRef` / `ConsumerRef` 等具体字段 |
| authority kind | participant actor / system actor / integration actor / trusted source actor |
| scope requirement | must be in participant scope / may bypass membership / must match visibility hint |
| exception condition | 具体 source kind、event、fact kind 或 policy rule |
| non-bypass gates | active state、visibility、digest、source isolation、forbidden body、idempotency 等仍需执行的 gate |
| 失败行为 | reject / not visible / quarantine / delayed / fail-closed |

正确示例:

```text
RuntimeResultCommittedEvent.system_actor_ref 是 trusted source actor。
source_kind = RuntimeResult 且 actor_kind = System 时,不要求 actor 出现在 ParticipantScope.participants。
仍必须校验 active space、participant scope appendable、visibility open、payload digest、fact_kind = RuntimeResult、source result-only 和 forbidden-body boundary。
缺失或 actor_kind 不匹配时 quarantine。
```

错误示例:

```text
consumer append 使用 system actor。
append policy 要求 actor 在 participant scope 内。
```

错误原因:

- 实现者无法判断是否应把 system / integration actor 塞进 participant scope。
- accepted event path 会被普通 membership policy 拒掉,或者实现侧会自行放宽所有 append 校验。
- trusted source 例外如果没有 non-bypass gates,会变成绕过 visibility / digest / source isolation 的后门。

### 2.7 Ref 到 scope 的解析口径必须闭合

凡是 flow、policy、repository call 或 projection stale 要求从一个 public ref 得到 project / member / space / participant / backlog / visibility / tenant 等 scope,设计必须给出正式解析来源。

必须明确：

- 输入 ref 类型,例如 `FormalWorkRef`、`ExternalFactRef`、`ConversationRef`。
- 输出 scope schema,例如 `{ project_ref, backlog_ref, assignee_ref? }`。
- 解析 owner,例如 repository read、resolver port、snapshot store 或 command request 字段。
- 缺失 / 不一致 / stale scope 的错误映射。
- 该 scope 后续用于哪些 policy、graph、projection stale 或 repository key。

禁止在函数流中写未定义 helper,例如 `project_ref_from(work_ref)`、`space_from(actor)`、`visibility_from(payload)`。也禁止让实现者解析 id 字符串、猜测 parent / membership join 或私自增加 repository 依赖。

正确示例：

```text
WorkItemRepository.get_formal_work_scope(work_ref)
  -> Option<FormalWorkScope { work_ref, project_ref, backlog_ref, assignee_ref }>
LinkWorkDependencyFlow 使用 downstream scope 读取 graph snapshot 并构造 project-board / member-work stale refs。
```

错误示例：

```text
DependencyRepository.load_graph_snapshot(project_ref_from(request.downstream_work_ref))
ProjectionRepository.mark_stale(affected public views)
```

错误原因：

- `FormalWorkRef` 本身不携带 project id。
- implementation agent 不知道是否应从 WorkItem、Backlog membership、parent ChildWorkItem 或 request body 取 scope。
- projection stale 的 affected views 无法稳定构造。
- fake adapter / repository tests 无法验证 scope 来源。

### 2.8 当前 phase 必须形成依赖闭包

每个 phase / commit boundary 必须明确：

- 可新增对象
- 可读取对象
- 可调用 service / factory / method
- 可用 repository / port
- 可写 truth / projection / artifact
- 可发 event / outbox
- 可执行测试与验收门禁
- 禁止使用的后续 phase 对象
- 预列但当前 boundary reserved 的 enum variant、domain method、DTO、history record 和 state transition

正确示例：

```text
commit-02-b 只生成 DerivedBindingView。
LanguageBindingView 需要 CrossLanguageConceptMap，归 commit-03-a。
因此 commit-02-b 不调用 LanguageBindingView::from_concept_map(...)。
```

错误示例：

```text
commit-02-b flow 生成 language views。
但 semantic baseline / concept map port 在 commit-03-a 才允许使用。
```

错误原因：

- 实现者必须越界引用后续 phase，提交边界不可审查。

### 2.9 phase-reserved 状态和方法必须显式标注

正式设计可以提前列出 P0 总体状态集合或对象方法,但只要其中一部分不属于当前 phase / commit boundary,必须在对象契约、状态矩阵、flow、测试切口和实施计划里用同一口径标注。

至少要说明:

- 哪些 enum variant / method / DTO / history record 是当前 boundary 可实现的。
- 哪些是 `reserved` / `future phase` / `PH-xx only`。
- 当前 boundary 遇到 reserved path 时是不可调用、reject,还是完全不暴露 public command。
- 当前 boundary 的 domain / contract tests 只覆盖哪个非 reserved 子集。
- 后续 boundary 从 reserved 变为 active 时需要补哪些 flow、repository、history、outbox 和验收。

正确示例:

```text
commit-03-a implements ProcessInstanceState NotStarted / Running / Completed / Cancelled.
Waiting / Recovering / Failed and pause_for_gate / mark_recovering are PH-04 reserved.
commit-03-a tests cover running subset only;commit-04-a covers waiting/recovery illegal transitions.
```

错误示例:

```text
commit-03-a excludes waiting/recovery。
Step 6 ProcessInstance method table exposes pause_for_gate / mark_recovering without reserved marker。
Step 10 state matrix requires Waiting / Recovering transitions。
Step 16 says process_instance_state_transitions covers recovery path。
```

错误原因:

- 实现者无法判断当前 boundary 应实现未来 phase 对象,还是应该拒绝 / 暂不暴露这些路径。
- contract / domain tests 会越过 phase boundary,迫使实现提前引入后续 repository、history record 和 DTO。
- 后续 phase 的设计空间被当前临时实现锁死。

## 三、字段闭环标准

### 3.1 字段来源必须可追踪

Domain 对象、event、artifact metadata、projection view 的每个必填字段，必须能回指到以下来源之一：

- request / command / query / event / job DTO 字段
- metadata / context 字段
- repository / port lookup 结果
- upstream contract / snapshot 字段
- system generated id / clock / digest / version
- 正式派生规则

字段闭环表：

| 对象 | 字段 | 类型 | 来源类型 | 来源字段 / 方法 | 缺失处理 | 测试 |
|---|---|---|---|---|---|---|

### 3.2 状态条件字段也必须闭环

如果状态矩阵、业务规则、验收标准或测试断言要求某个状态必须携带证据、receipt、marker、reason、timestamp 或其它条件字段,该字段即使在非该状态下可为空,也必须进入 domain truth schema 并写成 `Option<T>` 或等价可选形态。

最少要闭合:

- domain struct 字段和字段表。
- 触发状态转换的 domain method 参数与赋值规则。
- 持久化契约中的存储字段或外部 evidence store 归属。
- query view / outbound event 是否暴露该字段。
- 缺失或未验证时的错误映射。
- 对应测试和验收断言。

正确示例:

```rust
pub struct ChildWorkItem {
    pub work_state: WorkItemState,
    pub completion_ref: Option<ExternalEvidenceRef>,
}
```

并说明:

```text
WorkItemState::Completed 必须有 verified ExternalEvidenceRef。
ChildWorkItem::transition_lifecycle(Completed, ..., Some(evidence_ref), actor)
写入 completion_ref;缺失或未验证 evidence 返回 DomainError::InvalidStateTransition。
```

错误示例:

```rust
pub struct ChildWorkItem {
    pub work_state: WorkItemState,
}
```

同时状态矩阵写:

```text
ChildWorkItem Completed 必须有 verified evidence。
```

错误原因:

- 实现者无法知道 verified evidence 应保存到哪个 truth 字段。
- query / event / duplicate result 无法稳定回放 completed evidence。
- 持久化 adapter 只能自行补列或丢失状态条件。

### 3.3 DTO 到 domain factory 必须闭合

如果 DTO 字段映射到 domain truth 必填字段，则必须满足以下任一条件：

1. 该字段直接传入 factory / method。
2. 该字段通过正式派生规则进入 factory / method。
3. 该字段由 repository / port lookup 生成，并在 flow 中明确。

正确示例：

```rust
ConversationFact::from_append_input(
    space,
    request.fact_kind,
    source,
    visibility,
    request.payload_ref,
)
```

错误示例：

```rust
ConversationFact::from_append_input(space, source, visibility, request.payload_ref)
```

同时 `ConversationFact` 又有必填 `fact_kind`。

错误原因：

- request 中的 `fact_kind` 无法进入 domain truth。

### 3.4 同名或近名引用不得默认等价

以下名称接近但语义不同的 ref 必须显式区分：

- `core_event_ref` vs `core_event_envelope_ref`
- `api_ref` vs `replacement_api_ref`
- `service_capability_ref` object vs `service_capability_ref` string id
- `event_mapping_ref` vs `EventSemanticMapping`
- `RuntimeConfig` vs `ConversationRuntimeConfig`

如果允许映射，必须写清：

- 源类型
- 目标类型
- 映射函数 / lookup 方法
- 失败处理

### 3.5 Query response / view 也是 public DTO

Query 不能只写返回类型名、builder 名或“从 projection 构造”。只要返回对象进入 public query surface，就必须按 DTO schema 定义。

Query response 最少要定义：

- request DTO 的正式名称和落码模块
- response view / page / marker DTO 的正式名称和落码模块
- 每个 response 字段的类型、来源和可见性裁剪规则
- 每个 response 字段引用的 shared enum / ref / helper 类型的归属,不得指向 domain-only 类型
- empty / not visible / stale / failed / rebuilding / disabled / missing state 的返回口径
- page token、consistency、consumer / actor context 来自 query body 还是 metadata / envelope
- HLD `*Query`、DDD `*Request`、Rust DTO 名称是否收敛，以及一对一映射

Query response 引用 repository helper 时,helper 本身也必须定义 schema 和归属。例如 repository 返回 `Page<T>` 时,必须说明 `Page<T>` / `PageInfo` 属于 application port helper、字段包含 `items` / `next_page_token` / `has_more`,并说明如何映射到 public response page DTO。不得只写 `Result<Page<T>, RepositoryError>` 而不定义 `Page`。

Repository / application port 的返回类型必须保持设计指定的 domain object、projection object 或 application helper 类型,不得因为当前 implementation step 尚未实现某个 domain 对象,临时改成 public contracts view DTO。public view DTO 只能在 query service / API handler 输出边界由已授权的 domain / projection 对象映射生成。

正确示例：

```text
HLD GetConversationReadModelQuery 是语义入口名。
Rust DTO 统一为 GetConversationReadModelRequest。
ConversationReadModelView 属于 contracts/views.rs。
ProjectionRepository.get_read_model 返回 domain ConversationReadModel。
ConversationReadModelView::from_authorized(authorized_read_model, projection_state, ...) 在 query 输出边界构造。
projection_state 字段来自 ConversationProjectionStateView::from_state_or_empty(...);
projection 缺失时返回 empty stale marker，不返回 Fresh。
```

错误示例：

```text
GetConversationReadModel 返回 ConversationReadModelView。
ConversationReadModelView::from_authorized(read_model)。
ProjectionRepository.get_read_model 临时返回 ConversationReadModelView。
```

错误原因：

- 实现者无法定义 response DTO 字段。
- 实现者无法判断 response DTO 字段能否合法依赖某个 domain enum。
- repository / application helper 缺少 schema,导致 page DTO 的 `next_page_token` 和 `has_more` 无来源。
- `NotVisible`、empty view、stale / failed projection marker 无法测试。
- HLD `*Query` 与 DDD `*Request` 可能被实现成两套类型。
- public DTO 进入 repository port 后会绕过 domain policy / visibility filter,并把 adapter 层绑定到对外 response schema。

### 3.6 Public read-model / projection identity 必须闭合

read model、projection、cursor、page marker 只要出现在 query response 中，就必须定义 id / ref 的正式 schema。

最少要说明：

- id / ref 属于哪个 contracts 模块
- 是 string newtype、复合 ref，还是上游 typed projection ref
- 与 repository key 的关系
- 稳定派生规则
- 缺失 row 时是否返回 marker、error 或 empty view

正确示例：

```text
ConversationReadModelId 属于 contracts/refs.rs。
ConversationReadModelId::for_consumer(space_id, consumer_ref) 生成稳定 id。
ConversationProjectionStateId::for_kind(space_id, projection_kind) 生成稳定 projection state id。
```

错误示例：

```text
ConversationReadModel 引用 ConversationReadModelId。
Projection state view 返回 projection_state_id。
```

错误原因：

- repository 无法确定 lookup key。
- 空 view 和正常 view 的 identity 不稳定。
- projection state 缺失时无法构造 public marker。

如果 command、consumer 或 job flow 要求 `ProjectionRepository.mark_stale(affected_views, ...)`,每一个 affected view 都必须来自当前 phase 已正式定义的 public projection identity,例如 `Derived*ViewRef` 稳定派生表。不能因为某个 truth、marker 或 intake 发生变化,就在实现阶段临时派生 `promote-*`、`intake-*`、`review-*` 等 view ref。

如果 affected views 需要从 external ref、snapshot ref、member ref、method definition ref、source ref 或其他非 view ref 输入推导,设计还必须定义正式 repository / port 读取面来枚举 existing public view refs。该读取面必须说明输入 ref、分页 helper、返回类型、稳定排序、空结果语义和错误映射。实现不得自行扫描 storage、解析字符串、从 event payload 拼接 `Derived*ViewRef`,或用临时 helper 伪造 project / member / search view identity。

设计必须二选一:

- 当前 boundary 不提供该 truth / marker 的 query / projection surface:明确该 flow 不 mark projection stale,或只在影响已有 public view identity 时标记已有 view。
- 当前 boundary 需要可读 projection:先补 query / view DTO schema、repository key、`Derived*ViewRef` 派生规则、stale marker 语义和测试映射,再要求 flow mark stale。
- 当前 boundary 需要按 external ref / snapshot ref 标脏既有 public views:先补 `list_views_affected_by_*` 或等价正式读取面,再要求 flow mark stale;列表为空时必须明确是 no-op,不是由实现临时构造 view ref。

正确示例:

```text
P0 public DerivedWorkViewRef 只有 project-board / member-work / iteration-summary / work-search。
RequestWorkPromotion 创建 PromoteResult,但 PromoteResult 没有 P0 public query / projection surface。
因此 RequestWorkPromotion 不 mark projection stale。
ReviewWorkPromotion accept 创建 formal WorkItem 时,只标记受影响的既有 board / member / search views stale。
ReviewWorkPromotion reject 不 mark projection stale。
ConsumeIdentityMemberChanged 要按 member ref 标脏时,先调用 ProjectionRepository.list_views_affected_by_member(member_ref, page)。
该 repository 只返回已存在 public DerivedWorkViewRef;空页表示不标脏。
```

错误示例:

```text
RequestWorkPromotionFlow 要求 projection stale。
Step 8 只定义 project-board / member-work / iteration-summary / work-search。
实现阶段临时派生 promote-intake:{source_id}。
ConsumeMethodDefinitionChangedFlow 写 affected_method_views(definition_ref)。
但 Step 7 没有定义任何 repository / port 可以从 definition_ref 枚举 existing public view refs。
```

错误原因:

- repository / fake 无法验证临时 view ref 的 key 规则。
- query surface 不存在,stale marker 没有可观察返回口径。
- projection rebuild 无法知道该 view 如何从 committed truth 重建。
- implementation boundary 会被迫新增未授权 DTO / repository 方法 / tests。

### 3.7 Public protocol surface 的传递类型必须闭合

任何进入公开协议 surface 的类型,即使只是某个 DTO 字段的字段类型,也必须有正式 schema、归属和 crate 边界说明。

公开协议 surface 包括:

- Command result / receipt
- Query view / page / marker
- Inbound Event envelope / payload / receipt
- Outbound Event payload
- Operations Job input / output / report
- public error / disposition / quarantine marker

每个传递类型至少要定义:

- 正式归属模块,例如 `contracts/refs.rs`、`contracts/events.rs` 或 `core-contracts`
- struct 字段、enum variant 或 newtype schema
- 哪些 public DTO 使用它
- 字段来源、缺失处理、duplicate / retry / quarantine / delayed 口径
- 是否允许 domain 复用 shared enum,或是否需要 domain 到 public DTO 的正式映射
- crate 依赖方向,尤其是 contracts 不得依赖 domain-only 类型

正确示例:

```text
ManifestationState 属于 contracts/refs.rs shared enum。
domain/manifestation.rs::CrossDomainManifestation 直接复用该 enum。
ManifestExternalFactResult.manifestation_state 和 CrossDomainManifestationChangedEvent.manifestation_state 都使用同一 shared enum。
```

```rust
pub struct InboundEventEnvelope<T> {
    pub event_id: EventId,
    pub event_envelope_ref: EventEnvelopeRef,
    pub event_source_ref: EventSourceRef,
    pub idempotency_key: IdempotencyKey,
    pub occurred_at: Timestamp,
    pub trace_ref: TraceContextRef,
    pub payload: T,
}
```

错误示例:

```text
ManifestExternalFactResult.manifestation_state: ManifestationState。
Consumer handler returns ConsumerReceipt。
Inbound events use InboundEventEnvelope<T>。
```

但 `ManifestationState` 只在 domain 对象章节定义,`ConsumerReceipt` 和 `InboundEventEnvelope<T>` 只有类型名,没有字段。

错误原因:

- contracts DTO 会被迫依赖 domain enum,或在 contracts 中复制第二套 mirror enum。
- consumer 无法判断 duplicate、quarantine、delayed 和 no-op 的返回字段。
- payload 字段和 envelope 字段可能被重复定义,幂等 digest 也无法稳定。
- implementation step 会自行补 schema 或放松校验。

### 3.8 target / intent / output / marker ref 生命周期角色必须闭合

同一 flow 中若同时出现 target ref、intent、port output ref、marker ref 或 receipt ref,设计必须明确它们分别处于哪个生命周期阶段,不得因为名称相近或都指向外部边界而默认等价。

最小定义表:

| 生命周期角色 | 要求 |
|---|---|
| target ref | 表示调用前的目标或接收方,通常来自 request / job input / policy;不得表示外部 port 已生成的结果 |
| intent | 表示交给 port / adapter 的准备意图,字段必须来自 truth、target ref、metadata 或正式派生规则 |
| port output ref | 表示外部 port / adapter 返回的结果指针,只能在调用成功后出现 |
| marker / receipt ref | 表示本仓记录已准备、已交接、已发布或已归档的本地证据,必须说明使用 target ref 还是 output ref |

正确示例:

```text
TraceHandoffTargetRef 是 PrepareTraceHandoffJobInput.target_ref,表示 handoff 目标。
TraceHandoffIntent.target_ref 使用 TraceHandoffTargetRef。
TraceHandoffPort.prepare_trace_handoff(intent) 返回 TraceHandoffRef。
TraceHandoffMarker::from_trace(trace_id, handoff_ref) 使用 TraceHandoffRef 记录 port 返回结果。
ArchiveHandoffRef 是 ArchiveHandoffPort 的输出,不得作为 trace handoff intent 输入。
```

错误示例:

```text
TraceHandoffIntent.target_ref: TraceHandoffTargetRef。
WorkTraceRecord.prepare_handoff(archive_ref: ArchiveHandoffRef)。
Flow 中又写 record.prepare_handoff(input.target_ref.into_archive_ref())。
```

错误原因:

- target ref 和 output ref 的生命周期角色相反,实现者无法判断 domain helper 应接收调用前目标还是调用后结果。
- port 成功前无法获得 output ref,flow 会被迫伪造转换函数或提前生成外部结果。
- marker / receipt 无法稳定断言是记录“准备意图”还是“外部返回结果”。

### 3.9 Truth change 到 outbound event routing 必须闭合

任何会被用于创建 trace / outbox 的 domain truth change variant,都必须有正式的一对一 routing 链路。实现者不得自行判断是否复用某个已有 outbound event。

最小 routing 链路:

```text
TruthChange variant
  -> OutboxEventKind
  -> OutboundEvent payload schema
  -> payload builder / truth lookup
  -> topic
  -> publisher dispatch branch
  -> contract / publisher / acceptance test mapping
  -> implementation boundary
```

每个 routing 至少要定义:

- truth change variant 的字段和来源。
- 对应的 outbox event kind。
- outbound payload 的 struct / enum schema、字段来源和禁止携带字段。
- payload builder 需要加载的 committed truth 或 reason / marker。
- topic 名称和订阅方。
- publisher dispatch 分支和失败 / retry / failed marker 口径。
- 测试方案、验收接口同步和实施计划中的事件计数与用例映射。

如果一个 truth change 被设计为复用聚合事件,必须在字段表中证明该聚合事件能承载该 truth change 的全部状态、reason 和 ref;否则必须新增专用 event。新增或删除 outbound event 时,正式文档、测试方案、验收标准和实施计划中的事件数量必须同批更新。

如果 publisher 需要由 outbox record 构造 outbound payload,设计还必须定义 outbox fact 到 committed source object 的正式闭环。`event_kind` 只能说明路由类别,不能替代 source identity。设计必须二选一并写入对象契约、repository / port、flow 和持久化契约:

1. outbox record 持久化 typed source identity,例如 `source_ref` / `payload_source_ref`,并携带 payload 所需的 safe reason、marker、trace context 或 occurred time。
2. 保持 outbox record 极简,但定义正式 source loader,例如 `load_<event>_source(outbox_id)`,并说明它如何从 `outbox_id` 找到 committed source object 和 payload supplement。

每个 outbound event 至少要说明:

- outbox record 中保存哪些 source identity / reason / marker / trace fields。
- publisher 读取哪个 repository / port 回查 committed source object。
- payload 字段哪些来自 source object,哪些来自 outbox record。
- source missing、event kind / source mismatch、payload supplement missing 时如何 mark failed。
- publisher adapter 接收的是完整 outbound publication material,还是 outbox record;若只接收 outbox record,必须证明 adapter 有正式 source loader,不得自行扫描 storage 或用 latest state 补字段。

禁止写法:

```text
WorkOutboxRecord 只有 outbox_id、event_kind、publication_state。
Publisher 根据 outbox ref load source object。
ProjectChangedEvent::from_project(project, reason)。
```

错误原因:

- `outbox_id` 没有定义到 Project / Backlog / trace / derived view 的回查路径。
- `event_kind` 无法携带 payload 所需的 reason、handoff marker、trace context 或 occurred_at。
- publisher 会被迫自行解析 id、扫描 repository、读取 latest truth 或发明 typed source loader,形成第二真相。

正确示例:

```text
WorkTruthChange::BacklogAvailabilityChanged(BacklogRef)
  -> WorkOutboxEventKind::BacklogChanged
  -> WorkOutboxSourceRef::Backlog { backlog_ref, reason }
  -> BacklogChangedEvent { backlog_ref, project_ref, backlog_state, reason }
  -> work.backlog.changed.v1
```

错误示例:

```text
WorkTruthChange::BacklogAvailabilityChanged 已进入 outbox。
Outbound event list 只有 ProjectChanged,且 ProjectChangedEvent 没有 backlog_state / BacklogMaintenanceReason。
```

错误原因:

- 实现者无法判断 backlog availability 是否应复用 ProjectChanged 或新增事件。
- outbox event kind、payload builder、topic 和 publisher dispatch 无法 1:1 落码。
- 测试与验收仍按旧事件数量编排,会漏掉新增 truth change 的发布闭环。

## 四、状态闭环标准

### 4.1 状态名必须全链路一致

以下位置必须使用同一套正式状态名：

- domain enum
- state matrix
- protocol DTO / event
- query projection
- test case
- acceptance criteria
- implementation plan

错误示例：

```text
03-详细设计: Rejected
Step 6 object contract: Failed
Step 10 state matrix: Failed
测试断言: Rejected
```

错误原因：

- 代码 enum、测试断言和验收结果无法统一。

### 4.2 transition 必须归属唯一 phase

每条状态迁移必须明确由哪个 command / flow / phase 推进。

正确示例：

```text
PH-03 RunDeliveryProgression: Pending -> Delivered / Failed
PH-05 RecordDeliveryFeedback: Delivered -> Completed
```

错误示例：

```text
PH-03 测试要求 RunDeliveryProgression 直接到 Completed。
PH-05 又定义 feedback 才能 mark_completed。
```

错误原因：

- 一个状态被两个 phase 同时拥有。

### 4.3 状态矩阵引用的错误必须进入错误模型

状态矩阵、非法转换表、flow 错误映射或测试切口中出现的每个错误 variant,都必须在正式错误模型中有定义。

最少要闭合:

- 所属层和模块,例如 `DomainError` / `ApplicationError` / `JobError`
- enum variant 或错误类型名称
- 触发条件
- 是否可重试
- 对外映射
- 恢复口径
- 测试断言或 evidence 口径

正确示例:

```text
TraceHandoffState.RetryPending -> RetryPending 的 mark_retry(...) 在超限时返回 DomainError::RetryLimitExceeded。
Step 12 错误类型表定义 DomainError::RetryLimitExceeded。
错误映射为 handoff Failed marker / operations evidence。
恢复口径为停止自动 retry,由 operations review 或创建新 handoff intent。
测试断言 TC-CONV-HANDOFF-* 使用 RetryLimitExceeded 或 failed marker。
```

错误示例:

```text
Step 10 状态矩阵写 DomainError::RetryLimitExceeded。
Step 12 错误模型只列 InvalidStateTransition、BoundaryViolation、DigestMismatch。
实现仓 domain errors.rs 也没有 RetryLimitExceeded。
```

错误原因:

- 实现者无法 1:1 定义 domain error enum。
- 状态机单测无法选择断言 `InvalidStateTransition` 还是 `RetryLimitExceeded`。
- application / job 层无法稳定映射 retry exhausted 与普通非法状态。
- 后续实现会被迫自行补错误 variant 或把精确错误退化成泛化错误。

### 4.4 factory 初始状态必须保留 command 可执行迁移

只要当前 phase 的 command / flow 会调用某个 domain transition method,该对象的 factory 初始状态、状态矩阵和 flow 伪码必须共同保留一条可执行迁移。

不得让 factory 直接创建到该 command method 的目标终态,再让 flow 对同一个对象调用 no-op 或非法 transition。

最少要闭合:

- factory 根据 kind / source / intent 选择的初始状态。
- command flow 调用的 domain method。
- 状态矩阵中该 method 的 `from -> to` 迁移。
- 目标终态是否允许 factory 直接创建;若允许,必须说明该 flow 不再调用对应 transition method。
- domain / service 测试同时覆盖 factory 初始状态和 command transition。

正确示例:

```text
GatewayKind::ParallelJoin factory -> GatewayState::PendingJoin。
JoinGateway flow 调用 Gateway.join_tokens(token_set)。
状态矩阵定义 PendingJoin -> Joined。
测试覆盖 pure join factory 初始为 PendingJoin,以及 PendingJoin -> Joined 后 selected_route_ref 为空。
```

错误示例:

```text
GatewayKind::ParallelJoin factory -> GatewayState::Joined。
JoinGateway flow 仍然调用 Gateway.join_tokens(token_set)。
状态矩阵只定义 RouteSelected -> Joined。
```

错误原因:

- command flow 没有合法 from-state,实现者只能把 transition 写成 no-op、放宽非法状态或自行新增状态。
- domain 单测无法判断 pure join gateway 是创建即终态,还是必须由 JoinGateway 推进。
- application flow 与状态矩阵对同一 command 的职责不一致。

### 4.5 public target enum variant 必须穷尽闭环

只要一个 `*Target`、`*Decision`、`*Action` 或等价 public command target enum 进入 request DTO,其中每个未标记为 reserved / future-only 的 variant 都必须有正式闭环。

最少要闭合:

- request DTO schema 和字段表。
- variant 到 domain method 的 flow 分支。
- variant 对应的 reason / evidence / actor / version 校验口径。
- 状态矩阵中的 from / to 迁移。
- contract / domain / service 测试切口。
- 验收接口或 evidence 映射。

如果某个 variant 暂不暴露为当前 boundary 的 public write path,必须二选一:

- 从 public DTO enum 中移除该 variant。
- 明确标注该 variant 为 reserved / future-only,并说明当前 flow must reject 或不接受该值。

正确示例:

```text
DependencyTarget includes Active / Satisfied / Waived / Cancelled.
UpdateWorkDependencyStateFlow has branches for all four variants.
Active requires DependencyChangeReasonKind::Activated and performs Proposed -> Active.
Satisfied requires verified evidence and DependencyChangeReasonKind::SatisfiedByEvidence.
Step 10 and tests cover Proposed -> Active and Active -> terminal.
```

错误示例:

```text
public enum DependencyTarget includes Active.
State matrix says Proposed -> Active via UpdateWorkDependencyStateFlow.
Flow pseudo-code only handles Satisfied / Waived / Cancelled.
Test plan only covers Active -> terminal.
```

错误原因:

- 实现者无法判断 public DTO 是否应该接受 `Active`。
- domain state test 和 application contract test 会选择不同状态范围。
- 后续 service / outbox / audit 分支会形成第二真相。

### 4.6 history record 构造必须闭环

如果 flow、transaction boundary、state matrix、test cut 或验收标准要求 `append history`、`write history`、`history record` 或等价副作用,设计必须同时给出对应 history object 的正式构造闭环。

最少要闭合:

- history record 的 schema、归属模块、主键和 append-only 语义。
- history / progression record 主键的来源;若 domain 不得自行生成 id,必须在 `IdGeneratorPort` 或等价 application id source 中定义对应 `new_*_id()` 方法,并让 factory / domain method 接收该 id。
- factory / constructor 签名,以及每个输入参数的来源。
- history 字段从哪个 truth、request、policy output 或 adapter result 读取。
- 哪些 flow 可以构造该 history,哪些相似 flow 明确不构造。
- transaction boundary 中 state save、history append、trace / outbox、idempotency complete 的顺序。
- 测试断言是检查 history object,还是只检查 trace / audit / outbox。
- 若某个 domain method 返回 history / progression record,该 method 的入参和对象可见字段必须足够构造 record 的所有必填字段;否则 method 只能返回 `()` / changed entity / marker,由 application 在同一 UoW 用正式 factory 构造 record。
- 若 history / progression record 的字段来自多个同事务 truth 变更,必须明确构造时机晚于所有字段来源形成;前置 domain transition 只能返回 state delta / transition outcome,不得提前返回完整 record。

通用文案不得把 `history / trace` 写成所有 accepted command 都必须追加一个 history record。若某个 lifecycle-only flow 没有可定义的 history 字段来源,必须明确写成 trace / audit / outbox only,或先补 history schema 与 factory。

正确示例:

```text
IterationChangeRecord { change_id, iteration_ref, changed_work_refs }
factory: from_commitment(change_id, iteration, commitment, actor)
only used by CommitIterationScopeFlow and UpdateIterationCommitmentFlow.
UpdateIterationLifecycleFlow does not append IterationChangeRecord;
lifecycle change is represented by iteration save、optional commitment close、trace、IterationChanged outbox and projection stale.
```

错误示例:

```text
UpdateIterationLifecycleFlow -> append IterationChangeRecord.
IterationChangeRecord only has from_commitment(...), with changed_work_refs from commitment.
Lifecycle flow has no changed_work_refs source, so implementation constructs changed_work_refs = [].
```

错误原因:

- 实现者会被迫发明空 history、临时 constructor 或第二 truth。
- transaction tests 无法判断应断言 history append 还是 trace / outbox。
- append-only history 表会保存语义不成立的记录,后续 query / evidence 会误读业务变化。

正确示例:

```text
ActivityTransitionOutcome { progression_id, activity_ref, from_state, to_state, feedback_ref } is returned by Activity.ready/start/complete/...。
ActivityProgressionRecord { progression_id, activity_ref, from_state, to_state, feedback_ref, token_refs, gateway_ref, selected_route_ref }
IdGeneratorPort.new_activity_progression_id() -> ActivityProgressionId。
Activity.ready(progression_id, actor) -> ActivityTransitionOutcome。
ActivityProgressionRecord::from_activity_transition(outcome, changed_token_refs, changed_gateway) is called by application after token / gateway flow-control truth has changed in the same UoW。
ProcessInstance.advance(activity_ref, actor) -> () only updates current_activity_ref;
it does not return ActivityProgressionRecord because ProcessInstance cannot see from_state / to_state / token_refs / gateway_ref.

ProcessTraceRecord::from_truth_change(trace_id, change, trace_context) is called by application after committed truth.
IdGeneratorPort.new_process_trace_id() -> ProcessTraceId。
ProcessInstance.complete(actor) -> () only updates instance_state;
ProcessInstance.cancel(reason, actor) -> () only updates instance_state / terminal truth.
They do not return ProcessTraceRecord because ProcessInstance cannot see trace_id or TraceContext.
```

错误示例:

```text
ActivityProgressionRecord requires progression_id.
factory: from_activity_transition(activity, from_state, to_state, token_refs, gateway)
IdGeneratorPort has no new_activity_progression_id.
Activity.ready(progression_id, actor) -> ActivityProgressionRecord,
but token_refs / gateway_ref / selected_route_ref are only known after token / gateway flow-control runs.
ProcessInstance.advance(activity_ref, actor) -> ActivityProgressionRecord,
but ProcessInstance has no activity state, feedback ref, token refs, or gateway ref fields.

ProcessTraceRecord requires trace_id and TraceContext.
factory: from_truth_change(trace_id, change, trace_context)
IdGeneratorPort has new_process_trace_id(), but ProcessInstance.complete(actor) -> ProcessTraceRecord.
ProcessInstance.cancel(reason, actor) -> ProcessTraceRecord.
The instance object has no trace_id or TraceContext fields.
```

错误原因:

- domain 会被迫自行生成 id,违反 id source 规则。
- factory 无法填充 record 主键。
- 返回 record 的 method 没有足够可见数据,实现只能临时补字段、加载外部对象或构造不完整 record。
- record 构造早于 token / gateway / route 等字段来源形成,会迫使实现从 request 或 adapter 私有字段推导 committed truth。

### 4.7 public command intent 必须结构化闭环

只要 request DTO 中的 `*IntentRef`、`*ProgressionInput`、`*ActionRef` 或等价字段会决定调用哪个 domain method,它就不能是未定义的 opaque string / ref。即使字段名包含 `Ref`,只要它驱动状态迁移或 flow-control 副作用,设计必须把它作为结构化 command intent helper 正式定义。

最少要闭合:

- intent helper 的归属模块、struct / enum schema、variant 和字段级 validation。
- 每个 intent variant 到 domain method 的唯一映射,例如 `Ready -> Activity.ready(progression_id, actor)`。
- variant 需要的 reason、evidence、summary、target、version、scope 和 policy input 来源。
- 同一 command 中 token / gateway / graph / projection 等 flow-control 副作用的 truth 落点。
- 状态矩阵中 from / to 迁移和副作用字段,以及持久化契约中的保存字段 / repository 读取口径。
- command result、outbound event、history / trace 字段是否复制该 intent 造成的 committed truth。
- canonical digest / idempotency 是否使用结构化 intent,以及 duplicate replay 是否返回原 result surface。
- contract / domain / service / event 测试是否覆盖每个非 reserved variant。

正确示例:

```text
ActivityProgressionIntentRef {
  activity_transition: ActivityProgressionTransition,
  flow_control: ActivityFlowControlIntent
}

ActivityProgressionTransition::Complete { reason, feedback_summary_ref }
  -> Activity.complete(progression_id, reason, actor)
  -> feedback summary from ReferenceSnapshotRepository

ActivityFlowControlIntent::SelectGatewayRoute { token_ref, gateway_ref, route_ref, next_position_ref, decision_reason }
  -> ProcessShapeRepository.get_gateway_route_set(gateway_ref)
  -> GatewayRoutingPolicy.assert_route_allowed(...)
  -> Gateway.select_route(route_ref, decision_reason, actor)
  -> Token.move_to(next_position_ref)
  -> Gateway.selected_route_ref is persisted and copied to result/event.
```

错误示例:

```text
AdvanceProcessActivityRequest { progression_ref: ActivityProgressionIntentRef }
Flow says "based on progression_ref call Activity.ready/start/complete/skip/fail".
ActivityProgressionIntentRef has no schema, and selected route is not stored on Gateway.
```

错误原因:

- 实现者无法知道 request 值对应哪个 domain transition。
- token / gateway 副作用会被实现为临时字符串约定或 adapter 私有字段。
- command result、outbound event 和 duplicate replay 无法从 committed truth 复制稳定字段。
- 状态矩阵说“记录 selected route”,但 truth / persistence 没有落点,会形成第二真相。

---

### 4.8 command intent membership / bootstrap summary 读取面必须闭合

只要 command intent 中的 ref 需要校验“属于某个 active profile、runtime shape、external snapshot、safe summary 或其它正式集合”,并且 flow 还要用该 ref 构造 domain object、选择 kind、创建 gateway / route / token / activity、或校验是否需要 tracking,设计不能只写“validate against shape / profile / summary”。必须定义正式 body-free summary schema 和 repository / port 读取面。

最少要闭合:

- summary 类型归属、字段 schema 和禁止正文规则。
- repository / port 方法签名,包括输入 scope ref、candidate ref、返回 `Option<Summary>` / error、空结果语义。
- summary 字段到 domain factory / policy 的映射,例如 `activity_kind -> Activity::from_shape_node(...)`。
- request intent 字段与 summary 字段的匹配规则,包括 required / forbidden / mismatch 的错误口径。
- id 生成来源:caller ref 若只是 shape / external summary identity,不得替代本仓 truth id。
- contract / service / fake 测试覆盖 success、missing summary、membership mismatch、required field missing、forbidden field present 和 kind 来源。
- 明确不得读取外部 body、runtime shape body、adapter 私有字段、storage scan 或字符串约定来补 summary。

正确示例:

```text
StartProcessInstanceRequest.start_intent_ref.start_node_ref 要求属于 active profile 的 runtime shape start node set。
Step 7 定义 ProcessShapeRepository.get_start_bootstrap_summary(profile.shape_ref, start_node_ref)
  -> Option<ProcessStartBootstrapSummary>。
ProcessStartBootstrapSummary 包含 start_node_ref、activity_kind、requires_gateway_tracking、initial_gateway { gateway_ref, shape_node_ref, gateway_kind }。
Flow 用 summary.activity_kind 创建 Activity,用 summary.requires_gateway_tracking 校验 request.initial_gateway_ref 是否必填 / 禁止,用 summary.initial_gateway.shape_node_ref / gateway_kind 创建 Gateway。
GatewayId 仍由 IdGeneratorPort 生成;request.initial_gateway_ref 只用于匹配 shape summary。
```

错误示例:

```text
StartProcessInstanceFlow 写:
validate start_node_ref belongs to active profile runtime shape start node set;
initial_gateway_ref only when start node requires gateway tracking;
Activity::from_shape_node(...) requires ActivityKind.

但 Step 7 只有 get_gateway_route_set(gateway_ref),没有 start node set、shape node -> ActivityKind、requires gateway tracking 的读取面。
```

错误原因:

- service 无法判断 start node membership 和 gateway tracking 要求。
- `ActivityKind` / `GatewayKind` 没有正式来源,实现会从 node id 字符串或 adapter 私有状态推断。
- fake repository 无法构造 missing / mismatch / forbidden gateway 的 contract test。
- caller ref 可能被误用为本仓生成的 `GatewayId` 或其它 truth id。
- duplicate result、trace、outbox 和 integration tests 无法证明 bootstrap 使用的是 committed body-free shape summary。

## 五、metadata / idempotency / UoW 标准

### 5.1 metadata authority 必须唯一

每个项目必须说明 metadata 来源：

- 复用上游 shared metadata
- 本项目 wrapper shared metadata
- 本项目自定义 metadata

如果复用上游，就不得在本地 DTO 中重复承载同一字段。

正确示例：

```text
Conversation command 使用 core_contracts::CommandMetadata.request 承载 request_id、trace_id、idempotency_key。
本地 command DTO 不再定义顶层 trace_ref / idempotency_key。
```

错误示例：

```text
本地 command 顶层有 idempotency_key / trace_ref。
core CommandMetadata.request 也有 idempotency_key / trace_id。
```

### 5.2 idempotency 必须定义 digest 和 result ref

幂等契约至少要定义：

- operation
- idempotency key
- request digest
- reserve / complete / conflict 签名
- result_ref / application_result_ref
- duplicate same digest 返回
- same key different digest conflict 返回
- UoW 是否参与
- result_ref 如何读回完整 result surface
- stored result 缺失时的错误 / 恢复口径

正确示例：

```text
IdempotencyRepository.reserve(operation, key, request_digest, uow)。
same key + same digest 返回 Duplicate(result_ref)。
same key + different digest 返回 Conflict(conflict_ref)。
CommandResultRepository.get_result(result_ref) 读取原 result surface。
```

错误示例：

```text
IdempotencyRepository.reserve(operation, key)。
duplicate/conflict 根据 request digest 判断。
```

错误原因：

- repository 签名没有 digest，却要求 digest 语义。

### 5.3 duplicate result surface 必须有读取闭环

如果设计要求 duplicate same digest 返回“既有 result surface”,不能只定义 `result_ref` / `application_result_ref`。必须继续定义这个 ref 到完整 public result DTO 的读取链路。

至少要定义：

- result surface 存储位置或重构来源。
- 保存 result surface 的 repository / port / store 签名。
- success path 中 result surface save 与 `IdempotencyRepository.complete(...)` 的 UoW 顺序。
- duplicate path 中按 `result_ref` load 的 repository / port 签名。
- result kind / operation 不匹配时的错误。
- result surface 缺失时的错误、恢复和对外映射。
- duplicate receipt 是持久化原值还是 replay 时 overlay。
- 禁止重放 domain transition 的边界。

若 duplicate 对象是 operations job,且文档写了 “duplicate returns stored report / existing report / existing marker”,同样必须定义 job report result surface。不能只定义 command result store,也不能让 job duplicate 重新扫描当前 truth / projection / outbox 后临时生成一个新 report。

### 5.4 optimistic version 必须有来源闭环

如果 repository / port / flow 要求 `save(entity, expected_version, uow)` 或等价 optimistic lock 参数,设计不能只写 `expected_version` / `current_version` 变量名。必须说明该 version 从哪里来,并让读取 / 请求 / 创建路径 1:1 可落码。

合法来源只能是:

- public command / job request 中的 `expected_version` 字段,且协议 schema 和字段表已定义。
- 同一 flow 内前置 `create(...) -> Version` 或等价新建返回值。
- repository / port 的带 version 读取函数,例如 `get_with_version(id) -> Option<(Entity, Version)>` 或 `get_by_project_with_version(project_ref) -> Option<(Backlog, Version)>`。

如果 service 内部级联更新另一个 aggregate / truth,不应临时要求 public request 增加内部 aggregate 的 version,除非该 version 本来就是 public command 语义的一部分。更常见的正确做法是为该内部读取补正式带 version 的 repository 函数。

正确示例:

```text
UpdateProjectLifecycle archive path:
BacklogRepository.get_by_project_with_version(project_ref) -> Option<(Backlog, Version)>。
Backlog.archive_with_project(project_ref, actor)。
BacklogRepository.save(backlog, current_backlog_version, uow)。
```

错误示例:

```text
let backlog = BacklogRepository.get_by_project(project_ref)?;
BacklogRepository.save(backlog, current_backlog_version, uow)?;
```

错误原因:

- `current_backlog_version` 没有正式读取来源。
- repository save 要求 optimistic version,但 trait 只返回 entity。
- 实现者会被迫自行补 `get_with_version`、把 version 塞进 public request,或绕过 optimistic lock。

推荐默认口径:

```text
CommandResultRepository.save_result(result_ref, StoredCommandResult, &uow)
  必须先于 IdempotencyRepository.complete(reservation, result_ref, &uow)。

IdempotencyRepository.Duplicate(result_ref)
  -> CommandResultRepository.get_result(result_ref)
  -> return stored result with duplicate receipt overlay。

JobResultRepository.save_report(result_ref, StoredJobResult, &uow)
  必须先于 IdempotencyRepository.complete(reservation, result_ref, &uow)。

IdempotencyRepository.Duplicate(result_ref)
  -> JobResultRepository.get_report(result_ref)
  -> return stored job report;若 report 携带 receipt,只 overlay duplicate receipt。
```

错误示例：

```text
IdempotencyRepository.complete(..., result_ref)。
Duplicate(result_ref) => load_duplicate_result(result_ref)。
```

错误原因：

- 没有定义 `load_duplicate_result` 由哪个 port 提供。
- 没有定义 result_ref 指向哪个 stored DTO。
- 实现者只能自行选择“从当前 truth 重算”或“另存完整 result”,会形成第二真相源。

### 5.5 runtime technical write 与 domain truth write 必须分层

如果 runtime boundary 禁止 domain truth 写事务，但允许技术记录写入，必须明确：

- 是否开启 technical UoW
- technical UoW 覆盖哪些 repository
- 是否拆 runtime repository

错误示例：

```text
Runtime boundary 不开启 SDK domain truth 写事务。
SdkIdempotencyRepository.reserve(...) 又必须带 UnitOfWorkHandle。
flow 中调用 reserve(...) 没有 uow。
```

## 六、projection rebuild 标准

### 6.1 每个 projection 必须声明 rebuild truth source

projection rebuild 只能来自：

- committed domain truth
- committed event / outbox truth
- formally declared artifact replay source
- upstream snapshot truth

不能从 projection 自己重建 projection。

projection rebuild 表：

| Projection | Rebuild source | Source fields | Replay / repository port | 缺失处理 |
|---|---|---|---|---|

正确示例：

```text
DocsExampleView 从 committed docs evidence artifact replay。
DocsEvidenceArtifactReaderPort.read_examples(evidence_artifact_ref) 返回 example 明细。
```

错误示例：

```text
RebuildSdkProjections 重建 docs example projection。
VerificationEvidence 只存 aggregate fields。
DocsExampleView 明细只在 projection table 中。
```

错误原因：

- truth 不含 projection 明细，无法重建。

## 七、artifact / evidence 标准

### 7.1 需要运行的 artifact 必须可 materialize

如果测试、docs runner、validation runner、package runner 需要实际运行 artifact，设计必须提供 materialization 口径。

可选方式：

- job input 携带 run-scoped artifact root
- artifact metadata 携带 location ref
- artifact store port 提供 resolve / materialize 接口

错误示例：

```text
ValidateDocsExamples 输入 candidate_id + docs_example_set_ref + language_set。
Runner 要运行 candidate artifact。
Artifact metadata 只有 artifact_ref / digest，没有 path / location / materialize port。
```

错误原因：

- runner 无法拿到可执行材料。

### 7.2 artifact / report 路径必须跨文档一致

以下文档中的路径必须一致：

- `04-配置设计.md`
- `05-测试方案.md`
- `06-验收标准.md`
- `07-实施计划.md`
- scripts / gates / reports 契约

正确示例：

```text
gate artifact root: artifacts/test/<run_id>
run report root: reports/runs/<run_id>
acceptance report root: reports/acceptance
```

错误示例：

```text
配置默认 ./artifacts/sdk。
测试方案要求 artifacts/test/<run_id>。
验收标准固定 artifacts/test/<run_id>。
```

---

### 7.3 report generator 与最终证据必须区分成熟度

如果 report generator / redaction checker / path checker 先于最终送验证据落码,设计必须显式区分以下成熟度:

- script capability: 脚本参数、路径检查、失败摘要和 redaction 初稿能独立运行。
- minimal index shell: 从 run-scoped machine artifact 渲染最小 `evidence-index.md`,只证明 EV / TC / suite / path 链接形态可解析。
- final EV detail pages: 每个 P0 EV 的人类可读明细页已生成并被完整 evidence index 引用。
- acceptance handoff: `reports/acceptance/*` 已生成初稿并由人或 Agent 审查补充。

commit boundary 必须说明当前阶段允许生成哪一层,并明确禁止提前生成哪一层。不得把“最小 evidence index 壳”与“完整 EV 明细页 / 验收结论”混写成同一个输出。

正确示例:

```text
commit-08-a: generate_reports.sh 支持 --run-id,检查 path shape,生成 summary、gate-results、redaction-check 和最小 evidence-index.md 壳。
commit-08-a 不生成最终 EV 明细页,不生成 acceptance 结论。
commit-08-b: 生成完整 evidence-index.md、EV-CONV-*.md、acceptance handoff、veto checklist 和 risk/open issues 初稿。
```

错误示例:

```text
commit-08-a 交付 report generator。
测试方案要求 generate_reports.sh 生成 evidence-index.md。
实施计划又把 evidence index 全部放到 commit-08-b。
```

错误原因:

- 实现者无法判断当前阶段是否必须生成 `reports/runs/<run_id>/evidence-index.md`。
- 脚本能力、索引壳、最终 EV 页面和 acceptance conclusion 混在一起,导致 phase boundary 不可审查。

## 八、正反例总表

| 场景 | 正例 | 反例 |
|---|---|---|
| DTO 可选字段 | schema 写 `Option<T>`，并定义 derive source | schema 必填，字段表又说可缺失 |
| Domain 必填字段 | request 字段传入 factory | request 有字段，factory 没参数 |
| 状态条件字段 | `Completed` 要求 evidence 时 truth schema 有 `completion_ref: Option<...>` 且 transition 写入 | 状态矩阵要求 evidence,对象 schema 没有承载字段 |
| Query response view | view / page / marker 都有字段 schema 和 empty / stale / not visible 口径 | 只写返回类型名或 builder 名 |
| Projection stale identity | `mark_stale` 的 affected views 全部来自正式 public view ref;从 external ref 标脏时有正式 repository / port 枚举 existing public view refs;没有 query / projection surface 就明确不标脏 | 写路径要求 projection stale,但实现临时派生 `promote-*` / `intake-*` view ref;或只写 `affected_*_views(ref)` 却没有读取面 |
| Ref 到 scope 解析 | flow 调用正式 repository / resolver 得到 scope DTO 后再读 graph / 标 stale | flow 写 `project_ref_from(work_ref)` 或实现者解析 id 字符串 |
| Query view 传递类型 | view 字段引用的 enum / ref 归属到 contracts shared 或有正式映射 | contracts view 字段直接引用 domain-only enum |
| Repository page helper | `Page<T>` / `PageInfo` 有 application port schema,并映射到 public page DTO | repository 返回 `Page<T>`,但没有定义 `Page` / `page_info` 字段 |
| Ref 类型 | 新增 `EventSemanticMappingRef` 并定义 lookup key | protocol 使用 `"event_mapping_01"`，对象契约无 ref 类型 |
| 校验规则 | 定义 repository / port lookup | 只写“必须属于 public surface” |
| 状态名 | enum / matrix / test 使用同一名称 | `Failed` 与 `Rejected` 混用 |
| Factory 初始状态 | factory 初始 state 给当前 phase command method 保留可执行 from-state | factory 直接落 command target 终态,flow 仍调用 transition method |
| Public target variant | request enum 的每个非 reserved variant 都有 flow branch、reason / evidence 校验、state matrix 和测试映射 | enum 有 `Active`,但 flow / tests 只覆盖 terminal targets |
| Phase boundary | flow 只调用本 phase 允许对象 | 当前 phase 调用后续 phase 对象 |
| Projection rebuild | 从 committed truth 或 artifact replay | 从 projection 自己重建 |
| Artifact runner | store 有 materialize / resolve | runner 只拿 metadata，无法定位文件 |
| Report evidence maturity | commit boundary 区分 script capability、minimal index shell、final EV pages、acceptance handoff | report generator 早期提交与最终 evidence index 归属互相冲突 |
| Metadata | 复用 core metadata 或正式 wrapper | 顶层 envelope 与 core metadata 双承载 |
| Idempotency | reserve 接收 digest，record 有 result_ref | 语义要求 digest，签名没有 digest |
| Optimistic version | `save(..., expected_version)` 的 version 来自 request / create 返回 / `get_with_version` | flow 使用 `current_version`，但 repository read 只返回 entity |

## 九、开工前复核清单

### 9.1 交付实现前整体审计

在项目正式交给实现 agent 或切换新的 design baseline 前,必须先完成一次整体审计:

| 审计维度 | 通过条件 | 失败处理 |
|---|---|---|
| 切片覆盖 | `07-实施计划.md` 中每个 phase / commit boundary 都被逐一审计 | 补审缺失 boundary |
| 文档范围 | 每个 boundary 至少复核正式 `03/05/06/07` 与必要 `design-calibration` 来源 | 暂停移交,补齐复核范围 |
| 标准覆盖 | 本章适用复核项均有结论,不能只写“遵循标准” | 回到本标准逐项复核 |
| blocker 处理 | 未通过项已回写设计文档并固定新的 design baseline | 不得移交实现 |
| 交付记录 | 审计表记录 boundary、涉及文件/章节、blocker、修复 commit 或 baseline | 补审计记录 |

该审计是交付实现门禁,不是替代实现 agent 在每个 boundary 开工前的复核。整体审计用于提前发现跨文档闭环缺口;开工前复核用于确认当前实现仓基线仍与设计一致。

### 9.2 每个 boundary 开工前复核

每个 phase / commit boundary 开工前必须复核：

| 复核项 | 通过条件 | 失败处理 |
|---|---|---|
| 字段闭环 | 当前 phase 所有 domain 必填字段和状态条件字段均有来源与 truth 承载 | 暂停，回写设计 |
| DTO 构造闭环 | request / event / job 能构造目标对象 | 暂停，回写设计 |
| Query response 闭环 | view / page / marker DTO 有字段 schema、来源和 empty / visibility / degraded surface | 暂停，补 query view schema |
| Projection stale 闭环 | 每个 `mark_stale` affected view 都有正式 public projection identity;无 identity 的 truth / marker 已明确不标脏 | 暂停，补 view identity 或取消 stale 要求 |
| Ref-scope 解析闭环 | 每个由 ref 推导 project / member / visibility / graph scope 的 flow 都有正式 scope DTO、repository / resolver 函数和错误映射 | 暂停，补 scope resolver / repository 读取口径 |
| factory 签名闭环 | flow 调用参数与 object contract 一致 | 暂停，统一签名 |
| 状态闭环 | enum / matrix / test / acceptance 状态名一致,且 factory 初始状态为当前 phase command 保留可执行迁移 | 暂停，统一状态词表或补可执行来源状态 |
| public target 穷尽闭环 | request target / decision enum 的每个非 reserved variant 都有 flow 分支、reason / evidence 校验、状态迁移和测试 / 验收映射 | 暂停，补 flow / test / acceptance 或移除 / reserved 该 variant |
| public command intent 结构化闭环 | request intent / progression input 有结构化 schema、variant-to-method 映射、flow-control 副作用 truth 落点和 result/event 字段来源 | 暂停，补 intent schema / 映射表 / 副作用落点 |
| history 构造闭环 | 每个要求 append history 的 flow 都有正式 history schema、factory、字段来源和测试断言;无来源的 lifecycle / marker flow 已明确 trace / audit / outbox only | 暂停，补 history 契约或删除 history 要求 |
| record id / 返回面闭环 | append-only history / progression / audit-like record 的 id source、factory 入参、domain method 返回类型和对象可见字段一致 | 暂停，补 id generator / factory 入参或调整返回类型 |
| ref identity 闭环 | 所有 lookup ref 都有正式类型和 key | 暂停，补 ref schema |
| validation truth 闭环 | 每条校验都有 truth source 和 port | 暂停，补 source / port |
| metadata 闭环 | metadata authority 唯一 | 暂停，删除双真相 |
| idempotency 闭环 | key / digest / result_ref / UoW 已定义 | 暂停，补幂等契约 |
| projection rebuild 闭环 | projection 有 committed truth source | 暂停，调整 rebuild set 或补 truth |
| public read-model identity | read model / projection / cursor id/ref 有 schema、repository key 和派生规则 | 暂停，补 public ref schema |
| artifact materialization | runner 可解析 artifact location | 暂停，补 location / materialize |
| phase boundary | 不引用后续 phase 对象 / 结果 / 证据;预列未来状态 / 方法已明确 reserved 且当前测试门禁只覆盖非 reserved 子集 | 暂停，调整 phase 或补 reserved 标记 |
| path baseline | config / test / acceptance / scripts 路径一致 | 暂停，统一路径 |

失败处理原则：

```text
实现者不得在代码中自行补字段、自行选择状态名、自行改 phase scope 或自行发明 truth source。
发现设计真相源冲突时，必须暂停当前 boundary，回写设计仓，再基于新 design commit 继续。
```

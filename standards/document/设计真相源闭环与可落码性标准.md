# 设计真相源闭环与可落码性标准

> 本标准用于判断设计文档是否已经达到“实现者可以 1:1 落码”的程度。
> 它不是替代需求、架构、概要、详细、测试、验收或实施计划，而是为这些文档提供统一的闭环复核口径。

## 二、核心原则

### 2.1 设计真相源必须唯一

同一个概念只能有一个正式定义来源。其他文档可以引用、展开或映射，但不能重新定义。

必须唯一的内容包括：

- struct / enum / value object 字段
- command / query / event / job DTO schema
- result / receipt / reason / ref 类型
- 状态枚举与状态迁移
- metadata / idempotency / trace / request digest
- artifact root / report root / evidence root
- phase / commit boundary

正确示例：

```text
SDK 复用 core_contracts::CommandMetadata。
SDK 文档只说明本项目如何使用该 metadata，不重新定义字段。
```

错误示例：

```text
03-详细设计定义 CommandMetadata = idempotency_key + trace_context。
Step 8 定义 CommandMetadata = request_id + requested_at。
core-contracts 又定义 CommandMetadata = RequestMetadata + reason。
```

错误原因：

- 实现者无法判断 public DTO surface。
- 下游测试和上游 contracts 会分别引用不同定义。

### 2.1.1 继续任务必须从真相源恢复

设计 agent 或实现 agent 在继续任务前,必须先恢复当前真相源状态,不能只依赖历史对话、口头“同意”或上下文记忆。

继续任务前必须读取:

- 项目级恢复入口 `projects/<project>/design-calibration/project_execution_ledger.md`。
- 当前阶段对应的正式 `00`~`07` 文档章节。
- 正式章节列出的具体 `design-calibration/...` 校准来源。
- 对应 `<doc>_calibration_flow.md` 的状态台账。
- 当前 Step / 模块文件 `<doc>_step_<NN>_<topic>.md`。
- 当前 phase / commit boundary 的实施计划阅读门禁。
- 如果是实现 agent,还必须读取 `projects/<project>/design-calibration/implementation_execution_ledger.md` 和当前 boundary 台账 `projects/<project>/design-calibration/implementation-boundaries/<boundary_id>.md`。
- 若是实现 blocker 修复,还必须读取 blocker 指向的正式文档、校准文件和本标准相关条目。

blocker 闭口要求:

- 设计闭口必须更新正式文档或对应 `design-calibration` 文件,不能只在对话中确认。
- 多文档讨论链必须同步更新 `project_execution_ledger.md`,确保项目级恢复点、全局 blocker、当前文档 / Step / 模块和下一动作一致。
- 对应 `<doc>_calibration_flow.md` 必须同步更新 Step gate_status、gate_reason 和 next_allowed_action。
- 对应 Step 文件必须同步更新模块级门禁、正式回填状态和自检状态。
- 如果闭口改变 schema、port、state、phase、evidence、artifact 或测试口径,必须同步更新拥有该真相源的正式章节和受影响的下游章节。
- 实现 agent 只以文件中的 baseline 为准;历史对话可作为线索,不得作为正式落码依据。
- 如果文件状态台账与正式文档互相冲突,必须暂停并回报冲突,不得选择其中一边继续落码。
- `/tmp` 计划只能作为临时线索,不得替代项目级执行台账作为长期恢复状态源。

### 2.1.2 实现阶段必须由实施台账和门禁驱动

实现 agent 进入代码仓前,必须按 `代码实施台账与门禁规范.md` 建立或读取实施台账。实施台账不是 checklist,而是实现状态机。它至少必须记录:

- 当前 design baseline,且应是明确 commit hash 或项目正式认可 baseline。
- 当前 phase / commit boundary。
- 当前 `gate_status`。
- 当前 `next_allowed_action`。
- 当前 allowed scope / forbidden scope。
- 当前 blocker、门禁证据和恢复点。

实现阶段的硬规则:

- 没有项目级实施台账和当前 boundary 台账时,不得开始修改代码;必须先创建台账并把 `next_allowed_action` 设为 `read_docs`。
- `gate_status = blocked` 时,不得继续实现或提交;若 blocker 是设计缺口,`next_allowed_action` 必须是 `wait_design`。
- 任何 `pass` 门禁必须有证据,例如命令、文件路径、commit hash、staged file 列表或正式文档位置;不得只写“已完成”。
- 提交前必须通过 Commit Gate,至少覆盖 staged scope、unrelated changes、commit message format、whitespace 和 required checks。
- 提交后必须回写 commit hash、commit message、post-commit status 和下一 boundary / handoff 状态。

实现 agent 发现 schema、port、state、mapper、config key、test evidence schema、artifact schema 或 commit boundary 缺口时,必须:

1. 在 boundary 实施台账中记录 blocker。
2. 把项目级实施台账更新为 `gate_status = blocked`。
3. 把 `next_allowed_action` 更新为 `wait_design` 或 `fix_gate_failure`。
4. 回报设计仓需要闭口的位置和影响范围。
5. 停止自行落码,不得通过 fake 私有语义、字符串推断、临时默认值或本地约定绕过正式设计。

### 2.2 进入实现边界的类型必须有 schema

任何进入 DTO、domain method、factory、repository、event、test fixture 的类型，都不能只停留在名称级描述。

至少要定义：

- 归属文档和模块
- struct / enum / newtype 形态
- 字段或 variant
- 必填 / 可选
- 与上游 / 下游字段的映射
- validation rule
- 缺失、not_found、conflict 或 reject 行为

正确示例：

```rust
/// 会话事实追加失败原因。
pub enum FactAppendRejectionReason {
    /// 请求试图携带正文，而事实协议只允许 payload 引用。
    InlineBodyForbidden,
    /// payload_ref 类型要求 digest，但请求未提供 payload_digest。
    MissingPayloadDigest,
}
```

错误示例：

```text
FactAppendRejectionReason: fact append rejected 时使用。
```

错误原因：

- 无法生成 enum variant。
- 测试无法断言具体失败分支。

### 2.2.1 support carrier / ref-set / status 必须随当前 boundary 闭口

对象字段、DTO 字段、repository 返回值、factory 参数、domain member capability 参数、transition helper 参数、policy method 参数或 test fixture 只要引用了二级支撑类型,这些支撑类型也必须被视为当前实现边界的可落码输入。不能只在主对象字段表里写类型名,也不能只在成员能力表里写 `reason_ref` / `marker_ref` / `summary_ref` / `decision_ref`,却把该类型的 Rust-facing 形态留给实现者自行决定。

适用类型包括但不限于:

- `*Kind` / `*Type` / `*Category`
- `*IdentityKey` / `*CanonicalKey`
- `*Summary` / `*SummaryRefSet`
- `*RefSet` / `*Refs`
- `*Classification` / `*ApplicabilitySummary`
- `*Status` / `*Disposition`
- 当前 boundary 的 helper enum、body-free carrier、marker carrier、selection item
- 当前 boundary 对象成员能力 / factory / transition helper / policy method 的 `*ReasonRef`、`*Marker`、`*Decision`、`*Summary`、`*ContextRef` 参数

必须闭合:

- owner / module / crate 边界:定义该 carrier 属于 contracts、domain、application port、infra adapter state 还是测试 evidence schema。
- owner scope 同步:如果闭口需要新增 typed-ref kind、enum label、registry tag、named wrapper export 或 shared public helper,当前 implementation boundary 的 allowed_scope 必须包含 owning crate/file 的最小变更;否则必须调整 boundary 或改用已有闭口类型,不得让实现端越界修改 owner 或私造 local alias。
- Rust-facing shape:`closed enum`、`newtype`、`struct`、`deterministic ref-set`、`Page<T>`、`NonEmptyVec<T>` 等形态必须唯一。
- enum variant / status label:列出当前 boundary 可用标签、reserved 标签和 forbidden fallback;`*Status` 必须说明与 Step 10 lifecycle/state matrix 的关系。
- struct 字段:每个字段的类型、必填 / 可选、来源和 body-free 限制必须明确。
- ref-set 语义:成员类型、去重键、稳定排序、是否允许 empty、是否保持输入顺序、是否分页、是否禁止携带 body/raw provider payload。
- ref-set member ref exact kind:只闭合 `*RefSet` 壳不算完成;每个 member ref 必须同时闭合 owner typed-ref family、Rust-facing named wrapper、exact kind/variant、合法创建来源和 wrong-kind reject 规则。
- summary / classification / applicability carrier:字段来源必须来自 committed truth、正式 resolver summary、policy output、projection builder output 或 request typed input;禁止混入 raw body、provider 原文、UI label、search snippet、runtime diagnostic、config string 或 fake 私有 payload。
- object member capability parameter:每个参数都必须明确 Rust-facing carrier、是否复用既有 carrier、合法来源、禁止替代和测试红线;若当前 boundary 选择复用 `SafeMarker` / shared typed ref,必须在 formal source 中显式写出,不得让实现端自行推断。
- truth lifecycle / status carrier:凡是 Step 9 flow 或 Step 10 state matrix 要求 truth object 发生业务状态迁移、终态守卫、post-state rejection 或 duplicate replay 观察该状态,当前 boundary 必须在 Step 6 truth object 或等价正式 carrier 中暴露 exact lifecycle/status 字段、enum labels、factory 初始值、transition member、repository 持久化/读取语义和 fake/durable parity。状态机 prose、stored result kind、catalog status、projection status、HTTP status、字符串 status 或 fake private side-state 都不能替代 truth lifecycle carrier。
- state-machine-to-carrier mapping:若 Step 10 使用内部生命周期归纳名,但 Rust-facing 实现使用另一个 status enum,当前 boundary 必须明确二者的 exact mapping、哪些 enum label 由当前 flow 生成、哪些 label 只可读取/拒绝/后移、以及不得 silent default 的标签。`Registered` / `Visible` 这类同义映射不能留给实现端猜。
- same-layer transition helper closure:凡是 Step 9 / Step 10 要求 truth object 执行业务迁移,Step 6 必须在该对象同层闭合 transition helper / member capability、参数 carrier、合法来源、终态守卫和禁止替代。不得让 repository save、stored result、mapper、fake adapter 或 service private function 承担未定义的 domain transition。
- object helper persisted-field coverage:对象 factory / transition helper 的签名或 field-copy rule 必须覆盖当前 boundary 会构造、保存、更新的全部 persisted fields。若 service input 含 `catalog_classification` / `applicability_summary`,对象 helper 不能只写 `definition_ref` / `scope_ref`;否则实现端会被迫自补 helper 参数或保留 stale field。
- opaque-ref factory closure:只列出 opaque named ref wrapper / exact kind 不等于可落码闭口。凡当前 boundary 需要生成 operation context、idempotency、digest、dedup scope、stored result、accepted/rejected/effect/replay refs,必须闭合 application-owned factory/helper port、输入 carrier、输出 carrier、error surface、IdGenerator 使用边界和禁止替代。实现端不得从 route、raw body、timestamp、counter、repository id、typed-ref text 或 fake map 拼 opaque refs。
- flow precondition callable closure:凡是 Step 9 flow 或 Step 10 state matrix 写出会改变 accepted / rejected / conflict / replay 行为的前置检查,当前 implementation boundary 必须在 Step 7 或等价正式 source 中闭合 exact callable surface、输入 carrier、输出 / error surface、fake/durable parity 和 allowed scope。若该前置检查属于后续 phase / boundary,当前 source 必须显式 carve out,写明当前 boundary 不执行该检查、禁止的替代方式和后续 owning boundary。不得让实现端通过新增 repository method、扫描 fake map、解析 typed ref、读取 stored result、借用 catalog/status 或临时 policy helper 自行补 precondition。
- fake / durable 等价:fake 只能实现已定义的 schema、排序、去重、缺失和冲突规则,不得补私有 map、字符串解析或隐式默认值。
- implementation boundary 引用:当前 boundary 若实现主对象或 DTO,其 required 字段所用支撑 carrier 必须在同一 boundary 闭口,或者明确标为 reserved/deferred 且当前代码不需要构造、保存、返回或测试该字段。

禁止做法:

- Step 6 主对象字段表列出 `MethodAssetDefinitionKind`、`MethodAssetIdentityKey`、`ExternalSourceSummaryRefSet`、`MethodAssetCatalogEntryStatus`,但没有任何 schema / variant / fields / set semantics。
- Step 6 已定义 `ExternalSourceSummaryRefSet = Vec<ExternalSourceSummaryRef>`,但 typed-ref family 表没有把 `ExternalSourceSummaryRef` 归入正式 owner family,也没有 exact kind label。
- Step 6 成员能力表写 `MethodAssetCatalogEntry.mark_deprecated(reason_ref)`,但没有说明 `reason_ref` 是 `MethodLibrarySafeMarker`、local `*ReasonRef`、typed ref wrapper 还是 deferred。
- Step 6 要求新增 exact `MethodLibraryTypedBoundaryRefKind` label,但 implementation boundary allowed_scope 没有打开 owning contracts ref registry / export 文件。
- Step 10 写 `MethodAssetDefinition: Active -> Retired`,Step 9 写 `RetireMethodAssetDefinitionFlow mark retired; save`,但 Step 6 的 `MethodAssetDefinition` 没有 `definition_lifecycle` / status 字段,Step 7 repository 又返回 `Versioned<MethodAssetDefinition>`;实现端只能在 fake repository 私下保存 lifecycle 或自行补字段。
- Step 9 写 `retire_definition` 要检查 linked formal version / active formal-version conflict,Step 10 也把它列为 precondition,但当前 boundary 的 Step 7 callable surface 只闭合 definition repository;若不 carve out,实现端只能私造 `FormalMethodAssetVersionRepository` 方法或 fake map 扫描。

- Step 7 `RegisterMethodAssetCatalogEntryInput` 有 `catalog_classification` / `applicability_summary`,但 Step 6 `create_for_definition(definition_ref, scope_ref)` 没有这些参数或 field-copy rule;实现端只能私下扩展 helper 或把 summary 留成默认值。

### 2.2.1A application service / facade / repository callable surface 必须随当前 boundary 闭口

当前 commit boundary 只要要实现 application service、API/worker/jobs facade、repository fake、UnitOfWork、idempotency 或 stored result,设计不能只写“service / repo fake / UoW / stored result”或 family-level port 语义。必须把当前 boundary 可调用的 Rust-facing surface 写到实现者可以直接落 trait / struct / method 的粒度。

必须闭合:

- entry/facade 调用面:entry 允许调用哪个 application facade,输入 carrier 是什么,输出 carrier 是什么,entry 禁止直连哪些 repository/domain/UoW/adapter。
- facade I/O exact schema:facade input/output carrier 不能只给类型名;必须列出 struct 字段、字段类型、必填 / 可选、来源、body-free 限制、allowed family 和 rejected / duplicate / ignored / accepted 输出形态。
- service method 列表:当前 boundary 允许实现哪些 service method,每个 method 的 input carrier、required typed refs / markers / summaries、accepted output 和 rejected output。
- service input exact schema:每个 service `*Input` 必须列出完整字段集合、字段顺序无关规则、optional 语义、expected version / idempotency / digest / dedup / operation context 来源、禁止 fallback 和 test fixture 生成规则;不能只写 required inputs prose。
- repository method 列表:每个 repository 的 exact read / stable lookup / save / append / get 方法名、输入 key、返回类型、missing 语义和冲突语义。
- repository error exact enum:repository error 不能只点名 `VersionConflict` 或说“repository error”;必须列出当前 boundary 允许的 enum variants、每个 variant 字段、safe marker 来源、retry / reject 映射和禁止暴露的 raw SQL/IO/HTTP/panic/fake-only variant。
- version / optimistic lock carrier:`Versioned<T>`、`ExpectedVersion`、`VersionedRef<TRef>` 或等价 carrier 的 owner、字段、来源和禁止替代。
- UnitOfWork 顺序:begin、read、save、stored result、commit / rollback 的逻辑顺序,以及 rollback 后哪些 truth / result / effect 必须不可见。
- stored result / replay surface:save / get / lookup 方法、idempotency key、digest / scope、result variants、完整 replay-safe fields、missing / wrong-digest 处理。
- shared shell selector:如果一个 shared command/query/job shell 通过 facade 分派到多个 exact service input,必须定义 selector enum、唯一 selector source、selector value 到 service input / method 的映射、unsupported / unknown / missing selector 的 safe rejection、required refs/markers 缺失时是否停在同一 selector、duplicate digest 是否包含 selector。不得让实现端从 route、RPC method、DTO type name、typed_refs 顺序、marker 文本、config key、service locator 或 fake private map 推断分支。
- selected input source map:selector 只闭合“选择哪个 service input / method”。若 selected input 的字段不在 shared shell 中,必须定义 exact per-field source map 或 current-boundary body-free source carrier,并写清 source variant 与 selector 的一致性校验、每个字段的 copy source、expected version / repository load source、optional / empty 语义、missing / mismatch / wrong-kind 的 safe rejection、duplicate digest 是否包含 source variant 与字段 canonicalization。不得让实现端从 shell `typed_refs` 顺序/数量、marker 文本、route、DTO type name、config、fake private map 或 raw body 推字段。
- fake / durable parity:fake 的 version、UoW staging、rollback、unique key、duplicate replay、conflict 和 missing 行为必须与 durable 语义一致。
- deferred surface carve-out:如果当前 service flow 提到后续 phase 对象,必须明确本 boundary 只做 named-ref validation / placeholder / no-op,还是必须暂停等后续 phase;不得让实现端猜。

禁止做法:

- Step 7 只写 `MethodAssetDefinitionRepository: definition exact read, identity lookup, versioned save`,没有 `get_*_with_version` / `find_*` / `save_*` 方法名、输入、返回和 conflict 语义。
- Step 6 API entry 字段写 `application_dispatch_ref`,但 Step 7 没有定义 dispatch ref 的 exact carrier、合法值和 application facade。
- Step 7 写 `MethodAssetDefinitionCatalogCommandDispatchInput`、`EstablishMethodAssetDefinitionInput` 等名称和 required inputs,但没有列出 exact struct 字段、optional 字段、来源和 forbidden fallback。

### 2.2.2 跨仓 shared type 必须在上游实现中可检索

如果设计声明某个类型“来自 `L0-core` / `core-contracts` / sibling contracts,本仓不得重新定义”,则该类型必须同时满足:

- 上游正式设计给出 schema 或引用到已存在 schema。
- 上游实现仓有可检索的类型定义。
- 上游 contracts crate 已导出该类型,下游 package 能通过允许的 dependency import。
- 本仓只说明字段映射和使用场景,不得重新定义字段或临时 newtype。

若上游实现仓不存在该类型,设计者只能二选一:

1. 先升级上游 contracts 并形成新的 committed baseline。
2. 本仓设计改用上游已经存在且已导出的 shared type,并同步对象、DTO、port、flow、persistence、测试和实施 boundary。

正确示例:

```text
Governance 需要传播分布式 trace。
core-contracts 已有 RequestMetadata.trace_id: TraceId,且 TraceId 已导出。
Governance 对象字段使用 core_trace_id: TraceId,并规定 command 来源为 CommandMetadata.request.trace_id。
```

错误示例:

```text
GovernanceTraceRecord.trace_context: TraceContext。
字段表写“TraceContext 来自 L0-core,本仓不得重新定义”。
但 core-contracts 中没有 TraceContext 类型,只有 RequestMetadata.trace_id。
```

错误原因:

- 实现者无法 import 正式类型。
- 本仓若自行定义 `TraceContext` 会违反真相源唯一。
- 若临时用 String 或 TraceId 代替,又会偏离字段名、DTO schema、persistence 和测试断言。

### 2.3 设计必须按闭环链路复核

每个 command / query / event / job 至少要完成以下链路复核：

```text
Request / Event / Job DTO
  -> Metadata / Context
  -> Application flow
  -> Domain factory / method
  -> Repository / Port / Adapter
  -> Outbox / Event / Projection / Artifact
  -> Result / Receipt
  -> State matrix
  -> Test / Acceptance
  -> Implementation phase / commit boundary
```

如果链路中任一节点缺字段、缺类型、缺 truth source 或依赖后续 phase，本项不能交给实现者自行处理。

设计准备移交给实现 agent 前,不得只声明“适用本标准”。必须由设计者按 `07-实施计划.md` 的 phase / commit boundary 对正式 `03-详细设计.md`、`05-测试方案.md`、`06-验收标准.md` 和 `07-实施计划.md` 做一次整体可落码闭环审计。审计输出至少记录 boundary、复核范围、适用标准项、结论、blocker、修复后的 design baseline。未通过时先回写设计真相源并重复核,不得把问题留给实现阶段逐个暴露。

实现 agent 的责任是开工前二次校验和执行期阻塞回报:确认当前实现仓、设计 baseline 和实施计划复核结论仍一致;发现设计与实现条件不符时暂停并回报具体缺口。实现 agent 不承担现场补 schema、补 port、改 phase boundary 或替设计者选择口径的责任。

```json
{ "visibility_scope_id": "VisibilityScopeId" }
```

同时字段表写：

- Rust DTO 无法同时表达必填和可省略。

### 2.5 每条校验规则必须有 truth source

凡是设计中出现以下规则，必须同时定义读取来源：

- ref 必须存在
- ref 必须属于某 public surface
- replacement ref 必须可解析
- version 必须大于当前版本
- scope 必须允许 read / append / publish
- artifact digest 必须匹配
- projection freshness 必须可判定

校验规则最小定义：

| 项 | 要求 |
|---|---|
| 输入字段 | 待校验的 DTO / command / query 字段 |
| truth source | domain truth / upstream snapshot / repository / artifact replay source |
| lookup port | 具体 repository / port / adapter 方法 |
| 失败行为 | not_found / reject / conflict / quarantine / error |
| 测试切口 | 对应 TC / AC / unit test |

正确示例：

```text
replacement_api_ref 必须通过 PublicSdkApiRepository.get(api_ref) 解析到 public SDK surface。
```

```text

```

错误原因：

- 没有 port 或 truth source，无法落码。

### 2.6 Actor authority 与 scope policy 必须闭合

凡是设计中出现 actor、consumer、source actor、system actor、integration actor、participant scope、visibility scope 或 trusted source 例外,必须明确以下内容:

- actor 字段来自 command metadata、event payload、consumer context、repository lookup 还是系统生成。
- 该 actor 表示业务参与者、系统执行者、外部集成入口还是来源边界代理。
- 是否要求 actor 存在于 participant / membership / visibility scope 中。
- 如果允许 trusted source actor 例外,必须列出适用 source kind、actor kind、入口协议和不可绕过的 gate。
- 普通 actor path 与 trusted source path 的错误映射必须不同步漂移。

最小定义表:

| 项 | 要求 |
|---|---|
| 输入 actor 字段 | `ActorRef` / `SystemActorRef` / `ConsumerRef` 等具体字段 |
| authority kind | participant actor / system actor / integration actor / trusted source actor |
| scope requirement | must be in participant scope / may bypass membership / must match visibility hint |
| exception condition | 具体 source kind、event、fact kind 或 policy rule |
| non-bypass gates | active state、visibility、digest、source isolation、forbidden body、idempotency 等仍需执行的 gate |
| 失败行为 | reject / not visible / quarantine / delayed / fail-closed |

正确示例:

```text
RuntimeResultCommittedEvent.system_actor_ref 是 trusted source actor。
source_kind = RuntimeResult 且 actor_kind = System 时,不要求 actor 出现在 ParticipantScope.participants。
仍必须校验 active space、participant scope appendable、visibility open、payload digest、fact_kind = RuntimeResult、source result-only 和 forbidden-body boundary。
缺失或 actor_kind 不匹配时 quarantine。
```

错误示例:

```text
consumer append 使用 system actor。
append policy 要求 actor 在 participant scope 内。
```

错误原因:

- 实现者无法判断是否应把 system / integration actor 塞进 participant scope。
- accepted event path 会被普通 membership policy 拒掉,或者实现侧会自行放宽所有 append 校验。
- trusted source 例外如果没有 non-bypass gates,会变成绕过 visibility / digest / source isolation 的后门。

### 2.7 Ref 到 scope 的解析口径必须闭合

凡是 flow、policy、repository call 或 projection stale 要求从一个 public ref 得到 project / member / space / participant / backlog / visibility / tenant 等 scope,设计必须给出正式解析来源。

必须明确：

- 输入 ref 类型,例如 `FormalWorkRef`、`ExternalFactRef`、`ConversationRef`。
- 输出 scope schema,例如 `{ project_ref, backlog_ref, assignee_ref? }`。
- 解析 owner,例如 repository read、resolver port、snapshot store 或 command request 字段。
- 缺失 / 不一致 / stale scope 的错误映射。
- 该 scope 后续用于哪些 policy、graph、projection stale 或 repository key。

禁止在函数流中写未定义 helper,例如 `project_ref_from(work_ref)`、`space_from(actor)`、`visibility_from(payload)`。也禁止让实现者解析 id 字符串、猜测 parent / membership join 或私自增加 repository 依赖。

正确示例：

```text
WorkItemRepository.get_formal_work_scope(work_ref)
  -> Option<FormalWorkScope { work_ref, project_ref, backlog_ref, assignee_ref }>
LinkWorkDependencyFlow 使用 downstream scope 读取 graph snapshot 并构造 project-board / member-work stale refs。
```

错误示例：

```text
DependencyRepository.load_graph_snapshot(project_ref_from(request.downstream_work_ref))
ProjectionRepository.mark_stale(affected public views)
```

错误原因：

- `FormalWorkRef` 本身不携带 project id。
- implementation agent 不知道是否应从 WorkItem、Backlog membership、parent ChildWorkItem 或 request body 取 scope。
- projection stale 的 affected views 无法稳定构造。
- fake adapter / repository tests 无法验证 scope 来源。

### 2.7.1 Query visibility resolution 必须闭合

凡是 public query 在返回 truth view、projection view、report、trace 或 reconciliation artifact 前需要调用 read visibility policy,设计必须在 policy 调用前给出正式的 visibility resolution surface。

必须明确：

- resolution DTO / object 名称,例如 `GovernanceReadVisibilityResolution`。
- resolution 必填字段,至少包括 `read_subject_ref`、`scope_ref`、resolution source marker;如后续 policy 或 view assembly 需要 governed subject、report subject、trace subject,也必须显式入 schema。
- resolution 来源 owner,例如 query request 显式字段、query resolver port、repository read 或 committed view/report 字段。
- request 不携带 scope 时,必须有正式 resolver / repository 读取面;不得让 query service 从 ref 字符串、cursor、timestamp、route path 或 adapter 私有索引反推。
- loaded truth / report / view 字段只能作为一致性校验或 view assembly 输入;若要作为 visibility scope 来源,必须写入 resolution 生成规则。
- missing / mismatch / stale / unauthorized / hidden 的错误或 query status 映射。
- fake adapter 与 durable adapter 的等价语义和测试断言。

正确示例：

```text
GovernanceReadVisibilityResolverPort.resolve_context_read(
  context_ref,
  actor_ref,
) -> GovernanceReadVisibilityResolution {
  read_subject_ref,
  scope_ref,
  governed_subject_ref,
  source_marker,
}

GetGovernanceContextFlow:
  resolution = read_visibility_resolver.resolve_context_read(request.context_ref, actor_ref)
  context = context_repo.get(request.context_ref)
  resolution.assert_matches_loaded_context(context)
  decision = ReadVisibilityPolicy::for_actor(actor_ref, resolution.scope_ref)
    .evaluate(resolution.read_subject_ref)
  if decision.hidden => return NotVisible marker
  assemble view from loaded context
```

错误示例：

```text
GetGovernanceContextFlow:
  scope_ref = scope_from_context_ref(request.context_ref)
  read_subject_ref = read_subject_from_id(request.context_ref)
  ReadVisibilityPolicy::for_actor(actor_ref, scope_ref)
```

错误示例：

```text
GovernanceReadVisibilityResolution::for_loaded_context(context, source_marker)
  // helper 内部从 context_id、context.subject_ref 或本地 fixture 推导 scope/read subject
```

错误原因：

- `context_ref`、`trace_ref` 或 `report_ref` 通常不携带可见性 scope。
- query service 会被迫解析 id 字符串、读取 projection 私有字段或硬编码 fixture。
- loaded truth 字段通常不是 visibility resolution 的完整来源,尤其缺少正式 scope relation / source marker。
- loaded-truth helper 会绕开 Step 7 resolver / repository 读取面。
- fake / durable adapter 容易产生不同可见性结果。
- NotVisible、Filtered、Degraded 等 query marker 无法稳定从正式 decision 复制。
- 正确做法是 resolver-first:先通过正式 resolver 取得 resolution,再用 loaded truth 校验 subject/context 一致性并组装 view。

### 2.8 当前 phase 必须形成依赖闭包

每个 phase / commit boundary 必须明确：

- 可新增对象
- 可读取对象
- 可调用 service / factory / method
- 可用 repository / port
- 可写 truth / projection / artifact
- 可发 event / outbox
- 可执行测试与验收门禁
- 禁止使用的后续 phase 对象
- 预列但当前 boundary reserved 的 enum variant、domain method、DTO、history record 和 state transition

正确示例：

```text
commit-02-b 只生成 DerivedBindingView。
LanguageBindingView 需要 CrossLanguageConceptMap，归 commit-03-a。
因此 commit-02-b 不调用 LanguageBindingView::from_concept_map(...)。
```

错误示例：

```text
commit-02-b flow 生成 language views。
但 semantic baseline / concept map port 在 commit-03-a 才允许使用。
```

错误原因：

- 实现者必须越界引用后续 phase，提交边界不可审查。

### 2.8.1 Public scope branch 展开读取面必须闭合

凡是 public job、query、reconciliation、refresh、handoff 或 rebuild request 中出现 `*Scope` / `*ScopeKind` / `*ScopeRef` enum,且某个 branch 需要展开为一组 refs、subjects、views、artifacts、markers 或 truth summaries,设计必须为每个当前 phase 可执行 branch 给出正式展开口径。

必须明确：

- branch 输入字段,例如 `Project` 需要 `project_ref`,`ExplicitRefs` 需要非空 refs。
- 展开 owner,例如 repository read、resolver port、snapshot store 或 request body。
- 返回集合 schema,例如 `Page<ExternalReferenceRef>`、`Vec<DerivedViewRef>` 或 body-free summary DTO。
- 集合成员来源表,包括允许的 truth / snapshot / marker 来源和必须排除的来源。
- 去重规则、稳定排序规则、分页应用时机和 empty page 语义。
- invalid scope、missing required field、unsupported branch、stale source 的错误映射。
- 展开结果后续用于哪些 resolver、policy、projection stale、job report 或 repository key。

禁止在 flow 中只写 `expand(scope)`、`load_scope_refs(...)`、`refs_for_project(...)` 这类未定义 helper。也禁止让实现者扫描 storage、解析字符串、从 projection 反推 truth,或自行决定 Project / Member / Artifact / Reference scope 包含哪些 ref。

正确示例：

```text
ReferenceSnapshotRepository.list_project_references(project_ref, page)
  -> Page<ExternalReferenceRef>
Project branch 只枚举 committed Work truth / snapshot index 中可发现的 typed external refs,先按 ExternalReferenceRef stable identity 去重并按 variant + canonical inner ref 排序,再分页。
```

错误示例：

```text
if reference_scope is Project:
  refs = affected_project_external_refs(project_ref)
```

错误原因：

- implementation agent 不知道 project scope 是否包含 member、method、source、evidence、timebox 或 handoff refs。
- fake adapter 无法验证分页 / 去重 / empty page。
- resolver job 可能从 projection、event payload 或字符串 id 临时拼接 external reference key。

### 2.8.2 SOP 中间产物分批写入必须保持内容完整

当项目使用 SOP 逐步生成 `design-calibration/` 中间产物时,分批写入是为了降低单次审查风险,不是为了限制章节内容、对象卡片或字段闭环的最终详尽程度。

必须明确:

- 每个 SOP Step 的中间产物先独立完成,不得跳步直接修改正式文档。
- 每批写入可以控制在约 300 行或团队约定的可审查规模内,但该限制只约束单次写入规模,不约束一个章节、对象组或状态表的最终长度。
- 若某个大段内容超过单批规模,必须拆成多批继续写完,不得删减字段、函数、状态、来源、约束、正反例或 blocker 条件。
- 每完成一个批次或 SOP Step 后必须更新校准 flow/status,并停下来让 reviewer 审查。
- 正式 `03-详细设计.md`、`04-配置设计.md` 等目标文档只能在对应装配 Step 中从已完成中间产物汇总写入;不得在早期 Step 边写中间产物边直接修正式文档。

正确示例:

```text
Step 6.1 对象契约需要 900 行。
拆为 6.1-a / 6.1-b / 6.1-c 三批写入,每批约 300 行。
三批都保留完整字段表、函数签名、状态和字段来源。
每批完成后更新 03_ddd_calibration_flow.md 并停审。
正式 03-详细设计.md 等 Step 19 再装配。
```

错误示例:

```text
Step 6.1 只能新增 300 行,因此删掉部分字段来源、状态表和反例。
或者边写 Step 6 中间产物,边直接修改正式 03-详细设计.md。
```

错误原因:

- reviewer 无法判断缺失内容是“尚未写入下一批”还是“被省略”。
- 实现 agent 会把不完整中间产物当作正式 schema,导致字段、状态或读取面缺口。

### 2.8.3 对象契约必须可回指模块功能

详细设计 Step 6 中进入实现边界的对象契约,不能只来自对象名、名词清单、旧实现或一次性生成的全局对象列表。每个对象必须能回指所属模块的正式 capability / 功能,并通过功能到对象映射证明它为什么存在。

必须明确:

- 模块职责和模块需要完成的 capability / 功能。
- 每个功能的输入、输出、状态 / 副作用、协作边界和后续 Step 承接点。
- 每个功能由哪些对象承接,对象类别是 truth object、policy / guard、view / report、application helper、adapter state、entry object 还是 shared helper。
- 每个对象承接哪些对象级能力,不承接哪些能力,是否越过模块边界。
- 对象字段、factory 入参、成员函数、状态 enum、variant 和不变量分别来源于哪个对象能力。
- 每个模块完成后的模块内审查结论:功能是否有人承接、对象是否有功能来源、字段来源是否闭合、状态是否闭合、是否越界。
- 所有模块完成后的跨模块审计结论:shared ref、重复对象、字段传递、状态语义、命名和依赖方向是否一致。

禁止做法:

- 把 contracts、domain、application、infra、worker、jobs 等所有对象一次性混在一个全局对象清单中,没有模块内 capability 来源。
- 从概要设计对象清单机械扩写字段表,没有说明对象承接哪个功能。
- 根据对象名、旧代码或测试愿望猜字段、factory 入参和状态 variant。
- 以 shared vocabulary 为理由把具体 truth object、policy、view、application helper 或 adapter state 长期停留在全局章节。
- 某个对象承接多个不相干模块功能,却没有拆分、重新归属或标为正式 shared helper。

正确示例:

```text
Governance domain module:
  capability:
    - create context
    - open gate
    - record decision
    - close nonconformity
  功能到对象:
    - GovernanceContext 承接 context readiness
    - Gate 承接 pending decision
    - GovernanceDecision 承接 formal outcome
  对象能力到字段 / 函数:
    - Gate::open(gate_id, context_ref, requirement_ref, actor)
    - Gate.state: Pending / Satisfied / Rejected
    - requirement_ref 来源于 command intent 或 committed requirement truth
module 审查通过后,再进入 application module。
所有模块完成后做 shared ref、字段来源、状态语义和依赖方向审计。
```

错误示例:

```text
Step 6:
  Object list:
    GovernanceContext
    Gate
    GovernanceDecision
    WorkflowService
    ProjectionStore
字段:
  根据名称补充 id、state、created_at。
状态:
  Pending / Done / Failed。
```

错误原因:

- 不知道 `WorkflowService` 属于哪个模块,也不知道它承接哪个 capability。
- `Gate.state` 的 variant 没有来源功能、允许迁移和副作用。
- `created_at` 字段没有说明来自 command metadata、system clock、trace context 还是 persistence metadata。
- Step 7 / 8 / 9 无法判断 port、DTO、flow 应该调用哪个对象能力。
- 正式文档与中间产物提前分叉,后续 Step 19 装配失去真相源。

### 2.8.4 无人值守流式执行不得压缩 Step 内校准

当用户允许 Agent 自动完成多个 SOP Step 时,自动化只替代人工逐步确认,不能替代 Step 内的推导过程。每个 Step 的中间产物必须证明结论是从问题回答、诊断和取舍中收敛出来的,而不是先生成正式结论再补模板栏目。

必须明确:

- 自动执行多个 Step 时,仍然逐 Step 落盘、逐 Step 更新 flow/status。
- 单个 Step 内部按 `问题回答 -> 当前材料诊断 -> 设计取舍 -> 结构化中间产物 -> 复杂度判断 -> 回填草稿 -> 自检` 顺序推进。
- 问题回答阶段不得提前输出最终对象表、接口表、状态表或正式章节草稿。
- 诊断阶段必须指出具体旧材料、当前草稿或上游输入中的缺口,不得只写“需要更清晰”。
- 取舍阶段必须有未采用方案或后移方案,说明为什么不采用。
- 复杂 Step 必须判断是否按能力、模块、对象组、接口族、状态机或测试切口拆分;需要拆分时先拆主控文件和附录,不得压缩成一张总表。
- 回填草稿只能从结构化中间产物摘录,不能引入中间产物没有出现的新结论。
- 自检发现缺口时,必须回到对应小阶段修正,不能把缺口交给后续正式文档或实现 agent。

正确示例:

```text
自动执行 L1-identity 02 Step 6。
Step 内先回答 SOP 问题:
  - 哪些主要组成部分需要对象承接?
  - 哪些对象是 truth / state / policy / projection / reference / outbox?
  - 哪些名称不得作为关键对象?
再诊断旧材料:
  - GlobalMember 与 ProjectMember 边界是否混层。
  - RoleCapabilitySummary 是否误保存 RoleDefinition body。
  - MemoryReference 是否误保存 memory body。
再做取舍:
  - 采用按 identity anchor / lifecycle / role capability / career / memory / projection / outbox 分附录。
  - 不采用全仓对象一张表。
最后每个模块输出 capability -> object -> field/function -> prohibition,再 assembly 正式 02。
```

错误示例:

```text
自动执行 L1-identity 00~02。
每个 step 生成一个有十段标题的文件。
02 Step 6 中:
  - 问题回答写“本仓关键对象包括 GlobalMember、LifecycleState、RoleCapabilitySummary 等”。
  - 诊断写“旧文档对象边界不够清晰”。
  - 取舍写“采用分层对象模型”。
  - 结构化产物直接给出所有对象、字段、函数总表。
正式 02 再把字段和 flow 扩得很厚。
```

错误原因:

- 标题完整不等于校准完整;AI 只是一次性填满模板。
- 对象、字段和函数缺少问题回答与能力来源,正式文档越厚,实现者越难判断真相源。
- 诊断和取舍没有实际约束后续对象抽象,实现阶段会继续出现字段来源、状态来源和 port 读取面 blocker。

### 2.8.5 总流程计划 / Step 内计划必须绑定产物和门禁

总 SOP 流程必须通过 `*_calibration_flow.md` 显式维护总流程计划;单个 Step 必须在 `*_step_N_*.md` 中显式维护 Step 内计划。计划不是进度装饰,而是设计真相源形成过程的一部分。

必须明确:

- 总流程计划覆盖每个 Step 的编号、名称、输入文件、输出文件、前序依赖、状态、完成门禁和下一步许可。
- Step 内计划覆盖读取输入、SOP 问题回答、诊断、取舍、结构化产物、复杂度判断、回填草稿和自检。
- 每个计划项完成后,必须能在同一文件或明确附录中找到对应产物。
- 前序 Step 的问题回答、诊断、取舍和待确认事项必须作为当前 Step 输入。
- 复杂 Step 的 Step 内计划必须包含是否拆模块 / 附录的判断;拆分后每个附录也必须有自身产物和门禁。
- 不能一次列出计划,然后在同一批输出中把所有项标为 done,除非每一项都已有可审查产物。
- 自检失败不得直接进入下一 Step;必须回到对应 Step 内计划项修正。
- 总流程计划可以一次性列全,但未来 Step 中间产物不能提前批量落盘。未到达的 Step 只能存在于 flow 计划表中;不得提前创建、替换、清空或写入“待开始”框架。
- 清理旧真相源与推进当前 Step 必须分离。允许清空正式目标文档为“待装配”占位,允许更新 flow 总计划;不允许一次性批量改写未来 Step 文件后再回头填当前 Step。

正确示例:

```text
02_hld_calibration_flow.md:
Step 6 关键对象
  输入:
    - 02_hld_step_04_code_subject_framework.md
    - 02_hld_step_05_components_boundary.md
  输出:
    - 02_hld_step_06_key_objects.md
    - 02_hld_step_06_key_objects_identity_anchor.md
    - 02_hld_step_06_key_objects_lifecycle.md
  状态: in_progress
  完成门禁:
    - 每个对象都能回指 capability
    - 对象字段 / 函数停留在概要设计骨架层
    - 重对象组已经拆出附录

02_hld_step_06_key_objects.md:
Step 内计划:
  [x] 读取输入
  [x] 回答 SOP 问题
  [x] 诊断旧对象混层问题
  [x] 决定按组成部分拆附录
  [~] 写 lifecycle 对象附录
  [ ] 装配回填草稿
  [ ] 自检并更新流程文件
```

错误示例:

```text
02_hld_calibration_flow.md:
Step 1~14 已完成。

02_hld_step_06_key_objects.md:
Step 内计划:
  [x] 完成 Step 6。

正文:
  一张表列出所有对象、字段和函数。
```

错误原因:

- 总流程计划没有输入、输出、依赖、门禁和真实状态。
- Step 内计划没有分解问题回答、诊断、取舍和复杂度判断。
- 对象总表无法证明来自 Step 5 的主要组成部分和 capability。
- reviewer 只能看到“完成声明”,看不到“完成证据”。

未来 Step 文件提前落盘错误示例:

```text
重建 L1-identity 01。
先清空 01-架构设计.md。
再一次性把 01_arch_step_02 到 01_arch_step_16 全部替换成“待开始”模板。
随后回到 01_arch_step_02 开始填内容。
```

错误原因:

- Step 3~16 虽然没有正式结论,但中间产物状态已经被改写。
- 旧真相源被批量删除后,当前 Step 尚未形成替代产物,造成真相源空洞。
- reviewer 无法确认每个未来 Step 是未开始、已清理还是被部分处理。
- 后续 agent 容易把这些“待开始”文件当作已进入流程的证据,跳过当前 Step 门禁。

正确示例:

```text
重建 L1-identity 01。
先更新 01_architecture_calibration_flow.md,列出 Step 1~16 总流程计划。
只创建或改写当前正在执行的 01_arch_step_02_goals_constraints.md。
Step 2 完成自检并更新 flow 状态后,再创建或改写 Step 3 文件。
```

正确原因:

- flow 提供全局路线,当前 Step 文件提供当前可审查证据。
- 未到达 Step 不产生文件级状态,不会形成伪进度。
- 清理旧正式文档不会扩大成未来 Step 中间产物批量替换。

### 2.9 phase-reserved 状态和方法必须显式标注

正式设计可以提前列出 P0 总体状态集合或对象方法,但只要其中一部分不属于当前 phase / commit boundary,必须在对象契约、状态矩阵、flow、测试切口和实施计划里用同一口径标注。

至少要说明:

- 哪些 enum variant / method / DTO / history record 是当前 boundary 可实现的。
- 哪些是 `reserved` / `future phase` / `PH-xx only`。
- 当前 boundary 遇到 reserved path 时是不可调用、reject,还是完全不暴露 public command。
- 当前 boundary 的 domain / contract tests 只覆盖哪个非 reserved 子集。
- 后续 boundary 从 reserved 变为 active 时需要补哪些 flow、repository、history、outbox 和验收。

正确示例:

```text
commit-03-a implements ProcessInstanceState NotStarted / Running / Completed / Cancelled.
Waiting / Recovering / Failed and pause_for_gate / mark_recovering are PH-04 reserved.
commit-03-a tests cover running subset only;commit-04-a covers waiting/recovery illegal transitions.
```

错误示例:

```text
commit-03-a excludes waiting/recovery。
Step 6 ProcessInstance method table exposes pause_for_gate / mark_recovering without reserved marker。
Step 10 state matrix requires Waiting / Recovering transitions。
Step 16 says process_instance_state_transitions covers recovery path。
```

错误原因:

- 实现者无法判断当前 boundary 应实现未来 phase 对象,还是应该拒绝 / 暂不暴露这些路径。
- contract / domain tests 会越过 phase boundary,迫使实现提前引入后续 repository、history record 和 DTO。
- 后续 phase 的设计空间被当前临时实现锁死。

### 2.10 Public job surface 不能被 phase boundary 后置

如果当前 phase 的正式 flow、protocol contract 或 application service 已经把某个能力声明为 public job surface,例如 flow 输入是 `*Job` DTO、输出是 `JobRunReceipt` / `JobError` / `JobDisposition`,或 duplicate 语义依赖 stored job result replay,实施计划必须把该 job 的最小可执行共享 schema 放进同一个 commit boundary。

最少要闭合:

- `*Job` request / scope DTO。
- `JobMetadata`、receipt、disposition、error 和 report / receipt ref。
- job idempotency reserve / duplicate replay 的 result surface。
- application service / runner 的正式签名。
- 本 boundary 的 contract tests、duplicate tests 和 failure / retry tests。
- 后续 operations job phase 是否只承接 non-current job,不得重新定义或后置当前 job DTO。

如果设计意图是不在当前 phase 暴露 public job,必须把当前 flow 明确改成 worker-internal formal surface,并同步 protocol、function flow、idempotency、test plan 和 implementation plan。不能一边在 Step 8 / Step 9 定义 public job DTO,一边在 `07-实施计划.md` 把 DTO / receipt / error 留到后续 phase。

正确示例:

```text
commit-08-e implements PublishProcessOutboxFlow.
Step 8 / Step 9 define PublishProcessOutboxJob -> JobRunReceipt / JobError.
Therefore commit-08-e includes minimal contracts/src/jobs.rs publish job schema,
publish job idempotency result replay,
ProcessOutboxService.publish_pending(...),
and publish job contract / duplicate / retry tests.

commit-09-a starts only non-publish operations job shared foundation.
```

错误示例:

```text
commit-08-e implements publisher worker loop and retry / failed state.
Step 9 says PublishProcessOutboxFlow accepts PublishProcessOutboxJob.
07-实施计划.md keeps JobMetadata, JobRunReceipt, JobError and PublishProcessOutboxJob in commit-09-a.
```

错误原因:

- 实现者无法让 publisher loop 同时满足当前 flow 签名和后置 DTO 边界。
- job duplicate replay、stored receipt 和 error mapping 没有当前 boundary 的正式 result surface。
- 实现侧只能临时走 worker-internal loop 或提前补 job DTO,两者都会和部分正式设计冲突。

### 2.11 前置 surface repair 必须进入当前 boundary 首批

如果当前 commit boundary 要实现 application service、consumer、job、publisher 或 handler,而这些 flow 依赖的前置 surface 已在正式详细设计中闭合,但实现仓尚未落地,实施计划不能只写“实现 services / repos / handlers”。必须明确把这些前置 surface repair 放进当前 boundary 的首批,否则实现者会被迫在服务实现中自行补 schema、port、history、payload 或 stored result 变体。

适用的前置 surface 包括:

- `IdGeneratorPort` / clock / UoW / cursor helper 等基础 application port 方法。
- subject mapper / ref mapper / source mapper 的当前 truth family helper。
- 当前 flow 必需的 repository trait、resolver port、publisher port、handoff port 和 fake parity 要求。
- append-only history / trace-like / audit-like record schema、id source、factory 和 repository append/read surface。
- outbox payload DTO、payload snapshot、event kind mapping 和 builder 输入 source。
- idempotency duplicate replay 的 stored command / job result variants、store/load port 和缺失恢复口径。
- 当前 boundary 的 contract/domain/application compile smoke 和最小 targeted tests。

实施计划必须说明:

- 这些 surface 已由哪些正式 `03` Step 6/7/8/9/11/13 或测试切口闭合。
- 当前 commit 的第一批只补已闭合 surface,不得新增详细设计未定义的 schema、状态或 port。
- surface repair 之后再按服务族 / flow family 分批落 accepted path。
- 哪些 query view、event consumer、job、release evidence 或后续 phase surface 仍然不进入当前 boundary。
- 如果实现中发现还需要列表之外的前置 surface,必须暂停回写设计,不得借 repair 名义扩大边界。

正确示例:

```text
commit-04-d implements PH-04 accepted services.
Step 6/7/8/13 already define PH-04 id generator methods,
subject mapper helpers, repository traits, history records,
outbox payloads and stored result variants.

07-实施计划.md says:
Batch 04-05a first lands those prerequisite surfaces in contracts/domain/application.
Batch 04-05b~d then implement policy, control/compliance and NC services.
commit-04-d still excludes query views, event consumers and jobs.
If another PH-04 port is needed but not in Step 7, pause and update design.
```

错误示例:

```text
commit-04-d says "implement PH-04 services, repositories, handlers".
Implementation repo has only PH-03 ports and stored results.
Services need new PolicyEffectiveFactRepository, PolicyChangeRecord,
PolicyEffectiveFactChangedPayload and PolicyCommandResult.
The plan does not say whether commit-04-d may add these surfaces.
```

错误原因:

- 实现者无法判断补前置 port / payload / stored result 是合法 repair 还是 phase 越界。
- service code 会先写临时 trait、临时 enum 或 fake-only shortcut,再反向牵引正式设计。
- review 无法区分“已在详细设计闭合但实现仓未落地”和“设计尚未闭合”的两类缺口。
- duplicate replay、outbox、history 和 redaction tests 会在不同批次选择不同 surface,形成第二真相源。

### 2.12 配置绑定不能改变业务不变量

详细设计中的配置章节只能定义代码绑定点、adapter 选择、topic transport 映射、timeout / retry / retention / batch 等运行参数的读取位置。配置不得改变业务 truth 归属、状态矩阵、metadata / idempotency 要求、actor / visibility policy、query no-write、job no-truth-repair、外部正文排除或 phase boundary。

必须明确:

- 哪些模块允许读取配置,通常是 infra / api / worker / jobs 装配层。
- config root / validated config ref 的归属,以及 raw config、secret、URL、topic、cron、retry 数字是否进入对象契约。
- 每个 store、resolver、publisher、handoff、export、clock、id generator adapter 的绑定位置。
- topic-neutral event key 如何映射到 transport topic,且该映射不得改变 event kind、schema version 或 payload DTO。
- timeout / retry / retention / batch 等数值由 `04-配置设计.md` 或等价配置设计给出,详细设计只写代码绑定点。
- 哪些 sibling repo 是编译期依赖,哪些只能通过 runtime adapter、event、projection、handoff、API 或 fake 协作。
- 配置不可用、adapter disabled / degraded / unavailable 的错误映射。

正确示例:

```text
GovernanceRuntimeConfig 只保存 validated config refs。
infra/runtime_builder.rs 读取 publisher_ref,把 Step 8 topic-neutral key
governance.context.changed.v1 映射到部署 transport topic。
application 只接收 GovernanceOutboxPublisherPort。
domain / contracts 不读取 config。
timeout、retry、retention 具体数值留给 04-配置设计.md。
```

错误示例:

```text
配置项 enable_fast_path=true 时跳过 idempotency reserve 和 visibility check。
配置对象保存 raw bus URL、secret token、transport topic 和 retry 数字。
因为本地有 quantalithos-identity,所以把 identity crate 加成 Cargo path dependency。
```

错误原因:

- 配置变成绕过业务 invariant 的后门。
- raw secret / endpoint / transport topic 进入对象契约,导致详细设计替代配置设计并泄露部署细节。
- 运行期 / 事件依赖进入 Cargo dependency,破坏架构依赖裁剪。
- 实现者无法判断 adapter disabled 是 startup reject、degraded surface、job failed marker 还是普通业务 rejection。

配置 profile、fixture、测试和实现示例中出现的 adapter kind、store kind、profile kind、feature kind 等配置枚举值,必须进入正式配置 schema / enum,并说明每个值的 validation、默认 profile、失败映射和是否可用于 P0。不能在 `04-配置设计.md`、测试 fixture 或实现配置中使用未进入 `03` / `04` 正式 schema 的字符串值。

Entry local args 必须有正式入口 schema。凡是 `api`、`worker`、`jobs`、gate 或 report binary 需要读取本地 CLI / argv / env 输入,配置设计或实施计划必须列出:

- CLI flag 名称。
- 对应环境变量 key。
- 默认值或缺失处理。
- 适用 binary。
- 参数是否只影响本次入口 / job run,是否允许覆盖全局配置。
- 复杂业务 scope 是进入 typed DTO / config file,还是允许由 flag 直接表达。

正确示例:

```text
ExternalAdapterKind = Fake | Controlled | Endpoint | Disabled。
integration-like profile 使用 adapter_kind = controlled。
Controlled 必须有 controlled endpoint ref,失败映射为 explicit unavailable / retry / failed marker,不得 fallback fake success。

process-job-refresh-external-context
  required: --run-id <job_run_ref>, --job-input <path>
  optional: --config <path>, --profile <profile>, --diagnostics <off|redacted>
  env: PROCESS_JOB_RUN_ID, PROCESS_JOB_INPUT, PROCESS_CONFIG_PATH, PROCESS_PROFILE, PROCESS_DIAGNOSTICS
  scope 来自 RefreshExternalContextSnapshotsJob JSON,不使用 --scope 字符串。
```

错误示例:

```text
ExternalAdapterKind = Fake | Endpoint | Disabled。
04-配置设计.md 写 integration-like 使用 controlled resolver。
config/profiles/integration-like.json 写 "adapter_kind": "controlled"。

entry local args 包括 config path、profile、job run id、scope、dry-run、diagnostic。
设计没有 flag 名、env key、默认 profile、各 binary 参数面。
```

错误原因:

- 实现者无法判断 `controlled` 是正式 enum、新的 fake 变体、endpoint 别名还是非法配置。
- fixture 和测试会推动实现支持一个设计未闭合的字符串值。
- CLI / env schema 缺失会迫使实现者自行发明 `--config`、`--profile`、`--scope` 或默认 profile。
- 如果复杂 scope 用临时字符串 flag 承载,会绕开 typed job DTO 和 public protocol 二级类型闭环。

### 2.13 Job policy executable summary 必须闭合

如果 operations job 的 flow 要根据 `*_policy_ref` 执行 retry、expiry、retention、throttle、quota、cleanup、abandon、dead-letter 或其它可执行判定,设计不能只给 policy ref。必须同时定义:

- policy ref 的归属和 schema。
- body-free executable summary DTO,只包含当前 job 判定需要的字段。
- 正式 repository / resolver / config binding 读取面,例如 `get_*_policy(policy_ref) -> Option<*PolicySummary>`。
- missing policy / invalid policy 的 job-level error 或 item-level failure 映射。
- 每个判定所需的 committed truth 字段,例如 `captured_at`、`started_at`、`failure_count`、`last_failed_at`、`source_version_ref`、`state_changed_at`。
- 判定结果到状态迁移的唯一映射,包括 no-op 分支。
- 禁止读取 adapter retry counter、transport redelivery count、repository insertion order、history list length 或 config body 来补判定输入。

正确示例:

```text
MaintainRecoveryAttemptsJob.retry_policy_ref
  -> RecoveryMaintenancePolicyRepository.get_retry_policy(...)
  -> RecoveryRetryPolicySummary { max_failures }
  -> RecoveryAttempt.failure_count
  -> failure_count >= max_failures => RecoveryAttempt.abandon(RetryPolicyExhausted)
  -> failure_count < max_failures => remain Failed / no-op
```

反例:

```text
MaintainRecoveryAttemptsJob.retry_policy_ref
  -> flow 写 "apply retry policy"
  -> RecoveryAttempt 没有 failure_count / last_failed_at
  -> repository 没有 policy summary loader
  -> 实现者从 history 条数或 adapter retry counter 猜 exhausted
```

反例问题:

- policy ref 不是可执行 policy body。
- job 判定没有正式输入,实现者只能私推规则。
- duplicate replay、partial failure 和 fake adapter tests 无法稳定复现。

### 2.14 可观测性与业务审计必须分层闭合

详细设计定义可观测性时,必须区分 runtime log / metric、business trace / audit / history、outbox publication marker、handoff / export marker、job report 和 diagnostic issue。它们可以通过 ref 串联,但不能互相替代。

必须明确:

- 哪些 accepted truth change 必须写业务 trace / audit / history / outbox / stored result。
- 哪些 rejected、unsupported、delayed、failed、duplicate replay 或 query no-write path 只写日志、指标、receipt、report 或 rejected issue,不得伪造成 accepted trace。
- 日志埋点表:位置、级别、字段、目的。
- 指标埋点表:指标名、类型、打点位置、低基数标签。
- 审计事件表:触发位置、记录字段、消费方。
- `TraceContext` 来源是 metadata / event / job envelope,不是 domain object 自行生成。
- trace / audit / history / marker 字段只能记录 body-free refs、state、reason、source cursor、receipt / report ref、redacted issue ref。
- metric label 禁止使用 request id、actor id、subject id、trace id、outbox id、marker id、payload digest、free text、secret 或 raw endpoint。
- diagnostic / log 禁止保存 raw request、raw event payload、adapter response body、stack trace、credential、secret、observability ledger body、archive package body 或 external document body。
- 告警阈值、SLO、dashboard、采样率、日志保留和 runbook 留给运维 / 配置文档。

### 2.14-a accepted side-effect inventory 必须逐 flow 闭合

不能把 “accepted command” 机械等同于 “必须创建 trace + audit + outbox + stale projection + stored result”。每条 accepted mutation / callback / job flow 必须显式列出 side-effect inventory,说明本 flow 是否创建 trace、audit、outbox、projection stale、reference stale、job report、stored result 和 command effect summary,以及每个 ref 的正式来源。

尤其是 outbox:

- 只有 Step 8 / protocol truth source 已定义 canonical outbound payload、topic/schema marker、payload marker builder 和 publish flow 的 accepted path,才能创建 `OutboxRecord`。
- 若 accepted path 只创建 intent、marker、report-only state、handoff preparation state 或其它本仓内部 operations truth,但没有正式 outbound payload,必须明确 `effect.outbox_refs = []` 或等价空集合。
- 不得为满足通用 command effect 模板而临时发明第 N+1 个 outbound event、复用不匹配 payload、或把 handoff / job / report marker 塞进 existing payload。
- `CommandEffectSummary.outbox_refs` / public effect `outbox_refs` 可以是空集合,但必须在对应 flow 写清原因和测试切口。

正确示例:

```text
PrepareTraceHandoff accepted:
  save TraceHandoffIntent(PendingHandoff)
  append accepted trace/audit for intent
  mark affected handoff read projection stale
  save stored command result and effect summary
  effect.outbox_refs = [] because no TraceHandoffIntentPrepared outbound payload exists
```

错误示例:

```text
PrepareTraceHandoff accepted:
  create MemoryArchiveHandoffStateChanged outbox without ArchiveHandoffRef
  or invent TraceHandoffPreparedPayload in service implementation
```

错误原因:

- existing payload schema 不能表达该 accepted source。
- implementation 会在 service/fake/publisher 私造 event name、topic key、payload marker 或 body store。
- duplicate replay 和 downstream compatibility 无法从 truth source 反查。

正确示例:

```text
Command accepted:
  save truth
  append GovernanceTraceRecord::from_truth_change(...)
  append domain history record with trace_ref
  append GovernanceAuditTrail trace ref
  append GovernanceOutboxRecord with same trace_ref
  complete stored result
  log info(command_kind, subject_ref, trace_record_ref, outbox_ref, result_ref)
  inc governance_command_total{command_kind,result="accepted"}

Query not visible:
  return body-free NotVisible surface
  log info(query_kind, read_subject_ref, visibility_marker_ref)
  inc governance_query_total{query_kind,surface="not_visible"}
  do not append audit / outbox / idempotency / projection repair
```

错误示例:

```text
所有成功请求只写 runtime log,不写 trace / audit / history。
所有失败请求也写 SuccessTrace 方便查询。
Metric label 包含 subject_id、actor_id、trace_id 和 raw endpoint。
Handoff marker 保存 observability ledger body / archive package body。
```

错误原因:

- runtime log 无法替代 accepted business truth 的可追溯审计。
- rejected / unsupported / failed path 被伪装成 accepted truth,下游 trace query 和 archive 会误读事实。
- 高基数 / 敏感 label 破坏指标系统和安全边界。
- handoff / archive / external GRC body 进入本仓,破坏外部正文排除规则。

### 2.15 测试切口必须是最小验证入口

详细设计中的测试切口章节用于证明前序对象、协议、flow、状态、事务、错误、幂等、配置和观测契约都有可验证入口。它不得替代完整测试方案,也不得只写“后续补测试”。

必须明确:

- 每个实现模块至少一个测试切口,例如 contracts / domain / application / infra / api / worker / jobs。
- 每个 public Command / Query / Event / Job 至少有正向和异常测试切口。
- 每个正式状态机至少有合法转换和非法转换测试切口。
- 事务、一致性、幂等、并发、duplicate replay、commit unknown、partial failure 和 retry / dead-letter 必须有测试切口。
- 配置绑定、adapter availability、forbidden configurable boundary 必须有测试切口。
- 可观测性 / redaction / metric label / audit refs-only 必须有测试切口。
- 每个测试切口必须能反查对应详细设计 Step、协议、flow、状态矩阵或持久化契约。
- 具体 TC 编号、优先级、覆盖率、fixture 目录、真实外部依赖联调、CI job 分层、报告模板和执行排期留给 `05-测试方案.md`。

正确示例:

```text
Step 16:
  command_duplicate_same_key_same_digest
    对应 Step 13 duplicate replay
    验证返回 stored command result,无新 truth / trace / outbox
    建议测试类型: application service

  query_no_write_side_effects
    对应 Step 9 query no-write
    验证 Query 不 begin write UoW,不修 projection/reference/audit
    建议测试类型: query service

05-测试方案.md:
  再分配 TC 编号、fixture 路径、优先级、CI suite 和覆盖率目标。
```

错误示例:

```text
Step 16:
  测试方案详见后续。
  或者直接写完整 TC 编号、优先级、fixture 文件、CI job、验收 EV 页面。
  或者只列模块测试,不列每个 Command / Query / Event / Job 的正反向切口。
```

错误原因:

- 实现者无法从详细设计判断当前契约是否有最小验证入口。
- Step 16 越界替代测试方案会导致 `03` 与 `05` 分叉。
- 只写模块测试会漏掉 protocol、state matrix、duplicate replay、query no-write 和 redaction 等关键契约。

## 三、字段闭环标准

### 3.1 字段来源必须可追踪

Domain 对象、event、artifact metadata、projection view 的每个必填字段，必须能回指到以下来源之一：

- request / command / query / event / job DTO 字段
- metadata / context 字段
- repository / port lookup 结果
- upstream contract / snapshot 字段
- system generated id / clock / digest / version
- 正式派生规则

字段闭环表：

| 对象 | 字段 | 类型 | 来源类型 | 来源字段 / 方法 | 缺失处理 | 测试 |
|---|---|---|---|---|---|---|

### 3.2 状态条件字段也必须闭环

如果状态矩阵、业务规则、验收标准或测试断言要求某个状态必须携带证据、receipt、marker、reason、timestamp 或其它条件字段,该字段即使在非该状态下可为空,也必须进入 domain truth schema 并写成 `Option<T>` 或等价可选形态。

最少要闭合:

- domain struct 字段和字段表。
- 触发状态转换的 domain method 参数与赋值规则。
- 持久化契约中的存储字段或外部 evidence store 归属。
- query view / outbound event 是否暴露该字段。
- 缺失或未验证时的错误映射。
- 对应测试和验收断言。

正确示例:

```rust
pub struct ChildWorkItem {
    pub work_state: WorkItemState,
    pub completion_ref: Option<ExternalEvidenceRef>,
}
```

并说明:

```text
WorkItemState::Completed 必须有 verified ExternalEvidenceRef。
ChildWorkItem::transition_lifecycle(Completed, ..., Some(evidence_ref), actor)
写入 completion_ref;缺失或未验证 evidence 返回 DomainError::InvalidStateTransition。
```

错误示例:

```rust
pub struct ChildWorkItem {
    pub work_state: WorkItemState,
}
```

同时状态矩阵写:

```text
ChildWorkItem Completed 必须有 verified evidence。
```

错误原因:

- 实现者无法知道 verified evidence 应保存到哪个 truth 字段。
- query / event / duplicate result 无法稳定回放 completed evidence。
- 持久化 adapter 只能自行补列或丢失状态条件。

### 3.3 DTO 到 domain factory 必须闭合

如果 DTO 字段映射到 domain truth 必填字段，则必须满足以下任一条件：

1. 该字段直接传入 factory / method。
2. 该字段通过正式派生规则进入 factory / method。
3. 该字段由 repository / port lookup 生成，并在 flow 中明确。

正确示例：

```rust
ConversationFact::from_append_input(
    space,
    request.fact_kind,
    source,
    visibility,
    request.payload_ref,
)
```

错误示例：

```rust
ConversationFact::from_append_input(space, source, visibility, request.payload_ref)
```

同时 `ConversationFact` 又有必填 `fact_kind`。

错误原因：

- request 中的 `fact_kind` 无法进入 domain truth。

状态化对象还必须做逐状态 factory 闭环:

- 同一个 truth / snapshot struct 的必填字段,必须能被该对象每个当前 boundary 会调用的 factory / transition path 填充。
- `Resolved` / `Accepted` / `Active` 分支已经闭合,不代表 `Unavailable` / `Unrecognized` / `Pending` / `Rejected` / `Stale` 分支自动闭合。
- 如果某个状态确实不应携带该字段,字段必须在 Step 6 schema 中改成条件 optional,并在 Step 10 / Step 11 / query / event / replay 中说明按状态 nullable 规则。
- 如果字段保持必填,所有 factory 签名、Step 8 DTO / event、Step 9 flow 和 Step 10 matrix 都必须给出同一字段来源;不得让实现端用 placeholder、timestamp、id、digest 或 optimistic version 代替。

错误示例:

```rust
pub struct SourceSnapshot {
    pub source_ref: SourceRef,
    pub source_version_ref: SourceVersionRef,
    pub state: SourceState,
}

pub fn resolved(source_ref: SourceRef, source_version_ref: SourceVersionRef) -> Self;
pub fn unavailable(source_ref: SourceRef) -> Self;
```

错误原因:

- `source_version_ref` 是对象必填字段,但 `unavailable(...)` 无法填充。
- 实现只能自行发明空版本、时间版本或复用 snapshot id,导致 stale / superseded / replay 语义不稳定。
- 正确做法是让 `unavailable(...)` 也接收正式 source version,或把 schema 改成按状态条件 optional 并同步所有状态/持久化/公开 surface。

### 3.3.1 Flow 可选状态分支必须有输入来源

同一 command / consumer / job flow 中,如果 Step 9 伪码、状态矩阵或测试切口声明了 optional accepted、pending evidence、degraded、delayed、failed、wait 等分支,每个分支都必须满足以下任一条件:

1. 分支需要的字段直接来自该 flow 的 request / event / job DTO。
2. 分支需要的字段来自该 flow 已加载的 existing truth 字段。
3. 分支需要的字段来自正式 repository / resolver / policy output,且 Step 7 / Step 11 已定义读取面和错误映射。

如果分支无法满足上述任一条件,设计必须二选一:

- 缩窄当前 flow,只保留字段来源闭合的分支。
- 把该分支移动到另一个已经拥有正式输入字段或读取面的 command / job / consumer flow。

正确示例:

```text
SubmitGovernanceInputRequest 只有 context_ref / input_kind / source_ref。
SubmitGovernanceInputFlow 只创建 GovernanceInput::receive(...),保存 state = Received。
UpdateGovernanceInputStateRequest 有 target_state / pending_evidence_ref / reject_reason / superseded_by。
UpdateGovernanceInputStateFlow 负责 accept / wait_for_evidence / reject / supersede,其中 PendingEvidence 的 evidence_ref 来自 request.pending_evidence_ref。
```

错误示例:

```text
SubmitGovernanceInputRequest 没有 evidence_ref。
SubmitGovernanceInputFlow 写:
  if context ready -> input.accept(...)
  else if evidence required -> input.wait_for_evidence(evidence_ref, actor)
测试又要求 SubmitGovernanceInput 覆盖 Accepted / PendingEvidence。
```

错误原因:

- `evidence_ref` 没有来自 request、existing truth 或正式 resolver output。
- 实现者只能从 source_ref 猜 evidence、临时补 port,或把所有输入落成 Received。
- 状态矩阵、flow 和测试切口互相拉扯,导致 commit boundary 无法 1:1 落码。

### 3.4 同名或近名引用不得默认等价

以下名称接近但语义不同的 ref 必须显式区分：

- `core_event_ref` vs `core_event_envelope_ref`
- `api_ref` vs `replacement_api_ref`
- `service_capability_ref` object vs `service_capability_ref` string id
- `event_mapping_ref` vs `EventSemanticMapping`
- `RuntimeConfig` vs `ConversationRuntimeConfig`

如果允许映射，必须写清：

- 源类型
- 目标类型
- 映射函数 / lookup 方法
- 失败处理

### 3.5 Query response / view 也是 public DTO

Query 不能只写返回类型名、builder 名或“从 projection 构造”。只要返回对象进入 public query surface，就必须按 DTO schema 定义。

Query response 最少要定义：

- request DTO 的正式名称和落码模块
- response view / page / marker DTO 的正式名称和落码模块
- 每个 response 字段的类型、来源和可见性裁剪规则
- 每个 response 字段引用的 shared enum / ref / helper 类型的归属,不得指向 domain-only 类型
- empty / not visible / stale / failed / rebuilding / disabled / missing state 的返回口径
- page token、consistency、consumer / actor context 来自 query body 还是 metadata / envelope
- HLD `*Query`、DDD `*Request`、Rust DTO 名称是否收敛，以及一对一映射

Query response 引用 repository helper 时,helper 本身也必须定义 schema 和归属。例如 repository 返回 `Page<T>` 时,必须说明 `Page<T>` / `PageInfo` 属于 application port helper、字段包含 `items` / `next_page_token` / `has_more`,并说明如何映射到 public response page DTO。不得只写 `Result<Page<T>, RepositoryError>` 而不定义 `Page`。

Repository / application port 的返回类型必须保持设计指定的 domain object、projection object 或 application helper 类型,不得因为当前 implementation step 尚未实现某个 domain 对象,临时改成 public contracts view DTO。public view DTO 只能在 query service / API handler 输出边界由已授权的 domain / projection 对象映射生成。

### 3.5.1 Generic ref 与 repository typed ref 必须分离

只要 job report、handoff、archive、external export、policy proof 或 public DTO 中存在泛化 ref,例如 `*ReportRef`、`*ArtifactRef`、`*PackageRef` 或 `*ExternalRef`,同时某个 repository 只能按更具体 typed ref 读取,设计必须明确两者的边界。

必须明确：

- 哪个 ref 是 repository-readable key,例如 `GovernanceReconciliationReportRef`。
- 哪个 ref 只是 public/job/adapter-facing generic body-free ref,例如 `GovernanceReportRef`。
- generic ref 是否允许作为 request input;如果 flow 需要 repository load,request 必须携带 repository-readable typed ref,或 Step 7 必须定义正式 generic-ref lookup repository。
- typed ref -> generic ref 的单向 conversion helper、canonical key 规则和 owner。
- 是否允许 generic ref -> typed ref。默认禁止;若允许,必须定义正式 repository / resolver 读取面,不能解析字符串。
- fake 与 durable adapter 必须使用同一规则。

禁止事项：

- service 把 `ExternalSourceRef`、generic report ref 或 storage ref 字符串拆开后构造 typed repository key。
- adapter/fake 从 generic ref 反查本地 repository。
- flow 写 `report_ref as GenericReportRef` 或 `GenericReportRef -> typed report ref` 这类未定义 cast。
- job report assembly 接收 caller 手写 generic ref,而没有说明该 ref 来自哪个 typed report helper。

正确示例：

```text
Archive handoff input uses GovernanceReconciliationReportRefSet.
Flow loads each report through GovernanceReconciliationReportRepository.get(report_ref).
After load, flow calls report_ref.to_governance_report_ref().
Archive adapter and job report receive GovernanceReportRefSet only after conversion.
No component parses GovernanceReportRef back into GovernanceReconciliationReportRef.
```

错误示例：

```text
Archive handoff input uses GovernanceReportRefSet.
Flow calls reconciliation_report_repo.get(report_ref).
Implementation parses report_ref.0 and constructs GovernanceReconciliationReportRef.
```

错误原因：

- generic ref 的 opaque string 不保证承载 repository key。
- typed report ref 的 identity、visibility、persistence 和 duplicate replay 语义会被绕过。
- fake runtime 可能通过私有 map 或字符串前缀通过测试,durable adapter 无法等价。
- 后续 job report replay 会保存无法重新读取或校验的 ref。

正确示例：

```text
HLD GetConversationReadModelQuery 是语义入口名。
Rust DTO 统一为 GetConversationReadModelRequest。
ConversationReadModelView 属于 contracts/views.rs。
ProjectionRepository.get_read_model 返回 domain ConversationReadModel。
ConversationReadModelView::from_authorized(authorized_read_model, projection_state, ...) 在 query 输出边界构造。
projection_state 字段来自 ConversationProjectionStateView::from_state_or_empty(...);
projection 缺失时返回 empty stale marker，不返回 Fresh。
```

错误示例：

```text
GetConversationReadModel 返回 ConversationReadModelView。
ConversationReadModelView::from_authorized(read_model)。
ProjectionRepository.get_read_model 临时返回 ConversationReadModelView。
```

错误原因：

- 实现者无法定义 response DTO 字段。
- 实现者无法判断 response DTO 字段能否合法依赖某个 domain enum。
- repository / application helper 缺少 schema,导致 page DTO 的 `next_page_token` 和 `has_more` 无来源。
- `NotVisible`、empty view、stale / failed projection marker 无法测试。
- HLD `*Query` 与 DDD `*Request` 可能被实现成两套类型。
- public DTO 进入 repository port 后会绕过 domain policy / visibility filter,并把 adapter 层绑定到对外 response schema。

### 3.5.1 Query status marker 来源必须闭合

如果 query response 的 public surface 要求返回 `NotVisible`、`Degraded`、`Unavailable`、`Filtered`、`Stale` 或等价 status marker,设计不能只定义 marker DTO 字段,还必须定义该 marker 的正式来源。

必须明确:

- 哪个 policy、repository、projection 或 application helper 返回该 status decision/result。
- decision/result 的正式 schema、字段、归属模块和错误类型。
- public marker 从 decision/result 的哪些字段复制,例如 consumer、reason、freshness、projection state、reference state 或 cursor。
- hidden / filtered / filtered-to-empty / dependency failure / unavailable 等分支如何映射到 public status、marker 和 error。
- `NotAuthorized`、`NotVisible`、`Missing`、`Degraded` 等相近 surface 的边界,尤其哪些是 public query status,哪些是 API error。

禁止把 query marker 的来源写成裸布尔、`Result<(), Error>`、`assert_*`、`can_read == false`、临时 error message 或 adapter 私有字段。裸错误只能表达“调用失败”或“上下文无效”,不能稳定承载 public marker 需要的 reason、consumer、source cursor 或 projection state。

正确示例:

```text
ReadVisibilityPolicy.evaluate_read_visibility(
  subject_ref,
  consumer_ref,
  actor_context,
) -> ProcessReadVisibilityDecision

ProcessReadVisibilityDecision {
  subject_ref,
  consumer_ref,
  visibility_decision: VisibilityDecision::{Visible, Filtered, Hidden},
  visibility_marker: Option<ProcessVisibilityMarker>,
}

VisibilityDecision::Hidden -> ProcessViewStatus::NotVisible + visibility_marker.
VisibilityDecision::Filtered with empty visible items -> ProcessViewStatus::NotVisible + visibility_marker.
invalid actor / authority context -> ProcessApiError::NotAuthorized.
```

错误示例:

```text
ReadVisibilityPolicy.assert_can_read(subject_ref, consumer_ref) -> Result<(), ApplicationError>

Flow:
  assert_can_read(...)?
  error -> ProcessViewStatus::NotVisible
  visibility_marker = ProcessVisibilityMarker { reason: "denied" }
```

错误原因:

- `ProcessVisibilityMarker.consumer_ref`、`visibility_decision` 和 `reason_ref` 没有正式来源。
- hidden、filtered-to-empty 和 actor not authorized 被实现侧混成同一个 error。
- query service 只能在 catch error 后临时拼 marker,无法稳定测试 NotVisible surface。
- fake policy 无法覆盖 filtered-but-non-empty、filtered-to-empty、hidden 和 policy dependency failure 的差异。

#### 3.5.1.1 API handler query disposition 映射必须闭合

如果 API / RPC handler 有 transport-neutral handler result、disposition enum 或 response mapping layer,并且 query surface 可以返回 visible success、not visible、degraded、stale、missing 或 redacted surface,设计必须明确 query surface 到 handler disposition 的完整映射。

必须明确:

- visible 且非 degraded 的 query success 使用哪个 disposition。
- not visible / hidden / redacted query 使用哪个 disposition,以及 marker 从哪里复制。
- degraded / stale / unavailable / partial query 使用哪个 disposition,以及 degraded marker 的必填规则。
- command accepted truth mutation 与 query visible success 是否复用同一 disposition;若复用,必须说明它只是 handler completion,不是 domain accepted truth。
- query success 是否允许 `application_result_ref`、stored command result、trace / audit / outbox 或 projection write;通常必须显式禁止。
- Step 6 object contract、Step 10 state / disposition matrix、Step 16 handler tests 和 implementation boundary 是否使用同一口径。

正确示例:

```text
GovernanceApiHandlerResult::query_surface(route_ref, visibility, degraded):
  if !visibility.is_visible -> disposition = NotVisible
  else if degraded.is_some_and(|marker| marker.is_degraded) -> disposition = Degraded
  else -> disposition = Accepted

query Accepted means visible non-degraded handler completion only.
application_result_ref = None.
No stored command result, trace, audit, outbox, projection or reference repair.
```

错误示例:

```text
GovernanceApiHandlerDisposition = Accepted / Rejected / NotVisible / Degraded.
query_surface(route_ref, visibility, degraded) exists.
State matrix only maps command accepted, query NotVisible and query Degraded.
Visible query success is left unspecified.
```

错误原因:

- 实现者无法判断 visible query success 是否应复用 `Accepted`、新增 `Visible`、还是隐式不设置 disposition。
- handler tests 无法断言可见成功、not visible 和 degraded 的三类返回。
- command accepted truth mutation 与 query read success 容易混淆,导致 query handler 误生成 stored result、trace / audit / outbox 或写 projection。
- API error mapping 与 query surface mapping 口径分裂,同类 query 在不同 handler 中实现不一致。

### 3.5.2 Sidecar truth 的保存与读取必须成对闭合

只要一个 command、consumer 或 job 在 accepted path 中保存了与主 truth 绑定的 context、snapshot、marker、change record、pause context、handoff marker、resolution state 或其它 sidecar truth,并且后续 command / query / publisher / job flow 需要读取它来继续状态迁移、构造 view、生成 event、判断 degraded 或执行恢复,设计必须定义正式读取面。

必须明确:

- sidecar truth 的 identity / ref 字段,以及主 truth 如何引用它。
- 保存接口与读取接口,例如 `save_pause_context(...)` 和 `get_pause_context(pause_context_ref)`.
- 读取返回类型是否带 optimistic version;若后续只读构造 view,可返回 `Option<T>`;若后续要更新,必须给出 version 来源。
- 若 sidecar truth 的更新路径以 subject、scope、source、target 或其它业务唯一键定位,repository 必须提供按该唯一键读取 `Versioned<T>` 的正式接口,例如 `get_audit_trail_by_subject_with_version(subject_ref)`;只有 primary ref 读取面不足以支撑 accepted path 更新。
- 缺失时的路径差异:command 是否 `NotFound` / `DomainRejected` / integrity failure;query 是否 `Missing` / `Degraded`;job 是否 partial failure。
- 该 sidecar truth 是否 immutable、append-only 或 versioned,以及同 UoW / same transaction 约束。

禁止只在 repository 中定义 `save_*` / `append_*`,然后在 flow 里写 "load context / marker / record"。也禁止让实现者通过扫描主 truth、解析 id、读取 private in-memory maps 或从 query view 反推 sidecar truth。

正确示例:

```text
WaitingGate.pause_context_ref -> PauseContextRef
WaitingGateRepository.save_pause_context(context, &uow)
WaitingGateRepository.get_pause_context(pause_context_ref) -> Option<PauseContext>
ResumeWaitingGateFlow missing pause context -> ProcessApiError::DomainRejected / invariant violation.
GetWaitingGateFlow missing pause context -> ProcessViewStatus::Degraded.

GovernanceAuditTrail 使用唯一 audit_subject_ref
GovernanceAuditHistoryRepository.get_audit_trail_by_subject_with_version(audit_subject_ref) -> Option<Versioned<GovernanceAuditTrail>>
Some(versioned) -> 追加 trace 并用 Some(versioned.version) 保存
None -> start_for_subject(new_audit_trail_id(), audit_subject_ref),再用 None 保存
```

错误示例:

```text
OpenWaitingGateFlow saves pause context.
ResumeWaitingGateFlow loads PauseContext.
WaitingGateRepository has save_pause_context only.

GovernanceAuditTrail 有唯一 audit_subject_ref。
Accepted command 只有 audit_subject_ref。
Repository 只有 get_audit_trail_with_version(audit_ref)。
Service 从 audit_subject_ref 推导 audit_ref,或 fake 私下扫描 private map。
```

错误原因:

- implementation agent 不知道从哪里读 `PauseContext`.
- command 和 query 对 missing context 的处理不同,实现侧会被迫选边。
- fake adapter 无法断言 same transaction 保存后的后续读取和缺失场景。
- mutable sidecar 的 expected_version 没有正式来源,实现侧只能拼 primary ref、全表扫描或绕过 trait。

### 3.5.3 Body-free snapshot typed read 面必须闭合

只要一个 flow、query、policy guard、view assembler 或 job 需要把已保存的 body-free snapshot 本体作为输入,设计不能只提供 `save_*_snapshot(...)`,也不能只提供通用 `get_reference_state(...)`。必须定义返回该 snapshot 类型本体的 typed read 面。

必须明确:

- snapshot 类型与 key,例如 `ActorCapabilitySnapshot` by `ActorRef`、`MethodPolicySnapshot` by `MethodPolicyRef` / version、`MethodControlSnapshot` by control ref。
- typed read repository / port 函数,例如 `get_actor_capability_snapshot(actor_ref) -> Option<ActorCapabilitySnapshot>`。
- typed read 的缺失映射:command 是 rejected / dependency unavailable,query 是 degraded / not visible / body none,job 是 partial failure / failed item。
- 是否带 version:只读 view / visibility 可返回 `Option<T>`;后续若要更新 snapshot 或依赖 optimistic lock,必须返回 `Versioned<T>`。
- fake adapter 与 durable adapter 必须使用同一 typed read 语义。
- 该 read 是否允许触发外部 resolver / refresh。默认不允许;refresh 必须属于独立 consumer / job / command precheck flow。

禁止用 `ReferenceResolutionState`、snapshot ref 字符串、external ref 字符串、query view 字段、private fake map 或 resolver side call 代替 typed snapshot。`ReferenceResolutionState` 只能说明来源解析状态,不能承载 role refs、capability refs、safe summary marker 等 snapshot 本体字段。

正确示例:

```text
ReferenceSnapshotRepository.get_actor_capability_snapshot(actor_ref)
  -> Option<ActorCapabilitySnapshot>

GetApprovalResponsibilityFlow:
  reader_snapshot = reference_snapshot_repo.get_actor_capability_snapshot(query_actor_ref)
  visibility = ReadVisibilityPolicy.evaluate_read_subject(read_subject_ref, reader_snapshot)
  assigned_snapshot = responsibility.actor_ref
    ? reference_snapshot_repo.get_actor_capability_snapshot(responsibility.actor_ref)
    : None
  missing assigned_snapshot -> view.actor_snapshot = None + degraded marker
```

错误示例:

```text
ReferenceSnapshotRepository.save_actor_capability_snapshot(...)

GetApprovalResponsibilityFlow:
  actor_state = reference_repo.get_reference_state_with_version(actor_external_ref)
  visibility = ReadVisibilityPolicy.evaluate_read_subject(read_subject_ref, actor_state)
```

错误原因:

- `ReferenceResolutionState` 没有 role refs / capability refs,不能满足 `ActorCapabilitySnapshot` 输入。
- query service 会被迫读取 fake 私有 map、调用 external resolver 或忽略 actor snapshot。
- missing snapshot 的 degraded / not-visible 口径无法稳定测试。
- durable adapter 和 fake adapter 容易出现不同语义。

### 3.5.4 Resolver refresh failure outcome 必须可判别

只要 reference refresh、external snapshot refresh、adapter refresh 或类似 job 会根据 resolver 结果写入 `Unavailable`、`Invalid`、`Unresolved`、`Failed` 等可持久化状态,port 不能只返回 `Result<T, ApplicationError>` 后让 service 从错误类型、错误字符串或 fake 约定推断状态。必须定义正式 business outcome enum,把“调用成功但外部引用当前不可用 / 无效 / 未解析”与“resolver call 本身失败”分开。

必须明确:

- success outcome 携带的 typed body-free snapshot / ref / summary 与新的 resolution state。
- unavailable / invalid / unresolved outcome 携带的 reason marker、checked_at、是否保留 source version。
- service 在每个 outcome 下调用哪个 domain / contract helper,例如 `mark_unavailable(...)`、`mark_invalid(...)`、`mark_unresolved(...)`。
- `ApplicationError` 只表示无法形成可持久化 business outcome,例如 adapter wiring 缺失、runtime/store 不可用、serialization defect、contract bug 或 timeout unknown;此时 flow 只能记录 job failed/dependency item,不得改业务状态。
- fake adapter 与 durable adapter 必须使用同一个 outcome enum;fake 不得通过 private map 或错误 message 模拟状态分类。

正确示例:

```text
ExternalSourceResolver.resolve_method_policy(policy_ref)
  -> Result<ReferenceRefreshResolution<MethodPolicySnapshot>, ApplicationError>

Resolved { state, body } -> save_method_policy_snapshot(body, expected_version)
Unavailable { reason, checked_at } -> loaded_state.mark_unavailable(reason, checked_at)
Invalid { reason, checked_at } -> loaded_state.mark_invalid(reason, checked_at)
Unresolved { reason, checked_at } -> loaded_state.mark_unresolved(reason, checked_at)
ApplicationError::DependencyUnavailable -> job failed/dependency item only;no state mutation
```

错误示例:

```text
resolve_method_policy(policy_ref) -> Result<MethodPolicySnapshot, ApplicationError>

Err(e) if e.to_string().contains("timeout") -> mark_unavailable(...)
Err(e) if e.to_string().contains("invalid") -> mark_invalid(...)
```

错误原因:

- service/fake 需要解析错误字符串或 adapter 私有 code。
- durable adapter 与 fake adapter 可能给同一失败落不同状态。
- `ApplicationError::DependencyUnavailable` 会同时表示 resolver call 没执行成功和外部引用 business unavailable,导致 job report、retry 和 state matrix 不可测试。

### 3.5.5 状态矩阵前必须先筛选状态主语

Step 10 不是把所有对象都写成状态机。进入状态矩阵前,必须先从 Step 6 object contract 和 Step 9 flow 中筛选状态主语,说明哪些候选对象进入矩阵、哪些被排除以及原因。

可以进入状态矩阵的状态主语必须同时满足:

- 已在 Step 6 定义 state enum、state value、disposition、availability、validation、dispatch、report result 或等价状态字段。
- Step 9 flow 会读取、推进、暴露、回放或按该状态分支。
- 状态会改变允许操作、持久化结果、query surface、stored replay、job report、outbox/handoff/entry result 或非法转换判断。

不得进入状态矩阵的对象包括:

- 纯 ref / id / marker。
- 只承载字段、不改变允许操作的 value object。
- 没有独立生命周期的 DTO wrapper。
- 外部仓 truth 状态。
- UI state、cache state、retry counter、SQL lock、transport connection 等实现细节。

状态主语进入矩阵前必须先归入状态族,至少区分:

- business truth state。
- source / reference state。
- read / visibility surface state。
- projection / reconciliation maintenance state。
- outbox / handoff propagation state。
- idempotency / stored replay / job report state。
- runtime / adapter / entry technical state。

不得为了统一管理新增 `GlobalState` / `SystemState` 这类全局状态机。除非 Step 6 已经把它定义为正式 truth object,且 Step 9 有明确 flow 推进它;否则跨对象规则只能放在跨状态机审计表中,不能用全局状态 enum 混写。

正确示例:

```text
Identity Step 10:
  Include GlobalLifecycleState because Step 6 defines GlobalLifecycleStateKind
  and UpdateGlobalLifecycleStateFlow changes allowed member operations.

  Include IdentityOutboxRecord because OutboxStateKind drives publish/retry/failure
  and stored job report exposes outbox item refs.

  Exclude GlobalMemberRef because it is a typed ref, not a lifecycle state.
  Exclude IdentityRequestDigest because it is a replay key material, not a state machine.
  Put duplicate replay state under IdentityIdempotencyRecord instead.
```

错误示例:

```text
Step 10 defines IdentityGlobalState {
  MemberAvailable,
  ProjectionStale,
  OutboxPublished,
  ApiDispatchSucceeded,
  AdapterUnavailable
}

Every object is listed in one global state table.
```

错误原因:

- business truth、projection maintenance、outbox propagation、entry dispatch 和 adapter availability 被混成同一状态机。
- 实现者无法判断哪个 flow 拥有状态迁移,也无法把状态保存到正确 repository。
- query no-write、job no-truth-repair、Published != Delivered、EntryValid != ApplicationAccepted 等边界被全局状态表抹平。

### 3.5.6 状态矩阵中的迁移必须有正式触发 surface

状态矩阵只声明 `A -> B` 不足以可落码。每条当前 boundary 会执行的迁移,必须在同一层对象、policy 或 repository 契约中有正式触发函数 / 保存面,并说明参数来源、失败 marker、expected_version 和 fake/durable 等价语义。

必须明确:

- 迁移由 domain method、contract helper、repository atomic update 还是 policy outcome 触发。
- 触发函数的完整签名,例如 `mark_unavailable(failure_ref)` 而不是“repository state update by maintenance policy”。
- 迁移所需 reason / failure / receipt / cursor / actor / checked_at 等字段来源。
- repository 是否只能保存已转换对象,还是被授权提供专门 atomic update;二者只能选一条正式口径。
- missing-state / first-materialization 分支是否允许创建目标状态;不能让实现自行决定是否补 state row。

正确示例:

```text
DerivedGovernanceViewState:
  Fresh/Stale/Rebuilding/Failed -> Unavailable
  trigger = mark_unavailable(failure_ref)
  failure_ref = persisted failure marker or job report item ref
  repository.replace_*_view(view, state, expected_version)
```

错误示例:

```text
State matrix:
  Fresh/Stale/Rebuilding/Failed -> Unavailable
trigger = repository state update by maintenance policy
Step 6 object has no mark_unavailable(...)
```

错误原因:

- implementation agent 只能自行扩 domain API 或绕过 domain method。
- fake runtime 可能直接改字段,而 durable repository 通过 SQL update,语义分裂。
- 状态矩阵测试无法引用正式函数,只能断言最终字段值。

### 3.6 Public read-model / projection identity 必须闭合

read model、projection、cursor、page marker 只要出现在 query response 中，就必须定义 id / ref 的正式 schema。

最少要说明：

- id / ref 属于哪个 contracts 模块
- 是 string newtype、复合 ref，还是上游 typed projection ref
- 与 repository key 的关系
- 稳定派生规则
- 缺失 row 时是否返回 marker、error 或 empty view

正确示例：

```text
ConversationReadModelId 属于 contracts/refs.rs。
ConversationReadModelId::for_consumer(space_id, consumer_ref) 生成稳定 id。
ConversationProjectionStateId::for_kind(space_id, projection_kind) 生成稳定 projection state id。
```

错误示例：

```text
ConversationReadModel 引用 ConversationReadModelId。
Projection state view 返回 projection_state_id。
```

错误原因：

- repository 无法确定 lookup key。
- 空 view 和正常 view 的 identity 不稳定。
- projection state 缺失时无法构造 public marker。

如果 command、consumer 或 job flow 要求 `ProjectionRepository.mark_stale(affected_views, ...)`,每一个 affected view 都必须来自当前 phase 已正式定义的 public projection identity,例如 `Derived*ViewRef` 稳定派生表。不能因为某个 truth、marker 或 intake 发生变化,就在实现阶段临时派生 `promote-*`、`intake-*`、`review-*` 等 view ref。

如果 affected views 需要从 external ref、snapshot ref、member ref、method definition ref、source ref 或其他非 view ref 输入推导,设计还必须定义正式 repository / port 读取面来枚举 existing public view refs。该读取面必须说明输入 ref、分页 helper、返回类型、稳定排序、空结果语义和错误映射。实现不得自行扫描 storage、解析字符串、从 event payload 拼接 `Derived*ViewRef`,或用临时 helper 伪造 project / member / search view identity。

如果 projection-backed query request 只携带 scope、context、subject、nonconformity、artifact 或其他非 view ref,而 flow 要先读取 stable public view ref,设计必须定义正式 projection index lookup port。该读取面必须说明:

- lookup 输入字段和 typed ref,例如 `scope_ref -> PolicyEffectiveViewRef`。
- 返回类型是 typed view ref 还是 `Option<typed view ref>`。
- lookup row 的持久化唯一键和与 view body 字段的一致性。
- missing lookup 是 missing/degraded projection surface、empty page、not found 还是 request rejection。
- query 不允许创建 view ref、重建 projection、扫描 truth store 或保存 index row。
- fake adapter 与 durable adapter 对 lookup hit、missing、duplicate row、stale row 的等价语义。

仅在持久化章节写 unique key 不足以支撑 query 落码。只要 flow 写了 “map request ref -> stable view ref through projection index”,Step 7 / port 文档必须有等价 `find_*_view_ref_by_*` 读取面,Step 9 必须调用该读取面,Step 11 必须说明 lookup row 和 missing 语义,实施计划必须把该 port 纳入同一 query boundary。

设计必须二选一:

- 当前 boundary 不提供该 truth / marker 的 query / projection surface:明确该 flow 不 mark projection stale,或只在影响已有 public view identity 时标记已有 view。
- 当前 boundary 需要可读 projection:先补 query / view DTO schema、repository key、`Derived*ViewRef` 派生规则、stale marker 语义和测试映射,再要求 flow mark stale。
- 当前 boundary 需要按 external ref / snapshot ref 标脏既有 public views:先补 `list_views_affected_by_*` 或等价正式读取面,再要求 flow mark stale;列表为空时必须明确是 no-op,不是由实现临时构造 view ref。

正确示例:

```text
P0 public DerivedWorkViewRef 只有 project-board / member-work / iteration-summary / work-search。
RequestWorkPromotion 创建 PromoteResult,但 PromoteResult 没有 P0 public query / projection surface。
因此 RequestWorkPromotion 不 mark projection stale。
ReviewWorkPromotion accept 创建 formal WorkItem 时,只标记受影响的既有 board / member / search views stale。
ReviewWorkPromotion reject 不 mark projection stale。
ConsumeIdentityMemberChanged 要按 member ref 标脏时,先调用 ProjectionRepository.list_views_affected_by_member(member_ref, page)。
该 repository 只返回已存在 public DerivedWorkViewRef;空页表示不标脏。

GetPolicyEffectiveView(scope_ref) 先调用 ProjectionRepository.find_policy_effective_view_ref_by_scope(scope_ref)。
命中后读取 PolicyEffectiveView 和 view state。
missing 返回 missing projection degraded surface。
query 不创建新的 PolicyEffectiveViewRef,也不从 scope_ref 拼接 view id。

GetGateDecision(decision_ref) 先调用 ProjectionRepository.find_decision_summary_view_ref_by_decision(decision_ref)。
GetGateDecision(gate_ref) 先调用 ProjectionRepository.find_decision_summary_view_ref_by_gate(gate_ref)。
命中后读取 DecisionSummaryView 和 view state。
missing 返回 missing projection degraded surface。
query 不创建新的 DecisionSummaryViewRef,也不从 decision_ref / gate_ref 拼接 view id。
```

错误示例:

```text
RequestWorkPromotionFlow 要求 projection stale。
Step 8 只定义 project-board / member-work / iteration-summary / work-search。
实现阶段临时派生 promote-intake:{source_id}。
ConsumeMethodDefinitionChangedFlow 写 affected_method_views(definition_ref)。
但 Step 7 没有定义任何 repository / port 可以从 definition_ref 枚举 existing public view refs。

GetPolicyEffectiveViewFlow 写 "map scope_ref -> stable PolicyEffectiveViewRef through projection index"。
Step 7 只有 get_policy_effective_view(view_ref),没有 find_policy_effective_view_ref_by_scope(scope_ref)。
实现者在 query service 中拼 policy-effective:{scope_ref} 或扫描 projection store。

GetGateDecisionFlow 写返回 DecisionSummaryView。
Step 7 只有 get_decision_summary_view(view_ref),没有 find_decision_summary_view_ref_by_decision(decision_ref) 或 find_decision_summary_view_ref_by_gate(gate_ref)。
实现者在 query service 中拼 decision-summary:{decision_id} 或扫描 projection store 找 gate 当前 summary。
```

错误原因:

- repository / fake 无法验证临时 view ref 的 key 规则。
- query surface 不存在,stale marker 没有可观察返回口径。
- projection rebuild 无法知道该 view 如何从 committed truth 重建。
- implementation boundary 会被迫新增未授权 DTO / repository 方法 / tests。
- projection-backed query 的 missing/degraded surface 无法稳定测试;fake 与 durable adapter 可能一个拼出 view ref、一个返回 missing。

### 3.7 Public protocol surface 的传递类型必须闭合

任何进入公开协议 surface 的类型,即使只是某个 DTO 字段的字段类型,也必须有正式 schema、归属和 crate 边界说明。

公开协议 surface 包括:

- Command result / receipt
- Query view / page / marker
- Inbound Event envelope / payload / receipt
- Outbound Event payload
- Operations Job input / output / report
- public error / disposition / quarantine marker

每个传递类型至少要定义:

- 正式归属模块,例如 `contracts/refs.rs`、`contracts/events.rs` 或 `core-contracts`
- struct 字段、enum variant 或 newtype schema
- 哪些 public DTO 使用它
- 字段来源、缺失处理、duplicate / retry / quarantine / delayed 口径
- 是否允许 domain 复用 shared enum,或是否需要 domain 到 public DTO 的正式映射
- crate 依赖方向,尤其是 contracts 不得依赖 domain-only 类型

正确示例:

```text
ManifestationState 属于 contracts/refs.rs shared enum。
domain/manifestation.rs::CrossDomainManifestation 直接复用该 enum。
ManifestExternalFactResult.manifestation_state 和 CrossDomainManifestationChangedEvent.manifestation_state 都使用同一 shared enum。
```

```rust
pub struct InboundEventEnvelope<T> {
    pub event_id: EventId,
    pub event_envelope_ref: EventEnvelopeRef,
    pub event_source_ref: EventSourceRef,
    pub idempotency_key: IdempotencyKey,
    pub occurred_at: Timestamp,
    pub trace_ref: TraceContextRef,
    pub payload: T,
}
```

错误示例:

```text
ManifestExternalFactResult.manifestation_state: ManifestationState。
Consumer handler returns ConsumerReceipt。
Inbound events use InboundEventEnvelope<T>。
```

但 `ManifestationState` 只在 domain 对象章节定义,`ConsumerReceipt` 和 `InboundEventEnvelope<T>` 只有类型名,没有字段。

错误原因:

- contracts DTO 会被迫依赖 domain enum,或在 contracts 中复制第二套 mirror enum。
- consumer 无法判断 duplicate、quarantine、delayed 和 no-op 的返回字段。
- payload 字段和 envelope 字段可能被重复定义,幂等 digest 也无法稳定。
- implementation step 会自行补 schema 或放松校验。

#### 3.7.0 Public protocol 二级类型命名必须唯一

同一 public protocol 概念在 Step 6 object/helper、Step 8 DTO、Step 9 flow、Step 10 state/disposition、Step 12 error/recovery 和 implementation boundary 中必须使用一个正式类型名。若需要从 application helper 映射到 public DTO,也必须明确是“同一 shared type 复用”还是“helper type -> public type 的显式 mapper”,不能让两个同义类型同时存在。

必须检查:

- Step 6 helper 字段类型与 Step 8 public DTO 字段类型是否同名或有正式 mapper。
- `*Ref`、`*MarkerRef`、`*SchemaVersionRef`、`*AlgorithmRef` 这类 body-free marker 是否只有一个 canonical 类型名。
- open item 是否已经把当前 implementation boundary 需要的 shell 排除在外;不能让“算法细节后移”继续阻塞“类型名 / 字段壳可编码”。
- public marker 被 DTO 引用前,是否已经有最小 newtype / struct / enum schema、owner crate 和字段来源。

正确示例:

```text
IdentityRequestDigest.schema_version_ref 使用 IdentityProtocolSchemaVersionRef。
IdentityRequestDigest.algorithm_ref 使用 IdentityDigestAlgorithmMarkerRef。
Step 8 IdentityRequestDigestMarker 使用同一组类型。
OPEN item 只保留 canonical material 和算法迁移细节,不再保留 shell 命名选择。
```

错误示例:

```text
Step 6 IdentityRequestDigest 使用 IdentityDigestSchemaVersionRef / IdentityDigestAlgorithmRef。
Step 8 IdentityRequestDigestMarker 使用 IdentityProtocolSchemaVersionRef / IdentityDigestAlgorithmMarkerRef。
实施计划要求 contracts shell,但 open item 仍声明 schema version / algorithm naming 未闭口。
```

错误原因:

- contracts crate 无法判断应该导出哪一组 public 类型。
- stored replay / idempotency digest / request metadata 会出现两套不可比较 marker。
- 实现端会被迫私下 alias、复制 mirror type 或改 DTO 字段名。

### 3.7.1 Consumer receipt 的 trace record 来源必须闭合

如果 inbound consumer 的 receipt、audit、observability 或 flow 中出现 `trace_record_ref`、`append trace marker`、`trace marker` 或等价字段,设计必须明确该 consumer 是否真的写入正式 trace record。只有同时满足以下条件时,accepted consumer 才能填充 `trace_record_ref`:

- 存在正式 `TraceSubjectRef` / `ProcessTraceSubjectRef` / 等价 trace subject variant。
- 存在正式 trace record schema、factory 和 id 来源。
- flow 中发生的是本仓 committed truth change,或设计明确该 consumer marker 本身是可追溯 truth subject。
- repository / transaction boundary 允许该 trace record 在同一 UoW 中追加。

如果 consumer 只更新 external snapshot、reference resolution state、projection stale marker、pending marker、no-op marker 或 idempotency receipt,且没有正式 trace subject / trace record source,设计必须明确 `ConsumerReceipt.trace_record_ref = None` 或等价 optional 空值。若设计要求 reference-only consumer 也 append marker trace,必须额外定义正式 marker subject mapper / helper,明确从哪个 typed reference marker 输入生成 trace subject、canonical key 表、flow 调用点、transaction ordering 和 fake/durable 等价。不得为了让 receipt “看起来可追溯”而把外部 definition、snapshot、reference state、method ref、source ref 或 projection ref 伪装成现有 trace subject。

同样,如果 handoff、archive、external export、operations job 或其它 marker flow 要求先 append marker trace、生成 non-empty `trace_refs`、或把 marker trace ref 写入 job report / handoff marker,也必须定义正式 marker subject mapper / helper。该 helper 必须声明 typed input 来源,例如 `scope_ref + target_ref`、`handoff_intent_ref` 或其它已闭合 ref;给出 canonical key 表;写明 flow 调用点和 marker trace 相对 adapter / marker save 的顺序;并要求 fake runtime 与 durable adapter 使用同一规则。不得由 service 用 target string、scope string、package ref、receipt ref、job name、job run id、idempotency key、trace id 或 hard-coded string 拼接 trace subject。

正确示例:

```text
ConsumeMethodDefinitionChanged 保存 MethodDefinitionSnapshot、ReferenceResolutionState 和 affected projection stale marker。
MethodDefinitionRef 不是 ProcessTraceSubjectRef,该 consumer 没有 committed Process truth change。
ConsumerReceipt.trace_record_ref = None。
事件追溯由 ConsumerReceipt、StoredOperationResult、consumer audit/log 字段承载。
```

正确示例:

```text
ConsumeMethodDefinitionChangedFlow 保存 MethodDefinitionSnapshot、ReferenceResolutionState 和 affected projection stale marker。
设计正式定义 ReferenceMarkerSubjectMapper.reference_marker_subject(reference_ref)。
canonical key = "process:reference-marker:<reference_ref.0>"。
flow 在同一 UoW 中先 save reference/snapshot,再分配 reference_cursor,再 append TraceRecord::from_marker(trace_id, marker_subject, kind, trace_id, Some(reference_cursor))。
fake runtime 和 durable adapter 使用同一 canonical key。
```

错误示例:

```text
ConsumeMethodDefinitionChangedFlow 第 6 步写 append trace marker。
TraceRepository.append_trace(record) 只接收 committed Process truth change。
ProcessTraceSubjectRef 没有 MethodDefinition / ReferenceSnapshot variant。
实现把 MethodDefinitionRef 塞进 RuntimeShape 或 DerivedView subject,或临时新增字符串 subject。
```

错误示例:

```text
ConsumeMethodDefinitionChangedFlow 写 append trace marker。
TraceRecord::from_marker(..., TraceSubjectRef(format!("reference:{}", event.source_ref)), ...)。
设计没有 ReferenceMarkerSubjectMapper,没有 canonical key 表,也没有 fake/durable 等价规则。
```

错误原因:

- trace query 会把 external snapshot intake 错读成 Process truth change。
- repository / fake 无法验证伪造 subject 的 projection、handoff 和 audit 关系。
- duplicate receipt 的 `trace_record_ref` 无法稳定 replay。
- 实现者被迫自行新增 public subject variant 或绕过正式 flow。
- fake 与 durable 可能生成不同 marker subject,导致 duplicate replay、trace query 和测试断言无法稳定。

### 3.8 target / intent / output / marker ref 生命周期角色必须闭合

同一 flow 中若同时出现 target ref、intent、port output ref、marker ref 或 receipt ref,设计必须明确它们分别处于哪个生命周期阶段,不得因为名称相近或都指向外部边界而默认等价。

最小定义表:

| 生命周期角色 | 要求 |
|---|---|
| target ref | 表示调用前的目标或接收方,通常来自 request / job input / policy;不得表示外部 port 已生成的结果 |
| intent | 表示交给 port / adapter 的准备意图,字段必须来自 truth、target ref、metadata 或正式派生规则 |
| port output ref | 表示外部 port / adapter 返回的结果指针,只能在调用成功后出现 |
| marker / receipt ref | 表示本仓记录已准备、已交接、已发布或已归档的本地证据,必须说明使用 target ref 还是 output ref |

正确示例:

```text
TraceHandoffTargetRef 是 PrepareTraceHandoffJobInput.target_ref,表示 handoff 目标。
TraceHandoffIntent.target_ref 使用 TraceHandoffTargetRef。
TraceHandoffPort.prepare_trace_handoff(intent) 返回 TraceHandoffRef。
TraceHandoffMarker::from_trace(trace_id, handoff_ref) 使用 TraceHandoffRef 记录 port 返回结果。
ArchiveHandoffRef 是 ArchiveHandoffPort 的输出,不得作为 trace handoff intent 输入。
```

错误示例:

```text
TraceHandoffIntent.target_ref: TraceHandoffTargetRef。
WorkTraceRecord.prepare_handoff(archive_ref: ArchiveHandoffRef)。
Flow 中又写 record.prepare_handoff(input.target_ref.into_archive_ref())。
```

错误原因:

- target ref 和 output ref 的生命周期角色相反,实现者无法判断 domain helper 应接收调用前目标还是调用后结果。
- port 成功前无法获得 output ref,flow 会被迫伪造转换函数或提前生成外部结果。
- marker / receipt 无法稳定断言是记录“准备意图”还是“外部返回结果”。

### 3.9 Truth change 到 outbound event routing 必须闭合

任何会被用于创建 trace / outbox 的 domain truth change variant,都必须有正式的一对一 routing 链路。实现者不得自行判断是否复用某个已有 outbound event。

最小 routing 链路:

```text
TruthChange variant
  -> OutboxEventKind
  -> OutboundEvent payload schema
  -> payload builder / truth lookup
  -> topic
  -> publisher dispatch branch
  -> contract / publisher / acceptance test mapping
  -> implementation boundary
```

每个 routing 至少要定义:

- truth change variant 的字段和来源。
- 对应的 outbox event kind。
- outbound payload 的 struct / enum schema、字段来源和禁止携带字段。
- payload builder 需要加载的 committed truth 或 reason / marker。
- topic 名称和订阅方。
- publisher dispatch 分支和失败 / retry / failed marker 口径。
- 测试方案、验收接口同步和实施计划中的事件计数与用例映射。

如果一个 truth change 被设计为复用聚合事件,必须在字段表中证明该聚合事件能承载该 truth change 的全部状态、reason 和 ref;否则必须新增专用 event。新增或删除 outbound event 时,正式文档、测试方案、验收标准和实施计划中的事件数量必须同批更新。

如果 publisher 需要由 outbox record 构造 outbound payload,设计还必须定义 outbox fact 到 committed source object 的正式闭环。`event_kind` 只能说明路由类别,不能替代 source identity。设计必须二选一并写入对象契约、repository / port、flow 和持久化契约:

1. outbox record 持久化 typed source identity,例如 `source_ref` / `payload_source_ref`,并携带 payload 所需的 safe reason、marker、trace context 或 occurred time。
2. 保持 outbox record 极简,但定义正式 source loader,例如 `load_<event>_source(outbox_id)`,并说明它如何从 `outbox_id` 找到 committed source object 和 payload supplement。

每个 outbound event 至少要说明:

- outbox record 中保存哪些 source identity / reason / marker / trace fields。
- publisher 读取哪个 repository / port 回查 committed source object。
- payload 字段哪些来自 source object,哪些来自 outbox record。
- source missing、event kind / source mismatch、payload supplement missing 时如何 mark failed。
- publisher adapter 接收的是完整 outbound publication material,还是 outbox record;若只接收 outbox record,必须证明 adapter 有正式 source loader,不得自行扫描 storage 或用 latest state 补字段。
- publisher / handoff / export adapter 的失败如何映射到 retryable failed、permanent failed、dead-letter、delivered 或 skipped 等状态;如果这些状态分支会由 port 返回结果驱动,port 必须返回正式 outcome enum 或等价结构化分类,不得只返回 raw error / string reason 再让 service 或 fake 自行判断。

Adapter failure outcome 分类也必须闭环:

| 正例 | 反例 |
|---|---|
| `publish(...) -> OutboxPublisherOutcome::{Published, RetryableFailed, FatalFailed}`;flow 只按 variant 调用 `mark_published` / `mark_failed` / `mark_dead_lettered` | `publish(...) -> Result<PublicationRef, FailureReason>`;service 根据 `FailureReason` 文本、HTTP status 或异常类型决定 dead-letter |
| `deliver_handoff(...) -> HandoffDeliveryOutcome::{Delivered, RetryableFailed, Failed}`;fake 与 durable 使用同一 enum | fake 对某些 target 默认 delivered,durable adapter 抛 error 后 service 自行猜是否可重试 |

禁止写法:

```text
WorkOutboxRecord 只有 outbox_id、event_kind、publication_state。
Publisher 根据 outbox ref load source object。
ProjectChangedEvent::from_project(project, reason)。
```

错误原因:

- `outbox_id` 没有定义到 Project / Backlog / trace / derived view 的回查路径。
- `event_kind` 无法携带 payload 所需的 reason、handoff marker、trace context 或 occurred_at。
- publisher 会被迫自行解析 id、扫描 repository、读取 latest truth 或发明 typed source loader,形成第二真相。

正确示例:

```text
WorkTruthChange::BacklogAvailabilityChanged(BacklogRef)
  -> WorkOutboxEventKind::BacklogChanged
  -> WorkOutboxSourceRef::Backlog { backlog_ref, reason }
  -> BacklogChangedEvent { backlog_ref, project_ref, backlog_state, reason }
  -> work.backlog.changed.v1
```

错误示例:

```text
WorkTruthChange::BacklogAvailabilityChanged 已进入 outbox。
Outbound event list 只有 ProjectChanged,且 ProjectChangedEvent 没有 backlog_state / BacklogMaintenanceReason。
```

错误原因:

- 实现者无法判断 backlog availability 是否应复用 ProjectChanged 或新增事件。
- outbox event kind、payload builder、topic 和 publisher dispatch 无法 1:1 落码。
- 测试与验收仍按旧事件数量编排,会漏掉新增 truth change 的发布闭环。

### 3.10 Outbox payload snapshot 保存面迁移必须进入实施边界

当详细设计已经要求 outbox record 持久化 payload snapshot、trace context、visibility marker 或 typed source identity,而实现仓仍保留旧的 outbox intent / minimal event kind port 时,实施计划必须把正式 outbox record 保存面的迁移放进第一个依赖该 payload 的 commit boundary。不能只把 payload builder / DTO 列入 boundary,让实现者继续在旧 port 上旁路保存或 publish 时重算 payload。

最少要在实施计划中明确:

- 哪个 commit boundary 负责把 repository trait 改为正式 outbox record 保存面。
- 哪些 application accepted-flow call sites 必须从旧 append intent 改为 `append(record)`。
- infra fake / in-memory store 必须保存哪些正式字段。
- payload builder tests 之外,需要有 outbox record persistence tests 证明 snapshot 在 accepted transaction 内保存。
- 旧保存面不得继续作为 parallel path 或 publisher 旁路输入。

正确示例:

```text
commit-08-b:
先迁移 ProcessOutboxRepository::append(ProcessOutboxRecord, ...),
并更新 accepted-flow call sites 和 in-memory outbox store,
再实现 ProcessInstanceChanged / ActivityProgressed / ProcessTimingChanged payload builders.
测试覆盖 payload_snapshot 在 accepted transaction 内保存。
```

错误示例:

```text
commit-08-b 只实现 ActivityProgressedEvent payload builder。
现有 ProcessOutboxRepository 仍只保存 event_kind + subject_ref + trace_ref。
publish job 或测试 helper 另外读取 current truth 生成 payload。
```

错误原因:

- payload builder 没有正式持久化路径,只能成为旁路 helper。
- publish job 会绕过 accepted transition snapshot,重读 latest truth 形成第二真相。
- 后续 retry / duplicate / invalid mapping tests 无法证明发布的是已提交 outbox record。

## 四、状态闭环标准

### 4.1 状态名必须全链路一致

以下位置必须使用同一套正式状态名：

- domain enum
- state matrix
- protocol DTO / event
- query projection
- test case
- acceptance criteria
- implementation plan

错误示例：

```text
03-详细设计: Rejected
Step 6 object contract: Failed
Step 10 state matrix: Failed
测试断言: Rejected
```

错误原因：

- 代码 enum、测试断言和验收结果无法统一。

### 4.2 transition 必须归属唯一 phase

每条状态迁移必须明确由哪个 command / flow / phase 推进。

Precheck 只允许验证当前 truth 是否已经满足前置条件,不得隐藏执行状态迁移。若某个 flow 在 precheck 阶段需要把对象从 A 推到 B,设计必须把该迁移提升为该 flow 的正式 domain step,并同步写入 Step 9 flow、Step 10 状态矩阵、Step 16 测试切口和 `07-实施计划.md` commit boundary。否则 precheck 必须只拒绝不满足状态的输入,不能顺手修正状态。

正确示例：

```text
PH-03 RunDeliveryProgression: Pending -> Delivered / Failed
PH-05 RecordDeliveryFeedback: Delivered -> Completed
```

正确示例：

```text
OpenGovernanceGateFlow:
  no approver_requirement_intent -> final GateState::Open.
  with approver_requirement_intent -> create responsibility, then call gate.request_decision_by_ref(...) in the same command, final GateState::PendingDecision.

RecordGovernanceDecisionFlow:
  precheck requires loaded gate already PendingDecision.
  if loaded gate is Open, reject;do not perform Open -> PendingDecision inside precheck.
```

错误示例：

```text
PH-03 测试要求 RunDeliveryProgression 直接到 Completed。
PH-05 又定义 feedback 才能 mark_completed。
```

错误示例：

```text
Step 9 says OpenGovernanceGateFlow final state is GateState::Open.
Step 10 says request_decision_by_ref belongs to RecordGovernanceDecisionFlow precheck.
RecordGovernanceDecisionFlow silently changes Open -> PendingDecision before proposing a decision.
```

错误原因：

- 一个状态被两个 phase 同时拥有。
- precheck 的语义从“校验”变成“状态修复”,实现者无法判断应该在 OpenGate 还是 RecordDecision 中保存 final gate。
- trace/outbox/result 的 final state 也不唯一,同一个 command 可能记录 Open 或 PendingDecision。

### 4.3 状态矩阵引用的错误必须进入错误模型

状态矩阵、非法转换表、flow 错误映射或测试切口中出现的每个错误 variant,都必须在正式错误模型中有定义。

最少要闭合:

- 所属层和模块,例如 `DomainError` / `ApplicationError` / `JobError`
- enum variant 或错误类型名称
- 触发条件
- 是否可重试
- 对外映射
- 恢复口径
- 测试断言或 evidence 口径

正确示例:

```text
TraceHandoffState.RetryPending -> RetryPending 的 mark_retry(...) 在超限时返回 DomainError::RetryLimitExceeded。
Step 12 错误类型表定义 DomainError::RetryLimitExceeded。
错误映射为 handoff Failed marker / operations evidence。
恢复口径为停止自动 retry,由 operations review 或创建新 handoff intent。
测试断言 TC-CONV-HANDOFF-* 使用 RetryLimitExceeded 或 failed marker。
```

错误示例:

```text
Step 10 状态矩阵写 DomainError::RetryLimitExceeded。
Step 12 错误模型只列 InvalidStateTransition、BoundaryViolation、DigestMismatch。
实现仓 domain errors.rs 也没有 RetryLimitExceeded。
```

错误原因:

- 实现者无法 1:1 定义 domain error enum。
- 状态机单测无法选择断言 `InvalidStateTransition` 还是 `RetryLimitExceeded`。
- application / job 层无法稳定映射 retry exhausted 与普通非法状态。
- 后续实现会被迫自行补错误 variant 或把精确错误退化成泛化错误。

### 4.4 factory 初始状态必须保留 command 可执行迁移

只要当前 phase 的 command / flow 会调用某个 domain transition method,该对象的 factory 初始状态、状态矩阵和 flow 伪码必须共同保留一条可执行迁移。

不得让 factory 直接创建到该 command method 的目标终态,再让 flow 对同一个对象调用 no-op 或非法 transition。

最少要闭合:

- factory 根据 kind / source / intent 选择的初始状态。
- command flow 调用的 domain method。
- 状态矩阵中该 method 的 `from -> to` 迁移。
- 目标终态是否允许 factory 直接创建;若允许,必须说明该 flow 不再调用对应 transition method。
- domain / service 测试同时覆盖 factory 初始状态和 command transition。

正确示例:

```text
GatewayKind::ParallelJoin factory -> GatewayState::PendingJoin。
JoinGateway flow 调用 Gateway.join_tokens(token_set)。
状态矩阵定义 PendingJoin -> Joined。
测试覆盖 pure join factory 初始为 PendingJoin,以及 PendingJoin -> Joined 后 selected_route_ref 为空。
```

错误示例:

```text
GatewayKind::ParallelJoin factory -> GatewayState::Joined。
JoinGateway flow 仍然调用 Gateway.join_tokens(token_set)。
状态矩阵只定义 RouteSelected -> Joined。
```

错误原因:

- command flow 没有合法 from-state,实现者只能把 transition 写成 no-op、放宽非法状态或自行新增状态。
- domain 单测无法判断 pure join gateway 是创建即终态,还是必须由 JoinGateway 推进。
- application flow 与状态矩阵对同一 command 的职责不一致。

### 4.5 public target enum variant 必须穷尽闭环

只要一个 `*Target`、`*Decision`、`*Action` 或等价 public command target enum 进入 request DTO,其中每个未标记为 reserved / future-only 的 variant 都必须有正式闭环。

最少要闭合:

- request DTO schema 和字段表。
- variant 到 domain method 的 flow 分支。
- variant 对应的 reason / evidence / actor / version 校验口径。
- 状态矩阵中的 from / to 迁移。
- contract / domain / service 测试切口。
- 验收接口或 evidence 映射。

如果某个 variant 暂不暴露为当前 boundary 的 public write path,必须二选一:

- 从 public DTO enum 中移除该 variant。
- 明确标注该 variant 为 reserved / future-only,并说明当前 flow must reject 或不接受该值。

正确示例:

```text
DependencyTarget includes Active / Satisfied / Waived / Cancelled.
UpdateWorkDependencyStateFlow has branches for all four variants.
Active requires DependencyChangeReasonKind::Activated and performs Proposed -> Active.
Satisfied requires verified evidence and DependencyChangeReasonKind::SatisfiedByEvidence.
Step 10 and tests cover Proposed -> Active and Active -> terminal.
```

错误示例:

```text
public enum DependencyTarget includes Active.
State matrix says Proposed -> Active via UpdateWorkDependencyStateFlow.
Flow pseudo-code only handles Satisfied / Waived / Cancelled.
Test plan only covers Active -> terminal.
```

错误原因:

- 实现者无法判断 public DTO 是否应该接受 `Active`。
- domain state test 和 application contract test 会选择不同状态范围。
- 后续 service / outbox / audit 分支会形成第二真相。

### 4.6 history record 构造必须闭环

如果 flow、transaction boundary、state matrix、test cut 或验收标准要求 `append history`、`write history`、`history record` 或等价副作用,设计必须同时给出对应 history object 的正式构造闭环。

最少要闭合:

- history record 的 schema、归属模块、主键和 append-only 语义。
- history / progression record 主键的来源;若 domain 不得自行生成 id,必须在 `IdGeneratorPort` 或等价 application id source 中定义对应 `new_*_id()` 方法,并让 factory / domain method 接收该 id。
- factory / constructor 签名,以及每个输入参数的来源。
- history 字段从哪个 truth、request、policy output 或 adapter result 读取。
- 哪些 flow 可以构造该 history,哪些相似 flow 明确不构造。
- transaction boundary 中 state save、history append、trace / outbox、idempotency complete 的顺序。
- 测试断言是检查 history object,还是只检查 trace / audit / outbox。
- 若某个 domain method 返回 history / progression record,该 method 的入参和对象可见字段必须足够构造 record 的所有必填字段;否则 method 只能返回 `()` / changed entity / marker,由 application 在同一 UoW 用正式 factory 构造 record。
- 若 history / progression record 的字段来自多个同事务 truth 变更,必须明确构造时机晚于所有字段来源形成;前置 domain transition 只能返回 state delta / transition outcome,不得提前返回完整 record。
- 若一个 command flow 在主对象之外创建 / 更新 secondary truth object,并为该 secondary object 发出独立 changed event、audit 或 projection stale,必须显式裁定是否 append 该对象家族的 history record。若 append,必须给出 change kind、history id source、trace ref 来源、audit flag、same UoW 顺序和测试断言;若不 append,必须明确写成 trace / audit / outbox only,并说明该 secondary transition 没有 history 语义。

通用文案不得把 `history / trace` 写成所有 accepted command 都必须追加一个 history record。若某个 lifecycle-only flow 没有可定义的 history 字段来源,必须明确写成 trace / audit / outbox only,或先补 history schema 与 factory。

正确示例:

```text
IterationChangeRecord { change_id, iteration_ref, changed_work_refs }
factory: from_commitment(change_id, iteration, commitment, actor)
only used by CommitIterationScopeFlow and UpdateIterationCommitmentFlow.
UpdateIterationLifecycleFlow does not append IterationChangeRecord;
lifecycle change is represented by iteration save、optional commitment close、trace、IterationChanged outbox and projection stale.
```

错误示例:

```text
UpdateIterationLifecycleFlow -> append IterationChangeRecord.
IterationChangeRecord only has from_commitment(...), with changed_work_refs from commitment.
Lifecycle flow has no changed_work_refs source, so implementation constructs changed_work_refs = [].
```

错误原因:

- 实现者会被迫发明空 history、临时 constructor 或第二 truth。
- transaction tests 无法判断应断言 history append 还是 trace / outbox。
- append-only history 表会保存语义不成立的记录,后续 query / evidence 会误读业务变化。

正确示例:

```text
OpenGovernanceGateFlow:
- no approver_requirement_intent:
  save Gate(Open), emit GateChanged, no responsibility history.
- with approver_requirement_intent:
  save Gate(PendingDecision)、ApproverRequirement、ApprovalResponsibility、ResponsibilityChain;
  emit GateChanged and ApprovalResponsibilityChanged;
  append ResponsibilityTraceRecord::from_responsibility_change(
    new_responsibility_trace_record_id(),
    responsibility,
    "responsibility-required" or "responsibility-assigned",
    actor,
    approval_responsibility_trace_ref,
    audit_required = true
  ) in the same UoW.
TC-GOV-CMD-004 asserts the responsibility record, change kind, trace/outbox/stale/result in one transaction.
```

错误示例:

```text
OpenGovernanceGateFlow:
with requirement -> save optional responsibility/chain;
append trace/audit/outbox/stale/result.

No statement says whether ResponsibilityTraceRecord is appended.
ApprovalResponsibilityChanged event still exists.
```

错误原因:

- 实现者无法判断是否要为同一 `ApprovalResponsibilityChanged` 追加 responsibility history。
- fake runtime、durable repository 和测试可能分别选择“补 history”或“只写 trace/outbox”,形成第二真相。
- audit 事件如果带 `responsibility_record_ref`,就会缺少正式来源;如果不带,又与对象家族 history 语义不一致。

正确示例:

```text
ActivityTransitionOutcome { progression_id, activity_ref, from_state, to_state, feedback_ref } is returned by Activity.ready/start/complete/...。
ActivityProgressionRecord { progression_id, activity_ref, from_state, to_state, feedback_ref, token_refs, gateway_ref, selected_route_ref }
IdGeneratorPort.new_activity_progression_id() -> ActivityProgressionId。
Activity.ready(progression_id, actor) -> ActivityTransitionOutcome。
ActivityProgressionRecord::from_activity_transition(outcome, changed_token_refs, changed_gateway) is called by application after token / gateway flow-control truth has changed in the same UoW。
ProcessInstance.advance(activity_ref, actor) -> () only updates current_activity_ref;
it does not return ActivityProgressionRecord because ProcessInstance cannot see from_state / to_state / token_refs / gateway_ref.

ProcessTraceRecord::from_truth_change(trace_id, change, trace_context) is called by application after committed truth.
IdGeneratorPort.new_process_trace_id() -> ProcessTraceId。
ProcessInstance.complete(actor) -> () only updates instance_state;
ProcessInstance.cancel(reason, actor) -> () only updates instance_state / terminal truth.
They do not return ProcessTraceRecord because ProcessInstance cannot see trace_id or TraceContext.
```

错误示例:

```text
ActivityProgressionRecord requires progression_id.
factory: from_activity_transition(activity, from_state, to_state, token_refs, gateway)
IdGeneratorPort has no new_activity_progression_id.
Activity.ready(progression_id, actor) -> ActivityProgressionRecord,
but token_refs / gateway_ref / selected_route_ref are only known after token / gateway flow-control runs.
ProcessInstance.advance(activity_ref, actor) -> ActivityProgressionRecord,
but ProcessInstance has no activity state, feedback ref, token refs, or gateway ref fields.

ProcessTraceRecord requires trace_id and TraceContext.
factory: from_truth_change(trace_id, change, trace_context)
IdGeneratorPort has new_process_trace_id(), but ProcessInstance.complete(actor) -> ProcessTraceRecord.
ProcessInstance.cancel(reason, actor) -> ProcessTraceRecord.
The instance object has no trace_id or TraceContext fields.
```

错误原因:

- domain 会被迫自行生成 id,违反 id source 规则。
- factory 无法填充 record 主键。
- 返回 record 的 method 没有足够可见数据,实现只能临时补字段、加载外部对象或构造不完整 record。
- record 构造早于 token / gateway / route 等字段来源形成,会迫使实现从 request 或 adapter 私有字段推导 committed truth。

### 4.7 public command intent 必须结构化闭环

只要 request DTO 中的 `*IntentRef`、`*ProgressionInput`、`*ActionRef` 或等价字段会决定调用哪个 domain method,它就不能是未定义的 opaque string / ref。即使字段名包含 `Ref`,只要它驱动状态迁移或 flow-control 副作用,设计必须把它作为结构化 command intent helper 正式定义。

最少要闭合:

- intent helper 的归属模块、struct / enum schema、variant 和字段级 validation。
- 每个 intent variant 到 domain method 的唯一映射,例如 `Ready -> Activity.ready(progression_id, actor)`。
- variant 需要的 reason、evidence、summary、target、version、scope 和 policy input 来源。
- 同一 command 中 token / gateway / graph / projection 等 flow-control 副作用的 truth 落点。
- 状态矩阵中 from / to 迁移和副作用字段,以及持久化契约中的保存字段 / repository 读取口径。
- command result、outbound event、history / trace 字段是否复制该 intent 造成的 committed truth。
- canonical digest / idempotency 是否使用结构化 intent,以及 duplicate replay 是否返回原 result surface。
- contract / domain / service / event 测试是否覆盖每个非 reserved variant。

正确示例:

```text
ActivityProgressionIntentRef {
  activity_transition: ActivityProgressionTransition,
  flow_control: ActivityFlowControlIntent
}

ActivityProgressionTransition::Complete { reason, feedback_summary_ref }
  -> Activity.complete(progression_id, reason, actor)
  -> feedback summary from ReferenceSnapshotRepository

ActivityFlowControlIntent::SelectGatewayRoute { token_ref, gateway_ref, route_ref, next_position_ref, decision_reason }
  -> ProcessShapeRepository.get_gateway_route_set(gateway_ref)
  -> GatewayRoutingPolicy.assert_route_allowed(...)
  -> Gateway.select_route(route_ref, decision_reason, actor)
  -> Token.move_to(next_position_ref)
  -> Gateway.selected_route_ref is persisted and copied to result/event.
```

错误示例:

```text
AdvanceProcessActivityRequest { progression_ref: ActivityProgressionIntentRef }
Flow says "based on progression_ref call Activity.ready/start/complete/skip/fail".
ActivityProgressionIntentRef has no schema, and selected route is not stored on Gateway.
```

错误原因:

- 实现者无法知道 request 值对应哪个 domain transition。
- token / gateway 副作用会被实现为临时字符串约定或 adapter 私有字段。
- command result、outbound event 和 duplicate replay 无法从 committed truth 复制稳定字段。
- 状态矩阵说“记录 selected route”,但 truth / persistence 没有落点,会形成第二真相。

### 4.8 command intent membership / bootstrap summary 读取面必须闭合

只要 command intent 中的 ref 需要校验“属于某个 active profile、runtime shape、external snapshot、safe summary 或其它正式集合”,并且 flow 还要用该 ref 构造 domain object、选择 kind、创建 gateway / route / token / activity、或校验是否需要 tracking,设计不能只写“validate against shape / profile / summary”。必须定义正式 body-free summary schema 和 repository / port 读取面。

最少要闭合:

- summary 类型归属、字段 schema 和禁止正文规则。
- repository / port 方法签名,包括输入 scope ref、candidate ref、返回 `Option<Summary>` / error、空结果语义。
- summary 字段到 domain factory / policy 的映射,例如 `activity_kind -> Activity::from_shape_node(...)`。
- request intent 字段与 summary 字段的匹配规则,包括 required / forbidden / mismatch 的错误口径。
- id 生成来源:caller ref 若只是 shape / external summary identity,不得替代本仓 truth id。
- contract / service / fake 测试覆盖 success、missing summary、membership mismatch、required field missing、forbidden field present 和 kind 来源。
- 明确不得读取外部 body、runtime shape body、adapter 私有字段、storage scan 或字符串约定来补 summary。

正确示例:

```text
StartProcessInstanceRequest.start_intent_ref.start_node_ref 要求属于 active profile 的 runtime shape start node set。
Step 7 定义 ProcessShapeRepository.get_start_bootstrap_summary(profile.shape_ref, start_node_ref)
  -> Option<ProcessStartBootstrapSummary>。
ProcessStartBootstrapSummary 包含 start_node_ref、activity_kind、requires_gateway_tracking、initial_gateway { gateway_ref, shape_node_ref, gateway_kind }。
Flow 用 summary.activity_kind 创建 Activity,用 summary.requires_gateway_tracking 校验 request.initial_gateway_ref 是否必填 / 禁止,用 summary.initial_gateway.shape_node_ref / gateway_kind 创建 Gateway。
GatewayId 仍由 IdGeneratorPort 生成;request.initial_gateway_ref 只用于匹配 shape summary。
```

错误示例:

```text
StartProcessInstanceFlow 写:
validate start_node_ref belongs to active profile runtime shape start node set;
initial_gateway_ref only when start node requires gateway tracking;
Activity::from_shape_node(...) requires ActivityKind.

但 Step 7 只有 get_gateway_route_set(gateway_ref),没有 start node set、shape node -> ActivityKind、requires gateway tracking 的读取面。
```

错误原因:

- service 无法判断 start node membership 和 gateway tracking 要求。
- `ActivityKind` / `GatewayKind` 没有正式来源,实现会从 node id 字符串或 adapter 私有状态推断。
- fake repository 无法构造 missing / mismatch / forbidden gateway 的 contract test。
- caller ref 可能被误用为本仓生成的 `GatewayId` 或其它 truth id。
- duplicate result、trace、outbox 和 integration tests 无法证明 bootstrap 使用的是 committed body-free shape summary。

### 4.9 body-free snapshot helper 判定字段必须闭合

只要 body-free snapshot、safe summary、reference marker 或本地 mirror helper 暴露 `matches_*`、`covers_*`、`supports_*`、`relates_to_*`、`is_applicable_to_*` 等判定函数,设计不能只写“基于 summary / marker 判断”。判定函数用到的 marker、scope、kind、capability set、version、source family 或其它输入必须成为该 helper 的正式 schema 字段,并进入 factory、字段来源、持久化、flow precheck、event / job digest 和测试断言。

最少要闭合:

- helper 所属模块和 public / domain / application 边界。
- 判定所需字段 schema、字段表、来源和缺失处理。
- factory / resolver / consumer payload 如何填充这些字段。
- 判定函数的精确定义,例如 stable identity equality、set contains、kind equality 或 finite-state check。
- 哪些复杂关系不由 helper 判断,例如 scope inheritance、graph traversal、policy override 或 external body parsing。
- flow 在调用 helper 前后的 reject / degraded / delayed / unavailable 错误口径。
- persistence / fake runtime 是否保存该字段,duplicate digest 是否包含该字段。
- contract / domain / service tests 覆盖 match、mismatch、missing marker 和 forbidden body。

禁止写法:

- `matches_scope(...)` 声称“基于 summary ref / scope marker”,但 snapshot schema 没有 scope marker 字段。
- helper 通过解析 `SafeSummaryRef`、opaque id 字符串、external ref path 或 adapter 私有字段判断适用范围。
- helper 暗中读取 policy body、shape body、profile body、external GRC body 或 storage scan。
- flow 只写 “validate snapshot applies to scope”,没有说明 helper 字段、repository / resolver 来源和 mismatch 行为。

正确示例:

```text
MethodPolicySnapshot:
  policy_ref: MethodPolicyRef
  policy_version_ref: MethodPolicyVersionRef
  scope_ref: GovernanceScopeRef
  summary_ref: SafeSummaryRef
  snapshot_state: ReferenceResolutionState

from_method_library(policy_ref, version_ref, scope_ref, summary_ref, snapshot_state)
  要求 scope_ref 来自 method safe summary / resolver 的 body-free scope marker。

matches_scope(scope_ref)
  只比较 self.scope_ref.same_scope(&scope_ref)。
  不读取 AIPolicyDef body,不解析 summary_ref,不判断 parent/child scope。

ActivatePolicyEffectiveFactFlow:
  if !policy_snapshot.matches_scope(scope_ref) => reject before saving PolicyEffectiveFact。
  跨 scope 继承和 override 另由 PolicyScopePolicy + repository relation 处理。
```

错误示例:

```text
MethodPolicySnapshot:
  policy_ref
  policy_version_ref
  summary_ref
  snapshot_state

matches_scope(scope_ref)
  基于 summary ref / scope marker 判断。
```

错误原因:

- schema 没有 `scope_ref` 或 `scope_marker_ref`,实现者只能解析 `summary_ref` 或临时读取 method body。
- factory 无法从 consumer payload / resolver summary 填充判定输入。
- flow 的 scope mismatch 无法稳定落成 reject,service / fake / tests 会各自发明规则。
- duplicate digest 和 persistence 不保存判定字段,重复回放可能与首次执行不一致。

### 4.10 domain guard / policy 的每个参数必须有正式来源

只要 Step 9 flow 调用 domain guard、policy factory 或校验函数,函数签名中的每个参数都必须能从正式 request DTO、loaded truth、resolver / repository port、operation context 或已生成 id 中逐一取得。设计不能只在 flow 里写局部变量名,也不能要求实现者从 opaque ref、scope ref、route path 或 adapter 私有索引反推出缺失参数。

最少要闭合:

- guard / policy 函数签名和所有参数类型。
- 每个参数的来源字段、读取 port 或生成 port。
- 缺失、不可解析、不匹配时的 rejected / degraded / delayed 口径。
- 是否允许从 loaded truth 复制字段;若允许,必须说明 loaded truth 的 repository 读取面。
- 是否禁止反向推导;例如 `scope_ref` 不得反推出 `subject_ref`,除非 Step 7 明确定义唯一读取面。
- 若 guard 判断的是两个 ref 之间的业务关系,必须给出正式 relation decision / resolver / repository 或字段级 contract 规则;两个 request ref 同时存在不等于关系成立。
- duplicate digest、stored result 和测试切口必须包含会影响 guard 结果的 request 参数。

正确示例:

```text
ActivatePolicyEffectiveFactRequest:
  policy_snapshot: MethodPolicySnapshot
  subject_ref: GovernedSubjectRef
  scope_ref: GovernanceScopeRef
  priority: PolicyPriority
  activation_intent: PolicyActivationIntent

ActivatePolicyEffectiveFactFlow:
  relation = external_source_resolver.resolve_scope_subject_relation(
    request.subject_ref,
    request.scope_ref,
  )
  scope_policy = PolicyScopePolicy::for_subject(request.subject_ref, request.scope_ref)
  scope_policy.assert_scope_matches_subject(relation)
  if relation.state in [Mismatch, Unknown] => reject before save
  if !request.policy_snapshot.matches_scope(request.scope_ref) => reject before save

Digest stable input:
  policy_snapshot ref/state/digest fields + subject_ref + scope_ref + priority + activation_intent

Test fixture:
  resolver returns Allowed / Mismatch / Unknown explicitly
```

错误示例:

```text
ActivatePolicyEffectiveFactRequest:
  policy_snapshot
  subject_ref
  scope_ref
  priority
  activation_intent

ActivatePolicyEffectiveFactFlow:
  scope_policy = PolicyScopePolicy::for_subject(request.subject_ref, request.scope_ref)
  scope_policy.assert_scope_matches_subject(request.scope_ref, request.subject_ref)
```

错误原因:

- `subject_ref` 和 `scope_ref` 同时来自 request,只能证明入参存在,不能证明二者业务关系成立。
- `assert_scope_matches_subject(request.scope_ref, request.subject_ref)` 若没有 relation source,只能落成恒真同一性检查或临时解析字符串。
- 实现者只能解析 `scope_ref`、扫描 repository 私有索引或硬编码 fixture 才能构造 guard。
- subject/scope mismatch 测试和 duplicate digest 无法稳定复现首次执行结果。

## 五、metadata / idempotency / UoW 标准

### 5.1 metadata authority 必须唯一

每个项目必须说明 metadata 来源：

- 复用上游 shared metadata
- 本项目 wrapper shared metadata
- 本项目自定义 metadata

如果复用上游，就不得在本地 DTO 中重复承载同一字段。

正确示例：

```text
Conversation command 使用 core_contracts::CommandMetadata.request 承载 request_id、trace_id、idempotency_key。
本地 command DTO 不再定义顶层 trace_ref / idempotency_key。
```

错误示例：

```text
本地 command 顶层有 idempotency_key / trace_ref。
core CommandMetadata.request 也有 idempotency_key / trace_id。
```

### 5.2 idempotency 必须定义 digest 和 result ref

幂等契约至少要定义：

- operation
- idempotency key
- request digest
- reserve / complete / conflict 签名
- result_ref / application_result_ref
- duplicate same digest 返回
- same key different digest conflict 返回
- UoW 是否参与
- result_ref 如何读回完整 result surface
- stored result 缺失时的错误 / 恢复口径

正确示例：

```text
IdempotencyRepository.reserve(operation, key, request_digest, uow)。
same key + same digest 返回 Duplicate(result_ref)。
same key + different digest 返回 Conflict(conflict_ref)。
CommandResultRepository.get_result(result_ref) 读取原 result surface。
```

如果 `IdempotencyRecord` 还保存 channel / entry kind / operation context 字段,则正确示例必须升级为:

```text
context = OperationContext::from_command_or_event_or_job(...)。
IdempotencyRepository.reserve(&context, request_digest, uow)。
```

错误示例：

```text
IdempotencyRepository.reserve(operation, key)。
duplicate/conflict 根据 request digest 判断。
```

错误原因：

- repository 签名没有 digest，却要求 digest 语义。

### 5.3 duplicate result surface 必须有读取闭环

如果设计要求 duplicate same digest 返回“既有 result surface”,不能只定义 `result_ref` / `application_result_ref`。必须继续定义这个 ref 到完整 public result DTO 的读取链路。

至少要定义：

- result surface 存储位置或重构来源。
- 保存 result surface 的 repository / port / store 签名。
- success path 中 result surface save 与 `IdempotencyRepository.complete(...)` 的 UoW 顺序。
- duplicate path 中按 `result_ref` load 的 repository / port 签名。
- result kind / operation 不匹配时的错误。
- result surface 缺失时的错误、恢复和对外映射。
- duplicate receipt 是持久化原值还是 replay 时 overlay。
- 禁止重放 domain transition 的边界。

若 duplicate 对象是 operations job,且文档写了 “duplicate returns stored report / existing report / existing marker”,同样必须定义 job report result surface。不能只定义 command result store,也不能让 job duplicate 重新扫描当前 truth / projection / outbox 后临时生成一个新 report。

如果 worker/job/API entry object 要在 dispatch 后维护逐项 outcome refs,例如 `published_outbox_refs`、`failed_outbox_refs`、`skipped_refs` 或 `processed_refs`,这些 refs 必须由 application facade 返回的 public result/report 或 stored replay surface 直接携带。不能只在 application result 中保存聚合 counters,再让 entry 通过 repository、adapter state、fake runtime 私有 map 或再次扫描当前 truth 反推 success/failed 明细。

如果 operations job 设计了 `*ReportAssembly` / accumulator,并在其中累计 `view_refs`、`refreshed_reference_refs`、`processed_refs`、`failed_refs`、`report_refs`、`marker_refs` 等逐项 refs,这些字段必须进入最终 public report schema、stored result envelope、typed save/get surface、duplicate replay 表和测试切口。`finish(...)` / `finish_from_counts(...)` 不能丢弃 accumulator 字段;否则实现只能重跑 job body或从 repository 反推 refs,违反 duplicate replay 和 entry/result 明细闭环。

如果 operations maintenance job 的 success / partial path 依赖 target plan、resolver outcome 或 target inspection context,这些中间结果必须有正式 port output schema,不能只写“由 target 选择 / resolver 成功后 / loaded maintenance state 推导”。最低要求:

- projection rebuild target plan 必须返回 writer 所需 typed refs 和 non-empty collection,例如 member summary rebuild 必须返回 complete body-free view inputs;缺失或空集合是 safe issue,不是 default scope / default view。
- resolver 若可能产生 sidecar refs,返回面必须显式包含 `state` 与 optional typed sidecar bundle;service 只能复制 outcome,不得从 returned state、safe summary、source version、adapter error 或 fake private map 推 sidecar。
- reconciliation / report-only inspection 必须有 `target_ref -> typed loaded target context` 正式读取面,context 至少区分 projection/reference/report typed target,并只携带 safe issue/finding refs 与状态 marker。
- target expansion 与 inspection 均不得返回 core truth write target,也不得让 service/fake 解析 opaque target marker、scope string、projection ref、external ref 或 report ref 来补 typed context。
- fake 与 durable 必须实现同一 port output 语义;测试应覆盖 string-like ref、missing plan、empty scope、missing inspection context 不会被 fake 私有 map 补成成功。

正确示例:

```text
RebuildMemberSummaryProjection:
plan = ProjectionRepository.get_member_summary_rebuild_plan(projection_ref)
if plan is missing or plan.projection_ref != projection_ref or plan.view_inputs is empty:
  issue = MaintenanceIssueMapper.projection_missing_rebuild_input_issue(projection_ref)
  mark item failed
else:
  for input in plan.view_inputs:
    view = MemberSummaryView::from_projection(
      input.view_ref,
      input.member_ref,
      input.visibility_scope_ref,
      input.anchor_slice_ref,
      input.lifecycle_slice_ref,
      input.role_capability_slice_refs,
      input.career_slice_refs,
      input.memory_slice_refs,
      input.visibility_result_ref,
      input.read_surface_kind,
      input.source_cursor_ref,
      input.projection_freshness_ref,
      input.read_material_marker
    )
    save_member_summary_view(view)
```

错误示例:

```text
for each formal member summary visibility scope selected by projection target:
  build view
```

错误原因:

- 没有正式 port 返回 view input 列表。
- 没有正式 port 返回保存 view 所需的完整 body-free 字段。
- 实现会被迫从 projection ref、scope、view ref、config、existing view 或 fake map 推 scope / slice / visibility / freshness / material marker。
- durable/fake 很容易出现不同 target selection 或 view assembly 语义。

如果 projection rebuild writer 要保存 read model / view,plan 或 builder output 必须提供目标 view factory 的全部 body-free typed inputs。只给 `projection_ref`、`member_ref`、`visibility_scope_ref` 或“selected by target”不够;只要 service 还需要补 `view_ref`、slice refs、visibility result、read surface、source cursor、freshness marker、material marker 或类似字段,设计就没有闭合。

正确示例:

```text
MemberSummaryProjectionRebuildViewInput {
  view_ref,
  member_ref,
  visibility_scope_ref,
  anchor_slice_ref,
  lifecycle_slice_ref,
  role_capability_slice_refs,
  career_slice_refs,
  memory_slice_refs,
  visibility_result_ref,
  read_surface_kind,
  source_cursor_ref,
  projection_freshness_ref,
  read_material_marker
}
```

错误示例:

```text
get_member_summary_rebuild_plan(...) -> { member_ref, visibility_scope_refs }
service loads existing view or fake map to fill remaining fields
```

如果 reference refresh / external reference maintenance job 的 target selection branch 后续需要调用 `get_reference_state_with_version(reference_ref)`、resolver、`save_reference_state(...)` 或 typed sidecar save,selection port 必须直接返回正式 reference bundle key。若正式 bundle key 是 `ExternalReferenceRef`,owner/kind/stale/scope list 也必须返回 `Page<ExternalReferenceRef>` 或等价 typed target,不能返回 `ReferenceResolutionStateRef` 后让 service/fake 反查。

最低要求:

- Step 7 port signature 明确 selection output type 是 repository 后续 load/save/resolve 所需的 bundle key。
- Step 9 flow 写清每个 selector branch 的输出 key 与后续 load/save/resolve 使用同一个 key。
- Step 11 持久化 / index 表说明 owner/kind/stale/scope index 直接维护 bundle key,不是 state-ref 到 bundle 的隐式反查。
- Step 12/13 写明 selected bundle missing / stale index mismatch 的失败口径,不得用 reverse lookup 修复。
- fake 与 durable 不得通过 sibling store scan、private map、字符串解析、state row 字段猜测或 business source ref 反推出 bundle key。

正确示例:

```text
list_reference_states_by_owner(owner_ref, page) -> Page<ExternalReferenceRef>
for reference_ref in page:
  loaded = get_reference_state_with_version(reference_ref)
  outcome = resolve_external_reference(reference_ref, loaded.reference_owner_ref)
  save_reference_state(outcome.state, loaded.version)
```

错误示例:

```text
list_reference_states_by_owner(owner_ref, page) -> Page<ReferenceResolutionStateRef>
reference_ref = fake_store.find_external_ref_by_state_ref(state_ref)
```

错误原因:

- 后续 flow 需要的是 bundle key,不是 state identity。
- state ref -> bundle key 的读取面未正式定义。
- durable/fake 容易通过字符串、sibling store 或 private map 形成不同语义。
- duplicate replay / failed item report 无法证明当次 selection 的正式 target key。

如果 duplicate 对象是 inbound consumer receipt、command rejection 或其它 public receipt/rejection/report envelope,必须同时定义 typed save 与 typed get surface。例如 `save_consumer_receipt(envelope, uow)` 和 `get_consumer_receipt(result_ref) -> Option<ConsumerReceiptEnvelope>` 必须成对出现。accepted / delayed / rejected / unsupported path 只要产生 public receipt 并进入 idempotency complete,就必须保存完整 replay envelope,而不是只保存 `StoredResultKind`、`result_ref`、trace ref 或最小 placeholder。

错误示例:

```text
Step 9 写 save stored consumer receipt。
Step 7 只有 get_consumer_receipt(result_ref),没有 save_consumer_receipt(...),或只定义 save(StoredResultShell)。
```

错误原因:

- 实现者不知道是否要持久化完整 public receipt body。
- duplicate replay 会被迫临时重建 receipt、重跑 mutation 或从 fake 私有 map 读取。
- typed get 可以读取完整 surface,但没有 typed save 说明首次 accepted path 如何产生同一 surface。

### 5.3.1 entry object 到 operation context 构造面必须闭合

如果 API / worker / job entry object 定义 `to_operation_context(...)`,application helper 必须有对应的正式 factory,并逐字段说明来源和禁止事项。不能只在 entry object 中写“构造 operation context”,却让实现自行增加 `from_inbound_event(...)`、`from_job(...)` 或临时字段。

至少要定义:

- application context factory 名称和签名。
- entry field 到 context field 的映射。
- channel variant。
- idempotency key / dedup key / job key 的归一化来源。
- command/query/job/inbound metadata 哪些必须为 `Some` / `None`。
- trace id、actor、operation name 的来源。
- 禁止用 source event ref、job run id、trace id 或 result id 替代 idempotency key / stored result id 的规则。

正确示例:

```text
GovernanceInboundConsumerEntry::to_operation_context(...)
  -> GovernanceOperationContext::from_inbound_event(operation_name, actor, source_event_ref, dedup_key, core_trace_id)
from_inbound_event 固定 channel=InboundEvent, idempotency_key 由 dedup_key 归一化, command/query/job metadata 均为 None。
```

错误示例:

```text
Worker entry 写 to_operation_context(...): channel 为 InboundEvent。
GovernanceOperationContext 只有 from_command / from_query。
实现时临时增加 from_inbound_event 或直接构造 struct 字段。
```

错误原因:

- implementation boundary 无法判断新增 factory 是合法 repair 还是越界。
- event dedup key、source event ref、trace id、job run id 容易被混用。
- fake runtime、handler 和 service 会形成多个 context 构造真相源。

### 5.4 optimistic version 必须有来源闭环

如果 repository / port / flow 要求 `save(entity, expected_version, uow)` 或等价 optimistic lock 参数,设计不能只写 `expected_version` / `current_version` 变量名。必须说明该 version 从哪里来,并让读取 / 请求 / 创建路径 1:1 可落码。

合法来源只能是:

- public command / job request 中的 `expected_version` 字段,且协议 schema 和字段表已定义。
- 同一 flow 内前置 `create(...) -> Version` 或等价新建返回值。
- repository / port 的带 version 读取函数,例如 `get_with_version(id) -> Option<(Entity, Version)>` 或 `get_by_project_with_version(project_ref) -> Option<(Backlog, Version)>`。

如果 service 内部级联更新另一个 aggregate / truth,不应临时要求 public request 增加内部 aggregate 的 version,除非该 version 本来就是 public command 语义的一部分。更常见的正确做法是为该内部读取补正式带 version 的 repository 函数。

若一个 repository 把 primary mutable state 与多个 typed sidecar snapshot/ref 作为同一个 reference / aggregate bundle 持久化,也可以不为每个 sidecar 定义独立 `get_*_with_version(...)`,但必须明确定义“共用 bundle version”规则:

- 哪个 primary ref 是 bundle key,例如 `ExternalGovernanceReferenceRef`。
- 哪个带 version 的读取面提供 bundle version,例如 `get_reference_state_with_version(reference_ref)` 或 `list_reference_states(...)->Versioned<ReferenceResolutionState>`。
- 哪些 typed sidecar save 复用该 version,例如 `save_method_policy_snapshot(...)`、`save_process_context_ref(...)`。
- `None` 只允许在同一 UoW 内创建 primary state + sidecar;否则 missing primary state 必须 delayed / rejected / failed。
- durable adapter 和 fake adapter 必须执行同一 version conflict 规则。

禁止把 source version、snapshot version、event schema version、dedup key、idempotency digest、timestamp、page cursor、trace id、snapshot ref 字符串或 fake 私有 map 当作 typed sidecar 的 `expected_version`。

如果同一个 flow 同时出现 reference bundle key 与业务 source link / pending marker source,必须显式区分两者:

- `External*ReferenceRef` / `*ReferenceRef` 这类被 repository 明确声明为 reference bundle key 的字段,才可以用于 `get_reference_state_with_version(...)`、typed sidecar `expected_version`、reference marker trace subject 和 affected-view reference lookup。
- `GovernanceSourceRef`、`IdentitySourceRef`、`EventSourceRef` 等业务来源 ref 只表达业务 source link、pending input / nonconformity marker、command source 或 audit source 时,不得自动视为 reference bundle key。
- 若 protocol payload 同时有 `payload.source_ref` 和 envelope / typed sidecar `reference_ref`,必须逐字段写明哪个字段保存 `ReferenceResolutionState`,哪个字段只做 pending marker/source link。
- 若 flow 允许同一事务更新两个不同 reference bundles,必须定义第二个 bundle 的 versioned read、typed sidecar save、affected-view expansion、marker trace subject、transaction ordering 和 conflict mapping。
- 若没有 dual-bundle 规则,实现只能更新一个正式导出的 reference bundle;另一个 source ref 不得保存 reference state,不得复用同一个 expected_version。

如果 reference refresh / maintenance job 要对 `list_reference_states(...)->Versioned<ReferenceResolutionState>` 返回项调用不同 typed resolver,返回项必须携带正式 dispatch target,例如 `GovernanceReferenceRefreshTarget::{ActorCapability, MethodPolicy, MethodControl, EvidenceSummary, ProcessContext, WorkContext, RuntimeSignal, MarkerOnly}` 或等价 typed enum。该 target 必须包含 resolver 所需 typed ref,并随 tracked reference state 持久化、分页返回、进入 digest/test cut。不能只保存 `ExternalGovernanceReferenceRef`、`source_family` 或 resolver family,再由 service/fake/durable adapter 解析字符串、查私有 map、扫描 sibling body 或猜测 resolver 分支。

如果 reference refresh / maintenance job 支持 `GovernanceScope(scope_ref)` 或等价 scope-based expansion,设计必须同时闭合 scope index 写入面,不能只定义 list 语义。最低要求:

- 有正式 row/schema 或 port surface 表达 `scope_ref -> reference_ref` link,并说明 unique key、分页顺序、link source 和 stale row / missing tracked state 的处理。
- 每类 reference family 必须说明 link 的写入、替换和删除时机,以及 scope_ref 的来源。只有当前 flow 已有正式 `GovernanceScopeRef` 时才能写 link;repository/fake 不得从 sidecar body、projection body、truth body、ref 字符串或 private map 推导 scope。
- scope index 必须 join tracked reference state,并校验 `refresh_target` 一致性;index row 不能成为第二套 resolver dispatch source。
- fake adapter 与 durable adapter 必须使用同一个显式 index 语义。测试必须覆盖 sibling body / string-like ref 不会被 `GovernanceScope` list 返回。
- 若某 reference family 没有正式 scope 来源,必须明确它只能通过 explicit refs / unhealthy refs / future boundary refresh,不得把它纳入 scope expansion。

正确示例:

```text
UpdateProjectLifecycle archive path:
BacklogRepository.get_by_project_with_version(project_ref) -> Option<(Backlog, Version)>。
Backlog.archive_with_project(project_ref, actor)。
BacklogRepository.save(backlog, current_backlog_version, uow)。
```

正确示例:

```text
ConsumeMethodPolicyDefinitionChangedFlow:
reference_ref = payload.policy_snapshot.snapshot_state.reference_ref
state_v = ReferenceSnapshotRepository.get_reference_state_with_version(reference_ref)
expected_version = state_v.version
ReferenceSnapshotRepository.save_method_policy_snapshot(payload.policy_snapshot, expected_version, uow)
ReferenceSnapshotRepository.save_reference_state(new_state, expected_version, uow)
```

正确示例:

```text
ConsumeRuntimeSignalRecordedFlow:
reference_ref = payload.runtime_signal_ref.signal_state.reference_ref
assert reference_ref == envelope.source_ref
state_v = ReferenceSnapshotRepository.get_reference_state_with_version(reference_ref)
expected_version = state_v.version
ReferenceSnapshotRepository.save_runtime_signal_ref(payload.runtime_signal_ref, expected_version, uow)
ReferenceSnapshotRepository.save_reference_state(new_state_for(reference_ref), expected_version, uow)
payload.source_ref: GovernanceSourceRef 只进入 pending input marker,不保存 reference state。
```

错误示例:

```text
let backlog = BacklogRepository.get_by_project(project_ref)?;
BacklogRepository.save(backlog, current_backlog_version, uow)?;
```

错误原因:

- `current_backlog_version` 没有正式读取来源。
- repository save 要求 optimistic version,但 trait 只返回 entity。

错误示例:

```text
reference_ref = payload.runtime_signal_ref.signal_state.reference_ref
expected_version = get_reference_state_with_version(reference_ref).version
save_runtime_signal_ref(payload.runtime_signal_ref, expected_version, uow)
save_reference_state(from(payload.source_ref: GovernanceSourceRef), expected_version, uow)
```

错误原因:

- `payload.source_ref` 不是正式 reference bundle key。
- 第二个 reference state 的 version 来源未定义。
- 实现把两个不同 reference bundles 强行复用同一个 expected_version。
- 实现者会被迫自行补 `get_with_version`、把 version 塞进 public request,或绕过 optimistic lock。

推荐默认口径:

```text
CommandResultRepository.save_result(result_ref, StoredCommandResult, &uow)
  必须先于 IdempotencyRepository.complete(reservation, result_ref, &uow)。

IdempotencyRepository.Duplicate(result_ref)
  -> CommandResultRepository.get_result(result_ref)
  -> return stored result with duplicate receipt overlay。

JobResultRepository.save_report(result_ref, StoredJobResult, &uow)
  必须先于 IdempotencyRepository.complete(reservation, result_ref, &uow)。

IdempotencyRepository.Duplicate(result_ref)
  -> JobResultRepository.get_report(result_ref)
  -> return stored job report;若 report 携带 receipt,只 overlay duplicate receipt。
```

错误示例：

```text
IdempotencyRepository.complete(..., result_ref)。
Duplicate(result_ref) => load_duplicate_result(result_ref)。
```

错误原因：

- 没有定义 `load_duplicate_result` 由哪个 port 提供。
- 没有定义 result_ref 指向哪个 stored DTO。
- 实现者只能自行选择“从当前 truth 重算”或“另存完整 result”,会形成第二真相源。

### 5.5 accepted truth / reference marker cursor 必须有来源闭环

如果 object / flow / trace / outbox / projection stale / result surface 要求 `TruthChange.source_cursor`、reference-only stale cursor 或同类 accepted source cursor,设计不能只写 `change.source_cursor` / `current_cursor()`。必须说明 cursor 的正式来源、生成时机、事务可见性、rollback 语义和 fake adapter 等价行为。

合法来源必须明确写入 Step 7 / Step 9 / Step 11,常见可选口径包括:

- `UnitOfWork.assign_truth_change_cursor(...)`: accepted command 已把 changed truth save/stage 到同一 UoW 后,由 UoW / store 分配提交边界 cursor。
- `UnitOfWork.assign_reference_change_cursor(...)`: inbound consumer / reference refresh 已把 reference state 与 typed snapshot/ref save/stage 到同一 UoW 后,由 UoW / store 分配 reference marker 提交 cursor;它只能用于 projection stale、optional marker trace、receipt/report 对齐,不创建 `TruthChange` 或 outbox payload。
- repository `save(...) -> SavedTruth<T>` 或 `save(...) -> (Ref, TruthCursor)`: save path 直接返回 committed/staged cursor。
- committed truth scan cursor: 仅用于 snapshot / projection rebuild / reconciliation 这类 read/job path,不能替代 command write path 的 accepted cursor。

设计必须同时说明:

- validation failure、policy denial、duplicate replay、idempotency conflict 和 rollback path 不分配 accepted truth cursor。
- 如果一个 command 在同一 accepted transaction 内修改多个 truth subject,是每个 subject 一个 cursor,还是一个 command boundary cursor 被多个 `TruthChange` 复用。
- trace、outbox、projection stale、stored result / effect summary 中的 cursor 从同一个 accepted truth change 复制,不得各自生成。
- reference-only consumer / refresh path 若 mark stale,必须从同一个 reference marker cursor 复制到 projection stale 和 optional marker trace;不得把 source version、snapshot version、event dedup key、idempotency digest 或 optimistic version 当 cursor。
- in-memory fake / durable adapter 的 cursor 单调性、稳定性和可断言行为。

正确示例:

```text
context_repo.save(context, expected_version, &uow)。
source_cursor = uow.assign_truth_change_cursor()。
change = GovernanceTruthChange { subject_ref, event_kind, source_cursor }。
trace_repo.append(GovernanceTraceRecord::from_truth_change(trace_id, &change, ...), &uow)。
outbox_repo.append(GovernanceOutboxRecord::from_truth_change(outbox_id, &change, trace_ref), payload_snapshot, &uow)。
projection_repo.mark_stale(affected_views, change.source_cursor, &uow)。
stored_result_repo.save(result.with_source_cursor(change.source_cursor), &uow)。
```

正确示例:

```text
reference_repo.save_reference_state(new_state, expected_version, &uow)。
snapshot_repo.save_actor_capability_snapshot(snapshot, &uow)。
reference_cursor = uow.assign_reference_change_cursor()。
projection_repo.mark_stale(affected_views, reference_cursor, &uow)。
trace_repo.append(GovernanceTraceRecord::from_marker(trace_id, subject, kind, trace_id, Some(reference_cursor)), &uow)。
```

错误示例:

```text
change.source_cursor = page.next_cursor。
change.source_cursor = GovernanceTruthCursor::from(current_version)。
change.source_cursor = GovernanceTruthCursor::from(clock.now())。
change.source_cursor = id_generator.new_truth_cursor()。
reference_cursor = GovernanceTruthCursor::from(source_version_ref)。
reference_cursor = GovernanceTruthCursor::from(event_dedup_key)。
reference_cursor = GovernanceTruthCursor::from(idempotency_digest)。
```

错误原因:

- page cursor 只表示 list 位置,不是 truth commit boundary。
- optimistic version 只保护单个 mutable object,不是跨 trace / outbox / stale 的 source position。
- timestamp、id generator、trace id、event dedup key、idempotency digest 和 hard-coded string 没有证明 truth/reference marker 已保存进同一事务。
- 实现者会被迫自行选择 cursor 来源,导致 trace、outbox、projection stale 和 duplicate result 指向不同真相源。

### 5.5-a idempotency reserve 必须承接 operation context/channel

如果 idempotency record schema 或 factory 声明从 operation context 复制 `channel`、`operation_name`、`idempotency_key` 或 actor/trace metadata,repository reserve surface 必须接收 `OperationContext` 或等价 typed context/channel surface。不能让 Step 6 写 `IdempotencyRecord::reserve(context, digest)`,而 Step 7 port 只接收 `(operation_name, key, digest, uow)`。

设计必须同时说明:

- query 不创建 idempotency record。
- command / inbound event / job 的 channel 来源分别来自正式 operation context factory。
- repository unique key 是否包含 channel,以及 same key across different channel/operation 的 conflict / isolation 语义。
- fake runtime 不得在 reserve 内硬编码 channel 或从 operation name 字符串推断 channel。

正确示例:

```text
context = OperationContext::from_inbound_event(operation_name, actor, event_ref, dedup_key, trace_id)。
reservation = IdempotencyRepository.reserve(&context, request_digest, &uow)。
IdempotencyRecord::reserve(&context, request_digest) 复制 channel / operation_name / idempotency_key。
```

错误示例:

```text
IdempotencyRepository.reserve(operation_name, key, digest, uow)。
IdempotencyRecord::reserve(context, digest)。
fake reserve 根据 operation_name 前缀写 channel = InboundEvent。
```

错误原因:

- object factory 和 repository port 的字段来源不一致。
- inbound consumer / job path 无法 1:1 持久化 channel。
- fake/durable adapter 可能产生不同 duplicate key 空间。

### 5.6 accepted subject identity 必须同源映射

如果 accepted command path 同时构造 `TruthChange.subject_ref`、`TraceRecord.subject_ref`、`AuditTrail.subject_ref`、`OutboxRecord.subject_ref` 或 event envelope subject,设计不能只写一个 mapper trait 名或“从 truth ref 映射”。必须给出:

- mapper / helper 的正式 owner 和函数签名。
- typed truth ref 到 canonical subject key 的完整映射表。
- trace / audit / outbox subject 是否同值;若同值,必须说明它们包装同一个 canonical key;若不同,必须给出各自的 key 表和关系校验规则。
- fake runtime 与 durable adapter 的等价语义,让测试可以断言稳定 subject key。
- 禁止由 service、repository、adapter 或 fake 临时拼接 route path、title、topic、trace id、cursor 或 external body。

正确示例:

```text
GovernanceTruthChangeSubjectMapper.context_subjects(context_ref)
  -> canonical key = "governance:context:<context_id>"
  -> outbox_subject_ref = GovernanceOutboxSubjectRef(key)
  -> trace_subject_ref = GovernanceTraceSubjectRef(key)
  -> audit_subject_ref = GovernanceAuditSubjectRef(key)

change.subject_ref = refs.outbox_subject_ref。
trace = TraceRecord::from_truth_change(..., refs.trace_subject_ref, ...)。
audit = AuditTrail::start_for_subject(..., refs.audit_subject_ref)。
```

错误示例:

```text
trait SubjectMapper {
  fn context_subject(context_ref) -> OutboxSubjectRef;
}

service: OutboxSubjectRef(format!("context:{}", id))。
trace repo: TraceSubjectRef(format!("ctx/{}", id))。
audit repo: AuditSubjectRef(format!("governance-context-{}", id))。
```

错误原因:

- trait 只有形状,没有 canonical key 规则,实现者仍然需要自行选择字符串格式。
- trace / audit / outbox 对同一 accepted truth change 使用不同 subject key,后续 query、handoff、audit append 和 fake 断言无法稳定关联。
- repository 或 fake 自行推导 subject 会形成第二套 identity 真相源。

### 5.7 runtime technical write 与 domain truth write 必须分层

如果 runtime boundary 禁止 domain truth 写事务，但允许技术记录写入，必须明确：

- 是否开启 technical UoW
- technical UoW 覆盖哪些 repository
- 是否拆 runtime repository

错误示例：

```text
Runtime boundary 不开启 SDK domain truth 写事务。
SdkIdempotencyRepository.reserve(...) 又必须带 UnitOfWorkHandle。
flow 中调用 reserve(...) 没有 uow。
```

projection rebuild 只能来自：

- committed domain truth
- committed event / outbox truth
- formally declared artifact replay source
- upstream snapshot truth

projection rebuild 表：

|---|---|---|---|---|

正确示例：

```text
DocsExampleView 从 committed docs evidence artifact replay。
DocsEvidenceArtifactReaderPort.read_examples(evidence_artifact_ref) 返回 example 明细。
```

错误示例：

```text
RebuildSdkProjections 重建 docs example projection。
VerificationEvidence 只存 aggregate fields。
DocsExampleView 明细只在 projection table 中。
```

错误原因：

- truth 不含 projection 明细，无法重建。

## 七、artifact / evidence 标准

### 7.1 需要运行的 artifact 必须可 materialize

如果测试、docs runner、validation runner、package runner 需要实际运行 artifact，设计必须提供 materialization 口径。

可选方式：

- job input 携带 run-scoped artifact root
- artifact metadata 携带 location ref
- artifact store port 提供 resolve / materialize 接口

错误示例：

```text
ValidateDocsExamples 输入 candidate_id + docs_example_set_ref + language_set。
Runner 要运行 candidate artifact。
Artifact metadata 只有 artifact_ref / digest，没有 path / location / materialize port。
```

错误原因：

- runner 无法拿到可执行材料。

### 7.2 artifact / report 路径必须跨文档一致

以下文档中的路径必须一致：

- `04-配置设计.md`
- `05-测试方案.md`
- `06-验收标准.md`
- `07-实施计划.md`
- scripts / gates / reports 契约

正确示例：

```text
gate artifact root: artifacts/test/<run_id>
run report root: reports/runs/<run_id>
acceptance report root: reports/acceptance
```

错误示例：

```text
配置默认 ./artifacts/sdk。
测试方案要求 artifacts/test/<run_id>。
验收标准固定 artifacts/test/<run_id>。
```

### 7.3 report generator 与最终证据必须区分成熟度

如果 report generator / redaction checker / path checker 先于最终送验证据落码,设计必须显式区分以下成熟度:

- script capability: 脚本参数、路径检查、失败摘要和 redaction 初稿能独立运行。
- minimal index shell: 从 run-scoped machine artifact 渲染最小 `evidence-index.md`,只证明 EV / TC / suite / path 链接形态可解析。
- final EV detail pages: 每个 P0 EV 的人类可读明细页已生成并被完整 evidence index 引用。
- acceptance handoff: `reports/acceptance/*` 已生成初稿并由人或 Agent 审查补充。

commit boundary 必须说明当前阶段允许生成哪一层,并明确禁止提前生成哪一层。不得把“最小 evidence index 壳”与“完整 EV 明细页 / 验收结论”混写成同一个输出。

正确示例:

```text
commit-08-a: generate_reports.sh 支持 --run-id,检查 path shape,生成 summary、gate-results、redaction-check 和最小 evidence-index.md 壳。
commit-08-a 不生成最终 EV 明细页,不生成 acceptance 结论。
commit-08-b: 生成完整 evidence-index.md、EV-CONV-*.md、acceptance handoff、veto checklist 和 risk/open issues 初稿。
```

错误示例:

```text
commit-08-a 交付 report generator。
测试方案要求 generate_reports.sh 生成 evidence-index.md。
实施计划又把 evidence index 全部放到 commit-08-b。
```

错误原因:

- 实现者无法判断当前阶段是否必须生成 `reports/runs/<run_id>/evidence-index.md`。
- 脚本能力、索引壳、最终 EV 页面和 acceptance conclusion 混在一起,导致 phase boundary 不可审查。

### 7.4 机器 artifact JSON schema 与 digest 必须闭合

凡是测试方案、验收标准、job entry、gate 或 report writer 要求写入机器可读 artifact,例如:

- `suites/<suite>/report.json`
- `suites/<suite>/cases/<case_id>.json`
- `meta/context.json`
- `meta/source-commits.json`
- `meta/config-digest.json`
- `evidence-index.json`
- `artifacts/<safe_artifact_name>.json`

设计不能只写“必须包含 suite、status、failure reason、duration、artifact digest”等字段清单。必须给出可直接编码的 schema:

- artifact DTO / local DTO owner,以及是否进入 public contracts / application / domain。
- `schema_version` 字段和值。
- 每个 JSON 文件的正式字段名、required/optional、类型和值域。
- status / assertion / review / redaction 等 enum values。
- `artifact_digest_algorithm` 支持值。
- `artifact_digest` 计算对象、格式、canonicalization 规则和自引用字段处理。
- stdout/stderr/log 等非 JSON artifact 是否内嵌 digest,或由哪个 JSON 引用 digest。
- writer owner、reader/report generator owner、failure artifact 保留规则。
- redaction / forbidden body 边界:只能保存 safe refs、safe summaries、redacted diagnostics,不得保存 raw secret、raw external body、stack trace 或 full sensitive ref body。

正确示例:

```text
SuiteReportArtifact {
  schema_version = "governance.artifact.v1",
  run_id,
  suite,
  status: passed|failed|partial|skipped|unavailable,
  case_refs,
  case_digests,
  failure_reason_ref?,
  duration_ms,
  config_profile,
  artifact_digest_algorithm = sha256,
  artifact_digest = sha256(canonical JSON excluding artifact_digest)
}
```

错误示例:

```text
report.json 必须含 suite、case refs、status、failure reason、duration、config profile、artifact digest。
cases/*.json 至少含 TC id、status、assertions、evidence candidate 和 artifact digest。
```

错误原因:

- 实现者必须自行决定 JSON key、enum spelling、optional 字段和 digest 自引用处理。
- 不同 writer / report generator / audit script 会生成互不兼容的 artifact。
- digest 无 canonicalization 时无法稳定复核、duplicate replay 或 evidence audit。
- raw artifact 很容易把 secret、body、stack trace 或 full sensitive ref 当作 diagnostic 输出。

### 7.5 正式 EV 的 tc_refs 必须回指正式 TC

如果 `05-测试方案.md`、`06-验收标准.md` 或 evidence index schema 要求 evidence item 含 `tc_refs` 且类型为 `TC-*`,每个正式 `EV-*` 都必须能回指一个或多个正式测试用例 ID。不得用“all P0 suite pairing”“representative suite”“manual audit”“all blocking suites”等自然语言替代 `tc_refs`。

正确示例:

```text
EV-GOV-REPORT-001:
  suite = report-generation-audit
  tc_refs = [TC-GOV-REPORT-001, TC-GOV-REPORT-002, TC-GOV-REPORT-003, TC-GOV-REPORT-004]
```

错误示例:

```text
EV-GOV-REPORT-001:
  suite = report-generation-audit
  tc_refs = "all P0 suite pairing"
```

错误原因:

- evidence index generator 无法 1:1 生成合法 `tc_refs`。
- acceptance traceability 要求每个 EV item 含 TC 时会出现孤儿证据。
- report audit / no-static-evidence 脚本只能私自发明 TC 或放宽 schema,都会破坏证据闭环。

## 九、开工前复核清单

### 9.1 交付实现前整体审计

在项目正式交给实现 agent 或切换新的 design baseline 前,必须先完成一次整体审计:

| 审计维度 | 通过条件 | 失败处理 |
|---|---|---|
| 切片覆盖 | `07-实施计划.md` 中每个 phase / commit boundary 都被逐一审计 | 补审缺失 boundary |
| 文档范围 | 每个 boundary 至少复核正式 `03/05/06/07` 与必要 `design-calibration` 来源 | 暂停移交,补齐复核范围 |
| 标准覆盖 | 本章适用复核项均有结论,不能只写“遵循标准” | 回到本标准逐项复核 |
| blocker 处理 | 未通过项已回写设计文档并固定新的 design baseline | 不得移交实现 |
| 交付记录 | 审计表记录 boundary、涉及文件/章节、blocker、修复 commit 或 baseline | 补审计记录 |

该审计是交付实现门禁,不是替代实现 agent 在每个 boundary 开工前的复核。整体审计用于提前发现跨文档闭环缺口;开工前复核用于确认当前实现仓基线仍与设计一致。

| record id / 返回面闭环 | append-only history / progression / audit-like record 的 id source、factory 入参、domain method 返回类型和对象可见字段一致 | 暂停，补 id generator / factory 入参或调整返回类型 |
| ref identity 闭环 | 所有 lookup ref 都有正式类型和 key | 暂停，补 ref schema |
| validation truth 闭环 | 每条校验都有 truth source 和 port | 暂停，补 source / port |
| metadata 闭环 | metadata authority 唯一 | 暂停，删除双真相 |
| idempotency 闭环 | key / digest / result_ref / UoW 已定义 | 暂停，补幂等契约 |
| stored receipt typed save/get 闭环 | 当前 boundary 的 duplicate replay surface 若包含 consumer receipt / rejection / report,typed save、typed get、完整 envelope schema、UoW 顺序、missing/wrong-kind 映射均已定义 | 暂停，补 typed save/get surface;不得只用 generic shell 或 placeholder |
| entry context factory 闭环 | 当前 boundary 的 API / worker / job entry 到 application context 有正式 factory、字段映射、channel、key 归一化、metadata Some/None 规则和 fake 等价语义 | 暂停，补 operation context factory 或调整 entry boundary |
| adapter failure outcome 分类闭环 | publisher / handoff / export 等 adapter 结果若驱动 retry、failed、dead-letter、delivered、skipped 等状态分支,port 返回面已有正式 outcome enum 或确定映射表,且 fake/durable 使用同一分类 | 暂停，补 adapter outcome enum / 映射表 / flow 分支;不得让 service/fake 解析错误字符串或异常类型 |
| projection rebuild 闭环 | projection 有 committed truth source | 暂停，调整 rebuild set 或补 truth |
| public read-model identity | read model / projection / cursor id/ref 有 schema、repository key 和派生规则 | 暂停，补 public ref schema |
| artifact materialization | runner 可解析 artifact location | 暂停，补 location / materialize |
| machine artifact JSON schema | 当前 boundary 会写入或读取机器 JSON artifact 时,字段名、required/optional、enum、schema_version、digest algorithm/canonicalization、writer/reader owner 和 redaction 边界已定义 | 暂停，补 raw artifact schema;不得只凭字段清单实现 writer |
| phase boundary | 不引用后续 phase 对象 / 结果 / 证据;预列未来状态 / 方法已明确 reserved 且当前测试门禁只覆盖非 reserved 子集 | 暂停，调整 phase 或补 reserved 标记 |
| path baseline | config / test / acceptance / scripts 路径一致 | 暂停，统一路径 |
| blocker 经验回写 | 本 boundary 曾暴露的新型 blocker 已检查本标准;未覆盖的规则已补充标准、正反例、复核清单,并横向扫描同类设计面 | 暂停，先完成标准回写或记录无需回写的理由 |

失败处理原则：

```text
实现者不得在代码中自行补字段、自行选择状态名、自行改 phase scope 或自行发明 truth source。
发现设计真相源冲突时，必须暂停当前 boundary，回写设计仓，再基于新 design commit 继续。
```

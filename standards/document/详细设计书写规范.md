# 详细设计书写规范

> 详细设计回答 **"具体怎么做"**。
> 它是设计文档漏斗的下层——展开实现，直接指导编码。
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)
> 架构图绘制方法见 → [设计文档编写通则](设计文档编写通则.md) 第二章

---

## 一、详细设计的目标

详细设计的核心目标是**让开发者能够不看代码就能完成编码**。为此，它要解决五个核心问题：

1. **代码骨架**：目录结构怎么组织、源文件怎么划分
2. **数据结构**：每个结构体怎么定义、每个成员变量做什么
3. **接口契约**：每个模块对外暴露什么、依赖什么
4. **实现逻辑**：关键函数内部怎么走、伪代码怎么写
5. **流程与异常**：正常流程怎么走、异常怎么处理、边界条件

> **详细设计的终极检验标准**：一个没有参与过该项目的开发者，仅凭概要设计 + 详细设计，能否直接编写出与设计意图一致的代码？如果不能，说明详细设计还不够细。

## 四、各模块编写要点

### 4.1 文档元信息与数据来源声明

**必须附加"数据来源声明"**，明确声明本文档中的结构体字段、函数签名等信息的来源（如"均从 `Order.java` 提取"），确保文档与代码的一致性有可追溯的基线。

**编写要点**：
- 数据来源声明是详细设计独有的，概要设计不需要
- 声明的方式：写明源文件路径，并注明"如代码发生变更，本文档须同步更新"

### 4.2 代码目录结构

**编写要点**：
- 目录树必须标注每个文件/包的职责（一句话）
- 标注文件与模块的映射关系（哪个文件属于哪个逻辑模块）
- 目录结构应反映架构分层——读者从目录就能看出模块边界

**示例格式**：

```
order-domain/src/main/java/com/example/order/
│
├── domain/
│   ├── Order.java              # 订单聚合根，核心业务逻辑
│   ├── OrderItem.java          # 订单行项值对象
│   └── OrderStatus.java        # 订单状态枚举
│
├── application/
│   ├── OrderAppService.java    # 应用服务：编排创建订单流程
│   └── CreateOrderCmd.java     # 创建订单命令
│
├── infra/
│   ├── OrderRepoImpl.java      # 仓储实现：DB 读写
│   └── StockProxyImpl.java     # 库存服务调用适配
│
└── api/
    └── OrderController.java    # REST 入口
```

### 4.3 结构体定义

**编写要点**：
- 每个核心结构体必须定义，每个成员变量必须有作用说明
- 字段必须标注默认值、有效范围、约束
- 结构体间引用/组合关系必须标注
- 涉及异步资源的数据结构必须附生命周期图

**理论深度**：

结构体定义不是简单的字段罗列，它是**数据模型的精确契约**。每个字段都应回答三个问题：
1. **是什么**：类型和语义
2. **约束是什么**：有效范围、默认值、是否可空
3. **为什么需要**：在业务流程中的角色

**示例格式**：

```java
public class Order {
    String      orderId;       // 订单唯一ID，格式: ORD + 时间戳 + 4位随机数
    String      userId;        // 下单用户ID，关联用户服务
    OrderStatus status;        // 订单当前状态，参见 OrderStatus 枚举
    List<OrderItem> items;     // 订单行项列表，1~50 个
    long        totalAmount;   // 订单总金额（分），由领域服务计算
    long        discountAmount;// 优惠金额（分），初始0，使用优惠券后更新
    int         version;       // 乐观锁版本号，每次更新 +1，防并发修改
}
```

### 4.4 接口定义

**编写要点**：
- API 签名必须完整：方法 / 路径 / 入参 / 出参
- 返回值使用**三值语义**：0=成功 / 1=可恢复异常 / -1=不可恢复异常
- 关键 API 必须写前置条件（Precondition）和后置条件（Postcondition）——这是契约式设计（DbC）的核心
- 错误码要分类：可恢复 vs 不可恢复，让调用方知道是否该重试

**理论深度**：

接口定义的终极目标是**消除歧义**。自然语言描述"创建订单"可能有多种理解——接口契约通过前置/后置条件精确约束行为边界：
- **前置条件**：调用方必须保证的条件（如 `cmd != null && cmd.getItems().size() > 0`）
- **后置条件**：被调用方保证的结果（如"成功时 Order 状态为 CREATED，失败时无副作用"）
- **副作用**：接口调用对外部产生的影响（如"写入订单记录、扣减库存、发送领域事件"）

**示例格式**：

```
POST /api/v1/orders

Request:
  user_id:    string, 必填, 用户ID
  items:      array,  必填, 1~50 项
  address_id: string, 必填, 收货地址ID
  coupon_id:  string, 可选, 优惠券ID

Response (200):
  order_id:     string, 订单号
  status:       "CREATED"
  total_amount: integer, 总金额（分）

Error Codes:
  ORDER_001  库存不足       （可恢复：稍后重试或更换商品）
  ORDER_002  优惠券不可用   （可恢复：去掉优惠券重试）
  ORDER_003  地址不存在     （不可恢复：数据不一致）
```

### 4.5 关键函数伪代码

**编写要点**：
- 用自然语言 + 代码混合写，不需要严格语法正确，但逻辑必须精确
- 每个分支都要写清楚走向（包括 return / throw / continue）
- try-catch 的补偿逻辑必须写出来
- 标注关键性能路径（如 RPC 调用、批量查询）
- 状态转换函数应列出完整的合法转换矩阵

**理论深度**：

伪代码是详细设计的**核心交付物**——它直接决定了开发者能否"照着写就能编码"。伪代码粒度的判断标准：

| 粒度 | 判断标准 | 是否合格 |
|------|---------|---------|
| 过粗 | 只写了函数名和一句话描述 | ✗ 开发者需要自己设计逻辑 |
| 适中 | 写了完整的控制流、分支、异常处理 | ✓ 开发者可直接翻译 |
| 过细 | 写了具体语言语法、库调用 | ✗ 绑定实现语言，丧失灵活性 |

**示例格式**：

```
function createOrder(cmd):
    // 前置检查
    if cmd.items.isEmpty() then throw INVALID_ARGUMENT
    if cmd.items.size() > 50 then throw INVALID_ARGUMENT

    // 幂等检查（请求指纹去重）
    existing = idempotentRepo.findByFingerprint(cmd.fingerprint)
    if existing != null then return existing.orderId

    // 库存预扣（外部调用，需补偿）
    try:
        stockResult = stockProxy.batchDeduct(cmd.items)  // [RPC] 性能敏感
    catch TimeoutException:
        throw STOCK_SERVICE_UNAVAILABLE  // 可恢复异常
    if !stockResult.success then throw STOCK_INSUFFICIENT

    // 构建订单聚合根
    order = Order.create(cmd.userId, cmd.items, cmd.addressId)
    order.applyCoupon(cmd.couponId)  // 可选步骤，失败不影响主流程

    // 持久化（乐观锁）
    orderRepo.save(order)  // version=0 首次插入，无需乐观锁

    // 发布领域事件（最终一致性）
    eventBus.publish(OrderCreatedEvent(order))

    return order.orderId
```

> **要点**：每个分支都有明确的走向（throw / return / try-catch），外部调用标注了 `[RPC]`，异常处理标注了可恢复性，开发者可以直接翻译为正式代码。

### 4.6 数据设计

**编写要点**：
- 数据表必须提供完整 DDL（含索引、约束、分区策略），不应只画 ER 图
- 缓存设计必须包含：Key 格式 / Value 结构 / TTL / 击穿防护策略
- 每张表必须声明数据所有权（谁写谁读），遵循 Single Writer 原则
- 数据生命周期（创建/变更/归档/删除）必须描述

**理论深度**：

数据设计是详细设计中**最容易被低估**的模块。常见错误是只画 ER 图不写 DDL——ER 图表达的是逻辑关系，DDL 表达的是物理实现，两者之间有巨大的鸿沟（索引策略、分区策略、约束实现等）。

**缓存设计的理论框架**：
1. **Cache-Aside**：读时回填，写时失效——最通用
2. **Write-Through**：写时同步更新缓存——强一致但延迟高
3. **Write-Behind**：写时异步更新缓存——高吞吐但可能丢数据
4. 击穿防护的两种策略：SETNX 互斥锁 / 逻辑过期

**数据所有权声明的理论依据**：

每张表有且仅有一个写入方（Single Writer 原则），这是微服务数据自治的基石。违反此原则会导致：
- 数据竞争：多方写入导致不一致
- 部署耦合：写同一张表的服务无法独立发布
- 事故扩散：一个服务的 Bug 可能污染另一服务的数据

**示例格式**：

DDL 示例：

```sql
CREATE TABLE `t_order` (
    `id`             BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT COMMENT '主键',
    `order_id`       VARCHAR(32)      NOT NULL COMMENT '订单号，格式: ORD+时间戳+4位随机',
    `user_id`        VARCHAR(32)      NOT NULL COMMENT '用户ID',
    `status`         TINYINT          NOT NULL DEFAULT 0 COMMENT '状态: 0=CREATED, 10=PAID, 20=SHIPPED, 30=COMPLETED, -10=CANCELLED',
    `total_amount`   BIGINT           NOT NULL DEFAULT 0 COMMENT '总金额（分）',
    `discount_amount` BIGINT          NOT NULL DEFAULT 0 COMMENT '优惠金额（分）',
    `version`        INT              NOT NULL DEFAULT 0 COMMENT '乐观锁版本号',
    `created_at`     DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at`     DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_order_id` (`order_id`),
    KEY `idx_user_id_status` (`user_id`, `status`),
    KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单主表'
PARTITION BY RANGE (TO_DAYS(`created_at`)) (
    PARTITION p202501 VALUES LESS THAN (TO_DAYS('2025-02-01')),  -- 按月分区，便于归档
    PARTITION p202502 VALUES LESS THAN (TO_DAYS('2025-03-01')),  -- 提前建好未来分区
    PARTITION pmax   VALUES LESS THAN MAXVALUE
);
```

缓存 Key 设计示例：

| Key 模式 | Value 结构 | TTL | 击穿防护 | 说明 |
|---------|-----------|-----|---------|------|
| `order:{orderId}` | Order JSON | 30min | SETNX 互斥锁 | 单订单查询 |
| `user_orders:{userId}:{page}` | OrderId 列表 | 5min | 逻辑过期 | 用户订单列表 |
| `order_stock_reserved:{orderId}` | reservedItems JSON | 15min | 无（短 TTL） | 库存预扣记录 |

> **击穿防护选择依据**：订单详情是热点读场景，用 SETNX 互斥锁保证只回填一次；列表页容忍短暂脏读，用逻辑过期降低延迟；预扣记录 TTL 短且写入后很少再读，无需击穿防护。

数据所有权声明示例：

| 表名 | 写入方 | 读取方 | 说明 |
|------|--------|--------|------|
| t_order | OrderService | OrderService, ReportService | OrderService 独占写入 |
| t_order_item | OrderService | OrderService, ReportService | 随主表一同写入 |
| t_order_log | OrderService | OrderService, AuditService | 审计日志只追加不改 |
| t_stock | StockService | OrderService（RPC） | **跨服务读取走 RPC，不直连 DB** |

> **关键原则**：如果读取方和写入方属于不同服务，读取方必须通过 RPC 调用，不能直连对方数据库。跨服务直连 DB 是微服务架构的反模式。

**状态机转换矩阵示例**：

以订单状态机为例，合法转换用 ✓ 标注，非法转换标注处理策略：

| 从 \ 到 | CREATED | PAID | SHIPPED | COMPLETED | CANCELLED |
|---------|---------|------|---------|-----------|-----------|
| CREATED | — | ✓ 支付成功 | ✗ 未支付不可发货 | ✗ | ✓ 主动取消 / 超时取消 |
| PAID    | ✗ | — | ✓ 发货 | ✗ | ✓ 退款后取消 |
| SHIPPED | ✗ | ✗ | — | ✓ 确认收货 | ✗ 已发货不可取消 |
| COMPLETED | ✗ | ✗ | ✗ | — | ✗ 终态 |
| CANCELLED | ✗ | ✗ | ✗ | ✗ | — 终态 |

非法转换处理策略：
- **未支付不可发货**：在 `ship()` 方法前置条件检查 `status == PAID`，不满足则抛出 `ILLEGAL_STATE_TRANSITION`
- **已发货不可取消**：前端隐藏取消按钮，后端 `cancel()` 方法检查 `status in [CREATED, PAID]`
- **终态不可变更**：所有状态变更方法前置检查 `status not in [COMPLETED, CANCELLED]`

> **要点**：转换矩阵的价值不在于列出合法转换（这是显然的），而在于**明确定义每个非法转换的处理策略**——忽略非法转换 = 在运行时暴露 Bug。

### 4.8 异常处理与容错

**编写要点**：
- 异常分类为三层：可恢复（重试/降级） / 不可恢复（快速失败+告警） / 需补偿（回滚+修复）
- 幂等设计三要素缺一不可：幂等键 + 幂等窗口 + 实现方式
- 补偿逻辑必须写出：哪一步失败后做什么回退

**理论深度**：

异常处理的本质是**降低不确定性**。每个可能失败的步骤都需要回答：
1. **失败后状态是什么**：是原地不动、还是部分变更了？
2. **如何恢复**：重试 / 降级 / 补偿 / 人工介入？
3. **恢复的代价**：是否需要人工介入？恢复需要多长时间？

**幂等设计的理论框架**：

| 策略 | 实现方式 | 适用场景 | 局限 |
|------|---------|---------|------|
| 请求指纹去重 | Redis SETNX + TTL | 创建类操作 | TTL 内的重复请求 |
| 唯一业务键 | 数据库唯一约束 | 创建类操作 | 需要自然键 |
| 乐观锁 | version 字段 | 更新类操作 | 需要先读再写 |
| 状态机守卫 | 前置状态检查 | 状态变更操作 | 仅限状态机场景 |

**幂等方案示例**：

以"创建订单"场景为例，采用请求指纹去重策略：

```
幂等键设计：
  fingerprint = MD5(userId + itemsHash + addressId + couponId)
  Redis Key  = idempotent:order:{fingerprint}
  TTL         = 24h（幂等窗口）

实现逻辑：
  1. 生成 fingerprint
  2. SETNX idempotent:order:{fingerprint} "" EX 86400
     - 如果 SETNX 返回 0（key 已存在），查询并返回已有订单
     - 如果 SETNX 返回 1（key 不存在），继续创建订单
  3. 创建成功后，更新 Redis value 为 orderId
  4. 创建失败后，删除 Redis key（允许重试）
```

**补偿逻辑示例**：

以"创建订单"流程中的部分失败场景为例：

| 步骤 | 失败场景 | 失败后状态 | 补偿动作 |
|------|---------|-----------|----------|
| 1. 库存预扣 | RPC 超时 | 未知（可能成功） | 查询库存服务确认：成功则继续，失败则重试一次，仍失败则终止 |
| 2. 优惠券锁定 | 优惠券服务不可用 | 订单已创建但无优惠 | 降级：无优惠继续创建，异步补偿锁定优惠券 |
| 3. 订单入库 | DB 死锁 | 订单未持久化 | 乐观锁重试（3 次），仍失败则回滚库存预扣 |
| 4. 发送事件 | MQ 发送失败 | 订单已持久化 | 本地消息表记录，定时任务重试发送 |

> **要点**：每个失败场景都必须回答三个问题——失败后状态是什么？如何恢复？恢复的代价是什么？"未知"状态是最危险的，必须有查询确认机制。

### 4.9 并发与一致性

**编写要点**：
- 逐一分析竞态场景：哪些路径会并发读写同一资源
- 明确并发控制策略：锁 / CAS / 队列 / 版本号
- 声明事务边界与隔离级别
- 声明模型之外的例外分析（如"Java memory model 下 Order.status 无需 volatile，因为所有读写都经过 DB"）

**理论深度**：

并发分析的核心方法是**识别共享可变状态**——每个被多个线程/进程同时访问的可变数据，都是潜在的竞态点。分析框架：

1. **识别共享状态**：哪些数据会被并发读写？
2. **分类竞态类型**：读-写竞态 / 写-写竞态 / 复合操作竞态
3. **选择控制策略**：乐观（CAS/版本号） vs 悲观（锁）
4. **声明一致性模型**：强一致 / 最终一致 / 因果一致
5. **例外分析**：哪些场景绕过了模型，为什么安全？

**竞态分析表示例**：

以订单系统为例，逐一识别竞态场景：

| 竞态场景 | 共享资源 | 竞态类型 | 控制策略 | 一致性模型 |
|---------|---------|---------|---------|-----------|
| 同一用户同时下两单 | 库存 | 写-写（扣减同一 SKU） | DB 行锁 `SELECT ... FOR UPDATE` | 强一致 |
| 支付回调与取消请求并发 | Order.status | 写-写（状态转换） | 乐观锁（version 字段） | 强一致 |
| 多个订单同时扣同一 SKU 库存 | Stock.available | 写-写 | `UPDATE stock SET available = available - ? WHERE sku = ? AND available >= ?` | 强一致（CAS） |
| 订单列表缓存与订单状态变更 | Redis 缓存 | 读-写 | Cache-Aside：写时删缓存 | 最终一致 |
| 超时关单定时任务与用户支付 | Order.status | 写-写 | 乐观锁 + 状态守卫 | 强一致 |

> **分析要点**：
> - 每个竞态场景都必须明确**共享资源是什么**——没有共享就没有竞态
> - **读-写竞态**通常用缓存失效或版本号解决；**写-写竞态**必须用锁或 CAS
> - 例外声明：`Order.items` 在创建后不可修改（immutable），因此无需考虑并发修改

事务边界示例：

```
创建订单事务边界：
  BEGIN
    INSERT t_order        -- 订单主表
    INSERT t_order_item   -- 订单行项（批量）
    UPDATE t_stock SET available = available - ?  -- 库存扣减
  COMMIT

  -- 事务外（最终一致性）
  INSERT t_order_log     -- 操作日志（允许延迟）
  PUBLISH OrderCreatedEvent  -- 领域事件（允许延迟）

隔离级别：READ_COMMITTED
  理由：订单创建无幻读风险，REPEATABLE_READ 的间隙锁在高并发下导致死锁
```

### 4.10 框架集成与代码骨架

**编写要点**：
- 依赖注入/组件注册方式必须明确：哪些用构造器注入、哪些用配置类注册
- 中间件/拦截器注册方式必须写明：拦截器的顺序、作用范围
- 配置加载与绑定方式必须标注：@Value / @ConfigurationProperties / 配置中心
- 提供可直接复制粘贴的类骨架模板——这是"照着写就能编码"的直接支撑

**理论深度**：

框架集成是详细设计中**连接设计与实现的关键桥梁**。没有这部分，开发者拿到设计文档后还需要自己决定：
- Bean 怎么注册？构造器注入还是字段注入？
- 中间件怎么配置？顺序是什么？
- 配置项怎么绑定？从哪读取？

这些决策看似简单，但在团队协作中，不一致的做法会导致：
- 代码风格不统一——A 用 @Autowired，B 用构造器注入
- 注册遗漏——某个 Bean 没有被注册到容器中
- 配置散落——同类型的配置分散在不同地方

类骨架模板的价值不在于"复制粘贴"，而在于**统一编码范式**——它定义了"这个团队的代码长什么样"。

**依赖注入示例**：

```java

```

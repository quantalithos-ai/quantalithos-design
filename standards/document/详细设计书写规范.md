# 详细设计书写规范

> 详细设计回答 **“如何把概要设计中已经收稳的代码主体骨架，展开为可以 1:1 实现的代码实现契约”**。
> 它位于概要设计与实施计划之间，负责定义模块、文件、对象、函数、协议、状态、事务、错误和测试切口的实现级约束。
> 详细设计不是概要设计的重复，也不是实施计划、测试方案、部署运维手册或配置手册。

## 一、详细设计的目标

详细设计要解决的问题包括：

1. 当前仓的实现单元、文件布局和模块边界如何落地
2. 每个模块包含哪些对象、trait、adapter、错误类型和测试切口
3. 每个 struct / enum / value object / service / trait 的字段、函数和约束如何定义
4. 每个 API / Command / Query / Event / Operations Job 的协议契约如何定义
5. 每个关键接口的函数级数据流、事务边界、错误分支和状态变化如何发生
6. 哪些状态机、持久化、一致性、并发、幂等和审计规则必须被代码实现遵守
7. 详细设计如何交付给实施计划，使实现者可以按文档还原代码

详细设计不回答：

```text
重新定义需求目标、用户故事、功能需求或验收标准
重新定义系统上下文、限界上下文、方案取舍或架构级技术选型
重新组织概要设计中的主要组成部分和代码主体骨架
编写开发排期、任务拆分、每日实施顺序
编写完整测试方案、部署运维手册、配置手册或应急处置手册
```

详细设计的完成标准是：

```text
其他 agent 可以仅凭已收稳的概要设计 + 详细设计，
在目标仓中按模块、文件、对象、函数、协议和测试切口实现出与设计意图一致的代码。
```

## 二、详细设计与上游 / 下游文档的边界

### 2.1 相对需求文档

详细设计承接需求文档中已经稳定的功能边界、非功能约束和验收方向，但不重写：

- 目标与非目标
- 用户故事
- 功能需求
- 数据需求
- 验收标准

### 2.2 相对架构设计

详细设计承接架构设计中已经稳定的系统边界、依赖方向、通信方式、数据所有权和技术取舍，但不重写：

- 系统上下文
- 限界上下文与子域划分
- 容器 / 部署架构
- 架构方案取舍
- ADR 结论

### 2.3 相对概要设计

详细设计必须以概要设计为直接输入。

概要设计提供：

- 代码主体框架
- 主要组成部分、职责与边界
- 关键对象轮廓
- API / 接口骨架
- 关键处理流 / 重要函数数据流
- 状态定义与状态流转轮廓
- 详细设计承接清单

详细设计继续展开：

- 文件路径、模块路径和 crate / package 布局
- 完整对象实现契约
- 完整函数签名、参数类型、返回类型和副作用
- trait / port / adapter 契约
- 请求 / 响应 / event / command / query / job schema
- 函数级调用链、事务边界和错误映射
- 状态机转换矩阵、非法转换处理和恢复口径
- 持久化、索引、事务、一致性、并发和幂等实现约束

### 2.4 相对实施计划、测试方案、配置设计和运维手册

详细设计只写实现契约，不替代其他下游文档。

| 下游文档 | 详细设计中允许写 | 详细设计中禁止写 |
|---|---|---|
| 实施计划 | 实现前置阅读、实现单元依赖、承接清单 | 开发排期、每日任务、提交计划 |
| 测试方案 | 每个模块 / 接口的测试切口和最小验证清单 | 完整测试策略、覆盖率计划、测试排期 |
| 配置设计 | 代码需要读取的配置项名称、类型和绑定点 | 完整配置手册、环境矩阵、部署参数全集 |
| 部署与运维手册 | 代码埋点、日志、审计和健康检查切口 | 部署拓扑、告警阈值、故障处置流程 |

## 三、详细设计的章节主链

正式文档建议使用以下章节顺序：

```text
1. 与上游文档的关系声明
2. 本次详细设计目标与范围
3. 实现约束与编码规范承接
4. 实现单元与文件布局
5. 模块实现契约
6. 全局对象 / Trait / API 索引
7. API / Command / Query / Event / Job 协议契约
8. 逐接口函数级处理流
9. 状态机与转换矩阵
10. 数据持久化、事务与一致性契约
11. 错误模型、异常分支与恢复口径
12. 并发、幂等与重入保护
13. 配置引用与外部依赖绑定
14. 可观测性与审计埋点契约
15. 测试切口与最小验证清单
16. 详细设计到实施计划的承接清单
17. 风险与待确认事项
18. 参考
```

### 3.1 主组织轴

详细设计的主组织轴是 **模块实现契约**。

```text
正确组织方式：
  按模块 / crate / package / 文件组展开
  每个模块内部定义对象、trait、函数、错误、持久化和测试切口

错误组织方式：
  把所有 struct 集中堆到一个章节
  把所有 trait 集中堆到一个章节
  把所有函数集中堆到一个章节
  让实现者在多个全局章节之间来回拼装同一个模块
```

因此，第 5 章必须是全文核心；第 6 章只是全局索引，不能替代模块内实现契约。

### 3.2 第 5 章与第 6 章的边界

```text
第 5 章：按“模块”组织
  说明每个模块的文件、对象、函数、trait、错误和测试切口如何实现。

第 6 章：按“索引”组织
  汇总全文对象、trait、API、事件和 job 的定义位置，帮助查找，不承载正文设计。
```

### 3.3 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式详细设计时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/03_ddd_step_05_module_contracts.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章详细设计结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的实现契约。

## 四、通用输出规则

### 4.1 表 / 图 / 代码块使用规则

详细设计线整体采用：

- 表格收稳契约
- 代码块表达 Rust 签名、结构体、enum、trait 和 schema
- ASCII 图表达调用关系、状态流和模块交互
- 短文解释边界和取舍

其中：

- 表格必须有稳定列名，不能退化成自由 checklist。
- Rust 代码块必须使用 `rust` 代码块。
- JSON 示例必须使用 `json` 代码块。
- Proto 示例必须使用 `proto` 代码块。
- ASCII 图必须使用 `text` 代码块。
- 详细设计中的 Rust 代码片段是实现契约，不是随意示例；字段、函数和注释必须可以被实现者直接采用或逐项翻译。

### 4.2 ASCII 图统一格式

所有 ASCII 图必须采用以下结构：

````md
#### <图类型>: <图标题>

```text
<ASCII 图正文>
```

关键说明：
- <图表达了什么结构关系>
- <图没有表达哪些下游细节>
- <图中最容易误解的边界是什么>
````

ASCII 图写法约束：

- 只使用稳定文本字符：`+ - | / \ > < v ^ [ ] ( ) : .`
- 不使用 Mermaid、PlantUML、Graphviz 或截图
- 图中节点名必须与正文中的模块名、对象名、函数名或接口名一致
- 箭头旁必须标注交互类型，例如 `call`、`event`、`query`、`tx`、`append`
- 图后必须有 2~5 条关键说明
- 图不能承载完整字段、完整 schema、完整 DDL 或完整伪代码

### 4.3 Rustdoc 注释规则

对象、字段、enum、enum variant、trait 和公开函数必须使用 Rustdoc 风格中文注释。

结构体写法：

```rust
/// 平台级成员聚合根，维护成员身份真相与生命周期不变量。
pub struct GlobalMember {
    /// 平台级成员唯一标识。
    pub global_member_id: GlobalMemberId,

    /// 当前生命周期状态，决定成员是否允许被分配到项目。
    pub lifecycle: GlobalMemberLifecycle,
}
```

枚举写法：

```rust
/// 成员生命周期状态集合。
///
/// 该枚举只表达状态值本身;合法迁移必须由生命周期对象或领域函数控制。
pub enum GlobalMemberLifecycle {
    /// 新雇佣但尚未进入项目工作的成员。
    Hired,

    /// 可被分配到项目并参与工作的活跃成员。
    Active,

    /// 暂停参与项目,不可被自动分配新任务。
    Paused,

    /// 已退役成员,仅保留历史追溯。
    Retired,
}
```

enum 注释要求：

- enum 本身必须说明它表达的状态 / 分类 / 错误集合的边界。
- 每个 enum variant 必须单独写 Rustdoc 注释，说明该取值的业务语义和使用场景。
- 带载荷的 variant 必须说明载荷类型承载什么错误、数据或上下文。
- 状态类 enum 的迁移规则不得只写在注释里，必须另有状态转换表或领域函数约束。

函数签名写法：

```rust
impl GlobalMember {
    /// 激活处于 hired 或 paused 状态的成员。
    pub fn activate(&mut self, actor: ActorRef) -> Result<(), IdentityError>;
}
```

写法约束：

- 结构体注释必须说明“这个对象代表什么、维护什么不变量”。
- 字段注释必须说明“字段的业务含义、约束或使用位置”。
- 函数注释必须说明“函数做什么、改变什么、不改变什么”。
- 参数必须写类型，禁止只写 `activate(actor, reason)` 这类裸参数。
- 如果使用伪代码调用，必须写成 `对象.函数(Type 参数名)` 或 `Type::函数(Type 参数名)`。

### 4.4 函数调用注释规则

关键处理流中的伪代码必须标明调用对象、函数、参数类型和用途。

推荐写法：

```rust
// [UnitOfWork.begin()]
// 开启本次命令处理的事务边界。
let tx = unit_of_work.begin().await?;

// [GlobalMemberRepository.get_for_update(GlobalMemberId member_id)]
// 以写锁读取成员聚合，防止生命周期并发更新。
let member = repository.get_for_update(command.global_member_id).await?;

// [GlobalMember.activate(ActorRef actor)]
// 在领域对象内部校验生命周期转换并修改状态。
member.activate(actor)?;
```

禁止写法：

```text
调用仓储读取成员
更新状态
保存
```

错误原因：

```text
没有对象、函数、参数类型和调用用途，实现者无法 1:1 还原调用链。
```

### 4.5 正式章节必须保留校准来源入口

整理正式详细设计时，每个正式章节开头必须回答：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~18。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/03_ddd_step_05_module_contracts.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/03_ddd_step_05_module_contracts.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解模块实现契约如何从概要设计骨架收敛到可 1:1 实现的代码契约。
```

### 4.6 对象、协议、流程和状态闭环规则

详细设计必须证明每个核心对象、协议输入、处理流和状态机可以互相回指。不能只让单章看起来完整，而在组合实现时缺字段、缺状态、缺构造规则或 phase 边界。

本节所有复核项必须遵守 `standards/document/设计真相源闭环与可落码性标准.md`。若本规范中的表格与该标准存在口径差异，以该标准为准；本规范只定义详细设计中的落文位置和表格承载方式。

必须至少完成以下复核：

| 复核项 | 必须回答的问题 | 落点 |
|---|---|---|
| 字段闭环 | Domain 对象的每个必填字段来自哪里，缺失时怎么处理 | §5 / §7 / §8 / §15 |
| DTO 构造闭环 | 每个 Command / Event / Job 是否能完整构造目标对象 | §7 / §8 |
| Query response 闭环 | 每个 Query 的 response view / page / marker 是否有字段 schema、来源和 empty / visibility / degraded surface | §7 / §8 / §10 |
| 状态闭环 | enum 变体、状态图、转换矩阵、测试和验收是否使用同一套正式状态名 | §5 / §9 / §15 |
| 处理流闭环 | 伪代码中的函数是否能回指对象、trait、repository 和协议契约 | §5 / §7 / §8 |
| Phase boundary 闭环 | 当前实现阶段是否引用了后续阶段才定义的对象、结果或测试证据 | §16 / 实施计划 |
| 命名一致性 | 字段、函数、状态、用例、证据是否存在旧名、口语名或别名漂移 | 全文 |
| Metadata / Idempotency 闭环 | metadata authority、request digest、result_ref 和 UoW 是否唯一且可实现 | §7 / §8 / §10 / §12 |
| Projection rebuild 闭环 | 每个 projection 是否声明 committed truth source 或 artifact replay source | §5 / §10 / §16 |
| Artifact materialization 闭环 | runner / validator 是否能解析 artifact location 或 materialize artifact | §7 / §10 / §13 |

字段闭环表格式：

| Domain 对象 | 字段 | 类型 | 字段来源 | 构造入口 | DTO / Event 字段 | 缺失处理 | 测试覆盖 |
|---|---|---|---|---|---|---|---|

DTO 到 Domain 构造闭环表格式：

| 输入契约 | 目标 Domain 对象 | 必填字段是否齐全 | 派生字段来源 | 不得混同的字段 | 缺失时行为 | 关联处理流 |
|---|---|---|---|---|---|---|

Query response / view 闭环表格式：

| Query | Response DTO / View | 字段 | 类型 | 字段来源 | empty / not visible / degraded 口径 | 测试覆盖 |
|---|---|---|---|---|---|---|

状态闭环表格式：

| 状态枚举 | 正式状态值 | 产生函数 | 合法迁移 | 禁止迁移 | 测试切口 | 验收引用 |
|---|---|---|---|---|---|---|

正确示例：

```md
| 输入契约 | 目标 Domain 对象 | 必填字段是否齐全 | 派生字段来源 | 不得混同的字段 | 缺失时行为 | 关联处理流 |
|---|---|---|---|---|---|---|
| CommittedOutboxFactInput | PublicationMaterial | 是 | core_event_ref 来自 envelope metadata 解析 | core_event_ref != core_event_envelope_ref | 缺失 core_event_ref 时 reject accepted publication | AcceptCommittedOutboxFact |
```

错误示例：

```md
CommittedOutboxFactInput 可以构造 PublicationMaterial。
delivery_mode 后续再补。
core_event_envelope_ref 可先当作 core_event_ref 用。
```

错误原因：

- 没有字段来源和缺失处理。
- 把两个语义不同的引用混同。
- 实现者需要自行补设字段，无法按设计 1:1 实现。

## 五、章节级规范

允许的默认布局形态有两类:

| 布局形态 | 典型目录 | 适用条件 | 边界约束方式 |
|---|---|---|---|

选择规则:

```text
如果边界主要是代码组织边界
        -> 使用单 crate 模块分层架构

如果边界需要被编译依赖 / 公共契约 / 多运行入口强约束
        -> 使用 workspace 多 crate 架构
```

判断问题:

| 问题 | 是 | 否 |
|---|---|---|
| 其他仓库是否需要直接依赖本仓 Rust 类型、DTO、Event、Snapshot、Job 或 Error? | 倾向 workspace 多 crate | 继续判断 |
| 是否存在 API server、worker、subscriber、operations job 等多个运行入口共享核心逻辑? | 倾向 workspace 多 crate | 继续判断 |
| 是否必须用编译依赖关系强制 domain 不依赖 infra / HTTP / DB / bus? | 倾向 workspace 多 crate | 继续判断 |
| 本仓是否主要是一个业务服务内部实现,外部只通过 API / Event 交互? | 倾向单 crate 模块分层 | 若仍不确定,列入风险与待确认事项 |

- Query response 字段引用的 enum / ref / value object 必须写明归属;contracts view 不得直接依赖 domain-only 类型,需要共享时应上提到 contracts shared 或定义正式映射。
- Repository page helper 如 `Page<T>` / `PageInfo` 必须写明归属、字段和与 public page DTO 的映射;不得只在 trait 返回值中出现类型名。

- HLD `*Query`、DDD `*Request`、Rust DTO 名称如果发生收敛，必须在协议章节写明一对一映射。

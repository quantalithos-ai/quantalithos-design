# 详细设计讨论流程_SOP

> 目标：定义“详细设计内容如何生成”，用于把已收稳的概要设计结果转译成可以 1:1 实现的代码实现契约。  
> 适用对象：人类作者、Claude/其他 Agent、多人协作讨论。  
> 与 `详细设计书写规范.md` 的关系：书写规范负责定义最终结果结构；本 SOP 负责定义章节如何被讨论、收敛和回填。
> 与 `设计文档讨论中间产物规范.md` 的关系：本 SOP 定义每一步问什么；中间产物规范定义每一步讨论后留下什么、如何确认、如何回填。

## 1. 适用前提

本 SOP 适用于：

```text
需要为一个仓 / 一个模块 / 一个子系统编写 03-详细设计.md
且希望先通过讨论逐步收敛内容，再落正式文档
```

它不适用于：

```text
重新定义需求目标与用户故事
重新定义架构边界、子域划分与技术取舍
重新定义概要设计中的主要组成部分和代码主体骨架
直接编写实施计划、测试方案、配置设计或部署运维手册
```

## 2. 核心原则

### 2.1 先承接概要设计，后展开实现契约

详细设计不是从零开始，而是在概要设计已经收稳的代码主体框架、主要组成部分、关键对象、接口骨架、处理流和状态机基础上继续下沉。

### 2.2 以模块为主轴

详细设计必须按模块 / crate / package / 文件组展开，而不是把所有对象、trait、函数集中堆在全局章节。

```text
模块是详细设计的组织主轴。
对象、trait、函数、错误、持久化和测试切口是模块内的固定内容。
```

### 2.3 结果结构与生成流程分离

- `详细设计书写规范.md` 负责定义最终文档结构。
- `详细设计讨论流程_SOP.md` 负责定义生成流程。

### 2.4 按输入驱动输出收敛

每一步不是自由问答，而是：

```text
先检查本步输入是否满足
再确认本步输出是什么
然后围绕输出反推问题
最后按书写规范落文
```

### 2.5 代码契约必须可实现

详细设计中的类型、字段、函数、schema、错误和状态转换必须足够具体，使实现者可以直接写代码。

特别要求：

- struct / enum / enum variant / value object 必须有 Rustdoc 风格中文注释。
- 成员变量必须写类型和作用。
- 成员函数必须写函数签名、参数类型、返回类型和作用。
- enum 必须说明分类边界;每个 variant 必须说明业务语义,带载荷 variant 必须说明载荷语义。
- 关键伪代码必须写明 `对象.函数(Type 参数名)` 或 `Type::函数(Type 参数名)`。
- 每个需要实现的 Command / Query / Event / Job 都必须有独立处理流。

### 2.6 门禁真实生效

如果概要设计输入不足、模块边界不清、文件布局不清、对象契约不清，就不应强行进入后续步骤。

### 2.7 不确定项不脑补

无法确认的实现细节必须进入风险与待确认事项，不得写成已经收稳的代码契约。

### 2.8 ASCII 图输出统一

凡是本 SOP 中要求或允许输出 ASCII 图的 Step，都必须在讨论阶段同时收稳：

```text
图类型
图标题
ASCII 图正文
图后 2~5 条关键说明
```

所有 ASCII 图必须遵守 `详细设计书写规范` 4.2 `ASCII 图统一格式`。

产图 Step 的最小输出结构为：

````md
#### <图类型>: <图标题>

```text
<ASCII 图正文>
```

关键说明：
- <图表达了什么结构关系>
- <图没有表达哪些下游细节>
- <图中最容易误解的边界是什么>
````

如果某一步按需可画图但本轮不画，必须说明“不画图的原因”，不能留下空图占位。

### 2.9 中间产物先于正式文档

每个 Step 不得直接跳到正式 `03-详细设计.md`。

执行链路必须是：

```text
本步输入
  -> 应问的问题
  -> SOP 问题回答
  -> Step 中间产物
  -> 回填草稿
  -> 用户确认 / 门禁通过
  -> 正式文档章节
```

Step 中间产物必须遵循 `standards/document/设计文档讨论中间产物规范.md`，至少包含：

- Step 状态
- 本步输入
- SOP 问题回答
- 当前文档问题诊断
- 改动前后对比
- 设计取舍
- 结构化中间产物
- 回填草稿
- 待确认事项
- 进入下一步条件

如果用户要求逐步讨论或逐步划掉，必须先在对应子项目内建立 `design-calibration/03_ddd_calibration_flow.md` 工作台文件，并在每个 Step 完成后更新状态。

### 2.10 通用执行纪律

详细设计讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `03-详细设计.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。
- 对象实现契约、Trait / Port / Adapter 契约、协议契约、逐接口处理流、状态机和事务一致性等重 Step 应单独成批完成。

正确示例：

```text
先创建 03-详细设计.md 骨架。
Step 6 对象契约很重，先建 Step 6 文件骨架，再按模块分批写对象。
Step 9 逐接口处理流按 Command、Query、Job 分批写入。
每批写完后检查函数签名、参数类型和校准来源。
```

错误示例：

```text
一次性生成完整 03-详细设计.md，预计 1500 行。
把 Step 6 对象契约、Step 7 trait 契约、Step 8 协议契约合并成一个“实现契约总表”。
为了降低篇幅，省略 enum variant 注释和函数参数类型。
正式章节没有列出对应中间产物。
```

错误原因：

- 详细设计要求实现者 1:1 还原，压缩重 Step 会直接造成实现缺口。
- 单次超长写入容易漏字段、漏函数、漏错误分支和旧口径残留。
- 无追溯来源时无法判断实现契约来自哪一步讨论。

### 2.11 跨文档闭环必须前置消解

详细设计讨论必须在收口前完成跨文档一致性复核。该复核不是最后格式检查，而是确认实现者不需要自行猜字段、猜状态、猜函数或猜 phase 边界。

本节复核必须同时执行 `standards/document/设计真相源闭环与可落码性标准.md`。该标准负责定义统一判断口径，本 SOP 负责规定在详细设计讨论中何时检查、如何回填和何时暂停。

必须复核：

```text
Step 6 对象契约
  -> Step 8 协议契约
  -> Step 9 处理流
  -> Step 10 状态机
  -> Step 16 测试切口
  -> Step 17 实施承接清单
```

并额外复核：

```text
metadata authority
idempotency key / request digest / result_ref / UoW
ref / reason / result / receipt schema
validation truth source / repository / port
projection rebuild truth source
artifact materialization / evidence path
```

正确示例：

```text
在 Step 8 为 AcceptPublicationCommand 输出 DTO -> PublicationMaterial 构造闭环表。
在 Step 10 明确 DeliveryStatus 正式枚举值。
在 Step 16 测试切口只引用正式状态名。
在 Step 17 标记 PH-03 不依赖 PH-05 的 FeedbackResult。
```

错误示例：

```text
Step 6 写 Pending, Step 10 写 Draft, 测试方案写 dispatched。
Step 8 的 DTO 缺少 Domain 必填字段, Step 9 仍假设能直接构造对象。
Step 17 把后续 phase 才实现的对象放进当前 phase 门禁。
```

错误原因：

- 单个章节可能看起来完整，但组合后无法 1:1 实现。
- 实现者会被迫自行补设字段、选择状态名或调整 phase scope。
- 测试和验收会继续引用旧口径，导致实现后仍无法通过审查。

如果上述任一复核项未通过，不得把问题留给实现 agent。必须先回写正式设计真相源，或在风险与待确认事项中明确标为阻塞并停止进入实施计划。

## 3. Step 模板的字段关系

每个 Step 都由以下字段组成：

| 字段 | 作用 |
|---|---|
| 本步目标 | 定义本步存在的意义，说明这一步要解决什么问题。 |
| 本步输入 | 定义本步开始前必须具备的前提、上游结论或已收敛结果。 |
| 本步输出 | 定义本步必须收敛出的结果类型。 |
| 应问的问题 | 用于把输入收敛成输出的问题集合，不是独立问卷。 |
| 期望产出 | 本步应交付的具体结论项，是对“本步输出”的展开。 |
| 回填位置 | 指明本步产出最终写入的规范章节或正式文档位置。 |
| 执行约束 | 规定本步过程中哪些做法允许，哪些做法禁止。 |
| 进入下一步的条件 | 判断本步是否完成的门槛。 |

### 执行顺序

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 回填位置
  -> 进入下一步的条件
```

## 4. 建议的讨论总流程

```text
Step 1. 确认概要设计输入边界
Step 2. 明确本轮实现范围和非范围
Step 3. 收稳编码规范、语言 / runtime、仓库约束
Step 4. 收稳实现单元与文件布局
Step 5. 定义模块实现契约主轴
Step 6. 逐模块定义对象实现契约
Step 7. 逐模块定义 Trait / Port / Adapter 契约
Step 8. 定义 API / Command / Query / Event / Job 协议契约
Step 9. 逐接口定义函数级处理流
Step 10. 定义状态机与转换矩阵
Step 11. 定义持久化、事务与一致性契约
Step 12. 定义错误模型、异常分支与恢复口径
Step 13. 定义并发、幂等与重入保护
Step 14. 定义配置引用与外部依赖绑定
Step 15. 定义可观测性与审计埋点契约
Step 16. 定义测试切口与最小验证清单
Step 17. 收口详细设计到实施计划的承接清单
Step 18. 风险与待确认事项
Step 19. 整理正式详细设计文档
```

## 5. 每一步的讨论目标、输入与产出

### Step 1. 确认概要设计输入边界

#### 本步目标

确认当前详细设计依赖的概要设计结论已经收敛到足以支撑实现契约展开的程度，并识别哪些上游结论会直接影响模块、文件、对象、接口、处理流和状态机。

#### 本步输入

- 当前仓对应的 `00-需求文档.md`
- 当前仓对应的 `01-架构设计.md`
- 当前仓对应的 `02-概要设计.md`
- 概要设计中的详细设计承接清单
- 已确认的编码规范和仓库约束线索

#### 本步输出

- 上游关系映射表
- `本文不再回答` 清单
- `本文必须回答` 清单
- 输入不足风险清单

#### 应问的问题

```text
1. 当前详细设计直接承接概要设计中的哪些结论？
2. 概要设计中的代码主体框架是否已经足够稳定？
3. 概要设计中的关键对象、接口骨架、处理流和状态机是否足够继续展开？
4. 哪些内容仍停留在概要设计轮廓，进入详细设计前必须补清？
5. 哪些需求或架构结论会影响详细设计，但不能在详细设计中重新定义？
```

#### 期望产出

```md
| 来源文档 | 承接内容 | 本文继续展开什么 |
|---|---|---|

本文不再回答：
- <已由需求 / 架构 / 概要设计收稳的问题>

本文必须回答：
- <本详细设计必须继续收稳的实现契约问题>

输入不足风险：
- <缺失项及影响>
```

#### 回填位置

- `详细设计书写规范` 5.1 与上游文档的关系声明
- `详细设计书写规范` 5.17 风险与待确认事项

#### 执行约束

- 本步只确认详细设计可承接什么，不重写上游文档。
- 如果概要设计没有收稳代码主体、对象、接口或状态机，应先返回概要设计补齐。
- 不允许把待确认项写成详细设计正文契约。

#### 进入下一步的条件

```text
已明确详细设计承接哪些上游结论、继续展开哪些实现契约，并识别所有会阻塞详细设计的输入缺口。
```

### Step 2. 明确本轮实现范围和非范围

#### 本步目标

明确本轮详细设计要覆盖哪些实现单元、模块、接口和流程，以及哪些内容明确不进入本轮。

#### 本步输入

- Step 1 的上游关系映射表
- 概要设计的设计目标、范围和详细设计承接清单
- 当前仓的实现优先级或阶段边界

#### 本步输出

- 设计目标表
- 非范围表

#### 应问的问题

```text
1. 本轮详细设计必须覆盖哪些模块？
2. 本轮必须定义哪些对象、接口、事件、job 和状态机？
3. 哪些能力属于 P1 / 后续阶段，不应在本轮展开？
4. 哪些内容属于测试方案、实施计划、配置设计或运维手册？
5. 实现者拿到本文后，应能完成哪些代码范围？
```

#### 期望产出

```md
| 目标 | 说明 | 交付给实现者的结果 |
|---|---|---|

| 非范围 | 留给哪一层 / 哪份文档 |
|---|---|
```

#### 回填位置

- `详细设计书写规范` 5.2 本次详细设计目标与范围

#### 执行约束

- 目标必须是实现契约目标，不是用户故事或功能需求复述。
- 非范围必须写清楚归属层次或文档。
- 不写排期和开发任务拆分。

#### 进入下一步的条件

```text
本轮要实现什么、不实现什么已经清楚，且可以据此进入编码规范和仓库约束讨论。
```

### Step 3. 收稳编码规范、语言 / runtime、仓库约束

#### 本步目标

确认详细设计必须遵守的语言、编码、注释、仓库、提交、runtime、依赖和安全边界约束。

#### 本步输入

- Step 2 的本轮范围
- `standards/coding` 下的 Rust 编码规范
- 项目提交规范、git config 用户约束、注释规范
- 架构设计中的技术选型和安全边界结论
- `/home/aris/Projects` 下已经实现或计划实现的 sibling repo
- 需求 / 架构阶段已确认的本仓依赖裁剪表和依赖类型分类表

#### 本步输出

- 编码规范承接表
- 实现约束表
- 本地多仓依赖约束表

#### 应问的问题

```text
1. 本仓使用什么语言、runtime、框架和主要依赖？
2. Rust 编码规范中哪些内容会影响结构体、错误、trait、async、测试和注释？
3. 是否必须遵守 rustdoc 风格注释？struct、字段、enum、enum variant、函数分别如何注释？
4. 实施者开始前必须阅读哪些提交规范和 git config 用户要求？
5. 哪些安全、鉴权、网关或外部边界不应在本仓实现？
```

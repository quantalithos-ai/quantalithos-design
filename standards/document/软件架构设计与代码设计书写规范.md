# 🏗️ 优秀的软件架构设计与代码设计规范 — 综合参考清单

> 设计模式并不是彼此孤立的"招式清单"，而是软件系统在不同维度上的可复用设计经验。  
> GoF 模式主要面向对象的创建、结构和行为协作；PEAA 面向企业应用的分层、领域逻辑与持久化映射；微服务与云原生模式面向服务拆分、自治、弹性、治理与可观测性；DDD 模式强调业务建模与边界划分；并发、Reactive 与函数式模式则更多关注异步协作、数据流与可组合性。  
> 在真实项目中，一个成熟框架通常会同时组合多种模式，而不是只体现某一种模式。

## 一、GoF 23 种经典设计模式

### 1.1 创建型模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 单例 | Singleton | 保证一个类只有一个实例，并提供全局访问点 |
| 工厂方法 | Factory Method | 定义创建对象的接口，让子类决定实例化哪个具体类 |
| 抽象工厂 | Abstract Factory | 提供一个接口，用于创建一组相关或相互依赖的对象，而无需指定具体类 |
| 建造者 | Builder | 将复杂对象的构建过程与其表示分离，使同一构建过程可以创建不同表示 |
| 原型 | Prototype | 通过复制现有对象来创建新对象，从而避免直接依赖具体类的构造过程 |

### 1.2 结构型模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 适配器 | Adapter | 将一个类的接口转换成客户端期望的另一个接口 |
| 桥接 | Bridge | 将抽象部分与实现部分分离，使它们可以独立变化 |
| 组合 | Composite | 将对象组合成树形结构以表示"部分—整体"层次，并让客户端一致对待单个对象和组合对象 |
| 装饰器 | Decorator | 在不改变对象接口的前提下，动态地给对象添加职责 |
| 门面 | Facade | 为复杂子系统提供一个统一的高层接口，简化其使用 |
| 享元 | Flyweight | 通过共享细粒度对象来减少内存占用和对象创建成本 |
| 代理 | Proxy | 为另一个对象提供替身或占位，以控制对该对象的访问 |

### 1.3 行为型模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 职责链 | Chain of Responsibility | 将请求沿处理者链传递，使多个对象都有机会处理该请求 |
| 命令 | Command | 将请求封装为对象，从而支持参数化、排队、日志和撤销操作 |
| 解释器 | Interpreter | 为某种语言定义文法表示，并提供解释该语言句子的解释器 |
| 迭代器 | Iterator | 提供一种顺序访问聚合对象中元素的方法，而不暴露其内部表示 |
| 中介者 | Mediator | 用一个中介对象封装一组对象之间的交互，降低对象间耦合 |
| 备忘录 | Memento | 在不破坏封装的前提下捕获并恢复对象的内部状态 |
| 观察者 | Observer | 定义对象间一对多依赖关系，使状态变化时自动通知并更新依赖对象 |
| 状态 | State | 允许对象在内部状态改变时改变其行为，看起来像修改了类 |
| 策略 | Strategy | 定义一系列可互换算法，并将它们封装起来使其可独立变化 |
| 模板方法 | Template Method | 在父类中定义算法骨架，将某些步骤延迟到子类实现 |
| 访问者 | Visitor | 在不改变对象结构的前提下，为元素增加新的操作 |

## 二、企业应用架构模式（PEAA）

> 依据 Martin Fowler 的 *Patterns of Enterprise Application Architecture* 目录整理。这是企业应用架构领域最经典的模式目录之一，对 Java/.NET/Spring/Hibernate 一类企业应用框架影响非常深。

### 2.1 领域逻辑模式（Domain Logic Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 事务脚本 | Transaction Script | 按过程组织业务逻辑，每个过程处理表现层的一个请求 |
| 领域模型 | Domain Model | 包含行为和数据的领域对象模型 |
| 表模块 | Table Module | 处理数据库表或视图中所有行业务逻辑的单实例 |
| 服务层 | Service Layer | 定义应用边界，通过一组服务建立可用操作集合并协调应用响应 |

### 2.2 数据源架构模式（Data Source Architectural Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 表数据入口 | Table Data Gateway | 充当数据库表网关的对象，一个实例处理表中所有行 |
| 行数据入口 | Row Data Gateway | 充当数据源中单条记录网关的对象，每行一个实例 |
| 活动记录 | Active Record | 包装数据库表行的对象，封装数据库访问并在数据上添加领域逻辑 |
| 数据映射器 | Data Mapper | 在对象和数据库之间移动数据的映射层，保持两者互相独立 |

### 2.3 对象-关系行为模式（Object-Relational Behavioral Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 工作单元 | Unit of Work | 维护受业务事务影响的对象列表，协调变更写出和并发问题解决 |
| 标识映射 | Identity Map | 确保每个对象只加载一次，通过映射查找已加载对象 |
| 延迟加载 | Lazy Load | 包含不全部数据但知道如何获取的对象 |

### 2.4 对象-关系结构模式（Object-Relational Structural Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 标识字段 | Identity Field | 在对象中保存数据库 ID 字段，维护内存对象与数据库行的标识 |
| 继承映射器 | Inheritance Mappers | 组织处理继承层次结构的数据库映射器结构 |
| 外键映射 | Foreign Key Mapping | 将对象间关联映射为表间外键引用 |
| 关联表映射 | Association Table Mapping | 将关联保存为带有外键的表 |
| 从属映射 | Dependent Mapping | 由一个类为子类执行数据库映射 |
| 嵌入值 | Embedded Value | 将对象映射到另一个对象表的多个字段 |
| 序列化大对象 | Serialized LOB | 通过序列化将对象图存储到数据库单个大对象字段 |
| 单表继承 | Single Table Inheritance | 用一张包含所有类字段的表表示继承层次 |
| 类表继承 | Class Table Inheritance | 每个类一张表来表示继承层次 |
| 具体表继承 | Concrete Table Inheritance | 每个具体类一张表来表示继承层次 |

### 2.5 对象-关系元数据映射模式（Object-Relational Metadata Mapping Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 元数据映射 | Metadata Mapping | 在元数据中保存对象-关系映射细节 |
| 查询对象 | Query Object | 表示数据库查询的对象 |
| 仓储 | Repository | 使用类似集合的接口在领域和数据映射层之间进行中介 |

### 2.6 Web 表现层模式（Web Presentation Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| MVC | Model View Controller | 将用户界面交互分为三个不同角色 |
| 页面控制器 | Page Controller | 处理网站特定页面或动作请求的对象 |
| 前端控制器 | Front Controller | 处理网站所有请求的单一控制器 |
| 模板视图 | Template View | 通过在 HTML 中嵌入标记来渲染页面 |
| 转换视图 | Transform View | 逐条处理领域数据并转换为 HTML |
| 两步视图 | Two Step View | 先将领域数据转为逻辑呈现，再转为 HTML |
| 应用控制器 | Application Controller | 集中管理 URL 到动作和视图的映射 |

### 2.7 分布式模式（Distribution Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 远程外观 | Remote Facade | 为细粒度对象提供粗粒度远程接口 |
| 数据传输对象 | Data Transfer Object | 在进程间传输数据的序列化载体 |

### 2.8 离线并发模式（Offline Concurrency Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 乐观离线锁 | Optimistic Offline Lock | 通过检测冲突来解决并发访问问题 |
| 悲观离线锁 | Pessimistic Offline Lock | 通过提前获取独占权来防止冲突 |
| 粗粒度锁 | Coarse-Grained Lock | 用单个锁锁定多个相关对象 |
| 隐式锁 | Implicit Lock | 由框架自动管理锁的获取和释放 |

### 2.9 会话状态模式（Session State Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 客户端会话状态 | Client Session State | 将会话数据存储在客户端 |
| 服务端会话状态 | Server Session State | 将会话数据存储在服务端 |
| 数据库会话状态 | Database Session State | 将会话数据序列化存储在数据库 |

### 2.10 基础模式（Base Patterns）

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 网关 | Gateway | 封装对外部系统或资源的访问 |
| 服务桩 | Service Stub | 在测试中替代外部服务的占位实现 |
| 记录集 | Record Set | 列表式的内存数据结构 |
| 映射器 | Mapper | 在两个独立对象之间建立通信 |
| 层超类型 | Layer Supertype | 充当某层所有类型超类型的类 |
| 分离接口 | Separated Interface | 在不同包中定义接口和实现 |
| 注册表 | Registry | 全局知名对象查找服务 |
| 值对象 | Value Object | 小而简单的对象，通过值而非身份比较 |
| 金额对象 | Money | 表示货币值的值对象 |
| 特例对象 | Special Case | 特殊情况的子类，提供空行为 |
| 插件 | Plugin | 在配置时而非编译时选择实现 |

### 2.11 参考资源

| 资源 | 说明 |
|------|------|
| [Martin Fowler PEAA 目录](https://martinfowler.com/eaaCatalog/) | 企业应用架构模式完整在线目录 |
| 《Patterns of Enterprise Application Architecture》Martin Fowler | PEAA 原书 |

## 三、微服务设计模式

> 依据 Chris Richardson 在 microservices.io 上的模式目录整理。这是微服务架构最常引用的模式语言之一。

### 3.1 架构风格

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 单体架构 | Monolithic Architecture | 将应用构建为单一可部署单元 |
| 微服务架构 | Microservice Architecture | 将应用构建为一组松耦合、可独立部署的服务 |

### 3.2 服务拆分

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 按业务能力拆分 | Decompose by Business Capability | 围绕业务能力组织服务 |
| 按子域拆分 | Decompose by Subdomain | 围绕 DDD 限界上下文组织服务 |
| 自包含服务 | Self-contained Service | 每个服务独立处理请求，最小化同步依赖 |
| 每团队一服务 | Service per Team | 服务与团队对齐 |

### 3.3 服务协作与数据

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 每服务独享数据库 | Database per Service | 确保服务松耦合，每服务自有私有数据库 |
| Saga | Saga | 用一组本地事务和补偿动作替代跨服务分布式事务 |
| API 组合 | API Composition | 通过 API 网关或组合服务聚合多个服务的数据 |
| CQRS | CQRS | 将写模型和读模型分离 |
| 领域事件 | Domain Event | 在服务间异步通知业务事实 |
| 事件溯源 | Event Sourcing | 以事件序列持久化聚合状态变更 |

### 3.4 事务消息

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 事务外盒 | Transactional Outbox | 将业务数据和待发布事件原子写入 |
| 事务日志拖尾 | Transaction Log Tailing | 通过追踪数据库事务日志发布消息 |
| 轮询发布者 | Polling Publisher | 通过轮询 Outbox 表发布消息 |

### 3.5 对外 API

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| API 网关 | API Gateway | 对外统一入口，承载路由、鉴权、聚合、限流等职责 |
| 前端专属后端 | Backend for Front-end (BFF) | 为特定前端提供定制化 API |

### 3.6 服务发现

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 客户端发现 | Client-side Discovery | 客户端查询服务注册表并选择实例 |
| 服务端发现 | Server-side Discovery | 路由器/负载均衡器查询服务注册表 |
| 服务注册表 | Service Registry | 维护服务实例位置信息的数据库 |
| 自注册 | Self Registration | 服务实例自行注册到服务注册表 |
| 第三方注册 | 3rd Party Registration | 由第三方将服务实例注册到服务注册表 |

### 3.7 可靠性

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 熔断器 | Circuit Breaker | 当下游错误率过高时快速失败，避免雪崩 |

### 3.8 可观测性

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 日志聚合 | Log Aggregation | 将分散实例日志汇聚检索 |
| 应用指标 | Application Metrics | 采集并可视化服务指标 |
| 审计日志 | Audit Logging | 记录用户行为 |
| 分布式追踪 | Distributed Tracing | 通过链路追踪还原跨服务调用路径 |
| 异常跟踪 | Exception Tracking | 集中记录和跟踪异常 |
| 健康检查 API | Health Check API | 让平台知道服务实例是否可接流量 |

### 3.9 部署

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 每容器一个服务实例 | Service Instance per Container | 每个服务实例运行在独立容器中 |
| 无服务器部署 | Serverless Deployment | 使用 FaaS 部署服务 |
| 服务部署平台 | Service Deployment Platform | 自动化服务部署的抽象平台 |

### 3.10 横切关注点

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 微服务底盘 | Microservice Chassis | 处理横切关注点的基础框架 |
| 外部化配置 | Externalized Configuration | 将配置与代码分离，便于环境切换 |
| 服务模板 | Service Template | 包含横切关注点实现的起始模板 |

### 3.11 通信风格

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 远程过程调用 | Remote Procedure Invocation | 使用同步的请求/响应协议 |
| 消息通信 | Messaging | 使用异步消息进行服务间通信 |
| 幂等消费者 | Idempotent Consumer | 允许消息重复投递而不造成业务副作用 |

### 3.12 向服务化重构

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 绞杀者应用 | Strangler Application | 逐步用新服务替换单体应用 |
| 防腐层 | Anti-Corruption Layer | 用转换层隔离外部模型对本域模型的污染 |

### 3.13 参考资源

| 资源 | 说明 |
|------|------|
| [microservices.io](https://microservices.io/patterns/) | Chris Richardson 的微服务模式目录 |
| 《Microservices Patterns》Chris Richardson | 微服务模式原书 |
| [Martin Fowler Microservices](https://martinfowler.com/articles/microservices.html) | 微服务概念经典阐述 |

## 四、云原生设计模式

> 云原生模式来自 Kubernetes、Service Mesh、分布式系统和 DevOps 实践中的高频模式集合。

### 4.1 Pod / Runtime 侧模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 边车 | Sidecar | 将日志、代理、监控等辅助能力放到与主容器共生的伴生容器中 |
| 大使 | Ambassador | 用伴生代理容器统一处理主容器的出站访问 |
| 适配器 | Adapter | 将应用输出转换为平台统一格式 |
| 初始化容器 | Init Container | 在主容器启动前完成依赖准备和配置生成 |
| 服务网格 | Service Mesh | 把流量治理、认证、重试、熔断、观测等能力从业务代码下沉到基础设施层 |

### 4.2 控制面 / 运维自动化模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 操作器 | Operator | 用代码把人工运维知识固化成控制器，实现声明式运维 |
| 控制器 / 协调回路 | Controller / Reconciliation Loop | 持续比较期望状态与实际状态，并自动收敛系统 |
| 声明式配置 | Declarative Configuration | 描述"想要什么状态"，由平台负责达到该状态 |
| 不可变基础设施 | Immutable Infrastructure | 通过替换而不是原地修改来升级运行环境 |
| 外部化配置 | Externalized Configuration | 将配置与镜像/代码分离，便于环境切换和集中治理 |

### 4.3 韧性 / 容错模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 熔断器 | Circuit Breaker | 当下游错误率过高时快速失败，避免雪崩 |
| 重试 | Retry | 对瞬时失败进行有限次数重试 |
| 超时 | Timeout | 为远程调用设置明确的最大等待时间 |
| 降级 | Fallback | 主路径失败时提供备用结果或受限服务 |
| 舱壁隔离 | Bulkhead | 将资源隔离，避免局部故障拖垮全局 |
| 限流 | Rate Limiting | 对请求速率进行限制，保护系统稳定性 |
| 负载削峰 | Load Shedding | 在超载场景下主动拒绝部分请求 |

### 4.4 数据一致性 / 集成模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| Saga | Saga | 用一组本地事务和补偿动作替代跨服务分布式事务 |
| 事务外盒 | Transactional Outbox | 将业务数据和待发布事件原子写入 |
| CQRS | CQRS | 将写模型和读模型分离 |
| 事件溯源 | Event Sourcing | 不存最终状态，只存状态变化事件 |
| 幂等消费者 | Idempotent Consumer | 允许消息重复投递而不造成业务副作用 |
| 竞争消费者 | Competing Consumers | 多个消费者并行消费同一队列以扩展吞吐 |

### 4.5 服务治理 / 可观测性模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| API 网关 | API Gateway | 对外统一入口，承载路由、鉴权、聚合、限流等职责 |
| 服务发现 | Service Discovery | 动态发现服务实例位置 |
| 健康探针 | Health Check / Readiness / Liveness Probe | 让平台知道实例是否存活、是否可接流量 |
| 分布式追踪 | Distributed Tracing | 通过链路追踪还原跨服务调用路径 |
| 集中日志 | Centralized Logging | 将分散实例日志汇聚检索 |
| 指标与告警 | Metrics + Alerting | 通过指标采集与阈值告警及时发现异常 |

### 4.6 发布 / 弹性模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 滚动发布 | Rolling Update | 逐步替换实例，降低升级风险 |

## 五、领域驱动设计（DDD）模式

> DDD 分为战略设计和战术设计两层。战略设计解决"领域边界怎么划"；战术设计解决"模型内部怎么落"。

### 5.1 战略设计模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 统一语言 | Ubiquitous Language | 团队用一致的业务术语沟通需求、模型和代码 |
| 限界上下文 | Bounded Context | 明确某个模型适用的边界，避免概念在全局混用 |
| 上下文映射 | Context Map | 描述多个限界上下文之间的关系和集成方式 |
| 核心域 | Core Domain | 最能体现业务竞争力、最值得投入建模能力的领域 |
| 支撑子域 | Supporting Subdomain | 支撑核心域但不构成竞争壁垒的子域 |
| 通用子域 | Generic Subdomain | 通用性强、可购买或复用现成方案的子域 |
| 共享内核 | Shared Kernel | 多个上下文共享一小部分稳定模型 |
| 伙伴关系 | Partnership | 两个上下文协同演进，共同维护集成契约 |
| 客户-供应商 | Customer-Supplier | 上游根据下游需求提供稳定能力 |
| 遵奉者 | Conformist | 下游直接遵从上游模型，减少翻译成本 |
| 防腐层 | Anti-Corruption Layer | 用转换层隔离外部模型对本域模型的污染 |
| 开放主机服务 | Open Host Service | 对外提供清晰稳定的服务协议 |
| 已发布语言 | Published Language | 用共享协议/文档/消息格式作为上下文间的公共语言 |
| 各走各路 | Separate Ways | 上下文尽量独立，不建立强耦合集成 |

### 5.2 战术设计模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 实体 | Entity | 通过身份而不是属性值来区分的对象 |
| 值对象 | Value Object | 通过值定义、通常不可变、没有独立身份的对象 |
| 聚合 | Aggregate | 一组业务一致性边界内的对象集合 |
| 聚合根 | Aggregate Root | 聚合的唯一外部入口，负责维护聚合不变式 |
| 仓储 | Repository | 提供像集合一样访问聚合的方法，屏蔽持久化细节 |
| 领域服务 | Domain Service | 承载不自然归属于某个实体/值对象的领域规则 |
| 应用服务 | Application Service | 编排用例流程、事务和安全，不承载核心业务规则 |
| 工厂 | Factory | 负责创建复杂聚合或保证创建时满足不变式 |
| 规约 | Specification | 将复杂业务判断抽象为可组合、可复用的规则对象 |
| 模块 | Module | 按业务语义组织领域模型，控制复杂度 |
| 领域事件 | Domain Event | 表达"领域中已经发生的重要事实" |

### 5.3 DDD 在分布式/事件驱动中的扩展模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| Saga / 进程管理器 | Saga / Process Manager | 管理跨聚合、跨上下文的长事务与补偿流程 |
| 事件溯源 | Event Sourcing | 用事件而非当前状态来保存聚合演化过程 |
| CQRS | CQRS | 将命令模型与查询模型分离 |
| Outbox + 领域事件 | Outbox + Domain Event | 确保领域事件可靠地从事务边界发布出去 |

## 六、并发与反应式设计模式

### 6.1 并发编程模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 线程池 | Thread Pool | 复用工作线程来处理任务，降低线程频繁创建/销毁开销 |
| 生产者-消费者 | Producer-Consumer | 通过队列解耦任务生产与消费 |
| Future / Promise | Future / Promise | 以占位对象表示异步结果 |
| 分治并行 | Fork/Join | 将任务递归拆分后并行执行，再汇总结果 |
| 反应器 | Reactor | 用事件循环监听 I/O 事件，再分发给处理器 |
| 前摄器 | Proactor | 由异步 I/O 完成后通知应用处理结果 |
| 主动对象 | Active Object | 将方法调用转换为异步消息，通过调度器串行执行 |
| Actor 模型 | Actor Model | 通过消息而非共享内存进行并发协作 |
| 监视器对象 | Monitor Object | 将共享状态与同步机制封装在对象内部 |
| 读写锁 | Read-Write Lock | 区分读共享与写互斥，提高读多写少场景吞吐 |
| 线程封闭 | Thread Confinement | 将状态限制在线程内部，避免共享同步成本 |
| 工作窃取 | Work Stealing | 空闲线程从其他线程队列窃取任务，提高资源利用率 |
| 流水线 | Pipeline | 将处理流程拆为多个阶段并行推进 |
| 领导者-追随者 | Leader-Follower | 多个工作线程轮流充当事件接收者 |

### 6.2 Reactive 模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 观察者 | Observer | 状态变化时自动通知订阅方，响应式编程的基础 |
| 发布-订阅 | Publish-Subscribe | 通过事件总线或主题解耦发布方和订阅方 |
| 事件流 | Event Stream | 将离散事件建模为持续流并进行组合处理 |
| 响应式流 | Reactive Streams | 定义异步流处理规范，强调非阻塞与背压 |
| 背压 | Backpressure | 下游处理不过来时向上游反馈，防止内存失控 |
| 调度器 | Scheduler | 将流处理逻辑与执行线程/线程池策略解耦 |
| 防抖 | Debounce | 在短时间高频事件中只取最后一次有效事件 |
| 节流 / 采样 | Throttle / Sample | 在固定时间窗口内限制事件处理频率 |
| 缓冲 / 窗口 | Buffer / Window | 将连续事件按数量或时间分批处理 |
| 重试 / 重复 | Retry / Repeat | 对失败流或完成流按策略重新订阅 |
| 热流 / 冷流 | Hot / Cold Stream | 区分"共享事件源"与"订阅时才开始生产"的流 |

现代高性能系统常见组合：

- `Producer-Consumer + Backpressure`

- `Pipeline + Work Stealing`
- `Observer + Scheduler + Retry`

## 七、函数式编程设计模式

> FP 里的"模式"不是 GoF 那种面向对象协作模板，而是数据建模方式、组合方式、求值策略和代数抽象。

### 7.1 基础语义模式

| 模式 | 英文名 | 核心意图 |
|------|--------|---------|
| 不可变性 | Immutability | 数据一旦创建就不修改，变化通过返回新值表达 |
| 纯函数 | Pure Function | 相同输入总产生相同输出，且无副作用 |
| 引用透明 | Referential Transparency | 表达式可安全替换为其结果而不改变程序行为 |
| 高阶函数 | Higher-Order Function | 函数可以接收函数或返回函数 |
| 函数组合 | Function Composition | 将多个小函数连接成更高层行为 |
| 柯里化 | Currying | 将多参数函数转换为一连串单参数函数 |
| 偏应用 | Partial Application | 预先固定部分参数，生成更专用的函数 |
| 惰性求值 | Lazy Evaluation | 仅在真正需要时才计算表达式 |

### 9.2 架构方法论与模式

#### 9.2.1 Clean Architecture（整洁架构）

> 提出者：Robert C. Martin (Uncle Bob)，2012 年

**核心思想**：依赖规则必须由外向内——内层（业务规则）不能依赖外层（框架、数据库、UI）。系统应该独立于框架、可测试、独立于 UI、独立于数据库、独立于任何外部机构。

**四层模型**：

```
┌─────────────────────────────────────────────────┐
│  Frameworks & Drivers（框架与驱动层）             │
│  ┌─────────────────────────────────────────────┐ │
│  │  Interface Adapters（接口适配器层）           │ │
│  │  ┌─────────────────────────────────────────┐ │ │
│  │  │  Application Business Rules（用例层）    │ │ │
│  │  │  ┌─────────────────────────────────────┐ │ │ │
│  │  │  │  Enterprise Business Rules（实体层） │ │ │ │
│  │  │  └─────────────────────────────────────┘ │ │ │
│  │  └─────────────────────────────────────────┘ │ │
│  └─────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────┘
依赖方向：外层 → 内层（越往内越稳定、越抽象）
```

**关键设计要点**：

| 要点 | 说明 |
|------|------|
| 依赖规则 | 源码层面的依赖只能从外圈指向内圈，内圈完全不知道外圈的存在 |
| 跨边界调用 | 内层通过依赖倒置（DIP）定义接口，外层提供实现 |
| 实体层（Entities） | 封装企业级通用业务规则，最稳定最不容易变化 |
| 用例层（Use Cases） | 封装应用级业务规则，编排实体完成业务场景 |
| 接口适配器层 | 将用例层/实体层的数据格式转换为外层需要的格式（Controller、Presenter、Gateway） |
| 框架与驱动层 | 数据库、Web 框架、UI 等，是细节而非核心，应可替换 |
| 可测试性 | 核心业务逻辑不依赖任何外部组件，可独立进行单元测试 |

**与前身架构的关系**：Clean Architecture 是对 Hexagonal Architecture、Onion Architecture、Screaming Architecture、DCI 等思想的统一归纳，它们的共同点是都强调"依赖方向由外向内"。

> 参考资源：[Robert C. Martin 原文](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)

---

#### 9.2.2 Hexagonal Architecture（六边形架构 / 端口与适配器）

> 提出者：Alistair Cockburn，2005 年

**核心思想**：创建可以在没有 UI 和数据库的情况下运行的应用程序，使其能被自动化回归测试驱动、在数据库不可用时仍能工作、并在无需用户介入的情况下与其他应用集成。

**关键洞察**：用户界面侧和数据源侧的问题本质相同——都是业务逻辑与外部实体的纠缠。真正的对称性不是"左右"之分，而是"内外"之分。代码属于"内部"的部分不应泄漏到"外部"。

**架构模型**：

```
          ┌─────────────┐
          │   Adapter    │  自动化测试
          │  (FIT/FitNesse)
          └──────┬───────┘
                 │
┌───────────┐   ┌┴──────────────┐   ┌───────────┐
│  Adapter  │   │               │   │  Adapter  │
│  (HTTP)   ├───┤   Application ├───┤  (SQL DB) │
│           │   │   (Ports)     │   │           │
└───────────┘   │               │   └───────────┘
                └───────┬───────┘
┌───────────┐          │          ┌───────────┐
│  Adapter  │          │          │  Adapter  │
│  (GUI)    ├───┘          └───┤  (Mock DB)│
│           │                     │           │
└───────────┘                     └───────────┘
```

**关键设计要点**：

| 要点 | 说明 |
|------|------|
| 端口（Port） | 定义应用与外部世界对话的目的和协议，以 API 形式表达 |
| 适配器（Adapter） | 将外部技术特定的信号转换为端口 API 所需的调用，反之亦然 |
| 内外分离 | 应用"内部"只知道端口 API，不知道任何外部技术的存在 |
| 等价对待 | 用户、自动化测试、批处理脚本、远程程序——对应用来说都是等同的外部驱动者 |
| 数据库可替换 | SQL 数据库、扁平文件、内存 Mock 数据库——对应用来说只是同一端口的不同适配器 |
| 可测试性 | 用 FIT/FitNesse 等测试框架驱动端口，配合 Mock 数据库，实现完全隔离测试 |
| 开发顺序 | 先用测试 + Mock 驱动 → 再加 UI → 再接入真实数据库 |

**与分层架构的对比**：传统分层架构的"层线"常被忽视，业务逻辑容易泄漏跨越边界。六边形架构用"内外"替代"上下"的视觉隐喻，强制约束内部代码不泄漏到外部，并允许多于两个端口的情况。

> 参考资源：[Alistair Cockburn 原文](https://alistair.cockburn.us/hexagonal-architecture/)

#### 9.2.3 Domain-Driven Design（领域驱动设计）

> 提出者：Eric Evans，2003 年

**核心思想**：软件的核心是其解决业务问题的能力。大多数软件项目失败不是因为技术选型错误，而是因为没有正确理解业务领域。DDD 提供了一套以业务领域为中心的软件设计方法论。

**两大设计维度**：

```
┌──────────────────────────────────────────────────────────┐
│                    战略设计（Strategic Design）            │
│  解决"领域边界怎么划"的问题                               │
│  ┌────────────────────────────────────────────────────┐  │
│  │  统一语言 → 限界上下文 → 上下文映射 → 子域划分       │  │
│  └────────────────────────────────────────────────────┘  │
├──────────────────────────────────────────────────────────┤
│                    战术设计（Tactical Design）            │
│  解决"模型内部怎么落"的问题                               │
│  ┌────────────────────────────────────────────────────┐  │
│  │  实体 → 值对象 → 聚合 → 仓储 → 领域服务 → 领域事件   │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

**关键设计要点**：

| 要点 | 说明 |
|------|------|
| 统一语言（Ubiquitous Language） | 开发者与业务专家使用同一套术语，代码中的命名与业务概念一一对应 |
| 限界上下文（Bounded Context） | 同一术语在不同上下文中有不同含义，明确边界防止概念混用 |
| 上下文映射（Context Map） | 描述多个限界上下文间的关系模式（防腐层、开放主机服务、共享内核等） |
| 核心域（Core Domain） | 体现业务竞争力的领域，值得投入最优秀的建模资源 |
| 聚合（Aggregate） | 事务一致性边界，外部只能通过聚合根访问 |
| 领域事件（Domain Event） | 表达"领域中已经发生的重要事实"，实现上下文间的异步解耦 |
| 防腐层（Anti-Corruption Layer） | 隔离外部模型对本域模型的污染，保护核心域的纯净性 |

**DDD 成功的关键**：不是技术实现有多精巧，而是团队是否建立了真正有效的统一语言，是否正确识别了核心域和限界上下文。

> 参考资源：《领域驱动设计》Eric Evans / 《Implementing Domain-Driven Design》Vaughn Vernon

#### 9.2.4 CQRS + Event Sourcing（命令查询职责分离 + 事件溯源）

> CQRS 提出者：Greg Young；Martin Fowler 于 2011 年撰文阐述

**CQRS 核心思想**：使用不同的模型来更新信息（Command）和读取信息（Query），而非传统 CRUD 中读写共用同一模型。在复杂领域里，命令和查询共用模型会导致模型过于复杂，哪方面都做不好。

**CQRS 架构模型**：

```
         Command Model              Query Model
        ┌─────────────┐           ┌─────────────┐
  Cmd → │  Write Side  │ → Events → │  Read Side   │ → Queries
        │  (Domain)    │           │  (Projections)│
        │  Aggregate   │           │  Denormalized │
        │  Invariants  │           │  View Models  │
        └──────┬───────┘           └──────┬────────┘
               │                          │
        ┌──────┴───────┐           ┌──────┴────────┐
        │  Write DB    │           │  Read DB      │
        │  (Normalized)│           │  (Optimized)  │
        └──────────────┘           └───────────────┘
```

**Event Sourcing 核心思想**：不存储对象的当前状态，而是存储所有改变状态的事件。系统状态是事件日志的投影，任何时候都可以通过重放事件来重建状态。类似于版本控制系统——commit 日志是事件存储，工作目录是系统状态。

**CQRS 关键设计要点**：

| 要点 | 说明 |
|------|------|
| 读写模型分离 | 命令侧和查询侧使用不同的对象模型，可以运行在不同进程/硬件上 |
| 异步通信 | 命令侧处理完成后通过事件通知查询侧更新，通常采用最终一致性 |
| 独立优化 | 写模型专注于业务规则和一致性，读模型专注于查询性能和展示需求 |
| 独立扩展 | 读写可独立水平扩展，适用于读写负载差异大的场景 |
| 适合复杂领域 | 与 DDD 天然契合，命令侧承载聚合和不变式，查询侧承载各种视图 |
| ⚠️ 谨慎使用 | Martin Fowler 明确警告：CQRS 增加了显著的复杂性，只应在特定限界上下文中使用，不应整个系统使用 |

**Event Sourcing 关键设计要点**：

| 要点 | 说明 |
|------|------|
| 事件即真相 | 事件存储是主要的事实来源，系统状态是派生的 |
| 完整审计 | 事件日志提供了天然的强审计能力 |
| 时间旅行 | 可以重放事件到任意时间点，重建历史状态 |
| 替代历史 | 可以注入假设事件探索"如果"场景 |
| 快照优化 | 为避免每次从头重放，定期构建工作副本快照 |
| ⚠️ 模式与异步无关 | 事件处理不必须是异步的（如本地 Git 操作就是同步的），不要混淆 |
| ⚠️ 事件日志 ≠ 直接访问 | 大多数处理应基于工作副本（projection），只有真正需要事件日志信息的组件才操作日志 |

**CQRS + Event Sourcing 的典型组合**：
- 命令侧使用领域模型 + 聚合 + 事件溯源
- 查询侧使用事件驱动的投影 + 非规范化的读模型
- 两者通过事件总线或消息队列连接

> 参考资源：[Martin Fowler CQRS](https://martinfowler.com/bliki/CQRS.html) / [Martin Fowler Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) / Greg Young 的[经典总结](http://codebetter.com/gregyoung/2010/02/16/cqrs-task-based-uis-event-sourcing-agh/)

#### 9.2.5 Microservices Architecture（微服务架构）

> 提出者：James Lewis & Martin Fowler (ThoughtWorks)，2014 年

**核心思想**：将单一应用程序开发为一组小型服务的方法，每个服务运行在独立进程中，通过轻量级机制（通常是 HTTP API）通信，围绕业务能力构建，可独立部署，去中心化管理。

**九大核心特征**：

| 特征 | 核心设计 |
|------|---------|
| **通过服务组件化** | 服务（而非库）是主要组件化手段；服务可独立替换和升级；远程调用比进程内调用昂贵，但接口更明确 |
| **围绕业务能力组织** | 服务按业务能力划分而非技术层（避免 UI 团队/服务端团队/DB 团队的分割），遵循 Conway's Law |
| **产品而非项目** | 团队对服务的整个生命周期负责（"你构建，你运维"），而非项目制交付后移交 |
| **智能端点与哑管道** | 服务间通过 REST/gRPC 等简单协议通信，避免像 ESB 那样在管道中塞入复杂逻辑；去中心化的智能 |
| **去中心化治理** | 不追求统一技术栈，各团队选择最适合的工具；通过"实战检验的标准"和"强制标准"的平衡来治理 |
| **去中心化数据管理** | 每个服务管理自己的数据库（Database per Service）；接受概念模型的不一致性；通过事件或 API 实现跨服务一致性 |
| **基础设施自动化** | 持续交付流水线；自动化部署；容器化；基础设施即代码 |
| **为失败而设计** | 服务随时可能不可用，需要在调用方实现熔断器、超时、重试、降级等弹性机制 |
| **演进式设计** | 架构不是预先设计的，而是随业务增长逐步拆分演进；遵循"先建单体，后拆服务"的原则 |

**微服务 vs 单体**：

```
单体架构：                          微服务架构：
┌──────────────────────┐           ┌────┐ ┌────┐ ┌────┐
│    ┌──┐  ┌──┐  ┌──┐ │           │ A  │ │ B  │ │ C  │
│    │UI│  │UI│  │UI│ │           └─┬──┘ └─┬──┘ └─┬──┘
│    └──┘  └──┘  └──┘ │             │      │      │
│    ┌──────────────┐  │           ┌─┴──┐ ┌─┴──┐ ┌─┴──┐
│    │  Business    │  │           │ D  │ │ E  │ │ F  │
│    │  Logic       │  │           └──┬─┘ └──┬─┘ └──┬─┘
│    └──────────────┘  │              │      │      │
│    ┌──────────────┐  │           ┌──┴─┐ ┌──┴─┐ ┌──┴─┐
│    │   Database   │  │           │ DB │ │ DB │ │ DB │
│    └──────────────┘  │           └────┘ └────┘ └────┘
└──────────────────────┘
改一处 = 重新部署全部              改一处 = 只部署对应服务
扩展 = 复制整个应用               扩展 = 按需独立扩展每个服务
```

**重要警告**：微服务引入了分布式系统的复杂性（网络延迟、数据一致性、运维复杂度），不是所有系统都适合。Martin Fowler 建议"先构建单体，当你确实需要时再拆分"。

> 参考资源：[Martin Fowler Microservices](https://martinfowler.com/articles/microservices.html)

#### 9.2.6 Event-Driven Architecture（事件驱动架构）

> Martin Fowler 于 2017 年总结的四种事件模式

**核心思想**：事件驱动并非单一模式，而是包含多种不同语义的模式，容易混淆导致设计错误。

**四种事件模式**：

| 模式 | 核心设计 | 优点 | 风险 |
|------|---------|------|------|
| **事件通知（Event Notification）** | 系统发送事件消息通知其他系统发生了变更；源系统不关心响应；事件通常只携带 ID 和链接 | 低耦合，实现简单 | 跨事件的业务流程不显式，难以调试和修改；易将命令伪装成事件（被动攻击性命令） |
| **事件携带状态转移（Event-Carried State Transfer）** | 事件不仅通知变更，还携带变更的详细数据；接收方缓存数据后不再需要回查源系统 | 提高弹性（源系统不可用时仍可工作）；降低延迟；减少源系统查询负载 | 大量数据冗余和副本；接收方维护状态的复杂性增加 |
| **事件溯源（Event Sourcing）** | 不存储当前状态，只存储所有状态变更事件；事件存储是主要事实来源，状态通过重放事件派生 | 完整审计；时间旅行；替代历史；支持 Memory Image | 事件回放依赖外部系统交互时变得复杂；事件 Schema 演化困难；整体复杂度较高 |
| **CQRS** | 读写使用不同的数据结构和模型；常与前三种模式组合使用 | 复杂领域模型简化；读写独立优化和扩展 | 增加系统复杂性，容易被误用 |

**关键区分**：
- 事件通知 ≠ 命令：事件表达"已发生的事实"，命令表达"请执行某操作"
- 事件溯源 ≠ 异步：事件处理可以是同步的（如 Git 本地操作），不要将两者混淆
- 事件溯源 ≠ 直接访问事件日志：大多数处理应基于 projection（工作副本），不是所有组件都需要操作原始事件日志

> 参考资源：[Martin Fowler — What do you mean by "Event-Driven"?](https://martinfowler.com/articles/201701-event-driven.html)

#### 9.2.7 Serverless Architecture（无服务器架构）

**核心思想**：将服务器管理、容量规划、基础设施运维等责任完全交给云平台，开发者只关注业务逻辑代码。Serverless 不是"没有服务器"，而是"不需要管理服务器"。

**两种形态**：

| 形态 | 说明 | 典型服务 |
|------|------|---------|
| **FaaS（函数即服务）** | 将业务逻辑部署为独立函数，由事件触发执行，按调用次数和执行时间计费 | AWS Lambda / Azure Functions / Google Cloud Functions / 阿里云函数计算 |
| **BaaS（后端即服务）** | 将后端能力（认证、存储、数据库、消息推送等）作为托管服务直接使用 | Firebase / AWS Cognito / AWS DynamoDB / Supabase |

**关键设计要点**：

| 要点 | 说明 |
|------|------|
| 事件触发 | 函数由 HTTP 请求、队列消息、定时器、数据库变更等事件触发，而非常驻进程 |
| 按需计费 | 只在函数执行时计费，空闲时不产生费用；适合突发性、间歇性负载 |
| 自动伸缩 | 平台根据请求量自动扩缩容，无需手动配置 |
| 无状态 | 每次函数调用都是独立的，不依赖前一次调用的内存状态 |
| 冷启动 | 函数首次调用或长时间空闲后需要初始化运行环境，造成延迟 |
| 执行时长限制 | 单次函数执行有时间上限（如 AWS Lambda 最长 15 分钟），不适合长时间运行任务 |
| 碎片化编排 | 复杂业务流程需要通过 Step Functions / 工作流引擎编排多个函数 |
| 供应商锁定 | 深度使用特定云平台的 FaaS + BaaS 后，迁移成本很高 |

**适用场景**：
- ✅ API 后端、数据处理管道、定时任务、事件响应、IoT 数据处理
- ❌ 长时间运行任务、需要保持状态的服务、低延迟要求的实时系统

> 参考资源：[AWS Serverless](https://aws.amazon.com/serverless/) / [Serverless Framework](https://www.serverless.com/)

### 9.3 架构设计原则

| 原则 | 说明 |
|------|------|
| **SOLID** | SRP(职责单一) / OCP(开闭) / LSP(里氏替换) / ISP(接口隔离) / DIP(依赖倒置) |
| **DRY** | Don't Repeat Yourself — 不重复，抽象共性 |
| **KISS** | Keep It Simple, Stupid — 保持简单 |
| **YAGNI** | You Ain't Gonna Need It — 避免过度设计 |
| **SoC** | Separation of Concerns — 关注点分离 |
| **LoD** | Law of Demeter — 迪米特法则（最少知识原则）|
| **CQS** | Command-Query Separation — 命令查询分离 |
| **CoC** | Convention over Configuration — 惯例优于配置 |
| **Hollywood Principle** | "Don't call us, we'll call you" — IoC/DI 的基础 |
| **High Cohesion & Low Coupling** | 高内聚，低耦合 |

## 十、代码设计规范

### 10.1 国际大厂编码风格指南

> 以下为国际主流编码风格指南的核心要点提取，各规范的完整内容请参考官方链接。

#### 10.1.1 Google Style Guides

> **官方来源**：[google.github.io/styleguide](https://google.github.io/styleguide/) | **中文翻译**：[zh-google-styleguide.readthedocs.io](https://zh-google-styleguide.readthedocs.io/)
> 覆盖 C++/Java/Python/JavaScript/TypeScript/Go/R/Shell/Swift 等 16 种语言。

##### Google Java Style Guide 核心要点

**命名规范**

| 标识符类型 | 命名风格 | 示例 | 说明 |
|---|---|---|---|
| 包名 (Package) | 全小写，无下划线 | `com.example.deepspace` | 连续单词直接连接 |
| 类名/接口名/枚举名 | **UpperCamelCase** | `Character`, `ImmutableList` | 通常是名词或名词短语；测试类以 `Test` 结尾 |
| 方法名 | **lowerCamelCase** | `sendMessage`, `stop` | 通常是动词或动词短语 |
| 常量字段名 | **UPPER_SNAKE_CASE** | `NUMBER`, `COMMA_JOINER` | 必须是 `static final` 且**深度不可变** |
| 非常量字段名 | **lowerCamelCase** | `computedValues`, `index` | 无论是否 static，均为小驼峰 |
| 参数名/局部变量名 | **lowerCamelCase** | — | 公共方法中避免单字符参数名 |
| 类型变量 (泛型) | 单个大写字母或 UpperCamelCase+T | `E`, `T`, `RequestT` | 两种形式均可 |

**驼峰命名转换规则**：缩略词视为普通单词整体小写 → `XmlHttpRequest` ✅ `XMLHTTPRequest` ❌ | `newCustomerId` ✅ `newCustomerID` ❌ | `supportsIpv6OnIos` ✅

**格式/排版规范**

| 规则项 | 要求 |
|---|---|
| 花括号 | if/else/for/do/while **必须使用花括号**，即使体为空或单语句 |
| 花括号风格 | **K&R 风格**（埃及括号）：左括号不换行，右括号独占一行 |
| 缩进 | **每次 +2 空格**，不使用 Tab |
| 列限制 | **100 字符**（Unicode 码位计数） |
| 换行缩进 | 续行至少 **+4 空格** |
| 换行位置 | 非赋值运算符前断行；赋值运算符后断行 |
| 导入语句 | **禁止通配符导入** (`import x.*`)；先静态导入组，再非静态导入组；组内 ASCII 排序 |
| 源文件结构 | ①版权信息 → ②package 声明 → ③imports → ④唯一顶级类声明 |
| switch | 必须有 `default` 标签；fall-through 必须注释说明 |
| 水平对齐 | **永远不要求**用变长空格来对齐变量声明 |

**编程实践**

| 规则项 | 要求 |
|---|---|
| @Override | **始终使用**——覆盖或实现方法时必须标注 |
| 异常处理 | **捕获的异常不能被忽略**（空 catch 是错误的）；至少记录日志或重新抛出 |
| 静态成员访问 | 使用**类名限定**而非对象引用 |
| 文件编码 | UTF-8 |

> ⚠️ **特别注意**：常量定义非常严格——必须是 `static final` + 深度不可变；`Logger` 和可变集合即使声明为 `static final` 也**不算常量**。每个源文件只有一个顶级类。

#### 10.1.2 PEP 8 — Python 编码规范

> **官方来源**：[peps.python.org/pep-0008](https://peps.python.org/pep-0008/) | **中文翻译**：[pythoncjh.cn/PEP8](https://pythoncjh.cn/PEP8/)

**代码布局**

| 规则项 | 要求 |
|---|---|
| 缩进 | 使用 4 个空格，不使用 Tab；续行使用悬挂缩进或与分隔符对齐 |
| 最大行长度 | 代码 79 字符；docstring/注释 72 字符（团队可放宽到 99/100） |
| 换行与二元运算符 | 在二元运算符**之前**换行（Donald Knuth 风格） |
| 空行 | 顶级函数和类定义之间空 2 行；类内方法之间空 1 行 |
| 源文件编码 | 使用 UTF-8（Python 3 默认，无需声明） |

**导入规范**

- 每个 `import` 独占一行
- 顺序（用空行分隔）：标准库 → 第三方库 → 本地库
- 推荐**绝对导入**；同包内可使用显式相对导入 `from . import xxx`
- 避免 `from module import *`（通配符导入）

**命名约定**

| 类型 | 约定 |
|---|---|
| 模块/包 | `lower_snake_case` |
| 类 | `CapWords` (PascalCase) |
| 异常 | `CapWords` + `Error` 后缀 |
| 函数/变量/方法 | `lower_snake_case` |
| 常量 | `UPPER_SNAKE_CASE` |
| 类型变量 | `CapWords`，短名如 `T`, `AnyStr` |
| 内部使用 | 前缀 `_single_underscore` |
| 避免关键字冲突 | 后缀 `trailing_underscore_` |

**编程建议**

- 与 `None` 比较用 `is` / `is not`，不用 `==`
- 布尔值比较：`if greeting:` 而非 `if greeting == True:`
- 异常使用 `raise X from Y`；捕获尽量具体，避免裸 `except:`
- 不用 `lambda` 赋值给标识符（改用 `def`）
- 字符串拼接用 `''.join()` 而非 `+=` 循环
- 类型检查用 `isinstance(obj, cls)` 而非 `type(obj) == cls`

#### 10.1.3 Airbnb JavaScript Style Guide

**核心规则摘要**

| **迭代器** | 避免 `for-in` / `for-of`；优先用 `map`/`filter`/`reduce`/`every`/`some` |
| **空白** | 2 空格缩进；大括号前空格；文件末尾留空行 |

#### 10.1.4 Rust API Guidelines

> **官方来源**：[rust-lang.github.io/api-guidelines](https://rust-lang.github.io/api-guidelines/)

**命名 (Naming)**

| 类型 | 命名风格 | 示例 |
|---|---|---|

- 所有公共项必须有 rustdoc 文档；文档示例可编译通过
- 函数使用泛型或 trait 对象接受广泛输入（`&str` / `AsRef<str>` / `impl Display`）

### 10.2 国内大厂编码规范

**命名规约（强制）**

| 规则 | 说明 |
|---|---|

**OOP 规约（强制）**

| 规则 | 说明 |
|---|---|
| 避免 through 一个类的引用来访问类的静态变量或方法 | 用类名访问，无谓增加编译器解析成本 |

**注释规约（强制）**

| 规则 | 说明 |
|---|---|

##### MySQL 数据库规约（强制）

| 规则 | 说明 |
|---|---|
| 表达是与否概念的字段使用 `is_xxx` 命名 | 数据类型是 unsigned tinyint（1 是 / 0 否） |
| 表名、字段名**必须使用小写字母或数字** | 单词间用下划线 `_` 连接 |
| 表名不使用复数名词 | `user` 而非 `users` |
| 禁用保留字 | 如 `desc`、`range`、`match`、`delayed` 等 |
| 小数类型使用 **decimal** | 禁止使用 float 和 double（精度丢失） |
| `varchar` 长度按需分配 | 不统一分配过大长度 |
| 单表行数超过 500 万行或单表容量超过 2 GB | 推荐分库分表 |

##### 工程结构规约

| 规则 | 说明 |
|---|---|

| 二方库版本号命名 | `主版本号.次版本号.修订号`：主版本号不兼容 API 变更；次版本号可兼容功能新增；修订号兼容 BugFix |
| 线上应用不要依赖 SNAPSHOT 版本 | 不安全且不稳定 |

### 10.4 Clean Code（代码整洁之道）核心要点

> 依据 Robert C. Martin（Uncle Bob）*Clean Code: A Handbook of Agile Software Craftsmanship*（2008）整理。
> 全书共 17 章，涵盖从命名、函数、注释、格式到类设计、系统架构、并发编程和逐步改进的完整方法论。

#### 10.4.1 有意义的命名（第 2 章）

| 原则 | 说明 | 示例 |
|------|------|------|
| **名副其实** | 名称应该告诉读者：为什么存在、做什么、怎么用 | `const currentDate = moment().format("YYYY/MM/DD")` ✅ vs `yyyymmdstr` ❌ |
| **避免误导** | 避免使用与公认含义不同的词；避免小写 `l`/大写 `O` 等易混淆字符 | `accountList` 若实际不是 List 则误导 ❌ |
| **做有意义的区分** | 如果名称必须不同，其含义也应不同；避免用数字系列命名（a1, a2） | `getActiveAccount()` / `getInactiveAccount()` ✅ vs `getData1()` / `getData2()` ❌ |
| **使用可读的名称** | 便于搜索；避免魔法数字 | `const MILLISECONDS_PER_DAY = 86400000` ✅ vs 直接写 `86400000` ❌ |
| **使用可发音的名称** | 方便团队成员口头讨论 | `genymdhms`（不可读）❌ → `generationTimestamp` ✅ |
| **避免双关** | 一个词一个含义，同一概念统一术语 | `getUserInfo()` / `getClientData()` / `getCustomerRecord()`（同一概念多种词）❌ → 统一为 `getUser()` ✅ |
| **添加有意义的上下文** | 给名称提供足够语境，但不要加不必要的上下文 | 类 `Car` 中字段无需 `car` 前缀：`make`/`model` ✅ vs `carMake`/`carModel` ❌ |

#### 10.4.2 函数设计原则（第 3 章）

| 原则 | 说明 | 要点 |
|------|------|------|
| **短小** | 函数的第一规则是要短小，第二规则是还要更短 | 函数体应在 20 行以内，理想情况不超过 10 行 |
| **只做一件事** | 函数应该做一件事、做好这件事、只做这一件事 | 判断方法：能否在函数中再提取出一个函数且不破坏原函数语义？如果能，说明做了多件事 |
| **每个函数一个抽象层级** | 函数内的语句应在同一抽象层次上；自顶向下读代码（向下规则） | 高层步骤调用低层函数，形成清晰的抽象层次 |
| **switch 语句** | switch 天然地做 N 件事，应 buried deep in low-level class 且不被复用 | 用多态替代 switch（见 OCP 原则） |
| **描述性的名称** | 函数名要能描述它做的事；名字长一点没关系，只要清晰 | `includeSetupPageInto(newPage)` 比 `inclPage(p)` 更好 |
| **参数越少越好** | 最理想是零参数，其次是一参数，尽量避免三参数及以上 | 多参数时考虑封装为对象（参数对象模式）；标志位参数尤其应禁止 |
| **无副作用** | 函数承诺做一件事但暗地里做了其他事（如修改全局变量、操作入参对象），就是副作用 | 避免在 getter 中修改状态；输出参数比输入参数更危险 |
| **指令与询问分离（CQS）** | 函数要么做什么事（命令），要么回答什么事（查询），不可两者兼之 | `if (setAttribute("name", "value"))` 混合了设置和判断 ❌ |
| **错误处理是一件事** | 当错误处理是函数唯一要做的事时，函数本身还是只做了一件事 | try/catch 独立成一个函数 |
| **别重复自己（DRY）** | 重复是软件中一切邪恶的根源 | 代码重复、结构重复、逻辑重复都应消除 |

#### 10.4.3 注释原则（第 4 章）

**好注释的价值**：好的注释可以弥补代码未能表达意图时的不足。但优先级永远是：**让代码自己说话 > 必要时才加注释**。

| 应该写的注释 | 不应该写的注释（坏注释） |
|------------|------------------|
| 法律信息（版权、作者等） | 自言自语式的废话（`i++ // i 加 1`） |
| 提供信息的注释（如解释正则的含义） | 冗余注释（代码已说清楚的事再注释一遍） |
| 对意图的解释（为什么这样做而非做了什么） | 误导性注释（与代码行为不一致——比没注释更糟） |
| 阐释（将晦涩的参数/返回值翻译成人话） | 强制性注释（每个函数都必须有 Javadoc 的规定） |
| 警示（如 TODO/FIXME/HACK 标记重要风险） | 日志式注释（记录每次修改——这是版本控制的工作） |
| 公共 API 的 Javadoc/Docstring | 位置标记（`// Actions /////////////////////////`） |
| **最重要的注释**：用好命名和代码结构来减少注释需求 | 注释掉的代码（直接删除即可，Git 会保留历史） |

#### 10.4.4 格式规范（第 5 章）

| 维度 | 规范 |
|------|------|
| **垂直格式** | 文件应短小，通常不超过 500 行；源文件如同报纸文章：高层概念在顶部，细节逐层向下展开 |
| **垂直密度** | 密切相关的代码应相互靠近；变量声明应尽可能靠近使用位置 |
| **垂直距离** | 变量声明靠近使用；实例变量在类顶部声明；相关函数垂直放在一起；调用者尽量在被调用者上方 |
| **水平格式** | 行应短小，避免超过 120 个字符；行宽不必严格一致，但要体现分组和层次关系 |
| **缩进** | 源文件的缩进展现作用域层次，绝不忽略缩进；团队统一缩进风格（空格数或 Tab） |
| **空白区** | 赋值运算符周围加空格增强可读性；函数名与左括号之间不加空格（表示绑定关系） |
| **团队规则** | 团队必须遵守同一种格式规范；使用自动化工具（formatter/linter）强制执行 |

#### 10.4.5 对象与数据结构（第 6 章）

| 概念 | 说明 | 示例 / 要点 |
|------|------|-------------|
| **数据抽象** | 隐藏实现并非仅仅是在变量上放置 `private`；真正的抽象是以接口暴露行为而非数据 | 使用 getters/setters 提供对私有字段的受控访问 |
| **数据/对象不对称性** | 数据结构暴露数据、没有有意义的行为；对象隐藏数据、暴露行为 | 过程式代码（使用数据结构）易于在不改变现有数据结构的前提下添加新函数；面向对象代码（使用对象）易于在不改变现有函数的前提下添加新类 |
| **得墨忒耳定律（LoD）** | 模块不应了解它所操作对象的内部情形；最少知识原则 | `a.getB().getC().doSomething()` 违反 LoD ❌ → 让 A 委托给 B 来完成 ✅ |
| **数据传输对象（DTO）** | 只有公共变量、没有行为的纯数据类（如 Java Bean） | DTO 在应用各层之间传输数据时非常有用 |

#### 10.4.6 错误处理（第 7 章）

| 原则 | 说明 |
|------|------|
| **使用异常而非返回码** | 返回码违反了指令与询问分离；返回码迫使调用方立即处理错误，打断了正常流程 |
| **先写 Try-Catch-Finally 语句** | TDD 中先写异常路径测试，确保异常被正确处理后再编写正常逻辑 |
| **给出异常上下文** | 异常消息应包含导致失败的操作及失败类型，便于诊断 |
| **依需定义异常类** | 第三方库定义的异常通常不够具体；根据调用者的需要定义特定异常类 |
| **特殊模式替代 null** | 不要返回 null 值（会导致 NPE 风险传播），也不要传递 null 参数；可抛出异常或返回空集合/特例对象（Null Object Pattern）替代 null |


#### 10.4.7 边界（第 8 章）

| 原则 | 说明 |
|------|------|
| **使用第三方代码** | 学习性测试：通过编写测试来学习第三方 API 的行为和边界 |
| **探索和学习边界** | 不要过度深入第三方代码内部；通过适配器/门面隔离第三方 API |
| **学习性测试不只是免费测试** | 它是对 API 的验证性理解，确保你对 API 的假设正确 |
| **干净边界** | 边界上的代码应有清晰的分隔和合理的接口；避免系统代码过多依赖第三方 API |
| **Adapter 模式** | 用适配器将第三方 API 转换为符合自身系统风格的接口 |

#### 10.4.8 单元测试（第 9 章）

| 原则 | 说明 |
|------|------|
| **TDD 三定律** | ① 编写失败单元测试前不可编写生产代码 ② 只可编写刚好无法通过的单元测试（编译失败也算）③ 只可编写刚好能使当前失败测试通过的代码 |
| **保持测试整洁** | 测试代码和生产代码同等重要，甚至更重要——测试保证生产代码的可扩展性 |
| **F.I.R.S.T 规则** | **F**ast（快速）、**I**ndependent（独立）、**R**epeatable（可重复）、**S**elf-Validating（自验证）、**T**imely（及时） |
| **每个测试一个断言** | 每个测试函数只验证一个概念，保持测试意图清晰 |
| **测试的 readability** | 测试的可读性比生产代码还重要；测试应像良好文档一样表达意图 |

#### 10.4.9 类设计（第 10 章）

| 原则 | 说明 |
|------|------|
| **类应该短小** | 类的度量方式是**职责**——计算类的职责数量；SRP 要求类或模块应有且只有一个修改的理由 |
| **内聚性** | 类中的方法和变量相互依赖、紧密结合的程度；保持高内聚 |
| **保持变更隔离** | 类的修改应只影响最小范围；大的类往往意味着多个修改原因 |
| **OCP（开闭原则）** | 类应对扩展开放，对修改关闭；通过抽象和多态实现 |
| **DIP（依赖倒置原则）** | 依赖抽象而不依赖具体实现；高层模块不应依赖低层模块 |

#### 10.4.10 系统设计（第 11 章）

| 原则 | 说明 |
|------|------|
| **构造与使用分离** | 应用的启动过程（构造）与运行逻辑（使用）应分离；依赖注入是实现手段之一 |
| **面向切面编程（AOP）** | 将横切关注点（日志、安全、事务）从业务逻辑中剥离为独立的切面 |
| **放大设计的重要性** | 系统架构应讲清楚“做什么”，而非“怎么做”；架构应像故事一样可理解 |
| **使用标准** | 没有标准就自己发明——但优先使用已有的成熟方案（如 Spring、JPA 等） |
| **系统需要领域特定语言（DSL）** | 架构应允许用接近业务语言的方式表达逻辑 |

#### 10.4.11 迭进 / 逐步改进（第 12 章）

| 原则 | 说明 |
|------|------|
| **通过重构达到整洁** | 整洁不是一开始就能做到的，而是通过持续重构逐步逼近的 |
| **简单设计四规则** | ① 通过所有测试 ② 消除重复 ③ 表达程序员意图 ④ 保持类和方法精简 |
| **意图明确** | 代码应清晰表达作者的意图；命名是第一手段，必要时辅以注释 |
| **减少重复到极致** | 重复不仅是代码层面的，还包括结构重复和逻辑重复；模板方法模式和策略模式常用于消除重复 |
| **保持简洁** | 代码行数、函数数量、类数量都应尽可能少；但不是以牺牲可读性为代价 |

#### 10.4.12 并发编程（第 13 章）

| 原则 | 说明 |
|------|------|
| **并发防御原则** | 并发代码缺陷往往是偶发的、难以复现的；必须从设计层面防御 |
| **SRP 在并发中的体现** | 并发本身就是一个独立的修改理由——并发相关代码应与其他业务代码分离 |
| **数据独立性** | 共享数据是并发问题的根源；尽可能不共享可变数据 |
| **警惕同步方法之间的依赖** | 同步方法之间如果存在依赖，可能导致死锁或其他难以发现的问题 |
| **保持同步区域微小** | synchronized 块或锁的范围应尽可能小，减少持有锁的时间 |
| **已知问题** | 竞态条件、死锁、活锁、饥饿等经典并发问题 |

### 10.5 Refactoring（重构）核心要点

> 依据 Martin Fowler *Refactoring: Improving the Design of Existing Code*（1999 第 1 版 / 2018 第 2 版）及 Refactoring.Guru 网站整理。
> 重构是在**不改变软件可观察行为**的前提下，改善其内部结构的过程。

#### 10.5.1 什么是重构

| 维度 | 说明 |
|------|------|
| **定义** | 对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高其可理解性、降低其修改成本 |
| **核心特征** | 重构不改功能——这是重构与重写/重新设计的本质区别 |
| **为什么重构** | 修复 Bug 时更易定位、添加功能时更易理解、Code Review 更高效、提升长期开发速度 |
| **何时重构** | ③添加功能时 ④修 Bug 时 ⑤Code Review 时 |
| **何时不重构** | 代码太混乱不如重写时、临近发布 deadline 时 |
| **重构步骤** | ① 建立可靠的测试集 ② 小步修改 ③ 每步后运行测试确认无回归 |

#### 10.5.2 Code Smells（代码异味）完整目录

Refactoring.Guru 将代码异味分为 **6 大类别**，共 **25 种**常见异味：

##### Bloaters（臃肿）— 代码体量过大或过于复杂

| 异味名称 | 英文名 | 描述 | 典型解决方案 |
|----------|--------|------|-------------|
| **长方法** | Long Method | 方法过长，包含太多逻辑，难以理解和维护 | Extract Method / Replace Temp with Query / Substitute Algorithm |
| **大类** | Large Class | 类承担了过多职责，变得庞大难懂 | Extract Class / Extract Subclass / Extract Interface |
| **原始类型偏执** | Primitive Obsession | 使用基本类型（int, string）而非有意义的对象来表示概念 | Replace Type Code with Class / Replace Type Code with Subclasses / Replace Array with Object |
| **长参数列表** | Long Parameter List | 方法参数超过 3 个，调用困难且难以记忆 | Introduce Parameter Object / Preserve Whole Object / Replace Parameter with Method Call |
| **数据泥团** | Data Clumps | 一组数据项总是同时出现在多个地方（如 x, y 坐标） | Extract Class / Introduce Parameter Object / Replace Array with Object |

##### Object-Orientation Abusers（面向对象滥用）— 未充分利用面向对象特性

| 异味名称 | 英文名 | 描述 | 典型解决方案 |
|----------|--------|------|-------------|
| **Switch 语句** | Switch Statements | 复杂的 switch/if-else 链散布在多处，新增类型需修改多处 | Replace Conditional with Polymorphism / Replace Type Code with State/Strategy |
| **临时字段** | Temporary Field | 类中某些字段只在特定情况下被使用，其余时间为 null/null | Extract Class / Replace Method with Method Object |
| **被拒绝的遗赠** | Refused Bequest | 子类继承了父类的行为和数据，却只使用了其中一部分 | Replace Inheritance with Delegation / Push Down Method/Field |
| **替代类的不同接口** | Alternative Classes with Different Interfaces | 不同类做相似的事，但接口不同（如 `get()` vs `fetch()`） | Rename Method / Move Method / Extract Interface |

##### Change Preventers（变更阻碍者）— 修改一处需要同时修改多处

| 异味名称 | 英文名 | 描述 | 典型解决方案 |
|----------|--------|------|-------------|
| **发散式变化** | Divergent Change | 一个类因多种不同原因而被修改（如数据库格式变了改一次、XML 格式变了又改一次） | Extract Class — 将不同变化方向拆分到不同类 |
| **霰弹式手术** | Shotgun Surgery | 一种变化需要在多个完全不相关的类中进行修改（发散式的反面） | Move Method / Move Field / Inline Class |
| **平行继承体系** | Parallel Inheritance Hierarchies | 每当为某个类创建子类时，就必须为另一个类也创建子类 | Merge Hierarchy / Collapse Hierarchy |

##### Dispensables（可有可无）— 代码冗余或不必要

| 异味名称 | 英文名 | 描述 | 典型解决方案 |
|----------|--------|------|-------------|
| **注释** | Comments | 函数/代码块需要大量注释才能让人理解——说明代码本身不够清晰 | Extract Method / Rename Method / Replace Method with Method Object（注释本身不是异味，但可能是其他异味的信号） |
| **重复代码** | Duplicate Code | 相同或高度相似的代码结构出现在多个位置 | Extract Method / Extract Class / Pull Up Method / Template Method |
| **懒类** | Lazy Class | 类承担的工作太少，存在的价值不足以抵消维护成本 | Inline Class / Collapse Hierarchy |
| **数据类** | Data Class | 只有 getter/setter 字段、没有任何行为的贫血类 | Encapsulate Field / Move Method / Extract Method |
| **死代码** | Dead Code | 不被任何地方调用的代码（未使用的变量、方法、类） | 直接删除 |
| **推测性泛化** | Speculative Generality | 设计了“以防万一”将来可能用到但目前从未使用的抽象 | Collapse Hierarchy / Inline Class / Remove Parameter |

##### Couplers（耦合）— 过度依赖

| 异味名称 | 英文名 | 描述 | 典型解决方案 |
|----------|--------|------|-------------|
| **特性依恋** | Feature Envy | 一个方法的实现大量调用另一个对象的属性和方法（它更想属于那个对象） | Move Method / Extract Method |
| **不当亲密** | Inappropriate Intimacy | 一个类过度深入另一个类的内部，依赖其私有细节 | Move Method / Change Bidirectional to Unidirectional / Hide Delegate |
| **消息链** | Message Chains | 客户端代码需要一长串的 getThis().getThat() 调用来获取所需对象 | Hide Delegate / Extract Method |
| **中间人** | Middle Man | 一个类的大部分方法只是委托给另一个类，自身没有实质行为 | Remove Middle Man / Inline Class / Replace Delegation with Inheritance |

##### Other Smells（其他异味）

| 异味名称 | 英文名 | 描述 | 典型解决方案 |
|----------|--------|------|-------------|
| **不完整的库类** | Incomplete Library Class | 无法修改的第三方库类缺少你需要的方法 | Introduce Foreign Method / Introduce Local Extension |

| 以方法对象取代方法 | Replace Method with Method Object | 将大方法提取为独立的方法对象 |

#### 10.5.4 重构时机

| 场景 | 是否适合重构 | 说明 |
|------|-----------|------|
| **添加新功能时** | ✅ 最佳时机 | 理解现有代码的同时顺便改善结构 |
| **修复 Bug 时** | ✅ 最佳时机 | Bug 往往暗示着代码结构有问题 |
| **Code Review 时** | ✅ 最佳时机 | 同伴评审能发现个人盲点 |
| **性能优化前** | ✅ 推荐先重构 | 清晰的结构更容易找到性能瓶颈 |
| **临近发布 Deadline** | ❌ 不建议 | 重构引入风险，此时应以稳定为主 |
| **代码完全无法理解** | ⚠️ 谨慎评估 | 可能需要重写而非重构 |
| **日常开发习惯** | ✅ 推荐 | "两顶帽子"：写代码时不重构，重构时不写功能 |

### 10.6 clean-code-javascript 核心原则

> 依据 [ryanmcdermott/clean-code-javascript](https://github.com/ryanmcdermott/clean-code-javascript)（90k+ Stars）整理。
> 这是《Clean Code》在 JavaScript/TypeScript 社区的实践指南，覆盖变量、函数、对象、类、SOLID 等方面。

#### 10.6.1 变量（Variables）

| 原则 | 反例 → 正例 |
|------|------------|
| **使用有意义的、可读的名字** | `yyyymmdstr` → `currentDate` |
| **同一概念统一术语** | `getUserInfo()` / `getClientData()` / `getCustomerRecord()` → 统一为 `getUser()` |
| **使用可搜索的命名（避免魔法数字）** | `setTimeout(blastOff, 86400000)` → `const MILLISECONDS_PER_DAY = 86400000; setTimeout(blastOff, MILLISECONDS_PER_DAY)` |
| **使用可解释的变量** | 多次调用 `address.match(regex)[N]` → 解构为 `[_, city, zipCode]` 后使用 |
| **避免不明确的映射** | `.forEach(l => { ... })` 中 `l` 含义不明 → 改为 `location` |
| **不添加不必要的上下文** | `Car` 类中 `carMake` / `carModel` → `make` / `model` |
| **使用默认参数代替 `||` 运算符** | `const name = name || "default"` → `function(name = "default")` |

#### 10.6.2 函数（Functions）

| 原则 | 要点 |
|------|------|
| **参数尽量少于两个** | 超过 2 个参数时应考虑使用对象解构 `{ title, body, buttonText }` 作为参数 |
| **只做一件事** | 如果需要从函数内再提取出另一个函数，说明原函数做了不止一件事 |
| **函数名要说明它做什么** | `addToDate(date, month)` 含义模糊 → `addMonthToDate(month, date)` |
| **每个函数一层抽象** | 大函数应拆分为高层调用 + 底层实现的层次结构 |
| **移除重复代码** | `showDeveloperList` 和 `showManagerList` 高度相似 → 统一为 `showEmployeeList` + switch 类型 |
| **使用 Object.assign 设置默认对象** | 避免逐个字段设置默认值的冗长代码 |
| **不要使用标志位作为参数** | `createFile(name, temp)` 有 flag → 拆分为 `createFile(name)` + `createTempFile(name)` |
| **避免副作用** | 不要修改全局变量、不要修改传入的对象参数（应返回新对象） |
| **不要改变全局函数** | 不要扩展 `Array.prototype` 等原生原型链 → 使用 class 继承替代 |
| **偏好函数式编程** | 用 `reduce`/`map`/`filter` 替代 for 循环 + 临时变量 |
| **封装条件判断** | `if (fsm.state === "fetching" && isEmpty(listNode))` → 提取为 `shouldShowSpinner(fsm, listNode)` |
| **避免负向条件判断** | `if (!isDOMNodeNotPresent(node))` → `if (isDOMNodePresent(node))` |
| **避免条件判断（用多态替代）** | 类中的 switch/type 判断 → 用子类/策略模式替代 |
| **避免类型检查（instanceof / typeof）** | 应利用多态和鸭子类型，让代码自然处理不同类型 |
| **不要过度优化** | 现代浏览器已做了大量优化，不必手动缓存 `list.length` 等微优化 |
| **移除不使用的代码** | 死代码会制造混淆，直接删除即可（Git 保留历史） |

#### 10.6.3 对象和数据结构

| 原则 | 要点 |
|------|------|
| **使用 getters 和 setters** | 通过闭包或 `#private` 实现私有字段，暴露受控的 getter/setter |
| **让对象拥有私有成员** | 使用工厂函数（Factory Function）而非 `class` + `this` 来创建真正私有的状态 |

#### 10.6.4 类（Classes）

| 原则 | 要点 |
|------|------|
| **使用 ES2015/ES6 classes** | 替代 ES5 的 function 构造 + prototype 继承方式 |
| **支持链式调用** | setter 方法返回 `this`，使 API 可流畅链式调用 |
| **"has-a" 关系使用复合** | EmployeeTaxData 不应 extends Employee（不是一种员工），而应在 Employee 中组合 TaxData |

#### 10.6.5 SOLID 原则在 JavaScript 中的实践

| 原则 | JavaScript 实践要点 |
|------|------------------|
| **SRP（单一职责）** | `UserSettings` 不应包含 `verifyCredentials()` → 拆分为 `UserAuth` + `UserSettings` |
| **OCP（开闭原则）** | 新增 Adapter 类型时不应修改 `HttpRequester.fetch()` 的 if-else → 用多态/注册机制开放扩展 |
| **LSP（里氏替换）** | 子类应能完美替代父类而不破坏程序语义 |
| **ISP（接口隔离）** | JS 中可用小粒度的对象/Mixin 替代庞大的接口 |
| **DIP（依赖倒置）** | 高层模块不应依赖低层模块的具体实现，依赖注入（DI）容器是实现手段 |

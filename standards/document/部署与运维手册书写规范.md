# 部署与运维手册书写规范

> 部署与运维手册回答 **"如何把系统安全地部署出去、稳定地运行起来、在出问题时快速止血并恢复"**。  
> 它位于设计、开发、测试之后，是工程交付真正进入运行态的桥梁——把版本、环境、配置、监控、回滚、应急、维护这些运行事实固定下来。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)  
> 架构输入见 → [架构设计书写规范](架构设计书写规范.md)  
> 上线门禁与签收裁决见 → [验收文档书写规范](验收文档书写规范.md)

## 一、部署与运维手册的目标

部署与运维手册的核心目标，不是“把几个命令记下来”，而是**让没有参与过项目开发的人，也能基于手册独立完成部署、巡检、回滚、故障处置和日常维护**。

一个合格的部署与运维手册，至少要解决八个核心问题：

1. **部署对象是什么**：本次要部署哪些服务、脚本、任务、配置、数据库变更
2. **部署前提是什么**：环境、权限、依赖、变更窗口、发布门禁是否满足
3. **怎么部署**：按什么顺序执行、每一步做什么、做完如何验证
4. **怎么运行**：服务正常运行时应该看哪些指标、日志、Dashboard、健康检查
5. **怎么回滚**：触发条件是什么、回滚步骤是什么、数据兼容性如何保证
6. **怎么应急**：发生故障时谁负责、如何升级、如何止血、如何恢复、如何复盘
7. **怎么维护**：日常巡检、证书续期、容量扩缩、任务重跑、依赖升级如何处理
8. **证据在哪里**：版本、配置、告警、发布记录、值班记录、变更记录如何追溯

> **部署与运维手册的终极检验标准**：一个没有参与过该项目的值班同学，仅凭系统设计文档、发布产物和部署与运维手册，能否独立完成一次标准发布、一次回滚、一次故障止血，并清楚知道风险边界？如果不能，说明手册还不够好。

### 部署与运维文档的分类

部署与运维相关文档通常不是只有一种。工程上至少有四类常见工件：

| 类型 | 作用 | 产出时机 | 回答的问题 |
|------|------|---------|-----------|
| 部署手册 / 发布手册 | 定义“怎么发” | 发布前 | 部署前检查什么、如何部署、如何验证、如何回滚 |
| 运行手册 / Runbook | 定义“怎么跑” | 系统运行期 | 日常巡检看什么、常见操作怎么做、异常如何处理 |
| 应急预案 / 故障手册 | 定义“怎么止血” | 高风险系统必须提前准备 | 故障分级、升级、止血、恢复、沟通、复盘 |
| 维护手册 | 定义“怎么养” | 运行稳定后持续维护 | 证书、备份、扩容、升级、定时任务、依赖维护 |

**经验法则**：
- 小型项目可以把部署、运行、应急合并成一份 `部署与运维手册`
- 中大型项目应拆分为：`部署手册`、`运行手册`、`应急手册`、`值班附录` 四类文档
- 一旦涉及跨环境、数据库迁移、夜间发布、多人值守、灾备切换，**强烈建议拆分**

- 复杂项目不要把所有命令、截图、Dashboard 截图都塞进正文；正文应保留**步骤、判定标准、证据索引**，原始材料放附件或平台链接

- 手册超过 1500 行，或附录命令/截图过多时，建议拆成：`部署手册`、`运行手册`、`应急手册`、`附录索引`

## 四、各模块编写要点

### 4.1 手册的本质：运行态执行文档，不是设计摘要

部署与运维手册最常见的错误，是把它写成：

- “架构设计的复读稿”
- “一些命令的堆砌”
- “只有熟悉系统的人才能看懂的内部黑话备忘录”

这些都不是好的运维手册。

**好的部署与运维手册本质上是运行态执行文档**。它必须支持下面四件事：

1. **执行**：按文档能完成部署、验证、回滚、常见运行操作
2. **判定**：每一步都知道什么叫成功、什么叫失败、失败后怎么走
3. **升级**：知道什么时候找谁、怎么同步、谁拍板、谁承担风险
4. **追溯**：知道这次发布的是哪一版、改了什么、谁执行、谁批准、出了什么问题

> **原则**：任何关键步骤都不能依赖“这个大家都知道”。凡是需要熟人带着操作才能做的事情，都说明手册还没写清楚。

### 4.2 文档元信息与适用范围

**编写要点**：
- 必须标明文档类型：`部署手册`、`运行手册`、`应急手册` 或 `综合手册`
- 必须标明适用系统、适用版本、适用环境、更新责任人
- 必须声明数据来源，如“环境拓扑来自 IaC 仓库”“指标来自 Grafana Dashboard 定义”“告警阈值来自 SLO 评审结论”
- 必须写明文档状态，避免永远停留在“最新版”这种模糊描述

**推荐状态**：
- `draft`：草稿中，信息未补齐
- `review_ready`：已可评审
- `active`：已发布，可作为当前执行依据
- `deprecated`：已废弃，不再适用当前环境
- `archived`：历史归档版本，仅用于追溯

**示例格式**：

| 字段 | 示例 |
|------|------|
| 文档标题 | 订单服务生产部署与运维手册 |
| 文档类型 | `综合手册` |
| 适用版本 | `v3.4.x` |
| 适用环境 | `staging` / `prod` |
| 当前状态 | `active` |
| 更新责任人 | `sre.order` |
| 数据来源 | IaC 仓库 / CI 发布流水线 / Grafana |
| 最后校验时间 | 2026-05-12 |

### 4.3 系统概览与职责边界

**编写要点**：
- 用 3~5 句话写清系统做什么、不做什么
- 标出关键运行单元：API 服务、异步任务、消息消费者、数据库、缓存、定时任务、第三方依赖
- 标出运维边界：哪些部分是本团队负责，哪些依赖外部团队或平台
- 写明关键依赖的可用性假设和限制，如第三方支付、对象存储、消息队列、证书服务

**示例**：

```text
订单服务负责处理订单创建、支付状态同步、履约状态推进和订单查询。
它不负责库存真实扣减，也不直接管理支付渠道配置。
本团队直接负责：订单 API、订单消费者、订单数据库、订单缓存、订单告警。
外部依赖：库存服务、支付回调、消息队列、统一鉴权网关。
```

> **关键原则**：运维手册必须明确“谁负责什么”，否则出了故障最先发生的不是止血，而是甩锅。

### 4.4 环境与部署拓扑

**编写要点**：
- 环境必须分开写：`dev`、`test`、`staging`、`prod` 的资源规格、依赖、权限、访问方式不要混写
- 拓扑必须说明：入口流量、服务节点、数据库、缓存、消息队列、定时任务、外部依赖
- 多地域 / 多可用区 / 主备 / 灾备要明确标识
- 标出运行约束：例如“生产禁止手工 SSH 变更，只能通过流水线发布”

**环境矩阵示例**：

| 环境 | 用途 | 入口地址 | 部署形态 | 依赖差异 | 权限要求 |
|------|------|---------|---------|---------|---------|
| `dev` | 本地联调 | 内网 / 本地 | 单实例 | Mock 支付、Mock MQ | 开发账号 |
| `test` | 功能测试 | `test-order.xxx` | 2 实例 | 测试库存、测试支付沙箱 | QA / 开发 |
| `staging` | 预发布验证 | `staging-order.xxx` | 类生产 | 接近生产依赖 | QA / SRE |
| `prod` | 生产 | `order.xxx` | 多 AZ 多实例 | 真实依赖 | 运维审批 + 发布权限 |

**拓扑示意示例**：

```
公网流量
   │
   ▼
API Gateway
   │
   ▼
┌─────────────────────┐
│   Order Service     │  3 replicas / 2 AZ
└──────┬───────┬──────┘
       │       │
       │       ├────────▶ Redis
       │
       ├────────▶ MySQL Primary / Replica
       │
       ├────────▶ MQ (Order Events)
       │
       └────────▶ Payment / Stock / User Services
```

### 4.5 版本、制品与配置基线

部署出问题，很多时候不是代码坏，而是**版本、配置、数据库、开关、证书并不在同一基线**。

**编写要点**：
- 每次发布必须有唯一版本标识：代码版本、构建号、镜像 Tag、数据库 Schema 版本
- 配置必须分环境列出，至少说明：名称、默认值、范围、敏感性、变更方式、生效方式
- Feature Flag 要写清默认值、灰度人群、回收条件、关闭后影响
- 密钥、证书、token 不要直接贴值，要写管理位置、引用方式、轮换周期、过期时间
- 要显式列出“发布时必须同步更新的对象”：如镜像、配置、脚本、任务、数据库变更

**版本基线示例**：

| 对象 | 标识 | 来源 |
|------|------|------|
| 应用镜像 | `order-service:3.4.1-build314` | CI 镜像仓库 |
| Commit | `abc1234` | Git 主干 |
| DB 迁移 | `V20260512_01__order_index.sql` | Migration 仓库 |
| Feature Flag | `order_new_cancel_flow=false` | 配置中心 |
| Helm Chart | `order-chart-1.8.2` | IaC 仓库 |

**配置项五要素示例**：

| 配置项 | 默认值 | 取值范围 | 依赖 | 排查方式 |
|-------|--------|---------|------|---------|
| `ORDER_DB_POOL_SIZE` | `32` | `8~128` | DB 连接数上限 | 看连接池监控 |
| `PAYMENT_TIMEOUT_MS` | `2000` | `500~5000` | 支付服务 SLA | 看 timeout 日志 |
| `ORDER_CANCEL_CRON` | `0 */5 * * * ?` | cron 表达式 | 定时任务平台 | 看调度执行日志 |
| `ORDER_FEATURE_IDEM` | `true` | `true/false` | Redis 可用性 | 看幂等命中率指标 |

> **关键原则**：没有基线，就没有可重复部署；没有配置说明，就没有稳定运行。

### 4.6 部署前检查

部署手册最容易缺的不是部署步骤，而是**部署前到底该确认什么**。

**编写要点**：
- 检查变更范围：这次发布包含哪些需求、缺陷修复、脚本变更、配置变更
- 检查审批与窗口：发布窗口是否批准、值守是否排好、回滚责任人是否在线
- 检查环境：目标环境是否健康、依赖服务是否可用、资源是否足够
- 检查数据与备份：数据库是否备份、关键配置是否快照、回滚所需数据是否齐备
- 检查门禁：测试 / 验收 / 安全 / 合规结论是否满足条件

**部署前检查表示例**：

| 检查项 | 要求 | 结果 |
|--------|------|------|
| 发布窗口已批准 | 有审批记录 | ✅ |
| 值守安排已确认 | 发布人 / 观察人 / 回滚人在线 | ✅ |
| 测试与验收通过 | 有结论链接 | ✅ |
| 监控告警已就绪 | Dashboard 与告警已校验 | ✅ |
| 数据库已备份 | 备份编号可追溯 | ✅ |
| 回滚预案已确认 | 回滚责任人已知悉 | ✅ |
| 外部依赖稳定 | 支付 / 库存 / MQ 无重大告警 | ✅ |

> **关键原则**：凡是上线前能确认的，不要等线上出事后再发现。

### 4.7 部署步骤

部署步骤必须做到：**顺序清晰、责任明确、判定明确、失败有退路**。

**编写要点**：
- 按顺序编号，避免“大家自行理解顺序”
- 每一步至少写清：执行人、前置条件、操作命令/动作、预期结果、失败后动作
- 涉及数据库变更时，必须写清楚是在代码发布前还是后执行，以及兼容窗口
- 涉及多服务联动时，必须写明先后顺序和原因
- 不要只写命令，要写“命令成功之后看什么”

**部署步骤模板**：

| 步骤 | 执行人 | 操作 | 预期结果 | 失败处理 |
|------|--------|------|---------|---------|
| 1 | 运维 | 拉取发布单与版本基线 | 确认版本一致 | 停止发布 |
| 2 | DBA / 流水线 | 执行 DB Migration | Schema 升级成功 | 按 DB 回滚预案处理 |
| 3 | 运维 | 发布应用新镜像 | Pod 滚动更新成功 | 暂停并观察 |
| 4 | 运维 | 校验健康检查 | `/health` 返回正常 | 回滚服务版本 |
| 5 | 开发 / 运维 | 打开灰度开关 10% | 核心指标稳定 | 关闭开关 |
| 6 | 运维 | 放量至 100% | 业务指标稳定 | 回滚或暂停 |

**反例**：
- “执行部署脚本即可”
- “发布后观察一下”
- “有问题回滚”

这些都不够，因为没有判定标准和操作边界。

### 4.8 发布后验证与冒烟检查

一个发布动作只有在“部署成功”之后才刚刚开始，真正关键的是**发布后的验证与观察**。

**编写要点**：
- 验证分层：健康检查 → 接口冒烟 → 核心业务路径 → 指标观察 → 告警确认
- 每项验证要有明确观察窗口，如“灰度 10% 后观察 15 分钟”
- 指标要同时覆盖：业务成功率、错误率、延迟、资源使用、消息堆积、依赖错误率
- 冒烟必须覆盖最小关键路径，而不是全量回归

**发布后验证示例**：

| 类型 | 检查项 | 判定标准 |
|------|-------|---------|
| 健康检查 | `/health` / `/ready` | 全实例通过 |
| 接口冒烟 | 创建订单 / 查询订单 | 响应成功，错误码正常 |
| 业务指标 | 下单成功率 | 与基线无显著下降 |
| 系统指标 | CPU / 内存 / 线程池 / 连接池 | 不持续超阈值 |
| 依赖状态 | MQ 堆积 / 支付超时 / 库存错误率 | 无显著异常 |
| 告警状态 | 新版本相关告警 | 无 P1/P0 告警 |

**灰度推进原则**：
- 小流量先行，观察再放量
- 每次放量前必须重新检查关键指标
- 放量条件和暂停条件必须提前写死，不能临场拍脑袋

### 4.9 回滚与补救预案

回滚预案不是一句“有问题就回滚”，而是**明确何时回、怎么回、回完验证什么、哪些东西回不去**。

**编写要点**：
- 必须定义回滚触发条件：错误率、延迟、核心功能失败、数据异常、告警等级
- 必须明确回滚类型：应用版本回滚、配置回滚、Feature Flag 回滚、数据库回滚、流量切回
- 必须说明数据兼容性：数据库变更是否可逆、双写期多长、旧版本是否能读新数据
- 如果不能直接回滚，必须给出止血方案，如关闭开关、熔断功能、只读模式、人工补偿

**回滚策略示例**：

| 场景 | 触发条件 | 处理策略 |
|------|---------|---------|
| 应用版本异常 | 发布后 10 分钟内错误率 > 5% | 回滚镜像到上一稳定版本 |
| Feature Flag 问题 | 新流程异常但旧流程可用 | 关闭新开关，保留版本不动 |
| DB 迁移不可逆 | 新索引导致性能抖动 | 停止放量，执行补救脚本，不直接降 Schema |
| 外部依赖抖动 | 支付超时激增 | 打开降级开关，维持核心功能 |

**关键原则**：
- **应用可回滚 ≠ 数据可回滚**
- 数据兼容性必须写在手册里，不能只在 DBA 脑子里

### 4.10 监控、日志与告警

好的运维手册，不是“有监控就行”，而是**知道该看什么、在哪里看、什么时候告警、告警后谁处理**。

**编写要点**：
- 至少覆盖三层：业务指标、系统指标、依赖指标
- 日志要说明：入口日志、错误日志、关键 Trace ID、采样策略、保留周期
- Dashboard 要按职责组织：发布观察、日常运行、故障排查、容量趋势
- 告警要写阈值、路由、静默规则、升级规则
- 对关键告警要附上“一句话处置建议”

**指标分类示例**：

| 类别 | 指标 | 说明 |
|------|------|------|
| 业务指标 | 下单成功率、支付成功率、取消成功率 | 反映业务是否正常 |
| 系统指标 | CPU、内存、GC、线程池、连接池 | 反映资源是否健康 |
| 依赖指标 | DB 慢查询、Redis 命中率、MQ 堆积、第三方超时率 | 反映外部依赖健康 |
| 安全指标 | 登录失败率、越权告警、密钥过期告警 | 反映安全风险 |

**告警表模板**：

| 告警名 | 阈值 | 严重级别 | 通知对象 | 处置建议 |
|-------|------|---------|---------|---------|
| 订单创建错误率过高 | 5 分钟 > 2% | P1 | 值班 + 开发 + SRE | 先确认依赖错误，再考虑回滚 |
| MQ 堆积持续增长 | 15 分钟持续上升 | P2 | 值班 + 开发 | 看消费者是否卡死 |
| DB 连接池耗尽 | 使用率 > 90% 持续 10 分钟 | P1 | 值班 + DBA | 先限流，再查慢 SQL |
| 证书即将过期 | 7 天内到期 | P2 | 运维 + 安全 | 启动证书续期流程 |

### 4.11 日常运行与巡检

没有巡检的系统，稳定只是运气；没有规范化巡检的团队，故障只是时间问题。

**编写要点**：
- 巡检项按频率区分：每日、每周、每月、季度
- 巡检要尽量自动化，但即便自动化，也要写“失败时怎么处理”
- 常见运行操作要写 SOP：重启、扩容、切流、任务重跑、缓存清理、开关切换
- 每项巡检都要说明判定标准，而不是“看一下有无异常”

**巡检表示例**：

| 频率 | 巡检项 | 判定标准 |
|------|-------|---------|
| 每日 | P1/P0 告警回顾 | 无未处理遗留 |
| 每日 | 核心业务指标健康度 | 成功率、延迟在阈值内 |
| 每周 | 磁盘与日志保留检查 | 不超容量上限 |
| 每周 | 失败任务与死信队列检查 | 已处理或已登记 |
| 每月 | 证书 / 密钥到期检查 | 无临期未处理项 |
| 每月 | 恢复脚本抽查 | 恢复步骤可执行 |

**常见运行操作示例**：
- 重启单实例前先摘流
- 扩容前先确认 DB / Redis / MQ 是否能承受新增压力
- 重跑任务前先确认是否幂等
- 清缓存前先确认是否会造成流量击穿

### 4.12 故障处理与升级路径

应急手册的核心不是“写得很吓人”，而是**让故障时的人不用靠情绪和经验即兴发挥**。

**编写要点**：
- 必须定义故障分级，例如 `P0`、`P1`、`P2`
- 必须明确升级路径：谁先响应、谁拍板、谁负责对外同步、谁负责复盘
- 必须写通讯录或至少写角色映射，避免故障时还在查人
- 必须写应急流程：发现 → 定级 → 止血 → 恢复 → 通知 → 复盘
- 必须有信息同步模板，减少故障时的信息混乱

**故障分级示例**：

| 等级 | 含义 | 示例 |
|------|------|------|
| P0 | 全站或核心链路不可用，严重业务损失 | 全量下单失败、核心数据损坏 |
| P1 | 主要功能明显受损，有较大影响 | 支付成功后订单状态不同步 |
| P2 | 局部问题，存在替代路径 | 某后台页面异常 |
| P3 | 一般问题，影响有限 | 单个监控面板缺图 |

**应急流程示例**：

```text
发现异常
  -> 确认是否真实告警
  -> 评估影响范围与等级
  -> 拉起对应值班群 / 电话升级
  -> 先止血（回滚 / 降级 / 限流 / 只读 / 切流）
  -> 再恢复（修复 / 补偿 / 重放 / 扩容）
  -> 同步进展与结论
  -> 事故结束后 24~48 小时内复盘
```

**信息同步模板建议至少包含**：
- 事件标题
- 发现时间
- 当前等级
- 影响范围
- 当前处置动作
- 下一次同步时间
- 负责人

### 4.13 备份、恢复与连续性

很多团队写了“备份每天做”，但从来没写过“怎么恢复、多久恢复、谁来恢复、恢复之后怎么验证”。这不算完整的运维手册。

**编写要点**：
- 明确备份对象：数据库、对象存储、配置、证书、重要脚本、消息偏移、任务状态
- 明确备份频率、保留周期、存储位置、加密方式
- 明确恢复目标：`RTO`（恢复时间目标）、`RPO`（可接受数据丢失窗口）
- 明确恢复流程与演练频率
- 灾备切换条件必须写清，而不是只写“有灾备能力”

**备份恢复表示例**：

| 对象 | 备份频率 | 保留期 | 恢复目标 | 恢复验证 |
|------|---------|-------|---------|---------|
| MySQL 主库 | 每日全量 + 每小时增量 | 30 天 | `RTO < 2h` / `RPO < 1h` | 恢复后跑校验 SQL |
| Redis 配置快照 | 每日 | 7 天 | `RTO < 30min` | 应用读取正常 |
| 配置中心导出 | 每次发布前 | 90 天 | `RTO < 15min` | 配置比对通过 |
| 证书备份 | 更新前 | 到下一次轮换 | 快速替换 | TLS 校验通过 |

**连续性计划至少要回答**：
- 什么情况下触发恢复或灾备切换
- 谁可以宣布进入灾备流程
- 切换后哪些能力降级、哪些能力保留
- 如何切回主环境
- 是否做过演练，最近一次演练结果如何

### 4.14 安全与权限控制

运维手册不能只讲“怎么操作”，还要讲**谁有权操作、哪些操作必须审批、哪些日志必须留痕**。

**编写要点**：
- 区分查看权限、发布权限、回滚权限、数据库权限、配置修改权限
- 高危操作要明确双人复核或审批要求
- 敏感信息只写管理位置和引用方式，不把真实秘钥写进文档
- 必须说明审计要求：谁操作、什么时候操作、操作了什么、在哪里留痕
- 必须说明紧急提权流程和有效期

**权限矩阵示例**：

| 操作 | 开发 | QA | SRE | DBA | 安全 |
|------|------|----|-----|-----|------|
| 查看生产日志 | 只读申请后可用 | ❌ | ✅ | ✅ | ✅ |
| 发布生产版本 | ❌ | ❌ | ✅（审批后） | ❌ | ❌ |
| 回滚生产版本 | ❌ | ❌ | ✅（双人复核） | ❌ | ❌ |
| 执行 DB 变更 | ❌ | ❌ | ❌ | ✅（变更审批） | ❌ |
| 修改密钥/证书 | ❌ | ❌ | ✅（审批） | ❌ | ✅（审计） |

### 4.15 维护计划与变更管理

系统上线并不意味着结束，真正长期决定稳定性的，是维护节奏和变更纪律。

**编写要点**：
- 区分计划内维护、紧急维护、版本升级、依赖升级、证书轮换、资源扩缩容
- 维护计划要写周期、责任人、影响面、操作窗口、验证步骤
- 紧急变更要有特殊流程，但不能绕过记录和复盘
- 下线流程也要写：如何摘流、如何清理资源、如何归档数据、如何通知上下游

**维护计划表示例**：

| 事项 | 周期 | 责任人 | 操作窗口 | 验证方式 |
|------|------|--------|---------|---------|
| 证书续期 | 每季度检查 | 运维 | 周二 10:00 | TLS 握手检查 |
| DB 小版本升级 | 半年一次 | DBA | 周末窗口 | 慢 SQL 与连接数对比 |
| SDK 依赖升级 | 按风险评估 | 开发 | 非高峰窗口 | 回归 + 监控观察 |
| 备份恢复演练 | 每季度 | SRE + DBA | 预定演练窗口 | 恢复报告 |
| 监控阈值复审 | 每月 | SRE | 工作日 | 告警噪音分析 |

### 4.16 证据与审计记录

没有记录，就没有追溯；没有追溯，就没有可靠运维。

**编写要点**：
- 发布必须有发布记录：时间、执行人、版本、变更范围、结果、证据链接
- 回滚必须有回滚记录：触发原因、执行步骤、影响范围、恢复验证
- 故障必须有故障记录：级别、时间线、影响范围、处置动作、根因、改进项
- 巡检、备份、恢复、演练也应留记录，至少可检索到结果
- 不建议把原始证据都贴正文，正文保留索引和摘要即可

**记录表示例**：

| 记录类型 | 必要字段 |
|---------|---------|
| 发布记录 | 发布单号、版本、执行人、时间、结果、验证结论 |
| 回滚记录 | 触发原因、回滚版本、执行人、恢复结果 |
| 故障记录 | 等级、时间线、影响范围、止血动作、根因、复盘链接 |
| 巡检记录 | 巡检时间、巡检项、异常项、处理人 |
| 演练记录 | 场景、目标、结果、发现问题、整改计划 |

### 4.17 FAQ 与附录

FAQ 不是可有可无，它能把高频、重复、容易犯错的问题从口口相传变成组织资产。

**建议至少包含**：
- 新同学第一次值班前先看什么
- 证书快过期去哪看
- Dashboard 链接在哪
- 生产日志怎么查
- 数据库备份在哪里申请恢复
- 回滚脚本或流水线入口在哪
- 常见错误码 / 常见告警如何初判
- 高危操作审批入口在哪

**附录常见内容**：
- Dashboard 链接索引
- 日志平台索引
- 发布流水线链接
- IaC 仓库链接
- 脚本目录说明
- 联系人列表
- 术语表

## 五、从交付到运行：实施路线图

部署与运维手册写完后，应当能指导团队把“能交付”落到“能运行”。建议采用如下路线图：

```
┌──────────────────────────────────────────────────────────────┐
│  从交付到运行的实施路线图                                      │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  第 1 步：定基线（Day 0）                                     │
│  ─────────────────────                                       │
│  输入：架构设计 + 发布制品 + 配置清单                          │
│  动作：                                                       │
│    1. 固化版本、制品、环境、配置、依赖基线                    │
│    2. 明确系统边界与运维责任边界                              │
│    3. 明确适用环境和文档责任人                                │
│  检查点：能回答“本次到底发什么、发到哪、谁负责”               │
│                                                              │
│  第 2 步：补部署（Day 0-1）                                   │
│  ──────────────────────                                      │
│  输入：发布流程 + 流水线 + 发布门禁                           │
│  动作：                                                       │
│    1. 编写部署前检查清单                                      │
│    2. 编写顺序化部署步骤                                      │
│    3. 编写发布后验证与灰度推进条件                            │
│  检查点：值班同学按文档可独立完成标准发布                     │
│                                                              │
│  第 3 步：补回退（Day 1）                                     │
│  ─────────────────────                                       │
│  输入：版本兼容性说明 + 数据变更方案                           │
│  动作：                                                       │
│    1. 编写回滚触发条件                                        │
│    2. 编写回滚步骤与补救方案                                  │
│    3. 明确数据兼容窗口                                        │
│  检查点：能回答“出问题时怎么止血，什么不能直接回”             │
│                                                              │
│  第 4 步：补观测（Day 1-2）                                   │
│  ──────────────────────                                      │
│  输入：指标、日志、Trace、告警平台                            │
│  动作：                                                       │
│    1. 固化 Dashboard 与告警阈值                               │
│    2. 固化巡检项                                              │
│    3. 固化发布观察窗口                                        │
│  检查点：值班同学知道“去哪里看、看到什么算异常”               │
│                                                              │
│  第 5 步：补应急（Day 2）                                     │
│  ─────────────────────                                       │
│  输入：故障分级规则 + 通讯录 + 历史事故                        │
│  动作：                                                       │
│    1. 固化故障分级与升级路径                                  │
│    2. 固化止血、恢复、通知、复盘流程                          │
│    3. 补充常见故障 FAQ                                        │
│  检查点：发生 P1 故障时，不依赖熟人经验也能快速拉起处置       │
│                                                              │
│  第 6 步：补维护（Day 2-3）                                   │
│  ──────────────────────                                      │
│  输入：备份恢复、证书、依赖升级、维护计划                      │
│  动作：                                                       │
│    1. 固化维护周期与责任人                                    │
│    2. 固化备份恢复和演练计划                                  │
│    3. 固化审计记录模板                                        │
│  检查点：系统不只“能上线”，而且“能长期被维护”                 │
│                                                              │
│  原则：                                                       │
│  · 先固化基线，再固化步骤，再固化应急                         │
│  · 先回答“怎么发”，再回答“怎么跑”，最后回答“怎么救”           │
│  · 每一个高风险操作都要有失败分支和证据留存                   │
│  · 如果关键操作还依赖口口相传，说明手册还没写完               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

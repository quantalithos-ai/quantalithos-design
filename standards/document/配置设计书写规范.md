# 配置设计书写规范

> 本规范定义 `04-配置设计.md` 最终应该写成什么样。
> 配置设计回答：系统通过哪些配置被驱动、这些配置从哪里来、按什么优先级生效、如何校验、出错如何失效、变更如何留痕。
> 它位于 `03-详细设计.md` 之后、`05-测试方案.md` 之前，是连接实现契约、环境差异、测试矩阵、验收门禁和运维落地的配置控制面设计。
> 与 `配置设计讨论流程_SOP.md` 的关系：本规范定义结果结构；SOP 定义生成步骤。
> 与 `设计文档讨论中间产物规范.md` 的关系：中间产物规范定义每个 Step 的问题回答、诊断、取舍和回填草稿如何留存。
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)

## 一、配置设计的目标

配置设计不是环境变量清单，也不是部署手册。它的目标是把详细设计中“可被环境、部署、策略、凭据、运行形态影响的行为”整理成可审查、可测试、可验收、可运维的配置控制面。

配置设计必须让开发、测试、运维、安全和验收方在以下问题上形成一致理解：

1. 系统有哪些配置项，配置项控制什么行为。
2. 哪些行为允许配置化，哪些是架构不变量或领域不变量，禁止配置化。
3. 配置从哪里来，来源之间如何覆盖，冲突如何处理。
4. 不同环境、region、tenant、profile 的配置差异是什么。
5. 哪些配置是敏感配置，如何存储、读取、轮换、审计。
6. 配置如何加载、校验、生效、热更新、冷更新、回滚。
7. 配置缺失、错误、过期、不可达、漂移时系统如何失效。
8. 测试方案、验收标准、实施计划、部署运维手册应如何引用配置设计。

终极检验标准：

```text
一个未参与项目的人，
仅凭 00/01/02/03/04，
能否独立理解配置控制面、准备环境、填充配置、判断配置错误、执行配置变更评审，
并把配置矩阵交给 05/06/07/09 继续展开。
```

## 二、与上游 / 下游文档的边界

### 2.1 相对需求文档

配置设计承接需求文档中的：

- 环境差异
- 安全和合规要求
- 非功能目标
- 数据边界
- 运维和审计要求

配置设计不重新定义需求目标、用户故事、功能需求或验收标准。

### 2.2 相对架构设计

配置设计承接架构设计中的：

- 系统上下文和部署边界
- 外部依赖
- 数据所有权
- 安全边界
- 横切关注点
- 架构红线

配置设计不重新选择架构方案，不通过配置开关绕过架构不变量。

### 2.3 相对概要设计

配置设计承接概要设计中的：

- 主要组成部分
- 关键对象轮廓
- 外部接口骨架
- 处理流和状态边界
- 异常与边界场景

配置设计不展开代码实现细节，但必须说明哪些组成部分受哪些配置控制。

### 2.4 相对详细设计

配置设计强承接详细设计中的：

- 配置引用与外部依赖绑定
- runtime config、builder、adapter、port
- Command / Query / Job / worker 的入口形态
- 状态机、事务、幂等、错误、审计和观测边界
- 测试切口中涉及的配置前置条件

配置设计不替代详细设计中的代码契约，不重新定义 struct / enum / trait / function / DTO。

配置设计允许发现详细设计中的配置契约缺口，但必须按以下规则处理：

```text
配置结论只影响来源、优先级、默认值、profile、敏感级别或失效策略
  -> 留在 04-配置设计.md

配置结论改变 runtime config、builder、adapter constructor、trait / port、error、函数流或 DTO
  -> 必须回写 03-详细设计.md
```

禁止在 `04-配置设计.md` 中静默新增代码契约。凡是会改变实现签名、对象字段、trait 边界、adapter 构造参数或错误模型的配置结论，都必须先进入“详细设计回写清单”，在正式配置设计定稿前完成回写或明确标为阻塞待确认项。

### 2.5 相对测试方案

配置设计为测试方案提供：

- 测试环境配置矩阵
- 配置组合边界
- 必填配置缺失场景
- 错误配置和敏感配置场景
- fake / stub / real-like 外部依赖配置

测试方案继续回答如何验证这些配置，不在配置设计中展开完整测试用例。

### 2.6 相对验收标准

配置设计提供配置门禁输入，验收标准做裁决。

```text
04-配置设计
  - 哪些配置必须存在
  - 哪些配置不能错
  - 哪些配置变更必须审计

06-验收标准
  - 什么配置结果算通过
  - 哪些配置问题一票否决
  - 哪些配置风险可以接受
```

### 2.7 相对实施计划、部署与运维手册

实施计划引用配置设计来安排配置准备、提交边界和门禁嵌入。部署与运维手册引用配置设计来写具体环境文件、密钥挂载、发布命令、告警阈值和值班处置。

配置设计不写：

- 具体部署命令
- 值班流程
- 告警面板布局
- 每日排期
- 人员分工

## 三、配置设计章节主链

正式 `04-配置设计.md` 必须使用以下主链。

```text
1. 与上游文档的关系声明
2. 本次配置设计目标与范围
3. 配置控制面总览
4. 配置分类与边界
5. 配置来源、优先级与冲突处理
6. 环境、部署 profile 与配置矩阵
7. 配置项清单
8. 敏感配置与密钥管理
9. 配置加载、校验与生效机制
10. 配置变更、审计与回滚
11. 失效模式与降级 / fail-fast 策略
12. 测试、验收、实施与运维承接
13. 配置迁移、废弃与演进
14. 风险与待确认事项
15. 参考
```

章节不得随意改名。确需增减章节时，必须在文档元信息中说明原因。

### 3.1 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式配置设计时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/04_config_step_07_config_items.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章配置设计结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的配置项、优先级、来源、密钥策略、失效策略或变更流程。
- 正式章节正文只承载收口后的配置设计结论；问题回答、旧材料诊断、方案取舍、差异审计、模块自检和停审记录必须留在 `design-calibration` 中间产物。
- `设计文档讨论中间产物规范.md` 中的 100~300 行规则只约束单次写入 / patch 批次，不限制正式配置设计文档、章节、模块、表格或附录的最终长度。
- 正式章节写入前必须按 `设计文档讨论中间产物规范.md` 的写入前检查确认对应 Step / 模块思考记录、写入记录和自检状态已经完成。
- 不得为了满足单批行数而压缩配置完整性；配置项清单、优先级、敏感配置、加载校验、失效策略和迁移废弃口径必须按本规范完整收口。

## 四、通用输出规则

### 4.1 表 / 图 / 清单使用规则

配置设计以表格为主，ASCII 图按需使用，短文用于解释边界和取舍。

| 表达形式 | 适用场景 | 约束 |
|---|---|---|
| 表格 | 配置分类、来源优先级、环境矩阵、配置项清单、敏感配置、失效模式、变更流程 | 必须有稳定列名，不得只写散文 |
| ASCII 图 | 配置加载链、来源覆盖链、热更新链、变更审计链 | 必须有标题和关键说明 |
| 清单 | 禁止配置化项、进入准则、变更检查项、发布前检查项 | 每项必须可判定 |
| 短文 | 解释配置边界、取舍和风险 | 不得替代表格或矩阵 |

### 4.2 无配置项目的文档规则

如果确认某个项目、仓、模块或子系统不需要任何运行时配置,仍然必须生成配置设计中间产物和正式 `04-配置设计.md`。

该文档不是空文档,而是“无配置说明文档”。它至少必须说明：

| 必须说明项 | 内容 |
|---|---|
| 判断依据 | 为什么该项目不需要配置,引用哪些 00/01/02/03 结论 |
| 配置项清单 | 明确写“当前无 P0 / P1 / P2 配置项” |
| 配置来源 | 明确不读取 config file / env / CLI flags / config center / secret provider |
| 不可配置边界 | 哪些行为是设计不变量,不得被后续 agent 擅自配置化 |
| 对 03 的影响 | 是否需要回写详细设计;通常应为“无回写” |
| 下游承接 | 05/06/07/09 如何处理“无配置”结论 |
| 未来触发项 | 什么情况发生时必须重新打开配置设计 |

写法约束：

- 不得因为“没有配置”而跳过 `04-配置设计.md`。
- 不得删除 Step 中间产物;应在中间产物中记录“不需要配置”的判断过程。
- 正式文档仍必须标注 `design-calibration` 校准来源。
- 配置项清单表可以为空,但必须显式写明“当前无配置项”,不能留空。
- 如未来新增配置,必须重新走配置设计 SOP,不能直接把配置项塞进实施计划或部署手册。

无配置说明固定最小结构：

```text
1. 与上游文档的关系声明
2. 无配置结论与判断依据
3. 当前配置项清单: 无
4. 禁止配置化边界
5. 对详细设计的影响判定
6. 测试、验收、实施与运维承接
7. 未来重新打开配置设计的触发条件
8. 参考
```

### 4.3 ASCII 图统一格式

配置设计中所有 ASCII 图必须使用以下格式。

````md
#### <图类型>: <图标题>

```text
<ASCII 图正文>
```

关键说明:

- <图表达的配置关系>
- <图不表达的部署或代码细节>
- <图中最容易误解的边界>
````

允许的图类型：

| 图类型 | 用途 |
|---|---|
| 配置来源链图 | 表达 default / file / env / secret / config center / admin override 的覆盖关系 |
| 配置加载流程图 | 表达 load / parse / validate / assemble / expose 的过程 |
| 热更新流程图 | 表达新配置如何校验、拒绝、应用、回滚 |
| 敏感配置读取图 | 表达 secret ref、KMS / Vault、runtime 使用方的关系 |
| 变更审计链图 | 表达 change request、review、apply、audit、rollback |

### 4.4 配置项命名规则

配置项命名必须稳定、分层、可检索。

项目本地配置推荐格式：

```text
<module>.<setting>
<module>.<group>.<setting>
```

示例：

```text
audit.root
outbox.batch_size
reference_resolver.scheme_allow_list
```

系统级聚合配置推荐格式：

```text
<project_key>.<module>.<setting>
<project_key>.<module>.<group>.<setting>
```

示例：

```text
core.audit.root
core.outbox.batch_size
core.reference_resolver.scheme_allow_list
```

禁止：

- 使用临时缩写或拼音。
- 同一语义出现多个名字。
- 用布尔配置绕过安全、审计、一致性、append-only 等架构红线。
- 在项目本地配置中重复项目名,例如 L0-core 的本地配置不得强制写成 `core.audit.root`。
- 使用 `storage`、`common`、`misc`、`runtime` 这类泛化模块承载多个不同功能的配置。

模块粒度规则：

- JSON 的模块层必须对应功能边界或设计中的主要模块,不能只对应技术分类。
- 不同功能即使都落在文件系统上,也应拆成不同模块,例如 `audit.root`、`outbox.root`、`idempotency.root`。
- 只有同一功能内部的配置才能放在同一模块下,例如 `outbox.root`、`outbox.batch_size`、`outbox.retry_policy`。
- 如果某个模块名需要承载多个功能,说明模块拆分过粗,必须先重新拆分模块再写 JSON demo。

### 4.5 配置文件格式与示例规则

默认配置文件格式必须使用 JSON。

写法约束：

- 正式配置文件、模块级 demo 和可复制的示例必须使用严格 JSON。
- JSON 只是外部配置文件格式,不等于代码契约;配置仍必须经过 parse、type validate、cross-field validate 后装配到 runtime config。
- 每个主要模块必须给出一个 JSON demo,并在 demo 下方用表格逐项说明配置项作用、类型、默认值、约束和失败策略。
- 配置章节结尾必须给出完整配置 demo。
- 如果完整配置 demo 需要在代码块内直接注释配置作用,必须使用 `jsonc` 标注为“文档注释示例”;实际运行时配置必须去掉注释并保持严格 JSON。
- YAML、TOML、HCL、CUE 等不得作为默认配置格式;确需使用时必须在架构或配置设计中说明原因和取舍。

模块级示例固定格式：

````md
#### <模块名> 配置 demo

```json
{
  "<module>": {
    "<setting>": "<value>"
  }
}
```

| 配置项 | 类型 | 示例值 | 作用 | 约束 / 校验 | 失败策略 |
|---|---|---|---|---|---|
````

完整带注释示例固定格式：

````md
```jsonc
{
  // 注释只用于文档说明;实际 JSON 配置必须删除注释。
  "<module>": {}
}
```
````

### 4.6 配置项清单最小列

配置项清单至少必须包含以下列。

| 配置项 | 类型 | 默认值 | 是否必填 | 来源 | 作用域 | 生效方式 | 敏感级别 | 失败策略 | 关联模块 |
|---|---|---|---|---|---|---|---|---|---|

推荐附加列：

| 附加列 | 用途 |
|---|---|
| 允许值 / 范围 | 说明枚举、数值范围、路径格式、URI scheme |
| 变更影响 | 标记 low / medium / high / critical |
| 关联测试 | 指向测试方案用例或测试切口 |
| 关联验收 | 指向验收门禁 |
| 备注 | 说明非平凡约束 |

### 4.7 敏感级别

配置设计必须统一敏感级别。

| 敏感级别 | 含义 | 示例 | 处理要求 |
|---|---|---|---|
| `public` | 可公开，无敏感含义 | feature label、公开 endpoint | 可进入配置文件 |
| `internal` | 内部运行配置，不应对外公开 | batch size、root path、timeout | 可进入内部配置文件 |
| `sensitive` | 暴露会产生安全或运营风险 | DSN、token ref、secret ref | 不能进日志，变更需审计 |
| `secret` | 真实秘密材料 | password、private key、raw token | 不得写入普通配置文件，必须通过密钥系统或受控 secret ref |

### 4.8 生效方式

| 生效方式 | 含义 | 文档必须说明 |
|---|---|---|
| `startup` | 仅启动时加载，变更需重启 | 启动失败策略 |
| `reload` | 可重新加载但需要显式操作 | reload 触发方式和失败回退 |
| `hot` | 可运行时自动热更新 | 校验、灰度、回滚 |
| `build-time` | 构建期决定 | 变更需要重新构建 |
| `static` | 设计不变量，不是普通配置 | 修改需变更设计或版本 |

### 4.9 失效策略

| 失效策略 | 含义 | 适用场景 |
|---|---|---|
| `fail-fast` | 配置无效时阻止启动或阻止操作 | 必填 root、密钥、门禁依赖 |
| `fail-closed` | 前置依赖不可用时拒绝危险动作 | gate、reference、security policy |
| `last-known-good` | 新配置不可用时保留旧配置 | hot / reload 策略配置 |
| `default-fallback` | 缺失时使用安全默认值 | 非敏感、非关键阈值 |
| `degraded` | 保持有限功能并暴露降级状态 | 观测输出、可选外部依赖 |
| `reject-new-value` | 拒绝新值但保持当前值 | 热更新非法配置 |

## 五、各章节写法规则

### 5.1 与上游文档的关系声明

本章说明配置设计从哪些上游文档抽取配置输入。

必须输出：

| 来源文档 | 配置输入 | 本文继续展开什么 |

## 八、常见错误

| 错误 | 问题 | 修正方式 |
|---|---|---|
| 只列 env var 名称 | 无法判断默认值、来源、失败策略和风险 | 按配置项清单最小列补全 |
| 所有行为都开放成配置 | 破坏架构稳定性和不变量 | 单独列禁止配置化项 |
| 不区分热更新和冷更新 | 运行时误操作风险高 | 为每项配置写生效方式 |
| 敏感配置和普通配置混写 | 容易泄露 secret | 单独写敏感配置与密钥管理 |
| 不写环境差异 | dev / staging / prod 行为不可预测 | 写环境、profile 与配置矩阵 |
| 不写失效模式 | 配置中心、KMS、文件缺失时无人知道如何处理 | 写失效模式与 fail-fast / fail-closed 策略 |
| 把部署命令写进配置设计 | 混淆部署手册职责 | 部署命令留给部署与运维手册 |
| 把未确认配置写成正式项 | 实施和测试会按错误契约执行 | 进入风险与待确认事项 |
| 在 04 中新增代码契约但不回写 03 | 详细设计和配置设计冲突，实施者无法 1:1 还原 | 进入详细设计回写清单，先回写 03 再定稿 04 |

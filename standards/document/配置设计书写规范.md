# 配置设计书写规范

> 配置设计回答 **"系统通过哪些配置被驱动、这些配置从哪里来、按什么优先级生效、出错会怎样失效"**。  
> 它位于详细设计之后、测试与验收之前，是连接“设计意图”和“环境落地”的静态控制层。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)  
> 设计输入见 → [详细设计书写规范](详细设计书写规范.md)  
> 测试与验收见 → [测试方案书写规范](测试方案书写规范.md) / [验收标准书写规范](验收标准书写规范.md)

## 一、配置设计的目标

配置设计的核心目标，不是“把环境变量列一遍”，而是**把系统可变行为的控制面设计清楚**，让开发、测试、运维、审计都能回答：

1. **有哪些配置项**：系统有哪些可调节项、默认值是什么、为什么需要它
2. **配置从哪里来**：代码常量、配置文件、环境变量、配置中心、密钥系统、数据库、运行时下发分别承担什么角色
3. **谁能改、何时生效**：哪些配置只在启动时加载，哪些可热更新，谁有权限改，改完如何验证
4. **优先级是什么**：当多处同时配置同一项时，以哪个来源为准，覆盖链如何定义
5. **边界是什么**：哪些能力可以做成配置，哪些不应该做成配置，哪些配置改变会破坏架构不变量
6. **失败会怎样**：缺配置、错配置、过期配置、权限不足、密钥取不到时系统如何失效与告警

> **配置设计的终极检验标准**：一个未参与该项目的人，仅凭配置设计文档，能否在不猜测实现细节的情况下完成环境准备、配置填充、差异比对、变更评审与故障排查？如果不能，说明配置设计还不够好。

## 四、各模块编写要点

### 4.1 配置设计的本质：系统控制面设计，而不是参数清单

配置设计最常见的错误是：
- 只列环境变量名
- 不写默认值和来源
- 不说明优先级与生效时机
- 把所有“未来可能想调的东西”都做成配置

这些都会让系统进入“看似可配，实则不可控”的状态。

**好的配置设计本质上是系统控制面设计**。它要求你回答：
- 这个系统的哪些行为应该开放给环境差异调节？
- 哪些是架构不变量，绝不能做成配置？
- 哪些配置改变会影响安全、审计、性能或一致性？

> **原则**：不是能配就要配。配置设计首先要做的是减法。

### 4.2 配置分类与边界

配置至少应分成以下几类：

| 类型 | 说明 | 示例 |
|------|------|------|
| 启动配置 | 仅启动时读取，改动需重启 | DB DSN、监听端口 |
| 运行时配置 | 可热更新，影响在线行为 | 限流阈值、超时、缓存 TTL |
| 策略配置 | 表达规则或权限，不等同普通参数 | Gate sensitivity policy、tool allowlist |
| 凭据配置 | token/secret/cert 等敏感材料 | OAuth secret、KMS key ref |
| 调试配置 | 仅开发/测试临时可用 | DEBUG、trace sampling override |

**必须写清楚哪些不能配置化**，例如：
- 领域不变量
- 审计链开关
- 安全门禁是否启用
- append-only 是否关闭

这些只能通过设计或版本决策修改，不能作为普通配置开放。

### 4.3 配置来源与优先级

每个系统都必须写清楚配置的来源链，比如：

```text
代码默认值
  < 配置文件
  < 环境变量
  < 配置中心
  < 运行时管理员下发(如适用)
```

并明确：
- 同名项冲突时谁覆盖谁
- 未设置时是否回退到默认值
- 必填项缺失是否阻断启动
- 配置中心不可达时是 fail-fast 还是 last-known-good

**示例**：

| 配置项 | 默认值 | 来源优先级 | 必填 | 缺失行为 |
|--------|--------|-----------|------|---------|
| `http.port` | `8080` | file < env | 否 | 用默认值 |
| `db.primary_dsn` | 无 | kms-ref < env | 是 | 启动失败 |
| `policy.push_timeout_ms` | `30000` | file < config center | 否 | 用默认值并告警 |

### 4.4 配置项清单的写法

配置项清单至少要有七列，推荐九列：

| name | type | default | required | allowed values | source | scope | reload | sensitivity |
|------|------|---------|----------|----------------|--------|-------|--------|-------------|

必要时再加：
- 说明
- 关联模块
- 关联测试项
- 变更影响级别

> **铁律**：不能只写“某字段是字符串”，必须写清“这个配置控制什么、谁会受影响、错了会怎样”。

### 4.5 敏感配置设计

敏感配置至少要说明：
- 存储位置（ENV / KMS / Vault / file ref）
- 是否允许本地文件明文
- 轮换方式
- 访问权限
- 审计留痕要求

示例：

| 配置项 | 敏感级别 | 存储方式 | 是否可明文 | 轮换方式 | 审计要求 |
|--------|----------|----------|------------|----------|----------|
| `slack.bot_token` | 高 | KMS / OAuth | 否 | 手动/自动轮换 | 读取与变更留痕 |
| `db.primary_dsn` | 高 | Secret Manager | 否 | 定期轮换 | 变更审批 |
| `trace.export_endpoint` | 低 | file/env | 是 | 无 | 可选 |

### 4.6 配置加载、校验与热更新

要写清：
- 加载时机：进程启动、请求处理前、定时拉取、事件驱动更新
- 校验机制：类型校验、范围校验、交叉字段校验
- 错误策略：启动失败、降级、拒绝应用、保留旧值
- 热更新机制：哪些项热更，哪些项冷更，哪些更改需要灰度或回滚

**示例判断表**：

| 配置项 | 加载时机 | 校验方式 | 生效方式 | 失败策略 |
|--------|----------|----------|----------|----------|
| `cache.ttl_seconds` | 启动 + 热更新 | 数值范围校验 | 热更新 | 拒绝新值,保留旧值 |
| `db.primary_dsn` | 启动 | DSN 解析 + 连接测试 | 冷更新 | 启动失败 |
| `gate.sensitivity_policy` | 运行时拉取 | schema 校验 | 热更新 | 回退 last-known-good |

### 4.7 配置测试与验收连接

配置设计必须显式告诉后续：
- 哪些配置场景要在 `05-测试方案.md` 中覆盖
- 哪些配置项是 `06-验收标准.md` 的门禁项
- 哪些失效模式必须做故障演练

例如：
- 必填密钥缺失 -> 启动失败测试
- 配置中心不可达 -> 降级策略测试
- 热更新非法值 -> 拒绝生效测试
- 高敏感策略配置变更 -> 审计留痕验证

### 4.8 配置迁移与废弃

配置不会永远稳定，所以文档必须说明：
- 新增配置如何引入
- 旧配置如何弃用
- 是否有兼容窗口
- 是否需要自动迁移脚本
- 是否需要双写/双读过渡

示例：

| 旧配置 | 新配置 | 状态 | 兼容窗口 | 迁移策略 |
|--------|--------|------|----------|----------|
| `member_image` | `image_variant_ref` | deprecated | 2 个版本 | 双读,只写新字段 |
| `bot_token` | `oauth_ref` | migration | 1 个版本 | 提供迁移脚本 |

## 五、配置设计的文档时机

推荐放在：
- 详细设计之后
- 测试方案之前
- 验收标准之前
- 实施计划之前

推荐文档链路：

```text
00-需求文档
01-架构设计
02-概要设计
03-详细设计
04-配置设计
05-测试方案
06-验收标准
07-实施计划
08-问题与处置记录
09-部署与运维手册
```

原因：
- 测试和验收依赖配置矩阵
- 实施计划需要知道配置准备和门禁条件
- 部署手册需要直接引用配置设计而不是重新定义配置

## 六、常见错误

### 错误 1：把配置设计写成 env var 列表
只列名字不列：
- 默认值
- 优先级
- 生效时机
- 错误行为
- 敏感级别

结果：文档无法用于评审、测试、审计或运维。

### 错误 2：所有行为都开放成配置
这会破坏架构稳定性。
不能配置化的边界必须写清。

### 错误 3：不区分热更新与冷更新
这会直接导致运行时误操作。

### 错误 4：敏感配置与普通配置混写
secret/token/cert 不能和普通阈值型配置在同一语义层无差别处理。

### 错误 5：不写环境差异
结果 dev 能跑,staging/prod 行为无法预测。

### 错误 6：配置失效模式未定义
当配置中心、KMS、ENV、文件出问题时，没有人知道系统该 fail-fast 还是降级。

# 配置设计讨论流程_SOP

> 目标：定义 `04-配置设计.md` 如何通过讨论逐步生成。
> 适用对象：人类作者、Codex/其他 Agent、多人协作讨论。
> 与 `配置设计书写规范.md` 的关系：书写规范定义最终结果结构；本 SOP 定义内容生成顺序。
> 与 `设计文档讨论中间产物规范.md` 的关系：本 SOP 定义每一步问什么；中间产物规范定义每一步讨论后留下什么、如何确认、如何回填。

## 1. 适用前提

本 SOP 适用于：

```text
需要为一个仓 / 一个模块 / 一个子系统编写 04-配置设计.md，
且希望先通过讨论逐步收敛配置输入、配置边界、来源优先级、环境矩阵、配置项、密钥、加载校验、变更审计和失效策略。
```

它不适用于：

```text
重新定义需求目标
重新定义架构方案
替代详细设计
替代测试方案
替代部署与运维手册
直接编写具体环境配置文件或发布命令
```

## 2. 核心原则

### 2.1 先承接详细设计，后设计配置

配置设计必须从 `00/01/02/03` 中抽取配置输入，尤其要承接详细设计中的配置引用、runtime builder、adapter、external dependency、状态、错误和测试切口。

### 2.2 无配置也必须留痕

如果在 Step 1 或 Step 2 判断项目不需要任何运行时配置,不得直接跳过配置设计。

必须继续产出：

```text
design-calibration/04_config_calibration_flow.md
design-calibration/04_config_step_01_upstream_boundary.md
design-calibration/04_config_step_02_scope.md
design-calibration/04_config_step_14_risks_open_questions.md
design-calibration/04_config_step_15_formal_document_assembly.md
04-配置设计.md
```

正式 `04-配置设计.md` 应写成“无配置说明文档”,明确：

- 判断依据。
- 当前无配置项。
- 不读取 config file / env / CLI flags / config center / secret provider。
- 哪些行为禁止被后续配置化。
- 对 `03-详细设计.md` 无回写或需要回写的判定。
- 05/06/07/09 如何承接“无配置”结论。
- 未来什么条件触发重新打开配置设计。

如果无配置结论已经成立,可以跳过 Step 3 ~ Step 13 的逐项展开,但必须在流程文件中标记为“不适用”,并在 Step 14 记录风险和触发条件。

### 2.3 允许反向校准详细设计

配置设计不能替代详细设计，也不能在 `04-配置设计.md` 中静默新增代码契约。

但配置设计允许发现 `03-详细设计.md` 中的配置契约缺口。判定规则如下：

```text
只影响配置语义、来源、优先级、默认值、profile、敏感级别或失败策略
  -> 留在 04-配置设计.md

影响 CoreRuntimeConfig、runtime builder、adapter constructor、trait / port、error、DTO 或函数流
  -> 必须回写 03-详细设计.md
```

每个 Step 的中间产物都必须包含“对详细设计的影响判定”。

固定格式：

| 配置结论 | 是否影响 03 | 影响类型 | 03 回写位置 | 处理状态 |
|---|---|---|---|---|

处理状态只允许使用：

```text
无回写
待回写
已回写
阻塞待确认
```

如果存在 `待回写` 或 `阻塞待确认` 项，不得进入正式 `04-配置设计.md` 定稿。

### 2.4 先边界，后清单

必须先明确哪些行为允许配置化、哪些禁止配置化，再列配置项清单。

错误顺序：

```text
先列 env var -> 再解释用途
```

正确顺序：

```text
配置控制面 -> 配置分类与边界 -> 来源优先级 -> 配置项清单
```

### 2.5 配置是控制面，不是部署脚本

配置设计只定义配置语义、来源、优先级、校验、生效和失效策略。部署命令、容器挂载、平台操作和值班流程属于部署与运维手册。

### 2.6 敏感配置必须单独收口

token、password、cert、private key、DSN、secret ref 等不得和普通阈值型配置混写。配置设计必须说明存储、读取、轮换、审计和禁止输出边界。

### 2.7 以配置域 / 配置项为小循环主轴

配置设计不能先生成一张全局配置项大表,再事后补来源、优先级、敏感性和加载校验。需要配置时,必须按配置控制面 / 配置域 / 配置项逐个小循环展开:

```text
配置控制面
  -> 配置域 / 功能模块
  -> 配置项
  -> 来源与优先级
  -> 敏感级别与密钥处理
  -> 加载、校验和生效机制
  -> 变更、审计和回滚
  -> 失效策略
  -> 对 03-详细设计影响判定
  -> 配置域 / 配置项停审
```

每个配置域完成后必须停审:

- 配置域是否来自 Step 3 控制面和 Step 4 允许配置化边界。
- 配置项是否都有类型、默认值、必填性、来源、作用域、生效方式、敏感级别、失败策略和关联模块。
- 敏感配置是否已经从普通配置中拆出并定义存储、读取、轮换、审计和禁止输出边界。
- 加载校验、变更审计、回滚和失效策略是否闭合。
- 是否改变 `03-详细设计.md` 的 runtime config、builder、adapter constructor、port、error 或 flow 契约。

所有配置域完成后,必须做跨配置域闭环审计,检查重复配置项、来源优先级冲突、敏感配置误归类、环境矩阵差异、加载校验缺口、变更审计缺口和详细设计回写缺口。

无配置结论成立时,本小循环标为不适用,但仍必须保留 Step 1 / 2 / 14 / 15 和正式无配置说明文档。

### 2.8 中间产物先于正式文档

不得直接跳到正式 `04-配置设计.md`。

执行链路必须是：

```text
本步输入
  -> 应问的问题
  -> SOP 问题回答
  -> Step 中间产物
  -> 回填草稿
  -> 用户确认 / 门禁通过
  -> 正式配置设计章节
```

Step 中间产物必须放在对应子项目的 `design-calibration/` 目录下，并遵循 `standards/document/设计文档讨论中间产物规范.md`。

每个 Step 的中间产物至少包含：

- Step 状态
- 本步输入
- SOP 问题回答
- 当前文档问题诊断
- 改动前后对比
- 配置设计取舍
- 结构化中间产物
- 对详细设计的影响判定
- 回填草稿
- 待确认事项
- 进入下一步条件

推荐命名：

```text
04_config_calibration_flow.md
04_config_step_01_upstream_boundary.md
04_config_step_02_scope.md
...
```

### 2.9 ASCII 图输出统一

凡是本 SOP 中要求或允许输出 ASCII 图的 Step，必须同时收稳：

```text
图类型
图标题
ASCII 图正文
图后 2~5 条关键说明
```

所有 ASCII 图必须遵守 `配置设计书写规范.md` 4.2。

### 2.10 通用执行纪律

配置设计讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 本 SOP 只定义配置设计的 Step 顺序和应问问题;Step 内小阶段、模块级先思考后写入、重启模式、旧材料后置差异审计和写入批次规则,统一以 `设计文档讨论中间产物规范.md` 为准。
- Step 开工、用户只说“继续 / 同意 / 开始下一步”、上下文压缩或 agent 切换时,必须先按 `设计文档讨论中间产物规范.md` 的状态台账和上下文恢复门禁读取 `04_config_calibration_flow.md`,确认当前 Step、当前模块和下一动作。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `04-配置设计.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。
- 100~300 行只约束单次写入批次,不是正式文档、Step 文件或章节最终长度上限。
- 项目级 `/tmp` 计划只能裁剪本项目的必读文档、Step 模块和输出路径,不得重新定义本 SOP 或中间产物规范中的通用流程。
- 即使确认项目不需要配置，也必须按本 SOP 生成必要中间产物和正式无配置说明文档。

正确示例：

```text
Step 1 判断上游配置输入。
Step 2 判断本仓是否需要配置。
若无需配置，仍生成 flow、Step 1、Step 2、Step 14、Step 15 和正式 04-配置设计.md。
若重写 04-配置设计.md，先删除旧文件，再创建新版配置说明骨架。
```

错误示例：

```text
直接说“本仓无配置”，不创建中间产物。
把 Step 3~Step 13 合并为“配置项汇总”。
在旧配置设计中追加一段“已改为 JSON”。
正式章节不标注校准来源。
```

错误原因：

- 无配置结论也需要可追溯，否则后续测试、验收和实施无法承接。
- 配置来源、优先级、敏感配置和失效策略混写会导致配置边界不清。
- 旧配置格式和新版 JSON 规则容易残留冲突。

## 3. Step 模板字段

每个 Step 必须包含以下字段：

| 字段 | 作用 |
|---|---|
| 本步目标 | 说明本步要解决什么配置设计问题 |
| 本步输入 | 说明进入本步前必须具备哪些上游信息 |
| 本步输出 | 说明本步必须产出什么结构化结果 |
| 应问的问题 | 用于把输入收敛成输出的问题集合 |
| 期望产出 | 本步应该沉淀的表、图、矩阵或清单 |
| 详细设计影响判定 | 判断本步配置结论是否改变 `03-详细设计.md` 中的代码契约 |
| 回填位置 | 指向 `04-配置设计.md` 的章节 |
| 执行约束 | 说明本步允许和禁止的做法 |
| 进入下一步的条件 | 判断本步是否完成的门禁 |

执行顺序：

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 详细设计影响判定
  -> 回填位置
  -> 进入下一步的条件
```

## 4. 建议的讨论总流程

```text
Step 1. 确认配置输入边界
Step 2. 明确配置设计目标、范围和非范围
Step 3. 建立配置控制面总览
Step 4. 定义配置分类与禁止配置化边界
Step 5. 定义配置来源、优先级与冲突处理
Step 6. 定义环境、部署 profile 与配置矩阵
Step 7. 定义配置项清单
Step 8. 定义敏感配置与密钥管理
Step 9. 定义配置加载、校验与生效机制
Step 10. 定义配置变更、审计与回滚
Step 11. 定义失效模式与降级 / fail-fast 策略
Step 12. 定义测试、验收、实施与运维承接
Step 13. 定义配置迁移、废弃与演进
Step 14. 定义风险与待确认事项
Step 15. 整理正式配置设计文档
```

## 5. 每一步的讨论目标、输入与产出

### Step 1. 确认配置输入边界

#### 本步目标

确认配置设计依赖的需求、架构、概要、详细设计和下游输入是否足够。

#### 本步输入

- `00-需求文档.md`
- `01-架构设计.md`
- `02-概要设计.md`
- `03-详细设计.md`
- `05-测试方案.md` 草案或测试方向
- `06-验收标准.md` 草案或验收方向

#### 本步输出

- 上游输入映射表
- 不再回答的问题清单
- 配置设计必须回答的问题清单

#### 应问的问题

1. 当前配置设计要承接哪些需求、非功能、安全和环境差异?
2. 详细设计中哪些配置引用、runtime builder、adapter 或外部依赖需要进入配置设计?
3. 哪些测试和验收场景依赖配置矩阵?
4. 哪些内容不应在配置设计中重新定义?
5. 当前上游是否存在会阻塞配置设计的缺口?

#### 期望产出

| 来源文档 | 配置输入 | 回填章节 |
|---|---|---|

#### 回填位置

`04-配置设计.md` §1。

#### 执行约束

- 不得重新定义详细设计中的 struct / enum / trait / function。
- 上游缺口必须进入待确认事项。

#### 进入下一步的条件

- 输入文档清单明确。
- 配置设计边界明确。

### Step 2. 明确配置设计目标、范围和非范围

#### 本步目标

定义本轮配置设计要覆盖哪些配置控制面，不覆盖哪些配置细节。

#### 本步输入

- Step 1 输入映射
- 详细设计配置引用与外部依赖绑定
- 需求文档目标 / 非目标

#### 本步输出

- 配置设计目标
- 范围 / 非范围表
- P0 / P1 / P2 配置口径

#### 应问的问题

1. P0 必须定义哪些配置才能运行主链?
2. 哪些配置属于 P1 / P2 或后续扩展?
3. 哪些配置细节应留给部署与运维手册?
4. 哪些配置细节应留给实施计划?
5. 哪些非范围仍有残余风险?

#### 期望产出

| 目标 | 说明 | 交付给下游的结果 |
|---|---|---|

| 非范围 | 留给哪一层 / 哪份文档 |
|---|---|

#### 回填位置

`04-配置设计.md` §2。

#### 执行约束

- 不得把部署命令写入配置设计范围。
- 非范围必须说明去向。

#### 进入下一步的条件

- 配置范围和非范围已收稳。

### Step 3. 建立配置控制面总览

#### 本步目标

建立配置来源、装配入口、使用模块和下游影响的全景。

#### 本步输入

- Step 2 范围
- 详细设计 runtime config / builder / adapter 章节
- 架构设计外部依赖边界

#### 本步输出

- 配置来源链图
- 配置控制面总表
- 配置域 / 功能模块总表
- 配置控制面停审记录
- 跨控制面审计表

#### 应问的问题

1. 当前系统配置从哪些来源读取?
2. 配置进入系统的唯一或主要装配入口是什么?
3. 哪些模块读取配置,哪些模块不得直接读取配置?
4. 配置控制哪些行为,不控制哪些领域不变量?
5. 配置变化会影响哪些下游文档?
6. 每个配置控制面应拆成哪些配置域 / 功能模块?
7. 每个配置域对应哪些详细设计 runtime config、builder、adapter 或外部依赖?
8. 每个配置域完成后是否通过停审?
9. 所有配置域完成后,是否存在控制面重叠、领域不变量误配置化或 03 契约影响未识别?

#### 期望产出

#### 配置来源链图: <项目名> 配置覆盖链

```text
[code defaults]
  -> [config file]
  -> [environment variables]
  -> [secret refs]
```

关键说明:

- <配置来源覆盖关系>
- <不表达部署命令>
- <架构不变量不受配置控制>

| 控制面 | 作用 | 对应模块 | 是否 P0 |
|---|---|---|---|

| 配置域 / 功能模块 | 来源控制面 | 对应详细设计模块 | 允许配置的能力 | 禁止控制的能力 |
|---|---|---|---|---|

#### 配置控制面停审记录

| 配置域 | 审查项 | 结论 | 缺口 / 修正 |
|---|---|---|---|

#### 跨控制面审计表

| 审计项 | 结论 | 缺口 / 修正 |
|---|---|---|

#### 回填位置

`04-配置设计.md` §3。

#### 执行约束

- 必须画来源链图。
- 不得把领域不变量写成配置控制项。
- 必须先按控制面拆出配置域 / 功能模块,不得直接进入配置项清单。

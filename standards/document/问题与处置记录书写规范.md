# 问题与处置记录书写规范

> 问题与处置记录回答 **"开发、集成、部署和运行中遇到了什么非显然问题、根因是什么、如何处置、以后如何避免再犯"**。
> 它不是随手笔记,而是工程知识沉淀文档——用于保存那些**代码里看不出来、但以后还会反复踩到**的问题与处置经验。
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)
> 运行落地见 → [部署与运维手册书写规范](部署与运维手册书写规范.md)

---

## 一、问题与处置记录的目标

问题与处置记录的核心目标，不是“记住谁曾经报过错”，而是**把非显然、可复发、值得复用的工程问题沉淀为可检索、可传承、可追责的知识资产**。

一个合格的问题与处置记录，至少要解决六个问题：

1. **问题是什么**：现象如何表现，影响到谁，发生在什么阶段
2. **根因是什么**：是设计缺口、实现缺陷、配置错误、环境差异、第三方限制，还是运维操作问题
3. **怎么止血**：问题发生时怎样快速降低影响
4. **怎么修复**：临时修复与长期修复分别是什么
5. **怎么验证**：修复后用什么方式确认问题已解决、未引入新问题
6. **怎么避免复发**：应该在文档、测试、配置、发布、告警或流程上增加什么护栏

> **问题与处置记录的终极检验标准**：一个后来者只看这份记录，能否在同类问题再次出现时快速定位、止血、复现、修复，并知道应该补什么预防措施？如果不能，说明这条记录还不够好。

## 二、这类文档记录什么、不记录什么

### 2.1 应该记录的内容

应记录以下类型的问题：

| 类型 | 说明 | 示例 |
|------|------|------|
| 设计边界问题 | 代码修了但真正根因在设计边界 | Gate 可绕过、listing 漂移、配置优先级冲突 |
| 集成坑 | 与上游/下游/第三方系统协作出现的非显然问题 | Slack SDK 事件重复、KMS token 刷新失败 |
| 环境差异问题 | dev 能跑、staging/prod 失败 | region 配置、时钟偏差、LFS 行为差异 |
| 运维/部署问题 | 发布、回滚、扩容、证书、资源限制带来的问题 | 蓝绿切换脚本遗漏、证书链不全 |
| 供应链/安全问题 | 密钥、签名、审计、权限、敏感数据暴露问题 | 明文 token、镜像未签名仍放行 |
| 长期会复发的问题 | 即使暂时绕过，未来极可能再发生 | metadata 损坏、桥接限流、热更新不生效 |

### 2.2 不应该记录的内容

以下内容不适合放进本类文档：

| 类型 | 原因 |
|------|------|
| 一次性临时报错 | 没有复用价值 |
| 已完全体现在代码中的显然逻辑 | 应该放代码或设计文档,而不是重复一遍 |
| 纯聊天式 debug 过程 | 噪音太大,不可复用 |
| 无法确认根因的猜测 | 会污染知识库 |
| 个人情绪化描述 | 无助于复现与处置 |

> **原则**：这类文档是工程知识库，不是工作日志。

## 三、问题与处置记录必须包含的模块

```text
┌─────────────────────────────────────────────────────────────┐
│                 问题与处置记录结构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 文档元信息                                               │
│     - 标题 / 作者 / 日期 / 状态 / 适用系统 / 关联版本         │
│                                                             │
│  2. 记录对象与适用范围                                       │
│     - 记录的是开发问题 / 集成问题 / 部署问题 / 运行问题       │
│                                                             │
│  3. 问题摘要                                                 │
│     - 一句话描述问题                                         │
│     - 严重级别 / 影响范围 / 首次发现时间                      │
│                                                             │
│  4. 现象与触发条件                                           │
│     - 具体表现、触发方式、复现前置条件                        │
│                                                             │
│  5. 影响分析                                                 │
│     - 影响用户 / 功能 / 数据 / 审计 / 部署 / 性能 / 安全      │
│                                                             │
│  6. 根因分析                                                 │
│     - 直接原因 / 深层原因 / 为什么事前没发现                  │
│                                                             │
│  7. 临时处置                                                 │
│     - 止血动作 / workaround / 风险提示                        │
│                                                             │
│  8. 正式修复方案                                             │
│     - 修复位置 / 修复方式 / 影响面                            │
│                                                             │
│  9. 验证与回归                                               │
│     - 如何确认修好 / 补了哪些测试 / 有没有回归风险            │
│                                                             │
│  10. 预防复发措施                                            │
│     - 文档、测试、告警、流程、配置、权限等改进项              │
│                                                             │
│  11. 关联材料                                                │
│     - issue / PR / commit / 日志 / 报警 / 复盘 / 截图         │
│                                                             │
│  12. 结论与状态                                              │
│     - open / mitigated / fixed / verified / archived         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

注意：如果问题记录很多,应按条目拆分或索引化管理,不要把所有问题堆进一篇超长流水账。

## 四、问题与处置记录的输入与输出

| 维度 | 输入材料 | 输出内容 |
|------|---------|---------|
| 现象 | 报错、日志、告警、用户反馈、复现步骤 | 问题摘要、触发条件、影响分析 |
| 根因 | 代码、配置、设计、第三方行为、运维记录 | 根因分析、深层原因 |
| 修复 | 临时绕过、正式修复、补丁、脚本 | 临时处置、正式修复方案 |
| 验证 | 测试结果、复验结果、回归报告 | 验证结论、回归影响 |
| 改进 | 复盘结论、流程变更、文档补充 | 预防复发措施 |

### 输入材料清单

| 序号 | 材料名称 | 来源 | 必要性 | 说明 |
|------|---------|------|--------|------|
| 1 | 错误日志 / 告警 / 报错截图 | 系统 / 用户 / SRE | **必须** | 用于描述现象 |
| 2 | 复现步骤 / 环境信息 | 开发 / QA / SRE | **必须** | 用于固定触发条件 |
| 3 | 相关代码 / 配置 / 设计文档 | 开发 / 架构 | **必须** | 用于根因分析 |
| 4 | 修复 PR / commit / patch | 开发 | 推荐 | 便于追踪修复 |
| 5 | 测试与复验结果 | QA / 开发 | 推荐 | 用于证明已修复 |
| 6 | 复盘 / 事故记录 | SRE / 项目负责人 | 视场景 | 大事故应引用 |

### 输出内容清单

| 序号 | 输出物 | 形式 | 受众 |
|------|--------|------|------|
| 1 | 问题摘要 | 文字 + 表格 | 全团队 |
| 2 | 根因分析 | 文字 + 链接 | 开发 + 架构 |
| 3 | 处置步骤 | 列表 / 表格 | 开发 + SRE |
| 4 | 修复与验证说明 | 文字 + 测试证据 | 开发 + QA |
| 5 | 复发预防措施 | 表格 | 全团队 |
| 6 | 关联材料索引 | 链接清单 | 全团队 |

## 五、各模块编写要点

### 5.1 现象描述必须可复现，不可模糊

错误写法：
- “有时会失败”
- “偶发卡住”
- “某些环境不行”

正确写法必须至少包含：
- 发生阶段（开发/测试/部署/运行）
- 触发动作
- 影响对象
- 复现条件
- 具体可见症状

示例：

| 字段 | 示例 |
|------|------|
| 发生阶段 | staging 发布后 5 分钟内 |
| 触发动作 | 执行 `qs-sync push-review` |
| 现象 | CLI 返回成功，但 review Gate 未创建 |
| 影响范围 | 所有本地回推用户 |
| 复现条件 | governance 服务在短时 5xx 状态 |

### 5.2 根因分析要分“直接原因”和“深层原因”

很多记录会停在“代码这里写错了”，这不够。

应至少分两层：
- **直接原因**：程序/配置/脚本哪里错了
- **深层原因**：为什么这个错误没有更早被设计、测试、监控或流程挡住

示例：

| 层次 | 内容 |
|------|------|
| 直接原因 | `push-review` 成功响应在 Gate 创建前就提前返回 |
| 深层原因 | review return 状态模型未区分“提交到平台成功”和“进入 Gate 成功” |

### 5.3 临时处置和正式修复要分开

同一个问题常有两种动作：
- **临时处置**：先止血
- **正式修复**：彻底消除问题

这两者必须分开写,否则后人会把临时 workaround 当成最终方案。

示例：

| 类型 | 内容 |
|------|------|
| 临时处置 | 暂停某平台 adapter 的自动回写,保留平台内真相 |
| 正式修复 | 重构 bridge core 的回写确认语义,增加 backlog retry 与 audit sink |

### 5.4 验证与回归必须写“如何证明修好了”

不能只写“已修复”。必须写：
- 怎么验证
- 用什么环境
- 是否补了自动化测试
- 是否评估了回归风险

示例：

| 维度 | 内容 |
|------|------|
| 验证环境 | staging |
| 验证方式 | 手工复现 + 集成测试 `TC-BRIDGE-023` |
| 结果 | Gate 创建成功且 CLI 不再提前返回 |
| 回归 | 检查了其他 review-return 路径无同类问题 |

### 5.5 预防复发措施必须具体到动作

不要写抽象话术，如：
- “以后加强测试”
- “后续注意”

应该写成：
- 新增哪条测试
- 哪个文档要补
- 哪个告警要加
- 哪个流程要加审批
- 哪个配置要改成 fail-fast

示例：

| 类型 | 预防措施 |
|------|----------|
| 文档 | 在 `05-测试方案.md` 补 `push-review` 与 Gate 双状态校验 |
| 测试 | 新增 integration case: 平台提交成功但 Gate 创建失败 |
| 监控 | 增加 `review_submission_without_gate` 告警 |
| 流程 | 相关发布前必须做一轮 staging 回推验证 |

## 六、状态流转建议

建议问题记录至少支持以下状态：

- `open`：问题已确认,未处置
- `mitigated`：已有临时缓解措施
- `fixed`：代码/配置已修复,待验证
- `verified`：已验证修复有效
- `archived`：历史归档,仅供检索
- `rejected`：误报或非问题

示例：

| 状态 | 含义 |
|------|------|
| open | 问题真实存在 |
| mitigated | 已止血,但根因仍在 |
| fixed | 修复已提交,尚未复验 |
| verified | 测试/复验已证明修复生效 |
| archived | 长期沉淀,供后续检索 |

## 七、常见错误

### 错误 1：把问题记录写成聊天纪要
没有结构,没有根因,没有验证,后续不可复用。

### 错误 2：只写现象,不写复现条件
后人根本无法确认是不是同一个问题。

### 错误 3：只写直接原因,不写深层原因
结果问题会换个形式再次出现。

### 错误 4：临时 workaround 被误当正式方案
造成技术债长期悬空。

### 错误 5：不写回归和预防措施
相当于问题被解决一次,但系统没有变得更强。

### 错误 6：记录所有琐碎报错
会把真正有价值的问题淹没在噪音里。

## 八、自检清单

- [ ] 这条记录是否真的值得未来复用
- [ ] 问题现象是否可复现、可定位
- [ ] 是否区分了直接原因与深层原因
- [ ] 是否区分了临时处置与正式修复
- [ ] 是否明确写了验证方式与回归影响
- [ ] 是否给出了具体的复发预防措施
- [ ] 是否附了必要的链接、PR、日志、告警或复盘材料
- [ ] 是否更新了状态而不是永远停在 open

建议文件名：
- `08-问题与处置记录.md`

建议标题：
- `# 08-问题与处置记录 · [项目名]`

建议头部声明示例：

```markdown
# 08-问题与处置记录 · L6-bridges
```

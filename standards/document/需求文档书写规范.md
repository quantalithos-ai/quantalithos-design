# 需求文档书写规范

> 需求文档回答 **"要做什么、为什么要做、做到什么程度算完成"**。  
> 它是软件工程的源头——需求定义不清，后续架构、设计、开发、测试都会失焦。  
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)

## 一、需求文档的目标

需求文档要解决五个核心问题：

1. **问题定义**：当前存在什么问题或机会，为什么值得做
2. **边界定义**：这个仓 / 模块是什么、不是什么、拥有什么真相范围
3. **需求范围**：做什么、不做什么、收敛到什么程度
4. **协作关系**：谁使用、依赖谁、向谁提供什么
5. **验收标准**：怎么判断做完了、做对了、没有越界

需求文档定义的是：

```text
为什么做
做什么
不做什么
核心能力闭环是什么
如何验收
```

需求文档**不定义**：

```text
数据库表结构
Rust 结构体
handler 伪代码
事务实现
repository / service / adapter 组织方式
代码目录结构
内部关键函数调用链
```

## 二、需求文档的两层结构

为了同时适应：

- 人类逐步讨论
- Agent 逐步生成
- 最终文档归档与评审

本规范区分两层结构。

### 2.1 第一层：讨论生成流程

推荐按以下顺序推进：

```text
Step 1. 与上游文档的关系声明
Step 2. 本仓定位与边界
Step 3. 背景与问题定义
Step 4. 目标与非目标
Step 5. 用户与角色
Step 6. 使用方与依赖
Step 7. 核心能力闭环
Step 8. 用户故事
Step 9. 功能需求
Step 10. 业务规则与边界约束
Step 11. 数据需求与数据归属
Step 12. 接口与依赖
Step 13. 非功能需求
Step 14. 验收标准
Step 15. 风险与待确认事项
Step 16. 需求追溯矩阵
Step 17. 整理正式文档
```

这一层不是最终目录，而是**推荐生成顺序**。

### 2.2 第二层：最终成文目录

正式文档建议使用以下结构：

```text
1. 与上游文档的关系声明
2. 本仓定位与边界
3. 背景与问题定义
4. 目标与非目标
5. 用户与角色
6. 使用方与依赖
7. 核心能力闭环
8. 用户故事
9. 功能需求
10. 业务规则与边界约束
11. 数据需求与数据归属
12. 接口与依赖
13. 非功能需求
14. 验收标准
15. 风险与待确认事项
16. 需求追溯矩阵
```

### 2.3 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式需求文档时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/00_req_step_03_problem_context.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”和“回填草稿”小节，了解本章结论如何从讨论收敛而来。
```

写法要求：

1. 每个正式章节都必须列出对应的 `design-calibration` 中间产物。
2. 如果一个正式章节引用多个中间产物，必须逐行列出，不得合并写成“见 Step 1~3”。
3. 引用路径使用相对当前子项目的路径，例如 `design-calibration/00_req_step_09_functional_requirements.md`。
4. “延伸阅读”必须明确引导读者继续阅读对应中间产物，不得只写“详见中间产物”。
5. 正式章节正文只承载收口后的结论；推理过程、改动前后对比、待确认项处理建议保留在 `design-calibration` 中间产物中。

## 三、总体写作原则

### 3.1 先讨论，后成文

需求文档不建议由人或 Agent 一次性直接生成完整正文。
推荐方式是：

```text
逐章讨论
逐章确认
逐章填充
最后统一润色收口
```

### 3.2 先边界，后能力

如果边界不稳定，后续用户故事、功能需求和数据归属都会串线。
因此必须优先钉住：

```text
这个仓是什么
这个仓不是什么
这个仓最容易和哪些仓混淆
```

### 3.3 先依赖关系，后核心能力闭环

在收敛核心能力闭环之前，必须先明确：

```text
本仓为谁提供能力
本仓依赖谁的闭环前置能力
哪些依赖会阻塞核心能力闭环成立
```

如果使用方与依赖未收敛，核心能力闭环会失真。

### 3.4 先核心能力闭环，后外围增强

在扩展用户故事和功能需求之前，必须先收敛：

```text
核心能力闭环是什么
```

### 3.5 需求只写外部可见行为，不写内部实现组织

需求阶段禁止提前进入：

```text
数据库表结构
Rust 结构体
handler 伪代码
事务实现
service / repository / adapter / port 命名
outbox / projection 的内部实现步骤
代码目录树
内部关键函数调用链
```

### 3.6 正式章节必须保留校准来源入口

正式需求文档不是替代 `design-calibration` 中间产物，而是从中间产物收口后的主文档。

因此每个正式章节都必须保留一个清晰入口，让后续读者能够回到对应中间产物查看：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~16。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/00_req_step_09_functional_requirements.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/00_req_step_09_functional_requirements.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解功能需求如何从用户故事和核心能力闭环收敛而来。
```

### 3.7 不确定项不脑补

无法确认的信息必须进入：

```text
风险与待确认事项
```

## 四、章节级规范

### 4.1 与上游文档的关系声明

#### 4.1.1 本章目标

说明本文的语义来源，明确这份需求文档是对哪些上游文档的细化，而不是另起一套定义。

#### 4.1.2 本章应回答的问题

```text
1. 本文承接哪些上游文档？
2. 承接的是上游哪一部分主题？
3. 本文为什么不是重新定义该主题？
4. 本文在当前仓里承担什么细化作用？
```

#### 4.1.3 本章不应回答的问题

```text
- 不解释本仓与相邻仓的边界
- 不解释本仓拥有什么真相
- 不解释本仓不负责什么
- 不展开使用方与依赖
- 不展开核心能力闭环
- 不展开功能需求、规则、数据归属和接口设计
```

#### 4.1.4 推荐表达形式

##### 主表达形式（必需）

4.1 必须固定为：

```text
A. 一张来源映射表
B. 一段收束说明短文字
```

##### 来源映射表（固定结构）

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|
| `product/最终目的.md` | `§3.2 AI 员工是有身份的个体` | 平台级成员身份主题 |
| `product/六域模型.md` | `§三 身份域 Identity` | Identity 域的仓级需求承接范围 |
| `architecture/仓库拆分方案.md` | `§四 L1 · 六域服务层 / 4.1 quantalithos-identity` | `L1-identity` 的仓级职责定位 |

##### 表格填写规则

```text
1. 一行只承接一个上游语义单元。
2. 同一来源文档如涉及多个章节，应逐行展开，不应在同一单元格中并列多个章节号。
3. 上游章节/模块优先写“章节号 + 标题”。
4. 若上游文档没有稳定编号，可写模块名 / 域名 / 仓定义块 / ADR 编号。
5. 不要求细到段落、句子或行号级。
6. 承接内容只写“主题”或“范围”，不写功能列表、接口列表或实现机制。
```

##### 收束说明短文字

短文字必须回答：

```text
1. 本文讨论的主题是什么
2. 本文不是重新定义什么
3. 本文只做什么层级的细化
```

##### 短文字粒度约束

```text
- 共 1 段
- 2~3 句
- 总长度建议 60~120 字
- 只能做来源收束说明
- 不得进入本仓边界、依赖、核心能力闭环、功能需求、数据归属或接口设计
```

#### 4.1.5 粒度要求

- 只写文档来源与承接关系
- 不写仓级职责清单
- 不写边界说明表
- 不写 ASCII 图
- 不写使用方与依赖
- 不写核心能力闭环
- 不写功能需求、业务规则、数据归属与接口设计

#### 4.1.6 完成标准

- 读者能知道本文从哪些上游文档细化而来
- 读者能知道本文不是另起炉灶
- 没有提前滑入本仓边界、依赖、主链或实现内容

#### 4.1.7 阶段门禁

```text
如果 4.1 没收敛，不能进入本仓定位与边界。
```

#### 4.1.8 正反例

**正确示例（identity）：**

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|
| `product/最终目的.md` | `§3.2 AI 员工是有身份的个体` | 平台级成员身份主题 |
| `product/六域模型.md` | `§三 身份域 Identity` | Identity 域的仓级需求承接范围 |
| `architecture/仓库拆分方案.md` | `§四 L1 · 六域服务层 / 4.1 quantalithos-identity` | `L1-identity` 的仓级职责定位 |

本文讨论的主题是：上述上游结论在 `L1-identity` 仓上的需求收束方式。本文不重新定义成员概念，也不重新划定 Identity 域边界，只对上游已经成立的平台级成员身份主题做仓级细化。

**错误示例 A：混入本仓定位与边界**

```text
identity 是成员身份真相仓，不负责认证，不负责项目成员分配。
```

错误原因：

```text
这已经进入 4.2 本仓定位与边界，不属于 4.1 的来源声明。
```

**错误示例 B：在同一行并列多个章节**

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|
| `product/最终目的.md` | `§3.2、§4.1、§6.3` | identity 相关需求 |

错误原因：

```text
多个上游语义单元被压在同一行，承接关系不清晰，也不利于后续维护和审查。
```

**错误示例 C：承接内容写成后文细项**

| 来源文档 | 上游章节/模块 | 承接内容 |
|---|---|---|
| `product/六域模型.md` | `§三 身份域 Identity` | HireGlobalMember、GetMemberSummary、PublishMemberEvent |

错误原因：

```text
承接内容应写主题或范围，不应提前写成功能需求、接口或闭环动作。
```

### 4.2 本仓定位与边界

#### 4.2.1 本章目标

在正文开始前，用最小信息量建立对本仓的正确心智，防止后续章节串线。

#### 4.2.2 本章允许回答的问题

```text
1. 本仓一句话定义是什么？
2. 为什么它需要单独成仓？
3. 本仓不是什么？
4. 最容易与哪些相邻仓或概念混淆？
```

#### 4.2.3 本章禁止展开的问题

```text
- 不展开使用方与依赖
- 不展开核心能力闭环
- 不展开用户故事
- 不展开功能需求
- 不展开业务规则表
- 不展开数据归属矩阵
- 不展开接口清单
- 不展开非功能指标
- 不展开风险与待确认
```

#### 4.2.4 推荐表达形式

##### 主表达形式（必需）

4.2 必须固定为：

```text
A. 一张固定结构的边界声明表
B. 一段边界说明短文字
```

##### 边界声明表（固定结构）

| 字段 | 写什么 | 不写什么 |
|---|---|---|
| 一句话定义 | 本仓最短定义 | 不写实现路径 |
| 本仓不是什么 | 明确排除职责 | 不写后文规则表 |
| 边界对象列表 | 列出最容易混淆的仓或概念对象 | 不展开成数据归属矩阵 |
| 单独成仓原因 | 为什么不能并到相邻仓 | 不展开架构选型对比 |

##### 表格填写规则

```text
1. 每个字段只写一句完整陈述。
2. “本仓不是什么”可以使用并列短句，但不展开解释。
3. “边界对象列表”用于列出最容易与本仓混淆的相邻对象。
4. 边界对象可以是：仓、层、能力、概念主题。
5. 不要求统一为单一对象类型，但必须显式标明类型。
6. 推荐写法为：
   - 仓：<仓名>
   - 层：<层名>
   - 能力：<能力名>
   - 概念：<概念名>
7. “边界对象列表”只列对象，不在表中解释混淆原因。
8. 解释性内容统一放到表后短文字中。
9. 表格中不得出现接口名、事件名、数据分类名、闭环动作名。
```

##### 边界说明短文字

短文字必须回答：

```text
1. 为什么本仓需要单独存在
2. 它最容易与哪些仓混淆
3. 这些边界为什么必须分开
```

##### 短文字粒度约束

```text
- 共 1 段
- 2~4 句
- 总长度建议 80~180 字
- 只能做仓级边界声明
- 不得进入使用方与依赖、核心能力闭环、功能需求、业务规则、数据归属或接口设计
```

#### 4.2.5 完成标准

- 已能用 3~5 句话说清本仓定位

- 已能指出至少 2 个最易混淆边界
- 没有提前滑入依赖、核心能力闭环、功能、规则、数据归属或接口设计

#### 4.2.6 阶段门禁

```text

```

#### 4.2.7 正反例

**正确示例（identity）：**

| 字段 | 内容 |
|---|---|
| 一句话定义 | `L1-identity` 是平台级成员身份真相仓。 |
| 本仓不是什么 | 它不是认证系统，不是权限判定系统，也不是项目成员分配仓。 |

### 4.3 背景与问题定义

#### 4.3.1 本章目标
说明为什么值得做，而不是提前写方案。

#### 4.3.2 推荐子结构

```text
4.3.1 业务背景
4.3.2 现状与问题
4.3.3 业务问题 vs 技术问题
```

#### 4.3.3 子结构的输出形式

##### 4.3.3.1 业务背景

**推荐输出形式**
- 主：一段短文字
- 辅：必要时补充一张背景约束小表

**写作要求**
- 说明这个仓为什么在当前阶段值得讨论
- 说明它处在什么更大的产品 / 系统推进背景下
- 说明当前讨论它，是为了补哪一类空白或收束哪一类主题

**粒度约束**
- 1 段
- 2~4 句
- 总长度建议 80~180 字
- 不写本仓边界（那是 4.2）
- 不写目标（那是 4.4）
- 不写方案（后文才写）

##### 4.3.3.2 现状与问题

**推荐输出形式**
- 主：问题现状表
- 辅：必要时补一段短文字说明

**固定表格模板**

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|

**写作要求**
- 优先量化问题
- 如果不能量化，也必须说明：当前表现、影响范围和后果
- 一般列 1~3 个核心问题即可
- 不允许把解决方案写进来

**粒度约束**
- 不写目标
- 不写功能需求
- 不写接口方案
- 不写数据归属
- 不写“我们将通过 X 解决”这种表述

##### 4.3.3.3 业务问题 vs 技术问题

**推荐输出形式**
- 主：二分表

**固定表格模板**

| 类型 | 内容 |
|---|---|
| 业务问题 | ... |
| 技术问题 | ... |

**写作要求**
- 业务问题：说明为什么对业务 / 产品推进有影响
- 技术问题：说明为什么对需求收束、后续设计或实现有影响
- 只做分类，不给方案

**粒度约束**
- 不把解决方案塞进去
- 不把目标写成问题
- 不把用户故事提前写进来

#### 4.3.4 推荐表达形式
- 主：短文字 + 现状与问题表 + 问题分类表
- 辅：必要时问题对比表

#### 4.3.5 粒度要求
- 业务背景：只说明本仓当前所处的产品 / 系统背景
- 现状与问题：优先量化问题；若无法量化，至少说明当前表现、影响范围和后果
- 业务问题 vs 技术问题：只做问题分类，不写解决方案
- 不写目标与非目标
- 不写核心能力闭环
- 不写用户故事、功能需求、业务规则、接口、数据归属或实现路径

#### 4.3.6 完成标准
- 已说明当前业务背景
- 已列出 1~3 个主要问题
- 能量化的问题已量化
- 无法量化的问题已说明当前表现、影响范围和后果
- 已区分业务问题和技术问题
- 没有把解决方案、目标或功能需求写进本章

#### 4.3.7 阶段门禁
- 4.3 未收敛前，不能进入 4.4 目标与非目标。

#### 4.3.8 正反例

**正确示例（identity）：**

##### 4.3.1 业务背景

Quantalithos 的产品叙事要求 AI 员工作为“有身份的个体”长期存在，而不是一次性执行器或临时会话实例。随着平台进入多项目、多成员、跨阶段协作场景，成员需要被跨仓、跨项目稳定引用，因此平台需要对成员身份主题进行单独的仓级需求收束。

##### 4.3.2 现状与问题

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 平台级成员身份边界未独立收束 | 成员容易被误当作运行时实例、项目成员或认证主体 | 后续需求、架构和详细设计容易串线 |
| `GlobalMember` 与 `ProjectMember` 关系不清 | 平台级成员与项目级成员的职责容易混在一起讨论 | 影响 identity 与 work 的边界稳定性 |
| 身份主题与角色定义 / 外部正文存储关系未收紧 | 角色定义、成员画像、memory / archive 引用容易被混在同一层 | method-library / identity / 外部存储边界易漂移 |

##### 4.3.3 业务问题 vs 技术问题

| 类型 | 内容 |
|---|---|
| 业务问题 | 平台缺少对“AI 员工作为长期身份个体”的正式需求收束，难以支撑跨项目引用、生命周期管理和审计追溯。 |
| 技术问题 | `GlobalMember` / `ProjectMember`、角色定义 / 成员画像、身份真相 / 外部正文引用等边界若不在需求层先讲清，会导致后续设计与实现阶段反复串线。 |

**错误示例 A：把目标写进背景**

```text
identity 的目标是提供稳定的成员身份真相、成员生命周期能力和跨仓事件同步能力。
```

错误原因：

```text
这已经进入 4.4 目标与非目标，不是 4.3 的问题陈述。
```

**错误示例 B：把解决方案写进问题**

```text
当前成员管理存在问题，因此需要引入 RoleCatalog 索引、事件同步和外部引用模型来解决。
```

错误原因：

```text
这里已经开始写“怎么解决”，而 4.3 只能写“当前问题是什么”。
```

**错误示例 C：把功能需求写进现状表**

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 缺少 HireGlobalMember | 系统无法创建成员 | 影响成员创建能力 |

错误原因：

```text
`HireGlobalMember` 已经是功能需求命名，不能拿它来写问题定义。4.3 应该写“缺少平台级成员身份收束”，而不是直接写能力名。
```

**错误示例 D：强行伪量化**

| 问题 | 当前表现 | 影响范围 / 后果 |
|---|---|---|
| 身份边界混淆率较高 | 问题严重 | 影响较大 |

错误原因：

```text
这既没有真实量化，也没有说明具体表现和后果，属于空洞表述。若不能量化，就应明确写“当前表现”和“后果”，而不是造抽象程度词。
```

### 4.4 目标与非目标

#### 4.4.1 本章目标
收口范围，明确本次需求要达成什么、不达成什么，并为后续用户故事、功能需求和验收标准设定边界。

#### 4.4.2 本章应回答的问题

```text
1. 本次需求结束后，应成立哪些状态、边界或能力？
2. 这些目标如何被验证？
3. 哪些事项虽然相关，但明确不纳入当前范围？
4. 哪些事情必须交给相邻仓或后续阶段处理？
```

#### 4.4.3 本章不应回答的问题

```text
- 不写核心能力闭环步骤
- 不写用户故事
- 不写功能需求清单
- 不写业务规则表
- 不写接口清单
- 不写实现方案
- 不写事务、表结构、结构体或代码目录
```

#### 4.4.4 推荐表达形式

##### 主表达形式
两张表：

1. 目标表
2. 非目标表

##### 目标表固定结构

| 目标 | 说明 | 验证方式 |
|---|---|---|

##### 非目标表固定结构

| 非目标 | 不做原因 |
|---|---|

#### 4.4.5 粒度要求

##### 目标
目标应写成：

```text
本次需求完成后，应成立的状态、边界或能力范围
```

而不是：

- 功能名
- 接口名
- 愿景口号
- 实现路径

##### 非目标
非目标应写成：

```text
虽然相关，但当前明确不纳入本仓 / 本文处理范围的事项
```

而不是：

- 不解决所有问题
- 不考虑未来扩展
- 不做过度设计

#### 4.4.6 完成标准

- 每个目标都可验证
- 每个非目标都具体且有边界作用
- 没有把功能需求写成目标
- 没有把实现方案写成目标
- 没有把空洞口号写成目标
- 没有把废话写成非目标

#### 4.4.7 阶段门禁

```text
如果 4.4 没收敛，不能进入 4.5 用户与角色、4.6 使用方与依赖，也不应继续扩写用户故事和功能需求。
```

#### 4.4.8 正反例

**正确示例（identity）：**

| 支撑成员身份核心能力闭环的需求收束 | 为后文核心能力闭环提供明确边界和验收口径 | 核心能力闭环章节可被收敛为独立结构锚点 |

### 4.6 使用方与依赖

#### 4.6.1 本章目标

说明本仓在仓际协作网络中，为哪些仓 / 系统提供能力、依赖哪些仓 / 系统的前置能力，以及哪些依赖会阻塞核心能力闭环成立。

### 4.7 核心能力闭环

#### 4.7.1 本章目标

从仓存在的必要性出发，定义“这个仓成立所需的核心能力骨架”，区分闭环核心、外围增强和边界外能力，为后续用户故事、功能需求和验收标准提供结构锚点。

#### 4.7.2 本章应回答的问题

```text
1. 如果没有这个仓，系统会缺什么不可替代的能力或结构？
2. 这个仓成立必须共同具备哪些能力？
3. 哪些能力缺一个，这个仓就不算真正成立？
4. 哪些能力只是外围增强，而不是闭环核心？
5. 哪些能力根本不属于这个仓？
6. 当前已有或预期功能中，哪些是在支撑这些核心能力？
```

#### 4.7.3 本章不应回答的问题

```text

- 不写事件流
- 不写函数调用顺序
```


##### 闭环定义短文

短文必须回答：

```text

2. 这些能力为什么必须共同成立
3. 缺少这些能力时，为什么仓的需求边界会不完整
```

##### 核心能力闭环图

图中节点必须写“能力成立描述”或“能力状态描述”，不写接口动作、实现动作或事件步骤。

###### 箭头语义

```text

  -> 能力 B 成立
  -> 能力 C 成立
  -> 能力 D 成立
```

###### 图的约束

```text
1. 节点写能力成立描述，不写接口名、事件名、对象字段、数据库动作或实现组件名。
2. 优先使用单向链式结构。
3. 节点数建议 3~5 个；少于 3 个通常说明闭环定义过粗，多于 5 个通常说明把外围能力也塞进了核心闭环。
4. 图中不得出现角色、仓名、外部系统名、阶段优先级标签、开发顺序或实现机制。
5. 外围增强能力和边界外能力不得进入闭环图，应放入能力层级划分表。
```

|---|---|---|---|

#### 4.11.5 数据类型（正式定稿）

| 数据类型 | 定义 |
|---|---|
| 真相数据 | 由本仓拥有正式真相，并由本仓负责其需求层生命周期的数据。 |
| 快照数据 | 上游拥有正式真相，本仓仅为稳定消费而保留的目录、摘要、索引或镜像型数据。 |

```text
1. 本仓是否拥有该数据的正式真相？
   - 是 -> 真相数据
2. 本仓是否只为稳定消费保留摘要 / 目录 / 索引？
   - 是 -> 快照数据
3. 本仓是否只保存指向外部对象的引用关系？
   - 是 -> 引用数据
4. 本仓是否明确不得保存其正文？
   - 是 -> 禁止保存正文
```

#### 4.11.6 归属说明写法规则

```text
1. 归属说明应写成一句归属判断句，不写开放性长段解释。

4. 推荐按数据类型使用固定句式模板。
```

| 引用数据 | 本仓只保存对 `[外部对象]` 的引用关系，不拥有其正文真相。 |
| 禁止保存正文 | `[对象]` 正文不属于本仓真相范围，本仓不得保存其正文。 |

```text
1. 生命周期口径应写成一句需求层生命周期判断句。
2. 生命周期口径回答的是“这个数据在本仓需求层如何存在、变化、退出”，不回答实现存储方式。
3. 不得写数据库保留策略、缓存 TTL、归档机制或实现流程。
4. 推荐按数据类型使用固定句式模板。
```

##### 生命周期口径模板

#### 4.12.2 本章应回答的问题

```text
1. 本仓对外提供哪些能力级接口？
2. 本仓消费哪些能力级输入？
3. 哪些是同步能力边界，哪些是异步能力边界？
4. 哪些依赖是输入型，哪些结果是输出型？
5. 哪些能力边界属于当前阶段核心闭环，哪些只是外围增强？
```

#### 4.12.3 本章不应回答的问题

```text
- 不写 API 路径
- 不写 HTTP / gRPC / RPC 方法签名
- 不写 DTO / JSON / proto
- 不写事件 schema
- 不写字段名
- 不写 handler / service / repository / outbox
- 不写重试 / fallback / relay / transaction
```

#### 4.12.4 推荐表达形式

##### 主表达形式

##### 依赖裁剪承接

```text

3. 若某条关系来自 Quantalithos 内部仓，必须保留其依赖类型判断：编译期依赖 / 运行期依赖 / 事件协作依赖。
```

#### 4.12.5 接口类型（正式定稿）

| 接口类型 | 含义 |
|---|---|
| 查询接口 | 对外提供读取、检索、引用能力的接口面 |
| 变更接口 | 对外提供建立、调整、处置等正式变更能力的接口面 |
| 事件输出 | 本仓对外发出的可被其他仓持续消费的能力输出面 |
| 事件输入 | 本仓从外部持续消费的事件型输入面 |
| 后台任务接口（按需） | 以任务或后台操作形式体现的能力入口，非所有仓必有 |

#### 4.12.6 依赖类型（正式定稿）

| 依赖类型 | 含义 |
|---|---|
| 定义来源依赖 | 本仓依赖上游定义、目录、模板或语义来源才能成立自身能力边界 |
| 治理结论依赖 | 本仓依赖正式治理结论、批准、处置结论等外部判断结果 |
| 下游消费依赖 | 本仓能力的成立依赖下游体系持续消费其输出，或需明确下游消费面 |
| 外部能力依赖（按需） | 本仓依赖外部系统或外部能力边界提供前置能力，非所有仓必有 |

| 字段 | 写什么 | 不写什么 |

- 已使用正式定稿的接口类型与依赖类型枚举

### 4.13 非功能需求

#### 4.13.1 本章目标

定义本仓在需求层必须满足的质量约束，说明哪些非功能底线必须成立，并尽量给出可判断、可验证的口径。

#### 4.13.2 本章应回答的问题

```text
1. 这个仓必须满足哪些性能要求？
2. 这个仓必须满足哪些可用性要求？
3. 这个仓必须满足哪些安全要求？
4. 这个仓必须满足哪些审计 / 可追溯要求？
5. 这个仓必须满足哪些幂等 / 一致性要求？
6. 这个仓必须满足哪些可观测性要求？
7. 哪些要求能量化，哪些只能给出判断口径？
```

#### 4.13.3 本章不应回答的问题

```text
- 不写具体监控平台配置
- 不写具体日志字段
- 不写重试算法
- 不写缓存参数
- 不写数据库优化策略
- 不写加密实现细节
- 不写具体 SLO 仪表盘配置
- 不写详细测试方案
```

#### 4.13.4 推荐表达形式

##### 主表达形式
非功能需求表。

##### 固定结构表

| 非功能类别 | 要求 | 判断口径 / 目标值 |
|---|---|---|

#### 4.13.5 非功能类别（正式定稿）

| 非功能类别 | 关注点 |
|---|---|
| 性能 | 本仓关键能力是否会在当前阶段成为主链瓶颈 |
| 可用性 | 本仓核心能力在依赖失效或外围能力降级时是否仍能成立 |
| 安全 | 本仓是否越权持有不应持有的能力、数据或正文 |
| 审计 / 可追溯 | 本仓关键状态变化和关键动作是否可被正式追溯 |
| 幂等 / 一致性 | 本仓关键对象和关键变化是否保持单一正式语义 |
| 可观测性 | 本仓关键状态、关键变化和异常是否可被平台稳定观察 |

##### 使用规则

```text
1. 以上 6 类为默认检查框架。
2. 各仓应逐项判断其是否适用，并按适用程度展开，不应机械平均展开。
3. 不适用的类别应明确说明不适用原因，而不是直接跳过。
```

#### 4.13.6 “要求”列写法规则

```text
1. 要求必须写成判断句，不写抽象口号词。
2. 要求必须落在本仓能力或边界上，不得脱离本仓语义。
3. 要求优先描述“什么必须成立 / 不得发生”，而不是“如何实现”。
4. 要求不得写成技术方案、实现手段或工具选型。
5. 每条要求应能被后续“判断口径 / 目标值”直接承接。
```

##### 分类写法提示

| 非功能类别 | 写法提示 |
|---|---|
| 性能 | 说明什么能力不能成为瓶颈；若无法量化，至少说明“不应成为主链阻塞点” |
| 可用性 | 说明哪些核心能力在依赖失效时仍应成立 |
| 安全 | 说明本仓不得越权拥有或处理什么 |
| 审计 / 可追溯 | 说明哪些关键变化必须可追溯 |
| 幂等 / 一致性 | 说明哪些关键语义必须保持单一正式含义 |
| 可观测性 | 说明哪些关键状态、变化或异常必须被稳定观察 |

#### 4.13.7 “判断口径 / 目标值”列写法规则

```text
1. 能量化就写目标值。
2. 不能量化也必须写判断口径。
3. 不得留空。
4. 不得把实现手段当作判断口径。
```

#### 4.13.8 完成标准

- 已按 6 类最小非功能类别逐项检查适用性
- 每项非功能要求都有判断口径或目标值
- “要求”列没有退化成口号，也没有滑入实现方案
- 该仓真正关键的非功能要求已被重点展开

#### 4.13.9 阶段门禁

```text

```

错误原因：

```text
缺少验收类别，无法清楚追溯这些验收项分别承接哪一层需求结构。
```

**错误示例 D：没有一票否决项**

```text
只列普通验收项，不单独标出核心边界破坏条件。
```

错误原因：

```text
这会让核心闭环失效、仓边界被打穿等严重问题被淹没在普通缺陷中。
```

### 4.15 风险与待确认事项

#### 4.15.1 本章目标

显式收纳尚未关闭的风险和待确认问题，防止作者或 AI 为了填满文档而脑补确定性结论。

#### 4.15.2 本章应回答的问题

```text
1. 当前还有哪些尚未关闭的风险？
2. 这些风险会影响哪一层需求结构？
3. 当前还有哪些待确认事项？
4. 哪些待确认项会影响前文结论是否成立？
5. 哪些风险是当前阶段可接受的，哪些会阻塞后续推进？
```

#### 4.15.3 本章不应回答的问题

```text
- 不补写前文章节遗漏的功能
- 不临时新增目标
- 不临时新增规则
- 不在这里继续做设计方案选择
- 不把“未来可能优化”都写成风险
- 不把普通 TODO 当成风险或待确认事项
```

#### 4.15.4 推荐表达形式

##### 主表达形式
- 风险清单
- 待确认事项表

##### 风险清单

| 风险 | 影响范围 | 当前处理口径 |
|---|---|---|

##### 待确认事项

| 待确认事项 | 影响章节 | 当前状态 |
|---|---|---|

#### 4.15.5 “当前处理口径”列写法规则

```text
1. 当前处理口径回答的是“当前如何约束、暂存或归类这个风险”，不回答“最终如何解决”。
2. 不得写实施方案、技术方案或空泛动作词。
3. 推荐写成：当前按边界排除 / 当前按外围增强处理 / 当前已在前文章节显式收口 / 当前保留为边界背景。
```

#### 4.15.6 “当前状态”列写法规则

```text
1. 当前状态回答的是“在尚未确认的前提下，这个问题当前如何被挂起”。
2. 不得只写“未定”或“后续再看”。
3. 推荐写成：当前暂按外围增强处理 / 当前暂不纳入主链 / 当前暂按边界背景处理 / 当前保持待确认状态，不强行定论。
```

#### 4.15.7 粒度要求

- 风险必须写成具体风险句，不写泛词
- 待确认事项必须是会影响前文结构成立的问题，不写普通 TODO
- 两张表都必须明确“当前如何处理”，而不是只报问题
- 本章不负责解决问题，只负责显式保留并约束不确定性

#### 4.15.8 完成标准

- 已明确拆分风险与待确认事项两张表
- 每条风险都有影响范围和当前处理口径
- 每条待确认事项都有影响章节和当前状态
- 没有把 TODO、未来优化项或实施方案写进本章
- 没有为了填满文档而脑补确定性结论

#### 4.15.9 阶段门禁

```text
如果 4.15 没收敛，就不应进入 4.16 需求追溯矩阵。
```

#### 4.15.10 正反例

**正确示例（identity）：**

##### 风险清单

| 风险 | 影响范围 | 当前处理口径 |
|---|---|---|
| `GlobalMember` 与 `ProjectMember` 边界在后续需求展开中仍可能被重新混写 | 影响 4.2、4.7、4.9、4.10 | 当前已在边界章节和规则章节显式收口，后续按该边界继续审查。 |
| 角色定义来源与成员画像边界若不持续收紧，identity 可能侵入 method-library 的定义真相 | 影响 4.6、4.9、4.11 | 当前按“定义来源依赖 + 快照消费”处理，不允许定义正文进入本仓。 |
| 外部正文引用边界若失守，identity 容易膨胀为全档案仓 | 影响 4.2、4.10、4.11、4.14 | 当前已明确“禁止保存正文”，后续以数据归属和验收标准共同约束。 |

##### 待确认事项

| 待确认事项 | 影响章节 | 当前状态 |
|---|---|---|
| 高风险成员处置是否需要独立治理路径 | 4.6、4.10、4.13、4.14 | 当前暂按外围增强处理，不进入核心能力闭环。 |
| richer capability profile 是否进入当前仓主闭环 | 4.7、4.8、4.9 | 当前作为外围增强能力保留，不进入核心闭环。 |
| 某些外部引用关系是否需要在当前阶段提升为正式依赖 | 4.6、4.11、4.12 | 当前暂按边界背景处理，不纳入正式依赖主线。 |

**错误示例 A：把 TODO 当风险**

```text
后续补更多查询能力。
```

错误原因：

```text
这是后续工作项，不是风险。
```

**错误示例 B：写成空话**

```text
有一定复杂度，未来可能有变化。
```

错误原因：

```text
这是抽象判断，没有具体风险对象、影响范围或处理口径。
```

**错误示例 C：当前状态写成“未定”**

```text
未定。
```

错误原因：

```text
没有说明当前如何挂起或暂存这个问题，信息量不足。
```

**错误示例 D：把解决方案写进处理口径**

```text
后续通过事件总线和统一索引机制解决。
```

错误原因：

```text
这已经进入实施 / 设计方案，不是“当前处理口径”。
```

### 4.16 需求追溯矩阵

#### 4.16.1 本章目标

把前文已确认的闭环、故事、功能、规则、数据和验收结构显式连接起来，用于发现漏项、孤儿项和串线项。

#### 4.16.2 本章应回答的问题

```text
1. 每个核心能力闭环节点对应哪些用户故事？
2. 每个用户故事对应哪些功能需求？
3. 每个功能需求对应哪些业务规则？
4. 每个功能需求对应哪些数据归属要求？
5. 每个功能需求对应哪些验收标准？
6. 是否存在没有来源的功能、没有承接的规则、没有验收的能力？
```

#### 4.16.3 本章不应回答的问题

```text
- 不重新解释前文章节内容
- 不新增前文未讨论的关系
- 不补写前文遗漏项
- 不把矩阵写成自然语言长段总结
- 不把矩阵当成实施计划或测试计划
```

#### 4.16.4 推荐表达形式

##### 主表达形式
- 主追溯矩阵
- 漏项检查表

##### 主追溯矩阵（固定结构）

| 功能需求 | 支撑的核心能力闭环 | 对应的用户故事 | 对应的业务规则 | 对应的数据归属要求 | 对应的验收标准 |
|---|---|---|---|---|---|

##### 漏项检查表（固定结构）

| 检查项 | 结果 |
|---|---|
| 是否存在没有故事来源的功能需求 | 是 / 否 |
| 是否存在没有闭环映射的功能需求 | 是 / 否 |
| 是否存在没有规则保护的核心功能 | 是 / 否 |
| 是否存在没有验收标准的功能需求 | 是 / 否 |
| 是否存在未进入前文结构却出现在矩阵中的新项 | 是 / 否 |

#### 4.16.5 粒度要求

- 主追溯矩阵以“功能需求”为中心，不改用故事、规则或闭环节点作主轴
- 每一列都应只写映射结果，不重写前文章节全文
- 不允许在矩阵中新增前文未定义的对象、故事、能力、规则或验收项
- 漏项检查表必须显式给出结论，不得省略

#### 4.16.6 完成标准

- 已用主矩阵把闭环、故事、功能、规则、数据和验收连接起来
- 已提供漏项检查表
- 矩阵中没有新增前文未确认的新项
- 能快速发现孤儿需求、孤儿规则、孤儿验收项和结构串线

#### 4.16.7 正反例

**正确示例（identity）：**

|---|---|---|---|---|---|

| 成员高风险处置增强 | 外围增强能力 | 审计者查看高风险处置轨迹的故事 | 高风险成员处置必须附带治理结论引用 | 相关外部治理引用为引用数据 | 外围增强能力验收；规则边界验收 |

| 是否存在没有验收标准的功能需求 | 否 |

**错误示例 A：矩阵里新增前文没有定义的新项**

错误原因：

## 七、推荐生成方式

### 7.1 基本原则

```text
需求文档不建议一次性直接生成。
推荐按章节讨论、逐步收敛、逐步填充。
```

### 7.2 推荐流程

```text
1. 先钉边界
2. 再钉核心能力闭环
3. 再写用户故事
4. 再归并功能需求
5. 再补规则、数据、接口、非功能、验收
6. 最后整理正式文档
```

### 7.3 生成纪律

- 每一步先说目标、问题、当前结论、待确认项
- 每一步完成后确认，再进入下一步
- 不确定项统一写入待确认事项
- 需求阶段严禁越层写实现内容

## 1. 适用前提

本 SOP 适用于：

```text
需要为一个仓 / 一个模块 / 一个子系统编写 00-需求文档.md
且希望先通过讨论逐步收敛内容，再落正式文档
```

它不适用于：

```text
小型修订
错别字修复
纯格式清理
已有文档的局部补丁
```

---

## 2. 核心原则

### 2.1 先讨论，后成文

需求文档不应由 Agent 一次性生成完整正文。
正确方式是：

```text
先按章节推进讨论
每步收敛结论
确认后再填入正式文档
```

### 2.2 先边界，后能力

如果边界不稳定，功能需求一定会漂。
因此必须先钉住：

```text
这个仓是什么
这个仓不是什么
这个仓承接哪类真相范围
这个仓最容易和哪些仓混淆
```

### 2.3 先核心能力闭环，后外围增强

需求讨论必须先回答：

```text
这个仓成立所需的核心能力闭环是什么？
```

如果核心能力闭环没收敛，就不应该进入大量功能罗列。

### 2.4 需求只写外部可见行为，不写内部实现组织

需求阶段禁止写：

```text
数据库表结构
Rust 结构体
handler 伪代码
事务实现
repository 设计
service / adapter / port 命名
outbox / projection 内部步骤
关键函数调用链
代码目录
```

### 2.5 通用执行纪律

需求文档讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `00-需求文档.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。

正确示例：

```text
Step 8 单独生成用户故事中间产物。
Step 9 单独生成功能需求中间产物。
正式 00-需求文档.md 的用户故事章节标注对应校准来源。
如果重写 00-需求文档.md，先删除旧文件，再创建新版主链骨架。
```

错误示例：

```text
一次性生成 Step 8~Step 14 的综合总结。
在旧 00-需求文档.md 上直接替换几个标题。
正式文档只写“来源：前面讨论过”。
一次性写入 900 行需求正文。
```

错误原因：

- 用户故事、功能需求、业务规则和验收方向边界会混在一起。
- 旧需求口径容易残留。
- 后续架构设计无法追溯需求结论来自哪一步。

### 2.6 Step 模板的字段关系

每个 Step 都由以下字段组成：

- 本步目标
- 本步输入
- 本步输出
- 应问的问题
- 期望产出
- 回填位置
- 执行约束
- 进入下一步的条件

这些字段不是并列 checklist，而是一个有顺序的收敛单元。

#### 字段职责说明

| 字段 | 作用 |
|---|---|
| 本步目标 | 定义本步存在的意义，说明这一步要解决什么问题。 |
| 本步输入 | 定义本步开始前必须具备的前提、上游结论或已收敛结果。 |
| 本步输出 | 定义本步必须收敛出的结果类型。 |
| 应问的问题 | 用于把输入收敛成输出的问题集合，不是独立问卷。 |
| 期望产出 | 本步应交付的具体结论项，是对“本步输出”的展开。 |
| 回填位置 | 指明本步产出最终写入的规范章节或正式文档位置。 |
| 执行约束 | 规定本步过程中哪些做法允许，哪些做法禁止。 |
| 进入下一步的条件 | 判断本步是否完成的门槛。 |

#### 执行顺序

执行顺序不是“按字段随意阅读”，而应按以下顺序推进：

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 回填位置
  -> 进入下一步的条件
```

#### 关系说明

```text
输入限定本步前提。
输出定义本步目标结果。
问题用于把输入收敛成输出。
产出是输出的具体化清单。
回填位置决定这些产出最终落在哪里。
执行约束防止本步跑偏。
进入下一步的条件判断本步是否完成。
```

也就是说：

```text
目标定意义
输入定前提
输出定结果
问题做收敛
约束防跑偏
产出做交付
回填定落点
门禁定完成
```

## 3. 建议的讨论总流程

```text
Step 1. 与上游文档的关系声明
Step 2. 本仓定位与边界
Step 3. 背景与问题定义
Step 4. 目标与非目标
Step 5. 用户与角色
Step 6. 使用方与依赖
Step 7. 核心能力闭环
Step 8. 用户故事
Step 9. 功能需求
Step 10. 业务规则与边界约束
Step 11. 数据需求与数据归属
Step 12. 接口与依赖
Step 13. 非功能需求
Step 14. 验收标准
Step 15. 风险与待确认事项
Step 16. 需求追溯矩阵
Step 17. 正式整理为 00-需求文档
```

每一步都遵循统一动作：

```text
1. 说明本步目标
2. 列出要回答的问题
3. 讨论并收敛结论
4. 标记未确认项
5. 确认是否进入下一步
```

## 4. 每一步的讨论目标、输入与产出

### Step 1. 与上游文档的关系声明

#### 本步目标
先校准本文的语义来源，明确它承接哪些上游结论，而不是另起一套定义。

#### 本步输入
- 当前仓对应的上游产品文档
- 当前仓对应的上游需求 / 全局架构文档
- 已知的仓定位或主题背景（若有）

#### 本步输出
- 上游文档来源结论
- 承接主题结论
- 收束说明结论

#### 应问的问题

```text
本文承接哪些上游文档？
承接的是上游哪一部分主题？
本文为什么不是重新定义该主题？
本文在当前仓里承担什么细化作用？
```

#### 期望产出

```text
上游文档来源结论
承接主题结论
收束说明结论
```

#### 回填位置
- `需求文档书写规范` 4.1 与上游文档的关系声明

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.1 为准。

#### 进入下一步的条件

```text
读者能知道本文从哪些上游文档细化而来，且不会误以为本文在重新发明该主题。
```

---

### Step 2. 本仓定位与边界

#### 本步目标
建立对本仓的正确心智，防止后续章节串线。

#### 本步输入
- Step 1 已收敛的来源与承接结论
- 当前仓在全局系统中的已知定位信息
- 与相邻仓的已知边界线索（若有）

#### 本步输出
- 一句话定义结论
- 非职责结论
- 边界对象结论
- 单独成仓原因结论

#### 应问的问题

```text
本仓一句话定义是什么？
为什么它需要单独成仓？
本仓不是什么？
最容易与哪些相邻仓或概念混淆？
```

#### 期望产出

```text
一句话定义结论
非职责结论
边界对象结论
单独成仓原因结论
```

#### 回填位置
- `需求文档书写规范` 4.2 本仓定位与边界

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.2 为准。

#### 进入下一步的条件

```text
已能用 3~5 句话说清本仓定位，且不会把相邻仓职责混入本仓。
```

---

### Step 3. 背景与问题定义

#### 本步目标
说明为什么值得做，而不是提前写方案。

#### 本步输入
- Step 2 已收敛的本仓边界
- 当前业务背景 / 产品驱动力材料
- 已知问题、痛点、机会点材料

#### 本步输出
- 业务背景结论
- 现状与问题结论
- 问题分类结论

#### 应问的问题

```text
当前业务背景是什么？
当前的主要痛点或机会点是什么？
这些问题能否量化？
哪些是业务问题，哪些是技术问题？
```

#### 期望产出

```text
业务背景结论
现状与问题结论
问题分类结论
```

#### 回填位置
- `需求文档书写规范` 4.3 背景与问题定义

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.3 为准。

#### 进入下一步的条件

```text
已说明背景，已列出主要问题，已区分业务问题与技术问题，且没有把方案或目标写进问题定义。
```

---

### Step 4. 目标与非目标

#### 本步目标
收口范围，明确本次需求要达成什么、不达成什么。

#### 本步输入
- Step 2 已收敛的边界结论
- Step 3 已收敛的问题定义
- 当前阶段的业务取舍前提（若有）

#### 本步输出
- 目标结论
- 非目标结论
- 范围收束结论

#### 应问的问题

```text
本次需求结束后，应成立哪些状态、边界或能力？
这些目标如何被验证？
哪些事项虽然相关，但明确不纳入当前范围？
哪些事情必须交给相邻仓或后续阶段处理？
```

#### 期望产出

```text
目标结论
非目标结论
范围收束结论
```

#### 回填位置
- `需求文档书写规范` 4.4 目标与非目标

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.4 为准。

#### 进入下一步的条件

```text
每个目标都可验证，每个非目标都足够具体，且没有把功能、方案或空洞口号写进本步结果。
```

---

### Step 5. 用户与角色

#### 本步目标
明确谁以什么身份接触本仓，并区分人类角色与系统角色。

#### 本步输入
- Step 2 已收敛的本仓边界
- Step 4 已收敛的目标与非目标
- 当前已知的人类角色 / 系统角色线索

#### 本步输出
- 角色结论
- 系统角色结论
- 使用场景结论
- 必要时的权限差异结论

#### 应问的问题

```text
本仓有哪些主要角色？
哪些是人类角色，哪些是系统角色？
这些角色分别在什么场景下接触本仓？
是否存在管理、审计或维护类角色？
是否需要进一步补权限矩阵？
```

#### 期望产出

```text
角色结论
系统角色结论
使用场景结论
必要时的权限差异结论
```

#### 回填位置
- `需求文档书写规范` 4.5 用户与角色

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.5 为准。

#### 常见错误提醒

```text
不要把仓际依赖写成角色，不要把用户故事写成角色说明，不要把接口动作写进使用场景。
```

#### 进入下一步的条件

```text
已明确主要角色及其接触场景，且不会把仓际依赖关系、用户故事或接口动作混写进本章。
```

---

### Step 6. 使用方与依赖

#### 本步目标
说明本仓在仓际协作网络中，为谁提供能力、依赖谁的前置能力，以及哪些依赖会阻塞核心能力闭环成立。

#### 本步输入
- Step 2 已收敛的本仓边界
- Step 5 已收敛的角色与使用场景
- 当前已知的仓际协作事实与外部依赖事实

#### 本步输出
- 仓际能力关系结论
- 闭环前置依赖结论
- 依赖失效后果结论

#### 应问的问题

```text
本仓向哪些仓 / 系统提供哪些能力？
本仓依赖哪些仓 / 系统提供哪些能力？
哪些依赖是闭环前置？
哪些依赖失效时会影响本仓当前阶段能力？
哪些关系只是消费 / 引用，哪些关系会形成强阻塞？
哪些依赖虽然存在，但不属于当前阶段前置条件？
```

#### 期望产出

```text
仓际能力关系结论
闭环前置依赖结论
依赖失效后果结论
```

#### 回填位置
- `需求文档书写规范` 4.6 使用方与依赖

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.6 为准。

#### 常见错误提醒

```text
不要把角色说明写进本章，不要把接口名 / 事件名写进关系表，不要把主链步骤写进本章。
```

#### 进入下一步的条件

```text
已明确本仓的输入依赖、输出能力和闭环前置关系，且没有把角色、接口细节或主链步骤混写进本章。
```

---

### Step 7. 核心能力闭环

#### 本步目标
从仓存在的必要性出发，收敛“这个仓成立所需的核心能力骨架”，而不是先从功能清单或阶段优先级出发。

#### 本步输入
- Step 2 已收敛的本仓边界
- Step 4 已收敛的目标与非目标
- Step 6 已收敛的仓际依赖关系
- 当前已知的功能与能力线索

#### 本步输出
- 仓存在必要性结论
- 核心能力闭环结论
- 外围增强能力结论
- 边界外能力结论
- 功能回填映射结论

#### 应问的问题

```text
如果没有这个仓，系统会缺什么不可替代的能力或结构？
这个仓成立必须共同具备哪些能力？
哪些能力缺一个，这个仓就不算真正成立？
哪些能力只是外围增强，而不是闭环核心？
哪些能力根本不属于这个仓？
当前已有或预期功能中，哪些是在支撑这些核心能力？
```

#### 期望产出

```text
仓存在必要性结论
核心能力闭环结论
外围增强能力结论
边界外能力结论
功能回填映射结论
```

#### 回填位置
- `需求文档书写规范` 4.7 核心能力闭环

#### 执行约束
- 当前以“核心能力闭环”思路收敛本步讨论，不再以“当前先做什么”为第一出发点。
- 本步结果回填到 `需求文档书写规范` 4.7 核心能力闭环。
- 不直接从功能清单定义闭环；应先从仓存在必要性和闭环成立条件出发，再用功能回填映射。
- 核心能力闭环图中的箭头表示“能力成立的逻辑依赖关系”，不是运行时调用顺序、接口时序、事件传播顺序或开发实施步骤。
- 图中节点只写能力成立描述，不写接口名、事件名、对象字段、数据库动作或实现组件名。

#### 常见错误提醒

```text
不要把功能清单直接当成闭环，不要把接口或事件链写成闭环，不要把阶段优先级表误当成能力结构。
```

#### 进入下一步的条件

```text
已说明仓存在的必要性，已收敛闭环核心能力、外围增强能力和边界外能力，且不会把实现步骤、接口细节或功能列表直接当成闭环本身。
```

### Step 8. 用户故事

#### 本步目标
围绕核心能力闭环展开角色目标叙事，说明哪些用户故事在支撑本仓核心闭环，哪些只是外围增强，而不是重新退化成普通故事清单。

#### 本步输入
- Step 5 已收敛的角色与使用场景
- Step 7 已收敛的核心能力闭环

#### 本步输出
- 核心闭环故事结论
- 外围增强故事结论
- 故事与闭环映射结论

#### 应问的问题


## 5. 推荐的人机协作方式

### 模式 A：人工主导 + Agent辅助

适用于边界尚不稳定的仓。

```text
人工回答关键问题
Agent 负责整理、归并、编号、检查遗漏
```

### 模式 B：Agent 引导提问 + 人工确认

适用于已有较强上层心智的仓。

```text
Agent 每步提问
人工确认结论
Agent 只在确认后填充对应章节
```

### 模式 C：先口头收敛，再由 Agent 成文

适用于仓定位已经很清楚，但文档尚未结构化的情况。

```text
人工先给出结论要点
Agent 按 SOP 逐章回填
再逐章确认
```

## 6. 给 Agent 的硬约束模板

可直接复用如下提示：

```text
请按需求文档讨论流程协助我完善某个仓的 00-需求文档。

要求：
1. 不要直接生成完整文档，先逐步讨论。
2. 每一步必须先说明：
   - 本步目标是什么
   - 需要回答哪些问题
   - 改动前后区别是什么
   - 有哪些待确认项
3. 需求阶段禁止写：
   - 数据库表结构
   - Rust 结构体
   - handler 伪代码
   - 事务实现
   - 具体框架代码
   - 代码目录树
   - service / repository / adapter / port 命名
   - outbox / projection 的内部实现步骤
   - 内部关键函数调用链
4. 必须逐步收敛：
   - 本仓定位与边界
   - 背景与问题定义
   - 目标与非目标
   - 使用方与依赖
   - 核心能力闭环
   - 用户故事
   - 功能需求
   - 业务规则与边界约束
   - 数据需求与数据归属
   - 接口与依赖
   - 非功能需求
   - 验收标准
   - 风险与待确认事项
   - 需求追溯矩阵
5. 所有用户故事、功能需求、业务规则、验收标准必须编号。
6. 功能需求必须按业务能力拆分，不按对象 / CRUD / API / Command 拆分。
7. 所有核心需求必须可验收。
8. 不确定的地方不要脑补，写入待确认项。
9. 每一步完成后，等待确认，再进入下一步。
```

## 8. 最小合格标准

一套合格的需求讨论流程，至少应确保：

```text
1. 没有先写实现后补需求
2. 没有边界不清就展开功能
3. 没有在核心能力闭环未收敛前罗列全量愿望清单
4. 没有按对象 / CRUD 拆功能需求
5. 没有把数据归属拖到最后才发现串仓
6. 没有无法验收的核心需求
7. 没有脑补出来的“确定结论”
8. 最终文档能从用户故事一路追到验收标准
```

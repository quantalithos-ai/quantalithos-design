## 1. 适用前提

本 SOP 适用于：

```text
需要为一个仓 / 一个模块 / 一个子系统编写 00-需求文档.md
且希望先通过讨论逐步收敛内容，再落正式文档
```

它不适用于：

```text
小型修订
错别字修复
纯格式清理
已有文档的局部补丁
```

---

## 2. 核心原则

### 2.1 先讨论，后成文

需求文档不应由 Agent 一次性生成完整正文。
正确方式是：

```text
先按章节推进讨论
每步收敛结论
确认后再填入正式文档
```

### 2.2 先边界，后能力

如果边界不稳定，功能需求一定会漂。
因此必须先钉住：

```text
这个仓是什么
这个仓不是什么
这个仓承接哪类真相范围
这个仓最容易和哪些仓混淆
```

### 2.3 先核心能力闭环，后外围增强

需求讨论必须先回答：

```text
这个仓成立所需的核心能力闭环是什么？
```

如果核心能力闭环没收敛，就不应该进入大量功能罗列。

### 2.4 以核心能力为小循环主轴

需求文档的后半段不应一次性铺开所有用户故事、功能、规则、数据、接口和验收项。
正确方式是先把核心能力闭环拆成稳定的能力节点，再围绕每个能力节点逐个完成需求小循环：

```text
核心能力节点
  -> 支撑该能力的用户故事
  -> 该能力必须提供的功能需求
  -> 保护该能力成立的业务规则
  -> 该能力涉及的数据归属
  -> 该能力对外体现的接口与依赖边界
  -> 该能力必须满足的质量约束
  -> 该能力的验收条件与一票否决条件
  -> 能力级停审
```

一个能力节点未完成停审前，不应同时展开多个能力节点的细节。
非功能需求可以分为“能力级质量约束”和“全局质量约束”：能回指某个能力节点的，跟随该能力节点收敛；覆盖全仓的，在 Step 13 统一收敛并在 Step 16 做跨能力审计。
全部能力节点完成小循环后，再做跨能力追溯审计，检查孤儿故事、孤儿功能、孤儿规则、孤儿数据、孤儿接口和孤儿验收。

正确示例：

```text
先确认“接收外部事实引用”是核心能力节点。
随后只围绕该能力收敛用户故事、功能需求、规则、数据归属、接口边界、质量约束和验收项。
该能力停审通过后，再进入“生成可追溯结果”能力节点。
所有能力节点完成后，再统一检查是否存在跨能力重复、遗漏或串仓。
```

错误示例：

```text
先一次性生成全仓用户故事。
再一次性生成全仓功能需求。
再一次性生成全仓规则和数据归属。
最后才发现某些故事没有功能承接，某些验收项找不到来源。
```

错误原因：

- 一次性生成容易把不同能力的边界混在一起。
- 后续追溯矩阵只能做事后补丁，无法保证每个能力从故事到验收都闭合。
- AI 容易为了填满章节补出没有来源的功能、规则或验收项。

### 2.4.1 无人值守需求流的 Step 内正反例

即使用户要求自动完成需求文档后续 Step,Agent 也必须在单个 Step 内先做问题回答,再做诊断、取舍、结构化和回填,不得一次性填完模板。

正确示例:

```text
Step 9 功能需求:
1. 先逐项回答:每个核心能力节点需要哪些外部可见功能?哪些能力不属于本仓?
2. 再诊断:旧文档是否把内部 repository、handler、event schema 或相邻仓能力写成需求功能?
3. 再取舍:采用能力节点小循环;不采用全仓功能大表一次性生成。
4. 再结构化:按能力节点列功能、输入语境、输出结果、边界反例。
5. 最后回填正式功能需求章节。
```

错误示例:

```text
Step 9 一次性写完:
- 问题回答:本仓需要 create / update / list / search 等功能。
- 诊断:旧文档功能不够清晰。
- 取舍:采用按能力分组。
- 结构化产物:直接列 40 条功能需求。
```

错误原因:

- 功能没有先回指核心能力节点,容易出现孤儿功能。
- 诊断没有指出哪些旧功能越界或过早实现化。
- 取舍没有真正筛掉内部实现项,后续规则、数据、接口和验收会跟着失真。

### 2.4.2 需求总流程计划 / Step 内计划正反例

需求校准流程文件必须先维护总流程计划;每个需求 Step 文件必须维护 Step 内计划。需求线的 Step 内计划要特别证明“核心能力节点”如何进入故事、功能、规则、数据、接口和验收。

正确示例:

```text
00_requirements_calibration_flow.md:
Step 7 核心能力闭环
  输入: Step 2 边界、Step 4 目标、Step 6 依赖裁剪
  输出: 00_req_step_07_core_capability_loop.md
  完成门禁: 核心能力节点已命名、排序,且每个节点都有进入 / 退出条件

00_req_step_09_functional_requirements.md:
Step 内计划:
  [x] 读取 Step 7 能力节点
  [x] 按能力节点回答功能需求问题
  [x] 诊断旧功能清单中的孤儿项和仅实现项
  [x] 选择能力小循环分组,不采用全局功能大表
  [x] 按能力结构化功能、输入、输出和边界
  [x] 自检没有孤儿功能
```

错误示例:

```text
00_requirements_calibration_flow.md:
全部需求 Step 已完成。

00_req_step_09_functional_requirements.md:
Step 内计划:
  [x] 编写功能需求。
正文:
  全仓功能需求 1~40。
```

错误原因:

- Step 9 没有证明输入来自 Step 7 的核心能力节点。
- 不能判断每个功能是否有用户故事、规则、数据和验收承接。
- 容易把 repository、handler、event schema 等内部实现写成需求功能。

### 2.5 需求只写外部可见行为，不写内部实现组织

需求阶段禁止写：

```text
数据库表结构
Rust 结构体
handler 伪代码
事务实现
repository 设计
service / adapter / port 命名
outbox / projection 内部步骤
关键函数调用链
代码目录
```

### 2.6 通用执行纪律

需求文档讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 本 SOP 只定义需求文档的 Step 顺序和应问问题;Step 内小阶段、模块级先思考后写入、重启模式、旧材料后置差异审计和写入批次规则,统一以 `设计文档讨论中间产物规范.md` 为准。
- Step 开工、用户只说“继续 / 同意 / 开始下一步”、上下文压缩或 agent 切换时,必须先按 `设计文档讨论中间产物规范.md` 的状态台账和上下文恢复门禁读取 `00_requirements_calibration_flow.md`,确认当前 Step、当前模块和下一动作。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `00-需求文档.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。
- 100~300 行只约束单次写入批次,不是正式文档、Step 文件或章节最终长度上限。
- 项目级 `/tmp` 计划只能裁剪本项目的必读文档、Step 模块和输出路径,不得重新定义本 SOP 或中间产物规范中的通用流程。

正确示例：

```text
Step 8 单独生成用户故事中间产物。
Step 9 单独生成功能需求中间产物。
正式 00-需求文档.md 的用户故事章节标注对应校准来源。
如果重写 00-需求文档.md，先删除旧文件，再创建新版主链骨架。
```

错误示例：

```text
一次性生成 Step 8~Step 14 的综合总结。
在旧 00-需求文档.md 上直接替换几个标题。
正式文档只写“来源：前面讨论过”。
一次性写入 900 行需求正文。
```

错误原因：

- 用户故事、功能需求、业务规则和验收方向边界会混在一起。
- 旧需求口径容易残留。
- 后续架构设计无法追溯需求结论来自哪一步。

### 2.7 Step 模板的字段关系

每个 Step 都由以下字段组成：

- 本步目标
- 本步输入
- 本步输出
- 应问的问题
- 期望产出
- 回填位置
- 执行约束
- 进入下一步的条件

这些字段不是并列 checklist，而是一个有顺序的收敛单元。

#### 字段职责说明

| 字段 | 作用 |
|---|---|
| 本步目标 | 定义本步存在的意义，说明这一步要解决什么问题。 |
| 本步输入 | 定义本步开始前必须具备的前提、上游结论或已收敛结果。 |
| 本步输出 | 定义本步必须收敛出的结果类型。 |
| 应问的问题 | 用于把输入收敛成输出的问题集合，不是独立问卷。 |
| 期望产出 | 本步应交付的具体结论项，是对“本步输出”的展开。 |
| 回填位置 | 指明本步产出最终写入的规范章节或正式文档位置。 |
| 执行约束 | 规定本步过程中哪些做法允许，哪些做法禁止。 |
| 进入下一步的条件 | 判断本步是否完成的门槛。 |

#### 执行顺序

执行顺序不是“按字段随意阅读”，而应按以下顺序推进：

```text
本步目标
  -> 本步输入
  -> 本步输出
  -> 应问的问题
  -> 执行约束
  -> 期望产出
  -> 回填位置
  -> 进入下一步的条件
```

#### 关系说明

```text
输入限定本步前提。
输出定义本步目标结果。
问题用于把输入收敛成输出。
产出是输出的具体化清单。
回填位置决定这些产出最终落在哪里。
执行约束防止本步跑偏。
进入下一步的条件判断本步是否完成。
```

也就是说：

```text
目标定意义
输入定前提
输出定结果
问题做收敛
约束防跑偏
产出做交付
回填定落点
门禁定完成
```

## 3. 建议的讨论总流程

```text
Step 1. 与上游文档的关系声明
Step 2. 本仓定位与边界
Step 3. 背景与问题定义
Step 4. 目标与非目标
Step 5. 用户与角色
Step 6. 使用方与依赖
Step 7. 核心能力闭环
Step 8. 用户故事
Step 9. 功能需求
Step 10. 业务规则与边界约束
Step 11. 数据需求与数据归属
Step 12. 接口与依赖
Step 13. 非功能需求
Step 14. 验收标准
Step 15. 风险与待确认事项
Step 16. 需求追溯矩阵
Step 17. 正式整理为 00-需求文档
```

每一步都遵循统一动作：

```text
1. 说明本步目标
2. 列出要回答的问题
3. 讨论并收敛结论
4. 标记未确认项
5. 确认是否进入下一步
```

从 Step 7 开始，应优先采用“核心能力节点小循环”：

```text
先列出能力节点顺序
按能力节点逐个收敛 Step 8~14 的内容；全局非功能需求在 Step 13 单独总审
每个能力节点完成后停审
全部能力节点停审后再执行 Step 16 的跨能力追溯审计
```

## 4. 每一步的讨论目标、输入与产出

### Step 1. 与上游文档的关系声明

#### 本步目标
先校准本文的语义来源，明确它承接哪些上游结论，而不是另起一套定义。

#### 本步输入
- 当前仓对应的上游产品文档
- 当前仓对应的上游需求 / 全局架构文档
- 已知的仓定位或主题背景（若有）

#### 本步输出
- 上游文档来源结论
- 承接主题结论
- 收束说明结论

#### 应问的问题

```text
本文承接哪些上游文档？
承接的是上游哪一部分主题？
本文为什么不是重新定义该主题？
本文在当前仓里承担什么细化作用？
```

#### 期望产出

```text
上游文档来源结论
承接主题结论
收束说明结论
```

#### 回填位置
- `需求文档书写规范` 4.1 与上游文档的关系声明

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.1 为准。

#### 进入下一步的条件

```text
读者能知道本文从哪些上游文档细化而来，且不会误以为本文在重新发明该主题。
```

---

### Step 2. 本仓定位与边界

#### 本步目标
建立对本仓的正确心智，防止后续章节串线。

#### 本步输入
- Step 1 已收敛的来源与承接结论
- 当前仓在全局系统中的已知定位信息
- 与相邻仓的已知边界线索（若有）

#### 本步输出
- 一句话定义结论
- 非职责结论
- 边界对象结论
- 单独成仓原因结论

#### 应问的问题

```text
本仓一句话定义是什么？
为什么它需要单独成仓？
本仓不是什么？
最容易与哪些相邻仓或概念混淆？
```

#### 期望产出

```text
一句话定义结论
非职责结论
边界对象结论
单独成仓原因结论
```

#### 回填位置
- `需求文档书写规范` 4.2 本仓定位与边界

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.2 为准。

#### 进入下一步的条件

```text
已能用 3~5 句话说清本仓定位，且不会把相邻仓职责混入本仓。
```

---

### Step 3. 背景与问题定义

#### 本步目标
说明为什么值得做，而不是提前写方案。

#### 本步输入
- Step 2 已收敛的本仓边界
- 当前业务背景 / 产品驱动力材料
- 已知问题、痛点、机会点材料

#### 本步输出
- 业务背景结论
- 现状与问题结论
- 问题分类结论

#### 应问的问题

```text
当前业务背景是什么？
当前的主要痛点或机会点是什么？
这些问题能否量化？
哪些是业务问题，哪些是技术问题？
```

#### 期望产出

```text
业务背景结论
现状与问题结论
问题分类结论
```

#### 回填位置
- `需求文档书写规范` 4.3 背景与问题定义

#### 执行约束
- 具体输出形式、粒度要求和正反例，以 `需求文档书写规范` 4.3 为准。

#### 进入下一步的条件

## 5. 推荐的人机协作方式

### 模式 A：人工主导 + Agent辅助

适用于边界尚不稳定的仓。

```text
人工回答关键问题
Agent 负责整理、归并、编号、检查遗漏
```

### 模式 B：Agent 引导提问 + 人工确认

适用于已有较强上层心智的仓。

```text
Agent 每步提问
人工确认结论
Agent 只在确认后填充对应章节
```

### 模式 C：先口头收敛，再由 Agent 成文

适用于仓定位已经很清楚，但文档尚未结构化的情况。

```text
人工先给出结论要点
Agent 按 SOP 逐章回填
再逐章确认
```

## 6. 给 Agent 的硬约束模板

可直接复用如下提示：

```text
请按需求文档讨论流程协助我完善某个仓的 00-需求文档。

要求：
1. 不要直接生成完整文档，先逐步讨论。
2. 每一步必须先说明：
   - 本步目标是什么
   - 需要回答哪些问题
   - 改动前后区别是什么
   - 有哪些待确认项
3. 需求阶段禁止写：
   - 数据库表结构
   - Rust 结构体
   - handler 伪代码
   - 事务实现
   - 具体框架代码
   - 代码目录树
   - service / repository / adapter / port 命名
   - outbox / projection 的内部实现步骤
   - 内部关键函数调用链
4. 必须逐步收敛：
   - 本仓定位与边界
   - 背景与问题定义
   - 目标与非目标
   - 使用方与依赖
   - 核心能力闭环
   - 用户故事
   - 功能需求
   - 业务规则与边界约束
   - 数据需求与数据归属
   - 接口与依赖
   - 非功能需求
   - 验收标准
   - 风险与待确认事项
   - 需求追溯矩阵
5. 所有用户故事、功能需求、业务规则、验收标准必须编号。
6. 功能需求必须按业务能力拆分，不按对象 / CRUD / API / Command 拆分。
7. 所有核心需求必须可验收。
8. 不确定的地方不要脑补，写入待确认项。
9. 每一步完成后，等待确认，再进入下一步。
10. 从核心能力闭环开始，必须先列出能力节点执行顺序，再按能力节点逐个收敛用户故事、功能需求、业务规则、数据归属、接口依赖和验收标准。
11. 每个能力节点完成后必须停审；停审通过前，不得继续展开下一个能力节点或汇总正式章节。
12. 全部能力节点完成后，必须执行跨能力追溯审计，检查孤儿故事、孤儿功能、孤儿规则、孤儿数据、孤儿接口、孤儿验收、重复定义和边界串线。
```

---

## 7. 建议的正式文档结构（与 SOP 对齐）

建议最终成文目录为：

```text
1. 与上游文档的关系声明 / 本仓定位与边界
2. 背景与问题定义
3. 目标与非目标
4. 用户与角色
5. 核心能力闭环
6. 用户故事
7. 功能需求
8. 业务规则与边界约束
9. 数据需求与数据归属
10. 接口与依赖
11. 非功能需求
12. 验收标准
13. 风险与待确认事项
14. 需求追溯矩阵
```

---

## 8. 最小合格标准

一套合格的需求讨论流程，至少应确保：

```text
1. 没有先写实现后补需求
2. 没有边界不清就展开功能
3. 没有在核心能力闭环未收敛前罗列全量愿望清单
4. 没有按对象 / CRUD 拆功能需求
5. 没有把数据归属拖到最后才发现串仓
6. 没有无法验收的核心需求
7. 没有脑补出来的“确定结论”
8. 最终文档能从用户故事一路追到验收标准
9. 每个核心能力节点都完成故事、功能、规则、数据、接口和验收的小循环停审
10. 跨能力追溯审计没有发现孤儿项、重复定义或边界串线
```

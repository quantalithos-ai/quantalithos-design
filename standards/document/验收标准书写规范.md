# 验收文档书写规范

> 验收文档回答 **"是否达到约定、是否可以签收、是否可以进入下一阶段或发布"**。
> 它位于需求、设计、开发、测试之后，是工程闭环的收口层——固定验收基线，记录验证证据，形成正式裁决。
> 通用原则见 → [设计文档编写通则](设计文档编写通则.md)
> 验收阶段门禁讨论见 → [阶段 4：验收、发布准备与最终确认（验收与发布门禁）](阶段4-验收、发布准备与最终确认.md)

---

## 一、验收文档的目标

验收文档的核心目标，不是“证明大家已经很努力”，而是**清楚回答交付物当前是否满足约定，以及这个结论基于什么证据得出**。

一个合格的验收文档，至少要解决六个核心问题：

1. **依据是什么**：本次验收是依据哪一版需求、哪一版范围、哪一版设计进行判断
2. **验什么、不验什么**：哪些内容在本轮验收范围内，哪些内容明确排除
3. **在什么基线上验**：具体是哪个版本、哪个环境、哪套配置、哪批数据、哪些账号
4. **怎么验、验了什么**：执行了哪些场景、有哪些步骤、预期结果是什么、实际结果是什么
5. **有哪些问题和风险**：当前存在哪些缺陷、遗留项、限制条件，是否已复验，谁接受风险
6. **最终结论是什么**：通过 / 有条件通过 / 不通过，是否允许进入发布准备或下一阶段，谁签字确认

> **验收文档的终极检验标准**：一个没有参与过项目的人，仅凭需求基线、验收文档和附带证据，能否回答“这次到底验了什么、结果如何、为什么可以或不可以通过”？如果不能，说明验收文档还不够好。

### 验收相关文档的分类

验收相关文档通常不是只有一种。工程上至少有两类：

| 类型 | 作用 | 产出时机 | 回答的问题 |
|------|------|---------|-----------|
| 验收方案 / 验收计划 | 定义“怎么验” | 验收开始前 | 要验哪些项、用什么环境、谁来验、什么条件下算通过 |
| 验收报告 / 验收结论 | 记录“验得怎么样” | 验收执行后 | 实际执行了什么、证据是什么、问题有哪些、最终是否通过 |

**经验法则**：
- 小型需求（1~3 天、场景少、参与方少）可以将“验收方案 + 验收报告”合并为一份文档
- 中大型项目应拆分为：`验收方案`、`验收报告`、`证据附件索引` 三类文档
- 如果涉及跨团队、上线门禁、数据核对、非功能指标，则**强烈建议分开写**

- 验收正文超过 1200 行，或证据图片超过 30 张时，建议拆成：`验收方案`、`验收报告`、`证据附件` 三份
- 如果本次验收是数据/指标验收，还必须补充**口径说明、时间窗口、样本范围、验证方法**

## 四、各模块编写要点

### 4.1 验收文档的本质：裁决文档，不是过程流水账

验收文档最容易写歪的地方，是把它写成：

- “我们测试了很多东西”的过程流水账
- “演示了一遍”的会议纪要
- “问题挺多但先过吧”的口头共识备忘录

这些都不是好的验收文档。

**好的验收文档本质上是裁决文档**。它必须能支持下面四件事：

1. **追溯**：回到哪一版需求、哪一版范围、哪一版交付物
2. **证明**：为每个结论提供证据，而不是只写一句“已验证”
3. **定责**：明确谁验、谁修、谁复验、谁签收、谁接受风险
4. **门禁**：支持“通过 / 有条件通过 / 不通过”的正式判断

> **原则**：验收文档不能依赖“大家都知道”才能看懂。凡是需要靠口头补充才能成立的结论，都还没有真正写清楚。

### 4.2 文档元信息与状态管理

**编写要点**：
- 元信息不只是标题、作者、日期，还必须有：当前状态、验收负责人、参与角色、计划时间窗
- 必须关联上游基线：需求链接、设计链接、测试报告链接、发布单链接
- 状态必须可流转，避免永远停留在“最新版”这种模糊状态

**推荐状态**：
- `draft`：草稿中，内容未齐
- `review_ready`：已备齐材料，可评审
- `in_execution`：验收执行中
- `blocked`：因环境、阻断缺陷等暂停
- `pass`：通过
- `conditional_pass`：有条件通过
- `fail`：不通过
- `closed`：结论归档完成

**示例格式**：

| 字段 | 示例 |
|------|------|
| 文档标题 | 订单服务 V3.2 验收报告 |
| 当前状态 | `in_execution` |
| 验收负责人 | 张三 |
| 参与角色 | 业务、QA、开发、SRE |
| 计划时间窗 | 2026-05-12 ~ 2026-05-14 |
| 关联需求 | PRD-ORDER-219 |
| 关联设计 | 概要设计 / 详细设计 / 发布说明 |
| 送验版本 | `release-2026.05.12-rc1` |

### 4.3 验收基线与范围

**编写要点**：
- 必须写清楚本次验收的**唯一判断基线**：按哪个需求版本、哪个范围冻结点来判断
- 必须明确 `In Scope` 和 `Out of Scope`，避免验收现场临时加项或临时改口径
- 验收项必须能映射到需求 ID 或设计章节，不能变成“想到什么验什么”
- 已知延期项、拆分到后续版本的项，必须在范围中显式声明

**理论深度**：

验收最常见的争议，不是“系统有没有问题”，而是**双方判断基线不一致**：

- 产品按最新口头想法验
- 开发按上周冻结需求验
- QA 按测试计划验
- 业务按演示预期验

如果基线不固定，验收结论必然失真。因此，验收文档的第一责任不是列用例，而是**固定裁决基线**。

**推荐写法**：

| 维度 | 内容 |
|------|------|
| 需求基线 | `PRD v2.3 (2026-05-08 审批通过)` |
| 范围基线 | `scope-freeze-2026-05-10` |
| 设计基线 | `详细设计 v1.4` |
| 非验收项 | “优惠券批量导入”不在本次范围，转下期 |
| 特殊说明 | 移动端暗黑模式仅验证 iOS，不验证 Android |

**验收范围表示例**：

| 需求 ID | 验收项 | 是否本轮验收 | 说明 |
|---------|--------|-------------|------|
| ORD-001 | 创建订单主流程 | 是 | 核心路径 |
| ORD-002 | 取消订单 | 是 | 含超时取消 |
| ORD-003 | 优惠券核销 | 有条件 | 限单券，不含组合券 |
| ORD-004 | 批量导入 | 否 | 已拆到后续版本 |

### 4.4 进入条件与退出条件

**编写要点**：
- 验收不是随时都能开始，必须定义**进入条件**
- 结论也不是凭感觉给，必须定义**退出条件 / 通过条件 / 驳回条件**
- 进入条件不满足时，应写明“不能开始验收”，而不是带病送验
- 退出条件要能支持明确裁决，而不是“看起来差不多”

**推荐进入条件**：
- 需求、范围、版本已冻结
- 交付包已部署到指定环境
- 测试报告已出，阻断缺陷为 0
- 关键依赖环境可用
- 验收账号、测试数据、工具链已准备齐全

**推荐退出条件**：
- 所有 `P0/P1` 场景已执行完毕
- 所有阻断问题已关闭或明确结论
- 所有证据已归档并可访问
- 非功能项已完成最小验证
- 最终结论与签字已形成

**示例格式**：

| 类别 | 条件 | 是否满足 | 备注 |
|------|------|---------|------|
| 进入条件 | 送验版本已部署到 UAT | 是 | `uat-order-v3.2-rc1` |
| 进入条件 | 阻断缺陷数 = 0 | 是 | 见缺陷列表 |
| 进入条件 | 支付沙箱可用 | 否 | 导致验收阻塞 |
| 退出条件 | 核心场景全部通过 | 待定 | 执行中 |
| 退出条件 | 证据包已归档 | 待定 | 执行后更新 |

### 4.5 验收对象、版本、环境与数据基线

**编写要点**：
- 必须明确“验的是哪一个版本”，不能只写“最新代码”
- 必须写环境地址、依赖版本、数据库 Schema 版本、Feature Flag 状态
- 必须写数据基线：用什么数据、时间窗口、样本量、抽样方式
- 对数据/指标验收，必须写明口径、维度、计算方式和时间范围

**社区实践提炼**：
- 测试验收报告常常要求补充“处置前截图 / 系统反馈消息 / 处置后截图”，本质上是在固定**版本 + 操作 + 结果状态**
- 指标验收文档通常要求写“验证方法 / 数据集链接 / 问题反馈 / 修复状态 / 验收日期 / 验收人 / 结果”，本质上是在固定**数据口径 + 验证方法 + 闭环状态**

**推荐版本基线表**：

| 对象 | 版本 / 标识 | 说明 |
|------|-------------|------|
| 前端 | `web-order@1.8.2-rc1` | 验收页面 |
| 后端 | `order-service:2026.05.12-rc1` | 主服务 |
| 数据库 | `schema-20260511-07` | DDL 基线 |
| 配置 | `config-set order-uat-v12` | 配置集 |
| 开关 | `coupon_combo=false` | 组合券关闭 |
| Commit | `a1b2c3d4` | 构建来源 |

**推荐环境与数据基线表**：

| 维度 | 内容 |
|------|------|
| 验收环境 | `https://uat-order.example.com` |
| 依赖系统 | 支付沙箱、库存 UAT、消息队列 UAT |
| 测试账号 | `buyer_uat_01` / `seller_uat_02` |
| 测试数据 | 10 个 SKU、3 类优惠券、2 个无库存样本 |
| 时间窗口 | 指标验收使用 `2026-05-01 ~ 2026-05-07` |
| 抽样规则 | 随机抽样 100 单 + 边界样本 20 单 |

### 4.6 验收场景 / 用例矩阵

**编写要点**：
- 验收项必须是**可执行场景**，而不是模糊表述
- 每个场景都应有：前置条件、步骤、预期结果、优先级、证据类型
- 场景必须与需求 ID、设计点或问题修复项建立映射
- 核心路径、异常路径、边界路径、回归路径都要覆盖

**坏例子**：
- “验证订单功能正常”
- “看一下数据没问题”

**好例子**：
- “当库存充足且优惠券有效时，买家提交 3 个 SKU 的订单，系统应在 3 秒内返回订单号，并在订单详情页展示 `CREATED` 状态”
- “当库存不足时，系统返回 `ORDER_001`，不创建订单记录，不扣减库存”

**推荐矩阵格式**：

| 场景 ID | 来源需求 | 优先级 | 前置条件 | 执行步骤 | 预期结果 | 证据类型 |
|---------|---------|--------|---------|---------|---------|---------|
| AC-001 | ORD-001 | P0 | 买家已登录，库存充足 | 提交订单 | 返回订单号，状态为 `CREATED` | 截图 + 接口响应 |

### 4.7 执行记录与证据组织

**编写要点**：
- 每个验收项都必须留下可审计证据，不能只写“已通过”
- 证据必须能说明：操作前状态、执行动作、系统反馈、执行后状态
- UI 验收至少应有：**前态截图 + 关键反馈 + 后态截图**
- API 验收至少应有：请求、响应、关键日志或 Trace ID
- 数据验收至少应有：数据源链接 / SQL / 时间窗口 / 计算口径 / 对比结果

**理论深度**：

验收证据不是“材料越多越好”，而是要形成**闭环证据链**：

1. **起点状态**：验证前对象处于什么状态
2. **触发动作**：谁在什么环境、用什么数据、做了什么操作
3. **系统反馈**：接口响应、提示文案、日志、事件、指标变化
4. **终点状态**：执行后状态是否符合预期
5. **定位锚点**：截图编号、Trace ID、日志链接、SQL 链接

如果缺少其中任何一环，证据就容易被质疑。

**不同类型验收的证据要求**：

| 验收类型 | 必备证据 |
|---------|---------|
| UI / 交互 | 操作前截图、操作步骤、系统提示、操作后截图 |
| API / 服务 | 请求参数、响应体、状态码、Trace ID、关键日志 |
| 数据 / 指标 | 数据源、SQL / 报表链接、时间窗口、口径说明、对账结果 |
| 异步流程 | 触发动作、消息 / 事件、最终状态、延迟时间 |
| 性能 / 稳定性 | 测试脚本版本、样本规模、环境说明、结果图表、阈值对比 |

**推荐执行记录表**：

| 场景 ID | 执行人 | 验收日期 | 实际结果 | 证据链接 | 结论 |
|---------|--------|---------|---------|---------|------|
| AC-001 | 李四 | 2026-05-12 | 订单创建成功 | 截图 #12，Trace `abc123` | 通过 |
| AC-002 | 李四 | 2026-05-12 | 返回 `ORDER_001`，DB 无订单记录 | 响应体 #7，SQL #3 | 通过 |
| AC-003 | 王五 | 2026-05-12 | 页面取消成功，但消息延迟 45s | 截图 #18，日志 #11 | 有问题 |

### 4.8 问题、缺陷与复验闭环

**编写要点**：
- 验收发现的问题必须结构化记录，不能只写在聊天记录里
- 每个问题都要有：严重级别、责任人、修复计划、复验结果
- 问题要区分：阻断问题、严重问题、一般问题、建议项
- 验收报告必须体现“首次发现”与“复验通过”两个时点

**推荐严重级别**：
- `Blocker`：阻断验收，核心流程不可用或结论无法给出
- `Critical`：核心能力错误，通常不能直接通过
- `Major`：非阻断但影响明显，需要评估是否允许条件通过
- `Minor`：局部缺陷，不影响主流程，可作为遗留项处理
- `Suggestion`：优化建议，不作为验收阻断依据

**推荐问题闭环表**：

| 问题 ID | 来源场景 | 严重级别 | 问题描述 | 负责人 | 当前状态 | 修复版本 | 复验结果 |
|---------|---------|---------|---------|--------|---------|---------|---------|
| BUG-001 | AC-003 | Critical | 取消后 MQ 延迟 45s，超出 SLA | 赵六 | 已修复 | `rc2` | 通过 |
| BUG-002 | AC-006 | Major | 导出按钮文案错误 | 陈七 | 待修复 | 待定 | 未复验 |
| BUG-003 | AC-009 | Minor | 空列表态图标偏移 | 陈七 | 已接受遗留 | 无 | 不适用 |

**复验记录必须包含**：
- 复验版本
- 复验时间
- 复验人
- 复验步骤摘要
- 复验结论

### 4.9 非功能验收

**编写要点**：
- 验收不能只看功能，至少要检查与本次发布相关的非功能项
- 非功能项应以**量化指标**表达，而不是“性能还可以”
- 不是所有项目都要全量做压测、安全扫描，但至少要声明哪些做了、哪些没做、为什么

**常见非功能项**：
- 性能：P95/P99、吞吐量、批处理时长
- 稳定性：重试、超时、故障恢复
- 安全：鉴权、越权、敏感数据脱敏
- 可观测性：日志、指标、Trace、告警
- 兼容性：浏览器、移动端、上下游协议
- 容量：样本规模、增长预期、资源余量

**推荐格式**：

| 类别 | 验收项 | 阈值 / 标准 | 实际结果 | 证据 | 结论 |
|------|--------|------------|---------|------|------|
| 性能 | 创建订单 P99 | `< 500ms` | `420ms` | 压测报告 #1 | 通过 |
| 安全 | 未登录下单拦截 | 必须拒绝 | 已拒绝，返回 401 | 接口日志 #5 | 通过 |
| 可观测性 | 核心链路 Trace | 必须可串联 | 已可串联 | Trace 样例 #3 | 通过 |
| 兼容性 | iOS / Android / Web | 必须覆盖 | Android 未验证 | 说明 #2 | 风险 |

### 4.10 发布准备与运维门禁

**编写要点**：
- 通过功能验收，不等于可以发布
- 验收文档需要明确记录发布准备状态，尤其是大版本、跨团队项目、数据变更项目
- 必须检查监控、告警、回滚、值守、发布窗口、开关策略
- 如果是有条件通过，必须说明是否允许先进入发布准备，而不是直接默认可上线

**推荐门禁清单**：
- 发布包已固化，版本可追溯
- 回滚预案已演练或经评审确认
- 监控面板和告警阈值已配置
- 关键 Feature Flag 已确认默认值
- 值守负责人和窗口已排好
- 数据迁移脚本已验证可回退或可重放

**示例格式**：

| 项目 | 要求 | 当前状态 | 说明 |
|------|------|---------|------|
| 发布窗口 | 已确认 | 是 | 2026-05-15 22:00 |
| 回滚预案 | 已准备 | 是 | 见 runbook #9 |
| 监控告警 | 已配置 | 是 | 订单失败率、延迟、库存扣减失败 |
| 值守安排 | 已排班 | 否 | 待业务确认 |
| 数据迁移验证 | 已验证 | 是 | 见 SQL 演练记录 |

### 4.11 风险接受与遗留项

**编写要点**：
- 不是所有问题都必须修完才能结束验收，但所有遗留项都必须被显式接受
- 风险接受不是一句“先这样吧”，而是要写清：影响、范围、接受理由、补救计划、截止时间、责任人
- 有条件通过的核心就是把遗留项从“隐性共识”变成“显性承诺”

**推荐格式**：

| 风险 / 遗留项 | 影响范围 | 当前处理 | 接受理由 | 后续计划 | 责任人 | 截止日期 | 批准人 |
|--------------|---------|---------|---------|---------|--------|---------|--------|
| Android 暗黑模式未验 | Android 用户 | 本轮不阻断 | 本次只面向 iOS 灰度 | 下期补验 | 王五 | 2026-05-20 | 产品负责人 |
| 报表延迟 5 分钟 | 运营看板 | 允许短暂延迟 | 不影响交易闭环 | 优化离线链路 | 李四 | 2026-05-25 | 业务负责人 |

### 4.12 最终结论与签字

**编写要点**：
- 最终结论必须清晰，不允许使用“基本通过”“原则上可以”“大体没问题”这类模糊措辞
- 推荐使用三值结论：**通过 / 有条件通过 / 不通过**
- 结论必须说明是否允许进入下一阶段、是否允许发布准备、是否允许正式上线
- 必须写明签字人和日期，不能只有“大家都同意”

**三值结论定义**：

| 结论 | 含义 | 典型条件 |
|------|------|---------|
| 通过 | 满足本轮验收标准，无阻断问题 | 核心场景通过，证据完整，阻断项为 0 |
| 有条件通过 | 允许进入下一阶段，但存在显式遗留项 | 核心场景通过，遗留项已被批准，责任与期限明确 |
| 不通过 | 不满足本轮验收标准，需回退修复后重验 | 核心场景失败、关键风险未接受、证据不足 |

**推荐结论格式**：

| 维度 | 结论 |
|------|------|
| 功能验收 | 通过 |
| 数据验收 | 有条件通过 |
| 非功能验收 | 通过 |
| 发布准备 | 待补值守安排后通过 |
| 总体结论 | 有条件通过 |
| 是否允许进入发布准备 | 是 |
| 是否允许正式上线 | 否，待值守安排确认 |

**签字表示例**：

| 角色 | 姓名 | 结论 | 日期 |
|------|------|------|------|
| 业务负责人 | 张三 | 同意有条件通过 | 2026-05-12 |
| QA 负责人 | 李四 | 同意有条件通过 | 2026-05-12 |
| 开发负责人 | 王五 | 承诺遗留项整改 | 2026-05-12 |
| SRE | 赵六 | 发布准备待补齐 | 2026-05-12 |

### 4.13 如何写一个好的验收文档

一个好的验收文档，通常具备以下特征：

#### 1. 基线固定，而不是边验边改标准
- 文档开头就明确需求版本、范围边界、送验版本
- 现场新增诉求不会直接混入本轮结论，而是转成变更或后续项

#### 2. 场景可执行，而不是抽象评价
- 写“怎么操作、预期是什么、用什么账号和数据”
- 避免“验证正常”“符合预期”这种脱离上下文的判断

#### 3. 证据可审计，而不是口头共识
- 每个重要结论都能找到对应截图、日志、响应、报表或 Trace
- 证据足够支持他人在事后复核

#### 4. 问题有闭环，而不是只罗列
- 问题后面必须跟着责任人、修复状态、复验结果
- 遗留项必须有接受人和截止时间

#### 5. 结论可裁决，而不是语言模糊
- 明确写“通过 / 有条件通过 / 不通过”
- 明确写“能不能进下一阶段、能不能进发布准备、能不能上线”

#### 6. 聚焦当前事实，而不是未来承诺
- 验收判断基于当前版本的真实状态
- “后面会补”“上线前会修”不能替代当前结论，只能作为风险说明

**常见错误**：

| 错误 | 后果 | 修正 |
|------|------|------|
| 只写“已验收通过” | 无法复盘，也无法定责 | 补齐场景、证据、签字 |
| 只贴一堆截图 | 读者看不出结论 | 每张证据绑定场景和结论 |
| 不写非验收项 | 范围漂移 | 显式写 `Out of Scope` |
| 问题只写在群聊里 | 无法闭环 | 统一归档到缺陷表 |
| 用未来承诺代替当前结果 | 结论失真 | 把未来计划放到风险接受表 |
| 只有功能，没有发布门禁 | 容易“验过了但发不了” | 补发布准备检查 |

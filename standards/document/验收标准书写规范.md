# 验收标准书写规范

> 本规范定义 `06-验收标准.md` 最终应该写成什么样。
> 验收标准回答: 在什么条件下交付物算通过、算有条件通过、算不通过。
> 与 `验收标准讨论流程_SOP.md` 的关系: 本规范定义结果结构;SOP 定义生成步骤。
> 与 `05-测试方案.md` 的关系: 测试方案提供验证方案和证据结构;验收标准定义裁决门禁和结论口径。

## 一、验收标准的目标

验收标准不是验收报告,也不是测试用例清单。

它的目标是把需求目标、设计边界、测试证据和风险规则转成可裁决的门禁,使团队能清楚回答:

1. 本轮验收依据哪些需求、设计、测试方案和交付版本。
2. 哪些能力必须满足,哪些不在本轮裁决范围。
3. 什么结果算通过,什么结果算有条件通过,什么结果算不通过。
4. 哪些问题是一票否决。
5. 哪些风险可以接受,由谁接受,需要什么后续动作。
6. 最终结论如何签署和归档。

终极检验标准:

```text
一个未参与项目的人,
只看 06-验收标准.md 和关联证据,
能否判断该交付物是否可以进入下一阶段、发布准备或正式上线。
```

## 二、与上游 / 下游文档的边界

### 2.1 相对需求文档

验收标准承接需求文档中的:

- 目标和非目标
- P0 / P1 / P2 范围
- 功能需求
- 非功能需求
- 业务规则
- 一票否决项

验收标准不重新定义需求,只把需求转成裁决条件。

### 2.2 相对设计文档

验收标准承接架构、概要和详细设计中的:

- 架构边界
- 数据所有权
- 关键对象和流程
- 状态机
- 事务一致性
- 错误恢复
- 审计和观测
- 风险与待确认事项

验收标准不替代设计评审,只判断这些设计约束在交付物中是否成立。

### 2.3 相对测试方案

测试方案回答“怎么测”,验收标准回答“测到什么程度算通过”。

```text
05-测试方案
  -> 测试场景
  -> 用例
  -> 环境
  -> 数据
  -> 自动化门禁
  -> 证据

06-验收标准
  -> 验收项
  -> 通过条件
  -> 失败条件
  -> 一票否决
  -> 风险接受
  -> 最终结论
```

### 2.4 相对实施计划、部署与运维

验收标准可以定义是否允许进入实施下一阶段、发布准备或上线,但不安排具体开发任务和发布步骤。

实施计划和部署运维手册需要引用验收标准中的门禁。

## 三、验收标准章节主链

正式 `06-验收标准.md` 必须使用以下主链。

```text
1. 与上游文档的关系声明
2. 验收目标与范围
3. 验收基线
4. 进入条件与退出条件
5. 功能验收门禁
6. 数据边界与架构红线验收
7. 接口、事件与跨仓同步验收
8. 状态机、事务与一致性验收
9. 非功能验收门禁
10. 可观测性、审计与证据门禁
11. 一票否决项
12. 缺陷分级、复验与放行规则
13. 风险接受与遗留项
14. 最终结论与签署
15. 参考
```

章节不得随意改名。确需增减章节时,必须说明原因。

### 3.1 正式文档与 `design-calibration` 的关系

通过 SOP 生成正式验收标准时，每个正式章节必须在正文开始前标注其校准来源。

固定写法如下：

```md
> 校准来源：
> - `design-calibration/06_acceptance_step_05_function_gate.md`
>
> 延伸阅读：
> - 建议继续阅读上述中间产物的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解本章验收标准结论如何从讨论收敛而来。
```

写法要求：

- 必须引用具体中间产物文件，不能只写 `design-calibration` 目录。
- 如果一个正式章节由多个 Step 合并而来，必须逐条列出对应中间产物。
- 延伸阅读必须说明读者应继续阅读中间产物中的哪些小节。
- 正式章节正文不得新增未在中间产物中出现或未被确认的验收门禁、裁决口径或证据要求。

## 四、通用输出规则

### 4.1 表 / 图 / 清单使用规则

验收标准以门禁表、裁决表和清单为主。

| 表达形式 | 适用场景 | 约束 |
|---|---|---|
| 门禁表 | 功能、非功能、同步、一致性、证据 | 必须有通过条件和失败条件 |
| 清单 | 进入条件、退出条件、一票否决项 | 每项必须可判定 |
| 风险表 | 遗留项、条件通过、风险接受 | 必须有接受人和后续动作 |
| ASCII 图 | 验收裁决流、证据流、发布门禁关系 | 必须有标题和关键说明 |
| 短文 | 解释验收口径 | 不得替代门禁表 |

### 4.2 验收结论三值规则

验收结论只允许使用以下三类:

| 结论 | 含义 | 典型条件 |
|---|---|---|
| 通过 | 满足全部 P0 门禁,无阻断缺陷,证据完整 | 可进入下一阶段或发布准备 |
| 有条件通过 | P0 主线成立,存在已接受遗留项 | 可进入下一阶段,但必须跟踪条件 |
| 不通过 | P0 门禁失败或出现一票否决项 | 必须修复后重验 |

禁止使用:

```text
基本通过
原则上通过
大体没问题
后面补一下
```

### 4.3 验收项编号规则

验收项编号必须稳定。

推荐格式:

```text
AC-<类型>-<三位序号>
```

示例:

```text
AC-FUNC-001
AC-SYNC-002
AC-NFR-003
AC-BLOCKER-001
```

### 4.4 证据引用规则

验收标准不直接粘贴大量测试日志或截图,只引用证据 ID、报告路径、Trace、链接或附件索引。

| 引用对象 | 推荐格式 |
|---|---|
| 测试证据 | `EV-API-001` |
| 测试用例 | `TC-CMD-001` |
| 缺陷 | `BUG-001` |
| 原始 artifact | `artifacts/test/<run_id>/...` |
| 运行报告 | `reports/runs/<run_id>/...` |
| 验收交接报告 | `reports/acceptance/handoff.md` |
| Trace | `trace_id=<id>` |

证据引用必须遵守：

- 验收基线必须固定 `<run_id>`，不得使用 `latest`。
- 正式验收优先引用 `reports/runs/<run_id>/...` 和 `reports/acceptance/...`。
- 需要复核机器原始证据时，再从 report 回指 `artifacts/test/<run_id>/...`。
- 不得引用 `artifacts/test/<project>/<run_id>` 或 `reports/<project>/...`。
- `reports/acceptance/handoff.md`、`reports/acceptance/veto-checklist.md` 和 `reports/acceptance/risk-acceptance.md` 是验收交接的固定入口。

### 4.5 正式章节必须保留校准来源入口

整理正式验收标准时，每个正式章节开头必须回答：

```text
本章引用了哪份中间产物
本章结论来自哪一步讨论
读者应该继续阅读哪份中间产物的结构化中间产物 / 回填草稿 / 待确认事项
```

禁止出现以下写法：

```text
本章由前序讨论得出。
详见 design-calibration。
见 Step 1~15。
```

原因：

```text
这些写法没有给出可点击、可定位、可追溯的具体中间产物入口。
```

正确写法：

```md
> 校准来源：
> - `design-calibration/06_acceptance_step_05_function_gate.md`
>
> 延伸阅读：
> - 建议继续阅读 `design-calibration/06_acceptance_step_05_function_gate.md` 的“结构化中间产物”“回填草稿”和“待确认事项”小节，了解功能验收门禁如何从需求、测试证据和设计红线收敛而来。
```

## 五、章节级规范

### 5.1 与上游文档的关系声明

本章目标:

说明验收标准依据哪些上游文档,以及这些文档如何影响裁决。

必须输出:

| 来源文档 | 验收输入 | 本文如何裁决 |
|---|---|---|
| `00-需求文档.md` | <目标 / 需求 / 非功能 / 一票否决> | <转成验收项和通过条件> |
| `01-架构设计.md` | <边界 / 交互 / 数据所有权> | <转成架构红线验收> |
| `02-概要设计.md` | <主要组成部分 / 流程 / 状态> | <转成功能和状态验收> |
| `03-详细设计.md` | <协议 / 状态机 / 事务 / 错误 / 并发> | <转成接口、一致性和恢复验收> |
| `05-测试方案.md` | <用例 / 证据 / 退出准则> | <作为验收证据来源> |

完成标准:

- 验收依据清楚。
- 不把验收标准写成测试方案或测试报告。

### 5.2 验收目标与范围

本章目标:

定义本轮验收要裁决什么、不裁决什么。

必须输出范围表:

| 验收范围项 | 类型 | 优先级 | 裁决目标 | 非范围 / 说明 |
|---|---|---|---|---|

写法规则:

- 范围必须绑定需求 ID、设计章节、测试证据或风险项。
- 非范围必须说明是否影响最终结论。

### 5.3 验收基线

本章目标:

固定验收裁决所依据的版本、环境、配置和数据。

必须输出:

| 基线类型 | 基线内容 | 版本 / 标识 | 说明 |
|---|---|---|---|
| 需求基线 | <文档> | <版本> | <说明> |
| 设计基线 | <文档> | <版本> | <说明> |
| 测试基线 | <测试方案 / 报告> | <版本 / run_id> | <说明> |
| 交付基线 | <commit / build / image> | <标识> | <说明> |
| 环境基线 | <env> | <配置> | <说明> |
| 数据基线 | <fixture / seed / snapshot> | <标识> | <说明> |
| artifact 基线 | `artifacts/test/<run_id>/...` | <run_id> | <原始机器证据> |
| report 基线 | `reports/runs/<run_id>/...` | <run_id> | <人类可读报告> |
| 验收交接基线 | `reports/acceptance/...` | <review version> | <handoff / veto / risk acceptance> |

### 5.4 进入条件与退出条件

本章目标:

定义什么时候可以开始验收,什么时候可以结束验收。

进入条件:

```md
- [ ] 需求 / 设计 / 测试方案基线已确认
- [ ] 送验版本已固定
- [ ] P0 测试报告或证据已生成
- [ ] 阻断缺陷为 0 或已明确不进入验收
- [ ] 环境、数据、账号和依赖可用
```

退出条件:

```md
- [ ] 全部 P0 验收门禁有结论
- [ ] 一票否决项全部通过
- [ ] 缺陷和复验状态清楚
- [ ] 残余风险已接受或转入待办
- [ ] 最终结论和签署完成
```

### 5.5 功能验收门禁

本章目标:

把 P0/P1 功能需求转成可裁决门禁。

必须输出:

| 验收项 ID | 功能 / 场景 | 优先级 | 通过条件 | 失败条件 | 证据来源 |
|---|---|---|---|---|---|

写法规则:

- 通过条件必须可判定。
- 失败条件必须说明何时不通过。
- P0 功能不得缺少证据来源。

### 5.6 数据边界与架构红线验收

本章目标:

验证架构边界、数据所有权和禁止事项是否成立。

必须输出:

| 红线 ID | 红线 | 通过条件 | 失败条件 | 证据来源 |
|---|---|---|---|---|

常见红线:

- 不保存不属于本仓的数据真相。
- 不绕过上游治理门禁。
- 不让下游反向改写本仓真相。
- 不用 projection / cache 反写真相。
- 不把 P1 能力混入 P0 主链。

### 5.7 接口、事件与跨仓同步验收

本章目标:

验证 Command、Query、Event、Job 和跨仓同步契约是否成立。

必须输出:

| 验收项 ID | 接口 / 事件 / 下游 | 全局依赖类型 | 协作方式 | 通过条件 | 失败条件 | 证据来源 |
|---|---|---|---|---|---|---|

写法规则:

- 每个 P0 outbound event 必须有下游可消费或可重放证据。
- Query 必须验证只读边界。
- Job 必须验证幂等和恢复语义。
- 跨仓验收项必须承接 `全局项目依赖关系与裁剪规则.md` 的依赖类型判断。
- 编译期依赖验收可以验证 package dependency、contract compile 和版本兼容。
- 运行期依赖验收必须验证 API / SDK / adapter 接缝，不得要求源码直接依赖。
- 事件协作依赖验收必须验证 publish / subscribe / replay / projection 证据。

### 5.8 状态机、事务与一致性验收

本章目标:

验证状态转换、事务边界、一致性、幂等和并发控制。

必须输出:

| 验收项 ID | 主题 | 通过条件 | 失败条件 | 证据来源 |
|---|---|---|---|---|
| AC-STATE-001 | <状态合法迁移> | <条件> | <条件> | <证据> |
| AC-TX-001 | <事务原子性> | <条件> | <条件> | <证据> |
| AC-IDEM-001 | <幂等> | <条件> | <条件> | <证据> |

### 5.9 非功能验收门禁

本章目标:

定义性能、安全、可用性、兼容性、容量、可恢复性等非功能通过条件。

必须输出:

| 验收项 ID | 维度 | 指标 / 要求 | 阈值 | 证据来源 | 结论口径 |
|---|---|---|---|---|---|

写法规则:

- 阈值必须有来源。
- 未执行的非功能项必须进入风险接受。

### 5.10 可观测性、审计与证据门禁

本章目标:

验证关键行为是否可追溯、可审计、可复盘。

必须输出:

| 验收项 ID | 证据主题 | 必须存在的证据 | 通过条件 | 失败条件 |
|---|---|---|---|---|

证据类型包括:

- 测试报告
- 自动化报告
- `reports/runs/<run_id>/summary.md`
- `reports/runs/<run_id>/evidence-index.md`
- `reports/runs/<run_id>/gate-results.md`
- `reports/runs/<run_id>/redaction-check.md`
- `reports/acceptance/handoff.md`
- `reports/acceptance/veto-checklist.md`
- `reports/acceptance/risk-acceptance.md`
- Trace
- structured log
- metric
- audit record
- outbox / event record
- DB snapshot
- replay report

写法规则:

- P0 验收门禁必须能追溯到 `reports/runs/<run_id>/evidence-index.md`。
- 一票否决项必须能追溯到 `reports/acceptance/veto-checklist.md` 或等价固定路径。
- 有条件通过必须能追溯到 `reports/acceptance/risk-acceptance.md`。
- 缺少 `reports/acceptance/handoff.md` 时，不得宣称送验交接完整。
- redaction / boundary scan 失败时，不得通过可观测性、审计与证据门禁。

### 5.11 一票否决项

本章目标:

定义任何情况下都不能通过验收的问题。

必须输出:

| 否决项 ID | 否决项 | 原因 | 证据 / 检查方式 |
|---|---|---|---|

写法规则:

- 一票否决项必须来自需求红线、架构红线、详细设计关键不变量或安全/合规要求。
- 一票否决项失败时,总体结论必须为不通过。

### 5.12 缺陷分级、复验与放行规则

本章目标:

定义缺陷对验收结论的影响。

必须输出:

| 缺陷级别 | 定义 | 对结论的影响 | 复验要求 |
|---|---|---|---|
| S | <阻断> | 不通过 | 修复后全量相关回归 |
| A | <主线风险> | 通常不通过或有条件通过 | 修复后回归 |
| B | <一般问题> | 可风险接受 | 抽样复验 |

### 5.13 风险接受与遗留项

本章目标:

定义哪些遗留问题可以有条件接受。

必须输出:

| 风险 / 遗留项 | 影响 | 接受理由 | 后续动作 | 责任人 | 接受人 | 截止时间 |
|---|---|---|---|---|---|---|

写法规则:

- 没有接受人的风险不能支撑有条件通过。
- 一票否决项不能风险接受。

### 5.14 最终结论与签署

本章目标:

记录最终裁决口径和签署角色。

必须输出:

| 维度 | 结论 | 说明 |
|---|---|---|
| 功能验收 | 通过 / 有条件通过 / 不通过 | <说明> |
| 非功能验收 | 通过 / 有条件通过 / 不通过 | <说明> |
| 发布准备 | 通过 / 有条件通过 / 不通过 | <说明> |
| 总体结论 | 通过 / 有条件通过 / 不通过 | <说明> |
| 是否允许进入下一阶段 | 是 / 否 / 有条件 | <说明> |

签署表:

| 角色 | 姓名 / 责任 | 结论 | 日期 |
|---|---|---|---|

## 六、评审清单

| 检查项 | 通过标准 |
|---|---|
| 基线固定 | 需求、设计、测试、交付、环境、数据基线明确 |
| 范围清楚 | In Scope / Out of Scope 可判定 |
| 门禁可裁决 | 每条验收项有通过条件和失败条件 |
| 证据可追溯 | 每个 P0 门禁有证据来源 |
| 校准来源完整 | 每个正式章节都列出对应的 `design-calibration` 中间产物，并引导读者继续阅读 |
| 红线明确 | 架构和数据边界有验收项 |
| 一票否决有效 | 否决项失败会导致总体不通过 |
| 风险不隐藏 | 遗留项有接受理由、责任人、接受人和截止时间 |
| 结论明确 | 只使用通过 / 有条件通过 / 不通过 |
| 签署完整 | 关键角色均有结论和日期 |

## 八、正反例

### 8.1 正确示例

```md
| 验收项 ID | 功能 / 场景 | 优先级 | 通过条件 | 失败条件 | 证据来源 |
|---|---|---|---|---|---|
| AC-FUNC-001 | PublishMethodContent | P0 | state、version、fingerprint、audit、outbox 同事务成立 | 任一缺失或状态不一致 | EV-API-004 / EV-DB-002 |
```

正确原因:

- 有稳定验收项 ID。
- 通过条件和失败条件明确。
- 证据可追溯。

### 8.2 错误示例

```md
发布功能验收通过。
```

错误原因:

- 没有说明按哪个需求和设计裁决。
- 没有通过条件和失败条件。
- 没有证据来源。
- 无法判断是否可复验。

## 1. 适用前提

本 SOP 适用于:

```text
需要为一个仓 / 一个模块 / 一个子系统编写 06-验收标准.md
且希望先通过讨论逐步收敛验收目标、验收基线、门禁、证据、一票否决和风险接受
```

它不适用于:

```text
重新定义需求目标
重新定义测试用例
记录测试执行报告
安排开发实施任务
替代发布 runbook
```

## 2. 核心原则

### 2.1 验收标准是裁决文档

验收标准必须支持“通过 / 有条件通过 / 不通过”的明确判断,不能写成测试过程流水账。

### 2.2 先固定基线,后定义门禁

不先固定需求、设计、测试、交付、环境和数据基线,就不能定义验收门禁。

### 2.3 门禁必须可判定

每条验收项都必须有通过条件、失败条件和证据来源。

### 2.4 风险接受必须显式

有条件通过只能建立在明确风险、接受人、后续动作和截止时间的基础上。

### 2.5 以验收项为裁决小循环主轴

验收标准不能先生成一张全局门禁总表,再事后补证据。必须按验收主题和验收项逐个小循环收敛:

```text
验收主题 / 范围项
  -> 验收项
  -> 设计契约
  -> 测试用例
  -> 证据 ID / report path
  -> 通过条件 / 失败条件
  -> 裁决影响
  -> 验收项停审
```

每个 P0 验收项完成后必须停审:

- 是否有正式设计契约和测试用例来源。
- 是否有固定 evidence ID、report path 和必要 raw artifact 追溯。
- 通过条件和失败条件是否可判定,不是主观描述。
- 失败是否影响“不通过”“有条件通过”或一票否决。
- 是否使用正式字段、状态、接口、事件和错误名称。

所有验收项完成后,必须做跨门禁裁决审计,检查孤儿验收项、孤儿 P0 测试证据、重复或冲突门禁、VETO 覆盖缺口、风险接受越权和证据路径断裂。

### 2.6 中间产物先于正式文档

不得直接跳到正式 `06-验收标准.md`。

执行链路必须是:

```text
本步输入
  -> 应问的问题
  -> SOP 问题回答
  -> Step 中间产物
  -> 回填草稿
  -> 用户确认 / 门禁通过
  -> 正式验收标准章节
```

Step 中间产物必须放在对应子项目的 `design-calibration/` 目录下，并遵循 `standards/document/设计文档讨论中间产物规范.md`。

每个 Step 的中间产物至少包含：

- Step 状态
- 本步输入
- SOP 问题回答
- 当前文档问题诊断
- 改动前后对比
- 验收裁决取舍
- 结构化中间产物
- 回填草稿
- 待确认事项
- 进入下一步条件

推荐中间产物命名:

```text
06_acceptance_calibration_flow.md
06_acceptance_step_01_input_boundary.md
06_acceptance_step_02_scope.md
...
```

### 2.7 ASCII 图输出统一

如本 SOP 中输出验收裁决流、证据流或发布门禁关系图,必须同时收稳:

```text
图类型
图标题
ASCII 图正文
图后 2~5 条关键说明
```

所有 ASCII 图必须遵守 `验收标准书写规范.md` 的通用输出规则。

### 2.8 通用执行纪律

验收标准讨论必须遵守 `设计文档讨论中间产物规范.md` 的“通用执行纪律”：

- 严格按 Step 独立执行，不得合并 Step。
- 本 SOP 只定义验收标准的 Step 顺序和应问问题;Step 内小阶段、模块级先思考后写入、重启模式、旧材料后置差异审计和写入批次规则,统一以 `设计文档讨论中间产物规范.md` 为准。
- Step 开工、用户只说“继续 / 同意 / 开始下一步”、上下文压缩或 agent 切换时,必须先按 `设计文档讨论中间产物规范.md` 的状态台账和上下文恢复门禁读取 `06_acceptance_calibration_flow.md`,确认当前 Step、当前模块和下一动作。
- 明确要求重写 / 重建 / 替换旧文件时，先删除旧文件，再按新文件标准创建。
- 正式 `06-验收标准.md` 的章节必须能追溯到具体 `design-calibration/...` 中间产物。
- 长文档先建骨架，再按 Step 或章节分批写入。
- 单次写入以 100~300 行为宜；预计超过 300 行应拆分；预计超过 500 行必须拆分。
- 100~300 行只约束单次写入批次,不是正式文档、Step 文件或章节最终长度上限。
- 项目级 `/tmp` 计划只能裁剪本项目的必读文档、Step 模块和输出路径,不得重新定义本 SOP 或中间产物规范中的通用流程。
- 功能门禁、红线门禁、接口同步、一致性、非功能、证据、一票否决、缺陷和风险接受等 Step 必须分别裁决。

正确示例：

```text
Step 5 单独定义功能验收门禁。
Step 10 单独定义可观测性、审计与证据门禁。
Step 11 单独定义一票否决项。
正式 06-验收标准.md 每章标注具体 Step 校准来源。
```

错误示例：

```text
把 Step 5~Step 11 合并成“验收门禁总表”。
在旧 06-验收标准.md 上保留旧验收主语，只替换部分门禁名称。
正式章节只写“证据见 05”。
一次性写入 900 行验收标准。
```

错误原因：

- 验收标准是裁决文档，合并门禁会让失败条件和一票否决边界不清。
- 旧验收主语会污染新版裁决口径。
- 未追溯到具体中间产物时，无法审计结论如何收敛。

### 2.9 验收项必须闭环到设计和测试证据

验收标准不能只写“通过 / 不通过”的主观判断。每个 P0 验收项必须同时回指设计契约、测试用例、证据 ID 和固定 report 路径。

正确示例：

```text
AC-SYNC-001
  -> 设计契约: 03 §7 AcceptPublicationCommand / §5 PublicationMaterial
  -> 测试用例: TC-BUS-PUB-002
  -> 证据: EV-API-002 / reports/runs/<run_id>/evidence-index.md
  -> 裁决: 缺 core_event_ref 时不得 accepted
```

错误示例：

```text
AC-SYNC-001
  -> 同步功能基本正常
  -> 证据见测试报告
```

错误原因：

- 没有固定设计契约和证据入口。
- 无法判断测试证据是否覆盖该验收项。
- 读者不能复验，也不能审计结论。

## 3. Step 模板字段

| 字段 | 作用 |
|---|---|
| 本步目标 | 说明本步要解决什么验收裁决问题 |
| 本步输入 | 说明进入本步前必须具备哪些上游信息 |
| 本步输出 | 说明本步必须产出什么结构化结果 |
| 应问的问题 | 用于把输入收敛成输出的问题集合 |
| 期望产出 | 本步应该沉淀的表、图、矩阵或清单 |
| 回填位置 | 指向 `06-验收标准.md` 的章节 |
| 执行约束 | 说明本步允许和禁止的做法 |
| 进入下一步的条件 | 判断本步是否完成的门禁 |

## 4. 建议的讨论总流程

```text
Step 1. 确认验收输入边界
Step 2. 明确验收目标与范围
Step 3. 固定验收基线
Step 4. 定义进入条件与退出条件
Step 5. 定义功能验收门禁
Step 6. 定义数据边界与架构红线验收
Step 7. 定义接口、事件与跨仓同步验收
Step 8. 定义状态机、事务与一致性验收
Step 9. 定义非功能验收门禁
Step 10. 定义可观测性、审计与证据门禁
Step 11. 定义一票否决项
Step 12. 定义缺陷分级、复验与放行规则
Step 13. 定义风险接受与遗留项
Step 14. 定义最终结论与签署口径
Step 15. 整理正式验收标准文档
```

## 5. 每一步的讨论目标、输入与产出

### Step 1. 确认验收输入边界

#### 本步目标

确认验收标准承接哪些需求、设计、测试和交付输入。

#### 本步输入

- `00-需求文档.md`
- `01-架构设计.md`
- `02-概要设计.md`
- `03-详细设计.md`
- `05-测试方案.md`
- 交付版本 / 送验说明

#### 本步输出

- 验收输入映射表
- 验收标准不再回答的问题
- 验收标准必须回答的问题

#### 应问的问题

1. 本轮验收依据哪些需求和设计?
2. 哪些测试证据会支撑验收裁决?
3. 哪些交付版本、环境和数据会成为基线?
4. 哪些内容属于测试方案或实施计划,不应写进验收标准?
5. 是否存在阻塞验收标准生成的上游缺口?

#### 期望产出

| 来源文档 | 验收输入 | 本文如何裁决 |
|---|---|---|

#### 回填位置

`06-验收标准.md` §1。

#### 执行约束

- 不得重新发明需求和测试用例。
- 不得把测试执行结果写入验收标准草案。

#### 进入下一步的条件

- 验收输入和边界清楚。

### Step 2. 明确验收目标与范围

#### 本步目标

定义本轮验收裁决什么、不裁决什么。

#### 本步输入

- Step 1 输入映射
- 需求目标 / 非目标
- 测试方案范围

#### 本步输出

- 验收目标
- 范围 / 非范围表

#### 应问的问题

1. 本轮验收的核心裁决目标是什么?
2. P0/P1/P2 验收范围如何划分?
3. 哪些下游能力只验接缝?
4. 哪些非范围会影响最终结论?
5. 哪些范围项可能成为一票否决?
6. 哪些验收范围必须使用详细设计正式字段、状态或接口名?

#### 期望产出

| 验收范围项 | 类型 | 优先级 | 裁决目标 | 非范围 / 说明 |
|---|---|---|---|---|

#### 回填位置

`06-验收标准.md` §2。

#### 执行约束

- 非范围必须显式。
- 不能用“本次全部验收”代替范围表。

#### 进入下一步的条件

- 验收范围可裁决。

### Step 3. 固定验收基线

#### 本步目标

固定需求、设计、测试、交付、环境和数据基线。

#### 本步输入

- 范围表
- 送验版本
- 测试报告 / 证据 run
- 环境配置

#### 本步输出

- 验收基线表
- artifact / report / acceptance handoff 基线表

#### 应问的问题

1. 按哪一版需求和设计验收?
2. 按哪一版测试方案和测试结果裁决?
3. 送验 build / commit / image 是什么?
4. 环境、配置、数据和依赖是什么?
5. 基线变更如何处理?
6. 本轮验收固定的 `run_id` 是什么?
7. 原始机器证据是否位于 `artifacts/test/<run_id>`?
8. 人类可读报告是否位于 `reports/runs/<run_id>`?
9. 验收交接文件是否位于 `reports/acceptance/`?
10. 是否存在 `latest`、`reports/<project>` 或 `artifacts/test/<project>/<run_id>` 这类不可作为正式基线的引用?

#### 期望产出

| 基线类型 | 基线内容 | 版本 / 标识 | 说明 |
|---|---|---|---|

| 证据入口 | 固定路径 | 版本 / 标识 | 验收用途 |
|---|---|---|---|
| 原始 artifact | `artifacts/test/<run_id>/...` | `<run_id>` | 复核机器原始证据 |
| 运行报告 | `reports/runs/<run_id>/...` | `<run_id>` | 阅读测试摘要、EV 索引和门禁结果 |
| 验收交接 | `reports/acceptance/handoff.md` | `<review version>` | 送验总说明 |
| 一票否决检查 | `reports/acceptance/veto-checklist.md` | `<review version>` | 判断 VETO 是否触发 |
| 风险接受 | `reports/acceptance/risk-acceptance.md` | `<review version>` | 支撑有条件通过 |

#### 回填位置

`06-验收标准.md` §3。

#### 执行约束

- 不得使用“最新版本”作为基线。
- 不得使用 `latest` 作为正式验收基线。
- 不得使用 `artifacts/test/<project>/<run_id>` 或 `reports/<project>`。
- 如果 `reports/acceptance/*` 尚未生成，必须记录为送验前置缺口。

#### 进入下一步的条件

- 基线可定位、可复查。

### Step 4. 定义进入条件与退出条件

#### 本步目标

定义验收开始和结束的门禁。

#### 本步输入

- 验收基线
- 测试方案退出准则

#### 本步输出

- 进入条件
- 退出条件

#### 应问的问题

1. 开始验收前哪些基线必须确认?
2. 哪些测试证据必须先生成?
3. 哪些缺陷会阻断进入验收?
4. 退出验收需要哪些结论?
5. 哪些风险必须先接受?

#### 期望产出

```md
### 进入条件

- [ ] <条件>

### 退出条件

- [ ] <条件>
```

#### 回填位置

`06-验收标准.md` §4。

#### 执行约束

- 条件必须可判定。

#### 进入下一步的条件

- 进入 / 退出条件无模糊项。

### Step 5. 定义功能验收门禁

#### 本步目标

把功能需求和主流程转成验收项。

#### 本步输入

- 需求功能清单
- 详细设计处理流
- 测试方案用例与证据

#### 本步输出

- 功能验收门禁表
- 功能验收项停审记录
- 跨功能门禁裁决审计表

#### 应问的问题

1. 每个 P0 功能的通过条件是什么?
2. 每个 P0 功能的失败条件是什么?
3. 证据来自哪些测试用例或报告?
4. 哪些 P1 功能只做后置边界验收?
5. 哪些功能失败会导致总体不通过?
6. 每个功能验收项能否回指需求 / 设计契约、测试用例、证据 ID 和 report path?
7. 每个功能验收项完成后是否通过停审?
8. 所有功能验收项完成后,是否存在 P0 功能缺门禁、证据重复或裁决影响冲突?

#### 期望产出

| 验收项 ID | 功能 / 场景 | 优先级 | 通过条件 | 失败条件 | 证据来源 |
|---|---|---|---|---|---|

| 验收项 ID | 设计契约 | 测试用例 | 证据 ID | report path | 裁决影响 |
|---|---|---|---|---|---|

#### 功能验收项停审记录

| 验收项 ID | 审查项 | 结论 | 缺口 / 修正 |
|---|---|---|---|

#### 跨功能门禁裁决审计表

| 审计项 | 结论 | 缺口 / 修正 |
|---|---|---|

#### 回填位置

`06-验收标准.md` §5。

#### 执行约束

- 不得只写“功能可用”。
- 每个 P0 功能验收项必须同时写通过条件、失败条件、测试用例、证据 ID、report path 和裁决影响。
- 每个 P0 功能验收项完成后必须停审:设计来源是否正式、证据是否固定、通过 / 失败条件是否可判定、是否误用后续 phase 结果。
- 所有功能验收项完成后必须审计 P0 功能缺门禁、重复证据、冲突裁决、P1 污染 P0 和证据路径断裂。

#### 进入下一步的条件

- P0 功能都有可裁决门禁。
- 功能验收项已停审,跨功能门禁裁决审计没有 unresolved 冲突。

### Step 6. 定义数据边界与架构红线验收

#### 本步目标

把架构边界和数据所有权转成验收红线。

#### 本步输入

- 架构设计数据所有权
- 概要 / 详细设计禁止事项

#### 本步输出

- 架构红线验收表

#### 应问的问题

1. 哪些数据不得由本仓保存?
2. 哪些下游不得反向改写真相?
3. 哪些 projection / cache 不得反写真相?
4. 哪些 P1 能力不得污染 P0?

- 验收标准可作为实施计划和发布准备门禁输入。
- 跨门禁裁决总审计没有 unresolved 冲突。

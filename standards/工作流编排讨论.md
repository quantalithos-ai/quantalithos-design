# 工作流编排讨论

> 核心问题：谁来编排多 Agent 协作？Agent 怎么知道自己该做什么？

---

## 协作的三个层次

```
第一层：阶段流转    — 项目现在在哪个阶段？    → daemon 状态机控制（已有）
第二层：阶段内编排  — 这个阶段内谁先做谁后做？ → 工作流模板驱动（本次讨论）
第三层：即时交互    — 两个 Agent 之间怎么对话？ → 沟通协议（已有）
```

---

## 问题出在哪

当前体系已经具备三类基础能力：

- `6` 个阶段的状态机：由 daemon 控制项目在大阶段之间流转
- 角色身份与规则：通过 `identity.md` 和 `shared_rules` 约束各角色的行为方式
- 即时沟通协议：定义消息类型、`@` 触发和回复格式

但这里存在一个关键断层：**Agent 知道自己是谁，也知道局部规则，却不知道当前是否轮到自己行动。**

具体表现为：

- 不知道现在轮到自己做什么
- 不知道应该等待谁的消息或哪个前置 step 完成
- 不知道做完后应该通知谁
- 不知道整个项目在当前阶段内部推进到了哪一步

换句话说：

- 第一层“阶段流转”已经有了
- 第三层“即时交互”已经有了
- 第二层“阶段内编排”仍然缺失

这意味着现有系统更像是：**一组有身份、有规则、能通信的 Agent**，但还不是一组**能按顺序协作完成项目的 Agent**。

---

## 本次对话形成的结论

这次讨论的核心结论是：**要补上第二层“阶段内编排”，需要引入工作流模板，由 daemon 按模板驱动 Agent。**

可以把整个模式概括为：

- daemon：负责全局控制和 step 推进
- 工作流模板：负责描述阶段内部的协作顺序
- Agent：负责执行当前被分配的 step

因此，Agent 不需要理解完整工作流，它只需要在运行时知道三件事：

| 问题 | 来源 | 示例 |
|------|------|------|
| 我是谁 | `identity.md` | 我是后端开发工程师 |
| 我现在该做什么 | daemon 注入的当前 step | 请实现 `TASK-013`，按 TDD 方式 |
| 我做完后怎么交付 | daemon 注入的完成要求 | 完成后发送 `DELIVERABLE` |

也就是说，**流程感知由 daemon 提供，角色执行由 Agent 负责，整体协作顺序由工作流模板定义。**

---

## 解法：daemon 编排 + 工作流模板 + Agent 执行

**daemon 是指挥，Agent 是演奏者，工作流模板是乐谱。**

### 工作流模板示例（阶段 1）

```yaml
workflow: requirement_analysis
  steps:
    - id: collect
      name: "需求收集"
      actor: tech-lead
      trigger: stage_entered
      action: "与用户一对一沟通，收集需求信息"
      input: project_application
      output: requirement_summary
      next: brainstorm

    - id: brainstorm
      name: "团队头脑风暴"
      actor: all
      trigger: collect.completed
      action: "从各自角度讨论方案和风险"
      input: requirement_summary
      output: discussion_notes
      next: propose

    - id: propose
      name: "方案整理"
      actor: tech-lead
      trigger: brainstorm.completed
      action: "整理讨论结果，向用户展示 2-3 方案"
      input: discussion_notes
      output: proposal
      next: review
      loop_to: brainstorm

    - id: review
      name: "需求评审"
      actor: all
      trigger: proposal.accepted
      action: "全员审查 PRD"
      input: prd_draft
      output: prd_final
      next: null
      gate: user_approval
```

### daemon 驱动流程

```
daemon 状态机进入某阶段
  → 加载对应的工作流模板
  → 执行当前 step
    → @对应 Agent，注入 step 的 action 到 prompt
    → Agent 执行，完成后发送 DELIVERABLE
    → daemon 判断 step.completed
  → 执行下一个 step
  → ...
```

### Agent 只管当前 step

Agent 不需要知道整体流程。daemon 在每个 step 触发时注入上下文：

```
你当前的任务：
  阶段：迭代开发
  步骤：编码实现
  任务工单：TASK-013
  输入：[工单内容]
  完成条件：verification_command 全部通过
  完成后：发送 DELIVERABLE 消息
```

## 工作流模板的来源

### 1. 系统预装标准工作流

```
system_workflows/
  ├── requirement_analysis.yaml
  ├── design_and_planning.yaml
  ├── iterative_development.yaml
  ├── user_review.yaml
  ├── branch_finishing.yaml
  ├── deployment.yaml
  └── bugfix.yaml
```

### 2. 规模裁剪自动选择

| 规模 | 加载的工作流 |
|------|-------------|
| hotfix | bugfix.yaml |
| small | 简化版 requirement_analysis + design_and_planning + iterative_development |
| medium | 全部标准工作流 |
| large | 全部标准工作流，iterative_development 启用并行模式 |

### 3. 用户/公司自定义工作流（高级）

```
company_workflows/       # 优先级高于 system_workflows
  └── iterative_development.yaml
```

## 如何限制角色按给定流程运行

核心原则：**不要主要依赖 Agent 自觉遵守流程，而要把流程控制权收回到 daemon 和工作流模板。**

### 三层约束机制

| 约束层 | 手段 | 强度 | 作用 |
|--------|------|------|------|
| Prompt 层 | 注入当前 step 的任务说明、禁止事项、完成条件 | 弱 | 给 Agent 行为边界和执行指引 |
| 校验层 | gate、output_schema、完成条件检查 | 中 | 阻止未完成或不合规的 step 进入下一步 |
| 状态机层 | daemon 只允许执行当前状态对应的 step | 强 | 从系统侧阻止跳步、越权和乱序执行 |

### 设计原则 1：Agent 只看见当前 step

不要把完整工作流直接暴露给 Agent，而是由 daemon 在触发 step 时注入最小必要上下文：

```text
你当前的任务：
  阶段：迭代开发
  步骤：编码实现
  任务工单：TASK-013
  输入：[工单内容]
  完成条件：verification_command 全部通过
  完成后：发送 DELIVERABLE
```

这样 Agent 不需要理解全局流程，也不应该自行决定进入后续步骤。

### 设计原则 2：工具权限随 step 动态收缩

不同 step 应暴露不同工具集，降低越权执行的可能性：

| Step | 建议开放工具 | 建议限制工具 |
|------|--------------|--------------|
| 需求收集 | 对话、读取上下文、记录结果 | 代码修改、终端执行、分支操作 |
| 方案设计 | 文档编辑、引用上下文 | 代码修改、发布部署 |
| 编码实现 | 代码读写、搜索、测试命令 | 发布生产、合并分支 |
| 代码审查 | 只读代码、评论、差异查看 | 直接改代码、直接提交 |

如果平台支持，工具权限应由 daemon 在 step 进入时动态下发，而不是由 Agent 自由决定。

### 设计原则 3：每个 step 都要有显式完成条件

除了 `input` / `output` / `next`，建议补充以下字段：

```yaml
- id: implement
  actor: developer
  input: task_ticket
  output: code_patch
  done_when:
    - tests_passed
    - deliverable_submitted
  output_schema:
    type: object
    required: [summary, changed_files, verification]
```

约束点：
- 未满足 `done_when`，daemon 不允许 step 标记完成
- 输出不符合 `output_schema`，daemon 要求重试或补充
- gate 未通过，不允许进入 next

### 设计原则 4：把“禁止跳步”做成系统规则，不只写在提示词里

例如：

- 未经过 `proposal.accepted`，不得进入需求评审
- 未经过 `user_approval`，不得进入实现阶段
- 未提供验证结果，不得宣称完成

这些规则应由 daemon 检查，而不是仅由 Agent 在 prompt 中“自觉遵守”。

### 建议的最小落地方案

1. daemon 维护阶段状态 + 当前 step
2. 工作流模板定义 `actor / trigger / input / output / next / gate / done_when / output_schema`
3. Agent 每次只收到一个 step 的上下文
4. step 完成后必须提交结构化 `DELIVERABLE`
5. daemon 校验通过后再推进到下一个 step

这样可以形成一个清晰分工：**流程由系统保证，执行由 Agent 负责，合规由校验层兜底。**

## 现有 LLM 框架是否能满足我们的要求

结论先行：**现有 LLM 框架不能直接满足我们的目标，但也没有必要从零重写一整套底层框架。更合理的路线是：复用底层能力，自研面向 AI 团队协作的编排框架。**

### 为什么通用框架不够

我们当前要解决的，不只是“调用模型”或“让多个 Agent 一起工作”，而是更高一层的问题：

- 有阶段状态机
- 有阶段内工作流模板
- 有角色身份、权限和工具边界
- 有用户审批门禁
- 有项目现场快照和恢复
- 有 PRD、任务卡、DELIVERABLE 等结构化产物
- 有长期项目运行，而不只是一次性任务执行

因此，我们要做的不是普通 Agent Demo，而是一个 **AI 团队协作运行时**。

### 对现有框架的判断

#### 1. LangChain / LangGraph

优点：
- 擅长多步骤工作流、状态传递、条件分支、循环和 checkpoint
- 适合做 step 级执行引擎、结构化输出和工具接入

不足：
- 不直接提供项目阶段语义
- 不直接提供角色体系、权限矩阵、用户审批门禁
- 不直接解决项目快照恢复和团队协作协议

判断：**适合作为工作流执行底座，不适合作为完整产品框架。**

#### 2. CrewAI

优点：
- 擅长角色分工、任务拆分和多 Agent 协作
- 适合快速验证“多角色协作”是否有效

不足：
- 更偏任务协作，不偏项目治理
- 对严格流程控制、阶段状态机、长期项目状态支持不足
- 不适合直接承载硬门禁、权限收缩、阶段恢复等需求

判断：**适合作为协作抽象参考，不适合作为平台内核。**

#### 3. Hermes Agent 类系统

优点：
- 擅长长期运行、记忆、技能、工具系统、MCP 接入和委派
- 适合做 Agent runtime 和长期上下文平台

不足：
- 不直接提供项目阶段状态机
- 不直接提供工作流模板 DSL
- 不直接提供任务卡流转、审批门禁和项目群组编排

判断：**适合作为运行时能力参考，不足以直接支撑我们的业务编排层。**

### 我们真正缺的是什么

不是“再找一个更强的 Agent 框架”，而是补出我们自己的核心框架层：

- StageMachine：管理阶段 0 到阶段 5 的流转
- WorkflowEngine：管理阶段内 step 的触发、推进、回退和循环
- RoleRuntime：管理 identity、shared_rules 和 permissions
- GateKeeper：管理 user approval、done_when、output_schema
- ProjectSnapshot：管理项目现场快照和恢复
- ArtifactSystem：管理 PRD、任务卡、会议纪要、交付物等结构化产物

这部分基本没有通用框架会替我们做好，因为它本身就是产品定义的一部分。

### 建议的技术路线

推荐路线不是“完全依赖现成框架”，也不是“从零重写全部底层”，而是：

```text
上层：自研 AI 团队协作编排框架
  - 阶段状态机
  - 工作流模板解析
  - step 调度器
  - gate / approval
  - deliverable schema
  - role permission runtime
  - snapshot / recovery
  - project docs / task cards / artifacts

下层：复用现有通用能力
  - 模型调用 SDK
  - tool calling
  - 结构化输出
  - graph/state 执行引擎
  - checkpoint
  - MCP / RAG / memory
```

一句话：**底层复用，核心自研。**

### 哪些能力适合复用

可以优先复用的能力：
- 模型调用与 provider 适配
- 工具调用层
- 结构化输出
- RAG / 检索能力
- graph 执行、checkpoint、部分持久化
- MCP 接入
- 子 Agent 委派能力

### 哪些能力必须自研

必须自研的核心能力：
- 项目阶段状态机
- 工作流模板 DSL
- step 调度器
- 用户审批门禁
- DELIVERABLE 校验
- 角色模板系统
- 权限运行时
- 项目现场快照与恢复
- 项目群组协作协议
- PRD / 任务卡 / 设计文档等领域对象

### 当前建议

如果目标只是做 Demo，现有框架已经够用；但如果目标是做一个长期运行、可审计、可恢复、可控流程的 AI 公司协作平台，就必须有我们自己的框架层。

因此，下一步讨论不应停留在“选哪个框架”，而应转向：

- 我们自研框架的最小边界是什么？
- 哪些模块必须第一版就做？
- 哪些底层能力可以先借用现成框架？
- 如何先跑通阶段 0 → 阶段 1 → 阶段 2 的最小闭环？

## 流程图是否可以作为工作流设计载体

可以，而且非常适合我们的系统。但前提是：**流程图不能只作为“给人看的说明图”，而要能映射到真正可执行的工作流模板。**

也就是说，我们后续设计的“开发流程图”，最好同时承担两层作用：

- 面向人：帮助理解整个软件开发流程、角色分工和依赖关系
- 面向系统：能够映射到 step、trigger、actor、artifact、gate、permission 等结构化字段

如果只是普通流程图，它只能表达“看起来应该怎么走”；如果能映射到工作流运行时，它才真正能够用于约束 Agent 按流程协作。

### 推荐的三层图模型

建议不要只画一张总图，而是分成三层：

#### 1. 总流程图

描述项目级或阶段级的主流程，回答：
- 当前处于哪一步
- 上一步完成后进入哪里
- 哪些节点可并行
- 哪些节点有门禁

例如：任务拆解 → 并行开发 → 代码审查 → 测试验证 → 集成验收。

#### 2. 角色子图

从单个角色视角描述它自己的执行路径，回答：
- 我何时被触发
- 我拿到什么输入
- 我要产出什么
- 我做完交给谁

例如后端开发子图可以是：
收到任务 → 阅读任务卡 → 编写测试 → 实现代码 → 运行验证 → 提交 DELIVERABLE → 等待审查。

#### 3. 编排约束图

描述系统如何保证 Agent 不跳步、不越权、不乱序，回答：
- 当前 step 允许哪个 actor 执行
- 当前 step 开放哪些工具
- 必须提交哪些交付物
- 满足什么条件才能进入下一步

这一层非常关键，因为它把“图”从说明材料变成运行时约束模型。

### 软件开发流程图中建议包含的组件

如果后续要形成统一图语言，建议至少支持以下组件：

#### 1. 开始 / 结束节点

表示流程入口和出口，例如：开始、阶段完成、任务关闭、阻塞终止。

建议符号：
- 圆形或圆角椭圆：开始 / 结束

#### 2. 动作节点

表示某个角色执行一个动作，例如：收集需求、实现接口、运行测试、提交交付物。

建议符号：
- 矩形：普通动作节点

#### 3. 决策节点

表示条件分支，例如：测试是否通过、用户是否批准、是否需要回退、是否需要新增角色。

建议符号：
- 菱形：条件判断

#### 4. 并行 / 汇合节点

用于表达前后端并行开发、测试和 DevOps 并行准备、多任务并行推进等情况。

建议表示：
- fork / join 节点
- 或一对显式的“并行开始 / 并行结束”节点

#### 5. 子流程节点

表示一个节点可以展开为更细的子图，例如：后端开发子流程、需求评审子流程、代码审查子流程。

建议符号：
- 双边框矩形或 `subprocess` 节点

#### 6. 产物节点

用于表达流程中的结构化产物，例如：PRD、任务卡、API 文档、测试报告、DELIVERABLE。

建议符号：
- 文档节点
- 或统一使用 `{Artifact}` 形式标识

#### 7. 状态 / 存储节点

用于表达运行时状态和持久化对象，例如：`project-state.yaml`、`snapshot`、`tasks/`、`requirements/`。

建议符号：
- 数据存储节点或圆柱体

#### 8. 消息 / 事件节点

这是 Agent 协作系统与普通软件流程图的关键区别。流程里不只是函数调用，还有：
- `@tech-lead`
- `@backend-dev`
- `DELIVERABLE`
- `BUG_REPORT`
- `proposal.accepted`
- `user_approval`

建议表示：
- 事件节点
- 或在箭头上显式标注事件名

#### 9. 门禁节点

用于表示“不是角色自己说完成就算完成”，而是需要系统或用户批准，例如：
- 用户审批
- deliverable schema 校验
- done_when 条件校验
- review 全部完成

建议把门禁单独建模，而不是混入普通判断节点。

#### 10. 角色泳道

如果图涉及多个 Agent 协作，建议用泳道图区分：
- 用户
- daemon
- Tech Lead
- 前端开发
- 后端开发
- 测试
- DevOps

这样可以清楚表达：谁触发谁、谁等待谁、谁产出什么。

### 推荐的基础符号系统

为了便于统一语言，可以先约定一套轻量符号：

- `(Start / End)`：开始 / 结束
- `[Action]`：动作节点
- `<Decision?>`：决策节点
- `[[Subflow]]`：子流程节点
- `{Artifact}`：产物节点
- `((Store))`：状态 / 存储节点
- `@Role`：角色标识
- `-->`：控制流
- `==>`：消息或交付物流
- `||`：并行分叉 / 汇合

### 一个简化示例

下面是“TL 分配任务给前后端，并按流程推进”的简化总图：

```text

   |
   v
[TL 创建任务卡]
   |
   v
<是否可并行开发?>
   |是
   v
================ 并行开始 ================
   |                                      |
   v                                      v
[[前端开发子流程]]                    [[后端开发子流程]]
   |                                      |
   | ==> {FE_DELIVERABLE}                 | ==> {BE_DELIVERABLE}
   |                                      |
   +-------------------+------------------+
                       |
                       v
                [TL 代码审查]
                       |
                       v
                <审查通过?>
                  |是      |否
                  v        v
            [测试工程师验证]  [打回对应开发]
                  |
                  v
             <测试通过?>
               |是    |否
               v      v
            (完成)  [创建 BUG_REPORT]
                        |
                        v
                    [[修复子流程]]
```

### 为什么流程图本身还不够

流程图只能表达“应该怎样走”，不能自动约束 Agent。真正的约束来自：

- 图节点映射到 workflow step
- 每个 step 绑定 actor
- 每个 step 绑定输入 / 输出
- 每个 step 绑定工具权限
- 每个 step 绑定 done_when / gate / output_schema
- 运行时由 daemon 决定当前允许谁执行

也就是说：
- 图是给人理解的
- 模板是给系统执行的
- 权限和门禁是给 Agent 上锁的

### 我们的平台特有组件

因为我们的系统是多 Agent 协作平台，不是普通 BPMN 工具，所以建议额外强调这些专有组件：

- 审批节点：用户批准、TL 批准
- 消息节点：`@触发`、`DELIVERABLE`、`BUG_REPORT`
- 权限节点：进入 step 时切换工具权限
- 校验节点：schema 校验、done_when 校验
- 快照节点：保存现场、支持恢复
- 回退节点：失败后回到指定 step

### 当前结论

如果后续要把流程图作为系统设计基础，建议遵循一个原则：**每个图节点都应该能映射到一个结构化 step。**

这样最终形成的就不是“画给人看的图”，而是：
- 可读的总流程图
- 可展开的角色子图
- 可执行的工作流模板
- 可运行的 Agent 编排规则

## 节点元模型：哪些字段必填，哪些节点必须可执行

为了让流程图不只是“展示图”，而能真正映射到工作流运行时，建议把节点分成三类：

- 执行节点：会进入调度器，真正推动流程前进
- 运行时引用节点：不主动执行，但会被执行节点读写
- 展示节点：只用于人理解，不参与运行时调度

### 一、可执行节点的公共必填字段

凡是会进入运行时的节点，建议至少具备这些公共字段：

| 字段 | 含义 |
|------|------|
| `id` | 节点唯一 ID |
| `type` | 节点类型 |
| `name` | 节点名称 |
| `stage` | 所属阶段 |
| `lane` | 所属泳道 / 角色 |
| `input` | 输入对象 |
| `output` | 输出对象 |
| `next` | 成功后的下一节点 |
| `on_fail` | 失败后的去向 |
| `status` | 当前状态 |
| `description` | 节点说明 |

这些字段让系统能够回答：这是什么节点、谁来执行、拿什么做、产出什么、下一步去哪。

### 二、各类节点的必填字段

#### 1. Action 节点

用于表示真正由某个 Agent 执行的动作，例如：实现页面、运行测试、提交交付物。

必填字段：
- `id`
- `type: action`
- `actor`
- `goal`
- `input`
- `output`
- `allowed_tools`
- `done_when`
- `output_schema`
- `next`
- `on_fail`

示例：

```yaml
- id: fe_implement
  type: action
  actor: frontend-dev
  goal: "实现标签筛选页面"
  input: [task_card, ui_spec, api_spec]
  output: [fe_code_patch, fe_verification_report]
  allowed_tools: [read_code, edit_code, run_test]
  done_when:
    - build_passed
    - deliverable_submitted
  output_schema: fe_deliverable_schema
  next: fe_review_wait
  on_fail: fe_fix
```

#### 2. Decision 节点

用于表示条件分支，例如：测试是否通过、用户是否同意、是否需要回退。

必填字段：
- `id`
- `type: decision`
- `condition`
- `evaluator`
- `branches`

#### 3. Gate 节点

用于表示门禁，不是普通分支，而是必须满足外部批准或系统校验。

必填字段：
- `id`
- `type: gate`
- `gate_kind`
- `checker`
- `required`
- `on_pass`
- `on_reject`

#### 4. EventWait 节点

用于表示等待消息或事件，例如等待 `DELIVERABLE`、等待用户审批。

必填字段：
- `id`
- `type: event_wait`
- `event`
- `source`
- `timeout`
- `next`

#### 5. Fork / Join 节点

用于表达并行分叉与并行汇合。

`fork` 必填字段：
- `id`
- `type: fork`
- `branches`
- `join`

`join` 必填字段：
- `id`
- `type: join`
- `wait_for`
- `merge_rule`
- `next`

#### 6. Subflow 节点

用于表示主流程中的某一步其实引用一个可展开的子流程。

必填字段：
- `id`
- `type: subflow`
- `workflow_ref`
- `actor`
- `input_mapping`
- `output_mapping`
- `completion_rule`
- `next`

示例：

```yaml
- id: fe_subflow
  type: subflow
  workflow_ref: frontend_task_execution
  actor: frontend-dev
  input_mapping:
    task: TASK-FE-013
    ui_spec: UI-SPEC-02
    api_spec: API-SPEC-05
  output_mapping:
    fe_deliverable: artifacts.fe_deliverable
  completion_rule:
    - subflow.status == completed
  next: tl_review
```

### 三、运行时引用节点的必填字段

#### 1. Artifact 节点

用于表示流程中的结构化产物，如 `PRD`、`任务卡`、`测试报告`、`DELIVERABLE`。

必填字段：
- `id`
- `type: artifact`
- `schema`
- `producer`
- `path`

#### 2. Store 节点

用于表示项目状态、快照、任务目录等运行时状态存储。

必填字段：
- `id`
- `type: store`
- `store_ref`
- `mode`

### 四、展示节点

下面这些节点可以只存在于可视化层，不必进入执行引擎：

- `lane`：泳道
- `group`：分组框
- `note`：说明注释
- `legend`：图例
- `phase_label`：阶段标题
- 颜色、边框样式、视觉标签

它们帮助人理解，但不会驱动运行时推进。

### 五、哪些节点必须能执行

必须进入运行时的节点：
- `start`
- `end`
- `action`
- `decision`
- `gate`
- `event_wait`
- `fork`
- `join`
- `subflow`

运行时可引用但不主动调度的节点：
- `artifact`
- `store`

仅用于展示的节点：
- `lane`
- `group`
- `note`
- `legend`
- `phase_label`

## 简单例子：从前端子任务开始，说明节点推进与子流回填

假设主需求是：

- `REQ-001`：博客系统增加标签功能

Tech Lead 在设计与规划阶段拆出两个子任务：

- `TASK-FE-013`：实现标签筛选页面
- `TASK-BE-014`：实现标签查询接口

下面只看前端子任务的子流程，以及它如何回到主流程。

### 一、主流程图

```text
(Start)
   |
   v
[TL 拆解主任务]
   |
   v
<是否可前后端并行?>
   |是
   v
============ 并行开始 ============
   |                            |
   v                            v
[[前端任务子流]]            [[后端任务子流]]
   |                            |
   | ==> {FE_DELIVERABLE}       | ==> {BE_DELIVERABLE}
   |                            |
   +-------------+--------------+
                 |
                 v
            [TL 汇总审查]
                 |
                 v
            [测试验证]
                 |
                 v
               (完成)
```

这里：
- `[[前端任务子流]]` 是一个 `subflow` 节点
- 前端子流完成后，需要把 `FE_DELIVERABLE` 回填到主流程
- 主流程不会立刻继续，而是要等后端子流也完成，并在 `join` 节点汇合

### 二、前端子流图

```text
(Start: TASK-FE-013 assigned)
   |
   v
[读取任务卡 / 设计稿 / API 说明]
   |
   v
[实现页面与交互]
   |
   v
[运行前端测试与构建]
   |
   v
<验证通过?>
  |是         |否
  v           v
[提交 FE_DELIVERABLE]   [修复问题]
   |                      |
   +----------<-----------+
   |
   v
(End: subflow completed)
```

### 三、这个子流对应的可执行模型

```yaml
workflow: frontend_task_execution
nodes:
  - id: start
    type: start
    next: fe_read_context

  - id: fe_read_context
    type: action
    actor: frontend-dev
    goal: "阅读任务卡、UI 设计稿和 API 说明"
    input: [task_card, ui_spec, api_spec]
    output: [implementation_plan]
    allowed_tools: [read_docs, read_code]
    done_when:
      - deliverable_submitted
    output_schema: implementation_plan_schema
    next: fe_implement
    on_fail: blocked

  - id: fe_implement
    type: action
    actor: frontend-dev
    goal: "实现标签筛选页面"
    input: [implementation_plan]
    output: [fe_code_patch]
    allowed_tools: [read_code, edit_code]
    done_when:
      - code_changed
    output_schema: code_patch_schema
    next: fe_verify
    on_fail: fe_fix

  - id: fe_verify
    type: action
    actor: frontend-dev
    goal: "运行前端测试与构建"
    input: [fe_code_patch]
    output: [verification]
    allowed_tools: [run_test]
    done_when:
      - verification_generated
    output_schema: verification_schema
    next: fe_check
    on_fail: fe_fix

  - id: fe_check
    type: decision
    evaluator: daemon
    condition: "verification.pass == true"
    branches:
      yes: fe_submit
      no: fe_fix

  - id: fe_fix
    type: action
    actor: frontend-dev
    goal: "修复构建或测试问题"
    input: [verification]
    output: [fe_code_patch]
    allowed_tools: [read_code, edit_code, run_test]
    done_when:
      - issue_fixed
    output_schema: fix_report_schema
    next: fe_verify
    on_fail: blocked

  - id: fe_submit
    type: action
    actor: frontend-dev
    goal: "提交 FE_DELIVERABLE"
    input: [fe_code_patch, verification]
    output: [fe_deliverable]
    allowed_tools: [write_artifact]
    done_when:
      - deliverable_submitted
    output_schema: fe_deliverable_schema
    next: end
    on_fail: blocked

  - id: end
    type: end
```

## LLM 框架应该如何设计，才能推动节点流转

这里的“框架”不只是模型调用层，而是工作流运行时。建议至少包含下面几个模块：

### 1. WorkflowDefinition

职责：
- 保存图定义与 YAML 配置
- 保存节点和边关系
- 保存子流引用
- 保存 schema、权限、门禁和分支规则

### 2. ExecutionState

职责：
- 记录当前流程运行到哪个节点
- 记录各节点状态
- 记录 artifacts、deliverables、snapshots
- 支持子流状态和父流程状态分别持久化

主流程示意：

```yaml
project_state:
  workflow: main_dev_flow
  current_node: fe_subflow
  node_status:
    fe_subflow: in_progress
    be_subflow: in_progress
  artifacts:
    fe_deliverable: null
    be_deliverable: null
```

子流示意：

```yaml
subflow_state:
  workflow: frontend_task_execution
  current_node: fe_implement
  node_status:
    fe_read_context: completed
    fe_implement: in_progress
```

### 3. Scheduler / TransitionEngine

职责：
- 找出当前可执行节点
- 把节点分配给正确 actor
- 在节点完成后，根据 `next`、`on_fail`、`branches` 推进到下一个节点
- 在 `join` 节点等待并行分支全部完成

### 4. AgentRuntime

职责：
- 只把当前节点的上下文注入给对应 Agent
- 动态下发工具权限
- 屏蔽全局流程，避免 Agent 自行跳步

例如给前端工程师的注入内容应类似：

```text
你当前的任务：
工作流：frontend_task_execution
节点：fe_implement
角色：frontend-dev
目标：实现标签筛选页面
输入：
- TASK-FE-013
- UI-SPEC-02
- API-SPEC-05
允许工具：
- 读取代码
- 编辑前端代码
禁止：
- 修改后端代码
- 跳过验证
完成条件：
- 产出 fe_code_patch
完成后：
- 提交结构化 DELIVERABLE
```

### 5. ValidationEngine

职责：
- 校验节点输出是否符合 `output_schema`
- 校验是否满足 `done_when`
- 校验是否使用了允许的工具和路径
- 决定节点是否允许标记为 completed

### 6. EventBus / ArtifactBus

职责：
- 传递 `TASK_ASSIGNED`、`NODE_COMPLETED`、`DELIVERABLE_SUBMITTED`、`SUBFLOW_COMPLETED` 等事件
- 作为节点推进和子流回填的事件基础设施

---

## 一个节点完成后，如何推进到下一个节点

以 `fe_verify` 节点为例：

1. 前端 Agent 执行 `fe_verify`
2. 返回结构化结果，例如：

```json
{
  "node_id": "fe_verify",
  "actor": "frontend-dev",
  "status": "done",
  "artifacts": {
    "verification": {
      "build_passed": true,
      "tests_passed": true,
      "command": "npm test && npm run build"
    }
  }
}
```

3. `ValidationEngine` 校验：
- 是否是当前节点的结果
- schema 是否匹配
- `verification` 是否存在
- 是否满足 `done_when`

4. 校验通过后：
- 将 `fe_verify` 标记为 `completed`
- 写入 artifact store
- 发出 `NODE_COMPLETED(fe_verify)` 事件

5. `TransitionEngine` 根据图定义推进：
- `next = fe_check`
- `fe_check` 是 `decision` 节点，由 daemon 自己判断
- 若 `verification.pass == true`，进入 `fe_submit`
- 否则进入 `fe_fix`

这里的关键点是：**不是 Agent 自己决定“下一步做什么”，而是 runtime 根据图定义推进。**

---

## 子流完成后，如何反馈给主任务流程

主流程中的 `fe_subflow` 节点可以这样定义：

```yaml
- id: fe_subflow
  type: subflow
  workflow_ref: frontend_task_execution
  input_mapping:
    task_card: TASK-FE-013
    ui_spec: UI-SPEC-02
    api_spec: API-SPEC-05
  output_mapping:
    fe_deliverable: artifacts.fe_deliverable
  completion_rule:
    - subflow.end_reached == true
  next: tl_review
```

当子流运行到 `end` 时，发生以下事情：

1. 子流状态被标记为 `completed`
2. 子流最后产出的 `fe_deliverable` 写回父流程
3. 父流程中的 `fe_subflow` 节点被标记为 `completed`
4. 系统发出 `SUBFLOW_COMPLETED(fe_subflow)` 事件
5. 父流程检查是否满足继续推进条件

如果主流程当前处于并行阶段，则：
- 前端子流完成，不代表主流程立刻继续
- 还要等待 `be_subflow` 也完成
- 到 `join` 节点汇合后，才能继续进入 `TL 汇总审查`

可以把它理解为：
- 子流是函数内部执行过程
- 主流程是函数调用者
- `output_mapping` 就像函数返回值

## 当前结论

如果后续要把流程图真正用于驱动 Agent 协作，建议遵循以下原则：

- 每个可执行节点都必须有明确字段，而不是只有图形
- 展示节点与执行节点必须分层，不要混用
- 子流程必须支持 `input_mapping` 和 `output_mapping`
- 节点推进权必须在 runtime，不在 Agent 手里
- 子流完成后必须通过事件和 artifacts 回填主流程

这样，流程图才能真正落地成：
- 可视化设计层
- 可执行模板层
- 可运行的 LLM 编排层

## 边（Edge）元模型：节点之间如何连接与推进

定义完节点之后，还需要定义“边”。因为真正让流程跑起来的，不只是节点本身，而是：**在什么条件下，从哪个节点流转到哪个节点。**

如果节点定义的是“做什么”，那么边定义的就是“何时推进、为什么推进、推进到哪里”。

### 一、边的公共必填字段

凡是会参与运行时推进的边，建议至少具备以下公共字段：

| 字段 | 含义 |
|------|------|
| `id` | 边唯一 ID |
| `type` | 边类型 |
| `from` | 起始节点 |
| `to` | 目标节点 |
| `label` | 边的显示名称 |
| `trigger` | 触发条件或触发事件 |
| `priority` | 多条边同时可用时的优先级 |
| `guard` | 边生效前需要满足的额外约束 |
| `status` | 是否启用 |
| `description` | 说明 |

这些字段让系统能够回答：这条边从哪来、到哪去、什么时候能走、和其他边冲突时先走哪条。

### 二、边的主要类型

#### 1. Sequence Edge（顺序边）

用于表示最普通的顺序流转：上一个节点完成后进入下一个节点。

必填字段：
- `id`
- `type: sequence`
- `from`
- `to`
- `trigger: node.completed`

示例：

```yaml
- id: edge_fe_impl_to_verify
  type: sequence
  from: fe_implement
  to: fe_verify
  trigger: fe_implement.completed
```

#### 2. Conditional Edge（条件边）

用于表示带判断的分支边，通常从 `decision` 节点流出。

必填字段：
- `id`
- `type: conditional`
- `from`
- `to`
- `condition`
- `priority`

示例：

```yaml
- id: edge_check_yes
  type: conditional
  from: fe_check
  to: fe_submit
  condition: verification.pass == true
  priority: 10

- id: edge_check_no
  type: conditional
  from: fe_check
  to: fe_fix
  condition: verification.pass == false
  priority: 10
```

#### 3. Event Edge（事件边）

用于表示由外部消息或系统事件触发的流转，例如：`DELIVERABLE_SUBMITTED`、`user_approval`、`BUG_REPORT_CREATED`。

必填字段：
- `id`
- `type: event`
- `from`
- `to`
- `event_name`
- `source`

示例：

```yaml
- id: edge_wait_deliverable
  type: event
  from: wait_fe_deliverable
  to: fe_review_gate
  event_name: FE_DELIVERABLE_SUBMITTED
  source: frontend-dev
```

#### 4. Failure Edge（失败边）

用于表示节点执行失败、校验失败或被阻塞时的回退路径。

必填字段：
- `id`
- `type: failure`
- `from`
- `to`
- `trigger`
- `reason_code`

示例：

```yaml
- id: edge_verify_fail
  type: failure
  from: fe_verify
  to: fe_fix
  trigger: fe_verify.failed
  reason_code: verification_failed
```

#### 5. Loop Edge（循环边）

用于表示流程回到前面某个节点，例如修改后重新测试、用户反馈后回到方案讨论。

必填字段：
- `id`
- `type: loop`
- `from`
- `to`
- `trigger`
- `loop_kind`

示例：

```yaml
- id: edge_fix_back_to_verify
  type: loop
  from: fe_fix
  to: fe_verify
  trigger: fe_fix.completed
  loop_kind: retry
```

#### 6. Fork Edge（并行分叉边）

用于从一个节点进入多个并行分支，常见于任务拆解后前后端并行开发。

必填字段：
- `id`
- `type: fork_branch`
- `from`
- `to`
- `fork_group`

示例：

```yaml
- id: edge_fork_fe
  type: fork_branch
  from: dev_fork
  to: fe_subflow
  fork_group: impl_parallel

- id: edge_fork_be
  type: fork_branch
  from: dev_fork
  to: be_subflow
  fork_group: impl_parallel
```

#### 7. Join Edge（并行汇合边）

用于多个分支结束后汇合到同一个节点。

必填字段：
- `id`
- `type: join_branch`
- `from`
- `to`
- `join_group`

示例：

```yaml
- id: edge_fe_to_join
  type: join_branch
  from: fe_subflow
  to: impl_join
  join_group: impl_parallel

- id: edge_be_to_join
  type: join_branch
  from: be_subflow
  to: impl_join
  join_group: impl_parallel
```

#### 8. Subflow Return Edge（子流返回边）

用于表示子流程完成后，把控制权与输出返回给父流程。

必填字段：
- `id`
- `type: subflow_return`
- `from`
- `to`
- `output_mapping`
- `trigger`

示例：

```yaml
- id: edge_fe_subflow_return
  type: subflow_return
  from: fe_subflow.end
  to: fe_subflow
  output_mapping:
    fe_deliverable: artifacts.fe_deliverable
  trigger: subflow.completed
```

### 三、哪些边必须进入执行引擎

必须进入 runtime 的边：
- `sequence`
- `conditional`
- `event`
- `failure`
- `loop`
- `fork_branch`
- `join_branch`
- `subflow_return`

只用于展示、可以不进入 runtime 的边：
- 注释连接线
- 分组框辅助连线
- 图例说明连线
- 纯视觉对齐线

也就是说，**只有真正影响流转逻辑的边才进入执行模型。**

### 四、前端子任务例子：边如何推动节点前进

继续使用 `TASK-FE-013` 的例子。前端子流中的核心边如下：

```yaml
edges:
  - id: e1
    type: sequence
    from: start
    to: fe_read_context
    trigger: workflow.started

  - id: e2
    type: sequence
    from: fe_read_context
    to: fe_implement
    trigger: fe_read_context.completed

  - id: e3
    type: sequence
    from: fe_implement
    to: fe_verify
    trigger: fe_implement.completed

  - id: e4
    type: conditional
    from: fe_check
    to: fe_submit
    condition: verification.pass == true
    priority: 10

  - id: e5
    type: conditional
    from: fe_check
    to: fe_fix
    condition: verification.pass == false
    priority: 10

  - id: e6
    type: loop
    from: fe_fix
    to: fe_verify
    trigger: fe_fix.completed
    loop_kind: retry

  - id: e7
    type: sequence
    from: fe_submit
    to: end
    trigger: fe_submit.completed
```

这组边定义出来后，运行时就能明确：
- 开始后先进入 `fe_read_context`
- 实现完成后进入 `fe_verify`
- 判断成功则去 `fe_submit`
- 判断失败则去 `fe_fix`
- 修复完成后重新回到 `fe_verify`

也就是说，**节点负责执行，边负责推进。**

### 五、任务完成后如何推进到下一个节点

以 `fe_submit` 节点为例：

1. 前端 Agent 提交结构化 `FE_DELIVERABLE`
2. `ValidationEngine` 校验 `output_schema`
3. `ExecutionState` 将 `fe_submit` 标记为 `completed`
4. `EventBus` 发出 `fe_submit.completed`
5. `TransitionEngine` 查找所有 `from = fe_submit` 的边
6. 找到 `e7: fe_submit -> end`
7. 满足触发条件后，将当前节点推进到 `end`

这里说明一个关键原则：

- 节点完成是“状态变化”
- 边负责监听这个状态变化并决定去向
- runtime 通过“节点状态 + 边触发条件”推进流程

### 六、子流完成后如何反馈给主流程

在主流程里，`fe_subflow` 可以被视为一个“展开执行的节点”。它的内部子流走完后，不是直接跳到主流程的下一个业务节点，而是分两步回填：

#### 第一步：子流内部结束

当前端子流走到 `end`：
- 子流状态标记为 `completed`
- 子流内部 artifacts 固化
- 触发 `subflow.completed`

#### 第二步：通过返回边回填主流程

```yaml
- id: edge_fe_subflow_return
  type: subflow_return
  from: fe_subflow.end
  to: fe_subflow
  output_mapping:
    fe_deliverable: artifacts.fe_deliverable
  trigger: subflow.completed
```

runtime 收到这个返回边后：
- 把 `fe_deliverable` 写回父流程 artifacts
- 把父流程中的 `fe_subflow` 标记为 `completed`
- 发出 `SUBFLOW_COMPLETED(fe_subflow)`

然后主流程继续处理：
- 如果后端分支未完成，则停在 `join`
- 如果前后端都完成，则 `join` 节点满足条件
- 流程继续进入 `TL 汇总审查`

### 七、边模型带来的好处

当节点和边都结构化之后，我们就能获得这些能力：

- 可视化图能映射为可执行模型
- 流程推进不再依赖 Agent 自觉说明“下一步”
- 并行、回退、重试、审批都能统一建模
- 子流与主流程之间的衔接有明确机制
- runtime 可以做审计、回放、恢复、超时处理

### 当前结论

如果节点是“做什么”，那么边就是“何时推进、为什么推进、推进到哪里”。

因此，完整的工作流图元模型至少要同时定义两层：
- 节点模型：描述动作、门禁、子流、产物、状态
- 边模型：描述顺序、条件、事件、失败、循环、并行、返回

只有节点和边都结构化，流程图才能真正成为我们的 LLM 编排框架的一部分。

## 工作流文件整体 Schema：如何把节点、边和运行时对象组织成一份定义

当节点模型和边模型都确定之后，下一步就不是继续画图，而是要定义：**一份工作流文件到底长什么样。**

这份文件的目标不是单纯存图，而是作为 runtime 的输入，能够完整描述：

- 这是哪个工作流
- 它适用于哪个阶段
- 包含哪些节点和边
- 涉及哪些 artifacts / stores / events
- 需要哪些权限和默认规则
- 子流程如何引用
- 运行时从哪里开始、如何结束、如何恢复

也就是说，这份 Schema 是“图模型”和“运行时执行模型”之间的桥梁。

### 一、建议的顶层结构

建议一份工作流文件至少包含这些顶层字段：

| 字段 | 含义 |
|------|------|
| `workflow` | 工作流基本信息 |
| `scope` | 适用范围，如阶段、项目规模、需求类型 |
| `roles` | 该工作流涉及的角色 |
| `artifacts` | 该工作流中使用和产出的结构化对象 |
| `stores` | 运行时状态与持久化对象 |
| `events` | 该工作流关心的事件类型 |
| `nodes` | 节点定义 |
| `edges` | 边定义 |
| `permissions` | 工作流级默认权限策略 |
| `runtime` | 运行时配置 |
| `subflows` | 子流程引用表 |

### 二、顶层字段说明

#### 1. `workflow`

描述工作流本身的身份信息。

建议字段：
- `id`
- `name`
- `version`
- `description`
- `stage`
- `owner`

示例：

```yaml
workflow:
  id: iterative_development_main
  name: "迭代开发主流程"
  version: 1
  description: "用于任务拆解后前后端并行开发、审查和测试的主流程"
  stage: ITERATIVE_DEVELOPMENT
  owner: system
```

#### 2. `scope`

描述这个工作流适用于什么上下文。

建议字段：
- `project_types`
- `sizes`
- `entry_conditions`
- `exit_conditions`

示例：

```yaml
scope:
  project_types: [new_project, enhancement]
  sizes: [small, medium, large]
  entry_conditions:
    - prd_final_approved
    - task_cards_created
  exit_conditions:
    - all_tasks_completed
    - review_passed
```

#### 3. `roles`

声明工作流中允许出现哪些角色，以及它们在该工作流中的职责。

建议字段：
- `id`
- `role_template`
- `required`
- `responsibilities`

#### 4. `artifacts`

声明该工作流会读写哪些结构化产物。

建议字段：
- `id`
- `schema`
- `producer`
- `consumers`
- `path`
- `required`

示例：

```yaml
artifacts:
  - id: fe_deliverable
    schema: FE_DELIVERABLE_SCHEMA
    producer: frontend-dev
    consumers: [tech-lead, tester]
    path: artifacts/frontend/
    required: true

  - id: be_deliverable
    schema: BE_DELIVERABLE_SCHEMA
    producer: backend-dev
    consumers: [tech-lead, tester]
    path: artifacts/backend/
    required: true
```

#### 5. `stores`

声明运行时会使用哪些状态对象和存储。

建议字段：
- `id`
- `store_ref`
- `mode`
- `persistence`

示例：

```yaml
stores:
  - id: project_state
    store_ref: project-state.yaml
    mode: read_write
    persistence: persistent

  - id: snapshot_store
    store_ref: .snapshot/
    mode: write
    persistence: persistent
```

#### 6. `events`

声明该工作流中会监听或发出的事件。

建议字段：
- `name`
- `source`
- `payload_schema`
- `direction` (`emit` / `listen` / `both`)

示例：

```yaml
events:
  - name: TASK_ASSIGNED
    source: daemon
    payload_schema: TASK_ASSIGNED_SCHEMA
    direction: listen

  - name: FE_DELIVERABLE_SUBMITTED
    source: frontend-dev
    payload_schema: FE_DELIVERABLE_SCHEMA
    direction: both
```

#### 7. `permissions`

定义工作流级默认权限策略，用于在 role template 权限之外再做一层收缩。

建议字段：
- `default_tools`
- `forbidden_tools`
- `path_overrides`
- `node_overrides`

这里的作用是：**角色模板定义“通常可以做什么”，工作流定义“在这个流程里暂时允许做什么”。**

#### 8. `runtime`

定义运行时行为。

建议字段：
- `start_node`
- `end_nodes`
- `timeout_policy`
- `retry_policy`
- `checkpoint_policy`
- `concurrency`
- `resume_strategy`

示例：

```yaml
runtime:
  start_node: dev_fork
  end_nodes: [workflow_end]
  timeout_policy:
    default: 2d
  retry_policy:
    max_retries: 3
  checkpoint_policy:
    on_node_completed: true
    on_subflow_completed: true
  concurrency:
    enabled: true
  resume_strategy: from_last_checkpoint
```

#### 9. `subflows`

统一登记本工作流引用的子流程。

建议字段：
- `id`
- `workflow_ref`
- `description`
- `version`

### 三、完整示意结构

下面给一个简化后的整体示意：

```yaml
workflow:
  id: iterative_development_main
  name: "迭代开发主流程"
  version: 1
  description: "前后端并行开发并汇总审查"
  stage: ITERATIVE_DEVELOPMENT
  owner: system

scope:
  project_types: [enhancement]
  sizes: [medium]
  entry_conditions: [prd_final_approved, task_cards_created]
  exit_conditions: [all_tasks_completed, test_passed]

roles:
  - id: tech-lead
    role_template: tech-lead
    required: true
    responsibilities: [task_split, review]
  - id: frontend-dev
    role_template: frontend-developer
    required: true
    responsibilities: [frontend_impl]
  - id: backend-dev
    role_template: backend-developer
    required: true
    responsibilities: [backend_impl]
  - id: tester
    role_template: tester
    required: true
    responsibilities: [verification]

artifacts:
  - id: fe_deliverable
    schema: FE_DELIVERABLE_SCHEMA
    producer: frontend-dev
    consumers: [tech-lead, tester]
    path: artifacts/frontend/
    required: true
  - id: be_deliverable
    schema: BE_DELIVERABLE_SCHEMA
    producer: backend-dev
    consumers: [tech-lead, tester]
    path: artifacts/backend/
    required: true

stores:
  - id: project_state
    store_ref: project-state.yaml
    mode: read_write
    persistence: persistent

events:
  - name: FE_DELIVERABLE_SUBMITTED
    source: frontend-dev
    payload_schema: FE_DELIVERABLE_SCHEMA
    direction: both
  - name: BE_DELIVERABLE_SUBMITTED
    source: backend-dev
    payload_schema: BE_DELIVERABLE_SCHEMA
    direction: both

permissions:
  default_tools: [read_code, read_docs]
  forbidden_tools: [deploy_prod, merge_main]
  node_overrides:
    fe_implement:
      allow: [edit_code, run_test]
    tl_review:
      allow: [read_code, write_docs]

runtime:
  start_node: dev_fork
  end_nodes: [workflow_end]
  timeout_policy:
    default: 2d
  retry_policy:
    max_retries: 3
  checkpoint_policy:
    on_node_completed: true
  concurrency:
    enabled: true
  resume_strategy: from_last_checkpoint

subflows:
  - id: frontend_task_execution
    workflow_ref: frontend_task_execution
    description: "前端单任务执行子流程"
    version: 1
  - id: backend_task_execution
    workflow_ref: backend_task_execution
    description: "后端单任务执行子流程"
    version: 1

nodes:
  - id: dev_fork
    type: fork
    name: "并行开发开始"
    stage: ITERATIVE_DEVELOPMENT
    lane: daemon
    input: [task_cards]
    output: []
    next: []
    on_fail: blocked
    status: pending
    description: "分叉前后端开发分支"

  - id: fe_subflow
    type: subflow
    name: "前端任务子流"
    stage: ITERATIVE_DEVELOPMENT
    lane: frontend-dev
    actor: frontend-dev
    workflow_ref: frontend_task_execution
    input: [task_card, ui_spec, api_spec]
    output: [fe_deliverable]
    input_mapping:
      task_card: TASK-FE-013
      ui_spec: UI-SPEC-02
      api_spec: API-SPEC-05
    output_mapping:
      fe_deliverable: artifacts.fe_deliverable
    completion_rule:
      - subflow.status == completed
    next: impl_join
    on_fail: blocked
    status: pending
    description: "执行前端任务"

  - id: impl_join
    type: join
    name: "并行汇合"
    stage: ITERATIVE_DEVELOPMENT
    lane: daemon
    input: [fe_deliverable, be_deliverable]
    output: [merged_deliverables]
    wait_for: [fe_subflow, be_subflow]
    merge_rule: all_completed
    next: tl_review
    on_fail: blocked
    status: pending
    description: "等待前后端交付都完成"

edges:
  - id: edge_fork_fe
    type: fork_branch
    from: dev_fork
    to: fe_subflow
    label: "前端分支"
    trigger: dev_fork.completed
    priority: 10
    guard: null
    status: enabled
    description: "启动前端子流"

  - id: edge_fe_to_join
    type: join_branch
    from: fe_subflow
    to: impl_join
    label: "前端完成并汇合"
    trigger: fe_subflow.completed
    priority: 10
    guard: null
    status: enabled
    description: "前端分支汇合"
```

### 四、为什么需要整体 Schema

如果只有节点和边，系统仍然缺少很多上下文：

- 这个工作流适用于什么项目
- 哪些角色必须在场
- 哪些 artifacts 是强制产物
- 哪些事件需要监听
- 当前流程允许哪些工具
- 子流程从哪里引用
- 如何 checkpoint 和恢复

整体 Schema 的价值就在于：**把图结构、角色约束、事件系统、存储对象、运行时策略统一放进一个可加载的定义里。**

### 五、当前建议

后续如果继续细化，我建议再分成两步：

1. 先把这份整体 Schema 固定成“第一版规范”
2. 再从这份规范中挑一个阶段，比如“阶段 1 需求理解”或“阶段 3 单任务开发”，写出一份完整实例

这样我们就不只是讨论抽象概念，而是能开始验证：
- 这套 Schema 是否足够表达真实流程
- runtime 是否能依据它推进 Agent 协作
- 哪些字段其实是冗余的，哪些字段还不够

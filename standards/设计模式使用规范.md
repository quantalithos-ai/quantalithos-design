# 设计模式实用指南

> 模式不是目标，问题才是起点。
> 不要为了用模式而用模式，要先识别痛点再选最小解法。

---

## 一、什么情况下才该考虑设计模式？

### 1.1 三条黄金法则

| 法则 | 说明 |
|------|------|
| **有真实痛点，才有模式** | 代码已经出现了可触碰的问题（重复、膨胀、耦合、难以扩展），而不是"将来可能" |
| **简单方案先试** | 如果 if/else、普通函数、直接组合已经够清晰，就不要上模式 |
| **团队能理解** | 模式的价值在于沟通共识；如果团队看不懂，它就是技术债 |

### 1.2 该用 vs 不该用的信号

```
✅ 该考虑引入模式                          ❌ 不该用模式
─────────────────────────────────        ─────────────────────────────────
同一类 if/else 出现 3+ 处且持续增长        只有 2 个分支且不会增长
构造一个对象需要 5+ 个参数且部分可选         3~4 个稳定参数，直接构造即可
新增一种策略要改 5 个文件                   新增功能只需改 1~2 处
两个模块互相依赖无法独立测试                模块间依赖简单，测试无障碍
子类数量爆炸，且仅因某一个小维度不同          继承层次浅且稳定（2~3 层）
跨服务事务一致性出问题                      单进程内逻辑简单清晰
```

### 1.3 反模式清单

- 🚫 **模式驱动设计**：看到代码就问"这里该用什么模式"
- 🚫 **过度抽象**：2 个分支也要上策略 + 工厂 + 注册表
- 🚫 **只会背定义**：能说出 23 种模式的名字，却说不清当前问题是什么
- 🚫 **把分布式问题误当类设计问题**：跨服务一致性不是观察者能解决的

## 二、创建型模式

> 核心问题：**对象创建太复杂、变体太多、构造过程不稳定**

### 2.1 工厂方法（Factory Method）

**场景**：你需要创建对象，但不希望调用方依赖具体类。

典型信号：
- `if type == "A" then new ConcreteA() else new ConcreteB()` 在多处出现
- 未来可能增加新的类型，且不想每次都改调用方

```
┌──────────┐      create()       ┌──────────────┐
│  Creator  │ ──────────────────> │   Product     │  (interface)
└──────────┘                     └──────────────┘
      ▲                                ▲
      │                                │
┌──────────────┐              ┌────────────────┐
│ConcreteCreator│              │ConcreteProduct │
│  create() →   │─────────────>│                │
│  new ConcrPrd │              └────────────────┘
└──────────────┘
```

**Rust demo**：

```rust
trait Product {
    fn name(&self) -> &str;
}

struct ProductA;
struct ProductB;

impl Product for ProductA {
    fn name(&self) -> &str { "A" }
}
impl Product for ProductB {
    fn name(&self) -> &str { "B" }
}

trait Creator {
    fn create(&self) -> Box<dyn Product>;
}

struct CreatorA;
struct CreatorB;

impl Creator for CreatorA {
    fn create(&self) -> Box<dyn Product> { Box::new(ProductA) }
}
impl Creator for CreatorB {
    fn create(&self) -> Box<dyn Product> { Box::new(ProductB) }
}

fn main() {
    let creator: Box<dyn Creator> = Box::new(CreatorA);
    let product = creator.create();
    println!("{}", product.name()); // A
}
```

**Python demo**：

```python
from abc import ABC, abstractmethod

class Product(ABC):
    @abstractmethod
    def name(self) -> str: ...

class ProductA(Product):
    def name(self) -> str: return "A"

class ProductB(Product):
    def name(self) -> str: return "B"

class Creator(ABC):
    @abstractmethod
    def create(self) -> Product: ...

class CreatorA(Creator):
    def create(self) -> Product: return ProductA()

class CreatorB(Creator):
    def create(self) -> Product: return ProductB()
```

**何时不用**：类型只有 1~2 种且非常稳定，直接构造即可。

### 2.2 抽象工厂（Abstract Factory）

**场景**：需要创建**一组相关对象**，且这组对象必须搭配使用（如不同主题的 UI 组件）。

典型信号：
- 创建 A 时必须同时创建配套的 B，否则语义不一致
- 有多套"产品族"，运行时切换整套

```
┌─────────────────┐
│  AbstractFactory │
│  + create_btn()  │
│  + create_input()│
└────────┬────────┘
         │
    ┌────┴─────┐
    ▼          ▼
┌────────┐ ┌──────────┐
│ Light  │ │  Dark    │     各返回一整套配套组件
│Factory │ │ Factory  │
└────────┘ └──────────┘
```

**Rust demo**：

```rust
trait Button { fn render(&self); }
trait Input  { fn render(&self); }

struct LightButton;
struct DarkButton;
struct LightInput;
struct DarkInput;

impl Button for LightButton { fn render(&self) { println!("light button"); } }
impl Button for DarkButton  { fn render(&self) { println!("dark button"); } }
impl Input  for LightInput  { fn render(&self) { println!("light input"); } }
impl Input  for DarkInput   { fn render(&self) { println!("dark input"); } }

trait UiFactory {
    fn create_button(&self) -> Box<dyn Button>;
    fn create_input(&self) -> Box<dyn Input>;
}

struct LightFactory;
struct DarkFactory;

impl UiFactory for LightFactory {
    fn create_button(&self) -> Box<dyn Button> { Box::new(LightButton) }
    fn create_input(&self)  -> Box<dyn Input>  { Box::new(LightInput) }
}
impl UiFactory for DarkFactory {
    fn create_button(&self) -> Box<dyn Button> { Box::new(DarkButton) }
    fn create_input(&self)  -> Box<dyn Input>  { Box::new(DarkInput) }
}

fn build_ui(factory: &dyn UiFactory) {
    factory.create_button().render();
    factory.create_input().render();
}
```

**何时不用**：产品族只有 1 套，或组件之间没有搭配约束。

### 2.3 建造者（Builder）

**场景**：构造函数参数太多（5+），且部分可选、部分有依赖关系。

典型信号：
- `new Config(host, port, timeout, retry, pool_size, ssl, ...)`
- 参数之间有约束（如设了 ssl 就必须设 cert_path）

```
Director (可选)
    │
    │  build_step_a()
    │  build_step_b()
    │  build_step_c()
    ▼
 Builder ──────> Product
```

**Python demo**：

```python
class ServerConfig:
    def __init__(self):
        self.host: str = "localhost"
        self.port: int = 8080
        self.timeout: int = 30
        self.ssl: bool = False

class ServerConfigBuilder:
    def __init__(self):
        self._config = ServerConfig()

    def host(self, host: str) -> "ServerConfigBuilder":
        self._config.host = host
        return self

    def port(self, port: int) -> "ServerConfigBuilder":
        self._config.port = port
        return self

    def timeout(self, t: int) -> "ServerConfigBuilder":
        self._config.timeout = t
        return self

    def enable_ssl(self) -> "ServerConfigBuilder":
        self._config.ssl = True
        return self

    def build(self) -> ServerConfig:
        return self._config

# 使用
cfg = ServerConfigBuilder().host("api.example.com").port(443).enable_ssl().build()
```

**Rust demo**：

```rust
struct ServerConfig {
    host: String,
    port: u16,
    timeout: u64,
    ssl: bool,
}

impl ServerConfig {
    fn builder() -> ServerConfigBuilder {
        ServerConfigBuilder {
            host: "localhost".into(),
            port: 8080,
            timeout: 30,
            ssl: false,
        }
    }
}

struct ServerConfigBuilder {
    host: String,
    port: u16,
    timeout: u64,
    ssl: bool,
}

impl ServerConfigBuilder {
    fn host(mut self, host: &str) -> Self { self.host = host.into(); self }
    fn port(mut self, port: u16) -> Self   { self.port = port; self }
    fn timeout(mut self, t: u64) -> Self   { self.timeout = t; self }
    fn ssl(mut self) -> Self               { self.ssl = true; self }
    fn build(self) -> ServerConfig {
        ServerConfig {
            host: self.host, port: self.port,
            timeout: self.timeout, ssl: self.ssl,
        }
    }
}

// 使用
let cfg = ServerConfig::builder()
    .host("api.example.com")
    .port(443)
    .ssl()
    .build();
```

**何时不用**：参数只有 3~4 个且稳定，直接构造或用参数对象即可。

### 2.4 单例（Singleton）

**场景**：全局只需要一个实例，且需要延迟初始化。

典型信号：
- 配置对象、日志管理器、连接池——全局共享且只应有一份

```
┌─────────────────────┐
│     Singleton        │
│  ─────────────────── │
│  - instance: Self    │
│  + get() → &Self     │
│  (私有构造)           │
└─────────────────────┘
```

**Rust demo**（使用 `std::sync::OnceLock`）：

```rust
use std::sync::OnceLock;

struct DatabasePool {
    url: String,
}

static POOL: OnceLock<DatabasePool> = OnceLock::new();

impl DatabasePool {
    fn get() -> &'static DatabasePool {
        POOL.get_or_init(|| DatabasePool {
            url: "postgres://localhost/mydb".into(),
        })
    }
}
```

**Python demo**：

```python
class DatabasePool:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance.url = "postgres://localhost/mydb"
        return cls._instance

pool1 = DatabasePool()
pool2 = DatabasePool()
assert pool1 is pool2
```

**何时不用**：
- 只是为了"方便传参"而用全局单例 → 应该用依赖注入
- 多线程需要各自独立实例 → 不要用单例
- **单例是最容易被滥用的模式**，大部分场景用依赖注入替代更好

### 2.5 原型（Prototype）

**场景**：创建新对象成本高（深拷贝复杂结构），通过克隆已有对象来创建。

典型信号：
- 对象有大量嵌套字段，手动构造太繁琐
- 运行时需要"基于当前状态再改一改"来创建新对象

**Python demo**（利用 `copy` 模块）：

```python
import copy

class Template:
    def __init__(self, name: str, config: dict):
        self.name = name
        self.config = config

    def clone(self) -> "Template":
        return copy.deepcopy(self)

original = Template("base", {"timeout": 30, "retry": 3})
variant = original.clone()
variant.name = "custom"
variant.config["timeout"] = 60
```

**Rust demo**（利用 `Clone` trait）：

```rust
#[derive(Clone)]
struct Template {
    name: String,
    config: Config,
}

#[derive(Clone)]
struct Config {
    timeout: u64,
    retry: u32,
}

let original = Template { name: "base".into(), config: Config { timeout: 30, retry: 3 } };
let variant = original.clone();
```

**何时不用**：对象结构简单，直接 new 即可，克隆反而增加认知负担。

## 三、结构型模式

> 核心问题：**接口不兼容、想扩展功能但不改原类、子系统太复杂**

### 3.1 适配器（Adapter）

**场景**：两个接口天然不兼容，但必须协作。

典型信号：
- 引入第三方库，它的接口和你内部的接口不一致
- 你只控制其中一边的代码

```
┌──────────┐     期望的接口      ┌──────────┐
│  Client   │ ────────────────> │  Target   │
└──────────┘                    └────┬─────┘
                                     │ implements
                                ┌────┴─────┐
                                │ Adapter   │ ── 内部持有 Adaptee
                                └──────────┘
                                     │
                                ┌────┴─────┐
                                │ Adaptee   │  (第三方不可改的接口)
                                └──────────┘
```

**Python demo**：

```python
class OldPrinter:
    def print_text(self, text: str):
        print(f"[old] {text}")

class NewPrinterInterface:
    def print_document(self, doc: dict): ...

class PrinterAdapter(NewPrinterInterface):
    def __init__(self, old: OldPrinter):
        self._old = old

    def print_document(self, doc: dict):
        self._old.print_text(doc.get("content", ""))

adapter = PrinterAdapter(OldPrinter())
adapter.print_document({"content": "hello"})  # [old] hello
```

**Rust demo**：

```rust
trait Target {
    fn request(&self) -> String;
}

struct Adaptee;

impl Adaptee {
    fn specific_request(&self) -> String {
        String::from("legacy data")
    }
}

struct Adapter {
    adaptee: Adaptee,
}

impl Target for Adapter {
    fn request(&self) -> String {
        // 转换接口
        self.adaptee.specific_request()
    }
}
```

**何时不用**：如果你同时控制两边接口，优先直接统一接口，不要加适配层。

### 3.2 装饰器（Decorator）

**场景**：需要在不修改原类的情况下**动态叠加职责**。

典型信号：
- 用继承会产生子类爆炸（维度 × 变体）
- 职责可以自由组合（如压缩 + 加密 + 日志）

```
┌───────────────────┐
│   Component       │  ← 统一接口
│   + operation()   │
└────────┬──────────┘
         │
    ┌────┴─────────────┐
    ▼                  ▼
┌──────────┐   ┌──────────────┐
│Concrete  │   │  Decorator   │ ── 也实现 Component
│Component │   │  + wrapped   │ ── 内部持有 Component
└──────────┘   └──────┬───────┘
                      │
              ┌───────┴────────┐
              ▼                ▼
        ┌──────────┐    ┌──────────┐
        │ Compress │    │ Encrypt  │  ← 可无限嵌套
        │ Decorator│    │ Decorator│
        └──────────┘    └──────────┘
```

**Python demo**：

```python
class DataSource:
    def read(self) -> str: ...
    def write(self, data: str): ...

class FileDataSource(DataSource):
    def __init__(self, name: str):
        self.name = name

    def read(self) -> str:
        return f"data from {self.name}"

    def write(self, data: str):
        print(f"writing '{data}' to {self.name}")


class DataSourceDecorator(DataSource):
    def __init__(self, inner: DataSource):
        self._inner = inner

    def read(self) -> str:
        return self._inner.read()

    def write(self, data: str):
        self._inner.write(data)


class EncryptionDecorator(DataSourceDecorator):
    def write(self, data: str):
        encrypted = f"[encrypted({data})]"
        self._inner.write(encrypted)

    def read(self) -> str:
        data = self._inner.read()
        return f"[decrypted from {data}]"


class CompressionDecorator(DataSourceDecorator):
    def write(self, data: str):
        compressed = f"[compressed({data})]"
        self._inner.write(compressed)

# 使用 —— 自由组合
source = CompressionDecorator(EncryptionDecorator(FileDataSource("log.txt")))
source.write("hello world")
# writing '[compressed([encrypted(hello world)])]' to log.txt
```

**Rust demo**：

```rust
trait DataSource {
    fn read(&self) -> String;
    fn write(&self, data: &str);
}

struct FileDataSource {
    name: String,
}

impl DataSource for FileDataSource {
    fn read(&self) -> String { format!("data from {}", self.name) }
    fn write(&self, data: &str) { println!("writing '{}' to {}", data, self.name); }
}

struct EncryptionDecorator<T: DataSource> {
    inner: T,
}

impl<T: DataSource> DataSource for EncryptionDecorator<T> {
    fn read(&self) -> String {
        format!("[decrypted from {}]", self.inner.read())
    }
    fn write(&self, data: &str) {
        self.inner.write(&format!("[encrypted({})]", data));
    }
}

struct CompressionDecorator<T: DataSource> {
    inner: T,
}

impl<T: DataSource> DataSource for CompressionDecorator<T> {
    fn read(&self) -> String {
        let data = self.inner.read();
        format!("[decompressed from {}]", data)
    }
    fn write(&self, data: &str) {
        self.inner.write(&format!("[compressed({})]", data));
    }
}

// 使用
let source = CompressionDecorator {
    inner: EncryptionDecorator {
        inner: FileDataSource { name: "log.txt".into() },
    },
};
source.write("hello world");
```

**何时不用**：只有单一扩展路径，子类或组合更简单。

### 3.3 门面（Facade）

**场景**：复杂子系统暴露给上层使用很困难，需要一个简化的统一入口。

典型信号：
- 调用一个功能要依次操作 5 个子模块
- 上层只需要"做这件事"，不关心内部步骤

```
┌────────┐         ┌──────────────────────────┐
│ Client │ ──────> │       Facade             │
└────────┘         │  simplified_operation()  │
                   └────┬──┬──┬───────────────┘
                        │  │  │
              ┌─────────┘  │  └─────────┐
              ▼            ▼            ▼
         ┌────────┐  ┌────────┐  ┌────────┐
         │Sub A   │  │Sub B   │  │Sub C   │
         └────────┘  └────────┘  └────────┘
```

**Python demo**：

```python
class VideoConverter:
    """门面：一行代码完成 视频读取 → 格式转换 → 音频提取 → 写出"""
    def convert(self, filename: str, target_format: str) -> str:
        video = VideoFile.read(filename)
        audio = AudioExtractor.extract(video)
        converted = CodecFactory.create(target_format).encode(video, audio)
        return FileWriter.write(converted)

# 客户端：不需要知道内部的 4 个步骤
converter = VideoConverter()
converter.convert("funny.avi", "mp4")
```

**何时不用**：子系统本身已经足够简单。

### 3.4 代理（Proxy）

**场景**：需要控制对另一个对象的访问（延迟加载、权限检查、远程调用）。

典型信号：
- 对象创建成本高，希望用的时候才创建（虚拟代理）
- 需要在访问前后加控制逻辑（保护代理 / 智能代理）

```
┌──────────┐       ┌──────────┐       ┌──────────────┐
│  Client   │ ───> │  Proxy   │ ───> │  RealSubject  │
└──────────┘       └──────────┘       └──────────────┘
                    (控制访问)
```

**Rust demo**（延迟加载代理）：

```rust
trait Image {
    fn display(&self);
}

struct RealImage {
    filename: String,
}

impl RealImage {
    fn new(filename: &str) -> Self {
        println!("Loading image from disk: {}", filename);
        Self { filename: filename.into() }
    }
}

impl Image for RealImage {
    fn display(&self) {
        println!("Displaying {}", self.filename);
    }
}

struct ImageProxy {
    filename: String,
    real: Option<RealImage>,  // 延迟到首次 display 才加载
}

impl ImageProxy {
    fn new(filename: &str) -> Self {
        Self { filename: filename.into(), real: None }
    }
}

impl Image for ImageProxy {
    fn display(&mut self) {
        if self.real.is_none() {
            self.real = Some(RealImage::new(&self.filename));
        }
        self.real.as_ref().unwrap().display();
    }
}
```

**何时不用**：不需要任何访问控制或延迟加载，直接引用即可。

### 3.5 组合（Composite）

**场景**：需要一致地对待"单个对象"和"对象组合"（树形结构）。

典型信号：
- 有"部分-整体"层次结构（文件系统、组织架构、UI 组件树）
- 客户端不想区分"叶子"和"容器"

```
         ┌──────────────┐
         │  Component   │
         │ + operation()│
         └──────┬───────┘
           ┌────┴────┐
           ▼         ▼
    ┌───────────┐  ┌───────────┐
    │   Leaf    │  │ Composite │── children: Vec<Component>
    └───────────┘  └───────────┘
```

**Rust demo**：

```rust
trait Node {
    fn print(&self, indent: usize);
}

struct File { name: String }

impl Node for File {
    fn print(&self, indent: usize) {
        println!("{}- {}", " ".repeat(indent), self.name);
    }
}

struct Folder { name: String, children: Vec<Box<dyn Node>> }

impl Node for Folder {
    fn print(&self, indent: usize) {
        println!("{}+ {}", " ".repeat(indent), self.name);
        for child in &self.children {
            child.print(indent + 2);
        }
    }
}

// 使用
let root = Folder {
    name: "src".into(),
    children: vec![
        Box::new(File { name: "main.rs".into() }),
        Box::new(Folder {
            name: "utils".into(),
            children: vec![
                Box::new(File { name: "mod.rs".into() }),
            ],
        }),
    ],
};
root.print(0);
```

**何时不用**：结构是扁平的，不存在嵌套。

### 3.6 桥接（Bridge）

**场景**：一个类有**两个独立变化的维度**，用继承会导致子类爆炸。

典型信号：
- `Shape + Color` → 不想创建 `RedCircle`, `BlueCircle`, `RedSquare`, `BlueSquare`...
- 两个维度可以独立扩展

```
┌──────────┐        ┌──────────────┐
│ Abstraction│──────>│ Implementor  │
│ (Shape)    │       │ (Renderer)   │
└─────┬──────┘       └──────┬───────┘
      │                     │
 ┌────┴────┐          ┌────┴────┐
 ▼         ▼          ▼         ▼
Circle   Square    Vector    Raster
```

**Python demo**：

```python
from abc import ABC, abstractmethod

class Renderer(ABC):
    @abstractmethod
    def render_circle(self, radius: float): ...

class VectorRenderer(Renderer):
    def render_circle(self, radius: float):
        print(f"Drawing a circle of radius {radius} (vector)")

class RasterRenderer(Renderer):
    def render_circle(self, radius: float):
        print(f"Drawing a circle of radius {radius} (raster/pixels)")

class Shape:
    def __init__(self, renderer: Renderer):
        self.renderer = renderer

class Circle(Shape):
    def __init__(self, renderer: Renderer, radius: float):
        super().__init__(renderer)
        self.radius = radius

    def draw(self):
        self.renderer.render_circle(self.radius)

# 使用 —— 2×2 组合，不需要 4 个子类
Circle(VectorRenderer(), 5).draw()   # vector
Circle(RasterRenderer(), 5).draw()   # raster
```

**何时不用**：只有单一变化维度，不需要拆桥。

---

### 3.7 享元（Flyweight）

**场景**：大量细粒度对象导致内存爆炸，其中大部分状态可以共享。

典型信号：
- 创建了百万级相似对象（如棋盘上的棋子、文本中的字符）
- 对象的大部分状态是**内在的**（可共享），只有少部分是**外在的**（需单独持有）

**Rust demo**：

```rust
use std::collections::HashMap;

// 内在状态：可共享
#[derive(Clone)]
struct TreeType {
    name: String,
    color: String,
}

// 享元工厂
struct TreeFactory {
    types: HashMap<String, TreeType>,
}

impl TreeFactory {
    fn get(&mut self, name: &str) -> TreeType {
        self.types.entry(name.to_string())
            .or_insert_with(|| TreeType { name: name.into(), color: "green".into() })
            .clone()
    }
}

// 外在状态：每棵树的位置不同
struct Tree {
    x: i32,
    y: i32,
    tree_type: TreeType,  // 共享的内在状态
}

// 100 万棵树，只有 3 种 TreeType，大幅节省内存
```

**何时不用**：对象数量不多，或每个对象状态都不同，无法共享。

---

## 四、行为型模式

> 核心问题：**if/else 太多、算法可切换、对象间通信复杂**

### 4.1 策略（Strategy）⭐ 最常用

**场景**：运行时需要切换多种算法/策略，且算法可能继续增长。

典型信号：
- 同一类 if/else / match 出现在多个地方
- 新增一种策略要改多处代码

```
┌──────────┐         ┌──────────────┐
│  Context  │ ──────> │  Strategy    │  (interface)
│           │         │ + execute()  │
└──────────┘         └──────┬───────┘
                           ┌┴──────┬──────────┐
                           ▼       ▼          ▼
                      ┌────────┐┌────────┐┌────────┐
                      │  StrA  ││  StrB  ││  StrC  │
                      └────────┘└────────┘└────────┘
```

**Python demo**：

```python
from abc import ABC, abstractmethod

class PricingStrategy(ABC):
    @abstractmethod
    def calculate(self, price: float) -> float: ...

class RegularPricing(PricingStrategy):
    def calculate(self, price: float) -> float: return price

class DiscountPricing(PricingStrategy):
    def calculate(self, price: float) -> float: return price * 0.8

class VipPricing(PricingStrategy):
    def calculate(self, price: float) -> float: return price * 0.6

class Order:
    def __init__(self, strategy: PricingStrategy):
        self._strategy = strategy

    def set_strategy(self, strategy: PricingStrategy):
        self._strategy = strategy

    def checkout(self, price: float) -> float:
        return self._strategy.calculate(price)

order = Order(RegularPricing())
print(order.checkout(100))  # 100
order.set_strategy(VipPricing())
print(order.checkout(100))  # 60
```

**Rust demo**：

```rust
trait PricingStrategy {
    fn calculate(&self, price: f64) -> f64;
}

struct RegularPricing;
struct VipPricing;

impl PricingStrategy for RegularPricing {
    fn calculate(&self, price: f64) -> f64 { price }
}
impl PricingStrategy for VipPricing {
    fn calculate(&self, price: f64) -> f64 { price * 0.6 }
}

struct Order {
    strategy: Box<dyn PricingStrategy>,
}

impl Order {
    fn checkout(&self, price: f64) -> f64 {
        self.strategy.calculate(price)
    }
}
```

**何时不用**：只有 2 个分支且不会继续增长，普通 if/else 就行。

---

### 4.2 观察者（Observer）⭐ 最常用

**场景**：一个对象状态变化需要通知多个订阅者。

典型信号：
- "当 X 发生时，A、B、C 都需要做出反应"
- 订阅者数量和种类可能变化

```
┌──────────────┐    notify()    ┌──────────────┐
│   Subject    │ ─────────────> │   Observer    │
│ + attach()   │               │ + update()   │
│ + detach()   │         ┌─────┴──────────────┤
│ + notify()   │         ▼          ▼          ▼
└──────────────┘   ┌────────┐ ┌────────┐ ┌────────┐
                   │ Obs A  │ │ Obs B  │ │ Obs C  │
                   └────────┘ └────────┘ └────────┘
```

**Python demo**：

```python
from typing import Callable, List

class EventEmitter:
    def __init__(self):
        self._listeners: List[Callable] = []

    def on(self, callback: Callable):
        self._listeners.append(callback)

    def off(self, callback: Callable):
        self._listeners.remove(callback)

    def emit(self, *args, **kwargs):
        for cb in self._listeners:
            cb(*args, **kwargs)

# 使用
bus = EventEmitter()

bus.on(lambda data: print(f"Logger: {data}"))
bus.on(lambda data: print(f"Metrics: {data}"))

bus.emit("user_created")
# Logger: user_created
# Metrics: user_created
```

**Rust demo**：

```rust
type Listener = Box<dyn Fn(&str)>;

struct EventEmitter {
    listeners: Vec<Listener>,
}

impl EventEmitter {
    fn new() -> Self { Self { listeners: vec![] } }

    fn on(&mut self, listener: Listener) {
        self.listeners.push(listener);
    }

    fn emit(&self, data: &str) {
        for listener in &self.listeners {
            listener(data);
        }
    }
}

let mut bus = EventEmitter::new();
bus.on(Box::new(|data| println!("Logger: {}", data)));
bus.on(Box::new(|data| println!("Metrics: {}", data)));
bus.emit("user_created");
```

**何时不用**：跨进程、跨服务 → 用消息队列/Pub/Sub，而不是内存观察者。

### 4.3 命令（Command）

**场景**：命令需要排队、撤销、日志化，或者需要将"请求"本身当一等公民。

典型信号：
- 需要撤销/重做（编辑器操作）
- 需要延迟执行、排队执行（任务队列）

```
┌──────────┐  execute()   ┌──────────┐
│ Invoker  │ ───────────> │ Command  │ ──> Receiver
│ (按钮)   │  undo()      │ (操作对象)│
└──────────┘              └──────────┘
```

**Python demo**：

```python
from abc import ABC, abstractmethod

class Command(ABC):
    @abstractmethod
    def execute(self): ...
    @abstractmethod
    def undo(self): ...

class Light:
    def on(self):  print("light on")
    def off(self): print("light off")

class LightOnCommand(Command):
    def __init__(self, light: Light): self.light = light
    def execute(self): self.light.on()
    def undo(self):    self.light.off()

class RemoteControl:
    def __init__(self):
        self._history: list[Command] = []

    def press(self, cmd: Command):
        cmd.execute()
        self._history.append(cmd)

    def undo_last(self):
        if self._history:
            self._history.pop().undo()

light = Light()
remote = RemoteControl()
remote.press(LightOnCommand(light))  # light on
remote.undo_last()                    # light off
```

**何时不用**：不需要撤销/排队/日志，直接调用方法即可。

---

### 4.4 状态（State）

**场景**：对象的行为随内部状态变化而变化，且状态转换有明确规则。

典型信号：
- 大量 `if state == "X" ... elif state == "Y" ...` 散落在多个方法里
- 状态之间有合法的转换路径

```
┌──────────────────────────────────────┐
│             Context                  │
│  ─────────────────────────────────── │
│  state: State                        │
│  + request() → state.handle()       │
└────────────────┬─────────────────────┘
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
  ┌────────┐┌────────┐┌────────┐
  │StateA  ││StateB  ││StateC  │
  │handle()││handle()││handle()│
  └────────┘└────────┘└────────┘
```

**Python demo**：

```python
from abc import ABC, abstractmethod

class State(ABC):
    @abstractmethod
    def handle(self, context: "VendingMachine"): ...

class IdleState(State):
    def handle(self, context: "VendingMachine"):
        print("投入硬币...")
        context.state = HasCoinState()

class HasCoinState(State):
    def handle(self, context: "VendingMachine"):
        print("出货中...")
        context.state = IdleState()

class VendingMachine:
    def __init__(self):
        self.state: State = IdleState()

    def insert_coin_and_buy(self):
        self.state.handle(self)

vm = VendingMachine()
vm.insert_coin_and_buy()  # 投入硬币... 出货中...
vm.insert_coin_and_buy()  # 投入硬币... 出货中...
```

**何时不用**：状态只有 1~2 种，用简单枚举 + if 即可。

### 4.5 职责链（Chain of Responsibility）

**场景**：请求需要沿处理者链传递，让多个对象都有机会处理。

典型信号：
- "审批流"：经理 → 总监 → CEO
- "中间件链"：日志 → 鉴权 → 限流 → 业务
- 处理顺序可能变化，或某些环节可选

```
Handler A ──> Handler B ──> Handler C ──> (end)
   │              │              │
   ▼              ▼              ▼
 处理/传递      处理/传递      处理/传递
```

**Python demo**（中间件风格）：

```python
from typing import Callable, Optional

Handler = Callable[[str], Optional[str]]

def make_chain(*handlers: Handler) -> Handler:
    def chain(request: str) -> Optional[str]:
        for h in handlers:
            result = h(request)
            if result is not None:
                return result
        return None
    return chain

def auth_handler(req: str) -> Optional[str]:
    if "token" not in req:
        return "401 Unauthorized"
    return None  # 传递给下一个

def rate_limit_handler(req: str) -> Optional[str]:
    if "spam" in req:
        return "429 Too Many Requests"
    return None

def business_handler(req: str) -> Optional[str]:
    return f"200 OK: {req}"

pipeline = make_chain(auth_handler, rate_limit_handler, business_handler)

print(pipeline("hello"))         # 401 Unauthorized
print(pipeline("token+hello"))   # 200 OK: token+hello
print(pipeline("token+spam"))    # 429 Too Many Requests
```

**Rust demo**：

```rust
type Handler = Box<dyn Fn(&str) -> Option<String>>;

fn make_chain(handlers: Vec<Handler>) -> impl Fn(&str) -> Option<String> {
    move |req: &str| {
        for h in &handlers {
            if let Some(resp) = h(req) {
                return Some(resp);
            }
        }
        None
    }
}
```

**何时不用**：请求总是由固定一个处理器处理，不需要链式传递。

### 4.6 模板方法（Template Method）

**场景**：算法的整体步骤固定，但某些步骤的实现在子类中变化。

典型信号：
- 多个类有相同的执行骨架，只是个别步骤不同
- 想控制"先做什么再做什么"的顺序

```
┌─────────────────────────┐
│  AbstractClass           │
│  + template_method()    │  ← 固定步骤顺序
│    step_1()             │  ← 固定
│    step_2()  ← abstract │  ← 子类实现
│    step_3()             │  ← 固定
└──────────┬──────────────┘
           ▼
    ┌──────────────┐
    │ ConcreteClass│
    │  step_2()    │
    └──────────────┘
```

**Python demo**：

```python
from abc import ABC, abstractmethod

class DataMiner(ABC):
    def mine(self):  # 模板方法
        self.open_file()
        self.extract_data()
        self.parse_data()
        self.analyze()
        self.close_file()

    def open_file(self):  print("Opening file...")
    def close_file(self): print("Closing file...")
    def analyze(self):    print("Analyzing data...")

    @abstractmethod
    def extract_data(self): ...

    @abstractmethod
    def parse_data(self): ...

class PdfMiner(DataMiner):
    def extract_data(self): print("Extracting PDF text...")
    def parse_data(self):   print("Parsing PDF structure...")

class CsvMiner(DataMiner):
    def extract_data(self): print("Reading CSV rows...")
    def parse_data(self):   print("Parsing CSV fields...")

PdfMiner().mine()
```

**何时不用**：步骤顺序不固定，或不需要控制顺序。

---

### 4.7 中介者（Mediator）

**场景**：一组对象之间有复杂的网状交互，想将交互逻辑集中到一个中介对象。

典型信号：
- 对象 A 变化要通知 B、C、D，B 又要通知 E → 耦合越来越紧
- "谁和谁说话"的逻辑散落在各处

```
Before:                     After:
 A ←→ B                    ┌──────────┐
 ↕  ✕  ↕                   │ Mediator  │
 C ←→ D                    └──┬─┬─┬─┬──┘
                               │ │ │ │
                               A B C D  (各只和 Mediator 通信)
```

**Python demo**：

```python
class ChatRoom:
    """中介者：管理用户之间的消息路由"""
    def __init__(self):
        self._users: list["User"] = []

    def join(self, user: "User"):
        self._users.append(user)

    def broadcast(self, message: str, sender: "User"):
        for u in self._users:
            if u is not sender:
                u.receive(message)

class User:
    def __init__(self, name: str, room: ChatRoom):
        self.name = name
        self.room = room
        room.join(self)

    def send(self, message: str):
        self.room.broadcast(f"{self.name}: {message}", self)

    def receive(self, message: str):
        print(f"[{self.name} sees] {message}")

room = ChatRoom()
alice = User("Alice", room)
bob   = User("Bob", room)
alice.send("Hi everyone!")
# [Bob sees] Alice: Hi everyone!
```

**何时不用**：交互关系简单（1对1或少量），不需要中介。

---

### 4.8 迭代器（Iterator）

**场景**：需要遍历集合的内部元素，而不暴露其内部表示。

**Rust demo**（Rust 的 Iterator trait 就是该模式的原生实现）：

```rust
struct Countdown {
    count: u32,
}

impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.count == 0 { None }
        else { self.count -= 1; Some(self.count + 1) }
    }
}

for n in Countdown { count: 3 } {
    println!("{}", n);  // 3, 2, 1
}
```

**何时不用**：直接用语言内置的 for-each 即可，大部分语言已原生支持。

### 4.9 访问者（Visitor）

**场景**：需要在不改变对象结构的前提下，为元素增加新的操作。

典型信号：
- 有一组稳定的数据节点（如 AST），但操作经常新增（类型检查、代码生成、格式化...）
- 不想每次加操作都改所有节点类

**Python demo**：

```python
from abc import ABC, abstractmethod

class Visitor(ABC):
    @abstractmethod
    def visit_number(self, node: "Number"): ...
    @abstractmethod
    def visit_add(self, node: "Add"): ...

class Expr(ABC):
    @abstractmethod
    def accept(self, visitor: Visitor): ...

class Number(Expr):
    def __init__(self, value: float): self.value = value
    def accept(self, visitor: Visitor): visitor.visit_number(self)

class Add(Expr):
    def __init__(self, left: Expr, right: Expr):
        self.left = left; self.right = right
    def accept(self, visitor: Visitor): visitor.visit_add(self)

class Evaluator(Visitor):
    def visit_number(self, node: Number): return node.value
    def visit_add(self, node: Add):
        return node.left.accept(self) + node.right.accept(self)

class Printer(Visitor):
    def visit_number(self, node: Number): return str(node.value)
    def visit_add(self, node: Add):
        return f"({node.left.accept(self)} + {node.right.accept(self)})"

expr = Add(Number(1), Add(Number(2), Number(3)))
print(expr.accept(Evaluator()))  # 6
print(expr.accept(Printer()))    # (1 + (2 + 3))
```

**何时不用**：节点类型经常变化（加新节点就要改所有 Visitor）——此时 Visitor 反而增加负担。

---

### 4.10 备忘录（Memento）

**场景**：需要保存和恢复对象的内部状态（撤销、快照）。

**Python demo**：

```python
class EditorState:
    """备忘录：只存数据，不暴露给外部"""
    def __init__(self, content: str):
        self._content = content

    def get_content(self) -> str:
        return self._content

class Editor:
    def __init__(self):
        self._content = ""

    def type_text(self, text: str):
        self._content += text

    def save(self) -> EditorState:
        return EditorState(self._content)

    def restore(self, state: EditorState):
        self._content = state.get_content()

    def content(self) -> str:
        return self._content

editor = Editor()
editor.type_text("Hello ")
snapshot = editor.save()
editor.type_text("World")
print(editor.content())    # Hello World
editor.restore(snapshot)
print(editor.content())    # Hello
```

## 五、企业/分布式高频模式

> 不在 GoF 23 种之内，但企业开发中极常用。

### 5.1 仓储（Repository）

**场景**：将数据访问逻辑与领域逻辑隔离，让业务代码像操作集合一样操作持久化对象。

**Rust demo**：

```rust
trait UserRepository {
    fn find_by_id(&self, id: u64) -> Option<User>;
    fn save(&mut self, user: &User);
}

struct InMemoryUserRepository {
    users: std::collections::HashMap<u64, User>,
}

impl UserRepository for InMemoryUserRepository {
    fn find_by_id(&self, id: u64) -> Option<User> {
        self.users.get(&id).cloned()
    }
    fn save(&mut self, user: &User) {
        self.users.insert(user.id, user.clone());
    }
}
```

### 5.2 Saga（编排分布式事务）

**场景**：跨服务操作需要一致性，但不能使用单库事务。

```
Order Service     Payment Service     Inventory Service
    │                   │                     │
    │── create_order ──>│                     │
    │                   │── charge ──────────>│
    │                   │                     │── reserve ──✓
    │<── order_ok ──────│                     │
    │                   │                     │

如果 Payment 失败:
    │── cancel_order ──>│                     │
    │                   │── refund ──────────>│
    │                   │                     │── release ──✓
```

**关键**：每个步骤都要有**补偿操作**。

### 5.3 事务外盒（Transactional Outbox）

**场景**：业务数据和事件必须原子写入，但数据库和消息队列不是同一个事务。

```
┌─────────────────────────────┐
│  Application                │
│  1. BEGIN TX                │
│  2. INSERT order            │
│  3. INSERT outbox_event     │
│  4. COMMIT TX   ← 原子！    │
└─────────────────────────────┘
         │
         ▼ (异步轮询 / CDC 拖尾)
┌─────────────────────────────┐
│  Message Relay              │
│  5. SELECT from outbox      │
│  6. PUBLISH to MQ           │
│  7. DELETE from outbox      │
└─────────────────────────────┘
```

### 5.4 CQRS（命令查询职责分离）

**场景**：读写模型差异大（写需强一致性验证，读需灵活组合和高吞吐）。

```
                ┌──────────┐
    Command ──> │  Write    │ ──> Write DB
                │  Model    │
                └────┬─────┘
                     │ (事件同步)
                ┌────┴─────┐
    Query  ───> │  Read     │ ──> Read DB (可物化视图)
                │  Model    │
                └──────────┘
```

## 六、快速决策表

| 你遇到的问题 | 优先考虑 | 更简单的替代 |
|---|---|---|
| 运行时切换多种算法 | **Strategy** | 2 个分支且不增长 → if/else |
| 构造参数太多且部分可选 | **Builder** | 3~4 个稳定参数 → 直接构造 |
| 动态叠加职责 | **Decorator** | 单一扩展 → 子类/组合 |
| 状态变化通知多个订阅者 | **Observer** | 跨服务 → Pub/Sub / MQ |
| 两个接口不兼容但必须协作 | **Adapter** | 两边都能改 → 统一接口 |
| 复杂子系统需要简化入口 | **Facade** | — |
| 命令需要排队/撤销 | **Command** | 不需要撤销 → 直接调用 |
| 大量 if/else + 状态判断 | **State / Strategy** | 1~2 个状态 → 枚举 + if |
| 算法骨架固定、步骤可变 | **Template Method** | 步骤顺序不固定 → Strategy |
| 两个维度独立变化 | **Bridge** | 单一维度 → 不需要 |
| 大量相似对象内存爆炸 | **Flyweight** | 对象数量不多 → 不需要 |
| 网状交互需要解耦 | **Mediator** | 交互简单 → 直接通信 |
| 跨服务事务一致性 | **Saga + Outbox** | 单库事务即可 → 不需要 |
| 读写模型差异大 | **CQRS** | 读写简单 → 不需要 |
